      الإضافات (Plugins)

      لدى Hermes نظام إضافات لإضافة أدوات وhooks وتكاملات مخصصة دون تعديل الكود الأساسي.

      إذا كنت تريد إنشاء أداة مخصصة لنفسك، أو لفريقك، أو لمشروع واحد، فهذا هو المسار الصحيح عادةً. صفحة Adding Tools في دليل المطوّر مخصصة لأدوات Hermes الأساسية المدمجة التي تعيش في tools/ وtoolsets.py.

      → Build a Hermes Plugin — دليل تفصيلي مع مثال عملي كامل.

      نظرة سريعة​

      ضع مجلدًا في ~/.hermes/plugins/ يحتوي على plugin.yaml وكود Python:

      ~/.hermes/plugins/my-plugin/
      ├── plugin.yaml      # manifest
      ├── __init__.py      # register() — wires schemas to handlers
      ├── schemas.py       # tool schemas (what the LLM sees)
      └── tools.py         # tool handlers (what runs when called)

      شغّل Hermes — تظهر أدواتك جنبًا إلى جنب مع الأدوات المدمجة. يمكن للنموذج استدعاءها فورًا.

      مثال عملي بسيط​

      إليك إضافة كاملة تضيف أداة hello_world وتسجّل كل استدعاء أداة عبر hook.

      ~/.hermes/plugins/hello-world/plugin.yaml

      name: hello-world
      version: "1.0"
      description: A minimal example plugin

      ~/.hermes/plugins/hello-world/__init__.py

      """Minimal Hermes plugin — registers a tool and a hook."""

      import json


      def register(ctx):
          # --- Tool: hello_world ---
          schema = {
              "name": "hello_world",
              "description": "Returns a friendly greeting for the given name.",
              "parameters": {
                  "type": "object",
                  "properties": {
                      "name": {
                          "type": "string",
                          "description": "Name to greet",
                      }
                  },
                  "required": ["name"],
              },
          }

          def handle_hello(params, **kwargs):
              del kwargs
              name = params.get("name", "World")
              return json.dumps({"success": True, "greeting": f"Hello, {name}!"})

          ctx.register_tool(
              name="hello_world",
              toolset="hello_world",
              schema=schema,
              handler=handle_hello,
          )

          # --- Hook: log every tool call ---
          def on_tool_call(tool_name, params, result):
              print(f"[hello-world] tool called: {tool_name}")

          ctx.register_hook("post_tool_call", on_tool_call)

      ضع الملفين في ~/.hermes/plugins/hello-world/، وأعد تشغيل Hermes، ويصبح بإمكان النموذج استدعاء hello_world فورًا. يطبع الـ hook سطر سجلّ بعد كل استدعاء للأداة.

      وصف الأداة الموجّه للنموذج مكانه schema["description"]. أما قيمة ctx.register_tool(description=...) الاختيارية فهي بيانات وصفية منفصلة خاصة بسجلّ ToolEntry: عند إغفالها، تُستخدم القيمة الافتراضية من وصف الـ schema، لكن Hermes لا ينسخها مرة أخرى إلى schema يفتقر إلى description. يُفضَّل تعريف النص مرة واحدة في الـ schema. إن قدّمت القيمتين معًا، فحافظ على تطابقهما؛ فالنموذج يرى قيمة الـ schema.

      الإضافات المحلية للمشروع تحت ./.hermes/plugins/ مُعطَّلة افتراضيًا. فعّلها فقط للمستودعات الموثوقة عبر ضبط HERMES_ENABLE_PROJECT_PLUGINS=true قبل تشغيل Hermes.

      ما يمكن أن تفعله الإضافات​

      كل واجهة ctx.* أدناه متاحة داخل دالة register(ctx) الخاصة بالإضافة.

      الإمكانيةالطريقة
      إضافة أدواتctx.register_tool(name=..., toolset=..., schema=..., handler=...)
      إضافة hooksctx.register_hook("post_tool_call", callback)
      إضافة slash commandsctx.register_command(name, handler, description) — يضيف /name في جلسات CLI وgateway
      استدعاء أدوات من الأوامرctx.dispatch_tool(name, args) — يستدعي أداة مسجَّلة مع ربط تلقائي لسياق الوكيل الأصل
      إضافة أوامر CLIctx.register_cli_command(name, help, setup_fn, handler_fn) — يضيف hermes <plugin> <subcommand>
      حقن رسائلctx.inject_message(content, role="user", session_key=...) - راجع حقن الرسائل (Injecting Messages)
      شحن ملفات بياناتPath(__file__).parent / "data" / "file.yaml"
      تضمين مهاراتctx.register_skill(name, path) — يُسمّى بصيغة plugin:skill، ويُحمَّل عبر skill_view("plugin:skill")
      الاشتراط بمتغيرات البيئةrequires_env: [API_KEY] في plugin.yaml — يُطلَب أثناء hermes plugins install
      التوزيع عبر pip[project.entry-points."hermes_agent.plugins"]
      تسجيل منصة gateway (Discord، Telegram، IRC، …)ctx.register_platform(name, label, adapter_factory, check_fn, ...) — راجع Adding Platform Adapters
      تسجيل باكند لتوليد الصورctx.register_image_gen_provider(provider) — راجع إضافات مزوّدي توليد الصور
      تسجيل باكند لتوليد الفيديوctx.register_video_gen_provider(provider) — راجع إضافات مزوّدي توليد الفيديو
      تسجيل محرّك ضغط سياقctx.register_context_engine(engine) — راجع إضافات Context Engine
      تسجيل باكند تنفيذ طرفية (sandbox سحابي)ctx.register_terminal_environment_provider(provider) — راجع إضافات مزوّدي بيئة Terminal
      توجيه طلبات الموافقة البشريةctx.register_approval_transport(name, present_fn) — راجع وسائط الموافقة (Approval transports)
      تسجيل باكند ذاكرةاشتقاق فئة فرعية من MemoryProvider في plugins/memory/<name>/__init__.py — راجع إضافات مزوّدي الذاكرة (يستخدم نظام اكتشاف منفصل)
      تنفيذ استدعاء LLM يملكه المضيفctx.llm.complete(...) / ctx.llm.complete_structured(...) — يستعير نموذج المستخدم النشط ومصادقته لإتمام لمرة واحدة مع تحقّق اختياري من JSON schema. راجع وصول الإضافات إلى LLM
      استدعاء أداة MCP (مقيّد بإمكانية)ctx.call_mcp(server, tool, arguments, timeout=30) — راجع استدعاء خواديم MCP من الإضافات
      تسجيل باكند inference (مزوّد LLM)register_provider(ProviderProfile(...)) في plugins/model-providers/<name>/__init__.py — راجع إضافات مزوّدي النماذج (يستخدم نظام اكتشاف منفصل)

      اكتشاف الإضافات​

      المصدرالمسارحالة الاستخدام

      المستخدم~/.hermes/plugins/إضافات شخصية

      المصادر اللاحقة تُلغي السابقة عند تعارض الأسماء، فإضافة مستخدم بنفس اسم إضافة مدمجة تحلّ محلّها.

      الفئات الفرعية للإضافات​

      داخل كل مصدر، يتعرّف Hermes أيضًا على مجلدات فئات فرعية توجّه الإضافات إلى أنظمة اكتشاف متخصصة:

      المجلد الفرعيما يحتويهنظام الاكتشاف
      plugins/ (الجذر)إضافات عامة — أدوات، hooks، slash commands، أوامر CLI، مهارات مضمَّنةPluginManager (النوع: standalone أو backend)
      plugins/platforms/<name>/محوّلات قنوات gateway (ctx.register_platform())PluginManager (النوع: platform، بمستوى أعمق واحد)
      plugins/image_gen/<name>/باكندات توليد الصور (ctx.register_image_gen_provider())PluginManager (النوع: backend، بمستوى أعمق واحد)
      plugins/memory/<name>/مزوّدو ذاكرة (اشتقاق فئة فرعية من MemoryProvider)محمّل خاص في plugins/memory/__init__.py (النوع: exclusive — واحد فعّال في كل مرة)
      plugins/context_engine/<name>/محرّكات ضغط السياق (ctx.register_context_engine())محمّل خاص في plugins/context_engine/__init__.py (واحد فعّال في كل مرة)
      plugins/model-providers/<name>/ملفات تعريف مزوّدي LLM (register_provider(ProviderProfile(...)))محمّل خاص في providers/__init__.py (يُفحص بتكاسل عند أول استدعاء لـ get_provider_profile())

      إضافات المستخدم في ~/.hermes/plugins/model-providers/<name>/ تُلغي مزوّدي النماذج المدمجين بنفس الاسم (يفوز آخر من يكتب في register_provider())، فيمكنك استبدال ملف تعريف مزوّد مدمج دون أي تعديل على المستودع. أما مزوّدو الذاكرة فيعملون بالاتجاه المعاكس: بالنسبة لـ ~/.hermes/plugins/memory/<name>/ يفوز المزوّد المدمج عند تعارض الأسماء (المدمج، ثم المستخدم، ثم المشروع، ثم نقاط الدخول؛ يفوز الأول الذي يُعثَر عليه)، لذا يحتاج مزوّد ذاكرة من المستخدم إلى اسم فريد خاص به.

      الإضافات اختيارية بالتفعيل (مع استثناءات قليلة)​

      الإضافات العامة والباكندات المثبَّتة من المستخدم مُعطَّلة افتراضيًا — يجدها الاكتشاف (فتظهر في hermes plugins وفي /plugins)، لكن لا شيء من الـ hooks أو الأدوات يُحمَّل حتى تضيف اسم الإضافة إلى plugins.enabled في ~/.hermes/config.yaml. هذا يمنع تشغيل كود من طرف ثالث دون موافقتك الصريحة.

      plugins:
        enabled:
          - my-tool-plugin
          - disk-cleanup
        disabled:       # optional deny-list — always wins if a name appears in both
          - noisy-plugin
        # Optional: wall-clock cap (seconds) for timeout-bounded in-process Python
        # plugin hook callbacks (hot-path observers + pre_tool_call). Default 30;
        # set 0 to disable; values above 600 are clamped. Timed-out pre_tool_call
        # callbacks fail closed (block the tool). Caller-thread hooks such as
        # subagent_stop are never moved onto a timeout worker.
        # Shell hooks keep their own per-entry timeout under the top-level hooks: key.
        hook_callback_timeout: 30

      ثلاث طرق لتبديل الحالة:

      hermes plugins                    # interactive toggle (space to check/uncheck)
      hermes plugins enable <name>      # add to allow-list
      hermes plugins disable <name>     # remove from allow-list + add to disabled

      بعد hermes plugins install owner/repo، يُطرح عليك السؤال Enable 'name' now? [y/N] — الافتراضي هو الرفض. تخطَّ الطلب في التثبيتات المكتوبة عبر سكربت باستخدام --enable أو --no-enable.

      من أجل تثبيت قابل لإعادة الإنتاج، ثبّت commit كامل غير قابل للتغيير (لا تُقبل الوسوم tags، ولا الفروع، ولا الـ SHA المختصرة):

      hermes plugins install owner/repo --ref 0123456789abcdef0123456789abcdef01234567

      يقوم Hermes بعمل checkout للـ commit في وضع منفصل، ويتحقق من أن HEAD يطابق تمامًا الـ SHA المطلوب، ويسجّل المصدر الأصلي، والنسخة المثبَّتة، وحالة التثبيت الثابت في الملف الشخصي الحالي. يرفض hermes plugins update نقل إضافة مثبَّتة على commit ثابت؛ اختر commit جديدًا محددًا صراحةً باستخدام hermes plugins install <source> --force --ref <new-commit>. لا تحتوي بيانات التثبيت المحلية الخاصة بالملف الشخصي على أي قيم إعدادات، أو قيم بيئة، أو أسرار، أو منح إمكانيات.

      التثبيت نفسه متاح في Hermes Desktop: Skills → Plugins → Install from Git يحتوي على حقل Pin to commit يقبل الـ SHA الكامل المكوَّن من 40 حرفًا، وتعرض قائمة الإضافات شارة pinned @ <sha8> على كل تثبيت مثبَّت على commit، بحيث يمكن للفريق التأكد من أن الجميع يشغّل نفس الـ commit. تطبع hermes plugins list حالة التثبيت في عمود المصدر (git pinned@<sha8>). يعمل التثبيت الثابت على commit مع المستودعات الخاصة أيضًا، عبر بيانات الاعتماد المخزَّنة نفسها الموضَّحة أدناه.

      التثبيت من مستودع خاص​

      hermes plugins install يستنسخ دون تفاعل (لا يطلب أبدًا اسم مستخدم أو كلمة مرور)، لذا يحتاج المستودع الخاص إلى بيانات اعتماد يستطيع Hermes إيجادها بنفسه. بالنسبة لمصدر https:// يجرّب بالترتيب:

      1. GITHUB_TOKEN أو GH_TOKEN من ملف .env (مضيفات GitHub فقط).
      2. تسجيل دخول أداة gh (gh auth login)، مضيفات GitHub فقط.
      3. helper بيانات اعتماد git لديك (git credential fill) لذلك المضيف — يعمل مع GitLab وBitbucket والخواديم ذاتية الاستضافة إذا كانت بيانات الاعتماد مخزَّنة مسبقًا.

      تُرسَل بيانات الاعتماد كترويسة HTTP لمرة واحدة لذلك التثبيت أو التحديث؛ ولا تُكتَب أبدًا في .git/config الخاص بالإضافة ولا في بيانات التثبيت. مصادر SSH (git@host:owner/repo.git) تُوثَّق عبر ssh-agent كما كان الحال سابقًا. ينطبق نفس منطق التحديد على hermes plugins update، وتثبيتات MCP من الكتالوج عبر git، وتوزيعات الملفات الشخصية المجلوبة من رابط git.

      ما لا تقيّده القائمة المسموح بها​

      عدة فئات من الإضافات تتجاوز plugins.enabled — فهي جزء من السطح المدمج الأساسي لـ Hermes، وستُعطِّل الوظائف الأساسية لو كانت مقيَّدة افتراضيًا:

      نوع الإضافةكيف تُفعَّل بدلًا من ذلك
      إضافات منصات مدمجة (IRC، Teams، إلخ تحت plugins/platforms/)تُحمَّل تلقائيًا بحيث تتوفر كل قناة gateway مشحونة. القناة الفعلية تُفعَّل عبر gateway.platforms.<name>.enabled في config.yaml.
      باكندات مدمجة (مزوّدو توليد الصور تحت plugins/image_gen/، إلخ)تُحمَّل تلقائيًا حتى يعمل الباكند الافتراضي "من دون تدخّل". يتم الاختيار عبر <category>.provider في config.yaml (مثال: image_gen.provider: openai).
      مزوّدو الذاكرة (plugins/memory/)جميعهم يُكتشَفون؛ واحد فقط فعّال، يُختار عبر memory.provider في config.yaml.
      محرّكات السياق (plugins/context_engine/)جميعها تُكتشَف؛ واحد فعّال، يُختار عبر context.engine في config.yaml.
      مزوّدو النماذج (plugins/model-providers/)جميع المزوّدين المدمجين تحت plugins/model-providers/ يُكتشَفون ويُسجَّلون عند أول استدعاء لـ get_provider_profile(). يختار المستخدم واحدًا في كل مرة عبر --provider أو config.yaml.
      إضافات backend المثبَّتة عبر pipاختيارية عبر plugins.enabled (كالإضافات العامة).
      منصات مثبَّتة من المستخدم (تحت ~/.hermes/plugins/platforms/)اختيارية عبر plugins.enabled — محوّلات gateway من طرف ثالث تحتاج موافقة صريحة.

      باختصار: البنية التحتية المدمجة "التي تعمل دائمًا" تُحمَّل تلقائيًا؛ أما الإضافات العامة من طرف ثالث فاختيارية بالتفعيل. قائمة السماح plugins.enabled هي البوابة المخصصة تحديدًا لأي كود عشوائي يضعه المستخدم في ~/.hermes/plugins/.

      وسائط الموافقة (Approval transports)​

      وسيط الموافقة يغيّر أين يرى إنسان طلب موافقة على أداة ويجيب عنه في Hermes. لا يقرّر ما إذا كان أمر ما يحتاج موافقة، وليس واجهة برمجية لسياسة تفويض.

      def present(request):
          # Deliver request.command and request.description to your UI, wait for
          # its authenticated human response, then return a request-bound decision.
          choice = send_to_my_ui_and_wait(request)  # once/session/always/deny
          return request.respond(choice)


      def register(ctx):
          ctx.register_approval_transport("my-ui", present)

      يمكن أن يكون present متزامنًا أو غير متزامن. يشغّله Hermes على عامل مقيَّد، ويفرض مهلة approvals.timeout القياسية حتى لو لم تفعل الإضافة ذلك. الطلب غير قابل للتعديل ويحتوي على نص عرض منقّح، وفئة عرضه على المضيف (cli أو gateway)، ومهلة المضيف، والخيارات المسموح بها، ومعرّف/بصمة طلب مبهمة. أعد نتيجة request.respond(choice)؛ تُرفَض القواميس غير المرتبطة ومعرفات/بصمات الطلبات القديمة أو المتغيرة. لا يمكن للإضافة إرجاع نطاق لم يعرضه المضيف (مثلًا always على طلب لمرة واحدة فقط).

      التسجيل وحده لا يفعل شيئًا. تفعيل الإضافة واختيار وسيطها صراحةً خطوتا موافقة منفصلتان:

      plugins:
        enabled: [my-approval-plugin]

      security:
        approval:
          transport: my-ui
          transport_fallback: deny     # default

      استثناءات الوسيط، والمهلات، والتسجيلات غير المتاحة، والخيارات غير الصالحة، والاستجابات القديمة، كلها تُرفَض افتراضيًا. لعرض الطلب عمدًا على سطح CLI/TUI/gateway/ACP العادي عند فشل الوسيط المختار، اضبط transport_fallback: builtin. من دون هذا التفعيل الصريح بالضبط، لن يُظهر Hermes الطلب أبدًا على سطح آخر.

      ما يزال Hermes يملك حظر hardline، وحماية sudo-stdin، وقواعد رفض المستخدم، وربط الطلبات، والنطاقات المسموحة، والحفظ، والـ hooks، والتفويض النهائي. تُحظَر الأوامر hardline قبل أي استدعاء رجوعي من الوسيط. لا توجد عمدًا سياسة موافقة إضافة، أو استدعاء رجوعي للسماح التلقائي، أو pre_tool_call إلزامي في هذه الواجهة. قد تستخدم إمكانية سياسة موافقة مستقبلية نموذج موافقة الإمكانيات الخاص بالإضافات، لكن اختيار الوسيط لا يمنحها.

      الانتقال للمستخدمين الحاليين​

      عند الترقية إلى إصدار من Hermes يحتوي على إضافات اختيارية بالتفعيل (schema الإعدادات v21+)، فإن أي إضافات مستخدم مثبَّتة مسبقًا تحت ~/.hermes/plugins/ ولم تكن موجودة أصلًا في plugins.disabled تُدرَج تلقائيًا ضمن plugins.enabled. يستمر إعدادك الحالي بالعمل. الإضافات المستقلة المدمجة لا تُدرَج تلقائيًا — حتى المستخدمون الحاليون عليهم التفعيل صراحةً. (إضافات المنصات/الباكندات المدمجة لم تحتج قط لهذا الإدراج التلقائي لأنها لم تكن مقيَّدة أصلًا.)

      إضافات NixOS التصريحية​

      على NixOS، يمكن تثبيت الإضافات تصريحيًا عبر خيارات الوحدة — دون الحاجة إلى hermes plugins install. راجع دليل إعداد Nix لكل التفاصيل.

      services.hermes-agent = {
        # Directory plugin (source tree with plugin.yaml)
        extraPlugins = [ (pkgs.fetchFromGitHub { ... }) ];
        # Entry-point plugin (pip package)
        extraPythonPackages = [ (pkgs.python312Packages.buildPythonPackage { ... }) ];
        # Enable in config
        settings.plugins.enabled = [ "my-plugin" ];
      };

      الإضافات التصريحية تُربَط برابط رمزي مسبوق بـ nix-managed- — تتعايش مع الإضافات المثبَّتة يدويًا وتُزال تلقائيًا عند حذفها من إعداد Nix.

      إدارة الإضافات​

      hermes plugins                               # unified interactive UI
      hermes plugins list                          # table: enabled / disabled / not enabled
      hermes plugins search <term>                 # search the Hermes plugin catalog
      hermes plugins install <name>                # install a catalog entry (repo @ reviewed pinned SHA)
      hermes plugins install user/repo             # install from Git, then prompt Enable? [y/N]
      hermes plugins install user/repo --enable    # install AND enable (no prompt)
      hermes plugins install user/repo --no-enable # install but leave disabled (no prompt)
      hermes plugins update my-plugin              # pull latest (local edits are autostashed and re-applied)
      hermes plugins remove my-plugin              # uninstall
      hermes plugins enable my-plugin              # add to allow-list
      hermes plugins disable my-plugin             # remove from allow-list + add to disabled
      hermes plugins capabilities [my-plugin]      # declared vs granted capabilities

      روابط تثبيت بنقرة واحدة (Desktop)​

      يسجّل Hermes Desktop مخطط رابط hermes://، بحيث يمكن لموقع، أو ملف README، أو رسالة محادثة أن ترتبط مباشرةً بتثبيت إضافة:

      hermes://plugin/install?repo=owner/repo            # main install link
      hermes://plugin/install?repo=owner/repo&enable=1   # enable the agent plugin after install
      hermes://plugin/install?repo=owner/repo&force=1    # replace an existing install

      النقر على أحدها يفتح Hermes ويعرض مربع حوار تأكيد — معرّف المستودع، وملاحظة "قبل أن تثبّت"، وروابط تصفّح واستنساخ GitHub — ثم يستنسخ المستودع استنساخًا سطحيًا لاكتشاف ما يشحنه (إضافة وكيل — Python الخلفي، أو إضافة سطح مكتب — واجهة تطبيق، أو كلاهما). تختار المكوّنات عبر مربعات اختيار ثم تؤكّد. لا يُثبَّت شيء حتى تفعل ذلك؛ الروابط العميقة لا تثبّت تلقائيًا أبدًا، وتثبيتات إضافات الوكيل تمر عبر نفس فحص الأمان وقت التثبيت كما في hermes plugins install.

      المستودعات الهجينة (نصفا وكيل + سطح مكتب في مستودع واحد) تستخدم رابطًا واحدًا ومربع حوار واحد. يمكن الوصول إلى نفس النافذة المنبثقة دون رابط عبر Capabilities → Plugins → Install from Git. روابط hermes://plugin-agent/… و hermes://plugin-desktop/… القديمة تُوجَّه إلى نفس مربع الحوار. في إصدارات التطوير (npm run dev) المخطط هو hermes-dev://.

      لا تحتاج المواقع إلى أي SDK — تكفي وصلة عادية:

      <a href="hermes://plugin/install?repo=owner/repo&enable=1">Install in Hermes</a>

      لخواديم MCP صيغة رابط مماثلة — راجع رابط Add to Hermes.

      إمكانيات الإضافات والموافقة​

      يمكن للإضافات الإعلان عن أسطح المضيف المميّزة التي تريدها في plugin.yaml:

      name: my-plugin
      capabilities:
        - tools.override        # replace built-in tools
        - llm.model_override    # pick the model for host-owned LLM calls

      عندما تعلن إضافة عن إمكانيات، يعرض hermes plugins install (و hermes plugins enable) القائمة مع أوصاف مخاطر من سطر واحد و يسأل مرة واحدة. الموافقة تسجّل المنح تحت plugins.entries.<id>.granted_capabilities مع بصمة موافقة وطابع زمني. الرفض يترك الإضافة مفعَّلة مع تعطيل تلك الإمكانيات — الإضافة المصمَّمة جيدًا تستكشف الحال بـ ctx.has_capability() وتتراجع بسلاسة.

      إعادة الموافقة عند التحديث: إذا أعلن تحديث لإضافة عن إمكانيات لم تمنحها، يعرض hermes plugins update الإضافات ويسأل مجددًا. تبقى الإمكانيات الجديدة مُعطَّلة حتى توافق — تحديث إضافة لا يمكن أبدًا أن يوسّع صلاحياتها بصمت.

      الجلسات غير التفاعلية تفشل بأمان: تثبيت أو تحديث دون TTY يكمل التثبيت، لكن الإمكانيات المُعلَنة لا تُمنَح. شغّل hermes plugins enable <id> تفاعليًا لمنحها لاحقًا.

      hermes plugins capabilities             # all plugins with declared/granted capabilities
      hermes plugins capabilities my-plugin   # one plugin, declared vs granted

      ليست sandbox

      الإمكانيات هي طبقة موافقة وتدقيق، وليست عزلًا. الإضافات تعمل ككود Python عادي داخل العملية نفسها: إضافة خبيثة يمكن أن تتجاهل كل بوابة هنا. منح إمكانية هو إعلان ثقة بمؤلف الإضافة — وليس تدقيقًا للكود، ولم يراجع Hermes كود الإضافة. ثبّت فقط إضافات من مصادر تثق بها.

      إجراءات المنصة​

      ctx.platform_actions يمنح الإضافة مجموعة أفعال صغرى مقيَّدة بالإمكانيات للتصرف على منصات دردشة متصلة عبر سجلّ محوّلات gateway الحي — البديل المعتمد لتصحيح محوّل بشكل غير رسمي (monkeypatching). مُعطَّل افتراضيًا: كل استدعاء يعيد فحص إمكانية gateway.platform_actions (المفتاح القديم plugins.entries.<id>.allow_platform_actions)، وأي استدعاء غير ممنوح يعيد خطأً منظَّمًا بدلًا من التصرف.

      أفعال v1 (كلاهما async، وكلاهما يعيد قاموسًا عاديًا، ولا يرفعان استثناءً أبدًا في تنفيذ الـ hooks):

      result = await ctx.platform_actions.add_reaction(
          platform="telegram", chat_id="-100123", message_id="456", emoji="👍",
      )
      result = await ctx.platform_actions.set_thread_title(
          platform="discord", chat_id="123", thread_id="456", title="New title",
      )
      if not result["ok"]:
          print(result["error"], result.get("detail"))

      النجاح هو {"ok": True, "action": <verb>}. الإخفاقات هي {"ok": False, "error": <code>, "detail": <str>} برموز خطأ ثابتة: capability_not_granted، invalid_argument، gateway_unavailable، unknown_platform، adapter_not_registered، adapter_disconnected، unsupported_platform_action، action_failed. الأفعال تتحقق من أن المحوّل الهدف موجود ومتصل قبل التصرف؛ المحوّل غير المتصل أو المفقود يتدهور إلى خطأ منظَّم، وليس استثناءً أبدًا.

      المنصات المدعومة في v1: Telegram وDiscord. add_reaction في Telegram يضبط تفاعل البوت (Bot API يستبدل تفاعل بوت سابق بدلًا من تكديسه). كل إجراء — مسموح أو مرفوض — يُكتَب في السجل مع معرّف الإضافة، والفعل، والمنصة، والنتيجة.

      ملاحظة أمنية

      إجراءات المنصة هي صلاحية إرسال رسائل باسم البوت: إضافة ممنوحة يمكنها التفاعل وإعادة تسمية سلاسل المحادثات في أي محادثة يستطيع بوت gateway الوصول إليها، وليس فقط المحادثة التي شغّلت الـ hook. امنح gateway.platform_actions فقط للإضافات التي تثق بها، وفضّل الإضافات التي توثّق بدقة الإجراءات التي تتخذها. الوصول الخام إلى حمولة/مقبض SDK المنصة ليس عمدًا جزءًا من هذا السطح — بحسب تصحيح التصميم من الجولة الثانية #64176، فهو يحتاج إمكانية خاصة به (gateway.raw_events) بوسم "لا ضمان استقرار" وتصميمًا منفصلًا، ولم يُشحَن بعد.

      اكتشاف الإضافات — كتالوج إضافات Hermes​

      hermes plugins search <term> يبحث في كتالوج إضافات Hermes — الكتالوج المنسَّق والمثبَّت بـ SHA، والمُدار في مستودع hermes-agent (plugin-catalog/). يشمل التطابق أسماء المدخلات، والأوصاف، والأدوات المُعلَنة:

      hermes plugins search telegram    # search the catalog
      hermes plugins browse             # browse every entry
      hermes plugins info <name>        # full details for one entry

      بمجرد أن تجد إضافة، ثبّتها بالاسم المجرد — يُحلّ الاسم إلى مستودع المدخلة عند الـ SHA المثبَّت، وتُسجَّل نشأة الكتالوج بحيث يمكن لـ hermes plugins update إعادة التثبيت عندما يتحرك الكتالوج:

      hermes plugins install <catalog-name>

      معرّفات owner/repo أو روابط Git الصريحة لا تلامس الكتالوج أبدًا وتُوسَم كمصادر مخصصة (غير مراجَعة). --ref <40-char commit SHA> صريح يثبّت تثبيتًا مخصصًا.

      راجع كتالوج الإضافات لنموذج الثقة الكامل، وCI القبول، وسير عمل التقديم.

      مُدرَج في الكتالوج ≠ مُدقَّق

      وجود مدخلة في الكتالوج يعني أن بيانات المدخلة الوصفية والإمكانيات المُعلَنة رُوجِعَت عند القبول — وهذا ليس تدقيقًا للكود. التثبيت لا يزال يمر عبر تدفق الموافقة العادي (تثبيت الإضافات مُعطَّل افتراضيًا، والتفعيل خطوة صريحة، وحقوق تجاوز الأداة تتطلب منحًا منفصلًا). راجع مصدر الإضافة قبل تفعيلها.

      حزم الإضافات​

      حزمة الإضافات (plugin pack) هي ملف YAML تصريحي قابل للمشاركة (hermes-pack.yaml) يثبّت مجموعة من الإضافات — مثل مشاركة modpack. تثبيت حزمة يتفرّع إلى تثبيتات ثابتة عادية؛ لا شيء جديد يوجد في وقت التشغيل.

      name: voice-assistant-pack
      description: STT + streaming TTS + approval relay
      author: hyper
      version: 1.0.0
      plugins:
        - name: hermes-telegram-business       # bare plugin-catalog name…
          ref: e905f3bc5eeaa5a9dab9bc5155601b3ebec75757
        - repo: owner/approval-relay           # …or explicit owner/repo (or git URL)
          ref: 8f3c2d1a9b4e5f6071829304a5b6c7d8e9f00112
          subdir: plugins/relay                # optional monorepo path
      config:                                  # optional, non-secret seeds only
        hermes-media-studio:
          default_model: flux-3
      skills: []                               # declared list only (not auto-installed yet)
      hermes plugins pack show ./hermes-pack.yaml     # dry-run review
      hermes plugins pack install ./hermes-pack.yaml  # review → confirm → install
      hermes plugins pack export > hermes-pack.yaml   # snapshot the current install
      hermes plugins pack export --enabled-only       # only plugins.enabled

      وضعية سلسلة التوريد. يجب أن يكون ref لكل مدخلة SHA كامل مكوَّن من 40 حرفًا — تُرفَض الوسوم tags وأسماء الفروع بخطأ يسمّي المدخلة، وهي نفس القاعدة المطبَّقة على كتالوج الإضافات. تسلك تثبيتات الحزمة نفس مسار التثبيت الثابت تمامًا مثل hermes plugins install --ref <sha> وتسجّل نفس النشأة في plugins/.install-metadata.json، بحيث يُحلّ تثبيتان لنفس الحزمة إلى الشيء نفسه. تُبنى الحزم على حقول manifest v2 (manifest_version، api_version، requires_plugins) — كل manifest خاص بإضافة لا يزال يُتحقَّق منه عبر مسار التثبيت العادي.

      الموافقة لا تُمنَح جماعيًا أبدًا. تعرض pack install شاشة مراجعة إلزامية (كل إضافة، ومصدرها، وrefها المثبَّت، والإمكانيات التي تعلن عنها)، ثم تطلب تأكيدًا واحدًا لمحتويات الحزمة. بعد ذلك، تمر إمكانيات كل إضافة المُعلَنة عبر طلب موافقة الإمكانيات القياسي لكل إضافة — مطابق لـ hermes plugins install منفردة. لا وجود لـ --yes، ولا يمكن للجلسات غير التفاعلية تثبيت الحزم.

      الأسرار لا تنتقل أبدًا في الحزم. تقتصر بذور config: على مفاتيح plugins.entries.<id> غير السرية — أسماء المفاتيح ذات الشكل السري (*token*، *key*، *password*، …)، ومنح الإمكانيات، وبوابات الثقة allow_* المُهملة، تُرفَض عند التثبيت وتُحذَف عند التصدير. الإضافات التي تحتاج أسرارًا تعلن عنها في requires_env الخاص بها، والتي تُطلَب أثناء التثبيت كالمعتاد. القيم الموجودة أصلًا لدى المستخدم في plugins.entries.<id> تفوز دائمًا على بذور الحزمة.

      الفشل الجزئي. تُثبَّت كل إضافة باستقلالية؛ تُبلَّغ الإخفاقات لكل إضافة، وتستمر البقية، ويخرج الأمر برمز غير صفري إذا فشلت أي إضافة.

      تحفظات التصدير. يشمل pack export فقط الإضافات ذات نشأة Git معروفة (المثبَّتة عبر hermes plugins install). الإضافات المحلية فقط تُدرَج كتعليقات تحذير في YAML المُصدَر، وليست كمدخلات قابلة للتثبيت.

      قائمة skills: تُحلَّل وتُعرَض عند التثبيت لكنها لا تُثبَّت تلقائيًا بعد — ثبّت تلك يدويًا في الوقت الحالي (hermes skills). ربط معرّفات skill-hub في تثبيت الحزم هو مسار تتمة موثَّق.

      فحص الأمان وقت التثبيت​

      كل hermes plugins install وhermes plugins update يشغّل فحصًا أمنيًا ثابتًا على شجرة الإضافة قبل تفعيلها (مستوحى من فحص أمان المهارات والإضافات في Claude Cowork). يعيد الفاحص استخدام نفس محرّك أنماط التهديد الخاص بـ حارس Skills Hub — تسريب مخازن بيانات الاعتماد، وقذائف عكسية، وأوامر مدمِّرة، وآليات استمرارية، وتنفيذ مبهم، وحقن prompt في ملفات التوثيق — مع استثناءات واعية بالإضافات: إضافة مزوّد تقرأ مفتاح API الخاص بها من البيئة (نمط requires_env الموثَّق) لا تُوسَم.

      ثلاثة أحكام، مطابقة لـ pass/warn/fail الخاصة بـ Cowork:

      الحكمالسلوك
      آمن (safe)يثبَّت عاديًا، دون مخرجات إضافية
      احتراس (caution)تُعرَض النتائج؛ تؤكّد Install anyway? [y/N] (أو تمرّر --force)
      خطر (dangerous)محظور. --force لا يتجاوزه

      في hermes plugins update، حكم خطر على الشجرة المحدَّثة يعطّل الإضافة حتى تراجع النتائج وتعيد تفعيلها.

      الفحص مفعَّل افتراضيًا؛ عطّله في config.yaml:

      plugins:
        scan_on_install: false

      واجهة تفاعلية​

      تشغيل hermes plugins دون وسائط يفتح شاشة تفاعلية مركّبة:

      Plugins
        ↑↓ navigate  SPACE toggle  ENTER configure/confirm  ESC done

        General Plugins
       → [✓] my-tool-plugin — Custom search tool
         [ ] webhook-notifier — Event hooks
         [ ] disk-cleanup — Auto-cleanup of ephemeral files [bundled]

        Provider Plugins
           Memory Provider          ▸ honcho
           Context Engine           ▸ compressor
      • قسم الإضافات العامة — مربعات اختيار، بدّل بمفتاح SPACE. محدَّد = في plugins.enabled، غير محدَّد = في plugins.disabled (تعطيل صريح).
      • قسم إضافات المزوّد — يعرض الاختيار الحالي. اضغط ENTER للدخول إلى منتقٍ راديو حيث تختار مزوّدًا فعّالًا واحدًا.
      • الإضافات المدمجة تظهر في نفس القائمة بوسم [bundled].

      اختيارات إضافة المزوّد تُحفَظ في config.yaml:

      memory:
        provider: "honcho"      # empty string = built-in only

      context:
        engine: "compressor"    # default built-in compressor

      مفعَّل مقابل معطَّل مقابل لا هذا ولا ذاك​

      تشغل الإضافات إحدى ثلاث حالات:

      الحالةالمعنىفي plugins.enabled؟في plugins.disabled؟
      enabledيُحمَّل في الجلسة التاليةنعملا
      disabledمعطَّل صراحةً — لن يُحمَّل حتى لو كان أيضًا في enabled(غير ذي صلة)نعم
      not enabledمكتشَف لكن لم يُوافَق عليه أبدًالالا

      الافتراضي لإضافة مثبَّتة حديثًا أو مدمجة هو not enabled. يعرض hermes plugins list الحالات الثلاث المختلفة لتعرف ما عُطِّل صراحةً مقابل ما ينتظر التفعيل فقط.

      في جلسة قيد التشغيل، يعرض /plugins الإضافات المحمَّلة حاليًا.

      حقن الرسائل (Injecting Messages)​

      يمكن للإضافات حقن رسائل في محادثة CLI أو جلسة gateway معروفة باستخدام ctx.inject_message():

      # Active CLI conversation
      ctx.inject_message("New data arrived from the webhook", role="user")

      # Existing gateway conversation
      ctx.inject_message(
          "New data arrived from the webhook",
          role="user",
          session_key="agent:main:telegram:dm:123456789",
      )

      التوقيع: ctx.inject_message(content: str, role: str = "user", *, session_key: str | None = None) -> bool

      في وضع CLI:

      • إذا كان الوكيل خاملًا (بانتظار إدخال المستخدم)، تُصفّ الرسالة كإدخال تالٍ وتبدأ دورًا جديدًا.
      • إذا كان الوكيل وسط دور (قيد التشغيل فعليًا)، تقاطع الرسالة العملية الجارية — تمامًا كما لو كتب المستخدم رسالة جديدة وضغط Enter.
      • بالنسبة للأدوار غير "user"، يُسبَق المحتوى بـ [role] (مثل [system] ...).
      • تُعيد True إذا صُفَّت الرسالة بنجاح.

      في وضع gateway:

      • session_key مطلوب ويجب أن يُعرّف جلسة gateway موجودة. إنه مفتاح التوجيه الثابت، وليس معرّف جلسة CLI.
      • يعيد Hermes استخدام المنصة، والمحادثة، والسلسلة، والملف الشخصي، وسجل المحادثة المخزَّنين لتلك الجلسة. لا يمكن للإضافات توفير مسار محادثة جديد عبر هذه الواجهة.
      • يعيد Hermes فحص المسار المخزَّن مقابل قواعد التفويض الحالية لـ gateway قبل الإرسال.
      • المسارات التي اعتمدت فقط على قرار تفويض وقت المحوّل أو من مصدر أعلى تُرفَض ما لم يتمكن Hermes من إعادة التحقق منها من قوائم السماح الأساسية الحالية، أو الاقتران، أو إعداد صريح للسماح بكل شيء.
      • النص المحقون هو دائمًا إدخال محادثة عادي. لا يمكنه استدعاء slash commands، أو الموافقة على أدوات، أو حلّ طلبات تأكيد أو توضيح معلَّقة.
      • يبقى المسار والمحادثة مثبَّتين أثناء انتظار الإرسال. يُسقِط Hermes الطلب إذا غيّر استرجاع الموضوع المسار أو دارت الجلسة قبل بدء المعالجة.
      • يدخل الطلب مسار رسائل محوّل المنصة العادي. الجلسات النشطة تستخدم طابور الجلسة المشغولة الحالي بدلًا من بدء دور منافس.
      • تُعيد True عندما يقبل gateway الحي الطلب للإرسال غير المتزامن. هذا لا يؤكّد أن دور الوكيل أو التسليم على المنصة قد اكتمل.
      • تُعيد False عندما تُغفَل session_key، أو لا تُمنَح الصلاحية، أو لا يوجد gateway حي يقبل الطلب. مفاتيح الجلسة غير المعروفة أو غير القابلة للتوجيه المكتشَفة بعد القبول غير المتزامن تُكتَب في سجل gateway.

      هذا يتيح لإضافات مثل عارضات التحكم عن بُعد، أو جسور المراسلة، أو مستقبِلات webhook، تغذية المحادثة برسائل من مصادر خارجية.

      يمكن لحقن gateway إرسال رد الوكيل إلى منصة مراسلة خارجية. مُعطَّل افتراضيًا لكل إضافة. امنحه لكل إضافة في config.yaml:

      plugins:
        entries:
          my-plugin:
            allow_gateway_injection: true
      تحذير

      امنح حقن gateway فقط للإضافات التي تثق بها. يتحقق Hermes من صلاحية واجهة المضيف هذه ويقيّدها بمسارات جلسات موجودة، لكن إضافات Python تعمل داخل العملية نفسها وهذا الإعداد ليس sandbox.

      ملاحظة

      لا تعرض واجهة الإضافة هذه نقطة نهاية HTTP عامة ولا أمر CLI لعمليات خارجية. يجب أن تعرف الإضافة مسبقًا session_key الخاص بـ gateway الهدف، مثلًا من إعداداتها الموثوقة الخاصة أو حالة جلسة محتفَظ بها سابقًا.

      استدعاء خواديم MCP من الإضافات​

      ctx.call_mcp() يتيح للإضافة استدعاء أداة على أحد خواديم MCP المُعدَّة للمستخدم — بشكل متزامن، من أي hook أو معالج أداة — عبر عميل MCP الأصلي الحالي في Hermes (نفس الاتصالات، وبوابات مستوى الثقة، وقاطع الدارة، ومنطق إعادة الاتصال المستخدَمة في أدوات MCP التي يستدعيها النموذج؛ أبدًا عميل موازٍ).

      result = ctx.call_mcp(
          "knowledge_rag",            # server name from mcp.servers
          "query_knowledge",          # tool on that server
          {"query": "deploy runbook"},
          timeout=30,                 # seconds; clamped to 1–600
      )
      if result["ok"]:
          print(result["result"])
      else:
          print("MCP error:", result["error"])

      التوقيع: ctx.call_mcp(server: str, tool: str, arguments: dict | None = None, timeout: float = 30) -> dict

      تُعيد ظرفًا ثابتًا: {"ok": True, "result": ...} (بالإضافة إلى structuredContent عندما يوفّره الخادم) أو {"ok": False, "error": "..."}. النتائج التي تتجاوز ~64 كيلوبايت تُقتَطع وتُوسَم بـ "truncated": True.

      الأمان: مُعطَّل افتراضيًا، قائمة سماح لكل خادم​

      لا تملك الإضافة أي وصول إلى MCP افتراضيًا. يجب على المشغّل منح كل خادم صراحةً في config.yaml:

      plugins:
        entries:
          my-plugin:
            mcp_allowlist: ["knowledge_rag", "github"]
      • استدعاء خادم غير موجود في القائمة يرفع PermissionError يسمّي مفتاح الإعداد الدقيق الواجب ضبطه.
      • المنح لكل خادم ولكل إضافة — أبدًا صلاحية شاملة على كل خادم مُعدّ، ووسوم "*" غير مقبولة.
      • كل استدعاء له مهلة مفروضة (30 ثانية افتراضيًا) بحيث لا يمكن لخادم MCP معلَّق أن يعطّل خط hooks أو الأدوات الذي استدعاه.
      • خواديم MCP تعيد محتوى غير موثوق. عامل result كبيانات، لا كتعليمات — لا تُدخله في قرارات مميَّزة (موافقات، تنفيذ أوامر) دون تحقّق.
      تحذير

      منح mcp_allowlist يمنح الإضافة نفس وصول النموذج إلى ذلك الخادم — بما في ذلك أي أدوات قادرة على الكتابة يعرضها الخادم (رهنًا ببوابات مستوى trust الخاصة بالخادم). امنح فقط الخواديم التي تحتاجها الإضافة فعلًا.

      راجع الدليل الكامل لعقود المعالِج، وصيغة الـ schema، وسلوك الـ hook، ومعالجة الأخطاء، والأخطاء الشائعة.

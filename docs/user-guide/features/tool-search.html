      البحث عن الأدوات (Tool Search)

      عندما تكون لديك خوادم MCP كثيرة أو أدوات إضافات (plugins) غير أساسية مرتبطة بجلسة ما، فقد تستهلك مخططات JSON الخاصة بها (schemas) جزءًا كبيرًا من الـ context window في كل دور — حتى عندما يكون عدد قليل منها فقط ذا صلة بما طلبه المستخدم فعلًا.

      Tool Search هي طبقة الإفصاح التدريجي (progressive disclosure) الاختيارية في Hermes لمعالجة هذه المشكلة. عند تفعيلها، تُستبدل أدوات MCP وأدوات الإضافات في مصفوفة الأدوات المرئية للنموذج بثلاث أدوات جسر (bridge tools)، ويحمّل النموذج مخطط كل أداة محددة عند الحاجة.

      أدوات Hermes المدمجة لا تُؤجَّل أبدًا

      الأدوات التي تشكّل مجموعة القدرات الأساسية في Hermes (terminal، read_file، write_file، patch، search_files، todo، memory، browser_*، web_search، web_extract، clarify، execute_code، delegate_task، session_search، وبقية _HERMES_CORE_TOOLS) تُحمَّل مباشرةً دائمًا. ولا يكون قابلًا للتأجيل سوى أدوات MCP وأدوات الإضافات غير الأساسية.

      آلية العمل​

      عندما تُفعَّل Tool Search في دور ما، يرى النموذج ثلاث أدوات جديدة بدلًا من الأدوات المؤجَّلة:

      tool_search(queries, limit?)   search the deferred-tool catalog (one or more queries)
      tool_describe(names)           load the full schemas for one or more tools
      tool_call(calls)               invoke deferred tools; `calls` is an array of {name, arguments}

      يأخذ calls إدخالًا واحدًا لكل استدعاء؛ فالاستدعاء المحلي الواحد مصفوفة من عنصر واحد. ولا يجوز تجميع سوى الأسماء التي تبدأ بـ connectors__ معًا في دفعة واحدة؛ وتُرفض الدفعات المختلطة والدفعات التي تضم عدة أدوات محلية.

      يبدو التفاعل النموذجي على النحو التالي:

      Model: tool_search(["create a github issue", "send a slack message"])
        → { results: [ { query: "create a github issue",
                         matches: ["mcp_github_create_issue", ...] },
                       { query: "send a slack message",
                         matches: ["mcp_slack_post_message", ...] } ],
            tools: { mcp_github_create_issue: { description: "...",
                                                required: ["title"], ... },
                     mcp_slack_post_message: { ... } } }
      Model: tool_describe(["mcp_github_create_issue", "mcp_slack_post_message"])
        → { tools: { mcp_github_create_issue: { parameters: { ... } },
                     mcp_slack_post_message: { parameters: { ... } } } }
      Model: tool_call({ calls: [{ name: "mcp_github_create_issue",
                                   arguments: { title: "...", body: "..." } }] })
        → { ok: true, issue_number: 42 }

      يُبحث عن كل استعلام في استدعاء tool_search بشكل مستقل ضمن الكتالوج نفسه (ويُطبَّق limit على كل استعلام)؛ وتحمل المجموعات الخاصة بكل استعلام أسماء الأدوات فقط، بينما تحتفظ الخريطة المشتركة tools بوصف كل أداة مطابقة وأسماء معاملاتها المطلوبة مرة واحدة. تُطبَّق على الاستعلامات عملية التجذيع (stemming)، لذا فإن "issues" تعثر على create_issue. وكل مجموعة استعلام لا تُرجع أي تطابقات تتضمن ملخص available_sources للخوادم المتصلة، كي لا يُفهم إخفاق المطابقة اللفظية على أنه غياب للقدرة نفسها. يحلّ tool_describe جميع الأسماء المطلوبة في استدعاء واحد؛ وتُذكر الأسماء غير المعروفة في not_found دون أن يفشل باقي الدفعة.

      عندما يستدعي النموذج tool_call، فإن Hermes يفكّ غلاف الجسر ويُرسل الأداة الفعلية تمامًا كما لو كان النموذج قد استدعاها مباشرةً. إذ تعمل hooks ما قبل استدعاء الأداة، وقيود الحماية (guardrails)، وطلبات الموافقة، و hooks ما بعد استدعاء الأداة جميعها على اسم الأداة الحقيقي — لا على tool_call. كما يفكّ سجل النشاط في CLI و gateway الغلاف أيضًا، بحيث ترى الأداة الفعلية لا أداة الجسر.

      متى تُفعَّل؟​

      تستخدم Tool Search الإفصاح المتدرّج حسب المستويات: فوجود أي أداة قابلة للتأجيل (MCP/plugin) يفعّل الجسر؛ وما يتغير بحسب حجم الكتالوج هو مقدار ما يبقى مرئيًا منه، لا ما إذا كانت المخططات تُؤجَّل أم لا.

      المستوى (Tier)الشرطما يراه النموذج
      0لا توجد أدوات MCP/pluginكل الأدوات تُحمَّل فورًا، ولا يوجد جسر. تمرير مباشر.
      1قائمة الكتالوج المؤجَّل تتسع ضمن الميزانيةالجسر + بيان (manifest) على غرار المهارات لكل أداة مؤجَّلة (الاسم + وصف قصير، مع التراجع إلى الأسماء فقط عند تجاوز الميزانية). ويكون التراجع لكل خادم على حدة: فعند ربط خادم ضخم جدًا (Cloudflare) إلى جانب خوادم صغيرة (Linear)، تحتفظ الخوادم الصغيرة بقوائم أدواتها التفصيلية، ولا يُختزل إلى سطر ملخص سوى الخادم الضخم.
      2قائمة الأدوات تتجاوز الميزانية حتى بالأسماء فقط لكل الخوادم (مثل واجهة API المسطّحة الخاصة بـ Cloudflare وحدها: نحو 3,300 أداة تبلغ أسماؤها نحو 32K token)الجسر وحده + ملخص بسطر واحد لكل خادم (اسم الخادم + عدد الأدوات)، كي يعرف النموذج النطاقات التي يمكن الوصول إليها؛ ولا يمكن اكتشاف الأدوات الفردية إلا عبر tool_search.

      ميزانية القائمة هي min(threshold_pct% of context, listing_max_tokens). ويُعاد تقييم القرار في كل مرة تُبنى فيها مصفوفة الأدوات، لذا فإن إضافة خوادم MCP أو إزالتها في منتصف الجلسة تنقل الجلسة بين المستويات عند التجميع التالي.

      الإعدادات​

      tools:
        tool_search:
          enabled: auto       # auto (default), on, or off
          threshold_pct: 5    # listing budget as a percentage of context
          search_default_limit: 5
          max_search_limit: 25
          listing: auto       # embed a grouped name+description catalog manifest
          listing_max_tokens: 4000
      المفتاحالقيمة الافتراضيةالمعنى
      enabledautoالقيمتان auto/on تفعّلان الميزة متى وُجدت أداة واحدة على الأقل قابلة للتأجيل؛ و off تعطّلها كليًا (فتبقى كل الأدوات محمّلة فورًا). القيمة auto حاليًا اسم بديل لـ on — وهي محجوزة لوضع مستقبلي يُدرج المخططات مباشرةً عندما تتسع في السياق ولا يؤجّلها إلا عندما لا تتسع. ثبّت القيمة على on أو off إذا أردت ضمان السلوك الحالي عبر الترقيات.
      threshold_pct5ميزانية القائمة كنسبة مئوية من طول سياق النموذج النشط. النطاق 0–100.
      search_default_limit5عدد النتائج المُرجعة لكل استعلام عندما يستدعي النموذج tool_search دون تحديد limit.
      max_search_limit25الحد الأعلى الصارم الذي يمكن للنموذج طلبه عبر limit (لكل استعلام). النطاق 1–50.
      listingautoتضمين بيان على غرار المهارات لكل أداة مؤجَّلة (الاسم + الجملة الأولى من وصفها، بحد أقصى 60 حرفًا، مجمّعة حسب خادم MCP) في وصف أداة الجسر tool_search. تُضمّنه القيمة auto عندما يتسع ضمن الميزانية (مع التراجع إلى الأسماء فقط، ثم إلى ملخص الخوادم في المستوى 2)؛ أما on/off فتفرضان أحد الخيارين.
      listing_max_tokens4000حد أقصى مطلق للقائمة المضمّنة، بغض النظر عن حجم السياق. النطاق 200–60000. تتراجع الكتالوجات الكبيرة إلى الأسماء فقط أو إلى ملخصات لكل خادم، مع إبقاء المخططات الكاملة متاحة عبر البحث.

      الحدود القصوى لحجم المصفوفات في كل استدعاء هي حدود أمان داخلية، وليست إعدادات قابلة للضبط. الاستدعاءات التي تتجاوز الحد تُرجع خطأً كي يتمكن النموذج من إعادة المحاولة بدفعة أصغر.

      لماذا توجد القائمة​

      بدونها تكون القدرات المؤجَّلة غير مرئية — فقد أظهرت القياسات الحية أن النماذج تستبدل بها أدوات أساسية مرئية (كتشغيل gh في الطرفية بدلًا من البحث عن أداة GitHub المؤجَّلة) أو تعلن أن قدرة ما غير موجودة بدلًا من استدعاء tool_search. تطبّق القائمة نمط المهارات على الأدوات: فتبقى كل قدرة قابلة للاكتشاف بالاسم في جميع الأوقات، بينما تظل مخططات المعاملات الكاملة مؤجَّلة. وإذا رأى النموذج اسم الأداة الدقيق في القائمة، يمكنه تخطي tool_search والانتقال مباشرةً إلى tool_describe، موفّرًا بذلك جولة ذهاب وإياب (round trip).

      يمكنك أيضًا استخدام الصيغة المنطقية (boolean) القديمة:

      tools:
        tool_search: true   # equivalent to {enabled: auto}

      الموصِّلات (Connectors) — الأدوات البعيدة​

      عندما تكون مسجّلًا الدخول إلى Nous Portal، يصل الجسر أيضًا إلى connectors — وهي أدوات بعيدة يقدّمها tool gateway المُدار. ولا تُسجَّل محليًا أبدًا: إذ يرسل tool_search كل استعلام إلى الـ gateway، ويضيف نتائج الـ gateway إلى الكتالوج المحلي كمستندات (موسومة بـ source: "connectors"، وتحمل أسماء بصيغة connectors__<connector>__<tool>)، ويرتّب الاثنين معًا بتمريرة BM25 نفسها وقاعدة الـ token الأندر نفسها، بحيث يحدّ limit المجموعة ككل، ولا تُزاح أبدًا أداة connector تجيب عن الاستعلام بسبب أدوات محلية تشاركها كلمة واحدة. ويُحدَّد استدعاء الـ gateway بمدة 30 ثانية؛ فإذا كان الـ gateway بطيئًا أو متوقفًا، يُكتفى بالنتائج المحلية فقط. يجلب tool_describe مخططات الـ connectors من الـ gateway، ويرسل tool_call كل إدخال connector في الدفعة كطلب مستقل إلى الـ gateway، بترتيب الإدخال (واسم الأداة الذي لا يعرفه الـ gateway تحت الـ slug المعتاد تُعاد محاولته مرة واحدة تحت الـ slug الحرفي، لذا قد يكلّف الإدخال الواحد طلبين). وإذا حدث أن قدّم connector الأداتين GMAIL_X و X الحرفية معًا، فستتحول كلتاهما إلى connectors__gmail__X، الذي يشغّل GMAIL_X؛ فيحتفظ البحث بتلك النسخة، ويُسقط الأخرى، ويسجّل تحذيرًا. وتُعاد النتائج إلى ترتيب الدفعة الأصلي مع إعادة حساب الأعداد.

      tools:
        connectors:
          enabled: true   # false — never touch connector routes; the bridge
                          # behaves exactly as if the feature didn't exist

      عند تسجيل الخروج (أو عندما لا يقدّم الـ gateway أي connectors لحسابك)، يصبح كل ما سبق غير مرئي: ويتصرف البحث المحلي تمامًا كما هو موضح في بقية هذه الصفحة، دون إظهار أي أخطاء للنموذج.

      استدعاء الـ connector الذي يحتاج إلى حساب لم تربطه يُرجع خطأ CONNECTION_REQUIRED يحمل رابطًا للربط. أما الأداة manage_connections (المتاحة وفق الشرط نفسه الذي يُتاح به جسر الـ connectors) فتسرد الـ connectors وحالة اتصالها، وتبدأ عملية التفويض، ويمكنها الانتظار حتى يُكملها المستخدم؛ أما فصل الحساب فيقوم به المستخدم بنفسه من الـ Portal.

      يقبل tool_call دفعة: فالحقل calls مصفوفة من إدخالات {name, arguments} (والاستدعاء الواحد مصفوفة من عنصر واحد). وكل إدخال connector في الدفعة يُرسَل كطلب مستقل إلى الـ gateway، واحدًا تلو الآخر؛ أما الأدوات المحلية المؤجَّلة فتبقى بإدخال واحد لكل tool_call. تُحسم الموافقات لكل إدخال قبل الإرسال، وأمر /stop بين الإدخالات يترك الإدخالات التي لم تبدأ دون إرسال (وتُبلغ خاناتها عن INTERRUPTED).

      متى لا تستخدمها​

      تقايض Tool Search تكلفةً ثابتة من الـ tokens في كل دور (مخططات أدوات الجسر الثلاث بالإضافة إلى قائمة الكتالوج) وجولةَ ذهاب وإياب إضافية واحدة على الأقل مع الأدوات غير المحمّلة بعد (describe → call) مقابل التوفير في المخططات المؤجَّلة. في المستوى 1 تُبقي القائمة كل قدرة مرئية، لذا تختفي عادةً جولة الاكتشاف — إذ ينتقل النموذج مباشرةً إلى tool_describe. وقد أظهرت القياسات الحية أن وضع القائمة يضاهي التحميل الفوري في نسبة نجاح المهام، بتكلفة أقل من الجسر وحده.

      إذا أردت السلوك القديم القائم على التحميل الفوري دائمًا مع toolset صغير، فاضبط enabled: off.

      مقايضات لا مفرّ منها​

      تنبع هذه المقايضات من ثابت سلامة التخزين المؤقت للـ prompt (prompt cache) — وهي متأصلة في أي تصميم يعتمد على الإفصاح التدريجي، وليست خاصة بهذا التنفيذ:

      • جولة ذهاب وإياب إضافية مع الأدوات غير المحمّلة بعد. في المرة الأولى التي يحتاج فيها النموذج إلى أداة مؤجَّلة، يُنفق استدعاءً أو استدعاءين إضافيين للنموذج للعثور على المخطط وتحميله. التوفير في الـ tokens على الجانب الثابت حقيقي، لكن جزءًا منه يُدفع مجددًا وقت التشغيل.
      • لا فائدة من التخزين المؤقت للمخططات المؤجَّلة. نتيجة tool_describe المحمّلة تدخل سجل المحادثة (لذا تُخزَّن مؤقتًا بالفعل في الأدوار اللاحقة) لكنها لا تستفيد أبدًا من بادئة التخزين المؤقت الخاصة بالـ system prompt.
      • لا يوجد تحقق أصلي من جهة المزوّد للمخططات المؤجَّلة. تتيح tool_describe للنموذج قراءة مخطط الأداة المؤجَّلة، لكن المزوّد يظل لا يرى سوى الكائن العام tool_call.arguments. لذلك يحوّل Hermes الوسائط الفعلية إلى الأنواع الصحيحة ويتحقق منها محليًا قبل الإرسال؛ وتظل الأداة الفعلية أو خادم MCP مسؤولَين عن المخططات التي لا يستطيع Hermes التحقق منها بأمان، مثل المخططات المشوّهة أو المراجع الخارجية.
      • الاعتماد على جودة النموذج. تفترض Tool Search أن النموذج قادر على كتابة استعلام بحث معقول عن الأداة التي يريدها. والنماذج الأصغر تؤدي ذلك بكفاءة أقل؛ وتُظهر الأرقام المنشورة من Anthropic (49% → 74% على Opus 4 مع البحث عن الأدوات مقابل بدونه) الفائدة، لكنها تُظهر أيضًا أن نحو 26 نقطة من الدقة لا تزال تمثل إخفاقًا في الاسترجاع.
      • تعديلات الـ toolset تُبطل التخزين المؤقت. إضافة أداة أو إزالتها في منتصف الجلسة تغيّر أوصاف أدوات الجسر (التي تتضمن عدد الأدوات المؤجَّلة) والكتالوج، فيُبطَل التخزين المؤقت للـ prompt. وهذه المقايضة نفسها التي تنطبق على أي تعديل في الـ toolset.

      تفاصيل التنفيذ​

      • الاسترجاع: خوارزمية BM25 على اسم الأداة بعد تقسيمه إلى tokens، واسم المصدر (خادم MCP أو toolset الإضافة الذي تنتمي إليه الأداة، بحيث يعثر البحث عن "linear" على أدوات ذلك الخادم حتى عندما لا يتضمن اسم الأداة نفسه اسم الخدمة)، والوصف، وأسماء المعاملات، مع تطبيق التجذيع بخوارزمية Snowball (للإنجليزية) على كلٍّ من الفهرس والاستعلام بحيث تتطابق الصيغ الصرفية المختلفة ("issues" تعثر على create_issue). ولا تُعدّ الأداة نتيجةً إلا إذا احتوت على الـ token الأندر في الاستعلام (أي الموجود في أقل عدد من مستندات الأدوات، وهو بالتالي الكلمة التي تعبّر عن القصد: gmail، github، incident، لا send أو create). والاستعلام الذي لا يظهر الـ token الأندر فيه في أي أداة يُرجع مجموعة فارغة مع المصادر المتصلة وتلميح لإعادة المحاولة، بدلًا من إرجاع limit أداة تشترك في كلمة شائعة واحدة.
      • التنفيذ المتوازي يفكّ غلاف الجسر. يحدد مخطط الدفعات التزامن بناءً على الأداة الفعلية في tool_call، لا على اسم الجسر الحرفي — لذا فإن خادم MCP الذي فعّل التوازي عبر supports_parallel_tool_calls: true يحتفظ بتزامنه عندما تُستدعى أدواته عبر الجسر، وتُنفَّذ عمليات البحث tool_search / tool_describe بالتزامن في دفعات مثل أي أداة للقراءة فقط.
      • الكتالوج عديم الحالة (stateless) عبر الأدوار. إذ يُعاد بناؤه من قائمة تعريفات الأدوات الحالية عند كل تجميع — دون Map مرتبط بالجلسة. وهذا يتجنب فئة الأخطاء التي يخرج فيها الكتالوج المخزَّن عن التزامن مع سجل الأدوات الحي.
      • الكتالوج محصور في toolsets الجلسة. فالأدوات tool_search، tool_describe، و tool_call لا ترى ولا تستدعي إلا الأدوات التي مُنحت للجلسة فعلًا. ولا يمكن لـ subagent أو kanban worker أو جلسة gateway مقيّدة بمجموعة فرعية من الـ toolsets استخدام الجسر لاكتشاف أداة خارج تلك المجموعة الفرعية أو استدعائها — فالكتالوج المؤجَّل هو الشريحة القابلة للتأجيل من toolsets الجلسة المفعّلة/المعطّلة الخاصة بها، لا سجل العملية بالكامل.
      • لا يوجد JS sandbox. يستخدم Hermes وضع "structured tools" الأبسط (search / describe / call كدوال عادية). أما وضع "code mode" القائم على JS sandbox الذي تقدّمه بعض التطبيقات الأخرى فيمثل مساحة سطح كبيرة؛ لذا نتخطاه.

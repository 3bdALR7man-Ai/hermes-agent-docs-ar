      مزوّدو الذاكرة (Memory Providers)

      يأتي Hermes Agent مع 8 إضافات (plugins) لمزوّدي الذاكرة الخارجيين تمنح الوكيل معرفة دائمة عبر الجلسات تتجاوز الملفين المدمجين MEMORY.md و USER.md. ولا يمكن تفعيل أكثر من مزوّد خارجي واحد في الوقت نفسه — بينما تبقى الذاكرة المدمجة مفعّلة دائمًا إلى جانبه.

      البدء السريع​

      hermes memory setup      # interactive picker + configuration
      hermes memory status     # check what's active
      hermes memory off        # disable external provider

      يمكنك أيضًا اختيار مزوّد الذاكرة النشط عبر hermes plugins → Provider Plugins → Memory Provider.

      أو اضبطه يدويًا في ~/.hermes/config.yaml:

      memory:
        provider: openviking   # or honcho, mem0, hindsight, holographic, retaindb, byterover, supermemory

      كيف يعمل​

      عندما يكون أحد مزوّدي الذاكرة نشطًا، يقوم Hermes تلقائيًا بما يلي:

      1. حقن سياق المزوّد في system prompt (ما يعرفه المزوّد)
      2. الجلب المسبق للذكريات ذات الصلة قبل كل دور (في الخلفية، دون حجب)
      3. مزامنة أدوار المحادثة مع المزوّد بعد كل رد
      4. استخلاص الذكريات عند انتهاء الجلسة (للمزوّدين الذين يدعمون ذلك)
      5. عكس عمليات الكتابة إلى الذاكرة المدمجة على المزوّد الخارجي
      6. إضافة أدوات خاصة بالمزوّد كي يتمكن الوكيل من البحث في الذكريات وتخزينها وإدارتها

      تستمر الذاكرة المدمجة (MEMORY.md / USER.md) في العمل تمامًا كما كانت. فالمزوّد الخارجي إضافة إليها لا بديل عنها.

      المزوّدون المتاحون​

      Honcho​

      نمذجة للمستخدم عبر الجلسات مصمَّمة أصلًا للذكاء الاصطناعي (AI-native)، مع استدلال جدلي (dialectic reasoning)، وحقن للسياق ضمن نطاق الجلسة، وبحث دلالي، واستنتاجات (conclusions) دائمة. ويتضمن السياق الأساسي الآن ملخص الجلسة إلى جانب تمثيل المستخدم (representation) وبطاقات الـ peers (peer cards)، مما يمنح الوكيل وعيًا بما نوقش بالفعل.

      الأنسب لـالأنظمة متعددة الوكلاء التي تحتاج إلى سياق عبر الجلسات، والتوافق بين المستخدم والوكيل
      المتطلباتpip install honcho-ai + مفتاح API أو نسخة مستضافة ذاتيًا
      تخزين البياناتHoncho Cloud أو مستضاف ذاتيًا
      التكلفةحسب تسعير Honcho (سحابي) / مجاني (مستضاف ذاتيًا)

      الأدوات (5): honcho_profile (قراءة بطاقة الـ peer أو تحديثها)، honcho_search (بحث دلالي)، honcho_context (سياق الجلسة — الملخص، والتمثيل، والبطاقة، والرسائل)، honcho_reasoning (مُركَّب بواسطة LLM)، honcho_conclude (إنشاء الاستنتاجات أو حذفها)

      البنية المعمارية: حقن السياق على طبقتين — طبقة أساسية (ملخص الجلسة + التمثيل + بطاقة الـ peer، وتُحدَّث وفق contextCadence) إضافةً إلى ملحق جدلي (استدلال LLM، ويُحدَّث وفق dialecticCadence). ويختار المكوّن الجدلي تلقائيًا بين prompts البدء البارد (حقائق عامة عن المستخدم) و prompts البدء الدافئ (سياق ضمن نطاق الجلسة) بناءً على وجود السياق الأساسي من عدمه.

      ثلاثة مفاتيح إعداد متعامدة تتحكم في التكلفة والعمق كلٌّ على حدة:

      • contextCadence — عدد مرات تحديث الطبقة الأساسية (تكرار استدعاءات API)
      • dialecticCadence — عدد مرات تشغيل LLM الجدلي (تكرار استدعاءات LLM)
      • dialecticDepth — عدد تمريرات .chat() في كل استدعاء جدلي (1–3، عمق الاستدلال)

      كما يُكيّف المكوّن الجدلي المحقون تلقائيًا مستوى استدلاله حسب طول الاستعلام (استعلام أطول → استدلال أعمق، بحد أقصى reasoningLevelCap)؛ راجع مستوى الاستدلال المتكيّف مع الاستعلام.

      معالج الإعداد:

      hermes memory setup        # select "honcho" — runs the Honcho-specific post-setup

      لا يزال الأمر القديم hermes honcho setup يعمل (إذ يُعيد التوجيه الآن إلى hermes memory setup)، لكنه لا يُسجَّل إلا بعد اختيار Honcho مزوّدًا نشطًا للذاكرة.

      الأجهزة بلا واجهة رسومية / البعيدة: للمصادقة السحابية على جهاز لا يتوفر فيه متصفح (SSH، أو VM بعيد)، اختر device عند سؤال المعالج عن طريقة المصادقة. تطبع CLI رمزًا قصيرًا ورابط تحقق؛ افتح الرابط في متصفح على أي جهاز آخر، ووافق، فيكتمل الإعداد — دون نسخ مفتاح API ولصقه. ويختار المعالج هذا الخيار افتراضيًا بشكل تلقائي عندما لا يكتشف متصفحًا محليًا صالحًا للاستخدام.

      الإعدادات: $HERMES_HOME/honcho.json (محلي للـ profile) أو ~/.honcho/config.json (عام). ترتيب الأولوية: $HERMES_HOME/honcho.json > ~/.hermes/honcho.json > ~/.honcho/config.json. راجع مرجع الإعدادات ودليل التكامل مع Honcho.

      الانتقال من hermes honcho

      إذا كنت تستخدم سابقًا hermes honcho setup، فإن إعداداتك وجميع البيانات المخزنة على الخادم سليمة. ما عليك سوى إعادة التفعيل عبر معالج الإعداد مجددًا، أو ضبط memory.provider: honcho يدويًا لإعادة التفعيل عبر النظام الجديد.

      إعداد متعدد الـ peers:

      ينمذج Honcho المحادثات على أنها peers يتبادلون الرسائل — peer واحد للمستخدم إضافةً إلى peer للذكاء الاصطناعي لكل profile في Hermes، وجميعهم يتشاركون مساحة عمل واحدة. مساحة العمل هي البيئة المشتركة: فالـ peer الخاص بالمستخدم عام عبر الـ profiles، بينما لكل peer خاص بالذكاء الاصطناعي هويته المستقلة. ويبني كل peer للذكاء الاصطناعي تمثيلًا / بطاقة مستقلة من ملاحظاته الخاصة، بحيث يبقى profile coder موجّهًا نحو الكود بينما يبقى profile writer موجّهًا نحو التحرير مع المستخدم نفسه.

      التقابل بين المفاهيم:

      المفهومما هو
      مساحة العمل (Workspace)بيئة مشتركة. ترى جميع profiles الخاصة بـ Hermes ضمن مساحة عمل واحدة هوية المستخدم نفسها.
      peer المستخدم (User peer) (peerName)الإنسان. مشترك بين الـ profiles في مساحة العمل.
      peer الذكاء الاصطناعي (AI peer) (aiPeer)واحد لكل profile في Hermes. مفتاح المضيف hermes → الافتراضي؛ و hermes.<profile> للبقية.
      الملاحظة (Observation)مفاتيح تبديل لكل peer تتحكم فيما ينمذجه Honcho ومن رسائل مَن. directional (الافتراضي، المفاتيح الأربعة كلها مفعّلة) أو unified (مجمّع بمراقب واحد).

      profile جديد مع peer جديد في Honcho​

      hermes profile create coder --clone

      يُنشئ --clone كتلة مضيف hermes.coder في honcho.json مع aiPeer: "coder"، و workspace مشتركة، وقيم موروثة لكل من peerName، و recallMode، و writeFrequency، و observation، وغيرها. ويُنشأ الـ peer الخاص بالذكاء الاصطناعي في Honcho مسبقًا بحيث يكون موجودًا قبل الرسالة الأولى.

      profiles موجودة: إنشاء peers لها في Honcho بأثر رجعي​

      hermes honcho sync

      يفحص كل profile في Hermes، ويُنشئ كتل مضيف لأي profile يفتقر إليها، ويرث الإعدادات من الكتلة الافتراضية hermes، ويُنشئ الـ peers الجديدة الخاصة بالذكاء الاصطناعي مسبقًا. وهو متساوي الأثر (idempotent) — إذ يتخطى الـ profiles التي تمتلك كتلة مضيف بالفعل.

      الملاحظة لكل profile​

      يمكن لكل كتلة مضيف تجاوز إعدادات الملاحظة بشكل مستقل. مثال: profile يركّز على الكود، يلاحظ فيه الـ peer الخاص بالذكاء الاصطناعي المستخدمَ لكنه لا ينمذج نفسه:

      "hermes.coder": {
        "aiPeer": "coder",
        "observation": {
          "user": { "observeMe": true, "observeOthers": true },
          "ai":   { "observeMe": false, "observeOthers": true }
        }
      }

      مفاتيح تبديل الملاحظة (مجموعة واحدة لكل peer):

      المفتاحالتأثير
      observeMeيبني Honcho تمثيلًا لهذا الـ peer من رسائله الخاصة
      observeOthersيلاحظ هذا الـ peer رسائل الـ peer الآخر (مما يغذّي الاستدلال بين الـ peers)

      الإعدادات المسبقة عبر observationMode:

      • "directional" (الافتراضي) — الخيارات الأربعة كلها مفعّلة. ملاحظة متبادلة كاملة؛ ويُتيح الاستدلال الجدلي بين الـ peers.
      • "unified" — للمستخدم observeMe: true، وللذكاء الاصطناعي observeOthers: true، والبقية false. مجمّع بمراقب واحد؛ ينمذج الذكاء الاصطناعي المستخدمَ دون نفسه، والـ peer الخاص بالمستخدم ينمذج نفسه فقط.

      مفاتيح التبديل المضبوطة على الخادم عبر لوحة تحكم Honcho لها الأولوية على القيم الافتراضية المحلية — وتُزامَن مرة أخرى عند تهيئة الجلسة.

      راجع صفحة Honcho للاطلاع على المرجع الكامل للملاحظة.

      ربط الهويات في Gateway​

      يغطي نموذج الـ peers الموضّح أعلاه جلسات CLI و TUI و Desktop، حيث تُحال كل محادثة إلى peerName. أما الـ gateway فيضيف محورًا ثانيًا: إذ يصل المستخدمون بمعرّفات وقت تشغيل خاصة بكل منصة (Telegram UID، و Discord snowflake، و Slack user)، وتحدد ثلاثة مفاتيح الـ peer الذي يُحال إليه كل معرّف.

      المفتاحالتأثير
      pinUserPeer: trueيُدمج كل مستخدم للـ gateway ليس وكيلًا في peerName. ويُفحص هذا التثبيت أولًا، لذا فهو يتجاوز جميع الأسماء المستعارة — اختره فقط عندما لا تحتاج أي هوية من جهة المستخدمين إلى peer خاص بها
      userPeerAliasesيربط معرّفات وقت تشغيل محددة بـ peers ({"7654321": "alice"}). وهو الموضع المناسب لتوجيه الهويات المتمايزة — بما في ذلك الوكلاء الذين يحمل كلٌّ منهم peer خاصًا به
      runtimePeerPrefixيضيف نطاق أسماء لأي معرّف وقت تشغيل غير مربوط (telegram_7654321) كي لا تتصادم المعرّفات المتشابهة الشكل بين المنصات

      خارج الـ gateway، لا تفعل هذه المفاتيح شيئًا. ولا يسأل hermes memory setup عنها إلا عندما يكتشف منصة gateway متصلة. راجع صفحة Honcho للاطلاع على تسلسل الحلّ (resolver ladder) وخطوات الإعداد.

      راجع مرجع الإعدادات ودليل التكامل مع Honcho.

      OpenViking​

      قاعدة بيانات للسياق من Volcengine (ByteDance) تتميز بتسلسل هرمي للمعرفة على غرار نظام الملفات، واسترجاع متدرّج المستويات، واستخلاص تلقائي للذكريات ضمن 6 فئات.

      الأنسب لـإدارة المعرفة المستضافة ذاتيًا مع تصفّح منظَّم
      المتطلباتأن يكون OpenViking مُهيّأً ومُتحقَّقًا منه وقيد التشغيل
      تخزين البياناتمستضاف ذاتيًا (محليًا أو في السحابة)
      التكلفةمجاني (مفتوح المصدر، AGPL-3.0)

      الأدوات (6): viking_search (بحث دلالي)، viking_read (متدرّج: abstract/overview/full)، viking_browse (التنقل في نظام الملفات)، viking_remember (تخزين الحقائق)، viking_forget (حذف ملف ذاكرة بواسطة URI viking:// الدقيق)، viking_add_resource (استيعاب عناوين URL والمستندات)

      الإعداد:

      # Prepare OpenViking first
      openviking-server init
      openviking-server doctor
      openviking-server

      # Then configure Hermes
      hermes memory setup    # select "openviking"
      # Or manually:
      hermes config set memory.provider openviking

      يستطيع hermes memory setup إعادة استخدام قيم الاتصال أو نسخها من ~/.openviking/ovcli.conf. أما الإعداد اليدوي فيستخدم ملف .env الخاص بالـ profile النشط؛ وهو بالنسبة إلى الـ profile الافتراضي ~/.hermes/.env، أما الـ profiles المسمّاة فاستخدم لها ~/.hermes/profiles/<profile>/.env.

      OPENVIKING_ENDPOINT=http://127.0.0.1:1933
      # OPENVIKING_API_KEY=...
      # OPENVIKING_ACCOUNT=default
      # OPENVIKING_USER=default

      توجد إعدادات خادم OpenViking في ov.conf (--config، أو OPENVIKING_CONFIG_FILE، أو ~/.openviking/ov.conf). أما قيم اتصال العميل فتوجد في ovcli.conf (OPENVIKING_CLI_CONFIG_FILE أو ~/.openviking/ovcli.conf).

      الميزات الرئيسية:

      • تحميل متدرّج للسياق: L0 (~100 token) → L1 (~2k) → L2 (كامل)
      • استخلاص تلقائي للذكريات عند تثبيت الجلسة (session commit) (الملف الشخصي، والتفضيلات، والكيانات، والأحداث، والحالات، والأنماط)
      • مخطط URI viking:// لتصفّح المعرفة بشكل هرمي

      يُستخدم OPENVIKING_ACCOUNT و OPENVIKING_USER في الوضع المحلي/الموثوق. وهوية الـ peer اختيارية. فافتراضيًا، لا يرسل Hermes أي معرّف peer ويكتب الذكريات الصريحة إلى viking://user/<user>/memories/.... ولا يسأل الإعداد عن معرّف peer. وللحصول على سياق منفصل للمساعد، اضبط memory.openviking.agent: work-assistant في config.yaml.

      تحتفظ إعدادات الـ peer الموجودة غير الفارغة بعمليات الكتابة والاسترجاع ضمن نطاق الـ peer. ويشمل ذلك OPENVIKING_AGENT و actor_peer_id أو agent_id القديم في إعدادات OpenViking المرتبطة. ولا تُنقل الذكريات الموجودة ولا تُحذف. ومن دون معرّف peer، يغطي البحث الافتراضي ذاكرة المستخدم وذكريات الـ peers الموجودة تحت مستخدم OpenViking نفسه. وتبقى ذكريات الـ peers القديمة قابلة للبحث في مساراتها الحالية. ويحدد الترتيب وحدود النتائج الذكريات التي تُعاد. اضبط memory.openviking.agent: hermes لاستعادة عمليات الكتابة القديمة ضمن نطاق الـ peer. أما الذكريات المكتوبة ضمن نطاق المستخدم قبل هذا التغيير فتبقى هناك وتظل قابلة للبحث. فهذا الإعداد يغيّر عمليات الكتابة المستقبلية، لا مواقع الذكريات الموجودة.

      يرسل Hermes الترويسة User-Agent: openviking-memory-hermes/<version> مع طلبات OpenViking. وهذا المعرّف القياسي للأداة لا يحتوي على أي معرّف خاص بالمستخدم، ولا يُضيف طلبًا منفصلًا.

      Mem0​

      استخلاص للحقائق بواسطة LLM على جانب الخادم، مع بحث دلالي، وإعادة ترتيب النتائج (reranking)، وإزالة تلقائية للتكرار. يتوفر بثلاثة أوضاع اتصال: Platform (Mem0 Cloud)، ولوحة تحكم مستضافة ذاتيًا (خادم Mem0 تشغّله عبر Docker)، و OSS (Mem0 داخل العملية مع LLM ومخزن متجهات خاصين بك).

      الأنسب لـإدارة الذاكرة دون تدخّل — إذ يتولى Mem0 الاستخلاص تلقائيًا
      المتطلباتpip install mem0ai + مفتاح API (platform)، أو خادم Mem0 قيد التشغيل (لوحة تحكم مستضافة ذاتيًا)، أو LLM + مخزن متجهات (OSS)
      تخزين البياناتMem0 Cloud (platform)، أو خادم Mem0 الخاص بك (لوحة تحكم مستضافة ذاتيًا)، أو داخل العملية (OSS)
      التكلفةحسب تسعير Mem0 (platform) / مجاني (مستضاف ذاتيًا أو OSS)

      الأدوات (4): mem0_search (بحث دلالي؛ مع إعادة ترتيب اختيارية في وضع platform، معطّلة افتراضيًا)، mem0_add (تخزين الحقائق حرفيًا)، mem0_update (التحديث بواسطة المعرّف)، mem0_delete (الحذف بواسطة المعرّف)

      الإعداد (Platform):

      hermes memory setup    # select "mem0" → "Platform"
      # Or manually:
      hermes config set memory.provider mem0
      echo "MEM0_API_KEY=your-key" >> ~/.hermes/.env

      الإعداد (OSS):

      hermes memory setup    # select "mem0" → "Open Source (self-hosted)"
      # Or via flags:
      hermes memory setup mem0 --mode oss --oss-llm openai --oss-llm-key sk-... --oss-vector qdrant

      معاينة دون كتابة ملفات:

      hermes memory setup mem0 --mode oss --oss-llm-key sk-... --dry-run

      الإعداد (لوحة تحكم مستضافة ذاتيًا): اتصل بخادم Mem0 تشغّله عبر Docker (واجهة REST API الخاصة بلوحة التحكم):

      hermes memory setup    # select "mem0" → "Self-hosted server"
      # Or via flags:
      hermes memory setup mem0 --mode selfhosted --host http://localhost:8888 --api-key your-admin-api-key

      أو اضبطه يدويًا — إما عبر متغيرات البيئة:

      echo "MEM0_HOST=http://localhost:8888" >> ~/.hermes/.env
      echo "MEM0_API_KEY=your-admin-api-key" >> ~/.hermes/.env

      أو في mem0.json:

      { "host": "http://localhost:8888", "api_key": "your-admin-api-key" }

      تُصادق الإضافة باستخدام X-API-Key وتستخدم مسارات الخادم /search / /memories. والمفتاح api_key اختياري (احذفه فقط مع الخوادم التي تعمل بـ AUTH_DISABLED). لا تضبط mode: oss — لأن له الأولوية على host.

      الإعدادات: $HERMES_HOME/mem0.json (إعدادات السلوك). ولا يوضع إلا السر MEM0_API_KEY في ~/.hermes/.env.

      المفتاحالقيمة الافتراضيةالوصف
      modeplatformplatform (Mem0 Cloud) أو oss (مُدار ذاتيًا، داخل العملية)
      host—عنوان URL لخادم Mem0 المستضاف ذاتيًا (لوحة تحكم Docker). يوجّه الطلبات عبر HTTP مع X-API-Key؛ لا تجمعه مع mode: oss
      user_idhermes-userمعرّف المستخدم
      agent_idhermesمعرّف الوكيل
      rerankfalseإعادة ترتيب نتائج البحث حسب الصلة (في وضع platform فقط)
      sync_max_chars450حد أقصى للأحرف في كل رسالة يُطبَّق قبل إرسال كل دور لاستخلاص الحقائق، ويُقتطع النص عند آخر حد لجملة. تناسب القيمة الافتراضية نماذج التضمين (embedders) ذات 512 token (Ollama bge-small-zh-v1.5، all-minilm)؛ ارفعها (مثلًا إلى 6000) لنماذج التضمين ذات 8k token مثل text-embedding-3-small أو jina-embeddings-v3 أو bge-m3

      المزوّدون المدعومون في OSS:

      المكوّنالمزوّدون
      LLMopenai، ollama
      نموذج التضمين (Embedder)openai، ollama
      مخزن المتجهات (Vector Store)qdrant (محلي/خادم)، pgvector

      التبديل بين الأوضاع: أعد تشغيل hermes memory setup mem0 --mode <platform|selfhosted|oss> أو عدّل mem0.json مباشرةً.

      Hindsight​

      ذاكرة طويلة الأمد مع رسم بياني معرفي (knowledge graph)، وتحديد الكيانات (entity resolution)، واسترجاع متعدد الاستراتيجيات. توفّر الأداة hindsight_reflect تركيبًا عبر الذكريات لا يقدّمه أي مزوّد آخر. ويحتفظ تلقائيًا بأدوار المحادثة كاملة (بما في ذلك استدعاءات الأدوات) مع تتبّع المستندات على مستوى الجلسة.

      الأنسب لـالاسترجاع المعتمد على الرسم البياني المعرفي مع العلاقات بين الكيانات
      المتطلباتالسحابي: مفتاح API من ui.hindsight.vectorize.io. المحلي: مفتاح API لـ LLM (OpenAI، أو Groq، أو OpenRouter، وغيرها)
      تخزين البياناتHindsight Cloud أو PostgreSQL مضمّن محليًا
      التكلفةحسب تسعير Hindsight (سحابي) أو مجاني (محلي)

      الأدوات: hindsight_retain (تخزين مع استخلاص الكيانات)، hindsight_recall (بحث متعدد الاستراتيجيات)، hindsight_reflect (تركيب عبر الذكريات)

      الإعداد:

      hermes memory setup    # select "hindsight"
      # Or manually:
      hermes config set memory.provider hindsight
      echo "HINDSIGHT_API_KEY=your-key" >> ~/.hermes/.env

      يثبّت معالج الإعداد الاعتماديات تلقائيًا، ولا يثبّت إلا ما يلزم للوضع المختار (hindsight-client للسحابي، و hindsight-all للمحلي). يتطلب hindsight-client >= 0.4.22 (وتجري ترقيته تلقائيًا عند بدء الجلسة إذا كان قديمًا).

      واجهة المستخدم في الوضع المحلي: hindsight-embed -p hermes ui start

      الإعدادات: $HERMES_HOME/hindsight/config.json

      المفتاحالقيمة الافتراضيةالوصف
      modecloudcloud أو local
      bank_idhermesمعرّف بنك الذاكرة
      recall_budgetmidمدى شمولية الاسترجاع: low / mid / high
      memory_modehybridhybrid (سياق + أدوات)، context (حقن تلقائي فقط)، tools (أدوات فقط)
      auto_retaintrueالاحتفاظ بأدوار المحادثة تلقائيًا
      auto_recalltrueاسترجاع الذكريات تلقائيًا قبل كل دور

      retain_contextconversation between Hermes Agent and the Userتسمية السياق للذكريات المحتفَظ بها
      retain_tags—الوسوم الافتراضية المطبّقة على الذكريات المحتفَظ بها؛ وتُدمج مع وسوم الأداة الخاصة بكل استدعاء
      retain_source—قيمة metadata.source اختيارية تُرفق بالذكريات المحتفَظ بها
      retain_user_prefixUserالتسمية المستخدمة قبل أدوار المستخدم في النصوص المحتفَظ بها تلقائيًا

      Holographic​

      مخزن حقائق محلي على SQLite مع بحث نصي كامل FTS5، وتقييم للثقة، و HRR (Holographic Reduced Representations) للاستعلامات الجبرية التركيبية.

      الأنسب لـذاكرة محلية فقط مع استرجاع متقدم، ودون اعتماديات خارجية
      المتطلباتلا شيء (SQLite متاح دائمًا). و NumPy اختياري لجبر HRR.
      تخزين البياناتSQLite محلي
      التكلفةمجاني

      الأدوات: fact_store (9 إجراءات: add، search، probe، related، reason، contradict، update، remove، list)، fact_feedback (تقييم helpful/unhelpful يُدرّب درجات الثقة)

      الإعداد:

      hermes memory setup    # select "holographic"
      # Or manually:
      hermes config set memory.provider holographic

      الإعدادات: config.yaml تحت plugins.hermes-memory-store

      المفتاحالقيمة الافتراضيةالوصف
      db_path$HERMES_HOME/memory_store.dbمسار قاعدة بيانات SQLite
      auto_extractfalseاستخلاص الحقائق تلقائيًا عند نهاية الجلسة
      default_trust0.5درجة الثقة الافتراضية (0.0–1.0)

      القدرات الفريدة:

      • probe — استرجاع جبري خاص بكيان محدد (جميع الحقائق عن شخص/شيء ما)
      • reason — استعلامات AND تركيبية عبر عدة كيانات
      • contradict — اكتشاف آلي للحقائق المتعارضة
      • تقييم الثقة بتغذية راجعة غير متماثلة (+0.05 لـ helpful / -0.10 لـ unhelpful)

      ByteRover​

      ذاكرة دائمة عبر أداة CLI المسماة brv — شجرة معرفة هرمية مع استرجاع متدرّج (بحث نصي تقريبي (fuzzy) → بحث يقوده LLM). تعتمد على التخزين المحلي أولًا مع مزامنة سحابية اختيارية.

      الأنسب لـالمطوّرون الذين يريدون ذاكرة محمولة ومحلية أولًا عبر CLI
      المتطلباتByteRover CLI (npm install -g byterover-cli أو سكربت التثبيت)
      تخزين البياناتمحلي (الافتراضي) أو ByteRover Cloud (مزامنة اختيارية)
      التكلفةمجاني (محلي) أو حسب تسعير ByteRover (سحابي)

      الأدوات: brv_query (البحث في شجرة المعرفة)، brv_curate (تخزين الحقائق/القرارات/الأنماط)، brv_status (إصدار CLI + إحصاءات الشجرة)

      الإعداد:

      # Install the CLI first
      curl -fsSL https://byterover.dev/install.sh | sh

      # Then configure Hermes
      hermes memory setup    # select "byterover"
      # Or manually:
      hermes config set memory.provider byterover

      الميزات الرئيسية:

      • استخلاص تلقائي قبل الضغط (يحفظ الأفكار المستخلصة قبل أن يتخلص منها ضغط السياق)
      • تُخزَّن شجرة المعرفة في $HERMES_HOME/byterover/ (ضمن نطاق الـ profile)
      • مزامنة سحابية حاصلة على شهادة SOC2 Type II (اختيارية)

      Supermemory​

      ذاكرة دلالية طويلة الأمد مع استرجاع الملف الشخصي، وبحث دلالي، وأدوات ذاكرة صريحة، واستيعاب المحادثة عند نهاية الجلسة عبر Supermemory graph API.

      الأنسب لـالاسترجاع الدلالي مع بناء ملف تعريفي للمستخدم ورسم بياني على مستوى الجلسة
      المتطلباتpip install supermemory + مفتاح API سحابي، أو خادم مستضاف ذاتيًا
      تخزين البياناتSupermemory Cloud أو مستضاف ذاتيًا
      التكلفةحسب تسعير Supermemory (سحابي) / مجاني (مستضاف ذاتيًا)

      الأدوات: supermemory_store (حفظ ذكريات صريحة)، supermemory_search (بحث بالتشابه الدلالي)، supermemory_forget (النسيان بواسطة المعرّف أو بأفضل استعلام مطابق)، supermemory_profile (الملف الشخصي الدائم + السياق الحديث)

      الإعداد:

      hermes memory setup    # select "supermemory"
      # Or manually:
      hermes config set memory.provider supermemory
      echo 'SUPERMEMORY_API_KEY=***' >> ~/.hermes/.env

      إعداد النسخة المستضافة ذاتيًا:

      npx supermemory local

      قبل تشغيل hermes memory setup، اضبط base_url في $HERMES_HOME/supermemory.json:

      {
        "base_url": "http://localhost:6767"
      }

      ثم شغّل hermes memory setup وأدخل مفتاح API الذي يطبعه الخادم المحلي. فضبط الـ endpoint أولًا يضمن أن يبقى فحص الاتصال أثناء الإعداد محليًا أيضًا.

      الإعدادات: $HERMES_HOME/supermemory.json

      المفتاحالقيمة الافتراضيةالوصف
      base_urlhttps://api.supermemory.aiالـ endpoint الخاص بـ API لنسخة Supermemory المستضافة أو المستضافة ذاتيًا. له الأولوية على SUPERMEMORY_BASE_URL.
      container_taghermesوسم الحاوية (container tag) المستخدم للبحث والكتابة. يدعم القالب {identity} للوسوم الخاصة بنطاق الـ profile.
      auto_recalltrueحقن سياق الذاكرة ذي الصلة قبل الأدوار
      auto_capturetrueتخزين أدوار المستخدم والمساعد بعد تنظيفها عقب كل رد
      max_recall_results10الحد الأقصى للعناصر المسترجعة التي تُنسَّق ضمن السياق
      profile_frequency50تضمين حقائق الملف الشخصي في الدور الأول ثم كل N دورًا
      capture_modeallتخطي الأدوار الصغيرة جدًا أو التافهة افتراضيًا
      search_modehybridوضع البحث: hybrid، أو memories، أو documents
      api_timeout5.0المهلة الزمنية لطلبات SDK والاستيعاب

      متغيرات البيئة: SUPERMEMORY_API_KEY (مطلوب)، SUPERMEMORY_BASE_URL (قيمة احتياطية للتوافق عندما لا يكون base_url مضبوطًا)، SUPERMEMORY_CONTAINER_TAG (يتجاوز ملف الإعدادات).

      ترتيب أولوية عنوان URL الأساسي هو supermemory.json → SUPERMEMORY_BASE_URL → https://api.supermemory.ai. وتستخدم عمليات SDK، وفحوص الإعداد/الحالة، واستيعاب المحادثات جميعها الـ endpoint الذي جرى تحديده.

      الميزات الرئيسية:

      • تسييج تلقائي للسياق (context fencing) — يزيل الذكريات المسترجعة من الأدوار الملتقطة لمنع التلوث التكراري للذاكرة
      • استيعاب الجلسة كاملة — تُرسل المحادثة بأكملها مرة واحدة عند حدود الجلسة
      • استيعاب المحادثة عند نهاية الجلسة (إلى /v4/conversations) لبناء ملف شخصي ورسم بياني أغنى في Supermemory
      • توجيه مستضاف ذاتيًا من طرف إلى طرف — تستخدم طلبات SDK والفحص واستيعاب المحادثات الـ endpoint المضبوط نفسه
      • تُحقن حقائق الملف الشخصي في الدور الأول وعلى فترات قابلة للضبط
      • حاويات ضمن نطاق الـ profile — استخدم {identity} في container_tag (مثل hermes-{identity} → hermes-coder) لعزل الذكريات لكل profile في Hermes
      • وضع الحاويات المتعددة — فعّل enable_custom_container_tags مع قائمة custom_containers للسماح للوكيل بالقراءة والكتابة عبر حاويات مسمّاة. أما العمليات التلقائية فتبقى على الحاوية الأساسية.
      مثال على الحاويات المتعددة
      {
        "container_tag": "hermes",
        "enable_custom_container_tags": true,
        "custom_containers": ["project-alpha", "shared-knowledge"],
        "custom_container_instructions": "Use project-alpha for coding context."
      }

      الدعم: Discord · support@supermemory.com

      Memori​

      ذاكرة منظَّمة طويلة الأمد باستخدام Memori Cloud، مع التقاط الأدوار المكتملة في الخلفية، وسياق للأدوار يراعي الأدوات، وأدوات استرجاع صريحة للحقائق، والملخصات، والحصة، والتسجيل، والملاحظات.

      الأنسب لـاسترجاع يتحكم فيه الوكيل مع إسناد منظَّم إلى المشروع والجلسة
      المتطلباتpip install hermes-memori + hermes-memori install + مفتاح Memori API
      تخزين البياناتMemori Cloud
      التكلفةحسب تسعير Memori

      الأدوات: memori_recall (البحث في الذاكرة طويلة الأمد)، memori_recall_summary (سياق ملخّص)، memori_quota (الاستخدام/الحصة)، memori_signup (طلب رسالة بريد إلكتروني للتسجيل)، memori_feedback (إرسال ملاحظات حول التكامل)

      الإعداد:

      pip install hermes-memori
      hermes-memori install
      hermes config set memory.provider memori
      hermes memory setup

      المزوّدالتخزينالتكلفةالأدواتالاعتمادياتالميزة الفريدة

      عزل الـ Profiles​

      تُعزل بيانات كل مزوّد لكل profile على حدة:

      • مزوّدو التخزين المحلي (Holographic، و ByteRover) يستخدمون مسارات $HERMES_HOME/ التي تختلف من profile إلى آخر
      • المزوّدون المعتمدون على ملفات الإعدادات (Honcho، و Mem0، و Hindsight، و Supermemory) يخزّنون الإعدادات في $HERMES_HOME/، لذا يكون لكل profile بيانات اعتماده الخاصة
      • المزوّدون السحابيون (RetainDB) يشتقّون تلقائيًا أسماء مشاريع خاصة بنطاق كل profile
      • المزوّدون المعتمدون على متغيرات البيئة (OpenViking) يُضبطون عبر ملف .env الخاص بكل profile

      بيئة تشغيل Codex App-Server

      يمكن لـ Hermes اختياريًا تسليم أدوار openai/* و openai-codex/* إلى Codex CLI app-server بدلًا من تشغيل حلقة الأدوات الخاصة به. عند التفعيل، تُنفَّذ أوامر الطرفية وتعديلات الملفات والـ sandboxing واستدعاءات أدوات MCP جميعها داخل بيئة تشغيل Codex — ويصبح Hermes الغلاف المحيط بها (قاعدة بيانات الجلسات، و slash commands، والـ gateway، ومراجعة الذاكرة والمهارات).

      هذه الميزة اختيارية بالكامل (opt-in). يبقى سلوك Hermes الافتراضي دون تغيير ما لم تفعّل الخيار. ولا يوجّهك Hermes تلقائيًا أبدًا إلى بيئة التشغيل هذه.

      نصيحة

      لا تستخدم OpenAI Codex؟ يضبط الأمر hermes setup --portal backend غير تابع لـ Codex مع Claude/Gemini وغيرها في خطوة واحدة. راجع Nous Portal.

      لماذا؟​

      • شغّل أدوار وكيل OpenAI على اشتراك ChatGPT الخاص بك (دون الحاجة إلى مفتاح API) باستخدام مسار المصادقة نفسه الذي يستخدمه Codex CLI.
      • استخدم toolset و sandbox الخاصين بـ Codex — shell للطرفية/القراءة/الكتابة/البحث، و apply_patch للتعديلات المنظّمة، و update_plan للتخطيط، وكلها تعمل داخل sandboxing من نوع seatbelt/landlock.
      • إضافات Codex الأصلية (Native Codex plugins) — مثل Linear و GitHub و Gmail و Calendar و Canva وغيرها — المثبّتة عبر codex plugin تُرحَّل تلقائيًا وتكون نشطة في جلسة Hermes.
      • أدوات Hermes الأغنى تأتي معها — تعمل web_search و web_extract وأتمتة المتصفح والرؤية (vision) وتوليد الصور والمهارات و TTS عبر MCP callback. إذ يعود Codex إلى Hermes لاستدعاء الأدوات غير المدمجة فيه.
      • تستمر تنبيهات الذاكرة والمهارات (nudges) في العمل — تُسقَط أحداث Codex على بنية رسائل Hermes، فترى حلقة التحسين الذاتي سجل محادثة يبدو عاديًا.

      الأدوات المتاحة فعليًا للنموذج​

      هذا هو الجزء الذي يريد معظم المستخدمين معرفته مسبقًا. عند تفعيل بيئة التشغيل هذه، يكون لدى النموذج الذي يشغّل دورك ثلاثة مصادر مستقلة للأدوات:

      1. الـ toolset المدمج في Codex (مفعّل دائمًا)​

      تأتي هذه الأدوات مع codex app-server نفسه — دون تدخل من Hermes، ودون MCP، ودون إضافات. والأدوات الخمس كلها متاحة لحظة بدء بيئة التشغيل:

      • shell — تشغّل أي أوامر shell داخل الـ sandbox. وبها يقرأ النموذج الملفات (cat، head، tail)، ويكتبها (echo > foo، و heredocs)، ويبحث فيها (find، rg، grep)، ويتنقل بين الأدلة (ls، cd)، ويشغّل عمليات البناء، ويدير العمليات، وأي شيء آخر قد تفعله في bash.
      • apply_patch — تطبّق diff منظّمًا متعدد الملفات بصيغة patch الخاصة بـ Codex. يستخدمها النموذج لتعديلات الكود غير البسيطة (مثل إضافة دالة، أو إعادة الهيكلة عبر عدة ملفات)؛ ولا تزال heredocs في الـ shell متاحة لعمليات الكتابة لمرة واحدة.
      • update_plan — متتبّع المهام / الخطط الداخلي في codex. وهو مكافئ لأداة todo في Hermes، لكنه يُدار بالكامل داخل بيئة تشغيل codex.
      • view_image — تحمّل ملف صورة محليًا إلى المحادثة كي يتمكن النموذج من رؤيته.
      • web_search — لدى codex بحث ويب مدمج خاص به عند إعداده. كما يتيح Hermes أيضًا web_search (المعتمد على Firecrawl) عبر الـ callback الموضح أدناه؛ ويختار النموذج أيهما يفضّل.

      لذا فإن كل ما قد تفعله عبر الطرفية — القراءة/الكتابة/البحث/الإيجاد/التشغيل — يفعله codex بشكل أصلي. ويتحكم profile الـ sandbox (وهو :workspace افتراضيًا عند تفعيل بيئة التشغيل) فيما يمكن الكتابة إليه.

      2. إضافات Codex الأصلية (تُرحَّل تلقائيًا من تثبيت codex plugin لديك)​

      عند تفعيل بيئة التشغيل، يستعلم Hermes عبر plugin/list RPC الخاص بـ codex، ويكتب مدخلًا [plugins."<name>@openai-curated"] لكل إضافة ثبّتها. أما الإضافات نفسها فيديرها codex، ويُصرَّح لها مرة واحدة عبر واجهة codex الخاصة.

      أمثلة (تلك التي أبرزها نقاش OpenClaw على أنها "تستحق فيديو على YouTube"):

      • Linear — إيجاد issues وتحديثها
      • GitHub — البحث في الكود، وعرض PRs، والتعليق
      • Gmail — قراءة البريد وإرساله
      • Google Calendar — إنشاء الأحداث وإيجادها
      • Outlook calendar/email — البنية نفسها عبر موصّل Microsoft
      • Canva — توليد التصاميم
      • ...وأي شيء آخر ثبّتته عبر codex plugin marketplace add openai-curated + codex plugin install ...

      ما لا يُرحَّل:

      • الإضافات التي لم تثبّتها بعد — ثبّتها في Codex أولًا.
      • مدخلات متجر تطبيقات ChatGPT (app/list) — فهي مفعّلة مسبقًا داخل codex بحكم مصادقة حسابك.

      3. الـ tool callback الخاص بـ Hermes (خادم MCP مسجّل في ~/.codex/config.toml)​

      يسجّل Hermes نفسه كخادم MCP كي يتمكن codex من استدعائه للأدوات التي لا تأتي مع codex. المتاح عبر الـ callback:

      • web_search / web_extract — معتمدتان على Firecrawl؛ وتميلان إلى تقديم نتائج أنظف من الـ scraping للمحتوى المنظّم.
      • browser_navigate / browser_click / browser_type / browser_press / browser_snapshot / browser_scroll / browser_back / browser_get_images / browser_console / browser_vision — أتمتة كاملة للمتصفح عبر Camofox أو Browserbase.
      • vision_analyze — تستدعي نموذج رؤية منفصلًا لفحص صورة (وهي تختلف عن view_image في codex التي تحمّل الصورة إلى المحادثة).
      • image_generate — توليد الصور عبر سلسلة إضافات image_gen في Hermes.
      • skill_view / skills_list — القراءة من مكتبة مهارات Hermes.
      • text_to_speech — TTS عبر المزوّد المضبوط في Hermes.

      عندما يريد النموذج إحدى هذه الأدوات، يُنشئ codex العملية الفرعية hermes_tools_mcp_server عبر stdio MCP، ويُوزَّع الاستدعاء عبر model_tools.handle_function_call() (مسار الكود نفسه في بيئة تشغيل Hermes الافتراضية)، وتُعاد النتيجة إلى codex مثل أي استجابة MCP أخرى.

      ما لا يتوفر في بيئة التشغيل هذه​

      تتطلب أدوات Hermes الأربع التالية سياق AIAgent قيد التشغيل (حالة منتصف الحلقة) كي تُوزَّع، ولا يستطيع MCP callback عديم الحالة تشغيلها. عُد إلى بيئة التشغيل الافتراضية (/codex-runtime auto) عندما تحتاج إلى أي منها:

      • delegate_task — إنشاء subagents
      • memory — مخزن الذاكرة الدائمة في Hermes
      • session_search — البحث عبر الجلسات
      • todo — مخزن المهام في Hermes (والأداة update_plan في codex هي المكافئ داخل بيئة التشغيل)

      ميزات سير العمل (/goal، و kanban، و cron)​

      /goal (حلقة Ralph)​

      يعمل في بيئة التشغيل هذه. تُحفظ الأهداف في state_meta مفهرسةً بمعرّف الجلسة، ويُعاد prompt المتابعة كرسالة مستخدم عادية عبر run_conversation()، وينفّذ codex الدور التالي بشكل أصلي. ويعمل حَكَم الأهداف (goal judge) عبر العميل المساعد (المضبوط عبر auxiliary.goal_judge في config.yaml)، بمعزل عن بيئة التشغيل النشطة. ويُعد حكم الحَكَم "blocked, needs user input" مخرجًا نظيفًا إذا تعثّر codex عند الموافقات.

      أمر يجب الانتباه إليه: كل prompt متابعة هو دور جديد في codex، ما يعني أن codex يعيد تقييم سياسة الموافقة على الأوامر من الصفر. إذا كنت تنفّذ هدفًا طويل الأمد بكثير من عمليات الكتابة، فتوقّع طلبات موافقة أكثر مما قد تراه في مهمة واحدة داخل الجلسة. اضبط default_permissions = ":workspace" (وهو ما يفعله Hermes تلقائيًا عند تفعيل بيئة التشغيل) كي لا تتطلب عمليات الكتابة البسيطة في مساحة العمل طلب موافقة.

      Kanban (توزيع worktree متعدد الوكلاء)​

      يعمل في بيئة التشغيل هذه، مع اعتمادية دقيقة واحدة. يُنشئ مُوزِّع kanban كل عامل كعملية فرعية منفصلة hermes chat -q تقرأ إعدادات المستخدم — ما يعني أنه إذا ضُبط model.openai_runtime: codex_app_server على المستوى العام، فإن العمّال أيضًا سيعملون على بيئة تشغيل codex.

      ما يعمل داخل عامل يستخدم بيئة تشغيل codex:

      • الـ toolset الكامل في Codex (shell و apply_patch و update_plan و view_image و web_search) — ينفّذ العامل عمله الفعلي على المهمة بشكل أصلي
      • إضافات codex المُرحَّلة — Linear و GitHub وغيرها
      • الـ tool callback الخاص بـ Hermes لأدوات browser_* والرؤية و image_gen والمهارات و TTS

      وما يعمل أيضًا لأن MCP callback يتيحه:

      • kanban_complete / kanban_block / kanban_comment / kanban_heartbeat — أدوات التسليم (handoff) الخاصة بالعامل. تقرأ هذه الأدوات HERMES_KANBAN_TASK من البيئة (يضبطه المُوزِّع)، وتتحكم في الوصول بشكل صحيح، وتكتب إلى قاعدة بيانات SQLite الخاصة بكل لوحة والمثبّتة عبر HERMES_KANBAN_DB. ولولا وجودها في الـ callback، لتمكّن العامل في بيئة التشغيل هذه من أداء مهمته دون أن يستطيع الإبلاغ عنها، فيبقى معلّقًا حتى انتهاء مهلة المُوزِّع.
      • kanban_show / kanban_list — استعلامات على اللوحة للقراءة فقط كي يتحقق العامل من سياقه الخاص.
      • kanban_create / kanban_unblock / kanban_link — عمليات خاصة بالمنسّق (orchestrator) فقط. متاحة لوكلاء المنسّق العاملين على بيئة تشغيل codex الذين يحتاجون إلى توزيع مهام جديدة.

      تُقيَّد أدوات kanban بمتغير البيئة HERMES_KANBAN_TASK الذي يضبطه المُوزِّع — ويُمرَّر هذا المتغير إلى العملية الفرعية لـ codex (إذ يرث codex البيئة) ومنها إلى العملية الفرعية لخادم MCP المسمى hermes-tools التي يُنشئها. لذا ترى الأدوات معرّف المهمة الصحيح وتتحكم في الوصول بشكل صحيح. ولعمّال Codex app-server، يمرّر Hermes أيضًا تجاوزات sandbox ضيقة إلى app-server عند وجود HERMES_KANBAN_TASK: الإبقاء على sandboxing من نوع workspace-write، وإضافة دليل قاعدة بيانات اللوحة إضافة إلى كل مسار Kanban ثبّته المُوزِّع كجذور إضافية قابلة للكتابة (HERMES_KANBAN_WORKSPACES_ROOT، و HERMES_KANBAN_WORKSPACE، و HERMES_KANBAN_ROOT القديم — مع إزالة التكرار، ودليل قاعدة البيانات أولًا)، وإبقاء الشبكة معطّلة افتراضيًا. يتجنب هذا الحلَّ البديل الهش :danger-no-sandbox، مع السماح لـ kanban_complete / kanban_block بتحديث قاعدة بيانات اللوحة و السماح للعمّال بكتابة التقارير/الملفات الناتجة تحت نقاط تركيب مساحات العمل الموجودة خارج دليل قاعدة البيانات (مثل /media/.../kanban-workspaces/... على قرص منفصل — issue #27941).

      مهام Cron​

      لم يُختبر تحديدًا. تعمل مهام cron عبر cronjob → AIAgent.run_conversation، وهو مسار الكود نفسه في CLI. إذا كانت إعدادات مهمة cron تحتوي على openai_runtime: codex_app_server فستعمل على codex. وتنطبق قواعد توفر الأدوات نفسها — تعمل أدوات codex المدمجة + الإضافات + MCP callback، بينما لا تعمل أدوات حلقة الوكيل (delegate_task و memory و session_search و todo). إذا كانت مهمة cron لديك تعتمد على تلك الأدوات، فاجعل نطاقها profile يستخدم بيئة التشغيل الافتراضية.

      العرض الحي​

      رغم أن حلقة الوكيل تعمل داخل العملية الفرعية لـ Codex، فإن بيئة التشغيل تربط تدفق أحداث Codex بمسار العرض نفسه الذي تستخدمه بيئة التشغيل الافتراضية:

      • تظهر الأجزاء الحية المتدفقة (deltas) من رد المساعد، والاستدلال (بما في ذلك أجزاء الملخص)، وأحداث بدء الأدوات واكتمالها ذات المعرّفات الثابتة في TUI وتطبيق سطح المكتب و messaging gateways أثناء تنفيذ الدور. ويبقى مُسقِط السجل الخاص بأحداث الاكتمال فقط منفصلًا، لذا فإن الجلسة المستأنفة تعيد بناء بطاقات الأدوات نفسها التي عُرضت أثناء الدور.
      • يبقى تعليق الـ gateway مرئيًا عند تعطيل بث الـ token، وتُمرَّر أحداث الأدوات الحية حتى للإشعارات المُستهلكة قبل طلب الموافقة. ويلتزم التعليق بالإعداد display.show_commentary.

      المتطلبات المسبقة​

      1. تثبيت Codex CLI:

        npm i -g @openai/codex
        codex --version   # 0.130.0 or newer

      2. تسجيل الدخول إلى Codex عبر OAuth. تقرأ العملية الفرعية لـ codex الملف ~/.codex/auth.json. هناك طريقتان لملئه:

        codex login                  # writes tokens to ~/.codex/auth.json

        الأمر hermes auth add openai-codex الخاص بـ Hermes يكتب إلى ~/.hermes/auth.json — وتلك جلسة منفصلة. نفّذ codex login بشكل منفصل إذا لم تكن قد فعلت ذلك.

      3. (اختياري) ثبّت إضافات Codex التي تريدها. عند تفعيل بيئة التشغيل، يرحّل Hermes تلقائيًا أي إضافات منتقاة (curated) ثبّتها مسبقًا عبر Codex CLI:

        codex plugin marketplace add openai-curated
        # then via codex's TUI, install Linear / GitHub / Gmail / etc.

        سيكتشفها Hermes ويكتب مدخلات [plugins."<name>@openai-curated"] إلى ~/.codex/config.toml تلقائيًا.

      التفعيل​

      داخل جلسة Hermes:

      /codex-runtime codex_app_server

      هذا الأمر:

      • يتحقق من تثبيت codex CLI (ويتوقف مع تلميح للتثبيت إن لم يكن مثبّتًا).
      • يحفظ model.openai_runtime: codex_app_server في ملف config.yaml لديك.
      • يرحّل خوادم MCP الخاصة بالمستخدم من ~/.hermes/config.yaml إلى ~/.codex/config.toml.
      • يكتشف إضافات Codex الأصلية المثبّتة ويرحّلها (Linear و GitHub و Gmail و Calendar و Canva وغيرها) عبر الاستعلام من plugin/list RPC الخاص بـ Codex.
      • يسجّل أدوات Hermes الخاصة كخادم MCP كي تتمكن العملية الفرعية لـ codex من استدعائه للأدوات التي لا تأتي مع codex.
      • يكتب default_permissions = ":workspace" كي يسمح الـ sandbox بالكتابة داخل مساحة العمل دون طلب موافقة لكل عملية.
      • يخبرك بما رُحِّل. ويسري التغيير في الجلسة التالية — إذ يحتفظ الوكيل المخزّن مؤقتًا حاليًا ببيئة التشغيل السابقة كي تبقى ذاكرات الـ prompt المؤقتة (prompt caches) صالحة.

      مرادفات: /codex-runtime on، /codex-runtime off، /codex-runtime auto.

      للتحقق من الحالة الحالية دون تغيير أي شيء:

      /codex-runtime

      يمكنك أيضًا ضبطه يدويًا في ~/.hermes/config.yaml:

      model:
        openai_runtime: codex_app_server   # default is "auto" (= Hermes runtime)

      حلقة التحسين الذاتي (تنبيهات الذاكرة + المهارات)​

      تنطلق عملية التحسين الذاتي في خلفية Hermes عند بلوغ عتبات العدّادات:

      • كل 10 prompts من المستخدم → يفحص وكيل مراجعة متفرّع (forked) المحادثة ويقرر ما إذا كان ينبغي حفظ أي شيء في الذاكرة.
      • كل 10 تكرارات للأدوات ضمن دور واحد → الفكرة نفسها لكن للمهارات (عمليات الكتابة عبر skill_manage).

      يستمر كلاهما في العمل على بيئة تشغيل codex. يُسقط مسار codex كل عنصر مكتمل من نوع commandExecution / fileChange / mcpToolCall / dynamicToolCall إلى رسالة اصطناعية assistant tool_call + نتيجة tool، بحيث ترى المراجعة عند تشغيلها البنية نفسها التي تراها في بيئة تشغيل Hermes الافتراضية.

      كيف يبقى الربط متكافئًا:

      بيئة التشغيل الافتراضيةبيئة تشغيل Codex
      زيادة _turns_since_memoryلكل prompt من المستخدم، في مرحلة ما قبل الحلقة داخل run_conversationمسار الكود نفسه، قبل الإرجاع المبكر
      زيادة _iters_since_skillلكل تكرار أداة في حلقة chat-completionsبمقدار turn.tool_iterations بعد عودة دور codex
      مُشغِّل الذاكرة (_turns_since_memory >= _memory_nudge_interval)يُحسب قبل الحلقة، وينطلق بعد الرديُحسب قبل الحلقة، ويُمرَّر إلى الدالة المساعدة لـ codex
      مُشغِّل المهارات (_iters_since_skill >= _skill_nudge_interval)يُحسب بعد الحلقةيُحسب بعد دور codex
      _spawn_background_review(messages_snapshot=..., review_memory=..., review_skills=...)يُستدعى عند انطلاق أي من المُشغِّلينيُستدعى بالطريقة نفسها عند انطلاق أي من المُشغِّلين

      تفصيل واحد: يحتاج فرع المراجعة نفسه إلى استدعاء أدوات حلقة الوكيل في Hermes (memory، skill_manage)، والتي تتطلب آلية التوزيع الخاصة بـ Hermes. لذا عندما يكون الوكيل الأب على codex_app_server، فإن فرع المراجعة يُخفَّض إلى codex_responses — بيانات اعتماد OAuth نفسها، والمزوّد openai-codex نفسه، لكنه يتواصل مع Responses API من OpenAI مباشرة كي يمتلك Hermes الحلقة وتعمل أدوات حلقة الوكيل. وهذا غير مرئي للمستخدم.

      النتيجة الصافية: فعّل بيئة تشغيل codex وستستمر تنبيهات الذاكرة + المهارات في الانطلاق تمامًا كما كانت ستفعل بدونها.

      كيف تعمل الموافقات​

      يطلب Codex الموافقة قبل تنفيذ الأوامر أو تطبيق الـ patches. وتُحوَّل هذه الطلبات إلى طلب "Dangerous Command" القياسي في Hermes:

      ╭───────────────────────────────────────╮
      │ Dangerous Command                     │
      │                                       │
      │ /bin/bash -lc 'echo hello > foo.txt'  │
      │                                       │
      │ ❯ 1. Allow once                       │
      │   2. Allow for this session           │
      │   3. Deny                             │
      │                                       │
      │ Codex requests exec in /your/cwd      │
      ╰───────────────────────────────────────╯
      • Allow once → الموافقة على هذا الأمر فقط.
      • Allow for this session → لن يطلب Codex الموافقة مجددًا للأوامر المشابهة.
      • Deny → يُرفض الأمر؛ ويستمر Codex في وضع القراءة فقط.

      بالنسبة لموافقات apply_patch (تعديل الملفات)، يعرض Hermes ملخصًا لما تغيّر (1 add, 1 update: /tmp/new.py, /tmp/old.py) عندما يوفّر codex البيانات عبر عنصر fileChange المقابل.

      ملفات تعريف الصلاحيات (Permission profiles)​

      لدى Codex ثلاثة profiles صلاحيات مدمجة:

      • :read-only — لا كتابة؛ وكل أمر shell يتطلب موافقة
      • :workspace — يُسمح بالكتابة داخل مساحة العمل الحالية دون طلب موافقة (الافتراضي في Hermes عند تفعيل بيئة التشغيل)
      • :danger-no-sandbox — بلا sandbox على الإطلاق (لا تستخدمه إلا إذا كنت تفهم عواقبه)

      يمكنك تجاوز القيمة الافتراضية في ~/.codex/config.toml خارج الكتلة التي يديرها Hermes:

      default_permissions = ":read-only"

      (سيحافظ Hermes على تجاوزك عند إعادة الترحيل ما دام موجودًا خارج العلامتين # managed by hermes-agent.)

      المهام المساعدة وتكلفة الـ token في اشتراك ChatGPT​

      عند تفعيل بيئة التشغيل هذه مع المزوّد openai-codex، تمر المهام المساعدة (توليد العناوين، وضغط السياق، والاكتشاف التلقائي للرؤية، وفرع مراجعة التحسين الذاتي في الخلفية) أيضًا عبر اشتراك ChatGPT الخاص بك افتراضيًا، لأن العميل المساعد في Hermes يستخدم المزوّد/النموذج الرئيسي عند عدم ضبط تجاوز خاص بكل مهمة.

      هذا ليس خاصًا بـ codex_app_server — فهو ينطبق على المسار الحالي codex_responses أيضًا — لكنه أوضح هنا لأنك تختار صراحةً الفوترة عبر الاشتراك.

      لتوجيه مهام مساعدة محددة إلى نموذج أرخص / مختلف، اضبط تجاوزات صريحة في ~/.hermes/config.yaml:

      auxiliary:
        title_generation:
          provider: openrouter
          model: google/gemini-3-flash-preview
        compression:
          provider: openrouter
          model: google/gemini-3-flash-preview
        vision:
          provider: openrouter
          model: google/gemini-3-flash-preview
        goal_judge:
          provider: openrouter
          model: google/gemini-3-flash-preview

      يرث فرع مراجعة التحسين الذاتي بيئة التشغيل الرئيسية عبر _current_main_runtime()، ويخفّضه Hermes من codex_app_server إلى codex_responses تلقائيًا (كي يتمكن الفرع فعلًا من استدعاء memory و skill_manage — وهما من أدوات حلقة الوكيل الخاصة بـ Hermes). ولا يزال ذلك الفرع يستخدم مصادقة اشتراكك ما لم تكن قد وجّهت المهام المساعدة إلى مكان آخر.

      تعديل ~/.codex/config.toml بأمان​

      يغلّف Hermes كل ما يديره بين تعليقَين يعملان كعلامتين:

      # managed by hermes-agent — `hermes codex-runtime migrate` regenerates this section
      default_permissions = ":workspace"
      [mcp_servers.filesystem]
      ...
      [plugins."github@openai-curated"]
      ...
      # end hermes-agent managed section

      كل ما يقع خارج تلك الكتلة ملك لك. تستبدل إعادة تشغيل الترحيل (عبر /codex-runtime codex_app_server أو كلما فعّلت بيئة التشغيل) الكتلة المُدارة في مكانها، لكنها تحافظ حرفيًا على محتوى المستخدم الموجود فوقها وتحتها. هذا يعني أنه يمكنك:

      • إضافة خوادم MCP خاصة بك لا يعرفها Hermes
      • تجاوز default_permissions إلى :read-only إذا كنت تفضّل أن تُطلب منك الموافقة
      • ضبط خيارات خاصة بـ codex فقط (النموذج، والمزوّدين، و otel، وغيرها)
      • إضافة profiles صلاحيات يعرّفها المستخدم في جداول [permissions.<name>]

      أي شيء تضيفه داخل الكتلة المُدارة سيُستبدل عند الترحيل التالي. إذا احتجت إلى تعديل يتطلب تحرير الكتلة المُدارة، فافتح issue وسنضيف خيار الضبط المناسب.

      إعدادات متعددة الـ profiles / متعددة المستأجرين (multi-tenant)​

      افتراضيًا، يوجّه Hermes العملية الفرعية لـ codex إلى ~/.codex/ بغض النظر عن الـ profile النشط في Hermes. هذا يعني أن hermes -p work و hermes -p personal يتشاركان مصادقة Codex وإضافاته وإعداداته نفسها. وبالنسبة لمعظم المستخدمين، هذا هو السلوك الصحيح — فهو يطابق ما يحدث عند تشغيل codex CLI مباشرة.

      إذا أردت عزل Codex لكل profile (مصادقة منفصلة، وإضافات مثبّتة منفصلة، وإعدادات منفصلة)، فاضبط CODEX_HOME صراحةً لكل profile. وأنظف طريقة هي توجيهه إلى دليل تحت HERMES_HOME الخاص بك:

      # Inside the work profile, you might wrap hermes:
      CODEX_HOME=~/.hermes/profiles/work/codex hermes chat

      ستحتاج إلى إعادة تنفيذ codex login مرة واحدة مع ضبط CODEX_HOME ذاك كي تُحفظ OAuth tokens في الموقع الخاص بالـ profile. بعد ذلك، سيعمل hermes -p work على حالة Codex معزولة.

      لا نحدد هذا النطاق تلقائيًا لأن نقل ~/.codex/ الخاص بمستخدم حالي سيُبطل بصمت مصادقة Codex CLI لديه — فأي شخص نفّذ codex login مسبقًا سيضطر إلى إعادة المصادقة. ويبدو التفعيل الاختياري (opt-in) أكثر أمانًا من مفاجأة المستخدمين.

      تمرير متغير البيئة HOME​

      لا يعيد Hermes كتابة HOME عند تشغيل العملية الفرعية codex app-server (نستخدم os.environ.copy() ولا نضيف فوقها إلا CODEX_HOME و RUST_LOG). وهذا يعني:

      • الأوامر التي ينفّذها codex عبر أداة shell الخاصة به ترى مجلد HOME الحقيقي للمستخدم، فتعثر على ~/.gitconfig و ~/.gh/ و ~/.aws/ و ~/.npmrc وغيرها بشكل صحيح.
      • تبقى الحالة الداخلية لـ Codex معزولة عبر CODEX_HOME (الذي يشير افتراضيًا إلى ~/.codex/).

      يتوافق هذا مع الحدّ الذي انتهى إليه OpenClaw بعد بعض التجارب المبكرة: اعزل حالة Codex، واترك مجلد المنزل الخاص بالمستخدم على حاله. (راجع openclaw/openclaw#81562.)

      ترحيل خوادم MCP​

      تُحوَّل إعدادات mcp_servers في Hermes تلقائيًا إلى صيغة TOML التي يتوقعها Codex. يعمل الترحيل في كل مرة تفعّل فيها بيئة التشغيل (runtime)، وهو متساوي القوة (idempotent) — إذ تستبدل مرات التشغيل اللاحقة القسمَ المُدار مع الحفاظ على أي إعدادات Codex عدّلها المستخدم بنفسه.

      ما يُحوَّل:

      Hermes (config.yaml)Codex (config.toml)
      command + args + envنقل stdio
      url + headersنقل streamable_http
      timeouttool_timeout_sec
      connect_timeoutstartup_timeout_sec
      enabled: falseenabled = false

      ما لا يُرحَّل:

      • المفاتيح الخاصة بـ Hermes مثل sampling (لا يوجد مقابل لها في عميل MCP الخاص بـ Codex — لذا تُحذف مع تحذير لكل خادم).

      ترحيل إضافات Codex الأصلية​

      تُكتشف الإضافات المثبّتة عبر codex plugin (مثل Linear و GitHub و Gmail و Calendar و Canva وغيرها) من خلال استدعاء RPC plugin/list في Codex. ولكل إضافة تكون فيها installed: true، يكتب Hermes كتلة [plugins."<name>@openai-curated"] تفعّلها في جلسة Hermes الخاصة بك.

      وهذا يعني: عندما يقول صديقك "لديّ Calendar و GitHub مُعدّان في Codex CLI" ثم يفعّل بيئة تشغيل codex في Hermes، فإن Hermes يفعّلهما تلقائيًا. دون حاجة إلى إعادة الإعداد.

      ما لا يُرحَّل:

      • الإضافات التي لم تثبّتها بعد — ثبّتها في Codex أولًا.
      • الإضافات التي يُبلغ codex عنها بـ availability != AVAILABLE (تثبيت معطوب، أو OAuth منتهي الصلاحية، أو إزالة من السوق، إلخ). تُتخطّى هذه الإضافات لتجنّب كتابة إعدادات ستفشل عند التفعيل.
      • إدخالات سوق تطبيقات ChatGPT (نتائج app/list الخاصة بكل حساب — فهي مفعّلة مسبقًا داخل codex بحكم مصادقة حسابك).
      • OAuth الخاص بالإضافات — تمنح التفويض لكل إضافة مرة واحدة داخل Codex نفسه؛ ولا يمسّ Hermes بيانات الاعتماد.

      استدعاء أدوات Hermes الراجع (خادم MCP الجديد)​

      تغطي toolset المدمجة في Codex عمليات الـ shell والملفات والتصحيحات (patches)، لكنها لا تتضمن البحث في الويب أو أتمتة المتصفح أو الرؤية أو توليد الصور وغيرها. ولإبقاء هذه الأدوات قابلة للاستخدام خلال دور codex، يسجّل Hermes نفسه بوصفه خادم MCP في ~/.codex/config.toml:

      [mcp_servers.hermes-tools]
      command = "/path/to/python"
      args = ["-m", "agent.transports.hermes_tools_mcp_server"]
      env = { HERMES_HOME = "/your/.hermes", PYTHONPATH = "...", HERMES_QUIET = "1" }
      startup_timeout_sec = 30.0
      tool_timeout_sec = 600.0

      عندما يستدعي النموذج web_search (أو أي أداة أخرى مكشوفة من Hermes)، يشغّل codex العملية الفرعية hermes_tools_mcp_server عبر stdio، ويُمرَّر الطلب من خلال model_tools.handle_function_call()، ثم تُعاد النتيجة إلى codex مثل أي استجابة MCP أخرى.

      الأدوات المتاحة عبر الاستدعاء الراجع: web_search، web_extract، browser_navigate، browser_click، browser_type، browser_press، browser_snapshot، browser_scroll، browser_back، browser_get_images، browser_console، browser_vision، vision_analyze، image_generate، skill_view، skills_list، text_to_speech.

      الأدوات غير المتاحة: delegate_task و memory و session_search و todo. تحتاج هذه الأدوات إلى سياق AIAgent قيد التشغيل لتنفيذها (حالة منتصف الحلقة)، ولا يستطيع استدعاء MCP راجع عديم الحالة (stateless) تشغيلها. استخدم بيئة تشغيل Hermes الافتراضية (/codex-runtime auto) عندما تحتاج إليها.

      التعطيل​

      يمكنك العودة في أي وقت:

      /codex-runtime auto

      يسري التغيير في الجلسة التالية. تبقى كتلة Codex المُدارة في ~/.codex/config.toml حتى تتمكن من إعادة التفعيل لاحقًا دون فقدان الإعدادات — أو احذفها يدويًا إن شئت.

      القيود​

      بيئة التشغيل هذه إصدار تجريبي (beta) بالاشتراك الاختياري (opt-in). ما يعمل حتى Hermes Agent 2026.5 + Codex CLI 0.130.0:

      • المحادثات متعددة الأدوار
      • موافقات commandExecution و fileChange (apply_patch) عبر واجهة Hermes
      • استدعاءات أدوات MCP (جرى التحقق منها مع @modelcontextprotocol/server-filesystem ومع الاستدعاء الراجع الجديد hermes-tools)
      • ترحيل إضافات Codex الأصلية (جرى التحقق منه مع مخزون Linear / GitHub / Calendar)
      • مسارات الرفض/الإلغاء
      • دورة التشغيل/الإيقاف
      • عدّادات التذكير (nudge) الخاصة بالذاكرة والمهارات (جرى التحقق منها مباشرةً عبر اختبارات التكامل)
      • أداة web_search في Hermes عبر codex (جرى التحقق منها مباشرةً: أُعيدت "OpenAI Codex CLI – Getting Started" من البداية إلى النهاية)

      القيود المعروفة:

      • مصادقة Hermes ومصادقة codex جلستان منفصلتان. تحتاج إلى كلٍّ من codex login و hermes auth add openai-codex للحصول على أسلس تجربة استخدام (إذ تستخدم بيئة التشغيل جلسة codex لاستدعاء LLM). هذا خيار تصميمي مقصود في _import_codex_cli_tokens لدى Hermes — فلا يشارك Hermes حالة OAuth مع codex CLI تجنبًا لأن يطمس كلٌّ منهما بيانات الآخر عند تحديث الـ token.
      • delegate_task و memory و session_search و todo غير متاحة في بيئة التشغيل هذه. فهي تحتاج إلى سياق AIAgent قيد التشغيل، وهو ما لا يستطيع استدعاء MCP راجع عديم الحالة توفيره. استخدم /codex-runtime auto عندما تحتاج إليها.
      • لا توجد معاينة مضمّنة للتصحيح في مطالبات الموافقة عندما لا يتتبّع codex مجموعة التغييرات. لا تحمل معاملات موافقة fileChange في Codex مجموعةَ التغييرات دائمًا. يخزّن Hermes مؤقتًا البيانات القادمة من إشعار item/started المقابل متى أمكن، لكن إذا وصلت الموافقة قبل بثّ العنصر، تعود المطالبة إلى أي reason يوفّره codex.
      • الإلغاء في أقل من ثانية غير مضمون. تُرسل المقاطعات أثناء البث (Ctrl+C بينما يردّ codex) عبر turn/interrupt، لكن إذا كان codex قد أرسل الرسالة النهائية بالفعل، فستصلك الاستجابة على أي حال.

      إذا وجدت خطأً، افتح issue مرفقًا بمخرجات hermes logs --since 5m. واذكر codex-runtime في العنوان ليسهل فرزه.

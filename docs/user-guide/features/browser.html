      أتمتة المتصفح

      يتضمن Hermes Agent مجموعة أدوات (toolset) كاملة لأتمتة المتصفح مع عدة خيارات للـ backend:

      • وضع Browser Use السحابي عبر Browser Use للحصول على Chromium مُدار مع وضع التخفّي (stealth)، و proxies سكنية، وحلّ CAPTCHA، و profiles متصفح قابلة لإعادة الاستخدام
      • وضع Browserbase السحابي عبر Browserbase كمزوّد بديل للمتصفح السحابي مع أدوات لمكافحة اكتشاف الروبوتات (anti-bot)
      • وضع Browser Use عبر Browser Use CLI 3.0، وهو مشغّل المتصفح الافتراضي لـ Chrome المحلي ولمتصفحات Browser Use السحابية
      • وضع Firecrawl السحابي عبر Firecrawl للحصول على متصفحات سحابية مع استخراج مدمج للبيانات (scraping)
      • وضع Camofox المحلي عبر Camofox للتصفح المحلي المقاوم للاكتشاف (انتحال بصمة المتصفح المعتمد على Firefox)
      • محرك Lightpanda المحلي عبر Lightpanda — متصفح headless بُني من الصفر بلغة Zig ومصمَّم للآلات؛ يبدأ فورًا، ويستهلك ذاكرة أقل بـ 16 مرة، وأسرع بـ 9 مرات من Chrome. يعمل في وضع Browser Use (يشغّله Hermes، دون الحاجة إلى Chromium أو Node) ومع الأدوات المدمجة (مع رجوع تلقائي إلى Chrome للإجراءات التي لا يدعمها بعد)
      • CDP محلي لعائلة Chromium — اربط أدوات المتصفح بنسخة Chrome أو Brave أو Chromium أو Edge الخاصة بك باستخدام /browser connect
      • وضع المتصفح المحلي عبر أداة agent-browser CLI وتثبيت محلي لـ Chromium

      في جميع الأوضاع، يستطيع الوكيل التنقل في المواقع، والتفاعل مع عناصر الصفحة، وتعبئة النماذج، واستخراج المعلومات.

      نظرة عامة​

      تُمثَّل الصفحات في صورة أشجار إمكانية الوصول (accessibility trees) (لقطات نصية)، مما يجعلها مثالية لوكلاء LLM. تحصل العناصر التفاعلية على معرّفات مرجعية (ref IDs) (مثل @e1 و @e2) يستخدمها الوكيل للنقر والكتابة.

      القدرات الرئيسية:

      • تنفيذ سحابي متعدد المزوّدين — Browser Use أو Browserbase أو Firecrawl — دون الحاجة إلى متصفح محلي
      • تكامل محلي مع عائلة Chromium — اتصل بمتصفح Chrome أو Brave أو Chromium أو Edge قيد التشغيل لديك عبر CDP للتصفح العملي المباشر
      • دعم سحابي لمكافحة الروبوتات — يتضمن Browser Use Cloud وضع التخفّي، و proxies سكنية، وحلّ CAPTCHA
      • Profiles سحابية دائمة — يستطيع Browser Use Cloud إعادة استخدام ملفات تعريف الارتباط (cookies) و localStorage وكلمات المرور المحفوظة عبر الجلسات
      • عزل الجلسات — تحصل كل مهمة على جلسة متصفح خاصة بها
      • تنظيف تلقائي — تُغلق الجلسات غير النشطة بعد انقضاء مهلة زمنية
      • تحليل بصري (Vision) — لقطة شاشة + تحليل بالذكاء الاصطناعي للفهم البصري

      الإعداد​

      لمشتركي Nous

      إذا كان لديك اشتراك مدفوع في Nous Portal، فيمكنك استخدام أتمتة المتصفح عبر Tool Gateway دون أي مفاتيح API منفصلة. يمكن للتثبيتات الجديدة تنفيذ hermes setup --portal لتسجيل الدخول وتفعيل كل أدوات الـ gateway دفعة واحدة؛ أما التثبيتات الحالية فيمكنها اختيار Nous Subscription كمزوّد للمتصفح عبر hermes model أو hermes tools.

      وضع Browser Use السحابي​

      لاستخدام Browser Use كمزوّد للمتصفح السحابي، أضف:

      # Add to ~/.hermes/.env
      BROWSER_USE_API_KEY=***

      احصل على مفتاح API من browser-use.com.

      يشغّل Browser Use Cloud متصفح Chromium مُدارًا مع تفعيل وضع التخفّي (stealth) و الـ proxies السكنية افتراضيًا، ويتضمن حلّ CAPTCHA، ويدعم الـ profiles الدائمة لملفات تعريف الارتباط (cookies) و localStorage وكلمات المرور المحفوظة.

      وضع Browserbase السحابي​

      لاستخدام متصفحات سحابية تديرها Browserbase، أضف:

      # Add to ~/.hermes/.env
      BROWSERBASE_API_KEY=***
      BROWSERBASE_PROJECT_ID=your-project-id-here

      احصل على بيانات الاعتماد من browserbase.com.

      اختيار المزوّد

      توفّر مفاتيح .env أعلاه بيانات الاعتماد فقط. أما المتصفح السحابي النشط فيُحدَّد بواسطة الاختيار browser.cloud_provider الذي يكتبه hermes tools → Browser Automation (browserbase أو browser-use أو camofox أو nous لـ Nous Subscription). بمجرد وجود اختيار، لا تؤدي إضافة مفتاح أو إزالته إلى تبديل المزوّد — والمزوّد المختار الذي ينقصه مفتاح يُنتج خطأً مع توجيه لتنفيذ hermes tools بدلًا من إعادة التوجيه بصمت. أما الإعدادات التي لم تُضبط من قبل فتواصل الاكتشاف التلقائي من بيانات الاعتماد المتاحة.

      وضع Browser Use (الافتراضي)​

      يستخدم وضع Browser Use أداة Browser Use CLI 3.0 بدلًا من أدوات المتصفح المدمجة. يكتب الوكيل كود Python وينفّذه في المتصفح للنقر والكتابة والسحب واستخراج البيانات والتفاعل مع صفحات الويب.

      هذا هو وضع المتصفح الافتراضي: عندما لا يكون browser.backend مضبوطًا وتكون أداة browser-use CLI قابلة للتشغيل (مثبّتة، أو متاحة عبر uvx)، يحصل الوكيل على أداة واحدة هي browser_exec. وإذا تعذّر تشغيل CLI، يرجع Hermes تلقائيًا إلى أدوات المتصفح المدمجة.

      هذا الوضع مشغّل (driver) يتكامل مع backend المتصفح الذي أعددته: فهو يقود متصفح Chromium الـ headless الخاص بـ Hermes، أو متصفحًا سحابيًا عبر اشتراك Nous، أو Browserbase، أو Firecrawl، أو متصفحات Browser Use السحابية — أيًّا كان مصدر المتصفح المختار في hermes tools → Browser Automation. الاستثناء الوحيد هو Camofox، الذي لا يملك CDP endpoint يمكن للـ harness الاتصال به؛ لذا تحتفظ إعدادات Camofox تلقائيًا بأدوات المتصفح المدمجة.

      يستخدم التصفح المحلي Chromium المضمّن، لا متصفح Chrome الخاص بك. عند عدم إعداد مزوّد سحابي أو endpoint عبر /browser connect، يُطلق Hermes نسخة Chromium نفسها التي تستخدمها الأدوات المدمجة (المثبّتة عبر hermes tools → Browser Automation، والمُدارة عبر agent-browser) ويوجّه Browser Use CLI إليها. لا يُمَسّ متصفح Chrome المثبّت لديك أبدًا، لذا لا يوجد مفتاح تصحيح عن بُعد في chrome://inspect تحتاج إلى تفعيله، ولا نافذة منبثقة "Allow remote debugging?" — كما يعمل على المضيفات عديمة الواجهة (headless) التي لا تحتوي على Chrome إطلاقًا. يتشارك المتصفح دورة حياة الأدوات المدمجة: فهو يُغلق بعد browser.inactivity_timeout، وعند الخروج، وبواسطة عملية تنظيف العمليات اليتيمة. لقيادة متصفح سجّلت الدخول فيه، استخدم /browser connect أو مفتاح الـ profile الحقيقي.

      الجلسات المتزامنة: تقبل browser_exec الوسيط session=<name> الذي يعزل عمل المتصفح حسب الاسم على كل backend. يحصل كل اسم على daemon خاص به للـ harness (مع IPC socket وسجل وحالة خاصة به) وعلى متصفح خاص به (نسخة Chromium مضمّنة منفصلة محليًا، ومتصفح سحابي منفصل على الـ backends السحابية) — لذا لم تعد الـ subagents المتوازية أو المحادثات المتزامنة تتصادم على اتصال مشترك واحد. يؤدي حذف session إلى استخدام الـ daemon الافتراضي المشترك، وهو مناسب للتصفح بمهمة واحدة في كل مرة.

      لإلغاء هذا الوضع وفرض استخدام أدوات المتصفح المدمجة، استخدم /browser use off، أو:

      # Add to ~/.hermes/config.yaml
      browser:
        backend: "off"

      (تبقى backend: "browser-use" صالحة لفرض الوضع صراحةً.)

      تحتاج متصفحات Browser Use السحابية الخاصة به إلى browser-use auth login أو BROWSER_USE_API_KEY؛ أما مصادر المتصفح الأخرى فتستخدم بيانات اعتمادها الحالية دون تغيير.

      ملاحظة

      نظرًا لأن وضع Browser Use ينفّذ كود Python يكتبه النموذج على جهازك، فإن أداة browser_exec لا تُتاح إلا للجلسات التي تملك أيضًا صلاحية الوصول إلى الطرفية. أما المنصات المُعدّة دون toolset الطرفية (مثل واجهة مراسلة مقيّدة) فتحتفظ بأدوات المتصفح الافتراضية بدلًا من ذلك.

      وضع Firecrawl السحابي​

      لاستخدام Firecrawl كمزوّد للمتصفح السحابي، أضف:

      # Add to ~/.hermes/.env
      FIRECRAWL_API_KEY=fc-***

      احصل على مفتاح API من firecrawl.dev. ثم اختر Firecrawl كمزوّد للمتصفح:

      hermes setup tools
      # → Browser Automation → Firecrawl

      إعدادات اختيارية:

      # Self-hosted Firecrawl instance (default: https://api.firecrawl.dev)
      FIRECRAWL_API_URL=http://localhost:3002

      # Session TTL in seconds (default: 300)
      FIRECRAWL_BROWSER_TTL=600

      التوجيه الهجين: السحابة لعناوين URL العامة، والمتصفح المحلي لـ LAN/localhost​

      عند إعداد مزوّد سحابي، يُطلق Hermes تلقائيًا متصفح Chromium محليًا مساعدًا (sidecar) لعناوين URL التي تُحلّ إلى عنوان خاص/loopback/LAN (localhost و 127.0.0.1 و 192.168.x.x و 10.x.x.x و 172.16-31.x.x و *.local و *.lan و *.internal، و IPv6 loopback ::1، و link-local 169.254.x.x). أما عناوين URL العامة فتستمر في استخدام المزوّد السحابي في المحادثة نفسها.

      يحلّ هذا سير العمل الشائع "أطوّر محليًا لكنني أستخدم Browserbase" — إذ يستطيع الوكيل التقاط لقطة شاشة للوحة التحكم لديك على http://localhost:3000 وكذلك استخراج بيانات https://github.com دون أن تبدّل المزوّدين أو تعطّل حماية SSRF. ولا يرى المزوّد السحابي عنوان URL الخاص أبدًا.

      هذه الميزة مفعّلة افتراضيًا. لتعطيلها (فتذهب جميع عناوين URL إلى المزوّد السحابي المُعدّ، كما في السابق):

      # ~/.hermes/config.yaml
      browser:
        cloud_provider: browserbase
        auto_local_for_private_urls: false

      عند تعطيل التوجيه التلقائي، تُرفض عناوين URL الخاصة مع الرسالة "Blocked: URL targets a private or internal address" ما لم تضبط أيضًا browser.allow_private_urls: true (الذي يسمح للمزوّد السحابي بمحاولة الوصول إليها — وهو ما لن ينجح عادةً لأن Browserbase وأمثاله لا يستطيعون الوصول إلى شبكة LAN لديك).

      المتطلبات: يستخدم الـ sidecar المحلي أداة agent-browser CLI نفسها التي يستخدمها الوضع المحلي الخالص، لذا تحتاج إلى تثبيتها (يثبّتها hermes setup tools → Browser Automation تلقائيًا). ولا تزال عمليات إعادة التوجيه بعد التنقل من عنوان URL عام إلى عنوان خاص محظورة (فلا يمكنك استخدام حيلة إعادة التوجيه إلى عنوان داخلي للوصول إلى شبكة LAN لديك عبر المسار العام).

      التصفح بالـ profile الحقيقي (استخدم تسجيلات دخولك)​

      افتراضيًا، يعمل التصفح المحلي في profile نظيف مؤقت يُتخلّص منه لاحقًا — فالوكيل غير مسجّل الدخول في أي شيء. فعّل التصفح بالـ profile الحقيقي لتسمح للوكيل بالتصفح بصفتك أنت، مع تسجيلات الدخول وملفات تعريف الارتباط الموجودة لديك:

      # ~/.hermes/config.yaml
      browser:
        use_real_profile: true

      عند التفعيل، ينسخ Hermes الـ profile النشط لمتصفحك الافتراضي — أي الـ profile الذي تتصفح به فعلًا (Local State → profile.last_used)، مع ملفات تعريف الارتباط وتسجيلات الدخول المحفوظة والتفضيلات — إلى لقطة (snapshot) مُدارة تحت ~/.hermes/browser-profile/<browser>/، ثم يُطلق الملف التنفيذي الحقيقي لمتصفحك على تلك اللقطة ويربط محرك التصفح به. إن إطلاق الملف التنفيذي الحقيقي (بدلًا من Chromium مضمّن مع خيارات mock-keychain) هو ما يُبقي ملفات تعريف الارتباط المشفّرة بواسطة نظام التشغيل قابلة لفك التشفير — ففي macOS تُشفَّر ملفات تعريف الارتباط في Chrome عبر Keychain، والإطلاق باستخدام mock-keychain سيُسقطها جميعًا بصمت، فيفتح المتصفح دون تسجيل دخول. لا يُفتح الـ profile الحي لمتصفحك مباشرةً أبدًا: فاللقطة مجلد منفصل، لذا لا تتنازع مع متصفحك قيد التشغيل على قفل الـ profile، كما تتجنّب حظر Chrome 136+ للتصحيح عن بُعد على مجلد الـ profile الافتراضي. تُعاد مزامنة ملفات المصادقة (cookies/logins/preferences) من الـ profile الحقيقي كلما أُطلقت جلسة جديدة، لذا فإن تسجيلات الدخول التي تُجريها في متصفحك تظهر في جلسة الوكيل. لا يُنسخ إلا الـ profile النشط — ولا تُلتقط أبدًا لقطات لأي profiles أخرى في Chrome.

      يعمل متصفح اللقطة في وضع headless — فهو يقود الـ profile الخاص بك في الخلفية دون نافذة مرئية ولا يسرق التركيز أبدًا، لذا يمكنك مواصلة العمل بينما ينشر الوكيل التغريدات أو يعبّئ النماذج أو يستخرج البيانات نيابةً عنك. (يعني headless هنا وضع headless الجديد في Chrome، الذي يقرأ مخزن ملفات تعريف الارتباط العادي لديك، لذا تظل تسجيلات دخولك تُحمَّل.) وإذا كنت تفضّل مشاهدته أثناء العمل، فإن مفتاح الوضع المرئي (headed) نفسه ينطبق هنا — إذ يفتح browser.headed: true (أو AGENT_BROWSER_HEADED=1) نافذة مرئية للتصفح بالـ profile الحقيقي أيضًا. أما على مضيف بلا شاشة (الخوادم، CI) فيعمل دائمًا في وضع headless بغض النظر عن ذلك.

      إذا كان لمتصفحك عدة profiles (مثل profile للعمل وآخر شخصي) ولا تريد أن يحدد "أيّ profile استخدمته آخر مرة" هوية الوكيل، فثبّت مصدر اللقطة صراحةً:

      # ~/.hermes/config.yaml
      browser:
        use_real_profile: true
        real_profile_pin: "Profile 2"   # directory name under the browser's user-data dir

      التثبيت الذي يسمّي مجلد profile غير موجود يفشل بشكل مغلق (fails closed) مع رسالة تُرشدك إلى الإصلاح — ولا يرجع أبدًا بصمت إلى آخر profile مُستخدم.

      عند إيقاف المفتاح مجددًا، يحذف Hermes مخزن اللقطات (~/.hermes/browser-profile/) عند الاستخدام التالي للمتصفح، حتى لا تبقى بيانات الاعتماد المنسوخة بعد سحب موافقتك.

      Windows: يجب إغلاق المتصفح بالكامل

      في Windows، يحتفظ متصفح Chrome/Edge/Brave قيد التشغيل بقواعد بيانات ملفات تعريف الارتباط وتسجيلات الدخول بقفل حصري (يمنع الجميع)، لذا لا يستطيع Hermes نسخها بينما المتصفح مفتوح — فيفشل سريعًا مع رسالة "fully quit the browser and retry" بدلًا من التعليق أو إنتاج جلسة غير مسجّلة الدخول. لذلك يتطلب التصفح بالـ profile الحقيقي في Windows إغلاق المتصفح بالكامل، بما في ذلك أي نسخة تعمل في الخلفية أو في شريط النظام (فخيار "continue running background apps when closed" في Chrome يُبقي chrome.exe قيد التشغيل بعد إغلاق النافذة). أما في macOS و Linux فيمكن عادةً نسخ الـ profile أثناء تشغيل المتصفح. وعلى كل المنصات، لكل نسخة احتياطية من قواعد بيانات المصادقة مهلة إعادة محاولة مدتها خمس ثوانٍ. إذا ظلت قاعدة بيانات المصدر أو اللقطة مقفلة، يوقف Hermes الإطلاق ويطلب منك إغلاق المتصفح وإعادة المحاولة. وهو يحافظ على بيانات WAL المُلتزَم بها (committed) عبر SQLite بدلًا من الرجوع إلى نسخ خام للملف، وهو ما قد يُفقد تسجيلات الدخول الحديثة بصمت. كما توقف قواعد البيانات غير القابلة للقراءة أو التالفة الإطلاقَ أيضًا.

      اضبط browser.real_profile_autoclose: true لتسمح لـ Hermes بأن يعرض عليك إغلاق المتصفح نيابةً عنك عندما يكون محتفظًا بالـ profile. وحتى مع تفعيل هذا الخيار، لا يُغلق Hermes المتصفح تلقائيًا أبدًا — فعندما يكون الـ profile مقفلًا يتوقف دائمًا ويسألك الوكيل أولًا؛ ولا يُنفّذ hermes browser close-profile إلا بعد موافقتك (وهو يُنهي شجرة عمليات المتصفح المرتبطة بذلك الـ profile، مع فقدان علامات التبويب غير المحفوظة)، ثم يعيد المحاولة. وإذا ظل الـ profile مقفلًا بعد ذلك (مثلًا إذا أُعيد إطلاق نسخة في الخلفية أو في شريط النظام)، يبقى Hermes متوقفًا ويطلب منك إغلاق المتصفح بالكامل — ولن يكرر المحاولة أو يُنهي العملية مجددًا من تلقاء نفسه.

      • المتصفحات المدعومة: Chrome و Edge و Brave و Brave Origin و Chromium (أيّها كان الافتراضي في نظام التشغيل). وإذا كان المتصفح الافتراضي من خارج عائلة Chromium (مثل Firefox) فيفشل بشكل مغلق مع رسالة واضحة بدلًا من التخمين.
      • يعمل على أي backend. على backend محلي يعمل تلقائيًا بمجرد تفعيل المفتاح. وتحت backend متصفح سحابي، لا يزال بإمكان الوكيل فتح جلسة محلية بالـ profile الحقيقي عند الطلب عبر أداة browser_exec باستخدام وسيطها local (لا تُتيح الأداة هذا الوسيط إلا عند تفعيل هذا المفتاح) — بينما يواصل الـ backend السحابي خدمة كل ما عدا ذلك.
      • الإطار الأمني: هذه ميزة للراحة مشروطة بالموافقة، وليست حدًّا للعزل. فالصفحة التي يزورها الوكيل تعمل مع تسجيلات دخولك الحقيقية، لذا لا تفعّلها إلا عندما تريد أن يتصرف الوكيل بصفتك. معطّلة افتراضيًا.
      • Desktop: بدّل المفتاح من Capabilities → Tools → Browser → Use My Real Browser Profile (يقع المفتاح أعلى خيارات الـ backend)، أو من Settings → Config ضمن قسم browser.

      وضع Camofox المحلي​

      Camofox خادم Node.js مستضاف ذاتيًا يغلّف Camoufox (نسخة متفرعة من Firefox مع انتحال للبصمة مكتوب بلغة C++). ويوفّر تصفحًا محليًا مقاومًا للاكتشاف دون اعتماد على السحابة.

      # Clone the Camofox browser server first
      git clone https://github.com/jo-inc/camofox-browser
      cd camofox-browser

      # Build and start with Docker using the default container settings
      # (auto-detects arch: aarch64 on M1/M2, x86_64 on Intel)
      make up

      # Stop and remove the default container
      make down

      # Force a clean rebuild (for example, after upgrading VERSION/RELEASE)
      make reset

      # Just download binaries without building
      make fetch

      # Override arch or version explicitly
      make up ARCH=x86_64
      make up VERSION=135.0.1 RELEASE=beta.24

      يُشغّل make up الحاوية الافتراضية فورًا. إذا كنت تريد إعدادات تشغيل مخصصة مثل ذاكرة heap أكبر لـ Node، أو VNC، أو مجلد profile دائم، فابنِ الصورة (image) أولًا ثم شغّلها بنفسك:

      # Build the image without starting the default container
      make build

      # Start with persistence, VNC live view, and a larger Node heap
      mkdir -p ~/.camofox-docker
      docker run -d \
        --name camofox-browser \
        --restart unless-stopped \
        -p 9377:9377 \
        -p 6080:6080 \
        -p 5901:5900 \
        -e CAMOFOX_PORT=9377 \
        -e ENABLE_VNC=1 \
        -e VNC_BIND=0.0.0.0 \
        -e VNC_RESOLUTION=1920x1080 \
        -e MAX_OLD_SPACE_SIZE=2048 \
        -v ~/.camofox-docker:/root/.camofox \
        camofox-browser:135.0.1-aarch64

      مع تفعيل VNC، يعمل المتصفح في الوضع المرئي (headed) ويمكن مشاهدته مباشرةً في متصفحك على http://localhost:6080 (noVNC). ويمكنك أيضًا ربط عميل VNC أصلي بـ localhost:5901.

      إذا كنت قد نفّذت make up بالفعل، فأوقف تلك الحاوية الافتراضية واحذفها قبل تشغيل الحاوية المخصصة:

      make down
      # then run the custom docker run command above

      ثم اضبط في ~/.hermes/.env:

      CAMOFOX_URL=http://localhost:9377

      إذا كان Camofox يعمل في Docker وتريد أن يفتح تطبيقات ويب تُقدَّم من الجهاز المضيف، ففعّل إعادة كتابة عناوين loopback. يجب أن يظل CAMOFOX_URL مشيرًا إلى control API المنشورة على المضيف، لكن عناوين URL للصفحات مثل http://127.0.0.1:3000 يجب فتحها من داخل الحاوية بصيغة http://host.docker.internal:3000:

      # ~/.hermes/config.yaml
      browser:
        camofox:
          rewrite_loopback_urls: true
          loopback_host_alias: host.docker.internal  # default; use a LAN IP if needed

      متغيرات البيئة المكافئة:

      CAMOFOX_REWRITE_LOOPBACK_URLS=true
      CAMOFOX_LOOPBACK_HOST_ALIAS=host.docker.internal

      لا تنطبق إعادة الكتابة إلا على عناوين URL الخاصة بالتنقل في الصفحات ذات مضيفات loopback (localhost و 127.0.0.1 و ::1). ولا تغيّر CAMOFOX_URL. اتركها معطّلة لتثبيتات Camofox التي لا تستخدم Docker، حيث يعمل المتصفح أصلًا على المضيف وتكون عناوين loopback صحيحة.

      أو اضبطه عبر hermes tools → Browser Automation → Camofox.

      يُختار Camofox مثل أي backend متصفح آخر: اختر Camofox في hermes tools → Browser Automation، الذي يكتب browser.cloud_provider: camofox في config.yaml. أما CAMOFOX_URL فهو عنوان الخادم فقط — ولم يعد ضبطه وحده يختار الـ backend بمجرد وجود اختيار للمتصفح (الإعدادات التي لم تُضبط من قبل لا تزال تكتشفه تلقائيًا).

      جلسات المتصفح الدائمة​

      افتراضيًا، تحصل كل جلسة Camofox على هوية عشوائية — فلا تبقى ملفات تعريف الارتباط وتسجيلات الدخول بعد إعادة تشغيل الوكيل. لتفعيل جلسات المتصفح الدائمة، أضف ما يلي إلى ~/.hermes/config.yaml:

      browser:
        camofox:
          managed_persistence: true

      ثم أعد تشغيل Hermes بالكامل حتى تُقرأ الإعدادات الجديدة.

      المسار المتداخل مهم

      يقرأ Hermes المفتاح browser.camofox.managed_persistence، وليس مفتاح managed_persistence في المستوى الأعلى. من الأخطاء الشائعة كتابة:

      # ❌ Wrong — Hermes ignores this
      managed_persistence: true

      إذا وُضع الخيار في المسار الخطأ، يرجع Hermes بصمت إلى userId مؤقت عشوائي، وستفقد حالة تسجيل الدخول في كل جلسة.

      ما يفعله Hermes​
      • يرسل userId حتميًا مرتبطًا بالـ profile إلى Camofox حتى يتمكن الخادم من إعادة استخدام Firefox profile نفسه عبر الجلسات.
      • يتخطى تدمير السياق على جانب الخادم عند التنظيف، لذا تبقى ملفات تعريف الارتباط وتسجيلات الدخول بين مهام الوكيل.
      • يربط نطاق userId بـ Hermes profile النشط، لذا تحصل Hermes profiles المختلفة على profiles متصفح مختلفة (عزل الـ profiles).
      ما لا يفعله Hermes​
      • لا يفرض الاستمرارية على خادم Camofox. يرسل Hermes فقط userId ثابتًا؛ ويجب على الخادم احترامه بربط userId ذلك بمجلد Firefox profile دائم.
      • إذا كانت نسخة خادم Camofox لديك تتعامل مع كل طلب على أنه مؤقت (مثلًا تستدعي دائمًا browser.newContext() دون تحميل profile مخزَّن)، فلا يستطيع Hermes جعل تلك الجلسات دائمة. تأكد من أنك تشغّل نسخة Camofox تُطبّق استمرارية الـ profiles المعتمدة على userId.
      تحقّق من أنه يعمل​
      1. شغّل Hermes وخادم Camofox.
      2. افتح Google (أو أي موقع يتطلب تسجيل الدخول) في مهمة متصفح وسجّل الدخول يدويًا.
      3. أنهِ مهمة المتصفح بشكل طبيعي.
      4. ابدأ مهمة متصفح جديدة.
      5. افتح الموقع نفسه مجددًا — يُفترض أن تظل مسجّل الدخول.

      إذا سجّلت الخطوة 5 خروجك، فهذا يعني أن خادم Camofox لا يحترم userId الثابت. راجع مسار الإعدادات مجددًا، وتأكد من أنك أعدت تشغيل Hermes بالكامل بعد تعديل config.yaml، وتحقّق من أن إصدار خادم Camofox لديك يدعم profiles دائمة لكل مستخدم.

      أين تُخزَّن الحالة​

      يستمد Hermes قيمة userId الثابتة من المجلد المرتبط بالـ profile ~/.hermes/browser_auth/camofox/ (أو ما يكافئه تحت $HERMES_HOME للـ profiles غير الافتراضية). أما بيانات profile المتصفح الفعلية فتوجد على جانب خادم Camofox، مفهرسةً بقيمة userId تلك. لإعادة ضبط profile دائم بالكامل، امسحه على خادم Camofox واحذف مجلد الحالة الخاص بـ Hermes profile المقابل.

      جلسات Camofox المُدارة خارجيًا​

      عندما يقود تطبيق آخر متصفح Camofox المرئي (مساعد سطح مكتب، أو تكامل مخصص، أو وكيل آخر)، اضبط Hermes ليعمل داخل الهوية نفسها بدلًا من إنشاء profile معزول خاص به.

      تتحكم ثلاثة إعدادات في هذا السلوك:

      الإعدادمتغير البيئةالتأثير
      browser.camofox.user_idCAMOFOX_USER_IDقيمة Camofox userId التي يستخدمها Hermes عند إنشاء علامات التبويب. يؤدي ضبطها إلى إدخال الجلسة في وضع "externally managed" (مُدار خارجيًا).
      browser.camofox.session_keyCAMOFOX_SESSION_KEYsessionKey (ويُعرف أيضًا بـ listItemId) الذي يُرسل عند إنشاء علامة التبويب. يُستخدم لمطابقة علامة تبويب موجودة أثناء التبنّي. تكون قيمته الافتراضية خاصة بكل مهمة إذا لم يُضبط.
      browser.camofox.adopt_existing_tabCAMOFOX_ADOPT_EXISTING_TABعند ضبطه على true، يستدعي Hermes GET /tabs?userId=<user_id> عند أول استخدام ويعيد استخدام علامة تبويب موجودة قبل إنشاء واحدة جديدة.

      تتقدّم متغيرات البيئة على config.yaml. وتعمل أيٌّ من الصيغتين:

      browser:
        camofox:
          user_id: shared-camofox
          session_key: visible-tab
          adopt_existing_tab: true
      CAMOFOX_USER_ID=shared-camofox
      CAMOFOX_SESSION_KEY=visible-tab
      CAMOFOX_ADOPT_EXISTING_TAB=true

      ما الذي يتغير عند ضبط user_id:

      • يتخطى Hermes التنظيف المُدمِّر في نهاية المهمة (مثل managed_persistence: true). وتبقى علامة التبويب وملفات تعريف الارتباط والـ profile الخاصة بالتطبيق الآخر.
      • لا يستدعي Hermes DELETE /sessions/<user_id> — فهذا الـ endpoint يمسح جميع بيانات المستخدم، لذا سيدمّر جلسة التطبيق الخارجي إن نُفّذ.

      كيف يعمل تبنّي علامات التبويب (عند ضبط adopt_existing_tab: true):

      1. عند أول استدعاء لأداة متصفح بعد بدء العملية، يُرسل Hermes الطلب GET /tabs?userId=<user_id> (بمهلة 5 ثوانٍ).
      2. إذا كانت أي علامة تبويب في الاستجابة تحمل listItemId == session_key، يتبنّى Hermes أحدثها إنشاءً في تلك المجموعة.
      3. وإلا، يتبنّى Hermes أحدث علامة تبويب أُنشئت للمستخدم (بأي listItemId).
      4. إذا لم توجد علامات تبويب أو فشل الطلب، يرجع Hermes إلى إنشاء علامة تبويب جديدة في العملية التالية.

      لا يحدث التبنّي إلا إلى أن تُملأ قيمة tab_id للجلسة. إذا أغلق التطبيق الخارجي علامة التبويب المتبنّاة أثناء التشغيل، فسيُظهر استدعاء أداة المتصفح التالي خطأً من Camofox — إذ لا يعيد Hermes البحث عن علامة تبويب جديدة في كل استدعاء.

      اختيار session_key: إذا كنت تريد أن يتصل Hermes بشكل موثوق بعلامة تبويب موجودة محددة، فاضبط session_key على قيمة listItemId التي استخدمها التطبيق الخارجي عند إنشائها. وإذا تركت session_key دون ضبط وضبطت user_id فقط، يولّد Hermes قيمة session_key خاصة بكل مهمة (task_<id>) — وسيتشارك Hermes ملفات تعريف الارتباط والـ profile مع التطبيق الخارجي، لكنه سيفتح علامة تبويب خاصة به إلى جانبها بدلًا من إعادة استخدام واحدة.

      ملاحظة حول التزامن: يستطيع التطبيق الخارجي و Hermes قيادة userId نفسه في Camofox في الوقت ذاته، لكن Camofox لا ينسّق التركيز على مستوى علامات التبويب بين العملاء. نسّق الملكية على مستوى طبقة التطبيق (مثلًا يتوقف التطبيق الخارجي مؤقتًا أثناء عمل Hermes).

      العرض المباشر عبر VNC​

      عندما يعمل Camofox في الوضع المرئي (headed) (مع نافذة متصفح ظاهرة)، فإنه يكشف منفذ VNC في استجابة فحص الصحة (health check). يكتشف Hermes ذلك تلقائيًا ويُضمّن عنوان VNC URL في استجابات التنقل، حتى يتمكن الوكيل من مشاركة رابط تشاهد من خلاله المتصفح مباشرةً.

      محرك Lightpanda المحلي​

      Lightpanda متصفح headless مفتوح المصدر كُتب من الصفر. يبدأ فورًا، ويعمل أسرع بـ 9 مرات ويستهلك ذاكرة أقل بـ 16 مرة من Chrome، وهذا مهم للوكلاء الذين يعملون على أجهزة افتراضية (VMs) صغيرة لفترات طويلة.

      Lightpanda محرك محلي (مصدر للمتصفح، مثل "Local Browser")، وليس مزوّدًا سحابيًا. ثبّت الملف التنفيذي وضعه ضمن PATH لديك (راجع دليل تثبيت Lightpanda)، ثم اختر Lightpanda في hermes tools → Browser Automation، أو اضبط:

      # Add to ~/.hermes/config.yaml
      browser:
        cloud_provider: local
        engine: lightpanda

      أو عبر متغير البيئة:

      AGENT_BROWSER_ENGINE=lightpanda

      يعمل المحرك مع مشغّلَي المتصفح كليهما:

      • وضع Browser Use (الافتراضي). يُطلق Hermes بنفسه lightpanda serve --host 127.0.0.1 --port <free> — عملية واحدة لكل اسم جلسة browser_exec (أو لكل مهمة) — ويوجّه Browser Use CLI إليها. لا حاجة إلى Chromium أو Playwright أو Node.js. تُنهى العملية بعد browser.inactivity_timeout، وعند الخروج، وبواسطة عملية تنظيف العمليات اليتيمة إذا تعطّل Hermes. تتشارك كل هذه العمليات تخزينًا مؤقتًا واحدًا لـ HTTP على القرص في $HERMES_HOME/cache/browser-use/lightpanda/http-cache، لذا تتخطى الزيارات المتكررة إعادة تنزيل الموارد. لا يمرّر Hermes خيار التخزين المؤقت إلا عندما يدعمه إصدار Lightpanda المثبّت (0.3.x+)؛ أما الملفات التنفيذية الأقدم فتعمل ببساطة دون تخزين مؤقت. لمسحه، أوقف جلسات Lightpanda أولًا، ثم احذف ذلك المجلد. لا يملك Lightpanda محرك عرض رسومي، لذا فإن capture_screenshot() غير متاحة ويُوجّه وصف الأداة النموذجَ إلى العمل بالنص أولًا؛ كما أنه يحتفظ بصفحة واحدة لكل جلسة، لذا يُطلب من النموذج استدعاء new_tab() مرة واحدة ثم goto_url() بعد ذلك (تجري متابعة ذلك في المشروع الأصلي عبر lightpanda-io/browser#1962).
      • أدوات المتصفح المدمجة (/browser use off). يقود Hermes متصفح Lightpanda عبر agent-browser --engine lightpanda باستخدام CDP، بالطريقة نفسها التي يقود بها Chrome المحلي، مع رجوع تلقائي إلى Chrome: يتولى Lightpanda الإجراءات التي يدعمها (navigate و snapshot و click و type و scroll و back و press و eval)، ويعيد Hermes بشفافية محاولة أي إجراء لا يدعمه على Chrome. أما لقطات الشاشة و browser_vision فتُوجَّه مباشرةً إلى Chrome.

      متى يُتجاهل المحرك. browser.engine هو إعداد المتصفح ذو الأسبقية الأدنى: فالمزوّد السحابي (بما في ذلك متصفح اشتراك Nous — وفي الإعدادات التي لم تُضبط من قبل، يؤدي وجود أي BROWSERBASE_API_KEY / BROWSER_USE_API_KEY في ~/.hermes/.env إلى اختيار أحدها تلقائيًا)، و Camofox، وتجاوز browser.cdp_url / /browser connect، و browser.use_real_profile كلها تتقدّم عليه. يؤدي اختيار Lightpanda في hermes tools إلى كتابة cloud_provider: local نيابةً عنك؛ ويُبلغ /browser status و hermes doctor عندما يكون المحرك مُعدًّا لكنه محجوب، ويذكران ما الذي يحجبه.

      متصفح محلي من عائلة Chromium عبر CDP (/browser connect)​

      بدلًا من مزوّد سحابي، يمكنك ربط أدوات متصفح Hermes بنسخة Chrome أو Brave أو Chromium أو Edge قيد التشغيل لديك عبر Chrome DevTools Protocol (CDP). ويفيد هذا عندما تريد رؤية ما يفعله الوكيل في الوقت الفعلي، أو التفاعل مع صفحات تتطلب ملفات تعريف الارتباط/الجلسات الخاصة بك، أو تجنّب تكاليف المتصفح السحابي.

      ملاحظة

      /browser connect هو slash command خاص بـ CLI التفاعلية — ولا يُعالجه الـ gateway. إذا حاولت تشغيله داخل WebUI أو Telegram أو Discord أو أي محادثة gateway أخرى، فستُرسل الرسالة إلى الوكيل كنص عادي ولن يُنفّذ الأمر. شغّل Hermes من الطرفية (hermes أو hermes chat) وأصدر الأمر /browser connect هناك.

      في CLI، استخدم:

      /browser connect                 # Auto-launch/connect to a local Chromium-family browser at http://127.0.0.1:9222
      /browser connect ws://host:port  # Connect to a specific CDP endpoint
      /browser status                  # Check current connection
      /browser disconnect              # Detach and return to cloud/local mode

      إذا لم يكن هناك متصفح يعمل بالفعل مع تفعيل التصحيح عن بُعد، فسيحاول Hermes إطلاق متصفح مدعوم من عائلة Chromium تلقائيًا مع --remote-debugging-port=9222. يشمل الاكتشاف Brave و Brave Origin/Nightly و Google Chrome و Chromium و Microsoft Edge، مع مسارات التثبيت الشائعة في Linux وأسماء الملفات التنفيذية مثل brave-origin و brave-origin-nightly و /opt/brave.com/brave-origin/brave-origin و /opt/brave.com/brave-origin-nightly/brave-origin و /opt/brave-bin/brave و /snap/bin/brave.

      نصيحة

      لتشغيل متصفح من عائلة Chromium يدويًا مع تفعيل CDP، استخدم user-data-dir مخصصًا حتى يعمل منفذ التصحيح فعلًا حتى لو كان المتصفح يعمل بالفعل بالـ profile العادي لديك:

      # Linux — Brave
      brave-browser \
        --remote-debugging-port=9222 \
        --user-data-dir=$HOME/.hermes/chrome-debug \
        --no-first-run \
        --no-default-browser-check &

      # Linux — Google Chrome
      google-chrome \
        --remote-debugging-port=9222 \
        --user-data-dir=$HOME/.hermes/chrome-debug \
        --no-first-run \
        --no-default-browser-check &

      # macOS — Brave
      "/Applications/Brave Browser.app/Contents/MacOS/Brave Browser" \
        --remote-debugging-port=9222 \
        --user-data-dir="$HOME/.hermes/chrome-debug" \
        --no-first-run \
        --no-default-browser-check &

      # macOS — Google Chrome
      "/Applications/Google Chrome.app/Contents/MacOS/Google Chrome" \
        --remote-debugging-port=9222 \
        --user-data-dir="$HOME/.hermes/chrome-debug" \
        --no-first-run \
        --no-default-browser-check &

      ثم شغّل Hermes CLI ونفّذ /browser connect.

      لماذا --user-data-dir؟ بدونه، يؤدي إطلاق متصفح من عائلة Chromium أثناء تشغيل نسخة عادية منه عادةً إلى فتح نافذة جديدة ضمن العملية الموجودة — وتلك العملية لم تُبدأ مع --remote-debugging-port، لذا لا يُفتح المنفذ 9222 أبدًا. يفرض user-data-dir المخصص بدء عملية متصفح جديدة يستمع فيها منفذ التصحيح فعلًا. ويتخطى --no-first-run --no-default-browser-check معالج التشغيل الأول للـ profile الجديد.

      يجعل Chrome 136+ الـ profile المخصص إلزاميًا. هناك آليتان منفصلتان تعملان هنا، ولا تنطبق أيٌّ منهما بمجرد تمرير --user-data-dir غير افتراضي. أولًا، منذ Chrome 136 صار --remote-debugging-port و --remote-debugging-pipe "لا يُحترمان عند محاولة تصحيح مجلد بيانات Chrome الافتراضي" — إذ يُتجاهل الخيار بصمت دون أي نافذة حوار، ويتلقى /browser connect (أو curl http://127.0.0.1:9222/json/version) رفضًا للاتصال حتى عند البدء من حالة الإيقاف الكامل. ثانيًا، يضيف Chrome 144+ مسار موافقة اختياريًا لتصحيح الـ profile الحقيقي: تفعّله من chrome://inspect/#remote-debugging، ثم يعرض Chrome نافذة الحوار "Allow remote debugging?" مع كل اتصال وارد (وليس مرة واحدة لكل إطلاق)، ولا يستمع أي شيء حتى تضغط Allow. إذا رأيت نافذة الحوار هذه، فأنت على مسار الموافقة لا مسار الخيار. والحل هو الأوامر أعلاه تمامًا: وجّه --user-data-dir إلى مكان غير مجلد الـ profile الافتراضي لديك (مثل $HOME/.hermes/chrome-debug)، وهو ما لا يحتاج إلى المفتاح ولا إلى نافذة الحوار. ينطبق هذا على إصدارات Chrome و Chromium و Edge و Brave التي تبنّت هذا التغيير.

      يبدأ الـ profile المخصص دون تسجيل دخول في أي شيء. إذا كنت تريد أن يتصفح الوكيل بتسجيلات دخولك الحالية مع عدم ظهور أي نافذة موافقة، فاستخدم browser.use_real_profile بدلًا من ذلك: فهو ينسخ الـ profile النشط لديك في لقطة ويقودها، وهي user-data-dir غير افتراضي، لذا لا تُفعّل أيًّا من الآليتين أبدًا.

      عند الاتصال عبر CDP، تعمل جميع أدوات المتصفح (browser_navigate و browser_click وغيرهما) على نسخة متصفحك الحية بدلًا من تشغيل جلسة سحابية.

      WSL2 مع Chrome على Windows: فضّل MCP على /browser connect​

      إذا كان Hermes يعمل داخل WSL2 بينما تعمل نافذة Chrome التي تريد التحكم فيها على مضيف Windows، فغالبًا لا يكون /browser connect هو المسار الأفضل.

      السبب:

      • يتوقع /browser connect أن يصل Hermes نفسه إلى CDP endpoint قابل للاستخدام
      • غالبًا ما تكشف جلسات التصحيح الحي في إصدارات Chrome الحديثة endpoint محليًا على المضيف لا يمكن الوصول إليه مباشرةً من WSL بالطريقة نفسها التي يُوصل بها إلى منفذ 9222 التقليدي
      • حتى عندما يكون Chrome على Windows قابلًا للتصحيح، فإن أنظف تكامل غالبًا هو ترك خادم MCP للمتصفح على جانب Windows يتصل بـ Chrome، وجعل Hermes يتواصل مع خادم MCP ذلك

      لهذا الإعداد، فضّل استخدام chrome-devtools-mcp عبر دعم MCP في Hermes.

      راجع دليل MCP للاطلاع على خطوات الإعداد العملية:

      الأدوات المتاحة​

      browser_navigate​

      تنتقل إلى عنوان URL. يجب استدعاؤها قبل أي أداة متصفح أخرى، وهي تُهيّئ جلسة Browserbase.

      Navigate to https://github.com/NousResearch
      نصيحة

      لاسترجاع المعلومات البسيطة، فضّل web_search أو web_extract — فهما أسرع وأقل تكلفة. استخدم أدوات المتصفح عندما تحتاج إلى التفاعل مع صفحة (النقر على الأزرار، وتعبئة النماذج، والتعامل مع المحتوى الديناميكي).

      browser_snapshot​

      تحصل على لقطة نصية لشجرة إمكانية الوصول (accessibility tree) للصفحة الحالية. تُعيد العناصر التفاعلية مع معرّفات مرجعية مثل @e1 و @e2 لاستخدامها مع browser_click و browser_type.

      • full=false (الافتراضي): عرض مضغوط يُظهر العناصر التفاعلية فقط
      • full=true: محتوى الصفحة كاملًا

      تُقتطع اللقطات الأكبر من browser.snapshot_threshold (الافتراضي 15,000 حرف — وهي ميزانية الصفحة نفسها المستخدمة في web_extract) تلقائيًا عند حدود الأسطر، دون أي تلخيص بواسطة LLM. وعندما يحدث ذلك، تُحفظ اللقطة الكاملة في ~/.hermes/cache/web/ ويتضمن ناتج الأداة مسار الملف إضافةً إلى استدعاء read_file جاهز للاستخدام، حتى يتمكن الوكيل من تصفّح شجرة إمكانية الوصول الكاملة — بما في ذلك مراجع العناصر الواقعة بعد نقطة القطع — دون التقاط لقطة جديدة.

      ارفع الحد للصفحات الطويلة التي ينبغي أن يصل فيها مزيد من المحتوى الأصلي إلى الوكيل مباشرةً:

      # ~/.hermes/config.yaml
      browser:
        snapshot_threshold: 30000

      يمكنك أيضًا تنفيذ hermes config set browser.snapshot_threshold 30000. ينطبق الإعداد على استدعاءات browser_snapshot الصريحة وعلى اللقطة التلقائية المُعادة بعد التنقل، بما في ذلك backend الخاص بـ Camofox (الحد الأدنى 1000). أعد تشغيل جلسة Hermes الحالية بعد تغييره حتى يُعاد تحميل التخزين المؤقت لإعدادات المتصفح.

      browser_click​

      تنقر على عنصر يُحدَّد بمعرّفه المرجعي (ref ID) من اللقطة.

      Click @e5 to press the "Sign In" button

      browser_type​

      تكتب نصًا في حقل إدخال. تمسح الحقل أولًا، ثم تكتب النص الجديد.

      Type "hermes agent" into the search field @e3

      browser_scroll​

      تمرّر الصفحة لأعلى أو لأسفل لإظهار مزيد من المحتوى.

      Scroll down to see more results

      browser_press​

      تضغط مفتاحًا على لوحة المفاتيح. مفيدة لإرسال النماذج أو للتنقل.

      Press Enter to submit the form

      المفاتيح المدعومة: Enter و Tab و Escape و ArrowDown و ArrowUp وغيرها.

      browser_back​

      تعود إلى الصفحة السابقة في سجل المتصفح.

      browser_get_images​

      تسرد جميع الصور في الصفحة الحالية مع عناوين URL الخاصة بها ونصوصها البديلة (alt text). مفيدة للعثور على صور لتحليلها.

      browser_vision​

      تلتقط لقطة شاشة وتحللها باستخدام الذكاء الاصطناعي البصري (vision AI). استخدمها عندما لا تلتقط اللقطات النصية معلومات بصرية مهمة — وهي مفيدة خاصةً مع CAPTCHA أو التخطيطات المعقدة أو تحديات التحقق البصري.

      تُحفظ لقطة الشاشة بشكل دائم ويُعاد مسار الملف مع تحليل الذكاء الاصطناعي. على منصات المراسلة (Telegram و Discord و Slack و WhatsApp)، يمكنك أن تطلب من الوكيل مشاركة لقطة الشاشة — وستُرسل كمرفق صورة أصلي عبر آلية MEDIA:.

      What does the chart on this page show?

      تُخزَّن لقطات الشاشة في ~/.hermes/cache/screenshots/ وتُنظَّف تلقائيًا بعد 24 ساعة.

      browser_console​

      تحصل على مخرجات وحدة تحكم المتصفح (رسائل log/warn/error) واستثناءات JavaScript غير الملتقطة من الصفحة الحالية. وهي ضرورية لاكتشاف أخطاء JS الصامتة التي لا تظهر في شجرة إمكانية الوصول.

      Check the browser console for any JavaScript errors

      استخدم clear=True لمسح وحدة التحكم بعد القراءة، بحيث لا تُظهر الاستدعاءات اللاحقة إلا الرسائل الجديدة.

      تُقيّم browser_console أيضًا كود JavaScript عند استدعائها مع الوسيط expression — بالشكل نفسه المستخدم في وحدة تحكم DevTools، وتعود النتيجة محلَّلة (تصبح الكائنات المُسلسَلة بصيغة JSON قواميس dicts، وتبقى القيم البدائية كما هي).

      browser_console(expression="document.querySelector('h1').textContent")
      browser_console(expression="JSON.stringify(performance.timing)")

      عندما يكون CDP supervisor نشطًا للجلسة الحالية (وهو المعتاد لأي جلسة نفّذت browser_navigate على backend يدعم CDP)، يجري التقييم عبر WebSocket الدائم الخاص بالـ supervisor — دون تكلفة بدء عملية فرعية. وإلا فيرجع إلى مسار agent-browser CLI القياسي. السلوك متطابق في الحالتين؛ ولا يتغير سوى زمن الاستجابة.

      التقييم غير مقيّد افتراضيًا — إذ يستطيع الوكيل استخدام fetch، وقراءة التخزين، والاستعلام عن قيم النماذج، وتنفيذ أي استخراج من DOM. ولا تزال الطلبات الموجّهة إلى عناوين خاصة/داخلية محظورة على الـ backends غير المحلية (فحماية SSRF مستقلة عن هذا الإعداد). إذا كنت تتصفح صفحات معادية باستخدام profile مسجّل الدخول وتريد قائمة حظر صارمة على دوال JS البدائية الحساسة (ملفات تعريف الارتباط، والتخزين، والحافظة، واستدعاءات الشبكة، وقيم النماذج)، ففعّلها باستخدام browser.restrict_evaluate: true في config.yaml. لاحظ أن قائمة الحظر تطابق أسماء الدوال البدائية، لذا فهي تحظر أيضًا التعبيرات المشروعة التي تحتوي فقط على كلمات مثل fetch أو cookie.

      browser_cdp​

      تمرير خام لأوامر Chrome DevTools Protocol — وهو منفذ الطوارئ لعمليات المتصفح التي لا تغطيها الأدوات الأخرى. استخدمها للتعامل مع نوافذ الحوار الأصلية، أو التقييم ضمن نطاق iframe، أو التحكم في ملفات تعريف الارتباط/الشبكة، أو أي أمر CDP يحتاجه الوكيل.

      متاحة فقط عندما يمكن الوصول إلى CDP endpoint عند بدء الجلسة — أي عندما يكون /browser connect قد اتصل بمتصفح Chrome أو Brave أو Chromium أو Edge قيد التشغيل، أو يكون browser.cdp_url مضبوطًا في config.yaml. لا يكشف وضع agent-browser المحلي الافتراضي، ولا Camofox، ولا المزوّدون السحابيون (Browserbase و Browser Use و Firecrawl) حاليًا CDP لهذه الأداة — فالمزوّدون السحابيون لديهم عناوين CDP URL لكل جلسة، لكن توجيه الجلسات الحية عمل مُخطط له لاحقًا.

      مرجع أساليب CDP: https://chromedevtools.github.io/devtools-protocol/ — يستطيع الوكيل تنفيذ web_extract على صفحة أسلوب محدد للاطلاع على معاملاته وشكل القيمة المُعادة.

      أنماط شائعة:

      # List tabs (browser-level, no target_id)
      browser_cdp(method="Target.getTargets")

      # Handle a native JS dialog on a tab
      browser_cdp(method="Page.handleJavaScriptDialog",
                  params={"accept": true, "promptText": ""},
                  target_id="<tabId>")

      # Evaluate JS in a specific tab
      browser_cdp(method="Runtime.evaluate",
                  params={"expression": "document.title", "returnByValue": true},
                  target_id="<tabId>")

      # Get all cookies
      browser_cdp(method="Network.getAllCookies")

      تحذف الأساليب على مستوى المتصفح (Target.* و Browser.* و Storage.*) المعامل target_id. أما الأساليب على مستوى الصفحة (Page.* و Runtime.* و DOM.* و Emulation.*) فتتطلب target_id مأخوذًا من Target.getTargets. كل استدعاء عديم الحالة مستقل — فالجلسات لا تستمر بين الاستدعاءات.

      إطارات iframe متعددة الأصول (cross-origin): مرّر frame_id (من browser_snapshot.frame_tree.children[] حيث is_oopif=true) لتوجيه استدعاء CDP عبر جلسة الـ supervisor الحية لذلك الـ iframe. هكذا يعمل Runtime.evaluate داخل iframe متعدد الأصول على Browserbase، حيث قد تصطدم اتصالات CDP عديمة الحالة بانتهاء صلاحية عناوين URL الموقّعة. مثال:

      browser_cdp(
        method="Runtime.evaluate",
        params={"expression": "document.title", "returnByValue": True},
        frame_id="<frame_id from browser_snapshot>",
      )

      لا تحتاج إطارات iframe ذات الأصل نفسه إلى frame_id — استخدم بدلًا من ذلك document.querySelector('iframe').contentDocument من Runtime.evaluate على المستوى الأعلى.

      browser_dialog​

      تستجيب لنافذة حوار JS أصلية (alert / confirm / prompt / beforeunload). قبل وجود هذه الأداة، كانت نوافذ الحوار تحجب بصمت خيط JavaScript الخاص بالصفحة، فتتعلّق استدعاءات browser_* اللاحقة أو تُطلق أخطاء؛ أما الآن فيرى الوكيل نوافذ الحوار المعلّقة في مخرجات browser_snapshot ويستجيب لها صراحةً.

      سير العمل:

      1. استدعِ browser_snapshot. إذا كانت هناك نافذة حوار تحجب الصفحة، فستظهر بالشكل pending_dialogs: [{"id": "d-1", "type": "alert", "message": "..."}].
      2. استدعِ browser_dialog(action="accept") أو browser_dialog(action="dismiss"). بالنسبة لنوافذ الحوار prompt()، مرّر prompt_text="..." لتقديم الاستجابة.
      3. التقط لقطة جديدة — ستكون pending_dialogs فارغة، وقد استأنف خيط JS في الصفحة عمله.

      يحدث الاكتشاف تلقائيًا عبر CDP supervisor دائم — WebSocket واحد لكل مهمة يشترك في أحداث Page/Runtime/Target. ويملأ الـ supervisor أيضًا الحقل frame_tree في اللقطة حتى يتمكن الوكيل من رؤية بنية إطارات iframe في الصفحة الحالية، بما في ذلك إطارات iframe متعددة الأصول (OOPIF).

      مصفوفة التوفر:

      الـ Backendالاكتشاف عبر pending_dialogsالاستجابة (أداة browser_dialog)
      Chrome المحلي عبر /browser connect أو browser.cdp_url✓✓ سير عمل كامل
      Browserbase✓✓ سير عمل كامل (عبر جسر XHR مُحقَن)
      Camofox / agent-browser المحلي الافتراضي✗✗ (لا يوجد CDP endpoint)

      كيف يعمل على Browserbase. يرفض CDP proxy الخاص بـ Browserbase نوافذ الحوار الأصلية الحقيقية تلقائيًا على جانب الخادم خلال ~10ms، لذا لا يمكننا استخدام Page.handleJavaScriptDialog. يحقن الـ supervisor سكربتًا صغيرًا عبر Page.addScriptToEvaluateOnNewDocument يستبدل window.alert/confirm/prompt بطلب XHR متزامن. ونعترض طلبات XHR هذه عبر Fetch.enable — فيبقى خيط JS في الصفحة محجوبًا على طلب XHR حتى نستدعي Fetch.fulfillRequest مع استجابة الوكيل. وتعود القيم المُرجعة من prompt() إلى JS الصفحة دون تغيير.

      سياسة نوافذ الحوار تُضبط في config.yaml تحت browser.dialog_policy:

      السياسةالسلوك
      must_respond (الافتراضي)الالتقاط، ثم الإظهار في اللقطة، ثم انتظار استدعاء browser_dialog() صريح. مع رفض تلقائي احترازي بعد browser.dialog_timeout_s (الافتراضي 300s) حتى لا يتمكن وكيل معطوب من التعليق إلى الأبد.
      auto_dismissالالتقاط، ثم الرفض فورًا. يظل الوكيل يرى نافذة الحوار في سجل browser_state لكنه لا يحتاج إلى اتخاذ أي إجراء.
      auto_acceptالالتقاط، ثم القبول فورًا. مفيد عند التنقل في صفحات تُظهر مطالبات beforeunload مُلحّة.

      شجرة الإطارات داخل browser_snapshot.frame_tree محدودة بـ 30 إطارًا وبعمق OOPIF يساوي 2 لإبقاء حجم الحمولة محدودًا في الصفحات المليئة بالإعلانات. ويظهر الخيار truncated: true عند بلوغ هذه الحدود؛ ويمكن للوكلاء الذين يحتاجون إلى الشجرة الكاملة استخدام browser_cdp مع Page.getFrameTree.

      تعبئة نموذج ويب​

      User: Sign up for an account on example.com with my email john@example.com

      Agent workflow:
      1. browser_navigate("https://example.com/signup")
      2. browser_snapshot()  → sees form fields with refs
      3. browser_type(ref="@e3", text="john@example.com")
      4. browser_type(ref="@e5", text="SecurePass123")

      3. Returns formatted results

      تسجيل الجلسات​

      سجّل جلسات المتصفح تلقائيًا كملفات فيديو بصيغة WebM:

      browser:
        record_sessions: true  # default: false

      عند التفعيل، يبدأ التسجيل تلقائيًا مع أول استدعاء لـ browser_navigate ويُحفظ في ~/.hermes/browser_recordings/ عند إغلاق الجلسة. يعمل في الوضعين المحلي والسحابي (Browserbase). وتُحذف التسجيلات الأقدم من 72 ساعة تلقائيًا.

      وضع Headed (نافذة متصفح مرئية)​

      افتراضيًا، يعمل المتصفح المحلي في وضع headless. فعّل وضع headed للحصول على نافذة Chromium مرئية يمكنك مشاهدتها والتفاعل معها:

      browser:
        headed: true  # default: false

      أو عبر متغير البيئة: AGENT_BROWSER_HEADED=1.

      يؤدي وضع headed أمرين:

      1. يُطلق Chromium بنافذة مرئية (يمرّر --headed إلى agent-browser في الوضع المحلي).
      2. يُبقي النافذة مفتوحة بين الأدوار. عادةً تُنظَّف جلسة المتصفح بعد كل رد من الوكيل؛ أما في وضع headed فيُتخطى التنظيف الخاص بكل دور حتى تتمكن من مشاهدة الوكيل أثناء العمل، والتدخل يدويًا (تحديات تسجيل الدخول، CAPTCHA)، والإبقاء على حالة تسجيل الدخول نشطة طوال المحادثة.

      لا تزال الجلسات الخاملة تُنهى بعد browser.inactivity_timeout (الافتراضي 120s دون أي نشاط في المتصفح)، وتُغلق جميع الجلسات عند إيقاف التشغيل. يؤثر وضع headed في المتصفح المحلي فقط — ولا تتأثر الجلسات السحابية (Browserbase).

      إدارة الجلسات​

      • تحصل كل مهمة على جلسة متصفح معزولة عبر Browserbase
      • تُنظَّف الجلسات تلقائيًا بعد فترة من عدم النشاط (الافتراضي: دقيقتان)
      • يفحص خيط (thread) يعمل في الخلفية كل 30 ثانية بحثًا عن الجلسات القديمة
      • يعمل تنظيف طارئ عند خروج العملية لمنع بقاء جلسات يتيمة
      • تُحرَّر الجلسات عبر Browserbase API (بالحالة REQUEST_RELEASE)

      القيود​

      • تفاعل نصي — يعتمد على شجرة إمكانية الوصول، لا على إحداثيات البكسل
      • حجم اللقطة — تُقتطع الصفحات الكبيرة عند browser.snapshot_threshold (الافتراضي 15,000 حرف، مطابقًا لـ web_extract؛ دون تلخيص بواسطة LLM)؛ وتُحفظ اللقطة الكاملة في ~/.hermes/cache/web/ ويشير الناتج إليها لتصفّحها عبر read_file
      • مهلة الجلسة — تنتهي صلاحية الجلسات السحابية وفقًا لإعدادات خطة المزوّد لديك
      • التكلفة — تستهلك الجلسات السحابية أرصدة المزوّد؛ وتُنظَّف الجلسات تلقائيًا عند انتهاء المحادثة أو بعد فترة من عدم النشاط. استخدم /browser connect للتصفح المحلي المجاني.
      • لا يمكن تنزيل الملفات — لا تستطيع تنزيل الملفات من المتصفح

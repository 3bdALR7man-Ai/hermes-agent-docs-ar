      ذاكرة Honcho

      Honcho هو backend للذاكرة مصمَّم أصلًا للذكاء الاصطناعي (AI-native)، يضيف الاستدلال الجدلي (dialectic reasoning) والنمذجة العميقة للمستخدم فوق نظام الذاكرة المدمج في Hermes. فبدلًا من التخزين البسيط بصيغة مفتاح-قيمة، يحتفظ Honcho بنموذج متجدد عن هوية المستخدم — تفضيلاته وأسلوب تواصله وأهدافه وأنماطه — من خلال الاستدلال على المحادثات بعد حدوثها.

      Honcho إضافة لمزوّد الذاكرة (Memory Provider Plugin)

      Honcho مدمج في نظام مزوّدي الذاكرة (Memory Providers). جميع الميزات الموضّحة أدناه متاحة عبر واجهة مزوّد الذاكرة الموحّدة.

      ما الذي يضيفه Honcho​

      القدرةالذاكرة المدمجةHoncho
      الاستمرارية عبر الجلسات✔ قائمة على الملفات MEMORY.md/USER.md✔ على الخادم عبر API
      الملف الشخصي للمستخدم✔ تنسيق يدوي من الوكيل✔ استدلال جدلي تلقائي
      ملخّص الجلسة—✔ حقن سياق محصور بالجلسة
      العزل بين الوكلاء المتعددين—✔ فصل الملفات الشخصية لكل peer
      أوضاع المراقبة—✔ مراقبة موحّدة أو اتجاهية
      الاستنتاجات (رؤى مشتقة)—✔ استدلال على الأنماط من جهة الخادم
      البحث عبر السجل✔ بحث في الجلسات عبر FTS5✔ بحث دلالي في الاستنتاجات

      الاستدلال الجدلي: بعد كل دور في المحادثة (وفق ما يحدده dialecticCadence)، يحلّل Honcho التبادل ويستخلص رؤى حول تفضيلات المستخدم وعاداته وأهدافه. تتراكم هذه الرؤى مع الوقت، فتمنح الوكيل فهمًا يتعمّق باستمرار ويتجاوز ما صرّح به المستخدم. يدعم الاستدلال الجدلي عمقًا متعدد المراحل (1–3 مراحل) مع اختيار تلقائي بين prompt بارد وآخر دافئ (cold/warm) — إذ تركّز استعلامات البدء البارد على الحقائق العامة عن المستخدم، بينما تعطي الاستعلامات الدافئة الأولوية للسياق المحصور بالجلسة.

      السياق المحصور بالجلسة: يتضمن السياق الأساسي الآن ملخّص الجلسة إلى جانب تمثيل المستخدم وبطاقة الـ peer. يمنح هذا الوكيلَ وعيًا بما نوقش بالفعل في الجلسة الحالية، مما يقلل التكرار ويتيح الاستمرارية.

      الملفات الشخصية متعددة الوكلاء: عندما تتحدث عدة نسخ من Hermes مع المستخدم نفسه (مثل مساعد برمجة ومساعد شخصي)، يحتفظ Honcho بملفات "peer" شخصية منفصلة. يرى كل peer ملاحظاته واستنتاجاته فقط، مما يمنع تداخل السياق بينها.

      الإعداد​

      hermes memory setup    # select "honcho" from the provider list

      أو اضبط الإعدادات يدويًا:

      # ~/.hermes/config.yaml
      memory:
        provider: honcho
      echo 'HONCHO_API_KEY=***' >> ~/.hermes/.env

      احصل على مفتاح API من honcho.dev.

      البنية المعمارية​

      حقن السياق على طبقتين​

      في كل دور (في وضع hybrid أو context)، يجمّع Honcho طبقتين من السياق تُحقنان في الـ system prompt:

      1. السياق الأساسي — ملخّص الجلسة، وتمثيل المستخدم، وبطاقة peer المستخدم، والتمثيل الذاتي للذكاء الاصطناعي، وبطاقة هوية الذكاء الاصطناعي. يُحدَّث وفق contextCadence. هذه هي طبقة "من هو هذا المستخدم".
      2. الملحق الجدلي — استدلال يولّده LLM حول حالة المستخدم الحالية واحتياجاته. يُحدَّث وفق dialecticCadence. هذه هي طبقة "ما المهم الآن".

      تُدمج الطبقتان معًا ثم تُقتطعان لتلائما ميزانية contextTokens (إن كانت مضبوطة).

      اختيار الـ Prompt البارد/الدافئ​

      يختار الاستدلال الجدلي تلقائيًا بين استراتيجيتين للـ prompt:

      • البدء البارد (Cold start) (لا يوجد سياق أساسي بعد): استعلام عام — "Who is this person? What are their preferences, goals, and working style?"
      • الجلسة الدافئة (Warm session) (يوجد سياق أساسي): استعلام محصور بالجلسة — "Given what's been discussed in this session so far, what context about this user is most relevant?"

      يحدث هذا تلقائيًا بناءً على ما إذا كان السياق الأساسي قد مُلئ أم لا.

      ثلاثة مفاتيح ضبط مستقلة​

      تُضبط التكلفة والعمق عبر ثلاثة مفاتيح مستقلة:

      المفتاحما يتحكم فيهالقيمة الافتراضية
      contextCadenceعدد الأدوار بين استدعاءات context() لـ API (تحديث الطبقة الأساسية)1
      dialecticCadenceعدد الأدوار بين استدعاءات LLM عبر peer.chat() (تحديث الطبقة الجدلية)2 (الموصى به 1–5)
      dialecticDepthعدد مراحل .chat() في كل استدعاء جدلي (1–3)1

      هذه المفاتيح مستقلة بعضها عن بعض (orthogonal) — يمكنك تحديث السياق بصورة متكررة مع استدلال جدلي متباعد، أو تشغيل استدلال جدلي عميق متعدد المراحل بتكرار منخفض. مثال: contextCadence: 1, dialecticCadence: 5, dialecticDepth: 2 يحدّث السياق الأساسي في كل دور، ويشغّل الاستدلال الجدلي كل 5 أدوار، وتُجري كل عملية جدلية مرحلتين.

      عمق الاستدلال الجدلي (متعدد المراحل)​

      عندما تكون قيمة dialecticDepth > 1، يُجري كل استدعاء جدلي عدة مراحل من .chat():

      • المرحلة 0: prompt بارد أو دافئ (انظر أعلاه)
      • المرحلة 1: تدقيق ذاتي — تحدّد الثغرات في التقييم الأولي وتجمع الأدلة من الجلسات الأخيرة
      • المرحلة 2: التوفيق — تتحقق من وجود تناقضات بين المراحل السابقة وتُنتج خلاصة نهائية

      تستخدم كل مرحلة مستوى استدلال متناسبًا (مراحل مبكرة أخف، والمستوى الأساسي للمرحلة الرئيسية). يمكنك تجاوز مستوى كل مرحلة عبر dialecticDepthLevels — مثل ["minimal", "medium", "high"] لتشغيل بعمق 3.

      تتوقف المراحل مبكرًا إذا أعادت المرحلة السابقة إشارة قوية (مخرجات طويلة ومنظّمة)، لذا لا يعني العمق 3 دائمًا إجراء 3 استدعاءات LLM.

      التهيئة المسبقة عند بدء الجلسة (Prewarm)​

      عند تهيئة الجلسة، يُطلق Honcho استدعاءً جدليًا في الخلفية بكامل قيمة dialecticDepth المضبوطة، ويسلّم النتيجة مباشرةً إلى عملية تجميع سياق الدور 1. غالبًا ما تُعيد التهيئة المسبقة أحادية المرحلة على peer بارد مخرجات هزيلة — أما العمق متعدد المراحل فيُشغّل دورة التدقيق/التوفيق قبل أن يتحدث المستخدم أصلًا. وإذا لم تكتمل التهيئة المسبقة بحلول الدور 1، يلجأ الدور 1 إلى استدعاء متزامن بمهلة زمنية محدودة.

      مستوى استدلال يتكيّف مع الاستعلام​

      يرفع الاستدلال الجدلي المحقون تلقائيًا قيمة dialecticReasoningLevel بحسب طول الاستعلام: +1 مستوى عند ≥120 حرفًا، و+2 عند ≥400، بحدٍّ أقصى هو reasoningLevelCap (الافتراضي "high"). عطّل ذلك عبر reasoningHeuristic: false لتثبيت كل استدعاء تلقائي على dialecticReasoningLevel. المستويات المتاحة: minimal، low، medium، high، max.

      خيارات الإعدادات​

      تُضبط إعدادات Honcho في ~/.honcho/config.json (عامة) أو $HERMES_HOME/honcho.json (محلية للـ profile). يتولى معالج الإعداد (setup wizard) ذلك نيابةً عنك.

      Honcho مستضاف ذاتيًا مع المصادقة​

      عند توجيه Hermes إلى خادم Honcho مستضاف ذاتيًا، يطلب hermes honcho setup (و hermes memory setup) إدخال JWT / bearer token محلي بعد عنوان URL الأساسي. الصق JWT موقّعًا بقيمة AUTH_JWT_SECRET الخاصة بالخادم (متغير البيئة في ملف compose الخاص بـ Honcho) لتفعيل الوصول المصادَق عليه، أو اتركه فارغًا للخوادم التي تعمل مع AUTH_USE_AUTH=false. يُخزَّن الـ token المحلي ضمن كتلة المضيف (hosts.<host>.apiKey في honcho.json)، منفصلًا عن أي apiKey سحابي، لذا يمكنك لاحقًا إعادة إجابة سؤال Cloud or local? إلى cloud دون فقدان أيٍّ من بيانات الاعتماد.

      استراتيجية الجلسة تتحكم في كيفية ربط جلسات Honcho بعملك:

      • per-session — يحصل كل تشغيل لـ hermes على جلسة جديدة. بدايات نظيفة، والذاكرة متاحة عبر الأدوات. موصى به للمستخدمين الجدد.
      • per-directory — جلسة Honcho واحدة لكل مجلد عمل. يتراكم السياق عبر مرات التشغيل.
      • per-repo — جلسة واحدة لكل مستودع git.
      • global — جلسة واحدة لجميع المجلدات.

      وضع الاستدعاء (Recall mode) يتحكم في كيفية تدفق الذاكرة إلى المحادثات:

      • hybrid — يُحقن السياق تلقائيًا في الـ system prompt وتكون الأدوات متاحة أيضًا (يقرر النموذج متى يستعلم).
      • context — حقن تلقائي فقط، والأدوات مخفية.
      • tools — أدوات فقط، دون حقن تلقائي. يجب على الوكيل استدعاء honcho_reasoning و honcho_search وغيرها صراحةً.

      ربط الهويات في Gateway​

      لا تهمّ هذه الإعدادات إلا عند تشغيل Gateway الخاص بـ Hermes — نقطة الدخول الوحيدة التي يصل عبرها المستخدمون بمعرّفات وقت تشغيل أصلية خاصة بالمنصة (Telegram UID، و Discord snowflake، ومستخدم Slack). أما جلسات CLI و TUI وسطح المكتب فليس لها معرّف وقت تشغيل، وتُحَل دائمًا إلى peerName، لذا لا أثر لهذه المفاتيح خارج الـ gateway.

      يكتشف معالج الإعداد ما إذا كانت هناك منصة gateway متصلة، ويتخطى هذه الخطوة كليًا إن لم تكن كذلك. وعند تشغيلها، يطرح سؤالًا واحدًا — who talks to this gateway? (من يتحدث إلى هذا الـ gateway؟) — ويستنتج المفاتيح من إجابتك:

      الإجابةالنتيجة
      just me (أنا فقط)pinUserPeer: true — يُدمج كل مستخدم للـ gateway ليس وكيلًا في الـ peer الخاص بك. التثبيت (pin) يتجاوز جميع الأسماء المستعارة، لذا اختر هذا الخيار فقط عندما لا تحتاج أي هوية من جهة المستخدمين إلى peer خاص بها. وإذا كان هناك وكلاء منفصلون يصلون إلى الـ gateway ويحتاج كل منهم إلى peer مميز، فلا تستخدم التثبيت — اترك pinUserPeer: false واربطهم عبر userPeerAliases (المحرر [e]) بدلًا من ذلك
      me + other people (أنا وأشخاص آخرون، مجمّع)pinUserPeer: false + userPeerAliases يربط معرّفات وقت التشغيل الخاصة بك بـ peerName — فتبقى أنت على سجلك المشترك، ويحصل الآخرون على peers خاصة بهم
      only other people (أشخاص آخرون فقط)pinUserPeer: false، مع runtimePeerPrefix اختياري — يحصل كل مستخدم على peer خاص به

      اختر [e] عند ظهور السؤال لضبط المفاتيح الثلاثة مباشرةً بدلًا من ذلك.

      يجرّب المحلِّل (resolver) المفاتيح من الأعلى إلى الأسفل، ويُعتمد أول تطابق: pinUserPeer → userPeerAliases[id] → runtimePeerPrefix + id → معرّف وقت التشغيل الخام → peerName → الاحتياطي القائم على مفتاح الجلسة (session-key fallback).

      يُكتب كل دور تحت peer الشخص الذي كتبه، لذا لم يعد أول من يرسل رسالة في المحادثة المشتركة يجمع حقائق الجميع. أما الدور الوارد من بوت آخر (رسالة مباشرة في Bot Mode موسومة بـ bot:<profile>، أو حساب منصة يصنّفه الـ adapter على أنه بوت) فيحصل دائمًا على peer خاص به: إذ يوحّد pinUserPeer حسابات شخص واحد، ولا يشمل البوتات أبدًا. يُسجَّل دور البوت في جلسة a2a خاصة بكل مُرسِل (انظر a2aSessions)، وترفض honcho_conclude / honcho_profile عمليات الكتابة أثناء تنفيذ مثل هذا الدور، لأن الاستنتاجات والبطاقات تصف الإنسان.

      إلغاء التثبيت يترك الذاكرة المجمّعة معزولة

      تحويل pinUserPeer من true إلى false لا ينقل البيانات — تبقى الذاكرة المتراكمة تحت peerName في مكانها، ويُحَل مستخدمو المنصات إلى peers جديدة فارغة. للحفاظ على استمراريتك، اختر المسار المجمّع (pooled) حتى تُربط معرّفات وقت التشغيل الخاصة بك مجددًا بـ peerName. يعرض المعالج هذا التوجيه تلقائيًا عندما يكتشف هذا التحوّل.

      مفتاح مهمل (deprecated)

      pinPeerName اسم مستعار قديم لـ pinUserPeer — لا يزال يُقرأ للتوافق مع الإصدارات السابقة (تكون الأولوية لـ pinUserPeer عند ضبط الاثنين)، لكنه لا يُكتب أبدًا. تؤدي إعادة تشغيل الإعداد إلى ترحيله إلى المفتاح المعتمد.

      المراقبة (الاتجاهية مقابل الموحّدة)​

      يمثّل Honcho المحادثة على أنها peers يتبادلون الرسائل. لكل peer مفتاحا مراقبة يقابلان إعدادات SessionPeerConfig في Honcho مقابلةً مباشرة (1:1):

      المفتاحالتأثير
      observeMeيبني Honcho تمثيلًا لهذا الـ peer من رسائله الخاصة
      observeOthersيراقب هذا الـ peer رسائل الـ peer الآخر (يغذّي الاستدلال بين الـ peers)

      اثنان من الـ peers × مفتاحان = أربع رايات (flags). والمفتاح observationMode إعداد مسبق مختصر:

      الإعداد المسبقرايات المستخدمرايات الذكاء الاصطناعيالدلالة
      "directional" (الافتراضي)me: on, others: onme: on, others: onمراقبة متبادلة كاملة. تتيح الاستدلال الجدلي بين الـ peers — "ما الذي يعرفه الذكاء الاصطناعي عن المستخدم، بناءً على ما قاله المستخدم وما ردّ به الذكاء الاصطناعي."
      "unified"me: on, others: offme: off, others: onدلالة المجمّع المشترك — يراقب الذكاء الاصطناعي رسائل المستخدم فقط، ويكتفي peer المستخدم بنمذجة ذاته. مجمّع بمراقِب واحد.

      تجاوز الإعداد المسبق بكتلة observation صريحة للتحكم في كل peer على حدة:

      "observation": {
        "user": { "observeMe": true,  "observeOthers": true },
        "ai":   { "observeMe": true,  "observeOthers": false }
      }

      الأنماط الشائعة:

      الهدفالإعداد
      مراقبة كاملة (معظم المستخدمين)"observationMode": "directional"
      لا ينبغي للذكاء الاصطناعي إعادة نمذجة المستخدم من ردوده الخاصة"ai": {"observeMe": true, "observeOthers": false}
      شخصية (persona) قوية لا ينبغي لـ peer الذكاء الاصطناعي تحديثها من المراقبة الذاتية"ai": {"observeMe": false, "observeOthers": true}

      المفاتيح المضبوطة من جهة الخادم عبر لوحة تحكم Honcho لها الأولوية على القيم الافتراضية المحلية — إذ يزامنها Hermes عند تهيئة الجلسة.

      الأدوات​

      عندما يكون Honcho مزوّد الذاكرة النشط، تصبح خمس أدوات متاحة:

      الأداةالغرض
      honcho_profileقراءة بطاقة الـ peer أو تحديثها — مرّر card (قائمة حقائق) للتحديث، أو أغفِله للقراءة
      honcho_searchبحث دلالي في السياق — مقتطفات خام دون توليف من LLM
      honcho_contextسياق الجلسة الكامل — الملخّص، والتمثيل، والبطاقة، والرسائل الأخيرة
      honcho_reasoningإجابة مُولَّفة من LLM الخاص بـ Honcho — مرّر reasoning_level (minimal/low/medium/high/max) للتحكم في العمق
      honcho_concludeإنشاء الاستنتاجات أو حذفها — مرّر conclusion للإنشاء، و delete_id للحذف (للبيانات الشخصية PII فقط)

      أوامر CLI​

      الأمر الفرعي hermes honcho لا يُسجَّل إلا عندما يكون Honcho مزوّد الذاكرة النشط (memory.provider: honcho في config.yaml). في التثبيت الجديد، اضبط Honcho مباشرةً باستخدام hermes memory setup honcho (أو شغّل hermes memory setup واختره من القائمة)؛ وسيظهر بعدها الأمر الفرعي hermes honcho في الاستدعاء التالي.

      hermes memory setup honcho    # Configure Honcho directly (works before activation)
      hermes honcho status          # Connection status, config, and key settings
      hermes honcho setup           # Redirects to `hermes memory setup` (post-activation alias)
      hermes honcho strategy        # Show or set session strategy (per-session/per-directory/per-repo/global)
      hermes honcho peer            # Show or update peer names + dialectic reasoning level
      hermes honcho mode            # Show or set recall mode (hybrid/context/tools)
      hermes honcho tokens          # Show or set token budget for context and dialectic
      hermes honcho identity        # Seed or show the AI peer's Honcho identity
      hermes honcho sync            # Sync Honcho config to all existing profiles
      hermes honcho peers           # Show peer identities across all profiles
      hermes honcho sessions        # List known Honcho session mappings
      hermes honcho map             # Map current directory to a Honcho session name
      hermes honcho enable          # Enable Honcho for the active profile
      hermes honcho disable         # Disable Honcho for the active profile
      hermes honcho migrate         # Step-by-step migration guide from openclaw-honcho

      الانتقال من hermes honcho​

      إذا كنت تستخدم سابقًا الأمر المستقل hermes honcho setup:

      1. تبقى إعداداتك الحالية (honcho.json أو ~/.honcho/config.json) محفوظة
      2. تبقى بياناتك على الخادم (الذكريات، والاستنتاجات، وملفات المستخدمين الشخصية) سليمة
      3. اضبط memory.provider: honcho في config.yaml لإعادة التفعيل

      لا حاجة إلى إعادة تسجيل الدخول أو إعادة الإعداد. شغّل hermes memory setup واختر "honcho" — وسيكتشف المعالج إعداداتك الحالية.

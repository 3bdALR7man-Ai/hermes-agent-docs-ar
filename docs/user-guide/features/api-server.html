      خادم API

      يوفّر خادم API وكيل hermes-agent على شكل HTTP endpoint متوافق مع OpenAI. ويمكن لأي واجهة أمامية (frontend) تتعامل بصيغة OpenAI — مثل Open WebUI و LobeChat و LibreChat و NextChat و ChatBox ومئات غيرها — الاتصال بـ hermes-agent واستخدامه كـ backend.

      يعالج وكيلك الطلبات بمجموعة أدواته الكاملة (الطرفية، وعمليات الملفات، والبحث في الويب، والذاكرة، والمهارات) ثم يُرجع الاستجابة النهائية. وعند البث (streaming)، تظهر مؤشرات تقدّم الأدوات ضمن الاستجابة مباشرةً لتتمكن الواجهات الأمامية من عرض ما يفعله الوكيل.

      backend واحد يغطي النماذج والأدوات

      يحتاج Hermes نفسه إلى مزوّد مُعدّ وإلى backends للأدوات حتى يكون خادم API مفيدًا. ويتكفّل اشتراك Nous Portal بالأمرين معًا — أكثر من 300 نموذج إضافةً إلى الويب/الصور/TTS/المتصفح عبر Tool Gateway. نفّذ hermes setup --portal مرة واحدة قبل تشغيل خادم API، وستحصل الواجهات الأمامية مثل Open WebUI أو LobeChat على backend مجهّز بالأدوات بالكامل.

      البدء السريع​

      1. فعّل خادم API​

      أضف ما يلي إلى ~/.hermes/.env:

      API_SERVER_ENABLED=true
      API_SERVER_KEY=change-me-local-dev
      # Optional: only if a browser must call Hermes directly
      # API_SERVER_CORS_ORIGINS=http://localhost:3000

      2. شغّل gateway​

      hermes gateway

      سترى ما يلي:

      [API Server] API server listening on http://127.0.0.1:8642

      3. اربط واجهة أمامية​

      وجّه أي عميل متوافق مع OpenAI إلى http://localhost:8642/v1:

      # Test with curl
      curl http://localhost:8642/v1/chat/completions \
        -H "Authorization: Bearer change-me-local-dev" \
        -H "Content-Type: application/json" \
        -d '{"model": "hermes-agent", "messages": [{"role": "user", "content": "Hello!"}]}'

      أو اربط Open WebUI أو LobeChat أو أي واجهة أمامية أخرى — راجع دليل التكامل مع Open WebUI للاطلاع على التعليمات خطوة بخطوة.

      Endpoints​

      POST /v1/chat/completions​

      صيغة OpenAI Chat Completions القياسية. عديمة الحالة (stateless) — إذ تُضمَّن المحادثة الكاملة في كل طلب عبر المصفوفة messages.

      الطلب:

      {
        "model": "hermes-agent",
        "messages": [
          {"role": "system", "content": "You are a Python expert."},
          {"role": "user", "content": "Write a fibonacci function"}
        ],
        "stream": false
      }

      الاستجابة:

      {
        "id": "chatcmpl-abc123",
        "object": "chat.completion",
        "created": 1710000000,
        "model": "hermes-agent",
        "choices": [{
          "index": 0,
          "message": {"role": "assistant", "content": "Here's a fibonacci function..."},
          "finish_reason": "stop"
        }],
        "usage": {"prompt_tokens": 50, "completion_tokens": 200, "total_tokens": 250}
      }

      إدخال الصور المضمّنة: يمكن لرسائل المستخدم إرسال content كمصفوفة من أجزاء text و image_url. وتُدعم كلٌّ من عناوين http(s) البعيدة وعناوين data:image/...:

      {
        "model": "hermes-agent",
        "messages": [
          {
            "role": "user",
            "content": [
              {"type": "text", "text": "What is in this image?"},
              {"type": "image_url", "image_url": {"url": "https://example.com/cat.png", "detail": "high"}}
            ]
          }
        ]
      }

      أما الملفات المرفوعة (file / input_file / file_id) وعناوين data: التي لا تمثّل صورًا فتُرجع 400 unsupported_content_type.

      البث (Streaming) ("stream": true): يُرجع Server-Sent Events (SSE) تتضمن أجزاء الاستجابة token تلو الآخر. في Chat Completions، يستخدم البث أحداث chat.completion.chunk القياسية إضافةً إلى الحدث المخصص hermes.tool.progress من Hermes لإظهار بدء تشغيل الأدوات في الواجهة. وفي Responses، يستخدم البث أنواع أحداث OpenAI Responses مثل response.created و response.output_text.delta و response.output_item.added و response.output_item.done و response.completed.

      تقدّم الأدوات أثناء البث:

      • Chat Completions: يُصدر Hermes الحدث event: hermes.tool.progress لإظهار بدء الأدوات دون تلويث نص المساعد المحفوظ.
      • Responses: يُصدر Hermes عناصر مُخرَجات function_call و function_call_output الأصلية وفق المواصفة أثناء بث SSE، لكي يتمكن العملاء من عرض واجهة أدوات منظّمة في الوقت الفعلي.

      POST /v1/responses​

      صيغة OpenAI Responses API. تدعم الاحتفاظ بحالة المحادثة على جانب الخادم عبر previous_response_id — إذ يخزّن الخادم سجل المحادثة الكامل (بما في ذلك استدعاءات الأدوات ونتائجها)، فيُحفظ السياق عبر الأدوار المتعددة دون أن يضطر العميل إلى إدارته.

      الطلب:

      {
        "model": "hermes-agent",
        "input": "What files are in my project?",
        "instructions": "You are a helpful coding assistant.",
        "store": true
      }

      الاستجابة:

      {
        "id": "resp_abc123",
        "object": "response",
        "status": "completed",
        "model": "hermes-agent",
        "output": [
          {"type": "function_call", "status": "completed", "name": "terminal", "arguments": "{\"command\": \"ls\"}", "call_id": "call_1"},
          {"type": "function_call_output", "status": "completed", "call_id": "call_1", "output": "README.md src/ tests/"},
          {"type": "message", "role": "assistant", "content": [{"type": "output_text", "text": "Your project has..."}]}
        ],
        "usage": {"input_tokens": 50, "output_tokens": 200, "total_tokens": 250}
      }

      استدعاءات الأدوات الموجودة في المصفوفة output نفّذها وكيل Hermes مسبقًا على جانب الخادم — وتُعاد مع "status": "completed" لعرض واجهة أدوات منظّمة، ولا تُقدَّم أبدًا كاستدعاءات معلّقة ينفّذها العميل.

      إدخال الصور المضمّنة: يمكن أن يحتوي input[].content على أجزاء input_text و input_image. وتُدعم كلٌّ من عناوين URL البعيدة وعناوين data:image/...:

      {
        "model": "hermes-agent",
        "input": [
          {
            "role": "user",
            "content": [
              {"type": "input_text", "text": "Describe this screenshot."},
              {"type": "input_image", "image_url": "data:image/png;base64,iVBORw0K..."}
            ]
          }
        ]
      }

      أما الملفات المرفوعة (input_file / file_id) وعناوين data: التي لا تمثّل صورًا فتُرجع 400 unsupported_content_type.

      المحادثات متعددة الأدوار باستخدام previous_response_id​

      اربط الاستجابات بسلسلة للحفاظ على السياق الكامل (بما في ذلك استدعاءات الأدوات) عبر الأدوار:

      {
        "input": "Now show me the README",
        "previous_response_id": "resp_abc123"
      }

      يعيد الخادم بناء المحادثة الكاملة من سلسلة الاستجابات المخزّنة — مع الاحتفاظ بجميع استدعاءات الأدوات ونتائجها السابقة. كما تتشارك الطلبات المتسلسلة الجلسة نفسها، لذا تظهر المحادثات متعددة الأدوار كمُدخل واحد في لوحة التحكم وفي سجل الجلسات.

      المحادثات المسمّاة​

      استخدم المعامل conversation بدلًا من تتبّع معرّفات الاستجابات:

      {"input": "Hello", "conversation": "my-project"}
      {"input": "What's in src/?", "conversation": "my-project"}
      {"input": "Run the tests", "conversation": "my-project"}

      يربط الخادم تلقائيًا بأحدث استجابة في تلك المحادثة، على غرار الأمر /title في جلسات gateway.

      GET /v1/responses/{id}​

      يسترجع استجابة مخزّنة سابقًا بواسطة معرّفها.

      DELETE /v1/responses/{id}​

      يحذف استجابة مخزّنة.

      GET /v1/models​

      يسرد الوكيل كنموذج متاح. ويكون اسم النموذج المُعلَن افتراضيًا هو اسم الـ profile (أو hermes-agent للـ profile الافتراضي). تحتاج إليه معظم الواجهات الأمامية لاكتشاف النماذج.

      المسار /v1/models هو عمدًا الواجهة الخفيفة المتوافقة مع OpenAI. فهو لا يسرد كل تركيبات المزوّد/النموذج المصادَق عليها التي يمكن لـ Hermes التوجيه إليها، ولا يُثري النتائج بمعلومات الأسعار أو القدرات.

      GET /api/model/options​

      يمكن للعملاء المُدركين لخصائص Hermes طلب قائمة المزوّدين/النماذج المنتقاة نفسها التي تستخدمها لوحة التحكم و TUI. يستخدم هذا المسار مصادقة bearer المعتادة في خادم API، ويُرجع صفوف المزوّدين، وتلميحات حول قدرات النماذج، وبيانات وصفية للأسعار لا مكان لها في استجابة /v1/models المتوافقة مع OpenAI:

      curl \
        -H "Authorization: Bearer $API_SERVER_KEY" \
        "http://127.0.0.1:8642/api/model/options"

      هذه البيانات هي الأساس نفسه الذي تعتمد عليه صفحة Models في لوحة التحكم واستدعاء RPC المسمّى model.options في TUI. فهي تُرجع المزوّدين المصادَق عليهم، وقوائم النماذج المنتقاة، وأسعار كل نموذج، وتلميحات حول قدرات النماذج.

      الفتح العادي متحفّظ عمدًا مع المزوّدين المخصّصين: إذ لا يفحص Hermes إلا الـ endpoint المخصص المحدَّد حاليًا، حتى لا يعطّل endpoint محفوظ قديم أو غير متصل المنتقي. أما التحديث الصريح فينتقل إلى الفحص الكامل ويُفرغ التخزين المؤقت لنماذج المزوّد:

      curl \
        -H "Authorization: Bearer $API_SERVER_KEY" \
        "http://127.0.0.1:8642/api/model/options?refresh=1"

      استخدم /v1/models عندما يحتاج عميل متوافق مع OpenAI إلى اسم نموذج فقط لإرساله في طلبات chat/responses. واستخدم /api/model/options عندما تحتاج واجهة مصادَق عليها إلى البيانات الوصفية الأغنى الخاصة بمنتقي Hermes.

      GET /v1/capabilities​

      يُرجع وصفًا قابلًا للقراءة آليًا للواجهة المستقرة التي يوفّرها خادم API، وذلك للواجهات الخارجية ومنظِّمات التشغيل (orchestrators) وجسور الإضافات.

      {
        "object": "hermes.api_server.capabilities",
        "platform": "hermes-agent",
        "model": "hermes-agent",
        "auth": {"type": "bearer", "required": true},
        "features": {
          "chat_completions": true,
          "responses_api": true,
          "run_submission": true,
          "run_status": true,
          "run_events_sse": true,
          "run_stop": true
        }
      }

      استخدم هذا الـ endpoint عند دمج لوحات التحكم أو واجهات المتصفح أو مستويات التحكم (control planes)، لكي تكتشف ما إذا كان إصدار Hermes العامل يدعم runs والبث والإلغاء واستمرارية الجلسة، دون الاعتماد على تفاصيل Python الداخلية الخاصة.

      التحكم عبر امتداد المتصفح​

      يمكن لـ Hermes توجيه أدوات المتصفح عبر امتداد متصفح (browser extension) مصادَق عليه يتحكم في جلسة المتصفح المرتبطة بجلسة Hermes الحالية. هذه الميزة معطّلة افتراضيًا؛ اضبط browser.extension_control.enabled على true لتفعيلها:

      browser:
        extension_control:
          enabled: true

      يتطلب مسار API المحلي أيضًا مفتاح bearer الخاص بخادم API. ولا يمكن لوحدة التحكم (controller) التسجيل إلا لجلسة خادم موجودة. ويشتق Hermes هوية الجهة الأساسية (principal) لوحدة التحكم من حالة الخادم المصادَق عليها؛ ويُتجاهل أي principal_id يقدّمه العميل.

      اكتشف العقد الحالي عبر GET /v1/capabilities. يوضّح الكائن browser_extension_control ما إذا كانت الميزة مفعّلة، وإصدار البروتوكول، وأسماء وسائل النقل (transports)، وقائمة القدرات المسموح بها بدقة:

      controller.noop
      browser_back
      browser_click
      browser_navigate
      browser_press
      browser_screenshot
      browser_scroll
      browser_snapshot
      browser_tab_activate
      browser_tabs
      browser_type

      تُستبعد القدرات المطلوبة التي تقع خارج تلك القائمة. ولا تُعدّ CDP الخام، ولا تقييم السكربتات العشوائية، ولا الوصول إلى console، ولا الرفع، ولا استخراج الصور، ولا الرؤية (vision) جزءًا من بروتوكول وحدة التحكم.

      عندما لا تكون للطلب هوية وحدة تحكم مرتبطة به، أو عندما تكون الميزة معطّلة، يحتفظ Hermes بـ backend المتصفح الحالي. أما بمجرد أن يربط gateway هوية وحدة تحكم وعائلة وسيلة نقل بالطلب، يصبح مسار الامتداد هذا هو المرجع الحاسم: فوحدات التحكم المفقودة أو الملتبسة أو غير المتصلة أو غير القادرة تفشل بشكل مغلق (fail closed) بدلًا من الانتقال بصمت إلى متصفح محلي/سحابي مختلف. وبعد اختيار وحدة تحكم بعينها، تكون نتيجتها أو خطؤها هي المرجع الحاسم، ولا يعيد Hermes أبدًا محاولة الإجراء نفسه عبر backend آخر.

      التسجيل عبر API المحلي​

      1. أرسل طلب POST /v1/browser-control/register مصادَقًا عليه يتضمن protocol_version و session_id و controller_id و browser_profile_id و القدرات المطلوبة في capabilities.
      2. يُرجع Hermes تذكرة (ticket) للاستخدام مرة واحدة بمدة صلاحية (TTL) قدرها 30 ثانية، مع نطاق وحدة التحكم بعد تصفيته وربطه بالخادم.
      3. افتح GET /v1/browser-control/ws مع كلا بروتوكولَي WebSocket الفرعيين: hermes-browser-control-v1 و hermes-browser-control-ticket.<ticket>.

      لا تُقبل التذكرة أبدًا في سلسلة الاستعلام (query string). والتذاكر غير المعروفة أو المنتهية أو المُعاد استخدامها أو المشوّهة تفشل قبل ترقية الاتصال إلى WebSocket.

      إطارات وحدة التحكم​

      يرسل Hermes إطارات browser.controller.command تحتوي على command_id، و action، ووسائط arguments غير قابلة للتعديل، ومعرّفات المتصفح/وحدة التحكم، و tool_call_id الذي نشأ منه الطلب. وتردّ وحدة التحكم بـ browser.controller.result مع command_id نفسه، وقيمة منطقية دقيقة ok، وإما result أو error. ويؤدي الإلغاء وانتهاء المهلة إلى إصدار browser.controller.cancel؛ وتُتجاهل النتائج المتأخرة.

      يؤدي الانقطاع غير المتوقع للـ socket إلى وسم وحدة التحكم بأنها غير متصلة، مع الاحتفاظ بالعمل الجاري بالفعل حتى الموعد النهائي الأصلي لكل أمر. وإعادة الاتصال بنفس الجهة الأساسية والـ profile والجلسة ومعرّف وحدة التحكم وprofile المتصفح وهوية وسيلة النقل تُحدّث وسيلة النقل دون قبول عمل جديد قبل تنفيذ أي عمليات إلغاء مؤجلة. وقد تتغير القدرات المتفاوض عليها عند إعادة الاتصال تلك؛ فهي ليست من حقول الهوية. أما اختلاف معرّف وحدة التحكم أو profile المتصفح ضمن مسار الجلسة المصادَق عليه نفسه فيُعدّ استبدالًا نهائيًا: إذ يُلغى العمل المعلّق القديم قبل أن تصبح الوحدة البديلة قابلة للتوجيه. أرسل browser.controller.detach عبر وسيلة النقل المصادَق عليها لوحدة التحكم لإجراء فصل نهائي مقصود — وهذا يلغي العمل المعلّق فورًا. أما مجرد إغلاق الـ socket فيُعامل كانقطاع قابل للاسترداد.

      توفّر وسيلة النقل المصادَق عليها في لوحة التحكم دلالات التسجيل والنتائج ونبضات الحياة (heartbeat) والقدرات والملكية نفسها عبر قناة Gateway RPC/الأحداث الخاصة بها. وفي كلتا وسيلتي النقل، يتطلب الاختيار تطابقًا دقيقًا واحدًا لا لبس فيه في الجهة الأساسية والـ profile والجلسة ووحدة التحكم وprofile المتصفح وعائلة وسيلة النقل والقدرة. وبمجرد الاختيار، يكون فشل وحدة التحكم هو المرجع الحاسم ولا تُعاد محاولته أبدًا عبر backend متصفح مختلف.

      اختيار النموذج لكل طلب​

      يمكن للعملاء المصادَق عليهم تجاوز اختيار النموذج الافتراضي في Hermes لكل طلب على حدة بإرسال:

      • model — معرّف النموذج المستهدف لهذا الدور
      • provider — المعرّف المختصر (slug) لمزوّد Hermes لتحديد بيانات الاعتماد/بيئة التشغيل لهذا الدور
      • model_options — عناصر تحكم الاستدلال (reasoning) / فئة الخدمة (service tier) الخاصة بهذا الطلب فقط

      تُقبل حقول الطلب نفسها على:

      • POST /v1/chat/completions
      • POST /v1/responses
      • POST /v1/runs
      • POST /api/sessions/{session_id}/chat
      • POST /api/sessions/{session_id}/chat/stream

      ترتيب الأولوية حتمي:

      1. تجاوز /model على مستوى الجلسة، إن كان للجلسة تجاوز بالفعل
      2. ربط ثابت في gateway.platforms.api_server.model_routes يُختار عندما تكون قيمة model في الطلب اسمًا مستعارًا لمسار مُعدّ
      3. قيمتا model / provider المباشرتان في الطلب عندما لا يتطابق أي اسم مستعار لمسار
      4. الإعدادات العامة لـ gateway / القيم الافتراضية من البيئة

      يظل model_options خاصًا بالطلب بغض النظر عن النموذج/المزوّد الذي يُعتمد في النهاية. وإذا أرسل طلبٌ provider يتعارض مع اسم مستعار مُعدّ في model_routes، يرفض Hermes الطلب مع 400 بدلًا من خلط بيانات اعتماد المسار بصمت مع مزوّد آخر.

      قيم model المجرّدة على endpoints المتوافقة مع OpenAI تتطلب تفعيلًا صريحًا. فعملاء OpenAI العامّون كثيرًا ما يثبّتون أسماء النماذج في الكود (gpt-4o، ...)، وتعتمد عمليات النشر القائمة على عودة هذه القيم إلى النموذج الافتراضي في gateway. لذلك، على POST /v1/chat/completions و POST /v1/responses، تُتجاهل قيمة model المُرسلة دون أي provider ما لم تفعّل:

      gateway:
        platforms:
          api_server:
            direct_model_requests: true

      أما الطلبات التي تتضمن provider صريحًا — وكذلك endpoints الأصلية في Hermes مثل /v1/runs و endpoints محادثة الجلسات — فتلتزم دائمًا بالنموذج المطلوب بغض النظر عن هذا الخيار.

      مثال:

      {
        "model": "MiniMax-M3",
        "provider": "minimax",
        "model_options": {
          "reasoning_effort": "high",
          "service_tier": "priority"
        },
        "messages": [
          {"role": "user", "content": "Summarize the repo status."}
        ]
      }

      GET /health​

      فحص السلامة (health check). يُرجع {"status": "ok"}. ومتاح أيضًا على GET /v1/health لعملاء OpenAI المتوافقين الذين يتوقعون البادئة /v1/.

      GET /health/detailed​

      فحص جاهزية مصادَق عليه لأنظمة المراقبة ومستويات التحكم. يعرض حالة موجزة لإعدادات الـ profile النشط، وقاعدة بيانات الحالة، والنموذج المُعدّ، ومساحة القرص، وحالة gateway/المنصات، وعمليات API الجارية، وعمليات إكمال العمليات المعلّقة، والتفويضات النشطة. وتكشف الاستجابة عن الحالة والأعداد فقط، لا عن قيم الإعدادات أو بيانات الاعتماد أو المسارات أو الأوامر أو حمولات قوائم الانتظار أو الأخطاء الخام.

      يبقى المسار العام /health فحصًا خفيفًا لبقاء الخدمة حيّة (liveness) ولا يُجري فحوص الجاهزية. ونتيجة الجاهزية المتدهورة لا تزال تستخدم HTTP 200؛ لذا افحص الحقلين status و readiness.checks في المستوى الأعلى.

      Runs API (بديل ملائم للبث)​

      إلى جانب /v1/chat/completions و /v1/responses، يوفّر الخادم واجهة runs API للجلسات الطويلة التي يريد فيها العميل الاشتراك في أحداث التقدّم بدلًا من إدارة البث بنفسه.

      POST /v1/runs​

      ينشئ تشغيلًا (run) جديدًا للوكيل. ويُرجع run_id يمكن استخدامه للاشتراك في أحداث التقدّم.

      {
        "run_id": "run_abc123",
        "status": "started"
      }

      تقبل عمليات التشغيل سلسلة input بسيطة، ويمكن اختياريًا إرسال session_id أو instructions أو conversation_history أو previous_response_id. وعند تقديم session_id، يُظهره Hermes في حالة التشغيل لتتمكن الواجهات الخارجية من ربط عمليات التشغيل بمعرّفات المحادثات الخاصة بها.

      لجعل عملية الإنشاء آمنة لإعادة المحاولة، أرسل الترويسة Idempotency-Key (من 1 إلى 255 حرف ASCII مرئي). يحجز Hermes المفتاح بشكل دائم قبل بدء العمل. وتُرجع إعادة المحاولة المطابقة run_id الأصلي مع HTTP 202 و Idempotency-Replayed: true، حتى بعد إعادة تشغيل gateway وبعد اكتمال التشغيل أو فشله أو إلغائه. وإعادة استخدام المفتاح نفسه مع حمولة JSON مختلفة تُرجع HTTP 409 مع الرمز idempotency_key_conflict. تُعزل المفاتيح حسب profile/بيانات اعتماد API المصادَق عليها، وتُحفظ لمدة 24 ساعة بعد آخر تحديث لحالتها؛ لذا ينبغي للعملاء استخدام مفاتيح فريدة يصعب تخمينها، ويجب ألا يعيدوا استخدامها في عمليات غير ذات صلة. أما الطلبات التي لا تتضمن الترويسة فتحتفظ بالسلوك القديم وتنشئ دائمًا تشغيلًا جديدًا.

      عندما يحدد session_id جلسة Hermes موجودة، ولا يُقدَّم conversation_history أو previous_response_id صريح، يحمّل التشغيل النص الكامل النشط لتلك الجلسة (transcript). وتعمل عقود إيجار أدوار الجلسة (session turn leases) على ترتيب الكتّاب المتزامنين تسلسليًا، وتحديث النص الكامل بعد انتظار ناتج عن التنافس.

      GET /v1/runs/{run_id}​

      استطلع حالة التشغيل الحالية. وهذا مفيد للوحات التحكم التي تحتاج إلى الحالة دون إبقاء اتصال SSE مفتوحًا، أو للواجهات التي تعيد الاتصال بعد التنقل.

      {
        "object": "hermes.run",
        "run_id": "run_abc123",
        "status": "completed",
        "session_id": "space-session",
        "model": "hermes-agent",
        "output": "Done.",
        "usage": {"input_tokens": 50, "output_tokens": 200, "total_tokens": 250}
      }

      تُحفظ الحالات لفترة وجيزة بعد بلوغ الحالات النهائية (completed أو failed أو cancelled) لأغراض الاستطلاع ومزامنة الواجهة.

      GET /v1/runs/{run_id}/events​

      بث Server-Sent Events لتقدّم استدعاءات الأدوات في التشغيل، وتغيّرات الـ tokens، وأحداث دورة الحياة. صُمّم للوحات التحكم وتطبيقات العميل الكاملة (thick clients) التي تريد الارتباط/الانفصال دون فقدان الحالة.

      عندما يفوّض الوكيل العمل إلى subagents في الخلفية، يحمل البث أيضًا أحداث دورة الحياة subagent.start و subagent.complete، لكي يتمكن العملاء من مراقبة نتائج التفويض — بما في ذلك انتهاء المهلة والإخفاقات — بدلًا من صمت التشغيل بينما يعمل الوكيل الفرعي. وتحمل حمولة subagent.complete حالة الوكيل الفرعي، وملخّصه، ومدته، وأرقام الـ tokens/التكلفة، و child_session_id لأغراض الربط، و delegation_id الخاص بالدفعة التي ينتمي إليها (لتبقى عمليات التوزيع المتزامنة أو المتداخلة قابلة للتمييز)؛ وتخضع الحقول النصية الحرة لإخفاء إلزامي للأسرار قبل مغادرة العملية. أما أحداث الوكيل الفرعي الخاصة بكل أداة (subagent.tool، ونبضات التقدّم) فهي عمدًا لا تُمرَّر — لأنها ضجيج كثيف في الواجهة؛ استخدم ملفات النص الحي لكل وكيل فرعي لمتابعة التفاصيل خطوة بخطوة. هذه الأحداث متاحة ما دام بث الأصل مفتوحًا؛ وأي إكمال منفصل متأخر لا يعيد فتح بث SSE لتشغيل منتهٍ ولا يغيّر حالته النهائية.

      النتائج المنفصلة وسجل الجلسة​

      يتطلب التفويض في الخلفية استئنافًا يقرأ سجل الجلسة على جانب الخادم: أي ترويسة X-Hermes-Session-Id صريحة في Chat Completions، أو طلب /api/sessions/{id}/chat أصلي، أو طلب Runs يستخدم سجل الجلسة. أما طلبات Chat Completions بلا ترويسة، وسلاسل Responses، وطلبات Runs التي تتضمن previous_response_id أو سجلًا يقدّمه المستدعي، فتنفّذ التفويض بشكل متزامن بدلًا من ذلك، وتُرجع النتيجة في الدور الأصلي. ومجرد اشتقاق معرّف جلسة من محتوى الطلب لا يُفعّل التسليم المنفصل.

      في الطلبات القابلة للاستئناف، تُحفظ نتيجة الإكمال مرة واحدة لكل وحدة تفويض. وهي متاحة عبر GET /api/sessions/{id}/messages وفي سجل الجلسة للدور الفعلي التالي من العميل. ولا تُدرج إعادة المحاولة النتيجة نفسها مجددًا؛ أما إشعارات فشل المهام المؤقتة فلها هويات منفصلة. وينتظر التسليم ما دام دور العميل يملك عقد إيجار الجلسة، ويتبع عمليات الاستئناف الناتجة عن الضغط (compression). ويعيد Chat Completions معرّف الجلسة الصريح الذي قدّمته في كلٍّ من استجابات JSON واستجابات البث؛ لذا استمر في إرسال ذلك المعرّف حتى بعد الضغط.

      لا تبدأ نتيجة الإكمال أبدًا دورًا للنموذج دون طلب، ولا تتجاوز تأكيدًا بشريًا معلّقًا. فالعميل هو من يملك الدور التالي. أما العملاء الذين يواصلون استخدام لقطات (snapshots) السجل الخاصة بهم فينبغي أن يستخدموا التفويض المتزامن بدلًا من توقّع دمج صف تسليم من جانب الخادم في تلك اللقطات.

      تنتهي صلاحية مخازن الأحداث غير المستهلكة بعد خمس دقائق، حتى لا يتسبب عميل منفصل في تضخّم الذاكرة إلى ما لا نهاية. ولا ينتهي بذلك إلا حالة وسيلة النقل: فالتشغيل الذي لا يزال قيد التنفيذ يبقى مرئيًا لاستطلاع الحالة، والموافقة، والتحكم في الإيقاف، و احتساب التزامن إلى أن ينتهي عمل المنفّذ الخاص به فعليًا. ويواصل مشترك SSE المتصل استهلاك الأحداث بشكل طبيعي.

      POST /v1/runs/{run_id}/stop​

      يقاطع دور وكيل قيد التشغيل. يُرجع الـ endpoint فورًا {"status": "stopping"} بينما يطلب Hermes من الوكيل النشط التوقف عند نقطة المقاطعة الآمنة التالية. ويبقى التشغيل مُتتبَّعًا بالحالة stopping إلى أن ينتهي العمل المدعوم بالمنفّذ، ثم يستقر على الحالة cancelled؛ فطلب الإيقاف لا يُخفي أبدًا عاملًا (worker) لا يزال قيد التشغيل.

      POST /v1/runs/{run_id}/approval​

      يحسم موافقة معلّقة لتشغيل ينتظر قرارًا بشريًا (مثل استدعاء أداة يخضع لسياسة موافقة). يحمل جسم الطلب قرار الموافقة، ويُستأنف التشغيل بمجرد تسجيل القرار. ويُعلَن عن هذا الـ endpoint في /v1/capabilities على أنه الميزة run_approval، لكي تتمكن الواجهات الخارجية من اكتشاف الدعم قبل عرض طلب موافقة.

      Jobs API (أعمال مجدولة في الخلفية)​

      يوفّر الخادم واجهة CRUD خفيفة للمهام (jobs) لإدارة عمليات تشغيل الوكيل المجدولة / العاملة في الخلفية من عميل بعيد. وجميع الـ endpoints محمية بمصادقة bearer نفسها.

      GET /api/jobs​

      يسرد جميع المهام المجدولة.

      POST /api/jobs​

      ينشئ مهمة مجدولة جديدة. يقبل جسم الطلب البنية نفسها التي يقبلها hermes cron — الـ prompt، والجدول الزمني، والمهارات، وتجاوز المزوّد، ووجهة التسليم.

      GET /api/jobs/{job_id}​

      يجلب تعريف مهمة واحدة وحالة آخر تشغيل لها.

      PATCH /api/jobs/{job_id}​

      يحدّث حقول مهمة موجودة (الـ prompt، والجدول الزمني، وغيرها). وتُدمج التحديثات الجزئية.

      DELETE /api/jobs/{job_id}​

      يزيل مهمة. ويلغي أيضًا أي تشغيل جارٍ لها.

      POST /api/jobs/{job_id}/pause​

      يوقف مهمة مؤقتًا دون حذفها. وتُعلَّق الطوابع الزمنية للتشغيل المجدول التالي حتى الاستئناف.

      POST /api/jobs/{job_id}/resume​

      يستأنف مهمة أُوقفت مؤقتًا في السابق.

      POST /api/jobs/{job_id}/run​

      يُطلق تشغيل المهمة فورًا، خارج جدولها الزمني.

      Sessions API (التحكم في الجلسات عبر REST)​

      يمكن للواجهات الخارجية إدارة جلسات Hermes عبر REST دون الحاجة إلى تشغيل لوحة التحكم. جميع الـ endpoints محمية بـ API_SERVER_KEY وتقع تحت /api/sessions/*.

      الطريقةالمسارالوصف
      GET/api/sessionsيسرد الجلسات (مع ترقيم الصفحات — limit، offset، source، include_children)
      POST/api/sessionsينشئ جلسة فارغة
      GET/api/sessions/{id}يقرأ البيانات الوصفية للجلسة
      PATCH/api/sessions/{id}يحدّث العنوان أو end_reason
      DELETE/api/sessions/{id}يحذف جلسة
      GET/api/sessions/{id}/messagesسجل رسائل الجلسة
      POST/api/sessions/{id}/forkيتفرّع من الجلسة عبر سلسلة النَّسب في SessionDB (بنفس دلالات الأمر /branch في CLI)
      POST/api/sessions/{id}/chatيشغّل دورًا واحدًا متزامنًا للوكيل
      POST/api/sessions/{id}/chat/streamwrapper بتقنية SSE حول دور واحد — يُصدر الأحداث assistant.delta و tool.started و tool.completed و run.completed

      يُعلن /v1/capabilities عن الواجهة الكاملة عبر علامات الميزات session_* ومُدخلات endpoints.session_*، لكي تتمكن الواجهات الخارجية من اكتشاف الدعم والرجوع إلى بديل بأمان. وتُدعم الصور المضمّنة في حمولات chat و chat/stream (عبر مسار يدعم الوسائط المتعددة).

      # fork a session and run one turn
      curl -X POST http://localhost:8642/api/sessions/$ID/fork \
        -H "Authorization: Bearer $API_SERVER_KEY" \
        -d '{"title": "explore alt path"}'

      # stream a turn over SSE
      curl -N -X POST http://localhost:8642/api/sessions/$ID/chat/stream \
        -H "Authorization: Bearer $API_SERVER_KEY" \
        -d '{"input": "what files changed in the last hour?"}'

      اكتشاف المهارات و toolsets​

      يتيح GET /v1/skills و GET /v1/toolsets للعملاء الخارجيين سرد قدرات الوكيل بشكل حتمي عبر REST بدلًا من سؤال النموذج. كلاهما للقراءة فقط ومحميّ بـ API_SERVER_KEY.

      curl http://localhost:8642/v1/skills \
        -H "Authorization: Bearer $API_SERVER_KEY"
      # → [{"name": "github-pr-workflow", "description": "...", "category": "..."}, ...]

      curl http://localhost:8642/v1/toolsets \
        -H "Authorization: Bearer $API_SERVER_KEY"
      # → [{"name": "core", "label": "...", "description": "...", "enabled": true,
      #     "configured": true, "tools": ["read_file", "write_file", ...]}, ...]

      يُرجع /v1/skills البيانات الوصفية نفسها التي يستخدمها Skills Hub داخليًا. ويُرجع /v1/toolsets مجموعات toolsets كما تُحلّ لمنصة api_server، مع قائمة tools الفعلية التي تتوسع إليها كل منها. ويُعلَن عن كليهما تحت endpoints.* في /v1/capabilities.

      تحديد نطاق الذاكرة طويلة المدى (X-Hermes-Session-Key)​

      تحتاج الواجهات الأمامية متعددة المستخدمين مثل Open WebUI إلى معرّف ثابت لكل قناة من أجل الذاكرة طويلة المدى (Honcho وغيرها)، يكون مستقلًا عن X-Hermes-Session-Id المرتبط بنطاق النص الكامل للمحادثة (والذي يتغيّر عند /new). مرّر X-Hermes-Session-Key على /v1/chat/completions أو /v1/responses أو /v1/runs، وسيمرّره Hermes حتى AIAgent(gateway_session_key=...)، حيث يستخدمه مزوّد ذاكرة Honcho لاشتقاق نطاق ثابت.

      POST /v1/chat/completions HTTP/1.1
      Authorization: Bearer ***
      X-Hermes-Session-Id: transcript-alpha
      X-Hermes-Session-Key: agent:main:webui:dm:user-42

      القواعد: الحد الأقصى 256 حرفًا، وتُرفض محارف التحكم (\r، \n، \x00)، وتُعاد القيمة في الاستجابات (JSON و SSE). ويُعلن /v1/capabilities عن الدعم عبر "session_key_header": "X-Hermes-Session-Key". وبدون المفتاح، تُنتج استراتيجية per-session في Honcho نطاقًا مختلفًا لكل session_id — وهو تمامًا السلوك الذي كان عليه Hermes سابقًا.

      التعامل مع System Prompt​

      عندما ترسل واجهة أمامية رسالة system (في Chat Completions) أو حقل instructions (في Responses API)، فإن hermes-agent يضيفها كطبقة فوق الـ system prompt الأساسي الخاص به. يحتفظ وكيلك بجميع أدواته وذاكرته ومهاراته — ويضيف الـ system prompt الخاص بالواجهة الأمامية تعليمات إضافية فقط.

      هذا يعني أنه يمكنك تخصيص السلوك لكل واجهة أمامية دون فقدان أي قدرات:

      • الـ system prompt في Open WebUI: "أنت خبير في Python. أضف دائمًا تلميحات الأنواع (type hints)."
      • يظل لدى الوكيل الطرفية، وأدوات الملفات، والبحث في الويب، والذاكرة، وغيرها.

      المصادقة​

      مصادقة Bearer token عبر الترويسة Authorization:

      Authorization: Bearer ***

      اضبط المفتاح عبر متغير البيئة API_SERVER_KEY. وإذا كنت تحتاج إلى أن يستدعي متصفحٌ Hermes مباشرةً، فاضبط أيضًا API_SERVER_CORS_ORIGINS على قائمة سماح صريحة.

      التوجيه متعدد الـ profiles (/p/<profile>/…)​

      عند تفعيل توجيه gateway متعدد الـ profiles (gateway.multiplex_profiles)، يخدم المستمع المشترك كل profile عبر بادئة URL بالشكل /p/<profile>/ — وترتبط المصادقة بالـ profile الموجَّه إليه:

      • يجب أن تقدّم الطلبات الموجّهة إلى /p/<profile>/v1/... المفتاح الخاص بذلك الـ profile نفسه API_SERVER_KEY (من ~/.hermes/profiles/<profile>/.env). ويُرفض مفتاح المستمع الافتراضي على بادئات الـ profiles المسمّاة.
      • تواصل المسارات بلا بادئة و /p/default/... استخدام مفتاح الـ profile الافتراضي.
      • الـ profile المسمّى الذي ليس له API_SERVER_KEY خاص به يفشل بشكل مغلق — إذ تبقى بادئته غير قابلة للوصول حتى تضبط مفتاحًا له.
      • نطاق عمليات التشغيل خاص بكل profile: فالمسار /v1/runs/{run_id} ومساراته events و stop و steer و approval لا تستجيب إلا للـ profile الذي أنشأ التشغيل (بما في ذلك عمليات التشغيل التي بدأت عبر /api/sessions/{id}/chat/stream)؛ أما معرّف تشغيل يخص profile آخر فيُرجع 404، وليس 403 أبدًا.
      تغيير كاسر للتوافق (يوليو 2026)

      قبل هذا الإصلاح، كان مفتاح الـ profile الافتراضي الصالح مقبولًا على أي بادئة /p/<profile>/. إذا كنت تعتمد على مفتاح واحد مشترك عبر بادئات الـ profiles، فاضبط API_SERVER_KEY مختلفًا في ملف .env لكل profile — إذ أصبحت المفاتيح الافتراضية المُعاد استخدامها على البادئات المسمّاة تُرجع الآن 401.

      الأمان

      يمنح خادم API وصولًا كاملًا إلى مجموعة أدوات hermes-agent، بما في ذلك أوامر الطرفية. والمفتاح API_SERVER_KEY مطلوب في كل عملية نشر، بما في ذلك الربط الافتراضي بعنوان loopback على 127.0.0.1. أبقِ API_SERVER_CORS_ORIGINS ضيق النطاق للتحكم في وصول المتصفحات عندما تسمح صراحةً بالاستدعاء من المتصفح.

      الإعدادات​

      متغيرات البيئة (Environment Variables)​

      المتغيرالقيمة الافتراضيةالوصف
      API_SERVER_ENABLEDfalseيفعّل خادم API
      API_SERVER_PORT8642منفذ خادم HTTP
      API_SERVER_HOST127.0.0.1عنوان الربط (localhost فقط افتراضيًا)
      API_SERVER_KEY(مطلوب)Bearer token للمصادقة
      API_SERVER_CORS_ORIGINS(لا شيء)مصادر المتصفح المسموح بها، مفصولة بفواصل
      API_SERVER_MODEL_NAME(اسم الـ profile)اسم النموذج على /v1/models. القيمة الافتراضية هي اسم الـ profile، أو hermes-agent للـ profile الافتراضي.

      config.yaml​

      يمكن وضع الإعدادات نفسها في ~/.hermes/config.yaml ضمن قسم متداخل gateway.api_server::

      gateway:
        api_server:
          enabled: true
          port: 8642
          host: 127.0.0.1
          key: your-secret-key
          cors_origins: http://localhost:3000
          model_name: my-hermes
          max_concurrent_runs: 10   # concurrent-run cap; 0 disables the limit

      تُنقل الخيارات port و key و host و cors_origins و model_name تلقائيًا إلى إعدادات extra الخاصة بالمنصة، لذا تتصرف تمامًا مثل نظيراتها من متغيرات البيئة API_SERVER_*. ولمتغيرات البيئة الأولوية على قيم config.yaml. كما تُقبل هذه الكتلة أيضًا تحت gateway.platforms.api_server: أو ضمن قسم platforms.api_server: في المستوى الأعلى.

      حدّ عمليات التشغيل المتزامنة​

      يحدّ خادم API عدد عمليات تشغيل الوكيل التي يمكن تنفيذها في الوقت نفسه عبر endpoints المتوافقة مع OpenAI و endpoints الخاصة بـ Runs. يُقرأ الحد من gateway.api_server.max_concurrent_runs (القيمة الافتراضية 10؛ والقيمة 0 تعطّل الحد، والقيم السالبة تُقيَّد إلى 0). وعند بلوغ الحد، تُرفض الطلبات الجديدة التي تبدأ عمليات تشغيل مع HTTP 429 Too many concurrent runs (max N) — وينبغي للعملاء التراجع ثم إعادة المحاولة.

      ترويسات الأمان​

      تتضمن جميع الاستجابات ترويسات أمان:

      • X-Content-Type-Options: nosniff — تمنع تخمين نوع MIME (MIME sniffing)
      • Referrer-Policy: no-referrer — تمنع تسريب المُحيل (referrer)

      CORS​

      خادم API لا يفعّل CORS للمتصفحات افتراضيًا.

      للوصول المباشر من المتصفح، اضبط قائمة سماح صريحة:

      API_SERVER_CORS_ORIGINS=http://localhost:3000,http://127.0.0.1:3000

      عند تفعيل CORS:

      • استجابات Preflight تتضمن Access-Control-Max-Age: 600 (تخزين مؤقت لمدة 10 دقائق)
      • استجابات البث عبر SSE تتضمن ترويسات CORS لكي تعمل عملاء EventSource في المتصفح بشكل صحيح
      • X-Hermes-Session-Id ترويسة طلب مسموح بها، لذا يمكن للمتصفحات على مصدر مُدرج في قائمة السماح طلب استئناف الجلسة.
      • Idempotency-Key ترويسة طلب مسموح بها — ويمكن للعملاء إرسالها لمنع التكرار (تُخزَّن الاستجابات مؤقتًا حسب المفتاح لمدة 5 دقائق)

      معظم الواجهات الأمامية الموثّقة مثل Open WebUI تتصل من خادم إلى خادم ولا تحتاج إلى CORS إطلاقًا.

      إعداد متعدد المستخدمين باستخدام Profiles​

      لمنح عدة مستخدمين نسخة Hermes معزولة خاصة بكل منهم (إعدادات وذاكرة ومهارات منفصلة)، استخدم الـ profiles:

      # Create a profile per user
      hermes profile create alice
      hermes profile create bob

      # Configure each profile's API server on a different port. API_SERVER_* are env
      # vars (not config.yaml keys), so write them to each profile's .env:
      cat >> ~/.hermes/profiles/alice/.env <<EOF
      API_SERVER_ENABLED=true
      API_SERVER_PORT=8643
      API_SERVER_KEY=alice-secret
      EOF

      cat >> ~/.hermes/profiles/bob/.env <<EOF
      API_SERVER_ENABLED=true
      API_SERVER_PORT=8644
      API_SERVER_KEY=bob-secret
      EOF

      # Start each profile's gateway
      hermes -p alice gateway &
      hermes -p bob gateway &

      يُعلن خادم API الخاص بكل profile تلقائيًا عن اسم الـ profile بوصفه معرّف النموذج:

      • http://localhost:8643/v1/models → النموذج alice
      • http://localhost:8644/v1/models → النموذج bob

      في Open WebUI، أضف كلًّا منها كاتصال منفصل. ستعرض القائمة المنسدلة للنماذج alice و bob كنموذجين مختلفين، يعتمد كلٌّ منهما على نسخة Hermes معزولة تمامًا. راجع دليل Open WebUI لمزيد من التفاصيل.

      القيود​

      • تخزين الاستجابات — تُحفظ الاستجابات المخزّنة (الخاصة بـ previous_response_id) في SQLite وتبقى بعد إعادة تشغيل gateway. الحد الأقصى 100 استجابة مخزّنة (مع الإزالة وفق LRU).
      • لا يوجد رفع للملفات — الصور المضمّنة مدعومة على كلٍّ من /v1/chat/completions و /v1/responses، لكن الملفات المرفوعة (file، input_file، file_id) ومدخلات المستندات غير المصوّرة غير مدعومة عبر API.
      • عملاء OpenAI البسيطة ما زالت ترى اسمًا مستعارًا — يُعلن /v1/models عن الاسم المستعار الثابت لـ Hermes (hermes-agent أو اسم الـ profile النشط). أما العملاء الأغنى بالميزات فيمكنها إرسال تجاوزات صريحة لـ provider / model_options في الطلبات.

      Proxy Mode​

      يعمل خادم API أيضًا كـ backend لوضع gateway proxy mode. فعندما تُضبط نسخة Hermes gateway أخرى بـ GATEWAY_PROXY_URL يشير إلى خادم API هذا، فإنها تُعيد توجيه جميع الرسائل إليه بدلًا من تشغيل وكيلها الخاص. وهذا يتيح عمليات نشر مقسّمة — مثل حاوية Docker تتولى Matrix E2EE وتمرّر الرسائل إلى وكيل يعمل على الجهاز المضيف.

      راجع Proxy Mode في Matrix للاطلاع على دليل الإعداد الكامل.

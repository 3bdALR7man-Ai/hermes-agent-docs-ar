      خادم API

      يوفّر خادم API وكيل hermes-agent على شكل HTTP endpoint متوافق مع OpenAI. ويمكن لأي واجهة أمامية (frontend) تتعامل بصيغة OpenAI — مثل Open WebUI و LobeChat و LibreChat و NextChat و ChatBox ومئات غيرها — الاتصال بـ hermes-agent واستخدامه كـ backend.

      يعالج وكيلك الطلبات بمجموعة أدواته الكاملة (الطرفية، وعمليات الملفات، والبحث في الويب، والذاكرة، والمهارات) ثم يُرجع الاستجابة النهائية. وعند البث (streaming)، تظهر مؤشرات تقدّم الأدوات ضمن الاستجابة مباشرةً لتتمكن الواجهات الأمامية من عرض ما يفعله الوكيل.

      backend واحد يغطي النماذج والأدوات

      يحتاج Hermes نفسه إلى مزوّد مُعدّ وإلى backends للأدوات حتى يكون خادم API مفيدًا. ويتكفّل اشتراك Nous Portal بالأمرين معًا — أكثر من 300 نموذج إضافةً إلى الويب/الصور/TTS/المتصفح عبر Tool Gateway. نفّذ hermes setup --portal مرة واحدة قبل تشغيل خادم API، وستحصل الواجهات الأمامية مثل Open WebUI أو LobeChat على backend مجهّز بالأدوات بالكامل.

      البدء السريع​

      1. فعّل خادم API​

      أضف ما يلي إلى ~/.hermes/.env:

      API_SERVER_ENABLED=true
      API_SERVER_KEY=change-me-local-dev
      # Optional: only if a browser must call Hermes directly
      # API_SERVER_CORS_ORIGINS=http://localhost:3000

      2. شغّل gateway​

      hermes gateway

      سترى ما يلي:

      [API Server] API server listening on http://127.0.0.1:8642

      3. اربط واجهة أمامية​

      وجّه أي عميل متوافق مع OpenAI إلى http://localhost:8642/v1:

      # Test with curl
      curl http://localhost:8642/v1/chat/completions \
        -H "Authorization: Bearer change-me-local-dev" \
        -H "Content-Type: application/json" \
        -d '{"model": "hermes-agent", "messages": [{"role": "user", "content": "Hello!"}]}'

      أو اربط Open WebUI أو LobeChat أو أي واجهة أمامية أخرى — راجع دليل التكامل مع Open WebUI للاطلاع على التعليمات خطوة بخطوة.

      دلالات المحادثة والنتيجة النهائية​

      تستخدم طلبات API طابور القبول الدائم (durable admission queue) الخاص بالـ gateway. يبقى محتوى الصور المنظَّم منظَّمًا طوال التنفيذ؛ ولا يُفسَّر بوصفه slash command للـ gateway.

      • يحتفظ /v1/runs و /v1/responses بالمحادثة التي تعلنها الترويسة X-Hermes-Session-Key. وتكون الأسبقية لجلسة صريحة أو سلسلة استجابات صريحة، ولا تنقل إلى ترويسة مختلفة هوية محادثتها.
      • في /v1/runs، يكون conversation_history غير الفارغ هو المرجع الحاسم، حتى مع وجود session_id صريح. وإلا فإن استكمال الجلسة يحمّل السجل عند تنفيذ الدور، بعد انتهاء الأعمال المصطفّة قبله.
      • يتفق استطلاع Runs و SSE على الحالتين cancelled و failed. ويستخدم Responses الحالة النهائية نفسها والحدثين response.cancelled / response.failed، بما في ذلك عند وجود نص تشخيصي. ويُبلغ Chat Completions عن finish_reason: "cancelled" للأدوار المقاطَعة وعن "error" للإخفاقات، لا عن "stop" الناجح.
      • الدور (turn) الذي ينفد ميزانية تكراراته (agent.max_turns) يظل يجيب بخلاصة الوكيل لما وجده. يُسلّم Chat Completions هذا النص مع finish_reason: "length" و hermes.error_code: "iteration_budget_exhausted"؛ أما Responses فيُبلغ عن status: "incomplete". تعامل مع المحتوى بوصفه إجابة صالحة للاستخدام عن مهمة توقفت قبل اكتمالها، لا بوصفه إلغاءً.
      • تتضمن ردود محادثة الجلسة الحقل status؛ وتبلّغ تدفقاتها عن أحداث تشغيل نهائية مطابقة. وإطار إنهاء رد المساعد ليس بحد ذاته دليلًا على نجاح التنفيذ.

      مفاتيح Idempotency​

      يقبل POST /v1/chat/completions و POST /v1/responses الترويسة Idempotency-Key. وما يضمنه المفتاح يعتمد على وضع التنفيذ:

      • الوضع المرجعي (Canonical mode) (يشغّل الـ gateway جهة صلاحية للجلسات session authority): المفتاح هوية قبول دائمة. يُقبل الطلب الأول الحامل له ويعمل مرة واحدة، ويظل المفتاح ملكًا لعملية القبول تلك من حينها. تنحصر المفاتيح في نطاق API profile وبيانات الاعتماد المصادَق عليهما، ولذلك فإن profile آخر أو API_SERVER_KEY مُدوَّر يعيد استخدام مفتاح العميل نفسه يُعدّ طلبًا جديدًا. ويصف بقية هذا القسم هذا الوضع.
      • الوضع القديم (Legacy mode) (بلا session authority): تُزال تكرارات الطلبات غير المتدفقة عبر cache في الذاكرة مدته 5 دقائق. أما الطلبات المتدفقة (streaming) فلا تُزال تكراراتها.

      لمفاتيح /v1/runs سجلّها الخاص (ledger) واحتفاظ مدته 24 ساعة (انظر Runs API أدناه).

      إعادات المحاولة المطابقة والتعارضات. تكون إعادة المحاولة مطابقة عندما تكرر المفتاح نفسه مع حقول الهوية نفسها والهدف المعلَن نفسه. أما تغيير أحد حقول الهوية، أو إرسال المفتاح إلى جلسة أخرى، فهو تعارض: يُرفض بالرمز admission_conflict ولا يُنفَّذ شيء. وتختلف طريقة وصول الرفض بحسب الطلب:

      • Responses (JSON أو متدفق) وChat Completions غير المتدفق: HTTP 409 مع رمز الخطأ admission_conflict.
      • Chat Completions المتدفق: يكون التدفق قد فُتح بالفعل بـ HTTP 200، لذا يأتي الرفض في آخر chunk فيه، مع finish_reason: "error" و error.message "admission_conflict"، يليه data: [DONE]. افحص ذلك الـ chunk لا رمز الحالة.

      تختلف حقول الهوية باختلاف الـ endpoint:

      • Responses: input و instructions و previous_response_id و conversation و conversation_history و model و provider و model_options و tools، إضافة إلى truncation عند إرساله.
      • Chat Completions: آخر رسالة للمستخدم، والرسائل السابقة (ما لم تُرسَل X-Hermes-Session-Id، وفي هذه الحالة يأتي السجل من الجلسة)، و system prompt، وإعدادات الدور مثل النموذج والمزوّد المطلوبين و model_options. أما tools و tool_choice فليسا جزءًا منها: إعادة المحاولة التي تغيّر هذين فقط تعيد الرد الأصلي بدلًا من أن تُحدث تعارضًا.

      وضع التسليم ليس جزءًا من الهوية في أي من الـ endpoint-ين: يجوز لإعادة المحاولة أن تبدّل بين JSON و stream: true وتحصل على الجواب نفسه بالصيغة المطلوبة.

      الإعادة (replay) ومنع التكرار أمران منفصلان. تعيد إعادة المحاولة المطابقة الجواب الأصلي فقط ما دام الخادم يحتفظ بهوية الطلب الخاصة بالمفتاح مع سجل إعادته أو مع قبول نهائي يمكن إعادة بناء الجواب منه. وحين لا تعود الإعادة ممكنة، يظل المفتاح لا يعمل مجددًا ما بقي دليل قبوله: تُرفض إعادة المحاولة بوصفها تعارضًا ولا يُنفَّذ شيء. وقد تتلقى إعادة محاولة Responses بدلًا من ذلك HTTP 409 unknown_execution: يحتفظ المخزن بمطالبة المفتاح (مثلًا مطالبة سجّلها إصدار أقدم) لكن دون جواب، فلا يُعرف هل نُفّذت المحاولة الأولى. وهذا ليس إذنًا بإعادة إرسال العمل بمفتاح جديد؛ فقد تكون المحاولة الأولى نُفّذت بالفعل.

      بعد حذف جلسة (DELETE /api/sessions/{id}) تُحفظ عمليات القبول الخاصة بها بوصفها شواهد (tombstones). وبعد سبعة أيام من الحذف تصبح مؤهلة للتقليم (pruning)؛ ولا تُزال إلا عند تشغيل تمريرة تقليم، وإلى ذلك الحين يتصرف المفتاح كما يلي.

      • Chat Completions: تعيد إعادة المحاولة المطابقة الجواب الأصلي دون إعادة إنشاء الجلسة، ويُرفض المفتاح المرسل إلى أي جلسة أخرى بوصفه تعارضًا. وبعد تقليم الشواهد يمكن للمفتاح أن يسمّي عملًا جديدًا على هدف جديد صالح.
      • Responses: تحتاج الإعادة أيضًا إلى أن يحتفظ مخزن الاستجابات بهوية المفتاح، ولذلك قد تنتهي قبل مرور الأيام السبعة: تُحفظ الهويات المستقرة بعدد محدود، ويزيل DELETE /v1/responses/{id} إحداها فورًا. المفتاح الذي زالت هويته يُجاب بـ 409 admission_conflict، حتى على جلسة حية. وحين تزول هويته وتُقلَّم شواهده، يمكن للمفتاح أن يسمّي عملًا جديدًا.
      ملاحظة

      يحتفظ مخزن الاستجابات افتراضيًا بآخر 1,000 هوية استقرّت لكل profile (10 لكل خانة استجابة مخزّنة). ولا تُحتسب الهويات المعلّقة أو الجارية ولا تُسقَط أبدًا، ويؤدي حذف استجابة إلى إزالة هويتها مبكرًا. وهذا افتراضي حالي وليس ضمانًا للإعادة.

      لا يُعاد تعيين X-Hermes-Session-Id الصريح أبدًا. يظل معرّف الجلسة المحذوفة محجوبًا حتى بعد التقليم. وإعادة المحاولة المطابقة ذات المفتاح التي لا تزال هويتها محفوظة هناك تُعاد، أما المتغيّرة فتُرفض بوصفها تعارضًا. والطلب الذي لا هوية محفوظة له هناك، مثل طلب جديد أو إعادة محاولة قُلّمت هويتها، يُرفض بالرمز not_found.

      يشتق طلب Chat Completions بلا X-Hermes-Session-Id جلسته من system prompt ورسالة المستخدم الأولى. ولا يُعاد استخدام معرّف جلسة محذوفة أبدًا، لذلك تحصل محادثة جديدة تبدأ مثل محادثة محذوفة على جلسة جديدة، وتستقر أدوارها اللاحقة على تلك الجلسة نفسها، بما في ذلك بعد إعادة التشغيل. أما إعادة المحاولة المطابقة ذات المفتاح لدور من المحادثة المحذوفة فلا تُنقل؛ وتُعاد كما هو موصوف أعلاه.

      Endpoints​

      POST /v1/chat/completions​

      صيغة OpenAI Chat Completions القياسية. عديمة الحالة (stateless) — إذ تُضمَّن المحادثة الكاملة في كل طلب عبر المصفوفة messages.

      الطلب:

      {
        "model": "hermes-agent",
        "messages": [
          {"role": "system", "content": "You are a Python expert."},
          {"role": "user", "content": "Write a fibonacci function"}
        ],
        "stream": false
      }

      الاستجابة:

      {
        "id": "chatcmpl-abc123",
        "object": "chat.completion",
        "created": 1710000000,
        "model": "hermes-agent",
        "choices": [{
          "index": 0,
          "message": {"role": "assistant", "content": "Here's a fibonacci function..."},
          "finish_reason": "stop"
        }],
        "usage": {"prompt_tokens": 50, "completion_tokens": 200, "total_tokens": 250}
      }

      إدخال الصور المضمّنة: يمكن لرسائل المستخدم إرسال content كمصفوفة من أجزاء text و image_url. وتُدعم كلٌّ من عناوين http(s) البعيدة وعناوين data:image/...:

      {
        "model": "hermes-agent",
        "messages": [
          {
            "role": "user",
            "content": [
              {"type": "text", "text": "What is in this image?"},
              {"type": "image_url", "image_url": {"url": "https://example.com/cat.png", "detail": "high"}}
            ]
          }
        ]
      }

      أما الملفات المرفوعة (file / input_file / file_id) وعناوين data: التي لا تمثّل صورًا فتُرجع 400 unsupported_content_type.

      البث (Streaming) ("stream": true): يُرجع Server-Sent Events (SSE) تتضمن أجزاء الاستجابة token تلو الآخر. في Chat Completions، يستخدم البث أحداث chat.completion.chunk القياسية إضافةً إلى الحدث المخصص hermes.tool.progress من Hermes لإظهار بدء تشغيل الأدوات في الواجهة. وفي Responses، يستخدم البث أنواع أحداث OpenAI Responses مثل response.created و response.output_text.delta و response.output_item.added و response.output_item.done و response.completed.

      تصدر جميع تدفقات SSE (Chat Completions و Responses و /api/sessions/{id}/chat/stream و /v1/runs/{id}/events) سطر تعليق : keepalive كلما لم يُرسل حدث لمدة 10 ثوانٍ، كي لا تؤدي استدعاءات الأدوات الطويلة إلى انتهاء مهلة خمول العميل. تتجاهل عملاء SSE القياسية أسطر التعليقات؛ ويجب على المحلّلات المخصّصة تخطّي الأسطر التي تبدأ بـ :.

      تقدّم الأدوات أثناء البث:

      • Chat Completions: يُصدر Hermes الحدث event: hermes.tool.progress لإظهار بدء الأدوات دون تلويث نص المساعد المحفوظ. يمكن لعملاء OpenAI الصارمة التي لا تقبل أحداث SSE المسمّاة تعطيل هذه الأُطر باستخدام gateway.platforms.api_server.tool_progress_events: false (القيمة الافتراضية true)؛ ولا تتأثر أجزاء المحتوى. ينطبق التعطيل على Chat Completions فقط — يُصدر /v1/runs/{id}/events أحداث الأدوات دائمًا، وهو ما تصفه ميزة tool_progress_events في /v1/capabilities.
      • Responses: يُصدر Hermes عناصر مُخرَجات function_call و function_call_output الأصلية للمواصفة أثناء تدفق SSE، ليتمكن العملاء من عرض واجهة أدوات منظّمة في الوقت الفعلي.

      استدلال النموذج (لا يُصدر إلا عندما ينتج النموذج استدلالًا فعليًا وتسمح به إعدادات reasoning المحددة؛ وخيار تعطيله من المدخلات هو model_options.reasoning.enabled: false):

      • Chat Completions: تصل تغيّرات الاستدلال كأجزاء choices[0].delta.reasoning_content (الحقل بأسلوب DeepSeek الذي يعرضه Open WebUI و opencode و Vercel AI SDK ككتلة تفكير)؛ ويبقى نص الإجابة في delta.content.
      • Responses: كل دفعة تفكير عنصر مخرج reasoning أصلي للمواصفة — response.output_item.added (item.type: "reasoning")، response.reasoning_summary_part.added، response.reasoning_summary_text.delta … response.reasoning_summary_text.done، response.reasoning_summary_part.done، response.output_item.done — يُغلق قبل فتح الرسالة التالية أو عنصر function_call، ويُكرر في مخرج response.completed بصيغة {"id": "rs_…", "type": "reasoning", "status": "completed", "summary": [{"type": "summary_text", "text": "…"}]}. يظل sequence_number متزايدًا رتيبًا عبر أحداث الاستدلال والنص والأدوات.
      • دون بث: /v1/chat/completions يُرجع استدلال الدور في choices[0].message.reasoning_content؛ و /v1/responses يُرجع عناصر مخرج reasoning نفسها قبل الرسالة (وقبل عناصر function_call الخاصة بتلك الخطوة)، وكذلك عند إعادة عرض GET /v1/responses/{id}.
      • يمكن إعادة إرسال قائمة output لاستجابة سابقة بوصفها input التالية (ما تفعله عملاء Responses SDK): تُتجاهل عناصر reasoning عند الإدخال بدلًا من تحليلها كأدوار مستخدم فارغة.
      • يُعلن الدعم بوصفه features.reasoning_streaming: true في GET /v1/capabilities.

      POST /v1/responses​

      صيغة OpenAI Responses API. تدعم الاحتفاظ بحالة المحادثة على جانب الخادم عبر previous_response_id — إذ يخزّن الخادم سجل المحادثة الكامل (بما في ذلك استدعاءات الأدوات ونتائجها)، فيُحفظ السياق عبر الأدوار المتعددة دون أن يضطر العميل إلى إدارته.

      الطلب:

      {
        "model": "hermes-agent",
        "input": "What files are in my project?",
        "instructions": "You are a helpful coding assistant.",
        "store": true
      }

      الاستجابة:

      {
        "id": "resp_abc123",
        "object": "response",
        "status": "completed",
        "model": "hermes-agent",
        "output": [
          {"type": "function_call", "status": "completed", "name": "terminal", "arguments": "{\"command\": \"ls\"}", "call_id": "call_1"},
          {"type": "function_call_output", "status": "completed", "call_id": "call_1", "output": "README.md src/ tests/"},
          {"type": "message", "role": "assistant", "content": [{"type": "output_text", "text": "Your project has..."}]}
        ],
        "usage": {"input_tokens": 50, "output_tokens": 200, "total_tokens": 250}
      }

      استدعاءات الأدوات الموجودة في المصفوفة output نفّذها وكيل Hermes مسبقًا على جانب الخادم — وتُعاد مع "status": "completed" لعرض واجهة أدوات منظّمة، ولا تُقدَّم أبدًا كاستدعاءات معلّقة ينفّذها العميل.

      مع "stream": true، يصل تعليق المساعد في منتصف الدور (تمهيدات التقدم openai-codex الخاصة بـ backend phase="commentary"، أو النص الذي يكتبه نموذج مع استدعاءات أدواته) كعنصر مخرج message مكتمل مستقل يحمل "phase": "commentary" (response.output_item.added + response.output_item.done، ومدرج أيضًا في response.completed). لا يُدمج أبدًا في عنصر الإجابة النهائية، فيستطيع العملاء عرضه كتقدم مباشر وتخطّيه عند تجميع الرد. لا يصل الاستدلال الخاص إلى هذا العنصر مطلقًا. يؤدي display.interim_assistant_messages: false (أو تجاوز display.platforms.api_server) إلى كتمه على جميع واجهات خادم API.

      إدخال الصور المضمّنة: input[].content يمكن أن يحتوي على أجزاء input_text و input_image. وتُدعم كلٌّ من عناوين URL البعيدة وعناوين data:image/...:

      {
        "model": "hermes-agent",
        "input": [
          {
            "role": "user",
            "content": [
              {"type": "input_text", "text": "Describe this screenshot."},
              {"type": "input_image", "image_url": "data:image/png;base64,iVBORw0K..."}
            ]
          }
        ]
      }

      أما الملفات المرفوعة (input_file / file_id) وعناوين data: التي لا تمثّل صورًا فتُرجع 400 unsupported_content_type.

      المحادثات متعددة الأدوار باستخدام previous_response_id​

      اربط الاستجابات بسلسلة للحفاظ على السياق الكامل (بما في ذلك استدعاءات الأدوات) عبر الأدوار:

      {
        "input": "Now show me the README",
        "previous_response_id": "resp_abc123"
      }

      يعيد الخادم بناء المحادثة الكاملة من سلسلة الاستجابات المخزّنة — وتُحفظ جميع استدعاءات الأدوات ونتائجها السابقة. وتشترك الطلبات المتسلسلة أيضًا في الجلسة نفسها، فتظهر المحادثات متعددة الأدوار كمدخل واحد في لوحة التحكم وسجل الجلسات.

      لا تسرد قائمة output لكل استجابة إلا عناصر ذلك الدور (مدخلات function_call / function_call_output و message النهائي)، ولا تسرد استدعاءات أدوات الأدوار السابقة أبدًا — بما في ذلك عندما يصلح Hermes السجل المقدَّم قبل الاستدعاء (بدمج عناصر assistant أو user المتتالية وإسقاط نتائج الأدوات اليتيمة)، أو يضغطه وسط السلسلة. تكون السلسلة المخزّنة هي نص المحادثة المُصلح، فلا ينمو السجل بنسخة ثانية في كل دور.

      المحادثات المسمّاة​

      استخدم المعامل conversation بدلًا من تتبّع معرّفات الاستجابات:

      {"input": "Hello", "conversation": "my-project"}
      {"input": "What's in src/?", "conversation": "my-project"}
      {"input": "Run the tests", "conversation": "my-project"}

      يربط الخادم تلقائيًا بأحدث استجابة في تلك المحادثة، على غرار الأمر /title في جلسات gateway.

      GET /v1/responses/{id}​

      يسترجع استجابة مخزّنة سابقًا بواسطة معرّفها.

      DELETE /v1/responses/{id}​

      يحذف استجابة مخزّنة.

      GET /v1/models​

      يسرد الوكيل كنموذج متاح. ويكون اسم النموذج المُعلَن افتراضيًا هو اسم الـ profile (أو hermes-agent للـ profile الافتراضي). تحتاج إليه معظم الواجهات الأمامية لاكتشاف النماذج.

      /v1/models هو عمدًا الواجهة الخفيفة المتوافقة مع OpenAI. فهو لا يسرد كل تركيبات المزوّد/النموذج المصادَق عليها التي يمكن لـ Hermes التوجيه إليها، ولا يُثري النتائج بمعلومات الأسعار أو القدرات.

      GET /api/model/options​

      يمكن للعملاء المُدركين لخصائص Hermes طلب قائمة المزوّدين/النماذج المنتقاة نفسها التي تستخدمها لوحة التحكم و TUI. يستخدم هذا المسار مصادقة bearer المعتادة في خادم API، ويُرجع صفوف المزوّدين، وتلميحات حول قدرات النماذج، وبيانات وصفية للأسعار لا مكان لها في استجابة /v1/models المتوافقة مع OpenAI:

      curl \
        -H "Authorization: Bearer $API_SERVER_KEY" \
        "http://127.0.0.1:8642/api/model/options"

      هذه البيانات هي الأساس نفسه الذي تعتمد عليه صفحة Models في لوحة التحكم واستدعاء RPC المسمّى model.options في TUI. فهي تُرجع المزوّدين المصادَق عليهم، وقوائم النماذج المنتقاة، وأسعار كل نموذج، وتلميحات حول قدرات النماذج.

      الفتح العادي متحفّظ عمدًا مع المزوّدين المخصّصين: إذ لا يفحص Hermes إلا الـ endpoint المخصص المحدَّد حاليًا، حتى لا يعطّل endpoint محفوظ قديم أو غير متصل المنتقي. أما التحديث الصريح فينتقل إلى الفحص الكامل ويُفرغ التخزين المؤقت لنماذج المزوّد:

      curl \
        -H "Authorization: Bearer $API_SERVER_KEY" \
        "http://127.0.0.1:8642/api/model/options?refresh=1"

      استخدم /v1/models عندما يحتاج عميل متوافق مع OpenAI إلى اسم نموذج فقط لإرساله في طلبات chat/responses. واستخدم /api/model/options عندما تحتاج واجهة مصادَق عليها إلى البيانات الوصفية الأغنى الخاصة بمنتقي Hermes.

      GET /v1/capabilities​

      يُرجع وصفًا قابلًا للقراءة آليًا للواجهة المستقرة التي يوفّرها خادم API، وذلك للواجهات الخارجية ومنظِّمات التشغيل (orchestrators) وجسور الإضافات.

      {
        "object": "hermes.api_server.capabilities",
        "platform": "hermes-agent",
        "model": "hermes-agent",
        "auth": {"type": "bearer", "required": true},
        "features": {
          "chat_completions": true,
          "responses_api": true,
          "run_submission": true,
          "run_status": true,
          "run_events_sse": true,
          "run_stop": true,
          "reasoning_streaming": true
        }
      }

      استخدم هذا الـ endpoint عند دمج لوحات التحكم أو واجهات المتصفح أو مستويات التحكم (control planes)، لكي تكتشف ما إذا كان إصدار Hermes العامل يدعم runs والبث والإلغاء واستمرارية الجلسة، دون الاعتماد على تفاصيل Python الداخلية الخاصة.

      التحكم عبر إضافة المتصفح (أُزيل)​

      أُزيل بروتوكول وحدة التحكم في إضافة المتصفح (POST /v1/browser-control/register، وGET /v1/browser-control/ws، ومسارات /v1/artifacts/*، واستدعاءات RPC في لوحة التحكم browser.controller.*، ومفتاح الإعدادات browser.extension_control). كان يوجّه الأدوات القديمة browser_navigate/browser_click/…، وهي لم تعد موجودة: أصبحت أتمتة المتصفح الآن عبر browser_exec فوق CDP. ولكي يتحكم Hermes في متصفح تشغّله بالفعل، وجّهه إلى endpoint الخاص بـ DevTools في ذلك المتصفح عبر browser.cdp_url في config.yaml أو /browser connect — راجع Your own browser via CDP. تؤدي الترقية إلى حذف كتلة browser.extension_control المتبقية من config.yaml.

      اختيار النموذج لكل طلب​

      يمكن للعملاء المصادَق عليهم تجاوز اختيار النموذج الافتراضي في Hermes لكل طلب على حدة بإرسال:

      • model — معرّف النموذج المستهدف لهذا الدور
      • provider — المعرّف المختصر (slug) لمزوّد Hermes لتحديد بيانات الاعتماد/بيئة التشغيل لهذا الدور
      • model_options — عناصر تحكم الاستدلال (reasoning) / فئة الخدمة (service tier) الخاصة بهذا الطلب فقط

      تُقبل حقول الطلب نفسها على:

      • POST /v1/chat/completions
      • POST /v1/responses
      • POST /v1/runs
      • POST /api/sessions/{session_id}/chat
      • POST /api/sessions/{session_id}/chat/stream

      ترتيب الأولوية حتمي:

      1. تجاوز /model على مستوى الجلسة، إن كان للجلسة تجاوز بالفعل
      2. ربط ثابت في gateway.platforms.api_server.model_routes يُختار عندما تكون قيمة model في الطلب اسمًا مستعارًا لمسار مُعدّ
      3. قيمتا model / provider المباشرتان في الطلب عندما لا يتطابق أي اسم مستعار لمسار
      4. الإعدادات العامة لـ gateway / القيم الافتراضية من البيئة

      model_options يظل خاصًا بالطلب بغض النظر عن النموذج/المزوّد الذي يُعتمد. إذا أرسل طلب provider يتعارض مع اسم مستعار مضبوط في model_routes، يرفض Hermes الطلب مع 400 بدلًا من خلط بيانات اعتماد المسار بمزوّد آخر بصمت.

      قيم model المجرّدة على endpoints المتوافقة مع OpenAI تتطلب تفعيلًا صريحًا. فعملاء OpenAI العامّون كثيرًا ما يثبّتون أسماء النماذج في الكود (gpt-4o، ...)، وتعتمد عمليات النشر القائمة على عودة هذه القيم إلى النموذج الافتراضي في gateway. لذلك، على POST /v1/chat/completions و POST /v1/responses، تُتجاهل قيمة model المُرسلة دون أي provider ما لم تفعّل:

      gateway:
        platforms:
          api_server:
            direct_model_requests: true

      أما الطلبات التي تتضمن provider صريحًا — وكذلك endpoints الأصلية في Hermes مثل /v1/runs و endpoints محادثة الجلسات — فتلتزم دائمًا بالنموذج المطلوب بغض النظر عن هذا الخيار.

      مثال:

      {
        "model": "MiniMax-M3",
        "provider": "minimax",
        "model_options": {
          "reasoning_effort": "high",
          "service_tier": "priority"
        },
        "messages": [
          {"role": "user", "content": "Summarize the repo status."}
        ]
      }

      GET /health​

      فحص السلامة (health check). يُرجع {"status": "ok"}. ومتاح أيضًا على GET /v1/health لعملاء OpenAI المتوافقين الذين يتوقعون البادئة /v1/.

      GET /health/detailed​

      فحص جاهزية مصادَق عليه لأنظمة المراقبة ومستويات التحكم. يعرض حالة موجزة لإعدادات الـ profile النشط، وقاعدة بيانات الحالة، والنموذج المُعدّ، ومساحة القرص، وحالة gateway/المنصات، وعمليات API الجارية، وعمليات إكمال العمليات المعلّقة، والتفويضات النشطة. وتكشف الاستجابة عن الحالة والأعداد فقط، لا عن قيم الإعدادات أو بيانات الاعتماد أو المسارات أو الأوامر أو حمولات قوائم الانتظار أو الأخطاء الخام.

      يبقى المسار العام /health فحصًا خفيفًا لبقاء الخدمة حيّة (liveness) ولا يُجري فحوص الجاهزية. ونتيجة الجاهزية المتدهورة لا تزال تستخدم HTTP 200؛ لذا افحص الحقلين status و readiness.checks في المستوى الأعلى.

      Runs API (بديل ملائم للبث)​

      إلى جانب /v1/chat/completions و /v1/responses، يوفّر الخادم واجهة عمليات التشغيل API للجلسات الطويلة التي يريد فيها العميل الاشتراك في أحداث التقدّم بدلًا من إدارة البث بنفسه.

      POST /v1/runs​

      ينشئ تشغيلًا (run) جديدًا للوكيل. ويُرجع run_id يمكن استخدامه للاشتراك في أحداث التقدّم.

      {
        "run_id": "run_abc123",
        "status": "started"
      }

      تقبل عمليات التشغيل سلسلة input بسيطة، ويمكن اختياريًا إرسال session_id, instructions, conversation_history أو previous_response_id. وعند تقديم session_id، يُظهره Hermes في حالة التشغيل لتتمكن الواجهات الخارجية من ربط عمليات التشغيل بمعرّفات المحادثات الخاصة بها.

      لجعل عملية الإنشاء آمنة لإعادة المحاولة، أرسل الترويسة Idempotency-Key (من 1 إلى 255 حرف ASCII مرئي). يحجز Hermes المفتاح بشكل دائم قبل بدء العمل. وتُرجع إعادة المحاولة المطابقة run_id الأصلي مع HTTP 202 و Idempotency-Replayed: true، حتى بعد إعادة تشغيل gateway وبعد اكتمال التشغيل أو فشله أو إلغائه. وإعادة استخدام المفتاح نفسه مع حمولة JSON مختلفة تُرجع HTTP 409 مع الرمز idempotency_key_conflict. تُعزل المفاتيح حسب profile/بيانات اعتماد API المصادَق عليها، وتُحفظ لمدة 24 ساعة بعد آخر تحديث لحالتها؛ لذا ينبغي للعملاء استخدام مفاتيح فريدة يصعب تخمينها، ويجب ألا يعيدوا استخدامها في عمليات غير ذات صلة. أما الطلبات التي لا تتضمن الترويسة فتحتفظ بالسلوك القديم وتنشئ دائمًا تشغيلًا جديدًا.

      التشغيل الذي لم يستطع الـ gateway قبوله لا يحتفظ بأي حجز، لذا فإعادة المحاولة المطابقة آمنة. وعندما يكون الـ profile في حالة تصريف (draining) أو تقاعد، أو عندما تبقى قاعدة بيانات الحالة مقفلة بعد مهلة الكتابة، يُجيب POST /v1/runs وعناصر التحكم في التشغيل بـ HTTP 503 (runtime_draining أو storage_unavailable) مع Retry-After؛ ويُجيب جسم تحكم مشوَّه بـ 400 invalid_params؛ وتبقى حالات رفض الملكية والجيل (generation) والهوية برمز 409.

      عندما يحدد session_id جلسة Hermes موجودة، ولا يُقدَّم conversation_history أو previous_response_id صريح، يحمّل التشغيل النص الكامل النشط لتلك الجلسة (transcript). وتعمل عقود إيجار أدوار الجلسة (session turn leases) على ترتيب الكتّاب المتزامنين تسلسليًا، وتحديث النص الكامل بعد انتظار ناتج عن التنافس.

      جلسات API هي جلسات خاصة بها. يجوز لـ session_id (هنا) وللترويسة X-Hermes-Session-Id (في /v1/chat/completions و /v1/responses) أن تسمّي جلسة أنشأها خادم API أو جلسة يجوز له إنشاؤها؛ ولا يمكنها ربط جلسة تملكها واجهة أخرى — محادثة CLI أو TUI أو Desktop أو ACP أو المراسلة. يُرفض مثل هذا الطلب بـ HTTP 409 ورمز الخطأ permission_denied قبل أي قبول: فلا يُنشأ تشغيل، ولا يُحتفظ بحجز Idempotency-Key، وتُجاب إعادة المحاولة المطابقة بـ 409 مرة أخرى. وهذا يحل محل السلوك السابق الذي كان خادم API يشغّل فيه وكيله الخاص على سجل جلسة غريبة بالتوازي مع مالكها الحي. وللعمل على محادثة من واجهة أخرى، اتصل عبر WebSocket الخاص بالـ gateway (prompt.submit على الجلسة المشتركة) بدلًا من المسارات المتوافقة مع OpenAI.

      GET /v1/runs/{run_id}​

      استطلع حالة التشغيل الحالية. وهذا مفيد للوحات التحكم التي تحتاج إلى الحالة دون إبقاء اتصال SSE مفتوحًا، أو للواجهات التي تعيد الاتصال بعد التنقل.

      {
        "object": "hermes.run",
        "run_id": "run_abc123",
        "status": "completed",
        "session_id": "space-session",
        "model": "hermes-agent",
        "output": "Done.",
        "usage": {"input_tokens": 50, "output_tokens": 200, "total_tokens": 250, "cache_read_tokens": 40, "cache_write_tokens": 0},
        "runtime": {"provider": "openai", "model": "gpt-5", "route_source": "global"}
      }

      model يعكس ما طلبه الطلب. وفي تشغيل مكتمل، يكون runtime زوج المزوّد/النموذج الذي خدم الدور فعليًا — وبعد الانتقال إلى مزوّد احتياطي يذكر الزوج الاحتياطي، كي ينسب نظام استقصاء التكلفة التشغيل إلى المزوّد الصحيح. و usage.cache_read_tokens / usage.cache_write_tokens هي قراءات التخزين المؤقت للـ prompt وكتاباته في الجلسة، فلا يُسعّر الإدخال المخزّن مؤقتًا بالسعر الكامل. ولـ runtime البنية نفسها الموجودة في /v1/chat/completions و /v1/responses: route_source يوضح كيفية اختيار بيئة التشغيل (global, raw_request, model_routes)، ويحصل الطلب الذي حدد model/provider أيضًا على requested: {provider, model} كي يمكن مقارنة الزوج المطلوب بالزوج المستخدم. ويحمل حدث run.completed في stream الأحداث الحقلين usage و runtime نفسيهما.

      تُحفظ الحالات لفترة وجيزة بعد بلوغ الحالات النهائية (completed أو failed أو cancelled أو interrupted) للاستطلاع والتوفيق مع UI. وعندما يتوقف الـ gateway بينما التشغيل نشط، يُحفظ التشغيل بوصفه interrupted (الخطأ Gateway shutdown interrupted the run.، والحدث النهائي run.interrupted) قبل طلب توقف الوكيل، فلا يبقى أي تشغيل دائم بعد إعادة التشغيل بوصفه running؛ ولا تستطيع نتيجة متأخرة من الدور الذي قوطع الكتابة فوقه. أما التشغيل المرجعي الذي أُعيد تشغيل مالكه في منتصف الدور فيُبلغ عن unknown بدلًا من ذلك، وهي حالة غير نهائية: تنتظر الأدوار اللاحقة في تلك الجلسة إلى أن يُقَرّ بها عبر POST /v1/runs/{run_id}/resolve-unknown (أدناه).

      بينما ما زال الـ gateway يصرف الأعمال الجارية (hermes gateway stop/restart أو SIGTERM أثناء تنفيذ دور)، يحمل كل تشغيل غير نهائي أيضًا shutdown_requested_at (ثواني Unix) منذ لحظة رفض الأدوار الجديدة. ويبقى status بالقيمة running لأن الدور ما زال يُخدم؛ ويعرف نظام الاستقصاء الذي يرى الحقل أن العملية في طريقها إلى التوقف وأن التشغيل سينتهي interrupted على أبعد تقدير عند انتهاء ميزانية تصريف العمل. ولا تحصل عمليات التشغيل النهائية على هذا الحقل مطلقًا.

      GET /v1/runs/{run_id}/events​

      stream عبر Server-Sent Events يعرض تقدم استدعاءات الأدوات، وفروق tokens ، وأحداث دورة حياة التشغيل. صُمم للوحات التحكم والعملاء متكاملين الوظائف الذين يريدون الاتصال/الانفصال دون فقدان الحالة.

      يصل تعليق المساعد في منتصف الدور — مقدمات التقدم openai-codex الخاصة بـ backend phase="commentary"، أو النص الذي يكتبه نموذج إلى جانب استدعاءات أدواته — بصيغة message.interim (text, already_streamed)، وهو العقد نفسه الذي يستخدمه TUI gateway. ويعني already_streamed: true أن النص خرج أيضًا بصيغة message.delta، فيمكن للعملاء الذين يعرضون الفروق تجاوزه. وما زالت الإجابة النهائية لا تصل إلا في run.completed؛ ولا يصبح الاستدلال الخاص message.interim مطلقًا. شرط التمكين: display.interim_assistant_messages (الافتراضي true).

      تحمل أحداث دورة حياة الأداة tool.started (tool, preview للوسائط) و tool.completed (tool, duration بالثواني، و error، و preview للنتيجة). ويعكس الخيار error نتيجة الأداة نفسها — قيمة exit_code غير صفرية للطرفية، أو نتيجة {"error": ...} منظّمة، أو موافقة مرفوضة — سواء وصلت النتيجة كسلسلة JSON أو ككائن محلّل مسبقًا. ويكون preview الخاص بالإكمال نص النتيجة (تُرمّز النتائج المنظّمة بصيغة JSON)، ويمر عبر تنقيح إلزامي للأسرار ثم يُقتطع إلى 500 محرف، كي يستطيع العميل تمييز رفض الموافقة (BLOCKED: ...) عن الفشل العادي دون تلقي حمولة الأداة غير المحدودة.

      عندما يفوّض الوكيل العمل إلى subagents في الخلفية، يحمل البث أيضًا أحداث دورة الحياة subagent.start و subagent.complete، لكي يتمكن العملاء من مراقبة نتائج التفويض — بما في ذلك انتهاء المهلة والإخفاقات — بدلًا من صمت التشغيل بينما يعمل الوكيل الفرعي. وتحمل حمولة subagent.complete حالة الوكيل الفرعي، وملخّصه، ومدته، وأرقام الـ tokens/التكلفة، و child_session_id لأغراض الربط، و delegation_id الخاص بالدفعة التي ينتمي إليها (لتبقى عمليات التوزيع المتزامنة أو المتداخلة قابلة للتمييز)؛ وتخضع الحقول النصية الحرة لإخفاء إلزامي للأسرار قبل مغادرة العملية. أما أحداث الوكيل الفرعي الخاصة بكل أداة (subagent.tool، ونبضات التقدّم) فهي عمدًا لا تُمرَّر — لأنها ضجيج كثيف في الواجهة؛ استخدم ملفات النص الحي لكل وكيل فرعي لمتابعة التفاصيل خطوة بخطوة. هذه الأحداث متاحة ما دام بث الأصل مفتوحًا؛ وأي إكمال منفصل متأخر لا يعيد فتح بث SSE لتشغيل منتهٍ ولا يغيّر حالته النهائية.

      النتائج المنفصلة وسجل الجلسة​

      يتطلب التفويض في الخلفية استئنافًا يقرأ سجل الجلسة على جانب الخادم: أي ترويسة X-Hermes-Session-Id صريحة في Chat Completions ، أو طلب /api/sessions/{id}/chat أصلي، أو طلب Runs يستخدم سجل الجلسة. أما طلبات Chat Completions بلا ترويسة، وسلاسل Responses ، وطلبات Runs التي تتضمن previous_response_id أو سجلًا يقدّمه المستدعي، فتنفّذ التفويض بشكل متزامن بدلًا من ذلك، وتُرجع النتيجة في الدور الأصلي. ومجرد اشتقاق معرّف جلسة من محتوى الطلب لا يُفعّل التسليم المنفصل.

      في الطلبات القابلة للاستئناف، تُحفظ نتيجة الإكمال مرة واحدة لكل وحدة تفويض. وهي متاحة عبر GET /api/sessions/{id}/messages وفي سجل الجلسة للدور الفعلي التالي من العميل. ولا تُدرج إعادة المحاولة النتيجة نفسها مجددًا؛ أما إشعارات فشل المهام المؤقتة فلها هويات منفصلة. وينتظر التسليم ما دام دور العميل يملك عقد إيجار الجلسة، ويتبع عمليات الاستئناف الناتجة عن الضغط (compression). ويعيد Chat Completions معرّف الجلسة الصريح الذي قدّمته في كلٍّ من استجابات JSON واستجابات البث؛ لذا استمر في إرسال ذلك المعرّف حتى بعد الضغط.

      لا تبدأ نتيجة الإكمال أبدًا دورًا للنموذج دون طلب، ولا تتجاوز تأكيدًا بشريًا معلّقًا. فالعميل هو من يملك الدور التالي. أما العملاء الذين يواصلون استخدام لقطات (snapshots) السجل الخاصة بهم فينبغي أن يستخدموا التفويض المتزامن بدلًا من توقّع دمج صف تسليم من جانب الخادم في تلك اللقطات.

      تنتهي صلاحية مخازن الأحداث غير المستهلكة بعد خمس دقائق، حتى لا يتسبب عميل منفصل في تضخّم الذاكرة إلى ما لا نهاية. ولا ينتهي بذلك إلا حالة وسيلة النقل: فالتشغيل الذي لا يزال قيد التنفيذ يبقى مرئيًا لاستطلاع الحالة، والموافقة، والتحكم في الإيقاف، و احتساب التزامن إلى أن ينتهي عمل المنفّذ الخاص به فعليًا. ويواصل مشترك SSE المتصل استهلاك الأحداث بشكل طبيعي.

      POST /v1/runs/{run_id}/resolve-unknown​

      بعد إعادة تشغيل مالك الجهة (authority-owner)، يكون لدور سبقت المطالبة به نتيجة تنفيذ مجهولة، ويُبلغ عنها GET /v1/runs/{run_id} بالقيمة "status": "unknown" (غير نهائية). يوقف Hermes الأعمال اللاحقة في تلك الجلسة بدلًا من المخاطرة بإعادة تشغيل الرأس المفقود. اقرأ admission_id و execution_generation بدقة من ذلك الجسم، ثم أقِرّ بأن التنفيذ المفقود لن يكتمل:

      {
        "admission_id": "adm_abc123",
        "execution_generation": 7
      }

      الطلب مصادَق عليه ومحصور بمالك التشغيل مثل عناصر التحكم الأخرى في التشغيل؛ ويحتاج المستدعون من الغرف المستضافة (hosted-room) إلى منحة stop الموجودة. والاستجابة الناجحة هي إيصال النهاية المرجعي (outcome: "interrupted") مع run_id. وهي تحرر طابور FIFO مرة واحدة وتجدول التابع المصطف دون إعادة تشغيل الرأس المجهول. وتعيد الإعادة المطابقة لحسم سبق تثبيته الإيصال نفسه (200)، فإعادة المحاولة بعد ضياع الاستجابة آمنة. ويعيد الجيل (generation) القديم أو غير الصحيح، أو التشغيل غير المجهول حاليًا، الرمز 409 stale_generation؛ ويعيد معرّف قبول لا ينتمي إلى تشغيل المسار 409 not_found. ويجب أن يحتوي الجسم على هذين الحقلين بالضبط، وإلا يُرجع الخادم 400 invalid_params.

      تحسم homes الغرف المستضافة تشغيلَ عضو بحالة unknown بهذه الطريقة عند استطلاعها التالي وتُنهي مهمة الغرفة بوصفها مقاطَعة ("member gateway restarted"). أما room home على إصدار أقدم فلا يعرف الحالة unknown ويُبلغ عن حالة تشغيل غير مطابقة إلى أن تتم ترقيته.

      يُعلَن عن عنصر التحكم في الاسترداد هذا بوصفه features.run_unknown_resolution وبوصفه endpoint باسم run_unknown_resolution فقط عندما تكون جهة صلاحية الجلسات المرجعية (canonical session authority) نشطة. ولا يعلن عنه وضع تنفيذ API القديم. أما POST /v1/runs/{run_id}/stop العادي فيبقى عمدًا منفصلًا ويُرجع 409 unknown_execution لقبول مجهول.

      بالنسبة إلى عمليات القبول التي أنشأها هذا الإصدار، يُخزَّن نطاق مالك التشغيل المعتم (opaque run-owner scope) ذريًّا مع القبول المرجعي ويُحتفظ به طوال عمر التحكم/الحالة لذلك القبول، بما في ذلك الحالة النهائية. وهو حالة خاصة بالخادم، وليس بيانات اعتماد حامل (bearer) ولا مدخلًا للنموذج ولا حقلًا في استجابة API. تبقى الطلبات غير ذات المفتاح غير متكافئة القوة (non-idempotent)، فتظل أجسام الطلبات المتطابقة تُنشئ تشغيلات منفصلة. أما عمليات القبول القديمة غير ذات المفتاح فلا نطاق مالك محفوظًا لها وتستمر في الفشل بإغلاق آمن (fail closed) بعد إعادة تشغيل المحوّل (adapter)؛ ولا يمكن ملؤها راجعًا بأمان. وتواصل التشغيلات القديمة ذات المفتاح استخدام سجل idempotency القائم. ويزيل إنهاء الجلسة الصريح حمولة القبول المرجعي ومالكها القابل للاسترداد. سجل الإعادة والقبول المرجعي معاملتان منفصلتان في قاعدة البيانات؛ ولا يعد عنصر التحكم في الاسترداد هذا بتنفيذ مرة واحدة بالضبط (exactly-once) على المستوى العام.

      POST /v1/runs/{run_id}/stop​

      يقاطع دور وكيل قيد التشغيل. يُرجع الـ endpoint فورًا {"status": "stopping"} بينما يطلب Hermes من الوكيل النشط التوقف عند نقطة المقاطعة الآمنة التالية. ويبقى التشغيل مُتتبَّعًا بالحالة stopping إلى أن ينتهي العمل المدعوم بالمنفّذ، ثم يستقر على الحالة cancelled؛ فطلب الإيقاف لا يُخفي أبدًا عاملًا (worker) لا يزال قيد التشغيل.

      POST /v1/runs/{run_id}/approval​

      يحسم موافقة معلّقة لتشغيل ينتظر قرارًا بشريًا (مثل استدعاء أداة يخضع لسياسة موافقة). يحمل جسم الطلب قرار الموافقة، ويُستأنف التشغيل بمجرد تسجيل القرار. ويُعلَن عن هذا الـ endpoint في /v1/capabilities على أنه الميزة run_approval، لكي تتمكن الواجهات الخارجية من اكتشاف الدعم قبل عرض طلب موافقة.

      مع مالك gateway المرجعي، يعرض GET /v1/runs/{run_id} الحقل pending_controls، مستخدمًا prompt_id و execution_generation نفسيهما اللذين يراهما مشاهدو WebSocket المرتبطون. أجِب بالهوية الحالية الدقيقة:

      {"request_id": "<prompt_id>", "execution_generation": 3, "choice": "once"}

      لا تقبل عناصر التحكم المرجعية ردودًا بلا هوية أو جماعية. وتعيد الأجيال القديمة، ومعرّفات prompt الغريبة، والتشغيلات المستقرة HTTP 409. وتظل قيود مصادقة التشغيل القائمة وموافقة الغرف المستضافة سارية.

      POST /v1/runs/{run_id}/clarify​

      أجِب عن توضيح مرجعي بالحقول request_id و execution_generation و answer (سلسلة نصية). يحسم هذا الـ endpoint المصادَق عليه و clarify.respond في WebSocket الأداة المنتظرة نفسها؛ والإجابة لا تُرسل دور inference آخر. وتظهر موافقة بوابة الثقة في MCP — لأداة قادرة على الكتابة في خادم مُعدّ بالقيمة trust: untrusted — بالطريقة نفسها: يُصدر التشغيل حدث approval.request ويتوقف في waiting_for_approval إلى أن يحسمه هذا الـ endpoint (once يشغّل الأداة، و deny يمنعها).

      Jobs API (أعمال مجدولة في الخلفية)​

      يوفّر الخادم واجهة CRUD خفيفة للمهام (jobs) لإدارة عمليات تشغيل الوكيل المجدولة / العاملة في الخلفية من عميل بعيد. وجميع الـ endpoints محمية بمصادقة bearer نفسها.

      GET /api/jobs​

      يسرد جميع المهام المجدولة.

      POST /api/jobs​

      ينشئ مهمة مجدولة جديدة. يقبل جسم الطلب البنية نفسها التي يقبلها hermes cron — الـ prompt ، والجدول الزمني، والمهارات، وتجاوز المزوّد، ووجهة التسليم.

      GET /api/jobs/{job_id}​

      يجلب تعريف مهمة واحدة وحالة آخر تشغيل لها.

      PATCH /api/jobs/{job_id}​

      يحدّث حقول مهمة موجودة (الـ prompt ، والجدول الزمني، وغيرها). وتُدمج التحديثات الجزئية.

      DELETE /api/jobs/{job_id}​

      يزيل مهمة. ويلغي أيضًا أي تشغيل جارٍ لها.

      POST /api/jobs/{job_id}/pause​

      يوقف مهمة مؤقتًا دون حذفها. وتُعلَّق الطوابع الزمنية للتشغيل المجدول التالي حتى الاستئناف.

      POST /api/jobs/{job_id}/resume​

      يستأنف مهمة أُوقفت مؤقتًا في السابق.

      POST /api/jobs/{job_id}/run​

      يُطلق تشغيل المهمة فورًا، خارج جدولها الزمني.

      Sessions API (التحكم في الجلسات عبر REST)​

      يمكن للواجهات الخارجية إدارة جلسات Hermes عبر REST دون الحاجة إلى تشغيل لوحة التحكم. جميع الـ endpoints محمية بـ API_SERVER_KEY وتقع تحت /api/sessions/*.

      الطريقةالمسارالوصف
      GET/api/sessionsيسرد الجلسات (مع ترقيم الصفحات — limit, offset, source, include_children)
      POST/api/sessionsينشئ جلسة فارغة
      GET/api/sessions/{id}يقرأ البيانات الوصفية للجلسة
      PATCH/api/sessions/{id}يحدّث العنوان أو end_reason
      DELETE/api/sessions/{id}يحذف جلسة
      GET/api/sessions/{id}/messagesسجل رسائل الجلسةinclude_compacted=true يعيد أيضًا الأدوار التي أرشفها ضغط السياق (الافتراضي: نص المحادثة الحي فقط). ويعرض inline_images=false مرفقات الصور كعناصر نائبة [image] بدل data URIs المضمّنة — فيُرسل نص المحادثة بالكيلوبايتات للعملاء الذين يقرأونه عبر الشبكة

      /v1/capabilities عن الواجهة الكاملة عبر علامات الميزات session_* ومُدخلات endpoints.session_*، لكي تتمكن الواجهات الخارجية من اكتشاف الدعم والرجوع إلى بديل بأمان. وتُدعم الصور المضمّنة في حمولات chat و chat/stream (عبر مسار يدعم الوسائط المتعددة).

      # fork a session and run one turn
      curl -X POST http://localhost:8642/api/sessions/$ID/fork \
        -H "Authorization: Bearer $API_SERVER_KEY" \
        -d '{"title": "explore alt path"}'

      # stream a turn over SSE
      curl -N -X POST http://localhost:8642/api/sessions/$ID/chat/stream \
        -H "Authorization: Bearer $API_SERVER_KEY" \
        -d '{"input": "what files changed in the last hour?"}'

      curl http://localhost:8642/v1/skills \

      # → [{"name": "github-pr-workflow", "description": "...", "category": "..."}, ...]

      curl http://localhost:8642/v1/toolsets \

      تحديد نطاق الذاكرة طويلة المدى (X-Hermes-Session-Key)​

      تحتاج الواجهات الأمامية متعددة المستخدمين مثل Open WebUI إلى معرّف ثابت لكل قناة من أجل الذاكرة طويلة المدى (Honcho وغيرها)، يكون مستقلًا عن X-Hermes-Session-Id المرتبط بنطاق النص الكامل للمحادثة (والذي يتغيّر عند /new). مرّر X-Hermes-Session-Key على /v1/chat/completions, /v1/responses أو /v1/runs، وسيمرّره Hermes حتى AIAgent(gateway_session_key=...)، حيث يستخدمه مزوّد ذاكرة Honcho لاشتقاق نطاق ثابت.

      POST /v1/chat/completions HTTP/1.1
      Authorization: Bearer ***
      X-Hermes-Session-Id: transcript-alpha
      X-Hermes-Session-Key: agent:main:webui:dm:user-42

      القواعد: الحد الأقصى 256 حرفًا، وتُرفض محارف التحكم (\r, \n, \x00) تُرفض، وتُعاد القيمة في الاستجابات (JSON + SSE). /v1/capabilities عن الدعم عبر "session_key_header": "X-Hermes-Session-Key". دون المفتاح، فإن استراتيجية Honcho per-session في Honcho نطاقًا مختلفًا لكل session_id — وهو سلوك Hermes السابق بالضبط.

      يتبع الاسترجاع التلقائي نص المحادثة: يُهيّأ مزوّد الذاكرة مرة واحدة لكل جلسة ويُحتفظ به عبر الطلبات، لذا تتلقى الجلسة المستمرة (X-Hermes-Session-Id, previous_response_id، أو محادثة X-Hermes-Session-Key مُعلنة) الاسترجاع الذي أعده المزوّد بعد الدور السابق، تمامًا مثل محادثة Telegram أو Discord. أما الطلب دون أي استمرارية فيبدأ جلسة جديدة، ومثل الدور الأول في أي جلسة CLI جديدة لا تكون هناك عناصر مُدرجة بعد. وتحرر الجلسات الخاملة مزوّدها بعد TTL الخمول نفسه الخاص بالتخزين المؤقت لوكلاء الـ gateway (agent.agent_cache.idle_ttl_secs — وهو تمامًا السلوك الذي كان عليه Hermes سابقًا.

      التعامل مع System Prompt​

      عندما ترسل واجهة أمامية رسالة system (في Chat Completions) أو حقل instructions (في Responses API)، فإن hermes-agent يضيفها كطبقة فوق الـ system prompt الأساسي الخاص به. يحتفظ وكيلك بجميع أدواته وذاكرته ومهاراته — ويضيف الـ system prompt الخاص بالواجهة الأمامية تعليمات إضافية فقط.

      هذا يعني أنه يمكنك تخصيص السلوك لكل واجهة أمامية دون فقدان أي قدرات:

      • الـ system prompt في Open WebUI: "أنت خبير في Python. أضف دائمًا تلميحات الأنواع (type hints)."
      • يظل لدى الوكيل الطرفية، وأدوات الملفات، والبحث في الويب، والذاكرة، وغيرها.

      المصادقة​

      مصادقة Bearer token عبر الترويسة Authorization في الترويسة:

      Authorization: Bearer ***

      اضبط المفتاح عبر متغير البيئة API_SERVER_KEY. وإذا كنت تحتاج إلى أن يستدعي متصفحٌ Hermes مباشرةً، فاضبط أيضًا API_SERVER_CORS_ORIGINS على قائمة سماح صريحة.

      التوجيه متعدد الـ profiles (/p/<profile>/…)​

      عند تفعيل توجيه gateway متعدد الـ profiles مفعّل (gateway.multiplex_profiles)، يخدم المستمع المشترك كل profile عبر بادئة URL بالشكل /p/<profile>/ — وترتبط المصادقة بالـ profile الموجَّه إليه:

      • يجب أن تقدّم الطلبات الموجّهة إلى /p/<profile>/v1/... المفتاح الخاص بذلك الـ profile نفسه API_SERVER_KEY (من ~/.hermes/profiles/<profile>/.env). ويُرفض مفتاح المستمع الافتراضي على بادئات الـ profiles المسمّاة.
      • تواصل المسارات بلا بادئة و /p/default/... استخدام مفتاح الـ profile الافتراضي.
      • الـ profile المسمّى الذي ليس له API_SERVER_KEY خاص به يفشل بشكل مغلق — إذ تبقى بادئته غير قابلة للوصول حتى تضبط مفتاحًا له.
      • نطاق عمليات التشغيل خاص بكل profile: فالمسار /v1/runs/{run_id} ومساراته events, stop, steer و approval لا تستجيب إلا للـ profile الذي أنشأ التشغيل (بما في ذلك عمليات التشغيل التي بدأت عبر /api/sessions/{id}/chat/stream)؛ أما معرّف تشغيل يخص profile آخر فيُرجع 404، وليس 403.
      تغيير كاسر للتوافق (يوليو 2026)

      قبل هذا الإصلاح، كان مفتاح الـ profile الافتراضي الصالح مقبولًا على أي بادئة /p/<profile>/. إذا كنت تعتمد على مفتاح واحد مشترك عبر بادئات الـ profiles ، فاضبط API_SERVER_KEY مختلفًا في ملف .env لكل profile — إذ أصبحت المفاتيح الافتراضية المُعاد استخدامها على البادئات المسمّاة تُرجع الآن 401.

      الأمان

      يمنح خادم API وصولًا كاملًا إلى مجموعة أدوات hermes-agent ، بما في ذلك أوامر الطرفية. API_SERVER_KEY هو مطلوب في كل عملية نشر، بما في ذلك الربط الافتراضي بعنوان loopback على 127.0.0.1. أبقِ API_SERVER_CORS_ORIGINS ضيق النطاق للتحكم في وصول المتصفحات عندما تسمح صراحةً بالاستدعاء من المتصفح.

      config.yaml​

      يمكن وضع الإعدادات نفسها في ~/.hermes/config.yaml ضمن قسم متداخل gateway.api_server: في القسم:

      gateway:
        api_server:
          enabled: true
          port: 8642
          host: 127.0.0.1
          key: your-secret-key
          cors_origins: http://localhost:3000
          model_name: my-hermes
          max_concurrent_runs: 10   # concurrent-run cap; 0 disables the limit
          history_tool_output_max_chars: 0   # cap tool outputs in stored /v1/responses history; 0 = verbatim

      port, key, host, cors_origins و model_name تلقائيًا إلى إعدادات extra الخاصة بالمنصة، لذا تتصرف تمامًا مثل نظيراتها من متغيرات البيئة API_SERVER_* المكافئة من متغيرات البيئة. تتقدم متغيرات البيئة على config.yaml. كما تُقبل هذه الكتلة أيضًا تحت gateway.platforms.api_server: أو ضمن قسم platforms.api_server: في المستوى الأعلى.

      حدّ عمليات التشغيل المتزامنة​

      يحد خادم API عدد عمليات تشغيل الوكيل التي يمكن تنفيذها معًا عبر endpoints التي تبدأ تشغيلًا مباشرة: endpoints المتوافقة مع OpenAI ، و endpoints الخاصة بـ Runs ، و endpoints محادثة الجلسة (POST /api/sessions/{id}/chat ونسخته /stream، اللذان يحملان رسائل الوكلاء المباشرة بين الأجهزة). تمر عمليات التشغيل التي يفعّلها cron (POST /api/jobs/{id}/run, POST /api/cron/fire) عبر مُجدول cron وتخضع لحدود cron نفسها، لا لهذا السقف. ويُقرأ السقف من gateway.api_server.max_concurrent_runs (القيمة الافتراضية 10; 0 تعطّل الحد، والقيم السالبة تُقيَّد إلى 0). وعند بلوغ الحد، تُرفض الطلبات الجديدة التي تبدأ عمليات تشغيل مع HTTP 429 Too many concurrent runs (max N) — على العملاء زيادة مهلة الانتظار ثم إعادة المحاولة.

      حجم السجل المخزّن لتسلسل previous_response_id​

      تضمّن كل لقطة /v1/responses مخزّنة سجل المحادثة التراكمي الكامل (وهذا ما يعيد تسلسل previous_response_id و conversation تشغيله)، بما في ذلك كل مخرجات الأدوات حرفيًا. لذا قد تجعل محادثة ذات بضعة مخرجات أدوات كبيرة عملية response_store.db واحدة تكتب عدة مئات KB. اضبط gateway.api_server.history_tool_output_max_chars (الافتراضي 0 = التخزين حرفيًا) لتقييد كل مُخرج أداة وكل وسيط نصي لاستدعاء أداة في السجل المخزّن بهذا العدد من المحارف؛ ويُقتطع أي شيء أطول إلى بدايته بالإضافة إلى علامة ...[N more chars]. ولا يُمس نص المستخدم والمساعد مطلقًا، و response.completed وأحداث SSE التزايدية لا تتأثر. ولأن السجل المخزّن هو ما يراه النموذج في الدور المتسلسل التالي، فإن تفعيل السقف يقلّص أيضًا ما يُعاد عرضه على النموذج — اتركه عند 0 إذا احتاج سير عملك مخرجات أدوات كاملة عبر الأدوار.

      ترويسات الأمان​

      تتضمن جميع الاستجابات ترويسات أمان:

      • X-Content-Type-Options: nosniff — تمنع تخمين نوع MIME (MIME sniffing)
      • Referrer-Policy: no-referrer — تمنع تسريب المُحيل (referrer)

      CORS​

      خادم API لا يفعّل CORS للمتصفحات افتراضيًا.

      للوصول المباشر من المتصفح، اضبط قائمة سماح صريحة:

      API_SERVER_CORS_ORIGINS=http://localhost:3000,http://127.0.0.1:3000

      عند تفعيل CORS:

      • استجابات Preflight تتضمن Access-Control-Max-Age: 600 (تخزين مؤقت لمدة 10 دقائق)
      • استجابات البث عبر SSE تتضمن ترويسات CORS لكي تعمل عملاء EventSource في المتصفح بشكل صحيح
      • X-Hermes-Session-Id ترويسة طلب مسموح بها، لذا يمكن للمتصفحات على مصدر مُدرج في قائمة السماح طلب استئناف الجلسة.
      • Idempotency-Key ترويسة طلب مسموح بها — ويمكن للعملاء إرسالها لمنع التكرار (راجع مفاتيح Idempotency لمعرفة ما يغطيه المفتاح ومدة الاحتفاظ به)

      معظم الواجهات الأمامية الموثّقة مثل Open WebUI تتصل من خادم إلى خادم ولا تحتاج إلى CORS إطلاقًا.

      إعداد متعدد المستخدمين باستخدام Profiles​

      لمنح عدة مستخدمين نسخة Hermes معزولة خاصة بكل منهم (إعدادات وذاكرة ومهارات منفصلة)، استخدم الـ profiles:

      # Create a profile per user
      hermes profile create alice
      hermes profile create bob

      # Configure each profile's API server on a different port. API_SERVER_* are env
      # vars (not config.yaml keys), so write them to each profile's .env:
      cat >> ~/.hermes/profiles/alice/.env <<EOF
      API_SERVER_ENABLED=true
      API_SERVER_PORT=8643
      API_SERVER_KEY=alice-secret
      EOF

      cat >> ~/.hermes/profiles/bob/.env <<EOF
      API_SERVER_ENABLED=true
      API_SERVER_PORT=8644
      API_SERVER_KEY=bob-secret
      EOF

      # Start each profile's gateway
      hermes -p alice gateway &
      hermes -p bob gateway &

      يُعلن خادم API الخاص بكل profile تلقائيًا عن اسم الـ profile بوصفه معرّف النموذج:

      • http://localhost:8643/v1/models → النموذج alice
      • http://localhost:8644/v1/models → النموذج bob

      في Open WebUI ، أضف كلًّا منها كاتصال منفصل. ستعرض القائمة المنسدلة للنماذج alice و bob كنموذجين مختلفين، يعتمد كلٌّ منهما على نسخة Hermes معزولة تمامًا. راجع دليل Open WebUI لمزيد من التفاصيل.

      القيود​

      • تخزين الاستجابات — تُحفظ الاستجابات المخزّنة (الخاصة بـ previous_response_id) في SQLite وتبقى بعد إعادة تشغيل gateway. الحد الأقصى 100 استجابة مخزّنة (مع الإزالة وفق LRU).
      • لا يوجد رفع للملفات — الصور المضمّنة مدعومة على كلٍّ من /v1/chat/completions و /v1/responses، لكن الملفات المرفوعة (file, input_file, file_id) ومدخلات المستندات غير المصوّرة غير مدعومة عبر API.
      • عملاء OpenAI البسيطة ما زالت ترى اسمًا مستعارًا — /v1/models عن الاسم المستعار الثابت لـ Hermes (hermes-agent أو اسم الـ profile النشط). أما العملاء الأغنى بالميزات فيمكنها إرسال تجاوزات صريحة لـ provider / model_options في الطلبات.

      Proxy Mode​

      يعمل خادم API أيضًا كـ backend لوضع وضع proxy في gateway. فعندما تُضبط نسخة Hermes gateway أخرى بـ GATEWAY_PROXY_URL يشير إلى خادم API هذا، فإنها تُعيد توجيه جميع الرسائل إليه بدلًا من تشغيل وكيلها الخاص. وهذا يتيح عمليات نشر مقسّمة — مثل حاوية Docker تتولى Matrix E2EE وتمرّر الرسائل إلى وكيل يعمل على الجهاز المضيف.

      راجع Proxy Mode في Matrix للاطلاع على دليل الإعداد الكامل.

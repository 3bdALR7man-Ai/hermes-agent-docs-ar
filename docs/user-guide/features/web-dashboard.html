      لوحة تحكم Hermes على الويب

      لوحة التحكم على الويب (web dashboard) هي واجهة تعمل في المتصفح لإدارة تثبيت Hermes Agent الخاص بك. فبدلًا من تحرير ملفات YAML أو تشغيل أوامر CLI، يمكنك ضبط الإعدادات وإدارة مفاتيح API ومراقبة الجلسات من واجهة ويب واضحة ومرتّبة.

      نصيحة

      تستخدم المصادقة في الوضع المستضاف (hosted mode) خدمة OAuth من Nous Portal؛ وإذا أردت أيضًا أن تتواصل لوحة التحكم مع backend حقيقي، فإن hermes setup --portal يربط النموذج و Tool Gateway كذلك. راجع Nous Portal.

      البدء السريع​

      hermes dashboard

      يشغّل هذا الأمر خادم ويب محليًا ويفتح http://127.0.0.1:9119 في متصفحك. تعمل لوحة التحكم بالكامل على جهازك — ولا تغادر أي بيانات localhost.

      الخيارات​

      hermes dashboard --no-open

      إدارة عدة Profiles​

      لوحة التحكم واجهة إدارة على مستوى الجهاز: خادم واحد يدير كل profile على الجهاز. يحدّد مبدّل الـ profiles في الشريط الجانبي (الظاهر كلما وُجد أكثر من profile واحد) أيَّ profile تقرأ منه صفحات الإدارة وتكتب إليه — إذ تتبعه صفحات Config و API Keys و Skills و MCP و Models وتبويب Chat جميعها. وعند اختيار profile غير الـ profile الخاص بلوحة التحكم نفسها، يظهر شريط تنبيه كهرماني اللون يحمل اسم الـ profile المُدار، حتى لا يكون هدف الكتابة ملتبسًا أبدًا.

      يُحفَظ الاختيار في URL (?profile=<name>)، لذا فإن الروابط العميقة مثل http://127.0.0.1:9119/skills?profile=worker تفتح والمبدّل مضبوط مسبقًا على الـ profile المطلوب، ويبقى الاختيار قائمًا بعد تحديث الصفحة.

      تشغيل لوحة التحكم من اسم مستعار (alias) لـ profile يوجّهك إلى لوحة التحكم الخاصة بالجهاز بدلًا من تشغيل خادم ثانٍ:

      worker dashboard
      # → already running: opens the browser at ?profile=worker
      # → not running:     starts the machine dashboard with "worker" preselected

      مرّر --isolated لإلغاء هذا السلوك وتشغيل خادم مخصّص يقتصر نطاقه على ذلك الـ profile (وهو السلوك السابق لعملية التوحيد — ومفيد إذا كنت تتعمّد إتاحة لوحات تحكم لـ profiles مختلفة بإعدادات مصادقة مختلفة).

      يتبع تبويب Chat المبدّل أيضًا: فالمحادثة المقيّدة بنطاق profile تُنشئ عملية PTY فرعية باستخدام HERMES_HOME الخاص بالـ profile المختار، لذا تجري المحادثة بنموذج ذلك الـ profile ومهاراته وذاكرته وسجل جلساته. ويؤدي تبديل الـ profile إلى بدء جلسة طرفية جديدة.

      ما يبقى خاصًا بكل profile ولا يشمله المبدّل: عمليات الـ gateway (أدِرها عبر hermes -p <name> gateway …)، وقاعدة بيانات الجلسات الخاصة بكل profile، ومجدولات cron (إذ تجمع صفحة Cron بالفعل بيانات جميع الـ profiles مع مرشّح خاص بها).

      المتطلبات المسبقة​

      لا يتضمن التثبيت الافتراضي لـ hermes-agent حزمة HTTP ولا أداة PTY المساعدة — فهما من الإضافات (extras) الاختيارية. تحتاج لوحة التحكم على الويب إلى FastAPI و Uvicorn (الإضافة web). ويحتاج تبويب Chat أيضًا إلى ptyprocess لتشغيل TUI المضمّنة خلف طرفية زائفة (pseudo-terminal) (الإضافة pty على أنظمة POSIX). ثبّت الاثنين باستخدام:

      cd ~/.hermes/hermes-agent && uv pip install -e ".[web,pty]"

      تجلب الإضافة web كلًا من FastAPI و Uvicorn؛ وتجلب pty الحزمة ptyprocess (على POSIX) أو pywinpty (على Windows الأصلي — لاحظ أن TUI المضمّنة نفسها لا تزال تتطلب WSL). ويتضمن cd ~/.hermes/hermes-agent && uv pip install -e ".[all]" كلتا الإضافتين، وهو أسهل طريق إذا كنت تريد أيضًا المراسلة والصوت وغيرهما.

      عند تشغيل hermes dashboard دون الاعتماديات اللازمة، سيخبرك بما يجب تثبيته. وإذا لم تكن الواجهة الأمامية (frontend) قد بُنيت بعد وكان npm متاحًا، فإنها تُبنى تلقائيًا عند التشغيل الأول.

      تبويب Chat جزء من كل تشغيل لـ hermes dashboard — فلوحة المحادثة المضمّنة في المتصفح (التي تشغّل TUI عبر PTY/WebSocket) متاحة دائمًا، دون الحاجة إلى أي خيار إضافي.

      الصفحات​

      الحالة (Status)​

      تعرض الصفحة الرئيسية نظرة عامة مباشرة على تثبيتك:

      • إصدار الوكيل وتاريخ صدوره
      • حالة الـ gateway — قيد التشغيل/متوقف، و PID، والمنصات المتصلة وحالة كل منها
      • الجلسات النشطة — عدد الجلسات التي كانت نشطة خلال آخر 5 دقائق
      • الجلسات الأخيرة — قائمة بأحدث 20 جلسة مع النموذج، وعدد الرسائل، واستهلاك الـ tokens، ومعاينة للمحادثة

      تُحدَّث صفحة الحالة تلقائيًا كل 5 ثوانٍ.

      شريط التنبيه بضغط الموارد​

      عندما يوشك الجهاز المضيف على نفاد الذاكرة أو مساحة القرص، يظهر شريط تنبيه أعلى لوحة التحكم (يعتمد على استطلاع الحالة نفسه — دون أي طلبات إضافية):

      • "Your agent is almost out of memory and may restart" — انخفضت الذاكرة المتاحة في النظام إلى المستوى elevated (أقل من 128 MiB أو أقل من 15%) أو المستوى critical (أقل من 64 MiB أو أقل من 5%)، وفقًا لقياسات نبضة الـ gateway (heartbeat) التي تتكرر كل 30 ثانية.
      • "Your agent restarted unexpectedly, most likely because it ran out of memory" — سجّل دفتر دورة الحياة (lifecycle ledger) خروجًا غير نظيف تحت ضغط الذاكرة في الإقلاع السابق (يُشتبه في أنه إنهاء بسبب OOM).
      • تحذيرات القرص — وحدة التخزين التي تحتوي على ~/.hermes توشك على الامتلاء (المستوى elevated عندما تقل المساحة الحرة عن 512 MB، والمستوى critical عندما تقل عن 256 MB).

      لا يظهر إلا التحذير النشط الأشد خطورة في كل مرة (القرص critical > الذاكرة critical > إعادة التشغيل بسبب OOM > القرص elevated > الذاكرة elevated). ويقتصر نطاق إغلاق التحذيرات على الإقلاع الحالي للـ gateway: فإغلاق تحذير يُظهر التحذير النشط التالي، وإعادة تشغيل الـ gateway أو تصاعد المستوى (elevated → critical) يُعيد إظهاره، أما النبضة القديمة (stale heartbeat) فلا تعرض شيئًا بدلًا من إطلاق تنبيه زائف.

      المحادثة (Chat)​

      يضمّن تبويب Chat واجهة Hermes TUI الكاملة (الواجهة نفسها التي تحصل عليها من hermes --tui) مباشرةً في المتصفح. كل ما يمكنك فعله في TUI داخل الطرفية — slash commands، وأداة اختيار النموذج، وبطاقات استدعاء الأدوات، وبث Markdown، ومطالبات التوضيح/sudo/الموافقة، وتنسيق المظاهر (skins) — يعمل هنا بالطريقة نفسها تمامًا، لأن لوحة التحكم تشغّل ملف TUI التنفيذي الحقيقي وتعرض مخرجاته بتنسيق ANSI عبر xterm.js مع أداة العرض WebGL الخاصة به للحصول على تخطيط خلايا دقيق على مستوى البكسل.

      آلية العمل:

      • يفتح /api/pty اتصال WebSocket مُصادَقًا عليه باستخدام session token الخاص بلوحة التحكم
      • يشغّل الخادم hermes --tui خلف طرفية زائفة (pseudo-terminal) من نوع POSIX
      • تنتقل ضغطات المفاتيح إلى الـ PTY، وتُبَث مخرجات ANSI عائدةً إلى المتصفح
      • ترسم أداة العرض WebGL في xterm.js كل خلية على شبكة ذات بكسلات صحيحة؛ ويُعرض تتبّع الفأرة (SGR 1006)، والأحرف العريضة (Unicode 11)، ورموز رسم الإطارات كلها بشكل أصلي
      • يؤدي تغيير حجم نافذة المتصفح إلى تغيير حجم TUI عبر الإضافة @xterm/addon-fit

      استئناف جلسة موجودة: من تبويب Sessions، انقر أيقونة التشغيل (▶) بجوار أي جلسة. سينقلك ذلك إلى /chat?resume=<id> ويشغّل TUI مع --resume، محمّلًا السجل الكامل.

      مبدّل الجلسات (الشريط الأيمن): يحتوي تبويب Chat على قائمة محادثات خاصة به على غرار ChatGPT، في شريط أيمن رفيع بجانب الطرفية، لتتمكن من التنقل بين المحادثات دون مغادرة الصفحة. يضع الشريط أداة اختيار النموذج في الأعلى وقائمة الجلسات أسفلها مباشرةً، بينما تشغل الطرفية معظم الشاشة. تعرض القائمة أحدث جلساتك للـ profile النشط — العنوان (أو معاينة لرسالة إن لم يوجد عنوان)، ووقت آخر نشاط بصيغة نسبية، وعدد الرسائل، وقناة المصدر للجلسات التي لم تبدأ من CLI. انقر أي صف لاستئنافه في مكانه (تُعاد تهيئة الطرفية بسجل تلك المحادثة)؛ وتُميَّز الجلسة النشطة. يبدأ New chat جلسة جديدة، ويُعيد عنصر التحديث جلب القائمة. الشريط مخصّص للتنقل فقط — إذ لا تزال عمليات الحذف وإعادة التسمية والتصدير والتنظيف الجماعي موجودة في تبويب Sessions. وعلى الشاشات الضيقة، يتحوّل إلى لوحة منزلقة.

      المتطلبات المسبقة:

      • Node.js (المتطلب نفسه الخاص بـ hermes --tui؛ إذ تُبنى حزمة TUI عند التشغيل الأول)
      • ptyprocess — تُثبَّت عبر الإضافة pty (cd ~/.hermes/hermes-agent && uv pip install -e ".[web,pty]"، أو [all] التي تشمل الاثنتين)
      • نواة POSIX (Linux أو macOS أو WSL2). تحتاج لوحة الطرفية في /chat تحديدًا إلى PTY من نوع POSIX — ولا يوجد مكافئ لها في Python على Windows الأصلي، لذا في التثبيت على Windows الأصلي يعمل باقي لوحة التحكم (الجلسات، والمهام، والمقاييس، ومحرّر الإعدادات)، لكن تبويب /chat سيعرض شريطًا يخبرك باستخدام WSL2 لهذه الميزة.

      أغلق تبويب المتصفح، وستُنهى عملية الـ PTY بشكل نظيف على الخادم. وإعادة فتحه تبدأ جلسة جديدة.

      لتوجيه Hermes Desktop إلى لوحة تحكم تعمل على جهاز آخر بدلًا من الـ backend المضمّن فيه، راجع قسم الـ backend البعيد أدناه.

      ربط Hermes Desktop بـ backend بعيد​

      يشغّل Hermes Desktop عادةً الـ backend المحلي الخاص به، لكن يمكنه أيضًا الاتصال بلوحة تحكم تعمل على جهاز بعيد (آلة افتراضية VM، أو جهاز في مختبر منزلي، وغير ذلك) عبر Settings → Gateways → Remote gateway. وهذا هو المصدر الأكثر شيوعًا لبلاغات "Desktop says the backend is ready but chat never works"، لأن فحص الجاهزية في Desktop يتحقق من أمور أقل مما يحتاجه اتصال المحادثة المباشر فعليًا.

      متطلب مسبق: يجب أن يكون hermes dashboard قيد التشغيل على الجهاز البعيد

      الـ "remote backend" الذي يتصل به Desktop هو عملية hermes dashboard تعمل على الجهاز البعيد — أي الخادم نفسه الذي توثّقه هذه الصفحة. يجب أن يكون قيد التشغيل ويمكن الوصول إليه قبل أن يكون لأي من الخطوات التالية معنى؛ فـ Desktop يتصل به ولا يشغّله نيابةً عنك. أبقِه قيد التشغيل عبر systemd/tmux/وما شابه، ليبقى يعمل بعد تسجيل الخروج وإعادة التشغيل. أما الـ gateway (Telegram/Discord/Slack/وغيرها) فهو عملية منفصلة طويلة التشغيل — شغّله بشكل مستقل إذا كنت تعتمد على قنوات المراسلة؛ وهو ليس ما يتصل به تطبيق سطح المكتب.

      لا يطرق فحص "remote backend is ready" في Desktop إلا GET /api/status، وهو endpoint عام — يستجيب بمجرد تشغيل أي لوحة تحكم على الجهاز. أما اتصال المحادثة المباشر فهو اتصال WebSocket منفصل إلى /api/ws (و /api/pty)، وهذا الاتصال محميّ بفحصين إضافيين لا يمسّهما فحص الحالة أبدًا:

      1. يجب أن تكون مُصادَقًا. عندما تُربَط لوحة التحكم على عنوان غير loopback، تُفعَّل بوابة المصادقة الخاصة بها. احمِها باسم مستخدم وكلمة مرور (عبر مزوّد اسم المستخدم/كلمة المرور المضمّن)؛ يسجّل Desktop الدخول مرة واحدة ويُعيد استخدام الجلسة الناتجة لاتصال WebSocket عبر تذكرة (ticket) صالحة لمرة واحدة. ودون مزوّد مُعدّ، ترفض لوحة التحكم المربوطة على عنوان غير loopback العمل عند بدء التشغيل.
      2. يجب أن يسمح عنوان الربط بالعميل وأن يطابق ترويسة Host. الربط على loopback (127.0.0.1) لا يقبل إلا عملاء loopback، لذا يُرفَض الجهاز البعيد على مستوى الـ socket بغض النظر عن بيانات الاعتماد. اربط على عنوان غير loopback (--host 0.0.0.0) كي يسمح حارس عنوان IP للطرف الآخر (peer-IP guard) بمرور العميل البعيد. ويجب أن يصل URL البعيد الذي تُدخله في Desktop إلى لوحة التحكم عبر اسم المضيف نفسه الذي رُبطت عليه — إذ يتطلب حارس DNS-rebinding تطابق ترويسة Host.

      إعداد لوحة التحكم البعيدة​

      اضبط اسم مستخدم وكلمة مرور، ثم شغّل لوحة التحكم مربوطةً على عنوان يمكن الوصول إليه. بالنسبة إلى خدمة systemd:

      [Service]
      EnvironmentFile=%h/.hermes/.env
      ExecStart=/path/to/venv/bin/python -m hermes_cli.main dashboard \
          --host 0.0.0.0 --port 9119 --no-open

      مع احتواء ~/.hermes/.env على:

      HERMES_DASHBOARD_BASIC_AUTH_USERNAME=admin
      HERMES_DASHBOARD_BASIC_AUTH_PASSWORD=choose-a-strong-password
      HERMES_DASHBOARD_BASIC_AUTH_SECRET=<32+ random bytes; openssl rand -base64 32>

      ثم أدخل في Desktop قيمة Remote URL (مثل http://VM_IP:9119) واضغط Sign in باستخدام اسم المستخدم وكلمة المرور تلك. راجع قسم مزوّد اسم المستخدم/كلمة المرور للاطلاع على جميع خيارات الإعداد.

      تحقّق من تفعيل بوابة المصادقة قبل إعادة المحاولة في Desktop

      من أي جهاز، تحقّق من أن لوحة التحكم تُعلن عن مزوّد اسم المستخدم/كلمة المرور:

      curl -s http://VM_IP:9119/api/status | jq '.auth_required, .auth_providers'
      # true
      # ["basic"]
      • auth_required: true مع وجود "basic" في قائمة المزوّدين → سيعمل مسار Sign in في Desktop.
      • auth_required: false → الربط على loopback، أو أن بوابة المصادقة لم تُفعَّل. اربط على عنوان غير loopback.
      • auth_required: true لكن دون مزوّد "basic" → متغيرات البيئة الخاصة باسم المستخدم/كلمة المرور لم تُحمَّل. أصلحها أولًا.

      إذا أظهر /api/status أن بوابة المصادقة مفعّلة مع المزوّد "basic" وظل Desktop مع ذلك يفشل في الاتصال بعد تسجيل الدخول، فالمشكلة تتجاوز الإعداد الأساسي — احصل على نسخة حديثة من desktop.log (Settings → Gateways → Open logs) إضافةً إلى سجلات لوحة التحكم من نافذة إعادة المحاولة نفسها، وابحث عن رمز إغلاق /api/ws (4403 = رفض حارس الطلبات لاتصال WS الخاص بالمحادثة، مثلًا بسبب عدم تطابق Host/peer؛ 4401 = فشل مصادقة تذكرة WS).

      الإعدادات (Config)​

      محرّر قائم على النماذج (forms) لملف config.yaml. تُكتشَف جميع حقول الإعدادات التي يزيد عددها على 150 حقلًا تلقائيًا من DEFAULT_CONFIG، وتُنظَّم في فئات موزّعة على تبويبات:

      • model — النموذج الافتراضي، والمزوّد، و base URL، وإعدادات الاستدلال (reasoning)
      • terminal — الـ backend (local/docker/ssh/modal)، والمهلة، وتفضيلات الـ shell
      • display — المظهر (skin)، وعرض تقدّم الأدوات، وعرض الاستئناف، وإعدادات مؤشر الانتظار (spinner)
      • agent — الحد الأقصى للتكرارات، ومهلة الـ gateway، وفئة الخدمة (service tier)
      • delegation — حدود الـ subagents، ومستوى جهد الاستدلال (reasoning effort)
      • memory — اختيار المزوّد، وإعدادات حقن السياق
      • approvals — وضع الموافقة على الأوامر الخطرة (smart/manual/off)
      • والمزيد — فلكل قسم في config.yaml حقول مقابلة في النموذج

      الحقول ذات القيم الصالحة المعروفة (terminal backend، والمظهر، ووضع الموافقة، وغيرها) تُعرض كقوائم منسدلة. والقيم المنطقية (Booleans) تُعرض كمفاتيح تبديل. وكل ما عدا ذلك يُعرض كحقل إدخال نصي.

      الإجراءات:

      • Save — يكتب التغييرات إلى config.yaml فورًا
      • Reset to defaults — يُعيد جميع الحقول إلى قيمها الافتراضية (دون حفظ إلى أن تنقر Save)
      • Export — ينزّل الإعدادات الحالية بصيغة JSON
      • Import — يرفع ملف إعدادات بصيغة JSON ليحلّ محل القيم الحالية
      نصيحة

      تسري تغييرات الإعدادات في جلسة الوكيل التالية أو عند إعادة تشغيل الـ gateway. تحرّر لوحة التحكم على الويب ملف config.yaml نفسه الذي يقرأ منه hermes config set والـ gateway.

      مفاتيح API (API Keys)​

      أدِر ملف .env الذي تُخزَّن فيه مفاتيح API وبيانات الاعتماد. تُجمَّع المفاتيح حسب الفئة:

      • LLM Providers — OpenRouter و Anthropic و OpenAI و DeepSeek وغيرها
      • Tool API Keys — Browserbase و Firecrawl و Tavily و Keenable و ElevenLabs وغيرها
      • Messaging Platforms — bot tokens لـ Telegram و Discord و Slack وغيرها
      • Agent Settings — متغيرات بيئة غير سرية مثل API_SERVER_ENABLED

      يعرض كل مفتاح:

      • ما إذا كان مضبوطًا حاليًا (مع معاينة محجوبة جزئيًا للقيمة)
      • وصفًا للغرض منه
      • رابطًا إلى صفحة التسجيل/المفاتيح لدى المزوّد
      • حقل إدخال لضبط القيمة أو تحديثها
      • زر حذف لإزالته

      المفاتيح المتقدمة/نادرة الاستخدام مخفية افتراضيًا خلف مفتاح تبديل.

      الجلسات (Sessions)​

      تصفّح جميع جلسات الوكيل وافحصها. يعرض كل صف عنوان الجلسة، وأيقونة منصة المصدر (CLI، Telegram، Discord، Slack، cron)، واسم النموذج، وعدد الرسائل، وعدد استدعاءات الأدوات، والمدة المنقضية منذ آخر نشاط. وتُميَّز الجلسات الحية بشارة نابضة.

      • التصفية — تحدّد تبويبات Chats / Automation / All نطاق القائمة: يعرض Chats (الافتراضي) المحادثات البشرية ويُخفي ضجيج الأتمتة (جلسات cron والأدوات و API و ACP)؛ ويعرض Automation تلك الجلسات فقط؛ ويعرض All كل شيء. وتضيّق قائمة منسدلة للمصدر الدقيق النتائج أكثر لتقتصر على قناة واحدة (مثل Telegram فقط). ويحترم البحث المرشّح النشط.
      • البحث — بحث نصي كامل في محتوى جميع الرسائل باستخدام FTS5. تعرض النتائج مقتطفات مع إبراز الكلمات المطابقة، وتنتقل تلقائيًا إلى أول رسالة مطابقة عند توسيع الجلسة.
      • الإحصاءات — يعرض شريط ملخّص إجمالي الجلسات، وعدد النشط منها في المخزن، وعدد المؤرشَف، وإجمالي الرسائل، وتفصيلًا حسب كل مصدر.
      • التوسيع — انقر جلسة لتحميل سجل رسائلها الكامل. تُلوَّن الرسائل حسب الدور (user، assistant، system، tool) وتُعرض بتنسيق Markdown مع تمييز الصياغة (syntax highlighting).
      • استدعاءات الأدوات — تعرض رسائل المساعد التي تتضمن استدعاءات أدوات كتلًا قابلة للطي تحتوي على اسم الدالة ووسائط JSON.
      • إعادة التسمية — اضبط عنوان الجلسة أو امسحه مباشرةً في مكانه (أيقونة القلم).
      • التصدير — نزّل الجلسة (البيانات الوصفية + سجل الرسائل الكامل) بصيغة JSON (أيقونة التنزيل).
      • التنظيف (Prune) — يحذف الزر "Prune old sessions" في الترويسة الجلسات المنتهية الأقدم من N يومًا.
      • الحذف — أزِل جلسة وسجل رسائلها باستخدام أيقونة سلة المهملات.

      السجلات (Logs)​

      اعرض ملفات سجلات الوكيل والـ gateway والأخطاء مع إمكانية التصفية والمتابعة المباشرة (live tailing).

      • File — للتبديل بين ملفات السجلات agent و errors و gateway
      • Level — للتصفية حسب مستوى السجل: ALL أو DEBUG أو INFO أو WARNING أو ERROR
      • Component — للتصفية حسب المكوّن المصدر: all أو gateway أو agent أو tools أو cli أو cron
      • Lines — لاختيار عدد الأسطر المعروضة (50 أو 100 أو 200 أو 500)
      • Auto-refresh — لتفعيل المتابعة المباشرة التي تستطلع أسطر السجل الجديدة كل 5 ثوانٍ أو تعطيلها
      • ترميز لوني — تُلوَّن أسطر السجل حسب الخطورة (الأحمر للأخطاء، والأصفر للتحذيرات، ولون باهت لرسائل التصحيح)

      التحليلات (Analytics)​

      تحليلات للاستخدام والتكلفة محسوبة من سجل الجلسات. اختر فترة زمنية (7 أو 30 أو 90 يومًا) لعرض:

      • بطاقات الملخّص — إجمالي الـ tokens (الإدخال/الإخراج)، ونسبة إصابة التخزين المؤقت (cache hit)، وإجمالي التكلفة التقديرية أو الفعلية، وإجمالي عدد الجلسات مع المتوسط اليومي
      • مخطط الـ tokens اليومي — مخطط أعمدة مكدّسة يعرض استهلاك tokens الإدخال والإخراج لكل يوم، مع تلميحات عند التمرير تعرض التفاصيل والتكلفة
      • جدول التفصيل اليومي — التاريخ، وعدد الجلسات، و tokens الإدخال، و tokens الإخراج، ومعدل إصابة التخزين المؤقت، والتكلفة لكل يوم
      • التفصيل حسب النموذج — جدول يعرض كل نموذج مُستخدَم، وعدد جلساته، واستهلاكه من الـ tokens، وتكلفته التقديرية

      Cron​

      أنشئ مهام cron المجدولة وأدِرها، وهي مهام تشغّل prompts للوكيل وفق جدول متكرر.

      • الإنشاء — املأ الاسم (اختياري)، والـ prompt، وتعبير cron (مثل 0 9 * * *)، ووجهة التسليم (local، أو Telegram، أو Discord، أو Slack، أو email)
      • قائمة المهام — تعرض كل مهمة اسمها، ومعاينة للـ prompt، وتعبير الجدولة، وشارة الحالة (enabled/paused/error)، ووجهة التسليم، ووقت آخر تشغيل، ووقت التشغيل التالي
      • الإيقاف المؤقت / الاستئناف — لتبديل المهمة بين الحالة النشطة والحالة الموقوفة مؤقتًا
      • التحرير — يفتح نافذة منبثقة معبّأة مسبقًا لتغيير الـ prompt الخاص بالمهمة، أو جدولها، أو اسمها، أو وجهة التسليم
      • Trigger now — ينفّذ المهمة فورًا خارج جدولها المعتاد
      • الحذف — يزيل مهمة cron نهائيًا

      Profiles​

      أنشئ profiles وأدِرها — وهي نُسخ معزولة من Hermes لكل منها إعداداتها ومهاراتها وجلساتها الخاصة.

      • بطاقات الـ Profiles — تعرض كل بطاقة النموذج/المزوّد، وعدد المهارات، وحالة الـ gateway، والوصف، والشارات (active، default، alias)
      • الإنشاء — الاسم + خيارات اختيارية: clone-from-default / clone-everything / no-bundled-skills، والوصف، والنموذج؛ وتوفّر صفحة Profile Builder المخصّصة (/profiles/new) المسار الكامل (النموذج، وخوادم MCP، والمهارات)
      • Manage skills & tools — ينقلك إلى صفحة Skills مقيّدةً بنطاق ذلك الـ profile (ويضبط مبدّل الـ profiles في الشريط الجانبي)
      • Set as active — يبدّل الـ profile الافتراضي الدائم الذي تعتمده عمليات تشغيل CLI/gateway المستقبلية (مثل hermes profile use). وهذا لا يغيّر ما تديره لوحة التحكم — فتلك مهمة مبدّل الـ profiles
      • تحرير النموذج / الوصف / SOUL — محرّرات مضمّنة في الصفحة تكتب إلى ذلك الـ profile
      • إعادة التسمية / الحذف — للـ profiles المُسمّاة فقط

      المهارات (Skills)​

      تصفّح المهارات و toolsets المثبّتة وابحث فيها وفعّلها أو عطّلها، وثبّت مهارات جديدة من الـ hub. تُحمَّل المهارات من ~/.hermes/skills/ وتُجمَّع حسب الفئة.

      • البحث — لتصفية المهارات و toolsets المثبّتة حسب الاسم أو الوصف أو الفئة
      • مرشّح الفئات — انقر أزرار الفئات لتضييق القائمة (مثل MLOps، MCP، Red Teaming، AI)
      • التبديل — فعّل مهارات بعينها أو عطّلها باستخدام مفتاح تبديل. تسري التغييرات في الجلسة التالية.
      • Toolsets — عرض منفصل يعرض الـ toolsets المدمجة (عمليات الملفات، وتصفّح الويب، وغيرها) مع حالتها النشطة/غير النشطة، ومتطلبات إعدادها، وقائمة الأدوات المضمّنة فيها
      • Browse hub — عرض ثالث يبحث في skill hub عبر جميع المصادر (مثل hermes skills search)، ويثبّت أي نتيجة حسب معرّفها مع سجل تثبيت مباشر، ويوفّر زر "Update all" لتحديث المهارات المثبّتة.

      MCP​

      أدِر خوادم MCP دون CLI. تعمل الصفحة على كتلة mcp_servers نفسها في config.yaml التي يقرأ منها hermes mcp.

      خوادم MCP الخاصة بك:

      • الإضافة — سجّل خادم HTTP/SSE (عبر URL) أو خادم stdio (أمر + وسائط)، مع متغيرات بيئة اختيارية بالصيغة KEY=VALUE لخوادم stdio
      • التفعيل / التعطيل — شغّل الخادم أو أوقفه دون حذفه. يبقى الخادم المعطّل في الإعدادات لتتمكن من إعادة تفعيله لاحقًا. ويسري التغيير عند إعادة تشغيل الـ gateway التالية.
      • الاختبار — يتصل بالخادم، ويعرض أدواته، ثم يقطع الاتصال — للتحقق من الاتصال قبل أن يعتمد عليه الوكيل
      • الإزالة — يحذف الخادم من الإعدادات
      • تُحجَب قيم متغيرات البيئة التي تبدو كأسرار في عرض القائمة

      الكتالوج: تصفّح خوادم MCP المعتمدة من Nous (كتالوج optional-mcps/ المضمّن) وثبّت أيًّا منها بنقرة واحدة. العناصر التي تحتاج إلى مفاتيح API تطلبها منك مباشرةً في الصفحة؛ وتُحفَظ القيم في .env. وهذا هو الكتالوج نفسه الذي يستخدمه hermes mcp catalog / hermes mcp install.

      Webhooks​

      أدِر اشتراكات webhook الديناميكية. يجب تفعيل منصة webhook في إعدادات المراسلة أولًا؛ وتعرض الصفحة تلميحًا عندما لا تكون مفعّلة.

      • الإنشاء — الاسم، والوصف، ومرشّح الأحداث، ووجهة التسليم، ووضع التسليم المباشر الاختياري، و prompt للوكيل. وعند الإنشاء تعرض الصفحة URL المسار (route) وسر HMAC الذي يظهر لمرة واحدة لتنسخه.
      • التفعيل / التعطيل — شغّل الاشتراك أو أوقفه. تبقى المسارات المعطّلة في ملف الاشتراكات، لكن الـ gateway يرفض أحداثها الواردة (403). ويُعيد الـ gateway تحميل الملف فوريًا (hot-reload)، لذا يسري التغيير مع الحدث التالي — دون الحاجة إلى إعادة التشغيل.
      • القائمة — يعرض كل اشتراك URL الخاص به، والأحداث، ووجهة التسليم
      • الحذف — يزيل الاشتراك

      الاقتران (Pairing)​

      وافق على مستخدمي المراسلة أو ألغِ صلاحياتهم دون CLI — وهي الطريقة التي يضيف بها المسؤول عن بُعد مستخدمي Telegram/Discord/وغيرهما إلى gateway مقترن. وتوفّر الصفحة تكافؤًا كاملًا مع hermes pairing.

      • الطلبات المعلّقة — يعرض كل طلب المنصة، والرمز، والمستخدم، وعمر الطلب، مع زر Approve
      • المستخدمون المعتمدون — يعرض كل منهم المنصة والمستخدم، مع زر Revoke
      • Clear pending — يحذف جميع رموز الاقتران المعلّقة

      القنوات (Channels)​

      اربط Hermes بأي منصة مراسلة من المتصفح — بتكافؤ كامل مع hermes setup gateway. تعرض الصفحة كل قناة مدعومة (Telegram، Discord، Slack، Matrix، Mattermost، WhatsApp، Signal، BlueBubbles/iMessage، Email، SMS/Twilio، DingTalk، Feishu/Lark، WeCom، WeChat، QQ Bot، Yuanbao، إضافةً إلى خادم API و webhook endpoints) مع حالة اتصالها المباشرة.

      • الضبط — يفتح نموذجًا خاصًا بكل منصة يحتوي تحديدًا على الحقول التي تحتاجها تلك القناة (bot token، و app token، و URL الخادم، وقائمة السماح، وغيرها). تُعرض الأسرار كحقول كلمات مرور وتُخزَّن محجوبة؛ وترك الحقل فارغًا يُبقي القيمة الحالية. وتُميَّز الحقول المطلوبة ويُتحقَّق من صحتها. ويشير رابط "Setup guide" إلى وثائق بيانات الاعتماد الخاصة بالمنصة.
      • التفعيل / التعطيل — شغّل القناة أو أوقفها. تبقى بيانات الاعتماد على القرص؛ ولا تتغير إلا حالة التفعيل.
      • الاختبار — يتحقق مما إذا كانت القناة مُعدّة ومفعّلة، وما إذا كان الـ gateway يُبلغ عن اتصال مباشر بها.
      • Restart gateway — تُكتب بيانات الاعتماد إلى ~/.hermes/.env وعلامة التفعيل إلى config.yaml؛ ويتصل الـ gateway بكل قناة مفعّلة عند إعادة تشغيله التالية، والتي يمكنك إطلاقها مباشرةً من الصفحة.

      النظام (System)​

      لوحة إدارة موحّدة للعمليات التي تشمل التثبيت بأكمله:

      • Host — إحصاءات النظام المباشرة: نظام التشغيل / النواة، والبنية، واسم المضيف، وإصدارا Python و Hermes، وعدد أنوية CPU + نسبة استخدامها، والذاكرة، واستخدام القرص لمجلد Hermes الرئيسي، ومدة التشغيل، ومتوسط الحِمل. (تأتي بيانات CPU/الذاكرة/القرص من psutil عند تثبيته؛ أما حقول التعريف فتظهر دائمًا.) ويعرض إصدار Hermes شارة حالة التحديث (up to date / N commits behind) وزر Check for updates. وعندما يتوفر تحديث في تثبيت عبر git، يفتح زر Update now مربع حوار للتأكيد — يوضّح عدد الـ commits التي ستسحبها — قبل تشغيل hermes update في الخلفية. أما في تثبيتات Docker/Nix فلا تستطيع لوحة التحكم تطبيق التحديث في مكانه، لذا تعرض بدلًا من ذلك الأمر الصحيح الذي يجب تنفيذه خارجها.
      • Nous Portal — حالة تسجيل الدخول، ومزوّد inference النشط، وجدول التوجيه في Tool Gateway (أي الأدوات تعمل عبر Portal وأيها تعمل محليًا)، مع رابط لإدارة اشتراكك. وهي نسخة للقراءة فقط مطابقة لـ hermes portal.
      • Skill curator — حالة صيانة المهارات في الخلفية (active / paused، والفاصل الزمني، وآخر تشغيل) مع إيقاف مؤقت/استئناف وزر للتشغيل الفوري. وهي مطابقة لـ hermes curator.
      • Gateway — تشغيل gateway المراسلة وإيقافه وإعادة تشغيله، مع الحالة المباشرة (قيد التشغيل/متوقف، و PID، والحالة)
      • Memory — اختر مزوّد الذاكرة الخارجي (أو المدمج فقط)، وأعِد تعيين مخزني الذاكرة المدمجين MEMORY.md / USER.md
      • Credential pool — أضف مفاتيح API الدوّارة التي يتناوب الوكيل على استخدامها (لكل مزوّد) أو أزِلها. تُحجَب المفاتيح في القائمة؛ ولا تصل القيمة الخام إلا إلى الوكيل.
      • Operations — شغّل doctor، أو تدقيقًا أمنيًا، أو أنشئ نسخة احتياطية، أو استعد من أرشيف نسخة احتياطية، أو حدّث المهارات، أو اعرض تفصيل حجم الـ system prompt، أو ولّد ملف تفريغ للدعم (support dump)، أو رحّل الإعدادات الخاصة بالخيارات المُلغاة. يُطلق كل منها إجراءً في الخلفية يُبَث سجله المباشر إلى الصفحة.
      • Checkpoints — اعرض حجم المخزن الظلّي (shadow store) الخاص بـ /rollback ونظّفه
      • Shell hooks — تعرض الـ hooks المُعدّة مع حالة الموافقة وقابلية التنفيذ لكل منها، وتتيح إنشاء hook (الحدث، والأمر، والمُطابِق (matcher)، والمهلة، مع منح موافقة اختيارية)، وإزالة hook. تشغّل الـ hooks أوامر عشوائية، لذا يتضمن نموذج الإنشاء تحذيرًا أمنيًا، ولا يُطلَق الـ hook إلا بعد منح الموافقة.

      تتضمن الاستجابة أيضًا كتلتين استشاريتين عن الموارد (لا تؤثران أبدًا في حكم السلامة components/overall):

      المصادقة (الوضع المحمي)​

      عندما تُربَط لوحة التحكم على عنوان عام أو غير loopback — أي عنوان غير 127.0.0.1 / localhost — يُفعّل Hermes Agent بوابة مصادقة (auth gate). يجب أن يحمل كل طلب ملف تعريف ارتباط (cookie) لجلسة مُتحقَّق منها، وإلا يُعاد توجيهه إلى صفحة تسجيل الدخول. وتأتي ثلاثة مزوّدين جاهزين مع التثبيت:

      • اسم المستخدم/كلمة المرور — أبسط طريقة لإضافة المصادقة إلى لوحة تحكم مستضافة ذاتيًا / داخل مقر المؤسسة (on-prem) / في مختبر منزلي. دون مزوّد هوية خارجي. لا تستخدمه إلا على شبكة موثوقة أو خلف VPN — وليس لإتاحة لوحة التحكم على الإنترنت العام.
      • OAuth (Nous Portal) — لعمليات النشر المستضافة وأي لوحة تحكم يمكن الوصول إليها عبر الإنترنت العام، وهو المسار الموصى به لاتصال Hermes Desktop البعيد. يُتحقَّق من كل عملية تسجيل دخول مقابل حسابك في Nous، لذا فهو المزوّد المناسب للاستخدام المُتاح على الإنترنت.
      • OIDC مستضاف ذاتيًا — لاستخدام مزوّد الهوية الخاص بك عبر معيار OpenID Connect (Keycloak، Auth0، Okta، Google، GitHub عبر جسر OIDC، وغيرها). دون أي دور لـ Nous Portal؛ ومناسب للإتاحة على الإنترنت العام عندما يكون خلف خادم OIDC متوافق مع المعيار.

      لوحات التحكم التي يملكها المشغّل والمربوطة على loopback لا تتأثر — فلا مصادقة ولا صفحة تسجيل دخول.

      متى تُفعَّل بوابة المصادقة​

      الخياراتبوابة المصادقةحالة الاستخدام
      hermes dashboard (الافتراضي — يُربَط على 127.0.0.1)معطّلةالتطوير المحلي
      hermes dashboard --host 0.0.0.0مفعّلةبعيد / بيئة الإنتاج — احمِها بمزوّد اسم المستخدم/كلمة المرور أو OAuth

      تكون بوابة المصادقة مفعّلة إذا وفقط إذا كان عنوان الربط غير 127.0.0.1 أو ::1 أو localhost. فالربط على 0.0.0.0 (أو أي عنوان RFC1918 / LAN) يُفعّل البوابة. والخيار القديم --insecure لم يعد يعطّلها — إذ يُقبَل للتوافق مع الإصدارات السابقة لكنه يُتجاهَل مع عرض تحذير.

      --insecure بلا تأثير — ولا يعطّل المصادقة

      منذ تعزيزات الأمان في يونيو 2026، لم يعد --insecure يتجاوز مصادقة لوحة التحكم: فالربط على عنوان غير loopback يتطلب دائمًا مزوّد مصادقة (مزوّد اسم المستخدم/كلمة المرور أو OAuth). وإذا أردت لوحة تحكم دون مصادقة، فاربطها على 127.0.0.1 وصِل إليها عبر نفق SSH أو Tailscale.

      سلوك الإغلاق عند الفشل (Fail-closed)​

      إذا كانت بوابة المصادقة ستُفعَّل لكن لم يُسجَّل أي DashboardAuthProvider (لا إضافة Nous ولا إضافة مخصّصة)، يرفض hermes dashboard الربط مع رسالة خطأ صريحة. لا يوجد سلوك احتياطي من نوع "default-deny but accept everything" — فلوحة التحكم المحمية ذات الإعداد الخاطئ لا تبدأ أبدًا.

      عندما تشغّل hermes dashboard --host 0.0.0.0 بشكل تفاعلي (في طرفية حقيقية) دون أن يكون أي مزوّد مُعدًّا بعد، لا يكتفي Hermes بالفشل — بل يعرض عليك إعداد مزوّد في الحال: اختر username & password (يكتب dashboard.basic_auth إلى config.yaml فتصبح لوحة التحكم قيد التشغيل خلال ثوانٍ) أو OAuth (يوجّهك إلى hermes dashboard register). أما الاستدعاءات غير التفاعلية — Docker/s6، و CI، والتشغيل عبر pipes — فتتخطى هذا السؤال وتصطدم بخطأ الإغلاق عند الفشل المذكور أعلاه، لذا لا يبدأ النشر غير المراقَب أبدًا دون مصادقة.

      المزوّد الافتراضي: Nous Research​

      الإضافة المضمّنة plugins/dashboard_auth/nous مثبّتة دائمًا وتُحمَّل تلقائيًا. وهي تسجّل تلقائيًا DashboardAuthProvider باسم nous عند إعداد معرّف عميل (client ID).

      لأن كل عملية تسجيل دخول يُتحقَّق منها مقابل Nous Portal وتحميها حسابك في Nous، فإن مزوّد Nous هو المناسب لإتاحة لوحة التحكم على الإنترنت العام.

      تسجيل لوحة تحكم​

      لاستخدام مزوّد Nous تحتاج إلى معرّف عميل OAuth (بالشكل agent:{id}). وهناك طريقتان للحصول عليه:

      • CLI — hermes dashboard register. شغّله على الجهاز الذي توجد عليه لوحة التحكم. يستخدم تسجيل دخولك الحالي إلى Nous (نفّذ hermes setup أولًا إن لم تكن مسجّلًا الدخول)، ويسجّل عميل OAuth مستضافًا ذاتيًا لدى Portal، ويكتب HERMES_DASHBOARD_OAUTH_CLIENT_ID إلى ~/.hermes/.env نيابةً عنك. الخيارات الاختيارية: --name (تسمية مقروءة للبشر، وإلا تُولَّد تلقائيًا) و --redirect-uri (URL رد اتصال (callback) عام عبر HTTPS لجهاز مُتاح على الإنترنت).

        hermes dashboard register
        # ✓ Registered dashboard "swift_falcon"
        # …writes HERMES_DASHBOARD_OAUTH_CLIENT_ID to ~/.hermes/.env

      • GUI — صفحة Local Dashboards. افتح /local-dashboards في Nous Portal لتسجيل لوحات التحكم المستضافة ذاتيًا وتسميتها وإدارتها وإلغائها من المتصفح. انسخ معرّف العميل الناتج agent:{id} إلى HERMES_DASHBOARD_OAUTH_CLIENT_ID (متغير بيئة) أو dashboard.oauth.client_id (في config.yaml). وهذا أيضًا المكان الذي تُلغي منه لوحة تحكم سُجّلت عبر CLI.

      الإعدادات​

      تقرأ الإضافة من مصدرين، وتكون الأولوية لمتغير البيئة عندما يُضبط بقيمة غير فارغة:

      config.yaml — المصدر المعتمد:

      dashboard:
        oauth:
          client_id: agent:01HXYZ…             # required to engage the gate

      متغيرات البيئة — تجاوزات يضبطها المشغّل:

      متغير البيئةيتجاوزالصيغةيُوفَّر بواسطة
      HERMES_DASHBOARD_OAUTH_CLIENT_IDdashboard.oauth.client_idagent:{instance_id}hermes dashboard register

      وفقًا لاصطلاح Hermes Agent (الملف ~/.hermes/.env مخصّص لمفاتيح API / الأسرار فقط)، فإن config.yaml هو المكان الموصى به لضبط هذه القيم في التطوير المحلي، وفي بيئات on-prem، وفي أي نشر تتحكم فيه مباشرةً. أما مسار متغيرات البيئة فموجود كي تتمكن آلية حقن الأسرار في منصة الاستضافة من تمرير قيم client_id خاصة بكل نشر دون أن يضطر أحد إلى تحرير config.yaml داخل الصورة (image) — وهذا هو غرضه الأساسي.

      تُعامَل قيم متغيرات البيئة الفارغة كأنها غير مضبوطة، لذا لا يمكن لسرٍّ في المنصة جرى توفيره دون تعبئته أن يحجب عن طريق الخطأ إدخالًا صالحًا في config.yaml.

      إذا لم يوفّر أيٌّ من المصدرين قيمة client_id، تُبلغ الإضافة عن السبب المحدد، ويخبرك خطأ الربط الناتج عن الإغلاق عند الفشل في لوحة التحكم بما يجب إصلاحه تحديدًا:

      Refusing to bind dashboard to 0.0.0.0 — the auth gate engages on
      non-loopback binds, but no auth providers are registered.

      Bundled providers reported these issues:
        • nous: HERMES_DASHBOARD_OAUTH_CLIENT_ID is not set (and
          dashboard.oauth.client_id in config.yaml is empty). …

      Configure an auth provider before exposing the dashboard:
        • Password: set dashboard.basic_auth.username + password_hash in config.yaml
        • OAuth: run `hermes dashboard register` (Nous Portal) or install a
          DashboardAuthProvider plugin.
      There is no unauthenticated public-bind option — to keep it local, bind
      127.0.0.1 and tunnel in (SSH / Tailscale).

      مثال تطبيقي: Nous Research​

      من تثبيت Hermes مسجّل الدخول إلى لوحة تحكم محمية بـ Nous في ثلاث خطوات.

      1. سجّل الدخول وسجّل لوحة التحكم. يستخدم hermes dashboard register تسجيل دخولك الحالي إلى Nous لتوفير عميل OAuth، ويكتب HERMES_DASHBOARD_OAUTH_CLIENT_ID إلى ~/.hermes/.env نيابةً عنك:

      hermes setup            # if you're not already logged into Nous Portal
      hermes dashboard register
      # ✓ Registered dashboard "swift_falcon"
      # …writes HERMES_DASHBOARD_OAUTH_CLIENT_ID to ~/.hermes/.env

      2. شغّل لوحة التحكم على عنوان يمكن الوصول إليه. الربط على عنوان غير loopback يُفعّل بوابة OAuth، وقيمة client_id التي كُتبت للتو تُفعّل المزوّد nous:

      hermes dashboard --host 0.0.0.0 --port 9119 --no-open

      3. سجّل الدخول. افتح http://<host>:9119/، وسيُعاد توجيهك إلى /login. انقر Sign in with Nous Research → صادِق في Portal → ستعود إلى لوحة التحكم بعد المصادقة. تحقّق من بوابة المصادقة من أي جهاز:

      curl -s http://<host>:9119/api/status | jq '.auth_required, .auth_providers'
      # true
      # ["nous"]

      بعد ذلك يُعيد GET /api/auth/me الجلسة المُتحقَّق منها (provider: nous). ولجهاز مُتاح على الإنترنت، سجّل باستخدام --redirect-uri https://hermes.example.com/auth/callback واضبط HERMES_DASHBOARD_PUBLIC_URL كي يُحال رد اتصال OAuth إلى URL العام الخاص بك (راجع تجاوز Public URL).

      مزوّد اسم المستخدم/كلمة المرور (دون OAuth IDP)​

      إذا كنت لا تريد ربط مزوّد هوية OAuth — في نشر مستضاف ذاتيًا من نوع "just put a password on my dashboard" — فإن الإضافة المضمّنة plugins/dashboard_auth/basic تسجّل DashboardAuthProvider باسم basic يصادق باستخدام اسم مستخدم وكلمة مرور بدلًا من إعادة توجيه OAuth.

      يتصل هذا المزوّد ببوابة المصادقة نفسها التي يستخدمها مزوّد OAuth: إذ تُفعَّل البوابة عند الربط على عنوان غير loopback، وتعرض صفحة تسجيل الدخول نموذج بيانات اعتماد لهذا المزوّد (بدلًا من زر "Log in with X")، وكل ما يلي تسجيل الدخول — ملفات تعريف ارتباط الجلسة، والتحديث الشفاف، وتذاكر WS، وتسجيل الخروج، وسجل التدقيق — مطابق لمسار OAuth. الجلسات عبارة عن tokens عديمة الحالة موقّعة بـ HMAC يُصدرها المزوّد بنفسه، لذا لا توجد قاعدة بيانات ولا IDP خارجي. ويستخدم تجزئة كلمات المرور scrypt من المكتبة القياسية (دون أي اعتمادية من طرف ثالث).

      استخدمه على الشبكات الموثوقة فقط — وليس على الإنترنت العام

      مزوّد اسم المستخدم/كلمة المرور مخصّص للوحات التحكم المستضافة ذاتيًا / داخل مقر المؤسسة / في المختبرات المنزلية على شبكة موثوقة، أو التي لا يمكن الوصول إليها إلا عبر VPN. فهو يحمي بيانات اعتماد مشتركة واحدة دون مزوّد هوية خارجي أو MFA أو حسابات لكل مستخدم، لذا فهو غير مناسب لإتاحة لوحة التحكم مباشرةً على الإنترنت العام. ولوحة تحكم مُتاحة على الإنترنت، استخدم بدلًا من ذلك مزوّد Nous Research (أو مزوّد OIDC مستضافًا ذاتيًا / OAuth مخصّصًا خاصًا بك).

      الإعدادات​

      كما هو الحال مع مزوّد Nous، يقرأ هذا المزوّد من config.yaml (المصدر المعتمد) مع إعطاء الأولوية لمتغيرات البيئة عند ضبطها بقيم غير فارغة. ولا يُفعَّل إلا عند إعداد username مع password_hash (المفضّل) أو password — وإلا فلا تأثير له، لذا لا يتأثر مستخدمو OAuth ولا المشغّلون على loopback.

      config.yaml:

      dashboard:
        basic_auth:
          username: admin
          # Preferred — no plaintext at rest. Compute with:
          #   python -c "from plugins.dashboard_auth.basic import hash_password; print(hash_password('PW'))"
          password_hash: "scrypt$16384$8$1$…$…"
          # ...or a plaintext password (hashed in-memory at load; less safe at rest):
          # password: "s3cret"
          secret: "<32+ random bytes, base64 or hex>"  # token-signing key
          session_ttl_seconds: 43200                    # optional; access-token lifetime (default 12h)

      تجاوزات متغيرات البيئة:

      متغير البيئةيتجاوزملاحظات
      HERMES_DASHBOARD_BASIC_AUTH_USERNAMEdashboard.basic_auth.usernameمطلوب للتفعيل
      HERMES_DASHBOARD_BASIC_AUTH_PASSWORD_HASHdashboard.basic_auth.password_hashالمفضّل (لا نص صريح مخزّن)
      HERMES_DASHBOARD_BASIC_AUTH_PASSWORDdashboard.basic_auth.passwordنص صريح؛ يتقدّم على password_hash المضبوط في الإعدادات لتتمكن من تدوير كلمة المرور عبر env
      HERMES_DASHBOARD_BASIC_AUTH_SECRETdashboard.basic_auth.secretمفتاح توقيع الـ tokens
      HERMES_DASHBOARD_BASIC_AUTH_TTL_SECONDSdashboard.basic_auth.session_ttl_secondsمدة صلاحية access token
      اضبط قيمة secret صريحة للحصول على جلسات مستقرة

      عندما تكون secret فارغة، يُولَّد مفتاح توقيع عشوائي لكل عملية. وهذا مقبول لعملية واحدة، لكنه يعني أن كل الجلسات تُبطَل عند إعادة التشغيل وأن الجلسات لا تمتد عبر عدة workers. اضبط قيمة secret صريحة لعمليات النشر التي يجب أن تصمد أمام إعادة التشغيل / متعددة الـ workers.

      يخضع endpoint /auth/password-login لحدّ المعدل (rate limit) لكل عنوان IP للعميل (افتراضيًا 10 محاولات/دقيقة → HTTP 429)، ويُعيد استجابة عامة واحدة 401 Invalid credentials سواء كان المستخدم غير معروف أو كانت كلمة المرور خاطئة، لذا لا يمكن استخدامه وسيلةً لتعداد أسماء المستخدمين.

      مثال تطبيقي: اسم المستخدم/كلمة المرور​

      من الصفر إلى لوحة تحكم محمية بكلمة مرور على شبكة موثوقة في ثلاث خطوات.

      1. اضبط بيانات الاعتماد في ~/.hermes/.env. احسب تجزئة (hash) كلمة المرور حتى لا يُخزَّن أي نص صريح، واضبط سر توقيع ثابتًا كي تصمد الجلسات أمام إعادة التشغيل:

      # Compute a scrypt hash of your chosen password:
      HASH=$(python -c "from plugins.dashboard_auth.basic import hash_password; print(hash_password('choose-a-strong-password'))")

      cat >> ~/.hermes/.env <<EOF
      HERMES_DASHBOARD_BASIC_AUTH_USERNAME=admin
      HERMES_DASHBOARD_BASIC_AUTH_PASSWORD_HASH=$HASH
      HERMES_DASHBOARD_BASIC_AUTH_SECRET=$(openssl rand -base64 32)
      EOF
      chmod 600 ~/.hermes/.env

      2. شغّل لوحة التحكم على عنوان يمكن الوصول إليه. الربط على عنوان غير loopback يُفعّل بوابة المصادقة، واسم المستخدم + التجزئة يُفعّلان المزوّد basic:

      hermes dashboard --host 0.0.0.0 --port 9119 --no-open

      3. سجّل الدخول. افتح http://<host>:9119/، وسيُعاد توجيهك إلى /login — وهي نموذج بيانات اعتماد (لا زر "Sign in with X"). أدخل admin / كلمة مرورك → ستصل إلى لوحة التحكم بعد المصادقة. تحقّق من بوابة المصادقة من أي جهاز:

      curl -s http://<host>:9119/api/status | jq '.auth_required, .auth_providers'
      # true
      # ["basic"]

      بعد ذلك يُعيد GET /api/auth/me الجلسة المُتحقَّق منها (provider: basic). أبقِ هذا الإعداد خلف VPN — راجع التحذير أعلاه؛ ولجهاز عام استخدم بدلًا من ذلك مزوّد Nous Research أو مزوّد OIDC المستضاف ذاتيًا.

      كتابة مزوّد كلمات مرور خاص بك​

      ليس basic إلا تطبيقًا واحدًا لنقطة توسعة. إذ يمكن لأي إضافة تسجيل مزوّد كلمات مرور: اضبط supports_password = True في صنفك الفرعي المشتق من DashboardAuthProvider ونفّذ complete_password_login(*, username, password) -> Session (أطلق InvalidCredentialsError عند الرفض، و ProviderError إذا كان مخزن البيانات الخلفي متوقفًا). ويمكن ترك دالتي OAuth start_login / complete_login كبدائل تُطلق NotImplementedError في مزوّد يعتمد على كلمات المرور فقط. هذا هو المسار المناسب لـ LDAP-bind، أو قاعدة بيانات لبيانات الاعتماد، أو أي مخطط مصادقة آخر لا يعتمد على إعادة التوجيه — ويتولى إطار العمل النموذج، والمسار (route)، وملفات تعريف الارتباط، والتحديث نيابةً عنك.

      مزوّد OIDC مستضاف ذاتيًا​

      إذا كنت تشغّل مزوّد هوية خاصًا بك، فإن الإضافة المضمّنة plugins/dashboard_auth/self_hosted تصادق لوحة التحكم مقابله باستخدام معيار OpenID Connect — دون كود خاص بكل IDP، ودون أي دور لـ Nous Portal. وقد جرى التحقق منها وهي تعمل مع أي خادم OIDC متوافق مع المعيار:

      Authentik · Keycloak · Zitadel · Authelia · Auth0 · Okta · Google · …

      كما هو الحال مع مزوّد Nous، تُحمَّل تلقائيًا ولا تسجّل نفسها إلا بعد إعدادها، لذا لا تأثير لها في لوحات التحكم المربوطة على loopback.

      الإعدادات​

      اضبط issuer و client_id (عميل PKCE عام — دون client secret). تجلب الإضافة قيم authorization_endpoint و token_endpoint و jwks_uri الخاصة بالـ IDP من {issuer}/.well-known/openid-configuration، لذا لن تحتاج أبدًا إلى تثبيت عناوين endpoints يدويًا في الكود.

      config.yaml — المصدر المعتمد:

      dashboard:
        oauth:
          provider: self-hosted
          self_hosted:
            issuer: https://auth.example.com/application/o/hermes/   # required
            client_id: hermes-dashboard                              # required
            scopes: "openid profile email"                           # optional (this is the default)

      متغيرات البيئة — تجاوزات يضبطها المشغّل (تتقدّم env على config.yaml عند ضبطها بقيمة غير فارغة؛ وتُعامَل القيمة الفارغة كأنها غير مضبوطة):

      متغير البيئةيتجاوزملاحظات
      HERMES_DASHBOARD_OIDC_ISSUERdashboard.oauth.self_hosted.issuerURL الخاص بـ OIDC issuer — مطلوب
      HERMES_DASHBOARD_OIDC_CLIENT_IDdashboard.oauth.self_hosted.client_idمعرّف العميل العام — مطلوب
      HERMES_DASHBOARD_OIDC_SCOPESdashboard.oauth.self_hosted.scopesالقيمة الافتراضية openid profile email

      في الـ IDP الخاص بك، سجّل تطبيقًا/عميلًا عامًا مع منح authorization-code + PKCE (S256)، وأضف رد اتصال لوحة التحكم كـ redirect URI مسموح به. رد الاتصال هو <dashboard public URL>/auth/callback (راجع تجاوز Public URL لمعرفة كيف تستنتج لوحة التحكم URL العام الخاص بها خلف proxy).

      ما الذي يتحقق منه​

      يتحقق المزوّد من ID token الخاص بـ OpenID Connect (RS256/ES256) مقابل jwks_uri المُكتشَف، مع تقييد الـ claims iss و aud بقيمتي issuer و client_id المُعدّتين لديك. وتُربط الـ claims القياسية في OIDC بجلسة لوحة التحكم على النحو التالي:

      حقل الجلسةالـ Claim(s)
      user_idsub (مطلوب)
      emailemail
      display_namename → preferred_username → nickname → email
      org_idorg_id / organization، وإلا فقيم groups مدموجة

      الـ ID token هو ما يُثبت الهوية — أما access token فيُعامَل كقيمة معتمة (opaque) (إذ لا تشترط مواصفات OIDC أن يكون JWT). ويُشترط أن تكون عناوين endpoints عبر HTTPS (يُسمح بـ http:// على loopback لمزوّدي الهوية في التطوير المحلي)، ويجب أن تطابق قيمة issuer المُعلنة في مستند الاكتشاف القيمةَ المُعدّة لديك (يُتسامَح مع اختلاف الشرطة المائلة في النهاية). وتُستخدم refresh tokens، عندما يُصدرها الـ IDP، لإعادة المصادقة بصمت عبر منح refresh_token القياسي؛ ويستدعي تسجيل الخروج revocation_endpoint الخاص بالـ IDP وفق RFC 7009 عندما يكون مُعلَنًا.

      العملاء السريّون (Confidential clients) (أي التي لديها client_secret) غير مدعومين بعد — اضبط عميلًا عامًا + PKCE، وهو الخيار المعتاد للوحة تحكم تعمل في المتصفح.

      مثال تطبيقي: Keycloak​

      يُعد Keycloak من أسهل خوادم OIDC المستضافة ذاتيًا في التشغيل لاختبار محلي — إذ يعمل كحاوية واحدة في وضع التطوير (مع قاعدة بيانات في الذاكرة) ويوفّر اكتشاف OIDC نموذجيًا. يأخذك هذا الشرح من الصفر إلى تسجيل دخول يعمل في لوحة التحكم خلال دقائق.

      1. شغّل Keycloak مع realm مُعدّ مسبقًا. احفظ ملف تصدير الـ realm هذا باسم realm-hermes.json — فهو يعرّف realm باسم hermes، وعميل PKCE عامًا (hermes-dashboard)، ومستخدمًا تجريبيًا، ويُستورد كل ذلك عند الإقلاع فلا حاجة إلى النقر على أي شيء في واجهة الإدارة:

      {
        "realm": "hermes",
        "enabled": true,
        "clients": [
          {
            "clientId": "hermes-dashboard",
            "name": "Hermes Agent Dashboard",
            "enabled": true,
            "publicClient": true,
            "standardFlowEnabled": true,
            "protocol": "openid-connect",
            "redirectUris": ["http://localhost:9119/auth/callback"],
            "webOrigins": ["http://localhost:9119"],
            "attributes": { "pkce.code.challenge.method": "S256" }
          }
        ],
        "users": [
          {
            "username": "testuser",
            "enabled": true,
            "emailVerified": true,
            "email": "testuser@example.com",
            "firstName": "Test",
            "lastName": "User",
            "credentials": [
              { "type": "password", "value": "testpassword", "temporary": false }
            ]
          }
        ]
      }

      شغّله (Keycloak 26 أو أحدث)، مع ربط ذلك الملف بمجلد الاستيراد:

      docker run --rm -p 8080:8080 \
        -e KC_BOOTSTRAP_ADMIN_USERNAME=admin \
        -e KC_BOOTSTRAP_ADMIN_PASSWORD=admin \
        -v "$PWD/realm-hermes.json:/opt/keycloak/data/import/realm-hermes.json:ro" \
        quay.io/keycloak/keycloak:26.0 \
        start-dev --import-realm

      بمجرد تشغيله، يُعلن الـ realm عن اكتشاف OIDC القياسي على http://localhost:8080/realms/hermes/.well-known/openid-configuration (والـ issuer هو http://localhost:8080/realms/hermes). وتوجد وحدة تحكم الإدارة على http://localhost:8080/ (admin / admin).

      2. وجّه لوحة التحكم إليه. تسمح الإضافة المستضافة ذاتيًا بـ issuer يستخدم http:// على loopback (بينما يُشترط HTTPS لأي issuer غير loopback)، لذا يعمل Keycloak المحلي كما هو:

      export HERMES_DASHBOARD_OIDC_ISSUER="http://localhost:8080/realms/hermes"
      export HERMES_DASHBOARD_OIDC_CLIENT_ID="hermes-dashboard"
      export HERMES_DASHBOARD_PUBLIC_URL="http://localhost:9119"
      hermes dashboard --host 0.0.0.0 --port 9119 --no-open

      يُخبر HERMES_DASHBOARD_PUBLIC_URL لوحة التحكم بأن رد اتصال OAuth الخاص بها هو http://localhost:9119/auth/callback — وهو redirect URI الذي سجّله الـ realm أعلاه. والربط على 0.0.0.0 (ربط غير loopback) هو ما يُفعّل بوابة OAuth.

      3. سجّل الدخول. افتح http://localhost:9119/، وسيُعاد توجيهك إلى /login. انقر Sign in with Self-Hosted OIDC → صادِق في Keycloak باسم testuser / testpassword → ستعود إلى لوحة التحكم بعد المصادقة. يعرض الشريط الجانبي Logged in as Test User via self-hosted، ويُعيد GET /api/auth/me الجلسة المُتحقَّق منها (provider: self-hosted، email: testuser@example.com).

      إذا ربطت لوحة التحكم أو تصفّحتها على مضيف/منفذ مختلف، فأضف …/auth/callback الخاص بذلك الأصل (origin) إلى Valid redirect URIs الخاصة بالعميل في وحدة تحكم إدارة Keycloak (Clients → hermes-dashboard → Settings). ويعمل النمط نفسه مع Authentik و Zitadel و Authelia وخوادم OIDC الأخرى — ولا يختلف سوى URL الخاص بالـ issuer وواجهة تسجيل العميل.

      تجاوز Public URL​

      افتراضيًا، تعيد لوحة التحكم بناء URL رد اتصال OAuth من الطلب — X-Forwarded-Host + X-Forwarded-Proto + X-Forwarded-Prefix (عندما يكون uvicorn مُعدًّا باستخدام proxy_headers=True، وهو ما يفعّله start_server عند تفعيل بوابة المصادقة). ويعمل هذا مباشرةً دون إعداد إضافي خلف reverse proxy يضبط الترويسات الثلاث جميعها بشكل صحيح.

      لعمليات النشر خلف reverse proxies لا تمرّر تلك الترويسات بشكل موثوق (إعدادات nginx اليدوية، و ingresses داخل مقر المؤسسة، وعمليات النشر على نطاقات مخصّصة مع سلاسل proxy جزئية)، اضبط dashboard.public_url (أو HERMES_DASHBOARD_PUBLIC_URL) على URL العام الكامل الذي يُوصَل من خلاله إلى لوحة التحكم:

      dashboard:
        public_url: "https://dashboard.example.com/hermes"
        trusted_proxies:
          - "172.20.0.5"

      عند ضبطه، يصبح URL رد اتصال OAuth هو <public_url>/auth/callback حرفيًا — ويُتجاهَل X-Forwarded-Prefix في ذلك المسار البرمجي لأن المشغّل صرّح بالـ URL العام صراحةً. وهذا مقصود: فإضافة البادئة فوقه ستُكرّر البادئة في الحالة الشائعة التي تكون فيها البادئة مُضمّنة أصلًا في public_url.

      يُقبَل اسم المضيف الوارد في public_url أيضًا كقيمة مطابقة تمامًا لترويسة HTTP Host ولقيمة WebSocket Origin. ويدعم هذا reverse proxy يحافظ على اسم المضيف الظاهر للمتصفح بينما يمرّر الطلبات إلى لوحة تحكم مربوطة على 127.0.0.1. ولا يُسمح بأحرف البدل (wildcards) ولا بمطابقة اللواحق، لذا يظل مضيف مهاجم مثل dashboard.example.com.evil.test مرفوضًا من قِبل حارس DNS-rebinding.

      التصريح بقيمة public_url غير loopback يُفعّل دائمًا بوابة مصادقة لوحة التحكم، حتى عندما يكون الـ backend مربوطًا على loopback. اضبط مزوّد كلمة مرور أو OAuth أولًا؛ فبدونه يرفض Hermes العمل عند بدء التشغيل (fail closed). ويمنع هذا تحوّل session token الخاص بالـ SPA المحلي إلى آلية مصادقة عن بُعد عبر الـ proxy. كما يفعّل Uvicorn معالجة ترويسات الـ proxy في هذا الوضع. وتُعدّ proxies الـ loopback موثوقة تلقائيًا. وإذا كان منهي TLS (TLS terminator) يتصل من حاوية أو جهاز آخر، فأضف عنوان IP الدقيق الخاص به إلى dashboard.trusted_proxies، أو أضف نطاق CIDR محدودًا لشبكة proxy مخصّصة عندما يكون العنوان ديناميكيًا:

      dashboard:
        public_url: "https://dashboard.example.com/hermes"
        trusted_proxies:
          - "172.20.0.0/24"

      لا يحق إلا للأطراف المُدرجة تمرير X-Forwarded-Proto و X-Forwarded-For. ويحافظ Hermes دائمًا على الثقة في loopback ويرفض * و 0.0.0.0/0 و ::/0. والثقة في شبكة ما تعني أن كل حاوية أو جهاز على تلك الشبكة يستطيع تمرير بيانات التوجيه الوصفية، لذا فضّل عنوان IP دقيقًا للـ proxy أو شبكة مخصّصة للـ proxy وحده.

      # Backend remains reachable only on this machine.
      hermes dashboard --host 127.0.0.1 --port 9119 --no-open

      وجّه TLS reverse proxy إلى http://127.0.0.1:9119 واستخدم الأصل الخارجي نفسه في dashboard.public_url.

      يُعد Tailscale Serve مثالًا على هذا الشكل من النشر: إذ يمكنه إنهاء HTTPS المقتصر على الـ tailnet على اسم مضيف https://<machine>.<tailnet>.ts.net مع تمرير الطلبات إلى لوحة التحكم على loopback. استخدم أصل HTTPS هذا بعينه كقيمة لـ dashboard.public_url. ولا يزال يُعامَل كأصل غير loopback ظاهر للمتصفح، وبالتالي يتطلب مزوّد مصادقة للوحة التحكم؛ لكن هذا لا يستلزم جعل الخدمة قابلة للوصول من الإنترنت العام.

      ترتيب الأولوية نفسه المتّبع في إعدادات لوحة التحكم الأخرى — تتقدّم env على config.yaml:

      المصدرمسار التجاوزمتى تستخدمه
      dashboard.public_url في config.yamlHERMES_DASHBOARD_PUBLIC_URLالتطوير المحلي / on-prem (المصدر المعتمد)

      (غير مضبوط)—الافتراضي — إعادة البناء من ترويسات X-Forwarded-*

      يرفض التحقق القيم التي لا تحتوي على المخطط http:// / https://، أو لا تحتوي على مضيف، أو تحتوي على علامات اقتباس / أقواس زاوية / مسافات بيضاء / أحرف تحكم. وتنتقل القيمة غير الصالحة بصمت إلى إعادة البناء من الترويسات، كي يستمر مسار تسجيل الدخول في العمل بدلًا من إرسال المستخدم إلى URL معادٍ.

      ملاحظة: لا يتجاوز public_url إلا URL رد اتصال OAuth. أما علامة ملف تعريف الارتباط Secure فلا يزال يتحكم فيها request.url.scheme، مع استخدام X-Forwarded-Proto فقط عندما يكون الطرف المتصل على loopback أو مُدرجًا في trusted_proxies. اقرن public_url ذا HTTPS بإنهاء TLS وإدخال محدود للـ proxy الموثوق عندما لا يكون الـ proxy على loopback.

      تدفّق OAuth​

      يطبّق المزوّد عقد OAuth الخاص بـ Nous Portal، الإصدار v1 — منح authorization-code مع PKCE (S256):

      1. يطلب المستخدم / دون cookie للجلسة → تعيد بوابة المصادقة توجيهه إلى /login.
      2. تعرض صفحة تسجيل الدخول زر "Continue with Nous Research" → /auth/login?provider=nous.
      3. يخزّن الخادم حالة PKCE في cookie قصير العمر، ويعيد توجيه المستخدم إلى https://portal.nousresearch.com/oauth/authorize?….
      4. يصادق المستخدم لدى Portal، ثم يصل إلى /auth/callback?code=…&state=….
      5. يستبدل الخادم الرمز (code) بـ access token عبر POST /api/oauth/token، ويتحقق من توقيع JWT مقابل JWKS الخاص بـ Portal (/.well-known/jwks.json)، ويضبط ملف تعريف الارتباط hermes_session_at.
      6. يُعاد توجيه المستخدم إلى / (أو إلى مسار الرابط العميق الأصلي عبر معامل الاستعلام next=).

      مدة صلاحية access tokens هي 15 دقيقة. لا يوجد refresh token في الإصدار v1 من العقد — فعند انتهاء صلاحية الـ token، يكتشف غلاف fetch في الـ SPA استجابة 401 وينتقل بتحميل صفحة كامل عائدًا إلى /login لإعادة تشغيل التدفّق.

      تسجيل الخروج​

      يعرض عنصر الشريط الجانبي Logged in as <user_id…> via nous مع أيقونة تسجيل الخروج. والنقر عليها يرسل طلب POST إلى /auth/logout، الذي يمسح جميع ملفات تعريف الارتباط الخاصة بمصادقة لوحة التحكم ويعيد التوجيه إلى /login.

      سجل التدقيق​

      تُكتب كل بداية تسجيل دخول، وكل نجاح، وكل فشل، وكل فشل في التحقق من الجلسة كسطر JSON في $HERMES_HOME/logs/dashboard-auth.log. وتُحجَب الحقول الحساسة (access_token، و refresh_token، و code، و code_verifier، و state، وترويسة Authorization) قبل التسجيل.

      المزوّدون المخصّصون​

      لربط مزوّد OAuth غير Nous (مثل Google أو GitHub أو OIDC مخصّص)، أنشئ إضافة تسجّل DashboardAuthProvider:

      # ~/.hermes/plugins/dashboard-auth-myidp/__init__.py
      from hermes_cli.dashboard_auth import DashboardAuthProvider, Session, LoginStart

      class MyIdPProvider(DashboardAuthProvider):
          name = "myidp"
          display_name = "My Identity Provider"

          def start_login(self, *, redirect_uri): ...
          def complete_login(self, *, code, state, code_verifier, redirect_uri): ...
          def verify_session(self, *, access_token): ...
          def refresh_session(self, *, refresh_token): ...
          def revoke_session(self, *, refresh_token): ...

      def register(ctx):
          ctx.register_dashboard_auth_provider(MyIdPProvider())

      تعرض صفحة تسجيل الدخول جميع المزوّدين المسجّلين؛ ويمكن الجمع بين عدة مزوّدين، ويختار المستخدم أحدهم في /login.

      المصادقة غير التفاعلية (bearer token)​

      إلى جانب تسجيل الدخول التفاعلي للبشر (ملفات تعريف ارتباط الجلسة + التحديث)، يدعم الصنف المجرّد (ABC) DashboardAuthProvider قدرةً غير تفاعلية، من خدمة إلى خدمة عبر supports_token = True + verify_token(token=...). وعندما يختار مزوّدٌ تفعيلها، يُتحقَّق من ترويسة Authorization: Bearer <token> الواردة، وعند النجاح يُرفَق TokenPrincipal بالطلب (request.state.token_principal) للـ endpoints التي يحدّدها ذلك المزوّد على أنها قابلة للمصادقة بالـ token — دون cookie، ودون إعادة توجيه، ودون تحديث.

      أول مستهلك مضمّن لهذه القدرة هو المزوّد drain (plugins/dashboard_auth/drain): إذ يوفّر nous-account-service سرًا خاصًا بكل وكيل عبر HERMES_DASHBOARD_DRAIN_SECRET، ويتحقق المزوّد من bearer tokens الواردة مقابله بمقارنة ثابتة الزمن، ويسجّل /api/gateway/drain على أنه قابل للمصادقة بالـ token. وهو يُغلق عند الفشل — فالسر الضعيف/القصير (< 256 بت) يُرفض عند التسجيل ويبقى الـ endpoint معطّلًا؛ ولا تأثير له عندما لا يكون متغير البيئة مضبوطًا. وتوجد خيارات ضبط السلوك (scope، min_secret_chars) تحت dashboard.drain_auth في config.yaml.

      يمكن للمزوّدين المخصّصين تنفيذ supports_token/verify_token بالطريقة نفسها لإتاحة endpoints خاصة بهم قابلة للمصادقة الآلية.

      ربط Hermes Desktop بـ backend بعيد​

      يستطيع Hermes Desktop تشغيل backend لـ Hermes يعمل على جهاز آخر (VPS، أو خادم منزلي، أو جهاز Mini خلف Tailscale). وفي التطبيق يوجد هذا الإعداد تحت Settings → Gateways → Remote gateway، الذي يطلب Remote URL وطريقةً لـ Sign in. (أما عن تطبيق سطح المكتب نفسه — التثبيت، والإعدادات، والمحادثة — فراجع صفحة Hermes Desktop.)

      تحمي لوحة التحكم البعيدة بأحد مزوّدي المصادقة المضمّنين، ويسجّل تطبيق سطح المكتب الدخول عبر المزوّد الذي يُعلن عنه الـ backend. وبالنسبة إلى backend يمكن الوصول إليه من خارج جهازك — VPS، أو مضيف عام، أو أي شيء مُتاح على الإنترنت — فالمزوّد الموصى به هو OAuth (Nous Portal) (سجّله باستخدام hermes dashboard register وسجّل الدخول عبر Sign in with Nous Research). أما مزوّد اسم المستخدم/كلمة المرور المضمّن فهو الخيار الأسرع عندما يكون الـ backend على شبكة LAN موثوقة أو لا يمكن الوصول إليه إلا عبر VPN، لكنه غير مناسب للإتاحة المباشرة على الإنترنت العام. ربط لوحة التحكم على عنوان غير loopback يُفعّل بوابة المصادقة الخاصة بها؛ وبعد تسجيل الدخول، يُعيد Desktop استخدام الجلسة لاتصال WebSocket الخاص بالمحادثة تلقائيًا — فلا يوجد token لنسخه أو لصقه.

      تستخدم الوصفة أدناه مسار اسم المستخدم/كلمة المرور لأنه الأسرع في الإعداد على شبكة موثوقة؛ ولمسار OAuth راجع المزوّد الافتراضي: Nous Research.

      على الـ backend (الجهاز البعيد)​

      # 1. Set the dashboard login credentials in ~/.hermes/.env (secrets file, 0600).
      cat >> ~/.hermes/.env <<'EOF'
      HERMES_DASHBOARD_BASIC_AUTH_USERNAME=admin
      HERMES_DASHBOARD_BASIC_AUTH_PASSWORD=choose-a-strong-password
      # Recommended: a stable signing secret so sessions survive restarts.
      HERMES_DASHBOARD_BASIC_AUTH_SECRET=$(openssl rand -base64 32)
      EOF
      chmod 600 ~/.hermes/.env

      # 2. Run the dashboard bound to a reachable address. The non-loopback bind
      #    engages the auth gate; the username/password provider handles login.
      hermes dashboard --no-open --host 0.0.0.0 --port 9119

      تفضّل عدم تخزين كلمة المرور كنص صريح؟ استخدم بدلًا من ذلك HERMES_DASHBOARD_BASIC_AUTH_PASSWORD_HASH مع تجزئة scrypt — راجع مزوّد اسم المستخدم/كلمة المرور للاطلاع على جميع الخيارات.

      إذا كنت تشغّل لوحة التحكم كخدمة systemd، فإن ~/.hermes/.env يُحمَّل تلقائيًا عندما تحتوي الوحدة على EnvironmentFile=%h/.hermes/.env، فتكون بيانات الاعتماد موجودة في البيئة عند الإقلاع.

      تحذير

      تقرأ لوحة التحكم ملف .env الخاص بك (مفاتيح API، والأسرار) وتكتب إليه، ويمكنها تشغيل أوامر الوكيل. إعداد اسم المستخدم/كلمة المرور الموضّح هنا مخصّص لشبكة موثوقة — لا تُتِح أبدًا لوحة تحكم محمية بكلمة مرور مباشرةً على الإنترنت المفتوح. ضعها خلف VPN. ويُعد Tailscale الخيار الأنظف: اربط على عنوان IP الخاص بـ tailscale للجهاز (--host <tailscale-ip>) واستخدم http://<tailscale-ip>:9119 كقيمة لـ Remote URL. ولن يتمكن من الوصول إليها إلا الأجهزة الموجودة على الـ tailnet الخاص بك. وللوصول إلى backend عبر الإنترنت العام، استخدم بدلًا من ذلك مزوّد OAuth (Nous Portal).

      في Hermes Desktop​

      Settings → Gateways → Remote gateway:

      • Remote URL — http://<backend-host>:9119 (البادئات في المسار مثل /hermes مدعومة إذا وضعت أمامه reverse proxy)
      • Sign in — يكتشف التطبيق gateway اسم المستخدم/كلمة المرور ويعرض زر Sign in؛ انقره وأدخل بيانات الاعتماد من الخطوة 1
      • Save and reconnect — ينقل واجهة تطبيق سطح المكتب إلى الـ backend البعيد

      تُحدَّث الجلسة تلقائيًا وتصمد أمام إعادة التشغيل عندما يكون HERMES_DASHBOARD_BASIC_AUTH_SECRET مضبوطًا على الـ backend.

      التجاوز عبر متغير البيئة​

      بدلًا من الإعداد داخل التطبيق، يمكنك توجيه تطبيق سطح المكتب إلى backend عبر متغير بيئة قبل تشغيله. عندما يكون HERMES_DESKTOP_REMOTE_URL مضبوطًا، فإنه يتجاوز URL المحفوظ داخل التطبيق (تعرض لوحة إعدادات Gateway شارة "env override" وتعطّل التحرير)؛ ولا يزال عليك Sign in باسم المستخدم وكلمة المرور من اللوحة.

      متغير البيئةالقيمة

      استكشاف الأخطاء وإصلاحها​

      • "Remote gateway incomplete" — لم تُدخل URL بعيدًا.
      • فشل تسجيل الدخول مع 401 / "Invalid credentials" — اسم المستخدم أو كلمة المرور لا يطابقان HERMES_DASHBOARD_BASIC_AUTH_USERNAME / HERMES_DASHBOARD_BASIC_AUTH_PASSWORD على الـ backend. يُعيد الـ backend الخطأ العام نفسه للمستخدم غير المعروف ولكلمة المرور الخاطئة، لذا تحقّق من الاثنين. وتأكّد من بوابة المصادقة باستخدام curl -s http://<host>:9119/api/status | jq '.auth_required, .auth_providers' — يجب أن يُبلغ عن true وأن يتضمن "basic".
      • لا يوجد زر "Sign in" — ويُطلب session token بدلًا منه — مزوّد اسم المستخدم/كلمة المرور غير نشط (لن يُدرج /api/status القيمة "basic"). تأكّد من ضبط اسم المستخدم وكلمة مرور (أو تجزئة كلمة مرور)، ومن أن عملية لوحة التحكم حمّلتها.
      • تسجيل الخروج عند كل إعادة تشغيل — اضبط HERMES_DASHBOARD_BASIC_AUTH_SECRET على قيمة ثابتة؛ وإلا يُعاد توليد مفتاح التوقيع عند كل إقلاع.
      • رفض الاتصال / انتهاء المهلة — الـ backend مربوط على 127.0.0.1 (الافتراضي) بدلًا من عنوان يمكن الوصول إليه، أو أن جدار حماية/VPN يحجب المنفذ. اربط على 0.0.0.0 أو على عنوان IP الخاص بـ tailscale، وافتح المنفذ لشبكتك الموثوقة.

      CORS​

      يقيّد خادم الويب CORS بأصول localhost فقط:

      • http://localhost:9119 / http://127.0.0.1:9119 (الإنتاج)
      • http://localhost:3000 / http://127.0.0.1:3000
      • http://localhost:5173 / http://127.0.0.1:5173 (خادم تطوير Vite)

      إذا شغّلت الخادم على منفذ مخصّص، يُضاف ذلك الأصل تلقائيًا.

      التطوير​

      إذا كنت تساهم في الواجهة الأمامية للوحة التحكم على الويب:

      # Terminal 1: start the backend API
      hermes dashboard --no-open

      # Terminal 2: start the Vite dev server with HMR
      cd web/
      npm install
      npm run dev

      يمرّر خادم تطوير Vite على http://localhost:5173 طلبات /api إلى الـ backend المبني بـ FastAPI على http://127.0.0.1:9119.

      الواجهة الأمامية مبنية باستخدام React 19 و TypeScript و Tailwind CSS v4 ومكوّنات على نمط shadcn/ui. وتُخرَج نسخ الإنتاج إلى hermes_cli/web_dist/، الذي يقدّمه خادم FastAPI كـ SPA ثابت.

      البناء التلقائي عند التحديث​

      عند تشغيل hermes update، يُعاد بناء الواجهة الأمامية للويب تلقائيًا إذا كان npm متاحًا. ويُبقي هذا لوحة التحكم متزامنة مع تحديثات الكود. وإذا لم يكن npm مثبّتًا، يتخطى التحديث بناء الواجهة الأمامية، وسيبنيها hermes dashboard عند التشغيل الأول.

      السمات والإضافات​

      تأتي لوحة التحكم مع ثماني سمات مدمجة، ويمكن توسيعها بسمات يعرّفها المستخدم، وتبويبات إضافات، ومسارات API في الـ backend — وكلها تُضاف بمجرد وضع الملفات، دون الحاجة إلى استنساخ المستودع.

      بدّل السمات مباشرةً من شريط الترويسة — انقر أيقونة لوحة الألوان بجوار مبدّل اللغة. يُحفَظ الاختيار في config.yaml تحت dashboard.theme ويُستعاد عند تحميل الصفحة.

      غيّر الخط بشكل مستقل من أداة الاختيار نفسها — إذ يتجاوز قسم Font أسفل قائمة السمات خط الواجهة في أي سمة نشطة. ويبقى الاختيار محفوظًا عند التبديل بين السمات (config.yaml → dashboard.font)؛ واختر Theme default لمسحه والعودة إلى الخط الخاص بالسمة النشطة.

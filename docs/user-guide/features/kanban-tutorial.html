      درس تطبيقي: Kanban

      جولة عملية على حالات الاستخدام الأربع التي صُمّم نظام Kanban في Hermes من أجلها، مع فتح لوحة التحكم (dashboard) في المتصفح. إن لم تكن قد قرأت النظرة العامة على Kanban بعد، فابدأ بها — إذ يفترض هذا الدرس أنك تعرف معنى المهمة (task) والتشغيل (run) والمُكلَّف (assignee) والموزِّع (dispatcher).

      الإعداد​

      hermes kanban init           # optional; first `hermes kanban <anything>` auto-inits
      hermes dashboard             # opens http://127.0.0.1:9119 in your browser
      # click Kanban in the left nav

      لوحة التحكم هي المكان الأكثر راحة لكي تراقب أنت النظام. أما العمّال (workers) من الوكلاء الذين يشغّلهم الموزِّع فلا يرون لوحة التحكم ولا CLI أبدًا — بل يتعاملون مع اللوحة عبر مجموعة kanban_* المخصّصة من الأدوات (toolset) (kanban_show، kanban_list، kanban_complete، kanban_block، kanban_heartbeat، kanban_comment، kanban_attach، kanban_attach_url، kanban_attachments، kanban_create، kanban_link، kanban_unblock). تمرّ الواجهات الثلاث — لوحة التحكم و CLI وأدوات العمّال — عبر قاعدة بيانات SQLite نفسها الخاصة بكل لوحة (~/.hermes/kanban.db للّوحة الافتراضية، و ~/.hermes/kanban/boards/<slug>/kanban.db لأي لوحة تنشئها لاحقًا)، لذا تبقى كل لوحة متسقة بغضّ النظر عن الجهة التي جاء منها التغيير.

      يستخدم هذا الدرس اللوحة default طوال الوقت. إذا أردت عدة طوابير معزولة (واحدًا لكل مشروع / مستودع / مجال)، فراجع اللوحات (متعددة المشاريع) في النظرة العامة — إذ تنطبق مسارات CLI ولوحة التحكم والعمّال نفسها على كل لوحة، ولا يستطيع العمّال فعليًا رؤية المهام الموجودة في لوحات أخرى.

      في أنحاء هذا الدرس، كتل الكود الموسومة بـ bash هي أوامر تشغّلها أنت. أما كتل الكود الموسومة بـ # worker tool calls فهي ما يُصدره نموذج العامل المُشغَّل على هيئة استدعاءات أدوات — وتُعرض هنا لكي ترى الحلقة كاملة من البداية إلى النهاية، لا لأنك ستشغّلها بنفسك يومًا ما.

      اللوحة في لمحة​

      ستة أعمدة، من اليسار إلى اليمين:

      • Triage — الأفكار الخام. افتراضيًا، يشغّل الموزِّع تلقائيًا المُفكِّك (decomposer) على المهام الموجودة هنا: يستخدم المُفكِّك المدمج auxiliary.kanban_decomposer، ويقرأ قائمة الـ profiles لديك مع أوصافها، ثم يُنتج مخططًا من المهام الفرعية الموجّهة إلى أنسب المتخصصين. تُبقى المهمة الأصلية حيّة بوصفها المهمة الأم، بحيث يستيقظ المُكلَّف بها (kanban.orchestrator_profile، أو الـ profile الافتراضي النشط عند عدم ضبطه) مجددًا ليحكم على الإنجاز حين ينتهي كل شيء. بدّل مفتاح Orchestration: Auto/Manual أعلى صفحة kanban للتبديل بين الوضعين. في الوضع اليدوي انقر ⚗ Decompose على البطاقة، أو شغّل hermes kanban decompose <id> / /kanban decompose <id>. وللمهام المفردة التي لا تحتاج إلى توزيع على عدة مهام، ينفّذ ✨ Specify إعادة كتابة للمواصفات دفعة واحدة (الهدف، والنهج، ومعايير القبول) ثم يرقّي المهمة إلى todo. اضبط النماذج تحت auxiliary.kanban_decomposer و auxiliary.triage_specifier في config.yaml. راجع التنسيق التلقائي مقابل اليدوي في دليل Kanban الرئيسي.
      • Todo — مهام أُنشئت لكنها تنتظر اعتمادياتها، أو لم تُسنَد بعد.
      • Ready — مهام أُسندت وتنتظر أن يستلمها الموزِّع.
      • In progress — عامل يشغّل المهمة حاليًا. عند تفعيل "Lanes by profile" (وهو الافتراضي)، يُقسَّم هذا العمود إلى مجموعات فرعية حسب المُكلَّف لتعرف في لمحة ما يفعله كل عامل.
      • Blocked — طلب عامل مدخلات بشرية، أو انطلق قاطع الدائرة (circuit breaker).
      • Done — مهام مكتملة.

      يحتوي الشريط العلوي على مرشّحات للبحث والمستأجر (tenant) والمُكلَّف، إضافةً إلى مفتاح Lanes by profile وزر Nudge dispatcher الذي يشغّل دورة توزيع واحدة فورًا بدلًا من انتظار الفاصل الزمني التالي للـ daemon. يؤدي النقر على أي بطاقة إلى فتح لوحتها الجانبية على اليمين.

      العرض المسطّح​

      إذا كانت مسارات الـ profiles مزدحمة، فعطّل "Lanes by profile" وسيتحوّل عمود In Progress إلى قائمة مسطّحة واحدة مرتّبة حسب وقت الاستلام:

      القصة 1 — مطوّر منفرد يُطلق ميزة​

      أنت تبني ميزة. التدفق المعتاد: صمّم المخطط (schema)، ونفّذ الـ API، واكتب الاختبارات. ثلاث مهام بينها اعتماديات من نوع أم→ابن.

      SCHEMA=$(hermes kanban create "Design auth schema" \
          --assignee backend-dev --tenant auth-project --priority 2 \
          --body "Design the user/session/token schema for the auth module." \
          --json | jq -r .id)

      API=$(hermes kanban create "Implement auth API endpoints" \
          --assignee backend-dev --tenant auth-project --priority 2 \
          --parent $SCHEMA \
          --body "POST /register, POST /login, POST /refresh, POST /logout." \
          --json | jq -r .id)

      hermes kanban create "Write auth integration tests" \
          --assignee qa-dev --tenant auth-project --priority 2 \
          --parent $API \
          --body "Cover happy path, wrong password, expired token, concurrent refresh."

      بما أن API لها SCHEMA مهمةً أمًّا، و tests لها API مهمةً أمًّا، فإن SCHEMA وحدها تبدأ في ready. وتبقى المهمتان الأخريان في todo حتى تكتمل مهامهما الأم. هذا هو محرّك ترقية الاعتماديات يؤدي عمله — فلن يلتقط أي عامل آخر مهمة كتابة الاختبارات قبل وجود API لاختباره.

      في دورة الموزِّع التالية (كل 60 ثانية افتراضيًا، أو فورًا إذا ضغطت Nudge dispatcher) يُشغَّل الـ profile backend-dev بوصفه عاملًا مع HERMES_KANBAN_TASK=$SCHEMA في بيئته. إليك شكل حلقة استدعاءات الأدوات لدى العامل من داخل الوكيل:

      # worker tool calls — NOT commands you run
      kanban_show()
      # → returns title, body, worker_context, parents, prior attempts, comments

      # (worker reads worker_context, uses terminal/file tools to design the schema,
      #  write migrations, run its own checks, commit — the real work happens here)

      kanban_heartbeat(note="schema drafted, writing migrations now")

      kanban_complete(
          summary="users(id, email, pw_hash), sessions(id, user_id, jti, expires_at); "
                  "refresh tokens stored as sessions with type='refresh'",
          metadata={
              "changed_files": ["migrations/001_users.sql", "migrations/002_sessions.sql"],
              "decisions": ["bcrypt for hashing", "JWT for session tokens",
                            "7-day refresh, 15-min access"],
          },
      )

      تستخدم kanban_show القيمة الافتراضية لـ task_id وهي $HERMES_KANBAN_TASK، لذا لا يحتاج العامل إلى معرفة المعرّف الخاص به. وتكتب kanban_complete الملخص + البيانات الوصفية في صف task_runs الحالي، وتُغلق ذلك التشغيل، وتنقل المهمة إلى done — كل ذلك في خطوة ذرّية واحدة عبر kanban_db.

      عندما تصل SCHEMA إلى done، يرقّي محرّك الاعتماديات API إلى ready تلقائيًا. وعندما يلتقط عامل الـ API المهمة، سيستدعي kanban_show() ويرى ملخص SCHEMA وبياناتها الوصفية مرفقة بتسليم المهمة الأم — فيعرف قرارات المخطط دون إعادة قراءة مستند تصميم طويل.

      انقر على مهمة المخطط المكتملة في اللوحة، وستعرض اللوحة الجانبية كل شيء:

      قسم Run History في الأسفل هو الإضافة الأهم. محاولة واحدة: النتيجة completed، والعامل @backend-dev، والمدة، والطابع الزمني، وملخص التسليم كاملًا. وتُخزَّن كتلة البيانات الوصفية (changed_files، decisions) على التشغيل أيضًا، وتُعرض لأي عامل لاحق يقرأ هذه المهمة الأم.

      يمكنك فحص البيانات نفسها من الطرفية في أي وقت — هذه الأوامر هي أنت تُلقي نظرة على اللوحة، لا العامل:

      hermes kanban show $SCHEMA
      hermes kanban runs $SCHEMA
      # #  OUTCOME       PROFILE       ELAPSED  STARTED
      # 1  completed     backend-dev        0s  2026-04-27 19:34
      #     → users(id, email, pw_hash), sessions(id, user_id, jti, expires_at); refresh tokens ...

      القصة 2 — تشغيل أسطول من العمّال​

      لديك ثلاثة عمّال (مترجم، ومُفرِّغ نصوص، وكاتب محتوى) وكومة من المهام المستقلة. تريد أن يسحب الثلاثة المهام بالتوازي وأن يُحرزوا تقدمًا مرئيًا. هذه أبسط حالة استخدام لـ kanban، وهي الحالة التي صُمّم التصميم الأصلي لتحسينها.

      أنشئ العمل:

      for lang in Spanish French German; do
          hermes kanban create "Translate homepage to $lang" \
              --assignee translator --tenant content-ops
      done
      for i in 1 2 3 4 5; do
          hermes kanban create "Transcribe Q3 customer call #$i" \
              --assignee transcriber --tenant content-ops
      done
      for sku in 1001 1002 1003 1004; do
          hermes kanban create "Generate product description: SKU-$sku" \
              --assignee copywriter --tenant content-ops
      done

      شغّل الـ gateway وانصرف — فهو يستضيف الموزِّع المضمَّن الذي يلتقط مهام الـ profiles المتخصصة الثلاثة من kanban.db نفسها:

      hermes gateway start

      الآن رشّح اللوحة على content-ops (أو ابحث ببساطة عن "Transcribe") وستحصل على هذا:

      مهمتا تفريغ مكتملتان، وواحدة قيد التشغيل، واثنتان جاهزتان تنتظران دورة الموزِّع التالية. عمود In Progress مجمّع حسب الـ profile (الوضع الافتراضي "Lanes by profile") فترى المهمة النشطة لكل عامل دون تفحّص قائمة مختلطة. سيرقّي الموزِّع المهمة الجاهزة التالية إلى التشغيل فور اكتمال المهمة الحالية. ومع ثلاثة daemons تعمل على ثلاث مجموعات من المُكلَّفين بالتوازي، يُستنفد طابور المحتوى بأكمله دون أي تدخل بشري إضافي.

      كل ما قالته القصة 1 عن التسليم المنظَّم لا يزال ينطبق هنا. فعامل الترجمة الذي يُنهي مهمة يُصدر kanban_complete(summary="translated 4 pages, style matched existing marketing voice", metadata={"duration_seconds": 720, "tokens_used": 2100}) — وهو أمر مفيد للتحليلات ولأي مهمة لاحقة تعتمد على هذه المهمة.

      القصة 3 — pipeline أدوار مع إعادة المحاولة​

      هنا يُثبت Kanban جدارته مقارنةً بقائمة TODO مسطّحة. مدير منتج يكتب المواصفات. مهندس ينفّذها. مراجِع يرفض المحاولة الأولى. يحاول المهندس مجددًا بعد إجراء تعديلات. يوافق المراجِع.

      عرض لوحة التحكم، مع الترشيح على auth-project:

      تستخدم لقطة الشاشة نموذج البطاقة اللاحقة المُنشأة مسبقًا: لبطاقة التنفيذ مهمة ابن مخصّصة للمراجِع. في هذا النموذج يجب أن يستدعي المهندس kanban_complete عندما يصبح التنفيذ جاهزًا، لكي تتمكن مهمة المراجِع الابن من مغادرة todo. لا تحظر (block) مهمة التنفيذ الأم لمجرد طلب مراجعة.

      أما في سير العمل الذي تتولى فيه البطاقة نفسها التنفيذ والمراجعة، فاستخدم دورة حياة المراجعة المدمجة بدلًا من ذلك. التسلسل الكامل تنفيذ → مراجعة → تعديلات → إعادة مراجعة هو:

      # --- Engineer: first implementation attempt ---
      kanban_show()
      # (write code, run tests, prepare the candidate)
      kanban_request_review(
          summary="implemented reset flow; candidate is ready for review",
          metadata={"changed_files": ["auth/reset.py"], "tests_run": 8},
          reviewer="reviewer",
      )
      # → the same card enters review; the implementation run closes as
      #   outcome='review_requested'

      # --- Reviewer: request concrete changes ---
      kanban_show()
      # (inspect the handoff and candidate)
      kanban_request_changes(
          reason="Add password-strength validation and make reset tokens single-use."
      )
      # → the review run closes as outcome='changes_requested'; the card returns
      #   to backend-dev in ready/todo without touching block-loop accounting

      # --- Engineer: second implementation attempt ---
      kanban_show()  # prior review evidence is in worker_context
      # (apply feedback and re-run tests)
      kanban_request_review(
          summary="added zxcvbn validation and single-use reset tokens",
          metadata={
              "changed_files": [
                  "auth/reset.py",
                  "auth/tests/test_reset.py",
                  "migrations/003_single_use_reset_tokens.sql",
              ],
              "tests_run": 11,
              "review_iteration": 2,
          },
          reviewer="reviewer",
      )

      # --- Reviewer: approve ---
      kanban_complete(summary="review passed; acceptance criteria verified")
      # → done

      يسجّل سجلّ تشغيل المهمة الآن review_requested → changes_requested → review_requested → completed. لكل محاولة فاعلها وملخصها وبياناتها الوصفية ونتيجتها، لذا يرى المهندس في المحاولة الثانية بالضبط ما رفضه المراجِع، وتبقى الموافقة النهائية قابلة للتدقيق. تُحجز kanban_block للتصعيد الخارجي الحقيقي (صلاحية وصول مفقودة، أو قرار يخص المنتج، أو بنية تحتية غير متاحة)، لا لملاحظات المراجعة العادية.

      إذا كنت تستخدم عمدًا نموذج البطاقة اللاحقة الظاهر في لقطة الشاشة، فإن المراجِع يفتح Review password reset PR بعد اكتمال مهمة التنفيذ الأم:

      يتضمن worker_context الخاص ببطاقة المراجِع تسليمَ التنفيذ المكتمل. هذا سير عمل قائم على بطاقة منفصلة؛ فلا تجمعه مع kanban_request_review على البطاقة نفسها وإلا ستُكرّر مسار المراجعة.

      القصة 4 — قاطع الدائرة والتعافي من الأعطال​

      العمّال الحقيقيون يفشلون. بيانات اعتماد مفقودة، أو إنهاء بسبب نفاد الذاكرة (OOM)، أو أخطاء شبكة عابرة. لدى الموزِّع خطّا دفاع: قاطع الدائرة الذي يحظر المهمة تلقائيًا بعد N من الإخفاقات المتتالية كي لا تدور اللوحة في حلقة مفرغة إلى الأبد، و كشف الأعطال الذي يستعيد المهمة التي اختفى PID عاملها قبل انتهاء مدة TTL الخاصة بها.

      قاطع الدائرة — إخفاق يبدو دائمًا​

      مهمة نشر لا تستطيع تشغيل عاملها لأن AWS_ACCESS_KEY_ID غير مضبوط في بيئة الـ profile:

      hermes kanban create "Deploy to staging (missing creds)" \
          --assignee deploy-bot --tenant ops \
          --max-retries 3

      يحاول الموزِّع تشغيل العامل. يفشل التشغيل (RuntimeError: AWS_ACCESS_KEY_ID not set). يُحرِّر الموزِّع الاستلام، ويزيد عدّاد الإخفاقات، ويحاول مجددًا في الدورة التالية. وبما أن هذا المثال يضبط --max-retries 3، ينطلق القاطع بعد ثلاثة إخفاقات متتالية: تنتقل المهمة إلى blocked بالنتيجة gave_up. إذا حذفت هذا الخيار، يستخدم Hermes القيمة kanban.failure_limit (الافتراضي: 2). لا مزيد من المحاولات حتى يرفع إنسانٌ الحظر عنها.

      انقر على المهمة المحظورة:

      ثلاثة تشغيلات، جميعها بالخطأ نفسه في الحقل error. أول اثنين spawn_failed (قابلان لإعادة المحاولة)، والثالث gave_up (نهائي). يعرض سجل الأحداث أعلاه التسلسل الكامل: created → claimed → spawn_failed → claimed → spawn_failed → claimed → gave_up.

      في الطرفية:

      hermes kanban runs t_ef5d
      # #   OUTCOME        PROFILE        ELAPSED  STARTED
      # 1   spawn_failed   deploy-bot          0s  2026-04-27 19:34
      #       ! AWS_ACCESS_KEY_ID not set in deploy-bot env
      # 2   spawn_failed   deploy-bot          0s  2026-04-27 19:34
      #       ! AWS_ACCESS_KEY_ID not set in deploy-bot env
      # 3   gave_up        deploy-bot          0s  2026-04-27 19:34
      #       ! AWS_ACCESS_KEY_ID not set in deploy-bot env

      إذا كان Telegram / Discord / Slack موصولًا، يُطلق الـ gateway إشعارًا عند حدث gave_up فتعلم بالعطل دون الحاجة إلى تفقّد اللوحة.

      التعافي من الأعطال — العامل يتوقف في منتصف العمل​

      أحيانًا ينجح التشغيل لكن عملية العامل تموت لاحقًا — بسبب segfault أو OOM أو systemctl stop. يستطلع الموزِّع kill(pid, 0) ويكتشف الـ pid الميت؛ فيُحرَّر الاستلام، وتعود المهمة إلى ready، وتمنحها الدورة التالية لعامل جديد.

      المثال الموجود في البيانات الأولية هو عملية ترحيل كانت تنفد منها الذاكرة:

      # Worker claims, starts scanning 2.4M rows, OOM kills it at ~2.3M
      # Dispatcher detects dead pid, releases claim, increments attempt counter
      # Retry with a chunked strategy succeeds

      تعرض اللوحة الجانبية السجل الكامل للمحاولتين:

      التشغيل 1 — crashed، مع الخطأ OOM kill at row 2.3M (process 99999 gone). التشغيل 2 — completed، مع "strategy": "chunked with LIMIT + WHERE id > last_id" في بياناته الوصفية. رأى العامل الذي أعاد المحاولة عطل التشغيل 1 في سياقه فاختار استراتيجية أكثر أمانًا؛ وتوضّح البيانات الوصفية لأي مراقب مستقبلي (أو كاتب تقرير ما بعد الحادثة) ما الذي تغيّر.

      التسليم المنظَّم — لماذا تهمّ summary و metadata​

      في كل قصة أعلاه، استدعى العمّال kanban_complete(summary=..., metadata=...) في النهاية. هذا ليس للزينة — بل هو قناة التسليم الأساسية بين مراحل سير العمل.

      عندما يُشغَّل عامل على المهمة B ويستدعي kanban_show()، فإن worker_context الذي يتلقاه يتضمن:

      • المحاولات السابقة للمهمة B (التشغيلات السابقة: النتيجة، والملخص، والخطأ، والبيانات الوصفية) كي لا يكرّر العامل الذي يعيد المحاولة مسارًا فاشلًا.
      • نتائج المهام الأم — لكل مهمة أم، ملخص آخر تشغيل مكتمل وبياناته الوصفية — كي يرى العمّال اللاحقون لماذا وكيف أُنجز العمل السابق.

      يحلّ هذا محلّ رحلة "التنقيب في التعليقات ومخرجات العمل" التي تُرهق أنظمة kanban المسطّحة. يكتب مدير المنتج معايير القبول في البيانات الوصفية للمواصفات، فيراها عامل المهندس بشكل منظَّم في تسليم المهمة الأم. ويسجّل المهندس الاختبارات التي شغّلها وعدد الناجح منها، فيكون لدى عامل المراجِع تلك القائمة قبل فتح أي diff.

      توجد حماية الإغلاق الجماعي لأن هذه البيانات خاصة بكل تشغيل. يُرفض الأمر hermes kanban complete a b c --summary X (منك أنت، من CLI) — فنسخ الملخص نفسه ولصقه على ثلاث مهام يكاد يكون خطأً دائمًا. أما الإغلاق الجماعي دون خيارات التسليم فلا يزال يعمل في الحالة الشائعة "أنهيتُ كومة من المهام الإدارية". ولا تكشف واجهة الأدوات عن أي صيغة جماعية على الإطلاق؛ فـ kanban_complete تعمل دائمًا على مهمة واحدة في كل مرة للسبب نفسه.

      متابعة بطاقة مكتملة — معالجة أعطال CI عبر رابط المهمة الأم​

      بطاقة التنفيذ في القصة 1 أصبحت done. وبعد ساعتين يفشل CI على الـ branch المدموج. لا تُعِد فتح البطاقة المكتملة — فالبطاقات المكتملة تاريخ، وتسليمها يتدفق إلى الأمام. أنشئ بطاقة معالجة تكون البطاقة المكتملة مهمتها الأم:

      hermes kanban create "Fix CI: test_backoff_jitter flakes on 3.11" \
          --assignee backend-dev \
          --parent t_impl \
          --workspace worktree --branch wt/ci-fix-backoff \
          --body "CI run #4812 failed after t_impl completed.
      FAILED tests/test_retry.py::test_backoff_jitter - TimeoutError
      Acceptance: tests/test_retry.py green on 3.11 and 3.12."

      ثلاثة أمور تجعل هذا يعمل:

      • توزيع فوري. بما أن المهمة الأم done بالفعل، تُنشأ المهمة الابن مباشرةً في ready — ويستطيع الموزِّع استلامها في الدورة التالية. (أما ابن مهمة أم لا تزال مفتوحة فينتظر في todo.)
      • سياق موروث. يتضمن سياق عامل المعالجة قسم Parent task results الذي يحمل ملخص إنجاز t_impl وبياناته الوصفية — أي الملفات المعدّلة والقرارات التي سجّلها العامل الأصلي — فيعرف لماذا صيغ الكود على هذا النحو قبل أن يقرأ سطرًا منه.
      • أدلة جديدة في المتن. لم يكن سجل CI موجودًا عند اكتمال t_impl، لذا لا يمكن أن يكون في تسليم المهمة الأم — بل يوضع في متن البطاقة الجديدة، إلى جانب معايير قبول صريحة.

      يُفضَّل استخدام worktree/branch جديد لبطاقة المعالجة. فسحب الـ branch الأصلي يمنح العامل حالة المستودع لكن دون أيٍّ من المبررات — وتسليم المهمة الأم هو ما يحمل تلك المبررات. واستخدام profile المُكلَّف نفسه هو الصواب عادةً: فالـ profile الذي كتب الكود يمتلك المهارات اللازمة لإصلاحه.

      فحص مهمة قيد التشغيل​

      للاكتمال — إليك اللوحة الجانبية لمهمة لا تزال قيد التنفيذ (تنفيذ الـ API من القصة 1، التي استلمها backend-dev لكنها لم تكتمل بعد):

      الحالة Running. يظهر التشغيل النشط في قسم Run History بالنتيجة active ودون ended_at. إذا مات هذا العامل أو انتهت مهلته، يُغلق الموزِّع هذا التشغيل بالنتيجة المناسبة ويفتح تشغيلًا جديدًا عند الاستلام التالي — ولا يختفي صف المحاولة أبدًا.

      الخطوات التالية​

      • النظرة العامة على Kanban — نموذج البيانات الكامل، ومفردات الأحداث، ومرجع CLI.
      • hermes kanban --help — كل أمر فرعي، وكل خيار.
      • hermes kanban watch --kinds completed,gave_up,timed_out — بث مباشر للأحداث النهائية عبر اللوحة بأكملها.
      • hermes kanban notify-subscribe <task> --platform telegram --chat-id <id> — احصل على تنبيه من الـ gateway عند انتهاء مهمة محددة.

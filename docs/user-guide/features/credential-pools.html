      مجمّعات بيانات الاعتماد (Credential Pools)

      تتيح لك مجمّعات بيانات الاعتماد (Credential Pools) تسجيل عدة مفاتيح API أو رموز OAuth لنفس المزوّد. فعندما يصل أحد المفاتيح إلى حدّ المعدل (rate limit) أو حصة الفوترة، يقوم Hermes تلقائيًا بالتناوب إلى المفتاح الصحي التالي — مما يبقي جلستك عاملة دون التبديل إلى مزوّد آخر.

      يختلف هذا عن المزوّدين الاحتياطيين (fallback providers)، الذين يبدّلون إلى مزوّد مختلف تمامًا. مجمّعات بيانات الاعتماد هي تناوب ضمن المزوّد نفسه؛ بينما المزوّدون الاحتياطيون هم تجاوز فشل عبر مزوّدين مختلفين. تُجرَّب المجمّعات أولًا — فإذا استُنفدت كل مفاتيح المجمّع، عندها يُفعَّل المزوّد الاحتياطي.

      تناوب المفاتيح يصفّر ذاكرة التخزين المؤقت للـ prompt

      ذاكرات التخزين المؤقت للـ prompt الخاصة بالمزوّد (Anthropic و OpenAI و OpenRouter) مرتبطة بالحساب/مفتاح API الذي أجرى الطلب. فعندما يتناوب المجمّع إلى مفتاح مختلف في منتصف الجلسة، لا يملك المفتاح الجديد أي بادئة مخزّنة مؤقتًا لمحادثتك — يُعيد الطلب التالي قراءة السجل الكامل بسعر الإدخال الكامل دون خصم، والعودة إلى المفتاح السابق لاحقًا هي إعادة قراءة كاملة أخرى ما لم تكن مدة صلاحية ذاكرة المفتاح السابق لا تزال فعّالة. التناوب يبقي جلستك عاملة، وهذا هو المقصود منه، لكن على المحادثات الطويلة تكلّف كل عملية تناوب مرورًا واحدًا كاملًا بالسعر الكامل على السياق.

      نصيحة

      مجمّعات بيانات الاعتماد مخصصة أساسًا لمزوّدي مفاتيح API (OpenRouter و Anthropic). OAuth واحد لـ Nous Portal يغطي أكثر من 300 نموذج، لذا لا يحتاج معظم المستخدمين على Portal إلى مجمّع.

      كيف يعمل​

      Your request
        → Pick key from pool (round_robin / least_used / fill_first / random)
        → Send to provider
        → 429 rate limit?
            → Plan/usage limit reached (e.g. ChatGPT/Codex "usage limit reached")?
                → Rotate to next pool key immediately (no retry — the cap won't clear on retry)
            → Generic / transient 429?
                → Retry same key once (transient blip)
                → Second 429 → rotate to next pool key
            → All keys exhausted → fallback_model (different provider)
        → 402 billing error?
            → Immediately rotate to next pool key (1h cooldown)
        → 401 auth expired?
            → Try refreshing the token (OAuth)
            → Refresh failed → rotate to next pool key
        → Success → continue normally

      البدء السريع​

      إذا كان لديك بالفعل مفتاح API مضبوط في .env، يكتشفه Hermes تلقائيًا كمجمّع من مفتاح واحد. وللاستفادة من التجميع، أضف المزيد من المفاتيح:

      # Add a second OpenRouter key
      hermes auth add openrouter --api-key sk-or-v1-your-second-key

      # ...or let a browser login mint one (OpenRouter OAuth PKCE; stored as a plain API key)
      hermes auth add openrouter --type oauth

      # Add a second Anthropic key
      hermes auth add anthropic --type api-key --api-key sk-ant-api03-your-second-key

      # Add an Anthropic OAuth credential (requires Claude Max plan + extra usage credits)
      hermes auth add anthropic --type oauth
      # Opens browser for OAuth login

      تحقّق من مجمّعاتك:

      hermes auth list

      الناتج:

      openrouter (2 credentials):
        #1  OPENROUTER_API_KEY   api_key id=ab12cd34 priority=0 env:OPENROUTER_API_KEY ←
        #2  backup-key           api_key id=ef56gh78 priority=1 manual

      anthropic (3 credentials):
        #1  hermes_pkce          oauth   id=ab12cd34 priority=0 hermes_pkce ←
        #2  claude_code          oauth   id=cd34ef56 priority=1 claude_code
        #3  ANTHROPIC_API_KEY    api_key id=ef56gh78 priority=2 env:ANTHROPIC_API_KEY

      تشير ← إلى بيانات الاعتماد المختارة حاليًا. id= هو معرّف الإدخال الذي تقبله hermes auth remove <provider> <target> عندما يكون التصنيف (label) غامضًا، وpriority= هو الترتيب الذي يحاول به المجمّع بيانات الاعتماد ضمن استراتيجية fill_first.

      الإدارة التفاعلية​

      شغّل hermes auth بدون أمر فرعي للحصول على معالج تفاعلي:

      hermes auth

      يعرض هذا حالة مجمّعك الكاملة ويقدّم قائمة:

      What would you like to do?
        1. Add a credential
        2. Remove a credential
        3. Reset cooldowns for a provider
        4. Set rotation strategy for a provider
        5. Exit

      بالنسبة للمزوّدين الذين يدعمون كلًا من مفاتيح API و OAuth (Anthropic و Nous و Codex)، يسأل مسار الإضافة عن النوع المطلوب:

      anthropic supports both API keys and OAuth login.
        1. API key (paste a key from the provider dashboard)
        2. OAuth login (authenticate via browser)
      Type [1/2]:

      أوامر CLI​

      الأمرالوصف
      hermes authمعالج تفاعلي لإدارة المجمّعات
      hermes auth listعرض كل المجمّعات وبيانات الاعتماد
      hermes auth list <provider>عرض مجمّع مزوّد معيّن
      hermes auth add <provider>إضافة بيانات اعتماد (يطلب النوع والمفتاح)
      hermes auth add <provider> --type api-key --api-key <key>إضافة مفتاح API بدون تفاعل
      hermes auth add <provider> --type oauthإضافة بيانات اعتماد OAuth عبر تسجيل الدخول من المتصفح
      hermes auth add <provider> --priority 0إضافة بيانات اعتماد ووضعها أولًا في ترتيب fill_first
      hermes auth priority <provider> <target> <n>نقل بيانات اعتماد إلى الأولوية n (0 = تُجرَّب أولًا)؛ تُعاد ترقيم البقية
      hermes auth remove <provider> <index>إزالة بيانات اعتماد حسب الفهرس الذي يبدأ من 1
      hermes auth reset <provider>مسح كل حالات التهدئة (cooldowns)/الاستنفاد
      hermes auth reset <provider> <target>مسح فترة التهدئة لبيانات اعتماد واحدة حسب الفهرس أو المعرّف أو التصنيف
      hermes auth refresh <provider> [target]تحديث رموز بيانات اعتماد OAuth واحدة وإعادتها إلى التناوب (يثبت أن المنحة (grant) ما زالت حية؛ يعيد الطلب التالي فحص الحصة)

      بالنسبة لـ Nous، لا يدعم auth refresh إلا singleton الخاص بتسجيل الدخول بـdevice_code. تُرفض حسابات مجمّع Nous المستقلة قبل التحديث؛ وتُحفظ رموزها وفترات تهدئتها. أعد المصادقة باستخدام hermes auth add nous --type oauth لتحديث الـ singleton؛ وهذا لا يحدّث حسابًا مستقلًا. أما المزوّدون الآخرون فيحتفظون بدعم التحديث الخاص بمصدرهم القائم.

      استراتيجيات التناوب​

      مواضع الأولوية تبدأ من صفر وتنحصر عند طرفَي المجمّع؛ الأهداف المعروضة هي فهارس تبدأ من 1، أو معرّفات إدخال، أو تصنيفات دقيقة غير غامضة. كما أن auth add --priority يضع أيضًا إدخالًا موجودًا تم تحديثه عبر إعادة المصادقة. يُبقي Anthropic بيانات الاعتماد اليدوية قبل بيانات الاعتماد المزروعة (seeded)، لذا يُبلِغ الأمر عن الموضع الفعلي عندما تغيّره هذه القاعدة. قد تتجاوز استراتيجيات أخرى الأولوية، ولا تُعيد إعادة الترتيب ربط بيانات الاعتماد التي تحتفظ بها جلسة قيد التشغيل بالفعل.

      كل اختيار ناجح للمجمّع يزيد request_count، بصرف النظر عن الاستراتيجية. عمليات البحث الخاصة بالتحديث فقط والاستطلاعات (peeks) لا تُحتسب. هذه عدّادات اختيار وليست إجماليات فوترة أو عدّ لكل طلب استدلال: يمكن لبيانات اعتماد مخزّنة مؤقتًا أن تخدم عدة طلبات. تبقى العدّادات في الذاكرة حتى عملية الكتابة التالية على المجمّع الموجود (مثل التناوب أو الاستنفاد أو التحديث أو تغيير إداري)؛ وهذا لا يضيف كتابة على القرص لكل اختيار.

      اضبطها عبر hermes auth ← "Set rotation strategy" أو في config.yaml:

      credential_pool_strategies:
        openrouter: round_robin
        anthropic: least_used
      الاستراتيجيةالسلوك
      fill_first (الافتراضي)استخدام أول مفتاح سليم حتى يُستنفد، ثم الانتقال إلى التالي؛ الترتيب هو priority كل بيانات اعتماد (يغيّره hermes auth priority)
      round_robinالتنقّل بين المفاتيح بالتساوي، مع التناوب بعد كل اختيار
      least_usedاختيار المفتاح ذي عدد الطلبات الأقل دائمًا
      randomاختيار عشوائي بين المفاتيح السليمة

      التعافي من الأخطاء​

      يتعامل المجمّع مع الأخطاء المختلفة بطرق مختلفة:

      الخطأالسلوكفترة التهدئة
      429 حدّ المعدل (Rate Limit)إعادة محاولة المفتاح نفسه مرة واحدة (عابر). 429 ثانٍ متتالٍ يتناوب إلى المفتاح التاليساعة واحدة
      402 الفوترة/الحصةالتناوب فورًا إلى المفتاح التاليساعة واحدة
      401 انتهت صلاحية المصادقةمحاولة تحديث رمز OAuth أولًا. التناوب فقط إذا فشل التحديث5 دقائق
      استُنفدت كل المفاتيحالانتقال إلى fallback_model إن كان مُعدًّا—

      الطوابع الزمنية reset_at التي يوفّرها المزوّد تتجاوز فترات التهدئة الافتراضية هذه.

      تُعاد تهيئة علامة has_retried_429 عند كل استدعاء API ناجح، لذا لا يؤدي خطأ 429 عابر واحد إلى التناوب.

      مجمّعات endpoint المخصّصة​

      تحصل نقاط الوصول (endpoints) المخصّصة المتوافقة مع OpenAI (Together.ai و RunPod والخوادم المحلية) على مجمّعاتها الخاصة، مُفهرَسة باسم الـ endpoint من قاموس providers: في config.yaml (أو قائمة custom_providers القديمة، التي تُنقَل تلقائيًا).

      عندما تُعِدّ endpoint مخصصًا عبر hermes model، يُولَّد اسم تلقائيًا مثل "Together.ai" أو "Local (localhost:8080)". يصبح هذا الاسم مفتاح المجمّع.

      # After setting up a custom endpoint via hermes model:
      hermes auth list
      # Shows:
      #   Together.ai (1 credential):
      #     #1  config key    api_key config:Together.ai ←

      # Add a second key for the same endpoint:
      hermes auth add Together.ai --api-key sk-together-second-key

      تُخزَّن مجمّعات endpoint المخصّصة في auth.json ضمن credential_pool بسابقة custom::

      {
        "credential_pool": {
          "openrouter": [...],
          "custom:together.ai": [...]
        }
      }

      الاكتشاف التلقائي​

      يكتشف Hermes تلقائيًا بيانات الاعتماد من مصادر متعددة ويزرع المجمّع عند بدء التشغيل:

      المصدرمثالمزروعة تلقائيًا؟
      متغيرات البيئةOPENROUTER_API_KEY، ANTHROPIC_API_KEYنعم
      رموز OAuth (auth.json)رمز جهاز Codex، رمز جهاز Nousنعم
      بيانات اعتماد Claude Code~/.claude/.credentials.jsonنعم (Anthropic)
      Hermes PKCE OAuth~/.hermes/auth.jsonنعم (Anthropic)
      إعدادات endpoint مخصّصmodel.api_key في config.yamlنعم (endpoints المخصّصة)
      إدخالات يدويةأُضيفت عبر hermes auth addمحفوظة في auth.json

      تُحدَّث الإدخالات المزروعة تلقائيًا عند كل تحميل للمجمّع — فإذا أزلت متغير بيئة، يُحذف إدخاله من المجمّع تلقائيًا. أما الإدخالات اليدوية (المضافة عبر hermes auth add) فلا تُحذف تلقائيًا أبدًا.

      الأسرار (secrets) المستعارة وقت التشغيل (مثل متغيرات البيئة، ومراجع Bitwarden/Vault/keyring/systemd، وقيم الإعدادات المخصّصة) تكون مرجعية فقط عند حدود auth.json. يمكن لـ Hermes استخدام القيمة المحلولة في الذاكرة للتشغيل الحالي، لكنه لا يحفظ سوى بيانات وصفية مثل مرجع المصدر والتصنيف والحالة وعدّادات الطلبات وبصمة (fingerprint) غير قابلة للعكس. أما الإدخالات اليدوية وحالة OAuth/رمز الجهاز المملوكة لـ Hermes فتحتفظ بالرموز الدائمة التي تحتاجها للتحديث.

      التفويض ومشاركة Subagent​

      عندما ينشئ الوكيل subagents عبر delegate_task، تُشارَك مجمّعة بيانات اعتماد الوالد تلقائيًا مع الأبناء:

      • نفس المزوّد — يتلقى الابن مجمّعة الوالد الكاملة، مما يتيح تناوب المفاتيح عند بلوغ حدّ المعدل
      • مزوّد مختلف — يحمّل الابن مجمّعة ذلك المزوّد الخاصة (إن كانت مُعدَّة)
      • لا مجمّع مُعدّ — يعود الابن إلى مفتاح API الفردي الموروث

      هذا يعني أن الـ subagents تستفيد من نفس مرونة تحمّل حدّ المعدل مثل الوالد، دون أي إعداد إضافي. يضمن استئجار بيانات الاعتماد لكل مهمة (per-task credential leasing) عدم تعارض الأبناء مع بعضهم عند التناوب على المفاتيح في آن واحد.

      أمان الـ threads​

      يستخدم مجمّع بيانات الاعتماد قفل threading لكل تعديلات الحالة (select()، mark_exhausted_and_rotate()، try_refresh_current()، mark_used()). هذا يضمن وصولًا آمنًا ومتزامنًا عندما يتعامل gateway مع عدة جلسات محادثة في آن واحد.

      عبر العمليات (المتعدّدة subagents، أو gateway مع CLI، أو مهام cron)، تُسلسَل تحديثات OAuth عبر قفل ملف على auth.json. فعندما تنتهي صلاحية منحة (grant) OAuth مشتركة واحدة تحت عمليات متزامنة كثيرة، تقوم عملية واحدة بالضبط بالتحديث؛ وتكتشف البقية أن الرمز المخزّن على القرص لم يعد يطابق الرمز الذي فشل فتتبنّاه بدلًا من إعادة تدوير رمز التحديث أحادي الاستخدام مرة أخرى. أما العملية التي تخسر سباق القفل فتحتفظ بإدخالها سليمًا وتعيد المحاولة — ولا يُسجَّل تنازع القفل أبدًا كفشل في بيانات الاعتماد.

      البنية المعمارية (Architecture)​

      لمخطط تدفق البيانات الكامل، راجع docs/credential-pool-flow.excalidraw في المستودع (repository).

      يتكامل مجمّع بيانات الاعتماد على طبقة تحديد المزوّد:

      1. agent/credential_pool.py — مدير المجمّع: التخزين والاختيار والتناوب وفترات التهدئة؛ agent/credential_pool_admin.py يتولّى تحديد الهدف المُقفل، وإعادة التعيين، والإضافة، والإزالة، وتعديلات الأولوية
      2. hermes_cli/auth_commands.py — أوامر CLI والمعالج التفاعلي
      3. hermes_cli/runtime_provider.py — تحديد بيانات اعتماد واعٍ بالمجمّع
      4. agent/turn_api_error.py — التعافي من الأخطاء: 429/402/401 ← تناوب المجمّع ← احتياطي

      التخزين​

      تُخزَّن حالة المجمّع في ~/.hermes/auth.json ضمن مفتاح credential_pool:

      {
        "version": 1,
        "credential_pool": {
          "openrouter": [
            {
              "id": "abc123",
              "label": "OPENROUTER_API_KEY",
              "auth_type": "api_key",
              "priority": 0,
              "source": "env:OPENROUTER_API_KEY",
              "secret_source": "bitwarden",
              "secret_fingerprint": "sha256:12ab34cd56ef7890",
              "last_status": "ok",
              "request_count": 142
            }
          ],
          "anthropic": [
            {
              "id": "manual1",
              "label": "personal-api-key",
              "auth_type": "api_key",
              "priority": 0,
              "source": "manual",
              "access_token": "sk-ant-api03-..."
            }
          ]
        }
      }

      إدخال OpenRouter أعلاه مستعار من مصدر خارجي، لذا لا يُخزَّن المفتاح الخام في auth.json. أما إدخال Anthropic اليدوي فقد أُضيف عمدًا إلى مخزن بيانات اعتماد Hermes، لذا يبقى رمزه قابلًا للحفظ.

      تُخزَّن الاستراتيجيات في config.yaml (وليس auth.json):

      credential_pool_strategies:
        openrouter: round_robin
        anthropic: least_used

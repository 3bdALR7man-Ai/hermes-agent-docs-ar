      الرؤية (Vision) ولصق الصور

      يدعم Hermes Agent الرؤية متعددة الوسائط (multimodal vision) — إذ يمكنك لصق الصور من الحافظة مباشرةً في CLI وأن تطلب من الوكيل تحليلها أو وصفها أو العمل عليها. تُرسل الصور إلى النموذج ككتل محتوى مرمّزة بـ base64، لذا يستطيع أي نموذج يدعم الرؤية معالجتها.

      نصيحة

      يحصل مشتركو Portal على نماذج تدعم الرؤية (Claude و GPT-5 و Gemini) في الكتالوج نفسه — دون الحاجة إلى بيانات اعتماد إضافية. راجع Nous Portal.

      آلية العمل​

      1. انسخ صورة إلى الحافظة (لقطة شاشة، أو صورة من المتصفح، وما إلى ذلك)
      2. أرفقها باستخدام إحدى الطرق الموضحة أدناه
      3. اكتب سؤالك واضغط Enter
      4. تظهر الصورة كشارة [📎 Image #1] فوق حقل الإدخال
      5. عند الإرسال، تُرسل الصورة إلى النموذج ككتلة محتوى رؤية

      يمكنك إرفاق عدة صور قبل الإرسال — وتحصل كل منها على شارتها الخاصة. اضغط Ctrl+C لمسح جميع الصور المرفقة.

      تُحفظ الصور في ~/.hermes/images/ كملفات PNG بأسماء تتضمن طابعًا زمنيًا.

      طرق اللصق​

      تعتمد طريقة إرفاق الصورة على بيئة الطرفية لديك. فليست كل الطرق تعمل في كل مكان — وإليك التفصيل الكامل:

      الأمر /paste​

      الطريقة الاحتياطية الصريحة الأكثر موثوقية لإرفاق الصور.

      /paste

      اكتب /paste واضغط Enter. يفحص Hermes الحافظة بحثًا عن صورة ويرفقها. هذا هو الخيار الأكثر أمانًا عندما تعيد الطرفية لديك كتابة Cmd+V/Ctrl+V، أو عندما تنسخ صورة فقط ولا يوجد نص مُلصق بنمط bracketed-paste لفحصه.

      Ctrl+V / Cmd+V​

      يتعامل Hermes الآن مع اللصق كتدفق متعدد الطبقات:

      • لصق النص العادي أولًا
      • الرجوع إلى نص الحافظة الأصلية / OSC52 إذا لم تُسلّم الطرفية النص بشكل سليم
      • إرفاق صورة عندما تشير الحافظة أو المحتوى الملصق إلى صورة أو مسار صورة

      هذا يعني أن مسارات لقطات الشاشة المؤقتة في macOS ومعرّفات URI للصور من نوع file://... يمكن إرفاقها فورًا بدلًا من بقائها في محرر الرسائل كنص خام.

      تحذير

      إذا كانت الحافظة تحتوي على صورة فقط (دون نص)، فلا تزال الطرفيات عاجزة عن إرسال بايتات الصورة الثنائية مباشرةً. استخدم /paste كطريقة احتياطية صريحة لإرفاق الصور.

      الأمر /terminal-setup لـ VS Code / Cursor / Windsurf​

      إذا كنت تشغّل TUI داخل طرفية مدمجة محلية من عائلة VS Code على macOS، يستطيع Hermes تثبيت اختصارات workbench.action.terminal.sendSequence الموصى بها لتحسين التكافؤ في الإدخال متعدد الأسطر والتراجع/الإعادة:

      /terminal-setup

      هذا مفيد بشكل خاص عندما يعترض الـ IDE اختصارات Cmd+Enter أو Cmd+Z أو Shift+Cmd+Z. شغّله على الجهاز المحلي فقط — وليس داخل جلسة SSH.

      التوافق مع المنصات​

      البيئة/pasteCmd/Ctrl+V/terminal-setupملاحظات
      macOS Terminal / iTerm2✅✅لا ينطبقأفضل تجربة — الحافظة الأصلية + استعادة مسارات لقطات الشاشة
      Apple Terminal✅✅لا ينطبقإذا أُعيدت كتابة Cmd+←/→/⌫، فاستخدم البدائل Ctrl+A / Ctrl+E / Ctrl+U
      سطح مكتب Linux X11✅✅لا ينطبقيتطلب xclip (apt install xclip)
      سطح مكتب Linux Wayland✅✅لا ينطبقيتطلب wl-paste (apt install wl-clipboard)
      WSL2 (Windows Terminal)✅✅لا ينطبقيستخدم powershell.exe — دون الحاجة إلى تثبيت إضافي
      VS Code / Cursor / Windsurf (محلي)✅✅✅موصى به لتحسين التكافؤ في Cmd+Enter / التراجع / الإعادة
      VS Code / Cursor / Windsurf (عبر SSH)❌²❌²❌³شغّل /terminal-setup على الجهاز المحلي بدلًا من ذلك
      طرفية SSH (أيًّا كانت)❌²❌²لا ينطبقلا يمكن الوصول إلى الحافظة البعيدة

      ² راجع SSH والجلسات البعيدة أدناه ³ يكتب هذا الأمر اختصارات لوحة المفاتيح الخاصة بالـ IDE المحلي، ولا ينبغي تشغيله من المضيف البعيد

      الإعداد حسب المنصة​

      macOS​

      لا يلزم أي إعداد. يستخدم Hermes الأداة osascript (المدمجة في macOS) لقراءة الحافظة. ولأداء أسرع، يمكنك اختياريًا تثبيت pngpaste:

      brew install pngpaste

      Linux (X11)​

      ثبّت xclip:

      # Ubuntu/Debian
      sudo apt install xclip

      # Fedora
      sudo dnf install xclip

      # Arch
      sudo pacman -S xclip

      Linux (Wayland)​

      كثيرًا ما تستخدم أسطح مكتب Linux الحديثة (Ubuntu 22.04+ و Fedora 34+) Wayland افتراضيًا. ثبّت wl-clipboard:

      # Ubuntu/Debian
      sudo apt install wl-clipboard

      # Fedora
      sudo dnf install wl-clipboard

      # Arch
      sudo pacman -S wl-clipboard
      كيف تتحقق مما إذا كنت تستخدم Wayland
      echo $XDG_SESSION_TYPE
      # "wayland" = Wayland, "x11" = X11, "tty" = no display server

      WSL2​

      لا يلزم أي إعداد إضافي. يكتشف Hermes بيئة WSL2 تلقائيًا (عبر /proc/version) ويستخدم powershell.exe للوصول إلى حافظة Windows من خلال System.Windows.Forms.Clipboard في .NET. هذه الإمكانية مدمجة في التشغيل البيني (interop) بين WSL2 و Windows — إذ يتوفر powershell.exe افتراضيًا.

      تُنقل بيانات الحافظة كصورة PNG مرمّزة بـ base64 عبر stdout، لذا لا حاجة إلى تحويل مسارات الملفات أو إلى ملفات مؤقتة.

      ملاحظة حول WSLg

      إذا كنت تستخدم WSLg (أي WSL2 مع دعم الواجهة الرسومية)، يجرّب Hermes مسار PowerShell أولًا، ثم يرجع إلى wl-paste. لا يدعم جسر الحافظة في WSLg سوى صيغة BMP للصور — لذا يحوّل Hermes صور BMP إلى PNG تلقائيًا باستخدام Pillow (إن كانت مثبّتة) أو الأمر convert من ImageMagick.

      التحقق من الوصول إلى الحافظة في WSL2​

      # 1. Check WSL detection
      grep -i microsoft /proc/version

      # 2. Check PowerShell is accessible
      which powershell.exe

      # 3. Copy an image, then check
      powershell.exe -NoProfile -Command "Add-Type -AssemblyName System.Windows.Forms; [System.Windows.Forms.Clipboard]::ContainsImage()"
      # Should print "True"

      SSH والجلسات البعيدة​

      لصق الصور من الحافظة لا يعمل بشكل كامل عبر SSH. عندما تتصل بجهاز بعيد عبر SSH، يعمل Hermes CLI على المضيف البعيد. وأدوات الحافظة (xclip و wl-paste و powershell.exe و osascript) تقرأ حافظة الجهاز الذي تعمل عليه — وهو الخادم البعيد، لا جهازك المحلي. لذلك تتعذر قراءة الصورة الموجودة في حافظتك المحلية من الجانب البعيد.

      قد يُنقل النص أحيانًا عبر لصق الطرفية أو OSC52، لكن الوصول إلى الصور في الحافظة ومسارات لقطات الشاشة المؤقتة المحلية يظل مرتبطًا بالجهاز الذي يشغّل Hermes.

      حلول بديلة لـ SSH​

      1. ارفع ملف الصورة — احفظ الصورة محليًا، ثم ارفعها إلى الخادم البعيد عبر scp، أو مستكشف الملفات في VSCode (بالسحب والإفلات)، أو أي وسيلة لنقل الملفات. ثم أشر إليها بمسارها. (من المخطط إضافة أمر /attach <filepath> في إصدار مستقبلي.)

      2. استخدم URL — إذا كانت الصورة متاحة عبر الإنترنت، فالصق الـ URL في رسالتك فحسب. يستطيع الوكيل استخدام vision_analyze لفحص أي صورة عبر الـ URL الخاص بها مباشرةً.

      3. تمرير X11 (X11 forwarding) — اتصل باستخدام ssh -X لتمرير X11. يتيح ذلك لـ xclip على الجهاز البعيد الوصول إلى حافظة X11 المحلية لديك. يتطلب ذلك خادم X يعمل محليًا (XQuartz على macOS، ومدمج في أسطح مكتب Linux X11). وهو بطيء مع الصور الكبيرة.

      4. استخدم منصة مراسلة — أرسل الصور إلى Hermes عبر Telegram أو Discord أو Slack أو WhatsApp. تتعامل هذه المنصات مع رفع الصور بشكل أصلي ولا تتأثر بقيود الحافظة/الطرفية.

      لماذا لا تستطيع الطرفيات لصق الصور​

      هذا مصدر شائع للالتباس، لذا إليك الشرح التقني:

      الطرفيات واجهات نصية. عندما تضغط Ctrl+V (أو Cmd+V)، يقوم محاكي الطرفية بما يلي:

      1. يقرأ الحافظة بحثًا عن محتوى نصي
      2. يغلّفه بتسلسلات الهروب الخاصة بـ bracketed paste
      3. يرسله إلى التطبيق عبر تدفق النص في الطرفية

      إذا كانت الحافظة تحتوي على صورة فقط (دون نص)، فلن يكون لدى الطرفية ما ترسله. فلا يوجد تسلسل هروب قياسي في الطرفيات لبيانات الصور الثنائية، ولذلك لا تفعل الطرفية شيئًا ببساطة.

      ولهذا يستخدم Hermes فحصًا منفصلًا للحافظة — فبدلًا من استقبال بيانات الصورة عبر حدث اللصق في الطرفية، يستدعي أدوات على مستوى نظام التشغيل (osascript و powershell.exe و xclip و wl-paste) مباشرةً عبر عملية فرعية (subprocess) لقراءة الحافظة بشكل مستقل.

      النماذج المدعومة​

      يعمل لصق الصور مع أي نموذج يدعم الرؤية. تُرسل الصورة كـ data URL مرمّز بـ base64 بصيغة محتوى الرؤية الخاصة بـ OpenAI:

      {
        "type": "image_url",
        "image_url": {
          "url": "data:image/png;base64,..."
        }
      }

      تدعم معظم النماذج الحديثة هذه الصيغة، ومنها GPT-4 Vision و Claude (مع الرؤية) و Gemini، والنماذج مفتوحة المصدر متعددة الوسائط المقدَّمة عبر OpenRouter.

      توجيه الصور (النماذج الداعمة للرؤية مقابل النماذج النصية فقط)​

      عندما يرفق المستخدم صورة — من حافظة CLI، أو عبر الـ gateway (صورة في Telegram/Discord)، أو من أي نقطة دخول أخرى — يوجّهها Hermes بناءً على ما إذا كان نموذجك الحالي يدعم الرؤية فعلًا:

      نموذجكما يحدث للصورة
      يدعم الرؤية (GPT-4V و Claude مع الرؤية و Gemini و Qwen-VL و MiMo-VL و DeepSeek Flash / V4.1-Flash وغيرها)تُرسل بكسلات حقيقية باستخدام صيغة محتوى الصور الأصلية لدى المزوّد الموضحة أعلاه، دون طبقة ملخص نصي.
      نصي فقط (DeepSeek V4 Pro و DeepSeek V3 والنماذج مفتوحة المصدر الأصغر، و endpoints المحادثة القديمة النصية فقط)تُوجَّه عبر الأداة المساعدة vision_analyze — إذ يصف نموذج رؤية مساعد الصورة، ويُحقن الوصف النصي في المحادثة.

      لا تحتاج إلى ضبط ذلك — إذ يبحث Hermes عن قدرات نموذجك الحالي في البيانات الوصفية للمزوّد ويختار المسار الصحيح تلقائيًا. والأثر العملي: يمكنك التبديل بين النماذج الداعمة للرؤية وغير الداعمة لها في منتصف الجلسة، ويستمر التعامل مع الصور "بلا مشكلات" دون تغيير سير عملك. وتحصل النماذج النصية فقط على سياق متماسك عن الصورة بدلًا من حمولة متعددة الوسائط معطوبة كانت ستضطر إلى رفضها.

      يمكن ضبط النموذج المساعد الذي يتولى مسار الوصف النصي ضمن auxiliary.vision — راجع النماذج المساعدة (Auxiliary Models).

      للأداة vision_analyze السلوك المزدوج نفسه​

      تتبع الأداة vision_analyze نفسها التوجيه ذاته. فعندما يكون النموذج الرئيسي النشط داعمًا للرؤية ويدعم مزوّده محتوى الصور داخل نتائج الأدوات (حاليًا حزم Anthropic و OpenAI و Azure-OpenAI و Gemini 3.x)، تتجاوز vision_analyze أداة الوصف المساعدة وتعيد بكسلات الصورة الخام داخل غلاف نتيجة أداة متعدد الوسائط. فيرى النموذج الرئيسي الصورة بشكل أصلي في دوره التالي — دون استدعاء مساعد، ودون فقدان معلومات بسبب الملخص النصي، ودون تأخير إضافي.

      أما مع النماذج الرئيسية النصية فقط (أو المزوّدين الذين لا تنقل قناة نتائج الأدوات لديهم الصور)، فترجع vision_analyze إلى المسار القديم: إذ تطلب من نموذج الرؤية المساعد المضبوط وصف الصورة وتعيد الوصف كنص عادي. وفي الحالتين يبقى توقيع استدعاء الأداة نفسه — فالأداة هي التي تقرر المسار الذي تسلكه وقت التشغيل بناءً على النموذج النشط.

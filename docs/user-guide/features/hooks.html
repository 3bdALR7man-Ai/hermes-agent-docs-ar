      Event Hooks

      لدى Hermes أربعة أنظمة hooks تُشغّل كودًا مخصّصًا عند نقاط رئيسية من دورة الحياة:

      النظاميُسجَّل عبريعمل فيحالة الاستخدام
      Gateway hooksHOOK.yaml + handler.py في ~/.hermes/hooks/الـ Gateway فقطالتسجيل، التنبيهات، webhooks
      Plugin hooksctx.register_hook() في إضافة (plugin)CLI + Gatewayاعتراض الأدوات، القياسات، الضوابط الوقائية
      Shell hooksكتلة hooks: في config.yaml الخاص بالـ profile تشير إلى سكربتات shellCLI + Gateway + محادثة Desktop/TUI/لوحة التحكمسكربتات جاهزة للحجب والتنسيق التلقائي وحقن السياق
      Outbound webhooksقائمة hooks.outbound: في ~/.hermes/config.yamlCLI + Gatewayدفع أحداث دورة حياة موقّعة إلى نقاط نهاية HTTP خارجية — CI، لوحات تحكم، وكلاء آخرون

      تُعزَل أخطاء ردود نداء الـ hooks وتُسجَّل بدلًا من تعطيل الوكيل. ليست كل الـ hooks سلبية: يمكن لـ hooks التوجيه/التحكم تغيير التدفّق، ويمكن للتحويلات استبدال المحتوى، ويمكن لـ hook من نوع pre_tool_call على مستوى shell أن يحجب أو يفشل بأمان.

      Gateway Event Hooks​

      تُطلَق Gateway hooks تلقائيًا أثناء عمل الـ gateway (Telegram، Discord، Slack، WhatsApp، Teams) دون حجب خط أنابيب الوكيل الرئيسي.

      إنشاء Hook​

      كل hook هو مجلد تحت ~/.hermes/hooks/ يحتوي ملفين:

      ~/.hermes/hooks/
      └── my-hook/
          ├── HOOK.yaml      # Declares which events to listen for
          └── handler.py     # Python handler function

      HOOK.yaml​

      name: my-hook
      description: Log all agent activity to a file
      events:
        - agent:start
        - agent:end
        - agent:step

      تحدّد قائمة events الأحداث التي تُشغِّل مُعالِجك. يمكنك الاشتراك في أي تركيبة من الأحداث، بما فيها أشكال جامعة مثل command:*.

      handler.py​

      import json
      from datetime import datetime
      from pathlib import Path

      LOG_FILE = Path.home() / ".hermes" / "hooks" / "my-hook" / "activity.log"

      async def handle(event_type: str, context: dict):
          """Called for each subscribed event. Must be named 'handle'."""
          entry = {
              "timestamp": datetime.now().isoformat(),
              "event": event_type,
              **context,
          }
          with open(LOG_FILE, "a") as f:
              f.write(json.dumps(entry) + "\n")

      قواعد المُعالِج:

      • يجب أن يُسمَّى handle
      • يستقبل event_type (نص) وcontext (قاموس)
      • يمكن أن يكون async def أو def عادية — كلاهما يعمل
      • تُلتقَط الأخطاء وتُسجَّل، دون أن تُعطِّل الوكيل أبدًا

      الأحداث المتاحة​

      الحدثمتى يُطلَقمفاتيح السياق
      gateway:startupبدء عملية الـ gatewayplatforms (قائمة أسماء المنصات النشطة)
      session:startإنشاء جلسة مراسلة جديدةplatform، user_id، session_id، session_key
      session:endانتهاء جلسة (قبل إعادة الضبط)platform، user_id، session_key
      session:resetشغّل المستخدم /new أو /resetplatform، user_id، session_key
      session:compressاكتمال ضغط السياق لجلسةplatform، session_id، old_session_id (فارغ عند الضغط في المكان نفسه)، in_place (منطقي — true = ضُغط النص في نفس المعرّف، false = دُوِّر من old_session_id)، compression_count
      agent:startيبدأ الوكيل معالجة رسالةplatform، user_id، chat_id، thread_id (معرّف موضوع منتدى/جذر thread؛ فارغ خارج موضوع)، chat_type ("dm" | "group" | "forum"؛ فارغ إن كان مجهولًا)، session_id، message (مُقتصَرة على 500 حرف)
      agent:stepكل تكرار من حلقة استدعاء الأدواتplatform، user_id، session_id، iteration، tool_names
      agent:endانتهاء الوكيل من المعالجةنفس مفاتيح agent:start، بالإضافة إلى response (مُقتصَرة على 500 حرف)
      reaction:addedأُضيف تفاعل إيموجي إلى رسالة يستطيع البوت رؤيتها (adapter الخاص بـ Slack حاليًا). يتطلّب صلاحية reactions:read + اشتراك حدث البوت reaction_added؛ ويجب أن يكون البوت عضوًا في القناة.platform، reaction، user_id، item_user_id، item_type، channel_id، message_ts، team_id، event_ts، raw_event
      reaction:removedأُزيل تفاعل إيموجي من رسالة يستطيع البوت رؤيتها. يتطلّب اشتراك حدث البوت reaction_removed.نفس شكل reaction:added
      command:*تنفيذ أي slash commandplatform، user_id، command، args

      مطابقة الرموز الجامعة​

      تُطلَق المُعالِجات المسجَّلة لـ command:* عند أي حدث command: (command:model، command:reset، إلخ). راقب كل الـ slash commands باشتراك واحد.

      الردود ضمن المواضيع

      يجب أن يُضمِّن المُعالِج الذي يرسل رسالة متابعة إلى نفس موضوع منتدى Telegram العنصر message_thread_id=int(thread_id) عندما يكون chat_type == "forum" وthread_id غير فارغ.

      أمثلة​

      تنبيه Telegram عند المهام الطويلة​

      أرسل لنفسك رسالة عندما يتجاوز الوكيل 10 خطوات:

      # ~/.hermes/hooks/long-task-alert/HOOK.yaml
      name: long-task-alert
      description: Alert when agent is taking many steps
      events:
        - agent:step
      # ~/.hermes/hooks/long-task-alert/handler.py
      import os
      import httpx

      THRESHOLD = 10
      BOT_TOKEN = os.getenv("TELEGRAM_BOT_TOKEN")
      CHAT_ID = os.getenv("TELEGRAM_HOME_CHANNEL")

      async def handle(event_type: str, context: dict):
          iteration = context.get("iteration", 0)
          if iteration == THRESHOLD and BOT_TOKEN and CHAT_ID:
              tools = ", ".join(context.get("tool_names", []))
              text = f"⚠️ Agent has been running for {iteration} steps. Last tools: {tools}"
              async with httpx.AsyncClient() as client:
                  await client.post(
                      f"https://api.telegram.org/bot{BOT_TOKEN}/sendMessage",
                      json={"chat_id": CHAT_ID, "text": text},
                  )

      مُسجِّل استخدام الأوامر​

      تتبّع أي slash commands تُستخدَم:

      # ~/.hermes/hooks/command-logger/HOOK.yaml
      name: command-logger
      description: Log slash command usage
      events:
        - command:*
      # ~/.hermes/hooks/command-logger/handler.py
      import json
      from datetime import datetime
      from pathlib import Path

      LOG = Path.home() / ".hermes" / "logs" / "command_usage.jsonl"

      def handle(event_type: str, context: dict):
          LOG.parent.mkdir(parents=True, exist_ok=True)
          entry = {
              "ts": datetime.now().isoformat(),
              "command": context.get("command"),
              "args": context.get("args"),
              "platform": context.get("platform"),
              "user": context.get("user_id"),
          }
          with open(LOG, "a") as f:
              f.write(json.dumps(entry) + "\n")

      Webhook بدء الجلسة​

      أرسل POST إلى خدمة خارجية عند الجلسات الجديدة:

      # ~/.hermes/hooks/session-webhook/HOOK.yaml
      name: session-webhook
      description: Notify external service on new sessions
      events:
        - session:start
        - session:reset
      # ~/.hermes/hooks/session-webhook/handler.py
      import httpx

      WEBHOOK_URL = "https://your-service.example.com/hermes-events"

      async def handle(event_type: str, context: dict):
          async with httpx.AsyncClient() as client:
              await client.post(WEBHOOK_URL, json={
                  "event": event_type,
                  **context,
              }, timeout=5)

      درس تطبيقي: BOOT.md — تشغيل قائمة تحقّق عند بدء التشغيل في كل إقلاع للـ gateway​

      نمط شائع من المجتمع: ضع قائمة تحقّق بصيغة Markdown في ~/.hermes/BOOT.md، واجعل الوكيل يُشغّلها مرة واحدة في كل مرة يبدأ فيها الـ gateway. مفيد لـ "في كل إقلاع، تحقّق من إخفاقات cron ليلًا وأبلغني على Discord إن فشل أي شيء"، أو "لخّص آخر 24 ساعة من deploy.log وانشره في Slack #ops".

      يُظهر هذا الدرس التطبيقي كيفية بناء ذلك بنفسك كـ hook مُعرَّف من المستخدم. لا يشحن Hermes hook مدمج لـ BOOT.md — بل تُعِدّ بالضبط السلوك الذي تريده.

      ما الذي نبنيه​

      1. ملف في ~/.hermes/BOOT.md يحتوي تعليمات بدء تشغيل بلغة طبيعية.
      2. gateway hook يُطلَق عند gateway:startup، ويُنشئ وكيلًا لمرة واحدة بنموذج/بيانات اعتماد الـ gateway الخاص بك المُحلَّلة، ويُشغّل تعليمات BOOT.md.
      3. عُرف [SILENT] ليتمكّن الوكيل من الانسحاب من إرسال رسالة عندما لا يوجد ما يُبلَّغ عنه.

      الخطوة 1: اكتب قائمة تحقّقك​

      أنشئ ~/.hermes/BOOT.md. اكتبها كما لو كنت تعطي تعليمات لمساعد بشري:

      # Startup Checklist

      1. Run `hermes cron list` and check if any scheduled jobs failed overnight.
      2. If any failed, summarize them for Discord #ops (the hook delivers your final response to its configured target).
      3. Check if `/opt/app/deploy.log` has any ERROR lines from the last 24 hours. If yes, summarize them and include in the same report.
      4. If nothing went wrong, reply with only `[SILENT]` so no message is sent.

      يرى الوكيل هذا كجزء من الـ prompt الخاص به، لذا فإن أي شيء يمكنك وصفه بلغة عادية يعمل — استدعاءات الأدوات، أوامر shell، إرسال الرسائل، تلخيص الملفات.

      الخطوة 2: أنشئ الـ hook​

      ~/.hermes/hooks/boot-md/
      ├── HOOK.yaml
      └── handler.py

      ~/.hermes/hooks/boot-md/HOOK.yaml

      name: boot-md
      description: Run ~/.hermes/BOOT.md on gateway startup
      events:
        - gateway:startup

      ~/.hermes/hooks/boot-md/handler.py

      """Run ~/.hermes/BOOT.md on every gateway startup."""

      import logging
      import threading
      from pathlib import Path

      logger = logging.getLogger("hooks.boot-md")

      BOOT_FILE = Path.home() / ".hermes" / "BOOT.md"


      def _build_prompt(content: str) -> str:
          return (
              "You are running a startup boot checklist. Follow the instructions "
              "below exactly.\n\n"
              "---\n"
              f"{content}\n"
              "---\n\n"
              "Execute each instruction. Put any user-facing summary in your "
              "final response — the hook delivers it to the configured channel "
              "(e.g. Discord or Slack); you do not send messages yourself.\n"
              "If nothing needs attention and there is nothing to report, reply "
              "with ONLY: [SILENT]"
          )


      def _run_boot_agent(content: str) -> None:
          """Spawn a one-shot agent and execute the checklist.

          Uses the gateway's resolved model and runtime credentials so this works
          against custom endpoints, aggregators, and OAuth-based providers alike.
          """
          try:
              from gateway.run import _resolve_gateway_model, _resolve_runtime_agent_kwargs
              from run_agent import AIAgent

              agent = AIAgent(
                  model=_resolve_gateway_model(),
                  **_resolve_runtime_agent_kwargs(),
                  platform="gateway",
                  quiet_mode=True,
                  skip_context_files=True,
                  skip_memory=True,
                  max_iterations=20,
              )
              result = agent.run_conversation(_build_prompt(content))
              response = (result.get("final_response", "") or "").strip()
              if response.upper() not in {"[SILENT]", "SILENT", "NO_REPLY", "NO REPLY"}:
                  logger.info("boot-md completed: %s", response[:200])
              else:
                  logger.info("boot-md completed (nothing to report)")
          except Exception as e:
              logger.error("boot-md agent failed: %s", e)


      async def handle(event_type: str, context: dict) -> None:
          if not BOOT_FILE.exists():
              return
          content = BOOT_FILE.read_text(encoding="utf-8").strip()
          if not content:
              return

          logger.info("Running BOOT.md (%d chars)", len(content))

          # Background thread so gateway startup isn't blocked on a full agent turn.
          thread = threading.Thread(
              target=_run_boot_agent,
              args=(content,),
              name="boot-md",
              daemon=True,
          )
          thread.start()

      السطران الأساسيان:

      • تقرأ _resolve_gateway_model() النموذج المُعدّ حاليًا للـ gateway.
      • تُحلّ _resolve_runtime_agent_kwargs() بيانات اعتماد المزوّد بنفس طريقة دور gateway عادي — بما في ذلك مفاتيح API وعناوين URL الأساسية ورموز OAuth ومجمّعات بيانات الاعتماد.

      بدون هذين، يعود AIAgent() المجرد إلى الافتراضيات المدمجة ويُخفق بخطأ 401 أمام أي نقطة نهاية غير افتراضية.

      الخطوة 3: اختبرها​

      أعد تشغيل الـ gateway:

      hermes gateway restart

      راقب السجلّات:

      hermes logs --follow --level INFO | grep boot-md

      يجب أن ترى Running BOOT.md (N chars) متبوعًا إمّا بـ boot-md completed: ... (ملخّص لما فعله الوكيل) أو boot-md completed (nothing to report) عندما يرد الوكيل برمز صمت دقيق مثل [SILENT].

      احذف ~/.hermes/BOOT.md لتعطيل قائمة التحقّق — يبقى الـ hook مُحمَّلًا لكنه يتخطّى بصمت عندما لا يكون الملف موجودًا.

      توسعة النمط​

      • قوائم تحقّق واعية بالجدول: اعتمد على datetime.now().weekday() داخل تعليمات BOOT.md ("إذا كان الإثنين، تحقّق أيضًا من سجلّ النشر الأسبوعي"). التعليمات نص حرّ، لذا فأي شيء يستطيع الوكيل الاستدلال عليه مقبول.
      • قوائم تحقّق متعددة: وجّه الـ hook إلى ملف مختلف (STARTUP.md، MORNING.md، إلخ) وسجّل مجلدات hook منفصلة لكل واحد.
      • البديل بلا وكيل: إن لم تحتج إلى حلقة وكيل كاملة، تخطَّ AIAgent كليًا واجعل المُعالِج ينشر إشعارًا ثابتًا مباشرة عبر httpx. أرخص وأسرع وبلا اعتماد على مزوّد.

      لماذا ليس هذا ميزة مدمجة​

      شحن إصدار سابق من Hermes هذا كـ hook مدمج وكان يُنشئ وكيلًا بصمت بافتراضيات مجردة عند كل إقلاع للـ gateway. فاجأ ذلك المستخدمين ذوي نقاط النهاية المخصّصة وجعل الميزة غير مرئية للمستخدمين الذين لم يعرفوا أنها تعمل. الحفاظ عليها كنمط موثَّق — تبنيه أنت، في مجلد الـ hooks الخاص بك — يعني أنك ترى بالضبط ما يفعله وتختار المشاركة فيه بكتابة الملفات.

      كيف يعمل​

      1. عند إقلاع الـ gateway، يفحص HookRegistry.discover_and_load() مجلد ~/.hermes/hooks/
      2. يُحمَّل كل مجلد فرعي يحتوي HOOK.yaml + handler.py ديناميكيًا
      3. تُسجَّل المُعالِجات للأحداث المُعلَنة الخاصة بها
      4. عند كل نقطة من دورة الحياة، يُطلق hooks.emit() كل المُعالِجات المطابقة
      5. تُلتقَط الأخطاء في أي مُعالِج وتُسجَّل — لا يُعطِّل hook معطوب الوكيل أبدًا
      معلومة

      تُطلَق Gateway hooks فقط في الـ gateway (Telegram، Discord، Slack، WhatsApp، Teams). لا يُحمِّل CLI gateway hooks. للـ hooks التي تعمل في كل مكان، استخدم plugin hooks.

      Plugin Hooks​

      يمكن لـالإضافات (Plugins) تسجيل hooks تُطلَق في جلسات CLI والـ gateway معًا. تُسجَّل هذه برمجيًا عبر ctx.register_hook() في دالة register() الخاصة بإضافتك.

      لتفاصيل تعبئة الإضافات وتسجيلها، راجع دليل الإضافات (Plugins).

      def register(ctx):
          ctx.register_hook("pre_tool_call", my_tool_observer)
          ctx.register_hook("post_tool_call", my_tool_logger)
          ctx.register_hook("pre_llm_call", my_memory_callback)
          ctx.register_hook("post_llm_call", my_sync_callback)
          ctx.register_hook("on_session_start", my_init_callback)
          ctx.register_hook("on_session_end", my_cleanup_callback)
          # Kanban board lifecycle (dependency-wait blocking may fire inside its transaction):
          ctx.register_hook("kanban_task_claimed", my_claim_callback)     # dispatcher process
          ctx.register_hook("kanban_task_completed", my_done_callback)    # worker process
          ctx.register_hook("kanban_task_blocked", my_blocked_callback)   # worker process

      قواعد عامة لكل الـ hooks:

      • تستقبل ردود النداء وسائط بالكلمة المفتاحية (keyword arguments). اقبل دائمًا **kwargs للتوافق المستقبلي.
      • تُسجَّل استثناءات ردود النداء وتُتخطَّى؛ وتستمر ردود النداء اللاحقة.
      • إذا كان رد نداء إضافة Python على hook مقيَّد بمهلة زمنية (مراقِبات المسار الساخن مثل post_tool_call / pre_llm_call، بالإضافة إلى hook السياسة pre_tool_call) محجوبًا لمدة أطول من plugins.hook_callback_timeout (الافتراضي 30 ثانية، اضبطها على 0 للتعطيل، والحد الأقصى 600)، يُهجَر دون انتظار عامل العمل حتى تستمر حلقة الوكيل. ردود نداء pre_tool_call التي انتهت مهلتها أو ما تزال قيد التشغيل تفشل بأمان (تحجب الأداة)؛ بينما ردود النداء المقيَّدة الأخرى تفشل بانفتاح (تُتخطَّى). لا تُنقَل الـ hooks ذات عقد الخيط المستدعي الموثَّق (subagent_stop) إلى عامل مهلة زمنية أبدًا. تحتفظ shell hooks بـ timeout خاص بها لكل إدخال.
      • الكتالوج أدناه وصفي: تتجاهل المراقِبات القيم المُعادة، وتقبل التحويلات أول استبدال نصّي صالح، وتستهلك hooks التوجيه/التحكم أشكالًا مُعادة موثَّقة. Plugin middleware سجلّ وسطح منفصلان، لا فئة hook أخرى.
      • حقول الارتباط مثل turn_id، وapi_request_id، وtask_id، وsession_id، وapi_call_count خاصة بكل hook وقد تكون غائبة. عامل المعرّفات كقيم مبهمة.
      • صحة أسماء الأحداث وقت التشغيل تأتي من hermes_cli.plugins.VALID_HOOKS. يسرد hermes hooks list الـ shell/outbound hooks المُعدَّة، لا كل حدث متاح؛ ويُبلِغ hermes hooks test <event> عن المجموعة الصالحة فقط عندما يُمرَّر حدث غير صالح.

      أقسام system prompt آمنة للتخزين المؤقت​

      يمكن للإضافات التي تحتاج توجيهًا دائمًا وثابت الحضور تسجيل قسم system prompt مُقيَّد بدلًا من حقن نفس النص عبر pre_llm_call في كل دور:

      def board_rules(session_info):
          return f"Apply the worker rules for profile {session_info['profile_name']}."

      def register(ctx):
          ctx.register_system_prompt_section(
              "kanban-advanced.worker-rules",
              board_rules,                       # a string is also accepted
              position="after_memory",
              max_chars=4000,
          )

      العقد ضيّق عن قصد:

      • المعرّفات عالمية وثابتة ومكوَّنة من 1 إلى 128 حرفًا صغيرًا باستخدام فقط الحروف والأرقام و. و_ و-. تُرفَض المعرّفات المكرَّرة.
      • after_memory هو مرساة الوضع الوحيدة. تُرتَّب الأقسام حسب المعرّف، وتُعرَض بعد سياق الذاكرة/الـ profile وقبل بيانات الجلسة الوصفية؛ لا يمكن للإضافات إعادة ترتيب أو استبدال محتوى الـ prompt الأساسي.
      • يستقبل الكائن القابل للاستدعاء تعيينًا للقراءة فقط يحوي session_id، وmodel، وprovider، وplatform، وprofile_name، وcwd. يعمل مرة واحدة لكل جلسة جديدة. تُجمَّد وحداته البايتية المُصيَّرة عند الضغط وتُستعاد من system prompt الكامل المخزَّن مسبقًا بعد إعادة تشغيل/استئناف العملية؛ لا تُعاد قراءة حالة الإضافة لجلسة موجودة.
      • max_chars محدود بـ 4000 حرف. كل أقسام الإضافات معًا، بما فيها عناوين المراجعة الخاصة بها، محدودة بـ 8000 حرف و32 قسمًا. تُتخطَّى الأقسام الفارغة، أو غير النصية، أو الزائدة الحجم، أو المتجاوزة للميزانية الإجمالية، أو التي تُثير استثناءً، مع تحذير؛ ويستمر بناء الـ prompt.
      • يُذكَر كل قسم مقبول باسمه في الـ prompt ويُسجَّل عند بدء الجلسة مع إضافته وموضعه وعدد أحرفه.

      استخدم pre_llm_call للسياق الديناميكي الحقيقي لكل دور. لا يوجد عن قصد أي hook لتلميحات بيئة الإضافات في هذا العقد: تغيير المجلد الحالي، أو الفرع، أو بيانات بيئة أخرى يجب ألا يُغيِّر بصمت الـ prompt المخزَّن مؤقتًا لجلسة. مثل هذا الـ hook يحتاج مستهلكًا ملموسًا ونفس دلالات التجميد/الاستئناف الآمنة قبل أن يمكن إضافته.

      Hooks مخرجات التدفّق (streaming)​

      تتيح هذه الـ hooks المُخصَّصة للمراقبة فقط للإضافات استهلاك مخرجات LLM المُتدفِّقة للقياسات، أو لوحات التحكم الحية، أو خطوط أنابيب TTS دون تغيير الردّ. تُسلَّم عبر طوابير مُقيَّدة يملكها المضيف بعامل خلفي واحد لكل رد نداء مُسجَّل، لذا لا تعمل ردود نداء الإضافات أبدًا داخل مسار الرموز مباشرة. إذا تعطّل رد نداء واحد، يمكن فقط لطابور ذلك الرد أن يمتلئ ويُسقِط أقدم حدث مراقبة معلَّق لديه؛ تستمر المراقِبات الأخرى في استقبال الأحداث بشكل مستقل.

      سجّلها كأي plugin hook آخر:

      def on_delta(delta, kind, model, provider, **kwargs):
          if kind == "text":
              print(delta, end="", flush=True)

      def register(ctx):
          ctx.register_hook("on_stream_delta", on_delta)

      pre_tool_call​

      يُطلَق قبل تنفيذ الأداة مباشرة — سواء كانت أداة مدمجة أو أداة تابعة لإضافة.

      توقيع الاستدعاء (callback):

      def my_callback(tool_name: str, args: dict, task_id: str, **kwargs):
      المعاملالنوعالوصف
      tool_namestrاسم الأداة على وشك التنفيذ (مثل "terminal" أو "web_search" أو "read_file")
      argsdictالوسائط التي مرّرها النموذج إلى الأداة
      task_idstrمعرّف الجلسة/المهمة. سلسلة فارغة إن لم يُضبط.

      يُطلَق: في model_tools.py، داخل handle_function_call()، قبل تشغيل معالج الأداة. يُطلَق مرة واحدة لكل استدعاء أداة — إذا استدعى النموذج 3 أدوات بالتوازي، يُطلَق 3 مرات.

      قيمة الإرجاع — الحظر أو طلب الموافقة:

      return {"action": "block", "message": "Reason the tool call was blocked"}
      # or
      return {"action": "approve", "message": "Why approval is required", "rule_key": "optional:scope"}

      يفوز أول توجيه صالح (إضافات Python المسجّلة أولًا، ثم hooks الـ shell). يتطلّب block رسالة message غير فارغة ويوقف الأداة فورًا واضعًا هذا النص خطأً يُعاد إلى النموذج. يُصعّد approve الاستدعاء إلى بوابة موافقة بشرية موجودة أصلًا؛ حقلا message و rule_key اختياريان، وأي رفض أو انتهاء مهلة أو خطأ في البوابة يفشل بشكل مغلق (fail closed). القيم الأخرى المُعادة تُتجاهَل، لذا تبقى الاستدعاءات القائمة على المراقبة فقط تعمل دون تغيير.

      قيمة الإرجاع — إعادة كتابة وسائط الأداة:

      return {"action": "modify", "args": {"new_string": "fixed content"}}

      يُدمَج قاموس args المُعاد دمجًا سطحيًا (shallow-merge) فوق وسائط الأداة الأصلية قبل تنفيذ الأداة. تتراكم عدة hooks من نوع modify — تُدمَج مفاتيح كل hook في قاموس تراكمي واحد مبني على الوسائط الأصلية، بحيث ينجو تغيير hook A لـ path وتغيير hook B لـ content معًا. وإذا عدّل hookان نفس المفتاح، يفوز الأحدث.

      تقبل hooks الـ shell أيضًا الصيغة المتوافقة مع Claude Code:

      {"decision": "modify", "tool_input": {"new_string": "fixed content"}}

      تُطبَّع كلتا الصيغتين داخليًا إلى {"action": "modify", "args": {...}}.

      إذا تجاوز استدعاء pre_tool_call مهلة plugins.hook_callback_timeout (أو كان لا يزال قيد التشغيل من إطلاق سابق انتهت مهلته)، فإن Hermes يفشل بشكل مغلق: تُحظر الأداة برسالة انتهاء مهلة بدلًا من المتابعة دون قرار سياسة.

      حالات الاستخدام: التسجيل، سجلات التدقيق، عدّادات استدعاءات الأدوات، حظر العمليات الخطرة، تحديد المعدل (rate limiting)، فرض السياسات لكل مستخدم، تعقيم الوسائط، إعادة كتابة المسارات، حقن معاملات افتراضية.

      مثال — سجل تدقيق لاستدعاءات الأدوات:

      import json, logging
      from datetime import datetime

      logger = logging.getLogger(__name__)

      def audit_tool_call(tool_name, args, task_id, **kwargs):
          logger.info("TOOL_CALL session=%s tool=%s args=%s",
                      task_id, tool_name, json.dumps(args)[:200])

      def register(ctx):
          ctx.register_hook("pre_tool_call", audit_tool_call)

      مثال — تحذير عند استخدام أدوات خطرة:

      post_tool_call​

      يُطلَق مباشرة بعد عودة كل تنفيذ للأداة.

      توقيع الاستدعاء:

      def my_callback(tool_name: str, args: dict, result: str, task_id: str,
                      duration_ms: int, **kwargs):
      المعاملالنوعالوصف
      tool_namestrاسم الأداة التي نُفّذت للتو
      argsdictالوسائط التي مرّرها النموذج إلى الأداة
      resultstrالقيمة المُعادة من الأداة (دائمًا سلسلة JSON)
      task_idstrمعرّف الجلسة/المهمة. سلسلة فارغة إن لم يُضبط.
      duration_msintمدة تنفيذ الأداة بالميلي ثانية (تُقاس بـ time.monotonic() حول registry.dispatch()).

      يُطلَق: في model_tools.py، داخل handle_function_call()، بعد عودة معالج الأداة. يُطلَق مرة واحدة لكل استدعاء أداة. لا يُطلَق إذا رفعت الأداة استثناءً غير مُعالَج (يُلتقَط الخطأ ويُعاد كسلسلة JSON للخطأ بدلًا من ذلك، ويُطلَق post_tool_call بتلك السلسلة كـ result).

      قيمة الإرجاع: تُتجاهَل.

      حالات الاستخدام: تسجيل نتائج الأدوات، جمع المقاييس، تتبّع معدلات نجاح/فشل الأدوات، لوحات مراقبة زمن الاستجابة، تنبيهات ميزانية لكل أداة، إرسال إشعارات عند اكتمال أدوات معيّنة.

      مثال — تتبّع مقاييس استخدام الأدوات:

      from collections import Counter, defaultdict
      import json

      _tool_counts = Counter()
      _error_counts = Counter()
      _latency_ms = defaultdict(list)

      def track_metrics(tool_name, result, duration_ms=0, **kwargs):
          _tool_counts[tool_name] += 1
          _latency_ms[tool_name].append(duration_ms)
          try:
              parsed = json.loads(result)
              if "error" in parsed:
                  _error_counts[tool_name] += 1
          except (json.JSONDecodeError, TypeError):
              pass

      def register(ctx):
          ctx.register_hook("post_tool_call", track_metrics)

      pre_llm_call​

      يُطلَق مرة واحدة لكل دور (turn)، قبل بدء حلقة استدعاء الأدوات. تُجمَّع كل قيم الإرجاع الصالحة من الاستدعاءات بترتيب الإضافات وتُحقَن في رسالة المستخدم لهذا الدور.

      توقيع الاستدعاء:

      def my_callback(session_id: str, user_message: str, conversation_history: list,
                      is_first_turn: bool, model: str, platform: str, **kwargs):
      المعاملالنوعالوصف
      session_idstrمعرّف فريد للجلسة الحالية
      user_messagestrرسالة المستخدم الأصلية لهذا الدور (قبل أي حقن للمهارات)
      conversation_historylistنسخة من قائمة الرسائل الكاملة (بصيغة OpenAI: [{"role": "user", "content": "..."}])
      is_first_turnboolTrue إذا كان هذا أول دور في جلسة جديدة، False في الأدوار اللاحقة
      modelstrمعرّف النموذج (مثل "anthropic/claude-sonnet-4.6")
      platformstrمكان تشغيل الجلسة: "cli"، "telegram"، "discord"، إلخ

      يُطلَق: في agent/turn_context.py (تحضير الدور لـ run_conversation() في agent/conversation_loop.py)، بعد ضغط السياق (context compression) وقبل حلقة while الرئيسية. يُطلَق مرة واحدة لكل استدعاء لـ run_conversation() (أي مرة واحدة لكل دور للمستخدم)، وليس مرة لكل استدعاء API ضمن حلقة الأدوات.

      قيمة الإرجاع: إذا أعاد الاستدعاء قاموسًا يحوي مفتاح "context"، أو سلسلة نصية بسيطة غير فارغة، يُضاف النص إلى رسالة المستخدم لهذا الدور. أعِد None لعدم الحقن.

      # Inject context
      return {"context": "Recalled memories:\n- User likes Python\n- Working on hermes-agent"}

      # Plain string (equivalent)
      return "Recalled memories:\n- User likes Python"

      # No injection
      return None

      أين يُحقَن السياق: دائمًا في رسالة المستخدم، ولا يُحقَن أبدًا في الـ system prompt. هذا يحافظ على ذاكرة التخزين المؤقت للـ prompt — يبقى الـ system prompt مطابقًا عبر الأدوار، فتُعاد الاستفادة من الـ tokens المخزّنة مؤقتًا. الـ system prompt هو نطاق Hermes الخاص (توجيه النموذج، فرض استخدام الأدوات، الشخصية، المهارات). تسهم الإضافات بسياق إلى جانب مُدخَل المستخدم.

      يبقى محتوى content النظيف لرسالة المستخدم دون تغيير. من أجل إعادة التشغيل (replay) واستقرار التخزين المؤقت للـ prompt، قد يحفظ Hermes رسالة الـ API الدقيقة، بما فيها السياق المحقون من الإضافات، في الحقل الجانبي api_content ضمن الصف.

      عندما تُعيد عدة إضافات سياقًا، تُدمَج مخرجاتها بفواصل سطرين متتاليَين حسب ترتيب اكتشاف الإضافات (أبجديًا حسب اسم المجلد).

      حالات الاستخدام: استرجاع الذاكرة، حقن سياق RAG، الضوابط الوقائية (guardrails)، تحليلات لكل دور.

      مثال — استرجاع الذاكرة:

      import httpx

      MEMORY_API = "https://your-memory-api.example.com"

      def recall(session_id, user_message, is_first_turn, **kwargs):
          try:
              resp = httpx.post(f"{MEMORY_API}/recall", json={
                  "session_id": session_id,
                  "query": user_message,
              }, timeout=3)
              memories = resp.json().get("results", [])
              if not memories:
                  return None
              text = "Recalled context:\n" + "\n".join(f"- {m['text']}" for m in memories)
              return {"context": text}
          except Exception:
              return None

      def register(ctx):
          ctx.register_hook("pre_llm_call", recall)

      مثال — الضوابط الوقائية:

      POLICY = "Never execute commands that delete files without explicit user confirmation."

      def guardrails(**kwargs):
          return {"context": POLICY}

      def register(ctx):
          ctx.register_hook("pre_llm_call", guardrails)

      pre_verify​

      يُطلَق مرة واحدة لكل دور عدّل فيه الوكيل الكود، مباشرة قبل انتهائه (بعد حارس التحقق-عند-التوقف verify-on-stop المدمج). هذه بوابة سياسة للمستخدم/الإضافة: يمكن للاستدعاء إبقاء الوكيل مستمرًا — تشغيل فحص، تأجيله، تنظيف الفروق (diff) — بدلًا من السماح له بالتوقف.

      إرشاد التحقق المدمج في Hermes ليس hook افتراضيًا من نوع pre_verify. بل يُضاف إلى تنبيه التحقق-عند-التوقف المبني على الأدلة عندما يفتقر الكود المُعدَّل إلى دليل تحقق حديث، وبذلك لا يُنشئ مسار استمرار افتراضيًا ثانيًا. اضبط agent.verify_guidance: false لإبقاء ذلك التنبيه المدمج مقتضبًا.

      final_responsestrالرد الذي يوشك الوكيل على تسليمه
      changed_pathslistالملفات التي عدّلها الوكيل في هذا الدور (مُرتَّبة، وغير فارغة دائمًا هنا)

      قيّد الـ hook بسياق البرمجة عبر فحص coding واجعله يُطلَق مرة واحدة عبر attempt (تقرأ hooks الـ shell كليهما من .extra)، بنفس الطريقة التي يُقيَّد بها hook من نوع pre_tool_call بحسب tool_name — بحيث يمكنك تسجيل عدة hooks من نوع pre_verify، كل منها يُطلَق فقط حيث ينبغي.

      يُطلَق: في agent/conversation_loop.py، عند النقطة التي سيقبل فيها الوكيل ردًا نهائيًا، مباشرة بعد فحص التحقق-عند-التوقف — لكن فقط عندما يكون الوكيل قد عدّل الكود في هذا الدور وسُجِّل hook واحد على الأقل من نوع pre_verify.

      قيمة الإرجاع — إبقاء الوكيل مستمرًا:

      return {"action": "continue", "message": "Run the formatter on your changes, then finish."}

      تُضاف message كدور اصطناعي للمستخدم وتعمل الحلقة مرة أخرى. تُقبَل أيضًا صيغة Claude-Code لـ Stop ({"decision": "block", "reason": "..."}، حيث حظر التوقف يعني الاستمرار). التوجيه دون رسالة — أو أي قيمة إرجاع أخرى — يسمح للدور بالانتهاء.

      مقيَّد: توجيهات الاستمرار المتتالية في دور واحد محدودة بـ agent.max_verify_nudges (الافتراضي 3)، لذا لا يمكن أبدًا لـ hook يقول "استمر" دائمًا أن يُوقِع الحلقة في فخ. تُحفَظ الإجابة المحاوَلة في السجل لكن لا تُعرَض للمستخدم أثناء تنبيه الوكيل.

      اجعله متكرر التطبيق دون تأثير جانبي (idempotent): يُعاد إطلاق الـ hook بعد كل تنبيه، لذا قيّده بـ attempt (if attempt: return None) — وإلا فسيستمر في التنبيه حتى يُصادف الحد الأقصى.

      حالات الاستخدام: تأجيل الاختبارات/الفحوصات اللغوية أثناء التكرار الإبداعي، اشتراط اجتياز فحوصات ناجحة لمسارات معيّنة، حظر "الانتهاء" حتى يُوجَد سجل تغييرات (changelog)، تشغيل قائمة تحقق خاصة بالمشروع.

      مثال — تأجيل الفحوصات في أعمال واجهة المستخدم الإبداعية، مقيَّد وذو تطبيق واحد:

      UI = (".tsx", ".jsx", ".css", ".scss")

      def defer_ui_checks(coding, attempt, changed_paths, **kwargs):
          if attempt or not coding:
              return None  # one-shot, coding only
          if not all(p.endswith(UI) for p in changed_paths):
              return None  # only pure-UI edits
          return {
              "action": "continue",
              "message": "This is UI work — don't run tests/lints yet; ask the user to "
                         "eyeball it first, and clean the diff before any commit.",
          }

      def register(ctx):
          ctx.register_hook("pre_verify", defer_ui_checks)

      للإرشاد الدائم الذي يجب أن يشكّل تنبيه الدليل الناقص المدمج، استخدم agent.verify_guidance. لقواعد وضعية البرمجة الأوسع التي لا تحتاج إلى تقييد التحقق، يُفضَّل استخدام agent.coding_instructions في config.yaml — فهي تُرفَق بموجز البرمجة (coding brief) دون تكلفة دور إضافي.

      transform_api_error_classification​

      يُطلَق مرة واحدة لكل استدعاء API فاشل، في بداية agent/error_classifier.classify_api_error()، قبل خط الأنابيب المدمج. تستخدمه إضافات المزوّدين للتحكّم في خصوصيات أخطاء مزوّدها دون تعديل النواة. إنه يُغيّر السلوك (فئة transform): يُحدِّد التصنيف المُعاد إعادة المحاولة، ضغط السياق، تدوير بيانات الاعتماد، وتوجيه الاحتياط (fallback).

      تتلقى الاستدعاءات سياق الخطأ المُحلَّل كوسائط مفتاحية (kwargs) — provider (اجعل نطاق الـ hook محصورًا بهذا)، model، status_code، error_type، error_code، error_message، error_body، error، approx_tokens، context_length، num_messages. أعِد None للرفض، أو قاموسًا للمطالبة بالخطأ:

      return {"reason": "model_not_found",   # required: a FailoverReason name
              "retryable": False, "should_fallback": True}  # optional recovery-hint overrides

      يُنفَّذ التوزيع بمبدأ "تشغيل الكل ثم اختيار الأول" (run-all-then-pick-first): يعمل كل استدعاء، وتُعزَل الإخفاقات، ويفوز أول نتيجة صالحة بترتيب التسجيل (النتائج الصالحة الخاسرة تُسجَّل بتحذير وقت التشغيل). تُتجاهَل القواميس غير الصالحة والأسباب غير المعروفة، لذا لا يمكن أبدًا لإضافة معطوبة أن تُفسد التصنيف.

      الخصوصية: قد يحمل error_message و error_body بيانات غير محجوبة من المزوّد. إضافات Python فقط — تُرفَض تسجيلات الـ shell عند تحليل الإعدادات مع تحذير.

      transform_tool_result​

      يُطلَق بعد عودة أداة ما وقبل إضافة النتيجة إلى المحادثة. يتيح لإضافة إعادة كتابة سلسلة نتيجة أي أداة — وليس مخرجات الطرفية فقط — قبل أن يراها النموذج.

      توقيع الاستدعاء:

      قيمة الإرجاع: أول str يستبدل النتيجة (بما في ذلك سلسلة فارغة)؛ None يتركها دون تغيير.

      حالات الاستخدام: حجب بيانات PII الخاصة بمؤسسة معيّنة من مخرجات web_extract، تغليف استجابات أدوات JSON الطويلة برأس ملخّص، حقن تلميحات RAG في نتائج read_file، إعادة كتابة تقارير الوكيل الفرعي من delegate_task بمخطط خاص بالمشروع.

      transform_llm_output​

      يُطلَق مرة واحدة لكل دور بعد اكتمال حلقة استدعاء الأدوات وإنتاج النموذج ردًا نهائيًا، قبل تسليم ذلك الرد إلى المستخدم (CLI، أو الـ gateway، أو مستدعٍ برمجي). يتيح لإضافة إعادة كتابة النص النهائي للوكيل باستخدام أساليب برمجية كلاسيكية — دون استهلاك tokens استدلال إضافية على نص نكهة SOUL أو تحويل مبني على مهارة.

      توقيع الاستدعاء:

      def my_callback(
          response_text: str,
          session_id: str,
          model: str,
          platform: str,
          **kwargs,
      ) -> str | None:
      المعاملالنوعالوصف
      response_textstrنص الرد النهائي للوكيل في هذا الدور.
      session_idstrمعرّف الجلسة لهذه المحادثة (قد يكون فارغًا للتشغيلات الفردية).
      modelstrاسم النموذج الذي أنتج الرد (مثل anthropic/claude-sonnet-4.6).
      platformstrمنصة التسليم (cli، telegram، discord، …؛ فارغة إن لم تُضبط).

      قيمة الإرجاع: str غير فارغة لاستبدال نص الرد، أو None أو سلسلة فارغة لتركه دون تغيير. تفوز أول سلسلة غير فارغة عند تسجيل عدة إضافات. بخلاف تحويلي الأداة والطرفية، لا تُقبَل السلسلة الفارغة كاستبدال.

      حالات الاستخدام: تطبيق تحويل شخصية/مفردات (كلام قراصنة، سبونجبوب)، حجب معرّفات خاصة بالمستخدم من النص النهائي، إلحاق توقيع خاص بالمشروع، فرض دليل أسلوب داخلي دون استهلاك tokens على تعليمات SOUL.

      عند تفعيل بث CLI، يُطبَع تحويل إلحاقي فقط بعد الجسم المُبثّ. أما التحويل الذي يستبدل الرد فيُطبَع كاملًا بعد الجسم المُبثّ، موسومًا كتحويل بعد-البث، بحيث لا يُفقَد المحتوى البديل صمتًا أبدًا.

      import os, re

      def spongebob(response_text, **kwargs):
          if os.environ.get("SPONGEBOB_MODE") != "on":
              return None  # pass through unchanged

      def register(ctx):

      Hooks مراقبة طلبات API​

      pre_api_request​

      يُطلَق لكل محاولة مزوّد مباشرة قبل إرسالها. هذا للمراقبة فقط. حقول user_message و conversation_history و request_messages القديمة خام وغير مُنقَّاة عمدًا لأغراض التوافق؛ يُفضَّل للمستهلكين الجدد استخدام مغلَّف request المُنقَّى.

      post_api_request​

      يُطلَق بعد تطبيع استجابة المزوّد بنجاح. هذا للمراقبة فقط. يُفضَّل استخدام response المُنقَّاة؛ assistant_message هي الرسالة المطبَّعة الخام، و usage تحوي بيانات المحاسبة.

      api_request_error​

      يُطلَق لمحاولة مزوّد فاشلة مع توقيت الحالة/إعادة المحاولة، وكائن error، و request المُنقَّاة. هذا للمراقبة فقط. قد تحوي رسائل الخطأ بيانات المزوّد أو المستخدم.

      on_skill_lifecycle​

      يُطلَق بعد تغيير حالة استخدام مهارة موثوق. هذا للمراقبة فقط، ويكشف skill_name المحلي، ومصدره، ومعرّفات الارتباط، وعدد مرات الاستخدام، وأعلام إعادة الاستخدام.

      مراقِبو دورة حياة Kanban​

      kanban_task_claimed​

      يُطلَق بعد التزام الاستحواذ (claim) في عملية الموزِّع، مباشرة قبل إطلاق العامل (worker).

      kanban_task_completed​

      يُطلَق بعد الإكمال والتنظيف، عادة في عملية العامل. يمكن أن يحوي summary محتوى خاصًا بالمشروع أو المستخدم.

      kanban_task_blocked​

      يُطلَق بعد انتقال حظر عادي. يستدعيه مسار انتظار الاعتماديات قبل خروج معاملة الكتابة تلك. يمكن أن يحوي reason محتوى خاصًا بالمشروع أو المستخدم.

      كل hooks الـ kanban الثلاثة للمراقبة فقط وتحمل task_id، و profile_name، و board، و assignee، و run_id؛ ويضيف الإكمال summary، ويضيف الحظر reason.

      مراقِبو دورة حياة عامل Kanban، وتعديل المهام، والتوزيع​

      تُوسِّع خمسة مراقِبين إضافيين (RFC #58548) عائلة kanban. جميعها للمراقبة فقط، وتُطلَق بعد التزام المعاملة ذات الصلة، وتُختصَر عند has_hook — فبلا مشترِك، يبقى سلوك التوزيع دون تغيير. تحمل hooks المحصورة بمهمة نفس الحقول المشتركة التي تحملها hooks أعلاه.

      • on_kanban_worker_spawned — بعد عودة spawn_fn وحفظ معرّف عملية العامل (PID). يضيف worker_pid (قد يكون None) و workspace_path. يعمل داخل قفل التوزيع؛ اجعل الاستدعاءات سريعة.
      • on_kanban_worker_exited — مشتق من التكة (tick)، عندما يستعيد detect_crashed_workers مهمة ذات PID ميت. يضيف worker_pid، و exit_kind، و exit_code، و outcome، و retry_status.
      • on_kanban_worker_stale_claim — عندما تُستعاد ملكية منتهية الصلاحية (TTL)؛ لا تُطلَق تمديدات PID الحي. يضيف worker_pid، و heartbeat_stale، و retry_status.
      • on_kanban_task_updated — بعد كتابة ملتزَمة لحقل مهمة خارج دورة حياة الاستحواذ/الإكمال/الحظر (assign_task، تجاوزات النموذج/الاستدلال، محرِّرات لوحة التحكم). يضيف changed_fields — أسماء الحقول فقط، دون قيمها أبدًا.
      • on_kanban_dispatch_tick — مرة واحدة لكل تكة موزِّع، بعد تحرير قفل التوزيع مباشرة، بما في ذلك تكات الخمول والمتنازَع عليها بالقفل. الحمولة: board، و profile_name، و dry_run، و outcome، و result.

      Shell Hooks​

      أعلن عن hooks بسكربتات shell في ملف config.yaml الخاص بـ profile، وسيُشغِّلها Hermes كعمليات فرعية كلما أُطلِق حدث الـ hook المطابق للإضافة — في جلسات CLI، والـ gateway، وDesktop، وTUI، ومحادثة لوحة التحكم. لا حاجة إلى تأليف إضافة Python.

      يسجّل Desktop وTUI ومحادثة لوحة التحكم الـ hooks عند بناء وكيل، باستخدام إعدادات profile تلك الجلسة وقائمة سماح الموافقة الخاصة بها. تبديل الـ profiles لا يعيد استخدام hooks profile آخر. تظل متطلبات موافقة الـ hooks القائمة وسلوك الوضع الآمن ساريَين؛ تُتخطَّى الـ hooks غير المعتمَدة بدلًا من الموافقة عليها صمتًا.

      استخدم hooks الـ shell عندما تريد سكربتًا جاهزًا وحيد الملف (Bash، أو Python، أو أي شيء بشيبانغ) من أجل:

      • حظر أو تعديل استدعاء أداة — رفض أوامر terminal الخطرة، وفرض سياسات لكل دليل، واشتراط الموافقة على عمليات write_file / patch المدمِّرة، أو إعادة كتابة الوسائط (تعقيم المسارات، حقن الافتراضيات) قبل تشغيل الأداة.
      • التشغيل بعد استدعاء أداة — تنسيق ملفات Python أو TypeScript التي كتبها الوكيل للتو تلقائيًا، وتسجيل استدعاءات API، وإطلاق سير عمل CI.
      • حقن سياق في دور الـ LLM التالي — إلحاق مخرجات git status، أو اليوم الحالي من الأسبوع، أو مستندات مسترجَعة برسالة المستخدم (انظر pre_llm_call).
      • مراقبة أحداث دورة الحياة — كتابة سطر سجل عند اكتمال وكيل فرعي (subagent_stop) أو بدء جلسة (on_session_start).

      تُسجَّل hooks الـ shell باستدعاء agent.shell_hooks.register_from_config(cfg) في كل من بدء تشغيل CLI (hermes_cli/main.py) وبدء تشغيل الـ gateway (gateway/run.py). تتكامل بشكل طبيعي مع hooks إضافات Python — يمر كلاهما عبر نفس الموزِّع (dispatcher).

      بروتوكول النقل عبر JSON​

      في كل مرة يُطلَق فيها الحدث، يُطلِق Hermes عملية فرعية لكل hook مطابق (بحسب المُطابِق matcher)، ويُمرِّر حمولة JSON عبر stdin، ويقرأ stdout كـ JSON.

      stdin — الحمولة التي يتلقاها السكربت:

      {
        "hook_event_name": "pre_tool_call",
        "tool_name":       "terminal",
        "tool_input":      {"command": "rm -rf /"},
        "session_id":      "sess_abc123",
        "cwd":             "/home/user/project",
        "profile":         "default",
        "extra":           {"task_id": "...", "tool_call_id": "..."}
      }

      يسمّي profile profile Hermes الذي أطلق الـ hook ("default" خارج الـ profiles)، بحيث يمكن لسكربت واحد أن يخدم كل profile خلف gateway متعدد الإرسال؛ وتعمل العملية الفرعية أيضًا ضمن HERMES_HOME الخاصة بذلك الـ profile. tool_name و tool_input تكون null للأحداث غير المتعلقة بأداة (pre_llm_call، subagent_stop، أحداث دورة حياة الجلسة). يحمل قاموس extra كل الوسائط المفتاحية الخاصة بالحدث (user_message، conversation_history، child_role، duration_ms، …). القيم غير القابلة للتسلسل تُحوَّل إلى نص بدلًا من حذفها.

      stdout — الاستجابة الاختيارية:

      // Block a pre_tool_call (both shapes accepted; normalised internally):
      {"decision": "block", "reason":  "Forbidden: rm -rf"}   // Claude-Code style
      {"action":   "block", "message": "Forbidden: rm -rf"}   // Hermes-canonical

      // Modify a pre_tool_call — rewrite tool args before dispatch:
      {"action": "modify", "args": {"new_string": "fixed content"}}         // Hermes-canonical
      {"decision": "modify", "tool_input": {"new_string": "fixed content"}} // Claude-Code style

      // Inject context for pre_llm_call:
      {"context": "Today is Friday, 2026-04-17"}

      // Keep the agent going at the verify gate (pre_verify); both shapes accepted:
      {"action": "continue", "message": "Run the formatter, then finish."}
      {"decision": "block",  "reason":  "Run the formatter, then finish."}

      // Silent no-op — any empty / non-matching output is fine:

      JSON المشوَّه، ورموز الخروج غير الصفرية، وانتهاءات المهلة تُسجِّل تحذيرًا لكنها لا تُوقِف حلقة الوكيل أبدًا.

      رمز الخروج 2 = حظر (متوافق مع Claude Code / Cursor)​

      يحظر hook من نوع pre_tool_call يخرج برمز 2 استدعاء الأداة حتى عندما لا يحمل stdout الخاص به JSON حظر. تُحدَّد رسالة الحظر بترتيب الأولوية:

      1. JSON حظر في stdout (reason / message)، إن وُجد؛
      2. أول 400 حرف من stderr؛
      3. افتراضي عام هو "Blocked by shell hook.".

      لذا فإن أبسط hook حاجب ممكن هو:

      #!/usr/bin/env bash
      echo "policy violation: rm -rf is not permitted" >&2
      exit 2

      بالنسبة للأحداث التي لا يُحتَرَم توجيه الحظر فيها (كل الأحداث ما عدا pre_tool_call)، يُعامَل الخروج برمز 2 كأي خروج آخر غير صفري: يُسجَّل تحذير، ويُحلَّل stdout رغم ذلك.

      الفشل المفتوح مقابل الفشل المغلق​

      افتراضيًا، تفشل hooks الـ shell بشكل مفتوح: يُسجِّل خطأ التشغيل، أو انتهاء المهلة، أو stdout غير القابل للتحليل تحذيرًا وتستمر العملية. هذا هو الافتراضي الصحيح لـ hooks المراقبة — لكنه خاطئ لبوابات الأمان. يجب ألا يسمح ماسح أسرار معطوب صمتًا باستدعاء الأداة الذي كان من المفترض أن يفحصه.

      اضبط fail_closed: true (أو failClosed: true، تهجئة Cursor/Claude Code) على مُدخَل pre_tool_call لعكس ذلك:

      hooks:
        pre_tool_call:
          - matcher: "terminal|write_file|patch"
            command: "~/.hermes/agent-hooks/secret-scan.sh"
            timeout: 10
            fail_closed: true

      مع fail_closed: true، يصبح كل مما يلي الآن حاجبًا لاستدعاء الأداة برسالة hook <command> failed closed: <reason>:

      الإخفاقالفشل المفتوح (الافتراضي)fail_closed: true
      الأمر غير موجود / غير قابل للتنفيذتحذير، متابعةحظر
      انتهاء المهلةتحذير، متابعةحظر
      stdout غير JSON (مثل تتبّع مكدّس)تحذير، متابعةحظر
      خروج نظيف، JSON صالح بلا إجراء ({})متابعةمتابعة

      ينطبق fail_closed فقط على الأحداث القادرة على الحظر (pre_tool_call حاليًا)؛ ضبطه على أي حدث آخر يُسجِّل تحذيرًا وقت تحليل الإعدادات ويُتجاهَل. يعكس hermes hooks test هذه الدلالات — يُظهر سطر parsed بالضبط شكل الحظر الذي سيتلقاه الموزِّع.

      أمثلة عملية​

      1. تنسيق ملفات Python تلقائيًا بعد كل كتابة​

      # ~/.hermes/config.yaml
      hooks:
        post_tool_call:
          - matcher: "write_file|patch"
            command: "~/.hermes/agent-hooks/auto-format.sh"
      #!/usr/bin/env bash
      # ~/.hermes/agent-hooks/auto-format.sh
      payload="$(cat -)"
      path=$(echo "$payload" | jq -r '.tool_input.path // empty')
      [[ "$path" == *.py ]] && command -v black >/dev/null && black "$path" 2>/dev/null
      printf '{}\n'

      رؤية الوكيل السياقية للملف لا تُعاد قراءتها تلقائيًا — فإعادة التنسيق تؤثّر فقط على الملف على القرص. تلتقط استدعاءات read_file اللاحقة النسخة المُنسَّقة.

      2. حظر أوامر terminal المدمِّرة​

      hooks:
        pre_tool_call:
          - matcher: "terminal"
            command: "~/.hermes/agent-hooks/block-rm-rf.sh"
            timeout: 5
      #!/usr/bin/env bash
      # ~/.hermes/agent-hooks/block-rm-rf.sh
      payload="$(cat -)"
      cmd=$(echo "$payload" | jq -r '.tool_input.command // empty')
      if echo "$cmd" | grep -qE 'rm[[:space:]]+-rf?[[:space:]]+/'; then
        printf '{"decision": "block", "reason": "blocked: rm -rf / is not permitted"}\n'
      else
        printf '{}\n'
      fi

      3. حقن git status في كل دور (مكافئ UserPromptSubmit في Claude Code)​

      hooks:
        pre_llm_call:
          - command: "~/.hermes/agent-hooks/inject-cwd-context.sh"
      #!/usr/bin/env bash
      # ~/.hermes/agent-hooks/inject-cwd-context.sh
      cat - >/dev/null   # discard stdin payload
      if status=$(git status --porcelain 2>/dev/null) && [[ -n "$status" ]]; then
        jq --null-input --arg s "$status" \
           '{context: ("Uncommitted changes in cwd:\n" + $s)}'
      else
        printf '{}\n'
      fi

      حدث UserPromptSubmit في Claude Code ليس عمدًا حدثًا منفصلًا في Hermes — يُطلَق pre_llm_call في نفس الموضع ويدعم حقن السياق أصلًا. استخدمه هنا.

      4. تسجيل كل اكتمال لوكيل فرعي​

      hooks:
        subagent_stop:
          - command: "~/.hermes/agent-hooks/log-orchestration.sh"
      #!/usr/bin/env bash
      # ~/.hermes/agent-hooks/log-orchestration.sh
      log=~/.hermes/logs/orchestration.log
      jq -c '{ts: now, parent: .session_id, extra: .extra}' < /dev/stdin >> "$log"
      printf '{}\n'

      نموذج الموافقة​

      يطلب كل زوج فريد من (event, command) موافقة المستخدم في المرة الأولى التي يراه فيها Hermes، ثم يحفظ القرار في ~/.hermes/shell-hooks-allowlist.json. تتخطى التشغيلات اللاحقة (CLI أو الـ gateway) المطالبة.

      ثلاثة مخارج تتجاوز المطالبة التفاعلية — يكفي أي واحد منها:

      1. خيار --accept-hooks في CLI (مثل hermes --accept-hooks chat)
      2. متغير البيئة HERMES_ACCEPT_HOOKS=1
      3. hooks_auto_accept: true في ~/.hermes/config.yaml

      تحتاج التشغيلات غير التفاعلية (gateway، cron، CI) إلى واحد من هذه الثلاثة — وإلا فإن أي hook مُضاف حديثًا يبقى غير مسجَّل صمتًا ويُسجِّل تحذيرًا.

      تعديلات السكربت موثوقة صمتًا. تعتمد قائمة السماح على سلسلة الأمر الدقيقة، لا على بصمة (hash) السكربت، لذا فتعديل السكربت على القرص لا يُبطل الموافقة. يُبلِّغ hermes hooks doctor عن انحراف وقت التعديل (mtime) حتى تتمكن من رصد التعديلات وتقرير ما إذا كنت ستوافق مجددًا.

      إضافة يدوية إلى قائمة السماح​

      الإضافة اليدوية إلى قائمة السماح مفيدة لعمليات النشر غير التفاعلية أو حسابات الخدمة حيث لا يستطيع المُشغِّل الإجابة على مطالبة أول استخدام تفاعليًا. ملف قائمة السماح هو ~/.hermes/shell-hooks-allowlist.json، والصيغة المتوقَّعة هي مصفوفة approvals. تسجّل كل موافقة event الحدث و command سلسلة الأمر الدقيقة:

      {
        "approvals": [
          {
            "event": "post_llm_call",
            "command": "/home/hermes/.hermes/hooks/my-hook.py"
          }
        ]
      }

      يجب أن تطابق سلسلة الأمر أمر الـ hook المُعَدّ تمامًا. الكائن المُفهرَس بالمسار مع حقل sha256 ليس الصيغة المتوقَّعة ولن يُوافِق على الـ hook. تحقّق من المُدخلات اليدوية بـ hermes hooks list.

      واجهة سطر الأوامر hermes hooks​

      الأمرما يفعله
      hermes hooks listعرض الـ hooks المُعدَّة مع المُطابِق (matcher)، والمهلة، وحالة الموافقة
      hermes hooks test <event> [--for-tool X] [--payload-file F]تشغيل كل hook مطابق ضد حمولة اصطناعية وطباعة الاستجابة المُحلَّلة
      hermes hooks revoke <command>إزالة كل مُدخَل من قائمة السماح مطابق لـ <command> (يسري عند إعادة التشغيل التالية)
      hermes hooks doctorلكل hook مُعَدّ: فحص صلاحية التنفيذ (exec bit)، وحالة قائمة السماح، وانحراف وقت التعديل، وصحة مخرجات JSON، ووقت تنفيذ تقريبي

      الأمان​

      تعمل hooks الـ shell ببيانات اعتماد المستخدم الكاملة — نفس حد الثقة الذي يتمتع به مُدخَل cron أو اسم مستعار (alias) للـ shell. عامل كتلة hooks: في config.yaml كإعدادات مميَّزة:

      • اقتصر على الإشارة إلى سكربتات كتبتها بنفسك أو راجعتها بالكامل.
      • أبقِ السكربتات داخل ~/.hermes/agent-hooks/ ليسهل تدقيق المسار.
      • أعِد تشغيل hermes hooks doctor بعد سحب إعدادات مشتركة لرصد الـ hooks المُضافة حديثًا قبل تسجيلها.
      • إذا كان ملف config.yaml خاضعًا للتحكم بالإصدار (version-controlled) ضمن فريق، راجع طلبات السحب (PRs) التي تُغيِّر قسم hooks: بنفس الطريقة التي تراجع بها إعدادات CI.

      الترتيب والأسبقية​

      تمر كل من hooks إضافات Python وhooks الـ shell عبر نفس موزِّع invoke_hook(). تُسجَّل إضافات Python أولًا (discover_and_load())، ثم hooks الـ shell ثانيًا (register_from_config())، لذا تسبق قرارات حظر pre_tool_call الخاصة بـ Python في حالات التعادل. يفوز أول حظر صالح — يعيد المُجمِّع (aggregator) النتيجة بمجرد أن يُنتِج أي استدعاء {"action": "block", "message": str} برسالة غير فارغة.

      Webhooks الصادرة​

      webhooks الصادرة هي مرآة الدفع (push) المقابلة لـ منصة webhooks الواردة: توقظ webhooks الواردة Hermes عندما يتغيّر العالم؛ وتخبر webhooks الصادرة العالم عندما يفعل Hermes شيئًا. اضبط قائمة نقاط نهاية HTTP وأحداث دورة الحياة التي تهمها، وسيرسل Hermes حمولة JSON موقَّعة إلى كل نقطة نهاية كلما أُطلِق حدث مطابق — دون استقصاء (polling) من جهة الاستقبال.

      الاستخدامات النموذجية:

      • إعلام نظام CI أو لوحة تحكم عند انتهاء دور وكيل (on_session_end)
      • تتبّع اكتمالات الوكلاء الفرعيين عبر أسطول من الوكلاء (subagent_stop)
      • تغذية المراقبة الخارجية بنشاط الأدوات (post_tool_call مع matcher)
      • إيقاظ نسخة أخرى من Hermes: وجّه الرابط إلى webhook الوارد الخاص بتلك النسخة

      الإعدادات​

      أضف قائمة hooks.outbound: إلى ~/.hermes/config.yaml:

      hooks:
        outbound:
          - name: ci-notify                       # optional label for logs
            url: https://ci.example.com/hermes-events
            events: [on_session_end, subagent_stop]
            secret_env: HERMES_OUTBOUND_WEBHOOK_SECRET   # env var holding the HMAC secret
            timeout: 10                           # per-attempt seconds (1–60)

          - name: tool-monitor
            url: https://metrics.example.com/hooks/hermes
            events: [post_tool_call]
            matcher: "terminal|delegate_task"     # regex, tool-scoped events only

      أي حدث من مجموعة hooks الإضافات صالح (pre_tool_call، و post_tool_call، و pre_llm_call، و post_llm_call، و on_session_start، و on_session_end، و subagent_start، و subagent_stop، ...). المُدخلات المشوَّهة تُحذِّر وتُتخطَّى — لا يُوقِف webhook معطوب الوكيل أبدًا. تسري التغييرات عند جلسة CLI التالية / إعادة تشغيل الـ gateway.

      الأسرار: يُفضَّل secret_env (اسم متغير بيئة، يُضبَط عادة في ~/.hermes/.env) على قيمة secret: نصية مباشرة، حتى يبقى ملف الإعدادات خاليًا من بيانات الاعتماد. المُدخلات بلا سر تُسلَّم دون توقيع (تُوسَم بـ UNSIGNED بواسطة hermes hooks list).

      صيغة النقل​

      يُرسِل كل إطلاق حدث جسم JSON بنفس الشكل العلوي لـ stdin الخاص بـ hooks الـ shell، إضافة إلى بيانات وصفية للتسليم. يسمّي profile profile Hermes الذي أصدر الحدث ("default" خارج الـ profiles)، بحيث يمكن للمستقبِلين خلف gateway متعدد الإرسال التمييز بين الـ profiles:

      {
        "hook_event_name": "on_session_end",
        "profile": "default",
        "tool_name": null,
        "tool_input": null,
        "session_id": "sess_abc123",
        "cwd": "/home/user/project",
        "extra": {"completed": true, "interrupted": false, "model": "...", "platform": "cli"},
        "delivery_id": "3f2c9a...",
        "timestamp": "2026-07-22T14:00:00Z"
      }

      الترويسات (Headers):

      الترويسةالقيمة
      Content-Typeapplication/json
      X-Hermes-Eventاسم حدث الـ hook
      X-Hermes-Deliveryمعرّف فريد لكل تسليم — نفس قيمة delivery_id في الجسم
      X-Hermes-Signature-256sha256=<hex> — HMAC-SHA256 للجسم الخام، بأسلوب GitHub؛ موجودة فقط عند ضبط سر

      تحقّق من التوقيع تمامًا كما تفعل مع webhook خاص بـ GitHub:

      import hashlib, hmac

      def verify(body: bytes, header: str, secret: str) -> bool:
          expected = "sha256=" + hmac.new(secret.encode(), body, hashlib.sha256).hexdigest()
          return hmac.compare_digest(expected, header)

      بما أن delivery_id و timestamp يعيشان داخل الجسم الموقَّع، فإن المستقبِل المتحقِّق يحصل أيضًا على حماية من إعادة التشغيل (replay) مجانًا:

      • إزالة التكرار بناءً على delivery_id (أو ترويسة X-Hermes-Delivery المطابقة) — تذكّر المعرّفات المرصودة مؤخرًا وتخطَّ التكرارات. يعيد Hermes محاولة التسليمات الفاشلة مرة واحدة، لذا يمكن أن يصل نفس المعرّف مرتين بشكل مشروع.
      • رفض الأحداث القديمة عبر مقارنة timestamp بساعتك ضمن نافذة تسامح (5 دقائق هو الافتراضي الشائع). لا يستطيع مهاجم يعيد تشغيل طلب مُلتقَط تزوير طابع زمني حديث دون السر.

      دلالات التسليم​

      • أطلق ولا تنتظر، خارج المسار الحرج. تُسلسَل الأحداث وتُضاف إلى قائمة الانتظار فورًا؛ ويقوم خيط خلفي واحد بعمليات POST عبر HTTP. لا يمكن أبدًا لنقطة نهاية بطيئة أو ميتة أن تُعطِّل استدعاء أداة أو دور وكيل.
      • للإعلام فقط. بخلاف hooks الـ shell، لا يمكن لـ webhooks الصادرة حظر استدعاءات الأدوات أو حقن سياق — يُتجاهَل جسم الاستجابة. فهي تراقب، ولا توجّه أبدًا.
      • محاولات إعادة محدودة. تُعاد محاولة أخطاء الاتصال واستجابات 5xx مرة واحدة مع تأخير تصاعدي (backoff)؛ ولا تُعاد محاولة استجابات 4xx (إذ يقول المستقبِل إن الطلب نفسه خاطئ). تُسجَّل الإخفاقات وتُسقَط — التسليم بأفضل جهد، وليس مضمونًا.
      • لا يُتبَع إعادة التوجيه أبدًا. تُعامَل استجابة 3xx كإعداد خاطئ وتُسجَّل — فاتّباع POST مُعاد توجيهه سيُسقِط الحمولة الموقَّعة صمتًا. وجّه url إلى نقطة النهاية النهائية.
      • قائمة انتظار محدودة. إذا تراكمت قائمة الانتظار (نقطة نهاية ميتة، عاصفة أحداث)، تُسقَط الأحداث الجديدة بتحذير بدلًا من استهلاك ذاكرة غير محدودة.
      • لا مطالبة موافقة. لا تُنفِّذ الأهداف الصادرة أي كود على جهازك — فهي تتلقى بيانات على رابط ضبطته أنت. يتخطى HERMES_SAFE_MODE=1 التسجيل رغم ذلك، مثل الإضافات وhooks الـ shell. لاحظ أن الحمولات تتضمّن مُدخلات الأدوات وبيانات وصفية للأحداث، لذا وجّه الأهداف فقط إلى نقاط نهاية تثق بها، وفضّل https://.

      يعرض hermes hooks list الأهداف الصادرة المُعدَّة إلى جانب hooks الـ shell، بما في ذلك ما إذا كان كل هدف موقَّعًا.

      تفويض المهام إلى Subagents

      تُنشئ الأداة delegate_task نُسخًا فرعية من AIAgent بسياق معزول، ووصول موروث إلى الأدوات، وجلسات طرفية خاصة بكل منها. تحصل كل نسخة فرعية على محادثة جديدة وتعمل باستقلالية، ولا يدخل سياقَ الوكيل الأب سوى ملخصها النهائي.

      تعمل استدعاءات النموذج على المستوى الأعلى في الخلفية تلقائيًا. يعيد Hermes معرّف تتبع (handle) فورًا لتستمر المحادثة، ثم ينشر النتيجة لاحقًا في رسالة جديدة. أما الـ subagent المنسِّق (orchestrator) فينتظر العمّال التابعين له حتى يتمكن من تجميع نتائجهم قبل أن يعود.

      تسليم نتائج الإنجاز​

      لا تُقِرّ messaging gateways باستلام نتائج الإنجاز الخلفية إلا بعد أن يجدول المحوّل (adapter) الخاص بها الحدث فعليًا أو يدرجه في طابور الجلسة. أما غياب المعالِجات، أو عدم تطابق مسارات الجلسة، أو امتلاء الطوابير، فتُبقي نتيجة الإنجاز معلّقة لإعادة المحاولة؛ ولا تستهلك حالات رفض القبول هذه رصيد محاولات التسليم الدائم. ويمنع القبول الناجح تكرار التسليم داخل الـ gateway العامل، لكنه ليس دليلًا على اكتمال دور النموذج أو إرسال الرد الصادر. يبقى التسليم بعد التعطل أو إعادة التشغيل مضمونًا لمرة واحدة على الأقل، مع مراعاة حدّ عمر إعادة التشغيل (replay) الحالي؛ أما إخفاقات النقل الفعلية فتحتفظ بسياسة إعادة المحاولة المحدودة الخاصة بها.

      يبقى مسار خادم API غير المتاح في حالة التعليق دون تكرار تحذيرات غياب المسار. أما مسارات المراسلة ذات الصيغة غير الصحيحة فلا تزال تُنتج رسائل تشخيصية. وعلى خادم API، يقتصر ما يضيفه إنجاز التفويض غير المتزامن على صف تسليم دائم في الخط الزمني فقط: فالعميل هو من يتولى دور النموذج التالي. ويؤدي ضبط إشعارات العمليات الخلفية على off إلى الاستمرار في تفريغ أحداث مراقبة الأنماط بصمت.

      عمر العمليات الخلفية​

      تنتمي عمليات الطرفية الخلفية إلى الوكيل الذي يبدؤها. يؤدي إغلاق وكيل فرعي أثناء إنهاء التفويض إلى إنهاء عملياته المتبقية، بما في ذلك العمل الذي بدأه في أدوار سابقة، دون إيقاف العمليات المملوكة للوكيل الأب أو الوكلاء الأشقاء. ومشاركة بيئة الطرفية لا تنقل ملكية العمليات.

      ينبغي للوكيل الفرعي انتظار عمليات البناء والاختبارات وغيرها من الأوامر الخلفية محدودة المدة قبل إعادة ملخصه النهائي. ابدأ مراقِب CI أو الخادم في جلسة الوكيل الأب إذا كان يجب أن يستمر بعد انتهاء الوكيل الفرعي؛ فإعادة معرّف العملية لا تنقل ملكيتها إلى الوكيل الأب.

      مهمة واحدة​

      delegate_task(
          goal="Debug why tests fail",
          context="Error: assertion in test_foo.py line 42"
      )

      دفعة متوازية​

      حتى 10 subagents متزامنة افتراضيًا (قابل للضبط، دون حدّ أقصى ثابت):

      delegate_task(tasks=[
          {"goal": "Research topic A", "context": "Focus on recent primary sources"},
          {"goal": "Research topic B", "context": "Compare the leading explanations"},
          {"goal": "Fix the build", "context": "Project root: /home/user/project"}
      ])

      المخرجات المهيكلة (output_schema)​

      يمكن أن تحمل كل مهمة قيمة output_schema اختيارية، وهي كائن JSON Schema يجب أن تجتاز الإجابة النهائية للوكيل الفرعي التحقق وفقًا له. يرى الوكيل الفرعي المخطط مسبقًا بوصفه عقدًا للمخرجات؛ وعندما تعود الإجابة يتحقق منها الوكيل الأب، وعند الإخفاق يرسل إلى الوكيل الفرعي دور تصحيح واحدًا محدودًا بالضبط يتضمن أخطاء التحقق حرفيًا (دون إعادة لصق المخطط). بعدها تُضاف إلى نتيجة المهمة القيمة schema_valid (true/false)، وعند الإخفاق schema_errors.

      delegate_task(
          tasks=[{
              "goal": "Check which of these three endpoints return 200",
              "context": "https://a.example, https://b.example, https://c.example",
              "output_schema": {
                  "type": "object",
                  "properties": {
                      "healthy": {"type": "array", "items": {"type": "string"}},
                      "failing": {"type": "array", "items": {"type": "string"}}
                  },
                  "required": ["healthy", "failing"]
              }
          }]
      )

      اجعل المخططات متساهلة: اشترط فقط الحقول التي ستقرؤها فعلًا. المهام التي لا تحتوي على output_schema لا تتأثر.

      كيف يعمل سياق الـ Subagent​

      بالغ الأهمية: الـ Subagents لا تعرف شيئًا

      تبدأ الـ Subagents بمحادثة جديدة كليًا. فهي لا تعرف شيئًا على الإطلاق عن سجل محادثة الوكيل الأب، أو استدعاءات الأدوات السابقة، أو أي شيء نوقش قبل التفويض. السياق الوحيد للـ subagent يأتي من الحقلين goal وcontext اللذين يملؤهما الوكيل الأب عند استدعاء delegate_task.

      استثناء واحد: عندما يكون لدى الوكيل الأب مجلد workspace محدد، يُضمِّن الـ system prompt لكل subagent ملفات سياق المشروع الخاصة بذلك الـ workspace (.hermes.md > سلسلة AGENTS.md > CLAUDE.md > .cursorrules، بآلية الاكتشاف والأولوية وحدود الحجم نفسها المطبّقة على الـ system prompt للوكيل الرئيسي؛ مع استثناء SOUL.md). وبذلك تعمل الـ subagents داخل المستودع وفق أعراف المستودع نفسه دون الحاجة إلى إعادة اكتشافها.

      هذا يعني أن على الوكيل الأب تمرير كل ما يحتاجه الـ subagent في الاستدعاء:

      # BAD - subagent has no idea what "the error" is
      delegate_task(goal="Fix the error")

      # GOOD - subagent has all context it needs
      delegate_task(
          goal="Fix the TypeError in api/handlers.py",
          context="""The file api/handlers.py has a TypeError on line 47:
          'NoneType' object has no attribute 'get'.
          The function process_request() receives a dict from parse_body(),
          but parse_body() returns None when Content-Type is missing.
          The project is at /home/user/myproject and uses Python 3.11."""
      )

      يحصل الـ subagent على system prompt مركّز مبني من الهدف والسياق اللذين حددتهما، يوجّهه إلى إكمال المهمة وتقديم ملخص مهيكل لما فعله، وما توصّل إليه، والملفات التي عدّلها، وأي مشكلات واجهها.

          The project uses Flask, PyJWT, and bcrypt.

      إعادة هيكلة متعددة الملفات​

      فوّض مهمة إعادة هيكلة كبيرة كانت ستُغرق سياق الوكيل الأب:

      delegate_task(
          goal="Refactor all Python files in src/ to replace print() with proper logging",
          context="""Project at /home/user/myproject.
          Use the 'logging' module with logger = logging.getLogger(__name__).
          Replace print() calls with appropriate log levels:
          - print(f"Error: ...") -> logger.error(...)
          - print(f"Warning: ...") -> logger.warning(...)
          - print(f"Debug: ...") -> logger.debug(...)
          - Other prints -> logger.info(...)
          Don't change print() in test files or CLI output.
          Run pytest after to verify nothing broke."""
      )

      تفاصيل وضع الدفعات​

      عندما يقدّم وكيل من المستوى الأعلى مصفوفة tasks، يعيد Hermes معرّف تتبع خلفيًا واحدًا ويشغّل الـ subagents بالتوازي. افتراضيًا، يعيد الاستدعاء رسالة مجمّعة واحدة بعد انتهاء جميع المهام. ولا تُسلَّم النتائج إلا بين أدوار الوكيل الأب: لذا ينبغي للوكيل الأب إنهاء كل ما لا يعتمد على الوكلاء الفرعيين، ثم إنهاء دوره بدلًا من استطلاع السجلات أو المخرجات أو CI أثناء الانتظار.

      نتائج الإنجاز المستقلة (اختيارية)​

      اضبط delegation.independent_completions: true لتصل النتائج لكل وحدة إنجاز فور انتهائها بدلًا من ذلك. لا يُعلَن عن الحقل group الموجّه إلى النموذج ولا عن إرشادات التجميع إلا عند تفعيل هذا الخيار. ابدأ جلسة جديدة بعد تغييره حتى يعكس مخطط الأداة هذا الإعداد دون تغيير البادئة المخزّنة مؤقتًا لمحادثة قائمة. تبقى الاستدعاءات القديمة التي تحتوي على group مقبولة؛ وعند إيقاف الخيار، يعود الاستدعاء بأكمله دفعة واحدة.

      عند تفعيل نتائج الإنجاز المستقلة:

      • احذف group عندما تكون كل نتيجة مفيدة للتصرف بناءً عليها على حدة. عندها تُبلغ كل مهمة عن نتيجتها فور انتهائها.
      • استخدم سلسلة group نفسها عندما تريد مراجعة المخرجات معًا: للمقارنة، أو التجميع، أو اتخاذ قرار منسّق واحد. تعيد المجموعة رسالة مجمّعة واحدة بعد انتهاء جميع مهامها. وحتى المهام القابلة للتنفيذ باستقلالية يمكن أن تنتمي إلى مجموعة واحدة إذا كانت نتائجها تخدم القرار نفسه.
      • تُبلغ المجموعات المختلفة عن نتائجها باستقلالية؛ ويمكن للمهام المجمّعة وغير المجمّعة أن تتشارك استدعاءً واحدًا.

      هذا الخيار معطّل افتراضيًا لأن كل وحدة تمثّل دورًا جديدًا للمنسِّق: فالاستدعاء الذي يضم 15 مهمة يصبح حتى 15 عملية إيقاظ، وهو ما كان يجزّئ الحملات الطويلة. يتحكم التجميع في تسليم النتائج، لا في ترتيب التنفيذ: إذ تظل جميع المهام تعمل بالتوازي. إذا كانت المهمة B تحتاج إلى ناتج المهمة A لأداء عملها، فأرسل A أولًا، ثم أرسل B مع ذلك الناتج بعد عودة A.

      {"tasks": [
        {"goal": "Review PR #101 ..."},
        {"goal": "Review PR #102 ..."},
        {"goal": "Benchmark approach A ...", "group": "bench"},
        {"goal": "Benchmark approach B ...", "group": "bench"}
      ]}

      يسرد معرّف تتبع الإرسال كل وحدة (units[].delegation_id وgroup وtask_indexes)؛ ومعرّفات الوحدات هي معرّف الاستدعاء مع اللاحقة -1 و-2 و…، وتتشارك جميع وحدات الاستدعاء الواحد خانة واحدة من delegation.max_concurrent_children، لذا لا يغيّر التجميع أبدًا طريقة احتساب السعة (يتوسع مجمّع العمّال ليطابق عدد الوحدات النشطة، فلا تنتظر أي وحدة خلف مجمّع ممتلئ). أما الـ subagent المنسِّق فينتظر دفعته كاملة في الدور الحالي حتى يتمكن من تجميع النتائج.

      • الحد الأقصى للتزامن: 10 مهام افتراضيًا (قابل للضبط عبر delegation.max_concurrent_children أو متغير البيئة DELEGATION_MAX_CONCURRENT_CHILDREN؛ بحد أدنى 1 ودون حد أقصى ثابت). الدفعات التي تتجاوز الحد تعيد خطأ أداة بدلًا من اقتطاعها بصمت.
      • مجمّع الخيوط (Thread pool): يستخدم ThreadPoolExecutor مع جعل حدّ التزامن المضبوط هو الحد الأقصى لعدد العمّال
      • عرض التقدم: في وضع CLI، يعرض مخطط شجري استدعاءات الأدوات من كل subagent في الوقت الفعلي مع سطر إنجاز لكل مهمة. وفي وضع gateway، يُجمَّع التقدم على دفعات ويُمرَّر إلى دالة رد النداء (callback) الخاصة بتقدم الوكيل الأب. تستخدم إشعارات الإنجاز في CLI و TUI عناوين تبدأ بالمهمة مثل Subagent Task Completed: Review changes؛ أما المجموعات متعددة المهام فتستخدم اسم المجموعة وعدد المهام. ويحصل العمل غير الناجح أو غير المكتمل على تسمية حالة مقابلة. ولا تحلّ هذه الإشعارات المختصرة محلّ النتائج الكاملة المُسلَّمة إلى الوكيل الأب.
      • ترتيب النتائج: داخل الوحدة، تُرتَّب النتائج حسب فهرس المهمة لتطابق ترتيب المدخلات بغض النظر عن ترتيب الإنجاز؛ وتُرقِّم تسميات TASK i/N الاستدعاء بأكمله
      • الإلغاء: لا تُلغي رسائل المتابعة دفعة خلفية من المستوى الأعلى. يؤدي /stop أو إغلاق الجلسة المالكة أو إعادة ضبطها إلى إلغاء الوكلاء الفرعيين النشطين التابعين لها. أما الوكلاء الفرعيون المتزامنون التابعون لمنسِّق فيظلون يتبعون حالة المقاطعة الخاصة بالوكيل الأب

      يعمل التفويض المتزامن لمهمة واحدة من منسِّق مباشرةً دون العبء الإضافي لمجمّع الخيوط.

      نتائج الإنجاز الخلفية الدائمة​

      عندما ينتهي تفويض خلفي، يخزّن Hermes حدث الإنجاز الخاص به في state.db الخاص بالـ profile النشط قبل نشره في طابور الأدوار الجديدة المعتاد. إذا أُعيد تشغيل Hermes بعد الإنجاز وقبل التسليم، يُستعاد الحدث المعلّق ويُوجَّه عبر فحوصات الملكية نفسها. ويستخدم المستهلكون المتنافسون حجزًا دائمًا، بحيث لا يُقِرّ بالتسليم إلا المستهلك الذي ينجح في قبول الدور الاصطناعي؛ أما المحاولات الفاشلة فتحرّر الحجز لإعادة المحاولة.

      لا يستأنف هذا تنفيذ الوكيل الفرعي بعد التعطل. فالتفويض الذي تختفي عملية مالكه بينما لا يزال قيد التشغيل يُسجَّل بالحالة unknown، لأن Hermes لا يستطيع إثبات ما إذا كانت آثاره الجانبية الخارجية قد حدثت أم لا. وسجلات الأحداث المعلّقة والمُسلَّمة محدودة العدد ومحلية على مستوى الـ profile.

      إشعارات العمليات الخلفية للوكلاء الفرعيين​

      العمليات الخلفية التي يبدؤها subagent (مثل npm ci مع notify_on_complete) توجّه تقنيًا إشعارات الإنجاز ومراقبة الأنماط الخاصة بها إلى محادثة الوكيل الأب، لأن كل ما يعيش أطول من الوكيل الفرعي يحتاج إلى مستهلك دائم. افتراضيًا، تكون هذه الإشعارات مكتومة في محادثة الوكيل الأب، لأن نتيجة التفويض المجمّعة للوكيل الفرعي هي المُخرَج المطلوب، وسيل رسائل "process finished" وسط المحادثة الناتج عن عمليات البناء الداخلية للوكيل الفرعي مجرد ضجيج. تُسجَّل الأحداث المكتومة بمستوى debug مع معرّف جلسة العملية ومعرّف مهمة الـ subagent، لتبقى قابلة للتشخيص.

      أما نتيجة التفويض نفسها فلا تُكتم أبدًا. لاستعادة تسليم إشعارات عمليات الوكيل الفرعي (يحمل كل منها سطر إسناد "Started by subagent …"):

      delegation:
        surface_child_process_notifications: true   # default: false

      تسليم عملية إلى الوكيل الأب​

      تُنهى العمليات الخلفية للـ subagent أيضًا عند انتهاء الـ subagent، لذا فإن مراقِب CI أو عملية البناء التي يبدؤها وكيل فرعي مع notify=true لن تُبلغ أحدًا أبدًا. توضّح نتيجة terminal الخاصة بالوكيل الفرعي ذلك (notify_on_complete: false مع subagent_note)، ولدى الوكيل الفرعي ثلاثة خيارات صريحة قبل أن ينتهي:

      • الانتظار: process_manage(action="wait", session_id=...) ثم الإبلاغ عن النتيجة بنفسه؛
      • الإنهاء: process_manage(action="kill", ...)؛
      • التسليم: process_manage(action="handoff", session_id=..., data="<one sentence: what it is for>"). تنقل بيئة التشغيل الملكية إلى الوكيل الأب تحت قفل السجل (حتى 3 عمليات لكل وكيل فرعي؛ ولا تُقبل إلا عملية قيد التشغيل يملكها الوكيل الفرعي، وأي شيء آخر يُعدّ خطأ أداة). بعد ذلك يصل إشعار الإنجاز إلى محادثة الوكيل الأب مع Handed off to you by a subagent… Purpose: …، ويستطيع الوكيل الأب استطلاعها أو قراءة سجلها أو إنهاءها كما لو كانت عمليته.

      العملية التي تنتهي بينما لا يزال الوكيل الفرعي قيد التشغيل لا تحتاج إلى تسليم: إذ يقرؤها الوكيل الفرعي (poll/wait/log) ويُبلغ عنها. وإذا لم يقرأها الوكيل الفرعي أبدًا، يُرفق رمز الخروج وذيل المخرجات بنتيجته بوصفها unread_completions ويُعرضان على الوكيل الأب. وكل ما لا يزال قيد التشغيل ولم يُنهَ أو يُسلَّم يُذكر في نتيجته (orphaned_processes) وفي إشعار التفويض لدى الوكيل الأب بوصفه منتهيًا، بحيث يعلم الوكيل الأب من بيئة التشغيل، لا من نص الوكيل الفرعي، أن عبارة "the watcher is running" لم تعد صحيحة. وبالنسبة إلى مراقِبات CI، يبقى النمط الأفضل: أن يعيد الوكيل الفرعي المعلومة (رقم PR، والـ SHA) ويشغّل الوكيل الأب مراقِبه الخاص.

      تجاوز النموذج​

      يمكنك ضبط نموذج مختلف للـ subagents عبر config.yaml، وهو أمر مفيد لتفويض المهام البسيطة إلى نماذج أرخص أو أسرع:

      # In ~/.hermes/config.yaml
      delegation:
        model: "google/gemini-flash-2.0"    # Cheaper model for subagents
        provider: "openrouter"              # Optional: route subagents to a different provider

      إذا حُذف هذا الإعداد، تستخدم الـ subagents النموذج نفسه الذي يستخدمه الوكيل الأب.

      استراتيجية التكلفة: مخطِّط من الطراز الأول، وعمّال منخفضو التكلفة​

      تفكيك مشكلة إلى مهام فرعية محددة جيدًا يتطلب قدرة تقدير بمستوى النماذج المتقدمة (frontier)؛ أما تنفيذ مهمة فرعية تأتي أصلًا بهدف واضح وسياق كامل وعقد للمخرجات فلا يتطلب ذلك عادةً. وفي الوقت نفسه، فإن الوكلاء الفرعيين هم حيث تُستهلك الـ tokens: إذ تستهلك دفعة متوازية من الـ subagents عادةً الغالبية العظمى من إجمالي tokens التشغيل، لذا فإن نموذج العمّال هو موضع التكلفة الحقيقي. تثبيت delegation.model على نموذج منخفض التكلفة مع إبقاء جلستك الرئيسية على نموذج متقدم يحافظ على جودة التخطيط حيث تهمّ، ويخفّض الإنفاق حيث يكون الحجم:

      # ~/.hermes/config.yaml
      model:
        default: "your-frontier-model"     # parent (planner) stays on the frontier model
      delegation:
        model: "your-inexpensive-model"    # all delegate_task children run on this
        provider: "openrouter"             # optional: route children to a different provider

      ترتيب التحديد: تكون الأولوية لـ delegation.base_url (endpoint مباشر)، ثم delegation.provider (حزمة بيانات اعتماد كاملة تُحدَّد عبر نظام المزوّدين وقت التشغيل)، وعند عدم ضبط أيٍّ منهما يرث الوكلاء الفرعيون مزوّد الوكيل الأب وبيانات اعتماده؛ ويُطبَّق delegation.model في جميع الحالات، وعندما يكون فارغًا يرث الوكلاء الفرعيون نموذج الوكيل الأب. ضبط delegation.provider إلى جانب delegation.base_url يُبقي الـ endpoint الصريح، لكنه ينقل إلى الوكيل الفرعي تجاوزات الطلبات والحد الأقصى لـ tokens المخرجات الخاصة بذلك المزوّد. ويُحترم القاموس الصريح delegation.request_overrides في كل الحالات، ويُدمج فوق تلك القيم المشتقة وقت التشغيل (راجع الإعدادات أدناه).

      لاحظ أن التثبيت عام: فالأداة delegate_task لا تملك معاملًا لتحديد النموذج لكل مهمة، لذا يعمل كل وكيل فرعي في الدفعة على نموذج التفويض المضبوط. بالنسبة إلى المهام الفرعية الحساسة للجودة التي تحتاج إلى نموذج أقوى، إما أن تترك delegation.model دون ضبط في تلك الجلسة، أو أن تسلّم المهمة إلى لوحة kanban، التي تدعم تجاوز النموذج لكل مهمة.

      الأمر /review​

      يُنشئ /review وكيلًا فرعيًا (subagent) خلفيًا مستقلًا بصلاحيات كاملة، مهمته الوحيدة مراجعة العمل الذي أنتجته محادثتك للتو: PR، أو diff، أو كود، أو توثيق، أو تصميم. ويعمل على كل الواجهات: CLI و TUI وتطبيق Desktop وكل منصات المراسلة عبر الـ gateway.

      /review                       # review whatever the last 10 messages presented
      /review focus on security     # add extra instructions for the reviewer

      ما يحدث:

      1. تُلتقط آخر 10 رسائل من المستخدم والمساعد بوصفها الأدلة الأولية للمراجِع (تُستبعد مخرجات الأدوات ورسائل النظام).
      2. يُرسَل subagent مراجِع عبر مسار التفويض الخلفي نفسه الذي تستخدمه delegate_task، ويحصل على الـ toolset الكامل المعتاد للـ subagents (الطرفية، والويب، والملفات، والمتصفح...)، لذا فهو يفتح الـ PR فعليًا ويقرأ الـ diff ويشغّل الكود بدلًا من إصدار حكمه بناءً على المقتطف.
      3. يرث المراجِع سياق عمل الوكيل الأساسي: فأي مهارات حمّلها الوكيل الأساسي (سواء حُمِّلت مسبقًا عند الإطلاق أو عبر skill_view خلال الجلسة) تُذكر بأسمائها في إحاطته مع تعليمة بتحميلها وتقييم العمل وفق أعرافها. وكما هو الحال مع كل subagent، يُضمِّن الـ system prompt الخاص به أيضًا ملفات سياق المشروع في الـ workspace (AGENTS.md / CLAUDE.md / .cursorrules) بوصفها أعرافًا ملزمة.
      4. عند انتهائه، تعود مراجعته الكاملة إلى الجلسة نفسها بوصفها نتيجة إنجاز عادية لـ subagent خلفي، فيراها وكيلك الأساسي ويستطيع التصرف بناءً عليها (إصلاح الملاحظات، أو دفع تحديثات لاحقة، أو الرد عليك).

      التدفق النموذجي: يفتح وكيلك الرئيسي PR، فتكتب /review، ليفحصه طرف ثانٍ بينما تواصل عملك؛ ثم تعود المراجعة إلى المحادثة موجّهةً إلى الوكيل الذي أنشأ الـ PR.

      لا يطبع الإرسال سوى “Review started. Results will return here.” يعرّف عارض الـ subagents المباشر العامل بالاسم Review: your focus (أو Review recent work عند استخدام /review دون وسائط)، مع تسمية مختصرة من سطر واحد؛ ويظل المراجِع يتلقى تعليماتك كاملة. في CLI الكلاسيكي، يعرض الشريط أعلى مربع الكتابة الوقت المنقضي وآخر نشاط؛ ويفتح Ctrl+T (أو F6) قائمة الوكلاء مع النموذج والسجل وأدوات التوجيه والإيقاف. وتظهر تسمية المراجعة نفسها في عارضَي الـ subagents في TUI و Desktop.

      نموذج المراجعة​

      افتراضيًا، يعمل المراجِع على نموذجك الرئيسي. لتثبيت نموذج مخصص للمراجعة، اضبط auxiliary.review في config.yaml:

      auxiliary:
        review:
          provider: openrouter               # or nous, anthropic, a direct base_url, ...
          model: anthropic/claude-opus-4.6   # a strong reviewer model

      تُحدَّد بيانات الاعتماد تمامًا كما في تثبيت delegation.provider (حزمة المزوّد الكاملة وقت التشغيل: base_url و api key و api_mode). وتعني provider: auto مع model فارغ "وراثة نموذج الوكيل الرئيسي"، وهذا هو الافتراضي.

      الأمر /review منفصل عمدًا عن /refine: فالأمر /refine يراجع المحادثة لتحديث الذاكرة والمهارات، بينما يراجع /review ناتج العمل الذي أنشأته المحادثة.

      الوصول الموروث إلى الأدوات​

      لا تقبل delegate_task معامل toolsets موجّهًا إلى النموذج. إذ يرث كل subagent الـ toolsets المفعّلة لدى الوكيل الأب، حتى لا يستطيع النموذج منح وكيل فرعي قدرات لا يملكها الوكيل الأب. اضبط أدوات الوكيل الأب قبل بدء المحادثة إذا كان العمل المفوَّض يحتاج إلى قدرات إضافية.

      بعض الأدوات محظورة على الـ subagents حتى لو كانت متاحة للوكيل الأب:

      • delegate_task: محظورة على الـ subagents الطرفية (leaf) (الافتراضي). وتُتاح للوكلاء الفرعيين ذوي role="orchestrator"، ضمن حدود max_spawn_depth؛ راجع حدّ العمق والتنسيق المتداخل أدناه.
      • clarify: لا تستطيع الـ subagents التفاعل مع المستخدم
      • memory: لا كتابة في الذاكرة الدائمة المشتركة
      • send_message: لا آثار جانبية عبر المنصات
      • cronjob: لا جدولة لمزيد من العمل باسم الوكيل الأب

      يحتفظ كلا الدورين بـ execute_code (استدعاء الأدوات برمجيًا) حتى يتمكن الوكلاء الفرعيون من تجميع الأعمال الآلية في دفعات.

      الحد الأقصى للتكرارات​

      لكل subagent حدّ للتكرارات (الافتراضي: 250) يتحكم في عدد أدوار استدعاء الأدوات التي يمكنه تنفيذها. يُضبط هذا الحد على المستوى العام في config.yaml ويُطبَّق على كل وكيل فرعي؛ وليس معاملًا يُمرَّر في كل استدعاء لـ delegate_task:

      # In ~/.hermes/config.yaml
      delegation:
        max_iterations: 60   # lower it for fleets of simple tasks, raise it for long investigations

      الوكيل الفرعي الذي يستنفد رصيده يعود مع exit_reason: max_iterations وtruncated: true، ليتمكن الوكيل الأب من التمييز بين التوقف بسبب نفاد الرصيد والمهمة المكتملة.

      مهلة الوكيل الفرعي​

      افتراضيًا، لا توجد مهلة زمنية فعلية على الـ subagents. لا يفشل الوكلاء الفرعيون إلا بسبب ما يفعلونه فعلًا، كأخطاء API أو أخطاء الأدوات أو بلوغ رصيد التكرارات، وليس أبدًا بسبب مؤقّت على مستوى التفويض. كانت الإصدارات السابقة تتضمن حدًا صارمًا (300 ثانية، ثم 600 ثانية لاحقًا)، وكان يقتل باستمرار وكلاء فرعيين مشغولين لأسباب مشروعة في منتصف مهامهم: فمراجعات الكود العميقة، وعمليات البحث الموزّعة الكبيرة، ونماذج الاستدلال البطيئة تحتاج روتينيًا إلى أكثر من 10 دقائق مع إحراز تقدم ثابت طوال الوقت.

      ولا يزال اكتشاف الوكلاء الفرعيين العالقين فعلًا ممكنًا: إذ يتوقف مراقِب تقادم نبضات القلب (heartbeat) عن تحديث نشاط الوكيل الأب عندما لا يُحرز الوكيل الفرعي أي تقدم (لا استدعاءات API، ولا بدء لأدوات، ولا تحديث للطابع الزمني للنشاط)، مما يسمح لمهلة عدم النشاط في الـ gateway بالانطلاق على العامل العالق فعلًا. أما انتظار النموذج الجاري فيُحتسب تقدمًا: إذ تُحدِّث الـ subagents ساعة النشاط أثناء انتظار المزوّد، لذا لا يُعامَل الإكمال البطيء محليًا أو ذو مرحلة prefill الطويلة على أنه متوقف.

      إذا أردت حدًا صارمًا رغم ذلك (مثلًا للتحكم في التكلفة في التفويض غير المراقَب الذي تقوده مهام cron)، فعّله على مستوى كل تثبيت:

      delegation:
        child_timeout_seconds: 0     # default: 0 = no timeout
        # child_timeout_seconds: 1800  # opt-in hard cap (floor 30s)

      تفرض القيمة الموجبة حدًا زمنيًا فعليًا صارمًا على كل وكيل فرعي؛ بينما تعطّله القيمة 0 أو أي قيمة سالبة.

      عند انطلاق حدّ مضبوط، تحمل نتيجة الوكيل الفرعي بيانات وصفية مهيكلة عن المهلة إلى جانب رسالة الخطأ، ليتمكن الآباء والـ hooks من التمييز بين القتل بسبب المؤقّت والإخفاقات الأخرى دون تحليل النص: timeout_seconds (الحد المضبوط)، وtimed_out_after_seconds (الوقت الفعلي المنقضي)، و timeout_phase (القيمة before_first_llm_call عندما لا يصل الوكيل الفرعي أبدًا إلى طلبه الأول، وafter_llm_calls في غير ذلك). وتكون القيم الثلاث null في الأخطاء غير المتعلقة بالمهلة.

      إظهار الإخفاقات​

      الـ subagent الذي يُخفق، سواء بسبب خطأ مزوّد غير قابل لإعادة المحاولة (404/400)، أو انتهاء المهلة، أو التعطل، أو عدم وجود مخرجات صالحة للاستخدام، لا يُخفق بصمت أبدًا:

      • CLI: تطبع شجرة التفويض سببًا من سطر واحد: ⚠️ Subagent failed — "your goal": HTTP 404: model not found (after 12s). وتُلحق تشغيلات الدفعات السبب بسطر الإنجاز ✗ الخاص بكل مهمة.
      • منصات الـ Gateway (Telegram و Discord و Slack و...): يُسلَّم السطر الواضح نفسه بوصفه إشعارًا مستقلًا في المحادثة، حتى عندما يكون tool_progress معطّلًا لتلك المنصة.
      • الوكيل الأب: يحمل إدخال نتيجة الأداة status: "failed" إضافة إلى نص error الكامل، ليتمكن النموذج من التصرف (إعادة المحاولة، أو إعادة التوجيه، أو الإبلاغ).

      يُختزل نص الخطأ إلى السطر الأكثر إفادة (رسالة الاستثناء، لا جدار من تتبّع الأخطاء) مع تقييد طوله.

      تفريغ تشخيصي عند انتهاء المهلة دون أي استدعاء

      عند ضبط حدّ صارم، إذا انتهت مهلة subagent دون أن يُجري أي استدعاء API (والسبب عادةً: تعذّر الوصول إلى المزوّد، أو إخفاق المصادقة، أو رفض مخطط الأدوات)، تكتب delegate_task ملفًا تشخيصيًا مهيكلًا في ~/.hermes/logs/subagent-timeout-<session>-<timestamp>.log يحتوي على لقطة (snapshot) من إعدادات الـ subagent، وتتبّع عملية تحديد بيانات الاعتماد، وأي رسائل خطأ مبكرة، وتتبّعات المكدّس (stack traces) لـ جميع الخيوط النشطة (لا لخيوط الوكيل الفرعي وحده)، إذ لا يمكن التمييز بين وكيل فرعي متوقف بانتظار خيط مساعد متداخل ومزوّد بطيء دون الصورة الكاملة.

      اكتشاف توقّف الـ Subagents الخلفية​

      تخضع عمليات التفويض الخلفية (delegate_task(background=true)) لمراقبة مراقِب توقّف قائم على التقدم، مفعّل افتراضيًا ودون أي إعداد. وعلى خلاف المهلة الزمنية الفعلية، لا يمسّ هذا المراقِب أبدًا وكيلًا فرعيًا يُحرز تقدمًا، مهما طالت مدة تشغيله.

      يأخذ المراقِب عينات من إشارات التقدم لكل وكيل فرعي منفصل: عدد استدعاءات API، والأداة الحالية، والطابع الزمني لآخر نشاط (الذي يُحدَّث مع كل token مُتدفِّق، وكل انتقال بين الأدوات، وكل حدّ لاستدعاء API، لذا فالوكيل الفرعي الذي يكون في منتصف تدفق رد طويل يُعدّ دائمًا نشطًا):

      1. لا يُمسّ الوكلاء الفرعيون الذين يُحرزون تقدمًا أبدًا. فأي إشارة متقدمة تعيد ضبط المؤقّت.
      2. الوكيل الفرعي الذي يتجمد تقدمه كليًا متجاوزًا عتبة التقادم (450 ثانية في حالة الخمول، و1200 ثانية أثناء وجوده داخل أداة، إذ تحصل أوامر الطرفية وعمليات جلب الويب البطيئة لأسباب مشروعة على الحد الأعلى) يُقاطَع ويُمنح نافذة سماح مدتها 120 ثانية. والوكيل الفرعي الذي ينهي عمله في الوقت المناسب يُسلّم نتائجه الجزئية عبر مسار الإنجاز المعتاد.
      3. أما الوكيل الفرعي الذي لا يعود أبدًا فيُنهى قسرًا بحدث إنجاز نهائي stalled، بحيث تتلقى الجلسة المالكة نتيجةً بدلًا من الصمت، وتتحرر الخانة غير المتزامنة لعمل جديد.

      يحمل الحدث stalled بيانات وصفية مهيكلة تحاكي حقول المهلة في المسار المتزامن: stalled_after_quiet_seconds وstall_threshold_seconds وstall_phase (idle / in_tool) وstall_grace_seconds.

      عالج ذلك نمط إخفاق قديمًا كان فيه الوكيل الفرعي الخلفي العالق يترك جلسته تبدو ميتة حتى إعادة تشغيل العملية. كما أُصلح سبب التعلّق الأساسي (تعلّق الوكلاء الفرعيين عند أول استدعاء API لهم بعد تشغيل الـ gateway لعدة أيام متواصلة) من جذوره: إذ بات الوكلاء الفرعيون المفوَّضون ينفّذون طلبات API بصيغة OpenAI مباشرةً ضمن خيط المحادثة الخاص بهم بدلًا من خيط عامل متداخل، وهي الطبقة التي كان يحدث فيها التعلّق. ويبقى مراقِب التوقّف شبكة أمان لأي حالة أخرى.

      مراقبة الـ Subagents قيد التشغيل (/agents)​

      يأتي TUI مع طبقة عرض /agents (والاسم البديل /tasks) تحوّل توزيع delegate_task التعاودي إلى واجهة تدقيق متكاملة:

      • عرض شجري مباشر للـ subagents قيد التشغيل والمنتهية مؤخرًا، مجمّعة حسب الوكيل الأب
      • ملخصات لكل فرع تشمل التكلفة والـ tokens والملفات التي جرى التعامل معها
      • أدوات الإنهاء والإيقاف المؤقت: ألغِ subagent محددًا أثناء عمله دون مقاطعة أشقائه
      • المراجعة اللاحقة: تنقّل خطوة بخطوة عبر سجل كل subagent دورًا بدور حتى بعد عودته إلى الوكيل الأب

      النشاط المباشر أعلى مربع الكتابة​

      يعرض كلٌّ من CLI الكلاسيكي و TUI و Desktop الـ subagents النشطة تلقائيًا أعلى مربع الكتابة. ويمكنك مواصلة الكتابة أثناء متابعة العدد المباشر، وأسماء المهام، والوقت المنقضي، وآخر نشاط. يحدّ شريط الطرفية عدد الصفوف المرئية وفق ارتفاع الشاشة ويُظهر عدد العمّال الإضافيين المخفيين؛ بينما يعرض Desktop معاينة لما يصل إلى ثلاثة عمّال.

      يعيدك إغلاق مراقِب الطرفية إلى مسودتك الحالية في مربع الكتابة. يستخدم التوجيه حقل إدخال خاصًا به ويُقِرّ بأن الرسالة في الطابور، لا بأنها سُلِّمت: إذ يستهلك الوكيل الفرعي التوجيهات عند نقطة تحقق. ولا يقاطع الإيقاف الأشقاء غير المعنيين.

      اضغط F7 في مربع الكتابة في CLI الكلاسيكي أو TUI للتبديل بين معاينة الشريط متعددة الصفوف وسطر ملخص واحد مظلّل. يحتفظ الملخص بالعدد المباشر وتلميحات التوسيع والاستعادة، ويضيف النشاط عندما تسمح المساحة. وتبقى الكتابة والإرسال متاحين؛ كما يحافظ فتح المراقِب وإغلاقه على مسودتك وموضع المؤشر. هذا خيار عرض محلي، وليس تغييرًا محفوظًا في الإعدادات.

      ذيل السجل المباشر مقتطف حديث محدود، وليس متصفحًا غير محدود للمحادثة. والوكيل الفرعي الذي يغادر السجل المباشر يختفي من الشريط؛ وتبقى رسائل الإنجاز وعروض السجل في TUI/Desktop هي المكان المناسب لمراجعة العمل المنتهي. وآخر نشاط هو مجرد ملاحظة، لا تقديرًا لنسبة الإنجاز.

      لا يزال الأمران /agents و/tasks في CLI الكلاسيكي يطبعان ملخصًا نصيًا؛ أما Ctrl+T (أو F6) فهو المراقِب التفاعلي الفوري، حتى أثناء انشغال الوكيل الأب. راجع TUI — الـ Slash commands.

      في CLI الكلاسيكي وفي كل منصات الـ gateway (Telegram و Discord و Slack و...)، يسرد /agents أيضًا عمليات التفويض الخلفية مع النشاط المباشر لكل وكيل فرعي، بعيّنات تُؤخذ مباشرةً من كل وكيل فرعي قيد التشغيل:

      Background delegations: 1 running
      - deleg_ab12cd34 · running · research the delegation stall monitor
        - child 1: 4 api calls · in web_search · active 12s ago
        - child 2: 7 api calls · between turns · active 3s ago

      يظهر التفويض الذي أشّر عليه مراقِب التوقّف بالشكل stalling · no progress 450s — interrupting، بينما يُظهر الوكلاء الفرعيون الهادئون لفترة طويلة لكنهم سليمون مدة هدوئهم، لتتمكن من التمييز بين "slow" و"stuck" بنظرة سريعة.

      توجيه Subagent قيد التشغيل​

      مقاطعة الوكيل الفرعي تُهدر العمل الجاري لديه؛ وغالبًا ما تريد فقط إعادة توجيهه.

      من الوكيل الأب (موجّه إلى النموذج)​

      ينسّق الوكيل الأب وكلاءه الفرعيين قيد التشغيل باستخدام الأداة delegate_task نفسها التي أنشأهم بها، دون أداة تحكم منفصلة:

      {"action": "list"}
      {"action": "steer", "subagent_id": "sa-0-1a2b3c4d", "message": "focus on pricing instead"}
      {"action": "stop",  "subagent_id": "sa-0-1a2b3c4d"}
      • يعيد list الوكلاء الفرعيين النشطين في المحادثة: subagent_id، والهدف، والحالة، وrunning_seconds، وaccepting_steer، ومسار السجل المباشر. كما تعود المعرّفات أيضًا في استجابة إرسال الإنشاء بوصفها subagent_ids.
      • يضع steer تصحيحًا للمسار في طابور وكيل فرعي قيد التشغيل دون إيقافه (دلالات التسليم موضّحة أدناه).
      • يُنهي stop الوكيل الفرعي مبكرًا عند حدّ التكرار التالي؛ وتظل النتيجة الجزئية تعود إلى المحادثة بوصفها رسالة إنجاز عادية.

      تُنفَّذ إجراءات التحكم بشكل متزامن ضمن الدور نفسه (ولا تُرسَل إلى الخلفية أبدًا)، ويقتصر نطاقها على شجرة الإنشاء الخاصة بالمستدعي، إذ لا يمكن لمحادثة أبدًا رؤية الوكلاء الفرعيين لجلسة أخرى أو التحكم فيهم، ولا تستهلك أبدًا حدّ إنشاء الـ subagents لكل دور، لذا يظل stop يعمل حتى بعد بلوغ الحد.

      من TUI / الـ gateway (موجّه إلى الجلسة)​

      الدالة steer_subagent(subagent_id, text) في tools/delegate_tool_registry.py هي نظيرة interrupt_subagent() على جانب إعادة التوجيه: فهي تضع نصًا في طابور وكيل فرعي نشط عبر الآلية نفسها التي يستخدمها /steer، إذ يُلحق النص بآخر نتيجة أداة لدى الوكيل الفرعي عند حدّ التكرار التالي، ولا يُقطع استدعاء الأداة الجاري أبدًا، ويرى الوكيل الفرعي النص بوصفه رسالة مستخدم خارج السياق المعتاد. تصل إليها المضيفات البرمجية عبر RPC الـ gateway subagent.steer المحصور بنطاق الجلسة، والموجود إلى جانب subagent.interrupt:

      {"method": "subagent.steer", "params": {"session_id": "owning-ui-session", "subagent_id": "sa-0-1a2b3c4d", "text": "focus on pricing instead"}}

      تأتي معرّفات الـ subagents من delegation.status (أو list_active_subagents())، وهو المصدر نفسه الذي يحصل منه subagent.interrupt عليها. لا يقبل الـ gateway التوجيه إلا من جلسة الواجهة/الـ gateway النشطة نفسها بالضبط التي أنشأت الوكيل الفرعي. وتُرفض هوية الجلسة المفقودة أو الغريبة أو الملتبسة أو القديمة/المُعاد تدويرها؛ فمعرفة معرّف subagent عام لا تمنح أي صلاحية. ويحتفظ المستدعون المباشرون داخل العملية نفسها عمدًا بعقد الدالة المساعدة غير المقيّد بنطاق.

      الوضع في الطابور لا يعني التسليم، لكنه لا يعني أبدًا نجاحًا وهميًا. تعني الاستجابة "queued" أن النص قُبل قبل حدّ إنجاز الوكيل الفرعي، لا بالضرورة أن الوكيل الفرعي قد رآه. والقبول والإنجاز متزامنان: فإما أن يظل الوكيل الفرعي قادرًا على استهلاك النص، أو يُفرَّغ نصه بالضبط في النتيجة بوصفه pending_steer. وتعيد الاستدعاءات بعد الإغلاق "rejected". إذا قبل وكيل فرعي التوجيه لكنه كان قد أنتج إجابته النهائية بالفعل، يحتفظ إدخال الإنجاز الذي يتلقاه الوكيل الأب به بوصفه missed_steer، مع ملاحظة تُلحق بالملخص:

      [steer did not land — the subagent finished before it could be delivered: focus on pricing instead]

      وبذلك يستطيع الوكيل الأب (أو المشغّل الذي يديره) التمييز بين وكيل فرعي تلقّى التوجيه وآخر أنهى عمله وفق التعليمات القديمة، وإعادة إصدار التوجيه بوصفه متابعة بدلًا من افتراض أنه وصل.

      السجلات المباشرة​

      يُنشئ كل إرسال لـ delegate_task أيضًا سجلًا واحدًا لكل مهمة، قابلًا للإلحاق فقط ومقروءًا للبشر، لتتمكن أنت (أو الوكيل الأب) من متابعة عمل الـ subagent في الوقت الفعلي بدلًا من انتظار الملخص المجمّع:

      <hermes_home>/cache/delegation/live/<delegation_id>/task-<n>.log

      تتضمن استجابة الإرسال المسارات بوصفها live_transcripts، وتُنشأ الملفات مسبقًا لحظة الإرسال، لذا يعمل هذا فورًا:

      tail -f ~/.hermes/cache/delegation/live/deleg_ab12cd34/task-0.log

      يحمل كل سطر طابعًا زمنيًا ويعرض نص المساعد لدى الوكيل الفرعي، ومقتطفات من التفكير، واستدعاءات الأدوات (-> tool_name({args}))، ونتائج الأدوات، وعلامة حالة نهائية. ويصف ملف manifest.json في المجلد نفسه الدفعة (الأهداف، وعدد المهام، وحالة كل مهمة). تبقى السجلات محفوظة بعد الإنجاز، إذ تعمل أيضًا بوصفها السجل التشغيلي الكامل الدقة إلى جانب الملخص، وتُحذف المجلدات التي يزيد عمرها على 7 أيام تلقائيًا عند عمليات الإرسال الجديدة. ولأنها موجودة ضمن cache/delegation، فهي قابلة للقراءة أيضًا من terminal backends البعيدة (Docker/Modal/SSH).

      حدّ العمق والتنسيق المتداخل​

      افتراضيًا، يكون التفويض مسطّحًا: ينشئ الوكيل الأب (العمق 0) وكلاء فرعيين (العمق 1)، ولا يمكن لهؤلاء الوكلاء الفرعيين التفويض أكثر. وهذا يمنع التفويض التعاودي الخارج عن السيطرة.

      بالنسبة إلى سير العمل متعدد المراحل (بحث → تجميع، أو تنسيق متوازٍ عبر مشكلات فرعية)، يمكن للوكيل الأب إنشاء وكلاء فرعيين منسِّقين (orchestrator) يستطيعون تفويض عمّالهم الخاصين:

      delegate_task(
          goal="Survey three code review approaches and recommend one",
          role="orchestrator",  # Allows this child to spawn its own workers
          context="...",
      )
      • role="leaf" (الافتراضي): لا يستطيع الوكيل الفرعي التفويض أكثر، وهو سلوك مطابق للتفويض المسطّح.
      • role="orchestrator": يحتفظ الوكيل الفرعي بالـ toolset delegation. ويخضع ذلك لـ delegation.max_spawn_depth (الافتراضي 1 = مسطّح، لذا لا يكون لـ role="orchestrator" أي أثر مع القيم الافتراضية). ارفع max_spawn_depth إلى 2 للسماح للوكلاء الفرعيين المنسِّقين بإنشاء أحفاد طرفيين (leaf)؛ و3 فأكثر لأشجار أعمق. لا يوجد حد أقصى، والتكلفة هي الحد العملي.
      • delegation.orchestrator_enabled: false: مفتاح إيقاف عام يفرض leaf على كل وكيل فرعي بغض النظر عن المعامل role.

      تحذير بشأن التكلفة: مع max_spawn_depth: 3 وmax_concurrent_children: 3، يمكن أن تصل الشجرة إلى 3×3×3 = 27 وكيلًا طرفيًا متزامنًا. كل مستوى إضافي يضاعف الإنفاق، لذا ارفع max_spawn_depth عن قصد.

      مدة الحياة والديمومة​

      ديمومة نتائج الإنجاز الخلفية لا تعني تنفيذًا دائمًا

      تعمل استدعاءات delegate_task الموجّهة إلى النموذج على المستوى الأعلى في الخلفية تلقائيًا حيثما تدعم الجلسة التسليم اللاحق. يعيد Hermes معرّف تتبع فورًا، وتعود النتيجة إلى المحادثة بعد انتهاء الوكيل الفرعي أو الدفعة. أما الـ subagents المنسِّقة فتنتظر عمّالها في الدور الحالي لأن عليها تجميع تلك النتائج قبل العودة. وتعود الـ endpoints عديمة الحالة القائمة على الطلب/الاستجابة إلى التنفيذ المتزامن عندما لا تستطيع تسليم نتيجة منفصلة لاحقًا.

      • لا تُلغي رسائل المتابعة العادية الوكلاء الفرعيين الخلفيين. يلغي /stop عمليات التفويض الخلفية قيد التشغيل، ويؤدي إغلاق الجلسة المالكة أو إعادة ضبطها إلى تجاهل وكلائها الفرعيين النشطين.
      • يقاطع الإغلاق أو إعادة الضبط الصريحان للجلسة وكلاءها الفرعيين الخلفيين. أما إغلاق عارض TUI لجلسة يملكها الـ gateway فلا يُنهي عمل الـ gateway.
      • إعادة تشغيل عملية Hermes لا تستأنف وكيلًا فرعيًا قيد التشغيل. إذ تصبح محاولته unknown لأن Hermes لا يستطيع إثبات الآثار الجانبية التي حدثت.
      • الوكيل الفرعي الذي أكمل عمله قبل إعادة التشغيل لكن نتيجته لم تُسلَّم يُستعاد ويُوجَّه مجددًا عبر الفحوصات المعتادة للجلسة المالكة.
      • يعيد الوكلاء الفرعيون الملغون نتيجة مهيكلة (status="interrupted"، exit_reason="interrupted")، لكن لأن الوكيل الأب قوطع هو الآخر، فإن هذه النتيجة غالبًا لا تصل أبدًا إلى رد مرئي للمستخدم.

      للحصول على تنفيذ دائم يجب أن يصمد أمام إغلاق الجلسة أو إعادة تشغيل العملية، استخدم:

      • cronjob (action=create): يجدول تشغيلًا منفصلًا للوكيل؛ ولا يتأثر بمقاطعات دور الوكيل الأب.
      • terminal(background=True, notify_on_complete=True): أوامر shell طويلة التشغيل تستمر في العمل بينما يؤدي الوكيل مهام أخرى.

      الخصائص الرئيسية​

      • يحصل كل subagent على جلسة طرفية خاصة به (منفصلة عن الوكيل الأب)
      • ترث الـ subagents الـ toolsets المفعّلة لدى الوكيل الأب؛ ولا يستطيع النموذج اختيارها أو توسيعها في كل استدعاء
      • التفويض المتداخل اختياري: لا يستطيع التفويض أكثر إلا الوكلاء الفرعيون ذوو role="orchestrator"، وفقط عند رفع max_spawn_depth عن قيمته الافتراضية 1 (مسطّح). عطّله على المستوى العام باستخدام orchestrator_enabled: false.
      • لا تستطيع الـ subagents الطرفية (leaf) استدعاء: delegate_task، clarify، memory، send_message، cronjob. وتحتفظ الـ subagents المنسِّقة بـ delegate_task مع إبقاء الحظر على البقية. ويحتفظ كلا الدورين بـ execute_code (استدعاء الأدوات برمجيًا) حتى يتمكن الوكلاء الفرعيون من تجميع الأعمال الآلية في دفعات بدلًا من استهلاك تكرارات الاستدلال.
      • الإلغاء يتبع الملكية: يؤدي /stop أو إغلاق الجلسة المالكة أو إعادة ضبطها إلى إلغاء وكلائها الفرعيين الخلفيين؛ ويتبع الأحفاد المتزامنون التابعون للمنسِّقين حالة المقاطعة الخاصة بالوكيل الأب
      • لا يدخل سياقَ الوكيل الأب سوى الملخص النهائي، مما يُبقي استهلاك الـ tokens فعّالًا
      • ترث الـ subagents مفتاح API وإعدادات المزوّد ومجمّع بيانات الاعتماد الخاصة بالوكيل الأب (مما يتيح تدوير المفاتيح عند بلوغ حدود المعدل)

      العزل عبر Worktree​

      افتراضيًا، تتشارك الـ subagents مجلد العمل الخاص بالوكيل الأب، وهذا مناسب للبحث والأعمال التي يغلب عليها القراءة، لكن الوكلاء الفرعيين المتوازين الذين يعدّلون المستودع نفسه قد يتصادمون. اضبط delegation.worktree_isolation: true لمنح كل وكيل فرعي git worktree خاصًا به، متفرعًا من HEAD الحالي للمستودع (مستوحى من الخيار --subagent-worktree-isolation في Muse Code):

      delegation:
        worktree_isolation: true   # default: false

      عند تفعيل العزل:

      • يبدأ كل وكيل فرعي طرفيته في <repo>/.worktrees/subagent-<id> على الـ branch الخاص به hermes-subagent/subagent-<id>، وتوجّهه رسالة الهدف إلى العمل وإنشاء الـ commits هناك.
      • تبقى النسخة المسحوبة (checkout) الخاصة بالوكيل الأب دون مساس؛ ولا يستطيع الوكلاء الفرعيون الكتابة فوق تعديلات بعضهم.
      • عندما ينتهي وكيل فرعي، يُضاف إلى إدخال نتيجته حقل worktree يُبلغ عن path وbranch وcommits (المتقدمة على الأساس) وdirty. ويراجع الوكيل الأب كل branch أو يدمجه (git log <branch>، git merge <branch>).
      • الـ worktree الذي يُترك دون commits وبشجرة نظيفة يُحذف تلقائيًا (pruned: true)؛ أما أي worktree يحتوي على عمل فيُحتفظ به.
      • يتطلب الحذف دليلًا. فإذا فشل فحص git، أو حدث خطأ في مرحلة الإنهاء نفسها، يُحتفظ بالـ worktree والـ branch ويحمل الإدخال inspection_failed: true إضافة إلى note، وعندها تكون commits/dirty قيمًا افتراضية لا قياسات، لذا افحص الـ worktree بدلًا من افتراض أن الوكيل الفرعي لم يُنتج شيئًا.

      النطاق: اختياري، ويقتصر على git، وعلى terminal backend المحلي فقط. في مجلد لا يستخدم git، أو على backends من نوع docker/ssh/modal، أو إذا فشل إنشاء الـ worktree، يتراجع الإعداد بصمت إلى سلوك مساحة العمل المشتركة المعتاد حاليًا، ولا يُنتج خطأً أبدًا.

      # routing hints when delegating straight to openrouter.ai via base_url:
      delegation:

        base_url: "https://openrouter.ai/api/v1"

          extra_body:

              sort: throughput   # children route to the fastest OpenRouter provider

      عندما يشير base_url إلى endpoint متوافق مع Anthropic، مثل مسار ينتهي بـ /anthropic، أو مسار Claude في Azure Foundry، أو proxy من MiniMax بالمسار /anthropic، يُكتشف api_mode تلقائيًا على أنه anthropic_messages، ليستخدم الـ subagent صيغة النقل الصحيحة دون أن تضبط أي شيء. اضبط api_mode صراحةً عندما يكون تخمين الاكتشاف التلقائي خاطئًا (وهذا نادر).

      تُجري الـ subagents الضغط (compaction) عند عتبة النسبة نفسها المطبّقة على الوكيل الأب (compression.threshold، أي 0.50 × حجم النافذة افتراضيًا). ويضيف delegation.compression_threshold_tokens (الافتراضي 0، أي معطّل) حدًا مطلقًا اختياريًا على عتبة بدء الضغط لدى الوكيل الفرعي، ويُطبَّق باعتماد القيمة الأدنى بينه وبين عتبة النسبة؛ ولا يمسّ أبدًا حمولة الطلب أو الوكيل الأب. يُفعَّل عند ضبط عدد tokens لا يقل عن 16000؛ أما true أو "200k" فهي أخطاء إعدادات يُحذَّر منها وتُتجاهل. ويبقى معطّلًا افتراضيًا لأن إعادة تشغيل تجربة ضمّت 1,393 وكيلًا أظهرت أن الحدود بين 200K و400K تتقارب في التكلفة ضمن نطاق 5% بمجرد بقاء بادئات التخزين المؤقت سليمة، كما أن كل عملية ضغط تمثل فرصة لفقدان التفاصيل.

      يعمل delegation.request_overrides في الحالات الثلاث كلها لتحديد المزوّد: base_url المباشر، وprovider المسمّى، والوراثة الخالصة، لذا يسري مفعوله دائمًا. المفاتيح على المستوى الأعلى هي وسائط API (مثل service_tier)؛ أما القاموس الفرعي extra_body فيُدمج في extra_body الخاص بالطلب. تُدمج القيم الصريحة فوق التجاوزات المشتقة من بيئة التشغيل أو من الوكيل الأب: فالمفاتيح الصريحة على المستوى الأعلى تكون لها الأولوية، ويُدمج extra_body دمجًا عميقًا بمستوى واحد، بحيث تبقى خصائص الطلب الخاصة بالمزوّد (مثل thinking: {type: disabled}) ما لم يُعِد مفتاحك تعريفها. راجع الإعدادات → التفويض لمزيد من التفاصيل.

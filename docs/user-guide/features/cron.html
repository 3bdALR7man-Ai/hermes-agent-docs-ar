      المهام المجدولة (Cron)

      جدوِل مهامًا لتعمل تلقائيًا بلغة طبيعية أو بتعبيرات cron. يعرض Hermes إدارة cron عبر أداة cronjob واحدة بعمليات على شكل أفعال بدلًا من أدوات جدولة/سرد/إزالة منفصلة.

      ما يمكن لـ cron فعله الآن​

      يمكن لمهام cron أن:

      • تجدول مهامًا لمرة واحدة أو متكررة
      • توقف، وتستأنف، وتُحرَّر، وتُشغَّل، وتُزال
      • ترفق صفر، أو مهارة واحدة، أو عدة مهارات بمهمة
      • تسلّم النتائج إلى المحادثة الأصلية، أو ملفات محلية، أو أهداف منصة مُعدَّة
      • تعمل في جلسات وكيل جديدة بقائمة الأدوات الثابتة العادية
      • تعمل في وضع بلا وكيل — سكربت على جدول، يُسلَّم مخرجه القياسي (stdout) حرفيًا، دون أي تدخّل من LLM (راجع قسم وضع بلا وكيل أدناه)

      كل هذا متاح لـ Hermes نفسه عبر أداة cronjob، فيمكنك إنشاء المهام وإيقافها وتحريرها وإزالتها بمجرد الطلب بلغة عادية — دون الحاجة إلى CLI.

      نصيحة

      على أي نموذج تعمل مهمة cron؟ الحل عند وقت التشغيل هو: تثبيت خاص بالمهمة ← cron.model في config.yaml ← الافتراضي العام من hermes model.

      • تثبيت خاص بالمهمة — يضبطه أنت عبر لوحة التحكم، أو hermes cron create/edit --model … --provider …، أو بتحرير ~/.hermes/cron/jobs.json. بمجرد ضبطه، يبقى ثابتًا حتى تغيّره. لا تستطيع أداة cronjob الخاصة بالوكيل ضبط أو تغيير نماذج مثبَّتة لكل مهمة — تثبيتات الاستدلال (inference) يملكها المستخدم.
      • cron.model / cron.model_provider — افتراضي لأسطول cron بأكمله: كل مهمة غير مثبَّتة تعمل على هذا النموذج، بمعزل عن نموذج محادثتك. اضبطه مرة واحدة (hermes config set cron.model <name>)، وتبديل نموذج محادثتك عبر hermes model أو /model لن يمسّ أسطول cron أبدًا.
      • الافتراضي العام — فقط عندما لا يُضبَط أي من السابقين تتبع المهمة hermes model. يأخذ Hermes لقطة للمزوّد والنموذج عند الإنشاء، وتلك اللقطة هي التثبيت الفعلي للمهمة: إذا بدّلت لاحقًا الافتراضي العام (hermes model، أو /model، أو hermes config set model.default …)، تظل المهمة تعمل على النموذج والمزوّد اللذين أُنشئت تحتهما وتسجّل سطر INFO واحدًا لكل تشغيل يذكر الفرق. تغيير النموذج العام لا يوقف مهمة مجدولة أبدًا، ومهمة غير مُشرَف عليها لا ترث بصمت أبدًا تبديلًا إلى مزوّد/نموذج مدفوع (#44585). لنقل مهمة إلى الافتراضي الجديد، أعد اللقطة (resnap) (hermes cron resnap <job_id>، أو --all لكل مهمة غير مثبَّتة) بحيث تتبنّى الافتراضي الحالي مع بقائها غير مثبَّتة، أو ثبّتها (hermes cron edit <job_id> --provider <provider> --model <model>)، أو اضبط cron.model لنقل الأسطول كله دفعة واحدة. المهام المُنشأة قبل وجود اللقطات تظل تتبع الافتراضي العام الحي.

      أيًّا كان المزوّد الذي تُحلّ إليه المهمة، فإن إعدادات طلبه الخاصة بالمزوّد (مثل request_overrides كـ extra_body/extra_headers للمزوّدين المخصصين) تنتقل إلى التشغيل المجدوَل تمامًا كما في جلسة تفاعلية.

      hermes setup --portal هو الخيار الأقل احتكاكًا للتشغيلات غير المُشرَف عليها لأن تجديد OAuth تلقائي. راجع Nous Portal.

      نصيحة

      جهد الاستدلال (reasoning effort) الخاص بكل مهمة. يمكن لمهمة تثبيت مستوى تفكيرها الخاص، بمعزل عن تثبيت النموذج: واحد من none، minimal، low، medium، high، xhigh، max، ultra. عند ضبطه، يتجاوز كلًّا من agent.reasoning_effort العام وagent.reasoning_overrides الخاص بكل نموذج لتشغيلات تلك المهمة (none يعطّل التفكير). اضبطه عبر hermes cron create/edit --reasoning-effort high؛ مرّر نصًا فارغًا عند التحرير لمسح التثبيت والعودة لاتّباع الإعدادات. (لم يُعرَض عمدًا في أداة cronjob الخاصة بالوكيل — إعداد النموذج يبقى قرار المستخدم.) المستويات التي لا يدعمها نموذج ما تُقيَّد أو تُهمَل من قِبل المزوّد وقت الطلب — تثبيت xhigh على نموذج سقفه high يشغّله عند high. لا أثر للتثبيت على مهام no_agent (لا يوجد استدعاء LLM لضبطه). استخدمه لتشغيل تحليلات مجدولة ثقيلة عند high بينما تعمل المهام المتكررة الرخيصة عند minimal، دون المساس بافتراضيك العام.

      تحذير

      جلسات تشغيل cron لا يمكنها إنشاء مزيد من مهام cron بشكل تكراري. يعطّل Hermes أدوات إدارة cron داخل تنفيذات cron لمنع حلقات جدولة متسلسلة بلا توقف.

      إنشاء مهام مجدولة​

      في المحادثة باستخدام /cron​

      /cron add "in 30m" "Remind me to check the build"
      /cron add "every 2h" "Check server status"
      /cron add "every 1h" "Summarize new feed items" --skill blogwatcher
      /cron add "every 1h" "Use both skills and combine the result" --skill blogwatcher --skill maps

      من الـ CLI المستقل​

      hermes cron create "every 2h" "Check server status"
      hermes cron create "every 1h" "Summarize new feed items" --skill blogwatcher
      hermes cron create "every 1h" "Use both skills and combine the result" \
        --skill blogwatcher \
        --skill maps \
        --name "Skill combo"

      عبر محادثة طبيعية​

      اطلب من Hermes بشكل عادي:

      Every morning at 9am, check Hacker News for AI news and send me a summary on Telegram.

      سيستخدم Hermes أداة cronjob الموحَّدة داخليًا.

      التحقق من الإعداد قبل الإرسال​

      قبل بناء أي آلية وكيل لتشغيل مجدوَل، يتحقق المجدوِل من أن إعداد المهمة يستطيع فعلًا إنتاج تشغيل ناجح:

      • يُحلّ مفتاح API الخاص بالمزوّد (يُتخطى عند إعداد سلسلة fallback_providers، لأن مسار الاحتياط قد ينقذ مفتاحًا أساسيًا مفقودًا)،
      • المهارات المرفقة جاهزة (لا متغيرات بيئة، أو أوامر، أو ملفات بيانات اعتماد مطلوبة مفقودة)،
      • أهداف منصة التسليم معروفة ولها بيانات اعتماد gateway مُعدَّة (أهداف local/origin لا تُفحَص أبدًا).

      عندما يفشل التحقق، تصبح last_status الخاصة بالمهمة blocked_config، ويُسلَّم تنبيه واحد (لا يتكرر كل نبضة)، ولا يُجرى أي استدعاء LLM — مهمة سيئة الإعداد لا تنفق tokens أبدًا. أول تشغيل سليم يمسح الحالة المحظورة بحيث ينبّه عطل إعداد مستقبلي مجددًا.

      لتعطيل التحقق واستعادة السلوك القديم (يستمر التشغيل ويفشل أثناء التنفيذ):

      cron:
        preflight: false

      أو: hermes config set cron.preflight false

      نقل المهام غير المثبَّتة إلى افتراضي عام جديد​

      تبقى المهمة غير المثبَّتة على المزوّد/النموذج الذي أُنشئت تحته، فتغيير نموذج محادثتك لا يغيّر أسطول cron الخاص بك (ولا يوقفه) أبدًا. عندما تريد فعلًا نقل المهام المجدولة:

      hermes cron edit <job_id> --provider <provider> --model <model>   # one job
      hermes config set cron.model <model>                               # every unpinned job

      يعرض hermes config set model.default … وقائمة اختيار النموذج في Desktop المهام غير المثبَّتة التي ستحتفظ بنموذجها الأصلي بحيث تقرّر عن وعي. تُحدَّث اللقطات المخزَّنة كلما حرّرت مزوّد مهمة، أو نموذجها، أو رابط قاعدتها الأساسي.

      إعادة اللقطة (resnapping) تحدّث اللقطة المخزَّنة لمهمة غير مثبَّتة إلى الحل العام الحالي دون تثبيتها، بحيث تظل تتبع التغييرات المستقبلية:

      hermes cron resnap <job_id>   # one job
      hermes cron resnap --all      # every unpinned agent job

      تقبل أداة cronjob الخاصة بالوكيل نفس الفعل (action=resnap job_id=<id> أو action=resnap all=true). المحاور المثبَّتة ومهام السكربت no_agent تُترَك دون تعديل.

      مهام cron المدعومة بمهارات​

      يمكن لمهمة cron تحميل مهارة واحدة أو أكثر قبل تشغيل الـ prompt.

      مهارة واحدة​

      cronjob(
          action="create",
          skill="blogwatcher",
          prompt="Check the configured feeds and summarize anything new.",
          schedule="0 9 * * *",
          name="Morning feeds",
      )

      مهارات متعددة​

      تُحمَّل المهارات بالترتيب. يصبح الـ prompt تعليمة المهمة المُضافة فوق تلك المهارات.

      cronjob(
          action="create",
          skills=["blogwatcher", "maps"],
          prompt="Look for new local events and interesting nearby places, then combine them into one short brief.",
          schedule="every 6h",
          name="Local brief",
      )

      هذا مفيد عندما تريد لوكيل مجدوَل أن يرث سير عمل قابل لإعادة الاستخدام دون حشو نص المهارة الكامل في prompt الـ cron نفسه.

      تشغيل مهمة داخل مجلد مشروع​

      مهام cron تعمل افتراضيًا منفصلة عن أي مستودع — لا يُحمَّل AGENTS.md، ولا CLAUDE.md، ولا .cursorrules، وتعمل أدوات terminal / الملفات / تنفيذ الكود من أي مجلد عمل بدأ فيه gateway. مرّر --workdir (في CLI) أو workdir= (في استدعاء الأداة) لتغيير ذلك:

      # Standalone CLI (schedule and prompt are positional)
      hermes cron create "every 1d at 09:00" \
        "Audit open PRs, summarize CI health, and post to #eng" \
        --workdir /home/me/projects/acme
      # From a chat, via the cronjob tool
      cronjob(
          action="create",
          schedule="every 1d at 09:00",
          workdir="/home/me/projects/acme",
          prompt="Audit open PRs, summarize CI health, and post to #eng",
      )

      عند ضبط workdir:

      • AGENTS.md، وCLAUDE.md، و.cursorrules من ذلك المجلد تُحقَن في الـ system prompt (بنفس ترتيب الاكتشاف المستخدَم في CLI التفاعلي)
      • terminal، وread_file، وwrite_file، وpatch، وsearch_files، وexecute_code تستخدم جميعها ذلك المجلد كمجلد عملها
      • يجب أن يكون المسار مجلدًا مطلقًا موجودًا فعلًا — تُرفَض المسارات النسبية والمجلدات المفقودة عند الإنشاء / التحديث
      • مرّر --workdir "" (أو workdir="" عبر الأداة) عند التحرير لمسحه واستعادة السلوك القديم
      العزل

      كل تشغيل وكيل يربط workdir بهوية مهمة ذلك التشغيل الفريدة. لذا تستخدم مهام workdir التجمّع المتوازي العادي دون تعديل حالة الطرفية العامة للعملية أو تسريب مسارات بين تشغيلات متزامنة. اضبط cron.max_parallel_jobs إذا أردت تقييد إجمالي تزامن cron.

      تحرير المهام​

      لست بحاجة لحذف المهام وإعادة إنشائها فقط لتغييرها.

      مرجع المهمة

      يقبل العنصر النائب <job_id> أدناه (وفي إجراءات دورة الحياة) أيضًا اسم المهمة (بغضّ النظر عن حالة الأحرف) — مفيد عندما تتذكّر morning-digest لكن ليس المعرّف السداسي عشري. معرّف مهمة دقيق يسبق تطابقات الأسماء في الأولوية؛ إذا لم يكن المرجع معرّفًا وطابق اسم أكثر من مهمة، يرفض الأمر ويطبع المعرّفات المرشَّحة لتتمكن من التمييز.

      المحادثة​

      /cron edit <job_id> --schedule "every 4h"
      /cron edit <job_id> --prompt "Use the revised task"
      /cron edit <job_id> --skill blogwatcher --skill maps
      /cron edit <job_id> --remove-skill blogwatcher
      /cron edit <job_id> --clear-skills

      الـ CLI المستقل​

      hermes cron edit <job_id> --schedule "every 4h"
      hermes cron edit <job_id> --prompt "Use the revised task"
      hermes cron edit <job_id> --skill blogwatcher --skill maps
      hermes cron edit <job_id> --add-skill maps
      hermes cron edit <job_id> --remove-skill blogwatcher
      hermes cron edit <job_id> --clear-skills

      ملاحظات:

      • تكرار --skill يستبدل قائمة المهارات المرفقة بالمهمة
      • --add-skill يُلحِق بالقائمة الحالية دون استبدالها
      • --remove-skill يزيل مهارات مرفقة محددة
      • --clear-skills يزيل كل المهارات المرفقة

      إجراءات دورة الحياة​

      مهام cron لديها الآن دورة حياة أكمل من مجرد الإنشاء/الإزالة.

      المحادثة​

      /cron list
      /cron pause <job_id>
      /cron resume <job_id>
      /cron run <job_id>
      /cron remove <job_id>

      الـ CLI المستقل​

      hermes cron list
      hermes cron pause <job_id_or_name>
      hermes cron resume <job_id_or_name>
      hermes cron run <job_id_or_name>
      hermes cron remove <job_id_or_name>
      hermes cron edit <job_id_or_name> [...flags]
      hermes cron status
      hermes cron tick

      ما تفعله:

      • pause — إبقاء المهمة مع وقف جدولتها
      • resume — إعادة تفعيل المهمة وحساب التشغيل المستقبلي التالي
      • run — تشغيل المهمة في نبضة المجدوِل التالية
      • remove — حذفها بالكامل
      • edit — تعديل الجدول، أو الـ prompt، أو التسليم، إلخ

      البحث بالاسم. الأفعال الأربعة المُغيِّرة (pause، وresume، وrun، وremove، وedit) بالإضافة إلى أداة cronjob الخاصة بالوكيل، جميعها تقبل الآن اسم المهمة (بغضّ النظر عن حالة الأحرف) بدلًا من المعرّف السداسي عشري. يفضّل الوكيل وCLI كلاهما تطابقًا دقيقًا للمعرّف إن وُجد؛ تطابقات الأسماء الغامضة (عدة مهام تشترك في نفس الاسم) تُرفَض مع قائمة كاملة بالمعرّفات المرشَّحة لتتمكن من الاختيار صراحةً. الأسماء غير فريدة، لذا هذا الضمان جوهري — يمنع تعديل المهمة الخطأ بصمت عندما تشترك مهمتان في نفس الاسم.

      إنشاء مهمة موقوفة (اختبار canary آمن)​

      أنشئ مهمة canary دون سباق جدولة إنشاء-ثم-إيقاف:

      hermes cron create "every 1h" "Post the digest" --paused --paused-reason "Awaiting review"
      hermes cron resume <job_id>

      --paused يخزّن enabled: false، وstate: paused، وnext_run_at: null، وطابعًا زمنيًا للإيقاف وسببًا قابلًا للتدقيق في أول كتابة مقفَلة، دون تسجيل مشغِّل. أغفل السبب لتخزين "Created paused; awaiting operator approval." أغفل --paused للاحتفاظ بالإنشاء المفعَّل العادي. --paused-reason يتطلب --paused؛ تُرفَض القيم غير الصالحة قبل الحفظ.

      نفس المنطق المنطقي paused والنص الاختياري paused_reason مقبولان من cron.jobs.create_job، وفعل create في أداة إدارة cron، وواجهة gateway POST /api/jobs، ولوحة التحكم POST /api/cron/jobs. يجدول الاستئناف التشغيل المستقبلي التالي. الإيقاف يمنع الإطلاق التلقائي، لا تجاوزات المشغّل: يبقى سلوك التشغيل الآن الصريح / التشغيل القسري السابق متاحًا ويمكنه استئناف المهمة وتشغيلها. ليس حدًا أمنيًا ضد مشغّل يستطيع تشغيل المهام.

      الجدولة المُدارة بالوكيل (مهام cron تدير مهام cron)​

      افتراضيًا، الوكلاء المُطلَقون عبر المجدوِل لا يستطيعون استخدام أداة cronjob — لا يمكن لمهمة مجدولة إنشاء، أو تحرير، أو إزالة مهام أخرى. فعّلها اختياريًا عبر config.yaml:

      cron:
        allow_agent_scheduling: true   # default: false

      عند التفعيل، يمكن لوكيل مجدوَل إدارة جدول cron مثل أي جلسة محادثة: جدولة مهام تالية لمرة واحدة من داخل عمل مجدوَل، أو ضبط وتيرته الخاصة، أو تشغيل مهمة "أمين مكتبة cron" تراجع الجدول بأكمله (سرد، ثم تحديث/إزالة/إنشاء حسب الحاجة). خاصيتان تبقيان هذا معقولًا:

      • جدول واحد مسطَّح، مملوك للمستخدم. المهام المُنشأة من تشغيل cron تحطّ في نفس jobs.json مع كل مهمة أخرى دون ملكية خاصة — يمكنك سردها، أو تحريرها، أو إزالتها تمامًا كما لو أنشأتها بنفسك.
      • لا تسليم معلَّق. تشغيل cron عابر، لذا deliver: origin من داخل واحد يُحلّ عند وقت الإنشاء إلى هدف المهمة المُنشِئة الفعلي (platform:chat_id[:thread_id]، أو local إذا كانت المهمة المُنشِئة لا تسلّم إلى أي مكان). المهمة المُنشأة من قِبل وكيل مجدوَل لا يمكنها أبدًا توجيه مخرجها إلى جلسة لم تعد موجودة. الأهداف الصريحة (local، all، telegram:<chat_id>) تُحترَم حرفيًا.

      فضّل الـ prompts التي تحدّث مهامًا موجودة (سرد أولًا، ثم تحديث بالمعرّف) على تلك التي تُنشئ مهامًا جديدة في كل تشغيل.

      كيف يعمل​

      تنفيذ cron يتولاه daemon الـ gateway. ينبض gateway المجدوِل كل 60 ثانية، ويشغّل أي مهام مستحقة في جلسات وكيل معزولة.

      hermes gateway install     # Install as a user service
      sudo hermes gateway install --system   # Linux: boot-time system service for servers
      hermes gateway             # Or run in foreground

      hermes cron list
      hermes cron status

      سلوك مجدوِل gateway​

      في كل نبضة يقوم Hermes بما يلي:

      1. تحميل المهام من ~/.hermes/cron/jobs.json
      2. فحص next_run_at مقابل الوقت الحالي
      3. بدء جلسة AIAgent جديدة لكل مهمة مستحقة
      4. حقن مهارة واحدة أو أكثر مرفَقة في تلك الجلسة الجديدة، اختياريًا
      5. تشغيل الـ prompt حتى الاكتمال
      6. تسليم الرد النهائي
      7. تحديث بيانات التشغيل الوصفية والوقت المجدوَل التالي

      قفل ملف عند ~/.hermes/cron/.tick.lock يمنع نبضات المجدوِل المتداخلة من تشغيل نفس دفعة المهام مرتين.

      عمّال آمنون عند إعادة التشغيل تحت systemd​

      عندما يعمل gateway كخدمة systemd، تُسلَّم كل مهمة مستحقة إلى عملية عامل خارجية تُطلَق في نطاق مستخدم عابر (systemd-run --user --scope)، بحيث لا تؤدي إعادة تشغيل gateway وسط مهمة إلى قتلها. إنشاء ذلك النطاق يحتاج جلسة systemd للمستخدم؛ المضيفات التي تفتقر إليها (الحاويات، LXCs الصغرى، مستخدم خدمة دون linger) لا يمكنها توفيرها.

      افتراضيًا يتدهور cron عندئذٍ: تظل المهمة تعمل كعملية خارجية منفصلة بنفس تسليم التنفيذ، لكن دون عزل cgroup، بحيث تؤدي إعادة تشغيل gateway أثناء المهمة إلى قتلها (يسجّل دفتر التنفيذ ذلك). يُسجَّل تحذير واحد لكل عملية gateway. للفشل بأمان بدلًا من ذلك — تخطّي المهمة وتسجيل الخطأ في صف المهمة — اضبط:

      cron:
        require_restart_safe_scope: true

      الحل الدائم هو جلسة مستخدم لمستخدم gateway: sudo loginctl enable-linger <gateway-user> (وXDG_RUNTIME_DIR / DBUS_SESSION_BUS_ADDRESS في الوحدة للتثبيتات على مستوى النظام)، ثم إعادة تشغيل gateway. عمّال Kanban يتطلبون دائمًا نطاقًا ويفشلون بأمان بغضّ النظر عن هذا المفتاح.

      سجل التنفيذ​

      يسجّل Hermes كل محاولة cron مطالَب بها في قاعدة البيانات المحلية للملف الشخصي ~/.hermes/cron/executions.db قبل الإرسال إلى المنفِّذ أو المزوّد. تنتقل المحاولات عبر claimed، ثم running، ثم حالة نهائية واحدة غير قابلة للتغيير: completed، أو failed، أو unknown. بعد إعادة التشغيل، يعلِّم Hermes محاولة مهجورة بـ unknown فقط عندما يثبت PID الأصلي وبصمة بدء العملية أن مالكها قد اختفى. المحاولات غير المعروفة هي سجلات تدقيق ولا تُعاد تلقائيًا أبدًا.

      افحص المحاولات الأخيرة بـ hermes cron runs [job-id] --limit 20 (اسم بديل: history). سجل التاريخ النهائي محدود؛ المحاولات النشطة لا تُقلَّم أبدًا. يُدرَج الدفتر ضمن النسخ الاحتياطية السريعة.

      المحاولات المجدولة تسجّل أيضًا لحظتها المجدولة الدقيقة، منفصلة عن الوقت الذي طُولِبَ بها فيه. إذا أعادت لقطة قديمة من jobs.json تسليح حدوث سجّله الدفتر المحفوظ بأنه مكتمل، يتخطى Hermes تلك الإعادة ويعيد تثبيت مرجعية المهام المتكررة. يعمل هذا حتى عندما تسبق اللقطة طابع الإرسال أو عندما بدأ التشغيل الأصلي متأخرًا. التشغيلات اليدوية الصريحة لا تستهلك هوية حدوث مجدوَل.

      هذا ليس ضمانًا لتأثير جانبي يحدث مرة واحدة بالضبط: الصفوف القديمة دون هوية، والسجل المُقلَّم، والدفاتر غير المتاحة، والمحاولات المقطوعة لا يمكنها إثبات الاكتمال. استعادة الدفتر نفسه إلى نسخة احتياطية أقدم تزيل أيضًا ذلك الدليل. استدعاءات الإطلاق الخارجية تُعرِّف مطالبة المخزن المقبولة حاليًا، وليس فتحة مجدولة من مصدر أعلى غائبة عن الاستدعاء.

      تنبيه مراجعة عند الفشل المتكرر​

      تتبّع كل مهمة failure_streak — تشغيلات فاشلة متتالية (إخفاقات التسليم لا تُحسَب). تشغيل يفشل قبل الوصول إلى الوكيل أصلًا — استيراد فاسد بعد تحديث نصف مُطبَّق، أو عميل مزوّد يتعذّر إنشاؤه — يُحسَب وينبّه تمامًا كما لو فشله الوكيل نفسه. عندما يصل تتابع مهمة متكررة إلى العتبة، تكتسب رسالة الفشل المُسلَّمة إلى المحادثة تنبيه مراجعة يخبرك أن المهمة فشلت N تشغيل على التوالي ويقترح أن تُصلحها، أو توقفها (hermes cron pause <job>)، أو تزيلها. أي تشغيل ناجح يعيد تعيين التتابع، ويعرض hermes cron list التتابع بجانب آخر تشغيل لمهمة فاشلة. المهام لمرة واحدة لا تنبّه أبدًا.

      cron:
        failure_nudge_threshold: 3   # default; 0 disables the nudge

      إعادة تشغيل تلقائية عندما يتعذّر الوصول إلى النموذج​

      مهمة متكررة يفشل تشغيلها بخطأ شبكة أو DNS عابر قبل إجراء أي استدعاء نموذج واحد — الحالة الكلاسيكية هي إطلاق فور استيقاظ الحاسوب، بينما لا تزال VPN أو Wi-Fi تعيد الاتصال — لا تفوّت فترة كاملة. يعيد المجدوِل تشغيلها تلقائيًا بعد 5، و15، و 30 دقيقة (مستوحى من إعادة التشغيل للمهام المجدولة في Claude Cowork)، ثم يعود إلى الجدول العادي. لأنه لم تُجرَ أي استدعاءات API، فإن إعادة التشغيل محايدة من حيث الإنفاق ولا يمكنها تكرار أي تأثير جانبي.

      أثناء انتظار إعادة تشغيل، يُخفى إشعار الفشل المؤقت — تحصل على النتيجة الحقيقية عند نجاح إعادة التشغيل، أو تنبيه فشل عادي بمجرد استنفاد السلّم. أي تشغيل يصل إلى النموذج (نجاحًا أو فشلًا) يعيد تعيين السلّم. المهام لمرة واحدة مستثناة: محاسبة إرسالها هي على الأكثر مرة واحدة، وإرسال مُستهلَك لا يُبعَث أبدًا. لا تُطلَق إعادة المحاولات أبدًا بعد الحدوث المستقبلي التالي للجدول نفسه إذا جاء أقرب.

      cron:
        retry_unreachable: false   # default true; disables the automatic re-runs

      حوادث الفشل: الإقرار بفشل معروف​

      مهمة متكررة تستمر بالفشل بـنفس الخطأ تنبّهك في كل تشغيل. كل فشل يُسجَّل أيضًا كـ حادثة دائمة، مفتاحها المهمة بالإضافة إلى توقيع مُوحَّد لنص الخطأ، في نفس دفتر لكل ملف شخصي المستخدَم لسجل التنفيذ.

      hermes cron incidents                 # list incidents (newest activity first)
      hermes cron incidents --state alerted # filter: detected | alerted | closed
      hermes cron incidents ack <id>        # acknowledge — stop re-pinging

      الإقرار بحادثة يُسكِت تنبيه الفشل لكل تشغيل لذلك التوقيع المحدد فقط. لا شيء آخر يتغيّر: سجل التشغيل ما يزال يسجّل كل فشل، ويستمر تتابع الفشل بالعدّ، وفي اللحظة التي تبدأ فيها المهمة بالفشل بخطأ مختلف تُصكّ حادثة جديدة وتُطلَق التنبيهات مجددًا. تشغيل ناجح لا يمسّ الحوادث — فهي لكل توقيع، لا لكل مهمة.

      دورة حياة الحادثة: detected (سُجِّل فشل) ← alerted (وصل تنبيه فشل واحد على الأقل إلى التسليم) ← closed (أُقرَّ به؛ نهائي لذلك التوقيع). نص الخطأ المخزَّن منقَّح من الأسرار ومقتطَع قبل كتابته.

      التسجيل مفعَّل دائمًا ولا يكلّف شيئًا تجاهله — لا يُكبَت أي تنبيه أبدًا حتى تقرّه صراحةً (ack).

      فحص صحة الأسطول: hermes cron doctor​

      hermes cron doctor هو فحص صحة للقراءة فقط عبر كل مهمة نشطة. يطبع مشكلات مجمَّعة لكل مهمة ويخرج بالرمز 1 عند وجود أي شيء قابل للتصرف (0 عند السلامة)، لذا يعمل من طرفية، أو سكربت مراقبة، أو فحص سريع بأسلوب CI:

      hermes cron doctor

      الفحوصات لكل مهمة نشطة:

      • فشل آخر تشغيل (last_status ليس سليمًا، مع الخطأ المسجَّل)،
      • فشل آخر تسليم (أُنتِج المخرج لكنه لم يصلك أبدًا)،
      • next_run_at مفقود، أو محشور في الماضي متجاوزًا هامش تسامح 15 دقيقة للمُنبِّه — إشارة "المهمة لا تُطلَق بصمت" (المجدوِل معطَّل، أو gateway متوقف، أو مطالبة إطلاق متعطِّلة)،
      • السكربت مفقود، أو ليس ملفًا، أو يُحلّ خارج HERMES_HOME/scripts،
      • مهمة no_agent دون سكربت،
      • workdir مُعدّ لم يعد موجودًا.

      الفحص لا يعدِّل المهام أو الحالة أبدًا — يقتصر على الإبلاغ فقط. اقرنه مع hermes cron incidents (سجلات فشل دائمة) وhermes cron runs (دفتر المحاولات) عند التعمّق في مهمة موسومة.

      إخفاقات التسليم حالة مستقلة​

      يُتتبَّع التنفيذ والتسليم بشكل منفصل. عندما ينجح تشغيل الوكيل لكن المخرجات لا تصل إلى الهدف (خطأ 5xx من المنصة، حدّ المعدل، جلسة قديمة، لم يُقدّم adapter أي دليل إيجابي على الإرسال)، تسجّل المهمة last_status: delivery_failed — وليس ok بسيطة أبدًا — مع السبب في last_delivery_error. يعرضها hermes cron list باللون الأصفر بصيغة delivery_failed: <reason>، ويُبلغ عنها hermes cron doctor كمشكلة تسليم، ويُبلغ تشغيل cronjob run اليدوي عن success: false مع خطأ التسليم. لا يُحتسب إخفاق التسليم ضمن failure_streak الخاص بالمهمة (فالوكيل أدّى مهمته)؛ ويُعيد التشغيل الناجح التالي بالكامل الحالة إلى ok.

      تسليم Bot Chat (bot-chat)​

      يسلّم bot-chat المخرجات إلى جلسة "Bot Chat" القانونية الخاصة بـ profile كرسالة حقيقية. وخلافًا لكل هدف آخر — حيث يكون المستلم إنسانًا يقرأ قناة — فالمستلم هنا هو البوت نفسه: يتلقّى المخرجات كرسالة واردة، ويتصرف بناءً على أي شيء يستلزم فعلاً، ويردّ في محادثته. استخدمه عندما يجب معالجة المخرجات المجدولة لا مجرد نشرها.

      • bot-chat (مجردة) تستهدف الـ profile الخاص بالمهمة نفسها.
      • bot-chat:<profile> تستهدف profile آخر على نفس الجهاز. تُتحقق الأسماء مقابل hermes profile list عند إنشاء المهمة؛ لا يمكن أبدًا استهداف profiles على gateways أو أجهزة أخرى، لذا تكون الـ profiles المتماثلة الاسم عبر الأجهزة غير ملتبسة.
      • يكلّف كل تسليم البوتَ الهدف دورة وكيل كاملة — انتبه لتكرار الجدولة.
      • يمكن دمجه مع أهداف أخرى (bot-chat,telegram) لكنه لا يُدرَج أبدًا ضمن all.
      • إذا كانت المحادثة القانونية مفتوحة في terminal backend يدعم mailbox في Desktop/TUI، يُصفّ التسليم بشكل دائم فورًا، سواء كان البوت خاملًا أو مشغولًا. فقط ذلك المالك الحي يُشغّل الدور الوارد؛ لا يبدأ cron كاتب CLI منافس. بدون مالك mailbox حي، يبقى مسار hermes chat -c "Bot Chat" --create-if-missing الحالي متاحًا (تظل فحوصات ملكية الجلسة العادية سارية).
      • الاصطفاف ليس اكتمالًا. يسجّل cron معرّفات الاستلام وحالات queued/claimed في last_delivery_queued، مع نتيجة تسليم queued (لا مُسلَّمة ولا فاشلة). تُظهر المهمة الناجحة delivery_queued؛ لا تزال الأخطاء الحقيقية في الأهداف الأخرى لها الأولوية كإخفاقات تسليم. قد يكمل البوت لاحقًا. الإيصال الدائم في runtime/bot_live_delivery/<receipt-id>.json الخاص بـ profile الهدف هو المرجع الموثوق؛ لا تُحدَّث حالة cron التاريخية تلقائيًا.
      • إعادة فحص نفس التنفيذ يفحص إيصاله الموجود، حتى لو اختفى المالك. لا يعود أبدًا إلى كاتب آخر بعد القبول. لا تُعاد محاولة إيصالات failed أو cancelled أو ambiguous تلقائيًا؛ افحص المحادثة والإيصال قبل بدء عمل جديد عن قصد. لكل تنفيذ cron جديد معرّف تسليم مستقل.

      نيّة التوجيه (all)​

      تتيح لك all إرسال مهمة cron واحدة إلى كل قناة مراسلة أعددتها، دون الحاجة إلى سردها بالاسم. تُحلّ عند وقت الإطلاق، لذا فإن مهمة أُنشئت قبل ربط Telegram ستلتقط Telegram في الدورة التالية بعد ضبط TELEGRAM_HOME_CHANNEL.

      الدلالة: تتوسّع all إلى كل منصة لها قناة رئيسية مُعدّة. الصفر مقبول؛ تُنتج المهمة ببساطة صفر أهداف تسليم وتُسجَّل كإخفاق تسليم في مرحلة سابقة.

      تُدمَج all مع الأهداف الصريحة. تُسلِّم origin,all إلى محادثة المصدر بالإضافة إلى كل قناة رئيسية أخرى متصلة، مع إزالة التكرار حسب (platform, chat_id, thread_id).

      موضوع cron في Telegram (TELEGRAM_CRON_THREAD_ID)​

      عندما يكون وضع المواضيع في Telegram مفعّلًا، تُحجَز محادثة الـ DM الجذرية كردهة نظام — تُرفَض الردود المرسلة إليها بتذكير بالردهة، ويُسقَط reply_to_message_id، لذا لا يمكنك الرد على رسالة cron التي وصلت إلى المحادثة الرئيسية.

      وجّه cron بدلًا من ذلك إلى موضوع منتدى مخصّص:

      1. في Telegram، افتح الـ DM الخاص بالبوت وأنشئ موضوعًا باسم مثل Cron. اضغط مطوّلًا على رأس الموضوع ← Copy link؛ العدد الصحيح الأخير هو message_thread_id الخاص بالموضوع.
      2. اضبط TELEGRAM_CRON_THREAD_ID=<that id> في ملف .env الخاص بك.

      ينطبق هذا فقط على تسليمات cron. متغير TELEGRAM_HOME_CHANNEL_THREAD_ID (المستخدم في مواضع أخرى، مثل إشعارات إعادة التشغيل) يبقى دون تغيير. أهداف deliver="telegram:chat_id:thread_id" الصريحة تستمر في التغلّب على متغير البيئة. تصل الآن الردود على رسائل cron في جلسة الموضوع الموجودة، فيمكنك التعامل معها مباشرة.

      تغليف الردّ​

      افتراضيًا، تُغلَّف مخرجات cron المُسلَّمة برأس وتذييل ليعرف المستلم أنها وصلت من مهمة مجدولة:

      Cronjob Response: Morning feeds
      -------------

      <agent output here>

      Note: The agent cannot see this message, and therefore cannot respond to it.

      لتسليم مخرجات الوكيل الخام بدون الغلاف، اضبط cron.wrap_response على false:

      # ~/.hermes/config.yaml
      cron:
        wrap_response: false

      الإشعارات الفورية (cron.delivery.notify)​

      مخرجات cron هي تسليم نهائي، لا رسالة تقدّم، لذا فهي تُرسَل افتراضيًا مع تفعيل علامة الإشعار الخاصة بالمنصة — على Telegram يعني هذا أن الملخّص المختصر يُطلق إشعارًا فوريًا حتى عندما يكون وضع إشعارات الـ adapter important (الذي يرسل بخلاف ذلك مع disable_notification=true، ويُبلغ المستخدمون أن الملخّص الصامت "لم يصل أبدًا"). لاستعادة التسليمات الصامتة:

      # ~/.hermes/config.yaml
      cron:
        delivery:
          notify: false   # default: true

      تنطبق هذه العلامة على كل من إرسال النص وأي مرفقات وسائط، لذا لا يُطلق التشغيل إشعارًا لأحدهما ويبقى صامتًا للآخر.

      تأكيد التسليم وحالة UNVERIFIED​

      يُسجَّل تسليم عبر adapter حي كمُسلَّم فقط استنادًا إلى دليل إيجابي من الـ adapter: نجاح success صريح ليس إسقاطًا مُصفّى (delivered: false)، بالإضافة إلى message_id أو raw_response. تُقبَل نتيجة تحمل success بدون أي من هذين الدليلين — وهو الشكل الذي تُعيده adapters Slack وMatrix وMattermost — (فذلك ليس دليلًا على الفشل)، لكن يُسجَّل التشغيل على المهمة كـ last_delivery_unverified ويظهر في hermes cron list:

      ⚠ Delivery UNVERIFIED: adapter acked slack:C0123456 without message_id/raw_response

      وفي hermes cron doctor كـ last delivery unverified (...). يُزال هذا المؤشر عند التشغيل التالي الذي يُسلِّم بدليل. لا يُسلَّم أبدًا حِمل فارغ (بلا نص ولا وسائط) إلى أي adapter؛ بل يفشل بأمان ويُبلَّغ عنه في last_delivery_error بدلًا من تسجيله كمُسلَّم.

      المهام القابلة للمتابعة (الردّ على تسليم cron)​

      افتراضيًا، تسليم cron هو إرسال دون متابعة: تُرسَل الرسالة، لكنها لا تعيش في سجلّ محادثة المحادثة، فإن رددت عليها لا يكون لدى الوكيل سجلّ لما قاله. اضبط مهمة على أنها قابلة للمتابعة ويصبح الملخّص المُسلَّم محادثة يمكنك الرد عليها — يكون الملخّص في سياق الوكيل بدلًا من أن يسأل "ما هي المهمة رقم 2؟".

      اختياري، ومعطّل افتراضيًا. فعّله عالميًا في الإعدادات، أو لكل مهمة عبر أداة cronjob وحقلها attach_to_session (الذي يتجاوز الإعداد العام لتلك المهمة وحدها):

      # ~/.hermes/config.yaml
      cron:
        mirror_delivery: false   # set true to make cron deliveries continuable

      السلوك يفضّل المواضيع (thread-preferred)، ومحصور في محادثة المهمة نفسها:

      • المنصات القادرة على المواضيع (مواضيع Telegram، مواضيع Discord/Slack): يفتح كل تسليم موضوعه الخاص المخصّص ويُبذَر الملخّص في جلسة ذلك الموضوع، فيتابع الرد ضمن الموضوع بالسياق الكامل. تفتح مهمة متكررة (مثل ملخّص يومي) موضوعًا جديدًا لكل تشغيل، ما يحافظ على عزل نقاش المتابعة لكل تسليم.
      • المنصات القاصرة على DM (WhatsApp، Signal، SMS): لا وجود لمواضيع، لذا يُنسَخ الملخّص إلى جلسة الـ DM الهدف بدلًا من ذلك (الـ DM الأصلي، أو الـ DM الرئيسي للأهداف الاحتياطية والمهام ذات المنصة المجردة) — يكون الـ DM نفسه سطح المتابعة.

      لا تُلمَس سوى محادثة المهمة الخاصة بها أبدًا:

      • محادثة المصدر التي أُنشئت المهمة فيها؛
      • القناة الرئيسية الاحتياطية عندما لا يلتقط deliver: origin أي مصدر (مهام أُنشئت بواسطة سكربتات أو الـ API لا من محادثة gateway حيّة) — إذ تقوم محادثة المستخدم الرئيسية مقام المصدر؛
      • هدف platform:chat صريح ووحيد للمهمة، لكن فقط عندما تختار المهمة نفسها ذلك بـ attach_to_session: true — يُصرّح مؤلف المهمة بأن ذلك الهدف محادثة. لا تجعل علامة mirror_delivery العامة وحدها محادثة مُخاطَبة صراحة قابلة للمتابعة أبدًا.

      لا تُجعَل توسّعات البث (all) قابلة للمتابعة أبدًا. اسم منصة مجرد كتبه المستخدم (deliver: slack) يخاطب القناة الرئيسية لتلك المنصة عن قصد ويتبع نفس قواعد القناة الرئيسية الاحتياطية أعلاه. بعد الترقية، يمكن لمهام deliver: <platform> الموجودة والتي تحمل cron.mirror_delivery: true فتح موضوع جديد لكل تشغيل على المنصات القادرة على المواضيع. اضبط attach_to_session: false على مهمة للانسحاب من سلوك الموضوع-لكل-تشغيل هذا.

      تُكتَب المرآة كدور مستخدم موسوم ([Cron delivery: <task name>])، ما يحافظ على تناوب سجلّ المحادثة آمنًا عبر كل مزوّدي النماذج.

      المتابعة المسطّحة داخل القناة (Slack)​

      يسكّ السلوك المفضّل للمواضيع أعلاه موضوعًا مخصّصًا في كل تسليم. إن أردت أن تصل مهمة قابلة للمتابعة مسطّحة في الجدول الزمني للقناة — بلا موضوع — اضبط سطح المتابعة الخاص بـ Slack على in_channel:

      # ~/.hermes/config.yaml
      slack:
        cron_continuable_surface: in_channel   # default: thread
        reply_in_thread: false                 # required pairing (see below)
        require_mention: false                 # so a plain reply continues the job

      في وضع in_channel يُسلَّم الملخّص كرسالة عادية على المستوى الأعلى في القناة (لا يُفتَح أي موضوع)، ويتابع ردّك المهمة عبر الجلسة المشتركة للقناة. تعمل ثلاثة إعدادات معًا:

      • cron_continuable_surface: in_channel — يتخطّى إنشاء الموضوع عند التسليم.
      • reply_in_thread: false (مطلوب) — يجعل البوت يجيب على ردّك مسطّحًا في القناة ويربطه بنفس جلسة القناة الكاملة التي بُذر فيها الملخّص. بدونه تظل المتابعة تعمل لكنها تصل في موضوع (يعود بأمان إلى متابعة على نمط الموضوع، دون أن يفقد أي رد أبدًا — يسجّل الـ gateway تحذيرًا عند بدء التشغيل حتى تكتشف عدم التطابق).
      • require_mention: false (أو أضف القناة إلى free_response_channels) — حتى تتمكن من الرد برسالة عادية؛ وإلا لا يستيقظ البوت إلا عندما تذكره بـ @ في كل رد.

      بما أن المتابعة هي جلسة القناة كاملة، فهي مشتركة: أحاديث أخرى في القناة — ومهمة قابلة للمتابعة ثانية داخل القناة — تنضم إلى نفس المحادثة المتدحرجة. هذا متأصل في "التسطيح داخل قناة" وهو نفس المقايضة التي يتقبّلها مستخدمو reply_in_thread: false فعلًا؛ استخدم سطح thread الافتراضي عندما تريد عزل متابعة كل تسليم.

      هذه قدرة خاصة بـ Slack حاليًا. تقبل المنصات الأخرى المفتاح لكنها تعود إلى سطح thread (تختلف بدائيات المتابعة لديها)؛ يُضبط الاختيار لكل منصة على حدة، ضمن إعدادات كل منصة. إنها علامة إعداد من جانب الـ gateway — يلتقطها /restart؛ لا حاجة لإعادة تثبيت تطبيق Slack.

      محادثات 1:1 المباشرة

      cron_continuable_surface إعداد على مستوى القناة — لا يوجد في محادثة DM فردية انقسام موضوع-مقابل-جدول زمني يُختار بينهما (فالـ DM مسطّح أصلًا)، لذا لا أثر للمفتاح هناك. ما يحكم كون تسليم cron في DM قابلًا للمتابعة هو الإعداد المنفصل والموجود مسبقًا slack.dm_top_level_threads_as_sessions:

      • false — تشترك كل رسائل DM على المستوى الأعلى في جلسة DM متدحرجة واحدة، فيصل ملخّص cron قابل للمتابعة وردّك إلى نفس الجلسة وتستمر المهمة في السياق. هذا ما تريده لـ cron قابل للمتابعة في DM.
      • true (الافتراضي) — كل رسالة DM على المستوى الأعلى هي جلستها الخاصة، فيبدأ الرد على ملخّص مُسلَّم جلسة جديدة لا سجلّ فيها للملخّص. لا تعمل المتابعة في هذا الوضع (لا لـ cron ولا لأي تسليم مسطّح آخر).

      لذا من أجل مهمة cron قابلة للمتابعة مُسلَّمة إلى DM فردي، اضبط slack.dm_top_level_threads_as_sessions: false. لا حاجة إلى cron_continuable_surface (ويُتجاهَل) في حالات الـ DM.

      الكتم الصامت​

      إذا احتوى ردّ الوكيل النهائي على [SILENT]، يُكبَت التسليم كليًا. تُحفَظ المخرجات مع ذلك محليًا للمراجعة (في ~/.hermes/cron/output/)، لكن لا تُرسَل أي رسالة إلى هدف التسليم.

      هذا مفيد لمهام المراقبة التي يجب أن تُبلِغ فقط عند وجود خطأ ما:

      Check if nginx is running. If everything is healthy, respond with only [SILENT].
      Otherwise, report the issue.

      تُسلَّم المهام الفاشلة دائمًا بصرف النظر عن علامة [SILENT] — فقط التشغيلات الناجحة يمكن كتمها. لمهام المراقبة الهادئة، وجّه الوكيل ليرد بـ [SILENT] فقط عندما لا يوجد ما يُبلَّغ عنه.

      مهلة السكربت​

      للسكربتات التي تُشغَّل قبل التنفيذ (المرفقة عبر معامل script) مهلة افتراضية مدتها 3600 ثانية (ساعة واحدة). يحدّ هذا السكربت وحده — تعمل المهام القائمة على المهارات/التي يقودها الـ LLM على موازنة خمول منفصلة ولا تُحدّها هذه القيمة. إذا احتاجت سكربتاتك حدًا مختلفًا، يمكنك تغييره:

      # ~/.hermes/config.yaml
      cron:
        script_timeout_seconds: 1800   # 30 minutes

      أو اضبط متغير البيئة HERMES_CRON_SCRIPT_TIMEOUT. ترتيب الأولوية هو: متغير البيئة ← config.yaml ← القيمة الافتراضية 3600 ثانية.

      يحدّ cron أيضًا تنظيف الجلسة وموارد الوكيل بعد التشغيل. يحدث هذا بعد عودة دور الـ LLM، لذا فهو منفصل عن مهلة الخمول. القيمة الافتراضية 10 ثوانٍ لكل عملية تنظيف. إذا توقف مُنهي (finalizer) للتخزين أو العميل عن الاستجابة، يسجّل المُجدوِل خطأً، ويحرّر حارس المهمة الجاري تنفيذها، ويسمح للتشغيلات اللاحقة بالانطلاق بدلًا من تخطّي تلك المهمة إلى الأبد.

      # ~/.hermes/config.yaml
      cron:
        cleanup_timeout_seconds: 10

      اضبط cleanup_timeout_seconds: 0 فقط لاستعادة سلوك التنظيف غير المحدود القديم.

      مهلة إرسال الوسائط​

      عندما يتضمّن تسليم cron مرفقات وسائط (ملف PDF مُولَّد، صوت TTS، تقرير مُصدَّر) مُرسَلة عبر adapter لـ gateway حيّ، يُحدّ كل رفع مرفق بمهلة — 300 ثانية افتراضيًا. قد تحتاج الملفات الكبيرة على اتصالات صاعدة بطيئة إلى مدة أطول:

      # ~/.hermes/config.yaml
      cron:
        media_send_timeout_seconds: 600   # 10 minutes per attachment

      أو اضبط متغير البيئة HERMES_CRON_MEDIA_SEND_TIMEOUT. ترتيب الأولوية هو: متغير البيئة ← config.yaml ← القيمة الافتراضية 300 ثانية. يُسجَّل المرفق الذي تجاوز المهلة في حالة تشغيل المهمة كإخفاق تسليم جزئي (يظل النص مُسلَّمًا).

      مهلة تسليم Bot Chat​

      يُشغّل تسليم bot-chat دور وكيل كاملًا في محادثة البوت الهدف، لذا يُقاس حدّه بالدقائق لا الثواني — 600 ثانية افتراضيًا:

      # ~/.hermes/config.yaml
      cron:
        bot_chat_delivery_timeout_seconds: 900

      يُسجَّل التسليم الذي تجاوز المهلة في last_delivery_error؛ قد يكتمل دور البوت لاحقًا من تلقاء نفسه.

      وضع بلا وكيل (مهام السكربت فقط)​

      للمهام المتكررة التي لا تحتاج إلى استدلال LLM — مراقِبات حراسة كلاسيكية، تنبيهات القرص/الذاكرة، نبضات الحياة، اختبارات CI — مرّر no_agent=True عند الإنشاء. يُشغّل المُجدوِل سكربتك حسب الجدول ويُسلِّم مخرجاته القياسية مباشرة، متخطّيًا الوكيل كليًا:

      hermes cron create "every 5m" \
        --no-agent \
        --script memory-watchdog.sh \
        --deliver telegram \
        --name "memory-watchdog"

      الدلالات:

      • مخرجات السكربت القياسية (بعد التشذيب) ← تُسلَّم حرفيًا كالرسالة.
      • مخرجات قياسية فارغة ← دورة صامتة، بلا تسليم. هذا نمط مراقب الحراسة: "قل شيئًا فقط عند وجود خطأ".
      • خروج بكود غير صفري أو تجاوز المهلة ← يُسلَّم تنبيه خطأ، حتى لا يفشل مراقب حراسة معطّل بصمت.
      • {"wakeAgent": false} في السطر الأخير ← دورة صامتة (نفس البوابة التي تستخدمها مهام LLM).
      • بلا tokens، بلا نموذج، بلا احتياطي مزوّد — لا تلامس المهمة طبقة الـ inference إطلاقًا.

      تُشغَّل ملفات .sh / .bash عبر bash من PATH عند توفّره، وإلا فعبر /bin/bash (مهم على Windows Git Bash). يُشغَّل أي شيء آخر عبر مفسّر Python الحالي (sys.executable). يجب أن تُحلّ السكربتات داخل $HERMES_HOME/scripts/ — تُقبَل الأسماء النسبية، والمسارات المطلقة، والمسارات ذات البادئة ~ عندما يبقى الهدف المُحلَّل داخل ذلك المجلد؛ تُرفَض المسارات التي تفلت منه. تُطهَّر بيئة العملية الفرعية (_sanitize_subprocess_env): بيانات اعتماد API الخاصة بالمزوّدين وأسرار Hermes الأخرى لا تُورَّث إلى سكربتات cron.

      يُعِدّ الوكيل هذه من أجلك​

      يُظهر مخطط أداة cronjob الحقل no_agent لـ Hermes مباشرة، فيمكنك وصف مراقب حراسة في المحادثة وترك الوكيل يُعِدّه:

      Ping me on Telegram if RAM is over 85%, every 5 minutes.

      سيكتب Hermes سكربت الفحص إلى ~/.hermes/scripts/ عبر write_file، ثم يستدعي:

      cronjob(action="create", schedule="every 5m",
              script="memory-watchdog.sh", no_agent=True,
              deliver="telegram", name="memory-watchdog")

      يختار no_agent=True تلقائيًا عندما يكون محتوى الرسالة محدَّدًا بالكامل من السكربت (مراقبات الحراسة، تنبيهات العتبة، نبضات الحياة). تتيح الأداة نفسها أيضًا للوكيل إيقاف المهام مؤقتًا واستئنافها وتعديلها وحذفها — فتكون دورة الحياة كاملة مدفوعة بالمحادثة دون أن يلمس أحد CLI.

      راجع دليل مهام Cron بالسكربتات فقط للاطلاع على أمثلة عملية.

      تسلسل المهام باستخدام context_from​

      تُشغَّل مهام cron في جلسات معزولة بلا ذاكرة عن التشغيلات السابقة. لكن أحيانًا تكون مخرجات مهمة بالضبط ما تحتاجه المهمة التالية. يربط المعامل context_from هذا الاتصال تلقائيًا — يحصل prompt المهمة B على أحدث مخرجات المهمة A مُلحَقة كسياق وقت التشغيل.

      # Job 1: Collect raw data
      cronjob(
          action="create",
          prompt="Fetch the top 10 AI/ML stories from Hacker News. Save them to ~/.hermes/data/briefs/raw.md in markdown format with title, URL, and score.",
          schedule="0 7 * * *",
          name="AI News Collector",
      )

      # Job 2: Triage — receives Job 1's output as context
      # Get Job 1's ID from: cronjob(action="list")
      cronjob(
          action="create",
          prompt="Read ~/.hermes/data/briefs/raw.md. Score each story 1–10 for engagement potential and novelty. Output the top 5 to ~/.hermes/data/briefs/ranked.md.",
          schedule="30 7 * * *",
          context_from="<job1_id>",
          name="AI News Triage",
      )

      # Job 3: Ship — receives Job 2's output as context
      cronjob(
          action="create",
          prompt="Read ~/.hermes/data/briefs/ranked.md. Write 3 tweet drafts (hook + body + hashtags). Deliver to telegram:7976161601.",
          schedule="0 8 * * *",
          context_from="<job2_id>",
          name="AI News Brief",
      )

      كيف يعمل:

      • عندما تُطلَق المهمة 2، يقرأ Hermes أحدث مخرجات المهمة 1 من ~/.hermes/cron/output/{job1_id}/*.md
      • تُلحَق تلك المخرجات بـ prompt المهمة 2 تلقائيًا
      • لا تحتاج المهمة 2 إلى ترميز "اقرأ هذا الملف" صراحة — بل تتلقّى المحتوى كسياق
      • يمكن أن يكون طول السلسلة أي طول: المهمة 1 ← المهمة 2 ← المهمة 3 ← ...

      ما الذي يقبله context_from:

      الصيغةمثال
      معرّف مهمة واحد (نص)context_from="a1b2c3d4"
      معرّفات مهام متعددة (قائمة)context_from=["job_a", "job_b"]

      تُدمَج المخرجات بالترتيب المذكور.

      الاستمرارية: حمل مخرجات التشغيل السابق

      اضبط continuity=true وستحقن المهمة مخرجاتها الخاصة الأحدث في كل تشغيل. تبدأ المهام المتكررة عادةً كل تشغيل بفقدان للذاكرة — يعيد كشّاف أخبار الإبلاغ عن نفس الأخبار، ويعيد مراقِب التنبيه بشأن نفس الحالة. مع تفعيل الاستمرارية، تستيقظ المهمة وهي ترى ما أبلغت عنه آخر مرة ويمكنها إزالة التكرار والمتابعة من حيث توقفت:

      cronjob(
          action="create",
          prompt="Scan HN and arXiv for new agent-tooling papers. Report only items NOT already covered in your previous run's output.",
          schedule="every 6h",
          continuity=True,
          name="Agent Tooling Scout",
      )

      ليس للتشغيل الأول مخرجات سابقة، لذا يُنفَّذ الـ prompt كما هو. تُتخطَّى دورات مراقبة صامتة (no_change)، والمخرجات الفارغة، وسجلات المراجعة wakeAgent=false عند اختيار السياق، لذا تحافظ فترة الهدوء على آخر مخرجات جوهرية. تبقى ملفات المراجعة على القرص. تظل مستندات الخطأ مؤهّلة لإعطاء التشغيل التالي سياق تعافٍ؛ فهذا ليس مرشّح سجلّ يقتصر على النجاح فقط. في التشغيلات اللاحقة، تُلحَق المخرجات السابقة بإطار استمرارية ("تجنّب تكرار ما أُبلغ عنه بالفعل"). تُدمَج بحرية مع مهام أعلى في السلسلة (context_from=["<other_job_id>"] مع continuity=true)، وتُطفئها continuity=false عند التحديث مع الإبقاء على مدخلات context_from الأخرى. داخليًا، تُخزَّن العلامة كمُدخل محجوز self ضمن context_from.

      من الـ CLI: hermes cron create "every 6h" "Scan for news" --continuity، وhermes cron edit <job_id> --continuity / --no-continuity لتبديلها على مهمة موجودة. يظهر نفس المفتاح في محرر cron الخاص بلوحة التحكم وفي مربع حوار routine الخاص بـ Bot Mode في التطبيق المكتبي.

      متى تستخدمه:

      • خطوط أنابيب متعددة المراحل (جمع ← تصفية ← تنسيق ← تسليم)
      • مهام متتابعة حيث يعتمد عمل الخطوة N على مخرجات الخطوة N−1
      • أنماط التوزيع/التجميع حيث تُجمِّع مهمة واحدة نتائج عدة مهام أخرى
      • كشّافات/مراقِبات متكررة يجب أن تزيل التكرار عن تقريرها السابق (continuity=true)

      تعافي المزوّد​

      ترث مهام cron مزوّديك الاحتياطيين المُعدّين وتدوير مجمّع بيانات الاعتماد. إذا كان مفتاح API الأساسي محدود المعدل أو أعاد المزوّد خطأً، يمكن لوكيل cron:

      • الرجوع إلى مزوّد بديل إذا كان لديك fallback_providers (أو fallback_model القديم) مُعدًّا في config.yaml
      • التدوير إلى بيانات الاعتماد التالية في مجمّع بيانات الاعتماد لنفس المزوّد

      هذا يعني أن مهام cron التي تعمل بتردد عالٍ أو خلال ساعات الذروة أكثر مرونة — لن يُفشل مفتاح واحد محدود المعدل التشغيل بأكمله.

      إخفاقات التشغيل (last_error)​

      يسجّل تشغيل الوكيل الفاشل last_error موجزًا، مرئيًا في قوائم المهام وفي /cron list مع تنقيح أنماط بيانات الاعتماد وبيانات اعتماد URL (بما في ذلك الأخطاء المخزّنة سابقًا). هذا منفصل عن last_fire_error (تسليم المُجدوِل) وlast_delivery_error (التسليم). يمكن أن تكون تلك الحقول فارغة بشكل صحيح عندما يفشل الوكيل نفسه.

      لفحص خلل اتصال، افحص وثيقة التشغيل تحت cron/output/<job_id>/ في مجلد Hermes النشط الرئيسي. يتضمن قسم ## Error فيها التتبع المتسلسل (traceback)، مع تنقيح أنماط بيانات الاعتماد وبيانات اعتماد URL. يستخدم الملف صلاحيات ملف المخرجات الخاصة الحالية؛ لا تُلتقَط المتغيرات المحلية في التتبع. تحتفظ إشعارات التسليم وlast_error بالخطأ الموجز فقط، لا التتبع الكامل. راجع التشخيصات قبل مشاركتها: التنقيح ليس ضمانًا بأن بيانات التطبيق العشوائية غير حساسة.

      الإطلاقات المجدولة الفائتة (last_fire_error)​

      على النشرات المُستضافة (cron مُدار)، ينتقل الإطلاق المجدول من مُجدوِل المنصة عبر لوحة التحكم إلى خادم الـ API الداخلي الخاص بالـ gateway. إذا فشل هذا التسليم النهائي — كانت عملية الـ gateway متوقفة، أو لم يبدأ مستمع خادم الـ API الخاص بها قط — لا يبدأ التشغيل أبدًا، فلا يوجد سجلّ تنفيذ ولا last_status لفحصه. العلامة المميزة: تعمل المهمة في كل مرة تُطلقها يدويًا، لكنها لا تُطلَق تلقائيًا أبدًا.

      تُختَم هذه الحالات الفائتة على سجلّ المهمة كـ last_fire_error (طابع زمني + السبب) وتُعرَض عبر:

      • أداة cronjob ← action: "list" — حقل last_fire_error
      • hermes cron list — سطر أحمر ⚠ Missed scheduled fire: تحت المهمة
      • عرض المهمة في لوحة التحكم

      يعكس الختم دائمًا صحة الإطلاق التلقائي الحالية: يُستبدَل بإخفاقات أحدث ويُمسَح تلقائيًا عند التشغيل الناجح التالي. إن رأيته، فالمهمة وجدولها بخير — الجانب الخاص بالـ gateway من مسار الإطلاق يحتاج انتباهًا (الأكثر شيوعًا، أعد تشغيل الـ gateway عبر مُشرِفه ليُحمِّل بيئة الـ profile الكاملة: hermes gateway restart).

      سياسة التشغيل المحلي الفائت​

      إذا كان الـ gateway متوقفًا (أو يعيد التشغيل) عندما مرّ الوقت المجدول لمهمة متكررة، تُدرِك المهمة الفوات مرة واحدة عندما يعود المُجدوِل: تُطلَق فترة فائتة داخل فجوة إعادة تشغيل مرة واحدة بالضبط، ولا تُشغَّل أبدًا فترة سبق تشغيلها قبل إعادة التشغيل مرة أخرى، وينهار انقطاع طويل إلى تشغيل واحد بدلًا من تشغيل لكل فترة فائتة. لا تُدرِك المهام المُوقَّفة الفوات أبدًا. يظهر كل تدارُك في hermes cron list كـ ⚠ late / ⚠ catch-up after missed fire.

      لتفادي حِمل التدارُك ذلك بعد إيقاف مخطَّط للـ gateway، اضبط:

      cron:
        catch_up_missed: false   # default: true

      أو شغّل hermes config set cron.catch_up_missed false. مع هذا الاستثناء، تُعاد مؤاخذة مهمة متكررة متأخرة عن نافذة السماح الحالية (نصف فترتها، محصورة بين 120 ثانية و2 ساعة) إلى موعدها المستقبلي التالي دون الإطلاق الآن. يُسجَّل التخطّي. تعمل المهام الواقعة ضمن نافذة السماح والإطلاقات اليدوية الصريحة بشكل طبيعي؛ إذا تعذَّر حساب الموعد التالي، يُحافَظ على البديل الحالي القائم على تشغيل مرة واحدة. هذا لا يغيّر انتهاء صلاحية المهام أحادية التنفيذ، ولا سلوك الاستئناف، ولا اجتياح المزوّد المُستضاف أدناه. لا يوجد استثناء لكل مهمة على حدة.

      تدارك الإطلاقات الفائتة​

      عندما يكون مُجدوِل خارجي نشطًا (cron مُدار في النشرات المُستضافة)، يُشغّل الـ gateway أيضًا اجتياح تدارُك: تُطالَب مهمة مرّ وقتها المجدول دون إطلاق مُسلَّم — وانقضت نافذة سماحها — وتُشغَّل محليًا، لذا يكلّف انقطاع في تسليم الإطلاق دقائق بدلًا من اليوم بأكمله. يُزال تكرار الاجتياح مقابل إعادات محاولة المُجدوِل المتأخرة باستخدام نفس ادّعاء المخزن المستخدم للإطلاقات العادية.

      cron:
        misfire_grace_minutes: 10   # wait this long for the scheduler's own retries
                                    # before catching up locally; 0 disables catch-up

      لا تحتاج النشرات المحلية (المُنقِّط المدمج) إلى هذا — يلتقط المُنقِّط بالفعل المهام المتأخرة في دورته التالية.

      صيغ الجدولة​

      يُسلَّم ردّ الوكيل النهائي تلقائيًا إلى هدف deliver: الخاص بالمهمة — لم يعد الوكيل يُطلق الرسائل بنفسه، فالمحتوى الموجَّه للمستخدم يذهب ببساطة في الردّ النهائي. للتسليم إلى أهداف إضافية أو مختلفة، اسرد عدة أهداف deliver: على مهمة cron (مفصولة بفواصل، مثل deliver: "telegram,discord") بدلًا من أن يرسلها الوكيل.

      تأخيرات نسبية (مرة واحدة)​

      in 30m  → Run once in 30 minutes
      in 2h   → Run once in 2 hours
      in 1d   → Run once in 1 day

      فواصل زمنية (متكررة)​

      30m          → Every 30 minutes (bare durations are recurring)
      every 30m    → Every 30 minutes
      every 2h     → Every 2 hours
      every 1d     → Every day
      every hour   → Every hour (bare unit = 1)

      جداول يوم/وقت طبيعية (متكررة)​

      every monday 9am         → Weekly, Mondays at 9:00 AM
      every day at 9am         → Daily at 9:00 AM
      weekdays at 9am          → Weekdays at 9:00 AM
      weekends at 10am         → Saturdays and Sundays at 10:00 AM
      daily at 7am             → Daily at 7:00 AM
      monday, wednesday at 9am → Mondays and Wednesdays at 9:00 AM

      تقبل الأوقات 9am، 9:30pm، 14:00، الساعات المجردة بنظام 24 ساعة (at 7)، noon، وmidnight. تُترجَم هذه الصيغ داخليًا إلى تعبيرات cron (تتطلّب حزمة croniter، المثبَّتة افتراضيًا).

      تعبيرات Cron​

      0 9 * * *       → Daily at 9:00 AM
      0 9 * * 1-5     → Weekdays at 9:00 AM
      0 9 * * MON-FRI → Weekdays at 9:00 AM (named weekdays/months accepted)
      0 */6 * * *     → Every 6 hours
      30 8 1 * *      → First of every month at 8:30 AM
      0 0 * * 0       → Every Sunday at midnight

      طوابع زمنية بصيغة ISO​

      2026-03-15T09:00:00    → One-time at March 15, 2026 9:00 AM

      إدارة المهام برمجيًا​

      الـ API المُوجَّه للوكيل أداة واحدة:

      cronjob(action="create", ...)
      cronjob(action="list")
      cronjob(action="update", job_id="...")
      cronjob(action="pause", job_id="...")
      cronjob(action="resume", job_id="...")
      cronjob(action="run", job_id="...")
      cronjob(action="remove", job_id="...")

      من أجل update، مرّر skills=[] لإزالة كل المهارات المُرفقة.

      التشغيلات اليدوية غير متزامنة​

      يُطلق cronjob(action="run") المهمة فورًا في الخلفية (مثل delegate_task): يعود استدعاء الأداة فورًا بمقبض، وتعود نتيجة المهمة — نجاح/فشل، هدف التسليم، التشغيل المجدول التالي، ومقتطف من المخرجات — إلى المحادثة كرسالة جديدة عند انتهاء التشغيل. يمكن للوكيل (ولك) الاستمرار في العمل في الأثناء، وتُرفَض مهمة قيد التشغيل بالفعل برسالة "already running" بدلًا من الإطلاق المزدوج.

      يمكنك أيضًا تمرير prompt مع action="run" لحقن سياق مؤقت خاص بذلك التشغيل:

      cronjob(action="run", job_id="...", prompt="CONTEXT: focus on the EU region today")

      يُلحَق السياق بـ prompt المهمة المخزَّن تحت ترويسة ## Run Context لذلك الإطلاق الوحيد فقط — لا يُخزَّن أبدًا في تعريف المهمة، ويمرّ بنفس فحص حقن الـ prompt الذي تمرّ به الـ prompts المخزَّنة.

      تعود بيئات التشغيل التي لا يمكنها استقبال نتائج منفصلة (hermes -z لمرة واحدة، hermes cron run من CLI، جلسات cron الفرعية، عمّال Kanban) إلى التنفيذ المتزامن تلقائيًا.

      Toolsets المتاحة لمهام cron​

      يُشغّل cron كل مهمة في جلسة وكيل جديدة بلا منصة محادثة مرفقة. افتراضيًا، يحصل وكيل cron على toolset الذي أعددته لمنصة cron في hermes tools — ليس افتراضي CLI، ولا كل شيء تحت الشمس.

      hermes tools
      # → pick the "cron" platform in the curses UI
      # → toggle toolsets on/off just like you would for Telegram/Discord/etc.

      تحكّم أدقّ لكل مهمة متاح عبر حقل enabled_toolsets على cronjob.create (أو على مهمة موجودة عبر cronjob.update):

      cronjob(action="create", name="weekly-news-summary",
              schedule="every sunday 9am",
              enabled_toolsets=["web", "file"],      # just web + file, no terminal/browser/etc.
              prompt="Summarize this week's AI news: ...")

      عندما يُضبَط enabled_toolsets على مهمة، فهو يغلب؛ وإلا فيغلب إعداد منصة cron في hermes tools؛ وإلا يعود Hermes إلى الافتراضيات المدمجة. هذا مهم للتحكّم في التكلفة: حمل browser وdelegation في كل مهمة صغيرة من نوع "اجلب الأخبار" يُضخّم prompt مخطط الأدوات في كل استدعاء LLM.

      تخطّي الوكيل كليًا: wakeAgent​

      إذا أرفقت مهمة cron الخاصة بك سكربت فحص مسبق (عبر script=)، يمكن للسكربت أن يقرر وقت التشغيل ما إذا كان على Hermes استدعاء الوكيل أصلًا. أصدر سطر مخرجات قياسية أخير بالصيغة:

      {"wakeAgent": false}

      …ويتخطّى cron تشغيل الوكيل كليًا لهذه الدورة. مفيد للاستطلاعات المتكررة (كل 1–5 دقائق) التي تحتاج فقط إلى إيقاظ الـ LLM عندما تتغير الحالة فعلًا — وإلا فأنت تدفع ثمن أدوار وكيل بلا محتوى مرارًا وتكرارًا.

      # pre-check script
      import json, sys
      latest = fetch_latest_issue_count()
      prev = read_state("issue_count")
      if latest == prev:
          print(json.dumps({"wakeAgent": False}))   # skip this tick
          sys.exit(0)
      write_state("issue_count", latest)
      print(json.dumps({"wakeAgent": True, "context": {"new_issues": latest - prev}}))

      عندما تُحذَف wakeAgent، تكون القيمة الافتراضية true (استيقظ الوكيل كالمعتاد).

      وصفات: بوابات رخيصة قبل التشغيل​

      تمنحك بوابة wakeAgent طريقة بتكلفة صفرية لتقرير ما إذا كان على مهمة مجدولة أن تنفق أي tokens من LLM أصلًا. تغطي ثلاثة أنماط معظم حالات الاستخدام.

      بوابة تغيّر الملف — تُشغَّل فقط عندما يكون لملف مراقَب محتوى جديد منذ آخر دورة ناجحة. يسجّل المُجدوِل last_run_at لكل مهمة؛ قارنه بزمن تعديل الملف (mtime).

      #!/bin/bash
      # ~/.hermes/scripts/feed-changed.sh
      FEED="$HOME/data/feed.json"
      STATE="$HOME/.hermes/scripts/.feed-changed.last"
      test -f "$FEED" || { echo '{"wakeAgent": false}'; exit 0; }
      mtime=$(stat -c %Y "$FEED")
      last=$(cat "$STATE" 2>/dev/null || echo 0)
      if [ "$mtime" -le "$last" ]; then
        echo '{"wakeAgent": false}'
      else
        echo "$mtime" > "$STATE"
        echo '{"wakeAgent": true}'
      fi
      cronjob(action="create", name="process-feed",
              schedule="every 30m",
              script="feed-changed.sh",
              prompt="A new ~/data/feed.json has landed. Summarize what changed.")

      بوابة علامة خارجية — تُشغَّل فقط عندما تكون عملية أخرى قد أشارت إلى الجاهزية (مثل، يُسقط hook للنشر ملفًا، أو تضبط مهمة CI قيمة في مخزن حالتك).

      #!/bin/bash
      # ~/.hermes/scripts/flag-ready.sh
      if test -f /tmp/new-data-ready; then
        rm -f /tmp/new-data-ready
        echo '{"wakeAgent": true}'
      else
        echo '{"wakeAgent": false}'
      fi
      cronjob(action="create", name="nightly-analysis",
              schedule="0 9 * * *",
              script="flag-ready.sh",
              prompt="Run the nightly analysis over today's batch.")

      بوابة عدّ SQL — تُشغَّل فقط عندما توجد صفوف جديدة لمعالجتها في قاعدة بياناتك الخاصة. يمكن للسكربت أيضًا تمرير العدد إلى الوكيل عبر context، حتى يعرف الوكيل كمّية ما ينظر إليه دون إعادة الاستعلام.

      #!/usr/bin/env python
      # ~/.hermes/scripts/new-rows.py
      import json, sqlite3
      conn = sqlite3.connect("/home/me/data/app.db")
      n = conn.execute(
          "SELECT COUNT(*) FROM messages WHERE ts > strftime('%s','now','-2 hours')"
      ).fetchone()[0]
      if n < 1:
          print(json.dumps({"wakeAgent": False}))
      else:
          print(json.dumps({"wakeAgent": True, "context": {"new_rows": n}}))
      cronjob(action="create", name="summarize-new-msgs",
              schedule="every 2h",
              script="new-rows.py",
              prompt="Summarize the new messages from the last 2 hours.")

      يعمل النمط نفسه لأي مصدر بيانات يمكنك الاستعلام عنه من سكربت — Postgres، أو واجهة HTTP API، أو مخزن حالتك الخاص — دون تضمين مُقيِّم SQL داخل نظام cron الفرعي.

      نصيحة

      ~/.hermes/state.db الخاص بـ Hermes نفسه مخطط داخلي يتغيّر بين الإصدارات. لا تستعلم عنه من بوابة قبل التشغيل — وجّه بدلًا من ذلك إلى قاعدة بياناتك أو تغذيتك الخاصة.

      الفضل: طرحت هذه المجموعة من الوصفات استكشاف @iankar8 في #2654، الذي اقترح إضافة triggers من نوع sql/file/command كآلية موازية. تغطّي بوابة script + wakeAgent بالفعل الحالات الثلاث بتكلفة صفرية، فوصل العمل كتوثيق بدلًا من ذلك.

      تسلسل المهام: context_from​

      يمكن لمهمة cron استهلاك أحدث مخرجات ناجحة لمهمة أخرى أو أكثر بسرد أسمائها (أو معرّفاتها) في context_from:

      cronjob(action="create", name="daily-digest",
              schedule="every day 7am",
              context_from=["ai-news-fetch", "github-prs-fetch"],
              prompt="Write the daily digest using the outputs above.")

      تُحقَن أحدث المخرجات المكتملة للمهام المُشار إليها فوق الـ prompt كسياق لهذا التشغيل. يجب أن يكون كل إدخال أعلى في السلسلة معرّف مهمة أو اسمًا صالحًا (راجع cronjob action="list"). ملاحظة: يقرأ التسلسل أحدث مخرجات مكتملة — لا ينتظر مهامًا أعلى في السلسلة تعمل في نفس الدورة.

      تخزين المهام​

      تُخزَّن المهام في ~/.hermes/cron/jobs.json. تُحفَظ مخرجات تشغيلات المهام في ~/.hermes/cron/output/{job_id}/{timestamp}.md.

      تعريفات المهام JSON عادي على القرص: تنجو من hermes update، وإعادة تشغيل الـ gateway، وإعادة تشغيل الجهاز. تُوسَم المهمة التي كانت قيد التشغيل أثناء إعادة تشغيل بـ unknown في سجلّ التنفيذ — لا تُعاد محاولتها تلقائيًا، لكن الدورة المجدولة التالية للمهمة تُطلَق بشكل طبيعي. راجع سجلّ التنفيذ للتفاصيل.

      نصيحة

      اطلب من الوكيل إدارة المهام عبر أداة cronjob، أو hermes cron edit، أو /cron — لا بتعديل jobs.json مباشرة. يمكن أن تفشل التعديلات المباشرة بصمت عندما تحجب سلامة كتابة الملفات المسار (مثلًا عند ضبط HERMES_WRITE_SAFE_ROOT)، وتذييل مُتحقق تعديل الملفات هو الإشارة الموثوقة على أن شيئًا لم يُحفَظ.

      يمكن للمهام تخزين model وprovider كـ null. عند حذف تلك الحقول، يحلّها Hermes وقت التنفيذ من الإعدادات العامة. تظهر فقط في سجلّ المهمة عند ضبط تجاوز خاص بالمهمة.

      يستخدم التخزين كتابات ملفات ذرية حتى لا تترك الكتابات المُقاطَعة ملف مهمة مكتوبًا جزئيًا.

      الـ prompts المكتفية ذاتيًا لا تزال مهمة​

      مهم

      تُشغَّل مهام cron في جلسة وكيل جديدة كليًا. يجب أن يحتوي الـ prompt كل ما يحتاجه الوكيل ولم توفّره المهارات المرفقة بالفعل.

      سيّئ: "Check on that server issue"

      جيّد: "SSH into server 192.168.1.100 as user 'deploy', check if nginx is running with 'systemctl status nginx', and verify https://example.com returns HTTP 200."

      الأمان​

      تُفحَص prompts المهام المجدولة بحثًا عن أنماط حقن الـ prompt واستخراج بيانات الاعتماد عند الإنشاء والتحديث. تُحظَر الـ prompts التي تحتوي حِيَل Unicode غير مرئية، أو محاولات باب خلفي عبر SSH، أو حِمولات استخراج أسرار واضحة.

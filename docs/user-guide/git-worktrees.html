      Git Worktrees

      كثيرًا ما يُستخدم Hermes Agent على مستودعات كبيرة وطويلة العمر. فعندما تريد:

      • تشغيل عدة وكلاء بالتوازي على المشروع نفسه، أو
      • إبقاء عمليات إعادة الهيكلة (refactors) التجريبية معزولة عن الـ branch الرئيسي،

      فإن worktrees في Git هي الطريقة الأكثر أمانًا لمنح كل وكيل نسخته المسحوبة (checkout) الخاصة دون تكرار المستودع بأكمله.

      توضّح هذه الصفحة كيفية الجمع بين worktrees و Hermes بحيث تحصل كل جلسة على مجلد عمل نظيف ومعزول.

      لماذا تستخدم worktrees مع Hermes؟​

      يتعامل Hermes مع مجلد العمل الحالي على أنه جذر المشروع:

      • CLI: المجلد الذي تشغّل فيه hermes أو hermes chat
      • Messaging gateways: المجلد المحدد عبر terminal.cwd في ~/.hermes/config.yaml

      إذا شغّلت عدة وكلاء في النسخة المسحوبة نفسها، فقد تتداخل تغييراتهم مع بعضها:

      • قد يحذف أحد الوكلاء ملفات يستخدمها الآخر أو يعيد كتابتها.
      • يصبح من الأصعب معرفة أي التغييرات تنتمي إلى أي تجربة.

      باستخدام worktrees، يحصل كل وكيل على:

      • branch ومجلد عمل خاصين به
      • سجل Checkpoint Manager خاص به لاستخدامه مع /rollback

      راجع أيضًا: نقاط الحفظ (Checkpoints) و /rollback.

      البدء السريع: إنشاء worktree​

      من داخل الجلسة: /worktree new​

      أسرع طريقة (مستوحاة من /worktree new في Copilot CLI): من جلسة CLI تفاعلية، نفّذ

      /worktree new my-experiment

      يُنشئ Hermes المجلد .worktrees/my-experiment/ داخل المستودع (على الـ branch hermes/my-experiment، استنادًا إلى أحدث commit في المستودع البعيد بعد جلبه للتو، ما لم يكن worktree_sync: false)، ويعيد توجيه أدوات الطرفية والملفات الخاصة بالجلسة إليه — دون الحاجة إلى إعادة التشغيل. احذف الاسم لتحصل على شجرة عشوائية باسم hermes-<id>. يعرض /worktree وحده الشجرة النشطة؛ ويسرد /worktree list جميع الأشجار. وعند الخروج لا تُحفظ الشجرة إلا إذا كانت تحتوي على commits لم تُدفع (push) بعد، تمامًا كما في hermes -w.

      يدويًا باستخدام git​

      من المستودع الرئيسي (الذي يحتوي على .git/)، أنشئ worktree جديدًا لـ feature branch:

      # From the main repo root
      cd /path/to/your/repo

      # Create a new branch and worktree in ../repo-feature
      git worktree add ../repo-feature feature/hermes-experiment

      يُنشئ هذا:

      • مجلدًا جديدًا: ../repo-feature
      • branch جديدًا: feature/hermes-experiment مسحوبًا في ذلك المجلد

      يمكنك الآن الانتقال بالأمر cd إلى الـ worktree الجديد وتشغيل Hermes هناك:

      cd ../repo-feature

      # Start Hermes in the worktree
      hermes

      سيقوم Hermes بما يلي:

      • اعتبار ../repo-feature جذرًا للمشروع.
      • استخدام ذلك المجلد لملفات السياق وتعديلات الكود والأدوات.
      • استخدام سجل نقاط حفظ منفصل لـ /rollback مقصور على هذا الـ worktree.

      تشغيل عدة وكلاء بالتوازي​

      يمكنك إنشاء عدة worktrees، لكل منها branch خاص به:

      cd /path/to/your/repo

      git worktree add ../repo-experiment-a feature/hermes-a
      git worktree add ../repo-experiment-b feature/hermes-b

      في طرفيات منفصلة:

      # Terminal 1
      cd ../repo-experiment-a
      hermes

      # Terminal 2
      cd ../repo-experiment-b
      hermes

      كل عملية Hermes:

      • تعمل على الـ branch الخاص بها (feature/hermes-a مقابل feature/hermes-b).
      • تكتب نقاط الحفظ تحت hash مختلف لمستودع الظل (shadow repo) (مشتق من مسار الـ worktree).
      • يمكنها استخدام /rollback بشكل مستقل دون التأثير على الأخرى.

      يفيد هذا خصوصًا عند:

      • تشغيل عمليات إعادة هيكلة دفعية.
      • تجربة مناهج مختلفة للمهمة نفسها.
      • الجمع بين جلسات CLI و gateway على المستودع الأصلي (upstream) نفسه.

      تنظيف worktrees بأمان​

      عندما تنتهي من تجربة ما:

      1. قرّر ما إذا كنت ستحتفظ بالعمل أم ستتخلص منه.
      2. إذا أردت الاحتفاظ به:
        • ادمج (merge) الـ branch في الـ branch الرئيسي كالمعتاد.
      3. أزِل الـ worktree:
      cd /path/to/your/repo

      # Remove the worktree directory and its reference
      git worktree remove ../repo-feature

      ملاحظات:

      • يرفض git worktree remove إزالة worktree يحتوي على تغييرات لم تُنفَّذ لها commit ما لم تفرض ذلك.
      • إزالة الـ worktree لا تحذف الـ branch تلقائيًا؛ ويمكنك حذف الـ branch أو الاحتفاظ به باستخدام أوامر git branch المعتادة.
      • لا تُحذف بيانات نقاط الحفظ الخاصة بـ Hermes ضمن ~/.hermes/checkpoints/ تلقائيًا عند إزالة worktree، لكنها عادةً صغيرة جدًا.

      أفضل الممارسات​

      • worktree واحد لكل تجربة Hermes
        • أنشئ branch/worktree مخصصًا لكل تغيير جوهري.
        • يُبقي هذا الفروقات (diffs) مركّزة، والـ PRs صغيرة وقابلة للمراجعة.
      • سمِّ الـ branches باسم التجربة
        • مثل feature/hermes-checkpoints-docs، feature/hermes-refactor-tests.
      • نفّذ commits بشكل متكرر
        • استخدم git commits للمراحل الرئيسية.
        • استخدم نقاط الحفظ و /rollback كشبكة أمان للتعديلات التي تُجريها الأدوات فيما بينها.
      • تجنّب تشغيل Hermes من جذر المستودع المجرّد عند استخدام worktrees
        • فضّل بدلًا من ذلك مجلدات الـ worktrees، بحيث يكون لكل وكيل نطاق واضح.

      استخدام hermes -w (وضع worktree التلقائي)​

      يتضمن Hermes الخيار المدمج -w الذي يُنشئ تلقائيًا git worktree مؤقتًا مع branch خاص به. لا تحتاج إلى إعداد worktrees يدويًا — فقط انتقل بالأمر cd إلى مستودعك ونفّذ:

      cd /path/to/your/repo
      hermes -w

      سيقوم Hermes بما يلي:

      • إنشاء worktree مؤقت ضمن .worktrees/ داخل مستودعك.
      • سحب branch معزول (مثل hermes/hermes-<hash>).
      • تشغيل جلسة CLI كاملة داخل ذلك الـ worktree.

      هذه أسهل طريقة للحصول على عزل worktree. ويمكنك أيضًا دمجها مع استعلام واحد:

      hermes -w -z "Fix issue #123"

      للوكلاء المتوازين، افتح عدة طرفيات ونفّذ hermes -w في كل منها — إذ يحصل كل استدعاء على worktree و branch خاصين به تلقائيًا.

      جمع كل ما سبق معًا​

      • استخدم git worktrees لمنح كل جلسة Hermes نسختها المسحوبة النظيفة الخاصة.
      • استخدم الـ branches لتسجيل السجل العام لتجاربك.
      • استخدم نقاط الحفظ + /rollback للتعافي من الأخطاء داخل كل worktree.

      يمنحك هذا الجمع:

      • ضمانات قوية بألا يتداخل الوكلاء والتجارب المختلفة مع بعضها.
      • دورات تكرار سريعة مع سهولة التعافي من التعديلات السيئة.
      • pull requests نظيفة وقابلة للمراجعة.

      تطوير واجهات UI عبر worktrees​

      تحتاج واجهات TypeScript (ui-tui/، apps/desktop/) كلٌّ منها إلى node_modules، وتنفيذ npm ci جديد لكل worktree يكرّرها عبر كل branch. إذا كنت تعمل على TUI أو تطبيق سطح المكتب من عدة worktrees، فراجع تطوير TUI و Desktop من Worktrees للتعرّف على الأداتين المساعدتين htui / hgui اللتين تتشاركان تثبيتًا واحدًا عبر symlink.

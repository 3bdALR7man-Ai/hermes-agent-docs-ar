      Bot Mode

      Bot Mode الـ profiles الخاصة بـ Hermes إلى قائمة من البوتات (Bots) المسمّاة. لكل بوت دوره ونموذجه وذاكرته ومهاراته وصورته الرمزية الخاصة؛ وتشغّل البوتات مهامَّ روتينية متكررة، وتتداول معًا في المحادثات الجماعية، وتتراسل فيما بينها مباشرةً. ابنِ بوتًا متخصصًا مرة واحدة وسيبقى متاحًا دائمًا، على بُعد نقرة واحدة.

      يأتي Bot Mode مدمجًا في تطبيق سطح المكتب ويكون مفعّلًا افتراضيًا — دون الحاجة إلى أي تثبيت. ويظهر كتبويب Bots بجوار Sessions في الشريط الجانبي الأيسر، مع لوحة Routines مثبّتة بجوار المحادثة أثناء تفعيل تبويب Bots.

      البوت هو profile

      لا يوجد مفهوم أساسي جديد عليك تعلّمه: فالبوت هو profile في Hermes — إعدادات وذاكرة ومهارات وبيانات اعتماد وسجل محادثات معزولة تحت ~/.hermes/profiles/<name>/. و Bot Mode واجهة مستخدم فوق هذا المفهوم، لذا فكل ما تفعله فيه مرئي من CLI أيضًا: يفتح hermes -p <bot> chat الوكيل نفسه، وتظهر المهام الروتينية للبوتات في hermes cron list. لا تعديلات على النواة، ولا daemons في الخلفية، ولا تخزين إضافي.

      راجع Profiles والوكلاء والبوتات لمعرفة علاقة Bot Mode ببوتات المراسلة و subagents المفوّضة.

      هل تنتقل من profiles ؟​

      تبقى profiles تعمل تمامًا كما كانت؛ ويضيف Bot Mode الأجزاء التي لا يملكها profile وحده:

      مع profiles العاديةمع Bot Mode
      مجموعة جلسات لكل profile ؛ تختار واحدة أو تبدأ أخرىمحادثة Bot Chat دائمة واحدة لكل Bot. انقر Bot فتعود إلى المحادثة نفسها؛ ويضغطها /new بدل تفريعها
      تبدّل profiles للتحدث إلى متخصص مختلفكل Bot في قائمة واحدة مع صورته الرمزية وأحدث رسالة وحالة الرسائل غير المقروءة
      لا تتحدث profiles مع بعضها مطلقًاتقوم Bots بـ مراسلة بعضها وتشارك محادثات جماعية
      توجد المهام المجدولة في hermes cron بعيدًا عن أي محادثةتُجدول routines لكل Bot وتُعدّل بجوار محادثته

      لا ينتقل شيء: تبقى الإعدادات والذاكرة والمهارات وبيانات الاعتماد في ~/.hermes/profiles/<name>/، وما زال hermes -p <bot> chat يفتح الوكيل نفسه.

      جزء Bots​

      تعرض القائمة صفًا واحدًا لكل profile وكيل: الصورة الرمزية، ومعاينة آخر رسالة، والطابع الزمني.

      • انقر على بوت للانتقال إلى محادثته — فلكل Bot محادثة أساسية دائمة Bot Chat تُنشأ (وتُثبّت) لحظة إنشاء Bot. يفتح النقر على الصف دائمًا Bot Chat تلك (المحادثة نفسها التي يعاينها الصف)، حتى مع وجود تبويبات أخرى مفتوحة للبوت؛ وتبقى تلك التبويبات مفتوحة بجوارها. وفي شريط التبويبات يُعنون Bot Chat باسم البوت، كي تميز Bot اثنين مفتوحين بنظرة واحدة.
      • Right-click a Bot → Open recent session للانتقال إلى أحدث محادثة عادية نشطة له — تشغيل cron ، أو مهمة مفوّضة، أو thread جانبي — كتبويب بجوار Bot Chat. ولا يتغير سلوك النقر على الصف نفسه مطلقًا؛ و Bot الذي لا توجد له محادثة أخرى بعد يفتح Bot Chat الخاصة به فقط.
      • Active now — يتضمن مرشّح النشاط في القائمة صاحبَ الدور الحيّ الذي عليه التركيز، والبوتات التي كتبت خلال آخر 90 ثانية، والبوتات التي لديها نبضة (heartbeat) حديثة من عامل. ومجرد وجود gateway متصل لا يعني أن البوت يعمل.
      • البحث يرشّح القائمة أثناء الكتابة.
      • إخفاء بوت — انقر بالزر الأيمن على صف → Hide Bot لإخراج بوت لا تستخدمه من القائمة ومن شريط Active-now. الإخفاء للعرض فقط: إذ تظل الإشارات بـ @ تُحلّ، وتبقى عضويات المحادثات الجماعية دون تغيير، وتستمر المهام الروتينية في العمل. وبمجرد إخفاء بوت واحد على الأقل، يظهر مفتاح على شكل عين في ترويسة الجزء — انقره لإظهار البوتات المخفية باهتة في مكانها، ثم انقر بالزر الأيمن → Unhide Bot لإعادة أحدها. لا تُصدر البوتات المخفية إشعارات أبدًا، لكنها تراكم النشاط غير المقروء بصمت، وتعرض العين نقطة لتعلم أن شيئًا ما قد حدث. تُحفظ حالة الإخفاء في البيانات الوصفية لـ profile البوت، لذا تنتقل مع البوت إلى كل تطبيق سطح مكتب متصل بذلك الـ backend.
      محادثة Bot Chat الأساسية محادثة دائمة

      كتابة /new (أو /reset) داخل المحادثة الأساسية لبوت ستؤدي إلى تفريع العلاقة إلى جلسة مؤقتة — وهو الشيء الوحيد الذي يَعِد Bot Mode بألا يحدث أبدًا. لذا يعيد مربع الكتابة توجيهها إلى /compact بدلًا من ذلك: سياق عمل جديد، والمحادثة نفسها. أما الجلسات العادية على الـ profile نفسه فتحتفظ بحرية استخدام /new كاملة.

      تؤدي أرشفة Bot Chat من الشريط الجانبي إلى إخراجها من الاستخدام: تبدأ النقرة التالية على Bot محادثة جديدة تصبح Bot Chat الأساسية الجديدة. وتظل المحادثة المتقاعدة مؤرشفة ومخفية — يُحفظ سجلها في قاعدة البيانات، لكنه لم يعد قابلًا للوصول من Bot أو عرض الأرشيف. ولا يُخرج مسح الأرشفة التلقائية للخمول (sessions.auto_archive) Bot Chat من الاستخدام مطلقًا؛ ولا تفعل ذلك إلا الأرشفة الصريحة.

      تنظيم البوتات في أقسام​

      الأقسام مجلدات تنشئها بنفسك — Clients, Team، أو أي تسمية تناسبك — كمحور ثانٍ إلى جانب التجميع التلقائي حسب الـ gateway. وعند عدم إنشاء أي أقسام، تبقى القائمة قائمة بسيطة كما كانت دائمًا.

      • أنشئ قسمًا من قائمة + في الجزء → New section، أو انقر بالزر الأيمن على بوت → Move to section → New section… (فيُضاف البوت إلى القسم لحظة إنشائه).
      • أضف بوتًا إلى قسم بسحب صفه إلى القسم — يُميَّز القسم المستهدف أثناء التمرير فوقه، ويلغي Esc السحب — أو انقر بالزر الأيمن → Move to section واختر قسمًا. ويعيده Remove from section إلى Unassigned.
      • أعد تسمية قسم، أو أعد ترتيبه، أو احذفه من قائمة النقر بالزر الأيمن على عنوانه (أو من ⋯ الذي يظهر عند التمرير فوقه)؛ وانقر نقرًا مزدوجًا على العنوان لإعادة تسميته. وتُطوى العناوين كما تُطوى عناوين الـ gateways.
      • حذف القسم لا يحذف البوتات أبدًا — إذ تعود إلى Unassigned، ويعرض الإشعار خيار Undo. ولا يُطلب أي تأكيد.

      تُخزَّن العضوية في البيانات الوصفية لـ profile كل بوت (واسمه — مخزّن في البيانات الوصفية للـ profile لكل Bot (ui_meta)، لذا يتبع قسم Bot ذلك البوت إلى كل تطبيق Desktop متصل بذلك backend: يعيد تطبيق Desktop ثانٍ بناء عناوين الأقسام من أعضائها عند أول تحميل للقائمة، وتصل إعادة التسمية من تطبيق Desktop واحد إلى الآخرين بالطريقة نفسها. وتُحفظ قائمة الأقسام نفسها (الترتيب والأقسام الفارغة) لكل Desktop ، لذا يترك حذف قسم على جهاز واحد عنوانًا فارغًا على الآخرين حتى تحذفه هناك أيضًا. تحمل Bots المصنفة قبل إضافة الأسماء المعرّف فقط؛ ويضيف تطبيق Desktop الذي أنشأ القسم الاسم إليها تلقائيًا عند تحميل قائمته التالي، وتلتقط تطبيقات Desktop الأخرى القسم من هناك. وعندما تعرض القائمة أكثر من gateway ، تتداخل الأقسام داخل مجموعة كل gateway.

      إنشاء بوت​

      انقر New Agent في القائمة. المسار السريع ثلاثة حقول — Name, Title, الوصف — ويصبح البوت موجودًا خلال ثوانٍ، ويعرّف بنفسه في أول رسالة في محادثة Bot Chat الجديدة الخاصة به.

      يفتح القسم القابل للكشف Advanced الواجهة الكاملة للقدرات:

      • الاستنساخ من profile موجود — ابدأ من إعدادات بوت آخر ومهاراته و SOUL وذاكرته، أو اختر Fresh profile لبداية نظيفة.
      • إنشاء فارغ — تخطَّ المهارات المضمّنة بالكامل للحصول على profile بالحد الأدنى.
      • تثبيت النموذج والمزوّد — امنح Bot نموذجه الخاص. يعمل أي زوج مزوّد/نموذج يعرفه Hermes ، وتستطيع Bots مختلفة تشغيل نماذج مختلفة جنبًا إلى جنب. اتركه دون ضبط ليرث من profile الإطلاق. ويظل اختيار نموذج من محرر رسالة Bot Chat خاصًا بتلك المحادثة (يبقى بعد إعادة فتح التطبيق) حتى تغير نموذج profile البوت، الذي يتولى التحكم مجددًا.
      • ملف SOUL.md مخصص — شخصية البوت وتعليماته الدائمة.
      • التفعيل لكل مهارة، ولكل toolset ، ولكل خادم MCP — حدّد بدقة القدرات التي يحتاجها هذا البوت المتخصص.
      • نسخ مفاتيح API من الـ profile الرئيسي — مفعّل افتراضيًا. يحصل كل Bot على مخزن بيانات اعتماده الخاص: تُنسخ مفاتيح API الثابتة إليه، أما تسجيلات دخول OAuth أحادية الاستخدام (Anthropic و OpenAI Codex و xAI) فلا تُنسخ — سجّل دخول الـ Bot بنفسه باستخدام hermes -p <name> auth add <provider>. راجع تسجيلات OAuth مشتركة وليست منسوخة.

      اختيار الجهاز الذي يعيش عليه البوت ("Create on")​

      عند تسجيل أكثر من اتصال واحد في Settings → Connections، تضاف إلى نافذة New Agent أداة اختيار Create on. اختر جهازًا وسيُنشأ الـ profile على الـ backend الخاص بـذلك الجهاز — دون أن تبدّل نافذتك الـ gateway أبدًا. ثم يظهر البوت الجديد في القائمة كبوت من Connections (مع معرّف @name-device عندما يوجد الاسم على عدة أجهزة)، وتُوجَّه المحادثة معه إلى جهازه الخاص. ثم يعرض Clone from profile ما يوجد على الجهاز المستهدف — default الخاص به، أو Fresh profile — بدل قائمة هذه النافذة؛ ولا يلزم تبديل gateways لإنشاء Bot جديد في مكان آخر.

      مع وجود اتصال واحد (وهي الحالة الشائعة) تُخفى أداة الاختيار ويُنشأ البوت على الجهاز الذي أنت متصل به — تمامًا كالسلوك السابق.

      ملاحظات حول الإنشاء عن بُعد:

      • مصدر الاستنساخ هو profile على الجهاز المستهدف (الـ default الخاص به) — فالجهاز البعيد لا يملك الـ profiles المحلية الخاصة بك لاستنساخها.
      • يرتبط تبويب Capabilities الحيّ بالـ backend الخاص بالجهاز المستهدف، لذا فإن المهارات والأدوات وخوادم MCP التي تضبطها أثناء الإنشاء تُطبَّق على الجهاز الذي سيعيش عليه البوت. (أما إصدارات سطح المكتب الأقدم فتلجأ إلى قوائم تحقق مرحلية لـ Skills/Tools/MCP للأهداف البعيدة؛ وكلا الأسلوبين يقرأ كتالوج الجهاز المستهدف.)
      • إلغاء النافذة يتجاهل مسودة الـ profile على أي جهاز أُنشئت عليه.

      Edit Profile (بالنقر بالزر الأيمن على بوت) فتح الواجهة نفسها على الـ profile الحيّ في أي وقت: الصورة الرمزية، والعنوان، والوصف، وتثبيت النموذج، والمهارات، والـ toolsets ، وخوادم MCP ، وملف SOUL.md كاملًا.

      Duplicate (بالنقر بالزر الأيمن) نسخة كاملة من البوت — الإعدادات، والمهارات، و SOUL.md ، والذاكرة، ومظهره. ويزيل Delete Profile بوتًا بشكل دائم، بعد تأكيد الحذف نفسه الذي تستخدمه قائمة الـ profiles في تطبيق سطح المكتب؛ ولا يمكن حذف الـ profile الافتراضي.

      الصور الرمزية (Avatars)​

      يحصل كل بوت على وجه:

      • وجوه Blob (الافتراضي) — وجه ليّن حتمي يُرسم انطلاقًا من اسم البوت: الاسم نفسه يعطي الوجه نفسه، إلى الأبد. أثناء كتابة الاسم في New Agent يتغيّر الوجه معه مباشرةً؛ انقر Randomize لتوليد وجه جديد، أو Lock face للإبقاء على الوجه الذي أعجبك حتى لو تغيّر الاسم، أو ثبّت أحد الأشكال الستة (round ، organic ، boxy ، nub ، cloud ، sun) بينما يبقى كل ما عداه مشتقًا من الاسم.
      • وجوه هندسية — الأشكال الكلاسيكية الـ 7 × 10 ألوان. أثناء دور حيّ عليه التركيز، يميل البوت صاحب الدور وينظر إلى الأعلى مع ثلاث نقاط متحركة، ثم يعود بهدوء إلى وضع الخمول عند انتهاء الدور. وتشمل الملكية الاتصال أيضًا، فلا تستعير البوتات التي تحمل الاسم نفسه على gateways مختلفة هذه الوضعية. ويحتفظ العمّال في الخلفية بحركة العمل الحالية الخاصة بهم؛ وتحتفظ الصور ووجوه Blob والرموز (sigils) بطريقة عرضها الخاصة.
      • صورة مرفوعة — أي صورة تحبها.
      • صورة شخصية مولّدة بالذكاء الاصطناعي — عند ضبط backend للصور، تُولَّد في مكانها (يعتمد ذلك على RPC القياسي image.generate ويعمل مع الـ gateways المحلية والبعيدة على حد سواء).
      • حيوان أليف بأسلوب pixel — رفيق من معرض petdex يقفز بجوار الصورة الرمزية أثناء انشغال البوت. نفّذ hermes pets في الطرفية لاستكشاف المعرض.

      يُخزَّن مظهر البوت وعنوانه ووصفه في البيانات الوصفية للـ profile على الـ backend ، لذا يظهر البوت نفسه بالشكل نفسه على كل تطبيق سطح مكتب متصل بذلك الـ backend.

      الأصوات​

      يتحدث Bot بإعدادات TTS الخاصة بـ الـ profile الخاص به (tts.* في config.yaml لذلك الـ profile) على الـ gateway الخاص به. ويُولّد Read Aloud والنطق التلقائي والمحادثة الصوتية في محادثة Bot — في خانة مقسّمة أو مفتوحة في اللوحة الرئيسية — الصوت عبر (الاتصال، والـ profile) الخاصين بالبوت، لذا يبدو Bot اثنان بصوتين مختلفين مختلفين، ولا يتشارك Bot اثنان لهما اسم profile نفسه على gateway مختلف صوتًا مطلقًا. ويستخدم profile البوت الذي لا يملك tts.* خاصًا به إعدادات الخادم الافتراضية لذلك الـ profile ؛ ولا تستخدم صوت الـ profile النشط إلا محادثة دون مالك معروف (جلسة عادية). ويظل تحويل الكلام إلى نص في محادثة Bot يستخدم إعدادات STT للـ profile النشط.

      المهام الروتينية (Routines)​

      يربط جزء Routines يربط المهام المتكررة بالـ Bot الذي ينفذها — فتوجد "لخّص صندوق بريدي كل صباح" بجوار Bot المسؤول عنها. وتُثبّت اللوحة بجوار المحادثة فقط أثناء تفعيل تبويب Bots ، وتتنحى عند العودة إلى Sessions (وتُبقيها إصدارات Desktop الأقدم ظاهرة دائمًا). ويخفيها إغلاقها بعلامة ✕ حتى تغادر تبويب Bots وتعود إليه، فتظهر كتبويب مطوي عند الحافة اليمنى. ويبني منتقي جدول منظّم الجدول (التكرار أولًا، ثم التفاصيل المهمة فقط)، مع حقل Advanced يعرض سلسلة جدول Hermes الخام.

      المهام الروتينية ليست إلا مهام cron عادية في Hermes ضمن نطاق أسماء [bot:<name>] <routine> — وتظهر أيضًا في hermes cron list وفي صفحة Cron الأساسية. وتُسجَّل نتائج التشغيل في سجل محادثة البوت نفسه، فتكون النتيجة في المكان الذي كنت ستتحدث فيه إلى ذلك البوت على أي حال.

      المجموعات والمحادثات الجماعية​

      تنتظر الرسائل المرسلة أثناء دور أحد الأعضاء في الطابور خلف تشغيل الغرفة النشط، بما فيها الردود في السلسلة (thread) نفسها. ولا تقاطع ذلك العضو ولا تجعل الرسائل غير المشاهدة مقروءة. يلغي Stop الاستمرارات المنتظرة ويعلّق الأعضاء حتى الاستئناف: أشر بـ @mention إلى عضو معلّق، أو خاطب الغرفة كاملةً (@all … / @everyone …، بأي صياغة) لتحرير الجميع — ولا يُعدّ @all resume عبارة إلزامية بعينها. لا تعلّق stop أو halt أو pause عضوًا إلا عندما تجاور الكلمة إشارته @mention (stop @bot، أو @bot please pause)؛ أما الكلمة نفسها في موضع آخر من الجملة فتُقرأ كنص عادي، ولذلك لا تعود الكلمة الألمانية halt تُسكت البوت الذي أُرسلت إليه — لكن هذه الرسالة لا تحرّر أيضًا عضوًا معلّقًا (فالرسالة @bot please just stop now لا توقظه أبدًا؛ كرّر كلمة التوقف بجوار الإشارة لتعليقه). كلمات التوقف داخل كتل الكود المسوّرة (fenced code) أو الكود المضمّن أو الاقتباسات أو أسطر blockquote هي محتوى، لا توجيهات، ولا تعلّق أحدًا أبدًا. ويتلقى العضو المعلّق الرسائل التي تجاوزها تعليقه — بما فيها الرسالة التي سبّبته — في أول دور له بعد التحرير، فلا تضيع أي رسالة موجّهة إليه. أما الغرف التي لا تستخدم "stop" كأمر فيمكنها تعطيل Detect stop directives في مربع حوار إعدادات المجموعة؛ ويظل زر Stop يلغي التشغيل النشط في كلتا الحالتين. يحتفظ العضو الذي يظهر أنه لا يزال يعمل بدوره لمدة تصل إلى 3 ساعات (أما العضو الذي يتوقف عن الإبلاغ عن عمله فتنتهي مهلته بعد 3 دقائق من الصمت مهما كان الحال)؛ ثم تراقب الغرفة الهادئة الأعضاء الذين انتهت مهلتهم 3 ساعات إضافية بعد انتهاء الانتظار الأمامي، ولا تمدّد نافذة المراقبة هذه الدور نفسه. تظل إخفاقات الأعضاء غير المعالجة ظاهرةً في ملخص Activity المطوي بعد استقرار الغرفة — بما فيها الدور الذي أخفق فيه backend العضو نفسه (بيانات اعتماد غير صحيحة، أو أخطاء المزوّد)، ويُبلَّغ عنه لحظة إبلاغ gateway به بدلًا من أن يبدو كأنه عشرون دقيقة من التفكير. يسمّي صف الإخفاق سببه: builder hit an error — <first line of the error> (مع تنقيح tokens الشبيهة بالأسرار وبتر الأسطر الطويلة). وسّع Activity لترى تسلسل الأدوار؛ وخاطب العضو من جديد لإعادة المحاولة. ولا يُعاد تلقائيًا إرسال إخفاق إرسال ملتبس (ambiguous submit failure).

      انقر بزر الفأرة الأيمن على Bot محلي → Manage groups لإضافته إلى أي عدد من المحادثات الجماعية أو إزالته منها. اختر مجموعات موجودة بصورة مستقلة أو أنشئ واحدة في الموضع نفسه. تُخزَّن العضوية المحلية في بيانات الـ profile الوصفية الخاصة بالـ Bot والمتزامنة مع backend، فتتبع ذلك الـ profile عبر أجهزة سطح المكتب؛ وتظل الـ profiles الأقدم ذات المجموعة القديمة الواحدة تعمل. تنضم Bots الخاصة بـ Connections عبر منتقي New Group Chat وتظل هويتها مرتبطة بالمصدر في الحالة المشتركة للغرفة. أما المجموعات التي يديرها gateway واحد فتعرض Bots الاتصال النشط فقط، بينما قد تحتفظ غرف Desktop الأقدم بأعضاء من اتصالات مختلطة.

      لتحرير غرفة موجودة كوحدة واحدة، استخدم Manage members — من أيقونة الأشخاص في رأس الغرفة أو زر Manage members… في Group settings. تحدد قائمة الاختيار الأعضاء الحاليين مسبقًا وتسرد كل Bot محلي وكل Bot من Connections؛ أضف عدة أعضاء أو أزلهم معًا، ثم يطبّق Save members القائمة الجديدة (تظل من 2 إلى 6 Bots)، مع بقاء الغرفة وسجلها وجلسة الغرفة الخاصة بكل عضو. لا يأخذ Bot مُزال أدوارًا لاحقة؛ ويقرأ Bot مضاف سجل الغرفة الحديث في دوره الأول. ولا يغير Cancel شيئًا.

      يحمل دور كل عضو كل رسائل الغرفة منذ دوره السابق — حتى نحو 200 رسالة أو 32,000 حرف من النص، أيهما يمتلئ أولًا — وتُختصر الرسالة الواحدة المفرطة الطول إلى مقتطف موسوم من 8,000 حرف (يخزّن سجل الغرفة المقتطف نفسه)، بدلًا من مزاحمة الرسائل المحيطة بها؛ وإذا ظلت النافذة تتجاوز الحد، يحدد الـ prompt بالضبط عدد الرسائل السابقة التي أُغفلت.

      تتبع الغرف gateways الخاصة بك، لا تطبيق Desktop واحدًا.تُعكس الرسائل الحديثة لكل غرفة وأعضاؤها وصورتها واسمها في بيانات profile الوصفية المشتركة لـ كل gateway يتصل بها Desktop، مع ترقيم إصدارات لكل gateway بحيث تُدمج كتابات تطبيقي Desktop المتزامنة بدلًا من استبدال بعضها. افتح Hermes Desktop على جهاز آخر متصل بـ gateway نفسها (شبكة محلية، أو Tailscale، أو أي مكان)، فتظهر الغرفة بسجلها؛ ويراها أيضًا العملاء المتصلون بـ gateway فقط. تحمل الغرف هوية داخلية دائمة، ولذلك لا تغير إعادة التسمية إلا اسم العرض في كل مكان، ويزيل حلّ الغرفة وجودها نهائيًا من كل عميل — حتى العملاء الذين كانوا غير متصلين وقتها؛ ويتذكر Desktop عمليات الحلّ التي نفذها، فلا تستطيع gateway التي لم يصل الحذف إلى نسختها إعادة الغرفة — ويبدأ إنشاء مجموعة بالاسم نفسه غرفة جديدة فعلًا. وإذا تعطلت gateway أو أُزيلت، فلا يضيع شيء: يحتفظ كل Desktop متصل بالغرفة كاملةً محليًا ويعيد تزويد أي gateway يتصل بها مجددًا بنسختها. (يظل سجل التنسيق الكامل في التخزين المحلي لكل Desktop؛ أما المرآة المشتركة فهي إسقاط محدود للسجل الحديث.)

      يمكن تحرير هوية المجموعة عند إنشائها وبعد ذلك:

      • New Group Chat يتيح لك ضبط صورة للغرفة اختيارية إلى جانب الاسم — ارفع واحدة من جهازك أو ولّدها (عندما يكون image backend مضبوطًا)، باستخدام pipeline الصور الرمزية للبوتات نفسها. تظهر الصورة في صف القائمة (بدلًا من رمز المجموعة الافتراضي) وتسبق العنوان في رأس الغرفة.
      • يفتح زر الترس في رأس الغرفة Group settings، حيث يمكنك إعادة تسمية المجموعة أو ضبط صورتها أو استبدالها أو إزالتها في أي وقت. تنتقل كل العناصر مع إعادة التسمية — سجل الغرفة، وجلسة الغرفة لكل عضو، والعضويات، والصورة — فلا يُفقد أي سجل. ويُرفض تغيير الاسم إلى اسم مستخدم بالفعل بدلًا من إلحاق لاحقة به بصمت.
      • Group settings تسرد أيضًا كل عضو مع زر Compress history. يحتفظ كل عضو بجلسة مخفية خاصة بالغرفة تنمو مع كل دور؛ وعندما تكبر بما يكفي، يبدأ العضو الإجابة بردود فارغة (The model returned no response after processing tool results). يشغّل Compress history ضغط السياق نفسه الذي ينفّذه /compress على تلك الجلسة المخفية — التي لا يمكن الوصول إليها من الشريط الجانبي أو مربع كتابة الغرفة — ويعرض عدد الرسائل المطوية. اضغط عضوًا واحدًا في كل مرة؛ ولا يُمس سجل الغرفة نفسه.

      المجموعات صفوف مستقلة في القائمة المرتبة حسب النشاط نفسها التي تضم الرسائل المباشرة مع Bots. يحتفظ Bot بصف رسالة مباشرة واحد حتى إذا انضم إلى عدة مجموعات، بينما تحصل كل مجموعة على صف غرفة خاص بها يضم عدد الأعضاء، ومعاينة أحدث رسالة، والطابع الزمني، وحالة الاحتياج إليك.

      يمكن تنظيم صف الغرفة مثل صف Bot. انقر عليه بزر الفأرة الأيمن → Pin to top لإبقاء غرفة تستخدمها يوميًا فوق Bots والغرف غير المثبتة (يعيدها Unpin إلى ترتيب الحداثة)؛ ويُحفظ التثبيت مع الغرفة على Desktop هذا. انقر بزر الفأرة الأيمن → Move to section لوضع الغرفة في أحد أقسامك — أو اسحب الصف إلى عنوان قسم — ويعيدها Remove from section إلى فئة المحادثات الجماعية. يُخزَّن قسم الغرفة في سجلها (لا تملك الغرف profile)، فيظل محليًا لهذا Desktop مثل قائمة الأقسام نفسها.

      يبدأ مربع الكتابة في الغرفة (ومربع الرد داخل السلسلة) كسطر واحد ويتمدد عندما يلتف الـ prompt أو تُضاف فواصل أسطر عبر Shift+Enter، حتى نصف النافذة (بحد أقصى 24rem)؛ ثم يصبح قابلًا للتمرير داخل المربع ليحتفظ سجل المحادثة بمساحته. يرسل Enter الرسالة.

      استخدم سهمي Move up و Move down بجوار الغرفة لاختيار موضعها بين الغرف. حتى أول نقل، لا يتغير الترتيب الحالي: المثبتة أولًا، ثم النشاط الأحدث. بعد النقل، يُحفظ ترتيب الغرف على Desktop هذا ويستمر بعد إعادة التحميل؛ وتتبع الغرف الجديدة الغرف المرتبة صراحةً ضمن فئتها المثبتة أو غير المثبتة. لا يمكن للنقل عبور حد التثبيت، ولا تؤدي التصفية إلى حذف الغرف المخفية من الترتيب المحفوظ. تعيد هذه العناصر ترتيب غرف Group Chat الفعلية، لا مجلدات Bots التي أنشأها المستخدم، ولا تغيّر العضوية أو ملكية gateway.

      Open chat على أي صف مجموعة (من 2 إلى 6 Bots) يفتح غرفة مشتركة ينسّق فيها كل أفراد المجموعة:

      • محادثة واحدة مرئية. تظل الرسائل العامة ورد كل عضو مقروءة بترتيب وصولها، مع اسم المتحدث والطابع الزمني. ولا يؤدي بدء موضوع آخر إلى طي الردود السابقة. يواصل Reply in thread ذلك الموضوع دون إعادة ترتيب الغرفة؛ أما Activity فهو عرض ثانوي للحالة، لا بديل للرسائل. وتظل محادثات Bot Chat الخاصة منفصلة.

      • تطلق رسالتك ما يصل إلى 3 جولات متتابعة من أدوار الأعضاء. تستجيب Bots المشار إليها بـ @mention (ويستجيب الجميع عندما لا يُشار إلى أحد)؛ ويجيب كل Bot بإيجاز أو يتجاوز دوره، وتستقر الغرفة عندما تمر جولة كاملة بصمت.

      • يمكن لزملاء الفريق تسليم المهمة إلى Bot الأساسي عبر @hermes، بما في ذلك الغرف المحفوظة الأقدم؛ وتحتفظ Bots على gateways الأخرى بإشاراتها المؤهّلة باسم الجهاز (مثل @default-vera).

      • تستدعي Bots بعضها باستخدام @name، وتصعّد إليك القرارات التي تحتاج فعلًا إلى حكم بشري باستخدام @user — ويعرض صف المجموعة شارة needs you حين يحدث ذلك. تضيء الشارة أيضًا للأسئلة وموافقات الأوامر المعلّقة؛ ولا يؤدي حل آخر prompt إلا إلى إزالة تنبيه ذلك الـ prompt، لا إشارة مستقلة. تجيب الموافقة على أمر داخل الغرفة بمجرد النقر — ترسل once، و session، و always، أو deny فورًا دون زر ثانٍ تبحث عنه. تتبع prompts الغرفة عند إعادة تسميتها، بينما يلغيها حل الغرفة حتى إذا وصل استطلاع عضو قيد التنفيذ لاحقًا.

      • تمنع الحدود الصارمة (10 رسائل لكل إرسال، و 3 جولات) الغرف من الدوران بلا نهاية.

      • يحتفظ كل عضو بجلسة غرفة دائمة خاصة به، ولذلك يستمر سياق الغرفة مثل أي محادثة أخرى.

      • لا يرد كل Bot على كل رسالة. يختار كل عضو التحدث بنفسه — فلا يجيب Bot إلا إذا كان لديه جديد يضيفه، ويتجاوز دوره خلاف ذلك؛ وتقتصر الجولة على الأعضاء المحددين عند الإشارة إليهم بـ @mention. توقع كلام من خاطبتهم (أو من لديه شيء يقوله)، وصمت الباقين.

      • تستمر الغرف في العمل عند إغلاق Desktop. عندما يكون كل أعضاء الغرفة على gateway واحد، يتولى ذلك الـ gateway جدولة الأدوار عبر مشغّل (driver) دائم: لا يؤدي إغلاق Hermes Desktop (أو فقد اتصاله) إلى إيقاف الغرفة وسط النقاش، ويلحق Desktop ببساطة بسجل الغرفة عند إعادة الاتصال. يُبلغ groups.capabilities على gateway عن driver: true عندما ينطبق ذلك. وقد يشارك أكثر من عامل غرفة (room worker) مجلد home واحدًا — فكلٌّ من gateway المضيف الذي يتصل به Desktop (hermes gateway run) و backend الخاص بـ hermes serve / hermes dashboard يشغّل واحدًا — ويشغّل الدور التالي من يملك عقد (lease) مشغّل الغرفة؛ ولا تُحجز جلسة الغرفة الخاصة بالعضو إلا طوال دوره، فيمكن انتقال العقد بين العمال دون رفض أي دور. توجد حالة الغرفة في shared-state.db في جذر التثبيت؛ وتحصل التثبيتات التي أنشأت غرفًا قبل وجود ذلك الملف (حين كانت الغرف لا تزال محفوظة في state.db الجذر) على نسخة من تلك الغرف مرة واحدة، عند أول فتح بعد التحديث، فتظل Group Chats الموجودة سابقًا قابلة للوصول. وتختلف الغرف القديمة التي تمتد عضويتها عبر عدة أجهزة: إذ تعمل أدوار كل عضو على gateway الخاص به، وينطبق على تلك الغرف الناقل (courier) العابر للاتصالات الموضح تحت Bot-to-bot messaging.

      • تُقرأ الإشارات كهويات. تظهر إشارة @bot الموجّهة، وإحالة المهمة إلى الإنسان عبر @user، والبث إلى @everyone / @all في سجل المحادثة كمراجع مضمّنة (نص مميز، لا شارات كبسولية)؛ وتظل @words غير المعروفة وعناوين البريد نصًا عاديًا. مرّر المؤشر فوق رسالة Bot واستخدم Reply to @handle لوضع @handle في مربع الكتابة، فتذهب رسالتك التالية إلى ذلك Bot وحده (عندما يشارك الغرفة Bot من Connection بالاسم نفسه، تُؤهَّل الإشارة باسم الجهاز، مثل @reviewer-mini / @reviewer-local) — ويظل Reply in thread يواصل السلسلة كاملة. وإذا كان مربع رد لسلسلة مختلفة مفتوحًا، يضع Reply to الإشارة في مربع الكتابة الرئيسي بدلًا منه، فيبدأ سلسلة جديدة؛ استخدم Reply in thread لمواصلة تلك السلسلة.

      • يمكن أن تمتد الغرف عبر أجهزة. يتحقق New Group Chat من كيفية تشغيل gateway النشط للغرف الجماعية قبل عرض الأعضاء. المجموعات التي يديرها gateway واحد تعرض Bots الاتصال النشط فقط، بحيث يمكن لذلك الـ gateway الوصول إلى كل عضو مختار. وتحتفظ غرف Desktop الأقدم بالاختيار من اتصالات مختلطة؛ ويحمل هؤلاء الأعضاء شارة جهاز (dixie · Mac Mini) في الغرفة وفي سجلات الأعضاء الآخرين، وتعمل أدوار كل عضو على جهازه وفي جلسة غرفته. ينتهي دور العضو الذي يستمر بعد توقف Desktop هذا، لأنك أغلقته أو تعطل أثناء الدور، على جهاز العضو نفسه: تنشر الغرفة ذلك الرد عند تشغيلها التالي، ولا تعيد تشغيل العضو بينما لا يزال يعمل.

      • تعرض الغرف الهوية نفسها المعروضة في القائمة. تحدد صفوف سجل المحادثة وسطر “X is thinking…” وصفوف Activity عنوان كل عضو وصورته الرمزية بحسب الاتصال و profile المالكين له — ويحدّث تغيير عنوان Bot أو صورته كل غرفة يشترك فيها؛ ويحتفظ الأعضاء البعيدون بعناوينهم الخاصة، ولا يستعير Botان بالاسم نفسه على اتصالين مختلفين صورة أحدهما. وإذا بقي عضوان متطابقين في العرض، يضيف Activity تسمية الاتصال (Reviewer · Mac Mini).

      • يمكن للإضافات مراقبة عمل الأعضاء. يسجل سجل الغرفة الدائم turn.started و turn.settled؛ أما ما يفعله العضو بينهما (الأدوات، والموافقات، والنص المتدفق)، فيُعرَض للإضافات عبر on_room_member_activity مع إحداثيات الغرفة والعضو والدور، ليستطيع عملاء المجتمع بناء بطاقات أدوات وحالة أعضاء مباشرة فوق Group Chat دون قراءة آليات Hermes الداخلية.

      • يصل إلى الغرفة أيضًا ما يقوله العضو خارجها. جلسة الغرفة لكل عضو جلسة Hermes عادية (بعنوان Group: <room> · <thread>)، لذلك يمكنك استئنافها من CLI، أو يمكن لروتين النشر فيها، أو لأدوات Bot نفسه الكتابة إليها. عند فتح الغرفة، وفي كل مرة تشغّل فيها ذلك العضو، يُنشر كل ما أضافه أولئك الكتّاب منذ آخر فحص للغرفة — أسئلتك وإجابات العضو — في سجل الغرفة باسم ذلك العضو مرة واحدة، وفي السلسلة التي تنتمي إليها الجلسة؛ ولا تكرره إعادة تشغيل النافذة. لا تُكرر prompts أدوار الغرفة نفسها وردودها بهذه الطريقة مطلقًا، ولا صفوف صيانة الوكيل (ملاحظات ضغط السياق، وتسليم الروتينات، ونتائج التفويض) ولا استجابات العضو لها. تبدأ الغرفة مراقبة الجلسة عند رؤيتها لأول مرة: لا يُعاد عرض ما كان في الجلسة قبل ذلك، ولذلك لا تعيد الغرفة المستعادة على Desktop ثانٍ نشر سجل أعضائها.

      المراسلة بين الـ Bots​

      تتراسل الـ Bots فيما بينها مع نسبة كل رسالة إلى مُرسِلها، ويمكنك تسليم العمل من أي محادثة:

      • @mentions — اكتب @researcher have a look at this في أي محادثة، وسيساعدك الإكمال التلقائي لـ @ في مربع الكتابة (composer) على اختيار الـ Bot المناسب؛ وعند الإرسال تُطابَق الإشارة مع قائمة الأعضاء (roster) الحية، ويُبلَّغ الـ Bot النشط بدقة بمن تقصده (الـ profile، والاسم المألوف، والجهاز بالنسبة إلى الـ Bots الموجودة على اتصالات أخرى). ثم يصوغ الـ Bot رسالته بنفسه ويرسلها باستخدام message_agent — لا يُمرَّر نصك حرفيًا أبدًا، ويعود الرد منسوبًا إلى ذلك الوكيل. أما عنوان البريد الإلكتروني أو @ غير المعروف فيمرّ دون أي تغيير. ويمكن الوصول إلى الـ Bots على الأجهزة المتصلة الأخرى بالطريقة نفسها: إذ يمرّر Desktop الرسالة عبر الـ socket الخاص بذلك الاتصال (راجع الـ Bots عبر الأجهزة أدناه).
      • تبقى وسوم الـ Bots المُعاد تسميتها متزامنة — امنح الـ Bot اسمًا مألوفًا (عبر أيقونة القلم في ترويسة محادثته، أو hermes profile rename) ليصبح بالإمكان الإشارة إليه بذلك الاسم: فالـ Bot المسمّى Research Buddy يستجيب لـ @research-buddy (و @researchbuddy أيضًا)، في المحادثات العادية وفي غرف المجموعات على حد سواء. ويقترح الإكمال التلقائي لـ @ يعرض الإكمال التلقائي الوسم المعاد تسميته، ويطابق أيضًا عند كتابة اسم profile القديم، الذي يظل يعمل. يشمل ذلك البوت الأساسي: سمّه Maia وستقدّمه prompts أدوار المجموعة باسم @maia ، وتوقّع رسائله بين الوكلاء باسم Message from 🤖 Maia (@hermes) ، ويمكن للزملاء message_agent(target="maia") عليه — وتبقى @hermes اسمًا بديلًا صالحًا.
      • تظهر Bots البعيدة في الإكمال بعناوينها، من أي محادثة. يسرد الإكمال التلقائي لـ @ Bots على أجهزتك الأخرى المتصلة بمجرد اتصال Desktop — لا تحتاج إلى فتح لوحة Bots أولًا — وتظهر default البعيدة تحت عنوان Bot Mode الخاص بها (@cos-bot لـ default بعيد بعنوان CoS Bot، لا كـ @hermes ثانية). عندما تتطابق وسوم بوتين، يُدرج المنتقي الصيغة المقيّدة بالاتصال (@cos-bot@<connection>)، التي تحدّد بوت ذلك الجهاز بالضبط. تظل الرسالة المرحّلة الموقّعة Message from 🤖 hermes (@hermes@<connection>) تُعرض كإشعار وكيل، لا كنص منك.
      • الرسائل المباشرة — تتضمن كل Bot Chat الأداة message_agent: يراسل الـ Bot زميلًا له باستدعاء message_agent(target="researcher", message="…"). الهدف اسم profile الزميل أو اسمه الودّي (hermes profile rename أو عنوان Bot Mode — Scribe, Dr. Foo) أو وسم @ الذي يدرجه Desktop له (@scribe, @dr-foo, @drfoo); @hermes تعني دائمًا البوت الأساسي. يُطابق اسم profile أولًا، فلا يمكن لاسم بوت ودّي آخر اختطافه؛ ويُرفض الاسم الودّي المشترك بين بوتين مع عرض القائمة بدلًا من التخمين. تتحقق الأداة من الهدف مقابل قائمة الزملاء الحيّة، وتسبق الرسالة تلقائيًا بنسبة Message from 🤖 <friendly name> (@<handle>): للمرسل، وتسلّم إلى Bot Chat المعتمدة للزميل. التسليم fire-and-forget: يتلقى المرسل إقرار إرسال (status: queued مع delivery_id — و process_id لعملية التسليم الخلفية — يعني أن الرسالة سُلّمت لتلك العملية، لا أنها وصلت)، وينهي دوره، ويحمل إشعار اكتمال العملية النتيجة — الرد أو فشل التسليم. في الواجهات التي لا يمكنها استقبال إشعارات الاكتمال (جلسة api_server أو مشغّلات المرة الواحدة)، يحمل الإقرار بدلًا من ذلك reply_delivery: poll: يسترد المرسل النتيجة باستخدام process(action="wait", session_id=…) قبل إنهاء دوره، وتُحفظ النتيجة أيضًا في نص جلسة المرسل كصف تسليم عند خروج العملية، فلا يُفقد الرد بصمت. يحمل الإشعار الرد كاملًا حتى حد حجم الرسالة (16,000 حرف)؛ ويصل الرد الأطول كذيله مع ذكر مقدار الاقتطاع (تحتوي process(action="log", session_id=…) على الباقي). تنتقل الرسالة كمعامل حقيقي (لا يفسّر الـ shell شيئًا — علامات الاقتباس و $(...) و backticks تصل حرفيًا)، ويصوغ الـ Bot رسالته بنفسه بدلًا من تمرير كلماتك. وتشكّل قائمة زملاء الفريق — الأسماء والأدوار المأخوذة من عنوان/وصف كل profile — جزءًا من system prompt لكل Bot Chat، بحيث تعرف الـ Bots من يتولى ماذا قبل اختيار المستلم. لا توجد هذه الأداة إلا في جلسات Bot Chat الأساسية على التثبيتات التي يديرها Bot Mode؛ أما المحادثات العادية، وجلسات الأعضاء في غرف المجموعات، وجلسات CLI فلا تراها أبدًا.

      تصل الرسائل المحلية أيضًا إلى Bot Chat تبقى مفتوحة في Desktop أو في TUI. يحتفظ الـ backend المستقبِل بالملكية: فهو يقرأ الوارد الدائم (durable ingress) عبر أداة استطلاع الإشعارات (notification poller) الموجودة لديه، ويقبل الرسالة فورًا إن كان خاملًا، أو ينتظر حتى ينتهي الدور الجاري والـ prompts البشرية الموجودة مسبقًا في قائمة الانتظار. إشعار الاستلام queued يؤكد القبول الدائم، لا اكتمال الرد. ويحتفظ الـ profile الهدف بمعرّف التسليم وإيصاله ضمن runtime/bot_live_delivery/; settled فتؤكد الاكتمال. لا يُعاد تشغيل الدور المستورد تلقائيًا إذا تعطّل أو أُلغي، ويبقى العمل المعلّق المرتبط بمالك غادر قابلًا للفحص بدلًا من إعادة تشغيله بصمت. لا تُعِد إرسال تسليم نتيجته غير معروفة. تحتفظ الـ backends الأقدم التي تفتقر إلى قدرة التسليم المباشر (live delivery) بسلوك رفض الملكية الحالي؛ أعد تشغيل ذلك الـ backend بعد الترقية.

      • البقاء صامتًا — يمكن لبوت ليس لديه ما يضيفه إنهاء دور بإحدى tokens الصمت المتعمّد ([SILENT], NO_REPLY ، …). تحتفظ Bot Chat بذلك الدور في نصها المسجّل لكنها لا تعرض شيئًا، ويحصل الزميل الذي راسله على رد فارغ بدلًا من token. تُعرض الأدوار الفاشلة والنثر الذي يذكر token فحسب كما هي.

      يُعلّم الـ backend جلسة Bot Chat الأساسية لكل Bot بروتوكول المراسلة تلقائيًا عند بناء الـ prompt — بما في ذلك عندما يفتحها زميل دون واجهة (headless) من CLI. لا تحصل على قسم البروتوكول إلا Bot Chat الأساسية؛ وتبقى جلساتك العادية وملف SOUL.md الخاص بك دون أي تعديل. يتحكم في ذلك الخيار agent.bot_mode_protocol في config.yaml (القيمة الافتراضية: مفعّل):

      agent:
        bot_mode_protocol: true   # inject the bot-to-bot messaging protocol into canonical Bot Chats

      ما الذي يجعل المحادثة Bot Chat فعلًا​

      agent.bot_mode_protocol هو المفتاح الرئيسي فقط. قبل حقن قسم البروتوكول — أو أداة message_agent — يجب تحقق شرطين آخرين، وفي تثبيت Desktop تلبي لوحة Bots كليهما فور إنشاء بوت:

      1. عنوان الجلسة يساوي تمامًا Bot Chat. العنوان الدقيق هو هوية المحادثة المعتمدة (تستخدمه createCanonicalChat لإضافة Desktop، ويستأنفه hermes -p <bot> chat -c "Bot Chat")؛ أي عنوان آخر أو جلسة تجريبية بلا عنوان لا تحصل على القسم ولا الأداة.
      2. profile واحد على الأقل في التثبيت يحمل كتلة ui_meta: { hermes-bots: … } في profile.yaml. هذه علامة "Bot-Mode-managed" التي تكتبها إضافة Desktop لكل بوت تملكه؛ تفحص البوابة كل profiles، لذا يوسم profile معلَّم واحد التثبيت كله. لا يوجد أمر CLI يكتبها.

      النتيجة العملية: في تثبيت دون واجهة أو تطبيق Desktop (مثل gateway مع Telegram)، لا يكتب شيء أي العلامتين، لذا فإن message_agent غير متاح حتى مع تفعيل المفتاح في التوثيق — تتراسل البوتات جيدًا عبر منصة المراسلة، لكن أداة message_agent جهة الوكيل لا تظهر مطلقًا. لتفعيلها دون واجهة، حقّق الشرطين يدويًا:

      # the canonical forever-chat, created once per Bot (later runs resume it)
      hermes -p <bot> chat -c "Bot Chat" --create-if-missing
      # ~/.hermes/profiles/<any-bot>/profile.yaml — an empty block is enough to mark the install
      ui_meta:
        hermes-bots: {}

      من الدور التالي في Bot Chat تلك، تُلتقط قائمة الزملاء وقسم البروتوكول و message_agent كلها — بما في ذلك عبر hermes -p <bot> chat على جهاز طرفية فقط.

      ملاحظة

      التسليم بين البوتات خاص بكل استدعاء: يلتقط البوت المستقبِل الرسالة عند تشغيله التالي. المقاطعة الحيّة لبوت وسط المحادثة عمل مستقبلي.

      إعادة محاولة الأدوار الفاشلة بأمان​

      يحافظ التسليم المحلي لمرة واحدة (one-shot) على رمز رفض الجلسة النشطة منفصلًا عن رسالته المقروءة للبشر. ينتج SESSION_NOT_OWNED الرمز target_busy ؛ ولا يُوسَم سجل التنسيق (coordination registry) غير القابل للقراءة خطأً على أنه مالك آخر. أما إصدارات CLI المحلية الأقدم التي لا تحمل علامة الرمز فلا تزال تستخدم صياغة الرفض القديمة.

      يُعاد تنفيذ دور التسليم الفاشل مرة واحدة على الأكثر، وفقط عندما يمكن لإعادة المحاولة أن تفيد فعلًا. فالإخفاقات العابرة (بيئة التشغيل الهدف غير متصلة، أو انتهاء مهلة التسليم، أو حدّ المعدل (rate limit) لدى المزوّد، أو خطأ في الخادم) تعيد تشغيل جلسة Bot Chat نفسها دون تغيير. كذلك يعيد إخفاق تجاوز السياق (context overflow) تشغيل الجلسة نفسها — إذ يضغط الدور المُعاد السجلَّ (transcript) الذي تجاوز الحد عبر مرحلة ضغط السياق المعتادة قبل استدعاء النموذج، فتتسع إعادة المحاولة حيث لم يتسع الدور الأصلي. أما إخفاقات المصادقة والحصة (quota) والإعدادات فلا يُعاد تنفيذها تلقائيًا أبدًا: فالمحاولة الثانية لا تستطيع إصلاحها ولا تفعل سوى استهلاك الحصة، لذا يُعرض الإخفاق فورًا. ولا يبدأ الدور المُعاد جلسة جديدة أبدًا — يبقى سجل Bot Chat وسياقها سليمين.

      عندما لا يكون للهدف مالك Desktop أو TUI حي، يفتح التسليم المحلي Bot Chat المعتمدة لذلك profile عبر دور CLI هادئ. يفضّل النقل نقطة دخول Hermes بجانب مفسّر Python لوقت تشغيل المرسل، فلا تستطيع نسخة hermes غير مرتبطة أو أقدم على PATH للخدمة التقدم عندما توجد نقطة الدخول المجاورة. يختار --in ~ مجلد العمل؛ ويُحدّد عنوان Bot Chat الصريح في قاعدة جلسات profile الهدف.

      عند فشل التسليم: أسباب مصنّفة​

      يحمل دور الـ Bot الفاشل أو التسليم الفاشل عبر الـ relay رمز reason قابلًا للقراءة آليًا إلى جانب نص الخطأ المقروء للبشر، من البداية إلى النهاية: يصنّف الـ gateway الهدف الإخفاق (provider_auth_or_access, provider_quota_limit, provider_rate_limit, provider_server_error, context_overflow, missing_config, model_unavailable, runtime_offline, queued_expired, delivery_timeout, target_busy, unknown)، ويمرّره Desktop، ويُوسَم إشعار الاكتمال لدى الوكيل المُرسِل بـ [reason: <code>] قبل نص الخطأ. يمكن للوكيل المستدعي أن يتفرّع بحسب الرمز — "سجّل الدخول مجددًا" مقابل "أعد المحاولة لاحقًا" — بدلًا من تحليل النص الوصفي الصادر عن المزوّد. وتستخدم شارة needs-attention (يحتاج إلى انتباه) في Desktop الرموز نفسها.

      المراسلة عبر الأجهزة المتصلة (Desktop relay)​

      كل gateway تسجّله في Settings → Connections — محليًا كان، أو عبر URL بعيد، أو SSH، أو Hermes Cloud، أو docker — هو خط اتصال دائم يُبقيه Desktop مفتوحًا، ويستخدم Bot Mode هذه الخطوط للمراسلة تلقائيًا. دون أي إعداد إضافي:

      • تنتشر قوائم الأعضاء من تلقاء نفسها. أثناء عمل Desktop، يُبلغ دوريًا كل gateway متصل بالوكلاء الموجودين على الاتصالات الأخرى. عندها تدرجهم قائمة زملاء الفريق في كل Bot Chat ("Teammates on OTHER connected machines")، مع أسمائهم وأدوارهم والجهاز الذي يعملون عليه — وتتحدّث القائمة عندما يظهر وكلاء أو يختفون أو تُغيَّر أسماؤهم (capability epoch).
      • message_agent إليهم مباشرةً. يراسل الـ Bot الموجود على حاسوبك المحمول الوكيلَ السحابي باستخدام message_agent(target="moxie", …) تمامًا كما يراسل زميلًا محليًا. وإذا وُجد المعرّف (handle) نفسه على عدة أجهزة، فأزِل الالتباس باستخدام target="moxie@<connection>" (يخبر خطأ الأداة البوت بالصيغ الدقيقة). يُسرد كل زميل باسم الجهاز من Settings → Connections، فيقرأ البوت @moxie on Homelab بدلًا من معرّف اتصال مجرد. يمر التسليم عبر Desktop: يضع gateway المرسل الرسالة في الصف، ويرحّلها Desktop إلى gateway اتصال الهدف، وينفّذ البوت الهدف دورًا في Bot Chat المعتمدة — كدورها التالي عندما تكون مفتوحة في Desktop — ويعود الرد للمرسل بإشعار الاكتمال الخلفي نفسه المستخدم للرسائل المباشرة المحلية (العملية المنتظرة له نقطة دخول Hermes، فتبدأ تحت approvals.single_query_mode: deny — الافتراضي لدور رد البوت لمرة واحدة — أيضًا؛ أما المحادثة المفتوحة التي لم تجب ضمن ميزانية التسليم الحي فتذكر بدلًا من ذلك أن الرسالة في صفها؛ لا تعِد الإرسال). تُسلّم رسائل Bots مختلفة بالتوازي، فلا يؤخّر دور طويل لبوت بريد بوت آخر (ولا يجعل عمره يتجاوز bot_mode.envelope_ttl_seconds)؛ وتُسلّم الرسائل إلى البوت نفسه بالترتيب، دورًا واحدًا في كل مرة.
      • Desktop هو الناقل. يعمل التسليم بين الاتصالات ما دام Desktop يعرف الاتصالين ويعمل (فهو يحتفظ بالمقابس وبيانات الاعتماد — لا ترى gateways مصادقة بعضها). إذا أُغلق Desktop وسط التسليم، يُخبر بوت المرسل أن الرد لم يصل بدلًا من تركه معلّقًا؛ والرسالة التي التقطها Desktop ولم يسلّمها للهدف (انقطع بينهما) تُعرض مجددًا في التفريغ التالي — مرة واحدة، وفقط بعد انقضاء مهلة تسليم Desktop الخاصة (نحو 26 دقيقة) دون رد، فلا يُسلَّم دور بطيء لكنه حي مرتين. ينتظر المرسل مدة تكفي لإتمام التسليم الثاني (نحو 52 دقيقة إجمالًا)؛ وإذا لم يصله رد بعد ذلك يُخبر بالسبب delivery_timeout. بينما تنتظر الرسالة المعروضة مجددًا التفريغ، ينطبق bot_mode.envelope_ttl_seconds عليها كما على رسالة جديدة في الصف تمامًا، وأول رد مسجّل للرسالة هو المعتمد. للمراسلة الدائمة بين الأجهزة دون Desktop في المسار، سجّل peer (hermes peer ، أدناه) — ويمكن للمسارين أن يتعايشا.
      • قيمة default البعيدة تُعرف بعنوانها. قيمة default لكل جهاز هي @hermes ، لذا تُعرض النسخة البعيدة — ويمكن الوصول إليها — تحت عنوان Bot Mode بدلًا من ذلك (نسخة default البعيدة بعنوان CoS Bot هي @cos-bot ؛ ودون عنوان، hermes@<connection>)، وتصل الرسالة المباشرة التي ترسلها موقّعة بصيغة الرد الآمنة نفسها، لا بـ @hermes مجردة تشير إلى default الخاص بك.
      • يحد سقف 10 دقائق دور الهدف، لا إحالاته. تمنح الرسالة المرحّلة البوت الهدف 10 دقائق لإكمال دوره. عندما يراسل ذلك الدور زميلًا بنفسه، تبقى عملية التسليم حيّة بعده — بحد terminal.oneshot_completion_wait_seconds — ليصل رد الزميل إلى Bot Chat الخاصة به (ويصبح، إذا وصل في الوقت المناسب، الرد المرحّل عائدًا). لا يُحتسب الانتظار ضمن السقف مطلقًا: يُبلغ المرسل بإجابة الدور المكتمل، لا بكونه delivery_timeout ، وتُترك إحالته لتكتمل.

      رسائل مباشرة يبدؤها الـ Bot عبر الأجهزة (hermes peer)​

      يمكن للـ Bots على جهاز ما مراسلة الـ Bots الموجودة على gateway جهاز آخر دون وجود أي Desktop في المسار. سجّل الـ gateway الآخر بوصفه peer (نظيرًا) (عنوان URL لخادم API الخاص به + API_SERVER_KEY):

      hermes peer add spark --url http://spark.lan:8377 --key <API_SERVER_KEY>
      hermes peer list
      hermes peer dm spark < ~/.hermes/cache/scratch/dm.txt        # message body from a file (nothing shell-interpreted)
      hermes peer dm spark/researcher < ~/.hermes/cache/scratch/dm.txt   # named profile on a multiplexed peer
      hermes peer run spark --idempotency-key ticket-123 < ~/.hermes/cache/scratch/long-task.txt
      hermes peer status spark run_abc123
      hermes peer stop spark run_abc123

      hermes peer dm الرسالة إلى Bot Chat الأساسية للوكيل البعيد عبر خادم API الموجود لدى النظير، وينفّذ هناك دورًا واحدًا للوكيل، ثم يطبع الرد على stdout — فهو المقابل المطابق تمامًا، عبر الأجهزة، للأمر المحلي hermes -p <bot> chat الأمر.

      استخدم peer dm فقط للاستعلامات القصيرة والإيصالات، لأنه يحتفظ باتصال HTTP واحد حتى ينتهي الدور. إذا أخذ peer الرسالة لكن امتد الدور بعد ذلك الاتصال، تكون الرسالة بالفعل في Bot Chat الخاصة به ويستمر الدور هناك، لذا يذكر الأمر ذلك بدقة بدلًا من وصف peer بأنه غير متاح — إعادة الإرسال تشغّل الدور مرتين. انتهاء المهلة عند الاتصال يظل يذكر أن peer غير متاح. عندما تكون Bot Chat الخاصة به مفتوحة في Desktop، تُسلّم الرسالة للمحادثة المفتوحة وتعمل فيها كدورها التالي — يراها كل من يراقب، ويعود الرد عبر الاستدعاء نفسه (يجيب مسار البث بالطريقة نفسها، كحدث اكتمال واحد لذلك الدور)؛ إذا ظل الدور يعمل بعد خمس دقائق، peer dm إلا للاستعلامات القصيرة وإيصالات الاستلام، لأنه يُبقي اتصال HTTP واحدًا مفتوحًا حتى ينتهي الدور. أما للدور الطويل، فيعيد peer run قيمة run_id فورًا؛ استطلع حالته باستخدام peer status. إذا كانت Bot Chat الخاصة بـ peer مفتوحة في Desktop لديه، يكون التشغيل دور تلك المحادثة التالي، وتتبع حالته إثبات المحادثة نفسه. يرث التشغيل النص المسجّل لـ Bot Chat المعتمدة، وتتيح قيمة ثابتة من --idempotency-key الثابتُ إعادةَ المحاولة تُعيد التشغيل الأصلي بدلًا من بدء عمل مكرر. استخدم peer stop مع معرّف التشغيل ذاك تحديدًا لمقاطعته دون استهداف دور آخر.

      بمجرد تسجيل نظير، يتضمن بروتوكول المراسلة الذي تتعلمه كل Bot Chat (agent.bot_mode_protocol) قائمة النظراء تلقائيًا، وتقبل message_agent أهداف النظراء مباشرةً — message_agent(target="spark/researcher", …) ، أو target="spark" للوكيل الرئيسي لدى النظير — وهكذا تتعلم الـ Bots الخاصة بك من تلقاء نفسها أن هناك زملاء على أجهزة أخرى وكيف تصل إليهم. يؤدي تسجيل نظير أو إزالته إلى تحديث بروتوكول كل Bot Chat عند رسالتها التالية (capability epoch).

      المتطلبات: يشغّل جهاز النظير منصة الـ gateway المسماة api_server مع مفتاح API_SERVER_KEY قوي؛ أما إمكانية الوصول فهي مسؤولية شبكتك (LAN، أو Tailscale، أو VPN). المفتاح من بيانات الاعتماد ويُخزَّن في ~/.hermes/.env باسم HERMES_PEER_<NAME>_KEY ؛ بينما تُخزَّن أسماء النظراء وعناوين URL الخاصة بهم في config.yaml ضمن bot_peers.

      الوصول في اتجاه واحد (NAT)

      الروابط بين الـ gateways اتصالات مباشرة من gateway إلى gateway — فـ Desktop هنا أداة عرض، وليس relay. يستطيع الـ gateway الموجود خلف NAT منزلي أن يبادر بالاتصال بنظير عام (الحاسوب المحمول → VPS: ينجح)، لكن الاتجاه المعاكس لا يملك مسارًا واردًا (VPS → المنزل: يفشل) ما لم توفّر شبكتك مسارًا كهذا. إذا امتدت Group Chat عبر حدود NAT، فضع سلطة الغرفة (authority) على المضيف الذي يستطيع كل المشاركين الوصول إليه (عادةً الـ VPS العام)، أو اربط الشبكتين باستخدام Tailscale/VPN.

      نقل سلطة الغرفة المستضافة​

      الاستحواذ على السلطة إجراء استرداد يتولاه المشغّل، وليس تسليمًا ذريًا (atomic). استخدم أساليب JSON-RPC الموجودة groups.promote و groups.demote على الـ gateway المناسب. لا توجد أساليب باسم groups.peer.promote أو groups.peer.demote ؛ ويسرد groups.capabilities الأساليب التي يدعمها الـ gateway لديك.

      اعزل الكاتب القديم قبل الترقية

      قبل إرسال confirm: true ، تيقّن من أن السلطة السابقة لا يمكنها تثبيت أي كتابة (commit)، وأبقِ هذا العزل (fence) قائمًا حتى تُخفَّض رتبتها. أوقف عملياتها التي تكتب في الغرفة وامنع إعادة تشغيلها تلقائيًا، أو استخدم عزلًا مكافئًا على مستوى البنية التحتية. انتهاء مهلة الشبكة، أو قطع اتصال Desktop، أو groups.stop ليس دليلًا: فقد يظل الـ gateway القديم يعمل، وإيقاف دورٍ ما لا يُلغي سلطة الغرفة. إذا لم تتمكن من إقامة العزل، فلا تُجرِ الترقية.

      1. تحقق من تغطية النسخة المتماثلة (replica). على الـ gateway البديل، افحص groups.replica_state باستخدام {"room_id":"ROOM_ID"} وقارن last_seq مع latest_seq. اشترط وجود نسخة متماثلة كاملة قبل أي استحواذ مخطط له؛ فالترقية نفسها لا تتحقق من هذه التغطية. يُبلغ groups.replicate بالحالة caught_up بعد استيعاب الصفحات التي يعيدها groups.log ؛ ولا يثبت تسجيل النظير وحده أن البديل يملك سجل الغرفة. تصف حالة المواكبة (caught-up) آخر صفحة جرى نسخها، وليست دليلًا على أن الكاتب القديم قد توقف أو على عدم وجود أحداث أحدث. في النقل المخطط له، أوقف الكتّاب مؤقتًا، وانسخ حتى المؤشر (cursor) الأخير، ثم حافظ على العزل. أما في التعافي من الكوارث، فخذ في الحسبان أي سجل لم يصل إلى النسخة المتماثلة قط.

      2. لا تُجرِ الترقية إلا والكاتب القديم معزول. على البديل:

        {"jsonrpc":"2.0","id":1,"method":"groups.promote","params":{"room_id":"ROOM_ID","confirm":true,"reason":"planned-handover"}}

        room_id و confirm: true مطلوبان؛ أما reason فاختياري وقيمته الافتراضية authority-unreachable. التأكيد إقرار منك بأن السلطة السابقة لا يمكنها تثبيت أي كتابة، وليس طلبًا لعزلها تلقائيًا. من دون التأكيد يعيد الاستدعاء الخطأ 4118. وتتضمن النتيجة الناجحة authority_gateway_id و authority_epoch (الـ epoch المنسوخ مضافًا إليه واحد).

      3. خفّض رتبة السلطة القديمة قبل إعادتها إلى الخدمة. أبقِ كتّاب الغرفة المعتادين لديها معزولين أثناء تطبيق استدعاء RPC هذا عبر اتصال استرداد مضبوط على الـ gateway القديم. استبدل معرّف الـ gateway والـ epoch الواردين في المثال بالقيم الدقيقة التي أعادتها الترقية الناجحة:

        {"jsonrpc":"2.0","id":2,"method":"groups.demote","params":{"room_id":"ROOM_ID","observed_gateway_id":"NEW_GATEWAY_ID","observed_epoch":2}}

        المعاملات الثلاثة كلها مطلوبة. لا تخمّن epoch مستقبليًا: فخفض الرتبة يتطلب دليلًا على وجود سلطة أحدث، لا قيمة مختلَقة. يسجّل هذا الإجراء authority.lost ويعتمد السلالة (lineage) المرصودة؛ وتكرار السلالة نفسها لا يغيّر النتيجة (idempotent). إذا كان المضيف القديم غير متاح، فأبقِه معزولًا ونفّذ هذه الخطوة قبل استعادة كتّابه المعتادين.

      4. تحقق وأعد الاتصال. اقرأ groups.state على كلا الـ gateways وقارن room.authority_gateway_id و room.authority_epoch بنتيجة الترقية. يجب أن تُرفض عمليات الإرسال من السلطة القديمة؛ ووجّه العملاء إلى البديل. يعزل خفض الرتبة عمليات الكتابة؛ لكنه لا يدمج السجلات ولا يحوّل تلقائيًا المخزن المرجعي القديم إلى نسخة متماثلة متزامنة.

      إجراء الترقية بينما لا يزال الـ gateway القديم قابلًا للكتابة يسمح لمخزني state.db المستقلين كليهما بقبول الرسائل وتكوين سجلات متباعدة. ولا يؤدي وجود epoch أعلى على البديل إلى تعطيل الكاتب القديم عن بُعد؛ كما أن حالة انقسام الدماغ (split-brain) لا تشترط تساوي قيم epoch. إذا تباعدت السجلات بالفعل، فاعزل الكتّاب واحتفظ بكلا السجلين للاسترداد، بدلًا من افتراض أن الترقية أو خفض الرتبة أو إعادة التشغيل (replay) ستدمجها.

      الـ Bots عبر الأجهزة​

      عندما تسجّل عدة backends في Settings → Connections — بيئة التشغيل المحلية، أو gateways بعيدة، أو مضيفات SSH، أو نُسخ Hermes Cloud — تعرض قائمة الأعضاء الـ Bots من كل مصدر متصل، وبشكل دائم: إذ تُجرَد مصادر SSH دون تشغيل أي شيء على الجهاز البعيد، وتحتفظ الأجهزة التي يتعذر الوصول إليها مؤقتًا بآخر صفوفها المعروفة بدلًا من أن تختفي. وعندما يوجد اسم الـ profile نفسه على عدة مصادر، تُميَّز المعرّفات بالصيغة @name-device (مثلًا @research-homelab). تعيش محادثات الـ Bot وجلساته وذاكرته وروتيناته (routines) على الجهاز الذي يملك الـ profile.

      النقر على Bot من Connections لا ينقل نافذتك إلى ذلك الجهاز — ابقَ في محادثتك وأشِر إليه عبر @mention ، أو أجلِسه في محادثة جماعية، أو أنشئ عليه وكلاء جددًا مباشرةً باستخدام أداة الاختيار Create on. بهذه الطريقة يتشارك الوكلاء السحابيون والمحليون قائمة أعضاء واحدة: سجّل نسخة Hermes Cloud الخاصة بك وجهازك المكتبي (مثلًا عبر Tailscale أو SSH)، وستتمكن الـ Bots لديهما من مراسلة بعضها والجلوس في الغرف نفسها، مع تشغيل عمل كل وكيل على جهازه الخاص. وتمرّ الرسائل المباشرة بين الـ Bots عبر تلك الأجهزة من خلال Desktop relay تلقائيًا (راجع المراسلة عبر الأجهزة المتصلة أعلاه).

      راجع ربط Desktop بعدة نُسخ من Hermes للاطلاع على الدليل الكامل للاتصالات المتعددة.

      Bots المحلية و gateway (كم bot تعمل في وقت واحد)​

      لا يشغّل Desktop backend لكل Bot. فعملية gateway واحدة لكل مضيف تملك جلسات كل profile محلي: عندما تفتح Bot محليًا، ينفّذ Desktop الأمر hermes gateway ensure --json لذلك الـ profile، فيتصل بالـ gateway العامل أو يشغّله إذا لم يكن هناك ما يخدم الـ profile بعد، ثم يتصل به عبر WebSocket (/api/ws) بتذكرة (ticket) أحادية الاستخدام. لا توجد مجموعة backends (pool) من جهة Desktop، ولا إعداد يحدّد عدد Bots التي يمكن إبقاؤها جاهزة (warm)، ولا مُنهٍ للخمول (idle reaper) — فلا ينتظر فتح Bot آخر خانةً أبدًا، وتكلّف قراءة سجل Bot آخر طلبًا واحدًا فقط إلى الـ gateway نفسه.

      عمر الـ gateway مستقل عن نوافذ Desktop. فإغلاق نافذة أو الخروج من Desktop لا ينسيان إلا الاتصال؛ ولا يوقفان الـ gateway أبدًا، فتستمر bots المراسلة والروتينات (routines) والأدوار الجارية في العمل، ويعيد Desktop الاتصال عند الفتح التالي. أوقفه عمدًا باستخدام hermes gateway stop. وإذا أعيد تشغيل الـ gateway من تحت Desktop (بسبب تحديث، أو انهيار، أو hermes gateway stop يتبعه فتح لاحق)، ينفّذ Desktop الأمر gateway ensure مرة أخرى ويعيد الاتصال. أما الـ profile المعلَّم بـ gateway.standalone: true فيحتفظ بـ gateway خاص به؛ ويتصل به Desktop بالطريقة نفسها.

      تُعدّ gateways البعيدة ومضيفات SSH ومثيلات Hermes Cloud في Settings → Connections مضيفات مستقلة بعملياتها الخاصة؛ وتعمل Bots الخاصة بها على ذلك الجهاز (راجع Bots across machines أعلاه)، لا على gateway هذا المضيف.

      إيقاف تشغيله​

      Bot Mode إضافة (plugin) مضمّنة في Desktop. أوقف مفتاح Desktop الخاص بها في Capabilities → Plugins → Bots — فيُلغى تسجيل قائمة الأعضاء ولوحة Routines والـ middleware الخاص بمربع الكتابة مباشرةً، دون الحاجة إلى إعادة التشغيل. تبقى الـ profiles والجلسات ومهام cron الخاصة بك دون أي تغيير في الحالتين؛ فـ Bot Mode لا يمتلك بياناتك أبدًا، بل يعرضها فقط.

      يوجد أيضًا تفضيل لإخفاء جلسات Bot Chat الأساسية من قائمة الجلسات العادية في الشريط الجانبي، بحيث لا تظهر إلا داخل لوحة Bots. (يستخدم هذا علامة الجلسة المخفية (hidden-session flag) في النواة؛ أما على الـ gateways الأقدم فتبقى المحادثات ظاهرة ببساطة.)

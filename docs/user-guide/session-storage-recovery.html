      استعادة تخزين الجلسات

      يحتفظ Hermes بكل محادثة في ملف SQLite واحد لكل profile، هو state.db، مع ملفين جانبيين تديرهما SQLite بنفسها: state.db-wal (سجل الكتابة المسبقة) و state.db-shm. يمكن لعمليات Hermes متعددة مشاركة ذلك الملف بأمان — يكتب gateway وتطبيق Desktop ولوحة التحكم و cron وأوامر CLI جميعًا عبر أقفال SQLite نفسها.

      هناك أمر واحد غير آمن: إعادة كتابة المخزن بينما تكتب إليه عملية أخرى. عندما يحدث ذلك، تتوقف العمليات التي لا تزال تمسك النسخة القديمة من السجل عن الكتابة عمدًا، ويجيب كل دور برسالة مثل:

      another Hermes process still holds an old copy of the session database's write-ahead log, so Hermes stopped writing to keep the file safe …

      هذه الصفحة هي الدليل الذي تربط به تلك الرسالة. لا يضيع شيء عندما تراها؛ وُضع الرفض تحديدًا كي لا يضيع شيء.

      الحل في ثلاث خطوات​

      1. أغلق كل عمليات Hermes على ذلك الـ profile. تطبيق Desktop و gateway ولوحة التحكم و cron:

        hermes gateway stop          # add -p <profile> for a named profile

        ثم أغلق تطبيق Desktop من قائمته وأوقف أي لوحة تحكم (hermes dashboard --stop) أو خدمة مخصّصة تشغّلها. لا تكفي إعادة تشغيل واحدة منها — فعملية واحدة باقية تمسك السجل القديم تجعل كل عملية جديدة تستمر في الرفض.

      2. اسأل doctor عمّن لا يزال يمسك السجل.

        hermes doctor                # add -p <profile> for a named profile

        ما دام أي شيء يمسك السجل المتقاعد، يطبع doctor كل عملية ماسكة بصيغة PID N (command) مع الحل نفسه، ويتجاوز فحوص الصحة وأي عمل --fix كي لا يصبح كاتبًا آخر. أوقف العمليات المدرجة وشغّله مجددًا حتى يختفي السطر.

      3. ابدأ Hermes مجددًا (عملية واحدة أولًا — gateway أو تطبيق Desktop) وأرسل رسالتك مرة أخرى. تستأنف محادثتك من حيث توقفت.

      ما يجب تجنّبه​

      • لا تشغّل hermes doctor --fix بينما تعمل العمليات. يرفض doctor نقطة checkpoint عندما يستطيع رؤية عملية تمسك السجل المتقاعد، لكن على مضيف لا يمكنه فحص عملياته يكون مسار الإصلاح هو بالضبط الكاتب الثاني الذي سبّب المشكلة.
      • لا تحذف state.db-wal أو state.db-shm. يحتوي السجل على محادثات مثبَّتة لم تُنقل بعد إلى state.db. حذفه هو الإجراء الوحيد الذي يحوّل الرفض إلى فقدان بيانات حقيقي.
      • لا تنسخ state.db وحده. الملفات الثلاثة صورة واحدة. استخدم لقطة (hermes backup) أو hermes sessions recover، وليس cp state.db somewhere/.
      • لا تطلب من الوكيل إصلاحه. جلسة الوكيل نفسه في المخزن ذاته؛ وسيواجه الرفض نفسه.

      أوامر الصيانة ترفض العمل أثناء كتابة عملية أخرى​

      hermes sessions optimize, hermes sessions optimize-storage و hermes sessions prune تعيدان كتابة المخزن (VACUUM وإعادة بناء فهرس النص الكامل والحذف الجماعي). تشغيل إحداهما مع gateway حي هو ما يؤدي إلى رفض أسطول الوكلاء أعلاه، لذا تتحققان أولًا الآن وترفضان بينما تمسك عملية أخرى قاعدة البيانات:

      Refusing `hermes sessions optimize-storage`: another process is using ~/.hermes/state.db.
        PID 41230 (hermes gateway run): state.db, state.db-shm, state.db-wal
        PID 41355 (hermes serve --profile work): state.db-wal
      Rewriting the database under a live writer is how every agent ends up refusing turns with the
      retired state.db-wal error. Nothing is lost.
      Stop them first (`hermes gateway stop`, quit the Desktop app, pause cron), then re-run.
      Override with --force if you accept the risk.

      --dry-run لا تُحجب أبدًا كمعاينات. أما --force فيشغّل الأمر رغم ذلك — استخدمه فقط عندما تعرف أن العمليات المدرجة خاملة (مثل قارئ بدأتَه بنفسك). يُجرى الفحص نفسه عندما تكتب sessions optimize في طرفية Desktop.

      ملفات قد تجدها بجانب state.db​

      الملف أو المجلدما هوما يجب فعله
      state.db-wal, state.db-shmسجل الكتابة المسبقة الحي في SQLite وفهرس الذاكرة المشتركة الخاص به. كِبَر -wal طبيعي أثناء تشغيل gateway أو Desktop.اتركهما دون تغيير. يصغران تلقائيًا عند checkpoint التالية.
      state.db.retired-wal-<timestamp>-<pid>/نسخة التقطها Hermes من السجل الذي ظلت عملية تمسكه حين رفض الكتابة، مع manifest.json يصفها. أدلة جنائية، وليست نسخة احتياطية تستعيدها دون فحص.احتفظ بها. إذا كانت محادثات الفترة السابقة للحادث مباشرة مفقودة بعد الاستعادة، فأرفق المجلد ببلاغ خلل؛ يستطيع أحد القائمين على الصيانة تحديد، من manifest.json، ما إذا كانت تلك الإطارات ينبغي إضافتها فوق الملف الحالي.
      state.db.pre-update-emergency-<timestamp>.bakلقطة يأخذها محدّث Desktop قبل أن يمسّ المخزن.احتفظ بها حتى تستخدم التطبيق المحدَّث لبعض الوقت. لا تستعدها إلا بعد إيقاف كل عمليات Hermes: شغّل hermes sessions recover --source <file> --inspect-only أولًا.
      state.db.corrupt.<timestamp>.bak, *.malformed-backupنسخ من ملف وجده Hermes تالفًا قبل إصلاحه أو عزله.لا تستعدها فوق state.db — فهي تحمل التلف نفسه. احتفظ بها لبلاغ؛ ويمكن حذفها بأمان بعد العودة إلى الحالة الطبيعية.
      state-snapshots/لقطات سريعة يأخذها hermes update و hermes backup.استعدها مع إيقاف كل عمليات Hermes؛ راجع hermes backup.

      عندما لا تنجح الخطوات الثلاث​

      إذا كانت كل عمليات Hermes متوقفة، ولم يعد hermes doctor يسرد أي عملية ماسكة، وظل gateway يرفض الكتابة عند بدء تشغيله، فقد يكون الملف نفسه تالفًا. أوقف كل شيء مجددًا وافحص دون كتابة:

      hermes sessions recover --source ~/.hermes/state.db --inspect-only

      --inspect-only لا يعدّل الملف أبدًا. إذا أبلغ أن المخزن قابل للاستعادة، فاتبع الأمر الذي يطبعه، أو استعد أحدث لقطة من state-snapshots/. تشرح آلية ذلك كله صفحات دليل المطوّر: استعادة State DB و تخزين الجلسات.

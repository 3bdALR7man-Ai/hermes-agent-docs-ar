      إعدادات Hermes Agent

      تُخزَّن جميع الإعدادات في دليل ~/.hermes/ ليسهل الوصول إليها.

      أسهل طريق للحصول على config.yaml يعمل

      نفّذ hermes setup --portal — عملية OAuth واحدة تمنحك مزوّد نماذج وجميع أدوات Tool Gateway الأربع دون تعديل YAML يدويًا. يحصل مشتركو Portal أيضًا على خصم 10% على المزوّدين المفوترين بالـ token. راجع Nous Portal.

      بنية الدليل​

      ~/.hermes/
      ├── config.yaml     # Settings (model, terminal, TTS, compression, etc.)
      ├── .env            # API keys and secrets
      ├── auth.json       # OAuth provider credentials (Nous Portal, etc.)
      ├── SOUL.md         # Primary agent identity (slot #1 in system prompt)
      ├── memories/       # Persistent memory (MEMORY.md, USER.md)
      ├── skills/         # Agent-created skills (managed via skill_manage tool)
      ├── cron/           # Scheduled jobs
      ├── sessions/       # Gateway sessions
      └── logs/           # Logs (errors.log, gateway.log — secrets auto-redacted)

      إدارة الإعدادات​

      hermes config              # View current configuration
      hermes config edit         # Open config.yaml in your editor
      hermes config get KEY      # Print a resolved value
      hermes config set KEY VAL  # Set a specific value
      hermes config unset KEY    # Remove a user-set value
      hermes config check        # Check for missing options (after updates)
      hermes config migrate      # Interactively add missing options

      # Examples:
      hermes config get model
      hermes config set model anthropic/claude-opus-4
      hermes config set terminal.backend docker
      hermes config unset terminal.backend
      hermes config set OPENROUTER_API_KEY sk-or-...  # Saves to .env
      نصيحة

      يوجّه الأمر hermes config set القيم تلقائيًا إلى الملف المناسب — تُحفظ مفاتيح API في .env، وكل ما عداها في config.yaml.

      أسبقية الإعدادات​

      تُحسم الإعدادات وفق هذا الترتيب (الأعلى أولوية أولًا):

      1. وسيطات CLI — مثل hermes chat --model anthropic/claude-sonnet-4 (تجاوز لكل استدعاء)
      2. ~/.hermes/config.yaml — ملف الإعدادات الأساسي لجميع الإعدادات غير السرّية
      3. ~/.hermes/.env — احتياطي لمتغيرات البيئة؛ ومطلوب للأسرار (مفاتيح API، والـ tokens، وكلمات المرور)
      4. القيم الافتراضية المدمجة — قيم افتراضية آمنة مُضمَّنة تُستخدم عند عدم ضبط أي شيء آخر
      قاعدة عامة

      توضع الأسرار (مفاتيح API، وtokens البوتات، وكلمات المرور) في .env. أما كل ما عداها (النموذج، وterminal backend، وإعدادات الضغط، وحدود الذاكرة، والـ toolsets) فيوضع في config.yaml. عند ضبط الاثنين، تكون الأولوية لـ config.yaml بالنسبة للإعدادات غير السرّية.

      عمليات نشر المؤسسات

      يمكن للمسؤول تثبيت قيم إعدادات وأسرار محددة لا يستطيع المستخدم العادي تجاوزها، عبر دليل مُدار على مستوى النظام. راجع Managed Scope.

      حدود وقت التشغيل​

      تُطبّق واجهات خادم Hermes طويلة الأمد (بما فيها الـ gateway و hermes serve --isolated) الحد الناعم المضبوط لـ RLIMIT_NOFILE أثناء بدء التشغيل عندما يدعم نظام التشغيل ذلك:

      runtime:
        nofile_soft_limit: 4096

      القيمة الافتراضية هي 4096. يُقيّد Hermes الهدف بحد نظام التشغيل الصارم ولا يخفّض أبدًا عملية لديها بالفعل حد ناعم أعلى. اضبط القيمة على 0 أو false أو null لتعطيل الضبط. على Windows وفي البيئات المعزولة حيث لا يمكن تغيير الحد، يستمر بدء التشغيل دون تغيير الحد.

      إعدادات قاعدة البيانات​

      يتحكّم القسم database: في كيفية فتح Hermes لقاعدة بيانات الحالة SQLite (state.db)، التي تخزّن الجلسات والرسائل وتوجيه الـ gateway:

      database:
        # Journal mode for state.db: wal (default) or delete.
        # Use delete on filesystems where WAL is unsafe (network mounts, some
        # virtiofs setups). Note: an existing on-disk WAL database is never
        # live-downgraded — Hermes keeps WAL and logs an error telling you the
        # configured delete did not apply. To convert an existing database, stop
        # every process using it and run a one-time offline
        # `PRAGMA journal_mode=DELETE` on the file.
        journal_mode: wal

        # Durability level for every state.db connection: OFF, NORMAL, FULL,
        # EXTRA (or 0-3). Unset leaves SQLite's compile-time default, which
        # differs between interpreter builds. On macOS this is a floor, not a
        # pin: values below FULL are refused to protect against Darwin fsync
        # reordering; EXTRA is honored.
        # synchronous: FULL

        # Optional WAL sizing pragmas (integers). Unset = SQLite defaults.
        # wal_autocheckpoint: 1000     # pages between automatic checkpoints
        # journal_size_limit: 67108864 # cap the WAL/journal size in bytes

      يُحذّر Hermes أيضًا (مرة واحدة لكل عملية لكل قاعدة بيانات) عندما يُقلَب وضع journal على القرص لقاعدة بيانات موجودة بصمت إلى WAL عند الفتح — كأن يكون مثلًا مشغّل قد حوّلها يدويًا إلى delete — ويذكر database.journal_mode بصفته الإعداد الذي يجعل هذا الاختيار ثابتًا.

      استبدال متغيرات البيئة​

      يمكنك الإشارة إلى متغيرات البيئة في config.yaml باستخدام صيغة ${VAR_NAME}:

      auxiliary:
        vision:
          api_key: ${GOOGLE_API_KEY}
          base_url: ${CUSTOM_VISION_URL}

      delegation:
        api_key: ${DELEGATION_KEY}

      تعمل الإشارات المتعددة في قيمة واحدة: url: "${HOST}:${PORT}". إذا لم يكن المتغير المُشار إليه مضبوطًا، يُترك العنصر النائب كما هو حرفيًا (يبقى ${UNDEFINED_VAR} كما هو) ويُسجَّل تحذير. لا يُوسَّع $VAR المجرد.

      ضمن gateway متعدد الـ profiles ومتعدد الإرسال (multiplexed)، تُحسم الإشارات في config.yaml الخاص بـ profile ما مقابل الجزء الخاص بذلك الـ profile في .env (نطاق أسراره)، وليس مقابل بيئة العملية المشتركة — يبقى ${MATRIX_ACCESS_TOKEN} في profile B غير محلول (يُترك حرفيًا، ويُسجَّل تحذير) ما لم يُعرّف B المتغير بنفسه. ينطبق هذا أينما حُمِّلت إعدادات B داخل الـ multiplexer: أدوار الـ gateway الموجَّهة، وبدء تشغيل adapter الخاص بـ B، ومهام cron الخاصة بـ B. عمليات التشغيل ذات profile واحد تبقى بلا تغيير. راجع ما الذي يُعزَل لكل profile للاطلاع على القائمة الكاملة.

      صيغة SecretRef على طراز Cursor مقبولة أيضًا: يُحسم ${env:VAR_NAME} تمامًا مثل ${VAR_NAME} (تُحذف بادئة env:)، لذا تعمل مقتطفات MCP أو المزوّدين المنسوخة من إعدادات Cursor / Claude دون تغيير في كلٍّ من config.yaml وقسم mcp_servers. أما مصادر SecretRef الأخرى (${file:...}، ${vault:...}، ${bitwarden:...}) فـلا تُحسم مضمَّنة — تحقن الخلفيات الخارجية للأسرار قيمها في البيئة عند بدء التشغيل عبر قسم secrets:، لذا أشِر إليها بصيغة ${env:NAME} بدلًا من ذلك؛ أما البادئات غير المعروفة فتحذّر مرة واحدة وتبقى حرفية.

      للاطلاع على إعداد مزوّدي الذكاء الاصطناعي (OpenRouter وAnthropic وCopilot وnقاط النهاية المخصصة وLLMs مستضافة ذاتيًا والنماذج الاحتياطية، وغيرها)، راجع مزوّدو الذكاء الاصطناعي (AI Providers).

      مهلات المزوّدين (Provider Timeouts)​

      يمكنك ضبط providers.<id>.request_timeout_seconds لمهلة طلب على مستوى المزوّد بأكمله، إضافة إلى providers.<id>.models.<model>.timeout_seconds لتجاوز خاص بنموذج معيّن. ينطبق هذا على عميل الدور الأساسي على كل نقل (OpenAI-wire، Anthropic الأصلي، المتوافق مع Anthropic)، وسلسلة الاحتياط، وعمليات إعادة البناء بعد تدوير بيانات الاعتماد، و(بالنسبة لـ OpenAI-wire) وسيط المهلة الخاص بكل طلب — بحيث تتغلّب القيمة المضبوطة على متغير البيئة القديم HERMES_API_TIMEOUT.

      يمكنك أيضًا ضبط providers.<id>.stale_timeout_seconds لكاشف المكالمات الراكدة غير المتدفقة (non-streaming)، إضافة إلى providers.<id>.models.<model>.stale_timeout_seconds لتجاوز خاص بنموذج معيّن. تتغلّب هذه القيمة على متغير البيئة القديم HERMES_API_CALL_STALE_TIMEOUT.

      يؤدي ترك هذه الإعدادات دون ضبط إلى الإبقاء على القيم الافتراضية القديمة (HERMES_API_TIMEOUT=1800 ثانية، وHERMES_API_CALL_STALE_TIMEOUT=90 ثانية، وAnthropic الأصلي 900 ثانية). يُعطَّل كاشف الركود غير المتدفق تلقائيًا لنقاط النهاية المحلية عند تركه ضمنيًا ويمكن أن يتوسّع للسياقات الكبيرة جدًا. غير مفعَّل حاليًا لـ AWS Bedrock (يستخدم كل من مسار bedrock_converse ومسار AnthropicBedrock SDK مكتبة boto3 بإعدادات المهلة الخاصة بها). راجع المثال المُعلَّق في cli-config.yaml.example.

      سلوك التحديث​

      الفحوصات في الخلفية​

      تسأل فحوصات التحديث السلبية (شريط CLI، وشارة TUI، ولوحة التحكم، وتطبيق سطح المكتب) واجهة GitHub REST API عن أحدث نقطة في main، وعندما تختلف عن نسختك المسحوبة (checkout)، تسأل نقطة نهاية المقارنة عن العدد الدقيق وسجل التغييرات. لا تُشغِّل هذه الفحوصات أبدًا git fetch، وكل تثبيت يسأل مرة واحدة على الأكثر كل 24 ساعة (يُعاد فحص فاشل بعد ساعة). يقوم تطبيق تحديث (hermes update، أو زر Update في تطبيق سطح المكتب) دائمًا بجلب البيانات مجددًا وإبطال الإجابة المخزَّنة مؤقتًا. أما الفحوصات الصريحة — hermes update --check، وعنصر القائمة "Check for Updates…" في تطبيق سطح المكتب، وSettings → About → "Check now" — فتتجاوز التخزين المؤقت.

      مصادقة SSH​

      يقرأ فحص التحديث عند بدء التشغيل عنوان URL الأصلي (origin) بنفس إعدادات Git المعزولة المستخدمة في اتصالاته الشبكية. لذا لا يمكن لإعادة كتابة url.*.insteadOf العامة إخفاء remote رسمي عبر SSH عن المسار العام HTTPS.

      تعتمد أوامر Git الداخلية المعزولة في Hermes افتراضيًا على ssh -o BatchMode=yes: تفشل مفاتيح المضيف غير المعروفة، وكلمات المرور، والمفاتيح المشفَّرة التي تحتاج عبارة مرور بدلًا من فتح موجّه طرفية. أما المضيفون الموثوقون بمفاتيح صالحة أو وكيل SSH فيستمرون في المصادقة. لا يغيّر هذا إعدادات Git أو SSH لديك على القرص، ولا الأوامر التي تنفّذها في أداة الطرفية.

      يتغلّب الإعداد الداخلي الافتراضي على إعدادات core.sshCommand الخاصة بالمستودع. أما متغير البيئة الصريح GIT_SSH_COMMAND فتبقى له الأولوية، بحيث يمكن الاحتفاظ فيه بأوامر هوية أو نقل مخصصة. ضمِّن -o BatchMode=yes في مثل هذا التجاوز إذا وجب أن يبقى غير تفاعلي؛ فالتجاوز الذي يسمح بالمطالبة يمكن أن يقاطع فحصًا في الخلفية.

      تعيش إعدادات hermes update تحت updates في config.yaml:

      updates:
        pre_update_backup: quick       # quick (state snapshot, default) | full (snapshot + HERMES_HOME zip) | off
        backup_keep: 5                 # Keep this many full pre-update backup zips
        non_interactive_local_changes: stash  # stash | discard
        auto_switch_parked_branch: true       # auto-switch a clean, fully merged parked branch back to main

      pre_update_backup هو مفتاح الأمان الوحيد لما قبل التحديث: يلتقط quick (الافتراضي) لقطات لملفات الحالة الحرجة (بيانات الاقتران، ومهام cron، والإعدادات، والمصادقة؛ تُتجاوز الملفات التي تفوق 1 GiB) إلى state-snapshots/؛ ويضغط full إضافةً إلى ذلك كل محتويات HERMES_HOME في ملف zip داخل backups/ وقد يضيف دقائق على المسارات الرئيسية الكبيرة؛ بينما يعطّل off الاثنين. تُحترَم القيم المنطقية القديمة (true ← full، false ← off).

      تذهب نسخ زمنية من config.yaml نفسه (تُلتقط قبل أن يعيد hermes setup كتابته، وقبل أن يعدّله hermes migrate، وفي كل مرة يُحلَّل فيها الملف بنجاح، وعند فشل تحليله) إلى backups/config/config.yaml.<reason>.<timestamp>. تُتجاوز التكرارات المتطابقة ولا تُحفظ سوى أحدث خمس نسخ لكل سبب، بحيث لا تتراكم أبدًا بجانب config.yaml. إذا كان config.yaml معطوبًا، يقدّم Hermes أحدث نسخة good بدلًا من القيم الافتراضية المدمجة ويحذّر عند كل بدء تشغيل حتى يُصلَح ملف YAML؛ ولا يُعدَّل الملف المعطوب أبدًا.

      بالنسبة لعمليات التثبيت عبر git، يخزّن Hermes تلقائيًا (auto-stash) الملفات المتتبَّعة غير المحفوظة والملفات غير المتتبَّعة قبل سحب فرع التحديث أو تنفيذ pull. تطالبك تحديثات الطرفية التفاعلية قبل استعادة ذلك الـ stash. أما التحديثات غير التفاعلية (تطبيق سطح المكتب/الدردشة، أو الـ gateway، أو --yes) فتستخدم updates.non_interactive_local_changes: يستعيد stash تعديلات المصدر المحلية بعد نجاح الـ pull، بينما يُسقط discard الـ stash الذي أنشأه التحديث بعد نجاح الـ pull. استخدم discard فقط في عمليات التثبيت المُدارة حيث لا يُقصَد لتعديلات المصدر المحلية أن تبقى.

      قبل خطوة الـ stash تلك، يستعيد Hermes أيضًا فروق package-lock.json المتتبَّعة التي يتركها اضطراب تثبيت/بناء npm. نفّذ commit أو خزّن يدويًا (stash) تعديلات lockfile المقصودة قبل التحديث.

      إعدادات terminal backend​

      يدعم Hermes سبعة terminal backends. يحدّد كل واحد منها المكان الذي تُنفَّذ فيه فعليًا أوامر shell الخاصة بالوكيل — جهازك المحلي، أو حاوية Docker، أو خادم بعيد عبر SSH، أو sandbox سحابي من Modal (مباشرة أو عبر gateway المُدار من Nous)، أو workspace من Daytona، أو Vercel Sandbox، أو حاوية Singularity/Apptainer.

      terminal:
        backend: local    # local | docker | ssh | modal | daytona | vercel_sandbox | singularity
        cwd: "."          # Gateway/cron working directory (CLI always uses launch dir)
        temp_dir: ""      # Session temp root; empty = TMPDIR, else ~/.hermes/cache/terminal
        font_family: ""   # Desktop terminal font; e.g. "MesloLGS NF"
        timeout: 180      # Per-command timeout in seconds
        home_mode: auto   # auto | real | profile — subprocess HOME policy
        env_passthrough: []  # Env var names to forward to sandboxed execution (terminal + execute_code)
        singularity_image: "docker://nikolaik/python-nodejs:python3.11-nodejs20"  # Container image for Singularity backend
        modal_image: "nikolaik/python-nodejs:python3.11-nodejs20"                 # Container image for Modal backend
        daytona_image: "nikolaik/python-nodejs:python3.11-nodejs20"               # Container image for Daytona backend

      يتحكّم terminal.temp_dir في مكان وضع Hermes للعناصر المؤقتة للجلسة على الـ backend المحلي — سجلات/pid/ملفات خروج العمليات الخلفية، وsandboxes تنفيذ الكود، ونتائج الأدوات المُنسكبة (spilled). عندما تكون فارغة (الوضع الافتراضي)، يحترم Hermes أي قيمة صريحة لـ TMPDIR/TMP/TEMP من البيئة، وإلا يستخدم دليلًا مُدارًا على تخزين حقيقي في ~/.hermes/cache/terminal بدلًا من /tmp — ففي كثير من التوزيعات (توزيعات مبنية على Arch خصوصًا) يكون /tmp عبارة عن tmpfs صغير مدعوم بالذاكرة العشوائية يمكن أن تملأه عناصر جلسة Hermes تحت الحمل. يُقلَّم الدليل المُدار تلقائيًا: تُكنَس العناصر الأقدم من 72 ساعة كل ساعة عبر أعمال صيانة الـ gateway، ومرة واحدة لكل عملية في التثبيتات القائمة على CLI فقط. اضبط temp_dir على مسار مطلق موجود لإعادة توجيه العناصر المؤقتة للجلسة إلى أي مكان آخر؛ لا تُقلَّم المسارات التي يضبطها المستخدم تلقائيًا أبدًا.

      يتحكّم terminal.font_family في الطرفية المضمَّنة في Hermes Desktop. يقبل إما اسم عائلة خط مثبَّتة محليًا (على سبيل المثال MesloLGS NF) أو مجموعة خطوط CSS. يُلحق Hermes مجموعة JetBrains Mono المضمَّنة كخيار احتياطي، وتُبقي القيمة الفارغة على الافتراضي. يمكنك تعديل نفس هذا الإعداد المحدد النطاق بمستوى profile في Settings → Appearance → Terminal Font؛ ولا حاجة لتنزيل من Google Fonts أو صلاحية خطوط نظام.

      بالنسبة إلى sandboxes السحابية مثل Modal وDaytona وVercel Sandbox، تعني container_persistent: true أن Hermes سيحاول الحفاظ على حالة نظام الملفات عبر إعادة إنشاء الـ sandbox. لا يَعِد ذلك بأن نفس الـ sandbox الحي، أو نفس فضاء PID، أو نفس العمليات الخلفية ستظل تعمل لاحقًا.

      الـ Backend المحلي​

      الافتراضي. تُنفَّذ الأوامر مباشرة على جهازك دون أي عزل. لا حاجة لأي إعداد خاص.

      terminal:
        backend: local

      افتراضيًا، تحتفظ العمليات الفرعية للأدوات المحلية بـ HOME الفعلي لمستخدم نظام التشغيل لديك. يتيح هذا لأدوات CLI الخارجية مثل git وَssh وَgh وَaz وَnpm وClaude Code وCodex العثور على بيانات الاعتماد والإعدادات التي تستخدمها بالفعل في shell العادي لديك. لا تزال حالة Hermes محدودة النطاق بحسب profile عبر HERMES_HOME؛ فـHOME ليس الطريقة التي تختار بها الـ profiles الإعدادات أو الذاكرة أو الجلسات أو المهارات.

      لا يغيّر Hermes أبدًا HOME الخاص بك على مستوى النظام، أو ملفات بدء تشغيل shell لديك، أو دليل حساب نظام التشغيل. يتحكّم هذا الإعداد فقط في البيئة الممرَّرة إلى العمليات الفرعية التي يطلقها Hermes عبر أدوات مثل terminal، والعمليات الطرفية الخلفية، وexecute_code، وعمليات ACP المساعدة.

      profileاستخدام {HERMES_HOME}/home عند وجودهاستخدام {HERMES_HOME}/home عند وجودهعزل صارم لإعدادات CLI لكل profile، لكن لن تظهر ~/.ssh وَ~/.gitconfig وَ~/.azure وَ~/.config/gh ومصادقة Claude/Codex وحالة npm العادية وغيرها ما لم تُهيّئها أو تربطها داخل home الخاص بالـ profile.

      terminal:

      Backend الخاص بـ Docker​

      يشغّل الأوامر داخل حاوية Docker مع تقوية أمنية (إسقاط جميع الصلاحيات، ومنع تصعيد الامتيازات، وحدود عدد العمليات PID).

      حاوية واحدة دائمة، مشتركة عبر عمليات Hermes. يبدأ Hermes حاوية واحدة طويلة الأمد عند أول استخدام ويوجّه كل استدعاء terminal وfile وَexecute_code عبر docker exec إلى تلك الحاوية نفسها — عبر الجلسات، و/new، و/reset، وsubagents الخاصة بـdelegate_task. تنتقل تغييرات دليل العمل، والحزم المثبَّتة، والملفات في /workspace، والعمليات الخلفية من استدعاء أداة إلى التالي، ومن عملية Hermes إلى التالية. عندما تُغلق جلسة TUI، أو تنفّذ /quit، أو تبدأ استدعاءً جديدًا لـhermes، تبقى الحاوية تعمل وتُعيد استخدامها عملية Hermes التالية عبر بحث بالتصنيفات (labels). راجع دورة حياة الحاوية أدناه لمعرفة قواعد إيقاف التشغيل الدقيقة.

      وضع العزل لكل جلسة (container_persistent: false). يؤدي ضبط container_persistent: false على backend الخاص بـ Docker إلى التحوّل إلى حاوية واحدة لكل جلسة: تحصل كل محادثة (جلسة تطبيق سطح المكتب، أو محادثة gateway، أو جلسة TUI) على sandbox جديد خاص بها، يُنشأ عند أول استدعاء terminal/file لها ويُزال عند إغلاق الجلسة أو دخولها في الخمول متجاوزةً lifetime_seconds. لا شيء ينتقل بين الجلسات — لا حالة نظام ملفات، ولا mounts، ولا عمليات خلفية. مع docker_mount_cwd_to_workspace: true، لا يُركَّب سوى workspace المرفَق بتلك الجلسة في /workspace؛ وتحصل جلسة جديدة بلا دليل مرفَق على workspace فارغ بدلًا من وراثة mount الجلسة السابقة. لا تزال subagents الخاصة بـdelegate_task تشترك في حاوية الجلسة الأصل. استخدم هذا الوضع عندما يكون الـ sandbox حدًّا أمنيًا بين المحادثات؛ وأبقِ على الافتراضي true عندما تريد الحاوية المشتركة طويلة الأمد الموصوفة أعلاه.

      terminal:
        backend: docker
        docker_image: "nikolaik/python-nodejs:python3.11-nodejs20"
        docker_mount_cwd_to_workspace: false  # Mount launch dir into /workspace
        docker_run_as_host_user: false   # See "Running container as host user" below
        docker_snap_compat: false        # See "Snap-packaged Docker (AppArmor)" below
        docker_forward_env:              # Host env vars to forward into container
          - "GITHUB_TOKEN"
        docker_env:                      # Literal env vars to inject (KEY=value)
          DEBUG: "1"
          PYTHONUNBUFFERED: "1"
        docker_volumes:                  # Host directory mounts
          - "/home/user/projects:/workspace/projects"
          - "/home/user/data:/data:ro"   # :ro for read-only
        docker_extra_args:               # Extra flags appended verbatim to `docker run`
          - "--gpus=all"
          - "--network=host"
        docker_network: true             # false = air-gap the container (--network=none)

        # Resource limits
        container_cpu: 1                 # CPU cores (0 = unlimited)
        container_memory: 5120           # MB (0 = unlimited)
        container_disk: 51200            # MB (requires overlay2 on XFS+pquota)
        container_persistent: true       # true = persist /workspace + /root, shared container; false = fresh container per session (see below)

        # Cross-process container reuse (defaults match the "one long-lived
        # container shared across sessions" contract — see Container lifecycle).
        docker_persist_across_processes: true   # Reuse container across Hermes restarts
        docker_shared_container_key: ""         # Opt in trusted profiles to one identity
        docker_orphan_reaper: true              # Sweep abandoned Exited containers at startup

        # Cross-backend lifecycle settings (apply to docker as well)
        timeout: 180                     # Per-command timeout in seconds
        lifetime_seconds: 300            # Idle-reaper window; also feeds 2× orphan-reaper threshold

      docker_env مقابل docker_forward_env: يحقن الأول أزواج KEY=value حرفية تحدّدها في الإعدادات (تعيش القيم في config.yaml أو تُمرَّر كقاموس JSON عبر TERMINAL_DOCKER_ENV='{"DEBUG":"1"}'). أما الثاني فيوجّه قيمًا من shell لديك أو من ~/.hermes/.env، بحيث لا يظهر السرّ الفعلي في ملف الإعدادات أبدًا. استخدم docker_forward_env للـ tokens وَdocker_env للخيارات الثابتة التي تحتاجها الحاوية.

      terminal.docker_extra_args (يمكن تجاوزها أيضًا عبر TERMINAL_DOCKER_EXTRA_ARGS='["--gpus=all"]') تتيح لك تمرير أعلام docker run عشوائية لا يعرضها Hermes كمفاتيح أساسية — مثل --gpus وَ--network وَ--add-host وتجاوزات بديلة لـ--security-opt، وغيرها. يجب أن يكون كل عنصر سلسلة نصية؛ وتُلحَق القائمة أخيرًا باستدعاء docker run المُجمَّع بحيث يمكنها تجاوز افتراضيات Hermes عند الحاجة. استخدمها بحذر — فالأعلام المتعارضة مع تقوية الـ sandbox (إسقاط الصلاحيات، و--user، وbind mount الـ workspace) ستُضعف العزل بصمت.

      terminal.docker_network (الافتراضي true؛ متغير البيئة: TERMINAL_DOCKER_NETWORK) — اضبطها على false لتشغيل حاوية الـ sandbox بـ--network=none، مما يقطع كل خروج شبكي (egress) من أوامر الوكيل. ينطبق هذا على حاوية التنفيذ المستخدمة من قِبل terminal وَexecute_code وأدوات الملفات. وبما أن الحاويات تستمر عبر عمليات Hermes، فإن قلب هذه القيمة إلى false بينما توجد حاوية أقدم متصلة بالشبكة سيؤدي إلى إزالة تلك الحاوية وبدء حاوية جديدة معزولة عن الشبكة تمامًا (يُسجَّل تحذير)؛ وتُفقَد العمليات الخلفية التي كانت تعمل بداخلها. يُفضَّل استخدام هذا المفتاح على تمرير --network=none عبر docker_extra_args.

      المتطلبات: Docker Desktop أو Docker Engine مثبَّت وقيد التشغيل. يفحص Hermes $PATH إضافة إلى مواقع تثبيت macOS الشائعة (/usr/local/bin/docker، وَ/opt/homebrew/bin/docker، وحزمة تطبيق Docker Desktop). Podman مدعوم جاهزًا: اضبط HERMES_DOCKER_BINARY=podman (أو المسار الكامل) لفرضه عند تثبيت الاثنين معًا.

      دورة حياة الحاوية​

      تُوسَم كل حاوية يديرها Hermes بثلاث تصنيفات (labels) بحيث يمكن للعمليات اللاحقة (وحاصد العناصر اليتيمة) تحديدها:

      • hermes-agent=1 — يشير إلى أنها مُدارة من Hermes
      • hermes-task-id=<sanitized task_id> — يُستخدم كمفتاح لاستقصاء إعادة الاستخدام لكل مهمة
      • hermes-profile=<sanitized profile name> — يحدّد نطاق إعادة الاستخدام والحصاد بحسب profile Hermes النشط افتراضيًا؛ وعند ضبط docker_shared_container_key، تُستخدم قيمته المُطهَّرة بدلًا من ذلك

      عند بدء التشغيل، ينفّذ Hermes docker ps --filter label=hermes-task-id=<id> --filter label=hermes-profile=<identity> ويتصل بالحاوية الموجودة عند العثور عليها. الهوية هنا هي الـ profile النشط ما لم يُدرِج docker_shared_container_key صراحةً profiles موثوقة في قيمة مشتركة. إذا كانت الحاوية exited (مثلًا بعد إعادة تشغيل خدمة Docker daemon)، تُشغَّل بـdocker start ويُعاد استخدامها — تنجو حالة نظام الملفات وأي حزم مثبَّتة، لكن لا تنجو العمليات الخلفية داخل الحاوية.

      عندما تخرج عملية Hermes — عبر /quit، أو إغلاق جلسة TUI، أو إيقاف الـ gateway، أو حتى SIGKILL — يكون مسار التنظيف عملية بلا أثر (no-op) بالنسبة للحاوية في الوضع الافتراضي. تبقى الحاوية تعمل. تتصل بها عملية Hermes التالية في أجزاء من الثانية عبر استقصاء التصنيفات. هذا هو السلوك الذي يقتضيه عقد "حاوية واحدة طويلة الأمد مشتركة عبر الجلسات": إنها الطريقة الوحيدة التي تنجو بها العمليات الخلفية (مراقبو npm، وخوادم التطوير، واختبارات pytest طويلة الأمد) عبر الجلسات.

      لا تُفكَّك الحاوية (تُوقَف وتُحذَف بـdocker rm -f) إلا في هذه الحالات:

      المُحفِّزمتى يُفعَّل
      docker_persist_across_processes: falseعزل صريح لكل عملية. كل cleanup() ينفّذ stop ثم rm -f. يطابق سلوك ما قبل issue #20561.
      حاصد الخمول (lifetime_seconds، الافتراضي 300 ثانية)فقط عندما تكون البيئة persist_across_processes=false. تُترَك بيئات وضع الاستمرارية بلا أثر (no-op)؛ وتنجو الحاوية من مسح الخمول.
      حاصد العناصر اليتيمة عند بدء التشغيل التالييكنس الحاويات المُوسَومة بـHermes التي حالتها Exited والأقدم من 2 × lifetime_seconds (الافتراضي 600 ثانية = 10 دقائق)، ضمن نطاق الـ profile الحالي. لا يُمَسّ الحاويات قيد التشغيل أبدًا — لسلامة العمليات المتزامنة (sibling). اضبط docker_orphan_reaper: false لتعطيله.
      إجراء مباشر من المستخدمdocker rm -f، أو docker system prune، أو إعادة تشغيل Docker Desktop. لا نضبط --restart=always، لذا تترك إعادة تشغيل المضيف الحاوية بحالة Exited (تنجو طبقة CoW الخاصة بها ويُعاد استخدامها عند بدء التشغيل التالي، لكن العمليات الخلفية تختفي).

      حالات حافة تستحق المعرفة:

      • قتل OOM لـ PID 1 داخل الحاوية يحوّل الحاوية إلى Exited. سيُشغّلها الاستخدام التالي بـdocker start؛ وتنجو حالة نظام الملفات، لكن لا تنجو العمليات الخلفية.
      • تبديل الـ profiles يعزل الحاويات عن بعضها — حاوية موسومة بـhermes-profile=work غير مرئية لعملية Hermes تعمل تحت hermes-profile=research. حاصد العناصر اليتيمة أيضًا محدود النطاق بحسب profile، لذا لا تُحصَد الحاويات عبر الـ profiles عرضًا، لكنها أيضًا لن تُنظَّف تلقائيًا حتى تبدأ Hermes مجددًا تحت الـ profile الأصلي الخاص بها.
      • المشاركة الصريحة عبر الـ profiles — اضبط نفس docker_shared_container_key غير الفارغ تحت terminal: للـ profiles التي تتعاون عن قصد في مساحة عمل موثوقة واحدة. يستبدل هذا فقط تصنيف هوية حاويتها؛ وتظل فحوصات توافق المهمة والخروج الشبكي (egress) والشبكة سارية. تبقى الـ profiles بلا هذا المفتاح معزولة. يُشتَق تصنيف الهوية من المفتاح مع لاحقة اختصار (digest) قصيرة، بحيث لا تتصادم المفاتيح المتشابهة الشكل (مثل team/workspace مقابل team_workspace) أبدًا في حاوية واحدة. مهم: تُنشأ الحاوية المشتركة مرة واحدة، من قِبل أي profile يبدأها أولًا — وتفوز إعدادات ذلك الـ profile من docker_image والـ volumes وحجم shm وإعدادات Docker الثابتة الأخرى، وتتصل الـ profiles اللاحقة بها كما هي؛ وتُتجاهَل الإعدادات المختلفة في ملفات إعداداتها حتى تُزال الحاوية وتُعاد إنشاؤها. ينبغي على الـ profiles التي تتشارك مفتاحًا الاتفاق على الصورة (image) والـ mounts.

      تشترك subagents المتوازية المُطلَقة عبر delegate_task(tasks=[...]) في هذه الحاوية الواحدة؛ فتغييرات cd، وتعديلات البيئة، والكتابة إلى نفس المسار المتزامنة يمكن أن تتصادم. إذا احتاج subagent إلى sandbox معزول، عليه تسجيل تجاوز صورة لكل مهمة عبر register_task_env_overrides()، وهو ما تفعله تلقائيًا بيئات RL والمعايير القياسية (مثل TerminalBench2، وHermesSweEnv) لصور Docker الخاصة بكل مهمة لديها.

      التقوية الأمنية:

      • --cap-drop ALL مع إعادة إضافة DAC_OVERRIDE وَCHOWN وَFOWNER فقط
      • --security-opt no-new-privileges
      • --pids-limit 256
      • tmpfs محدود الحجم لـ/tmp (512MB)، وَ/var/tmp (256MB)، وَ/run (64MB)

      توجيه بيانات الاعتماد: تُحسم متغيرات البيئة المُدرَجة في docker_forward_env من بيئة shell لديك أولًا، ثم من ~/.hermes/.env. يمكن للمهارات أيضًا أن تُعلن required_environment_variables التي تُدمَج تلقائيًا.

      Backend الخاص بـ SSH​

      يشغّل الأوامر على خادم بعيد عبر SSH. يستخدم ControlMaster لإعادة استخدام الاتصال (استمرار خمول لمدة 5 دقائق). الـ shell الدائم مفعَّل افتراضيًا — تنجو الحالة (دليل العمل، متغيرات البيئة) عبر الأوامر.

      terminal:
        backend: ssh
        persistent_shell: true           # Keep a long-lived bash session (default: true)

      متغيرات البيئة المطلوبة:

      TERMINAL_SSH_HOST=my-server.example.com
      TERMINAL_SSH_USER=ubuntu

      اختياري:

      المتغيرالافتراضيالوصف
      TERMINAL_SSH_PORT22منفذ SSH
      TERMINAL_SSH_KEY(افتراضي النظام)مسار مفتاح SSH الخاص
      TERMINAL_SSH_PERSISTENTtrueتفعيل الـ shell الدائم

      كيف يعمل: يتصل عند وقت التهيئة بـBatchMode=yes وَStrictHostKeyChecking=accept-new. يُبقي الـ shell الدائم على عملية bash -l واحدة حيّة على المضيف البعيد، تتواصل عبر ملفات مؤقتة. الأوامر التي تحتاج stdin_data أو sudo تعود تلقائيًا إلى الوضع الفوري (one-shot).

      تمرير متغيرات المهارة/الإعدادات: المتغيرات التي تعلنها مهارة في required_environment_variables، أو التي تُدرِجها تحت terminal.env_passthrough، تُمرَّر عبر SendEnv الخاصة بـ OpenSSH — تذهب الأسماء إلى سطر أمر ssh بينما تسافر القيم في بيئة العميل، ولا تظهر أبدًا في نص الأمر البعيد. يجب أن يقبلها sshd البعيد؛ أضِفها إلى /etc/ssh/sshd_config على الخادم وأعِد تحميل sshd:

      AcceptEnv NEXTCLOUD_URL NEXTCLOUD_*      # or the names your skills need

      بدون AcceptEnv مطابقة، يُسقِط الخادم المتغيرات بصمت ويرى الـ shell البعيد أنها غير مضبوطة. بيانات اعتماد مزوّدي Hermes (OPENAI_API_KEY، ...) لا تُمرَّر أبدًا حتى لو أُدرِجت. راجع تمرير متغيرات البيئة (Env Var Passthrough).

      Backend الخاص بـ Modal​

      يشغّل الأوامر في sandbox سحابي من Modal. تحصل كل مهمة على VM معزول بإعدادات قابلة للتخصيص من CPU وذاكرة وقرص. يمكن أخذ لقطة (snapshot) من نظام الملفات واستعادتها عبر الجلسات.

      terminal:
        backend: modal
        container_cpu: 1                 # CPU cores
        container_memory: 5120           # MB (5GB)
        container_disk: 51200            # MB (50GB)
        container_persistent: true       # Snapshot/restore filesystem

      مطلوب: إما متغيرا البيئة MODAL_TOKEN_ID وَMODAL_TOKEN_SECRET، أو ملف إعدادات ~/.modal.toml.

      الاستمرارية: عند تفعيلها، تُؤخَذ لقطة من نظام ملفات الـ sandbox عند التنظيف وتُستعاد في الجلسة التالية. تُتَتَبَّع اللقطات في ~/.hermes/modal_snapshots.json. يحافظ هذا على حالة نظام الملفات، وليس على العمليات الحية، أو فضاء PID، أو المهام الخلفية.

      ملفات بيانات الاعتماد: تُركَّب تلقائيًا من ~/.hermes/ (tokens الخاصة بـ OAuth، وغيرها) وتُزامَن قبل كل أمر.

      Backend الخاص بـ Daytona​

      يشغّل الأوامر في workspace مُدار من Daytona. يدعم الإيقاف/الاستئناف من أجل الاستمرارية.

      terminal:
        backend: daytona
        container_cpu: 1                 # CPU cores
        container_memory: 5120           # MB → converted to GiB
        container_disk: 10240            # MB → converted to GiB (max 10 GiB)
        container_persistent: true       # Stop/resume instead of delete

      مطلوب: متغير البيئة DAYTONA_API_KEY.

      الاستمرارية: عند تفعيلها، تُوقَف الـ sandboxes (لا تُحذَف) عند التنظيف وتُستأنَف في الجلسة التالية. تتبع أسماء الـ sandboxes نمط hermes-{task_id}.

      حد القرص: يفرض Daytona حدًا أقصى قدره 10 GiB. تُقيَّد الطلبات التي تتجاوز ذلك مع تحذير.

      Backend الخاص بـ Vercel Sandbox​

      يشغّل الأوامر في microVM سحابي من Vercel Sandbox. يستخدم Hermes واجهات الطرفية والملفات المعتادة؛ ولا توجد أدوات خاصة بـ Vercel يراها النموذج.

      terminal:
        backend: vercel_sandbox
        vercel_runtime: node24          # node24 | node22 | python3.13
        cwd: /vercel/sandbox            # default workspace root
        container_persistent: true      # Snapshot/restore filesystem
        container_disk: 51200           # Shared default only; custom disk is unsupported

      التثبيت المطلوب: ثبّت الإضافة الاختيارية (extra) الخاصة بالـ SDK:

      pip install 'hermes-agent[vercel]'

      المصادقة المطلوبة: اضبط مصادقة access-token بجميع المتغيرات الثلاثة VERCEL_TOKEN وَVERCEL_PROJECT_ID وَVERCEL_TEAM_ID. هذا هو الإعداد المدعوم لعمليات النشر ولعمليات Hermes الطويلة الأمد العادية على Render وRailway وDocker وما شابهها من المضيفين.

      للتطوير المحلي لمرة واحدة، يقبل Hermes أيضًا tokens قصيرة الأمد من Vercel OIDC:

      VERCEL_OIDC_TOKEN="$(vc project token <project-name>)" hermes chat

      من دليل مشروع Vercel مرتبط، يمكنك حذف اسم المشروع:

      VERCEL_OIDC_TOKEN="$(vc project token)" hermes chat

      tokens الخاصة بـ OIDC قصيرة الأمد ولا ينبغي استخدامها كمسار نشر موثَّق.

      وقت التشغيل: يدعم terminal.vercel_runtime كلًا من node24 وَnode22 وَpython3.13. إذا لم تُضبط، يستخدم Hermes افتراضيًا node24.

      الاستمرارية: عندما تكون container_persistent: true، يأخذ Hermes لقطة من نظام ملفات الـ sandbox أثناء التنظيف ويستعيد sandbox لاحقًا لنفس المهمة من تلك اللقطة. يمكن أن تتضمّن محتويات اللقطة بيانات اعتماد ومهارات وملفات تخزين مؤقت مزامَنة من Hermes نُسِخت إلى الـ sandbox. يحافظ هذا على حالة نظام الملفات فقط؛ ولا يحافظ على هوية الـ sandbox الحية، أو فضاء PID، أو حالة الـ shell، أو العمليات الخلفية الجارية.

      الأوامر الخلفية: يستخدم terminal(background=true) مسار Hermes العام للعمليات الخلفية غير المحلية. يمكنك إطلاق العمليات، واستقصاءها، والانتظار عليها، وعرض سجلاتها، وإنهاؤها عبر أداة العمليات المعتادة طالما الـ sandbox حي. لا يوفّر Hermes استعادة أصلية للعمليات المنفصلة (detached) الخاصة بـ Vercel بعد التنظيف أو إعادة التشغيل.

      حجم القرص: لا يدعم Vercel Sandbox حاليًا مفتاح مورد container_disk الخاص بـ Hermes. اترك container_disk بلا ضبط أو على الافتراضي المشترك 51200؛ فالقيم غير الافتراضية تفشل في التشخيصات وإنشاء الـ backend بدلًا من أن تُتجاهَل بصمت.

      Backend الخاص بـ Singularity/Apptainer​

      يشغّل الأوامر في حاوية Singularity/Apptainer. مصمَّم لمجموعات HPC والأجهزة المشتركة حيث لا يتوفر Docker.

      terminal:
        backend: singularity
        singularity_image: "docker://nikolaik/python-nodejs:python3.11-nodejs20"
        container_cpu: 1                 # CPU cores
        container_memory: 5120           # MB
        container_persistent: true       # Writable overlay persists across sessions

      المتطلبات: ثنائي apptainer أو singularity في $PATH.

      التعامل مع الصور: تُحوَّل عناوين Docker (docker://...) تلقائيًا إلى ملفات SIF وتُخزَّن مؤقتًا. تُستخدَم ملفات .sif الموجودة مباشرة.

      دليل Scratch: يُحسَم بهذا الترتيب: TERMINAL_SCRATCH_DIR ← TERMINAL_SANDBOX_DIR/singularity ← /scratch/$USER/hermes-agent (اصطلاح HPC) ← ~/.hermes/sandboxes/singularity.

      العزل: يستخدم --containall --no-home لعزل namespaces كامل دون تركيب دليل home الخاص بالمضيف.

      مشكلات terminal backend الشائعة​

      إذا فشلت أوامر الطرفية فورًا أو أُبلِغ عن أداة الطرفية بأنها معطَّلة:

      • Local — لا متطلبات خاصة. الافتراضي الأكثر أمانًا عند البدء.
      • Docker — نفّذ docker version للتحقق من أن Docker يعمل. إذا فشل، أصلح Docker أو نفّذ hermes config set terminal.backend local.
      • SSH — يجب ضبط كلٍّ من TERMINAL_SSH_HOST وَTERMINAL_SSH_USER. يسجّل Hermes خطأً واضحًا إذا كان أحدهما مفقودًا.
      • Modal — يحتاج متغير البيئة MODAL_TOKEN_ID أو ~/.modal.toml. نفّذ hermes doctor للتحقق.
      • Daytona — يحتاج DAYTONA_API_KEY. يتولى SDK الخاص بـ Daytona إعداد عنوان URL للخادم.
      • Singularity — يحتاج apptainer أو singularity في $PATH. شائع على مجموعات HPC.

      عند الشك، أعِد terminal.backend إلى local وتحقّق أولًا من أن الأوامر تعمل هناك.

      مزامنة الحالة من البعيد إلى المضيف عند إيقاف التشغيل​

      بالنسبة للـ backends الخاصة بـSSH وَModal وَDaytona، يدفع Hermes حالة ~/.hermes/ الخاصة بك (ملفات بيانات الاعتماد، والمهارات، وذاكرة التخزين المؤقت) إلى الـ sandbox البعيد أثناء الجلسة، وعند إيقاف التشغيل يزامن ملفات الحالة المتغيرة عائدةً إلى مواقعها الأصلية على المضيف. تُطبَّق الملفات التي تختلف عمّا دُفع أصلًا (بمقارنة تجزئة (hash) المحتوى) في مكانها؛ وتُطابَق الملفات البعيدة الجديدة تحت دليل مُزامَن (مثل مهارة أنشأها الوكيل عن بعد) مع المسار المضيف المقابل. لا تُستبدَل أبدًا ملفات بيانات الاعتماد المخصصة للرفع فقط على المضيف.

      • تُعاد محاولة المزامنة العائدة حتى 3 مرات مع تراجع تدريجي (backoff) وترفض استخراج أرشيفات بعيدة أكبر من 2 GiB.
      • يستخدم Docker وSingularity bind mounts (عرض مباشر لنظام ملفات المضيف) ولا يحتاجان إلى هذا.
      • يغطي هذا حالة Hermes (~/.hermes/)، وليس ملفات شجرة العمل العشوائية داخل الـ sandbox — اجعل الوكيل ينسخ العناصر المهمة خارجًا صراحةً (مثلًا عبر scp أو modal volume put) قبل تدمير الـ sandbox.

      Mounts الخاصة بـ Docker Volume​

      عند استخدام backend الخاص بـ Docker، تتيح لك docker_volumes مشاركة أدلة المضيف مع الحاوية. يستخدم كل عنصر صيغة -v القياسية لـ Docker: host_path:container_path[:options].

      terminal:
        backend: docker
        docker_volumes:
          - "/home/user/projects:/workspace/projects"   # Read-write (default)
          - "/home/user/datasets:/data:ro"              # Read-only
          - "/home/user/.hermes/cache/documents:/output" # Gateway-visible exports

      هذا مفيد من أجل:

      • تقديم ملفات إلى الوكيل (مجموعات بيانات، وإعدادات، وكود مرجعي)
      • استقبال ملفات من الوكيل (كود مُولَّد، وتقارير، وتصديرات)
      • مساحات عمل مشتركة حيث تصل أنت والوكيل معًا إلى نفس الملفات

      إذا كنت تستخدم messaging gateway وتريد أن يرسل الوكيل ملفات مُولَّدة عبر MEDIA:/...، يُفضَّل استخدام mount تصدير مخصص مرئي للمضيف مثل /home/user/.hermes/cache/documents:/output.

      • اكتب الملفات داخل Docker إلى /output/...
      • أصدِر مسار المضيف في MEDIA:، على سبيل المثال: MEDIA:/home/user/.hermes/cache/documents/report.txt
      • لا تُصدِر /workspace/... أو /output/... ما لم يكن ذلك المسار بعينه موجودًا أيضًا لعملية الـ gateway على المضيف
      تحذير

      تُبطل مفاتيح YAML المكرَّرة صمتًا المفاتيح السابقة. إذا كان لديك بالفعل قسم docker_volumes:، ادمج mounts الجديدة في نفس القائمة بدلًا من إضافة مفتاح docker_volumes: آخر لاحقًا في الملف.

      يمكن ضبطها أيضًا عبر متغير بيئة: TERMINAL_DOCKER_VOLUMES='["/host:/container"]' (مصفوفة JSON).

      توجيه بيانات الاعتماد لـ Docker​

      افتراضيًا، لا ترث جلسات طرفية Docker بيانات اعتماد المضيف العشوائية. إذا احتجت token معينًا داخل الحاوية، أضِفه إلى terminal.docker_forward_env.

      terminal:
        backend: docker
        docker_forward_env:
          - "GITHUB_TOKEN"
          - "NPM_TOKEN"

      يحسم Hermes كل متغير مُدرَج من shell الحالي لديك أولًا، ثم يعود إلى ~/.hermes/.env إذا حُفِظ عبر hermes config set.

      تحذير

      أي شيء مُدرَج في docker_forward_env يصبح مرئيًا للأوامر التي تعمل داخل الحاوية. لا توجّه سوى بيانات الاعتماد التي تشعر بالارتياح لكشفها لجلسة الطرفية.

      تشغيل الحاوية بحساب مستخدم المضيف لديك​

      افتراضيًا تعمل حاويات Docker باسم root (UID 0). تصبح الملفات المُنشأة داخل /workspace أو غيرها من bind-mounts مملوكة لـ root على المضيف، لذا عليك بعد الجلسة تنفيذ sudo chown عليها قبل أن تتمكّن من تحريرها من محرر المضيف لديك. يعالج مفتاح terminal.docker_run_as_host_user هذا:

      terminal:
        backend: docker
        docker_run_as_host_user: true   # default: false

      عند التفعيل، يُلحق Hermes --user $(id -u):$(id -g) إلى أمر docker run بحيث تصبح الملفات المكتوبة في الأدلة ذات bind-mount (/workspace، وَ/root، وأي شيء في docker_volumes) مملوكة لمستخدم المضيف لديك، وليس root. المقايضة: لم يعد بإمكان الحاوية تنفيذ apt install أو الكتابة إلى مسارات مملوكة لـ root مثل /root/.npm — استخدم صورة أساسية HOME فيها مملوك لمستخدم غير root (أو أضف أدواتك المطلوبة وقت بناء الصورة) إذا احتجت الاثنين معًا.

      اترك هذا على false (الافتراضي) للحفاظ على التوافق مع السلوك السابق. فعّله عندما يكون سير عملك في معظمه "تحرير ملفات المضيف المُركَّبة" وسئمت من sudo chown -R.

      Docker المُعبَّأ كـ snap (AppArmor)​

      على المضيفين حيث ثُبِّت Docker كحزمة snap (شائع على صور Ubuntu السحابية، مثل أجهزة Azure الافتراضية)، يرفض تقييد AppArmor الخاص بالـ snap علمين من أعلام تقوية الـ sandbox وتموت الحاوية عند البدء:

      exec /sbin/docker-init: operation not permitted     # --init
      exec /usr/bin/sleep: operation not permitted        # --security-opt no-new-privileges

      هذا قيد من قيود snapd (LP#1908448)، وليس شيئًا يمكن لـ Hermes الالتفاف حوله. إما ثبّت Docker من مستودع apt الخاص بـ Docker بدلًا من الـ snap (مفضَّل — تبقى كل إجراءات التقوية فعّالة)، أو اختر:

      terminal:
        docker_snap_compat: true   # drops --init and no-new-privileges; cap-drop, tmpfs, PID limits stay

      عند تفعيل ذلك، لا تُحصَد العمليات الميتة (zombie) داخل الـ sandbox من قِبل init، ويمكن لثنائي setuid داخل الحاوية استعادة الامتيازات؛ ويُسجَّل تحذير عند بدء الحاوية.

      اختياري: تركيب دليل الإطلاق في /workspace​

      تبقى sandboxes الخاصة بـ Docker معزولة افتراضيًا. لا يُمرِّر Hermes دليل عمل المضيف الحالي لديك إلى الحاوية إلا إذا اخترت ذلك صراحةً.

      فعّله في config.yaml:

      terminal:
        backend: docker
        docker_mount_cwd_to_workspace: true

      عند التفعيل:

      • إذا أطلقت Hermes من ~/projects/my-app، يُركَّب ذلك الدليل المضيف بـbind-mount في /workspace
      • يبدأ backend الخاص بـ Docker في /workspace
      • ترى أدوات الملفات وأوامر الطرفية معًا نفس المشروع المُركَّب

      عند التعطيل، يبقى /workspace مملوكًا للـ sandbox ما لم تُركِّب شيئًا صراحةً عبر docker_volumes.

      المقايضة الأمنية:

      • false يحافظ على حدود الـ sandbox
      • true يمنح الـ sandbox وصولًا مباشرًا إلى الدليل الذي أطلقت منه Hermes

      استخدم هذا الخيار الاختياري فقط عندما تريد عن قصد أن تعمل الحاوية على ملفات المضيف الحية.

      الـ Shell الدائم​

      افتراضيًا، يعمل كل أمر طرفية في عملية فرعية خاصة به — تُعاد تهيئة دليل العمل ومتغيرات البيئة ومتغيرات الـ shell بين الأوامر. عند تفعيل الـ shell الدائم، تُبقى عملية bash واحدة طويلة الأمد حيّة عبر استدعاءات execute() بحيث تنجو الحالة بين الأوامر.

      هذا أكثر فائدة لـbackend الخاص بـ SSH، حيث يزيل أيضًا عبء الاتصال لكل أمر. الـ shell الدائم مفعَّل افتراضيًا لـ SSH ومعطَّل للـ backend المحلي.

      terminal:
        persistent_shell: true   # default — enables persistent shell for SSH

      للتعطيل:

      hermes config set terminal.persistent_shell false

      ما الذي ينجو بين الأوامر:

      • دليل العمل (تلتصق cd /tmp للأمر التالي)
      • متغيرات البيئة المصدَّرة (export FOO=bar)
      • متغيرات الـ shell (MY_VAR=hello)

      الأسبقية:

      المستوىالمتغيرالافتراضي
      الإعداداتterminal.persistent_shelltrue
      تجاوز SSHTERMINAL_SSH_PERSISTENTيتبع الإعدادات
      التجاوز المحليTERMINAL_LOCAL_PERSISTENTfalse

      لمتغيرات البيئة الخاصة بكل backend الأسبقية الأعلى. إذا أردت الـ shell الدائم على الـ backend المحلي أيضًا:

      export TERMINAL_LOCAL_PERSISTENT=true
      ملاحظة

      الأوامر التي تحتاج stdin_data أو sudo تعود تلقائيًا إلى الوضع الفوري (one-shot)، بما أن مُدخَل الـ shell الدائم مشغول بالفعل ببروتوكول IPC.

      راجع تنفيذ الكود وَقسم Terminal في الـ README لتفاصيل كل backend.

      إعدادات المهارات​

      يمكن للمهارات إعلان إعداداتها الخاصة عبر frontmatter الخاص بـ SKILL.md. هذه قيم غير سرّية (مسارات، وتفضيلات، وإعدادات نطاق) تُخزَّن تحت مساحة الأسماء skills.config في config.yaml.

      skills:
        config:
          myplugin:
            path: ~/myplugin-data   # Example — each skill defines its own keys

      كيف تعمل إعدادات المهارات:

      • hermes config migrate يفحص كل المهارات المفعَّلة، ويجد الإعدادات غير المضبوطة، ويعرض مطالبتك بها
      • hermes config show يعرض جميع إعدادات المهارات تحت "Skill Settings" مع المهارة التي تنتمي إليها
      • عند تحميل مهارة، تُحقَن قيم إعداداتها المحسومة تلقائيًا في سياق المهارة

      ضبط القيم يدويًا:

      hermes config set skills.config.myplugin.path ~/myplugin-data

      لتفاصيل عن إعلان إعدادات ضبط في مهاراتك الخاصة، راجع إنشاء المهارات — إعدادات الضبط.

      حارس على كتابات المهارات التي ينشئها الوكيل​

      عندما يستخدم الوكيل skill_manage لإنشاء مهارة أو تعديلها أو تصحيحها (patch) أو حذفها، يمكن لـ Hermes اختياريًا فحص المحتوى الجديد/المُحدَّث بحثًا عن أنماط كلمات مفتاحية خطيرة (جمع بيانات الاعتماد، وحقن prompt واضح، وتعليمات تسريب). الماسح مُعطَّل افتراضيًا — كانت سير عمل الوكلاء الحقيقية التي تلمس بشكل مشروع ~/.ssh/ أو تذكر $OPENAI_API_KEY تُفعِّل هذا الإجراء التقريبي (heuristic) كثيرًا. فعِّله مجددًا إذا أردت أن يطالبك الماسح قبل أن تصل كتابات مهارة الوكيل:

      skills:
        guard_agent_created: true   # default: false

      عند التفعيل، تظهر أي كتابة skill_manage مُعلَّمة كمطالبة موافقة مع مبرر الماسح. تصل الكتابات المقبولة؛ وتُعيد الكتابات المرفوضة خطأً توضيحيًا إلى الوكيل.

      موافقة الكتابة لكتابات المهارات​

      بمعزل عن ماسح المحتوى أعلاه، يحجب skills.write_approval كل كتابة مهارة من الوكيل (إنشاء / تعديل / تصحيح / حذف / ملفات داعمة) خلف موافقتك الصريحة — بنفس آلية القبول/الرفض المستخدمة للأوامر الخطيرة:

      skills:
        write_approval: false   # false = write freely (default) | true = stage every write for review

      عند التفعيل، تُخزَّن كتابات المهارات مرحليًا تحت ~/.hermes/pending/skills/ وتُراجَع عبر /skills pending وَ/skills diff <id> وَ/skills approve <id> وَ/skills reject <id> — من CLI أو أي منصة مراسلة. بدّل وقت التشغيل عبر /skills approval on|off. للذاكرة نفس البوابة (memory.write_approval، أدناه). شرح كامل: حجب كتابات مهارات الوكيل.

      إعدادات الذاكرة​

      memory:
        memory_enabled: true
        user_profile_enabled: true
        memory_char_limit: 2200   # ~800 tokens
        user_char_limit: 1375     # ~500 tokens
        write_approval: false     # true = require approval before any memory write

      مع memory.write_approval: true، تحتاج كتابات الذاكرة إلى موافقتك قبل أن تصل: تطالبك أدوار CLI التفاعلية مضمَّنة؛ أما جلسات المراسلة ومراجعة التحسين الذاتي في الخلفية فتُخزِّن الكتابة مرحليًا لمراجعة /memory pending ← /memory approve <id> / /memory reject <id>. بدّل وقت التشغيل عبر /memory approval on|off. راجع التحكم في كتابات الذاكرة.

      اقتطاع ملفات السياق​

      يتحكّم في مقدار المحتوى الذي يحمّله Hermes من كل ملف سياق تلقائي قبل تطبيق الاقتطاع من البداية/النهاية. ينطبق هذا على الملفات المحقونة في system prompt مثل SOUL.md وَ.hermes.md وَAGENTS.md وَCLAUDE.md وَ.cursorrules. لا يؤثر على أداة read_file.

      context_file_max_chars: null  # default — dynamic cap scaled to the model's context window (floor 20K, ceiling 500K chars)

      اضبط عددًا صحيحًا موجبًا لتثبيت حد ثابت بدلًا من السلوك الديناميكي:

      context_file_max_chars: 25000

      يُقيَّد كل قراءة لملف سياق أيضًا بـcontext_file_read_timeout (بالثواني، الافتراضي 5.0). يُتجاوَز الملف الذي تستغرق قراءته وقتًا أطول — عادةً على نظام ملفات مدعوم بالشبكة مثل iCloud Drive أو OneDrive أو NFS — مع تحذير بحيث تستمر بقية system prompt في التحميل:

      context_file_read_timeout: 5.0

      أمان قراءة الملفات​

      يتحكّم في مقدار المحتوى الذي يمكن أن يعيده استدعاء read_file واحد. تُرفَض القراءات التي تتجاوز الحد بخطأ يُطلِع الوكيل على استخدام offset وَlimit لنطاق أصغر. يمنع هذا قراءة واحدة لحزمة JS مُصغَّرة (minified) أو ملف بيانات كبير من إغراق نافذة السياق.

      file_read_max_chars: 100000  # default — ~25-35K tokens

      ارفعه إذا كنت تستخدم نموذجًا بنافذة سياق كبيرة وتقرأ ملفات كبيرة كثيرًا. خفّضه للنماذج ذات السياق الصغير للحفاظ على كفاءة القراءات:

      # Large context model (200K+)
      file_read_max_chars: 200000

      # Small local model (16K context)
      file_read_max_chars: 30000

      يزيل الوكيل أيضًا تكرار قراءات الملفات تلقائيًا — إذا قُرِئت منطقة الملف نفسها مرتين ولم يتغيّر الملف، تُعاد كعب (stub) خفيف بدلًا من إعادة إرسال المحتوى. يُعاد ضبط هذا عند ضغط السياق بحيث يمكن للوكيل إعادة قراءة الملفات بعد تلخيص محتواها بعيدًا.

      حدود اقتطاع مخرجات الأدوات​

      ثلاثة حدود مترابطة تتحكّم في مقدار المخرجات الخام التي يمكن لأداة إعادتها قبل أن يقتطعها Hermes:

      tool_output:
        max_bytes: 50000        # terminal output cap (chars)
        max_lines: 2000         # read_file pagination cap
        max_line_length: 2000   # per-line cap in read_file's line-numbered view
      • max_bytes — عندما ينتج أمر terminal أكثر من هذا العدد من الأحرف في stdout/stderr مجتمعين، يحتفظ Hermes بأول 40% وآخر 60% ويُدرج إشعار [OUTPUT TRUNCATED] بينهما. الافتراضي 50000 (نحو 12-15 ألف token عبر مُجزِّئات النصوص (tokenisers) المعتادة).
      • max_lines — الحد الأقصى لوسيط limit في استدعاء read_file واحد. تُقيَّد الطلبات الأعلى من هذا بحيث لا يمكن لقراءة واحدة إغراق نافذة السياق. الافتراضي 2000.
      • max_line_length — حد لكل سطر يُطبَّق عندما يُخرِج read_file العرض المُرقَّم بالأسطر. تُقتطَع الأسطر الأطول من هذا إلى هذا العدد من الأحرف متبوعًا بـ... [truncated]. الافتراضي 2000.

      ارفع الحدود على النماذج ذات نوافذ السياق الكبيرة التي يمكنها تحمّل مخرجات خام أكثر لكل استدعاء. خفّضها للنماذج ذات السياق الصغير للحفاظ على إيجاز نتائج الأدوات:

      # Large context model (200K+)
      tool_output:
        max_bytes: 150000
        max_lines: 5000

      # Small local model (16K context)
      tool_output:
        max_bytes: 20000
        max_lines: 500

      ميزانية انسكاب نتائج الأدوات (Spillover)​

      بمعزل عن الاقتطاع، تُنسكب نتائج الأدوات كبيرة الحجم إلى القرص بدلًا من قصّها: تُحفظ المخرجات الكاملة تحت $HERMES_HOME/cache/spillover/ ويُستبدَل المحتوى داخل السياق بمعاينة إضافةً إلى مسار الملف المحفوظ (قابل للقراءة بـread_file باستخدام offset/limit، أو قابل للمعالجة بـexecute_code). عتبة الانسكاب العامة لكل نتيجة هي 100,000 حرف، تُقاس تنازليًا تلقائيًا للنماذج ذات السياق الصغير.

      تنسكب نتائج أدوات MCP (الأدوات المسمّاة mcp_*) بعتبة افتراضية أضيق قدرها 50,000 حرف: تعيد خوادم MCP بشكل روتيني حمولات كبيرة غير مُقسَّمة إلى صفحات (كتالوجات اكتشاف الأدوات، والتنفيذات الدفعية) كانت ستبقى تحت العتبة العامة وتُضخِّم السياق في كل دور لاحق. لا شيء يُفقَد — تُحفَظ النتيجة الكاملة على القرص. تجاوَز العتبة عبر:

      tool_budget:
        mcp_result_size_chars: 50000   # per-result spillover threshold for mcp_* tools

      عتبة MCP دائمًا مُقيَّدة بالعتبة العامة لكل نتيجة (المُقاسة تنازليًا بحسب السياق أحيانًا)، بحيث لا يمكن لرفعها أن يتجاوز ما تسمح به نافذة النموذج النشط.

      يشير Hermes أيضًا إلى الحذف من جانب المزوّد (provider-side elision): عندما تضمِّن نتيجة أداة MCP أو ويب علامات اقتطاع خاصة بها (...N more items، وَ"has_more": true، وملاحظات "saved to sandbox")، يُلحَق إشعار من سطر واحد بالنتيجة يحذّر من أن البيانات المرئية غير مكتملة وينبغي تصفّحها/جلبها قبل معاملة أي تعداد على أنه مكتمل.

      تعطيل Toolset عام​

      لقمع toolsets محددة عبر CLI وكل منصة gateway في مكان واحد، أدرِج أسماءها تحت agent.disabled_toolsets:

      agent:
        disabled_toolsets:
          - memory       # hide memory tools + MEMORY_GUIDANCE injection
          - web          # no web_search / web_extract anywhere

      ينطبق هذا بعد إعدادات الأدوات لكل منصة (platform_toolsets التي يكتبها hermes tools)، لذا يُزال toolset مُدرَج هنا دائمًا — حتى لو كانت إعدادات منصة محفوظة لا تزال تُدرِجه. استخدم هذا عندما تريد مفتاحًا واحدًا لـ "أطفئ X في كل مكان" بدلًا من تعديل أكثر من 15 صفًا لكل منصة في واجهة hermes tools.

      ترك القائمة فارغة، أو حذف المفتاح، لا يفعل شيئًا.

      عزل Git Worktree​

      فعّل عزل git worktrees لتشغيل عدة وكلاء بالتوازي على نفس المستودع:

      worktree: true    # Always create a worktree (same as hermes -w)
      # worktree: false # Default — only when -w flag is passed

      عند التفعيل، تنشئ كل جلسة CLI worktree جديدًا تحت .worktrees/ بفرعه الخاص. يمكن للوكلاء تعديل الملفات، وتنفيذ commit، وpush، وإنشاء PRs دون أن يتداخلوا مع بعضهم. تُزال الـ worktrees النظيفة عند الخروج؛ وتُبقى القذرة (dirty) للاسترداد اليدوي.

      افتراضيًا يتفرّع الـ worktree الجديد من أحدث نقطة remote تم جلبها للتو (fetched) (upstream الفرع الحالي، وإلا الفرع الافتراضي للـ remote) بحيث يبدأ متزامنًا مع المشروع بدلًا من HEAD المحلي الذي قد يكون قديمًا في النسخة المستنسخة المحلية (clone). يبقي هذا نطاق فرق PR مقتصرًا على التغيير الفعلي بدلًا من وراثة ما كانت النسخة المستنسخة المحلية متأخرة عنه. اضبط worktree_sync: false للتفرُّع من HEAD المحلي بدلًا من ذلك — مفيد بلا اتصال، أو عندما تريد عن قصد الحالة الحالية بالضبط للنسخة المستنسخة كأساس. إذا تعذّر الوصول إلى الـ remote، يعود تلقائيًا إلى HEAD المحلي.

      worktree_sync: true    # Default — branch from the fetched remote tip
      # worktree_sync: false # Branch from local HEAD (offline / pinned base)

      يمكنك أيضًا إدراج ملفات مُتجاهَلة عبر gitignore لنسخها إلى الـ worktrees عبر .worktreeinclude في جذر مستودعك:

      # .worktreeinclude
      .env
      .venv/
      node_modules/

      ضغط السياق​

      يضغط Hermes تلقائيًا المحادثات الطويلة للبقاء ضمن نافذة سياق نموذجك. مُلخِّص الضغط هو استدعاء LLM منفصل — يمكنك توجيهه إلى أي مزوّد أو نقطة نهاية.

      تعيش جميع إعدادات الضغط في config.yaml (بلا متغيرات بيئة).

      المرجع الكامل​

      compression:
        enabled: true                                     # Toggle compression on/off
        progress_notices: false                           # Opt-in: deliver routine compression progress notices to chat platforms — see below
        threshold: 0.50                                   # Compress at this % of context limit
        threshold_tokens: null                            # Absolute token cap (optional) — takes lower of ratio vs absolute
        target_ratio: 0.20                                # Fraction of threshold to preserve as recent tail
        tail_mode: lean                                   # Tail retention: "lean" (default — clamped 2.5% tail, 10K-25K, with a detailed session log + anchor index + session_search recovery pointers in the summary, all from ONE auxiliary summarizer call; ~3x fewer retained tokens after compaction) or "legacy" (0.20×threshold verbatim tail)
        protect_last_n: 20                                # Min recent messages to keep uncompressed
        protect_first_n: 3                                # Non-system head messages pinned across compactions (0 = pin nothing)
        in_place: true                                    # Compact on the same session id (no rotation) — see below
        idle_compact_after_seconds: 0                     # Opt-in idle compaction (0 = disabled) — see below
        hygiene_hard_message_limit: 5000                  # Gateway safety valve — see below
        hygiene_timeout_seconds: 30                       # Max seconds of NO summary-model output before hygiene compression is cut off
        hygiene_total_ceiling_seconds: 600                # Absolute cap on the hygiene wait even while tokens are still streaming
        hygiene_max_turn_hold_seconds: 10                 # Max wall-clock the incoming turn waits on hygiene compression before proceeding uncompressed — see below
        hygiene_failure_cooldown_seconds: 300             # First rung of the per-session hygiene-failure backoff (x1/x3/x9, capped at 1h)
        context_timeout_seconds: 120                      # Inactivity budget for in-agent compress_context (loop /compress / preflight) — see below
        context_total_ceiling_seconds: 600                # Absolute cap on the *pre-commit* in-agent compress_context wait even while tokens are still streaming (an already-started SessionDB commit is never abandoned; overruns are logged + surfaced)
        proactive_prune_tokens: 0                         # Opt-in tokens trigger for the no-LLM tool-result prune (0 = off; see below)
        proactive_prune_min_result_chars: 8000            # Prune's summarize pass only touches tool results larger than this (clamped >= 200)
        proactive_prune_min_reclaim_tokens: 4096          # Prune only commits when it reclaims at least this many tokens (0 = commit any)

      ترحيل الإعدادات القديمة

      تُرحَّل تلقائيًا الإعدادات القديمة التي تحتوي على compression.summary_model وَcompression.summary_provider وَcompression.summary_base_url إلى auxiliary.compression.* عند أول تحميل (إصدار الإعدادات 17). لا حاجة لأي إجراء يدوي.

      يتحكّم progress_notices (الافتراضي false) فيما إذا كانت حالات تقدُّم الضغط الروتينية تصل إلى منصات الدردشة (Telegram، وDiscord، وSlack، وغيرها). بحسب التصميم، الضغط التلقائي صامت على واجهات الدردشة — يعمل في الخلفية بتسجيل من جانب الخادم فقط. اضبط progress_notices: true لتفعيل رؤية دورة الحياة الروتينية على منصات الدردشة: إشعار البدء "Compacting context…"، ومُحفِّزات الضغط قبل الفحص المسبق/قبل استدعاء API، والانضغاط عند الخمول، وتقدُّم إعادة المحاولة ("Compressed 30 → 12 messages, retrying…")، وإشعار "Context compaction complete". تقتصر البوابة على حالات الضغط فقط — تبقى الضوضاء التشغيلية غير المرتبطة (فشل النموذج المساعد، وضجيج حدّ المعدل/إعادة المحاولة من المزوّد) مكتومة في كل الأحوال. إشعارات فشل الضغط وملاحظات /compress اليدوية مرئية دائمًا بصرف النظر عن هذا الإعداد. تعديل هذه القيمة على gateway قيد التشغيل يسري مفعوله عند الرسالة التالية.

      hygiene_hard_message_limit هو صمام أمان لما قبل الضغط خاص بالـ gateway فقط. يوجد لكسر دوامة موت: عندما تستمر استدعاءات API في الانقطاع على جلسة متضخمة الحجم، لا يتلقى الـ gateway بيانات استخدام token أبدًا، فلا يمكن للعتبة القائمة على token أن تُفعَّل، فيستمر النص الكامل (transcript) في النمو وتزداد الانقطاعات سوءًا. يُفعَّل هذا الحد الأرضي القائم على عدد الرسائل (معروف دائمًا، بصرف النظر عن أعطال API) بمجرد وصوله لفرض الضغط واستعادة الجلسة. الافتراضي 5000 — أعلى بكثير من أي جلسة عادية، بما في ذلك النماذج ذات السياق الكبير (1M+) التي تنفّذ آلاف الأدوار القصيرة، والتي تُضغَط عند عتبة الـ token قبل الوصول إلى هذا الحد بوقت طويل. ارفعه أكثر للمنصات غير الاعتيادية، أو خفّضه لفرض ضغط أكثر شراسة. تعديل هذه القيمة على gateway قيد التشغيل يسري مفعوله عند الرسالة التالية (انظر أدناه).

      hygiene_timeout_seconds هو ميزانية عدم النشاط الخاصة بالـ gateway لهذا التمرير الضاغط لما قبل الوكيل — وليس سقفًا كليًا لزمن الجدار (wall-clock). يتدفق استدعاء تلخيص الضغط من النموذج، وكل token يصل يُعَدّ تقدُّمًا فعليًا: فنموذج استدلال بطيء لا يزال يولّد يمدّد مهلته الخاصة، بحيث لا تُقطَع نماذج التلخيص البطيئة لكن السليمة أثناء التوليد. فقط عندما لا ينتج نموذج التلخيص أي مخرجات لهذا العدد من الثواني (توقف الخلفية، اتصال معلَّق، مزوّد صامت) يحذّر الـ gateway المستخدم، ويكمل الرسالة الواردة دون ضغط، ويسجّل فترة تهدئة فشل مؤقتة لكل جلسة بدلًا من الظهور عالقًا.

      يُقيِّد hygiene_total_ceiling_seconds (الافتراضي 600) الانتظار الكلي حتى مع استمرار حركة الـ tokens، بحيث لا يمكن لتدفق متعثِّر أن يُبقي دورًا رهينة إلى ما لا نهاية. يُقيَّد بحد أدنى قيمة hygiene_timeout_seconds.

      hygiene_max_turn_hold_seconds (الافتراضي 10) هو ميزانية تعليق الدور الخاصة بالـ gateway — الحد الأقصى لزمن الجدار الذي تُحبَس فيه الرسالة الواردة انتظارًا لضغط النظافة (hygiene) قبل أن يتوقف الـ gateway عن الانتظار ويتابع على النص غير المضغوط. يوجد لأن hygiene_total_ceiling_seconds وحده يمكن أن يترك الخط صامتًا لمدة أطول بكثير من مهلة خمول نقل الدردشة: فنموذج تلخيص لا يزال يبث tokens يستمر في إعادة ضبط شريحة عدم النشاط، بحيث يمكن للانتظار دون ميزانية تعليق دور أن يمتد نحو السقف بينما لا يصل أي بايت إلى المستخدم — عندها تُسقِط Telegram (ونواقل مشابهة) الاتصال ويبدو الدور مجمَّدًا. يضمن تحديد انتظار الدور بهذه الميزانية (أقل بكثير من مهلة خمول النقل النموذجية البالغة نحو 30 ثانية) الرد على الرسالة فورًا. لا يُفقَد الضغط عند انتهاء الميزانية: يستمر العامل (worker) في العمل منفصلًا — وعندما يكون التزامه محاطًا بعلامة مائية (watermark-fenced) (الحالة العادية مع قاعدة بيانات جلسة)، يحتفظ بقبول التزامه، بحيث يُتبنى الملخَّص النهائي عند أقرب نقطة آمنة تالية وتنجو الأدوار المُلحقة بعد التخلي عن الانتظار حرفيًا كذيل متزامن. يهم هذا خصوصًا نماذج تلخيص التفكير/الاستدلال (DeepSeek وQwQ وغيرها) التي يمكن أن تتجاوز مرحلة تفكيرها وحدها الميزانية: تصل ملخصاتها متأخرة دورًا واحدًا بدلًا من ألا تصل أبدًا. إذا تعذّر تسييج الالتزام بأمان، يُهمَل الناتج المتأخر (CompressionCommitFence) ولا يمكنه الكتابة فوق أدوار أحدث. ارفع الميزانية إذا كنت تفضّل تطبيق الضغط ضمن الدور نفسه وكان ناقلك يتحمّل الانتظار؛ خفّضها لاستعادة أسرع على خلفيات بطيئة جدًا.

      يتحكّم hygiene_failure_cooldown_seconds في تلك التهدئة لكل جلسة بعد مهلة أو إجهاض ضغط نظافة. أثناء التهدئة، يتجاوز الـ gateway محاولات النظافة المتكررة لنفس الجلسة المتضخمة الحجم بحيث لا تُحبَس كل رسالة واردة على نفس الخلفية المساعدة المعطوبة. لا يزال بإمكان /compress أو /reset أو دور لاحق سليم استعادة الجلسة.

      القيمة هي الدرجة الأولى في سلّم تصاعدي، وليست فترة ثابتة: تنتظر الإخفاقات المتتالية لنفس الجلسة 1x ثم 3x ثم 9x هذه القيمة، بحد أقصى ساعة واحدة. لذا فإن جلسة نموذج تلخيصها معطوب بشكل دائم تتراجع بدلًا من إعادة المحاولة إلى الأبد بفترة ثابتة، وتُعيد أي عملية تُنقص فعلًا حجم النص (transcript) الحالة إلى الدرجة الأولى. التصاعد لكل جلسة ومحلي للعملية — تعيد إعادة تشغيل الـ gateway ضبطه إلى الدرجة الأولى بينما ينجو موعد التهدئة نفسه.

      context_timeout_seconds (الافتراضي 120) هو نفس ميزانية عدم النشاط لـcompress_context داخل الوكيل — حلقة المحادثة، والانضغاط قبل الفحص المسبق، وَ/compress اليدوي — بحيث لا يمكن لنموذج تلخيص معلَّق تعطيل جلسة إلى ما لا نهاية. تمدّد tokens الملخَّص المتدفقة الانتظار؛ ويُقطَع فقط العامل الصامت. عند انتهاء المهلة، يعيد Hermes محاولة التلخيص مرة واحدة مقابل أول إدخال في auxiliary.compression.fallback_chain (باستخدام timeout الخاص بذلك الإدخال إذا أعلن واحدًا) — المسار المتعثِّر لا يرفع خطأً أبدًا، بحيث لا يمكن لمعالجة الاحتياط الخاصة بعميل النموذج المساعد رؤيته. فقط إذا فشلت تلك المحاولة أيضًا، أو لم تُضبط سلسلة احتياط، يتجاوز Hermes الانضغاط، ويُبقي على الرسائل الحالية، ويحذّر المستخدم. اضبطها على 0 للتعطيل. يحتفظ نظافة جلسة الـ gateway بمسار hygiene_timeout_seconds الخاص بها ولا تُلَفّ مرتين.

      يُقيِّد context_total_ceiling_seconds (الافتراضي 600) انتظار ما قبل الالتزام داخل الوكيل (مرحلة التلخيص/البث) حتى مع استمرار حركة الـ tokens. يُقيَّد بحد أدنى قيمة context_timeout_seconds. الضمان الدقيق: مرحلة التلخيص مُقيَّدة بهذا السقف؛ ومرحلة الالتزام تُسجَّل وتُبرَز إذا تجاوزته. بمجرد أن يدخل العامل تسييج التزام الضغط ويكون تحوُّل SessionDB جاريًا، لا يُهمَل الالتزام أبدًا في منتصف الطريق — إذ قد يجازف ذلك بتباعد النص — لكن الانتظار لم يعد صامتًا: إذا تجاوز الالتزام السقف، يسجّل Hermes التجاوز (WARNING، يتصاعد إلى ERROR عند التكرار)، ويرسل تحذيرًا لمرة واحدة عبر قناة التحذير المرئية للمستخدم، ويستمر في الانتظار بزيادات محدودة حتى يكتمل الالتزام. عندما ينتهي السقف أثناء مرحلة التلخيص، يُغلَق بث نموذج التلخيص في تلك اللحظة نفسها على كل ناقل مساعد (chat.completions، وCodex Responses، وAnthropic Messages) — فلا يُدفَع ثمن ملخَّص متروك حتى اكتماله على اتصال لا ينتظره أحد، ويُحرَّر عقد جلسته للمحاولة التالية.

      يتحكّم protect_first_n في عدد رسائل البداية غير النظامية (non-system) المثبَّتة عبر كل انضغاط. الافتراضي 3 — ينجو تبادل المستخدم/المساعد الافتتاحي عبر كل تمرير للمُلخِّص بحيث يبقى الهدف الأصلي مرئيًا. في جلسات الانضغاط المتدحرج طويلة الأمد حيث لم يعد الدور الافتتاحي ذا صلة، اضبط protect_first_n: 0 لعدم تثبيت شيء سوى system prompt والملخَّص والذيل. يُحفَظ system prompt نفسه دائمًا بصرف النظر عن هذا الإعداد.

      يتحكّم in_place (الافتراضي true) في ما يحدث لهوية الجلسة عند تفعيل الانضغاط. عندما تكون true، يعيد الانضغاط كتابة قائمة الرسائل وإعادة بناء system prompt دون تدوير معرِّف الجلسة — تحتفظ المحادثة بمعرِّف دائم واحد طوال حياتها (لا سلسلة parent_session_id، ولا إعادة ترقيم name #2 / #3 في قوائم الجلسات). الانضغاط غير مُدمِّر: يُضغَط السياق الحي، لكن الأدوار السابقة للضغط تُؤرشَف بشكل غير حاد (soft-archived) تحت نفس المعرِّف (تُوسَم غير نشطة/مضغوطة) — لا تزال قابلة للبحث عبر session_search وقابلة للاسترداد، وليست محذوفة. تشاهد الـ hooks الوضع عبر حقل in_place في حدث session:compress. اضبط in_place: false لاستعادة السلوك القديم حيث يدوّر كل انضغاط إلى معرِّف جلسة جديد مرتبط بالقديم.

      يضبط threshold_tokens سقفًا مطلقًا اختياريًا لعدد الـ tokens لمُحفِّز الضغط. عند ضبطه، يُفعَّل الضغط عند الأدنى بين threshold القائم على النسبة وهذا العدد المطلق — بحيث لا يُفعَّل الضغط أبدًا متأخرًا عن رقم الـ token المفضَّل للمستخدم بصرف النظر عن النموذج النشط. يحل هذا مشكلة أن التبديل بين نماذج بنوافذ سياق مختلفة (مثل 1M ← 400K) يزيح نقطة التفعيل المطلقة. يُقيَّد السقف بطول سياق النموذج، لذا ضبطه أعلى مما يدعمه النموذج آمن — إذ يُستخدم عندها العتبة القائمة على النسبة. الافتراضي null (معطَّل — عتبة قائمة على النسبة فقط). ينجو السقف عبر تبديل النماذج وتفعيل الاحتياط.

      idle_compact_after_seconds هو مُحفِّز اختياري قائم على الزمن يُكمِّل العتبة threshold القائمة على الحجم. الافتراضي 0 (معطَّل). عند ضبطه أعلى من 0، تُضغَط جلسة تستأنف بعد ما لا يقل عن هذا العدد من ثواني عدم النشاط تاريخها المتراكم مسبقًا، قبل الرد الأول — بحيث لا تعيد سلسلة طويلة الأمد (مثل محادثة Telegram تعود إليها بعد ساعات) قراءة سياقها الكامل القديم في كل دور لاحق. لا يُفعَّل أبدًا عندما يكون السياق بالفعل عند أو دون الهدف بعد الضغط (threshold × target_ratio)، ويحترم نفس ضمانات تهدئة الفشل، ومنع الاضطراب (anti-thrash)، والقفل لكل جلسة التي يحترمها كل انضغاط تلقائي. مثال: idle_compact_after_seconds: 1800 يضغط بعد 30 دقيقة من الخمول.

      يُفعِّل proactive_prune_tokens تقليمًا حتميًا بلا LLM لحمولات نتائج الأدوات القديمة يعمل بمعزل عن threshold. على النماذج ذات النافذة الكبيرة، نادرًا ما يُفعَّل انضغاط threshold (نحو 50% من النافذة)، لذا تبقى مخرجات الأدوات الضخمة (تفريغات الطرفية، وقراءات الملفات، ومستخرجات الويب) عالقة في التاريخ وتُعاد في كل دور لاحق. عندما يتجاوز التاريخ المُعاد إرساله proactive_prune_tokens (الافتراضي 0 = مُعطَّل؛ جرّب 48000 للتفعيل)، يزيل التقليم تكرار النتائج المتطابقة، ويلخِّص الأقدم الضخمة منها، ويقتطع وسائط استدعاء الأدوات الكبيرة — مع حماية أحدث protect_last_n رسالة ودون استدعاء النموذج أبدًا. تبقى المخرجات الكاملة قابلة للاسترداد من مخزن الجلسة. يضبط proactive_prune_min_result_chars (الافتراضي 8000، مقيَّد إلى ≥ 200) الحجم الذي دونه تُترَك نتيجة الأداة دون مساس. يمنع proactive_prune_min_reclaim_tokens (الافتراضي 4096) التقليم من الالتزام ما لم يسترجع على الأقل هذا العدد من الـ tokens — فالتقليم المُلتزَم به يعيد كتابة تاريخ سبق إرساله ويُبطل بادئة التخزين المؤقت للـ prompt الخاصة بالمزوّد، لذا تُبقي هذه البوابة انقطاعات التخزين المؤقت تلك عرضية ومُستهلَكة تدريجيًا (انقطاع واحد ذو معنى، مثل حد ضغط) بدلًا من التفعيل عند كل تكرار أداة. يعمل هذا فقط تحت محرك compressor المدمج؛ وترث محركات السياق الأخرى سلوكًا بلا أثر (no-op).

      إعادة التحميل الفوري للـ gateway لإعدادات الضغط وطول السياق

      ابتداءً من الإصدارات الأخيرة، تعديل model.context_length أو أي مفتاح compression.* في config.yaml على gateway قيد التشغيل يسري مفعوله عند الرسالة التالية — دون إعادة تشغيل gateway، ودون /reset، ودون تدوير جلسة. يتضمن توقيع الوكيل المخزَّن مؤقتًا هذه المفاتيح، لذا يعيد الـ gateway بناء الوكيل شفافيًا عندما يرصد تغييرًا. لا تزال مفاتيح API وإعدادات الأدوات/المهارات تحتاج إلى مسارات إعادة التحميل المعتادة.

      إعدادات شائعة​

      الافتراضي (اكتشاف تلقائي) — لا حاجة لإعداد:

      compression:
        enabled: true
        threshold: 0.50

      يستخدم مزوّدك ونموذجك الرئيسيين. تجاوَز لكل مهمة (مثلًا auxiliary.compression.provider: openrouter + model: google/gemini-2.5-flash) إذا أردت الضغط على نموذج أرخص من نموذج الدردشة الرئيسي لديك.

      فرض مزوّد محدد (قائم على OAuth أو مفتاح API):

      auxiliary:
        compression:
          provider: nous
          model: gemini-3-flash

      يعمل مع أي مزوّد: nous، وَopenrouter، وَcodex، وَanthropic، وَmain، وغيرها.

      نقطة نهاية مخصصة (مستضافة ذاتيًا، وOllama، وzai، وDeepSeek، وغيرها):

      auxiliary:
        compression:
          model: glm-4.7
          base_url: https://api.z.ai/api/coding/paas/v4

      مهلة عقد الدور في الـ Gateway​

      يُسلسِل الـ gateway الأدوار بحسب معرِّف الجلسة المُحسوم لها بحيث لا يمكن لمفتاحيّ توجيه تحميل وكتابة نفس النص (transcript) في آن واحد. اضبط الحد الأقصى لانتظار العقد بمعزل عن مهلة عدم نشاط الوكيل العادية:

      agent:
        gateway_turn_lease_timeout: 5

      إذا كان دور آخر لا يزال يمسك عقد الجلسة عند انتهاء هذه الميزانية، يفشل Hermes بأمان (fail closed): فلا يحمِّل النص ولا يشغِّل النموذج للرسالة المنتظِرة. يتلقى المستخدم إشعار رفض ويجب عليه إعادة الإرسال. لا يعيد Hermes وضع الرسالة في قائمة الانتظار تلقائيًا لأن القيام بذلك دون ترتيب دائم وضمان عدم التكرار (idempotency) قد يعالجها مرتين. تستخدم القيم غير الموجبة الافتراضي البالغ 5 ثوانٍ.

      مراقب تجمُّد الجلسة (Session Stall Watchdog)​

      يشغّل الـ gateway مراقب تجمُّد للإشعار فقط (agent.session_stall_timeout، الافتراضي 300 ثانية، 0 = معطَّل). عندما يكون لدى جلسة مشغولة متابعة واردة معلَّقة وكانت ساعة النشاط المشتركة للوكيل خاملة لهذا العدد من الثواني على الأقل، يسجّل الـ gateway تحذيرًا (WARNING) ويرسل إلى المستخدم إشعارًا لمرة واحدة:

      ⚠️ Agent session appears stalled (last activity N min ago). Try /new to reset.

      الدلالات:

      • للإشعار فقط. لا يقتل المراقب الدور أبدًا — بخلاف agent.gateway_timeout، الذي يلغي التشغيل بعد عدم نشاط طويل. إشعار التجمُّد يخبرك فقط أن الوكيل يبدو عالقًا كي تقرر (/new، أو /stop، أو مواصلة الانتظار).
      • إشعار واحد لكل نوبة تجمُّد. يُصفَّر المزلاج (latch) عندما تُستنزَف المتابعة الواردة المعلَّقة أو يستأنف النشاط، بحيث تُشعِر جلسة تتعافى ثم تتجمَّد مجددًا مرة أخرى.
      • يأتي التقدُّم فقط من لقطة النشاط المشتركة (استدعاءات الأدوات، وتقدُّم بث API، ونبضات الضغط). المتابعة الواردة المعلَّقة بوابة إشعار، وليست ساعة تقدُّم.
      agent:
        session_stall_timeout: 300   # seconds; 0 disables the watchdog

      تصعيد الانتباه عند إعادة الاتصال​

      عندما يفشل adapter منصة في الاتصال (انقطاع شبكي، أو token بوت مُلغى، أو sidecar معطوب)، يعيد الـ gateway محاولة الاتصال إلى ما لا نهاية بتراجع أُسّي محدود السقف — لا تتوقف إعادة المحاولات أبدًا، بحيث يُشفى انقطاع مؤقت دائمًا ذاتيًا دون إجراء من المشغّل. العيب هو أن فشلًا دائمًا (token مُلغى لـ Telegram، أو نوايا Discord privileged مفقودة) يبدو مطابقًا لعطل عابر: "إعادة المحاولة"، إلى الأبد.

      آليتان تجعلان الإخفاقات الدائمة مرئية:

      • التصنيف النهائي (Terminal classification). الإخفاقات التي يثبت نوع استثنائها أنها لا يمكن أن تُشفى ذاتيًا أبدًا — tokens مرفوضة/مُلغاة (telegram_auth_error، وَdiscord_auth_error، وَemail_auth_error)، ونوايا privileged مفقودة (discord_intents_required)، وsidecar من Photon لا يمكن تثبيت اعتمادياته (SIDECAR_DEPS_MISSING) أو ثنائي node الخاص به مفقود (SIDECAR_NODE_MISSING) — تُوسَم فادحة (fatal) بدلًا من الدخول إلى قائمة إعادة المحاولة. التصنيف قائم بصرامة على النوع؛ وتستمر الإخفاقات الغامضة في إعادة المحاولة دائمًا.
      • تصعيد يحتاج انتباهًا. منصة تبقى باستمرار في قائمة إعادة المحاولة بعد تجاوز agent.reconnect_attention_after (الافتراضي 7200 ثانية = ساعتان، وَ0 يعطِّل) تحصل على needs_attention: true وطابع زمني retrying_since في حالة وقت تشغيل الـ gateway (hermes status)، إضافة إلى سجل WARNING. تستمر إعادة المحاولات بلا تغيير — هذه إشارة، وليست قاطع دارة. تُصفَّى العلامة عند نجاح إعادة الاتصال.
      agent:
        reconnect_attention_after: 7200   # seconds; 0 disables the escalation flag

      ذاكرة تخزين وكيل الـ Gateway المؤقتة​

      يحتفظ الـ gateway بوكيل واحد لكل جلسة بحيث تعيد المحادثة استخدام بادئة الـ prompt المخزَّنة مؤقتًا بدلًا من إعادة بناء system prompt في كل دور. يحتفظ ذلك الوكيل المخزَّن أيضًا بالنص الكامل للجلسة — بما في ذلك مخرجات الأدوات، وهو ما يبلغ عشرات الميغابايتات في جلسة بها مئات استدعاءات الأدوات. على gateway مشغول متعدد المنصات، تكون ذاكرة التخزين المؤقت لذلك أكبر مستهلك واحد للذاكرة في العملية.

      agent:
        agent_cache:
          max_size: 128            # LRU entry cap
          idle_ttl_secs: 3600      # evict an agent idle this long
          memory_high_mb: auto     # anon-RSS budget; number, "auto", or 0/off
          max_evictions_per_pass: 16
          protect_recent: 8

      يُقيِّد max_size وَidle_ttl_secs ذاكرة التخزين المؤقت بالعدد والزمن. لا يعرف أيّهما عدد البايتات التي تحتفظ بها، لذا يضيف memory_high_mb حدًا ثالثًا: بمجرد أن تتجاوز الذاكرة المقيمة المجهولة (anonymous resident memory) الخاصة بالـ gateway نفسه الميزانية، يتخلّى عن النصوص الأقل استخدامًا مؤخرًا (least-recently-used)، والتي تُعاد تحميلها من الجلسة المخزَّنة عند الدور التالي. خفِّضه إذا كان الـ gateway يتنافس على الذاكرة مع خدمات أخرى؛ ارفعه (أو اضبطه على 0 لإيقاف هذا التمرير) إذا كنت تفضّل إبقاء كل بادئة دافئة.

      يشتق auto الميزانية من حد الذاكرة الذي يعمل الـ gateway تحته فعليًا — حد cgroup لحاوية أو وحدة systemd، أو إجمالي RAM بخلاف ذلك — بحيث يُحتَرَم MemoryMax/MemoryHigh على الوحدة دون رقم ثانٍ يجب مزامنته.

      لا تُنزَع أبدًا الجلسات التي في منتصف دور، وَprotect_recent من الجلسات الأحدث استخدامًا، وأي جلسة لم يكتمل بعد كتابة نصها إلى القرص. يُسجَّل الطرد عند مستوى WARNING مع الذاكرة المقيمة (RSS) المقيسة والجلسات المُسقَطة:

      Agent cache pressure: anon RSS 6802MB over budget 6656MB — evicting 5 LRU session(s): ...

      محرك السياق​

      يتحكّم محرك السياق في كيفية إدارة المحادثات عند الاقتراب من حد token للنموذج. يستخدم محرك compressor المدمج تلخيصًا فاقدًا (lossy) (راجع ضغط السياق). يمكن لمحركات الإضافات (plugin) استبداله باستراتيجيات بديلة.

      context:
        engine: "compressor"    # default — built-in lossy summarization

      لاستخدام محرك إضافة (مثل LCM لإدارة سياق بلا فقدان):

      context:
        engine: "lcm"          # must match the plugin's name

      محركات الإضافات لا تُفعَّل تلقائيًا أبدًا — عليك ضبط context.engine صراحةً على اسم الإضافة. يمكن تصفّح المحركات المتاحة واختيارها عبر hermes plugins ← Provider Plugins ← Context Engine.

      راجع مزوّدو الذاكرة (Memory Providers) للاطلاع على النظام المماثل ذي الاختيار الواحد لإضافات الذاكرة.

      ميزانية التكرار (Iteration Budget)​

      عندما يعمل الوكيل على مهمة معقّدة بعدد كبير من استدعاءات الأدوات، قد يستهلك ميزانية التكرار الخاصة به (الافتراضي: 500 دور). لا يُدرج Hermes تحذيرات ضغط منتصف المهمة — كانت الإصدارات السابقة تحذّر النموذج عند 70%/90% من الميزانية، ما كان يدفع النماذج إلى التخلي عن المهام المعقّدة قبل الأوان، فأُزيلت هذه الآلية في أبريل 2026.

      بدلًا من ذلك، عندما تُستنفد الميزانية فعليًا (500/500)، يُدرج Hermes رسالة واحدة تطلب من النموذج إنهاء العمل، ويسمح بـ استدعاء سماح واحد ليتمكن من تقديم رد نهائي. إذا لم ينتج عن استدعاء السماح هذا نص أيضًا، يُطلب من الوكيل تلخيص ما أنجزه.

      agent:
        max_turns: none              # Iterations per conversation turn (default: none = unlimited)
                                     # Set a positive integer to cap; "none"/"null"/
                                     # "unlimited"/"inf"/"infinity"/"infinite"/0/-1 = no limit
        budget_warning_ratio: null   # Optional one-time checkpoint warning, e.g. 0.75
        api_max_retries: 3           # Retries per provider before fallback engages (default: 3)

      agent.max_turns غير محدود افتراضيًا — تسبّب سقف الأدوار في مشاكل أكثر مما حلّها (اقتطاع صامت في منتصف المهمة)، لذا يُنفّذ Hermes بشكل افتراضي دور المحادثة حتى اكتماله. لفرض سقف، اضبط عددًا صحيحًا موجبًا. للتصريح بوضوح بـ"بلا حدّ"، تعمل أي من هذه الصيغ (بغض النظر عن حالة الأحرف): "none"، "null"، "unlimited"، "infinite"، "infinity"، "inf"، 0، -1 (تُحلّ إلى قيمة حارسة sys.maxsize بحيث لا تنتهي الحلقة أبدًا بسبب عدد الأدوار).

      agent.budget_warning_ratio مُعطّل افتراضيًا في المحادثات العادية والمفوَّضة. عند ضبطه على قيمة تقع بشكل صارم بين 0 و 1 إلى جانب max_turns محدود، يُلحق Hermes إشعار نقطة تحقّق واحد مرئي للنموذج بآخر نتيجة أداة بعد بلوغ العتبة. يُعاد تفعيل الإشعار في كل دور محادثة ويستخدم ميزانية التكرار الخاصة بكل وكيل. يُلحَق فقط بذيل نتيجة أداة حالية، وليس بدور سابق أبدًا، ولا يضيف رسالة مستخدم/نظام اصطناعية أو يغيّر آلية استدعاء السماح عند الاستنفاد. يتلقى عمّال Kanban التابعون لـ Dispatcher نقطة تحقّق اكتمال عند 90% افتراضيًا (تغيير نسبة صريحة يعدّل هذه العتبة)، مع بقاء أدواتهم متاحة. تطلب نقطة التحقّق اكتمالًا مُتحقَّقًا منه أو تعليق تقدّم دائمًا، لا نجاحًا مبكرًا غير مؤكد.

      يتحكّم agent.api_max_retries في عدد مرات إعادة محاولة Hermes لاستدعاء API لدى المزوّد عند الأخطاء العابرة (حدود المعدل، انقطاعات الاتصال، أخطاء 5xx) قبل تفعيل التحويل إلى مزوّد احتياطي. القيمة الافتراضية هي 3 — أي أربع محاولات إجمالًا. إذا كان لديك مزوّدون احتياطيون مُعدّون وتريد التحويل بشكل أسرع، اخفض هذه القيمة إلى 0 بحيث ينتقل أول خطأ عابر على مزوّدك الأساسي فورًا إلى المزوّد الاحتياطي بدل استنزاف المحاولات على endpoint غير مستقر.

      ميزانية التشغيل الزمنية (Wall-Clock Run Budget)​

      بمعزل عن ميزانية التكرار، يمكنك منح كل تشغيل محادثة ميزانية زمنية فعلية اختيارية. صُمم هذا للاستدعاءات ذات المرة الواحدة واستدعاءات أطر التقييم (eval-harness) التي تعمل تحت سقف زمني خارجي صارم (مثل حدّ 900 ثانية لكل مهمة): فبدونه، قد ينتهي وقت التشغيل والعمل شبه مكتمل — على بُعد توليد واحد من إصدار الرد النهائي، أو عالقًا في استدعاء مزوّد واحد متجمّد.

      agent:
        run_budget_seconds: null     # Optional; unset/null = feature fully off (default)

      أو لكل استدعاء عبر CLI:

      hermes chat --run-budget 850 -q "..."

      عند ضبط ميزانية، يحدث أمران:

      1. إشعار الإنهاء عند 80%. عند انقضاء 80% من الميزانية، يُدرج Hermes إشعارًا لمرة واحدة (يُسلَّم بأمان للتخزين المؤقت، ويُلحق بأحدث نتيجة أداة مثل رسائل /steer) يطلب من النموذج التوقف عن الاستكشاف/التحقّق الجديد وإنتاج المُخرَج النهائي من الحالة التي وصل إليها بالفعل. يظهر مرة واحدة على الأكثر لكل تشغيل ويحاكي آلية إنهاء ميزانية التكرار الحالية — فلا توجد تحذيرات ضغط متكررة.
      2. مهلات ركود مُقاسة حسب الموعد النهائي. تُحدّد مهلات الركود الضمنية غير المتدفقة (الافتراضي 90 ثانية وحدود نماذج الاستدلال، مثل 600 ثانية لنماذج DeepSeek الاستدلالية) بسقف max(60, remaining_budget × 0.5) بحيث لا يستهلك استدعاء مزوّد متجمّد بصمت بقية وقت التشغيل. لا يعمل هذا السقف إلا على تشديد المهلة — لا يرفعها أبدًا — أما stale_timeout_seconds المُعدّة صراحةً (في إعدادات المزوّد/النموذج أو HERMES_API_CALL_STALE_TIMEOUT) فتبقى نافذة دون مساس دائمًا.

      الميزانية لكل دور من run_conversation (تُعاد ضبطها عند كل رسالة مستخدم) والميزة معطّلة تمامًا عندما لا تُضبط — لا قراءات للساعة، ولا إدراج، ولا تغييرات على المهلات.

      التحقّق عند التوقف (Verify-on-Stop) — تحقّق البرمجة​

      عند التفعيل، يرفض Hermes قبول رد نهائي في دور عدّل فيه الوكيل كودًا في مساحة عمل دون إنتاج دليل تحقّق حديث (تشغيل اختبار ناجح، بناء، فحص lint، إلخ) — فيُدرج متابعة اصطناعية تطلب من الوكيل التحقّق أو توضيح سبب عدم قدرته على ذلك. تعديلات المستندات/markdown/المهارات وحدها لا تُفعّل هذه الآلية أبدًا، والحلقة محدودة بحيث لا يمكن أن تُحاصر الوكيل أبدًا.

      agent:
        verify_on_stop: false        # true | false | "auto" (surface-aware: on for CLI/TUI/desktop, off for messaging)
        verify_guidance: true        # Append creative-UI / clean-diff guidance to the missing-evidence nudge
        max_verify_nudges: 3         # Cap on consecutive continue nudges per turn (built-in + pre_verify hooks)
        coding_instructions: ""      # Standing project-wide coding rules appended to the coding brief

      يقبل verify_on_stop القيم true (مُفعّل في كل مكان)، أو false (معطّل — الافتراضي)، أو "auto" (سلوك قديم واعٍ بالسطح: مُفعّل في أسطح البرمجة التفاعلية — CLI وTUI وDesktop — والمستدعين البرمجيين؛ ومعطّل في أسطح المراسلة كـ Telegram/Discord حيث تُقرأ سردية التحقّق كضوضاء دردشة). المعطّل هو الافتراضي في كل مكان: التثبيتات الجديدة تُشحن بـ false وقد أوقف ترحيل الإعدادات هذه الميزة في التثبيتات القائمة، لذا تفعيلها اختيار صريح. يتجاوز متغير البيئة HERMES_VERIFY_ON_STOP قيمة الإعدادات عند ضبطه.

      الدليل الذي يغذّي هذا الحارس (أي أوامر اختبار/lint/بناء عملت، وأي ملفات عُدّلت منذ ذلك الحين) يعيش في ~/.hermes/verification_evidence.db. هذا السجل لا يُكتب أو يُنشأ إلا عندما يكون الحارس مُفعّلًا؛ ومع verify_on_stop: false لا يُسجَّل شيء ويمكن حذف ملف موجود بحرّية.

      لبوّابة سياسة مستخدم/إضافة عند النقطة نفسها — تُبقي الوكيل يعمل مع فحوصك الخاصة — راجع hook الـ pre_verify.

      الأهداف الدائمة (/goal)​

      عندما يكون هدف دائم نشطًا، يحكم Hermes على ما إذا كان كل رد للمساعد يحقّقه. إن لم يكن كذلك، يُعيد تغذية prompt متابعة إلى الجلسة نفسها ويواصل العمل حتى يكتمل الهدف، أو تُستنفد ميزانية الأدوار، أو يوقفه المستخدم/يمسحه. ميزانية الأدوار هي خط الدفاع الحقيقي — إذ تفشل عمليات الحكم بشكل مفتوح (أي تستمر) حتى لا يعطّل حكم معطوب التقدّم أبدًا.

      goals:
        max_turns: 20   # Max continuation turns before Hermes auto-pauses the goal (default: 20)

      يحدّد max_turns عدد أدوار المتابعة التي يمكن أن يدفع بها الهدف قبل أن يوقفه Hermes تلقائيًا ويطلب من المستخدم تنفيذ /goal resume. يحمي هذا من النتائج السلبية الخاطئة للحكم (الهدف مكتمل فعليًا لكن الحكم يقول استمرّ) ومن الإنفاق غير المحدود على النموذج بسبب أهداف غامضة أو غير قابلة للتحقيق. راجع الأهداف الدائمة (Goals) للاطلاع على الميزة كاملةً.

      مهلات API​

      لدى Hermes طبقات مهلة منفصلة للتدفّق (streaming)، بالإضافة إلى كاشف ركود للاستدعاءات غير المتدفقة. تُضبط كواشف الركود تلقائيًا للمزوّدين المحليين فقط عندما تتركها على قيمها الافتراضية الضمنية.

      المهلةالافتراضيالمزوّدون المحليونالإعدادات / متغير البيئة
      مهلة قراءة الـ socket120 ثانيةتُرفع تلقائيًا إلى 1800 ثانيةHERMES_STREAM_READ_TIMEOUT
      كشف ركود التدفّق180 ثانيةتُرفع إلى سقف 900 ثانية (agent.local_stream_stale_timeout)HERMES_STREAM_STALE_TIMEOUT
      كشف ركود غير التدفّق90 ثانيةتُعطّل تلقائيًا عند تركها ضمنيةproviders.<id>.stale_timeout_seconds أو HERMES_API_CALL_STALE_TIMEOUT
      استدعاء API (غير متدفّق)1800 ثانيةبلا تغييرproviders.<id>.request_timeout_seconds / timeout_seconds أو HERMES_API_TIMEOUT

      تتحكّم مهلة قراءة الـ socket في المدة التي تنتظرها httpx للجزء التالي من البيانات من المزوّد. يمكن أن تستغرق النماذج اللغوية المحلية دقائق للمعالجة الأولية (prefill) على سياقات كبيرة قبل إنتاج أول رمز، لذا يرفع Hermes هذه القيمة إلى 30 دقيقة عند اكتشاف endpoint محلي. إذا ضبطت HERMES_STREAM_READ_TIMEOUT صراحةً، تُستخدم تلك القيمة دائمًا بغض النظر عن اكتشاف الـ endpoint.

      يُنهي كشف ركود التدفّق الاتصالات التي تتلقّى إشارات نبض SSE (keep-alive) دون محتوى فعلي. بالنسبة للمزوّدين المحليين (الذين لا يرسلون إشارات نبض أثناء المعالجة الأولية)، يُرفع الافتراضي إلى سقف محدود مقداره 900 ثانية بدلًا من الأساس البالغ 180 ثانية — يُضبط عبر agent.local_stream_stale_timeout أو متغير البيئة HERMES_LOCAL_STREAM_STALE_TIMEOUT.

      يُنهي كشف ركود غير التدفّق الاستدعاءات غير المتدفقة التي لا تُنتج ردًا لفترة طويلة جدًا. بشكل افتراضي، يُعطّل Hermes هذا على النقاط الطرفية المحلية لتجنّب الإيجابيات الكاذبة أثناء المعالجات الأولية الطويلة. إذا ضبطت providers.<id>.stale_timeout_seconds أو providers.<id>.models.<model>.stale_timeout_seconds أو HERMES_API_CALL_STALE_TIMEOUT صراحةً، تُحترم تلك القيمة الصريحة حتى على النقاط الطرفية المحلية.

      تحدّ هذه الميزانية كل استدعاء غير متدفّق. المزوّد الذي يقبل طلبًا ثم يصمت — الاتصال مفتوح، لا بايتات، لا خطأ — يُلغى عند مهلة الركود ويُعاد تنفيذه، بدلًا من التعليق حتى مهلة قراءة الـ socket الأطول بكثير (أو، في حالة تشغيل cron غير مراقَب، حتى يُنهي شيء خارجي العملية).

      يظهر إشعار انتظار المزوّد الدوري فقط بعد 60 ثانية على الأقل من الصمت. تصف حالة الانتظار في Codex Responses الصمت، لا إجمالي وقت التوليد: تُبقي أحداث التدفّق النشطة (بما فيها الاستدلال) الحالة صامتة. إذا توقّفت الأحداث، تُبلّغ الحالة عن وقت بلا أحداث تدفّق بدلًا من الادّعاء بعدم وصول أي رد؛ ويُمسح الإشعار عند استئناف الأحداث. عندما تبدأ عملية إعادة اتصال مرحلة مراقبة الحدث الأول من جديد، تتبع حالة الانتظار تلك المرحلة. سلوك العرض هذا لا يمدّد ميزانية استدعاء الركود الزمنية المنفصلة ولا يغيّر مهلات المراقبة. وبالمثل، تُخفي تدفقات إكمال الدردشة تحذير الصمت فورًا عند استئناف القطع، دون استبدال حالة تحميل نموذج محلي.

      تُنفّذ مهام Cron والـ subagents المفوَّضة التدفّق أيضًا. تُنفّذ الطلب مباشرةً على مسارها الخاص (عامل المقاطعة الذي تستخدمه الجلسات الأخرى ينحشر داخل تجمّعات الخيوط المتداخلة الخاصة بـ gateway)، لكن طلب الاتصال يبقى stream: true، لذا فإن ميزانية كشف ركود التدفّق أعلاه تحكمها — إذ يُعدّ كل رمز دليل حياة، فلا يُخلط بين نموذج استدلالي يفكّر لدقائق ومزوّد متجمّد، وتبقى الوكلاء الوسيطة (proxies) التي تُنهي الاتصالات الصامتة ترى بايتات.

      تعطيل تدفّق API​

      يفرض model.streaming: false طلبات غير متدفقة لكامل الجلسة — الوكيل الأصلي والـ subagents على حدّ سواء. إنه مخرج طوارئ للخوادم المتوافقة مع OpenAI المستضافة ذاتيًا التي يكون مسار استدعاء الأدوات المتدفّق فيها معطوبًا (على سبيل المثال، يمكن لـ vLLM مع --tool-call-parser qwen3_xml بالإضافة إلى مُحلّل استدلال أن يُسرّب ترميز استدعاء الأدوات إلى نص عادي ويُعيد صفر tool_calls، فتصمت المهام المفوَّضة دون تنفيذ). الافتراضي هو true؛ اتركه إلا إذا واجهت هذا الصنف من الأعطال، لأن الاستدعاءات غير المتدفقة تفقد خصائص دليل الحياة الموصوفة أعلاه. هذا منفصل عن display.streaming الذي يتحكّم فقط في عرض الرموز في الطرفية.

      model:
        streaming: false

      تحذيرات ضغط السياق​

      بمعزل عن ضغط ميزانية التكرار، يتتبّع ضغط السياق مدى قرب المحادثة من عتبة الضغط (compaction) — النقطة التي يبدأ عندها ضغط السياق بتلخيص الرسائل الأقدم. يساعد هذا كلًا منك ومن الوكيل على فهم متى تصبح المحادثة طويلة.

      التقدّمالمستوىما يحدث
      ≥ 60% من العتبةمعلومةتعرض CLI شريط تقدّم سماويًا؛ ويرسل gateway إشعارًا إعلاميًا
      ≥ 85% من العتبةتحذيرتعرض CLI شريطًا أصفر عريضًا؛ ويحذّر gateway من اقتراب الضغط

      في CLI، يظهر ضغط السياق كشريط تقدّم في تغذية مُخرَجات الأداة:

        ◐ context ████████████░░░░░░░░ 62% to compaction  48k threshold (50%) · approaching compaction

      وعلى منصات المراسلة، تُرسل إشعارات نصّية بسيطة:

      ◐ Context: ████████████░░░░░░░░ 62% to compaction (threshold: 50% of window).

      إذا كان الضغط التلقائي معطّلًا، يُخبرك التحذير بأن السياق قد يُقتطع بدلًا من ذلك.

      ضغط السياق تلقائي — لا حاجة لإعدادات. يعمل فقط كإشعار موجّه للمستخدم ولا يُعدّل تدفّق الرسائل أو يُدرج شيئًا في سياق النموذج.

      استراتيجيات مجمّعات بيانات الاعتماد (Credential Pool)​

      عندما يكون لديك عدة مفاتيح API أو رموز OAuth للمزوّد نفسه، اضبط استراتيجية التناوب:

      credential_pool_strategies:
        openrouter: round_robin    # cycle through keys evenly
        anthropic: least_used      # always pick the least-used key

      الخيارات: fill_first (الافتراضي)، round_robin، least_used، random. راجع مجمّعات بيانات الاعتماد (Credential Pools) للتوثيق الكامل.

      التخزين المؤقت للـ Prompt​

      يُفعّل Hermes التخزين المؤقت للـ prompt عبر الجلسات تلقائيًا عندما يدعمه المزوّد النشط — دون أي إعداد من المستخدم.

      بالنسبة لـ Claude عبر Anthropic الأصلية وOpenRouter وNous Portal، يُرفق Hermes نقاط توقّف cache_control بمدة صلاحية ساعة واحدة (ttl: "1h") على system prompt وكتل المهارات. يدفع الإرسال الأول ضمن ساعة جديدة كامل معدّلات الإدخال؛ أما الإرسالات اللاحقة عبر أي جلسة ضمن الساعة نفسها فتُسحب من التخزين المؤقت بمعدّل القراءة المخفَّض. يعني هذا أن system prompt، ومحتوى المهارات المُحمَّل، والجزء الأولي من أي include طويل السياق يُعاد استخدامها عبر جلسات hermes وعبر الـ subagents المتفرّعة خلال الساعة الأولى.

      يُحدّد Qwen Cloud (Alibaba DashScope) لدى المزوّد الأعلى مدة صلاحية التخزين المؤقت بـ 5 دقائق، لذا يستخدم Hermes مدة صلاحية نقطة التوقّف البالغة 5 دقائق هناك بدلًا من ذلك. أما مسارات Claude الأخرى عبر طرف ثالث (AWS Bedrock وAzure Foundry) فتعود إلى إعدادات التخزين المؤقت الافتراضية الخاصة بالمزوّد. يستخدم xAI Grok آلية منفصلة قائمة على معرّف محادثة مثبَّت للجلسة — راجع التخزين المؤقت للـ prompt في xAI.

      لا يوجد مفتاح لتعطيل هذا — التخزين المؤقت مُفعّل دائمًا ويوفّر المال حتى في المحادثات ذات الدور الواحد لأن system prompt وحده يمثّل نسبة معتبرة من عدد رموز الإدخال.

      المفتاح الصريح الوحيد هو مستوى مدة صلاحية التخزين المؤقت الذي يطلبه Hermes على نقاط توقّف من نمط Anthropic:

      prompt_caching:
        cache_ttl: "5m"   # "5m" or "1h" (Anthropic-supported tiers); other values are ignored

      يحدّد cache_ttl مدة صلاحية نقطة التوقّف التي يُرفقها Hermes لـ Claude عبر Anthropic API الأصلية وOpenRouter وNous Portal. يُحترم فقط المستويان اللذان تدعمهما Anthropic ("5m"، "1h") — وتُتجاهل أي قيمة أخرى. أما المزوّدون ذوو الحدود الخاصة (مثل Qwen Cloud، الذي لا يتجاوز 5 دقائق) فتبقى مُحدَّدة بما يسمح به الطرف الأعلى.

      النماذج المساعدة (Auxiliary Models)​

      يستخدم Hermes نماذج "مساعدة" لمهام جانبية مثل تحليل الصور، وتحليل لقطات شاشة المتصفح، وتوليد عناوين الجلسات، وضغط السياق. افتراضيًا (auxiliary.*.provider: "auto")، يوجّه Hermes كل مهمة مساعدة إلى نموذج الدردشة الرئيسي لديك — أي المزوّد/النموذج نفسه الذي اخترته في hermes model. لست بحاجة لإعداد أي شيء للبدء، لكن انتبه إلى أن المهام المساعدة تضيف تكلفة معتبرة على نماذج الاستدلال المكلفة (Opus، MiniMax M2.7، إلخ). إذا أردت مهامًا جانبية رخيصة وسريعة بغض النظر عن نموذجك الرئيسي، اضبط auxiliary.<task>.provider و auxiliary.<task>.model صراحةً (على سبيل المثال، Gemini Flash على OpenRouter للرؤية). (استخراج الويب ليس مهمة مساعدة: يقتطع web_extract ولقطات المتصفح المحتوى الطويل بشكل حتمي ويخزّنان النص الكامل لترقيم صفحات read_file — دون تدخّل أي LLM.)

      لماذا يستخدم "auto" نموذجك الرئيسي

      كانت الإصدارات السابقة تفصل مستخدمي المُجمِّعات (aggregators) (OpenRouter، Nous Portal) إلى مزوّد رخيص افتراضي من طرف المزوّد. كان ذلك مفاجئًا — إذ يرى المستخدمون الذين دفعوا مقابل اشتراك في مُجمِّع نموذجًا مختلفًا يتعامل مع حركة مرورهم المساعدة. الآن يستخدم auto النموذج الرئيسي للجميع، وتظل التجاوزات الخاصة بكل مهمة في config.yaml غالبة (راجع مرجع إعدادات المهام المساعدة الكامل أدناه).

      إعداد النماذج المساعدة تفاعليًا​

      بدلًا من تحرير YAML يدويًا، شغّل hermes model واختر "Configure auxiliary models" من القائمة. ستحصل على مُنتقي تفاعلي لكل مهمة:

      $ hermes model
      → Configure auxiliary models

      [ ] vision               currently: auto / main model
      [ ] title_generation     currently: openrouter / google/gemini-3-flash-preview
      [ ] tts_audio_tags       currently: auto / main model
      [ ] compression          currently: auto / main model
      [ ] approval             currently: auto / main model
      [ ] triage_specifier     currently: auto / main model
      [ ] kanban_decomposer    currently: auto / main model
      [ ] profile_describer    currently: auto / main model
      [ ] delegation           currently: auto / inherit main agent

      اختر مهمة، ثم مزوّدًا (تفتح تدفّقات OAuth متصفّحًا؛ ويطلب مزوّدو مفاتيح API إدخال المفتاح)، ثم نموذجًا. يُحفظ التغيير في auxiliary.<task>.* ضمن config.yaml. الآلية نفسها المستخدمة في مُنتقي النموذج الرئيسي — لا حاجة لتعلّم صياغة إضافية.

      إدخال التفويض (Delegation) خاص: فهو يوجّه النموذج الذي يستخدمه subagents التابعون لـ delegate_task ويُحفظ في قسم delegation.* العلوي (delegation.provider / delegation.model) بدلًا من auxiliary.*، لأن الـ subagents وكلاء فرعيون كاملون، لا استدعاءات LLM جانبية. وتعني قيمته auto "ورث مزوّد الوكيل الأصل ونموذجه وبيانات اعتماده."

      إذا لم ترغب في أن يولّد Hermes عناوين تلقائيًا بعد أول تبادل، اضبط auxiliary.title_generation.enabled: false. تظل العناوين اليدوية تعمل عبر /title و hermes sessions rename.

      النقاط الطرفية المقتصرة على التدفّق (Stream-only)​

      ترفض بعض النقاط الطرفية المتوافقة مع OpenAI طلبات الدردشة غير المتدفقة تمامًا (مثلًا يُعيد Tencent Copilot الرمز 400 "Non-stream chat request is currently not supported"). الدردشة التفاعلية تتدفّق أصلًا، لكن المهام المساعدة (توليد العناوين، الضغط، الرؤية) تستخدم استدعاءات غير متدفّقة وستفشل في كل محاولة. يعامل Hermes دائمًا copilot.tencent.com كـ stream-only؛ ولأي نقطة طرفية أخرى من هذا النوع، أدرج جزءًا من رابط URL ضمن auxiliary.stream_only_base_urls:

      auxiliary:
        stream_only_base_urls:
          - "my-stream-only-proxy.example.com"

      تُرسل الاستدعاءات المساعدة المطابقة بـ stream=True وتُجمَّع القطع (بما فيها فروقات استدعاء الأدوات) على جانب العميل — دون أي تغيير في السلوك لأي نقطة طرفية أخرى.

      نمط الإعدادات العام​

      يستخدم كل فتحة نموذج في Hermes — المهام المساعدة، الضغط، الاحتياطي — المفاتيح الثلاثة نفسها:

      المفتاحما يفعلهالافتراضي
      providerأي مزوّد يُستخدم للمصادقة والتوجيه"auto"
      modelأي نموذج يُطلبافتراضي المزوّد
      base_urlنقطة طرفية مخصّصة متوافقة مع OpenAI (تتجاوز المزوّد)غير مضبوط

      تقبل كتل المهام المساعدة إضافةً إلى ذلك مفتاح reasoning_effort:

      المفتاحما يفعلهالافتراضي
      reasoning_effortمستوى التفكير لاستدعاءات LLM الخاصة بتلك المهمة: none، minimal، low، medium، high، xhigh، max، ultraغير مضبوط (افتراضي المزوّد)

      هذا هو النظير الخاص بكل مهمة لمفتاح agent.reasoning_effort العام: شغّل الضغط عند low أو الرؤية عند none لتقليل زمن استجابة وتكلفة المهام الجانبية عندما يكون نموذجك الرئيسي نموذج استدلال مكلفًا، دون المساس بسلوك دردشتك الرئيسية. يُطبَّق على مهام العميل المساعد مثل vision و compression و title_generation و curator، عبر صيغ الاتصال المساعدة الثلاث كلها (chat completions، Codex Responses، Anthropic Messages). أي extra_body.reasoning صريح على المهمة نفسها يتغلّب على هذا الاختصار.

      مراجعة الخلفية (Background review) مختلفة: فرع المراجعة بالنموذج نفسه يرث دائمًا مستوى استدلال الوكيل الأصل. يُتجاهل auxiliary.background_review.reasoning_effort في هذا المسار، حتى عند اختيار مزوّد/نموذج الوكيل الأصل صراحةً. يحافظ هذا على تطابق حرفي لإعدادات الاستدلال، وsystem prompt، ولقطة المحادثة الكاملة، وتعريفات الأدوات من أجل تطابق التخزين المؤقت للـ prompt؛ فلا يوجد مفتاح جهد مستقل للمراجعات بالنموذج نفسه. راجع استدلال مراجعة النموذج نفسه. أما مسألة جهد الفرع الموجَّه المنفصلة فهي مُتتبَّعة في #94825.

      يستخدم MoA أيضًا إعدادات مختلفة: يُضبط عمق الاستدلال لـ Mixture-of-Agents لكل فتحة (slot) ضمن preset الـ MoA (moa.presets.<name>.reference_models[].reasoning_effort / aggregator.reasoning_effort)، وليس على كتل moa_reference/moa_aggregator المساعدة — راجع Mixture of Agents.

      auxiliary:
        compression:
          reasoning_effort: "low"    # summaries don't need deep thinking
        vision:
          reasoning_effort: "none"   # disable thinking for image description

      عند ضبط base_url، يتجاهل Hermes المزوّد ويستدعي تلك النقطة الطرفية مباشرةً (باستخدام api_key أو OPENAI_API_KEY للمصادقة). وعند ضبط provider فقط، يستخدم Hermes مصادقة ذلك المزوّد الداخلية ونقطته الطرفية الأساسية.

      المزوّدون المتاحون للمهام المساعدة: auto، main، بالإضافة إلى أي مزوّد في سجل المزوّدين — openrouter، nous، openai-codex، copilot، copilot-acp، anthropic، gemini، qwen-oauth، zai، kimi-coding، kimi-coding-cn، minimax، minimax-cn، minimax-oauth، deepseek، nvidia، xai، xai-oauth، ollama-cloud، alibaba، bedrock، huggingface، arcee، xiaomi، kilocode، opencode-zen، opencode-go، opencode-free، commandcode، commandcode-anthropic، ai-gateway، azure-foundry — أو أي مزوّد مخصّص مسمّى من قاموس providers: الخاص بك (مثل provider: "beans").

      MiniMax OAuth

      يسجّل minimax-oauth الدخول عبر OAuth في المتصفح (دون حاجة لمفتاح API). شغّل hermes model واختر MiniMax (OAuth) للمصادقة. تستخدم المهام المساعدة MiniMax-M2.7-highspeed تلقائيًا. راجع دليل MiniMax OAuth.

      xAI Grok OAuth

      يسجّل xai-oauth الدخول عبر OAuth في المتصفح لمشتركي SuperGrok وX Premium+ (دون حاجة لمفتاح API). شغّل hermes model واختر xAI Grok OAuth (SuperGrok / Premium+) للمصادقة. يُعاد استخدام رمز OAuth نفسه لكل سطح مباشر مع xAI (الدردشة، المهام المساعدة، TTS، توليد الصور، توليد الفيديو، النسخ الصوتي). راجع دليل xAI Grok OAuth، وإذا كان Hermes على جهاز بعيد راجع OAuth عبر SSH / الأجهزة البعيدة.

      "main" للمهام المساعدة فقط

      يعني خيار المزوّد "main" "استخدم أيًا كان المزوّد الذي يستخدمه وكيلي الرئيسي" — وهو صالح فقط داخل auxiliary: و compression: وإدخالات الاحتياطي الأساسية (fallback_providers: أو fallback_model: القديم). وهو ليس قيمة صالحة لإعداد model.provider العلوي لديك. إذا كنت تستخدم نقطة طرفية مخصّصة متوافقة مع OpenAI، اضبط provider: custom في قسم model:. راجع مزوّدو الذكاء الاصطناعي (AI Providers) لكل خيارات مزوّد النموذج الرئيسي.

      معلومة

      لضغط السياق كتلة compression: خاصة به للعتبات وكتلة auxiliary.compression: لإعدادات النموذج/المزوّد — راجع ضغط السياق أعلاه. تستخدم سلسلة الاحتياط الأساسية قائمة fallback_providers: علوية — راجع المزوّدون الاحتياطيون (Fallback Providers). تتبع الثلاثة جميعها نمط provider/model/base_url نفسه.

      سلسلة الاحتياط لكل مهمة في المهام المساعدة​

      يمكن لكل مهمة مساعدة أن تعرّف اختياريًا fallback_chain — قائمة إدخالات provider/model يجربها Hermes عندما يفشل المزوّد المساعد الأساسي بسبب حدود المعدل، أو مشاكل الاتصال، أو قيود الدفع:

      auxiliary:
        compression:
          provider: openrouter
          model: openai/gpt-4o-mini
          fallback_chain:
            - provider: nous
              model: deepseek/deepseek-chat
            - provider: openrouter
              model: google/gemini-2.5-flash

      عندما يُعيد المزوّد المساعد الأساسي (openrouter / openai/gpt-4o-mini) خطأ حدّ معدل، أو مهلة اتصال، أو خطأ دفع مطلوب، يسير Hermes عبر fallback_chain بالترتيب. يتخطّى الإدخالات التي يطابق مزوّدها المزوّد الفاشل بالفعل، ويجرّب كل إدخال متبقٍ حتى ينجح أحدها أو تُستنفد السلسلة. إذا فشلت كل البدائل الاحتياطية، يعود Hermes إلى نموذج الوكيل الرئيسي كشبكة أمان أخيرة.

      يدعم كل إدخال المفاتيح الثلاثة نفسها التي تدعمها أي إعدادات مهمة مساعدة:

      المفتاحالوصف
      providerاسم المزوّد (nous، openrouter، anthropic، gemini، main، إلخ)
      modelاسم النموذج لذلك المزوّد
      base_url(اختياري) نقطة طرفية مخصّصة متوافقة مع OpenAI

      fallback_chain متاح لأي مهمة مساعدة — compression، vision، approval، skills_hub، mcp، إلخ.

      تحديد التزامن للمهام المساعدة​

      يحدّ max_concurrency من استدعاءات LLM الجارية للمهام المساعدة مثل compression و title_generation عبر العملية بأكملها. يُستثنى auxiliary.vision.max_concurrency: فهو يتحكّم بالفعل فقط في عمّال ترميز/تحجيم الصور المرتبطين بالمعالج (CPU) الخاصين بالرؤية، لا طلبات LLM. هذا مفيد أكثر ما يكون عندما:

      • يمكن أن تُطلق جلسات كثيرة عملًا خلفيًا في آن واحد (قنوات Discord/Telegram، طرفيات متعددة)
      • مزوّدك محدود المعدل أو يمرّ بحادثة، وإعادة المحاولة قد تضخّم الاندفاع

      الافتراضي غير محدود. سقف أمان نموذجي هو 2:

      auxiliary:
        title_generation:
          max_concurrency: 2
        compression:
          max_concurrency: 2

      تُحيط الإشارة (semaphore) بكامل الاستدعاء، بما في ذلك إعادات المحاولة والاحتياطيات، لذا يُحتسب الاستدعاء البطيء الواحد مرة واحدة فقط ضمن الحدّ.

      توجيه OpenRouter وموجِّه Pareto Code للمهام المساعدة​

      عندما تُحلّ مهمة مساعدة إلى OpenRouter (سواء صراحةً أو عبر provider: "main" بينما وكيلك الرئيسي على OpenRouter)، فإن إعدادات provider_routing و openrouter.min_coding_score الخاصة بالوكيل الرئيسي لا تنتقل تلقائيًا — بالتصميم، كل مهمة مساعدة مستقلة. لضبط تفضيلات مزوّد OpenRouter أو استخدام موجِّه Pareto Code لمهمة مساعدة معيّنة، اضبطها لكل مهمة عبر extra_body:

      auxiliary:
        compression:
          provider: openrouter
          model: openrouter/pareto-code         # use the Pareto Code router for this task
          extra_body:
            provider:                            # OpenRouter provider routing prefs
              order: [anthropic, google]         # try these providers in order
              sort: throughput                   # or "price" | "latency"
              # only: [anthropic]                # restrict to a specific provider
              # ignore: [deepinfra]              # exclude specific providers
            plugins:                             # OpenRouter Pareto Code router knob
              - id: pareto-router
                min_coding_score: 0.5            # 0.0–1.0; higher = stronger coders

      يعكس الشكل ما يقبله OpenRouter في جسم طلب chat completions. يُمرّر Hermes extra_body بأكمله كما هو، لذا يعمل أي حقل آخر موثَّق في جسم طلب OpenRouter على openrouter.ai/docs بالطريقة نفسها.

      تغيير نموذج الرؤية​

      لاستخدام GPT-4o بدلًا من Gemini Flash لتحليل الصور:

      auxiliary:
        vision:
          model: "openai/gpt-4o"

      أو عبر متغير بيئة (في ~/.hermes/.env):

      AUXILIARY_VISION_MODEL=openai/gpt-4o

      خيارات المزوّد​

      تنطبق هذه الخيارات على إعدادات المهام المساعدة (auxiliary:، compression:) وإدخالات الاحتياطي الأساسية (fallback_providers: أو fallback_model: القديم)، لا على إعداد model.provider الرئيسي لديك.

      المزوّدالوصفالمتطلبات

      يعمل هنا أيضًا مزوّدو مفاتيح API المباشرون من كتالوج المزوّدين الرئيسي عندما تريد أن تتجاوز المهام الجانبية موجِّهك الافتراضي. فمثلًا، gmi صالح متى أُعدّ GMI_API_KEY، و fireworks صالح متى أُعدّ FIREWORKS_API_KEY:

      auxiliary:
        compression:
          provider: "gmi"
          model: "anthropic/claude-opus-4.6"

      لتوجيه GMI المساعد، استخدم معرّف النموذج الدقيق الذي تُعيده نقطة GMI الطرفية /v1/models. تستخدم معرّفات نماذج Fireworks الصيغة الأصلية بشرطة مائلة للمزوّد، على سبيل المثال accounts/fireworks/models/glm-5p2.

      إعدادات شائعة​

      استخدام نقطة طرفية مخصّصة مباشرة (أوضح من provider: "main" لواجهات API المحلية/المستضافة ذاتيًا):

      auxiliary:
        vision:
          base_url: "http://localhost:1234/v1"
          api_key: "local-key"
          model: "qwen2.5-vl"

      يسبق base_url في الأولوية provider، لذا هذه هي الطريقة الأكثر وضوحًا لتوجيه مهمة مساعدة إلى نقطة طرفية محدّدة. لتجاوزات النقطة الطرفية المباشرة، يستخدم Hermes api_key المُعدّ أو يعود إلى OPENAI_API_KEY؛ ولا يعيد استخدام OPENROUTER_API_KEY لتلك النقطة الطرفية المخصّصة.

      auxiliary:

      model:

        base_url: https://api.minimax.io/anthropic

      نصيحة

      إذا كنت تستخدم Codex OAuth كمزوّد نموذجك الرئيسي، تعمل الرؤية تلقائيًا — دون إعداد إضافي. يُدرَج Codex ضمن سلسلة الاكتشاف التلقائي للرؤية.

      تحذير

      تتطلّب الرؤية نموذجًا متعدّد الوسائط. إذا ضبطت provider: "main"، تأكّد من أن نقطتك الطرفية تدعم تعدّد الوسائط/الرؤية — وإلا سيفشل تحليل الصور.

      متغيرات البيئة (قديمة)​

      يمكن أيضًا إعداد النماذج المساعدة عبر متغيرات البيئة. مع ذلك، config.yaml هو الطريقة المفضّلة — فهي أسهل في الإدارة وتدعم كل الخيارات بما فيها base_url و api_key.

      مزوّد الرؤيةAUXILIARY_VISION_PROVIDER
      نموذج الرؤيةAUXILIARY_VISION_MODEL
      نقطة الرؤية الطرفيةAUXILIARY_VISION_BASE_URL

      نصيحة

      شغّل hermes config لعرض إعدادات النماذج المساعدة الحالية لديك. لا تظهر التجاوزات إلا عندما تختلف عن الافتراضيات.

      جهد الاستدلال (Reasoning Effort)​

      تحكّم في مقدار "التفكير" الذي يقوم به النموذج قبل الرد:

      agent:
        reasoning_effort: ""   # empty = medium. Options: none, minimal, low, medium, high, xhigh, max, ultra

      عندما لا يُضبط (الافتراضي)، يكون جهد الاستدلال "medium" افتراضيًا — مستوى متوازن يناسب معظم المهام. يتجاوز ضبط قيمة هذا الافتراضي — إذ يمنح جهد الاستدلال الأعلى نتائج أفضل على المهام المعقّدة مقابل مزيد من الرموز وزمن الاستجابة.

      نماذج التفكير التكيّفي (Claude 4.6+، فئة Fable/Mythos) عبر OpenRouter

      تستخدم هذه النماذج تفكيرًا تكيّفيًا ولا تقبل حقل reasoning.effort المعتاد — يتجاهله OpenRouter بالنسبة لها. يوجّه Hermes reasoning_effort الخاص بك بشفافية إلى معامل verbosity الخاص بـ OpenRouter بدلًا من ذلك (والذي يُطابق output_config.effort لدى Anthropic)، بحيث يستمر مفتاح الجهد نفسه في العمل مع المستويات التي يدعمها النموذج المختار. none (أو عدم الضبط) يترك النموذج على افتراضه التكيّفي الخاص. أما مزوّد Anthropic الأصلي فيتحكّم في الجهد مباشرةً وغير متأثر بهذا.

      نماذج OpenRouter ومستويات الجهد المدعومة

      بالنسبة للنماذج الأخرى المُوجَّهة عبر OpenRouter، يقرأ Hermes بيانات الاستدلال الوصفية للكتالوج الحي للنماذج (supported_parameters بالإضافة إلى reasoning.supported_efforts الخاصة بكل نموذج) ليقرّر ما إذا كان سيرسل ضوابط استدلال من الأساس، وليحصر الجهد المطلوب منك إلى أقرب مستوى يدعمه المسار فعليًا (هبوطًا دائمًا — مثلًا يصبح ultra هو high على مسار يتوقف عند high، أبدًا تصعيدًا صامتًا). تعمل جهات البيع الجديدة القادرة على الاستدلال تلقائيًا دون انتظار تحديث لـ Hermes؛ وعندما يتعذّر الوصول إلى الكتالوج أو لا يكون نموذج مُدرجًا، يعود Hermes إلى قائمة عائلات النماذج المدمجة الخاصة به ويمرّر جهدك دون تغيير.

      يمكنك أيضًا تغيير جهد الاستدلال أثناء التشغيل باستخدام الأمر /reasoning:

      /reasoning                # Show current effort level and display state
      /reasoning high           # Set reasoning effort to high (this session only)
      /reasoning high --global  # Set effort and persist to config.yaml
      /reasoning none           # Disable reasoning (this session only)
      /reasoning show           # Show model thinking above each response
      /reasoning hide           # Hide model thinking

      تغييرات الجهد مقتصرة على نطاق الجلسة افتراضيًا؛ أضف --global لحفظ المستوى الجديد كافتراضي agent.reasoning_effort لديك.

      تجاوزات الاستدلال لكل نموذج​

      يمكنك ضبط مستويات جهد استدلال مختلفة لنماذج مختلفة. هذا مفيد عندما تريد جهدًا عاليًا للنماذج المعقّدة ومتوسطًا للنماذج الأسرع:

      agent:
        reasoning_effort: "medium"       # global default
        reasoning_overrides:
          "openrouter/anthropic/claude-opus-4.5": "xhigh"
          "openai/gpt-5": "low"
          "claude-sonnet-4.6": "high"    # bare model name also works

      مطابقة المفاتيح متسامحة مع طريقة الكتابة — تُطابَق أي صيغة كتابة معقولة:

      • claude-opus-4.5، claude-opus-4-5، claude-opus.4.5 (النقاط والشرطات قابلة للتبادل)
      • anthropic/claude-opus-4.5، openrouter/anthropic/claude-opus-4.5 (بادئة المزوّد اختيارية)
      • المطابقات الدقيقة لها الأولوية على المتغيرات
      ملاحظة

      لا يوجد دعم في hermes config set لمفاتيح reasoning_overrides — حرّر ملف YAML مباشرةً. السبب أن أسماء النماذج غالبًا ما تحتوي على نقاط (مثل claude-opus-4.5)، وهو ما يتعارض مع صياغة المفاتيح المنقوطة الخاصة بـ CLI.

      أولوية الحل:

      1. تجاوز /reasoning --session على نطاق الجلسة (gateway فقط)
      2. تجاوز لكل نموذج من agent.reasoning_overrides (متسامح مع طريقة الكتابة)
      3. agent.reasoning_effort العام
      4. افتراضي المزوّد

      يُطبَّق التجاوز تلقائيًا في كل مكان: بدء تشغيل CLI، وgateway المراسلة، وDesktop/TUI، ومهام cron، وتبديلات /model في منتصف الجلسة، وتفعيل النموذج الاحتياطي.

      الوضع السريع (Fast Mode)​

      يطلب الوضع السريع من المزوّد مُخرَجات أسرع مقابل سعر إضافي: Priority Processing من OpenAI (service_tier: priority)، وxAI Priority Processing على Grok 4.6، وFast Mode من Anthropic (speed: fast، لـ Opus 4.8 / Opus 5 فقط). وهو معطّل افتراضيًا.

      agent:
        service_tier: ""          # "" / normal | fast | auto | cold
        fast_auto_seconds: 60     # window for auto / cold
      الوضعمتى تُرسَل معاملات السرعةاستخدمه من أجل
      normal (الافتراضي، "")أبدًاالأرخص؛ زمن استجابة قياسي
      fastكل طلبالجلسات التفاعلية الطويلة حيث تريد السرعة دائمًا
      autoالطلبات في أول fast_auto_seconds من كل دورردّ أول سريع؛ حلقات الأدوات الطويلة تعود إلى التسعير القياسي
      coldالنافذة نفسها، لكن فقط في الدور الأول من الجلسة (بلا تاريخ سابق)ردّ سريع لبداية الجلسة، وتسعير قياسي بعد ذلك

      يبدّل /fast normal|fast|auto|cold الوضع لتلك الجلسة؛ أضف --global لحفظه في config.yaml. يعرض /fast وحده الوضع الحالي.

      ملاحظة حول التكلفة: يفرض كلا المزوّدَين رسومًا على الطلبات السريعة بمُضاعِف على الأسعار القياسية (Anthropic: 10$ / 50$ لكل مليون رمز إدخال/إخراج على Opus 4.8 وOpus 5)، وتتراكم مع تسعير التخزين المؤقت للـ prompt. يحدّ auto/cold تلك الزيادة إلى النافذة فقط. تُرسل معاملات السرعة فقط إلى النقطة الطرفية من الطرف الأول التي تدعمها (api.openai.com / اشتراك Codex، api.anthropic.com، api.x.ai)؛ ولا تتلقّاها مسارات OpenRouter وNous Portal وCopilot وAzure وBedrock وأي base_url مخصّص في أي وضع. لا يتغيّر إلا المعامل الخاص بكل طلب بين الطلبات — يبقى system prompt والأدوات والرسائل مطابقة حرفيًا، لذا ينجو التخزين المؤقت للـ prompt من حدود النافذة.

      فرض استخدام الأدوات (Tool-Use Enforcement)​

      تصف بعض النماذج أحيانًا الإجراءات المقصودة كنص بدلًا من إجراء استدعاءات أدوات ("سأشغّل الاختبارات..." بدلًا من استدعاء الطرفية فعليًا). يُدرج فرض استخدام الأدوات إرشادًا في system prompt يعيد توجيه النموذج نحو استدعاء الأدوات فعليًا.

      agent:
        tool_use_enforcement: "auto"   # "auto" | true | false | ["model-substring", ...]
      القيمةالسلوك
      "auto" (الافتراضي)مُفعّل للنماذج المطابقة لـ: gpt، codex، gemini، gemma، grok، glm، qwen، deepseek، muse. معطّل لكل ما عداها (مثل Claude).
      trueمُفعّل دائمًا، بغض النظر عن النموذج. مفيد إذا لاحظت أن نموذجك الحالي يصف الإجراءات بدلًا من تنفيذها.
      falseمعطّل دائمًا، بغض النظر عن النموذج.
      ["gpt", "codex", "qwen", "llama"]مُفعّل فقط عندما يحتوي اسم النموذج على إحدى السلاسل المُدرجة (بغض النظر عن حالة الأحرف).

      ما الذي يُدرَج​

      عند التفعيل، قد تُضاف طبقتان من الإرشاد إلى system prompt:

      1. فرض استخدام الأدوات العام (كل النماذج المطابقة) — يوجّه النموذج لإجراء استدعاءات الأدوات فورًا بدلًا من وصف النوايا، ومواصلة العمل حتى اكتمال المهمة، وعدم إنهاء دور بوعد بعمل مستقبلي أبدًا.

      2. إرشاد Google التشغيلي (نماذج Gemini وGemma فقط) — الإيجاز، والمسارات المطلقة، واستدعاءات الأدوات المتوازية، وأنماط التحقّق قبل التعديل.

      هذه الإرشادات شفافة للمستخدم ولا تؤثر إلا على system prompt. النماذج التي تستخدم الأدوات بموثوقية بالفعل (مثل Claude) لا تحتاج إلى هذا الإرشاد، وهذا سبب استثناء "auto" لها.

      متى تفعّله​

      إذا كنت تستخدم نموذجًا غير مُدرَج في قائمة auto الافتراضية ولاحظت أنه كثيرًا ما يصف ما كان سيفعله بدلًا من فعله، اضبط tool_use_enforcement: true أو أضف جزءًا من اسم النموذج إلى القائمة:

      agent:
        tool_use_enforcement: ["gpt", "codex", "gemini", "grok", "my-custom-model"]

      إرشاد انضباط التنفيذ (Execution-Discipline)​

      بمعزل عن فرض استخدام الأدوات، يُدرج Hermes كتلة انضباط تنفيذ لعائلات نماذج تتشارك مجموعة من أنماط الفشل الوكيلي المُلاحَظة في آثار التقييم: إجراء الحساب في النثر بدلًا من الكود، وتخطّي التحقّق بالقراءة الرجعية بعد الكتابات الخارجية، و"إصلاح" المعرّفات المشوَّهة، وادّعاء الاكتمال رغم تباين الأعداد، وإعلان "الانتهاء" دون التحقّق من كل معيار قبول.

      agent:
        execution_guidance: "auto"   # "auto" | true | false | ["model-substring", ...]
      القيمةالسلوك
      "auto" (الافتراضي)مُفعّل للنماذج المطابقة لـ: gpt، codex، grok، deepseek، kimi، qwen، glm، minimax، mimo، mistral، muse.
      trueمُفعّل دائمًا، بغض النظر عن النموذج.
      falseمعطّل دائمًا، بغض النظر عن النموذج.
      ["deepseek", "my-custom-model"]مُفعّل فقط عندما يحتوي اسم النموذج على إحدى السلاسل المُدرجة (بغض النظر عن حالة الأحرف).

      تغطّي الكتلة المُدرجة:

      • مثابرة الأدوات — مواصلة استدعاء الأدوات حتى تكتمل المهمة وتُتحقَّق؛ إعادة محاولة نتائج البحث الفارغة أو الجزئية أو الضيّقة بشكل مريب باستعلام أوسع أو مختلف قبل الخلوص إلى نتيجة.
      • استخدام الأدوات الإلزامي — الحساب، والتجزئات (hashes)، والتواريخ، وحالة النظام، وحقائق الملفات تأتي دائمًا من أداة، لا من حساب ذهني أبدًا.
      • القراءة الرجعية بعد الكتابة الخارجية — بعد أي كتابة تُغيّر الحالة إلى نظام خارجي، اقرأ الهدف الدقيق قبل ادّعاء النجاح (تعديلات الملفات الداخلية التي أكّدتها أداة بالفعل لا تُعاد التحقّق منها).
      • تسوية الأعداد — الإجماليات المُعلَنة (total، reply_count، has_more) تأكيدات صارمة؛ عند التباين، أعد الجلب أو التحليل برمجيًا.
      • الحفاظ الحرفي — عدم تطبيع أو "إصلاح" المعرّفات التي تفشل في مطابقة صيغة محدّدة أبدًا؛ نجاح البحث لا يُصحّح رمز مصدر مشوَّه.
      • الاكتمال المشروط بالتحقّق — "الانتهاء" يعني أن كل معيار قبول مُسمّى تم التحقّق منه، لا مجموعة جزئية معقولة أبدًا.

      هذه البوّابة مستقلة عن tool_use_enforcement — يمكن تفعيل إحداهما دون الأخرى. يُختار الإرشاد مرة واحدة عند بدء الجلسة استنادًا إلى اسم النموذج، بحيث يبقى system prompt ثابتًا حرفيًا (وملائمًا للتخزين المؤقت للـ prompt) طوال عمر المحادثة. تُستثنى Gemini/Gemma من قائمة auto لأنها تتلقّى إرشاد Google التشغيلي الأكثر تحديدًا؛ ويُستثنى Claude لأنه لا يُظهر أنماط الفشل هذه — أدرج أي نموذج بـ true أو بقائمة سلاسل فرعية.

      حواجز حماية حلقات الأدوات (Tool-Loop Guardrails)​

      يكتشف Hermes متى يكون الوكيل عالقًا في حلقة استدعاء أدوات غير مثمرة — الاستدعاء نفسه يفشل مرارًا، أو الأداة نفسها تفشل مرارًا وتكرارًا، أو استدعاء عديم التأثير (idempotent) يُعيد النتيجة نفسها دون تقدّم. افتراضيًا، يُدرج تحذيرًا في نتيجة الأداة كي يصحّح النموذج نفسه ذاتيًا. تبقى جلسات CLI وTUI وDesktop وACP التفاعلية تحذيرية فقط لأن بإمكان شخص التدخّل؛ أما جلسات gateway وcron غير المراقَبة فتُفعّل التوقفات الصارمة افتراضيًا.

      يمكن تعطيل الافتراضي الواعي بالمنصة لنشر غير مراقَب، أو يمكن تفعيل التوقفات الصارمة صراحةً على كل منصة:

      tool_loop_guardrails:
        warnings_enabled: true       # inject warnings into tool results (default: true)
        hard_stop_enabled: false     # also BLOCK the call past the hard-stop threshold (default: false)
        non_interactive_hard_stop_enabled: true  # default hard stops for gateway/cron
        warn_after:
          exact_failure: 2           # identical failing call repeated N times
          same_tool_failure: 3       # same tool failing N times (different args)
          idempotent_no_progress: 2  # same result, no progress, N times
        hard_stop_after:
          exact_failure: 5
          same_tool_failure: 8
          idempotent_no_progress: 5
        loop_caps:
          max_web_searches: 50       # max web_search calls per turn (0 = unlimited)
          max_subagents: 50          # max subagents spawned per turn (0 = unlimited)

      يُفعّل hard_stop_enabled صراحةً التوقفات الصارمة على كل منصة. وعندما يبقى false، لا يزال non_interactive_hard_stop_enabled يُفعّلها لمنصات gateway/cron غير المراقَبة مع الحفاظ على السلوك التحذيري فقط لـ CLI وTUI وDesktop وACP والـ subagents وتشغيلات api_server (حلقات مهام مُشرَف عليها بوجود أصل أو عميل حيّ). اضبط non_interactive_hard_stop_enabled: false لإخراج نشر غير مراقَب من ذلك. راجع أيضًا Docker / عمليات النشر غير المراقَبة.

      صُممت التوقفات الصارمة لالتقاط عمليات الإعادة (replays) — الاستدعاء نفسه، دون تغيير، دون أن يحدث شيء بينهما — لا التكرار المشروع:

      • التعديل ثم إعادة التشغيل ليست حلقة أبدًا. أي استدعاء ناجح يُغيّر الحالة (write_file، patch، تشغيل ناجح لـ terminal/execute_code، إجراء متصفح، تعديل مهمة/رسالة/cron) يُسجّل تقدّمًا لكل استدعاء فاشل ما زال يُحتسب. تبدأ إعادة المحاولة المتطابقة التالية (إعادة تشغيل اختبار فاشل بعد إصلاح، إعادة أخذ لقطة بعد نقرة) سلسلة جديدة بدلًا من التراكم نحو حظر.
      • الأوامر الفاشلة المتمايزة تشخيص، لا حلقة. بالنسبة للأدوات التي يكون خروجها غير الصفري مُخرَجًا عاديًا فيها (terminal، execute_code، مستطلعو العمليات، browser_navigate، web_extract)، تحذّر عتبة same_tool_failure فقط ولا توقف أبدًا. لا يمكن إيقافها إلا بإعادة تنفيذ مطابقة تمامًا للمعاملات دون تغيير متداخل، أو سلسلة نتائج متطابقة.
      • التوقف ينهي الدور، لا الجلسة. يردّ الوكيل بذكر الحاجز الذي أُطلق وسببه؛ والردّ بـ"تابع" يستأنف بعدّادات جديدة لكل دور.

      أسقف الحلقات المنفلتة لكل دور​

      بمعزل عن العتبات القائمة على الفشل أعلاه، يضبط loop_caps أسقفًا صارمة لعدد استدعاءات web_search وعمليات إطلاق subagents التي يمكن أن تجريها حلقة وكيل واحدة (دور). تُعاد ضبط العدّادات في بداية كل دور، لذا لا تُحرَم جلسة مشروعة متعددة الأدوار أبدًا — لكن دورًا واحدًا ينزلق إلى بحث أو تفويض غير محدود يُوقَف. هذه دائمًا مُفعّلة وتُطلَق بغض النظر عن hard_stop_enabled. دور واحد يُصدر عشرات عمليات البحث في الويب أو يُطلق عشرات الـ subagents مرَضي بالفعل، لذا فإن الافتراضيات منخفضة. عند بلوغ سقف، يُحظر استدعاء الأداة المخالف برسالة توضيحية ويتوقف الدور بنظافة بدلًا من استنزاف بقية الميزانية. اضبط أيًا من القيمتين على 0 لتعطيل ذلك السقف تمامًا.

      تُحتسَب كل مهمة في دفعة delegate_task واحدة ضمن max_subagents (تُنفق دفعة من 3 مهام 3)، لذا يتتبّع السقف عدد الـ subagents الفعلي المُطلَق لا استدعاءات delegate_task.

      يحاكي هذا أسقف WebSearch والـ subagents لكل جلسة في Claude Code (الإصدار v2.1.212)، والتي تكون افتراضيًا 200 أيضًا وتُعاد ضبطها عند /clear.

      حرّاس منع التجمّد وقت التشغيل​

      استكمالًا للحواجز القائمة على الفشل أعلاه، يُفعّل agent.stall_guards (الافتراضي true) حارسَين متحفّظَين وقت التشغيل ضد إهدار الأدوار. أولًا، كاسر حلقة الاستدعاء المتطابق: عندما تُستدعى الأداة نفسها 3 مرات متتالية أو أكثر بمعاملات متطابقة وتُعيد نتيجة متطابقة، يُلحَق إشعار قصير من سطر واحد بنتيجة تلك الأداة يخبر النموذج بعدم تكرار الاستدعاء — في الجلسات التحذيرية فقط لا يحظر الاستدعاء أبدًا، والمستطلعون (pollers) القابلون للتكرار المشروع (process، *_get_result، *_poll) مُستثنَون. عندما تكون التوقفات الصارمة مُفعَّلة (سواء hard_stop_enabled صراحةً، أو منصة gateway/cron غير مراقَبة)، تصبح السلسلة نفسها توقفًا صارمًا أيضًا حال بلوغها hard_stop_after.idempotent_no_progress استدعاءً متطابقًا متتاليًا — لـأي أداة، لا الأدوات للقراءة فقط التي يتتبّعها حارس idempotent_no_progress فحسب — بحيث يُوقَف نموذج يعيد استدعاء terminal أو skill_view الناجح نفسه بدلًا من استنزاف ميزانية التكرار (identical_call_streak_halt). ثانيًا، استرداد نيّة المواصلة: عندما ينهي النموذج دورًا دون استدعاءات أدوات لكن رده القصير ينتهي بإعلان عن إجراء ("دعني الآن أحدّث الملف…")، يُعيد Hermes تحفيزه للتصرّف عبر آلية الاستمرار المحدودة نفسها المستخدمة لاسترداد نيّة الإقرار (بحدّ أقصى إعادتَي تحفيز لكل دور). كلاهما آمنان للتخزين المؤقت (تُضاف الإشعارات عند بناء النتيجة، لا بأثر رجعي أبدًا) ويمكن تعطيلهما معًا:

      agent:
        stall_guards: false

      تُفعّل البوّابة نفسها أيضًا اختزال مرجعية النتيجة: عندما يُعيد استدعاء أداة مُعاد إصداره متطابقًا نتيجة جديدة مطابقة حرفيًا، تدخل الحمولة (payload) المكرَّرة السياق كطُوقة (stub) مرجعية قصيرة تشير إلى النتيجة السابقة (اسم الأداة، و tool_call_id، وملخّص للمعاملات، وإن كانت النتيجة الأولى قد حُفظت على القرص، مسار الفائض الخاص بها) بدلًا من تكرار المُخرَج الكامل. تُنفَّذ الأداة في كل مرة رغم ذلك، فتُحفَظ دلالة الاستطلاع (polling): تمرّ أي نتيجة متغيّرة دائمًا كاملة. لا تُختزَل أبدًا النتائج الأقل من 512 حرفًا، ونتائج الخطأ، والنتائج متعدّدة الوسائط، بينما تُختزَل نتائج المستطلعين (pollers) — فالاستطلاع غير المتغيّر هو تحديدًا الحالة التي لا تحمل فيها الحمولة المكرَّرة أي معلومة.

      مراقب دليل حياة الدور (Turn Liveness Watchdog)​

      يحدّ agent.turn_liveness المدة التي يمكن أن يمرّ فيها دور محادثة دون تقدّم ملحوظ قبل أن يُجري Hermes استردادًا قسريًا له. تعتمد المراقبة على ساعة النشاط (الإشارة نفسها التي تُختم بها انتظارات API، ورموز التدفّق، ونبضات الأداة — تجديد الإيجار (lease) لا يُحتسب أبدًا)، بحيث يظهر بصوت عالٍ الدور الذي ينحشر صامتًا في منتصف تنفيذه (لوحظ ذلك في المسألة رقم 95548: لا تنفيذ أداة، ولا استدعاء API، ولا خطأ، لكن الجلسة تبقى "مشغولة" إلى ما لا نهاية)، فيُقاطَع بحيث يُلفّ (unwind) كدور قابل لإعادة المحاولة مقاطَع — وعندما يتعذّر على المقاطعة فكّ الانحشار، يتوقف تجديد إيجار الدور الدائم كي يستطيع تنظيف الأدوار الراكدة استرداد الجلسة بدلًا من تعليقها حتى تُقتَل العملية.

      agent:
        turn_liveness:
          timeout_s: 600.0   # idle bound; <= 0 disables the watchdog
          poll_s: 15.0        # sampling interval (seconds)

      لا يُعاقَب العمل البطيء المشروع: فالردود المتدفّقة، ونبضات الأداة (كل 30 ثانية أثناء تشغيل أداة)، وانتظارات الموافقة تلمس جميعها الساعة، لذا لا يُطلَق المراقب إلا في دور لا يحرز أي تقدّم طوال الحدّ الكامل. تُسجَّل القيم غير الصالحة (خطأ إملائي، NaN، Inf، poll_s غير موجب) تحذيرًا وتعود إلى الافتراضيات — فهي لا تُعطّل بدء التشغيل أبدًا أو تُعطّل المراقب صامتًا. يُبلّغ إلغاء أُطلق عن التجمّد فور بدء الاسترداد، ولا يُصدر النتيجة النهائية (مقاطَع/توقّف الإيجار) إلا بعد أن تكون المقاطعة قد التزمت فعليًا.

      ملخّص الدور وتدفّق رموز مؤشر الانتظار (Spinner)​

      يطبع display.turn_summary (الافتراضي true) سطر محاسبة خافتًا واحدًا بعد كل دور في CLI التفاعلي، يلخّص ما فعله ذلك الدور فعليًا:

      ⋯ 12.4s · edited 2 files +18 -3 · read 4 files · ran 3 commands

      يُلاحَظ الحصر من تغذية تقدّم الأدوات التي تتلقّاها CLI بالفعل، لذا لا يكلّف شيئًا إضافيًا. تفاصيل:

      • وقت الجدار الزمني هو المدة الفعلية للدور (2m05s بعد نقطة الدقيقة الواحدة).
      • تُجمَّع استدعاءات الأدوات حسب الفعل (edited، read، ran، searched، …) بصيغة جمع صحيحة؛ وتُدمَج أدوات الإضافات/MCP التي لا فعل مُنسَّق لها في called N tools.
      • يظهر السطر +X -Y لفروقات الأسطر فقط عندما تُبلّغ نتيجة الأداة بالفعل عن فرق (حاليًا patch). لا يستدعي Hermes git أبدًا لحسابها، لذا يُحتسَب تعديل write_file دون فرق.
      • لا تُحتسَب استدعاءات الأدوات الفاشلة — كتابة مرفوضة لا تُعرَض أبدًا كتعديل ناجح (راجع مدقّق تعديل الملفات للتحذير المكمّل).
      • تُحدَّد الأدوار الطويلة بأربعة أجزاء فعل بالإضافة إلى ذيل +N more بحيث لا يلتفّ السطر أبدًا.
      • لا يطبع دور سريع بلا استدعاءات أدوات شيئًا على الإطلاق.

      يُلحق display.spinner_token_flow (الافتراضي true) رموز الإخراج التراكمية للدور الجاري بمؤقت مؤشر الانتظار الحي في CLI:

        ⚡ Reading cli.py  (  2.3s · ↓ 1.2k tok)

      العدّ لكل دور (تُحدَّد إجماليات الجلسة كخط أساس عند بداية الدور) ويتحدّث مع تبليغ كل استدعاء API في الدور عن الاستخدام. لا يُعرَض شيء قبل وصول أول تقرير استخدام، فلن ترى أبدًا ↓ 0 tok مضلّلًا.

      مدقّق تعديل الملفات​

      عندما يكون display.file_mutation_verifier على true (الافتراضي)، يُلحق Hermes تنبيهًا من سطر واحد برد المساعد النهائي كلّما فشل استدعاء write_file أو patch أثناء الدور ولم يُستبدَل قط بكتابة ناجحة إلى المسار نفسه. يلتقط هذا صنف "دفعة تصحيحات متوازية، نصفها يفشل صامتًا، والنموذج يلخّص النجاح" دون أن يتطلّب منك تشغيل git status يدويًا بعد كل تعديل.

      مثال على تذييل:

      ⚠️ File-mutation verifier: 3 file(s) were NOT modified this turn despite any wording above that may suggest otherwise. Run `git status` or `read_file` to confirm.
        • concepts/automatic-organization.md — [patch] Could not find match for old_string
        • concepts/lora.md — [patch] Could not find match for old_string
        • concepts/rag-pipeline.md — [patch] Could not find match for old_string

      اضبط file_mutation_verifier: false (أو HERMES_FILE_MUTATION_VERIFIER=0) لكبت التذييل. لا يُطلَق المدقّق إلا عندما تبقى إخفاقات فعلية معلَّقة عند نهاية الدور — نموذج يعيد محاولة تصحيح فاشل وينجح ضمن الدور نفسه لن يُطلقه لذلك الملف.

      ثِق بالمدقّق أكثر من ملخّص النموذج. يعني التذييل أن الملفات المُدرجة لم تُعدَّل على القرص، حتى لو قالت رسالة المساعد الختامية إن المهمة اكتملت. الأسباب الشائعة:

      • الكتابة مرفوضة — المسار على قائمة حظر بيانات الاعتماد أو خارج HERMES_WRITE_SAFE_ROOT (راجع أمان كتابة الملفات)
      • عدم تطابق الترقيع (Patch) — لم يطابق old_string الملف على القرص
      • بوّابة الصياغة (Syntax) — فشل المحتوى المرشَّح في التحقّق من صحة JSON/YAML/TOML قبل الكتابة

      مثال على تذييل عند حظر الكتابات:

      ⚠️ File-mutation verifier: 2 file(s) were NOT modified this turn despite any wording above that may suggest otherwise. Run `git status` or `read_file` to confirm.
        • ~/.hermes/cron/jobs.json — [patch] Write denied: '…' is outside HERMES_WRITE_SAFE_ROOT (/path/to/project)
        • ~/.hermes/scripts/monitor.py — [write_file] Write denied: '…' is outside HERMES_WRITE_SAFE_ROOT (/path/to/project)

      إذا كانت الكتابات إلى حالة Hermes (مهام cron، والمهارات، والسكربتات تحت ~/.hermes/) تفشل، تحقّق مما إذا كان HERMES_WRITE_SAFE_ROOT مضبوطًا في بيئتك. لتغييرات cron، استخدم أداة cronjob أو hermes cron edit بدلًا من ترقيع jobs.json مباشرةً.

      لغة واجهة المستخدم للرسائل الثابتة​

      يترجم إعداد display.language مجموعة صغيرة من الرسائل الثابتة الموجّهة للمستخدم — مطالبة الموافقة في CLI، وبعض ردود أوامر gateway الشرطية (مثل إشعارات إيقاف إعادة التشغيل التدريجي، و"انتهت صلاحية الموافقة"، و"تم مسح الهدف"). وهو لا يترجم ردود الوكيل، أو سطور السجلّ، أو مُخرَجات الأدوات، أو تتبّعات الأخطاء (tracebacks)، أو أوصاف الأوامر الشرطية — تبقى هذه بالإنجليزية. إذا أردت أن يردّ الوكيل نفسه بلغة أخرى، فأخبره ببساطة في prompt أو رسالة النظام الخاصة بك.

      القيم المدعومة: en (الافتراضي)، zh (الصينية المبسّطة)، zh-hant (الصينية التقليدية)، ja (اليابانية)، de (الألمانية)، es (الإسبانية)، fr (الفرنسية)، tr (التركية)، uk (الأوكرانية)، af (الأفريكانية)، ko (الكورية)، it (الإيطالية)، ga (الأيرلندية)، pt (البرتغالية)، ru (الروسية)، hu (المجرية). القيم غير المعروفة تعود إلى الإنجليزية.

      يمكنك أيضًا ضبط هذا لكل جلسة عبر متغير البيئة HERMES_LANGUAGE، الذي يتجاوز قيمة الإعدادات.

      عرض التركيز (/focus، CLI + TUI)​

      يُفعّل display.focus_view: true عرض التركيز — وضع عرض مخفَّض المُخرَجات لوقت تريد فيه الإجابة، لا سرد الأحداث خطوة بخطوة. إنه طبقة رقيقة فوق آلية tool_progress نفسها بدلًا من مسار كبت ثانٍ:

      • تفعيله يُثبّت tool_progress على off ويخزّن وضعك السابق في display.focus_saved_tool_progress؛
      • يستعيد /focus off ذلك الوضع تمامًا، بحيث ينجو إعداد /verbose verbose من رحلة الذهاب والإياب؛
      • ينتهي كل دور مكتمل بسطر استرداد خافت — ⋯ 7 tool lines hidden · /focus off to show — يُحتسَب مقابل وضعك قبل التركيز، بحيث لا يدّعي أبدًا إخفاء أسطر كنت قد أوقفتها بالفعل؛
      • شارة ◉ focus دائمة تجلس في شريط الحالة (كلٌّ من CLI المبني على prompt_toolkit وInk TUI) بحيث لا يكون الوضع المخفَّض غير مرئي أبدًا؛
      • التنقّل عبر /verbose أثناء تفعيل التركيز يعيد الوضع إلى /verbose ويمسح الشارة.

      عرض التركيز مخصّص للعرض فقط. فهو لا يعدّل أبدًا تاريخ المحادثة، أو system prompt، أو مخططات الأدوات، أو أي حمولة طلب؛ فالتفصيل المخفي مكبوت على الشاشة، لا محذوف أبدًا، والتخزين المؤقت للـ prompt غير متأثر تمامًا.

      اختيار حقول شريط الحالة (CLI/TUI)​

      يعرض شريط الحالة التفاعلي أسفل CLI/TUI النموذج، واستخدام السياق، وعدد عمليات الضغط، وعدّادات النشاط الخلفي، والمؤقّتات، وشارات الوضع. يختار display.status_bar.fields أيًا منها يكون مرئيًا — مفيد لشريط أدنى (النموذج + المدة فقط) أو لإظهار إجمالي رموز الجلسة الاختياري:

      display:
        status_bar:
          fields: ["model", "duration", "total_tokens"]   # visibility only; built-in order is preserved

      الحقول المدعومة: model، و context_detail (الرموز المستخدَمة/الإجمالية)، و context_pct (النسبة المئوية + مقياس)، و cache_hit (نسبة إصابة التخزين المؤقت للـ prompt — تُعاد ضبطها عند تبديل النموذج والضغط)، و latency (متوسط زمن استجابة API المتحرّك، لآخر 10 استدعاءات)، و tps (متوسط رموز الإخراج/الثانية المتحرّك، لآخر 10 استدعاءات)، و compressions، و bg_tasks، و bg_processes، و bg_subagents، و goal، و git_branch (⎇ فرع git الحالي لدليل العمل — اختياري فقط، لا يُعرَض افتراضيًا أبدًا؛ يعرض HEAD المنفصل commit مختصرًا)، و duration، و prompt_elapsed، و idle_since، و focus، و yolo، و stash، و battery، و title (شارة الجلسة محاذاة لليمين)، و total_tokens (مجموع الجلسة Σ — اختياري فقط، لا يُعرَض افتراضيًا أبدًا).

      • تتحكّم الإعدادات في الظهور، لا الترتيب؛ تُعرَض الحقول في مواضعها المدمجة.
      • ما زالت الطرفيات الضيّقة تسقط الحقول الخاصة بالوضع العريض فقط (context_detail، cache_hit، latency، tps، prompt_elapsed، idle_since) بغض النظر عن الإعدادات (يظهر cache_hit أيضًا في الفئة المتوسطة ≥52 عمودًا).
      • يبقى latency/tps مخفيَّين حتى تُسجَّل استدعاءات API (مثلًا لا يُبلّغ backend خادم تطبيق Codex عن زمن استجابة).
      • يتوافق ظهور battery و title هنا مع مفاتيح التبديل الخاصة بهما (/battery، /title) — يجب تفعيل كليهما ليظهر القطاع.
      • يُصفّي المفتاح نفسه أيضًا قاعدة حالة Ink TUI (hermes tui)، حيث تُعرَض cache_hit و latency و tps كأجزاء ذيلية مُخصَّصة بالعرض (◎ / ◷ / ↑) على الطرفيات ذات ≥96/104/110 عمودًا على التوالي.
      • مخصّص للعرض فقط: لا أثر على التخزين المؤقت للـ prompt أو حمولات الطلبات. تسري التغييرات عند بدء الجلسة التالية.

      تذييل بيانات التشغيل الوصفية (gateway فقط)​

      عندما يكون display.runtime_footer.enabled: true، يُلحق Hermes تذييل سياق تشغيل صغيرًا بالرسالة الأخيرة من كل دور gateway. يمكن أن يعرض التذييل الحالي النموذج، ونسبة نافذة السياق المئوية، ودليل العمل الحالي. معطّل افتراضيًا؛ فعّله لكل gateway إن أراد فريقك أن يتضمّن كل ردّ هذا الإسناد.

      display:
        runtime_footer:
          enabled: true
          fields: ["model", "context_pct", "cwd"]   # order shown; drop any to hide

      تجاوزات التقدّم لكل منصة​

      لدى منصات مختلفة احتياجات إسهاب مختلفة. استخدم display.platforms لضبط أوضاع لكل منصة:

      display:
        tool_progress: all          # global default
        platforms:
          signal:
            tool_progress: 'off'    # Signal cannot currently display tool-progress bubbles
          telegram:
            tool_progress: verbose  # detailed progress on Telegram
          slack:
            tool_progress: 'off'    # quiet in shared Slack workspace

      من CLI، استخدم المسار الأصلي — hermes config set display.platforms.telegram.streaming false. يُقبل الاختصار hermes config set platforms.telegram.streaming false أيضًا: لأن إعدادات العرض الخاصة بكل منصة (streaming، show_reasoning، tool_progress، …) لا تُقرأ إلا من display.platforms، تُعيد config set/get/unset توجيه ذلك الاختصار إلى المفتاح الأصلي وتطبع ملاحظة. مفاتيح الاتصال ضمن الكتلة العلوية platforms.<name> (token، enabled، reply_to_mode، extra) لا يُعاد توجيهها.

      المنصات التي لا تحمل تجاوزًا تعود إلى قيمة tool_progress العامة. مفاتيح المنصات الصالحة: telegram، discord، slack، signal، whatsapp، matrix، mattermost، email، sms، homeassistant، dingtalk، feishu، wecom، weixin، bluebubbles، qqbot. لا يزال مفتاح display.tool_progress_overrides القديم يُحمَّل للتوافق مع الإصدارات السابقة لكنه متقادم ويُرحَّل إلى display.platforms عند أول تحميل.

      Signal مُدرَجة كمفتاح منصة صالح لأن الإعداد يمكن أن يُحفَظ لكل منصة، لكن مهايئ Signal الحالي لا يستطيع تحرير الرسائل المُرسَلة ولا يعرض فقاعات تقدّم الأدوات. أبقِ tool_progress لـ Signal مضبوطًا على off؛ استخدم CLI أو منصة مراسلة قادرة على التحرير إذا أردت مشاهدة كل استدعاء أداة مباشرة.

      interim_assistant_messages خاص بـ gateway فقط. عند تفعيله، يرسل Hermes تحديثات المساعد المكتملة في منتصف الدور كرسائل دردشة منفصلة. هذا مستقل عن tool_progress ولا يتطلّب تدفّق gateway.

      يتحكّم show_commentary (الافتراضي true) في قناة التعليق الخاصة بنماذج Codex Responses — السرد المصقول للتقدّم الذي تنتجه هذه النماذج إلى جانب استدلالها الخاص. عند التفعيل، تُسلَّم كل رسالة تعليق مكتملة كتحديث مرحلي مرئي (على gateway يتطلّب هذا أيضًا interim_assistant_messages). اضبطه على false إذا كان السرد الإضافي يزعجك: يعود التعليق حينها إلى قناة الاستدلال ولا يُعرَض إلا عند تفعيل show_reasoning.

      هوية طلب OpenAI Codex​

      تطلب OpenAI من أطر Codex الخارجية (Third-party harnesses) أن تُعرِّف نفسها. ترسل الطلبات المصادَق عليها عبر ChatGPT إلى نقطة Codex الطرفية الرسمية تلقائيًا originator: hermes-agent و User-Agent: HermesAgent/<version>. تُحفَظ ترويسة حساب ChatGPT الحالية كما هي. لا يُرسَل أي محتوى prompt إضافي أو طلب قياس عن بُعد (telemetry). تظل طلبات OpenAI API المباشرة والنقاط الطرفية الوسيطة المخصّصة دون تغيير.

      تحويل الكلام إلى نص (STT)​

      stt:
        enabled: true                # Auto-transcribe inbound voice messages (default: true)
        echo_transcripts: true       # Post raw transcripts back to the chat as 🎙️ "..." (default: true)
        provider: "local"            # "local" | "groq" | "openai" | "mistral" | "xai" | "elevenlabs" | "deepinfra" | ...
        language: "en"               # GLOBAL language hint for every provider (per-provider language wins); set "" for auto-detect
        cloud_trim_silence: true     # trim long pauses with ffmpeg before uploading to a cloud provider (default: true)
        cloud_trim_threshold_db: -40 # audio quieter than this counts as silence
        cloud_trim_keep_ms: 300      # how much of each pause survives the trim (keeps natural pacing)
        # prompt: "Hermes, Teknium, Nous Research, kanban"   # Static vocabulary hint (see below)
        local:
          model: "base"              # tiny, base, small, medium, large-v3
          language: ""               # per-provider override of stt.language
          initial_prompt: ""         # optional whisper prompt to bias vocabulary/script (e.g. Simplified Chinese)
          vad: true                  # Silero VAD filter (default on) — silence never reaches whisper; false = raw behavior (music/ambient)
          vad_min_silence_ms: 500    # min silence (ms) that splits speech chunks when vad is on
          no_speech_prob_threshold: 0.6  # drop a segment only when no_speech_prob > this...
          logprob_threshold: -1.0        # ...AND avg_logprob < this (both must hit — quiet real speech survives)
          unload_after_idle_seconds: 0   # 0=never unload (default); e.g. 300 = release the model after 5min idle
        groq:
          language: ""               # per-provider override of stt.language
        openai:
          model: "whisper-1"         # whisper-1 | gpt-4o-mini-transcribe | gpt-4o-transcribe | gpt-transcribe
          language: ""               # per-provider override of stt.language
        # model: "whisper-1"         # Legacy fallback key still respected

      حل اللغة واحد بالنسبة لـكل مزوّد STT (local، وgroq، وopenai، وmistral، وxai، وelevenlabs، وdeepinfra، ومزوّدي الأوامر، والإضافات): stt.<provider>.language ← stt.language ← متغير البيئة HERMES_LOCAL_STT_LANGUAGE ← الاكتشاف التلقائي للمزوّد. الافتراضي هو stt.language: "en" — إذ يخطئ الاكتشاف التلقائي لـ Whisper كثيرًا في تحديد المقاطع القصيرة أو ذات اللكنة، ما يظهر كملاحظات صوتية تُنسَخ بلغة خاطئة. ينبغي على المتحدثين بغير الإنجليزية ضبط stt.language إلى رمز لغتهم مرة واحدة (مثل "es"، "zh"، "uk")؛ اضبطه على "" لاستعادة الاكتشاف التلقائي للاستخدام متعدّد اللغات.

      اضبط stt.echo_transcripts: false عندما يحتاج gateway إلى نسخ الملاحظات الصوتية للوكيل لكن يجب ألا ينشر النسخ الخام مرة أخرى في المحادثة (على سبيل المثال، بوتات WhatsApp الموجَّهة للعملاء).

      سلوك المزوّد:

      • يستخدم local برنامج faster-whisper العامل على جهازك. ثبّته بشكل منفصل عبر pip install faster-whisper. تصليب هلوسة الصمت مُفعّل افتراضيًا: يمنع مرشّح Silero VAD الصمت/الضجيج من الوصول إلى Whisper إطلاقًا، ويُعطَّل الاشتراط عبر النوافذ (cross-window conditioning)، وتُسقَط المقاطع التي يُصنّفها النموذج نفسه بأنها على الأرجح ليست كلامًا ومنخفضة الثقة معًا. اضبط stt.local.vad: false لنسخ صوت غير كلامي (موسيقى، محيطي) بالسلوك الخام. يبقى النموذج مُحمَّلًا في الذاكرة بين الرسائل الصوتية لنسخ منخفض زمن الاستجابة؛ اضبط stt.local.unload_after_idle_seconds (مثل 300 لخمس دقائق) لتحرير النموذج تلقائيًا عند الخمول. يحرّر هذا ذاكرة GPU على مضيفات CUDA (الفائدة الرئيسية عندما يشارك نموذج محلي وحدة معالجة الرسومات)؛ وعلى المعالج (CPU) تصبح الذاكرة قابلة لإعادة الاستخدام من قِبل العملية، رغم أن البصمة المرئية لنظام التشغيل قد لا تنكمش حتى تحتاج العملية إلى المساحة لشيء آخر. تُعيد الرسالة الصوتية التالية تحميل النموذج بشفافية.
      • يستخدم groq نقطة Groq الطرفية المتوافقة مع Whisper ويقرأ GROQ_API_KEY. مرّر stt.groq.language (أو متغير البيئة العام HERMES_LOCAL_STT_LANGUAGE) لتخطّي الاكتشاف التلقائي وتقليل زمن الاستجابة.
      • يستخدم openai واجهة OpenAI للكلام ويقرأ VOICE_TOOLS_OPENAI_KEY.

      يحصل مزوّدو السحابة (groq، وopenai، وmistral، وxai، وelevenlabs، وdeepinfra) على اقتصاص صمت قبل الرفع افتراضيًا عند تثبيت ffmpeg: تُطوى فترات الصمت الطويلة في ملاحظة صوتية على جانب العميل قبل رفع الملف، مع الاحتفاظ بـ cloud_trim_keep_ms من كل فترة توقّف بحيث ينجو الإيقاع الطبيعي. يعني الصوت الأقصر رفعًا أسرع، وفوترة أقل لكل دقيقة صوت، وهلوسات صمت أقل من النموذج البعيد. تتخطّى المقاطع الأقصر من 12 ثانية الاقتصاص تمامًا (لا يمكن أن تُحدث التوفيرات فرقًا هناك، ويفرض عدة مزوّدين حدًّا أدنى للفوترة لكل طلب على أي حال). الاقتصاص بأفضل جهد — إذا كان ffmpeg مفقودًا، أو فشل الاقتصاص، أو كان المقطع في معظمه صمتًا، أو كان الاقتصاص سيوفّر أقل من نحو 10%، يُرفَع الملف الأصلي دون تغيير. اضبط stt.cloud_trim_silence: false لرفع الأصل دائمًا (مثلًا عند نسخ موسيقى أو صوت محيطي عبر مزوّد سحابي). لا تحصل مزوّدو نوع الأوامر (command) والإضافات على صوت مُقتصَّص أبدًا.

      يُحترَم stt.provider المختار صراحةً بصرامة — إذا كان غير متاح، يفشل النسخ برسالة توجيهية لتشغيل hermes tools بدلًا من تبديل المزوّدين. لا يكتشف Hermes تلقائيًا إلا عندما لم يُختَر أي مزوّد قط، وبهذا الترتيب: local ← groq ← openai.

      تجاوزات نموذج Groq وOpenAI مُدفوعة بمتغيرات البيئة:

      STT_GROQ_MODEL=whisper-large-v3-turbo
      STT_OPENAI_MODEL=whisper-1
      GROQ_BASE_URL=https://api.groq.com/openai/v1
      STT_OPENAI_BASE_URL=https://api.openai.com/v1

      prompt النسخ (تلميحات مفردات)​

      stt.prompt تلميح ثابت اختياري يُمرَّر إلى خلفيات STT القادرة على استقبال prompt. استخدمه لأسماء الأعلام، وأسماء المنتجات، والمصطلحات التخصّصية التي تخطئ فيها نماذج عائلة Whisper سماعًا في العادة:

      stt:
        provider: "local"
        prompt: "Hermes, Teknium, Nous Research, kanban, Ollama"

      التركيب. قيمة الإعدادات هي الأساس. الإضافات التي تُسجّل hook الـ pre_transcription تُعدّل فوقه، مع أسبقية آخر كاتب لكل حقل. تتألف تلميحات إضافات متعدّدة بشكل حتمي: يُحمّل اكتشاف الإضافات الإضافات بترتيب مُرتَّب حسب معرّف الإضافة، وتعمل استدعاءات كل إضافة بترتيب تسجيلها الخاص، بحيث تُنتج المجموعة نفسها من الإضافات دائمًا prompt نهائيًا واحدًا. يمسح hook يُعيد سلسلة فارغة لـ prompt prompt الإعدادات لذلك الطلب. يمكن للـ hooks أيضًا تجاوز language و model؛ أما file_path فللقراءة فقط وأي محاولة لتغييره تُسجَّل وتُسقَط. مع عدم وجود hook مُسجَّل وعدم ضبط stt.prompt، يكون الطلب الصادر مطابقًا للإصدارات السابقة.

      تُرفَع الـ prompts مع صوتك

      تُرسَل الـ prompt النهائية إلى مزوّد STT المُعدّ إلى جانب ملف الصوت. أبقِ الأسرار والسياق المشتقّ من الجلسة خارج stt.prompt وخارج أي شيء يُعيده hook الـ pre_transcription، خصوصًا عندما يكون المزوّد واجهة API مستضافة لا faster-whisper المحلية.

      الوضع الصوتي (CLI)​

      voice:
        record_key: "ctrl+b"         # Push-to-talk key inside the CLI
        max_recording_seconds: 120    # Hard stop for long recordings
        auto_tts: false               # Enable spoken replies automatically when /voice on
        beep_enabled: true            # Play record start/stop beeps in CLI voice mode
        beep_volume: 0.3              # Beep amplitude (0.0-1.0); raise it on quiet systems / headphones
        silence_threshold: 200        # RMS threshold for speech detection
        silence_duration: 3.0         # Seconds of silence before auto-stop

      استخدم /voice on في CLI لتفعيل وضع الميكروفون، و record_key لبدء/إيقاف التسجيل، و /voice tts لتبديل الردود المنطوقة. راجع الوضع الصوتي (Voice Mode) للإعداد الشامل والسلوك الخاص بكل منصة.

      البث (Streaming)​

      ابثّ الـ tokens إلى الطرفية أو منصات المراسلة أولًا بأول، بدلًا من انتظار الاستجابة كاملة.

      بث CLI​

      display:
        streaming: true         # Stream tokens to terminal in real-time
        show_reasoning: true    # Also stream reasoning/thinking tokens (optional)

      عند التفعيل، تظهر الاستجابات token بعد token داخل صندوق بث. تظل استدعاءات الأدوات مُلتقَطة بصمت. إذا لم يدعم المزوّد البث، يعود النظام تلقائيًا إلى العرض العادي.

      بث Gateway (Telegram، Discord، Slack)​

      streaming:
        enabled: true           # Enable progressive message editing (default: false)
        transport: auto         # "auto" (default) | "edit" (progressive message editing) | "off"
        edit_interval: 0.8      # Seconds between message edits (default: 0.8)
        buffer_threshold: 24    # Characters before forcing an edit flush (default: 24)
        cursor: " ▉"            # Cursor shown during streaming
        fresh_final_after_seconds: 0    # Opt in to fresh final (Telegram) when preview is this old

      عند التفعيل، يرسل البوت رسالة عند وصول أول token، ثم يعدّلها تدريجيًا كلما وصلت المزيد من الـ tokens. المنصات التي لا تدعم تعديل الرسائل (Signal، Email، Home Assistant) يُكتشف ذلك تلقائيًا عند أول محاولة — يُعطَّل البث بسلاسة لتلك الجلسة دون إغراق برسائل متعددة.

      للحصول على تحديثات منتصف الدور الطبيعية بشكل منفصل دون تعديل تدريجي للـ tokens، اضبط display.interim_assistant_messages: true.

      معالجة التجاوز: إذا تجاوز النص المبثوث حد طول رسالة المنصة (~4096 حرفًا)، تُنهى الرسالة الحالية وتبدأ رسالة جديدة تلقائيًا.

      النهاية الحديثة (Telegram): تحافظ editMessageText في Telegram على الطابع الزمني الأصلي للرسالة، لذا فإن ردًا مبثوثًا طويل الأمد سيحتفظ بطابع أول token الزمني حتى بعد الانتهاء. اضبط fresh_final_after_seconds > 0 للاشتراك في تسليم المعاينات القديمة كرسائل نهائية جديدة تمامًا مع حذف المعاينة على أساس أفضل جهد. القيمة الافتراضية هي 0، والتي تُنهي دائمًا الردود المبثوثة في مكانها وتتجنب تسلسل الرسالة المكررة/الحذف اللحظي على العملاء الذين يُظهرون العمليتين معًا.

      الإعدادات الافتراضية للبث لكل منصة

      المفتاح الرئيسي streaming.enabled قيمته false افتراضيًا — لا شيء يُبث حتى تُفعّله. بعد التفعيل، يُحدَّد البث لكل منصة على حدة: يأتي Telegram بـ display.platforms.telegram.streaming: true (يبث) بينما Discord بـ display.platforms.discord.streaming: false (لا يبث). لذا بعد تفعيل البث، يبث Telegram مباشرة بينما يبقى Discord على الردود بالرسالة الكاملة حتى تغيّر مفتاحه. يمكنك ضبط مفاتيح كل منصة هذه من مفاتيح Channels في لوحة التحكم أو مباشرة في ~/.hermes/config.yaml.

      عزل جلسات المحادثة الجماعية​

      حدّد عدد جلسات المحادثة التي يمكن أن تكون مفتوحة فعليًا في آن واحد عبر CLI وTUI/لوحة التحكم وgateway المراسلة:

      max_concurrent_sessions: null  # null/0 = unlimited; positive integer = active session cap

      تُشغَل الخانة (slot) عندما تنفّذ الجلسة دورها الأول، لا عند فتح نافذة محادثة. فتح محادثة أو استئنافها أو إعادة الاتصال بها لا يكلّف شيئًا حتى ترسل رسالة، لذا فإن تبويبات Desktop الخاملة (وإعادة الاتصال في الخلفية التي يطلقها websocket متقطع) لا يمكنها استنزاف gateway المراسلة الذي يشارك هذا الحد.

      عند بلوغ الحد، يُعيد Hermes رسالة حد مباشرة تسمّي الواجهات التي تشغل الخانات. تحتفظ الجلسات النشطة الحالية بسلوكها المعتاد. شغّل hermes status لرؤية استخدام الخانات الحالي وكل من يشغلها.

      المفتاح الأساسي هو max_concurrent_sessions على المستوى الأعلى. يقبل Hermes أيضًا gateway.max_concurrent_sessions كخيار احتياطي، لكن المفتاح على المستوى الأعلى يفوز عند ضبط الاثنين معًا.

      يُفرض الحد عبر ملف إيجار (lease) محلي وقت التشغيل وهو بأفضل جهد: يفشل Hermes بأمان (fails open) إذا تعذّرت قراءة السجل أو قفله حتى لا يُترك المستخدمون معلّقين. وهو مُصمّم لبيئة تشغيل مضيف/profile واحد، وليس لـ $HERMES_HOME مشترك مُحمّل عبر عدة أجهزة.

      حدّد ما إذا كانت المحادثات المشتركة تحتفظ بمحادثة واحدة لكل غرفة أو محادثة واحدة لكل مشارك:

      group_sessions_per_user: true  # true = per-user isolation in groups/channels, false = one shared session per chat
      • true هي القيمة الافتراضية والموصى بها. في قنوات Discord ومجموعات Telegram وقنوات Slack والسياقات المشتركة المماثلة، يحصل كل مُرسِل على جلسته الخاصة عندما توفّر المنصة معرّف مستخدم.
      • false يعيد سلوك الغرفة المشتركة القديم. قد يكون هذا مفيدًا إذا أردت صراحة أن يعامل Hermes قناة ما كمحادثة تعاونية واحدة، لكنه يعني أيضًا أن المستخدمين يتشاركون السياق وتكاليف الـ tokens وحالة المقاطعة.
      • الرسائل المباشرة (DM) لا تتأثر. لا يزال Hermes يفهرس الـ DMs حسب معرّف المحادثة/DM كالمعتاد.
      • تظل الخيوط (Threads) معزولة عن قناتها الأصل في كلتا الحالتين؛ ومع true، يحصل كل مشارك أيضًا على جلسته الخاصة داخل الخيط.

      لتفاصيل السلوك والأمثلة، راجع الجلسات (Sessions) ودليل Discord.

      سلوك الرسائل المباشرة غير المصرَّح بها​

      حدّد ما يفعله Hermes عندما يرسل مستخدم مجهول رسالة مباشرة:

      unauthorized_dm_behavior: pair

      whatsapp:
        unauthorized_dm_behavior: ignore
      • pair هي القيمة الافتراضية لمنصات المحادثة المباشرة المشابهة للدردشة. يرفض Hermes الوصول، لكنه يردّ برمز إقران لمرة واحدة في الرسائل المباشرة.
      • ignore يُسقط الرسائل المباشرة غير المصرَّح بها بصمت.
      • يفترض البريد الإلكتروني القيمة ignore ما لم يُضبط platforms.email.unauthorized_dm_behavior: pair، لأن صناديق الوارد قد تحتوي على بريد غير مقروء لا علاقة له بالموضوع.
      • تتجاوز أقسام المنصات القيمة الافتراضية العامة، لذا يمكنك إبقاء الإقران مفعّلًا على نطاق واسع مع جعل منصة واحدة أكثر هدوءًا.

      الأوامر السريعة​

      عرّف أوامر مخصّصة تُنفّذ إما أوامر shell دون استدعاء LLM، أو تُسمِّي slash command بديلًا لآخر. أوامر Exec السريعة لا تستهلك tokens ومفيدة من منصات المراسلة (Telegram، Discord، إلخ) لفحوصات الخادم أو السكربتات المساعدة السريعة.

      quick_commands:
        status:
          type: exec
          command: systemctl status hermes-agent
        disk:
          type: exec
          command: df -h /
        update:
          type: exec
          command: cd ~/.hermes/hermes-agent && git pull && uv pip install -e .
        gpu:
          type: exec
          command: nvidia-smi --query-gpu=name,utilization.gpu,memory.used,memory.total --format=csv,noheader
        restart:
          type: alias
          target: /gateway restart

      الاستخدام: اكتب /status أو /disk أو /update أو /gpu أو /restart في CLI أو أي منصة مراسلة. تُنفَّذ أوامر exec محليًا على المضيف وتُعيد المخرجات مباشرة — دون استدعاء LLM ودون استهلاك tokens. أوامر alias تُعيد التوجيه إلى slash command المُهيَّأ كهدف.

      • مهلة 30 ثانية — تُنهى الأوامر طويلة التشغيل مع رسالة خطأ
      • الأولوية — تُفحص الأوامر السريعة قبل أوامر المهارات، لذا يمكنك تجاوز أسماء المهارات
      • الإكمال التلقائي — تُحلّ الأوامر السريعة وقت الإرسال ولا تظهر في جداول الإكمال التلقائي المدمجة لـ slash commands
      • النوع — الأنواع المدعومة هي exec وalias؛ الأنواع الأخرى تُظهر خطأ
      • يعمل في كل مكان — CLI وTelegram وDiscord وSlack وWhatsApp وSignal والبريد الإلكتروني وHome Assistant

      اختصارات الـ prompt النصية فقط ليست أوامر سريعة صالحة. لسير عمل prompt قابل لإعادة الاستخدام، أنشئ مهارة أو alias لـ slash command موجود.

      تنفيذ الكود​

      اضبط أداة execute_code:

      code_execution:
        mode: project                # project (default) | strict
        timeout: 300                 # Max execution time in seconds
        max_tool_calls: 50           # Max tool calls within code execution

      mode يتحكم في دليل العمل ومفسّر Python للسكربتات:

      • project (الافتراضي) — تعمل السكربتات في دليل عمل الجلسة باستخدام python الخاص بـ virtualenv/conda النشط. تُحلّ اعتماديات المشروع (pandas، torch، حزم المشروع) والمسارات النسبية (.env، ./data.csv) بشكل طبيعي، مطابِقةً ما تراه terminal().
      • strict — تعمل السكربتات في دليل تجهيز مؤقت باستخدام sys.executable (بايثون Hermes الخاص). أقصى قابلية لإعادة الإنتاج، لكن اعتماديات المشروع والمسارات النسبية لن تُحلّ.

      تنظيف متغيرات البيئة (يزيل *_API_KEY و*_TOKEN و*_SECRET و*_PASSWORD و*_CREDENTIAL و*_PASSWD و*_AUTH) وقائمة السماح للأدوات تنطبقان بالتساوي في كلا الوضعين — تغيير الوضع لا يغيّر الوضع الأمني.

      خلفيات البحث في الويب​

      تدعم أداتا web_search وweb_extract خمسة مزوّدي خلفية. اضبط الخلفية في config.yaml أو عبر hermes tools:

      web:
        backend: firecrawl    # firecrawl | searxng | parallel | tavily | perplexity | keenable | exa

        # Or use per-capability keys to mix providers (e.g. free search + paid extract):
        search_backend: "searxng"
        extract_backend: "firecrawl"

        # Keyless free-tier fallback (default: true). With no backend configured
        # and no API keys present, web tools rotate across the Exa/Parallel/
        # Firecrawl/Keenable free tiers. Set false to disable.
        keyless_fallback: true

        # One-shot keyless rescue (default: true). When the chosen/keyed backend
        # fails a call, that single call retries on the keyless ring; the next
        # call attempts the chosen backend again (never sticky).
        keyless_rescue: true

        # Pin Exa/Parallel to a tier (set by the hermes tools Free/Paid rows).
        # free = always the anonymous endpoint; paid = always the keyed SDK path;
        # unset = auto (key present -> paid, otherwise free).
        provider_tier:
          parallel: free
          exa: paid

      SearXNGSEARXNG_URL✔—
      ParallelPARALLEL_API_KEY (اختياري — مستوى مجاني بلا مفتاح)✔✔
      TavilyTAVILY_API_KEY (اختياري — بلا مفتاح عند اختياره)✔✔

      اختيار الخلفية: يستخدم وقت التشغيل دائمًا اختيار web.backend المخزَّن (يُضبط عبر hermes tools؛ يوجّه nous عبر Tool Gateway المُدار). فقط إذا لم يُختَر أي خلفية ويب من قبل، يُكتشف واحد تلقائيًا من مفاتيح API المتاحة: إذا كان SEARXNG_URL فقط مضبوطًا، يُستخدم SearXNG؛ وإذا كان EXA_API_KEY فقط، يُستخدم Exa؛ وإذا كان TAVILY_API_KEY فقط، يُستخدم Tavily؛ وإذا كان PERPLEXITY_API_KEY فقط، يُستخدم Perplexity؛ وإذا كان PARALLEL_API_KEY فقط، يُستخدم Parallel؛ وإذا كان KEENABLE_API_KEY فقط، يُستخدم Keenable. مع عدم وجود اختيار وعدم وجود أي بيانات اعتماد على الإطلاق، تتناوب الطلبات بنظام round-robin عبر حلقة المستوى المجاني بلا مفتاح (Exa / Parallel / Firecrawl / Keenable) مع تجاوز تلقائي إلى التالي في الطابور عند بلوغ حدود المعدل — راجع دليل البحث في الويب للتفاصيل. بمجرد وجود اختيار، لا تغيّر إضافة مفتاح إلى .env المسار. اختيار Tavily أو Firecrawl أو Keenable في hermes tools يعمل أيضًا دون مفتاح.

      SearXNG محرك بحث تلوي (metasearch) مجاني ومستضاف ذاتيًا ويحترم الخصوصية يستعلم أكثر من 70 محرك بحث. لا حاجة إلى مفتاح API — فقط اضبط SEARXNG_URL على نُسختك (مثلًا http://localhost:8080). SearXNG للبحث فقط؛ تتطلب web_extract مزوّد استخراج منفصلًا (اضبط web.extract_backend). راجع دليل إعداد البحث في الويب لتعليمات إعداد Docker.

      Firecrawl المستضاف ذاتيًا: اضبط FIRECRAWL_API_URL ليشير إلى نسختك الخاصة. عند ضبط رابط مخصّص، يصبح مفتاح API اختياريًا (اضبط `USE_DB_AUTHENTICATION=*** على الخادم لتعطيل المصادقة).

      أوضاع بحث Parallel: اضبط PARALLEL_SEARCH_MODE للتحكم في سلوك البحث — fast أو one-shot أو agentic (الافتراضي: agentic).

      Exa: اضبط EXA_API_KEY في ~/.hermes/.env. يدعم التصفية حسب category (company، research paper، news، people، personal site، pdf) وفلاتر النطاق والتاريخ.

      المنطقة الزمنية​

      تجاوز المنطقة الزمنية المحلية للخادم بسلسلة منطقة زمنية IANA. يؤثر في الطوابع الزمنية في السجلات، وجدولة cron، وحقن الوقت في system prompt.

      timezone: "America/New_York"   # IANA timezone (default: "" = server-local time)

      القيم المدعومة: أي معرّف منطقة زمنية IANA (مثل America/New_York، Europe/London، Asia/Kolkata، UTC). اتركه فارغًا أو احذفه لاستخدام الوقت المحلي للخادم.

      Discord​

      اضبط سلوكيات Discord الخاصة بـ gateway المراسلة:

      discord:
        require_mention: true          # Require @mention to respond in server channels
        free_response_channels: ""     # Comma-separated channel IDs where bot responds without @mention
        auto_thread: true              # Auto-create threads on @mention in channels
      • require_mention — عندما تكون true (الافتراضي)، يستجيب البوت في قنوات الخادم فقط عند الإشارة إليه بـ @BotName. الرسائل المباشرة تعمل دائمًا دون إشارة.
      • free_response_channels — قائمة معرّفات قنوات مفصولة بفواصل يستجيب فيها البوت لكل رسالة دون الحاجة إلى إشارة.
      • auto_thread — عندما تكون true (الافتراضي)، تُنشئ الإشارات في القنوات خيطًا تلقائيًا للمحادثة، مما يبقي القنوات نظيفة (مماثل لخيوط Slack).

      الأمان​

      الفحص الأمني قبل التنفيذ وتعتيم الأسرار:

      security:
        redact_secrets: true           # Redact API key patterns in tool output and logs (on by default)
        tirith_enabled: true           # Enable Tirith security scanning for terminal commands
        tirith_path: "tirith"          # Path to tirith binary (default: "tirith" in $PATH)
        tirith_timeout: 5              # Seconds to wait for tirith scan before timing out
        tirith_fail_open: true         # Allow command execution if tirith is unavailable
        website_blocklist:             # See Website Blocklist section below
          enabled: false
          domains: []
          shared_files: []
      • redact_secrets — عندما تكون true، يكتشف النظام تلقائيًا الأنماط الشبيهة بمفاتيح API والـ tokens وكلمات المرور ويعتّمها في مخرجات الأدوات قبل دخولها سياق المحادثة والسجلات. مفعّلة افتراضيًا. اضبطها على false صراحة فقط عندما تحتاج إلى سلاسل شبيهة ببيانات اعتماد خام لأغراض التصحيح أو تطوير المُعتِّم.
      • tirith_enabled — عندما تكون true، تُفحص أوامر الطرفية بواسطة Tirith قبل التنفيذ للكشف عن العمليات الخطرة المحتملة.
      • tirith_path — مسار ملف tirith التنفيذي. اضبط هذا إذا كان tirith مثبَّتًا في موقع غير قياسي.
      • tirith_timeout — أقصى عدد من الثواني لانتظار فحص tirith. تتابع الأوامر تنفيذها إذا انتهت مهلة الفحص.
      • tirith_fail_open — عندما تكون true (الافتراضي)، يُسمح بتنفيذ الأوامر إذا كان tirith غير متاح أو فشل. اضبطها على false لمنع الأوامر عندما لا يستطيع tirith التحقق منها.

      قائمة حظر المواقع​

      احظر نطاقات معيّنة من الوصول إليها بواسطة أدوات الويب والمتصفح الخاصة بالوكيل:

      security:
        website_blocklist:
          enabled: false               # Enable URL blocking (default: false)
          domains:                     # List of blocked domain patterns
            - "*.internal.company.com"
            - "admin.example.com"
            - "*.local"
          shared_files:                # Load additional rules from external files
            - "/etc/hermes/blocked-sites.txt"

      عند التفعيل، يُرفض أي رابط يطابق نمط نطاق محظور قبل تنفيذ أداة الويب أو المتصفح. ينطبق هذا على web_search وweb_extract وbrowser_navigate وأي أداة تصل إلى الروابط.

      تدعم قواعد النطاق:

      • نطاقات دقيقة: admin.example.com
      • نطاقات فرعية عامة (wildcard): *.internal.company.com (تحظر كل النطاقات الفرعية)
      • نطاقات TLD عامة: *.local

      تحتوي الملفات المشتركة على قاعدة نطاق واحدة في كل سطر (يُتجاهل السطر الفارغ وتعليقات #). الملفات المفقودة أو غير القابلة للقراءة تسجّل تحذيرًا لكنها لا تعطّل أدوات الويب الأخرى.

      تُخزَّن السياسة مؤقتًا لمدة 30 ثانية، لذا تسري تغييرات الإعدادات بسرعة دون إعادة تشغيل.

      الموافقات الذكية​

      تحكّم في كيفية تعامل Hermes مع الأوامر الخطرة المحتملة:

      approvals:
        mode: smart   # smart | manual | off
      الوضعالسلوك
      smart (الافتراضي)استخدم LLM مساعدًا لتقييم ما إذا كان الأمر المُعلَّم خطيرًا فعلًا. الأوامر منخفضة الخطورة تُوافَق تلقائيًا لذلك الأمر فقط. الأوامر الخطرة فعلًا تُرفض، والقرارات غير المؤكدة تُصعَّد إلى المستخدم.
      manualاطلب موافقة المستخدم قبل تنفيذ أي أمر مُعلَّم. في CLI، تظهر نافذة موافقة تفاعلية. في المراسلة، تُصفّ طلب موافقة معلّق.
      offتخطَّ كل فحوصات الموافقة. مكافئ لـ HERMES_YOLO_MODE=true. استخدمها بحذر.

      الوضع الذكي مفيد بوجه خاص لتقليل إرهاق الموافقات — فهو يتيح للوكيل العمل بشكل أكثر استقلالية على العمليات الآمنة مع الاستمرار في رصد الأوامر المدمّرة فعلًا.

      تحذير

      ضبط approvals.mode: off يعطّل كل فحوصات الأمان لأوامر الطرفية. استخدم هذا فقط في بيئات موثوقة ومعزولة (sandboxed).

      قاطع دائرة الرفض​

      approvals.denial_breaker_threshold (الافتراضي 3) يحمي من إعادة محاولة الوكيل لتنويعات من أمر يستمر مراجع الموافقة الذكية في رفضه — كل إعادة محاولة تستهلك استدعاء LLM حارس آخر. بعد هذا العدد من الرفضات المتتالية في جلسة واحدة، تتصاعد رسالة الرفض إلى تعليمة توقف صارمة تخبر الوكيل بالتوقف والإبلاغ عن العملية المحظورة وطلب تشغيلها يدويًا منك أو عبر /approve. أي موافقة تعيد ضبط العدّاد؛ اضبط 0 للتعطيل:

      approvals:
        denial_breaker_threshold: 3   # 0 disables the breaker

      قواعد الرفض​

      approvals.deny هي قائمة بأنماط glob تحظر أوامر الطرفية المطابقة دون قيد أو شرط — حتى تحت --yolo أو /yolo أو mode: off. إنها النظير القابل للتحرير من قِبل المستخدم لقائمة الحظر الصارمة المدمجة:

      approvals:
        deny:
          - "git push --force*"
          - "*curl*|*sh*"

      الأنماط عبارة عن أنماط fnmatch غير حساسة لحالة الأحرف ويجب وضعها بين علامتي اقتباس في YAML (نجمة * في البداية دون اقتباس تسبب خطأ تحليل). راجع الأمان — قواعد الرفض المُعرَّفة من المستخدم للتفاصيل.

      سياسة موافقة ذكية مخصّصة​

      approvals.smart_policy تتيح لك إضافة قواعدك الخاصة إلى تعليمات مراجع الموافقة الذكية. عند ضبطه، يُضاف النص إلى system prompt لـ LLM الحارس (القناة الموثوقة — لا يُدمج أبدًا مع نص الأمر غير الموثوق)، لذا يمكنك تشديد حكمه أو تخفيفه لبيئتك دون تعديل الكود:

      approvals:
        smart_policy: |
          Always ESCALATE commands that modify anything under /etc.
          APPROVE docker compose restarts in ~/deploys — they are routine here.

      التفويض (Delegation)​

      اضبط سلوك subagent لأداة delegate:

      delegation:
        # model: "google/gemini-3-flash-preview"  # Override model (empty = inherit parent)
        # provider: "openrouter"                  # Override provider (empty = inherit parent)
        # base_url: "http://localhost:1234/v1"    # Direct OpenAI-compatible endpoint (takes precedence over provider)
        # api_key: "local-key"                    # API key for base_url (falls back to OPENAI_API_KEY)
        # api_mode: ""                            # Wire protocol for base_url: "chat_completions", "codex_responses", or "anthropic_messages". Empty = auto-detect from URL (e.g. /anthropic suffix → anthropic_messages). Set explicitly for non-standard endpoints the heuristic can't detect.
        compression_threshold_tokens: 0          # Optional absolute cap on a subagent's compaction trigger (>= 16000); 0 = off, children use the ratio threshold
        # request_overrides:                      # Per-child request settings sent on every subagent API call (all resolution branches).
        #   extra_body:                           # Merged into the request's extra_body — e.g. OpenRouter routing hints:
        #     provider:
        #       sort: throughput
        max_concurrent_children: 3                # Parallel children per batch (floor 1, no ceiling). Also via DELEGATION_MAX_CONCURRENT_CHILDREN env var.
        worktree_isolation: false                 # Give each child its own git worktree branched from HEAD (local backend + git repos only; inspired by Muse Code). See Subagent Delegation → Worktree Isolation.
        max_spawn_depth: 1                        # Delegation tree depth cap (1-3, clamped). 1 = flat (default): parent spawns leaves that cannot delegate. 2 = orchestrator children can spawn leaf grandchildren. 3 = three levels.
        orchestrator_enabled: true                # Global kill switch. When false, role="orchestrator" is ignored and every child is forced to leaf regardless of max_spawn_depth.

      تجاوز provider:model للـ subagent: افتراضيًا، يرث subagent مزوّد ونموذج الوكيل الأصل. اضبط delegation.provider وdelegation.model لتوجيه subagents إلى زوج provider:model مختلف — مثلًا استخدم نموذجًا رخيصًا وسريعًا للمهام الفرعية الضيقة النطاق بينما يشغّل وكيلك الرئيسي نموذج استدلال مكلفًا.

      سلسلة احتياطية للـ subagent: اضبط delegation.fallback_providers لمنح العُمّال (workers) سلسلتهم الخاصة (بنفس شكل القائمة على المستوى الأعلى). الابن المُثبَّت صراحة (عبر provider أو endpoint أو model) يستخدم تلك السلسلة فقط عندما تُصرَّح، وإلا فإنه يفشل بوضوح بدلًا من استعارة مسار الوكيل الأصل. أما الابن غير المُثبَّت، فإن غياب الإعداد أو ضبطه على null يحافظ على وراثة السلسلة من الأصل. استخدم fallback_providers: [] تحت delegation: لتعطيل الاحتياط للأبناء كليًا.

      تجاوز endpoint مباشر: إذا أردت مسار endpoint مخصّص مباشرًا، اضبط delegation.base_url وdelegation.api_key وdelegation.model. هذا يُرسل subagents مباشرة إلى ذلك الـ endpoint المتوافق مع OpenAI ويسبق delegation.provider في الأولوية. إذا حُذف delegation.api_key، يعود Hermes إلى OPENAI_API_KEY فقط. عند ضبط delegation.provider جنبًا إلى جنب مع delegation.base_url، يفوز الـ endpoint والمفتاح الصريحان مع ذلك، لكن إعدادات طلب ذلك المزوّد (تجاوزات extra_body والحد الأقصى لـ tokens الخرج من مدخل custom_providers الخاص بك) تُنقل إلى subagent.

      إعدادات الطلب لكل ابن (request_overrides): delegation.request_overrides قاموس بإعدادات طلب تُرسل في كل استدعاء API لـ subagent. المفاتيح على المستوى الأعلى هي وسائط API (مثل service_tier)؛ يُدمج قاموس فرعي extra_body في extra_body الخاص بالطلب. يُحترم هذا في جميع الفروع الثلاثة للحل — base_url المباشر، وprovider المُسمّى، والوراثة الخالصة — لذا يسري المفتاح دائمًا. الأولوية: تُدمج قيم request_overrides الصريحة فوق أي تجاوزات مشتقة من وقت التشغيل أو من الأصل — المفاتيح الصريحة على المستوى الأعلى تفوز، ويُدمج extra_body بعمق مستوى واحد بحيث تنجو مفاتيح extra_body الخاصة بوقت التشغيل (مثل شخصية thinking: {type: disabled} لمزوّد ما) إلا إذا أعاد مفتاحك تعريفها. حالة الاستخدام الأساسية هي تلميحات توجيه OpenRouter لأبناء التفويض:

      delegation:
        model: "deepseek/deepseek-v4-flash-0731"
        base_url: "https://openrouter.ai/api/v1"
        api_key: "sk-or-..."
        request_overrides:
          extra_body:
            provider:
              sort: throughput   # route children to the fastest OpenRouter provider

      بروتوكول النقل (api_mode): يكتشف Hermes بروتوكول النقل تلقائيًا من delegation.base_url (مثلًا المسارات المنتهية بـ /anthropic ← anthropic_messages؛ تحتفظ أسماء مضيفي Codex / Anthropic الأصلي / Kimi-coding باكتشافها الحالي). بالنسبة إلى endpoints التي لا يمكن للاستدلال (heuristic) تصنيفها — مثل Azure AI Foundry أو MiniMax أو Zhipu GLM أو وكلاء LiteLLM proxies الواجهة أمام backend بشكل Anthropic — اضبط delegation.api_mode صراحة إلى إحدى القيم chat_completions أو codex_responses أو anthropic_messages. اتركه فارغًا (الافتراضي) للإبقاء على الاكتشاف التلقائي.

      يستخدم مزوّد التفويض نفس آلية حل بيانات الاعتماد المستخدمة عند بدء تشغيل CLI/gateway. جميع المزوّدين المُهيَّئين مدعومون: openrouter، nous، copilot، zai، kimi-coding، minimax، minimax-cn. عند ضبط مزوّد، يحلّ النظام تلقائيًا الـ base URL الصحيح ومفتاح API ووضع API الصحيحين — دون الحاجة إلى ربط بيانات اعتماد يدويًا.

      الأولوية: delegation.base_url في الإعدادات ← delegation.provider في الإعدادات ← المزوّد الأصل (موروث). delegation.model في الإعدادات ← النموذج الأصل (موروث). ضبط model فقط دون provider يغيّر اسم النموذج فقط مع الاحتفاظ ببيانات اعتماد الأصل (مفيد للتبديل بين النماذج ضمن المزوّد نفسه مثل OpenRouter).

      العرض والعمق: max_concurrent_children يحدّد عدد subagents التي تعمل بالتوازي في كل دفعة (الافتراضي 3، الحد الأدنى 1، بلا سقف). يمكن أيضًا ضبطه عبر متغير البيئة DELEGATION_MAX_CONCURRENT_CHILDREN. عندما يُرسل النموذج مصفوفة tasks أطول من الحد، تُعيد delegate_task خطأ أداة يشرح الحد بدلًا من البتر الصامت. max_spawn_depth يتحكم في عمق شجرة التفويض (محصور بين 1 و3). عند القيمة الافتراضية 1، يكون التفويض مسطّحًا: لا يمكن للأبناء توليد أحفاد، وتمرير role="orchestrator" يتراجع بصمت إلى leaf. ارفعه إلى 2 ليتمكن الأبناء orchestrator من توليد أحفاد leaf؛ و3 لأشجار من ثلاثة مستويات. يختار الوكيل التنسيق (orchestration) في كل استدعاء عبر role="orchestrator"؛ وorchestrator_enabled: false يجبر كل ابن على العودة إلى leaf بغضّ النظر. تتضاعف التكلفة تضاعفيًا — عند max_spawn_depth: 3 مع max_concurrent_children: 3، يمكن للشجرة أن تصل إلى 3×3×3 = 27 وكيل leaf متزامن. راجع تفويض المهام إلى Subagents ← حد العمق والتنسيق المتداخل لأنماط الاستخدام.

      إشعارات العمليات الفرعية للأبناء: العمليات الخلفية التي يبدأها subagents توجّه إشعارات إتمامها/مراقبتها إلى المحادثة الأصل، لكنها مكتومة هناك افتراضيًا — نتيجة الابن المُدمجة هي التسليم النهائي. اضبط delegation.surface_child_process_notifications: true لتسليمها (مع إسناد إلى subagent). نتائج التفويض نفسها لا تُكتم أبدًا. راجع تفويض المهام إلى Subagents ← إشعارات العمليات الخلفية للأبناء.

      الشبكة​

      حلول التفافية لمشاكل الاتصال الصادر عبر HTTP:

      network:
        force_ipv4: false   # Force IPv4 for outbound connections (default: false)

      force_ipv4 — على الخوادم ذات IPv6 معطل أو غير قابل للوصول، يحلّ Python سجلات AAAA أولًا وقد يتعلّق طوال مهلة TCP الكاملة قبل الرجوع إلى IPv4. اضبط هذا على true لتخطي IPv6 كليًا والاتصال عبر IPv4 مباشرة.

      التهيئة الأولى (Onboarding)​

      تلميحات التهيئة عند أول لمسة وعرض بناء profile البنيوي:

      onboarding:
        profile_build: "ask"   # "ask" (default) | "off"
        seen: {}               # internal latch — leave empty
      • profile_build — يتحكم في مسار بناء profile المعروض عند أول رسالة gateway على الإطلاق. "ask" (الافتراضي) يعرض بناء profile للمستخدم؛ العرض اختياري ويتطلب موافقة — يسأل الوكيل قبل أي استعلام ولا يقرأ الحسابات المرتبطة بصمت أبدًا. "off" يعرض مقدمة بسيطة فقط. يظهر العرض مرة واحدة على الأكثر.
      • seen — حالة داخلية. يُثبّت Hermes كل تلميح مُعروض هنا بحيث لا يظهر مرة أخرى أبدًا؛ يُسجَّل عرض بناء profile هنا أيضًا بمجرد عرضه. لا تُحرِّره يدويًا — امسح قسم onboarding بالكامل إذا أردت رؤية كل التلميحات مجددًا.

      لوحة التحكم​

      إعدادات لوحة التحكم على الويب — المظهر البصري، والرابط العام، ومزوّدو المصادقة. مزوّدو المصادقة (OAuth، كلمة المرور الأساسية، drain) موثّقون بالتفصيل في صفحة لوحة التحكم على الويب؛ هذا هو شكل config.yaml.

      dashboard:
        theme: "default"            # "default" | "midnight" | "ember" | "mono" | "cyberpunk" | "rose"
        show_token_analytics: false # Re-enable the (local-estimate-only) token/cost analytics surfaces
        public_url: ""              # Full public authority for OAuth redirect_uri (env: HERMES_DASHBOARD_PUBLIC_URL)
        trusted_proxies: []         # Proxy IPs/CIDRs allowed to supply X-Forwarded-* headers
        oauth:                      # Portal OAuth gate (engaged with --host and not --insecure)
          client_id: ""             # agent:{instance_id} — Portal provisions this
          portal_url: ""            # blank → plugin default (production Portal)
        basic_auth:                 # Self-hosted username/password gate (dashboard_auth/basic plugin)
          username: ""              # blank → plugin no-op
          password_hash: ""         # scrypt$... (preferred — no plaintext at rest)
          password: ""              # plaintext fallback (hashed in-memory at load)
          secret: ""                # token-signing key; blank → random per-process
          session_ttl_seconds: 0    # 0 → plugin default (12h)
        drain_auth:                 # Drain-control service-credential gate (dashboard_auth/drain plugin)
          scope: "drain"            # capability label on the verified principal
          min_secret_chars: 43      # entropy bar (url-safe-b64 chars; 43 ≈ 256 bits)
        ws_ping_interval: 20.0      # Non-loopback WebSocket keepalive ping interval (seconds)
        ws_ping_timeout: 20.0       # Non-loopback WebSocket keepalive pong timeout (seconds)
        ws_orphan_reap_grace_s: 20.0 # Grace before a WS-detached session is reaped (seconds)
        ssh_isolated_idle_grace_s: 900.0 # Desktop-over-SSH backend exits after this long with no client and no running turn
        ws_orphan_activity_stale_s: 600.0 # Activity idle bound before a detached RUNNING turn is interrupted (seconds)
        startup_orphan_sweep: true  # Close session rows orphaned by a dead gateway process at boot
      • theme — المظهر البصري للوحة التحكم.
      • show_token_analytics — مُعطَّل افتراضيًا. صفحة Analytics وأرقام tokens/التكلفة هي تقدير محلي بحد أدنى (تستثني الاستدعاءات المساعدة، وإعادات المحاولة، والاحتياطات، وكتابات التخزين المؤقت)، لذا قد تظهر أقل بكثير من فاتورة المزوّد. اضبطها على true فقط إذا كنت تدرك أنها ليست فوترة.
      • public_url — عند ضبطه، يصبح هذا هو المرجع الكامل (المخطط + المضيف + بادئة المسار الاختيارية) الذي يُبنى منه redirect_uri الخاص بـ OAuth. اضبطه للنشر خلف وكلاء عكسيين (reverse proxies) لا يعيدون توجيه ترويسات X-Forwarded-* بشكل موثوق. اتركه فارغًا لاستخدام إعادة بناء ترويسات الوكيل.
      • trusted_proxies — عناوين IP أو شبكات CIDR محدودة يُسمح لها بتزويد X-Forwarded-Proto وX-Forwarded-For. يظل loopback موثوقًا تلقائيًا. اضبط هذا عندما يتصل وكيل TLS العكسي من حاوية أو مضيف آخر. فضّل عنوان IP الدقيق للوكيل؛ استخدم شبكة مخصّصة صغيرة فقط عندما يكون عنوانه متغيّرًا. تُرفض الرموز العامة (wildcards) وشبكات /0.
      • oauth / basic_auth / drain_auth — إعدادات مزوّد المصادقة التي تقرأها إضافات dashboard-auth المضمّنة. سرّ drain نفسه لا يُضبط هنا؛ بل يُوفَّر عبر متغير البيئة HERMES_DASHBOARD_DRAIN_SECRET. راجع لوحة تحكم Hermes على الويب لإعداد المصادقة الكامل.
      • ws_ping_interval / ws_ping_timeout — ضبط دقيق لإبقاء اتصال WebSocket حيًا للربط غير loopback (اتصالات loopback لا تُرسل نبضات أبدًا). ارفع هذه القيم على الروابط عالية الكمون (Tailscale، أنفاق SSH البعيدة) حيث يمكن للقيم الافتراضية البالغة 20 ثانية أن تُصنِّع قطعًا وهميًا برمز 1006.
      • ssh_isolated_idle_grace_s (الافتراضي 900) — backend من نوع hermes serve --isolated يملكه Desktop ويُصل إليه عبر SSH يُفصل عن جلسة SSH عمدًا، حتى لا يستطيع نوم الحاسوب المحمول أثناء الاتصال إسقاطه؛ كانت كل إعادة اتصال بعد استيقاظ مظلم تترك backend آخر يمسك بـ state.db. يتقاعد الـ backend الآن من تلقاء نفسه بمجرد ألا يكون هناك عميل WebSocket متصل لهذه المدة ولا يعمل دور وكيل (الدور الجاري يبقيه حيًا؛ وحالة دور غير قابلة للقراءة تبقيه حيًا أيضًا). اضبطه مرتفعًا إذا كنت تعتمد على backend مفصول لإنهاء عمل طويل بعد نوم الحاسوب المحمول. تُرسل مثل هذه الـ backends أيضًا نبضة WebSocket بطيئة (60 ثانية، مهلة 10 دقائق) بحيث يُلاحَظ النفق نصف المفتوح.
      • ws_orphan_reap_grace_s — المدة التي تنتظرها جلسة منفصلة عن WS قبل أن يجمعها حاصد اليتامى (orphan reaper). ارفعها إلى جانب قيم إبقاء الاتصال حيًا إذا كان العملاء يعيدون الاتصال ببطء. تُتمّم صيانة الجلسة الدورية أيضًا تنظيف المقابس المغلقة وتعيد تسليح مؤقت يتيم مفقود، لذا لا يمكن لمحادثة منفصلة الاحتفاظ بحق ملكيتها لمجرد فقدان تنظيفها الأولي أو مؤقتها. إعادة الاتصال تُلغي ذلك المؤقت؛ ويظل العمل المفوَّض النشط والأدوار الجارية السليمة محميين بفحوصات حاصد اليتامى العادية. (يبقى HERMES_TUI_WS_ORPHAN_REAP_GRACE_S كتجاوز داخلي.)
      • ws_orphan_activity_stale_s (الافتراضي 600) — المدة التي يجب أن تظل فيها ساعة نشاط دور جارٍ منفصل (نفس الساعة التي يراقبها حارس agent.turn_liveness: انتظارات API، tokens البث، نبضات الأدوات) خاملة قبل أن يقاطعه حاصد اليتامى. الدور الغائب عن العميل الذي لا يزال يُنتج فعليًا يستمر في العمل حتى الاكتمال بشكل منفصل — إغلاق الحاسوب المحمول، أو تشغيل تطبيق الجوال في الخلفية، أو تحديث سطح المكتب لم يعد يُلغي الأدوار الطويلة السليمة؛ فقط الدور المُعطَّل فعليًا يُقاطَع. اضبطه على 0 للمقاطعة عند نافذة الإمهال بغضّ النظر عن النشاط (السلوك القديم).
      • startup_orphan_sweep (الافتراضي true) — مؤقت حصد يتامى WS أعلاه يعمل داخل العملية نفسها، لذا فإن إعادة تشغيل gateway (تحديث، عطل، systemd) قبل أن يُطلَق يترك صف الجلسة مفتوحًا إلى الأبد — عمل "نشط" وهمي في /resume ولوحات التحكم. عند كل إقلاع لـ gateway — كلٌّ من TUI عبر stdio (entry.main) وsidecar WebSocket لسطح المكتب/لوحة التحكم (handle_ws) — تُغلَق الصفوف التي مصدرها tui / desktop / subagent والتي يكون وقت بدئها وأحدث رسالة فيها أقدم من مدة صلاحية الجلسة (HERMES_TUI_SESSION_TTL_S، الافتراضي 6 ساعات) بسبب إغلاق end_reason: startup_orphan_reap. جلسات منصات المراسلة (Telegram، Discord، …) لا تُمس أبدًا، وتُستثنى الجلسات الحية في الذاكرة (عميل استأنف بالفعل)، وتظل الجلسات المُجرَّفة قابلة للاستئناف.

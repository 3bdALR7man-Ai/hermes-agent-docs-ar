      Pinggy Tunnel

      أنفاق (tunnels) لـ localhost بلا تثبيت عبر SSH باستخدام Pinggy.

      بيانات المهارة الوصفية​

      المصدراختيارية — ثبّتها باستخدام hermes skills install official/devops/pinggy-tunnel
      المسارoptional-skills/devops/pinggy-tunnel
      الإصدار0.1.0
      المؤلفTeknium (teknium1), Hermes Agent
      الترخيصMIT
      المنصاتlinux, macos, windows
      الوسومPinggy, Tunnel, Networking, SSH, Webhook, Localhost

      المرجع: ملف SKILL.md كاملًا​

      معلومة

      ما يلي هو التعريف الكامل للمهارة الذي يحمّله Hermes عند تفعيل هذه المهارة، وهو ما يراه الوكيل كتعليمات أثناء عمل المهارة.

      Pinggy Tunnel Skill

      اعرض خدمة محلية (خادم تطوير، مستقبِل webhook، endpoint خاص بـ MCP، عرض توضيحي) على شبكة الإنترنت العامة باستخدام نفق SSH عكسي من Pinggy. لا حاجة إلى تثبيت أي daemon — يتصل عميل SSH الافتراضي لدى المستخدم بـ a.pinggy.io:443 وتعيد Pinggy رابط HTTP/HTTPS عامًا.

      الفئة المجانية: أنفاق مدتها 60 دقيقة، نطاق فرعي عشوائي، بلا تسجيل. الفئة الاحترافية (3 دولارات شهريًا) اختيارية وتتطلب token.

      متى تُستخدم​

      • يطلب المستخدم "عرض هذا محليًا للخارج"، "مشاركة خادم التطوير الخاص بي"، "اجعل هذا الرابط عامًا"، "أنشئ نفقًا للمنفذ N"، "احصل على رابط عام لـ webhook"
      • الحاجة إلى استقبال استدعاء webhook أثناء مهمة محلية (Stripe، GitHub، Discord، AgentMail)
      • مشاركة عرض HTTP لمرة واحدة (خادم MCP، endpoint خاص بـ Ollama/vLLM، لوحة تحكم) مع طرف بعيد
      • يملك المضيف SSH لكن لا يملك ملفًا تنفيذيًا مثل cloudflared / ngrok، وتثبيت واحد منهما سيكون مبالغة

      إذا كان المضيف يملك بالفعل cloudflared مُعدًّا، فضّل مهارة cloudflared-quick-tunnel — فأنفاق Cloudflare السريعة لا تنتهي صلاحيتها بعد 60 دقيقة.

      المتطلبات المسبقة​

      • ssh على PATH (ssh -V). موجود افتراضيًا على Linux وmacOS وWindows 10 وما بعده. لا حاجة إلى أي تثبيت آخر.
      • خدمة محلية تستمع على 127.0.0.1:<port> قبل بدء النفق. ستعيد Pinggy روابط لكنها ستُرجع 502 حتى يعمل المصدر المحلي.

      اختياري:

      • متغير البيئة PINGGY_TOKEN لميزات الفئة الاحترافية المدفوعة (نطاق فرعي دائم، نطاق مخصّص، أنفاق متعددة، بلا حد الستين دقيقة). الفئة المجانية لا تحتاج إلى بيانات اعتماد.

      مرجع سريع​

      # Plain HTTP/HTTPS tunnel for port 8000 (free tier)
      ssh -p 443 -o StrictHostKeyChecking=no -o ServerAliveInterval=30 \
          -R0:localhost:8000 free@a.pinggy.io

      # TCP tunnel (databases, raw SSH, etc.)
      ssh -p 443 -o StrictHostKeyChecking=no -R0:localhost:5432 tcp@a.pinggy.io

      # TLS tunnel (Pinggy can't decrypt — bring your own certs at origin)
      ssh -p 443 -o StrictHostKeyChecking=no -R0:localhost:443 tls@a.pinggy.io

      # Basic auth gate (b:user:pass)
      ssh -p 443 -o StrictHostKeyChecking=no -R0:localhost:8000 \
          "b:admin:secret+free@a.pinggy.io"

      # Bearer token gate (k:token)
      ssh -p 443 -o StrictHostKeyChecking=no -R0:localhost:8000 \
          "k:mysecrettoken+free@a.pinggy.io"

      # IP whitelist (w:CIDR)
      ssh -p 443 -o StrictHostKeyChecking=no -R0:localhost:8000 \
          "w:203.0.113.0/24+free@a.pinggy.io"

      # Enable CORS + force HTTPS redirect
      ssh -p 443 -o StrictHostKeyChecking=no -R0:localhost:8000 \
          "co+x:https+free@a.pinggy.io"

      # Pro tier (persistent URL, no 60-min cap)
      ssh -p 443 -o StrictHostKeyChecking=no -R0:localhost:8000 "$PINGGY_TOKEN+a.pinggy.io"

      الإجراء — إنشاء نفق والحصول على الرابط​

      ينبغي على النموذج استخدام أداة terminal. يجب أن يبقى النفق حيًّا طوال مدة المشاركة، لذا شغّله كعملية خلفية وحلّل الرابط العام من stdout.

      1. تأكّد من أن المصدر المحلي يعمل​

      curl -sI http://127.0.0.1:8000/ | head -1
      # expect HTTP/1.x 200 (or any non-connection-refused response)

      إن لم يكن هناك شيء يستمع بعد، شغّله أولًا (مثل python -m http.server 8000 --bind 127.0.0.1). ستعيد Pinggy رابطًا مُشيرًا إلى لا شيء دون مشكلة — وسيرى المستخدم 502 حتى يعمل المصدر.

      2. أطلق النفق كعملية خلفية​

      استخدم terminal(background=True) والتقط المخرجات في ملف سجل (تطبع Pinggy الروابط على stdout ثم تُبقي الاتصال مفتوحًا):

      LOG=/tmp/pinggy-8000.log
      nohup ssh -p 443 \
          -o StrictHostKeyChecking=no \
          -o UserKnownHostsFile=/dev/null \
          -o ServerAliveInterval=30 \
          -o ServerAliveCountMax=3 \
          -R0:localhost:8000 free@a.pinggy.io \
          > "$LOG" 2>&1 &
      echo $! > /tmp/pinggy-8000.pid

      يتجاوز StrictHostKeyChecking=no + UserKnownHostsFile=/dev/null رسالة تأكيد مفتاح المضيف عند التشغيل الأول. ويُبقي ServerAliveInterval=30 جلسة SSH من الانقطاع بسبب NAT خامل.

      3. حلّل الرابط من السجل​

      sleep 4
      grep -oE 'https://[a-z0-9-]+\.[a-z]+\.pinggy\.link' /tmp/pinggy-8000.log | head -1

      المخرجات المتوقعة تبدو كالتالي:

      You are not authenticated.
      Your tunnel will expire in 60 minutes.
      http://yqycl-98-162-69-48.a.free.pinggy.link
      https://yqycl-98-162-69-48.a.free.pinggy.link

      سلّم رابط https://...pinggy.link للمستخدم.

      4. تحقّق​

      curl -sI https://<the-url>/ | head -3
      # expect 200/302/whatever the local origin actually returns

      إذا ظهر 502 Bad Gateway، فإن جلسة SSH تعمل لكن المصدر المحلي لا يستمع — أصلح الخطوة 1 أولًا.

      5. إنهاء النفق​

      kill "$(cat /tmp/pinggy-8000.pid)"
      # or, if the pid file got lost:
      pkill -f 'ssh -p 443 .* free@a\.pinggy\.io'

      إذا كان لديك session_id من terminal(background=True)، فضّل process(action='kill', session_id=...).

      التحكم بالوصول عبر كلمات مفتاحية في اسم المستخدم​

      تُكدّس Pinggy أعلام التحكم داخل اسم مستخدم SSH مفصولة بـ +. ضع دائمًا معطى user@host بأكمله بين علامتي اقتباس عندما يحتوي على +:

      الكلمة المفتاحيةالتأثير
      b:user:passبوابة مصادقة HTTP Basic
      k:tokenبوابة ترويسة Bearer token (Authorization: Bearer <token>)
      w:CIDRقائمة IP بيضاء (IP واحد أو CIDR، قابل للتكرار)
      coإضافة Access-Control-Allow-Origin: * (CORS)
      x:httpsفرض HTTPS — إعادة توجيه HTTP إلى HTTPS تلقائيًا
      a:Name:Valueإضافة ترويسة طلب
      u:Name:Valueتحديث ترويسة طلب
      r:Nameإزالة ترويسة طلب
      qrطباعة رمز QR للرابط على stdout (مفيد للمشاركة عبر الهاتف)

      اجمعها بحرّية: "b:admin:secret+co+x:https+free@a.pinggy.io".

      مُصحّح الويب (اختياري)​

      يمكن لـ Pinggy أن تعكس (mirror) حركة المرور الواردة إلى localhost:4300 للفحص. أضِف توجيهًا محليًا (local forward) إلى أمر SSH:

      ssh -p 443 -L4300:localhost:4300 -R0:localhost:8000 free@a.pinggy.io

      ثم افتح http://localhost:4300 في متصفح لرؤية أزواج الطلب/الاستجابة الحية.

      المزالق الشائعة​

      • حد صارم 60 دقيقة في الفئة المجانية. تنتهي جلسة SSH عند علامة الستين دقيقة؛ يتوقف الرابط عن العمل. للمشاركات الأطول، استخدم إما PINGGY_TOKEN (الفئة الاحترافية) أو أعِد التشغيل تلقائيًا بحلقة shell (لاحظ أن الرابط يتغيّر عند كل إعادة تشغيل في الفئة المجانية).
      • رابط الفئة المجانية عشوائي ويتغيّر عند إعادة التشغيل. لا تحفظه كإشارة مرجعية، ولا تلصقه في ملف إعدادات. أعِد تحليله من السجل في كل مرة.
      • الأنفاق المجانية المتزامنة محدودة بنفق واحد لكل عنوان IP مصدر. بدء نفق ثانٍ من الجهاز نفسه يُنهي عادةً الأول. تُلغي الفئة الاحترافية هذا القيد.
      • يجب وضع + في أسماء المستخدمين بين علامتي اقتباس. يعمل ssh ... b:admin:secret+free@a.pinggy.io بلا اقتباس في bash لكنه ينكسر في shells التي تعامل + معاملة خاصة أو عند تركيبه برمجيًا. ضعه دائمًا بين علامتي اقتباس مزدوجتين.
      • لا تُنشئ نفقًا لأي شيء حسّاس دون علم تحكم بالوصول. يمكن لأي شخص يملك الرابط الوصول إلى نفق HTTP عادي. استخدم b: أو k: أو w: للخدمات غير العامة.
      • قد يفوّت process(action='log') مخرجات لافتة SSH. تطبع Pinggy الروابط ثم تدخل جلسة SSH وضع التفاعل. وجّه دائمًا المخرجات إلى ملف سجل واستخدم grep على الملف مباشرة — نفس نمط cloudflared-quick-tunnel.
      • رسالة تأكيد مفتاح المضيف عند التشغيل الأول. تطلب إعدادات OpenSSH الافتراضية من المستخدم قبول مفتاح مضيف Pinggy. مرّر دائمًا -o StrictHostKeyChecking=no -o UserKnownHostsFile=/dev/null للتشغيلات غير المراقَبة.
      • تعيد أنفاق TCP وTLS زوجًا من الصيغة <subdomain>.a.pinggy.online:<port>، لا رابط https. حلّلها بتعبير نمطي مختلف (tcp:// ومنفذ). لا تفترض أن كل نفق Pinggy هو HTTP.
      • يتطلب وضع Pro الـ token كاسم مستخدم، لا كعلم. استخدم "$PINGGY_TOKEN+a.pinggy.io" (بلا free@). مع token يمكنك أيضًا إضافة :persistent للحصول على نطاق فرعي ثابت — راجع pinggy.io/docs/.

      وصفات​

      أنماط مركّبة تجمع بين مصدر محلي ونفق Pinggy. كل وصفة قائمة بذاتها — ابدأ المصدر، ابدأ النفق، حلّل الرابط، وسلّمه للمستخدم.

      الوصفة 1 — استقبال استدعاء webhook​

      استخدم هذه الوصفة عندما تحتاج خدمة خارجية (Stripe، GitHub، Discord، AgentMail، إلخ) إلى إرسال POST إلى رابط يمكن الوصول إليه علنًا أثناء مهمة محلية.

      # 1. Tiny capturing server: every request gets appended to /tmp/webhook-hits.log
      cat >/tmp/webhook-server.py <<'PY'
      import http.server, json, datetime, pathlib
      LOG = pathlib.Path("/tmp/webhook-hits.log")
      class H(http.server.BaseHTTPRequestHandler):
          def _capture(self):
              n = int(self.headers.get("content-length") or 0)
              body = self.rfile.read(n).decode("utf-8", "replace") if n else ""
              rec = {"t": datetime.datetime.utcnow().isoformat(), "path": self.path,
                     "method": self.command, "headers": dict(self.headers), "body": body}
              with LOG.open("a") as f: f.write(json.dumps(rec) + "\n")
              self.send_response(200); self.send_header("content-type","application/json")
              self.end_headers(); self.wfile.write(b'{"ok":true}\n')
          def do_GET(self): self._capture()
          def do_POST(self): self._capture()
          def log_message(self,*a,**k): pass
      http.server.HTTPServer(("127.0.0.1", 18080), H).serve_forever()
      PY
      nohup python /tmp/webhook-server.py >/tmp/webhook-server.log 2>&1 &
      echo $! >/tmp/webhook-server.pid

      # 2. Tunnel — bearer-token-gate so randos can't pollute the capture log
      nohup ssh -p 443 -o StrictHostKeyChecking=no -o UserKnownHostsFile=/dev/null \
          -o ServerAliveInterval=30 \
          -R0:localhost:18080 "k:$(openssl rand -hex 12)+free@a.pinggy.io" \
          >/tmp/webhook-pinggy.log 2>&1 &
      echo $! >/tmp/webhook-pinggy.pid
      sleep 5
      URL=$(grep -oE 'https://[a-z0-9-]+\.[a-z]+\.pinggy\.link' /tmp/webhook-pinggy.log | head -1)
      echo "Webhook URL: $URL"

      # 3. While the agent works, watch hits land
      tail -f /tmp/webhook-hits.log

      سلّم $URL إلى الخدمة التي تحتاج إلى استدعائك. الإنهاء: kill $(cat /tmp/webhook-server.pid) $(cat /tmp/webhook-pinggy.pid).

      الوصفة 2 — عرض خادم MCP عبر HTTP/SSE​

      استخدمها عندما يحتاج عميل MCP بعيد (Claude Desktop على جهاز آخر، محرّر زميل، إلخ) إلى الوصول إلى خادم MCP يعمل على الجهاز المحلي. يعمل هذا فقط مع خوادم MCP التي تتحدث عبر نقل HTTP — لا يمكن إنشاء نفق لخوادم في وضع stdio.

      # 1. Start the MCP server in HTTP mode (example: a FastMCP server on port 8765)
      nohup python my_mcp_server.py --transport http --port 8765 \
          >/tmp/mcp-server.log 2>&1 &
      echo $! >/tmp/mcp-server.pid

      # 2. Tunnel with a bearer token — MCP traffic should not be open to the internet
      TOKEN=$(openssl rand -hex 16)
      nohup ssh -p 443 -o StrictHostKeyChecking=no -o UserKnownHostsFile=/dev/null \
          -o ServerAliveInterval=30 \
          -R0:localhost:8765 "k:$TOKEN+free@a.pinggy.io" \
          >/tmp/mcp-pinggy.log 2>&1 &
      echo $! >/tmp/mcp-pinggy.pid
      sleep 5
      URL=$(grep -oE 'https://[a-z0-9-]+\.[a-z]+\.pinggy\.link' /tmp/mcp-pinggy.log | head -1)
      echo "MCP URL: $URL"
      echo "Bearer token: $TOKEN"

      يتصل العميل البعيد بـ $URL باستخدام Authorization: Bearer $TOKEN. إعدادات عميل MCP الأصلي الخاص بـ Hermes: {"transport": "http", "url": "<URL>", "headers": {"Authorization": "Bearer <TOKEN>"}}.

      الوصفة 3 — عرض endpoint خاص بـ LLM محلي (Ollama / vLLM / llama.cpp)​

      شارك نموذجًا محليًا مع مستدعٍ بعيد (وكيل آخر، هاتف، زميل). تستمع Ollama على المنفذ :11434، وvLLM وllama.cpp عادةً على المنفذ :8000.

      # Pre-req: the model server is already running on 127.0.0.1:11434 (Ollama default)
      TOKEN=$(openssl rand -hex 16)
      nohup ssh -p 443 -o StrictHostKeyChecking=no -o UserKnownHostsFile=/dev/null \
          -o ServerAliveInterval=30 \
          -R0:localhost:11434 "k:$TOKEN+co+free@a.pinggy.io" \
          >/tmp/llm-pinggy.log 2>&1 &
      echo $! >/tmp/llm-pinggy.pid
      sleep 5
      URL=$(grep -oE 'https://[a-z0-9-]+\.[a-z]+\.pinggy\.link' /tmp/llm-pinggy.log | head -1)
      echo "Endpoint: $URL"
      echo "Token:    $TOKEN"

      # Verify
      curl -s "$URL/api/tags" -H "Authorization: Bearer $TOKEN" | head

      يفعّل co خاصية CORS كي يستطيع مستدعٍ من متصفح الوصول إلى الـ endpoint. احذف co للمستدعين من الخلفية فقط. بالنسبة إلى endpoint متوافق مع OpenAI لـ vLLM/llama.cpp، يستخدم المستدعون الرابط الأساسي $URL/v1 مع Authorization: Bearer $TOKEN — لكن لاحظ أن Pinggy لا تحذف أو تستبدل شيئًا في المحتوى، لذا يرى خادم النموذج نفسه token الخاص بـ Pinggy؛ ينبغي إعداد الخادم المحلي لتجاهل المصادقة (فهو أصلًا على 127.0.0.1) وترك عملية التحكم بالوصول لـ Pinggy.

      الوصفة 4 — مشاركة خادم تطوير بكلمة مرور لمرة واحدة​

      أسرع نمط لـ "دع زميلًا يجرّب تطبيقي قيد التشغيل". كلمة مرور عشوائية، تُطبع مرة واحدة، وتموت عند الضغط على Ctrl-C.

      PASS=$(openssl rand -base64 12 | tr -d '+/=' | head -c 12)
      echo "Dev server password: $PASS"
      ssh -p 443 -o StrictHostKeyChecking=no -o UserKnownHostsFile=/dev/null \
          -o ServerAliveInterval=30 \
          -R0:localhost:3000 "b:dev:$PASS+co+x:https+free@a.pinggy.io"
      # URL prints to the terminal. Share URL + password. Ctrl-C to tear down.

      يحمي b:dev:$PASS الرابط بمصادقة HTTP Basic. يفرض x:https TLS. يضيف co دعم CORS لواجهات SPA الأمامية.

      التحقق​

      # End-to-end: spin up a trivial origin, tunnel it, hit it, tear down
      python -m http.server 18000 --bind 127.0.0.1 >/tmp/origin.log 2>&1 &
      ORIGIN_PID=$!

      nohup ssh -p 443 \
          -o StrictHostKeyChecking=no \
          -o UserKnownHostsFile=/dev/null \
          -R0:localhost:18000 free@a.pinggy.io >/tmp/pinggy-verify.log 2>&1 &
      SSH_PID=$!

      sleep 5
      URL=$(grep -oE 'https://[a-z0-9-]+\.[a-z]+\.pinggy\.link' /tmp/pinggy-verify.log | head -1)
      echo "URL: $URL"
      curl -sI "$URL/" | head -1

      kill "$SSH_PID" "$ORIGIN_PID"

      المتوقّع: رابط pinggy.link واستجابة HTTP/2 200 عند طلب curl head.

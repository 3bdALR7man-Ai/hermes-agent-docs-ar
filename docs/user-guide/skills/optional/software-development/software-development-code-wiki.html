      Code Wiki

      أنشئ مستندات wiki ومخططات Mermaid لأي قاعدة كود.

      بيانات المهارة الوصفية​

      المصدراختيارية — ثبّتها باستخدام hermes skills install official/software-development/code-wiki

      المرجع: ملف SKILL.md كاملًا​

      معلومة

      ما يلي هو التعريف الكامل للمهارة الذي يحمّله Hermes عند تفعيل هذه المهارة، وهو ما يراه الوكيل كتعليمات أثناء عمل المهارة.

      مهارة Code Wiki

      أنشئ ويكي كاملًا لأي قاعدة كود — نظرة عامة، بنية معمارية، تفصيل لكل وحدة على حدة، ومخططات Mermaid للفئات (class) والتسلسل (sequence). مستوحاة من Google CodeWiki، لكنها تعمل على المستودعات المحلية، والمستودعات الخاصة، وبأي لغة. تستخدم فقط أدوات Hermes الموجودة (terminal، read_file، search_files، write_file) دون الحاجة إلى Docker أو خدمات خارجية أو اعتماديات إضافية.

      تنتج هذه المهارة مستندات مرجعية (ماذا/كيف). ولا تنتج سردًا استراتيجيًا (لماذا — وهذه مهارة مختلفة).

      متى تُستخدم​

      • يقول المستخدم "وثّق قاعدة الكود هذه"، "أنشئ ويكي"، "اصنع مخططات بنية معمارية"
      • عند التعرّف على مستودع غير مألوف والحاجة إلى مرجع منظّم
      • يشير المستخدم إلى رابط GitHub ويطلب توثيقًا
      • الحاجة إلى ناتج ثابت (markdown + Mermaid) يُعرض بشكل صحيح على GitHub

      لا تستخدمها في الحالات التالية:

      • توثيق ملف واحد أو دالة واحدة — أجب مباشرة فحسب
      • مرجع API لنقطة نهاية (endpoint) واحدة محددة — استخدم read_file وأجب ضمن المحادثة
      • السرد الاستراتيجي حول "لماذا يوجد هذا" — مهارة مختلفة بغرض مختلف
      • قواعد الكود التي يعمل عليها المستخدم فعليًا في هذه الجلسة — اكتفِ بالإجابة عن الأسئلة كلما وردت

      المتطلبات المسبقة​

      • لا حاجة إلى متغيرات بيئة.
      • git متاح في PATH لتتبّع SHA المستودع والاستنساخ عن بُعد.
      • اختياري: pygount لإحصاءات توزيع اللغات (راجع مهارة codebase-inspection).

      طريقة التشغيل​

      استدعِها عبر أداة terminal من جذر المستودع الهدف، ثم استخدم read_file / search_files / write_file لإنتاج الويكي. موقع الإخراج الافتراضي هو ~/.hermes/wikis/<repo-name>/. لا تكتب داخل المستودع (docs/wiki/) إلا إذا طلب المستخدم ذلك صراحةً.

      مرجع سريع​

      الخطوةالإجراء
      1حدّد الهدف — دليل العمل الحالي، أو مسار معطى، أو git clone --depth 50 <url> إلى دليل مؤقت
      2افحص البنية — ls، find -maxdepth 3، ملفات manifest، README
      3اختر 8 إلى 10 وحدات لتوثيقها
      4اكتب README.md (نظرة عامة + خريطة الوحدات)
      5اكتب architecture.md مع مخطط تدفق Mermaid
      6اكتب مستندات كل وحدة في modules/
      7اكتب diagrams/class-diagram.md (مخطط classDiagram في Mermaid)
      8اكتب diagrams/sequences.md (مخطط sequenceDiagram في Mermaid، بمعدل 2 إلى 4 مسارات عمل)
      9اكتب getting-started.md
      10اكتب api.md إن انطبق، وإلا تخطَّه
      11اكتب .codewiki-state.json
      12أبلغ المستخدم بالمسارات

      الإجراء​

      1. حدّد الهدف​

      لرابط GitHub:

      WIKI_TMP=$(mktemp -d)
      git clone --depth 50 <url> "$WIKI_TMP/repo"
      cd "$WIKI_TMP/repo"
      REPO_SHA=$(git rev-parse HEAD)
      REPO_NAME=$(basename <url> .git)

      لمسار محلي (أو دليل العمل الحالي إن لم يُحدَّد شيء):

      cd <path>
      REPO_SHA=$(git rev-parse HEAD 2>/dev/null || echo "uncommitted")
      REPO_NAME=$(basename "$PWD")

      ثم اضبط دليل الإخراج:

      OUTPUT_DIR="$HOME/.hermes/wikis/$REPO_NAME"
      mkdir -p "$OUTPUT_DIR/modules" "$OUTPUT_DIR/diagrams"

      2. افحص بنية المستودع​

      استخدم أداة terminal لعمليات shell، وread_file لملفات manifest:

      # Shallow tree first
      ls -la

      # Deeper tree, noise filtered
      find . -type d \
        -not -path '*/\.*' \
        -not -path '*/node_modules*' \
        -not -path '*/venv*' \
        -not -path '*/__pycache__*' \
        -not -path '*/dist*' \
        -not -path '*/build*' \
        -not -path '*/target*' \
        -maxdepth 3 | sort

      # Language breakdown (skip if pygount unavailable)
      pygount --format=summary \
        --folders-to-skip=".git,node_modules,venv,.venv,__pycache__,.cache,dist,build,target" \
        . 2>/dev/null || true

      ثم استخدم read_file لقراءة ملفات manifest ذات الصلة (package.json، pyproject.toml، setup.py، Cargo.toml، go.mod، pom.xml، build.gradle) وملف README الخاص بالمشروع. استخدم search_files target='files' للعثور عليها بدلًا من تخمين أسمائها.

      3. اختر الوحدات المراد توثيقها​

      احصر الجولة الأولى في 8 إلى 10 وحدات. القواعد الإرشادية حسب اللغة:

      • Python: الحزم (packages) على المستوى الأعلى (الأدلة التي تحتوي __init__.py)، إضافة إلى أدلة الأنظمة الفرعية
      • JS/TS: src/<subdir>، أدلة workspace على المستوى الأعلى
      • Rust: كل crate ضمن workspace، أو أدلة src/<module> على المستوى الأعلى
      • Go: كل دليل حزمة (package) على المستوى الأعلى
      • مختلط/غير مألوف: الأدلة على المستوى الأعلى التي تحتوي كود مصدري (وليست إعدادات أو اختبارات)

      للمستودعات الكبيرة جدًا، رتّب الأولوية حسب:

      1. عدد مرات الاستيراد (الوحدة التي تُستورَد من قِبل وحدات كثيرة تُعدّ أساسية)
      2. عدد أسطر الكود (LOC) (الوحدات الأكبر تستحق عادة مستندًا خاصًا بها)
      3. ذكرها في README أو المستندات على المستوى الأعلى

      اذكر للمستخدم قائمة الوحدات قبل توليد مستندات كل وحدة في المستودعات الكبيرة — يمنحه ذلك فرصة لإعادة التوجيه.

      4. اكتب README.md​

      استخدم read_file لقراءة ملف README الفعلي للمشروع مع أهم 2 إلى 3 ملفات نقطة دخول. ثم استخدم write_file:

      # <Project Name>

      <One paragraph: what it is and what it's for. Self-contained — don't assume the
      reader has the source README.>

      ## Key Concepts

      - **<Concept 1>** — <one line>
      - **<Concept 2>** — <one line>

      ## Entry Points

      - [`path/to/main.py`](https://github.com/NousResearch/hermes-agent/blob/main/optional-skills/software-development/code-wiki/<link>) — <what runs when you start it>
      - [`path/to/cli.py`](https://github.com/NousResearch/hermes-agent/blob/main/optional-skills/software-development/code-wiki/<link>) — <CLI surface>

      ## High-Level Architecture

      <2-3 sentences. Detail goes in architecture.md.>

      See [architecture.md](https://github.com/NousResearch/hermes-agent/blob/main/optional-skills/software-development/code-wiki/architecture.md).

      ## Module Map

      | Module | Purpose |
      |---|---|
      | [`<module>`](https://github.com/NousResearch/hermes-agent/blob/main/optional-skills/software-development/code-wiki/modules/<module>.md) | <one-line purpose> |

      ## Getting Started

      See [getting-started.md](https://github.com/NousResearch/hermes-agent/blob/main/optional-skills/software-development/code-wiki/getting-started.md).

      في الوضع المحلي استخدم مسارات نسبية لأهداف الروابط. أما بالنسبة للمستودعات المستنسخة فاستخدم https://github.com/<owner>/<repo>/blob/<sha>/<path> حتى تبقى الروابط صالحة عبر الـ commits المستقبلية.

      5. اكتب architecture.md​

      # Architecture

      <2-3 paragraphs: shape of the system. What talks to what. Where data enters,
      where it exits, where state lives.>

      ## Components

      - **<Component>** — <1-2 sentences>. See [`modules/<module>.md`](https://github.com/NousResearch/hermes-agent/blob/main/optional-skills/software-development/code-wiki/modules/<module>.md).

      ## System Diagram

      ```mermaid
      flowchart TD
          User([User]) --> Entry[Entry Point]
          Entry --> Core[Core Engine]
          Core --> StorageA[(Database)]
          Core --> ExternalAPI{{External API}}
      ```

      ## Data Flow

      1. **<Step>** — [`<file>`](https://github.com/NousResearch/hermes-agent/blob/main/optional-skills/software-development/code-wiki/<link>)
      2. **<Step>** — [`<file>`](https://github.com/NousResearch/hermes-agent/blob/main/optional-skills/software-development/code-wiki/<link>)

      ## Key Design Decisions

      - <Anything load-bearing the reader should know>

      دلالات أشكال Mermaid:

      • [] = مكوّن
      • [()] = قاعدة بيانات / تخزين
      • {{}} = خدمة خارجية
      • (()) = نقطة دخول أو نهاية (terminal)
      • --> = استدعاء متزامن، -.-> = غير متزامن/حدث

      احصر المخطط في نحو 20 عقدة كحد أقصى. قسّمه إلى مخططات فرعية إن كان أكبر من ذلك.

      6. اكتب مستندات كل وحدة في modules/​

      لكل وحدة مختارة، افحص بنيتها باستخدام ls، وحدّد 3 إلى 5 من أهم الملفات (بحسب الحجم، أو التسمية core.py / main.py / __init__.py، أو كثرة استيرادها)، ثم استخدم read_file لقراءة تلك الملفات (استعمل offset / limit لقراءة ما تحتاجه فقط، وفضّل search_files لرموز محددة).

      - <bullet>

      7. اكتب diagrams/class-diagram.md​

      اختر 5 إلى 10 من أهم الفئات (classes)/الأنواع. استخدم read_file لقراءتها، ثم اكتب:

      # Class Diagram

      ## Core Types

      ```mermaid
      classDiagram
          class Agent {
              +string name
              +list~Tool~ tools
              +chat(message) string
          }
          class Tool {
              <<interface>>
              +name string
              +execute(args) any
          }
          Agent --> Tool : uses
          Tool <|-- TerminalTool
          Tool <|-- WebTool
      ```

      ## Notes

      <Anything the diagram can't express — lifecycle, threading, etc.>

      للغات التي لا تحتوي فئات (Go، C، Rust): استخدم المخطط لعلاقات الـ structs، أو تخطَّ ملف class-diagram.md واشرح الأمر نثرًا في architecture.md. لا تفرض شكلًا لا يناسب اللغة.

      8. اكتب diagrams/sequences.md​

      اختر 2 إلى 4 من أهم مسارات العمل. تتبّع مسار كل استدعاء عبر الكود (اقرأ نقطة الدخول، وتابع استدعاءات الدوال)، ثم:

      # Sequence Diagrams

      ## Workflow: <Name>

      <1 sentence describing what this does and when it runs.>

      ```mermaid
      sequenceDiagram
          participant User
          participant CLI
          participant Agent
          participant LLM
          User->>CLI: types message
          CLI->>Agent: chat(message)
          Agent->>LLM: API call
          LLM-->>Agent: response + tool_calls
          Agent->>Agent: execute tools
          Agent-->>CLI: final response
      ```

      ### Walkthrough

      1. **User input** — [`cli.py:HermesCLI.run_session`](https://github.com/NousResearch/hermes-agent/blob/main/optional-skills/software-development/code-wiki/<link>)
      2. **Message dispatch** — [`run_agent.py:AIAgent.chat`](https://github.com/NousResearch/hermes-agent/blob/main/optional-skills/software-development/code-wiki/<link>)

      لا تختلق مشاركين (participants). يجب أن يقابل كل مربع مكوّنًا حقيقيًا يستطيع القارئ إيجاده في الكود.

      10. اكتب api.md (تخطَّه إن لم ينطبق)​

      اكتب هذا الملف فقط إذا كان المشروع مكتبة أو خادم API. إن كان كذلك:

      • حدّد سطح الـ API العام (صادرات __init__.py، مواصفات OpenAPI، معالجات المسارات، الأنواع المُصدَّرة)
      • وثّق كل نقطة عامة مع التوقيع (signature) والمعاملات ونوع القيمة المُعادة ووصف من سطر واحد
      • صنّفها ضمن فئات

      11. اكتب ملف الحالة​

      cat > "$OUTPUT_DIR/.codewiki-state.json" <<EOF
      {
        "repo_name": "$REPO_NAME",
        "source_path": "$PWD",
        "source_sha": "$REPO_SHA",
        "generated_at": "$(date -u +%Y-%m-%dT%H:%M:%SZ)",
        "generator": "hermes-agent code-wiki skill v0.1.0",
        "modules_documented": []
      }
      EOF

      12. أبلغ المستخدم​

      اذكر بالضبط ما تم توليده وأين:

      Generated wiki at ~/.hermes/wikis/<repo-name>/:
        README.md                   project overview, module map
        architecture.md             system architecture + flowchart
        getting-started.md          setup, first run, workflows
        modules/<N files>           per-module deep-dives
        diagrams/architecture.md    Mermaid flowchart
        diagrams/class-diagram.md   Mermaid class diagram
        diagrams/sequences.md       Mermaid sequence diagrams

      إذا استنسخت إلى دليل مؤقت، ذكّر المستخدم بأنه يمكن حذفه (rm -rf "$WIKI_TMP") بعد مراجعته للويكي.

      التحكم في النطاق​

      توليد ويكي كامل لمستودع أحادي (monorepo) بحجم 500 ألف سطر كود مكلف جدًا من حيث الـ tokens. اجعل النطاق محدودًا افتراضيًا:

      • الفحص الأولي: عمق أقصى 3 أدلة
      • مستندات كل وحدة: حدّها بـ 10 وحدات ما لم يوسّع المستخدم النطاق
      • قراءة الملفات: فضّل search_files للرموز مع read_file باستخدام offset/limit بدلًا من القراءة الكاملة
      • تخطَّ الكود المُستورد جاهزًا (vendor/، third_party/، الكود المُولَّد، _pb2.py، .min.js)

      إذا قال المستخدم "نفّذ الأمر كاملًا وبشمولية"، صدّقه — لكن قدّر التكلفة أولًا: "هذا المستودع يحتوي نحو 340 ملفًا مصدريًا، والتغطية الشاملة ستكون مكلفة — هل تؤكد؟"

      إعادة التشغيل / التحديث​

      إذا كان .codewiki-state.json موجودًا مسبقًا في المسار الهدف:

      • اقرأه للحصول على SHA السابق وقائمة الوحدات
      • إذا تطابق SHA المصدر: اسأل المستخدم إن كان يريد إعادة التوليد أو التخطي
      • إذا اختلف SHA: اقترح إعادة توليد الوحدات ذات الملفات المتغيرة فقط (git diff --name-only <old-sha> HEAD)

      إعادة التوليد التزايدية الكاملة تحسين مستقبلي — أما الآن، فإعادة توليد كل شيء أمر مقبول.

      المزالق​

      • اختلاق مكوّنات. يجب أن تكون كل عقدة في المخطط وكل استدعاء دالة مزعوم موجودًا فعلًا في المصدر. استخدم read_file قبل الكتابة. أكبر أنماط الفشل في المستندات المُولَّدة تلقائيًا هو الاختلاق الذي يبدو معقولًا.
      • نثر عام من الذكاء الاصطناعي. عبارة "هذه الوحدة مسؤولة عن..." خالية من أي مضمون. اذكر ما تفعله الوحدة فعلًا بمصطلحات خاصة بالمجال.
      • إعادة صياغة الكود نثرًا. مستند وحدة يقول "تقوم دالة process بمعالجة الأشياء عبر استدعاء process_item على كل عنصر" أسوأ من مجرد الربط بالدالة.
      • مخطط Mermaid بأكثر من 50 عقدة. لا يُعرض بوضوح. قسّمه.
      • توثيق الاختبارات أو الكود المُولَّد أو الاعتماديات المستوردة جاهزة وكأنها كود المنتج. تخطَّها.
      • الإخراج داخل المستودع دون سؤال. الافتراضي هو ~/.hermes/wikis/. لا تكتب داخل المستودع إلا إذا طلب المستخدم ذلك صراحةً.
      • الرموز الخاصة في Mermaid تحتاج علامات اقتباس: A["Tool / Agent"] وليس A[Tool / Agent]. استخدم <br> لفواصل الأسطر داخل العقدة.
      • أسيجة الكود المتداخلة في SKILL.md. عند كتابة مثال markdown يحتوي كتلة Mermaid، استخدم أسيجة خارجية من 4 علامات backtick حتى لا تُغلق الكتلة الداخلية ذات الـ3 علامات ```mermaid السياج الخارجي. (ملف SKILL.md هذا يفعل ذلك.)
      • الأنواع العامة (generics) في classDiagram تُعرض بالصيغة ~T~ (مثل List~Tool~) وليس <T>.
      • سمة Mermaid على GitHub ثابتة — لا تُضمِّن كتل %%{init: ...}%%؛ إذ تُحذف عند العرض.

      التحقق​

      بعد الكتابة، تحقّق من:

      1. توازن كتل Mermaid — تساوي عدد الفتحات مع عدد الإغلاقات لكل ملف: 
        for f in "$OUTPUT_DIR"/diagrams/*.md "$OUTPUT_DIR"/architecture.md; do
          opens=$(grep -c '^```mermaid' "$f")
          total=$(grep -c '^```' "$f")
          echo "$f: $opens mermaid blocks, $total total fences (expect total = opens*2)"
        done
      2. وجود جميع الملفات المتوقعة — 
        ls "$OUTPUT_DIR"/{README.md,architecture.md,getting-started.md,.codewiki-state.json} \
           "$OUTPUT_DIR"/modules/ "$OUTPUT_DIR"/diagrams/
      3. تطابق عدد الوحدات مع ما قصدته — يجب أن تساوي نتيجة ls "$OUTPUT_DIR/modules" | wc -l عدد الوحدات التي التزمت بها في الخطوة 3.
      4. عدم وجود مسارات مختلقة — تحقّق يدويًا من أن 2 إلى 3 روابط مصدرية تشير إلى ملفات حقيقية.

      التطوير المُدار عبر Subagent

      نفّذ الخطط عبر subagents باستخدام delegate_task (مراجعة على مرحلتين).

      بيانات المهارة الوصفية​

      المصدراختيارية — ثبّتها باستخدام hermes skills install official/software-development/subagent-driven-development

      معلومة

      ما يلي هو التعريف الكامل للمهارة الذي يحمّله Hermes عند تفعيل هذه المهارة، وهو ما يراه الوكيل كتعليمات أثناء عمل المهارة.

      التطوير المُدار عبر Subagent

      نظرة عامة​

      نفّذ خطط التنفيذ عن طريق إرسال subagents جديدة لكل مهمة، مع مراجعة منهجية على مرحلتين.

      المبدأ الأساسي: subagent جديد لكل مهمة + مراجعة على مرحلتين (المواصفات ثم الجودة) = جودة عالية وتكرار سريع.

      متى تُستخدم​

      استخدم هذه المهارة عندما:

      • تملك خطة تنفيذ (من مهارة plan أو من متطلبات المستخدم)
      • تكون المهام مستقلة في الغالب
      • تكون الجودة والالتزام بالمواصفات مهمَّين
      • تريد مراجعة آلية بين المهام

      مقارنةً بالتنفيذ اليدوي:

      • سياق (context) جديد لكل مهمة (بلا التباس ناتج عن حالة متراكمة)
      • عملية المراجعة الآلية تكتشف المشكلات مبكرًا
      • فحوصات جودة متسقة عبر كل المهام
      • تستطيع الـ subagents طرح أسئلة قبل بدء العمل

      العملية​

      1. اقرأ الخطة وحلّلها​

      اقرأ ملف الخطة. استخرج كل المهام بنصها الكامل وسياقها مسبقًا. أنشئ قائمة مهام (todo):

      # Read the plan
      read_file("docs/plans/feature-plan.md")

      # Create todo list with all tasks
      todo([
          {"id": "task-1", "content": "Create User model with email field", "status": "pending"},
          {"id": "task-2", "content": "Add password hashing utility", "status": "pending"},
          {"id": "task-3", "content": "Create login endpoint", "status": "pending"},
      ])

      مهم: اقرأ الخطة مرة واحدة. استخرج كل شيء. لا تجعل الـ subagents تقرأ ملف الخطة — قدّم نص المهمة الكامل مباشرةً ضمن السياق.

      2. سير العمل لكل مهمة​

      لكل مهمة في الخطة:

      الخطوة 1: أرسل subagent التنفيذ​

      استخدم delegate_task مع سياق كامل:

      delegate_task(
          goal="Implement Task 1: Create User model with email and password_hash fields",
          context="""
          TASK FROM PLAN:
          - Create: src/models/user.py
          - Add User class with email (str) and password_hash (str) fields
          - Use bcrypt for password hashing
          - Include __repr__ for debugging

          FOLLOW TDD:
          1. Write failing test in tests/models/test_user.py
          2. Run: pytest tests/models/test_user.py -v (verify FAIL)
          3. Write minimal implementation
          4. Run: pytest tests/models/test_user.py -v (verify PASS)
          5. Run: pytest tests/ -q (verify no regressions)
          6. Commit: git add -A && git commit -m "feat: add User model with password hashing"

          PROJECT CONTEXT:
          - Python 3.11, Flask app in src/app.py
          - Existing models in src/models/
          - Tests use pytest, run from project root
          - bcrypt already in requirements.txt
          """,
          toolsets=['terminal', 'file']
      )

      الخطوة 2: أرسل مراجع الالتزام بالمواصفات​

      بعد أن ينتهي المنفِّذ، تحقّق من التطابق مع المواصفات الأصلية:

      delegate_task(
          goal="Review if implementation matches the spec from the plan",
          context="""
          ORIGINAL TASK SPEC:
          - Create src/models/user.py with User class
          - Fields: email (str), password_hash (str)
          - Use bcrypt for password hashing
          - Include __repr__

          CHECK:
          - [ ] All requirements from spec implemented?
          - [ ] File paths match spec?
          - [ ] Function signatures match spec?
          - [ ] Behavior matches expected?
          - [ ] Nothing extra added (no scope creep)?

          OUTPUT: PASS or list of specific spec gaps to fix.
          """,
          toolsets=['file']
      )

      إذا وُجدت مشكلات في المواصفات: أصلح الفجوات، ثم أعد تشغيل مراجعة المواصفات. لا تكمل إلا عند الالتزام الكامل بالمواصفات.

      الخطوة 3: أرسل مراجع جودة الكود​

      بعد اجتياز مراجعة الالتزام بالمواصفات:

      delegate_task(
          goal="Review code quality for Task 1 implementation",
          context="""
          FILES TO REVIEW:
          - src/models/user.py
          - tests/models/test_user.py

          CHECK:
          - [ ] Follows project conventions and style?
          - [ ] Proper error handling?
          - [ ] Clear variable/function names?
          - [ ] Adequate test coverage?
          - [ ] No obvious bugs or missed edge cases?
          - [ ] No security issues?

          OUTPUT FORMAT:
          - Critical Issues: [must fix before proceeding]
          - Important Issues: [should fix]
          - Minor Issues: [optional]
          - Verdict: APPROVED or REQUEST_CHANGES
          """,
          toolsets=['file']
      )

      إذا وُجدت مشكلات في الجودة: أصلحها، ثم أعد المراجعة. لا تكمل إلا بعد الموافقة.

      الخطوة 4: علّم المهمة كمكتملة​

      todo([{"id": "task-1", "content": "Create User model with email field", "status": "completed"}], merge=True)

      3. المراجعة النهائية​

      بعد اكتمال كل المهام، أرسل مراجع تكامل نهائي:

      delegate_task(
          goal="Review the entire implementation for consistency and integration issues",
          context="""
          All tasks from the plan are complete. Review the full implementation:
          - Do all components work together?
          - Any inconsistencies between tasks?
          - All tests passing?
          - Ready for merge?
          """,
          toolsets=['terminal', 'file']
      )

      4. تحقّق ونفّذ commit​

      # Run full test suite
      pytest tests/ -q

      # Review all changes
      git diff --stat

      # Final commit if needed
      git add -A && git commit -m "feat: complete [feature name] implementation"

      حجم تفصيل المهام​

      كل مهمة = 2 إلى 5 دقائق من العمل المركّز.

      مهمة كبيرة جدًا:

      • "نفّذ نظام مصادقة المستخدمين"

      الحجم الصحيح:

      • "أنشئ نموذج User بحقلَي البريد الإلكتروني وكلمة المرور"
      • "أضف دالة تجزئة (hashing) لكلمة المرور"
      • "أنشئ نقطة نهاية (endpoint) لتسجيل الدخول"
      • "أضف توليد رمز JWT"
      • "أنشئ نقطة نهاية للتسجيل"

      إشارات تحذير — لا تفعل هذه أبدًا​

      • بدء التنفيذ دون خطة
      • تخطّي المراجعات (الالتزام بالمواصفات أو جودة الكود)
      • المتابعة مع وجود مشكلات حرجة/مهمة لم تُصلَح
      • إرسال عدة subagents تنفيذ لمهام تلمس نفس الملفات
      • جعل الـ subagent يقرأ ملف الخطة (قدّم النص الكامل ضمن السياق بدلًا من ذلك)
      • تخطّي سياق تمهيد المشهد (يحتاج الـ subagent إلى فهم موقع المهمة ضمن السياق العام)
      • تجاهل أسئلة الـ subagent (أجب قبل السماح لها بالمتابعة)
      • قبول "قريب بما يكفي" في الالتزام بالمواصفات
      • تخطّي حلقات المراجعة (المراجع يجد مشكلات ← المنفِّذ يصلحها ← مراجعة أخرى)
      • السماح للمراجعة الذاتية من المنفِّذ بأن تحل محل مراجعة فعلية (كلتاهما ضروريتان)
      • بدء مراجعة جودة الكود قبل أن تنجح مراجعة الالتزام بالمواصفات (ترتيب خاطئ)
      • الانتقال إلى المهمة التالية بينما لا تزال أي من المراجعتين تحتوي مشكلات مفتوحة

      التعامل مع المشكلات​

      إذا طرح الـ subagent أسئلة​

      • أجب بوضوح وبشكل كامل
      • قدّم سياقًا إضافيًا إذا لزم الأمر
      • لا تستعجله نحو التنفيذ

      إذا وجد المراجع مشكلات​

      • يصلحها subagent المنفِّذ (أو subagent جديد)
      • يراجع المراجع مرة أخرى
      • كرّر حتى الموافقة
      • لا تتخطَّ إعادة المراجعة

      إذا فشل الـ subagent في مهمة​

      • أرسل subagent إصلاح جديدًا بتعليمات محددة عمّا حدث من خلل
      • لا تحاول الإصلاح يدويًا في جلسة المتحكم (تلويث السياق)

      ملاحظات حول الكفاءة​

      لماذا subagent جديد لكل مهمة:

      • يمنع تلويث السياق الناتج عن حالة متراكمة
      • يحصل كل subagent على سياق نظيف ومركّز
      • لا التباس ناتج عن كود أو تفكير مهام سابقة

      لماذا المراجعة على مرحلتين:

      • مراجعة المواصفات تكتشف النقص أو الإفراط في البناء مبكرًا
      • مراجعة الجودة تضمن أن التنفيذ مبني جيدًا
      • تكتشف المشكلات قبل أن تتراكم عبر المهام

      مقايضة التكلفة:

      • استدعاءات subagent أكثر (منفِّذ + مراجعَين لكل مهمة)
      • لكنها تكتشف المشكلات مبكرًا (أرخص من تصحيح مشكلات متراكمة لاحقًا)

      التكامل مع مهارات أخرى​

      مع plan​

      تنفّذ هذه المهارة الخطط التي أنشأتها مهارة plan:

      1. متطلبات المستخدم ← plan ← خطة تنفيذ
      2. خطة التنفيذ ← subagent-driven-development ← كود يعمل

      مع test-driven-development​

      ينبغي أن تتّبع subagents المنفِّذة منهجية TDD:

      1. اكتب اختبارًا فاشلًا أولًا
      2. نفّذ الحد الأدنى من الكود
      3. تحقّق من نجاح الاختبار
      4. نفّذ commit

      أدرج تعليمات TDD في سياق كل subagent منفِّذ.

      مع requesting-code-review​

      عملية المراجعة على مرحلتين هي في حد ذاتها مراجعة الكود. لمراجعة التكامل النهائية، استخدم أبعاد المراجعة الخاصة بمهارة requesting-code-review.

      مع systematic-debugging​

      إذا واجه subagent أخطاء أثناء التنفيذ:

      1. اتّبع منهجية systematic-debugging
      2. حدّد السبب الجذري قبل الإصلاح
      3. اكتب اختبار انحدار (regression)
      4. استأنف التنفيذ

      مثال على سير العمل​

      [Read plan: docs/plans/auth-feature.md]
      [Create todo list with 5 tasks]

      --- Task 1: Create User model ---
      [Dispatch implementer subagent]
        Implementer: "Should email be unique?"
        You: "Yes, email must be unique"
        Implementer: Implemented, 3/3 tests passing, committed.

      [Dispatch spec reviewer]
        Spec reviewer: ✅ PASS — all requirements met

      [Dispatch quality reviewer]
        Quality reviewer: ✅ APPROVED — clean code, good tests

      [Mark Task 1 complete]

      --- Task 2: Password hashing ---
      [Dispatch implementer subagent]
        Implementer: No questions, implemented, 5/5 tests passing.

      [Dispatch spec reviewer]
        Spec reviewer: ❌ Missing: password strength validation (spec says "min 8 chars")

      [Implementer fixes]
        Implementer: Added validation, 7/7 tests passing.

      [Dispatch spec reviewer again]
        Spec reviewer: ✅ PASS

      [Dispatch quality reviewer]
        Quality reviewer: Important: Magic number 8, extract to constant
        Implementer: Extracted MIN_PASSWORD_LENGTH constant
        Quality reviewer: ✅ APPROVED

      [Mark Task 2 complete]

      ... (continue for all tasks)

      [After all tasks: dispatch final integration reviewer]
      [Run full test suite: all passing]
      [Done!]

      تذكّر​

      Fresh subagent per task
      Two-stage review every time
      Spec compliance FIRST
      Code quality SECOND
      Never skip reviews
      Catch issues early

      الجودة ليست صدفة. إنها نتيجة عملية منهجية.

      قراءات إضافية (حمّلها عند الحاجة)​

      عندما تستهلك عملية التنسيق سياقًا كبيرًا، أو تتطلّب حلقات مراجعة طويلة، أو نقاط تحقّق معقّدة، حمّل هذه المراجع للحصول على الانضباط المحدد:

      • references/context-budget-discipline.md — نموذج تدهور السياق ذو المستويات الأربعة (PEAK / GOOD / DEGRADING / POOR)، وقواعد عمق القراءة التي تتغيّر بحسب حجم نافذة السياق، وعلامات الإنذار المبكر للتدهور الصامت. حمّله عندما يستهلك التشغيل سياقًا كبيرًا بوضوح (خطط متعددة المراحل، subagents كثيرة، نواتج ضخمة).
      • references/gates-taxonomy.md — الأنواع الأربعة القياسية للبوابات (Pre-flight، Revision، Escalation، Abort) مع سلوكها وطريقة التعافي منها وأمثلة عليها. حمّله عند تصميم أو مراجعة أي سير عمل يحتوي نقاط تحقّق — استخدم المصطلحات صراحةً بحيث يكون لكل بوابة نقطة دخول وسلوك فشل وقواعد استئناف محدَّدة.

      Sketch

      نماذج HTML قابلة للاستهلاك: 2-3 صيغ تصميم للمقارنة.

      المرجع: ملف SKILL.md كاملًا​

      معلومة

      ما يلي هو التعريف الكامل للمهارة الذي يحمّله Hermes عند تفعيل هذه المهارة، وهو ما يراه الوكيل كتعليمات أثناء عمل المهارة.

      Sketch

      استخدم هذه المهارة عندما يريد المستخدم رؤية اتجاه تصميم قبل الالتزام به — باستكشاف فكرة UI/UX كنماذج HTML قابلة للاستهلاك. الهدف هو توليد 2-3 صيغ تفاعلية حتى يتمكّن المستخدم من مقارنة الاتجاهات البصرية جنبًا إلى جنب، لا إنتاج كود جاهز للتسليم.

      حمّل هذه المهارة عندما يقول المستخدم أشياء مثل "اعرض لي رسمًا تخطيطيًا لهذه الشاشة"، "أرِني كيف يمكن أن يبدو X"، "قارن التخطيط A مع B"، "أعطِني 2-3 صيغ لهذه الواجهة"، "دعني أرى بعض المتغيّرات"، "اصنع نموذجًا لهذا قبل أن أبنيه".

      متى لا تُستخدم​

      • يريد المستخدم مكوّنًا للإنتاج — استخدم claude-design أو ابنِه بشكل صحيح
      • يريد المستخدم قطعة HTML مصقولة لمرة واحدة (صفحة هبوط، عرض تقديمي) — claude-design
      • يريد المستخدم رسمًا بيانيًا — excalidraw، architecture-diagram
      • التصميم محسوم بالفعل — ابنِه فقط

      إذا كان لدى المستخدم نظام GSD الكامل مثبّتًا​

      إذا ظهرت gsd-sketch كمهارة شقيقة (مثبّتة عبر npx get-shit-done-cc --hermes)، يمكنك استخدام gsd-sketch لسير عمل أشمل: .planning/sketches/ دائمة مع MANIFEST، وتحليل frontier mode، وتدقيقات اتساق عبر الرسومات التخطيطية السابقة، وتكامل مع بقية GSD. هذه المهارة هي النسخة الخفيفة المستقلة — رسم تخطيطي لمرة واحدة بلا آلية الحالة.

      ملاحظة: مشروع GSD الأصلي (gsd-build/get-shit-done) مؤرشف / لم يعد يُصان على GitHub. لا تزال حزمة npm (get-shit-done-cc) تُثبَّت، لكن تعامل معها كمشروع مجتمعي مؤرشف — هذه المهارة المستقلة sketch هي المسار المُصان ولا تحتاج إلى أي شيء إضافي.

      الأسلوب الأساسي​

      intake  →  variants  →  head-to-head  →  pick winner (or iterate)

      1. الاستقبال (تخطَّه إذا كان المستخدم قد أعطاك ما يكفي بالفعل)​

      قبل توليد الصيغ، احصل على ثلاثة أشياء — سؤالًا واحدًا في كل مرة، لا كلها دفعة واحدة:

      1. الشعور. "كيف يجب أن يبدو شعور هذا؟ صفات، مشاعر، أجواء." — "هادئ، تحريري، مثل Linear" يخبرك أكثر من "بسيط".
      2. المراجع. "ما التطبيقات أو المواقع أو المنتجات التي تجسّد الشعور الذي تتخيّله؟" — المراجع الفعلية أفضل من الأوصاف المجرّدة.
      3. الفعل الأساسي. "ما أهم شيء واحد يفعله المستخدم على هذه الشاشة؟" — يجب أن تخدم كل الصيغ هذا الفعل جيدًا؛ وإلا فهي مجرّد زخرفة.

      لخّص كل إجابة بإيجاز قبل السؤال التالي. إذا أعطاك المستخدم الإجابات الثلاث مسبقًا، انتقل مباشرة إلى الصيغ.

      2. الصيغ (2-3، أبدًا 1، ونادرًا 4+)​

      أنتج 2-3 صيغ دفعة واحدة. كل صيغة ملف HTML كامل مستقل. لا تصف الصيغ — ابنِها. الهدف هو المقارنة.

      يجب أن تتبنّى كل صيغة موقفًا تصميميًا مختلفًا، لا قيم بكسل مختلفة. ثلاثة محاور صيغ جيدة:

      • الكثافة: مضغوط / فضفاض / كثيف للغاية (اختر قطبين متباينين)
      • التركيز: المحتوى أولًا / الفعل أولًا / الأداة أولًا
      • الجمالية: تحريري / وظيفي / مرح
      • التخطيط: عمود واحد / شريط جانبي / لوحة مقسومة
      • الأساس: قائم على البطاقات / محتوى عارٍ / بأسلوب المستند

      اختر محورًا واحدًا وابنِ عليه بوضوح. صيغتان تختلفان فقط في لون التمييز جهد مهدور — لا يستطيع المستخدم التمييز بينهما.

      تسمية الصيغ: صِف الموقف، لا الرقم.

      sketches/
      ├── 001-calm-editorial/
      │   ├── index.html
      │   └── README.md
      ├── 001-utilitarian-dense/
      │   ├── index.html
      │   └── README.md
      └── 001-playful-split/
          ├── index.html
          └── README.md

      3. اجعلها HTML حقيقية​

      كل صيغة ملف HTML واحد قائم بذاته:

      • <style> مضمّن — بلا خطوة بناء، بلا CSS خارجي
      • خطوط النظام أو خط Google واحد عبر <link>
      • Tailwind عبر شبكة توزيع CDN (<script src="https://cdn.tailwindcss.com"></script>) مقبول
      • محتوى وهمي واقعي — جمل فعلية، أسماء فعلية، لا "Lorem ipsum"
      • تفاعلي: روابط قابلة للنقر، تحويم حقيقي، تحوّل حالة واحد على الأقل (فتح/إغلاق، تصفية، تبديل). صورة ثابتة مجمّدة spike أسوأ من واحد متحرك ولو بشكل بسيط.

      افتحها في متصفح. إذا بدت معطوبة، أصلحها قبل عرضها على المستخدم.

      تحقّق من الصيغ بصريًا — استخدم أدوات المتصفح الخاصة بـ Hermes. لا تكتفِ بكتابة HTML والأمل بأن تُعرض بشكل صحيح؛ حمّل كل صيغة وانظر إليها:

      browser_navigate(url="file:///absolute/path/to/sketches/001-calm-editorial/index.html")
      browser_vision(question="Does this layout look clean and readable? Any visible bugs (overlapping text, unstyled elements, broken images)?")

      تُعيد browser_vision وصفًا بالذكاء الاصطناعي لما يظهر فعليًا على الصفحة إضافة إلى مسار لقطة شاشة — يكشف أخطاء تخطيط يفوتها فحص الكود المصدري وحده (مثل استيراد خط فشل بصمت، أو حاوية flex انهارت). أصلح وأعِد التصفّح حتى تبدو كل صيغة صحيحة.

      إعادة ضبط CSS افتراضية + مجموعة خطوط نظام لبدء سريع:

      <style>
        * { box-sizing: border-box; margin: 0; padding: 0; }
        body {
          font-family: -apple-system, BlinkMacSystemFont, "Segoe UI", Roboto,
                       "Helvetica Neue", Arial, sans-serif;
          -webkit-font-smoothing: antialiased;
          color: #1a1a1a;
          background: #fafafa;
          line-height: 1.5;
        }
      </style>

      4. ملف README لكل صيغة​

      يجيب ملف README.md الخاص بكل صيغة على:

      ## Variant: {stance name}

      ### Design stance
      One sentence on the principle driving this variant.

      ### Key choices
      - Layout: ...
      - Typography: ...
      - Color: ...
      - Interaction: ...

      ### Trade-offs
      - Strong at: ...
      - Weak at: ...

      ### Best for
      - The kind of user or use case this variant actually serves

      5. مواجهة مباشرة​

      بعد بناء كل الصيغ، اعرضها كمقارنة. لا تكتفِ بالسرد — أبدِ رأيًا:

      ## Three takes on the home screen

      | Dimension | Calm editorial | Utilitarian dense | Playful split |
      |-----------|----------------|-------------------|---------------|
      | Density   | Low            | High              | Medium        |
      | Primary action visibility | Low | High | Medium |
      | Scan-ability | High | Medium | Low |
      | Feel | Calm, trusted | Sharp, tool-like | Inviting, energetic |

      **My take:** Utilitarian dense for power users, calm editorial for content-forward audiences. Playful split is weakest — tries to do both and commits to neither.

      دع المستخدم يختار فائزًا، أو يدمج اثنتين في هجين، أو يطلب جولة أخرى.

      التنسيق البصري (عندما يكون للمشروع هوية بصرية)​

      إذا كان لدى المستخدم طابع بصري موجود (ألوان، خطوط، tokens)، ضع الـ tokens المشتركة في sketches/themes/tokens.css و@import ها في كل صيغة. أبقِ الـ tokens في حدّها الأدنى:

      /* sketches/themes/tokens.css */
      :root {
        --color-bg: #fafafa;
        --color-fg: #1a1a1a;
        --color-accent: #0066ff;
        --color-muted: #666;
        --radius: 8px;
        --font-display: "Inter", sans-serif;
        --font-body: -apple-system, BlinkMacSystemFont, sans-serif;
      }

      لا تُفرط في تكوين tokens لرسم تخطيطي قابل للاستهلاك — ثلاثة ألوان وخط واحد يكفيان عادة.

      حدّ التفاعلية​

      يكون الرسم التخطيطي تفاعليًا بما يكفي عندما يستطيع المستخدم:

      1. النقر على فعل أساسي ويحدث شيء مرئي (تغيّر حالة، نافذة منبثقة، إشعار toast، إيهام بالتنقّل)
      2. رؤية تحوّل حالة واحد ذي معنى (تصفية قائمة، تبديل وضع، فتح/إغلاق لوحة)
      3. التحويم على عناصر تفاعل قابلة للتمييز (أزرار، صفوف، تبويبات)

      أكثر من ذلك إفراط هندسي على شيء قابل للاستهلاك. أقل من ذلك مجرّد لقطة شاشة.

      Frontier mode (اختيار ما يُرسم تخطيطيًا تاليًا)​

      إذا كانت هناك رسومات تخطيطية موجودة بالفعل وسأل المستخدم "ماذا يجب أن أرسم تاليًا؟":

      • فجوات الاتساق — صيغتان فائزتان من رسومات تخطيطية مختلفة اتخذتا خيارات مستقلة لم تُركَّب معًا بعد
      • شاشات لم تُرسم تخطيطيًا — مذكورة لكن لم تُستكشف أبدًا
      • تغطية الحالات — تم رسم المسار السعيد تخطيطيًا، لكن ليس الفارغ / التحميل / الخطأ / 1000 عنصر
      • فجوات الاستجابة — تم التحقّق عند حجم شاشة واحد؛ هل يصمد على الجوّال / الشاشة الفائقة العرض؟
      • أنماط التفاعل — التخطيطات الثابتة موجودة؛ التحوّلات والسحب وسلوك التمرير غير موجودة

      اقترح 2-4 مرشحين مسمّين. دع المستخدم يختار.

      الناتج​

      • أنشئ sketches/ (أو .planning/sketches/ إذا كان المستخدم يستخدم اصطلاحات GSD) في جذر المستودع
      • مجلد فرعي واحد لكل صيغة: NNN-stance-name/index.html + README.md
      • أخبر المستخدم كيف يفتحها: open sketches/001-calm-editorial/index.html على macOS، وxdg-open على Linux، وstart على Windows
      • أبقِ الصيغ قابلة للاستهلاك — الرسم التخطيطي الذي شعرت بالحاجة إلى الحفاظ عليه يجب ترقيته إلى كود مشروع حقيقي، لا تنظيمه كأصل

      تسلسل أدوات نموذجي لصيغة واحدة:

      terminal("mkdir -p sketches/001-calm-editorial")
      write_file("sketches/001-calm-editorial/index.html", "<!doctype html>...")
      write_file("sketches/001-calm-editorial/README.md", "## Variant: Calm editorial\n...")
      browser_navigate(url="file://$(pwd)/sketches/001-calm-editorial/index.html")
      browser_vision(question="How does this look? Any obvious layout issues?")

      كرّر لكل صيغة، ثم اعرض جدول المقارنة.

      معلومة

      ما يلي هو التعريف الكامل للمهارة الذي يحمّله Hermes عند تفعيل هذه المهارة، وهو ما يراه الوكيل كتعليمات أثناء عمل المهارة.

      ذاكرة Honcho لـ Hermes

      يوفّر Honcho نمذجة مستخدم عابرة للجلسات وأصيلة الذكاء الاصطناعي (AI-native). فهو يتعلّم من هو المستخدم عبر المحادثات، ويمنح كل profile في Hermes هوية نظير (peer) خاصة به مع مشاركة رؤية موحّدة للمستخدم.

      متى تُستخدم​

      • إعداد Honcho (سحابي أو مستضاف ذاتيًا)
      • استكشاف أخطاء عدم عمل الذاكرة / عدم مزامنة النظراء (peers)
      • إنشاء إعدادات متعددة الـ profiles حيث يمتلك كل وكيل نظير Honcho خاصًا به
      • ضبط إعدادات الملاحظة (observation)، والاسترجاع، وعمق الجدل (dialectic)، أو تكرار الكتابة
      • فهم ما تفعله أدوات Honcho الخمس ومتى تُستخدم
      • ضبط ميزانيات السياق وحقن ملخص الجلسة

      الإعداد​

      سحابي (app.honcho.dev)​

      hermes memory setup honcho
      # select "cloud", paste API key from https://app.honcho.dev

      مستضاف ذاتيًا​

      hermes memory setup honcho
      # select "local", enter base URL (e.g. http://localhost:8000)

      راجع: https://docs.honcho.dev/v3/guides/integrations/hermes#running-honcho-locally-with-hermes

      تحقّق​

      hermes honcho status    # shows resolved config, connection test, peer info

      البنية المعمارية​

      حقن السياق الأساسي​

      عندما يحقن Honcho سياقًا في الـ system prompt (في وضعَي الاسترجاع hybrid أو context)، فإنه يجمّع كتلة السياق الأساسي بهذا الترتيب:

      1. ملخص الجلسة -- موجز قصير للجلسة الحالية حتى الآن (يوضع أولًا حتى يحصل النموذج على استمرارية محادثة فورية)
      2. تمثيل المستخدم -- نموذج Honcho المتراكم عن المستخدم (التفضيلات، الحقائق، الأنماط)
      3. بطاقة نظير الذكاء الاصطناعي (AI peer card) -- بطاقة هوية نظير الذكاء الاصطناعي لهذا الـ profile في Hermes

      يُولَّد ملخص الجلسة تلقائيًا بواسطة Honcho في بداية كل دور (عند وجود جلسة سابقة). فهو يمنح النموذج بداية دافئة (warm start) دون إعادة تشغيل السجل الكامل.

      اختيار الـ prompt البارد / الدافئ​

      يختار Honcho تلقائيًا بين استراتيجيتين للـ prompt:

      الحالةالاستراتيجيةما يحدث
      لا جلسة سابقة أو تمثيل فارغبداية باردة (Cold start)prompt تمهيدي خفيف؛ يتخطى حقن الملخص؛ يشجّع النموذج على التعرّف على المستخدم
      تمثيل موجود و/أو سجل جلسةبداية دافئة (Warm start)حقن كامل للسياق الأساسي (ملخص ← تمثيل ← بطاقة)؛ system prompt أغنى

      لست بحاجة لضبط هذا -- فهو تلقائي بناءً على حالة الجلسة.

      النظراء (Peers)​

      يُنمذج Honcho المحادثات كتفاعلات بين نظراء (peers). ينشئ Hermes نظيرين لكل جلسة:

      • نظير المستخدم (peerName): يمثّل الإنسان. يبني Honcho تمثيلًا للمستخدم من الرسائل المُلاحَظة.
      • نظير الذكاء الاصطناعي (aiPeer): يمثّل نسخة Hermes هذه. يحصل كل profile على نظير ذكاء اصطناعي خاص به بحيث تطوّر الوكلاء آراءً مستقلة.

      الملاحظة (Observation)​

      لكل نظير مفتاحا ملاحظة يتحكمان فيما يتعلّمه Honcho:

      المفتاحما يفعله
      observeMeتُلاحَظ رسائل النظير نفسه (يبني تمثيلًا ذاتيًا)
      observeOthersتُلاحَظ رسائل النظراء الآخرين (يبني فهمًا متبادلًا بين النظراء)

      الافتراضي: كل المفاتيح الأربعة مفعّلة (ملاحظة ثنائية الاتجاه كاملة).

      اضبطها لكل نظير في honcho.json:

      {
        "observation": {
          "user": { "observeMe": true, "observeOthers": true },
          "ai":   { "observeMe": true, "observeOthers": true }
        }
      }

      أو استخدم الإعدادات المختصرة الجاهزة (presets):

      الإعداد الجاهزالمستخدمالذكاء الاصطناعيحالة الاستخدام
      "directional" (الافتراضي)me:on, others:onme:on, others:onوكلاء متعددون، ذاكرة كاملة
      "unified"me:on, others:offme:off, others:onوكيل واحد، نمذجة المستخدم فقط

      الإعدادات المُغيَّرة في لوحة تحكم Honcho تُزامَن عند تهيئة الجلسة -- وتتغلّب إعدادات الخادم على الإعدادات الافتراضية المحلية.

      الجلسات​

      تحدّد جلسات Honcho نطاق وصول الرسائل والملاحظات. خيارات الاستراتيجية:

      الاستراتيجيةالسلوك
      per-directory (الافتراضي)جلسة واحدة لكل مجلد عمل
      per-repoجلسة واحدة لكل جذر مستودع git
      per-sessionجلسة Honcho جديدة لكل تشغيل Hermes
      globalجلسة واحدة عبر كل المجلدات

      تجاوز يدوي: hermes honcho map my-project-name

      أوضاع الاسترجاع (Recall)​

      كيف يصل الوكيل إلى ذاكرة Honcho:

      الوضعحقن سياق تلقائي؟أدوات متاحة؟حالة الاستخدام
      hybrid (الافتراضي)نعمنعميقرّر الوكيل متى يستخدم الأدوات مقابل السياق التلقائي
      contextنعملا (مخفية)أقل تكلفة token، بلا استدعاءات أدوات
      toolsلانعميتحكم الوكيل صراحة في كل وصول إلى الذاكرة

      ثلاثة مقابض مستقلة​

      يُتحكَّم في سلوك الجدل (dialectic) في Honcho عبر ثلاثة أبعاد مستقلة. يمكن ضبط كل منها دون التأثير على الآخرَين:

      الوتيرة (متى)​

      تتحكم في عدد مرات حدوث استدعاءات الجدل والسياق.

      المفتاحالافتراضيالوصف
      contextCadence1الحد الأدنى من الأدوار بين استدعاءات API للسياق
      dialecticCadence2الحد الأدنى من الأدوار بين استدعاءات API للجدل. يُنصح بـ 1–5
      injectionFrequencyevery-turnevery-turn أو first-turn لحقن السياق الأساسي

      القيم الأعلى للوتيرة تُشغّل نموذج الجدل بشكل أقل تكرارًا. dialecticCadence: 2 تعني أن المحرك يعمل كل دور آخر. ضبطها على 1 يُشغّله كل دور.

      العمق (كم مرة)​

      يتحكم في عدد جولات استدلال الجدل التي ينفّذها Honcho لكل استعلام.

      المفتاحالافتراضيالمدىالوصف
      dialecticDepth11-3عدد جولات استدلال الجدل لكل استعلام
      dialecticDepthLevels--مصفوفةتجاوزات مستوى اختيارية لكل جولة عمق (انظر أدناه)

      dialecticDepth: 2 تعني أن Honcho يشغّل جولتين من التوليف الجدلي. تنتج الجولة الأولى إجابة أولية؛ وتُنقّحها الثانية.

      تتيح لك dialecticDepthLevels ضبط مستوى الاستدلال لكل جولة على حدة:

      {
        "dialecticDepth": 3,
        "dialecticDepthLevels": ["low", "medium", "high"]
      }

      إذا حُذفت dialecticDepthLevels، تستخدم الجولات مستويات تناسبية مشتقة من dialecticReasoningLevel (الأساس):

      العمقمستويات التمرير
      1[base]
      2[minimal, base]
      3[minimal, base, low]

      يُبقي هذا التمريرات الأولى رخيصة مع استخدام العمق الكامل في التوليف النهائي.

      العمق عند بدء الجلسة. يشغّل التسخين المسبق (prewarm) عند بدء الجلسة العمق الكامل المضبوط في dialecticDepth في الخلفية قبل الدور الأول. غالبًا ما يعيد التسخين المسبق أحادي التمرير على نظير بارد مخرجات ضحلة — بينما يشغّل العمق متعدد التمريرات دورة التدقيق/التوفيق قبل أن يتحدث المستخدم أصلًا. يستهلك الدور الأول نتيجة التسخين المسبق مباشرة؛ وإذا لم يكتمل التسخين المسبق في الوقت، يعود الدور الأول إلى استدعاء متزامن بمهلة محدودة.

      المستوى (كم القوة)​

      يتحكم في شدّة كل جولة استدلال جدلي.

      المفتاحالافتراضيالوصف
      dialecticReasoningLevellowminimal، low، medium، high، max
      dialecticDynamictrueعندما تكون true، يمكن للنموذج تمرير reasoning_level إلى honcho_reasoning لتجاوز الافتراضي لكل استدعاء. false = استخدام dialecticReasoningLevel دائمًا، وتُتجاهل تجاوزات النموذج

      المستويات الأعلى تنتج توليفًا أغنى لكن بتكلفة token أعلى على خادم Honcho.

      إعداد متعدد الـ Profiles​

      يحصل كل profile في Hermes على نظير ذكاء اصطناعي خاص به في Honcho مع مشاركة نفس مساحة العمل (سياق المستخدم). وهذا يعني:

      • كل الـ profiles ترى نفس تمثيل المستخدم
      • يبني كل profile هويته وملاحظاته الخاصة بالذكاء الاصطناعي
      • الاستنتاجات المكتوبة من قِبل profile واحد مرئية للآخرين عبر مساحة العمل المشتركة

      إنشاء profile بنظير Honcho​

      hermes profile create coder --clone
      # creates host block hermes.coder, AI peer "coder", inherits config from default

      ما تفعله --clone بالنسبة لـ Honcho:

      1. تنشئ كتلة مضيف hermes.coder في honcho.json
      2. تضبط aiPeer: "coder" (اسم الـ profile)
      3. ترث workspace، وpeerName، وwriteFrequency، وrecallMode، وغيرها من الافتراضي
      4. تُنشئ النظير في Honcho مسبقًا حتى يكون موجودًا قبل أول رسالة

      تعبئة الـ profiles الموجودة بأثر رجعي​

      hermes honcho sync    # creates host blocks for all profiles that don't have one yet

      إعدادات لكل profile​

      تجاوز أي إعداد في كتلة المضيف:

      {
        "hosts": {
          "hermes.coder": {
            "aiPeer": "coder",
            "recallMode": "tools",
            "dialecticDepth": 2,
            "observation": {
              "user": { "observeMe": true, "observeOthers": false },
              "ai": { "observeMe": true, "observeOthers": true }
            }
          }
        }
      }

      الأدوات​

      يملك الوكيل 5 أدوات Honcho ثنائية الاتجاه (مخفية في وضع الاسترجاع context):

      الأداةاستدعاء LLM؟التكلفةتُستخدم عندما
      honcho_profileلاضئيلةلقطة سريعة وواقعية في بداية المحادثة أو لبحث سريع عن الاسم/الدور/التفضيل
      honcho_searchلامنخفضةجلب حقائق سابقة محددة لتحلّلها بنفسك — مقتطفات خام، بلا توليف
      honcho_contextلامنخفضةلقطة كاملة لسياق الجلسة: الملخص، التمثيل، البطاقة، الرسائل الأخيرة
      honcho_reasoningنعممتوسطة–عاليةسؤال بلغة طبيعية يوليفه محرك الجدل في Honcho
      honcho_concludeلاضئيلةكتابة أو حذف حقيقة دائمة؛ مرّر peer: "ai" لمعرفة الذكاء الاصطناعي بنفسه

      honcho_profile​

      قراءة أو تحديث بطاقة نظير — حقائق أساسية منسّقة (الاسم، الدور، التفضيلات، أسلوب التواصل). مرّر card: [...] للتحديث؛ اترك المعامل فارغًا للقراءة. بلا استدعاء LLM.

      honcho_search​

      بحث دلالي عبر السياق المخزَّن لنظير محدد. يُعيد مقتطفات خام مرتّبة حسب الصلة، بلا توليف. الافتراضي 800 token، والحد الأقصى 2000. مفيد عندما تحتاج حقائق سابقة محددة لتحلّلها بنفسك بدلًا من إجابة مُوَلَّفة.

      honcho_context​

      لقطة كاملة لسياق الجلسة من Honcho — ملخص الجلسة، وتمثيل النظير، وبطاقة النظير، والرسائل الأخيرة. بلا استدعاء LLM. استخدمها عندما تريد رؤية كل ما يعرفه Honcho عن الجلسة والنظير الحاليين دفعة واحدة.

      honcho_reasoning​

      سؤال بلغة طبيعية يجيب عنه محرك الاستدلال الجدلي في Honcho (استدعاء LLM على خادم Honcho). تكلفة أعلى وجودة أعلى. مرّر reasoning_level للتحكم في العمق: minimal (سريع/رخيص) ← low ← medium ← high ← max (شامل). اتركه فارغًا لاستخدام الافتراضي المضبوط (low). استخدمها لفهم مُوَلَّف لأنماط المستخدم أو أهدافه أو حالته الحالية.

      honcho_conclude​

      كتابة أو حذف استنتاج دائم عن نظير. مرّر conclusion: "..." للإنشاء. مرّر delete_id: "..." لإزالة استنتاج (لإزالة معلومات تعريف شخصية (PII) — يُصحّح Honcho الاستنتاجات الخاطئة ذاتيًا بمرور الوقت، لذا لا يلزم الحذف إلا للـ PII). يجب أن تمرّر واحدًا فقط من الاثنين بالضبط.

      استهداف النظراء ثنائي الاتجاه​

      تقبل كل الأدوات الخمس معامل peer اختياريًا:

      • peer: "user" (الافتراضي) — يعمل على نظير المستخدم
      • peer: "ai" — يعمل على نظير الذكاء الاصطناعي لهذا الـ profile
      • peer: "<explicit-id>" — أي معرّف نظير في مساحة العمل

      أمثلة:

      honcho_profile                        # read user's card
      honcho_profile peer="ai"              # read AI peer's card
      honcho_reasoning query="What does this user care about most?"
      honcho_reasoning query="What are my interaction patterns?" peer="ai" reasoning_level="medium"
      honcho_conclude conclusion="Prefers terse answers"
      honcho_conclude conclusion="I tend to over-explain code" peer="ai"
      honcho_conclude delete_id="abc123"    # PII removal

      أنماط استخدام الوكيل​

      إرشادات لـ Hermes عندما تكون ذاكرة Honcho مفعّلة.

      عند بدء المحادثة​

      1. honcho_profile                  → fast warmup, no LLM cost
      2. If context looks thin → honcho_context  (full snapshot, still no LLM)
      3. If deep synthesis needed → honcho_reasoning  (LLM call, use sparingly)

      لا تستدعِ honcho_reasoning في كل دور. فالحقن التلقائي يتكفّل بالفعل بتحديث السياق الجاري. استخدم أداة الاستدلال فقط عندما تحتاج فعليًا رؤية مُوَلَّفة لا يوفّرها السياق الأساسي.

      عندما يشارك المستخدم شيئًا يجب تذكّره​

      honcho_conclude conclusion="<specific, actionable fact>"

      استنتاجات جيدة: "يفضّل أمثلة الكود على الشروحات النثرية"، "يعمل على مشروع Rust غير متزامن حتى أبريل 2026" استنتاجات سيئة: "قال المستخدم شيئًا عن Rust" (غامض جدًا)، "يبدو المستخدم تقنيًا" (موجود بالفعل في التمثيل)

      عندما يسأل المستخدم عن سياق سابق / تحتاج إلى تذكّر تفاصيل محددة​

      honcho_search query="<topic>"       → fast, no LLM, good for specific facts
      honcho_context                       → full snapshot with summary + messages
      honcho_reasoning query="<question>"  → synthesized answer, use when search isn't enough

      متى تستخدم peer: "ai"​

      استخدم استهداف نظير الذكاء الاصطناعي لبناء معرفة الوكيل بنفسه واستعلامها:

      • honcho_conclude conclusion="I tend to be verbose when explaining architecture" peer="ai" — تصحيح ذاتي
      • honcho_reasoning query="How do I typically handle ambiguous requests?" peer="ai" — تدقيق ذاتي
      • honcho_profile peer="ai" — مراجعة بطاقة هويته الخاصة

      متى لا تستدعي الأدوات​

      في وضعَي hybrid وcontext، يُحقَن السياق الأساسي (تمثيل المستخدم + البطاقة + ملخص الجلسة) تلقائيًا قبل كل دور. لا تُعِد جلب ما تم حقنه بالفعل. استدعِ الأدوات فقط عندما:

      • تحتاج شيئًا لا يحتويه السياق المُحقَن
      • يطلب منك المستخدم صراحة استرجاع الذاكرة أو التحقق منها
      • تكتب استنتاجًا عن شيء جديد

      الوعي بالوتيرة​

      تشترك honcho_reasoning على جانب الأدوات في نفس تكلفة الجدل التلقائي عبر الحقن. بعد استدعاء أداة صريح، تُعاد ضبط وتيرة الحقن التلقائي -- لتجنّب احتساب التكلفة مرتين في نفس الدور.

      مرجع الإعدادات​

      ملف الإعدادات: $HERMES_HOME/honcho.json (محلي للـ profile) أو ~/.honcho/config.json (عام).

      الإعدادات الرئيسية​

      المفتاحالافتراضيالوصف
      apiKey--مفتاح API (احصل على واحد)
      baseUrl--عنوان URL الأساسي لـ Honcho المستضاف ذاتيًا
      peerName--هوية نظير المستخدم
      aiPeerمفتاح المضيفهوية نظير الذكاء الاصطناعي
      workspaceمفتاح المضيفمعرّف مساحة العمل المشتركة
      recallModehybridhybrid، أو context، أو tools
      observationالكل مفعّلقيم منطقية observeMe/observeOthers لكل نظير
      writeFrequencyasyncasync، أو turn، أو session، أو عدد صحيح N
      sessionStrategyper-directoryper-directory، per-repo، per-session، global
      messageMaxChars25000الحد الأقصى للأحرف لكل رسالة (تُقسَّم إذا تجاوزت الحد)

      إعدادات الجدل (Dialectic)​

      المفتاحالافتراضيالوصف
      dialecticReasoningLevellowminimal، low، medium، high، max
      dialecticDynamictrueرفع مستوى الاستدلال تلقائيًا بحسب تعقيد الاستعلام. false = مستوى ثابت
      dialecticDepth1عدد جولات الجدل لكل استعلام (1-3)
      dialecticDepthLevels--مصفوفة اختيارية للمستويات لكل جولة، مثل ["low", "high"]
      dialecticMaxInputChars10000الحد الأقصى للأحرف لمدخل استعلام الجدل

      ميزانية السياق والحقن​

      المفتاحالافتراضيالوصف
      contextTokensغير محدودالحد الأقصى لـ token لحقن السياق الأساسي المُجمَّع (الملخص + التمثيل + البطاقة). حد اختياري — اتركه فارغًا ليبقى غير محدود، أو اضبطه على عدد صحيح لتحديد حجم الحقن.
      injectionFrequencyevery-turnevery-turn أو first-turn
      contextCadence1الحد الأدنى من الأدوار بين استدعاءات API للسياق
      dialecticCadence2الحد الأدنى من الأدوار بين استدعاءات LLM للجدل (يُنصح بـ 1–5)

      تُفرَض ميزانية contextTokens عند وقت الحقن. إذا تجاوز مجموع ملخص الجلسة + التمثيل + البطاقة الميزانية، يقلّص Honcho الملخص أولًا، ثم التمثيل، مع الحفاظ على البطاقة. هذا يمنع تضخم السياق في الجلسات الطويلة.

      تعقيم سياق الذاكرة​

      يعقّم Honcho كتلة memory-context قبل الحقن لمنع حقن الأوامر (prompt injection) والمحتوى المشوَّه:

      • يزيل علامات XML/HTML من الاستنتاجات التي كتبها المستخدم
      • يوحّد المسافات البيضاء وأحرف التحكم
      • يقتطع الاستنتاجات الفردية التي تتجاوز messageMaxChars
      • يهرب تسلسلات الفواصل التي قد تُخلّ ببنية الـ system prompt

      يعالج هذا الإصلاح حالات حدّية حيث يمكن لاستنتاجات المستخدم الخام التي تحتوي على ترميز أو أحرف خاصة أن تُفسد كتلة السياق المحقونة.

      استكشاف الأخطاء وإصلاحها​

      "Honcho not configured"​

      نفّذ hermes honcho setup. تأكد من وجود memory.provider: honcho في ~/.hermes/config.yaml.

      الذاكرة لا تستمر عبر الجلسات​

      تحقّق من hermes honcho status -- تأكد من أن saveMessages: true وأن writeFrequency ليست session (التي تكتب فقط عند الخروج).

      الـ profile لا يحصل على نظير خاص به​

      استخدم --clone عند الإنشاء: hermes profile create <name> --clone. للـ profiles الموجودة: hermes honcho sync.

      تغييرات الملاحظة في لوحة التحكم لا تنعكس​

      تُزامَن إعدادات الملاحظة من الخادم عند كل تهيئة جلسة. ابدأ جلسة جديدة بعد تغيير الإعدادات في واجهة Honcho.

      اقتطاع الرسائل​

      الرسائل التي تتجاوز messageMaxChars (الافتراضي 25 ألفًا) تُقسَّم تلقائيًا بعلامات [continued]. إذا كنت تواجه هذا كثيرًا، تحقق مما إذا كانت نتائج الأدوات أو محتوى المهارات يُضخّم حجم الرسالة.

      حقن السياق كبير جدًا​

      إذا رأيت تحذيرات حول تجاوز ميزانية السياق، خفّض contextTokens أو قلّل dialecticDepth. يُقلَّص ملخص الجلسة أولًا عندما تكون الميزانية ضيقة.

      ملخص الجلسة مفقود​

      يتطلب ملخص الجلسة دورًا سابقًا واحدًا على الأقل في جلسة Honcho الحالية. عند البدء البارد (جلسة جديدة، بلا سجل)، يُحذف الملخص ويستخدم Honcho استراتيجية prompt البداية الباردة بدلًا منه.

      Hermes Agent Skill Authoring

      تأليف ملفات SKILL.md داخل المستودع: الترويسة والبنية.

      بيانات المهارة الوصفية​

      المصدرمضمّنة (مثبّتة افتراضيًا)
      المسارskills/software-development/hermes-agent-skill-authoring
      الإصدار2.0.0
      المؤلفHermes Agent
      الترخيصMIT
      المنصاتlinux, macos, windows
      الوسومskills, authoring, hermes-agent, conventions, skill-md
      مهارات ذات صلةrequesting-code-review

      المرجع: ملف SKILL.md كاملًا​

      معلومة

      ما يلي هو التعريف الكامل للمهارة الذي يحمّله Hermes عند تفعيل هذه المهارة، وهو ما يراه الوكيل كتعليمات أثناء عمل المهارة.

      تأليف مهارات Hermes-Agent (داخل المستودع)

      نظرة عامة​

      يوجد مكانان يمكن أن يعيش فيهما ملف SKILL.md:

      1. محلي للمستخدم: ~/.hermes/skills/<maybe-category>/<name>/SKILL.md — شخصي، غير مُشارَك. يُنشأ عبر skill_manage(action='create').
      2. داخل المستودع (هذه المهارة عن هذه الحالة): skills/<category>/<name>/SKILL.md أو optional-skills/<category>/<name>/SKILL.md داخل مستودع hermes-agent — مُلتزَم به (committed)، يُشحَن مع الحزمة. استخدم write_file + git add. لا يستهدف skill_manage(action='create') هذه الشجرة.

      يجب أن تلبّي المهارات داخل المستودع معايير التأليف الصارمة (hardline) الخاصة بالمستودع (راجع AGENTS.md، قسم "Skill authoring standards (HARDLINE)" — هذا القسم هو مصدر الحقيقة؛ هذه المهارة هي الشرح التنفيذي). يرفض المراجعون طلبات الدمج (PRs) التي تخالفها، فتحقيقها من البداية أرخص من عملية إصلاح لاحقة.

      متى تُستخدم​

      • يطلب المستخدم منك إضافة مهارة "في هذا الفرع / المستودع / الالتزام (commit)"
      • أنت تُلزِم (commit) سير عمل قابلًا لإعادة الاستخدام ينبغي أن يُشحَن مع hermes-agent
      • أنت تحرّر مهارة موجودة تحت skills/ أو optional-skills/ (استخدم patch للتعديلات الصغيرة، وwrite_file لإعادة الكتابة؛ لا يزال skill_manage يعمل مع patch للمهارات داخل المستودع، لكن ليس مع create)
      • لا تستخدمها لـ: المهارات الشخصية في ~/.hermes/skills/ (استخدم skill_manage فقط)

      حدّد المستوى أولًا: مضمّنة أم اختيارية​

      • مضمّنة (skills/<category>/) — سلوك يومي، مفيد على نطاق واسع لأنواع مستخدمين كثيرة، أثر خفيف. المعيار الصارم: يمكنك القول "سيُحمِّل مستخدم هذه المهارة في 5+ جلسات شهريًا" دون مبالغة.
      • اختيارية (optional-skills/<category>/) — متخصّصة، خاصة بقطاع (blockchain، الألعاب، التمويل، تطبيق واحد)، مهارات مهمة/وظيفة متكررة، أو أي شيء ثقيل. تُثبَّت عبر hermes skills install official/<category>/<skill>.

      عند الشك، اجعلها اختيارية. الترقية لاحقًا سهلة؛ التخفيض عبء إضافي. "ستكون مفيدة لأي شخص قد يحتاجها يومًا" حجة لمستوى الاختيارية، لا للمضمّن.

      اختر الفئة حسب طبيعة الأداة، لا حسب الشعور بها (أداة CLI لوكيل ذكاء اصطناعي تذهب إلى autonomous-ai-agents/ حتى لو "شعرت أنها إنتاجية"). أكّد الفئات الموجودة بـ search_files(pattern='*', target='files', path='skills') ولا تخترع فئات عليا جديدة بشكل عرضي.

      لا مهارات موجِّهة / فهرسية / محورية. المهارة التي يكون محتواها الأساسي جدول توجيه يشير إلى مهارات شقيقة تضيف خطوة تحويل زائدة وتكرّر عوامل When to Use الخاصة بالمهارات الشقيقة نفسها. إذا كانت المهارة ستصبح فارغة بدون إشارات "حمّل المهارة X بدلًا من ذلك"، لا تكتبها — الكتالوج وعوامل تحفيز كل مهارة شقيقة يقومان بتلك المهمة بالفعل.

      الترويسة المطلوبة​

      مصدر الحقيقة للمُدقِّق: tools/skill_manager_tool.py::_validate_frontmatter. متطلبات المُدقِّق الصارمة:

      • تبدأ بـ --- كأول بايتات (بلا سطر فارغ في المقدّمة).
      • تُغلَق بـ \n---\n قبل المتن.
      • تُحلَّل كخريطة YAML.
      • حقل name موجود.
      • حقل description موجود (سقف المُدقِّق 1024 حرفًا — لكن راجع المعيار الصارم في المستودع أدناه، وهو أكثر صرامة بكثير).
      • متن غير فارغ بعد --- الختامية.

      الشكل القياسي في المستودع (كل الحقول متوقّعة، حتى حيث لا يفرضها المُدقِّق):

      ---
      name: my-skill-name               # lowercase, hyphens, ≤64 chars (MAX_NAME_LENGTH)
      description: Concise capability statement, under sixty chars.
      version: 0.1.0                    # semver; new skills start at 0.1.0
      author: Real Name (github-handle), Hermes Agent
      license: MIT
      platforms: [linux, macos, windows]   # audit, don't guess — see Platform Gating
      metadata:
        hermes:
          tags: [Short, Descriptive, Tags]
          related_skills: [other-in-repo-skill]
      ---

      قواعد description (صارمة (HARDLINE) — سقف المُدقِّق 1024 ليس هو المعيار)​

      • ≤ 60 حرفًا. جملة واحدة. تنتهي بنقطة.
      • اذكر القدرة، لا آلية التنفيذ، ولا تكرّر اسم المهارة.
      • بلا كلمات تسويقية ("powerful"، "comprehensive"، "seamless"، "advanced").
      • يقطع فهرس المهارات في system prompt عند 57 حرفًا + "..." — يجب أن يكون المحفّز/القدرة مكتملًا ذاتيًا ضمن تلك النافذة.
      • إذا احتوى الوصف على :، ضعه بين علامتي اقتباس مزدوجتين أو ستُفسّره YAML كخريطة وسينهار مُولِّد الوثائق. علامات الاقتباس لا تُحسَب ضمن الـ60.

      جيد: Track named companies for material news with cited digests. سيّئ: Use when a user asks to monitor named competitors or companies for product launches, pricing changes, funding, ... (240 حرفًا — رُفض في المراجعة)

      قواعد author​

      • اذكر الإنسان أولًا، ثم "Hermes Agent" كمتعاون ثانوي: Ben Barclay (benbarclay), Hermes Agent.
      • لا تكتب أبدًا author: Hermes Agent منفردًا للمهارات المُساهَم بها — انسب الفضل إلى الإنسان، لا إلى الأداة، حتى (خصوصًا) عندما يكتب وكيل ذكاء اصطناعي النص.
      • المهارات التي كتبها القائمون على الصيانة: Teknium (teknium1), Hermes Agent.

      قواعد related_skills​

      • يجب أن يشير كل مُدخل إلى مهارة داخل المستودع موجودة فعليًا في حالة الشجرة نفسها التي عليها طلب الدمج (PR) الخاص بك. لا تُشِر إلى مهارات كانت مخطَّطًا لها فقط، أو موجودة في PR آخر، أو موجودة فقط في ~/.hermes/skills/.
      • تحقّق من كل مُدخل: search_files(pattern='<name>', target='files', path='skills') (وoptional-skills/).

      تحديد المنصات: دقّق، لا تثِق​

      platforms: تُقيّد التحميل حسب نظام التشغيل المُستضيف. اضبطها بناءً على ما يستدعيه نص المهارة وسكربتاتها فعليًا:

      المهارة تستخدم فقط…platforms:
      أدوات Hermes + مكتبة Python القياسية + واجهات CLI عابرة للمنصات[linux, macos, windows]
      أنابيب bash، سلاسل grep/awk/sed، heredocs[linux, macos]
      osascript, defaults, pmset[macos]
      apt/systemctl//proc[linux]

      إشارات خاصة بـ POSIX يجب البحث عنها في scripts/: fcntl, termios, pty, os.fork, os.killpg, signal.SIGKILL, فحوصات os.kill(pid, 0) للتحقّق من الحياة، مسارات مُثبَّتة مباشرة مثل /tmp /proc /etc. الوضع الافتراضي: أصلح أولًا للعمل عبر المنصات (tempfile.gettempdir(), pathlib.Path, psutil.pid_exists)؛ حدّد النطاق تضييقًا فقط عندما تكون التبعية مرتبطة حقًا بمنصة معيّنة، واذكر السبب في ## Pitfalls.

      حدود الحجم​

      • ملف SKILL.md كاملًا: ≤ 100,000 حرف مفروضة (MAX_SKILL_CONTENT_CHARS)، لكن الهدف ~100 سطر لمهارة بسيطة، ~200 لمهارة معقّدة. المهارات النظيرة تقع بين 8-14 ألف حرف.
      • المواد الضخمة أو الخاصة بفرع معيّن تذهب إلى references/*.md، أو templates/، أو scripts/ — تُشار إليها من SKILL.md، لا مُضمَّنة فيه.
      • لا تتوقّع من النموذج كتابة محلّلات (parsers) أو منطق غير تافه بشكل مضمّن في كل استدعاء — اشحن سكربتًا مساعدًا في scripts/ وأشِر إليه بمساره.

      بنية المتن (الترتيب الحديث للأقسام)​

      # <Skill> Skill
      2-3 sentence intro: what it does, what it doesn't do, dependency stance.

      ## When to Use          — bulleted triggers (+ "Don't use for:" counter-triggers)
      ## Prerequisites        — exact env vars, installs, API key sourcing
      ## How to Run           — canonical invocation through the `terminal` tool
      ## Quick Reference      — flat command list, no narration
      ## Procedure            — numbered steps, each with a checkable completion criterion
      ## Pitfalls             — known limits, things that look broken but aren't
      ## Verification         — how to prove the skill worked

      لا ينطبق كل قسم على كل مهارة (فمهارة إجرائية بحتة قد لا تحتوي على مرجع سريع)، لكن When to Use + متن قابل للتنفيذ + Pitfalls + Verification هي الحد الأدنى. احذف المقدّمات التسويقية، وعناصر "Setup Check" التي لا تفعل شيئًا، وإعادة شرح متغيّرات البيئة الموجودة سلفًا في Prerequisites.

      أشِر إلى أدوات Hermes، لا إلى shell الخام​

      عندما تحتاج المهارة إلى قدرة، اذكر أداة Hermes الصحيحة بين علامتي backtick: terminal, read_file, write_file, patch, search_files, web_search, web_extract, browser_navigate, vision_analyze, delegate_task, cronjob. لا تُسمِّ أدوات shell التي يمتلك الوكيل غلافًا لها بالفعل (grep ← search_files، cat ← read_file، sed/awk ← patch، find/ls ← search_files target='files'). ينبغي لمهارة الغلاف على CLI أن تصيغ الاستدعاءات كـ terminal(command="<tool> ...", timeout=...) — نص shell الخام ("نفّذ foo --version") هو مخالفة توقف المراجعة. إذا اعتمدت المهارة على خادم MCP، اذكره ووثّق الإعداد في Prerequisites.

      لا تستخدم أبدًا مسارات محلية بجهاز محدّد​

      اكتب مسارات نسبية للمستودع (skills/..., tools/skill_manager_tool.py). مسار /home/<you>/... مُضمَّن في مهارة مُلتزَم بها يُعطِّل عمل كل مستخدم آخر وهو علامة مراجعة فورية.

      مبادئ جودة الكتابة​

      تُوجَد المهارة لجعل عملية الوكيل أكثر قابلية للتوقّع — يتبع الوكيل باستمرار الانضباط المفيد نفسه.

      1. حسِّن من أجل قابلية توقّع العملية. إذا لم يغيّر سطر ما السلوك، احذفه.
      2. اختر حِمل السياق الصحيح. يُدفَع ثمن الوصف في كل دور (turn)؛ التفاصيل تذهب إلى المتن أو المراجع المرتبطة.
      3. اختم الخطوات بمعايير اكتمال. قابلة للتحقّق، وشاملة عند الأهمية: "كل ملف مُعدَّل مُحاسَب عليه" أفضل من "لخّص التغييرات."
      4. ضع القواعد قرب المفهوم الذي تحكمه.
      5. استخدم كلمات افتتاحية قوية ("حلقة ضيقة (tight loop)"، "السبب الجذري (root cause)"، "اختبار انحدار (regression test)") بدلًا من شروح مطوّلة مكرَّرة.
      6. شذّب التكرار والعناصر التي لا تفعل شيئًا. "كن حذرًا" و"استخدم أفضل الممارسات" لا تغيّران سلوك النموذج — استبدلهما بمعيار قابل للتحقّق أو احذفهما.

      الاختبارات والوثائق (مطلوبة للمهارات داخل المستودع)​

      1. الاختبارات تعيش في tests/skills/test_<skill>_skill.py — المكتبة القياسية + pytest + unittest.mock فقط، بلا شبكة فعلية. شغّلها عبر scripts/run_tests.sh tests/skills/test_<skill>_skill.py -q. (نجاح tests/tools/test_skill_manager_tool.py العام لا يبرهن شيئًا عن مهارتك.)
      2. إعادة توليد الوثائق: شغّل python website/scripts/generate-skill-docs.py، ثم طبّق انضباط النطاق — يُعيد المولِّد كتابة كل صفحة مُولَّدة تلقائيًا. نفّذ git checkout -- على كل ما ليس ملكك؛ يجب أن يُظهر الفرق النهائي فقط SKILL.md الخاص بك، وصفحة وثائقك الفردية، وصف كتالوج واحد، وإدراج سطر واحد في website/sidebars.ts (تحقّق بـ search_files(pattern='<your-slug>', path='website/sidebars.ts') — نتيجة واحدة بالضبط، أو الصفحة يتيمة).
      3. .env.example (فقط إذا احتاجت المهارة متغيرات بيئة جديدة): كتلة واحدة مُحدَّدة بوضوح بتعليق؛ لا تلمس أي شيء آخر في الملف.

      سير العمل​

      1. استطلع النظراء في الفئة المستهدفة بـ search_files(target='files') واقرأ 2-3 ملفات SKILL.md نظيرة لمطابقة النغمة والبنية. يُفضَّل توسيع مهارة موجودة على إنشاء شقيقة ضيّقة.
      2. حدّد المستوى والفئة (راجع أعلاه). عند الشك، اجعلها اختيارية — واسأل قبل الدفع بدلًا من الافتراض.
      3. أنشئ المسودة بـ write_file إلى skills/<category>/<name>/SKILL.md (أو optional-skills/...).
      4. تحقّق محليًا: 
        import yaml, re, pathlib
        content = pathlib.Path("skills/<category>/<name>/SKILL.md").read_text()
        assert content.startswith("---")
        m = re.search(r'\n---\s*\n', content[3:])
        fm = yaml.safe_load(content[3:m.start()+3])
        assert "name" in fm and "description" in fm
        assert len(fm["description"]) <= 60, f"description {len(fm['description'])} chars — hardline is 60"
        assert fm["description"].endswith(".")
        assert "platforms" in fm
        assert len(content) <= 100_000
        تحقّق أيضًا أن كل مُدخل related_skills موجود داخل المستودع.
      5. أضف اختبارات وأعد توليد الوثائق (القسم السابق).
      6. نفّذ git add + commit على الفرع النشط؛ افتح طلب دمج (PR).
      7. ملاحظة: مُحمِّل المهارات للجلسة الحالية مُخزَّن مؤقتًا — لن يرى skill_view / skills_list المهارة الجديدة حتى جلسة جديدة. هذا متوقّع، لا خطأ.

      تحرير المهارات الموجودة داخل المستودع​

      • تصحيح صغير: skill_manage(action='patch', ...) يعمل على المهارات داخل المستودع، وكذلك patch.
      • إعادة كتابة كبرى: استخدم write_file لكتابة SKILL.md كاملًا.
      • الملفات الداعمة: استخدم write_file إلى references/، أو templates/، أو scripts/ تحت مجلد المهارة.
      • التزم (commit) دائمًا — المهارات داخل المستودع مصدر، لا حالة تشغيل. أعد تشغيل مولِّد الوثائق عند تغيّر الترويسة.

      المزالق الشائعة​

      1. استخدام skill_manage(action='create') لمهارة داخل المستودع. فهو يكتب إلى ~/.hermes/skills/، لا شجرة المستودع. استخدم write_file.
      2. الثقة بحدود المُدقِّق كالمعيار. يسمح المُدقِّق بأوصاف 1024 حرفًا، لكن المراجعة ترفض أي شيء يتجاوز 60. لا يفحص المُدقِّق platforms:، أو صيغة المؤلف، أو الاختبارات، أو الوثائق — المراجعة تفعل.
      3. author: Hermes Agent على مهارة مُساهَم بها. انسب الفضل إلى الإنسان أولًا.
      4. مسافة بياض قبل ---. يفشل التحقّق مع أي سطر فارغ في المقدّمة أو BOM.
      5. وصف عام جدًا أو محفّز مدفون بعد الحرف 57.
      6. related_skills يشير إلى مهارات غير موجودة داخل المستودع (محلية للمستخدم، مخطَّط لها، أو في PR شقيق).
      7. تكرار مهارة نظيرة. استطلع الفئة أولًا؛ وسِّع بدلًا من إضافة شقيقة.
      8. تخطّي مولِّد الوثائق أو دفع انحرافه غير المرتبط. كلا الاتجاهين خاطئ: بلا إعادة توليد = مهارة يتيمة بلا صفحة وثائق؛ إعادة توليد عمياء = فرق مُنتفِخ مليء بانحراف مهارات أخرى.
      9. توقّع أن ترى الجلسة الحالية المهارة الجديدة. المُحمِّل يُهيَّأ عند بدء الجلسة.
      10. السماح بتراكم الترسبات في المهارات. عند إضافة قاعدة، أزل الصياغة القديمة التي تحل محلها.

      قائمة التحقّق​

      • تحديد المستوى عمدًا (المعيار للمضمّنة: 5+ جلسات/شهر؛ وإلا optional-skills/)
      • الملف في skills/<category>/<name>/SKILL.md أو optional-skills/<category>/<name>/SKILL.md
      • الترويسة تبدأ من البايت 0 بـ ---، وتُغلَق بـ \n---\n
      • name, description, version, author, license, platforms, metadata.hermes.{tags, related_skills} كلها موجودة
      • الوصف ≤ 60 حرفًا، جملة واحدة، ينتهي بنقطة، بلا كلمات تسويقية
      • author ينسب الفضل إلى المساهم الإنسان أولًا
      • platforms: مُدقَّقة مقابل النص/السكربتات الفعلية، لا منسوخة من مهارة شقيقة
      • كل مُدخل في related_skills موجود داخل المستودع
      • يتبع المتن ترتيب الأقسام الحديث؛ الأوامر مصاغة عبر أدوات Hermes
      • لا مسارات محلية بجهاز محدّد في أي مكان في الملف
      • كل خطوة مُرقَّمة تحمل معيار اكتمال قابلًا للتحقّق
      • الاختبارات في tests/skills/test_<skill>_skill.py تنجح تحت scripts/run_tests.sh
      • إعادة توليد الوثائق بانضباط النطاق؛ الشريط الجانبي يحمل مُدخلًا واحدًا بالضبط للـ slug
      • git add + commit على الفرع المقصود؛ طلب دمج (PR) مفتوح

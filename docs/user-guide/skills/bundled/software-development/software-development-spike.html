      Spike

      تجارب قابلة للتخلص منها للتحقق من فكرة قبل البناء.

      معلومة

      ما يلي هو التعريف الكامل للمهارة الذي يحمّله Hermes عند تفعيل هذه المهارة، وهو ما يراه الوكيل كتعليمات أثناء عمل المهارة.

      Spike

      استخدم هذه المهارة حين يريد المستخدم استشعار فكرة قبل الالتزام ببناء حقيقي — للتحقق من الجدوى، أو مقارنة الأساليب، أو إظهار المجاهيل التي لن يجيب عنها أي قدر من البحث النظري. الـ spikes قابلة للتخلص منها بالتصميم. تخلَّص منها بمجرد أن تسدّد دَينها.

      حمِّل هذه المهارة حين يقول المستخدم أشياء مثل "let me try this"، أو "I want to see if X works"، أو "spike this out"، أو "before I commit to Y"، أو "quick prototype of Z"، أو "is this even possible?"، أو "compare A vs B".

      متى لا تُستخدم هذه المهارة​

      • الإجابة معروفة من الوثائق أو من قراءة الكود — فقط ابحث، لا تبنِ
      • العمل ضمن مسار الإنتاج — استخدم مهارة plan بدلًا من ذلك
      • الفكرة تحققت صحتها بالفعل — انتقل مباشرة إلى التنفيذ

      إذا كان لدى المستخدم نظام GSD الكامل مثبّتًا​

      إذا ظهرت gsd-spike كمهارة مجاورة (مثبَّتة عبر npx get-shit-done-cc --hermes)، فضّل gsd-spike حين يريد المستخدم سير عمل GSD الكامل: حالة دائمة في .planning/spikes/، وتتبع MANIFEST عبر الجلسات، وصيغة حكم Given/When/Then، وأنماط commit تتكامل مع بقية GSD. هذه المهارة هي النسخة الخفيفة المستقلة لمن لا يملك النظام الكامل (أو لا يريده).

      المنهج الأساسي​

      بصرف النظر عن الحجم، تتبع كل spike هذه الحلقة:

      decompose  →  research  →  build  →  verdict
         ↑__________________________________________↓
                        iterate on findings

      1. التفكيك (Decompose)​

      فكِّك فكرة المستخدم إلى 2 إلى 5 أسئلة جدوى مستقلة. كل سؤال هو spike واحد. اعرضها في جدول بصيغة Given/When/Then:

      #Spikeيتحقق من (Given/When/Then)المخاطرة
      001websocket-streamingGiven a WS connection, when LLM streams tokens, then client receives chunks < 100msعالية
      002apdf-parse-pdfjsGiven a multi-page PDF, when parsed with pdfjs, then structured text is extractableمتوسطة
      002bpdf-parse-camelotGiven a multi-page PDF, when parsed with camelot, then structured text is extractableمتوسطة

      أنواع الـ spikes:

      • standard — أسلوب واحد يجيب عن سؤال واحد
      • comparison — نفس السؤال، أساليب مختلفة (رقم مشترك، بلاحقة حرف a/b/c)

      أسئلة spike جيدة: جدوى محددة بمخرَج قابل للملاحظة. أسئلة spike سيئة: واسعة جدًا، بلا مخرَج قابل للملاحظة، أو مجرد "اقرأ الوثائق عن X".

      رتّب حسب المخاطرة. الـ spike الأكثر احتمالًا لإسقاط الفكرة يُشغَّل أولًا. لا فائدة من بناء نماذج أولية للأجزاء السهلة إذا لم يعمل الجزء الصعب.

      تخطَّ التفكيك فقط إذا كان المستخدم يعرف بالفعل بالضبط ما يريد اختباره عبر spike وذكر ذلك صراحة. عندها اعتبر فكرته spike واحدًا.

      2. المواءمة (للأفكار متعددة الـ spikes)​

      اعرض جدول الـ spikes. اسأل: "أبني الكل بهذا الترتيب، أم تريد تعديله؟" دع المستخدم يُسقط بندًا أو يعيد ترتيبه أو يعيد صياغته قبل أن تكتب أي كود.

      3. البحث (لكل spike، قبل البناء)​

      الـ spikes ليست خالية من البحث — تبحث بما يكفي لاختيار الأسلوب الصحيح، ثم تبني. لكل spike:

      1. وجِّزه. جملتان إلى ثلاث: ما هذا الـ spike، ولمَ يهم، وأبرز مخاطره.

      2. أظهر الأساليب المتنافسة إن وُجد خيار حقيقي:

        الأسلوبالأداة/المكتبةالإيجابياتالسلبياتالحالة
        ............maintained / abandoned / beta

      3. اختر واحدًا. اذكر السبب. إذا كان اثنان أو أكثر معقولَين، ابنِ متغيّرات سريعة داخل الـ spike نفسه.

      4. تخطَّ البحث للمنطق الصرف الذي لا يعتمد على تبعيات خارجية.

      استخدم أدوات Hermes لخطوة البحث:

      • web_search("python websocket streaming libraries 2025") — للعثور على مرشحين
      • web_extract(urls=["https://websockets.readthedocs.io/..."]) — لقراءة الوثائق الفعلية (تُعيد markdown)
      • terminal("pip show websockets | grep Version") — للتحقق مما هو مثبَّت في venv الخاص بالمشروع

      بالنسبة إلى المكتبات التي لا تملك صفحات وثائق، استنسخها (clone) واقرأ ملف README.md/مجلد examples/ عبر read_file. يُعد Context7 MCP (إن كان مُعدًّا لدى المستخدم) مصدرًا جيدًا أيضًا — mcp_*_resolve-library-id ثم mcp_*_query-docs.

      4. البناء​

      مجلد واحد لكل spike. أبقه مستقلًا بذاته.

      spikes/
      ├── 001-websocket-streaming/
      │   ├── README.md
      │   └── main.py
      ├── 002a-pdf-parse-pdfjs/
      │   ├── README.md
      │   └── parse.js
      └── 002b-pdf-parse-camelot/
          ├── README.md
          └── parse.py

      مِل نحو شيء يمكن للمستخدم التفاعل معه. تفشل الـ spikes حين يكون المخرَج الوحيد سطر سجل يقول "إنها تعمل". يريد المستخدم أن يشعر بأن الـ spike يعمل. الخيارات الافتراضية، بترتيب الأفضلية:

      1. واجهة CLI قابلة للتشغيل تأخذ مُدخلًا وتطبع مخرَجًا قابلًا للملاحظة
      2. صفحة HTML مصغّرة تُظهر السلوك
      3. خادم ويب صغير بنقطة نهاية (endpoint) واحدة
      4. اختبار وحدة (unit test) يُشغِّل السؤال بتأكيدات (assertions) قابلة للتمييز

      العمق أهم من السرعة. لا تعلن أبدًا "إنها تعمل" بعد تشغيل واحد ناجح (happy path). اختبر الحالات الحدّية. تتبّع النتائج المفاجئة. لا يكون الحكم موثوقًا إلا حين يكون التحقيق أمينًا.

      تجنّب ما لم يتطلبه الـ spike تحديدًا: إدارة حزم معقدة، أدوات بناء (build tools)/bundlers، Docker، ملفات بيئة، أنظمة إعدادات. رمِّز كل شيء مباشرة (hardcode) — فهو spike.

      بناء spike واحد — تسلسل أدوات نموذجي:

      terminal("mkdir -p spikes/001-websocket-streaming")
      write_file("spikes/001-websocket-streaming/README.md", "# 001: websocket-streaming\n\n...")
      write_file("spikes/001-websocket-streaming/main.py", "...")
      terminal("cd spikes/001-websocket-streaming && python main.py")
      # Observe output, iterate.

      spikes مقارنة متوازية (002a / 002b) — فوِّض المهمة. حين يمكن تشغيل أسلوبين بالتوازي ويتطلب كلاهما هندسة حقيقية (لا نماذج أولية من 10 أسطر)، تفرَّع باستخدام delegate_task:

      delegate_task(tasks=[
          {"goal": "Build 002a-pdf-parse-pdfjs: ...", "toolsets": ["terminal", "file", "web"]},
          {"goal": "Build 002b-pdf-parse-camelot: ...", "toolsets": ["terminal", "file", "web"]},
      ])

      يعيد كل subagent حكمه الخاص؛ وأنت تكتب المقارنة المباشرة (head-to-head) بينهما.

      5. الحكم (Verdict)​

      يختتم ملف README.md لكل spike بما يلي:

      ## Verdict: VALIDATED | PARTIAL | INVALIDATED

      ### What worked
      - ...

      ### What didn't
      - ...

      ### Surprises
      - ...

      ### Recommendation for the real build
      - ...

      VALIDATED = تمت الإجابة عن السؤال الأساسي بنعم، مع أدلة. PARTIAL = يعمل ضمن قيود X وY وZ — وثِّقها. INVALIDATED = لا يعمل، لهذا السبب. هذا spike ناجح رغم ذلك.

      Spikes المقارنة​

      حين يجيب أسلوبان عن نفس السؤال (002a / 002b)، ابنِهما الواحد تلو الآخر، ثم أجرِ مقارنة مباشرة بينهما في النهاية:

      ## Head-to-head: pdfjs vs camelot

      | Dimension | pdfjs (002a) | camelot (002b) |
      |-----------|--------------|----------------|
      | Extraction quality | 9/10 structured | 7/10 table-only |
      | Setup complexity | npm install, 1 line | pip + ghostscript |
      | Perf on 100-page PDF | 3s | 18s |
      | Handles rotated text | no | yes |

      **Winner:** pdfjs for our use case. Camelot if we need table-first extraction later.

      وضع الحدود القصوى (Frontier mode) (اختيار ما يُختبر تاليًا)​

      إذا كانت هناك spikes موجودة بالفعل وسأل المستخدم "ما الذي يجب أن أختبره تاليًا؟"، تصفّح المجلدات القائمة وابحث عن:

      • مخاطر التكامل — spike محقَّقان يمسّان نفس المورد لكن اختُبرا بشكل مستقل
      • تسليم البيانات (Data handoffs) — افتُرض أن مخرَج spike A متوافق مع مُدخَل spike B؛ لم يُثبَت ذلك قط
      • ثغرات في الرؤية — قدرات مُفترَضة لكن غير مُثبَتة
      • أساليب بديلة — زوايا مختلفة لـ spikes بحالة PARTIAL أو INVALIDATED

      اقترح 2 إلى 4 مرشحين بصيغة Given/When/Then. دع المستخدم يختار.

      المخرَجات​

      • أنشئ spikes/ (أو .planning/spikes/ إذا كان المستخدم يتبع اصطلاحات GSD) في جذر المستودع
      • مجلد واحد لكل spike: NNN-descriptive-name/
      • ملف README.md لكل spike يوثّق السؤال والأسلوب والنتائج والحكم
      • أبقِ الكود قابلًا للتخلص منه — فـ spike يستغرق يومين لـ"تنظيفه ليصلح للإنتاج" كان spike سيئًا

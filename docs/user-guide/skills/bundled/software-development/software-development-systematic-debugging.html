      التصحيح المنهجي (Systematic Debugging)

      تصحيح جذر المشكلة على 4 مراحل: افهم الأخطاء قبل إصلاحها.

      بيانات المهارة الوصفية​

      المصدرمضمّنة (مثبّتة افتراضيًا)
      المسارskills/software-development/systematic-debugging
      الإصدار1.1.0
      المؤلفHermes Agent (مُقتبَسة من obra/superpowers)
      الترخيصMIT
      المنصاتlinux, macos, windows
      الوسومdebugging, troubleshooting, problem-solving, root-cause, investigation
      مهارات ذات صلةtest-driven-development, subagent-driven-development

      المرجع: ملف SKILL.md كاملًا​

      معلومة

      ما يلي هو التعريف الكامل للمهارة الذي يحمّله Hermes عند تفعيل هذه المهارة، وهو ما يراه الوكيل كتعليمات أثناء عمل المهارة.

      التصحيح المنهجي

      نظرة عامة​

      الإصلاحات العشوائية تهدر الوقت وتخلق أخطاءً جديدة. الترقيعات السريعة تُخفي المشكلات الكامنة.

      المبدأ الأساسي: ابحث دائمًا عن السبب الجذري قبل محاولة الإصلاح. إصلاح الأعراض فشل.

      مخالفة نص هذه العملية هو مخالفة لروح التصحيح.

      القانون الحديدي​

      NO FIXES WITHOUT ROOT CAUSE INVESTIGATION FIRST

      إن لم تُكمل المرحلة 1، لا يمكنك اقتراح إصلاحات.

      قاعدة حلقة التغذية الراجعة​

      حلقة التغذية الراجعة هي عمل التصحيح نفسه. قبل قراءة الكود لبناء نظرية، أنشئ أو حدّد أمرًا محكمًا (tight) يمكنه إظهار فشل (أحمر) عند العَرَض الدقيق الذي يواجهه المستخدم ونجاح (أخضر) عند إصلاح الخطأ. الحلقة المحكمة سريعة، حتمية (deterministic)، قابلة للتشغيل من قبل الوكيل، ودقيقة بما يكفي لالتقاط هذا الخطأ بعينه — لا مجرد «لا يتعطّل».

      عندما يكون إعادة الإنتاج النظيف صعبًا، اصرف جهدًا غير متناسب في بناء الحلقة. التخمين دون حلقة قادرة على الفشل (red-capable) هو نمط الفشل الذي وُجدت هذه المهارة لمنعه.

      متى تستخدمها​

      استخدمها لأي مشكلة تقنية:

      • فشل الاختبارات
      • أخطاء في الإنتاج
      • سلوك غير متوقع
      • مشكلات الأداء
      • فشل البناء (build)
      • مشكلات التكامل

      استخدمها خصوصًا عندما:

      • تحت ضغط الوقت (الطوارئ تجعل التخمين مغريًا)
      • يبدو «إصلاح سريع واحد فقط» واضحًا
      • جرّبت بالفعل إصلاحات متعددة
      • الإصلاح السابق لم ينجح
      • لا تفهم المشكلة فهمًا كاملًا

      لا تتخطَّها عندما:

      • تبدو المشكلة بسيطة (للأخطاء البسيطة أسباب جذرية أيضًا)
      • أنت في عجلة من أمرك (الاستعجال يضمن إعادة العمل)
      • يريد أحدهم إصلاحها الآن (المنهجية أسرع من التخبّط)

      المراحل الأربع​

      يجب عليك إكمال كل مرحلة قبل الانتقال إلى التالية.

      المرحلة 1: التحقيق في السبب الجذري​

      قبل محاولة أي إصلاح:

      1. اقرأ رسائل الخطأ بعناية​

      • لا تتجاوز الأخطاء أو التحذيرات
      • غالبًا ما تحتوي على الحل بالضبط
      • اقرأ تتبّعات المكدس (stack traces) كاملة
      • دوّن أرقام الأسطر، مسارات الملفات، رموز الأخطاء

      الإجراء: استخدم read_file على ملفات المصدر ذات الصلة. استخدم search_files للعثور على نص الخطأ في قاعدة الكود.

      2. ابنِ حلقة تغذية راجعة محكمة​

      • هل يمكنك إطلاق العَرَض الدقيق الذي يواجهه المستخدم بأمر واحد؟
      • هل يفشل الأمر بسبب هذا الخطأ فقط وينجح فقط بعد إصلاحه؟
      • هل هو سريع بما يكفي للتشغيل المتكرر؟
      • هل هو حتمي؟ بالنسبة للأخطاء المتقطعة (flaky)، هل يمكنك رفع معدل إعادة الإنتاج بما يكفي للتصحيح؟
      • إذا تعذّر إعادة الإنتاج ← اجمع مزيدًا من البيانات، لا تخمّن.

      طرق بناء الحلقة — جرّبها تقريبًا بهذا الترتيب:

      1. اختبار فاشل عند نقطة الوصل (seam) التي تصل إلى الخطأ: وحدة، تكامل، أو من طرف إلى طرف.
      2. سكربت HTTP / curl ضد خادم تطوير قيد التشغيل.
      3. استدعاء CLI بمدخل تجهيزي (fixture)، مع مقارنة (diff) stdout/stderr بالمخرجات المتوقعة.
      4. سكربت متصفح بلا واجهة (headless) (Playwright/Puppeteer) يتحقق من الـ DOM أو الـ console أو الشبكة.
      5. إعادة تشغيل تتبّع مُلتقط (trace): HAR، أو حمولة طلب، أو سجل أحداث، أو رسالة طابور، أو محتوى webhook.
      6. هيكل اختبار مؤقت (throwaway harness) يشغّل أصغر شريحة مفيدة من النظام ويستدعي المسار الفاشل.
      7. حلقة خصائص / fuzz عندما يكون الخطأ خرجًا خاطئًا متقطعًا عبر مساحة إدخال واسعة.
      8. هيكل تجزئة (bisection) مناسب لـ git bisect run عندما ظهر الخطأ بين حالتين معروفتين.
      9. حلقة تفاضلية (differential) تقارن الإصدار القديم بالجديد، أو إعدادين، أو مزوّدين، أو مجموعتَي بيانات.
      10. سكربت بمشاركة إنسان (human-in-the-loop) كملاذ أخير فقط: اكتب خطوات الإنسان كسكربت والتقط نتيجتها لتبقى الحلقة منظّمة.

      أحكِم الحلقة بعد وجودها:

      • اجعلها أسرع: خزّن الإعداد مؤقتًا، ضيّق النطاق، تخطَّ التهيئة غير ذات الصلة.
      • اجعل الإشارة أوضح: تحقّق من العَرَض بدقة، لا من نجاح عام.
      • اجعلها أكثر حتمية: ثبّت الوقت، ابذر العشوائية، اعزل نظام الملفات، جمّد الشبكة.

      بالنسبة للأخطاء غير الحتمية، الهدف الفوري هو رفع معدل إعادة الإنتاج، لا الكمال. شغّل المُطلِق (trigger) 100 مرة، وزِّعه بالتوازي، أضف ضغطًا (stress)، ضيّق نوافذ التوقيت، أو حقن فترات انتظار (sleeps). التقطّع بنسبة 50% قابل للتصحيح؛ أما 1% فعادة لا.

      الإجراء: استخدم أداة terminal لتشغيل الحلقة المحكمة:

      # Run a specific failing test
      pytest tests/test_module.py::test_name -v

      # Or run a scripted repro
      python scripts/repro_bug.py

      # Or run a high-repetition flaky repro
      for i in {1..100}; do pytest tests/test_flake.py::test_name -q || break; done

      3. تحقّق من التغييرات الأخيرة​

      • ما الذي تغيّر وقد يسبب هذا؟
      • diff في git، الالتزامات (commits) الأخيرة
      • اعتماديات جديدة، تغييرات في الإعدادات

      الإجراء:

      # Recent commits
      git log --oneline -10

      # Uncommitted changes
      git diff

      # Changes in specific file
      git log -p --follow src/problematic_file.py | head -100

      4. اجمع الأدلة في الأنظمة متعددة المكوّنات​

      عندما يحتوي النظام على مكوّنات متعددة (API ← خدمة ← قاعدة بيانات، CI ← بناء ← نشر):

      قبل اقتراح الإصلاحات، أضف أدوات تشخيص (instrumentation):

      عند كل حدود مكوّن:

      • سجّل البيانات الداخلة إلى المكوّن
      • سجّل البيانات الخارجة من المكوّن
      • تحقّق من انتشار البيئة/الإعدادات
      • تحقّق من الحالة عند كل طبقة

      شغّله مرة واحدة لجمع أدلة تُظهر أين يحدث العطل. ثم حلّل الأدلة لتحديد المكوّن الفاشل. ثم حقّق في ذلك المكوّن تحديدًا.

      5. تتبّع تدفّق البيانات​

      عندما يكون الخطأ عميقًا في مكدس الاستدعاءات:

      • من أين تنشأ القيمة الخاطئة؟
      • ما الذي استدعى هذه الدالة بالقيمة الخاطئة؟
      • واصل التتبّع صعودًا (upstream) حتى تجد المصدر
      • أصلح عند المصدر، لا عند العَرَض

      الإجراء: استخدم search_files لتتبّع المراجع:

      # Find where the function is called
      search_files("function_name(", path="src/", file_glob="*.py")

      # Find where the variable is set
      search_files("variable_name\\s*=", path="src/", file_glob="*.py")

      قائمة تحقّق إتمام المرحلة 1​

      • قُرئت رسائل الخطأ وفُهمت بالكامل
      • أمر حلقة محكمة موجود وشُغّل مرة واحدة على الأقل
      • الحلقة قادرة على الفشل (red-capable): تتحقق من العَرَض الدقيق للمستخدم، لا من فشل قريب منه
      • الحلقة حتمية، أو أن الخطأ المتقطع له معدل إعادة إنتاج مرتفع بما يكفي للتصحيح
      • جرى تحديد التغييرات الأخيرة ومراجعتها
      • جُمعت الأدلة (السجلات، الحالة، تدفّق البيانات)
      • عُزلت المشكلة إلى مكوّن/كود محدد
      • يمكن صياغة فرضيات السبب الجذري واختبارها

      توقّف: لا تنتقل إلى المرحلة 2 حتى تفهم لماذا يحدث ذلك.

      المرحلة 2: تحليل النمط​

      اعثر على النمط قبل الإصلاح:

      0. اختزل إعادة الإنتاج إلى الحد الأدنى​

      بمجرد أن تصبح الحلقة حمراء، اختزل إعادة الإنتاج إلى أصغر سيناريو يظل يفشل. احذف المدخلات والمستدعين والإعدادات والبيانات والخطوات واحدة تلو الأخرى، مع إعادة تشغيل الحلقة بعد كل حذف. أبقِ فقط ما هو ضروري لحدوث الفشل.

      انتهيت عندما تجعل إزالة أي عنصر متبقٍّ الحلقة تصبح خضراء. إعادة الإنتاج المختزلة تضيّق مساحة الفرضيات وغالبًا ما تصبح أنظف اختبار تراجع (regression).

      1. اعثر على أمثلة عاملة​

      • حدّد موضع كود مشابه يعمل في قاعدة الكود نفسها
      • ما الذي يعمل ويشبه ما هو معطوب؟

      الإجراء: استخدم search_files للعثور على أنماط مماثلة:

      search_files("similar_pattern", path="src/", file_glob="*.py")

      2. قارن مع المراجع​

      • إذا كنت تنفّذ نمطًا، اقرأ التنفيذ المرجعي كاملًا
      • لا تتصفّح سريعًا — اقرأ كل سطر
      • افهم النمط بالكامل قبل تطبيقه

      3. حدّد الاختلافات​

      • ما الفرق بين ما يعمل وما هو معطوب؟
      • سجّل كل اختلاف، مهما كان صغيرًا
      • لا تفترض أن «هذا لا يمكن أن يهم»

      4. افهم الاعتماديات​

      • ما المكوّنات الأخرى التي يحتاجها هذا؟
      • ما الإعدادات، الضبط، البيئة؟
      • ما الافتراضات التي يقوم عليها؟

      المرحلة 3: الفرضية والاختبار​

      المنهج العلمي:

      1. صُغ فرضيات قابلة للدحض ومرتّبة​

      • ولّد 3 إلى 5 فرضيات معقولة قبل اختبار أي واحدة منها.
      • رتّبها حسب احتمالها وسهولة دحضها.
      • حدّد التوقّع الذي تصنعه كل فرضية: «إذا كان X هو السبب، فإن تغيير أو مراقبة Y يجب أن يجعل Z يحدث».
      • استبعد أو نقّح أي فرضية لا تصنع توقّعًا قابلًا للاختبار.

      إذا كان المستخدم حاضرًا، اعرض القائمة المرتّبة قبل الاختبار. قد تكون لديه معرفة بالمجال تعيد ترتيبها فورًا. إذا كان المستخدم غائبًا، امضِ وفق ترتيبك.

      2. اختبر بأقل قدر ممكن​

      • اختبر الفرضية الأعلى ترتيبًا بأصغر فحص ممكن.
      • غيّر متغيرًا واحدًا في كل مرة.
      • لا تصلح عدة أشياء دفعة واحدة.
      • فضّل فحص المصحّح/REPL عند توفره؛ نقطة توقف واحدة أفضل من عشرة سجلات.
      • إذا أضفت سجلات، ضع لكل سطر مؤقت بادئة فريدة مثل [DEBUG-a4f2] بحيث يصبح التنظيف بحثًا واحدًا.

      3. تحقّق قبل المتابعة​

      • هل نجح؟ ← المرحلة 4
      • لم ينجح؟ ← صُغ فرضية جديدة
      • لا تضِف إصلاحات أخرى فوقها

      4. عندما لا تعرف​

      • قل «لا أفهم X»
      • لا تتظاهر بالمعرفة
      • اطلب المساعدة من المستخدم
      • ابحث أكثر

      المرحلة 4: التنفيذ​

      أصلح السبب الجذري، لا العَرَض:

      1. أنشئ حالة اختبار فاشلة​

      • أبسط إعادة إنتاج ممكنة
      • اختبار آلي إن أمكن
      • يجب أن يكون موجودًا قبل الإصلاح
      • استخدم مهارة test-driven-development

      2. نفّذ إصلاحًا واحدًا​

      • عالج السبب الجذري المحدَّد
      • تغيير واحد في كل مرة
      • لا تحسينات «طالما أنا هنا»
      • لا إعادة هيكلة مرفَقة

      3. تحقّق من الإصلاح​

      # Run the specific regression test
      pytest tests/test_module.py::test_regression -v

      # Run full suite — no regressions
      pytest tests/ -q

      4. إن لم ينجح الإصلاح — قاعدة الثلاث​

      • توقّف.
      • عُدّ: كم إصلاحًا جرّبت؟
      • إن كان العدد أقل من 3: عُد إلى المرحلة 1، أعد التحليل بمعلومات جديدة
      • إن كان العدد 3 أو أكثر: توقّف وشكّك في البنية المعمارية (الخطوة 5 أدناه)
      • لا تحاول الإصلاح رقم 4 دون نقاش معماري

      5. إذا فشلت 3 إصلاحات أو أكثر: شكّك في البنية المعمارية​

      نمط يشير إلى مشكلة معمارية:

      • كل إصلاح يكشف حالة مشتركة/ترابطًا (coupling) جديدًا في مكان مختلف
      • الإصلاحات تتطلب «إعادة هيكلة ضخمة» لتنفيذها
      • كل إصلاح يخلق أعراضًا جديدة في مكان آخر

      توقّف وشكّك في الأساسيات:

      • هل هذا النمط سليم من حيث الأساس؟
      • هل «نتمسك به بمجرد القصور الذاتي»؟
      • هل ينبغي إعادة هيكلة البنية المعمارية بدلًا من الاستمرار في إصلاح الأعراض؟

      ناقش الأمر مع المستخدم قبل محاولة مزيد من الإصلاحات.

      هذه ليست فرضية فاشلة — هذه بنية معمارية خاطئة.

      إشارات تحذير — توقّف واتّبع العملية​

      إذا وجدت نفسك تفكّر:

      • «إصلاح سريع الآن، سأحقّق لاحقًا»
      • «جرّب فقط تغيير X وانظر إن نجح»
      • «أضف عدة تغييرات، شغّل الاختبارات»
      • «تخطَّ الاختبار، سأتحقّق يدويًا»
      • «على الأرجح أنه X، دعني أصلح ذلك»
      • «لا أفهم تمامًا لكن قد ينجح هذا»
      • «يقول النمط X لكنني سأكيّفه بشكل مختلف»
      • «إليك المشكلات الرئيسية: [قائمة إصلاحات دون تحقيق]»
      • اقتراح حلول قبل تتبّع تدفّق البيانات
      • «محاولة إصلاح أخرى» (بعد محاولتين أو أكثر)
      • كل إصلاح يكشف مشكلة جديدة في مكان مختلف

      كل ما سبق يعني: توقّف. عُد إلى المرحلة 1.

      إذا فشلت 3 إصلاحات أو أكثر: شكّك في البنية المعمارية (المرحلة 4 الخطوة 5).

      تبريرات شائعة​

      العذرالواقع
      «المشكلة بسيطة، لا حاجة للعملية»للمشكلات البسيطة أسباب جذرية أيضًا. العملية سريعة للأخطاء البسيطة.
      «طارئ، لا وقت للعملية»التصحيح المنهجي أسرع من التخبّط بالتخمين والتحقق.
      «جرّب هذا أولًا، ثم حقّق»الإصلاح الأول يحدّد النمط. افعله بشكل صحيح منذ البداية.
      «سأكتب الاختبار بعد التأكد من نجاح الإصلاح»الإصلاحات غير المختبرة لا تدوم. الاختبار أولًا يثبت ذلك.
      «عدة إصلاحات دفعة واحدة توفّر الوقت»لا يمكن عزل ما نجح. يسبب أخطاء جديدة.
      «المرجع طويل جدًا، سأكيّف النمط»الفهم الجزئي يضمن الأخطاء. اقرأه بالكامل.
      «أرى المشكلة، دعني أصلحها»رؤية الأعراض لا تعني فهم السبب الجذري.
      «محاولة إصلاح أخرى» (بعد فشلين أو أكثر)3 حالات فشل أو أكثر = مشكلة معمارية. شكّك في النمط، لا تصلح مجددًا.

      مرجع سريع​

      المرحلةالأنشطة الرئيسيةمعايير النجاح
      1. السبب الجذرياقرأ الأخطاء، أعد الإنتاج، تحقّق من التغييرات، اجمع الأدلة، تتبّع تدفّق البياناتافهم ماذا ولماذا
      2. النمطاعثر على أمثلة عاملة، قارن، حدّد الاختلافاتاعرف ما الذي اختلف
      3. الفرضيةصُغ نظرية، اختبر بأقل قدر ممكن، متغير واحد في كل مرةفرضية مؤكَّدة أو جديدة
      4. التنفيذأنشئ اختبار تراجع، أصلح السبب الجذري، تحقّقحُلّ الخطأ، ونجحت جميع الاختبارات

      أدوات التحقيق​

      استخدم أدوات Hermes التالية خلال المرحلة 1:

      • search_files — العثور على نصوص الأخطاء، تتبّع استدعاءات الدوال، تحديد الأنماط
      • read_file — قراءة الكود المصدري مع أرقام الأسطر لتحليل دقيق
      • terminal — تشغيل الاختبارات، مراجعة تاريخ git، إعادة إنتاج الأخطاء
      • web_search/web_extract — البحث عن رسائل الأخطاء ووثائق المكتبات

      مع delegate_task​

      للتصحيح المعقد متعدد المكوّنات، أرسل subagents للتحقيق:

      delegate_task(
          goal="Investigate why [specific test/behavior] fails",
          context="""
          Follow systematic-debugging skill:
          1. Read the error message carefully
          2. Reproduce the issue
          3. Trace the data flow to find root cause
          4. Report findings — do NOT fix yet

          Error: [paste full error]
          File: [path to failing code]
          Test command: [exact command]
          """,
          toolsets=['terminal', 'file']
      )

      مع test-driven-development​

      عند إصلاح الأخطاء:

      1. اكتب اختبارًا يعيد إنتاج الخطأ (أحمر)
      2. صحّح الخطأ منهجيًا لإيجاد السبب الجذري
      3. أصلح السبب الجذري (أخضر)
      4. يثبت الاختبار الإصلاح ويمنع التراجع

      الأثر الواقعي​

      من جلسات التصحيح الفعلية:

      • النهج المنهجي: 15-30 دقيقة للإصلاح
      • نهج الإصلاحات العشوائية: 2-3 ساعات من التخبّط
      • معدل نجاح الإصلاح من أول محاولة: 95% مقابل 40%
      • الأخطاء الجديدة المُدخَلة: شبه معدومة مقابل شائعة

      لا اختصارات. لا تخمين. المنهجية تفوز دائمًا.

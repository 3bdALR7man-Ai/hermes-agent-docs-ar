      Simplify Code

      تنظيف متوازي بأربعة وكلاء لتغييرات الكود الأخيرة.

      معلومة

      ما يلي هو التعريف الكامل للمهارة الذي يحمّله Hermes عند تفعيل هذه المهارة، وهو ما يراه الوكيل كتعليمات أثناء عمل المهارة.

      Simplify Code — مراجعة وتنظيف متوازيان

      راجع تغييرات الكود الأخيرة لديك باستخدام أربعة مراجعين مركّزين يعملون في آنٍ واحد، اجمع نتائجهم، ثم طبّق الإصلاحات التي تستحق التطبيق.

      هذه جولة تنظيف، لا صيد أخطاء. أنت تحسّن جودة كود يعمل بالفعل — بإزالة التكرار، وتسطيح التعقيد غير الضروري، وقطع الهدر، وتعميق الإصلاحات المؤقتة (band-aid). لا تنطلق في البحث عن أخطاء الصحة (correctness) هنا؛ فذلك ما تتكفّل به requesting-code-review.

      المبدأ الأساسي: أربعة مراجعين ضيّقي التخصص أفضل من مراجع واحد واسع النطاق. كل واحد منهم يبحث بعمق في قاعدة الكود عن فئة واحدة من المشكلات — إعادة الاستخدام، الجودة، الكفاءة، الارتفاع (altitude) — دون تشتيت انتباهه بين الأربع. يعملون في وقت واحد، فتدفع تكلفة زمنية لمراجعة واحدة فقط، لا لأربع.

      متى تُستخدم​

      فعّل هذه المهارة حين يقول المستخدم أيًا مما يلي:

      • "simplify" / "simplify my changes" / "simplify these changes"
      • "review my code" / "review my recent changes" / "clean up my changes"
      • "/simplify" (إن كان قادمًا من عادة اكتسبها من Claude Code)

      مُعدِّلات اختيارية قد يضيفها المستخدم — التزم بها:

      • التركيز (Focus): "simplify focus on efficiency" ← شغّل مراجع الكفاءة فقط (أو رجّح التجميع لصالحه). التركيزات المعروفة: reuse، quality (تقبل أيضًا simplification)، efficiency، altitude.
      • تشغيل تجريبي (Dry run): "simplify but don't change anything" / "just report" ← شغّل المراجعين الأربعة، اعرض النتائج، ولا تطبّق أي شيء. اسأل قبل التطبيق.
      • النطاق (Scope): "simplify the last commit" / "simplify staged" / "simplify src/foo.py" ← ضيّق مصدر الفرق (diff) وفقًا لذلك (انظر المرحلة 1).

      لا تُشغّل هذه المهارة تلقائيًا بعد كل تعديل، ولا تُلحقها بنهاية مهام غير متصلة. فهي تكلّف مقدار توكنات أربعة subagents — استدعها فقط حين يطلبها المستخدم صراحةً.

      العملية​

      المرحلة 1 — تحديد التغييرات​

      التقط الفرق (diff) المطلوب مراجعته. اختر المصدر بحسب ما طلبه المستخدم، وبهذا الترتيب الافتراضي:

      # 1. Default: uncommitted working-tree changes (tracked files)
      git diff

      # 2. If that's empty, include staged changes
      git diff HEAD

      # 3. Scoped variants the user may request:
      git diff --staged                 # "staged changes"
      git diff HEAD~1                    # "the last commit"
      git diff main...HEAD              # "this branch" / "my PR"
      git diff -- src/foo.py            # specific file(s)

      إذا كان كل من git diff وgit diff HEAD فارغَين ولا يوجد مستودع git أو لا توجد تغييرات، فارجع إلى الملفات التي سمّاها المستخدم صراحةً أو التي أُنشئت/عُدِّلت مؤخرًا في هذه الجلسة. وإن تعذّر عليك فعلًا إيجاد أي كود متغيّر، فقل ذلك وتوقف — فلا شيء هنا يستحق التبسيط.

      التقط نص الفرق كاملًا. لاحظ حجمه: إذا كان كبيرًا جدًا (لنقل أكثر من 2000 سطر متغيّر)، حذّر المستخدم من أن حمل أربعة subagents لكامل الفرق سيكون مكلفًا من حيث التوكنات، واعرض تضييق النطاق (حسب المجلد أو الـ commit) قبل المتابعة.

      المرحلة 2 — إطلاق أربعة مراجعين بالتوازي​

      استخدم delegate_task في وضع الدفعات (batch mode) — مرّر المهام الأربع كلها في مصفوفة tasks واحدة كي تعمل في آنٍ واحد. أربعة هو التفرّع (fan-out) الصحيح لهذا النمط؛ وهو ضمن ميزانية delegation.max_concurrent_children في أي تثبيت افتراضي.

      لا تفويض متاح؟ إذا تعذّر عليك استدعاء delegate_task في هذا السياق (كنت subagent طرفيًا، أو التفويض معطّل، أو استُنفدت الميزانية)، فلا تتخطَّ المراجعة ولا تُسقط أيًا من الزوايا. اعمل عبر الزوايا الأربع بنفسك، بالتسلسل، في هذا السياق نفسه — بنفس معايير البحث وصيغة النتائج ذاتها. ثم اذكر بوضوح في ملخصك النهائي أن هذه كانت مراجعة داخلية أحادية المرور، لا تفرّعًا متوازيًا، كي يعرف المستخدم ما الذي جرى فعلًا.

      أعطِ كل مراجع الفرق كاملًا (لا أجزاءً منه — فمشكلات التداخل بين الملفات تختبئ في الفجوات) إضافةً إلى المسار المطلق للمستودع كي يتمكن من البحث في قاعدة الكود الأوسع. يحصل كل مراجع على toolsets الخاصة بـ terminal وfile وsearch (كي يتمكن من استخدام git وread_file و search_files/grep).

      وجّه كل مراجع إلى:

      • البحث في قاعدة الكود القائمة عن أدلة (لا الاستدلال من الفرق وحده).
      • تطبيق سياج تشيسترتون (Chesterton's Fence): قبل وسم أي شيء للحذف، شغّل git blame على السطر لفهم سبب وجوده. إن تعذّر عليك تحديد الغرض الأصلي، فضعه ضمن confidence: low — لا تخمّن.
      • الإبلاغ عن النتائج كمخرجات مُهيكلة مع التكلفة الملموسة ومستوى الثقة والمخاطر: 
        file:line → problem → cost (what's duplicated/wasted/harder to maintain) → suggested fix | confidence: high/medium/low | risk: SAFE/CAREFUL/RISKY
        حقل التكلفة (cost) يُلزم كل نتيجة بتبرير نفسها — فالنتيجة التي لا تستطيع توضيح ما تكلّفه المشكلة فعلًا تكون على الأرجح مجرد ملاحظة تافهة.
        • SAFE = ثابت أنه لا يؤثر على السلوك (استيرادات غير مستخدمة، كود معلَّق، أغلفة تمريرية). طبّق هذه تلقائيًا.
        • CAREFUL = يحسّن دون تغيير الدلالة (إعادة تسمية متغير محلي، تسطيح عامل ثلاثي متداخل، استخراج دالة مساعدة). طبّقها مع التحقق عبر الاختبارات.
        • RISKY = قد يغيّر السلوك أو يكسر عقودًا عامة (إعادة هيكلة N+1، إعادة تسمية API عام، تغيير في دورة حياة الذاكرة). ضع علامة لمراجعة بشرية — لا تطبّقها تلقائيًا.
      • تجاوز الملاحظات التافهة والتغييرات الأسلوبية البحتة. لا تُبلغ إلا عمّا يُحسّن الكود بصورة ملموسة.

      مرّر هذه الأهداف الأربعة (أسقط أيًا منها استبعده تركيز المستخدم):

      المراجع 1 — إعادة استخدام الكود

      راجع هذا الفرق بحثًا عن كود يكرر وظائف موجودة أصلًا في قاعدة الكود. ابحث في وحدات الأدوات المساعدة، والدوال المشتركة، والملفات المجاورة (باستخدام search_files / grep) عن دوال أو ثوابت أو أنماط قائمة يمكن للكود الجديد استدعاءها بدلًا من إعادة تنفيذها. ضع علامة على: دوال جديدة تكرر دوالًا موجودة؛ منطق مكتوب يدويًا تؤديه أداة موجودة بالفعل (معالجة يدوية للسلاسل النصية/المسارات، فحوصات بيئة مخصّصة، حراس أنواع مرتجلة، تحليل مُعاد تنفيذه). لكل حالة، سمِّ الشيء الموجود الذي ينبغي استخدامه ومكانه.

      المراجع 2 — جودة الكود

      راجع هذا الفرق بحثًا عن مشكلات الجودة. ابحث عن: حالة زائدة (قيم تكرر أو يمكن اشتقاقها من حالة موجودة؛ ذاكرات تخزين مؤقت لا حاجة لوجودها)؛ تضخم المعاملات (parameters جديدة أُلصقت حيث كان ينبغي إعادة هيكلة الدالة)؛ نسخ ولصق مع تغييرات طفيفة (كتل شبه مكررة ينبغي أن تشترك في تجريد واحد)؛ تجريدات مسرّبة (كشف تفاصيل داخلية، كسر حدود تغليف قائمة)؛ كود من النوع النصي البحت (stringly-typed) (سلاسل نصية خام حيث يوجد ثابت/enum/سجل معتمد بالفعل — تحقق من السجلات المعتمدة قبل الوسم)؛ شروط متداخلة بعمق (سلاسل عوامل ثلاثية، أهرامات if/else بثلاث مستويات فأكثر — سطّحها بحراس الشروط أو returns مبكرة أو جدول بحث)؛ أنماط "هلوسة" مولّدة بالذكاء الاصطناعي (تعليقات زائدة تُعيد صياغة كود واضح مثل // increment counter فوق count++؛ فحوصات null دفاعية غير ضرورية على مدخلات مُتحقَّق منها أصلًا؛ تحويلات as any تتجاوز نظام الأنواع؛ أنماط لا تتّسق مع بقية الملف). لكل حالة، قدّم إعادة الهيكلة الملموسة.

      المراجع 3 — الكفاءة

      راجع هذا الفرق بحثًا عن مشكلات الكفاءة. ابحث عن: عمل غير ضروري (حساب متكرر، قراءات ملفات متكررة، استدعاءات API مكررة، أنماط وصول N+1)؛ تزامن مفقود (عمليات مستقلة تُنفَّذ تسلسليًا)؛ تضخّم المسار الساخن (عمل ثقيل/حاجز عند بدء التشغيل أو في مسارات كل طلب)؛ أنماط TOCTOU مضادة (فحص وجود مسبق قبل عملية بدلًا من تنفيذ العملية ومعالجة الخطأ)؛ مشكلات الذاكرة (نمو غير محدود، غياب التنظيف، تسريبات في المستمعين/المقابض؛ استدعاءات أو كائنات طويلة العمر مبنية كإغلاقات (closures) تلتقط النطاق المحيط بأكمله — فكل ما يُلتقط يبقى حيًا طوال بقاء الكائن، لذا يُفضَّل صنف صغير أو بنية حقول صريحة تنسخ فقط ما تحتاجه)؛ قراءات واسعة النطاق أكثر من اللازم (تحميل ملفات كاملة حين تكفي شريحة منها)؛ إخفاقات صامتة (كتل catch فارغة، قيم أخطاء متجاهَلة، except: pass، .catch(() => {}) بلا معالجة، فجوات في انتشار الأخطاء — فهذه تُخفي الأخطاء وينبغي تسجيلها في الحد الأدنى قبل ابتلاعها). لكل حالة، قدّم الإصلاح الملموس وسبب كونه أسرع أو أكثر أمانًا.

      المراجع 4 — الارتفاع (Altitude)

      راجع هذا الفرق بحثًا عن تغييرات نُفِّذت على العمق الخاطئ — إصلاحات مؤقتة (band-aid) فُرشت فوق بنية تحتية مشتركة بدل إصلاح البنية التحتية نفسها. علامات الإصلاح الضحل جدًا: حالة خاصة أُضيفت إلى مسار كود عام لخدمة مستدعٍ واحد (فرع if (caller == X)، فحص نوع، مخرج طارئ بقيمة سحرية)؛ عرَض مُعالَج عند موقع الاستدعاء بينما تحتفظ مواقع الاستدعاء الشقيقة بنفس العيب؛ حلّ التفافي مُكدَّس فوق حلّ التفافي سابق؛ غلاف أُضيف لتجنّب لمس الشيء الذي يحتاج فعلًا إلى تغيير؛ إعدادات أو أعلام (flags) أُدخلت للالتفاف حول قيمة افتراضية معطوبة بدلًا من إصلاح تلك القيمة الافتراضية. لكل حالة، حدّد الآلية الأساسية التي يتجنبها التغيير وصف الإصلاح الأعمق — عمّم المسار المشترك، أصلح القيمة الافتراضية الجذرية، أو أصلح فئة الخطأ بأكملها — وأشر بصدق حين يكون الإصلاح الأعمق كبيرًا بما يكفي ليصبح مهمة قائمة بذاتها بدلًا من جزء من هذا التنظيف. اقرأ الكود المحيط وgit blame أولًا: فما يبدو إصلاحًا مؤقتًا قد يكون أحيانًا حدًا متعمدًا (طبقات توافق، هجرات مرحلية، عزل كود مستورد من طرف ثالث). لا تضع علامة على هذه الحالات.

      المرحلة 3 — التجميع والتطبيق​

      انتظر عودة الأربعة جميعًا (وضع الدفعات يعيدها معًا).

      1. ادمج النتائج في قائمة واحدة، مع إزالة التكرار حيث يتداخل المراجعون — حين تستهدف نتيجتان نفس السطر أو نفس الآلية الأساسية، ادمجهما في نتيجة واحدة.
      2. استبعد الإيجابيات الكاذبة — لديك أوسع سياق؛ لست مضطرًا للجدال مع مراجع، فقط أسقط الاقتراحات الضعيفة أو الخاطئة بصمت.
      3. احسم التعارضات. قد يختلف المراجعون (المراجع 1: "استخدم الأداة الموجودة X"؛ المراجع 3: "X بطيئة، ضمّنها مباشرة"). ترتيب الحسم الافتراضي: الصحة (correctness) > تركيز المستخدم المُعلَن > القابلية للقراءة/إعادة الاستخدام > الأداء الدقيق (micro-perf). لا تطبّق "إصلاح" أداء يضرّ بالوضوح ما لم يكن المسار ساخنًا فعلًا. حين يكون اقتراحان متنافيين ومقبولين معًا، اختر الذي يمسّ كودًا أقل واذكر البديل.
      4. طبّق حسب ترتيب فئة المخاطر:
        • SAFE أولًا (تطبيق تلقائي): استيرادات غير مستخدمة، كود معلَّق، أغلفة تمريرية، تأكيدات نوع زائدة. شغّل الاختبارات بعدها.
        • CAREFUL بعد ذلك (طبّق مع تحقق، ملفًا تلو الآخر): إعادة تسمية متغيرات محلية، تسطيح عوامل ثلاثية، استخراج دوال مساعدة، دمج التكرارات. شغّل الاختبارات بعد كل ملف. تراجع عن أي تغيير يكسر الاختبارات.
        • RISKY أخيرًا (وسم لمراجعة — لا تطبّق تلقائيًا): إعادة هيكلة N+1، تغييرات API عامة، إصلاحات تزامن، تغييرات معالجة الأخطاء. اعرض كل حالة مع وصف المخاطر وحالة تغطية الاختبارات. نتائج الارتفاع غالبًا ما تقع هنا — إذ يعني تعميق الإصلاح لمس بنية تحتية مشتركة، فاعرض الإصلاح الأعمق ودع المستخدم يقرر تنفيذه الآن أو كمتابعة لاحقة. إذا اختار المستخدم تشغيلًا تجريبيًا، اعرض الفئات الثلاث كلها ولا تطبّق شيئًا.
      5. تحقق من أنك لم تكسر شيئًا: شغّل اختبارات المشروع المُستهدفة للملفات التي لمستها (لا مجموعة الاختبارات كاملة)، وأعد تشغيل أي فاحص لينت (linter) أو فحص أنواع يستخدمه المستودع. إذا كسر إصلاح ما اختبارًا، تراجع عن ذلك الإصلاح تحديدًا وأبلغ عنه.
      6. لخّص ما غيّرته: قائمة موجزة بالإصلاحات المُطبَّقة مصنّفة حسب فئة المراجع وفئة المخاطر، إضافةً إلى أي نتائج تجاهلتها عمدًا وسبب ذلك. إذا عملت داخليًا (بلا تفويض)، اذكر ذلك هنا.

      المزالق​

      • لا تتفرّع لأكثر من 4. مزيد من المراجعين يعني تكلفة أعلى واقتراحات متعارضة أكثر ينبغي التوفيق بينها، لا تغطية أفضل. الفئات الأربع تغطي المساحة بأكملها.
      • أعطِ الفرق الكامل لكل مراجع. تقسيم الفرق بين المراجعين يُفشِل التصميم — فالتكرار بين الملفات ومشكلات N+1 لا تظهر إلا بالصورة الكاملة.
      • المراجعون يبحثون، لا يخمّنون. نتيجة إعادة استخدام بلا إشارة إلى الأداة الموجودة ("ربما توجد دالة مساعدة لهذا") مجرد ضوضاء. اشترط دليل file:line؛ أسقط النتائج التي تفتقر إليه.
      • التطبيق ليس إعادة كتابة. هذا تنظيف لتغييرات المستخدم الأخيرة، لا ترخيص لإعادة هيكلة الوحدة بأكملها. أبقِ التعديلات ضمن نطاق ما لمسه الفرق زائد أدنى تغيير محيط يتطلبه الإصلاح. نتائج الارتفاع هي الاستثناء الذي يؤكد القاعدة: حين يكون الإصلاح الصحيح أعمق من الفرق، ضع عليه علامة — لا تُعِد بناء الآلية المشتركة من جانب واحد داخل جولة تنظيف.
      • لا تنجرف إلى صيد الأخطاء. إذا كشف مراجع عن خطأ صحة حقيقي، أبلغ عنه بوضوح — لكن كملاحظة "عثرت على خطأ" منفصلة، لا مطويّة ضمن إصلاحات التنظيف. مراجعة الصحة عملية منفصلة بمعايير تحقق مختلفة.
      • احترم اصطلاحات المشروع. إذا كان المستودع يحتوي AGENTS.md أو CLAUDE.md أو HERMES.md أو إعدادات لينتر، أدرج تلك القواعد ضمن توجيهات المراجعين كي تتوافق الاقتراحات مع أسلوب المشروع بدلًا من مخالفته.
      • الفروق الكبيرة تُنهك السياق. إذا كان الفرق ضخمًا، ضيّق نطاقه قبل التفويض — فحمل أربعة subagents كل منها لفرق من 5000 سطر مكلف وقد يُقتطع.
      • الثقة الزائدة بأدوات الكود الميت. أدوات مثل knip وts-prune و depcheck تُبلغ عن تصديرات تُستخدم فعلًا بصورة ديناميكية (استيرادات قائمة على سلاسل نصية، انعكاس/reflection). ابحث دائمًا بالـ grep عن اسم الرمز قبل حذفه — فتقرير نظيف من أداة ليس دليلًا.
      • إعادة التسمية دون التحقق من العقود العامة. أسماء التصدير، ومسارات مسارات API، وأسماء أعمدة قواعد البيانات، ومفاتيح الإعدادات كلها عقود — حتى إن كان الاسم سيئًا، فإعادة تسميته تكسر المستهلكين. صنّف تغييرات العقود العامة كـ RISKY؛ لا تُعد تسميتها تلقائيًا أبدًا.
      • حذف معالجة أخطاء "غير ضرورية". قد تكون كتلة catch فارغة أو خطأ متجاهَل مقصودَين — بمعنى أن الخطأ متوقع وغير ضار في ذلك السياق. ضع علامة عليه ولا تحذفه؛ ودع الإنسان يقرر.
      • ليست كل حالة خاصة إصلاحًا مؤقتًا. طبقات التوافق، والهجرات المرحلية، وطبقات العزل حول الكود المستورد من طرف ثالث تبدو كمخالفات ارتفاع لكنها تصميم متعمد. تحقق من git blame والتعليقات المحيطة قبل الوسم؛ وحين يكون القصد غير واضح، ضعه ضمن confidence: low.

      ذات صلة​

      إذا كان تثبيتك يحتوي مهارة subagent-driven-development (اختيارية)، فهي تغطي الحالة المكمّلة: مراجعة متوازية أثناء التنفيذ، لكل مهمة. أما هذه المهارة فهي جولة التنظيف المستقلة اللاحقة للتنفيذ. استخدم requesting-code-review لبوابة الأمان/الجودة قبل الـ commit — فتلك هي جولة صيد الأخطاء؛ وهذه هي التنظيف.

      Python debugpy

      صحّح أخطاء Python: REPL الخاص بـ pdb + debugpy عن بُعد (DAP).

      بيانات المهارة الوصفية​

      المصدرمضمّنة (مثبّتة افتراضيًا)
      المسارskills/software-development/python-debugpy

      المرجع: ملف SKILL.md كاملًا​

      معلومة

      ما يلي هو التعريف الكامل للمهارة الذي يحمّله Hermes عند تفعيل هذه المهارة، وهو ما يراه الوكيل كتعليمات أثناء عمل المهارة.

      مصحّح Python (pdb + debugpy)

      نظرة عامة​

      ثلاث أدوات، تُختار حسب الموقف:

      الأداةمتى تُستخدم
      breakpoint() + pdbمحلية، تفاعلية، الأبسط. أضف breakpoint() في الكود المصدري، شغّله بشكل عادي، واحصل على REPL عند ذلك السطر.
      python -m pdbتشغيل سكربت موجود تحت pdb دون أي تعديل على المصدر. مفيدة للفحص السريع.
      debugpyعن بُعد / بلا واجهة رسومية / «الاتصال بعملية قيد التشغيل فعلًا». يتحدث DAP، قابل للسكربتة من الطرفية، يعمل مع العمليات طويلة الأمد (gateway، daemon، عمليات PTY الفرعية).

      ابدأ بـ breakpoint(). إنها أرخص وسيلة تنجح.

      متى تستخدمها​

      • يفشل اختبار ولا يكشف تتبّع الاستثناء (traceback) سبب خطأ إحدى القيم
      • تحتاج إلى الخطو عبر دالة ومراقبة تغيّر مجموعة (collection)
      • تسيء عملية طويلة التشغيل (hermes gateway، tui_gateway) التصرف ولا يمكنك إعادة تشغيلها
      • تحليل ما بعد الحدث (post-mortem): أُطلق استثناء في كود شبيه بالإنتاج وتريد فحص المتغيرات المحلية عند موضع الانهيار
      • عملية فرعية / تابعة (Python _SlashWorker، عامل جسر PTY) هي موضع الخطأ الفعلي

      لا تستخدمها في: ما يحلّه print() / logging.debug في أقل من دقيقة، أو ما يكشفه أصلًا pytest -vv --tb=long --showlocals.

      مرجع سريع لـ pdb​

      داخل أي موجّه pdb ((Pdb)):

      الأمرالإجراء

      sخطو داخل

      unt Nالمتابعة حتى السطر N

      l / llعرض الكود المصدري حول السطر الحالي / الدالة كاملة
      wwhere (تتبّع المكدس)
      u / dالتنقل لأعلى / لأسفل في المكدس
      aطباعة معطيات (args) الدالة الحالية
      p expr / pp exprطباعة / طباعة منسّقة للتعبير
      display exprطباعة التعبير تلقائيًا عند كل توقف

      b file:line, condنقطة توقف شرطية

      أمر interact هو الأقوى — يمكنك استيراد أي شيء، وفحص كائنات معقّدة، بل واستدعاء توابع تغيّر الحالة. المتغيرات المحلية للقراءة فقط افتراضيًا؛ استخدم !x = 42 من موجّه (Pdb) لتغييرها.

      الوصفة 1: نقطة توقف محلية​

      الأسهل. عدّل الملف:

      def compute(x, y):
          result = some_helper(x)
          breakpoint()           # <-- drops into pdb here
          return result + y

      شغّل الكود بشكل عادي. ستصل إلى سطر breakpoint() مع وصول كامل إلى المتغيرات المحلية.

      لا تنسَ إزالة breakpoint() قبل الالتزام (commit). استخدم git diff أو بحثًا (grep) قبل الالتزام:

      rg -n 'breakpoint\(\)' --type py

      الوصفة 2: تشغيل سكربت تحت pdb (دون تعديل المصدر)​

      python -m pdb path/to/script.py arg1 arg2
      # Lands at first line of script
      (Pdb) b path/to/script.py:42
      (Pdb) c

      الوصفة 3: تصحيح اختبار pytest​

      يدعم كلٌّ من مشغّل اختبارات hermes و pytest ذلك:

      # Drop to pdb on failure (or on any raised exception):
      scripts/run_tests.sh tests/path/to/test_file.py::test_name --pdb

      # Drop to pdb at the START of the test:
      scripts/run_tests.sh tests/path/to/test_file.py::test_name --trace

      # Show locals in tracebacks without pdb:
      scripts/run_tests.sh tests/path/to/test_file.py --showlocals --tb=long

      ملاحظة: يشغّل scripts/run_tests.sh كل ملف اختبار في عملية فرعية مُلتقطة (captured) عبر run_tests_parallel.py (دون xdist)، لذا لا يعمل pdb التفاعلي تحت هذا الغلاف (wrapper). شغّل pytest مباشرة لاستخدام --pdb:

      source .venv/bin/activate
      python -m pytest tests/foo_test.py::test_bar --pdb

      هذا يتجاوز ضمانات البيئة المعزولة (hermetic-env) — مقبول للتصحيح، لكن أعد التشغيل تحت الغلاف للتأكد قبل الدفع (push).

      الوصفة 4: تحليل ما بعد الحدث لأي استثناء​

      import pdb, sys
      try:
          run_the_thing()
      except Exception:
          pdb.post_mortem(sys.exc_info()[2])

      أو غلّف سكربتًا كاملًا:

      python -m pdb -c continue script.py
      # When it crashes, pdb catches it and you're in the frame of the exception

      أو عيّن hook عامًا في repl/jupyter:

      import sys
      def excepthook(etype, value, tb):
          import pdb; pdb.post_mortem(tb)
      sys.excepthook = excepthook

      الوصفة 5: تصحيح عن بُعد بـ debugpy (الاتصال بعملية قيد التشغيل)​

      للعمليات طويلة الأمد: hermes gateway، tui_gateway، أو daemon، أو عملية تسيء التصرف بالفعل ولا يمكن إعادة تشغيلها بشكل نظيف.

      الإعداد​

      source <hermes-agent-repo>/.venv/bin/activate
      pip install debugpy

      النمط أ: تعديل المصدر — العملية تنتظر المصحّح عند الإطلاق​

      أضف قرب أعلى نقطة الدخول (أو داخل الدالة التي تريد تصحيحها):

      import debugpy
      debugpy.listen(("127.0.0.1", 5678))
      print("debugpy listening on 5678, waiting for client...", flush=True)
      debugpy.wait_for_client()
      debugpy.breakpoint()       # optional: pause immediately once attached

      شغّل العملية؛ ستُحجب عند wait_for_client().

      النمط ب: دون تعديل المصدر — التشغيل بـ -m debugpy​

      python -m debugpy --listen 127.0.0.1:5678 --wait-for-client your_script.py arg1

      المكافئ لنقطة دخول وحدة (module):

      python -m debugpy --listen 127.0.0.1:5678 --wait-for-client -m your.module

      النمط ج: الاتصال بعملية قيد التشغيل فعلًا​

      يحتاج إلى رقم العملية (PID) وإلى تثبيت debugpy مسبقًا في بيئة الهدف:

      python -m debugpy --listen 127.0.0.1:5678 --pid <pid>
      # debugpy injects itself into the process. Then attach a client as below.

      بعض النواة (kernels)/إعدادات الأمان تمنع الحقن المعتمد على ptrace (/proc/sys/kernel/yama/ptrace_scope). أصلح ذلك بـ:

      echo 0 | sudo tee /proc/sys/kernel/yama/ptrace_scope

      توصيل عميل من الطرفية​

      أسهل عميل DAP من جهة الطرفية هو CLI الخاص بـ VS Code أو سكربت صغير. من داخل Hermes لديك خياران عمليان:

      الخيار 1: REPL CLI الخاص بـ debugpy نفسه — ليست ميزة رسمية، لكنها سكربت عميل DAP صغير:

      # /tmp/dap_client.py
      import socket, json, itertools, time, sys

      HOST, PORT = "127.0.0.1", 5678
      s = socket.create_connection((HOST, PORT))
      seq = itertools.count(1)

      def send(msg):
          msg["seq"] = next(seq)
          body = json.dumps(msg).encode()
          s.sendall(f"Content-Length: {len(body)}\r\n\r\n".encode() + body)

      def recv():
          header = b""
          while b"\r\n\r\n" not in header:
              header += s.recv(1)
          length = int(header.decode().split("Content-Length:")[1].split("\r\n")[0].strip())
          body = b""
          while len(body) < length:
              body += s.recv(length - len(body))
          return json.loads(body)

      send({"type": "request", "command": "initialize", "arguments": {"adapterID": "python"}})
      print(recv())
      send({"type": "request", "command": "attach", "arguments": {}})
      print(recv())
      send({"type": "request", "command": "setBreakpoints",
            "arguments": {"source": {"path": sys.argv[1]},
                          "breakpoints": [{"line": int(sys.argv[2])}]}})
      print(recv())
      send({"type": "request", "command": "configurationDone"})
      # ... loop reading events and sending continue/stepIn/etc.

      هذا مناسب لأتمتة لمرة واحدة لكنه مؤلم كتجربة تفاعلية.

      الخيار 2: الاتصال من VS Code / Cursor / Zed — إن كان لدى المستخدم أحدها مفتوحًا، يمكنه إضافة launch.json:

      {
        "name": "Attach to Hermes",
        "type": "debugpy",
        "request": "attach",
        "connect": { "host": "127.0.0.1", "port": 5678 },
        "justMyCode": false,
        "pathMappings": [
          { "localRoot": "${workspaceFolder}", "remoteRoot": "<hermes-agent-repo>" }
        ]
      }

      الخيار 3: تخلَّ عن DAP، استخدم remote-pdb — عادةً ما تريده فعليًا من وكيل الطرفية:

      pip install remote-pdb

      في كودك:

      from remote_pdb import set_trace
      set_trace(host="127.0.0.1", port=4444)   # blocks until connection

      ثم من الطرفية:

      nc 127.0.0.1 4444
      # You get a (Pdb) prompt exactly as if debugging locally.

      remote-pdb هو الخيار الأنظف والأنسب للوكيل عندما يكون بروتوكول DAP الخاص بـ debugpy مبالغًا فيه. استخدم debugpy فقط عندما تحتاج فعلًا إلى تكامل مع بيئة تطوير (IDE).

      تصحيح عمليات خاصة بـ Hermes​

      الاختبارات​

      راجع الوصفة 3. يلتقط الغلاف مخرجات العملية الفرعية، لذا شغّل pytest مباشرة لاستخدام pdb التفاعلي.

      run_agent.py / CLI — لمرة واحدة​

      الأسهل: أضف breakpoint() قرب السطر المشتبه به، ثم شغّل hermes بشكل عادي. يعود التحكم إلى طرفيتك عند نقطة التوقف.

      عملية tui_gateway الفرعية (التي يُطلقها hermes --tui)​

      تعمل الـ gateway كعملية تابعة لـ TUI الخاصة بـ Node. الخيارات:

      أ. عدّل مصدر الـ gateway:

      # tui_gateway/server.py near the top of serve()
      import debugpy
      debugpy.listen(("127.0.0.1", 5678))
      debugpy.wait_for_client()

      شغّل hermes --tui. ستبدو TUI متجمّدة (خلفيتها بانتظار). صل عميلًا؛ يستأنف التنفيذ عندما تنفّذ continue.

      ب. استخدم remote-pdb عند معالج محدد:

      from remote_pdb import set_trace
      set_trace(host="127.0.0.1", port=4444)   # in the RPC handler you want to trap

      شغّل أمر slash المطابق من TUI، ثم nc 127.0.0.1 4444 في طرفية أخرى.

      عملية _SlashWorker الفرعية​

      النمط نفسه — remote-pdb مع set_trace() داخل مسار exec الخاص بالعامل (worker). العامل مستمر عبر أوامر slash، فتتوقف أول محاولة إطلاق حتى تتصل؛ وتمر أوامر slash التالية بشكل عادي ما لم تُعِد التسليح (re-arm).

      الـ Gateway (gateway/run.py)​

      طويلة الأمد. استخدم remote-pdb عند معالج، أو debugpy مع --wait-for-client إن كنت ستعيد تشغيل الـ gateway على أي حال.

      مزالق شائعة​

      1. لا يفعل pdb شيئًا بصمت تحت مشغّل متوازٍ/يلتقط المخرجات. لن ترى الموجّه، والاختبار يتوقف فقط (صحيح مع pytest-xdist ومع العمليات الفرعية الملتقطة لكل ملف في scripts/run_tests.sh). شغّل pytest مباشرة على ملف واحد للتصحيح التفاعلي.

      2. breakpoint() في CI / سياقات بلا TTY يعلّق العملية. آمن محليًا؛ لا تلتزمه (commit) أبدًا. أضف بحث grep قبل الالتزام كشبكة أمان.

      3. PYTHONBREAKPOINT=0 يعطّل جميع استدعاءات breakpoint(). تحقّق من متغير البيئة إن كانت نقطة توقفك لا تُصاب:

        echo $PYTHONBREAKPOINT

      4. يحجب debugpy.listen فقط إن استدعيت أيضًا wait_for_client(). بدونها يستمر التنفيذ وقد تُطلق نقطة توقفك الأولى قبل اتصال العميل.

      5. يفشل الاتصال بـ PID على النواة المُشدَّدة (hardened). يسمح ptrace_scope=1 (الافتراضي في Ubuntu) فقط بـ ptrace من نفس المستخدم للعمليات الفرعية. الحل البديل: echo 0 > /proc/sys/kernel/yama/ptrace_scope (يحتاج صلاحيات root) أو التشغيل تحت debugpy من البداية.

      6. الخيوط (threads). يصحّح pdb الخيط الحالي فقط. للكود متعدد الخيوط، استخدم debugpy (وهو DAP واعٍ بالخيوط) أو عيّن threading.settrace() لكل خيط.

      7. asyncio. يعمل pdb في الدوال المشتركة (coroutines) لكن await داخل pdb يتطلب Python 3.13+ أو await من نمط interact في الإصدارات الأقدم. لإصداري 3.11/3.12، استخدم حيل asyncio.run_coroutine_threadsafe أو انتظارات (awaits) عبر !stmt باستخدام asyncio.ensure_future.

      8. يزيل scripts/run_tests.sh بيانات الاعتماد ويعيّن HOME=<tmpdir>. إذا كان خطؤك يعتمد على إعدادات المستخدم أو مفاتيح API حقيقية، فلن يتكرّر تحت الغلاف. صحّح باستخدام pytest الخام أولًا لإعادة إنتاجه، ثم تأكّد مجددًا تحت الغلاف.

      9. Forking / multiprocessing. لا يتتبّع pdb عمليات fork. تحتاج كل عملية فرعية إلى breakpoint() أو set_trace() خاصة بها. لـ subagents في Hermes، صحّح عملية واحدة في كل مرة.

      قائمة التحقق​

      • بعد pip install debugpy، تحقّق: python -c "import debugpy; print(debugpy.__version__)"
      • للتصحيح عن بُعد، تحقّق أن المنفذ يستمع فعليًا: ss -tlnp | grep 5678
      • نقطة التوقف الأولى تُصاب فعليًا (إن لم تُصب، فمن المرجّح أن لديك PYTHONBREAKPOINT=0، أو أنك تحت مشغّل متوازٍ/يلتقط المخرجات، أو انتهى التنفيذ قبل الاتصال)
      • يعرض where / w مكدس الاستدعاءات المتوقع
      • تنظيف ما بعد التصحيح: لا يوجد breakpoint() / set_trace() متبقٍّ في الكود الملتزَم (committed) 
        rg -n 'breakpoint\(\)|set_trace\(|debugpy\.listen' --type py

      وصفات لمرة واحدة​

      «لماذا يفتقد هذا القاموس (dict) مفتاحًا؟»

      # add above the KeyError site
      breakpoint()
      # then in pdb:
      (Pdb) pp d
      (Pdb) pp list(d.keys())
      (Pdb) w                # how did we get here

      «هذا الاختبار ينجح بمفرده لكنه يفشل ضمن المجموعة (suite).»

      scripts/run_tests.sh tests/the_test.py   # confirm it fails under the isolated runner first
      # For interactive debugging, or if it only fails WITH other tests:
      source .venv/bin/activate
      python -m pytest tests/ -x --pdb
      # Now it pdb-traps at the exact failing test after state accumulated.

      «معالجي غير المتزامن (async) يتجمّد (deadlock).»

      # Add at handler entry
      import remote_pdb; remote_pdb.set_trace(host="127.0.0.1", port=4444)

      أطلق المعالج. نفّذ nc 127.0.0.1 4444، ثم w لرؤية الإطار المعلَّق، و !import asyncio; asyncio.all_tasks() لرؤية ما هو معلّق أيضًا.

      «تحليل ما بعد الحدث لانهيار في عملية Ink فرعية / عملية فرعية.»

      PYTHONFAULTHANDLER=1 python -m pdb -c continue path/to/entrypoint.py
      # On crash, pdb lands at the frame of the exception with full locals

      إعداد Hermes باستخدام Docker

      هناك طريقتان مختلفتان يتقاطع بهما Docker مع Hermes Agent:

      1. تشغيل Hermes داخل Docker — يعمل الوكيل نفسه داخل حاوية (وهو المحور الأساسي لهذه الصفحة)
      2. Docker كـ terminal backend — يعمل الوكيل على جهازك المضيف لكنه ينفّذ كل أمر داخل حاوية sandbox واحدة ودائمة من Docker، تبقى قائمة عبر استدعاءات الأدوات و /new والـ subagents طوال عمر عملية Hermes (راجع الإعدادات → Docker Backend)

      تتناول هذه الصفحة الخيار 1. تخزّن الحاوية جميع بيانات المستخدم (الإعدادات، ومفاتيح API، والجلسات، والمهارات، والذكريات) في مجلد واحد مُركَّب من الجهاز المضيف على المسار /opt/data. أما الصورة (image) نفسها فلا تحتفظ بأي حالة (stateless)، ويمكن ترقيتها بسحب إصدار جديد دون فقدان أي إعدادات.

      البدء السريع​

      إذا كانت هذه أول مرة تشغّل فيها Hermes Agent، فأنشئ مجلد بيانات على الجهاز المضيف وشغّل الحاوية تفاعليًا لتشغيل معالج الإعداد (setup wizard):

      تجنّب وحدات تحكم VPS المستندة إلى المتصفح عند تنفيذ أوامر التثبيت

      يوفّر بعض مزوّدي VPS (مثل Hetzner Cloud وغيره) وحدة تحكم (console) مستندة إلى المتصفح لإدارة الأجهزة. تنقل هذه الوحدات المحارف الخاصة بشكل خاطئ — فقد يصل : على هيئة ;، وقد يُعرض @ بشكل خاطئ، ويكون الوضع أسوأ مع تخطيطات لوحة المفاتيح غير الإنجليزية — مما يُفسد بصمت وسائط docker run مثل -v ~/.hermes:/opt/data و -e KEY=value، ومفاتيح API / الـ tokens الملصوقة.

      اتصل عبر SSH بدلًا من ذلك (ssh root@<host>) لإدخال الأوامر بالنسخ واللصق بأمان. وإذا اضطررت إلى استخدام وحدة التحكم في المتصفح، فاكتب الأوامر يدويًا بدلًا من لصقها، وتحقّق جيدًا من كل : و @ و = و / في النتيجة قبل الضغط على Enter.

      mkdir -p ~/.hermes
      docker run -it --rm \
        -v ~/.hermes:/opt/data \
        nousresearch/hermes-agent setup

      ينقلك هذا إلى معالج الإعداد، الذي سيطلب منك مفاتيح API ويكتبها في ~/.hermes/.env. لا تحتاج إلى فعل ذلك إلا مرة واحدة. ويُوصى بشدة بإعداد نظام محادثة يعمل معه الـ gateway في هذه المرحلة.

      نصيحة

      داخل الحاوية، نفّذ hermes setup --portal مرة واحدة — إذ يبقى الـ refresh token محفوظًا في الـ volume المُركَّب ~/.hermes. راجع Nous Portal.

      التشغيل في وضع gateway​

      بعد الإعداد، شغّل الحاوية في الخلفية كـ gateway دائم (Telegram و Discord و Slack و WhatsApp وغيرها):

      docker run -d \
        --name hermes \
        --restart unless-stopped \
        -v ~/.hermes:/opt/data \
        -p 8642:8642 \
        nousresearch/hermes-agent gateway run

      يُتيح المنفذ 8642 خادم API المتوافق مع OpenAI الخاص بالـ gateway و endpoint فحص السلامة. وهو اختياري إذا كنت تستخدم منصات المحادثة فقط (Telegram و Discord وغيرها)، لكنه مطلوب إذا أردت أن تصل لوحة التحكم أو الأدوات الخارجية إلى الـ gateway.

      يعمل الـ gateway تحت الإشراف

      داخل صورة Docker الرسمية، يخضع gateway run لإشراف s6-overlay تلقائيًا: فإذا انهارت عملية الـ gateway يُعاد تشغيلها خلال ثانيتين تقريبًا دون فقدان الحاوية، كما تخضع لوحة التحكم (عند ضبط HERMES_DASHBOARD=1) للإشراف إلى جانبه. أما عملية CMD الخاصة بـ gateway run نفسها فهي نبضة sleep infinity تُبقي الحاوية حيّة بينما يدير s6 عملية الـ gateway الفعلية — لذا يظل docker stop يُوقف كل شيء بشكل نظيف، بينما يعرض docker logs مخرجات الـ gateway الخاضع للإشراف.

      سترى سطرًا واحدًا في docker logs يؤكد هذه الترقية. ولإلغاء ذلك — والعودة إلى السلوك السابق "الـ gateway هو العملية الرئيسية للحاوية، وخروج الحاوية = خروج الـ gateway" — مرّر --no-supervise أو اضبط HERMES_GATEWAY_NO_SUPERVISE=1. ويفيد إلغاء الإشراف في اختبارات CI السريعة (smoke tests) التي تتطلب خروج الحاوية برمز حالة الـ gateway؛ أما في عمليات النشر الإنتاجية فالإعداد الافتراضي الخاضع للإشراف أفضل بلا شك.

      ينطبق هذا السلوك على الصورة المستندة إلى s6 فقط. أما الصور الأقدم (المستندة إلى tini) فلا تزال تشغّل gateway run كعملية رئيسية في المقدمة.

      أين تذهب سجلات الـ gateway

      راجع قسم أين تذهب السجلات أدناه للاطلاع على خريطة التوجيه الكاملة (الـ gateways لكل profile، ولوحة التحكم، و boot reconciler، و docker logs على مستوى الحاوية).

      الإيقاف الصارم لحلقات الأدوات في الـ gateways غير المراقَبة

      تُفعّل جلسات الـ gateway و cron غير المراقَبة الإيقافَ الصارم لحلقات الأدوات (tool-loop hard stops) افتراضيًا عبر non_interactive_hard_stop_enabled. أما جلسات CLI و TUI و Desktop و ACP التفاعلية فتبقى مقتصرة على التحذير. ولإلغاء ذلك في نشر غير مراقَب، اضبط ما يلي في ملف config.yaml الخاص بالـ profile:

      tool_loop_guardrails:
        non_interactive_hard_stop_enabled: false

      ملاحظة: لا يعمل خادم API إلا مع API_SERVER_ENABLED=true. ولإتاحته خارج 127.0.0.1 داخل الحاوية، اضبط أيضًا API_SERVER_HOST=0.0.0.0 و API_SERVER_KEY (8 أحرف على الأقل — أنشئ واحدًا باستخدام openssl rand -hex 32). مثال:

      docker run -d \
        --name hermes \
        --restart unless-stopped \
        -v ~/.hermes:/opt/data \
        -p 8642:8642 \
        -e API_SERVER_ENABLED=true \
        -e API_SERVER_HOST=0.0.0.0 \
        -e API_SERVER_KEY="$(openssl rand -hex 32)" \
        -e API_SERVER_CORS_ORIGINS='*' \
        nousresearch/hermes-agent gateway run

      يُعدّ فتح أي منفذ على جهاز متصل بالإنترنت خطرًا أمنيًا، فلا تفعل ذلك ما لم تكن تدرك المخاطر.

      تشغيل لوحة التحكم​

      تعمل لوحة التحكم المدمجة على الويب كخدمة s6-rc خاضعة للإشراف إلى جانب الـ gateway في الحاوية نفسها. اضبط HERMES_DASHBOARD=1 لتشغيلها:

      docker run -d \
        --name hermes \
        --restart unless-stopped \
        -v ~/.hermes:/opt/data \
        -p 8642:8642 \
        -p 9119:9119 \
        -e HERMES_DASHBOARD=1 \
        nousresearch/hermes-agent gateway run

      تخضع لوحة التحكم لإشراف s6 — فإذا انهارت، يعيد s6-supervise تشغيلها تلقائيًا بعد فترة انتظار قصيرة. ويُمرَّر stdout/stderr الخاص بلوحة التحكم إلى docker logs <container> (دون بادئة؛ إذ صارت مخرجات الـ gateway نفسه تُحفظ في ملف s6-log لكل profile — راجع أين تذهب السجلات أدناه — لذا لا يتعارض التدفقان).

      متغير البيئةالوصفالقيمة الافتراضية
      HERMES_DASHBOARDاضبطه على 1 (أو true / yes) لتفعيل خدمة لوحة التحكم الخاضعة للإشراف(غير مضبوط — تُسجَّل الخدمة لكنها تبقى متوقفة)
      HERMES_DASHBOARD_HOSTعنوان الربط لخادم HTTP الخاص بلوحة التحكم0.0.0.0
      HERMES_DASHBOARD_PORTمنفذ خادم HTTP الخاص بلوحة التحكم9119
      HERMES_DASHBOARD_INSECUREمهمل (deprecated) / بلا أثر. كان سابقًا يتجاوز بوابة المصادقة؛ ومنذ تعزيز الأمان في يونيو 2026 لم يعد يعطّل المصادقة. والربط بعنوان غير loopback يتطلب دائمًا مزوّد مصادقة(يُتجاهل — اضبط مزوّدًا بدلًا منه)

      ترتبط لوحة التحكم داخل الحاوية افتراضيًا بالعنوان 0.0.0.0 — فبدون ذلك لن يكون المنفذ المنشور -p 9119:9119 قابلًا للوصول من الجهاز المضيف. ولتقييد الربط بعنوان loopback الخاص بالحاوية (في إعدادات sidecar / reverse proxy)، اضبط HERMES_DASHBOARD_HOST=127.0.0.1.

      تعمل بوابة المصادقة في لوحة التحكم تلقائيًا عند تحقق الشرطين التاليين معًا:

      1. أن يكون مضيف الربط غير loopback (مثل القيمة الافتراضية 0.0.0.0 داخل الحاوية)، و
      2. أن تكون هناك إضافة DashboardAuthProvider مسجّلة.

      هناك ثلاث طرق مضمّنة لتحقيق الشرط الثاني:

      • اسم المستخدم/كلمة المرور — الأبسط لحاوية مستضافة ذاتيًا / محلية (on-prem) / في homelab على شبكة موثوقة أو خلف VPN: اضبط HERMES_DASHBOARD_BASIC_AUTH_USERNAME + HERMES_DASHBOARD_BASIC_AUTH_PASSWORD (و HERMES_DASHBOARD_BASIC_AUTH_SECRET للحصول على جلسات تبقى بعد إعادة التشغيل). غير مناسبة للإتاحة المباشرة على الإنترنت العام.
      • OAuth (Nous Portal) — لعمليات النشر المستضافة/العامة: يُفعَّل المزوّد dashboard_auth/nous كلما ضُبط HERMES_DASHBOARD_OAUTH_CLIENT_ID.
      • OIDC مستضاف ذاتيًا — للمصادقة عبر مزوّد الهوية الخاص بك باستخدام OpenID Connect القياسي: يُفعَّل المزوّد dashboard_auth/self_hosted عند ضبط HERMES_DASHBOARD_OIDC_ISSUER + HERMES_DASHBOARD_OIDC_CLIENT_ID.

      أيًّا كان اختيارك، تُعيد البوابة توجيه الطالبين إلى صفحة تسجيل الدخول قبل أن يتمكنوا من الوصول إلى أي مسار محمي. راجع لوحة التحكم على الويب → المصادقة للاطلاع على المزوّدين الثلاثة.

      عندما يعمل reverse proxy مثل Traefik أو nginx في حاوية أخرى، لا يكون عنوانه على شبكة bridge موثوقًا افتراضيًا. اضبط الـ URL العام للوحة التحكم، ولا تثق إلا بعنوان IP الدقيق لذلك الـ proxy، أو بنطاق CIDR محدود لشبكة proxy مخصصة، وذلك في ملف config.yaml المُركَّب:

      dashboard:
        public_url: "https://dashboard.example.com"
        trusted_proxies:
          - "172.20.0.5"
          # Or, if the proxy address is dynamic on a dedicated network:
          # - "172.20.0.0/24"

      يسمح هذا لترويسة X-Forwarded-Proto: https القادمة من الـ proxy بالتحكم في ملفات تعريف الارتباط (cookies) الآمنة الخاصة بـ OAuth، مع إبقاء ترويسات التمرير القادمة من الأطراف الأخرى غير موثوقة. لا تستخدم * أو 0.0.0.0/0 أو ::/0؛ إذ يرفض Hermes هذه القيم غير المحدودة.

      إذا لم يكن هناك مزوّد مسجّل وكان الربط بعنوان غير loopback، تفشل لوحة التحكم بشكل مغلق (fail closed) عند بدء التشغيل مع خطأ محدد يشير إلى متغير البيئة المفقود. ولم يعد هناك منفذ للهروب يُتيح تقديم لوحة التحكم دون مصادقة على عنوان عام: فقد أصبح HERMES_DASHBOARD_INSECURE=1 خيارًا مهملًا بلا أثر (يسجّل تحذيرًا ويُتجاهل). اضبط مزوّدًا، أو اربط HERMES_DASHBOARD_HOST=127.0.0.1 وصِل إلى لوحة التحكم عبر نفق SSH / Tailscale بدلًا من ذلك.

      لماذا أُزيل --insecure

      كانت لوحة التحكم العامة غير المحمية بالمصادقة نقطةَ الدخول لحملة الاستمرار (persistence) عبر إعدادات MCP في يونيو 2026: إذ وصلت أدوات المسح على الإنترنت إلى لوحات التحكم المكشوفة (وخوادم OpenAI API) ودفعت الوكيل إلى زرع باب خلفي عبر مفتاح SSH. أصبحت بوابة المصادقة الآن إلزامية على كل ربط بعنوان غير loopback. وبالنسبة إلى جهاز على شبكة محلية موثوقة / homelab، فإن مزوّد اسم المستخدم/كلمة المرور المضمّن (HERMES_DASHBOARD_BASIC_AUTH_USERNAME + _PASSWORD) هو الطريقة التي لا تتطلب أي بنية تحتية لتحقيق ذلك.

      تشغيل لوحة التحكم في حاوية منفصلة مدعوم عندما تتشارك تلك الحاوية نطاق PID ونطاق الشبكة (namespace) مع الجهاز المضيف (مثل network_mode: host، كما يفعل ملف docker-compose.yml الخاص بالمستودع — راجع خدمة dashboard فيه). إذ يتطلب كشفها لحيوية الـ gateway نطاق PID مشتركًا مع عملية الـ gateway، لذا لا ينطبق القيد إلا على لوحات التحكم التي تعمل في حاويات معزولة على شبكة bridge دون نطاق PID مشترك.

      التشغيل التفاعلي (محادثة CLI)​

      لفتح جلسة محادثة تفاعلية على مجلد بيانات قيد الاستخدام:

      docker run -it --rm \
        -v ~/.hermes:/opt/data \
        nousresearch/hermes-agent

      أو إذا كنت قد فتحت طرفية بالفعل داخل الحاوية العاملة (عبر Docker Desktop مثلًا)، فنفّذ ببساطة:

      /opt/hermes/.venv/bin/hermes

      شجرة تثبيت غير قابلة للتعديل​

      في صور Docker المستضافة والمنشورة، يمثّل /opt/hermes شجرة التطبيق المثبّت. وهي مملوكة لـ root وللقراءة فقط بالنسبة إلى مستخدم وقت التشغيل hermes، لذا لا تستطيع أدوار الوكيل وجلسات الـ gateway وإجراءات لوحة التحكم وأوامر docker exec hermes hermes ... العادية تعديل الكود المصدري الأساسي أو .venv المضمّن أو node_modules أو حزمة TUI في مكانها.

      تنتمي كل حالة Hermes القابلة للتغيير إلى /opt/data: الإعدادات، و .env، والـ profiles، والمهارات، والذكريات، والجلسات، والسجلات، وملفات لوحة التحكم المرفوعة، والإضافات، وغيرها من الملفات التي يديرها المستخدم. كما تعطّل الصورة كتابة ملفات .pyc وقت التشغيل، وعمليات التثبيت الكسول (lazy) للاعتماديات التي يجريها Hermes داخل /opt/hermes؛ لذا ينبغي تضمين اعتماديات المنصات الاختيارية التي تحتاجها الصورة المنشورة داخل الصورة مسبقًا أو تثبيتها عبر بناء صورة جديدة.

      في الصور المستضافة/المنشورة، يقتصر التحسين الذاتي للوكيل على المهارات والذاكرة والإضافات والإعدادات ضمن /opt/data. أما الكود المصدري الأساسي المثبّت ضمن /opt/hermes فغير قابل للتعديل؛ إذ تُجرى التغييرات الأساسية عبر PRs إلى المستودع وتُشحن بتحديث الصورة، لا بالتعديل المباشر على التثبيت العامل.

      إذا احتاج المشغّل إلى إصلاح ملفات خارج /opt/data أو فحصها، فاستخدم shell بصلاحيات root عن قصد. عادةً ما يُعيد الـ shim hermes تنفيذ docker exec hermes hermes ... بمستخدم وقت التشغيل؛ لذا اضبط HERMES_DOCKER_EXEC_AS_ROOT=1 لاستدعاء لمرة واحدة بصلاحيات root عندما تحتاج صراحةً إلى سلوك root.

      يجب تهيئة أدوات CLI الخاصة بالمهارات التي تخزّن بيانات الاعتماد ضمن ~ باستخدام مجلد HOME الخاص بالعمليات الفرعية، لا جذر volume البيانات فقط. فعلى سبيل المثال، تخزّن مهارة xurl حالة OAuth في ~/.xurl؛ وفي تخطيط Docker الرسمي، تقرأ استدعاءات أدوات Hermes هذا المسار على أنه /opt/data/home/.xurl، لذا نفّذ مصادقة xurl اليدوية مع HOME=/opt/data/home وتحقّق منها باستخدام HOME=/opt/data/home xurl auth status.

      تحذير

      لا تشغّل أبدًا حاويتي gateway لـ Hermes على مجلد البيانات نفسه في وقت واحد — فملفات الجلسات ومخازن الذاكرة غير مصممة للكتابة المتزامنة.

      دعم عدة Profiles​

      يدعم Hermes عدة profiles — وهي مجلدات فرعية منفصلة ضمن ~/.hermes/ تتيح لك تشغيل وكلاء مستقلين (بـ SOUL ومهارات وذاكرة وجلسات وبيانات اعتماد مختلفة) من تثبيت واحد. داخل صورة Docker الرسمية، تتعامل شجرة الإشراف في s6 مع كل profile كخدمة خاضعة للإشراف من الدرجة الأولى، لذا فإن النشر المُوصى به هو حاوية واحدة تستضيف جميع الـ profiles.

      يحصل كل profile يُنشأ باستخدام hermes profile create <name> على:

      • خانة خدمة s6 مخصصة في /run/service/gateway-<name>/، يسجّلها وقت التشغيل ديناميكيًا — دون الحاجة إلى إعادة بناء الحاوية.
      • إعادة تشغيل تلقائية عند الانهيار، مع إدارة فترات الانتظار (backoff) بواسطة s6-supervise.
      • سجلات دوّارة لكل profile في ${HERMES_HOME}/logs/gateways/<name>/current (10 أرشيفات × 1 MB لكل منها).
      • استمرار الحالة عبر عمليات إعادة تشغيل الحاوية: يقرأ الـ reconciler وقت الإقلاع ملف gateway_state.json من مجلد كل profile ولا يعيد تشغيل الخانة إلا للـ profiles التي كانت آخر حالة مسجّلة لها running. ولا يبقى متوقفًا بعد إعادة التشغيل إلا الـ gateway الذي أوقفته صراحةً (hermes gateway stop) — أما إعادة تشغيل الحاوية أو ترقية الصورة أو الخروج غير المتوقع فتُبقي الحالة المسجّلة running، فيبدأ الـ gateway تلقائيًا في الإقلاع التالي.

      تعمل أوامر دورة الحياة التي تشغّلها على الجهاز المضيف بالطريقة نفسها من داخل الحاوية:

      # Create a profile — registers the gateway-<name> s6 slot.
      docker exec hermes hermes profile create coder

      # Start / stop / restart — dispatches s6-svc; the gateway lifecycle survives docker restart.
      docker exec hermes hermes -p coder gateway start
      docker exec hermes hermes -p coder gateway stop
      docker exec hermes hermes -p coder gateway restart

      # Status — reports `Manager: s6 (container supervisor)` inside the container.
      docker exec hermes hermes -p coder gateway status

      # Remove a profile — tears down the s6 slot too.
      docker exec hermes hermes profile delete coder

      في الخلفية، يُعترض hermes gateway start/stop/restart داخل الحاوية ويُوجَّه إلى s6-svc على مجلد الخدمة الصحيح؛ فلا تحتاج إلى تعلّم أوامر s6 مباشرةً. وللاطلاع على الحالة الخام للمشرف، استخدم /command/s6-svstat /run/service/gateway-<name> (لاحظ أن /command/ لا يكون ضمن PATH إلا للعمليات التي تُطلقها شجرة الإشراف — لذا عند الاستدعاء من docker exec، مرّر المسار المطلق).

      الوصول إلى أكثر من profile من خارج الحاوية​

      هناك واجهتان مختلفتان تصلان إلى الـ gateway الخاص بـ profile من الخارج، وتتصرفان بشكل مختلف — فلا تخلط بينهما:

      Hermes Desktop (ولوحة التحكم على الويب). يتواصل اتصال Remote Gateway في تطبيق Desktop مع backend من نوع hermes dashboard (افتراضيًا على المنفذ 9119، ويُفعَّل عبر HERMES_DASHBOARD=1) — وليس مع خادم OpenAI API. يخدم backend واحد للوحة التحكم كل الـ profiles الموجودة معه على الجهاز نفسه: إذ يرسل مبدّل الـ profiles في التطبيق الـ profile الهدف مع كل طلب، ويفتح الـ backend مجلد HERMES_HOME الخاص بذلك الـ profile على القرص. لذا لا تحتاج إلى منفذ ثانٍ — أو اتصال ثانٍ — لكل profile في Desktop؛ فاتصال واحد على :9119 يغطيها جميعًا عبر المبدّل.

      عملاء API المتوافقون مع OpenAI (Open WebUI و LobeChat و /v1/...). يتواصل هؤلاء مع خادم API الخاص بكل profile، والذي يرتبط بالمنفذ 8642 لكل profile (تُحدَّد القيمة من API_SERVER_PORT / platforms.api_server.extra.port — فلا يوجد تخصيص تلقائي ولا مفتاح config.yaml/gateway.port). إذا أردت أن يصل عميل إلى profile ثانٍ محدد، فامنح ذلك الـ profile قيمة API_SERVER_PORT مميزة في ملف البيئة الخاص به (.env)، وإلا فسيحاول الـ gateway الخاص به الارتباط بالمنفذ 8642 أيضًا ويتعارض مع الـ profile الافتراضي:

      # Create the profile (registers its gateway-<name> s6 slot)
      docker exec hermes hermes profile create work

      # Point its API server at a free port (write to the profile's own .env)
      cat >> /opt/data/profiles/work/.env <<'EOF'
      API_SERVER_ENABLED=true
      API_SERVER_PORT=8643
      EOF

      docker exec hermes hermes -p work gateway restart

      أبقِ API_SERVER_PORT في ملف البيئة الخاص بكل profile (.env)، ولا تضعه أبدًا في كتلة environment: على مستوى الحاوية — فالقيمة العامة ستفرض المنفذ نفسه على كل الـ profiles فتتصادم. ومع شبكات bridge، انشر المنفذ الإضافي في docker-compose.yml (- "8643:8643")؛ أما مع network_mode: host فهو قابل للوصول بالفعل على الجهاز المضيف. ولا يتأثر اتصال الـ profile الافتراضي على المنفذ 8642.

      لماذا حاوية واحدة بعدة profiles بدلًا من عدة حاويات​

      قبل الانتقال إلى s6، كان نمط "حاوية واحدة لكل profile" هو المُوصى به لعدم وجود مشرف داخل الحاوية لإدارة عدة gateways. أما مع s6 بوصفه PID 1، فلم يعد ذلك ضروريًا، وصار تخطيط الحاوية الواحدة أبسط من كل النواحي تقريبًا:

      يُسجَّل الـ profile الافتراضي (default) دائمًا عند أول إقلاع، لذا تأتي الحاوية الجديدة مع gateway واحد خاضع للإشراف جاهز للعمل مباشرةً. أما الـ profiles الإضافية فتُضاف بالكامل وقت التشغيل.

      متى تحتاج فعلًا إلى حاوية منفصلة​

      النمط الافتراضي هو تشغيل الـ profiles داخل الحاوية الواحدة. لا تشغّل حاوية منفصلة لكل profile إلا عندما يكون لديك سبب محدد:

      • عزل الموارد لكل عبء عمل — مثلًا، لا ينبغي لجلسة أداة متصفح خرجت عن السيطرة في الـ profile A أن تتسبب في نفاد ذاكرة (OOM) الـ profile B. وتمنحك الحاويات --memory / --cpus لكل profile.
      • تثبيت مستقل لإصدار الصورة — وسوم (tags) مختلفة للصورة الأصلية (upstream) لكل عبء عمل.
      • تقسيم الشبكة — شبكات Docker منفصلة لكل profile (مثل واحدة موجّهة للعملاء وأخرى داخلية).
      • الامتثال / نطاق الضرر — لا تتشارك بيانات الاعتماد المختلفة أبدًا شجرة عمليات واحدة على مستوى نظام التشغيل.

      في هذه الحالات، عرّف خدمة واحدة لكل profile بقيم مختلفة لـ container_name و volumes و ports:

      services:
        hermes-work:
          image: nousresearch/hermes-agent:latest
          container_name: hermes-work
          restart: unless-stopped
          command: gateway run
          ports:
            - "8642:8642"
          volumes:
            - ~/.hermes-work:/opt/data

        hermes-personal:
          image: nousresearch/hermes-agent:latest
          container_name: hermes-personal
          restart: unless-stopped
          command: gateway run
          ports:
            - "8643:8642"
          volumes:
            - ~/.hermes-personal:/opt/data

      يظل التحذير الوارد في الـ volumes الدائمة ساريًا: لا توجّه أبدًا حاويتين إلى مجلد ~/.hermes نفسه في وقت واحد. فمشرف s6 داخل كل حاوية يدير مجموعة الـ profiles الخاصة به؛ ومشاركة volume البيانات بين الحاويات تُفسد ملفات الجلسات ومخازن الذاكرة.

      أين تذهب السجلات​

      تحتوي حاوية s6 على أربعة مصادر مختلفة للسجلات، وسؤال "لماذا لا يُظهر الـ gateway أي شيء في docker logs" مفاجأة شائعة. إليك ملخصًا سريعًا:

      المصدرأين تُكتبكيفية قراءتها
      gateway لكل profile (hermes gateway run والـ gateways الخاصة بكل profile تحت s6)تُنسخ (tee) إلى مكانين: docker logs <container> (في الوقت الفعلي، دون بادئة إضافية) و ${HERMES_HOME}/logs/gateways/<profile>/current (دوّار، مع طوابع زمنية بصيغة ISO-8601، و10 أرشيفات × 1 MB لكل منها)docker logs -f hermes أو tail -F ~/.hermes/logs/gateways/default/current على الجهاز المضيف
      لوحة التحكم (عند ضبط HERMES_DASHBOARD=1)docker logs <container> (دون بادئة)docker logs -f hermes — متداخلة مع أسطر الـ gateway
      Boot reconciler (يسجّل الـ gateways الخاصة بالـ profiles التي استُعيدت عند كل بدء تشغيل للحاوية)${HERMES_HOME}/logs/container-boot.log (سجل تدقيق يُضاف إليه فقط)tail -F ~/.hermes/logs/container-boot.log
      سجلات Hermes العامة (agent.log، errors.log)${HERMES_HOME}/logs/ (تراعي الـ profile)docker exec hermes hermes logs --follow [--level WARNING] [--session <id>]

      نتيجتان عمليتان ينبغي معرفتهما:

      • النسخة المحفوظة في الملف logs/gateways/<profile>/current هي ما يبقى بعد إعادة تشغيل الحاوية. إذ لا يحتفظ docker logs إلا بمخرجات عمر الحاوية الحالية (ويُمسح عند docker rm)؛ بينما تبقى الملفات الدوّارة على الـ volume المُركَّب عبر bind-mount.
      • شكل سطر التدقيق الذي يكتبه boot reconciler هو <iso-timestamp> profile=<name> prior_state=<state> action=<registered|started>، لذا فإن تنفيذ grep profile=coder ~/.hermes/logs/container-boot.log سريعًا يكشف متى استُعيد profile معيّن آخر مرة وما إذا كان s6 قد شغّله تلقائيًا.

      تمرير متغيرات البيئة​

      تُقرأ مفاتيح API من الملف /opt/data/.env داخل الحاوية. ويمكنك أيضًا تمرير متغيرات البيئة مباشرة:

      docker run -it --rm \
        -v ~/.hermes:/opt/data \
        -e ANTHROPIC_API_KEY="sk-ant-..." \
        -e OPENAI_API_KEY="sk-..." \
        nousresearch/hermes-agent

      تتجاوز الخيارات -e المباشرة القيم الموجودة في .env. وهذا مفيد في CI/CD أو عند التكامل مع مديري الأسرار (secrets managers) حين لا تريد حفظ المفاتيح على القرص.

      هل تبحث عن استخدام Docker بوصفه terminal backend؟

      تتناول هذه الصفحة تشغيل Hermes نفسه داخل Docker. أما إذا أردت أن ينفّذ Hermes استدعاءات terminal / execute_code الخاصة بالوكيل داخل حاوية sandbox في Docker (حاوية واحدة طويلة العمر تتشاركها عمليات Hermes — راجع issue #20561)، فذلك قسم إعدادات منفصل — terminal.backend: docker إضافة إلى terminal.docker_image و terminal.docker_volumes و terminal.docker_forward_env و terminal.docker_env و terminal.docker_run_as_host_user و terminal.docker_extra_args و terminal.docker_persist_across_processes و terminal.docker_orphan_reaper. راجع الإعدادات → Docker Backend للاطلاع على المجموعة الكاملة، بما فيها قواعد دورة حياة الحاوية.

      مثال على Docker Compose​

      للنشر الدائم الذي يشمل الـ gateway ولوحة التحكم معًا، يكون الملف docker-compose.yaml خيارًا مريحًا:

      services:
        hermes:
          image: nousresearch/hermes-agent:latest
          container_name: hermes
          restart: unless-stopped
          command: gateway run
          ports:
            - "8642:8642"   # gateway API
            - "9119:9119"   # dashboard (only reached when HERMES_DASHBOARD=1)
          volumes:
            - ~/.hermes:/opt/data
          environment:
            - HERMES_DASHBOARD=1
            # Uncomment to forward specific env vars instead of using .env file:
            # - ANTHROPIC_API_KEY=${ANTHROPIC_API_KEY}
            # - OPENAI_API_KEY=${OPENAI_API_KEY}
            # - TELEGRAM_BOT_TOKEN=${TELEGRAM_BOT_TOKEN}
          deploy:
            resources:
              limits:
                memory: 4G
                cpus: "2.0"

      ابدأ التشغيل بالأمر docker compose up -d واعرض السجلات بالأمر docker compose logs -f. كما يُنسخ خرج stdout للـ gateway الخاضع للإشراف (عبر tee) إلى ${HERMES_HOME}/logs/gateways/<profile>/current على وحدة التخزين (volume) — راجع أين تذهب السجلات للاطلاع على خريطة التوجيه الكاملة.

      اختياري: جسر الصوت لسطح مكتب Linux​

      يحتاج الوضع الصوتي داخل Docker إلى أمرين منفصلين كي يعمل: يجب السماح لـ Hermes بفحص أجهزة الصوت داخل الحاوية، ويجب أن تتمكن الحاوية من الوصول إلى خادم الصوت على جهازك المضيف. يغطي الإعداد أدناه توصيلات الصوت على المضيف لأسطح مكتب Linux التي توفّر socket متوافقًا مع PulseAudio، بما في ذلك كثير من إعدادات PipeWire.

      تنبيه

      هذا حلّ بديل خاص بأسطح مكتب Linux، وليس ميزة عامة في Docker Desktop. وهو مفيد حين يكون الصوت يعمل لديك على المضيف وتريد استخدام الوضع الصوتي في CLI داخل حاوية Hermes. إذا ظل Hermes يعرض الرسالة Running inside Docker container -- no audio devices، فاستخدم إصدارًا يتضمن دعم فحص الصوت داخل Docker عبر PULSE_SERVER / PIPEWIRE_REMOTE.

      أولًا، أنشئ ملف إعدادات ALSA بجوار ملف Compose:

      asound.conf
      pcm.!default {
          type pulse
          hint {
              show on
              description "Default ALSA Output (PulseAudio)"
          }
      }

      pcm.pulse {
          type pulse
      }

      ctl.!default {
          type pulse
      }

      ثم ابنِ صورة مشتقة صغيرة مثبّتًا فيها plugin PulseAudio الخاص بـ ALSA:

      Dockerfile.audio
      FROM nousresearch/hermes-agent:latest

      USER root
      RUN apt-get update \
          && apt-get install -y --no-install-recommends libasound2-plugins \
          && rm -rf /var/lib/apt/lists/*

      استخدم تلك الصورة في Compose، ومرّر socket PulseAudio وملف cookie الخاصين بمستخدم المضيف:

      services:
        hermes:
          build:
            context: .
            dockerfile: Dockerfile.audio
          image: hermes-agent-audio
          container_name: hermes
          restart: unless-stopped
          command: gateway run
          volumes:
            - ~/.hermes:/opt/data
            - /run/user/${HERMES_UID}/pulse:/run/user/${HERMES_UID}/pulse
            - ~/.config/pulse/cookie:/tmp/pulse-cookie:ro
            - ./asound.conf:/etc/asound.conf:ro
          environment:
            - HERMES_UID=${HERMES_UID}
            - HERMES_GID=${HERMES_GID}
            - XDG_RUNTIME_DIR=/run/user/${HERMES_UID}
            - PULSE_SERVER=unix:/run/user/${HERMES_UID}/pulse/native
            - PULSE_COOKIE=/tmp/pulse-cookie

      شغّلها باستخدام UID/GID الخاصين بالمضيف كي تتمكن عملية الحاوية من الوصول إلى socket الصوت الخاص بكل مستخدم:

      export HERMES_UID="$(id -u)"
      export HERMES_GID="$(id -g)"
      docker compose up -d --build

      للتحقق مما يراه PortAudio داخل الحاوية:

      docker exec hermes /opt/hermes/.venv/bin/python -c "import sounddevice as sd; print(sd.query_devices())"

        -v ~/.hermes:/opt/data \
        nousresearch/hermes-agent gateway run

      ما الذي يفعله Dockerfile​

      تستند الصورة الرسمية إلى debian:13.4 وتتضمن:

      • Python 3.13 مع اعتماديات تُزامَن من ملف القفل (lockfile) عبر uv sync --frozen --no-install-project للإضافات (extras) المُدمجة في الصورة (all، messaging، وهوية Anthropic/Bedrock/Azure، و Hindsight، و Matrix)، يليها تثبيت قابل للتعديل (editable) لـ Hermes نفسه دون اعتماديات.
      • Node.js 26 + npm (لأتمتة المتصفح، وجسر WhatsApp، وحِزم TUI/Desktop، وأدوات بناء مساحة العمل)
      • Playwright مع Chromium (npx playwright install --with-deps chromium --only-shell)
      • ripgrep و ffmpeg و git و xz-utils كأدوات نظام
      • docker-cli — كي تتمكن الوكلاء العاملة داخل الحاوية من التحكم في Docker daemon على المضيف (اربط /var/run/docker.sock عبر bind-mount لتفعيل ذلك) لتنفيذ docker build و docker run وفحص الحاويات وغير ذلك.
      • openssh-client — يتيح استخدام SSH terminal backend من داخل الحاوية. إذ يستدعي SSH backend الملف التنفيذي ssh الخاص بالنظام؛ وبدونه كان يفشل بصمت في عمليات التثبيت داخل الحاويات.
      • جسر WhatsApp (scripts/whatsapp-bridge/)
      • s6-overlay v3 بوصفه PID 1 (بديلًا عن tini الأقدم) — يشرف على لوحة التحكم و gateways الخاصة بكل profile مع إعادة تشغيلها تلقائيًا عند الانهيار، ويحصد العمليات الفرعية الزومبي (zombie)، ويمرّر الإشارات (signals).

      تتعامل الصورة مع /opt/hermes بوصفه شجرة تثبيت غير قابلة للتغيير وقت التشغيل. يجب تضمين إضافات Python (extras) الاختيارية ومساحات عمل Node وأصول TUI التي يلزم توفرها داخل Docker أثناء بناء الصورة؛ فعمليات التثبيت الكسول (lazy installs) وقت التشغيل معطّلة، كي لا تحاول الـ gateways الخاضعة للإشراف وأوامر docker exec hermes … كتابة ملفات الاعتماديات في شجرة المصدر المخصصة للقراءة فقط.

      نقطة الدخول ENTRYPOINT للحاوية هي موزّع صغير (docker/entrypoint-dispatch.sh). عندما تمتلك الحاوية PID 1 (في Docker / Podman العاديين)، يُنفّذ (exec) الملف /init الخاص بـ s6-overlay فتحصل على شجرة الإشراف الكاملة الموضحة أدناه. أما عندما تغلّف منصةٌ ما نقطة دخول الصورة داخل نظام init خاص بها يعمل كـ PID 1 (مثل Fly.io Machines، و docker run --init، وبعض إعدادات Nomad/Kubernetes)، فإن /init سيتوقف مع الخطأ s6-overlay-suexec: fatal: can only run as pid 1 — ولذلك يشغّل الموزّع بدلًا من ذلك تهيئة stage2 مباشرة ثم ينفّذ الـ wrapper الرئيسي دون s6. في هذا المسار الاحتياطي يظل الأمر المطلوب يعمل، لكن الخدمات الخاضعة للإشراف (لوحة التحكم، و gateways الخاصة بكل profile) لا تكون متاحة.

      في مسار PID 1، يقوم /init بما يلي:

      1. يشغّل /etc/cont-init.d/01-hermes-setup (= docker/stage2-hook.sh) بصلاحيات root: إعادة تعيين UID/GID اختياريًا، وإصلاح ملكية وحدة التخزين، وإنشاء .env / config.yaml / SOUL.md الأولية عند الإقلاع الأول، وتشغيل ترحيلات مخطط الإعدادات (config-schema migrations) غير التفاعلية ما لم يُضبط HERMES_SKIP_CONFIG_MIGRATION=1، ومزامنة المهارات المضمّنة.
      2. يشغّل /etc/cont-init.d/02-reconcile-profiles (= hermes_cli.container_boot): يمرّ على $HERMES_HOME/profiles/<name>/، ويعيد إنشاء خانة خدمة s6 الخاصة بـ gateway كل profile تحت /run/service/gateway-<profile>/، ولا يشغّل تلقائيًا إلا الخدمات التي كانت آخر حالة مسجّلة لها running (راجع الإشراف على gateway لكل profile).
      3. يشغّل خدمتَي s6-rc الثابتتين main-hermes و dashboard.
      4. ينفّذ CMD الخاص بالحاوية بوصفه البرنامج الرئيسي (/opt/hermes/docker/main-wrapper.sh)، والذي يوجّه الوسائط التي مرّرها المستخدم إلى docker run:
        • بلا وسائط → hermes (الافتراضي)
        • الوسيط الأول ملف تنفيذي موجود في PATH (مثل sleep أو bash) → يُنفَّذ مباشرة
        • أي شيء آخر → hermes <args> (تمرير الأمر الفرعي) تنتهي الحاوية عندما ينتهي هذا البرنامج الرئيسي، وبرمز الخروج نفسه.
      تغيير جذري مقارنة بالصور السابقة لـ s6

      أصبحت نقطة الدخول ENTRYPOINT للحاوية هي الموزّع entrypoint-dispatch.sh (الذي يفوّض إلى /init الخاص بـ s6-overlay تحت PID 1)، وليس /usr/bin/tini. تتصرف أنماط استدعاء docker run الخمسة الموثّقة جميعها (بلا وسائط، و chat -q "…"، و sleep infinity، و bash، و --tui) بالطريقة نفسها تمامًا كما في الصورة المعتمدة على tini. إذا كان لديك wrapper لاحق يعتمد على سلوك الإشارات الخاص بـ tini أو يستدعي /usr/bin/tini -- بشكل ثابت في الكود، فثبّت وسم الصورة السابق.

      نموذج الصلاحيات

      لا تتجاوز نقطة دخول الصورة إلا إذا أبقيت /init (أو ما يعادله، أي الـ shim القديم docker/entrypoint.sh الذي يمرّر إلى stage2 hook) ضمن سلسلة الأوامر. يعمل /init الخاص بـ s6-overlay بصلاحيات root كي يتمكن من تغيير ملكية وحدة التخزين (chown) عند الإقلاع الأول، ثم ينتقل إلى المستخدم hermes عبر s6-setuidgid لكل خدمة خاضعة للإشراف وللبرنامج الرئيسي أيضًا. يُرفض افتراضيًا تشغيل hermes gateway run بصلاحيات root داخل الصورة الرسمية، لأنه قد يترك ملفات مملوكة لـ root في /opt/data ويعطّل عمليات تشغيل لوحة التحكم أو الـ gateway لاحقًا. لا تضبط HERMES_ALLOW_ROOT_GATEWAY=1 إلا إذا كنت تقبل هذا الخطر عن قصد.

      ينتقل docker exec تلقائيًا إلى المستخدم hermes​

      يعمل docker exec hermes <cmd> افتراضيًا بصلاحيات root داخل الحاوية، لكن الصورة تتضمن shim خفيفًا في /opt/hermes/bin/hermes (الأسبق في PATH) يكتشف المستدعين بصلاحيات root ويعيد تنفيذ الأمر بشفافية عبر s6-setuidgid hermes. لذلك فإن docker exec hermes login و docker exec hermes profile create … و docker exec hermes setup وغيرها تكتب جميعها ملفات مملوكة لـ UID 10000 — أي قابلة للقراءة من الـ gateway الخاضع للإشراف — دون الحاجة إلى خيار --user إضافي. أما المستدعون من غير root (العمليات الخاضعة للإشراف نفسها، و docker exec --user hermes، و kanban subagents داخل الحاوية) فيمرّون عبر مسار مختصر ينفّذ الملف التنفيذي الموجود في الـ venv مباشرة، فلا يوجد أي عبء إضافي على المسارات الأكثر استخدامًا.

      إذا كنت تحتاج تحديدًا إلى docker exec يحتفظ بصلاحيات root (جلسات التشخيص، أو فحص حالة لا يصل إليها إلا root، أو ملفات خارج /opt/data يصادف أنها مملوكة لـ root)، فألغِ هذا السلوك لكل استدعاء على حدة:

      docker exec -e HERMES_DOCKER_EXEC_AS_ROOT=1 hermes <cmd>

      يقبل الـ shim القيم 1 / true / yes (دون تمييز حالة الأحرف). وأي قيمة أخرى — بما في ذلك الأخطاء الإملائية مثل =0 — تؤدي إلى الانتقال للمستخدم غير الجذري، فلا يمكن إلغاء السلوك بصمت عن غير قصد. وإذا لم يكن s6-setuidgid متاحًا (في الإصدارات المخصصة التي أزالت s6-overlay)، يرفض الـ shim العمل بصلاحيات root ويخرج بالرمز 126 بدلًا من ذلك، كاشفًا عن خلل نموذج الصلاحيات بوضوح بدلًا من العودة إلى الفخ القديم الذي كان فيه docker exec hermes login يكتب auth.json بملكية root:root ويعطّل مصادقة الـ gateway الخاضع للإشراف مع كل رسالة من منصات المحادثة.

      الإشراف على gateway لكل profile​

      يحصل كل profile يُنشأ بالأمر hermes profile create <name> تلقائيًا على خدمة gateway خاضعة لإشراف s6 ومسجّلة في /run/service/gateway-<name>/، مع إعادة تشغيل تلقائية تحافظ على الحالة عبر عمليات إعادة تشغيل الحاوية. راجع دعم عدة profiles أعلاه للاطلاع على سير العمل من جهة المستخدم وأوامر دورة الحياة.

      مزايا الإشراف مقارنة بالصورة السابقة لـ s6:

      • يعيد s6-supervise تشغيل الـ gateway تلقائيًا عند انهياره بعد تأخير يقارب ثانية واحدة.
      • تخضع لوحة التحكم، عند تفعيلها بـ HERMES_DASHBOARD=1، للإشراف ضمن شجرة الإشراف نفسها وتحظى بإعادة التشغيل التلقائية ذاتها.
      • تحافظ docker restart وترقيات الصورة (docker compose up -d --force-recreate) وحالات الخروج غير المتوقعة على الـ gateways العاملة: إذ يقرأ مُسوّي cont-init الملف $HERMES_HOME/profiles/<name>/gateway_state.json ويعيد تشغيل الخانة إذا كانت آخر حالة مسجّلة running. ولا يُبقي الـ gateway متوقفًا بعد إعادة التشغيل إلا أمر صريح هو hermes gateway stop، إذ يسجّل الحالة stopped؛ أما إشارة SIGTERM التي ترسلها الحاوية/s6 عند إعادة التشغيل أو الترقية فتُعامل على أنها "لا يزال يعمل" فيُشغَّل تلقائيًا.
      • تُحفظ سجلات gateway الخاصة بكل profile تحت $HERMES_HOME/logs/gateways/<profile>/current (مع تدويرها بواسطة s6-log)، وتُلحق إجراءات المُسوّي بالملف $HERMES_HOME/logs/container-boot.log عند كل إقلاع. راجع أين تذهب السجلات للاطلاع على خريطة التوجيه الكاملة.

      يعرض hermes status داخل الحاوية Manager: s6 (container supervisor). استخدم /command/s6-svstat /run/service/gateway-<name> للحصول على عرض المشرف الخام (لاحظ أن /command/ موجود في PATH لعمليات شجرة الإشراف فقط؛ لذا مرّر المسار المطلق عند الاستدعاء من docker exec).

      الترقية​

      اسحب أحدث صورة وأعد إنشاء الحاوية. يُحفظ دليل بياناتك كما هو، وتشغّل الحاوية ترحيلات مخطط الإعدادات غير التفاعلية على الملف المركّب $HERMES_HOME/config.yaml قبل تشغيل الـ gateway. وعند الحاجة إلى ترحيل، يكتب Hermes أولًا نسخًا احتياطية مؤرخة بجوار config.yaml و .env.

      docker pull nousresearch/hermes-agent:latest
      docker rm -f hermes
      docker run -d \
        --name hermes \
        --restart unless-stopped \
        -v ~/.hermes:/opt/data \
        nousresearch/hermes-agent gateway run

      أو باستخدام Docker Compose:

      docker compose pull
      docker compose up -d

      لا تضبط HERMES_SKIP_CONFIG_MIGRATION=1 إلا إذا كنت تحتاج إلى فحص الإعدادات المحفوظة أو ترحيلها يدويًا قبل السماح للصورة الجديدة بإعادة كتابتها.

      المهارات وملفات بيانات الاعتماد​

      عند استخدام Docker بيئةً للتنفيذ (ليس بالطرق المذكورة أعلاه، بل عندما يشغّل الوكيل الأوامر داخل sandbox في Docker — راجع الإعدادات → Docker Backend)، يعيد Hermes استخدام حاوية واحدة طويلة العمر لجميع استدعاءات الأدوات، ويربط تلقائيًا (bind-mount) دليل المهارات (~/.hermes/skills/) وأي ملفات بيانات اعتماد تعلنها المهارات داخل تلك الحاوية كوحدات تخزين للقراءة فقط. تكون سكربتات المهارات وقوالبها ومراجعها متاحة داخل الـ sandbox دون إعداد يدوي، ولأن الحاوية تبقى طوال عمر عملية Hermes، فإن أي اعتماديات تثبّتها أو ملفات تكتبها تبقى متاحة لاستدعاء الأداة التالي.

      تحدث المزامنة نفسها مع SSH و Modal backends — إذ تُرفع المهارات وملفات بيانات الاعتماد عبر rsync أو Modal mount API قبل كل أمر.

      تثبيت مزيد من الأدوات في الحاوية​

      تأتي الصورة الرسمية مع مجموعة منتقاة من الأدوات (راجع ما الذي يفعله Dockerfile)، لكن ليست كل أداة قد يحتاجها الوكيل مثبّتة مسبقًا. هناك خمسة أساليب موصى بها، مرتبة تصاعديًا حسب الجهد المطلوب ومدى الديمومة.

      أدوات npm أو Python — استخدم npx أو uvx​

      لأي أداة منشورة على npm أو PyPI، اطلب من Hermes تشغيلها عبر npx (لـ npm) أو uvx (لـ Python) وأن يتذكر ذلك الأمر في ذاكرته الدائمة. وإذا كانت الأداة تحتاج إلى ملف إعدادات أو بيانات اعتماد، فاطلب منه وضعها تحت /opt/data (مثل /opt/data/<tool>/config.yaml).

      تُجلب الاعتماديات عند الطلب وتُخزَّن مؤقتًا طوال عمر الحاوية. وتبقى الإعدادات المكتوبة تحت /opt/data بعد إعادة تشغيل الحاوية لأنها موجودة في دليل المضيف المربوط عبر bind-mount. أما ذاكرة الحزم المؤقتة نفسها فيُعاد بناؤها بعد docker rm، لكن npx و uvx يعيدان جلبها بشفافية في المرة التالية التي تُشغَّل فيها الأداة.

      أدوات أخرى (حزم apt، ملفات تنفيذية) — ثبّتها واطلب تذكّرها​

      لأي شيء خارج npm أو PyPI — حزم apt، والملفات التنفيذية الجاهزة، وبيئات تشغيل اللغات غير الموجودة أصلًا في الصورة — أخبر Hermes بكيفية تثبيته (مثل apt-get update && apt-get install -y <package>) واطلب منه تذكّر أمر التثبيت. تبقى الأداة متاحة طوال ما تبقى من عمر الحاوية، وسيعيد Hermes تشغيل أمر التثبيت بعد إعادة تشغيل الحاوية عندما يحتاج إلى الأداة مجددًا.

      يناسب هذا الأسلوب الأدوات السريعة التثبيت التي تُستخدم أحيانًا. أما الأدوات التي تُستخدم باستمرار، فالأفضل لها الأسلوب التالي.

      تثبيتات دائمة — ابنِ صورة مشتقة​

      عندما يجب أن تكون الأداة متاحة فورًا عند كل تشغيل للحاوية دون تأخير لإعادة التثبيت، ابنِ صورة جديدة ترث من nousresearch/hermes-agent وتثبّت الأداة في طبقة (layer):

      FROM nousresearch/hermes-agent:latest

      USER root
      RUN apt-get update \
          && apt-get install -y --no-install-recommends <your-package> \
          && rm -rf /var/lib/apt/lists/*
      USER hermes

      ابنِها واستخدمها بدلًا من الصورة الرسمية:

      docker build -t my-hermes:latest .
      docker run -d \
        --name hermes \
        --restart unless-stopped \
        -v ~/.hermes:/opt/data \
        -p 8642:8642 \
        my-hermes:latest gateway run

      يُورَث سكربت نقطة الدخول ودلالات /opt/data دون تغيير، لذا يظل باقي هذه الصفحة منطبقًا. وتذكّر إعادة بناء الصورة عند سحب إصدار أحدث من الصورة الأصلية nousresearch/hermes-agent.

      أدوات معقدة أو حزم متعددة الخدمات — شغّل حاوية sidecar​

      للأدوات التي تأتي مع خدمتها الخاصة (قاعدة بيانات، أو خادم ويب، أو طابور رسائل، أو مزرعة متصفحات headless) أو التي تكون أثقل من أن تعيش داخل حاوية Hermes، شغّلها كحاوية منفصلة على شبكة Docker مشتركة. يصل Hermes إلى الـ sidecar عبر اسم الحاوية، بالطريقة نفسها التي يصل بها إلى خادم inference محلي (راجع الاتصال بخوادم inference المحلية).

      services:
        hermes:
          image: nousresearch/hermes-agent:latest
          container_name: hermes
          restart: unless-stopped
          command: gateway run
          ports:
            - "8642:8642"
          volumes:
            - ~/.hermes:/opt/data
          networks:
            - hermes-net

        my-tool:
          image: example/my-tool:latest
          container_name: my-tool
          restart: unless-stopped
          networks:
            - hermes-net

      networks:
        hermes-net:
          driver: bridge

      من داخل حاوية Hermes، يمكن الوصول إلى الـ sidecar على http://my-tool:<port> (أو أي بروتوكول يقدّمه). يُبقي هذا النمط دورة حياة كل خدمة وحدود مواردها ووتيرة ترقيتها مستقلة، ويتجنب تضخيم صورة Hermes باعتماديات لا تحتاجها إلا أداة واحدة.

      أدوات مفيدة على نطاق واسع — افتح issue أو pull request​

      إذا كان من المرجح أن تفيد أداةٌ ما معظم مستخدمي Hermes Agent، ففكّر في المساهمة بها في المشروع الأصلي بدلًا من الاحتفاظ بها في صورة مشتقة خاصة. افتح issue أو pull request في مستودع hermes-agent تصف فيه الأداة وحالة استخدامها. الأدوات التي تُضمَّن في الصورة الرسمية تفيد جميع المستخدمين وتُجنّبك عبء صيانة نسخة متفرعة (fork) لاحقة.

      الاتصال بخوادم inference المحلية (vLLM و Ollama وغيرها)​

      عند تشغيل Hermes في Docker بينما يعمل خادم inference لديك (vLLM أو Ollama أو text-generation-inference وغيرها) على المضيف أيضًا أو في حاوية أخرى، يتطلب إعداد الشبكة عناية إضافية.

      Docker Compose (موصى به)​

      ضع الخدمتين على شبكة Docker نفسها. هذا هو الأسلوب الأكثر موثوقية:

      services:
        vllm:
          image: vllm/vllm-openai:latest
          container_name: vllm
          command: >
            --model Qwen/Qwen2.5-7B-Instruct
            --served-model-name my-model
            --host 0.0.0.0
            --port 8000
          ports:
            - "8000:8000"
          networks:
            - hermes-net
          deploy:
            resources:
              reservations:
                devices:
                  - capabilities: [gpu]

        hermes:
          image: nousresearch/hermes-agent:latest
          container_name: hermes
          restart: unless-stopped
          command: gateway run
          ports:
            - "8642:8642"
          volumes:
            - ~/.hermes:/opt/data
          networks:
            - hermes-net

      networks:
        hermes-net:
          driver: bridge

      ثم في الملف ~/.hermes/config.yaml، استخدم اسم الحاوية كاسم للمضيف (hostname):

      model:
        provider: custom
        model: my-model
        base_url: http://vllm:8000/v1
        api_key: "none"
      نقاط أساسية
      • استخدم اسم الحاوية (vllm) كاسم للمضيف — وليس localhost أو 127.0.0.1، فهما يشيران إلى حاوية Hermes نفسها.
      • يجب أن تطابق قيمة model قيمة --served-model-name التي مرّرتها إلى vLLM.
      • اضبط api_key على أي سلسلة نصية غير فارغة (يتطلب vLLM وجود الترويسة لكنه لا يتحقق منها افتراضيًا).
      • لا تضع شرطة مائلة في نهاية base_url.

      تشغيل Docker مستقل (بدون Compose)​

      إذا كان خادم inference يعمل مباشرة على المضيف (وليس في Docker)، فاستخدم host.docker.internal على macOS/Windows، أو --network host على Linux:

      macOS / Windows:

      docker run -d \
        --name hermes \
        -v ~/.hermes:/opt/data \
        -p 8642:8642 \
        nousresearch/hermes-agent gateway run
      # config.yaml
      model:
        provider: custom
        model: my-model
        base_url: http://host.docker.internal:8000/v1
        api_key: "none"

      Linux (شبكة المضيف):

      docker run -d \
        --name hermes \
        --network host \
        -v ~/.hermes:/opt/data \
        nousresearch/hermes-agent gateway run
      # config.yaml
      model:
        provider: custom
        model: my-model
        base_url: http://127.0.0.1:8000/v1
        api_key: "none"
      مع --network host، يُتجاهل الخيار -p — إذ تُكشف جميع منافذ الحاوية مباشرة على المضيف.

      التحقق من الاتصال​

      من داخل حاوية Hermes، تأكد من إمكانية الوصول إلى خادم inference:

      docker exec hermes curl -s http://vllm:8000/v1/models

      من المفترض أن ترى استجابة JSON تسرد النموذج الذي يقدّمه الخادم. إذا فشل ذلك، فتحقق مما يلي:

      1. أن الحاويتين على شبكة Docker نفسها (docker network inspect hermes-net)
      2. أن خادم inference يستمع على 0.0.0.0، وليس 127.0.0.1
      3. أن رقم المنفذ مطابق

      Ollama​

      يعمل Ollama بالطريقة نفسها. إذا كان Ollama يعمل على المضيف، فاستخدم host.docker.internal:11434 (على macOS/Windows) أو 127.0.0.1:11434 (على Linux مع --network host). وإذا كان Ollama يعمل في حاويته الخاصة على شبكة Docker نفسها:

      model:
        provider: custom
        model: llama3
        base_url: http://ollama:11434/v1
        api_key: "none"

      استكشاف الأخطاء وإصلاحها​

      الحاوية تتوقف فور تشغيلها​

      راجع السجلات: docker logs hermes. الأسباب الشائعة:

      • ملف .env مفقود أو غير صالح — شغّل الحاوية تفاعليًا أولًا لإكمال الإعداد
      • تعارض المنافذ (ports) إذا كنت تشغّلها مع منافذ مكشوفة

      أخطاء "Permission denied"​

      يُسقط hook المرحلة stage2 في الحاوية الامتيازات إلى المستخدم غير الجذري hermes (UID 10000) عبر s6-setuidgid داخل كل خدمة خاضعة للإشراف. إذا كان المجلد ~/.hermes/ على المضيف مملوكًا لـ UID مختلف، فاضبط HERMES_UID/HERMES_GID — أو الاسمين البديلين PUID/PGID، للتوافق مع صور LinuxServer.io و NAS — ليطابقا مستخدم المضيف، أو تأكد من أن مجلد البيانات قابل للكتابة:

      chmod -R 755 ~/.hermes

      على أجهزة NAS (UGOS و Synology و unRAID) يكون مجلد البيانات عادةً bind mount مملوكًا لـ UID على المضيف لا تستطيع الحاوية تنفيذ chown عليه. اضبط PUID/PGID (أو HERMES_UID/HERMES_GID) على مستخدم المضيف هذا حتى تعمل بيئة التشغيل باسم مالك نقطة الربط بدلًا من UID 10000:

      docker run -d \
        --name hermes \
        -e PUID=1000 -e PGID=10 \
        -v /volume1/docker/hermes:/opt/data \
        nousresearch/hermes-agent gateway run

      ينتقل الأمر docker exec hermes <cmd> تلقائيًا إلى UID 10000 أيضًا — راجع قسم docker exec ينتقل تلقائيًا إلى المستخدم hermes للاطلاع على التفاصيل وطريقة إلغاء ذلك لكل استدعاء على حدة.

      مجلد البيانات المشترك يعود باستمرار إلى 0700​

      خارج الحاوية، يقفل Hermes المجلد HERMES_HOME (ومجلداته الفرعية cron/ و sessions/ و logs/ و memories/) على الوضع 0700 الخاص بالمالك فقط عند كل تشغيل. أما داخل الحاوية فيترك أوضاع المجلدات كما هي، لذا فإن bind mount المشترك مع حاوية شقيقة تعمل بـ UID مختلف (مثل واجهة ويب أو أداة لإصلاح الصلاحيات) يحتفظ بأي وضع وقوائم ACL تضبطها على المضيف. إذا أردت فرض وضع محدد للمجلد رغم ذلك، فاضبط HERMES_HOME_MODE (بالصيغة الثمانية، مثل HERMES_HOME_MODE=0755)؛ ويُطبَّق هذا داخل الحاويات أيضًا.

      خطأ "Permission denied" مع كل docker exec (مجلد التثبيت مقفل على 0700)​

      كانت الصور المبنية قبل أواخر أغسطس 2026 تعاني من خلل: عند كتابة ملف بيانات اعتماد مباشرةً تحت /opt/hermes كان هذا المجلد يُقيَّد بالوضع 0700، فيُمنع المستخدم hermes (UID 10000) من الوصول إلى شجرة التثبيت. ونتيجةً لذلك يفشل كل أمر docker exec جديد مع الخطأ Permission denied.

      يُصلح سحب صورة أحدث وإعادة إنشاء الحاوية هذه المشكلة نهائيًا (إذ يُشحن مجلد التثبيت بالوضع 0755 ولم تعد الإصدارات الحالية تقيّده). وإذا احتجت إلى استعادة حاوية قيد التشغيل في مكانها دون إعادة إنشائها:

      docker exec -u root hermes chmod 0755 /opt/hermes

      أدوات المتصفح لا تعمل​

      يحتاج Playwright إلى ذاكرة مشتركة. أضف --shm-size=1g إلى أمر تشغيل Docker:

      docker run -d \
        --name hermes \
        --shm-size=1g \
        -v ~/.hermes:/opt/data \
        nousresearch/hermes-agent gateway run

      الـ gateway لا يعيد الاتصال بعد مشكلات الشبكة​

      يتعامل الخيار --restart unless-stopped مع معظم الأعطال العابرة. إذا علق الـ gateway، فأعد تشغيل الحاوية:

      docker restart hermes

      التحقق من سلامة الحاوية​

      docker logs --tail 50 hermes          # Recent logs
      docker run -it --rm nousresearch/hermes-agent:latest version     # Verify version
      docker stats hermes                    # Resource usage

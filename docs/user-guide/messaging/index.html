      Messaging Gateway

      تحدث مع Hermes من Telegram أو Discord أو Slack أو WhatsApp أو Signal أو SMS أو Email أو Home Assistant أو Mattermost أو Matrix أو DingTalk أو Feishu/Lark أو WeCom أو Weixin أو BlueBubbles (iMessage) أو QQ أو Yuanbao أو Microsoft Teams أو LINE أو ntfy، أو من متصفحك. الـ gateway عبارة عن عملية خلفية واحدة تتصل بكل منصاتك المُعدّة، وتدير الجلسات، وتشغّل مهام cron، وتسلّم الرسائل الصوتية.

      لمجموعة ميزات الصوت كاملة — بما في ذلك وضع الميكروفون في CLI، والردود المنطوقة في المراسلة، والمحادثات الصوتية في Discord — راجع الوضع الصوتي (Voice Mode) واستخدام Voice Mode مع Hermes.

      نصيحة

      تحتاج البوتات إلى مزوّد نموذج ومزوّدي أدوات (TTS، الويب) معًا. يجمع اشتراك Nous Portal بينهما جميعًا.

      حالة المراسلة في Desktop ولوحة التحكم​

      تنتمي حالة المراسلة إلى الـ profile المحدد على الجهاز المحدد. يمكن لبيانات الاعتماد المحفوظة عبر hermes gateway setup تفعيل منصة تعتمد على بيانات الاعتماد دون وجود إدخال platforms في config.yaml؛ أما platforms.<name>.enabled: false الصريح فيظل يعطّلها. لا يرث profile مختلف أبدًا بيانات اعتماد عملية الخادم. المنصات التي تفتقر إلى حقول بيانات الاعتماد المطلوبة لا تُفعَّل لمجرد أن تلك القائمة فارغة.

      تسمية profile الخادم نفسه صراحةً (مثل profile=default على خادم بـ profile افتراضي) تعطي نفس حالة الطلب غير المحدد النطاق. تعني Saved أن بيانات الاعتماد مخزّنة، لا أن messaging gateway يعمل أو أن المنصة متصلة. يمكن أن تُظهر منصة مفعّلة بشكل صحيح Messaging gateway stopped.

      Hermes Relay

      Hermes Relay (تجريبي) ليس منصة محادثة بحد ذاته — بل هو نظام موصلات (connector) يقف أمام منصات مثل Discord وTelegram وSlack وWhatsApp عبر موصل خارجي يملك بيانات اعتماد المنصة. تُتفاوض القدرات (الوسائط، مطالبات الموافقة/الاستيضاح الأصلية، التفاعلات، Threads، الكتابة، Streaming) لكل موصل عند المصافحة (handshake) بدلًا من أن تكون ثابتة كما في الجدول أعلاه.

      البنية المعمارية​

      يستقبل كل platform adapter الرسائل، ويوجّهها عبر مخزن جلسات لكل محادثة، ثم يرسلها إلى AIAgent للمعالجة. يشغّل الـ gateway أيضًا جدولة cron، بمعدل نبضة كل 60 ثانية لتنفيذ أي مهام مستحقة.

      رموز الصمت المتعمد (Intentional Silence Tokens)​

      في المحادثات الجماعية والـ hooks وتدفقات الأتمتة، يدعم Hermes رموز صمت صريحة. إذا كانت الاستجابة النهائية للوكيل هي بالضبط أحد الرموز المدعومة، يوقف الـ gateway التسليم الصادر ولا يرسل شيئًا إلى المحادثة.

      الرموز المدعومة:

      • [SILENT]
      • SILENT
      • NO_REPLY
      • NO REPLY

      تُطبَّع المسافات البيضاء وحالة الأحرف، لكن يجب أن تكون الاستجابة النهائية بأكملها هي الرمز نفسه. جملة مثل "استخدم [SILENT] عندما لا يتغيّر شيء" تُسلَّم بشكل طبيعي.

      الصمت قرار تسليم فقط. يحتفظ Hermes بدور صمت المساعد في نص الجلسة، بحيث تظل المحادثة تتناوب بشكل طبيعي:

      user: side-channel chatter
      assistant: [SILENT]   # stored, not delivered
      user: next message

      لا تزال الأدوار الفاشلة تظهر كأخطاء؛ لا يخفي Hermes الإخفاقات لمجرد أن النص يشبه رمز صمت.

      الإعداد السريع​

      أسهل طريقة لإعداد منصات المراسلة هي المعالج التفاعلي:

      hermes gateway setup        # Interactive setup for all messaging platforms

      يرشدك هذا المعالج خلال إعداد كل منصة بتحديد باستخدام مفاتيح الأسهم، ويعرض المنصات المُعدّة مسبقًا، ويعرض عليك تشغيل أو إعادة تشغيل الـ gateway عند الانتهاء.

      أوامر Gateway​

      hermes gateway              # Run in foreground
      hermes gateway setup        # Configure messaging platforms interactively
      hermes gateway install      # Install as a user service (Linux) / launchd service (macOS)
      sudo hermes gateway install --system   # Linux only: install a boot-time system service
      hermes gateway start        # Start the default service
      hermes gateway stop         # Stop the default service
      hermes gateway status       # Check default service status
      hermes gateway status --system         # Linux only: inspect the system service explicitly

      مراقب حلقة الأحداث الاختياري في Linux (event-loop watchdog)​

      يمكن لـ gateway تديره systemd أن يفعّل استرداد العملية عند توقف حلقة أحداث asyncio في Python عن تلقّي وقت الجدولة. يغطي هذا حالات التجمّد الكامل للعملية التي تمنع أيضًا مهام فحص الحيوية (liveness) الخاصة بالمنصات من العمل:

      ~/.hermes/config.yaml
      gateway:
        systemd_watchdog_seconds: 120

      أعد توليد وحدة الخدمة (service unit) بعد تغيير هذا الإعداد:

      hermes gateway install --force

      القيمة الموجبة تجعل الوحدة المُولَّدة تستخدم Type=notify، وNotifyAccess=main، وWatchdogSec المطابقة. يرسل Hermes نبضات (heartbeats) فقط بينما تُحرز حلقة أحداثه تقدمًا في الوقت المناسب؛ يعيد systemd تشغيل العملية عند توقفها. القيمة الافتراضية 0 تُبقي سلوك Type=simple الحالي. هذا الإعداد خاص بـ Linux/systemd فقط ولا يعامل انقطاع شبكة عادي في إحدى المنصات كفشل في حلقة الأحداث.

      إدارة الجلسات​

      استمرارية الجلسة​

      تستمر الجلسات عبر الرسائل حتى يُعاد ضبطها. يتذكر الوكيل سياق محادثتك.

      العثور على الجلسات السابقة (/sessions)​

      يعرض /sessions جلساتك السابقة للمحادثة الحالية — بما في ذلك الجلسة التي أنت فيها الآن، والمُعلّمة بـ (current) — بينما تستأنف /sessions <name> إحداها (اختصار لـ /resume). عندما تطول القائمة، تُصفّي /sessions search <query> (بالاسم البديل find) حسب تطابق العنوان أو معرّف الجلسة، مرتبةً بحسب الأحدث نشاطًا. عرض الجلسات عبر مصادر مختلفة بـ /sessions all مقتصر على admin فقط — يتلقى المستخدمون العاديون إشعارًا يوضح أن القائمة بقيت مقتصرة على نطاق المحادثة، ولا يرون أبدًا سوى جلسات من مصدر محادثتهم الخاص.

      تجاوزات /model الدائمة​

      يُطبَّق تبديل /model في محادثة gateway على تلك الجلسة، وهو الآن يبقى بعد إعادة تشغيل الـ gateway: يُحفظ اختيار النموذج/المزوّد في مخزن الجلسة ويُستعاد عند أول استخدام بعد إعادة التشغيل (تُعاد معالجة بيانات الاعتماد وقت التحميل ولا تُكتب أبدًا على القرص). يمسح /new (أو /reset) هذا التجاوز، بينما تكتب /model <name> --global القيمة مباشرة إلى config.yaml. تُطبَّق /model <name> --once على دور واحد فقط.

      موثوقية التسليم​

      تُسجَّل استجابات الوكيل النهائية في دفتر تسليم (delivery ledger) دائم (state.db) حول كل عملية إرسال لمنصة. إذا تعطّل الـ gateway أو أعاد التشغيل بين إنتاج استجابة وتأكيد المنصة استلامها، فإن الإقلاع التالي يعيد تسليم الاستجابة المخزّنة بدلًا من فقدانها — أو إعادة تشغيل الدور بأكمله.

      الدلالات صادقة من نوع at-least-once:

      • الاستجابة التي لم يبدأ إرسالها أبدًا تُعاد تسليمها كما هي.
      • الاستجابة التي كانت قيد الإرسال عند توقف الـ gateway (وقد تكون المنصة استلمتها أو لا) تُعاد تسليمها مع بادئة ظاهرة "♻️ Recovered reply — … may be a duplicate". الغموض يُوسَم بوضوح، ولا يُعاد إرساله بصمت أبدًا.
      • الإرسال النهائي الذي ترفضه ضوابط الفيضان (flood control) (مثل حدود معدل Telegram) يُعاد المحاولة تلقائيًا بعد انتهاء الجزاء المسجّل، دون الحاجة إلى إعادة اتصال أو إعادة تشغيل. تعتمد إعادة التشغيل أثناء الجزاء الرد المخزّن دون استهلاك محاولة إعادة أو إعادة تشغيل الوكيل. تحتفظ إعادة المحاولة بملف البوت والمحادثة والمسار الفرعي الأصليين. تحذّر بادئة استرداد حدّ المعدل من أن أجزاء سابقة قد تكون وصلت بالفعل؛ لا يستطيع الدفتر استنتاج التسليم الجزئي من طول الرسالة.
      • إعادة التسليم محدودة: 3 محاولات، وحدّ نضارة 24 ساعة، ثم يُهجر السجل. تُحذف السجلات المُسلَّمة بعد 7 أيام.

      عطّل هذا عبر gateway.delivery_ledger: false في config.yaml (يعيد السلوك القديم: تُفقد الاستجابات قيد التنفيذ عند التعطل).

      استمرارية الجلسة​

      لا تُعاد ضبط محادثات الـ gateway بعد فترة خمول أو عند حد يومي. استخدم /new أو /reset لبدء محادثة جديدة صراحةً؛ يظل ضغط السياق تلقائيًا. تُتجاهل إعدادات session_reset القديمة، وتجاوزات سياسة إعادة الضبط، ومتغيرات بيئة مؤقّت إعادة الضبط. يمكن تحرير الوكلاء المخزّنين مؤقتًا لاستعادة الموارد دون استبدال المحادثة الدائمة. حدود نضارة استرداد إعادة التشغيل تحدّ من الاستمرار التلقائي فقط، لا من السجل الذي يُحمَّل عند إرسالك رسالة.

      تجاوزات النموذج و system prompt لكل قناة​

      يمكن لقنوات مختلفة تشغيل نماذج وشخصيات مختلفة من gateway واحد — مثلًا نموذج سريع ورخيص في #daily ونموذج متقدم بـ prompt متخصص في #dev. اضبط channel_overrides تحت المنصة في ~/.hermes/config.yaml:

      platforms:
        discord:
          enabled: true
          channel_overrides:
            "123456789012345678":        # channel/thread id
              model: anthropic/claude-sonnet-4.6
              provider: anthropic
              system_prompt: "You are the #dev channel code-review specialist."
            "987654321098765432":
              model: openai/gpt-5-mini

      تفاصيل:

      • المفاتيح الثلاثة جميعها اختيارية — اضبط model فقط، أو system_prompt فقط، أو أي مزيج منهما. الحقول غير المضبوطة تعود إلى القيم الافتراضية العامة.
      • ترتيب البحث هو معرّف القناة/المسار الفرعي الدقيق أولًا، ثم معرّف القناة/المنتدى الأصل (parent) — بحيث ترث مسارات Discord الفرعية تجاوز قناتها الأصل تلقائيًا.
      • أولوية تحديد النموذج هي: تجاوز /model للجلسة ← channel_overrides ← الإعدادات العامة. المستخدم الذي يشغّل /model في محادثة يظل له الأولوية على افتراضي القناة.
      • يستبدل تجاوز system_prompt prompt الـ gateway العام لتلك القناة (وهو مؤقت — يُحقَن في كل دور، ولا يُخزَّن في السجل).

      الاقتران عبر DM (بديل لقوائم السماح)​

      بدلًا من إعداد معرّفات المستخدمين يدويًا، يتلقى المستخدمون غير المعروفين رمز اقتران لمرة واحدة عند مراسلة البوت مباشرة (DM). البريد الإلكتروني هو الاستثناء: يُتجاهل مرسلو البريد الإلكتروني غير المعروفين ما لم يُفعَّل الاقتران عبر البريد الإلكتروني صراحةً.

      # The user sees: "Pairing code: XKGH5N7P"
      # You approve them with:
      hermes pairing approve telegram XKGH5N7P

      # Other pairing commands:
      hermes pairing list          # View pending + approved users
      hermes pairing revoke telegram 123456789  # Remove access

      تنتهي صلاحية رموز الاقتران بعد ساعة واحدة، وهي محدودة المعدل، وتستخدم عشوائية تشفيرية.

      المديرون (Admins) مقابل المستخدمين العاديين​

      تجيب قوائم السماح عن سؤال "هل يستطيع هذا الشخص الوصول إلى البوت أصلًا؟". أما تقسيم admin / user فيجيب عن سؤال "بما أنه دخل، فماذا يُسمح له بفعله؟"

      يقع كل مستخدم مسموح له في إحدى فئتين لكل نطاق (DM مقابل مجموعة/قناة):

      • Admin — وصول كامل. يمكنه تشغيل كل slash command مسجّل (مدمج + من الإضافات) واستخدام كل قدرة مقيّدة.
      • مستخدم عادي — وصول مقيّد. يمكنه محادثة الوكيل بشكل طبيعي، لكن لا يمكنه تشغيل سوى slash commands التي تفعّلها صراحةً. الحد الأدنى المسموح به دائمًا هو /help و/whoami.

      تُضبط الفئتان لكل منصة ولكل نطاق. صلاحية admin في DM لا تعني ضمنيًا صلاحية admin في المجموعة/القناة — لكل نطاق قائمة admin خاصة به.

      ما تقيّده الفئتان اليوم: slash commands. يعمل التقسيم عبر سجل الأوامر الحي، لذا يغطي الأوامر المدمجة والأوامر المسجّلة من الإضافات دون ربط يدوي لكل ميزة. المحادثة العادية غير متأثرة — لا يزال بإمكان غير الإداريين التحدث مع الوكيل.

      ما قد يُقيَّد مستقبلًا: ستُضاف أسطح قدرات أخرى (الوصول إلى الأدوات، تبديل النموذج، العمليات المكلفة) إلى نفس تمييز admin / user كلما أضفناها. ضبط هذا التقسيم الآن يعني أن تلك القيود المستقبلية ستُطبَّق بسلاسة دون أن تحتاج إلى إعادة تحديد من هو admin.

      الإعدادات​

      gateway:
        platforms:
          discord:
            extra:
              allow_from: ["111", "222", "333"]
              allow_admin_from: ["111"]                    # admins → all slash commands
              user_allowed_commands: [status, model]       # what non-admins may run
              # Optional: separate group/channel scope
              group_allow_admin_from: ["111"]
              group_user_allowed_commands: [status]

      التوافق الرجعي: إذا لم يُضبط allow_admin_from لنطاق ما، فإن تقسيم الفئات يُعطَّل لذلك النطاق ويحصل كل مستخدم مسموح له على وصول كامل. تستمر التثبيتات الحالية بالعمل دون أي تغيير — فعّل هذا الخيار عندما ترغب في التمييز.

      فحص صلاحية وصولك​

      استخدم /whoami من أي منصة لمعرفة النطاق النشط، وفئتك (admin / user / غير مقيّد)، وما هي slash commands التي يمكنك تشغيلها. راجع صفحتَي Telegram وDiscord للاطلاع على أمثلة خاصة بكل منصة.

      إعادة توجيه الوكيل​

      أرسل رسالة أثناء عمل الوكيل لتصحيح الدور الجاري:

      • يُعاد توليد النموذج مع الاحتفاظ بالسياق — يُحتفظ بالاستدلال الذي ظهر بالفعل وبالنص الجزئي المرئي كنقطة حفظ (checkpoint) عادية للمساعد
      • يبقى العمل المكتمل متاحًا — تظل استدعاءات الأدوات السابقة ونتائجها ضمن الدور
      • تكتمل الأدوات قيد التشغيل بأمان — يُطبَّق التصحيح عند الحد الفاصل التالي لنتيجة أداة بدلًا من إنهاء الأداة قسرًا
      • يبقى /stop أمر إيقاف حاسم — استخدمه لإلغاء الدور الجاري والعمل الذي يجري في الواجهة الأمامية

      الانتظار في الطابور مقابل المقاطعة مقابل التوجيه (وضع الإدخال أثناء الانشغال)​

      افتراضيًا، تؤدي مراسلة وكيل مشغول إلى إعادة توجيه دوره الجاري (إذ يُنقل أمر الطرفية الذي يعمل في الواجهة الأمامية إلى الخلفية بدلًا من إنهائه، لتُقرأ رسالتك فورًا). ويتوفر وضعان آخران:

      • queue — تنتظر رسائل المتابعة وتُنفَّذ كدور تالٍ بعد انتهاء المهمة الحالية.
      • steer — تُحقن رسائل المتابعة في التشغيل الحالي عبر /steer، فتصل إلى الوكيل بعد استدعاء الأداة التالي. لا مقاطعة ولا دور جديد. ويعود إلى سلوك queue إذا لم يكن الوكيل قد بدأ بعد.

      تحمل عمليات التوجيه في gateway (بما فيها /steer الصريح) وعمليات إعادة توجيه الدور الجاري ما يتوفر من معرّفات الحدث الطالب — المنصة والمحادثة والسلسلة (thread) والمرسل والرسالة والـ profile والنطاق — كسياق JSON مرفق بكل رسالة. ومع privacy.redact_pii: true، تُجزَّأ (hashing) المعرّفات الموجودة في هذا السياق المرئي للنموذج على المنصات المدعومة، بما في ذلك المعرّفات البديلة والأصلية، بينما تبقى معرّفات الحدث الأصلية داخلية لأغراض التوجيه. وفي غير ذلك تُحفظ المعرّفات كما هي تمامًا. ولا يغيّر أيٌّ من الوضعين الـ system prompt الخاص بالجلسة، ولا يختار وجهة رد احتياطية. فهذا السياق بيانات توجيه، وليس تفويضًا ولا ضمانًا للتسليم التلقائي.

      display:
        busy_input_mode: steer   # or queue, or interrupt (default)
        busy_ack_enabled: true   # set to false to suppress the ⚡/⏳/⏩ chat reply entirely

      في المرة الأولى التي تراسل فيها وكيلًا مشغولًا على أي منصة، يُلحق Hermes بإشعار الانشغال (busy-ack) تذكيرًا من سطر واحد يشرح هذا الخيار ("💡 First-time tip — …"). ويظهر التذكير مرة واحدة لكل تثبيت — إذ يثبّته علَم (flag) ضمن onboarding.seen.busy_input_prompt. احذف هذا المفتاح لترى النصيحة مجددًا.

      إذا وجدت إشعار الانشغال مزعجًا، فاضبط display.busy_ack_enabled: false. لا تتغير طريقة معالجة الإدخال؛ وتُخفى رسالة التأكيد فقط.

      أسئلة الاستيضاح (اختيار متعدد)​

      عندما يستخدم الوكيل أداة clarify ليطرح عليك سؤالًا، يعرض gateway الخيارات كقائمة مرقّمة (أو كأزرار أصلية على المنصات التي تدعمها). وتدعم أداة Clarify أيضًا أسئلة الاختيار المتعدد — إذ يمكن للوكيل أن يتيح لك اختيار عدة خيارات في آن واحد:

      • منصات المراسلة — تتضمن الرسالة عبارة "Multiple selections allowed"؛ فأجب بالأرقام مفصولة بفواصل أو مسافات (مثل 1, 3)، أو بنص الخيار، أو بإجابتك الحرة.
      • CLI الكلاسيكية / TUI — يُعرض الاختيار المتعدد كمربعات اختيار: يبدّل Space حالة الخيار، ويرسل Enter الاختيار.

      تعمل أسئلة الاختيار الفردي كما في السابق: اختر خيارًا واحدًا بالرقم أو الزر أو النص، أو اكتب إجابتك الخاصة عبر مسار "Other".

      إشعارات تقدّم الأدوات​

      تحكّم في مقدار نشاط الأدوات المعروض من خلال ~/.hermes/config.yaml:

      display:
        tool_progress: all    # off | new | all | verbose | log
        tool_progress_command: false  # set to true to enable /verbose in messaging
        # How progress is grouped on platforms that support message editing:
        #   accumulate (default) — edit one bubble in place as tools run
        #   separate             — send one message per tool (pre-v0.9 style; noisier)
        # Only applies where tool_progress is already enabled.
        tool_progress_grouping: accumulate   # accumulate | separate

      الوضع log — ملف تدقيق بدلًا من رسائل المحادثة​

      يؤدي ضبط display.tool_progress: log إلى عدم إرسال أي فقاعات تقدّم إلى المحادثة. وبدلًا من ذلك، يُلحق كل استدعاء أداة كسطر في ~/.hermes/logs/tool_calls.log — وهو ملف تدقيق دوّار (5 MB × 3 نسخ احتياطية) يمر عبر مُنسِّق حجب الأسرار نفسه المستخدم في السجلات العادية، فلا تُكتب بيانات الاعتماد على القرص أبدًا. استخدمه عندما تريد سجلًا كاملًا لاستدعاءات الأدوات دون أي ضجيج في المحادثة.

      عبارات الحالة القابلة للتخصيص​

      تستمد أسطر حالة gateway الخاصة بالمهام الطويلة (نبضات من نوع "still working…") عباراتها من كتالوج عبارات. وتأتي القيم الافتراضية المدمجة في gateway/assets/status_phrases.yaml؛ ويمكنك إضافة عباراتك الخاصة بملفات قابلة للنقل بين الـ profiles ضمن HERMES_HOME:

      • ~/.hermes/status_phrases.yaml أو أي ملف *.yaml داخل ~/.hermes/status_phrases/ (مسارات اصطلاحية تُحمَّل تلقائيًا)، أو
      • وجّه الإعدادات إلى مسار نسبي:
      display:
        status_phrases:
          path: status_phrases/whatsapp.yaml  # relative to HERMES_HOME
          mode: append                        # append (default) or replace

      تربط ملفات العبارات كل سطح عرض (status، generic) بقائمة من النصوص (بحد أقصى 80 عبارة لكل سطح، و160 حرفًا لكل عبارة). وتُتجاهل المسارات المطلقة ومحاولات الخروج عبر .. حتى تبقى الإعدادات قابلة للنقل بين الـ profiles. ولا تُستخدم إلا نصوص العبارات التي ضبطتها — فلا تُدرج أبدًا وسائط الأدوات الخام أو الأوامر أو نص الاستدلال داخل عبارة الحالة.

      الطوابع الزمنية للرسائل في سياق النموذج​

      معطّلة افتراضيًا. عند تفعيلها، يضيف Hermes طابعًا زمنيًا مقروءًا (مثل [Tue 2026-04-28 13:40:53 CEST]) في بداية كل رسالة من المستخدم ضمن سياق النموذج ليعرف الوكيل متى أُرسلت الرسائل — وهذا مفيد للاستدلال الزمني ("you asked this morning…"، أو ملاحظة فجوة زمنية طويلة). ولا يُضاف إلى رسائل المساعد ولا إلى الـ system prompt.

      gateway:
        message_timestamps:
          enabled: false   # set true to show send-times to the model

      تبقى النصوص المحفوظة للمحادثات نظيفة دائمًا — إذ يُخزَّن الطابع الزمني كبيانات وصفية للرسالة بغض النظر عن هذا الخيار، لذا فإن تفعيله لاحقًا يُظهر أيضًا أوقات إرسال الرسائل السابقة، ولا تتراكم البادئات المكررة عند إعادة التشغيل (replay) أبدًا.

      عند التفعيل، يرسل البوت رسائل حالة أثناء عمله:

      💻 `ls -la`...
      🔍 web_search...
      📄 web_extract...
      🐍 execute_code...

      الجلسات في الخلفية​

      شغّل prompt في جلسة خلفية منفصلة ليعمل عليه الوكيل باستقلالية بينما تبقى محادثتك الرئيسية مستجيبة:

      /bg Check all servers in the cluster and report any that are down

      يؤكد Hermes الاستلام فورًا:

      🔄 Background task started: "Check all servers in the cluster..."
         Task ID: bg_143022_a1b2c3

      آلية العمل​

      يُنشئ كل prompt يُرسل عبر /bg نسخة وكيل منفصلة تعمل بشكل غير متزامن:

      • جلسة معزولة — للوكيل العامل في الخلفية جلسته الخاصة بسجل محادثة مستقل. ولا يعرف شيئًا عن سياق محادثتك الحالية، ولا يتلقى إلا الـ prompt الذي تقدّمه.
      • الإعدادات نفسها — يرث النموذج والمزوّد والـ toolsets وإعدادات الاستدلال وتوجيه المزوّدين من إعداد gateway الحالي.
      • دون حجب — تبقى محادثتك الرئيسية تفاعلية بالكامل. أرسل رسائل، أو نفّذ أوامر أخرى، أو ابدأ مهامًا خلفية إضافية أثناء عمله.
      • تسليم النتيجة — عند انتهاء المهمة، تُرسل النتيجة إلى المحادثة أو القناة نفسها التي أصدرت منها الأمر، مسبوقة بعبارة "✅ Background task complete". وإذا فشلت، فسترى "❌ Background task failed" مع رسالة الخطأ.

      إشعارات العمليات في الخلفية​

      عندما يستخدم الوكيل العامل في جلسة خلفية terminal(background=true) لبدء عمليات طويلة التشغيل (خوادم، عمليات بناء، إلخ)، يمكن لـ gateway إرسال تحديثات الحالة إلى محادثتك. تحكّم في ذلك عبر display.background_process_notifications في ~/.hermes/config.yaml:

      display:
        background_process_notifications: concise    # concise | all | result | error | off
      الوضعما تتلقاه
      conciseرسالة حالة من سطر واحد عند الاكتمال؛ وفي حالات الفشل يُلحق بها ذيل قصير من المخرجات (الافتراضي)
      allتحديثات المخرجات أثناء التشغيل و رسالة المخرجات الخام النهائية
      resultرسالة الاكتمال النهائية بالمخرجات الخام فقط (بغض النظر عن رمز الخروج)
      errorرسالة المخرجات الخام النهائية فقط عندما يكون رمز الخروج غير صفري
      offلا رسائل من مراقب العمليات إطلاقًا

      يمكنك أيضًا ضبط ذلك عبر متغير بيئة:

      HERMES_BACKGROUND_NOTIFICATIONS=result

      حالات الاستخدام​

      • مراقبة الخوادم — "/bg Check the health of all services and alert me if anything is down"
      • عمليات البناء الطويلة — "/bg Build and deploy the staging environment" بينما تواصل المحادثة
      • مهام البحث — "/bg Research competitor pricing and summarize in a table"
      • عمليات الملفات — "/bg Organize the photos in ~/Downloads by date into folders"
      نصيحة

      المهام الخلفية على منصات المراسلة من نوع "أطلِق وانسَ" (fire-and-forget) — فلا حاجة إلى انتظارها أو متابعتها. تصل النتائج إلى المحادثة نفسها تلقائيًا عند انتهاء المهمة.

      إدارة الخدمة​

      Linux (systemd)​

      hermes gateway install               # Install as user service
      hermes gateway start                 # Start the service
      hermes gateway stop                  # Stop the service
      hermes gateway status                # Check status
      journalctl --user -u hermes-gateway -f  # View logs

      # Enable lingering (keeps running after logout)
      sudo loginctl enable-linger $USER

      # Or install a boot-time system service that still runs as your user
      sudo hermes gateway install --system
      sudo hermes gateway start --system
      sudo hermes gateway status --system
      journalctl -u hermes-gateway -f

      استخدم خدمة المستخدم على الحواسيب المحمولة وأجهزة التطوير. واستخدم خدمة النظام على خوادم VPS أو الأجهزة المضيفة بلا واجهة (headless) التي يجب أن تعود للعمل عند الإقلاع دون الاعتماد على خاصية linger في systemd.

      لا تُضف drop-in مخصصًا لإنهاء العملية عبر ExecStopPost

      الوحدة (unit) التي يثبّتها Hermes توقف gateway بشكل نظيف بالفعل باستخدام KillMode=mixed + KillSignal=SIGTERM، وتستخدم Restart=always مع RestartForceExitStatus كي تُعاد عمليات التحديث و/restart بشكل صحيح. لا تُضف drop-in لـ systemd مثل ExecStopPost=/bin/kill -9 $MAINPID — إذ يُنفَّذ ExecStopPost عند كل إيقاف، بما في ذلك عمليات إعادة التشغيل النظيفة، فيرسل SIGKILL إلى النسخة التي أُنشئت للتو قبل أن تستقر، ثم يعيد Restart=always تشغيلها فورًا. والنتيجة حلقة لا نهائية من إعادة التشغيل (وعلى Telegram، سيل من رسائل إعادة التشغيل). وإذا كنت قد أضفت drop-in كهذا، فأزله: systemctl --user edit hermes-gateway (أو sudo systemctl edit hermes-gateway لخدمة النظام) واحذف سطر ExecStopPost، ثم نفّذ systemctl --user daemon-reload.

      الأجهزة الافتراضية بلا واجهة: خدمة المستخدم + linger تجنّبك مطالبات root

      تحتاج خدمة النظام إلى صلاحيات root عند كل إعادة تشغيل — بما في ذلك إعادة تشغيل gateway التلقائية في نهاية hermes update. وعندما يُنفَّذ hermes update بمستخدم غير root، يحاول استخدام sudo systemctl دون كلمة مرور؛ فإن لم يكن ذلك متاحًا، يتخطى إعادة التشغيل ويطبع الأمر اليدوي sudo systemctl restart hermes-gateway (ولا يتوقف أبدًا بانتظار إدخال كلمة مرور تفاعليًا).

      بالنسبة إلى جهاز افتراضي بلا واجهة لا تسجّل الدخول إليه أبدًا، تمنحك خدمة مستخدم مع تفعيل linger سلوك التشغيل عند الإقلاع نفسه دون أي تدخل من root:

      hermes gateway install          # user service
      sudo loginctl enable-linger $USER   # one-time: start at boot, survive logout

      بعد ذلك، يستطيع hermes update إعادة تشغيل gateway دون أي صلاحيات. وإذا كنت تفضّل الإبقاء على خدمة النظام، فإما أن تشغّل التحديثات باستخدام sudo hermes update، أو تمنح حساب الخدمة صلاحية sudo دون كلمة مرور لـ systemctl، مثلًا في sudo visudo -f /etc/sudoers.d/hermes-gateway:

      hermes ALL=(root) NOPASSWD: /usr/bin/systemctl --no-ask-password reset-failed hermes-gateway*, /usr/bin/systemctl --no-ask-password start hermes-gateway*, /usr/bin/systemctl --no-ask-password restart hermes-gateway*

      تجنّب إبقاء وحدتي gateway للمستخدم وللنظام مثبّتتين معًا ما لم تقصد ذلك فعلًا. سيعرض Hermes تحذيرًا إذا اكتشف وجودهما معًا، لأن سلوك البدء/الإيقاف/الحالة يصبح ملتبسًا.

      تثبيتات متعددة

      إذا كنت تشغّل عدة تثبيتات من Hermes على الجهاز نفسه (بمجلدات HERMES_HOME مختلفة)، فيحصل كلٌّ منها على اسم خدمة systemd خاص به. يستخدم المجلد الافتراضي ~/.hermes الاسم hermes-gateway؛ بينما تستخدم التثبيتات الأخرى hermes-gateway-<hash>. وتستهدف أوامر hermes gateway تلقائيًا الخدمة الصحيحة الخاصة بـ HERMES_HOME الحالي لديك.

      macOS (launchd)​

      hermes gateway install               # Install as launchd agent
      hermes gateway start                 # Start the service
      hermes gateway stop                  # Stop the service
      hermes gateway status                # Check status
      tail -f ~/.hermes/logs/gateway.log   # View logs

      يوجد ملف plist المُولَّد في ~/Library/LaunchAgents/ai.hermes.gateway.plist. ويتضمن ثلاثة متغيرات بيئة:

      • PATH — قيمة PATH الكاملة للـ shell لديك وقت التثبيت، مع إضافة مجلد bin/ الخاص بالـ venv وnode_modules/.bin في بدايتها. وهذا يضمن توفر الأدوات التي ثبّتها المستخدم (Node.js و ffmpeg وغيرها) للعمليات الفرعية لـ gateway مثل جسر WhatsApp.
      • VIRTUAL_ENV — يشير إلى البيئة الافتراضية لـ Python كي تتمكن الأدوات من تحديد الحزم بشكل صحيح.
      • HERMES_HOME — يحصر نطاق gateway في تثبيت Hermes الخاص بك.
      تغييرات PATH بعد التثبيت

      ملفات plist الخاصة بـ launchd ثابتة — فإذا ثبّتّ أدوات جديدة (مثل إصدار جديد من Node.js عبر nvm، أو ffmpeg عبر Homebrew) بعد إعداد gateway، فنفّذ hermes gateway install مرة أخرى لالتقاط قيمة PATH المحدّثة. وسيكتشف gateway ملف plist القديم ويعيد التحميل تلقائيًا.

      تثبيتات متعددة

      كما في خدمة systemd على Linux، يحصل كل مجلد HERMES_HOME على تسمية launchd خاصة به. يستخدم المجلد الافتراضي ~/.hermes التسمية ai.hermes.gateway؛ بينما تستخدم التثبيتات الأخرى ai.hermes.gateway-<suffix>.

      تشغيل gateway متعدد المنصات​

      يشغّل gateway عادةً عدة محوّلات (adapters) في آن واحد (Telegram + Discord + Slack، إلخ). وتتناول الأقسام التالية العمليات اليومية بعد الإعداد (day-2 operations) التي تشمل جميع المنصات.

      الأمر /platform​

      بعد تشغيل gateway، استخدم الـ slash command /platform من أي جلسة CLI أو محادثة متصلة لفحص المحوّلات كلٍّ على حدة والتحكم بها دون إعادة تشغيل gateway بالكامل:

      /platform list                  # show all adapters and their state
      /platform pause <name>          # stop dispatching new messages to one adapter
      /platform resume <name>         # re-enable a paused adapter

      يعرض /platform list ما إذا كان كل محوّل في حالة running، أو paused (يدويًا)، أو paused-by-breaker (انظر أدناه). ويُبقي الإيقاف المؤقت المحوّلَ محمّلًا وحلقاته الخلفية نشطة — إذ تُهمل الرسائل الواردة، لكن الاتصال نفسه يبقى مفتوحًا فيكون الاستئناف فوريًا.

      راجع أيضًا أمر ملخص الحالة الأشمل /platforms.

      تعطيل منصة لا تزال بيانات اعتمادها موجودة في .env​

      الإعداد platforms.<name>.enabled: false في ~/.hermes/config.yaml هو المرجع الحاسم. فبيانات الاعتماد الخاصة بتلك المنصة المتروكة في البيئة (TELEGRAM_BOT_TOKEN، WEIXIN_TOKEN، HASS_TOKEN، EMAIL_*، TWILIO_ACCOUNT_SID، ...) تبقى مربوطة بإعدادات المنصة كي تواصل أدوات الإرسال فقط عملها، لكنها لم تعد تُشغّل المحوّل:

      ~/.hermes/config.yaml
      platforms:
        weixin:
          enabled: false   # wins over WEIXIN_TOKEN in .env

      كانت الإصدارات السابقة تسمح لمجرد وجود بيانات الاعتماد بإعادة تفعيل اثنتي عشرة منصة (Weixin و WhatsApp Cloud و Home Assistant و Email و SMS و DingTalk و Feishu و WeCom و WeCom callback و BlueBubbles و QQ Bot و Yuanbao) بغض النظر عن ذلك المفتاح. وإذا كنت تعتمد على ذلك، فإن gateway يسجّل الآن رسالة WARNING واحدة لكل منصة متأثرة عند بدء التشغيل حتى لا تتوقف بصمت:

      Platform 'weixin' is explicitly disabled by platforms.weixin.enabled: false in config.yaml,
      so the credentials found in the environment (WEIXIN_TOKEN, WEIXIN_ACCOUNT_ID) will NOT start
      its adapter. Environment credentials no longer override an explicit disable. Remove the key
      or set platforms.weixin.enabled: true to turn it back on.

      أما حذف المفتاح enabled كليًا فيُبقي السلوك المعتمد على البيئة وحدها: وجود بيانات الاعتماد ← يبدأ المحوّل.

      تجاهل proxy موروث (gateway.trust_env)​

      افتراضيًا، يلتزم كل محوّل منصة بالمتغيرات HTTP_PROXY / HTTPS_PROXY / NO_PROXY (و SSL_CERT_FILE) من بيئة gateway، ويكتشف proxy النظام في macOS تلقائيًا. وقد يرث gateway الذي تشغّله مهمة مجدولة في Windows (Scheduled Task) أو مدير خدمات proxy لا يراه الـ shell التفاعلي أبدًا — كمستمع Clash/V2Ray محلي لم يبدأ تشغيله بعد — فيسجّل Cannot connect to host 127.0.0.1:7890 عند كل عملية استطلاع. أوقف الـ proxy الموروث لجميع المحوّلات دفعة واحدة:

      ~/.hermes/config.yaml
      gateway:
        trust_env: false

      أما متغيرات الـ proxy الصريحة الخاصة بكل منصة (DISCORD_PROXY، TELEGRAM_PROXY، MATRIX_PROXY، ...) فيظل الالتزام بها قائمًا. أعد تشغيل gateway بعد تغيير هذا الإعداد.

      قاطع الدائرة التلقائي (circuit breaker)​

      يُغلَّف كل محوّل بقاطع دائرة. وتؤدي حالات الفشل المتكررة القابلة لإعادة المحاولة (انقطاعات الشبكة العابرة، وردود حدّ المعدل، واستجابات 5xx من الخدمة الأصلية، وانقطاعات websocket) إلى تفعيل القاطع — فيُوقَف المحوّل مؤقتًا تلقائيًا، ويُرسل إشعار للمشغّل إلى القناة الرئيسية (home channel) لمنصة أخرى تعمل إن كانت مضبوطة، ويُكتب سطر سجل منظّم.

      لا يستأنف القاطع العمل تلقائيًا — بل يبقى مفتوحًا إلى أن تنفّذ /platform resume <name> يدويًا. وهذا مقصود: فإذا كانت منصة ما تعاني انقطاعًا مستمرًا، فلن ترغب في أن يستنزف gateway نفسه بمحاولات إعادة الاتصال المتكررة.

      أين تبحث عندما تكون منصة موقوفة مؤقتًا​

      عندما يكون محوّل موقوفًا مؤقتًا، تحقق مما يلي:

      1. سجل gateway (~/.hermes/logs/gateway.log أو سجل وحدة systemd / launchd). ابحث عن اسم المنصة مع circuit breaker أو paused أو disabled. ويتضمن حدث التفعيل عدد حالات الفشل وآخر خطأ.
      2. مخرجات /platform list — تعرض الحالة الحالية وآخر سبب.
      3. صفحة حالة المزوّد (حالة Telegram bot API، وحالة Discord، إلخ). فقد تفعّل القاطع لأن المنصة كانت متعثرة؛ لذا لا تحاول الاستئناف حتى تعود للعمل.

      بمجرد أن تتعافى الخدمة الأصلية، يُعيد /platform resume <name> ضبط القاطع ويعيد تجهيز المحوّل.

      إشعارات إعادة التشغيل​

      عندما يُعاد تشغيل gateway (أو يُوقف أثناء وجود جلسات قيد التنفيذ)، يمكنه إرسال رسالة لمرة واحدة من نوع "the agent is back" / "the agent was interrupted" إلى القناة الرئيسية لكل منصة. ويُتحكم في ذلك لكل منصة عبر الخيار gateway_restart_notification في config.yaml، وقيمته الافتراضية true:

      gateway:
        platforms:
          telegram:
            home_chat_id: "123456789"
            gateway_restart_notification: false   # opt out for this platform
          discord:
            home_chat_id: "987654321"
            # gateway_restart_notification omitted → defaults to true

      عطّله على المنصات المزعجة أو منخفضة الأولوية مع إبقائه مفعّلًا لمحادثتك الرئيسية. يُرسل الإشعار مرة واحدة لكل إعادة تشغيل، بغض النظر عن عدد الجلسات التي كانت قيد التنفيذ.

      مؤشرات الكتابة​

      أثناء معالجة الوكيل لرسالة، يعرض gateway حالة كتابة مباشرة على المنصات التي تدعمها — فقاعة "typing…" على Telegram/Discord/Signal، أو حالة المساعد "is thinking…" على Slack. ويُتحكم في ذلك لكل منصة عبر الخيار typing_indicator في config.yaml، وقيمته الافتراضية true:

      gateway:
        platforms:
          slack:
            typing_indicator: false   # don't show "is thinking…" on Slack
          telegram:
            # typing_indicator omitted → defaults to true

      اضبط typing_indicator: false على أي منصة لا ترغب فيها بالمؤشر. يجد بعض المستخدمين حالة "is thinking…" في Slack مزعجة (كما أنها تعطّل مربع الكتابة لفترة وجيزة أثناء ظهورها، لأنها تستخدم Assistant API الخاصة بـ Slack). ولا يؤدي تعطيلها إلا إلى إخفاء المؤشر — أما تسليم الرسائل وكل ما عداه فلا يتغير. والخيار عام، لذا يعمل المفتاح نفسه مع كل منصة.

      استئناف الجلسات عبر عمليات إعادة تشغيل gateway​

      عندما يتوقف gateway أثناء وجود استدعاء أداة أو عملية توليد قيد التنفيذ، تُعلَّم الجلسات المتأثرة بالحالة restart_interrupted. وعند بدء التشغيل التالي، يجدول gateway استئنافًا تلقائيًا لكل منها — فيتلقى المستخدم تنبيهًا قصيرًا في المحادثة ("Send any message after restart and I'll try to resume where you left off.") وتستأنف الجلسة من آخر دور مُثبَّت عندما يرد.

      هذا السلوك مفعّل افتراضيًا ويُسجَّل عند بدء gateway:

      Scheduled auto-resume for N restart-interrupted session(s)

      لا يلزم أي إعداد. وإذا كنت لا تريد هذا التنبيه، فاضبط gateway_restart_notification: false على المنصة.

      إعدادات تقدّم افتراضية ملائمة للهاتف المحمول​

      غالبًا ما يُستخدم Telegram كصندوق وارد على الهاتف المحمول، لذا ضُبطت القيم الافتراضية لتلائم هذه الواجهة:

      • القيمة الافتراضية لـ tool_progress هي off — فلا يوجد سيل من إشعارات التتبع لكل أداة يملأ المحادثة.
      • القيمة الافتراضية لـ busy_ack_detail هي off — فتبقى إشعارات حالة الانشغال ونبضات المهام الطويلة مقتضبة (دون تفاصيل تصحيح مثل iteration 21/60).
      • يبقى interim_assistant_messages مفعّلًا — فتعليقات المساعد الفعلية في منتصف الدور (حين يخبرك النموذج حرفيًا بما هو على وشك فعله) معلومات مفيدة، لا ضجيج.
      • يبقى long_running_notifications مفعّلًا — إذ تتحدّث فقاعة واحدة تُعدَّل في مكانها "⏳ Working — N min" كل بضع دقائق، فتحصل على نبضة تطمئنك بدلًا من التحديق في typing… لنصف ساعة.

      يمكنك إلغاء أيٍّ من الإعدادين المفعّلين افتراضيًا، أو إعادة تفعيل عرض التقدّم المفصّل، لكل منصة:

      display:
        platforms:
          telegram:
            # Re-enable the tool-progress stream
            tool_progress: new
            # Show "iteration N/M, running: tool" in heartbeats and busy acks
            busy_ack_detail: true
            # Or quiet them entirely
            interim_assistant_messages: false
            long_running_notifications: false

      تنظيف فقاعات التقدّم (اختياري)​

      يمكن أيضًا حذف رسائل تقدّم الأدوات ونبضة "still working…" وفقاعات استدعاء الحالة تلقائيًا بعد وصول الرد النهائي. فعّل ذلك لكل منصة عبر display.platforms.<platform>.cleanup_progress:

      display:
        platforms:
          telegram:
            cleanup_progress: true
          discord:
            cleanup_progress: true

      القيمة الافتراضية false. ولا تلتزم بهذا الإعداد إلا المنصات التي يطبّق محوّلها delete_message (حاليًا Telegram و Discord). أما عمليات التشغيل الفاشلة فتتخطى التنظيف لتبقى الفقاعات كأثر يمكن تتبعه.

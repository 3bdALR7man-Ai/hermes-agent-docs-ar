      إعداد Google Chat

      اربط Hermes Agent بـ Google Chat كبوت. يعتمد هذا التكامل على اشتراكات السحب (pull subscriptions) في Cloud Pub/Sub لاستقبال الأحداث الواردة، وعلى Chat REST API لإرسال الرسائل الصادرة. تجربة الاستخدام مماثلة لـ Slack Socket Mode أو long-polling في Telegram: لا تحتاج عملية Hermes إلى URL عام أو نفق (tunnel) أو شهادة TLS. فهي تتصل وتُصادِق ثم تستمع على اشتراك، تمامًا كما يستمع بوت Telegram على token.

      نفّذ hermes gateway setup واختر Google Chat للحصول على إعداد موجَّه خطوة بخطوة.

      إصدار Workspace

      Google Chat جزء من Google Workspace. يمكنك استخدام هذا التكامل مع Workspace شخصي (@yourdomain.com مسجَّل عبر Google) أو مع Workspace للعمل تملك فيه صلاحيات المسؤول (Admin) اللازمة لنشر تطبيق. لا يمكن للحسابات التي تقتصر على Gmail استضافة تطبيقات Chat.

      نظرة عامة​

      المكوّنالقيمة
      المكتباتgoogle-cloud-pubsub، google-api-python-client، google-auth
      النقل الوارداشتراك سحب في Cloud Pub/Sub (بدون endpoint عام)
      النقل الصادرChat REST API (chat.googleapis.com)
      المصادقةملف JSON لـ Service Account مع الدور roles/pubsub.subscriber على الاشتراك
      تعريف المستخدمأسماء موارد Chat (users/{id}) + البريد الإلكتروني

      الخطوة 1: أنشئ مشروع GCP أو اختر مشروعًا قائمًا​

      تحتاج إلى مشروع Google Cloud لاستضافة موضوع (topic) Pub/Sub. إن لم يكن لديك مشروع، فأنشئه من console.cloud.google.com — تحصل الحسابات الشخصية على فئة مجانية (free tier) تغطي حركة البوت بسهولة.

      دوّن معرّف المشروع (مثل my-chat-bot-123)، إذ ستستخدمه في كل الخطوات اللاحقة.

      الخطوة 2: فعّل واجهتَي API​

      في وحدة التحكم (console)، انتقل إلى APIs & Services → Library وفعّل:

      • Google Chat API
      • Cloud Pub/Sub API

      كلتاهما مجانية ضمن أحجام الاستخدام التي يولّدها بوت شخصي.

      الخطوة 3: أنشئ Service Account​

      IAM & Admin → Service Accounts → Create Service Account.

      • الاسم: hermes-chat-bot
      • تخطَّ خطوة "Grant this service account access to project". كل ما تحتاجه هو صلاحيات IAM على الاشتراك المحدد — لا تمنح أدوار Pub/Sub على مستوى المشروع.

      بعد الإنشاء، افتح الـ SA، وانتقل إلى Keys → Add Key → Create new key → JSON ثم نزّل الملف. احفظه في مكان لا يستطيع قراءته إلا Hermes (مثل ~/.hermes/google-chat-sa.json مع chmod 600).

      لا يوجد دور باسم "Chat Bot Caller"

      من الأخطاء الشائعة البحث عن دور IAM خاص بـ Chat ومنحه على مستوى المشروع. هذا الدور غير موجود أصلًا. تأتي صلاحية بوت Chat من تثبيته في مساحة (space)، لا من IAM. كل ما يحتاجه الـ SA هو دور مشترك Pub/Sub على الاشتراك الذي ستنشئه في الخطوة التالية.

      الخطوة 4: أنشئ موضوع Pub/Sub والاشتراك​

      Pub/Sub → Topics → Create topic.

      • Topic ID: hermes-chat-events
      • اترك بقية الإعدادات على قيمها الافتراضية.

      بعد الإنشاء، تحتوي صفحة تفاصيل الموضوع على تبويب Subscriptions. أنشئ اشتراكًا:

      • Subscription ID: hermes-chat-events-sub
      • Delivery type: Pull
      • Message retention: 7 days (كي تبقى الرسائل المتراكمة بعد إعادة تشغيل hermes)
      • اترك الباقي على الافتراضي.

      الخطوة 5: ربط IAM على الموضوع (خطوة حاسمة)​

      على الموضوع (وليس الاشتراك)، أضف IAM principal:

      • Principal: chat-api-push@system.gserviceaccount.com
      • Role: Pub/Sub Publisher

      بدون هذه الخطوة، لن يتمكن Google Chat من نشر الأحداث إلى موضوعك، ولن يستقبل البوت أي شيء على الإطلاق.

      الخطوة 6: ربط IAM على الاشتراك​

      على الاشتراك، أضف Service Account الخاص بك بوصفه principal:

      • Principal: hermes-chat-bot@<your-project>.iam.gserviceaccount.com
      • Role: Pub/Sub Subscriber

      امنحه كذلك الدور Pub/Sub Viewer على الاشتراك نفسه — إذ يستدعي Hermes subscription.get() عند بدء التشغيل للتحقق من إمكانية الوصول.

      الخطوة 7: اضبط تطبيق Chat​

      انتقل إلى APIs & Services → Google Chat API → Configuration.

      • App name: أي اسم تريد أن يراه المستخدمون ("Hermes" خيار معقول).
      • Avatar URL: أي صورة PNG عامة (توفّر Google بعض الصور الافتراضية).
      • Description: جملة قصيرة تظهر في دليل التطبيقات.
      • Functionality: فعّل Receive 1:1 messages و Join spaces and group conversations.
      • Connection settings: اختر Cloud Pub/Sub، وأدخل اسم الموضوع projects/<your-project>/topics/hermes-chat-events.
      • Visibility: اقصر الظهور على مساحة العمل الخاصة بك (أو على مستخدمين محددين) — لا تنشره للجميع أثناء الاختبار.

      احفظ.

      الخطوة 8: ثبّت البوت في مساحة اختبار​

      افتح Google Chat في المتصفح. ابدأ محادثة مباشرة (DM) مع تطبيقك بالبحث عن اسمه من قائمة + New Chat. عند مراسلته أول مرة، ترسل Google حدث ADDED_TO_SPACE يستخدمه Hermes لتخزين معرّف البوت نفسه users/{id} مؤقتًا بغرض تصفية الرسائل الذاتية.

      الخطوة 9: اضبط Hermes​

      أضف قسم Google Chat إلى ~/.hermes/.env:

      # Required
      GOOGLE_CHAT_PROJECT_ID=my-chat-bot-123
      GOOGLE_CHAT_SUBSCRIPTION_NAME=projects/my-chat-bot-123/subscriptions/hermes-chat-events-sub
      GOOGLE_CHAT_SERVICE_ACCOUNT_JSON=/home/you/.hermes/google-chat-sa.json

      # Authorization — paste the emails of people allowed to talk to the bot
      GOOGLE_CHAT_ALLOWED_USERS=you@yourdomain.com,coworker@yourdomain.com

      # Optional
      GOOGLE_CHAT_HOME_CHANNEL=spaces/AAAA...         # default delivery destination for cron jobs
      GOOGLE_CHAT_MAX_MESSAGES=1                      # Pub/Sub FlowControl; 1 serializes commands per session
      GOOGLE_CHAT_MAX_BYTES=16777216                  # 16 MiB — cap on in-flight message bytes

      يعود معرّف المشروع احتياطيًا إلى GOOGLE_CLOUD_PROJECT، ويعود مسار الـ SA احتياطيًا إلى GOOGLE_APPLICATION_CREDENTIALS — استخدم الاصطلاح الذي تفضّله.

      ضمن gateway متعدد الـ profiles، يُقرأ كل إعداد GOOGLE_CHAT_* من ملف .env الخاص بالـ profile الذي وُجِّهت إليه الرسالة؛ ولا يرث أي profile ثانوي مشروع الـ profile الافتراضي أو اشتراكه أو Service Account الخاص به. إذا لم يكن لدى profile ما SA مضبوط بينما تحمل بيئة العملية SA يخص profile آخر، يرفض المحوِّل (adapter) الرجوع احتياطيًا إلى Application Default Credentials (لأن ذلك سيؤدي إلى المصادقة بهوية ذلك الـ profile الآخر)، ويسجّل بدلًا من ذلك خطأً صريحًا — ضع GOOGLE_CHAT_SERVICE_ACCOUNT_JSON في ملف .env الخاص بذلك الـ profile.

      ثبّت اعتماديات محوِّل Google Chat عبر المُثبّت (installer) المُعتمَد له، إذ يطبّق الحدود الدنيا نفسها للإصدارات الآمنة المثبّتة التي تستخدمها فحوصات وقت التشغيل:

      python -m plugins.platforms.google_chat.oauth --install-deps

      شغّل الـ gateway:

      hermes gateway

      يُفترض أن ترى سطر سجل مثل:

      [GoogleChat] Connected; project=my-chat-bot-123, subscription=<redacted>,
                   bot_user_id=users/XXXX, flow_control(msgs=1, bytes=16777216)

      أرسل "hola" في المحادثة المباشرة التجريبية. ينشر البوت مؤشر "Hermes is thinking…"، ثم يحرّر الرسالة نفسها في مكانها ليضع الرد الفعلي — دون أي آثار من نوع "message deleted".

      تخصيص مؤشر حالة العمل​

      يمكن ضبط نص المؤشر عبر typing_status_text في ~/.hermes/config.yaml — مثلًا لمساعدة على هيئة قطة صغيرة اسمها Ada:

      platforms:
        google_chat:
          # Custom working-state marker text (default: "Hermes is thinking…").
          typing_status_text: "is pouncing… 🐾"

      على عكس سطر الحالة المؤقت في Slack، فهذه رسالة منشورة حقيقية تُحرَّر في مكانها لتحمل الرد — لذا فأي نص تضبطه هنا يظهر لفترة وجيزة في المحادثة كرسالة عادية. اضبط typing_indicator: false لتعطيل المؤشر كليًا.

      التنسيق والإمكانات​

      يعرض Google Chat مجموعة فرعية محدودة من markdown:

      مدعومغير مدعوم
      *bold*، _italic_، ~strike~، `code`العناوين، القوائم
      الصور المضمّنة عبر URLأزرار Card v2 التفاعلية (في الإصدار v1 من هذا الـ gateway)
      المرفقات الأصلية للملفات (بعد /setup-files — راجع الخطوة 10)الملاحظات الصوتية الأصلية / ملاحظات الفيديو الدائرية

      يتضمن system prompt الخاص بالوكيل تلميحًا مخصصًا لـ Google Chat كي يعرف هذه القيود ويتجنب التنسيقات التي لن تُعرض.

      حد حجم الرسالة: 4000 حرف لكل رسالة. تُقسَّم ردود الوكيل الأطول تلقائيًا على عدة رسائل.

      دعم سلاسل الرسائل (threads): عندما يرد مستخدم داخل سلسلة، يكتشف Hermes قيمة thread.name وينشر رده في السلسلة نفسها، فتحصل كل سلسلة على جلسة Hermes مستقلة.

      أسئلة التوضيح كبطاقات تفاعلية​

      عندما يطرح الوكيل سؤال توضيح (clarify) متعدد الخيارات، يعرضه المحوِّل على هيئة Card v2 أصلية فيها زر لكل خيار، إضافة إلى زر "Other / type answer"، بدلًا من قائمة نصية مرقّمة عادية. يؤدي النقر على زر إلى الإجابة عن السؤال مباشرة (إذ توجّه أحداث CARD_CLICKED الخيار عائدةً إلى الجلسة المنتظرة). إذا فشل إرسال البطاقة، أو لم يكن للسؤال خيارات ثابتة، يرجع المحوِّل احتياطيًا إلى سؤال التوضيح النصي المعتاد. لا حاجة إلى أي إعداد.

      الخطوة 10: تسليم المرفقات الأصلية (اختياري)​

      افتراضيًا، يستطيع البوت نشر النصوص والصور المضمّنة عبر URL وبطاقات تنزيل للصوت والفيديو والمستندات. ولتسليم مرفقات Chat أصلية — أي عنصر الملف نفسه الذي تحصل عليه عندما يسحب شخص ملفًا ويُفلته — يفوّض كل مستخدم البوت مرة واحدة عبر تدفق OAuth خاص بكل مستخدم.

      لماذا تدفق منفصل​

      يرفض endpoint media.upload في Google Chat رفضًا قاطعًا المصادقة عبر Service Account:

      This method doesn't support app authentication with a service account. Authenticate with a user account.

      لا يوجد دور IAM أو نطاق (scope) يحل هذه المشكلة، فهذا الـ endpoint لا يقبل إلا بيانات اعتماد المستخدم. لذا يجب أن يتصرف البوت بصفته مستخدمًا كلما رفع ملفًا — وتحديدًا بصفة المستخدم الذي طلب الملف.

      إعداد لمرة واحدة (لكل profile)​

      1. انتقل إلى APIs & Services → Credentials في مشروع GCP نفسه.
      2. Create credentials → OAuth client ID → Desktop app.
      3. نزّل ملف JSON، ثم انقله إلى المضيف الذي يشغّل Hermes.
      4. سجّل العميل لدى Hermes (نفّذ الأمر ضمن الـ profile الذي تريد حصر العميل فيه):
      # Default profile:
      python -m plugins.platforms.google_chat.oauth \
          --client-secret /path/to/client_secret.json

      # A named profile gets its own separate registration:
      hermes -p <profile> python -m plugins.platforms.google_chat.oauth \
          --client-secret /path/to/client_secret.json

      يكتب ذلك سرّ العميل (client secret) في مجلد Hermes الرئيسي للـ profile النشط (مثل ~/.hermes/google_chat_user_client_secret.json للـ profile الافتراضي). سرّ العميل محصور في الـ profile ولا يُشارَك بين الـ profiles — إذ يسجّل كل profile سرّه الخاص. وهذا مقصود: فالـ profiles حدود مصادقة معزولة، لذا يمكن لـ profileين أن يشيرا إلى تطبيقات أو حسابات Google OAuth مختلفة. سجّله مرة واحدة لكل profile يحتاج إلى تسليم مرفقات Google Chat.

      التفويض لكل مستخدم (داخل المحادثة)​

      ينفّذ كل مستخدم هذا التدفق مرة واحدة، في محادثته المباشرة مع البوت:

      1. يرسل /setup-files إلى البوت، فيرد بالحالة والخطوة التالية.
      2. يرسل /setup-files start، فيرد البوت بـ URL خاص بـ OAuth.
      3. يفتح الـ URL وينقر Allow، ثم يرى المتصفح يفشل في تحميل http://localhost:1/?...&code=.... هذا الفشل متوقع — فرمز المصادقة موجود في شريط العنوان.
      4. ينسخ الـ URL الذي فشل تحميله (أو قيمة code=... فقط) ويلصقه في المحادثة بصيغة /setup-files <PASTED_URL>. يستبدله البوت بـ refresh token.

      يُحفَظ الـ token في ~/.hermes/google_chat_user_tokens/<sanitized_email>.json. تستخدم طلبات الملفات اللاحقة في المحادثة المباشرة لذلك المستخدم الـ token الخاص به، فيرفع البوت الملفات بهويته وتصل الرسالة إلى مساحته.

      للإلغاء لاحقًا: يحذف /setup-files revoke الـ token الخاص بذلك المستخدم فقط، ولا تتأثر tokens المستخدمين الآخرين.

      النطاق (Scope)​

      يطلب التدفق نطاقًا واحدًا فقط: chat.messages.create. وهو يغطي كلًّا من media.upload واستدعاء messages.create الذي يشير إلى attachmentDataRef المرفوع. لا Drive، ولا نطاقات Chat أوسع — فمبدأ أقل الصلاحيات مقصود هنا.

      السلوك مع تعدد المستخدمين​

      عندما لا يكون لدى صاحب الطلب token خاص به بعد، يرجع البوت احتياطيًا إلى token قديم لمستخدم واحد في ~/.hermes/google_chat_user_token.json (إن كان موجودًا من تثبيت سابق لدعم تعدد المستخدمين). وعندما لا يتوفر أيٌّ منهما، ينشر البوت إشعارًا نصيًا واضحًا يطلب من صاحب الطلب تنفيذ /setup-files.

      إلغاء مستخدم للتفويض لا يمسح إلا خانته. واستجابة 401/403 من token مستخدم ما لا تُخرج من التخزين المؤقت إلا بيانات ذلك المستخدم. لا يؤثر المستخدمون بعضهم على بعض.

      استكشاف الأخطاء وإصلاحها​

      يبقى البوت صامتًا بعد إرسال "hola."

      1. تحقّق في وحدة التحكم مما إذا كان اشتراك Pub/Sub يحتوي على رسائل غير مُسلَّمة. إن وُجدت، فهذا يعني أن Hermes غير مُصادَق — تحقّق من GOOGLE_CHAT_SERVICE_ACCOUNT_JSON ومن أن الـ SA مُدرَج بدور Pub/Sub Subscriber على الاشتراك.
      2. إذا لم يكن في الاشتراك أي رسائل، فإن Google Chat لا ينشر الأحداث. تحقّق مجددًا من ربط IAM على الموضوع: يجب أن يمتلك chat-api-push@system.gserviceaccount.com الدور Pub/Sub Publisher.
      3. ابحث في سجلات hermes gateway عن [GoogleChat] Connected. إذا رأيت [GoogleChat] Config validation failed، فرسالة الخطأ تخبرك بمتغير البيئة الذي يجب إصلاحه.

      يرد البوت، لكن تظهر رسالة خطأ بدلًا من إجابة الوكيل.

      ابحث في السجلات عن [GoogleChat] Pub/Sub stream died — إذا تكررت، فربما جرى تدوير بيانات اعتماد الـ SA أو حُذف الاشتراك. بعد 10 محاولات يعلن المحوِّل حالته خطأً فادحًا (fatal).

      ظهور "403 Forbidden" مع كل رسالة صادرة.

      أُزيل البوت من المساحة، أو ألغيته من وحدة تحكم Chat API. أعد تثبيته في المساحة (سيعيد حدث ADDED_TO_SPACE التالي تفعيل المراسلة تلقائيًا).

      كثرة تحذيرات "Rate limit hit".

      تسمح الحصص الافتراضية لـ Chat API بـ 60 رسالة لكل مساحة في الدقيقة. إذا كان وكيلك يُنتج ردودًا متدفقة طويلة تتجاوز ذلك، يعيد المحوِّل المحاولة مع تراجع أُسّي (exponential backoff) — لكنك ستظل ترى تأخيرًا ملحوظًا للمستخدم. فكّر في ردود موجزة أو في رفع الحصة من وحدة تحكم GCP.

      يواصل البوت نشر إشعار "/setup-files" بدلًا من الملفات.

      لا يملك صاحب الطلب token OAuth خاصًا به، ولا يوجد token قديم احتياطي. نفّذ /setup-files في محادثته المباشرة واتبع الخطوة 10. بعد اكتمال الاستبدال، سيُرفع طلب الملف التالي بشكل أصلي دون الحاجة إلى إعادة تشغيل الـ gateway.

      يعرض /setup-files start الرسالة "No client credentials stored."

      لم يُنفَّذ الإعداد لمرة واحدة لهذا الـ profile (سرّ العميل محصور في الـ profile، لذا فالتسجيل تحت profile لن يراه profile آخر). من الطرفية، نفّذه ضمن الـ profile الذي يستخدمه الـ gateway:

      # Default profile:
      python -m plugins.platforms.google_chat.oauth \
          --client-secret /path/to/client_secret.json

      # Named profile:
      hermes -p <profile> python -m plugins.platforms.google_chat.oauth \
          --client-secret /path/to/client_secret.json

      ثم أرسل /setup-files start مرة أخرى.

      يعرض /setup-files <PASTED_URL> الرسالة "Token exchange failed."

      رمز المصادقة صالح للاستخدام مرة واحدة وقصير العمر (عادةً بضع دقائق). أرسل /setup-files start للحصول على URL جديد وأعد المحاولة.

      ملاحظات أمنية​

      • نطاق Service Account: يطلب المحوِّل النطاقين chat.bot و pubsub. ينبغي أن يكون IAM هو أداة الإنفاذ الفعلية — امنح الـ SA الحد الأدنى (roles/pubsub.subscriber + roles/pubsub.viewer على الاشتراك)، لا أدوار Pub/Sub على مستوى المشروع أو المؤسسة.
      • حماية تنزيل المرفقات: لن يُرفق Hermes الـ bearer token الخاص بالـ SA إلا بعناوين URL يطابق مضيفها قائمة سماح (allowlist) قصيرة من النطاقات المملوكة لـ Google (googleapis.com، drive.google.com، lh[3-6].googleusercontent.com، وبعض النطاقات الأخرى). يُرفَض أي مضيف آخر قبل إرسال طلب HTTP، للحماية من سيناريوهات SSRF التي قد يعيد فيها حدث مُصمَّم بخبث توجيه الـ bearer token إلى خدمة البيانات الوصفية (metadata service) في GCE.
      • التنقيح (Redaction): تُزال عناوين البريد الإلكتروني لـ Service Account ومسارات الاشتراكات ومسارات المواضيع من مخرجات السجل بواسطة agent/redact.py. ويمر تفريغ الأظرف لأغراض التصحيح (GOOGLE_CHAT_DEBUG_RAW=1) عبر مرشح التنقيح نفسه ويُسجَّل بمستوى DEBUG.
      • الامتثال: إذا كنت تخطط لربط هذا البوت بمساحة عمل خاضعة للتنظيم (أي مساحة لها سياسة لإقامة البيانات أو لحوكمة الذكاء الاصطناعي)، فاحصل على تلك الموافقة قبل التثبيت الأول.
      • نطاق OAuth للمستخدم: يطلب تدفق المرفقات لكل مستخدم فقط chat.messages.create — وهو الحد الأدنى الذي يغطي media.upload إضافة إلى استدعاء messages.create اللاحق. تُحفَظ الـ tokens بصيغة JSON نصية عادية في ~/.hermes/google_chat_user_tokens/<sanitized_email>.json (صلاحيات نظام الملفات هي وسيلة الحماية — النموذج نفسه المتبع مع ملف مفتاح الـ SA). كل token يملكه مستخدم واحد بالضبط، والإلغاء محصور في ذلك المستخدم.

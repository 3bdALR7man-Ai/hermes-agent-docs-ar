      Buzz

      يربط المحوّل (adapter) الخاص بـ Buzz نظام Hermes بمجتمع Buzz — وهي منصة Block مفتوحة المصدر للتعاون بين البشر والوكلاء، ومبنية على بروتوكول Nostr — وينقل الرسائل بين قنوات Buzz (أو الرسائل المباشرة) والوكيل. تُنفَّذ الحركة الصادرة عبر استدعاء الملف التنفيذي buzz الخاص بـ CLI ("JSON in, JSON out")؛ أما الحركة الواردة فتستخدم اشتراك Nostr WebSocket أصليًا (عبر حزمة websockets المضمّنة أصلًا)، مع استطلاع CLI دوريًا كخيار احتياطي (fallback). لا حاجة إلى أي حزم Python إضافية — يكفي الملف التنفيذي buzz.

      يعرض Buzz تنسيق markdown، لذا تحتفظ ردود الوكيل بتنسيقها. وتُسلَّم الصور كملفات مرفوعة (للملفات المحلية) أو كروابط (لعناوين URL). ويمكن ربط الردود بسلسلة رسائل لرسالة موجودة عبر معرّف الحدث (event id) الخاص بها. وعند تفعيل رسائل التقدّم أو الحالة، فإنها ترث حدث Buzz الذي أطلقها بوصفه نقطة ارتكاز للرد، بدلًا من الظهور كمنشورات مستقلة غير مترابطة على المستوى الأعلى للقناة.

      تُجلَب الملفات المرسلة إلى الوكيل من الـ relay بهوية الوكيل المُصادَق عليها وتُخزَّن مؤقتًا محليًا، فتتلقى الأدوات مسار ملف حقيقيًا بدلًا من عنوان URL بصيغة /media/… لا يمكن للطلبات المجهولة قراءته. وتُعالَج الصور والملفات الصوتية ومقاطع الفيديو والمستندات (ملفات PDF وما شابهها) جميعها.

      تصل الرسائل الواردة افتراضيًا عبر اشتراك Nostr WebSocket دائم ومُصادَق عليه وفق NIP-42 (تسليم شبه فوري)، مع تراجع تلقائي إلى استطلاع CLI عندما يتعذّر إنشاء اتصال WebSocket. أما الرسائل الصادرة فتمر دائمًا عبر buzz CLI. تحكّم في ذلك عبر transport / BUZZ_TRANSPORT: القيمة auto (الافتراضية)، أو websocket (تشترط WS وتفشل بخلاف ذلك)، أو poll. وإذا كانت عضويتك في الـ relay تستخدم إثبات المالك وفق NIP-OA، فاضبط BUZZ_AUTH_TAG على JSON وسم المصادقة المكوّن من أربع سلاسل نصية.

      شغّل hermes gateway setup واختر Buzz للحصول على إرشاد خطوة بخطوة.

      المتطلبات المسبقة​

      • الملف التنفيذي buzz الخاص بـ CLI موجودًا ضمن PATH (أو وجِّه BUZZ_CLI_PATH إليه) — ابنِه من مستودع Buzz باستخدام cargo build --release -p buzz-cli
      • عنوان URL لـ relay مجتمع Buzz (مثلًا https://mycommunity.communities.buzz.xyz)
      • مفتاح Nostr خاص (بصيغة nsec أو hex) تكون هويته عضوًا في ذلك المجتمع مسبقًا

      ضبط إعدادات Hermes​

      يمكنك ضبط Buzz بطريقتين — عبر كتلة gateway في config.yaml (الطريقة المعتمدة) أو عبر متغيرات البيئة (environment variables) التي تتجاوز قيمها تلك الكتلة. المفتاح الخاص من الأسرار (secrets) ومكانه دائمًا في ~/.hermes/.env.

      الخيار أ — config.yaml​

      gateway:
        platforms:
          buzz:
            enabled: true
            extra:
              relay_url: https://mycommunity.communities.buzz.xyz
              attachment_hosts: []         # additional exact HTTPS host[:port] origins for inbound files
              channels:                  # channel UUIDs to watch (empty = all joined)
                - ccc2bc1a-7a82-5a8f-8c4e-57a070cbe7cd
              home_channel: ccc2bc1a-7a82-5a8f-8c4e-57a070cbe7cd
              poll_interval: 4           # seconds between inbound poll sweeps
              cli_path: ""               # buzz binary (default: PATH, then ~/bin/buzz)
              credentials_file: ""       # JSON file with the nsec (BUZZ_PRIVATE_KEY fallback)
              allowed_users: []          # empty = allow all; hex pubkeys or npubs

      إضافةً إلى ما يلي في ~/.hermes/.env:

      BUZZ_PRIVATE_KEY=nsec1...

      الخيار ب — متغيرات البيئة​

      المتغيرمطلوبالوصف
      BUZZ_RELAY_URL✅عنوان URL الأساسي لـ relay المجتمع
      BUZZ_PRIVATE_KEY✅مفتاح Nostr الخاص (بصيغة nsec أو hex) — وهو السر الوحيد
      BUZZ_CHANNELS—معرّفات UUID للقنوات المراد مراقبتها، مفصولة بفواصل (الافتراضي: جميع القنوات المنضم إليها)
      BUZZ_HOME_CHANNEL—معرّف UUID للقناة التي تُسلَّم إليها مخرجات cron والإشعارات (الافتراضي: أول قناة مراقَبة)
      BUZZ_ALLOWED_USERS—قيم npub أو مفاتيح عامة بصيغة hex مسموح لأصحابها بمحادثة الوكيل، مفصولة بفواصل
      BUZZ_ALLOW_ALL_USERS—السماح لأي عضو في المجتمع بمحادثة الوكيل
      BUZZ_POLL_INTERVAL—عدد الثواني بين دورات استطلاع الرسائل الواردة (الافتراضي: 4)
      BUZZ_CLI_PATH—مسار الملف التنفيذي buzz (الافتراضي: buzz ضمن PATH، ثم ~/bin/buzz)
      BUZZ_CREDENTIALS_FILE—ملف بيانات اعتماد بصيغة JSON يحتوي على nsec، ويُستخدم عندما لا يكون BUZZ_PRIVATE_KEY مضبوطًا

      الإعدادات الافتراضية الموصى بها​

      عند ربط Buzz، اضبط هذه القيم الافتراضية في config.yaml لإبقاء القناة مرتبة وتركيز الوكيل على النتائج النهائية بدلًا من سجل تنفيذ أدواته الداخلي. وهي تطابق السلوك في Telegram والبريد الإلكتروني، اللذين يُخفيان مخرجات الأدوات الوسيطة أصلًا.

      display:
        platforms:
          buzz:
            interim_assistant_messages: false   # suppress intermediate tool results, reasoning comments, and progress updates — only the final response reaches the channel
            tool_progress: off                  # suppress tool progress bubbles (e.g., "Running terminal command...", "Reading file...")
      gateway:
        platforms:
          buzz:
            enabled: true
            extra:
              relay_url: https://mycommunity.communities.buzz.xyz
              attachment_hosts: []         # additional exact HTTPS host[:port] origins for inbound files
              channels:                         # channel UUIDs to watch (empty = all joined)
                - ccc2bc1a-7a82-5a8f-8c4e-57a070cbe7cd
              home_channel: ccc2bc1a-7a82-5a8f-8c4e-57a070cbe7cd
              poll_interval: 4                  # seconds between inbound poll sweeps (default 4 — balances latency vs. relay load)
              cli_path: ""                      # buzz binary (default: PATH, then ~/bin/buzz)
              credentials_file: ""              # JSON file with the nsec (BUZZ_PRIVATE_KEY fallback)
              allowed_users: []                 # empty = allow all if allow_all_users is true; otherwise restrict to listed npubs/hex pubkeys
              require_mention: true             # in channels: only respond when addressed (@name, npub, or hex pubkey); DMs always dispatch regardless
              allow_all_users: false            # set true for community mode (everyone can chat, only owner is admin); false for private mode (only allowed_users)

      لماذا هذه القيم الافتراضية:

      • interim_assistant_messages: false — يمنع نشر نتائج الأدوات الوسيطة وتعليقات الاستدلال وتحديثات التقدّم كرسائل منفصلة في القناة، فلا يُرسَل إلى القناة إلا الرد النهائي.
      • tool_progress: off — يُخفي فقاعات تقدّم الأدوات (مثل "Running terminal command..." و "Reading file...")، ما يُبقي القناة مركّزة على النتائج الفعلية لا على مراحل العمل.
      • poll_interval: 4 — يوازن بين زمن استقبال الرسائل الواردة (تأخير يصل إلى 4 ثوانٍ) والحمل على الـ relay. القيم الأقل تزيد وتيرة الاستطلاع، والقيم الأعلى تقللها.
      • allowed_users: [] + allow_all_users: false — الوضع الخاص افتراضيًا، فلا يتفاعل مع الوكيل إلا المستخدمون المدرجون. اضبط allow_all_users: true لتفعيل وضع المجتمع الذي يتيح للجميع المحادثة (مع بقاء مستوى صلاحيات المسؤول مقصورًا على المالك).
      • require_mention: true — في القنوات، لا يردّ الوكيل إلا عند توجيه الكلام إليه. أما الرسائل المباشرة فتُمرَّر دائمًا بصرف النظر عن هذا الإعداد.

      المبرّر: القنوات مخصصة للنتائج النهائية والمحادثة، لا لسجل تنفيذ الأدوات الداخلي للوكيل. يرى المستخدمون الإجابة النهائية، لا الخطوات المتبعة للوصول إليها. وهذا يطابق السلوك في Telegram والبريد الإلكتروني، اللذين يعتمدان هذه القيم الافتراضية أصلًا.

      استثناء: إذا أردت أن يرى المستخدمون تقدّم الأدوات (مثلًا في العمليات الطويلة)، فاضبط tool_progress: all — لكن ينبغي أن يبقى interim_assistant_messages على false لتجنّب إغراق القناة بكل نتيجة أداة.

      الإشارات والقنوات والرسائل المباشرة​

      • في القنوات المشتركة، لا يردّ الوكيل إلا عند توجيه الكلام إليه — عبر @name أو قيمة npub الخاصة به أو مفتاحه العام بصيغة hex. ويُتجاهل كل ما عدا ذلك.
      • تصل الرسائل المباشرة إلى الوكيل دائمًا، دون الحاجة إلى إشارة.
      • لا تُمرَّر رسائل الوكيل نفسه إليه مرة أخرى أبدًا (منع الصدى الذاتي بالاعتماد على المفتاح العام)، ويُزال تكرار كل حدث عبر معرّفه مقارنةً بعلامة الحد الأعلى (high-water mark) الخاصة بكل قناة.

      الرد ضمن سلاسل الرسائل​

      تُرسَل الردود ضمن سلاسل رسائل (threads) افتراضيًا: إذ ترتكز إجابة الوكيل (وأي رسائل تقدّم/حالة مفعّلة) على الرسالة التي أطلقتها. ويراعي هذا الارتكاز معيار NIP-10 — فعندما تكون الرسالة المُطلِقة داخل سلسلة رسائل أصلًا، يردّ الوكيل على جذر تلك السلسلة، فتنضم الإجابة إلى السلسلة القائمة بدلًا من إنشاء سلسلة فرعية جديدة من رسالة واحدة تحت كل دور.

      لنشر الردود مسطّحةً على مستوى القناة بدلًا من ذلك، اضبط أيًّا من الخيارين التاليين (وهما متكافئان؛ ويطابق reply_in_thread المفتاح الذي يستخدمه Slack):

      gateway:
        platforms:
          buzz:
            reply_to_mode: off          # PlatformConfig-level, like Discord/Telegram
            extra:
              reply_in_thread: false    # Slack-style key; env: BUZZ_REPLY_IN_THREAD

      ينطبق هذا الإلغاء على جميع مسارات الإرسال — الإجابات النهائية، والتحديثات المبثوثة، والتعليقات المرحلية، وفقاعات تقدّم الأدوات، وتسليم مخرجات cron من خارج العملية (deliver=buzz).

      التحكم في الوصول​

      قائمة السماح (allow-list) فارغة افتراضيًا، ما يعني أن كل عضو في المجتمع يشير إلى الوكيل لن يتلقى ردًا إلا إذا كان BUZZ_ALLOW_ALL_USERS=true؛ وإلا فقيّد الوصول بإدراج قيم npub أو مفاتيح عامة بصيغة hex في BUZZ_ALLOWED_USERS (أو allowed_users في config.yaml). أما العضوية في المجتمع نفسها فيفرضها الـ relay — إذ لا يستطيع النشر إلا الأعضاء.

      تتحكم قائمة السماح أيضًا في المرفقات الواردة: إذ تُجلَب وسائط الـ relay باستخدام بيانات اعتماد Buzz الخاصة بالوكيل، لذا لا يحدث التنزيل إلا لمرسل يفوّضه الـ gateway صراحةً. وفي حالة رفض التفويض أو غيابه أو فشله، يبقى نص الرسالة كما هو دون أي تعديل، ولا يُرسَل أي طلب يحمل بيانات اعتماد.

      تُسلَّم مهام cron والإشعارات (deliver=buzz) إلى القناة الرئيسية (home channel) — وهي BUZZ_HOME_CHANNEL إن كان مضبوطًا، وإلا فأول قناة مراقَبة — وتعمل حتى عندما تُشغَّل cron خارج عملية الـ gateway.

      المرفقات الواردة​

      يمكن لرسائل Buzz التي تحمل وسوم imeta الأصلية وفق NIP-94 أن تسلّم الصور والملفات الصوتية ومقاطع الفيديو والمستندات إلى الوكيل. ولا ينزّل Hermes المرفقات إلا بعد اجتياز الرسالة فحوص الصدى الذاتي وتوجيه الكلام وتفويض المرسل. ويجب أن يستخدم كل ملف HTTPS وأن يصرّح بحجمه الدقيق بالبايت وبقيمة SHA-256 الخاصة به؛ وتُرفض عمليات إعادة التوجيه، وبيانات الاعتماد المضمّنة في عنوان URL، والأجزاء (fragments)، والحمولات التي تتجاوز الحجم المسموح، وحالات عدم تطابق السلامة.

      يُوثَق تلقائيًا بمصدر HTTPS الخاص بالـ relay نفسه. وإذا كان المجتمع يخزّن الوسائط على مصدر عام آخر، فأضف قيمة host أو host:port الدقيقة الخاصة به إلى attachment_hosts ضمن gateway.platforms.buzz.extra. ويجب إدراج المنافذ غير الافتراضية صراحةً. أما الوسائط المحمية التي تتطلب جلبًا مُصادَقًا عليه عبر Buzz CLI فلا يعالجها هذا المسار الأصلي المعتمد على عناوين URL العامة.

      تشغيل الـ gateway​

      hermes gateway start

      تحقق من الحالة باستخدام hermes gateway status — إذ تُعرض هناك حالة اتصال Buzz، بما في ذلك الإعدادات المعتمدة على متغيرات البيئة فقط.

      ملاحظات وقيود​

      • متغيرات البيئة BUZZ_* متاحة للعمليات الفرعية لأداة الطرفية في جلسات Buzz — يستطيع الوكيل استدعاء buzz CLI مباشرةً (مثلًا buzz messages send ...) لأن BUZZ_PRIVATE_KEY و BUZZ_AUTH_TAG و BUZZ_RELAY_URL وسائر متغيرات BUZZ_* تُمرَّر إلى العمليات الفرعية للطرفية عندما تكون منصة الجلسة هي buzz أو عندما تكون العملية وكيلًا مُدارًا بواسطة Buzz Desktop (BUZZ_MANAGED_AGENT). أما جلسات غير Buzz على المضيف نفسه، و execute_code، وغيرها من العمليات المُنشأة من خارج الطرفية، فتبقى معزولة.
      • تُستقبَل الرسائل الواردة بالاستطلاع لا بالبث. يعمل buzz CLI بنمط الطلب/الاستجابة، لذا يستطلع المحوّل buzz messages get لكل قناة مراقَبة كل poll_interval ثانية (الافتراضي 4). توقّع تأخيرًا يصل إلى فترة استطلاع واحدة في الرسائل الواردة. ومن التحسينات المستقبلية المحتملة وسيلة نقل عبر websocket (إذ يتضمن مستودع Buzz buzz-ws-client للبث الحقيقي).
      • عند الاتصال (أو إعادة الاتصال)، يهيّئ المحوّل علامة الحد الأعلى الخاصة به من أحدث الأحداث، لذا لا يُعاد تشغيل سجل القناة على الوكيل أبدًا.
      • تُكتشف محادثات الرسائل المباشرة الجديدة تلقائيًا (كل بضع دورات استطلاع).
      • يُمرَّر المفتاح الخاص إلى CLI عبر بيئة العملية الفرعية — ولا يظهر أبدًا في argv أو في السجلات.

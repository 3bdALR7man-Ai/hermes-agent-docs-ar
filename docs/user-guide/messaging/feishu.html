      إعداد Feishu / Lark

      يتكامل Hermes Agent مع Feishu و Lark كبوت متكامل الميزات. بعد الربط، يمكنك محادثة الوكيل في الرسائل المباشرة أو المحادثات الجماعية، وتلقّي نتائج مهام cron في المحادثة الرئيسية (home chat)، وإرسال النصوص والصور والمقاطع الصوتية ومرفقات الملفات عبر مسار gateway المعتاد.

      يدعم التكامل وضعَي الاتصال كليهما:

      • websocket — موصى به؛ إذ يفتح Hermes الاتصال الصادر، ولا تحتاج إلى webhook endpoint عام
      • webhook — مفيد عندما تريد أن يدفع Feishu/Lark الأحداث إلى gateway الخاص بك عبر HTTP

      كيف يتصرف Hermes​

      السياقالسلوك
      الرسائل المباشرةيردّ Hermes على كل رسالة.
      المحادثات الجماعيةيردّ Hermes فقط عند الإشارة إلى البوت بـ @mention في المحادثة.
      المحادثات الجماعية المشتركةافتراضيًا، يُعزل سجل الجلسة لكل مستخدم داخل المحادثة المشتركة.

      يُتحكَّم في سلوك المحادثات المشتركة هذا عبر config.yaml:

      group_sessions_per_user: true

      اضبطه على false فقط إذا كنت تريد صراحةً محادثة واحدة مشتركة لكل مجموعة.

      الخطوة 1: أنشئ تطبيق Feishu / Lark​

      موصى به: الإنشاء بالمسح (أمر واحد)​

      hermes gateway setup

      اختر Feishu / Lark وامسح رمز QR باستخدام تطبيق Feishu أو Lark على هاتفك. سينشئ Hermes تلقائيًا تطبيق بوت بالصلاحيات الصحيحة ويحفظ بيانات الاعتماد.

      بديل: الإعداد اليدوي​

      إذا لم يكن الإنشاء بالمسح متاحًا، ينتقل المعالج إلى الإدخال اليدوي:

      1. افتح وحدة تحكم المطوّرين في Feishu أو Lark:
        • Feishu: https://open.feishu.cn/
        • Lark: https://open.larksuite.com/
      2. أنشئ تطبيقًا جديدًا.
      3. في Credentials & Basic Info، انسخ App ID و App Secret.
      4. فعّل قدرة Bot للتطبيق.
      5. نفّذ hermes gateway setup، واختر Feishu / Lark، ثم أدخل بيانات الاعتماد عند المطالبة.
      تحذير

      حافظ على سرية App Secret، فأي شخص يملكه يستطيع انتحال هوية تطبيقك.

      ضبط الصلاحيات​

      في وحدة تحكم المطوّرين في Feishu، انتقل إلى Permission Management وأضف النطاقات (scopes) التالية. يمكنك استيرادها دفعة واحدة من صفحة الصلاحيات.

      الصلاحيات المطلوبة:

      النطاقالغرض
      im:messageاستقبال الرسائل وقراءتها
      im:message:send_as_botإرسال الرسائل بصفة البوت
      im:resourceالوصول إلى الصور والملفات والمقاطع الصوتية التي يرسلها المستخدمون
      im:chatالوصول إلى البيانات الوصفية للمحادثات/المجموعات
      im:chat:readonlyقراءة قائمة المحادثات والعضوية

      الصلاحيات الموصى بها (للحصول على كامل الوظائف):

      النطاقالغرض
      im:message.reactions:readonlyاستقبال أحداث تفاعلات الإيموجي
      admin:app.info:readonlyالاكتشاف التلقائي لهوية البوت لتقييد الرد بالإشارة (@mention)
      contact:user.id:readonlyتحديد معرّفات المستخدمين لمطابقتها مع قائمة السماح

      ضبط الأحداث​

      في Events and Callbacks:

      1. اضبط وضع الاتصال على Long Connection (WebSocket) (موصى به) أو اضبط عنوان URL لـ webhook
      2. في تبويب Event Configuration، اشترك في:
        • im.message.receive_v1 — مطلوب لاستقبال الرسائل
      3. في تبويب Callback Configuration (وهو تبويب منفصل عن تبويب الأحداث)، اضبط وضع الاتصال نفسه وأضف الـ callback card.action.trigger — وهو مطلوب لأزرار الموافقة ومطالبات التحديث. راجع إعدادات تطبيق Feishu المطلوبة.

      نشر التطبيق​

      بعد ضبط الصلاحيات والأحداث، انتقل إلى Version Management وانشر إصدارًا جديدًا من التطبيق. لن تسري الصلاحيات حتى يُنشر إصدار ويُعتمد (في تطبيقات المؤسسات، قد يتطلب ذلك موافقة المسؤول).

      الخطوة 2: اختر وضع الاتصال​

      موصى به: وضع WebSocket​

      استخدم وضع WebSocket عندما يعمل Hermes على حاسوبك المحمول أو محطة العمل أو خادم خاص، إذ لا يتطلب عنوان URL عامًا. يفتح Lark SDK الرسمي اتصال WebSocket صادرًا دائمًا ويحافظ عليه مع إعادة الاتصال التلقائية.

      FEISHU_CONNECTION_MODE=websocket

      المتطلبات: يجب تثبيت حزمة Python websockets. يتولى SDK داخليًا إدارة دورة حياة الاتصال ونبضات القلب (heartbeats) وإعادة الاتصال التلقائية.

      آلية العمل: يشغّل المحوّل (adapter) عميل WebSocket الخاص بـ Lark SDK في خيط تنفيذ (executor thread) في الخلفية. تُمرَّر الأحداث الواردة (الرسائل والتفاعلات وإجراءات البطاقات) إلى حلقة asyncio الرئيسية. وعند انقطاع الاتصال، يحاول SDK إعادة الاتصال تلقائيًا.

      اختياري: وضع Webhook​

      استخدم وضع webhook فقط إذا كنت تشغّل Hermes بالفعل خلف HTTP endpoint يمكن الوصول إليه.

      FEISHU_CONNECTION_MODE=webhook

      في وضع webhook، يشغّل Hermes خادم HTTP (عبر aiohttp) ويقدّم endpoint خاصًا بـ Feishu على العنوان:

      /feishu/webhook

      المتطلبات: يجب تثبيت حزمة Python aiohttp.

      يمكنك تخصيص عنوان الربط ومسار خادم webhook:

      FEISHU_WEBHOOK_HOST=127.0.0.1   # default: 127.0.0.1
      FEISHU_WEBHOOK_PORT=8765         # default: 8765
      FEISHU_WEBHOOK_PATH=/feishu/webhook  # default: /feishu/webhook

      عندما يرسل Feishu تحدّي التحقق من عنوان URL (type: url_verification)، يستجيب webhook تلقائيًا حتى تتمكن من إكمال إعداد الاشتراك في وحدة تحكم المطوّرين في Feishu. تُقيَّد الاستجابة للتحدّي بـ FEISHU_VERIFICATION_TOKEN عند ضبطه — إذ تُرفض طلبات التحدّي التي يغيب عنها الـ token أو لا يتطابق، حتى لا يتمكن طرف بعيد غير مصادَق من إثبات سيطرته على endpoint عبر إعادة بيانات تحدٍّ يتحكم فيها مهاجم.

      الخطوة 3: اضبط Hermes​

      الخيار A: الإعداد التفاعلي​

      hermes gateway setup

      اختر Feishu / Lark واملأ الحقول المطلوبة.

      الخيار B: الإعداد اليدوي​

      أضف ما يلي إلى ~/.hermes/.env:

      FEISHU_APP_ID=cli_xxx
      FEISHU_APP_SECRET=secret_xxx
      FEISHU_DOMAIN=feishu
      FEISHU_CONNECTION_MODE=websocket

      # Optional but strongly recommended
      FEISHU_ALLOWED_USERS=ou_xxx,ou_yyy
      FEISHU_HOME_CHANNEL=oc_xxx

      يقبل FEISHU_DOMAIN القيم التالية:

      • feishu لـ Feishu في الصين
      • lark لـ Lark الدولي

      الخطوة 4: شغّل Gateway​

      hermes gateway

      ثم راسل البوت من Feishu/Lark للتأكد من أن الاتصال يعمل.

      المحادثة الرئيسية (Home Chat)​

      استخدم /set-home في محادثة على Feishu/Lark لتعيينها قناةً رئيسية (home channel) لنتائج مهام cron والإشعارات العابرة للمنصات.

      يمكنك أيضًا ضبطها مسبقًا:

      FEISHU_HOME_CHANNEL=oc_xxx

      الأمان​

      قائمة السماح للمستخدمين​

      للاستخدام في بيئة الإنتاج، اضبط قائمة سماح بمعرّفات Feishu Open IDs:

      FEISHU_ALLOWED_USERS=ou_xxx,ou_yyy

      إذا تركت قائمة السماح فارغة، فقد يتمكن أي شخص يستطيع الوصول إلى البوت من استخدامه. في المحادثات الجماعية، تُطابَق قائمة السماح مع open_id الخاص بالمرسل قبل معالجة الرسالة.

      مفتاح تشفير Webhook​

      عند التشغيل في وضع webhook، اضبط مفتاح تشفير لتفعيل التحقق من توقيع حمولات webhook الواردة:

      FEISHU_ENCRYPT_KEY=your-encrypt-key

      تجد هذا المفتاح في قسم Event Subscriptions ضمن إعدادات تطبيق Feishu. عند ضبطه، يتحقق المحوّل من كل طلب webhook باستخدام خوارزمية التوقيع التالية:

      SHA256(timestamp + nonce + encrypt_key + body)

      تُقارَن قيمة الـ hash المحسوبة بالترويسة x-lark-signature باستخدام مقارنة آمنة من هجمات التوقيت (timing-safe). وتُرفض الطلبات ذات التوقيعات غير الصالحة أو المفقودة بالرمز HTTP 401.

      نصيحة

      في وضع WebSocket، يتولى SDK نفسه التحقق من التوقيع، لذا يكون FEISHU_ENCRYPT_KEY اختياريًا. أما في وضع webhook، فيُوصى به بشدة لبيئة الإنتاج.

      Verification Token​

      طبقة مصادقة إضافية تتحقق من الحقل token داخل حمولات webhook:

      FEISHU_VERIFICATION_TOKEN=your-verification-token

      تجد هذا الـ token أيضًا في قسم Event Subscriptions ضمن تطبيق Feishu. عند ضبطه، يجب أن تحتوي كل حمولة webhook واردة على token مطابق داخل الكائن header. وتُرفض القيم غير المتطابقة بالرمز HTTP 401.

      يمكن استخدام FEISHU_ENCRYPT_KEY و FEISHU_VERIFICATION_TOKEN معًا لتحقيق دفاع متعدد الطبقات (defense in depth).

      سياسة رسائل المجموعات​

      يتحكم متغير البيئة FEISHU_GROUP_POLICY في ما إذا كان Hermes يردّ في المحادثات الجماعية وكيفية ذلك:

      FEISHU_GROUP_POLICY=allowlist   # default
      القيمةالسلوك
      openيردّ Hermes على إشارات @mention من أي مستخدم في أي مجموعة.
      allowlistلا يردّ Hermes إلا على إشارات @mention من المستخدمين المُدرجين في FEISHU_ALLOWED_USERS.
      disabledيتجاهل Hermes جميع رسائل المجموعات كليًا.

      في جميع الأوضاع، يجب الإشارة إلى البوت صراحةً بـ @mention (أو @all) في المجموعة قبل معالجة الرسالة. أما الرسائل المباشرة فتتجاوز هذا الشرط دائمًا.

      اضبط FEISHU_REQUIRE_MENTION=false ليقرأ Hermes جميع رسائل المجموعة دون اشتراط @mention:

      FEISHU_REQUIRE_MENTION=false

      للتحكم على مستوى كل محادثة، اضبط require_mention ضمن مدخل في group_rules — راجع التحكم في الوصول لكل مجموعة أدناه.

      هوية البوت​

      يكتشف Hermes تلقائيًا قيمة open_id والاسم المعروض للبوت عند بدء التشغيل. لا تحتاج إلى ضبط هذه القيم يدويًا إلا عندما يتعذّر على الاكتشاف التلقائي الوصول إلى Feishu API، أو عندما يستخدم تطبيقك معرّفات مستخدمين مقيّدة بنطاق المستأجر (tenant-scoped):

      FEISHU_BOT_OPEN_ID=ou_xxx     # only when auto-detection fails
      FEISHU_BOT_USER_ID=xxx        # required if your app uses sender_id_type=user_id
      FEISHU_BOT_NAME=MyBot         # only when auto-detection fails

      المراسلة بين البوتات​

      افتراضيًا، يتجاهل Hermes الرسائل التي ترسلها بوتات أخرى. فعّل المراسلة بين البوتات عندما تريد أن يشارك Hermes في تنسيق A2A أو يتلقى إشعارات من بوتات أخرى في المجموعة نفسها.

      FEISHU_ALLOW_BOTS=mentions   # default: none
      القيمةالسلوك
      noneتجاهل جميع الرسائل الواردة من البوتات الأخرى (الافتراضي).
      mentionsالقبول فقط عندما يشير البوت الآخر إلى Hermes بـ @mention.
      allقبول كل رسائل البوتات الأخرى.

      يمكن ضبطه أيضًا عبر feishu.allow_bots في config.yaml (وتكون الأولوية لمتغير البيئة عند ضبط الاثنين).

      لا حاجة إلى إضافة البوتات الأخرى إلى FEISHU_ALLOWED_USERS — فقائمة السماح تلك تنطبق على المرسلين من البشر فقط.

      امنح النطاق application:bot.basic_info:read لعرض أسماء البوتات الأخرى؛ وبدونه، تُوجَّه رسائل البوتات الأخرى بشكل صحيح لكنها تظهر بقيمة open_id الخاصة بها.

      إجراءات البطاقات التفاعلية​

      عندما ينقر المستخدمون على الأزرار أو يتفاعلون مع البطاقات التفاعلية التي يرسلها البوت، يوجّه المحوّل هذه التفاعلات كأحداث أوامر اصطناعية /card:

      • تتحول نقرات الأزرار إلى: /card button {"key": "value", ...}
      • تُضمَّن حمولة value الخاصة بالإجراء من تعريف البطاقة بصيغة JSON.
      • تُزال تكرارات إجراءات البطاقات ضمن نافذة زمنية مدتها 15 دقيقة لمنع المعالجة المزدوجة.

      تستخدم مطالبات التحديث التي يطلقها gateway بطاقة Feishu أصلية بخياري Yes / No بدلًا من الرجوع إلى ردود نصية عادية. عندما يحتاج hermes update --gateway إلى تأكيد، يسجّل المحوّل الإجابة المختارة في ملف .update_response الخاص بـ Hermes ويستبدل البطاقة مباشرةً بحالة محسومة.

      تُرسَل أحداث إجراءات البطاقات بالنوع MessageType.COMMAND، لذا تمر عبر pipeline معالجة الأوامر المعتاد.

      وهكذا أيضًا تعمل الموافقة على الأوامر — فعندما يحتاج الوكيل إلى تنفيذ أمر خطير، يرسل بطاقة تفاعلية تحتوي على الأزرار Allow Once / Session / Always / Deny. ينقر المستخدم على أحدها، فيعيد callback إجراء البطاقة قرار الموافقة إلى الوكيل.

      إعدادات تطبيق Feishu المطلوبة​

      تحتاج البطاقات التفاعلية إلى الإعدادات التالية في Feishu Developer Console. والعَرَض المعتاد لوجود نقص هنا هو الخطأ 200340 عند نقر المستخدمين على أزرار البطاقة.

      1. اشترك في callback إجراء البطاقة (وليس كحدث): في Development Configuration > Events and Callbacks، افتح تبويب Callback Configuration — وهو منفصل عن تبويب Event Configuration الذي يوجد فيه im.message.receive_v1 — وأضف card.action.trigger ضمن Subscribed Callbacks. إضافته كحدث لا تؤدي إلى تسليم نقرات الأزرار.

      2. اضبط وضع تسليم callback: في التبويب نفسه، اختر Long Connection عندما يعمل Hermes في وضع websocket (إذ يستقبل Lark SDK الـ callback عبر الاتصال القائم)، أو أدخل عنوان URL للطلب في وضع webhook (وهو endpoint نفسه المستخدم لـ webhook الأحداث، مثل https://your-server:8765/feishu/webhook). يجب أن يتمكن Feishu من الوصول إلى هذا العنوان وحلّه؛ وإلا فستفشل النقرات بالخطأ 200342/200343.

      3. فعّل قدرة البطاقات التفاعلية: في App Features > Bot، تأكد من تفعيل مفتاح Interactive Card.

      4. انشر إصدارًا جديدًا من التطبيق: لا تسري تغييرات callback إلا بعد نشر Version Management > Create version (واعتماده، في تطبيقات المؤسسات). ووصف Feishu نفسه للخطأ 200340 هو "the application has not configured the card callback address or the configured address is invalid … ensure that you have created and published the latest version of the app".

      تحذير

      بدون callback منشور للبطاقات، سيظل Feishu قادرًا على إرسال البطاقات التفاعلية بنجاح (فالإرسال لا يتطلب سوى الصلاحية im:message:send)، لكن النقر على أي زر يُرجع الخطأ 200340. تبدو البطاقة وكأنها تعمل — ولا يظهر الخطأ إلا عندما يتفاعل معها المستخدم، ولا تصل النقرة إلى Hermes أبدًا (فلا يُسجَّل شيء)، لأن Feishu يرفضها قبل تسليم الـ callback.

      يشير رمزا الخطأ 200672 / 200673 إلى أن الـ callback وصل فعلًا إلى Hermes وأن Feishu رفض الاستجابة؛ إذا ظهرا لك، فيُرجى فتح issue مع أسطر gateway.log المطابقة.

      الرد الذكي على تعليقات المستندات​

      إلى جانب المحادثات، يستطيع المحوّل أيضًا الرد على إشارات @ المتروكة على مستندات Feishu/Lark. عندما يعلّق مستخدم على مستند (على نص محدَّد أو على المستند بأكمله) ويشير إلى البوت بـ @mention، يقرأ Hermes المستند إلى جانب سلسلة التعليقات المحيطة، وينشر ردًا مولَّدًا بواسطة LLM مباشرةً في السلسلة.

      بالاعتماد على الحدث drive.notice.comment_add_v1، يقوم المعالج (handler) بما يلي:

      • يجلب محتوى المستند والتسلسل الزمني للتعليقات بالتوازي (20 رسالة لسلاسل التعليقات على المستند بأكمله، و12 لسلاسل التعليقات على نص محدَّد).
      • يشغّل الوكيل باستخدام toolsets feishu_doc + feishu_drive مقيّدةً بجلسة ذلك التعليق وحده.
      • يقسّم الردود إلى أجزاء من 4000 حرف وينشرها كردود ضمن السلسلة.
      • يخزّن الجلسات الخاصة بكل مستند مؤقتًا لمدة ساعة واحدة بحدّ أقصى 50 رسالة، حتى تحتفظ التعليقات اللاحقة على المستند نفسه بالسياق.

      التحكم في الوصول بثلاثة مستويات​

      الردود على تعليقات المستندات لا تعمل إلا بمنح صريح — فلا يوجد وضع ضمني للسماح للجميع. تُحدَّد الصلاحيات بالترتيب التالي (أول تطابق هو المعتمد، لكل حقل على حدة):

      1. مستند محدَّد — قاعدة مقيّدة بـ token مستند معيّن.
      2. حرف بدل (Wildcard) — قاعدة تطابق نمطًا من المستندات.
      3. المستوى الأعلى — القاعدة الافتراضية لمساحة العمل.

      تتوفر سياستان لكل قاعدة:

      • allowlist — قائمة ثابتة من المستخدمين / المستأجرين.
      • pairing — القائمة الثابتة ∪ مخزن الموافقات وقت التشغيل. مفيدة عند الطرح التدريجي حيث يستطيع المشرفون منح الوصول مباشرةً.

      توجد القواعد في ~/.hermes/feishu_comment_rules.json (ومنح الاقتران في ~/.hermes/feishu_comment_pairing.json) مع إعادة تحميل فورية (hot-reload) مخزّنة مؤقتًا بحسب وقت التعديل (mtime) — فتسري التعديلات مع حدث التعليق التالي دون إعادة تشغيل gateway.

      CLI:

      # Inspect current rules and pairing state
      python -m gateway.platforms.feishu_comment_rules status

      # Simulate an access check for a specific doc + user
      python -m gateway.platforms.feishu_comment_rules check <fileType:fileToken> <user_open_id>

      # Manage pairing grants at runtime
      python -m gateway.platforms.feishu_comment_rules pairing list
      python -m gateway.platforms.feishu_comment_rules pairing add <user_open_id>
      python -m gateway.platforms.feishu_comment_rules pairing remove <user_open_id>

      إعدادات تطبيق Feishu المطلوبة​

      إضافةً إلى صلاحيات المحادثات والبطاقات الممنوحة بالفعل، أضف حدث تعليقات drive:

      • اشترك في drive.notice.comment_add_v1 ضمن Event Subscriptions.
      • امنح النطاقين docs:doc:readonly و drive:drive:readonly حتى يتمكن المعالج من قراءة محتوى المستند.

      أحداث دعوات الاجتماعات​

      يمكنك دعوة بوت Hermes على Feishu/Lark إلى اجتماع فيديو بالطريقة نفسها التي تدعو بها مشاركًا بشريًا. عندما يستقبل البوت حدث دعوة الاجتماع، يستطيع Hermes أن يبدأ تلقائيًا دورًا للوكيل يحاول فيه الانضمام إلى الاجتماع.

      بالاعتماد على الحدث vc.bot.meeting_invited_v1، يسير التدفق على النحو التالي:

      • يدعو مستخدمٌ البوتَ إلى اجتماع فيديو على Feishu/Lark.
      • يرسل Feishu/Lark حدث دعوة الاجتماع إلى Hermes.
      • يستخرج Hermes صاحب الدعوة وموضوع الاجتماع ورقمه.
      • إذا كان صاحب الدعوة مصرّحًا له وفق قائمة السماح أو سياسة الاقتران المعتادة في gateway، يتلقى الوكيل رقم الاجتماع ويحاول الانضمام تلقائيًا.
      • إذا كانت الدعوة غير سليمة البنية، أو تعذّر على الوكيل الانضمام، يُسقط Hermes الحدث أو يردّ على صاحب الدعوة بتوضيح موجز.

      تُتجاهَل الدعوات غير سليمة البنية التي لا تتضمن صاحب الدعوة و meeting_no معًا.

      إعدادات تطبيق Feishu المطلوبة​

      إضافةً إلى صلاحيات المحادثات والبطاقات الممنوحة بالفعل، أضف حدث دعوة اجتماع الفيديو:

      • اشترك في vc.bot.meeting_invited_v1 ضمن Event Subscriptions.
      • فعّل نطاق صلاحية Video Conferencing الذي تطلبه وحدة تحكم المطوّرين في Feishu/Lark لهذا الحدث.
      • أبقِ im:message و im:message:send_as_bot مفعّلين حتى يتمكن Hermes من الرد على صاحب الدعوة.
      • تأكد من أن قائمة السماح للمستخدمين أو سياسة الاقتران في gateway تصرّح لصاحب الدعوة. فدعوات الاجتماعات لا تتجاوز فحوصات الوصول المعتادة في gateway.

      دعم الوسائط​

      الوارد (الاستقبال)​

      يستقبل المحوّل أنواع الوسائط التالية من المستخدمين ويخزّنها مؤقتًا:

      النوعالامتداداتكيفية المعالجة
      الصور.jpg, .jpeg, .png, .gif, .webp, .bmpتُنزَّل عبر Feishu API وتُخزَّن مؤقتًا محليًا
      الصوت.ogg, .mp3, .wav, .m4a, .aac, .flac, .opus, .webmتُنزَّل وتُخزَّن مؤقتًا؛ ويُستخرج محتوى الملفات النصية الصغيرة تلقائيًا
      الفيديو.mp4, .mov, .avi, .mkv, .webm, .m4v, .3gpتُنزَّل وتُخزَّن مؤقتًا كمستندات
      الملفات.pdf, .doc, .docx, .xls, .xlsx, .ppt, .pptx وغيرهاتُنزَّل وتُخزَّن مؤقتًا كمستندات

      تُستخرج أيضًا الوسائط الموجودة في رسائل النص المنسّق (post) وتُخزَّن مؤقتًا، بما في ذلك الصور المضمّنة ومرفقات الملفات.

      بالنسبة إلى المستندات النصية الصغيرة (.txt و .md)، يُحقن محتوى الملف تلقائيًا في نص الرسالة حتى يتمكن الوكيل من قراءته مباشرةً دون الحاجة إلى أدوات.

      الصادر (الإرسال)​

      الدالةما الذي ترسله
      sendرسائل نصية أو رسائل post منسّقة (يُكتشف النوع تلقائيًا بناءً على وجود محتوى markdown)
      send_image / send_image_fileترفع الصورة إلى Feishu، ثم ترسلها كفقاعة صورة أصلية (مع تعليق اختياري)
      send_documentترفع الملف إلى Feishu API، ثم ترسله كمرفق ملف
      send_voiceترفع الملف الصوتي كمرفق ملف في Feishu
      send_videoترفع الفيديو وترسله كرسالة وسائط أصلية
      send_animationتُحوَّل صور GIF إلى مرفقات ملفات (إذ لا يدعم Feishu فقاعات GIF أصلية)

      يجري توجيه رفع الملفات تلقائيًا بناءً على الامتداد:

      • .ogg و .opus → تُرفع كصوت opus
      • .mp4 و .mov و .avi و .m4v → تُرفع كوسائط mp4
      • .pdf و .doc(x) و .xls(x) و .ppt(x) → تُرفع بنوع المستند الخاص بها
      • كل ما عدا ذلك → يُرفع كملف stream عام

      عرض Markdown والرجوع الاحتياطي من Post​

      عندما يحتوي النص الصادر على تنسيق markdown (عناوين، أو خط عريض، أو قوائم، أو كتل كود، أو روابط، وغيرها)، يرسله المحوّل تلقائيًا كرسالة post في Feishu مع وسم md مضمَّن بدلًا من نص عادي، ما يتيح عرضًا منسّقًا في عميل Feishu.

      إذا رفضت Feishu API حمولة post (مثلًا بسبب بنى markdown غير مدعومة)، يرجع المحوّل تلقائيًا إلى الإرسال كنص عادي بعد إزالة تنسيق markdown. يضمن هذا الرجوع الاحتياطي على مرحلتين تسليم الرسائل دائمًا.

      تُرسَل الرسائل النصية العادية (التي لا يُكتشف فيها markdown) بنوع الرسالة البسيط text.

      تفاعلات حالة المعالجة​

      أثناء عمل الوكيل، يعرض البوت تفاعل Typing على رسالتك. ويُزال هذا التفاعل عند وصول الرد، أو يُستبدل بـ CrossMark إذا فشلت المعالجة.

      اضبط FEISHU_REACTIONS=false لإيقافه.

      الحماية من الرسائل المتلاحقة والتجميع​

      يتضمن المحوّل (adapter) آلية debouncing لدفعات الرسائل السريعة المتلاحقة، تجنّبًا لإغراق الوكيل:

      تجميع النصوص​

      تُدمج مرفقات الوسائط المتعددة المرسلة بشكل متتابع وسريع (مثل سحب عدة صور) في حدث واحد:

      الإعدادمتغير البيئةالقيمة الافتراضية

      المعالجة التسلسلية لكل محادثة​

      تُعالَج الرسائل ضمن المحادثة الواحدة تسلسليًا (واحدة تلو الأخرى) للحفاظ على ترابط المحادثة. لكل محادثة قفلها (lock) الخاص، لذا تُعالَج الرسائل في المحادثات المختلفة بالتزامن.

      حدّ المعدل (وضع Webhook)​

      في وضع webhook، يفرض المحوّل حدًّا للمعدل (rate limit) لكل عنوان IP للحماية من إساءة الاستخدام:

      • النافذة: نافذة منزلقة مدتها 60 ثانية
      • الحد: 120 طلبًا لكل نافذة لكل ثلاثية (app_id, path, IP)
      • سقف التتبّع: تتبّع ما يصل إلى 4096 مفتاحًا فريدًا (لمنع النمو غير المحدود في استهلاك الذاكرة)

      تتلقى الطلبات التي تتجاوز الحد الرمز HTTP 429 (Too Many Requests).

      تتبّع الحالات الشاذة في Webhook​

      يتتبّع المحوّل استجابات الخطأ المتتالية لكل عنوان IP. بعد 25 خطأً متتاليًا من عنوان IP نفسه خلال نافذة مدتها 6 ساعات، يُسجَّل تحذير. يساعد ذلك على اكتشاف العملاء ذوي الإعدادات الخاطئة أو محاولات الاستكشاف (probing).

      حمايات إضافية لـ webhook:

      • حدّ حجم جسم الطلب: 1 MB كحد أقصى
      • مهلة قراءة جسم الطلب: 30 ثانية
      • فرض Content-Type: لا يُقبل إلا application/json

      ضبط WebSocket​

      عند استخدام وضع websocket، يمكنك تخصيص سلوك إعادة الاتصال وإرسال ping:

      platforms:
        feishu:
          extra:
            ws_reconnect_interval: 120   # Seconds between reconnect attempts (default: 120)
            ws_ping_interval: 30         # Seconds between WebSocket pings (optional; SDK default if unset)
      الإعدادمفتاح الإعدادالقيمة الافتراضيةالوصف
      الفاصل الزمني لإعادة الاتصالws_reconnect_interval120sمدة الانتظار بين محاولات إعادة الاتصال
      الفاصل الزمني لـ pingws_ping_interval(القيمة الافتراضية في SDK)معدل تكرار رسائل ping للحفاظ على اتصال WebSocket (keepalive)

      التحكم في الوصول لكل مجموعة​

      إلى جانب الإعداد العام FEISHU_GROUP_POLICY، يمكنك ضبط قواعد دقيقة لكل محادثة جماعية باستخدام group_rules في config.yaml:

      platforms:
        feishu:
          extra:
            default_group_policy: "open"     # Default for groups not in group_rules
            admins:                          # Users who can manage bot settings
              - "ou_admin_open_id"
            group_rules:
              "oc_group_chat_id_1":
                policy: "allowlist"          # open | allowlist | blacklist | admin_only | disabled
                allowlist:
                  - "ou_user_open_id_1"
                  - "ou_user_open_id_2"
              "oc_group_chat_id_2":
                policy: "admin_only"
              "oc_group_chat_id_3":
                policy: "blacklist"
                blacklist:
                  - "ou_blocked_user"
              "oc_free_chat":
                policy: "open"
                require_mention: false       # overrides FEISHU_REQUIRE_MENTION for this chat
      السياسةالوصف
      openيستطيع أي شخص في المجموعة استخدام البوت
      allowlistلا يستطيع استخدام البوت إلا المستخدمون المُدرجون في allowlist الخاصة بالمجموعة
      blacklistيستطيع الجميع استخدام البوت باستثناء المستخدمين المُدرجين في blacklist الخاصة بالمجموعة
      admin_onlyلا يستطيع استخدام البوت في هذه المجموعة إلا المستخدمون المُدرجون في قائمة admins العامة
      disabledيتجاهل البوت جميع الرسائل في هذه المجموعة

      اضبط require_mention: false ضمن مدخل في group_rules لتخطّي اشتراط @mention لتلك المحادثة تحديدًا. وعند إغفاله، ترث المحادثة القيمة العامة لـ FEISHU_REQUIRE_MENTION.

      ترجع المجموعات غير المُدرجة في group_rules إلى default_group_policy (وقيمته الافتراضية هي قيمة FEISHU_GROUP_POLICY).

      تظهر رسائل post كنص عاديرفضت Feishu API حمولة post؛ وهذا سلوك رجوع احتياطي طبيعي. راجع السجلات لمزيد من التفاصيل.
      البوت لا يستقبل الصور/الملفاتامنح نطاقَي الصلاحية im:message و im:resource لتطبيق Feishu
      لم تُكتشف هوية البوت تلقائيًاغالبًا ما تكون مشكلة شبكة عابرة في الوصول إلى endpoint معلومات البوت في Feishu. كحلّ مؤقت، اضبط FEISHU_BOT_OPEN_ID و FEISHU_BOT_NAME يدويًا.
      لا تزال رسائل البوتات الأخرى تُتجاهَل بعد تفعيل FEISHU_ALLOW_BOTSلا يستطيع Hermes التعرّف على نفسه بعد — اضبط FEISHU_BOT_OPEN_ID (و FEISHU_BOT_USER_ID إذا كان تطبيقك يستخدم sender_id_type=user_id).
      تظهر البوتات الأخرى بالقيمة ou_xxxxxx بدلًا من أسمائهاامنح النطاق application:bot.basic_info:read.
      الخطأ 200340 (ويظهر أيضًا بالرمز 220340) عند النقر على أزرار الموافقةلا يملك Feishu callback صالحًا للبطاقات في إصدار التطبيق المنشور: أضف card.action.trigger ضمن تبويب Callback Configuration (وليس Event Configuration)، واختر Long Connection أو عنوان URL للطلب، وفعّل Interactive Card، ثم انشر إصدارًا جديدًا. راجع إعدادات تطبيق Feishu المطلوبة. لا تصل النقرة إلى Hermes أبدًا، لذا لا يظهر شيء في gateway.log.
      الخطأ 200342 / 200343 عند النقر على أزرار الموافقةفي وضع webhook: لا يستطيع Feishu الاتصال بعنوان URL لطلب الـ callback أو حلّه. أصلح عنوان URL أو انتقل إلى Long Connection.
      Webhook rate limit exceededأكثر من 120 طلبًا في الدقيقة من عنوان IP نفسه. يدل ذلك عادةً على خطأ في الإعدادات أو على حلقة متكررة.

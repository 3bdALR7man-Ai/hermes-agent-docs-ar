      Hermes Relay (الموصِّل)

      تجريبي

      Relay ميزة تجريبية. قد يتغير عقد الاتصال (wire contract) ومخطط المصادقة والإعدادات دون دورة إهمال (deprecation) مسبقة، ما دام النظام قيد التحقق.

      Hermes Relay ليس منصة محادثة بحد ذاته — بل هو نظام موصِّلات (connector system) يتيح للـ gateway الخاص بك أن يكون واجهة أمامية لمنصة مراسلة حقيقية واحدة أو أكثر (Discord، Telegram، Slack، WhatsApp، …) دون الاحتفاظ بأي بيانات اعتماد للمنصات. إذ تتولى خدمة منفصلة، هي الموصِّل (connector)، امتلاك tokens البوتات والمقابس (sockets) الخاصة بالمنصات. يتصل الـ gateway خارجيًا بالموصِّل عبر اتصال WebSocket واحد مُصادَق عليه، ويستلم واصفًا للإمكانات (capability descriptor) أثناء المصافحة (handshake)، ثم يتبادل عبر ذلك المقبس أحداث رسائل موحَّدة (واردة) وإجراءات (صادرة).

      الخصائص الرئيسية:

      • اتصالات شبكية صادرة فقط. لا يفتح الـ gateway أي منفذ وارد أبدًا. تعود الرسائل الواردة عبر اتصال WebSocket نفسه الذي أنشأه الـ gateway، لذا يعمل relay خلف NAT وعلى المضيفين الذين لا يملكون عنوان IP عامًا.
      • لا أسرار للمنصات على الـ gateway. تبقى tokens البوتات على الموصِّل. وتُعاد استضافة عناوين URL للوسائط المحمية بالمصادقة على جانب الموصِّل، فلا تعبر بيانات اعتماد المنصات الاتصال أبدًا.
      • مستقل عن المنصة. يعرف الـ gateway ما تستطيع المنصة الأمامية فعله (حدود طول الرسائل، ولهجة markdown، ودعم التحرير وسلاسل الرسائل والبث المتدفق، والمجموعة الدقيقة من العمليات المدعومة) من واصف المصافحة، لا من منطق مُضمَّن مسبقًا لكل منصة.

      توجد الواجهة الرسمية بين الـ gateway ⇄ الموصِّل في المستودع ضمن docs/relay-connector-contract.md.

      متى تستخدم Relay​

      صُمّم Relay لعمليات النشر التي تدير فيها خدمة موصِّل مستضافة أو مشتركة جانب المنصة — مثل الاستضافة متعددة المستأجرين (multi-tenant) حيث يكون بوت مشترك واحد واجهة أمامية لوكلاء كثير من المستخدمين، أو الإعدادات التي لا تريد فيها وجود tokens البوتات على جهاز الـ gateway. أما إذا كنت تشغّل بوتاتك الخاصة مباشرة، فاستخدم محوِّلات المنصات الأصلية (Telegram، Discord، وغيرها) بدلًا من ذلك.

      التسجيل (Enrollment)​

      يُصادِق الـ gateway المستضاف ذاتيًا لدى الموصِّل بسرّ خاص بكل gateway. يستبدل الأمر hermes gateway enroll enrollment token صالحًا لمرة واحدة (يُصدره الموصِّل عند تجهيز مسار المستأجر الخاص بك ويُسلَّم مع إعدادات الـ gateway) بذلك السرّ:

      hermes gateway enroll \
        --token <enrollment-token> \
        --connector-url wss://connector.example.com/relay

      ما يفعله:

      1. يستخرج access token جديدًا لـ Nous Portal من تسجيل دخولك الحالي (~/.hermes/auth.json) — وهذا يثبت أي مؤسسة (مستأجر) في Nous تملكها. إذا كان gateway.idp.token_url مضبوطًا، فيُستخدم مزوّد الهوية (IdP) الخاص بك بدلًا من ذلك (مسار البيئات المعزولة عن الشبكة / IdP المستضاف ذاتيًا، دون أي دور لـ Nous Portal): فإذا ضُبط client_id/client_secret ينفّذ منحة OAuth2 عامة من نوع client-credentials؛ وإذا لم يُضبط أيٌّ منهما يُعامَل الـ URL كـ token endpoint محيطي (طلب GET عادي يكون متن استجابته هو الـ token — وهو نمط خادم البيانات الوصفية، مثل $DOMINO_API_PROXY/access-token في Domino). ضبط واحدة فقط من قيمتي بيانات الاعتماد يُعدّ خطأً.
      2. يرسل عبر POST الـ enrollment token ومعرّف الـ gateway إلى endpoint /relay/enroll في الموصِّل عبر TLS.
      3. يتحقق الموصِّل من الـ token (التوقيع، والاستخدام لمرة واحدة، ومطابقة المستأجر)، ثم يُصدر سرًّا خاصًا بالـ gateway ومفتاح تسليم خاصًا بالمستأجر، ويعيدهما مرة واحدة فقط.
      4. يحفظ بيانات الاعتماد في ~/.hermes/.env: GATEWAY_RELAY_ID، GATEWAY_RELAY_SECRET، GATEWAY_RELAY_DELIVERY_KEY (إضافة إلى GATEWAY_RELAY_URL / GATEWAY_RELAY_WAKE_URL عند توفيرهما).

      أعد تشغيل الـ gateway بعد ذلك كي يلتقط البيئة الجديدة.

      الخيارات (flags):

      الخيارالوصف
      --tokenالـ enrollment token الصالح لمرة واحدة. يمكن ضبطه أيضًا عبر GATEWAY_RELAY_ENROLL_TOKEN.
      --connector-urlURL الأساسي للموصِّل أو URL الخاص بـ relay (wss://…/relay أو https://…). يمكن ضبطه أيضًا عبر GATEWAY_RELAY_URL أو gateway.relay_url في config.yaml.
      --gateway-idمعرّف ثابت لنسخة الـ gateway هذه (يُستخدم لدقة التحكم في مفتاح الإيقاف الطارئ kill-switch). القيمة الافتراضية gw-<hostname>.
      --wake-urlURL اختياري يمكن الوصول إليه، ينبّهه الموصِّل (بطلب GET بلا حمولة) لإيقاظ هذا الـ gateway عند وصول عمل مخزَّن مؤقتًا أثناء خموله. يُحفَظ بوصفه GATEWAY_RELAY_WAKE_URL. وبدونه يظل الـ gateway يستنزف الرسائل المخزَّنة كلما أعاد الاتصال لاحقًا.
      التثبيتات المُدارة

      يرفض hermes gateway enroll العمل في التثبيتات المُدارة/المستضافة — إذ تتولى منصة الاستضافة هناك تجهيز سرّ relay مباشرة في بيئة الحاوية.

      الإعدادات​

      يُفعَّل Relay عند ضبط URL خاص بـ relay الموصِّل. لإبقاء profile ما خارج relay حتى عندما يحقن النشر URL، عطّل المنصة في config.yaml:

      platforms:
        relay:
          enabled: false
      • التعطيل الصريح له الأولوية. مع enabled: false لا يستخرج الـ gateway أي identity token، ولا يجهّز بيانات اعتماد GATEWAY_RELAY_* أو يعيد كتابتها، ولا يسجّل محوِّل relay ولا يرسل سياسة الصلة (relevance policy) — حتى مع ضبط gateway.relay_url أو GATEWAY_RELAY_URL. تتصل محوِّلات المراسلة الأصلية كما لو لم يكن هناك URL لـ relay، ولا يعامل تسليم cron أي منصة على أنها تمر عبر relay.
      • حذف enabled يُبقي التفعيل المعتمد على الـ URL. يظل enabled: true بحاجة إلى URL للموصِّل. أما ضبط gateway.json على enabled: false فهو استرشادي فقط، كما هو الحال مع كل منصة أخرى؛ ضع إلغاء الاشتراك في config.yaml (الخاص بالمستخدم أو المُدار).

      يُستمَد القرار من الملفات نفسها وعملية الدمج نفسها التي يستخدمها مُحمِّل الـ gateway (المستوى الأعلى أو كتلة gateway.platforms، والطبقة المُدارة)، ويُطبَّق وقت التفعيل. أعد تشغيل الـ gateway بعد تغييره؛ فمقبس relay المفتوح لا يُغلَق تلقائيًا. يبقى hermes gateway enroll متاحًا أثناء تعطيل relay وقت التشغيل.

      الإعدادالموضعالمعنى
      GATEWAY_RELAY_URLenv (~/.hermes/.env)عنوان WebSocket URL الخاص بـ relay الموصِّل. يفعّل relay ما لم يُعطَّل صراحةً في إعدادات المنصة.
      gateway.relay_urlconfig.yamlمثل السابق، بصيغة ملف الإعدادات (متغير البيئة له الأولوية).
      GATEWAY_RELAY_IDenvمعرّف نسخة الـ gateway هذه (يكتبه enroll).
      GATEWAY_RELAY_SECRETenvالسرّ الخاص بالـ gateway الذي يُصادِق ترقية اتصال WebSocket (يكتبه enroll).
      GATEWAY_RELAY_DELIVERY_KEYenvمفتاح التسليم الخاص بالمستأجر (يكتبه enroll؛ ويُحتفَظ به للتوافق المستقبلي).
      GATEWAY_RELAY_WAKE_URL / gateway.relay_wake_urlenv / config.yamlوجهة اختيارية لتنبيه الإيقاظ للـ gateways الخاملة أو المعلّقة.
      GATEWAY_RELAY_PLATFORMSenvقائمة مفصولة بفواصل بالمنصات التي يكون هذا الـ gateway واجهة أمامية لها عبر اتصال واحد (مثل discord,telegram). تُضبط عادةً من قِبل النشر أو أداة التنسيق (orchestrator).
      GATEWAY_RELAY_BOT_IDSenvخريطة JSON لهويات البوتات لكل منصة، مثل {"discord": {"botId": "…"}}. تُستخدم مع GATEWAY_RELAY_PLATFORMS.
      gateway.idp.token_urlconfig.yamlعند ضبطه، يُصادِق التسجيل والتجهيز لدى IdP الخاص بك بدلًا من Nous Portal: عبر OAuth2 client-credentials عندما يُضبط gateway.idp.client_id/client_secret أيضًا؛ وإلا فعبر token endpoint محيطي (طلب GET عادي يعيد الـ token، إما خامًا أو بصيغة {"access_token": …}).

      الإمكانات المدعومة​

      يُتفاوَض أثناء المصافحة على ما يعمل فعليًا عبر اتصال relay: إذ يُعلن الموصِّل قائمة supported_ops، ولا يستخدم الـ gateway إلا العمليات التي يُعلنها الموصِّل صراحةً (ترجع الموصِّلات الأقدم احتياطيًا إلى مجموعة قديمة هي send/edit/typing/follow_up). كذلك تأتي علامات الإمكانات الخاصة بكل منصة (البث المتدفق القائم على التحرير، وسلاسل الرسائل، وبث المسودات، ولهجة markdown، وحد طول الرسالة) من واصف المصافحة. ورهنًا بذلك التفاوض، يدعم relay ما يلي:

      • الرسائل النصية والبث المتدفق — الإرسال والردود، والبث المتدفق التدريجي القائم على التحرير عندما تدعم المنصة الأمامية تحرير الرسائل؛ وإلا تتراجع المخرجات إلى رسالة واحدة لكل مقطع.
      • الوسائط في الاتجاهين — تُرفع الصور والملاحظات الصوتية والصوت والفيديو والمستندات الصادرة إلى الموصِّل (أو يُشار إليها عبر URL عام)، وتُسلَّم عبر مسار الرفع الأصلي لكل منصة، مع التعليقات النصية. تُحوَّل المرفقات الواردة إلى ملفات محلية للوكيل؛ وتُعاد استضافة عناوين URL للمنصات المحمية بالمصادقة على جانب الموصِّل، فلا تصل بيانات اعتماد المنصات إلى الـ gateway أبدًا. الحد الأقصى لإعادة استضافة الوسائط 25 MB، وتنتهي صلاحيتها (بعد نحو ساعة).
      • مطالبات تفاعلية أصلية — تُعرض موافقات التنفيذ والتأكيدات وأسئلة التوضيح باستخدام عناصر تحكم أصلية للمنصة (أزرار Discord، ولوحات المفاتيح المضمّنة في Telegram، وإجراءات Slack Block Kit، ورسائل الأزرار/القوائم في WhatsApp) بدلًا من البدائل النصية المرقّمة. تعود نقرات الأزرار كاستجابات مُصادَق عليها من المستخدم الذي نقر فعلًا، لذا تُطبَّق بوابات التفويض في الـ gateway تمامًا كما تُطبَّق على الرد المكتوب. ويُفرَض انتهاء صلاحية المطالبات على جانب الـ gateway.
      • دورة حياة تفاعلات الإقرار — تعمل تفاعلات حالة المعالجة الخاصة بالبوت (👀 أثناء العمل، و ✅/❌ عند الاكتمال) عبر relay. التفاعلات بأفضل جهد: فشل تفاعل ما لا يُفشل الدور أبدًا.
      • دورة حياة سلاسل الرسائل — إنشاء سلاسل التسليم وإعادة تسمية السلاسل (بما في ذلك إعادة التسمية الدلالية التي يقترح LLM عناوينها) عبر عمليتَي thread_create / thread_rename المجرّدتين عن المنصة، مع حماية من الكتابة فوق التسمية بحيث تكون الأولوية لإعادة التسمية اليدوية التي يجريها شخص. يعتمد التوفر على المنصة (مثلًا لا يمكن إعادة تسمية سلاسل Slack؛ وWhatsApp لا يملك سلاسل رسائل).
      • مؤشرات الكتابة — يُرسل الـ gateway مؤشر الكتابة (وإيقافه) عبر الموصِّل أثناء المعالجة.
      • البيانات الوصفية للمحادثة — تُمرَّر استعلامات get_chat_info إلى الموصِّل عندما يُعلن دعمها.
      • التسليم المخزَّن والإيقاظ — عندما يصبح الـ gateway خاملًا أو ينقطع اتصاله، يخزّن الموصِّل الرسائل الواردة بشكل دائم ويعيد تشغيلها بالترتيب عند إعادة الاتصال (مع اشتراط الإقرار، دون فقدان أو تكرار). وإذا سُجّل URL للإيقاظ، ينبّهه الموصِّل عند وصول عمل مخزَّن لـ gateway نائم.

      الواجهة الأمامية لعدة منصات مدعومة: يمكن لـ gateway واحد أن يكون واجهة أمامية لعدة منصات (مثل Discord و Telegram) عبر اتصال relay واحد، مع وسم كل رسالة صادرة بالمنصة التي تستهدفها.

      استكشاف الأخطاء وإصلاحها​

      فشل التسجيل مع 401 — لم يتمكن الموصِّل من التحقق من identity token الخاص بك. أعد تسجيل الدخول باستخدام hermes auth add nous (أو hermes setup) ثم أعد المحاولة.

      فشل التسجيل مع 403 — الـ enrollment token غير صالح، أو منتهي الصلاحية، أو سبق استخدامه، أو يخص مستأجرًا مختلفًا. الـ enrollment tokens صالحة لمرة واحدة؛ اطلب token جديدًا ممن جهّز مسار المستأجر الخاص بك.

      "Could not reach the connector" — تحقّق من URL الموصِّل. يمكنك لصق عنوان الاتصال wss://…/relay أو العنوان الأساسي https://…؛ إذ تحوّل CLI بينهما تلقائيًا.

      enroll يرفض العمل — أنت في تثبيت مُدار/مستضاف، حيث تتولى منصة الاستضافة تجهيز سرّ relay. التسجيل الذاتي مخصص للـ gateways المستضافة ذاتيًا فقط.

      تظهر منصة relay معطّلة بعد أن كانت تعمل سابقًا — إغلاق اتصال WebSocket بالرمز 4401 بعد مصافحة ناجحة يعني أن سرّ الـ gateway قد أُلغي (مثلًا لأن النسخة أُلغي تجهيزها). يتوقف الـ gateway عمدًا عن إعادة الاتصال ويُبلغ بأن relay معطّل بدلًا من إعادة المحاولة. أما الرمز 4401 قبل أي مصافحة ناجحة فيُعامَل كحالة سباق عابرة ناتجة عن عدم اكتمال التجهيز بعد، وتُعاد المحاولة بشكل طبيعي.

      لم يتغير شيء بعد التسجيل — يقرأ الـ gateway متغيرات GATEWAY_RELAY_* عند بدء التشغيل. أعد تشغيله (hermes gateway restart).

      تتراجع ميزة ما (الأزرار، الوسائط، سلاسل الرسائل…) بصمت إلى نص عادي — لم يُعلن الموصِّل الخاص بمنصتك تلك العملية في supported_ops أثناء المصافحة. يرجع الـ gateway عمدًا إلى السلوك النصي بدلًا من إرسال عملية لا يستطيع الموصِّل التعامل معها.

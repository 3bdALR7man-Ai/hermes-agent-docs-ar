      إعداد Matrix

      يتكامل Hermes Agent مع Matrix، بروتوكول المراسلة المفتوح والاتحادي (federated). يتيح لك Matrix تشغيل homeserver خاص بك أو استخدام homeserver عام مثل matrix.org — في كلتا الحالتين، تحتفظ أنت بالسيطرة على اتصالاتك. يتصل البوت عبر SDK بايثون mautrix، ويعالج الرسائل عبر خط أنابيب Hermes Agent (بما في ذلك استخدام الأدوات، الذاكرة، والاستدلال)، ويستجيب في الوقت الفعلي. يدعم النصوص، مرفقات الملفات، الصور، الصوت، الفيديو، والتشفير التام بين الطرفين (E2EE) الاختياري.

      يعمل Hermes مع أي homeserver لـ Matrix — Synapse أو Conduit أو Dendrite أو matrix.org.

      قبل الإعداد، إليك الجزء الذي يريد معظم الناس معرفته: كيف يتصرف Hermes بمجرد اتصاله.

      كيف يتصرف Hermes​

      السياقالسلوك
      الرسائل المباشرة (DMs)يستجيب Hermes لكل رسالة. لا حاجة إلى @mention. لكل DM جلسته الخاصة. اضبط MATRIX_DM_MENTION_THREADS=true لبدء thread عند الإشارة إلى البوت (@mentioned) في DM.
      الغرف (Rooms)افتراضيًا، يتطلب Hermes إشارة (@mention) للاستجابة. اضبط MATRIX_REQUIRE_MENTION=false أو أضف معرّفات الغرف إلى MATRIX_FREE_RESPONSE_ROOMS لغرف الاستجابة الحرة. تُقبل دعوات الغرف تلقائيًا.
      الـ Threadsيدعم Hermes threads في Matrix (MSC3440). إذا رددت في thread، يُبقي Hermes سياق الـ thread معزولًا عن الخط الزمني الرئيسي للغرفة. الـ threads التي شارك فيها البوت مسبقًا لا تتطلب إشارة.
      الـ Threading التلقائيافتراضيًا، ينشئ Hermes تلقائيًا thread لكل رسالة يستجيب لها في غرفة. يحافظ هذا على عزل المحادثات. اضبط MATRIX_AUTO_THREAD=false لتعطيله. اضبط MATRIX_DM_AUTO_THREAD=true (الافتراضي false) لإنشاء threads تلقائيًا لرسائل DM أيضًا — وهذا مختلف عن MATRIX_DM_MENTION_THREADS، التي تبدأ thread فقط عند الإشارة إلى البوت (@mentioned) في DM.
      الأوامريقبل Hermes أوامر /commands العادية عندما يرسلها عميل Matrix الخاص بك. إذا كان عميلك يحجز / للأوامر المحلية، استخدم !commands بدلًا من ذلك؛ يوحّد Hermes الأسماء البديلة المعروفة لـ !command إلى /command.
      عناصر التحكم التفاعليةيمكن أن تستخدم موافقة الأوامر الخطرة واختيار /model ردود أفعال (reactions) Matrix. يمكن تقييد ردود أفعال الموافقة بالمستخدم الذي طلب الإجراء.
      نشاط التفكير والأدواتيستخدم Matrix أجزاء thread قابلة للتحرير لعرض التفكير/نشاط الأدوات عند تفعيل تقدّم الـ gateway، بحيث لا تُغرق التحديثات الخط الزمني الرئيسي للغرفة.
      الغرف المشتركة بين عدة مستخدمينافتراضيًا، يعزل Hermes سجل الجلسة لكل مستخدم داخل الغرفة. لا يشترك شخصان يتحدثان في نفس الغرفة في نسخة واحدة من المحادثة إلا إذا عطّلت ذلك صراحةً.
      رموز LaTeX الرياضيةتُرسَل $...$ (ضمن السطر) و $$...$$ (منفصلة) في الردود كترميز data-mx-maths الخاص بـ Element، لذا تنسّقها العملاء التي تفعّل Settings → Labs → Render LaTeX maths in messages باستخدام KaTeX. تبقى علامات الدولار غير المزدوجة ($5 or $10) كما هي حرفيًا، ويحتفظ نص body العادي بصيغة TeX الخام للعملاء الأخرى.
      نصيحة

      ينضم البوت تلقائيًا إلى الغرف عند دعوته. فقط ادعُ مستخدم Matrix الخاص بالبوت إلى أي غرفة وسينضم إليها ويبدأ بالاستجابة.

      نموذج الجلسة في Matrix​

      افتراضيًا:

      • لكل DM جلسته الخاصة
      • لكل thread مساحة اسم جلسة خاصة به
      • لكل مستخدم في غرفة مشتركة جلسته الخاصة داخل تلك الغرفة

      يُتحكم في هذا عبر config.yaml:

      group_sessions_per_user: true

      اضبطه على false فقط إذا كنت تريد صراحةً محادثة واحدة مشتركة للغرفة بأكملها:

      group_sessions_per_user: false

      يمكن أن تكون الجلسات المشتركة مفيدة لغرفة تعاونية، لكنها تعني أيضًا:

      • يشارك المستخدمون نمو السياق وتكاليف الـ token
      • يمكن لمهمة طويلة تعتمد بكثرة على الأدوات لشخص واحد أن تُثقل سياق الجميع
      • يمكن لتشغيل شخص واحد الجاري أن يقاطع متابعة شخص آخر في نفس الغرفة

      إعداد الإشارات (Mentions) والـ Threading التلقائي​

      يمكنك ضبط سلوك الإشارات والـ threading التلقائي عبر متغيرات البيئة أو config.yaml:

      matrix:
        require_mention: true           # Require @mention in rooms (default: true)
        allowed_users:                  # Matrix users allowed to trigger agent turns
          - "@alice:matrix.org"
        allowed_rooms:                  # Matrix rooms allowed to trigger agent turns
          - "!abc123:matrix.org"
        free_response_rooms:            # Rooms exempt from mention requirement
          - "!abc123:matrix.org"
        ignore_user_patterns:           # Bridge/appservice ghost users to ignore
          - "^@telegram_"
          - "^@whatsapp_"
        process_notices: false          # Ignore m.notice by default
        session_scope: room             # auto|room|thread; room is recommended for project rooms
        auto_thread: true               # Auto-create threads for responses (default: true)
        dm_mention_threads: false       # Create thread when @mentioned in DM (default: false)
        max_message_length: 16000       # Outbound chunk size in chars (default: 16000, max: 65535)

      أو عبر متغيرات البيئة:

      MATRIX_REQUIRE_MENTION=true
      MATRIX_ALLOWED_USERS=@alice:matrix.org
      MATRIX_ALLOWED_ROOMS=!abc123:matrix.org
      MATRIX_FREE_RESPONSE_ROOMS=!abc123:matrix.org,!def456:matrix.org
      MATRIX_IGNORE_USER_PATTERNS='^@telegram_,^@whatsapp_'
      MATRIX_PROCESS_NOTICES=false
      MATRIX_SESSION_SCOPE=room       # recommended for stable project-room context
      MATRIX_AUTO_THREAD=true
      MATRIX_DM_MENTION_THREADS=false
      MATRIX_REACTIONS=true          # default: true — emoji reactions during processing
      MATRIX_ALLOW_ROOM_MENTIONS=false
      تعطيل ردود الأفعال

      يؤدي MATRIX_REACTIONS=false إلى إيقاف ردود أفعال الإيموجي الخاصة بدورة حياة المعالجة (👀/✅/❌) التي ينشرها البوت على الرسائل الواردة. مفيد للغرف التي تكون فيها أحداث ردود الأفعال مزعجة أو غير مدعومة من جميع العملاء المشاركين.

      الإشارات على مستوى الغرفة

      يرسل Hermes إشارات مستخدم Matrix منظّمة لمعرّفات Matrix الصريحة مثل @alice:example.org. إشعارات @room على مستوى الغرفة معطّلة افتراضيًا؛ اضبط MATRIX_ALLOW_ROOM_MENTIONS=true فقط في الغرف المسموح فيها للبوت بإشعار الجميع.

      ملاحظة

      إذا كنت تُرقّي من إصدار لم يكن يحتوي على MATRIX_REQUIRE_MENTION، فقد كان البوت يستجيب سابقًا لجميع الرسائل في الغرف. للحفاظ على ذلك السلوك، اضبط MATRIX_REQUIRE_MENTION=false.

      عزل غرف المشاريع​

      إذا كنت تستخدم نفس بوت Matrix في عدة غرف مشاريع، اضبط جلسات ثابتة مرتبطة بالغرفة:

      MATRIX_SESSION_SCOPE=room
      MATRIX_AUTO_THREAD=false

      يقبل MATRIX_SESSION_SCOPE:

      النطاقالسلوك
      autoالافتراضي المتوافق مع الإصدارات السابقة. يتحكم سلوك MATRIX_AUTO_THREAD الحالي في الـ threads الاصطناعية.
      roomتبقى رسائل الغرفة غير المسلسلة (unthreaded) في جلسة غرفة ثابتة واحدة. لا تزال threads Matrix الحقيقية تستخدم جذر الـ thread الخاص بها.
      threadتُركّب رسائل الغرفة غير المسلسلة thread/جلسة من معرّف الحدث المُطلِق.

      يتضمن Hermes الآن اسم غرفة Matrix الحالية ومعرّفها وموضوعها ومعرّف الرسالة، وملاحظة حدود غرفة Matrix في prompt الوكيل. يعرض /status أيضًا نطاق غرفة/جلسة Matrix الحالي، ولن يستأنف /resume بصمت جلسة مسمّاة من غرفة Matrix أخرى ما لم تستخدم صراحةً /resume --cross-room <session name>.

      يتحكم MATRIX_SESSION_SCOPE=room في مسار الغرفة/الـ thread. لا يزال إعداد group_sessions_per_user الحالي يتحكم فيما إذا كان المستخدمون داخل تلك الغرفة يشتركون في المسار. مع group_sessions_per_user: true (الافتراضي)، يحصل Alice و Bob على جلستي Project B منفصلتين. مع group_sessions_per_user: false، تحصل الغرفة على محادثة Project B واحدة مشتركة.

      يرشدك هذا الدليل خلال عملية الإعداد الكاملة — من إنشاء حساب البوت الخاص بك إلى إرسال رسالتك الأولى.

      الخطوة 1: إنشاء حساب بوت​

      تحتاج إلى حساب مستخدم Matrix للبوت. هناك عدة طرق للقيام بذلك:

      الخيار أ: التسجيل على homeserver الخاص بك (موصى به)​

      إذا كنت تشغّل homeserver خاصًا بك (Synapse أو Conduit أو Dendrite):

      1. استخدم admin API أو أداة التسجيل لإنشاء مستخدم جديد:
      # Synapse example
      register_new_matrix_user -c /etc/synapse/homeserver.yaml http://localhost:8008
      1. اختر اسم مستخدم مثل hermes — سيكون معرّف المستخدم الكامل @hermes:your-server.org.

      الخيار ب: استخدام matrix.org أو homeserver عام آخر​

      1. اذهب إلى Element Web وأنشئ حسابًا جديدًا.
      2. اختر اسم مستخدم لبوتك (مثلًا hermes-bot).

      الخيار ج: استخدام حسابك الخاص​

      يمكنك أيضًا تشغيل Hermes كمستخدمك الخاص. هذا يعني أن البوت ينشر باسمك — مفيد للمساعدين الشخصيين.

      الخطوة 2: الحصول على رمز وصول (Access Token)​

      يحتاج Hermes إلى رمز وصول للمصادقة مع homeserver. لديك خياران:

      الخيار أ: رمز الوصول (موصى به)​

      الطريقة الأكثر موثوقية للحصول على رمز:

      عبر Element:

      1. سجّل الدخول إلى Element بحساب البوت.
      2. اذهب إلى Settings → Help & About.
      3. مرّر إلى الأسفل ووسّع Advanced — يُعرض رمز الوصول هناك.
      4. انسخه فورًا.

      عبر API:

      curl -X POST https://your-server/_matrix/client/v3/login \
        -H "Content-Type: application/json" \
        -d '{
          "type": "m.login.password",
          "user": "@hermes:your-server.org",
          "password": "your-password"
        }'

      تتضمن الاستجابة حقل access_token — انسخه.

      حافظ على أمان رمز الوصول الخاص بك

      يمنح رمز الوصول وصولًا كاملًا إلى حساب Matrix الخاص بالبوت. لا تشاركه علنًا أبدًا ولا ترفعه إلى Git. إذا تعرّض للاختراق، ألغِه بتسجيل الخروج من جميع الجلسات لذلك المستخدم.

      الخيار ب: تسجيل الدخول بكلمة مرور​

      بدلًا من توفير رمز وصول، يمكنك إعطاء Hermes معرّف مستخدم البوت وكلمة مروره. سيسجل Hermes الدخول تلقائيًا عند بدء التشغيل. هذا أبسط لكنه يعني تخزين كلمة المرور في ملف .env الخاص بك.

      MATRIX_USER_ID=@hermes:your-server.org
      MATRIX_PASSWORD=your-password

      الخطوة 3: العثور على معرّف مستخدم Matrix الخاص بك​

      يستخدم Hermes Agent معرّف مستخدم Matrix الخاص بك للتحكم في من يمكنه التفاعل مع البوت. تتبع معرّفات مستخدمي Matrix الصيغة @username:server.

      للعثور على معرّفك:

      1. افتح Element (أو عميل Matrix المفضل لديك).
      2. انقر على صورتك الرمزية → Settings.
      3. يُعرض معرّف المستخدم الخاص بك في أعلى الملف الشخصي (مثلًا @alice:matrix.org).
      نصيحة

      تبدأ معرّفات مستخدمي Matrix دائمًا بـ @ وتحتوي على : متبوعة باسم الخادم. مثال: @alice:matrix.org، @bob:your-server.com.

      الخطوة 4: إعداد Hermes Agent​

      الخيار أ: الإعداد التفاعلي (موصى به)​

      نفّذ أمر الإعداد الموجَّه:

      hermes gateway setup

      اختر Matrix عند مطالبتك، ثم وفّر رابط homeserver، ورمز الوصول (أو معرّف المستخدم + كلمة المرور)، ومعرّفات المستخدمين المسموح بهم عند سؤالك.

      الخيار ب: الإعداد اليدوي​

      أضف ما يلي إلى ملف ~/.hermes/.env:

      باستخدام رمز وصول:

      # Required
      MATRIX_HOMESERVER=https://matrix.example.org
      MATRIX_ACCESS_TOKEN=***

      # Optional: user ID (auto-detected from token if omitted)
      # MATRIX_USER_ID=@hermes:matrix.example.org

      # Security: restrict who can interact with the bot
      MATRIX_ALLOWED_USERS=@alice:matrix.example.org

      # Optional: restrict which rooms can trigger the bot
      MATRIX_ALLOWED_ROOMS=!abc123:matrix.example.org

      # Multiple allowed users (comma-separated)
      # MATRIX_ALLOWED_USERS=@alice:matrix.example.org,@bob:matrix.example.org

      باستخدام تسجيل الدخول بكلمة مرور:

      # Required
      MATRIX_HOMESERVER=https://matrix.example.org
      MATRIX_USER_ID=@hermes:matrix.example.org
      MATRIX_PASSWORD=***

      # Security
      MATRIX_ALLOWED_USERS=@alice:matrix.example.org

      تصليب النشر الخاص​

      لعمليات نشر Matrix الخاصة، اضبط قوائم السماح للمستخدمين والغرف معًا. إذا لم يُضبط MATRIX_ALLOWED_USERS، يمكن لأي مرسل يستطيع الوصول إلى البوت في غرفة انضم إليها أن يُطلق دورًا للوكيل. إذا لم يُضبط MATRIX_ALLOWED_ROOMS، يمكن لأي غرفة ينضم إليها البوت أن تُطلق دورًا للوكيل. يجب على النشر المُحكَم ضبط كليهما:

      MATRIX_ALLOWED_USERS=@alice:matrix.example.org,@bob:matrix.example.org
      MATRIX_ALLOWED_ROOMS=!ops:matrix.example.org,!dmroom:matrix.example.org

      تحتاج عمليات نشر الجسر (bridge) و appservice إلى حماية إضافية من الحلقات (loop protection). يتجاهل Hermes دائمًا أحداثه الخاصة، ومستخدمي Matrix من نوع appservice الذين يبدأ الجزء المحلي من معرّفهم بـ _، ومعرّفات الأحداث المكررة، وأحداث بدء التشغيل القديمة، وأحداث استبدال التحرير، و أحداث m.notice افتراضيًا. أضف أنماط ghost خاصة بالجسر لعملية النشر عندما يستخدم جسرك اصطلاح تسمية مختلفًا:

      MATRIX_IGNORE_USER_PATTERNS='^@telegram_,^@slack_,^@whatsapp_'

      فعّل الإشعارات فقط عندما يرسل سير عمل بشري موثوق m.notice فعلًا:

      MATRIX_PROCESS_NOTICES=true

      الإشعارات الصادرة لكامل الغرفة معطّلة افتراضيًا. أبقِ MATRIX_ALLOW_ROOM_MENTIONS=false ما لم يكن مسموحًا صراحةً للبوت بإيقاظ الغرفة بأكملها باستخدام @room.

      تُخفي التشخيصات وحمولات التصحيح رموز وصول Matrix ومفاتيح الاسترداد ومعرّفات الأجهزة ونصوص الرسائل. تُحدَّد تنزيلات الوسائط بروابط محتوى Matrix mxc:// وتُرفض عندما تتجاوز MATRIX_MAX_MEDIA_BYTES. عامل الغرف الاتحادية (federated) و homeservers غير الموثوقة كمدخلات غير موثوقة: أبقِ قوائم السماح للغرف محكمة، وفضّل الرسائل المباشرة أو الغرف الخاصة للعمل الكثيف الاعتماد على الأدوات، وتجنّب تفويض ghosts الجسر أو دُمى appservice كمستخدمين مسموح بهم.

      إعدادات السلوك الاختيارية في ~/.hermes/config.yaml:

      group_sessions_per_user: true
      • يحافظ group_sessions_per_user: true على عزل سياق كل مشارك داخل الغرف المشتركة

      تشغيل الـ Gateway​

      بمجرد الإعداد، شغّل gateway الخاص بـ Matrix:

      hermes gateway

      يجب أن يتصل البوت بـ homeserver الخاص بك ويبدأ بالمزامنة (sync) خلال ثوانٍ قليلة. أرسل له رسالة — سواء DM أو في غرفة انضم إليها — لاختباره.

      نصيحة

      يمكنك تشغيل hermes gateway في الخلفية أو كخدمة systemd للتشغيل المستمر. راجع وثائق النشر (deployment) للتفاصيل.

      التشفير التام بين الطرفين (E2EE)​

      يدعم Hermes التشفير التام بين الطرفين في Matrix، لذا يمكنك الدردشة مع بوتك في الغرف المشفّرة.

      المتطلبات​

      يتطلب E2EE مكتبة mautrix مع إضافات (extras) التشفير ومكتبة libolm بلغة C:

      # Install mautrix with E2EE support
      pip install 'mautrix[encryption]'

      # Or install with hermes extras
      cd ~/.hermes/hermes-agent && uv pip install -e ".[matrix]"

      تحتاج أيضًا إلى تثبيت libolm على نظامك:

      # Debian/Ubuntu
      sudo apt install libolm-dev

      # macOS
      brew install libolm

      # Fedora
      sudo dnf install libolm-devel

      تفعيل E2EE​

      أضف إلى ~/.hermes/.env:

      MATRIX_E2EE_MODE=required

      يقبل MATRIX_E2EE_MODE:

      الوضعالسلوك
      offلا تُهيّئ E2EE في Matrix.
      optionalحاول تفعيل E2EE عند توفر الاعتماديات، لكن أبقِ الغرف غير المشفّرة تعمل إذا تعذّرت تهيئة التشفير.
      requiredفشل بشكل مغلق (fail closed) إذا لم تكن اعتماديات E2EE أو إعداد التشفير متاحة.

      قد يعود الوضع الاختياري إلى تشغيل بدون E2EE عندما يكون إعداد التشفير غير متاح. يفشل الوضع الإلزامي بشكل مغلق بدلًا من التراجع بصمت.

      للتوافق مع الإصدارات السابقة، لا يزال MATRIX_ENCRYPTION=true يُفعّل سلوك E2EE الإلزامي.

      عند تفعيل E2EE، يقوم Hermes بما يلي:

      • تخزين مفاتيح التشفير في ~/.hermes/platforms/matrix/store/ (التثبيتات القديمة: ~/.hermes/matrix/store/)
      • رفع مفاتيح الجهاز عند أول اتصال
      • فك تشفير الرسائل الواردة وتشفير الرسائل الصادرة تلقائيًا
      • الانضمام التلقائي إلى الغرف المشفّرة عند الدعوة

      أدوات وعناصر تحكم Matrix​

      لا يعرض Hermes أدوات وكيل خاصة بـ Matrix (مثل إنشاء الغرف، الدعوات، أو الحذف/التنقيح (redaction)) — يتفاعل الوكيل مع Matrix عبر تسليم الرسائل العادي. يستخدم المحول (adapter) ردود الأفعال والحذف داخليًا لتشغيل مطالبات الموافقة والمنتقيات (pickers).

      إذا ضُبط MATRIX_ALLOWED_ROOMS، يستجيب Hermes فقط في تلك الغرف (الرسائل المباشرة معفاة).

      تستخدم عناصر تحكم ردود الأفعال:

      • ✅ موافقة لمرة واحدة
      • ♾️ موافقة دائمة
      • ❌ رفض
      • ردود أفعال رقمية لاختيارات /model

      اضبط MATRIX_APPROVAL_REQUIRE_SENDER=false إذا كنت تريد عن قصد أن يشغّل أي مستخدم Matrix مصرّح له في الغرفة مطالبة موافقة/اختيار نموذج. الإعداد الافتراضي مرتبط بالطالب عندما يعرف Hermes من طلب الإجراء.

      حدود الوسائط​

      يرفع Hermes وينزّل صور Matrix وملفاتها وصوتياتها وفيديوهاتها عبر واجهات برمجة وسائط Matrix. تُرسَل الصور المولّدة المتعددة كدفعة منطقية مرتّبة واحدة، مع الحفاظ على التسميات التوضيحية وسياق الـ thread عبر الدفعة.

      افتراضيًا، تُرفض وسائط Matrix التي تتجاوز 100 ميجابايت قبل الرفع/التنزيل. تجاوز ذلك بـ:

      MATRIX_MAX_MEDIA_BYTES=104857600

      يجب أن تستخدم الوسائط الواردة روابط محتوى Matrix mxc://. يرفض Hermes روابط وسائط HTTP(S) العشوائية في أحداث Matrix لتجنب تحويل غرفة اتحادية إلى أداة تنزيل غير مقيّدة.

      التحقق بالتوقيع المتقاطع (Cross-Signing) (موصى به)​

      إذا كان حساب Matrix الخاص بك يفعّل التوقيع المتقاطع (الافتراضي في Element)، اضبط مفتاح الاسترداد حتى يتمكن البوت من توقيع جهازه ذاتيًا عند بدء التشغيل. بدون هذا، قد ترفض عملاء Matrix الأخرى مشاركة جلسات التشفير مع البوت بعد تدوير مفتاح الجهاز.

      MATRIX_RECOVERY_KEY=EsT... your recovery key here

      أين تجده: في Element، اذهب إلى Settings → Security & Privacy → Encryption → مفتاح الاسترداد الخاص بك (يُسمى أيضًا "Security Key"). هذا هو المفتاح الذي طُلب منك حفظه عند إعداد التوقيع المتقاطع لأول مرة.

      عند كل بدء تشغيل، إذا ضُبط MATRIX_RECOVERY_KEY، يستورد Hermes مفاتيح التوقيع المتقاطع من التخزين الآمن للأسرار الخاص بـ homeserver ويوقّع الجهاز الحالي. هذا العملية مُتحايثة (idempotent) وآمنة لتُترك مفعّلة بشكل دائم.

      إذا أنشأ Hermes مفتاح استرداد Matrix جديدًا، فلن يسجّل المفتاح الخام أبدًا في السجلات. اضبط MATRIX_RECOVERY_KEY_OUTPUT_FILE=/secure/path/matrix-recovery-key.txt قبل بدء التشغيل لكتابة مفتاح مولَّد مرة واحدة بصلاحيات ملف 0600؛ لا يُستبدَل الملف إذا كان موجودًا بالفعل.

      حذف مخزن التشفير (crypto store)

      إذا حذفت ~/.hermes/platforms/matrix/store/crypto.db، يفقد البوت هوية التشفير الخاصة به. مجرد إعادة التشغيل بنفس معرّف الجهاز لن يُستعاد بالكامل — لا يزال homeserver يحتفظ بمفاتيح لمرة واحدة موقّعة بمفتاح الهوية القديم، ولا يمكن للأقران إنشاء جلسات Olm جديدة.

      يكتشف Hermes هذه الحالة عند بدء التشغيل ويرفض تفعيل E2EE، مسجّلًا: device XXXX has stale one-time keys on the server signed with a previous identity key.

      أسهل تعافٍ: إنشاء رمز وصول جديد (الذي يحصل على معرّف جهاز جديد بدون سجل مفاتيح قديمة). راجع قسم "الترقية من إصدار سابق مع E2EE" أدناه. هذا هو المسار الأكثر موثوقية ويتجنب المساس بقاعدة بيانات homeserver.

      التعافي اليدوي (متقدم — يحافظ على نفس معرّف الجهاز):

      1. أوقف Synapse واحذف الجهاز القديم من قاعدة بياناته:

        sudo systemctl stop matrix-synapse
        sudo sqlite3 /var/lib/matrix-synapse/homeserver.db "
          DELETE FROM e2e_device_keys_json WHERE device_id = 'DEVICE_ID' AND user_id = '@hermes:your-server';
          DELETE FROM e2e_one_time_keys_json WHERE device_id = 'DEVICE_ID' AND user_id = '@hermes:your-server';
          DELETE FROM e2e_fallback_keys_json WHERE device_id = 'DEVICE_ID' AND user_id = '@hermes:your-server';
          DELETE FROM devices WHERE device_id = 'DEVICE_ID' AND user_id = '@hermes:your-server';
        "
        sudo systemctl start matrix-synapse

        أو عبر admin API الخاص بـ Synapse (لاحظ معرّف المستخدم المُرمّز بترميز URL):

        curl -X DELETE -H "Authorization: Bearer ADMIN_TOKEN" \
          'https://your-server/_synapse/admin/v2/users/%40hermes%3Ayour-server/devices/DEVICE_ID'

        ملاحظة: قد يؤدي حذف جهاز عبر admin API أيضًا إلى إبطال رمز الوصول المرتبط. قد تحتاج إلى إنشاء رمز جديد بعد ذلك.

      2. احذف مخزن التشفير المحلي وأعد تشغيل Hermes:

        rm -f ~/.hermes/platforms/matrix/store/crypto.db*
        # restart hermes

      قد تخزّن عملاء Matrix أخرى (Element، matrix-commander) مؤقتًا مفاتيح الجهاز القديمة. بعد التعافي، اكتب /discardsession في Element لإجبار إنشاء جلسة تشفير جديدة مع البوت.

      معلومة

      إذا لم تكن حزمة mautrix[encryption] مثبّتة أو libolm مفقودة، يتراجع البوت تلقائيًا إلى عميل عادي (غير مشفّر). سترى تحذيرًا في السجلات.

      الغرفة الرئيسية (Home Room)​

      يمكنك تعيين "غرفة رئيسية" يرسل إليها البوت الرسائل الاستباقية (مثل مُخرَجات مهام cron، والتذكيرات، والإشعارات). هناك طريقتان لضبطها:

      باستخدام Slash Command​

      اكتب /sethome في أي غرفة Matrix يتواجد فيها البوت. تصبح تلك الغرفة هي الغرفة الرئيسية. إذا كان عميل Matrix الخاص بك يعترض الأوامر ذات الشرطة المائلة، اكتب !sethome بدلًا من ذلك.

      الإعداد اليدوي​

      أضف هذا إلى ملف ~/.hermes/.env:

      MATRIX_HOME_ROOM=!abc123def456:matrix.example.org

      قائمة السماح للغرف (allowed_rooms)​

      قيّد البوت بمجموعة ثابتة من غرف Matrix. عند ضبطها، يستجيب البوت فقط في الغرف التي يظهر معرّفها في القائمة — تُتجاهَل الرسائل من أي غرفة أخرى بصمت، حتى لو أُشير إلى البوت فيها.

      الرسائل المباشرة (غرف الدردشة المباشرة) معفاة من هذا الفلتر، حتى يتمكن المستخدمون المصرّح لهم دائمًا من الوصول إلى البوت وجهًا لوجه.

      matrix:
        allowed_rooms:
          - "!abc123def456:matrix.example.org"
          - "!opsroom789:matrix.example.org"

      أو عبر متغير بيئة (مفصول بفواصل):

      MATRIX_ALLOWED_ROOMS="!abc123def456:matrix.example.org,!opsroom789:matrix.example.org"

      السلوك:

      • فارغ / غير مضبوط → لا قيود (الافتراضي).
      • غير فارغ → يجب أن يكون معرّف الغرفة في القائمة. يُجرى هذا التحقق قبل أي تصفية أخرى (متطلب الإشارة، قائمة السماح للمرسل، إلخ).
      • استخدم المعرّف الداخلي للغرفة (!abc...:server)، وليس اسمها المستعار (#room:server). يمكنك العثور على المعرّف الداخلي للغرفة في Element عبر Room → Settings → Advanced.

      راجع أيضًا: تقسيم أوامر slash بين المسؤول والمستخدم.

      نصيحة

      للعثور على معرّف غرفة: في Element، اذهب إلى الغرفة → Settings → Advanced → يُعرض هناك Internal room ID (يبدأ بـ !).

      الأوامر في Matrix​

      يدعم Hermes نفس أوامر gateway التي يدعمها على منصات المراسلة الأخرى، بما فيها /commands، و /model، و /stop، و /queue، و /steer، و /goal، و /subgoal، و /bg، و /btw، و /tasks، و /yolo.

      تحجز بعض عملاء Matrix الشرطة المائلة البادئة / للأوامر المحلية للعميل وقد لا ترسل الأوامر المجهولة ذات الشرطة المائلة إلى الغرفة. في هذه الحالة، استخدم ! كاسم بديل آمن لـ Matrix:

      !commands
      !model
      !model gpt-5.5 --provider openrouter
      !queue continue with the next task
      !stop

      لا يوحّد Hermes !command إلا عندما يكون الأمر معروفًا لدى الـ gateway، أو أمر إضافة (plugin) مسجّل، أو أمر مهارة (skill) مثبّت. تبقى علامات التعجب العادية مثل !important رسائل دردشة عادية.

      استكشاف الأخطاء وإصلاحها​

      البوت لا يستجيب للرسائل​

      السبب: لم ينضم البوت إلى الغرفة، أو لا يتضمن MATRIX_ALLOWED_USERS معرّف المستخدم الخاص بك، أو لا يتضمن MATRIX_ALLOWED_ROOMS الغرفة، أو أن رسالة في الغرفة لم تُشر إلى البوت.

      الحل: ادعُ البوت إلى الغرفة — سينضم تلقائيًا عند الدعوة. تحقق من أن معرّف المستخدم الخاص بك موجود في MATRIX_ALLOWED_USERS (استخدم الصيغة الكاملة @user:server) وأن معرّف الغرفة موجود في MATRIX_ALLOWED_ROOMS إذا كانت قائمة السماح هذه مُهيّأة. في الغرف، أشر إلى البوت أو أضف الغرفة إلى MATRIX_FREE_RESPONSE_ROOMS. أعد تشغيل الـ gateway.

      ينضم البوت إلى الغرف لكنه يُسقط كل رسالة بصمت (انحراف الساعة)​

      السبب: ساعة نظام المضيف مضبوطة متقدمة عن الوقت الفعلي. يطبّق محول Matrix فلتر سماح لبدء التشغيل مدته 5 ثوانٍ (event_ts < startup_ts - 5) لتجاهل الأحداث المُعاد تشغيلها من المزامنة الأولية. عندما تكون الساعة الفعلية متقدمة، يبدو كل حدث وارد "أقدم من وقت بدء التشغيل" ويُسقَط قبل الوصول إلى معالج الرسائل — يبدو البوت متصلًا لكنه لا يرد أبدًا. راجع #12614.

      العَرَض: يعرض سجل الـ gateway Matrix: dropped N live events as 'too old' more than 30s after startup.

      الحل: زامن ساعة المضيف باستخدام NTP وأعد تشغيل البوت:

      # Debian/Ubuntu
      sudo timedatectl set-ntp true
      timedatectl status   # confirm "System clock synchronized: yes"

      # macOS
      sudo sntp -sS time.apple.com

      "Failed to authenticate" / "whoami failed" عند بدء التشغيل​

      السبب: رمز الوصول أو رابط homeserver غير صحيح.

      الحل: تحقق من أن MATRIX_HOMESERVER يشير إلى homeserver الخاص بك (مع تضمين https://، بدون شرطة مائلة زائدة في النهاية). تحقق من أن MATRIX_ACCESS_TOKEN صالح — جرّبه باستخدام curl:

      curl -H "Authorization: Bearer YOUR_TOKEN" \
        https://your-server/_matrix/client/v3/account/whoami

      إذا أعاد هذا معلومات المستخدم الخاص بك، فالرمز صالح. إذا أعاد خطأً، أنشئ رمزًا جديدًا.

      خطأ "mautrix not installed"​

      السبب: حزمة بايثون mautrix غير مثبّتة.

      الحل: ثبّتها:

      pip install 'mautrix[encryption]'

      أو باستخدام إضافات (extras) Hermes:

      cd ~/.hermes/hermes-agent && uv pip install -e ".[matrix]"

      أخطاء التشفير / "could not decrypt event"​

      السبب: مفاتيح تشفير مفقودة، أو libolm غير مثبّتة، أو جهاز البوت غير موثوق.

      الحل:

      1. تحقق من تثبيت libolm على نظامك (راجع قسم E2EE أعلاه).
      2. تأكد من ضبط MATRIX_ENCRYPTION=true في ملف .env الخاص بك.
      3. في عميل Matrix الخاص بك (Element)، اذهب إلى الملف الشخصي للبوت -> Sessions -> وثّق/وثّق بجهاز البوت.
      4. إذا انضم البوت للتو إلى غرفة مشفّرة، يمكنه فقط فك تشفير الرسائل المرسلة بعد انضمامه. الرسائل الأقدم غير متاحة.

      الترقية من إصدار سابق مع E2EE​

      نصيحة

      إذا حذفت أيضًا crypto.db يدويًا، راجع تحذير "حذف مخزن التشفير" في قسم E2EE أعلاه — هناك خطوات إضافية لمسح المفاتيح القديمة لمرة واحدة من homeserver.

      إذا كنت تستخدم Hermes سابقًا مع MATRIX_ENCRYPTION=true وتُرقّي إلى إصدار يستخدم مخزن التشفير الجديد المستند إلى SQLite، فإن هوية التشفير الخاصة بالبوت قد تغيّرت. قد يخزّن عميل Matrix الخاص بك (Element) مؤقتًا مفاتيح الجهاز القديمة ويرفض مشاركة جلسات التشفير مع البوت.

      الأعراض: يتصل البوت ويعرض "E2EE enabled" في السجلات، لكن جميع الرسائل تعرض "could not decrypt event" ولا يستجيب البوت أبدًا.

      ما الذي يحدث: حالة التشفير القديمة (من matrix-nio السابق أو خلفية mautrix المستندة إلى التسلسل) غير متوافقة مع مخزن التشفير الجديد المستند إلى SQLite. ينشئ البوت هوية تشفير جديدة، لكن عميل Matrix الخاص بك لا يزال يحتفظ بالمفاتيح القديمة مؤقتًا ولن يشارك جلسة تشفير الغرفة مع جهاز تغيّرت مفاتيحه. هذه ميزة أمان في Matrix -- تعامل العملاء مفاتيح الهوية المتغيّرة لنفس الجهاز على أنها مشبوهة.

      الحل (ترحيل لمرة واحدة):

      1. أنشئ رمز وصول جديدًا للحصول على معرّف جهاز جديد. أبسط طريقة:

        curl -X POST https://your-server/_matrix/client/v3/login \
          -H "Content-Type: application/json" \
          -d '{
            "type": "m.login.password",
            "identifier": {"type": "m.id.user", "user": "@hermes:your-server.org"},
            "password": "***",
            "initial_device_display_name": "Hermes Agent"
          }'

        انسخ access_token الجديد وحدّث MATRIX_ACCESS_TOKEN في ~/.hermes/.env.

      2. احذف حالة التشفير القديمة:

        rm -f ~/.hermes/platforms/matrix/store/crypto.db
        rm -f ~/.hermes/platforms/matrix/store/crypto_store.*

      3. اضبط مفتاح الاسترداد الخاص بك (إذا كنت تستخدم التوقيع المتقاطع — معظم مستخدمي Element يستخدمونه). أضف إلى ~/.hermes/.env:

        MATRIX_RECOVERY_KEY=EsT... your recovery key here

        هذا يسمح للبوت بالتوقيع الذاتي بمفاتيح التوقيع المتقاطع عند بدء التشغيل، بحيث يثق Element بالجهاز الجديد فورًا. بدون هذا، قد يرى Element الجهاز الجديد على أنه غير موثّق ويرفض مشاركة جلسات التشفير. اعثر على مفتاح الاسترداد الخاص بك في Element ضمن Settings → Security & Privacy → Encryption.

      4. أجبر عميل Matrix الخاص بك على تدوير جلسة التشفير. في Element، افتح غرفة الـ DM مع البوت واكتب /discardsession. هذا يجبر Element على إنشاء جلسة تشفير جديدة ومشاركتها مع جهاز البوت الجديد.

      5. أعد تشغيل الـ gateway:

        hermes gateway run

        إذا ضُبط MATRIX_RECOVERY_KEY، يجب أن ترى Matrix: cross-signing verified via recovery key في السجلات.

      6. أرسل رسالة جديدة. يجب أن يفك البوت التشفير ويستجيب بشكل طبيعي.

      ملاحظة

      بعد الترحيل، لا يمكن فك تشفير الرسائل المرسلة قبل الترقية -- فقد اختفت مفاتيح التشفير القديمة. هذا يؤثر فقط على مرحلة الانتقال؛ تعمل الرسائل الجديدة بشكل طبيعي.

      نصيحة

      التثبيتات الجديدة لا تتأثر. هذا الترحيل مطلوب فقط إذا كان لديك إعداد E2EE يعمل مع إصدار سابق من Hermes وأنت تُرقّي.

      لماذا رمز وصول جديد؟ يرتبط كل رمز وصول لـ Matrix بمعرّف جهاز محدد. إعادة استخدام نفس معرّف الجهاز مع مفاتيح تشفير جديدة يجعل عملاء Matrix الأخرى يفقدون الثقة بالجهاز (فهي ترى مفاتيح الهوية المتغيّرة كخرق أمني محتمل). يحصل رمز الوصول الجديد على معرّف جهاز جديد بدون سجل مفاتيح قديمة، لذا تثق به العملاء الأخرى فورًا.

      وضع الوكيل الوسيط (Proxy Mode) (E2EE على macOS)​

      يتطلب E2EE في Matrix مكتبة libolm، التي لا تُترجَم (compile) على macOS ARM64 (Apple Silicon). إضافة (extra) hermes-agent[matrix] مقتصرة على Linux فقط. إذا كنت على macOS، يتيح لك proxy mode تشغيل E2EE في حاوية Docker على VM يعمل بـ Linux بينما يعمل الوكيل الفعلي أصليًا على macOS مع وصول كامل إلى ملفاتك المحلية وذاكرتك ومهاراتك.

      كيف يعمل هذا​

      macOS (Host):
        └─ hermes gateway
             ├─ api_server adapter ← listens on 0.0.0.0:8642
             ├─ AIAgent ← single source of truth
             ├─ Sessions, memory, skills
             └─ Local file access (Obsidian, projects, etc.)

      Linux VM (Docker):
        └─ hermes gateway (proxy mode)
             ├─ Matrix adapter ← E2EE decryption/encryption
             └─ HTTP forward → macOS:8642/v1/chat/completions
                 (no LLM API keys, no agent, no inference)

      تتعامل حاوية Docker فقط مع بروتوكول Matrix + E2EE. عندما تصل رسالة، تفك تشفيرها وتُحيل النص إلى المضيف عبر طلب HTTP عادي. يشغّل المضيف الوكيل، ويستدعي الأدوات، ويولّد استجابة، ويبثّها مرة أخرى. تشفّر الحاوية الاستجابة وترسلها إلى Matrix. جميع الجلسات موحّدة — CLI و Matrix و Telegram وأي منصة أخرى تشترك في نفس الذاكرة وسجل المحادثة.

      الخطوة 1: إعداد المضيف (macOS)​

      فعّل خادم API حتى يقبل المضيف الطلبات الواردة من حاوية Docker.

      أضف إلى ~/.hermes/.env:

      API_SERVER_ENABLED=true
      API_SERVER_KEY=your-secret-key-here
      API_SERVER_HOST=0.0.0.0
      • API_SERVER_HOST=0.0.0.0 يربط بجميع الواجهات (interfaces) بحيث يمكن لحاوية Docker الوصول إليه.
      • API_SERVER_KEY مطلوب للربط غير المحلي (non-loopback). اختر سلسلة عشوائية قوية.
      • يعمل خادم API على المنفذ 8642 افتراضيًا (غيّره باستخدام API_SERVER_PORT إذا لزم الأمر).

      شغّل الـ gateway:

      hermes gateway

      يجب أن ترى خادم API يبدأ جنبًا إلى جنب مع أي منصات أخرى قمت بإعدادها. تحقق من أنه قابل للوصول من الـ VM:

      # From the Linux VM
      curl http://<mac-ip>:8642/health

      الخطوة 2: إعداد حاوية Docker (VM بـ Linux)​

      تحتاج الحاوية إلى بيانات اعتماد Matrix ورابط الـ proxy. لا تحتاج إلى مفاتيح API لـ LLM.

      docker-compose.yml:

      services:
        hermes-matrix:
          build: .
          environment:
            # Matrix credentials
            MATRIX_HOMESERVER: "https://matrix.example.org"
            MATRIX_ACCESS_TOKEN: "syt_..."
            MATRIX_ALLOWED_USERS: "@you:matrix.example.org"
            MATRIX_ENCRYPTION: "true"
            MATRIX_DEVICE_ID: "HERMES_BOT"

            # Proxy mode — forward to host agent
            GATEWAY_PROXY_URL: "http://192.168.1.100:8642"
            GATEWAY_PROXY_KEY: "your-secret-key-here"
          volumes:
            - ./matrix-store:/root/.hermes/platforms/matrix/store

      Dockerfile:

      FROM python:3.11-slim

      RUN apt-get update && apt-get install -y libolm-dev && rm -rf /var/lib/apt/lists/*
      RUN cd ~/.hermes/hermes-agent && uv pip install -e ".[matrix]"

      CMD ["hermes", "gateway"]

      هذه هي الحاوية بأكملها. بدون مفاتيح API لـ OpenRouter أو Anthropic أو أي مزوّد استدلال.

      الخطوة 3: تشغيل كليهما​

      1. شغّل gateway المضيف أولًا:

        hermes gateway

      2. شغّل حاوية Docker:

        docker compose up -d

      3. أرسل رسالة في غرفة Matrix مشفّرة. تفك الحاوية تشفيرها، وتحيلها إلى المضيف، وتبثّ الاستجابة مرة أخرى.

      مرجع الإعدادات​

      يُعدَّ proxy mode على جانب الحاوية (الـ gateway الرقيق):

      الإعدادالوصف
      GATEWAY_PROXY_URLرابط خادم API البعيد لـ Hermes (مثلًا http://192.168.1.100:8642)
      GATEWAY_PROXY_KEYرمز حامل (bearer token) للمصادقة (يجب أن يطابق API_SERVER_KEY على المضيف)
      gateway.proxy_urlنفس GATEWAY_PROXY_URL لكن في config.yaml

      يحتاج جانب المضيف إلى:

      الإعدادالوصف
      API_SERVER_ENABLEDاضبطه على true
      API_SERVER_KEYرمز حامل (مشترك مع الحاوية)
      API_SERVER_HOSTاضبطه على 0.0.0.0 للوصول عبر الشبكة
      API_SERVER_PORTرقم المنفذ (الافتراضي: 8642)

      يعمل لأي منصة​

      proxy mode ليس مقتصرًا على Matrix. يمكن لأي محول منصة (platform adapter) استخدامه — اضبط GATEWAY_PROXY_URL على أي مثيل gateway وسيُحيل إلى الوكيل البعيد بدلًا من تشغيل واحد محليًا. هذا مفيد لأي نشر يحتاج فيه محول المنصة إلى العمل في بيئة مختلفة عن الوكيل (عزل الشبكة، متطلبات E2EE، قيود الموارد).

      نصيحة

      تُحفَظ استمرارية الجلسة عبر ترويسة X-Hermes-Session-Id. يتتبّع خادم API الخاص بالمضيف الجلسات بهذا المعرّف، لذا تستمر المحادثات عبر الرسائل تمامًا كما لو كانت مع وكيل محلي.

      ملاحظة

      القيود (الإصدار 1): لا تُنقَل رسائل تقدّم الأدوات من الوكيل البعيد — يرى المستخدم الاستجابة النهائية المبثوثة فقط، وليس استدعاءات الأدوات الفردية. تُعالَج مطالبات موافقة الأوامر الخطرة على جانب المضيف، ولا تُنقَل إلى مستخدم Matrix. يمكن معالجة هذه في تحديثات مستقبلية.

      يتصل البوت ويرسل، لكنه يتجاهل الرسائل الواردة​

      السبب: تُفعَّل معالجات أحداث Matrix فقط عندما تُرسَل حمولات المزامنة (sync) عبر آلية handle_sync() الخاصة بـ mautrix. يمكن لاستطلاع client.sync() خام لا يستدعي أبدًا handle_sync() أن يترك المحول متصلًا (الإرسال يعمل) بينما لا تصل الرسائل الواردة أبدًا إلى _on_room_message.

      الحل: يستخدم Hermes حلقة مزامنة صريحة تستدعي client.handle_sync() في كل من المزامنة الأولية وكل استجابة مزامنة تزايدية. يطابق هذا التشخيص في المشكلة الأصلية (upstream) رقم #7914 والـ PR المُغلَق #37807، لكنه يحتفظ بمهام الصيانة الخلفية الخاصة بـ Hermes (تتبع الغرف المنضمّة، معالجة الدعوات، مشاركة مفاتيح E2EE) بدلًا من تفويض دورة الحياة الكاملة إلى client.start(). إذا استمر فشل الرسائل الواردة بعد إعادة تشغيل الـ gateway، تحقق من تسجيل المعالجات قبل المزامنة الأولى وراجع السجلات بحثًا عن sync event dispatch error.

      مشاكل المزامنة / تأخر البوت​

      السبب: يمكن لتنفيذات الأدوات الطويلة تأخير حلقة المزامنة، أو أن homeserver بطيء.

      الحل: تعيد حلقة المزامنة المحاولة تلقائيًا كل 5 ثوانٍ عند حدوث خطأ. راجع سجلات Hermes بحثًا عن تحذيرات متعلقة بالمزامنة. إذا استمر تأخر البوت، تأكد من أن homeserver الخاص بك يملك موارد كافية.

      البوت غير متصل​

      السبب: gateway الخاص بـ Hermes لا يعمل، أو فشل في الاتصال.

      الحل: تحقق من أن hermes gateway يعمل. راجع مُخرَج الطرفية بحثًا عن رسائل خطأ. المشاكل الشائعة: رابط homeserver خاطئ، رمز وصول منتهي الصلاحية، homeserver غير قابل للوصول.

      "User not allowed" / يتجاهلك البوت​

      السبب: معرّف المستخدم الخاص بك غير موجود في MATRIX_ALLOWED_USERS.

      الحل: أضف معرّف المستخدم الخاص بك إلى MATRIX_ALLOWED_USERS في ~/.hermes/.env وأعد تشغيل الـ gateway. استخدم الصيغة الكاملة @user:server.

      يتجاهل البوت غرفة بأكملها​

      السبب: MATRIX_ALLOWED_ROOMS مضبوط ومعرّف الغرفة الحالية غير مُدرَج فيه، أو أن الغرفة تتطلب إشارة ولم تُشر الرسالة إلى البوت.

      الحل: أضف معرّف الغرفة إلى MATRIX_ALLOWED_ROOMS، أو أزل قائمة السماح للغرف إذا كان هذا نشرًا شخصيًا. للعثور على معرّف غرفة في Element، افتح إعدادات الغرفة وتحقق من Advanced.

      رسائل الجسر تتكرر أو تتردد صداها​

      السبب: تقوم دُمية جسر/appservice بترحيل مُخرَج البوت مرة أخرى كرسالة مستخدم جديدة، أو أن الجسر يستخدم معرّفات مستخدم ghost غير قياسية.

      الحل: أبقِ ghosts الجسر خارج MATRIX_ALLOWED_USERS، وأضف إدخال MATRIX_IGNORE_USER_PATTERNS مطابقًا، واترك MATRIX_PROCESS_NOTICES=false ما لم تكن الإشعارات جزءًا من سير عمل موثوق.

      الأمان​

      تحذير

      اضبط دائمًا MATRIX_ALLOWED_USERS، وبالنسبة لعمليات النشر المشتركة/الخاصة، MATRIX_ALLOWED_ROOMS. بدون هذين، يمكن لأي شخص يستطيع مراسلة البوت في غرفة انضم إليها أن يُطلق الوكيل. لا تُفوّض إلا الأشخاص والغرف التي تثق بها — يملك المستخدمون المصرّح لهم وصولًا كاملًا إلى قدرات الوكيل، بما في ذلك استخدام الأدوات والوصول إلى النظام.

      لمزيد من المعلومات حول تأمين نشر Hermes Agent الخاص بك، راجع دليل الأمان.

      ملاحظات​

      • أي homeserver: يعمل مع Synapse، أو Conduit، أو Dendrite، أو matrix.org، أو أي homeserver متوافق مع مواصفات Matrix. لا يُشترط أي برنامج homeserver معيّن.
      • الاتحاد (Federation): إذا كنت على homeserver اتحادي، يمكن للبوت التواصل مع مستخدمين من خوادم أخرى — فقط أضف معرّفاتهم الكاملة @user:server إلى MATRIX_ALLOWED_USERS.
      • الانضمام التلقائي: يقبل البوت دعوات الغرف وينضم إليها تلقائيًا. يبدأ بالاستجابة فورًا بعد الانضمام.
      • دعم الوسائط: يمكن لـ Hermes إرسال واستقبال الصور والصوتيات والفيديو ومرفقات الملفات. تُرفَع الوسائط إلى homeserver الخاص بك باستخدام واجهة برمجة مستودع محتوى Matrix.
      • الرسائل الصوتية الأصلية (MSC3245): يضع محول Matrix تلقائيًا علامة org.matrix.msc3245.voice على الرسائل الصوتية الصادرة. هذا يعني أن استجابات TTS والصوتيات تُعرَض كـ فقاعات صوتية أصلية في Element والعملاء الأخرى التي تدعم MSC3245، بدلًا من مرفقات ملفات صوتية عامة. كما تُحدَّد الرسائل الصوتية الواردة التي تحمل علامة MSC3245 بشكل صحيح وتُوجَّه إلى تحويل الصوت إلى نص. لا حاجة إلى أي إعداد — يعمل هذا تلقائيًا.

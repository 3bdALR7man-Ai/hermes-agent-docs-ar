      ربط Desktop بعدة نُسخ من Hermes

      سجّل كل backend لـ Hermes تملكه — بيئة التشغيل المحلية، والـ gateways البعيدة على شبكتك المحلية (LAN) أو على VPS، ومضيفات SSH، ونُسخ Hermes Cloud — في تطبيق سطح مكتب واحد، واستخدم الوكلاء عليها جميعًا جنبًا إلى جنب. الاتصالات دائمة: إذ يتصل كل gateway مسجّل بالـ backends و WebSockets الخاصة به عند الطلب، ويواصل الوكلاء في الخلفية بثّ مخرجاتهم أثناء اطّلاعك على gateway آخر.

      هذه الصفحة هي المكمّل من جهة سطح المكتب لصفحة تشغيل عدة Gateways في وقت واحد: فتلك الصفحة تتناول استضافة عدة gateways على جهاز واحد، أما هذه فتتناول تطبيق سطح مكتب واحدًا يتواصل مع عدة أجهزة.

      أين تجدها​

      يوجد كل شيء في صفحة Settings → Gateways الموحّدة (كانت الإصدارات الأقدم تحتوي على صفحتين منفصلتين هما Gateway و Connections؛ وتُعاد توجيه الروابط العميقة القديمة لصفحة Connections إليها). وتؤدي إليها ثلاثة مداخل:

      • Settings → Gateways — الصفحة نفسها (Cmd/Ctrl+,، ثم Gateways في قائمة التنقل ضمن الإعدادات). وسجلّ الاتصالات قسمٌ من تلك الصفحة، يقع أسفل عناصر التحكم في وضع الاتصال على مستوى الجهاز.
      • شريط الـ profiles في الشريط الجانبي — زر القابس في الطرف الأيمن من الشريط (التلميح: "Connect another Hermes gateway…") ينقلك مباشرةً إلى صفحة Gateways. وهو ظاهر دائمًا، حتى قبل أن تُنشئ profile ثانيًا أو اتصالًا ثانيًا.
      • لوحة الأوامر (command palette) — Cmd/Ctrl+K، ثم اكتب Gateways (وتطابق أيضًا connections، add gateway، remote، ssh، instances).

      سجلّ الـ gateways​

      يدير قسم Registered gateways في Settings → Gateways قائمةً مُسمّاة من gateways الخاصة بـ Hermes. وتوضّح مقدمته ذلك صراحةً: "Manage this device and every Hermes gateway it can reach through remote, SSH, or Cloud connections." وكل عنصر فيها هو اتصال:

      النوعما هوالمصادقة
      Local"The Hermes runtime managed by this app." (بيئة تشغيل Hermes التي يديرها هذا التطبيق)تلقائية
      Remote gateway"A Hermes gateway reachable over HTTP(S) — LAN, Tailscale, or the internet." (gateway لـ Hermes يمكن الوصول إليه عبر HTTP(S) — شبكة محلية أو Tailscale أو الإنترنت)session token أو OAuth
      SSH"A Hermes install reached over SSH." (تثبيت لـ Hermes يُوصَل إليه عبر SSH). يفتح التطبيق النفق (tunnel) ويشغّل لوحة التحكم نيابةً عنكمفتاح SSH + token يتبنّاه التطبيق
      Hermes Cloud"A hosted instance discovered through your Hermes Cloud account." (نسخة مستضافة تُكتشف عبر حسابك في Hermes Cloud)تسجيل الدخول عبر البوابة (portal)

      قواعد ينبغي معرفتها:

      • يحتاج كل اتصال إلى اسم جهاز فريد ("Homelab"، "Work laptop"). يظهر الاسم في كل مكان تظهر فيه النسخة — شارات قائمة الوكلاء (roster)، والمعرّفات (handles)، ونتائج التحديث. ولا يميّز التفرّد بين الأحرف الكبيرة والصغيرة، لذا لا يمكن أن يوجد Homelab و homelab معًا.
      • يدير التطبيق العنصر المحلي (وتظهر عليه شارة App-managed) ولا يمكن إزالته. أما إزالة أي اتصال آخر فتُنهي الـ backends والأنفاق الحيّة الخاصة به؛ دون المساس بالنسخة نفسها.
      • يكون أحد الاتصالات دائمًا هو الاتصال Primary (مع شارة في صفه): وهو الخيار الاحتياطي في السجل لاستدعاءات الـ gateways المتعددة التي لا تُحدّد gateway بعينه. ولا يؤدي Make primary إلى تبديل مساحة عمل Sessions الحالية؛ وعند إزالة الاتصال الأساسي يُرجَع إلى العنصر المحلي.
      • يتحكم الخيار At startup, return to Sessions on the last-used gateway في الـ gateway الذي تفتح عليه Sessions بعد إعادة تشغيل التطبيق بالكامل. وهو معطّل افتراضيًا، لذا تفتح Sessions على Primary. فعّله لاستئناف آخر gateway نجح الاتصال به. لا يُحفظ التبديل الفاشل أبدًا، والـ gateway المحفوظ الذي أُزيل أو صار غير متاح يُرجَع بدلًا منه إلى Primary.
      • يفحص Test مساري HTTP و WebSocket الخاصين بالاتصال، لذا فالنجاح (إشعار "Reachable") يعني أن المحادثة ستعمل فعلًا — وليس مجرد أن المضيف استجاب لـ ping.
      • تُرفض العناصر المكررة عند الحفظ: لا يوجد إلا عنصر محلي واحد؛ وتُزال الازدواجية بين العناصر البعيدة و السحابية بناءً على الـ URL بعد توحيده (بإزالة المسافات، وحذف الشرطات المائلة في النهاية، وتحويله إلى أحرف صغيرة — وعبر النوعين معًا، فلا يمكن لعنصر سحابي وعنصر بعيد أن يشيرا إلى الـ URL نفسه)؛ وتُزال الازدواجية بين عناصر SSH بناءً على user@host:port بعد توحيده إضافةً إلى الـ profile البعيد.
      • تأتي عناصر Cloud عادةً من مسار تسجيل الدخول/الاكتشاف في Hermes Cloud أعلى صفحة Gateways — ونوع Hermes Cloud في محرر إضافة الاتصال يوجّهك إلى هناك.

      بدّل الـ gateways من الشريط الجانبي Sessions. تبقى الـ profiles والمحادثات والمراسلة و cron مقصورة على نطاق ذلك الـ gateway؛ بينما يظل backend النافذة الذي يديره التطبيق يُختار عبر عناصر التحكم في وضع الاتصال أعلاه. أما Primary فهو الخيار الاحتياطي في السجل ولا يبدّل مساحة العمل الحالية.

      تنظيم مجموعات الجلسات​

      في قائمة العرض ضمن الشريط الجانبي Sessions، اختر Gateway & profile أثناء عرض جميع الـ profiles. يحصل كل gateway على قسم خاص به قابل للطي، مع أقسام فرعية للـ profiles تحتوي على جلساتها. ويبقى أي اثنين من الـ gateways لديهما profile باسم default منفصلين. تبدأ عناوين الـ gateways باسم الاتصال المحفوظ؛ وتعرض عناوين الـ profiles اسم الـ profile.

      استخدم قائمة قسم الـ gateway أو الـ profile لتنفيذ Rename group أو Reset name أو Move up أو Move down. تغيّر إعادة التسمية تسمية الشريط الجانبي فقط، لا الـ gateway أو الـ profile نفسه. يُعاد ترتيب الـ gateways كأقسام كاملة، ويُعاد ترتيب الـ profiles داخل الـ gateway الخاص بها. اسحب الأيقونة الأولى في القسم لإعادة ترتيبه، أو ركّز على ذلك المقبض واستخدم Space ثم مفاتيح الأسهم ثم Space لوضعه في مكانه. تُحفظ الأسماء والترتيب والأقسام المطوية على هذا الجهاز. وطيّ gateway يحافظ على حالات الطي الفردية للـ profiles الخاصة به. وإجراء الجلسة الجديدة في كل profile يستهدف ذلك الـ profile على الـ gateway المالك له.

      تعرض لوحة Hermes Cloud أيضًا Saved Cloud gateways عندما يكون اكتشاف البوابة (portal) في حالة تسجيل خروج. يختار Use gateway اتصالًا محفوظًا موجودًا دون تغيير الـ gateway الافتراضي؛ بينما تُميّز Active in this window الاتصال الحالي. عند إضافة نسخة جديدة يُستخدم اسمها الودّي في Cloud، بينما تُحفظ أسماء الاتصالات المخصصة الموجودة. ولا تزال الاتصالات المحفوظة تحتاج إلى مصادقة gateway صالحة؛ لذا أدِر تسجيل الدخول من عناصر التحكم في الاتصالات المسجّلة.

      إضافة اتصال خطوة بخطوة​

      1. افتح Settings → Gateways ومرّر إلى سجلّ الاتصالات (أو انقر القابس في شريط الـ profiles).
      2. انقر Add connection.
      3. اختر النوع: Local أو Hermes Cloud أو Remote gateway أو SSH. (يكون Local معطّلًا ما دام العنصر المحلي الذي يديره التطبيق موجودًا — وهذا هو الحال دائمًا تقريبًا؛ ويوجّهك Hermes Cloud إلى مسار تسجيل الدخول/الاكتشاف السحابي أعلاه.)
      4. املأ الحقول:
        • Name — مطلوب وفريد؛ وهو "اسم الجهاز" الذي يظهر في كل مكان تظهر فيه هذه النسخة (النص المؤقت: Homelab). بحد أقصى 64 حرفًا.
        • لـ Remote gateway فقط:
          • Gateway URL — الـ URL الأساسي لـ backend يعمل بالأمر hermes serve، مثل http://homelab.lan:9119. وتعمل بادئات المسارات الخاصة بالـ reverse proxy.
          • Authentication — اختر Session token أو OAuth:
            • Session token — الصق session token الخاص بلوحة التحكم من الـ gateway البعيد. وعند التعديل: "Leave blank to keep the saved token." (اتركه فارغًا للاحتفاظ بالـ token المحفوظ).
            • OAuth — سجّل الدخول عبر مسار Nous Portal في المتصفح؛ دون الحاجة إلى لصق أي token.
        • لـ SSH فقط:
          • SSH host — حقل مركّب واحد بصيغة user@host:22 (المستخدم والمنفذ اختياريان). يُستخدم مفتاح SSH الخاص بك؛ ويتبنّى التطبيق token لوحة التحكم عبر النفق.
      5. انقر Save connection (أو Cancel).
      6. انقر Test في الصف الجديد وانتظر ظهور "Reachable".

      عدّل لاحقًا أي عنصر غير محلي باستخدام زر القلم، أو أزِله باستخدام زر سلة المهملات — إذ تطلب الإزالة تأكيدًا وتذكّرك بأن "The instance itself is not touched — you can add it again any time." (لا تُمسّ النسخة نفسها — ويمكنك إضافتها مجددًا في أي وقت).

      الـ backend البعيد هو عملية hermes serve قيد التشغيل

      لا يعمل شيء مما سبق ما لم يكن الـ backend يعمل فعلًا ويمكن الوصول إليه على الجهاز الآخر. يتصل تطبيق سطح المكتب به؛ لكنه لا يشغّله نيابةً عنك (باستثناء اتصالات SSH، إذ يشغّل التطبيق لوحة التحكم عبر النفق عند الطلب). راجع الاتصال بـ backend بعيد لإعداد جانب الـ backend — مزوّدو المصادقة، والربط بعنوان غير loopback، وإرشادات Tailscale.

      الانتقال من إعدادات الاتصال الواحد​

      يستورد أول تشغيل لإصدار يدعم السجل إعداداتك الحالية تلقائيًا: إذ يتحول وضع الاتصال العام وأي تجاوزات (overrides) قديمة لكل profile من Settings → Gateway إلى عناصر مُسمّاة في السجل (مع إزالة الازدواجية حسب URL/المضيف). (لم تعد الإصدارات الأحدث توفّر تجاوزات لكل profile في صفحة إعدادات Gateways — فاتصالات الـ gateway تكون على مستوى الجهاز، وتُكتشف الـ profiles من الـ gateways التي تتصل بها.) ويُترك ملف الإعدادات القديم دون تغيير، لذا تواصل الإصدارات الأقدم على الجهاز نفسه العمل. وإذا تعارض اسم مُرحَّل مع اسم آخر، تُضاف إليه لاحقة (Homelab 2).

      الوكلاء عبر الـ gateways​

      كل profile على كل اتصال مسجّل هو وكيل. والقائمة الموحّدة للوكلاء (union roster) هي ما تعرضه واجهات الـ gateways المتعددة (وقائمة Bot Mode المدمجة):

      • عندما يوجد اسم الـ profile نفسه على عدة gateways، تُميَّز المعرّفات (handles) بصيغة @name-device — فالـ profile research على Homelab يُعرض بالشكل @research-homelab، بينما يحتفظ الـ profile الفريد عبر جميع الـ gateways باسمه المجرّد.
      • يُحصى الوكلاء فورًا، أما الـ sockets فلا تُفتح إلا عند الحاجة: إذ يسرد التطبيق الوكلاء عبر REST دون الاتصال بـ WebSocket لكل gateway. والـ gateway الذي يتعذّر الوصول إليه يُبلغ عن ذلك في صفه بدلًا من إفساد القائمة؛ وتبقى اتصالات SSH في وضع الاتصال عند الطلب إلى أن تفتح وكيلًا عليها لأول مرة (دون أنفاق مفاجئة).
      • فتح وكيل يتصل بـ الـ gateway الخاص به — فالمحادثات والجلسات والذاكرة موجودة على الجهاز المالك للـ profile، تمامًا كما لو كنت تستخدم تلك النسخة مباشرةً.

      يحصل كل زوج (connection, profile) على backend و socket خاصين به، ضمن مجمّع يُطبَّق عليه تنظيف الاتصالات الخاملة نفسه المتبع في الـ backends المحلية لكل profile — لذا يواصل الوكلاء في الخلفية البثّ أثناء اطّلاعك على gateway آخر.

      تُوجَّه أزرار الموافقة إلى الـ backend المالك للجلسة، لا إلى أي profile محدد حاليًا. وبالنسبة إلى profile ثانوي محلي، يمكن لـ Desktop استخدام الـ socket الذي أوصل الطلب حتى عندما يكون ربط الجلسة المخزّن مؤقتًا مفقودًا. وتظل الأولوية لملكية الجلسة المحفوظة، كما أن حذف ذلك الـ profile المحلي أو إعادة تسميته يمسح هذا المسار المؤقت بدلًا من إعادة الاتصال بـ backend متقادم.

      التبديل وتحديد النطاق​

      يتبع أسفل الشريط الجانبي تسلسلًا هرميًا واحدًا: gateway → profile → sessions. فالـ gateways أجهزة أو backends مستضافة؛ والـ profiles وكلاء Hermes معزولون يعيشون على gateway واحد.

      • عند وجود gateway مسجّل واحد، لا يُضاف أي عنصر تحكم خاص بالـ gateway. ويحتفظ Desktop المحلي فقط بشريط الـ profiles نفسه وتدفق لوحة المفاتيح كما كان سابقًا.
      • عند وجود عدة gateways، يعرض الشريط الجانبي محدِّد gateway واحدًا يحمل اسمًا. وتُحدّد أيقونته (جهاز أو سحابة أو شبكة أو طرفية) نوع الاتصال؛ بينما تبقى الصور الرمزية للـ profiles عنصر تحكم منفصلًا بعد الفاصل. ويتسع المحدِّد نفسه من اثنين من الـ gateways إلى أسطول أكبر دون تحويل الـ backends إلى رموز تشبه الـ profiles أو مزاحمة إجراءات الـ profiles وإخراجها من الشريط.
      • يؤدي اختيار gateway إلى استعادة آخر profile استُخدم عليه. وتعيد شارة الصفحة الرئيسية (home) إلى الـ profile الافتراضي الخاص به، وتعرض شارة الطبقات All profiles on this gateway. وتواصل Cmd/Ctrl+1–9 التبديل بين الـ profiles داخل الـ gateway النشط.
      • عند وجود عدة gateways يصبح شريط الـ profiles شريط أسطول (fleet rail): إذ تصطف profiles كل gateway مسجّل على الشريط الواحد، وتتصدر كل مجموعة رمزُ نوع ذلك الـ gateway (جهاز، شبكة، طرفية، سحابة) — وهو الرمز نفسه الذي يستخدمه محدِّد الـ gateway. تبدو مربعات الـ gateway النشط تمامًا كما تبدو في Desktop ذي الـ gateway الواحد؛ بينما تكون مربعات الـ gateways الأخرى باهتة ("at rest"). ويؤدي تمرير المؤشر فوق مربع في حالة السكون إلى إظهار اسم جهازه (omer · This device)، فلا يبدو أبدًا اثنان من الـ profiles بالاسم نفسه على جهازين مختلفين متشابهين.
      • يؤدي النقر على مربع في حالة السكون التبديلَ نفسه الذي يؤديه محدِّد الـ gateway، وصولًا إلى (gateway, profile) المحدد تمامًا: يدور المربع أثناء الاتصال بالهدف، ويبقى الـ gateway السابق معروضًا حتى يستجيب الهدف، وإذا كان الهدف لا يستجيب يفشل النقر مع رسالة بدلًا من ترك النافذة في حالة تبديل جزئي. تحافظ المجموعات على ترتيب السجل أيًّا كان الـ gateway النشط، لذا لا يتحرك أي مربع أبدًا من تحت المؤشر الذي نقره. ويوفر النقر بزر الفأرة الأيمن على مربع في حالة السكون الخيارات Switch to و Color و Rename و Edit SOUL.md و Delete، وتُنفَّذ جميعها على الـ gateway الخاص بالمربع؛ ويُسمّي تأكيد الحذف الجهاز.
      • الـ gateway الذي تعذّر على آخر عملية إحصاء الوصول إليه يحتفظ بمربعاته، مع نقطة كهرمانية على رمزه — فالجهاز النائم لا يزال لك. ويُدمج تسجيلان لـ backend واحد في مجموعة واحدة. وعندما يتجاوز عدد المربعات ثلاثة عشر مربعًا عبر الأسطول، يتقلص الشريط إلى قائمة واحدة مقسّمة حسب الـ gateway.
      • لا يبقى الـ gateway المحدد بعد الخروج وإعادة التشغيل إلا عند تفعيل Settings → Gateways → At startup, return to Sessions on the last-used gateway. ويُخزَّن هذا التفضيل ومعرّف الـ gateway في سجلّ بيانات المستخدم الخاص بالتطبيق، لذا لا يؤدي استبدال حزمة التطبيق أو تحديثها إلى إعادة ضبطهما.
      • عند وجود أكثر من ثلاثة عشر profile على الـ gateway النشط، يتقلص شريط صورها الرمزية إلى محدِّد profile مُسمّى. وبذلك يمكن لمجموعات كبيرة من الـ gateways والـ profiles أن تتعايش دون تغيير نموذج gateway → profile → sessions.
      • يظل This device gateway من الدرجة الأولى حتى عندما يكون اتصال بعيد هو Primary. ويمكنه إبقاء الجلسات المحلية متاحة أثناء انقطاع الاتصال البعيد، لكن التطبيق لا يسمّي ذلك "offline mode": فالنموذج أو الأدوات المحددة قد تظل تتطلب اتصالًا بالإنترنت.
      • قائمة الجلسات، وقنوات المراسلة، ومهام cron، والإعدادات، والملفات، والذاكرة كلها مقصورة على نطاق (gateway, profile) النشط. والتبديل من gateway لـ Telegram إلى gateway لـ Signal لا يمكن أن يُبقي مجموعات القنوات أو الجلسات الخاصة بالـ gateway السابق في الشريط الجانبي.
      • مجرد عرض أداة التبديل يقرأ سجلّ الاتصالات المحلي في Electron. ولا تُفتح الـ gateways البعيدة إلا عند اختيارها؛ ولا يوجد استطلاع دوري للأسطول.
      • يؤدي تمرير المؤشر فوق وكيل إلى تهيئة الـ backend الخاص به مسبقًا، فلا يتحمّل التبديل كلفة إقلاع بارد.
      • لصفحة Capabilities (Skills / Tools / MCP) نطاق مطابق: إذ يسرد محدِّد Configuring فيها كل وكيل (profile, device) من القائمة الموحّدة، واختيار أحدها يقرأ ويكتب المهارات و toolsets وخوادم MCP الخاصة بـ ذلك الجهاز دون تبديل مساحة عمل Sessions. وتُطبَّق عمليات التثبيت من Hub ومفاتيح البيئة وإعداد MCP جميعها على الـ backend الخاص بالوكيل المحدد. ولا يظهر زر hot-reload into a live session في تبويب MCP إلا للوكلاء على الـ gateway المتصلة به النافذة؛ أما التعديلات على الأجهزة الأخرى فتُطبَّق في جلستها التالية.

      أضِف الـ gateways أو اختبرها أو أعد تسميتها أو أزِلها من Settings → Gateways. وزر القابس بجوار إجراءات الـ profile اختصار إلى مركز الإدارة الوحيد ذاك، وليس مسار إضافة ثانيًا.

      Sessions و Bot Mode​

      تعرض Sessions عمدًا gateway نشطًا واحدًا في كل مرة: فهذا يُبقي الملفات والأدوات والقنوات و cron وسجل الجلسات ضمن سياق تنفيذ واحد مفهوم. ولا يوسّع شريط الأسطول للـ profiles سوى أداة الاختيار — فمساحة العمل تظل على (gateway, profile) واحد تمامًا بعد كل نقرة. أما Bot Mode فيؤدي مهمة مختلفة وقد يعرض القائمة الموحّدة مجمّعةً حسب الـ gateway، بحيث يستطيع المستخدم فتح وكيل على NAS وآخر على VPS من واجهة واحدة. ومع ذلك يظل فتح بوت يُفعّل مسار (gateway, profile) الخاص به تمامًا.

      تظل الإشارات المباشرة إلى البوتات والتفويض محليةً ضمن الـ gateway افتراضيًا. فتجاوز حدود الـ backend يغيّر نظام الملفات وبيانات الاعتماد والأدوات وسياق الثقة، لذا ينبغي أن يكون التنفيذ عبر الـ gateways جسرًا صريحًا لا أثرًا جانبيًا عرضيًا لمشاركة نافذة Desktop واحدة.

      تحديث جميع النُسخ دفعة واحدة​

      يُرسل Settings → Gateways → Update all instances (الذي يظهر بمجرد تسجيل أكثر من اتصال واحد) الأمر hermes update إلى كل اتصال مؤهل بالتوازي:

      • يُحدَّث Local عبر pipeline التحديث الخاص بالتطبيق (المسار نفسه المتبع في Settings → Updates).
      • يُطلب من اتصالات Remote و SSH تحديث نفسها عبر الـ backend الخاص بها — فيجري التحديث على ذلك الجهاز.
      • تُتخطى نُسخ Hermes Cloud مع ملاحظة "Managed by Hermes Cloud": إذ تدير المنصة إصداراتها.

      تُبلغ كل نسخة عن نتيجتها بشكل مستقل، لذا لا يعطّل جهاز واحد يتعذّر الوصول إليه الدفعةَ كلها أبدًا. أما الـ backends التي تُدار تحديثاتها خارجيًا (Docker، Nix) فترفض بلطف برسالتها الخاصة، في كل صف.

      ومع ذلك نادرًا ما تحتاج إلى زر الإعدادات: فبمجرد وجود أكثر من هدف للتحديث، تُنفّذ عناصر التحديث المعتادة في التطبيق (Update now في لوحة About، و ⌘K Update Hermes، وإشعار جاهزية التحديث) التوزيعَ نفسه تلقائيًا — الـ backend النشط أولًا، ثم كل gateway مؤهل آخر، ثم تطبيق سطح المكتب نفسه أخيرًا. راجع التحديث في دليل سطح المكتب.

      ملاحظات أمنية​

      • مكان تخزين الـ tokens. تُخزَّن session tokens الخاصة بالـ gateways البعيدة (و OAuth tokens الخاصة بتسجيل الدخول الأصلي، مفهرسةً حسب الـ URL الأساسي للـ gateway) في مجلد بيانات المستخدم الخاص بالتطبيق كملفات لا يصل إليها إلا المالك (0600)، ضمن العملية الرئيسية لـ Electron؛ ولا ترى عملية العرض (renderer) ولا الإضافات بايتات الـ tokens أبدًا.
      • تشفير اختياري عبر keychain. افتراضيًا لا تمر الـ tokens عبر keychain نظام التشغيل — ففي macOS تحديدًا، يضع safeStorage في Electron مفتاحًا خاصًا بالتطبيق في login keychain، وإذا كان الـ keychain مقفلًا أو معطوبًا يتحول ذلك إلى طلب كلمة مرور عند كل تشغيل. إذا أردت التشفير أثناء التخزين (at-rest) فوق صلاحيات الملفات، ففعّل Settings → Gateway → "Encrypt saved secrets with the OS keychain"؛ فيُعاد تشفير الأسرار المخزّنة الحالية في مكانها (Keychain في macOS، و DPAPI في Windows، و keyring backend الخاص بالجلسة في Linux). وإيقاف الخيار مجددًا يفك تشفيرها.
      • ملف السجل (connections.json ضمن مجلد بيانات المستخدم الخاص بالتطبيق) يحتوي على التسميات والـ URLs والمضيفات — ولا تظهر الأسرار إلا داخل أغلفة مشفّرة.
      • تُرجع الدالة host.connections() في plugin SDK عمدًا التسميات والأنواع ومعرّف الاتصال الأساسي — ولا تُرجع أبدًا أي بيانات للـ tokens.

      لمؤلفي الإضافات​

      يتيح plugin SDK الخاص بـ Desktop واجهة الـ gateways المتعددة مباشرةً:

      • host.connections() — قائمة الاتصالات المسجّلة (التسميات، والأنواع، والاتصال الأساسي؛ دون بايتات الـ tokens أبدًا).
      • host.agents() — القائمة الموحّدة: صف واحد لكل (gateway, profile) مع المعرّف @name-device المحسوب مسبقًا.
      • host.ensureAgent(connectionId, profile) — يُفعّل الـ gateway الخاص بوكيل ما بحيث تصل استدعاءات host.request اللاحقة إلى الـ backend الخاص به.
      • host.warmAgent(connectionId, profile) — تهيئة مسبقة للـ socket دون انتظار النتيجة (fire-and-forget) عند نية التمرير (hover-intent).

      تُكتشف الدوال الأربع جميعها عبر كشف الميزات (feature detection): ففي إصدار Desktop أقدم لا تكون موجودة، وينبغي للإضافة الرجوع إلى مسار profiles.list الخاص بالـ gateway الواحد. وقائمة الوكلاء متعددة الـ gateways في Bot Mode هي المستهلك المرجعي لها.

      استكشاف الأخطاء وإصلاحها​

      • "Connection test failed" — لا يمكن الوصول إلى الـ backend على ذلك الـ URL من هذا الجهاز. تحقّق من أن hermes serve يعمل على المضيف البعيد، وأن المنفذ مفتوح، و(في حالة المصادقة بالـ token) أن الـ token ساري المفعول. أعد تشغيل Test بعد الإصلاح.
      • يظهر وكيل لكنه لا يُفتح — شغّل Test على اتصاله. ففشل مسار WebSocket مع نجاح HTTP يعني عادةً أن proxy أو جدار حماية أو حارس المصادقة/المصدر (origin) في الـ gateway يحظر /api/ws.
      • gateway بعيد مفقود من قائمة الوكلاء — الـ backend الخاص به متوقف أو يتعذّر الوصول إليه؛ وتسرده القائمة ضمن الـ gateways مع الخطأ. وتُظهر اتصالات SSH الحالة connect-on-demand حتى أول استخدام — وهذا مقصود بالتصميم، وليس فشلًا.
      • "Update Hermes Desktop to chat with agents on other connections" — التطبيق أقدم من حزمة الاتصالات المتعددة؛ حدّث تطبيق سطح المكتب نفسه.
      • أسماء أجهزة مكررة — غير ممكن؛ إذ يُفرض تفرّد الأسماء عند الحفظ. وإذا تعارض اسم مُرحَّل، تُضاف إليه لاحقة (Homelab 2).
      • "Could not save the connection" — السبب الأكثر شيوعًا هو غياب Name، أو اسم مستخدم بالفعل، أو Gateway URL / SSH host بصيغة غير صحيحة؛ وتُحدّد رسالة الخطأ المخالفة بدقة.

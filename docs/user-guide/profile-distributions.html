      توزيعات Profile: مشاركة وكيل كامل

      تحزم توزيعة الـ profile (profile distribution) وكيل Hermes كاملًا — الشخصية، والمهارات، ومهام cron، واتصالات MCP، والإعدادات — على هيئة مستودع git. يمكن لأي شخص لديه صلاحية الوصول إلى المستودع تثبيت الوكيل بأكمله بأمر واحد، وتحديثه في مكانه، مع إبقاء ذكرياته وجلساته ومفاتيح API الخاصة به دون أي تغيير.

      إذا كان الـ profile وكيلًا محليًا، فالتوزيعة هي ذلك الوكيل وقد أصبح قابلًا للمشاركة.

      طريقتان لمشاركة profile​

      يوفّر Hermes مسارين للمشاركة، ولكلٍّ منهما غرض مختلف. التوزيعات هي الخيار الدائم، أما ملفات التصدير فهي الخيار السريع.

      التوزيعة (مستودع git)ملف التصدير (.tar.gz)
      طريقة التسليمhermes profile install <repo>إرسال ملف — عبر المحادثة، أو AirDrop، أو USB، أو البريد الإلكتروني
      ما يحتاجه المستلمgit، وصلاحية الوصول إلى المستودعالملف
      التحديثاتيسحب hermes profile update الإصدارات الجديدةإعادة إرسال الملف
      إدارة الإصداراتالوسوم (tags)، و branches، وقيم SHA للـ commitsلا يوجد — لقطة في لحظة زمنية معينة
      كلفة الإعداد على المؤلفdistribution.yaml + .gitignore + مستودعلا شيء — أمر واحد
      المحتوى المنقولSOUL، والإعدادات، والمهارات، و cron، و MCP، والإضافاتالمحتوى نفسه، إضافةً إلى سمة تطبيق سطح المكتب وتخطيطه
      الأدوات المستخدمةhermes profile install / update/export و /import، أو hermes profile export / import

      اختر التوزيعة عندما يكون الوكيل منتجًا ستواصل تحسينه وينبغي للآخرين متابعة إصداراته: وكيل داخلي لفريق خضع للمراجعة، أو إصدار موجّه للمجتمع، أو الوكيل نفسه منشورًا على خمسة أجهزة.

      اختر ملف التصدير عندما تريد فقط أن يحصل شخص ما على إعدادك الآن، أو عندما تنتقل إلى حاسوب محمول جديد. لا مستودع ولا ملف manifest — نفّذ /export في المحادثة، وسلّم الملف، وينفّذ المستلم /import. راجع تصدير ملف profile واستيراده.

      الطريقتان ليستا متعارضتين. فكثير من المؤلفين يجرّبون الـ profile بأنفسهم أولًا، ثم يرسلونه عبر /export إلى زميل لأخذ رأي ثانٍ، ثم ينشرونه كتوزيعة عندما يصبح جديرًا بإدارة الإصدارات.

      ماذا يعني ذلك​

      قبل التوزيعات، كانت مشاركة وكيل Hermes تعني أن ترسل إلى شخص ما:

      1. ملف SOUL.md الخاص بك
      2. قائمة بالمهارات المطلوب تثبيتها
      3. ملف config.yaml الخاص بك بعد حذف الأسرار منه
      4. وصفًا لخوادم MCP التي ربطتها
      5. أي مهام cron جدولتها
      6. تعليمات بمتغيرات البيئة التي يجب ضبطها

      …ثم تأمل أن يجمعها بشكل صحيح. وكان كل رفع للإصدار أو إصلاح لخطأ يعني تكرار عملية التسليم.

      مع التوزيعات، يوجد كل ذلك في مستودع git واحد:

      my-research-agent/
      ├── distribution.yaml    # manifest: name, version, env-var requirements
      ├── SOUL.md              # the agent's personality / system prompt
      ├── config.yaml          # model, temperature, reasoning, tool defaults
      ├── skills/              # bundled skills that come with the agent
      ├── cron/                # scheduled tasks the agent runs
      └── mcp.json             # MCP servers the agent connects to

      ينفّذ المستلمون:

      hermes profile install github.com/you/my-research-agent --alias

      …وبذلك يصبح لديهم الوكيل بأكمله. يملؤون مفاتيح API الخاصة بهم (.env.EXAMPLE → .env)، ويمكنهم تشغيل my-research-agent chat أو التواصل معه عبر Telegram / Discord / Slack / أي منصة gateway. وعندما تدفع (push) إصدارًا جديدًا، ينفّذون hermes profile update my-research-agent لسحب تغييراتك — مع بقاء ذكرياتهم وجلساتهم كما هي.

      لماذا git؟​

      درسنا خيارات مثل ملفات tarball، وأرشيفات HTTP، وتنسيقًا مخصصًا، ولم يتفوق أيٌّ منها على git:

      • لا خطوة بناء على الإطلاق للمؤلفين. ادفع إلى GitHub، ويثبّت المستخدمون. لا توجد حلقة "احزم هذا، ارفع ذاك، حدّث الفهرس".
      • الوسوم (tags) و branches و commits هي بالفعل نظام إدارة الإصدارات. فدفع وسم واحد يؤدي لنا ما تؤديه عملية "حزم + رفع إصدار" في الأدوات الأخرى.
      • التحديثات مجرد عملية fetch. لا إعادة تنزيل للأرشيف بأكمله.
      • الشفافية. يمكن للمستخدمين تصفح المستودع، وقراءة الفروقات (diffs) بين الإصدارات، وفتح issues عليه، وعمل fork له لتخصيصه.
      • المستودعات الخاصة تعمل دون أي جهد إضافي. مفاتيح SSH، وأدوات git credential المساعدة، وبيانات الاعتماد المخزّنة في GitHub CLI — أي مصادقة مُعدّة مسبقًا في طرفيتك تُطبَّق تلقائيًا وبشفافية.
      • قابلية إعادة الإنتاج مجرد قيمة SHA لـ commit. وهو الشيء نفسه الذي يسجّله pip و npm.

      المقابل: يحتاج المستلمون إلى تثبيت git. وهذا متحقق بالفعل على أي جهاز يشغّل Hermes في 2026.

      متى ينبغي لك استخدام توزيعة؟​

      حالات مناسبة:

      • تشارك وكيلًا متخصصًا — مراقب امتثال، أو مراجع شيفرة، أو مساعد أبحاث، أو بوت دعم عملاء — مع فريق أو مع المجتمع.
      • تنشر الوكيل نفسه على عدة أجهزة ولا تريد نسخ الملفات يدويًا في كل مرة.
      • تعمل على تطوير وكيل بشكل متكرر وتريد أن يحصل المستلمون على الإصدارات الجديدة بأمر واحد.
      • تبني وكيلًا كمنتج — بقيم افتراضية مدروسة، ومهارات منتقاة، و prompts مضبوطة — ينبغي للآخرين استخدامه كنقطة انطلاق.

      حالات غير مناسبة:

      • تريد تسليم إعدادك لشخص ما مرة واحدة، الآن. تحتاج التوزيعة إلى مستودع وملف manifest وملف .gitignore، بينما لا يحتاج /export إلى أيٍّ من ذلك — راجع تصدير ملف profile واستيراده. وينطبق الأمر نفسه على النسخ الاحتياطي أو نقل profile إلى جهاز جديد.
      • تريد مشاركة سمة تطبيق سطح المكتب وتخطيطه. تحمل التوزيعة الوكيل — SOUL، والإعدادات، والمهارات، و cron، و MCP، والإضافات. أما التصدير المُنشأ من تطبيق سطح المكتب فيحمل المظهر أيضًا: الواجهة (skin)، والوضع الفاتح/الداكن، والسمات المخصصة، ولون الشريط الجانبي (rail)، وتخطيط النافذة.
      • تريد مشاركة مفاتيح API مع الوكيل. يُستبعد auth.json و .env من التوزيعات عمدًا، إذ يستخدم كل من يثبّت التوزيعة بيانات اعتماده الخاصة. (وملفات التصدير تُزيلها أيضًا.)
      • تريد مشاركة الذكريات / الجلسات / سجل المحادثات. هذه بيانات مستخدم، وليست من محتوى التوزيعة، ولا تُشحن أبدًا. (ملفات التصدير مختلفة هنا — اقرأ ما يحتويه ملف التصدير قبل إرسال أحدها.)
      تنبيه

      لا يتحكم Hermes في git. استثناءات الملفات الموضحة في هذه الصفحة يطبّقها المُثبّت (installer) عندما ينفّذ شخص ما hermes profile install أو hermes profile update. ولا تُطبَّق عند تنفيذك git add أو git commit.

      دورة الحياة: من المؤلف إلى المُثبِّت إلى التحديث​

      فيما يلي المسار الكامل من البداية إلى النهاية. اختر الجانب الذي يهمك.

      للمؤلفين: نشر توزيعة​

      الخطوة 1 — ابدأ من profile يعمل​

      ابنِ الوكيل وحسّنه كما تفعل مع أي profile آخر:

      hermes profile create research-bot
      research-bot setup                    # configure model, API keys
      # Edit ~/.hermes/profiles/research-bot/SOUL.md
      # Install skills, wire up MCP servers, schedule cron jobs, etc.
      research-bot chat                     # dogfood until it feels right

      الخطوة 2 — أضف ملف distribution.yaml​

      أنشئ ~/.hermes/profiles/research-bot/distribution.yaml:

      name: research-bot
      version: 1.0.0
      description: "Autonomous research assistant with arXiv and web tools"
      hermes_requires: ">=0.12.0"
      author: "Your Name"
      license: "MIT"

      # Tell installers which env vars the agent needs. These are checked against
      # the installer's shell and existing .env file so they don't get nagged
      # about keys they already have configured.
      env_requires:
        - name: OPENAI_API_KEY
          description: "OpenAI API key (for model access)"
          required: true
        - name: SERPAPI_KEY
          description: "SerpAPI key for web search"
          required: false
          default: ""

      هذا هو ملف الـ manifest بأكمله. لكل حقل باستثناء name قيمة افتراضية معقولة.

      الخطوة 3 — أنشئ ملف .gitignore قبل أول commit​

      تحذير

      نفّذ هذه الخطوة قبل تشغيل git init أو git add. إذا كنت قد تحادثت مع الـ profile، أو شغّلت الإعداد، أو استخدمته بأي شكل آخر، فإن الدليل يحتوي الآن على ملفات يجب ألا تشحنها: .env و auth.json و memories/ و sessions/ و state.db* و logs/ وغيرها.

      أنشئ ~/.hermes/profiles/research-bot/.gitignore بحيث يحتوي على الأقل على ما يلي:

      # Credentials & secrets — NEVER commit
      auth.json
      .env
      .env.EXAMPLE    # generated by install, not authorship domain

      # Runtime databases & state
      state.db
      state.db-shm
      state.db-wal
      hermes_state.db
      response_store.db
      response_store.db-shm
      response_store.db-wal
      gateway.pid
      gateway_state.json
      processes.json
      auth.lock
      active_profile
      .update_check

      # User data — NEVER commit
      memories/
      sessions/
      logs/
      plans/
      workspace/
      home/

      # Caches & generated artifacts
      image_cache/
      audio_cache/
      document_cache/
      browser_screenshots/
      cache/

      # Infrastructure (should not be in profile dir, but safe to exclude)
      hermes-agent/
      .worktrees/
      profiles/
      bin/
      node_modules/

      # User customization namespace — your local overrides
      local/

      # Checkpoints & backups (can be huge)
      checkpoints/
      sandboxes/
      backups/

      # Logs
      errors.log
      .hermes_history

      يطابق هذا المسارات المستبعدة إلزاميًا التي يُزيلها المُثبّت من جهته. وأي شيء آخر تريد إبقاءه خارج المستودع (ملفات مؤقتة، أو أصول كبيرة الحجم، أو مهارات محلية فقط) يجب إضافته هنا أيضًا.

      الخطوة 4 — ادفع إلى مستودع git​

      cd ~/.hermes/profiles/research-bot
      git init
      git add .
      git commit -m "v1.0.0"
      git remote add origin git@github.com:you/research-bot.git
      git tag v1.0.0
      git push -u origin main --tags

      أصبح المستودع الآن توزيعة، ويمكن لأي شخص لديه صلاحية الوصول تثبيتها.

      ملاحظة

      سيُزيل المُثبّت أيضًا المسارات المستبعدة إلزاميًا حتى لو شحنها المؤلف بطريقة ما — لكن ذلك يحمي من يثبّتون التوزيعة فقط، لا المؤلف.

      الخطوة 5 — ضع وسومًا للإصدارات​

      في كل مرة يبلغ فيها الوكيل مرحلة مستقرة، ارفع رقم الإصدار وضع وسمًا:

      # Edit distribution.yaml: version: 1.1.0
      git add distribution.yaml SOUL.md skills/
      git commit -m "v1.1.0: tighter research SOUL, add arxiv skill"
      git tag v1.1.0
      git push --tags

      سيسحب المستلمون الذين ينفّذون hermes profile update research-bot أحدث إصدار.

      شكل المستودع​

      توزيعة كاملة من إعداد المؤلف:

      research-bot/
      ├── .gitignore                   # excludes secrets & user data (see Step 3)
      ├── distribution.yaml            # required
      ├── SOUL.md                      # strongly recommended
      ├── config.yaml                  # model, provider, tool defaults
      ├── mcp.json                     # MCP server connections
      ├── skills/
      │   ├── arxiv-search/SKILL.md
      │   ├── paper-summarization/SKILL.md
      │   └── citation-lookup/SKILL.md
      ├── cron/
      │   └── weekly-digest.json       # scheduled tasks
      └── README.md                    # human-facing description (optional)

      ما تملكه التوزيعة مقابل ما يملكه المستخدم​

      عندما يحدّث من ثبّت التوزيعة إلى إصدار جديد، تُستبدل بعض الأشياء (نطاق المؤلف) وتبقى أشياء أخرى كما هي (نطاق المُثبِّت). القيم الافتراضية:

      الفئةالمساراتعند التحديث
      مملوكة للتوزيعةSOUL.md، config.yaml، mcp.json، skills/، cron/، distribution.yamlتُستبدل من النسخة المستنسخة الجديدة
      استثناء الإعداداتconfig.yamlيُحتفظ به افتراضيًا في الواقع — فربما يكون المُثبِّت قد ضبط النموذج أو المزوّد. مرّر --force-config عند التحديث لإعادة تعيينه.
      مملوكة للمستخدمmemories/، sessions/، state.db*، auth.json، .env، logs/، workspace/، plans/، home/، *_cache/، local/لا تُمسّ أبدًا

      يمكنك تجاوز قائمة الملفات المملوكة للتوزيعة في ملف الـ manifest:

      distribution_owned:
        - SOUL.md
        - skills/research/            # only my research skills; other installed skills stay
        - cron/digest.json

      عند حذفها، تُطبَّق القيم الافتراضية أعلاه — وهو ما تحتاجه معظم التوزيعات.

      للمثبِّتين: استخدام توزيعة​

      التثبيت​

      hermes profile install github.com/you/research-bot --alias

      ما يحدث:

      1. يستنسخ المستودع إلى دليل مؤقت.
      2. يقرأ distribution.yaml، ويعرض لك الـ manifest (الاسم، والإصدار، والوصف، والمؤلف، ومتغيرات البيئة المطلوبة).
      3. يتحقق من كل متغير بيئة مطلوب في بيئة الـ shell لديك وفي ملف .env الموجود في الـ profile الهدف، ويعلّم كلًّا منها بـ ✓ set أو needs setting لتعرف بالضبط ما يجب ضبطه.
      4. يطلب التأكيد. مرّر -y / --yes لتخطيه.
      5. ينسخ الملفات المملوكة للتوزيعة إلى ~/.hermes/profiles/research-bot/ (أو إلى المسار الذي يشير إليه الحقل name في الـ manifest). وتُزال المسارات المستبعدة إلزاميًا أثناء هذا النسخ، حتى لو تركها المؤلف في المستودع عن غير قصد.
      6. يكتب ملف .env.EXAMPLE مع المفاتيح المطلوبة في هيئة تعليقات — انسخه إلى .env واملأ القيم.
      7. مع --alias، يُنشئ wrapper لتتمكن من تشغيل research-bot chat مباشرةً.

      أنواع المصادر​

      يعمل أي URL لـ git:

      # GitHub shorthand
      hermes profile install github.com/you/research-bot

      # Full HTTPS
      hermes profile install https://github.com/you/research-bot.git

      # SSH
      hermes profile install git@github.com:you/research-bot.git

      # Self-hosted, GitLab, Gitea, Forgejo — any Git host
      hermes profile install https://git.example.com/team/research-bot.git

      # Private repo using your configured git auth
      hermes profile install git@github.com:your-org/internal-bot.git

      # Local directory during development (no git push needed)
      hermes profile install ~/my-profile-in-progress/

      تجاوز اسم الـ profile​

      مستخدمان يريدان التوزيعة نفسها بأسماء profile مختلفة:

      # Alice
      hermes profile install github.com/acme/support-bot --name support-us --alias
      # Bob (same distribution, different local name)
      hermes profile install github.com/acme/support-bot --name support-eu --alias

      ملء متغيرات البيئة​

      بعد التثبيت، يحتوي profile الوكيل على ملف .env.EXAMPLE:

      # Environment variables required by this Hermes distribution.
      # Copy to `.env` and fill in your own values before running.

      # OpenAI API key (for model access)
      # (required)
      OPENAI_API_KEY=

      # SerpAPI key for web search
      # (optional)
      # SERPAPI_KEY=

      انسخه:

      cp ~/.hermes/profiles/research-bot/.env.EXAMPLE ~/.hermes/profiles/research-bot/.env
      # Edit .env, paste your real keys

      المفاتيح المطلوبة الموجودة مسبقًا في بيئة الـ shell لديك (مثل OPENAI_API_KEY المُصدَّر في ~/.zshrc) تُعلَّم بـ ✓ set أثناء التثبيت — فلا حاجة إلى تكرارها في .env.

      التحديث​

      hermes profile update research-bot

      ما يحدث:

      1. يعيد استنساخ المستودع من URL المصدر المسجّل.
      2. يستبدل الملفات المملوكة للتوزيعة (SOUL، والمهارات، و cron، و mcp.json).
      3. يحتفظ بملف config.yaml الخاص بك — فربما تكون قد ضبطت النموذج أو درجة الحرارة (temperature) أو إعدادات أخرى. مرّر --force-config للكتابة فوقه.
      4. لا يمسّ أبدًا بيانات المستخدم: الذكريات، والجلسات، والمصادقة، و .env، والسجلات، والحالة.

      لا إعادة تنزيل للأرشيف بأكمله، ولا طمس لتغييراتك المحلية على الإعدادات، ولا حذف لسجل محادثاتك.

      الإزالة​

      hermes profile delete research-bot

      تعرض رسالة تأكيد الحذف معلومات التوزيعة قبل أن تطلب منك التأكيد:

      Profile: research-bot
      Path:    ~/.hermes/profiles/research-bot
      Model:   claude-opus-4 (anthropic)
      Skills:  12
      Distribution: research-bot@1.0.0
      Installed from: https://github.com/you/research-bot

      This will permanently delete:
        • All config, API keys, memories, sessions, skills, cron jobs
        • Command alias (~/.local/bin/research-bot)

      Type 'research-bot' to confirm:

      وبذلك لا تحذف أبدًا وكيلًا عن طريق الخطأ دون أن تعرف مصدره أو تتمكن من إعادة تثبيته.

      حالات الاستخدام والأنماط​

      الاستخدام الشخصي: مزامنة وكيل واحد عبر عدة أجهزة​

      أنشأت مساعد أبحاث على حاسوبك المحمول، وتريد الوكيل نفسه على محطة عملك.

      # Laptop — create .gitignore first (see "For authors" Step 3), then:
      cd ~/.hermes/profiles/research-bot
      git init && git add . && git status   # confirm no secrets staged
      git commit -m "initial"
      git remote add origin git@github.com:you/research-bot.git
      git push -u origin main

      # Workstation
      hermes profile install github.com/you/research-bot --alias
      # Fill in .env. Done.

      أي تعديل على الحاسوب المحمول (git commit && push) يُسحب إلى محطة العمل عبر hermes profile update research-bot. وتبقى الذكريات خاصة بكل جهاز — فالحاسوب المحمول يتذكر محادثاته، ومحطة العمل تتذكر محادثاتها، دون أن تتعارض.

      الفريق: شحن وكيل داخلي خضع للمراجعة​

      يريد فريقك الهندسي بوتًا مشتركًا لمراجعة الـ pull requests بملف SOUL محدد، ومهارات محددة، ومهمة cron تمرّر كل PR عبره.

      # Engineering lead — create .gitignore first (see "For authors" Step 3), then:
      cd ~/.hermes/profiles/pr-reviewer
      # ... build and tune ...
      git init && git add . && git status   # confirm no secrets staged
      git commit -m "v1.0 PR reviewer"
      git tag v1.0.0
      git push -u origin main --tags    # push to your company's internal Git host

      # Each engineer
      hermes profile install git@github.com:your-org/pr-reviewer.git --alias
      # Fill in .env with their own API key (billed to them), .env.EXAMPLE points at what's required
      pr-reviewer chat

      عندما يشحن قائد الفريق الإصدار v1.1 (ملف SOUL أفضل، ومهارة جديدة)، ينفّذ المهندسون hermes profile update pr-reviewer ويصبح الجميع على الإصدار الجديد خلال دقائق.

      المجتمع: نشر وكيل عام​

      أنشأت شيئًا مبتكرًا — ربما "متداول على Polymarket" أو "مُلخِّص للأوراق الأكاديمية" أو "مساعد لتشغيل خوادم Minecraft". وتريد مشاركته.

      # You — create .gitignore first (see "For authors" Step 3), then:
      cd ~/.hermes/profiles/polymarket-trader
      # Write a solid README.md at the repo root — GitHub shows it on the repo page
      git init && git add . && git status   # confirm no secrets staged
      git commit -m "v1.0"
      git tag v1.0.0
      # Publish to a public GitHub repo
      git remote add origin https://github.com/you/hermes-polymarket-trader.git
      git push -u origin main --tags

      # Anyone
      hermes profile install github.com/you/hermes-polymarket-trader --alias

      انشر أمر التثبيت في تغريدة. سيرسل إليك من يجرّبونه issues و PRs. وإذا أراد أحدهم التخصيص، فيمكنه عمل fork — وهو سير عمل git نفسه الذي يعرفه الجميع.

      المنتج: شحن وكيل بتوجهات محددة​

      بنيت شيئًا فوق Hermes — ربما منظومة لمراقبة الامتثال، أو حزمة لدعم العملاء، أو منصة أبحاث متخصصة في مجال معين. وتريد توزيعه كمنتج.

      # distribution.yaml
      name: telemetry-harness
      version: 2.3.1
      description: "Compliance telemetry harness — monitors and reviews regulated workflows"
      hermes_requires: ">=0.13.0"
      author: "Acme Compliance Inc."
      license: "Commercial"

      env_requires:
        - name: ACME_API_KEY
          description: "Your Acme Compliance license key (email support@acme.com)"
          required: true
        - name: OPENAI_API_KEY
          description: "OpenAI API key for model access"
          required: true
        - name: GRAPHITI_MCP_URL
          description: "URL for your Graphiti knowledge graph instance"
          required: false
          default: "http://127.0.0.1:8000/sse"

      يثبّته عملاؤك بأمر واحد؛ وتخبرهم معاينة التثبيت بالضبط بالمفاتيح التي يجب تجهيزها؛ وتصل التحديثات لحظة وضعك وسمًا لإصدار جديد؛ ولا تغادر بيانات الامتثال الخاصة بهم (memories/ و sessions/) أجهزتهم أبدًا.

      الاستخدام المؤقت: سكربتات لمرة واحدة على بنية تحتية مشتركة​

      أنت قائد فريق العمليات، وتريد وكيلًا مؤقتًا يشخّص حادثة في بيئة الإنتاج — ملف SOUL جاهز مع الأدوات واتصالات MCP المناسبة — ويعمل على الحواسيب المحمولة لثلاثة مهندسين مناوبين خلال الأسبوع القادم.

      # You — create .gitignore first (see "For authors" Step 3), then:
      # Build the profile, commit, push a private repo
      git push -u origin main

      # Each on-call
      hermes profile install git@github.com:your-org/incident-2026-q2.git --alias

      # Incident resolved — tear it down
      hermes profile delete incident-2026-q2

      دورة التثبيت والحذف منخفضة الكلفة بما يكفي لاستخدامها ثم التخلص منها.

      وصفات عملية​

      التقيّد بإصدار محدد​

      ملاحظة

      التقيّد بمرجع git محدد (#v1.2.0) مُخطَّط له لكنه غير متوفر في الإصدار الأولي — إذ يتتبع التثبيت حاليًا الـ branch الافتراضي. تابع الإصدار المثبّت لديك عبر hermes profile info <name> وأجّل التحديثات حتى تصبح مستعدًا.

      التحقق من إصدارك الحالي مقارنةً بأحدث إصدار​

      # Your installed version
      hermes profile info research-bot | grep Version

      # Latest upstream (without installing)
      git ls-remote --tags https://github.com/you/research-bot | tail -5

      الحفاظ على تخصيصات الإعدادات المحلية عبر التحديثات​

      سلوك التحديث الافتراضي يفعل ذلك بالفعل: إذ يُحتفظ بـ config.yaml. ولمزيد من الأمان، اكتب تعديلاتك المحلية في ملف لا تملكه التوزيعة:

      # ~/.hermes/profiles/research-bot/local/my-overrides.yaml
      # (distribution never touches local/)

      …ثم أشر إليه من config.yaml أو من ملف SOUL حسب الحاجة.

      فرض إعادة تثبيت نظيفة​

      # Nuke and re-install from scratch (loses memories/sessions too)
      hermes profile delete research-bot --yes
      hermes profile install github.com/you/research-bot --alias

      # Update to current main but reset config.yaml to the distribution's default
      hermes profile update research-bot --force-config --yes

      عمل fork والتخصيص​

      سير عمل git المعتاد — فالتوزيعات مجرد مستودعات:

      # Fork the repo on GitHub, then install your fork
      hermes profile install github.com/yourname/forked-research-bot --alias

      # Iterate locally in ~/.hermes/profiles/forked-research-bot/
      # Edit SOUL.md, commit, push to your fork
      # Upstream changes: pull them into your fork the usual way

      اختبار توزيعة قبل دفعها​

      من جهاز المؤلف:

      # Install from a local directory (no git push needed)
      hermes profile install ~/.hermes/profiles/research-bot --name research-bot-test --alias

      # Tweak, delete, re-install until it's right
      hermes profile delete research-bot-test --yes
      hermes profile install ~/.hermes/profiles/research-bot --name research-bot-test

      تصدير ملف profile واستيراده​

      عندما لا تحتاج إلى إدارة الإصدارات، استغنِ عن المستودع. يحزم /export الـ profile في ملف .tar.gz واحد؛ ويفكّ /import حزمته على هيئة profile جديد لدى الطرف الآخر. وتُزال بيانات الاعتماد عند التصدير.

      التصدير​

      في CLI أو TUI أو محادثة تطبيق سطح المكتب:

      /export                          # the active profile → managed profile-exports/<name>-<timestamp>.tar.gz
      /export research-bot             # a named profile
      /export research-bot -o ~/Desktop/research-bot.tar.gz

      من دون -o، تضع CLI و TUI الأرشيف في الدليل profile-exports/ الذي يديره Hermes ضمن الدليل الرئيسي الافتراضي لـ Hermes، وليس في دليل العمل الحالي. يُبقي ذلك عمليات التصدير الروتينية خارج النسخ المسحوبة (checkouts) من الشيفرة المصدرية، ويمنع الخلط بين لقطة الـ profile المُنشأة وملف مصدري في المستودع. وإذا كان الدليل الرئيسي لـ Hermes نفسه موجودًا داخل نسخة Git مسحوبة (في بعض عمليات النشر عبر Docker أو المخصصة)، فيُحفظ الأرشيف في ~/.hermes-profile-exports/ أو، إن تعذّر ذلك، في دليل خاص بالمستخدم ضمن الدليل المؤقت لنظام التشغيل — وليس داخل النسخة المسحوبة أبدًا. وإذا لم يوجد أي موقع تلقائي آمن على الإطلاق (أي أن كل المواقع المرشحة داخل نسخة Git مسحوبة)، يرفض التصدير مع الرسالة "No safe automatic export destination"، وعليك حينها تمرير -o مع مسار خارج النسخة المسحوبة. ويظل مسار -o الصريح معتمدًا عندما تختار عمدًا مكان حفظ الأرشيف.

      أو من الـ shell، بالآلية نفسها:

      hermes profile export research-bot
      hermes profile export research-bot -o ./research-bot.tar.gz

      في تطبيق سطح المكتب هناك ثلاثة مداخل، تنتهي جميعها بمربع حوار الحفظ الأصلي للنظام:

      • ⌘K → Export profile…
      • انقر بزر الفأرة الأيمن على مربع profile في الشريط الجانبي (rail) → Export profile…
      • أما زر الاستيراد الموجود بجوار + في الشريط الجانبي فيتولى الاتجاه المعاكس

      يضيف التصدير من تطبيق سطح المكتب ملفًا إضافيًا لا تضيفه CLI: desktop.json، الذي يحمل الواجهة (skin)، والوضع الفاتح/الداكن، وأي تعريفات سمات مخصصة تحتاجها الواجهة، ولون الـ profile في الشريط الجانبي، وتخطيط النافذة. ولهذا يصل الـ profile المُشارَك من تطبيق سطح المكتب بمظهر مطابق لما لديك، لا بسلوك مطابق فقط.

      الاستيراد​

      /import ~/Downloads/research-bot.tar.gz
      /import ~/Downloads/research-bot.tar.gz --name research-bot-2
      hermes profile import ./research-bot.tar.gz
      hermes profile import ./research-bot.tar.gz --name research-bot-2

      يُستنتج اسم الـ profile من الأرشيف ما لم تمرّر --name. ويُرفض الاستيراد فوق profile موجود — أعد تسمية القديم أو احذفه أولًا. ويُنشأ wrapper للـ shell (research-bot → hermes -p research-bot) عندما لا يتعارض الاسم مع أمر موجود.

      يطبّق الاستيراد في تطبيق سطح المكتب أيضًا الـ overlay الموجود في desktop.json، وينقلك إلى الـ profile الجديد في محادثة جديدة. ولا مشكلة في استيراد أرشيف مُنشأ من تطبيق سطح المكتب عبر CLI — إذ يبقى ملف الـ overlay محفوظًا على القرص ويُطبَّق في المرة التالية التي تفتح فيها ذلك الـ profile في تطبيق سطح المكتب.

      ملاحظة

      لا يمكنك الاستيراد باسم default — فهذا الاسم مخصص للـ profile الجذري المدمج (~/.hermes). مرّر --name something-else.

      ما يحتويه ملف التصدير​

      يُستبعد دائمًا، في كلا نوعَي الـ profiles: auth.json و .env. فمفاتيح API الخاصة بك لا تغادر الجهاز أبدًا.

      الـ profile الافتراضي (~/.hermes) يُصدَّر عبر قائمة سماح (allow-list) — تقتصر على ملفات Hermes المعروفة، حتى لا يُجرف معه أي ملف غير ذي صلة موجود في دليلك الرئيسي:

      config.yaml، SOUL.md، MEMORY.md، USER.md، todo.json، system_prompt.md، AGENTS.md، CLAUDE.md، .cursorrules، skills/، plugins/، cron/، scripts/، sessions/، memories/، knowledge/، preferences/، و desktop.json عندما يكون تطبيق سطح المكتب قد جهّز واحدًا.

      أما الـ profile المسمّى (~/.hermes/profiles/<name>) فيُنسخ دليله بأكمله باستثناء auth.json / .env. وهذا نطاق أوسع — فإذا كان الـ profile يحتوي على state.db أو سجلات أو ملفات تخزين مؤقت، فستدخل في الأرشيف أيضًا، ويكبر حجم الملف.

      راجع محتوى الأرشيف قبل إرساله

      التصدير لقطة من الـ profile الخاص بك، وليس إصدارًا منتقى المحتوى. وعلى عكس التوزيعة، يمكن أن يتضمن memories/ و sessions/ و USER.md — ولا يوجد ما يفحص المهارات أو الذكريات أو الشخصية بحثًا عن أي معلومات شخصية كتبتها فيها. تُرشَّح بيانات الاعتماد حسب اسم الملف؛ أما المحتوى فلا.

      قبل المشاركة مع شخص آخر، اعرض قائمة بما بداخله:

      tar -tzf research-bot.tar.gz | less

      إذا كان يحمل سجل محادثات تفضّل عدم تسليمه، فانشر توزيعة بدلًا من ذلك — فالتوزيعات لا تشحن الذكريات أو الجلسات أبدًا.

      ما لا تحتويه التوزيعة (أبدًا)​

      يستبعد المُثبّت هذه المسارات إلزاميًا حتى لو شحنها المؤلف عن طريق الخطأ. ولا يوجد أي خيار في الإعدادات يتيح لك تجاوز ذلك — فهذه الحماية قاعدة ثابتة مغطاة باختبارات الانحدار (regression tests):

      • auth.json — tokens الخاصة بـ OAuth، وبيانات اعتماد المنصات
      • .env — مفاتيح API، والأسرار
      • memories/ — ذاكرة المحادثات
      • sessions/ — سجل المحادثات
      • state.db، state.db-shm، state.db-wal — البيانات الوصفية للجلسات
      • logs/ — سجلات الوكيل والأخطاء
      • workspace/ — ملفات العمل المُنشأة
      • plans/ — الخطط المؤقتة
      • home/ — نقطة تحميل الدليل الرئيسي للمستخدم في backends الخاصة بـ Docker
      • *_cache/ — ملفات التخزين المؤقت للصور / الصوت / المستندات
      • local/ — نطاق أسماء محجوز للمستخدم لأغراض التخصيص

      عندما تستنسخ توزيعة بصفتك مُثبِّتًا، فإن هذه الملفات ببساطة لا تُنسخ إلى دليل الـ profile الخاص بك. وعند التحديث، تبقى نسخك كما هي. وإذا ثبّتَّ التوزيعة نفسها على خمسة أجهزة، فستكون لديك خمس مجموعات معزولة من هذه البيانات — واحدة لكل جهاز.

      تنبيه

      يُنفَّذ هذا الاستبعاد وقت التثبيت / التحديث على جهاز المُثبِّت. ولا يمنع المؤلف من إضافة ملفات حساسة/غير ضرورية في commit. يجب على المؤلفين استخدام ملف .gitignore لإبقاء الأسرار خارج المستودع.

      الأمان والثقة​

      توزيعات الـ profile غير موقّعة افتراضيًا. فأنت تثق في:

      • مستضيف git (GitHub / GitLab / أيًّا كان) بأن يقدّم البايتات نفسها التي دفعها المؤلف.
      • المؤلف بألّا يشحن ملف SOUL أو مهارات أو مهام cron خبيثة.

      مهام cron القادمة من توزيعة لا تُجدوَل تلقائيًا — إذ يطبع المُثبّت hermes -p <name> cron list وتفعّلها أنت صراحةً. أما SOUL.md والمهارات فتكون نشطة فعلًا بمجرد أن تبدأ المحادثة مع الـ profile، لذا اقرأها قبل أول تشغيل إذا كنت تثبّت من شخص لا تعرفه.

      تشبيه تقريبي: تثبيت توزيعة يشبه تثبيت إضافة للمتصفح أو إضافة لـ VS Code؛ سهولة كبيرة، وقدرات عالية، ويتطلب الثقة بالمصدر. وبالنسبة إلى التوزيعات الداخلية في الشركات، استخدم مستودعًا خاصًا ومصادقة git المعتادة لديك — دون أي شيء جديد لإعداده.

      قد تضيف الإصدارات المستقبلية التوقيع، وملف قفل (lockfile) هو .distribution-lock.yaml يتضمن قيمة SHA محددة للـ commit، وخيار --dry-run يطبع الفروقات قبل تطبيق التحديث. ولم يُطرح أيٌّ من ذلك بعد.

      خلف الكواليس​

      للاطلاع على تفاصيل التنفيذ، والسلوك الدقيق لـ CLI، وجميع الخيارات، راجع مرجع أوامر Profile.

      باختصار:

      • توجد install و update و info ضمن hermes profile — وليست شجرة أوامر موازية.
      • تنسيق الـ manifest هو YAML بمخطط إلزامي صغير جدًا (name فقط).
      • يستخدم المُثبّت ملف git التنفيذي المحلي لديك للاستنساخ، لذا تعمل أي مصادقة يتعامل معها الـ shell لديك مسبقًا (مفاتيح SSH، وأدوات credential helpers) بشفافية.
      • بعد الاستنساخ، يُزال .git/ — فالـ profile المثبّت ليس بحد ذاته نسخة git مسحوبة، مما يجنّبك فخاخًا من قبيل "يا إلهي، أضفت ملف .env عن طريق الخطأ إلى سجل git الخاص بالتوزيعة".
      • تُرفض أسماء الـ profiles المحجوزة (hermes و test و tmp و root و sudo) وقت التثبيت لتجنّب التعارض مع الملفات التنفيذية الشائعة.

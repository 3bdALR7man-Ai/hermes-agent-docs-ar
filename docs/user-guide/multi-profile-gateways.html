      تشغيل عدة Gateways في وقت واحد

      شغّل عدة profiles — لكل منها رموز البوت، والجلسات، والذاكرة الخاصة به — كخدمات مُدارة على جهاز واحد. تتناول هذه الصفحة الجوانب التشغيلية: تشغيلها كلها معًا، وعرض السجلات عبر الـ profiles، ومنع الجهاز المضيف من النوم، والتعافي من مشكلات launchd/systemd الشائعة.

      إذا كنت تشغّل وكيل Hermes واحدًا فقط، فلست بحاجة إلى هذه الصفحة — راجع Profiles للأساسيات. وإذا كانت نُسخك تعمل على أجهزة مختلفة ينبغي لتطبيق سطح مكتب واحد الوصول إليها في آن واحد، راجع ربط Desktop بعدة نُسخ من Hermes.

      متى تستخدم هذا​

      تحتاج إلى هذا الإعداد عندما يكون لديك وكيلا Hermes أو أكثر ينبغي أن يكونا متصلين في الوقت نفسه. من الأسباب الشائعة:

      • مساعد شخصي على بوت Telegram وواحد آخر وكيل برمجة على بوت آخر
      • وكيل واحد لكل فرد من العائلة أو وكيل واحد لكل مساحة عمل Slack
      • نُسخ Sandbox + إنتاج (production) من الإعدادات نفسها
      • وكيل بحث + وكيل كتابة + بوت مُشغَّل بواسطة cron — لكل منها ذاكرة ومهارات معزولة

      يحصل كل profile بالفعل على مدخل supervisor خاص به بحسب المنصة: LaunchAgent (ai.hermes.gateway-<name>.plist) أو خدمة مستخدم systemd (hermes-gateway-<name>.service) أو خدمة systemd على مستوى النظام عند تثبيتها باستخدام sudo hermes gateway install --system (تعمل بهوية المستخدم الذي يستدعيها عبر User=)، أو Windows Scheduled Task، أو خدمة s6/Docker — ويطلق تطبيق Desktop backend خاصًا بكل profile من نوع hermes serve. يضيف هذا الدليل أنماط إدارتها جميعًا معًا.

      البدء السريع​

      # Create profiles (once)
      hermes profile create coder
      hermes profile create personal-bot
      hermes profile create research

      # Configure each
      coder setup
      personal-bot setup
      research setup

      # Install each gateway as a managed service
      coder gateway install
      personal-bot gateway install
      research gateway install

      # Start them all
      coder gateway start
      personal-bot gateway start
      research gateway start

      هذا كل ما في الأمر — ثلاثة وكلاء مستقلين، كل منهم على عمليته الخاصة، تُعاد تشغيلها تلقائيًا عند العطل وعند تسجيل دخول المستخدم.

      بديل: gateway واحد لكل profiles (تعدد الإرسال)​

      يشغّل النموذج أعلاه عملية واحدة لكل profile . والبديل هو gateway واحدًا متعدد الإرسال: تصبح عملية gateway واحدة — أيًا كان الـ profile الذي أطلقها — العملية الواردة الوحيدة، وتخدم الرسائل لـ كل profile على الجهاز.

      تستهدف أوامر دورة الحياة للـ profile الافتراضي تلك العملية. ويمكن لـ profiles المُسمّاة إيقاف بوتاتها وحدها أو إعادة تشغيلها دون إيقاف المضيف:

      • hermes -p <name> gateway run أثناء عمله، فإنه يرتبط بدل بدء عملية ثانية: يطبع PID الخاص بالـ gateway المضيف ومجموعة profiles المخدومة ويخرج بالرمز 0. وإذا كان <name> غير مخدوم بعد، يطلب من gateway المضيف إعادة مسح profiles/ ويرتبط حين تضمّه الإجابة؛ ولا يرفض (برمز غير صفري) إلا حين يتعذّر جعل gateway المضيف يخدمه.
      • hermes gateway start --all / restart --all يعنيان مضيف تعدد الإرسال الواحد. ولا يمسحان كل عمليات gateway على الجهاز مطلقًا؛ ويُبلَّغ عن profile ما زال يشغّل gateway خاصًا به، ولا يُنهى مطلقًا، مع أمر hermes gateway migrate --multiplex من سطر واحد.
      • hermes gateway run --replace يستحوذ على العملية التي تخدم هذا الـ profile، أيًا كان الـ profile الذي أطلقها. وإذا كان مالك المضيف gateway منفردًا لـ profile آخر (مجموعة gateways لكل profile لم تُرحَّل)، فهو لا يخدم هذا الـ profile مطلقًا، لذا يبدأ --replace إلى جانبه تمامًا كما يفعل run العادي، بدل الرفض والدخول في عاصفة إعادة إنشاء تحت المشرف. وكان Hermes أقدم يكتب ملف systemd إضافيًا (hermes-gateway.service.d/20-replace.conf) يفرض --replace على الوحدة؛ ويزيل الآن hermes update / hermes gateway restart ذلك الملف. hermes gateway run --force يبدأ gateway منفصلًا دون سؤال عملية المضيف أصلًا (مخرج حين تكون عالقة أو تجيب خطأً).
      • تحت مشرف خدمات، يخرج الارتباط بالرمز 75، لا 0 — تعيد systemd و s6 و launchd تشغيل 75 بعد تأخير قصير، لذا تظل الوحدة تعيد المحاولة وتستحوذ تلقائيًا فور اختفاء عملية المضيف.
      • قد ترى وحدتان بدأتا معًا عدم وجود عملية مضيف بعد؛ ويحدد قفل المضيف أيهما يعمل، ويخرج الخاسر بالرمز 75 ويرتبط عند إعادة المحاولة. --replace لا يتجاوز ذلك الفحص (كل وحدة مولّدة تحمله)، ولا يتجاوزه إلا --force .

      تعدد الإرسال مفعّل افتراضيًا (gateway.multiplex_profiles قيمته الافتراضية true)، مع قاعدة أمان واحدة: الخيار غير المضبوط طلب يحسمه الـ gateway الافتراضي عند الإقلاع، لا قرارًا نهائيًا. وعند كل بدء تشغيل، ينفّذ الفحص المسبق نفسه الذي ينفّذه hermes gateway migrate --multiplex ولا يفعّل تعدد الإرسال إلا إذا كان الدمج آمنًا — profile اثنان أو أكثر، ولا profile ثانوي ما زال يشغّل gateway خاصًا به (عملية حية أو خدمة مثبتة، أو خانة لكل profile تحت s6 تعمل فعليًا )، ولا بيانات اعتماد بوت مكررة، ولا منصة تربط منفذًا دون مدخل /p/<profile>/ . عدم الضبط يعني التفعيل: حين لا يوجد عائق، يفعّل الـ gateway تعدد الإرسال ويكتب gateway.multiplex_profiles: true في config.yamlللـ profile الافتراضي (مع الحفاظ على التعليقات)، كي يذكر الملف ما تفعله بيئة التشغيل. وإلا يبدأ بخدمة الـ profile الافتراضي وحده ويعلن ذلك بوضوح على مضيف ذي profiles أخرى: تحذير داخل إطار عند بدء الـ gateway يسمّي profiles غير المخدومة والعائق والحل؛ والإطار نفسه في ملخّص hermes update وحالة hermes gateway status؛ ولافتة في لوحة التحكم (يحمل/api/status multiplex_standalone_reason). ولا يُحذَّر التثبيت ذو profile واحد — فلا يوجد ما يُخدَم. ولا يُكتب شيء عند الرفض.

      تتجاوز قيمة صريحة true الفحص المسبق للترحيل، عدا profile إطلاق ينسحب باستخدام gateway.standalone: true:

      • gateway.multiplex_profiles: true (ما يكتبه الترحيل) يفعّل تعدد الإرسال بغض النظر عن الفحص المسبق — فأنت، أو عملية الترحيل، اتخذت القرار.
      • gateway.multiplex_profiles له قيمة صالحة واحدة حاليًا: true، وتُكتب نيابةً عنك. ويُحسم المفتاح غير المضبوط على التفعيل ويُجعل صريحًا في config.yaml. false أما فقد أُوقفت: يعيد الـ gateway كتابتها إلى true في موضعها ويطبع إشعارًا لمرة واحدة داخل إطار عند ذلك البدء وفي ملخّص hermes update التالي — ولا يقلبها بصمت مطلقًا. والـ gateway الخاص بكل profile هو gateway.standalone: true في إعدادات ذلك الـ profile نفسه (طبقة توافق مؤقتة، لا بنية مدعومة) أو --force للحالات الحدّية أدناه.
      • GATEWAY_MULTIPLEX_PROFILES في بيئة العملية يتجاوز قرار المفتاح غير المضبوط بالطريقة نفسها التي تتجاوز بها قيمة true الصريحة.
      • gateway.standalone: true في إعدادات profile مُسمّى نفسه config.yaml (profiles/<name>/config.yaml) هو طبقة توافق مؤقتة (راجع أدناه): لا يخدم الـ gateway المضيف ذلك الـ profile، ويشغّل profile الـ gateway الخاص به دون --force. ولا يخدم gateway الخاص به إلا نفسه، حتى إذا ضُبط multiplex_profiles: true أيضًا (راجع لا gateways جديدة لكل profile). وعند ضبطه للـ profile الافتراضي يُتجاهَل مع تحذير — فالـ profile الافتراضي هو gateway المضيف. ولا يوجد متغير بيئة لهذا المفتاح.

      العمليات الأخرى (hermes -p <name> gateway start، ولوحة التحكم، و hermes gateway migrate) لا تخمّن مطلقًا كيفية حسم خيار غير مضبوط: تقرأ سجل served_profiles للـ gateway الافتراضي الجاري، ولا تعود إلى الخيار الصريح إلا حين لا يعمل gateway.

      متى تفضّل تعدد الإرسال​

      • نشر على حاوية/VPS تكون فيه N وحدات مشرف و N منافذ و N ملفات PID عبئًا.
      • profiles كثيرة قليلة الحركة لا يبرر كل منها عملية كاملة.
      • تريد شيئًا واحدًا للبدء والمراقبة وإعادة التشغيل.

      لم تعد عملية واحدة لكل profile بنية يمكن اختيارها ضمنيًا: يرفض gateway install / gateway start للـ profile المُسمّى دون --force (راجع لا gateways جديدة لكل profile). ويمكن لـ profile ما زال يحتاج gateway خاصًا به أثناء بقاء فجوة في تعدد الإرسال أن يضبط الخيار المؤقت gateway.standalone: true في config.yamlالخاص به؛ وحين يمنع حد حقيقي الدمج — مجموعة موزعة على مستخدمي UNIX، أو HERMES_HOME خارج <default home>/profiles/ — يحتفظ كل profile بـ --force مسارًا له.

      تثبيت الخيار​

      مع عدم ضبط الخيار، يقرر الـ gateway الافتراضي عند كل إقلاع (أعلاه). ولتثبيته، اضبطه في الـ profile الذي يعمل gateway الخاص به كعملية مضيف (عادةً الـ profile الافتراضي) وأعد تشغيل gateway الخاص به — تفرض true تعدد الإرسال حتى حين كان فحص الإقلاع المسبق سيمنعه (false موقوفة وتُتجاهَل):

      hermes config set gateway.multiplex_profiles true
      hermes gateway restart

      وبالمثل، في ~/.hermes/config.yaml:

      gateway:
        multiplex_profiles: true

      (يُقبل الخيار أيضًا على المستوى الأعلى باسم multiplex_profiles: true للتيسير). وعند تعدد الإرسال، يعدد الـ gateway الافتراضي كل profile، ويشغّل منصاته المفعّلة تحت بيانات اعتماده الخاصة، ويوجّه كل رسالة واردة إلى الـ profile الذي تنتمي إليه. ويحدد كل دور إعدادات الـ profile الموجّه إليه ومهاراته وذاكرته و SOUL و ومفاتيح المزوّدين — ولا تُشارَك بيانات الاعتماد عبر profiles مطلقًا.

      يخدم المضيف profiles الثانوية غير المتوقفة تلقائيًا. استخدم gateway start على profile متوقف لإعادته إلى الخدمة.

      إيقاف profile واحد دون إيقاف المضيف​

      للـ profile المُسمّى الذي يخدمه مضيف تعدد الإرسال:

      hermes -p coder gateway stop     # park coder; other profiles keep running
      hermes -p coder gateway start    # unpark coder and serve it again
      hermes -p coder gateway restart  # reconnect coder with its current configuration

      stop يكتب gateway.parked في مجلد الـ profile الرئيسي قبل طلب إيقاف محوّلاته من المضيف واستثناء مهام cron الخاصة به من الدورات اللاحقة. وتبقى العلامة عبر إعادة تشغيل المضيف. وتُتجاهَل محتوياتها؛ ويكفي ملف فارغ. ويمكن لعملية التهيئة إنشاء <profiles-root>/coder/gateway.parked مسبقًا كي يبقى profile مثبت متوقفًا. ولا يحذف الإيقاف الـ profile أو جلساته أو مهامه المجدولة.

      start يزيل العلامة ثم يطلب من مضيف جارٍ خدمة الـ profile. ودون مضيف جارٍ يزيل العلامة ويتبع مسار البدء العادي؛ ابدأ المضيف من الـ profile الافتراضي إذا طُلب منك. restart يزيل خدمة الـ profile ثم يعيدها دون كتابة علامة إيقاف، مع إعادة قراءة إعداداته. وفي profile متوقف دون gateway حي خاص به، يتصرف restart كـ start: يزيل العلامة ويبدأ خدمة الـ profile مباشرةً (gateway بدأ باستخدام --force إلى جانب العلامة يحتفظ بإعادة تشغيله الخاص بدلًا من ذلك). ولا تنهي هذه العمليات عملًا وزعته دورة cron بالفعل.

      يعيد المضيف أيضًا المسح كل 30 ثانية: تزيل إضافة العلامة يدويًا خدمة الـ profile؛ وتجعله إزالتها يدويًا مؤهلًا مجددًا. وإذا لم يؤكد socket التحكم الطلب، يبلغ CLI بذلك ويطبّق المسح التالي حالة العلامة. وقد يستغرق إنهاء المحوّل أو الاتصال وقتًا إضافيًا. hermes -p coder gateway status يبلغ عن parked (hermes -p coder gateway start) ما دامت العلامة موجودة.

      لا يمكن إخراج profile الإطلاق من الخدمة. وتُتجاهَل علامة الـ profile الافتراضي مع تحذير؛ وتحتفظ أوامر دورة حياته ومتغيرات --all بسلوكها على المضيف كله. والـ gateway الجاري منفصلًا --force يحتفظ بدورة حياة عمليته الخاصة.

      زرا لوحة التحكم و Desktop Stop / Start لـ profile مخدوم يفعلان الشيء نفسه: يوقفه Stop (ينشئ/api/gateway/stop?profile=coder الذي يشغّل hermes -p coder gateway stop)، ويزيل Start إيقافه حين يكون gateway المضيف حيًا، ويدرج /api/status parked_profiles. أما Start على profile مُسمّى غير متوقف فيعيد 409 أيضًا — إذ سيحتاج إلى gateway خاص به.

      المتوقف مقابل gateway.standalone: true​

      لا ينطبقان على الـ profile نفسه في الوقت نفسه مطلقًا، ولا يستلزم أحدهما الآخر:

      Profileيخدمه المضيف-p X gateway stop-p X gateway start
      مخدوم (الحالة الافتراضية)نعميوقفه (علامة + unserve-profile)مخدوم بالفعل
      متوقف (gateway.parked موجودة)لا، حتى يُزال إيقافهمتوقف بالفعليزيل الإيقاف (إزالة العلامة + serve-profile)
      منفرد (gateway.standalone: true)مطلقًايوقف عملية gateway الخاصة به؛ ولا يكتب علامةيبدأ gateway الخاص به

      gateway.standalone يأخذ الأولوية: لا يكتب المضيف gateway.parked لـ profile منفرد مطلقًا ولا يخدمه، سواء كان متوقفًا أم لا، لذا يظل stop و start في ذلك الـ profile بمعناها لكل عملية. والإيقاف هو الطريقة الأصلية في تعدد الإرسال لإخراج profile واحد من الخدمة — وهو ما يغلق فجوة "per-profile stop/restart" التي بقيت طبقة التوافق المؤقتة مفتوحَين لها.

      لا gateways جديدة لكل profile​

      افتراضيًا يخدم gateway مضيف واحد كل profile، ولا يحصل profile مُسمّى على gateway خاص به. ودون خيار الانسحاب أدناه، يرفض hermes -p coder gateway install (أو start, run، وخطوة الخدمة في hermes -p coder setup) برمز خروج 78 سواء كان gateway المضيف يعمل حاليًا أم لا:

      ❌ Profile 'coder' does not get a gateway of its own.
        Exactly one gateway per host is the inbound process for every
        profile. Starting a separate gateway for this profile would
        double-bind its platforms (two pollers on one bot token, port
        conflicts).

        Install or start the host gateway from the default profile; it serves this one too:

          hermes gateway install

        Or fold an existing per-profile fleet onto one host gateway:

          hermes gateway migrate --multiplex

        A separate per-profile gateway (for a fleet split across UNIX users or a
        HERMES_HOME outside profiles/) needs --force:  hermes -p coder gateway install --force

        Temporary compatibility path while multiplexing gaps are closed: set
        gateway.standalone: true in profiles/coder/config.yaml,
        then wait for the host gateway to rescan (<=30s) or send its rescan-profiles control verb.
        (gateway.standalone is a temporary compatibility shim while multiplexing gaps are fixed;
        it will be removed once they are — plan to fold this profile with `hermes gateway migrate --multiplex`.)

      حين يكون gateway المضيف يعمل بالفعل ويخدم الـ profile، يقرأ السطر الأول The host gateway already serves profile 'coder'. مع PID المالك ومجموعة profiles المخدومة، وتكون الإحالة hermes -p default gateway restart. ويعيد زر Start في لوحة التحكم لـ profile مُسمّى الرفض نفسه.

      مؤقت: gateway.standalone: true​

      توافق مؤقت مع الإصدارات السابقة، لا بنية نحتفظ بها

      الاتجاه هو تعدد الإرسال وحده: gateway واحد لكل مضيف يخدم كل profile. وصل التحول قبل سد كل الفجوات — والفجوات المفتوحة هي جسر WhatsApp والوسيط في profiles الثانوية وتحديد نطاق لوحة التحكم؛ أما الإيقاف/البدء/إعادة التشغيل لكل profile فقد حُلّت بـ الإيقاف — وفقدت المجموعات التي اعتمدت على gateways لكل profile هذه الـ gateways بين ليلة وضحاها. gateway.standalone: true موجود كي تستمر تلك المجموعات في العمل أثناء إصلاح تلك الفجوات. وسيُزال بعد إصلاحها، مع إشعار مسبق في ملاحظات الإصدار؛ وتذكر ذلك كل واجهة تطبعه. لا تبنِ إعدادات جديدة عليه: إذا بدأت من جديد، فشغّل مضيف تعدد الإرسال. وإذا منعتك فجوة اليوم، فاضبط المفتاح وأنشئ issue للفجوة أو صوّت لها كي نستطيع إزالة طبقة التوافق أسرع.

      اضبط gateway.standalone: true في إعدادات الـ profile نفسه config.yaml:

      # profiles/coder/config.yaml
      gateway:
        standalone: true

      حينئذ لا يخدم gateway المضيف الـ profile، ويسجّل سجل الإقلاع profile 'coder' is standalone (gateway.standalone: true); not served by this gateway. hermes -p coder gateway install|start|run يعمل دون --force. وإذا ظل المضيف الجاري يدرج الـ profile ضمن مجموعته المخدومة، يرفض الأمر حتى يعيد المسح: انتظر المسح التالي (30 ثانية على الأكثر في التشغيل العادي)، أو أرسل أمر التحكم rescan-profiles إلى gateway المضيف. ولا تلزم إعادة تشغيل المضيف.

      يجعل حذف المفتاح الـ profile مؤهلًا للمضيف مجددًا. وما دام gateway الـ profile نفسه حيًا، يتجاوز المضيف إضافته ويسجّل ضرورة إيقافه أولًا. أوقف ذلك الـ gateway؛ فيتبنّى المضيف الـ profile عند المسح التالي.

      لا تعمل محوّلات profile منفرد و cron ومدخل webhook وإشعارات Kanban الخاصة به إلا حين يعمل gateway الخاص به، لا تحت مضيف تعدد الإرسال أو hermes serve. وجّه عملاء webhook إلى مستمع gateway المنفرد نفسه؛ فلا يعود مدخل المضيف /p/<profile>/ يخدمه. ويحدد ذلك المستمع منفذه من .env أو config.yamlللـ profile نفسه، لذا حين يفعّل كلا الـ gateway المنفرد والمضيف خادم API أو مدخل webhook، أعطِ الـ profile قيمة مستقلة لـ API_SERVER_PORT / WEBHOOK_PORT؛ فالـ gatewayان المتروكان على القيم الافتراضية يحاولان كلاهما ربط المنافذ نفسها. وما زال منتقي وجهة cron يدرج profiles المنفردة كأهداف bot-chat:<name> ، لكن المضيف لا يستطيع التسليم إلى تلك الأهداف.

      hermes -p coder gateway status يطبع standalone by config (gateway.standalone: true) قبل حالة gateway الـ profile نفسه، ويدرجه hermes gateway status (الافتراضي) بصيغة standalone by config: coder بعد المجموعة المخدومة. hermes gateway migrate --multiplex يترك الـ profile دون تغيير ويطبعه بصيغة Standalone by config (gateway.standalone: true), left alone. ويعمل جسر WhatsApp والوسيط في gateway الـ profile نفسه، كما في أي gateway منفرد.

      --force ليس مسار طبقة التوافق هذه؛ ويبقى مخرجًا للحالتين الحدّيتين اللتين يذكرهما الرفض (مجموعة موزّعة على مستخدمي UNIX، أو HERMES_HOME خارج profiles/): يثبّت خدمة حقيقية لكل profile، وتظل تلك الخدمة (لا يحمل ExecStart لها --force) تبدأ طبيعيًا بعد ذلك.

      ما يتغير عند تفعيل تعدد الإرسال​

      يغيّر تعدد الإرسال سلوك أشياء قليلة. ولا ينطبق أي منها على profile ينسحب باستخدام gateway.standalone: true أو يشغّل gateway منفصلًا باستخدام --force على مضيف ممنوع.

      1. يجب ألا تبدأ profiles الثانوية gateway خاصًا بها​

      مع وجود مضيف تعدد إرسال جارٍ، يرتبط gateway run للـ profile المُسمّى به؛ ويرفض gateway install إنشاء عملية أخرى (رمز خروج 78). ويرفض CLI قبل لمس مدير خدمات، مما يمنع وحدة systemd فاشلة دائمًا أو حلقة إعادة إنشاء launchd. استخدم أوامر stop, start، و restart الخاصة بكل profile أعلاه لإدارة تابع داخل المضيف. hermes gateway stop على الـ profile الافتراضي يخرج كل profile مخدوم من الخدمة أيضًا. وتتبع لوحة التحكم وتطبيق Desktop CLI: يوقف إجراء "Stop" profile المخدوم ويزيل "Start" إيقافه (راجع أعلاه)؛ ويجيب "Start" على profile مُسمّى غير متوقف بـ 409 مع الشرح نفسه (معروضًا كإشعار مضمّن في صفحة System). ويعيد "Restart" تشغيل مضيف تعدد الإرسال (العملية التي تخدم الـ profile فعلًا) بدل إنشاء -p coder gateway restart لا يمكن إلا أن يفشل. ولأن إعادة التشغيل تعيد اتصال كل بوت على الجهاز، يسأل كلا التطبيقين أولًا "Restart the shared gateway? All bots on this device reconnect: default, coder, research" (القائمة هي served_profilesللـ gateway الجاري)، وتبلغ عن "Shared gateway restarted (3 bots)" عند الاكتمال. ويحتفظ profile المنفرد بإعادة التشغيل العادية. /api/status?profile=coder يحمل القائمة نفسها باسم gateway_shared_with (null لـ gateway منفرد). وتُقرأ "Served" من سجل الـ gateway الجاري نفسه (served_profiles في gateway_state.jsonداخل المجلد الافتراضي الرئيسي)، كي تبقى صحيحة حين يكون تعدد الإرسال قد فُعّل فقط عبر GATEWAY_MULTIPLEX_PROFILES في بيئة الـ profile الافتراضي، أو حين تُضاف profiles بعد بدء الـ gateway.

      تتبع تدفقات الإعداد القاعدة نفسها: hermes -p coder setup gateway, hermes -p coder setup, hermes -p coder gateway setup و hermes -p coder import يضبطان بوتات الـ profile لكن يتجاوزان خطوة "install the gateway background service" للـ profile المخدوم، مع طباعة "Profile 'coder' is already served by the default multiplexer" بدل تسجيل وحدة أو plist شاردة لا يمكن إلا أن تبقى متوقفة. أضف bot token ويلتقطه مضيف تعدد الإرسال الجاري.

      مضيف تعدد الإرسال هو عملية الوارد الوحيدة؛ وسيؤدي gateway لـ profile ثانٍ إلى ربط منصات ذلك الـ profile مرتين. وينسحب profile يريد عمدًا عملية منفصلة باستخدام gateway.standalone: true (راجع لا gateways جديدة لكل profile)؛ ومرّر --force (يقبله run, start, install و restart) فقط حين يمنع حد الدمج. ولذلك لا يُستخدم سكربت تغليف دورة الحياة عبر profiles الوارد سابقًا في الصفحة في وضع تعدد الإرسال — أدر المضيف أو profiles المُسمّاة فيه مباشرةً.

      2. تُوصل المنصات ذات HTTP الوارد عبر بادئة URL /p/<profile>/ ​

      تصل حركة HTTP الواردة لـ profile ثانوي على مستمع الـ profile الافتراضي الوحيد ضمن بادئة profile، لا على منفذ ثانٍ:

      # default profile
      POST http://host:8644/webhooks/<route>
      # the "coder" profile, same listener
      POST http://host:8644/p/coder/webhooks/<route>

      يعيد profile مجهول أو غير مضبوط في البادئة 404. والمستمع المشترك هو منفذ api_server للـ profile الافتراضي (أو منفذ webhook حين لا يُفعَّل خادم API)؛ ويخدم ثلاثة أنواع من المسارات ذات بادئة profile:

      • api_server و webhook تُعكَسان، ولا تُكرَّران مطلقًا. /p/coder/v1/... و /p/coder/webhooks/<route> يجيب عنهما محوّل الـ profile الافتراضي نفسه ضمن نطاق coder. لذا يجب على الـ profile الثانوي ألا يفعّل api_server أو webhook بنفسه (ترفض لوحة التحكم بـ 409؛ وتوفّر قيمة API_SERVER_KEY أو WEBHOOK_ENABLED في .env للثانوي بيانات الاعتماد دون بدء مستمع).
      • تعمل كل منصة واردة بمنفذ أخرى بوضع المستمع المشترك. يحصل profile ثانوي يضبط Twilio SMS أو LINE أو Teams أو BlueBubbles أو Microsoft Graph أو WhatsApp Cloud أو WeCom callback أو وضع Feishu webhook على نسخة محوّل خاصة به تُنشأ دون منفذ؛ ويمرّر المستمع الافتراضي /p/<profile>/<the adapter's usual path> إليها. راجع المنصات ذات المنافذ الواردة تحت مضيف تعدد الإرسال.
      • يعمل WhatsApp (الجسر) لكل profile مقترن. اقرن كل profile ثانوي باستخدام hermes -p work whatsapp. ويستخدم كل profile جلسته ومنفذ الجسر الخاص به؛ ويُتجاوز profile غير مقترن بعلامة whatsapp_unpaired وحل للاقتران. راجع إعداد WhatsApp متعدد profiles.
      • يبقى Relay مدخلًا مشتركًا يملكه الـ profile الافتراضي. فعّل Relay واضبطه في الـ profile الافتراضي، ثم وجّه الوارد إلى profiles عبر profile_routes. ويُبلَّغ عن إعداد Relay في ثانوي وحده بوصفه غير مخدوم. ويشغّل profile انسحب باستخدام gateway.standalone: true وسيطه الخاص في gateway الخاص به، كما يفعل أي gateway منفرد.

      تتبع المصادقة الـ profile المُسمّى في URL. وتستمر endpoints دون بادئة في استخدام بيانات اعتماد المستمع الافتراضي الحالية.

      • /p/coder/... يجب أن تستخدم طلبات خادم API على API_SERVER_KEY من ~/.hermes/profiles/coder/.env؛ ويُرفض مفتاح المستمع الافتراضي. وتحت مضيف تعدد الإرسال لا يصادق ذلك المفتاح إلا البادئة — ولا يفعّل مستمع api_server ثانيًا في الـ profile الثانوي، لذا لا تحتاج إلى تثبيت platforms.api_server.enabled: false في config.yaml.
      • يجب أن يصرّح مسار webhook الذي يستهدف coder بـ profile: coder إلى جانب secret الحالي الخاص بالمسار في config.yamlللـ profile الافتراضي. ولا يُقبل ذلك السر حينئذ إلا عند /p/coder/webhooks/<route> ويُرفض على كل بادئة profile أخرى.
      • تبقى مسارات webhook دون profile مسارات للـ profile الافتراضي ولا يمكن الوصول إليها عبر بادئة profile مُسمّى. وترتبط الاشتراكات الديناميكية بالطريقة نفسها: يكتب hermes webhook subscribe <name> --route-profile coder profile: coder في webhook_subscriptions.json للـ gateway الافتراضي ويطبع URL /p/coder/webhooks/<name> (ويعرضhermes webhook ls الارتباط). استخدم --route-profile، لا الخيار العام -p coder: -p الذي سيكتب الاشتراك في ملف اشتراكات coder نفسه، وهو ملف لا يقرؤه محوّل webhook للـ gateway الافتراضي مطلقًا.
      • يتبع التسليم الارتباط نفسه. ويخرج رد مسار profile: coder (أو رسالة deliver_only ) عبر محوّل coder لمنصة deliver ، ويرجع إلى القناة الرئيسية لـ coder عندما تكون deliver_extra.chat_id غير مضبوطة، ويشغّل تسليم github_comment الأمر gh باستخدام GH_TOKEN / GITHUB_TOKEN من profiles/coder/.env. وإذا لم يملك coder محوّلًا لتلك المنصة، يفشل التسليم (502) بدل النشر كبوت profile آخر؛ وكذلك لا يستعير المسار الافتراضي أبدًا منصة مفعّلة في profile ثانوي وحده.
      • /p/coder/api/platforms/<platform>/events يتحقق محوّل coder من callbacks هذه ويوزّعها؛ وحين لا يملك coder محوّلًا، يكون callback خطأ 503.

      ترفض طلبات API المُسمّاة بأمان عندما لا يملك الـ profile الهدف API_SERVER_KEY. وتبقى أخطاء إعدادات الأمان قاتلة: مثلًا، تظل منصة ذات سياسة خاصة open دون GATEWAY_ALLOW_ALL_USERS أو خيار سماح للجميع خاص بالمنصة توقف بدء الـ gateway بدل إسقاط الـ profile غير الآمن بصمت.

      منصات المنفذ الوارد تحت المضاعِف​

      يربط hermes -p coder gateway run المستقل خوادم webhook الخاصة بـ Twilio و LINE و Teams... التابعة لـ coder على منافذها الخاصة. تحت المضاعِف، تظل تلك المحوّلات تابعة لـ coder — بنفس بيانات الاعتماد من profiles/coder/.env، ونفس config.yaml، وتُرسَل الردود عبر قناة coder — لكنها لا تربط أي منفذ. يمرّر مستمِع الـ profile الافتراضي المشترك /p/coder/<path> إليها، حيث <path> هو المسار نفسه الذي يخدمه المحوّل بشكل مستقل. يتحقَّق من الطلب محوّل الخاص بـ coder بسر الخاص بـ coder (رمز مصادقة Twilio ، أو سر قناة LINE ، أو بيانات اعتماد تطبيق Teams ، أو كلمة مرور BlueBubbles ، ...) ويعمل ضمن نطاق تشغيل coder ؛ ويبقى /path الخاص بالـ profile الافتراضي نفسه سليمًا، ويحصل profile ليس لديه محوّل لمسار ما على 404، وليس أبدًا بوت profile آخر.

      المنصةرابط الاستدعاء (callback) للـ profile الثانوي على المستمِع المشتركيُتحقَّق منه ببيانات الـ profile المسمّى

      BlueBubbles (bluebubbles)http://<host>/p/<profile>/bluebubbles-webhook (يُسجَّل مع الخادم تلقائيًا)BLUEBUBBLES_PASSWORD
      Microsoft Graph (msgraph_webhook)https://<host>/p/<profile>/msgraph/webhookextra.client_state
      WhatsApp Cloud (whatsapp_cloud)https://<host>/p/<profile>/whatsapp/webhookWHATSAPP_CLOUD_APP_SECRET / رمز التحقق

      <host> هو اسم المضيف العام (نفق، وكيل عكسي (reverse proxy)) أمام مستمِع الـ profile الافتراضي؛ ويحرّك webhook_path مخصص في إعدادات الـ profile المسار بعد /p/<profile> تبعًا لذلك. تسجّل الـ gateway الرابط الدقيق عند بدء التشغيل:

      [sms] profile 'coder' is served on the default profile's shared listener:
      http://127.0.0.1:8642/p/coder/webhooks/twilio (point the vendor's callback URL at this path ...)

      ويكرّره كل سطح حالة، حتى تعرف ما تلصقه في لوحة تحكم البائع (vendor console):

      $ hermes -p coder gateway status
      ✓ Gateway is running via the default-profile multiplexer
        Manage it from the default profile: hermes gateway status

      Inbound callback URLs on the shared listener:
        line: http://127.0.0.1:8642/p/coder/line/webhook
        sms: http://127.0.0.1:8642/p/coder/webhooks/twilio

      hermes gateway status وhermes status على الـ profile الافتراضي الروابط نفسها لكل profile مخدوم، وتُظهرها صفحة Channels في لوحة التحكم وصفحة Messaging في Desktop باسم ingress_url الخاص بكل منصة عند عرض ذلك الـ profile. يُبلَّغ عن api_server وwebhook الخاصَين بالـ profile الافتراضي بالطريقة نفسها لـ profile مخدوم — بصفتهما متصلَين (connected) بـ ingress_url http://127.0.0.1:8642/p/coder/v1 (وعلى التوالي .../p/coder/webhooks/<route>) — لأن الـ profile ليس له محوّل خاص بهما؛ إنه مستمِع الافتراضي الذي يجيب تحت بادئة /p/coder/. يُتجاهَل SMS_WEBHOOK_PORT, LINE_PORT, TEAMS_PORT... الخاص بالثانوي في ملف .env تحت المضاعِف (لا شيء يربط منفذًا)؛ ويعود تطبيقه فور تشغيل ذلك الـ profile gateway مستقلة خاصة به.

      3. لا تزال المنصات القائمة على بيانات الاعتماد بحاجة إلى رمز خاص بكل profile​

      تعمل منصات الاستطلاع/الاتصال (Telegram و Discord و Slack و Matrix و Signal ، ...) جيدًا تحت الـ multiplexing ، لكن كل profile يفعّل واحدة منها يجب أن يزوّد رمز بوت خاصًا به — فلا يمكن استطلاع الرمز نفسه من قِبل profile ين في آن واحد. إذا أعدّ profile ان (platform, token) نفسه، تسجّل الـ gateway خطأ يسمّي كلا الـ profile ين وتُوقِف جانبًا المحوّل المكرَّر (يظهر كـ fatal / duplicate_credential في حالة التشغيل) بينما يظل المُطالِب الأول وكل profile آخر يعملان — لا تخرج الـ gateway نفسها. تتصل محوّلات الـ profile الافتراضي أولًا وتطالب ببيانات اعتمادها، لذا فإن المحوّل الموقَف جانبًا هو دائمًا محوّل الثانوي (راجع أمان تعارض الرموز — القاعدة لم تتغيّر، إنها فقط تُطبَّق داخل العملية الواحدة الآن).

      4. مفاتيح الجلسات موزَّعة على نطاقات (namespaced) حسب الـ profile​

      تعيش جلسات كل profile ضمن نطاق اسم agent:<profile>:… بحيث لا يتصادم profile ان على المنصة/المحادثة نفسها أبدًا في مخزن الجلسات المشترك. يحافظ الـ profile الافتراضي على نطاق الاسم التاريخي agent:main:… حرفيًا، لذا لا تتأثر جلسات الـ profile الافتراضي القائمة — لا ترحيل، ولا سجل يتيم. يقبل كل مسار gateway يقرأ مفتاحًا سابقًا — اكتمالات التفويض بعد إعادة التشغيل، وإشعارات الإيقاف، و/stop خاصًا بمحادثة مستخدم فردية لتشغيل تابع، و/undo، وأزرار موافقة QQ — شكل agent:<profile>:… أيضًا، فتحصل الـ profiles الثانوية على سلوك الـ profile الافتراضي نفسه. واسم الـ profile الوحيد الذي يتعارض مع نطاق أسماء الافتراضي، أي profile اسمه حرفيًا main، يُستخدم له المفتاح agent:main~:… كي يحتفظ بجلساته الخاصة و profiles/main/state.db.

      تحطّ صفوف كل profile في ملفه الخاص state.db: صفوف profile مسمّى تحت profiles/<name>/state.db، وصفوف الـ profile الافتراضي تحت منزل الإطلاق — حتى عندما تحدث الكتابة داخل دور موجَّه أو نبضة خلفية (tick) تابعة لـ profile آخر. يظل مخزن backend الخاص بـ Desktop/TUI مثبَّتًا على المنزل الذي أُطلق تحته، وتُحفَظ وكلاء Bot Chat الفرعيون (prompt.background) بجانب محادثتهم الأصل.

      5. PID/قفل واحد وسطح حالة واحد​

      يوجد PID وقفل واحد على مستوى العملية (المضاعِف، تحت منزل الافتراضي). يبلّغ hermes status --full على الـ profile الافتراضي عن المضاعِف ويسرد الـ profiles التي يخدمها (Serves: coder, research). hermes -p coder status وhermes -p coder gateway status جميعًا "running via the default-profile multiplexer" بدلًا من "stopped"، وتبلّغ صفحة /api/status?profile=coder / Channels في لوحة التحكم عن المضاعِف باعتباره gateway coder العاملة (مع محوّلات coder الخاصة بصفتها منصاته). يعيش gateway_state.json الواحد تحت المنزل الافتراضي: تظهر المحوّلات الثانوية هناك كإدخالات <profile>:<platform> بجانب served_profiles؛ ولا يُكتب ملف حالة gateway لكل profile.

      hermes -p coder cron status يسمي gateway المضيف الوحيد والـ profiles التي يخدمها — Scheduler host: the host gateway (PID 4211) serving profiles default, coder — ثم يفحص نبضة ticker الخاصة بـ coder وآخر tick ناجح. وتنتج النبضة الغائبة أو القديمة تحذيرًا بدل حكم غير مشروط بأنه يعمل. ويحذر cron list و cron create أيضًا عند غياب نبضة حديثة لـ profile مخدوم. ويضيف cron status تفاصيل إخفاق tick التي لا تقرؤها تلك الفحوص الخفيفة.

      عندما لا يملك أي gateway دور المضيف، يخبرك cron status بأن تبدأ gateway المضيف الوحيد (hermes --profile default gateway install / gateway run) وتتأكد من أنه يخدم هذا الـ profile. ولا يُعرض تثبيت خدمة لكل profile إلا تحت LEGACY (pre-multiplex topology, not recommended): إذ سيبدأ عملية gateway ثانية على المضيف. ويتبع hermes doctor القاعدة نفسها — ففي s6 يعرض Host gateway: the host gateway (PID 4211) serving profiles default, coder بدل عدد slots لكل profile ، ويعلّم أي slot لكل profile لا يزال خاضعًا للإشراف بـ LEGACY ، ويفحص linger لوحدة systemd للمضيف حتى عند تشغيل doctor من profile مخدوم. والـ state.db تذكر أسطر الجهات التي تفتح قاعدة البيانات عملية المضيف المشتركة أيضًا، فتحدد "3 process(es) holding the DB open" أي gateway وأي profiles ستتأثر بإيقافه.

      ما الذي لا يتغيّر​

      يبقى عزل بيانات اعتماد .env محفوظًا، بل أشد صرامة إن كان هناك اختلاف: تُحدد مفاتيح الـ profile من نطاقه الخاص ولا تُدمج مطلقًا في بيئة مشتركة. ولا ترى العمليات الفرعية مثل خوادم MCP وعمّال Kanban إلا أسرار الـ profile الخاص بها — بما فيها بيانات الاعتماد المحقونة من مصدر أسرار خارجي (1Password ، و Bitwarden ، …): يتلقى خادم stdio MCP الذي يبدأ للـ profile B قيمة B لذلك الاسم، أو لا شيء إن لم يملك B قيمة، ولا يتلقى قيمة الـ profile الافتراضي مطلقًا. وتُوصل خوادم MCP لكل profile على حدة: يحصل profile ان يسمّيان خادمًا بـ github بـ token خاص بكل منهما على اتصالين، ويرى كل منهما أدواته وحدها؛ والـ profiles التي يكون إدخال mcp_servers الخاص بها متطابقًا (المسار نفسه و بيانات الاعتماد، بما في ذلك mTLS client_cert/client_key) تشترك في اتصال واحد، ويعيد /reload-mcp لدى المالك تسجيل أدوات الـ profiles المشاركة دون إعادة تحميلها. ولا تُشارك خوادم auth: oauth بين profiles مطلقًا: يحتفظ كل profile بـ token الخاص به تحت mcp-tokens/ الخاص به ويفتح اتصاله الخاص. ويوصل بدء التشغيل الـ profiles واحدًا بعد آخر، وداخل profile الواحد لا يزيد عدد الخوادم المتصلة معًا عن mcp.discovery_concurrency (الافتراضي 4، و 0 = غير محدود)، فلا تعود مجموعة profiles ذات خوادم stdio كثيرة تُنشئ كل العمليات المساعدة في اللحظة نفسها. وتبقى سياسة الثقة لكل profile: فما زال profile trust: untrusted الذي يشارك اتصال profile trust: full يُسأل قبل كل استدعاء قادر على الكتابة، و supports_parallel_tool_calls لا ينطبق إلا على الـ profile الذي ضبطه. وتُحدَّد إعدادات الطرفية (terminal.backend, terminal.cwd, terminal.docker_volumes, terminal.docker_shared_container_key، أهداف SSH ، ...) كذلك لكل profile في كل دور موجَّه: يحصل profile يغفل مفتاح طرفية على الافتراضي الموثّق، لا قيمة profile الإطلاق أبدًا، ويُرفَض تنفيذ الطرفية لـ profile يتعذّر تحليل config.yaml/.env الخاص به بدلًا من تشغيله تحت سياسة sandbox لـ profile آخر. يغطّي حارس بيانات اعتماد تسليم الوسائط (قائمة الحظر خلف مرفقات MEDIA: المرفقات — .env, auth.json, config.yaml, state.db، ونصوص الجلسات، ومخازن رموز OAuth) كل profile تحت profiles/، بحيث لا يستطيع دور أي profile إرفاق أسرار أو سجل محادثات profile آخر في رد. التفويض أيضًا لكل profile: تُقرأ GATEWAY_ALLOW_ALL_USERS, GATEWAY_ALLOWED_USERS وكل قائمة سماح منصة أو خيار السماح للجميع من .env الخاص بالـ profile المالك — لا يفتح انضمام الـ profile الافتراضي إلى وصول مفتوح أبدًا بوت profile ثانوي، ويُحترَم انضمام ثانوي في .env الخاص به فقط. الأمر نفسه ينطبق على السلوك الخاص بكل بوت المكتوب في config.yaml (require_mention, mention_patterns, allow_bots, reactions, auto_thread, free_response_auto_thread, dm_policy, ignored_channels، و Matrix session_scope الخاصة بـ Matrix ، ...): لا يحطّ YAML لـ profile ثانوي أبدًا في بيئة العملية المشتركة، لذا لا يمكن أن يصبح سياسة الـ profile الافتراضي، ولا يحكم YAML الخاص بالـ profile الافتراضي بوتًا ثانويًا أبدًا. تُحلّ كذلك لكل profile قائمة السماح terminal.env_passthrough، وقناة المنزل المخصَّصة تلقائيًا لـ Yuanbao ، وحرّاس الكتابة الحامية لملف config.yaml الخاص بكل profile. يتصرف Kanban ، والمهارات/الذاكرة/SOUL المحدَّدة النطاق لكل profile ، وتوجيه النموذج جميعًا لكل profile تمامًا كما تتصرف مع gateways منفصلة.

      الهوية الصادرة أيضًا لكل profile. يرسل الدور العامل من أجل الـ profile P والذي يستدعي أداة send_message (إرسال، وتفاعل، ووسائط) عبر بوت P الخاص؛ وكذلك إشعارات "Gateway shutting down/restarted" و/update لجلسات P، وتنبيهات /loop المضبوطة من محادثات P، وتنبيه المشغِّل غير المصرَّح به لأمر Discord المائل (slash) الخاص ببوت Discord لـ P باستخدام بوت Discord الخاص به (إلى P). وإذا لم يكن لدى P بوت متصل لتلك المنصة، يفشل الإرسال برسالة خطأ واضحة — ولا يعود أبدًا إلى بوت الـ profile الافتراضي.

      تتبع بيانات اعتماد الأدوات ومزوّدي الذاكرة القاعدة نفسها. يُقرأ OCR المستضاف (FIRECRAWL_API_KEY)، وبوابات Modal / Browser Use السحابية، ومفتاح OpenAI الخاص بـ mem0 OSS ، وفيديو xAI ، وكل هوية مزوّد ذاكرة (MEM0_USER_ID, SUPERMEMORY_CONTAINER_TAG, RETAINDB_PROJECT, OPENVIKING_ACCOUNT/USER, HINDSIGHT_BANK_ID, HERMES_HONCHO_HOST) تُقرأ من .env، لذا تستقر ذاكرة profile ثانوي في خاص به account/bank/project الخاص به (أو القيمة الافتراضية لكل profile لدى المزوّد)، لا في الخاص بالـ profile الافتراضي مطلقًا. وتنتقل endpoints المخصصة مع مفاتيحها — OPENAI_BASE_URL, XAI_BASE_URL, NOUS_INFERENCE_BASE_URL, GATEWAY_PROXY_URL، وروابط Firecrawl / Browserbase / RetainDB / Supermemory / Honcho / Hindsight — بحيث لا يُرسَل مفتاح profile أبدًا إلى proxy أو خادم مستضاف ذاتيًا خاص بـ profile آخر. تكون WEIXIN_HOME_CHANNEL, HERMES_LANGUAGE، وdisplay.language، و hooks.outbound[].secret_env كذلك لكل profile ، ويعمل استخلاص الذاكرة عند نهاية الجلسة لجلسة ثانوية أُخليت (evicted) ضمن نطاق ذلك الـ profile.

      تتبع إعدادات وقت التشغيل لكل دور الـ profile الموجَّه إليه أيضًا: agent.max_turns, fallback_providers, file_read_max_chars, tool_output.*, browser.*، وtimezone (بما في ذلك TZ المُسلَّم لـ sandboxes الخاصة بـ execute_code sandboxes)، وسياسة تسليم الوسائط (gateway.strict, media_delivery_allow_dirs, trust_recent_files*)، وملف Nous auth.json المستخدَم للنداءات المساعِدة — كلها تُقرأ من الـ profile الذي يخدم الدور، وليس أبدًا من الـ profile الذي أُطلقت تحته الـ gateway. الأمر نفسه ينطبق على ملفات حالة كل profile (processes.json, checkpoints/، ومخازن لقطة sandbox ، وقواعد تعليقات/اقتران Feishu) وعلى hooks الـ gateway: يُحمَّل دليل hooks/ لكل profile على حدة، ويُفعّل فقط لأحداث ذلك الـ profile. وتعمل shell hooks مع HERMES_HOME الخاص بالـ profile الموجَّه إليه، دون أسرار الـ profile الافتراضي في بيئتها، وتحمل حمولة stdin الخاصة بها حقل profile يسمّي الـ profile الذي أطلقها.

      ما الذي يُعزَل لكل profile​

      مرجع سريع لما يحلّه دور مُضاعَف (multiplexed turn) من profile الخاص به ولا يشاركه أبدًا مع الافتراضي أو أي شقيق له:

      الشأنيُحَلّ منالسلوك عندما يفتقر الـ profile إليه
      مفاتيح المزوّد، ورموز البوت، ومراجع ${VAR} في config.yamlملف .env الخاص بالـ profile نفسه (نطاق أسراره)غير محلول / لا محوّل — لا قيمة الـ profile الافتراضي أبدًا
      التفويض (GATEWAY_ALLOW_ALL_USERS، GATEWAY_ALLOWED_USERS، قوائم السماح لكل منصة وخيارات السماح للجميع)ملف .env وconfig.yaml الخاصان بالـ profile المالكمغلق — لا يفتح انضمام الـ profile الافتراضي أبدًا بوت profile ثانوي
      تقييد slash commands (allow_admin_from, user_allowed_commands, group_allow_admin_from؛ راجع Slash Commands)الـ profile الذي تلقّى بوته الرسالة — تحكم كتلة extra الخاصة بالمنصة في الـ profile الثانوي بوتاته، لا كتلة الـ profile الافتراضيالمنع عند تعذّر التحقق: يُقيّد الـ profile المقدَّم الذي لم يحمّل مُعدّد الإرسال إعداداته بقائمة مسؤولين فارغة ودون أوامر فعّلها المستخدم، فلا تعمل إلا الأوامر المسموح بها دائمًا (/help, /whoami) — لا سياسة الإتاحة المفتوحة للـ profile الافتراضي
      HTTP endpoints (/p/<profile>/api/...، /p/<profile>/webhooks/...، نداءات أحداث المنصة)ملف API_SERVER_KEY الخاص بالـ profile المسمّى، ومسارات webhook المرتبطة بـ profile:، ومحوّله الخاص401/404؛ والتسليم من دون محوّل يكون 502/503، وليس أبدًا بوت profile آخر
      منصات المنفذ الوارد (/p/<profile>/webhooks/twilio، /p/<profile>/line/webhook، /p/<profile>/api/messages، …)محوّل الـ profile المسمّى الخاص وسره (رمز مصادقة Twilio، وسر قناة LINE، وتطبيق Teams، وكلمة مرور BlueBubbles، ...)؛ وتخرج الردود عبر ذلك المحوّل401/403 عند سر خاطئ، و404 عندما لا يملك الـ profile محوّلًا كهذا — وليس أبدًا محوّل الـ profile الافتراضي
      إعدادات المحوّل (*_REQUIRE_MENTION، *_REACTIONS, *_ALLOW_BOTS, *_PROXY, Discord allow_mentions, Matrix allowed_users / ignore_user_patterns، ومضيف webhook ومنفذه وعنوان URL الخاص به، وسياسة threads والجلسات و E2EE في Matrix، وحدود استدراك الرسائل والمرفقات في Discord، ووضع الرد في Buzz، وبطاقة وكيل A2A / عنوان URL العام، وسياسة جسر WhatsApp، وقناة Yuanbao الرئيسية)الـ profile المالك، بهذا الترتيب: .env صريحة → ملفه config.yaml → القيمة الافتراضية للمهايئالقيمة الافتراضية الموثّقة للمهايئ — لا إعداد الـ profile الافتراضي أبدًا. تحتفظ التثبيتات ذات profile واحد بأولوية البيئة على YAML تمامًا كما توثّق صفحة كل منصة

      الإعدادات التي تغيّرها من جلسة Desktop / TUI (/busy, /verbose, /approval, /cwd، والسمات وخيارات العرض)ملف config.yaml الخاص بالـ profile المالك للجلسة، حتى عندما يحمل RPC معرّف الجلسة فقطتُكتب إعدادات profile الجلسة نفسه؛ ولا يُمسّ ملف config.yaml الخاص بـ profile التشغيل ولا قيمة TERMINAL_CWD الخاصة به أبدًا
      اتصالات MCP في backend الخاص بـ Desktop/لوحة التحكم ومؤقّت cron لكل profileتُفهرس بحسب كل profile مقدَّم حتى عندما يكون gateway.multiplex_profiles معطّلًا — وهي قاعدة مُعدّد الإرسال نفسهايُعدّ الإدخال في mcp_servers الذي يحمل الاسم نفسه وبيانات اعتماد مختلفة اتصالًا مستقلًا؛ ولا يستدعي profile مقدَّم خادمًا بهوية profile آخر
      إجراءات لوحة التحكم (hermes -p <name> … التي يولّدها Desktop/لوحة التحكم)بيئة عملية فرعية مُنقَّاة مثبَّتة على HERMES_HOME الخاص بذلك الـ profileتحمّل العملية الفرعية ملف .env الخاص بها؛ ولا ترث tokens ومنافذ profile لوحة التحكم
      كل عملية فرعية تعمل لصالح profile مقدَّم (عامل slash commands، وتسليم Bot Chat، وتمرير A2A، ومساعد key_cmd، وبرنامج تشغيل المتصفح)ملف .env الخاص بذلك الـ profile + مصادر الأسرار فوق أساس منقّح من بيانات الاعتماد — سواء استُخدم gateway.multiplex_profiles أم لا (ويشمل ذلك مسار ?profile= في Desktop/لوحة التحكم)لا توجد في العملية الفرعية — فالمفتاح الذي وصل إلى عملية التشغيل فقط عبر systemd / Compose / الـ shell لا ترثه أبدًا عملية فرعية لـ profile آخر
      قيود التفويض في عملية فرعية أُنشئت لصالح profile آخر (*_ALLOWED_USERS / *_ALLOWED_CHANNELS / *_IGNORED_CHANNELS / *_ALLOW_ALL_USERS / *_ALLOW_BOTS, GATEWAY_ALLOW*) — إجراءات لوحة التحكم عبر hermes -p <name>، وعمال Kanban، وتسليم Bot Chat، وأمر gateway restartملفا .env / config.yaml الخاصان بالعملية الفرعية، وتحمّلهما العملية بنفسهامغلق (القيمة الافتراضية الموثّقة للمهايئ) — يُحذف القيد الذي صدّره ملف الوحدة أو الـ shell إلى العملية المنشئة قبل بدء العملية الفرعية، فلا يطبّق profile B قائمة قنوات أو مستخدمي profile A أبدًا؛ أما العملية الفرعية التابعة للـ profile نفسه فتحتفظ به
      اكتشاف الـ profile المُوجَّه في مضيف تضمين يعكس الـ profile المقدَّم في متغير البيئة الحي HERMES_HOME لدعم القرّاء القدامى (Hermes WebUI)مجلد التشغيل الذي ثبّته المضيف باستخدام hermes_constants.pin_process_hermes_home()؛ تُقارَن به مفاتيح اتصالات MCP، وتجريد بيئة التشغيل للعمليات الفرعية للـ profile المقدَّم، وقيمة allow-all الأولية المنقولة عبر الجسر، وحارس جسر البيئة الخاص بـ terminal.* جميعًادون تثبيت، يكون متغير البيئة الحي هو مجلد التشغيل، كما كان سابقًا تمامًا — ولا يحتاج المضيف الذي لا يغيّر HERMES_HOME إلى شيء
      بيانات اعتماد profile التشغيل (الافتراضي) نفسه داخل عملية hermes serve / لوحة تحكم تقدّم profile آخر أيضًاملف .env الخاص به + مصادر الأسرار فوق بيئة العملية، وهي مجمّدة منذ اللحظة التي يُقدَّم فيها أول profile آخر؛ ولا تُقرأ مجددًا بعد ذلكلا تُلتقط بيانات الاعتماد التي تغيّرت في بيئة العملية فقط (systemctl set-environment، أو wrapper مجدَّد لـ op run لم يُعِد تنفيذ العملية) حتى تُعاد العملية — ضع المفاتيح المتغيرة في .env أو مصدر أسرار، أو أعد التشغيل بعد تغييرها
      ضبط cron.env (HERMES_CRON_TIMEOUT، HERMES_MODEL كقيمة احتياطية، HERMES_CRON_MAX_PARALLEL، وملف prefill)، وبيئة العملية الفرعية للعامل / Bot Chatملف .env الخاص بالـ profile نفسه؛ ولا يرث الأبناء أبدًا إعدادات .env الخاصة بالـ profile الافتراضي أو سياسة TERMINAL_* المُجسَّرةافتراضيات cron / رفض النموذج، تمامًا كما في hermes -p <name> gateway run مستقلة
      عمّال Kanban والإشعارات لمهام profileملف .env + config.yaml الخاصان بالمكلَّف (تثبيت toolset، وbackend الطرفية، وسياسة الوسائط، ولغة العرض)—
      نبضات (ticks) /loop، وبوابة background_process_notifications، وnotice_delivery، واستعادة نقاط تحقق العملية الخلفيةملف state.db / config.yaml / processes.json الخاصة بالـ profile المالك—

      ما هو مشترك بالتصميم: العملية، وقفلها/PID الخاص بها وgateway_state.json (المنزل الافتراضي)، ومستمِع HTTP الواحد، وجدول profile_routes (المُعلَن على الـ profile الافتراضي).

      أي الـ profiles تُخدَم​

      يخدم gateway.multiplex_profiles: true الـ profile الافتراضي إضافة إلى كل profile مسمّى حيّ تحت profiles/، باستثناء تلك التي استُبعدت باستخدام gateway.standalone: true في ملف config.yaml الخاص بها — إذ يشغّل الـ profile المستقل gateway خاصًا به ولا يدرجه المضيف (راجع لا gateways جديدة لكل profile). (الخيار السابق gateway.multiplex_profile_allowlist السابق أُلغي؛ يزيله ترحيل الإعدادات من config.yaml، ويُؤرشف أو يُحذف بدلًا من ذلك الـ profile الذي لا تريد تقديمه ولم يستبعد نفسه — hermes profile delete <name>، أو انقل الدليل خارج profiles/.) تترك الـ profiles المحذوفة شاهدًا (tombstone) ولا تُعدَّد أبدًا؛ ولا يُعاد إنشاء profile اختفى دليله أبدًا من قِبل دور مخدوم، أو مؤقّت cron، أو توجيه السجلات.

      تتحكم المجموعة المخدومة في بادئات /p/<profile>/ الخاصة بـ API و webhook، وحالة بيئة التشغيل، وأهلية توجيه الـ profile، والـ profiles التي يشغّل لها مجدول cron داخل العملية دوراته (يعيد مؤقّت backend الخاص بـ Desktop تعداد المجموعة نفسها في كل دورة — وينضم profile أُنشئ أثناء عمل Desktop إلى مجموعة الدورات أو يغادرها إذا حُذف دون إعادة تشغيل — ويتنحّى لأي profile يقدّمه بالفعل مُعدّد إرسال جارٍ أو gateway خاص به). مُعدّد إرسال بدأ باستخدام hermes -p <name> gateway run يجري دائمًا مخزن cron الخاص بـ profile نفسه أيضًا.

      المجموعة المخدومة حيّة. يُخدَم profile أُنشئ أثناء تشغيل المضاعِف (hermes profile create، أو لوحة التحكم، أو Desktop، أو TUI) فورًا: يُرسل المنشئ إشارة إلى المضاعِف عبر مقبس التحكم (control socket) الخاص به، كما يعيد المضاعِف فحص profiles/ كل 30 ثانية كإجراء أمان إضافي. تُبنى مهايئات الـ profile الجديد بمجرد أن يتضمن config.yaml/.env token لبوت (عادةً ينشئ المستخدم الـ profile أولًا ثم يضيف الـ token)، وتُحدَّث served_profiles في ملف gateway_state.json الخاص بالـ profile الافتراضي، ويبلّغ hermes -p <name> gateway status أنه مقدَّم — دون إعادة تشغيل، ودون المساس بمهايئات الـ profiles الأخرى أو أدوارها الجارية. ويؤدي حذف profile إلى إيقاف مهايئاته وإزالة توجيهها بالطريقة نفسها، ويزيل hermes profile rename توجيه الاسم القديم قبل نقل المجلد ويقدّم الاسم الجديد أثناء التشغيل (ولا تعيد المهايئات أو مؤقّت cron اللذان كانا مرتبطين بالاسم القديم إحياءه). وتظل قاعدة بيانات اعتماد واحدة لكل مستقصٍ سارية: يُعلَّق الـ profile المضاف أثناء التشغيل الذي يعيد استخدام token لـ profile آخر مع duplicate_credential كخطأ، ولا يُشغَّل أبدًا كمستقصٍ ثانٍ.

      يوسّع الخدمة الساخنة (hot-serving) أيضًا حجز profile الخاص بالمُضاعِف (multiplexer): إذ يُؤخذ gateway.lock الخاص بالـ profile الجديد وتُبنى سلطة الجلسات الخاصة به، فيجد hermes -p <name> المُضاعِف بوصفه مالكه (دون daemon منفصل شارد لكل profile)، ويحجز hermes gateway restart التالي المجموعة كلها بسلاسة. أما الـ profile الذي يتعذّر فتح state.db الخاص به فيُوضع في الركن (parked) — يُسجَّل باسم Profile '<name>' not served ويُستبعد من served_profiles — وتستمر بقية الـ profiles في الإقلاع؛ أصلح المخزن ثم أعد تشغيل hermes profile create أو انتظر الفحص الدوري.

      توجيه محادثات البوت المشتركة إلى الـ profiles (profile_routes)​

      يختار الـ multiplexing profile لكل بيانات اعتماد (رمز البوت الخاص بكل profile) أو لكل بادئة رابط (URL prefix) (/p/<profile>/ لمنصات HTTP). عندما تشترك عدة مجتمعات في token واحد للبوت — مثل بوت Discord واحد يخدم guilds متعددة — يمكنك أيضًا توجيه مستخدمين/guilds/قنوات/threads محدَّدة إلى profiles مختلفة باستخدام gateway.profile_routes:

      gateway:
        multiplex_profiles: true
        profile_routes:
          # An entire Discord server → one profile
          - name: acme-server
            platform: discord
            guild_id: "1234567890"
            profile: acme

          # One channel in that server → a different profile
          - name: acme-support
            platform: discord
            guild_id: "1234567890"
            chat_id: "9876543210"
            profile: acme-support

          # A Telegram group (no guild concept — chat_id only)
          - name: tg-group
            platform: telegram
            chat_id: "-1001234567890"
            profile: tg-profile

          # A WhatsApp DM — write the phone number; JID and LID forms also match
          - name: owner-whatsapp
            platform: whatsapp
            chat_id: "15551234567"
            profile: owner

          # One Teams user across DMs, groups, and channels (exact sender id)
          - name: teams-owner
            platform: teams
            user_id: "00000000-0000-0000-0000-000000000000"
            profile: owner

      تُطابَق المسارات بحسب درجة تخصيص تراكمية: user_id = 16, thread_id = 8, chat_id = 4، و guild_id = 2. لذا يتقدّم user_id + chat_id (20) على user_id وحده (16)، وهذا يتقدّم على كل مسار يعتمد على الموقع فقط (14 كحد أقصى). يجب تحقق جميع الحقول المصرّح بها (AND)، وتحتفظ الدرجات المتساوية بترتيب التصريح، كما يطابق المسار المعتمد على قناة threads ومنشورات المنتديات التي تكون تلك القناة أصلها. تبقى الرسائل التي لا تطابق أي مسار في الـ profile الافتراضي/النشط. ويحصل الـ profile المُوجَّه على العزل الكامل لكل profile الموضّح أعلاه (الإعدادات والمهارات والذاكرة وبيانات الاعتماد ونطاق أسماء الجلسات). يعمل التوجيه على كل مهايئ منصة، وليس Discord فقط.

      user_id هو مرسِل الرسالة الواردة، وتُقارَن قيمته للتطابق التام. تعتمد موثوقيته على المهايئ الذي يبلّغ عنه، فلا تعتبره مدخل تفويض إلا في المنصات التي تصادق على المرسل عند الاستقبال. كما تُحدّد معرّفات المرسلين بنطاق المستأجر في بعض المنصات — فمعرّف مستخدم Slack محلي لمساحة العمل — لذا عند تقديم gateway لأكثر من مساحة عمل أو خادم، اقرن user_id بقيمة guild_id الخاصة بذلك النطاق (Discord guild أو مساحة عمل Slack أو خادم Matrix) بدلًا من الاعتماد على المعرّف وحده.

      يؤدي حذف user_id إلى إبقاء المسار غير مقيّد بالمرسل للتوافق مع الإصدارات السابقة. أما ضبطه على null أو سلسلة فارغة أو مسافات بيضاء فيُبطل المسار بدلًا من توسيعه ليشمل كل مرسل على المنصة.

      يختار التوجيه بحسب المرسل profile؛ ولا يشكّل تفويضًا قائمًا على المنع الافتراضي. ينتقل المرسل الذي لا يطابق أي مسار إلى الـ profile الافتراضي/النشط، تمامًا كالقناة غير الموجَّهة. لمنح شخص واحد profile مميّزًا وجميع الآخرين profile مقيّدًا، صرّح أولًا بمسار المرسل المميّز، ثم أضف بعده مسارًا شاملًا على مستوى المنصة إلى الـ profile المقيّد، وأبقِ قائمة السماح الخاصة باستقبال المنصة قائمة.

      لا ينطبق المسار إلا على الرسائل التي يستقبلها بوت الـ profile الافتراضي ما لم يسمِّ بوتًا آخر بـ bot_profile: <profile>. تستخدم الرسائل المباشرة في Telegram قيمة chat_id نفسه لكل بوت (معرّف المستخدم)، لذا من دون هذا فإن مسار chat_id مقصودًا للبوت المشترك سيلتقط أيضًا رسائل ذلك المستخدم المباشرة مع بوت مخصص تابع لـ profile ثانوي. تبقى الرسائل الواصلة إلى بوت خاص بـ profile ثانوي داخل ذلك الـ profile:

          # Pin one user's DM with team_b's OWN bot to a third profile
          - name: teamb-owner-dm
            platform: telegram
            bot_profile: team_b
            chat_id: "72719239"
            profile: ops-for-team-b

      يُحسَم التفويض لرسالة موجَّهة دائمًا بواسطة profile البوت المستقبِل (رمزه وقائمة سماحه)، بما في ذلك المتابَعات المرسَلة أثناء انشغال الوكيل والفحوص أثناء الدور مثل /topic أو /stop؛ ولا يحتاج الـ profile الموجَّه إليه نفسه أي نسخة من قائمة السماح. يتلقى profile موجَّه إليه لا يملك بوتًا خاصًا به أيضًا الإشعارات الخلفية (اكتمالات العمليات، والنبضات، ونتائج التفويض غير المتزامن) عبر البوت المشترك بعد إعادة تشغيل الـ gateway.

      على WhatsApp و WhatsApp Cloud، يطابق مسار chat_id عبر أشكال هوية المستخدم المختلفة: رقم هاتف مجرد (15551234567)، و JID (15551234567@s.whatsapp.net)، و LID (…@lid) — كلها تشير إلى الشخص نفسه بمجرد أن يقرنها الجسر (bridge) (نفس التحويل القانوني (canonicalization) الذي تستخدمه مفاتيح جلسات المطابقة وقوائم سماح المحوّل بالفعل). يمكنك وضع رقم الهاتف في profile_routes وستظل الرسائل المباشرة الواردة تطابق سواء سلّم WhatsApp JID أو LID. من دون ربط LID بعد، يظل شكل الرقم يطابق JID (تُحذَف اللاحقة) لكنه لا يستطيع حل LID مجهول — يسقط ذلك الوارد عندئذٍ إلى الـ profile الافتراضي إلى أن يظهر الربط. محادثات المجموعات (…@g.us) ليست هويات مرسِل وتظل تطابق تمامًا. تبقى معرّفات Telegram الرقمية دون تغيير.

      يتطلب profile_routes وجود gateway.multiplex_profiles: true؛ ومع إيقاف الـ multiplexing تُتجاهَل المسارات. إذا طابق مسار صريح لكنه يستهدف profile غير مثبَّت (أو محذوف)، ترفض الـ gateway ذلك الوارد وتسجّل المسار والهدف. ولا تُشغِّل الـ profile الافتراضي. أما الحركة التي لا تطابق أي مسار فتحافظ على السلوك الافتراضي التاريخي للـ profile.

      تُسلَّم مهام cron التي يملكها profile موجَّه إليه عبر البوت المشترك أيضًا، لكن فقط للأهداف التي يربطها مسار مفعَّل بـ chat_id/thread_id بذلك الـ profile (يؤهِّل مسار guild_id + chat_id قناته) — لا تُرسَل أبدًا مهمة لـ profile موجَّه إليه تستهدف محادثة غير موجَّهة (أو محادثة موجَّهة إلى profile آخر) عبر البوت المشترك. لا تؤهِّل المسارات المقتصرة على guild فقط هدف cron؛ أضف مسار chat_id لقناة التسليم. ولا تتأهل أيضًا المسارات التي تصرّح بـ user_id: لا يوجد لدى cron مرسِل وارد مُصادَق عليه، لذا تحتاج إلى مسار منفصل يعتمد على الموقع فقط. ولا يحتاج الـ profile المُوجَّه إلى platforms.<platform> الخاص به لهذا: يأتي تفويض البوت المشترك من المسار، لا من إعدادات القمر الصناعي (satellite).

      تشغيل أو إيقاف أو إعادة تشغيل كل الـ gateways دفعة واحدة​

      تأتي CLI مزوّدة بأوامر دورة حياة لـ profile واحد. للتصرف عبر كل profile، لُفّها في حلقة shell. ضع المقطع أدناه في ~/.local/bin/hermes-gateways ونفّذ عليه chmod +x عليه: 

      #!/bin/sh
      set -eu

      # Add or remove profile names here as you create / delete profiles.
      profiles="default coder personal-bot research"

      usage() {
        echo "Usage: hermes-gateways {start|stop|restart|status|list}"
      }

      run_for_profile() {
        profile="$1"
        action="$2"
        if [ "$profile" = "default" ]; then
          hermes gateway "$action"
        else
          hermes -p "$profile" gateway "$action"
        fi
      }

      action="${1:-}"
      case "$action" in
        start|stop|restart|status)
          for profile in $profiles; do
            echo "==> $action $profile"
            run_for_profile "$profile" "$action"
          done
          ;;
        list)
          hermes gateway list
          ;;
        *)
          usage
          exit 2
          ;;
      esac

      ثم:

      hermes-gateways start      # start every configured profile
      hermes-gateways stop       # stop every configured profile
      hermes-gateways restart    # restart all
      hermes-gateways status     # status across all
      hermes-gateways list       # delegates to `hermes gateway list`
      نصيحة

      يُستهدَف الـ profile default بـ hermes gateway <action> (بلا -p)، لا بـ hermes -p default gateway <action>. يتعامل الـ wrapper أعلاه مع كلا الشكلين.

      coder gateway run        # foreground (Ctrl-C to stop)

      coder gateway stop       # stop the managed service
      coder gateway restart    # restart
      coder gateway status     # status
      coder gateway install    # create the LaunchAgent / systemd unit
      coder gateway uninstall  # remove the service file

      هذه معادِلة لـ hermes -p coder gateway <action> — مفيدة إذا لم يكن اسم مستعار لـ profile موجودًا في PATH أو إذا كنت تستهدف الـ profiles ديناميكيًا من سكربت.

      ملفات الخدمة​

      coder gateway restart

      إبقاء الجهاز المضيف مستيقظًا​

      يمكن لعملية الـ gateway أن تعمل طوال اليوم، لكن نظام التشغيل سيحاول مع ذلك النوم عند عدم النشاط. نمطان:

      macOS — caffeinate​

      caffeinate مدمجة في macOS وتمنع النوم أثناء عملها. لا حاجة إلى تثبيت.

      caffeinate -dis                    # block display, idle, and system sleep
      caffeinate -dis -t 28800           # same, auto-exit after 8 hours
      caffeinate -i -w $(cat ~/.hermes/gateway.pid) &   # awake while default gateway runs

      # Persistent: run in background and forget
      nohup caffeinate -dis >/dev/null 2>&1 &
      disown

      # Inspect / stop
      pmset -g assertions | grep -iE 'caffeinate|prevent|user is active'
      pkill caffeinate
      الخيارالأثر
      -dحظر نوم الشاشة
      -iحظر نوم النظام عند الخمول (الافتراضي)
      -mحظر نوم القرص
      -sحظر نوم النظام (لأجهزة Mac الموصولة بالتيار الكهربائي فقط)
      -uمحاكاة نشاط المستخدم (يمنع قفل الشاشة)
      -t Nالخروج تلقائيًا بعد N ثانية
      -w Pالخروج عند خروج PID P في حالة الخروج
      إغلاق الغطاء ما زال يُنيم الـ Mac

      لا تستطيع caffeinate تجاوز نوم إغلاق الغطاء المدفوع بالعتاد على أجهزة MacBook. للتشغيل والغطاء مغلق، غيّر تفضيلات موفِّر الطاقة/البطارية أو استخدم أداة من طرف ثالث.

      Linux — systemd-inhibit أو loginctl​

      # Inhibit suspend while a command runs
      systemd-inhibit --what=idle:sleep --who=hermes --why="gateways running" \
        sleep infinity &

      # Allow user services to keep running after logout (recommended)
      sudo loginctl enable-linger "$USER"

      بعد تفعيل lingering، تستمر وحدات مستخدم systemd لديك (بما في ذلك hermes-gateway-<profile>.service) في العمل عبر انقطاعات SSH وإعادة التشغيل.

      أمان تعارض الـ tokens​

      يجب أن يستخدم كل profile رموز بوت فريدة لكل منصة. إذا شارك profileان رمز Telegram أو Discord أو Slack أو WhatsApp أو Signal، ترفض الـ gateway الثانية البدء برسالة خطأ تسمّي الـ profile المتعارض. تحت الـ multiplexing تُوقِف نفس القاعدة محوّل الـ profile المكرَّر فقط بينما تستمر الـ gateway المشتركة في العمل.

      للتدقيق:

      grep -H 'TELEGRAM_BOT_TOKEN\|DISCORD_BOT_TOKEN' \
           ~/.hermes/.env ~/.hermes/profiles/*/.env

      الترحيل من gateways لكل profile​

      إذا كانت الـ profiles لديك يشغّل كل منها gateway مستقلة حاليًا (وحدة systemd أو LaunchAgent لكل profile، من إصدار سابق لاعتماد multiplex وحده)، فإن الفحص المسبق عند إقلاع gateway الافتراضية يُبقيها مستقلة حتى تُدمَج البقية (لا تؤدي القيمة الافتراضية غير المضبوطة أبدًا إلى ربط مجموعة gateways عاملة بالمنافذ مرتين). يدمجها hermes update نيابةً عنك ما لم يمنع ذلك حد فعلي (أدناه)؛ ويُنفَّذ الدمج نفسه بأمر واحد، كما أن إعادة تشغيله على جهاز انتقل جزئيًا (خيار مفعّل أو وحدة متبقية أو تعطّل بين الخطوتين) تكمل العمل بدل الإبلاغ عن "already multiplexed":

      hermes gateway migrate --multiplex --dry-run   # print the plan and any blockers; changes nothing
      hermes gateway migrate --multiplex             # apply (asks for confirmation on a TTY; -y skips)

      لا يوجد أمر عكسي باسم --standalone: فمجموعة gateways مستقلة لكل profile ليست وجهة مدعومة. تستمر المجموعة التي يعيقها حد في العمل كما هي، ويحتفظ كل profile بـ hermes -p <name> gateway install --force كمساره — أو يستبعد نفسه من gateway المضيف باستخدام gateway.standalone: true (راجع لا gateways جديدة لكل profile)، ويلتزم hermes gateway migrate --multiplex بذلك.

      Docker / Hermes Cloud (حاوية بإشراف s6)​

      داخل الصورة الرسمية، يملك كل profile خانة s6 (/run/service/gateway-<profile>). يسجّل إقلاع الحاوية كل خانة مسمّاة بوصفها متوقفة ويدمج نية التشغيل التلقائي فيها ضمن خانة الجذر، لذا يستخدم الإقلاع الجديد multiplex بالفعل. ولم يعد التحديث في المكان يحتاج إلى إعادة تشغيل الحاوية للوصول إلى الحالة المطلوبة أيضًا: يوقف hermes gateway migrate --multiplex (وكذلك الـ hook الذي يشغّله hermes update) كل خانة مسمّاة ما زالت تعمل (s6-svc -d إضافة إلى ملف down حتى لا تعيدها إعادة تشغيل supervisor)، ويدمج نيتها في خانة الجذر وفق القاعدة نفسها المستخدمة عند الإقلاع، ثم يعيد تشغيل خانة الجذر. لا تشكّل الخانة المسجّلة بوصفها متوقفة عائقًا أبدًا — بل الخانة التي تعمل فعليًا فقط. ما زال هناك أمر واحد لا يستطيع هذا الأمر تنفيذه من الداخل: إنشاء خانة جذر لم يسجّلها الإقلاع أصلًا؛ وتُعرِّف هذه الحالة نفسها وتطلب إعادة تشغيل الحاوية.

      ما الذي يفعله hermes update​

      بعد تحديث ناجح، عندما يحتوي التثبيت على profileين أو أكثر، ويشغّل profile ثانوي واحد على الأقل gateway خاصة به (عملية حيّة أو خدمة مثبَّتة) ويكون gateway.multiplex_profiles معطّلًا، يجري hermes update الفحص المسبق نفسه:

      • لا شيء يعيقه → يعمل الترحيل تلقائيًا (بمسار الكود نفسه المستخدم في hermes gateway migrate --multiplex --yes) ويطبع ما فعله. هذا حتمي (deterministic) ولا يسأل أبدًا، لذا يعمل أيضًا في التحديثات بلا شاشة (headless)/عبر cron.
      • شيء يعيقه → تسرد كتلة تحذير كل عائق مع إصلاحه الدقيق والأمر ذي السطر الواحد لتشغيله لاحقًا. لا يتغيّر شيء.

      لا تُرحَّل أبدًا التثبيتات ذات profile واحد (فلا فائدة من ذلك)، ويُترَك التثبيت الذي يستخدم الـ multiplexing بالفعل كما هو. لا يفعل hermes update أيضًا شيئًا عندما لا تشغّل أي profile ثانوية gateway خاصة بها — فهو لا يبدّل الأوضاع أبدًا على تثبيت لم يكن فيه شيء يعمل.

      حدود لا يتجاوزها hermes update تلقائيًا أبدًا​

      لا يدمج الـ hook غير الخاضع للإشراف إلا الـ profiles التي تشترك في مستخدم UNIX واحد ونطاق خدمات واحد وشجرة profiles/ واحدة — وهي البنية التي ينتجها hermes profile create. وجود profile ثانوي مستقل خلف أي من الحدود التالية يوقف المسار التلقائي:

      الحدمثال
      اختلاف مدير الخدمات أو النطاقالافتراضي على systemd للمستخدم، وثانوي على systemd للنظام (أو launchd)، أو الافتراضي منفصل مع ثانوي مُدار بخدمة
      وجود أكثر من وحدة مثبّتة للـ profileوحدة للمستخدم و وحدة للنظام للـ profile نفسه (يزيل الأمر الصريح كلتيهما)
      اختلاف مستخدم UNIXوحدة للنظام لها User= خاص بها، أو gateway حيّة يملكها uid آخر؛ تُعدّ الوحدة النظامية التي لا يستطيع هذا الجهاز تحديد User= فيها — سواء في الثانوي أو في الافتراضي — مجهولة الهوية، ولا تُعدّ أبدًا "المستخدم نفسه"
      HERMES_HOME خارج <default home>/profiles/وحدة تثبّت HERMES_HOME=/opt/hermes/profiles/emma

      في هذه الحالة، يطبع hermes update الحد الذي وجده مع hermes gateway migrate --multiplex، ولا يغيّر شيئًا — لا تُزال أي وحدة وتستمر gateways الخاصة بكل profile في العمل (يظل --force مسارها عندما يمنع حد كهذه الحدود الدمج؛ أما profile الخالي منها فيستبعد نفسه باستخدام gateway.standalone: true). يستبدل دمج مثل هذه المجموعة حدًا تفرضه النواة (ملكية الملفات و User=) بعزل داخل العملية، وهو قرار المشغّل. ويظل الأمر الصريح ينفّذه: تظهر النتائج نفسها كتنبيهات ضمن hermes gateway migrate --multiplex --dry-run حتى تقرأها أولًا، ويتابع --multiplex عند تأكيدك.

      إلغاء الترحيل التلقائي​

      اضبط gateway.auto_multiplex_migration: false على الـ profile الافتراضي لمنع تشغيل الدمج التلقائي مطلقًا في هذا التثبيت:

      hermes config set gateway.auto_multiplex_migration false

      hermes update يترك عندئذ gateways الخاصة بكل profile كما هي تمامًا، دون مخرجات أو تغييرات، مهما بدا التثبيت مؤهلًا. يوجد الإعداد في ملف الإعدادات، لذا يبقى بعد التحديثات — يُتخذ القرار مرة واحدة بدل إعادة النظر فيه مع كل إصدار. يُقرأ من الإعدادات الفعلية كبقية الإعدادات، لذا تتقدّم القيمة المثبّتة ضمن النطاق المُدار (/etc/hermes/config.yaml) على ملف الـ profile نفسه. لا يتحكم إلا في المسار التلقائي: يُعدّ hermes gateway migrate --multiplex طلبًا صريحًا ويظل ينفّذ الترحيل (وهو الوسيلة المدعومة لتفعيله مجددًا). الإغفال أو قيمة true يُبقيان السلوك الافتراضي الموضّح أعلاه.

      ينطبق الإعداد نفسه على gateway أُقلع بالـ profile الافتراضي فقط. في الوضع الطبيعي، بمجرد إنشاء profile ثانٍ (عبر New Agent في Desktop أو hermes profile create)، يبدأ ذلك الـ gateway بخدمة كل الـ profiles في مكانه، دون إعادة تشغيل. أما مع auto_multiplex_migration: false فيستمر في خدمة الـ profile الخاص به فقط، ويُرفض الـ profile الجديد بهذا السبب إلى أن تنفّذ hermes gateway migrate --multiplex أو تعيد ضبط المفتاح إلى true. يُعاد قراءة المفتاح عند كل فحص للـ profiles، فيسري ضبطه من جديد خلال نحو 30 ثانية دون إعادة تشغيل.

      الأمر الصريح مختلف: يطبّق hermes gateway migrate --multiplex مع profileين أو أكثر ودون أي gateway ثانوية مستقلة الخطوة الأخيرة المتبقية — فهو يضبط gateway.multiplex_profiles: true ويشغّل gateway الافتراضية أو يعيد تشغيلها. لقد طلبت multiplex، فتحصل عليه.

      الاستنساخات لا تحمل القنوات

      hermes profile create --clone رموز بوت المصدر وقوائم سماحه خلف الركب (راجع Profiles → قنوات المراسلة لا تُستنسخ أبدًا)، بحيث لا تعود مجموعة من الاستنساخات تصطدم بعائق بيانات الاعتماد المكرَّرة أدناه. تُوسَم الاستنساخات القديمة التي ما زالت تحملها بواسطة hermes profile list.

      ما الذي يفعله الترحيل​

      1. يوقف الـ gateway المستقلة الخاصة بكل profile ثانوي ويلغي تثبيت خدمته (وحدة مستخدم/نظام systemd أو عميل launchd). يُسجَّل ما أُزيل في ~/.hermes/gateway_migration.json للتراجع.
      2. يضبط gateway.multiplex_profiles: true ضمن الـ profile الافتراضي في config.yaml الخاص به.
      3. يعيد تشغيل الـ gateway الافتراضية — أو يثبّتها ويشغّلها على مدير الخدمة نفسه الذي كانت تستخدمه الـ profiles الثانوية، بحيث يبقى الأسطول المُدار بـ systemd مُدارًا بـ systemd.
      4. ينتظر حتى تسجّل الـ gateway الافتراضية served_profiles التي تغطي كل profile، ثم يطبع ملخصًا.

      العوائق وإصلاحاتها​

      العائقالسببالإصلاح
      يعدّ profileان بيانات اعتماد المنصة نفسها (مثل TELEGRAM_BOT_TOKEN نفسه)تحت عملية واحدة، لا يمكن استطلاع رمز بوت إلا مرة واحدة؛ سيُوقِف المضاعِف المكرَّر جانبًا وسيصمت بوت ذلك الـ profileأزل الرمز من الـ profile الثاني، أو أبقه في default ووجّه محادثات ذلك الـ profile عبر profile_routes
      يفعّل profile ثانوي منصة ذات منفذ وارد لا يملك أي /p/<profile>/ على المستمِع الافتراضييتخطى المضاعِف ذلك الـ profile بأكمله (راجع القاعدة 2)عطّل المنصة في ذلك الـ profile (platforms.<name>.enabled: false)، أو شغّل profile مستقلًا: اضبط gateway.standalone: true في config.yaml الخاص به وانتظر إعادة الفحص من المضيف (30 ثانية كحد أقصى)، أو أرسل فعل التحكم rescan-profiles الخاص به. استخدم hermes -p <name> gateway install --force فقط حيث يمنع حد الدمج.

      يعيد فحص بيانات الاعتماد استخدام كشف تعارض الـ gateway نفسه، لذا يطابق حكمه ما تفعله الـ multiplexer عند البدء. تُقرأ المنصات ذات المنفذ الوارد التي تملك بوابة /p/<profile>/ من المحوّلات نفسها (يعلن كل منها serves_profile_prefix)، بحيث يظل الفحص المسبق صحيحًا مع اكتساب محوّلات HTTP-الوارد الجديدة البادئة.

      ما الذي يتغيّر بالنسبة إلى profiles المنفذ الوارد​

      الـ profile الثانوي الذي استخدم api_server أو webhook على منفذه الخاص لا يُحظَر — لكن رابطه يتغيّر. يطبع الفحص المسبق الرابط الجديد الدقيق، مثلًا:

      Profile 'coder': api_server moves onto the default listener at
      http://127.0.0.1:8642/p/coder/v1/... (its key/secret is unchanged; update
      clients that call the old per-profile port).

      يستمر API_SERVER_KEY أو سر webhook الخاص بالـ profile في مصادقة الرابط ذي البادئة؛ ولا يتغيّر شيء آخر بشأن المفتاح.

      الـ profiles المُنشأة بعد الترحيل​

      يُخدَم profile أُنشئ أثناء تشغيل المضاعِف من دون إعادة تشغيل (راجع أعلاه). يؤكد hermes profile create ذلك عندما يتلقَّط المضاعِف الحيّ الـ profile؛ ولا يطبع تذكير hermes gateway restart إلا عندما يتعذّر عليه الوصول إلى المضاعِف (على سبيل المثال، gateway بُدئت من إصدار قديم).

      معالجة الفشل والاستئناف​

      الترحيل معاملة ذرّية. تُرفض حالات الفشل التي يمكن توقّعها من الخطة (وحدة للنظام يجب أن تعمل بهوية root دون قيمة User= مسجّلة، أو ملف إعدادات يتعذّر إعادة كتابته) قبل إيقاف أي gateway خاصة بـ profile. أي فشل بعد كتابة manifest — كتابة الخيار أو إيقاف profile ثانوي لاحق أو إزالة وحدته أو تثبيت الافتراضي أو تشغيله — يؤدي فورًا إلى التراجع عبر manifest، بحيث لا يُترَك أي profile دون gateway. إذا توقفت العملية في أي موضع خلال تلك الفترة، يجد الاستدعاء التالي لـ hermes gateway migrate --multiplex أن الخيار مفعّل وأن manifest موجود وأنه لا يوجد multiplexer حي يخدم الـ profiles المرحّلة (لا تُحتسَب الوحدة الافتراضية المثبّتة لكنها متوقفة)، ويستأنف من manifest بدل الإبلاغ عن "already multiplexed". وجود manifest على القرص يعني دائمًا عدم الاكتمال: فهو سجل استئناف، لا أمر تراجع — لا يوجد عكس باسم --standalone، ولا تعمل آلية التعويض أعلاه إلا داخل تطبيق واحد فاشل حتى لا يُترك أي profile دون gateway.

      لا تُغطّى تلقائيًا الحاويات التي يشرف عليها s6 — فهي تصل إلى الحالة المطلوبة عند بدء الحاوية التالي (تُسجَّل خانات كل profile بوصفها متوقفة وتستخدم gateway الجذر multiplex؛ أما profile ذو gateway.standalone: true فيُقلع خانته الخاصة بناءً على نية تشغيله الخاصة). يدمج الأمر Windows Scheduled Tasks. تعرض صفحة System في لوحة التحكم الترحيل نفسه كزر عندما يجد الفحص المسبق تثبيتًا مؤهّلًا.

      تحديث الكود​

      hermes update أحدث كود مرة واحدة ويزامن المهارات المضمّنة الجديدة مع كل profile:

      hermes update
      hermes-gateways restart

      يعيد التحديث نفسه تشغيل الـ gateways العاملة؛ وفي تثبيت ما زال يشغّل gateway واحدة لكل profile، يعرض التحديث بعدها الترحيل إلى gateway واحدة مضاعَفة — تلقائيًا عندما لا يعيقه شيء، وإلا فكتحذير يسمّي الحد (مستخدم UNIX مختلف، أو HERMES_HOME خارج profiles/) والأمر ذي السطر الواحد الذي يمكنك تشغيله بنفسك.

      لا تُستبدَل أبدًا المهارات التي عدّلها المستخدم.

      استكشاف الأخطاء وإصلاحها​

      "Could not find service in domain for user gui: 501"​

      لقد شغّلت hermes gateway start بعد hermes gateway stop سابق. تجري stop الخاصة بـ CLI عملية launchctl unload كاملة، والتي تزيل الخدمة من سجل launchd. تلتقط CLI هذا الخطأ المحدَّد عند start و تعيد تحميل ملف plist تلقائيًا (↻ launchd job was unloaded; reloading service definition). تبدأ الخدمة بشكل طبيعي. لا شيء لإصلاحه.

      PID قديم بعد عطل (crash)​

      إذا أظهرت gateway الخاصة بـ profile not running بينما لا تزال عملية حيّة:

      ps -ef | grep "hermes_cli.*-p <profile>"
      cat ~/.hermes/profiles/<profile>/gateway.pid
      kill -TERM <pid>          # graceful
      kill -KILL <pid>          # if that fails after a few seconds
      <profile> gateway start

      فرض إعادة ضبط قسرية (hard reset) لخدمة واحدة​

      # macOS
      launchctl unload ~/Library/LaunchAgents/ai.hermes.gateway-<profile>.plist
      launchctl load   ~/Library/LaunchAgents/ai.hermes.gateway-<profile>.plist

      # Linux
      systemctl --user restart hermes-gateway-<profile>.service

      فحص السلامة (Health check)​

      hermes doctor                  # default profile
      hermes -p <profile> doctor     # one profile

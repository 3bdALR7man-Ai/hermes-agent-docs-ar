      تشغيل عدة Gateways في وقت واحد

      شغّل عدة profiles — لكل منها رموز البوت، والجلسات، والذاكرة الخاصة به — كخدمات مُدارة على جهاز واحد. تتناول هذه الصفحة الجوانب التشغيلية: تشغيلها كلها معًا، وعرض السجلات عبر الـ profiles، ومنع الجهاز المضيف من النوم، والتعافي من مشكلات launchd/systemd الشائعة.

      إذا كنت تشغّل وكيل Hermes واحدًا فقط، فلست بحاجة إلى هذه الصفحة — راجع Profiles للأساسيات. وإذا كانت نُسخك تعمل على أجهزة مختلفة ينبغي لتطبيق سطح مكتب واحد الوصول إليها في آن واحد، راجع ربط Desktop بعدة نُسخ من Hermes.

      متى تستخدم هذا​

      تحتاج إلى هذا الإعداد عندما يكون لديك وكيلا Hermes أو أكثر ينبغي أن يكونا متصلين في الوقت نفسه. من الأسباب الشائعة:

      • مساعد شخصي على بوت Telegram وواحد آخر وكيل برمجة على بوت آخر
      • وكيل واحد لكل فرد من العائلة أو وكيل واحد لكل مساحة عمل Slack
      • نُسخ Sandbox + إنتاج (production) من الإعدادات نفسها
      • وكيل بحث + وكيل كتابة + بوت مُشغَّل بواسطة cron — لكل منها ذاكرة ومهارات معزولة

      يحصل كل profile بالفعل على LaunchAgent خاص به لكل منصة (ai.hermes.gateway-<name>.plist) أو خدمة مستخدم systemd (hermes-gateway-<name>.service). يضيف هذا الدليل الأنماط اللازمة لإدارتها جميعًا معًا.

      البدء السريع​

      # Create profiles (once)
      hermes profile create coder
      hermes profile create personal-bot
      hermes profile create research

      # Configure each
      coder setup
      personal-bot setup
      research setup

      # Install each gateway as a managed service
      coder gateway install
      personal-bot gateway install
      research gateway install

      # Start them all
      coder gateway start
      personal-bot gateway start
      research gateway start

      هذا كل ما في الأمر — ثلاثة وكلاء مستقلين، كل منهم على عمليته الخاصة، تُعاد تشغيلها تلقائيًا عند العطل وعند تسجيل دخول المستخدم.

      البديل: gateway واحدة لكل الـ profiles (multiplexing)​

      يشغّل النموذج أعلاه عملية واحدة لكل profile. هذا هو الافتراضي وهو الخيار الصحيح لمعظم الإعدادات. لكن على جهاز مضيف يحتوي على عدة profiles — أو في نشر حاويات (container) حيث تكون عملية واحدة لكل profile عبئًا تشغيليًا — يمكنك بدلًا من ذلك تشغيل gateway واحدة مضاعِفة (multiplexing): تصبح gateway الـ profile الافتراضي العملية الواردة الوحيدة، وتخدم الرسائل لكل profile على الجهاز.

      هذا خيار اختياري (opt-in) ومعطّل افتراضيًا. عندما يكون معطّلًا، لا يتغيّر شيء في هذه الصفحة — كل سلوك أدناه خامل.

      متى تفضّل الـ multiplexing​

      • نشر على حاوية/VPS حيث تشكّل N وحدات إشراف (supervisor units)، وN منافذ، وN ملفات PID عبئًا.
      • عدد كبير من profiles منخفضة الحركة لا يبرر كل منها عملية كاملة.
      • تريد شيئًا واحدًا يُشغَّل ويُراقَب ويُعاد تشغيله.

      التزم بعملية واحدة لكل profile عندما تريد عزلًا صارمًا على مستوى العملية بين الـ profiles (بصمات ذاكرة منفصلة، ونطاقات عطل مستقلة، والقدرة على إعادة تشغيل profile واحد دون المساس بالباقي).

      كيفية التفعيل​

      اضبط الخيار على الـ profile الافتراضي (فهو من يملك المضاعِف (multiplexer)) وأعد تشغيل gateway الخاصة به:

      hermes config set gateway.multiplex_profiles true
      hermes gateway restart

      وبشكل معادل، في ~/.hermes/config.yaml الخاص بالـ profile الافتراضي:

      gateway:
        multiplex_profiles: true

      (يُقبَل الخيار أيضًا كحقل multiplex_profiles: true على المستوى الأعلى للراحة.) عند التشغيل التالي، تعدّد gateway الـ profile الافتراضي كل profile، وتُشغّل المنصات المفعّلة لكل profile ببيانات اعتماد ذلك الـ profile الخاصة، وتوجّه كل رسالة واردة إلى الـ profile الذي تخصّه. يحلّ كل دور (turn) إعدادات الـ profile الموجَّه إليه، ومهاراته، وذاكرته، وSOUL، ومفاتيح المزوّد — لا تُشارَك بيانات الاعتماد أبدًا بين الـ profiles.

      أنت لا تشغّل hermes gateway start للـ profiles الثانوية — فـ gateway الـ profile الافتراضي تخدمها. راجع تغييرات العقد أدناه.

      ما الذي يتغيّر عند تفعيل الـ multiplexing​

      يغيّر تفعيل الخيار سلوك بضعة أشياء. وتعود جميعها إلى طبيعتها فور إيقاف الخيار.

      1. يجب ألا تُشغّل الـ profiles الثانوية gateway الخاصة بها​

      مع تشغيل مضاعِف (multiplexer)، يصبح hermes gateway run أو start أو install أو restart على profile مسمّى خطأً فادحًا (hard error) (رمز الخروج 78)، يوجّهك إلى المضاعِف:

      The default gateway is running as a profile multiplexer and already serves
      profile 'coder'. ...

      يحدث الرفض في CLI قبل لمس أي مدير خدمات، بحيث لا ينتهي profile مخدوم أبدًا بوحدة systemd فاشلة بشكل دائم أو حلقة إعادة تشغيل launchd. يُرفض hermes -p coder gateway stop بالطريقة نفسها (الخروج 78) عندما لا يكون لـ coder gateway خاصة به — فليس هناك ما يُوقَف سوى المضاعِف، الذي يوقفه hermes gateway stop على الـ profile الافتراضي لكل profile مخدوم. تتبع لوحة التحكم وتطبيق Desktop سلوك CLI: بالنسبة إلى profile مخدوم، تجيب إجراءا "Start" و"Stop" الخاصان بـ gateway بالرمز 409 مع الشرح نفسه (يُعرض كإشعار مضمّن في صفحة System)، ويعيد "Restart" تشغيل المضاعِف (العملية التي تخدم فعليًا ذلك الـ profile) بدلًا من توليد -p coder gateway restart التي لا يمكن إلا أن تفشل. ولأن تلك الإعادة تعيد ربط كل بوت على الجهاز، يسأل كلا التطبيقين أولًا "إعادة تشغيل الـ gateway المشتركة؟ ستُعاد ربط كل البوتات على هذا الجهاز: default، وcoder، وresearch" (القائمة هي served_profiles الخاصة بـ gateway العاملة)، ويبلّغان "تمت إعادة تشغيل الـ gateway المشتركة (3 بوتات)" عند الاكتمال. أما الـ profile المستقل فيحافظ على إعادة التشغيل العادية. يحمل /api/status?profile=coder القائمة نفسها باسم gateway_shared_with (فارغة (null) لـ gateway مستقلة). تُقرأ حالة "مخدوم" من سجل gateway العاملة نفسها (served_profiles في gateway_state.json الخاص بالمنزل الافتراضي)، بحيث تبقى صحيحة عندما يكون المضاعِف قد فُعِّل فقط عبر GATEWAY_MULTIPLEX_PROFILES في بيئة الـ profile الافتراضي، أو عندما تُضاف profiles بعد بدء تشغيل الـ gateway.

      المضاعِف هو العملية الواردة الوحيدة؛ وإن وُجدت gateway ثانية لأي profile فستحاول ربط منصات ذلك الـ profile مرتين. مرّر --force (تقبله run وstart و install وrestart) فقط إذا كنت تريد فعلًا عملية منفصلة لذلك الـ profile (غير مستحسن أثناء تشغيل المضاعِف). لذلك لا تُستخدَم سكربت الـ wrapper المتعدّد الـ profiles الوارد سابقًا في هذه الصفحة في وضع الـ multiplex — فأنت تدير gateway الافتراضي فقط.

      2. تُستقبل منصات HTTP الواردة عبر بادئة URL على شكل /p/<profile>/​

      تصل حركة HTTP الواردة لـ profile ثانوي عبر مستمِع واحد للـ profile الافتراضي تحت بادئة profile، وليس منفذًا ثانيًا:

      # default profile
      POST http://host:8644/webhooks/<route>
      # the "coder" profile, same listener
      POST http://host:8644/p/coder/webhooks/<route>

      يعيد profile غير معروف أو غير مُعَدّ في البادئة الرمز 404. المستمِع المشترك هو منفذ api_server الخاص بالـ profile الافتراضي (أو منفذ webhook الخاص به عندما لا يكون خادم API مفعّلًا)؛ يخدم ثلاثة أنواع من المسارات ذات بادئة profile:

      • يُرآى api_server وwebhook، ولا يُكرَّران. يجيب على /p/coder/v1/... و/p/coder/webhooks/<route> محوّل الـ profile الافتراضي نفسه ضمن نطاق coder. لذا يجب على الثانوي ألا يفعّل api_server أو webhook بنفسه (ترفض لوحة التحكم بالرمز 409؛ فوجود API_SERVER_KEY أو WEBHOOK_ENABLED في .env الخاص بالثانوي يربط بيانات الاعتماد فقط دون تشغيل مستمِع).
      • تعمل كل منصة أخرى ذات منفذ وارد في وضع المستمِع المشترك. يحصل الثانوي الذي يعدّ Twilio SMS أو LINE أو Teams أو BlueBubbles أو Microsoft Graph أو WhatsApp Cloud أو WeCom callback أو وضع webhook لـ Feishu على محوّل خاص به يُبنى من دون منفذ؛ يمرّر المستمِع الافتراضي /p/<profile>/<the adapter's usual path> إليه. راجع منصات المنفذ الوارد تحت المضاعِف.

      تتبع المصادقة الـ profile المسمّى في الرابط. تستمر النقاط النهائية (endpoints) غير المسبوقة ببادئة في استخدام بيانات اعتماد المستمِع الافتراضي القائمة.

      • يجب أن تستخدم طلبات API-server عند /p/coder/... API_SERVER_KEY من ~/.hermes/profiles/coder/.env؛ ويُرفَض مفتاح المستمِع الافتراضي. تحت المضاعِف، لا يؤدي هذا المفتاح إلا إلى مصادقة البادئة — فهو لا يفعّل مستمِع api_server ثانيًا في الـ profile الثانوي، لذا لست بحاجة إلى تثبيت platforms.api_server.enabled: false في config.yaml الخاص بالثانوي.
      • يجب أن يعلن مسار webhook يستهدف coder عن profile: coder بجانب secret الخاص بمساره الموجود مسبقًا في config.yaml الخاص بالـ profile الافتراضي. عندئذٍ لا يُقبَل ذلك السر إلا عند /p/coder/webhooks/<route> ويُرفَض على أي بادئة profile أخرى.
      • تبقى مسارات webhook التي لا تحمل profile مسارات للـ profile الافتراضي ولا يمكن الوصول إليها عبر بادئة profile مسمّى.
      • يتبع التسليم الربط نفسه. يخرج ردّ مسار profile: coder (أو رسالة deliver_only) عبر محوّل coder لمنصة deliver، ويرجع إلى قناة منزل coder عندما يكون deliver_extra.chat_id غير مضبوط، ويشغّل تسليم github_comment الأمر gh بـ GH_TOKEN / GITHUB_TOKEN من profiles/coder/.env. إذا لم يكن لدى coder محوّل لتلك المنصة، يفشل التسليم (502) بدلًا من النشر كبوت profile آخر؛ وبالمثل لا يستعير مسار افتراضي أبدًا منصة مفعّلة فقط على profile ثانوي.
      • تُتحقَّق نداءات /p/coder/api/platforms/<platform>/events ويُرسلها محوّل coder؛ وحين لا يملك coder محوّلًا، يكون النداء 503.

      تفشل طلبات API المسمّاة بإغلاق تام عندما لا يملك الـ profile المستهدف API_SERVER_KEY. تظل أخطاء إعداد الأمان قاتلة: فمثلًا، منصة سياسة ذاتية open بلا GATEWAY_ALLOW_ALL_USERS أو خيار السماح للجميع الخاص بالمنصة تُلغي بدء تشغيل الـ gateway بدلًا من إسقاط الـ profile غير الآمن بصمت.

      منصات المنفذ الوارد تحت المضاعِف​

      يربط hermes -p coder gateway run المستقل خوادم webhook الخاصة بـ Twilio وLINE وTeams... التابعة لـ coder على منافذها الخاصة. تحت المضاعِف، تظل تلك المحوّلات تابعة لـ coder — بنفس بيانات الاعتماد من profiles/coder/.env، ونفس config.yaml، وتُرسَل الردود عبر قناة coder — لكنها لا تربط أي منفذ. يمرّر مستمِع الـ profile الافتراضي المشترك /p/coder/<path> إليها، حيث <path> هو المسار نفسه الذي يخدمه المحوّل بشكل مستقل. يتحقَّق من الطلب محوّل coder بسر coder (رمز مصادقة Twilio، أو سر قناة LINE، أو بيانات اعتماد تطبيق Teams، أو كلمة مرور BlueBubbles، ...) ويعمل ضمن نطاق تشغيل coder؛ ويبقى /path الخاص بالـ profile الافتراضي نفسه سليمًا، ويحصل profile ليس لديه محوّل لمسار ما على 404، وليس أبدًا بوت profile آخر.

      المنصةرابط الاستدعاء (callback) للـ profile الثانوي على المستمِع المشتركيُتحقَّق منه ببيانات الـ profile المسمّى
      Twilio SMS (sms)https://<host>/p/<profile>/webhooks/twilioتوقيع TWILIO_AUTH_TOKEN (يجب أن يكون SMS_WEBHOOK_URL هو هذا الرابط)
      LINE (line)https://<host>/p/<profile>/line/webhook (الوسائط: /p/<profile>/line/media/...)LINE_CHANNEL_SECRET
      Microsoft Teams (teams)https://<host>/p/<profile>/api/messagesرمز Bot Framework لـ TEAMS_CLIENT_ID
      BlueBubbles (bluebubbles)http://<host>/p/<profile>/bluebubbles-webhook (يُسجَّل مع الخادم تلقائيًا)BLUEBUBBLES_PASSWORD
      Microsoft Graph (msgraph_webhook)https://<host>/p/<profile>/msgraph/webhookextra.client_state
      WhatsApp Cloud (whatsapp_cloud)https://<host>/p/<profile>/whatsapp/webhookWHATSAPP_CLOUD_APP_SECRET / رمز التحقق
      WeCom callback (wecom_callback)https://<host>/p/<profile>/wecom/callbackرمز/مفتاح AES الخاص بـ callback التطبيق
      وضع Feishu webhook (feishu)https://<host>/p/<profile>/feishu/webhookFEISHU_VERIFICATION_TOKEN / FEISHU_ENCRYPT_KEY

      <host> هو اسم المضيف العام (نفق، وكيل عكسي (reverse proxy)) أمام مستمِع الـ profile الافتراضي؛ ويحرّك webhook_path مخصص في إعدادات الـ profile المسار بعد /p/<profile> تبعًا لذلك. تسجّل الـ gateway الرابط الدقيق عند بدء التشغيل:

      [sms] profile 'coder' is served on the default profile's shared listener:
      http://127.0.0.1:8642/p/coder/webhooks/twilio (point the vendor's callback URL at this path ...)

      ويكرّره كل سطح حالة، حتى تعرف ما تلصقه في لوحة تحكم البائع (vendor console):

      $ hermes -p coder gateway status
      ✓ Gateway is running via the default-profile multiplexer
        Manage it from the default profile: hermes gateway status

      Inbound callback URLs on the shared listener:
        line: http://127.0.0.1:8642/p/coder/line/webhook
        sms: http://127.0.0.1:8642/p/coder/webhooks/twilio

      يسرد hermes gateway status وhermes status على الـ profile الافتراضي الروابط نفسها لكل profile مخدوم، وتُظهرها صفحة Channels في لوحة التحكم وصفحة Messaging في Desktop باسم ingress_url الخاص بكل منصة عند عرض ذلك الـ profile. يُبلَّغ عن api_server وwebhook الخاصَين بالـ profile الافتراضي بالطريقة نفسها لـ profile مخدوم — بصفتهما متصلَين (connected) بـ ingress_url هو http://127.0.0.1:8642/p/coder/v1 (وعلى التوالي .../p/coder/webhooks/<route>) — لأن الـ profile ليس له محوّل خاص بهما؛ إنه مستمِع الافتراضي الذي يجيب تحت بادئة /p/coder/. يُتجاهَل SMS_WEBHOOK_PORT أو LINE_PORT أو TEAMS_PORT... الخاص بالثانوي في ملف .env تحت المضاعِف (لا شيء يربط منفذًا)؛ ويعود تطبيقه فور تشغيل ذلك الـ profile gateway مستقلة خاصة به.

      3. لا تزال المنصات القائمة على بيانات الاعتماد بحاجة إلى رمز خاص بكل profile​

      تعمل منصات الاستطلاع/الاتصال (Telegram وDiscord وSlack وMatrix وSignal، ...) جيدًا تحت الـ multiplexing، لكن كل profile يفعّل واحدة منها يجب أن يزوّد رمز بوت خاصًا به — فلا يمكن استطلاع الرمز نفسه من قِبل profileين في آن واحد. إذا أعدّ profileان (platform, token) نفسه، تسجّل الـ gateway خطأ يسمّي كلا الـ profileين وتُوقِف جانبًا المحوّل المكرَّر (يظهر كـ fatal / duplicate_credential في حالة التشغيل) بينما يظل المُطالِب الأول وكل profile آخر يعملان — لا تخرج الـ gateway نفسها. تتصل محوّلات الـ profile الافتراضي أولًا وتطالب ببيانات اعتمادها، لذا فإن المحوّل الموقَف جانبًا هو دائمًا محوّل الثانوي (راجع أمان تعارض الرموز — القاعدة لم تتغيّر، إنها فقط تُطبَّق داخل العملية الواحدة الآن).

      4. مفاتيح الجلسات موزَّعة على نطاقات (namespaced) حسب الـ profile​

      تعيش جلسات كل profile ضمن نطاق اسم agent:<profile>:… بحيث لا يتصادم profileان على المنصة/المحادثة نفسها أبدًا في مخزن الجلسات المشترك. يحافظ الـ profile الافتراضي على نطاق الاسم التاريخي agent:main:… حرفيًا، لذا لا تتأثر جلسات الـ profile الافتراضي القائمة — لا ترحيل، ولا سجل يتيم. يقبل كل مسار gateway يقرأ مفتاحًا سابقًا — اكتمالات التفويض بعد إعادة التشغيل، وإشعارات الإيقاف، و/stop خاصًا بمحادثة مستخدم فردية لتشغيل تابع، و/undo، وأزرار موافقة QQ — شكل agent:<profile>:… أيضًا، بحيث تحصل الـ profiles الثانوية على السلوك نفسه الذي يحصل عليه الافتراضي.

      تحطّ صفوف كل profile في ملفه الخاص من state.db: صفوف profile مسمّى تحت profiles/<name>/state.db، وصفوف الـ profile الافتراضي تحت منزل الإطلاق — حتى عندما تحدث الكتابة داخل دور موجَّه أو نبضة خلفية (tick) تابعة لـ profile آخر. يظل مخزن backend الخاص بـ Desktop/TUI مثبَّتًا على المنزل الذي أُطلق تحته، وتُحفَظ وكلاء Bot Chat الفرعيون (prompt.background) بجانب محادثتهم الأصل.

      5. PID/قفل واحد وسطح حالة واحد​

      يوجد PID وقفل واحد على مستوى العملية (المضاعِف، تحت منزل الافتراضي). يبلّغ hermes status على الـ profile الافتراضي عن المضاعِف ويسرد الـ profiles التي يخدمها (Serves: coder, research)؛ ويبلّغ hermes -p coder status وhermes -p coder gateway status وhermes -p coder cron status جميعًا "running via the default-profile multiplexer" بدلًا من "stopped"، وتبلّغ صفحة /api/status?profile=coder / Channels في لوحة التحكم عن المضاعِف باعتباره gateway coder العاملة (مع محوّلات coder الخاصة بصفتها منصاته). يعيش gateway_state.json الواحد تحت المنزل الافتراضي: تظهر المحوّلات الثانوية هناك كإدخالات <profile>:<platform> بجانب served_profiles؛ ولا يُكتب شيء تحت منزل profile ثانوي.

      ما الذي لا يتغيّر​

      يبقى عزل بيانات اعتماد .env لكل profile محفوظًا، بل يزداد صرامة إن اختلف الأمر: تُحلّ مفاتيح الـ profile من نطاقه الخاص ولا تُدمَج أبدًا في بيئة مشتركة. لا يرى الآخرون مثل خوادم MCP وعمّال Kanban سوى أسرار profileهم الخاص — بما في ذلك بيانات الاعتماد التي يحقنها مصدر سرّي خارجي (1Password، Bitwarden، ...): يتلقى خادم MCP بنمط stdio بُدئ من أجل profile B قيمة B لاسم كهذا، أو لا شيء إن لم يكن لدى B شيء، لا قيمة الـ profile الافتراضي أبدًا. تُوصَل خوادم MCP لكل profile على حدة: يحصل profileان يسمّيان خادمًا بـ github برمزهما الخاص على اتصالين ولا يرى كل منهما سوى أدواته الخاصة؛ أما الـ profiles التي يتطابق فيها إدخال mcp_servers (المسار وبيانات الاعتماد معًا) فتشترك في اتصال واحد، ويعيد /reload-mcp الخاص بالمالك تسجيل أدوات الـ profiles المشتركة دون أن تعيد تحميلها بنفسها. تُحلّ إعدادات الطرفية (terminal.backend، terminal.cwd، terminal.docker_volumes، terminal.docker_shared_container_key، أهداف SSH، ...) كذلك لكل profile في كل دور موجَّه: يحصل profile يغفل مفتاح طرفية على الافتراضي الموثّق، لا قيمة profile الإطلاق أبدًا، ويُرفَض تنفيذ الطرفية لـ profile يتعذّر تحليل config.yaml/.env الخاص به بدلًا من تشغيله تحت سياسة sandbox لـ profile آخر. يغطّي حارس بيانات اعتماد تسليم الوسائط (قائمة الحظر خلف مرفقات MEDIA: — .env، وauth.json، وconfig.yaml، وstate.db، ونصوص الجلسات، ومخازن رموز OAuth) كل profile تحت profiles/، بحيث لا يستطيع دور أي profile إرفاق أسرار أو سجل محادثات profile آخر في رد. التفويض أيضًا لكل profile: تُقرأ GATEWAY_ALLOW_ALL_USERS وGATEWAY_ALLOWED_USERS وكل قائمة سماح منصة أو خيار السماح للجميع من .env الخاص بالـ profile المالك — لا يفتح انضمام الـ profile الافتراضي إلى وصول مفتوح أبدًا بوت profile ثانوي، ويُحترَم انضمام ثانوي في .env الخاص به فقط. الأمر نفسه ينطبق على السلوك الخاص بكل بوت المكتوب في config.yaml الخاص بـ profile (require_mention، وmention_patterns، وallow_bots، وreactions، وauto_thread، وdm_policy، وignored_channels، وسياسة session_scope الخاصة بـ Matrix، ...): لا يحطّ YAML لـ profile ثانوي أبدًا في بيئة العملية المشتركة، لذا لا يمكن أن يصبح سياسة الـ profile الافتراضي، ولا يحكم YAML الخاص بالـ profile الافتراضي بوتًا ثانويًا أبدًا. تُحلّ كذلك لكل profile قائمة السماح terminal.env_passthrough، وقناة المنزل المخصَّصة تلقائيًا لـ Yuanbao، وحرّاس الكتابة الحامية لملف config.yaml الخاص بكل profile. يتصرف Kanban، والمهارات/الذاكرة/SOUL المحدَّدة النطاق لكل profile، وتوجيه النموذج جميعًا لكل profile تمامًا كما تتصرف مع gateways منفصلة.

      الهوية الصادرة أيضًا لكل profile. يرسل الدور العامل من أجل الـ profile P والذي يستدعي أداة send_message (إرسال، وتفاعل، ووسائط) عبر بوت P الخاص؛ وكذلك إشعارات "Gateway shutting down/restarted" و/update لجلسات P، وتنبيهات /loop المضبوطة من محادثات P، وتنبيه المشغِّل غير المصرَّح به لأمر Discord المائل (slash) الخاص ببوت Discord لـ P (إلى قناة منزل P). وإذا لم يكن لدى P بوت متصل لتلك المنصة، يفشل الإرسال برسالة خطأ واضحة — ولا يعود أبدًا إلى بوت الـ profile الافتراضي.

      تتبع بيانات اعتماد الأدوات ومزوّدي الذاكرة القاعدة نفسها. يُقرأ OCR المستضاف (FIRECRAWL_API_KEY)، وبوابات Modal / Browser Use السحابية، ومفتاح OpenAI الخاص بـ mem0 OSS، وفيديو xAI، وكل هوية مزوّد ذاكرة (MEM0_USER_ID، وSUPERMEMORY_CONTAINER_TAG، وRETAINDB_PROJECT، وOPENVIKING_ACCOUNT/USER، وHINDSIGHT_BANK_ID، وHERMES_HONCHO_HOST) من .env الخاص بالـ profile الموجَّه إليه، بحيث تحطّ ذاكرة profile ثانوي في حساب/بنك/مشروع خاص به (أو الافتراضي الخاص بالمزوّد لكل profile)، لا في حساب الـ profile الافتراضي أبدًا. تنتقل النقاط النهائية المخصَّصة مع مفاتيحها — OPENAI_BASE_URL، وXAI_BASE_URL، وNOUS_INFERENCE_BASE_URL، وGATEWAY_PROXY_URL، وروابط Firecrawl / Browserbase / RetainDB / Supermemory / Honcho / Hindsight — بحيث لا يُرسَل مفتاح profile أبدًا إلى proxy أو خادم مستضاف ذاتيًا خاص بـ profile آخر. تكون WEIXIN_HOME_CHANNEL، وHERMES_LANGUAGE، وdisplay.language، و hooks.outbound[].secret_env كذلك لكل profile، ويعمل استخلاص الذاكرة عند نهاية الجلسة لجلسة ثانوية أُخليت (evicted) ضمن نطاق ذلك الـ profile.

      تتبع إعدادات وقت التشغيل لكل دور الـ profile الموجَّه إليه أيضًا: agent.max_turns، وfallback_providers، وfile_read_max_chars، وtool_output.*، ومُهَل browser.*، وtimezone (بما في ذلك TZ المُسلَّم لـ sandboxes الخاصة بـ execute_code)، وسياسة تسليم الوسائط (gateway.strict، وmedia_delivery_allow_dirs، وtrust_recent_files*)، وملف Nous auth.json المستخدَم للنداءات المساعِدة — كلها تُقرأ من الـ profile الذي يخدم الدور، وليس أبدًا من الـ profile الذي أُطلقت تحته الـ gateway. الأمر نفسه ينطبق على ملفات حالة كل profile (processes.json، وcheckpoints/، ومخازن لقطة sandbox، وقواعد تعليقات/اقتران Feishu) وعلى hooks الـ gateway: يُحمَّل دليل hooks/ لكل profile بمفرده ويُطلَق فقط لأحداث ذلك الـ profile. تعمل hooks الـ shell بـ HERMES_HOME الخاص بالـ profile الموجَّه إليه، دون أسرار الـ profile الافتراضي في بيئتها، وتحمل حمولة stdin الخاصة بها حقل profile يسمّي الـ profile الذي أطلقها.

      ما الذي يُعزَل لكل profile​

      مرجع سريع لما يحلّه دور مُضاعَف (multiplexed turn) من profile خاصٍّ به ولا يشاركه أبدًا مع الافتراضي أو أي شقيق له:

      الشأنيُحَلّ منالسلوك عندما يفتقر الـ profile إليه
      مفاتيح المزوّد، ورموز البوت، ومراجع ${VAR} في config.yaml.env الخاص بالـ profile نفسه (نطاق أسراره)غير محلول / لا محوّل — لا قيمة الـ profile الافتراضي أبدًا
      التفويض (GATEWAY_ALLOW_ALL_USERS، GATEWAY_ALLOWED_USERS، قوائم السماح لكل منصة وخيارات السماح للجميع).env وconfig.yaml الخاصان بالـ profile المالكمغلق — لا يفتح انضمام الـ profile الافتراضي أبدًا بوت profile ثانوي
      نقاط HTTP النهائية (/p/<profile>/api/...، /p/<profile>/webhooks/...، نداءات أحداث المنصة)API_SERVER_KEY الخاص بالـ profile المسمّى، ومسارات webhook المرتبطة بـ profile:، ومحوّله الخاص401/404؛ والتسليم من دون محوّل يكون 502/503، وليس أبدًا بوت profile آخر
      منصات المنفذ الوارد (/p/<profile>/webhooks/twilio، /p/<profile>/line/webhook، /p/<profile>/api/messages، …)محوّل الـ profile المسمّى الخاص وسره (رمز مصادقة Twilio، وسر قناة LINE، وتطبيق Teams، وكلمة مرور BlueBubbles، ...)؛ وتخرج الردود عبر ذلك المحوّل401/403 عند سر خاطئ، و404 عندما لا يملك الـ profile محوّلًا كهذا — وليس أبدًا محوّل الـ profile الافتراضي
      إعدادات المحوّل (*_REQUIRE_MENTION، *_REACTIONS، *_PROXY، مضيف/منفذ/رابط webhook، سياسة الخيط/الجلسة/E2EE في Matrix، حدود النسخ الاحتياطي/المرفقات في Discord، وضع رد Buzz، بطاقة وكيل A2A).env وconfig.yaml الخاصان بالـ profile المالكالافتراضي الموثّق للمحوّل — وليس أبدًا إعداد الـ profile الافتراضي
      قائمة حظر مرفقات MEDIA:كل منزل تحت profiles/ إضافة إلى المنزل الافتراضي، مُعدَّدة وقت التحققلا يمكن لدور أبدًا أن يُرفق .env أو auth.json أو state.db أو جلسات أو مخازن رموز خاصة بـ profile آخر
      بيئة عملية MCP الفرعية بنمط stdioالأساس الآمن + قيم الـ profile المحدَّدة النطاق لأسماء مصادر الأسرار + env: الخاص بالخادم نفسهاسم يفتقر إليه الـ profile يكون غائبًا عن العملية الفرعية — لا رجوع إلى الـ profile الافتراضي
      الصادر الخارجي (send_message، إشعارات الإيقاف/إعادة التشغيل//update، تنبيهات /loop، تسليم webhook المرتبط بـ profile:، رموز github_comment)المحوّل المتصل و.env الخاصان بالـ profile نفسهفشل واضح؛ لا يُرسَل أبدًا عبر بوت الـ profile الافتراضي
      نطاق اسم الجلسةagent:<profile>:… (يحافظ الافتراضي على agent:main:…)لا يتشارك profileان على المحادثة نفسها التاريخ أبدًا

      أي الـ profiles تُخدَم​

      يخدم gateway.multiplex_profiles: true الـ profile الافتراضي إضافة إلى كل profile مسمّى حيّ تحت profiles/ — لا توجد قائمة استثناء لكل profile. (مفتاح gateway.multiplex_profile_allowlist السابق أُلغي؛ يزيله ترحيل الإعدادات من config.yaml، وأي profile لا تريد خدمته يُؤرشَف أو يُحذَف بدلًا من ذلك — hermes profile delete <name>، أو انقل الدليل خارج profiles/.) تترك الـ profiles المحذوفة شاهدًا (tombstone) ولا تُعدَّد أبدًا؛ ولا يُعاد إنشاء profile اختفى دليله أبدًا من قِبل دور مخدوم، أو مؤقّت cron، أو توجيه السجلات.

      تتحكم المجموعة المخدومة في بادئات /p/<profile>/ الخاصة بـ API وwebhook، وحالة التشغيل، وأهلية توجيه الـ profile، وأي profiles يجريها مجدوِل cron داخل العملية (يعدّد مؤقّت backend الخاص بـ Desktop المجموعة نفسها ويتنحّى لأي profile تخدمه بالفعل بوابة مضاعِفة (multiplexer) عاملة أو بوابته الخاصة). أي مضاعِف بُدئ بـ hermes -p <name> gateway run يجري دائمًا مخزن cron الخاص بـ profile نفسه أيضًا.

      المجموعة المخدومة حيّة. يُخدَم profile أُنشئ أثناء تشغيل المضاعِف (hermes profile create، أو لوحة التحكم، أو Desktop، أو TUI) فورًا: يُرسل المنشئ إشارة إلى المضاعِف عبر مقبس التحكم (control socket) الخاص به، كما يعيد المضاعِف فحص profiles/ كل 30 ثانية كإجراء أمان إضافي. تُبنى محوّلات الـ profile الجديد بمجرد أن يحمل config.yaml/.env الخاص به رمز بوت (عادةً ما ينشئ المنشئون أولًا، ثم يضيفون الرمز)، ويُحدَّث served_profiles في gateway_state.json الخاص بالـ profile الافتراضي، ويبلّغ hermes -p <name> gateway status عن أنه مخدوم — من دون إعادة تشغيل، ودون المساس بمحوّلات الـ profiles الأخرى وأدوارها الجارية. يوقف حذف profile محوّلاته ويلغي توجيهها بالطريقة نفسها. تظل قاعدة رمز واحد لكل مستطلِع (poller) سارية: يُوقَف profile أُضيف على عجل ويعيد استخدام رمز profile آخر جانبًا بخطأ duplicate_credential، ولا يُشغَّل أبدًا كمستطلِع ثانٍ.

      توجيه محادثات البوت المشتركة إلى الـ profiles (profile_routes)​

      يختار الـ multiplexing profile لكل بيانات اعتماد (رمز البوت الخاص بكل profile) أو لكل بادئة رابط (URL prefix) (/p/<profile>/ لمنصات HTTP). عندما تشترك عدة مجتمعات في بوت واحد — على سبيل المثال بوت Discord واحد يخدم عدة خوادم (guilds) — يمكنك إضافةً إلى ذلك توجيه خوادم/قنوات/خيوط محددة إلى profiles مختلفة عبر gateway.profile_routes:

      gateway:
        multiplex_profiles: true
        profile_routes:
          # An entire Discord server → one profile
          - name: acme-server
            platform: discord
            guild_id: "1234567890"
            profile: acme

          # One channel in that server → a different profile
          - name: acme-support
            platform: discord
            guild_id: "1234567890"
            chat_id: "9876543210"
            profile: acme-support

          # A Telegram group (no guild concept — chat_id only)
          - name: tg-group
            platform: telegram
            chat_id: "-1001234567890"
            profile: tg-profile

          # A WhatsApp DM — write the phone number; JID and LID forms also match
          - name: owner-whatsapp
            platform: whatsapp
            chat_id: "15551234567"
            profile: owner

      تُطابَق المسارات من الأكثر تحديدًا فالأقل (thread_id > chat_id > guild_id)، ويجب أن تتحقق كل الحقول المعلَنة (AND)، ويطابق مسار مربوط بقناة أيضًا الخيوط/منشورات المنتدى التي تكون تلك القناة أصلها. تبقى الرسائل التي لا تطابق أي مسار على الـ profile الافتراضي/النشط. يحصل الـ profile الموجَّه إليه على العزل الكامل لكل profile الموصوف أعلاه (الإعدادات، والمهارات، والذاكرة، وبيانات الاعتماد، ونطاق اسم الجلسة). يعمل التوجيه على كل محوّل منصة، وليس Discord فقط.

      لا ينطبق المسار إلا على الرسائل التي يستقبلها بوت الـ profile الافتراضي ما لم يسمِّ بوتًا آخر بـ bot_profile: <profile>. تستخدم رسائل Telegram المباشرة (DM) chat_id نفسه لكل بوت (معرّف المستخدم)، لذا من دون هذا فإن مسار chat_id مقصودًا للبوت المشترك سيلتقط أيضًا رسائل ذلك المستخدم المباشرة مع بوت مخصص تابع لـ profile ثانوي. تبقى الرسائل الواصلة إلى بوت خاص بـ profile ثانوي داخل ذلك الـ profile:

          # Pin one user's DM with team_b's OWN bot to a third profile
          - name: teamb-owner-dm
            platform: telegram
            bot_profile: team_b
            chat_id: "72719239"
            profile: ops-for-team-b

      يُحسَم التفويض لرسالة موجَّهة دائمًا بواسطة profile البوت المستقبِل (رمزه وقائمة سماحه)، بما في ذلك المتابَعات المرسَلة أثناء انشغال الوكيل والفحوص أثناء الدور مثل /topic أو /stop؛ ولا يحتاج الـ profile الموجَّه إليه نفسه أي نسخة من قائمة السماح. يتلقى profile موجَّه إليه لا يملك بوتًا خاصًا به أيضًا الإشعارات الخلفية (اكتمالات العمليات، والنبضات، ونتائج التفويض غير المتزامن) عبر البوت المشترك بعد إعادة تشغيل الـ gateway.

      على WhatsApp وWhatsApp Cloud، يطابق مسار chat_id عبر أشكال هوية المستخدم المختلفة: رقم هاتف مجرد (15551234567)، وJID (15551234567@s.whatsapp.net)، وLID (…@lid) — كلها تشير إلى الشخص نفسه بمجرد أن يقرنها الجسر (bridge) (نفس التحويل القانوني (canonicalization) الذي تستخدمه مفاتيح جلسات المطابقة وقوائم سماح المحوّل بالفعل). يمكنك وضع رقم الهاتف في profile_routes وستظل الرسائل المباشرة الواردة تطابق سواء سلّم WhatsApp JID أو LID. من دون ربط LID بعد، يظل شكل الرقم يطابق JID (تُحذَف اللاحقة) لكنه لا يستطيع حل LID مجهول — يسقط ذلك الوارد عندئذٍ إلى الـ profile الافتراضي إلى أن يظهر الربط. محادثات المجموعات (…@g.us) ليست هويات مرسِل وتظل تطابق تمامًا. تبقى معرّفات Telegram الرقمية دون تغيير.

      يتطلب profile_routes وجود gateway.multiplex_profiles: true؛ ومع إيقاف الـ multiplexing تُتجاهَل المسارات. إذا طابق مسار صريح لكنه يستهدف profile غير مثبَّت (أو محذوف)، ترفض الـ gateway ذلك الوارد وتسجّل المسار والهدف. ولا تُشغِّل الـ profile الافتراضي. أما الحركة التي لا تطابق أي مسار فتحافظ على السلوك الافتراضي التاريخي للـ profile.

      تُسلَّم مهام cron التي يملكها profile موجَّه إليه عبر البوت المشترك أيضًا، لكن فقط للأهداف التي يربطها مسار مفعَّل بـ chat_id/thread_id بذلك الـ profile (يؤهِّل مسار guild_id + chat_id قناته) — لا تُرسَل أبدًا مهمة لـ profile موجَّه إليه تستهدف محادثة غير موجَّهة (أو محادثة موجَّهة إلى profile آخر) عبر البوت المشترك. لا تؤهِّل المسارات المقتصرة على guild فقط هدف cron؛ أضف مسار chat_id لقناة التسليم. لا يحتاج الـ profile الموجَّه إليه إلى قسم platforms.<platform> الخاص به لهذا: يأتي تفويض البوت المشترك من المسار، لا من إعدادات القمر الصناعي (satellite).

      تشغيل أو إيقاف أو إعادة تشغيل كل الـ gateways دفعة واحدة​

      تأتي CLI مزوّدة بأوامر دورة حياة لـ profile واحد. للتصرف عبر كل profile، لُفّها في حلقة shell. ضع المقطع أدناه في ~/.local/bin/hermes-gateways ونفّذ عليه chmod +x:

      #!/bin/sh
      set -eu

      # Add or remove profile names here as you create / delete profiles.
      profiles="default coder personal-bot research"

      usage() {
        echo "Usage: hermes-gateways {start|stop|restart|status|list}"
      }

      run_for_profile() {
        profile="$1"
        action="$2"
        if [ "$profile" = "default" ]; then
          hermes gateway "$action"
        else
          hermes -p "$profile" gateway "$action"
        fi
      }

      action="${1:-}"
      case "$action" in
        start|stop|restart|status)
          for profile in $profiles; do
            echo "==> $action $profile"
            run_for_profile "$profile" "$action"
          done
          ;;
        list)
          hermes gateway list
          ;;
        *)
          usage
          exit 2
          ;;
      esac

      ثم:

      hermes-gateways start      # start every configured profile
      hermes-gateways stop       # stop every configured profile
      hermes-gateways restart    # restart all
      hermes-gateways status     # status across all
      hermes-gateways list       # delegates to `hermes gateway list`
      نصيحة

      يُستهدَف الـ profile default بـ hermes gateway <action> (بلا -p)، لا بـ hermes -p default gateway <action>. يتعامل الـ wrapper أعلاه مع كلا الشكلين.

      إدارة profile واحد​

      أوامر الاختصار التي يثبّتها كل profile:

      coder gateway run        # foreground (Ctrl-C to stop)
      coder gateway start      # start the managed service
      coder gateway stop       # stop the managed service
      coder gateway restart    # restart
      coder gateway status     # status
      coder gateway install    # create the LaunchAgent / systemd unit
      coder gateway uninstall  # remove the service file

      هذه معادِلة لـ hermes -p coder gateway <action> — مفيدة إذا لم يكن اسم مستعار لـ profile موجودًا في PATH أو إذا كنت تستهدف الـ profiles ديناميكيًا من سكربت.

      يثبّت كل profile خدمته الخاصة باسم فريد، بحيث لا تتعارض التثبيتات أبدًا:

      إبقاء الجهاز المضيف مستيقظًا​

      يمكن لعملية الـ gateway أن تعمل طوال اليوم، لكن نظام التشغيل سيحاول مع ذلك النوم عند عدم النشاط. نمطان:

      macOS — caffeinate​

      caffeinate مدمجة في macOS وتمنع النوم أثناء عملها. لا حاجة إلى تثبيت.

      caffeinate -dis                    # block display, idle, and system sleep
      caffeinate -dis -t 28800           # same, auto-exit after 8 hours
      caffeinate -i -w $(cat ~/.hermes/gateway.pid) &   # awake while default gateway runs

      # Persistent: run in background and forget
      nohup caffeinate -dis >/dev/null 2>&1 &
      disown

      # Inspect / stop
      pmset -g assertions | grep -iE 'caffeinate|prevent|user is active'
      pkill caffeinate

      -mحظر نوم القرص
      -sحظر نوم النظام (لأجهزة Mac الموصولة بالتيار الكهربائي فقط)

      إغلاق الغطاء ما زال يُنيم الـ Mac

      لا تستطيع caffeinate تجاوز نوم إغلاق الغطاء المدفوع بالعتاد على أجهزة MacBook. للتشغيل والغطاء مغلق، غيّر تفضيلات موفِّر الطاقة/البطارية أو استخدم أداة من طرف ثالث.

      Linux — systemd-inhibit أو loginctl​

      # Inhibit suspend while a command runs
      systemd-inhibit --what=idle:sleep --who=hermes --why="gateways running" \
        sleep infinity &

      # Allow user services to keep running after logout (recommended)
      sudo loginctl enable-linger "$USER"

      أمان تعارض الرموز​

      يجب أن يستخدم كل profile رموز بوت فريدة لكل منصة. إذا شارك profileان رمز Telegram أو Discord أو Slack أو WhatsApp أو Signal، ترفض الـ gateway الثانية البدء برسالة خطأ تسمّي الـ profile المتعارض. تحت الـ multiplexing تُوقِف نفس القاعدة محوّل الـ profile المكرَّر فقط بينما تستمر الـ gateway المشتركة في العمل.

      للتدقيق:

      grep -H 'TELEGRAM_BOT_TOKEN\|DISCORD_BOT_TOKEN' \
           ~/.hermes/.env ~/.hermes/profiles/*/.env

      الترحيل من gateways لكل profile​

      إذا كانت profiles لديك يشغّل كل منها gateway خاصة به اليوم (وحدة systemd أو عميل launchd واحد لكل profile)، يمكنك دمجها في gateway افتراضية مضاعَفة واحدة بأمر واحد — والتراجع بأمر آخر. تظل الـ gateways المستقلة لكل profile مدعومة تمامًا؛ وهذا ترحيل اختياري، لا إزالة.

      hermes gateway migrate --multiplex --dry-run   # print the plan and any blockers; changes nothing
      hermes gateway migrate --multiplex             # apply (asks for confirmation on a TTY; -y skips)
      hermes gateway migrate --standalone            # roll back to per-profile gateways

      ما الذي يفعله hermes update​

      بعد تحديث ناجح، عندما يحتوي التثبيت على profileين أو أكثر، ويشغّل profile ثانوي واحد على الأقل gateway خاصة به (عملية حيّة أو خدمة مثبَّتة) ويكون gateway.multiplex_profiles معطّلًا، يجري hermes update الفحص المسبق نفسه:

      • لا شيء يعيقه ← يعمل الترحيل تلقائيًا (بمسار الكود نفسه لـ hermes gateway migrate --multiplex --yes) ويطبع ما فعله. هذا حتمي (deterministic) ولا يسأل أبدًا، لذا يعمل أيضًا في التحديثات بلا شاشة (headless)/عبر cron.
      • شيء يعيقه ← يسرد كتلة تحذير كل عائق مع إصلاحه الدقيق والسطر الواحد الذي تشغّله لاحقًا. لا يتغيّر شيء.

      لا تُرحَّل أبدًا التثبيتات ذات profile واحد (فلا فائدة من ذلك)، ويُترَك التثبيت الذي يستخدم الـ multiplexing بالفعل كما هو. لا يفعل hermes update أيضًا شيئًا عندما لا تشغّل أي profile ثانوية gateway خاصة بها — فهو لا يبدّل الأوضاع أبدًا على تثبيت لم يكن فيه شيء يعمل.

      الأمر الصريح مختلف: يطبّق hermes gateway migrate --multiplex مع profileين أو أكثر ودون أي gateway ثانوية مستقلة الخطوة الأخيرة المتبقية — فهو يضبط gateway.multiplex_profiles: true، ويعيد تشغيل (أو يشغّل) الـ gateway الافتراضية ويكتب بيان التراجع نفسه (مع قائمة secondaries فارغة)، بحيث يتراجع عنه --standalone. طلبتَ الـ multiplex؛ فحصلتَ على الـ multiplex.

      الاستنساخات لا تحمل القنوات

      يترك hermes profile create --clone رموز بوت المصدر وقوائم سماحه خلف الركب (راجع Profiles → قنوات المراسلة لا تُستنسخ أبدًا)، بحيث لا تعود مجموعة من الاستنساخات تصطدم بعائق بيانات الاعتماد المكرَّرة أدناه. تُوسَم الاستنساخات القديمة التي ما زالت تحملها بواسطة hermes profile list.

      ما الذي يفعله الترحيل​

      1. يوقف الـ gateway المستقلة الخاصة بكل profile ثانوي ويلغي تثبيت خدمته (وحدة مستخدم/نظام systemd أو عميل launchd). يُسجَّل ما أُزيل في ~/.hermes/gateway_migration.json للتراجع.
      2. يضبط gateway.multiplex_profiles: true ضمن الـ profile الافتراضي في config.yaml الخاص به.
      3. يعيد تشغيل الـ gateway الافتراضية — أو يثبّتها ويشغّلها على مدير الخدمة نفسه الذي كانت تستخدمه الـ profiles الثانوية، بحيث يبقى الأسطول المُدار بـ systemd مُدارًا بـ systemd.
      4. ينتظر حتى تسجّل الـ gateway الافتراضية served_profiles التي تغطي كل profile، ثم يطبع ملخصًا.

      يعدّ profileان بيانات اعتماد المنصة نفسها (مثل TELEGRAM_BOT_TOKEN نفسه)تحت عملية واحدة، لا يمكن استطلاع رمز بوت إلا مرة واحدة؛ سيُوقِف المضاعِف المكرَّر جانبًا وسيصمت بوت ذلك الـ profileأزل الرمز من الـ profile الثاني، أو أبقه في default ووجّه محادثات ذلك الـ profile عبر profile_routes
      يفعّل profile ثانوي منصة ذات منفذ وارد لا يملك أي بوابة (ingress) /p/<profile>/ على المستمِع الافتراضييتخطى المضاعِف ذلك الـ profile بأكمله (راجع القاعدة 2)عطّل المنصة في ذلك الـ profile (platforms.<name>.enabled: false)، أو أبقِ الـ profile على gateway مستقلة بـ hermes -p <name> gateway start --force

      يعيد فحص بيانات الاعتماد استخدام كشف تعارض الـ gateway نفسه، لذا يطابق حكمه ما تفعله الـ multiplexer عند البدء. تُقرأ المنصات ذات المنفذ الوارد التي تملك بوابة /p/<profile>/ من المحوّلات نفسها (يعلن كل منها serves_profile_prefix)، بحيث يظل الفحص المسبق صحيحًا مع اكتساب محوّلات HTTP-الوارد الجديدة البادئة.

      ما الذي يتغيّر بالنسبة إلى profiles المنفذ الوارد​

      الـ profile الثانوي الذي استخدم api_server أو webhook على منفذه الخاص لا يُحظَر — لكن رابطه يتغيّر. يطبع الفحص المسبق الرابط الجديد الدقيق، مثلًا:

      Profile 'coder': api_server moves onto the default listener at
      http://127.0.0.1:8642/p/coder/v1/... (its key/secret is unchanged; update
      clients that call the old per-profile port).

      يستمر API_SERVER_KEY أو سر webhook الخاص بالـ profile في مصادقة الرابط ذي البادئة؛ ولا يتغيّر شيء آخر بشأن المفتاح.

      الـ profiles المُنشأة بعد الترحيل​

      يُخدَم profile أُنشئ أثناء تشغيل المضاعِف من دون إعادة تشغيل (راجع أعلاه). يؤكد hermes profile create ذلك عندما يتلقَّط المضاعِف الحيّ الـ profile؛ ولا يطبع تذكير hermes gateway restart إلا عندما يتعذّر عليه الوصول إلى المضاعِف (على سبيل المثال، gateway بُدئت من إصدار قديم).

      التراجع​

      hermes gateway migrate --standalone

      يقرأ gateway_migration.json، ويعيد ضبط gateway.multiplex_profiles إلى قيمته السابقة، ويعيد تشغيل الـ gateway الافتراضية، ويعيد تثبيت/تشغيل كل خدمة مسجَّلة لكل profile. يُزال البيان (manifest) بمجرد أن يعود كل شيء. إذا لم يوجد بيان (فعّلتَ الـ multiplexing يدويًا)، غادِر وضع الـ multiplex بـ hermes config set gateway.multiplex_profiles false && hermes gateway restart وأعد تثبيت خدمات كل profile التي تريدها.

      غير مغطّى تلقائيًا: الحاويات المُشرَف عليها بـ s6 (اضبط الخيار على الـ profile الافتراضي وأعد تشغيل الحاوية) ومهام Windows Scheduled Tasks (اضبط الخيار، وأوقف مهام كل profile، ثم hermes gateway restart). تعرض صفحة System في لوحة التحكم الترحيل نفسه كزر عندما يجد الفحص المسبق تثبيتًا مؤهَّلًا.

      تحديث الكود​

      يسحب hermes update أحدث كود مرة واحدة ويزامن المهارات المضمّنة الجديدة مع كل profile:

      hermes update
      hermes-gateways restart

      يعيد التحديث نفسه تشغيل الـ gateways العاملة؛ وفي تثبيت ما زال يشغّل gateway واحدة لكل profile، يعرض التحديث بعدها الترحيل إلى gateway واحدة مضاعَفة — تلقائيًا عندما لا يعيقه شيء، وإلا فكتحذير مع الإصلاحات.

      لا تُستبدَل أبدًا المهارات التي عدّلها المستخدم.

      استكشاف الأخطاء وإصلاحها​

      "Could not find service in domain for user gui: 501"​

      لقد شغّلت hermes gateway start بعد hermes gateway stop سابق. تجري stop الخاصة بـ CLI عملية launchctl unload كاملة، والتي تزيل الخدمة من سجل launchd. تلتقط CLI هذا الخطأ المحدَّد عند start و تعيد تحميل ملف plist تلقائيًا (↻ launchd job was unloaded; reloading service definition). تبدأ الخدمة بشكل طبيعي. لا شيء لإصلاحه.

      PID قديم بعد عطل (crash)​

      إذا أظهرت gateway الخاصة بـ profile not running بينما لا تزال عملية حيّة:

      ps -ef | grep "hermes_cli.*-p <profile>"
      cat ~/.hermes/profiles/<profile>/gateway.pid
      kill -TERM <pid>          # graceful
      kill -KILL <pid>          # if that fails after a few seconds
      <profile> gateway start

      فرض إعادة ضبط قسرية (hard reset) لخدمة واحدة​

      # macOS
      launchctl unload ~/Library/LaunchAgents/ai.hermes.gateway-<profile>.plist
      launchctl load   ~/Library/LaunchAgents/ai.hermes.gateway-<profile>.plist

      # Linux
      systemctl --user restart hermes-gateway-<profile>.service

      فحص السلامة (Health check)​

      hermes doctor                  # default profile
      hermes -p <profile> doctor     # one profile

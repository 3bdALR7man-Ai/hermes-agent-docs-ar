      البرمجيات الوسيطة في Hermes

      البرمجيات الوسيطة (middleware) في Hermes هي النظير الذي يغيّر السلوك لـ hooks المراقبة. تُبلغ hooks المراقبة عما حدث، بينما يمكن للبرمجيات الوسيطة تغيير ما يحدث بإعادة كتابة الطلب قبل التنفيذ أو بتغليف استدعاء التنفيذ الراجع نفسه.

      هذا العقد محايد تجاه backend عمدًا. يمكن للإضافة استخدامه للسياسات المحلية، أو تشكيل الطلبات، أو التتبع، أو التوجيه التكيّفي، أو التحكم في التخزين المؤقت، أو اختيار sandbox، أو التسليم إلى بيئات تشغيل مثل NeMo Relay دون تغيير مخطط Hermes، أو محوّلات مزوّدي النماذج، أو سجل الأدوات، أو الذاكرة، أو تجربة استخدام CLI.

      عند تفعيل البرمجيات الوسيطة، يمكن للإضافات:

      • إعادة كتابة kwargs لطلبات مزوّد LLM قبل أن يستدعي Hermes المزوّد.
      • إعادة كتابة وسائط الأدوات قبل أن تراها ضوابط الأمان وفحوص الموافقة و hooks وتنفيذ الأداة.
      • تغليف الاستدعاء الراجع لتنفيذ LLM الفعلي مع الحفاظ على سلوك Hermes في إعادة المحاولة والبث والمقاطعة و hooks.
      • تغليف الاستدعاء الراجع لتنفيذ الأداة الفعلي مع الحفاظ على ضوابط أمان Hermes والموافقة و hooks ما بعد الأداة وتحويل نتيجة الأداة.

      العقد​

      تسجّل الإضافات البرمجيات الوسيطة من register(ctx):

      def register(ctx):
          ctx.register_middleware("llm_request", on_llm_request)
          ctx.register_middleware("llm_execution", on_llm_execution)
          ctx.register_middleware("tool_request", on_tool_request)
          ctx.register_middleware("tool_execution", on_tool_execution)

      يتلقى كل استدعاء راجع للبرمجيات الوسيطة:

      • telemetry_schema_version: حاليًا hermes.observer.v1
      • middleware_schema_version: حاليًا hermes.middleware.v1
      • سياق تشغيل مثل session_id, task_id, turn_id, api_request_id, provider, model, api_mode, tool_name، و tool_call_id عند انطباقها.

      أنواع البرمجيات الوسيطة المدعومة:

      النوعالحمولةبنية القيمة المُعادةالغرض
      llm_requestrequest, original_request{"request": {...}}استبدال kwargs الفعلية للمزوّد قبل تنفيذه.
      tool_requesttool_name, args, original_args{"args": {...}}استبدال وسائط الأداة الفعلية قبل hooks وضوابط الأمان والموافقات والتنفيذ.
      llm_executionrequest, original_request, next_callأي استجابة من المزوّدتغليف استدعاء المزوّد الفعلي أو استبداله.
      tool_executiontool_name, args, original_args, next_callأي نتيجة للأداةتغليف استدعاء الأداة الفعلي أو استبداله.

      يمكن لبرمجيات الطلب الوسيطة إعادة حقول تتبع اختيارية:

      return {
          "request": updated_request,
          "source": "my-plugin",
          "reason": "selected fallback model",
      }

      يخزّن Hermes إدخالات التتبع تلك في حمولات hooks المراقبة اللاحقة باسم middleware_trace.

      تتلقى برمجيات التنفيذ الوسيطة استدعاءً راجعًا باسم next_call. استدعه لمواصلة السلسلة:

      def on_tool_execution(**kwargs):
          result = kwargs["next_call"](kwargs["args"])
          return result

      إذا سجّلت عدة إضافات النوع نفسه من برمجيات التنفيذ الوسيطة، يشغّلها Hermes كسلسلة متداخلة بترتيب التسجيل. لا توقف إخفاقات البرمجيات الوسيطة التنفيذ: يسجّل Hermes تحذيرًا ويتابع البرمجية الوسيطة التالية أو مسار التشغيل الأساسي. يُبلَّغ عن الاستدعاء الراجع الذي يفشل بالطريقة نفسها كل مرة (عادةً بسبب توقيع يسمّي حقلًا لا ترسله البرمجية الوسيطة) مرة واحدة بمستوى WARNING — وتسرد الرسالة الحقول التي يوفرها فعلًا — وتُنقل التكرارات المطابقة إلى DEBUG، كي لا تُغرق برمجية وسيطة معلنة خطأً السجل؛ وتعيد إعادة تحميل الإضافة ضبط الإبلاغ.

      ترتيب التنفيذ​

      استدعاءات LLM​

      لكل طلب إلى المزوّد، يطبّق Hermes البرمجيات الوسيطة بهذا الترتيب:

      1. بناء kwargs الخاصة بالمزوّد من المحادثة الحالية.
      2. تطبيق البرمجيات الوسيطة llm_request.
      3. إطلاق hooks المراقبة pre_api_request بالطلب الفعلي.
      4. تشغيل تنفيذ المزوّد عبر البرمجيات الوسيطة llm_execution.
      5. إطلاق hooks المراقبة post_api_request أو api_request_error.

      ترى برمجيات الطلب الوسيطة kwargs الكاملة للمزوّد، بما فيها messages أو input الخاصة بـ Responses API، وإعدادات النموذج، وتعريفات الأدوات، وخيارات البث، والخيارات الخاصة بالمزوّد. تتلقى برمجيات التنفيذ الوسيطة الطلب الفعلي نفسه إضافةً إلى next_call.

      استدعاءات الأدوات​

      لكل استدعاء أداة، يطبّق Hermes البرمجيات الوسيطة بهذا الترتيب:

      1. تحليل وسائط الأداة التي قدمها النموذج وتحويل أنواعها.
      2. تطبيق البرمجيات الوسيطة tool_request.
      3. تشغيل مسار Hermes المعتاد السابق للتنفيذ على الوسائط الفعلية: فحوص توفر الأداة، وتوجيهات الحظر للمراقب، وضوابط الأمان، وفحوص الموافقة.
      4. تشغيل تنفيذ الأداة عبر البرمجيات الوسيطة tool_execution.
      5. إطلاق hooks المراقبة post_tool_call.
      6. تطبيق hooks transform_tool_result قبل إضافة النتيجة إلى سياق المحادثة مجددًا.

      تعمل برمجيات طلب الأداة الوسيطة قبل فحوص الموافقة. استخدمها بحذر: فالمسار أو الأمر أو URL المُعاد كتابته هو القيمة التي ستقيّمها السياسة اللاحقة.

      التفعيل​

      لا تعمل البرمجيات الوسيطة إلا للإضافات المفعّلة. لإضافة مضمّنة:

      hermes plugins enable <plugin-name>

      للاختبار المحلي المعزول، استخدم قيمة واحدة لـ HERMES_HOME لتفعيل الإضافة وتشغيل الوكيل:

      export HERMES_HOME=$HOME/.hermes/cache/scratch/hermes-middleware-test
      mkdir -p "$HERMES_HOME"
      hermes plugins enable <plugin-name>
      hermes chat --query 'Reply exactly ok'

      في النسخ المسحوبة من المصدر، استخدم سير عمل المطوّر في PM ومجلدًا رئيسيًا منفصلًا للتطوير، لترى بيئة التشغيل الإضافات والبرمجيات الوسيطة من شجرة العمل:

      export HERMES_HOME="$HOME/hermes-middleware-test"
      export HERMES_RUNTIME_DIR="$HERMES_HOME/tools"
      source ./activate
      python hermes plugins enable <plugin-name>
      python hermes chat --query 'Reply exactly ok'

      أمثلة عامة للإضافات​

      الأمثلة أدناه صغيرة عمدًا. تعرض بنية عقد البرمجيات الوسيطة دون الاعتماد على NeMo Relay.

      برمجيات طلب LLM الوسيطة​

      توسم هذه الإضافة طلبات المزوّد وتسجّل إدخال تتبع للبرمجيات الوسيطة:

      def register(ctx):
          ctx.register_middleware("llm_request", tag_llm_request)


      def tag_llm_request(**kwargs):
          request = dict(kwargs["request"])
          extra_body = dict(request.get("extra_body") or {})
          extra_body.setdefault("metadata", {})["hermes_middleware_demo"] = True
          request["extra_body"] = extra_body
          return {
              "request": request,
              "source": "middleware-demo",
              "reason": "tagged provider request",
          }

      يُمرَّر الطلب الفعلي إلى pre_api_request وتنفيذ المزوّد و post_api_request.

      برمجيات طلب الأداة الوسيطة​

      تقيّد هذه الإضافة استدعاءات terminal بمجلد عمل معروف:

      from pathlib import Path


      def register(ctx):
          ctx.register_middleware("tool_request", normalize_terminal_workdir)


      def normalize_terminal_workdir(**kwargs):
          if kwargs.get("tool_name") != "terminal":
              return None
          args = dict(kwargs["args"])
          args.setdefault("workdir", str(Path.home() / ".hermes" / "cache" / "scratch" / "hermes-middleware-demo"))
          return {
              "args": args,
              "source": "middleware-demo",
              "reason": "defaulted terminal workdir",
          }

      لأن ذلك يعمل قبل hooks والموافقات، ترى بيانات الرصد والسياسة اللاحقة قيمة workdir.

      برمجيات تنفيذ LLM الوسيطة​

      تغلّف هذه الإضافة استدعاء المزوّد وتحافظ على استجابته الخام:

      import time


      def register(ctx):
          ctx.register_middleware("llm_execution", time_llm_execution)


      def time_llm_execution(**kwargs):
          started = time.monotonic()
          response = kwargs["next_call"](kwargs["request"])
          elapsed_ms = int((time.monotonic() - started) * 1000)
          print(f"llm_execution elapsed_ms={elapsed_ms}")
          return response

      أعِد بنية الاستجابة نفسها التي يتوقعها Hermes من محوّل المزوّد. لا تغلّف الاستجابة بغلاف خاص بالإضافة ما لم تتوقع بقية بيئة التشغيل ذلك الغلاف.

      برمجيات تنفيذ الأداة الوسيطة​

      تغلّف هذه الإضافة تنفيذ الأداة مع الحفاظ على نتيجتها:

      def register(ctx):
          ctx.register_middleware("tool_execution", annotate_tool_execution)


      def annotate_tool_execution(**kwargs):
          result = kwargs["next_call"](kwargs["args"])
          # Metrics, logging, or external routing can happen here.
          return result

      يمكن لبرمجيات التنفيذ الوسيطة استدعاء next_call(modified_args) لتمرير حمولة معدّلة إلى البرمجيات الوسيطة اللاحقة وموزّع الأدوات الأساسي.

      ينبغي أن توجد الأمثلة الخاصة بالإضافة ضمن الإضافة التي تملك السلوك. تُثبَّت برمجيات تنفيذ NeMo Relay الوسيطة عبر إعدادات المستخدم والنظام التي يكتشفها Relay، أو عبر plugins.toml صريح يُختار بواسطة HERMES_NEMO_RELAY_PLUGINS_TOML؛ راجع مقاييس Relay المشتركة.

      ملاحظات الأمان​

      • ينبغي أن تكون البرمجيات الوسيطة حتمية للمدخلات نفسها، إلا إذا كانت توجّه صراحةً إلى نظام خارجي ديناميكي.
      • ينبغي أن تعيد برمجيات الطلب الوسيطة حمولات بديلة كاملة، لا ترقيعات جزئية.
      • ينبغي أن تستدعي برمجيات التنفيذ الوسيطة next_call(...) مرة واحدة بالضبط، ما لم تكن تتجاوز التنفيذ عمدًا.
      • إذا أطلقت برمجيات التنفيذ الوسيطة استثناءً قبل استدعاء next_call(...)، يعامل Hermes ذلك كإخفاق للبرمجية الوسيطة ويواصل بقية السلسلة والتنفيذ الأساسي.
      • إذا استدعت برمجيات التنفيذ الوسيطة next_call(...) بنجاح ثم أطلقت استثناءً أثناء المعالجة اللاحقة، يحتفظ Hermes بالنتيجة اللاحقة ولا يشغّل المزوّد أو الأداة مرة ثانية.
      • إذا فشل التنفيذ اللاحق للمزوّد أو الأداة، يمكن للبرمجيات الوسيطة تمرير ذلك الخطأ أو تحويله عمدًا. لا يحوّل Hermes الإخفاق اللاحق إلى نتيجة None ناجحة.
      • تعمل برمجيات طلب الأداة الوسيطة قبل الموافقات. وإذا عدّلت مسارات الملفات أو الأوامر أو عناوين URL أو الوسائط، فالقيم المعدّلة هي ما تقيّمه ضوابط الأمان والموافقات.
      • تظل hooks المراقبة المكان الصحيح للرصد للقراءة فقط. استخدم البرمجيات الوسيطة فقط عندما تحتاج إضافة إلى تعديل السلوك أو تغليفه.

      آلية عمل Gateway من الداخل

      Messaging gateway هو العملية طويلة الأمد التي تصل Hermes بأكثر من 20 منصّة مراسلة خارجية عبر بنية معمارية موحّدة.

      الملفات الرئيسية​

      الملفالغرض
      gateway/run.pyGatewayRunner — تجمع mixins الشقيقة في gateway/run_*.py (البدء، المهايئات، الوارد، الدور، الانشغال، الأهداف، الإشعارات، الإيقاف، …) ومعالِجات gateway/slash_commands_*.py المعالجات
      gateway/session.pySessionStore — استمرارية المحادثة وبناء مفتاح الجلسة
      gateway/delivery.pyتسليم الرسائل الصادرة إلى المنصات/القنوات المستهدفة
      gateway/pairing.pyتدفّق اقتران الرسائل المباشرة (DM) لتفويض المستخدم
      gateway/channel_directory.pyيربط معرّفات المحادثات بأسماء مقروءة للتسليم عبر cron
      gateway/hooks.pyاكتشاف الـ hooks وتحميلها وتوزيع أحداث دورة الحياة
      gateway/mirror.pyمرآة الرسائل عبر الجلسات لأجل send_message
      gateway/status.pyإدارة أقفال التوكن لنسخ gateway المحدَّدة بـ profile
      gateway/builtin_hooks/نقطة توسعة للـ hooks المسجَّلة دائمًا (لا شيء مُضمَّن حاليًا)
      gateway/platform_registry.pyسجل المهايئات، والمصانع (factories)، ومحمِّلات مؤجَّلة (lazy) لإضافات المنصات المضمّنة
      plugins/platforms/<name>/مهايئات المراسلة المضمّنة (معظم المنصات: adapter.py + plugin.yaml)
      gateway/platforms/مشترَك base.py المشترك بالإضافة إلى مهايئات قديمة/مباشرة (Signal وخادم API والـ webhooks ، …)

      تدفّق الرسائل​

      عند وصول رسالة من أي منصّة:

      1. مهايئ المنصّة يستقبل الحدث الخام، ويوحّد صيغته إلى MessageEvent
      2. المهايئ الأساسي يتحقّق من حارس الجلسة النشطة:
        • إذا كان الوكيل يعمل بالفعل لهذه الجلسة → تُصفّ الرسالة في قائمة الانتظار، ويُضبط حدث مقاطعة
        • إذا كانت /approve, /deny, /stop → تتجاوز الحارس (تُوزَّع مباشرة (inline))
      3. GatewayRunner._handle_message() يستقبل الحدث:
        • يحدّد مفتاح الجلسة عبر _session_key_for_source() (الصيغة: agent:{namespace}:{platform}:{chat_type}:{chat_id}؛ ويكون نطاق الأسماء main للـ profile الافتراضي، و <profile> عند تعدد الإرسال — راجع Profiles متعددة الإرسال)
        • يتحقّق من التفويض (انظر التفويض أدناه)
        • يتحقّق مما إذا كانت slash command → يوزّعها إلى معالِج الأوامر
        • يتحقّق مما إذا كان الوكيل يعمل بالفعل → يعترض أوامر مثل /stop, /status
        • وإلا → ينشئ نسخة AIAgent ويشغّل المحادثة
      4. الاستجابة تُرسل عائدةً عبر مهايئ المنصّة

      صيغة مفتاح الجلسة​

      تُرمّز مفاتيح الجلسات سياق التوجيه الكامل:

      agent:{namespace}:{platform}:{chat_type}:{chat_id}

      على سبيل المثال: agent:main:telegram:private:123456789 للـ profile الافتراضي، أو agent:work:telegram:private:123456789 عندما يوجّه multiplexer تلك المحادثة إلى profile work (gateway/session.py::_session_key_namespace؛ ويُعلَّم profile اسمه حرفيًا main بـ main~).

      قد تُضمِّن المنصات المدركة للخيوط (Telegram forum topics ، Discord threads ، Slack threads) معرّفات الخيط ضمن جزء chat_id. لا تبنِ مفاتيح الجلسات يدويًا أبدًا — استخدم دائمًا build_session_key() من gateway/session.py.

      حارس رسائل ثنائي المستوى​

      عندما يكون الوكيل قيد التشغيل فعليًا، تمرّ الرسائل الواردة عبر حارسَين متتاليين:

      1. المستوى 1 — المهايئ الأساسي (gateway/platforms/base.py): يتحقّق من _active_sessions. إذا كانت الجلسة نشطة، يضع الرسالة في قائمة انتظار _pending_messages ويضبط حدث مقاطعة. يلتقط هذا الرسائل قبل وصولها إلى مشغّل gateway.

      2. المستوى 2 — مشغّل gateway (gateway/run_inbound.py): يتحقّق من _running_agents. يعترض أوامر محدَّدة (/stop, /new, /queue, /status, /approve, /deny) ويوجّهها بحسب الحاجة. أي شيء آخر يُطلق running_agent.interrupt().

      الأوامر التي يجب أن تصل إلى المشغّل أثناء انسداد الوكيل (مثل /approve) تُوزَّع مباشرة (inline) عبر await self._message_handler(event) — فهي تتجاوز نظام المهام الخلفية لتجنّب حالات التسابق (race conditions).

      التفويض​

      يستخدم gateway تحقّق تفويض متعدّد الطبقات، يُقيَّم بالترتيب التالي:

      1. علامة السماح للجميع الخاصة بكل منصّة (مثل TELEGRAM_ALLOW_ALL_USERS) — إذا ضُبطت، يُفوَّض جميع المستخدمين على تلك المنصّة
      2. قائمة السماح الخاصة بالمنصّة (مثل TELEGRAM_ALLOWED_USERS) — معرّفات مستخدمين مفصولة بفواصل
      3. اقتران DM — يمكن للمستخدمين المصادَق عليهم اقتران مستخدمين جدد عبر رمز اقتران
      4. السماح للجميع عالميًا (GATEWAY_ALLOW_ALL_USERS) — إذا ضُبطت، يُفوَّض جميع المستخدمين عبر كل المنصاتgateway.allow_all_users في config.yaml، ويُربط بمتغير البيئة بواسطة gateway/config_loader.py::bridge_core_env_settings) — إذا ضُبط، يُصرّح لكل المستخدمين عبر كل المنصات
      5. الافتراضي: الرفض — يُرفض المستخدمون غير المفوَّضين

      تدفّق اقتران DM​

      Admin: /pair
      Gateway: "Pairing code: ABC123. Share with the user."
      New user: ABC123
      Gateway: "Paired! You're now authorized."

      تُحفظ حالة الاقتران في gateway/pairing.py وتنجو من إعادة التشغيل.

      توزيع Slash Commands​

      تمرّ كل الـ slash commands في gateway عبر خط أنابيب الحسم نفسه:

      1. resolve_command() من hermes_cli/commands.py المُدخل بالاسم الأساسي (تعالج الأسماء البديلة، ومطابقة البادئات)
      2. يُتحقّق من الاسم الأساسي مقابل GATEWAY_KNOWN_COMMANDS
      3. _handle_message() (gateway/run_inbound.py) عن المعالِج بالاسم — _handle_<name>_command في mixins الخاصة بـ gateway/slash_commands_*.py — عبر _command_handler_table فوق _IDLE_COMMANDS / _PLAIN_COMMANDS في gateway/run_busy.py؛ ولا توجد سلسلة if canonical == ... السلسلة
      4. بعض الأوامر مقيَّدة بحسب الإعدادات (gateway_config_gate على CommandDef)

      حارس الوكيل قيد التشغيل​

      تُرفض الأوامر التي يجب ألا تُنفَّذ أثناء معالجة الوكيل مبكرًا:

      أثناء وجود _quick_key in self._running_agents, _dispatch_busy_slash_command() في gateway/run_busy.py كل أمر معروف حسب CommandDef.busy_policy / busy_handler الخاصة به: نسخة أثناء التشغيل (_busy_<key>_command) إن وُجدت، وإلا المعالِج العادي عندما تسمح busy_policy بذلك، وإلا رسالة رفض ("⏳ Agent is running — /model can't run mid-turn…").

      أوامر التجاوز (/stop, /new, /approve, /deny, /queue, /status) لها معالِجات أثناء التشغيل وتُوزَّع مباشرة (inline).

      مصادر الإعدادات​

      يقرأ gateway الإعدادات من مصادر متعدّدة:

      المصدرما يوفّره
      ~/.hermes/.envمفاتيح API ، وتوكنات البوت، وبيانات اعتماد المنصات
      ~/.hermes/config.yamlإعدادات النموذج، وإعداد الأدوات، وخيارات العرض
      متغيرات البيئةتتجاوز أيًا مما سبق

      خلافًا لـ CLI (الذي يستخدم load_cli_config() بقيم افتراضية مثبَّتة في الكود)، يقرأ gateway ملف config.yaml مباشرةً عبر محمِّل YAML. هذا يعني أن مفاتيح الإعدادات الموجودة في قاموس افتراضيات CLI ولكن غير الموجودة في ملف إعدادات المستخدم قد تتصرّف بشكل مختلف بين CLI و gateway.

      مهايئات المنصات​

      تُشحَن معظم منصات المراسلة كمهايئات إضافات تحت plugins/platforms/<name>/adapter.py؛ ولا تزال بضعة مهايئات قديمة تعيش مباشرةً في gateway/platforms/. تمتد جميعها من BasePlatformAdapter في gateway/platforms/base.py:

      plugins/platforms/                  # plugin-packaged adapters (one dir each)
      ├── telegram/adapter.py     # Telegram Bot API (long polling or webhook)
      ├── discord/adapter.py      # Discord bot via discord.py
      ├── slack/adapter.py        # Slack Socket Mode
      ├── whatsapp/adapter.py     # WhatsApp Business Cloud API
      ├── matrix/adapter.py       # Matrix via mautrix (optional E2EE)
      ├── mattermost/adapter.py   # Mattermost WebSocket API
      ├── email/adapter.py        # Email via IMAP/SMTP
      ├── sms/adapter.py          # SMS via Twilio
      ├── dingtalk/adapter.py     # DingTalk WebSocket
      ├── feishu/adapter.py       # Feishu/Lark WebSocket or webhook
      ├── wecom/adapter.py        # WeCom (WeChat Work) callback
      ├── line/adapter.py         # LINE Messaging API
      ├── teams/adapter.py        # Microsoft Teams
      ├── irc/adapter.py          # IRC (canonical scoped-lock example)
      └── …                       # google_chat, ntfy, photon, raft, simplex, …

      gateway/platforms/                  # core base + legacy direct adapters
      ├── base.py              # BasePlatformAdapter — shared logic for all platforms
      ├── signal.py            # Signal via signal-cli REST API
      ├── weixin.py            # Weixin (personal WeChat) via iLink Bot API

      ├── webhook.py           # Inbound/outbound webhook adapter
      └── api_server.py        # REST API server adapter

      التحميل المؤجَّل: تسجّل إضافات kind: platform المضمّنة محمِّلات register_deferred منخفضة التكلفة في gateway/platform_registry.py (عبر hermes_cli/plugins.py) بحيث لا تُستورد SDKs المنصات إلا عندما يبدأ gateway أو يُسلّم أو يشغّل الإعداد/الحالة — وليس عند تنفيذ hermes chat العادي. يحمّل الحسم مهايئًا واحدًا عند البحث؛ ويشغّل التعداد الكامل المحمِّلات المعلّقة فقط في المسارات التي تحتاج كل منصّة.

      تستخدم منصات موصولات الاختبار التجريبية (connector-backed) المهايئ العام للترحيل (relay) في gateway/relay/ بدلًا من وحدة منصّة مباشرة. عند ضبط GATEWAY_RELAY_URL أو gateway.relay_url، يسجّل gateway منصّة relay، ويطلب الموصول عبر WebSocket صادر، ويستقبل إطارات descriptor, inbound وinterrupt_inbound على نفس المقبس (socket). يعلن الموصول عن CapabilityDescriptor؛ ويمكن لـ Hermes إرسال ردود صادرة عادية، وعمليات follow_up بدون توكن، وإطارات مقاطعة عائدة عبر relay. يعيش عقد السلك (wire contract) المستند إلى المصدر في عقد Relay ↔ Connector.

      تنفّذ المهايئات واجهة مشتركة:

      • connect() / disconnect() — إدارة دورة الحياة
      • send() — تسليم الرسائل الصادرة
      • تُوحَّد الأحداث الواردة إلى MessageEvent وتُمرَّر عبر handle_message()

      يستخدم التنشيط (wake) الداخلي عبر الدفع gateway.wake.admit_internal_event: لا تزال handle_message() العامة تعيد None، لكن إيصال _gateway_accepted المحلي للعملية الخاص بالحدث لا يُضبط إلا بعد الجدولة أو الإدراج في قائمة الانتظار. المعالِج المفقود، أو مفتاح الجلسة الصريح غير المطابق، أو إسقاط بسبب سقف قائمة الانتظار ليست قبولًا. يجب على المهايئات المخصّصة التي تتجاوز الاستقبال (ingress) تفويض الأحداث الداخلية إلى BasePlatformAdapter.handle_message() (أو تسجيل القبول الفعلي صراحةً)، لا معادلة رد نداء استُهلِك/أُسقِط بالقبول. هذا الإيصال منفصل عن محاسبة تنفيذ نبضات الجلسة (heartbeat)، ولا يتجاوز التفويض أو الإيقاف الطارئ أو حواجز تحضير الدور اللاحقة.

      أقفال التوكن​

      تستدعي المهايئات التي تتصل ببيانات اعتماد فريدة acquire_scoped_lock() في connect() وrelease_scoped_lock() في disconnect(). يمنع هذا وجود profile اثنين يستخدمان نفس توكن البوت في آن واحد.

      يُصدَر تعارض القفل باسم {scope}_lock مع retryable=True بحيث يمكن لإعادة اتصال أثناء التشغيل أن تسترجع عملها بمجرد خروج الحائز الآخر. أما عند بدء التشغيل، فإن وجود حائز أجنبي حيّ يُعدّ تعارض إعداد: تتعرّف gateway/restart.py::is_global_startup_conflict() على عائلات رموز *_lock / lock_conflict، ويوقف موجّه بدء التشغيل المنصّة بشكل fatal بدلًا من وضعها في قائمة إعادة المحاولة. وإن لم يكن هناك شيء آخر متصل، يخرج gateway بالرمز 78 (EX_CONFIG, gateway_state=startup_failed) كي يتوقف supervisor عن إعادة تشغيله: systemd عبر RestartPreventExitStatus=78، و s6 عبر finish→125، و launchd عبر KeepAlive.SuccessfulExit=false بعد أن يحوّل wrapper stderr الرمز 78→0. وبجانب فشل نظير مؤقت فعلًا، يبقى الـ gateway حيًا ويعيد النظير وحده المحاولة.

      مسار التسليم​

      تتعامل التسليمات الصادرة (gateway/delivery.py) مع:

      • الرد المباشر — إرسال الاستجابة عائدةً إلى المحادثة الأصلية
      • التسليم إلى قناة رئيسية (home channel) — توجيه مخرجات مهام cron والنتائج الخلفية إلى قناة رئيسية مضبوطة
      • التسليم إلى هدف صريح — يحدّد محرّك الإرسال هدفًا مثل telegram:-1001234567890، مكشوفًا عبر hermes send CLI لسكربتات الـ shell وعبر أهداف deliver: في cron
      • التسليم عبر منصات مختلفة — التسليم إلى منصّة مختلفة عن منصّة الرسالة الأصلية

      تسليمات مهام cron لا تُرآى (mirror) في سجل جلسة gateway — بل تعيش في جلسة cron الخاصة بها فقط. هذا قرار تصميم متعمَّد لتجنّب انتهاكات تناوب الرسائل.

      Hooks​

      hooks الخاصة بـ gateway وحدات Python تستجيب لأحداث دورة الحياة:

      أحداث hooks الخاصة بـ Gateway​

      الحدثوقت الإطلاق
      gateway:startupبدء عملية gateway
      session:startبدء جلسة محادثة جديدة
      session:endاكتمال الجلسة أو انتهاء مهلتها
      session:resetيعيد المستخدم ضبط الجلسة بـ /new
      agent:startيبدأ الوكيل معالجة رسالة
      agent:stepيُكمل الوكيل تكرارًا واحدًا لاستدعاء أداة
      agent:endينهي الوكيل عمله ويعيد الاستجابة
      command:*تنفيذ أي slash command

      تُكتشَف hooks من gateway/builtin_hooks/ (نقطة توسعة — فارغة حاليًا في التوزيعة المُشحَنة؛ _register_builtin_hooks() جذع (stub) بلا عملية) ومن <profile home>/hooks/ (مثبّتة من المستخدم؛ ~/.hermes/hooks/ للـ profile الافتراضي، ودليل لكل profile مخدوم عند تعدد الإرسال — تُحدّد المسارات وقت الاستدعاء، لا عند الاستيراد مطلقًا). وكل hook دليل به HOOK.yaml وhandler.py.

      تكامل مزوّد الذاكرة​

      عندما تكون إضافة مزوّد ذاكرة (مثل Honcho) مفعّلة:

      1. ينشئ gateway نسخة AIAgent لكل رسالة بمعرّف الجلسة
      2. تُهيّئ MemoryManager المزوّد بسياق الجلسة
      3. تُوجَّه أدوات المزوّد (مثل honcho_profile, viking_search) عبر:
      AIAgent._invoke_tool()
        → self._memory_manager.handle_tool_call(name, args)
          → provider.handle_tool_call(name, args)
      1. عند انتهاء الجلسة أو إعادة ضبطها، تُطلق on_session_end() للتنظيف وتفريغ البيانات النهائي

      دورة حياة تفريغ الذاكرة​

      حدود المحادثة الصريحة (مثل /new, /reset أو /resume) تفرّغ الجلسة الصادرة وتُنهيها. أما وقت الخمول والحدود اليومية فلا تُنهيها أبدًا.

      إخلاء TTL الخاص بالموارد فقط، و LRU ، وإخلاء ضغط الذاكرة، يودِعون النسخة المخزَّنة مؤقتًا من المحادثة لدى مزوّدي الذاكرة المضبوطين قبل تحرير عملاء الوكيل. وهذا لا يُغلق المحادثة الدائمة: يعيد الدور التالي تحميل نفس المحادثة والهوية.

      الصيانة الخلفية​

      يشغّل gateway صيانة دورية جنبًا إلى جنب مع معالجة الرسائل:

      • نبض cron — يتحقّق من جداول المهام ويطلق المهام المستحقة
      • تدبير الجلسات — يستعيد الموارد المخزَّنة مؤقتًا دون إنهاء المحادثات
      • تفريغ الذاكرة — يودِع الذاكرة قبل الإخلاء المؤقت اللين
      • تحديث الذاكرة المؤقتة (cache) — يحدّث قوائم النماذج وحالة المزوّدين

      إدارة العمليات​

      يعمل gateway كعملية طويلة الأمد، تُدار عبر:

      • hermes gateway start / hermes gateway stop — تحكّم يدوي
      • systemctl (على لينكس) أو launchctl (على macOS) — إدارة الخدمات
      • ملف PID في ~/.hermes/gateway.pid — تتبّع عمليات محدَّد بـ profile

      محدَّد بـ profile مقابل عالمي: start_gateway() يستخدم ملفات PID ضمن نطاق الـ profile. في التشغيل المستقل (gateway لكل profile)، hermes -p x gateway stop يوقف gateway الخاص بذلك الـ profile فقط. عند تعدد الإرسال يوجد gateway واحد لكل مضيف، يملكه الـ profile الذي أطلقه (gateway/host_rendezvous.py ينشر PID والموطن ومجموعة الـ profiles المخدومة؛ و gateway/host_attach.py هو قرار الاتصال/إعادة المسح/الرفض الذي يمر عبره كل أمر لدورة الحياة): يُسقط hermes gateway stop على المالك كل الـ profiles المخدومة، ويرفض hermes -p x gateway stop للـ profile الثانوي المخدوم برمز خروج 78 (لأنه لا يملك gateway خاصًا به). ويتصل gateway run ثانٍ لـ profile مخدوم ثم يخرج بـ 0 — أما تحت supervisor للخدمات فيخرج بـ 75 (EX_TEMPFAIL)، كي تُعاد محاولة الوحدة الزائدة بدل تعليقها: "someone else serves me right now" ملاحظة وقت تشغيل تنتهي بانتهاء تلك العملية، وسيترك 78 (الذي تعامله systemd و s6 و launchd كحالة دائمة) الـ profile عالقًا. يتطلب ATTACH إجابة identify حية من المالك؛ فسجل الالتقاء الذي لا توجد وراءه استجابة يثبت وجود مالك، لا أنه يخدمك، لذا ينتج رفضًا مؤقتًا (خروج 75)، لا اتصالًا مطلقًا. والمالك الذي يجيب بـ multiplex: False لإعادة المسح هو gateway مستقل للـ profile الآخر، وليس multiplexer استبعدك: يبدأ الأمر gateway الخاص بهذا الـ profile بجواره (بنية عملية واحدة لكل profile)، ولا يرفض — فالرفض هناك كان يخرج بـ 78 ويعلّق كل وحدات launchd عدا أول وحدة استحوذت على قفل المضيف. hermes gateway stop --all فحص ps aux للبحث عن كل عمليات gateway وقتلها (يُستخدم أثناء التحديثات). ويُحدَّد كون العملية حية بواسطة gateway.status.live_gateway_pid_for_home (PID + بصمة وقت البدء)، لا مجرد وجود PID مطلقًا.

      إشعارات عمليات الخلفية​

      terminal(background=true, notify_on_complete=true) يبدأ مراقب gateway يرصد الإكمال ويفعّل دورًا جديدًا للوكيل. مستوى التفصيل: display.background_process_notifications (أو HERMES_BACKGROUND_NOTIFICATIONS): concise (الافتراضي؛ سطر واحد، وتضيف الإخفاقات نهاية المخرجات)، all (تحديثات أثناء التشغيل + المخرجات الخام النهائية)، result (المخرجات الخام النهائية فقط)، error (المخرجات الخام النهائية فقط عند الخروج غير الصفري)، off.

      يُفعَّل المراقب على حلقة الـ gateway وقت التسجيل (terminal_tool_background.py:: _register_completion_watcher → run_notifications.py::arm_process_watcher); pending_watchers ليس إلا البديل للعمليات المسجلة قبل أن يبدأ الـ gateway الخدمة (استعادة checkpoint) أو أثناء توقفه، وتُصرف عند البدء وبعد الدور. لا ترسل مراقبات agent-notify إقرارًا للمستخدم (فالدور التالي للوكيل هو التقرير)، إلا إذا كان الدور الذي أطلق العملية ما زال يعمل عند خروجها — حينها لا يُدرج الحقن إلا متابعة لاحقة، فيُرسل الإقرار الموجز فورًا.

      يصرف مراقب الإكمال الخامل أيضًا watch_match / watch_disabled؛ ولا تلزم متابعة من المستخدم. ويصرف وضع تعطيل الإشعار هذه العناصر دون إيقاظ. تُعاد محاولة إخفاقات النقل؛ ولا تستهلك الجهات المالكة/وسائل النقل الدائمة غير المتاحة محاولات تسليم. تحتفظ أحداث العمليات ضمن نطاق أسماء الـ profile بالـ adapter المالك لها، بما في ذلك إشعارات التقدم/النتيجة الخام. وقبول adapter يعني قبول الإدخال مرة واحدة على الأقل، لا دليلًا على اكتمال دور نموذج أو رد صادر نهائي. وتبقى الإكمالات غير المتزامنة لخادم API صفوف تسليم دائمة، لا أدوار نموذج جديدة مستقلة مطلقًا. اشترط إقرار admit_internal_event لحقن الإكمال/المراقبة: عودة المعالج بـ None ليست قبولًا. يعيد رفض الإدخال كل عناصر الدفعة الشقيقة المطالب بها دون استهلاك محاولة؛ وتحتفظ أخطاء التسليم الفعلية بسياسة إعادة المحاولة المحدودة. تُحدَّد مسارات API الخام المعروفة بعد مصادر المراسلة المحفوظة، وتؤجّل بصمت عند عدم الإتاحة؛ أما المسارات المشوهة فما زالت تحذّر.

      لتنفيذ cron جلسة خاصة. قد تعكس التسليمات المؤهلة للاستمرار المحادثة المواجهة للرد أو تهيئها: المصدر، أو بديل الموطن دون مصدر، أو موطن المنصة المجرد الذي كتبه المستخدم، أو أهداف صريحة مختارة. ولا تمنح توسعات all أهلية العكس إلى الموطن. وتكون الملخصات المعكوسة أدوار مستخدم معلَّمة تُلحق عند حد الدور، مع الحفاظ على تناوب الأدوار (cron/AGENTS.md).

      /login (خارج الدور، DM مقترنة فقط)​

      /login مسجّل في hermes_cli/commands.py مع busy_policy="dispatch" و desktop="settings"، ومدرج في run_busy.py::_PLAIN_COMMANDS، ويعالجه GatewayLoginCommandsMixin (gateway/slash_commands_login.py). يرفض العمل خارج DM مقترنة: chat_type in {"dm","private"}، و chat_id صادق، ومنصة تكون فيها "dm" محادثة مقترنة فعلًا — إذ تبلغ ntfy و raft و a2a جميعها عن chat_type="dm" لموضوع بث وقناة ووكيل نظير، لذا سينشر وضع رابط موافقة هناك الرابط علنًا.

      يربط التثبيت كله. يكتب تسجيل الدخول providers.nous الوحيد، لذا يملك من يوافق على الرمز inference لهذا الـ gateway وموصلاته لكل محادثة يخدمها. تقييد slash اختياري (gateway/slash_access.py): دون ضبط allow_admin_from، يستطيع كل مستخدم يُسمح له بإرسال DM للبوت تشغيله. ويجب على مشغّلي gateways المشتركة ضبطه.

      يعيد المعالج إقراره فورًا ويصرف anon_auth.run_sign_in على executor خاص ذي عامل واحد (_login_executor)، وليس في مجموعة الـ gateway المشتركة ذات 10 threads مطلقًا — فقد يمتد انتظار الترقية طوال صلاحية الرمز، ويجعل عامل حي في المجموعة المشتركة إيقاف التشغيل يتجاوز إغلاق SessionDB/checkpoint. محاولة واحدة لكل عملية، مختومة بهوية بادئها: يستبدل /login ثانٍ للهوية نفسها المحاولة السابقة (تنتهي الخاسرة بإرسال رسالة الاستبدال إلى محادثتها)؛ وتُرفض هوية مختلفة. لا يستطيع task.cancel() مقاطعة استقصاء حاجب داخل worker thread ، لذا يعمل الإيقاف والاستبدال كلاهما عبر attempt.cancelled، الذي يستقصيه wait_for_promotion الآن كل ≤1 s. ولا ترسل المحاولة الملغاة بسبب الإيقاف شيئًا — فالمهمة تموت وربما اختفت adapters بالفعل — لكن إذا كان الخادم قد أكمل النقل بالفعل، يظل محفوظًا لأن النقل لا رجعة فيه.

      عند الإكمال يطرد المعالج كل وكيل مخزّن مؤقتًا ما زال على nous/welcome ويمسح أي تجاوز لنموذج الجلسة مثبّت عليه. لا يبدّل الوكلاء في موضعهم، ولا يكتب تجاوزًا للنموذج: فقد نقل settle_after_upgrade بالفعل model.default/model.base_url في الإعدادات، ويعيد كل دور تحديد الإعدادات وبيانات الاعتماد، ويفرض _agent_config_signature بالفعل إعادة البناء عندما يتغير المسار — لذا لا يحقق التبديل في الموضع أي فائدة للتخزين المؤقت، وسيثبّت التجاوز access token منتهي الصلاحية لا يحدثه شيء.

      Profiles متعددة في عملية واحدة​

      مع gateway.multiplex_profiles: true ، تخدم عملية واحدة profile الافتراضي وكل مجلد حي تحت profiles/ (hermes_cli/profiles.py::profiles_to_serve(multiplex=True)). os.environ وتحتفظ متغيرات الوحدات العامة بقيم profile الخاص بـ الإطلاق، لذا يربط كل نشاط لـ profile ثانوي نطاقه صراحة — profile يجمع home + نطاق الأسرار + نطاق الطرفية:

      النشاطالربط
      دور موجّهgateway/run.py::_profile_runtime_scope(home) عبر run_turn.py::_profile_scope_for_source
      تحرير الوكيل / إخلاؤه (TTL و LRU وضغط الذاكرة)gateway/run_agent_cache.py::_run_release_in_profile_scope
      الإيقافgateway/run_shutdown.py::_finalize_session
      تسليم الوسائط بعد الدورgateway/platforms/base.py::_media_delivery_scope
      نبضة croncron/scheduler_provider.py::_profile_cron_scope(home) (مؤقّت واحد، و profiles بالتتابع)
      العمليات الفرعية (عمّال hermes -p X وأدوار relay و drivers المتصفحات)tools/environments/local.py::served_profile_child_env
      خيوط الخلفيةagent/memory_provider.py::spawn_context_thread

      تفشل قراءة الأسرار بطريقة مغلقة (يثير agent.secret_scope.get_secret الاستثناء UnscopedSecretError) فقط بعد set_multiplex_active(True) ، الذي يضبطه gateway و cron و gateway migrate و backend الخاص بـ Desktop/لوحة التحكم serve. لا يصل YAML الخاص بالمحوّل إلى os.environ في multiplex: يملأ gateway/platforms/_shared.py::apply_yaml_bridge قيمة PlatformConfig.extra ويتخطى الكتابة إلى environ تحت نطاق profile ثانوي؛ وتقرأ البوابات عبر platform_gate_env. تعمل منصات الاستقبال المشترك (WhatsApp bridge و Relay) على profile الافتراضي وحده؛ وإذا فعّل profile ثانوي إحداها، يُسجّل ذلك مرة ويُثبت في حالة وقت التشغيل (run_adapters.py::_note_unserved_secondary_platform). العزل لكل profile كما يراه المستخدم: Gateways متعددة Profiles § ما يُعزل لكل profile.

      تحميل الإضافات أثناء التشغيل​

      الإضافات التي تُحمّل بعد اتصال المحوّلات (التثبيت/التفعيل من CLI أو Desktop أو لوحة التحكم أو plugins.manage ؛ إعادة اكتشاف قسرية تُطلقها أداة) تعيد توصيل معالجات المنصات دون إعادة التشغيل (#87770). المكونات، وكلها في gateway/run_plugin_rewire.py:

      • مستمع الاكتشاف — _start_recover_previous_run يشترك بـ PluginManager.on_plugin_loaded لـ profile الإطلاق، ويفعل _load_secondary_profile_config ذلك لكل profile مخدوم. ينطلق الحدث من داخل discover_and_load (لا من RPC مطلقًا) للإضافات المحمّلة حديثًا؛ وينتقل callback إلى حلقة gateway باستخدام call_soon_threadsafe.
      • إعادة توصيل ثابتة الأثر عند التكرار — BasePlatformAdapter.rewire_plugin_handlers() يعيد قراءة get_platform_handler_factories(platform) ويشغّل فقط المصانع التي لم تُوصل بعد على العميل الأصلي الحي (بالمفتاح (plugin, qualname) لأن إعادة التحميل القسرية تعيد كائنات دوال جديدة). يرفع Telegram المعالجات المضافة قبل معالجات الجوهر الشاملة؛ ويعيد Slack أيضًا تسجيل callbacks الخاصة بـ register_slack_action_handler المفقودة مرة لكل AsyncApp.
      • reload-plugins فعل التحكم — تطلب عمليات أخرى (hermes plugins install, hermes serve) من gateway الجاري إعادة فحص home المطلوب (والمخدوم) قسرًا؛ وتتضمن الإجابة plugins و activations و adapters_rewired لكل إضافة، ليتمكن المستدعي من قول "نشطة الآن" بصدق.
      • حدود النطاق — المعالجات فقط. تنتظر أدوات الإضافة المتأخرة وأقسام system prompt الخاصة بها الجلسة التالية (ثابت ذاكرة الـ prompt المؤقتة)؛ وتنتظر خوادم MCP المحمولة mcp.reload. لا يُفصل شيء عند التعطيل.

      مراقبة Gateway

      مراقبة سلامة الخدمة مع تشخيصات تشغيلية منظّمة لـ daemon الخاص بـ Hermes gateway، تُصدَّر عبر OTLP/HTTP إلى endpoint يضبطه المشغّل (OpenTelemetry Collector أو DataDog أو أي مستقبل OTLP).

      هذه الطبقة خالية من المحتوى بحكم تصميمها. تصدّر حالة دورة حياة الـ gateway و cron، وسلامة موصّلات المنصات، وتشخيصات التحذير/الخطأ الخالية من المحتوى. ولا تصدّر أبدًا prompts أو رسائل أو وسائط الأدوات ونتائجها أو أسماء المهام أو وجهاتها أو جداولها أو الأخطاء الخام أو سجل الجلسات أو تحليلات الاستخدام أو سجلات التدقيق أو تتبعات التنفيذ التفصيلية. التقاط trajectories التشغيل/النموذج/الأداة طبقة منفصلة يقدّمها تكامل Hermes الأصلي مع NeMo Relay SDK ومشتركو Relay أو مصدّروه المضبوطون صراحةً.

      ما يُصدَّر​

      الإشارةمسار OTLPالمحتوى
      مقاييس Gateway/v1/metricshermes.gateway.up/state/busy/drainable/active_agents/background_work/background_delegations/restart_requested، hermes.platform.up/degraded مع خصائص error_code محدودة
      أحداث السلامة/دورة الحياة/v1/tracesgateway.lifecycle وانتقالات حالته (starting -> running -> draining -> stopped، startup_failed، والخروج)، gateway.health_snapshot، وتغيّرات حالة المنصات
      التشخيصات/v1/logsأحداث تحذير/خطأ الـ gateway ذات متن ثابت وخصائص محدودة للنظام الفرعي والشدة وفئة الخطأ ورمزه؛ لا تُصدّر رسائل السجل المصاغة مطلقًا
      مقاييس مجدول Cron/v1/metricsنبض ticker وعمر آخر نجاح (يُحذف إن لم يتوفر)، وعدّاد تزايدي لمرات التعويض من فرع النافذة القديمة في المجدول، وعدد المهام المفعّلة/الجارية، وعدد المتأخرة المشتق من next_run_at المحفوظ مع قاعدة السماح الحالية في المجدول
      دورة حياة تنفيذ Cron/v1/tracesحالات claimed/running/completed/failed/unknown الدائمة، ومصدر وفئة خطأ محدودان، ومفتاح مهمة معتم ذي بصمة، والمدة المنقضية إن توفرت الطوابع الزمنية، ونتيجة التسليم حين يعرفها المجدول؛ تحاول الحالات النهائية تفريغًا يستمر معه التشغيل عند الفشل وقد يؤخر الإكمال حتى ثانية واحدة

      تحمل الإشارات service.name والإصدار ووضع الإشراف وبصمة أحادية الاتجاه ثابتة لمعرّف التثبيت، ليتمكن المشغّل من تمييز النُّسخ دون تصدير هوية الحساب/الـ profile أو معرّف التثبيت الخام.

      hermes.gateway.active_agents و hermes.gateway.background_work و hermes.gateway.background_delegations متكاملة. يحسب active_agents أدوار رسائل الواجهة إضافةً إلى مهام cron الجارية وتشغيلات API — العمل الذي يستنزفه الـ gateway عند الإيقاف. ويحسب background_work العمل المنفصل الذي لا يتضمنه active_agents مطلقًا: subagents العاملة في الخلفية عبر delegate_task وعمليات terminal(background=true) وعمّال kanban؛ ويكون العدّ على مستوى المهام — دفعة تفريع من N subagents تُحسب N — لذا يعكس الحمل المتزامن الحقيقي للـ subagents. ولا يحسب background_delegations إلا وحدات التفويض غير المتزامن (كل إرسال عبر delegate_task وحدة واحدة، ودفعة التفريع وحدة واحدة)، بما يطابق حساب السعة في المجمّع غير المتزامن؛ قارنه في التنبيهات بـ delegation.max_concurrent_children لمعرفة الضغط على الخانات. اجمع active_agents و background_work للحصول على إجمالي العمل النشط لكل نسخة؛ واستخدم background_delegations لتشبّع المجمّع.

      التفعيل​

      # config.yaml
      monitoring:
        gateway_health_export:
          enabled: true
        export:
          otlp:
            enabled: true
            endpoint: http://collector-host:4318/v1/traces   # metrics/logs derive
            headers_env: {}   # header name -> ENV VAR NAME (values never stored)

      تحقّق من الوضع في أي وقت:

      hermes monitoring status

      تنتمي OpenTelemetry SDK إلى الإضافة (extra) otlp وتُثبّت عند الاستخدام الأول حين تسمح السياسة. لطلبها صراحةً من نسخة مسحوبة مجهّزة، نفّذ python -c "import pm; pm.sync_venv(['otlp'], explicit=True)". عند غياب SDK أو تعطل endpoint، يواصل الـ gateway عمله دون تأثر: يبقى جمع المقاييس وتصدير الأحداث العادية خارج المسار الحرج، بينما تحاول أحداث cron النهائية تفريغًا واحدًا محدودًا يستمر معه التشغيل عند الفشل لمدة أقصاها ثانية واحدة، لتقليل احتمال فقدان الحالة النهائية.

      يعمل بالطريقة نفسها تحت إشراف systemd/launchd/s6 أو في الحاويات أو tmux أو عند تشغيل hermes gateway run ببساطة: يوجد المصدّر داخل عملية الـ gateway، فلا يلزم sidecar أو وكيل أو collector على المضيف.

      الجمع في DataDog​

      شغّل OpenTelemetry Collector يملكه العميل ومرّر:

      # otel-collector config
      receivers:
        otlp:
          protocols:
            http:
      exporters:
        datadog:
          api:
            key: ${env:DD_API_KEY}
      service:
        pipelines:
          metrics:   {receivers: [otlp], exporters: [datadog]}
          traces:    {receivers: [otlp], exporters: [datadog]}
          logs:      {receivers: [otlp], exporters: [datadog]}

      وجّه monitoring.export.otlp.endpoint إلى collector. يجب أن تستند التنبيهات إلى hermes.gateway.up و hermes.platform.up و hermes.platform.degraded.

      استعلامات وتنبيهات عامة لأسطول النُّسخ​

      تعتمد الصياغة الدقيقة على backend الرصد لدى العميل. تستخدم الأمثلة التالية تعبيرات بأسلوب PromQL وتتجنب عمدًا التوجيه والوجهات وجرد العملاء الخاصة بمزوّد معيّن.

      جمّع عروض الأسطول بحسب خاصية المورد المعتمة service.instance.id. لا يمكن لعملية انتهت أن تصدر قيمة صفر خاصة بها، لذلك يحتاج كل نشر إلى كشف الحالة الصريحة وكشف السلاسل الغائبة معًا.

      # Explicit gateway failure.
      hermes_gateway_up == 0

      # Box disappeared or stopped exporting. Choose a window longer than the
      # configured export interval and collector retry allowance.
      absent_over_time(hermes_gateway_up[5m])

      # Locally owned bridge is explicitly down.
      hermes_platform_up == 0

      # Scheduler thread is stale even though the gateway may still be alive.
      hermes_cron_scheduler_heartbeat_age_seconds > 180

      # Ticker loops but has not completed a successful tick recently.
      hermes_cron_scheduler_last_success_age_seconds > 300

      # One or more jobs are beyond their existing scheduler grace window.
      hermes_cron_jobs_overdue > 0

      # Catch-up counter increased, proving at least one stale occurrence was
      # collapsed and run once after a delay.
      increase(hermes_cron_scheduler_catch_up_occurrences[15m]) > 0

      تصل سجلات دورة حياة تنفيذ cron على شكل spans من نوع hermes.cron_execution. أنشئ تنبيهات أو اشتق أحداثًا من خصائص محدودة مثل:

      hermes.status = failed|unknown
      hermes.delivery_outcome = failed|not_configured
      hermes.error_class = auth_failed|rate_limited|timeout|network_error|
                           dispatch_failed|interrupted|empty_response|
                           invalid_config|unknown

      عروض موصى بها للمشغّل:

      1. صف واحد لكل service.instance.id مع حالة الـ gateway والمنصات المحلية المضبوطة؛
      2. نبض المجدول، وعمر آخر نجاح، وعدد المهام الجارية والمتأخرة، وزيادة التعويض؛
      3. خلاصة دورة حياة cron لا تُفهرس إلا بالمفتاح المعتم hermes.job_key؛
      4. تنبيهات منفصلة لغياب الجهاز، وتعطل الجسر المحلي، وتقادم المجدول، وفشل/جهالة cron، وفشل التسليم، ونشاط التأخر/التعويض.

      احتفظ بحدود التنبيه وتوجيهه في إعدادات يملكها النشر. لا تضف أسماء المهام أو prompts أو المخرجات أو الجداول أو الوجهات أو الأخطاء الخام أو أسماء profiles أو هوية الحساب لمجرد تسهيل قراءة لوحة التحكم.

      سيناريوهات التحقق من الإصدار​

      قبل قبول نشر، افتعل الحالات الخمس جميعها وتحقّق منها عبر collector و backend الفعليين:

      1. نجاح Cron: راقب claimed -> running -> completed والمدة ونتيجة تسليم صادقة.
      2. فشل Cron: راقب failed مع فئة خطأ محدودة، دون استثناء خام أو محتوى في حمولة OTLP المفكوكة.
      3. مقاطعة Cron: أوقف الـ gateway المسؤول أثناء التنفيذ، وأعد تشغيله، وراقب الاسترداد إلى unknown.
      4. انقطاع جسر مملوك محليًا: عطّل موصّلًا أصليًا واحدًا، وراقب حالته المحدودة down/retrying/fatal واسترداده، وتحقّق من استمرار سلامة الأجهزة الأخرى.
      5. إنهاء Gateway: أنهِ نسخة canary واحدة، وتحقق من كشف السلاسل الغائبة، وأعد تشغيلها، وأكّد عودة هوية النسخة المعتمة نفسها.

      تظل سلامة نقل Relay الذي يملكه Hermes Agent ضمن النطاق. وتبقى خدمة gateway أو موصّل منفصلة المرجع المعتمد لأي حالة منصات مشتركة متصلة تملكها، ويجب أن تصدّر تلك الحالة عبر مسار قياساتها الخاص.

      في كل سيناريو، تحقّق من زوال الإشارة والتنبيه عند الاسترداد، وعدم تأثر الأجهزة الأخرى، واستمرار التشغيل عند فشل collector، وخلو المقاييس و spans والسجلات وخصائص الموارد المفكوكة من المحتوى.

      اختبار محلي سريع (دون Docker)​

      # terminal 1: capture collector on :4318
      python scripts/observability/otel_capture_collector.py \
        --host 127.0.0.1 --port 4318 --log ~/.hermes/cache/scratch/hermes_otel_capture.jsonl

      # terminal 2: drive the real exporter through lifecycle transitions,
      # a fatal platform, and a structured warning event, then flush
      python scripts/observability/gateway_health_export_probe.py \
        --endpoint http://127.0.0.1:4318/v1/traces \
        --log ~/.hermes/cache/scratch/hermes_otel_capture.jsonl --wait 8
      # exit 0 prints: {"requests": 6, "paths": ["/v1/logs", "/v1/metrics", "/v1/traces"]}

      صيانة هذه الطبقة وتوسعتها​

      تستخدم هذه الطبقة مفردات ثابتة ومعدّدة وخالية من المحتوى بحكم تصميمها. لا تعني إضافة إشارة مجرد "إصدار مقياس جديد" — بل يجب التصريح بكل اسم وخاصية جديدين في كل طبقة تفرض المفردات المحدودة، وإلا يُحذفان بصمت لاحقًا. اتبع قائمة التحقق الملائمة لتغييرك. القاعدة الذهبية: الإشارة الجديدة التي تُصدَر دون التصريح بها في كل طبقة تبدو كخطأ في الكود، لكنها خطأ في تسجيل المفردات — لا يظهر خطأ، بل لا تصل الإشارة مطلقًا.

      شرط الخلو من المحتوى (ينطبق على كل تغيير)​

      قبل إضافة أي شيء، أكّد أنه لا يمكنه حمل محتوى. الأرقام والقيم المنطقية والأعمار والمدد والعدّادات التزايدية والبصمات أحادية الاتجاه آمنة. لا تضف أبدًا خاصية يمكن أن تحمل اسم مهمة أو prompt أو مخرجًا أو جدولًا أو وجهة أو نص استثناء خامًا أو مسار ملف أو اسم profile أو معرّف حساب أو سلسلة حرة. عندما تحتاج إلى ربط سجل بمهمة/كيان، احسب بصمته (sha256(...)[:24]، راجع _job_key في agent/monitoring/cron_health.py) — لا تُصدر المعرّف الخام مطلقًا. يجب أن تمر كل الخصائص النصية التي قد تمسّ مدخلات المستخدم عبر redaction.redact_for_export وأن تُقتطع (راجع _span_attrs في agent/monitoring/otlp_exporter.py).

      إضافة مقياس جديد​

      1. أصدره في منشئ اللقطات (agent/monitoring/gateway_health.py build_gateway_health_snapshot أو cron_health.py build_cron_health_snapshot أو قارئ مماثل موصول بـ _read_runtime_snapshot في gateway_health_export.py). بأفضل جهد: لا تسمح لأي قارئ برفع استثناء إلى حلقة الجمع — أحِطْه بمعالجة وسجّل WARNING خاليًا من المحتوى يحمل اسم نوع الاستثناء فقط (النمط الذي تستخدمه قارئات cron والعمل في الخلفية)، ليظهر أي تراجع لاحق بدلًا من إسقاط الإشارة بصمت.
      2. سجّل اسم المقياس المفصول بنقاط في قائمة metric_names الخاصة بالمقاييس القابلة للرصد في gateway_health_export.py::_start_metric_provider. لا يُرصد مطلقًا المقياس الذي يُصدر في اللقطة دون تسجيله هنا.
      3. أضف صفًا في جدول التصدير ومثال تنبيه في هذا الملف.
      4. إذا وضع النشر أمام المصدّر OpenTelemetry Collector يستخدم قائمة سماح بأسماء المقاييس (معالج filter/... مع شروط name != "...")، فأضف الاسم الجديد هناك أيضًا — وإلا يُسقطه collector قبل وصوله إلى backend. ليس ذلك كودًا في المستودع، لكنه السبب الأكثر شيوعًا لعدم ظهور مقياس جديد صُدر بصورة صحيحة؛ اذكره في PR كي يحدّث المشغّل إعدادات collector.

      إضافة نظام فرعي جديد (عائلة إشارات جديدة)​

      اتبع نمط cron (cron_health.py + توصيله): ضع منطق القراءة/الإسقاط في وحدة خاصة به، وأتِح build_<subsystem>_health_snapshot() واحدة تُرجع كائنات GatewayMetric محدودة (وأحداثًا إن وجدت)، وألحقها بـ _read_runtime_snapshot مع حارس try/except-WARNING نفسه بأفضل جهد. ثم اتبع قائمة "إضافة مقياس" لكل اسم جديد، وقائمة "إضافة خاصية" لكل خاصية حدث جديدة. أضف سيناريو تحقق من الإصدار أدناه لنمط فشل النظام الفرعي.

      توسيع مفردات فئة الخطأ / الحالة / المصدر / الوضع​

      هذه هي التعدادات المغلقة التي تُبقي الطبقة محدودة. وسّع SET ثم المصنّف، ولا تعدّل أحدهما دون الآخر:

      • Cron (agent/monitoring/cron_health.py): _KNOWN_STATUSES و _KNOWN_SOURCES و _KNOWN_DELIVERY_OUTCOMES وفئات الكلمات المفتاحية في classify_cron_error. يُحوّل أي شيء خارج المجموعة إلى unknown عند الخروج، فلا تظهر قيمة جديدة لم تُضف إلى المجموعة.
      • Gateway/المنصة (agent/monitoring/gateway_health.py): _KNOWN_GATEWAY_STATES و _KNOWN_PLATFORM_STATES و classify_gateway_error.

      القواعد: أبقِ المفردات صغيرة وذات معنى تشغيلي (يجب أن تقابل فئة الخطأ إجراءً للمشغّل، لا صنف استثناء فرعيًا)؛ يجب أن تطابق الفئة الجديدة كلمة مفتاحية ثابتة، لا نص رسالة قد يتغير؛ حدّث قائمة hermes.error_class = ... في قسم التنبيهات بهذا الملف واختبار الوحدة للتعداد كي يُتحقق من العقد، لا أن يُجمّد كعدد.

      إضافة خاصية خالية من المحتوى إلى حدث/span قائم​

      أضف المفتاح إلى قائمة السماح keep_by_kind الخاصة بكل نوع لدى المصدّر في agent/monitoring/otlp_exporter.py::_span_attrs (تُحذف المفاتيح غير المدرجة)، ومرّره عبر إخفاء البيانات إن كان نصيًا في أي وقت؛ وكما في المقاييس، إذا كانت لدى collector النشر قائمة سماح keep_keys(...) بخصائص spans، فأضف الخاصية هناك أيضًا وإلا تُحذف أثناء النقل.

      التحقق من السلسلة كلها، لا الإصدار وحده​

      الإصدار ضروري لكنه غير كافٍ. أكّد بقاء الإشارة وصولًا إلى backend، لأن التعدادات وتسجيل metric_names وقائمة سماح خصائص المصدّر وأي قائمة سماح في collector تُسقط كلٌّ منها القيم غير المدرجة دون خطأ:

      hermes monitoring status                 # posture
      python scripts/observability/gateway_health_export_probe.py \
        --endpoint http://127.0.0.1:4318/v1/traces \
        --log ~/.hermes/cache/scratch/cap.jsonl --wait 8          # drive the real exporter

      فك حمولة OTLP الملتقطة وأكّد وجود الاسم/الخاصية الجديدين وعدم تسرب أي محتوى معًا. عندما يوجد collector فعلي أمامها، أضف مدخلات قائمة السماح وأعد التحقق مقابل backend، لا الالتقاط المحلي وحده.

      الحدود وخريطة الطريق​

      تُتيح CLI الخاصة بـ hermes monitoring عمدًا status فقط. يغطي هذا الإصدار الأول إشارات سلامة الخدمة والتشخيص التشغيلي المملوكة لـ Hermes Agent فقط، بما فيها سلامة نقل Relay المملوكة له. وتخرج صراحةً حالة الموصّلات/المنصات المشتركة المعتمدة لدى Team Gateway عن النطاق، وكذلك تحليلات المنتج وتقارير التدقيق/الجودة وتتبعات التنفيذ التفصيلية. يجري تصميم مقاييس استخدام العملاء المشتركة وقياسات التتبع المؤسسية ضمن تكامل NeMo Relay بحدود خاصة للموافقة والسياسة والتصدير؛ وتبقى طبقة المراقبة هذه ضيقة ليتمكن المشغّل من تفعيلها دون المساس بأي إشارة تحمل محتوى. وقد يُعاد تنظيم واجهة القياسات عند اكتمال ذلك.

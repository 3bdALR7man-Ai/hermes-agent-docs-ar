      بناء إضافة مزوّد ذاكرة (Memory Provider Plugin)

      تمنح إضافات مزوّدي الذاكرة Hermes Agent معرفة دائمة عبر الجلسات تتجاوز MEMORY.md وUSER.md المدمجين. يغطي هذا الدليل كيفية بناء واحدة.

      نصيحة

      مزوّدو الذاكرة هم أحد نوعين من إضافات المزوّد (provider plugin). الآخر هو إضافات Context Engine، التي تستبدل ضاغط السياق المدمج. يتبع كلاهما النمط نفسه: اختيار أحادي، مبني على الإعدادات، يُدار عبر hermes plugins.

      تخطيطات التثبيت​

      يكتشف Hermes مزوّدي الذاكرة من أربعة مصادر، بترتيب الأولوية هذا:

      المصدرالموقعملاحظات
      مضمّن (Bundled)plugins/memory/<name>/يُشحَن مع Hermes. مغلق أمام مزوّدين جدد — راجع CONTRIBUTING.
      المستخدم (User)$HERMES_HOME/plugins/<name>/يضعه المستخدم، لكل profile.
      المشروع (Project)./.hermes/plugins/<name>/اختياري (opt-in) عبر HERMES_ENABLE_PROJECT_PLUGINS=1.
      الحزمة (Package)hermes_agent.memory_providersنقطة دخول توزيعة يوفّرها مالك التثبيت؛ لا حاجة إلى نسخ شيء.

      المصادر السابقة تفوز عند تصادم الأسماء، بحيث لا يمكن لدليل يُوضع في شجرة عمل حجب مزوّد مُشحَن أبدًا.

      ملاحظة

      هذا عكس ترتيب "الأحدث يفوز" في نظام الإضافات العام. يُفعَّل مزوّد الذاكرة بـالاسم (memory.provider)، لذا فإن الحجب قد يعيد توجيه ذاكرة الوكيل بصمت بدلًا من مجرد استبدال أداة.

      الاكتشاف يعدّد فقط — ولا يستورد مزوّدًا مطلقًا. لا يعمل شيء حتى يسمّيه memory.provider.

      لا يثبّت اكتشاف نقاط الدخول الحزم. لا تحقن مزوّدًا في البيئة التي اختارها Hermes باستخدام pip. في التثبيتات التي يديرها PM، وزّع مزوّدًا بالدليل مع إعلان اعتماديات Python؛ يجهّز قبول الإضافات و hermes memory setup تلك الاعتماديات عبر PM قبل الاستخدام. يمكن للبنى التي يديرها المالك (مثل Nix) تضمين توزيعة نقطة دخول بصورة تصريحية.

      يشترك إعداد CLI ولوحة التحكم في تجهيز المرشحين. يضم PM ملف pyproject.toml أو الملف القديم pip_dependencies / python_dependencies الخاص بالمزوّد مع اتحاد الإضافات النشط؛ ولا تتجاوز الوحدة القابلة للاستيراد قيود الإصدارات المعلنة. تفحص جاهزية لوحة التحكم المدخلات نفسها دون تثبيت أي شيء. قد يتطلب نجاح التجهيز إعادة تشغيل Hermes قبل أن تستطيع العملية الجارية استخدام جيل الاعتماديات المختار. تظل فحوصات sidecar الخارجية وأوامر الإعداد منفصلة عن اتحاد Python.

      مزوّد بالدليل (Directory Provider)​

      يعيش مزوّد الدليل في plugins/memory/<name>/ عندما يكون مضمَّنًا مع Hermes، وفي $HERMES_HOME/plugins/<name>/ عندما يثبّته مستخدم، أو في ./.hermes/plugins/<name>/ لمزوّد محلي بالمشروع:

      plugins/memory/my-provider/
      ├── __init__.py      # MemoryProvider implementation + register() entry point
      ├── plugin.yaml      # Metadata (name, description, hooks)
      └── README.md        # Setup instructions, config reference, tools

      مزوّد مُحزَّم (Packaged Provider)​

      ينشر مزوّد مثبَّت عبر pip نقطة دخول في مجموعة hermes_agent.memory_providers. اسم نقطة الدخول هو اسم المزوّد الذي يختاره المستخدمون في memory.provider؛ وقيمتها تشير إلى دالة register(ctx) الخاصة بالمزوّد:

      pyproject.toml
      [project.entry-points."hermes_agent.memory_providers"]
      my-provider = "my_provider:register"

      اجعل نقطة الدخول تشير إلى الحزمة، أو إلى register(ctx) داخلها، واحتفظ بتنفيذك ومهاراتك ومواردك الأخرى في تخطيط حزمة Python العادي. لا حاجة لأي نسخ تحت $HERMES_HOME/plugins/.

      تحصل نقطة دخول الحزمة على كل ما يحصل عليه تثبيت الدليل، بما في ذلك الملفان اللذان يقرأهما Hermes من القرص بدلًا من استيرادهما — config_schema.py (لوحة إعدادات لوحة التحكم) وcli.py (أوامر hermes <provider> الفرعية الخاصة بك). يوجد كلاهما بجانب __init__.py الخاص بحزمتك، لذا اجعل نقطة الدخول تشير إلى حزمة بدلًا من وحدة (module) واحدة إذا شحنت أيًا منهما.

      الصنف المجرد MemoryProvider​

      تنفّذ إضافتك الصنف الأساسي المجرد (abstract base class) MemoryProvider من agent/memory_provider.py:

      from agent.memory_provider import MemoryProvider
      from agent.secret_scope import get_secret

      class MyMemoryProvider(MemoryProvider):
          @property
          def name(self) -> str:
              return "my-provider"

          def is_available(self) -> bool:
              """Check if this provider can activate. NO network calls."""
              return bool(get_secret("MY_API_KEY"))

          def initialize(self, session_id: str, **kwargs) -> None:
              """Called once at agent startup.

              kwargs always includes:
                hermes_home (str): Active HERMES_HOME path. Use for storage.
              """
              self._api_key = get_secret("MY_API_KEY") or ""
              self._session_id = session_id

          # ... implement remaining methods

      سياق التهيئة​

      AIAgent يمرّر سياق الجلسة عبر MemoryManager.initialize_all() إلى initialize(session_id, **kwargs). اقبل **kwargs وتقبّل غياب الحقول الاختيارية؛ فقد يهيّئ المستدعون مزوّدًا دون وكيل أو قاعدة بيانات جلسات.

      الكلمة المفتاحيةالمعنى
      hermes_homeدليل تخزين الـ profile النشط.
      platformواجهة الجلسة، مثل cli, gui, acp أو telegram.
      session_titleعنوان الجلسة المخزّن إن توفر. ليس عنوان العرض بالضرورة هوية اختارها المستخدم.
      session_title_sourceمصدر العنوان المخزّن إن توفر: derived, llm أو user. يجب ألا تُخلَط المصادر التلقائية مع تجاوزات الهوية الصريحة؛ ويُبقي غياب معلومات المصدر السلوك القديم للمزوّد. توجد الثوابت المشتركة في hermes_state_common.py.
      cwdمساحة عمل منطقية غير فارغة مقدّمة باسم AIAgent(cwd=...) ومتاحة قبل تهيئة المزوّد. تُحذَف عند قيمة None أو سلسلة فارغة.
      gateway_session_keyهوية ثابتة لمحادثة المراسلة لعزل الجلسات لكل محادثة.
      user_id, user_id_alt, user_name, chat_idحقول هوية gateway، تُضمَّن عند وجودها.
      agent_identityاسم الـ profile النشط إن توفر.
      agent_workspace, agent_contextنطاق الوكيل وقت التشغيل. قيمة agent_workspace هي hermes; agent_context هي cron لتشغيلات المجدول و subagent للعمليات الفرعية لـ delegate_task، وإلا فهي primary — تجاوز الكتابات التلقائية للقيم غير الأساسية.

      لا تفترض أن os.getcwd() يحدد مساحة عمل المحادثة: يمكن لـ backend واحد في Desktop أو gateway خدمة عدة جلسات. إذا غابت cwd واحتجت إلى توجيه الأدلة، تلتزم agent.runtime_cwd.resolve_agent_cwd() بسياق cwd للجلسة ثم قيمة terminal.cwd المحددة النطاق (المحمولة داخليًا باسم TERMINAL_CWD) ثم دليل الإطلاق. لا تتطلب بيانات مساحة العمل الوصفية عند الإنشاء تغيير cwd للعملية ولا إعادة بناء system prompt لمحادثة موجودة.

      تزامن تغييرات مساحة العمل في Desktop/TUI قيمة session_cwd للوكيل الحي عبر tui_gateway/session_workdir.py::_register_session_cwd، بما في ذلك عند إلحاق وكيل مؤجل بعد نقل مساحة العمل. يتيح ذلك لجلسة Codex app-server الأولى أو المعاد تشغيلها استخدام مساحة العمل الحالية بدل cwd وقت الإنشاء. لا ينقل thread في Codex تعمل بالفعل، ولا يعيد تهيئة مزوّدي الذاكرة ولا يغيّر هوية جلسة Honcho موجودة، ولا يُبطل system prompt المخزّن مؤقتًا. تظل تهيئة المزوّد تتلقى مساحة عمل وقت الإنشاء؛ ويظل cwd الغائب أو الفارغ غير مثبّت.

      نتائج prefetch كبيرة الحجم بشكل زائد​

      تُعاد نتائج prefetch() الخارجية كاملةً افتراضيًا، مع الحفاظ على الاسترجاع المرتّب حسب الصلة للمزوّد، حتى سقف أمان قدره 10× hooks.output_spill.max_chars (100,000 حرف على الأقل)، وفوقه تظل تُحفَظ في ملف فائض. أبقِ ميزانية الاسترجاع الخاصة بك أدنى من ذلك بكثير. لتفعيل حفظ النتائج كبيرة الحجم في ملفات فائض للـ profile النشط، اضبط:

      memory:
        prefetch_spill_enabled: true  # default: false

      عند التفعيل، تُكتَب النتائج التي تتجاوز عتبة hooks.output_spill.max_chars المشتركة (الافتراضي 10,000 حرفًا) إلى ملف فائض خاص، وتُستبدَل بمعاينة البداية/النهاية المضبوطة مع مساره. تحتفظ المعاينة الافتراضية بأول وآخر 500 حرف فقط؛ ويجب على النموذج قراءة الملف لاستعادة الوسط. تظل النتائج عند العتبة أو دونها دون تغيير.

      تظل أطوال معاينة hooks.output_spill المشتركة ودليلها سارية، وتعطّل hooks.output_spill.enabled: false حفظ الفائض حتى مع تفعيل خيار الذاكرة. يُلتقَط الإعدادان عند تسجيل المزوّد الخارجي؛ أعد تشغيل Hermes لتطبيق التغييرات على الجلسات الحالية. لا تتأثر الذاكرة المدمجة ولا آلية حفظ الفائض المعتادة في hooks الإضافات. راجع الإضافات — فيضان السياق الزائد الحجم.

      نقاط تفتيش ما قبل الضغط (فشل بأمان)​

      on_pre_compress() بأفضل جهد افتراضيًا: إذا أطلق مزوّدك استثناءً، يسجّل المضيف الإخفاق ويستمر الضغط. هذا هو الافتراضي الصحيح لاستخلاص الرؤى — والافتراضي الخاطئ لمزوّد مهمته أرشفة أدلة النص الكامل إلى مخزن دائم قبل إعادة الكتابة المُفقِدة (lossy). لهذه الحالة يقدّم المضيف عقد نقطة تفتيش اختياري (إصدار API v2):

      from agent.memory_provider import MemoryProvider

      class MyArchivingProvider(MemoryProvider):
          # Opt in: every successful on_pre_compress() return means the durable
          # checkpoint is committed. Raise on any failure — do not return partial
          # success. Version 1 (the inherited default) is the implicit historical
          # contract: best-effort semantics, raw message list.
          pre_compress_checkpoint_api_version = 2

          def on_pre_compress(self, messages, *, require_checkpoint=False):
              # require_checkpoint mirrors the operator's checkpoint_required
              # setting: True means a raise here blocks the lossy rewrite.
              ids = self._archive(messages)   # must be durable before returning
              return f"checkpoint: {ids}"     # forwarded into the summary prompt

      يفعّل المشغّلون هذا الفرض لكل نشر:

      compression:
        checkpoint_required: true   # default: false

      مع تفعيل هذا التقييد، يفشل الضغط بأمان قبل أي إعادة كتابة مُفقِدة ما لم يكمل مزوّد نشط يعلن عن الـ API نقطة تفتيشه: يُحفَظ النص الكامل غير المضغوط، وتخفق محاولة الضغط برمز BLOCKED_MISSING_PREREQUISITE، ويمكن إعادة المحاولة بمجرد أن يتعافى مخزنك. مع تعطيل هذا التقييد (الافتراضي)، لا يتغير شيء بالنسبة للمزوّدين الحاليين.

      لا يعلن أي مزوّد مضمّن مع Hermes عن checkpoint API v2 — فالعقد اختياري وموجود لمزوّدي الأرشفة الخارجيين. لذا فإن تفعيل checkpoint_required دون مزوّد كهذا يمنع كل محاولة ضغط (يدوية وتلقائية): تسجّل تهيئة الوكيل تحذيرًا يسمّي المزوّد النشط، ويسمّي كل رفض compression.checkpoint_required بوصفه المفتاح الذي ينبغي تعطيله.

      يرتبط التقييد بكل جهة مخوّلة بالضغط، لا بمُلخّص Hermes وحده: يُمنَع الضغط الأصلي من جانب الخادم (compression.codex_responses_native) بينما التقييد مسلَّح، ويُجبَر الضغط الدقيق بعد الدور (post-turn micro-compaction) (compression.micro_compact) على الإيقاف عند تهيئة الوكيل (فهو يمتصّ التبادلات القديمة في ملخّص متجدد بلا نقطة ربط لنقطة تفتيش في مساره)، ويُرفَض وضع API الخاص بـ codex_app_server عند تهيئة الوكيل — إذ يضغط وكيل codex سلسلته الخاصة بلا حد صادق لما قبل الضغط، لذا لا يمكن ضمان نقطة تفتيش مطلوبة هناك. يبقى ضاغط Hermes الواعي بنقاط التفتيش السلطة المُفقِدة الوحيدة.

      ما يستقبله مزوّدك يعتمد على إصدار API المُعلَن. مزوّدو الإصدار 1 (الافتراضي الضمني — كل مزوّد موجود مسبقًا) يحتفظون بالعقد التاريخي: قائمة الرسائل الخام، تمامًا كما كانت. مزوّدو نقاط تفتيش الإصدار 2 يستقبلون أدلة مباشرة مُطبَّعة بدلًا من ذلك: صفوف نصوص المستخدم/المساعد فقط — نتائج الأدوات، والرسائل النظامية، وحمولة tool_calls الخاصة برسائل المساعد (يُحتفَظ بنثرها)، وملخصات الضغط السابقة تُصفَّى من جهة المضيف. تُعرَف الملخصات السابقة عبر علامة رسالة دائمة _compressed_summary تنجو من إعادات تشغيل العملية، بحيث لا تُغذّي جلسة مستأنَفة أرشيفك بملخصات مشتقة أبدًا.

      يجب أن تكون نقاط التفتيش متماثلة القوة (idempotent). بعد حظر بسبب الفشل الآمن، تستدعي محاولة الضغط التالية on_pre_compress() مرة أخرى بنفس النص — والنص الذي نما قليلًا فقط ينتج أدلة متداخلة إلى حد كبير. رتّب كتابات أرشيفك حسب المحتوى (مثلًا بصمة رقمية للنص) واستخدم upsert، بحيث تتماثل إعادات المحاولة والتداخلات بدلًا من تراكم أرشيفات مكررة.

      اختبارات العقد: tests/agent/test_pre_compress_checkpoint_contract.py.

      تجربة الإعداد — ما يحتفظ به المزوّد المستقل​

      كل واجهة إعداد يمنحها Hermes لمزوّد مضمّن تعتمد على ملفات في دليل المزوّد نفسه، لذا يحتفظ بها كلها المزوّد المثبّت من كتالوج الإضافات:

      الواجهةما يوفّره المزوّد
      Desktop → Capabilities → Tools → Memory (لوحة الإعدادات)config_schema.py (أدناه)
      hermes memory setup معالج الإعدادget_config_schema() تعلن الحقول التي يطلبها المعالج، وتحفظها save_config(config, hermes_home)، وتعمل post_setup(hermes_home, config) بعدها لكل ما يتطلب تفاعلًا (OAuth أو المزامنة الأولى)؛ وتزوّد get_status_config() hermes memory status
      hermes <provider> … الأوامر الفرعيةcli.py مع register_cli(subparser) (إضافة أوامر CLI)
      اعتماديات Pythonpyproject.toml [project] dependencies (أو python_dependencies في plugin.yaml)؛ تُثبَّت وفق الإصدارات المثبّتة الخاصة بـ Hermes عند التثبيت وتُعاد تطبيقها عند hermes update

      اسم مزوّدك وقسم الإعدادات memory.<name> ودليل البيانات وأسماء الأدوات هي العقد مع المستخدمين الحاليين. يحتفظ المزوّد الذي ينتقل خارج النواة بالأربعة؛ ويثبّت Hermes عندئذ إضافة الكتالوج تلقائيًا لكل من لا تزال قيمة memory.provider عنده تسمّيه (عند hermes update ومرة واحدة عند بدء الوكيل إذا كانت security.allow_lazy_installs مفعّلة).

      مخطط الإعدادات (Config Schema)​

      get_config_schema() قائمة من واصفات الحقول (field descriptors) المستخدَمة في hermes memory setup:

      def get_config_schema(self):
          return [
              {
                  "key": "api_key",
                  "description": "My Provider API key",
                  "secret": True,           # → written to .env
                  "required": True,
                  "env_var": "MY_API_KEY",   # explicit env var name
                  "url": "https://my-provider.com/keys",  # where to get it
              },
              {
                  "key": "region",
                  "description": "Server region",
                  "default": "us-east",
                  "choices": ["us-east", "eu-west", "ap-south"],
              },
              {
                  "key": "project",
                  "description": "Project identifier",
                  "default": "hermes",
              },
          ]

      الحقول ذات secret: True وenv_var تذهب إلى .env. الحقول غير السرية تُمرَّر إلى save_config().

      مخطط مبسّط مقابل مخطط كامل

      يُطرَح كل حقل في get_config_schema() أثناء hermes memory setup. المزوّدون ذوو الخيارات الكثيرة ينبغي أن يبقوا المخطط مبسّطًا — لا تُدرِج سوى الحقول التي يجب على المستخدم ضبطها (مفتاح API، بيانات الاعتماد المطلوبة). وثّق الإعدادات الاختيارية في مرجع ملف إعدادات (مثل $HERMES_HOME/myprovider.json) بدل مطالبة المستخدم بها كلها أثناء الإعداد. يُبقي ذلك معالج الإعداد سريعًا مع دعم الإعدادات المتقدمة. راجع مزوّد Supermemory (مدخل في كتالوج الإضافات) كمثال — لا يطلب إلا مفتاح API؛ وتوجد كل الخيارات الأخرى في supermemory.json.

      حفظ الإعدادات​

      def save_config(self, values: dict, hermes_home: str) -> None:
          """Write non-secret config to your native location."""
          import json
          from pathlib import Path
          config_path = Path(hermes_home) / "my-provider.json"
          config_path.write_text(json.dumps(values, indent=2))

      بالنسبة للمزوّدين المعتمدين فقط على متغيرات البيئة، اترك القيمة الافتراضية دون تنفيذ.

      نقطة دخول الإضافة​

      def register(ctx) -> None:
          """Called by the memory plugin discovery system."""
          ctx.register_memory_provider(MyMemoryProvider())

      يمكن للمزوّد أيضًا عرض مهارات للقراءة فقط من نفس الاستدعاء. تكون المهارات مُقيَّدة باسم نقطة الدخول ولا تُحمَّل إلا عندما يكون مزوّد الذاكرة هذا نشطًا:

      from pathlib import Path

      SKILLS_DIR = Path(__file__).parent / "skills"

      def register(ctx) -> None:
          ctx.register_memory_provider(MyMemoryProvider())
          ctx.register_skill(
              "maintenance",
              SKILLS_DIR / "maintenance" / "SKILL.md",
              "Maintain the provider's memory store",
          )

      مع تفعيل نقطة الدخول my-provider، تصبح المهارة متاحة باسم my-provider:maintenance عبر skill_view().

      plugin.yaml​

      name: my-provider
      version: 1.0.0
      description: "Short description of what this provider does."
      hooks:
        - on_session_end    # list hooks you implement

      عقد الـ Threading​

      sync_turn() غير حاجبة (non-blocking). إذا كان backend لديك يستغرق وقتًا (استدعاءات API أو معالجة LLM)، نفّذ العمل في daemon thread — تُطلق باستخدام agent.memory_provider.spawn_context_thread لا threading.Thread مباشرةً. يوجد عزل الـ profile (HERMES_HOME النشط ونطاق الأسرار لكل دور) في contextvars، وتبدأ thread العادية بسياق فارغ: ضمن profiles المجمّعة ستكتب بصمت في مخزن الـ profile الافتراضي، وتفشل get_secret() فيه مع الرفض الآمن.

      from agent.memory_provider import spawn_context_thread

      def sync_turn(self, user_content, assistant_content, *, session_id="", messages=None):
          def _sync():
              try:
                  self._api.ingest(user_content, assistant_content, session_id=session_id, messages=messages)
              except Exception as e:
                  logger.warning("Sync failed: %s", e)

          if self._sync_thread and self._sync_thread.is_alive():
              self._sync_thread.join(timeout=5.0)
          self._sync_thread = spawn_context_thread(_sync, name="myprovider-sync")
          self._sync_thread.start()

      ينطبق ذلك على threads الجلب المسبق والكتابة أيضًا. تُقرأ ملفات JSON الصغيرة الملحقة بالإعدادات ($HERMES_HOME/<provider>.json) باستخدام utils.read_json_or_empty وتُكتَب باستخدام utils.atomic_json_write؛ ويمر كل ما هو ضمن config.yaml عبر hermes_cli.config.save_config(..., merge_existing=True).

      messages هو سياق محادثة اختياري بأسلوب OpenAI كما كان عند اكتمال الدور. عند وجوده، يتضمن رسائل المستخدم/المساعد، واستدعاءات أدوات المساعد، ورسائل نتائج الأدوات. المزوّدون الذين لا يحتاجون سياق الدور الخام يمكنهم حذف معامل messages؛ وسيستمر Hermes باستدعائهم بالتوقيع القديم.

      على مزوّدي السحابة توثيق أي أجزاء من messages تُرسَل خارج الجهاز. قد تحتوي استدعاءات الأدوات ونتائجها على مسارات ملفات، أو مخرجات أوامر، أو بيانات مساحة عمل أخرى.

      عزل Profile​

      كل مسارات التخزين يجب أن تستخدم معامل hermes_home من initialize()، لا المسار الثابت ~/.hermes مُثبَّتًا بشكل ثابت:

      # CORRECT — profile-scoped
      from hermes_constants import get_hermes_home
      data_dir = get_hermes_home() / "my-provider"

      # WRONG — shared across all profiles
      data_dir = Path("~/.hermes/my-provider").expanduser()

      إضافة أوامر CLI​

      يمكن لإضافات مزوّد الذاكرة تسجيل شجرة أوامر CLI فرعية خاصة بها (مثل hermes my-provider status، وhermes my-provider config). يستخدم هذا نظام اكتشاف قائمًا على الاصطلاح (convention-based) — بلا تغييرات على الملفات الأساسية.

      كيف يعمل​

      1. أضف ملف cli.py إلى دليل إضافتك
      2. عرّف دالة register_cli(subparser) تبني شجرة argparse
      3. يكتشفها نظام إضافة الذاكرة عند بدء التشغيل عبر discover_plugin_cli_commands()
      4. تظهر أوامرك تحت hermes <provider-name> <subcommand>

      التقييد حسب المزوّد النشط: تظهر أوامر CLI الخاصة بك فقط عندما يكون مزوّدك هو memory.provider النشط في الإعدادات. إذا لم يُعِد المستخدم ضبط مزوّدك، لن تظهر أوامرك في hermes --help.

      مثال​

      # plugins/memory/my-provider/cli.py

      def my_command(args):
          """Handler dispatched by argparse."""
          sub = getattr(args, "my_command", None)
          if sub == "status":
              print("Provider is active and connected.")
          elif sub == "config":
              print("Showing config...")
          else:
              print("Usage: hermes my-provider <status|config>")

      def register_cli(subparser) -> None:
          """Build the hermes my-provider argparse tree.

          Called by discover_plugin_cli_commands() at argparse setup time.
          """
          subs = subparser.add_subparsers(dest="my_command")
          subs.add_parser("status", help="Show provider status")
          subs.add_parser("config", help="Show provider config")
          subparser.set_defaults(func=my_command)

      التنفيذ المرجعي​

      راجع cli.py لمثال كامل بـ 13 أمرًا فرعيًا، وإدارة عبر عدة profiles (--target-profile)، وقراءة/كتابة الإعدادات.

      plugins/memory/my-provider/

      قاعدة المزوّد الواحد​

      يمكن أن يكون مزوّد ذاكرة خارجي واحد فقط نشطًا في وقت واحد. إذا حاول مستخدم تسجيل مزوّد ثانٍ، يرفضه MemoryManager بتحذير. هذا يمنع تضخّم مخطط الأدوات وتعارض الـ backends.

      HERMES_HOME عقد البقاء (ما يمكن للأغلفة الاعتماد عليه)​

      لمزوّدي نمط wrapper الذين يحتفظون ببيئة تشغيلهم في sidecar venv خارج Python التي يديرها Hermes (لا تعريف للاعتماديات — لا pyproject.toml، pip_dependencies، أو python_dependencies — في جذر الإضافة المفحوص؛ لا يُفحص pyproject.toml الذي يخص sidecar خارجيًا أو متداخلًا وحده):

      • الموقع. $HERMES_HOME/plugins/<name>/ هو موقع الإضافة المحدد النطاق بالـ profile، ويتبع HERMES_HOME تجاوز السياق النشط، ثم $HERMES_HOME، ثم القيمة الافتراضية للمنصة. مرّر HERMES_HOME عند إطلاق wrapper أو sidecar للحفاظ على عزل profiles؛ ويحقن MemoryManager.initialize_all قيمة hermes_home النشطة في كل مزوّد.
      • البقاء. لا تحذف تحديثات Hermes العادية — بما فيها إعادة بناء/استبدال venv المُدار بواسطة pm — $HERMES_HOME/plugins/** ولا تعيد كتابته. يبقى دليل wrapper مثبَّت وملف علامته (مثل mnemosyne-wrapper.json). تُستثنى من هذا الضمان تحديثات الإضافات الصريحة ومسارات الحذف (hermes uninstall، hermes plugins remove، وحذف profile، وحذف المستخدم).
      • عزل Sidecar. لا ينضم جذر إضافة دون تعريف للاعتماديات إلى اتحاد اعتماديات مساحة عمل pm أبدًا؛ ولا تجهّز إعادة المزامنة أو إعادة بناء venv اعتمادياته ولا تمس شجرته.
      • التعارضات.بالنسبة إلى الإضافات الأصلية ذات venv المشترك، يفشل اتحاد اعتماديات غير قابل للحل بصورة واضحة: تظل الإضافة المرشّحة غير مفعّلة وغير مستوردة (ترفض سلطة القبول قبل نشر الإعدادات، وتبلّغ بهوية الإضافة وسبب المحلِّل، مع مسار إعادة تفعيل/محاولة وإيصال pm مقروء آليًا). لا يعطّل حلّ الاعتماديات إضافات أخرى تلقائيًا، ولا يجري bisect. تحديثات الإضافات الصريحة وإزالتها وبوابات الأمان المستقلة عمليات منفصلة.

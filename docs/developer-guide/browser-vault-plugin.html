      إضافات Browser Vault

      يمكن لإضافة (plugin) أن تضيف مدير كلمات مرور (KeePass، أو vault خاصًا بالفريق، أو مخزنًا مدعومًا بالعتاد) كمصدر لتسجيل الدخول للأداة browser_vault، بشرط أن تأتي من مصدر موثَّق: إما مورّد المدير نفسه عبر كتالوج الإضافات، أو Nous (راجع من يستطيع تسجيل backend). عندئذٍ يعرض الوكيل بيانات تسجيل الدخول في ذلك المدير ويعبّئها بالطريقة نفسها التي يتعامل بها مع vault الخاص بـ Hermes المدمج و 1Password و Bitwarden: يرى المعرّفات (handles) والبيانات الوصفية فقط، ولا يرى كلمة المرور أبدًا.

      تختلف backends تسجيل الدخول في المتصفح عن مصادر الأسرار. فتسجيل SecretSource لا يجعل مدير كلمات المرور متاحًا للأداة browser_vault.

      تسجيل backend​

      تقوم الإضافة داخل العملية (in-process) بتوريث الصنف agent.vault_backends.base.LoginBackend وتسجّل نسخة واحدة منه:

      from agent.vault_backends.base import LoginBackend
      from agent.vault_store import VaultItemMeta


      class KeePassBackend(LoginBackend):
          name = "keepass"            # lowercase identifier; also the config key
          prefix = "keepass:"         # must be exactly "<name>:"
          display_name = "KeePass"

          def list_items(self) -> list[VaultItemMeta]:
              ...  # metadata only: ids "keepass:<opaque>", exact HTTPS origins, identifier

          def get_meta(self, handle: str) -> VaultItemMeta | None:
              ...

          def resolve_password(self, handle: str) -> str:
              ...  # called once per fill, after the page origin matched the item


      def register(ctx):
          ctx.register_login_backend(KeePassBackend())

      يبقى الـ backend معطّلًا إلى أن يفعّله المستخدم للـ profile:

      vault:
        keepass:
          enabled: true   # exactly true; installed code is never enabled automatically

      أنشئ الـ backend دون جلب بيانات الاعتماد ودون قراءة حالة الـ profile، واقرأ إعدادات الـ profile النشط بتأنٍّ (lazily). التسجيل مقيَّد بالـ profile، ويُزال عند إلغاء تحميل الإضافة.

      من يستطيع تسجيل backend​

      تأتي تكاملات مديري كلمات المرور من مصادر موثَّقة فقط. يُقبل ctx.register_login_backend من:

      • إضافة مضمّنة (bundled) مع Hermes، أو
      • إضافة مثبّتة من كتالوج إضافات Hermes بالمستوى tier: verified (ينشرها مورّد مدير كلمات المرور نفسه) أو tier: official (تتولى Nous صيانتها)، عند الـ pin الذي راجعه الكتالوج.

      تُرفض كل إضافة أخرى عند التسجيل مع سطر في السجل يذكر هذه القاعدة: إضافة وُضعت يدويًا في ~/.hermes/plugins/، أو تثبيت عبر عنوان Git URL، أو إدخال في الكتالوج بمستوى المجتمع (community)، أو تثبيت من الكتالوج نُقل عن الـ pin الخاص به باستخدام --ref، أو إضافة ثُبّتت باستخدام --allow-removed، أو إضافة مشروع، أو إضافة pip entry-point. تُقرأ الجهة المصدرية (provenance) من سجل التثبيت الخاص بـ Hermes (plugins/.install-metadata.json، ويكتبه المُثبّت)، ولا تُقرأ أبدًا من ملف داخل الإضافة نفسها، ولذلك لا يستفيد مستودع يشحن ملف .hermes-catalog.json خاصًا به بأي شيء. لا يوجد مفتاح إعدادات يخفّف هذه القاعدة.

      إذا كنت تبني مدير كلمات مرور وتريد إدراجه في Hermes، فأرسل الإضافة إلى الكتالوج من مستودعك الخاص واطلب المستوى verified (قاعدة القبول 18 في الكتالوج). أما التكاملات مع المديرين الذين لم ينشر مورّدوها إضافة فتأتي من Nous كإدخالات official.

      قواعد العزل​

      يغلّف Hermes كل backend تأتي به إضافة داخل محوّل (adapter) تملكه النواة قبل أن تراه أداة vault. تسري هذه القواعد مهما كانت طريقة تنفيذ الإضافة لصنفها:

      القاعدةما تعنيه لـ backend الخاص بك
      مساحة الأسماء الخاصة بك فقطمعرّفاتك (handles) على الصيغة <name>:…. يحدد Hermes الملكية من الاسم المسجَّل، فلا يستدعي owns() الخاصة بك أبدًا، ولا يمرّر إليك أبدًا معرّفًا من النوع vault_… (vault الخاص بـ Hermes) أو op:… أو bw:… أو معرّفًا يخص إضافة أخرى. تُسقَط العناصر التي تعيدها list_items() بمعرّف خارج مساحة أسمائك، وتُتجاهل إجابة get_meta() إذا لم يكن معرّفها هو المعرّف المطلوب.
      معرّف يدخل وقيمة تخرجلا تستقبل list_items() أي وسائط؛ أما get_meta() و resolve_password() و resolve_otp() و resolve_secret() فتستقبل معرّفك ولا شيء غيره. لا تستلم أبدًا الصفحة، ولا جلسة CDP/المتصفح، ولا المهمة، ولا عناصر vault الأخرى، ولا القيم المفكوكة التشفير من أي backend آخر.
      لا مطالبة بكلمة المرور الرئيسيةمطالبة فتح القفل في Hermes محجوزة للمديرين المدمجين. يُرفض عند التسجيل أي backend فيه needs_unlock = True، ولا يُعرض الإجراء unlock على backend تأتي به إضافة أبدًا، فلا يُطلب من المستخدم أن يكتب كلمة مرور رئيسية في نافذة وسمتها إضافة. صادِق عبر الوكيل (agent) الخاص بمديرك أو جلسته أو سلسلة مفاتيح نظام التشغيل (OS keychain).
      مساحات أسماء محجوزةتُرفض الأسماء local و onepassword و bitwarden و vault و op و bw، وأي بادئة تقع ضمن بادئة مدمجة (vault_x:). وكذلك يُرفض اسم تحتفظ به إضافة أخرى بالفعل في الـ profile: لا يمكن استبدال أي backend، مدمجًا كان أو من إضافة، ولا حجبه. يجب أن يكون name و prefix سمتين نصيتين عاديتين لا خاصيتين (properties)، ولا يجوز للصنف تجاوز __getattribute__ أو __class__: يحكم Hermes على التسجيل دون تشغيل شيفرتك.
      معطّل افتراضيًالا يشغّل الـ backend إلا vault.<name>.enabled: true.
      داخل العملية فقطيُرفض ctx.register_login_backend عند ضبط plugins.isolation: host، لأن fill_context() مدير سياق (context manager) محلي على الخادم.
      مسار التعبئة نفسهتمرّ عناصر الإضافة (كلمات المرور ورموز المرور لمرة واحدة التلقائية) عبر الفحص المسبق للأصل (origin) المطابق تمامًا، وإعادة التحقق من الأصل داخل الصفحة، وتقييم الأسرار عبر CDP من المشرف (supervisor) (لا عبر argv أبدًا)، وتأكيد الدفع، تمامًا كالعناصر المدمجة.
      الأسرار خارج المحادثةتُسجَّل القيم التي تعيدها لدى حدّ إخفاء نتائج المتصفح (redaction boundary) قبل أن تصل إلى الصفحة. وأي استثناء (exception) يرفعه الـ backend الخاص بك يُستبدل برسالة ثابتة (The <name> login backend failed.) قبل أن يبلغ نتيجة أداة أو سطرًا في السجل أو سلسلة استثناءات، فلا يمكن لسر موجود في نص الخطأ أن يصل إلى النموذج. وتُرفض القيمة ذات النوع الخاطئ بالطريقة نفسها. ينسخ Hermes ما تعيده (حقول البيانات الوصفية وكلمات المرور والرموز) إلى كائنات بسيطة خاصة به داخل الحارس نفسه، فإذا وقع خطأ أثناء قراءة حقل ما، تُعطى الرسالة الثابتة نفسها.

      الإضافة داخل العملية هي شيفرة Python عادية تعمل داخل Hermes، ولذلك فهذه القواعد عقد API وليست sandbox. فهي تضمن ألا يسلّم Hermes لـ backend الخاص بك بيانات backend آخر؛ لكنها لا تمنع شيفرة عشوائية في العملية نفسها من قراءة الملفات. وقاعدة المصدر الموثَّق أعلاه تحدد أي الإضافات يعرض عليها Hermes هذه الواجهة؛ وهي ليست sandbox كذلك.

      سياق التعبئة​

      القيمة الافتراضية لـ fill_context() هي عدم فعل شيء (no-op). ويجوز للـ backend أن يعيد مدير سياق خاصًا به لقفل عمليات التعبئة وتجميد إعدادات مرجع بيانات الاعتماد/الأصل طوال العملية، حتى لا يؤدي إعادة التحميل إلى إقران بيانات وصفية قديمة بسر جرى ضبطه حديثًا. لا يدخل Hermes هذا السياق إلا عند تعبئة معرّفاتك أنت (تعبئة كلمة مرور، وتعبئة رمز لمرة واحدة تلقائية لـ browser_vault action=enter_code، وكلتاهما عبر الكتابة داخل الصفحة)، وبعد أن يطابق أصل الصفحة قيمة get_meta() لعنصرك فقط: فالصفحة ذات الأصل المختلف لا تفتح سياقك أبدًا. وداخل السياق يستدعي Hermes get_meta() مرة أخرى ويرفض التعبئة ما لم يكن العنصر المجمَّد لا يزال مرتبطًا بأصل تلك الصفحة، فتأتي الأصول المفحوصة والسر المحلَّل من لقطة (snapshot) واحدة. يستدعي fill_context() دون وسائط ويخرج منه بالقيمة (None, None, None)، فلا ترى استثناء النواة أبدًا. حرّر القفل عند الخروج حتى لو فشلت التعبئة. ولا يؤدي قفل التعبئة إلى تسلسل التنقلات الأخرى غير ذات الصلة في المتصفح.

      كتابة الأخطاء​

      ارفع استثناءات برسائل تشخيصية ثابتة. يتجاهل Hermes نص الاستثناء الخاص بك، لكن سجلاتك أنت قد تدوّنه، لذا لا تضع فيه أبدًا قيم بيانات الاعتماد ولا أجسام استجابات مدير الأسرار. ولا تُتح أبدًا أداة موجَّهة للنموذج تعيد كلمة مرور: فستتجاوز كل قاعدة أعلاه.

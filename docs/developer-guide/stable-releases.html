      قبول الإصدارات المستقرة وترقيتها

      Stable Release هو بوابة الإصدار. نجاح عملية البناء وحده لا يعني إصدارًا مستقرًا. تستخدم الإصدارات المستقرة مراجع المحاولات كأقفال والوسوم النهائية كإيصالات نشر؛ ولا يُعدّ أي من الوسمين محفّزًا لسير العمل. لبنى Canary سير عمل مجدول خاص بها.

      إصدار المشروع المثبّت في المستودع هو دائمًا 0.0.0. تشتق مهام الإصدار نسخة الحمولة من المرجع المقبول وتوسم أشجار بناء معزولة. لا ترفع أرقام ملفات الإصدار على main.

      الترتيب​

      1. حدّث origin/main ومراجع المحاولات والعلامات البعيدة (rc.* و abandoned-rc.*). اشتق SemVer التالي من عائلة الإصدارات المنشورة المبدوءة عند 0.21.5 (آخر إصدار CalVer قديم، v2026.9.24) وحدها: الأحدث بين رأس R2 المستقر المحمي وأحدث إصدار GitHub منشور غير تمهيدي يحمل وسم vX.Y.Z. أما الإصدار الذي لا يبني أي حزم desktop فيحرّك الثاني وحده. ولا تحرّك المحاولات سلسلة الإصدارات. ويُرفَض أي قطع إصدار تكون نسخته التالية ذات وسم vX.Y.Z نهائي بالفعل حتى يكتمل ذلك النشر.
      2. ادفع مرجع محاولة مشروحًا باسم rc.<N>-vX.Y.Z بصورة ذرّية، وأنشئ عليه مسودة GitHub واحدة غير تمهيدية، وأرسل Stable Release من الفرع الافتراضي مع ذلك المرجع بوصفه مدخل tag. يأتي رقم المحاولة من مراجع المحاولات الموجودة لتلك النسخة. تربط رسالة الحجز commit الخاص بها ورقم المحاولة وسياسة النشر التلقائي ومجموعة المسارات (انظر المسارات) وحقبة زمنية واحدة تُخصَّص بتزايد مطّرد. تلك الحقبة هي تاريخ الإصدار والساعة المستخدمة في التغليف الأصلي لكل مسار في المصفوفة وكل إعادة محاولة. وتمنع محاولة معلّقة واحدة، لأي نسخة، إنشاء release جديد.
      3. اقبل SHA كائن الوسم المشروح البعيد نفسه، و commit الذي يشير إليه بعد فك الوسم، ونسب ذلك commit على origin/main. ويجب أن يكون التشغيل نفسه إرسال Stable Release من الفرع الافتراضي. وتأتي سير العمل وسكربتات الإصدار الخاصة به من main، لذا تتشارك caches الخاصة بـ Actions نطاقًا واحدًا عبر المحاولات. ويكون GITHUB_SHA هو رأس main، لا commit قيد الاختبار. ويُمرَّر commit المقبول إلى كل مسار يختبر الحمولة أو يبنيها، ويفرض ذلك فحص lint الخاص بتمرير commit في tests/ci/test_stable_release_commit_threading.py.
      4. شغّل المسارات التي يسجّلها الحجز: افتراضيًا كامل مخطط القبول الخاص بالمصدر وDocker وNix وحزمة PM والتثبيت/التحديث وWindows والحزم الموقّعة والترقية الأصلية، دون macOS Intel و Termux.
      5. ادفع artifacts الخاصة بـ Docker و R2 محددة الإصدار غير القابلة للتغيير من البايتات المختبرة. تُدفَع صورة Docker بمجرد نجاح اختباراتها الخاصة، وتُوسَم بمرجع المحاولة. لا تحرّك الأسماء البديلة stable أو latest بعد، ولا تُعِد البناء للنشر.
      6. أنشئ إيصال vMAJOR.MINOR.PATCH النهائي المشروح عند النشر، لا عند نجاح الاختبارات. يربط مرجع المحاولة الفائزة وكائنها و commit وبادئة الأرشيف و SHA256 لبيان المرشح (null عندما تجاوز الحجز الحزم) وبصمة manifest لـ Docker وسياسة النشر التلقائي.
      7. يعالج متحكم نشر الإصدارات المستقرة الإصدارات بالأقدم أولًا. ينشئ vX.Y.Z ويعيد توجيه الإصدار الذي ما زال مسودة إليه، ويحذف كتل التحذير، ويجعل الإصدار عامًا كآخر استدعاء، ثم يتحقق من بصمة Docker المرتبطة بالإيصال ويرقّيها، ويقدّم رؤوس App Installer و macOS و APT وصفحة التنزيلات و R2 المحمية.

      تنتظر المسودة الناجحة الوحيدة ما لم يختر حجزها النشر التلقائي. يدفع حجز ناجح لاحق جميع المسودات الناجحة السابقة المتصلة إلى المعالجة بالترتيب. يمنع حجز أقدم جارٍ النشر الأحدث. تُتجاوَز المحاولة المستنفدة وتُنشأ نسختها مجددًا بعد abandon. تظل المتطلبات الفاشلة والملغاة والمفقودة والتي جرى تجاوزها على نحو غير متوقع غير ناجحة.

      لا يدعم Docker Hub ولا R2 ولا APT ولا GitHub ولا Store معاملة واحدة تشمل الخدمات كلها. لذا فالمتحكم idempotent: بعد فشل جزئي، أعد تشغيله ودع كل عملية تعديل تتحقق من حالتها الحالية قبل المتابعة. الوسم النهائي هو إيصال الحيازة. لا تُعِد بناء البايتات المقبولة أو استبدالها أبدًا لإصلاح مؤشر.

      تستبدل الترقية صفحة التنزيلات المستقرة في releases/stable/index.html على المصدر العام لـ R2. تملك بنى وسوم Canary صفحة releases/canary/index.html، وتملك بنى commits صفحة releases/commit/<sha>/index.html. لا تسرد الصفحات إلا الكائنات المجهّزة والمدعومة بإيصالات؛ ولا يستطيع تشغيل أقدم إرجاع قناة محمية إلى الوراء.

      تشغيل إصدار مستقر أو نشره أو التخلي عنه​

      ابدأ من commit دقيق موجود بالفعل على main البعيد:

      python scripts/release.py release --commit "$(git rev-parse origin/main)" --bump patch --remote origin

      قيمة --bump الافتراضية patch؛ ولا تمرّر minor أو major إلا عندما يكون ذلك التغيير مقصودًا. ويجب أن يكون commit المختار من نسل أحدث vX.Y.Z منشور. وإذا لم يوجد وسم منشور، يُقبَل أي commit موجود بالفعل على main البعيد. ولا تفرض المحاولة المتروكة قيدًا على القطع التالي؛ فكثيرًا ما تُترك لأن commit الخاص بها سيئ. ويرفض release أيضًا ما دامت أي محاولة، لأي نسخة، معلّقة. ويطبع الرفض URL تشغيل سير العمل للمحاولة وأمر abandon وأمر إعادة التشغيل قبل أن يرفع الاستثناء. وفي طرفية تفاعلية يسأل بعد ذلك Abandon <ref> and cut a new attempt? [y/N]؛ فيتخلّى y عن المحاولة وينشئ التالية، والافتراضي هو لا. وفي أي حالة لا يكون فيها stdin أو stdout طرفية يرفع الاستثناء دون سؤال.

      مرجع المحاولة قفل عام، لا إصدار SemVer تمهيدي. يُكتَب rc.1-v0.21.5، لا v0.21.5-rc.1. يبقى إصدار الحزمة بسيطًا 0.21.5. parse_attempt_ref في scripts/releases/versioning.py هي القاعدة النحوية الوحيدة لصياغته.

      يحمل متن المسودة كتلة تحذير مسيّجة في الأعلى وأخرى في الأسفل: لا تنشر الإصدار من واجهة GitHub. نشره يدويًا يتجاوز وسم إيصال vX.Y.Z وموجزات التحديث والأسماء البديلة لـ Docker وفحص Store. الإصدارات المنشورة غير قابلة للتغيير، لذا لا يمكن إصلاح إصدار نُشر يدويًا لاحقًا، ويعيق pipeline: عندئذ لا تملك المحاولة مرجع علامة ولا وسمًا نهائيًا، فيرفضها release بوصفها معلّقة، ويرفضها abandon لأنها منشورة. تحذف جولة النشر الكتلتين المسيّجتين بينما ما زال الإصدار مسودة.

      أضف --autopublish للنشر فورًا عندما يصبح الحجز أقدم إصدار ناجح. بدونه، يبقى الإصدار مسودة حتى نشر صريح أو حجز ناجح لاحق يفرض المعالجة بالترتيب.

      المسارات (Lanes)​

      الإصدار المستقر مجموعة من المسارات. فمسار البناء ينتج شيئًا يحصل عليه المستخدمون؛ ومسار الاختبار مجموعة اختبارات تتحكم في بوابة الإصدار. ويبدأ release من المجموعة الافتراضية ويعدّلها:

      # The default: everything except macOS Intel and Termux
      python scripts/release.py release --commit "$(git rev-parse origin/main)" --remote origin
      # Only the signed Windows bundles and the Docker image, no tests
      python scripts/release.py release --commit "$(git rev-parse origin/main)" --only windows,docker --remote origin
      # Everything except the signed Windows pipeline (the Store bundle still builds and is submitted)
      python scripts/release.py release --commit "$(git rev-parse origin/main)" --without windows --remote origin
      # Only the Store bundle: no Azure signing anywhere
      python scripts/release.py release --commit "$(git rev-parse origin/main)" --only windows-store --remote origin
      # Everything, plus macOS Intel, without the install/update E2E
      python scripts/release.py release --commit "$(git rev-parse origin/main)" --with macos-intel --without install-e2e --remote origin

      يستبدل --only المجموعة الافتراضية، ويضيف --with مسارات، ويزيلها --without. يقبل كل منها أسماء مفصولة بفواصل ويمكن تكراره. ويعرض release --help كل مسار.

      المسارالافتراضيما يتحكم فيه
      dockeronبناء صورة Docker ونشرها
      windowsonحزم MSIX الموقّعة لـ Windows x64 و arm64 والحزمة الشاملة، وهي التي تغذّي قناة التحديث
      windows-storeonحزمة Microsoft Store غير الموقّعة، وتُرسل إلى Partner Center (ولا تحتاج إلى توقيع Azure)
      macos-arm64onDMG و ZIP لـ macOS Apple Silicon
      macos-inteloffDMG و ZIP لـ macOS Intel: غير مدعوم على main، ويضيف مشغّله أكثر من ساعة
      termuxoffحزمة APT لـ Termux (Android aarch64)
      ci, nix, docker-tests, pm-bundle, windows-live, install-e2e, bootstrap-versiononمجموعات الاختبارات المستقلة
      termux-checksonالتحقق من Termux؛ ولا يعمل إلا مع termux
      smokeonsmoke للتثبيت الأصلي والمحادثة لكل حزمة desktop مبنية
      upgradeonقبول ترقية الحزمة الموقّعة (من OLD إلى NEW) لكل حزمة desktop مبنية

      المسارات مفاتيح مستقلة. ولا تعمل المهمة إلا عندما تكون كل المسارات التي تحتاجها مفعّلة (JOB_LANES في scripts/releases/lanes.py)، لذا فإن مسار اختبار لشيء لا يُبنى لا يفعل شيئًا: فالمسار upgrade مع إيقاف macos-arm64 لا يخطّط لأي فرع ترقية لـ macOS.

      تُكتَب مجموعة المسارات في رسالة الحجز ("lanes": [...])، ولا تُمرَّر أبدًا كمدخل لسير العمل. تقرؤها admit من الحجز وتُخرج ناتجين: lanes (علم لكل مسار) و jobs (علم تشغيل لكل مهمة يتحكم فيها مسار). ويقرأ if الخاص بكل مهمة كهذه مدخلها في jobs، فيكون جدول المسارات هو المكان الوحيد الذي يحدد ما يعمل. ولا يمكن لإعادة تشغيل للتعافي تغييره. ولتغيير مسار، نفّذ abandon للمحاولة وأنشئ إصدارًا مجددًا.

      تبقى البوابات صارمة. تقرأ scripts.releases.stable gate المسارات وتتطلب من كل مهمة تزيلها هذه المسارات الإبلاغ عن skipped، ومن كل مهمة أخرى خاضعة للبوابة الإبلاغ عن success. والمهمة التي نُفّذت رغم أن مسارًا يزيلها تمنع الإصدار أيضًا. أما الحجز الذي أُنشئ قبل وجود المسارات (skipBundles و skipTests و includeMacosIntel و includeTermux) فيُقرأ بوصفه مجموعة المسارات التي كانت تتحكم في المهام نفسها. والحجز الذي لا يحتوي على lanesRevision أُنشئ حين كان windows يعني أيضًا حزمة Store، لذا يُقرأ windows فيه بوصفه windows زائد windows-store.

      ما ينشره الإصدار يتبع ما بناه:

      • Docker. مع إيقاف docker لا تُبنى أي صورة ولا تُرقّى، ويسجّل الوسم النهائي dockerManifestDigest: null.
      • الحزم (Bundles). بدون مسار desktop أو Termux لا يوجد manifest للمرشح، ويسجّل الوسم النهائي candidateManifestSha256: null.
      • لا تتحرك قناة desktop إلا لمجموعة desktop الكاملة (windows و macos-arm64). أما المجموعة الجزئية فتجهّز حزمها مع ذلك، وتسجّل manifest للمرشح بالأهداف التي بنتها بالضبط، وترسل حزمة Store عندما يكون windows-store مفعّلًا. والإصدار الخاص بـ Store فقط لا يحتوي على صفوف حزم، بل على ملف حزمة Store فقط، ولا يحرّك أي قناة. ويبقى رأس R2 المستقر المحمي وموجزا App Installer و macOS وقناة APT وصفحة التنزيلات و releases/stable/release-candidates.json وخط أساس الحزم الموقّعة على الإصدار الكامل السابق. وتتبع نسخ المصدر المسحوبة من المستودع الرسمي releases/stable/release-candidates.json، لذا تبقى هي أيضًا.
      • مكتمل. يكتمل الإصدار الذي يقدّم قناة desktop عندما يسمّيه رأس R2 المحمي. والذي لا يحرّك إلا Docker يكتمل عندما يحمل الاسم البديل stable البصمة التي يربطها وسمه النهائي. والذي لا يحرّك أي قناة يكتمل بمجرد أن يصبح عامًا. ويستخدم المنسّق هذه العلامات لتحديد الإصدارات التي ما زالت تحتاج جولة النشر.
      • بلا اختبارات. يسجّل manifest المرشح كل smoke أصلي بالحالة skipped، لا ناجحًا أبدًا، وترفض كل جهة قراءة تعرف الحجز (complete وتقديم R2 المحمي) manifest لا تتطابق نتائج smoke فيه مع مسار smoke للحجز. ويستخدم الإصدار الكامل التالي ذلك manifest خط أساس للترقية كغيره. أنشئ إصدارًا عاديًا بعد الإصدار غير المختبَر.

      عند استبعاد macOS Intel، تغيب صفوفه عن manifest المرشح وجدول التنزيلات في متن الإصدار وصفحة التنزيلات. وهناك موجز macOS مستقر واحد (releases/darwin/stable/stable-mac.yml)، ويستبدله promote بفرع arm64 وحده، لذا لا تحصل أجهزة Mac من نوع Intel على هذا الموجز على أي تحديث إلى أن يُقطع إصدار بالخيار --with macos-intel. وعند استبعاد Termux لا تُعاد كتابة فهارس APT، فتبقى قناة APT على إصدارها السابق. والإصدار الذي يعيد إضافة هدف بعد إصدار استبعده لا يملك خط أساس منشورًا له، لذا يُتخطّى فرع الترقية لذلك الهدف كما في الإصدار الأول.

      دفع الحجز هو قفل النسخة الذرّي. قد يشتق مستدعيان النسخة التالية نفسها، لكن لا ينجح إلا دفع واحد؛ ويبلّغ الخاسر عن منشئ الوسم الفائز ووقته و commit. يبقى الحجز المرفوض أو المتروك مستهلكًا. للنشر أو التخلي:

      python scripts/release.py publish --version 0.21.5 --remote origin
      python scripts/release.py abandon --version 0.21.5 --remote origin

      publish يجري فحصًا مسبقًا متزامنًا للاستبدال، ثم يرسل المتحكم المرتب نفسه المستخدم في التعافي التلقائي. يرفض نسخة معروفة مستنفدة أدنى من إصدار منشور أحدث. يُلغي abandon قسريًا تشغيلات Stable Release الجارية للمحاولة، ويحذف المسودة إن وجدت ويكتب مرجع علامة abandoned-rc.<N>-vX.Y.Z ويحتفظ بمرجع المحاولة. العلامة هي سجل التخلي؛ ولا يُحذف مرجع المحاولة أبدًا. لا تُستهلَك النسخة، لذا يكون الإنشاء التالي rc.<N+1>-vX.Y.Z.

      لا تُرسِل Stable Release يدويًا بوسم نهائي. يحتفظ التعافي بمرجع الحجز الأصلي و SHA للكائن و commit ومعرّف المسودة في قاعدة البيانات وسياسة النشر التلقائي وأعلام التخطي.

      الفشل والتعافي​

      عندما يفشل تشغيل مستقر، يبدأ حدث اكتماله Stable Release Publication، الذي يعيد فورًا تشغيل المهام الفاشلة وحدها ضمن تشغيل GitHub Actions نفسه. لا تأخير تراجعي ولا جدول. تطبّق الجولة إعادة المحاولة الأقدم غير المحسومة فقط، لأن GitHub لا يحتفظ إلا بتشغيل معلّق واحد في مجموعة التزامن المشتركة للإصدارات المستقرة. تنتظر إعادة التشغيل في تلك المجموعة حتى تنتهي الجولة. تُقبَل إعادتان للمحاولة كحد أقصى (محاولتا التشغيل 2 و 3). بعد فشل المحاولة 3، يصبح الحجز مستنفدًا ويمكن للمنسّق معالجة حجوزات لاحقة. يُستعاد طلب إعادة المحاولة المفقود أو التعطّل بين تعديلات النشر عند حدث الفشل التالي أو بإرسال Stable Release Publication يدويًا.

      يبقى الحجز المدفوع حديثًا الذي لم يُرصَد له تشغيل سير عمل غير محسوم لمدة ساعة. تغطي مهلة السماح هذه خطوات المسودة والإرسال غير الذرية. بعد الساعة، يُستنتَج أن الحجز الذي لم يبدأ بعد مستنفد. لا يُستنفَد أي حجز خلال نافذة الإنشاء المعتادة.

      توجد عمليات تسليم Desktop و Termux في أرشيف الوسوم غير القابل للتغيير في R2. مفتاح الأرشيف هو مرجع المحاولة: releases/tag/rc.<N>-vX.Y.Z/. لا تُكتَب releases/tag/vX.Y.Z/ أبدًا. يكتب كل منتج إيصال handoff-<target>.json يضم الوسم و commit والمسارات والأحجام وبصمات SHA256. توجد إيصالات كل معمارية بجوار manifest المرشح تحت تلك البادئة. ينتج تجميع المرشح release-candidates.json واحدًا مثبّتًا؛ يتحقق المستهلكون من بصمته ولا يعيدون رفع الحزم. لا تُسجَّل بصمته في أي موضع قبل النشر: تحسب جولة النشر hash لنسخة الأرشيف وتكتب تلك القيمة في الوسم النهائي. يدفع نشر Docker manifest واحدًا محدد الإصدار غير قابل للتغيير وموسومًا بمرجع المحاولة ويسجّل بصمته من السجل في الوسم النهائي. يرقّي النشر المؤجّل تلك البصمة من جهة السجل، فلا يعتمد على artifacts الخاصة بـ Actions التي تنتهي صلاحيتها.

      تجهّز مهام مرشحي Windows و macOS و Termux الحزم والبيانات الوصفية ضمن releases/tag/<attempt ref>/ قبل القبول. لا يُكتَب أي موجز مستقر في هذه المرحلة. يحمل مسار pool المستقر في APT أيضًا مرجع المحاولة: releases/termux/stable/pool/<attempt ref>/<c>/<name>.deb. رفع pool غير قابل للتغيير، مع ترويسة تخزين مؤقت لمدة سنة، لذا فإن إعادة إنشاء النسخة نفسها تكتب مفتاح pool مختلفًا. لا تقبل عمليات الرفع غير القابلة للتغيير كائنًا موجودًا إلا إذا تطابقت بايتاته. إذا اختلف كائن أرشيف أو بصمة الوسم النهائي أو وسم Docker المحدد الإصدار أو نتيجة القراءة الراجعة، فأوقف التعافي بدل استبدال المرشح المقبول.

      يربط manifest المرشح حقبة الحجز المقبول. يعيد القبول حساب رباعية Windows المستقرة من تلك الحقبة ويرفض إصدار MSIX أو VERSIONINFO للملف التنفيذي أو App Installer إذا كانت صيغته سليمة لكنه غير صحيح. يقرأ القبول الأصلي أيضًا اسم artifact في Electron و plist الخاص بـ macOS من الحزم المبنية. يوسم مخطط القبول شجرة bootstrap-installer معزولة، ويطلب من Cargo قراءة إصدار حزمة Tauri الناتج، ويبني ويفحص البيانات الوصفية وأسماء ملفات wheel/sdist في Python، ويفحص هويات بيئة التشغيل في Nix و Docker. تؤدي أي قيمة 0.0.0 ظاهرة للمستهلك أو أي إصدار غير مطابق إلى فشل البوابة.

      تبقى المسودة على مرجع المحاولة حتى النشر. حذفها هو abandon، ولا يستنفد النسخة. يربط الوسم النهائي المشروح معرّف إصدار GitHub في قاعدة البيانات المقبول مع الحجز. يعدّل النشر الإصدار فقط ما دام مسودة: ينشئ vX.Y.Z ويعيد توجيه الإصدار إليه ويحذف كتل التحذير من المتن ثم يقرأ الوسم والمتن مجددًا. جعل الإصدار عامًا هو آخر استدعاء. الإصدارات المنشورة غير قابلة للتغيير، فلا يمكن إعادة توجيه أي منها أو تغيير وسمه بعد ذلك.

      لا يوجّه أي شيء العميل إلى محاولة حتى النشر. يقارن المحدّث الإصدارات، لا عناوين URL، وهذا آمن فقط لهذا السبب. صفحة التشخيص في releases/tag/<attempt ref>/index.html ليست موجز تحديث، والمحاولة المثبّتة منها ليست آمنة للترقية: كل محاولات نسخة واحدة تحمل إصدار الحزمة نفسه، لذا لا تستبدلها البنية المنشورة أبدًا. تُدفَع صورة Docker مبكرًا تحت مرجع المحاولة؛ ويتحرك الاسمان البديلان stable و latest مع الموجز في جولة النشر. وتتبع بنية Store القاعدة نفسها: يُبقي التشغيل الأخضر commit الذي حجزه (مع تعطيل النشر التلقائي)، فيجري الاعتماد قبل البوابة، وتحوّل جولة النشر ذلك الإرسال إلى النشر التلقائي. وإذا رفضت API الإرسال هذا التحويل، تُصدر الجولة تحذيرًا: اختر Publish now في Partner Center بعد اعتماد البنية. ويُترك الإرسال الذي لا يحمل حزمة Store الخاصة بالإصدار دون مساس بينما تفحص الجولة الإصدارات المنشورة الأقدم بحثًا عن مالكه. وتعمل مصالحة Store حتى عندما تكون الموجزات والأسماء البديلة محدّثة بالفعل، فيمكن إعادة محاولة النشر المقاطَع دون إرجاعها. ويسجّل الإرسال المحجوز حجزه في ملاحظات الاعتماد: ولا يستطيع خلَفٌ استبداله إلا بعد أن يكون لذلك الحجز علامة تخلٍّ (abandon) بعيدة مطابقة. أما الإرساليات القديمة التي لا تحمل سجل مالك فتحتاج إلى تنظيف يدوي في Partner Center. ويتحول فشل الإرسال إلى تحذير؛ ويظل الإصدار منشورًا. وتحمل سجلات القناة المستقرة قيمة اختيارية باسم archiveRef تسمّي مرجع المحاولة؛ وتظل releaseTag بالقيمة vX.Y.Z، وترجع البادئة المحمية إليها عند غياب archiveRef.

      يسمّي المدخل الاختياري termux_upgrade_from_tag في سير عمل Desktop إصدارًا منشورًا دقيقًا لديه تسليم Termux في R2. لا تحتفظ بنى Desktop الصريحة التي لا تنشر بأي artifacts للمهام يمكن تنزيلها.

      يأخذ سير عمل desktop مدخل jobs بالمجموعات darwin-arm64 و darwin-x64 و win32-arm64 و win32-x64 و win32-bundle و linux-x64 و linux-arm64 و termux. يستدعيه stable مرة لكل مجموعة، باستثناء مجموعتي linux اللتين تنتظران بناء Linux فعليًا، ومجموعتي darwin-x64 و termux وأي مجموعة أخرى يستبعد الحجز مسارها، فلا يستدعيها. وتجهّز كل معمارية Mac وحزمة Windows إيصالًا، ويبدأ كل فرع تثبيت من إيصاله الخاص بمجرد تجهيز بايتاته. وacceptance هو نقطة الالتقاء الوحيدة التي تمنع النشر.

      تبدأ كل بوابة وكل مرشح مباشرةً بعد admit. فـ CI بوابة تتطلبها acceptance، لا قفل تنتظر خلفه البنى الموقّعة، لذا لا يمكن لبوابة بطيئة أن تؤخّر حزمة؛ والثمن أن main المعطوب يظل يتحمّل تكلفة مرشحين موقّعين ترفضهم acceptance لاحقًا. زالت مهمة smoke-win32-universal؛ وتغطي اختبارات smoke لـ MSIX الخاصة بكل معمارية كل معمارية، وتثبّت فروع تثبيت Windows ملف .msixbundle على المعماريتين. ويشغّل stable اختباري smoke لـ MSIX هذين في استدعاء win32-bundle الخاص به، بجانب التجميع، لا في الاستدعاءات الخاصة بكل معمارية: فيبدأ التجميع بمجرد بناء المعماريتين بدلًا من انتظار smoke المعمارية الأبطأ، ويظل استدعاء الحزمة (ومن ثم candidate-manifest) يفشل عندما يفشل أي من الاختبارين.

      نطاقات أسماء الوسوم والإيصالات​

      قبل الاعتماد على مراجع المحاولات كأقفال، طبّق ruleset للمستودع على refs/tags/v* و refs/tags/rc.* و refs/tags/abandoned-rc.* يقصر الإنشاء على مسؤولي المؤسسة وتكامل الإصدار ويمنع التحديث والحذف. لم يُطبَّق ruleset بعد؛ وحتى يطبّقه مسؤول، تعتمد هذه الأقفال على التزام المشاركين — يمكن لكل من لديه صلاحية push حذف مرجع علامة أو تحريك وسم إيصال. مراجع المحاولات والعلامات والوسوم النهائية غير قابلة للتغيير. تكتب بنى القنوات و commits إيصالات مشروحة بعد البناء مثل v0.0.7+channel.<YYYYMMDDTHHMMSSZ>.<run-id> و v0.0.0+commit.<YYYYMMDDTHHMMSSZ>.<run-id> فقط بعد نجاح النشر. لا تنشئ وسوم الإيصالات إصدارات GitHub ولا تفعّل سير العمل.

      هوية مصدر Canary هي v<stable>+canary.<YYYYMMDDTHHMMSSZ> وحدها. تجعل بيانات البناء الوصفية الإصدار متساويًا وفق SemVer مع نواته المستقرة عن قصد؛ ويحدد سجل القناة المحمي وطابع UTC المضمّن التقدّم. يتعامل عملاء Desktop مع تسلسل القناة المتحقق منه كمرجع للتحديث بدل مطالبة SemVer بترتيب بيانات البناء الوصفية. تعمل Canary Release مرة يوميًا عند 06:41 UTC من branch الافتراضي، ويبدأ الإرسال اليدوي تشغيلًا في أي وقت. تصطف التشغيلات مع cancel-in-progress: false. إذا لم تتضمن main commits جديدة، يستأنف التشغيل canary غير منشورة أو لا يفعل شيئًا. هويات -canary. التاريخية غير مدعومة. إذا توقفت عملية بعد دفع وسم canary، تتحقق إعادة تشغيل الأمر من كائن الوسم البعيد نفسه وتصلح المسودة المفقودة وتعيد الإرسال حتى يسجّل رأس canary المحمي إيصال ذلك الوسم. يتحقق متحكم النشر المحمي من كائن الوسم المشروح نفسه قبل تحويل إصدار GitHub التمهيدي من مسودة إلى عام، ويقرأ الحالتين مجددًا ثم يقدّم رأس R2 بعد ذلك فقط.

      هويات Canary وبنى Desktop لمرة واحدة​

      release.py --canary يبني تطبيق canary المنفصل. تختلف هوية حزمته وأمر CLI الخاص به (hermes-canary) عن stable؛ ولا يحدّث موجز canary الحالي إلا ذلك التطبيق. تستخدم البنى لمرة واحدة release.py --build-commit REV --remote REMOTE (أضف --publish للإرسال). تتضمن هوية تطبيقها وأمر CLI الخاص بها (hermes-<7-character-sha>) commit المثبّت. لا تستبدل بنيتان من commits مختلفين بعضهما.

      تُختار العلامة من مدخلات البناء تلك، لا من إعدادات وقت التشغيل: تستخدم canary أيقونات صفراء/صفراء داكنة؛ وتستخدم البنى لمرة واحدة أيقونات حمراء تحمل SHA المختصر. تُشتق كل صيغ أيقونات Desktop من التصميم نفسه.

      تستخدم وسوم البنى لمرة واحدة source: commit-build. لا يُنشَر لها موجز تحديث تطبيق ولا اشتراك App Installer، وترفض واجهة GUI و CLI المضمّنة كلتاهما طلبات التحديث. توجّهان المتلقي إلى طلب بنية جديدة من المطوّر. نسخ المصدر المسحوبة منفصلة: main قناتها الصالحة الوحيدة.

      --build-commit يطبع URL الحتمي لصفحة تنزيلاته قبل الإرسال، بما في ذلك التشغيلات التجريبية: https://hermes-assets.nousresearch.com/releases/commit/<full-sha>/index.html. تتجاوز CLOUDFLARE_R2_PUBLIC_URL المصدر العام. بعد القبول، يُنفَّذ ملخص commit حتى عند فشل مهمة بناء أو تجميع؛ ولا يسرد إلا التنزيلات الموجودة المدعومة بإيصالات ويضع علامة على الملفات التنفيذية المفقودة بأنها لم تُبنَ. ترتبط الملفات التنفيذية المفقودة بتشغيل سير العمل تحت View build run، لا بتنزيلات غير موجودة. لا تحتوي المنصات المعطّلة رابط تنزيل أو فشل. ما زال نشر الصفحة يتطلب وصولًا عاملًا إلى R2. يرتبط commit بمصدره على GitHub؛ وترتبط صفحات الوسوم والقنوات بوسم إصدار GitHub المناظر. تسرد صفحات commits أيضًا القيم الافتراضية الصريحة غير السرية لـ --bundle-env وعمليات المسح عبر --bundle-unset الممرّرة إلى حزم Desktop، لا بيئة CI. تُعرض القيم كسلاسل JSON (بما في ذلك "" للقيمة الفارغة)؛ وتُوسَم عمليات المسح باسم Unset. يُحذَف القسم عند عدم تقديم تجاوزات.

      تنشر البنى الموسومة أيضًا صفحة تشخيص خاصة بالوسم في releases/tag/<tag>/index.html بعد إخفاقات البناء أو الموجز، بما في ذلك عندما لم تُرفَع أي artifacts. لا يقدّم البناء غير المكتمل صفحة القناة ولا يجتاز بوابة نجاح الإصدار.

      يحتفظ الإرسال إلى Store بهويته الرسمية المستقرة الثابتة. يجب ألا تُرسَل الحزم غير المستقرة تحت تلك الهوية.

      قنوات ديناميكية في R2​

      أسماء القنوات كائنات R2، لا سجل في المستودع. تملك قناة معاينة هوية تطبيق أصلية واحدة عبر البنى من commits دقيقة. يسجّل طلب البناء غير القابل للتغيير commit المصدر والقيم الافتراضية للحزمة وتسلسل القناة وإصدارات الحزم بصورة منفصلة. يجب أن تنجح كل مهام البناء الأصلي و smoke الحالية قبل تقديم رأس القناة.

      عاين بنية مخصّصة ثم أرسلها صراحةً. لا تختار هوية المستودع السلوك: يعمل الإرسال المباشر نفسه من أي مستودع GitHub بعيد، لكن --channel لا يصل إلى R2 محليًا — يحدد commit المدفوع نفسه ويرسل سير عمل branch الافتراضي، الذي تنشئ خطوة التخصيص ذات الصلاحيات فيه القناة وتنتج طلب البناء غير القابل للتغيير في CI. لا يحتاج الأمر المحلي إلا token من نوع gh بصلاحية write أو maintain أو admin على المستودع المختار؛ ولا تُطلَب بيانات اعتماد R2.

      python scripts/release.py --channel pm-preview --build-commit my-branch --remote origin
      python scripts/release.py --channel pm-preview --build-commit my-branch --remote origin --publish
      python scripts/release.py --channels --remote origin

      افتراضيًا، تُثبَّت قناة المعاينة كتطبيق مستقل إلى جانب الآخر (Hermes NAME ومعرّف حزمة خاص بها). لاختبار commit دقيق كتطبيق عادي بدلًا من ذلك، أنشئ القناة باستخدام --branding stable: ينسخ اسم القناة المستقرة المنشورة وأيقونتها ومعرّف حزمتها، فتُثبَّت البنية فوق التطبيق الرسمي وتشارك إعدادات Desktop معه وتتبع التحديثات اللاحقة القناة. تُثبَّت العلامة عند إنشاء القناة؛ كرر الخيار في كل إرسال لتلك القناة واستخدم اسم قناة جديدًا لتغييرها. يتطلب --branding --channel، لأن بنية commit لمرة واحدة العادية تحمل دائمًا هويتها Hermes Agent <sha>.

      python scripts/release.py --channel my-commit --branding stable --build-commit SHA --remote origin --publish

      تحديد نطاق R2 مؤقت اختياري، للتشغيلات الاختبارية فقط. أرسل سير عمل Desktop باستخدام disposable_channel و build_commit لتخصيص نطاق أسماء ضمن ci-disposable/<repository-id>/<run-id>/، ثم استخدم أمر البناء المحدد النطاق نفسه الوارد في ملخصه. للإدارة المحلية لذلك التخصيص، مرّر R2_DISPOSABLE_RUN و GITHUB_REPOSITORY_ID الخاصين به في بيئة الأمر، مع إبقاء URL العام المضبوط عند الجذر غير المحدد النطاق. هذه مدخلات تشغيل اختبار، لا إعدادات تطبيق دائمة؛ يُفحَص معرّف المستودع مقارنةً بالبعيد المختار قبل قراءة بيانات الاعتماد، لذا يظل نطاق الأسماء المحدد خاصًا بمستودع واحد بالضبط.

      ينشئ أول استدعاء للنشر القناة (أثناء تخصيص CI)، وتحتفظ الاستدعاءات اللاحقة بهويتها. توجد الطلبات و artifacts ضمن releases/channel-builds/BUILD_ID/؛ والمؤشر القابل للتغيير هو releases/channels/NAME.json. يبقي البناء الفاشل رأسها السابق سليمًا. ترفض الكتابات الشرطية النشر القديم والقنوات المتقاعدة نهائيًا. تعيد المحاولة إرسال --channel NAME --build-commit SHA --publish، الذي يخصّص خانة تسلسل جديدة في CI؛ ولا يوجد أمر استئناف منفصل.

      يثبّت التقاعد البنية الرسمية المستقرة الحالية بوصفها المتلقي الأول:

      python scripts/release.py --retire-channel pm-preview --to stable --minimum-version VERSION --remote origin

      لا تضف --publish إلا بعد مراجعة التشغيل التجريبي وأدلة القبول الأصلي الدقيقة. لا يعيد هذا بناء stable تحت هوية المعاينة ولا يلغي تثبيت العملاء بصمت. يعرض العملاء المدركون للبروتوكول تسليمًا بين التطبيقات بموافقة المستخدم؛ ويجب أن تؤكد الوجهة جاهزيتها قبل إزالة المعاينة. أبقِ كائن التقاعد و artifacts المثبّتة متاحة للعملاء غير المتصلين. لا تملك البنى لمرة واحدة الحالية قارئًا للتقاعد وتتطلب استبدالًا.

      يجب أن يعلن manifest الوجهة دعم المتلقي المقروء من الوسم المضمّن في حزمتها. يملك سير عمل الإصدار المحمي الحالي القبول؛ ولا توجد وثيقة اعتماد عامة منفصلة ولا اعتماد على artifacts الخاصة بـ Actions التي تنتهي صلاحيتها. تبقى فحوصات التوقيع الأصلي والهوية وموافقة المتلقي والفحص المسبق للحالة المحفوظة وجاهزية الوجهة إلزامية. تصل المعاينة غير المتصلة إلى المتلقي الأول المثبّت حتى بعد تقدم stable؛ ثم يتحدّث ذلك التطبيق عبر stable.

      قبل إصدار قارئات المصدر المعتمدة على R2 وحده، هيّئ سجل main لـ branch المصدر وسجلات stable/canary المنشورة الموجودة عبر عملية bootstrap المحمية الصريحة. راجع manifests المقبولة الفعلية؛ ولا تختلق manifest أصليًا لـ main. تهيئة الإنتاج والتحقق من CDN cache/CAS وتأهيل الحزم الأصلية الموقّعة عمليات إصدار، ولا يعنيها نجاح مجموعة اختبارات مساعدة محلية. لا تخزّن مخرجات bootstrap كقائمة قنوات في المستودع مطلقًا.

      خط أساس الحزم الموقَّعة​

      يسجّل آخر إصدار مستقر ناجح نشر حزمًا releases/stable/release-candidates.json على أصل R2 العام المضبوط. لا يستبدله إصدار تخطى الحزم. عند عدم وجود خط أساس، يظل الإصدار يجري كل الفحوص السريعة الأصلية، لكنه يتخطى مسارات ترقية الحزم الموقَّعة. مدخل baseline-manifest غير الموجود عائق يمنع المتابعة. يحدد حزم Windows MSIX العامة الفعلية، وملفات ZIP لـ macOS، وبيانات مصدر الحزم. يجمع التشغيل التالي تلك السجلات مع manifest المرشّح ويستخدم أدوات تشغيل التحديث المضمّن الأصلية الحالية.

      لإصدار مستقر موجود يسبق هذه البيانات الوصفية، قدّم baseline-manifest كعنوان HTTPS على أصل R2 العام المضبوط يشير إلى manifest حالي بالمخطط 2 لحزمه المنشورة فعليًا ونتائج الفحوص السريعة الأصلية الناجحة. تُرفض المرشّحات بالمخطط 1؛ ولا يوجد مسار قبول قديم. يجب أن تبقى إعادات توجيه manifest على الأصل نفسه. يجب أن يكون tag خط الأساس إصدارًا مستقرًا منشورًا، وأن تتطابق هويات الحزم، وأن تتزايد الإصدارات. تستخدم حزم Windows المستقرة سياسة storePackageVersionAt الخاصة بـ electron-builder على الطابع الزمني الثابت لمنشئ tag في كائن tag المطالبة المقبول (year.hourOfYear.secondOfHour.0)، مستقلًا عن tag الحمولة بصيغة SemVer. غياب عناصر خط الأساس عائق، لا إذن للاختلاق أو تخطي القبول. راجع عقد التحديث المضمَّن.

      الاستثناءات الصريحة والسياسة​

      • اختبار Desktop Playwright E2E (e2e-desktop.yml) مؤجّل بطلب المالك لأنه غير مستقر. يُبلَّغ عنه كمؤجّل، لا ناجح. اجعله مستقرًا وأثبت تكرار تشغيلات CI الناجحة قبل إضافته إلى هذه البوابة.
      • اختبارات E2E للتثبيت/التحديث وقبول الحزم الأصلية الموقَّعة ليست مؤجّلة. فلا يزيلها إلا حجز لا يحتوي على مسار install-e2e أو smoke أو upgrade، وعندها تتطلب البوابة تخطّيها.
      • لا تنطبق فحوص السجل والتسميات ومراجعة diff الخاصة بـ PR فقط على tag مستقر. تظل جميع مهام CI المصدرية المنطبقة تعمل بغض النظر عن المسارات المتغيرة.
      • تحتفظ نتائج ثغرات OSV بسياستها الإرشادية الحالية. إخفاقات تنفيذ الماسح المطلوبة إخفاقات، لا نتائج إرشادية.
      • لا يُدَّعى نشر حزم Desktop على Linux المعطّلة. تظل حزم PM الأصلية على Linux، و Docker، و Nix، وفحوص التثبيت/التحديث مطلوبة.
      • سير عمل الصيانة، والإصلاح التلقائي، والتعليقات، وفهرسة المهارات/النشر، ليست مجموعات قبول للإصدار.

      ملكية التنفيذ​

      تملك Actions ترتيب المهام، واختيار runners، والصلاحيات، والبيئات. تملك Python قبول الإصدار المشترك، و manifests، و hashes العناصر، والنشر، وترقية القنوات تحت scripts/releases/ و scripts/bundles/. تظل إعدادات/hooks Electron-builder ومحوّلات Windows/macOS الأصلية في JavaScript أو PowerShell. تستهلك تلك المحوّلات حقائق الإصدار بدلًا من إعادة تنفيذ بوابة الإصدار. لا تستخدم مهام البوابة إلا مكتبة Python القياسية؛ ولا تثبّت التطبيق أو مساحة عمل JS للإبلاغ عن حكم.

      scripts.bundles.release_artifacts يملك App Installer XML ونشر الخلاصة. يأخذ المسلسِل هوية الحزمة والناشر والإصدار و URI الاشتراك و URI العنصر صراحةً. تستخدم ترقية الإصدار المستقر بيانات المرشّح المقبول الوصفية؛ ويتحقق نشر canary من manifest الحزمة الأصلية بمقارنته بالهوية التي يتوقعها المحوّل قبل رفع الحزمة ثم الواصف. يظل تجميع/توقيع SDK الأصلي في stage-msixbundle.mjs. تتوقف عمليات بناء Store و commit قبل تسليم الخلاصة ذاك؛ ويقدّم stable-store المرشّح المتحقق منه دون إعادة بنائه. يستخدم القبول الأصلي مسلسِل Python نفسه، بما فيه سياسة الفحص عند الإطلاق كل 12 ساعة.

      تبقى بيانات اعتماد التوقيع والنشر في بيئات مهامها المحمية. لا يرث استدعاء CI المصدري أسرار النشر. اضبط بيئتي توقيع الإصدار ونشر الحاويات الحاليتين قبل تشغيل هذا pipeline.

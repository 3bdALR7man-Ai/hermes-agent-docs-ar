      آلية عمل Agent Loop من الداخل

      محرّك التنسيق الأساسي هو صنف AIAgent. أصبح run_agent.py الآن مجرّد واجهة رقيقة: تعيش الحلقة نفسها في agent/conversation_loop.py، وكل مرحلة من مراحل الدور (turn) في agent/turn_*.py (تحضير التكرار، استدعاء API، خطأ API، الفيضان (overflow)، الاقتطاع، الاسترداد)، وربط المُنشئ (constructor) في agent/agent_init.py، وكل ما من تجميع الـ prompt إلى توزيع الأدوات إلى التبديل الاحتياطي بين المزوّدين موزَّع في وحدات agent/*.py مركّزة تُمزج داخل AIAgent.

      المسؤوليات الأساسية​

      AIAgent مسؤول عن:

      • تجميع الـ system prompt الفعلي ومخططات الأدوات عبر prompt_builder.py
      • اختيار المزوّد الصحيح ونمط API المناسب (chat_completions، codex_responses، anthropic_messages)
      • إجراء استدعاءات نموذج قابلة للمقاطعة مع دعم الإلغاء
      • تنفيذ استدعاءات الأدوات (بالتسلسل أو بالتزامن عبر thread pool)
      • الحفاظ على سجل المحادثة بصيغة رسائل OpenAI
      • معالجة الضغط وإعادة المحاولة والتبديل إلى نموذج احتياطي
      • تتبّع ميزانيات التكرار عبر الوكلاء الأصليين والفرعيين
      • تفريغ الذاكرة الدائمة قبل فقدان السياق

      نقطتا دخول​

      # Simple interface — returns final response string
      response = agent.chat("Fix the bug in main.py")

      # Full interface — returns dict with messages, metadata, usage stats
      result = agent.run_conversation(
          user_message="Fix the bug in main.py",
          system_message=None,           # auto-built if omitted
          conversation_history=None,      # auto-loaded from session if omitted
          task_id="task_abc123"
      )

      chat() غلاف رقيق حول run_conversation() يستخرج حقل final_response من قاموس النتيجة.

      أنماط API​

      يدعم Hermes ثلاثة أنماط تنفيذ لـ API، تُحدَّد بناءً على اختيار المزوّد والوسائط الصريحة وقواعد استدلال base URL:

      نمط APIيُستخدم لأجلنوع العميل
      chat_completionsendpoints متوافقة مع OpenAI (OpenRouter، مخصّصة، معظم المزوّدين)openai.OpenAI
      codex_responsesOpenAI Codex / Responses APIopenai.OpenAI بصيغة Responses
      anthropic_messagesAnthropic Messages API الأصليةanthropic.Anthropic عبر مهايئ

      يحدّد النمط كيفية تنسيق الرسائل، وكيفية بناء استدعاءات الأدوات، وكيفية تحليل الردود، وكيفية عمل التخزين المؤقت والبث. تتلاقى الأنماط الثلاثة على نفس صيغة الرسائل الداخلية (قواميس بأسلوب OpenAI بحقول role/content/tool_calls) قبل استدعاءات API وبعدها.

      ترتيب تحديد النمط:

      1. وسيط المُنشئ الصريح api_mode (الأولوية الأعلى)
      2. الاكتشاف الخاص بالمزوّد (مثل مزوّد anthropic ← anthropic_messages)
      3. قواعد استدلال base URL (مثل api.anthropic.com ← anthropic_messages)
      4. الافتراضي: chat_completions

      دورة حياة الدور (Turn)​

      يتبع كل تكرار في agent loop هذا التسلسل:

      run_conversation()
        1. Generate task_id if not provided
        2. Append user message to conversation history
        3. Build or reuse cached system prompt (prompt_builder.py)
        4. Check if preflight compression is needed (>50% context)
        5. Build API messages from conversation history
           - chat_completions: OpenAI format as-is
           - codex_responses: convert to Responses API input items
           - anthropic_messages: convert via anthropic_adapter.py
        6. Inject ephemeral prompt layers (budget warnings, context pressure)
        7. Apply prompt caching markers if on Anthropic
        8. Make interruptible API call (_interruptible_api_call)
        9. Parse response:
           - If tool_calls: execute them, append results, loop back to step 5
           - If text response: persist session, flush memory if needed, return

      صيغة الرسائل​

      تستخدم جميع الرسائل داخليًا صيغة متوافقة مع OpenAI:

      {"role": "system", "content": "..."}
      {"role": "user", "content": "..."}
      {"role": "assistant", "content": "...", "tool_calls": [...]}
      {"role": "tool", "tool_call_id": "...", "content": "..."}

      يُخزَّن محتوى الاستدلال (reasoning) (من النماذج التي تدعم التفكير الممتد) في assistant_msg["reasoning"] ويُعرض اختياريًا عبر reasoning_callback.

      قواعد تناوب الرسائل​

      يفرض agent loop تناوبًا صارمًا لأدوار الرسائل:

      • بعد رسالة النظام: User → Assistant → User → Assistant → ...
      • أثناء استدعاء الأدوات: Assistant (with tool_calls) → Tool → Tool → ... → Assistant
      • ممنوع وجود رسالتَي assistant متتاليتين
      • ممنوع وجود رسالتَي user متتاليتين
      • فقط الدور tool يمكن أن تتوالى فيه إدخالات متتالية (نتائج أدوات متوازية)

      يتحقّق المزوّدون من صحة هذه التسلسلات، ويرفضون أي سجلّ غير سليم البنية.

      استدعاءات API القابلة للمقاطعة​

      تُغلَّف طلبات API داخل _interruptible_api_call() التي تشغّل استدعاء HTTP الفعلي في مسار (thread) خلفي بينما تراقب حدث مقاطعة:

      ┌────────────────────────────────────────────────────┐
      │  Main thread                  API thread           │
      │                                                    │
      │   wait on:                     HTTP POST           │
      │    - response ready     ───▶   to provider         │
      │    - interrupt event                               │
      │    - timeout                                       │
      └────────────────────────────────────────────────────┘

      عند حدوث مقاطعة (يرسل المستخدم رسالة جديدة، أو أمر /stop، أو إشارة):

      • يُتخلّى عن مسار API (وتُهمَل الاستجابة)
      • يمكن للوكيل معالجة المُدخل الجديد أو الإيقاف بشكل نظيف
      • لا تُدرَج أي استجابة جزئية في سجل المحادثة

      تنفيذ الأدوات​

      تسلسلي مقابل متزامن​

      عندما يعيد النموذج استدعاءات أدوات:

      • استدعاء أداة واحد ← يُنفَّذ مباشرةً في المسار الرئيسي
      • استدعاءات أدوات متعددة ← تُنفَّذ بالتزامن عبر ThreadPoolExecutor
        • استثناء: الأدوات الموسومة كتفاعلية (مثل clarify) تفرض التنفيذ التسلسلي
        • تُعاد النتائج إلى ترتيبها الأصلي في استدعاء الأدوات بصرف النظر عن ترتيب اكتمالها

      تدفّق التنفيذ​

      for each tool_call in response.tool_calls:
          1. Resolve handler from tools/registry.py
          2. Fire pre_tool_call plugin hook
          3. Check if dangerous command (tools/approval.py)
             - If dangerous: invoke approval_callback, wait for user
          4. Execute handler with args + task_id
          5. Fire post_tool_call plugin hook
          6. Append {"role": "tool", "content": result} to history

      أدوات على مستوى الوكيل​

      بعض الأدوات يعترضها agent/tool_executor.py (المُستدعى من agent/conversation_loop.py) قبل الوصول إلى handle_function_call():

      الأداةسبب الاعتراض
      todoتقرأ/تكتب حالة مهام محلية للوكيل
      memoryتكتب إلى ملفات الذاكرة الدائمة مع حدود للأحرف
      session_searchتستعلم سجل الجلسة عبر قاعدة بيانات جلسات الوكيل
      delegate_taskتُنشئ subagent واحدًا أو أكثر بسياق معزول

      تُعدِّل هذه الأدوات حالة الوكيل مباشرةً وتعيد نتائج أدوات اصطناعية دون المرور عبر السجل (registry).

      أسطح رد النداء (Callback)​

      يدعم AIAgent عمليات رد نداء خاصة بكل منصّة تتيح عرض التقدّم في الوقت الفعلي داخل CLI وgateway وتكاملات ACP:

      رد النداء (Callback)وقت الإطلاقيُستخدم بواسطة
      tool_progress_callbackقبل/بعد كل تنفيذ أداةمؤشر التحميل (spinner) في CLI، رسائل تقدّم gateway
      thinking_callbackعند بدء/توقّف النموذج عن التفكيرمؤشّر "thinking..." في CLI
      reasoning_callbackعند إعادة النموذج لمحتوى استدلالعرض الاستدلال في CLI، كتل الاستدلال في gateway
      clarify_callbackعند استدعاء أداة clarifyموجّه الإدخال في CLI، رسالة تفاعلية في gateway
      step_callbackبعد كل دور كامل للوكيلتتبّع خطوات gateway، تقدّم ACP
      stream_delta_callbackعند كل رمز بث (streaming) (عند التفعيل)عرض البث في CLI
      tool_gen_callbackعند تحليل استدعاء أداة من البثمعاينة الأداة في مؤشر التحميل بـ CLI
      status_callbackتغييرات الحالة (تفكير، تنفيذ، إلخ)تحديثات حالة ACP

      سلوك الميزانية والاحتياط​

      ميزانية التكرار​

      يتتبّع الوكيل التكرارات عبر IterationBudget:

      • الافتراضي: 500 تكرار (قابل للضبط عبر agent.max_turns)
      • يحصل كل وكيل على ميزانيته الخاصة. تحصل الوكلاء الفرعيون على ميزانيات مستقلة محدودة بسقف delegation.max_iterations (الافتراضي 50) — يمكن لإجمالي التكرارات عبر الوكيل الأصلي والوكلاء الفرعيين أن يتجاوز سقف الوكيل الأصلي
      • عند بلوغ 100%، يتوقّف الوكيل ويعيد ملخّصًا للعمل المنجز

      النموذج الاحتياطي​

      عند فشل النموذج الأساسي (خطأ حدّ المعدل 429، خطأ خادم 5xx، خطأ مصادقة 401/403):

      1. يُتحقّق من قائمة fallback_providers في الإعدادات
      2. تُجرَّب كل بديل بالترتيب
      3. عند النجاح، تستمر المحادثة مع المزوّد الجديد
      4. عند 401/403، تُجرَّب إعادة تحديث بيانات الاعتماد قبل التحويل

      يغطّي نظام الاحتياط أيضًا المهام المساعدة بشكل مستقل — الرؤية (vision) والضغط واستخراج الويب لكل منها سلسلة احتياط خاصة قابلة للضبط عبر قسم الإعدادات auxiliary.*.

      الضغط والاستمرارية​

      متى يبدأ الضغط​

      • ما قبل التحليق (Preflight) (قبل استدعاء API): إذا تجاوزت المحادثة 50% من context window الخاصة بالنموذج
      • الضغط التلقائي في gateway: إذا تجاوزت 85% (أكثر جرأة، يعمل بين الأدوار)

      ما الذي يحدث أثناء الضغط​

      1. تُفرَّغ الذاكرة إلى القرص أولًا (لمنع فقدان البيانات)
      2. تُلخَّص أدوار المحادثة الوسطى في ملخّص مُكثَّف
      3. تُحفظ آخر N رسالة سليمةً (compression.protect_last_n، الافتراضي: 20)
      4. تُبقى أزواج رسائل استدعاء الأداة/نتيجتها معًا (لا تُقسَّم أبدًا)
      5. يُولَّد معرّف نَسَب (lineage) جلسة جديد (الضغط ينشئ جلسة "فرعية")

      استمرارية الجلسة​

      بعد كل دور:

      • تُحفظ الرسائل في مخزن الجلسات (SQLite عبر hermes_state.py)
      • تُفرَّغ تغييرات الذاكرة إلى MEMORY.md / USER.md
      • يمكن استئناف الجلسة لاحقًا عبر /resume أو hermes chat --resume

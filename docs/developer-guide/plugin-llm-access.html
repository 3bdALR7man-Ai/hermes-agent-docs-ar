      وصول الإضافات إلى LLM

      ctx.llm هي الطريقة المدعومة لكي تُجري الإضافة استدعاءً لـ LLM. إكمال المحادثة (chat completion)، والاستخراج المنظّم، والاستدعاء المتزامن وغير المتزامن، مع الصور أو بدونها — الواجهة نفسها، وبوابة الثقة نفسها، وبيانات الاعتماد نفسها التي يملكها المضيف (host).

      تلجأ الإضافات إلى هذه الواجهة عندما تحتاج إلى تنفيذ شيء يستعين بالنموذج لكنه ليس جزءًا من محادثة الوكيل. مثلًا: hook يعيد صياغة خطأ أداة بصورة يستطيع غير المهندسين فهمها. أو gateway adapter يترجم رسالة واردة قبل إدراجها في قائمة الانتظار. أو slash command يلخّص نصًا طويلًا مُلصقًا. أو مهمة مجدولة تقيّم نشاط الأمس وتكتب سطرًا واحدًا في لوحة الحالة. أو مرشّح مسبق يقرر ما إذا كانت الرسالة تستحق إيقاظ الوكيل أصلًا.

      هذه مهام لا ينبغي أن يكون الوكيل طرفًا فيها. كل ما تحتاجه استدعاء واحد لـ LLM، وإجابة ذات نوع محدد، ثم ينتهي الأمر.

      أصغر استدعاء ممكن​

      result = ctx.llm.complete(messages=[{"role": "user", "content": "ping"}])
      return result.text

      هذه هي الواجهة كاملةً في سطر واحد. لا مفاتيح، ولا إعدادات للمزوّد، ولا تهيئة لأي SDK. تعمل الإضافة مع المزوّد والنموذج اللذين يستخدمهما المستخدم حاليًا — وعندما يبدّل المزوّد، تتبعه الإضافة تلقائيًا.

      مثال محادثة أكثر اكتمالًا​

      result = ctx.llm.complete(
          messages=[
              {"role": "system", "content": "Rewrite errors as one short sentence a non-engineer can act on."},
              {"role": "user",   "content": traceback_text},
          ],
          max_tokens=64,
          purpose="hooks.error-rewrite",
      )
      return result.text

      purpose سلسلة تدقيق حرة الصياغة — تظهر في agent.log وفي result.audit ليتمكن المشغّلون من معرفة أي إضافة أجرت أي استدعاء. وهي اختيارية لكنها موصى بها لأي استدعاء يتكرر كثيرًا.

      المخرجات المنظّمة (Structured output)​

      عندما تحتاج الإضافة إلى إجابة ذات نوع محدد، انتقل إلى المسار المنظّم:

      result = ctx.llm.complete_structured(
          instructions="Score this support reply for urgency (0–1) and pick a category.",
          input=[{"type": "text", "text": message_body}],
          json_schema=TRIAGE_SCHEMA,
          purpose="support.triage",
          temperature=0.0,
          max_tokens=128,
      )

      if result.parsed["urgency"] > 0.8:
          await dispatch_to_oncall(result.parsed["category"], message_body)

      يطلب المضيف مخرجات JSON من المزوّد، ويحللها محليًا كخيار احتياطي، ويتحقق من صحتها وفق المخطط (schema) الخاص بك إذا كانت jsonschema مثبّتة، ثم يعيد كائن Python في result.parsed. وإذا لم يتمكن النموذج من إنتاج JSON صالح، تكون قيمة result.parsed هي None ويحمل result.text الاستجابة الخام.

      ما يقدّمه لك هذا المسار​

      • استدعاء واحد بأربعة أشكال. complete() للمحادثة، و complete_structured() لـ JSON ذي النوع المحدد، و acomplete() و acomplete_structured() لـ asyncio. الوسائط نفسها، وكائنات النتائج نفسها.
      • بيانات اعتماد يملكها المضيف. OAuth tokens، وتدفقات التحديث (refresh flows)، ومجمّع بيانات الاعتماد (credential pool)، والتجاوزات المساعدة (aux) لكل مهمة — ينطبق كل مفهوم لبيانات الاعتماد موجود بالفعل في Hermes. لا ترى الإضافة أي token إطلاقًا؛ ويُسند المضيف الاستدعاء إليها عبر result.audit.
      • محدود النطاق. استدعاء واحد متزامن أو غير متزامن. لا بثّ (streaming)، ولا حلقات أدوات، ولا حالة محادثة تحتاج إلى إدارتها. حدّد المدخلات، واحصل على النتيجة، ثم عُد.
      • ثقة مغلقة عند الإخفاق (fail-closed). الإضافة التي لم تُعدّها قط لا يمكنها أن تختار بنفسها المزوّد أو النموذج أو الوكيل أو بيانات الاعتماد المخزّنة. الوضع الافتراضي هو "استخدم ما يستخدمه المستخدم". ويفعّل المشغّلون تجاوزات محددة صراحةً، لكل إضافة على حدة، في config.yaml.

      البدء السريع​

      فيما يلي إضافتان كاملتان — واحدة للمحادثة، وأخرى للمخرجات المنظّمة. كلتاهما مضمّنتان في دالة register(ctx) واحدة، ولا تحتاجان إلى أي إعدادات خارجية للعمل مع النموذج النشط لدى المستخدم أيًّا كان.

      إكمال المحادثة — /tldr​

      def register(ctx):
          ctx.register_command(
              name="tldr",
              handler=lambda raw: _tldr(ctx, raw),
              description="Summarise the supplied text in one paragraph.",
              args_hint="<text>",
          )


      def _tldr(ctx, raw_args: str) -> str:
          text = raw_args.strip()
          if not text:
              return "Usage: /tldr <text to summarise>"
          result = ctx.llm.complete(
              messages=[
                  {"role": "system",
                   "content": "Summarise the user's text in one tight paragraph. No preamble."},
                  {"role": "user", "content": text},
              ],
              max_tokens=256,
              temperature=0.3,
              purpose="tldr",
          )
          return result.text

      result.text هو استجابة النموذج؛ و result.usage يحمل أعداد tokens؛ و result.provider و result.model يحملان معلومات الإسناد.

      الاستخراج المنظّم — /paste-to-tasks​

      def register(ctx):
          ctx.register_command(
              name="paste-to-tasks",
              handler=lambda raw: _paste_to_tasks(ctx, raw),
              description="Turn freeform meeting notes into structured tasks.",
              args_hint="<text>",
          )


      _TASKS_SCHEMA = {
          "type": "object",
          "properties": {
              "tasks": {
                  "type": "array",
                  "items": {
                      "type": "object",
                      "properties": {
                          "owner":  {"type": "string"},
                          "action": {"type": "string"},
                          "due":    {"type": "string", "description": "ISO date or empty"},
                      },
                      "required": ["action"],
                  },
              },
          },
          "required": ["tasks"],
      }


      def _paste_to_tasks(ctx, raw_args: str) -> str:
          if not raw_args.strip():
              return "Usage: /paste-to-tasks <meeting notes>"
          result = ctx.llm.complete_structured(
              instructions=(
                  "Extract concrete action items from these meeting notes. "
                  "One task per actionable line. If no owner is named, leave 'owner' blank."
              ),
              input=[{"type": "text", "text": raw_args}],
              json_schema=_TASKS_SCHEMA,
              schema_name="meeting.tasks",
              purpose="paste-to-tasks",
              temperature=0.0,
              max_tokens=512,
          )
          if result.parsed is None:
              return f"Couldn't parse a response. Raw output:\n{result.text}"
          lines = [f"- [{t.get('owner') or '?'}] {t['action']}" for t in result.parsed["tasks"]]
          return "\n".join(lines) or "(no tasks found)"

      يوجد مثال عملي ثالث، هذه المرة مع مدخلات صور، في مستودع hermes-example-plugins (مستودع مرافق للإضافات المرجعية — غير مضمّن مع hermes-agent نفسه). وللواجهة غير المتزامنة (acomplete() / acomplete_structured() مع asyncio.gather())، راجع plugin-llm-async-example في المستودع نفسه.

      متى تستخدم كل دالة​

      تريد…استخدم
      استجابة نصية حرة (ترجمة، أو تلخيص، أو إعادة صياغة، أو توليد)complete()
      prompt متعدد الأدوار (system + أمثلة few-shot + المستخدم)complete()
      إرجاع قاموس ذي نوع محدد، مُتحقَّق منه وفق مخططcomplete_structured()
      مدخلات صورة أو نص مع إرجاع قاموس ذي نوع محددcomplete_structured()
      الاستدعاء نفسه من شيفرة غير متزامنة (gateway adapters، و hooks غير المتزامنة)acomplete() / acomplete_structured()

      كل ما عدا ذلك — اختيار المزوّد، وتحديد النموذج، والمصادقة، والاحتياطي (fallback)، والمهلة، وتوجيه الرؤية (vision routing) — متماثل في الأشكال الأربعة.

      واجهة API​

      ctx.llm هو نسخة (instance) من agent.plugin_llm.PluginLlm.

      complete()​

      result = ctx.llm.complete(
          messages=[{"role": "user", "content": "Hi"}],
          provider=None,         # optional, gated — Hermes provider id (e.g. "openrouter")
          model=None,            # optional, gated — whatever string that provider expects
          temperature=None,
          max_tokens=None,
          timeout=None,          # seconds
          agent_id=None,         # optional, gated
          profile=None,          # optional, gated — explicit auth-profile name
          purpose="optional-audit-string",
          task=None,             # optional — a plugin-registered auxiliary slot
      )
      # → PluginLlmCompleteResult(text, provider, model, agent_id, usage, audit)

      إكمال محادثة عادي. messages بالبنية القياسية لـ OpenAI — قائمة من القواميس بالشكل {"role": "...", "content": "..."}. تعمل الـ prompts متعددة الأدوار (system + أزواج few-shot من user/assistant + رسالة user الأخيرة) تمامًا كما تعمل مع OpenAI SDK.

      provider= و model= مستقلان، ويتبعان البنية نفسها المستخدمة في الإعدادات الرئيسية للمضيف (model.provider + model.model). اضبط model= وحده لاستخدام المزوّد النشط لدى المستخدم مع نموذج مختلف عليه. واضبط كليهما لتبديل المزوّد بالكامل. وأيٌّ من الوسيطين دون تفعيل صريح من المشغّل يُطلق PluginLlmTrustError.

      complete_structured()​

      result = ctx.llm.complete_structured(
          instructions="What you want extracted.",
          input=[
              {"type": "text",  "text": "..."},
              {"type": "image", "data": b"...", "mime_type": "image/png"},
              {"type": "image", "url":  "https://..."},
          ],
          json_schema={...},     # optional — triggers parsed result + validation
          json_mode=False,       # set True without a schema to ask for JSON anyway
          schema_name=None,      # optional human-readable schema name
          system_prompt=None,
          provider=None,         # optional, gated
          model=None,            # optional, gated
          temperature=None,
          max_tokens=None,
          timeout=None,
          agent_id=None,
          profile=None,
          purpose=None,
          task=None,             # optional — a plugin-registered auxiliary slot
      )
      # → PluginLlmStructuredResult(text, provider, model, agent_id,
      #                             usage, parsed, content_type, audit)

      المدخلات عبارة عن كتل نصية أو كتل صور ذات أنواع محددة (تُرمَّز البايتات الخام بـ base64 تلقائيًا في صورة data: URL). عند تمرير json_schema أو json_mode=True، يطلب المضيف مخرجات JSON عبر response_format، ويحللها محليًا كخيار احتياطي، ويتحقق منها وفق المخطط الخاص بك إذا كانت jsonschema مثبّتة.

      • result.content_type == "json" — result.parsed كائن Python يطابق المخطط الخاص بك.
      • result.content_type == "text" — فشل التحليل أو التحقق؛ افحص result.text للاطلاع على استجابة النموذج الخام.

      الاستدعاءات غير المتزامنة (Async)​

      result = await ctx.llm.acomplete(messages=..., task="classifier")
      result = await ctx.llm.acomplete_structured(
          instructions=..., input=..., task="classifier"
      )

      لها الوسائط وأنواع النتائج نفسها التي لنظيراتها المتزامنة. استخدمها من gateway adapters، أو hooks غير المتزامنة، أو أي شيفرة إضافة تعمل بالفعل على حلقة asyncio.

      الاستدعاءات المساعدة الموجّهة حسب المهمة​

      مرّر task= إلى أيٍّ من أشكال الاستدعاء الأربعة عندما تحتاج الإضافة إلى مسار مساعد (auxiliary) خاص بها ومُعدّ مسبقًا. سجّل تلك المهمة أثناء إعداد الإضافة؛ وتُطبَّق القيم الافتراضية للإضافة إلى أن يتجاوز المشغّل المزوّد والنموذج الخاصين بها في auxiliary.<task>:

      def register(ctx):
          ctx.register_auxiliary_task(
              "classifier", display_name="Classifier", description="Classify input."
          )


      result = ctx.llm.complete(messages=[...], task="classifier")
      result = ctx.llm.complete_structured(instructions=..., input=..., task="classifier")
      auxiliary:
        classifier:
          provider: openrouter
          model: vendor/model-id

      يمكن للإضافات توفير قيم افتراضية لتسجيل المزوّد/النموذج لمهامها الخاصة. وتتجاوز إعدادات المشغّل في auxiliary.<task> هذه القيم الافتراضية وتتحكم في خيار النشر. لا يمكن للإضافة استخدام مهمة إلا إذا سجّلتها بنفسها؛ وتفشل أسماء المهام غير المعروفة أو التابعة لغيرها قبل استدعاء المزوّد. يُعدّ allow_task_override: true منحًا صريحًا من المشغّل لاستخدام المهام المساعدة المدمجة في Hermes؛ ولا يسمح باستخدام مهام إضافة أخرى. أغفل task= (أو استخدم "auto") للإبقاء على المزوّد/النموذج الرئيسي النشط.

      خصائص النتيجة​

      @dataclass
      class PluginLlmCompleteResult:
          text: str                    # the assistant's response
          provider: str                # e.g. "openrouter", "anthropic"
          model: str                   # whatever the provider returned for this call
          agent_id: str                # whose model/auth was used
          usage: PluginLlmUsage        # tokens + cache + cost estimate
          audit: Dict[str, Any]        # plugin_id, purpose, profile

      @dataclass
      class PluginLlmStructuredResult:
          # same fields as PluginLlmCompleteResult, plus:
          parsed: Optional[Any]        # JSON object when content_type == "json"
          content_type: str            # "json" or "text"
          # audit also carries schema_name when supplied

      يحمل usage القيم input_tokens و output_tokens و total_tokens و cache_read_tokens و cache_write_tokens و cost_usd عندما يُرجع المزوّد هذه الحقول.

      بوابة الثقة (Trust gate)​

      السلوك الافتراضي مغلق عند الإخفاق (fail-closed). في غياب كتلة الإعدادات plugins.entries، يمكن للإضافة:

      • تشغيل أيٍّ من الدوال الأربع مع المزوّد والنموذج النشطين لدى المستخدم،
      • ضبط الوسائط التي تشكّل الطلب (temperature و max_tokens و timeout و system_prompt و purpose و messages و instructions و input و json_schema)،

      …وهذا كل شيء. تُطلق الوسائط provider= و model= و agent_id= و profile= الخطأ PluginLlmTrustError إلى أن يفعّلها المشغّل صراحةً. وبالمثل، لا يمكن لـ task= أن تستخدم إلا المهمة المساعدة المسجّلة للإضافة، ما لم يمنح المشغّل allow_task_override لمهمة مدمجة.

      معظم الإضافات لا تحتاج إلى هذا القسم أبدًا. فالإضافة التي تكتفي باستدعاء ctx.llm.complete(messages=...) دون أي تجاوزات تعمل مع ما هو نشط لدى المستخدم دون أي إعدادات. ولا تكون الكتلة التالية ذات صلة إلا عندما تريد إضافة ما تحديدًا تثبيت نموذج أو مزوّد مختلف عمّا يستخدمه المستخدم.

      plugins:
        entries:
          my-plugin:
            llm:
              # Allow this plugin to choose a different Hermes provider
              # (must be one Hermes already knows about — same names as
              # `hermes model` and config.yaml model.provider).
              allow_provider_override: true

              # Optionally restrict which providers. Use ["*"] for any.
              allowed_providers:
                - openrouter
                - anthropic

              # Allow this plugin to ask for a specific model.
              allow_model_override: true

              # Optionally restrict which models. Use ["*"] for any.
              # Models are matched literally against whatever string the
              # plugin sends — Hermes does not look anything up.
              allowed_models:
                - openai/gpt-4o-mini
                - anthropic/claude-3-5-haiku

              # Allow cross-agent calls (rare).
              allow_agent_id_override: false

              # Allow the plugin to request a specific stored auth profile
              # (e.g. a different OAuth account on the same provider).
              allow_profile_override: false

      معرّف الإضافة هو الحقل name: في ملف manifest بالنسبة إلى الإضافات المسطّحة، أو المفتاح المشتق من المسار بالنسبة إلى الإضافات المتداخلة (image_gen/openai و memory/honcho وغيرها).

      ما تفرضه البوابة​

      التجاوزالقيمة الافتراضيةمفتاح الإعدادات
      provider=مرفوضallow_provider_override: true
      ↳ قائمة السماح (allowlist)—allowed_providers: [...]
      model=مرفوضallow_model_override: true
      ↳ قائمة السماح (allowlist)—allowed_models: [...]
      agent_id=مرفوضallow_agent_id_override: true
      profile=مرفوضallow_profile_override: true
      المهمة المدمجة task=مرفوضallow_task_override: true

      كل تجاوز محكوم ببوابة مستقلة. منح allow_model_override لا يمنح معه allow_provider_override — فالإضافة الموثوقة لاختيار نموذج تبقى مقيّدة بالمزوّد النشط لدى المستخدم ما لم تحصل على بوابة المزوّد أيضًا.

      ما لا تحتاج البوابة إلى فرضه​

      • الوسائط التي تشكّل الطلب — temperature و max_tokens و timeout و system_prompt و purpose و messages و instructions و input و json_schema و schema_name و json_mode — مسموح بها دائمًا؛ فهي لا تختار بيانات اعتماد ولا مسارات.
      • يعني وضع الرفض الافتراضي أن الإضافة غير المُعدّة لا تزال قادرة على أداء عمل مفيد — فهي تعمل ببساطة مع المزوّد والنموذج النشطين. ولا يحتاج المشغّلون إلى التفكير في plugins.entries إلا للإضافات التي تريد توجيهًا أدق.

      ما يتولاه المضيف​

      قائمة كاملة بالأمور التي تتولاها ctx.llm نيابةً عن الإضافة حتى لا تضطر إلى القيام بها:

      • تحديد المزوّد. يقرأ model.provider + model.model من إعدادات المستخدم (أو التجاوزات الصريحة عندما تكون الإضافة موثوقة).
      • المصادقة. يجلب مفاتيح API أو OAuth tokens أو refresh tokens من ~/.hermes/auth.json / متغيرات البيئة، بما في ذلك مجمّع بيانات الاعتماد عند إعداده. ولا تراها الإضافة أبدًا.
      • توجيه الرؤية (Vision routing). عند تمرير مدخلات صور وكان النموذج النشط لدى المستخدم نصيًا فقط، يلجأ المضيف تلقائيًا إلى نموذج الرؤية المُعدّ.
      • سلسلة الاحتياطي (Fallback chain). إذا أعاد المزوّد الأساسي للمستخدم أخطاء 5xx أو 429، يمر الطلب عبر آلية الاحتياطي المعتادة في Hermes المراعية للمجمِّعات (aggregators) قبل أن يُرجع خطأً إلى الإضافة.
      • المهلة (Timeout). يلتزم بالوسيط timeout= الذي تمرّره، ويعود عند غيابه إلى إعداد auxiliary.<task>.timeout أو القيمة الافتراضية العامة للاستدعاءات المساعدة.
      • تشكيل JSON. يرسل response_format إلى المزوّد عندما تطلب JSON، ثم يعيد التحليل محليًا من استجابة محاطة بسياج شيفرة (code fence) إذا أعاد المزوّد استجابة كهذه.
      • التحقق من المخطط. يتحقق وفق json_schema الخاص بك عندما تكون jsonschema مثبّتة؛ وإلا فإنه يكتب سطر debug في السجل ويتخطى التحقق الصارم.
      • سجل التدقيق. يكتب كل استدعاء سطر INFO واحدًا في agent.log يتضمن معرّف الإضافة، والمزوّد/النموذج، والغرض، وإجماليات tokens.

      ما تتولاه الإضافة​

      • بنية الطلب. messages للمحادثة، و instructions + input للمخرجات المنظّمة. الإضافة تبني الـ prompt؛ والمضيف ينفّذه.
      • المخطط. أي بنية تريد استلامها. لا يستنتجها المضيف نيابةً عنك.
      • معالجة الأخطاء. تُطلق complete_structured() الخطأ ValueError عند المدخلات الفارغة وعند فشل التحقق من المخطط. ويُطلَق PluginLlmTrustError عندما ترفض بوابة الثقة تجاوزًا ما. وأي خطأ آخر (أخطاء 5xx من المزوّد، أو عدم إعداد بيانات اعتماد، أو انتهاء المهلة) يُطلق ما تُطلقه auxiliary_client.call_llm().
      • التكلفة. يعمل كل استدعاء على حساب المزوّد المدفوع لدى المستخدم. لا تستدعِ complete() في حلقة لكل رسالة gateway دون التفكير في استهلاك tokens.

      موقع هذه الواجهة ضمن واجهات الإضافات​

      توسّع دوال ctx.* الحالية نظامًا فرعيًا قائمًا في Hermes:

      | ctx.register_tool | يضيف أداة يمكن للوكيل استدعاؤها | | ctx.register_platform | يربط gateway adapter جديدًا | | ctx.register_image_gen_provider | يستبدل backend توليد الصور | | ctx.register_memory_provider | يستبدل backend الذاكرة | | ctx.register_context_engine | يستبدل ضاغط السياق | | ctx.register_hook | يرصد حدثًا من أحداث دورة الحياة |

      ctx.llm هي أول واجهة تتيح للإضافة تشغيل النموذج نفسه الذي يتحدث إليه المستخدم، خارج مسار المحادثة (out of band)، دون الحاجة إلى أيٍّ مما سبق. وهذه وظيفتها الوحيدة. إذا كانت إضافتك تحتاج إلى تسجيل أداة يستدعيها الوكيل، فاستخدم register_tool. وإذا كانت تحتاج إلى التفاعل مع حدث من أحداث دورة الحياة، فاستخدم register_hook. وإذا كانت تحتاج إلى إجراء استدعاء خاص بها للنموذج — لأي سبب، بمخرجات منظّمة أو بدونها — فاستخدم ctx.llm.

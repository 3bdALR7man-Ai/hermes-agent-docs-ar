      تحديد المزوّد وقت التشغيل (Provider Runtime Resolution)

      يمتلك Hermes مُحلِّل تشغيل مزوّد (provider runtime resolver) مشترك يُستخدَم عبر:

      • CLI
      • gateway
      • مهام cron
      • ACP
      • استدعاءات النماذج المساعدة (auxiliary)

      التنفيذ الأساسي:

      • hermes_cli/runtime_provider.py — حلّ بيانات الاعتماد، وحلّ التشغيل لنقطة النهاية (endpoint) المخصّصة
      • hermes_cli/auth.py — سجلّ المزوّدين، resolve_provider()
      • hermes_cli/model_switch.py — مسار تبديل /model المشترك (CLI + gateway)
      • agent/auxiliary_client.py — توجيه النموذج المساعد (auxiliary)
      • providers/ — نقاط دخول ABC + السجلّ (ProviderProfile و register_provider و get_provider_profile و list_providers)
      • plugins/model-providers/<name>/ — إضافات لكل مزوّد على حدة (مضمّنة) تُصرّح api_mode و base_url و env_vars و fallback_models وتُسجّل نفسها في السجلّ عند أول وصول. إضافات المستخدم في $HERMES_HOME/plugins/model-providers/<name>/ تتجاوز (override) الإضافات المضمّنة التي تحمل الاسم نفسه.

      تُعيد get_provider_profile() في providers/ كائن ProviderProfile لمعرّف مزوّد معطى. يستدعي runtime_provider.py هذه الدالة وقت الحلّ للحصول على base_url القانوني، وقائمة أولويات env_vars، و api_mode، و fallback_models دون الحاجة إلى تكرار تلك البيانات في عدة ملفات. تكفي إضافة إضافة جديدة تحت plugins/model-providers/<your-provider>/ (أو $HERMES_HOME/plugins/model-providers/<your-provider>/) تستدعي register_provider() ليلتقطها runtime_provider.py — دون الحاجة إلى فرع في المُحلِّل نفسه.

      إذا كنت تحاول إضافة مزوّد استدلال (inference) من الدرجة الأولى، اقرأ إضافة مزوّدين ودليل إضافات مزوّدي النماذج إلى جانب هذه الصفحة.

      أشكال الاستدلال (reasoning) في chat-completions​

      يمكن للمُرحِّلات (relays) المتوافقة مع OpenAI أن تُعيد reasoning أو reasoning_content كسلاسل نصية، أو قواميس أجزاء نصية، أو قوائم من أجزاء نصية وشظايا سلاسل. يُسطِّح Hermes هذه الحقول قبل عمليات السلاسل النصية في المسار الرئيسي، وتسجيل Relay، والتدفقات المساعدة المتزامنة وغير المتزامنة، واستخراج الاستدلال من الاستجابة المكتملة. تحتفظ الشظايا بمسافاتها البيضاء الصريحة؛ ولا يضيف التطبيع أي فاصل داخل الحقل. يحتفظ المسار الرئيسي وتسجيل Relay بفواصل الفقرات الموجودة بين عناوين الاستدلال الغامقة الكاملة. يبقى الاستدلال منفصلًا عن الإجابة المرئية.

      أولوية الحلّ (Resolution precedence)​

      على مستوى عالٍ، يستخدم حلّ المزوّد:

      1. طلب CLI/تشغيل صريح
      2. إعدادات النموذج/المزوّد في config.yaml
      3. متغيرات البيئة
      4. الإعدادات الافتراضية الخاصة بالمزوّد أو الحلّ التلقائي

      هذا الترتيب مهم لأن Hermes يعامل اختيار النموذج/المزوّد المحفوظ كمصدر الحقيقة للتشغيلات العادية. هذا يمنع تصدير (export) قديمًا في الـ shell من تجاوز نقطة النهاية التي اختارها المستخدم آخر مرة في hermes model بصمت.

      مخرجات الحلّ وقت التشغيل​

      يُعيد المُحلِّل وقت التشغيل بيانات مثل:

      • provider
      • api_mode
      • base_url
      • api_key
      • source
      • بيانات وصفية خاصة بالمزوّد مثل معلومات الانتهاء/التجديد

      لماذا يهمّ هذا​

      هذا المُحلِّل هو السبب الرئيسي في قدرة Hermes على مشاركة منطق المصادقة/التشغيل بين:

      • hermes chat
      • معالجة رسائل gateway
      • مهام cron التي تعمل في جلسات جديدة
      • جلسات محرر ACP
      • مهام النموذج المساعد (auxiliary)

      AI Gateway​

      اضبط AI_GATEWAY_API_KEY في ~/.hermes/.env وشغّل باستخدام --provider ai-gateway. يجلب Hermes النماذج المتاحة من endpoint الخاص بـ /models التابع لـ gateway، مع تصفيتها لتقتصر على نماذج اللغة الداعمة لاستخدام الأدوات.

      OpenRouter و AI Gateway وعناوين base URL المخصّصة المتوافقة مع OpenAI​

      يحتوي Hermes على منطق لتجنّب تسريب مفتاح API الخاطئ إلى نقطة نهاية مخصّصة عندما توجد مفاتيح مزوّدين متعددة (مثل OPENROUTER_API_KEY و AI_GATEWAY_API_KEY و OPENAI_API_KEY).

      مفتاح API لكل مزوّد مُقيَّد بنطاق base URL الخاص به:

      • OPENROUTER_API_KEY يُرسَل فقط إلى نقاط نهاية openrouter.ai
      • AI_GATEWAY_API_KEY يُرسَل فقط إلى نقاط نهاية ai-gateway.vercel.sh
      • OPENAI_API_KEY يُستخدَم لنقاط النهاية المخصّصة وكاحتياطي (fallback)

      يميّز Hermes أيضًا بين:

      • نقطة نهاية مخصّصة حقيقية اختارها المستخدم
      • مسار OpenRouter الاحتياطي المستخدَم عند عدم ضبط أي نقطة نهاية مخصّصة

      هذا التمييز مهم بشكل خاص من أجل:

      • خوادم النماذج المحلية
      • واجهات API متوافقة مع OpenAI غير تابعة لـ OpenRouter/AI Gateway
      • تبديل المزوّدين دون إعادة تشغيل الإعداد
      • نقاط النهاية المخصّصة المحفوظة في الإعدادات، والتي يجب أن تستمر بالعمل حتى عندما لا يكون OPENAI_BASE_URL مُصدَّرًا (exported) في الـ shell الحالي

      المسار الأصلي لـ Anthropic​

      لم تعد Anthropic تُستخدَم "عبر OpenRouter" فقط.

      عندما يختار حلّ المزوّد anthropic، يستخدم Hermes:

      • api_mode = anthropic_messages
      • واجهة Anthropic Messages API الأصلية
      • agent/anthropic_adapter.py للترجمة

      أصبح حلّ بيانات الاعتماد لمسار Anthropic الأصلي يُفضِّل الآن بيانات اعتماد Claude Code القابلة للتجديد على tokens البيئة المنسوخة عندما يتوفّر كلاهما. عمليًا، هذا يعني:

      • تُعامَل ملفات بيانات اعتماد Claude Code كمصدر مُفضَّل عندما تتضمّن مصادقة قابلة للتجديد
      • لا تزال قيم ANTHROPIC_TOKEN / CLAUDE_CODE_OAUTH_TOKEN اليدوية تعمل كتجاوزات صريحة
      • يُجري Hermes فحصًا مسبقًا لتجديد بيانات اعتماد Anthropic قبل استدعاءات Messages API الأصلية
      • لا يزال Hermes يعيد المحاولة مرة واحدة عند خطأ 401 بعد إعادة بناء عميل Anthropic، كمسار احتياطي

      مسار OpenAI Codex​

      يستخدم Codex مسار Responses API منفصلًا:

      • api_mode = codex_responses
      • حلّ بيانات اعتماد مخصّص ودعم مخزن مصادقة (auth store) مخصّص

      توجيه النموذج المساعد (auxiliary)​

      يمكن للمهام المساعدة مثل:

      • الرؤية (vision)
      • تلخيص الاستخراج من الويب
      • ملخّصات ضغط السياق
      • عمليات Skills Hub
      • عمليات مساعدة MCP
      • عمليات تفريغ الذاكرة

      يمكن لهذه المهام أن تستخدم توجيه مزوّد/نموذج خاصًا بها بدلًا من النموذج المحادثي الرئيسي.

      عندما تُضبَط مهمة مساعدة بالمزوّد main، يحلّها Hermes عبر مسار التشغيل المشترك ذاته كالمحادثة العادية. عمليًا، هذا يعني:

      • نقاط النهاية المخصّصة المضبوطة عبر متغيرات البيئة لا تزال تعمل
      • نقاط النهاية المخصّصة المحفوظة عبر hermes model / config.yaml تعمل أيضًا
      • يمكن للتوجيه المساعد التمييز بين نقطة نهاية مخصّصة محفوظة حقيقية ومسار OpenRouter الاحتياطي

      النماذج الاحتياطية (Fallback models)​

      يدعم Hermes سلسلة مزوّدين احتياطيين مضبوطة — قائمة من إدخالات (provider, model) تُجرَّب بالترتيب عندما يواجه النموذج الأساسي أخطاء. لا يزال القاموس القديم أحادي الزوج fallback_model مقبولًا للتوافق مع الإصدارات السابقة (ويُرحَّل عند أول كتابة).

      كيف يعمل داخليًا​

      1. التخزين: تخزّن AIAgent.__init__ قاموس fallback_model وتضبط _fallback_activated = False.

      2. نقاط التفعيل: تُستدعى _try_activate_fallback() (المُحوَّلة إلى try_activate_fallback() في agent/chat_completion_helpers.py) من ثلاثة مواضع في مراحل الدور (agent/turn_api_error.py، agent/turn_response_check.py، agent/turn_recovery.py):

        • بعد أقصى عدد من إعادات المحاولة على استجابات API غير صالحة (خيارات None، محتوى مفقود)
        • عند أخطاء العميل غير القابلة لإعادة المحاولة (HTTP 401، 403، 404)
        • بعد أقصى عدد من إعادات المحاولة على الأخطاء العابرة (HTTP 429، 500، 502، 503)

      3. مسار التفعيل (_try_activate_fallback):

        • يُعيد False فورًا إذا كان مُفعَّلًا بالفعل أو غير مُهيَّأ
        • يستدعي resolve_provider_client() من auxiliary_client.py لبناء عميل جديد بمصادقة صحيحة
        • يحدّد api_mode: codex_responses لـ openai-codex، و anthropic_messages لـ anthropic، و chat_completions لكل ما عدا ذلك
        • يستبدل في المكان: self.model و self.provider و self.base_url و self.api_mode و self.client و self._client_kwargs
        • لاحتياطي anthropic: يبني عميل Anthropic أصليًا بدلًا من عميل متوافق مع OpenAI
        • يُعيد تقييم التخزين المؤقت للـ prompt (مُفعَّل لنماذج Claude على OpenRouter)
        • يضبط _fallback_activated = True — يمنع التفعيل مرة أخرى
        • يُعيد عدّاد إعادة المحاولة إلى 0 ويكمل الحلقة

      4. مسار الإعدادات:

        • CLI: يقرأ سلسلة الاحتياط عبر hermes_cli/fallback_config.get_fallback_chain() ← يمرّرها إلى AIAgent(fallback_model=...)
        • Gateway: تقرأ gateway/run_config_loaders.py._load_fallback_model() ملف config.yaml ← تمرّرها إلى AIAgent
        • التحقق: يجب أن يكون مفتاحا provider و model غير فارغين، وإلا يُعطَّل الاحتياط

      ما الذي لا يدعم الاحتياط (fallback)​

      • تفويض Subagent (tools/delegate_tool.py): يرث subagent مزوّد الوالد لكن ليس إعدادات الاحتياط
      • المهام المساعدة: تستخدم سلسلة اكتشاف تلقائي مستقلة خاصة بها للمزوّد (راجع توجيه النموذج المساعد أعلاه)

      مهام cron تدعم الاحتياط: تقرأ run_job() قيمة fallback_providers (أو fallback_model القديمة) من config.yaml وتمرّرها إلى AIAgent(fallback_model=...)، بما يطابق نمط _load_fallback_model() الخاص بـ gateway. راجع آلية عمل Cron من الداخل.

      تغطية الاختبارات​

      يُختبَر سلوك الاحتياط عبر عدة مجموعات اختبار:

      • tests/run_agent/test_fallback_credential_isolation.py — عزل بيانات الاعتماد بين النموذج الأساسي والاحتياطي
      • tests/hermes_cli/test_fallback_cmd.py — أمر CLI الخاص بـ /fallback
      • tests/gateway/test_fallback_eviction.py — إخلاء gateway للمزوّدين الفاشلين

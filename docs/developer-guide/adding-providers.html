      إضافة مزوّدين

      يستطيع Hermes بالفعل التواصل مع أي endpoint متوافق مع OpenAI عبر مسار المزوّد المخصّص (custom provider). لا تُضِف مزوّدًا مدمجًا إلا إذا أردت تجربة استخدام من الدرجة الأولى لتلك الخدمة، مثل:

      • مصادقة خاصة بالمزوّد أو تحديث الـ token
      • كتالوج نماذج منتقى بعناية
      • عناصر في قائمة الإعداد / قائمة hermes model
      • أسماء مستعارة (aliases) للمزوّد لصيغة provider:model
      • واجهة API بشكل غير متوافق مع OpenAI تحتاج إلى adapter

      إذا كان المزوّد مجرد "base URL آخر متوافق مع OpenAI مع مفتاح API"، فقد يكفي مزوّد مخصّص مُسمّى.

      النموذج الذهني​

      يجب أن يتّسق المزوّد المدمج عبر عدة طبقات:

      1. يحدّد hermes_cli/auth.py كيفية العثور على بيانات الاعتماد.
      2. يحوّل hermes_cli/runtime_provider.py ذلك إلى بيانات وقت التشغيل:
        • provider
        • api_mode
        • base_url
        • api_key
        • source
      3. يستخدم run_agent.py قيمة api_mode لتحديد كيفية بناء الطلبات وإرسالها.
      4. يجعل hermes_cli/models.py و hermes_cli/main.py المزوّد يظهر في CLI. (يفوّض hermes_cli/setup.py العمل إلى main.py تلقائيًا — فلا حاجة إلى أي تغييرات هناك.)
      5. يحافظ agent/auxiliary_client.py و agent/model_metadata.py على عمل المهام الجانبية وحساب ميزانية الـ tokens.

      التجريد الأهم هنا هو api_mode.

      • تستخدم معظم المزوّدين chat_completions.
      • يستخدم Codex و Meta Model API (api.meta.ai — Muse Spark) الوضع codex_responses (يُرسل تلقائيًا prompt_cache_retention: 24h للتخزين المؤقت للـ prompt؛ ولا يحقّق api.meta.ai نسب إصابة cache بين 93 و99% إلا على /v1/responses).
      • يستخدم Ramp Router (api.router.com) أيضًا codex_responses — فـ Responses هو بروتوكول النقل الأصلي لـ Router (أما /v1/chat/completions فهو مجرد طبقة توافق بسيطة)، ويتحقّق من reasoning.effort لكل نموذج على حدة، وهو ما يعالجه profile الخاص بـ router بالتصريح بالقيم المقبولة لكل نموذج انطلاقًا من الكتالوج الحي (ProviderProfile.supported_reasoning_efforts).
      • يستخدم Anthropic الوضع anthropic_messages.
      • يعني البروتوكول الجديد غير المتوافق مع OpenAI عادةً إضافة adapter جديد وفرع api_mode جديد.

      صيغة النقل لاستدعاءات الأدوات​

      يخزّن Hermes سجل المحادثة داخليًا بشكل OpenAI chat-completions، لذا فإن ناقل chat_completions تكاد دالتاه convert_messages / convert_tools (agent/transports/chat_completions.py) لا تُجريان أي تحويل، بينما يحوّل كل ناقل آخر من هذا الشكل إلى بروتوكوله الأصلي. المرجع المعتمد لهذا الشكل — تعريفات tools مع parameters بصيغة JSON-schema، وعناصر tool_calls الخاصة بالمساعد مع function.arguments مُحوّلة إلى نص، ورسائل النتائج role: "tool" المرتبطة بـ tool_call_id — هو مرجع OpenAI chat completions API. عند كتابة adapter أصلي، تحدّد تلك الصفحة جانب المدخلات في عملية التحويل، بينما تحدّد وثائق المزوّد جانب المخرجات.

      اختر مسار التنفيذ أولًا​

      المسار A — مزوّد متوافق مع OpenAI​

      استخدم هذا المسار عندما يقبل المزوّد طلبات قياسية بأسلوب chat-completions.

      العمل المعتاد:

      • إضافة البيانات الوصفية للمصادقة
      • إضافة كتالوج النماذج / الأسماء المستعارة
      • إضافة التحديد وقت التشغيل (runtime resolution)
      • إضافة ربط قائمة CLI
      • إضافة القيم الافتراضية للنماذج المساعدة (aux)
      • إضافة الاختبارات ووثائق المستخدم

      لا تحتاج عادةً إلى adapter جديد أو api_mode جديد.

      المسار B — مزوّد أصلي (Native)​

      استخدم هذا المسار عندما لا يتصرّف المزوّد مثل OpenAI chat completions.

      أمثلة موجودة في الشيفرة حاليًا:

      • codex_responses (OpenAI Codex و xAI Grok و Meta Muse Spark عبر api.meta.ai — والأخير يُرسل تلقائيًا prompt_cache_retention: 24h — و Ramp Router عبر api.router.com)
      • anthropic_messages

      يتضمّن هذا المسار كل ما في المسار A، إضافةً إلى:

      • adapter للمزوّد داخل agent/
      • فروع في run_agent.py لبناء الطلبات وإرسالها واستخراج بيانات الاستخدام ومعالجة المقاطعة وتوحيد شكل الاستجابات
      • اختبارات الـ adapter

      قائمة التحقق من الملفات​

      مطلوبة لكل مزوّد مدمج​

      1. hermes_cli/auth.py
      2. hermes_cli/models.py
      3. hermes_cli/runtime_provider.py
      4. hermes_cli/main.py
      5. agent/auxiliary_client.py
      6. agent/model_metadata.py
      7. الاختبارات
      8. الوثائق الموجّهة للمستخدم ضمن website/docs/
      نصيحة

      لا يحتاج hermes_cli/setup.py إلى أي تغييرات. يفوّض معالج الإعداد اختيار المزوّد/النموذج إلى select_provider_and_model() في main.py — وأي مزوّد يُضاف هناك يصبح متاحًا تلقائيًا في hermes setup.

      إضافية للمزوّدين الأصليين / غير المتوافقين مع OpenAI​

      1. agent/<provider>_adapter.py
      2. run_agent.py
      3. pyproject.toml إذا كان المزوّد يتطلّب SDK

      المسار السريع: مزوّدون بمفتاح API بسيط​

      إذا كان مزوّدك مجرد endpoint متوافق مع OpenAI يصادق بمفتاح API واحد، فلا حاجة إلى تعديل auth.py أو runtime_provider.py أو main.py أو أي من الملفات الأخرى في قائمة التحقق الكاملة أدناه.

      كل ما تحتاجه هو:

      1. مجلد إضافة (plugin) ضمن plugins/model-providers/<your-provider>/ يحتوي على:
        • __init__.py — يستدعي register_provider(profile) على مستوى الوحدة
        • plugin.yaml — ملف التعريف (manifest) (name، kind: model-provider، version، description)
      2. هذا كل شيء. تُحمَّل إضافات المزوّدين تلقائيًا في أول مرة يستدعي فيها أي جزء get_provider_profile() أو list_providers() — ويُلتقط كلٌّ من الإضافات المضمّنة (في هذا المستودع) وإضافات المستخدم الموجودة في $HERMES_HOME/plugins/model-providers/.

      عند إضافة إضافة تستدعي register_provider()، يُربط ما يلي تلقائيًا:

      1. عنصر PROVIDER_REGISTRY في auth.py (تحديد بيانات الاعتماد والبحث في متغيرات البيئة)
      2. ضبط api_mode على chat_completions
      3. أخذ base_url من الإعدادات أو من متغير البيئة المُصرَّح به
      4. فحص env_vars حسب ترتيب الأولوية للعثور على مفتاح API
      5. تسجيل قائمة fallback_models للمزوّد
      6. قبول الخيار --provider في CLI لمعرّف المزوّد
      7. تضمين المزوّد في قائمة hermes model
      8. تفويض معالج hermes setup إلى main.py تلقائيًا
      9. عمل صيغة الاسم المستعار provider:model
      10. إرجاع أداة التحديد وقت التشغيل للقيم الصحيحة لـ base_url و api_key
      11. قبول الخيار --provider <name> في CLI لمعرّف المزوّد
      12. قدرة تفعيل النموذج الاحتياطي على التبديل إلى المزوّد بسلاسة

      تتجاوز إضافات المستخدم الموجودة في $HERMES_HOME/plugins/model-providers/<name>/ الإضافات المضمّنة التي تحمل الاسم نفسه (آخر من يكتب يفوز في register_provider()) — وبذلك يستطيع الطرف الثالث تعديل أي profile مدمج أو استبداله دون تحرير المستودع.

      راجع plugins/model-providers/nvidia/ أو plugins/model-providers/gmi/ كقالب، ودليل Model Provider Plugin الكامل لمرجع الحقول وأنماط استخدام الـ hooks وأمثلة متكاملة من البداية إلى النهاية.

      المسار الكامل: OAuth والمزوّدون المعقّدون​

      استخدم قائمة التحقق الكاملة أدناه عندما يحتاج مزوّدك إلى أيٍّ مما يلي:

      • OAuth أو تحديث الـ token (Nous Portal، Codex، Qwen Portal، Copilot)
      • واجهة API بشكل غير متوافق مع OpenAI تتطلّب adapter جديدًا (Anthropic Messages، Codex Responses)
      • اكتشاف مخصّص للـ endpoint أو فحص عدة مناطق (z.ai، Kimi)
      • كتالوج نماذج ثابت منتقى أو جلب حي عبر /models
      • عناصر خاصة بالمزوّد في قائمة hermes model مع مسارات مصادقة مخصّصة

      الخطوة 1: اختر معرّفًا موحّدًا واحدًا للمزوّد​

      اختر معرّفًا واحدًا للمزوّد واستخدمه في كل مكان.

      أمثلة من المستودع:

      • openai-codex
      • kimi-coding
      • minimax-cn

      يجب أن يظهر المعرّف نفسه في:

      • PROVIDER_REGISTRY في hermes_cli/auth.py
      • _PROVIDER_LABELS في hermes_cli/models_catalog_static.py (يعيد hermes_cli/models.py تصديره)
      • _PROVIDER_ALIASES في كلٍّ من hermes_cli/auth.py و hermes_cli/models_catalog_static.py
      • خيارات --provider في CLI داخل hermes_cli/main.py
      • فروع الإعداد / اختيار النموذج
      • القيم الافتراضية للنماذج المساعدة
      • الاختبارات

      إذا اختلف المعرّف بين هذه الملفات، فسيبدو المزوّد نصف مربوط: قد تعمل المصادقة بينما يتجاهله /model أو الإعداد أو التحديد وقت التشغيل دون أي إشعار.

      الخطوة 2: أضف البيانات الوصفية للمصادقة في hermes_cli/auth.py​

      بالنسبة إلى المزوّدين الذين يعتمدون على مفتاح API، أضف عنصر ProviderConfig إلى PROVIDER_REGISTRY يتضمّن:

      • id
      • name
      • auth_type="api_key"
      • inference_base_url
      • api_key_env_vars
      • base_url_env_var اختياريًا

      أضف أيضًا الأسماء المستعارة إلى _PROVIDER_ALIASES.

      استخدم المزوّدين الحاليين كقوالب:

      • مسار مفتاح API البسيط: Z.AI، MiniMax
      • مسار مفتاح API مع اكتشاف الـ endpoint: Kimi، Z.AI
      • تحديد الـ token الأصلي: Anthropic
      • مسار OAuth / مخزن المصادقة: Nous، OpenAI Codex

      أسئلة يجب الإجابة عنها هنا:

      • ما متغيرات البيئة التي يجب أن يفحصها Hermes، وبأي ترتيب أولوية؟
      • هل يحتاج المزوّد إلى تجاوزات لـ base URL؟
      • هل يحتاج إلى فحص الـ endpoint أو تحديث الـ token؟
      • ماذا يجب أن تقول رسالة خطأ المصادقة عند غياب بيانات الاعتماد؟

      إذا كان المزوّد يحتاج إلى أكثر من "البحث عن مفتاح API"، فأضف أداة مخصّصة لتحديد بيانات الاعتماد بدلًا من حشر المنطق في فروع لا علاقة لها به.

      الخطوة 3: أضف كتالوج النماذج والأسماء المستعارة في hermes_cli/models.py​

      حدّث كتالوج المزوّدين حتى يعمل المزوّد في القوائم وفي صيغة provider:model.

      التعديلات المعتادة:

      • _PROVIDER_MODELS
      • _PROVIDER_LABELS
      • _PROVIDER_ALIASES
      • ترتيب عرض المزوّدين داخل list_available_providers()
      • provider_model_ids() إذا كان المزوّد يدعم الجلب الحي عبر /models

      إذا كان المزوّد يوفّر قائمة نماذج حية، فقدّمها أولًا وأبقِ _PROVIDER_MODELS كبديل احتياطي ثابت.

      هذا الملف أيضًا هو ما يجعل مدخلات كهذه تعمل:

      anthropic:claude-sonnet-4-6
      kimi:model-name

      إذا كانت الأسماء المستعارة مفقودة هنا، فقد تنجح مصادقة المزوّد لكنه يفشل رغم ذلك عند تحليل /model.

      الخطوة 4: حدّد بيانات وقت التشغيل في hermes_cli/runtime_provider.py​

      الدالة resolve_runtime_provider() هي المسار المشترك الذي تستخدمه CLI و gateway و cron و ACP والعملاء المساعدون.

      أضف فرعًا يُرجع dict يحتوي على الأقل على:

      {
          "provider": "your-provider",
          "api_mode": "chat_completions",  # or your native mode
          "base_url": "https://...",
          "api_key": "...",
          "source": "env|portal|auth-store|explicit",
          "requested_provider": requested_provider,
      }

      إذا كان المزوّد متوافقًا مع OpenAI، فيجب أن تبقى قيمة api_mode عادةً chat_completions.

      انتبه إلى أولوية مفاتيح API. يحتوي Hermes بالفعل على منطق يمنع تسريب مفتاح OpenRouter إلى endpoints لا علاقة لها به، ويجب أن يكون المزوّد الجديد صريحًا بالقدر نفسه بشأن أي مفتاح يذهب إلى أي base URL.

      الخطوة 5: اربط CLI في hermes_cli/main.py​

      لا يمكن اكتشاف المزوّد حتى يظهر في مسار hermes model التفاعلي.

      حدّث ما يلي في hermes_cli/main.py:

      • القاموس provider_labels
      • القائمة providers في select_provider_and_model()
      • توجيه المزوّد (if selected_provider == ...)
      • خيارات الوسيط --provider
      • خيارات تسجيل الدخول/الخروج إذا كان المزوّد يدعم هذه المسارات
      • دالة _model_flow_<provider>()، أو أعد استخدام _model_flow_api_key_provider() إن كانت مناسبة
      نصيحة

      لا يحتاج hermes_cli/setup.py إلى تغييرات — فهو يستدعي select_provider_and_model() من main.py، لذا يظهر مزوّدك الجديد تلقائيًا في كلٍّ من hermes model و hermes setup.

      الخطوة 6: حافظ على عمل الاستدعاءات المساعدة​

      هناك ملفان مهمان هنا:

      agent/auxiliary_client.py​

      أضف نموذجًا مساعدًا افتراضيًا رخيصًا / سريعًا إلى _API_KEY_PROVIDER_AUX_MODELS إذا كان هذا مزوّدًا مباشرًا بمفتاح API.

      تشمل المهام المساعدة أمورًا مثل:

      • تلخيص الرؤية (vision)
      • تلخيص المحتوى المستخرج من الويب
      • ملخصات ضغط السياق
      • ملخصات البحث في الجلسات
      • تفريغ الذاكرة (memory flushes)

      إذا لم يكن للمزوّد نموذج مساعد افتراضي معقول، فقد تلجأ المهام الجانبية إلى بديل احتياطي سيئ أو تستخدم نموذجًا رئيسيًا مكلفًا على نحو غير متوقع.

      agent/model_metadata.py​

      أضف أطوال السياق لنماذج المزوّد حتى تبقى ميزانية الـ tokens وعتبات الضغط والحدود منطقية.

      الخطوة 7: إذا كان المزوّد أصليًا، أضف adapter ودعمًا في run_agent.py​

      إذا لم يكن المزوّد chat completions عاديًا، فاعزل المنطق الخاص بالمزوّد في agent/<provider>_adapter.py.

      أبقِ run_agent.py مركّزًا على التنسيق (orchestration)؛ إذ يجب أن يستدعي الدوال المساعدة في الـ adapter، لا أن يبني حمولات المزوّد يدويًا ومباشرةً في مواضع متفرقة من الملف.

      يحتاج المزوّد الأصلي عادةً إلى عمل في هذه المواضع:

      ملف adapter جديد​

      المسؤوليات المعتادة:

      • بناء عميل SDK / HTTP
      • تحديد الـ tokens
      • تحويل رسائل المحادثة بأسلوب OpenAI إلى صيغة طلبات المزوّد
      • تحويل مخططات الأدوات (tool schemas) عند الحاجة
      • توحيد استجابات المزوّد وإعادتها إلى الشكل الذي يتوقعه run_agent.py
      • استخراج بيانات الاستخدام وسبب الانتهاء (finish-reason)

      run_agent.py​

      ابحث عن api_mode وراجع كل نقطة تبديل. تحقّق على الأقل من أن:

      • __init__ يختار api_mode الجديد
      • بناء العميل يعمل مع المزوّد
      • _build_api_kwargs() تعرف كيفية تنسيق الطلبات
      • _interruptible_api_call() توجّه الطلب إلى استدعاء العميل الصحيح
      • مسارات المقاطعة / إعادة بناء العميل تعمل
      • التحقق من الاستجابة يقبل شكل استجابة المزوّد
      • استخراج سبب الانتهاء صحيح
      • استخراج استهلاك الـ tokens صحيح
      • تفعيل النموذج الاحتياطي يستطيع التبديل إلى المزوّد الجديد بسلاسة
      • مسارات توليد الملخصات وتفريغ الذاكرة لا تزال تعمل

      ابحث أيضًا في run_agent.py عن self.client.. فأي مسار في الشيفرة يفترض وجود عميل OpenAI القياسي قد يتعطّل عندما يستخدم مزوّد أصلي كائن عميل مختلفًا أو self.client = None.

      التخزين المؤقت للـ prompt وحقول الطلب الخاصة بالمزوّد​

      من السهل أن يتراجع (regress) التخزين المؤقت للـ prompt وإعدادات الضبط الخاصة بالمزوّد.

      أمثلة موجودة بالفعل في الشيفرة:

      • لدى Anthropic مسار أصلي للتخزين المؤقت للـ prompt
      • يحصل OpenRouter على حقول توجيه المزوّدين (provider routing)
      • لا ينبغي أن يتلقى كل مزوّد كل خيار من خيارات الطلب

      عند إضافة مزوّد أصلي، تأكّد جيدًا من أن Hermes لا يُرسل إلا الحقول التي يفهمها ذلك المزوّد فعلًا.

      الخطوة 8: الاختبارات​

      عدّل على الأقل الاختبارات التي تحمي ربط المزوّد.

      المواضع الشائعة:

      • tests/hermes_cli/test_runtime_provider_resolution.py
      • tests/cli/test_cli_provider_resolution.py
      • tests/hermes_cli/test_model_switch_custom_providers.py (والملفات المجاورة tests/hermes_cli/test_model_switch_*.py)
      • tests/hermes_cli/test_setup_model_provider.py
      • tests/run_agent/test_provider_parity.py
      • tests/run_agent/test_run_agent.py
      • tests/test_<provider>_adapter.py للمزوّد الأصلي

      بالنسبة إلى الأمثلة الخاصة بالوثائق فقط، قد تختلف مجموعة الملفات الدقيقة. المهم هو تغطية:

      • تحديد المصادقة
      • قائمة CLI / اختيار المزوّد
      • تحديد المزوّد وقت التشغيل
      • مسار تنفيذ الوكيل
      • تحليل provider:model
      • أي تحويل للرسائل خاص بالـ adapter

      شغّل الاختبارات المستهدفة (أو استخدم scripts/run_tests.sh، الذي يشغّل كل ملف في عملية فرعية مستقلة):

      source venv/bin/activate
      python -m pytest tests/hermes_cli/test_runtime_provider_resolution.py tests/cli/test_cli_provider_resolution.py tests/hermes_cli/test_setup_model_provider.py tests/run_agent/test_provider_parity.py -q

      للتغييرات الأعمق، شغّل مجموعة الاختبارات كاملةً قبل الدفع (push):

      source venv/bin/activate
      python -m pytest tests/ -n0 -q

      الخطوة 9: التحقق الحي​

      بعد الاختبارات، شغّل اختبار دخان (smoke test) حقيقيًا.

      source venv/bin/activate
      python -m hermes_cli.main chat -q "Say hello" --provider your-provider --model your-model

      اختبر أيضًا المسارات التفاعلية إذا غيّرت القوائم:

      source venv/bin/activate
      python -m hermes_cli.main model
      python -m hermes_cli.main setup

      بالنسبة إلى المزوّدين الأصليين، تحقّق كذلك من استدعاء أداة واحد على الأقل، لا من استجابة نصية عادية فقط.

      الخطوة 10: حدّث الوثائق الموجّهة للمستخدم​

      إذا كان المزوّد مُعدًّا ليُطرح كخيار من الدرجة الأولى، فحدّث وثائق المستخدم أيضًا:

      • website/docs/getting-started/quickstart.md
      • website/docs/user-guide/configuration.md
      • website/docs/reference/environment-variables.md

      قد يربط المطوّر المزوّد ربطًا مثاليًا، ومع ذلك يترك المستخدمين عاجزين عن اكتشاف متغيرات البيئة المطلوبة أو مسار الإعداد.

      قائمة التحقق للمزوّد المتوافق مع OpenAI​

      استخدم هذه القائمة إذا كان المزوّد يعتمد chat completions القياسي.

      • إضافة ProviderConfig في hermes_cli/auth.py
      • إضافة الأسماء المستعارة في hermes_cli/auth.py و hermes_cli/models.py
      • إضافة كتالوج النماذج في hermes_cli/models.py
      • إضافة فرع وقت التشغيل في hermes_cli/runtime_provider.py
      • إضافة ربط CLI في hermes_cli/main.py (يرث setup.py ذلك تلقائيًا)
      • إضافة النموذج المساعد في agent/auxiliary_client.py
      • إضافة أطوال السياق في agent/model_metadata.py
      • تحديث اختبارات وقت التشغيل / CLI
      • تحديث وثائق المستخدم

      قائمة التحقق للمزوّد الأصلي​

      استخدم هذه القائمة عندما يحتاج المزوّد إلى مسار بروتوكول جديد.

      • كل ما في قائمة التحقق للمزوّد المتوافق مع OpenAI
      • إضافة الـ adapter في agent/<provider>_adapter.py
      • دعم api_mode الجديد في run_agent.py
      • مسار المقاطعة / إعادة البناء يعمل
      • استخراج بيانات الاستخدام وسبب الانتهاء يعمل
      • المسار الاحتياطي (fallback) يعمل
      • إضافة اختبارات الـ adapter
      • نجاح اختبار الدخان الحي

      أخطاء شائعة​

      1. إضافة المزوّد إلى المصادقة دون إضافته إلى تحليل النماذج​

      يؤدي ذلك إلى تحديد بيانات الاعتماد بشكل صحيح، بينما تفشل مدخلات /model و provider:model.

      2. نسيان أن config["model"] قد يكون نصًا أو dict​

      يجب على كثير من شيفرة اختيار المزوّد توحيد الشكلين كليهما.

      3. افتراض أن المزوّد المدمج ضروري​

      إذا كانت الخدمة مجرد خدمة متوافقة مع OpenAI، فقد يحلّ المزوّد المخصّص مشكلة المستخدم بالفعل بتكلفة صيانة أقل.

      4. نسيان المسارات المساعدة​

      قد يعمل مسار المحادثة الرئيسي بينما يفشل التلخيص أو تفريغ الذاكرة أو أدوات الرؤية المساعدة لأن توجيه النماذج المساعدة لم يُحدَّث قط.

      5. فروع المزوّد الأصلي المختبئة في run_agent.py​

      ابحث عن api_mode و self.client.. ولا تفترض أن مسار الطلب الواضح هو المسار الوحيد.

      6. إرسال إعدادات خاصة بـ OpenRouter فقط إلى مزوّدين آخرين​

      الحقول مثل توجيه المزوّدين مكانها فقط لدى المزوّدين الذين يدعمونها.

      7. تحديث hermes model دون hermes setup​

      يحتاج كلا المسارين إلى معرفة المزوّد.

      أهداف بحث مفيدة أثناء التنفيذ​

      إذا كنت تتعقّب كل المواضع التي يمسّها المزوّد، فابحث عن هذه الرموز:

      بناء إضافة لـ Hermes

      يرشدك هذا الدليل خلال بناء إضافة (plugin) كاملة لـ Hermes من الصفر. في النهاية ستكون لديك إضافة عاملة تحتوي على عدة أدوات، و hooks لدورة الحياة، وملفات بيانات مرفقة، ومهارة مضمّنة — أي كل ما يدعمه نظام الإضافات.

      لست متأكدًا من الدليل الذي تحتاجه؟

      لدى Hermes عدة واجهات مستقلة قابلة للتوسعة — بعضها يستخدم واجهات register_* البرمجية في Python، وبعضها الآخر قائم على الإعدادات أو على مجلدات جاهزة للإسقاط. استخدم هذه الخريطة أولًا:

      إضافات منتجات الأطراف الثالثة تُوزَّع مستقلة — لا ضمن الشيفرة الأساسية

      الإضافات التي تدمج منتج شخص آخر أو مشروعه — مثل backends المراقبة/المقاييس، وموصلات SaaS الخاصة بالمورّدين، ولوحات التحليلات، والتكاملات مع الخدمات المدفوعة — تُبنى وتُوزَّع على شكل مستودعات إضافات مستقلة، ولا تُدمج في NousResearch/hermes-agent. يثبّتها المستخدمون في ~/.hermes/plugins/ أو عبر pip entry point؛ وكل ما في هذا الدليل يعمل بالطريقة نفسها من مستودع مستقل. هذا قرار يتعلّق بالترابط والصيانة (فالشيفرة الأساسية تتطوّر بسرعة ونحن لا نملك الـ backend الخاص بك)، وليس معيارًا للجودة — فقد تكون الإضافة ممتازة ومع ذلك يكون مكانها في مستودعها الخاص. روّج لها في قناة #plugins-skills-and-skins على Discord الخاص بـ Nous Research. راجع CONTRIBUTING.md للاطلاع على السياسة.

      حزم Portable Agent Plugins v1​

      يستطيع Hermes أيضًا تثبيت وتحميل الحزم المكوّنة من مجلدات والتي تستهدف صيغة Agent Plugins v1.0.0. هذا adapter توافق للمكوّنات المحمولة التي يمتلكها Hermes بالفعل، ولا يحلّ محل الإضافات الأصلية المكوّنة من plugin.yaml مع register(ctx).

      my-portable-plugin/
      ├── plugin.json
      ├── skills/
      │   └── summarize/
      │       ├── SKILL.md
      │       └── references/
      └── mcp.json

      ثبّت الحزمة المحمولة وفعّلها عبر سير العمل المعتاد:

      hermes plugins install owner/repository --no-enable
      hermes plugins list
      hermes plugins enable <plugin-name>

      تكون الحزم المحمولة معطّلة بعد التثبيت ما لم تفعّلها صراحةً. قد توفّر الحزمة المفعّلة مجلدات skills/*/SKILL.md المباشرة وخوادم MCP من نوع stdio مُعرّفة في ملف mcp.json الموجود في الجذر. المهارات للقراءة فقط، وذات نطاقات أسماء (namespaced)، وتُحمَّل عبر skills_list مع skill_view. تُمرَّر أوامر MCP كـ token تنفيذي واحد مع قائمة وسائط منفصلة، ولا تمرّ أبدًا عبر shell. استخدم skills_list لاكتشاف الاسم المؤهّل الكامل للمهارة. تأخذ نطاقات أسماء المهارات المحمولة الصيغة الحتمية agent-plugin-<slug>-<hash>، المشتقة من مفتاح الإضافة المكتشف حتى لا تتصادم الأسماء بعد تنقيتها.

      يتحقّق Hermes محليًا من plugin.json، والـ frontmatter الخاص بـ Agent Skills، والمواقع الثابتة للمكوّنات، و mcp.json، والمسارات المحلولة، واحتواء الروابط الرمزية (symlinks). ولا يجلب مخططات JSON أثناء تحميل الحزمة. تُتخطّى المهارة المعطوبة أو عنصر MCP المعطوب عند حدوده الخاصة ما دامت المكوّنات الشقيقة الصالحة قادرة على التحميل. يشير PLUGIN_ROOT إلى جذر الحزمة المحلول، ويشير PLUGIN_DATA إلى مجلد قابل للكتابة خاص بالـ profile يديره Hermes. القيم المُصرَّح بها في env الخاص بـ MCP المحمول هي بيانات حزمة مرئية، وليست آلية لتخزين الأسرار. لا تضع بيانات الاعتماد في mcp.json.

      تدعم المجموعة الفرعية المحمولة الحالية عناصر MCP من نوع stdio و Streamable HTTP. تُوجَّه عناصر streamable-http المحمولة عبر عميل MCP البعيد الأصلي الموجود أصلًا في Hermes (وقت التشغيل نفسه الذي يشغّل إعدادات mcp_servers القائمة على URL)، مع فرض قواعد الحدود في v1: يجب أن يكون الـ URL مطلقًا بصيغة http(s) دون معلومات مستخدم أو fragment، ولا يُقبل HTTP العادي إلا لمضيفي localhost/loopback، ولا تُمرَّر الترويسات (headers) المُعدّة أبدًا عبر إعادة توجيه إلى أصل مختلف (cross-origin redirect). يُبلَّغ عن عناصر sse القديمة وتُتخطّى. لا تُعرّف Agent Plugins v1 الثقة أو الصلاحيات أو المصدر (provenance) أو sandbox. وتفعيل الحزمة يمنح تعليماتها وملفها التنفيذي المحلي وضع الثقة الكاملة نفسه الممنوح لإضافات Hermes المثبّتة الأخرى.

      يصف التوصيف المعروض على الموقع حاليًا الإصدار v1.0.0 بأنه Working Draft، بينما يسجّله مستودع التوصيف ذو الإصدارات بأنه Published. يبني Hermes سلوكه على معرّفات مخطط v1.0.0 المعتمدة والنص المعياري، لا على أيٍّ من تسميتي الحالة القابلتين للتغيير. هذه مجموعة فرعية مدعومة صراحةً، وليست ادعاءً بالتوافق الكامل مع Agent Plugins.

      عقد التوافق للإضافات الأصلية​

      الإضافات الأصلية المكوّنة من plugin.yaml مع register(ctx) محمية بالسلوك، لا برقم API عام واحد للإضافات. لا يوفّر Hermes PLUGIN_API_VERSION، ولا يشترط تطابق api: على مستوى ملف التعريف كله، ولا يُرفق رقم إصدار API بقيم لا علاقة لها بذلك. يجب أن تستمر الإضافة التي تستخدم سلوكًا موثّقًا في العمل بعد أي ترقية عادية لـ Hermes.

      قواعد التوافق هي:

      • التطوّر بالإضافة فقط. لا تُحذف دوال PluginContext الموثّقة ولا يُعاد تسميتها. المعاملات الجديدة اختيارية، ولها قيم افتراضية، ويجب أن تكون keyword-only. ولا تُحذف حقول الإرجاع الحالية ولا يتغيّر نوعها بصمت.
      • حمولات الـ hooks حمولات كلمات مفتاحية. تُضاف بيانات الـ hooks الجديدة كحقول كلمات مفتاحية، ولا يحدث ذلك أبدًا بتغيير معنى حقل موجود أو موضعه. يفحص Hermes تواقيع دوال الاستدعاء (callbacks): تتلقى الدالة القديمة الحقول التي تصرّح بها، بينما تتلقى الدالة التي تحتوي على **kwargs الحمولة الحالية كاملةً. يجب أن تقبل الإضافات الجديدة **kwargs حتى تتمكّن من تلقي البيانات الإضافية دون تغيير آخر في التوقيع.
      • ملفات التعريف مفتوحة للإضافات. تُتجاهل حقول plugin.yaml غير المعروفة. لذلك تستطيع إصدارات Hermes الأقدم تحميل إضافة يحتوي ملف تعريفها على بيانات وصفية قدّمها إصدار أحدث، بشرط أن تستخدم شيفرة الإضافة نفسها سلوكًا مدعومًا وقت التشغيل.
      • تنمو واجهات المزوّدين عبر القيم الافتراضية. لكل دالة مزوّد جديدة تطبيق افتراضي. وسياق الاستدعاء الجديد اختياري، ولا يُمرَّر إلا عندما يُظهر فحص التوقيع أن المزوّد يقبله. أما إضافة دالة مجردة (abstract) أو وسيط يُمرَّر دون شرط فتتطلّب فترة ترحيل (migration window) بدلًا من تغيير مفاجئ في التوقيع دفعة واحدة.
      • ضع رقم إصدار للعقد الذي يعبر حدًّا. يمكن أن تحمل القدرة رقم إصدار مخطط خاص بها عندما تُعرّف حمولة نقل أو صيغة تخزين دائمة (مثل حمولات المراقِبين أو حالة مصادر الأسرار). أبقِ الحقول قابلة للإضافة فقط ضمن ذلك المخطط المحلي. يجب أن تبقى حالة الإضافة المخزّنة وإعداداتها قابلة للقراءة، أو أن تأتي مع ترحيل صريح؛ ويجب أن تظل الجلسات المستأنفة المكتوبة بالصيغة القديمة قابلة لإعادة التشغيل. لا تُضِف قيم إصدار حرفية إلى قيم الاستدعاء أو السياق التي لا علاقة لها بذلك.

      سياسة الإهمال (Deprecation)​

      لا يجوز إهمال سلوك موثّق للإضافات الأصلية إلا بتوفّر كل ما يلي:

      1. بديل وتعليمات ترحيل في دليل الإضافات وملاحظات الإصدار؛
      2. تحذير يُصدر مرة واحدة على الأكثر لكل عملية، يذكر البديل وأقرب إصدار سيُزال فيه السلوك؛
      3. دعم السلوك القديم على مدى إصدارين فرعيين (minor) لاحقين على الأقل؛ و
      4. تغطية توافق قائمة على السلوك لكلٍّ من المسار القديم والبديل طوال تلك الفترة.

      يجب أن تتضمّن الإزالة بعد انتهاء الفترة أي ترحيل لازم للبيانات المخزّنة أو الجلسات القابلة للاستئناف. وعمليًا، تُفضَّل الأسماء المستعارة والـ adapters الإضافية على الإزالة.

      يفرض Hermes هذا العقد عبر مجموعات اختبار ثابتة (frozen fixtures) لإضافات خارجية تُكتشف من HERMES_HOME معزول. تحمّل هذه الاختبارات الإضافة وتستدعيها عبر PluginManager؛ وتتحقّق من نتائج التسجيل والاستدعاء الفعلية بدلًا من قوائم الرموز الداخلية أو شكل الشيفرة المصدرية.

      تفكيك الوحدات في سبتمبر 2026: تنتهي مسارات الاستيراد القديمة في 2026-09-14​

      قُسّمت الأجزاء الداخلية لـ Hermes إلى وحدات شقيقة بصيغة <stem>_<topic> في سبتمبر 2026 (PR #102117). لم تكن مسارات الاستيراد الداخلية يومًا جزءًا من عقد الإضافات المذكور أعلاه، لكن كثيرًا من الإضافات استخدمتها. يظل كل اسم نُقل قابلًا للاستيراد من وحدته القديمة حتى 2026-09-14، ثم تُزال طبقة التوافق.

      • افحص إضافتك: يعرض hermes plugins compat /path/to/your/plugin كل file:line يحتوي على المسار القديم مع المسار الجديد، وينتهي برمز الخروج 1 ما دام أيٌّ منها متبقيًا. ويحتوي COMPAT_MANIFEST.md في المستودع على الخريطة الكاملة.
      • ما يراه المستخدمون: إشعارًا أسفل شعار CLI، وفي hermes doctor وبعد hermes update، ونافذة حوار لمرة واحدة في Desktop تذكر اسم الإضافة. كما يُصدر كل استيراد عبر مسار قديم التحذير HermesPluginCompatWarning مرة واحدة لكل عملية.
      • بدءًا من 2026-09-14: الإضافات التي لا تزال تستورد مسارات قديمة لا تُحمَّل (يظهر السبب في hermes plugins list). يمكن للمستخدمين فرض التحميل باستخدام plugins.allow_deprecated_imports: true حتى تُزال الطبقة فعليًا، وعندها تُطلق المسارات القديمة ImportError.

      ما الذي ستبنيه​

      إضافة calculator (آلة حاسبة) تحتوي على أداتين:

      • calculate — تقييم التعابير الرياضية (2**16، sqrt(144)، pi * 5**2)
      • unit_convert — التحويل بين الوحدات (100 F → 37.78 C، 5 km → 3.11 mi)

      إضافةً إلى hook تسجّل كل استدعاء أداة، وملف مهارة مضمّن.

      التحقق باستخدام Plugin Doctor​

      يشغّل hermes plugins doctor [path-or-id] آليات اكتشاف المجلدات وتحليل ملف التعريف والاستيراد ذي النطاق (namespaced import) و register(ctx) وسجل الـ hooks وسجل الأدوات نفسها التي يستخدمها Hermes. ويبلّغ عن أسماء الـ hooks غير الصالحة، ودوال الاستدعاء التي لا تقبل **kwargs، وحالات فشل التسجيل، والتباين بين الأدوات/الـ hooks المُصرَّح بها وتلك المسجّلة فعليًا. مرّر --ci للخروج برمز غير صفري عند وجود خطأ:

      hermes plugins doctor . --ci

      يستخدم Doctor مجلد HERMES_HOME مؤقتًا، ويستعيد حالة تسجيل الإضافات بعد الفحص، ويحظر اتصالات Python socket المباشرة لكشف أي وصول غير مقصود إلى الشبكة أثناء التسجيل. هذا ليس sandbox: فشيفرة الإضافة لا تزال تُنفَّذ داخل العملية بصلاحيات المستخدم الحالي ويمكنها إنشاء عمليات فرعية، لذا لا تشغّل Doctor إلا على شيفرة تثق بها بما يكفي لاستيرادها.

      الخطوة 2: اكتب ملف التعريف (manifest)​

      أنشئ plugin.yaml:

      name: calculator
      version: 1.0.0
      description: Math calculator — evaluate expressions and convert units
      provides_tools:
        - calculate
        - unit_convert
      provides_hooks:
        - post_tool_call

      يقول هذا لـ Hermes: "أنا إضافة اسمها calculator، وأوفّر أدوات و hooks." الحقلان provides_tools و provides_hooks قائمتان بما تسجّله الإضافة.

      حقول اختيارية يمكنك إضافتها:

      author: Your Name
      requires_env:          # gate loading on env vars; prompted during install

        - name: OTHER_KEY    # rich format — shows description/url during install

        - llm.model_override # choose the model for host-owned LLM calls

      التصريح بالقدرات (Capabilities)​

      إذا كانت إضافتك تحتاج إلى واجهة مضيف ذات امتيازات — مثل تجاوز أداة مدمجة، أو اختيار النموذج لاستدعاءات ctx.llm، إلخ — فصرّح بها في capabilities:. عند التثبيت/التفعيل يرى المستخدم القائمة ويوافق عليها مرة واحدة؛ وإذا أضاف إصدار لاحق قدرة جديدة، يطلب مسار التحديث الموافقة مجددًا على الإضافة الجديدة فقط. القدرات غير المُصرَّح بها أو غير الموافق عليها تكون ببساطة معطّلة (fail closed)، لذا تحقّق من توفّرها قبل استخدامها وتعامل مع غيابها بسلاسة:

      def register(ctx):
          if ctx.has_capability("tools.override"):
              ctx.register_tool(..., override=True)
          else:
              ctx.register_tool(...)   # register under a non-conflicting name

      معرّفات القدرات المعروفة: tools.override، llm.provider_override، llm.model_override، llm.agent_id_override، llm.profile_override، llm.task_override (راجع hermes_cli/plugin_capabilities.py للاطلاع على السجل المعتمد). تُتجاهل المعرّفات غير المعروفة. لا تزال مفاتيح الإعدادات القديمة الخاصة بكل قدرة (plugins.entries.<id>.allow_tool_override، …) تعمل لكنها مهملة (deprecated) — صرّح بالقدرات بدلًا منها حتى يحصل المستخدمون على شاشة موافقة واحدة قابلة للتدقيق. القدرات موافقة + تدقيق، وهي ليست sandbox: فهي تتحكّم في الوصول إلى واجهات API الخاصة بالمضيف، لا أكثر.

      الإضافات الموزّعة عبر pip لا تملك مجلد plugin.yaml بعد تثبيتها، لذا صرّح بالقدرات في البيانات الوصفية للتوزيعة بدلًا من ذلك، عبر مجموعة entry-point المرافقة hermes_agent.plugin_capabilities. يُسمّى كل تصريح بالصيغة <plugin-id>.<capability-id> ويشير إلى الكائن نفسه الذي يشير إليه entry point الخاص بك hermes_agent.plugins:

      [project.entry-points."hermes_agent.plugins"]
      calculator = "my_pkg:register"

      [project.entry-points."hermes_agent.plugin_capabilities"]
      "calculator.tools.override" = "my_pkg:register"

      يقرأ Hermes هذه التصريحات من البيانات الوصفية المثبّتة دون استيراد شيفرتك، لذا يبقى hermes plugins capabilities ومسار الموافقة دقيقين في حالات التثبيت عبر pip.

      مرجع Manifest v2​

      يدعم plugin.yaml أيضًا مخطط v2 إضافيًا متوافقًا (#64165). كل حقل فيه اختياري؛ وملف التعريف الذي لا يحتوي على manifest_version هو ملف تعريف v1 ويبقى مدعومًا بالكامل إلى الأبد. لا تكسر الحقول غير المعروفة التحميل أبدًا — إذ تُتجاهل مع تحذير (توافق مستقبلي)، كما أن قيمة manifest_version الأحدث مما يفهمه إصدار Hermes الحالي تُحمَّل رغم ذلك مع تحذير.

      الحقلالنوعالمعنى
      manifest_versionintإصدار صيغة ملف التعريف. عند غيابه = 1. الحد الأقصى الحالي: 2. مستقل عن api_version.
      api_versionintجيل API الإضافات وقت التشغيل الذي تستهدفه الإضافة (واجهة ctx / تواقيع الـ hooks). وهو عمدًا محور منفصل عن manifest_version — فيمكن لإضافة api_version: 1 استخدام ملف تعريف v2.
      requires_pluginslistالاعتماديات بين الإضافات: - id: other-plugin مع version_range: ">=1.0,<2" اختياريًا. استشارية: تُسجّل الاعتمادية المفقودة تحذيرًا واضحًا لكن الإضافة تُحمَّل رغم ذلك — تحقّق وقت التشغيل باستخدام ctx.has_plugin("other-plugin"). يراعي ترتيب التحميل هذه العلاقات: عندما تتطلّب A الإضافة B، تُنفَّذ register() الخاصة بـ B قبل تلك الخاصة بـ A (ترتيب طوبولوجي مع كسر التعادل أبجديًا؛ وتُصدر الدورات تحذيرًا ويُعاد إلى الترتيب الأبجدي).
      python_dependencieslist من strمتطلبات pip المُصرَّح بها (مثل "requests>=2.0,<3"). للتصريح فقط — يتحقّق Hermes منها، ويُظهر hermes plugins install / hermes plugins doctor المفقود منها مع تلميح pip install، لكن Hermes لا يثبّتها تلقائيًا أبدًا. حدّد الحدود العليا للإصدارات.
      config_schemamappingوصف شبيه بـ JSON-schema للمفاتيح الموجودة ضمن plugins.entries.<id>.settings: api_url: {type: str, default: "", description: "...", required: false}. يُتحقَّق منه عند التحميل؛ وتُسجّل حالات عدم التطابق تحذيرات قابلة للتنفيذ تذكر المفتاح والنوع المتوقع — ولا تتسبّب أبدًا في فشل التحميل. الأنواع: str، int، float، bool، list، dict (إضافةً إلى الأسماء المستعارة في JSON-schema).
      licensestrمعرّف ترخيص بأسلوب SPDX (مثل MIT).
      homepagestrرابط URL للمشروع.
      tagslist من strوسوم اكتشاف حرة الصياغة (مثل [gateway, telegram]).
      # plugin.yaml — manifest v2 example
      name: my-plugin
      version: 1.2.0
      manifest_version: 2
      api_version: 1
      license: MIT
      homepage: https://github.com/owner/my-plugin
      tags: [gateway, demo]
      requires_plugins:
        - id: other-plugin
          version_range: ">=1.0,<2"
      python_dependencies:
        - "somepkg>=1.0,<2"     # surfaced, never auto-installed
      config_schema:
        api_url: {type: str, default: "", description: "Service endpoint"}
      عزل اعتماديات pip مؤجَّل

      الحقل python_dependencies مخصّص عمدًا للتصريح والإظهار فقط. فتثبيت حزم عشوائية في الـ venv المشترك لـ Hermes يفتح بابًا للتعارضات ولمخاطر سلسلة التوريد (supply-chain)، لذا فإن تصميم العزل لآلية التثبيت (التثبيت عبر ملف قيود مقابل قفل المضيف، أو مجلدات مضمّنة خاصة بكل إضافة، أو اكتشاف التعارض مع الرفض) عمل لاحق مؤجّل صراحةً — راجع مراجعة الجولة الثانية على #64165 و #15220. تُبنى حزم الإضافات (#64166) على حقول v2 هذه.

      الخطوة 4: اكتب معالجات الأدوات (handlers)​

      أنشئ tools.py — وهي الشيفرة التي تُنفَّذ فعليًا عندما يستدعي LLM أدواتك:

      """Tool handlers — the code that runs when the LLM calls each tool."""

      import json
      import math

      # Safe globals for expression evaluation — no file/network access
      _SAFE_MATH = {
          "abs": abs, "round": round, "min": min, "max": max,
          "pow": pow, "sqrt": math.sqrt, "sin": math.sin, "cos": math.cos,
          "tan": math.tan, "log": math.log, "log2": math.log2, "log10": math.log10,
          "floor": math.floor, "ceil": math.ceil,
          "pi": math.pi, "e": math.e,
          "factorial": math.factorial,
      }


      def calculate(args: dict, **kwargs) -> str:
          """Evaluate a math expression safely.

          Rules for handlers:
          1. Receive args (dict) — the parameters the LLM passed
          2. Do the work
          3. Return a JSON string — ALWAYS, even on error
          4. Accept **kwargs for forward compatibility
          """
          expression = args.get("expression", "").strip()
          if not expression:
              return json.dumps({"error": "No expression provided"})

          try:
              result = eval(expression, {"__builtins__": {}}, _SAFE_MATH)
              return json.dumps({"expression": expression, "result": result})
          except ZeroDivisionError:
              return json.dumps({"expression": expression, "error": "Division by zero"})
          except Exception as e:
              return json.dumps({"expression": expression, "error": f"Invalid: {e}"})


      # Conversion tables — values are in base units
      _LENGTH = {"m": 1, "km": 1000, "mi": 1609.34, "ft": 0.3048, "in": 0.0254, "cm": 0.01}
      _WEIGHT = {"kg": 1, "g": 0.001, "lb": 0.453592, "oz": 0.0283495}
      _DATA = {"B": 1, "KB": 1024, "MB": 1024**2, "GB": 1024**3, "TB": 1024**4}
      _TIME = {"s": 1, "ms": 0.001, "min": 60, "hr": 3600, "day": 86400}


      def _convert_temp(value, from_u, to_u):
          # Normalize to Celsius
          c = {"F": (value - 32) * 5/9, "K": value - 273.15}.get(from_u, value)
          # Convert to target
          return {"F": c * 9/5 + 32, "K": c + 273.15}.get(to_u, c)


      def unit_convert(args: dict, **kwargs) -> str:
          """Convert between units."""
          value = args.get("value")
          from_unit = args.get("from_unit", "").strip()
          to_unit = args.get("to_unit", "").strip()

          if value is None or not from_unit or not to_unit:
              return json.dumps({"error": "Need value, from_unit, and to_unit"})

          try:
              # Temperature
              if from_unit.upper() in {"C","F","K"} and to_unit.upper() in {"C","F","K"}:
                  result = _convert_temp(float(value), from_unit.upper(), to_unit.upper())
                  return json.dumps({"input": f"{value} {from_unit}", "result": round(result, 4),
                                   "output": f"{round(result, 4)} {to_unit}"})

              # Ratio-based conversions
              for table in (_LENGTH, _WEIGHT, _DATA, _TIME):
                  lc = {k.lower(): v for k, v in table.items()}
                  if from_unit.lower() in lc and to_unit.lower() in lc:
                      result = float(value) * lc[from_unit.lower()] / lc[to_unit.lower()]
                      return json.dumps({"input": f"{value} {from_unit}",
                                       "result": round(result, 6),
                                       "output": f"{round(result, 6)} {to_unit}"})

              return json.dumps({"error": f"Cannot convert {from_unit} → {to_unit}"})
          except Exception as e:
              return json.dumps({"error": f"Conversion failed: {e}"})

      قواعد أساسية للمعالجات:

      1. التوقيع: def my_handler(args: dict, **kwargs) -> str
      2. قيمة الإرجاع: سلسلة JSON دائمًا، سواء في حالة النجاح أو الخطأ.
      3. لا ترفع استثناءات أبدًا: التقط جميع الاستثناءات، وأرجع JSON يصف الخطأ بدلًا من ذلك.
      4. اقبل **kwargs: قد يمرّر Hermes سياقًا إضافيًا في المستقبل.

      الخطوة 5: اكتب التسجيل​

      أنشئ __init__.py — هذا الملف يربط المخططات بالمعالِجات:

      """Calculator plugin — registration."""

      import logging

      from . import schemas, tools

      logger = logging.getLogger(__name__)

      # Track tool usage via hooks
      _call_log = []

      def _on_post_tool_call(tool_name, args, result, task_id, **kwargs):
          """Hook: runs after every tool call (not just ours)."""
          _call_log.append({"tool": tool_name, "session": task_id})
          if len(_call_log) > 100:
              _call_log.pop(0)
          logger.debug("Tool called: %s (session %s)", tool_name, task_id)


      def register(ctx):
          """Wire schemas to handlers and register hooks."""
          ctx.register_tool(name="calculate",    toolset="calculator",
                            schema=schemas.CALCULATE,    handler=tools.calculate)
          ctx.register_tool(name="unit_convert", toolset="calculator",
                            schema=schemas.UNIT_CONVERT, handler=tools.unit_convert)

          # This hook fires for ALL tool calls, not just ours
          ctx.register_hook("post_tool_call", _on_post_tool_call)

      ما تفعله register():

      • تُستدعى مرة واحدة بالضبط عند بدء التشغيل
      • ctx.register_tool() يضع أداتك في السجل (registry) — يراها النموذج فورًا
      • ctx.register_hook() يشترك في أحداث دورة الحياة
      • ctx.register_cli_command() يسجّل أمرًا فرعيًا في CLI (مثل hermes my-plugin <subcommand>)
      • ctx.register_command() يسجّل slash command داخل الجلسة (مثل /myplugin <args> داخل محادثة CLI / gateway) — انظر تسجيل Slash Commands أدناه
      • ctx.dispatch_tool(name, arguments) — يستدعي أي أداة أخرى (مدمجة أو من إضافة أخرى) مع ربط سياق الوكيل الأصلي (الموافقات، بيانات الاعتماد، task_id) تلقائيًا. مفيد من معالِجات slash command التي تحتاج إلى استدعاء terminal أو read_file أو أي أداة أخرى كما لو كان النموذج قد استدعاها مباشرةً.
      • تصل ctx.get_config() / ctx.set_config() إلى مساحة اسم إعدادات هذه الإضافة فقط؛ ويخزّن ctx.state بيانات تشغيل مملوكة للإضافة تحت الـ profile النشط.
      • إذا تعطّلت هذه الدالة، تُعطَّل الإضافة لكن Hermes يستمر بشكل طبيعي

      مثال على dispatch_tool — slash command يشغّل أداة:

      def handle_scan(ctx, raw_args: str):
          """Implement /scan by invoking the terminal tool through the registry."""
          result = ctx.dispatch_tool("terminal", {"command": f"find . -name '{raw_args}'"})
          return result  # returned to the caller's chat UI

      def register(ctx):
          # Handlers receive a single raw_args string; close over ctx via a lambda.
          ctx.register_command(
              "scan",
              lambda raw: handle_scan(ctx, raw),
              description="Find files matching a glob",
          )

      تمرّ الأداة المُستدعاة عبر خطوط أنابيب الموافقة والتنقيح (redaction) والميزانية العادية — إنها استدعاء أداة حقيقي، لا اختصار يتجاوزها.

      تخزين الإعدادات وحالة التشغيل​

      استخدم مفاتيح إعدادات نسبية للإضافة لأجل السلوك المرئي للمستخدم. يحسم Hermes مواقعها تحت plugins.entries.<plugin-id>.settings ويرفض المسارات العالمية، والعابرة للإضافات، والمسارات التي تحاول الاجتياز (traversal):

      def register(ctx):
          endpoint = ctx.get_config("endpoint", default="https://example.invalid")
          retries = ctx.get_config("retry.attempts", default=3)

          ctx.set_config("endpoint", endpoint)
          ctx.set_config("retry.attempts", retries)

      استخدم ctx.state للمؤشرات (cursors) والذاكرة المؤقتة (cache) وبيانات إزالة التكرار المملوكة للإضافة بدلًا من وضع محاسبة وقت التشغيل في config.yaml:

      def register(ctx):
          cursor = ctx.state.get("cursor", default={"page": 0})
          ctx.state.set("cursor", {"page": cursor["page"] + 1})

      الحالة (state) محدَّدة بالـ profile، وتُستبدَل ذريًا، وآمنة عبر كاتبين متزامنين، ومحدودة بـ 10 ميبيبايت لكل إضافة. تشترك الحزم المحمولة في نفس الدليل مع PLUGIN_DATA الخاص بها؛ وتحصل الإضافات الأصلية على مساحة اسم مقاومة للتصادم وآمنة على Windows. يُبلَّغ عن الحالة الموجودة غير سليمة البنية وتُحفَظ كما هي.

      للإعدادات والحالة مالكان مختلفان: الإعدادات سلوك مرئي للمستخدم في config.yaml، بينما الحالة بيانات تشغيل مملوكة للإضافة تحت <HERMES_HOME>/plugin-data/. لا تكشف أي من الواجهتين مساحة اسم إضافة أخرى.

      • أسباب التخطّي: disabled via config، not enabled in config، exclusive plugin، no plugin.yaml, depth cap reached
      • عند التحميل: الإضافة قيد الاستيراد، بالإضافة إلى ملخّص من سطر واحد لما سجّلته register(ctx) (الأدوات، والـ hooks، وslash commands، وأوامر CLI)
      • عند فشل التحليل (parse): تتبّع استثناء كامل (أخطاء ماسح YAML، إلخ)
      • عند فشل register(): تتبّع كامل يشير إلى السطر في ملف __init__.py الخاص بك الذي رفع الخطأ

      تُكتب نفس السجلات دائمًا إلى ~/.hermes/logs/agent.log عند مستوى WARNING (الإخفاقات فقط) ومستوى DEBUG (كل شيء) عند ضبط متغير البيئة. لذا إذا لم تستطع التشغيل مع متغير البيئة (مثلًا من داخل gateway)، تابع ملف السجل بدلًا من ذلك:

      hermes logs --level WARNING | grep -i plugin

      الأسباب الشائعة لعدم ظهور إضافة:

      • غير مفعّلة في الإعدادات — الإضافات اختيارية (opt-in). نفّذ hermes plugins enable <name> (يأتي الاسم من مُخرَج plugins list، والذي قد يكون <category>/<plugin> للتخطيطات المتداخلة).
      • بنية دليل خاطئة: تستخدم الحزم الأصلية ~/.hermes/plugins/<plugin-name>/plugin.yaml (مسطّحة) أو مستوى فئة واحد. تستخدم الحزم المحمولة plugin.json جذريًا في نفس المواقع. يُتجاهَل أي شيء أعمق من ذلك.
      • __init__.py مفقود: تحتاج الحزم الأصلية إلى كل من plugin.yaml و__init__.py مع دالة register(ctx). لا تستورد الحزم المحمولة Python ولا تتطلّب __init__.py.
      • kind خاطئ — تحتاج مهايئات gateway إلى kind: platform في بياناتها الوصفية. تُكتشَف مزوّدات الذاكرة تلقائيًا كـ kind: exclusive وتُوجَّه عبر إعداد memory.provider بدلًا من plugins.enabled.

      البنية النهائية لإضافتك​

      ~/.hermes/plugins/calculator/
      ├── plugin.yaml      # "I'm calculator, I provide tools and hooks"
      ├── __init__.py      # Wiring: schemas → handlers, register hooks
      ├── schemas.py       # What the LLM reads (descriptions + parameter specs)
      └── tools.py         # What runs (calculate, unit_convert functions)

      • البيان (Manifest) يعلن ماهية الإضافة
      • المخططات (Schemas) تصف الأدوات لأجل LLM
      • المعالِجات (Handlers) تنفّذ المنطق الفعلي
      • التسجيل (Registration) يربط كل شيء معًا

      شحن ملفات بيانات​

      ضع أي ملفات في دليل الإضافة واقرأها وقت الاستيراد:

      # In tools.py or __init__.py
      from pathlib import Path

      _PLUGIN_DIR = Path(__file__).parent
      _DATA_FILE = _PLUGIN_DIR / "data" / "languages.yaml"

      with open(_DATA_FILE) as f:
          _DATA = yaml.safe_load(f)

      هذا للملفات التي تشحنها. الحالة التي تكتبها مختلفة — انظر القسم التالي.

      تخزين الحالة الدائمة​

      لا تكتب أبدًا حالة وقت التشغيل داخل دليل الإضافة: فهذا هو شجرة التثبيت، وhermes plugins update / remove يسحبان التحديثات عبر git أو يحذفانها — فتموت بيانات مستخدميك معها. المكان المعتمد هو جذر البيانات الخاص بكل إضافة، والذي يبقى بعد كليهما ويتبع الـ profile النشط:

      from plugins.plugin_storage import plugin_data_dir, plugin_db

      # <hermes home>/plugin-data/<name>/ — created on first use
      state_file = plugin_data_dir("my-plugin") / "state.json"

      # Or a SQLite database at <data dir>/data.db (WAL mode, thread-friendly)
      conn = plugin_db("my-plugin")
      conn.execute("CREATE TABLE IF NOT EXISTS runs (id TEXT PRIMARY KEY)")

      وجود دليل واحد لكل إضافة يعني أن بيانات كل إضافة قابلة للفحص في مكان واحد يمكن التنبؤ به. الأسرار لا مكان لها هنا — فقراءة بيانات الاعتماد تمر عبر مسار .env / secret-scope المعتاد كما في كل مكان آخر.

      تضمين المهارات (Skills)​

      يمكن للإضافات شحن ملفات مهارات يحمّلها الوكيل عبر skill_view("plugin:skill"). سجّلها في __init__.py الخاص بك:

      ~/.hermes/plugins/my-plugin/
      ├── __init__.py
      ├── plugin.yaml
      └── skills/
          ├── my-workflow/
          │   └── SKILL.md
          └── my-checklist/
              └── SKILL.md
      from pathlib import Path

      def register(ctx):
          skills_dir = Path(__file__).parent / "skills"
          for child in sorted(skills_dir.iterdir()):
              skill_md = child / "SKILL.md"
              if child.is_dir() and skill_md.exists():
                  ctx.register_skill(child.name, skill_md)

      يمكن للوكيل الآن تحميل مهاراتك باستخدام اسمها المُميّز بالنطاق (namespaced):

      skill_view("my-plugin:my-workflow")   # → plugin's version
      skill_view("my-workflow")              # → built-in version (unchanged)

      الخصائص الأساسية:

      • مهارات الإضافة للقراءة فقط — فهي لا تدخل ~/.hermes/skills/ ولا يمكن تعديلها عبر skill_manage.
      • مهارات الإضافة غير مُدرجة في فهرس <available_skills> الخاص بـ system prompt — فهي تحميلات صريحة تتطلب الاختيار (opt-in).
      • أسماء المهارات المجردة تبقى دون تأثير — إذ يمنع النطاق (namespace) أي تصادم مع المهارات المدمجة.
      • عندما يحمّل الوكيل مهارة إضافة، تُضاف في المقدمة لافتة سياق تجميعة (bundle context banner) تسرد المهارات الشقيقة من نفس الإضافة.
      نمط قديم

      النمط القديم shutil.copy2 (نسخ مهارة إلى ~/.hermes/skills/) لا يزال يعمل لكنه يخلق خطر تصادم أسماء مع المهارات المدمجة. يُفضَّل استخدام ctx.register_skill() للإضافات الجديدة.

      التقييد بمتغيرات البيئة (Environment Variables)​

      إذا كانت إضافتك بحاجة إلى مفتاح API:

      # plugin.yaml — simple format (backwards-compatible)
      requires_env:
        - WEATHER_API_KEY

      إذا لم يكن WEATHER_API_KEY مضبوطًا، تُعطَّل الإضافة برسالة واضحة. لا انهيار، ولا خطأ في الوكيل — فقط "Plugin weather disabled (missing: WEATHER_API_KEY)".

      عندما يُشغّل المستخدمون hermes plugins install، تتم مطالبتهم تفاعليًا بأي متغيرات requires_env مفقودة. تُحفظ القيم في .env تلقائيًا.

      لتجربة تثبيت أفضل، استخدم الصيغة الغنية مع الأوصاف وروابط التسجيل:

      # plugin.yaml — rich format
      requires_env:
        - name: WEATHER_API_KEY
          description: "API key for OpenWeather"
          url: "https://openweathermap.org/api"
          secret: true
      الحقلمطلوبالوصف
      nameنعماسم متغير البيئة
      descriptionلايُعرض على المستخدم أثناء مطالبة التثبيت
      urlلامكان الحصول على بيانات الاعتماد
      secretلاإذا كانت true، يُخفى الإدخال (كحقل كلمة مرور)

      يمكن مزج الصيغتين في القائمة نفسها. المتغيرات المضبوطة مسبقًا تُتجاوَز بصمت.

      التثبيت الكسول (Lazy) للاعتماديات الاختيارية في Python​

      إذا كانت إضافتك تغلّف SDK لن يمتلكه كل مستخدم مثبَّتًا (SDK تابع لمزوّد، أو مكتبة ML ثقيلة، أو حزمة خاصة بمنصة معينة)، فلا تستورده (import) في أعلى الوحدة (module). استخدم المساعد tools.lazy_deps.ensure(...) داخل معالج الأداة — سيُثبّت Hermes الحزمة عند أول استخدام، مقيّدًا بإعداد security.allow_lazy_installs الخاص بالمستخدم.

      # tools.py
      from tools.lazy_deps import ensure, FeatureUnavailable

      def my_tool_handler(args, **kwargs):
          try:
              ensure("my-plugin.my-backend")   # key must be in LAZY_DEPS
          except FeatureUnavailable as exc:
              return {"error": str(exc)}

          import my_backend_sdk   # safe now
          ...

      القاعدةالسبب
      يجب أن يظهر مفتاح ميزتك في قائمة السماح LAZY_DEPS الموجودة داخل الشجرةيمنع أي إعدادات ضارة من دفع Hermes لتثبيت حزم عشوائية — فقط المواصفات التي يشحنها Hermes نفسه مؤهلة
      المواصفات تكون بالاسم من PyPI فقطلا --index-url، ولا git+https://، ولا مسارات file:. ثبّت الإصدارات بصيغة PEP 440 ("my-sdk>=1.2,<2") داخل مدخل قائمة السماح

      بالنسبة للإضافات من طرف ثالث الموزَّعة عبر pip، أعلن الاعتماديات الاختيارية كإضافات (extras) في [project.optional-dependencies] ضمن pyproject.toml الخاص بك، وأخبر المستخدمين بتنفيذ pip install your-plugin[backend] — فهذا المسار لا يمر عبر lazy_deps. أسلوب التثبيت الكسول مفيد أكثر ما يكون للإضافات المضمّنة (bundled) حيث يؤدي شحن اعتمادية إلزامية مع كل تثبيت إلى تضخيم البصمة الأساسية لـ Hermes.

      عندما يُضبط security.allow_lazy_installs: false عالميًا، تُطلق ensure() استثناء FeatureUnavailable فورًا مع تلميح للمعالجة — يجب أن تلتقطه إضافتك وتتدهور بأمان (إعادة نتيجة خطأ، لا انهيار في حلقة الأداة).

      Singletons كسولة وآمنة للـ threads​

      كثيرًا ما تخزّن الإضافات كائنًا مكلفًا — عميل SDK، جلسة HTTP، مجمّع اتصالات — مؤقتًا في متغير على مستوى الوحدة (module) يُبنى عند أول استخدام:

      _client = None

      def get_client():
          global _client
          if _client is not None:
              return _client
          _client = ExpensiveClient(...)   # ← TOCTOU race
          return _client

      هذا فخّ. يشغّل Hermes عدة threads في عملية واحدة (استدعاءات الأدوات المفوَّضة، العمّال في الخلفية، fork التحسين الذاتي)، لذا يمكن لخيطين الوصول إلى get_client() قبل أن يُضبط _client، فيجتاز كلاهما فحص is not None، ويُشغّل كلاهما عملية البناء المكلفة، وتُتلِف الكتابة الثانية الأولى — مما يُسرّب أيًا كان المورد الذي فتحه الخاسر (اتصال، مقبض ملف، thread في الخلفية).

      لا تصنع القفل بنفسك. استخدم المساعدات في plugins/plugin_utils.py:

      from plugins.plugin_utils import lazy_singleton, SingletonSlot

      # Zero-arg accessor → decorate it:
      @lazy_singleton
      def get_client():
          return ExpensiveClient(load_config())   # runs exactly once

      client = get_client()    # safe across threads
      get_client.reset()       # drop the instance (tests / teardown)


      # Accessor that takes a build argument → use a slot:
      _slot: SingletonSlot = SingletonSlot()

      def get_client(config=None):
          return _slot.get(lambda: ExpensiveClient(resolve(config)))

      def reset_client():
          _slot.reset()

      كلاهما يسلسل الاستدعاءات الأولى المتزامنة بقفل مزدوج الفحص (double-checked locking) ويشغّل المصنع (factory) مرة واحدة على الأكثر. إذا أطلق المصنع استثناءً، لا يُخزَّن شيء ويُعاد المحاولة في الاستدعاء التالي. إضافة ذاكرة honcho (plugins/memory/honcho/client.py) هي المرجع المستهلك لهذا النمط.

      قاعدة عامة: في أي مرة تكتب فيها global _something متبوعًا بفحص is None ثم بناء، الجأ إلى إحدى هاتين الأداتين بدلًا من ذلك.

      استبدال أداة مدمجة​

      لاستبدال أداة مدمجة بتنفيذك الخاص (مثلًا استبدال أداة المتصفح الافتراضية بـ backend من نوع headed-Chrome CDP، أو استبدال web_search بفهرس داخلي مخصص للشركة)، مرّر override=True:

      def register(ctx):
          ctx.register_tool(
              name="browser_navigate",             # same name as the built-in
              toolset="plugin_my_browser",         # your own toolset namespace
              schema={...},
              handler=my_custom_navigate,
              override=True,                       # explicit opt-in
          )

      بدون override=True، يرفض السجل أي تسجيل قد يحجب أداة موجودة من toolset مختلفة — وهذا يمنع الاستبدالات العرَضية. استبدال أداة مدمجة يتطلب إضافة إلى ذلك موافقة المشغّل صراحة عبر plugins.entries.<plugin_id>.allow_tool_override: true في config.yaml؛ وبدون هذا التصريح، يُطلق register_tool(override=True) PluginToolOverrideError. يُسجَّل الاستبدال بحيث يكون قابلًا للتدقيق في ~/.hermes/logs/agent.log. تُحمَّل الإضافات بعد الأدوات المدمجة، لذا يكون ترتيب التسجيل صحيحًا: يستبدل معالِجك المعالِج المدمج.

      الإضافات غير المضمّنة تحتاج أيضًا إلى منح من المشغّل. بالنسبة لأي إضافة لا تُشحن مع نواة Hermes (مصدرها المستخدم أو المشروع أو pip)، يتطلب override=True ضد أداة مدمجة موجودة إضافةً إلى ذلك اختيارًا صريحًا لكل إضافة في config.yaml:

      plugins:
        entries:
          my-plugin:                    # the plugin's registry key from `hermes plugins list`
            allow_tool_override: true

      بدون هذا المنح، يُطلق ctx.register_tool(..., override=True) PluginToolOverrideError؛ وبما أن استثناءات register() يلتقطها المحمّل، تُعطَّل الإضافة ويستمر Hermes في العمل. يوجد هذا التقييد لأن إضافة مفعّلة تستبدل بصمت أداة مدمجة ذات صلاحيات مثل shell_exec أو write_file يمكن أن تعترض كل ما يوجّهه النموذج عبرها. الإضافات المضمّنة مُستثناة: فالاستبدال هناك قرار للقائمين على الصيانة. إذا تعذّر تحميل الإعدادات، يفشل هذا التقييد بأمان (fail closed).

      لا تحتاج عادةً إلى تعديل هذا المفتاح يدويًا أبدًا. يسأل hermes plugins enable <name> عمّا إذا كان يجب منح الصلاحية عند تفعيل إضافة غير مضمّنة (الافتراضي هو الرفض)، وتتجاوز الخيارات --allow-tool-override / --no-allow-tool-override هذا السؤال في عمليات التثبيت المُبرمَجة. يقيّد هذا المنح نفسه أيضًا deregister(): فبدونه، لا يمكن لإضافة إزالة أداة لا تملكها (وهو ما كان سيمثّل وسيلة للالتفاف على فحص الاستبدال).

      مرجع الـ hooks​

      كل hook موثّق بالكامل في مرجع Event Hooks — توقيعات الاستدعاء (callback signatures)، وجداول المعاملات، وتوقيت إطلاق كل واحد بالضبط، والأمثلة. إليك الملخص:

      Hookيُطلَق عندتوقيع الاستدعاءيُعيد

      post_tool_callبعد إعادة أي أداة نتيجتهاtool_name: str, args: dict, result: str, task_id: str, duration_ms: intيُتجاهَل
      pre_llm_callمرة واحدة لكل دور، قبل حلقة استدعاء الأدواتsession_id: str, user_message: str, conversation_history: list, is_first_turn: bool, model: str, platform: strحقن السياق
      post_llm_callمرة واحدة لكل دور، بعد حلقة استدعاء الأدوات (الأدوار الناجحة فقط)session_id: str, user_message: str, assistant_response: str, conversation_history: list, model: str, platform: strيُتجاهَل
      pre_api_requestقبل كل طلب API خام للمزوّد (عدة طلبات لكل دور عندما يستدعي النموذج أدوات)session_id: str, model: str, provider: str, base_url: str, api_mode: str, api_call_count: int, message_count: int, tool_count: int, approx_input_tokens: int, max_tokens: int, request: dictيُتجاهَل

      api_request_errorعند إطلاق استدعاء API للمزوّد استثناءًحقول الربط بالإضافة إلى status_code: int | None, retry_count: int | None, max_retries: int | None, retryable: bool | None, reason: str | None, error: dict, request: dictيُتجاهَل

      gateway_platform_eventتطبيع حدث أصلي مُصرَّح به من منصة عند حدود gateway (تفاعلات Telegram حاليًا)platform: str, event_type: str, payload: dictيُتجاهَل
      kanban_task_claimedيُطالَب بمهمة kanban (عملية الموزّع، قبل تشغيل العامل)task_id: str, board: str | None, assignee: str | None, run_id: int | None, profile_name: strيُتجاهَل
      kanban_task_completedاكتمال مهمة kanban (عملية العامل)task_id, board, assignee, run_id, profile_name, summary: str | Noneيُتجاهَل
      kanban_task_blockedحظر مهمة kanban (عملية العامل)task_id, board, assignee, run_id, profile_name, reason: str | Noneيُتجاهَل

      معظم الـ hooks هي مراقبات إطلاق-وتناسَ (fire-and-forget) — تُتجاهَل قيمها المُعادة. الاستثناءان هما pre_llm_call، الذي يمكنه حقن سياق في المحادثة، وpre_tool_call، الذي يمكنه إعادة توجيه حظر/موافقة.

      يجب أن تقبل كل الاستدعاءات (callbacks) **kwargs لضمان التوافق المستقبلي. إذا انهار استدعاء hook، يُسجَّل ويُتجاوز. تستمر بقية الـ hooks والوكيل بشكل طبيعي.

      تُطلَق hooks دورة حياة kanban بعد تثبيت تغيير قاعدة بيانات اللوحة، بحيث يرى الاستدعاء دائمًا حالة دائمة ولا يمكنه أبدًا الاحتفاظ بقفل الكتابة الخاص بـ SQLite. ولأن عمّال kanban يعملون كعمليات فرعية منفصلة من نوع hermes -p <profile> chat -q، يُطلَق kanban_task_claimed في عملية الموزّع (dispatcher) بينما تُطلَق kanban_task_completed / kanban_task_blocked في عملية العامل (worker) — استخدم الـ hook في الموزّع لمراقبة كل انتقال مركزيًا، أو في العامل للسياق داخل الجلسة لكل مهمة.

      hooks طلب API هي مراقبات للطلب الخام للمزوّد، بمستوى أدنى من زوج pre_llm_call / post_llm_call لكل دور: دور واحد يستدعي أدوات يُصدر عدة طلبات API، وتُطلَق هذه الـ hooks حول كل واحد منها. توجد لأجل إضافات المراقبة (تتبّع، محاسبة التكلفة، لوحات زمن الاستجابة). وسيطا request وresponse عبارة عن عروض JSON مُنقّاة ومحدودة الحجم لحمولة المزوّد (المفاتيح الحساسة مُخفاة، والسلاسل الطويلة مقصوصة، وكائنات SDK مُطبَّعة)، وusage هو قاموس ملخّص توكن بسيط. تحمل كل حمولة حقول الربط turn_id، وapi_request_id، وtask_id، وsession_id، وapi_call_count، بحيث يمكن للإضافة ربط الطلبات واستدعاءات الأدوات والأدوار معًا. تُطلَق api_request_error عندما يُطلق استدعاء المزوّد استثناءً وتضيف status_code، وretry_count / max_retries، وretryable، وreason، وقاموس error يحتوي على type وmessage.

      حقن السياق في pre_llm_call​

      هذا هو الـ hook الوحيد الذي تُهم قيمته المُعادة. عندما يُعيد استدعاء pre_llm_call قاموسًا يحوي مفتاح "context" (أو سلسلة نصية عادية)، يحقن Hermes ذلك النص في رسالة المستخدم للدور الحالي. هذه هي الآلية المستخدمة في إضافات الذاكرة، وتكاملات RAG، والحواجز الوقائية (guardrails)، وأي إضافة تحتاج إلى تزويد النموذج بسياق إضافي.

      صيغة القيمة المُعادة​

      # Dict with context key
      return {"context": "Recalled memories:\n- User prefers dark mode\n- Last project: hermes-agent"}

      # Plain string (equivalent to the dict form above)
      return "Recalled memories:\n- User prefers dark mode"

      # Return None or don't return → no injection (observer-only)
      return None

      أي قيمة مُعادة غير فارغة وغير None تحمل مفتاح "context" (أو سلسلة نصية غير فارغة) تُجمَع وتُلحَق برسالة المستخدم للدور الحالي.

      فيضان السياق الزائد الحجم​

      يُحدَّد سياق كل hook افتراضيًا بسقف 10,000 حرف. أي شيء يتجاوز هذا السقف يُكتب إلى $HERMES_HOME/hook_outputs/<session_id>/<uuid>.txt ويُستبدَل بمعاينة رأس/ذيل مع المسار المحفوظ. يمكن للنموذج قراءة المحتوى الكامل عبر read_file أو terminal إن احتاج إليه فعليًا. هذا يمنع أي إضافة منفلتة من تضخيم prompt كل دور لاحق وتفجير بادئة ذاكرة التخزين المؤقت الخاصة بالـ prompt. اضبط ذلك في config.yaml:

      hooks:
        output_spill:
          enabled: true          # default: true
          max_chars: 10000       # default; set higher to opt out of spilling
          preview_head: 500      # chars shown at the top of the preview
          preview_tail: 500      # chars shown at the bottom of the preview
          # directory: null      # default: $HERMES_HOME/hook_outputs

      كيف يعمل الحقن​

      يُلحَق السياق المحقون بـرسالة المستخدم، لا بـ system prompt. هذا خيار تصميمي متعمَّد:

      • الحفاظ على prompt cache — يبقى الـ system prompt مطابقًا عبر الأدوار. تُخزّن Anthropic وOpenRouter بادئة الـ system prompt مؤقتًا، لذا فإن إبقاءها ثابتة يوفّر أكثر من %75 على توكنات الإدخال في المحادثات متعددة الأدوار. لو عدّلت الإضافات الـ system prompt، لأصبح كل دور فرصة إخفاق للتخزين المؤقت (cache miss).
      • عابر (Ephemeral) — يحدث الحقن فقط وقت استدعاء API. رسالة المستخدم الأصلية في سجل المحادثة لا تُعدَّل أبدًا، ولا يُحفَظ شيء في قاعدة بيانات الجلسة.
      • الـ system prompt هو نطاق Hermes الخاص — فهو يحتوي على إرشادات خاصة بالنموذج، وقواعد فرض الأدوات، وتعليمات الشخصية، ومحتوى المهارات المخزَّن مؤقتًا. تسهم الإضافات بسياق إلى جانب مدخلات المستخدم، لا بتعديل تعليمات الوكيل الأساسية.

      مثال: إضافة استرجاع الذاكرة​

      """Memory plugin — recalls relevant context from a vector store."""

      import httpx

      MEMORY_API = "https://your-memory-api.example.com"

      def recall_context(session_id, user_message, is_first_turn, **kwargs):
          """Called before each LLM turn. Returns recalled memories."""
          try:
              resp = httpx.post(f"{MEMORY_API}/recall", json={
                  "session_id": session_id,
                  "query": user_message,
              }, timeout=3)
              memories = resp.json().get("results", [])
              if not memories:
                  return None  # nothing to inject

              text = "Recalled context from previous sessions:\n"
              text += "\n".join(f"- {m['text']}" for m in memories)
              return {"context": text}
          except Exception:
              return None  # fail silently, don't break the agent

      def register(ctx):
          ctx.register_hook("pre_llm_call", recall_context)

      عدة إضافات تُعيد سياقًا​

      عندما تُعيد عدة إضافات سياقًا من pre_llm_call، تُدمَج مخرجاتها بفواصل سطرين مزدوجة وتُلحَق برسالة المستخدم معًا. يتبع الترتيب ترتيب اكتشاف الإضافات (أبجديًا حسب اسم دليل الإضافة).

      Middleware: تغيير ما يحدث​

      تراقب الـ hooks حلقة الوكيل (مع أشكال التوجيه الموثّقة القليلة أعلاه). أما الـ middleware فيغيّر ما يحدث: تعيد middleware الطلب كتابة الحمولة الفعلية قبل أن يراها أي شيء لاحق، وتغلّف middleware التنفيذ الاستدعاء الفعلي نفسه. سجّلها من نقطة الدخول نفسها register(ctx):

      def cap_find_output(tool_name, args, **kwargs):
          """Rewrite terminal find commands to cap their output."""
          command = args.get("command", "")
          if tool_name == "terminal" and command.startswith("find "):
              return {
                  "args": {**args, "command": command + " | head -100"},
                  "source": "my-plugin",
                  "reason": "cap find output",
              }
          return None  # leave the call unchanged

      def register(ctx):
          ctx.register_middleware("tool_request", cap_find_output)

      القائمة المرجعية للأنواع هي VALID_MIDDLEWARE في hermes_cli/middleware.py:

      النوعيستقبلعقد القيمة المُعادة
      tool_requesttool_name، args، original_args، وسائط السياقأعِد {"args": {...}} لاستبدال وسائط الأداة الفعلية قبل أن تراها الـ hooks والحواجز الوقائية والموافقات والتنفيذ. أعِد None لترك الاستدعاء دون تغيير.
      llm_requestrequest، original_request، وسائط السياقأعِد {"request": {...}} لاستبدال وسائط المزوّد الفعلية قبل أن يرسلها Hermes.
      tool_executionالحمولة بالإضافة إلى next_callيغلّف تنفيذ الأداة. استدعِ next_call(payload) مرة واحدة بالضبط لتشغيل السلسلة اللاحقة (أو تجاوزها للاختصار) وأعِد النتيجة.
      llm_executionالحمولة بالإضافة إلى next_callالشكل نفسه، لكن يغلّف استدعاء المزوّد.

      قواعد ذات أثر عملي:

      • سلاسل middleware الطلب: يرى كل استدعاء الحمولة كما أعادت كتابتها الاستدعاءات السابقة، بينما تحمل original_args / original_request دائمًا النسخة قبل middleware. تُنسخ الحمولات بين الاستدعاءات، لذا يمكنك التعديل بحرية.
      • يمكنك تضمين سلاسل source وreason وname في القاموس المُعاد. تنتهي في أثر middleware، الذي تستقبله hooks المراقبة اللاحقة كوسيط middleware_trace.
      • next_call في middleware التنفيذ أحادي الاستخدام. استدعاؤه مرتين يُطلق استثناءً، لأن ذلك سيُعيد تشغيل المزوّد أو الأداة.
      • استدعاء middleware يُطلق استثناءً يُسجَّل ويُتجاوز؛ وتستمر السلسلة. أي إخفاق لاحق يُطلَق بعد next_call الخاص بك ينتشر كما هو. لا يمكن أبدًا لـ middleware كسر مسار وقت التشغيل الأساسي.
      • تحمل حمولات middleware middleware_schema_version (hermes.middleware.v1) إلى جانب حقول قياس المراقبة (observer telemetry).
      • تُسجَّل الأنواع غير المعروفة مع تحذير بدلًا من الفشل، بحيث تظل إضافة مكتوبة لإصدار أحدث من Hermes قابلة للتحميل على إصدار أقدم.

      تسجيل أوامر CLI​

      يمكن للإضافات إضافة شجرة أوامر فرعية hermes <plugin> خاصة بها:

      def _my_command(args):
          """Handler for hermes my-plugin <subcommand>."""
          sub = getattr(args, "my_command", None)
          if sub == "status":
              print("All good!")
          elif sub == "config":
              print("Current config: ...")
          else:
              print("Usage: hermes my-plugin <status|config>")

      def _setup_argparse(subparser):
          """Build the argparse tree for hermes my-plugin."""
          subs = subparser.add_subparsers(dest="my_command")
          subs.add_parser("status", help="Show plugin status")
          subs.add_parser("config", help="Show plugin config")
          subparser.set_defaults(func=_my_command)

      def register(ctx):
          ctx.register_tool(...)
          ctx.register_cli_command(
              name="my-plugin",
              help="Manage my plugin",
              setup_fn=_setup_argparse,
              handler_fn=_my_command,
          )

      بعد التسجيل، يمكن للمستخدمين تنفيذ hermes my-plugin status، وhermes my-plugin config، وما إلى ذلك.

      إضافات مزوّدي الذاكرة تستخدم نهجًا قائمًا على الاصطلاح (convention-based) بدلًا من ذلك: أضف دالة register_cli(subparser) إلى ملف cli.py الخاص بإضافتك. يجد نظام اكتشاف إضافات الذاكرة هذا تلقائيًا — لا حاجة لاستدعاء ctx.register_cli_command(). راجع دليل إضافة مزوّد الذاكرة للتفاصيل.

      التقييد حسب المزوّد النشط: تظهر أوامر CLI الخاصة بإضافة الذاكرة فقط عندما يكون مزوّدها هو memory.provider النشط في الإعدادات. إذا لم يُعِد المستخدم إعداد مزوّدك، فلن تُزاحم أوامر CLI الخاصة بك مخرجات المساعدة.

      تسجيل slash commands​

      يمكن للإضافات تسجيل slash commands داخل الجلسة — وهي أوامر يكتبها المستخدمون أثناء المحادثة (مثل /lcm status أو /ping). تعمل هذه الأوامر في كلٍّ من CLI و gateway (Telegram و Discord وغيرهما).

      def _handle_status(raw_args: str) -> str:
          """Handler for /mystatus — called with everything after the command name."""
          if raw_args.strip() == "help":
              return "Usage: /mystatus [help|check]"
          return "Plugin status: all systems nominal"

      def register(ctx):
          ctx.register_command(
              "mystatus",
              handler=_handle_status,

      استدعاء الأدوات من slash commands​

      ينبغي لمعالجات slash commands التي تحتاج إلى تنسيق الأدوات (إطلاق subagent عبر delegate_task، أو استدعاء file_edit، وغير ذلك) أن تستخدم ctx.dispatch_tool() بدلًا من الوصول إلى البنية الداخلية لإطار العمل. يُربط سياق الوكيل الأب (تلميحات مساحة العمل، ومؤشر الانتظار spinner، ووراثة النموذج) تلقائيًا.

      def register(ctx):
          def _handle_deliver(raw_args: str):
              result = ctx.dispatch_tool(
                  "delegate_task",
                  {
                      "goal": raw_args,
                      "toolsets": ["terminal", "file", "web"],
                  },
              )
              return result

          ctx.register_command(
              "deliver",
              handler=_handle_deliver,
              description="Delegate a goal to a subagent",
          )

      التوقيع (Signature): ctx.dispatch_tool(name: str, args: dict, *, parent_agent=None) -> str

      المعاملالنوعالوصف
      namestrاسم الأداة كما هو مسجّل في سجل الأدوات (مثل "delegate_task" و "file_edit")
      argsdictوسائط الأداة، بالبنية نفسها التي يرسلها النموذج
      parent_agentAgent | Noneتجاوز اختياري. عند إغفاله، يُحدَّد من وكيل CLI الحالي (أو يتراجع بسلاسة في وضع gateway)

      السلوك وقت التشغيل:

      • وضع CLI: يُحدَّد parent_agent من وكيل CLI النشط، فتُورَث تلميحات مساحة العمل ومؤشر الانتظار واختيار النموذج كما هو متوقع.
      • وضع Gateway: لا يوجد وكيل CLI، لذا تتراجع الأدوات بسلاسة — تُقرأ مساحة العمل من مجلد العمل المُعدّ للطرفية ولا يظهر مؤشر انتظار.
      • التجاوز الصريح: إذا مرّر المستدعي parent_agent= صراحةً، فإنه يُحترم ولا يُستبدل.

      هذه هي الواجهة العامة المستقرة لاستدعاء الأدوات من أوامر الإضافات. لا ينبغي للإضافات الوصول إلى ctx._cli_ref.agent أو أي حالة خاصة مشابهة.

      التصرف من داخل hook (الـ profile + الأدوات)​

      لا تُملأ قيمة ctx._cli_ref إلا في جلسة CLI تفاعلية. وتكون قيمتها None في gateway، وفي عمليات التشغيل غير التفاعلية عبر hermes chat -q، وفي جلسات العمّال (worker sessions) التي يُطلقها kanban — لذا فإن أي منطق في الإضافة يمر عبر _cli_ref لا يفعل شيئًا بصمت في هذه السياقات تحديدًا. تغطي واجهتا API مستقرتان ومستقلتان عن نوع الجلسة ما تحتاجه hooks فعلًا:

      • ctx.profile_name — اسم الـ profile النشط (مثل "default"، أو profile المُسنَد إليه المهمة في عامل kanban). يُشتق من HERMES_HOME، لذا يعمل في كل مكان دون أي اعتماد على _cli_ref.
      • ctx.dispatch_tool(name, args) — يستدعي أي أداة مسجّلة (مدمجة أو من إضافة)، بما في ذلك أدوات kanban_* و delegate_task و terminal و read_file وغيرها. يعمل من دوال رد النداء (callbacks) الخاصة بـ hooks بغض النظر عن العملية التي يُطلَق فيها الـ hook.

      معًا، تتيح هاتان الواجهتان لـ hook دورة حياة kanban أن يرصد انتقالًا ويتصرف على اللوحة دون المساس بالبنية الداخلية لإطار العمل:

      def register(ctx):
          def on_blocked(*, task_id, reason=None, **kw):
              # Runs in the worker process; ctx._cli_ref is None here.
              ctx.dispatch_tool("kanban_comment", {
                  "task_id": task_id,
                  "comment": f"[{ctx.profile_name}] auto-noted block: {reason}",
              })
          ctx.register_hook("kanban_task_blocked", on_blocked)

      لتشغيل أمر hermes <subcommand> كامل (مثل hermes kanban show)، نفّذه عبر الـ shell باستخدام أداة terminal من خلال ctx.dispatch_tool("terminal", {"command": "hermes kanban show ..."}) — إذ لا يوجد جسر داخل العملية لـ slash commands في جلسات العمّال التي تعمل دون واجهة (headless)، والأدوات هي الطريقة المدعومة لتشغيل Hermes من داخل hook.

      يمكن للإضافات التي تنشر رسائل Block Kit تحتوي على عناصر تفاعلية (أزرار، وقوائم overflow، ومنتقيات التاريخ، وغيرها) تسجيل معالجات النقر مباشرةً لدى Slack adapter — دون الحاجة إلى تعديل slack_bolt.AsyncApp وقت التشغيل (monkey-patching).

      تسجيل معالجات المنصة الأصلية (أي منصة)​

      يمكن للإضافات التي تحتاج إلى استقبال أحداث منصة لا يوجّهها الـ adapter الأساسي — أنواع تحديثات إضافية، ودوال رد نداء الأزرار الأصلية، وأحداث التفاعلات/الأعضاء، ومسارات webhook — أن تسجّل مصنع معالجات (handler factory) يستدعيه adapter المنصة وقت الاتصال. يعمل ذلك على كل منصات gateway.

      def register(ctx):
          def _wire(native, adapter):
              # native: the platform's client/app object (see table below)
              # adapter: the platform adapter instance (treat as read-only)
              # Import platform SDKs HERE so register() works without them.
              ...

          ctx.register_platform_handler("discord", _wire)

      • توضع المصانع في قائمة الانتظار وقت تحميل الإضافة وتُستدعى عند اتصال المنصة — وفي المنصات التي يهمّ فيها ترتيب التوزيع (Telegram و Slack و Teams وموجّهات aiohttp) تعمل قبل تسجيل المعالجات الأساسية، فتحظى معالجات الإضافة المقيّدة بالأولوية بينما يمرّ كل ما عداها إلى المعالجات التالية.
      • قيّد دائمًا نطاق المعالجات التي تضيفها إلى جداول التوزيع القائمة على أول تطابق. في Telegram، استخدم CallbackQueryHandler(..., pattern=r"^myplugin:") — فالمعالج غير المقيّد سيبتلع تدفقات الأزرار الأساسية (موافقات التنفيذ، ومنتقي النموذج، وطلبات التوضيح).
      • كل مصنع معزول: إذا أطلق استثناءً، يُسجَّل الخطأ وتواصل المنصة الاتصال بشكل طبيعي.
      • استورد SDK المنصة داخل جسم المصنع، لا على مستوى الوحدة (module) — إذ يجب أن تعمل register() حتى عندما لا تكون SDK مثبّتة.
      • يمكن لإضافة واحدة تسجيل مصانع لعدة منصات؛ ويُطلَق كل منها فقط عند اتصال منصته.

      الاسم البديل لـ Telegram: ctx.register_telegram_handler(factory) هو اسم بديل للتوافق مع الإصدارات السابقة لـ ctx.register_platform_handler("telegram", factory).

      مثال — Telegram، أزرار مضمّنة (inline) مقيّدة بنمط:

                  query = update.callback_query
                  await query.answer()
                  # ...handle "myplugin:*" callbacks

              application.add_handler(
                  CallbackQueryHandler(_on_button, pattern=r"^myplugin:")
              )

          ctx.register_platform_handler("telegram", _wire)

                  ...  # e.g. reaction-based voting / moderation

      Shell hooks — تشغيل أمر shell عند استدعاء الأدوات​

      إذا كنت تريد فقط تشغيل سكربت عند إطلاق أداة (الإشعارات، وسجلات التدقيق، وتنبيهات سطح المكتب، وأدوات التنسيق التلقائي)، فاستخدم shell hooks في config.yaml — دون الحاجة إلى Python:

      hooks:

      التوزيع لـ NixOS​

      لم يعد Nix مدعومًا صراحةً

      لم يعد Nix/NixOS مسار تثبيت مدعومًا صراحةً (الدعم بأفضل جهد فقط) — راجع إعداد Nix. أُبقي هذا القسم للمستخدمين الذين ينشرون بالفعل على NixOS.

      يستطيع مستخدمو NixOS تثبيت إضافتك بشكل تصريحي إذا وفّرت ملف pyproject.toml يتضمن نقاط دخول:

      الإضافات القائمة على نقاط الدخول (موصى بها للتوزيع):

      # User's configuration.nix
      services.hermes-agent.extraPythonPackages = [
        (pkgs.python312Packages.buildPythonPackage {
          pname = "my-plugin";
          version = "1.0.0";
          src = pkgs.fetchFromGitHub {
            owner = "you";
            repo = "hermes-my-plugin";
            rev = "v1.0.0";
            hash = "sha256-...";  # nix-prefetch-url --unpack
          };
          format = "pyproject";
          build-system = [ pkgs.python312Packages.setuptools ];
        })
      ];

      الإضافات القائمة على المجلدات (لا حاجة إلى pyproject.toml):

      services.hermes-agent.extraPlugins = [
        (pkgs.fetchFromGitHub {
          owner = "you";
          repo = "hermes-my-plugin";
          rev = "v1.0.0";
          hash = "sha256-...";
        })
      ];

      راجع دليل إعداد Nix للاطلاع على التوثيق الكامل، بما في ذلك استخدام overlay والتحقق من التعارضات.

      أخطاء شائعة​

      المعالج لا يُرجع سلسلة JSON:

      # Wrong — returns a dict
      def handler(args, **kwargs):
          return {"result": 42}

      # Right — returns a JSON string
      def handler(args, **kwargs):
          return json.dumps({"result": 42})

      غياب **kwargs من توقيع المعالج:

      # Wrong — will break if Hermes passes extra context
      def handler(args):
          ...

      # Right
      def handler(args, **kwargs):
          ...

      المعالج يُطلق استثناءات:

      # Wrong — exception propagates, tool call fails
      def handler(args, **kwargs):
          result = 1 / int(args["value"])  # ZeroDivisionError!
          return json.dumps({"result": result})

      # Right — catch and return error JSON
      def handler(args, **kwargs):
          try:
              result = 1 / int(args.get("value", 0))
              return json.dumps({"result": result})
          except Exception as e:
              return json.dumps({"error": str(e)})

      وصف المخطط (schema) مبهم أكثر من اللازم:

      # Bad — model doesn't know when to use it
      "description": "Does stuff"

      # Good — model knows exactly when and how
      "description": "Evaluate a mathematical expression. Use for arithmetic, trig, logarithms. Supports: +, -, *, /, **, sqrt, sin, cos, log, pi, e."

      تخزين الجلسات

      يستخدم Hermes Agent قاعدة بيانات SQLite (~/.hermes/state.db) لحفظ بيانات الجلسات الوصفية، وسجل الرسائل الكامل، وإعدادات النموذج عبر جلسات CLI وgateway. هذا يحلّ محلّ أسلوب ملفات JSONL السابق لكل جلسة على حدة.

      ملفات المصدر: hermes_state.py (الواجهة الأمامية) بالإضافة إلى ملفات hermes_state_*.py المرافقة (schema، fts، search، compression، portability، gateway، ...)

      عزل profile في Desktop وأجيال الضغط (compaction)​

      يخزّن كل profile مُسمّى نصّه الكامل (transcript) في $HERMES_HOME/state.db الخاص به، حتى عندما تخدم عملية hermes serve واحدة عدة profiles. يجب أن تحتفظ عمليات إعادة بناء الوكيل أثناء الجلسة (تحديث قدرات Bot Chat و tools.configure) بمقبض قاعدة بيانات تلك الجلسة، وأن تربط الصفحة الرئيسية (home) الخاصة بـ profile أثناء الإنشاء. يجب ألا يُغلق تحرير الوكيل الخارج المقبضَ الذي يرثه بديله. يحلّ tools.configure الإعدادات من profile_home الخاص بالجلسة الحيّة، حتى عندما يزوّد العميل session_id فقط. تُعِدّ عمليات إعادة البناء إعدادات النموذج قبل تخصيص بديل، ثم تُثبّت الوكيل وتنقل الملكية معًا؛ فشل التحضير يترك الوكيل الحالي مسؤولًا عن التفكيك. تفشل الـ profiles الصريحة التي يتعذّر حلّها أو التي اختفى مجلدها قبل الوصول إلى إعدادات الإطلاق أو السجل. وبالمثل، يُعيد معرّف جلسة tools.configure القديم (stale) رسالة session not found دون تغيير الإعدادات؛ وحذف معرّف الجلسة لا يزال يدعم عملية الإعدادات العامة.

      يؤرشف الضغط في المكان (in-place compaction) الصفوف القديمة بوضع active=0 ويُدرج السياق المُحتفَظ به كصفوف active=1. لذا يمكن لرسالة محمية أن تظهر بشكل مشروع في كلا الجيلين بنفس المحتوى والطابع الزمني. لا تحذف صفوف الأرشيف هذه باعتبارها تكرارًا. شخِّص التكرار في الكتابات الحيّة باستخدام active=1، وتحقّق من profile قاعدة البيانات كذلك إلى جانب معرّف الجلسة عند التحقيق في سجل يبدو وكأنه تراجع.

      ملكية الإدخال في Codex app-server​

      يحفظ الوكيل إدخال المستخدم المقبول قبل بدء دور Codex الخاص به. ثم يعرض Codex ذلك الإدخال كإشعار userMessage رائد (leading). عند حدّ الدمج (splice) وقت التشغيل، يستبعد Hermes ذلك العنصر الرائد فقط عندما يطابق تمامًا النص المُسلسَل في turn/start، بما في ذلك تحويل الإدخال الغني (rich-input coercion). تبقى أحداث المستخدم اللاحقة أو غير المطابقة سليمة، وكذلك الأدوار المتطابقة المقبولة بشكل منفصل. ينطبق هذا أيضًا على الإدخال الاصطناعي/عديم المفتاح (keyless)؛ ولا يعتمد على معرّف رسالة المنصة. لا تُعاد كتابة التكرارات التاريخية الموجودة. يتخطّى gateway كتابة النص الكامل الخاصة به عندما يُبلغ الوكيل أنه يمتلك عملية الحفظ.

      ملكية الإدخال في مسار استثناء gateway​

      يمكن أن يحدث استثناء gateway قبل إنشاء الوكيل أو بعد وصول إدخاله إلى SQLite. يمنح gateway الإدخال المقبول علامة مالك (owner marker) ضمن ملحق display_metadata الموجود، ويمرّره عبر مسار الحفظ الطبيعي للوكيل. لا تحتوي رسائل المزوّد أبدًا على هذه البيانات الوصفية. تُصنِّف علامات المنصة معرّف الرسالة الواردة حسب المنصة وprofile والنطاق (scope) والمحادثة والخيط (thread)؛ يبقى platform_message_id الأصلي دون تغيير لغرض حلّ الاقتباس/الرد. تحصل الأدوار عديمة المفتاح على علامة جديدة، حتى مع تطابق النص والطابع الزمني.

      يستقصي كاتب الاستثناء (exception writer) عن تلك العلامة فقط، متتبّعًا مسار إعادة التوجيه المنشور وخليفة الضغط الحيّ القانوني، ثم أسلاف الضغط. تُحتسب الصفوف النشطة وأرشيفات الضغط؛ أما الصفوف المُتراجَع عنها، والإدخال المُلاحَظ (observed)، والكتّاب غير المرتبطين فلا تُحتسب. لا يمكن لعملية غير مرتبطة تكتب في الجلسة نفسها أن تمنع هذا الدور. لا حاجة إلى خط أساس (baseline) لكامل السجل ولا إلى تخصيص لنص رسالة مؤرشفة. لا تُخوِّل قراءات الملكية الفاشلة إضافة تخمينية؛ تحتفظ حالات فشل قراءة السجل العادية باستجابة عدم توفّر السجل الحالية.

      الحفظ الطبيعي المملوك من الوكيل يبقى دون تغيير. هذا تحكيم بين كتّاب الفشل (failure-writer arbitration)، وليس تسليمًا شاملاً لمرة واحدة بالضبط (exactly-once)، ولا إزالة تكرار للمحتوى، ولا ترحيل schema. لا تُعاد كتابة الصفوف التاريخية؛ ولا يمكن للإدخالات التاريخية غير المُعلَّمة إثبات الملكية لحدث مُعاد تسليمه.

      نظرة عامة على البنية المعمارية​

      ~/.hermes/state.db (SQLite, WAL mode)
      ├── sessions              — Session metadata, token counts, billing
      ├── messages              — Full message history per session
      ├── session_model_usage   — Per-model/per-task usage attribution rows
      ├── messages_fts          — FTS5 virtual table (content + tool_name + tool_calls)
      ├── messages_fts_trigram  — FTS5 virtual table with trigram tokenizer (CJK / substring search)
      ├── messages_fts_cjk      — FTS5 virtual table with cjk_unicode61 tokenizer
      ├── state_meta            — Key/value metadata table
      ├── gateway_routing       — Gateway routing metadata
      ├── compression_locks     — Cross-process compression locking
      ├── async_delegations     — Async delegation bookkeeping
      ├── delivery_obligations  — Gateway outbox (owed replies); created lazily by gateway/delivery_ledger.py
      └── schema_version        — Single-row table tracking migration state

      ينسخ hermes sessions recover الجداول أعلاه التي تحمل صفوفًا إلى قاعدة البيانات المُستعادة (يُعاد توليد فهارس FTS و schema_version)، بما في ذلك سجلّ (ledger) delivery_obligations المُنشأ بشكل كسول (lazily) عندما يمتلك المصدر واحدًا — يُتحقّق من عدد صفوفه كما هو الحال في sessions/messages.

      قرارات التصميم الرئيسية:

      • وضع WAL للقرّاء المتزامنين + كاتب واحد (gateway متعدد المنصات)
      • جدول FTS5 الافتراضي للبحث النصي السريع عبر جميع رسائل الجلسة
      • نسب الجلسات (session lineage) عبر سلاسل parent_session_id (تقسيمات ناتجة عن الضغط)
      • وسم المصدر (cli، telegram، discord، إلخ) لتصفية المنصات
      • لا يُخزَّن هنا مُشغّل الدُفعات (batch runner) ومسارات RL (trajectories) (أنظمة منفصلة)

      Schema الخاص بـ SQLite​

      جدول الجلسات (Sessions)​

      مُختصر — راجع SCHEMA_SQL في hermes_state_common.py (المُطبَّق بواسطة hermes_state_schema.py) للاطلاع على قائمة الأعمدة الكاملة الحالية (والتي تتضمن أيضًا بيانات توجيه gateway الوصفية مثل session_key و chat_id و chat_type و thread_id و display_name و origin_json و expiry_finalized، وحقول بيئة العمل cwd / git_branch / git_repo_root، وحقول التسليم (handoff) وفشل الضغط، و profile_name و rewind_count و archived و pinned):

      CREATE TABLE IF NOT EXISTS sessions (
          id TEXT PRIMARY KEY,
          source TEXT NOT NULL,
          user_id TEXT,
          model TEXT,
          model_config TEXT,
          system_prompt TEXT,
          parent_session_id TEXT,
          started_at REAL NOT NULL,
          ended_at REAL,
          end_reason TEXT,
          message_count INTEGER DEFAULT 0,
          tool_call_count INTEGER DEFAULT 0,
          input_tokens INTEGER DEFAULT 0,
          output_tokens INTEGER DEFAULT 0,
          cache_read_tokens INTEGER DEFAULT 0,
          cache_write_tokens INTEGER DEFAULT 0,
          reasoning_tokens INTEGER DEFAULT 0,
          billing_provider TEXT,
          billing_base_url TEXT,
          billing_mode TEXT,
          estimated_cost_usd REAL,
          actual_cost_usd REAL,
          cost_status TEXT,
          cost_source TEXT,
          pricing_version TEXT,
          title TEXT,
          api_call_count INTEGER DEFAULT 0,
          -- ... additional gateway/workspace/handoff/compression columns ...
          FOREIGN KEY (parent_session_id) REFERENCES sessions(id)
      );

      CREATE INDEX IF NOT EXISTS idx_sessions_source ON sessions(source);
      CREATE INDEX IF NOT EXISTS idx_sessions_parent ON sessions(parent_session_id);
      CREATE INDEX IF NOT EXISTS idx_sessions_started ON sessions(started_at DESC);
      CREATE UNIQUE INDEX IF NOT EXISTS idx_sessions_title_unique
          ON sessions(title) WHERE title IS NOT NULL;

      جدول الرسائل (Messages)​

      مُختصر — يتضمن schema الكامل أيضًا effect_disposition و platform_message_id و observed و active و compacted و api_content و display_kind و display_metadata:

      CREATE TABLE IF NOT EXISTS messages (
          id INTEGER PRIMARY KEY AUTOINCREMENT,
          session_id TEXT NOT NULL REFERENCES sessions(id),
          role TEXT NOT NULL,
          content TEXT,
          tool_call_id TEXT,
          tool_calls TEXT,
          tool_name TEXT,
          timestamp REAL NOT NULL,
          token_count INTEGER,
          finish_reason TEXT,
          reasoning TEXT,
          reasoning_content TEXT,
          reasoning_details TEXT,
          codex_reasoning_items TEXT,
          codex_message_items TEXT
          -- ... additional display/compaction columns ...
      );

      CREATE INDEX IF NOT EXISTS idx_messages_session ON messages(session_id, timestamp);
      CREATE INDEX IF NOT EXISTS idx_messages_session_id ON messages(session_id, id);

      ملاحظات:

      • tool_calls يُخزَّن كسلسلة JSON (قائمة مُسلسلة من كائنات استدعاء الأدوات)
      • reasoning_details و codex_reasoning_items و codex_message_items تُخزَّن كسلاسل JSON
      • يحتفظ استرجاع سجل Desktop بالملحقات (sidecars) الخاصة بالمساعد في كلٍّ من إسقاطات REST وJSON-RPC (session.resume و session.activate و session.history)، بما في ذلك الصفوف التي تحتوي على استدلال (reasoning) واستدعاءات أدوات. قد تُعيد REST سلسلة JSON الخاصة بـ SQLite بينما تُعيد RPC عناصر مُفكّكة الترميز؛ يقبل Desktop كلا الشكلين. قد يقيم الرد النهائي من Responses في codex_message_items فقط بينما يكون content فارغًا. لا يزال المحتوى القانوني (canonical) له الأولوية، ولا تُرقّى عناصر التحليل والتعليق إلى نص الرد.
      • reasoning يخزّن نص الاستدلال الخام للمزوّدين الذين يعرضونه
      • api_content ملحق بدقّة بايتية (byte-fidelity): سلسلة المحتوى الدقيقة المرسلة إلى الـ API لهذه الرسالة عندما تختلف عن content (حقن الذاكرة المؤقتة/الإضافات، وتجاوزات الحفظ). يحافظ على بايتات النقل (wire bytes) لإعادة التشغيل المستقرة لتخزين الـ prompt المؤقت (cache) — يُخزَّن كما أُرسِل، باستثناء الأزواج البديلة المنفردة (lone surrogates) التي يتعذّر على sqlite3 ربطها والتي تُزيلها حلقة المحادثة من كل حمولة صادرة على أي حال. القيمة NULL تعني أن content أُرسِل حرفيًا.
      • الطوابع الزمنية هي قيم عشرية بتوقيت Unix epoch (time.time())

      البحث النصي الكامل FTS5​

      CREATE VIRTUAL TABLE IF NOT EXISTS messages_fts USING fts5(
          content,
          tool_name,
          tool_calls,
          content='messages',
          content_rowid='id'
      );

      يُبقَى جدول FTS5 متزامنًا عبر ثلاثة مُشغِّلات (triggers) تُفعَّل عند INSERT وUPDATE وDELETE على جدول messages. تُقيَّد المُشغِّلات الحالية بعلامتَي fts_rebuild_high_water / fts_rebuild_progress في state_meta (بحيث يمكن لإعادة بناء FTS في الخلفية المتابعة دون فهرسة مزدوجة) وتغطّي الأعمدة الثلاثة المفهرَسة كلها — راجع SCHEMA_SQL في hermes_state_common.py للاطلاع على SQL الدقيق.

      إصدار Schema والترحيلات (Migrations)​

      إصدار Schema الحالي: 23

      يخزّن جدول schema_version عددًا صحيحًا واحدًا. تُعالَج إضافات الأعمدة البسيطة بشكل تصريحي بواسطة _reconcile_columns() (التي تقارن الأعمدة الحيّة بـ SCHEMA_SQL وتضيف أي عمود مفقود). سلسلة الترحيل المقيَّدة بالإصدار محجوزة لترحيلات البيانات وتغييرات الفهرس/FTS التي يتعذّر التعبير عنها تصريحيًا:

      الإصدارالتغيير
      1Schema الأولي (sessions، messages، FTS5)
      2إضافة عمود finish_reason إلى messages
      3إضافة عمود title إلى sessions
      4إضافة فهرس فريد على title (القيم NULL مسموحة، وغير NULL يجب أن تكون فريدة)
      5إضافة أعمدة الفوترة: cache_read_tokens، cache_write_tokens، reasoning_tokens، billing_provider، billing_base_url، billing_mode، estimated_cost_usd، actual_cost_usd، cost_status، cost_source، pricing_version
      6إضافة أعمدة الاستدلال إلى messages: reasoning، reasoning_details، codex_reasoning_items
      7إضافة عمود reasoning_content إلى messages
      8إضافة عمود api_call_count إلى sessions
      9إضافة عمود codex_message_items إلى messages لإعادة تشغيل معرّف/مرحلة رسائل Codex Responses
      10إضافة جدول messages_fts_trigram الافتراضي (مُرمِّز trigram للبحث بالأحرف الصينية/اليابانية/الكورية وبالسلاسل الجزئية) وتعبئة الصفوف الموجودة بأثر رجعي
      11إعادة فهرسة messages_fts و messages_fts_trigram لتغطية tool_name + tool_calls والتحويل من المحتوى الخارجي إلى الوضع المضمَّن (inline)؛ إسقاط المُشغِّلات القديمة وتعبئة كل صف رسالة بأثر رجعي
      16وسم صفوف subagent المفوَّضة في model_config ($._delegate_from) لإبقاء منتقيات الجلسات نظيفة بعد أن يجعلها حذف الوالد يتيمة
      18توحيد بيانات gateway الوصفية — تعبئة display_name / origin_json / expiry_finalized بأثر رجعي من sessions.json
      20إسناد الاستخدام لكل نموذج — بذر صفوف session_model_usage من إجماليات المجموع التاريخية لكل جلسة
      22إسناد الاستخدام ببُعد المهمة (task) — إعادة بناء session_model_usage بحيث يشارك عمود task في PRIMARY KEY
      23إعادة تصميم تخزين FTS — استبدال جداول FTS ذات المحتوى الخارجي لنسخ الوضع المضمَّن في الإصدار 11 (انتقال اختياري لقواعد البيانات الموجودة)
      29تخرج جلسات cron من فهرس trigram (البحث بالسلاسل الجزئية/CJK)؛ عرض (view) messages_fts_trigram_src ومُشغِّلاته تُصفّي بناءً على sessions.source، وإعادة بناء لمرة واحدة تُطهّر الصفوف التاريخية
      30تخرج جلسات subagent المفوَّضة (delegate-child) أيضًا من فهرس trigram — source='subagent' أو علامة $._delegate_from (FTS_TRIGRAM_SESSION_SQL). تبقى الصفوف في messages وفهرس الكلمات القياسي messages_fts، لذا لا يزال session_search يجدها؛ فقط جداول trigram الظليّة (~2.6× حجمًا) تتقلّص. نفس إعادة البناء لمرة واحدة كما في الإصدار 29

      الإصدارات غير المذكورة أعلاه كانت إضافات أعمدة تصريحية عالجها _reconcile_columns() (زيادة رقم الإصدار فقط، دون ترحيل بيانات).

      تستخدم إضافات الأعمدة التصريحية ALTER TABLE ADD COLUMN مُغلَّفة بـ try/except للتعامل مع حالة وجود العمود مسبقًا (idempotent). يُزاد رقم الإصدار بعد كل كتلة ترحيل ناجحة.

      التعامل مع تنازع الكتابة​

      تشترك عدة عمليات hermes (gateway + جلسات CLI + وكلاء worktree) في state.db واحد. تتعامل فئة SessionDB مع تنازع الكتابة عبر:

      • مهلة SQLite قصيرة (1 ثانية) بدلًا من الافتراضية البالغة 30 ثانية
      • إعادة محاولة على مستوى التطبيق مع تذبذب عشوائي (jitter) (20-150 مللي ثانية، حتى 15 محاولة)
      • معاملات BEGIN IMMEDIATE لإظهار تنازع القفل عند بداية المعاملة
      • نقاط تفتيش WAL دورية كل 50 عملية كتابة ناجحة (وضع PASSIVE)

      هذا يتجنّب "تأثير القافلة" (convoy effect) حيث يتسبب التراجع الداخلي الحتمي لـ SQLite في أن تُعيد جميع الكتّاب المتنافسين المحاولة على نفس الفواصل الزمنية.

      _WRITE_MAX_RETRIES = 15
      _WRITE_RETRY_MIN_S = 0.020   # 20ms
      _WRITE_RETRY_MAX_S = 0.150   # 150ms
      _CHECKPOINT_EVERY_N_WRITES = 50

      العمليات الشائعة​

      التهيئة (Initialize)​

      from hermes_state import SessionDB

      db = SessionDB()                           # Default: ~/.hermes/state.db
      db = SessionDB(db_path=Path("/tmp/test.db"))  # Custom path

      إنشاء الجلسات وإدارتها​

      # Create a new session
      db.create_session(
          session_id="sess_abc123",
          source="cli",
          model="anthropic/claude-sonnet-4.6",
          user_id="user_1",

      نسب الجلسات (Session Lineage)​

      يمكن للجلسات تكوين سلاسل عبر parent_session_id. يحدث هذا عندما يُحفّز ضغط السياق تقسيم جلسة في gateway.

      استعلام: إيجاد نسب الجلسة​

      -- Find all ancestors of a session
      WITH RECURSIVE lineage AS (
          SELECT * FROM sessions WHERE id = ?
          UNION ALL
          SELECT s.* FROM sessions s
          JOIN lineage l ON s.id = l.parent_session_id
      )
      SELECT id, title, started_at, parent_session_id FROM lineage;

      -- Find all descendants of a session
      WITH RECURSIVE descendants AS (
          SELECT * FROM sessions WHERE id = ?
          UNION ALL
          SELECT s.* FROM sessions s
          JOIN descendants d ON s.parent_session_id = d.id
      )
      SELECT id, title, started_at FROM descendants;

      استعلام: الجلسات الأخيرة مع معاينة​

      SELECT s.*,
          COALESCE(
              (SELECT SUBSTR(m.content, 1, 63)
               FROM messages m
               WHERE m.session_id = s.id AND m.role = 'user' AND m.content IS NOT NULL
               ORDER BY m.timestamp, m.id LIMIT 1),
              ''
          ) AS preview,
          COALESCE(
              (SELECT MAX(m2.timestamp) FROM messages m2 WHERE m2.session_id = s.id),
              s.started_at
          ) AS last_active
      FROM sessions s
      ORDER BY s.started_at DESC
      LIMIT 20;

      استعلام: إحصائيات استخدام tokens​

      -- Total tokens by model
      SELECT model,
             COUNT(*) as session_count,
             SUM(input_tokens) as total_input,
             SUM(output_tokens) as total_output,
             SUM(estimated_cost_usd) as total_cost
      FROM sessions
      WHERE model IS NOT NULL
      GROUP BY model
      ORDER BY total_cost DESC;

      -- Sessions with highest token usage
      SELECT id, title, model, input_tokens + output_tokens AS total_tokens,
             estimated_cost_usd
      FROM sessions
      ORDER BY total_tokens DESC
      LIMIT 10;

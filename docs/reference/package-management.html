      إدارة الحزم

      hermes pm يدير ملفات أدوات Hermes التنفيذية وبيئات اعتماديات Python. وليس أداة تحديث التطبيق. استخدم طريقة التحديث الخاصة بالتثبيت لتحديث Hermes نفسه.

      الإصدارات المثبّتة وحالة التثبيت واختيار وقت التشغيل​

      لكل ملف دور مستقل:

      الملفالدور
      pm/lock.jsonإصدارات دقيقة للأدوات المُدارة، وعناوين URL خاصة بالهدف، وبصمات SHA-256.
      pm/pyproject.toml و pm/uv.lockمتطلبات Python المستقلة الخاصة بمدير الاعتماديات، ونتيجة حل الاعتماديات المقفلة.
      pyproject.toml و uv.lockمتطلبات Python والإضافات (extras) ومؤشرات المنصة ونتيجة حل اعتماديات Python المعتمدة في المستودع.
      مخزن الأدوات: facts.jsonعناصر الأدوات المثبّتة وهوياتها ومتغيرات البيئة التي تصدّرها وبصمات الملفات الفعلية.
      لكل تثبيت: facts.jsonبيئة Python المختارة، وبصمة مدخلاتها، والإضافات (extras) المفعّلة.
      الحمولة: manifest.jsonتخطيط الحمولة النسبي، وعقد الإطلاق المكتمل من أداة بناء الحزمة.
      install-stamp.jsonمنشأ البناء، والجهة المعلَنة المالكة للتوزيع/التحديث.

      لا يثبت عنصر في ملف قفل أن حزمةً مثبّتة. ويقارن hermes pm doctor حالة التثبيت بالقفل ويتحقق من البايتات الفعلية. ويستخدم بدء التشغيل تحققًا أقل تكلفةً. ولا يستعلم عن أحدث الإصدارات الأصلية عند كل إطلاق. وفي تثبيتات المصدر المدارة ذاتيًا، يقارن مُشغّل ما قبل الاستيراد بصمة نجاح الاعتماديات المسجَّلة في PM بالمدخلات الحالية. وتؤدي حالة اكتمال مفقودة أو متقادمة إلى مزامنة، ثم يُعاد تشغيل الأمر نفسه على Python المُدار قبل تحميل اعتماديات التطبيق. وتحتفظ المزامنات الفاشلة بالاختيار السابق وتُعاد محاولتها عند الإطلاق التالي؛ ولا يلزم وسم تحديث معلّق. وتحتفظ النسخ المسحوبة للمطوّرين والتثبيتات المحزّمة بجهتها المالكة الحالية.

      قد تواصل أدوات التحديث التاريخية تنفيذ كود Python القديم بعد استبدال شجرة المصدر. وتبدأ نقاط دخول التوافق عملية فرعية جديدة، وتنتظر اكتمالها، وتعيد حالة خروجها. وتطلب تهيئة العملية الفرعية من PM تجهيز الأدوات المطلوبة واختيار جيل Python قبل استيرادات التطبيق. ويعمل الإكمال في ذلك المفسّر مع سياق التحديث وإيصاله. ولا يمسح الأصل sys.modules ، أو يستورد مخطط التطبيق الجديد، أو يستأنف بديلًا احتياطيًا عبر pip.

      تسلّم تحديثات المصدر الحالية النسخة المسحوبة المختارة إلى جهة إكمال مالكة جديدة. وتعطّل Python الخاصة بالتهيئة الأولية تهيئة site-packages قبل طلب مزامنة الإضافات (extras) المسجَّلة والإضافات المفعّلة من PM. ثم تتولى Python المختارة أبنية الواجهة الأمامية وصيانة profiles/الإعدادات وإعادة تشغيل gateways والتحقق من وقت التشغيل. وتستخدم Git وإعادات المحاولة عند حداثة النسخة بالفعل والبديل الاحتياطي ZIP المسار نفسه. ويحتفظ الأمر الأصلي بقفل التحديث أثناء الانتظار؛ ولا يمكن لنتيجة إكمال مفقودة أو فاشلة الإبلاغ عن النجاح. وتبقى أخطاء PM المرتبطة في إيصال التحديث، وتحتفظ إعادات التشغيل المنقطعة بالتزامها تجاه مجموعة النُسخ. ولا تُعاد محاولة أخطاء الاعتماديات أو البناء عبر pip أو إعادة تنزيل المصدر أبدًا. استخدم hermes pm repair لملفات الاعتماديات التالفة. راجع ملاحظة ملكية إكمال تحديث المصدر للمطوّرين.

      تثبيتات المصدر والأبنية المحزّمة​

      تجهّز مُثبّتات المصدر الأدوات المطلوبة مع Python. وتختار إضافة Python all. وتُثبَّت الأدوات الاختيارية المسمّاة عند طلبها.

      للتثبيت المعتمد من المصدر، يتحقق Desktop من مُشغّل التثبيت المنشور وينفّذه. ويتولى PM مفسّره واختيار اعتمادياته. ولا يستبدل Desktop ذلك الأمر بمسار venv تخميني. وتحتفظ تجاوزات المطوّرين بمفسّرها المختار.

      تجهّز حزم Desktop الأصلية مجموعة الأدوات المدعومة وكل إضافات Python المتوافقة مع الهدف قبل التحزيم. ولا يُعدّ --extra all و --all-extras مترادفين. وتظل مؤشرات المنصة تستثني الاعتماديات التي لا تستطيع العمل على الهدف.

      تجمع أداة بناء Desktop الكاملة PM مع مزوّدي تحزيم Node/التحزيم الأصلي. ومن نسخة مسحوبة نظيفة عند release tag، يجهّز python scripts/bundles/desktop.py --tag vX.Y.Z الاعتماديات ويبني المُثبّت. أضف --prepare-only للتوقف بعد التجهيز؛ واستهلك نتيجته المحلية للمهمة باستخدام python scripts/bundles/desktop.py --prepared .build/desktop-job/prepared.json. ويختار --work و --cache جذرين مستقلين يملكهما البناء. وتنشئ مرحلة التجهيز مجلد العمل، لا المستدعي. ويمكن أن يحلّ SHA كامل لـ commit محل tag عبر --commit ؛ ويجب أن تطابقه النسخة المسحوبة.

      يستخدم التجهيز حالة PM معزولة وأدوات مثبّتة الإصدار وبيئات Python جديدة مرتبطة بالمسار واتحاد مساحات عمل JS الكامل و native bindings وأدوات التحزيم. ومخابئ الاعتماديات القابلة لإعادة الاستخدام ليست تثبيتات حية أو بيئات افتراضية قابلة للنقل. وتربط النتيجة المجهَّزة المصدر والهدف والمسارات؛ وتفشل عملية استهلاكها عند فقد المدخلات أو تغييرها بدلًا من إطلاق تنزيل. أعد التجهيز بعد نقل أو تغيير المدخلات. ولا يزال بإمكان التوقيع والتوثيق استخدام الشبكة. راجع دليل بناء Desktop لمتطلبات المُصرّف الأصلي وحدود التحقق من الإصدار.

      الحمولة الأساسية لتطبيق محزّم غير قابلة للتغيير. ويشغّل Hermes backend الخاص به منها، بدلًا من نسخ نسخة مصدر مسحوبة عند أول إطلاق. وتتحقق أداة بناء الحزمة من ملفاتها وتكتب مسارات الإطلاق في بصمة بناء Desktop. ويستخدم Electron تلك المسارات دون فحص الحمولة أو إصلاحها. ويمكن لأدوات إضافية مثبّتة الإصدار استخدام مخزن الأدوات القابل للكتابة. وتستخدم إضافات Python بيئةً كاملة قابلةً للكتابة خارج الحزمة الموقَّعة. ويحتفظ جيلها الأول بالإضافات (extras) المشحونة مع المتطلبات الجديدة. وتستخدم الأجيال اللاحقة اختيار الإضافات المسجَّل أساسًا لها.

      يستخدم Termux بناء bionic مستقلًا وحزمة APT محكمة. ويدمج Docker وقت تشغيله في الصورة ويعطّل تثبيت الاعتماديات عند الطلب. ويوفّر Nix وقت تشغيله عبر derivations. راجع أدلة Termux و Docker و Nix لمعرفة حدودها.

      الحالة القابلة للكتابة​

      جذر البيانات الافتراضي للمنصة هو ~/.hermes على POSIX، و %LOCALAPPDATA%\hermes على Windows. ويمكن لـ HERMES_HOME و profiles تغيير جذر البيانات الذي تستخدمه العملية.

      الحالةالموقع الافتراضي
      عناصر أدوات مشتركة قابلة للكتابةtools/ تحت جذر Hermes الافتراضي المحدَّد.
      تنزيلات قابلة للاستئنافcache/partials/ تحت ذلك الجذر، لا داخل حمولة موقَّعة.
      الاختيار والسجل لكل تثبيتinstalls/INSTALL_KEY/ تحت جذر حالة الاعتماديات.
      أجيال Pythoninstalls/INSTALL_KEY/environments/.
      إيصالات المزامنة والتحديثlogs/update_receipts/ تحت المجلد الرئيسي النشط.

      يُشتق مفتاح التثبيت من المسار المعتمد للمصدر أو مستودع الحمولة. ولذلك تملك النسخ المسحوبة المستقلة اختيارات Python مستقلة. ويمكن لـ profiles التي تشترك في تثبيت إضافة اعتماديات إلى البيئة نفسها. وتظل إعداداتها وبيانات اعتمادها محصورة في نطاق كل profile.

      لا تعدّل معلومات الحالة أو مسارات الأجيال يدويًا. وتحدّد المُشغّلات البيئة المختارة قبل استيرادات الجهات الخارجية. وتحتفظ العمليات باستيراداتها القائمة حتى إعادة تشغيلها. وتحافظ عملية جمع الموارد غير المستخدمة على الأجيال المختارة، والأجيال المدارة بعقود التي لديها قرّاء أحياء.

      تشترك التنزيلات في قفل لكل عنوان URL جزئي. ولا يمكن لنقل فاشل أو معلّق نشر وجهة جزئية، ولا يمكن لجمع الموارد غير المستخدمة حذف ملفات نقل حي. ولا يعيد الاستئناف استخدام النطاقات إلا عندما يظل طولها المسجَّل ومدقّقها وبصمتها الاختيارية مطابقًا. ودون ETag قوي أو بصمة مثبّتة، يبدأ النقل المنقطع من جديد بدلًا من خلط إصدارات مختلفة. وتبقى ملفات .locks/ الصغيرة بعد الاكتمال كي تستخدم العمليات المنتظرة القفل نفسه.

      اعتماديات Python الاختيارية والإضافات​

      تطلب ميزة مدمجة إضافة مشروع عبر pm.ensure_import. وتعلن إضافات المجلدات متطلبات Python في pyproject.toml. ودون ملف مشروع مؤلَّف، يجمع PM قائمتي pip_dependencies و python_dependencies القديمتين من plugin.yaml أو plugin.yml. ولا يتجاوز ملف مشروع قديم مولَّد عبر PM تلك القوائم. وتستخدم فحوص الموافقة وعضوية الاعتماديات وحداثتها قارئ الإعلانات نفسه.

      يجهّز PM متطلبات النواة والإضافات (extras) المفعّلة ومتطلبات الإضافات (plugins) المفعّلة معًا. ويبدأ الحل من ملف القفل (lock) الحالي. قد تتغير الإصدارات المتعدّية المتوافقة، لكن القيود المعلنة والتثبيتات الدقيقة تبقى ملزمة. يحصل كل مرشّح على مساحة عمل جديدة بمدخلات صريحة للمصدر وبذرة ملف القفل والبيئة المجهّزة. وتبقى مساحة العمل المولَّدة وملف القفل الموسّع خارج المصدر المشحون. تُحَلّ مساحة العمل للمنصة والمعمارية الخاصتين بالمفسّر الذي ستُثبَّت فيه فقط، لذا فإن اعتمادية إضافة لا تتوفر لها حزم wheel لمنصة أخرى (مثل onnxruntime أو torch على Android) لا تعطّلها؛ أما ملف القفل المشحون فيحتفظ بتغطيته الكاملة للمنصات. ويَنسخ الإصلاح مساحة العمل وملف القفل المسجَّلين، بما في ذلك مدخلات بناء الإضافات، بدلًا من الحل مقابل manifests حية جرى تعديلها.

      يُرسَل تفعيل الإضافات وتحديثات الكود المجهَّزة كبيانات إلى عامل PM المعزول. وتحت قفل التثبيت، يكتشف اتحاد الاعتماديات المقترح ويتحقق من المرشّح وينشر الإعدادات أو ملفات الإضافة وبياناتها الوصفية مع اختيار البيئة. ويرفض المدخلات التي تغيرت أثناء التجهيز. ويتيح سجل دائم الاستعادة قبل استيرادات التطبيق، بما في ذلك تحديثات الكود وحده التي لا تتطلب بيئة جديدة.

      تستخدم تغييرات اختيار الإضافات، بما فيها تفعيل الحِزم، معاملة القبول نفسها. ويقرأ PM أحدث اختيار تحت قفله المشترك قبل تطبيق كل تغيير. ولا يستبدل المرشّح الفاشل البيئة المختارة أو يعطّل إضافات أخرى بصمت. وإذا نجح التجهيز، فقد تظل عملية Hermes الجارية تحتاج إلى إعادة تشغيل لتفعيل البيئة الجديدة.

      تحافظ تحديثات تطبيق Hermes العادية على مجلدات إضافات المستخدم. ويمكن لتحديثات الإضافات الصريحة تغيير ملفات الإضافة المختارة. ولا ينضم wrapper بلا إعلان لاعتماديات Python إلى البيئة المشتركة. ويظل sidecar الخارجي الخاص به مملوكًا بصورة مستقلة. راجع دليل الإضافات.

      سياسة التثبيت عند الطلب​

      security.allow_lazy_installs يتحكم في التثبيت عند الطلب. وتظل الاعتماديات المثبّتة بالفعل قابلةً للاستخدام عندما يكون هذا الإعداد false.

      hermes config set security.allow_lazy_installs false

      أوامر التثبيت الصريحة تختلف عن التثبيت عند الطلب. لكن قائمة ميزات الحزمة المجمدة تظل تقيّد أسماء إضافات Python المطلوبة عندما يكون التثبيت عند الطلب معطّلًا. وقبول الإضافات الصريح عملية مستقلة، لا طلب ميزة عند الطلب. ولا تعتبر هذا الإعداد sandbox أو منعًا شاملًا للتثبيت اليدوي للحزم. ويضبط Docker أيضًا خيار تعطيل التثبيت عند الطلب الداخلي في الصورة.

      PM مدير اعتماديات، لا sandbox لكود الإضافات. ويتطلب تثبيت إضافة الثقة فيها وفي اعتمادياتها.

      أدوات الأمان الاختيارية​

      يتولى PM حزم bws و iron-proxy مثبّتة الإصدار في pm/security_packages.py. وتأتي إصداراتها وعناوين URL للأصول وبصمات SHA-256 من pm/lock.json. ويستخدم التنزيل والنشر مخزن الأدوات المشترك، لا مُثبّتات خاصة تحت $HERMES_HOME/bin.

      وبالنسبة إلى iron-proxy، يحصل PM أيضًا على ملفات توقيع مثبّتة ويتحقق من أن المجاميع الاختبارية للإصدار تغطي الأرشيف المثبّت. ويستدعي تجهيز الحزمة مدقّق التوقيع الخاص بالتكامل. ويظل فحص GPG مشروطًا بتوفر ملف تنفيذي. ويجب أن تظل ملفات المنشأ المقفلة متاحة ومطابقة لبصماتها. ويوقف رفض توقيع صريح التثبيت. وتظل الملفات التنفيذية الخارجية خارج ضمانات البصمات والتوقيعات في PM.

      bws و iron-proxy يراعيان ملفًا تنفيذيًا على PATH قبل فحص اختيار PM. ويخضع التثبيت عند الطلب لسياسة PM. وتفحص أوامر التثبيت الصريحة العناصر المُدارة وتصلحها، بما في ذلك الطلبات باستخدام --force.

      سير عمل المطوّر​

      يطلب التفعيل من PM تجهيز سلسلة الأدوات لنسخة مصدر مسحوبة أو مزامنتها، ثم يتيحها في الـ shell. لا يختار مفسّر Python لمحررك، ولا يعيد توجيه تطبيق Desktop مثبّت إلى هذه النسخة المسحوبة.

      تجهيز نسخة مسحوبة​

      استخدم طرفية عادية خارج تطبيق Hermes المغلّف. اخرج أولًا من أي بيئة Python افتراضية حالية. في Windows، استخدم PowerShell الأصلي مع Git. في ARM64، يجهّز PM أدوات Visual Studio C++ و Clang و Rust الأصلي ومكتبات OpenSSL التطويرية الثابتة قبل كل بناء اعتماديات من نسخة مسحوبة: الإعداد و activate.ps1, install.ps1, hermes update والإصلاح على السواء. يعيد استخدام التثبيتات الموجودة ويثبّت المتطلبات المفقودة. تتطلب مكونات Visual Studio المفقودة حقوق مسؤول: يطلبها التثبيت التفاعلي عبر UAC، بينما تحتاج عمليات CI و ssh والتشغيل المجدول إلى PowerShell بصلاحيات Administrator. يستخدم OpenSSL triplet arm64-windows-static-md من vcpkg. ينتج التثبيت المشترك المتضرر خطأ إصلاح، لا حذفًا تلقائيًا. لا تنطبق متغيرات بيئة المترجم و OpenSSL إلا على بناء اعتماديات PM، لا على الـ shell لديك مطلقًا.

      ما تزال المنصات الأخرى تتطلب أدوات المترجم الأصلية والمكتبات اللازمة للاعتماديات التي لا تملك wheels متوافقة.

      لإصدار Python المثبّت على macOS، يضبط PM AR افتراضيًا على /usr/bin/ar: ما يزال sysconfig للمفسّر الموزّع يشير إلى مجلد LLVM المؤقت الخاص بمورّده. ينطبق ذلك على بناء المصدر والحزم معًا. تبقى قيم AR و CC الصريحة هي المرجع؛ لا يغيّر PM سلسلة أدوات مفسّر يوفّره المستدعي مثل Nix Python. لا حاجة إلى افتراضي CC للإصدار المثبّت الحالي.

      استنسخ المستودع واختر branch قبل تجهيز الاعتماديات:

      git clone https://github.com/NousResearch/hermes-agent.git
      cd hermes-agent

      للتطوير المعزول، اختر home بيانات منفصلًا قبل أول أمر PM. احتفظ بالقيم نفسها عند العودة إلى هذه النسخة المسحوبة.

      Bash، من جذر المستودع:

      export HERMES_HOME="$HOME/hermes-dev-data"
      export HERMES_RUNTIME_DIR="$HERMES_HOME/tools"
      source ./activate

      PowerShell، من جذر المستودع:

      $env:HERMES_HOME = Join-Path $HOME 'hermes-dev-data'
      $env:HERMES_RUNTIME_DIR = Join-Path $env:HERMES_HOME 'tools'
      . .\activate.ps1

      HERMES_RUNTIME_DIR في هذه الأمثلة تجاوز تطوير محلي للعملية. يجعل bootstrap و PM يستخدمان المخزن القابل للكتابة نفسه. لا تحفظ مسارًا داخل MSIX مثبّت أو حزمة macOS. يشغّل التفعيل مسار وقت التشغيل وحده في سكربت الإعداد لتوفير الأدوات ومزامنة إضافة Python all. ولا يختار dev أو يثبّت مساحات عمل JS. يصون الأوامر المحلية للتثبيت ويصلح أغلفة PATH المملوكة الموجودة، لكنه لا ينشئ وسائل راحة PATH جديدة أو يحمّل إعدادات التطبيق. ويتخطى أيضًا عمل التثبيت الموجّه للمستخدم في الإعداد: إعداد الـ shell و .env والمهارات المضمّنة. شغّل سكربت الإعداد منفصلًا إذا أردت سير عمل التثبيت الكامل.

      قبل وجود Python، يحصل bootstrap الخاص بـ shell على المفسّر المثبّت. بمجرد إمكان تشغيل Python، يسلّم عمل الاعتماديات إلى PM. يجهّز محرك PM الخاص وقت تشغيله الصغير المقفول قبل حل اعتماديات التطبيق. مشروعه مستقل عن مساحة عمل التطبيق: يجب ألا تمنع اعتمادية تطبيق معطّلة مدير الاعتماديات من بدء التشغيل.

      uv تفصيل تنفيذ خاص بـ PM. يطلب كود التطبيق ومسارات الإعداد ومستدعو البناء عمليات Python، لا ملفات uv التنفيذية أو معاملات أوامره. لا تغيّر بيئة Hermes بأوامر pip أو uv الخام.

      يحتوي وقت تشغيل PM على ruamel.yaml, packaging, tomli-w و truststore لا شجرة اعتماديات التطبيق. تعمل أوامر CLI والتثبيتات والإصلاحات التي يطلبها التطبيق هناك. تبقى عمليات البحث للقراءة فقط عن المسارات والأدوات المثبّتة محلية. تستخدم فحوص حداثة البيئة عامل PM جاهزًا. لا يضيف PM اعتمادياته مطلقًا إلى استيرادات وكيل يعمل بالفعل. تستخدم قارئات وكاتبات YAML الأصلية ruamel؛ وقد تظل حزم الطرف الثالث تحتاج إلى PyYAML في بيئة التطبيق. تبقى إثباتات الفشل قائمة على stdlib فقط.

      يفعّل CLI والعامل في PM truststore قبل استيراد عملاء HTTPS. يستخدم ذلك مخزن شهادات المنصة حتى إذا لم تحدّد مسارات OpenSSL المضمّنة في Python bootstrap مكانه. لا تُطلب اعتماديات تطبيق أو تجاوزات مسارات شهادات. بعد أول تثبيت، يعيد PM بناء بيئته الصغيرة مقابل Python المُدار عند الاستدعاء التالي؛ وتعيد الاستدعاءات اللاحقة استخدامها.

      pm.venv_is_current() يفحص عبر عامل PM موجود، حتى عند تعطيل التثبيتات الكسولة. لا يُقلع PM مطلقًا من أجل فحص. إذا تعذّر وقت تشغيل المدير، يعيد false دون تنزيل أدوات أو اعتماديات. شغّل hermes pm install صراحة لتجهيز PM أولًا.

      تجهّز الحزم الأصلية وصور Docker lock PM نفسه عبر منشئ وقت التشغيل المشترك. يزوّد Termux ذلك المنشئ بـ wheelhouse دون اتصال ومتحقق منه. يبني Nix lock PM كـ derivation مستقل. لا تستخدم العمّال المغلّفة إلا مجلد اعتماديات PM المسجّل، لا مكتبات التطبيق مطلقًا.

      تفعيل تثبيت موجود​

      في كل shell جديد، استعد قيم home التطوير وادخل النسخة المسحوبة. ثم فعّلها؛ لا يوجد أمر إعداد منفصل لتتذكره:

      الـ shellالدخولالخروج
      Bashsource ./activatedeactivate
      fishsource ./activate.fishdeactivate
      PowerShell. .\activate.ps1deactivate

      النقطة والمسافة في البداية مطلوبتان في PowerShell. تنفيذ .\activate.ps1 دون dot-sourcing لا يوفّر نطاق الجلسة نفسه. activate يستخدم صيغة Bash. استخدم Bash لهذه الوصفة بدلًا من sh أو افتراض أن ملف بدء Zsh له دلالات Bash؛ لدى fish ملف activate.fish خاص به يعمل بالطريقة نفسها.

      يستدعي كل تفعيل مسار تثبيت/مزامنة PM، ويثق في digest الأداة المسجّل بدلًا من إعادة hash كل إدخال. ما يزال PM يثبّت أداة مفقودة ويعيد بناء جيل اعتماديات قديم؛ ويحتفظ التثبيت المتعمّد بفحص البايتات. شغّل python -m pm.cli install أو hermes update لإعادة فحص البايتات المحققة. يعيد فشل الإعداد خطأ قبل تغيير بيئة الـ shell المفعّلة، بما في ذلك عند إعادة تحميل بيئة نشطة أصلًا.

      بعد المزامنة، يسبق التفعيل PATH بأدوات PM المثبّتة ويضبط PYTHONPATH إلى هذه النسخة المسحوبة وشجرة اعتمادياتها المحددة. ويعرّف أيضًا hermes كدالة shell لهذا worktree. تشغّل الدالة CLI هذه النسخة وتخفي الأمر المثبّت، بما فيه اسم MSIX البديل. تعمل فقط عندما يكون الـ shell داخل worktree هذا، وترفض خارجه، فلا يرث worktree شقيق الأمر. يكتسب prompt بادئة تسمّي branch، ويفقدها خارج الشجرة. لا يغيّر PATH على مستوى النظام ولا يثبّت prompt تقليديًا لـ venv. ابدأ في shell نظيف بدلًا من تعشيشه داخل venv أخرى. deactivate يعيد قيم البيئة التي التقطها سكربت التفعيل، ويزيل الدالة وبادئة prompt. لا يلغي تثبيت الحزم ولا يوقف عمليات بدأتَها.

      لتشغيل أمر أو سكربت واحد في تلك البيئة دون تفعيل shell، سبقه بـ scripts/run-in-hermes-env. يطبّق البيئة نفسها على ذلك الأمر وحده، ويزامن أولًا إذا لم توجد بيئة موروثة أو كانت الموروثة قديمة، ويترك الـ shell كما هو. يعيد scripts/run_tests.sh تشغيل نفسه بهذه الطريقة، وتسلّم سكربتات Python في المستودع نفسها إليه من سطر shebang.

      scripts/run-in-hermes-env python scripts/release.py --help

      تحقّق من المفسّر والمصدر قبل العمل:

      python -c "import sys, pm; print(sys.executable); print(pm.__file__)"
      python -c "import httpx; print(httpx.__file__)"
      node --version
      npm --version
      hermes --version

      python يجب أن يشير إلى مفسّر مخزن PM. و pm.__file__ يجب أن يشير إلى داخل هذه النسخة المسحوبة. تأتي الاعتماديات من البيئة المحددة التي قد توجد خارج المستودع. يعني الاستيراد المفقود أن الإعداد أو الاختيار يحتاج مراجعة، حتى إذا أعاد source ./activate نفسه بنجاح.

      العمل على شجرة المصدر هذه​

      hermes هو CLI لهذا worktree بينما يكون الـ shell داخله. خارج worktree ترفض الدالة، فلا يمكنها تشغيل شجرة نسخة أخرى أو الرجوع إلى أمر مثبّت:

      hermes setup
      hermes
      hermes --tui
      python -m pm.cli status

      تستخدم هذه الأوامر home التطوير المحدد. يظهر تحرير ملف مصدر للعملية التالية. أعد تشغيل CLI أو gateway أو backend المتأثر بعد التعديلات. لا يلزم إعادة تثبيت كل اعتماديات لتغيير مصدر Python وحده.

      لمساحات عمل JavaScript، شغّل npm ci مرة في جذر المستودع، ثم شغّل أمر مساحة العمل المعنية. مثلًا:

      npm run build --workspace ui-tui
      npm run dev --workspace apps/desktop

      الموقع منفصل: npm ci --prefix website ، ثم npm run build:fast --prefix website. يوفّر تفعيل PM أدوات، لا مجلدات node_modules هذه ولا الأصول المبنية. لبناء Desktop الأصلي متطلبات إضافية في دليل بناء Desktop.

      تحديث الاعتماديات دون تغيير branches​

      بعد تغيير branch أو lockfile، أعد تحميل سكربت التفعيل لمزامنة الاعتماديات الجديدة واختيارها (source ./activate في Bash أو . .\activate.ps1 في PowerShell). للمزامنة دون تفعيل shell:

      python -m pm.cli install

      بعد مزامنة مستقلة، أعد تفعيل البيئة وأعد تشغيل العمليات المتأثرة. استخدم python -m pm.cli doctor لتشخيص الأدوات و python -m pm.cli status لآخر إثبات مزامنة. لا تشغّل hermes update لمجرد تحديث branch ميزة: فهو تحديث للتطبيق وقد يغيّر branch المصدر.

      أسماء الأدوات المُدارة وأسماء إضافات Python واجهتان مختلفتان:

      python -m pm.cli install chromium
      python -c "from pm import sync_venv; sync_venv(['anthropic'], explicit=True)"

      يثبّت الأمر الأول أداة. ويضيف الثاني extra معلنة لوقت التشغيل إلى اختيار Python الحالي لهذا التثبيت. تتراكم الإضافات (extras) عبر مزامنة PM. تنتمي مجموعتا الاعتماديات dev و test إلى بيئة الاختبار المنفصلة فقط، لا venv التطبيق المحددة. بعد تغيير extras، أعد التفعيل قبل بدء عملية Python أخرى.

      المزامنة بعد تحرير pyproject.toml​

      1. حرّر pyproject.toml. ثبّت إصدار كل اعتمادية كما تتطلب سياسة تثبيت إصدارات الاعتماديات. عبّر عن حدود المنصة بعلامات PEP 508، أو قيّد extra كاملة في [tool.hermes.extras-platforms].

      2. أعد إنشاء lock:

        hermes pm lock

        يعيد هذا حل uv.lock من pyproject.toml بالإعدادات نفسها التي يفحصها CI، بما فيها فحص عمر الإصدار exclude-newer البالغ 3 أيام. لا يغيّر أي بيئة. وعندما يكون lock محدّثًا أصلًا، يذكر ذلك ولا يكتب شيئًا. (hermes pm lock --bump NAME VERSION عملية مختلفة: تثبّت أداة مُدارة في pm/lock.json ولا تمس uv.lock.)

      3. أعد تحميل سكربت التفعيل (source ./activate أو . .\activate.ps1 في PowerShell) لمزامنة venv التطبيق ومفسّر الاختبار مع lock الجديد. يغطي التفعيل [all]. إذا أضفت extra اختيارية خارج [all], hermes pm lock يطبع الأمر الذي يضيفها أيضًا إلى مفسّر الاختبار، مثل source ./activate --test-extras all,NAME.

      4. أدرج pyproject.toml و uv.lock في commit معًا.

      لاعتماديات JS، حدّث manifest الحزمة المالكة و lock. لا تحرّر معلومات PM أو مساحات العمل المولّدة، ولا تثبّت حزمًا مباشرة داخل جيل محدد.

      بيئات الاختبار والمحرر​

      source ./activate (أو . .\activate.ps1 في PowerShell) وكلا سكربتي setup-hermes المباشرين تجهّز مفسّر اختبار معزولًا من مجموعتي الاعتماديات المقفلتين dev و test. يستخدم scripts/run_tests.sh ذلك المفسّر، ويعيد التفعيل إذا تغيّرت النسخة المسحوبة أو مدخلات اعتمادياتها. لا تختار venv التطبيق ولا أدوات التثبيت ولا الحزم أيًا من المجموعتين. يغطي افتراضي المطوّر [all] ؛ لتغيير تغطية الاختبار، مرّر --test-extras=anthropic إلى تفعيل POSIX أو -TestExtras anthropic إلى PowerShell؛ تختار تلك المعاملات extras لوقت التشغيل في مفسّر الاختبار وحده.

      في بيئة معزولة لا يتاح فيها التفعيل (مثل shell تطوير Nix)، يمكن للمستدعي توفير HERMES_PYTHON صراحة مع pytest، أو بناء بيئة مؤقتة مستقلة:

      python -m pm.build_env --source . --out .venv --group dev --group test

      يجب ألا يكون المخرج موجودًا. لإعادة توليده، أوقف عملياته وتعمد إزالة تلك البيئة المؤقتة وحدها أولًا. ثم شغّل scripts/run_tests.sh (عبر Bash في Windows). تتضمن مجموعة اعتماديات الاختبار اختبارات المشغّل الأصلي، ولا تدخل وقت تشغيل مغلّفًا مطلقًا.

      لتصحيح الأخطاء في المحرر، اختر ذلك المفسّر المستقل، واضبط مجلد العمل إلى هذه النسخة، وشغّل hermes كالسكربت. أبقِ HERMES_HOME الخاص به منفصلًا عن الإنتاج. لا يهيئ تفعيل الطرفية محررًا يعمل بالفعل. لا توجّه محررًا إلى جيل PM عابر أو ملف Python تنفيذي لتطبيق موقّع.

      واجهات عمليات Python​

      استخدم وحدة pm العامة لعمل اعتماديات Python:

      العمليةالملكية
      pm.sync_venv(extras, explicit=True)جهّز اتحاد اعتماديات التطبيق الكامل واختره، بما فيه الإضافات المفعّلة.
      pm.sync_venv(repair=True, explicit=True)أعد بناء مجموعة الاعتماديات المسجّلة في جيل تطبيق جديد.
      pm.build_environment(source=..., out=..., explicit=True)ابنِ مخرجًا جديدًا يملكه المستدعي وتحقّق منه. لا اكتشاف إضافات ولا اختيار للتطبيق.
      pm.lock_project(source, explicit=True)حدّث lock مشروع صريح دون اختيار بيئة.
      pm.ensure_environment(name, requirements, explicit=True)جهّز جيل اعتماديات معزولًا واختره، وأعد مسار Python الخاص به.
      pm.ensure_python_tool(name, requirements, executable, explicit=True)جهّز أداة معزولة وأعد مسار ملفها التنفيذي.
      pm.environment_python(name) / pm.python_tool(name, executable)اقرأ المسارات المحددة دون تثبيت شيء.
      pm.venv_is_current()اسأل عامل PM جاهزًا عما إذا كانت اعتماديات التطبيق محدّثة. أعد false إذا تعذّر وقت تشغيل المدير.

      pm.stage_manager_runtime(...) هو استثناء bootstrap. يجهّز وقت تشغيل PM المقفول نفسه عبر المحرك الخاص المباشر، لأن ذلك الوقت لا يستطيع بناء نفسه عبر عامله. لا يعرّض uv للمستدعي.

      pm.build_env هو واجهة الأوامر لأعمال البناء و lock الصريحة. شغّل python -m pm.build_env --help لخياراته المدعومة. افتراضيًا، تستخدم عمليات بناء المشاريع lock المعتمد. يحلّ --resolve قبل البناء. يختار --python مفسّر بناء صريحًا. يزيل --sealed مراجع .pth وقت البناء. ويتحكم --offline و --cache في الحصول على الاعتماديات.

      في بناءات بيئة التطبيق، يجب أن يكون PM قادرًا بالفعل على العمل داخل Python المستدعي. هذه البناءات ليست تهيئة (bootstrap) للمفسّر. فهي لا تعدّل عمليات الاستيراد في تطبيق قيد التشغيل ولا تستبدل بيئته المختارة. وتبقى بناءات uv2nix التصريحية الخاصة بـ Nix تحت مسؤولية Nix: إذ لا يزال nix develop يبني اعتمادياته باستخدام uv2nix، ثم ينقل ذلك venv إلى المفسّر الذي يثبّته pm/lock.json (لا يستطيع uv2nix البناء على مفسّر من نوع tarball). كما أن uv و node و npm و ripgrep و ffmpeg في الـ shell هي بناءات ملف القفل نفسه. ولا تدير أوامر مدير الحزم الخاصة بمشاريع غير ذات صلة أو بـ sandboxes الوكلاء Hermes نفسه.

      الأوامر​

      hermes pm --help
      hermes pm doctor
      hermes pm status
      hermes pm install
      hermes pm install chromium
      الأمرالأثر
      pm install [names...]ثبّت الحزم المسماة. دون أسماء، وفّر الأدوات المطلوبة مع Python، وضعها على PATH، ثم زامن extra all. يثبّت التثبيت المجرد أيضًا الأدوات الاختيارية الافتراضية (chromium، وهو المتصفح الذي يشغّله Hermes، و cua-driver)؛ وفشل تنزيلها يطبع تحذيرًا ولا يفشل التثبيت. تسمية حزمة رفضتها سابقًا تلغي ذلك الاختيار.
      pm install --without NAMEنفّذ تثبيتًا مجردًا دون الحزمة الاختيارية الافتراضية NAME (chromium أو cua-driver)، وسجّل هذا الاختيار. وتستبعدها أيضًا التثبيتات المجردة اللاحقة و hermes update. وتستخدم خيارات المُثبّتات --skip-browser / -SkipBrowser و --skip-computer-use / -SkipComputerUse (--without cua-driver) هذه الآلية. يمرّر خيار استبعاد المتصفح الاسم القديم --without agent-browser، الذي تقبله كل إصدارات PM وتقرؤه هذه النسخة على أنه chromium؛ والاختيار المسجَّل تحت ذلك الاسم لا يزال يتخطى chromium.
      pm install --tools-onlyثبّت مجموعة اعتماديات الأداة الكاملة وضعها على PATH، ثم توقف. لا تعمل مزامنة venv.
      pm env [names...]اطبع قيم البيئة التي يساهم بها PM للحزم المثبّتة كـ JSON. لا يثبّت حزمًا مفقودة، وإن كان إطلاق Hermes البارد قد يجهّز وقت تشغيل Python الخاص به أولًا.
      pm doctorافحص هويات الأدوات المثبّتة وملفاتها و digests مقابل lock.
      pm repairأعد بناء مجموعة اعتماديات Python المسجّلة في جيل جديد، وتحقق منها ثم اخترها. لا يحدّث الإصدارات المثبتة أو الميزات أو إعدادات الإضافات.
      pm statusاطبع آخر إثبات مزامنة/تحديث كـ JSON، أو أبلغ عن عدم وجود إثبات.
      pm gcأزل إدخالات مخزن الأدوات غير المرجعية وأجزاء التنزيل المؤهلة وأجيال Python غير المستخدمة والمُدارة بالعقود وحالة installs/INSTALL_KEY/ للنسخ المسحوبة المحذوفة (worktree أُزيل من مجلد .worktrees/ ما يزال موجودًا، أو clone تحت جذر البيانات؛ تُحفظ النسخ التي لا تستطيع هذه العملية رؤيتها، مثل تثبيت مضيف يُرى من حاوية تشارك جذر البيانات، وتُحفظ كذلك أي حالة ما يزال قفل تثبيتها أو عقد جيلها محتجزًا). يستعيد منظّف worktrees الذي يعمل عند التشغيل تلك المجلدات اليتيمة أيضًا.

      pm env يستبعد متغيرات العملية الموروثة، بما فيها بيانات الاعتماد. وقد تكشف مخرجاته مسارات تثبيت محلية؛ راجعها قبل مشاركتها.

      أوامر القائمين على الصيانة​

      تغيّر هذه الأوامر مدخلات الاعتماديات أو تجهّز مخرجات بناء. ليست بدائل لآلية تحديث تطبيق مثبّت.

      الأمرالأثر
      pm lockأعد إنشاء lock لـ uv.lock من pyproject.toml. لا يغيّر بيئة؛ ولا يكتب شيئًا عندما يكون lock محدّثًا.
      pm lock --bump NAME VERSIONحلّ مخرجات الأهداف المدعومة واحسب hashes لها، واكتب تثبيت الأداة في pm/lock.json، وأعد توليد تثبيتات التهيئة (bootstrap) في scripts/install.sh و scripts/install.ps1.
      pm update [names...]استعلم عن الإصدارات في المصدر الأصلي، وغيّر تثبيتات الأدوات، وأعد توليد تثبيتات التهيئة (bootstrap) الخاصة بالمُثبّتات، وثبّت الأدوات التي تغيّرت.
      pm update --checkاستعلم دون كتابة. قد يعني الخروج 1 وجود تحديثات؛ افحص المخرجات لتمييز الخطأ.
      pm update --target TARGETحل الإصدارات للهدف المحدد.
      pm update --skip-target TARGETاترك تثبيتات TARGET دون تغيير (قابل للتكرار)، مثل linux-arm64-bionic بينما يتأخر مستودع termux عن المصدر الأصلي. وتستمر عمليات التشغيل اللاحقة في الإبلاغ بأن الحزمة محدّثة. يعيد pm lock --bump NAME VERSION تثبيت كل الأهداف عند إصدار معيّن، ويعيد pm update --termux تثبيت صف linux-arm64-bionic المتقاعد.
      pm update --uv / --npmحدّث أيضًا حل اعتماديات Python أو npm.
      pm update --termux [--check]أعد تثبيت أرشيفات termux pool التي تقاعدت من rolling pool (جدول تثبيت runtime-lib وصفوف lock الخاصة بـ bionic). --check يُبلغ دون كتابة ويخرج 1 عند تقاعد تثبيت.
      pm install --target TARGET NAME...جهّز حزمًا صريحة لأهداف مختلفة دون تسجيلها كوقت تشغيل مثبّت للمضيف. هدف win32 git يثبّت أرشيف PortableGit ذاتي الاستخراج: تجهيزه يشغّل مستخرج المورّد، لذا يتطلب مضيف Windows.
      pm bundle --out DIR [--ref REF]جهّز لقطة مصدر وأدوات أصلية ومعلومات واعتماديات Python. لا ينتج مُثبّت Desktop موقّعًا.

      يبني منشئ Desktop الكامل أيضًا واجهات JavaScript، ويولّد مشغّلات ويستدعي التغليف الأصلي. يمكن للقائمين على الصيانة قراءة بناء أدوات تثبيت Desktop.

      إعادة محاولات الشبكة​

      يعيد PM محاولة أخطاء HTTP العابرة أثناء تنزيل الأدوات وحساب hashes للمخرجات والبحث عن الإصدارات. وللفحوص وعمليات النقل غير القابلة للاستئناف أربع محاولات كحد أقصى. وفترات التراجع (backoff) فيها 1 و 2 و 4 ثوانٍ. ويمكن لترويسة Retry-After تمديد هذه الفترات حتى 30 ثانية. أما عمليات النقل القابلة للاستئناف فتجدّد رصيد محاولاتها عندما تحفظ تقدمًا جديدًا؛ وتوقف أربعة إخفاقات دون تقدم جديد إعادةَ المحاولة. وعند توفر مرآة مثبّتة، تتحول الانتظارات التي تتجاوز 30 ثانية إلى تلك المرآة. ويحترم المصدر الأخير Retry-After حتى خمس دقائق ويتوقف عند الانتظارات الأطول. وتسجّل كل إعادة محاولة سببها وتأخيرها وعدد الإخفاقات المتتالية دون تقدم.

      حالات HTTP القابلة لإعادة المحاولة هي 408 و 429 و 500 و 502 و 503 و 504. كما تُعاد المحاولة عند إعادة تعيين الاتصال، وانتهاء المهلة، وأعطال DNS المؤقتة، وانقطاع أجسام الاستجابات. وتحفظ التنزيلات ذات النطاقات (ranged) نقطة تحقق كل خمس ثوانٍ وبعد كل محاولة. ويسجّل إخفاق نقطة التحقق الدورية تحذيرًا ويُعاد لاحقًا؛ أما نقطة التحقق الأخيرة فمطلوبة. وتتطلب الخوادم التي لا تدعم النطاقات بثًا جديدًا. ويقاطع الإيقاف المؤقت فترة التراجع ويحافظ على التنزيل الجزئي.

      لا يعيد PM محاولة hashes غير الصحيحة أو أخطاء الشهادات أو نظام الملفات المحلي أو غيرها من الأخطاء الدائمة. فحص ناجح يتبعه GET نطاق بخطأ 403 أو 404 يحافظ على احتياط CDN: محاولة تسلسلية واحدة للنطاقات المفقودة. لا تتكرر عمليات الاستخراج والتحقق والنشر. تبقى طلبات حزم Python و npm تحت سياسات إعادة المحاولة الخاصة بـ uv و npm.

      عمر الإصدار ومرايا الحِزم (package mirrors)​

      يجب أن يكون عمر كل حزمة Python يعتمد عليها Hermes نفسه ثلاثة أيام على الأقل عندما يقفلها Hermes (الخيار exclude-newer في uv، ويفرضه فحص lock في CI)، فلا يمكن لإصدار منشور حديثًا وربما مخترَق أن يصل إلى uv.lock. ويثبّت المستخدمون من ذلك lock، ولا يعيد تثبيتُ إضافة أو تفعيلها فحصَ التواريخ، لذلك تعمل مرايا الحِزم التي لا تنشر أوقات الرفع. والاستثناء الوحيد هو مخازن الثقة في CA (certifi): فالإصدار الذي يسحب الثقة من CA مخترَقة يُقفل في يوم صدوره، لأن الانتظار يُبقي الجذر السيئ موثوقًا. اضبط مرآة عبر index-url في pip.conf، الذي يمرّره Hermes إلى uv، أو عبر UV_INDEX_URL.

      hermes pm lock هو الخطوة الوحيدة التي تطبّق هذا الفحص. وإذا نفّذته على مرآة لا تحتوي أوقات رفع، فسيتوقف برسالة has no publish time؛ استخدم https://pypi.org/simple لتلك الخطوة.

      التشخيص​

      • بناء اعتماديات Python بطيء: تفعّل أوامر uv المتدفقة من PM المخرجات التفصيلية. تعرض سجلات الحزم والبناء نشاط الحزم و stdout/stderr الخاص بـ build-backend أثناء البناء، لا بعد الفشل فقط.
      • أداة مفقودة أو قديمة: اقرأ hermes pm doctor ، ثم استخدم تثبيت PM صريحًا على تثبيت قابل للكتابة.
      • بيئة جديدة تتطلب إعادة التشغيل: أعد تشغيل عملية Hermes المتأثرة. لا تضف شجرة site-packages ثانية إلى استيراداتها الحيّة.
      • تعارض اعتماديات: اقرأ hermes pm status. صحّح متطلبات الإضافة قبل إعادة محاولة القبول.
      • اعتماديات Python متضررة: شغّل hermes pm repair ، ثم أعد تشغيل Hermes. يعيد الإصلاح بناء مساحة عمل الجيل المحدد و lock المحفوظين دون تحليل إعدادات الإضافات. السجل غير المقروء أو lock المحفوظ المفقود يفشل دون اختيار مجموعة اعتماديات ناقصة. قبل وجود جيل، يستخدم الإصلاح lock المشحون أو المعتمد ومجموعة الميزات المسجّلة.
      • تثبيت اعتماديات منقطع: يطلب بدء التشغيل إصلاح PM نفسه قبل تفعيل الاعتماديات. المحاولات التلقائية محدودة؛ ويعيد pm repair المحاولة صراحة. يحفظ الإصلاح الفاشل الاختيار السابق وعلامة إعادة المحاولة.
      • ملف Python تنفيذي أو مصدر تطبيق متضرر: أصلح أو أعد التثبيت عبر مالك الحزمة. لا يستطيع PM العمل دون تلك الملفات. لا يعدّل إصلاح الاعتماديات ملفات الحمولة الموقّعة مطلقًا.
      • حزمة أو extra غير معروفة: استخدم الاسم المعلن. يأخذ pm install أسماء الحزم، لا أسماء extras الخاصة بـ Python أو مواصفات pip.

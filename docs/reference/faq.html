      الأسئلة الشائعة واستكشاف الأخطاء وإصلاحها

      إجابات سريعة وحلول لأكثر الأسئلة والمشكلات شيوعًا.

      الأسئلة الشائعة​

      ما مزوّدو LLM التي تعمل مع Hermes؟​

      يعمل Hermes Agent مع أي API متوافق مع OpenAI. تشمل المزوّدين المدعومين:

      • OpenRouter — الوصول إلى مئات النماذج عبر مفتاح API واحد (مُوصى به للمرونة)
      • Nous Portal — بوابة الاشتراك من Nous Research — أكثر من 300 نموذج بالإضافة إلى الويب/الصور/TTS/المتصفح عبر تسجيل دخول OAuth واحد (مُوصى به للمبتدئين)
      • OpenAI — نماذج GPT-5.4 وGPT-5-codex وGPT-4.1 وGPT-4o وغيرها
      • Anthropic — نماذج Claude (API مباشر، OAuth عبر hermes auth add anthropic، أو OpenRouter، أو أي proxy متوافق)
      • Google — نماذج Gemini (API مباشر عبر مزوّد gemini، أو OpenRouter، أو proxy متوافق)
      • z.ai / ZhipuAI — نماذج GLM
      • Kimi / Moonshot AI — نماذج Kimi
      • MiniMax — endpoints عالمية وأخرى خاصة بالصين
      • النماذج المحلية — عبر Ollama أو vLLM أو llama.cpp أو SGLang، أو أي خادم متوافق مع OpenAI

      اضبط مزوّدك عبر hermes model أو بتحرير ~/.hermes/.env. راجع مرجع متغيرات البيئة لكل مفاتيح المزوّدين.

      هل يعمل على Windows/Android/Termux/منصتي؟؟​

      راجع دعم المنصات للاطلاع على مصفوفة توفر المنصات الكاملة.

      أُشغّل Hermes في WSL2. ما أفضل طريقة للتحكم في Chrome العادي على Windows؟​

      يُفضَّل استخدام جسر MCP بدلًا من /browser connect.

      النمط المُوصى به:

      • شغّل Hermes داخل WSL2
      • واصل استخدام Chrome العادي المسجَّل الدخول على Windows
      • أضف chrome-devtools-mcp كخادم MCP عبر cmd.exe أو powershell.exe
      • دع Hermes يستخدم أدوات المتصفح الناتجة من MCP

      هذا أكثر موثوقية من محاولة إجبار نقل المتصفح الأساسي في Hermes على الاتصال مباشرة عبر الحد الفاصل بين WSL2 وWindows.

      راجع:

      • استخدام MCP مع Hermes
      • أتمتة المتصفح (Browser Automation)

      هل تُرسَل بياناتي إلى أي مكان؟​

      تذهب استدعاءات API فقط إلى مزوّد LLM الذي تضبطه (مثل OpenRouter، أو نسخة Ollama المحلية لديك). لا يجمع Hermes Agent أي بيانات قياس عن بعد (telemetry) أو بيانات استخدام أو تحليلات. تُخزَّن محادثاتك وذاكرتك ومهاراتك محليًا في ~/.hermes/.

      هل يمكنني استخدامه دون اتصال / مع نماذج محلية؟​

      نعم. شغّل hermes model، واختر Custom endpoint، وأدخل رابط خادمك:

      hermes model
      # Select: Custom endpoint (enter URL manually)
      # API base URL: http://localhost:11434/v1
      # API key: ollama
      # Model name: qwen3.5:27b
      # Context length: 64000   ← Hermes minimum; set this to match your server's actual context window

      أو اضبطه مباشرة في config.yaml:

      model:
        default: qwen3.5:27b
        provider: custom
        base_url: http://localhost:11434/v1

      يحفظ Hermes الـ endpoint والمزوّد والرابط الأساسي في config.yaml بحيث يبقى بعد إعادة التشغيل. إذا كان خادمك المحلي يحمّل نموذجًا واحدًا فقط، فإن /model custom يكتشفه تلقائيًا. يمكنك أيضًا ضبط provider: custom في config.yaml — فهو مزوّد أساسي بحدّ ذاته، وليس اسمًا بديلًا لأي شيء آخر.

      يعمل هذا مع Ollama وvLLM وخادم llama.cpp وSGLang وLocalAI وغيرها. راجع دليل الإعدادات للتفاصيل.

      لمستخدمي Ollama

      إذا ضبطت قيمة num_ctx مخصصة في Ollama (مثلًا، ollama run --num_ctx 64000)، فتأكد من ضبط طول السياق المطابق في Hermes — إذ يُبلِّغ /api/show في Ollama عن السياق الأقصى للنموذج، وليس قيمة num_ctx الفعلية التي ضبطتها.

      المهلات الزمنية مع النماذج المحلية

      يكتشف Hermes تلقائيًا endpoints المحلية ويخفف مهلات البث (رفع مهلة القراءة من 120 ثانية إلى 1800 ثانية، وتعطيل كشف البث الراكد). إذا استمررت في مواجهة مهلات مع سياقات كبيرة جدًا، اضبط HERMES_STREAM_READ_TIMEOUT=1800 في ملف .env. راجع دليل LLM المحلي للتفاصيل.

      كم تكلفته؟​

      Hermes Agent نفسه مجاني ومفتوح المصدر (ترخيص MIT). تدفع فقط مقابل استخدام API الخاص بـ LLM من المزوّد الذي تختاره. النماذج المحلية مجانية تمامًا للتشغيل.

      هل يمكن لعدة أشخاص استخدام نسخة واحدة؟​

      نعم. تتيح بوابة المراسلة (messaging gateway) لعدة مستخدمين التفاعل مع نفس نسخة Hermes Agent عبر Telegram أو Discord أو Slack أو WhatsApp أو Home Assistant. يُتحكَّم في الوصول عبر قوائم السماح (معرّفات مستخدمين محددة) واقتران DM (أول مستخدم يرسل رسالة يحصل على الوصول).

      ما الفرق بين الذاكرة والمهارات؟​

      • الذاكرة تخزّن الحقائق — أشياء يعرفها الوكيل عنك، وعن مشاريعك، وتفضيلاتك. تُسترجَع الذكريات تلقائيًا بحسب الصلة.
      • المهارات تخزّن الإجراءات — تعليمات خطوة بخطوة لكيفية القيام بالأشياء. تُستدعى المهارات عندما يواجه الوكيل مهمة مشابهة.

      كلاهما يبقى محفوظًا عبر الجلسات. راجع الذاكرة والمهارات للتفاصيل.

      هل يمكنني استخدامه في مشروع Python الخاص بي؟​

      نعم. استورد فئة AIAgent واستخدم Hermes برمجيًا:

      from run_agent import AIAgent

      agent = AIAgent(model="anthropic/claude-opus-4.7")
      response = agent.chat("Explain quantum computing briefly")

      راجع دليل مكتبة Python للاستخدام الكامل لواجهة البرمجة.

      استكشاف الأخطاء وإصلاحها​

      مشكلات التثبيت​

      hermes: command not found بعد التثبيت​

      السبب: لم يُعِد الـ shell لديك تحميل قيمة PATH المحدَّثة.

      الحل:

      # Reload your shell profile
      source ~/.bashrc    # bash
      source ~/.zshrc     # zsh

      # Or start a new terminal session

      إذا استمرت المشكلة، فتحقق من موقع التثبيت:

      which hermes
      ls ~/.local/bin/hermes
      نصيحة

      يضيف المُثبّت المسار ~/.local/bin إلى PATH لديك. إذا كنت تستخدم ملف إعدادات shell غير قياسي، فأضف export PATH="$HOME/.local/bin:$PATH" يدويًا.

      إصدار Python قديم جدًا​

      السبب: يتطلب Hermes الإصدار Python 3.11 أو أحدث.

      الحل:

      python3 --version   # Check current version

      # Install a newer Python
      sudo apt install python3.12   # Ubuntu/Debian
      brew install python@3.12      # macOS

      يتولى المُثبّت ذلك تلقائيًا — إذا ظهر لك هذا الخطأ أثناء التثبيت اليدوي، فرقِّ Python أولًا.

      أوامر الطرفية تُظهر node: command not found (أو nvm، pyenv، asdf، …)​

      السبب: يبني Hermes لقطة (snapshot) لبيئة كل جلسة عبر تشغيل bash -l مرة واحدة عند بدء التشغيل. يقرأ login shell في bash الملفات /etc/profile و ~/.bash_profile و ~/.profile، لكنه لا يُحمّل (source) الملف ~/.bashrc — لذا تبقى الأدوات التي تثبّت نفسها هناك (nvm و asdf و pyenv و cargo وعمليات تصدير PATH المخصصة) غير مرئية للّقطة. ويحدث هذا غالبًا عندما يعمل Hermes تحت systemd أو في shell مصغّر لم يُحمَّل فيه ملف تعريف الـ shell التفاعلي مسبقًا.

      الحل: يُحمّل Hermes الملف ~/.bashrc تلقائيًا بشكل افتراضي. إذا لم يكن ذلك كافيًا — مثلًا إذا كنت من مستخدمي zsh وكان PATH لديك مضبوطًا في ~/.zshrc، أو كنت تهيّئ nvm من ملف مستقل — فأدرج الملفات الإضافية المطلوب تحميلها في ~/.hermes/config.yaml:

      terminal:
        shell_init_files:
          - ~/.zshrc                     # zsh users: pulls zsh-managed PATH into the bash snapshot
          - ~/.nvm/nvm.sh                # direct nvm init (works regardless of shell)
          - /etc/profile.d/cargo.sh      # system-wide rc files
        # When this list is set, the default ~/.bashrc auto-source is NOT added —
        # include it explicitly if you want both:
        #   - ~/.bashrc
        #   - ~/.zshrc

      تُتخطّى الملفات غير الموجودة بصمت. يجري التحميل داخل bash، لذا قد تُسبّب الملفات التي تعتمد على صياغة خاصة بـ zsh أخطاءً — إذا كان ذلك يقلقك، فحمّل الجزء الخاص بضبط PATH فقط (مثل الملف nvm.sh الخاص بـ nvm مباشرةً) بدلًا من ملف rc بأكمله.

      لتعطيل سلوك التحميل التلقائي (والاكتفاء بدلالات login shell الصارمة فقط):

      terminal:
        auto_source_bashrc: false

      uv: command not found​

      السبب: مدير الحزم uv غير مثبّت أو غير موجود في PATH.

      الحل:

      curl -LsSf https://astral.sh/uv/install.sh | sh
      source ~/.bashrc

      أخطاء رفض الصلاحية (Permission denied) أثناء التثبيت​

      السبب: لا تتوفر صلاحيات كافية للكتابة في مجلد التثبيت.

      الحل:

      # Don't use sudo with the installer — it installs to ~/.local/bin
      # If you previously installed with sudo, clean up:
      sudo rm /usr/local/bin/hermes
      # Then re-run the standard installer
      curl -fsSL https://hermes-agent.nousresearch.com/install.sh | bash

      مشكلات المزوّد والنموذج​

      الوكيل يقول إن "Hermes policy" أو "Hermes guardrails" رفضت طلبي​

      لا يستطيع النموذج أن يحدد بشكل موثوق سبب رفضه لطلبٍ ما. إذا ظهر الرفض في النص النثري للمساعد فقط، فقد يكون ادعاؤه بأن سياسة وقت تشغيل خفية في Hermes هي السبب تفسيرًا مُختلَقًا ناتجًا عن الهلوسة، أو قيدًا فرضه النموذج أو المزوّد المختار.

      تطبيق القيود في Hermes صريح: إجراء الأداة المحظور يُعيد خطأ أداة يُسمّي الأمر أو المسار المرفوض، والإجراء الذي يتطلب موافقة يعرض طلب موافقة. ولا يحوّل Hermes ضوابط التنفيذ هذه بصمت إلى طبقة عامة لرفض المحتوى. ومع ذلك، قد تُطبَّق ضوابط على مستوى المزوّد عند إعدادها، مثل Amazon Bedrock Guardrails.

      لعزل مصدر الرفض:

      1. نفّذ /status للتأكد من النموذج والمزوّد النشطين.
      2. تحقق مما إذا كان الرفض يتضمن خطأ أداة فعليًا من Hermes أو طلب موافقة. إذا كان نصًا نثريًا فقط، فلا تتعامل مع نسبة النموذج للرفض على أنها دليل من وقت التشغيل.
      3. أعد المحاولة في جلسة جديدة باستخدام نموذج أو مزوّد آخر مُعَدّ. الرفض الذي يتغير بتغيّر النموذج هو سلوك خاص بالنموذج/المزوّد، وليس ضابط تنفيذ من Hermes.
      4. إذا ظهر خطأ أداة صريح، فاستخدم نصه الحرفي عند الإبلاغ عن المشكلة.

      راجع الأمان للاطلاع على ضوابط التنفيذ الموثّقة في Hermes، وصفحة المزوّدين (Providers) لمعرفة كيفية إعداد المزوّدين.

      /model يعرض مزوّدًا واحدًا فقط / تعذّر التبديل بين المزوّدين​

      السبب: لا يستطيع /model (داخل جلسة محادثة) التبديل إلا بين المزوّدين الذين سبق أن أعددتهم. إذا لم تُعِدّ سوى OpenRouter، فهذا كل ما سيعرضه /model.

      الحل: اخرج من جلستك واستخدم hermes model من الطرفية لإضافة مزوّدين جدد:

      # Exit the Hermes chat session first (Ctrl+C or /quit)

      # Run the full provider setup wizard
      hermes model

      # This lets you: add providers, run OAuth, enter API keys, configure endpoints

      بعد إضافة مزوّد جديد عبر hermes model، ابدأ جلسة محادثة جديدة — وسيعرض /model حينها جميع المزوّدين الذين أعددتهم.

      مرجع سريع
      إذا أردت...استخدم
      إضافة مزوّد جديدhermes model (من الطرفية)
      إدخال مفاتيح API أو تغييرهاhermes model (من الطرفية)
      تبديل النموذج أثناء الجلسة/model <name> (داخل الجلسة)
      التبديل إلى مزوّد آخر مُعَدّ/model provider:model (داخل الجلسة)

      مفتاح API لا يعمل​

      السبب: المفتاح مفقود، أو منتهي الصلاحية، أو مضبوط بشكل غير صحيح، أو يخص مزوّدًا آخر.

      الحل:

      # Check your configuration
      hermes config show

      # Re-configure your provider
      hermes model

      # Or set directly
      hermes config set OPENROUTER_API_KEY sk-or-v1-xxxxxxxxxxxx
      تحذير

      تأكد من أن المفتاح يطابق المزوّد. فمفتاح OpenAI لن يعمل مع OpenRouter والعكس صحيح. وتحقق من ~/.hermes/.env بحثًا عن إدخالات متعارضة.

      النموذج غير متاح / النموذج غير موجود​

      السبب: معرّف النموذج غير صحيح أو غير متاح لدى مزوّدك.

      الحل:

      # List available models for your provider
      hermes model

      # Set a valid model
      hermes config set model.default anthropic/claude-opus-4.7

      # Or specify per-session
      hermes chat --model openrouter/meta-llama/llama-3.1-70b-instruct

      تجاوز حدّ المعدل (أخطاء 429)​

      السبب: تجاوزت حدود المعدل (rate limits) لدى مزوّدك.

      الحل: انتظر لحظة ثم أعد المحاولة. أما للاستخدام المستمر، ففكّر في:

      • ترقية خطة الاشتراك لدى مزوّدك
      • التبديل إلى نموذج أو مزوّد مختلف
      • استخدام hermes chat --provider <alternative> للتوجيه إلى backend مختلف

      تجاوز طول السياق​

      السبب: أصبحت المحادثة أطول مما يتسع له context window الخاص بالنموذج، أو اكتشف Hermes طول سياق خاطئًا لنموذجك.

      الحل:

      # Compress the current session
      /compress

      # Or start a fresh session
      hermes chat

      # Use a model with a larger context window
      hermes chat --model openrouter/google/gemini-3-flash-preview

      إذا حدث هذا في أول محادثة طويلة، فربما يكون Hermes قد اعتمد طول سياق خاطئًا لنموذجك. تحقق مما اكتشفه:

      انظر إلى سطر بدء تشغيل CLI — فهو يعرض طول السياق المكتشف (مثل 📊 Context limit: 128000 tokens). ويمكنك أيضًا التحقق باستخدام /usage أثناء الجلسة.

      الخوادم المحلية (llama.cpp و Ollama) التي تصمت بدلًا من إظهار خطأ: عندما يرفض مزوّدٌ طلبًا لأنه كبير جدًا، يضغط Hermes المحادثة ويعيد بناء الطلب. ثم يعيد Hermes قياس الطلب المُعاد بناؤه كاملًا (system prompt + مخططات الأدوات + الرسائل) قبل إعادة المحاولة، ويُجري جولات ضغط إضافية محدودة إذا ظل الطلب فوق الحدّ. وإذا تعذّر احتواء الطلب رغم ذلك، ينتهي الدور بالرسالة Context length exceeded: compression could not reduce the rebuilt request below the safe threshold بدلًا من إرسال طلب ضخم يقتطعه llama.cpp بصمت (stop processing: n_tokens = 65535, truncated = 1 في سجل الخادم). إذا صادفت هذه الرسالة، فالحل في الغالب هو ضبط قيمة context_length المذكورة أعلاه: اجعلها مطابقة للقيمة الفعلية لـ -c / --ctx-size على الخادم.

      لإصلاح اكتشاف طول السياق، اضبطه صراحةً:

      # In ~/.hermes/config.yaml
      model:
        default: your-model-name
        context_length: 131072  # your model's actual context window

      أو بالنسبة إلى endpoints المخصصة، أضفه لكل نموذج على حدة ضمن إدخال المزوّد:

      providers:
        my-server:
          api: "http://localhost:11434/v1"
          models:
            qwen3.5:27b:
              context_length: 64000

      (تستخدم ملفات الإعدادات الأقدم القائمة القديمة custom_providers: — وهي لا تزال مدعومة وتُرحَّل تلقائيًا إلى providers:.)

      راجع اكتشاف طول السياق (Context Length Detection) لمعرفة كيفية عمل الاكتشاف التلقائي وجميع خيارات تجاوز القيمة.

      مشكلات الطرفية​

      حظر الأمر بوصفه خطيرًا​

      السبب: اكتشف Hermes أمرًا قد يكون مدمّرًا (مثل rm -rf أو DROP TABLE). وهذه ميزة أمان.

      الحل: عند ظهور الطلب، راجع الأمر واكتب y للموافقة عليه. ويمكنك أيضًا:

      • أن تطلب من الوكيل استخدام بديل أكثر أمانًا
      • أن تطّلع على القائمة الكاملة للأنماط الخطيرة في توثيق الأمان
      نصيحة

      هذا هو السلوك المقصود — فلا يشغّل Hermes الأوامر المدمّرة بصمت أبدًا. ويعرض لك طلب الموافقة بالضبط ما سيُنفَّذ.

      sudo لا يعمل عبر الـ messaging gateway​

      السبب: يعمل الـ messaging gateway دون طرفية تفاعلية، لذا لا يستطيع sudo طلب كلمة المرور.

      الحل:

      • تجنّب استخدام sudo عبر المراسلة — واطلب من الوكيل إيجاد بدائل
      • إذا كان لا بد من استخدام sudo، فاضبط sudo دون كلمة مرور لأوامر محددة في /etc/sudoers
      • أو انتقل إلى واجهة الطرفية لتنفيذ المهام الإدارية: hermes chat

      تعذّر اتصال Docker backend​

      السبب: الـ daemon الخاص بـ Docker لا يعمل، أو يفتقر المستخدم إلى الصلاحيات اللازمة.

      الحل:

      # Check Docker is running
      docker info

      # Add your user to the docker group
      sudo usermod -aG docker $USER
      newgrp docker

      # Verify
      docker run hello-world

      مشكلات المراسلة​

      البوت لا يرد على الرسائل​

      السبب: البوت لا يعمل، أو غير مُفوَّض، أو أن مستخدمك غير موجود في قائمة السماح (allowlist).

      الحل:

      # Check if the gateway is running
      hermes gateway status

      # Start the gateway
      hermes gateway start

      # Check logs for errors
      cat ~/.hermes/logs/gateway.log | tail -50

      الرسائل لا تصل​

      السبب: مشكلات في الشبكة، أو انتهاء صلاحية token البوت، أو خطأ في إعداد webhook المنصة.

      الحل:

      • تحقق من صلاحية token البوت باستخدام hermes gateway setup
      • راجع سجلات الـ gateway: cat ~/.hermes/logs/gateway.log | tail -50
      • بالنسبة إلى المنصات المعتمدة على webhook (Slack و WhatsApp)، تأكد من أن خادمك متاح للوصول العام

      التباس بشأن قائمة السماح — من يمكنه التحدث إلى البوت؟​

      السبب: وضع التفويض هو ما يحدد من يحصل على الوصول.

      الحل:

      الوضعآلية العمل
      قائمة السماح (Allowlist)لا يستطيع التفاعل إلا أصحاب معرّفات المستخدمين المدرجة في الإعدادات
      الاقتران عبر DM (DM pairing)أول مستخدم يراسل البوت في الرسائل المباشرة يحصل على وصول حصري
      مفتوح (Open)يمكن لأي شخص التفاعل (غير موصى به لبيئات الإنتاج)

      اضبط ذلك في ~/.hermes/config.yaml ضمن إعدادات الـ gateway الخاص بك. راجع توثيق المراسلة.

      تعذّر تشغيل الـ Gateway​

      السبب: اعتماديات مفقودة، أو تعارض في المنافذ، أو tokens مضبوطة بشكل خاطئ.

      الحل:

      # Install core messaging gateway dependencies
      cd ~/.hermes/hermes-agent && uv pip install -e ".[messaging]"  # Telegram, Discord, Slack, and shared gateway deps

      # Check for port conflicts
      lsof -i :8080

      # Verify configuration
      hermes config show

      WSL: الـ Gateway ينقطع اتصاله باستمرار أو يفشل hermes gateway start​

      السبب: دعم systemd في WSL غير موثوق. فكثير من تثبيتات WSL2 لا يكون systemd مفعّلًا فيها، وحتى عند تفعيله، قد لا تصمد الخدمات بعد إعادة تشغيل WSL أو بعد إيقاف Windows له بسبب الخمول.

      الحل: استخدم وضع المقدمة (foreground) بدلًا من خدمة systemd:

      # Option 1: Direct foreground (simplest)
      hermes gateway run

      # Option 2: Persistent via tmux (survives terminal close)
      tmux new -s hermes 'hermes gateway run'
      # Reattach later: tmux attach -t hermes

      # Option 3: Background via nohup
      nohup hermes gateway run > ~/.hermes/logs/gateway.log 2>&1 &

      إذا أردت تجربة systemd على أي حال، فتأكد من تفعيله:

      1. افتح /etc/wsl.conf (وأنشئه إن لم يكن موجودًا)
      2. أضف: 
        [boot]
        systemd=true
      3. من PowerShell: wsl --shutdown
      4. أعد فتح طرفية WSL
      5. تحقق: يجب أن يُظهر systemctl is-system-running القيمة "running" أو "degraded"
      التشغيل التلقائي عند إقلاع Windows

      للحصول على تشغيل تلقائي موثوق، استخدم Windows Task Scheduler لتشغيل WSL + الـ gateway عند تسجيل الدخول:

      1. أنشئ مهمة تشغّل wsl -d Ubuntu -- bash -lc 'hermes gateway run'
      2. اضبطها لتُطلَق عند تسجيل دخول المستخدم

      macOS: الـ gateway لا يعثر على Node.js / ffmpeg / أدوات أخرى​

      السبب: ترث خدمات launchd قيمة PATH مصغّرة (/usr/bin:/bin:/usr/sbin:/sbin) لا تتضمن مجلدات Homebrew أو nvm أو cargo أو غيرها من مجلدات الأدوات التي يثبّتها المستخدم. وهذا يعطّل غالبًا جسر WhatsApp (node not found) أو تفريغ الصوت إلى نص (ffmpeg not found).

      الحل: يلتقط الـ gateway قيمة PATH من الـ shell لديك عند تشغيل hermes gateway install. إذا ثبّتَّ أدوات بعد إعداد الـ gateway، فأعد تشغيل أمر التثبيت لالتقاط قيمة PATH المحدَّثة:

      hermes gateway install    # Re-snapshots your current PATH
      hermes gateway start      # Detects the updated plist and reloads

      ويمكنك التحقق من أن ملف plist يحتوي على قيمة PATH الصحيحة:

      /usr/libexec/PlistBuddy -c "Print :EnvironmentVariables:PATH" \
        ~/Library/LaunchAgents/ai.hermes.gateway.plist

      مشكلات الأداء​

      بطء الاستجابات​

      السبب: نموذج كبير، أو خادم API بعيد، أو system prompt ثقيل يتضمن أدوات كثيرة.

      الحل:

      • جرّب نموذجًا أسرع/أصغر: hermes chat --model openrouter/meta-llama/llama-3.1-8b-instruct
      • قلّل عدد toolsets النشطة: hermes chat -t "terminal"
      • تحقق من زمن استجابة الشبكة (latency) بينك وبين المزوّد
      • بالنسبة إلى النماذج المحلية، تأكد من توفر ذاكرة GPU VRAM كافية

      ارتفاع استهلاك tokens​

      السبب: محادثات طويلة، أو system prompts مُسهبة، أو استدعاءات أدوات كثيرة تُراكم السياق.

      الحل:

      # See exactly what the fixed prompt costs — breakdown by block
      # (system prompt, skills index, memory, tool schemas). Runs offline.
      hermes prompt-size

      # Compress the conversation to reduce tokens
      /compress

      # Check session token usage
      /usage

      إذا بدا خط الأساس مرتفعًا قبل أن تكتب أي شيء، فهذه هي ميزانية الـ prompt الثابتة — أي system prompt مع مخططات الأدوات (tool schemas) التي تُرسَل مع كل استدعاء. نفّذ hermes prompt-size لقياسها، ثم قلّصها: عطّل toolsets التي لا تستخدمها (hermes tools)، وألغِ تثبيت المهارات التي لا تحتاج إليها أو عطّلها (hermes skills).

      نصيحة

      استخدم /compress بانتظام خلال الجلسات الطويلة. فهو يلخّص سجل المحادثة ويقلّل استهلاك tokens بشكل ملحوظ مع الحفاظ على السياق.

      الجلسة أصبحت طويلة جدًا​

      السبب: تتراكم الرسائل ومخرجات الأدوات في المحادثات الممتدة، مما يقرّبها من حدود السياق.

      الحل:

      # Compress current session (preserves key context)
      /compress

      # Start a new session with a reference to the old one
      hermes chat

      # Resume a specific session later if needed
      hermes chat --continue

      مشكلات MCP​

      تعذّر الاتصال بخادم MCP​

      السبب: لم يُعثر على الملف التنفيذي للخادم، أو مسار الأمر خاطئ، أو بيئة التشغيل (runtime) اللازمة مفقودة.

      الحل:

      # Ensure MCP dependencies are installed (already included in standard install)
      cd ~/.hermes/hermes-agent && uv pip install -e ".[mcp]"

      # For npm-based servers, ensure Node.js is available
      node --version
      npx --version

      # Test the server manually
      npx -y @modelcontextprotocol/server-filesystem /tmp

      تحقق من إعدادات MCP في ~/.hermes/config.yaml:

      mcp_servers:
        filesystem:
          command: "npx"
          args: ["-y", "@modelcontextprotocol/server-filesystem", "/home/user/docs"]

      الأدوات لا تظهر من خادم MCP​

      السبب: بدأ الخادم لكن فشل اكتشاف الأدوات، أو استُبعدت الأدوات بفعل الإعدادات، أو أن الخادم لا يدعم قدرة MCP التي توقعتها.

      الحل:

      • راجع سجلات الـ gateway/الوكيل بحثًا عن أخطاء اتصال MCP
      • تأكد من أن الخادم يستجيب لطريقة RPC المسماة tools/list
      • راجع أي إعدادات tools.include أو tools.exclude أو tools.resources أو tools.prompts أو enabled ضمن ذلك الخادم
      • تذكّر أن الأدوات المساعدة الخاصة بالموارد (resources) والـ prompts لا تُسجَّل إلا عندما تدعم الجلسة تلك القدرات فعليًا
      • استخدم /reload-mcp بعد تغيير الإعدادات
      # Verify MCP servers are configured
      hermes config show | grep -A 12 mcp_servers

      # Restart Hermes or reload MCP after config changes
      hermes chat

      راجع أيضًا:

      • MCP (Model Context Protocol)
      • استخدام MCP مع Hermes
      • مرجع إعدادات MCP

      أخطاء انتهاء المهلة في MCP​

      السبب: يستغرق خادم MCP وقتًا طويلًا جدًا للاستجابة، أو تعطّل أثناء التنفيذ.

      الحل:

      • زِد المهلة (timeout) في إعدادات خادم MCP إن كان ذلك مدعومًا
      • تحقق مما إذا كانت عملية خادم MCP لا تزال تعمل
      • بالنسبة إلى خوادم MCP البعيدة عبر HTTP، تحقق من الاتصال بالشبكة
      تحذير

      إذا تعطّل خادم MCP في منتصف طلب، فسيُبلغ Hermes عن انتهاء المهلة. راجع سجلات الخادم نفسه (وليس سجلات Hermes فقط) لتشخيص السبب الجذري.

      الملفات الشخصية (Profiles)​

      ما الفرق بين الـ profiles ومجرد ضبط HERMES_HOME؟​

      الـ profiles طبقة مُدارة فوق HERMES_HOME. يمكنك ضبط HERMES_HOME=/some/path يدويًا قبل كل أمر، لكن الـ profiles تتولى كل التفاصيل التأسيسية نيابةً عنك: إنشاء بنية المجلدات، وتوليد أسماء مستعارة (aliases) للـ shell (hermes-work)، وتتبّع الـ profile النشط في ~/.hermes/active_profile، ومزامنة تحديثات المهارات عبر جميع الـ profiles تلقائيًا. كما تتكامل مع الإكمال التلقائي بمفتاح Tab، فلا تحتاج إلى تذكّر المسارات.

      هل يمكن لاثنين من الـ profiles مشاركة token البوت نفسه؟​

      لا. تتطلب كل منصة مراسلة (Telegram و Discord وغيرهما) وصولًا حصريًا إلى token البوت. إذا حاول اثنان من الـ profiles استخدام الـ token نفسه في الوقت ذاته، فسيفشل الـ gateway الثاني في الاتصال. أنشئ بوتًا منفصلًا لكل profile — وبالنسبة إلى Telegram، تحدّث إلى @BotFather لإنشاء بوتات إضافية.

      هل تتشارك الـ profiles الذاكرة أو الجلسات؟​

      لا. لكل profile مخزن ذاكرة خاص به، وقاعدة بيانات للجلسات، ومجلد للمهارات، فهي معزولة تمامًا. إذا أردت بدء profile جديد بالذكريات والجلسات الموجودة، فاستخدم hermes profile create newname --clone-all لنسخ كل شيء من الـ profile الحالي، أو أضف --clone-from <profile> للنسخ من profile مصدر محدد.

      وهذا العزل هو أيضًا سبب عدم تشغيل وكيلين أبدًا على الـ profile نفسه أو مجلد Hermes الرئيسي نفسه: فكلاهما يكتب في الذاكرة تلقائيًا، ويحمّل كلٌّ منهما ما كتبه الآخر عند بدء الجلسة، فتتدهور الحالة المخزّنة لديهما مع كل جلسة. وكيل واحد لكل profile؛ وإذا أردت ذاكرة مشتركة فعلًا بين الوكلاء، فاستخدم مزوّد ذاكرة خارجيًا.

      ماذا يحدث عند تشغيل hermes update؟​

      يسحب hermes update أحدث إصدار من الكود ويعيد تثبيت الاعتماديات مرة واحدة (وليس لكل profile)، ثم يزامن المهارات المحدَّثة مع جميع الـ profiles تلقائيًا. لا تحتاج إلى تشغيل hermes update إلا مرة واحدة — فهو يشمل كل profile على الجهاز.

      كم عدد الـ profiles التي يمكنني تشغيلها؟​

      لا يوجد حدّ صارم. فكل profile ما هو إلا مجلد ضمن ~/.hermes/profiles/. ويعتمد الحدّ العملي على مساحة القرص لديك وعلى عدد الـ gateways المتزامنة التي يستطيع نظامك التعامل معها (كل gateway عبارة عن عملية Python خفيفة). لا بأس بتشغيل عشرات الـ profiles؛ فالـ profile الخامل لا يستهلك أي موارد.

      سير العمل والأنماط​

      استخدام نماذج مختلفة لمهام مختلفة (سير عمل متعدد النماذج)​

      السيناريو: تستخدم GPT-5.4 كنموذجك اليومي، لكن Gemini أو Grok يكتب محتوى أفضل لوسائل التواصل الاجتماعي. التبديل اليدوي بين النماذج في كل مرة أمر مُتعب.

      الحل: إعدادات التفويض (Delegation config). يمكن لـ Hermes توجيه subagents إلى نموذج مختلف تلقائيًا. اضبط هذا في ~/.hermes/config.yaml:

      delegation:
        model: "google/gemini-3-flash-preview"   # subagents use this model
        provider: "openrouter"                    # provider for subagents

      الآن عندما تخبر Hermes «اكتب لي خيطًا على Twitter عن X» ويُنشئ subagent عبر delegate_task، يعمل ذلك الـ subagent على Gemini بدلًا من نموذجك الرئيسي. تبقى محادثتك الأساسية على GPT-5.4.

      يمكنك أيضًا أن تكون صريحًا في موجّهك: «فوّض مهمة لكتابة منشورات لوسائل التواصل الاجتماعي عن إطلاق منتجنا. استخدم subagent الخاص بك للكتابة الفعلية.» سيستخدم الوكيل delegate_task، والتي تلتقط تلقائيًا إعدادات التفويض.

      للتبديل لمرة واحدة بين النماذج بدون تفويض، استخدم /model في CLI:

      /model google/gemini-3-flash-preview    # switch for this session
      # ... write your content ...
      /model openai/gpt-5.4                   # switch back
      تحذير

      يعيد كل تبديل عبر /model ضبط ذاكرة الـ prompt المؤقتة (prompt cache) — إذ يتضمن مفتاح التخزين المؤقت النموذجَ نفسه، لذا تعيد أول رسالة بعد كل تبديل قراءة المحادثة كاملة بسعر الإدخال الكامل. في الجلسات الطويلة، يُفضَّل استخدام التفويض (تحصل subagents على سياق جديد خاص بها) أو جلسة جديدة بدلًا من التبديل المتكرر ذهابًا وإيابًا.

      راجع تفويض المهام إلى Subagents لمزيد حول آلية عمل التفويض.

      تشغيل عدة وكلاء على رقم WhatsApp واحد (ربط حسب المحادثة)​

      السيناريو: في OpenClaw، كان لديك عدة وكلاء مستقلين مرتبطين بمحادثات WhatsApp محددة — واحد لمجموعة قائمة تسوق العائلة، وآخر لمحادثتك الخاصة. هل يستطيع Hermes فعل ذلك؟

      القيد الحالي: يحتاج كل profile من profiles Hermes إلى رقم/جلسة WhatsApp خاصة به. لا يمكنك ربط عدة profiles بمحادثات مختلفة على نفس رقم WhatsApp — إذ يستخدم جسر WhatsApp (Baileys) جلسة مصادَق عليها واحدة لكل رقم.

      الحلول البديلة:

      1. استخدم profile واحد مع تبديل الشخصية. أنشئ ملفات سياق AGENTS.md مختلفة أو استخدم أمر /personality لتغيير السلوك حسب المحادثة. يرى الوكيل في أي محادثة هو ويمكنه التكيّف.

      2. استخدم مهام cron للمهام المتخصصة. بالنسبة لمتتبّع قائمة تسوق، أنشئ مهمة cron تراقب محادثة محددة وتدير القائمة — بلا حاجة لوكيل منفصل.

      3. استخدم أرقامًا منفصلة. إذا احتجت وكلاء مستقلين حقًا، اربط كل profile برقم WhatsApp خاص به. تعمل الأرقام الافتراضية من خدمات مثل Google Voice لهذا الغرض.

      4. استخدم Telegram أو Discord بدلًا من ذلك. تدعم هاتان المنصتان الربط حسب المحادثة بشكل أكثر طبيعية — تحصل كل مجموعة Telegram أو قناة Discord على جلستها الخاصة، ويمكنك تشغيل عدة رموز بوت (واحد لكل profile) على نفس الحساب.

      راجع Profiles وإعداد WhatsApp لمزيد من التفاصيل.

      التحكم فيما يظهر على Telegram (إخفاء السجلات والتفكير)​

      السيناريو: ترى سجلات تنفيذ الـ gateway، وتفكير Hermes، وتفاصيل استدعاءات الأدوات على Telegram بدلًا من المخرجات النهائية فقط.

      الحل: يتحكم إعداد display.tool_progress في config.yaml في مقدار نشاط الأدوات المعروض:

      display:
        tool_progress: "off"   # options: off, new, all, verbose
      • off — الاستجابة النهائية فقط. بلا استدعاءات أدوات، ولا تفكير، ولا سجلات.
      • new — يعرض استدعاءات الأدوات الجديدة أثناء حدوثها (أسطر موجزة).
      • all — يعرض كل نشاط الأدوات بما في ذلك النتائج.
      • verbose — تفاصيل كاملة تشمل معاملات الأدوات ومخرجاتها.

      لمنصات المراسلة، عادة ما تريد off أو new. بعد تحرير config.yaml، أعد تشغيل الـ gateway ليسري التغيير.

      يمكنك أيضًا تبديل هذا لكل جلسة عبر أمر /verbose (إن كان مفعّلًا):

      display:
        tool_progress_command: true   # enables /verbose in the gateway

      إدارة المهارات على Telegram (حدّ slash commands)​

      السيناريو: يفرض Telegram حدًا أقصى قدره 100 slash command، ومهاراتك تتجاوز هذا الحد. تريد تعطيل المهارات التي لا تحتاجها على Telegram، لكن إعدادات hermes skills config لا يبدو أنها تسري.

      الحل: استخدم hermes skills config لتعطيل المهارات لكل منصة على حدة. يكتب هذا إلى config.yaml:

      skills:
        disabled: []                    # globally disabled skills
        platform_disabled:
          telegram: [skill-a, skill-b]  # disabled only on telegram

      بعد تغيير هذا، أعد تشغيل الـ gateway (hermes gateway restart أو أوقفه وأعد تشغيله). تُعاد بناء قائمة أوامر بوت Telegram عند بدء التشغيل.

      نصيحة

      يتم اقتطاع المهارات ذات الأوصاف الطويلة جدًا إلى 40 حرفًا في قائمة Telegram للبقاء ضمن حدود حجم الحمولة. إذا لم تظهر المهارات، فقد تكون المشكلة في إجمالي حجم الحمولة أكثر منها في حدّ عدد الأوامر 100 — تعطيل المهارات غير المستخدَمة يساعد في كلتا الحالتين.

      جلسات محادثات مشتركة (عدة مستخدمين، محادثة واحدة)​

      السيناريو: لديك محادثة (thread) على Telegram أو Discord يذكر فيها عدة أشخاص البوت. تريد أن تكون كل الإشارات في تلك المحادثة جزءًا من محادثة واحدة مشتركة، وليس جلسات منفصلة لكل مستخدم.

      السلوك الحالي: ينشئ Hermes جلسات مرتبطة بمعرّف المستخدم في معظم المنصات، بحيث يحصل كل شخص على سياق محادثة خاص به. هذا مقصود من أجل الخصوصية وعزل السياق.

      الحلول البديلة:

      1. استخدم Slack. ترتبط جلسات Slack بالمحادثة (thread) وليس بالمستخدم. يشارك عدة مستخدمين في نفس المحادثة سياقًا واحدًا — وهو بالضبط السلوك الذي تصفه. هذا هو الأنسب طبيعيًا.

      2. استخدم محادثة جماعية مع مستخدم واحد. إذا كان شخص واحد هو «المشغّل» المعيَّن الذي يُوصِل الأسئلة، تبقى الجلسة موحّدة. يمكن للآخرين المتابعة قراءةً.

      3. استخدم قناة Discord. ترتبط جلسات Discord بالقناة، بحيث يشارك كل المستخدمين في نفس القناة السياق. استخدم قناة مخصصة للمحادثة المشتركة.

      تصدير Hermes إلى جهاز آخر​

      السيناريو: بنيتَ مهارات، ومهام cron، وذكريات على جهاز واحد وتريد نقل كل شيء إلى جهاز Linux جديد مخصص.

      الحل:

      1. ثبّت Hermes Agent على الجهاز الجديد:

        curl -fsSL https://hermes-agent.nousresearch.com/install.sh | bash

      2. على الجهاز المصدر، أنشئ نسخة احتياطية كاملة:

        hermes backup

        ينشئ هذا ملف zip لمجلد ~/.hermes/ بأكمله — الإعدادات، ومفاتيح API، والذكريات، والمهارات، والجلسات، والـ profiles — مُحفوظًا في مجلدك الرئيسي باسم ~/hermes-backup-<timestamp>.zip.

      3. انسخ ملف zip إلى الجهاز الجديد واستورده:

        # On the source machine
        scp ~/hermes-backup-<timestamp>.zip newmachine:~/

        # On the new machine
        hermes import ~/hermes-backup-<timestamp>.zip

      4. على الجهاز الجديد، شغّل hermes setup للتحقق من عمل مفاتيح API وإعدادات المزوّد.

      نقل profile واحد إلى جهاز آخر​

      السيناريو: تريد نقل أو مشاركة profile واحد محدد — وليس تثبيتك الكامل.

      # On the source machine
      hermes profile export work ./work-backup.tar.gz

      # Copy the file to the target machine, then:
      hermes profile import ./work-backup.tar.gz work

      سيحتوي الـ profile المستورَد على كل الإعدادات والذكريات والجلسات والمهارات من التصدير. قد تحتاج لتحديث المسارات أو إعادة المصادقة مع المزوّدين إذا كان للجهاز الجديد إعداد مختلف.

      hermes backup مقابل hermes profile export​

      الميزةhermes backuphermes profile export
      حالة الاستخدامترحيل الجهاز بالكاملنقل/مشاركة profile محدد
      النطاقعام (مجلد ~/.hermes بأكمله)محلي (مجلد profile واحد)
      يشملكل الـ profiles، والإعدادات العامة، ومفاتيح API، والجلساتprofile واحد: SOUL.md، والذكريات، والجلسات، والمهارات
      بيانات الاعتمادمشمولة (.env وauth.json)مُستبعدة (محذوفة للمشاركة الآمنة)

      الحل البديل اليدوي (rsync): إذا فضّلت نسخ الملفات مباشرة، استبعد مستودع الكود:

      rsync -av --exclude='hermes-agent' ~/.hermes/ newmachine:~/.hermes/
      نصيحة

      ينتج hermes backup لقطة متسقة حتى أثناء تشغيل Hermes فعليًا. يستبعد الأرشيف المُستعاد الملفات التشغيلية الخاصة بالجهاز مثل gateway.pid وcron.pid.

      رفض الإذن عند إعادة تحميل الـ shell بعد التثبيت​

      السيناريو: بعد تشغيل مثبّت Hermes، يعطي أمر source ~/.zshrc خطأ رفض الإذن.

      السبب: يحدث هذا عادة عندما يكون لملف ~/.zshrc (أو ~/.bashrc) صلاحيات ملف غير صحيحة، أو عندما لم يستطع المثبّت الكتابة إليه بسلاسة. إنها ليست مشكلة خاصة بـ Hermes — بل مشكلة صلاحيات في إعدادات الـ shell.

      الحل:

      # Check permissions
      ls -la ~/.zshrc

      # Fix if needed (should be -rw-r--r-- or 644)
      chmod 644 ~/.zshrc

      # Then reload
      source ~/.zshrc

      # Or just open a new terminal window — it picks up PATH changes automatically

      إذا أضاف المثبّت سطر PATH لكن الصلاحيات خاطئة، يمكنك إضافته يدويًا:

      echo 'export PATH="$HOME/.local/bin:$PATH"' >> ~/.zshrc

      خطأ 400 عند أول تشغيل للوكيل​

      السيناريو: يكتمل الإعداد بلا مشاكل، لكن أول محاولة محادثة تفشل بخطأ HTTP 400.

      السبب: عادة ما يكون عدم تطابق اسم النموذج — النموذج المضبوط غير موجود لدى مزوّدك، أو لا يملك مفتاح API صلاحية الوصول إليه.

      الحل:

      # Check what model and provider are configured
      hermes config show | head -20

      # Re-run model selection
      hermes model

      # Or test with a known-good model
      hermes chat -q "hello" --model anthropic/claude-opus-4.7

      إذا كنت تستخدم OpenRouter، تأكد من أن مفتاح API لديك يحتوي على رصيد. غالبًا ما يعني خطأ 400 من OpenRouter أن النموذج يتطلب خطة مدفوعة أو أن معرّف النموذج يحتوي على خطأ إملائي.

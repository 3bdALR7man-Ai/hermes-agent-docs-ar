      إعداد Nix و NixOS

      منصة من المستوى 2

      تُعد Nix و NixOS منصات من المستوى 2 (Tier 2). يُصان الـ flake ووحدة NixOS الموثّقان هنا بأفضل جهد فقط. وقد تؤدي عمليات commit إلى main إلى تعطيل هذه الحزم في أي وقت.

      للحصول على إعداد مدعوم، استخدم أحد مسارات التثبيت القياسية - إما Docker أو بيئة FHS.

      يوفّر Hermes Agent كلًّا من Nix flake، ووحدة NixOS، ووحدة Home Manager.

      المستوىلمن هوما تحصل عليه
      nix run / nix profile installأي مستخدم لـ Nix (macOS، Linux)ملف تنفيذي مبني مسبقًا مع جميع الاعتماديات — ثم تستخدم سير عمل CLI القياسي
      وحدة Home Managerوكيل لشخص واحد، على أي توزيعة أو على macOSإعدادات تصريحية (declarative) وخدمة على مستوى المستخدم، دون الحاجة إلى root
      وحدة NixOS (أصلية)عمليات النشر على خوادم NixOSإعدادات تصريحية، وخدمة systemd مُحصّنة، وأسرار مُدارة
      وحدة NixOS (حاوية)الوكلاء الذين يحتاجون إلى تعديل بيئتهم ذاتيًاكل ما سبق، إضافةً إلى حاوية Ubuntu دائمة يستطيع فيها الوكيل تنفيذ apt/pip/npm install
      ما الذي يختلف عن التثبيت القياسي

      يدير المُثبّت curl | bash كلًّا من Python و Node والاعتماديات بنفسه. أما Nix flake فيحلّ محل كل ذلك — فكل اعتمادية Python هي Nix derivation يبنيها uv2nix، وأدوات وقت التشغيل (Node.js و git و ripgrep و ffmpeg) مُضمَّنة في PATH الخاص بالملف التنفيذي. لا يوجد pip وقت التشغيل، ولا تفعيل لـ venv، ولا npm install.

      لمستخدمي غير NixOS، لا يتغير سوى خطوة التثبيت. فكل ما يليها (hermes setup، hermes gateway install، تعديل الإعدادات) يعمل تمامًا كما في التثبيت القياسي.

      لمستخدمي وحدة NixOS، تختلف دورة الحياة بأكملها: الإعدادات موجودة في configuration.nix، والأسرار تمر عبر sops-nix/agenix، والخدمة عبارة عن وحدة systemd، وأوامر الإعدادات في CLI محظورة. تدير hermes بالطريقة نفسها التي تدير بها أي خدمة NixOS أخرى.

      المتطلبات المسبقة​

      • Nix مع تفعيل flakes — يُوصى بـ Determinate Nix (يفعّل flakes افتراضيًا)
      • مفاتيح API للخدمات التي تريد استخدامها (على الأقل: مفتاح OpenRouter أو Anthropic)

      البدء السريع (لأي مستخدم Nix)​

      لا حاجة إلى الاستنساخ. يجلب Nix كل شيء ويبنيه ويشغّله:

      # Run the desktop app
      nix run github:NousResearch/hermes-agent#desktop

      # Or install persistently
      nix profile install github:NousResearch/hermes-agent#desktop

      # run the tui
      nix run github:NousResearch/hermes-agent -- setup
      nix run github:NousResearch/hermes-agent -- --tui

      # or install it in your profile
      nix profile install github:NousResearch/hermes-agent
      hermes setup
      hermes --tui

      بعد nix profile install، تصبح الأوامر hermes و hermes-agent و hermes-acp ضمن PATH. ومن هنا، يكون سير العمل مطابقًا لـ التثبيت القياسي — إذ يرشدك hermes setup خلال اختيار المزوّد، ويُعدّ hermes gateway install خدمة launchd (على macOS) أو خدمة systemd على مستوى المستخدم، وتوجد الإعدادات في ~/.hermes/.

      منصات المراسلة (Discord، Telegram، Slack)

      تتضمن الحزمة الافتراضية جميع المكتبات التي قد يحتاج إليها hermes-agent. إذا أردت نسخة أصغر، فاطّلع على مخرجات flake الأخرى.

      تضيف الحزمة default نحو 700 MB إلى الـ closure. أما إذا كنت تحتاج إلى منصات المراسلة فقط، فإن #messaging تضيف نحو 33 MB فقط.

      التشغيل من نسخة مستنسخة محليًا
      git clone https://github.com/NousResearch/hermes-agent.git
      cd hermes-agent
      nix develop
      hermes setup

      وحدة NixOS​

      يُصدِّر الـ flake الوحدة nixosModules.default — وهي وحدة خدمة NixOS كاملة تدير بشكل تصريحي إنشاء المستخدم، والمجلدات، وتوليد الإعدادات، والأسرار، والمستندات، ودورة حياة الخدمة.

      ملاحظة

      تحتاج هذه الوحدة إلى NixOS. إن Hermes وكيل لشخص واحد. إذا أردت وكيلًا لشخص واحد وليس خدمة نظام، فاستخدم وحدة Home Manager. تعمل تلك الوحدة على NixOS وعلى كل نظام آخر يدعمه Home Manager.

      أضف مُدخل الـ Flake​

      # /etc/nixos/flake.nix (or your system flake)
      {
        inputs = {
          nixpkgs.url = "github:NixOS/nixpkgs/nixos-unstable";
          hermes-agent.url = "github:NousResearch/hermes-agent";
        };

        outputs = { nixpkgs, hermes-agent, ... }: {
          nixosConfigurations.your-host = nixpkgs.lib.nixosSystem {
            system = "x86_64-linux";
            modules = [
              hermes-agent.nixosModules.default
              ./configuration.nix
            ];
          };
        };
      }

      الإعدادات الدنيا​

      # configuration.nix
      { config, ... }: {
        services.hermes-agent = {
          enable = true;
          settings.model.default = "anthropic/claude-sonnet-4";
          environmentFiles = [ config.sops.secrets."hermes-env".path ];
          addToSystemPackages = true;
        };
      }

      هذا كل شيء. ينشئ nixos-rebuild switch المستخدم hermes، ويولّد config.yaml، ويربط الأسرار، ويشغّل الـ gateway — وهي خدمة طويلة التشغيل تربط الوكيل بمنصات المراسلة (Telegram و Discord وغيرها) وتستمع للرسائل الواردة.

      الأسرار مطلوبة

      يفترض سطر environmentFiles أعلاه أنك قد أعددت sops-nix أو agenix. يجب أن يحتوي الملف على مفتاح واحد على الأقل لمزوّد LLM (مثل OPENROUTER_API_KEY=sk-or-...). راجع إدارة الأسرار للإعداد الكامل. إذا لم يكن لديك مدير أسرار بعد، فيمكنك استخدام ملف عادي كنقطة بداية — فقط تأكد من أنه غير قابل للقراءة من قِبل الجميع:

      echo "OPENROUTER_API_KEY=sk-or-your-key" | sudo install -m 0600 -o hermes /dev/stdin /var/lib/hermes/env
      services.hermes-agent.environmentFiles = [ "/var/lib/hermes/env" ];
      addToSystemPackages

      يؤدي ضبط addToSystemPackages = true إلى أمرين: يضع hermes CLI ضمن PATH الخاص بالنظام و يضبط HERMES_HOME على مستوى النظام بحيث تتشارك واجهة CLI التفاعلية الحالة (الجلسات، والمهارات، و cron) مع خدمة gateway. ومن دونه، يؤدي تشغيل hermes في الـ shell إلى إنشاء مجلد ~/.hermes/ منفصل.

      CLI مُدرِك للحاوية​

      معلومة

      عندما يكون container.enable = true و addToSystemPackages = true، يُوجَّه كل أمر hermes على المضيف تلقائيًا إلى داخل الحاوية المُدارة. وهذا يعني أن جلسة CLI التفاعلية تعمل داخل البيئة نفسها التي تعمل فيها خدمة gateway — مع إمكانية الوصول إلى جميع الحزم والأدوات المثبّتة في الحاوية.

      • التوجيه شفاف: فالأوامر hermes chat و hermes sessions list و hermes --version وغيرها تُنفَّذ جميعها داخل الحاوية خلف الكواليس
      • تُمرَّر جميع خيارات CLI كما هي
      • إذا لم تكن الحاوية قيد التشغيل، يعيد CLI المحاولة لفترة قصيرة (5 ثوانٍ مع مؤشر دوّار في الاستخدام التفاعلي، و 10 ثوانٍ بصمت في السكربتات) ثم يفشل برسالة خطأ واضحة — دون أي بديل احتياطي صامت
      • للمطورين الذين يعملون على قاعدة كود hermes، اضبط HERMES_DEV=1 لتجاوز التوجيه إلى الحاوية وتشغيل النسخة المحلية مباشرةً

      اضبط container.hostUsers لإنشاء رابط رمزي ~/.hermes يشير إلى مجلد حالة الخدمة، بحيث يتشارك CLI على المضيف والحاوية الجلسات والإعدادات والذكريات:

      services.hermes-agent = {
        container.enable = true;
        container.hostUsers = [ "your-username" ];
        addToSystemPackages = true;
      };

      يُضاف المستخدمون المدرجون في hostUsers تلقائيًا إلى المجموعة hermes للحصول على صلاحيات الوصول إلى الملفات.

      مستخدمو Podman: تشغّل خدمة NixOS الحاوية بصلاحيات root. يحصل مستخدمو Docker على الوصول عبر socket المجموعة docker، لكن حاويات Podman التي تعمل بصلاحيات root تتطلب sudo. امنح صلاحية sudo دون كلمة مرور لبيئة تشغيل الحاويات لديك:

      security.sudo.extraRules = [{
        users = [ "your-username" ];
        commands = [{
          command = "/run/current-system/sw/bin/podman";
          options = [ "NOPASSWD" ];
        }];
      }];

      يكتشف CLI تلقائيًا متى يلزم sudo ويستخدمه بشكل شفاف. ومن دون ذلك، ستحتاج إلى تشغيل sudo hermes chat يدويًا.

      تحقّق من أنه يعمل​

      بعد nixos-rebuild switch، تحقق من أن الخدمة قيد التشغيل:

      # Check service status
      systemctl status hermes-agent

      # Watch logs (Ctrl+C to stop)
      journalctl -u hermes-agent -f

      # If addToSystemPackages is true, test the CLI
      hermes --version
      hermes config       # shows the generated config

      اختيار وضع النشر​

      تدعم الوحدة وضعين، يتحكم فيهما container.enable:

      أصلي (Native) (افتراضي)حاوية (Container)
      طريقة التشغيلخدمة systemd مُحصّنة على المضيفحاوية Ubuntu دائمة مع ربط /nix/store عبر bind-mount
      الأمانNoNewPrivileges، ProtectSystem=strict، PrivateTmpعزل الحاوية، ويعمل بمستخدم غير ذي امتيازات داخلها
      هل يستطيع الوكيل تثبيت الحزم بنفسهلا — فقط الأدوات الموجودة في PATH الذي يوفّره Nixنعم — تبقى عمليات تثبيت apt و pip و npm بعد إعادة التشغيل
      واجهة الإعداداتنفسهانفسها
      متى تختارهعمليات النشر القياسية، وأقصى درجات الأمان، وقابلية إعادة الإنتاجعندما يحتاج الوكيل إلى تثبيت الحزم وقت التشغيل، أو بيئة قابلة للتعديل، أو أدوات تجريبية

      لتفعيل وضع الحاوية، أضف سطرًا واحدًا:

      {
        services.hermes-agent = {
          enable = true;
          container.enable = true;
          # ... rest of config is identical
        };
      }
      معلومة

      يفعّل وضع الحاوية تلقائيًا virtualisation.docker.enable عبر mkDefault. إذا كنت تستخدم Podman بدلًا من ذلك، فاضبط container.backend = "podman" و virtualisation.docker.enable = false.

      الإعدادات​

      الإعدادات التصريحية​

      يقبل الخيار settings مجموعة سمات (attrset) عشوائية تُحوَّل إلى config.yaml. ويدعم الدمج العميق عبر تعريفات وحدات متعددة (من خلال lib.recursiveUpdate)، لذا يمكنك تقسيم الإعدادات على عدة ملفات:

      # base.nix
      services.hermes-agent.settings = {
        model.default = "anthropic/claude-sonnet-4";
        toolsets = [ "all" ];
        terminal = { backend = "local"; timeout = 180; };
      };

      # personality.nix
      services.hermes-agent.settings = {
        display = { compact = false; personality = "kawaii"; };
        memory = { memory_enabled = true; user_profile_enabled = true; };
      };

      يُدمج كلاهما دمجًا عميقًا وقت التقييم. تتغلب المفاتيح المُعرَّفة في Nix دائمًا على المفاتيح الموجودة في ملف config.yaml الحالي على القرص، لكن المفاتيح التي يضيفها المستخدم ولا يمسّها Nix تبقى محفوظة. وهذا يعني أنه إذا أضاف الوكيل أو تعديل يدوي مفاتيح مثل skills.disabled أو streaming.enabled، فإنها تبقى بعد nixos-rebuild switch.

      تسمية النماذج

      يستخدم settings.model.default معرّف النموذج الذي يتوقعه المزوّد. مع OpenRouter (الافتراضي)، تبدو المعرّفات مثل "anthropic/claude-sonnet-4" أو "google/gemini-3-flash". إذا كنت تستخدم مزوّدًا مباشرةً (Anthropic، OpenAI)، فاضبط settings.model.base_url ليشير إلى API الخاص به، واستخدم معرّفات النماذج الأصلية لديه (مثل "claude-sonnet-4-20250514"). وعندما لا يكون base_url مضبوطًا، يستخدم Hermes مزوّد OpenRouter افتراضيًا.

      اكتشاف مفاتيح الإعدادات المتاحة

      نفّذ nix build .#configKeys && cat result لعرض كل مفتاح إعدادات نهائي مُستخرج من DEFAULT_CONFIG في Python. يمكنك لصق ملف config.yaml الحالي داخل الـ attrset الخاص بـ settings — فالبنية متطابقة بنسبة 1:1.

      مثال كامل: جميع الإعدادات الشائع تخصيصها
      { config, ... }: {
        services.hermes-agent = {
          enable = true;
          container.enable = true;

          # ── Model ──────────────────────────────────────────────────────────
          settings = {
            model = {
              base_url = "https://openrouter.ai/api/v1";
              default = "anthropic/claude-opus-4.6";
            };
            toolsets = [ "all" ];
            max_turns = 100;
            terminal = { backend = "local"; cwd = "."; timeout = 180; };
            compression = {
              enabled = true;
              threshold = 0.85;
              summary_model = "google/gemini-3-flash-preview";
            };
            memory = { memory_enabled = true; user_profile_enabled = true; };
            display = { compact = false; personality = "kawaii"; };
            agent = { max_turns = 60; verbose = false; };
          };

          # ── Secrets ────────────────────────────────────────────────────────
          environmentFiles = [ config.sops.secrets."hermes-env".path ];

          # ── Documents ──────────────────────────────────────────────────────
          # USER.md is memory, so it goes to HERMES_HOME. Workspace files use
          # `documents`, and that option needs an explicit `workingDirectory`.
          hermesHomeFiles = {
            "memories/USER.md" = ./documents/USER.md;
          };

          # ── MCP Servers ────────────────────────────────────────────────────
          mcpServers.filesystem = {
            command = "npx";
            args = [ "-y" "@modelcontextprotocol/server-filesystem" "/data/workspace" ];
          };

          # ── Container options ──────────────────────────────────────────────
          container = {
            image = "ubuntu:24.04";
            backend = "docker";
            hostUsers = [ "your-username" ];
            extraVolumes = [ "/home/user/projects:/projects:rw" ];
            extraOptions = [ "--gpus" "all" ];
          };

          # ── Service tuning ─────────────────────────────────────────────────
          addToSystemPackages = true;
          extraArgs = [ "--verbose" ];
          restart = "always";
          restartSec = 5;
        };
      }

      مخرج بديل: استخدم ملف إعداداتك الخاص​

      إذا كنت تفضّل إدارة config.yaml بالكامل خارج Nix، فاستخدم configFile:

      services.hermes-agent.configFile = /etc/hermes/config.yaml;

      يتجاوز هذا settings كليًا — لا دمج ولا توليد. يُنسخ الملف كما هو إلى $HERMES_HOME/config.yaml عند كل تفعيل.

      إدارة الأسرار​

      لا تضع مفاتيح API أبدًا في settings أو environment

      تنتهي القيم الموجودة في تعبيرات Nix داخل /nix/store، وهو قابل للقراءة من قِبل الجميع. استخدم دائمًا environmentFiles مع مدير أسرار.

      يُدمج كل من environment (متغيرات غير سرية) و environmentFiles (ملفات سرية) في $HERMES_HOME/.env وقت التفعيل (nixos-rebuild switch). يقرأ Hermes هذا الملف عند كل بدء تشغيل، لذا تسري التغييرات بتنفيذ systemctl restart hermes-agent — دون الحاجة إلى إعادة إنشاء الحاوية.

      {

      OAuth / التزويد المسبق ببيانات المصادقة​

      للمنصات التي تتطلب OAuth (مثل Discord)، استخدم authFile لتزويد بيانات الاعتماد مسبقًا عند أول نشر:

      {
        services.hermes-agent = {
          authFile = config.sops.secrets."hermes/auth.json".path;

      لا يُنسخ الملف إلا إذا لم يكن auth.json موجودًا بالفعل (ما لم يكن authFileForceOverwrite = true). أما تحديثات OAuth token وقت التشغيل فتُكتب في مجلد الحالة وتبقى محفوظة عبر عمليات إعادة البناء.

      المستندات​

      يقرأ Hermes الملفات من مجلدين، ولذلك يوجد خياران. استخدم الخيار الخاص بالمجلد الذي يجب أن يوضع فيه الملف.

      يثبّت documents الملفات في مجلد العمل الخاص بالوكيل، وهو workingDirectory. ويقرأ الوكيل سياق مشروعه من مساحة العمل تلك:

      {
        services.hermes-agent = {
          # documents needs this option. Read the note below.
          workingDirectory = "/var/lib/hermes/workspace";
          documents = {
            "AGENTS.md" = ./documents/AGENTS.md;   # path reference, copied from Nix store
            "notes/oncall.md" = "Page #infra before restarting anything.";
          };
        };
      }
      يحتاج documents إلى workingDirectory صريح

      ترفض الوحدة documents إلى أن تضبط workingDirectory. تختلف القيمة الافتراضية لهذا الخيار في كل وحدة: فهي مجلد home الخاص بك في Home Manager، و ${stateDir}/workspace في NixOS. ولذلك فإن ترك القيمة الافتراضية دون ضبط يضع الملفات في مجلد لم تختره أنت. أما اختيار مجلد له المسار نفسه للقيمة الافتراضية فهو اختيار صحيح، ويستوفي القاعدة.

      يثبّت hermesHomeFiles الملفات في HERMES_HOME. يقرأ Hermes ملف الهوية وملفات الذاكرة الخاصة بالوكيل من ذلك المجلد. لا يعمل SOUL.md و memories/ إلا من هناك. أما وضع SOUL.md في documents فينشئ ملفًا في مساحة العمل، ولا يحمّل Hermes ذلك الملف كهوية:

      {
        services.hermes-agent.hermesHomeFiles = {
          "SOUL.md" = "You are a helpful AI assistant.";
          "memories/USER.md" = ./documents/USER.md;
        };
      }

      كل قيمة إما نص (string) أو مسار. يمكن أن يحتوي المفتاح في أي من الخيارين على مجلدات فرعية، وتنشئ الوحدة المجلدات الأم. ويعيد كل تفعيل تثبيت الملفات من جديد.

      لا يحتاج hermesHomeFiles إلى workingDirectory، لأن الوحدة تملك المجلد HERMES_HOME. ومعظم المستخدمين يحتاجون إلى hermesHomeFiles.

      خوادم MCP​

      يضبط الخيار mcpServers بشكل تصريحي خوادم MCP (Model Context Protocol). يستخدم كل خادم إما وسيلة النقل stdio (أمر محلي) أو HTTP (عنوان URL بعيد).

      النقل عبر Stdio (خوادم محلية)​

      {
        services.hermes-agent.mcpServers = {
          filesystem = {
            command = "npx";
            args = [ "-y" "@modelcontextprotocol/server-filesystem" "/data/workspace" ];
          };
          github = {
            command = "npx";
            args = [ "-y" "@modelcontextprotocol/server-github" ];
            env.GITHUB_PERSONAL_ACCESS_TOKEN = "\${GITHUB_TOKEN}"; # resolved from .env
          };
        };
      }
      نصيحة

      تُستبدل متغيرات البيئة الواردة في قيم env من $HERMES_HOME/.env وقت التشغيل. استخدم environmentFiles لحقن الأسرار — ولا تضع tokens مباشرةً في إعدادات Nix أبدًا.

      النقل عبر HTTP (خوادم بعيدة)​

      {
        services.hermes-agent.mcpServers.remote-api = {
          url = "https://mcp.example.com/v1/mcp";
          headers.Authorization = "Bearer \${MCP_REMOTE_API_KEY}";
          timeout = 180;
        };
      }

      النقل عبر HTTP مع OAuth​

      اضبط auth = "oauth" للخوادم التي تستخدم OAuth 2.1. ينفّذ Hermes تدفق PKCE الكامل — اكتشاف البيانات الوصفية (metadata)، والتسجيل الديناميكي للعميل، وتبادل token، والتحديث التلقائي.

      {
        services.hermes-agent.mcpServers.my-oauth-server = {
          url = "https://mcp.example.com/mcp";
          auth = "oauth";
        };
      }

      تُخزَّن tokens في $HERMES_HOME/mcp-tokens/<server-name>.json وتبقى محفوظة بعد إعادة التشغيل وإعادة البناء.

      تفويض OAuth الأولي على الخوادم التي تعمل دون واجهة (headless)

      يتطلب تفويض OAuth الأول تدفق موافقة عبر المتصفح. في عمليات النشر دون واجهة، يطبع Hermes عنوان URL الخاص بالتفويض في stdout/السجلات بدلًا من فتح متصفح.

      الخيار A: التهيئة التفاعلية — شغّل التدفق مرة واحدة عبر docker exec (الحاوية) أو sudo -u hermes (الأصلي):

      # Container mode
      docker exec -it hermes-agent \
        hermes mcp add my-oauth-server --url https://mcp.example.com/mcp --auth oauth

      # Native mode
      sudo -u hermes HERMES_HOME=/var/lib/hermes/.hermes \
        hermes mcp add my-oauth-server --url https://mcp.example.com/mcp --auth oauth

      تستخدم الحاوية --network=host، لذا يمكن الوصول إلى مستمع OAuth callback على 127.0.0.1 من متصفح المضيف.

      الخيار B: تزويد tokens مسبقًا — أكمل التدفق على جهاز عمل، ثم انسخ tokens:

      hermes mcp add my-oauth-server --url https://mcp.example.com/mcp --auth oauth
      scp ~/.hermes/mcp-tokens/my-oauth-server{,.client}.json \
          server:/var/lib/hermes/.hermes/mcp-tokens/
      # Ensure: chown hermes:hermes, chmod 0600

      عند تشغيل hermes عبر وحدة NixOS، تكون أوامر CLI التالية محظورة، مع رسالة خطأ وصفية توجّهك إلى configuration.nix:

      hermes config editتُولَّد الإعدادات من settings
      hermes config set <key> <value>تُولَّد الإعدادات من settings
      hermes gateway installتتولى NixOS إدارة خدمة systemd
      hermes gateway uninstallتتولى NixOS إدارة خدمة systemd

      يمنع ذلك الانحراف بين ما يعرّفه Nix وما هو موجود على القرص. ويعتمد الاكتشاف على إشارتين:

      1. متغير البيئة HERMES_MANAGED. تضبطه الخدمة، وتقرؤه عملية gateway.
      2. ملف العلامة .managed في HERMES_HOME. يكتبه سكربت التفعيل، ويقرؤه الـ shell التفاعلي. ولذلك يحظر CLI أيضًا أوامر مثل docker exec -it hermes-agent hermes config set ....

      تحمل كلتا الإشارتين اسم النظام الذي يدير التثبيت، ولذلك تذكر رسالة الرفض أمر إعادة البناء الصحيح: فوحدة NixOS تعطي sudo nixos-rebuild switch، ووحدة Home Manager تعطي home-manager switch.

      وحدة Home Manager​

      يُصدِّر الـ flake أيضًا homeManagerModules.default. إن Hermes وكيل لشخص واحد؛ فبيانات الاعتماد والذاكرة والجلسات ومهام cron كلها تخص ذلك الشخص. ولذلك فإن خدمة على مستوى المستخدم هي الشكل الصحيح على الجهاز الشخصي. وهي تعمل على كل توزيعة يدعمها Home Manager، وليس على NixOS فقط.

      مجموعة الخيارات هي نفسها التي تستخدمها وحدة NixOS، أي services.hermes-agent، مع الخيارات نفسها settings و environmentFiles و documents و mcpServers و extraPlugins و backend. ويعمل كل مثال مما سبق هنا دون تغيير، ولا يختلف سوى الأجزاء الضرورية:

      وحدة NixOSوحدة Home Manager

      ثم استورد الوحدة في إعدادات Home Manager. يمكن أن تكون الإعدادات مستقلة، ويمكن أيضًا أن تكون ضمن home-manager.users.<name> في إعدادات NixOS أو nix-darwin:

      {

        services.hermes-agent = {
          enable = true;
          gateway.enable = true;
          settings.model.default = "anthropic/claude-sonnet-4";

      ينشئ home-manager switch المجلد ~/.hermes، ويكتب config.yaml، ويبني .env، ويشغّل الـ gateway كخدمة على مستوى المستخدم.

      فعّل linger، وإلا ستتوقف الخدمة عند تسجيل الخروج

      تنبيه: فعّل linger لحسابك. من دون linger، يوقف systemd مدير المستخدم (user manager) عند انتهاء آخر جلسة لك، وتتوقف الـ gateway معه. لا يستطيع Home Manager ضبط linger، لأن linger خاصية من خصائص الحساب:

      # NixOS
      users.users.your-username.linger = true;
      # anywhere else
      sudo loginctl enable-linger your-username

      لا يوجد خيار مكافئ على macOS؛ إذ يبدأ وكيل launchd المزوّد بـ RunAtLoad عند تسجيل الدخول ويستمر في العمل.

      تشغيل الواجهة الخلفية لـ Desktop / لوحة التحكم​

      يشغّل gateway.enable الـ messaging gateway لـ Telegram و Discord و Slack والمنصات الأخرى. أما Hermes Desktop ولوحة التحكم على الويب فيتصلان بعملية مختلفة، هي hermes serve أو hermes dashboard. ويشغّل backend.mode تلك العملية إلى جانب الـ gateway:

      {
        services.hermes-agent = {
          enable = true;
          gateway.enable = true;      # messaging platforms
          backend.mode = "dashboard"; # + the browser dashboard on 127.0.0.1:9119
          backend.port = 9119;
        };
      }

      يعمل serve دون واجهة مستخدم. فهو يوفّر الـ sockets /api/ws و /api/pty التي يتصل بها Hermes Desktop، ولا يبني تطبيق الويب. أما dashboard فيوفّر كل ذلك، ويقدّم أيضًا لوحة الإدارة في المتصفح. تستخدم كلتا العمليتين HERMES_HOME واحدًا مشتركًا مع الـ gateway، ولذلك تكون الجلسات والمهارات والذاكرة ومهام cron هي نفسها للجميع. ويعمل backend.mode بالطريقة نفسها في وحدة NixOS، لكن ليس في وضع الحاوية.

      الربط بعنوان غير عنوان loopback

      العنوان الافتراضي هو 127.0.0.1. وأي عنوان آخر يفعّل بوابة المصادقة الخاصة بلوحة التحكم. كما يرفض الخادم أي طلب يحمل ترويسة Host تختلف عن العنوان الذي رُبط به الخادم، وذلك للحماية من هجمات DNS rebinding. اربط الخادم بالاسم أو العنوان الذي يستخدمه عميلك.

      بنية الحاوية​

      معلومة

      لا يخصّ هذا القسم إلا من يستخدم container.enable = true. تخطَّه في عمليات النشر بالوضع الأصلي.

      عند تفعيل وضع الحاوية، يعمل hermes داخل حاوية Ubuntu دائمة، مع ربط الملف التنفيذي المبني بواسطة Nix من المضيف عبر bind-mount للقراءة فقط:

      Host                                    Container
      ────                                    ─────────
      /nix/store/...-hermes-agent-0.1.0  ──►  /nix/store/... (ro)
      ~/.hermes -> /var/lib/hermes/.hermes       (symlink bridge, per hostUsers)
      /var/lib/hermes/                    ──►  /data/          (rw)
        ├── current-package -> /nix/store/...    (symlink, updated each rebuild)
        ├── .gc-root -> /nix/store/...           (prevents nix-collect-garbage)
        ├── .container-identity                  (sha256 hash, triggers recreation)
        ├── .hermes/                             (HERMES_HOME)
        │   ├── .env                             (merged from environment + environmentFiles)
        │   ├── config.yaml                      (Nix-generated, deep-merged by activation)
        │   ├── .managed                         (marker file)
        │   ├── .container-mode                  (routing metadata: backend, exec_user, etc.)
        │   ├── state.db, sessions/, memories/   (runtime state)
        │   └── mcp-tokens/                      (OAuth tokens for MCP servers)
        ├── home/                                ──►  /home/hermes    (rw)
        └── workspace/                           (agent working directory)
            ├── AGENTS.md                        (from the documents option)
            └── (agent-created files)

      Container writable layer (apt/pip/npm):   /usr, /usr/local, /tmp

      يعمل الملف التنفيذي المبني بواسطة Nix داخل حاوية Ubuntu لأن /nix/store مربوط عبر bind-mount — فهو يجلب معه المفسّر الخاص به وجميع الاعتماديات، لذا لا يعتمد على مكتبات النظام في الحاوية. تُحَلّ نقطة الدخول (entrypoint) للحاوية عبر الرابط الرمزي current-package: /data/current-package/bin/hermes gateway run --replace. وعند تنفيذ nixos-rebuild switch، يُحدَّث الرابط الرمزي فقط — وتستمر الحاوية في العمل.

      فقدان الطبقة القابلة للكتابة

      عندما يتغير hash الهوية (ترقية الصورة، أو وحدات تخزين جديدة، أو خيارات حاوية جديدة)، تُحذف الحاوية ويُعاد إنشاؤها من نسخة جديدة مسحوبة من container.image. وتُفقد أي حزم مثبّتة عبر apt install أو pip install أو npm install في الطبقة القابلة للكتابة. أما الحالة في /data و /home/hermes فتبقى محفوظة (لأنها مربوطة عبر bind mount).

      إذا كان الوكيل يعتمد على حزم معيّنة، ففكّر في تضمينها داخل صورة مخصصة (container.image = "my-registry/hermes-base:latest") أو في كتابة سكربت لتثبيتها ضمن ملف SOUL.md الخاص بالوكيل.

      حماية GC Root​

      ينشئ سكربت preStart جذر GC (GC root) في ${stateDir}/.gc-root يشير إلى حزمة hermes الحالية. يمنع ذلك nix-collect-garbage من حذف الملف التنفيذي قيد التشغيل. وإذا تعطّل الـ GC root لسبب ما، فإن إعادة تشغيل الخدمة تعيد إنشاءه.

      الإضافات (Plugins)​

      تدعم وحدة NixOS تثبيت الإضافات بشكل تصريحي — دون الحاجة إلى الأمر الإجرائي hermes plugins install.

      إضافات المجلدات (extraPlugins)​

      للإضافات التي هي مجرد شجرة مصدر تحتوي على plugin.yaml + __init__.py (مثل hermes-lcm):

      services.hermes-agent.extraPlugins = [
        (pkgs.fetchFromGitHub {
          owner = "stephenschoettler";
          repo = "hermes-lcm";
          rev = "v0.7.0";
          hash = "sha256-...";
        })
      ];

      تُربط الإضافات رمزيًا داخل $HERMES_HOME/plugins/ وقت التفعيل، ويكتشفها Hermes عبر الفحص العادي للمجلدات. وتؤدي إزالة إضافة من القائمة ثم تنفيذ nixos-rebuild switch إلى حذف الرابط الرمزي.

      إضافات Entry-Point (extraPythonPackages)​

      للإضافات المُحزَّمة عبر pip والتي تسجّل نفسها من خلال [project.entry-points."hermes_agent.plugins"] (مثل rtk-hermes):

      services.hermes-agent.extraPythonPackages = [
        (pkgs.python312Packages.buildPythonPackage {

      مجموعات الاعتماديات الاختيارية (extraDependencyGroups)​

      للإضافات الاختيارية (extras) المُعرَّفة في ملف pyproject.toml الخاص بـ hermes-agent، استخدم extraDependencyGroups لتضمينها في الـ venv المختوم وقت البناء. وهذا مطلوب لأي إضافة غير موجودة في المجموعة الافتراضية [all] — إذ لا يمكن على Nix التثبيت وقت التشغيل داخل الـ store المخصص للقراءة فقط.

      # Enable Discord, Telegram, Slack
      services.hermes-agent.extraDependencyGroups = [ "messaging" ];
      # Enable a memory provider
      services.hermes-agent = {
        extraDependencyGroups = [ "hindsight" ];
        settings.memory.provider = "hindsight";
      };

      يحلّ uv هذه المجموعات إلى جانب الاعتماديات الأساسية — دون تعديل PYTHONPATH، ودون خطر التعارض. المجموعات المتاحة:

      فحوصات الـ Flake​

      يتضمن الـ flake عمليات تحقق وقت البناء تعمل في CI ومحليًا:

      # Run all checks
      nix flake check

      # Individual checks
      nix build .#checks.x86_64-linux.package-contents   # binaries exist + version
      nix build .#checks.x86_64-linux.entry-points-sync  # pyproject.toml ↔ Nix package sync

      programs.hermes-agent (Home Manager فقط)​

      يفصل Home Manager بين "ثبّت هذا التطبيق لي" و"شغّل هذا الـ daemon". يحتفظ services.hermes-agent بالحالة والإعدادات والـ daemons. أما programs.hermes-agent فيثبّت ما تستخدمه، ويقرأ hermesHome وعنوان الـ backend من الخدمات.

      الخيارالنوعالقيمة الافتراضيةالوصف
      enableboolfalseإضافة CLI الخاص بـ hermes إلى home.packages، وتصدير HERMES_HOME إلى الـ shells الخاصة بك
      packagepackageservices.hermes-agent.packageالحزمة المراد تثبيتها. تطبّق القيمة الافتراضية extraPythonPackages و extraDependencyGroups من الخدمات، فيكون كلاهما بناءً واحدًا.
      desktop.enableboolfalseإضافة تطبيق Hermes Desktop، مع مدخل في قائمة التطبيقات على Linux
      desktop.packagepackagepackage.hermesDesktopحزمة تطبيق سطح المكتب. تتبع القيمة الافتراضية package، فيعمل التطبيق والخدمات على بيئة تشغيل Hermes واحدة.
      programs.hermes-agent = {
        enable = true;
        desktop.enable = true;
      };

      services.hermes-agent = {
        enable = true;
        backend.mode = "serve";
        backend.sessionTokenFile = config.sops.secrets."hermes/desktop-token".path;
      };

      يحمل مدخل التشغيل (launcher) قيمة HERMES_HOME بنفسه. فقائمة سطح المكتب لا تقرأ أي shell profile، لذا فإن القيمة التي يصدّرها programs.hermes-agent.enable عبر home.sessionVariables لا تصل إلا إلى الـ shell التفاعلي. ودون وجود هذه القيمة في مدخل التشغيل، يفتح التطبيق ~/.hermes بينما تستخدم الخدمات hermesHome، فلا ترى أي جلسات ولا أي مفاتيح.

      عند استخدام backend.sessionTokenFile، يتصل التطبيق بالـ backend الخاص بالخدمة بدلًا من تشغيل backend خاص به. يقرأ الطرفان الملف عند بدء التشغيل، فلا يدخل الـ token أي مسار في Nix store. ودون هذا الخيار، يشغّل كل طرف الـ backend الخاص به.

      أُزيل الخيار services.hermes-agent.installPackage بسبب هذا الفصل. وأي ملف إعدادات لا يزال يضبطه يتلقى خطأً يذكر اسم الخيار البديل.

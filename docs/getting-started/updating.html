      التحديث & إلغاء التثبيت

      التحديث​

      اختر طريقة التحديث للتثبيت الجاري تشغيله:

      التثبيتطريقة التحديث
      نسخة مصدر مسحوبة مُدارةhermes update أو مسار تسليم التحديث في Desktop المبني من المصدر.
      MSIX مثبّت جانبيًا في Windowsعنصر Update في Desktop و Windows App Installer.
      حزمة Microsoft Storeتحديثات Microsoft Store.
      تطبيق macOS مُحزّمعنصر Update في Desktop عبر electron-updater.
      صورة Dockerاسحب الصورة المختارة وأعد إنشاء الحاوية مع تركيب البيانات نفسه.
      Nixحدّث flake/profile وأعد البناء.
      Termux APTpkg update ثم pkg upgrade hermes-agent.

      hermes update لا يعيد كتابة ملفات التطبيق المملوكة للحزمة. يدير PM الاعتماديات، لا توزيع التطبيق: يُعدّ hermes pm update أمرًا للمشرفين لتحديث الإصدارات المثبّتة، وليس محدّثًا بديلًا للتطبيق.

      لتثبيت مصدر مُدار:

      hermes update

      تتبع نسخة المصدر المسحوبة من المستودع الرسمي قناة stable: أحدث إصدار GitHub منشور يحمل vX.Y.Z (لا مسودة ولا إصدارًا تمهيديًا ولا وسم canary أبدًا)، وتُسحَب عند commit نفسه. ينتقل hermes update وزر تحديث Desktop من إصدار إلى التالي فقط، وليس commit تلو آخر أبدًا. تستمر forks والمرايا في تتبّع branch main الخاص بها. يجهّز التحديث الاعتماديات عبر PM ويبلّغ عن تغييرات الإعدادات ونتائج إعادة تشغيل العمليات.

      hermes update --set-channel main     # follow every commit on main instead
      hermes update --set-channel stable   # back to releases only
      hermes update --channel main         # one run against main; nothing is saved

      يُحفَظ الاختيار لكل تثبيت ضمن update.installs في config.yaml. لا يتقدّم التثبيت الذي لم يختر قناة إلا إلى الأمام: فالنسخة المسحوبة الأحدث بالفعل من أحدث إصدار (مثل نسخة كانت تتبع main قبل هذه القيمة الافتراضية) تبقى في مكانها حتى صدور إصدار أحدث. ويثبّت تشغيل --set-channel stable النسخة المسحوبة عند commit الإصدار نفسه، حتى لو كان أقدم؛ ويسمّي Desktop هذا الانتقال رجوعًا إلى الإصدار (rollback)، ويقول hermes update --check إن النسخة المسحوبة أحدث، بدلًا من الإعلان عن تحديث جديد.

      تضع المُثبّتات (install.sh و install.ps1 و Hermes-Setup) التثبيت الجديد على أحدث إصدار مستقر أيضًا. وإعادة تشغيل أحدها فوق تثبيت لم يختر قناة قط تنقله إلى ذلك الإصدار فقط إذا كان الإصدار منحدرًا من نسخته المسحوبة. أما أي نسخة مسحوبة أخرى (تتبع main، أو تجاوزت الإصدار بالفعل) فتبقى في مكانها، ويقرّر hermes update ذلك الانتقال: إذ يرفض إصدارًا يسبق مخازن الجلسات التي تستخدمها النسخة المسحوبة بالفعل. وفوق تثبيت اختار قناة غير main، تُبقي إعادة التشغيل نسخته المسحوبة في مكانها: فلا ينقلها إلا hermes update. لتثبيت أحدث ما في main بدلًا من ذلك، مرّر --channel main (-Channel main لـ install.ps1، أو اضبط HERMES_INSTALL_CHANNEL=main قبل أمر irm | iex المختصر)؛ ويحفظ المُثبّت هذا الاختيار بالطريقة نفسها التي يفعلها hermes update --set-channel main. ويظل تثبيت --commit الصريح ساريًا. ولا تتأثر تثبيتات Windows Store و MSIX و desktop المُحزَّم؛ فقناتها مدمجة في الحزمة (انظر أدناه).

      تحديثات Desktop المُحزّم​

      في Windows، يفحص التطبيق المثبّت جانبيًا مصدر App Installer المسجّل. ينزّل Apply واصف .appinstaller قبل إيقاف backends المملوكة للتطبيق، ويفتح الملف المحلي ثم يخرج حتى يستبدل Windows الحزمة. يحاول عامل انتظار منفصل إعادة الإطلاق تلقائيًا بعد تغير إصدار الحزمة. يؤدي فشل تسجيل عامل الانتظار إلى تحذير يطلب إعادة الفتح يدويًا.

      في macOS، ينزّل Apply تحديث ZIP وينتظر قبول Squirrel.Mac للتطبيق الموقّع قبل إيقاف backends. مسار Apply وحده يطلب التثبيت وإعادة الإطلاق. لا يثبّت الخروج العادي تنزيلًا معلّقًا. تُبقي إخفاقات التنزيل أو التحقق backends تعمل.

      تستخدم حزم Store المتجر بدل أي من موجزي التثبيت الجانبي. يجب ألا يُفسَّر فحص تحديث معطوب أو غير متاح بأنه "already up to date". يُحدَّث التطبيق وبيئة التشغيل الأساسية المضمّنة معه معًا؛ وتبقى بيانات المستخدم خارج الحزمة. راجع تثبيت Desktop.

      حزمتا Desktop المستقرة و canary تطبيقان منفصلان. لا يستبدل تثبيت canary stable، بما في ذلك على Windows مع MSIX. يحتفظ كل تطبيق بحالة Desktop الخاصة به ويتحدّث ضمن القناة المدمجة في بنيته؛ وتغيير القناة يعني تثبيت التطبيق الآخر، لا تغيير إعداد. لأيقونة canary خلفية صفراء (صفراء داكنة في الوضع الداكن)، وأمر CLI الخاص بها هو hermes-canary.

      حزم commits لمرة واحدة منفصلة عن قناتَي الإصدار وعن حزم commits الأخرى. تعرض أيقوناتها الحمراء SHA المختصر للبناء، المستخدم أيضًا في أمر hermes-<short-sha> في CLI. لا تفحص التحديثات ولا تثبّتها، بما في ذلك عبر hermes update أو hermes update --check. وتوضح ذلك:

      This build doesn't get updates. Ask the developer who gave it to you for a new build.

      تظل التطبيقات المنفصلة تتشارك profiles وإعدادات وجلسات Hermes ضمن مجلد Hermes الرئيسي نفسه. تشغيل بنى مختلفة على profile واحد ليس عزلًا للمخطط: قد تغيّر البنى الأحدث البيانات المخزّنة بحيث تعجز الأقدم عن قراءتها. انسخ البيانات المشتركة احتياطيًا قبل الاختبار. يحذّر Desktop و CLI المستقل عندما يستخدم تثبيت حي آخر profile نفسه؛ وهذا تنبيه إرشادي لا قفل. تنبيهات Desktop بعد التحديث خاصة بالتطبيق، لذا لا يستهلك تشغيل canary التنبيه المعلّق لـ stable. يظل مخطط URL hermes:// مشتركًا؛ ويتعامل مع الروابط التطبيق الذي سجّله أخيرًا.

      نصيحة

      hermes update خيارات الإعدادات الجديدة تلقائيًا ويطلب منك إضافتها. إذا تخطيت هذه المطالبة، يمكنك تنفيذ hermes config check يدويًا لعرض الخيارات الناقصة، ثم hermes config migrate لإضافتها تفاعليًا.

      إشعارات التحديث التلقائية​

      يمكن للتثبيتات المقيّدة بإصدار محدد (pinned) أو غير التفاعلية تعطيل الفحوصات التلقائية لإصدار CLI ولإشعارات التحديث في الشعار (banner):

      hermes config set updates.check false

      يُخفي هذا الإعداد إشعارات التحديث المخزّنة مؤقتًا، ويوقف طلبات الشبكة الخاصة بفحص التحديثات التلقائي، معًا. القيمة الافتراضية هي true. يظل التنفيذ الصريح لـ hermes update --check و hermes update يعمل؛ ولا يتحكم هذا الإعداد في أداة التحديث الخاصة بتطبيق Desktop.

      ما يحدث أثناء التحديث​

      لنسخة مصدر مسحوبة مقبولة، ينفّذ hermes update المراحل التالية:

      1. لقطة ما قبل التحديث (snapshot) — يحفظ Hermes ملفات حالة مختارة لكل profile في دليل state-snapshots/ الخاص به. تشمل بيانات الاقتران ومهام cron و config.yaml، و .env و auth.json. تتجاوز اللقطات السريعة التلقائية الملفات الفردية الأكبر من 1 GiB. يختار updates.pre_update_backup quick افتراضيًا، و full أو off. تستخدم الأرشيفات الكاملة استثناءات النسخ الاحتياطي. يستخدم التعافي اللقطات والتراجع. تستعيد اللقطات السريعة ملفات الحالة، لا كود التطبيق. اللقطة بأفضل جهد: إذا فشلت، يطبع التحديث تحذير ⚠ Pre-update snapshot FAILED ويتابع، ويسجّل الإيصال pre_update_backup كخطوة فاشلة (أما اختيار off/--no-backup عمدًا فيُسجَّل ضمن تجاوزات الإيصال مع سببه بدل ذلك).
      2. تحديث الكود — يطبّق branch المصدر المضبوط أو وسم الإصدار المستقر ويحدّث submodules. في Linux و macOS تُوقَف كل gateway تعمل من هذا التثبيت مؤقتًا قبل أول تغيير في النسخة مباشرةً (راجع انقطاع gateway أثناء التحديث)؛ التحديث الذي لا يملك شيئًا لتطبيقه أو يفشل قبل تغيير النسخة لا يوقف شيئًا.
      3. التحقق من صحة الصياغة بعد السحب + التراجع التلقائي — بعد السحب، يُصرّف Hermes الملفات الحرجة التسعة التي يستوردها كل استدعاء لـ hermes عند البدء. إذا فشل تحليل أي منها (مثل علامة تعارض دمج متبقية أو ملف اقتُطع بالخطأ)، يتراجع Hermes عن التثبيت حتى تبقى الـ shell قابلة للإقلاع: يعيد النسخة إلى commit الذي كانت عليه قبل السحب (git reset --hard <pre-pull-sha>)، أو عندما حوّل التحديث نسخة detached أو branch ميزات معلّقًا، يعود إليه باستخدام git checkout --detach <sha> / git checkout <branch> (الـ branch الذي يتعذّر سحبه مجددًا يُستعاد detached عند commit نفسه). أعد تشغيل hermes update بمجرد وصول الإصلاح إلى المستودع الأصلي (upstream).
      4. تجهيز الاعتماديات — يوفّر PM الأدوات المطلوبة ويجهّز بيئة Python كاملة من lock الجديد والإضافات (extras) الحالية ومتطلبات الإضافات المفعّلة. يتحقق من البيئة قبل نشر اختيارها. لا تتسبب إضافة مطلقًا في فشل التحديث. تُضاف الإضافة التي لم تعد تلائم النواة الجديدة إلى plugins.disabled في كل profile يفعّلها (ويُمسَح memory.provider لمزوّد الذاكرة). يشمل ذلك requires-python الذي يستبعد Python الخاص بـ Hermes و manifest_version الأحدث مما يدعمه هذا Hermes، والاعتماديات التي يثبت المحلّل تعذّر حلّها مع النواة والإضافات السابقة بترتيب الإعدادات، أو التي يفشل بناؤها نفسه. يُعاد تنزيل فاشل أو اتصال فاشل مرة واحدة، وتُعطَّل الإضافة إذا فشل مجددًا. يطبع التحديث ⚠ Disabled plugin '<name>' in <home>: <reason> ويسجّله في تحذيرات الإيصال ويتابع. أعد تفعيلها باستخدام hermes plugins enable <name> عندما تصدر نسخة متوافقة من الإضافة أو تعود الشبكة. لا يؤدي نطاق requires_hermes الذي لا تطابقه النسخة الجارية إلى تعطيل الإضافة مطلقًا، لأن نسخة المصدر دون وسوم إصدار قد تُقرأ كإصدار أقدم. تتوقف تلك الإضافة عن المشاركة بدلًا من ذلك (⚠ Left plugin '<name>' … out of this update) وتظل مفعّلة وتعود عندما يبلّغ Hermes عن إصدار تقبله. يتوقف profile ثانوي يتعذّر قراءة إعداداته بالطريقة نفسها حتى إصلاحها. وحدها النواة التي يتعذّر بناؤها بمفردها تفشل هذه الخطوة.
      5. ترحيل الإعدادات — يكتشف خيارات الإعدادات الجديدة المضافة منذ إصدارك ويطلب منك ضبطها
      6. إعادة بناء Desktop (التجهيز ثم الاستبدال) — إذا كان تطبيق Hermes Desktop قد بُني من هذه النسخة المسحوبة (checkout)، فيُعاد بناؤه لتتطابق الواجهة الرسومية (GUI) مع الكود الجديد. تحزم عملية إعادة البناء التطبيق في مجلد تجهيز مؤقت بجوار apps/desktop/release/ ويتحقق من التطبيق المجهّز، ثم يعيد تسميته فوق البنية السابقة فقط بعد ذلك (في Windows، يُتجاوَز احتجاز ماسح آني مؤقت لملف release/win-unpacked بعدة محاولات قصيرة). إذا فشلت إعادة البناء في أي نقطة — تنزيل Electron تالف أو اعتمادية مفقودة أو قرص ممتلئ — يبقى التطبيق السابق دون مساس وقابلًا للتشغيل؛ ويطبع التحديث سطر ⚠ ويتابع الخطوات المتبقية (ترحيل الإعدادات وإعادة تشغيل gateway) ويخرج بالرمز 0 مع متابعة build في إيصاله، ويعيد التشغيل التالي أو hermes update أو hermes desktop --build-only --force-build محاولة البناء. في macOS تُنسخ الحزمة المعاد بناؤها (باستخدام ditto مع بقاء التوقيع سليمًا) فوق نسخة قديمة في /Applications/Hermes.app أو ~/Applications/Hermes.app، حتى تطابق النسخة التي يطلقها Finder و Dock الـ backend؛ وتُترَك النسخة المثبّتة الجارية دون مساس، ويطلب التحديث منك إغلاقها وتنفيذ hermes update مجددًا. إذا أُزيلت نسخة ثبّتها تحديث سابق (بما في ذلك سحبها إلى Trash)، يعيد التحديث بناءها عند الحاجة ويعيد وضعها ويبلّغ بذلك، حتى يجد Finder و Dock و Spotlight تطبيق Hermes مجددًا؛ ويزيل hermes uninstall التطبيق نهائيًا. في Windows، عندما يُكمِل التحديث من داخل تطبيق Desktop الذي سيعيد بناءه (التطبيق الذي يكمل تحديثًا منقطعًا عند التشغيل)، تُتجاوَز إعادة البناء مع تنبيه: يقفل Windows ملفات التطبيق الجاري، وإيقافه سينهي التحديث معه. تكتمل بقية التحديث؛ أغلق Hermes Desktop ونفّذ hermes desktop من طرفية، أو استخدم Update now في Settings → About، لإعادة بنائه وفتحه.
      7. إعادة تشغيل الـ gateway تلقائيًا: في Linux و macOS تُشغَّل gateways الموقوفة مؤقتًا للتحديث بمجرد تجهيز الاعتماديات وتحديث المُشغِّلات، قبل بناء المنتجات؛ وفي Windows تُعاد تشغيلها بعد البناء. تُحدَّث أي gateway أخرى جارية بعد اكتمال التحديث. تُعاد تشغيل gateways التي تديرها خدمات (systemd في Linux و launchd في macOS) عبر مدير الخدمات. تُعاد إطلاق gateways اليدوية عندما يستطيع Hermes ربط PID الخاص بها بـ profile. أما backends الخاصة بـ hermes serve / hermes dashboard المُطلَقة يدويًا فمختلفة: يتركها المحدّث تعمل ويطلب من مالكها إعادة تشغيلها. راجع تذكيرات إعادة تشغيل backend اليدوي. تظل backends المملوكة لتطبيق Desktop جارٍ مسؤولية التطبيق.
      8. ترحيل Multiplex (التثبيتات متعددة الـ profiles) — بعد التحقق من أن الأسطول (fleet) يعمل على الكود الجديد، يُدمَج أي تثبيت يضم اثنين أو أكثر من الـ profiles التي لا تزال تشغّل gateway واحدًا لكل profile في gateway افتراضي واحد متعدد الإرسال (multiplexed) ما لم يمنع ذلك عائق (وهو ما يعادل hermes gateway migrate --multiplex --yes)؛ وإذا وُجد عائق (token بوت مشترك بين اثنين من الـ profiles، أو profile ثانوي يربط منفذًا دون مدخل /p/<profile>/) يطبع التحديث العوائق مع طرق إصلاحها ولا يغيّر شيئًا. لا تُمَسّ التثبيتات ذات الـ profile الواحد أبدًا. راجع الترحيل من gateway منفصل لكل profile.

      انقطاع gateway أثناء التحديث​

      في Linux و macOS، يوقف hermes update كل gateway تعمل من هذا التثبيت مباشرةً قبل أول تغيير في النسخة، ويشغّل المجموعة نفسها بالضبط على الكود الجديد بمجرد تجهيز الاعتماديات (قبل بناء واجهة الويب و TUI و Desktop الذي قد يستغرق دقائق). تكون بوتاتك غير متصلة خلال تلك الفترة: عادةً تحديث git ومزامنة الاعتماديات. قبل ذلك، كانت gateway تواصل تشغيل الكود القديم بينما يعيد git كتابة الملفات تحتها، وكانت أي وحدة تستوردها بكسل خلال تلك الفترة تأتي من الكود الجديد.

      • يطبع التحديث سطرًا واحدًا يسمّي ما أوقفه مؤقتًا (⏸ Paused for the update: hermes-gateway.service) وسطرًا عند عودته (▶ Restarted paused gateway(s): …).
      • تُوقَف وحدات systemd وعملاء launchd وتُشغَّل عبر systemd/launchd، فلا يستطيع مدير الخدمات إعادة تشغيلها بالكود القديم أثناء التحديث. تُفرَّغ gateway التي بدأتَها يدويًا (hermes gateway run) ثم تُشغَّل مجددًا في الخلفية من سطر الأوامر ومجلد Hermes الرئيسي نفسيهما؛ وتذهب مخرجاتها إلى logs/gateway-update-resume.log في ذلك المجلد بدل طرفيتك.
      • /update من المحادثة يستمر رغم الإيقاف المؤقت: عندما يعمل التحديث داخل وحدة systemd الخاصة بـ gateway نفسها، ينقل نفسه أولًا إلى نطاق خاص به. تأخذ المطالبة التي تُطرح أثناء إيقاف gateways قيمتها الافتراضية فورًا لأنه لا توجد gateway لترحيلها.
      • تُسجَّل المجموعة الموقوفة مؤقتًا في مجلد Hermes الرئيسي قبل أول إيقاف. إذا أُنهي التحديث، يشغّل أمر hermes التالي (أو hermes update) gateways نفسها مجددًا. يعيد التحديث الفاشل الذي لم يغيّر النسخة تشغيلها بالكود القديم. إذا فشلت مزامنة الاعتماديات بعد انتقال النسخة، تعود للعمل بعد أن يزامن تشغيلٌ الاعتماديات.
      • تُترَك gateway التي يتعذّر على المحدّث إيقافها عبر supervisor الخاص بها (وحدة s6 أو systemd مخصّصة أو --external-supervisor أو مهمة launchd بدأت هذا التحديث) تعمل وتُحدَّث بعد التحديث كما سابقًا.
      • --no-gateway-restart لا يوقف شيئًا؛ فأنت تدير gateways.
      • لا يعيق الإيقاف المؤقت التحديث مطلقًا. إذا تعذّر تعداد gateways أو تسجيلها أو إيقافها، يعيد تشغيل كل ما أوقفه ويذكر ذلك، ويواصل التحديث بالطريقة السابقة لوجود الإيقاف المؤقت: تعمل gateways أثناء التبديل وتُعاد تشغيلها بعده.

      كان Windows يوقف gateways مؤقتًا قبل التحديث بالفعل (لأنها تقفل ملفات تستبدلها مزامنة الاعتماديات) ويعيد تشغيلها عند اكتمال التحديث بعد البناء.

      الترقية إلى بيئة تشغيل الجلسات التي يملكها الـ gateway​

      بدءًا من هذا الإصدار يملك gateway واحد لكل مضيف كل جلسة محلية (CLI و TUI و Desktop و API و ACP و cron و Bot Chat). وهذا ما يراه التثبيت الحالي عند أول تحديث:

      • أُلغي cron.bot_chat_delivery_timeout_seconds. تُقبَل عمليات تسليم Bot Chat إلى gateway العامل للـ profile المستهدف وتُتتبَّع بإيصال؛ ولم يبقَ أي دور على جانب cron ينتهي بمهلة. ويزيل ترحيل الإعدادات v51 المفتاح مع ملاحظة لمرة واحدة (حتى من config.yaml بلا إصدار). وبدون gateway عامل يُسجَّل التشغيل delivery_failed؛ ولا يُعاد تسليمه تلقائيًا.
      • سجلات Bot Chat المعلقة القديمة (cron/bot_chat_pending/*.json التي خلّفتها مسار تسليم hermes chat الملغى) تُسلَّم إلى المالك الحي للهدف في دورات المجدوِل اللاحقة بمعرّفاتها الخاصة. وكان السجل claimed دور CLI غير مؤكد ولا يُعاد إرساله أبدًا. وتُحفظ السجلات بحالتها النهائية بوصفها دليلًا.
      • لا يُعاد تشغيل العمل الذي قاطعته إعادة التشغيل أثناء الانتقال أبدًا. عند أول بدء للـ gateway، يصبح أي إدخال كان في منتصف دور (started) وأي عامل مُدار كان يعمل unknown؛ وتنتظر المدخلات المصطفّة خلفه. افحص الجلسة، ثم أقرّ بـ /discard <admission_id> في hermes chat (أو ما يعادله في Desktop/TUI)، أو من سكربت بـ hermes sessions discard <session> --yes، قبل تشغيل المدخلات اللاحقة. وبالمثل، يُسوَّر تسليم cron كان gateway قد طالب به ولم ينهه بالحالة unknown ويُسجَّل delivery_failed.
      • الرجوع إلى إصدار أقدم غير مدعوم بمجرد أن يكتب الـ gateway الجديد في state.db. انظر الرجوع إلى إصدار أقدم.

      الرجوع إلى إصدار أقدم​

      لا يمكن لإصدار أقدم أن يعمل على state.db كتبته بيئة تشغيل الـ gateway. ويرفض كل موضع قد يفعل ذلك بدلًا من إفساد السجل:

      • يرفض hermes update هدفًا (--branch أو تبديل قناة أو إصدارًا مثبّتًا) يسبق بيئة تشغيل الـ gateway ما دام state.db لأي profile يحتوي على سجل لبيئة تشغيل الـ gateway. ويتوقف قبل المساس بالنسخة المسحوبة، ويعرض المخازن المتأثرة وطريق العودة.
      • إصدار أقدم يعمل على المخزن المُرقّى (عبر git checkout يدوي لوسم قديم) لا يستطيع حذف الجلسات التي لها سجل بيئة تشغيل gateway أو تقليمها. ويتوقف hermes sessions delete و prune مع Refused to delete a session that has gateway runtime history. وما زالت الإصدارات الأقدم تطبع هذا داخل traceback، ويتراجع prune عن دفعته كاملة.
      • الـ gateway العامل الذي تُنقل نسخته المسحوبة إلى إصدار كهذا يوقف نفسه خلال نحو 30 ثانية، ليتمكن الإصدار الأقدم من بدء gateway الخاص به.

      وللرجوع على أي حال، استعد الحالة السابقة للتحديث بدلًا من تشغيل الإصدار الأقدم على قاعدة البيانات المُرقّاة:

      1. hermes gateway stop
      2. اسحب (check out) الإصدار الأقدم.
      3. استعد أحدث لقطة قبل التحديث (/snapshot restore <id>)، أو نسخة احتياطية كاملة أُخذت بـ hermes update --backup (hermes import <backup.zip>). تتخطى اللقطات السريعة أي state.db أكبر من 1 GiB؛ وتحتاج المخازن الكبيرة إلى النسخة الاحتياطية الكاملة.

      الجلسات والرسائل التي أُنشئت بعد التحديث ليست في تلك اللقطة.

      لماذا قد تستغرق إعادة تشغيل gateway وقتًا​

      تُفرِّغ إعادة التشغيل العمل أولًا: ترفض gateway الجارية الأدوار الجديدة ثم تنتظر اكتمال الأعمال قيد التنفيذ (أدوار المحادثة ومهام cron وتشغيلات API) قبل الخروج، بحد أقصى تضبطه agent.restart_after_turn_timeout (30 دقيقة افتراضيًا) حتى لا تُقطع مهمة طويلة في منتصف التشغيل. أثناء الانتظار، يطبع المحدّث كل 30 ثانية ما تزال gateway تنتظره — مثل:

        → hermes-gateway: draining (up to 1875s)...
        ⏳ still draining — 1560s left before the forced restart
           waiting on 1 active work unit(s):
             • cron job 6ba19dab68df (nightly-scout) in external worker pid 573597, running 6m40s
           finish or kill the work above to release the drain now; agent.restart_after_turn_timeout in config.yaml caps this wait

      تعرض أدوار المحادثة مفتاح الجلسة والنموذج والأداة الحالية؛ وتعرض مهام cron معرّف المهمة واسمها والعملية التي تشغّلها (عاملًا خارجيًا آمنًا لإعادة التشغيل في تثبيتات systemd، وإلا gateway نفسها). تعرض hermes gateway status الوحدات نفسها أثناء تفريغ gateway. لإيقاف الانتظار، أنهِ العمل المُدرَج أو أوقفه قسريًا، أو اخفض agent.restart_after_turn_timeout في config.yaml (0 يُدخِل التفريغ القسري فورًا).

      لا يحتجز العمل العالق إعادة التشغيل: دور محادثة تجاوز خمولُه agent.gateway_timeout أو تشغيل cron أقدم من مهلة التنفيذ المسموحة للمجدول (max(2 × the job's interval, cron.inflight_max_minutes)، 30 دقيقة افتراضيًا) يُستبعَد من الانتظار وتُقاطعه إعادة التشغيل بدلًا من ذلك.

      العمل الذي يستمر بعد gateway لا يحتجز إعادة التشغيل أيضًا: تشغيل cron الذي سُلِّم بالفعل لعامل ضمن نطاق systemd خاص به (systemd-run --user --scope، الحالة المعتادة في تثبيت systemd) يواصل العمل عند توقف gateway، وتُسلَّم نتيجته من الطابور الدائم عبر أي gateway تبدأ لاحقًا — لذا تستمر إعادة التشغيل بدل الانتظار حتى السقف الكامل. العامل الذي تعذّر حصوله على نطاق مستقل (لا جلسة D-Bus للمستخدم يمكن الوصول إليها، راجع cron.require_restart_safe_scope) يبقى في cgroup الخاصة بـ gateway ويظل الانتظار قائمًا له، لأن إعادة التشغيل ستنهيه في منتصف عمله.

      ملفات أداة التحديث المفقودة على Windows​

      إذا كان سكربت أداة التحديث المُصانة مفقودًا (مثلًا بعد أن يعزله برنامج مكافحة الفيروسات)، يفشل مُحوِّل التحديث القديم (legacy update forwarder) بدلًا من الإبلاغ عن تسليم ناجح. أصلح التثبيت وراجع تقرير العزل الصادر عن برنامج الحماية قبل إعادة المحاولة؛ ولا تعطّل الحماية من الفيروسات. وقبل الإبلاغ عن النجاح، تتحقق أداة التحديث المُصانة من استيراد CLI، وترويسة الملف التنفيذي لـ Windows، وترويسة ASAR ونقطة الدخول الرئيسية المحزومة، وملف HTML الخاص بالـ renderer وقابليته للقراءة مع نقطة دخول لوحدة محلية، وملفات الوحدات الأولية، وختم البناء الحالي. هذه فحوصات دنيا للمخرجات، وليست تدقيقًا كاملًا للاعتماديات ولا اختبارًا لإطلاق التطبيق/الـ backend. يُبلَّغ عن غياب Python قبل انتظار إغلاق Desktop؛ ولا يزال يُسمح بتشغيل إصلاح الاعتماديات كجزء من التحديث. يتحقق Electron من المتطلبات المسبقة للتسليم المُصان قبل إيقاف الـ backends عند وجود هذا التخطيط؛ وتظل تخطيطات أداة التحديث القديمة المسطّحة (legacy-flat) الحقيقية مدعومة، لذا لا يُكتشف كل ملف مفقود من ملفات أداة التحديث قبل إيقاف الـ backend.

      على Windows، إذا أُعيد فتح Desktop أثناء التحزيم، فإنه يُوقَف مجددًا مباشرةً قبل ترقية البناء المُجهَّز. يقتصر هذا التنظيف على الملفات التنفيذية الموجودة داخل شجرة إصدار Desktop في تلك النسخة المسحوبة؛ ولا تُوقَف التثبيتات غير ذات الصلة. وأي قفل متبقٍّ يؤدي إلى فشل ترقية البناء المُجهَّز بدلًا من تجاوز خطأ إعادة التسمية.

      hermes update --branch release-candidate
      hermes update --check --branch experimental   # preview behindness only

      إذا كانت نسختك المحلية على branch مختلف، يُجري Hermes تلقائيًا stash لأي عمل غير مُثبَّت بـ commit، ويحوّل HEAD إلى الـ branch المستهدف، ثم يسحب التحديثات. الـ branches غير الموجودة محليًا تُتتبَّع تلقائيًا من origin/<name> (git checkout -B <name> origin/<name>). أما الـ branches غير الموجودة في أي مكان فتفشل بشكل نظيف — إذ تُستعاد تغييراتك المحفوظة في stash قبل الخروج، فلا تبقى عالقًا في حالة غريبة أبدًا. ويُتخطى تلقائيًا منطق مزامنة الـ fork مع upstream المخصص لـ main فقط، وذلك على الـ branches الأخرى غير main.

      نسخة مسحوبة متوقفة على branch ميزة​

      إذا تُركت النسخة المسحوبة من الكود المصدري على branch ميزة (بفعل أدوات ما، أو تجربة worktree، أو checkout يدوي)، فإن hermes update يعيدها تلقائيًا إلى هدف التحديث كلما كانت شجرة العمل نظيفة:

      • الـ branch مدموج بالكامل (كل commit موجود أصلًا في origin/main — ولا يُبلغ git cherry عن أي شيء غير مدموج): يوضح التحديث ذلك — Checkout was parked on '<branch>' (fully merged) — switched back to main — ويبقى على main بعد ذلك.
      • الـ branch يحتوي على commits غير مدموجة لكن الشجرة نظيفة: يظل التحديث ينتقل إلى main حتى يتمكن من المتابعة — وهذا ما تعتمد عليه الجهات المستدعية غير التفاعلية (زر التحديث في تطبيق سطح المكتب، و /update في الـ gateway، و cron)، إذ لا سبيل لديها لحل حالة التخطي. تبقى الـ commits الخاصة بك كما هي: فالأمر git checkout لا يتخلص أبدًا من العمل المُثبَّت بـ commit، ويطبع التحديث إشعارًا واضحًا يذكر اسم الـ branch وعدد الـ commits، إضافةً إلى الأمر git checkout <branch> لاستئناف العمل لاحقًا.

      إذا كنت تشغّل branch مخصصًا عن قصد (تعديلات محلية تحافظ عليها فوق main)، فاضبط updates.parked_branch_strategy: update_in_place في config.yaml. عندها يدمج التحديث origin/main داخل الـ branch الخاص بك بدلًا من الانتقال بعيدًا عنه — فلا تتحرك النسخة المسحوبة أبدًا، وتبقى الـ commits الخاصة بك، ويتقدّم الكود العامل. يُستخدم fast-forward متى أمكن؛ وعند التباعد يُجرى دمج حقيقي خلف وسم أمان pre-update-<stamp>، مع التوقف بشكل نظيف (دون تغيير أي شيء) عند حدوث تعارض. ويعيد hermes update --switch-branch السلوك إلى مسار الانتقال لتشغيل واحد — وهذا مفيد على branch ميزة بعيد عن main يجب ألا تتراكم فيه commits دمج ناتجة عن التحديثات.

      عندما يحتوي الـ branch المتوقف على تغييرات غير مُثبَّتة (شجرة غير نظيفة)، فإن Hermes لا يلمسه. ويُعلَّم تحديث الكود بأنه SKIPPED مع تحذير واضح يذكر اسم الـ branch، ومدى تأخره عن origin/main، والأوامر الدقيقة لحل المشكلة — بدلًا من التظاهر بنجاح التحديث. ويعرض سطر الاكتمال دائمًا الـ branch الفعلي و HEAD (✓ Update complete! [main @ 30fcf9580]) لتتضح أي انحرافات بنظرة سريعة. اضبط updates.auto_switch_parked_branch: false في config.yaml لتعطيل الانتقال التلقائي كليًا (يظل تحذير التخطي يظهر).

      commits محلية على branch الهدف​

      توقف الـ commits المنشأة مباشرةً على هدف التحديث (main) عمليات fast-forward بمجرد تحرك المصدر الأصلي، ولا تستطيع النسخة تمييزها عن force-push في المصدر الأصلي، لذا يعيد التحديث main إلى origin/main. قبل الإعادة، يحفظ HEAD القديم باسم refs/hermes-update-backups/diverged-main-<stamp>-<sha> ويطبع ذلك المرجع مع عدد commits التي ستغادر branch. تعرضها git log origin/main..<ref>؛ ويعيدها git branch <name> <ref> أو git cherry-pick. إعادة تشغيل المُثبّت فوق نسخة موجودة (install.sh / install.ps1، وهو ما يفعله bootstrap في Desktop) تكتب المراجع نفسها. كلما كتبت hermes update أحدها، تحتفظ بأحدث عشرة لكل نوع وتحذف الأقدم من 30 يومًا. للاحتفاظ بـ patches عبر التحديثات، أبقها على branch مخصّص مع updates.parked_branch_strategy: update_in_place بدلًا من ذلك.

      التغييرات المحلية في التحديثات غير التفاعلية​

      عند تنفيذ hermes update في الطرفية، يحفظ Hermes أي تغييرات غير مُثبَّتة في شجرة المصدر عبر stash، ثم يسحب التحديثات، ثم يسألك عما إذا كنت تريد استعادتها — تمامًا كما كان يفعل دائمًا. لا يتغير شيء في التحديثات التفاعلية.

      لا يشمل autostash إلا تغييرات شجرة المصدر. في تثبيت مسطّح — حيث يكون جذر نسخة git أيضًا $HERMES_HOME (مثل تثبيت أُنشئ باستخدام HERMES_INSTALL_DIR=$HERMES_HOME أو مُثبّت أقدم) — توجد حالة تشغيل profile (state.db وملفا WAL/SHM الملحقان به و state-snapshots/, backups/, sessions/, cron/jobs.json ومخازن cron/*.db و config.yaml, auth.json, memories/ وملفات lock/pid، …) داخل النسخة كملفات غير متتبعة. يتجاهل git تلك المسارات، لذا لا يمسها autostash مطلقًا وتحتفظ gateway الجارية بقاعدة بياناتها طوال التحديث. إذا احتفظت بملفات غير متتبعة أخرى في جذر تثبيت مسطّح، فانقلها خارج النسخة أو أضفها إلى .git/info/exclude؛ فكل ملف غير متتبع ولا متجاهَل يُضمّ إلى autostash مثل تعديل مصدر.

      عندما يعمل التحديث دون طرفية — من زر "Update" في تطبيق سطح المكتب/المحادثة أو من تحديث يطلقه الـ gateway — فلا توجد مطالبة للرد عليها. ويحدد الإعداد updates.non_interactive_local_changes مصير تغييراتك المحفوظة في stash:

      # ~/.hermes/config.yaml
      updates:
        non_interactive_local_changes: stash   # default: keep + auto-restore
        # non_interactive_local_changes: discard  # throw local source edits away
      • stash (الافتراضي) — stash تلقائي، ثم سحب، ثم استعادة تلقائية لتغييراتك فوق الكود المحدَّث. لا يُفقد شيء؛ وإذا واجهت الاستعادة تعارضات، تُحفظ التغييرات في git stash لاستعادتها يدويًا.
      • discard — stash تلقائي ثم حذف الـ stash بعد السحب، فيصل التحديث دائمًا إلى شجرة نظيفة. لا تستخدم هذا الخيار إلا على الأجهزة التي لا تنوي فيها أبدًا الاحتفاظ بتعديلات محلية على الكود المصدري لـ Hermes. يعتمد هذا الخيار على حذف الـ stash (وليس git reset --hard + git clean -fd)، لذا لا تُمَس أبدًا المسارات المتجاهَلة مثل node_modules و venv ومخرجات البناء.

      في تطبيق سطح المكتب، يوجد هذا الإعداد في Settings → Advanced → In-App Update Local Changes.

      تحديثات Desktop لا تستعيد التغييرات تلقائيًا أبدًا. تستدعي أداة التحديث في تطبيق سطح المكتب الأمر hermes update --keep-stash: فتظل تعديلات المصدر المحلية تُحفظ في stash حتى يتمكن التحديث من المتابعة، لكنها لا يُعاد تطبيقها بعد ذلك — بل تبقى محفوظة في git stash ويطبع سجل التحديث الأمر الدقيق git stash apply <ref> لإعادتها. يمنع هذا انتقال التعديلات المحلية بصمت عبر تحديثات سطح المكتب وتسبّبها في تعطيل التثبيت المحدَّث حديثًا. (يظل non_interactive_local_changes: discard هو المُقدَّم إذا اخترت الحذف.) لاستعادة التغييرات المحفوظة يدويًا:

      cd ~/.hermes/hermes-agent   # or your install root
      git stash list --format='%gd %H %s'   # find the hermes-update-autostash entry
      git stash apply stash@{0}

      يمكنك أيضًا تمرير --keep-stash إلى hermes update في الطرفية إذا أردت سلوك عدم إعادة التطبيق نفسه في الوضع التفاعلي.

      معاينة فقط: hermes update --check​

      hermes update --check يقارن النسخة بهدف القناة المختارة (أحدث إصدار مستقر افتراضيًا أو origin/main في قناة main) دون تطبيق كود أو تثبيت اعتماديات أو إعادة تشغيل gateways. يمكن للمقارنة جلب بيانات Git الوصفية؛ وليس ذلك وعدًا بعدم كتابة شيء في نظام الملفات. تعرض التثبيتات المملوكة للحزم طريقة تحديثها الخارجية.

      معاينة الأسطول: hermes update --plan​

      قبل تحديث جهاز يشغّل عدة profiles أو خدمات، نفّذ hermes update --plan. يطبع نوع التثبيت وخدمات Hermes الجارية عبر profiles والمشرفين عليها وإصدارات الكود الجاري وآلية إعادة التشغيل لكل خدمة. تظهر backends الخاصة بـ hermes serve / hermes dashboard المُطلَقة يدويًا مع endpoint الربط المسجّل، لكن تؤجَّل إعادة التشغيل إلى مالكها؛ ولا يوقفها المحدّث ولا يعيد إطلاقها. تعرض التثبيتات المُدارة بصور أو حزم أمر التحديث الخارجي بدل ذلك. الخطة للقراءة فقط وآمنة على مجموعة حية.

      ويُضمَّن الجرد نفسه في إيصال كل تحديث فعلي (~/.hermes/logs/update_receipts/)، لذا يمكنك بعد التحديث مقارنة ما رصدته أداة التحديث بما نفّذته فعلًا.

      إيصالات التحديث وفحص إصدارات الأسطول​

      يكتب كل تشغيل لـ hermes update إيصالًا قابلًا للقراءة آليًا في ~/.hermes/logs/update_receipts/ (يُحتفظ بآخر 20 إيصالًا، ويشير latest.json يشير دائمًا إلى أحدثها): خطة المجموعة قبل التحديث وكل خطوة منفّذة وكل ما جرى تجاوزه وسببه ونتيجة إعادة تشغيل gateway ومصفوفة إصدارات المجموعة النهائية. إصلاح بيئة تشغيل SQLite إحدى تلك الخطوات (sqlite_runtime_repair): يسجّل الإصلاح الفاشل السبب الفعلي (مثل خطأ uv sync) وزوج إصدارات SQLite، ويُسجَّل الإصلاح المؤجّل أو غير المنطبق ضمن التجاوزات مع سببه. بعد مرحلة إعادة التشغيل، يقارن المحدّث الكود الجاري لكل gateway حيّة بالنسخة المحدّثة حديثًا ويطبع مصفوفة لكل profile — يُبلَّغ بوضوح عن gateway التي ما زالت تخدم كود ما قبل التحديث مع أمر إعادة التشغيل الدقيق، وتُسجَّل كمتابعة gateway_restart في الإيصال؛ الكود في مكانه بالفعل، لذا يظل التحديث يخرج بالرمز 0، ويحذّر كل أمر لاحق حتى تخدم المجموعة الكود الجديد، فلا تُعدّ مجموعة مختلطة الإصدارات سليمة بصمت. يستعلم كل من --plan وفحص المجموعة مباشرةً من كل gateway جارية عبر control socket المحلي الخاص بها (gateway.sock في دليل بيانات profile أو named pipe في Windows) عند توفره، لذا تأتي معلومات الإصدار و supervisor من gateway نفسها؛ وتظل gateways من الإصدارات الأقدم تُكتشَف عبر ملفات حالتها كما سابقًا.

      gateway الافتراضية ذات multiplex عملية واحدة تخدم عدة profiles، لذا تظهر مرة واحدة في المصفوفة وتؤكد تغطية كل profile في سجل served_profiles الخاص بها. تمسح التغطية نفسها التلميح "A previous hermes update pulled new code but did not restart running gateways": بمجرد تشغيل تلك gateway (أو كل gateway أعاد التحديث تشغيلها بعد git pull يدوي) للكود الحالي، يكفي hermes gateway restart — لم يعد التلميح ينتظر hermes update التالي لكتابة إيصال جديد. ينطبق ذلك أيضًا على التزام إعادة التشغيل الذي تركه تحديث مات قبل تسجيل gateways المستحقة (أو محدّث أقدم لم يسجّلها قط): بمجرد تشغيل كل gateway حيّة للنسخة الحالية، ينتهي الالتزام ويتوقف التلميح. على مضيف لا يشغّل gateway مطلقًا (تطبيق Desktop وحده)، ينتهي الالتزام بعد التأكد من عدم وجود gateway لأي profile اختفت دون إيقاف نظيف وإعادة تشغيل كل backend جارٍ بواسطة supervisor الخاص به أو حفظ تذكيره الخاص. يُسجَّل ذلك الالتزام مرة واحدة لكل مضيف في دليل التنسيق المشترك بين profiles ($HERMES_GATEWAY_LOCK_DIR، وإلا $XDG_STATE_HOME/hermes/gateway-locks) باسم host-update-restart-<install key>.json (واحد لكل تثبيت، لذا تحتفظ نسخة Hermes ثانية للمستخدم نفسه بالتزامها؛ ويُحترَم host-update-restart.json غير المربوط بمفتاح من إصدار أقدم ولا يمسحه إلا تثبيت لا يملك سجلًا خاصًا به، حتى تحتفظ نسخة أخرى ما زالت على ذلك الإصدار بدينها)، لذا ترى CLI كل profile الالتزام نفسه: يعيد hermes -p coder update و hermes -p writer update تشغيل gateway المشتركة ذات multiplex مرة واحدة بينهما، لا مرة لكل منهما. يظل الالتزام الذي تركه محدّث أقدم لكل profile (fleet_restart_pending في مجلد Hermes الرئيسي لأحد profiles) يُقرأ ويُمسَح. التحديث الذي لم تجد خطته قبل التحديث أي gateway لا يترتب عليه شيء ولا يترك علامة. backend الذي يشرف عليه Desktop أو systemd أو launchd يعيد supervisor تشغيله ولا يمنع هذه التسوية؛ وحده backend اليدوي الذي تعذّر حفظ تذكيره يبقي الالتزام مفتوحًا.

      تذكيرات إعادة تشغيل backend اليدوي​

      بعد التحديث، اطلب من مالك كل backend أُطلق يدويًا إعادة إطلاق hermes serve أو hermes dashboard؛ وأعد ربط Desktop لـ backend عبر SSH. إعادة تشغيل gateways وحدها لا تحدّث هذه العمليات.

      لـ backend حي متحقق منه، يحفظ المحدّث تذكيرًا قبل تسجيل إعادة تشغيله بالحالة deferred. يتيح ذلك اكتمال التحديث إذا نجحت الفحوصات المتبقية. هوية عملية مجهولة لا تؤهل لتأجيل جديد.

      توجد التذكيرات في serve_restart_pending/ ضمن مجلد Hermes الرئيسي النشط، منفصلة عن إيصالات التحديث الدوّارة. يعرّف كل تذكير العملية بـ PID ووقت الإنشاء. تحتفظ تحذيرات بدء التشغيل به ما دامت العملية حية أو نشاطها مجهولًا، ولا تزيله إلا عند التأكد من اختفاء تلك العملية نفسها. لا يزيله تحديث لاحق ولا gateway سليمة.

      إذا فشل الحفظ، يحذّر Hermes وينقل الالتزام غير المحفوظ إلى الإيصالات اللاحقة لإعادة المحاولة. افحص صلاحيات التخزين والمساحة الحرة، وأعد تشغيل backend وفق التعليمات. إذا فشل تخزين التذكير والإيصال كليهما، فلا يمكن ضمان الاحتفاظ الدائم.

      تحديثات تلقائية من داخل gateway:--no-gateway-restart​

      التحديث المُطلَق بواسطة gateway (مهمة cron أو محدّث Desktop أو أي أتمتة تكون ابنة لعملية gateway) لا يستطيع الاستمرار بعد إعادة تشغيل مجموعته: تتفرغ gateway عند SIGUSR1 ثم يُنهي KillMode=mixed في systemd كل ما تبقى في cgroup، بما فيه المحدّث. ينفّذ hermes update --no-gateway-restart pipeline كاملًا (السحب والاعتماديات ومساحات عمل Node وواجهة الويب والصيانة) ويتجاوز إعادة التشغيل والتحقق من المجموعة وحدهما؛ وفي Linux و macOS يتجاوز أيضًا الإيقاف المؤقت قبل تغيير النسخة، فلا يُوقَف شيء. تُحتفَظ علامة إعادة التشغيل المعلّقة، لذا يحذّر بدء CLI التالي ويجعل hermes update العادي التالي (أو hermes gateway restart) المجموعة تلحق بالكود الجديد. اقرنه بخطوة إعادة تشغيل منفصلة، مثل مؤقّت بعد مهمة التحديث بـ 10–15 دقيقة. يسجّل الإيصال التأجيل؛ ولا يجعل تقادم المجموعة الناتج عن التأجيل وحده التحديث partial في مجلد بيانات الـ profile، أو named pipe على Windows) عند توفره، فتأتي معلومات الإصدار والمشرف من الـ gateway نفسه؛ أما الـ gateways من الإصدارات الأقدم فلا تزال تُكتشف عبر ملفات حالتها كما كان سابقًا.

      عمليات إعادة تشغيل الـ gateway المتقطعة​

      إذا سحب تحديث سابق الكود لكنه لم يُكمل إعادة تشغيل الأسطول، فإن التشغيل التالي لـ hermes update يعيد المحاولة حتى عندما تكون النسخة محدّثة بالفعل. لا يثبت خلو فحص العمليات التعافي: فقد لا توجد PID حية لوحدات systemd الفاشلة ومهام launchd المثبّتة. إذا فشل الاكتشاف أو إعادة التشغيل أو تعذّر التحقق من نشاط خدمة مطلوبة، تبقى العلامة معلّقة: يظل التحديث يخرج بالرمز 0 (الكود الجديد في مكانه)، ويطبع سطر ⚠ ومتابعة gateway_restart في إيصاله، ويحذّر كل بدء CLI من إعادة التشغيل المستحقة، ويعيد hermes update التالي المحاولة. استعد الخدمات المتأثرة بالأوامر المطبوعة أو أعد تنفيذ hermes update.

      لا يثبت إيصال تاريخي فاشل وحده أن gateways ما زالت قديمة. تتحقق تحذيرات بدء التشغيل وحالة gateway، وكذلك اللحاق بالتحديث، من وجود خلف حي على النسخة الحالية لكل profile gateway مسجّل في ذلك الإيصال. يمكن لإعادة تشغيل gateway يدويًا إنهاء تنبيه مبني على الإيصال وحده دون إعادة كتابة النتيجة التاريخية. يجب نقل التزامات backend اليدوي أولًا إلى تذكيراتها المنفصلة.

      تسجّل علامة إعادة التشغيل المعلّقة جرد بيئات التشغيل الخاص بها قبل التحديث و commit الهدف. يفحص التعافي ذلك الجرد، لا جرد إيصال أقدم. تتطلب التسوية مجموعة حالية متحققة غير فارغة، وخلفًا عند commit الهدف لكل profile gateway مسجّل، ومعالجة ناجحة لأي التزامات backend يدوي محددة. backend اليدوي الذي ما زال حيًا أو نشاطه مجهول يحتاج تذكيرًا محفوظًا؛ والعملية المؤكد خروجها لا تحتاج تذكيرًا. تُبقي gateways المفقودة أو بيئات التشغيل غير المدعومة أو فشل كتابة التذكيرات العلامة معلّقة.

      لا يمكن لبدء التشغيل أو تسوية اللحاق مسح العلامات القديمة دون جرد أو الجرد المشوّه أو غير المدعوم تلقائيًا. لا تكفي إعادة تشغيل كل gateways المرئية لتحديد ما كان مستحقًا لذلك التحديث. يبقى التحذير حتى اكتمال تحديث لاحق بعلامة جديدة تحمل جرده الخاص وتسويته بنجاح.

      نسخة احتياطية كاملة قبل التحديث: --backup​

      بالنسبة إلى الـ profiles عالية القيمة (gateways الإنتاج، والتثبيتات المشتركة بين أعضاء الفريق)، يمكنك اختيار إنشاء نسخة احتياطية كاملة من HERMES_HOME قبل السحب (الإعدادات، والمصادقة، والجلسات، والمهارات، والاقتران):

      hermes update --backup

      أو اجعلها السلوك الافتراضي لكل تشغيل:

      # ~/.hermes/config.yaml
      updates:
        pre_update_backup: full

      updates.pre_update_backup له ثلاثة أوضاع:

      • quick يحفظ ملفات الحالة المختارة الموضّحة أعلاه. هذا هو الافتراضي.
      • full يضيف أرشيف zip مع استثناءات النسخ الاحتياطي. قد تستغرق أدلة البيانات الكبيرة عدة دقائق.
      • off يعطّل النسخ الاحتياطية قبل التحديث. يختار --no-backup هذا الوضع لتشغيل واحد.

      تظل القيم المنطقية القديمة مدعومة: true تعني full، و false تعني off.

      هل تنتقل إلى جهاز جديد بدلًا من ذلك؟

      تحمي النسخ الاحتياطية للتحديث عملية التحديث في المكان نفسه. أما إذا كنت تنقل إعدادك بالكامل إلى عتاد مختلف، فاستخدم hermes backup + hermes import بدلًا من ذلك — راجع تصدير Hermes إلى جهاز آخر و hermes backup مقابل hermes profile export.

      ملكية العمليات وتغييرات الاعتماديات في Windows​

      يمكن لـ Windows إبقاء ملفات التنفيذ والإضافات الأصلية مفتوحة أثناء عمل العمليات. لذلك يجهّز PM أجيال الاعتماديات منفصلة بدل استبدال المكتبات المستوردة في مكانها. تحتفظ العملية الجارية باستيراداتها الحالية حتى إعادة تشغيلها.

      اتبع تشخيص العائق للعملية والتثبيت المحددين. لا تنهِ كل عملية اسمها Python أو Hermes. تختلف مسؤوليات التحديث من المصدر واستبدال حزمة MSIX ومتطلبات إغلاقهما.

      يحتفظ المحلّل بالخيارين --force و --force-venv للتوافق مع Windows. ليسا تعليمات تحديث معتادة ولا ضمانًا لتجاوز قفل ملف من نظام التشغيل. افحص hermes update --plan وسجل التحديث و hermes pm status قبل إعادة محاولة تحديث فاشل.

      التحقق الموصى به بعد التحديث​

      بعد تحديث المصدر، نفّذ التشخيصات التالية. لتطبيق مُحزّم، استخدم صفحة About الخاصة به وحالة backend بدل أوامر Git داخل الحزمة.

      1. git status --short — إذا كانت الشجرة غير نظيفة على نحو غير متوقع، فافحصها قبل المتابعة
      2. hermes doctor — يفحص الإعدادات والاعتماديات وسلامة الخدمات
      3. hermes --version — تأكد من أن الإصدار ارتفع كما هو متوقع
      4. إذا كنت تستخدم الـ gateway: hermes gateway status
      5. hermes pm status — افحص تجهيز الاعتماديات وأي خطوات فاشلة.
      شجرة عمل غير نظيفة بعد التحديث

      إذا أظهر git status --short تغييرات غير متوقعة بعد hermes update، فتوقف وافحصها قبل المتابعة. يعني هذا عادةً أن تعديلات محلية أُعيد تطبيقها فوق الكود المحدَّث، أو أن خطوة الاعتماديات حدّثت ملفات القفل (lockfiles).

      إذا انقطع اتصال الطرفية في منتصف التحديث​

      hermes update نفسه من فقدان الطرفية عن غير قصد:

      • يتجاهل التحديث الإشارة SIGHUP، لذا فإن إغلاق جلسة SSH أو نافذة الطرفية لم يعد يُنهيه في منتصف التثبيت. وترث العمليات الفرعية لـ pip و git هذه الحماية، فلا يمكن أن تبقى بيئة Python مثبّتة جزئيًا بسبب انقطاع الاتصال.
      • تُنسخ جميع المخرجات إلى ~/.hermes/logs/update.log أثناء تشغيل التحديث. إذا اختفت الطرفية، فأعد الاتصال وافحص السجل لمعرفة ما إذا كان التحديث قد اكتمل وما إذا نجحت إعادة تشغيل الـ gateway:
      tail -f ~/.hermes/logs/update.log
      • Ctrl-C (SIGINT) وإيقاف النظام (SIGTERM) يظلان مُحترَمَين — فهما إلغاءان مقصودان لا حادثان. تُخرج Ctrl-C بعد وجود الكود الجديد بالرمز 130 وتوضح ذلك: تبقى الخطوات المتبقية (الاعتماديات والبناء وإعادة تشغيل gateway) مستحقة، ويكملها التشغيل التالي أو hermes update.

      لم تعد بحاجة إلى تغليف hermes update داخل screen أو tmux لتجاوز انقطاع الطرفية.

      متى يرفض تحديث أو تشغيل بدل التخمين​

      تتوقف بعض الحالات برسالة بدل المتابعة، لأن المتابعة قد تترك نسخة محدّثة جزئيًا أو gateway تشغّل كودًا قديمًا:

      • تشغيل آخر يصلح تحديثًا منقطعًا. عندما أُنهي تحديث بينما كان git ينقل النسخة، يعيد تشغيل hermes التالي النسخة أولًا. تتناوب التشغيلات التي تبدأ معًا (gateway يعاد تشغيلها أو backend Desktop بجانب CLI). يخرج التشغيل الذي ينتظر إصلاح تشغيل آخر أكثر من 10 ثوانٍ بالحالة 1: hermes: another Hermes launch is finishing an interrupted 'hermes update'; launch again in a moment.شغّل مجددًا بعد انتهاء الآخر. يظهر backend الذي أطلقه Hermes Desktop عندئذ كبدء فاشل؛ وتكفي إعادة فتحه.
      • فشل git في Windows → بديل ZIP الاحتياطي. في Windows، يعود خطأ git أثناء hermes update إلى تنزيل ZIP الإصدار فقط عندما لم يمس git النسخة بعد: commit و branch نفسهما منذ بدء التحديث، ودون stash أو بدء انتقال الشجرة. بمجرد تنفيذ git لـ stash أو تبديل branch أو بدء نقل الملفات، يبلّغ التحديث عن خطأ git ويخرج بالرمز 1 بدل ذلك، لأن overlay الخاص بـ ZIP سيدفن تلك الحالة. أعد تشغيل hermes update بعد إصلاح مشكلة git.
      • تحتاج بنى Desktop إلى .git. بناء Hermes Desktop من نسخة باستخدام hermes desktop يأخذ قفل النسخة نفسه الذي يستخدمه hermes update (ويحتاجه أيضًا)، والمحفوظ في دليل git للنسخة. إذا لم يكن ذلك الدليل قابلًا للكتابة لمستخدمك (مثل نسخة يملكها حساب آخر)، يرفض البناء برسالة .../.git/hermes-update.lock is not writable بدل البناء بجانب تحديث محتمل. أصلح ملكية .git أو صلاحياته. في macOS/Linux يظل ملف قفل جعله sudo hermes update للقراءة فقط قابلًا للاستخدام.
      • سجل إعادة التشغيل غير قابل للكتابة. hermes update يسجّل إعادة تشغيل gateway المستحقة قبل نقل النسخة، في دليل حالة المضيف ($HERMES_GATEWAY_LOCK_DIR، وإلا $XDG_STATE_HOME/hermes/gateway-locks). إذا تعذّرت الكتابة إلى الدليل، يُحفَظ السجل في مجلد Hermes الرئيسي للـ profile الحالي بدلًا منه. لا يقرؤه إلا ذلك profile، لذا لا يتابع التحديث إلا في تثبيت لا يحتوي profile آخر. إذا وجدت profiles أخرى أو تعذّرت قراءة قائمتها، يرفض التحديث قبل نقل أي شيء. اجعل دليل الحالة قابلًا للكتابة ثم أعد تشغيله.

      صيانة المصدر والتراجع يدويًا​

      استخدم دليل التثبيت من المصدر لنسخة تطوير مستقلة. أنشئ commit للعمل المحلي أو احفظه بوسيلة أخرى قبل تغيير إصدار Git. أوقف الخدمات التي تملكها قبل استبدال الكود الذي تشغّله.

      بعد تغيير إصدار المصدر، نفّذ إجراء الاعتماديات/bootstrap الخاص بذلك الإصدار. تستخدم النسخ التي يديرها PM python -m pm.cli install من بيئة المصدر المختارة. تثبيت pip مباشر ليس مكافئًا: لا يجهّز مخزن الأدوات المُدار ولا اختيار بيئة التشغيل في PM.

      نسخة الكود وحدها ليست تراجعًا عن البيانات. قد ترحّل الإصدارات الأحدث الإعدادات أو قواعد البيانات بصيغ لا يستطيع الكود الأقدم قراءتها. استخدم نسخة احتياطية متسقة من قبل التحديث إذا تطلب إصدار أقدم تنسيق البيانات السابق. احفظ البيانات الحالية قبل محاولة الاستعادة.

      تستخدم التثبيتات المملوكة للحزم إجراء التراجع أو إعادة التثبيت الخاص بمدير حزمتها. لا تشغّل Git أو pip داخل تطبيق موقّع أو صورة غير قابلة للتغيير.

      Python 3.14 والمفسّرات الأقدم​

      لا يعمل Hermes إلا على Python 3.14. pyproject.toml ما زال يعلن requires-python = ">=3.11,<3.15"، لكن كل اعتماد لبيئة التشغيل يحمل علامة python_version >= '3.14'. ويوجد النطاق الأوسع لسبب واحد: يجب أن يستطيع تثبيت من المصدر سبق venv فيه الانتقال إلى PM (Python 3.11–3.13) سحب الكود الجديد وتشغيل hermes update مرة أخرى. ويسلّم هذا التحديث العمل إلى عملية إكمال جديدة، فيزوّد PM المفسّر المثبّت على 3.14 من pm/lock.json، ويبني بيئة الاعتماديات عليه، ويعيد توجيه المشغّلات. بعد ذلك لا يُستخدم المفسّر القديم.

      ما يعنيه ذلك خارج hermes update:

      • pip install ., uv pip install ., pip install -e .، أو حزمة Homebrew/PyPI مبنية على Python 3.11–3.13، تُثبّت hermes-agent مع لا اعتماديات، ولا يمكن استيراد الحزمة. وطرق التثبيت هذه غير مدعومة؛ استخدم مُثبّت المصدر أو إصدارًا محزّمًا.
      • يرى بناء Nix خارج flake المستودع مجموعة الاعتماديات المقيدة بالعلامات نفسها، ويحتاج مفسّر 3.14.
      • يجب إصلاح مشغّل hermes الذي ما زال يشير إلى venv سابق للانتقال يجب إصلاحه باستخدام hermes update (أو python -m pm.cli install من النسخة المسحوبة)، لا بإعادة التثبيت في venv القديم.

      التثبيتات المُدارة عبر الصور (Docker): علامة المصدر (provenance marker)​

      تتضمن صور Docker المنشورة علامة صغيرة للقراءة فقط (/etc/hermes/image-provenance.json) تُعرّف نظام الملفات بشكل موثوق على أنه مُدار عبر صورة. ويرجع كلٌّ من hermes update, hermes update --check وزر Update في لوحة التحكم إلى هذه العلامة قبل المساس بأي شيء: ففي التثبيت المُدار عبر صورة، يرفض كلٌّ منها العملية بشكل نظيف (رمز الخروج 2)، ويطبع أمر التحديث الفعلي (docker pull nousresearch/hermes-agent:latest)، ويكتب إيصالًا من نوع refused حتى تتمكن أدوات إدارة الأسطول من رؤية أن المحاولة قد حدثت. وتكون الأولوية للعلامة حتى عندما تُربط نسخة مسحوبة من الكود المصدري (bind-mount) داخل الحاوية — إذ يستند الرفض إلى حقيقة نظام الملفات العامل فعليًا، لا إلى ما يبدو عليه. وتظل العلامة التالفة تؤدي إلى الرفض (fail-closed). أما التثبيتات المُدارة عبر Nix و apt فتُرفض عبر البوابة نفسها باستخدام آلية الاكتشاف الحالية.

      ملاحظة لمستخدمي Nix​

      لم يعد Nix مسار تثبيت مدعومًا بشكل صريح (الدعم بحسب الإمكان فقط) — راجع إعداد Nix. إذا ثبّتَّ Hermes عبر Nix flake ، فإن التحديثات تُدار من خلال مدير الحزم Nix:

      # Update the flake input
      nix flake update hermes-agent

      # Or rebuild with the latest
      nix profile upgrade hermes-agent

      تثبيتات Nix غير قابلة للتعديل (immutable) — ويتولى نظام الأجيال (generations) في Nix عملية التراجع:

      nix profile rollback

      راجع إعداد Nix لمزيد من التفاصيل.

      إلغاء التثبيت​

      hermes uninstall

      تتيح لك أداة إلغاء التثبيت خيار الاحتفاظ بملفات الإعدادات (hermes uninstall --dry-run قبل الإزالة. يمكن للإزالة الافتراضية الحفاظ على الإعدادات وبيانات المستخدم. ويزيل --full البيانات أيضًا. ويزيل --data بيانات المستخدم دون حذف الكود المملوك للحزمة. هذه الأوضاع مدمّرة؛ أنشئ نسخة احتياطية أولًا.

      بالنسبة إلى MSIX/Store ، استخدم Windows Settings → Apps → Installed apps. وفي macOS ، أغلق Hermes وانقل حزمة التطبيق إلى Trash. وتستخدم Docker و Nix و Termux المدير نفسه الذي ثبّتها. ولا يزيل مُزيل المصدر ملفات حزمها. وحذف البيانات منفصل عن إزالة الحزمة.

      هل تنتقل إلى جهاز جديد بدلًا من المغادرة؟

      خذ إعدادك معك قبل إزالة أي شيء: يلتقط hermes backup قبل إزالة التثبيت. يتضمن الأرشيف الكامل بيانات الاعتماد لكنه يستبعد بيئات التشغيل المنزّلة، وبيئات الاعتماديات، والتخزين المؤقت، و profiles المتصفح. راجع تقرير الملفات المتجاوزة قبل حذف بيانات المصدر. hermes profile export يحزم profile واحدًا دون بيانات اعتماد. راجع hermes backup مقابل hermes profile export.

      التحديث وإلغاء التثبيت

      التحديث​

      حدّث إلى أحدث إصدار بأمر واحد:

      hermes update

      يسحب هذا الأمر أحدث كود من main، ويحدّث الاعتماديات، ويطلب منك ضبط أي خيارات جديدة أُضيفت منذ آخر تحديث.

      نصيحة

      يكتشف hermes update خيارات الإعدادات الجديدة تلقائيًا ويطلب منك إضافتها. إذا تخطيت هذه المطالبة، يمكنك تنفيذ hermes config check يدويًا لعرض الخيارات الناقصة، ثم hermes config migrate لإضافتها تفاعليًا.

      إشعارات التحديث التلقائية​

      يمكن للتثبيتات المقيّدة بإصدار محدد (pinned) أو غير التفاعلية تعطيل الفحوصات التلقائية لإصدار CLI ولإشعارات التحديث في الشعار (banner):

      hermes config set updates.check false

      يُخفي هذا الإعداد إشعارات التحديث المخزّنة مؤقتًا، ويوقف طلبات الشبكة الخاصة بفحص التحديثات التلقائي، معًا. القيمة الافتراضية هي true. يظل التنفيذ الصريح لـ hermes update --check و hermes update يعمل؛ ولا يتحكم هذا الإعداد في أداة التحديث الخاصة بتطبيق Desktop.

      ما يحدث أثناء التحديث​

      عند تنفيذ hermes update، تجري الخطوات التالية:

      1. لقطة ما قبل التحديث (snapshot) — تُحفظ افتراضيًا لقطة خفيفة للحالة (تشمل بيانات الاقتران (pairing)، ومهام cron، و config.yaml، و .env، و auth.json، وملفات الحالة الأخرى التي تُعدَّل وقت التشغيل؛ ويُتخطى أي ملف منفرد يتجاوز حجمه 1 GiB حتى لا تُبطئ قاعدة بيانات جلسات كبيرة عملية التحديث أبدًا). ولأن استبدال الكود وإعادة تشغيل الـ gateways يمسّان كل profile، تُلتقط اللقطة نفسها لـ كل profile في التثبيت — كلٌّ منها في مجلد state-snapshots/ الخاص به — وتتحقق شبكة الأمان الخاصة بمهام cron بعد التحديث من كل profile مقابل لقطته الخاصة. يتحكم في ذلك الإعداد updates.pre_update_backup (القيمة quick افتراضيًا، و full لإنشاء ملف zip لكامل HERMES_HOME، و off للتعطيل). ويمكن الاستعادة عبر مسار استعادة اللقطات الموضح في اللقطات (Snapshots) والتراجع. اللقطات السريعة وسيلة للتعافي من فقدان الملفات، وليست ضمانًا للتراجع عن الكود — وللتراجع المتسق إلى نقطة زمنية محددة استخدم --backup (الوضع الكامل).
      2. Git pull — يسحب أحدث كود من الـ branch main ويحدّث الوحدات الفرعية (submodules)
      3. التحقق من صحة الصياغة بعد السحب + التراجع التلقائي — بعد السحب، يُصرّف Hermes الملفات الحرجة التسعة التي يستوردها كل استدعاء لـ hermes عند بدء التشغيل. وإذا تعذّر تحليل أي منها (مثل علامة تعارض دمج متبقية، أو ملف مقتطع عن طريق الخطأ)، ينفّذ Hermes الأمر git reset --hard <pre-pull-sha> لإرجاع التثبيت إلى حالته السابقة كي تبقى الـ shell قابلة للتشغيل. أعد تنفيذ hermes update بمجرد وصول الإصلاح إلى المستودع الأصلي (upstream).
      4. تثبيت الاعتماديات — ينفّذ uv pip install -e ".[all]" لجلب الاعتماديات الجديدة أو المعدّلة
      5. ترحيل الإعدادات — يكتشف خيارات الإعدادات الجديدة المضافة منذ إصدارك ويطلب منك ضبطها
      6. إعادة بناء Desktop (التجهيز ثم الاستبدال) — إذا كان تطبيق Hermes Desktop قد بُني من هذه النسخة المسحوبة (checkout)، فيُعاد بناؤه لتتطابق الواجهة الرسومية (GUI) مع الكود الجديد. تحزم عملية إعادة البناء التطبيق في مجلد تجهيز مؤقت بجوار apps/desktop/release/، وتتحقق من التطبيق المُجهَّز، ولا تعيد تسميته فوق البناء السابق إلا بعد ذلك. وإذا فشلت إعادة البناء في أي مرحلة — تنزيل Electron تالف، أو اعتمادية مفقودة، أو امتلاء القرص — يبقى التطبيق السابق كما هو وقابلًا للتشغيل؛ ويُبلغ التحديث عن ⚠ Update partially complete ويعيد hermes desktop محاولة إعادة البناء.
      7. إعادة تشغيل الـ gateway تلقائيًا — تُحدَّث الـ gateways العاملة بعد اكتمال التحديث ليسري الكود الجديد فورًا. ويُعاد تشغيل الـ gateways التي يديرها مدير خدمات (systemd على Linux، و launchd على macOS) عبر مدير الخدمات. أما الـ gateways اليدوية فيُعاد إطلاقها تلقائيًا عندما يتمكن Hermes من ربط الـ PID العامل بـ profile معيّن. وتُعامَل الـ backends الخاصة بـ hermes serve / hermes dashboard التي أُطلقت يدويًا (مثل عملية serve مرتبطة بالشبكة تشغّل Desktop بعيدًا) بالطريقة نفسها: يسجّل كل backend عنوان الربط الخاص به في سجل الإطلاق (spawn ledger) الخاص بالتثبيت عند بدء التشغيل، فيوقفه التحديث قبل استبدال الكود ثم يعيد إطلاقه بعد ذلك على المضيف والمنفذ نفسيهما — فيعيد Desktop البعيد الموجَّه إلى ذلك الـ endpoint الاتصال بدلًا من أن يبقى معزولًا. أما الـ backends التي يملكها تطبيق Desktop قيد التشغيل فتُترك لآلية إعادة الإطلاق الخاصة بالتطبيق.
      8. ترحيل Multiplex (التثبيتات متعددة الـ profiles) — بعد التحقق من أن الأسطول (fleet) يعمل على الكود الجديد، يُدمَج أي تثبيت يضم اثنين أو أكثر من الـ profiles التي لا تزال تشغّل gateway واحدًا لكل profile في gateway افتراضي واحد متعدد الإرسال (multiplexed) ما لم يمنع ذلك عائق (وهو ما يعادل hermes gateway migrate --multiplex --yes)؛ وإذا وُجد عائق (token بوت مشترك بين اثنين من الـ profiles، أو profile ثانوي يربط منفذًا دون مدخل /p/<profile>/) يطبع التحديث العوائق مع طرق إصلاحها ولا يغيّر شيئًا. لا تُمَسّ التثبيتات ذات الـ profile الواحد أبدًا. راجع الترحيل من gateway منفصل لكل profile.

      ملفات أداة التحديث المفقودة على Windows​

      إذا كان سكربت أداة التحديث المُصانة مفقودًا (مثلًا بعد أن يعزله برنامج مكافحة الفيروسات)، يفشل مُحوِّل التحديث القديم (legacy update forwarder) بدلًا من الإبلاغ عن تسليم ناجح. أصلح التثبيت وراجع تقرير العزل الصادر عن برنامج الحماية قبل إعادة المحاولة؛ ولا تعطّل الحماية من الفيروسات. وقبل الإبلاغ عن النجاح، تتحقق أداة التحديث المُصانة من استيراد CLI، وترويسة الملف التنفيذي لـ Windows، وترويسة ASAR ونقطة الدخول الرئيسية المحزومة، وملف HTML الخاص بالـ renderer وقابليته للقراءة مع نقطة دخول لوحدة محلية، وملفات الوحدات الأولية، وختم البناء الحالي. هذه فحوصات دنيا للمخرجات، وليست تدقيقًا كاملًا للاعتماديات ولا اختبارًا لإطلاق التطبيق/الـ backend. يُبلَّغ عن غياب Python قبل انتظار إغلاق Desktop؛ ولا يزال يُسمح بتشغيل إصلاح الاعتماديات كجزء من التحديث. يتحقق Electron من المتطلبات المسبقة للتسليم المُصان قبل إيقاف الـ backends عند وجود هذا التخطيط؛ وتظل تخطيطات أداة التحديث القديمة المسطّحة (legacy-flat) الحقيقية مدعومة، لذا لا يُكتشف كل ملف مفقود من ملفات أداة التحديث قبل إيقاف الـ backend.

      على Windows، إذا أُعيد فتح Desktop أثناء التحزيم، فإنه يُوقَف مجددًا مباشرةً قبل ترقية البناء المُجهَّز. يقتصر هذا التنظيف على الملفات التنفيذية الموجودة داخل شجرة إصدار Desktop في تلك النسخة المسحوبة؛ ولا تُوقَف التثبيتات غير ذات الصلة. وأي قفل متبقٍّ يؤدي إلى فشل ترقية البناء المُجهَّز بدلًا من تجاوز خطأ إعادة التسمية.

      التحديث من branch غير افتراضي: --branch​

      يتتبّع hermes update افتراضيًا origin/main. مرّر --branch <name> للتحديث من branch مختلف — وهذا مفيد لقنوات ضمان الجودة (QA)، أو branches الميزات، أو اختبار الإصدارات المرشحة (release candidates):

      hermes update --branch release-candidate
      hermes update --check --branch experimental   # preview behindness only

      إذا كانت نسختك المحلية على branch مختلف، يُجري Hermes تلقائيًا stash لأي عمل غير مُثبَّت بـ commit، ويحوّل HEAD إلى الـ branch المستهدف، ثم يسحب التحديثات. الـ branches غير الموجودة محليًا تُتتبَّع تلقائيًا من origin/<name> (git checkout -B <name> origin/<name>). أما الـ branches غير الموجودة في أي مكان فتفشل بشكل نظيف — إذ تُستعاد تغييراتك المحفوظة في stash قبل الخروج، فلا تبقى عالقًا في حالة غريبة أبدًا. ويُتخطى تلقائيًا منطق مزامنة الـ fork مع upstream المخصص لـ main فقط، وذلك على الـ branches الأخرى غير main.

      نسخة مسحوبة متوقفة على branch ميزة​

      إذا تُركت النسخة المسحوبة من الكود المصدري على branch ميزة (بفعل أدوات ما، أو تجربة worktree، أو checkout يدوي)، فإن hermes update يعيدها تلقائيًا إلى هدف التحديث كلما كانت شجرة العمل نظيفة:

      • الـ branch مدموج بالكامل (كل commit موجود أصلًا في origin/main — ولا يُبلغ git cherry عن أي شيء غير مدموج): يوضح التحديث ذلك — Checkout was parked on '<branch>' (fully merged) — switched back to main — ويبقى على main بعد ذلك.
      • الـ branch يحتوي على commits غير مدموجة لكن الشجرة نظيفة: يظل التحديث ينتقل إلى main حتى يتمكن من المتابعة — وهذا ما تعتمد عليه الجهات المستدعية غير التفاعلية (زر التحديث في تطبيق سطح المكتب، و /update في الـ gateway، و cron)، إذ لا سبيل لديها لحل حالة التخطي. تبقى الـ commits الخاصة بك كما هي: فالأمر git checkout لا يتخلص أبدًا من العمل المُثبَّت بـ commit، ويطبع التحديث إشعارًا واضحًا يذكر اسم الـ branch وعدد الـ commits، إضافةً إلى الأمر git checkout <branch> لاستئناف العمل لاحقًا.

      إذا كنت تشغّل branch مخصصًا عن قصد (تعديلات محلية تحافظ عليها فوق main)، فاضبط updates.parked_branch_strategy: update_in_place في config.yaml. عندها يدمج التحديث origin/main داخل الـ branch الخاص بك بدلًا من الانتقال بعيدًا عنه — فلا تتحرك النسخة المسحوبة أبدًا، وتبقى الـ commits الخاصة بك، ويتقدّم الكود العامل. يُستخدم fast-forward متى أمكن؛ وعند التباعد يُجرى دمج حقيقي خلف وسم أمان pre-update-<stamp>، مع التوقف بشكل نظيف (دون تغيير أي شيء) عند حدوث تعارض. ويعيد hermes update --switch-branch السلوك إلى مسار الانتقال لتشغيل واحد — وهذا مفيد على branch ميزة بعيد عن main يجب ألا تتراكم فيه commits دمج ناتجة عن التحديثات.

      عندما يحتوي الـ branch المتوقف على تغييرات غير مُثبَّتة (شجرة غير نظيفة)، فإن Hermes لا يلمسه. ويُعلَّم تحديث الكود بأنه SKIPPED مع تحذير واضح يذكر اسم الـ branch، ومدى تأخره عن origin/main، والأوامر الدقيقة لحل المشكلة — بدلًا من التظاهر بنجاح التحديث. ويعرض سطر الاكتمال دائمًا الـ branch الفعلي و HEAD (✓ Update complete! [main @ 30fcf9580]) لتتضح أي انحرافات بنظرة سريعة. اضبط updates.auto_switch_parked_branch: false في config.yaml لتعطيل الانتقال التلقائي كليًا (يظل تحذير التخطي يظهر).

      التغييرات المحلية في التحديثات غير التفاعلية​

      عند تنفيذ hermes update في الطرفية، يحفظ Hermes أي تغييرات غير مُثبَّتة في شجرة المصدر عبر stash، ثم يسحب التحديثات، ثم يسألك عمّا إذا كنت تريد استعادتها — تمامًا كما كان يفعل دائمًا. لا يتغير شيء في التحديثات التفاعلية.

      عندما يعمل التحديث دون طرفية — من زر "Update" في تطبيق سطح المكتب/المحادثة أو من تحديث يطلقه الـ gateway — فلا توجد مطالبة للرد عليها. ويحدد الإعداد updates.non_interactive_local_changes مصير تغييراتك المحفوظة في stash:

      # ~/.hermes/config.yaml
      updates:
        non_interactive_local_changes: stash   # default: keep + auto-restore
        # non_interactive_local_changes: discard  # throw local source edits away
      • stash (الافتراضي) — stash تلقائي، ثم سحب، ثم استعادة تلقائية لتغييراتك فوق الكود المحدَّث. لا يُفقد شيء؛ وإذا واجهت الاستعادة تعارضات، تُحفظ التغييرات في git stash لاستعادتها يدويًا.
      • discard — stash تلقائي ثم حذف الـ stash بعد السحب، فيصل التحديث دائمًا إلى شجرة نظيفة. لا تستخدم هذا الخيار إلا على الأجهزة التي لا تنوي فيها أبدًا الاحتفاظ بتعديلات محلية على الكود المصدري لـ Hermes. يعتمد هذا الخيار على حذف الـ stash (وليس git reset --hard + git clean -fd)، لذا لا تُمَس أبدًا المسارات المتجاهَلة مثل node_modules و venv ومخرجات البناء.

      في تطبيق سطح المكتب، يوجد هذا الإعداد في Settings → Advanced → In-App Update Local Changes.

      تحديثات Desktop لا تستعيد التغييرات تلقائيًا أبدًا. تستدعي أداة التحديث في تطبيق سطح المكتب الأمر hermes update --keep-stash: فتظل تعديلات المصدر المحلية تُحفظ في stash حتى يتمكن التحديث من المتابعة، لكنها لا يُعاد تطبيقها بعد ذلك — بل تبقى محفوظة في git stash ويطبع سجل التحديث الأمر الدقيق git stash apply <ref> لإعادتها. يمنع هذا انتقال التعديلات المحلية بصمت عبر تحديثات سطح المكتب وتسبّبها في تعطيل التثبيت المحدَّث حديثًا. (يظل non_interactive_local_changes: discard هو المُقدَّم إذا اخترت الحذف.) لاستعادة التغييرات المحفوظة يدويًا:

      cd ~/.hermes/hermes-agent   # or your install root
      git stash list --format='%gd %H %s'   # find the hermes-update-autostash entry
      git stash apply stash@{0}

      يمكنك أيضًا تمرير --keep-stash إلى hermes update في الطرفية إذا أردت سلوك عدم إعادة التطبيق نفسه في الوضع التفاعلي.

      معاينة فقط: hermes update --check​

      هل تريد معرفة ما إذا كان هناك تحديث متاح قبل السحب؟ نفّذ hermes update --check — فهو يجلب الـ commits ويقارنها مع origin/main. لا تُعدَّل أي ملفات، ولا يُعاد تشغيل أي gateway. وهو مفيد في السكربتات ومهام cron التي تعتمد على شرط "هل يوجد تحديث".

      معاينة الأسطول: hermes update --plan​

      قبل تحديث جهاز يشغّل عدة profiles أو خدمات، يطبع hermes update --plan خطة التحديث الكاملة دون تغيير أي شيء: نوع التثبيت (git checkout، أو صورة Docker، أو مُدار عبر Nix/apt)، وكل خدمة Hermes عاملة عبر جميع الـ profiles مع المشرف عليها (systemd، أو launchd، أو يدوي) وإصدار الكود الذي تقدّمه فعليًا، وآلية إعادة التشغيل التي ستُطبَّق على كل منها. وتظهر أيضًا الـ backends الخاصة بـ hermes serve / hermes dashboard التي أُطلقت يدويًا (من سجل الإطلاق spawn ledger)، مع endpoint الربط المسجَّل لها وآلية إعادة تشغيل من نوع "الإيقاف قبل استبدال الكود، ثم إعادة الإطلاق بوسائط الإطلاق المسجَّلة". وفي التثبيتات المُدارة عبر صورة أو حزمة، تُبلغ الخطة بأن التثبيت غير قابل للتحديث في مكانه وتذكر أمر التحديث الصحيح بدلًا من ذلك. هذا الأمر للقراءة فقط وآمن على أسطول قيد التشغيل.

      ويُضمَّن الجرد نفسه في إيصال كل تحديث فعلي (~/.hermes/logs/update_receipts/)، لذا يمكنك بعد التحديث مقارنة ما رصدته أداة التحديث بما نفّذته فعلًا.

      إيصالات التحديث وفحص إصدارات الأسطول​

      يكتب كل تشغيل لـ hermes update إيصالًا قابلًا للقراءة آليًا في ~/.hermes/logs/update_receipts/ (يُحتفظ بآخر 20 إيصالًا، ويشير latest.json دائمًا إلى أحدثها): خطة الأسطول قبل التحديث، وكل خطوة نُفّذت، وكل ما تُخطّي وسبب ذلك، ونتيجة إعادة تشغيل الـ gateway، ومصفوفة الإصدارات النهائية للأسطول. وبعد مرحلة إعادة التشغيل، تقارن أداة التحديث الكود العامل في كل gateway نشط بالنسخة المسحوبة المحدَّثة حديثًا، وتطبع مصفوفة لكل profile — ويُبلَّغ بوضوح عن أي gateway لا يزال يقدّم كود ما قبل التحديث مع أمر إعادة التشغيل الدقيق، وينتهي التحديث برمز خروج غير صفري حتى لا تعدّ أدوات الأتمتة أبدًا أسطولًا مختلط الإصدارات سليمًا. ويستعلم كلٌّ من --plan وفحص الأسطول من كل gateway عامل مباشرةً عبر مقبس التحكم المحلي الخاص به (gateway.sock في مجلد بيانات الـ profile، أو named pipe على Windows) عند توفره، فتأتي معلومات الإصدار والمشرف من الـ gateway نفسه؛ أما الـ gateways من الإصدارات الأقدم فلا تزال تُكتشف عبر ملفات حالتها كما كان سابقًا.

      عمليات إعادة تشغيل الـ gateway المتقطعة​

      إذا سحب تحديث سابق الكود لكنه لم يُكمل إعادة تشغيل الأسطول، فإن التشغيل التالي لـ hermes update يعيد المحاولة حتى لو كانت النسخة المسحوبة محدَّثة بالفعل. خلوّ فحص العمليات من النتائج لا يثبت التعافي: فقد لا يكون لوحدات systemd الفاشلة ومهام launchd المثبّتة PID نشط. ويُحتفظ بعلامة إعادة التشغيل المعلّقة إذا فشل اكتشاف المشرف، أو فشلت إعادة تشغيل، أو تعذّر التحقق من أن خدمة مطلوبة نشطة. ينتهي التحديث برمز خروج غير صفري ويُبلغ عن الخدمات المتأثرة؛ استعدها باستخدام الأوامر المطبوعة ثم أعد تنفيذ hermes update.

      لا يثبت إيصال تاريخي فاشل بحد ذاته أن الـ gateways لا تزال قديمة. إذ تتحقق تحذيرات بدء التشغيل وحالة الـ gateway، وكذلك عملية اللحاق بالتحديث، من الأسطول النشط قبل التصرف بناءً على التزامات إعادة تشغيل مصدرها الإيصال وحده. ويجب أن يكون لكل profile مسجَّل لـ gateway خلفٌ نشط على النسخة المسحوبة الحالية؛ ولا يمكن لـ gateway حالي غير ذي صلة أن يحل محل بيئة تشغيل مفقودة، أو متوقفة، أو مجهولة الإصدار، أو ليست gateway. لذلك يمكن لإعادة تشغيل يدوية للـ gateway أن تُنهي التحذير دون إعادة تسجيل تحديث فاشل على أنه ناجح. وتظل علامة الانتظار المنفصلة هي المرجع المعتمد لأنها قد تعود إلى تحديث أحدث متقطع لم يصل جرده إلى الإيصال قط.

      نسخة احتياطية كاملة قبل التحديث: --backup​

      بالنسبة إلى الـ profiles عالية القيمة (gateways الإنتاج، والتثبيتات المشتركة بين أعضاء الفريق)، يمكنك اختيار إنشاء نسخة احتياطية كاملة من HERMES_HOME قبل السحب (الإعدادات، والمصادقة، والجلسات، والمهارات، والاقتران):

      hermes update --backup

      أو اجعلها السلوك الافتراضي لكل تشغيل:

      # ~/.hermes/config.yaml
      updates:
        pre_update_backup: full

      الإعداد updates.pre_update_backup مفتاح تحكم واحد بثلاثة أوضاع: quick (الافتراضي — لقطة الحالة الخفيفة الموضحة أعلاه)، و full (اللقطة السريعة إضافةً إلى ملف zip كامل لـ HERMES_HOME؛ وقد يضيف ذلك دقائق عندما يكون المجلد كبيرًا)، و off (دون أي نسخة احتياطية قبل التحديث — ويفعل --no-backup الشيء نفسه لتشغيل واحد). لا تزال القيم المنطقية القديمة تعمل: true تعني full، و false تعني off.

      هل تنتقل إلى جهاز جديد بدلًا من ذلك؟

      تحمي النسخ الاحتياطية للتحديث عملية التحديث في المكان نفسه. أما إذا كنت تنقل إعدادك بالكامل إلى عتاد مختلف، فاستخدم hermes backup + hermes import بدلًا من ذلك — راجع تصدير Hermes إلى جهاز آخر و hermes backup مقابل hermes profile export.

      Windows: توجد عملية hermes.exe أخرى قيد التشغيل​

      على Windows، يرفض hermes update العمل إذا اكتشف عملية hermes.exe أخرى تُبقي الملف التنفيذي لنقطة الدخول (entry-point) في الـ venv مفتوحًا — وغالبًا ما تكون الـ backend الذي أطلقه تطبيق Hermes Desktop، أو جلسة REPL مفتوحة لـ hermes في طرفية أخرى، أو gateway قيد التشغيل:

      $ hermes update
      ✗ Another hermes.exe is running:
          PID 12345  hermes.exe

        Updating now would fail to overwrite ...\venv\Scripts\hermes.exe because
        Windows blocks REPLACE on a running executable.

        Close Hermes Desktop, exit any open `hermes` REPLs, and
        stop the gateway (`hermes gateway stop`) before retrying.
        Override with `hermes update --force` if you've already
        confirmed those processes will not write to the venv.

      أغلق العمليات المدرجة ثم أعد التشغيل. إذا كنت متأكدًا من أن العملية المتزامنة لن تتداخل (نادرًا — ويكون ذلك مفيدًا عادةً فقط عندما يُنسب shim خاص ببرنامج مكافحة الفيروسات خطأً)، فمرّر --force لتخطي الفحص. في هذه الحالة ستظل أداة التحديث تعيد محاولة إعادة تسمية ملف .exe مع تأخير أُسّي (exponential backoff)، وعند الأقفال المستعصية تجدول الاستبدال لإعادة التشغيل التالية عبر MoveFileEx(MOVEFILE_DELAY_UNTIL_REBOOT) حتى يكتمل التحديث.

      وثمة حماية ثانية منفصلة ترفض المساس بالـ venv ما دامت أي عملية تعمل من مفسّر Python الخاص به (الـ backend الخاص بتطبيق Desktop، أو gateway، أو Python REPL). إذ تُبقي هذه العمليات ملفات الامتدادات الأصلية (.pyd) مقفلة، ومزامنة الاعتماديات التي تتوقف في منتصفها بسبب خطأ رفض الوصول تترك التثبيت عالقًا بين إصدارين. هذه الحماية لا يتجاوزها --force؛ فإذا كنت متأكدًا من أن العمليات المكتشفة نتائج إيجابية كاذبة، فاستخدم الأمر الصريح hermes update --force-venv.

      إعادة إنشاء الـ venv على Windows عملية معاملاتية (transactional)​

      عندما يضطر المُثبّت على Windows إلى إعادة إنشاء venv موجود، فإنه ينقل المجلد القديم أولًا إلى اسم فريد من نوع venv.stale.*، ثم ينشئ البديل ويتحقق منه. ولا تُحذف الشجرة القديمة إلا بعد اكتمال تثبيت الاعتماديات ونجاح الاستيرادات الأساسية في الشجرة الجديدة — وحتى ذلك الحين تبقى مصدر التراجع (مسجَّلة في venv.pending-backup).

      إذا تعذّر إكمال النقل، يتوقف المُثبّت ويترك venv العامل دون تغيير. وإذا فشل uv أو أبلغ عن النجاح دون إنشاء المفسّر، يُنقل أي بديل جزئي إلى venv.failed.* ويُستعاد الـ venv السابق. يُبقي هذا فحوصات السلامة والعوائق قابلة للاستخدام بعد فشل التثبيت.

      قد يبقى مجلد venv.stale.* أو venv.failed.* عندما تظل عملية أخرى تمتلك مقبض ملف (file handle). أغلق Hermes Desktop والـ gateways وعمليات Python التي تستخدم التثبيت، ثم أعد محاولة التثبيت/التحديث؛ وتُنظَّف المجلدات المتروكة قدر الإمكان بعد نجاح إعادة الإنشاء.

      يبدو الناتج المتوقع كما يلي:

      $ hermes update
      Updating Hermes Agent...
      📥 Pulling latest code...
      Already up to date.  (or: Updating abc1234..def5678)
      📦 Updating dependencies...
      ✅ Dependencies updated
      🔍 Checking for new config options...
      ✅ Config is up to date  (or: Found 2 new options — running migration...)
      🔄 Restarting gateways...
      ✅ Gateway restarted
      ✅ Hermes Agent updated successfully!

      التحقق الموصى به بعد التحديث​

      يتولى hermes update مسار التحديث الرئيسي، لكن التحقق السريع يؤكد أن كل شيء اكتمل بشكل سليم:

      1. git status --short — إذا كانت الشجرة غير نظيفة على نحو غير متوقع، فافحصها قبل المتابعة
      2. hermes doctor — يفحص الإعدادات والاعتماديات وسلامة الخدمات
      3. hermes --version — تأكد من أن الإصدار ارتفع كما هو متوقع
      4. إذا كنت تستخدم الـ gateway: hermes gateway status
      5. إذا أبلغ doctor عن مشكلات npm audit: نفّذ npm audit fix في المجلد المشار إليه
      شجرة عمل غير نظيفة بعد التحديث

      إذا أظهر git status --short تغييرات غير متوقعة بعد hermes update، فتوقف وافحصها قبل المتابعة. يعني هذا عادةً أن تعديلات محلية أُعيد تطبيقها فوق الكود المحدَّث، أو أن خطوة الاعتماديات حدّثت ملفات القفل (lockfiles).

      إذا انقطع اتصال الطرفية في منتصف التحديث​

      يحمي hermes update نفسه من فقدان الطرفية عن غير قصد:

      • يتجاهل التحديث الإشارة SIGHUP، لذا فإن إغلاق جلسة SSH أو نافذة الطرفية لم يعد يُنهيه في منتصف التثبيت. وترث العمليات الفرعية لـ pip و git هذه الحماية، فلا يمكن أن تبقى بيئة Python مثبّتة جزئيًا بسبب انقطاع الاتصال.
      • تُنسخ جميع المخرجات إلى ~/.hermes/logs/update.log أثناء تشغيل التحديث. إذا اختفت الطرفية، فأعد الاتصال وافحص السجل لمعرفة ما إذا كان التحديث قد اكتمل وما إذا نجحت إعادة تشغيل الـ gateway:
      tail -f ~/.hermes/logs/update.log
      • لا يزال Ctrl-C (SIGINT) وإيقاف تشغيل النظام (SIGTERM) يُحترمان — فهما إلغاءان مقصودان، وليسا حادثين عرضيين.

      لم تعد بحاجة إلى تغليف hermes update داخل screen أو tmux لتجاوز انقطاع الطرفية.

      التحقق من إصدارك الحالي​

      hermes --version

      قارنه بأحدث إصدار في صفحة الإصدارات على GitHub.

      التحديث من منصات المراسلة​

      يمكنك أيضًا التحديث مباشرةً من Telegram أو Discord أو Slack أو WhatsApp أو Teams بإرسال:

      /update

      يسحب هذا أحدث كود، ويحدّث الاعتماديات، ويعيد تشغيل الـ gateways العاملة. سيصبح البوت غير متصل لفترة وجيزة أثناء إعادة التشغيل (عادةً 5–15 ثانية) ثم يستأنف عمله.

      التحديث اليدوي​

      إذا ثبّتَّ Hermes يدويًا (وليس عبر المُثبّت السريع):

      cd /path/to/hermes-agent
      # Activate the venv you created during install (outside the source tree)
      export VIRTUAL_ENV="$HOME/.hermes/venvs/hermes-dev"
      export PATH="$VIRTUAL_ENV/bin:$PATH"

      # Pull latest code
      git pull origin main

      # Reinstall (picks up new dependencies)
      uv pip install -e ".[all]"

      # Check for new config options
      hermes config check
      hermes config migrate   # Interactively add any missing options

      تعليمات التراجع​

      إذا تسبب تحديث في مشكلة، يمكنك التراجع إلى إصدار سابق:

      cd /path/to/hermes-agent

      # List recent versions
      git log --oneline -10

      # Roll back to a specific commit
      git checkout <commit-hash>
      uv pip install -e ".[all]"

      # Restart the gateway if running
      hermes gateway restart

      للتراجع إلى وسم إصدار محدد (ضع مكانه وسمك السابق — مثل إصدار حديث كـ v2026.5.16، أو أي وسم أقدم من ناتج git tag --sort=-version:refname):

      git checkout vX.Y.Z
      uv pip install -e ".[all]"
      تحذير

      قد يسبب التراجع عدم توافق في الإعدادات إذا أُضيفت خيارات جديدة. نفّذ hermes config check بعد التراجع، واحذف أي خيارات غير معروفة من config.yaml إذا واجهت أخطاء.

      التثبيتات المُدارة عبر الصور (Docker): علامة المصدر (provenance marker)​

      تتضمن صور Docker المنشورة علامة صغيرة للقراءة فقط (/etc/hermes/image-provenance.json) تُعرّف نظام الملفات بشكل موثوق على أنه مُدار عبر صورة. ويرجع كلٌّ من hermes update و hermes update --check وزر Update في لوحة التحكم إلى هذه العلامة قبل المساس بأي شيء: ففي التثبيت المُدار عبر صورة، يرفض كلٌّ منها العملية بشكل نظيف (رمز الخروج 2)، ويطبع أمر التحديث الفعلي (docker pull nousresearch/hermes-agent:latest)، ويكتب إيصالًا من نوع refused حتى تتمكن أدوات إدارة الأسطول من رؤية أن المحاولة قد حدثت. وتكون الأولوية للعلامة حتى عندما تُربط نسخة مسحوبة من الكود المصدري (bind-mount) داخل الحاوية — إذ يستند الرفض إلى حقيقة نظام الملفات العامل فعليًا، لا إلى ما يبدو عليه. وتظل العلامة التالفة تؤدي إلى الرفض (fail-closed). أما التثبيتات المُدارة عبر Nix و apt فتُرفض عبر البوابة نفسها باستخدام آلية الاكتشاف الحالية.

      ملاحظة لمستخدمي Nix​

      لم يعد Nix مسار تثبيت مدعومًا بشكل صريح (الدعم بحسب الإمكان فقط) — راجع إعداد Nix. إذا ثبّتَّ Hermes عبر Nix flake، فإن التحديثات تُدار من خلال مدير الحزم Nix:

      # Update the flake input
      nix flake update hermes-agent

      # Or rebuild with the latest
      nix profile upgrade hermes-agent

      تثبيتات Nix غير قابلة للتعديل (immutable) — ويتولى نظام الأجيال (generations) في Nix عملية التراجع:

      nix profile rollback

      راجع إعداد Nix لمزيد من التفاصيل.

      إلغاء التثبيت​

      hermes uninstall

      تتيح لك أداة إلغاء التثبيت خيار الاحتفاظ بملفات الإعدادات (~/.hermes/) لإعادة التثبيت مستقبلًا.

      هل تنتقل إلى جهاز جديد بدلًا من المغادرة؟

      خذ إعدادك معك قبل إزالة أي شيء: يلتقط hermes backup مجلد ~/.hermes بالكامل بما في ذلك بيانات الاعتماد، بينما يحزم hermes profile export profile واحدًا مع استبعاد بيانات الاعتماد عمدًا (لذا فإن التصدير وحده ليس نسخة احتياطية كاملة). راجع hermes backup مقابل hermes profile export.

      إلغاء التثبيت يدويًا​

      rm -f ~/.local/bin/hermes
      rm -rf /path/to/hermes-agent
      rm -rf ~/.hermes            # Optional — keep if you plan to reinstall
      معلومة

      إذا ثبّتَّ الـ gateway كخدمة نظام، فأوقفه وعطّله أولًا:

      hermes gateway stop
      # Linux: systemctl --user disable hermes-gateway
      # macOS: launchctl remove ai.hermes.gateway

      التعليقات التلقائية على GitHub PR باستخدام Webhooks

      يرشدك هذا الدليل خطوة بخطوة إلى ربط Hermes Agent بـ GitHub بحيث يجلب تلقائيًا الـ diff الخاص بأي pull request، ويحلّل تغييرات الكود، ثم ينشر تعليقًا — ويُطلَق ذلك بحدث webhook دون أي prompt يدوي.

      عند فتح PR أو تحديثه، يرسل GitHub طلب webhook من نوع POST إلى نسخة Hermes لديك. يشغّل Hermes الوكيل بـ prompt يوجّهه إلى جلب الـ diff عبر gh CLI، ثم يُنشر الرد في سلسلة نقاش الـ PR.

      هل تريد إعدادًا أبسط دون endpoint عام؟

      إذا لم يكن لديك URL عام أو كنت تريد البدء بسرعة فحسب، فراجع بناء وكيل لمراجعة GitHub PR — إذ يستخدم مهام cron لاستطلاع طلبات PR وفق جدول زمني، ويعمل خلف NAT والجدران النارية.

      الوثائق المرجعية

      للاطلاع على المرجع الكامل لمنصة webhook (جميع خيارات الإعدادات، وأنواع التسليم، والاشتراكات الديناميكية، ونموذج الأمان)، راجع Webhooks.

      خطر حقن الـ Prompt (Prompt injection)

      تحتوي حمولات webhook على بيانات يتحكم فيها المهاجم — فقد تتضمن عناوين PR ورسائل commit والأوصاف تعليمات خبيثة. عندما يكون endpoint الخاص بـ webhook مكشوفًا على الإنترنت، شغّل الـ gateway في بيئة معزولة (sandbox) مثل Docker أو SSH backend. راجع قسم الأمان أدناه.

      المتطلبات المسبقة​

      • تثبيت Hermes Agent وتشغيله (hermes gateway)
      • تثبيت gh CLI ومصادقته على الجهاز المضيف للـ gateway (gh auth login)
      • URL عام يمكن الوصول إليه لنسخة Hermes لديك (راجع الاختبار المحلي باستخدام ngrok إذا كنت تشغّله محليًا)
      • صلاحية مسؤول (Admin) على مستودع GitHub (مطلوبة لإدارة webhooks)

      الخطوة 1 — تفعيل منصة webhook​

      أضف ما يلي إلى الملف ~/.hermes/config.yaml:

      platforms:
        webhook:
          enabled: true
          extra:
            port: 8644          # default; change if another service occupies this port
            rate_limit: 30      # max requests per minute per route (not a global cap)

            routes:
              github-pr-review:
                secret: "your-webhook-secret-here"   # must match the GitHub webhook secret exactly
                events:
                  - pull_request

                # The agent is instructed to fetch the actual diff before reviewing.
                # {number} and {repository.full_name} are resolved from the GitHub payload.
                prompt: |
                  A pull request event was received (action: {action}).

                  PR #{number}: {pull_request.title}
                  Author: {pull_request.user.login}
                  Branch: {pull_request.head.ref} → {pull_request.base.ref}
                  Description: {pull_request.body}
                  URL: {pull_request.html_url}

                  If the action is "closed" or "labeled", stop here and do not post a comment.

                  Otherwise:
                  1. Run: gh pr diff {number} --repo {repository.full_name}
                  2. Review the code changes for correctness, security issues, and clarity.
                  3. Write a concise, actionable review comment and post it.

                deliver: github_comment
                deliver_extra:
                  repo: "{repository.full_name}"
                  pr_number: "{number}"

      الحقول الرئيسية:

      الحقلالوصف
      secret (على مستوى المسار)سرّ HMAC لهذا المسار (route). يُستخدم extra.secret العام بديلًا عنه إذا حُذف.
      eventsقائمة بقيم الترويسة X-GitHub-Event المقبولة. القائمة الفارغة = قبول الكل.
      promptقالب؛ تُستبدل {field} و {nested.field} بقيمها من حمولة GitHub.
      deliverتنشر القيمة github_comment عبر gh pr comment. أما log فتكتفي بالكتابة في سجل الـ gateway.
      deliver_extra.repoتُستبدل بقيمة مثل org/repo من الحمولة.
      deliver_extra.pr_numberتُستبدل برقم الـ PR من الحمولة.
      الحمولة لا تحتوي على الكود

      تتضمن حمولة webhook من GitHub البيانات الوصفية للـ PR (العنوان، والوصف، وأسماء الـ branches، والروابط) لكنها لا تتضمن الـ diff. يوجّه الـ prompt أعلاه الوكيل إلى تشغيل gh pr diff لجلب التغييرات الفعلية. الـ toolset الافتراضي hermes-webhook مقيّد عمدًا (البحث في الويب/الاستخراج، والرؤية، والاستيضاح — دون طرفية) لأن حمولات webhook قد تحمل محتوى غير موثوق. للسماح لهذا المسار بتشغيل gh، أضف منحًا لـ toolset خاصًا بالمسار: toolsets: ["terminal", "web"] في إعدادات المسار — راجع Toolsets لكل مسار.

      الخطوة 2 — تشغيل الـ gateway​

      hermes gateway

      من المفترض أن ترى:

      [webhook] Listening on 0.0.0.0:8644 — routes: github-pr-review

      تحقّق من أنه يعمل:

      curl http://localhost:8644/health
      # {"status": "ok", "platform": "webhook"}

      الخطوة 3 — تسجيل الـ webhook على GitHub​

      1. انتقل إلى مستودعك → Settings → Webhooks → Add webhook
      2. املأ الحقول التالية:
        • Payload URL: https://your-public-url.example.com/webhooks/github-pr-review
        • Content type: application/json
        • Secret: القيمة نفسها التي ضبطتها لـ secret في إعدادات المسار
        • Which events? → اختر Select individual events → حدّد Pull requests
      3. انقر Add webhook

      سيرسل GitHub فورًا حدث ping لتأكيد الاتصال. يُتجاهل هذا الحدث بأمان — لأن ping ليس ضمن قائمة events لديك — ويُعيد {"status": "ignored", "event": "ping"}. ولا يُسجَّل إلا على مستوى DEBUG، لذا لن يظهر في وحدة التحكم عند مستوى السجل الافتراضي.

      الخطوة 4 — فتح PR تجريبي​

      أنشئ branch، وادفع تغييرًا (push)، ثم افتح PR. خلال 30–90 ثانية (بحسب حجم الـ PR والنموذج)، من المفترض أن ينشر Hermes تعليق مراجعة.

      لمتابعة تقدّم الوكيل في الوقت الفعلي:

      tail -f "${HERMES_HOME:-$HOME/.hermes}/logs/gateway.log"

      الاختبار المحلي باستخدام ngrok​

      إذا كان Hermes يعمل على حاسوبك المحمول، فاستخدم ngrok لإتاحته للوصول الخارجي:

      ngrok http 8644

      انسخ الرابط https://...ngrok-free.app واستخدمه بوصفه Payload URL في GitHub. في الفئة المجانية من ngrok يتغيّر الرابط في كل مرة يُعاد فيها تشغيل ngrok — لذا حدّث الـ webhook على GitHub في كل جلسة. أما حسابات ngrok المدفوعة فتحصل على نطاق ثابت.

      يمكنك إجراء اختبار سريع (smoke test) لمسار ثابت مباشرةً باستخدام curl — دون الحاجة إلى حساب GitHub أو PR حقيقي.

      استخدم deliver: log عند الاختبار محليًا

      غيّر deliver: github_comment إلى deliver: log في إعداداتك أثناء الاختبار. وإلا فسيحاول الوكيل نشر تعليق على المستودع الوهمي org/repo#99 الموجود في الحمولة التجريبية، وستفشل المحاولة. أعد القيمة إلى deliver: github_comment بعد أن تطمئن إلى مخرجات الـ prompt.

      SECRET="your-webhook-secret-here"
      BODY='{"action":"opened","number":99,"pull_request":{"title":"Test PR","body":"Adds a feature.","user":{"login":"testuser"},"head":{"ref":"feat/x"},"base":{"ref":"main"},"html_url":"https://github.com/org/repo/pull/99"},"repository":{"full_name":"org/repo"}}'
      SIG=$(printf '%s' "$BODY" | openssl dgst -sha256 -hmac "$SECRET" -hex | awk '{print "sha256="$2}')

      curl -s -X POST http://localhost:8644/webhooks/github-pr-review \
        -H "Content-Type: application/json" \
        -H "X-GitHub-Event: pull_request" \
        -H "X-Hub-Signature-256: $SIG" \
        -d "$BODY"
      # Expected: {"status":"accepted","route":"github-pr-review","event":"pull_request","delivery_id":"..."}

      ثم راقب تشغيل الوكيل:

      tail -f "${HERMES_HOME:-$HOME/.hermes}/logs/gateway.log"
      ملاحظة

      لا يعمل hermes webhook test <name> إلا مع الاشتراكات الديناميكية المُنشأة باستخدام hermes webhook subscribe. ولا يقرأ المسارات من config.yaml.

      التصفية على إجراءات محددة​

      يرسل GitHub أحداث pull_request لإجراءات كثيرة: opened، و synchronize، و reopened، و closed، و labeled، وغيرها. تُصفّي قائمة events بحسب قيمة الترويسة X-GitHub-Event، ويمكن لـ filters على مستوى المسار تضييق النطاق بحسب حقول الحمولة مثل action.

      يتعامل الـ prompt في الخطوة 1 مع ذلك مسبقًا، إذ يوجّه الوكيل إلى التوقف مبكرًا عند أحداث closed و labeled.

      الوكيل يظل يعمل ويستهلك tokens

      تمنع تعليمة "stop here" إجراء مراجعة ذات معنى، لكن الوكيل يظل يعمل حتى النهاية مع كل حدث pull_request أيًّا كان الإجراء. لذا يُفضَّل التصفية قبل أن يستيقظ الوكيل:

      filters:
        - field: "action"
          in: ["opened", "synchronize", "reopened"]

      وفي المستودعات كثيفة النشاط، لا يزال بإمكانك التصفية مسبقًا عبر سير عمل GitHub Actions يستدعي رابط الـ webhook الخاص بك بشكل مشروط.

      لا توجد صياغة Jinja2 ولا صياغة قوالب شرطية. {field} و {nested.field} هما الاستبدالان الوحيدان المدعومان. وأي شيء آخر يُمرَّر إلى الوكيل حرفيًا كما هو.

      استخدام مهارة لتوحيد أسلوب المراجعة​

      حمّل مهارة Hermes لمنح الوكيل شخصية مراجعة متّسقة. أضف skills إلى مسارك داخل platforms.webhook.extra.routes في config.yaml:

      platforms:
        webhook:
          enabled: true
          extra:
            routes:
              github-pr-review:
                secret: "your-webhook-secret-here"
                events: [pull_request]
                prompt: |
                  A pull request event was received (action: {action}).
                  PR #{number}: {pull_request.title} by {pull_request.user.login}
                  URL: {pull_request.html_url}

                  If the action is "closed" or "labeled", stop here and do not post a comment.

                  Otherwise:
                  1. Run: gh pr diff {number} --repo {repository.full_name}
                  2. Review the diff using your review guidelines.
                  3. Write a concise, actionable review comment and post it.
                skills:
                  - review
                deliver: github_comment
                deliver_extra:
                  repo: "{repository.full_name}"
                  pr_number: "{number}"

      ملاحظة: لا تُحمَّل إلا أول مهارة موجودة في القائمة. لا يجمع Hermes عدة مهارات معًا — وتُتجاهل الإدخالات اللاحقة.

      إرسال الردود إلى Slack أو Discord بدلًا من ذلك​

      استبدل الحقلين deliver و deliver_extra داخل مسارك بالمنصة المستهدفة:

      # Inside platforms.webhook.extra.routes.<route-name>:

      # Slack
      deliver: slack
      deliver_extra:
        chat_id: "C0123456789"   # Slack channel ID (omit to use the configured home channel)

      # Discord
      deliver: discord
      deliver_extra:
        chat_id: "987654321012345678"  # Discord channel ID (omit to use home channel)

      يجب أيضًا أن تكون المنصة المستهدفة مفعّلة ومتصلة في الـ gateway. وإذا حُذف chat_id، يُرسل الرد إلى القناة الرئيسية (home channel) المضبوطة لتلك المنصة.

      قيم deliver الصالحة: log · github_comment · telegram · discord · slack · signal · sms

      دعم GitLab​

      يعمل المحوّل (adapter) نفسه مع GitLab. يستخدم GitLab الترويسة X-Gitlab-Token للمصادقة (مطابقة نصية بسيطة، وليس HMAC) — ويتعامل Hermes مع الحالتين تلقائيًا.

      لتصفية الأحداث، يضبط GitLab الترويسة X-GitLab-Event على قيم مثل Merge Request Hook، و Push Hook، و Pipeline Hook. استخدم قيمة الترويسة كما هي تمامًا في events:

      events:
        - Merge Request Hook

      تختلف حقول حمولة GitLab عن حقول GitHub — فمثلًا {object_attributes.title} لعنوان الـ MR و {object_attributes.iid} لرقم الـ MR. أسهل طريقة لاكتشاف البنية الكاملة للحمولة هي زر Test في إعدادات الـ webhook على GitLab، مع سجل Recent Deliveries. وبدلًا من ذلك، احذف prompt من إعدادات المسار — وعندها سيمرّر Hermes الحمولة الكاملة كـ JSON منسّق مباشرةً إلى الوكيل، وسيصف رد الوكيل (الظاهر في سجل الـ gateway مع deliver: log) بنيتها.

      ملاحظات الأمان​

      • لا تستخدم INSECURE_NO_AUTH أبدًا في بيئة الإنتاج — فهو يعطّل التحقق من التوقيع كليًا، وهو مخصص للتطوير المحلي فقط.
      • بدّل سرّ الـ webhook بشكل دوري، وحدّثه في كلٍّ من GitHub (إعدادات الـ webhook) والملف config.yaml.
      • حدّ المعدل (Rate limiting) هو 30 طلبًا في الدقيقة لكل مسار افتراضيًا (قابل للضبط عبر extra.rate_limit). وتجاوزه يُعيد 429.
      • عمليات التسليم المكررة (إعادات محاولة الـ webhook) تُزال عبر cache للتكرار الآمن (idempotency) مدته ساعة واحدة. مفتاح الـ cache هو X-GitHub-Delivery إن وُجد، ثم X-Request-ID، ثم طابع زمني بالمللي ثانية. وعندما لا تُضبط أيٌّ من ترويستَي معرّف التسليم، لا تُزال إعادات المحاولة المكررة.
      • حقن الـ Prompt: عناوين PR وأوصافها ورسائل commit يتحكم فيها المهاجم. وقد تحاول طلبات PR الخبيثة التلاعب بإجراءات الوكيل. شغّل الـ gateway في بيئة معزولة (Docker، أو VM) عندما يكون مكشوفًا على الإنترنت العام.

      استكشاف الأخطاء وإصلاحها​

      العَرَضما يجب التحقق منه
      401 Invalid signatureالسرّ في config.yaml لا يطابق سرّ الـ webhook على GitHub
      404 Unknown routeاسم المسار في الرابط لا يطابق المفتاح في routes:
      429 Rate limit exceededتجاوزت 30 طلبًا في الدقيقة للمسار — وهو أمر شائع عند إعادة تسليم أحداث تجريبية من واجهة GitHub؛ انتظر دقيقة أو ارفع extra.rate_limit
      لم يُنشر أي تعليقgh غير مثبّت، أو غير موجود في PATH، أو غير مُصادَق (gh auth login)
      الوكيل يعمل لكن دون تعليقراجع سجل الـ gateway — فإذا كانت مخرجات الوكيل فارغة أو مجرد "SKIP"، تظل محاولة التسليم تُجرى
      المنفذ مستخدم بالفعلغيّر extra.port في config.yaml
      الوكيل يعمل لكنه يراجع وصف الـ PR فقطالـ prompt لا يتضمن تعليمة gh pr diff — فالـ diff غير موجود في حمولة الـ webhook
      لا يظهر حدث pingالأحداث المتجاهَلة تُعيد {"status":"ignored","event":"ping"} على مستوى سجل DEBUG فقط — راجع سجل التسليم في GitHub (repo → Settings → Webhooks → الـ webhook الخاص بك → Recent Deliveries)

      تبويب Recent Deliveries في GitHub (repo → Settings → Webhooks → الـ webhook الخاص بك) يعرض ترويسات الطلب الدقيقة، والحمولة، وحالة HTTP، ونص الاستجابة لكل عملية تسليم. وهو أسرع طريقة لتشخيص حالات الفشل دون الحاجة إلى فتح سجلات الخادم.

      المرجع الكامل للإعدادات​

      platforms:
        webhook:
          enabled: true
          extra:
            port: 8644               # listen port (default: 8644)
            secret: ""               # optional global fallback secret
            rate_limit: 30           # requests per minute per route
            max_body_bytes: 1048576  # payload size limit in bytes (default: 1 MB)

            routes:
              <route-name>:
                secret: "required-per-route"
                events: []            # [] = accept all; otherwise list X-GitHub-Event values
                prompt: ""            # {field} / {nested.field} resolved from payload
                skills: []            # first matching skill is loaded (only one)
                deliver: "log"        # log | github_comment | telegram | discord | slack | signal | sms
                deliver_extra: {}     # repo + pr_number for github_comment; chat_id for others

      ما التالي؟​

      • مراجعات PR المعتمدة على Cron — استطلع طلبات PR وفق جدول زمني، دون الحاجة إلى endpoint عام
      • مرجع Webhook — المرجع الكامل لإعدادات منصة webhook
      • بناء إضافة (Plugin) — غلّف منطق المراجعة في إضافة قابلة للمشاركة
      • Profiles — شغّل profile مخصصًا للمراجعة بذاكرته وإعداداته الخاصة

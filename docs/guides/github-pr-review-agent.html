      درس تطبيقي: بناء وكيل لمراجعة GitHub PR

      المشكلة: يفتح فريقك طلبات PR أسرع مما تستطيع مراجعته. تبقى طلبات PR معلّقة لأيام بانتظار من يطّلع عليها. يدمج المطوّرون المبتدئون أخطاءً لأن أحدًا لم يجد وقتًا للتحقق منها. وتقضي صباحاتك في اللحاق بالـ diffs بدلًا من البناء.

      الحل: وكيل ذكاء اصطناعي (AI agent) يراقب مستودعاتك على مدار الساعة، ويراجع كل PR جديد بحثًا عن الأخطاء والمشكلات الأمنية وجودة الكود، ثم يرسل إليك ملخّصًا — فلا تقضي وقتك إلا في طلبات PR التي تحتاج فعلًا إلى حكم بشري.

      ما الذي ستبنيه:

      ┌───────────────────────────────────────────────────────────────────┐
      │                                                                   │
      │   Cron Timer  ──▶  Hermes Agent  ──▶  GitHub API  ──▶  Review     │
      │   (every 2h)       + gh CLI           (PR diffs)       delivery   │
      │                    + skill                             (Telegram, │
      │                    + memory                            Discord,   │
      │                                                        local)     │
      │                                                                   │
      └───────────────────────────────────────────────────────────────────┘

      يستخدم هذا الدليل مهام cron لاستطلاع طلبات PR وفق جدول زمني — دون الحاجة إلى خادم أو endpoint عام. ويعمل خلف NAT والجدران النارية.

      هل تريد مراجعات فورية بدلًا من ذلك؟

      إذا كان لديك endpoint عام متاح، فراجع التعليقات التلقائية على GitHub PR باستخدام Webhooks — إذ يرسل GitHub الأحداث إلى Hermes فورًا عند فتح طلبات PR أو تحديثها.

      المتطلبات المسبقة​

      • تثبيت Hermes Agent — راجع دليل التثبيت
      • تشغيل الـ Gateway لتنفيذ مهام cron: 
        hermes gateway install   # Install as a service
        # or
        hermes gateway           # Run in foreground
      • تثبيت GitHub CLI (gh) ومصادقته: 
        # Install
        brew install gh        # macOS
        sudo apt install gh    # Ubuntu/Debian

        # Authenticate
        gh auth login
      • إعداد المراسلة (اختياري) — Telegram أو Discord
      لا تستخدم المراسلة؟ لا مشكلة

      استخدم deliver: "local" لحفظ المراجعات في ~/.hermes/cron/output/. وهو خيار ممتاز للاختبار قبل ربط الإشعارات.

      الخطوة 1: التحقق من الإعداد​

      تأكد من أن Hermes يستطيع الوصول إلى GitHub. ابدأ محادثة:

      hermes

      اختبر ذلك بأمر بسيط:

      Run: gh pr list --repo NousResearch/hermes-agent --state open --limit 3

      من المفترض أن ترى قائمة بطلبات PR المفتوحة. إذا نجح ذلك، فأنت جاهز.

      الخطوة 2: تجربة مراجعة يدوية​

      وأنت لا تزال في المحادثة، اطلب من Hermes مراجعة PR حقيقي:

      Review this pull request. Read the diff, check for bugs, security issues,
      and code quality. Be specific about line numbers and quote problematic code.

      Run: gh pr diff 3888 --repo NousResearch/hermes-agent

      سيقوم Hermes بما يلي:

      1. تنفيذ gh pr diff لجلب تغييرات الكود
      2. قراءة الـ diff بأكمله
      3. إنتاج مراجعة منظّمة تتضمن ملاحظات محددة

      إذا كنت راضيًا عن الجودة، فقد حان وقت أتمتتها.

      الخطوة 3: إنشاء مهارة للمراجعة​

      تمنح المهارة (skill) لـ Hermes إرشادات مراجعة متّسقة تستمر عبر الجلسات وتشغيلات cron. ومن دونها تتفاوت جودة المراجعة.

      mkdir -p ~/.hermes/skills/code-review

      أنشئ الملف ~/.hermes/skills/code-review/SKILL.md:

      ---
      name: code-review
      description: Review pull requests for bugs, security issues, and code quality
      ---

      # Code Review Guidelines

      When reviewing a pull request:

      ## What to Check
      1. **Bugs** — Logic errors, off-by-one, null/undefined handling
      2. **Security** — Injection, auth bypass, secrets in code, SSRF
      3. **Performance** — N+1 queries, unbounded loops, memory leaks
      4. **Style** — Naming conventions, dead code, missing error handling
      5. **Tests** — Are changes tested? Do tests cover edge cases?

      ## Output Format
      For each finding:
      - **File:Line** — exact location
      - **Severity** — Critical / Warning / Suggestion
      - **What's wrong** — one sentence
      - **Fix** — how to fix it

      ## Rules
      - Be specific. Quote the problematic code.
      - Don't flag style nitpicks unless they affect readability.
      - If the PR looks good, say so. Don't invent problems.
      - End with: APPROVE / REQUEST_CHANGES / COMMENT

      تحقّق من تحميلها — شغّل hermes ومن المفترض أن ترى code-review في قائمة المهارات عند بدء التشغيل.

      الخطوة 4: تعليمه أعراف فريقك​

      هذا ما يجعل المراجِع مفيدًا فعلًا. ابدأ جلسة وعلّم Hermes معايير فريقك:

      Remember: In our backend repo, we use Python with FastAPI.
      All endpoints must have type annotations and Pydantic models.
      We don't allow raw SQL — only SQLAlchemy ORM.
      Test files go in tests/ and must use pytest fixtures.
      Remember: In our frontend repo, we use TypeScript with React.
      No `any` types allowed. All components must have props interfaces.
      We use React Query for data fetching, never useEffect for API calls.

      تبقى هذه الذكريات محفوظة بشكل دائم — وسيطبّق المراجِع أعرافك دون أن تضطر إلى تذكيره في كل مرة.

      الخطوة 5: إنشاء مهمة Cron المؤتمتة​

      الآن اربط كل شيء معًا. أنشئ مهمة cron تعمل كل ساعتين:

      hermes cron create "0 */2 * * *" \
        "Check for new open PRs and review them.

      Repos to monitor:
      - myorg/backend-api
      - myorg/frontend-app

      Steps:
      1. Run: gh pr list --repo REPO --state open --limit 5 --json number,title,author,createdAt
      2. For each PR created or updated in the last 4 hours:
         - Run: gh pr diff NUMBER --repo REPO
         - Review the diff using the code-review guidelines
      3. Format output as:

      ## PR Reviews — today

      ### [repo] #[number]: [title]
      **Author:** [name] | **Verdict:** APPROVE/REQUEST_CHANGES/COMMENT
      [findings]

      If no new PRs found, say: No new PRs to review." \
        --name "pr-review" \
        --deliver telegram \
        --skill code-review

      تحقّق من جدولتها:

      hermes cron list

      جداول زمنية مفيدة أخرى​

      الجدول الزمنيالتوقيت
      0 */2 * * *كل ساعتين
      0 9,13,17 * * 1-5ثلاث مرات يوميًا، في أيام العمل فقط
      0 9 * * 1ملخّص أسبوعي صباح كل يوم إثنين
      30mكل 30 دقيقة (للمستودعات كثيفة النشاط)

      الخطوة 6: التشغيل عند الطلب​

      لا تريد انتظار موعد الجدول؟ شغّلها يدويًا:

      hermes cron run pr-review

      أو من داخل جلسة محادثة:

      /cron run pr-review

      التعمّق أكثر​

      نشر المراجعات مباشرةً على GitHub​

      بدلًا من التسليم إلى Telegram، اجعل الوكيل يعلّق على الـ PR نفسه:

      أضف ما يلي إلى الـ prompt الخاص بمهمة cron:

      After reviewing, post your review:
      - For issues: gh pr review NUMBER --repo REPO --comment --body "YOUR_REVIEW"
      - For critical issues: gh pr review NUMBER --repo REPO --request-changes --body "YOUR_REVIEW"
      - For clean PRs: gh pr review NUMBER --repo REPO --approve --body "Looks good"
      تنبيه

      تأكد من أن gh يملك token بنطاق repo. تُنشر المراجعات باسم الحساب الذي صادق به gh.

      لوحة PR أسبوعية​

      أنشئ نظرة عامة صباح كل يوم إثنين على جميع مستودعاتك:

      hermes cron create "0 9 * * 1" \
        "Generate a weekly PR dashboard:
      - myorg/backend-api
      - myorg/frontend-app
      - myorg/infra

      For each repo show:
      1. Open PR count and oldest PR age
      2. PRs merged this week
      3. Stale PRs (older than 5 days)
      4. PRs with no reviewer assigned

      Format as a clean summary." \
        --name "weekly-dashboard" \
        --deliver telegram

      مراقبة عدة مستودعات​

      وسّع النطاق بإضافة مزيد من المستودعات إلى الـ prompt. يعالجها الوكيل بالتتابع — دون الحاجة إلى أي إعداد إضافي.

      استكشاف الأخطاء وإصلاحها​

      "gh: command not found"​

      يعمل الـ gateway في بيئة محدودة. تأكد من وجود gh في مسار PATH الخاص بالنظام، ثم أعد تشغيل الـ gateway.

      المراجعات عامة أكثر من اللازم​

      1. أضف المهارة code-review (الخطوة 3)
      2. علّم Hermes أعراف فريقك عبر الذاكرة (الخطوة 4)
      3. كلما زاد السياق المتوفر لديه عن الـ stack التقني الخاص بك، تحسّنت المراجعات

      مهمة cron لا تعمل​

      hermes gateway status    # Is the gateway running?
      hermes cron list         # Is the job enabled?

      حدود المعدل (Rate limits)​

      يسمح GitHub بـ 5,000 طلب API في الساعة للمستخدمين المُصادَقين. تستهلك مراجعة كل PR نحو 3-5 طلبات (القائمة + الـ diff + تعليقات اختيارية). وحتى مراجعة 100 PR يوميًا تبقى ضمن الحدود بفارق كبير.

      ما التالي؟​

      • مراجعات PR المعتمدة على Webhook — احصل على مراجعات فورية عند فتح طلبات PR (يتطلب endpoint عامًا)
      • بوت الملخّص اليومي — ادمج مراجعات PR مع ملخّص الأخبار الصباحي
      • بناء إضافة (Plugin) — غلّف منطق المراجعة في إضافة قابلة للمشاركة
      • Profiles — شغّل profile مخصصًا للمراجعة بذاكرته وإعداداته الخاصة
      • المزوّدون الاحتياطيون (Fallback Providers) — اضمن استمرار المراجعات حتى عند تعطّل أحد المزوّدين

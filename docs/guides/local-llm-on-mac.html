      تشغيل LLMs محليًا على Mac

      لمستخدمي تطبيق سطح المكتب: هناك طريق بنقرة واحدة

      في تطبيق Hermes لسطح المكتب، يتولى Settings → Providers → Local Models تثبيت خادم llama.cpp محلي وإدارته نيابةً عنك — بما في ذلك تنزيل النماذج، وملاءمتها للذاكرة المتاحة، وضبط حجم السياق. راجع Local Models. هذا الدليل مخصص للإعداد اليدوي: MLX، أو الإصدارات المبنية يدويًا (custom builds)، أو الخوادم التي تريد تشغيلها بنفسك.

      يرشدك هذا الدليل خطوة بخطوة إلى تشغيل خادم LLM محلي على macOS مع API متوافق مع OpenAI. ستحصل على خصوصية كاملة، ودون أي تكاليف API، وعلى أداء جيد بشكل مفاجئ على معالجات Apple Silicon.

      نغطي نوعين من الـ backends:

      الـ Backendالتثبيتنقطة القوةالصيغة
      llama.cppbrew install llama.cppأسرع زمن للوصول إلى أول token، مع KV cache مُكمَّم (quantized) لتقليل استهلاك الذاكرةGGUF
      omlxomlx.aiأسرع توليد للـ tokens، مع تحسين أصلي لـ MetalMLX (safetensors)

      يوفّر كلاهما endpoint متوافقًا مع OpenAI على المسار /v1/chat/completions. ويعمل Hermes مع أي منهما — ما عليك سوى توجيهه إلى http://localhost:8080 أو http://localhost:8000.

      لـ Apple Silicon فقط

      يستهدف هذا الدليل أجهزة Mac المزودة بمعالجات Apple Silicon (M1 وما بعده). ستعمل أجهزة Mac بمعالجات Intel مع llama.cpp ولكن دون تسريع GPU — لذا توقّع أداءً أبطأ بكثير.

      اختيار النموذج​

      للبدء، نوصي بـ Qwen3.5-9B — فهو نموذج قوي في الاستدلال ويتسع بسهولة في ذاكرة موحّدة (unified memory) سعتها 8GB أو أكثر عند استخدام التكميم (quantization).

      النسخةالحجم على القرصالذاكرة المطلوبة (سياق 128K)الـ Backend
      Qwen3.5-9B-Q4_K_M (GGUF)5.3 GBنحو 10 GB مع KV cache مُكمَّمllama.cpp
      Qwen3.5-9B-mlx-lm-mxfp4 (MLX)~5 GB~12 GBomlx

      قاعدة تقريبية للذاكرة: حجم النموذج + KV cache. يبلغ حجم نموذج 9B بتكميم Q4 نحو 5 GB. ويضيف KV cache عند سياق 128K مع تكميم Q4 نحو 4-5 GB. أما مع KV cache الافتراضي (f16)، فيتضخم ذلك إلى نحو 16 GB. تُعد خيارات تكميم KV cache في llama.cpp الحيلة الأساسية للأنظمة محدودة الذاكرة.

      بالنسبة إلى النماذج الأكبر (27B، 35B)، ستحتاج إلى ذاكرة موحّدة سعتها 32 GB أو أكثر. ويُعد نموذج 9B الخيار الأمثل للأجهزة ذات الذاكرة 8-16 GB.

      الخيار A: llama.cpp​

      يُعد llama.cpp أكثر بيئات تشغيل LLM المحلية قابليةً للنقل. وعلى macOS يستخدم Metal لتسريع GPU مباشرةً دون أي إعداد إضافي.

      التثبيت​

      brew install llama.cpp

      يتيح لك هذا الأمر llama-server على مستوى النظام.

      تنزيل النموذج​

      تحتاج إلى نموذج بصيغة GGUF. وأسهل مصدر لذلك هو Hugging Face عبر huggingface-cli:

      brew install huggingface-cli

      ثم نزّل النموذج:

      huggingface-cli download unsloth/Qwen3.5-9B-GGUF Qwen3.5-9B-Q4_K_M.gguf --local-dir ~/models
      النماذج المقيّدة الوصول (Gated models)

      تتطلب بعض النماذج على Hugging Face المصادقة. نفّذ huggingface-cli login أولًا إذا ظهر لك الخطأ 401 أو 404.

      تشغيل الخادم​

      llama-server -m ~/models/Qwen3.5-9B-Q4_K_M.gguf \
        -ngl 99 \
        -c 131072 \
        -np 1 \
        -fa on \
        --cache-type-k q4_0 \
        --cache-type-v q4_0 \
        --host 0.0.0.0

      إليك وظيفة كل خيار:

      الخيارالغرض
      -ngl 99نقل جميع الطبقات إلى GPU (Metal). استخدم رقمًا كبيرًا لضمان عدم بقاء أي طبقة على CPU.
      -c 131072حجم context window (128K token). قلّل هذه القيمة إذا كانت الذاكرة لديك محدودة.
      -np 1عدد الخانات (slots) المتوازية. أبقِه على 1 للاستخدام من قِبل مستخدم واحد — فزيادة الخانات تقسّم ميزانية الذاكرة.
      -fa onFlash attention. يقلل استهلاك الذاكرة ويسرّع الـ inference في السياقات الطويلة.
      --cache-type-k q4_0تكميم key cache إلى 4-bit. هذا هو الخيار الأكبر أثرًا في توفير الذاكرة.
      --cache-type-v q4_0تكميم value cache إلى 4-bit. ومع الخيار السابق، يقلل هذا ذاكرة KV cache بنحو 75% مقارنةً بـ f16.
      --host 0.0.0.0الاستماع على جميع الواجهات الشبكية. استخدم 127.0.0.1 إذا لم تكن بحاجة إلى الوصول عبر الشبكة.

      يكون الخادم جاهزًا عندما ترى:

      main: server is listening on http://0.0.0.0:8080
      srv  update_slots: all slots are idle

      تحسين الذاكرة للأنظمة المحدودة​

      يُعد الخياران --cache-type-k q4_0 --cache-type-v q4_0 أهم تحسين للأنظمة ذات الذاكرة المحدودة. إليك أثرهما عند سياق 128K:

      نوع KV cacheذاكرة KV cache (سياق 128K، نموذج 9B)
      f16 (الافتراضي)~16 GB
      q8_0~8 GB
      q4_0~4 GB

      على جهاز Mac بذاكرة 8 GB، استخدم KV cache بنوع q4_0 واختر نموذجًا أصغر لا يزال قادرًا على استيعاب الحد الأدنى للسياق في Hermes وهو 64K. وعلى 16 GB، يمكنك استخدام سياق 128K بارتياح. أما على 32 GB أو أكثر، فيمكنك تشغيل نماذج أكبر أو عدة خانات متوازية.

      إذا استمر نفاد الذاكرة، فقلّل السياق شرط أن يبقى عند الحد الأدنى في Hermes وهو 64K أو أعلى منه؛ وإلا فانتقل إلى نموذج أصغر أو تكميم أصغر (Q3_K_M بدلًا من Q4_K_M).

      اختباره​

      curl -s http://localhost:8080/v1/chat/completions \
        -H "Content-Type: application/json" \
        -d '{
          "model": "Qwen3.5-9B-Q4_K_M.gguf",
          "messages": [{"role": "user", "content": "Hello!"}],
          "max_tokens": 50
        }' | jq .choices[0].message.content

      الحصول على اسم النموذج​

      إذا نسيت اسم النموذج، فاستعلم من endpoint النماذج:

      curl -s http://localhost:8080/v1/models | jq '.data[].id'

      الخيار B: MLX عبر omlx​

      يُعد omlx تطبيقًا أصليًا لنظام macOS يدير نماذج MLX ويقدّمها عبر خادم. وMLX هو إطار تعلّم الآلة الخاص بـ Apple، والمحسَّن خصيصًا لبنية الذاكرة الموحّدة في Apple Silicon.

      التثبيت​

      نزّله وثبّته من omlx.ai. يوفّر واجهة رسومية (GUI) لإدارة النماذج وخادمًا مدمجًا.

      تنزيل النموذج​

      استخدم تطبيق omlx لتصفّح النماذج وتنزيلها. ابحث عن Qwen3.5-9B-mlx-lm-mxfp4 ونزّله. تُخزَّن النماذج محليًا (عادةً في ~/.omlx/models/).

      تشغيل الخادم​

      يقدّم omlx النماذج افتراضيًا على http://127.0.0.1:8000. ابدأ التقديم من واجهة التطبيق، أو استخدم CLI إن كان متاحًا.

      اختباره​

      curl -s http://127.0.0.1:8000/v1/chat/completions \
        -H "Content-Type: application/json" \
        -d '{
          "model": "Qwen3.5-9B-mlx-lm-mxfp4",
          "messages": [{"role": "user", "content": "Hello!"}],
          "max_tokens": 50
        }' | jq .choices[0].message.content

      عرض النماذج المتاحة​

      يستطيع omlx تقديم عدة نماذج في آن واحد:

      curl -s http://127.0.0.1:8000/v1/models | jq '.data[].id'

      اختبارات الأداء: llama.cpp مقابل MLX​

      اختُبر كلا الـ backends على الجهاز نفسه (Apple M5 Max، بذاكرة موحّدة 128 GB) مع تشغيل النموذج نفسه (Qwen3.5-9B) بمستويات تكميم متقاربة (Q4_K_M لصيغة GGUF، وmxfp4 لـ MLX). استُخدمت خمسة prompts متنوعة، وثلاث مرات تشغيل لكل منها، واختُبر الـ backends بالتتابع لتجنّب التنافس على الموارد.

      النتائج​

      المقياسllama.cpp (Q4_K_M)MLX (mxfp4)الأفضل
      TTFT (المتوسط)67 ms289 msllama.cpp (أسرع بـ 4.3 مرة)
      TTFT (p50)66 ms286 msllama.cpp (أسرع بـ 4.3 مرة)
      التوليد (المتوسط)70 tok/s96 tok/sMLX (أسرع بنسبة 37%)
      التوليد (p50)70 tok/s96 tok/sMLX (أسرع بنسبة 37%)
      الزمن الكلي (512 token)7.3s5.5sMLX (أسرع بنسبة 25%)

      ماذا يعني ذلك​

      • يتفوّق llama.cpp في معالجة الـ prompt — إذ يوصلك pipeline الخاص به، القائم على flash attention مع KV cache المُكمَّم، إلى أول token خلال نحو 66ms. إذا كنت تبني تطبيقات تفاعلية تهمّ فيها سرعة الاستجابة الملموسة (بوتات المحادثة، والإكمال التلقائي)، فهذه ميزة ذات قيمة حقيقية.

      • أما MLX فيولّد الـ tokens أسرع بنحو 37% بمجرد أن يبدأ. وفي أحمال العمل الدفعية، أو التوليد الطويل، أو أي مهمة يهمّ فيها زمن الإنجاز الكلي أكثر من زمن الاستجابة الأولي، ينتهي MLX أسرع.

      • كلا الـ backends ثابتان للغاية في الأداء — فالتباين بين مرات التشغيل كان ضئيلًا جدًا، ويمكنك الاعتماد على هذه الأرقام.

      أيهما تختار؟​

      حالة الاستخدامالتوصية

      التوليد الطويل، والمعالجة المجمّعةMLX (omlx)
      الذاكرة المحدودة (8-16 GB)llama.cpp (لا مثيل لـ KV cache المُكمَّم فيه)

      الربط مع Hermes​

      بعد تشغيل الخادم المحلي:

      hermes model

      اختر Custom endpoint واتبع التعليمات. سيُطلب منك إدخال الـ URL الأساسي واسم النموذج — استخدم القيم الخاصة بالـ backend الذي أعددته أعلاه.

      مهلات الانتظار (Timeouts)​

      يكتشف Hermes الـ endpoints المحلية تلقائيًا (localhost، وعناوين IP في الشبكة المحلية LAN) ويخفّف مهلات البث (streaming) الخاصة به. لا حاجة إلى أي إعداد في معظم الحالات.

      إذا واجهت أخطاء انتهاء المهلة رغم ذلك (مثل السياقات الكبيرة جدًا على عتاد بطيء)، يمكنك تجاوز مهلة القراءة أثناء البث:

      # In your .env — raise from the 120s default to 30 minutes
      HERMES_STREAM_READ_TIMEOUT=1800
      المهلةالقيمة الافتراضيةالضبط التلقائي محليًاتجاوزها عبر متغير البيئة
      قراءة البث (على مستوى socket)120sتُرفع إلى 1800sHERMES_STREAM_READ_TIMEOUT
      اكتشاف البث المتوقف180sمُعطَّل تمامًاHERMES_STREAM_STALE_TIMEOUT
      استدعاء API (دون بث)1800sلا حاجة إلى تغييرHERMES_API_TIMEOUT

      مهلة قراءة البث هي الأكثر احتمالًا للتسبب في مشكلات — فهي المهلة القصوى على مستوى socket لاستلام الجزء التالي من البيانات. وأثناء مرحلة prefill في السياقات الكبيرة، قد لا تُنتج النماذج المحلية أي مخرجات لدقائق بينما تعالج الـ prompt. ويتعامل الاكتشاف التلقائي مع ذلك بشكل شفاف.

      الصمت في الدور الأول غالبًا مرحلة prefill، لا تعليق

      يرسل Hermes الـ system prompt ومخططات الأدوات (tool schemas) في كل استدعاء، لذا قد يتضمن الدور الأول على العتاد الأبطأ دقائق من الصمت بينما يعالج النموذج هذا الـ prompt قبل أن يولّد أي شيء. هذه مرحلة prefill قيد العمل، وليست جلسة متوقفة. راجع بطء الاستجابة الأولى (prefill) في دليل Ollama للاطلاع على طرق التخفيف، مثل إبقاء النموذج محمّلًا وتقليص الـ prompt الثابت باستخدام hermes prompt-size.

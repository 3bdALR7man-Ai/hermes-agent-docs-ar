      تسجيل الدخول الأصلي على سطح المكتب (RFC 8252)

      عندما يتصل تطبيق Hermes لسطح المكتب بـgateway مُقيَّد (لوحة تحكم مستضافة أو مستضافة ذاتيًا خلف مزوّد OAuth)، يمكنه تسجيل الدخول بطريقتين:

      1. تسجيل دخول أصلي (RFC 8252) — يفتح التطبيق متصفح نظامك الحقيقي، وتوافق في المتصفح الذي تثق به بالفعل، ويستلم التطبيق رموزًا (tokens) يخزّنها كملفات مقتصرة على المالك فقط في مجلد بيانات المستخدم الخاص به (يمكن تشفيرها اختياريًا عبر سلسلة مفاتيح نظام التشغيل — Settings ← Gateway). بلا webview مضمَّن، وبلا ملفات تعريف ارتباط (cookies) جلسة متصفح. هذا هو الافتراضي كلما دعمه gateway.
      2. تسجيل دخول مضمَّن (احتياطي قديم) — يفتح التطبيق نافذة متصفح صغيرة داخل التطبيق ويلتقط ملف تعريف ارتباط جلسة gateway. يُستخدَم تلقائيًا عندما يكون gateway نسخة أقدم لا تعلن عن دعم تسجيل الدخول الأصلي.

      أنت لا تختار بين هذين — يكتشف التطبيق ما يدعمه gateway ويختار الأنسب. توضّح هذه الصفحة ما الذي يحدث ولماذا.

      لماذا تسجيل الدخول الأصلي​

      لتضمين متصفح داخل تطبيق أصلي من أجل OAuth عيوب معروفة جيدًا: لا تستطيع صفحة تسجيل الدخول رؤية جلسة متصفحك الحالية (فتعيد كتابة بيانات الاعتماد وتعيد إجراء المصادقة متعددة العوامل)، وغالبًا ما لا تعمل مديرات كلمات المرور والمفاتيح المرورية (passkeys)، ويعتمد التطبيق على قراءة ملف تعريف ارتباط جلسة من webview خاص. RFC 8252 ("OAuth 2.0 for Native Apps") هي أفضل ممارسة معتمَدة في الصناعة تتجنّب كل ذلك: نفّذ التفويض في متصفح النظام وسلِّم التطبيق رموزه الخاصة.

      بالنسبة إلى Hermes تحديدًا، يعني تسجيل الدخول الأصلي:

      • بلا webview مضمَّن. يحدث التفويض في Safari / Chrome / Firefox / Edge — أيًا كان ما تستخدمه — مع بقاء تسجيلات دخولك، وإضافاتك، ومفاتيحك المرورية سليمة.
      • بلا ملفات تعريف ارتباط جلسة. يحمل التطبيق رمز وصول (access token) OAuth (قصير العمر) ورمز تحديث (refresh token)، مُخزَّنَين كملفات مقتصرة على المالك — مشفّرة عند السكون عبر سلسلة مفاتيح نظام التشغيل لديك (safeStorage الخاص بـ Electron) عند تفعيل مفتاح سلسلة المفاتيح الاختياري في Settings ← Gateway. تُصادَق استدعاءات REST وتذاكر WebSocket بترويسة Authorization: Bearer، لا بمخزن ملفات تعريف ارتباط.

      كيف يعمل​

      Desktop app                Gateway (/auth/native/*)          Nous Portal (IDP)
         │ 1. open loopback 127.0.0.1:<random port>
         │ 2. system browser ─►  /auth/native/authorize
         │    (PKCE challenge)    (starts the normal PKCE login) ─► /oauth/authorize
         │                        ◄──── code ──── /auth/callback ◄──┘
         │                        3. mint one-time gateway code
         │ ◄─ 302 127.0.0.1/cb?code=… ─┘
         │ 4. POST /auth/native/token (code + PKCE verifier)
         │ ◄─ 5. { access_token, refresh_token, expires_at } ───────┘
         │ 6. store in local token store; use Bearer for REST + WS tickets

      يتوسّط gateway (brokers) عملية التدفّق: فهو خادم التفويض بالنسبة إلى تطبيق سطح المكتب، وعميل OAuth بالنسبة إلى مزوّد الهوية الأعلى (Nous Portal). هذا مطلوب لأن client_id وروابط إعادة التوجيه المسموح بها لدى المزوّد الأعلى مرتبطة بمصدر (origin) gateway نفسه — لا يمكن لتطبيق سطح مكتب أن يكون عميلًا مباشرًا لـ Portal. ومع ذلك يحصل سطح المكتب على تجربة RFC 8252 الكاملة: زوج PKCE خاص به، وإعادة توجيه loopback خاصة به، ورموز يملكها هو.

      يحمي PKCE (RFC 7636) قفزة loopback: يصبح رمز gateway لمرة واحدة عديم الفائدة بلا مُحقِّق الرمز (code verifier)، الذي لا يغادر التطبيق أبدًا. الرمز أحادي الاستخدام وقصير العمر.

      اكتشاف القدرات والاحتياط​

      يقرأ سطح المكتب نقطة نهاية gateway العامة /api/status، التي تعلن مصفوفة auth_flows:

      قيمة auth_flowsالمعنى
      ["cookie", "native_pkce"]يدعم gateway تسجيل الدخول الأصلي ← يستخدمه التطبيق
      ["cookie"]يدعم gateway التدفّق القديم فقط ← يستخدم التطبيق webview المضمَّن
      (الحقل غائب)gateway أقدم ← يستخدم التطبيق webview المضمَّن

      إذا أُعلِن دعم تسجيل الدخول الأصلي لكنه فشل لسبب محلي — مثل أن أداة أمان تحجب مستمِع loopback، أو أغلقت تبويب المتصفح — يعود التطبيق تلقائيًا إلى التدفّق المضمَّن حتى تتمكّن من تسجيل الدخول رغم ذلك.

      دورة حياة الرمز (Token)​

      • رمز الوصول (Access token): قصير العمر (دقائق). يُرسَل كـ Authorization: Bearer في كل استدعاء REST وعند سكّ تذكرة WebSocket.
      • رمز التحديث (Refresh token): أطول عمرًا، ودوّار. عندما يقترب رمز الوصول من الانتهاء، يستدعي التطبيق /auth/native/refresh لتدوير كلا الرمزين، ثم يحدّث مخزن رموزه.
      • الانتهاء النهائي: إذا كان رمز التحديث ميتًا (منتهيًا / مُلغى / اكتُشف إعادة استخدامه)، يمسح التطبيق رموزه المخزَّنة ويطالب بتسجيل دخول جديد.
      • تسجيل الخروج: يمسح كلًّا من الرموز الأصلية المخزَّنة وأي ملف تعريف ارتباط جلسة قديم لذلك gateway.

      لمشغّلي gateway​

      يتوفّر تسجيل الدخول الأصلي تلقائيًا على أي gateway مُقيَّد لديه مزوّد جلسة تفاعلية مسجَّل. لا حاجة لأي إعداد — مسارات /auth/native/* وإعلان auth_flows جزء من نظام مصادقة لوحة التحكم الفرعي. يتوسّط مزوّدو OAuth (مثل مزوّد Nous المضمَّن) إعادة التوجيه إلى مزوّد الهوية الأعلى؛ أما مزوّدو كلمة المرور (مثل إضافة basic-auth المضمَّنة) فيُنزلون متصفح النظام على نموذج بيانات اعتماد /login الخاص بـ gateway بدلًا من ذلك — وهذا ما يتيح لمديرات كلمات مرور نظام التشغيل (macOS Passwords، إلخ) ملء النموذج تلقائيًا، وهو أمر لا يستطيع أي webview مضمَّن في سطح المكتب تقديمه. بيانات الاعتماد المعتمِدة على رمز فقط (مثل drain) ليست تسجيلات دخول تفاعلية ولا تعلن native_pkce.

      نقاط النهاية ذات الصلة (كلها عامة، وضمن التمهيد قبل المصادقة، مثل مسارات /auth/* الخاصة بـ OAuth الموجودة):

      • GET /auth/native/authorize — يبدأ تسجيل الدخول عبر PKCE المتوسَّط
      • POST /auth/native/token — يستبدل رمز loopback + المُحقِّق (verifier) برموز
      • POST /auth/native/refresh — يدوّر الرموز انطلاقًا من رمز تحديث التطبيق

      راجع أيضًا​

      • OAuth عبر SSH / الأجهزة البعيدة — نمط استدعاء loopback لتفويض OAuth الخاص بالمزوّد/MCP على الأجهزة البعيدة.

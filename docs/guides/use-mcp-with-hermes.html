      استخدام MCP مع Hermes

      يوضّح هذا الدليل كيفية استخدام MCP فعليًا مع Hermes Agent في سير العمل اليومي.

      إذا كانت صفحة الميزة تشرح ماهية MCP، فإن هذا الدليل يركّز على كيفية الاستفادة منه بسرعة وأمان.

      متى ينبغي أن تستخدم MCP؟​

      استخدم MCP عندما:

      • تكون الأداة متوفرة بالفعل بصيغة MCP ولا تريد بناء أداة أصلية في Hermes
      • تريد أن يعمل Hermes على نظام محلي أو بعيد عبر طبقة RPC نظيفة
      • تريد تحكمًا دقيقًا في ما يُتاح من كل خادم على حدة
      • تريد ربط Hermes بواجهات API داخلية، أو قواعد بيانات، أو أنظمة الشركة دون تعديل نواة Hermes

      لا تستخدم MCP عندما:

      • تكون هناك أداة مدمجة في Hermes تؤدي المهمة جيدًا بالفعل
      • يُتيح الخادم مجموعة ضخمة وخطيرة من الأدوات ولست مستعدًا لتصفيتها
      • لا تحتاج إلا إلى تكامل واحد محدود جدًا، وتكون الأداة الأصلية أبسط وأكثر أمانًا

      النموذج الذهني​

      فكّر في MCP على أنه طبقة مُحوِّل (adapter):

      • يبقى Hermes هو الوكيل
      • تساهم خوادم MCP بالأدوات
      • يكتشف Hermes هذه الأدوات عند بدء التشغيل أو عند إعادة التحميل
      • يستطيع النموذج استخدامها كأي أدوات عادية
      • تتحكم أنت في مقدار ما يظهر من كل خادم

      هذه النقطة الأخيرة مهمة. فالاستخدام الجيد لـ MCP ليس مجرد “اربط كل شيء”، بل هو “اربط الشيء المناسب، بأصغر نطاق مفيد ممكن.”

      الخطوة 1: تثبيت دعم MCP​

      إذا ثبّتَّ Hermes باستخدام سكربت التثبيت القياسي، فإن دعم MCP مضمّن بالفعل (إذ ينفّذ المُثبّت uv pip install -e ".[all]").

      إذا ثبّتَّه دون الإضافات (extras) وتحتاج إلى إضافة MCP بشكل منفصل:

      cd ~/.hermes/hermes-agent
      uv pip install -e ".[mcp]"

      بالنسبة إلى الخوادم المعتمدة على npm، تأكد من توفّر Node.js و npx.

      وبالنسبة إلى كثير من خوادم MCP المكتوبة بـ Python، يُعد uvx خيارًا افتراضيًا جيدًا.

      الخطوة 2: أضف خادمًا واحدًا أولًا​

      ابدأ بخادم واحد آمن.

      مثال: وصول إلى نظام الملفات مقتصر على مجلد مشروع واحد فقط.

      mcp_servers:
        project_fs:
          command: "npx"
          args: ["-y", "@modelcontextprotocol/server-filesystem", "/home/user/my-project"]

      ثم شغّل Hermes:

      hermes chat

      والآن اطرح سؤالًا محددًا:

      Inspect this project and summarize the repo layout.

      الخطوة 3: تحقّق من تحميل MCP​

      يمكنك التحقق من MCP بعدة طرق:

      • يجب أن تُظهر لافتة Hermes أو شريط حالته تكامل MCP عند إعداده
      • اسأل Hermes عن الأدوات المتاحة لديه
      • استخدم /reload-mcp بعد تغيير الإعدادات
      • راجع السجلات إذا فشل الاتصال بالخادم

      prompt عملي للاختبار:

      Tell me which MCP-backed tools are available right now.

      الخطوة 4: ابدأ التصفية فورًا​

      لا تنتظر إلى وقت لاحق إذا كان الخادم يُتيح عددًا كبيرًا من الأدوات.

      مثال: اسمح فقط بما تريده (whitelist)​

      mcp_servers:
        github:
          command: "npx"
          args: ["-y", "@modelcontextprotocol/server-github"]
          env:
            GITHUB_PERSONAL_ACCESS_TOKEN: "***"
          tools:
            include: [list_issues, create_issue, search_code]

      هذا عادةً أفضل خيار افتراضي للأنظمة الحساسة.

      WSL2: ربط Hermes داخل WSL بمتصفح Chrome على Windows​

      هذا هو الإعداد العملي عندما:

      • يعمل Hermes داخل WSL2
      • يكون المتصفح الذي تريد التحكم فيه هو متصفح Chrome المعتاد الذي سجّلت الدخول إليه على Windows
      • يكون /browser connect غير مريح أو غير موثوق من داخل WSL

      في هذا الإعداد، لا يتصل Hermes بـ Chrome مباشرةً. بل:

      • يعمل Hermes داخل WSL
      • يُشغّل Hermes خادم MCP محليًا من نوع stdio
      • يُطلَق خادم MCP هذا عبر آلية التشغيل البيني في Windows (interop) باستخدام (cmd.exe أو powershell.exe)
      • يرتبط خادم MCP بجلسة Chrome الحية لديك على Windows

      النموذج الذهني:

      Hermes (WSL) -> MCP stdio bridge -> Windows Chrome

      لماذا يُعد هذا الوضع مفيدًا​

      • تحتفظ بملف تعريف المتصفح الحقيقي على Windows، وملفات تعريف الارتباط (cookies)، وجلسات تسجيل الدخول
      • يبقى Hermes في بيئة Unix المدعومة الخاصة به (WSL2)
      • يُتاح التحكم في المتصفح كأدوات MCP بدلًا من الاعتماد على آلية نقل المتصفح في نواة Hermes

      الخادم الموصى به​

      استخدم chrome-devtools-mcp.

      إذا كان Chrome على Windows لديك مفعّلًا فيه التصحيح عن بُعد المباشر (live remote debugging) مسبقًا من chrome://inspect/#remote-debugging، فأضفه على هذا النحو من داخل WSL:

      hermes mcp add chrome-devtools-win --command cmd.exe --args /c npx -y chrome-devtools-mcp@latest --autoConnect --no-usage-statistics

      بعد حفظ الخادم:

      hermes mcp test chrome-devtools-win

      ثم ابدأ جلسة Hermes جديدة أو نفّذ:

      /reload-mcp

      prompt نموذجي​

      بعد التحميل، يستطيع Hermes استخدام أدوات المتصفح التي تحمل بادئة MCP مباشرةً. على سبيل المثال:

      调用 MCP 工具 mcp_chrome_devtools_win_list_pages，列出当前浏览器标签页。

      متى يكون /browser connect الأداة الخاطئة​

      إذا كان Hermes يعمل داخل WSL و Chrome يعمل على Windows، فقد يفشل /browser connect حتى لو كان Chrome مفتوحًا وقابلًا للتصحيح.

      الأسباب الشائعة:

      • لا يستطيع WSL الوصول إلى الـ endpoint المحلي نفسه الذي يُتيحه Chrome لأدوات Windows
      • مسارات التصحيح المباشر في إصدارات Chrome الأحدث ليست مماثلة للاتصال الكلاسيكي عبر ws://localhost:9222
      • يكون الارتباط بالمتصفح أسهل عبر أداة مساعدة تعمل على جانب Windows مثل chrome-devtools-mcp

      في هذه الحالات، احتفظ بـ /browser connect للإعدادات التي تعمل في البيئة نفسها، واستخدم MCP لربط المتصفح من WSL إلى Windows.

      مشكلات معروفة​

      • شغّل Hermes من مسار مُركَّب من Windows مثل /mnt/c/Users/<you> أو /mnt/c/workspace/... عند استخدام ملفات Windows التنفيذية من نوع stdio عبر MCP.
      • إذا شغّلت Hermes من /root أو /home/...، فقد يُصدر Windows تحذيرًا بشأن المجلد الحالي من نوع UNC قبل بدء خادم MCP.
      • إذا انتهت مهلة chrome-devtools-mcp --autoConnect أثناء حصر الصفحات، فقلّل عدد علامات التبويب العاملة في الخلفية أو المجمّدة في Chrome ثم أعد المحاولة.

      مثال: حظر الإجراءات الخطيرة (blacklist)​

      mcp_servers:
        stripe:
          url: "https://mcp.stripe.com"
          headers:
            Authorization: "Bearer ***"
          tools:
            exclude: [delete_customer, refund_payment]

      مثال: تعطيل الـ wrappers المساعدة أيضًا​

      mcp_servers:
        docs:
          url: "https://mcp.docs.example.com"
          tools:
            prompts: false
            resources: false

      ما الذي تؤثر فيه التصفية فعليًا؟​

      هناك فئتان من الوظائف التي تُتاح عبر MCP في Hermes:

      1. أدوات MCP الأصلية الخاصة بالخادم
      • تُصفّى باستخدام:
        • tools.include
        • tools.exclude
      1. الـ wrappers المساعدة التي يضيفها Hermes
      • تُصفّى باستخدام:
        • tools.resources
        • tools.prompts

      الـ wrappers المساعدة التي قد تراها​

      الموارد (Resources):

      • list_resources
      • read_resource

      الـ Prompts:

      • list_prompts
      • get_prompt

      لا تظهر هذه الـ wrappers إلا إذا:

      • كانت إعداداتك تسمح بها، و
      • كانت جلسة خادم MCP تدعم هذه القدرات فعليًا

      لذا لن يتظاهر Hermes بأن لدى الخادم موارد أو prompts إن لم تكن لديه.

      أنماط شائعة​

      النمط 1: مساعد مشروع محلي​

      استخدم MCP مع خادم نظام ملفات أو خادم git محلي خاص بالمستودع عندما تريد أن يعمل Hermes ضمن مساحة عمل محدودة النطاق.

      mcp_servers:
        fs:
          command: "npx"
          args: ["-y", "@modelcontextprotocol/server-filesystem", "/home/user/project"]

        git:
          command: "uvx"
          args: ["mcp-server-git", "--repository", "/home/user/project"]

      أمثلة على prompts جيدة:

      Review the project structure and identify where configuration lives.
      Check the local git state and summarize what changed recently.

      النمط 2: سجل عمل أصلي داخل المستودع باستخدام Open Scaffold​

      استخدم Open Scaffold عندما تريد أن يقرأ Hermes سجل عمل الذكاء الاصطناعي الدائم الخاص بمستودع ما: المهمة الأساسية (mission)، والخطط، وملاحظات الأدلة، وحزم التسليم (handoff packets)، ونتائج المراجعة/البوابات (gates). يبقى Hermes هو الوكيل، ويبقى Open Scaffold هو السجل المحلي الخاص بالمستودع.

      أضف الخادم لمستودع واحد مُهيّأ باستخدام Open Scaffold:

      hermes mcp add open_scaffold --command npx --args -y open-scaffold@latest mcp serve --repo /absolute/path/to/repo
      hermes mcp test open_scaffold

      ثم أبقِ النطاق المُتاح موجّهًا نحو القراءة. اختر select في مطالبة hermes mcp add، أو عدّل config.yaml بعد ذلك:

      mcp_servers:
        open_scaffold:
          command: "npx"
          args: ["-y", "open-scaffold@latest", "mcp", "serve", "--repo", "/absolute/path/to/repo"]
          tools:
            include:
              - list_plans
              - get_plan
              - get_mission
              - list_evidence
              - get_evidence
              - get_status
              - search_plans
              - list_amendments
              - get_handoff
              - analyze_loop
              - gate_loop
            prompts: false

      أمثلة على prompts جيدة:

      Use the Open Scaffold MCP tools to compile the current handoff packet and tell me the next legal action.
      Inspect the active plans and evidence notes, then say whether this repo is ready for human review or needs another attempt.

      ملاحظات حول الحدود:

      • يعمل Open Scaffold MCP محليًا في المقام الأول، وهو للقراءة فقط افتراضيًا.
      • تتطلب أدوات الكتابة الخاصة به تشغيل الخادم مع --allow-write؛ لا تفعّل ذلك حتى تريد صراحةً أن يعدّل Hermes ملفات .osc.
      • يسجّل Open Scaffold العمل ويضع له بوابات (gates)؛ لكنه لا يفوّض Hermes بالدمج (merge)، أو النشر، أو الـ deploy، أو إنشاء بيئات تشغيل (runtimes).
      • ثبّت الإصدار عبر open-scaffold@<version> بدلًا من @latest إذا كنت تحتاج إلى مخططات أدوات (tool schemas) قابلة لإعادة الإنتاج.

      النمط 3: مساعد لفرز مشكلات GitHub (triage)​

      mcp_servers:
        github:
          command: "npx"
          args: ["-y", "@modelcontextprotocol/server-github"]
          env:
            GITHUB_PERSONAL_ACCESS_TOKEN: "***"
          tools:
            include: [list_issues, create_issue, update_issue, search_code]
            prompts: false
            resources: false

      أمثلة على prompts جيدة:

      List open issues about MCP, cluster them by theme, and draft a high-quality issue for the most common bug.
      Search the repo for uses of _discover_and_register_server and explain how MCP tools are registered.

      النمط 4: مساعد لـ API داخلي​

      mcp_servers:
        internal_api:
          url: "https://mcp.internal.example.com"
          headers:
            Authorization: "Bearer ***"
          tools:
            include: [list_customers, get_customer, list_invoices]
            resources: false
            prompts: false

      أمثلة على prompts جيدة:

      Look up customer ACME Corp and summarize recent invoice activity.

      هذا هو نوع المواقف التي تكون فيها قائمة السماح الصارمة أفضل بكثير من قائمة الاستبعاد.

      النمط 4: خوادم التوثيق / المعرفة​

      تُتيح بعض خوادم MCP prompts أو موارد أقرب إلى أصول معرفية مشتركة منها إلى إجراءات مباشرة.

      mcp_servers:
        docs:
          url: "https://mcp.docs.example.com"
          tools:
            prompts: true
            resources: true

      أمثلة على prompts جيدة:

      List available MCP resources from the docs server, then read the onboarding guide and summarize it.
      List prompts exposed by the docs server and tell me which ones would help with incident response.

      درس تطبيقي: إعداد متكامل من البداية إلى النهاية مع التصفية​

      إليك تسلسلًا عمليًا للخطوات.

      المرحلة 1: أضف GitHub MCP مع قائمة سماح ضيقة​

      mcp_servers:
        github:
          command: "npx"
          args: ["-y", "@modelcontextprotocol/server-github"]
          env:
            GITHUB_PERSONAL_ACCESS_TOKEN: "***"
          tools:
            include: [list_issues, create_issue, search_code]
            prompts: false
            resources: false

      شغّل Hermes واسأل:

      Search the codebase for references to MCP and summarize the main integration points.

      المرحلة 2: وسّع النطاق عند الحاجة فقط​

      إذا احتجت لاحقًا إلى تحديث الـ issues أيضًا:

      tools:
        include: [list_issues, create_issue, update_issue, search_code]

      ثم أعد التحميل:

      /reload-mcp

      المرحلة 3: أضف خادمًا ثانيًا بسياسة مختلفة​

      mcp_servers:
        github:
          command: "npx"
          args: ["-y", "@modelcontextprotocol/server-github"]
          env:
            GITHUB_PERSONAL_ACCESS_TOKEN: "***"
          tools:
            include: [list_issues, create_issue, update_issue, search_code]
            prompts: false
            resources: false

        filesystem:
          command: "npx"
          args: ["-y", "@modelcontextprotocol/server-filesystem", "/home/user/project"]

      الآن يستطيع Hermes الجمع بينهما:

      Inspect the local project files, then create a GitHub issue summarizing the bug you find.

      وهنا تكمن قوة MCP: سير عمل يمتد عبر أنظمة متعددة دون تغيير نواة Hermes.

      توصيات للاستخدام الآمن​

      فضّل قوائم السماح للأنظمة الخطيرة​

      لأي شيء مالي، أو موجّه إلى العملاء، أو قد يكون مدمّرًا:

      • استخدم tools.include
      • ابدأ بأصغر مجموعة ممكنة

      عطّل الأدوات المساعدة غير المستخدمة​

      إذا كنت لا تريد أن يتصفّح النموذج الموارد أو الـ prompts التي يوفّرها الخادم، فعطّلها:

      tools:
        resources: false
        prompts: false

      أبقِ نطاق الخوادم ضيقًا​

      أمثلة:

      • خادم نظام ملفات جذره مجلد مشروع واحد، وليس مجلد المنزل (home) بأكمله
      • خادم git موجّه إلى مستودع واحد
      • خادم API داخلي يُتيح افتراضيًا أدوات يغلب عليها طابع القراءة

      أعد التحميل بعد تغيير الإعدادات​

      /reload-mcp

      افعل ذلك بعد تغيير:

      • قوائم include/exclude
      • خيارات التفعيل (enabled)
      • مفاتيح تشغيل resources/prompts
      • ترويسات المصادقة (auth headers) / متغيرات البيئة

      استكشاف الأخطاء وإصلاحها حسب العَرَض​

      "الخادم متصل لكن الأدوات التي توقعتها غير موجودة"​

      الأسباب المحتملة:

      • صُفّيت بواسطة tools.include
      • استُبعدت بواسطة tools.exclude
      • عُطّلت الـ wrappers المساعدة عبر resources: false أو prompts: false
      • الخادم لا يدعم الموارد أو الـ prompts فعليًا

      "الخادم مُعدّ لكن لا شيء يُحمَّل"​

      تحقّق من أن:

      • enabled: false لم يُترك في الإعدادات
      • الأمر أو بيئة التشغيل موجودة (npx، uvx، وغيرهما)
      • الـ HTTP endpoint قابل للوصول
      • متغيرات بيئة المصادقة أو الترويسات صحيحة

      "لماذا أرى أدوات أقل مما يُعلن عنه خادم MCP؟"​

      لأن Hermes أصبح يحترم السياسة التي تحددها لكل خادم، ويعتمد تسجيلًا يراعي القدرات المدعومة. هذا سلوك متوقع، وعادةً ما يكون مرغوبًا.

      "كيف أزيل خادم MCP دون حذف إعداداته؟"​

      استخدم:

      enabled: false

      يُبقي هذا الإعدادات محفوظة لكنه يمنع الاتصال والتسجيل.

      إعدادات MCP الأولى الموصى بها​

      خوادم مناسبة للبدء لمعظم المستخدمين:

      • filesystem
      • git
      • GitHub
      • خوادم MCP من نوع fetch أو خوادم التوثيق
      • API داخلي واحد محدود النطاق

      خوادم غير مناسبة للبدء:

      • أنظمة الأعمال الضخمة التي تحتوي على كثير من الإجراءات المدمّرة دون أي تصفية
      • أي شيء لا تفهمه جيدًا بما يكفي لتقييده

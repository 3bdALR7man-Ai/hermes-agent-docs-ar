Plugin Hooks

الإضافات (Plugins) تسجيل hooks تُطلَق في جلسات CLI والـ gateway معًا. تُسجَّل هذه برمجيًا عبر ctx.register_hook() في دالة register() الخاصة بإضافتك.

لتفاصيل تعبئة الإضافات وتسجيلها، راجع دليل الإضافات (Plugins).

قواعد عامة لكل الـ hooks:

  • تستقبل ردود النداء وسائط بالكلمة المفتاحية (keyword arguments). اقبل دائمًا **kwargs للتوافق المستقبلي.
  • تُسجَّل استثناءات الاستدعاءات الراجعة وتُتجاوز؛ وتستمر الاستدعاءات اللاحقة. يُبلَّغ عن الاستدعاء الذي يفشل بالطريقة نفسها في كل مرة (عادةً بسبب توقيع يسمّي حقلًا لا ترسله hook، مثل tool_data بدلًا من tool_name/args) مرة واحدة بمستوى WARNING — وتسرد الرسالة الحقول التي توفرها hook — وتُنقل التكرارات المطابقة إلى DEBUG، كي لا تُغرق إضافة معلنة خطأً السجل.
  • إذا كان رد نداء إضافة Python على hook مقيَّد بمهلة زمنية (مراقِبات المسار الساخن مثل post_tool_call / pre_llm_call، بالإضافة إلى hook السياسة pre_tool_call) محجوبًا لمدة أطول من plugins.hook_callback_timeout (الافتراضي 30 ثانية، اضبطها على 0 للتعطيل، والحد الأقصى 600)، يُهجَر دون انتظار عامل العمل حتى تستمر حلقة الوكيل. ردود نداء pre_tool_call التي انتهت مهلتها أو ما تزال قيد التشغيل تفشل بأمان (تحجب الأداة)؛ بينما ردود النداء المقيَّدة الأخرى تفشل بانفتاح (تُتخطَّى). لا تُنقَل الـ hooks ذات عقد الخيط المستدعي الموثَّق (subagent_stop) إلى عامل مهلة زمنية أبدًا. تحتفظ shell hooks بـ timeout خاص بها لكل إدخال.
  • الكتالوج أدناه وصفي: تتجاهل المراقِبات القيم المُعادة، وتقبل التحويلات أول استبدال نصّي صالح، وتستهلك hooks التوجيه/التحكم أشكالًا مُعادة موثَّقة. Plugin middleware سجلّ وسطح منفصلان، لا فئة hook أخرى.
  • حقول الارتباط مثل turn_id، وapi_request_id، وtask_id، وsession_id، وapi_call_count خاصة بكل hook وقد تكون غائبة. عامل المعرّفات كقيم مبهمة.
  • صحة أسماء الأحداث وقت التشغيل تأتي من hermes_cli.plugins.VALID_HOOKS. يسرد hermes hooks list الـ shell/outbound hooks المُعدَّة، لا كل حدث متاح؛ ويُبلِغ hermes hooks test <event> عن المجموعة الصالحة فقط عندما يُمرَّر حدث غير صالح.

أقسام system prompt آمنة للتخزين المؤقت

يمكن للإضافات التي تحتاج توجيهًا دائمًا وثابت الحضور تسجيل قسم system prompt مُقيَّد بدلًا من حقن نفس النص عبر pre_llm_call في كل دور:

العقد ضيّق عن قصد:

  • المعرّفات عالمية وثابتة ومكوَّنة من 1 إلى 128 حرفًا صغيرًا باستخدام فقط الحروف والأرقام و. و_ و-. تُرفَض المعرّفات المكرَّرة.
  • after_memory هو مرساة الوضع الوحيدة. تُرتَّب الأقسام حسب المعرّف، وتُعرَض بعد سياق الذاكرة/الـ profile وقبل بيانات الجلسة الوصفية؛ لا يمكن للإضافات إعادة ترتيب أو استبدال محتوى الـ prompt الأساسي.
  • يستقبل الكائن القابل للاستدعاء تعيينًا للقراءة فقط يحوي session_id، وmodel، وprovider، وplatform، وprofile_name، وcwd. يعمل مرة واحدة لكل جلسة جديدة. تُجمَّد وحداته البايتية المُصيَّرة عند الضغط وتُستعاد من system prompt الكامل المخزَّن مسبقًا بعد إعادة تشغيل/استئناف العملية؛ لا تُعاد قراءة حالة الإضافة لجلسة موجودة.
  • max_chars محدود بـ 4000 حرف. كل أقسام الإضافات معًا، بما فيها عناوين المراجعة الخاصة بها، محدودة بـ 8000 حرف و32 قسمًا. تُتخطَّى الأقسام الفارغة، أو غير النصية، أو الزائدة الحجم، أو المتجاوزة للميزانية الإجمالية، أو التي تُثير استثناءً، مع تحذير؛ ويستمر بناء الـ prompt.
  • يُذكَر كل قسم مقبول باسمه في الـ prompt ويُسجَّل عند بدء الجلسة مع إضافته وموضعه وعدد أحرفه.

استخدم pre_llm_call للسياق الديناميكي الحقيقي لكل دور. لا يوجد عن قصد أي hook لتلميحات بيئة الإضافات في هذا العقد: تغيير المجلد الحالي، أو الفرع، أو بيانات بيئة أخرى يجب ألا يُغيِّر بصمت الـ prompt المخزَّن مؤقتًا لجلسة. مثل هذا الـ hook يحتاج مستهلكًا ملموسًا ونفس دلالات التجميد/الاستئناف الآمنة قبل أن يمكن إضافته.

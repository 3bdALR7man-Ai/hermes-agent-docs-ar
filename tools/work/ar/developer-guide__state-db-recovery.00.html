استعادة قاعدة بيانات الحالة و FTS

للدليل الموجّه للمستخدم (ما الذي ينبغي إيقافه، وما الملفات بجانب state.db ، ولماذا ترفض أوامر الصيانة العمل أثناء وجود كاتب حي)، راجع استعادة تخزين الجلسات.

state.db يخزّن فئتين مختلفتين من البيانات:

  • sessions و messages هما سجل المحادثة المعتمد.
  • messages_fts* وجداولها و triggers المزامنة الخاصة بها فهارس بحث مشتقة.

يمكن فصل الفهارس المشتقة مؤقتًا. ويجب ألا تحوّل كتابة رسالة حية أو البحث فيها إلى إعادة بناء غير محدودة لسجل المحادثة كاملًا.

السلوك الحي عند تلف FTS

إذا أبلغت كتابة أو عملية بحث في FTS عن فئة خطأ التلف، فإن SessionDB:

  1. يسجّل الوسم الدائم fts_stale ؛
  2. يزيل triggers مزامنة FTS في المعاملة نفسها؛
  3. يعيد محاولة الكتابات المعتمدة دون مصبّات الفهارس المشتقة؛ و
  4. يخدم البحث من الصفوف المعتمدة عبر البديل LIKE.

لا تنفّذ العملية الحية الفاشلة FTS5('rebuild') أبدًا. وتظل ملكية الاستعادة القائمة دون تغيير: فقد يعيد فتح لاحق لـ SessionDB البناء تحت قفل القبول بين العمليات وحاجز الحامل الخارجي. وإذا تعذّر ذلك البناء المحمي، يظل FTS منفصلًا وتظل الكتابات المعتمدة متاحة، وتُبلِغ hermes doctor عن أمر الإصلاح الصريح.

السلوك الحي عند تلف الملف نفسه

إذا أبلغت كتابة حية عن SQLITE_CORRUPT / SQLITE_NOTADB مجردين (database disk image is malformed ، file is not a database) دون دليل على منشأ FTS، فالضرر في B-tree معتمدة أو المخطط أو freelist. وتعزل SessionDB ذلك المقبض عندئذٍ (StateDbCorruptError):

  1. تمرّر الكتابة الفاشلة الخطأ ذا النوع المحدَّد، ولا تُعاد محاولة أي شيء؛
  2. تفشل الكتابات اللاحقة على المقبض فورًا دون لمس الملف؛
  3. لا يعيد المقبض فتح اتصاله أبدًا بعد close() ؛ و
  4. close() يتخطّى checkpoint الصريح الخاص بـ WAL.

إيقاف الكتابات هو الحماية. ففي حالة فعلية، واصل مقبض الكتابة لنحو 50 دقيقة بعد أول خطأ بنيوي، ثم كتب 15 صفحة تحت أرقام صفحات غير صحيحة أثناء الإغلاق (استقبلت الصفحة 1 ورقةً من messages_fts_trigram_data)، فحوّل ملفًا تالفًا لكنه قابل للقراءة إلى ملف لا يُفتح أصلًا. وتخطّي checkpoint الصريح خط الدفاع الثاني؛ وعلى Python 3.12+، يعطّل العزل أيضًا checkpoint الخاص بـ SQLite عند إغلاق آخر اتصال (SQLITE_DBCONFIG_NO_CKPT_ON_CLOSE)، لذا يبقى الملف المصاحب -wal بعد close() للفحص الجنائي. وعلى Python 3.11، لا يتوفر ذلك المفتاح، وقد يظل SQLite ينفّذ checkpoint مرة عند الإغلاق، لذا انسخ state.db و state.db-wal و state.db-shm معًا قبل إعادة تشغيل أي شيء.

يعامل gateway ومسار تفريغ الوكيل العزلَ كملف مستبدَل: فتذهب سجلات المحادثة المعلّقة إلى sessions/<id>.jsonl ومخزن gateway pending_messages/ بدلًا من طابور إعادة المحاولة، ولا تُنفَّذ إعادة بناء FTS لمرة واحدة على الملف التالف أبدًا. والعزل لكل عملية — ويظل المقبض المشترك غير صالح لكل حامل حتى إعادة تشغيل العملية على ملف مُصلَح أو مستعاد. ولا تنفّذ hermes doctor --fix أثناء بقاء gateway قيد التشغيل. الخطوات التالية:

أو استعد أحدث لقطة من state-snapshots/.

الإصلاح الصريح

أوقف كل عملية يمكنها فتح قاعدة بيانات الـ profile قبل إصلاحها. وأبقِها متوقفةً طوال فترة الإصلاح والتحقق.

sessions repair ينشئ نسخة احتياطية من SQLite افتراضيًا، وينفّذ العمل البنيوي عبر مسار اللقطة والترقية المحمي في المستودع. ولا تنسخ state.db و state.db-wal و state.db-shm بصورة مستقلة باستخدام cp ؛ فهذه الملفات صورة SQLite حية واحدة.

بعد الإصلاح، تحقق من فحص السلامة ووسم التقادم ومجموعة triggers وأعداد الصفوف المعتمدة قبل إعادة تشغيل gateway:

يجب ألا يعيد استعلام الوسم أي صف، وأن توجد triggers FTS المتوقعة، وألا تنخفض أعداد الصفوف المعتمدة. وإذا فشل الإصلاح، فاحتفظ بقاعدة البيانات الحية والنسخة الاحتياطية المذكورة معًا؛ ولا تحذف صفوفًا معتمدة أبدًا لإخفاء خطأ في فهرس مشتق.

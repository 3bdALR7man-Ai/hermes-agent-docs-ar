هل تبحث عن استخدام Docker بوصفه terminal backend؟

تتناول هذه الصفحة تشغيل Hermes نفسه داخل Docker. أما إذا أردت أن ينفّذ Hermes استدعاءات terminal / execute_code الخاصة بالوكيل داخل حاوية sandbox في Docker (حاوية واحدة طويلة العمر تتشاركها عمليات Hermes — راجع issue #20561)، فذلك قسم إعدادات منفصل — terminal.backend: docker إضافة إلى terminal.docker_image و terminal.docker_volumes و terminal.docker_forward_env و terminal.docker_env و terminal.docker_run_as_host_user و terminal.docker_extra_args و terminal.docker_persist_across_processes و terminal.docker_orphan_reaper. راجع الإعدادات → Docker Backend للاطلاع على المجموعة الكاملة، بما فيها قواعد دورة حياة الحاوية.

اضبط الحدود في Docker:

ما الذي يفعله Dockerfile

تستند الصورة الرسمية إلى debian:13.4 وتتضمن:

  • Python 3.13 مع اعتماديات تُزامَن من ملف القفل (lockfile) عبر uv sync --frozen --no-install-project للإضافات (extras) المُدمجة في الصورة (all، messaging، وهوية Anthropic/Bedrock/Azure، و Hindsight، و Matrix)، يليها تثبيت قابل للتعديل (editable) لـ Hermes نفسه دون اعتماديات.
  • Node.js 26 + npm (لأتمتة المتصفح، وجسر WhatsApp، وحِزم TUI/Desktop، وأدوات بناء مساحة العمل)
  • Playwright مع Chromium (npx playwright install --with-deps chromium --only-shell)
  • ripgrep و ffmpeg و git و xz-utils كأدوات نظام
  • docker-cli — كي تتمكن الوكلاء العاملة داخل الحاوية من التحكم في Docker daemon على المضيف (اربط /var/run/docker.sock عبر bind-mount لتفعيل ذلك) لتنفيذ docker build و docker run وفحص الحاويات وغير ذلك.
  • openssh-client — يتيح استخدام SSH terminal backend من داخل الحاوية. إذ يستدعي SSH backend الملف التنفيذي ssh الخاص بالنظام؛ وبدونه كان يفشل بصمت في عمليات التثبيت داخل الحاويات.
  • جسر WhatsApp (scripts/whatsapp-bridge/)
  • s6-overlay v3 بوصفه PID 1 (بديلًا عن tini الأقدم) — يشرف على لوحة التحكم و gateways الخاصة بكل profile مع إعادة تشغيلها تلقائيًا عند الانهيار، ويحصد العمليات الفرعية الزومبي (zombie)، ويمرّر الإشارات (signals).

تتعامل الصورة مع /opt/hermes بوصفه شجرة تثبيت غير قابلة للتغيير وقت التشغيل. يجب تضمين إضافات Python (extras) الاختيارية ومساحات عمل Node وأصول TUI التي يلزم توفرها داخل Docker أثناء بناء الصورة؛ فعمليات التثبيت الكسول (lazy installs) وقت التشغيل معطّلة، كي لا تحاول الـ gateways الخاضعة للإشراف وأوامر docker exec hermes … كتابة ملفات الاعتماديات في شجرة المصدر المخصصة للقراءة فقط.

نقطة الدخول ENTRYPOINT للحاوية هي موزّع صغير (docker/entrypoint-dispatch.sh). عندما تمتلك الحاوية PID 1 (في Docker / Podman العاديين)، يُنفّذ (exec) الملف /init الخاص بـ s6-overlay فتحصل على شجرة الإشراف الكاملة الموضحة أدناه. أما عندما تغلّف منصةٌ ما نقطة دخول الصورة داخل نظام init خاص بها يعمل كـ PID 1 (مثل Fly.io Machines، و docker run --init، وبعض إعدادات Nomad/Kubernetes)، فإن /init سيتوقف مع الخطأ s6-overlay-suexec: fatal: can only run as pid 1 — ولذلك يشغّل الموزّع بدلًا من ذلك تهيئة stage2 مباشرة ثم ينفّذ الـ wrapper الرئيسي دون s6. في هذا المسار الاحتياطي يظل الأمر المطلوب يعمل، لكن الخدمات الخاضعة للإشراف (لوحة التحكم، و gateways الخاصة بكل profile) لا تكون متاحة.

في مسار PID 1، يقوم /init بما يلي:

  1. يشغّل /etc/cont-init.d/01-hermes-setup (= docker/stage2-hook.sh) بصلاحيات root: إعادة تعيين UID/GID اختياريًا، وإصلاح ملكية وحدة التخزين، وإنشاء .env / config.yaml / SOUL.md الأولية عند الإقلاع الأول، وتشغيل ترحيلات مخطط الإعدادات (config-schema migrations) غير التفاعلية ما لم يُضبط HERMES_SKIP_CONFIG_MIGRATION=1، ومزامنة المهارات المضمّنة.
  2. يشغّل /etc/cont-init.d/02-reconcile-profiles (= hermes_cli.container_boot): يمرّ على $HERMES_HOME/profiles/<name>/، ويعيد إنشاء خانة خدمة s6 الخاصة بـ gateway كل profile تحت /run/service/gateway-<profile>/، ولا يشغّل تلقائيًا إلا الخدمات التي كانت آخر حالة مسجّلة لها running (راجع الإشراف على gateway لكل profile).
  3. يشغّل خدمتَي s6-rc الثابتتين main-hermes و dashboard.
  4. ينفّذ CMD الخاص بالحاوية بوصفه البرنامج الرئيسي (/opt/hermes/docker/main-wrapper.sh)، والذي يوجّه الوسائط التي مرّرها المستخدم إلى docker run:
    • بلا وسائط → hermes (الافتراضي)
    • الوسيط الأول ملف تنفيذي موجود في PATH (مثل sleep أو bash) → يُنفَّذ مباشرة
    • أي شيء آخر → hermes <args> (تمرير الأمر الفرعي) تنتهي الحاوية عندما ينتهي هذا البرنامج الرئيسي، وبرمز الخروج نفسه.
تغيير جذري مقارنة بالصور السابقة لـ s6

أصبحت نقطة الدخول ENTRYPOINT للحاوية هي الموزّع entrypoint-dispatch.sh (الذي يفوّض إلى /init الخاص بـ s6-overlay تحت PID 1)، وليس /usr/bin/tini. تتصرف أنماط استدعاء docker run الخمسة الموثّقة جميعها (بلا وسائط، و chat -q "…"، و sleep infinity، و bash، و --tui) بالطريقة نفسها تمامًا كما في الصورة المعتمدة على tini. إذا كان لديك wrapper لاحق يعتمد على سلوك الإشارات الخاص بـ tini أو يستدعي /usr/bin/tini -- بشكل ثابت في الكود، فثبّت وسم الصورة السابق.

نموذج الصلاحيات

لا تتجاوز نقطة دخول الصورة إلا إذا أبقيت /init (أو ما يعادله، أي الـ shim القديم docker/entrypoint.sh الذي يمرّر إلى stage2 hook) ضمن سلسلة الأوامر. يعمل /init الخاص بـ s6-overlay بصلاحيات root كي يتمكن من تغيير ملكية وحدة التخزين (chown) عند الإقلاع الأول، ثم ينتقل إلى المستخدم hermes عبر s6-setuidgid لكل خدمة خاضعة للإشراف وللبرنامج الرئيسي أيضًا. يُرفض افتراضيًا تشغيل hermes gateway run بصلاحيات root داخل الصورة الرسمية، لأنه قد يترك ملفات مملوكة لـ root في /opt/data ويعطّل عمليات تشغيل لوحة التحكم أو الـ gateway لاحقًا. لا تضبط HERMES_ALLOW_ROOT_GATEWAY=1 إلا إذا كنت تقبل هذا الخطر عن قصد.

ينتقل docker exec تلقائيًا إلى المستخدم hermes

يعمل docker exec hermes <cmd> افتراضيًا بصلاحيات root داخل الحاوية، لكن الصورة تتضمن shim خفيفًا في /opt/hermes/bin/hermes (الأسبق في PATH) يكتشف المستدعين بصلاحيات root ويعيد تنفيذ الأمر بشفافية عبر s6-setuidgid hermes. لذلك فإن docker exec hermes login و docker exec hermes profile create … و docker exec hermes setup وغيرها تكتب جميعها ملفات مملوكة لـ UID 10000 — أي قابلة للقراءة من الـ gateway الخاضع للإشراف — دون الحاجة إلى خيار --user إضافي. أما المستدعون من غير root (العمليات الخاضعة للإشراف نفسها، و docker exec --user hermes، و kanban subagents داخل الحاوية) فيمرّون عبر مسار مختصر ينفّذ الملف التنفيذي الموجود في الـ venv مباشرة، فلا يوجد أي عبء إضافي على المسارات الأكثر استخدامًا.

إذا كنت تحتاج تحديدًا إلى docker exec يحتفظ بصلاحيات root (جلسات التشخيص، أو فحص حالة لا يصل إليها إلا root، أو ملفات خارج /opt/data يصادف أنها مملوكة لـ root)، فألغِ هذا السلوك لكل استدعاء على حدة:

يقبل الـ shim القيم 1 / true / yes (دون تمييز حالة الأحرف). وأي قيمة أخرى — بما في ذلك الأخطاء الإملائية مثل =0 — تؤدي إلى الانتقال للمستخدم غير الجذري، فلا يمكن إلغاء السلوك بصمت عن غير قصد. وإذا لم يكن s6-setuidgid متاحًا (في الإصدارات المخصصة التي أزالت s6-overlay)، يرفض الـ shim العمل بصلاحيات root ويخرج بالرمز 126 بدلًا من ذلك، كاشفًا عن خلل نموذج الصلاحيات بوضوح بدلًا من العودة إلى الفخ القديم الذي كان فيه docker exec hermes login يكتب auth.json بملكية root:root ويعطّل مصادقة الـ gateway الخاضع للإشراف مع كل رسالة من منصات المحادثة.

الإشراف على gateway لكل profile

يحصل كل profile يُنشأ بالأمر hermes profile create <name> تلقائيًا على خدمة gateway خاضعة لإشراف s6 ومسجّلة في /run/service/gateway-<name>/، مع إعادة تشغيل تلقائية تحافظ على الحالة عبر عمليات إعادة تشغيل الحاوية. راجع دعم عدة profiles أعلاه للاطلاع على سير العمل من جهة المستخدم وأوامر دورة الحياة.

مزايا الإشراف مقارنة بالصورة السابقة لـ s6:

  • يعيد s6-supervise تشغيل الـ gateway تلقائيًا عند انهياره بعد تأخير يقارب ثانية واحدة.
  • تخضع لوحة التحكم، عند تفعيلها بـ HERMES_DASHBOARD=1، للإشراف ضمن شجرة الإشراف نفسها وتحظى بإعادة التشغيل التلقائية ذاتها.
  • تحافظ docker restart وترقيات الصورة (docker compose up -d --force-recreate) وحالات الخروج غير المتوقعة على الـ gateways العاملة: إذ يقرأ مُسوّي cont-init الملف $HERMES_HOME/profiles/<name>/gateway_state.json ويعيد تشغيل الخانة إذا كانت آخر حالة مسجّلة running. ولا يُبقي الـ gateway متوقفًا بعد إعادة التشغيل إلا أمر صريح هو hermes gateway stop، إذ يسجّل الحالة stopped؛ أما إشارة SIGTERM التي ترسلها الحاوية/s6 عند إعادة التشغيل أو الترقية فتُعامل على أنها "لا يزال يعمل" فيُشغَّل تلقائيًا.
  • تُحفظ سجلات gateway الخاصة بكل profile تحت $HERMES_HOME/logs/gateways/<profile>/current (مع تدويرها بواسطة s6-log)، وتُلحق إجراءات المُسوّي بالملف $HERMES_HOME/logs/container-boot.log عند كل إقلاع. راجع أين تذهب السجلات للاطلاع على خريطة التوجيه الكاملة.

يعرض hermes status داخل الحاوية Manager: s6 (container supervisor). استخدم /command/s6-svstat /run/service/gateway-<name> للحصول على عرض المشرف الخام (لاحظ أن /command/ موجود في PATH لعمليات شجرة الإشراف فقط؛ لذا مرّر المسار المطلق عند الاستدعاء من docker exec).

المهارات وملفات بيانات الاعتماد

عند استخدام Docker بيئةً للتنفيذ (ليس بالطرق المذكورة أعلاه، بل عندما يشغّل الوكيل الأوامر داخل sandbox في Docker — راجع الإعدادات → Docker Backend)، يعيد Hermes استخدام حاوية واحدة طويلة العمر لجميع استدعاءات الأدوات، ويربط تلقائيًا (bind-mount) دليل المهارات (~/.hermes/skills/) وأي ملفات بيانات اعتماد تعلنها المهارات داخل تلك الحاوية كوحدات تخزين للقراءة فقط. تكون سكربتات المهارات وقوالبها ومراجعها متاحة داخل الـ sandbox دون إعداد يدوي، ولأن الحاوية تبقى طوال عمر عملية Hermes، فإن أي اعتماديات تثبّتها أو ملفات تكتبها تبقى متاحة لاستدعاء الأداة التالي.

تحدث المزامنة نفسها مع SSH و Modal backends — إذ تُرفع المهارات وملفات بيانات الاعتماد عبر rsync أو Modal mount API قبل كل أمر.

تثبيت مزيد من الأدوات في الحاوية

تأتي الصورة الرسمية مع مجموعة منتقاة من الأدوات (راجع ما الذي يفعله Dockerfile)، لكن ليست كل أداة قد يحتاجها الوكيل مثبّتة مسبقًا. هناك خمسة أساليب موصى بها، مرتبة تصاعديًا حسب الجهد المطلوب ومدى الديمومة.

أدوات npm أو Python — استخدم npx أو uvx

لأي أداة منشورة على npm أو PyPI، اطلب من Hermes تشغيلها عبر npx (لـ npm) أو uvx (لـ Python) وأن يتذكر ذلك الأمر في ذاكرته الدائمة. وإذا كانت الأداة تحتاج إلى ملف إعدادات أو بيانات اعتماد، فاطلب منه وضعها تحت /opt/data (مثل /opt/data/<tool>/config.yaml).

تُجلب الاعتماديات عند الطلب وتُخزَّن مؤقتًا طوال عمر الحاوية. وتبقى الإعدادات المكتوبة تحت /opt/data بعد إعادة تشغيل الحاوية لأنها موجودة في دليل المضيف المربوط عبر bind-mount. أما ذاكرة الحزم المؤقتة نفسها فيُعاد بناؤها بعد docker rm، لكن npx و uvx يعيدان جلبها بشفافية في المرة التالية التي تُشغَّل فيها الأداة.

أدوات أخرى (حزم apt، ملفات تنفيذية) — ثبّتها واطلب تذكّرها

لأي شيء خارج npm أو PyPI — حزم apt، والملفات التنفيذية الجاهزة، وبيئات تشغيل اللغات غير الموجودة أصلًا في الصورة — أخبر Hermes بكيفية تثبيته (مثل apt-get update && apt-get install -y <package>) واطلب منه تذكّر أمر التثبيت. تبقى الأداة متاحة طوال ما تبقى من عمر الحاوية، وسيعيد Hermes تشغيل أمر التثبيت بعد إعادة تشغيل الحاوية عندما يحتاج إلى الأداة مجددًا.

يناسب هذا الأسلوب الأدوات السريعة التثبيت التي تُستخدم أحيانًا. أما الأدوات التي تُستخدم باستمرار، فالأفضل لها الأسلوب التالي.

أدوات معقدة أو حزم متعددة الخدمات — شغّل حاوية sidecar

للأدوات التي تأتي مع خدمتها الخاصة (قاعدة بيانات، أو خادم ويب، أو طابور رسائل، أو مزرعة متصفحات headless) أو التي تكون أثقل من أن تعيش داخل حاوية Hermes، شغّلها كحاوية منفصلة على شبكة Docker مشتركة. يصل Hermes إلى الـ sidecar عبر اسم الحاوية، بالطريقة نفسها التي يصل بها إلى خادم inference محلي (راجع الاتصال بخوادم inference المحلية).

من داخل حاوية Hermes، يمكن الوصول إلى الـ sidecar على http://my-tool:<port> (أو أي بروتوكول يقدّمه). يُبقي هذا النمط دورة حياة كل خدمة وحدود مواردها ووتيرة ترقيتها مستقلة، ويتجنب تضخيم صورة Hermes باعتماديات لا تحتاجها إلا أداة واحدة.

أدوات مفيدة على نطاق واسع — افتح issue أو pull request

إذا كان من المرجح أن تفيد أداةٌ ما معظم مستخدمي Hermes Agent، ففكّر في المساهمة بها في المشروع الأصلي بدلًا من الاحتفاظ بها في صورة مشتقة خاصة. افتح issue أو pull request في مستودع hermes-agent تصف فيه الأداة وحالة استخدامها. الأدوات التي تُضمَّن في الصورة الرسمية تفيد جميع المستخدمين وتُجنّبك عبء صيانة نسخة متفرعة (fork) لاحقة.

نقاط أساسية
  • استخدم اسم الحاوية (vllm) كاسم للمضيف — وليس localhost أو 127.0.0.1، فهما يشيران إلى حاوية Hermes نفسها.
  • يجب أن تطابق قيمة model قيمة --served-model-name التي مرّرتها إلى vLLM.
  • اضبط api_key على أي سلسلة نصية غير فارغة (يتطلب vLLM وجود الترويسة لكنه لا يتحقق منها افتراضيًا).
  • لا تضع شرطة مائلة في نهاية base_url.

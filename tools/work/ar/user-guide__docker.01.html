دعم عدة Profiles

يدعم Hermes عدة profiles — وهي مجلدات فرعية منفصلة ضمن ~/.hermes/ تتيح لك تشغيل وكلاء مستقلين (بـ SOUL ومهارات وذاكرة وجلسات وبيانات اعتماد مختلفة) من تثبيت واحد. داخل صورة Docker الرسمية، تتعامل شجرة الإشراف في s6 مع كل profile كخدمة خاضعة للإشراف من الدرجة الأولى، لذا فإن النشر المُوصى به هو حاوية واحدة تستضيف جميع الـ profiles.

يحصل كل profile يُنشأ باستخدام hermes profile create <name> على:

  • خانة خدمة s6 مخصصة في /run/service/gateway-<name>/، يسجّلها وقت التشغيل ديناميكيًا — دون الحاجة إلى إعادة بناء الحاوية.
  • إعادة تشغيل تلقائية عند الانهيار، مع إدارة فترات الانتظار (backoff) بواسطة s6-supervise.
  • سجلات دوّارة لكل profile في ${HERMES_HOME}/logs/gateways/<name>/current (10 أرشيفات × 1 MB لكل منها).
  • استمرار الحالة عبر عمليات إعادة تشغيل الحاوية: يقرأ الـ reconciler وقت الإقلاع ملف gateway_state.json من مجلد كل profile ولا يعيد تشغيل الخانة إلا للـ profiles التي كانت آخر حالة مسجّلة لها running. ولا يبقى متوقفًا بعد إعادة التشغيل إلا الـ gateway الذي أوقفته صراحةً (hermes gateway stop) — أما إعادة تشغيل الحاوية أو ترقية الصورة أو الخروج غير المتوقع فتُبقي الحالة المسجّلة running، فيبدأ الـ gateway تلقائيًا في الإقلاع التالي.

يحصل profile مُنشأ من المضيف باستخدام ~/.hermes مربوط بـ bind-mount على دليله دون slot (لا تستطيع عملية المضيف الوصول إلى /run/service في الحاوية). وداخل الحاوية يسجل hermes -p <name> gateway start الـ slot المفقود عند الطلب ويبدأه — دون حاجة إلى docker restart. ولا يفعل ذلك إلا start، وللدليل الحقيقي للـ profile فقط (الذي يحمل SOUL.md); stop/restart على profile غير مسجّل واسم -p مكتوب خطأ ما زالا يفشلان بـ ✗ no such gateway.

تعمل أوامر دورة الحياة التي تشغّلها على الجهاز المضيف بالطريقة نفسها من داخل الحاوية:

في الخلفية، يُعترض hermes gateway start/stop/restart داخل الحاوية ويُوجَّه إلى s6-svc على مجلد الخدمة الصحيح؛ فلا تحتاج إلى تعلّم أوامر s6 مباشرةً. وللاطلاع على الحالة الخام للمشرف، استخدم /command/s6-svstat /run/service/gateway-<name> (لاحظ أن /command/ لا يكون ضمن PATH إلا للعمليات التي تُطلقها شجرة الإشراف — لذا عند الاستدعاء من docker exec، مرّر المسار المطلق).

الوصول إلى أكثر من profile من خارج الحاوية

هناك واجهتان مختلفتان تصلان إلى الـ gateway الخاص بـ profile من الخارج، وتتصرفان بشكل مختلف — فلا تخلط بينهما:

Hermes Desktop (ولوحة التحكم على الويب). يتواصل اتصال Remote Gateway في تطبيق Desktop مع backend من نوع hermes dashboard (افتراضيًا على المنفذ 9119، ويُفعَّل عبر HERMES_DASHBOARD=1) — وليس مع خادم OpenAI API. يخدم backend واحد للوحة التحكم كل الـ profiles الموجودة معه على الجهاز نفسه: إذ يرسل مبدّل الـ profiles في التطبيق الـ profile الهدف مع كل طلب، ويفتح الـ backend مجلد HERMES_HOME الخاص بذلك الـ profile على القرص. لذا لا تحتاج إلى منفذ ثانٍ — أو اتصال ثانٍ — لكل profile في Desktop ؛ فاتصال واحد على :9119 يغطيها جميعًا عبر المبدّل.

عملاء API المتوافقون مع OpenAI (Open WebUI و LobeChat و /v1/...). يتواصل هؤلاء مع خادم API الخاص بكل profile ، والذي يرتبط بالمنفذ 8642 لكل profile (تُحدَّد القيمة من API_SERVER_PORT / platforms.api_server.extra.port — فلا يوجد تخصيص تلقائي ولا مفتاح config.yaml/gateway.port). إذا أردت أن يصل عميل إلى profile ثانٍ محدد، فامنح ذلك الـ profile قيمة API_SERVER_PORT مميزة في ملف البيئة الخاص به .env)، وإلا فسيحاول الـ gateway الخاص به الارتباط بالمنفذ 8642 أيضًا ويتعارض مع الـ profile الافتراضي:

أبقِ API_SERVER_PORT في ملف البيئة الخاص .env)، ولا تضعه أبدًا في كتلة environment: على مستوى الحاوية — فالقيمة العامة ستفرض المنفذ نفسه على كل الـ profiles فتتصادم. ومع شبكات bridge ، انشر المنفذ الإضافي في docker-compose.yml (- "8643:8643")؛ أما مع network_mode: host فهو قابل للوصول بالفعل على الجهاز المضيف. ولا يتأثر اتصال الـ profile الافتراضي على المنفذ 8642.

متى تحتاج فعلًا إلى حاوية منفصلة

النمط الافتراضي هو تشغيل الـ profiles داخل الحاوية الواحدة. لا تشغّل حاوية منفصلة لكل profile إلا عندما يكون لديك سبب محدد:

  • عزل الموارد لكل عبء عمل — مثلًا، لا ينبغي لجلسة أداة متصفح خرجت عن السيطرة في الـ profile A أن تتسبب في نفاد ذاكرة (OOM) الـ profile B. وتمنحك الحاويات --memory / --cpus لكل profile.
  • تثبيت مستقل لإصدار الصورة — وسوم (tags) مختلفة للصورة الأصلية (upstream) لكل عبء عمل.
  • تقسيم الشبكة — شبكات Docker منفصلة لكل profile (مثل واحدة موجّهة للعملاء وأخرى داخلية).
  • الامتثال / نطاق الضرر — لا تتشارك بيانات الاعتماد المختلفة أبدًا شجرة عمليات واحدة على مستوى نظام التشغيل.

أين تذهب السجلات

تحتوي حاوية s6 على أربعة مصادر مختلفة للسجلات، وسؤال "لماذا لا يُظهر الـ gateway أي شيء في docker logs" مفاجأة شائعة. إليك ملخصًا سريعًا:

في الحاوية التفاعلية ذات إدخال وإخراج الطرفية (مثل docker run -it ... --tui أو bash)، يملك الأمر الذي يعمل في المقدمة الطرفية. يضبط entrypoint القيمتين الافتراضيتين S6_LOGGING=2 و S6_CMD_USE_TERMINAL=1 حتى لا يكتب إخراج الـ gateway ولوحة التحكم الخاضعين للإشراف فوق تلك الشاشة. ويذهب إخراج وحدة التحكم الخاص بهما إلى سجل s6 الشامل المُدوَّر في /run/uncaught-logs/current داخل الحاوية. وتبقى سجلات ملفات الـ gateway الخاصة بكل profile وسجلات Hermes العادية متاحة في المسارات المذكورة أعلاه. ودليل السجل الشامل هو تخزين وقت التشغيل، لذا لا يبقى بعد إعادة تشغيل الحاوية أو إزالتها.

تواصل الحاويات بلا واجهة (headless) تمرير إخراج الخدمات إلى docker logs. وتتقدّم إعدادات S6_LOGGING و S6_CMD_USE_TERMINAL الصريحة على هذه القيم الافتراضية التفاعلية.

نتيجتان عمليتان ينبغي معرفتهما:

  • النسخة المحفوظة في الملف logs/gateways/<profile>/current هي ما يبقى بعد إعادة تشغيل الحاوية. إذ لا يحتفظ docker logs إلا بمخرجات عمر الحاوية الحالية (ويُمسح عند docker rm)؛ بينما تبقى الملفات الدوّارة على الـ volume المُركَّب عبر bind-mount.
  • شكل سطر التدقيق الذي يكتبه boot reconciler هو <iso-timestamp> profile=<name> prior_state=<state> action=<registered|started>، لذا فإن تنفيذ grep profile=coder ~/.hermes/logs/container-boot.log سريعًا يكشف متى استُعيد profile معيّن آخر مرة وما إذا كان s6 قد شغّله تلقائيًا.

هل تبحث عن استخدام Docker بوصفه terminal backend?

تتناول هذه الصفحة تشغيل Hermes نفسه داخل Docker. أما إذا أردت أن ينفّذ Hermes استدعاءات terminal / execute_code الخاصة بالوكيل داخل حاوية sandbox في Docker (حاوية واحدة طويلة العمر تتشاركها عمليات Hermes — راجع issue #20561)، فذلك قسم إعدادات منفصل — terminal.backend: docker إضافة إلى terminal.docker_image, terminal.docker_volumes, terminal.docker_forward_env, terminal.docker_env, terminal.docker_run_as_host_user, terminal.docker_extra_args, terminal.docker_persist_across_processes و terminal.docker_orphan_reaper. راجع الإعدادات → Docker Backend للاطلاع على المجموعة الكاملة، بما فيها قواعد دورة حياة الحاوية.

اختياري: جسر الصوت لسطح مكتب Linux

يحتاج الوضع الصوتي داخل Docker إلى أمرين منفصلين كي يعمل: يجب السماح لـ Hermes بفحص أجهزة الصوت داخل الحاوية، ويجب أن تتمكن الحاوية من الوصول إلى خادم الصوت على جهازك المضيف. يغطي الإعداد أدناه توصيلات الصوت على المضيف لأسطح مكتب Linux التي توفّر socket متوافقًا مع PulseAudio ، بما في ذلك كثير من إعدادات PipeWire.

تنبيه

هذا حلّ بديل خاص بأسطح مكتب Linux ، وليس ميزة عامة في Docker Desktop. وهو مفيد حين يكون الصوت يعمل لديك على المضيف وتريد استخدام الوضع الصوتي في CLI داخل حاوية Hermes. إذا ظل Hermes يعرض الرسالة Running inside Docker container -- no audio devices، فاستخدم إصدارًا يتضمن دعم فحص الصوت داخل Docker عبر PULSE_SERVER / PIPEWIRE_REMOTE.

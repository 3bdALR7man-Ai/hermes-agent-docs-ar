وضع بلا وكيل (مهام السكربت فقط)

للمهام المتكررة التي لا تحتاج إلى استدلال LLM — مراقِبات حراسة كلاسيكية، تنبيهات القرص/الذاكرة، نبضات الحياة، اختبارات CI — مرّر no_agent=True عند الإنشاء. يُشغّل المُجدوِل سكربتك حسب الجدول ويُسلِّم مخرجاته القياسية مباشرة، متخطّيًا الوكيل كليًا:

الدلالات:

  • مخرجات السكربت القياسية (بعد التشذيب) → تُسلَّم حرفيًا كالرسالة.
  • مخرجات قياسية فارغة → دورة صامتة، بلا تسليم. هذا نمط مراقب الحراسة: "قل شيئًا فقط عند وجود خطأ".
  • خروج بكود غير صفري أو تجاوز المهلة → يُسلَّم تنبيه خطأ، حتى لا يفشل مراقب حراسة معطّل بصمت.
  • {"wakeAgent": false} في السطر الأخير → دورة صامتة (نفس البوابة التي تستخدمها مهام LLM).
  • بلا tokens، بلا نموذج، بلا احتياطي مزوّد — لا تلامس المهمة طبقة الـ inference إطلاقًا.

.sh / .bash عبر bash من PATH عند توفّره، وإلا فعبر /bin/bash (مهم على Windows Git Bash). يُشغَّل أي شيء آخر عبر مفسّر Python الحالي (sys.executable). يجب أن تُحلّ السكربتات داخل $HERMES_HOME/scripts/ — تُقبَل الأسماء النسبية، والمسارات المطلقة، والمسارات ذات البادئة ~ مقبولة إذا بقي الهدف النهائي في ذلك المجلد؛ وتُرفض المسارات التي تخرج منه. ويمكن لـ Python script أو monitor_script تثبيت venv يديرها المستخدم (للحزم التي لا يتضمنها وقت تشغيل Hermes) بتمرير --interpreter ~/venvs/.../bin/python عند الإنشاء/التحرير — راجع استخدام بيئة Python الخاصة بك. تظل venv المُدارة من Hermes ملكًا لـ Hermes؛ ولا يُثبّت ولا يُستعاد شيء تلقائيًا. تُنقّى بيئة العملية الفرعية، لذا فإن بيانات اعتماد API للمزوّد وغيرها من الأسرار المُدارة من Hermes تكون لا تُورَّث إلى سكربتات cron.

منح سكربت بيانات اعتماد

السكربت الذي يحتاج إلى المصادقة لخدمة خارجية (API token أو مفتاح حساب خدمة) يحصل عليها بالطريقة نفسها التي تحصل بها الطرفية والعمليات الفرعية لـ execute_code — أعلن اسم المتغير في config.yaml الخاص بـ profile المالك، وعرّف قيمته في .env الخاص بذلك profile (أو مصدر أسرار):

يُمرّر المتغير إلى بيئة السكربت بقيمة profile المالك: للمهمة التي تخص profile يخدمه gateway متعدد profiles أو backend الخاص بـ Desktop/لوحة التحكم، تُحدّد القيمة عبر نطاق أسرار ذلك profile، لا من بيئة عملية profile الإطلاق، ولا تصل بيانات اعتماد .env الخاصة بذلك profile إلى سكربتات profile آخر. لا يمكن إعلان بيانات اعتماد المزوّد التي يديرها Hermes (OPENAI_API_KEY و tokens الخاصة بـ gateway وغيرها) — ترفضها أداة التنقية. في تثبيت profile واحد، يرث السكربت ما وضعه .env الخاص بـ gateway في بيئة العملية، كما سابقًا. سجّل الوجود (set/MISSING) لا القيمة: تُسلّم مخرجات السكربت حرفيًا.

تسلسل المهام باستخدام context_from

تُشغَّل مهام cron في جلسات معزولة بلا ذاكرة عن التشغيلات السابقة. لكن أحيانًا تكون مخرجات مهمة بالضبط ما تحتاجه المهمة التالية. يربط المعامل context_from هذا الاتصال تلقائيًا — يحصل prompt المهمة B على أحدث مخرجات المهمة A مُلحَقة كسياق وقت التشغيل.

كيف يعمل:

  • عندما تُطلَق المهمة 2، يقرأ Hermes أحدث مخرجات المهمة 1 من ~/.hermes/cron/output/{job1_id}/*.md
  • تُلحَق تلك المخرجات بـ prompt المهمة 2 تلقائيًا
  • لا تحتاج المهمة 2 إلى ترميز "اقرأ هذا الملف" صراحة — بل تتلقّى المحتوى كسياق
  • يمكن أن يكون طول السلسلة أي طول: المهمة 1 → المهمة 2 → المهمة 3 → ...

ما الذي يقبله context_from يقبل:

الصيغةمثال
معرّف مهمة واحد (نص)context_from="a1b2c3d4"
معرّفات مهام متعددة (قائمة)context_from=["job_a", "job_b"]

تُدمَج المخرجات بالترتيب المذكور.

الاستمرارية: حمل مخرجات التشغيل السابق

اضبط continuity=true وستحقن المهمة مخرجاتها الخاصة الأحدث في كل تشغيل. تبدأ المهام المتكررة عادةً كل تشغيل بفقدان للذاكرة — يعيد كشّاف أخبار الإبلاغ عن نفس الأخبار، ويعيد مراقِب التنبيه بشأن نفس الحالة. مع تفعيل الاستمرارية، تستيقظ المهمة وهي ترى ما أبلغت عنه آخر مرة ويمكنها إزالة التكرار والمتابعة من حيث توقفت:

ليس للتشغيل الأول مخرجات سابقة، لذا يُنفَّذ الـ prompt كما هو. تُتخطَّى دورات مراقبة صامتة (no_change)، والمخرجات الفارغة، وسجلات المراجعة wakeAgent=false عند اختيار السياق، لذا تحافظ فترة الهدوء على آخر مخرجات جوهرية. تبقى ملفات المراجعة على القرص. تظل مستندات الخطأ مؤهّلة لإعطاء التشغيل التالي سياق تعافٍ؛ فهذا ليس مرشّح سجلّ يقتصر على النجاح فقط. في التشغيلات اللاحقة، تُلحَق المخرجات السابقة بإطار استمرارية ("تجنّب تكرار ما أُبلغ عنه بالفعل"). تُدمَج بحرية مع مهام أعلى في السلسلة (context_from=["<other_job_id>"] مع continuity=true)، وتُطفئها continuity=false عند التحديث مع الإبقاء على مدخلات context_from الأخرى. داخليًا، تُخزَّن العلامة كمُدخل محجوز self ضمن context_from.

من الـ CLI: hermes cron create "every 6h" "Scan for news" --continuity ، و hermes cron edit <job_id> --continuity / --no-continuity لتبديلها على مهمة موجودة. يظهر نفس المفتاح في محرر cron الخاص بلوحة التحكم وفي مربع حوار routine الخاص بـ Bot Mode في التطبيق المكتبي.

متى تستخدمه:

  • خطوط أنابيب متعددة المراحل (جمع → تصفية → تنسيق → تسليم)
  • مهام متتابعة حيث يعتمد عمل الخطوة N على مخرجات الخطوة N−1
  • أنماط التوزيع/التجميع حيث تُجمِّع مهمة واحدة نتائج عدة مهام أخرى
  • كشّافات/مراقِبات متكررة يجب أن تزيل التكرار عن تقريرها السابق (continuity=true)

تعافي المزوّد

ترث مهام cron مزوّديك الاحتياطيين المُعدّين وتدوير مجمّع بيانات الاعتماد. إذا كان مفتاح API الأساسي محدود المعدل أو أعاد المزوّد خطأً، يمكن لوكيل cron:

  • الرجوع إلى مزوّد بديل في مجمّع بيانات الاعتماد لديك للمزوّد نفسه. ينطبق ذلك على كل مهمة، مثبتة المسار أو غير مثبتة.
  • التدوير إلى بيانات الاعتماد التالية من fallback_providers (أو fallback_model القديم) في config.yaml — المهام غير مثبتة المسار فقط. يشمل ذلك الفشل عند تحديد بيانات الاعتماد قبل بدء التشغيل، وخطأ المزوّد أثناءه.

المهمة التي تملك provider, model أو base_url الخاص بها (مضبوطًا باستخدام --provider / --model, --pin أو لوحة التحكم أو jobs.json) لا ترجع مطلقًا إلى السلسلة العامة. يحدد التثبيت المسار الذي تعمل عليه المهمة، وإدخال الاحتياط مزوّد مختلف وغالبًا نموذج مختلف، لذا عند فشل المسار المثبّت يفشل التشغيل ويذكر تنبيه الفشل ذلك. وهي القاعدة نفسها التي يطبقها تفويض subagents على وكيل فرعي مثبّت المسار. للاحتفاظ بالاحتياط لمهمة، اتركها غير مثبتة: فهي تتبع cron.model / cron.model_provider (أو النموذج الرئيسي) وتعبر السلسلة مثل أي مهمة غير مثبتة.

قبل هذه القاعدة، كان يمكن لمهمة مثبّتة فشل مزوّدها أن تعمل على أول إدخال fallback_providers ناجح بدلًا منه، مع إشعار من سطر واحد في مخرجاتها. إذا اعتمدت على ذلك، فأزل تثبيت المهمة (hermes cron edit <job_id> --unpin) واضبط النموذج عبر cron.model بدلًا منه.

لذلك لا يؤدي مفتاح واحد بلغ حد المعدل إلى فشل تشغيل يملك بيانات اعتماد أخرى للمزوّد نفسه، وتظل المهام غير المثبتة تتجاوز انقطاع المزوّد إذا كانت سلسلة احتياط مضبوطة.

إخفاقات التشغيل (last_error)

يسجّل تشغيل الوكيل الفاشل last_error موجزًا، مرئيًا في قوائم المهام وفي /cron list مع تنقيح أنماط بيانات الاعتماد وبيانات اعتماد URL (بما في ذلك الأخطاء المخزّنة سابقًا). هذا منفصل عن last_fire_error (تسليم المُجدوِل) و last_delivery_error (التسليم). يمكن أن تكون تلك الحقول فارغة بشكل صحيح عندما يفشل الوكيل نفسه.

لفحص خلل اتصال، افحص وثيقة التشغيل تحت cron/output/<job_id>/ في مجلد Hermes النشط الرئيسي. يتضمن قسم ## Error فيها التتبع المتسلسل (traceback)، مع تنقيح أنماط بيانات الاعتماد وبيانات اعتماد URL. يستخدم الملف صلاحيات ملف المخرجات الخاصة الحالية؛ لا تُلتقَط المتغيرات المحلية في التتبع. تحتفظ إشعارات التسليم و last_error بالخطأ الموجز فقط، لا التتبع الكامل. راجع التشخيصات قبل مشاركتها: التنقيح ليس ضمانًا بأن بيانات التطبيق العشوائية غير حساسة.

الإطلاقات المجدولة الفائتة (last_fire_error)

على النشرات المُستضافة (cron مُدار)، ينتقل الإطلاق المجدول من مُجدوِل المنصة عبر لوحة التحكم إلى خادم الـ API الداخلي الخاص بالـ gateway. إذا فشل هذا التسليم النهائي — كانت عملية الـ gateway متوقفة، أو لم يبدأ مستمع خادم الـ API الخاص بها قط — لا يبدأ التشغيل أبدًا، فلا يوجد سجلّ تنفيذ ولا last_status لفحصه. العلامة المميزة: تعمل المهمة في كل مرة تُطلقها يدويًا، لكنها لا تُطلَق تلقائيًا أبدًا.

تُختَم هذه الحالات الفائتة على سجلّ المهمة كـ last_fire_error (طابع زمني + السبب) وتُعرَض عبر:

  • cronjob_manage الأداة → action: "list" — حقل last_fire_error الحقل
  • hermes cron list: تحذير أحمر من تنفيذ فائت تحت المهمة
  • hermes cron doctor: نتيجة تنفيذ فائت لكل مهمة تجعل الأمر يخرج بالقيمة 1
  • عرض المهمة في لوحة التحكم

يعكس الختم دائمًا صحة الإطلاق التلقائي الحالية: يُستبدَل بإخفاقات أحدث ويُمسَح تلقائيًا عند التشغيل الناجح التالي. إن رأيته، فالمهمة وجدولها بخير — الجانب الخاص بالـ gateway من مسار الإطلاق يحتاج انتباهًا (الأكثر شيوعًا، أعد تشغيل الـ gateway عبر مُشرِفه ليُحمِّل بيئة الـ profile الكاملة: hermes gateway restart).

سياسة التشغيل المحلي الفائت

إذا كان الـ gateway متوقفًا (أو يعيد التشغيل) عندما مرّ الوقت المجدول لمهمة متكررة، تُدرِك المهمة الفوات مرة واحدة عندما يعود المُجدوِل: تُطلَق فترة فائتة داخل فجوة إعادة تشغيل مرة واحدة بالضبط، ولا تُشغَّل أبدًا فترة سبق تشغيلها قبل إعادة التشغيل مرة أخرى، وينهار انقطاع طويل إلى تشغيل واحد بدلًا من تشغيل لكل فترة فائتة. لا تُدرِك المهام المُوقَّفة الفوات أبدًا. يظهر كل تدارُك في hermes cron list كـ ⚠ late / ⚠ catch-up after missed fire.

تدارك الإطلاقات الفائتة

عندما يكون مُجدوِل خارجي نشطًا (cron مُدار في النشرات المُستضافة)، يُشغّل الـ gateway أيضًا اجتياح تدارُك: تُطالَب مهمة مرّ وقتها المجدول دون إطلاق مُسلَّم — وانقضت نافذة سماحها — وتُشغَّل محليًا، لذا يكلّف انقطاع في تسليم الإطلاق دقائق بدلًا من اليوم بأكمله. يُزال تكرار الاجتياح مقابل إعادات محاولة المُجدوِل المتأخرة باستخدام نفس ادّعاء المخزن المستخدم للإطلاقات العادية.

لا تحتاج النشرات المحلية (المُنقِّط المدمج) إلى هذا — يلتقط المُنقِّط بالفعل المهام المتأخرة في دورته التالية.

صيغ الجدولة

التشغيلات اليدوية غير متزامنة

cronjob(action="run") المهمة فورًا في الخلفية (مثل delegate_task): يعود استدعاء الأداة فورًا بمقبض، وتعود نتيجة المهمة — نجاح/فشل، هدف التسليم، التشغيل المجدول التالي، ومقتطف من المخرجات — إلى المحادثة كرسالة جديدة عند انتهاء التشغيل. يمكن للوكيل (ولك) الاستمرار في العمل في الأثناء، وتُرفَض مهمة قيد التشغيل بالفعل برسالة "already running" بدلًا من الإطلاق المزدوج.

يمكنك أيضًا تمرير prompt مع action="run" لحقن سياق مؤقت خاص بذلك التشغيل:

يُلحَق السياق بـ prompt المهمة المخزَّن تحت ترويسة ## Run Context لذلك الإطلاق الوحيد فقط — لا يُخزَّن أبدًا في تعريف المهمة، ويمرّ بنفس فحص حقن الـ prompt الذي تمرّ به الـ prompts المخزَّنة.

تعود بيئات التشغيل التي لا يمكنها استقبال نتائج منفصلة (hermes -z, hermes cron run من CLI، جلسات cron الفرعية، عمّال Kanban) إلى التنفيذ المتزامن تلقائيًا.

Toolsets المتاحة لمهام cron

يُشغّل cron كل مهمة في جلسة وكيل جديدة بلا منصة محادثة مرفقة. افتراضيًا، يحصل وكيل cron على toolset الذي أعددته لمنصة cron في hermes tools — ليس افتراضي CLI، ولا كل شيء تحت الشمس.

تحكّم أدقّ لكل مهمة متاح عبر حقل enabled_toolsets على cronjob.create (أو على مهمة موجودة عبر cronjob.update):

عندما يُضبَط enabled_toolsets على مهمة، فهو يغلب؛ وإلا فيغلب إعداد منصة cron في hermes tools في إعدادات منصة cron تتقدم؛ وإلا يرجع Hermes إلى القيم الافتراضية المدمجة. إذا تعذّرت قراءة إعدادات toolset لمنصة cron أصلًا (مثل كتلة platform_toolsets غير سليمة في config.yaml)، يفشل التشغيل بخطأ مسجّل بدلًا من العمل بصمت بكل الأدوات — افحص hermes cron list / hermes cron doctor. هذا مهم لضبط التكلفة: حمل browser, delegation في كل مهمة صغيرة من نوع "اجلب الأخبار" يُضخّم prompt مخطط الأدوات في كل استدعاء LLM.

إذا كانت المهمة تتحكم في موقع سجّلت دخولك إليه، فلا بد من تجهيز تسجيل الدخول قبل التشغيل — ليس للنبضة المجدولة من يجيب عن prompt. التشغيل المجدول وغير المراقَب يغطي هذا الإعداد.

تخطّي الوكيل كليًا: wakeAgent

إذا أرفقت مهمة cron الخاصة بك سكربت فحص مسبق (عبر script=)، يمكن للسكربت أن يقرر وقت التشغيل ما إذا كان على Hermes استدعاء الوكيل أصلًا. أصدر سطر مخرجات قياسية أخير بالصيغة:

…ويتخطّى cron تشغيل الوكيل كليًا لهذه الدورة. مفيد للاستطلاعات المتكررة (كل 1–5 دقائق) التي تحتاج فقط إلى إيقاظ الـ LLM عندما تتغير الحالة فعلًا — وإلا فأنت تدفع ثمن أدوار وكيل بلا محتوى مرارًا وتكرارًا.

عندما تُحذَف wakeAgent ، تكون القيمة الافتراضية true (استيقظ الوكيل كالمعتاد).

وصفات: بوابات رخيصة قبل التشغيل

تمنحك بوابة wakeAgent تمنحك طريقة بكلفة $0 لتحديد ما إذا كانت المهمة المجدولة ستستهلك أي tokens من LLM أصلًا. تغطي ثلاثة أنماط معظم حالات الاستخدام.

بوابة تغيّر الملف — تُشغَّل فقط عندما يكون لملف مراقَب محتوى جديد منذ آخر دورة ناجحة. يسجّل المُجدوِل last_run_at لكل مهمة؛ قارنه بزمن تعديل الملف (mtime).

بوابة علامة خارجية — تُشغَّل فقط عندما تكون عملية أخرى قد أشارت إلى الجاهزية (مثل، يُسقط hook للنشر ملفًا، أو تضبط مهمة CI قيمة في مخزن حالتك).

بوابة عدّ SQL — تُشغَّل فقط عندما توجد صفوف جديدة لمعالجتها في قاعدة بياناتك الخاصة. يمكن للسكربت أيضًا تمرير العدد إلى الوكيل عبر context ، حتى يعرف الوكيل كمّية ما ينظر إليه دون إعادة الاستعلام.

يعمل النمط نفسه لأي مصدر بيانات يمكنك الاستعلام عنه من سكربت — Postgres، أو واجهة HTTP API، أو مخزن حالتك الخاص — دون تضمين مُقيِّم SQL داخل نظام cron الفرعي.

نصيحة

أداة Hermes الخاصة ~/.hermes/state.db الخاص بـ Hermes نفسه مخطط داخلي يتغيّر بين الإصدارات. لا تستعلم عنه من بوابة قبل التشغيل — وجّه بدلًا من ذلك إلى قاعدة بياناتك أو تغذيتك الخاصة.

الفضل: طرحت هذه المجموعة من الوصفات استكشاف @iankar8 في #2654، الذي اقترح إضافة triggers من نوع sql/file/command كآلية موازية. تغطّي بوابة script + wakeAgent تغطي بالفعل الحالات الثلاث بكلفة $0، لذا أُنجز العمل على هيئة توثيق بدلًا من ذلك.

تسلسل المهام: context_from

يمكن لمهمة cron استهلاك أحدث مخرجات ناجحة لمهمة أخرى أو أكثر بسرد أسمائها (أو معرّفاتها) في context_from:

تُحقَن أحدث المخرجات المكتملة للمهام المُشار إليها فوق الـ prompt كسياق لهذا التشغيل. يجب أن يكون كل إدخال أعلى في السلسلة معرّف مهمة أو اسمًا صالحًا (راجع cronjob action="list"). ملاحظة: يقرأ التسلسل أحدث مخرجات مكتملة — لا ينتظر مهامًا أعلى في السلسلة تعمل في نفس الدورة.

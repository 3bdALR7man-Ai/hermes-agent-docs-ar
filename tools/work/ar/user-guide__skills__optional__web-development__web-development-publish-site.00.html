نشر الموقع

خذ موقعًا، أو لوحة تحكم، أو تطبيق ويب بناه المستخدم (أو بنيته له) وضعه على الإنترنت على بنية تحتية يملكها المستخدم — GitHub Pages افتراضيًا، أو Cloudflare Pages أو Netlify عندما يحتاج إلى المزيد. الانضباط المتَّبع: عرض معاينة محلية للموافقة، ترقيم كل عملية نشر بعلامة (tag) في git، النشر عبر سلّم من المزوّدين، التحقق من الرابط المباشر بفحص HTTP حقيقي، وإبقاء التراجع (rollback) على بُعد أمر واحد.

تغطي هذه المهارة المواقع الثابتة وناتج بناء تطبيقات SPA (HTML/CSS/JS عادي، أو مجلد dist//build/ الناتج من Vite/Next-export/Astro/إلخ). ولا تغطي بيئات التشغيل من جانب الخادم — لعمليات نشر serverless قابلة للإهمال دون أي إعداد حساب، استخدم مهارة cloudflare-temporary-deploy الاختيارية بدلًا من ذلك.

متى تُستخدم

حمّل هذه المهارة عندما يطلب المستخدم:

  • وضع موقع على الإنترنت — "انشر هذا"، "استضف هذا في مكان ما"، "أعطني رابطًا يمكنني مشاركته"
  • نشر لوحة تحكم، أو تقرير، أو ملف أعمال، أو موقع مستندات، أو نموذج أولي أنشأته للتو
  • تحديث موقع منشور بالفعل بمحتوى جديد (إعادة النشر = إصدار جديد)
  • التراجع عن عملية نشر سيئة إلى الإصدار السابق
  • اختيار مضيف — لا يهمهم أين، بل يريدون رابطًا فقط

المتطلبات المسبقة

واجهة سطر أوامر (CLI) واحدة على الأقل لمزوّد مصادَق عليه (تحقّق بهذا الترتيب):

  • GitHub Pages (الافتراضي): ينجح gh auth status. يحتاج أيضًا إلى git.
  • Cloudflare Pages: ينجح wrangler whoami (أو يكون CLOUDFLARE_API_TOKEN مضبوطًا). التثبيت: npm i -g wrangler أو استخدم npx wrangler@latest.
  • Netlify (احتياطي): ينجح netlify status. التثبيت: npm i -g netlify-cli.

إضافة إلى:

  • دليل من الناتج الثابت للنشر (جذر الموقع أو مجلد dist//build/). إذا احتاج المشروع خطوة بناء، شغّلها أولًا وانشر دليل الناتج، وليس المصدر أبدًا.
  • لمشاركة معاينة محلية: cloudflared (اختياري — يكفي python3 -m http.server للمعاينة المحلية فقط).

طريقة التشغيل

تُشغَّل كل الأوامر أدناه عبر أداة terminal من دليل مشروع الموقع. المسار دائمًا الخطوات الخمس ذاتها:

  1. ابنِ ← 2. عاين للحصول على الموافقة ← 3. نفّذ commit + tag (الترقيم قبل النشر) ← 4. انشر عبر سلّم المزوّدين ← 5. تحقّق من الرابط المباشر بـ curl وأبلغ عنه.

الإجراء

1. ابنِ وعاين محليًا

ابنِ إذا لزم الأمر (npm run build، إلخ) وحدّد دليل الناتج. قدّمه (serve):

للحصول على رابط معاينة قابل للمشاركة (المستخدم على جهاز آخر، أو تريد موافقته قبل النشر الفعلي)، افتح نفقًا (tunnel) سريعًا في جلسة terminal تعمل في الخلفية:

أعطِ المستخدم رابط https://*.trycloudflare.com واحصل على موافقته قبل النشر. أوقف النفق بعد ذلك.

2. الترقيم قبل النشر — دون استثناءات

يجب أن تنبثق كل عملية نشر من commit في git، حتى تكون كل عملية نشر قابلة لإعادة الإنتاج ويكون التراجع بسيطًا.

إذا كان المشروع يملك مستودعًا بالفعل، فقط نفّذ commit + tag. لا تنشر ملفات غير مُسجَّلة في commit أبدًا.

3. النشر — سلّم المزوّدين

الدرجة 1 — GitHub Pages (الافتراضي: مجاني، بلا حسابات إضافية إن كان gh مصادَقًا عليه):

يظهر الموقع على https://<owner>.github.io/<name>/. إذا كان الموقع هو جذر المستودع (دون دليل بناء)، ادفع (push) main واضبط مصدر Pages على main بدلًا من استخدام subtree. بالنسبة للمشاريع ذات خطوة البناء التي ستُعاد نشرها كثيرًا، فضّل سير عمل actions/deploy-pages الرسمي حتى تُنشَر عمليات الدفع تلقائيًا.

الدرجة 2 — Cloudflare Pages (عندما يريد المستخدم نطاقًا مخصصًا، أو إعادة توجيه/ترويسات، أو Functions):

يُنشئ التشغيل الأول المشروع ويطبع رابط https://<name>.pages.dev. تُربط النطاقات المخصصة عبر لوحة تحكم Cloudflare (Pages ← project ← Custom domains).

الدرجة 3 — Netlify (احتياطي، أو عندما يعمل المستخدم عليه بالفعل):

يُعطي netlify deploy --dir dist (دون --prod) رابط مسودة — مفيد كمرحلة معاينة ثانية.

4. التراجع

التراجع = إعادة نشر علامة (tag) سابقة. لا تُعدِّل الناتج المباشر يدويًا أبدًا.

تحتفظ Cloudflare Pages وNetlify أيضًا بسجل لكل عملية نشر في لوحات تحكمهما ("Rollback to this deploy")، وهو أسرع عندما لا تكون واجهة سطر الأوامر (CLI) متاحة بسهولة.

5. الأسرار ومتغيرات البيئة

  • لا تُدرج الأسرار، أو مفاتيح API، أو ملفات .env في commit أبدًا — فستصبح عامة على استضافة Pages. تحقّق بـ git status قبل أول commit وأبقِ .env* ضمن .gitignore.
  • متغيرات بيئة وقت التشغيل تنتمي إلى لوحة تحكم المزوّد: Cloudflare Pages ← Settings ← Environment variables؛ Netlify ← Site settings ← Environment variables. GitHub Pages ثابت (static) فقط — لا بيئة خادم؛ وأي شيء مُضمَّن في الحزمة يكون عامًا بحكم التعريف. حذّر المستخدم إذا كان بناؤه يُضمِّن مفتاحًا.

المزالق

  • مسارات SPA تُعيد 404 على GitHub Pages. لا تملك Pages قواعد إعادة كتابة (rewrite). انسخ index.html إلى 404.html في دليل الناتج (cp dist/index.html dist/404.html) حتى يتعافى التوجيه من جانب العميل. تتعامل Cloudflare Pages وNetlify مع SPAs عبر _redirects (/* /index.html 200).
  • تأخّر بناء GitHub Pages. قد يستغرق ظهور الموقع من دقيقة إلى 10 دقائق بعد أول تفعيل، ونحو دقيقة واحدة لكل دفعة (push) لاحقة. لا تُعلن الفشل عند أول 404 — كرّر curl عدة مرات قبل التحقيق.
  • المسارات حسّاسة لحالة الأحرف. مضيفو Pages يعملون على Linux حسّاسة لحالة الأحرف؛ قد يُظهر موقع كان يعمل على macOS/Windows خطأ 404 لأصول (assets) مُشار إليها بـ Logo.PNG لكنها مُسجَّلة في commit بـ logo.png. ابحث (grep) في HTML عن اختلاف حالة الأحرف عندما يظهر أصل 404.
  • مسار أساس صفحة المشروع (base path). يُقدَّم https://<owner>.github.io/<name>/ تحت /<name>/ — روابط الأصول المطلقة مثل /app.js تنكسر. استخدم مسارات نسبية أو اضبط قيمة base في أداة البناء (vite build --base=/<name>/).
  • تدفّق مصادقة wrangler يحتاج متصفحًا. يفتح wrangler login عملية OAuth؛ في جلسة بلا واجهة (headless) فضّل CLOUDFLARE_API_TOKEN (ينشئه المستخدم في dash.cloudflare.com ← API Tokens) ولا تطبع الرمز (token) في السجلّات أبدًا.
  • انتشار DNS للنطاقات المخصصة. قد يستغرق سجل CNAME جديد من دقائق إلى ساعات. تحقّق أولًا من الرابط الافتراضي للمزوّد (*.pages.dev، *.netlify.app، *.github.io)، ثم تحقّق من النطاق المخصص بشكل منفصل — لا تخلط بين الفشلين.
  • نشر المصدر بدلًا من ناتج البناء. نشر جذر المستودع بينما الموقع الفعلي موجود في dist/ ينتج قائمة أدلة أو JSX خام. تأكّد دائمًا من أن دليل الناتج يحتوي index.html.

التحقق

لا تُبلّغ بالنجاح استنادًا إلى سجل النشر وحده. قبل إخبار المستخدم بأي شيء:

  1. يُعيد curl -sS -o /dev/null -w '%{http_code}' <live-url> قيمة 200 (أعد المحاولة على مدى نحو دقيقتين لأول نشر على GitHub Pages).
  2. يُظهر curl -sS <live-url> | head -30 محتوى index.html المتوقَّع — يمكنك اختياريًا تأكيد البنية (markup) باستخدام web_extract على الرابط المباشر.
  3. بالنسبة لتطبيقات SPA، استخدم curl أيضًا على مسار عميق (مثل /about) وتأكّد من أنه يُعيد 200، وليس 404.
  4. يُظهر git tag --list 'deploy-*' العلامة (tag) الخاصة بهذا النشر.

ثم أبلغ المستخدم بالرابط المباشر، مع علامة النشر التي يمكنه التراجع إليها.

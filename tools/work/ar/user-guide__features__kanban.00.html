Kanban — التعاون بين عدة وكلاء عبر الـ Profiles

هل تريد شرحًا عمليًا خطوة بخطوة؟ اقرأ درس تطبيقي: Kanban، الذي يعرض أربع قصص مستخدمين (مطوّر منفرد، وإدارة أسطول من المهام، وpipeline أدوار مع إعادة المحاولة، وقاطع الدائرة (circuit breaker)) مع لقطات شاشة من لوحة التحكم لكل منها. هذه الصفحة هي المرجع، والدرس التطبيقي هو السرد.

Hermes Kanban لوحة مهام دائمة، مشتركة بين جميع الـ profiles الخاصة بك في Hermes، تتيح لعدة وكلاء مسمّين التعاون في العمل دون الاعتماد على أسراب هشّة من الـ subagents داخل العملية نفسها. كل مهمة صفٌّ في ~/.hermes/kanban.db؛ وكل عملية تسليم صفٌّ يستطيع أي طرف قراءته والكتابة فيه؛ وكل عامل (worker) عملية كاملة على مستوى نظام التشغيل لها هويتها الخاصة.

نقاط تحقق الإنجاز قبل بلوغ حدّ التكرارات

يتلقى العمّال الذين يملكهم المُوزِّع (dispatcher) إشعار نقطة تحقق واحدًا عند بلوغ نحو 90% من رصيد التكرارات المحدود الخاص بهم، ويُرفق بنتيجة أداة جديدة بينما لا يزال هناك استدعاء آخر قادر على استخدام الأدوات. استخدم agent.budget_warning_ratio لاختيار عتبة أبكر. الأرصدة الصغيرة جدًا تُصدر التحذير في موعد لا يتجاوز التكرار قبل الأخير؛ أما التشغيل ذو التكرار الواحد فلا تكون لديه نافذة لنقطة تحقق قبل بلوغ الحد. يُحفظ الإشعار في سجل الجلسة قبل الطلب التالي. ينبغي للعمّال استدعاء kanban_complete فقط بعد التحقق من عقد المهمة، أو حفظ تعليق يوضح التقدم ثم المتابعة. ولا يُكمل الـ commit أو الـ diff وحده المهمة تلقائيًا أبدًا.

يبقى الحد الصارم، والملخص النهائي دون أدوات، وقاطع الدائرة الخاص بالإخفاقات المتتالية دون تغيير: فالعمّال الذين يستنفدون رصيدهم رغم ذلك يظلون خاضعين لعدد محدود من محاولات الإعادة. هذه فرصة للإبلاغ، وليست ضمانًا بأن النموذج سيلتزم بالإشعار. ولا ترث المحادثات العادية والوكلاء الفرعيون المفوَّضون نقطة التحقق التلقائية الخاصة بـ Kanban؛ إذ يبقى تحذير التكرارات لديهم اختياريًا.

واجهتان: النموذج يتعامل عبر الأدوات، وأنت تتعامل عبر CLI

للوحة مدخلان، وكلاهما مدعوم بالملف نفسه ~/.hermes/kanban.db:

  • يدير الوكلاء اللوحة عبر toolset مخصص هو kanban_* toolset — kanban_show وkanban_list وkanban_complete وkanban_request_review وkanban_request_changes وkanban_block وkanban_heartbeat وkanban_comment وkanban_attach وkanban_attach_url وkanban_attachments وkanban_create وkanban_link وkanban_unblock. يُنشئ المُوزِّع كل عامل وهذه الأدوات موجودة مسبقًا في مخططه؛ ويمكن لـ profiles المنسِّقة أيضًا تفعيل الـ toolset kanban صراحةً. يقرأ النموذج المهام ويوجّهها عبر استدعاء الأدوات مباشرةً، لا عبر تنفيذ hermes kanban في الـ shell. راجع كيف يتفاعل العمّال مع اللوحة أدناه.
  • أنت (والسكربتات و cron) تديرون اللوحة عبر hermes kanban … في CLI، أو /kanban … بوصفه slash command، أو عبر لوحة التحكم. هذه مخصصة للبشر والأتمتة، أي للأماكن التي لا يقف خلفها نموذج يستدعي الأدوات.

تمر الواجهتان عبر طبقة kanban_db نفسها، لذا تحصل عمليات القراءة على عرض متسق ولا يمكن أن تنحرف عمليات الكتابة. تعرض بقية هذه الصفحة أمثلة CLI لأنها سهلة النسخ واللصق، لكن لكل فعل في CLI مكافئًا على هيئة استدعاء أداة يستخدمه النموذج.

هذا هو الشكل الذي يغطي أحمال العمل التي لا تستطيع delegate_task تغطيتها:

  • فرز الأبحاث: باحثون متوازون + محلل + كاتب، مع مشاركة بشرية في الحلقة.
  • العمليات المجدولة: ملخصات يومية متكررة تبني يومياتٍ على مدى أسابيع.
  • التوائم الرقمية: مساعدون مسمّون دائمون (inbox-triage وops-review) تتراكم ذاكرتهم مع الوقت.
  • الـ pipelines الهندسية: تفكيك → تنفيذ في worktrees متوازية → مراجعة → تكرار → PR.
  • عمل الأساطيل: متخصص واحد يدير N من العناصر (50 حسابًا على وسائل التواصل الاجتماعي، 12 خدمة مراقَبة).

تُفهرس أنماط التعاون الثمانية القياسية في أنماط التعاون أدناه.

عقود إنجاز الـ PR

صرّح بأن العمل خاص بـ PR عند الإنشاء باستخدام --completion-contract OWNER/REPO (أو https://github.com/OWNER/REPO/pull/123 كعنوان URL مطابق للعمل الموجود مسبقًا).kanban_create القيمة نفسها completion_contract. استخدم local-only للعمل المحلي عن قصد؛ وتحتفظ البطاقات الموجودة وغير المصرَّح بها بهذا الافتراضي. وعناوين URL المذكورة في النص لا تُعدّ سياسة.

بعد النشر، مرّر metadata.published_pr عند الإنجاز. أول عنوان URL مطابق يرتبط بالبطاقة بشكل دائم؛ ولا يمكن لمحاولات الإعادة استبداله بـ PR شقيق ناجح. ويعرض show --json في CLI وkanban_show العقد المحفوظ.

تغطي نقطة الحدّ المشتركة complete_task أدوات العمّال، و CLI، والموافقة على المراجعة، والإنجاز من لوحة التحكم. فهي تقرأ حماية الـ branch الكلاسيكية والسياقات المطلوبة في مجموعات القواعد (rulesets) النشطة، وتتنقل بين صفحات تشغيلات الفحص والحالات القديمة الخاصة بالـ head المحدد بدقة، ثم تعيد قراءة head/base الخاصين بالـ PR. ولا تُسقط بيانات القياس الاختيارية للفحوصات الفاشلة أو المتخطّاة الفحوصاتِ المطلوبة المقبولة. أما الأدلة المطلوبة لا يمكنها إكمال البطاقة، سواء كانت مفقودة أو معلّقة أو فاشلة أو ملغاة أو منتهية المهلة أو قديمة أو متجاوزة أو محايدة. ولا يمكن ذلك أيضًا مع قبول دون تشغيل، أو سياسة غير قابلة للقراءة، أو إخفاقات GitHub API. يحتاج مستودع دون فحوص مطلوبة إلى عقد local-only.gh مُصادَقًا عليه مع صلاحية قراءة فحوص المستودع وقواعده؛ لا تُجري هذه البوابة أي كتابات بعيدة. تعمل قراءات القبول بهوية profile المكلَّف gh في gh — باستخدام GH_TOKEN / GH_CONFIG_DIR من ملف .env الخاص بالـ profile، وليس هوية الدخول المحيطة للعملية التي تُكمل البطاقة. على المضيفين متعددي الـ profiles (هوية GitHub لكل مؤسسة)، سجّل الدخول إلى gh لكل profile (GH_CONFIG_DIR في ملف .env الخاص بذلك الـ profile). يجب أن يوجد الـ token في .env الخاص بالـ profile (أو مصدر أسرار مضبوط): تُزال قيمة GH_TOKEN المصدَّرة فقط في الـ shell أو وحدة systemd من عملية gh الفرعية ولا تُعاد إضافتها أبدًا. يُرفض profile مكلَّف لا يملك تسجيل دخول gh خاصًا به — أو لم يعد موجودًا — بحالة not logged in بدلًا من الرجوع إلى ~/.config/gh؛ وتظل البطاقات غير المعيّنة تستخدم تسجيل الدخول المحيط. يُرفض تسجيل الدخول الذي لا يرى المستودع مع classification=auth، مع ذكر الـ profile والمستودع، بدلًا من إخفاق بنية تحتية قابل لإعادة المحاولة.

عند الرفض، تبقى البطاقة النشطة ومساحة العمل. وتخزّن أحداث pr_acceptance الدائمة عنوان URL الخاص بالـ PR، والـ SHA، والسياقات المطلوبة، ومعرّفات الفحوصات وعناوينها، والتصنيفات، وتعليمات التعافي؛ ويُظهر last_failure_error الخطوة التالية. أصلح الإخفاقات، أو أعد تشغيل فحوصات البنية التحتية أو انتظر، ثم أعد محاولة الإنجاز. استخدم kanban_block عندما يلزم تدخل بشري. لا يمكن لقيمة failure العامة من GitHub تحديد ما إذا كان الاختبار أو رفع المخرجات هو الذي فشل؛ لذا افحص عنوان URL المحفوظ الخاص به. وتُصنَّف استنتاجات البنية التحتية الصريحة وإخفاقات API بشكل منفصل. ولا يُنشأ أي عامل إضافي.

يُجري حفظ الإيصال وعملية الكتابة النهائية إعادة التحقق من ملكية التشغيل والحالة والعقد تحت قفل SQLite واحد: فالعامل الذي استُعيدت منه المهمة لا يستطيع إكمال التشغيل الجديد أو إرفاق قبول به. قراءة GitHub النهائية لقطة وقت الإنجاز، وليست معاملة موزّعة أو مراقبة مستمرة بعد الإنجاز. هذه حماية لدورة الحياة مخصصة لمستخدم واحد، وليست عزلًا على مستوى نظام التشغيل ضد عمليات الكتابة المباشرة العشوائية في قاعدة البيانات. ولا يشمل ذلك GitHub Enterprise. أعمال ذات صلة بالنشر ودورة الحياة: #91230، #84254، #52311؛ والتحقق المحلي والنشر وحدهما لا يعنيان القبول عن بُعد.

الفرق في جملة واحدة: delegate_task استدعاء دالة؛ أما Kanban فطابور عمل تكون فيه كل عملية تسليم صفًّا يستطيع أي profile (أو إنسان) رؤيته وتعديله.

لا تربط بطاقة دعم بالبطاقة التي يفترض أن تزيل عائقها

العامل المتوقف بسبب t_parent الذي ينشئ بطاقة دعم للجزء المفقود يجب ألا kanban_link(t_parent, t_support): يجعل الرابط بطاقة الدعم فرعًا للأصل المحظور، فتُحجب خلف الأصل الذي وُجدت لإزالة عائقه ولا تعمل أي من البطاقتين أبدًا. اذكر معرّف الأصل في متن بطاقة الدعم بدلًا من ذلك.link/kanban_link يبلّغ عن gated: true ويسجّل حدث dependency_wait عندما يخفض حالة فرع ready (ويفعل kanban_create مع parents الشيء نفسه عندما يعلّق البطاقة الجديدة)، فيظهر التعطل المتبادل على اللوحة؛ ويحرّرها hermes kanban unlink <parent> <child>.

استخدم delegate_task عندما يحتاج الوكيل الأب إلى إجابة استدلالية قصيرة قبل المتابعة، دون مشاركة بشرية، وتعود النتيجة إلى سياق الوكيل الأب.

استخدم Kanban عندما يتجاوز العمل حدود الوكلاء، أو يجب أن يصمد أمام إعادة التشغيل، أو قد يحتاج إلى مدخلات بشرية، أو قد يتولاه دور مختلف، أو يجب أن يكون قابلًا للاكتشاف لاحقًا.

كما يتعايشان داخل تشغيل واحد. إذ تُنفَّذ مهمة kanban في عامل مُدار معزول تحت gateway الخاص بالـ profile، ويحجز ذلك الـ gateway أبناء delegate_task الخاصين بها ضمن تنفيذ العامل: يحصل كل ابن على جلسته الخاصة (تُدرج بوصفها subagent لجلسة البطاقة)، ويُحتسب ضمن delegation.max_concurrent_children و delegation.max_spawn_depth، ويعيد نتيجته داخل دور البطاقة، وينتهي مع العامل. وإذا توقف الـ gateway أثناء عمل ابن، يُسحب هذا الابن من الخدمة ولا يُستأنف أبدًا. أما العمل الذي يجب أن يبقى بعد توقف الـ gateway أو يحتاج إلى مراجع خاص به فمكانه ما زال في البطاقات الفرعية (kanban_create مع parents).

المفاهيم الأساسية

  • اللوحة (Board): طابور مهام مستقل له قاعدة بيانات SQLite خاصة، ومجلد مساحات عمل، وحلقة مُوزِّع. يمكن أن يحتوي التثبيت الواحد على لوحات كثيرة (مثلًا لوحة لكل مشروع أو مستودع أو مجال)؛ راجع اللوحات (متعددة المشاريع) أدناه. يبقى مستخدمو المشروع الواحد على اللوحة default ولا يرون كلمة "board" خارج قسم التوثيق هذا.
  • المهمة (Task): صف يحتوي على عنوان، ومتن اختياري، ومُسنَد إليه واحد (اسم profile)، وحالة (triage | todo | ready | running | blocked | review | done | archived)، ونطاق أسماء اختياري للمستأجر (tenant)، ومفتاح idempotency اختياري (لإزالة تكرار عمليات الأتمتة المُعاد تنفيذها).
  • الرابط (Link): صف في task_links يسجّل اعتمادية من أب → ابن. يرقّي المُوزِّع المهمة todo → ready عندما تصبح جميع المهام الأب done. يُرفض إضافة رابط إلى فرع يعمل لأنه لا يمكنه تقييد عمل محجوز بالفعل؛ والاستثناء الوحيد عامل نشط يربط بطاقته الخاصة مع ملكية تشغيل يوفّرها الموزّع، مباشرة قبل تسليم التحكم بسبب عائق اعتمادية.
  • التعليق (Comment): بروتوكول التواصل بين الوكلاء. يضيف الوكلاء والبشر تعليقات؛ وعند إنشاء عامل (أو إعادة إنشائه) يقرأ سلسلة التعليقات كاملة بوصفها جزءًا من سياقه.
  • مساحة العمل (Workspace): المجلد الذي يعمل فيه العامل. وهي ثلاثة أنواع:
    • scratch (الافتراضي): مجلد مؤقت جديد ضمن ~/.hermes/kanban/workspaces/<id>/ (أو ~/.hermes/kanban/boards/<slug>/workspaces/<id>/ في اللوحات غير الافتراضية). يُحذف عند اكتمال المهمة، فمساحة scratch مؤقتة بطبيعة تصميمها. الملفات المصرَّح بها صراحةً عبر kanban_complete(artifacts=[...]) أو kanban_request_review(artifacts=[...]) إلى تخزين مرفقات دائم لكل مهمة قبل التنظيف (يهيّئها تسليم المراجعة عند التسليم، لأن إكمال المراجع لاحقًا هو الذي يحذف مساحة العمل المؤقتة)؛ وتتلقى مسارات المخرجات القائمة في ملخّصات الإكمال القديمة المعاملة نفسها. تُزال الملفات المؤقتة الأخرى. يبقي غياب مخرج مؤقت مصرّح به المهمة جارية ليصحح العامل المسار ويعيد المحاولة. استخدم worktree: أو dir:<path> عندما ينبغي أن تبقى مساحة العمل بأكملها متاحة. في المرة الأولى التي تُنشأ فيها مساحة عمل scratch في تثبيت ما، يسجّل المُوزِّع تحذيرًا ويُصدر حدث tip_scratch_workspace على المهمة (يظهر عبر hermes kanban show <id>).
    • dir:<path>: مجلد مشترك موجود (Obsidian vault، أو مجلد عمليات البريد، أو مجلد لكل حساب). يجب أن يكون مسارًا مطلقًا. تُرفض المسارات النسبية مثل dir:../tenants/foo/ عند الإرسال لأنها ستُحدَّد نسبةً إلى مجلد العمل الحالي (CWD) الذي يصادف أن يكون فيه المُوزِّع، وهذا ملتبس ويمثل منفذ هروب من نوع confused-deputy. وفيما عدا ذلك، يُعدّ المسار موثوقًا: فهو جهازك ونظام ملفاتك، ويعمل العامل بمعرّف المستخدم (uid) الخاص بك. هذا هو نموذج التهديد القائم على المستخدم المحلي الموثوق؛ فـ kanban مصمَّم للعمل على مضيف واحد. يُحتفظ به عند الإنجاز.
    • worktree: نسخة git worktree ضمن .worktrees/<id>/ لمهام البرمجة. استخدم worktree:<path> لتثبيت المسار الهدف بدقة. يُنشئه الأمر git worktree add على جانب العامل، مستخدمًا --branch عند توفيره. يُحتفظ به عند الإنجاز.
  • المُوزِّع (Dispatcher) — حلقة طويلة العمر تقوم كل N ثانية (الافتراضي 60) باسترداد الحجوز القديمة والعاملين المتعطلين (اختفاء PID دون انتهاء TTL بعد)، وتنظيف العمال الذين تجاوزوا عمر تشغيلهم المنتهي (يُنهى العامل الذي لا يزال حيًا بعد kanban_complete/kanban_block الخاص به بعد مرور دقيقتين على إغلاق تشغيله، لإتاحة الوقت لإنهاء دوره الأخير — تُطابق هويته باستخدام PID و بصمة وقت الإنشاء، فلا يُرسل signal أبدًا إلى PID أُعيد استخدامه؛ ويُسجَّل ذلك كحدث terminal_worker_reaped)، وترقية المهام الجاهزة والحجز ذريًا وإنشاء الـ profiles المعيّنة. تعمل داخل الـ gateway افتراضيًا (kanban.dispatch_in_gateway: true). يمسح مُوزِّع واحد جميع اللوحات في كل دورة؛ ويُنشأ العمّال مع تثبيت HERMES_KANBAN_BOARD حتى لا يروا اللوحات الأخرى. بعد kanban.failure_limit من إخفاقات الإنشاء المتتالية على المهمة نفسها (الافتراضي: 2)، يحظر المُوزِّع المهمة تلقائيًا مع ذكر آخر خطأ سببًا لذلك، مما يمنع الدوران العقيم على مهام لا يوجد الـ profile الخاص بها، أو تتعذر تهيئة مساحة عملها، وما إلى ذلك.
  • المستأجر (Tenant): نطاق أسماء نصي اختياري داخل اللوحة. يمكن لأسطول متخصص واحد خدمة عدة أعمال (--tenant business-a) مع عزل البيانات عبر مسار مساحة العمل وبادئة مفتاح الذاكرة. المستأجرون مرشِّح مرن؛ أما اللوحات فهي حدود العزل الصارمة.

اللوحات (متعددة المشاريع)

تتيح لك اللوحات فصل مسارات العمل غير المترابطة، لوحة لكل مشروع أو مستودع أو مجال، في طوابير معزولة. يحتوي التثبيت الجديد على لوحة واحدة بالضبط اسمها default (قاعدة بياناتها في ~/.hermes/kanban.db للتوافق مع الإصدارات السابقة). والمستخدمون الذين يريدون مسار عمل واحدًا فقط لا يحتاجون أبدًا إلى معرفة شيء عن اللوحات؛ فهذه الميزة اختيارية.

العزل على مستوى كل لوحة مطلق:

  • قاعدة بيانات SQLite منفصلة لكل لوحة (~/.hermes/kanban/boards/<slug>/kanban.db).
  • مجلدا workspaces/ وlogs/ منفصلان.
  • العمّال الذين يُنشؤون لمهمة ما يرون مهام لوحتهم فقط، إذ يضبط المُوزِّع HERMES_KANBAN_BOARD في بيئة الوكيل الفرعي، وكل أداة kanban_* يستطيع العامل الوصول إليها تقرأ هذا المتغير.
  • لا يُسمح بربط المهام عبر اللوحات (للحفاظ على بساطة المخطط؛ وإذا كنت تحتاج فعلًا إلى مراجع بين المشاريع، فاستخدم الإشارات النصية الحرة وابحث عنها بالمعرّف يدويًا).

إدارة اللوحات من CLI

ترتيب تحديد اللوحة (الأعلى أولوية أولًا):

  1. الخيار الصريح --board <slug> في استدعاء CLI.
  2. متغير البيئة HERMES_KANBAN_BOARD (يضبطه المُوزِّع عند إنشاء عامل، حتى لا يرى العمّال اللوحات الأخرى).
  3. ~/.hermes/kanban/current: الـ slug المحفوظ بواسطة hermes kanban boards switch.
  4. default.

يُتحقق من صحة الـ slugs: أحرف إنجليزية صغيرة وأرقام + شرطات + شرطات سفلية، من 1 إلى 64 حرفًا، ويجب أن تبدأ بحرف أو رقم. تُحوَّل الأحرف الكبيرة في المدخلات إلى صغيرة تلقائيًا. وأي شيء آخر (الشرطات المائلة، والمسافات، والنقاط، و..) يُرفض في طبقة CLI حتى لا تتمكن حيل اجتياز المسارات (path traversal) من تسمية لوحة.

إدارة اللوحات من لوحة التحكم

في hermes dashboard → تبويب Kanban، يظهر مُبدِّل اللوحات في الأعلى بمجرد وجود أكثر من لوحة (أو احتواء أي لوحة على مهام). أما مستخدمو اللوحة الواحدة فلا يرون سوى زر صغير + New board؛ ويبقى المُبدِّل مخفيًا حتى تصبح له أهمية.

  • Board dropdown (القائمة المنسدلة للوحات): اختر اللوحة النشطة. يُحفظ اختيارك في localStorage الخاص بالمتصفح، فيبقى بعد إعادة التحميل دون تغيير مؤشر current الخاص بـ CLI من تحت طرفية تركتها مفتوحة.
  • + New board — يفتح نافذة تطلب slug واسم العرض والوصف والأيقونة ومجلد المشروع، وعند وجود أي Project، محدّد Project. يوجد خيار للانتقال تلقائيًا إلى اللوحة الجديدة.
  • Settings: يفتح نافذة لتعديل اسم العرض الخاص باللوحة الحالية، ووصفها، ومجلد المشروع (default_workdir). مجلد المشروع هو مساحة العمل الافتراضية على مستوى اللوحة التي ترثها كل مهمة جديدة (مستودع git → worktree محفوظ، ومجلد عادي → مجلد محفوظ)؛ ويمكن لكل مهمة تجاوزه عند الإنشاء. يعيد مسح الحقل المهام الجديدة إلى مساحات عمل scratch مؤقتة — إلا إذا كان Project مرتبطًا، فيُستخدم المجلد الأساسي للـ Project؛ فك ارتباط المشروع أولًا للعودة إلى scratch.
  • Project (في النافذتين) — يربط اللوحة بـ Hermes Project (قيمة project_id للوحة). ترث المهام المنشأة على لوحة مرتبطة الـ Project؛ كما يؤدي اختيار مشروع مع ترك حقل المجلد فارغًا إلى ملء مجلد المشروع بالمجلد الأساسي للـ Project. يظهر المشروع المرتبط كشارة Project: <name> بجانب قائمة اللوحات؛ وتؤدي علامة × الخاصة به إلى فك ارتباط اللوحة (بإرسال project_id: "") دون المساس بمجلد المشروع، ويؤدي No binding في Settings الإجراء نفسه عند الحفظ. لا يظهر المحدّد إلا عند وجود Project واحد على الأقل.
  • Archive — لا يظهر إلا على اللوحات غير default. يطلب التأكيد، ثم ينقل مجلد اللوحة إلى boards/_archived/.

تقبل جميع API endpoints الخاصة بلوحة التحكم ?board=<slug> لتحديد نطاق اللوحة. يُربط WebSocket للأحداث بلوحة عند الاتصال؛ ويؤدي التبديل في الواجهة إلى فتح WS جديد للوحة الجديدة.

التبديل بين اللوحات في تطبيق Desktop

في تطبيق Desktop، يقع محدّد اللوحات في صف الترويسة أعلى صفحة Kanban بجانب عنوان الصفحة: عنصر Board يعرض اسم اللوحة الحالية وعدد مهامها مع سهم — مرّر المؤشر فوقه لعرض "Switch board". انقره لاختيار لوحة أخرى أو إعادة تسمية اللوحات أو إعدادها أو تصديرها أو استيرادها أو إنشائها أو أرشفتها. عندما يُفتح Kanban في جزء مقسّم، يوجد عنصر Board نفسه في صف ترويسة اللوحة بعد عدد المهام. وكما في لوحة التحكم، يحتفظ Desktop باختياره الخاص (محفوظًا محليًا) ولا يغيّر مؤشر current الخاص بـ CLI.

مرفقات الملفات

يمكن أن تحمل المهام مرفقات ملفات، مثل ملفات PDF والصور والمستندات المصدرية، ليحصل العامل على المواد المصدرية التي يحتاجها دون أن تضطر إلى لصق المسارات في متن المهمة على أمل أن يجدها.

  • الرفع: افتح مهمة في الدرج الجانبي للوحة التحكم واستخدم قسم Attachments وزر Upload file فيه (يمكن رفع عدة ملفات دفعة واحدة). والحد الأقصى لكل عملية رفع 25 MB.
  • التخزين: تُحفظ الملفات ضمن <hermes-home>/kanban/attachments/<task_id>/ للوحة الافتراضية، أو <hermes-home>/kanban/boards/<slug>/attachments/<task_id>/ للوحة مسمّاة. اضبط HERMES_KANBAN_ATTACHMENTS_ROOT لتثبيت موقع مخصص.
  • ما يراه العامل: عندما يسلّم المُوزِّع مهمة إلى عامل، يتضمن سياق العامل قسم Attachments يسرد اسم كل ملف ومساره المطلق. ولدى العامل وصول كامل إلى أدوات الملفات والطرفية، لذا يقرأ المرفقات مباشرةً (read_file، أو أدوات الـ shell مثل pdftotext).
  • التنزيل / الإزالة — تسرد اللوحة الجانبية كل مرفق مع رابط تنزيل وعنصر إزالة (×). تزيل إزالة المرفق صف بياناته الوصفية؛ ولا يُحذف الملف على القرص إلا عندما لا يشير إليه أي صف مرفق آخر (يبقى الملف المشترك بين مهام متعددة حتى إزالة آخر مرجع له). من CLI، يزيل hermes kanban attach-rm ATTACHMENT_ID المرفق بالطريقة نفسها.
الـ terminal backends البعيدة

تُحدَّد مسارات المرفقات مباشرةً على terminal backend المحلي، وهو الافتراضي لعمّال Kanban. إذا كنت تشغّل العمّال على backend بعيد (Docker، Modal)، فاربط (mount) مجلد attachments/ الخاص باللوحة داخل الـ sandbox حتى تكون المسارات المطلقة في سياق العامل قابلة للوصول.

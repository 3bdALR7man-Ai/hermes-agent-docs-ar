Desktop Plugin SDK

تطبيق Hermes Desktop الأصلي (native) مبني بالكامل على مبدأ المساهمة (contribution-driven): كل سطح في النافذة — الأجزاء (panes)، المسارات (routes)، تنقّل الشريط الجانبي، عناصر شريط الحالة، مدخلات لوحة الأوامر، اختصارات لوحة المفاتيح، السمات (themes) — يسجَّل في سجلّ مركزي واحد. يسجّل الأساسي (Core) أسطحه بنفس الطريقة التي تسجّل بها إضافة (plugin)، لذا فإن قصة الإضافات هي القصة الحقيقية، لا إضافة لاحقة مُلصَقة.

إضافة سطح المكتب (desktop plugin) هي ملف ESM واحد يُصدّر افتراضيًا HermesPlugin. يستورد وحدة واحدة — @hermes/plugin-sdk — ويحصل على كل شيء: حالة التطبيق الحية، باب gateway الخاص بـ JSON-RPC، مساحة أسماء خلفية REST/socket مخصّصة، React Query، وحتى عدة واجهة المستخدم (UI kit) الخاصة بالتطبيق لتبدو واجهة الإضافة أصلية افتراضيًا. دون استنساخ للمستودع، دون npm run build، ودون التعديل على كود التطبيق نفسه. ضع الملف في $HERMES_HOME/desktop-plugins/<id>/plugin.js وسيحمّله التطبيق خلال ثوانٍ ويعيد تحميله تلقائيًا (hot-reload) مع كل حفظ.

هذا ليس SDK إضافات لوحة تحكم الويب

تعني "Plugin" أشياء متعددة غير مترابطة في Hermes. تتناول هذه الصفحة SDK تطبيق سطح المكتب الأصلي (hermes desktop) — وحدة @hermes/plugin-sdk و $HERMES_HOME/desktop-plugins/. أما لوحة تحكم الويب (web dashboard) (hermes dashboard) فلها نظام إضافات خاص بها غير مرتبط بهذا، على window.__HERMES_PLUGIN_SDK__ مع manifest.json — موثّق في توسيع لوحة التحكم. أما إضافات Python الخاصة بـ CLI/gateway فموثّقة في بناء إضافة Hermes. الأنظمة الثلاثة لا تتشارك الكود ولا واجهات API ولا آلية التسليم. مساحة الأسماء الخلفية plugin_api.py فقط (/api/plugins/<id>) مشتركة بين SDK سطح المكتب و SDK لوحة التحكم.

النموذج الذهني

يتبع الـ SDK نموذج وحدات VS Code. يستورد مؤلّف الإضافة وحدة واحدة فقط ولا يلمس آليات التطبيق الداخلية أبدًا (فهي مستبعدة عبر lint من الإضافة المجمّعة (bundled)، ويفشل استيرادها في إضافة القرص). تأتي القدرات على شكل مستويات:

  • host.state.* — عروض للقراءة فقط على حالة التطبيق الحية (ذرّات nanostore): الجلسة النشطة، انشغال الدور (turn-busy) لكل جلسة، دليل العمل (cwd)، حالة socket الخاص بـ gateway، النموذج، profile، منفذ العرض (viewport). gateway هو WebSocket، وليس انشغال الدور.
  • إجراءات host.* — أفعال آمنة مُنتقاة بعناية: toast، التنقّل، متابعة السجلات (logs)، إعادة تشغيل gateway، الاشتراك في مجرى أحداث gateway.
  • host.request — باب gateway الخاص بـ JSON-RPC: الجلسات، الإعدادات، المهارات، cron — كل ما يستدعيه التطبيق نفسه.
  • captureGatewayFileDownload() — التقط إجراء حفظ ملف في الـ gateway مباشرة قبل بدء قراءة REST، واحتفظ به إلى جانب البيانات المعادة. يحافظ الإجراء (storedPath, suggestedName) => Promise<void> على نطاق الاتصال/profile الخاص بتلك القراءة حتى إذا بدّل المستخدم المضيفين قبل النقر. لا تستدعِه إلا استجابةً لإيماءة تنزيل صريحة من المستخدم، باستخدام مسار الملف المحفوظ في backend، لا مسار مساحة عمل مخمَّن أبدًا. يتولى Electron البث الموثّق، ومربع حوار الحفظ الأصلي، والرجوع الاحتياطي للـ gateways الأقدم؛ ولا تتلقى الإضافات بيانات الاعتماد مطلقًا ولا تفتح المسارات البعيدة باستخدام file://. ويعرض المضيف إشعارات "Saved" / "Download failed" نفسها التي تعرضها لوحة Files، ويظل صامتًا عند الإلغاء؛ ويُحسم الوعد عند حسم الحفظ ولا يُرفض أبدًا.
  • ctx.rest / ctx.socket — مساحة الأسماء الخلفية الخاصة بإضافتك (/api/plugins/<id>) إن كنت تشحن plugin_api.py.
  • ui.* — لغة التصميم: المكوّنات الحقيقية للتطبيق، متغيرات السمة، الأيقونات، والمنسّقات (formatters)، بحيث تطابق واجهة إضافتك واجهة التطبيق بكسل بكسل.

الطرق الثلاث تتبع نفس عقد HermesPlugin، وتظهر في Capabilities → Plugins، ويمكن تفعيلها/تعطيلها مباشرة. الحزمة الموحّدة ليست سوى باب القرص وهو يبحث داخل مجلد إضافة الوكيل الخاصة بك — راجع حزمة واحدة، SDK-ان. كل ما في هذه الصفحة مكتوب على أساس باب القرص (ما تكتبه أنت والوكيل)؛ تشرح الإضافات المضمّنة الفرقين الاثنين. يُشحن Radio كإضافة SDK مضمّنة فقط، معطّلة افتراضيًا. فعّلها من Capabilities → Plugins للحصول على بث مباشر مجاني، والبحث عن المحطات، وعناصر تحكم تشغيل في شريط الحالة للتحكم بالتشغيل مع شكل موجة متفاعل مع الصوت. وتستخدم مفتاح تفعيل الإضافات الحالي ولا تقدم أي مساهمة أثناء تعطيلها. وتوجد العروض المرجعية في المستودع المرافق hermes-example-plugins .

البدء السريع — إضافتك الأولى

أنشئ $HERMES_HOME/desktop-plugins/hello/plugin.js (وهو ~/.hermes/... افتراضيًا). إضافات سطح المكتب هي على مستوى التطبيق — جذر واحد لكل profile أو gateway أو جهاز بعيد تتصل به النافذة. يجب أن يطابق اسم المجلد معرّف الإضافة id.

احفظ الملف. يراقب التطبيق مجلد desktop-plugins/، ويحمّل الملف خلال ثوانٍ قليلة، ويعيد تحميله تلقائيًا (hot-reload) في مكانه مع كل حفظ لاحق. إن لم يظهر، نفّذ ⌘K → Reload desktop plugins. وإذا فشل التحميل، يظهر toast يسمّي الخطأ — أصلِحه ثم احفظ مجددًا.

لا JSX ولا بناء

يُحمَّل ملف القرص دون تجميع، لذا لن تُحلَّل صياغة JSX. اكتب الواجهة باستخدام استدعاءات jsx() / jsxs() من react/jsx-runtime (أو React.createElement). المُحدِّدات (specifiers) القابلة للاستيراد الوحيدة هي @hermes/plugin-sdk و react و react/jsx-runtime — وكل ما عداها يفشل في الحل، عمدًا.

عقد الإضافة

تُصدّر الإضافة افتراضيًا HermesPlugin:

تتلقى register كائن مخصَّصًا (scoped) من نوع PluginContext. فهو لا يلمس السجلّ مباشرة أبدًا — إذ يضيف السياق تلقائيًا وسم المصدر (source: 'plugin:<id>') ويضع كل معرّف مساهمة في مساحة أسماء خاصة (<id>:<localId>)، بحيث لا يمكن أبدًا لإضافتين أن تتعارضا.

المساهمة (contribution) هي المُكوّن الأولي الوحيد الذي يشترك فيه كل سطح:

يمكنك توفير render أو data أو كليهما، حسب المنطقة (area).

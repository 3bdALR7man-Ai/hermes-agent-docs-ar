3. قائمة مراجعة

عند إجراء مراجعة كود (محلية أو PR)، تحقّق بشكل منهجي من:

الصحة (Correctness)

  • هل يقوم الكود بما يدّعي القيام به؟
  • هل الحالات الحدّية معالَجة (مدخلات فارغة، قيم null، بيانات كبيرة، وصول متزامن)؟
  • هل مسارات الأخطاء مُعالَجة بسلاسة؟

الأمان

  • لا توجد أسرار (secrets) أو بيانات اعتماد أو مفاتيح API مضمّنة في الكود مباشرة
  • التحقق من صحة المدخلات (input validation) على المدخلات الموجَّهة للمستخدم
  • لا يوجد SQL injection أو XSS أو path traversal
  • وجود فحوص المصادقة/التفويض حيثما لزم

جودة الكود

  • تسمية واضحة (المتغيرات، الدوال، الأصناف)
  • لا تعقيد غير ضروري أو تجريد سابق لأوانه
  • مبدأ DRY — لا منطق مكرر كان ينبغي استخلاصه
  • الدوال مركّزة (مسؤولية واحدة)

الاختبار

  • هل مسارات الكود الجديدة مُختبَرة؟
  • هل المسار السليم وحالات الخطأ مغطّاة؟
  • هل الاختبارات قابلة للقراءة والصيانة؟

الأداء

  • لا استعلامات N+1 أو حلقات غير ضرورية
  • تخزين مؤقت مناسب حيثما كان مفيدًا
  • لا عمليات حاجبة (blocking) في مسارات الكود غير المتزامنة (async)

التوثيق

  • واجهات API العامة موثَّقة
  • المنطق غير الواضح يحتوي على تعليقات تشرح "السبب"
  • README محدَّث إذا تغيّر السلوك

4. سير عمل المراجعة قبل الدفع (Push)

عندما يطلب منك المستخدم "مراجعة الكود" أو "التحقق قبل الدفع":

  1. git diff main...HEAD --stat — اطّلع على نطاق التغييرات
  2. git diff main...HEAD — اقرأ الـ diff الكامل
  3. لكل ملف متغيّر، استخدم read_file إذا احتجت سياقًا إضافيًا
  4. طبّق القائمة أعلاه
  5. اعرض النتائج بالصيغة المنظَّمة (حرِج / تحذيرات / اقتراحات / جيد)
  6. إذا وُجدت مشكلات حرِجة، اعرض إصلاحها قبل أن يدفع المستخدم

الخطوة 9: التنظيف

القرار: اعتماد مقابل طلب تغييرات مقابل تعليق

  • اعتماد (Approve) — لا توجد مشكلات حرِجة أو على مستوى التحذير، فقط اقتراحات بسيطة أو كل شيء سليم
  • طلب تغييرات (Request Changes) — أي مشكلة حرِجة أو على مستوى التحذير يجب إصلاحها قبل الدمج
  • تعليق (Comment) — ملاحظات واقتراحات، لكن لا شيء يعيق الدمج (استخدمها عندما تكون غير متأكد أو عندما يكون الـ PR مسوّدة)

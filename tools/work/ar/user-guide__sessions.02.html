استيراد الجلسات من Claude Code و Codex CLI

بدأت محادثة في CLI وكيل آخر؟ يمكنك سحبها إلى Hermes ومتابعتها هنا. يقرأ Hermes سجلات جلسات Claude Code (~/.claude/projects/، أو $CLAUDE_CONFIG_DIR/projects/ عندما يكون دليل إعدادات Claude Code منقولًا) و rollouts الخاصة بـ Codex CLI (~/.codex/sessions/، أو $CODEX_HOME/sessions/) — تُقرأ الملفات الأجنبية فقط، ولا تُعدَّل أبدًا.

ينشئ hermes sessions import جلسة Hermes جديدة معنونة Imported from Claude Code: <first user message> (أو Codex CLI) ويطبع المعرّف بالإضافة إلى أمر hermes --resume <id> جاهز للصق. تعرض --resume @claude / --resume @codex نفس المُنتقي وتضعك مباشرة في المحادثة المستوردة.

Hermes Desktop يملك نفس أداة الاستيراد في لوحة الأوامر (Import session). تعرض السجلات على الجهاز الذي يعمل عليه الـ backend المتصل — وليس الحاسوب الذي يشغّل التطبيق — وتُظهر معاينة للقراءة فقط، وContinue in Hermes ينسخ المحادثة إلى profile المحدَّد. التصفح لا يكتب أبدًا إلى مخزن جلساتك، والاستيراد لا يمسّ الملف المصدر أبدًا، واستيراد نفس السجل مرتين يفتح النسخة الموجودة بدلًا من إنشاء نسخة أخرى.

ما الذي يُنقَل: محادثة المستخدم/المساعد المرتَّبة، مع تكثيف نشاط الأدوات إلى ملاحظات [ran tool: …] قصيرة داخل أدوار المساعد. تُترَك system prompts، والسياق المحقون، وآثار الاستدلال، ومخرجات الأدوات الخام خلفًا — الاستيراد نسخة نصية نظيفة، وليس إعادة تشغيل حرفية بايتًا بايت.

أداة البحث في الجلسات

يملك الوكيل أداة session_search مدمجة تُنفِّذ بحثًا نصيًا كاملًا عبر كل المحادثات السابقة باستخدام محرك FTS5 في SQLite — وتتيح للوكيل التمرير عبر أي جلسة يجدها. لا تُجري أي استدعاءات LLM وتُعيد عروضًا لرسائل فعلية من قاعدة البيانات بدلًا من توليد ملخصات.

أربعة أشكال استدعاء

تستدل الأداة على ما تريده من الوسائط التي تضبطها. لا يوجد وسيط mode.

1. الاكتشاف — مرّر query:

يُشغِّل FTS5، ويزيل التكرار حسب نسب الجلسة، ويُعيد أفضل N جلسة. يستخدم الاكتشاف تفصيلًا تكيّفيًا افتراضيًا: تتضمن أعلى النتائج تصنيفًا نافذة سياقها الكاملة وأطرافها، بينما تبقى النتائج الأدنى تصنيفًا مُضغَّطة. مرّر detail="full" لتفصيل كل نتيجة بالكامل.

تحمل كل نتيجة:

  • session_id، title، when، source
  • snippet — مقتطف مطابقة مُبرَز بواسطة FTS5
  • detail — full أو compact
  • bookend_start / bookend_end — أول/آخر 3 رسائل مستخدم+مساعد للنتائج الكاملة؛ قوائم فارغة للنتائج المُضغَّطة
  • messages — ±5 رسائل حول مطابقة FTS5 للنتائج الكاملة؛ رسالة الأنكر (anchor) المُعلَّمة فقط للنتائج المُضغَّطة
  • match_message_id، messages_before، messages_after

تعيد النتيجة الأولى بناء الهدف → المطابقة → الحل فورًا. إذا بدت نتيجة مختصرة أخرى أرجح فائدةً، فاستخدم معرّفي جلستها ورسالتها مع شكل التمرير. الزمن الفعلي المعتاد عشرات المللي ثانية على قاعدة بيانات جلسات حقيقية.

2. التمرير — مرّر session_id + around_message_id:

يُعيد نافذة من ±window رسالة تتمحور حول الأنكر. لا FTS5، لا أطراف — فقط الشريحة. استخدمه بعد استدعاء اكتشاف عندما تحتاج سياقًا أكثر من النافذة الافتراضية ±5.

  • للتمرير للأمام: مرّر messages[-1].id مرة أخرى كـ around_message_id
  • للتمرير للخلف: مرّر messages[0].id مرة أخرى كـ around_message_id
  • تظهر رسالة الحد في كلتا النافذتين كعلامة توجيه
  • عندما تكون messages_before أو messages_after أقل من window، فأنت عند بداية أو نهاية الجلسة

الزمن الفعلي المعتاد: 1-2 مللي ثانية لكل استدعاء تمرير.

3. القراءة — مرّر session_id دون أنكر:

يُعيد الجلسة كاملة، أو عرض بداية/نهاية محدود للجلسات الضخمة. يُستخدم هذا الشكل أيضًا لحل رابط @session:<profile>/<id>.

4. التصفح — بلا وسائط:

يُعيد الجلسات الأخيرة زمنيًا (العناوين، المعاينات، الطوابع الزمنية). مفيد عندما يسأل المستخدم "على ماذا كنت أعمل" دون تسمية موضوع.

صياغة استعلام FTS5

يدعم وضع الكلمات المفتاحية صياغة استعلام FTS5 القياسية:

  • كلمات مفتاحية بسيطة: docker deployment (يفترض FTS5 AND افتراضيًا)
  • عبارات: "exact phrase"
  • بوليانية: docker OR kubernetes، python NOT java
  • بادئة: deploy*

وسائط اختيارية

  • sort — newest أو oldest، فوق ترتيب FTS5. احذفه للترتيب حسب الصلة فقط (الافتراضي؛ مناسب للاستدعاء الاستكشافي). استخدم newest لأسئلة "أين تركنا X"، وoldest لأسئلة "كيف بدأ X".
  • detail — adaptive (الافتراضي) يُفصِّل فقط أعلى نتيجة اكتشاف بالكامل؛ full يُفصِّل كل نتيجة اكتشاف.
  • role_filter — أدوار مفصولة بفواصل لتضمينها. يفترض الاكتشاف user,assistant افتراضيًا (مخرجات الأدوات عادةً ضجيج). مرّر user,assistant,tool لتضمين مخرجات الأدوات (لتصحيح سلوك الأدوات) أو tool للبحث في مخرجات الأدوات فقط.

متى تُستخدم

يُوجَّه الوكيل لاستخدام بحث الجلسات تلقائيًا:

"عندما يشير المستخدم إلى شيء من محادثة سابقة أو تشتبه في وجود سياق سابق ذي صلة، استخدم session_search لاسترجاعه قبل أن تطلب منه التكرار."

المحفّزات النموذجية: "فعلنا هذا من قبل"، "تذكّر عندما"، "في المرة الماضية"، "كما ذكرت"، أو أي إشارة إلى مشروع/شخص/مفهوم ليس في النافذة الحالية.

جلسات جماعية مشتركة مقابل معزولة

افتراضيًا، يستخدم Hermes group_sessions_per_user: true في config.yaml. هذا يعني:

  • يمكن لأليس وبوب التحدث كلاهما مع Hermes في نفس قناة Discord دون مشاركة سجل النسخة النصية
  • مهمة ثقيلة بالأدوات لمستخدم واحد لا تلوّث نافذة سياق مستخدم آخر
  • يرتبط الدور الجاري بمفتاح المُرسل الذي بدأه، لكن /stop يظل يصل إليه — انظر أدناه

/stop يعني "أوقف ما يعمل في هذه المحادثة": يجرّب أولًا مفتاح جلسة المستدعي نفسه، ثم أي دور حي في هذه المحادثة — بما فيه تشغيلات المشاركين الآخرين داخل thread المستدعي — مع مراعاة التفويض، ولا يصل أبدًا إلى غرفة أو مساحة عمل أو profile آخر. لذا يمكن لأمر /stop من أليس غير النشطة إنهاء دور بدأه بوب (أو بوت) في الغرفة التي توجد فيها. نطاق أمر /stop المرسَل من داخل thread أضيق: يصل إلى التشغيلات التابعة لتلك الـ thread وإلى تشغيل على مستوى الغرفة لا يشغل خانة thread (شكل الرسائل المباشرة المتتابعة)، لكنه لا يصل أبدًا إلى thread أخرى في القناة نفسها أو إلى تشغيل نظير على المستوى الأعلى ومخصص لكل مُرسل.

إذا أردت "عقل غرفة" واحدًا مشتركًا بدلًا من ذلك، اضبط:

يُعيد ذلك المجموعات/القنوات إلى جلسة مشتركة واحدة لكل غرفة، مما يحافظ على السياق المحادثي المشترك لكن يشارك أيضًا تكاليف الـ tokens، وحالة المقاطعة، ونمو السياق.

استمرارية الجلسة

لا تُعاد ضبط محادثات gateway بعد الخمول أو عند حد يومي. استخدم /new أو /reset لمحادثة جديدة صريحة؛ يبقى ضغط السياق تلقائيًا. تُتجاهَل إعدادات session_reset القديمة، وتجاوزات سياسة إعادة الضبط، ومتغيرات البيئة لمؤقت إعادة الضبط، في المكوّن الأساسي. إذا كانت إعداداتك لا تزال تضبط session_reset.mode على idle، daily أو both، يُصدر بدء gateway و hermes doctor تحذيرًا بشأنها. للاحتفاظ بإعادة الضبط الزمنية، ثبّت إضافة الكتالوج التي تقرأ الكتلة نفسها دون تغيير: hermes plugins install hermes-session-reset-policy. قد تُحرَّر الوكلاء المخزّنة مؤقتًا لاستعادة الموارد دون استبدال المحادثة الدائمة. تحدّ حداثة الاستعادة بعد إعادة التشغيل من المتابعة التلقائية، لا من السجل المحمَّل عندما ترسل رسالة.

لا ينقل /new إلا العرض الذي نفّذه. يمكن أن تكون الجلسة الواحدة مفتوحة في عدة أماكن في آن واحد — نافذة Desktop، و TUI، وطرفية hermes chat --resume، ومحرّر ACP، وموضوع Telegram — وكلها مرتبطة بالمحادثة الحيّة نفسها على الـ gateway. وتشغيل /new (أو /reset) في أحدها ينشئ جلسة جديدة و يعيد ربط تلك النافذة أو مسار المحادثة بها. وتبقى العروض الأخرى على الجلسة الأصلية، ويبقى سجلها دون مساس، ويستمر أي دور يعمل فيها بالفعل. أما إنهاء المحادثة المشتركة أو مسحها فإجراء صريح منفصل (Stop، ثم /new؛ أو حذف، يُرفض أثناء وجود دور حيّ).

نظافة الجلسة: لماذا لا يزال ينبغي عليك تشغيل /new

لأن محادثات gateway لا تنتهي صلاحيتها من تلقاء نفسها أبدًا، من السهل تشغيل جلسة واحدة لأسابيع. هذا يعمل، لكنه يُبطل بصمت حلقة التعلّم ويُضخِّم التكاليف:

  • الذاكرة لا تُجدي إلا عند الحدود. تُحقَن MEMORY.md / USER.md عند بدء الجلسة، وتوجد session_search لاسترجاع ما سقط من السياق. في جلسة لا تنتهي أبدًا يبقى كل شيء داخل السياق، لذا لا سبب للوكيل لاستشارة الذاكرة — آلية "التعلّم الذاتي" بالكاد تعمل. تقطير الذاكرة (الحفظ قبل إعادة الضبط) لا يحدث أيضًا إلا عندما تنتهي جلسة فعلًا.
  • تنمو التكلفة مع السجل. يبقي الضغط جلسة طويلة عاملة، لكن كل دور لا يزال يحمل بادئة (مضغوطة) كبيرة. جلسة جديدة بذاكرة مُقطَّرة أرخص دائمًا تقريبًا من خيط عمره شهر.

قاعدة عملية: أنهِ جلسة عندما تنهي مهمة أو موضوعًا. شغّل /new (مُسمّاة اختياريًا، مثل /new payments-refactor) عند نقاط التوقف الطبيعية — يومية أو لكل مشروع كلاهما يعمل. قبل إعادة الضبط، اطلب من الوكيل "تذكّر أي شيء يستحق الاحتفاظ به" إذا أظهر العمل تفضيلات أو إجراءات دائمة؛ يحفظ الوكيل الذاكرة والمهارات من الجلسة المنتهية تلقائيًا، لكن التنبيه الصريح يساعد. إعادة تشغيل الجهاز أو الـ gateway ليست حدًا — تُستأنف نفس الجلسة.

راجع الذاكرة لمعرفة ما الذي يُنقَل عبر الحدود.

الاستمرارية بعد الأعطال وإعادة التشغيل

مُصمَّمة محادثة gateway لتكون جلسة مستمرة واحدة — تُضغَط مرارًا مع نموّها — حتى تشغّل صراحةً /new (أو /reset). يصمد هذا عبر أعطال gateway وإعادة تشغيله وتحديثاته:

  • تُكتَب هوية الجلسة (مفتاح التوجيه، المحادثة، الأصل) ذريًا عند إنشاء صف الجلسة، في كل مسار إنشاء (/new، الرسالة الأولى، أبناء /branch). إذا فشلت هذه الكتابة يومًا، فإن تحديث التوجيه في الدور التالي مباشرة يُصلح الصف تلقائيًا.
  • بعد إعادة التشغيل، يُعيد الـ gateway حل كل محادثة إلى الجلسة ذات أحدث نشاط فعلي — لا يمكن أبدًا لصف قديم راكد أن يفوز على المحادثة التي كنت تجريها فعلًا.
  • تحترم الاستعادة حدود /new: إذا كان أحدث حدث لمحادثة هو إعادة ضبط مقصودة، تبدأ الاستعادة من جديد بدلًا من التمدد خلف إعادة الضبط لإحياء جلسة أقدم. لا يمنع الوقت المنقضي وحده أبدًا استعادة محادثة دائمة.

sessions.json ليس قائمة الجلسات

يعيش فهرس توجيه gateway في جدول gateway_routing داخل state.db؛ ~/.hermes/sessions/sessions.json مرآة قديمة له، مُبقاة للتوافق إلى الخلف (عطِّلها بضبط gateway.write_sessions_json: false). تربط مفاتيح جلسات المراسلة (agent:main:<platform>:...) بمعرّفات الجلسات النشطة. تحتوي فقط على مدخلات gateway/المراسلة على الإطلاق، لذا إذا شغّلت منصة مراسلة سترى تلك فقط (مثل agent:main:whatsapp:dm:...).

هذا متوقَّع ولا يعني أن جلسات CLI الخاصة بك مفقودة. تقرأ hermes sessions list و/sessions ولوحة التحكم جميعها state.db، الذي يحتفظ بـكل جلسة (CLI وTUI وgateway). لقطات /save تحت ~/.hermes/sessions/saved/*.json صادرات ملائمة، وليست الفهرس.

إذا لم تظهر جلسات CLI فعلًا في hermes sessions list، فالسبب هو عدم استلام state.db لها — شغّل hermes sessions repair وراقب ظهور تحذير ⚠ Session store unavailable عند إقلاع CLI، مما يعني أن استمرارية SQLite فشلت لذلك التشغيل.

نُسخ JSONL نصية قديمة

قد يكون للجلسات المُنشأة قبل أن يصبح state.db أساسيًا ملفات *.jsonl متبقية في ~/.hermes/sessions/. لم تعد تُكتب أو تُقرأ بواسطة Hermes. آمن حذفها بعد التحقق من وجود الجلسة المقابلة في state.db.

مخطط قاعدة البيانات

الجداول الرئيسية في state.db:

  • sessions — البيانات الوصفية للجلسة (id، source، user_id، model، title، الطوابع الزمنية، عدد الـ tokens). للعناوين فهرس فريد (تُسمح القيم NULL، فقط غير NULL يجب أن تكون فريدة).
  • messages — سجل الرسائل الكامل (role، content، tool_calls، tool_name، token_count)
  • messages_fts — جدول افتراضي FTS5 للبحث النصي الكامل عبر محتوى الرسائل

انتهاء صلاحية الجلسات وتنظيفها

التنظيف التلقائي

  • تستمر محادثات gateway عبر الخمول؛ استخدم /new أو /reset لحد صريح
  • قبل إعادة الضبط، يحفظ الوكيل الذاكرة والمهارات من الجلسة المنتهية
  • التقليم التلقائي (معطَّل افتراضيًا؛ فعّله اختياريًا): عندما تكون sessions.auto_prune بالقيمة true، تُقلَّم الجلسات المنتهية الخاملة لمدة sessions.retention_days (الافتراضي 90) عند بدء CLI/gateway/cron
  • مطالبة انخفاض مساحة القرص. ما دام config.yaml لا يحتوي على المفتاح sessions.auto_prune، يفحص Hermes القرص الذي يحتضن state.db عند بدء الجلسة (استدعاءان لنظام الملفات، بلا تكلفة قابلة للقياس). وعندما تقلّ مساحة ذلك القرص (أقل من 2 GB حرة، أو أقل من 10% حرة مع بقاء أقل من 20 GB) يسأل مرة واحدة: يسأل CLI الكلاسيكي عند البدء (أول إطلاق عند انخفاض المساحة يقيس فقط في الخلفية، ويظهر السؤال من الإطلاق التالي فصاعدًا، فلا ينتظر البدء قاعدة البيانات أبدًا)، ويعرض TUI و Desktop إشعارًا، وينشر الـ gateway السؤال في قناته الرئيسية. وتقدّر المطالبة حجم السجل الذي سيحذفه التقليم (موزونًا بالبايتات المخزّنة، حتى لا تضخّمه رسائل قديمة صغيرة كثيرة) وتوضح بصراحة متى لن يحلّ التقليم مشكلة القرص (لا توجد جلسة أقدم من retention_days، أو أن السجل نسبة صغيرة من القرص الممتلئ). ويحرّر السجل المحذوف مساحة داخل state.db؛ ونادرًا ما يعمل VACUUM التلقائي الوارد أدناه بعد تقليم واحد، لذا نفّذ hermes sessions optimize لإعادة المساحة إلى القرص. أجب بـ /autoprune on أو /autoprune off (احتفظ بكل شيء؛ ولن يُسأل مجددًا) أو /autoprune later (تذكير بعد أسبوع)؛ ويعرض /autoprune وحده الحالة الحالية
  • sessions.retention_days يجب أن يكون عددًا صحيحًا من الأيام >= 0. تُرفض القيمة السالبة (أو المفقودة): تسجّل صيانة بدء التشغيل تحذيرًا يسمّي النطاق المسموح وتتخطى المسح، بدلًا من اعتبار موعد قطع مستقبلي يعني "كل شيء" — و sessions.auto_prune: false هو المفتاح الذي يعطّل التقليم
  • بعد تقليم أزال صفوفًا فعلًا، تخضع state.db لعملية VACUUM لاستعادة مساحة القرص فقط عندما يُجتاز كلا الشرطين: مرور sessions.min_vacuum_interval_days (الافتراضي 30) على الأقل منذ آخر VACUUM ناجح، وكون أكثر من 25% من صفحات الملف قابلة للاستعادة (PRAGMA freelist_count / page_count). قاعدة بيانات كثيفة لا تدفع أبدًا ثمن إعادة كتابة كاملة لاستعادة بضعة ميغابايتات (لا يُقلِّص SQLite الملف عند DELETE عادي)
  • يعمل التقليم مرة واحدة على الأكثر كل sessions.min_interval_hours (الافتراضي 24)؛ يُتَتبَّع طابع زمن آخر تشغيل داخل state.db نفسه بحيث يُشارَك عبر كل عملية Hermes في نفس HERMES_HOME

دون تقليم، ينمو state.db بلا حدود — أُبلغ عن ملفات بحجم عدة غيغابايتات خلال أسابيع على تثبيتات gateway و cron. ولتقييده، فعّله في ~/.hermes/config.yaml (أو أجب بـ /autoprune on):

تحتفظ التثبيتات التي تضبط أيًّا من هذه المفاتيح صراحةً بقيمها؛ ولا تتبع القيم الافتراضية إلا المفاتيح غير المضبوطة.

فقط الجلسات المنتهية فقط تُحذف. لا تُقلَّم الجلسات النشطة تلقائيًا أبدًا، بغض النظر عن عمرها. يُحسب عمر الجلسات المنتهية من آخر نشاط لها — أحدث النشاط الحي أو آخر رسالة أو بدء الجلسة — فلا تُحذف محادثة طويلة الأمد استُخدمت مؤخرًا لمجرد أنها بدأت قبل نافذة الاحتفاظ. ينطبق ذلك أيضًا على محادثة قسّمها الضغط إلى عدة جلسات: تُحفَظ مقاطعها الأقدم ما دام أي مقطع لاحق محفوظًا، وتُقلَّم معه عندما تصبح المحادثة كلها مؤهلة.

جلسات مفتوحة راكدة من الأتمتة. بعض المُنتِجين — مهام cron، عمّال kanban، subagents، تشغيلات CLI لمرة واحدة — يمكن أن يموتوا دون وسم جلستهم أبدًا كمنتهية، والتقليم لا يحذف إلا الصفوف المنتهية. لمنع تراكم تلك إلى الأبد، تُغلق كل مرحلة تقليم تلقائي أيضًا الجلسات المفتوحة من تلك المصادر المملوكة للحالة (cli، cron، kanban، acp، api_server، subagent، tool، إضافةً إلى العناصر النائبة recovered التي يُنشئها hermes sessions recover للرسائل اليتيمة) التي مضى على آخر نشاط لها أكثر من retention_days (end_reason: startup_orphan_reap). الإغلاق غير هدّام — تظل الجلسة قابلة للاستئناف — ويُحسب عمر الصف من إغلاقه، فلا يُحذف إلا في مرحلة لاحقة بعد نافذة احتفاظ كاملة أخرى. جلسات منصات المراسلة (Telegram، Discord، …)، وجلسات TUI/Desktop، والجلسات المثبَّتة، والجلسات ذات دور حي أو ضغط جارٍ لا يُغلقها هذا الاكتساح أبدًا.

حراسة النسخ النصية الضخمة الحجم

حدّان يمنعان تحميل نسخة نصية جامحة إلى الذاكرة دفعة واحدة (كلاهما افتراضيًا 20000 رسالة؛ 0 يعطّل الحارس):

max_export_messages ينطبق لكل جلسة على النسخة الاحتياطية JSON/JSONL (hermes sessions export، sessions export في hermes console، و /save json في CLI، والمراسلة، و TUI، و Desktop). يحتسب كل صف مخزّن، بما فيه المؤرشف، لأن النسخة الاحتياطية تضمها كلها. قد تتجاوز الحد حتى جلسة ضُغطت كثيرًا ولها ذيل حي صغير. أما إجراء Export في صفحة Sessions بلوحة التحكم فيبث الصفوف ولا يخضع للسقف.

max_resume_messages يحدّد ما يُحمِّله الاستئناف فعليًا، وليس كامل تاريخ المحادثة:

  • يُجسِّد الاستئناف التفاعلي البسيط (CLI --resume، TUI) نسب الضغط الكامل — كل مقطع مضغوط بالإضافة إلى الطرف الحي — لذا فهو محدود عبر النسب.
  • يُصفِّح استئناف Desktop البارد النسخة النصية عبر REST ولا يحتفظ في الذاكرة إلا بمقطع الطرف الحي، لذا فهو محدود بالطرف وحده. محادثة طويلة العمر ضُغطت مرات عديدة (عشرات المقاطع، عشرات آلاف الصفوف المؤرشفة خلف طرف صغير) هي بالضبط ما يُقصد به الضغط أن يُنتج، وتُفتح عاديًا؛ يعكس عدد رسائل تذييلها النسب المُخزَّن، لا الـ prompt الحي.

عندما يُرفَض استئناف، يتلقى العميل رمز الخطأ 4130 مع العدد والنطاق الذي قِيس فيه (across its lineage أو in its tip segment). يُعيد أمر /save في TUI/Desktop المرفوض بسبب max_export_messages رمز الخطأ 4131. hermes sessions export يظل يعمل لتلك الجلسات؛ وتتطلب نسخته الاحتياطية JSON/JSONL أن تبقى كل جلسة دون max_export_messages.

التنظيف اليدوي

نصيحة

التقليم التلقائي معطَّل افتراضيًا، ويسألك Hermes مرة واحدة عندما تنخفض مساحة القرص الذي يحتضن state.db (راجع التنظيف التلقائي أعلاه). وعند تفعيله، تُزال الجلسات المنتهية الخاملة لمدة sessions.retention_days (الافتراضي 90) عند الإقلاع، ولا تُمس الجلسات النشطة أبدًا. يُغذّي سجل الجلسات استرجاع session_search عبر المحادثات السابقة، لذا فالخيار لك: /autoprune on|off، أو sessions.auto_prune في config.yaml. ومع تعطيل التقليم التلقائي، يبقى hermes sessions prune متاحًا للتنظيف لمرة واحدة (نمط فشل مُلاحَظ دون أي تقليم: state.db بحجم 384 MB مع نحو 1000 جلسة يُبطئ إدراجات FTS5 وقوائم /resume).

عزل اتصال الشبكة الصادر لنشر Docker

عند تشغيل Hermes داخل Docker، يمنح network_mode: host الافتراضي عملية الوكيل وصولًا غير مقيّد إلى الشبكة الصادرة. يوضح هذا الدليل كيفية تقسيم حركة البيانات بحيث لا يصل جوهر الوكيل إلا إلى الخدمات المطلوبة، مع حظر الاتصالات الصادرة العشوائية.

هذا دفاع بالأساس ضد هجمات حقن الـ prompt التي تحاول تسريب البيانات عبر curl, wget أو HTTP الخام من أوامر الـ shell التي تولّدها الأدوات.

نموذج التهديد

يحدّد ملف Hermes SECURITY.md §2 نموذج الثقة. يُعد terminal backend حدّ التنفيذ الرئيسي. لكن عند التشغيل باستخدام network_mode: host ، يمكن لأي أمر ينفّذه الوكيل الوصول إلى أي endpoint على الشبكة، بما في ذلك endpoints الخارجية.

يضيف عزل الاتصال الصادر طبقة ثانية: حتى لو نُفّذ أمر خبيث داخل الحاوية، فلن يستطيع الوصول إلى endpoints خارج المجموعة المسموح بها صراحة.

البنية المعمارية (Architecture)

شبكتا Docker:

  • internal — دون مسار افتراضي أو اتصال إنترنت. يعمل هنا الوكيل ولوحة التحكم و gateway.
  • egress — تتصل بالإنترنت. ولا تتصل بها إلا الخدمات التي تحتاج الوصول إلى واجهات API خارجية.

خدمة gateway متصلة بالشبكتين، لتستطيع استقبال رسائل Telegram/Slack وغيرها وتمريرها إلى الوكيل على الشبكة الداخلية.

التحقق من الإعداد

بعد تشغيل الحزمة، تحقّق من العزل:

القيود

  • حلّ أسماء DNS: لا تزال شبكة internal قادرة على حلّ أسماء DNS الخارجية ما لم تشغّل أيضًا محلّل DNS محليًا يمنع الاستعلامات الخارجية. هذا مقبول في معظم نماذج التهديد، لأن حل أسماء DNS وحده لا يسرّب بيانات ذات قيمة.

  • ليس بديلًا لـ sandbox backends: يعزل هذا الدليل شبكة حاوية الوكيل. إذا استخدمت terminal backend المحلي الافتراضي، تُنفّذ أوامر الأدوات داخل الحاوية نفسها. لعزل أقوى، اجمع تقسيم الشبكة مع terminal backend في sandbox (Docker و Modal و Daytona).

  • تحتاج محوّلات المنصات إلى اتصال صادر: تحتاج خدمة gateway إلى وصول صادر لبلوغ APIs منصات المراسلة. إذا أضفت محوّلات منصات جديدة، فأضف endpoints الخاصة بـ APIs إلى قائمة سماح proxy.

التكامل مع Open WebUI

Open WebUI (126k★) هي أكثر واجهات المحادثة المستضافة ذاتيًا (self-hosted) للذكاء الاصطناعي شعبية. بفضل خادم API المدمج في Hermes Agent، يمكنك استخدام Open WebUI كواجهة ويب أمامية مصقولة لوكيلك — مع إدارة المحادثات، وحسابات المستخدمين، وواجهة محادثة عصرية.

البنية

تتصل Open WebUI بخادم API الخاص بـ Hermes Agent تمامًا كما تتصل بـ OpenAI. يعالج Hermes الطلبات باستخدام مجموعة أدواته الكاملة — الطرفية، وعمليات الملفات، والبحث في الويب، والذاكرة، والمهارات — ثم يعيد الرد النهائي.

مكان التشغيل

خادم API هو بيئة تشغيل لوكيل Hermes، وليس مجرد وكيل وسيط (proxy) لـ LLM. فمع كل طلب، ينشئ Hermes كائن AIAgent على جانب الخادم في المضيف الذي يعمل عليه خادم API. وتُنفَّذ استدعاءات الأدوات حيث يعمل ذلك الخادم.

على سبيل المثال، إذا وجّه حاسوب محمول Open WebUI أو أي عميل آخر متوافق مع OpenAI إلى خادم API لـ Hermes على جهاز بعيد، فإن pwd وأدوات الملفات وأدوات المتصفح وأدوات MCP المحلية وغيرها من أدوات مساحة العمل تعمل على مضيف خادم API البعيد، لا على الحاسوب المحمول.

تتواصل Open WebUI مع Hermes من خادم إلى خادم، لذا لا تحتاج إلى API_SERVER_CORS_ORIGINS لهذا التكامل.

تحذير

لا تسري متغيرات البيئة إلا عند التشغيل الأول لـ Open WebUI. بعد ذلك، تُخزَّن إعدادات الاتصال في قاعدة بياناتها الداخلية. لتغييرها لاحقًا، استخدم واجهة المسؤول أو احذف وحدة تخزين Docker ‏(volume) وابدأ من جديد.

نوع API: ‏Chat Completions مقابل Responses

تدعم Open WebUI وضعين لواجهة API عند الاتصال بـ backend:

الوضعالصيغةمتى تستخدمه
Chat Completions (الافتراضي)/v1/chat/completionsمستحسن. يعمل مباشرة دون إعداد إضافي.
Responses (تجريبي)/v1/responsesلحفظ حالة المحادثة على جانب الخادم عبر previous_response_id.

استخدام Chat Completions (مستحسن)

هذا هو الوضع الافتراضي ولا يتطلب أي إعداد إضافي. ترسل Open WebUI طلبات قياسية بصيغة OpenAI ويستجيب Hermes Agent وفقًا لذلك. يتضمن كل طلب سجل المحادثة كاملًا.

استخدام Responses API

لاستخدام وضع Responses API:

  1. انتقل إلى Admin Settings → Connections → OpenAI → Manage
  2. عدّل اتصال hermes-agent الخاص بك
  3. غيّر API Type من "Chat Completions" إلى "Responses (Experimental)"
  4. احفظ

مع Responses API، ترسل Open WebUI الطلبات بصيغة Responses (مصفوفة input + instructions)، ويستطيع Hermes Agent الحفاظ على السجل الكامل لاستدعاءات الأدوات عبر الأدوار باستخدام previous_response_id. وعند stream: true، يبث Hermes أيضًا عناصر function_call و function_call_output الأصلية وفق المواصفة، ما يتيح واجهات مخصصة ومُهيكلة لاستدعاءات الأدوات في العملاء التي تعرض أحداث Responses.

ملاحظة

لا تزال Open WebUI حاليًا تدير سجل المحادثة على جانب العميل حتى في وضع Responses — فهي ترسل سجل الرسائل كاملًا في كل طلب بدلًا من استخدام previous_response_id. الميزة الرئيسية لوضع Responses اليوم هي تدفق الأحداث المُهيكل: إذ تصل أجزاء النص (deltas) وعناصر function_call و function_call_output كأحداث SSE بصيغة OpenAI Responses بدلًا من أجزاء (chunks) بصيغة Chat Completions.

آلية العمل

عندما ترسل رسالة في Open WebUI:

  1. ترسل Open WebUI طلب POST /v1/chat/completions يحتوي على رسالتك وسجل المحادثة
  2. ينشئ Hermes Agent نسخة AIAgent على جانب الخادم باستخدام الـ profile الخاص بخادم API، وإعدادات النموذج والمزوّد، والذاكرة، والمهارات، وtoolsets المضبوطة لخادم API
  3. يعالج الوكيل طلبك — وقد يستدعي أدوات (الطرفية، وعمليات الملفات، والبحث في الويب، وغيرها) على مضيف خادم API
  4. أثناء تنفيذ الأدوات، تُبث رسائل تقدّم مضمّنة إلى الواجهة كي ترى ما يفعله الوكيل (مثل `💻 ls -la`، `🔍 Python 3.12 release`)
  5. يُبث الرد النصي النهائي للوكيل عائدًا إلى Open WebUI
  6. تعرض Open WebUI الرد في واجهة المحادثة الخاصة بها

يمكن لوكيلك الوصول إلى الأدوات والإمكانات نفسها المتاحة لنسخة Hermes التي تشغّل خادم API. فإذا كان خادم API بعيدًا، فتلك الأدوات بعيدة أيضًا.

إذا كنت تحتاج اليوم إلى تشغيل الأدوات على مساحة عملك المحلية، فشغّل Hermes محليًا ووجّهه إلى مزوّد LLM صرف أو إلى وكيل وسيط صرف للنماذج متوافق مع OpenAI (مثل vLLM وLiteLLM وOllama وllama.cpp وOpenAI وOpenRouter وغيرها). يجري تتبّع وضع مستقبلي لبيئة تشغيل مقسّمة من نوع "remote brain, local hands" في #18715؛ وهذا ليس سلوك خادم API الحالي.

تقدّم الأدوات

مع تفعيل البث المتدفق (وهو الافتراضي)، سترى مؤشرات مضمّنة موجزة أثناء تشغيل الأدوات — رمز الإيموجي الخاص بالأداة ووسيطها الرئيسي. تظهر هذه المؤشرات في تدفق الرد قبل الإجابة النهائية للوكيل، فتمنحك رؤية لما يجري خلف الكواليس.

استكشاف الأخطاء وإصلاحها

لا تظهر أي نماذج في القائمة المنسدلة

  • تحقّق من أن الـ URL ينتهي بـ /v1: http://host.docker.internal:8642/v1 (وليس :8642 فقط)
  • تحقّق من أن الـ gateway يعمل: يُفترض أن يعيد curl http://localhost:8642/health القيمة {"status": "ok"}
  • تحقّق من قائمة النماذج: يُفترض أن يعيد curl -H "Authorization: Bearer your-secret-key" http://localhost:8642/v1/models قائمة تتضمن hermes-agent
  • شبكة Docker: من داخل Docker، تعني localhost الحاوية نفسها، لا جهازك المضيف. استخدم host.docker.internal أو --network=host.
  • backend فارغ لـ Ollama يحجب المنتقي: إذا حذفت ENABLE_OLLAMA_API=false، فستعرض Open WebUI قسم Ollama فارغًا فوق نماذج Hermes. أعد تشغيل الحاوية مع -e ENABLE_OLLAMA_API=false أو عطّل Ollama من Admin Settings → Connections.

ينجح اختبار الاتصال لكن لا تُحمَّل أي نماذج

السبب في الغالب هو غياب اللاحقة /v1. اختبار الاتصال في Open WebUI مجرد فحص أساسي لإمكانية الاتصال — ولا يتحقق من أن سرد النماذج يعمل.

يستغرق الرد وقتًا طويلًا

قد يكون Hermes Agent بصدد تنفيذ عدة استدعاءات للأدوات (قراءة ملفات، تشغيل أوامر، البحث في الويب) قبل إنتاج رده النهائي. هذا طبيعي مع الاستعلامات المعقدة. يظهر الرد دفعة واحدة عندما ينتهي الوكيل.

أخطاء "Invalid API key"

تأكد من أن OPENAI_API_KEY في Open WebUI يطابق API_SERVER_KEY في Hermes Agent.

تحذير

تحفظ Open WebUI إعدادات الاتصال المتوافقة مع OpenAI في قاعدة بياناتها الخاصة بعد التشغيل الأول. إذا حفظت مفتاحًا خاطئًا عن طريق الخطأ في واجهة المسؤول، فلا يكفي إصلاح متغيرات البيئة وحدها — حدّث الاتصال المحفوظ أو احذفه من Admin Settings → Connections، أو أعد تعيين مجلد بيانات Open WebUI / قاعدة بياناتها.

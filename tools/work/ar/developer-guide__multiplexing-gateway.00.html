Multiplexing Gateway

يمكن لعملية gateway واحدة خدمة كل profile في التثبيت. الوضع مفعّل افتراضيًا (gateway.multiplex_profiles ، الافتراضي true)، وكل ما يغيّره يعود فور إيقاف الخيار. يُحسم الخيار غير المضبوط عند الإقلاع بواسطة hermes_cli/gateway_multiplex_mode.py::resolve_multiplex_mode ، الذي يجري فحص hermes gateway migrate المسبق، ويبقي gateway مستقلًا إذا ظل profile ثانوي يشغّل gateway خاصًا به، أو وجد مانع، أو تعذّر ترحيل المضيف (راجع "خيار الوضع"). هذا المستند يشرح مبررات التصميم المشار إليها من agent/secret_scope.py ("مسار العمل A"): ما يُعزل لكل profile وآلية عزله وما يبقى عمدًا عامًا للعملية.

نظرة عامة

دون multiplexing، تخدم عملية gateway واحدة profile واحدًا فقط — .env وجلساته ومهاراته ومحوّلات منصاته — وتشغّل التثبيتات المتعددة profiles عملية لكل profile. يجمع multiplexing ذلك في عملية واحدة: يحصل profile الافتراضي وكل profile مسمّى مخدوم على محوّلاته وأسراره وجلساته ونبضات cron الخاصة، مع مشاركة حلقة أحداث واحدة ومستمع HTTP واحد وقفل عملية واحد وواجهة حالة واحدة.

قيد التصميم الذي يشكّل كل ما أدناه: يجب ألا تلاحظ أدوار profile A حالة profile B مطلقًا. تُعزل الأسرار ومجلدات home والجلسات ومسارات المحوّلات لكل profile؛ وكل ما يتعذّر عزله بعد يفشل بطريقة مغلقة أو يُوثّق كقيد معروف في نهاية المستند.

خيار الوضع

  • الإعداد: gateway.multiplex_profiles (مقبول أيضًا في المستوى الأعلى). يُحلَّل في gateway/config.py بأولوية env > config > غير مضبوط. GatewayConfig يبقي الخيار غير المضبوط كـ None (تختبر القارئات صدقه، فيُقرأ كمعطّل)؛ load_gateway_config_for_runner يستدعي بعدها resolve_multiplex_mode ، الذي يكتب قرار الإقلاع — True في تثبيت افتراضي متعدد profiles وهادئ، False مع سبب مسجّل خلاف ذلك. تمر القيم الصريحة حرفيًا؛ ولا تُحسم إعدادات محقونة في GatewayRunner(config=...).
  • تقرأ العمليات الأخرى سجل served_profiles لـ gateway الحي أولًا، والخيار الصريح ثانيًا (gateway_multiplex_mode.default_gateway_multiplexes / explicit_multiplex_flag)، لا الافتراضي المدمج مطلقًا: named_profile_served_ by_running_multiplexer وتحذير التسجيل وحماية مستمع لوحة التحكم ومحلّل منفذ تشغيل cron وإقلاع الحاوية وخطة الترحيل (_read_multiplex_flag ، فيُقرأ الافتراضي غير المضبوط كـ "لم يُفعّل multiplexing بعد" ويستمر الجمع).
  • تجاوز البيئة: GATEWAY_MULTIPLEX_PROFILES يقبل tokens صريحة للقيم الصحيحة/الخاطئة فقط؛ والقيمة الفارغة أو غير المعروفة تعيد "لا تجاوز"، فلا يستطيع سر نشر فارغ حجب تفعيل في الإعدادات.
  • عند بدء التشغيل، يستدعي GatewayRunner.__init__ agent.secret_scope.set_multiplex_active(...) مرة واحدة. _MULTIPLEX_ACTIVE متغير وحدة عام عادي، لا contextvar: يصف وضع النشر، لا قيمة خاصة بكل مهمة. مهمته الوحيدة تفعيل سلوك الفشل المغلق في get_secret().
  • ليس لـ backend لوحة التحكم/Desktop (hermes serve) خيار كهذا، لذا hermes_cli/web_server.py::start_server يستدعي tui_gateway.launch_profile_policy.activate_multi_profile_hosting_eagerly() كآخر خطوة إقلاع: يفعّل المضيف الحماية عندما يملك الجهاز أكثر من home لـ profile قابل للخدمة، بدلًا من انتظار أول طلب ?profile=<other>. التفعيل أحادي الاتجاه، وكل ما كان backend قد فعله بالفعل (تفريغ النص المسجّل عند حصاد الخامل والغرف المستضافة و cron) لم يُعَد تحديد نطاقه. يعمل أخيرًا لأن التفعيل يجمّد أيضًا os.environ كبيانات اعتماد profile الإطلاق، وتلك اللقطة هي المصدر الوحيد لمفاتيح الإطلاق التي لا تملك .env لإعادة البناء منه (systemd Environment=, op run و Compose) — المفتاح المحقون أو المدوّر بعد التجميد غير مرئي طوال عمر العملية. المضيف ذو profile واحد فعلًا لا يفعّل الحماية؛ gateway.multiplex_profiles: false متقاعد ولا يُستشار عمدًا هنا (احترامه يخدم profile ثانيًا ببيانات اعتماد profile الإطلاق)؛ ومجلد profiles/ غير المقروء يفشل مغلقًا (يفعّل الحماية)، ويسجّل WARNING.
  • مع تفعيل الحماية، يصبح profile الإطلاق مستأجرًا أيضًا: متن بلا profile موجّه يربط launch_profile_scope_if_multiplexed() بدلًا من العمل بلا نطاق على os.environ المحيط. لاحظ ترتيب الأولوية داخل ذلك النطاق: .env الخاص بـ home الإطلاق يتقدم على البيئة المجمّدة، لذا ليس التفعيل أشد فقط على مستأجر الإطلاق — لمفتاح مضبوط في كل من os.environ و <launch home>/.env ، كانت القراءة دون نطاق تعيد القيمة المحيطة قبل التفعيل، وتعيد قيمة .env بعده. المفاتيح الموجودة في البيئة وحدها لا تتأثر.
  • المتن الذي لم يعد اسم profile الموجّه فيه يُحل (حُذف أو أُعيدت تسميته وسط التشغيل) لا يربط شيئًا: تثير قراءات بيانات اعتماده UnscopedSecretError بدلًا من الرجوع إلى بيانات profile الإطلاق. سؤال "لمن هذا؟" دون إجابة حالة فشل مغلق، لا استعارة مطلقًا.

تركيب النطاق

يركّب كل حدث وارد النطاقين المحليين للسياق نفسيهما قبل تشغيل أي كود يملكه profile:

_profile_runtime_scope يغلّف كل نقطة وصل ينفّذ فيها كود يملكه profile: تشغيل المحوّل الثانوي والاتصال وإعادة الاتصال ومعالج حدث المنصة الرئيسي والمعالجة المسبقة للوارد وحسم /model ومعلومات الجلسة ومهام الخلفية ودور الوكيل نفسه. تعمل إعادة تحميل الإعدادات تحت نطاق profile الافتراضي لتُحسم إعدادات gateway العامة (#64674) باتساق.

كلا النطاقين contextvars ، فينتقلان إلى خيوط عمّال executor عبر copy_context() ويتراجعان حتميًا — لا يُكتب شيء إلى os.environ مطلقًا.

مسار العمل A: نطاق أسرار محلي للسياق

agent/secret_scope.py موجود لأن التنفيذ البديهي — جمع كل ملفات .env الخاصة بـ profiles في os.environ — يسرّب مفاتيح profile A إلى أدوار profile B وإلى كل عملية فرعية تُطلق باستخدام env=dict(os.environ).

  • build_profile_secret_scope(home) يدمج .env الخاص بـ profile مع مصادر أسراره المضبوطة، مع تخطي العموميات.
  • set_secret_scope(mapping) يثبّته للمهمة الحالية.
  • get_secret(name) يحسم: قائمة السماح العامة → النطاق النشط → الاحتياط. الاحتياط هو الجزء الحاسم:
    • multiplexing معطّل: يقرأ os.environ ، فتعمل gateways ذات profile واحد وكل المستدعين خارج gateway كما سابقًا تمامًا؛
    • multiplexing مفعّل، ودون نطاق مثبّت: يثير UnscopedSecretError بدلًا من قراءة بيئة العملية بصمت. يفشل موضع استدعاء لم يُرحّل بوضوح عند ذلك السطر نفسه بدلًا من تسريب قيمة profile آخر.
  • قائمة سماح صغيرة (HERMES_HOME, HERMES_PROFILE وإعدادات proxy وإعدادات مستمع API_SERVER_* — دون API_SERVER_KEY عمدًا) تبقى عامة لأنها تصف العملية، لا profile.
  • سلاسل بيانات الاعتماد الافتراضية لـ Cloud SDK محيطة بحكم تصميمها (google.auth.default(), DefaultAzureCredential, boto3.Session() دون مفاتيح): كل مصدر تعبره — بيئة العملية وذاكرات CLI المؤقتة وبيانات المثيل الوصفية — هو هوية سياق الإطلاق. تحت multiplexing، profile مخدوم دون بيانات اعتماد كاملة خاصة به يُرفض من محوّلات Vertex و Entra ID و Bedrock بدلًا من استخدام تلك الهوية مقابل base_url الخاص به؛ وتحتفظ العمليات المستقلة بالسلسلة.

لأن إعادة تحميل .env عند كل دور لا أثر لها تحت multiplexing، تُلتقط بيانات الاعتماد المدوّرة عبر نطاق profile في الدور التالي — لا عبر os.environ مطلقًا. ينطبق ذلك عند حد المحمّل، لا في مساعد إعادة تحميل gateway وحده: يتخطى hermes_cli.env_loader.load_hermes_dotenv تحميل العملية العام كلما كان multiplexing نشطًا و كان تجاوز home لـ profile مثبّتًا (يصله مستدعو وقت الاستيراد و cron وسط الدور)، مع استمرار ملء مصادر الأسرار الخارجية لـ profile في لقطته الخاصة (#77562). لا يتغير تحميل بدء التشغيل غير المحدد بنطاق.

تغطي القاعدة نفسها التي تجعل النطاق مرجعًا نقاط وصل os.environ الأخرى التي يمكن لدور موجّه الوصول إليها: تُحسم مراجع ${VAR} / ${env:VAR} في config.yaml الخاص بـ profile عبر get_secret عند تثبيت نطاق (#84079)، وتحدّث كتابات .env المنفّذة تحت نطاق (save_env_value ، مثل نسخة منح إذن /pair) خريطة النطاق المثبّتة بدلًا من بيئة العملية (#88441).

تجاوز HERMES_HOME

hermes_constants.py يحتفظ بتجاوز محلي للسياق يستشيره get_hermes_home() قبل متغير البيئة HERMES_HOME. كل ما يحسم المسارات عبره — الإعدادات و state.db والمهارات والذاكرة و SOUL والجلسات و Kanban والأهداف واكتشاف الإضافات وتشغيل MCP — يتبع profile النشط تلقائيًا. يوجد get_process_hermes_home() للأصول القليلة على مستوى الجهاز التي يجب ألا تتبع التجاوز. يمنح hermes_home_key() السجلات الخاصة بكل home مفتاح نطاق ثابتًا. ينطلق تحذير لمرة واحدة (#18594) إذا عمل كود خاص بـ profile دون التجاوز حيث يُتوقع وجوده.

توجيه الوارد

gateway.profile_routes يربط (platform, user_id, guild_id, chat_id, thread_id) بـ profile؛ المطابقة تلازمية والأكثر تحديدًا أولًا، مع مطابقة محادثات سلاسل الأبوة لسلاسل الرسائل. لا يعمل التوجيه إلا عند نشاط multiplexing، ويُرفض المسار المطابق الذي يكون هدفه خارج المجموعة المخدومة (يُسقط الحدث، ولا يُسلّم خطأ). المخطط الكامل وقواعد المطابقة: توجيه محادثات البوت المشترك إلى profiles.

خدمة profiles محددة

profiles_to_serve(multiplex, profile_allowlist) في hermes_cli/profiles.py هو نقطة التحكم الوحيدة في profiles التي يخدمها multiplexer: الافتراضي مع كل مجلد profile صالح، مع تصفية اختيارية بقائمة سماح. تفشل قائمة سماح غير سليمة بأمان إلى الافتراضي وحده. تقيّد المجموعة المخدومة تشغيل المحوّلات ونبضات cron (#69377), /p/<profile>/ وقبول HTTP وأهلية المسار وواجهة حالة وقت التشغيل. يبقى profile المستبعد مثبّتًا ويمكنه تشغيل gateway مستقل خاص به.

التخزين الدائم لكل profile

SessionStore لا يربط مقبض قاعدة بيانات عند الإنشاء (#88532). تُحسم مقابض قواعد الجلسات وقت الاستدعاء عبر تجاوز HERMES_HOME النشط — مقبض مؤقت واحد لكل profiles/<name>/state.db محلول — فتُحفظ الجلسات في مخزن profile المالك حتى إذا كان كائن المخزن نفسه مشتركًا. تُنشأ مخازن الاقتران لكل profile مخدوم.

مسارات جلسات لكل بوت

مفاتيح الجلسات موزعة على فضاءات أسماء profiles (agent:main للافتراضي، agent:<name> لـ profiles المسماة). يحمل كل حدث وارد قيمة مجمّدة واحدة من RoutingIdentity (gateway/session_identity.py)، يحسمها resolve_identity() في معالجات الدخول بالمشغّل، وتُثبت على المصدر كخاصية غير مرئية على الاتصال: transport_profile (البوت الذي تلقاه — بيانات الاعتماد وقائمة السماح و authorization_home), runtime_profile (profile الموجّه الذي ينفّذ — runtime_home والمفتاح namespace, store_path)، ومرجع transport ضعيف إلى المحوّل المستقبِل. تُكتب "default" صراحة؛ None لا تعني الافتراضي مطلقًا. تحت multiplexing، يثير مسار إلى profile غير مخدوم IdentityUnresolved ويُسقط الحدث.

تحمل المحوّلات أيضًا _owner_profile (تُثبت عند إعداد المحوّل، قبل أي حدث وارد). يوحّد كل مسار دخول الهوية أولًا — يعمل BasePlatformAdapter._canonicalize عند handle_message وتجميع النصوص/الصور/الألبومات والمسار المشغول وكل مفتاح جلسة مشتق من المحوّل؛ ومعالجات المشغّل الخاصة بـ profile والافتراضية و callback فحص المصادقة وبوابة _handle_message المشتركة تفعل ذلك أيضًا — فلا يُنشأ مفتاح مسار قبل معرفة البوت المستقبِل. تجميع النصوص/الوسائط وتتبع الجلسة النشطة وحماية الجلسة المشغولة و /stop /new /reset وردود clarify كلها لها مفاتيح لكل مسار، فلا يشترك بوتان في محادثة بمسار جلسة، ولا يمكن لأمر تحكم على بوت الوصول إلى تشغيل الآخر. يُسقط المسار إلى profile غير مخدوم مع WARNING واحد عند أول نقطة وصل يصلها، ولا يُدرج مفتاحه في agent:main. انسخ مصدرًا باستخدام session_identity.replace_source لا dataclasses.replace ، وإلا تفقد النسخة وسيلة نقلها وهويتها.

الاستقبال مقابل التسليم: أي بوت يعالج الحدث

تجيب نقطتا وصل في المشغّل عن السؤالين اللذين يخلط بينهما gateway متعدد profiles باستمرار (gateway/authz_mixin.py):

  • _intake_adapter_for(source) — البوت الذي تلقى الحدث. منشأ حي فقط: مرجع النقل الذي ثبّته build_source ، أو محوّل relay على مستوى العملية للأحداث المُسلَّمة عبر relay، أو المحوّل المسجّل حاليًا لـ transport_profile الخاص بالهوية بعد إعادة الاتصال. يقيّد سياسة الاستقبال (قنوات Slack المتجاهلة وتقديم relay وإعادة إرسال حدث حي في الصف)، ويعيد None لمصدر بلا منشأ حي — لا يجوز إعادة قبول صف مستعاد ببوت متخيّل.
  • _delivery_adapter_for(source) — البوت الذي يجيب: الإرسال والتعديل والكتابة والتقدم والمنتقيات وخانات الرسائل المعلّقة. البوت المستقبِل كلما عُرف؛ وإلا المالك الوحيد لـ (platform, runtime_profile) — المحوّل الخاص بالثانوي، أو الأساسي لساتل بوت مشترك، و None للثانوي الذي انقطع بوته (لا يستعير البوت الافتراضي مطلقًا).

الاستعادة و relay و callbacks والانتقال بين الخيوط

يحفظ إدخال التوجيه transport_profile بجانب المفتاح (وعمود sessions.transport_profile في state.db)، فبعد إعادة التشغيل يظل المسار المستعاد يعرف البوت الذي تلقاه: يعيد _restored_source(entry) تثبيت RoutingIdentity دون محوّل حي، و _delivery_adapter_for يسلّم عبر محوّل ذلك البوت أو يفشل مغلقًا — الساتل الموجّه عبر البوت الافتراضي يواصل الإجابة منه، والمسار الذي يملكه ثانوي لا يرجع مطلقًا إلى بيانات اعتماد البوت الافتراضي. تحمل الإدخالات المكتوبة قبل وجود العمود null وتحتفظ باستدلالات البوت المشترك. عبر relay، تخبر قيمة metadata.profile في كل إطار صادر (وفضاء أسماء مفاتيح follow_up) الموصل بالـ profile الذي يوسمه على passthrough_forward التالي، فيبقى ضغط زر بعد slash command موجّه في profile نفسه. تلتقط callbacks المؤجّلة (منتقي /model) home الموجّه وقت الأمر، وتنسخ انتقالات executor في gateway نطاق ContextVar.

طبقة التحكم

لا تصل إضافات Desktop إلى gateway إلا عبر بوابة ws JSON-RPC، لذا يوجد تعداد profiles وإعدادها في tui_gateway/methods_profiles.py: profiles.list, profiles.create, profiles.describe, profiles.configure, profiles.set_asset, profiles.get_asset. تعمل القراءات والكتابات تحت تجاوز HERMES_HOME للـ profile الهدف. كتابات الأصول ذرية ومحدودة النوع والحجم.

أنماط الفشل

  • قاتل عند بدء التشغيل: أخطاء إعداد multiplex وتفعيل profile ثانوي لمنصة تربط منفذًا (MultiplexConfigError, SecondaryPortBindingConfigError) — يملك profile الافتراضي مستمع HTTP المشترك الوحيد.
  • تخطٍ غير قاتل: يُتخطى محوّل ثانوي واحد سيئ الإعداد مع تحذير بدلًا من إسقاط multiplexer.
  • فشل مغلق: قراءة get_secret() غير المحددة بنطاق تحت multiplexing تثير استثناء؛ ويُسقط حدث موجّه يستهدف profile غير مخدوم؛ ويدخل طلب /p/ غير المحدد بنطاق نطاق profile الافتراضي (#61276) بدلًا من نطاق غير معرّف.
  • فشل مغلق لكل profile: خادم MCP بعيد لا تزال قيم url / headers فيه تحمل ${VAR} حرفية بعد العرض تحت نطاق profile المالك لا يتصل (MCP server 'x': ${VAR} in url/headers is not set in this profile's .env or secret source)؛ يُعاد عرض المرجع تحت النطاق الجديد للمالك عند كل اتصال وإعادة اتصال، فيتعافى عندما يوفّر .env لذلك profile أو مصدر أسراره القيمة. تظل خريطة profile الإطلاق تتضمن بيئة إطلاقه المجمّدة (تُحسم بيانات اعتماد systemd Environment= / op run)؛ ويُحسم الثانوي من ملفاته وحدها.
  • بوابات منصات محددة بنطاق: يُقرأ تفعيل A2A (A2A_PORT) و Buzz عبر نطاق profile الخاص / قسم platforms.<name> ، فلا يعود متغير بيئة في profile الإطلاق يفعّل مستمع وارد في كل ثانوي.
  • احتياط: لا يدعم cron.provider الخارجي multiplexing فيرجع إلى المؤقّت المدمج مع تحذير.

ما ليس من الأهداف

يعزل multiplexing profiles؛ ولا يصادق على المستخدمين النهائيين ولا يفوّضهم. profile إعدادات، لا شخص: يثق gateway بوسيلة نقله وجدول توجيهه لتحديد profile الذي ينتمي إليه الحدث. الهوية على مستوى الطلب والتفويض لكل مستخدم فوق طبقة profile خارج نطاق هذا المستند.

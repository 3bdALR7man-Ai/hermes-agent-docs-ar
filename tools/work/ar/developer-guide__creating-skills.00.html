إنشاء المهارات (Skills)

المهارات (Skills) هي الطريقة المفضّلة لإضافة قدرات جديدة إلى Hermes Agent. إنشاؤها أسهل من إنشاء الأدوات، ولا تتطلب أي تعديل في كود الوكيل، ويمكن مشاركتها مع المجتمع.

هل تكون مهارة (Skill) أم أداة (Tool)؟

اجعلها مهارة (Skill) عندما:

  • يمكن التعبير عن القدرة عبر تعليمات + أوامر shell + أدوات موجودة مسبقًا
  • تُغلّف CLI أو API خارجيًا يستطيع الوكيل استدعاءه عبر terminal أو web_extract
  • لا تحتاج إلى تكامل Python مخصّص أو إدارة مفاتيح API مدمجة داخل الوكيل
  • أمثلة: البحث في arXiv، سير عمل git، إدارة Docker، معالجة PDF، البريد الإلكتروني عبر أدوات CLI

اجعلها أداة (Tool) عندما:

  • تتطلب تكاملًا شاملًا مع مفاتيح API أو مسارات مصادقة (auth) أو إعدادات متعددة المكوّنات
  • تحتاج إلى منطق معالجة مخصّص يجب أن يُنفَّذ بدقة في كل مرة
  • تتعامل مع بيانات ثنائية أو بث (streaming) أو أحداث فورية (real-time)
  • أمثلة: أتمتة المتصفح، TTS، تحليل الرؤية (vision)

المهارات الخاصة بمنصة معينة

يمكن للمهارات أن تقتصر على أنظمة تشغيل محدّدة باستخدام الحقل platforms:

عند ضبط هذا الحقل، تُخفى المهارة تلقائيًا من الـ system prompt ومن skills_list() ومن slash commands على المنصات غير المتوافقة. وإذا تُرك فارغًا أو لم يُذكر، تُحمَّل المهارة على كل المنصات (توافقًا مع الإصدارات السابقة).

التفعيل الشرطي للمهارة

يمكن للمهارات أن تعلن اعتماديات (dependencies) على أدوات أو toolsets محدّدة، وهذا يحدّد ما إذا كانت المهارة تظهر في الـ system prompt لجلسة معيّنة أم لا.

الحقلالسلوك
requires_toolsetsتكون المهارة مخفيّة عندما يكون أي toolset من القائمة غير متاح
requires_toolsتكون المهارة مخفيّة عندما تكون أي أداة من القائمة غير متاحة
fallback_for_toolsetsتكون المهارة مخفيّة عندما يكون أي toolset من القائمة متاحًا
fallback_for_toolsتكون المهارة مخفيّة عندما تكون أي أداة من القائمة متاحة

حالة استخدام fallback_for_*: أنشئ مهارة تعمل كحل بديل عندما لا تكون أداة أساسية متاحة. على سبيل المثال، مهارة duckduckgo-search مع fallback_for_tools: [web_search] لا تظهر إلا عندما لا تكون أداة البحث في الويب (التي تتطلب مفتاح API) مضبوطة.

حالة استخدام requires_*: أنشئ مهارة لا معنى لها إلا مع وجود أدوات معيّنة. على سبيل المثال، مهارة سير عمل لاستخراج بيانات الويب (web scraping) مع requires_toolsets: [web] لن تُثقل الـ prompt عندما تكون أدوات الويب معطّلة.

متطلبات متغيرات البيئة

يمكن للمهارات أن تعلن متغيرات البيئة التي تحتاجها. عند تحميل مهارة عبر skill_view، تُسجَّل متغيراتها المطلوبة تلقائيًا لتمريرها (passthrough) إلى بيئات التنفيذ المعزولة (terminal، execute_code).

يدعم كل عنصر:

  • name (مطلوب) — اسم متغير البيئة
  • prompt (اختياري) — نص السؤال عند طلب القيمة من المستخدم
  • help (اختياري) — نص مساعدة أو رابط للحصول على القيمة
  • required_for (اختياري) — يصف الميزة التي تحتاج هذا المتغير

يمكن للمستخدمين أيضًا ضبط متغيرات التمرير يدويًا في config.yaml:

راجع skills/apple/ للاطلاع على أمثلة عن مهارات خاصة بـ macOS فقط.

الإعداد الآمن عند التحميل

استخدم required_environment_variables عندما تحتاج المهارة إلى مفتاح API أو رمز مصادقة (token). القيم المفقودة لا تُخفي المهارة عن الاكتشاف؛ بل يطلبها Hermes بأمان عند تحميل المهارة في CLI المحلي.

يمكن للمستخدم تخطّي الإعداد ومواصلة تحميل المهارة. لا يكشف Hermes أبدًا قيمة السرّ الفعلية للنموذج. تعرض جلسات الـ gateway والمراسلة إرشادات إعداد محلية بدلًا من جمع الأسرار ضمن المحادثة نفسها.

تمرير Sandbox

عند تحميل مهارتك، فإن أي متغيرات بيئة معلَنة ضمن required_environment_variables ومضبوطة فعليًا تُمرَّر تلقائيًا إلى بيئات execute_code وterminal المعزولة — بما فيها terminal backends البعيدة مثل Docker وModal. يمكن لسكربتات مهارتك الوصول إلى $TENOR_API_KEY (أو os.environ["TENOR_API_KEY"] في Python) دون أن يحتاج المستخدم إلى ضبط أي شيء إضافي. راجع تمرير متغيرات البيئة للتفاصيل.

يبقى prerequisites.env_vars القديم مدعومًا كاسم بديل متوافق مع الإصدارات السابقة.

إعدادات التهيئة (config.yaml)

يمكن للمهارات أن تعلن إعدادات غير سرّية تُخزَّن في config.yaml ضمن مساحة الاسم skills.config. وخلافًا لمتغيرات البيئة (وهي أسرار تُخزَّن في .env)، تُستخدم إعدادات التهيئة للمسارات والتفضيلات وقيم أخرى غير حسّاسة.

يدعم كل عنصر:

  • key (مطلوب) — المسار النقطي (dotpath) للإعداد (مثلًا myplugin.path)
  • description (مطلوب) — يشرح ما يتحكم فيه الإعداد
  • default (اختياري) — القيمة الافتراضية إذا لم يضبطها المستخدم
  • prompt (اختياري) — نص يُعرض أثناء hermes config migrate؛ ويرجع افتراضيًا إلى description

كيف تعمل الآلية:

  1. التخزين: تُكتب القيم في config.yaml ضمن skills.config.<key>:

  2. الاكتشاف: يقوم hermes config migrate بمسح كل المهارات المفعّلة، ويجد الإعدادات غير المضبوطة، ويطلبها من المستخدم. تظهر الإعدادات أيضًا في hermes config show تحت "Skill Settings".

  3. الحقن وقت التشغيل: عند تحميل مهارة، تُحلَّل قيم إعداداتها وتُضاف إلى رسالة المهارة:

    يرى الوكيل القيم المضبوطة دون الحاجة لقراءة config.yaml بنفسه.

  4. الإعداد اليدوي: يمكن للمستخدمين أيضًا ضبط القيم مباشرة:

متى تستخدم كلًا منهما

استخدم required_environment_variables لمفاتيح API والرموز (tokens) وغيرها من الأسرار (تُخزَّن في ~/.hermes/.env، ولا تُعرض أبدًا للنموذج). واستخدم config للمسارات والتفضيلات والإعدادات غير الحسّاسة (تُخزَّن في config.yaml، وتظهر في config show).

متطلبات ملفات بيانات الاعتماد (رموز OAuth وغيرها)

يمكن للمهارات التي تستخدم OAuth أو بيانات اعتماد قائمة على الملفات أن تعلن ملفات يجب تحميلها (mount) داخل بيئات sandbox البعيدة. وهذا مخصّص لبيانات الاعتماد المخزّنة كـملفات (وليس متغيرات بيئة) — وعادةً ما تكون ملفات رموز OAuth الناتجة عن سكربت إعداد.

يدعم كل عنصر:

  • path (مطلوب) — مسار الملف نسبةً إلى ~/.hermes/
  • description (اختياري) — يشرح ماهية الملف وكيفية إنشائه

عند التحميل، يتحقق Hermes من وجود هذه الملفات. الملفات المفقودة تُطلق setup_needed. أما الملفات الموجودة فتُعامَل تلقائيًا كالتالي:

  • تُحمَّل (mount) في حاويات Docker كـ bind mounts للقراءة فقط
  • تُزامَن في بيئات Modal (عند الإنشاء + قبل كل أمر، بحيث تعمل عملية OAuth حتى في منتصف الجلسة)
  • متاحة على terminal backend المحلي دون أي معالجة خاصة
متى تستخدم كلًا منهما

استخدم required_environment_variables لمفاتيح API والرموز (tokens) البسيطة (سلاسل نصية تُخزَّن في ~/.hermes/.env). واستخدم required_credential_files لملفات رموز OAuth، وأسرار العميل (client secrets)، وملفات JSON لحسابات الخدمة، والشهادات، أو أي بيانات اعتماد تكون على شكل ملف على القرص.

راجع skills/productivity/google-workspace/SKILL.md للاطلاع على مثال كامل يستخدم كلا الأسلوبين.

إرشادات المهارات

دون اعتماديات خارجية

فضّل استخدام مكتبة Python القياسية (stdlib) وcurl وأدوات Hermes الموجودة (web_extract، terminal، read_file). إذا احتجت اعتمادية، وثّق خطوات تثبيتها في المهارة.

الإفصاح التدريجي (Progressive Disclosure)

ضع سير العمل الأكثر شيوعًا أولًا. الحالات الاستثنائية والاستخدام المتقدّم يوضعان في الأسفل. هذا يبقي استهلاك الـ tokens منخفضًا في المهام الشائعة.

أدرِج سكربتات مساعدة

لتحليل XML/JSON أو المنطق المعقّد، أدرِج سكربتات مساعدة في scripts/ — لا تتوقّع من النموذج اللغوي كتابة محلّلات (parsers) بشكل مباشر (inline) في كل مرة.

تسليم الوسائط كمستندات ([[as_document]])

إذا كانت مهارتك تُنتج لقطة شاشة عالية الدقة، أو رسمًا بيانيًا، أو أي صورة يضرّها ضغط المعاينة الفاقد للجودة — أدرِج التوجيه الحرفي [[as_document]] في مكان ما من الرد (عادةً في السطر الأخير). يزيل الـ gateway هذا التوجيه ويسلّم كل مسار وسائط مستخرَج في ذلك الرد كمرفق ملف قابل للتنزيل بدلًا من فقاعة صورة مضمّنة. راجع مخرجات المهارة وتسليم الوسائط للاطلاع على التفاصيل الكاملة.

الإشارة إلى السكربتات المضمّنة من SKILL.md

عند تحميل مهارة، تعرض رسالة التفعيل دليل المهارة بمساره المطلق كـ [Skill directory: /abs/path]، كما تستبدل رمزين من القوالب في أي مكان من نص SKILL.md:

الرمزيُستبدَل بـ
${HERMES_SKILL_DIR}المسار المطلق لدليل المهارة
${HERMES_SESSION_ID}معرّف الجلسة النشطة (يبقى كما هو إن لم توجد جلسة)

وهكذا يمكن لملف SKILL.md أن يطلب من الوكيل تشغيل سكربت مضمّن مباشرة بـ:

يرى الوكيل المسار المطلق بعد الاستبدال ويستدعي أداة terminal بأمر جاهز للتنفيذ — دون أي حسابات مسارات، ودون استدعاء إضافي لـ skill_view. عطّل الاستبدال عالميًا عبر skills.template_vars: false في config.yaml.

مقتطفات shell مضمّنة (اختيارية بالتفعيل)

يمكن للمهارات أيضًا تضمين مقتطفات shell مضمّنة تُكتب كـ !`cmd` في نص SKILL.md. عند التفعيل، يُدرَج مخرج stdout لكل مقتطف داخل الرسالة قبل أن يقرأها الوكيل، بحيث يمكن للمهارات حقن سياق ديناميكي:

هذه الميزة معطّلة افتراضيًا — لأن أي مقتطف في SKILL.md يُنفَّذ على الجهاز المضيف دون موافقة، فلا تفعّلها إلا لمصادر مهارات تثق بها:

تُنفَّذ المقتطفات مع دليل المهارة كدليل عمل لها، ويُحدّ المخرج بـ 4000 حرف. تظهر الإخفاقات (انتهاء المهلة، الخروج بقيمة غير صفرية) كعلامة قصيرة [inline-shell error: ...] بدلًا من كسر المهارة بأكملها.

اختبرها

شغّل المهارة وتحقّق من أن الوكيل يتّبع التعليمات بشكل صحيح:

أين يجب أن تقيم المهارة؟

المهارات المضمّنة (في skills/) تُشحَن مع كل تثبيت لـ Hermes. يجب أن تكون مفيدة على نطاق واسع لمعظم المستخدمين:

  • التعامل مع المستندات، بحث الويب، سير عمل التطوير الشائعة، إدارة النظام
  • تُستخدَم بانتظام من قِبل شريحة واسعة من الأشخاص

إذا كانت مهارتك رسمية ومفيدة لكن غير ضرورية للجميع (مثل تكامل مع خدمة مدفوعة، أو اعتمادية ثقيلة)، ضعها في optional-skills/ — إذ تُشحَن مع المستودع، ويمكن اكتشافها عبر hermes skills browse (موسومة بـ "official")، وتُثبَّت بثقة مدمجة.

وإذا كانت مهارتك متخصّصة أو مقدَّمة من المجتمع أو محدودة الاستخدام، فإن Skills Hub يناسبها أكثر — ارفعها إلى سجل (registry) وشاركها عبر hermes skills install.

Blueprints: مهارات تُعدّ أيضًا أتمتة

Blueprint هو مهارة عادية تعلن إضافةً إلى ذلك جدولة زمنية في الـ frontmatter الخاص بها. أضف كتلة metadata.hermes.blueprint فتتحوّل المهارة إلى أتمتة قابلة للمشاركة والتشغيل:

بما أن الـ blueprint هو مهارة، فإنه يمرّ عبر سلسلة معالجة المهارات (pipeline) كاملةً دون تغيير — البحث، والفحص، والتثبيت، وفحص الأمان، وتتبّع المصدر (provenance)، وtaps، والفهرس المركزي، وكذلك hermes skills publish للمشاركة. لا شيء جديد لتعلّمه.

تثبيت blueprint. عند تثبيت مهارة تحمل كتلة blueprint:، يسجّلها Hermes كـمهمة cron مقترحة بدلًا من جدولتها مباشرة. الجدولة اختيارية بالانضمام (opt-in) — التثبيت لا يُنشئ أبدًا مهمة متكررة دون علمك. يمكنك مراجعتها وقبولها عبر /suggestions:

الـ blueprints هي أحد مصادر واجهة المهام المجدولة المقترحة (Suggested Cron Jobs) الموحّدة — المكان نفسه الذي تظهر فيه الأتمتة الأولية المُنسَّقة، وكذلك (لاحقًا) اقتراحات أنماط الاستخدام والتكاملات. راجع المهام المجدولة المقترحة أدناه.

مشاركة أتمتة أنشأتها. يمكن تصدير blueprint حُمِّل عبر مهمة cron (hermes cron create --skill <name> ...) إلى ملف SKILL.md ونشره كأي مهارة أخرى، بحيث تتحوّل أتمتة ضبطتها لنفسك إلى تثبيت بأمر واحد لشخص آخر.

لا تضيف طبقة الـ blueprint أي نوع كائن جديد، أو مخزن، أو وسيلة نقل — فالـ blueprint هو مهارة، والجدولة هي مهمة cron، والمشاركة هي مسار النشر/الـ tap/الفهرس الموجود أصلًا.

المهام المجدولة المقترحة

يستطيع Hermes اقتراح أتمتة والسماح لك بقبولها بنقرة واحدة، بدلًا من إجبارك على تجميع مهام cron يدويًا. يمرّ كل اقتراح عبر واجهة واحدة — الأمر /suggestions — بصرف النظر عن مصدره:

المصدرالمُحفِّز
catalogأتمتة أولية مُنسَّقة (/suggestions catalog) — الملخّص اليومي، مراقبة البريد المهم، المراجعة الأسبوعية، تذكير بداية يوم العمل
blueprintثبّتّ مهارة تحمل كتلة blueprint:
usageلاحظت المراجعة الخلفية طلبًا متكررًا يمكن أن تخدمه جدولة
integrationربطت حسابًا (Gmail، GitHub، ...) وتُعرَض الأتمتة الواضحة تلقائيًا

قبول اقتراح يستدعي الدالة cron.jobs.create_job نفسها التي تستخدمها أداة cronjob — لا يوجد محرّك مهام ثانٍ. الاقتراحات لا تُنشئ مهامًا تلقائيًا أبدًا؛ القبول دائمًا صريح. تُقفل الاقتراحات المرفوضة عبر مفتاح ثابت بحيث لا يُعاد عرض الاقتراح نفسه مجددًا. قائمة الانتظار محدودة بحد أقصى بحيث لا تتحوّل أبدًا إلى جدار من التنبيهات المزعجة.

مدخل الكتالوج مراقبة البريد المهم هو نمط الاستطلاع → التصنيف → العرض: يُقيّم عناصر البريد الوارد بنموذج تصنيف رخيص (auxiliary.monitor في config.yaml) ويسلّم فقط ما يتجاوز عتبة إلحاح معيّنة، ويبقى صامتًا فيما عدا ذلك.

فحص الأمان

تمرّ جميع المهارات المثبَّتة من الـ hub بفاحص أمان يتحقق من:

  • أنماط تسريب البيانات (data exfiltration)
  • محاولات حقن الـ prompt (prompt injection)
  • الأوامر المدمِّرة
  • حقن shell

مستويات الثقة:

  • builtin — تُشحَن مع Hermes (موثوقة دائمًا)
  • official — من optional-skills/ في المستودع (ثقة مدمجة، دون تحذير من طرف ثالث)
  • trusted — من openai/skills، anthropics/skills، huggingface/skills
  • community — يمكن تجاوز النتائج غير الخطيرة بـ --force؛ أما أحكام dangerous فتبقى محظورة

أصبح بإمكان Hermes الآن استيعاب مهارات من أطراف ثالثة من عدة نماذج اكتشاف خارجية:

  • معرّفات GitHub المباشرة (مثلًا openai/skills/k8s)
  • معرّفات skills.sh (مثلًا skills-sh/vercel-labs/json-render/json-render-react)
  • نقاط النهاية المعروفة (well-known endpoints) المُقدَّمة من /.well-known/skills/index.json

إذا أردت أن تكون مهاراتك قابلة للاكتشاف دون مُثبِّت مخصّص لـ GitHub، ففكّر في تقديمها من نقطة نهاية معروفة (well-known endpoint) إضافةً إلى نشرها في مستودع أو سوق (marketplace).

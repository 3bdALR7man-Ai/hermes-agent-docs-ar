التحكم في الوصول إلى Slash Commands

افتراضيًا، يستطيع كل مستخدم مسموح له تشغيل جميع الـ slash commands. لتقسيم قائمة السماح (allowlist) إلى مسؤولين (admins) (وصول كامل إلى الـ slash commands) ومستخدمين عاديين (الأوامر التي تفعّلها لهم صراحةً فقط)، أضف allow_admin_from و user_allowed_commands إلى كتلة extra الخاصة بالمنصة:

السلوك:

  • يستطيع المستخدم المُدرج في allow_admin_from ضمن نطاق معيّن (الرسائل المباشرة أو المجموعة) تشغيل كل slash command مسجّل — الأوامر المدمجة والأوامر التي تسجّلها الإضافات أيضًا — عبر السجل الحي (live registry).
  • المستخدم الموجود في allow_from لكنه غير موجود في allow_admin_from لا يستطيع إلا تشغيل الأوامر المُدرجة في user_allowed_commands، إضافةً إلى الحد الأدنى المسموح به دائمًا: /help و /whoami.
  • لا تتأثر المحادثة العادية (الرسائل التي ليست slash commands). يظل بإمكان المستخدمين غير المسؤولين التحدث مع الوكيل بشكل طبيعي، لكنهم لا يستطيعون تشغيل أوامر عشوائية.
  • التوافق مع الإصدارات السابقة: إذا لم يُضبط allow_admin_from لنطاق ما، يُعطَّل تقييد الـ slash commands لذلك النطاق. وتستمر عمليات التثبيت الحالية في العمل دون أي تغييرات.
  • كونك مسؤولًا في الرسائل المباشرة لا يعني أنك مسؤول في المجموعات. لكل نطاق قائمة مسؤولين خاصة به.
  • إذا ضُبط group_allow_admin_from وحده، يبقى نطاق الرسائل المباشرة في الوضع غير المقيّد (وضع التوافق مع الإصدارات السابقة).

استخدم /whoami لمعرفة النطاق النشط ومستواك (admin / user / unrestricted) والـ slash commands التي يمكنك تشغيلها.

أداة اختيار النموذج التفاعلية

عند إرسال /model دون وسائط في محادثة Telegram، يعرض Hermes لوحة مفاتيح مضمّنة (inline keyboard) تفاعلية لتبديل النماذج:

  1. اختيار المزوّد — أزرار تعرض كل مزوّد متاح مع عدد نماذجه (مثل "OpenAI (15)"، و"✓ Anthropic (12)" للمزوّد الحالي).
  2. اختيار النموذج — قائمة نماذج مقسّمة إلى صفحات مع أزرار التنقل Prev/Next، وزر Back للعودة إلى المزوّدين، وزر Cancel.

يُعرض النموذج والمزوّد الحاليان في الأعلى. ويجري كل التنقل بتعديل الرسالة نفسها في مكانها (دون إغراق المحادثة برسائل إضافية).

نصيحة

إذا كنت تعرف اسم النموذج بالضبط، فاكتب /model <name> مباشرةً لتجاوز أداة الاختيار. ويمكنك أيضًا كتابة /model <name> --global للاحتفاظ بالتغيير عبر الجلسات.

عناوين IP الاحتياطية عبر DNS-over-HTTPS

في بعض الشبكات المقيّدة، قد يُترجَم api.telegram.org إلى عنوان IP يتعذّر الوصول إليه. يتضمن محوّل Telegram (Telegram adapter) آلية عناوين IP احتياطية (fallback IP) تعيد محاولة الاتصال بشفافية عبر عناوين IP بديلة مع الحفاظ على اسم مضيف TLS الصحيح و SNI.

آلية العمل

  1. إذا ضُبط TELEGRAM_FALLBACK_IPS، تُستخدم عناوين IP تلك مباشرةً.
  2. وإلا، يستعلم المحوّل تلقائيًا من Google DNS وCloudflare DNS عبر DNS-over-HTTPS (DoH) لاكتشاف عناوين IP بديلة لـ api.telegram.org.
  3. تُجرَّب عناوين IPv4 المعروفة لـ Telegram API قبل اسم المضيف api.telegram.org ثنائي المكدّس (dual-stack). فمسار IPv6 المحجوب (blackholed) قد يبقى عالقًا في connect() دون أن يُصدر خطأ، وهو ما كان يُجمّد حلقة الأحداث (event loop) فلا تنقضي مهلة التهيئة البالغة 30 ثانية أبدًا.
  4. إذا كان DoH محجوبًا أيضًا أو انتهت مهلته، تُستخدم قائمة بذرية ثابتة من عناوين IPv4 (149.154.166.110، 149.154.167.220) بوصفها قائمة IPv4 ذات الأولوية. ويبقى اسم المضيف الملاذ الأخير.
  5. بمجرد نجاح أحد المسارات، يصبح "ثابتًا" (sticky) — أي تستخدمه الطلبات اللاحقة مباشرةً. ويُحتفَظ باسم المضيف ملاذًا أخيرًا للشبكات التي تعتمد IPv6 فقط.

Prompts لكل قناة

خصّص system prompts مؤقتة لمجموعات Telegram أو موضوعات منتديات (forum topics) محددة. يُحقن الـ prompt وقت التشغيل في كل دور — ولا يُحفظ أبدًا في سجل المحادثة — لذا تسري التغييرات فورًا.

المفاتيح هي معرّفات المحادثات (للمجموعات والمجموعات الفائقة) أو معرّفات موضوعات المنتدى. وفي مجموعات المنتديات، تتقدّم الـ prompts على مستوى الموضوع على الـ prompt على مستوى المجموعة:

  • رسالة في الموضوع 42 داخل المجموعة -1001234567890 → تستخدم الـ prompt الخاص بالموضوع 42
  • رسالة في الموضوع 99 (دون إدخال صريح) → تعود إلى الـ prompt الخاص بالمجموعة -1001234567890
  • رسالة في مجموعة بلا إدخال → لا يُطبَّق أي prompt للقناة

تُحوَّل مفاتيح YAML الرقمية تلقائيًا إلى سلاسل نصية.

الأسئلة التفاعلية (clarify)

عندما يستدعي الوكيل أداة clarify — ليسألك عن النهج الذي تفضّله، أو ليحصل على ملاحظاتك بعد إنجاز مهمة، أو ليتحقق منك قبل اتخاذ قرار غير بسيط — يعرض Telegram السؤال مع أزرار لوحة مفاتيح مضمّنة (inline keyboard):

❓ Which framework should I use for the dashboard?

[1. Next.js] [2. Remix] [3. Astro] [✏️ Other (type answer)]

انقر على زر للإجابة، أو انقر على Other لكتابة رد حر (تصبح الرسالة التالية التي ترسلها هي الإجابة). أما استدعاءات clarify المفتوحة (بلا خيارات محددة مسبقًا) فتتجاوز الأزرار وتلتقط رسالتك التالية فحسب.

اضبط مهلة الرد عبر agent.clarify_timeout في ~/.hermes/config.yaml (القيمة الافتراضية 600 ثانية). وإذا لم تردّ خلال المهلة، يتحرّر الوكيل برسالة تنبيهية (sentinel) ويتكيّف مع الموقف بدلًا من البقاء عالقًا.

تعديل رسائل الحالة في مكانها

يوجّه محوّل Telegram استدعاءات الحالة المتكررة للوكيل (مثل "Compressing context…" و"Calling tool…") عبر send_or_update_status()، التي تحتفظ بذاكرة تخزين مؤقت {(chat_id, status_key) → message_id} وتعدّل الفقاعة الموجودة عند الإصدارات اللاحقة بدلًا من إلحاق فقاعة جديدة في كل مرة. تحصل كل قيمة status_key مختلفة على رسالتها الخاصة، ولا تتداخل المحادثات المختلفة أبدًا. وإذا فشل التعديل (مثلًا إذا حذف المستخدم الرسالة، أو كانت أقدم مما يسمح به Telegram للتعديل)، يُحذف الإدخال من ذاكرة التخزين المؤقت وينشر الإصدار التالي رسالة جديدة ويعيد تخزين معرّفها. لا يلزم أي إعداد — فهذا هو السلوك الافتراضي في Telegram. أما المحوّلات الأخرى التي لا تطبّق send_or_update_status فتعود إلى send() العادية دون تغيير.

تثبيت رسالة المستخدم الواردة أثناء دور الوكيل

عندما يرسل مستخدم رسالة تُطلق دورًا للوكيل، يثبّت محوّل Telegram تلك الرسالة الواردة طوال مدة الدور، ثم يلغي تثبيتها عند اكتمال الرد — وهو مؤشر مرئي خفيف على أن البوت يعمل فعليًا على الرسالة ولا يتجاهلها. يستخدم التثبيت disable_notification=true لتجنّب التنبيهات الإضافية. لا يلزم أي إعداد.

نوعان من خوادم MCP

خوادم Stdio

تعمل خوادم Stdio كعمليات فرعية محلية وتتواصل عبر stdin/stdout.

استخدم خوادم stdio عندما:

  • يكون الخادم مثبتًا محليًا
  • تريد وصولًا منخفض زمن الاستجابة إلى الموارد المحلية
  • تتبع وثائق خادم MCP تعرض command, args، و env

خوادم HTTP

خوادم HTTP MCP هي endpoints بعيدة يتصل بها Hermes مباشرةً.

استخدم خوادم HTTP عندما:

  • يكون خادم MCP مستضافًا في مكان آخر
  • تتيح مؤسستك MCP endpoints داخلية
  • لا تريد أن ينشئ Hermes عملية فرعية محلية لذلك التكامل

تحترم خوادم HTTP و SSE إعدادات proxy القياسية: HTTPS_PROXY / HTTP_PROXY / ALL_PROXY (يُطبَّع الاسم البديل socks:// إلى socks5://)، ثم proxy نظام التشغيل (سجل Windows، وإعدادات نظام macOS)، مع اتصال مضيفي NO_PROXY مباشرةً — بما في ذلك نطاقات CIDR وأنماط *.example.com .

خوادم HTTP الموثّقة بـ OAuth

تتطلب معظم خوادم MCP المستضافة (Cloudflare و Linear و Sentry و Atlassian و Asana و Figma و Stripe وغيرها) OAuth 2.1 بدل bearer token ثابت. اضبط auth: oauth ويتولى Hermes الاكتشاف، وتعريف العميل، و PKCE، وتبادل token وتحديثه، والمصادقة المعززة عبر MCP Python SDK.

يعرّف Hermes نفسه باستخدام Client ID Metadata Document على الخوادم التي تدعمها، ويرجع إلى Dynamic Client Registration على التي لا تدعمها. وكلاهما تلقائي؛ ولا تحتاج إلى ضبط شيء.

MCP البعيد في Figma

يسمح endpoint المستضاف لـ Figma (https://mcp.figma.com/mcp) بالتسجيل الديناميكي للعميل استنادًا إلى المطابقة الدقيقة client_name — إذ يؤدي "Hermes Agent" المجرّد إلى 403، بينما ينجح "Claude Code" و "Codex" . ويضبط Hermes تلقائيًا oauth.client_name: "Claude Code" لـ mcp.figma.com كي يعمل التثبيت/تسجيل الدخول دون حيلة خاصة:

أو: hermes mcp install figma، ثم hermes mcp login figma.

عند أول اتصال، يطبع Hermes URL للتفويض، ويفتح متصفحك إن أمكن، وينتظر OAuth callback على منفذ loopback محلي. وتُخزَّن tokens مؤقتًا عند ~/.hermes/mcp-tokens/<server>.json بصلاحيات 0o600؛ وتعيد عمليات التشغيل اللاحقة استخدامها بصمت حتى يفشل التحديث.

ترتبط refresh tokens بخادم التفويض الذي منحها: يسجّل Hermes الـ issuer المكتشَف إلى جانب tokens المخزّنة، وإذا تغير خادم التفويض الذي يعلنه أحد الخوادم (ترحيل الخادم، أو تعديل البيانات الوصفية، أو اختطافه)، يُسقَط refresh token المخزّن بدل إرساله إلى الـ issuer الجديد. ويواصل access token الحالي العمل حتى تنتهي صلاحيته، ثم تتم إعادة تفويض عادية لدى الـ issuer الجديد.

تُفحَص إعادة التوجيه من خادم التفويض وفق RFC 9207: عندما تعلن بيانات الخادم الوصفية authorization_response_iss_parameter_supported، تُرفض إعادة توجيه دون iss مطابق. ويعلن خادم تفويض Figma (https://api.figma.com) ذلك الدعم ثم يحذف iss؛ فيملأ Hermes القيمة المفقودة من الـ issuer المكتشَف لهذا الـ issuer وحده ويسجّل تحذيرًا، كي يكتمل hermes mcp login figma . وتظل قيمة iss الموجودة لكن المختلفة مرفوضة، ولا يحصل أي خادم آخر على الاستثناء.

يجب أن تسمّي وثيقة البيانات الوصفية لخادم التفويض الخادم الذي أعلنه المورد (RFC 8414 §3.3)؛ وتُرفض وثيقة لخادم مختلف قبل أي تسجيل أو دخول. وتُقبل صيغة واحدة دون تطابق كامل: خادم معلَن بمسار (https://host/path) تسمّي وثيقته، المجلوبة من https://host/.well-known/oauth-authorization-server/path، الأصل https://host بوصفه issuer — وينشر موصل MCP في Strava هذا الزوج تحديدًا. وحده مشغّل الأصل يتحكم في ذلك الموضع well-known، لذا تُعامل الوثيقة كوثيقة الخادم المعلَن نفسه؛ وتظل الوثيقة التي تسمّي أصلًا آخر أو مسارًا آخر، أو لا يُوصل إليها إلا عبر إعادة توجيه أو موضع احتياطي، تفشل بـ Authorization server metadata issuer mismatch.

خوادم تستضيفها Google (Gmail و Calendar). لا تصدر Google refresh token إلا حين يحمل طلب التفويض access_type=offline، وهو ما لا يعلنه اكتشاف MCP أبدًا. ويضيفه Hermes (مع prompt=consent، كي يُمنح آخر عند تسجيل الدخول مجددًا) كلما كان خادم التفويض المكتشَف هو accounts.google.com، كي يستمر الاتصال عبر إعادة التشغيل ويعمل من hermes gateway. ولا تُمس طلبات issuers الآخرين.

المضيفات البعيدة / دون واجهة. عندما يعمل Hermes على جهاز مختلف عن متصفحك، لا يستطيع loopback callback الوصول إلى حاسوبك المحمول. طرق إكمال التدفق:

  • Hermes Desktop (تلقائي): عند تسجيل الدخول عبر OAuth من واجهة إعداد MCP في تطبيق Desktop إلى backend بعيد، يستضيف Desktop مستمع callback على جهازك ويمرّر التفويض إلى الـ gateway تلقائيًا — دون نفق أو لصق أو proxy. ويتطلب تحديث تطبيق Desktop والـ backend كليهما.
  • إعادة اللصق (دون إعداد): في طرفية تفاعلية يطبع Hermes "Or paste the redirect URL here…" إلى جانب URL التفويض. افتح URL في متصفحك، ووافق، وانسخ URL الكامل الذي يصل إليه المتصفح (ستعرض إعادة التوجيه خطأ اتصال — وهذا متوقع)، ثم الصقه عند الـ prompt. وتعمل أيضًا سلاسل الاستعلام المجرّدة ?code=…&state=… .
  • تسجيل الدخول بـ device-code (دون callback إطلاقًا): إذا أعلن خادم التفويض للخادم endpoint لتفويض الجهاز، فنفّذ hermes mcp login <server> --flow device على الجهاز الذي يشغّل Hermes. ويطبع URL للتحقق ورمزًا قصيرًا؛ افتح URL على أي جهاز، وأدخل الرمز، ويستطلع Hermes الموافقة. ولا يُفتح متصفح على المضيف ولا يلزم مستمع callback. اضبط oauth.flow: device للخادم ليستخدمه login و reauth افتراضيًا. التفاصيل: تسجيل الدخول بـ device-code.
  • تمرير منفذ SSH: ssh -N -L <port>:127.0.0.1:<port> user@host في طرفية منفصلة، ثم دع إعادة التوجيه تجري بصورة طبيعية.
  • callback عبر proxy (redirect_uri): عندما يمرّر HTTPS endpoint عام إلى المضيف (مثل Tailscale Funnel أو reverse proxy يشير إلى منفذ callback)، اضبط oauth.redirect_uri وستصل إعادة التوجيه من المتصفح إلى Hermes تلقائيًا — دون نفق أو لصق:

للـ gateways التي تعمل تمامًا دون واجهة (بوت مراسلة، بلا طرفية تفاعلية مطلقًا)، فإن المهارة الاختيارية mcp-oauth-remote-gateway ترشد الوكيل لإكمال التدفق يدويًا وكتابة tokens حيث يتوقعها Hermes.

مأزق — يرفض WAF عناوين إعادة توجيه 127.0.0.1 . تضع قلة من المزوّدين خادم التفويض خلف WAF يعيد 403 لكل طلب تفويض تحوي سلسلة استعلامه القيمة الحرفية 127.0.0.1 (AWS API Gateway في Reclaim.ai مثال معروف — تعيد كل محاولة {"message":"Forbidden"} قبل الوصول إلى تطبيق OAuth). اضبط oauth.redirect_host: localhost لاستخدام http://localhost:<port>/callback بدلًا منه؛ ويظل مستمع callback مربوطًا بـ 127.0.0.1 في كلتا الحالتين.

راجع OAuth عبر SSH / الأجهزة البعيدة للشرح الكامل، بما فيه خوادم دون DCR (مثل Slack)، و client_id/client_secretالمسجّل مسبقًا، وتخصيص النطاق، وإعادة المصادقة عبر hermes mcp login <server>.

مأزق — مزوّدون لا يدعمون التسجيل التلقائي (Google Drive و Atlassian). ترفض بعض الخوادم خطوة التسجيل الديناميكي للعميل (RFC 7591) التي يعتمد عليها auth: oauth المجرّد — إذ يعيد خادم Drive الرسمي من Google (https://drivemcp.googleapis.com/mcp/v1) 400 Bad Request، لذا لا يُنشأ عميل OAuth ولا يُكتسَب token. والعَرَض خفي: فهذه الخوادم تقدم أيضًا tools/list دون مصادقة، لذا يستطيع hermes mcp login عرض الأدوات ويبدو أنه نجح، لكن تنتهي مهلة كل استدعاء أداة حقيقي لاحقًا. hermes mcp login يكتشف هذا الآن (بفحص أن token وصل فعليًا إلى القرص) ويطلب منك تقديم عميل OAuth الخاص بك. أنشئ واحدًا في لوحة المزوّد وأضفه إلى الإعدادات:

ثم نفّذ hermes mcp login googledrive — مع العميل المسجّل مسبقًا، يتجاوز Hermes التسجيل وينفّذ تدفق تفويض المتصفح المعتاد.

مأزق — سباق إعادة تحميل الإعدادات تلقائيًا. عندما تعدّل ~/.hermes/config.yaml من داخل جلسة Hermes جارية، يعيد CLI تحميل اتصالات MCP تلقائيًا بمهلة 30 ثانية. وهذا لا يكفي لتدفق OAuth تفاعلي. أضف العنصر، ثم نفّذ hermes mcp login <server> من طرفية جديدة — إذ ينتظر كامل 5 دقائق لتكمل المصادقة.

هل تحتاج إلى أكثر من 5 دقائق للموافقة؟ اضبط oauth.timeout في عنصر الخادم (بالثواني). hermes mcp loginولوحة التحكم وإعادة المصادقة في Desktop كلها تنتظر oauth.timeout + 15 ثانية (أو connect_timeoutللعنصر، أيهما أطول)؛ ويبلغ تسجيل الدخول الذي تنتهي مهلته رغم ذلك برسالة Connecting to MCP server '<name>' timed out after Ns تذكر الخيارين بدل سطر إخفاق فارغ.

mTLS / شهادات العميل

تُدعم خوادم HTTP MCP البعيدة التي تتطلب TLS متبادلًا (مصادقة بشهادة العميل) عبر client_cert / client_key. ويمرّر Hermes الشهادة المحددة إلى عميل HTTP الأساسي لمصافحة TLS.

client_cert يقبل ثلاث صيغ:

  • مسار PEM مدمج واحد — ملف واحد يحمل الشهادة والمفتاح الخاص معًا:
  • زوج [cert, key] ثنائي العناصر — الشهادة والمفتاح في ملفين منفصلين (مكافئ لضبط client_cert + client_key):
  • ثلاثية [cert, key, password] ثلاثي العناصر — عندما يكون المفتاح الخاص مشفّرًا، يكون العنصر الثالث عبارة مرور المفتاح:

يمكنك أيضًا إبقاء الشهادة والمفتاح منفصلين تمامًا عبر client_cert (PEM مدمج) مع client_keyصريح. وتدعم المسارات توسعة ~ ؛ ويؤدي الملف المفقود إلى خطأ واضح خاص بالخادم بدل إخفاق مبهم لمصافحة TLS.

ترويسة هوية لكل مستخدم

يمكن إرسال ترويسة هوية في كل طلب إلى خوادم HTTP/SSE MCP البعيدة التي تربط سلوكها بهوية المستدعي (حدود معدل لكل مستخدم، ومسارات تدقيق، وتوجيه متعدد المستأجرين) عبر identity_header:

  • value_from: static يرسل القيمة الحرفية value من config.yaml.
  • value_from: profile يرسل اسم Hermes profile النشط، المحدد مرة عند الاتصال — وهو مفيد حين تتواصل عدة profiles على جهاز واحد مع الخادم نفسه ويحتاج إلى تمييزها.

يأخذ العنصر الصريح في ربط headers للخادم بالاسم نفسه (مهما كانت حالة الأحرف) الأولوية دائمًا؛ ولا تتجاوز ترويسة الهوية إعدادات ترويساتك الخاصة مطلقًا. ويُحذَّر من كتل identity_header غير الصالحة وتُتجاهَل — ولا تحجب اتصال الخادم أبدًا. وعلى خوادم stdio يُتجاهَل المفتاح مع تحذير (لا توجد ترويسات لنقل stdio).

تنقية نتائج الأدوات و _meta

يُطبَّق سلوكان على كل نتيجة لأداة MCP قبل أن يراها النموذج:

  • تُزال محارف Unicode TAG غير المرئية. المحارف الواقعة في النطاق U+E0000–U+E007F لا تظهر إطلاقًا في الطرفيات وواجهات المحادثة، لكنها مرئية بالكامل للنموذج — وهي قناة تهريب كلاسيكية لحقن الـ prompt (prompt injection) يستغلها خادم خبيث أو مُخترَق. يزيلها Hermes من نتائج الأدوات، ومحتوى الموارد، وأوصاف الأدوات. أما تسلسلات وسوم الإيموجي المشروعة (مثل أعلام المناطق 🏴󠁧󠁢󠁳󠁣󠁴󠁿) فتُحفظ كما هي.
  • تُعرض بيانات _meta الخاصة بالمورِّدين؛ أما المفاتيح المحجوزة للبروتوكول فلا. عندما يُرفق خادم خريطة _meta بنتيجة أداة (بمساحات أسماء خاصة بالمورِّدين مثل com.example/handoff)، يمرّرها Hermes إلى النموذج إلى جانب محتوى النتيجة. وتُحذف المفاتيح الواقعة تحت البادئات المحجوزة للبروتوكول — أي تسمية modelcontextprotocol أو mcp متبوعة بتسمية أخرى، مثل modelcontextprotocol.io/... أو tools.mcp.com/... — بما يتوافق مع قواعد أسماء المفاتيح في مواصفة MCP. وإذا لم يتبقَّ شيء موجَّه إلى النموذج، يُحذف الحقل _meta كليًا.

نتائج الصور

تُحفَظ كتلة ImageContent (لقطة شاشة، أو مخطط معروض، أو التقاط صفحة) في تخزين صور Hermes المؤقت، ويُبلَّغ عن مسارها في النتيجة بصيغة MEDIA:/path/to/image.png، كي تطلب الملف على أي واجهة تدعم المرفقات. وعندما يستطيع النموذج الرئيسي رؤية الصور داخل نتائج الأدوات، تُرفَق الصورة نفسها بالنتيجة أيضًا، فيقرأ النموذج البكسلات مباشرةً. وتتبع نتائج MCP القاعدة نفسها التي تتبعها vision_analyze: agent.image_input_mode؛ وتنطبق auxiliary.vision الصريحة وقدرة النموذج على الرؤية جميعًا (راجع الرؤية (Vision)). وتُخفَّض أحجام الصور المرفقة إلى vision.embed_target_bytes (حتى 4 لكل نتيجة) لأنها تُرسَل مجددًا في كل دور لاحق. ولا تحصل النماذج النصية وحدها إلا على المسار.

أدوات MCP المساعدة

عندما يكون ذلك مدعومًا، يسجّل Hermes أيضًا أدوات مساعدة حول موارد MCP والـ prompts:

  • list_resources
  • read_resource
  • list_prompts
  • get_prompt

تُسجَّل هذه الأدوات لكل خادم بنمط البادئة نفسه، على سبيل المثال:

  • mcp_github_list_resources
  • mcp_github_get_prompt

مهم

أصبحت هذه الأدوات المساعدة الآن تراعي القدرات المتاحة:

  • لا يسجّل Hermes أدوات الموارد المساعدة إلا إذا كانت جلسة MCP تدعم فعلًا عمليات الموارد
  • لا يسجّل Hermes أدوات الـ prompts المساعدة إلا إذا كانت جلسة MCP تدعم فعلًا عمليات الـ prompts

لذا فإن الخادم الذي يوفّر أدوات قابلة للاستدعاء دون موارد/prompts لن يحصل على تلك الأغلفة الإضافية.

وضع Browser Use (الافتراضي)

يستخدم وضع Browser Use أداة Browser Use CLI 3.0 بدلًا من أدوات المتصفح المدمجة. يكتب الوكيل كود Python وينفّذه في المتصفح للنقر والكتابة والسحب واستخراج البيانات والتفاعل مع صفحات الويب.

هذا هو وضع المتصفح الافتراضي: عندما لا يكون browser.backend مضبوطًا وتكون أداة browser-use CLI قابلة للتشغيل (مثبّتة، أو متاحة عبر uvx)، يحصل الوكيل على أداة واحدة هي browser_exec. وإذا تعذّر تشغيل CLI، يرجع Hermes تلقائيًا إلى أدوات المتصفح المدمجة.

هذا الوضع مشغّل (driver) يتكامل مع backend المتصفح الذي أعددته: فهو يقود متصفح Chromium الـ headless الخاص بـ Hermes، أو متصفحًا سحابيًا عبر اشتراك Nous، أو Browserbase، أو Firecrawl، أو متصفحات Browser Use السحابية — أيًّا كان مصدر المتصفح المختار في hermes tools → Browser Automation. الاستثناء الوحيد هو Camofox، الذي لا يملك CDP endpoint يمكن للـ harness الاتصال به؛ لذا تحتفظ إعدادات Camofox تلقائيًا بأدوات المتصفح المدمجة.

يستخدم التصفح المحلي Chromium المضمّن، لا متصفح Chrome الخاص بك. عند عدم إعداد مزوّد سحابي أو endpoint عبر /browser connect، يُطلق Hermes نسخة Chromium نفسها التي تستخدمها الأدوات المدمجة (المثبّتة عبر hermes tools → Browser Automation، والمُدارة عبر agent-browser) ويوجّه Browser Use CLI إليها. لا يُمَسّ متصفح Chrome المثبّت لديك أبدًا، لذا لا يوجد مفتاح تصحيح عن بُعد في chrome://inspect تحتاج إلى تفعيله، ولا نافذة منبثقة "Allow remote debugging?" — كما يعمل على المضيفات عديمة الواجهة (headless) التي لا تحتوي على Chrome إطلاقًا. يتشارك المتصفح دورة حياة الأدوات المدمجة: فهو يُغلق بعد browser.inactivity_timeout، وعند الخروج، وبواسطة عملية تنظيف العمليات اليتيمة. لقيادة متصفح سجّلت الدخول فيه، استخدم /browser connect أو مفتاح الـ profile الحقيقي.

الجلسات المتزامنة: تقبل browser_exec الوسيط session=<name> الذي يعزل عمل المتصفح حسب الاسم على كل backend. يحصل كل اسم على daemon خاص به للـ harness (مع IPC socket وسجل وحالة خاصة به) وعلى متصفح خاص به (نسخة Chromium مضمّنة منفصلة محليًا، ومتصفح سحابي منفصل على الـ backends السحابية) — لذا لم تعد الـ subagents المتوازية أو المحادثات المتزامنة تتصادم على اتصال مشترك واحد. يؤدي حذف session إلى استخدام الـ daemon الافتراضي المشترك، وهو مناسب للتصفح بمهمة واحدة في كل مرة.

لإلغاء هذا الوضع وفرض استخدام أدوات المتصفح المدمجة، استخدم /browser use off، أو:

(تبقى backend: "browser-use" صالحة لفرض الوضع صراحةً.)

ملاحظة

نظرًا لأن وضع Browser Use ينفّذ كود Python يكتبه النموذج على جهازك، فإن أداة browser_exec لا تُتاح إلا للجلسات التي تملك أيضًا صلاحية الوصول إلى الطرفية. أما المنصات المُعدّة دون toolset الطرفية (مثل واجهة مراسلة مقيّدة) فتحتفظ بأدوات المتصفح الافتراضية بدلًا من ذلك.

التوجيه الهجين: السحابة لعناوين URL العامة، والمتصفح المحلي لـ LAN/localhost

عند إعداد مزوّد سحابي، يُطلق Hermes تلقائيًا متصفح Chromium محليًا مساعدًا (sidecar) لعناوين URL التي تُحلّ إلى عنوان خاص/loopback/LAN (localhost و 127.0.0.1 و 192.168.x.x و 10.x.x.x و 172.16-31.x.x و *.local و *.lan و *.internal، و IPv6 loopback ::1، و link-local 169.254.x.x). أما عناوين URL العامة فتستمر في استخدام المزوّد السحابي في المحادثة نفسها.

يحلّ هذا سير العمل الشائع "أطوّر محليًا لكنني أستخدم Browserbase" — إذ يستطيع الوكيل التقاط لقطة شاشة للوحة التحكم لديك على http://localhost:3000 وكذلك استخراج بيانات https://github.com دون أن تبدّل المزوّدين أو تعطّل حماية SSRF. ولا يرى المزوّد السحابي عنوان URL الخاص أبدًا.

هذه الميزة مفعّلة افتراضيًا. لتعطيلها (فتذهب جميع عناوين URL إلى المزوّد السحابي المُعدّ، كما في السابق):

عند تعطيل التوجيه التلقائي، تُرفض عناوين URL الخاصة مع الرسالة "Blocked: URL targets a private or internal address" ما لم تضبط أيضًا browser.allow_private_urls: true (الذي يسمح للمزوّد السحابي بمحاولة الوصول إليها — وهو ما لن ينجح عادةً لأن Browserbase وأمثاله لا يستطيعون الوصول إلى شبكة LAN لديك).

المتطلبات: يستخدم الـ sidecar المحلي أداة agent-browser CLI نفسها التي يستخدمها الوضع المحلي الخالص، لذا تحتاج إلى تثبيتها (يثبّتها hermes setup tools → Browser Automation تلقائيًا). ولا تزال عمليات إعادة التوجيه بعد التنقل من عنوان URL عام إلى عنوان خاص محظورة (فلا يمكنك استخدام حيلة إعادة التوجيه إلى عنوان داخلي للوصول إلى شبكة LAN لديك عبر المسار العام).

التصفح بالـ profile الحقيقي (استخدم تسجيلات دخولك)

افتراضيًا، يعمل التصفح المحلي في profile نظيف مؤقت يُتخلّص منه لاحقًا — فالوكيل غير مسجّل الدخول في أي شيء. فعّل التصفح بالـ profile الحقيقي لتسمح للوكيل بالتصفح بصفتك أنت، مع تسجيلات الدخول وملفات تعريف الارتباط الموجودة لديك:

عند التفعيل، ينسخ Hermes الـ profile النشط لمتصفحك الافتراضي — أي الـ profile الذي تتصفح به فعلًا (Local State → profile.last_used)، مع ملفات تعريف الارتباط وتسجيلات الدخول المحفوظة والتفضيلات — إلى لقطة (snapshot) مُدارة تحت ~/.hermes/browser-profile/<browser>/، ثم يُطلق الملف التنفيذي الحقيقي لمتصفحك على تلك اللقطة ويربط محرك التصفح به. إن إطلاق الملف التنفيذي الحقيقي (بدلًا من Chromium مضمّن مع خيارات mock-keychain) هو ما يُبقي ملفات تعريف الارتباط المشفّرة بواسطة نظام التشغيل قابلة لفك التشفير — ففي macOS تُشفَّر ملفات تعريف الارتباط في Chrome عبر Keychain، والإطلاق باستخدام mock-keychain سيُسقطها جميعًا بصمت، فيفتح المتصفح دون تسجيل دخول. لا يُفتح الـ profile الحي لمتصفحك مباشرةً أبدًا: فاللقطة مجلد منفصل، لذا لا تتنازع مع متصفحك قيد التشغيل على قفل الـ profile، كما تتجنّب حظر Chrome 136+ للتصحيح عن بُعد على مجلد الـ profile الافتراضي. تُعاد مزامنة ملفات المصادقة (cookies/logins/preferences) من الـ profile الحقيقي كلما أُطلقت جلسة جديدة، لذا فإن تسجيلات الدخول التي تُجريها في متصفحك تظهر في جلسة الوكيل. لا يُنسخ إلا الـ profile النشط — ولا تُلتقط أبدًا لقطات لأي profiles أخرى في Chrome.

يعمل متصفح اللقطة في وضع headless — فهو يقود الـ profile الخاص بك في الخلفية دون نافذة مرئية ولا يسرق التركيز أبدًا، لذا يمكنك مواصلة العمل بينما ينشر الوكيل التغريدات أو يعبّئ النماذج أو يستخرج البيانات نيابةً عنك. (يعني headless هنا وضع headless الجديد في Chrome، الذي يقرأ مخزن ملفات تعريف الارتباط العادي لديك، لذا تظل تسجيلات دخولك تُحمَّل.) وإذا كنت تفضّل مشاهدته أثناء العمل، فإن مفتاح الوضع المرئي (headed) نفسه ينطبق هنا — إذ يفتح browser.headed: true (أو AGENT_BROWSER_HEADED=1) نافذة مرئية للتصفح بالـ profile الحقيقي أيضًا. أما على مضيف بلا شاشة (الخوادم، CI) فيعمل دائمًا في وضع headless بغض النظر عن ذلك.

إذا كان لمتصفحك عدة profiles (مثل profile للعمل وآخر شخصي) ولا تريد أن يحدد "أيّ profile استخدمته آخر مرة" هوية الوكيل، فثبّت مصدر اللقطة صراحةً:

التثبيت الذي يسمّي مجلد profile غير موجود يفشل بشكل مغلق (fails closed) مع رسالة تُرشدك إلى الإصلاح — ولا يرجع أبدًا بصمت إلى آخر profile مُستخدم.

عند إيقاف المفتاح مجددًا، يحذف Hermes مخزن اللقطات (~/.hermes/browser-profile/) عند الاستخدام التالي للمتصفح، حتى لا تبقى بيانات الاعتماد المنسوخة بعد سحب موافقتك.

Windows: يجب إغلاق المتصفح بالكامل

في Windows، يحتفظ متصفح Chrome/Edge/Brave قيد التشغيل بقواعد بيانات ملفات تعريف الارتباط وتسجيلات الدخول بقفل حصري (يمنع الجميع)، لذا لا يستطيع Hermes نسخها بينما المتصفح مفتوح — فيفشل سريعًا مع رسالة "fully quit the browser and retry" بدلًا من التعليق أو إنتاج جلسة غير مسجّلة الدخول. لذلك يتطلب التصفح بالـ profile الحقيقي في Windows إغلاق المتصفح بالكامل، بما في ذلك أي نسخة تعمل في الخلفية أو في شريط النظام (فخيار "continue running background apps when closed" في Chrome يُبقي chrome.exe قيد التشغيل بعد إغلاق النافذة). أما في macOS و Linux فيمكن عادةً نسخ الـ profile أثناء تشغيل المتصفح. وعلى كل المنصات، لكل نسخة احتياطية من قواعد بيانات المصادقة مهلة إعادة محاولة مدتها خمس ثوانٍ. إذا ظلت قاعدة بيانات المصدر أو اللقطة مقفلة، يوقف Hermes الإطلاق ويطلب منك إغلاق المتصفح وإعادة المحاولة. وهو يحافظ على بيانات WAL المُلتزَم بها (committed) عبر SQLite بدلًا من الرجوع إلى نسخ خام للملف، وهو ما قد يُفقد تسجيلات الدخول الحديثة بصمت. كما توقف قواعد البيانات غير القابلة للقراءة أو التالفة الإطلاقَ أيضًا.

اضبط browser.real_profile_autoclose: true لتسمح لـ Hermes بأن يعرض عليك إغلاق المتصفح نيابةً عنك عندما يكون محتفظًا بالـ profile. وحتى مع تفعيل هذا الخيار، لا يُغلق Hermes المتصفح تلقائيًا أبدًا — فعندما يكون الـ profile مقفلًا يتوقف دائمًا ويسألك الوكيل أولًا؛ ولا يُنفّذ hermes browser close-profile إلا بعد موافقتك (وهو يُنهي شجرة عمليات المتصفح المرتبطة بذلك الـ profile، مع فقدان علامات التبويب غير المحفوظة)، ثم يعيد المحاولة. وإذا ظل الـ profile مقفلًا بعد ذلك (مثلًا إذا أُعيد إطلاق نسخة في الخلفية أو في شريط النظام)، يبقى Hermes متوقفًا ويطلب منك إغلاق المتصفح بالكامل — ولن يكرر المحاولة أو يُنهي العملية مجددًا من تلقاء نفسه.

  • المتصفحات المدعومة: Chrome و Edge و Brave و Brave Origin و Chromium (أيّها كان الافتراضي في نظام التشغيل). وإذا كان المتصفح الافتراضي من خارج عائلة Chromium (مثل Firefox) فيفشل بشكل مغلق مع رسالة واضحة بدلًا من التخمين.
  • يعمل على أي backend. على backend محلي يعمل تلقائيًا بمجرد تفعيل المفتاح. وتحت backend متصفح سحابي، لا يزال بإمكان الوكيل فتح جلسة محلية بالـ profile الحقيقي عند الطلب عبر أداة browser_exec باستخدام وسيطها local (لا تُتيح الأداة هذا الوسيط إلا عند تفعيل هذا المفتاح) — بينما يواصل الـ backend السحابي خدمة كل ما عدا ذلك.
  • الإطار الأمني: هذه ميزة للراحة مشروطة بالموافقة، وليست حدًّا للعزل. فالصفحة التي يزورها الوكيل تعمل مع تسجيلات دخولك الحقيقية، لذا لا تفعّلها إلا عندما تريد أن يتصرف الوكيل بصفتك. معطّلة افتراضيًا.
  • Desktop: بدّل المفتاح من Capabilities → Tools → Browser → Use My Real Browser Profile (يقع المفتاح أعلى خيارات الـ backend)، أو من Settings → Config ضمن قسم browser.

  • يتخطى تدمير السياق على جانب الخادم عند التنظيف، لذا تبقى ملفات تعريف الارتباط وتسجيلات الدخول بين مهام الوكيل.
  • يربط نطاق userId بـ Hermes profile النشط، لذا تحصل Hermes profiles المختلفة على profiles متصفح مختلفة (عزل الـ profiles).
ما لا يفعله Hermes
  • لا يفرض الاستمرارية على خادم Camofox. يرسل Hermes فقط userId ثابتًا؛ ويجب على الخادم احترامه بربط userId ذلك بمجلد Firefox profile دائم.
  • إذا كانت نسخة خادم Camofox لديك تتعامل مع كل طلب على أنه مؤقت (مثلًا تستدعي دائمًا browser.newContext() دون تحميل profile مخزَّن)، فلا يستطيع Hermes جعل تلك الجلسات دائمة. تأكد من أنك تشغّل نسخة Camofox تُطبّق استمرارية الـ profiles المعتمدة على userId.
تحقّق من أنه يعمل
  1. شغّل Hermes وخادم Camofox.
  2. افتح Google (أو أي موقع يتطلب تسجيل الدخول) في مهمة متصفح وسجّل الدخول يدويًا.
  3. أنهِ مهمة المتصفح بشكل طبيعي.
  4. ابدأ مهمة متصفح جديدة.
  5. افتح الموقع نفسه مجددًا — يُفترض أن تظل مسجّل الدخول.

إذا سجّلت الخطوة 5 خروجك، فهذا يعني أن خادم Camofox لا يحترم userId الثابت. راجع مسار الإعدادات مجددًا، وتأكد من أنك أعدت تشغيل Hermes بالكامل بعد تعديل config.yaml، وتحقّق من أن إصدار خادم Camofox لديك يدعم profiles دائمة لكل مستخدم.

أين تُخزَّن الحالة

يستمد Hermes قيمة userId الثابتة من المجلد المرتبط بالـ profile ~/.hermes/browser_auth/camofox/ (أو ما يكافئه تحت $HERMES_HOME للـ profiles غير الافتراضية). أما بيانات profile المتصفح الفعلية فتوجد على جانب خادم Camofox، مفهرسةً بقيمة userId تلك. لإعادة ضبط profile دائم بالكامل، امسحه على خادم Camofox واحذف مجلد الحالة الخاص بـ Hermes profile المقابل.

جلسات Camofox المُدارة خارجيًا

عندما يقود تطبيق آخر متصفح Camofox المرئي (مساعد سطح مكتب، أو تكامل مخصص، أو وكيل آخر)، اضبط Hermes ليعمل داخل الهوية نفسها بدلًا من إنشاء profile معزول خاص به.

تتحكم ثلاثة إعدادات في هذا السلوك:

الإعدادمتغير البيئةالتأثير
browser.camofox.user_idCAMOFOX_USER_IDقيمة Camofox userId التي يستخدمها Hermes عند إنشاء علامات التبويب. يؤدي ضبطها إلى إدخال الجلسة في وضع "externally managed" (مُدار خارجيًا).
browser.camofox.session_keyCAMOFOX_SESSION_KEYsessionKey (ويُعرف أيضًا بـ listItemId) الذي يُرسل عند إنشاء علامة التبويب. يُستخدم لمطابقة علامة تبويب موجودة أثناء التبنّي. تكون قيمته الافتراضية خاصة بكل مهمة إذا لم يُضبط.
browser.camofox.adopt_existing_tabCAMOFOX_ADOPT_EXISTING_TABعند ضبطه على true، يستدعي Hermes GET /tabs?userId=<user_id> عند أول استخدام ويعيد استخدام علامة تبويب موجودة قبل إنشاء واحدة جديدة.

تتقدّم متغيرات البيئة على config.yaml. وتعمل أيٌّ من الصيغتين:

ما الذي يتغير عند ضبط user_id:

  • يتخطى Hermes التنظيف المُدمِّر في نهاية المهمة (مثل managed_persistence: true). وتبقى علامة التبويب وملفات تعريف الارتباط والـ profile الخاصة بالتطبيق الآخر.
  • لا يستدعي Hermes DELETE /sessions/<user_id> — فهذا الـ endpoint يمسح جميع بيانات المستخدم، لذا سيدمّر جلسة التطبيق الخارجي إن نُفّذ.

كيف يعمل تبنّي علامات التبويب (عند ضبط adopt_existing_tab: true):

  1. عند أول استدعاء لأداة متصفح بعد بدء العملية، يُرسل Hermes الطلب GET /tabs?userId=<user_id> (بمهلة 5 ثوانٍ).
  2. إذا كانت أي علامة تبويب في الاستجابة تحمل listItemId == session_key، يتبنّى Hermes أحدثها إنشاءً في تلك المجموعة.
  3. وإلا، يتبنّى Hermes أحدث علامة تبويب أُنشئت للمستخدم (بأي listItemId).
  4. إذا لم توجد علامات تبويب أو فشل الطلب، يرجع Hermes إلى إنشاء علامة تبويب جديدة في العملية التالية.

لا يحدث التبنّي إلا إلى أن تُملأ قيمة tab_id للجلسة. إذا أغلق التطبيق الخارجي علامة التبويب المتبنّاة أثناء التشغيل، فسيُظهر استدعاء أداة المتصفح التالي خطأً من Camofox — إذ لا يعيد Hermes البحث عن علامة تبويب جديدة في كل استدعاء.

اختيار session_key: إذا كنت تريد أن يتصل Hermes بشكل موثوق بعلامة تبويب موجودة محددة، فاضبط session_key على قيمة listItemId التي استخدمها التطبيق الخارجي عند إنشائها. وإذا تركت session_key دون ضبط وضبطت user_id فقط، يولّد Hermes قيمة session_key خاصة بكل مهمة (task_<id>) — وسيتشارك Hermes ملفات تعريف الارتباط والـ profile مع التطبيق الخارجي، لكنه سيفتح علامة تبويب خاصة به إلى جانبها بدلًا من إعادة استخدام واحدة.

ملاحظة حول التزامن: يستطيع التطبيق الخارجي و Hermes قيادة userId نفسه في Camofox في الوقت ذاته، لكن Camofox لا ينسّق التركيز على مستوى علامات التبويب بين العملاء. نسّق الملكية على مستوى طبقة التطبيق (مثلًا يتوقف التطبيق الخارجي مؤقتًا أثناء عمل Hermes).

العرض المباشر عبر VNC

عندما يعمل Camofox في الوضع المرئي (headed) (مع نافذة متصفح ظاهرة)، فإنه يكشف منفذ VNC في استجابة فحص الصحة (health check). يكتشف Hermes ذلك تلقائيًا ويُضمّن عنوان VNC URL في استجابات التنقل، حتى يتمكن الوكيل من مشاركة رابط تشاهد من خلاله المتصفح مباشرةً.

محرك Lightpanda المحلي

Lightpanda متصفح headless مفتوح المصدر كُتب من الصفر. يبدأ فورًا، ويعمل أسرع بـ 9 مرات ويستهلك ذاكرة أقل بـ 16 مرة من Chrome، وهذا مهم للوكلاء الذين يعملون على أجهزة افتراضية (VMs) صغيرة لفترات طويلة.

Lightpanda هو محرك محلي (مصدر للمتصفح، مثل Chromium المحلي)، وليس مزوّدًا سحابيًا. ثبّت الملف التنفيذي وضعه ضمن PATH لديك (راجع دليل تثبيت Lightpanda)، ثم اختر Lightpanda في hermes tools → Browser Automation، أو اضبط:

يشغّل Hermes الأمر lightpanda serve --host 127.0.0.1 --port <free> بنفسه — عملية واحدة لكل اسم جلسة browser_exec (أو لكل مهمة) — ويوجّه browser_exec إليها. لا حاجة إلى Chromium أو Node.js. وتُنهى العملية بعد browser.inactivity_timeout، وعند الخروج، وبواسطة عملية تنظيف العمليات اليتيمة إذا تعطّل Hermes. وتتشارك كل هذه العمليات تخزينًا مؤقتًا واحدًا لـ HTTP على القرص في $HERMES_HOME/cache/browser-use/lightpanda/http-cache، لذا تتخطى الزيارات المتكررة إعادة تنزيل الموارد. ولا يمرّر Hermes خيار التخزين المؤقت إلا عندما يدعمه إصدار Lightpanda المثبّت (0.3.x+)؛ أما الملفات التنفيذية الأقدم فتعمل ببساطة دون تخزين مؤقت. لمسحه، أوقف جلسات Lightpanda أولًا، ثم احذف ذلك المجلد.

لا يملك Lightpanda محرك عرض رسومي، لذا فإن capture_screenshot() غير متاحة ويوجّه وصف الأداة النموذجَ إلى العمل نصيًا أولًا؛ كما أنه يحتفظ بصفحة واحدة لكل جلسة، لذا يُطلب من النموذج استدعاء new_tab() مرة واحدة ثم goto_url() بعد ذلك (تجري متابعة ذلك في المشروع الأصلي عبر lightpanda-io/browser#1962).

متى يُتجاهل المحرك. browser.engine هو إعداد المتصفح ذو الأسبقية الأدنى: فالمزوّد السحابي (بما في ذلك متصفح اشتراك Nous — وفي الإعدادات التي لم تُضبط من قبل، يؤدي وجود أي BROWSERBASE_API_KEY / BROWSER_USE_API_KEY في ~/.hermes/.env إلى اختيار أحدها تلقائيًا)، وتجاوز browser.cdp_url / /browser connect، و browser.use_real_profile كلها تتقدّم عليه. يؤدي اختيار Lightpanda في hermes tools إلى كتابة cloud_provider: local نيابةً عنك؛ ويُبلغ /browser status و hermes doctor عندما يكون المحرك مُعدًّا لكنه محجوب، ويذكران ما الذي يحجبه.

متصفحك الخاص عبر CDP (/browser connect)

بدلًا من Chromium الذي يشغّله Hermes أو مزوّد سحابي، يمكنك ربط أدوات المتصفح بنسخة Chrome أو Brave أو Chromium أو Edge قيد التشغيل لديك عبر Chrome DevTools Protocol (CDP). يفيد ذلك عندما تريد رؤية ما يفعله الوكيل في الوقت الفعلي، أو التفاعل مع صفحات تتطلب ملفات تعريف الارتباط/الجلسات الخاصة بك، أو تجنّب تكاليف المتصفحات السحابية.

ملاحظة

/browser connect هو slash command خاص بـ CLI التفاعلية — ولا يُعالجه الـ gateway. إذا حاولت تشغيله داخل WebUI أو Telegram أو Discord أو أي محادثة gateway أخرى، فستُرسل الرسالة إلى الوكيل كنص عادي ولن يُنفّذ الأمر. شغّل Hermes من الطرفية (hermes أو hermes chat) وأصدر الأمر /browser connect هناك.

نصيحة

لتشغيل متصفح من عائلة Chromium يدويًا مع تفعيل CDP، استخدم user-data-dir مخصصًا حتى يعمل منفذ التصحيح فعلًا حتى لو كان المتصفح يعمل بالفعل بالـ profile العادي لديك:

ثم شغّل Hermes CLI ونفّذ /browser connect.

لماذا --user-data-dir؟ بدونه، يؤدي إطلاق متصفح من عائلة Chromium أثناء تشغيل نسخة عادية منه عادةً إلى فتح نافذة جديدة ضمن العملية الموجودة — وتلك العملية لم تُبدأ مع --remote-debugging-port، لذا لا يُفتح المنفذ 9222 أبدًا. يفرض user-data-dir المخصص بدء عملية متصفح جديدة يستمع فيها منفذ التصحيح فعلًا. ويتخطى --no-first-run --no-default-browser-check معالج التشغيل الأول للـ profile الجديد.

يجعل Chrome 136+ الـ profile المخصص إلزاميًا. هناك آليتان منفصلتان تعملان هنا، ولا تنطبق أيٌّ منهما بمجرد تمرير --user-data-dir غير افتراضي. أولًا، منذ Chrome 136 صار --remote-debugging-port و --remote-debugging-pipe "لا يُحترمان عند محاولة تصحيح مجلد بيانات Chrome الافتراضي" — إذ يُتجاهل الخيار بصمت دون أي نافذة حوار، ويتلقى /browser connect (أو curl http://127.0.0.1:9222/json/version) رفضًا للاتصال حتى عند البدء من حالة الإيقاف الكامل. ثانيًا، يضيف Chrome 144+ مسار موافقة اختياريًا لتصحيح الـ profile الحقيقي: تفعّله من chrome://inspect/#remote-debugging، ثم يعرض Chrome نافذة الحوار "Allow remote debugging?" مع كل اتصال وارد (وليس مرة واحدة لكل إطلاق)، ولا يستمع أي شيء حتى تضغط Allow. إذا رأيت نافذة الحوار هذه، فأنت على مسار الموافقة لا مسار الخيار. والحل هو الأوامر أعلاه تمامًا: وجّه --user-data-dir إلى مكان غير مجلد الـ profile الافتراضي لديك (مثل $HOME/.hermes/chrome-debug)، وهو ما لا يحتاج إلى المفتاح ولا إلى نافذة الحوار. ينطبق هذا على إصدارات Chrome و Chromium و Edge و Brave التي تبنّت هذا التغيير.

يبدأ الـ profile المخصص دون تسجيل دخول في أي شيء. إذا كنت تريد أن يتصفح الوكيل بتسجيلات دخولك الحالية مع عدم ظهور أي نافذة موافقة، فاستخدم browser.use_real_profile بدلًا من ذلك: فهو ينسخ الـ profile النشط لديك في لقطة ويقودها، وهي user-data-dir غير افتراضي، لذا لا تُفعّل أيًّا من الآليتين أبدًا.

عند الاتصال، تقود browser_exec و browser_cdp و browser_dialog و browser_vault جميعها متصفحك الحي بدلًا من تشغيل متصفح خاص بها. ويمكن أيضًا ضبط الـ endpoint بشكل دائم عبر browser.cdp_url في config.yaml أو متغير البيئة BROWSER_CDP_URL.

WSL2 مع Chrome على Windows: فضّل MCP على /browser connect

إذا كان Hermes يعمل داخل WSL2 بينما تعمل نافذة Chrome التي تريد التحكم فيها على مضيف Windows، فغالبًا لا يكون /browser connect هو المسار الأفضل.

السبب:

  • يتوقع /browser connect أن يصل Hermes نفسه إلى CDP endpoint قابل للاستخدام
  • غالبًا ما تكشف جلسات التصحيح الحي في إصدارات Chrome الحديثة endpoint محليًا على المضيف لا يمكن الوصول إليه مباشرةً من WSL بالطريقة نفسها التي يُوصل بها إلى منفذ 9222 التقليدي
  • حتى عندما يكون Chrome على Windows قابلًا للتصحيح، فإن أنظف تكامل غالبًا هو ترك خادم MCP للمتصفح على جانب Windows يتصل بـ Chrome، وجعل Hermes يتواصل مع خادم MCP ذلك

لهذا الإعداد، فضّل استخدام chrome-devtools-mcp عبر دعم MCP في Hermes.

الأدوات المرافقة

تعمل browser_vault على جلسة المتصفح نفسها التي تقودها browser_exec — Chromium المحلي، أو متصفح سحابي، أو المتصفح المتصل عبر /browser connect. أما browser_cdp و browser_dialog فلا تُقدَّمان إلا أثناء ضبط CDP endpoint — /browser connect أو BROWSER_CDP_URL أو browser.cdp_url — وتعملان على ذلك المتصفح؛ ولا تأتي بهما جلسة محلية أو سحابية مُشغَّلة.

browser_cdp

تمرير خام لـ Chrome DevTools Protocol — منفذ الطوارئ للعمليات المفردة: التعامل مع النوافذ الأصلية، والتقييم ضمن نطاق iframe، والتحكم بملفات تعريف الارتباط/الشبكة، أو أي أمر CDP يحتاجه الوكيل. (داخل browser_exec تغطي الـ helper cdp() المجال نفسه للأعمال متعددة الخطوات.)

مرجع أساليب CDP: https://chromedevtools.github.io/devtools-protocol/ — يستطيع الوكيل تنفيذ web_extract على صفحة أسلوب محدد للاطلاع على معاملاته وشكل القيمة المُعادة.

أنماط شائعة:

تحذف الأساليب على مستوى المتصفح (Target.* و Browser.* و Storage.*) المعامل target_id. أما الأساليب على مستوى الصفحة (Page.* و Runtime.* و DOM.* و Emulation.*) فتتطلب target_id مأخوذًا من Target.getTargets. كل استدعاء عديم الحالة مستقل — فالجلسات لا تستمر بين الاستدعاءات.

إطارات iframe متعددة الأصول (cross-origin): مرّر frame_id لإطار iframe يعمل خارج العملية (cross-origin) لتوجيه الاستدعاء عبر جلسة CDP supervisor الحية لذلك الإطار. هكذا يعمل Runtime.evaluate داخل iframe متعدد الأصول على Browserbase، حيث قد تصطدم اتصالات CDP عديمة الحالة بانتهاء صلاحية عناوين URL الموقّعة. أما إطارات iframe ذات الأصل نفسه فلا تحتاج إلى frame_id — استخدم بدلًا من ذلك document.querySelector('iframe').contentDocument من Runtime.evaluate على المستوى الأعلى.

browser_dialog

تستجيب لنافذة حوار JS أصلية (alert / confirm / prompt / beforeunload). تحجب نافذة الحوار المفتوحة خيط JavaScript الخاص بالصفحة، فيتوقف عمل المتصفح على تلك الصفحة حتى يُرَدّ عليها.

يكتشف CDP supervisor دائم — اتصال WebSocket واحد لكل مهمة مشترك في أحداث Page/Runtime/Target — نوافذ الحوار لحظة فتحها. ويجيب الوكيل بـ browser_dialog(action="accept") أو browser_dialog(action="dismiss")؛ وفي نوافذ prompt() يمرّر prompt_text="..."، وعندما يكون أكثر من نافذة حوار في الانتظار يمرّر dialog_id لاختيار واحدة. ثم يستأنف خيط JS في الصفحة عمله.

كيف يعمل على Browserbase. يرفض CDP proxy الخاص بـ Browserbase نوافذ الحوار الأصلية الحقيقية تلقائيًا من جانب الخادم خلال ~10ms، لذا لا يمكن استخدام Page.handleJavaScriptDialog. يحقن الـ supervisor سكربتًا صغيرًا عبر Page.addScriptToEvaluateOnNewDocument يستبدل window.alert/confirm/prompt بطلب XHR متزامن، ويعترض طلبات XHR هذه عبر Fetch.enable — فيبقى خيط JS في الصفحة محجوبًا على طلب XHR حتى يستدعي الـ supervisor الأمر Fetch.fulfillRequest مع استجابة الوكيل. وتعود القيم المُرجعة من prompt() إلى JS الصفحة دون تغيير.

سياسة نوافذ الحوار تُضبط في config.yaml تحت browser.dialog_policy:

السياسةالسلوك
must_respond (الافتراضي)الالتقاط، ثم انتظار استدعاء browser_dialog() صريح. مع رفض تلقائي احترازي بعد browser.dialog_timeout_s (الافتراضي 300s) حتى لا يتمكن وكيل معطوب من التعليق إلى الأبد.
auto_dismissالالتقاط، ثم الرفض فورًا. لا يحتاج الوكيل إلى التصرف.
auto_acceptالالتقاط، ثم القبول فورًا. مفيد عند التنقل في صفحات تُظهر مطالبات beforeunload مُلحّة.

browser_vault

تستخدم بيانات تسجيل الدخول وكلمات المرور والبطاقات والعناوين والرموز لمرة واحدة المحفوظة في الصفحة الحالية دون أن تدخل الأسرار إلى المحادثة. يستدعي الوكيل browser_vault(action="list") لرؤية العناصر المحفوظة على هيئة مقابض (handles)، ثم fill أو save_login أو enter_code أو unlock (1Password / Bitwarden). وتُرفض عمليات التعبئة ما لم يطابق أصل الصفحة العنصر المحفوظ. راجع صفحة credential vault للإعداد وbackends مديري كلمات المرور والاستخدام في وضع headless.

إيقاف التصفح

لا يوجد مفتاح إعدادات للمتصفح — بل عطّل toolset الخاص بـ browser. نفّذ hermes tools وأزل تحديد Browser Automation للمنصات التي لا ينبغي أن تتصفح، أو افعل ذلك من سكربت:

وتختفي browser_exec أيضًا من أي جلسة لا تملك toolset الخاص بـ terminal.

Camofox

انتقل Camofox إلى إضافة (plugin): hermes plugins install camofox. وتُرحَّل إعدادات Camofox الحالية (حيث CAMOFOX_URL مضبوط، أو browser.cloud_provider: camofox) تلقائيًا عند التحديث: تُثبَّت الإضافة ويُعطَّل toolset الخاص بـ browser الأساسي في ذلك الـ profile. أما الـ profile الذي عطّل browser في كل مكان (agent.disabled_toolsets) فيُعطَّل فيه camofox أيضًا، ليبقى التصفح متوقفًا. وكتلة browser.camofox دون CAMOFOX_URL ليست إعداد Camofox. والـ profile الذي يُعدّ الإضافة بعد التحديث يُبقي browser_exec إلى جانبها.

القيود

  • مهلة الجلسة — تنتهي صلاحية الجلسات السحابية وفقًا لإعدادات خطة المزوّد لديك.
  • التكلفة — تستهلك الجلسات السحابية أرصدة المزوّد؛ وتُنظَّف الجلسات عند انتهاء المحادثة أو بعد فترة من عدم النشاط. أما Chromium المحلي و /browser connect فمجانيان.
  • Lightpanda — لا لقطات شاشة، وصفحة واحدة لكل جلسة.
  • لا طرفية، لا متصفح — تشغّل browser_exec شيفرة Python، لذا لا تحصل عليها الجلسات التي لا تملك toolset الخاص بـ terminal.

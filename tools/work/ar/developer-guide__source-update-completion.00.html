مسؤولية إكمال تحديث المصدر

الفاصل بين المرحلتين

تتولى عملية الأمر قبول التشغيل وقفل التحديث وعمر المخرجات والجرد قبل التحديث واللقطات لجميع الـ profiles وإيقاف gateway مؤقتًا واختيار Git و stash والاستعادة وضوابط الصياغة/HEAD، وتنزيل ZIP وتجهيزه وإعادة فحص التغييرات المحلية وإلحاق الإصدار والتبديل. تستورد وسيلة نقل الإكمال قبل تبديل الكود. بمجرد اختيار الشجرة النهائية (بما في ذلك دمج المصدر الأصلي)، ترسل مسارات Git والمحاولة عند كون النسخة محدّثة أصلًا و ZIP طلب JSON واحدًا محدد الإصدار إلى update_completion.py من تلك الشجرة. لا تُزال أي وحدة تطبيق مخزّنة مؤقتًا ولا يُعاد تحميلها داخل عملية الأمر.

يحمل الطلب المصدر/المجلد الرئيسي المعتمدين واختيار منتج Desktop والوضع التفاعلي ووضع gateway والإصدار قبل التحديث ومعرّفات لقطات profile النشط والـ profiles الشقيقة وخطة بيئة التشغيل المتسلسلة وهوية إيصال التشغيل المفتوح/بياناته و token إيقاف Windows المؤقت. يحتوي بيانات، لا دوال قابلة للاستدعاء ولا pickles. يظل stdin موروثًا لمطالبات الإعدادات التفاعلية؛ ويحتفظ وضع gateway بسلوكه غير التفاعلي. تظل مخرجات العملية الفرعية ظاهرة ويعكسها تدفق مخرجات التحديث في العملية الأم.

مسؤول الكود الجديد

تبدأ نقطة دخول تعتمد المكتبة القياسية وحدها باستخدام Python المتاح مع -I -S، فلا تُهيَّأ site-packages القديمة ولا ملفات .pth القابلة للتنفيذ. تعزل بادئة خاصة لذاكرة bytecode المؤقتة ملفات cache القديمة قبل أي استيراد من النسخة الجديدة. يشير مسار الاستيراد الصريح إلى النسخة الجديدة. تستدعي واجهة PM الجديدة لتجهيز اتحاد الاعتماديات المسجّل، ثم تبدأ Python المختار ببيئة التفعيل الجديدة. يبدأ ذلك المفسّر أيضًا مع تعطيل تهيئة site، ثم يحجز مسؤول بيئة التشغيل الجيل المختار ويفعّله قبل أي استيراد للتطبيق. هذا المفسّر وحده يستورد كود إكمال التطبيق. تعبر هوية الإيصال/الارتباط نفسها حدود التجهيز هذه (بما فيها نتائج PM). يتولى الإكمال في Python المختار نشر المُشغِّلات وعمليات البناء وإبطال cache وصيانة الإعدادات/الحالة/المهارات لجميع الـ profiles وفحص العمليات وإعادة تشغيل مجموعة gateways واستئناف Windows وإزالة تكرار لوحة التحكم والتحقق.

تبقى خوارزميات إعادة التشغيل والتعافي من الإلغاء الحالية لكل نوع؛ فإخفاقات supervisor/العمليات العابرة حقيقية حتى دون استيرادات مختلطة الأجيال. لا تختفي إلا حيلة المسح/إعادة التحميل وتركيبات مراحل الإكمال المستقلة لإعادة المحاولة/ZIP. تُكتب حالة خروج gateway قبل أن تتمكن إعادة التشغيل من إنهاء cgroup الخاص بالمحدّث. ينشر التحقق الإيصال النهائي.

لا يفشل شيء التحديث بعد نقطة التثبيت

بمجرد انتقال الشجرة، يخرج hermes update بالرمز 0 ما لم يُتراجَع عن الكود نفسه. كل خطوة إكمال مستقلة: فشل نشر مُشغِّل أو بناء منتج (تُجرَّب كل من TUI/الويب/Desktop حتى لو فشل غيرها) أو ترحيل إعدادات أو مسح bytecode أو إعادة تشغيل/تحقق gateway أو استئناف Windows أو تبنّي قناة متقاعدة يطبع سطر ⚠ ويُضاف إلى followups في الإيصال بالحالة {step, reason}، بينما تظل قيمة outcome في الإيصال "success". يظل الالتزام الخاص بالخطوة مفعّلًا: source-completion-pending لمرحلة الإكمال (المُشغِّلات والبناء والصيانة وترحيل الإعدادات)، والالتزام بإعادة تشغيل مجموعة gateways على المضيف (يواصل تحذير بدء CLI تسميته؛ وتسجّل إعادة التشغيل المستحقة gateways السابقة للتحديث في الالتزام، بحيث تظل gateway التي تعطلت عند الإقلاع مستحقة حتى تخدم النسخة المسحوبة بدل تسوية الالتزام لغياب gateways)، وبصمة bytecode غير الموسومة للمسح. يعيد التشغيل التالي أو hermes update — بما فيه مسار "Already up to date" الذي ينفّذ الإكمال نفسه — المحاولة. المضيف الموسوم "restarted" لهذا commit، بينما مجموعته ما زالت خارج النسخة المسحوبة، يعيد التشغيل مجددًا بدل الوصول إلى طريق مسدود. يحتفظ رمز الخروج 2 (مرفوض / متزامن) والرمز 1 (لم يُثبَّت شيء أو جرى التراجع) بمعنييهما.

مزامنة الـ profiles بأفضل جهد: تطبع _sync_profiles_after_update خطأً لكل profile وتواصل العمل، لذا لا يصبح ذلك الخطأ مستحقًا. وحدها المزامنة التي تفلت من الخطوة (مثلًا باستخدام SystemExit) تصبح متابعة profile_sync وتُبقي source-completion-pending مفعّلًا.

تُجرَّب استعادة gateway في Windows مرة واحدة بعد نقطة التثبيت: بواسطة العملية الفرعية للإكمال أو بواسطة العملية الأم عندما تبقى الاعتماديات مستحقة. يُسجَّل فشلها كمتابعة windows_resume. لا يعيد مسار خروج الأمر نفسه ولا شبكة أمان atexit المحاولة، ويُبلَّغ عن استئناف ما زال مستحقًا (لم تجب العملية الفرعية أصلًا) بالطريقة نفسها بدل رفع استثناء. يسجّل إكمال الاستحواذ التاريخي (update_finish) الفشل أيضًا كمتابعة ويحافظ على حالة خروجه.

يبقى الإيصال محفوظًا بصورة دائمة ما دام التشغيل مفتوحًا: تكتبه begin_update_receipt بالحالة outcome: "running" في ملف أرشيف التشغيل نفسه وفي latest.json، وتحدّثه كل حدود مرحلة، بحيث يترك التحديث الذي أُنهِي سجلّه الخاص. يوسم التحديث التالي سجل running الذي اختفت عملياته بالحالة interrupted (مع تسمية مرحلته الأخيرة) ويبلّغ عنه. تُحدَّد الإيصالات وتدفق tee الخاص بـ update.log داخل المجلد الرئيسي الجذري (hermes_constants.get_default_hermes_root())، لا مجلد profile ثابت؛ وكذلك قارئاتها (hermes logs update وحزمة debug وحالة التحديث في لوحة التحكم وإيصالات المزامنة لـ pm).

يحدث تجهيز الاعتماديات في bootstrap الإكمال (ensure_tools_for_sync، pm.sync_venv) أيضًا بعد انتقال الشجرة: فشله متابعة dependencies ("dependencies not installed yet — the next launch retries")، مع خروج 0 وإبقاء التزام مرحلة الإكمال مفعّلًا؛ أما العملية الفرعية المجهّزة التي تموت دون نتيجة فتصبح متابعة completion. يؤدي Ctrl-C بعد نقطة التثبيت إلى إغلاق التشغيل بالحالة interrupted (خروج 130، وليس failed أبدًا) ويذكر أن الكود الجديد في مكانه مع بقاء خطواته المتبقية مستحقة.

تتبع قناتان إضافيتان بعد التثبيت القاعدة نفسها. تحتفظ علامة gateway /update (.update_exit_code) بالنتيجة المثبّتة عندما تفشل إعادة تشغيل gateway (وحدة systemd أو التعافي من الإلغاء أو استئناف خدمة Windows): يكون دين إعادة التشغيل متابعة gateway_restart والتزام المضيف وأسطر ⚠ في المخرجات المُمرَّرة، ولا يكون أبدًا تنبيه "failed". مخزن الإيصالات الذي يرفض الكتابة النهائية يطبع ⚠ Update receipt not written، وتجيب العملية الفرعية للإكمال العملية الأم بالسجل النهائي المرتبط الذي أنهته في الذاكرة، لذا تظل حالة الخروج 0؛ وحده إجراء مستخدم مطلوب (تغييرات محلية متروكة في stash) يظل يخرج بالرمز 1.

دورة حياة العملية الأم والإخفاقات

تنتظر العملية الأم وتنقل نتيجة العملية الفرعية غير الصفرية كما هي (تُحوَّل الإشارة إلى 128+signal بأسلوب shell)؛ ولا تؤدي إخفاقات الخطوات بعد التثبيت إلى نتيجة كهذه. لا يكفي أن تخرج العملية الفرعية بالرمز صفر للنجاح: بل تُطلَب استجابة نهائية ذات هوية إيصال مطابقة. تعيد الاستجابة Windows token المعدّل حتى لا يكرر الاستئناف الطارئ المسجّل في العملية الأم عملًا مكتملًا. لا يجري الإكمال الطبيعي للعملية الأم أي صيانة.

تحتفظ العملية الأم بإيصالها الأصلي حتى تأكيد الإنهاء من العملية الفرعية؛ وتُبقي مخرجات العملية الفرعية المفقودة/الفاشلة الإيصال متاحًا لآلية إنهاء الفشل الحالية عند حدود الأمر. يعيد bootstrap المبني على المكتبة القياسية بيانات فشل PM المرتبطة حتى عند تعذّر استيرادات التطبيق، ويطبّع حالات خروج الإشارات السالبة عند كل حدود عملية. يمتلك إكمال POSIX جلسة/مجموعة عمليات جديدة؛ ويُنهي الإلغاء تلك المجموعة قبل تحرير القفل (يستخدم Windows شجرة taskkill /T الخاصة بالعملية الفرعية المحتفَظ بها). تسجّل العملية الأم التزام مجموعة gateways المعلّق قبل بدء عملية الإكمال، بما في ذلك عند تعذّر بدء التجهيز. يظل استئناف Windows الطارئ في العملية الأم التزامًا لدورة الحياة كملاذ أخير عندما تتعذّر على العملية الفرعية التنفيذ أو تُنهى. لا تمسح العملية الفرعية الفاشلة أبدًا التزام المجموعة المعلّق. لا تراجع تلقائي عن الكود بعد بدء الصيانة (تبقى لقطات SQLite وسيلة تعافٍ من فقد الملفات، لا تراجعًا).

كود تعافٍ تالف

يتطلب إصلاح النسخة المسحوبة عند التشغيل إمكان استيراد قفل النسخة وكذلك مشغّل حراسة العمليات الفرعية. إذا تلفت أي وحدة منهما، يتوقف التشغيل برسالة Cannot safely repair ويحتفظ بعلامة التحديث المنقطع بدل الكتابة دون استبعاد متبادل. يستطيع محدّث استورد كودًا سليمًا بالفعل إبقاء النسخة مقفلة والكتابة إليها حتى لو تلفت وحداته على القرص. انتظر انتهاء أي تحديث قيد التشغيل.

يوجد كود الإصلاح في الشجرة التي يمزّقها انتقال أُنهِي (hermes_bootstrap.py، hermes_cli/__init__.py، _early_recovery.py، update_lock.py، update_custody.py). قبل كتابات git، ينشر كل انتقال للشجرة وحدات التعافي/القفل/حراسة العمليات تلك، كما ثُبّتت عند commit بداية الانتقال، إلى <git dir>/hermes-update-recovery/<pre>/، خارج شجرة العمل ومربوطة بقيمة pre في العلامة (معرّف commit كامل، لا غير)، مع MANIFEST يضم معرّف blob لكل ملف؛ وتُنفَّذ fsync للملفات والدليل قبل إعادة التسمية. عندما يفشل الاستيراد من النسخة نفسها مع وجود العلامة، لا يشغّل المُشغِّل المنشأ (.hermes/bin/hermes) تلك النسخة المنشورة إلا إذا طابق hash كل ملف معرّفه في manifest. تُعاد بناء النسخة المفقودة أو التالفة أو الدخيلة أولًا (أو عند غيابها، من محدّث أقدم) من كائنات git عند pre (--no-replace-objects، باستخدام git المسجّل أو مدخل PATH مطلق، وليس الدليل الحالي أبدًا)، ويُتحقَّق منها بالطريقة نفسها. ثم: المكتبة القياسية مع النسخة فقط، وطلب الاستعادة نفسه وقفل النسخة المسحوبة نفسه (يحصل الكاتب الحي على Not repairing the checkout now وخروج 1، دون traceback)، ثم إعادة تشغيل من الشجرة المستعادة. الحدود: لا تمتلك نقاط الدخول الأخرى (python -m hermes_cli.main و hook hermes-agent) هذا البديل الاحتياطي؛ ولا يمتلكه مُشغِّل منشأ قبل وجوده، لذا فإن الإنهاء خلال أول تحديث إلى هذا الكود (يعمل تحت المُشغِّل القديم) غير مشمول؛ ولا تُستخدَم قيمة pre إذا افتقدت شجرتها قفل النسخة أو مشغّل حراسة العمليات.

تغييرات السلوك في مسار git

الاختلافات المقصودة عن المحدّث السابق غير المعاملاتي، لملاحظات الإصدار:

  • لا يعمل بديل ZIP الاحتياطي في Windows إلا من نسخة مسحوبة لم تُمسّ. بمجرد أن ينفّذ git stash أو تبديلًا أو انتقالًا جزئيًا للشجرة، فإن overlay الخاص بـ ZIP (الذي يستبدل كل مدخل في المستوى الأعلى) سيدفن تلك الحالة، لذا يفشل التشغيل بخطأ git بدلًا من ذلك.
  • تفعّل نقطة التثبيت مرحلة الإكمال وإعادة تشغيل مجموعة gateways والعلامة قبل كتابات git. إذا تعذّر حفظ أي منها بصورة دائمة، يتوقف التحديث مع إبقاء النسخة دون تغيير: الانتقال دونها هو حالة "مرحلة الإكمال لا تعمل أبدًا".
  • تُترجَم ملفات بدء التشغيل (المُشغِّل ومجموعة الاستيرادات المغلقة لـ hermes_bootstrap) عند commit الهدف قبل الانتقال، بمفسّر تسمح به requires-python الخاصة بالهدف (uv python find ثم python3.N). عند عدم تثبيت أي منها، يسمّي الرفض Python المطلوب تثبيته. الفحص المسبق عبارة عن git cat-file --batch واحدة.
  • يسمّي كل انتقال معرّف commit الذي حُدِّد، لا ref، ولا تُزال علامته إلا عندما يصبح HEAD ذلك commit. يُبلَّغ عن branch يتحرك أثناء التبديل كتبديل فاشل. تُستحَق إعادة التشغيل لـ HEAD الذي انتهى إليه التبديل فعليًا.
  • يُقيَّم fast-forward للمصدر الأصلي في fork بالطريقة نفسها قبل انتقاله. يؤدي commit معطوب في المصدر الأصلي إلى التراجع عن التحديث كله.
  • لا تُنهى علامة التعافي التي اختفى commit الهدف الخاص بها (gc أو إعادة استنساخ) إلا فوق شجرة متتبعة نظيفة عند pre. حتى ذلك الحين، يحذّر كل تشغيل.

الواجهة التاريخية

تظل جميع الأسماء المثبّتة من كامل تاريخ المحدّث المُصدَر القابل للوصول قابلة للحلّ. تحتفظ الـ hooks التاريخية للاعتماديات بجسر الاستحواذ القائم على المكتبة القياسية وحدها: تنتظر العملية الأم القديمة وتحمل حالة الإيصال/التعافي ولا تستأنف مطلقًا مُثبّتًا متقاعدًا. تتوقف الـ hooks المتقاعدة حديثًا للتجهيز وإعادة تحميل الوحدات والموسومة صراحةً بأنها غير مكتملة برمز غير صفري وتطلب hermes update مجددًا؛ ولا يمكنها اختلاق طلب إكمال مفقود. يستخدم المستدعون الحاليون لمسارات Git/النسخة المحدّثة/ZIP وسيلة نقل الإكمال المعتمدة وحدها، لا نقطة دخول الاستحواذ التاريخية. تُحذَف تركيبات إعادة المحاولة غير المثبّتة والموجودة في branches وحدها، بدل توفير shim لها. يستخدم نشر ACP الميسّر expose_cli الخاص بمسؤول المُشغِّل؛ أما مدخل ACP التاريخي فهو محوّل فقط، لا كاتب ثانٍ مطلقًا. لا تُقلَّص المجموعة المثبّتة ولا تُستبدَل بتغطية الوسوم وحدها. تُدمَج استيرادات المسار الحالي الجديدة مع ذلك التاريخ.

التحقق

استخدم مجلدات رئيسية معزولة ومستودعات Git مؤقتة ومحوّلات وهمية للاعتماديات/البناء/الخدمات فقط. اختبر عملية قديمة ذات وحدات مخزّنة مؤقتًا غير متوافقة عبر انتقال Git فعلي إلى كود جديد، والتنفيذ بـ Python المختار وهوية الإيصال ونقل اللقطات وخروج العملية الفرعية غير الصفري/المفاجئ وتحرير القفل وإرجاع Windows token. تغطي الاختبارات الحالية المركّزة فحوصات ZIP ذات التغييرات المحلية/الإلحاق واللقطات وتسوية مجموعة gateways وتوقيت supervisor والاستيرادات التاريخية. تبقى إعادة تشغيل الخدمات الأصلية وقبول Windows/macOS مسارات مطلوبة منفصلة؛ ولا تمس تشغيلات الاختبار لهذا التنفيذ أي خدمة حية للمستخدم أو حالته.

مصفوفة حالات الانهيار

تنهي كل حالة تشغيلًا فعليًا لـ hermes update (أو سكربت التسليم في Desktop) في نقطة واحدة من التحديث، ثم تتحقق مما يُستحَق للمستخدم: أن تشغيل hermes التالي قابل للعمل، وأن النسخة بعده مباشرةً تطابق commit ما قبل التحديث أو الهدف تمامًا (HEAD وكل بايت متتبع: git status نظيف و git diff --quiet HEAD؛ يغيّر كل هدف وحدات يستوردها كل تشغيل)، وألا يمنع أي شيء تركه التحديث المنتهي (قفل git أو .hermes-update-in-progress) التحديث التالي. الحالة التي إصلاحها في PR مفتوح تغلّف تأكيداتها النهائية وحدها في known_failure (tests/e2e/core/_pending_fixes.py) بعد كل التأكيدات الأخرى في الحالة: تُسجَّل XFAIL عند رسالة تلك الفجوة نفسها، وتفشل عند أي شيء آخر، وتنجح بمجرد دمج الإصلاح، أيًا كان ترتيب الدمج. يرفض تشغيل قبول لدفعة متكاملة هذا السماح: HERMES_E2E_STRICT_ACCEPTANCE=<owner> (مدخل الإرسال strict_acceptance الخاص بـ ci.yaml و windows-install-update-e2e.yml، مثل gh workflow run windows-install-update-e2e.yml --ref <branch> -f strict_acceptance=upd-txn) يحوّل كل فجوة يبدأ سببها بـ <owner>: إلى فشل (1: كل الفجوات). نقاط الإنهاء حالات مرصودة (عملية git فرعية في شجرة العمليات بحسب argv، أو git محتجَز داخل نسخته بمرشّح مع وجود index.lock، أو HEAD مقروء من ملفات ref، أو عملية التحديث الفرعية في التسليم مع علامتها)، لا فترات انتظار.

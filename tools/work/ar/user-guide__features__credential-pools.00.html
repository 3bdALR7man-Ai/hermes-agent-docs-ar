مجمّعات بيانات الاعتماد (Credential Pools)

تتيح لك مجمّعات بيانات الاعتماد (Credential Pools) تسجيل عدة مفاتيح API أو رموز OAuth لنفس المزوّد. فعندما يصل أحد المفاتيح إلى حدّ المعدل (rate limit) أو حصة الفوترة، يقوم Hermes تلقائيًا بالتناوب إلى المفتاح الصحي التالي — مما يبقي جلستك عاملة دون التبديل إلى مزوّد آخر.

يختلف هذا عن المزوّدين الاحتياطيين (fallback providers)، الذين يبدّلون إلى مزوّد مختلف تمامًا. مجمّعات بيانات الاعتماد هي تناوب ضمن المزوّد نفسه؛ بينما المزوّدون الاحتياطيون هم تجاوز فشل عبر مزوّدين مختلفين. تُجرَّب المجمّعات أولًا — فإذا استُنفدت كل مفاتيح المجمّع، عندها يُفعَّل المزوّد الاحتياطي.

تناوب المفاتيح يصفّر ذاكرة التخزين المؤقت للـ prompt

ذاكرات التخزين المؤقت للـ prompt الخاصة بالمزوّد (Anthropic و OpenAI و OpenRouter) مرتبطة بالحساب/مفتاح API الذي أجرى الطلب. فعندما يتناوب المجمّع إلى مفتاح مختلف في منتصف الجلسة، لا يملك المفتاح الجديد أي بادئة مخزّنة مؤقتًا لمحادثتك — يُعيد الطلب التالي قراءة السجل الكامل بسعر الإدخال الكامل دون خصم، والعودة إلى المفتاح السابق لاحقًا هي إعادة قراءة كاملة أخرى ما لم تكن مدة صلاحية ذاكرة المفتاح السابق لا تزال فعّالة. التناوب يبقي جلستك عاملة، وهذا هو المقصود منه، لكن على المحادثات الطويلة تكلّف كل عملية تناوب مرورًا واحدًا كاملًا بالسعر الكامل على السياق.

نصيحة

مجمّعات بيانات الاعتماد مخصصة أساسًا لمزوّدي مفاتيح API (OpenRouter و Anthropic). OAuth واحد لـ Nous Portal يغطي أكثر من 300 نموذج، لذا لا يحتاج معظم المستخدمين على Portal إلى مجمّع.

استراتيجيات التناوب

مواضع الأولوية تبدأ من صفر وتنحصر عند طرفَي المجمّع؛ والأهداف المعروضة فهارس تبدأ من 1، أو معرّفات عناصر، أو تسميات دقيقة غير ملتبسة. auth add --priority يضع أيضًا إدخالًا موجودًا تم تحديثه عبر إعادة المصادقة. يُبقي Anthropic بيانات الاعتماد اليدوية قبل بيانات الاعتماد المزروعة (seeded)، لذا يُبلِغ الأمر عن الموضع الفعلي عندما تغيّره هذه القاعدة. قد تتجاوز استراتيجيات أخرى الأولوية، ولا تُعيد إعادة الترتيب ربط بيانات الاعتماد التي تحتفظ بها جلسة قيد التشغيل بالفعل.

كل اختيار ناجح للمجمّع يزيد request_count ، بغضّ النظر عن الاستراتيجية. ولا تُحتسب عمليات البحث للتحديث فقط أو الاطلاع. وقراءات الحالة (hermes doctor ، وصفوف المزوّدين في محدّد /model ، وبطاقات المصادقة في لوحة التحكم) عمليات اطلاع: لا تحدّث بيانات اعتماد المجمّع أو تدوّرها أو تستبعدها مؤقتًا أبدًا، لذا لا يستطيع تعثّر endpoint الخاص بـ token أثناء فتح المحدّد إخفاء مزوّد لا يزال يخدم الطلبات. وهذه عدّادات اختيار، لا إجماليات فوترة أو عدد كل طلبات inference: فقد تخدم بيانات اعتماد مخزّنة مؤقتًا طلبات متعددة. وتظل الأعداد في الذاكرة حتى عملية كتابة المجمّع القائمة التالية (كالتدوير أو الاستنفاد أو التحديث أو التغيير الإداري)؛ ولا يضيف ذلك كتابة على القرص لكل اختيار.

اضبطها عبر hermes auth → "Set rotation strategy" أو في config.yaml:

الاستراتيجيةالسلوك

خفض أولوية بيانات اعتماد سليمة

لا يستبعد المجمّع بيانات اعتماد مؤقتًا إلا بعد أن يرفضها المزوّد (429/402/401). ولإبعاد بيانات اعتماد تستخدمها بنشاط في موضع آخر — مثل تسجيل دخول إلى Codex تريد توفير نافذته الأسبوعية للعمل التفاعلي — عن الاختيار الأول لـ gateway قبل استنفادها، انقلها إلى نهاية ترتيب fill_first بدلًا من إزالتها:

hermes auth priority <provider> <target> <priority> يعيد ترتيب بيانات اعتماد واحدة ويعيد ترقيم البقية، ثم يحفظ الترتيب الجديد في auth.json. ويظل العنصر المؤخَّر سليمًا: فهو غير مستنفَد، لذا لا يتعرض له فحص إعادة ضبط حصة Codex، ولا يوجد شيء يمسحه hermes auth reset ؛ ولا يُحدَّث على مؤقّت، ويظل مستخدمًا بعد استبعاد كل بيانات الاعتماد السابقة له مؤقتًا. وتحتفظ الجلسات التي تحمل بيانات اعتماد بالفعل بها حتى تدويرها؛ وتتبع الجلسات الجديدة (وبدء gateway التالي) الترتيب الجديد.

تُعاد تهيئة علامة has_retried_429 عند كل استدعاء API ناجح، لذا لا يؤدي خطأ 429 عابر واحد إلى التناوب.

استبعاد الحصة مؤقت للجلسة الحية أيضًا. عندما يؤدي 429/402 إلى تدوير الجلسة بعيدًا عن بيانات اعتماد، تفحص تلك الجلسة في بداية كل دور ما إذا كانت بيانات الاعتماد المستبعَدة قد عادت إلى التدوير، وتعود إليها فور انتهاء التهدئة — وهو الاختيار نفسه الذي تتخذه جلسة جديدة. ولذلك تعود المحادثة الطويلة (إذ يحتفظ gateway بالوكلاء مؤقتًا) إلى مقعد الاشتراك عند إعادة فتح نافذته بدلًا من فوترة البديل المحسوب بالاستخدام لبقية عمرها. ولا يؤدي استبعاد 401 إلى ذلك؛ ويُلغي تبديل صريح عبر /model أي عودة معلّقة.

أخطاء Anthropic 429 تخصّ كل نموذج. يفرض Anthropic حدود المعدل لكل نموذج، لذا يهدّئ 429 عام لنموذج Claude واحد بيانات الاعتماد لـ ذلك النموذج وحده — ويظل المفتاح نفسه يخدم كل نماذج Claude الأخرى، وتراعي tokens الخاصة بـ ANTHROPIC_API_KEY / المستعارة من Claude Code التهدئة نفسها لكل نموذج. وتظل أخطاء الفوترة (402 و usage-limit) والمصادقة (401) تستبعد بيانات الاعتماد كلها مؤقتًا.

يُبلَّغ عن تسجيل دخول OAuth ميت، ولا يُستبعد مؤقتًا. عندما يُرفض refresh token نهائيًا (invalid_grant أو invalid_token أو refresh_token_reused — بسبب إلغائه أو لأن برنامجًا آخر يحمل تسجيل الدخول نفسه دوّره أولًا — أو، في Nous، لأن الـ profile لا يملك تسجيل دخول إلى Portal أو زوج tokens للتحديث)، يسجّل المجمّع WARNING واحدًا يسمّي العنصر وأمر الإصلاح (hermes auth add <provider>)، وتغادر بيانات الاعتماد التدوير — موسومةً بـ dead أو محذوفةً إذا كانت لا تعكس إلا ملف token مسحه المجمّع للتو — إلى أن تسجّل الدخول مجددًا. وينطبق ذلك على تسجيلات OAuth إلى Anthropic و Codex و xAI و Nous على السواء. ولا تعود بيانات اعتماد ميتة إلى التدوير على مؤقّت أبدًا، لذا يظهر تسجيل الدخول المفقود مرةً واحدةً في السجل بدلًا من الفشل بصمت كل ساعة.

كل تسجيلات Codex في مجلد رئيسي دائم التشغيل ميتة: سجّل الدخول مجددًا، ولا تنتظر التبنّي. لا يستورد Hermes ملف ~/.codex/auth.json الخاص بـ Codex CLI تلقائيًا إلا لـ إصلاح تسجيل دخول يملكه بالفعل — عندما يفشل تحديثه الخاص لعنصر openai-codex ويكون auth.adopt_external_logins مفعّلًا (راجع تسجيلات دخول CLI المستعارة). والمجمّع الذي أصبحت كل عناصر Codex فيه dead (أو أُزيلت) لا يملك شيئًا لإصلاحه، لذا يظل gateway بلا واجهة أو profile cron دون بيانات اعتماد Codex حتى تنفّذ hermes auth add openai-codex في ذلك المجلد الرئيسي (hermes -p <profile> auth add openai-codex للـ profile المسمّى)، الذي يعرض استيراد Codex CLI تفاعليًا. ويمكن لـ profiles التي ينبغي أن تشترك في تسجيل دخول واحد الإشارة إلى HERMES_HOME نفسه بدلًا من حمل كل منها نسخةً من refresh token للاستخدام مرة واحدة.

بيانات الاعتماد الخاضعة للتهدئة أو الميتة لا تعني تثبيتًا فارغًا. عندما يبدأ profile مضبوط CLI وبيانات اعتماده الوحيدة مستبعَدة مؤقتًا أو معزولة، تطبع البداية الفشل، ومدة التهدئة المتبقية للاستبعاد المؤقت (أو أمر hermes auth add <provider> لإعادة تسجيل الدخول للميتة) — ولا يُعرَض معالج التشغيل الأول "No inference provider is configured yet" إلا إذا لم يجد المحلِّل أي إعدادات أصلًا.

عدة مفاتيح من البيئة

هل تريد أكثر من مفتاح لمزوّد دون تخزين أي منها في auth.json ؟ رقّمها. بجوار NVIDIA_API_KEY اضبط NVIDIA_API_KEY_2 و NVIDIA_API_KEY_3 و … في shell، أو .env ، أو مدير الأسرار (Bitwarden Secrets و Vault و …)، ويصبح كل منها عنصرًا مستقلًا في المجمّع عند التحميل التالي — دون أمر أو إعدادات. ويتوقف الاكتشاف عند أول رقم مفقود، لذا تُتجاهَل قيمة _5 منفردة دون _4. اجمعها مع credential_pool_strategies لتدويرها:

الأسرار (secrets) المستعارة وقت التشغيل (مثل متغيرات البيئة، ومراجع Bitwarden/Vault/keyring/systemd، وقيم الإعدادات المخصّصة) تكون مرجعية فقط عند حدود auth.json. يمكن لـ Hermes استخدام القيمة المحلولة في الذاكرة للتشغيل الحالي، لكنه لا يحفظ سوى بيانات وصفية مثل مرجع المصدر والتصنيف والحالة وعدّادات الطلبات وبصمة (fingerprint) غير قابلة للعكس. أما الإدخالات اليدوية وحالة OAuth/رمز الجهاز المملوكة لـ Hermes فتحتفظ بالرموز الدائمة التي تحتاجها للتحديث.

عندما ينشئ الوكيل subagents عبر delegate_task ، تُشارَك مجمّعة بيانات اعتماد الوالد تلقائيًا مع الأبناء:

  • نفس المزوّد — يتلقى الابن مجمّعة الوالد الكاملة، مما يتيح تناوب المفاتيح عند بلوغ حدّ المعدل
  • مزوّد مختلف — يحمّل الابن مجمّعة ذلك المزوّد الخاصة (إن كانت مُعدَّة)
  • لا مجمّع مُعدّ — يعود الابن إلى مفتاح API الفردي الموروث

هذا يعني أن الـ subagents تستفيد من نفس مرونة تحمّل حدّ المعدل مثل الوالد، دون أي إعداد إضافي. يضمن استئجار بيانات الاعتماد لكل مهمة (per-task credential leasing) عدم تعارض الأبناء مع بعضهم عند التناوب على المفاتيح في آن واحد.

أمان الـ threads

يستخدم مجمّع بيانات الاعتماد قفل threading لكل تعديلات الحالة (select() ، mark_exhausted_and_rotate() ، try_refresh_current() ، mark_used()). هذا يضمن وصولًا آمنًا ومتزامنًا عندما يتعامل gateway مع عدة جلسات محادثة في آن واحد.

عبر العمليات (المتعدّدة subagents، أو gateway مع CLI، أو مهام cron)، تُسلسَل تحديثات OAuth عبر قفل ملف على auth.json. وعندما تنتهي صلاحية منحة OAuth مشتركة واحدة في ظل عمليات متزامنة كثيرة، تنفّذ عملية واحدة بالضبط التحديث؛ وتكتشف البقية أن token على القرص لم يعد يطابق الذي فشل فتتبنّاه بدلًا من إعادة تدوير refresh token ذي الاستخدام الواحد. وتحتفظ العملية التي تخسر سباق القفل بعنصرها سليمًا وتعيد المحاولة — ولا يُسجَّل تنازع القفل أبدًا كفشل في بيانات الاعتماد. ولا تكتب جلسة أو عملية ما زالت تحمل نسخة أقدم من المجمّع tokens تلك النسخة فوق زوج دوّرته جهة أخرى منذ ذلك الحين؛ بل تحتفظ بالزوج الأحدث على القرص وتتبنّاه.

البنية المعمارية (Architecture)

لمخطط تدفق البيانات الكامل، راجع docs/credential-pool-flow.excalidraw في المستودع (repository).

يتكامل مجمّع بيانات الاعتماد على طبقة تحديد المزوّد:

  1. agent/credential_pool.py — مدير المجمّع: التخزين والاختيار والتناوب وفترات التهدئة؛ agent/credential_pool_admin.py يتولى تحديد الهدف تحت القفل وإعادة الضبط والإضافة والإزالة وتعديلات الأولوية؛ و agent/credential_pool_model_cooldowns.py يتولى فترات تهدئة Anthropic 429 لكل نموذج
  2. hermes_cli/auth_commands.py — أوامر CLI والمعالج التفاعلي
  3. hermes_cli/runtime_provider.py — تحديد بيانات اعتماد واعٍ بالمجمّع
  4. agent/turn_api_error.py — التعافي من الأخطاء: 429/402/401 → تناوب المجمّع → احتياطي

استُعير عنصر OpenRouter أعلاه من مصدر خارجي، لذا لا يُخزَّن المفتاح الخام في auth.json. وأُضيف عنصر Anthropic اليدوي عمدًا إلى مخزن بيانات اعتماد Hermes، لذا يظل token الخاص به قابلًا للحفظ الدائم.

يُعاد ملء صف env: من البيئة عند كل تحميل، ولا يلزم أن يكون اسم المتغير من الأسماء التي يعلنها Hermes للمزوّد: تظهر المتغيرات الشقيقة المرقّمة (OPENROUTER_API_KEY_2 ، راجع الاكتشاف التلقائي) هنا تلقائيًا، ويُملأ صف مكتوب يدويًا يشير إلى أي متغير آخر بالطريقة نفسها، دون كتابة السرّ أبدًا في auth.json.

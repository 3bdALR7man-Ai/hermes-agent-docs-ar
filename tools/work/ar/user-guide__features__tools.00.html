الأدوات و Toolsets

الأدوات (tools) هي دوال توسّع قدرات الوكيل، وهي منظّمة في مجموعات منطقية تُسمّى toolsets يمكن تفعيلها أو تعطيلها لكل منصة على حدة.

الأدوات المتاحة

يأتي Hermes مزوّدًا بسجل واسع من الأدوات المدمجة يغطي البحث في الويب، وأتمتة المتصفح، والتنفيذ في الطرفية، وتحرير الملفات، والذاكرة، والتفويض، والمهام المجدولة، و Home Assistant، وغير ذلك.

ملاحظة

ذاكرة Honcho العابرة للجلسات متاحة كإضافة (plugin) لمزوّد ذاكرة (plugins/memory/honcho/)، لا كـ toolset مدمج. راجع الإضافات (Plugins) لمعرفة طريقة التثبيت.

Nous Tool Gateway

يمكن للمشتركين في الباقات المدفوعة من Nous Portal استخدام البحث في الويب، وتوليد الصور، و TTS، وأتمتة المتصفح عبر Tool Gateway — دون الحاجة إلى مفاتيح API منفصلة. نفّذ hermes model لتفعيله، أو اضبط الأدوات كلًّا على حدة باستخدام hermes tools.

استخدام Toolsets

من الـ toolsets الشائعة: web، search، terminal، file، browser، vision، image_gen، skills، tts، todo، memory، session_search، cronjob، code_execution، delegation، clarify، homeassistant، messaging، spotify، discord، discord_admin، debugging، و safe.

راجع مرجع Toolsets للاطلاع على المجموعة الكاملة، بما فيها الإعدادات المسبقة الخاصة بالمنصات مثل hermes-cli و hermes-telegram، والـ toolsets الديناميكية الخاصة بـ MCP مثل mcp-<server>.

تعليقات نتائج الأدوات

من المفيد معرفة بعض سلوكيات الأدوات عند قراءة سجلات محادثات الوكيل (transcripts):

  • يُشرح سبب إنهاء العمليات بالإشارات (signals). عندما تُنهى عملية أمر في الطرفية بإشارة، تحمل النتيجة ملاحظة مقروءة بدلًا من رمز رقمي مجرد — فمثلًا يصبح رمز الخروج -9/137 "terminated by signal 9: SIGKILL — often the kernel OOM killer on memory exhaustion, or an explicit kill -9"، وتُوسَم بالطريقة نفسها أخطاء segfault، وحالات abort، و SIGTERM، والأنابيب المقطوعة (broken pipes)، وحدود CPU وحجم الملفات. تُذكر الرموز السالبة (وفق دلالات subprocess) بشكل قاطع؛ أما اصطلاح الـ shell 128+signum فيُذكر بتحفّظ مع كلمة "usually"، لأن التطبيق قد يخرج بهذه الرموز بشكل مشروع.
  • ملفات النص بترميز UTF-16 تُحوَّل بدلًا من رفضها. تكتشف read_file ترميز UTF-16 (عبر BOM أو استدلال من نمط البايتات، وبأيّ ترتيب للبايتات (endianness) — وهو شائع في ملفات Notepad على Windows وفي عمليات إعادة التوجيه > في PowerShell) وتحوّله إلى UTF-8 للعرض بدلًا من اعتبار الملف ثنائيًا. تتضمن النتيجة تلميحًا يُفصح عن هذا التحويل؛ وتُعيد التعديلات عبر patch/write_file ترميز الملف بصيغة UTF-8. أما الملفات التي يتجاوز حجمها 10 MB والملفات الثنائية فعلًا فتظل تُرفض كملفات ثنائية.

الإعدادات

ملفات بدء تشغيل الـ shell والأوامر غير التفاعلية

تشغّل استدعاءات الطرفية التي يجريها الوكيل الـ shell الخاص بك بشكل غير تفاعلي — فلا يوجد TTY ولا إنسان أمام الـ prompt. وقد تتسبب عمليات تهيئة الـ shell الثقيلة أو التفاعلية، التي لا تلاحظها أبدًا في الطرفية العادية، في تعطيل كل أمر ينفّذه الوكيل أو إبطائه بشدة:

  • التهيئة البطيئة (nvm، ومديرو الإصدارات، والـ prompts التي تتصل بالشبكة): يضيف تحميل nvm.sh بالطريقة التقليدية تأخيرًا ملحوظًا إلى كل بدء تشغيل للـ shell، والوكيل يشغّل عددًا كبيرًا من الـ shells. وملفات rc التي تستغرق عدة ثوانٍ تحوّل أمرًا سريعًا مثل git status إلى أمر مهدد بانتهاء المهلة.
  • الأجزاء التي تتوقع وجود TTY: أي شيء في .bashrc/.zshrc يطلب إدخالًا، أو ينفّذ الإلحاق بـ tmux/screen، أو يستدعي read، أو يطبع قائمة، سيجعل الـ shell غير التفاعلي يتوقف معلّقًا — فيبدو الأمر وكأنه يعمل إلى ما لا نهاية ثم تنتهي مهلته.
  • المخرجات غير المشروطة: ملفات rc التي تطبع لافتات عبر echo تلوّث مخرجات كل أمر يتعين على الوكيل تحليلها.

الحل هو الشرط الوقائي القياسي الذي تضعه معظم التوزيعات مسبقًا في أعلى .bashrc — العودة مبكرًا عندما يكون الـ shell غير تفاعلي، مع إبقاء أي شيء ثقيل أو تفاعلي أسفله:

لمستخدمي Zsh: ضع إعدادات تسجيل الدخول فقط في .zprofile والإعدادات التفاعلية فقط في .zshrc؛ واجعل .zshenv في حده الأدنى، لأنه يُنفَّذ مع كل shell بما في ذلك غير التفاعلية. وإذا كان الوكيل يحتاج فعلًا إلى أداة لا يضيفها إلى PATH سوى ملف rc الخاص بك، فصدّر تعديل PATH فوق الشرط الوقائي (تصدير المسارات لا يكلّف شيئًا يُذكر) أو أنشئ رابطًا رمزيًا (symlink) للملف التنفيذي داخل ~/.local/bin.

إذا كانت أوامر الطرفية التي ينفّذها الوكيل تتعلق أو تنتهي مهلتها فورًا بينما تعمل في طرفيتك الخاصة، فإن تهيئة الـ shell هي أول ما يجب الاشتباه فيه.

Docker Backend

حاوية دائمة واحدة مشتركة عبر العملية بأكملها. يبدأ Hermes حاوية واحدة طويلة العمر عند أول استخدام (docker run -d ... sleep infinity) ويوجّه كل استدعاء للطرفية والملفات و execute_code عبر docker exec إلى الحاوية نفسها. وتنتقل تغييرات مجلد العمل، والحزم المثبّتة، وتعديلات البيئة، والملفات المكتوبة في /workspace من استدعاء أداة إلى الذي يليه، عبر /new و /reset والـ subagents التي يُنشئها delegate_task، طوال عمر عملية Hermes. وتُوقف الحاوية وتُزال عند إيقاف التشغيل.

هذا يعني أن Docker backend يتصرف كآلة افتراضية (VM) من نوع sandbox دائمة، لا كحاوية جديدة لكل أمر. فإذا نفّذت pip install foo مرة واحدة، تبقى الحزمة موجودة لبقية الجلسة. وإذا نفّذت cd /workspace/project، فإن استدعاءات ls اللاحقة ترى ذلك المجلد. راجع Configuration → Docker Backend للاطلاع على تفاصيل دورة الحياة الكاملة وعلى الخيار container_persistent الذي يتحكم في بقاء /workspace و /root بعد إعادة تشغيل Hermes.

Vercel Sandbox

تتم المصادقة باستخدام المتغيرات الثلاثة معًا: VERCEL_TOKEN و VERCEL_PROJECT_ID و VERCEL_TEAM_ID. وإعداد access token هذا هو المسار المدعوم لعمليات النشر ولعمليات Hermes العادية طويلة التشغيل على Render و Railway و Docker والمنصات المستضيفة المشابهة. بيئات التشغيل المدعومة هي node24 و node22 و python3.13؛ ويستخدم Hermes افتراضيًا /vercel/sandbox كجذر لمساحة العمل البعيدة.

من داخل مجلد مشروع Vercel مرتبط:

مع container_persistent: true، يستخدم Hermes لقطات Vercel (snapshots) للحفاظ على حالة نظام الملفات عند إعادة إنشاء الـ sandbox للمهمة نفسها. وقد يشمل ذلك بيانات الاعتماد والمهارات وملفات التخزين المؤقت التي يزامنها Hermes داخل الـ sandbox. لا تحفظ اللقطات العمليات الجارية، ولا مساحة معرّفات العمليات (PID space)، ولا هوية الـ sandbox الحية نفسها.

تستخدم أوامر الطرفية التي تعمل في الخلفية مسار العمليات العام غير المحلي في Hermes: إذ تعمل إجراءات spawn و poll و wait و log و kill عبر أداة process العادية ما دام الـ sandbox حيًا، لكن Hermes لا يوفّر استعادة أصلية لعمليات Vercel المنفصلة (detached) بعد التنظيف أو إعادة التشغيل.

اترك container_disk دون تعيين أو على القيمة الافتراضية المشتركة 51200؛ فتخصيص حجم القرص غير مدعوم في Vercel Sandbox وسيؤدي إلى فشل التشخيص أو إنشاء الـ backend.

أمان الحاويات

تعمل جميع backends الحاويات مع تحصينات أمنية:

  • نظام ملفات جذري للقراءة فقط (Docker)
  • إسقاط جميع Linux capabilities
  • منع تصعيد الصلاحيات
  • حدود لعدد العمليات (256 عملية)
  • عزل كامل لمساحات الأسماء (namespaces)
  • مساحة عمل دائمة عبر volumes، لا عبر طبقة جذرية قابلة للكتابة

يمكن اختياريًا تمرير قائمة سماح (allowlist) صريحة لمتغيرات البيئة إلى Docker عبر terminal.docker_forward_env، لكن المتغيرات المُمرَّرة تكون مرئية للأوامر داخل الحاوية، ويجب اعتبارها مكشوفة لتلك الجلسة.

إدارة العمليات في الخلفية

ابدأ عمليات في الخلفية وأدِرها:

يتيح وضع PTY (pty=true) تشغيل أدوات CLI التفاعلية مثل Codex و Claude Code.

تحتفظ أوامر الخلفية المكتملة بحالة خروجها ومخرجاتها الملتقطة داخل الـ profile النشط. استأنف المحادثة التي أطلقت الأمر (أو امتدادها المضغوط)، ثم استخدم session_id الأصلي مع process(action="log") للحصول على المخرجات و process(action="poll") للحصول على حالة الخروج. لا يمكن للمحادثات غير المرتبطة، ولا للطلبات التي لا ترتبط بجلسة مالكة، قراءة الإيصالات المحفوظة، حتى مع امتلاك معرّف العملية الدقيق. كما يتضمن process(action="list") النتائج المحفوظة للمهمة أو المحادثة الحالية.

يحتفظ Hermes بأحدث 64 نتيجة مكتملة، لمدة تصل إلى 7 أيام بعد الاكتمال، داخل logs/process-results/ في مجلد Hermes الرئيسي الخاص بالـ profile. ويحتوي كل إيصال على ذيل المخرجات المتجدد بحد أقصى 200,000 حرف كما هو معمول به حاليًا، مع تطبيق قواعد حجب الأسرار الخاصة بالطرفية دائمًا، حتى عند تعطيل حجب المخرجات الحية. وتنتهي صلاحية الإيصالات عند عمليات قراءة النتائج أو كتابتها اللاحقة. لا تعيد الاستعادة تشغيل الأوامر ولا تعيد إرسال إشعارات الاكتمال. وهذا يحفظ العمل الذي اكتمل بينما كانت العملية الأم حية؛ لكنه لا يُبقي العمليات الفرعية غير المكتملة حية بعد انتهاء المهلة أو حدوث عطل.

دعم Sudo

في جلسة أم تفاعلية، تستخدم أوامر sudo المدعومة موجّه إدخال كلمة المرور المُقنَّع (ويُخزَّن مؤقتًا طوال الجلسة). ويشمل ذلك مسارات الملفات التنفيذية المطلقة أو المقتبسة حرفيًا، وبادئات env مع الخيارات والتعيينات العادية، مثل env -u UNUSED /usr/bin/sudo id. أما sudo بدون كلمة مرور فلا يحتاج إلى موجّه إدخال. ويمكنك أيضًا ضبط SUDO_PASSWORD في ملف .env الخاص بالـ profile على جهاز الوكيل.

لا يفسّر مُعيد كتابة كلمة المرور حمولات الـ shell مثل bash -c 'sudo id'، ولا السلاسل المقسّمة عبر env -S، ولا مسارات الملفات التنفيذية الديناميكية، ولا خيارات env غير المعروفة. استدعِ sudo مباشرةً عندما تحتاج إلى موجّه الإدخال التفاعلي. ولا تغيّر هذه المعالجة قواعد الموافقة ولا الحماية من كلمات مرور sudo التي يقدّمها الوكيل.

لا تستطيع الـ subagents المفوَّضة فتح موجّه لإدخال كلمة المرور: إذ لا يتوفر لعملها المتزامن قناة متسلسلة لإدخال كلمة المرور من قِبل إنسان. نفّذ الأمر في الجلسة الأم بدلًا من ذلك، أو وفّر SUDO_PASSWORD محليًا. ولا تملك جلسات المراسلة والجلسات بدون واجهة (headless) قناة آمنة للرد بكلمة المرور؛ فلا ترسل كلمات المرور في المحادثة أبدًا.

تحذير

على منصات المراسلة، إذا فشل sudo، تتضمن المخرجات تلميحًا لإضافة SUDO_PASSWORD إلى ~/.hermes/.env.

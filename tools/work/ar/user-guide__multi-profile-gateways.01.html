أي الـ profiles تُخدَم

يخدم gateway.multiplex_profiles: true الـ profile الافتراضي إضافة إلى كل profile مسمّى حيّ تحت profiles/ — لا توجد قائمة استثناء لكل profile. (مفتاح gateway.multiplex_profile_allowlist السابق أُلغي؛ يزيله ترحيل الإعدادات من config.yaml، وأي profile لا تريد خدمته يُؤرشَف أو يُحذَف بدلًا من ذلك — hermes profile delete <name>، أو انقل الدليل خارج profiles/.) تترك الـ profiles المحذوفة شاهدًا (tombstone) ولا تُعدَّد أبدًا؛ ولا يُعاد إنشاء profile اختفى دليله أبدًا من قِبل دور مخدوم، أو مؤقّت cron، أو توجيه السجلات.

تتحكم المجموعة المخدومة في بادئات /p/<profile>/ الخاصة بـ API وwebhook، وحالة التشغيل، وأهلية توجيه الـ profile، وأي profiles يجريها مجدوِل cron داخل العملية (يعدّد مؤقّت backend الخاص بـ Desktop المجموعة نفسها ويتنحّى لأي profile تخدمه بالفعل بوابة مضاعِفة (multiplexer) عاملة أو بوابته الخاصة). أي مضاعِف بُدئ بـ hermes -p <name> gateway run يجري دائمًا مخزن cron الخاص بـ profile نفسه أيضًا.

المجموعة المخدومة حيّة. يُخدَم profile أُنشئ أثناء تشغيل المضاعِف (hermes profile create، أو لوحة التحكم، أو Desktop، أو TUI) فورًا: يُرسل المنشئ إشارة إلى المضاعِف عبر مقبس التحكم (control socket) الخاص به، كما يعيد المضاعِف فحص profiles/ كل 30 ثانية كإجراء أمان إضافي. تُبنى محوّلات الـ profile الجديد بمجرد أن يحمل config.yaml/.env الخاص به رمز بوت (عادةً ما ينشئ المنشئون أولًا، ثم يضيفون الرمز)، ويُحدَّث served_profiles في gateway_state.json الخاص بالـ profile الافتراضي، ويبلّغ hermes -p <name> gateway status عن أنه مخدوم — من دون إعادة تشغيل، ودون المساس بمحوّلات الـ profiles الأخرى وأدوارها الجارية. يوقف حذف profile محوّلاته ويلغي توجيهها بالطريقة نفسها. تظل قاعدة رمز واحد لكل مستطلِع (poller) سارية: يُوقَف profile أُضيف على عجل ويعيد استخدام رمز profile آخر جانبًا بخطأ duplicate_credential، ولا يُشغَّل أبدًا كمستطلِع ثانٍ.

توجيه محادثات البوت المشتركة إلى الـ profiles (profile_routes)

يختار الـ multiplexing profile لكل بيانات اعتماد (رمز البوت الخاص بكل profile) أو لكل بادئة رابط (URL prefix) (/p/<profile>/ لمنصات HTTP). عندما تشترك عدة مجتمعات في بوت واحد — على سبيل المثال بوت Discord واحد يخدم عدة خوادم (guilds) — يمكنك إضافةً إلى ذلك توجيه خوادم/قنوات/خيوط محددة إلى profiles مختلفة عبر gateway.profile_routes:

تُطابَق المسارات من الأكثر تحديدًا فالأقل (thread_id > chat_id > guild_id)، ويجب أن تتحقق كل الحقول المعلَنة (AND)، ويطابق مسار مربوط بقناة أيضًا الخيوط/منشورات المنتدى التي تكون تلك القناة أصلها. تبقى الرسائل التي لا تطابق أي مسار على الـ profile الافتراضي/النشط. يحصل الـ profile الموجَّه إليه على العزل الكامل لكل profile الموصوف أعلاه (الإعدادات، والمهارات، والذاكرة، وبيانات الاعتماد، ونطاق اسم الجلسة). يعمل التوجيه على كل محوّل منصة، وليس Discord فقط.

لا ينطبق المسار إلا على الرسائل التي يستقبلها بوت الـ profile الافتراضي ما لم يسمِّ بوتًا آخر بـ bot_profile: <profile>. تستخدم رسائل Telegram المباشرة (DM) chat_id نفسه لكل بوت (معرّف المستخدم)، لذا من دون هذا فإن مسار chat_id مقصودًا للبوت المشترك سيلتقط أيضًا رسائل ذلك المستخدم المباشرة مع بوت مخصص تابع لـ profile ثانوي. تبقى الرسائل الواصلة إلى بوت خاص بـ profile ثانوي داخل ذلك الـ profile:

يُحسَم التفويض لرسالة موجَّهة دائمًا بواسطة profile البوت المستقبِل (رمزه وقائمة سماحه)، بما في ذلك المتابَعات المرسَلة أثناء انشغال الوكيل والفحوص أثناء الدور مثل /topic أو /stop؛ ولا يحتاج الـ profile الموجَّه إليه نفسه أي نسخة من قائمة السماح. يتلقى profile موجَّه إليه لا يملك بوتًا خاصًا به أيضًا الإشعارات الخلفية (اكتمالات العمليات، والنبضات، ونتائج التفويض غير المتزامن) عبر البوت المشترك بعد إعادة تشغيل الـ gateway.

على WhatsApp وWhatsApp Cloud، يطابق مسار chat_id عبر أشكال هوية المستخدم المختلفة: رقم هاتف مجرد (15551234567)، وJID (15551234567@s.whatsapp.net)، وLID (…@lid) — كلها تشير إلى الشخص نفسه بمجرد أن يقرنها الجسر (bridge) (نفس التحويل القانوني (canonicalization) الذي تستخدمه مفاتيح جلسات المطابقة وقوائم سماح المحوّل بالفعل). يمكنك وضع رقم الهاتف في profile_routes وستظل الرسائل المباشرة الواردة تطابق سواء سلّم WhatsApp JID أو LID. من دون ربط LID بعد، يظل شكل الرقم يطابق JID (تُحذَف اللاحقة) لكنه لا يستطيع حل LID مجهول — يسقط ذلك الوارد عندئذٍ إلى الـ profile الافتراضي إلى أن يظهر الربط. محادثات المجموعات (…@g.us) ليست هويات مرسِل وتظل تطابق تمامًا. تبقى معرّفات Telegram الرقمية دون تغيير.

يتطلب profile_routes وجود gateway.multiplex_profiles: true؛ ومع إيقاف الـ multiplexing تُتجاهَل المسارات. إذا طابق مسار صريح لكنه يستهدف profile غير مثبَّت (أو محذوف)، ترفض الـ gateway ذلك الوارد وتسجّل المسار والهدف. ولا تُشغِّل الـ profile الافتراضي. أما الحركة التي لا تطابق أي مسار فتحافظ على السلوك الافتراضي التاريخي للـ profile.

تُسلَّم مهام cron التي يملكها profile موجَّه إليه عبر البوت المشترك أيضًا، لكن فقط للأهداف التي يربطها مسار مفعَّل بـ chat_id/thread_id بذلك الـ profile (يؤهِّل مسار guild_id + chat_id قناته) — لا تُرسَل أبدًا مهمة لـ profile موجَّه إليه تستهدف محادثة غير موجَّهة (أو محادثة موجَّهة إلى profile آخر) عبر البوت المشترك. لا تؤهِّل المسارات المقتصرة على guild فقط هدف cron؛ أضف مسار chat_id لقناة التسليم. لا يحتاج الـ profile الموجَّه إليه إلى قسم platforms.<platform> الخاص به لهذا: يأتي تفويض البوت المشترك من المسار، لا من إعدادات القمر الصناعي (satellite).

أمان تعارض الرموز

يجب أن يستخدم كل profile رموز بوت فريدة لكل منصة. إذا شارك profileان رمز Telegram أو Discord أو Slack أو WhatsApp أو Signal، ترفض الـ gateway الثانية البدء برسالة خطأ تسمّي الـ profile المتعارض. تحت الـ multiplexing تُوقِف نفس القاعدة محوّل الـ profile المكرَّر فقط بينما تستمر الـ gateway المشتركة في العمل.

تسمية الـ Branches

قبل الإرسال

  1. شغّل الاختبارات: scripts/run_tests.sh لمطابقة بيئة CI. لا تستخدم python -m pytest ... مباشرةً إلا حين يكون السكربت المُغلِّف غير متاح أو حين تتعمّد تصحيح الأخطاء خارجه.
  2. اختبر يدويًا: شغّل hermes وجرّب مسار الكود الذي غيّرته
  3. تحقّق من الأثر عبر المنصات: ضع في اعتبارك macOS و Linux و WSL2 و Windows الأصلي. إذا كنت تعدّل عمليات إدخال/إخراج الملفات، أو إدارة العمليات، أو التعامل مع الطرفية، أو العمليات الفرعية، أو الإشارات، فشغّل scripts/check-windows-footguns.py.
  4. اجعل الـ PRs مركّزة: تغيير منطقي واحد لكل PR
  5. تغييرات الـ prompt أو مخطط الأداة (tool schema): إذا فشل tests/ci/test_prompt_surface.py، فهذا يعني أن تغييرك يعدّل system prompt أو مخطط أداة ترسله كل جلسة. أعد التوليد باستخدام scripts/run-in-hermes-env python scripts/ci/prompt_surface.py render ثم نفّذ commit للّقطة (snapshot). تحتاج التغييرات هناك إلى موافقة أحد المشرفين (راجع Prompt Assembly).
  6. مفاتيح إعدادات جديدة أو slash commands جديدة: إذا فشل tests/ci/test_docs_drift.py، فهذا يعني أن مفتاح DEFAULT_CONFIG أو slash command أضفته بلا توثيق. اذكر المفتاح بصيغته المنقوطة (agent.max_turns) أو اعرضه في مثال YAML ضمن website/docs/ (عادةً user-guide/configuration.md)، وأضف slash commands إلى reference/slash-commands.md. وإذا كان المفتاح يجب فعلًا أن يبقى بلا توثيق، فإن python scripts/ci/check_docs_drift.py --update يضيفه إلى scripts/ci/docs_drift_baseline.json حيث يراه المراجعون. أما المفاتيح التي كانت غير موثّقة عند إضافة هذا الفحص فهي مسجّلة أصلًا في baseline؛ ولن يفشل الفحص أبدًا عند توثيق أحدها.

  • كيفية اختباره خطوة بخطوة

أمثلة:

قوائم مراجعة محلية داخل المستودع: .agents/checks/*.md

يمكن للمشاريع المبنية على Hermes (أو التي يراجعها Hermes) الاحتفاظ بقوائم تحقق للمراجعين داخل المستودع ضمن .agents/checks/. كل ملف هو قائمة تحقق مركّزة بصيغة markdown عادية، يحمّلها الوكيل قبل مراجعة أي تغيير يمسّ المجال المطابق:

أعراف تجعل هذه القوائم تعمل جيدًا:

  • اهتمام واحد لكل ملف، ويُسمّى الملف باسم ذلك الاهتمام. فالملفات الصغيرة تُقرأ كاملة، أما ملف checklist.md الضخم فيُقرأ على عجل.
  • اكتب الفحوصات كإجراءات قابلة للتحقق («شغّل X وتأكد من Y»)، لا كتطلعات («يجب أن يكون الكود آمنًا»).
  • اذكر شرط التطبيق في أعلى الملف — أي المسارات أو أنواع التغييرات التي تنطبق عليها القائمة — كي يتمكن الوكيل (أو الإنسان) من تخطّي غير المتعلّق منها بسهولة.
  • احفظها في نظام التحكم بالإصدارات بجوار الكود الذي تحرسه: فهي تتطور مع قاعدة الكود، والـ PR الذي يغيّر القواعد يغيّر قائمة التحقق في الـ diff نفسه.

حين تطلب من Hermes مراجعة PR في مستودع يحتوي على .agents/checks/، اطلب منه (أو علّمه عبر مهارة) أن يقرأ قوائم التحقق ذات الصلة أولًا وأن يقدّم تقريره وفقًا لها. يمنح هذا وكلاء المراجعة المعيار الخاص بالمشروع الذي تغفله الـ prompts العامة للمراجعة.

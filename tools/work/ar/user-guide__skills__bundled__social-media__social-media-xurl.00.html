xurl — واجهة X (Twitter) API عبر الأداة الرسمية للسطر

xurl هي أداة سطر الأوامر الرسمية من منصة مطوّري X للتعامل مع X API. تدعم أوامر مختصرة للإجراءات الشائعة، إضافة إلى وصول خام بأسلوب curl إلى أي endpoint من الإصدار v2. تُعيد جميع الأوامر ناتجًا بصيغة JSON إلى stdout.

استخدم هذه المهارة من أجل:

  • النشر، الرد، الاقتباس، وحذف المنشورات
  • البحث عن منشورات خام (بيانات المنشور الفعلية بصيغة JSON مع المعرّفات التي يمكنك التفاعل معها) وقراءة الخط الزمني والإشارات
  • الإعجاب، إعادة النشر، الحفظ في المفضلة
  • المتابعة، إلغاء المتابعة، الحظر، الكتم
  • الرسائل المباشرة
  • رفع الوسائط (صور وفيديو)
  • الوصول الخام إلى أي endpoint من X API v2
  • سير عمل متعدد التطبيقات / متعدد الحسابات

تحل هذه المهارة محل مهارة xitter الأقدم (التي كانت تُغلّف أداة Python من طرف ثالث). يصون فريق منصة مطوّري X أداة xurl، وهي تدعم OAuth 2.0 PKCE مع تحديث تلقائي للرموز، وتغطي مساحة أكبر بكثير من الـ API.

سلامة الأسرار (إلزامي)

قواعد حاسمة عند العمل داخل جلسة وكيل/LLM:

  • لا تقم أبدًا بقراءة أو طباعة أو تحليل أو تلخيص أو رفع أو إرسال ~/.xurl إلى سياق LLM.
  • لا تطلب أبدًا من المستخدم لصق بيانات الاعتماد/الرموز في المحادثة.
  • يجب على المستخدم ملء ~/.xurl بالأسرار يدويًا على جهازه الخاص. في Docker، يجب أن يكون هذا هو ~ الذي تراه العمليات الفرعية لأدوات Hermes؛ راجع ملاحظة Docker أدناه.
  • لا تُوصِ أو تُنفّذ أبدًا أوامر مصادقة تحتوي أسرارًا مضمّنة داخل جلسات الوكيل.
  • لا تستخدم أبدًا --verbose / -v في جلسات الوكيل — فقد يكشف ذلك رؤوس المصادقة/الرموز.
  • للتحقق من وجود بيانات الاعتماد، استخدم فقط: xurl auth status.

الخيارات المحظورة في أوامر الوكيل (لأنها تقبل أسرارًا مضمّنة): --bearer-token, --consumer-key, --consumer-secret, --access-token, --token-secret, --client-id, --client-secret

يجب أن يقوم المستخدم يدويًا، خارج جلسة الوكيل، بتسجيل بيانات اعتماد التطبيق وتدويرها. بعد تسجيل بيانات الاعتماد، يُصادق المستخدم عبر xurl auth oauth2 — أيضًا خارج جلسة الوكيل. تُخزَّن الرموز في ~/.xurl بصيغة YAML. لكل تطبيق رموزه المعزولة الخاصة. تتحدث رموز OAuth 2.0 تلقائيًا.

خطأ شائع: إذا أغفلت --app my-app عند تنفيذ xurl auth oauth2، يُحفظ رمز OAuth في ملف التطبيق المدمج default — الذي لا يملك client-id أو client-secret. ستفشل الأوامر بأخطاء مصادقة رغم أن تدفّق OAuth بدا ناجحًا. إذا واجهت ذلك، أعد تنفيذ xurl auth oauth2 --app my-app ثم xurl auth default my-app.

خطأ HOME في Docker: في تخطيط Hermes Docker الرسمي، يمثّل /opt/data متغير HERMES_HOME، لكن العمليات الفرعية لأدوات Hermes تستخدم /opt/data/home كقيمة لـ HOME. هذا يعني أن ~/.xurl يُحلّ إلى /opt/data/home/.xurl بالنسبة لأوامر xurl التي يُشغّلها Hermes، لا إلى /opt/data/.xurl. نفّذ إعداد المستخدم بنفس قيمة HOME:

إذا نجح HOME=/opt/data xurl auth status بينما لا يُظهر HOME=/opt/data/home xurl auth status أي تطبيقات أو رموز، فلن ترى استدعاءات أدوات Hermes بيانات الاعتماد.

معالجة الأخطاء

  • رمز خروج غير صفري عند أي خطأ.
  • تُطبع أخطاء الـ API أيضًا بصيغة JSON إلى stdout، بحيث يمكنك تحليلها.
  • أخطاء المصادقة ← اطلب من المستخدم إعادة تنفيذ xurl auth oauth2 خارج جلسة الوكيل.
  • الأوامر التي تحتاج معرّف مستخدم المتصل (like، repost، bookmark، follow، إلخ) تجلبه تلقائيًا عبر /2/users/me. أي فشل مصادقة هناك يظهر كخطأ مصادقة.

سير عمل الوكيل

  1. تحقق من المتطلبات الأساسية: xurl --help و xurl auth status.
  2. قبل استخدام xurl search، تحقق من القصد. الجأ إليه عندما تحتاج المهمة إلى كائنات منشورات فعلية، أو سياق الحساب المُصادق عليه، أو عندما تُفضي إلى إجراء كتابة على X — فهو الوسيلة المناسبة عندما يريد المستخدم منشورات يمكنه التفاعل معها، لا مجرد ملخّص عن موضوع.
  3. تحقق من أن التطبيق الافتراضي يملك بيانات اعتماد. حلّل ناتج auth status. يُميَّز التطبيق الافتراضي بالرمز ▸. إذا كان التطبيق الافتراضي يُظهر oauth2: (none) بينما يملك تطبيق آخر مستخدم oauth2 صالحًا، أخبر المستخدم بتنفيذ xurl auth default <that-app> لإصلاح ذلك. هذا هو خطأ الإعداد الأكثر شيوعًا — يضيف المستخدم تطبيقًا باسم مخصص لكنه لا يضبطه كافتراضي أبدًا، فتستمر xurl في محاولة استخدام ملف default الفارغ.
  4. إذا كانت المصادقة مفقودة تمامًا، توقّف ووجّه المستخدم إلى قسم "إعداد المستخدم لمرة واحدة" — لا تحاول تسجيل التطبيقات أو تمرير الأسرار بنفسك.
  5. ابدأ بعملية قراءة رخيصة (xurl whoami، xurl user @handle، xurl search ... -n 3) للتأكد من إمكانية الوصول.
  6. تأكد من المنشور/المستخدم المستهدف ومن نيّة المستخدم قبل أي إجراء كتابة (نشر، رد، إعجاب، إعادة نشر، رسالة مباشرة، متابعة، حظر، حذف).
  7. ناتج أمر xurl فقط (أو استجابة X API الخام) هو ما يُثبت وقوع إجراء غيّر حالة X. لا تُبلغ أبدًا بأن عملية كتابة قد تمّت استنادًا إلى أي مصدر آخر — نتائج بحث، ملخصات، أو سياق سابق.
  8. استخدم ناتج JSON مباشرة — كل استجابة مُهيكلة أصلًا.
  9. لا تلصق أبدًا محتوى ~/.xurl في المحادثة.

ملاحظات

  • حدود المعدل: يفرض X حدود معدل لكل endpoint. الرمز 429 يعني الانتظار وإعادة المحاولة. لدى endpoints الكتابة (النشر، الرد، الإعجاب، إعادة النشر) حدود أضيق من القراءة.
  • النطاقات (Scopes): تستخدم رموز OAuth 2.0 نطاقات واسعة. عادة ما يعني الرمز 403 على إجراء محدد أن الرمز يفتقد نطاقًا — اطلب من المستخدم إعادة تنفيذ xurl auth oauth2.
  • تحديث الرمز: تتحدث رموز OAuth 2.0 تلقائيًا. لا شيء تفعله.
  • تطبيقات متعددة: لكل تطبيق بيانات اعتماد/رموز معزولة. بدّل باستخدام xurl auth default أو --app.
  • حسابات متعددة لكل تطبيق: اختر باستخدام -u / --username، أو اضبط افتراضيًا باستخدام xurl auth default APP USER.
  • تخزين الرموز: ~/.xurl بصيغة YAML. في Docker، استخدم HOME الخاص بالعمليات الفرعية لـ Hermes (/opt/data/home في الصورة الرسمية) بحيث تستقر الرموز تحت /opt/data/home/.xurl. لا تقرأ هذا الملف أو ترسله إلى سياق LLM أبدًا.
  • التكلفة: عادة ما يكون الوصول إلى X API مدفوعًا للاستخدام الفعلي. كثير من الأعطال هي مشاكل خطة/صلاحية، لا مشاكل كود.

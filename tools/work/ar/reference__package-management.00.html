إدارة الحزم

hermes pm يدير ملفات أدوات Hermes التنفيذية وبيئات اعتماديات Python. وليس أداة تحديث التطبيق. استخدم طريقة التحديث الخاصة بالتثبيت لتحديث Hermes نفسه.

الإصدارات المثبّتة وحالة التثبيت واختيار وقت التشغيل

لكل ملف دور مستقل:

الملفالدور
pm/lock.jsonإصدارات دقيقة للأدوات المُدارة، وعناوين URL خاصة بالهدف، وبصمات SHA-256.
pm/pyproject.toml و pm/uv.lockمتطلبات Python المستقلة الخاصة بمدير الاعتماديات، ونتيجة حل الاعتماديات المقفلة.
pyproject.toml و uv.lockمتطلبات Python والإضافات (extras) ومؤشرات المنصة ونتيجة حل اعتماديات Python المعتمدة في المستودع.
مخزن الأدوات: facts.jsonعناصر الأدوات المثبّتة وهوياتها ومتغيرات البيئة التي تصدّرها وبصمات الملفات الفعلية.
لكل تثبيت: facts.jsonبيئة Python المختارة، وبصمة مدخلاتها، والإضافات (extras) المفعّلة.
الحمولة: manifest.jsonتخطيط الحمولة النسبي، وعقد الإطلاق المكتمل من أداة بناء الحزمة.
install-stamp.jsonمنشأ البناء، والجهة المعلَنة المالكة للتوزيع/التحديث.

لا يثبت عنصر في ملف قفل أن حزمةً مثبّتة. ويقارن hermes pm doctor حالة التثبيت بالقفل ويتحقق من البايتات الفعلية. ويستخدم بدء التشغيل تحققًا أقل تكلفةً. ولا يستعلم عن أحدث الإصدارات الأصلية عند كل إطلاق. وفي تثبيتات المصدر المدارة ذاتيًا، يقارن مُشغّل ما قبل الاستيراد بصمة نجاح الاعتماديات المسجَّلة في PM بالمدخلات الحالية. وتؤدي حالة اكتمال مفقودة أو متقادمة إلى مزامنة، ثم يُعاد تشغيل الأمر نفسه على Python المُدار قبل تحميل اعتماديات التطبيق. وتحتفظ المزامنات الفاشلة بالاختيار السابق وتُعاد محاولتها عند الإطلاق التالي؛ ولا يلزم وسم تحديث معلّق. وتحتفظ النسخ المسحوبة للمطوّرين والتثبيتات المحزّمة بجهتها المالكة الحالية.

قد تواصل أدوات التحديث التاريخية تنفيذ كود Python القديم بعد استبدال شجرة المصدر. وتبدأ نقاط دخول التوافق عملية فرعية جديدة، وتنتظر اكتمالها، وتعيد حالة خروجها. وتطلب تهيئة العملية الفرعية من PM تجهيز الأدوات المطلوبة واختيار جيل Python قبل استيرادات التطبيق. ويعمل الإكمال في ذلك المفسّر مع سياق التحديث وإيصاله. ولا يمسح الأصل sys.modules ، أو يستورد مخطط التطبيق الجديد، أو يستأنف بديلًا احتياطيًا عبر pip.

تسلّم تحديثات المصدر الحالية النسخة المسحوبة المختارة إلى جهة إكمال مالكة جديدة. وتعطّل Python الخاصة بالتهيئة الأولية تهيئة site-packages قبل طلب مزامنة الإضافات (extras) المسجَّلة والإضافات المفعّلة من PM. ثم تتولى Python المختارة أبنية الواجهة الأمامية وصيانة profiles/الإعدادات وإعادة تشغيل gateways والتحقق من وقت التشغيل. وتستخدم Git وإعادات المحاولة عند حداثة النسخة بالفعل والبديل الاحتياطي ZIP المسار نفسه. ويحتفظ الأمر الأصلي بقفل التحديث أثناء الانتظار؛ ولا يمكن لنتيجة إكمال مفقودة أو فاشلة الإبلاغ عن النجاح. وتبقى أخطاء PM المرتبطة في إيصال التحديث، وتحتفظ إعادات التشغيل المنقطعة بالتزامها تجاه مجموعة النُسخ. ولا تُعاد محاولة أخطاء الاعتماديات أو البناء عبر pip أو إعادة تنزيل المصدر أبدًا. استخدم hermes pm repair لملفات الاعتماديات التالفة. راجع ملاحظة ملكية إكمال تحديث المصدر للمطوّرين.

تثبيتات المصدر والأبنية المحزّمة

تجهّز مُثبّتات المصدر الأدوات المطلوبة مع Python. وتختار إضافة Python all. وتُثبَّت الأدوات الاختيارية المسمّاة عند طلبها.

للتثبيت المعتمد من المصدر، يتحقق Desktop من مُشغّل التثبيت المنشور وينفّذه. ويتولى PM مفسّره واختيار اعتمادياته. ولا يستبدل Desktop ذلك الأمر بمسار venv تخميني. وتحتفظ تجاوزات المطوّرين بمفسّرها المختار.

تجهّز حزم Desktop الأصلية مجموعة الأدوات المدعومة وكل إضافات Python المتوافقة مع الهدف قبل التحزيم. ولا يُعدّ --extra all و --all-extras مترادفين. وتظل مؤشرات المنصة تستثني الاعتماديات التي لا تستطيع العمل على الهدف.

تجمع أداة بناء Desktop الكاملة PM مع مزوّدي تحزيم Node/التحزيم الأصلي. ومن نسخة مسحوبة نظيفة عند release tag، يجهّز python scripts/bundles/desktop.py --tag vX.Y.Z الاعتماديات ويبني المُثبّت. أضف --prepare-only للتوقف بعد التجهيز؛ واستهلك نتيجته المحلية للمهمة باستخدام python scripts/bundles/desktop.py --prepared .build/desktop-job/prepared.json. ويختار --work و --cache جذرين مستقلين يملكهما البناء. وتنشئ مرحلة التجهيز مجلد العمل، لا المستدعي. ويمكن أن يحلّ SHA كامل لـ commit محل tag عبر --commit ؛ ويجب أن تطابقه النسخة المسحوبة.

يستخدم التجهيز حالة PM معزولة وأدوات مثبّتة الإصدار وبيئات Python جديدة مرتبطة بالمسار واتحاد مساحات عمل JS الكامل و native bindings وأدوات التحزيم. ومخابئ الاعتماديات القابلة لإعادة الاستخدام ليست تثبيتات حية أو بيئات افتراضية قابلة للنقل. وتربط النتيجة المجهَّزة المصدر والهدف والمسارات؛ وتفشل عملية استهلاكها عند فقد المدخلات أو تغييرها بدلًا من إطلاق تنزيل. أعد التجهيز بعد نقل أو تغيير المدخلات. ولا يزال بإمكان التوقيع والتوثيق استخدام الشبكة. راجع دليل بناء Desktop لمتطلبات المُصرّف الأصلي وحدود التحقق من الإصدار.

الحمولة الأساسية لتطبيق محزّم غير قابلة للتغيير. ويشغّل Hermes backend الخاص به منها، بدلًا من نسخ نسخة مصدر مسحوبة عند أول إطلاق. وتتحقق أداة بناء الحزمة من ملفاتها وتكتب مسارات الإطلاق في بصمة بناء Desktop. ويستخدم Electron تلك المسارات دون فحص الحمولة أو إصلاحها. ويمكن لأدوات إضافية مثبّتة الإصدار استخدام مخزن الأدوات القابل للكتابة. وتستخدم إضافات Python بيئةً كاملة قابلةً للكتابة خارج الحزمة الموقَّعة. ويحتفظ جيلها الأول بالإضافات (extras) المشحونة مع المتطلبات الجديدة. وتستخدم الأجيال اللاحقة اختيار الإضافات المسجَّل أساسًا لها.

يستخدم Termux بناء bionic مستقلًا وحزمة APT محكمة. ويدمج Docker وقت تشغيله في الصورة ويعطّل تثبيت الاعتماديات عند الطلب. ويوفّر Nix وقت تشغيله عبر derivations. راجع أدلة Termux و Docker و Nix لمعرفة حدودها.

الحالة القابلة للكتابة

جذر البيانات الافتراضي للمنصة هو ~/.hermes على POSIX، و %LOCALAPPDATA%\hermes على Windows. ويمكن لـ HERMES_HOME و profiles تغيير جذر البيانات الذي تستخدمه العملية.

الحالةالموقع الافتراضي
عناصر أدوات مشتركة قابلة للكتابةtools/ تحت جذر Hermes الافتراضي المحدَّد.
تنزيلات قابلة للاستئنافcache/partials/ تحت ذلك الجذر، لا داخل حمولة موقَّعة.
الاختيار والسجل لكل تثبيتinstalls/INSTALL_KEY/ تحت جذر حالة الاعتماديات.
أجيال Pythoninstalls/INSTALL_KEY/environments/.
إيصالات المزامنة والتحديثlogs/update_receipts/ تحت المجلد الرئيسي النشط.

يُشتق مفتاح التثبيت من المسار المعتمد للمصدر أو مستودع الحمولة. ولذلك تملك النسخ المسحوبة المستقلة اختيارات Python مستقلة. ويمكن لـ profiles التي تشترك في تثبيت إضافة اعتماديات إلى البيئة نفسها. وتظل إعداداتها وبيانات اعتمادها محصورة في نطاق كل profile.

لا تعدّل معلومات الحالة أو مسارات الأجيال يدويًا. وتحدّد المُشغّلات البيئة المختارة قبل استيرادات الجهات الخارجية. وتحتفظ العمليات باستيراداتها القائمة حتى إعادة تشغيلها. وتحافظ عملية جمع الموارد غير المستخدمة على الأجيال المختارة، والأجيال المدارة بعقود التي لديها قرّاء أحياء.

تشترك التنزيلات في قفل لكل عنوان URL جزئي. ولا يمكن لنقل فاشل أو معلّق نشر وجهة جزئية، ولا يمكن لجمع الموارد غير المستخدمة حذف ملفات نقل حي. ولا يعيد الاستئناف استخدام النطاقات إلا عندما يظل طولها المسجَّل ومدقّقها وبصمتها الاختيارية مطابقًا. ودون ETag قوي أو بصمة مثبّتة، يبدأ النقل المنقطع من جديد بدلًا من خلط إصدارات مختلفة. وتبقى ملفات .locks/ الصغيرة بعد الاكتمال كي تستخدم العمليات المنتظرة القفل نفسه.

اعتماديات Python الاختيارية والإضافات

تطلب ميزة مدمجة إضافة مشروع عبر pm.ensure_import. وتعلن إضافات المجلدات متطلبات Python في pyproject.toml. ودون ملف مشروع مؤلَّف، يجمع PM قائمتي pip_dependencies و python_dependencies القديمتين من plugin.yaml أو plugin.yml. ولا يتجاوز ملف مشروع قديم مولَّد عبر PM تلك القوائم. وتستخدم فحوص الموافقة وعضوية الاعتماديات وحداثتها قارئ الإعلانات نفسه.

يجهّز PM متطلبات النواة والإضافات (extras) المفعّلة ومتطلبات الإضافات (plugins) المفعّلة معًا. ويبدأ الحل من ملف القفل (lock) الحالي. قد تتغير الإصدارات المتعدّية المتوافقة، لكن القيود المعلنة والتثبيتات الدقيقة تبقى ملزمة. يحصل كل مرشّح على مساحة عمل جديدة بمدخلات صريحة للمصدر وبذرة ملف القفل والبيئة المجهّزة. وتبقى مساحة العمل المولَّدة وملف القفل الموسّع خارج المصدر المشحون. تُحَلّ مساحة العمل للمنصة والمعمارية الخاصتين بالمفسّر الذي ستُثبَّت فيه فقط، لذا فإن اعتمادية إضافة لا تتوفر لها حزم wheel لمنصة أخرى (مثل onnxruntime أو torch على Android) لا تعطّلها؛ أما ملف القفل المشحون فيحتفظ بتغطيته الكاملة للمنصات. ويَنسخ الإصلاح مساحة العمل وملف القفل المسجَّلين، بما في ذلك مدخلات بناء الإضافات، بدلًا من الحل مقابل manifests حية جرى تعديلها.

يُرسَل تفعيل الإضافات وتحديثات الكود المجهَّزة كبيانات إلى عامل PM المعزول. وتحت قفل التثبيت، يكتشف اتحاد الاعتماديات المقترح ويتحقق من المرشّح وينشر الإعدادات أو ملفات الإضافة وبياناتها الوصفية مع اختيار البيئة. ويرفض المدخلات التي تغيرت أثناء التجهيز. ويتيح سجل دائم الاستعادة قبل استيرادات التطبيق، بما في ذلك تحديثات الكود وحده التي لا تتطلب بيئة جديدة.

تستخدم تغييرات اختيار الإضافات، بما فيها تفعيل الحِزم، معاملة القبول نفسها. ويقرأ PM أحدث اختيار تحت قفله المشترك قبل تطبيق كل تغيير. ولا يستبدل المرشّح الفاشل البيئة المختارة أو يعطّل إضافات أخرى بصمت. وإذا نجح التجهيز، فقد تظل عملية Hermes الجارية تحتاج إلى إعادة تشغيل لتفعيل البيئة الجديدة.

تحافظ تحديثات تطبيق Hermes العادية على مجلدات إضافات المستخدم. ويمكن لتحديثات الإضافات الصريحة تغيير ملفات الإضافة المختارة. ولا ينضم wrapper بلا إعلان لاعتماديات Python إلى البيئة المشتركة. ويظل sidecar الخارجي الخاص به مملوكًا بصورة مستقلة. راجع دليل الإضافات.

سياسة التثبيت عند الطلب

security.allow_lazy_installs يتحكم في التثبيت عند الطلب. وتظل الاعتماديات المثبّتة بالفعل قابلةً للاستخدام عندما يكون هذا الإعداد false.

أوامر التثبيت الصريحة تختلف عن التثبيت عند الطلب. لكن قائمة ميزات الحزمة المجمدة تظل تقيّد أسماء إضافات Python المطلوبة عندما يكون التثبيت عند الطلب معطّلًا. وقبول الإضافات الصريح عملية مستقلة، لا طلب ميزة عند الطلب. ولا تعتبر هذا الإعداد sandbox أو منعًا شاملًا للتثبيت اليدوي للحزم. ويضبط Docker أيضًا خيار تعطيل التثبيت عند الطلب الداخلي في الصورة.

PM مدير اعتماديات، لا sandbox لكود الإضافات. ويتطلب تثبيت إضافة الثقة فيها وفي اعتمادياتها.

أدوات الأمان الاختيارية

يتولى PM حزم bws و iron-proxy مثبّتة الإصدار في pm/security_packages.py. وتأتي إصداراتها وعناوين URL للأصول وبصمات SHA-256 من pm/lock.json. ويستخدم التنزيل والنشر مخزن الأدوات المشترك، لا مُثبّتات خاصة تحت $HERMES_HOME/bin.

وبالنسبة إلى iron-proxy، يحصل PM أيضًا على ملفات توقيع مثبّتة ويتحقق من أن المجاميع الاختبارية للإصدار تغطي الأرشيف المثبّت. ويستدعي تجهيز الحزمة مدقّق التوقيع الخاص بالتكامل. ويظل فحص GPG مشروطًا بتوفر ملف تنفيذي. ويجب أن تظل ملفات المنشأ المقفلة متاحة ومطابقة لبصماتها. ويوقف رفض توقيع صريح التثبيت. وتظل الملفات التنفيذية الخارجية خارج ضمانات البصمات والتوقيعات في PM.

bws و iron-proxy يراعيان ملفًا تنفيذيًا على PATH قبل فحص اختيار PM. ويخضع التثبيت عند الطلب لسياسة PM. وتفحص أوامر التثبيت الصريحة العناصر المُدارة وتصلحها، بما في ذلك الطلبات باستخدام --force.

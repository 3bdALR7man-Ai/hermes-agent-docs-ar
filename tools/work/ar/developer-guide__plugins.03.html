الاعتماديات المثبّتة يدويًا عبر pip ليست إعلانات PM دائمة. وقد لا تحتفظ بها عملية استبدال بيئة لاحقة. ويمكن لإضافات wrapper التي تظل بيئات Python الخاصة بها خارج PM استخدام عقد بقاء مزوّد الذاكرة. راجع إدارة الحزم لمعرفة تخطيط بيئة التشغيل وسياسة التثبيت الكسول.

للأدوات التي تعتمد على مكتبات اختيارية:

استبدال أداة مدمجة

لاستبدال أداة مدمجة بتنفيذك الخاص (مثلًا استبدال أداة المتصفح الافتراضية بـ backend من نوع headed-Chrome CDP ، أو استبدال web_search بفهرس داخلي مخصص للشركة)، مرّر override=True:

بدون override=True، يرفض السجل أي تسجيل قد يحجب أداة موجودة من toolset مختلفة — وهذا يمنع الاستبدالات العرَضية. استبدال أداة مدمجة يتطلب إضافة إلى ذلك موافقة المشغّل صراحة عبر plugins.entries.<plugin_id>.allow_tool_override: true في config.yaml؛ وبدون هذا التصريح، يُطلق register_tool(override=True) يرفع PluginToolOverrideError. يُسجَّل الاستبدال بحيث يكون قابلًا للتدقيق في ~/.hermes/logs/agent.log. تُحمَّل الإضافات بعد الأدوات المدمجة، لذا يكون ترتيب التسجيل صحيحًا: يستبدل معالِجك المعالِج المدمج.

الإضافات غير المضمّنة تحتاج أيضًا إلى منح من المشغّل. بالنسبة لأي إضافة لا تُشحن مع نواة Hermes (مصدرها المستخدم أو المشروع أو pip)، يتطلب override=True ضد أداة مدمجة موجودة إضافةً إلى ذلك اختيارًا صريحًا لكل إضافة في config.yaml:

بدون هذا المنح، يُطلق ctx.register_tool(..., override=True) يرفع PluginToolOverrideError؛ وبما أن استثناءات register() يلتقطها المحمّل، تُعطَّل الإضافة ويستمر Hermes في العمل. يوجد هذا التقييد لأن إضافة مفعّلة تستبدل بصمت أداة مدمجة ذات صلاحيات مثل shell_exec أو write_file يمكن أن تعترض كل ما يوجّهه النموذج عبرها. الإضافات المضمّنة مُستثناة: فالاستبدال هناك قرار للقائمين على الصيانة. إذا تعذّر تحميل الإعدادات، يفشل هذا التقييد بأمان (fail closed).

لا تعدّل هذا المفتاح يدويًا عادة. hermes plugins enable <name> يسأل ما إذا كان ينبغي منح القدرة فقط عندما يعلنها manifest الإضافة تحت capabilities: (شاشة الموافقة، مع الرفض افتراضيًا)؛ وتُفعّل الإضافة التي لا تعلن أي قدرات دون prompt منح. و --allow-tool-override / --no-allow-tool-override يمنحان الصلاحية أو يسحبانها صراحة في الحالتين، للتثبيتات البرمجية أو للتفويض المسبق لإضافة لم تعتمد كتلة manifest. ويقيد المنح نفسه أيضًا deregister(): فبدونه، لا يمكن لإضافة إزالة أداة لا تملكها (وهو ما كان سيمثّل وسيلة للالتفاف على فحص الاستبدال).

معظم الـ hooks هي مراقبات إطلاق-وتناسَ (fire-and-forget) — تُتجاهَل قيمها المُعادة. الاستثناءان هما pre_llm_call، الذي يمكنه حقن سياق في المحادثة، وpre_tool_call، الذي يمكنه إعادة توجيه حظر/موافقة.

يجب أن تقبل كل الاستدعاءات (callbacks) **kwargs لضمان التوافق المستقبلي. إذا انهار استدعاء hook ، يُسجَّل ويُتجاوز. تستمر بقية الـ hooks والوكيل بشكل طبيعي.

تُطلَق hooks دورة حياة kanban بعد تثبيت تغيير قاعدة بيانات اللوحة، بحيث يرى الاستدعاء دائمًا حالة دائمة ولا يمكنه أبدًا الاحتفاظ بقفل الكتابة الخاص بـ SQLite. ولأن عمّال kanban يعملون كعمليات فرعية منفصلة من نوع hermes -p <profile> chat -q، يُطلَق kanban_task_claimed في عملية الموزّع (dispatcher) بينما تُطلَق kanban_task_completed / kanban_task_blocked في عملية العامل (worker) — استخدم الـ hook في الموزّع لمراقبة كل انتقال مركزيًا، أو في العامل للسياق داخل الجلسة لكل مهمة.

الـ hooks طلب API مراقبات للطلب الخام للمزوّد، بمستوى أدنى من زوج pre_llm_call / post_llm_call زوجًا: يرسل الدور الواحد الذي يستدعي أدوات عدة طلبات API ، وتعمل هذه hooks حول كل طلب. وهي موجودة لإضافات الرصد (التتبع، وحساب التكلفة، ولوحات زمن الاستجابة). والـ request وresponse عبارة عن عروض JSON مُنقّاة ومحدودة الحجم لحمولة المزوّد (المفاتيح الحساسة مُخفاة، والسلاسل الطويلة مقصوصة، وكائنات SDK مُطبَّعة)، وusage هو قاموس ملخّص توكن بسيط. تحمل كل حمولة حقول الربط turn_id, api_request_id, task_id, session_id، وapi_call_count، كي تستطيع الإضافة ربط الطلبات واستدعاءات الأدوات والأدوار معًا. api_request_error يعمل عند رفع استدعاء المزوّد استثناء ويضيف status_code, retry_count / max_retries, retryable, reason، وقاموس error يحتوي على type وmessage.

pre_llm_call حقن السياق

هذا هو الـ hook الوحيد الذي تُهم قيمته المُعادة. عندما يُعيد استدعاء pre_llm_call قاموسًا يحوي مفتاح "context" (أو سلسلة نصية عادية)، يحقن Hermes ذلك النص في رسالة المستخدم للدور الحالي. هذه هي الآلية المستخدمة في إضافات الذاكرة، وتكاملات RAG ، والحواجز الوقائية (guardrails)، وأي إضافة تحتاج إلى تزويد النموذج بسياق إضافي.

صيغة القيمة المُعادة

أي قيمة مُعادة غير فارغة وغير None تحمل مفتاح "context" (أو سلسلة نصية غير فارغة) تُجمَع وتُلحَق برسالة المستخدم للدور الحالي.

فيضان السياق الزائد الحجم

يُحدَّد سياق كل hook افتراضيًا بسقف 10,000 محرف افتراضيًا. ويُكتب أي شيء يتجاوز السقف إلى $HERMES_HOME/hook_outputs/<session_id>/<uuid>.txt ويُستبدَل بمعاينة رأس/ذيل مع المسار المحفوظ. يمكن للنموذج قراءة المحتوى الكامل عبر read_file أو terminal إن احتاج إليه فعليًا. هذا يمنع أي إضافة منفلتة من تضخيم prompt كل دور لاحق وتفجير بادئة ذاكرة التخزين المؤقت الخاصة بالـ prompt. اضبط ذلك في config.yaml:

كيف يعمل الحقن

يُلحَق السياق المحقون بـرسالة المستخدم، لا بـ system prompt. هذا خيار تصميمي متعمَّد:

  • الحفاظ على prompt cache — يبقى system prompt متطابقًا عبر الأدوار. يخزّن Anthropic و OpenRouter بادئة system prompt مؤقتًا، لذا يوفر تثبيتها 75%+ من tokens الإدخال في المحادثات متعددة الأدوار. ولو عدّلت الإضافات system prompt ، لأصبح كل دور إخفاق تخزين مؤقت.
  • عابر (Ephemeral) — يحدث الحقن فقط وقت استدعاء API. رسالة المستخدم الأصلية في سجل المحادثة لا تُعدَّل أبدًا، ولا يُحفَظ شيء في قاعدة بيانات الجلسة.
  • الـ system prompt هو نطاق Hermes الخاص — فهو يحتوي على إرشادات خاصة بالنموذج، وقواعد فرض الأدوات، وتعليمات الشخصية، ومحتوى المهارات المخزَّن مؤقتًا. تسهم الإضافات بسياق إلى جانب مدخلات المستخدم، لا بتعديل تعليمات الوكيل الأساسية.

عدة إضافات تُعيد سياقًا

عندما تُعيد عدة إضافات سياقًا من pre_llm_call، تُدمَج مخرجاتها بفواصل سطرين مزدوجة وتُلحَق برسالة المستخدم معًا. يتبع الترتيب ترتيب اكتشاف الإضافات (أبجديًا حسب اسم دليل الإضافة).

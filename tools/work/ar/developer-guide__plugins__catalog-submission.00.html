إرسال إضافة إلى كتالوج الإضافات

يُعدّ كتالوج الإضافات دليلًا لإضافات Hermes تخضع إدخالاته لمراجعة بشرية. الإدراج فيه علامة ثقة: يثبّت المستخدمون إضافة الكتالوج بالاسم، عند commit نفسه الذي قرأه أحد المشرفين. تضم هذه الصفحة الإرشادات الكاملة لإدراج إضافة والإبقاء عليها فيه.

النسخة المعتمدة لقواعد القبول هي plugin-catalog/README.md في المستودع. يعكس قسم القواعد أدناه نصها حرفيًا، ويفشل أحد الاختبارات عملية البناء إذا اختلفت النسختان.

قبل الإرسال

  • مستودع عام. يجب أن يكون URL الخاص بـ repo عنوان https:// يستطيع أي شخص استنساخه (GitHub أو GitLab).

  • إضافة قابلة للتحميل عند commit الذي تثبّته. تتضمن الشجرة manifest باسم plugin.yaml مع نقطة دخول واحدة على الأقل يحمّلها Hermes: __init__.py (Python) أو desktop/plugin.js (Desktop) أو plugin.json (Agent Plugin محمولة) أو dashboard/manifest.json (لوحة تحكم الويب). إذا كانت الإضافة في monorepo، وجّه subdir إلى دليلها. يشرح دليل مطوّري الإضافات البنية.

  • واجهات عامة فقط. وسّع Hermes عبر الـ hooks والـ middleware وواجهات API الخاصة بـ ctx.register_* وإضافات المزوّدين و SDK إضافات Desktop. لا تعدّل كود Hermes أو وسوم Desktop في وقت التشغيل أبدًا. إذا كان الـ hook المطلوب غير موجود، راجع طلب hook.

  • نجاح التحقق محليًا. نفّذ الفحص نفسه الذي ينفّذه CI للكتالوج، على نسخة مسحوبة عند commit الذي ستثبّته:

    يفحص manifest و requires_hermes وإمكان تحميل الإضافة وتطابق ما تعلنه من capabilities مع ما تسجّله، و config_schema و requires_env واعتماديات Python مقارنةً بقيود Hermes الأساسية وفحص أمان التثبيت وقواعد desktop surface و no core override. أصلح كل إخفاق قبل فتح PR، واقرأ التحذيرات لأن المراجع سيقرأها.

فتح PR

  1. أضف ملفًا واحدًا، plugin-catalog/<name>.yaml، إلى NousResearch/hermes-agent. الحقول موثّقة في مخطط المدخل في README وفي محتويات المدخل. ثبّت sha على commit كامل من 40 حرفًا، وضع version بين علامتي اقتباس.
  2. اذكر في وصف PR وظيفة الإضافة وواجهات Hermes التي تستخدمها، وكل ما تطلب القاعدة 13 الإفصاح عنه. أضف لقطات شاشة لكل ما يتضمن واجهة مستخدم.
  3. انتظر نجاح مهمة CI للكتالوج. تستنسخ مستودعك عند commit المثبّت وتنفّذ hermes plugins validate.
  4. يراجع أحد المشرفين الشجرة المثبّتة ثم يدمج أو يطلب تغييرات أو يرفض. تؤدي مشكلات القاعدتين 3 و 9 إلى الرفض، لا إلى طلبات إصلاح أخطاء: يجب أن تغيّر الإضافة تصميمها قبل إمكان إدراجها.

تُبنَى صفحة إضافتك في /docs/plugins/<name> من الملف نفسه. يُعرَض README الموجود عند commit المثبّت فيها افتراضيًا، ويملأ screenshots: معرض الصور. لا يوجد إدراج منفصل لصيانته.

قواعد القبول

  1. بوابة دمج بشرية. لا تُضاف المدخلات إلا عبر PR إلى مستودع hermes-agent، يراجعه ويدمجه مشرف. لا يوجد سجل ذاتي الخدمة ولا استيعاب تلقائي.

  2. تثبيت SHA الدقيق إلزامي. يثبّت كل مدخل SHA كاملًا لـ commit من 40 حرفًا. يرفض المحمّل الـ branches والوسوم وقيم SHA المختصرة. تستنسخ عمليات التثبيت المستودع وتسحب ذلك commit نفسه.

  3. لا كود يحدّث نفسه. يجب ألا تجلب الإضافة المُدرَجة ملفاتها الخاصة وتستبدلها (ميزة "check for updates" داخل التطبيق أو أدوات تنزيل الإصدارات الموقّعة أو محمّلات plugin.js البعيدة). إن تثبيت SHA الدقيق هو نموذج الثقة؛ وتتيح أداة التحديث الذاتي انتقال النسخة المثبّتة إلى commit لم يراجعه أحد. لا تصل التحديثات إلى المستخدمين إلا عبر PR هنا لتغيير SHA، مع hermes plugins update <name>. أبقِ أداة التحديث في التوزيعة المستقلة إن أردتها؛ واحذفها من بنية الكتالوج.

  4. تغييرات SHA تتطلب PRs جديدة. تحديث التثبيت لمدخل ما هو PR جديد تُراجع فروقه (SHA القديم → SHA الجديد) من جديد مثل أي تغيير آخر — يُتوقَّع من المراجعين فحص نطاق commits في المصدر الأصلي الذي سيُعتمد.

  5. إرسال من المالك أو مساهم رئيسي، أو تجميع ينتقيه المشرفون. يجوز لمالك مستودع الإضافة أو أحد المساهمين الرئيسيين فيها إرسال مدخل؛ وتُرفَض الإرسالات العابرة لمستودعات أطراف ثالثة. يمكن لمشرفي Hermes أيضًا إضافة مدخلات على دفعات من مراجعة لإضافات المجتمع (يُتحقَّق من كل تثبيت ويُفحَص عند commit المثبّت، وتُجرى فحوصات التحديث الذاتي ومخازن بيانات الاعتماد، وتكون الواجهة بالإنجليزية أولًا). يحتفظ مؤلفو المدخلات المضافة بهذه الطريقة بالتحكم: يُقبَل عند الطلب PR من المالك لتعديل مدخله أو إزالته، وتظل تغييرات SHA محصورة في PRs من المالك أو المشرف وفق القاعدة 4.

  6. القدرات المعلنة يجب أن تطابق الواقع. يجب أن تطابق كتلة capabilities: (الأدوات والـ hooks والـ middleware ومتغيرات البيئة) ما تسجّله الإضافة فعليًا عند commit المثبّت. وإلا يفشل التحقق من المدخل — ويُعدّ توسّع القدرات غير المعلن مشكلة أمنية.

  7. يعمل فاحص التثبيت عند القبول. hermes plugins validate يتضمن security scan فحصًا: تؤدي نتيجة dangerous إلى فشل المدخل؛ وتظهر نتائج caution كتحذيرات في سجل CI ويقرأها المراجع قبل الدمج. في المقابل، تقبل عمليات التثبيت عند SHA المثبّت caution دون مطالبة (dangerous يظل مانعًا). راجع التحذيرات؛ ولا تدمج متجاهلًا إياها.

  8. تبقى إضافات Desktop داخل حدود SDK. يعمل ملف desktop/plugin.js في renderer الخاص بـ Desktop بكامل صلاحيات التطبيق (يعزل المحمّل الأخطاء لا القدرات)، لذا لا يجوز للإضافة المُدرَجة إلا استخدام SDK الإضافات: لا تعديل لـ prototype كائنات renderer أو المتصفح (Storage.prototype.y =، Object.defineProperty(...prototype)، ويتحقق المراجعون من ذلك يدويًا (إذ لا يفحصه lint)؛ أما مكتبة مضمّنة تضبط حقولًا على فئات تعرّفها بنفسها (مثل three.js وما شابهها) فلا بأس بها، ولا eval/new Function، ولا import() لأي شيء غير @hermes/plugin-sdk / react (بما في ذلك أجزاء حزمة التطبيق وعناوين blob أو http)، ولا حقن وسوم script، ولا وصول إلى مخازن التطبيق الداخلية أو إلى وسومه الخاصة (الاستعلام عن عناصر data-slot / data-tour / data-sidebar / data-testid من document، أو استخدام MutationObserver على document.body، لإعادة تنسيق الواجهة الأساسية أو إخفائها أو النقر عليها أو إعادة كتابتها). يرفض hermes plugins validate هذه الممارسات عند القبول (فحص desktop surface)؛ وتطلب الإضافة التي تحتاج قدرة لا تتيحها SDK إضافة SDK hook بدلًا من التحايل بالتعديل.

  9. لا تجاوزات وقت التشغيل لنواة Hermes. توسّع الإضافة المُدرَجة Hermes فقط عبر الواجهات العامة: الـ hooks والـ middleware وprofiles المزوّدين وواجهات register_* الأخرى، وخانات Desktop SDK ومساراته. يجب ألا تستبدل الدوال أو الأساليب أو خصائص الوحدات أو القواميس الخاصة في النواة أو تغلّفها أو تعيد ربطها في مكانها (AIAgent.<method> = ...، setattr(server, ...)، sys.modules[...]، أو الكتابة في جداول وحدة أساسية). تؤدي إضافتان تعدّلان نقطة التكامل نفسها إلى تعطيل إحداهما الأخرى بصمت، وقد يعطّلهما كل إصدار جديد للنواة. يرفض hermes plugins validate ذلك عند القبول (فحص no core override)، ويحذّر (دون إفشال) عند كل استيراد لوحدة أساسية غير موثّقة، مع ذكر الملف والسطر. إذا كان الـ hook الذي تحتاجه غير موجود، فافتح issue تصفه: نفضّل إضافة نقطة التكامل على إدراج تعديل مُرقَّع.

  10. سياسة أمان الاعتماديات تخص الإضافة. يغطي فحص عمر الإصدار exclude-newer البالغ 3 أيام في Hermes اعتماديات Hermes نفسه فقط، وفي وقت تثبيت Hermes لها؛ أما python_dependencies / pyproject.toml الخاصان بالإضافة فيُثبَّتان وفق سياسة الإضافة (دون فحص للعمر)، ضمن قيود Hermes الأساسية: فلا يمكن تحريك التثبيتات الدقيقة لـ Hermes. يقرأ المراجعون قائمة الاعتماديات عند SHA المثبّت: الحدود الدنيا وحدها (>=X دون حد أعلى) والحدود الدنيا عند أحدث إصدار تؤدي إلى طلب أقدم حد أدنى متوافق مع API إضافةً إلى حد أعلى، ويُنصح المؤلفون بشدة بتطبيق حجر إصدارات خاص بهم (uv --exclude-newer في CI الخاص بهم) — راجع سياسة أمان الاعتماديات في دليل المطوّر. ولا يُعدّ الحد الأدنى الحديث وحده سببًا لتعليق مدخل.

  11. تأتي بيانات الاعتماد عبر Hermes، لا من الملفات. لا تحصل الإضافة على الأسرار إلا عبر مسارات Hermes. تُقرأ أسرار requires_env وconfig_schema التي تصرّح بها باستخدام agent.secret_scope.get_secret(NAME)، الذي يلتزم بالـ profile النشط (قد تلتقط قراءة مباشرة عبر os.environ مفتاح profile آخر ضمن multiplexing). ولا يُستخدَم تسجيل الدخول للاشتراك (Codex / ChatGPT حاليًا) إلا عبر credentialed_provider_request مع requires_auth، لكي يُرفِق Hermes الـ token دون أن تحتفظ به الإضافة أبدًا. ويُصرَّح بعميل OAuth لواجهة API تابعة لطرف ثالث (مثل عميل Google Cloud الخاص بالمستخدم) تحت oauth: في plugin.yaml، ويُسجَّل الدخول به عبر hermes auth add <plugin>:<id> ويُستخدم عبر المساعد نفسه؛ ويخزّن Hermes هذا الـ token ويجدّده أيضًا. ويجب أن تكون authorize_url وtoken_url و hosts بـ https فقط، وأن تنتمي hosts إلى واجهة API التي تخصها النطاقات (scopes). لا تقرأ الإضافة أبدًا ملفات .env أو auth.json الخاص بـ Hermes أو بيانات دخول أداة أخرى (ملف token لواجهة CLI من مورّد أو profile متصفح أو keychain) أو أي مخزن بيانات اعتماد آخر مباشرةً، ولا تجدّد أو تدوّر أو تكتب OAuth tokens ولا تقدّم نفسها كعميل لمورّد آخر. إذا لم يوفر Hermes مسارًا لبيانات اعتماد تحتاجها إضافة، فاطلبه في issue أو PR لـ Hermes؛ ولا تتحايل الإضافة على غيابه.

  12. تُحترَم الموافقات والتشغيلات غير الخاضعة للإشراف. لا تتحايل الإضافة أبدًا على نظام الموافقات في Hermes: لا موافقات تلقائية ولا تعطيل للضوابط ولا إطلاق لعمليات Hermes أو shell فرعية ترث وضع YOLO أو الوضع غير التفاعلي لتنفيذ أوامر لم يوافق عليها أحد. كل ما ينتظر شخصًا (مطالبة أو تدفق OAuth عبر المتصفح) يفشل بوضوح أو تنتهي مهلته تحت cron و Messaging Gateway والتشغيلات الأخرى دون إشراف بدل تعليق الوكيل.

  13. يُفصَح عن السلوك المحفوف بالمخاطر. يُذكَر كل ما يريد المستخدم معرفته قبل التثبيت في وصف PR و README للإضافة: اتصالات الشبكة بخدمات أطراف ثالثة، وقراءات خارج بيانات الإضافة نفسها، وأوامر shell، والعمليات الخلفية طويلة التشغيل، وبيانات الاعتماد المخزّنة. القياس عن بُعد وتقارير الاستخدام اختياريان بموافقة صريحة. يلخّص المراجعون ذلك في أسطر إفصاح على PR المدخل؛ ويؤدي السلوك غير المعلن المكتشَف أثناء المراجعة إلى طلب تغييرات.

  14. بيانات التوافق الوصفية صادقة. requires_hermes حد أدنى وفق SemVer (">=0.21.5")، وليس تاريخ CalVer أبدًا، ولا أحدث من الإصدار الحالي أبدًا (وإلا يتجاوز المحمّل الإضافة). يطابق version الكود المثبّت، وتُحَلّ اعتماديات Python ضمن قيود Hermes الأساسية (hermes plugins validate --install-deps هو ما ينفّذه CI).

  15. لا مظاهر أو forks للإضافات المضمّنة. تغيير الإضافة المضمّنة هو PR على hermes-agent، لا إدراج منافس، ولا تُدرَج مظاهر تشبه واجهات المورّدين تحت علامة Nous.

  16. إدراج واحد لكل سلالة إضافة. لا يُدرَج fork لإضافة مجتمع مُدرَجة إلا إذا اختلف عنها جوهريًا: وسيلة نقل أو بنية معمارية مختلفة، أو قدرة تفتقدها الأصلية ورفض مؤلفها PR بشأنها أو لم يجب عنه خلال 30 يومًا. تُرسَل تحسينات الإضافة المُدرَجة إلى المصدر الأصلي كـ PR لمؤلفها. ويُرفَض fork الذي يغيّر الاسم أو العلامة أو يضيف تغييرات صغيرة لصالح الأصل. يذكر fork المُدرَج أصله في سطر الإفصاح (Derived from <entry>).

  17. لا حمولات تنفيذية يتعذّر فحصها. يجب أن يكون كل ما يقرؤه المراجع وماسح التثبيت عند الـ commit المثبّت شيفرة مصدرية يمكنهما قراءتها. يجب ألا تشحن الإضافة ملفًا ثنائيًا مترجمًا (ملفًا تنفيذيًا أو مكتبة أصلية لأي نظام تشغيل — يُكتشف بترويسة الملف لا بامتداده: ELF وMach-O وPE/MZ وWebAssembly)، ولا bytecode لـ Python مُودَعًا (.pyc/.pyo، بما في ذلك الـ caches بلا مصدر أو المزوّرة بالـ hash التي تعمل بدلًا من ملف .py المجاور لها)، ولا أرشيفًا لا تكون محتوياته شيفرة مصدرية قابلة للمراجعة. أما حزمة مصدرية نصية صرفة (ملف .tar.gz من ملفات .py/.ts/.md تفكّه الإضافة) فتُقرأ كأي مصدر آخر؛ بينما الحزمة التي تخفي ملفًا ثنائيًا لا تُقبل. لا يستطيع الماسح قراءة شيفرة الآلة، ولا يثبت الـ checksum المودَع في الـ commit نفسه إلا أن الملف لم يتغير بعد ذلك الـ commit، لا من أين جاء. وإذا كانت الإضافة تحتاج فعلًا إلى مكوّن أصلي، فيجب أن يُبنى الملف الثنائي بواسطة GitHub Actions العامة الخاصة بمستودع الإضافة نفسه انطلاقًا من المصدر في ذلك المستودع وأن يحمل شهادة بناء من GitHub (actions/attest-build-provenance) تربطه بذلك الـ workflow وذلك الـ commit؛ وتتحقق البوابة من الشهادة مقابل الـ commit المثبّت (gh attestation verify --repo <owner/repo> --source-digest <pinned sha>). ولا يُسمح بملف ثنائي يجلبه جهاز المستخدم نفسه وقت الإعداد إلا من المصدر الرسمي للأداة الأصلية، مثبّتًا بـ checksum، ومُفصحًا عنه (القاعدة 13) — وليس مضمّنًا أبدًا، ولا من مرآة غير رسمية.

تحديث مدخلك

تمر تحديثات التثبيت (نقل sha إلى commit أحدث) بعملية PR والمراجعة نفسها. يقرأ المراجع نطاق commits الذي تعتمد عليه. حدّث version في PR نفسه كي يطابق الاسم الذي يراه المستخدمون الكود، وأعد تثبيت أي عناوين URL لـ image / screenshots تضمّن SHA القديم.

تقارن الإضافات المثبّتة SHA المسجّل لديها بالتثبيت الحالي: تعرض hermes plugins list --json update_available، وتعرض علامة التبويب Plugins في Desktop زر Update to 1.4.0، ويسحب hermes plugins update <name> التثبيت الجديد نفسه بالضبط.

إذا أدرج مشرف إضافتك ضمن الكتالوج وأردت تغيير المدخل أو إزالته، فافتح PR على ملفه. يحتفظ المالكون بالتحكم في مدخلاتهم.

إلغاء الإدراج والإزالة

  • إلغاء الإدراج يحذف ملف المدخل: للإضافات غير المصانة أو التي حلّ غيرها محلها أو التي تحتكر اسمًا أو التي لم تعد تستوفي قاعدة. يحتفظ المستخدمون الذين ثبّتوا الإضافة بالفعل بها، ويُرحَّب بإعادتها بعد إصلاح المشكلة. عندما تؤثر قاعدة جديدة في إضافات مُدرَجة بالفعل، يتلقى مؤلفوها issue في مستودعاتهم تشرح التغيير وتمنحهم وقتًا للتحديث قبل إزالة أي شيء.
  • الإزالة تضيف الإضافة إلى removed.yaml، وهي قائمة مخصّصة للحوادث الأمنية ومخالفات السياسة. ترفض أدوات التثبيت أي شيء فيها، وتتوقف النسخ المثبّتة عن التحديث ولا يمكن تفعيلها.

طلب hook

إذا احتاجت إضافتك شيئًا لا تتيحه واجهة الإضافات، افتح issue على hermes-agent تصف ما تحتاجه وسببه. نفضّل كثيرًا إضافة نقطة تكامل سليمة على إدراج تعديل، والإضافة التي ستستخدم الـ hook هي بالضبط المستهلك الفعلي الذي يحتاجه أي hook جديد.

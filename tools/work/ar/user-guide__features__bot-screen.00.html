Bot Screen

على مضيف gateway يعمل بـ Linux دون شاشة (خادم أو VM سحابية أو Hermes Cloud)، يحصل كل بوت على سطح مكتب خاص به: شاشة Xfce تعمل عليها أداة computer_use والمتصفح ذو الواجهة الرسومية الخاصان بالبوت، وتُبث مباشرةً إلى Hermes Desktop. شاهد ما يفعله البوت، و تولَّ التحكّم عندما يصل إلى تسجيل دخول أو مطالبة 2FA أو CAPTCHA أو خطوة دفع، ثم أعد التحكّم إليه واتركه يواصل باستخدام الجلسة التي سجّلت دخولك إليها للتو. يواصل البوت العمل بعد إغلاق التطبيق أو إطفاء حاسوبك المحمول؛ توجد الشاشة على مضيف gateway، لا على جهازك. إذا شغّل gateway أداة terminal داخل sandbox (terminal.backend: docker أو ssh أو backend إضافة بالبث مثل singularity)، فتوجد الشاشة داخل ذلك sandbox بدلًا من ذلك، بجانب الـ shell، لكيلا تعمل أداة computer_use والمتصفح الخاصان بالبوت خارج الحد الذي حدّدته مطلقًا (راجع مكان تشغيل الشاشة).

لكل profile في Hermes ("بوت") شاشته و profile المتصفح وملفات cookies الخاصة به. الشاشات مساحات عمل، لا حدود أمان: تشترك البوتات في حساب مستخدم المضيف وملفاته وشبكته (النموذج نفسه الذي تستخدمه منتجات الوكلاء المستضافة الأخرى).

نموذج التهديد. ينتمي مقبس RFB الخاص بالشاشة وعرض X و profile المتصفح وملف حجز التحكّم (control-lease) جميعًا إلى مستخدم OS الخاص بالـ gateway. تستطيع أي عملية تعمل باسم ذلك المستخدم — بما فيها بوت آخر على المضيف نفسه وأداة terminal الخاصة بالبوت — الوصول إليها مباشرةً متجاوزةً اللوحة والحجز. الحجز قيد على مستوى أداتي computer_use والمتصفح، لا على مستوى OS. وهناك حد أوسع من مستخدم OS: يمكن الوصول إلى منفذ DevTools في Chromium (يعلن Browser في شريط الأدوات وكل Chromium يشغّله Hermes واحدًا على loopback لكي يستطيع الوكيل الاتصال) من أي مستخدم محلي على المضيف، ولا يوفّر Chromium قيدًا له لكل مستخدم. تشغيل كل بوت باسم مستخدم OS مستقل خارج النطاق؛ إذا كان هذا العزل مهمًا لك، أو كان للمضيف مستخدمون محليون غير موثوقين، فضع البوتات على مضيفين منفصلين. تفصيلان زمنيان يستحقان المعرفة: يخزّن جسر WebSocket قراره بشأن الحجز مؤقتًا لمدة تصل إلى 250 ms بين إعادات قراءة ملف الحجز، لذا يُفرض استحواذ عملية أخرى خلال تلك النافذة (تُبطَل نتائج أدوات البوت بواسطة حقبة الحجز (lease epoch) بصرف النظر عن النافذة). وتنتقل تذكرة display_ticket الخاصة بالمشاهد، التي تُستخدم مرة واحدة وتدوم 30 ثانية، عمدًا كمعلمة استعلام URL — لا يستطيع noVNC التفاوض على بروتوكولات WebSocket الفرعية، لذا لا يمكن استخدام ترويسة — مما يعني أن سجل وصول reverse proxy قد يسجّل تذكرة استُهلكت بالفعل.

المتطلبات

  • يعمل مضيف gateway على Linux. لدى مضيفي macOS و Windows عرض حقيقي بالفعل؛ ولا تُتاح اللوحة عليهما.

  • يجب تثبيت Xvnc من TigerVNC ومكوّنات Xfce الأساسية على المضيف. لا يثبّتها شيء بصمت: يترك hermes update والتثبيت الجديد كل جهاز كما هو. عندما تكون مفقودة، تعرض لوحة Screen في Hermes Desktop زر Install on host — بنقرة واحدة يُشغَّل مدير الحزم على مضيف gateway (يطلب كلمة مرور sudo لذلك المضيف في بطاقة مخفية الإدخال؛ تُرسل كلمة المرور إلى ذلك المضيف فقط ولا تُخزّن مطلقًا) ويُبث السجل. عندما يعمل Hermes نفسه باسم root — وهو المعتاد في حاوية — يشغّل المُثبّت مدير الحزم مباشرةً دون sudo أو بطاقة كلمة مرور. عندما لا يكون root ولا يوجد على المضيف sudo أصلًا، تطبع اللوحة و CLI أمر التثبيت الدقيق لتنفيذه على المضيف بدلًا من عرض بطاقة. صورة Docker الرسمية (nousresearch/hermes-agent، التي تستخدمها Hermes Cloud أيضًا) من الحالة الثانية: يعمل gateway كمستخدم غير ذي امتيازات ولا تحتوي الصورة على sudo، لذا تعرض اللوحة سطر apt-get وينفّذه المشغّل مرة واحدة باسم root داخل الحاوية (docker exec -u 0 <container> apt-get install -y …). أضف chromium إلى ذلك السطر إذا أردت أيقونة Browser في شريط الأدوات؛ راجع جلسات المتصفح أدناه. من shell، يطبع hermes computer-use screen status السطر الدقيق، وينفّذه hermes computer-use screen install:

  • Computer Use مفعّل للبوت (مع تثبيت cua-driver).

  • الذاكرة. القياسات في الصورة الرسمية: يستهلك gateway الخامل نحو 300 MB، ويضيف Xvnc + Xfce نحو 220 MB، ويضيف Chromium ذو الواجهة الذي يفتحه الإنسان أثناء تولّي التحكّم 0.5–1 GB (صفحة واحدة: نحو 550 MB). خطّط لـ نحو 1.1–1.5 GB لكل شاشة مفتوحة مع متصفح؛ سطح المكتب وحده قليل الكلفة، والمتصفح هو المكلف. CPU ليس عائقًا (سطح المكتب الخامل ≈ 0.01 نواة، والبث المباشر ≈ 0.03 نواة). تستهلك الحزم نحو 930 MB من القرص على Debian 13.

    قبل بدء شاشة، يتحقّق Hermes من أن المضيف — أو cgroup الخاصة بحاويته، أيهما أشد تقييدًا — يملك bot_desktop.min_free_memory_mb حرة (القيمة الافتراضية 1536؛ 0 يعطّل الفحص). دون ذلك، تعرض اللوحة السبب بدلًا من Start screen، ويرفض hermes computer-use screen start؛ ولا تُوقَف شاشة تعمل بالفعل بهذا الفحص مطلقًا. تتوقف الشاشة غير المستخدمة بعد bot_desktop.idle_stop_minutes (القيمة الافتراضية 30) وتعود عند الاستخدام التالي، لذا لا تدفع النسخة كلفة سطح مكتب إلا عندما يوجد عليه عمل. إرشاد عملي للنسخ الصغيرة: يشغّل 4 GB سطح المكتب، ويتيح 8 GB تولّي التحكّم مع متصفح براحة.

تضمين الحزم في صورة حاوية

لا تستطيع صورة لنشر مستضاف أو غير ذي امتيازات تثبيت أي شيء وقت التشغيل، لذا يجب تضمين الحزم فيها. ينشر CI نسختين من كل إصدار: tags بلا لاحقة (:latest, :v*) دون الحزم، و tags -desktop (:latest-desktop, :v*-desktop) معها. يحصل نشر مستضاف (Fly Machines أو Azure container instances) على Bot Screen بسحب tag ذي اللاحقة؛ فلا يمكن لوسيط بناء الوصول إليه أصلًا، لأنه لا ينفّذ بناءً. لا يختار شيء في أداة التزويد -desktop بعد، لذا لا تزال النسخة المستضافة تبدأ خفيفة؛ ويمكنك حاليًا سحب tag ذي اللاحقة بنفسك.

ابنِ نسختك فقط إذا أردت الحزم في صورة مخصّصة. يحتوي Dockerfile الرسمي على وسيط بناء اختياري، معطّل افتراضيًا لكي يبقى docker build . العادي خفيفًا:

يضيف TigerVNC ومكوّنات Xfce و chromium الخاصة بالتوزيعة (المسار الاحتياطي لـ sandbox الموصوف ضمن جلسات المتصفح) — بلغ قياس طبقة apt نحو 930 MB على Debian 13. لا يضيف متصفح Playwright ثانيًا: تحمل كل صورة، خفيفة أو -desktop، بالفعل Chromium الكامل المثبّت عبر PM، القادر على فتح نافذة. لا يبدأ شيء عند الإقلاع؛ لا تستهلك صورة مبنية بهذه الطريقة ذاكرة حتى تُشغّل شاشة.

الاستخدام

حاسوب كل بوت على بُعد نقرة واحدة في ثلاثة مواضع من Hermes Desktop:

  • Bots → a bot → Scheduled Jobs: تتصدر شاشة البوت أعلى اللوحة، فوق العنوان والمهام الروتينية: معاينة مباشرة لسطح المكتب (تُحدّث كل بضع ثوانٍ ما دامت اللوحة مرئية) مع بيان من يملك التحكّم؛ انقر الصورة لتوسيعها إلى وصول مباشر. عندما تكون الشاشة متوقفة أو غير مثبّتة، يذكر الصندوق نفسه ذلك ويعرض Start / Install.
  • Bots → right-click a bot → Open Screen. تحتوي القائمة نفسها على Open Screen when the bot uses it: عند تحديده، يتقدم تبويب Screen عند أول استدعاء computer_use أو متصفح للبوت في التشغيل، لكي تراه يعمل بدلًا من اكتشاف ذلك لاحقًا. معطّل افتراضيًا، ولكل بوت على حدة. يرفع التبويب دون سحب تركيز لوحة المفاتيح، ولا يُفعّل للسجل المعاد عرضه مطلقًا، وبحد أقصى مرة كل 30 ثانية، وإذا أغلقت التبويب أثناء التشغيل يبقى مغلقًا حتى التشغيل التالي للبوت.
  • الشريط الجانبي للجلسات، مجمّعًا حسب gateway / profile: يوجد صندوق Screen نفسه تحت عنوان كل profile، لكي يمكنك الوصول إلى جهاز profile من محادثاته أيضًا.
  1. افتح Screen من أي إدخال أعلاه. الشاشة معطّلة افتراضيًا ولا يبدأها شيء نيابةً عنك: انقر Start screen في اللوحة، أو نفّذ hermes computer-use screen start على المضيف، أو اضبط bot_desktop.auto_start: true إذا أردت أن يبدأ مضيف دون شاشة الشاشةَ بنفسه عند أول استدعاء computer_use أو أول استخدام لمتصفح ذي واجهة (browser.headed: true) — معطّل لكيلا ينتج عن تثبيت TigerVNC شاشة لم يطلبها أحد. يفتح المتصفح ذو الواجهة على الشاشة بمجرد تشغيلها.
  2. تبث اللوحة سطح مكتب البوت. يبيّن المؤشر في العنوان من يملك التحكّم: Bot is in control افتراضيًا.
  3. انقر Take over. يتحوّل الحد إلى الأحمر، وتتحكّم لوحة مفاتيحك وفأرتك الآن في شاشة البوت. سجّل الدخول، وحل CAPTCHA، ووافق على الدفع.
  4. انقر Hand back. يستعيد البوت التحكّم ويعيد التقاط الشاشة قبل المتابعة. يعيد إغلاق اللوحة التحكّم أيضًا. أما الاتصال المنقطع فمختلف: إذا أُغلق غطاء حاسوبك المحمول أو انقطع Wi-Fi وأنت تملك التحكّم، فإنك تحتفظ به — يظل البوت ممنوعًا من شاشة قد تكون في منتصف تسجيل الدخول عليها — حتى تعيد الاتصال وتعيد التحكّم. إذا عدت بعد إعادة تحميل وظلت اللوحة تذكر أن إنسانًا يملك التحكّم، يظهر زر Hand back (force) لإزالته.

ما دمت تملك التحكّم، تُرفض أدوات computer_use والمتصفح الخاصة بالبوت بالقيمة human_has_control، بما فيها اللقطات. هذا قيد على مستوى الأداة، لا OS: يعمل البوت باسم المستخدم نفسه الذي تملك به شاشته. لا تكتب أسرارًا في بوت لا تثق بأن تعهد إليه بها.

عندما يصل البوت إلى خطوة لا ينبغي أن ينفّذها بنفسه (تسجيل دخول أو 2FA أو CAPTCHA أو دفع)، يذكر ذلك في رده وينهي دوره؛ ويصلك الطلب في أي محادثة تستخدمها. تولَّ التحكّم عندما تكون مستعدًا، ونفّذ الخطوة، وأعد التحكّم، واطلب من البوت المتابعة. لا يتوقف شيء على جانب البوت أثناء انتظاره: بدء تولّي التحكّم يعود إليك دائمًا، ولا يُبقي البوت استدعاء أداة مفتوحًا في انتظارك مطلقًا.

مشاهدان لشاشة واحدة: يفوز آخر Take over؛ ويعود المتحكّم السابق إلى المشاهدة.

جلسات متصفح تبقى عبر تسليم التحكّم

أثناء عمل الشاشة، تكون أداة متصفح البوت وأيقونة Browser في شريط الأدوات المتصفحَ نفسه: Chromium الذي يتحكّم به browser_exec، بمجلد بيانات مستخدم (user-data-dir) دائم واحد لكل بوت (<HERMES_HOME>/bot-desktop/browser-profile؛ اضبط browser.user_data_dir لتثبيت مجلدك الخاص — يُوسَّع ~، ويُحلّ مسار نسبي مثل pin بالنسبة إلى HERMES_HOME لذلك البوت، أي <HERMES_HOME>/pin). انقر Browser أثناء تولّي التحكّم لتدخل نوافذ البوت ومخزن cookies نفسه؛ ويستخدم البوت ما تسجّل الدخول إليه بعدها وفي كل جلسة لاحقة حتى ينهي الموقع صلاحية الدخول. اضبط browser.headed: true لكي يكون تصفّح البوت نفسه مرئيًا على الشاشة أيضًا.

تُهيّأ أيقونات شريط الأدوات مرة واحدة، عند بدء الشاشة لأول مرة لـ profile. الحارس هو ملف تخطيط اللوحة <HERMES_HOME>/bot-desktop/xdg/xfce4/xfconf/xfce-perchannel-xml/xfce4-panel.xml: ما دام موجودًا، يترك المشغّل اللوحة كما هي، لذا لا يعيد تغيير browser.executable_path أو browser.user_data_dir وإعادة تشغيل الشاشة تثبيت أيقونة Browser. احذف ذلك الملف ليُعاد بناء شريط الأدوات عند screen start التالي وفق ما يكون مثبّتًا حينها.

نسخة Chromium التي يستخدمها الشريط والبوت: يتقدّم browser.executable_path الصريح؛ وإلا يستخدم Hermes نسخة Chromium المُدارة عبر PM، ويعود احتياطيًا إلى chromium / google-chrome في النظام. يحصل المستخدم غير root على مضيف به kernel.apparmor_restrict_unprivileged_userns=1 (Ubuntu 23.10 وأحدث) على الترتيب المعكوس، لأن الإصدار المُدار لا يستطيع هناك إعداد sandbox ويخرج بالرسالة FATAL: No usable sandbox!، بينما توفّر Chromium الخاصة بالتوزيعة profile AppArmor يسمح بذلك. إذا كان الاختيار غير مناسب لمضيفك، فاضبط browser.executable_path: /usr/bin/chromium (أو مسار Chrome لديك) في config.yaml الخاص بالبوت. تسجّل صورة Docker الرسمية Chromium الكامل المثبّت عبر PM في /etc/hermes/chromium-executable-path؛ وهذا الإصدار قادر على عرض نافذة، لذا تستخدمه أيقونة Browser في الشريط. وتحمل tags -desktop أيضًا chromium الخاصة بالتوزيعة — اضبط browser.executable_path: /usr/bin/chromium على المضيفين الذين يرفضون sandbox الإصدار المثبّت. لا يُستخدم headless shell الخاص بـ Playwright للأيقونة مطلقًا: عندما يكون المتصفح الوحيد، تُبلّغ اللوحة / screen status بالحالة no headed browser حتى تثبّت متصفحًا بواجهة (apt-get install chromium). تبدأ أيقونة الشريط المتصفح بإعدادات sandbox نفسها التي يستخدمها مشغّل Chromium في Hermes في تلك الحاوية، لذا يكون Browser الخاص بالإنسان ومتصفح البوت واحدًا.

مكان تشغيل الشاشة

computer_use ومتصفح البوت والشاشة التي يعملان عليها تعمل دائمًا في المكان نفسه. يحدّد bot_desktop.placement المكان:

terminal.backendplacement: auto (القيمة الافتراضية)ما يعنيه ذلك
localمضيف gatewayتشترك الطرفية والشاشة والمتصفح و computer_use جميعًا في الجهاز الذي يشغّل gateway.
docker و ssh و singularity (إضافة)داخل sandboxيعمل Xvnc + Xfce و Chromium و cua-driver في الحاوية / على مضيف SSH، ويُطلقون عبر قناة docker exec / ssh نفسها التي تستخدمها الطرفية. تبث اللوحة شاشة sandbox؛ ولا يمكن الوصول إلى أي جزء من سطح مكتب المضيف.
backend لإضافة plugin يصرّح بالخاصية supports_streamsداخل الـ sandboxمثل ما سبق، لكن عبر قناة exec الخاصة بالإضافة.
modal وdaytona وvercel_sandbox وغيرها من backends الإضافاتمرفوضلا تستطيع هذه backends استضافة عرض بعد. بدلًا من تشغيل الشاشة بصمت على المضيف بجانب sandbox الذي اخترته للوكيل، يشرح Start السبب ويشير إلى placement: gateway.

placement: gateway يفرض السلوك السابق (الشاشة على مضيف gateway حتى مع طرفية معزولة داخل sandbox) بموافقة اختيارية صريحة؛ ويفرض placement: terminal sandbox ويعطي خطأ عندما يعجز عن استضافتها (مع backend local، تكون الطرفية هي مضيف gateway، لذا تُحلّ هناك).

التموضع سياسة، لا لقطة لما يعمل مصادفةً. عندما توضع الشاشة في sandbox، يبدأها أول استدعاء متصفح أو computer_use هناك عند الطلب (لا حاجة إلى تفعيل auto_start: sandbox هو الحد الذي اخترته، ولا تمس شاشة داخله أي شيء خارجه)، وعندما يتعذّر بدؤها يفشل الاستدعاء مع السبب. لا يكون المضيف مسارًا احتياطيًا لـ sandbox شاشته متوقفة مطلقًا. لا تفقد إعادة تشغيل gateway الشاشة أيضًا: تسجّل العلامة على جهة المضيف الحاوية التي تملكها، لكي يعاود gateway المعاد تشغيله الاتصال بـ sandbox ما زال يعمل، ويوقف Stop الشاشة حيث تعمل فعليًا حتى إذا غيّرت placement في أثناء ذلك.

يحتاج sandbox إلى منظومة سطح المكتب. الصورة nousresearch/hermes-sandbox:desktop هي الافتراضية لكل backend حاويات (Docker و Modal و Daytona و Singularity): قاعدة nikolaik/python-nodejs (Python 3.13 / Node 26) إضافةً إلى TigerVNC ومكوّنات Xfce و Chromium بواجهة و cua-driver والأدوات اليومية التي تفتقر إليها القاعدة (jq و ripgrep و fd و tmux و rsync و sudo لمستخدم الصورة pn). المستخدم الافتراضي root كما في السابق، لذا لا تتغيّر إجراءات الـ shell. تُترك الصورة التي ثبّتّها بنفسك دون مساس، وتخبرك الشاشة عندئذ بأنها تحتاج إلى هذه الصورة أو bot_desktop.placement: gateway:

مع صورة عادية، تُبلّغ لوحة Screen عن الثنائيات المفقودة وتذكر هذا tag.

تُحوّل الصورة نفسها تحت Singularity/Apptainer إلى SIF (docker://nousresearch/hermes-sandbox:desktop)؛ يبقى ENV في Dockerfile عبر التحويل، لكن USER الخاص بالصورة لا يبقى: يعمل كل شيء باسمك، لذا يوجد profile المتصفح في $HOME الخاص بك داخل الحاوية، وهو overlay الدائم افتراضيًا. تعمل النسخة مع --containall، لذا يكون مجلدها المؤقت (حيث توجد حالة وقت تشغيل الشاشة) tmpfs جلسة Apptainer، بحجم 64 MiB ما لم يرفع مسؤولك sessiondir max size. جرى التحقّق من هذا المسار بمقارنته بتوثيق Apptainer، ولم يُجرّب مباشرةً.

مضيف SSH هو ما توجّه backend إليه، لذا يجب أن يحمل المنظومة بنفسه: الثنائيات نفسها (TigerVNC و Xfce و cua-driver، ومتصفح Chromium بواجهة رسومية)، والمتاحة من جلسة تسجيل دخول غير تفاعلية. هذه النقطة الأخيرة هي موضع اختلاف مضيف مبني من صورة سطح المكتب عن docker exec: لا يصل ENV في Dockerfile إلى جلسة ssh مطلقًا، لذا تكتب الصورة أيضًا PLAYWRIGHT_BROWSERS_PATH إلى /etc/environment ليطبّقه PAM. يحتاج مضيفك الخاص إلى ما يعادله، وإلا لا يجد المتصفح أي Chromium عبر ssh بينما يعمل في shell محلي.

الترقية من القيمة الافتراضية السابقة. يُحتفظ بـ Docker sandbox الموجود لديك، ولا يُستبدل: عندما لا يُضبط docker_image وتعمل حاوية دائمة على صورة أخرى (القيمة الافتراضية القديمة، nikolaik/python-nodejs:python3.11-nodejs20)، تواصل الطرفية استخدام تلك الحاوية ويعود قرار التبديل إليك. تسأل CLI التفاعلية مرة واحدة عند بدء التشغيل؛ وتعرض لوحة Screen الاختيار نفسه مع Switch image / Keep current image; hermes config set terminal.docker_image nousresearch/hermes-sandbox:desktop يعطي الإجابة نفسها من أي shell. تكتب أي من الإجابتين terminal.docker_image، والصورة المكتوبة قرار: لا تُعاد إنشاء الحاوية عند استدعاء الطرفية التالي إلا إذا اخترت الصورة الجديدة، وبعد سحبها فقط (يبقي tag خاص أو خاطئ إملائيًا أو انقطاع السجل الحاوية الحالية عاملة بدلًا من تركك بلا شيء). معنى التبديل: تبقى الملفات تحت /root و /workspace (وهي مجلدات مضيف تحت ~/.hermes/sandboxes/)، وتُعاد تثبيت الحزم المثبّتة داخل الحاوية باستخدام apt/pip/npm -g عند الطلب، وتحتاج virtualenvs الخاصة بـ Python 3.11 إلى إعادة بناء على 3.13. لا تقرّر gateways و cron مطلقًا؛ تحتفظ بـ sandbox وتسجّل الإشعار. أُزيل ضبط الإعدادات التي احتوت حرفيًا القيمة الافتراضية القديمة عند الترقية (كانت تلك القيمة قالبًا منسوخًا، لا تثبيتًا صريحًا). يستعيد Modal لقطته ويعيد Daytona استخدام sandbox الموسوم لديه بصرف النظر عن الصورة المضبوطة، لذا لا يُمسّ sandbox موجود فيهما ولا تحصل على الصورة الجديدة إلا نسخة جديدة. تعمل عمليات سطح المكتب باسم مستخدم الصورة غير ذي الامتيازات pn (uid 1000)؛ ويحصل Chromium على --no-sandbox داخل الحاويات (يرفض profile seccomp في Docker مساحات أسماء المستخدم التي يحتاجها sandbox الخاص به؛ والحاوية هي sandbox).

توجد حالة وقت التشغيل داخل sandbox (مقبس X و cookie وسجل المشغّل) تحت <sandbox tmp>/hermes-bot-desktop/<profile>/؛ ولا يحتفظ المضيف إلا بعلامة تحت <HERMES_HOME>/bot-desktop/. يوجد profile المتصفح (الدخول و cookies) في مجلد مستخدم سطح المكتب داخل sandbox، ~/.hermes/bot-desktop/browser-profile، ويشترك فيه متصفح الوكيل وأيقونة المتصفح (Browser) في الشريط. يتبع استمرارية الحاوية نفسها: يبقى عبر إيقاف حاوية دائمة وإعادة تشغيلها، ويزول مع حاوية مؤقتة أو عند موافقتك على تبديل الصورة (الطبقة القابلة للكتابة للحاوية هي ما يستبدله التبديل). وهو عمدًا خارج مجلد الحاوية المؤقت الذي يركّبه Docker كـ tmpfs صغير يُفرّغ عند كل إيقاف. تُنسخ لقطات أدوات المتصفح إلى المضيف لكي تظل مسارات MEDIA: تعمل، وتُلتقط الصورة المصغّرة للوحة داخل sandbox، ويصل browser_exec / الملء التلقائي من vault إلى Chromium في sandbox عبر منفذ مُمرَّر على قناة docker exec / ssh نفسها.

الإعدادات

auto_start معطّل افتراضيًا. ابدأ الشاشة من لوحة Screen في Desktop (Start screen)، أو من hermes computer-use screen start، أو اضبط الخيار على true لمضيف دون شاشة ينبغي أن يبدأ شاشته عند أول استدعاء للبوت computer_use أو فتحه متصفحًا بواجهة (browser.headed: true) مع عدم وجود عرض متاح.

توجد الحالة تحت <HERMES_HOME>/bot-desktop/ لكل profile (مقبس RFB Unix و Xauthority وسجل المشغّل و xfconf خاص بكل profile).

آلية العمل

  • TigerVNC Xvnc هو خادم X وخادم RFB في عملية واحدة لكل profile، ولا يستمع إلا على مقبس Unix من نوع 0600. لا منفذ TCP ولا كلمة مرور VNC: لا تستطيع الوصول إليه إلا عمليات تعمل باسم مستخدم gateway (راجع نموذج التهديد أعلاه)، وجسر WebSocket في gateway هو مسار الدخول الموثَّق.
  • Xfce يبدأ مكوّنًا بمكوّن (xfsettingsd, xfwm4 --compositor=off, xfdesktop, xfce4-panel) تحت جلسة D-Bus خاصة، دون xfce4-session، لكيلا يحاول شيء قفل الشاشة أو الوصول إلى logind.
  • Hermes Desktop يضمّن noVNC. يطلب من gateway تذكرة تُستخدم مرة واحدة (display.observe) عبر اتصاله المعتاد الموثَّق، ويفتح WebSocket موازيًا إلى /api/display/ws؛ ويمرّر gateway تدفق RFB من خلاله. لا يُكشف شيء جديد؛ تعمل اللوحة على الاتصالات المحلية و SSH و URL+token و Hermes Cloud على السواء.
  • حجز التحكّم. يُسقط gateway رسائل لوحة المفاتيح والمؤشر والحافظة من أي مشاهد لا يملك الحجز، على مستوى بايتات RFB؛ خيار المشاهدة فقط في noVNC مجرد إشارة في الواجهة. يضبط الحجز نفسه الوصول إلى computer_use وأدوات المتصفح. وهو ملف تحت <HERMES_HOME>/bot-desktop/: عدم وجود ملف يعني أن البوت يملك التحكّم (profile جديد)؛ أما الملف الموجود الذي يتعذّر قراءته أو تحليله فيؤدي إلى الرفض — يُعامل البوت على أنه ممنوع حتى يعيد تسليم ناجح تالٍ كتابة الملف. لا يدفع Xvnc حافظة الشاشة إلى المشاهدين مطلقًا (-SendCutText=0)، لذا لا يتلقى المشاهدون ما ينسخه صاحب التحكّم؛ ويظل اللصق داخل الشاشة يعمل.
  • ربط العرض. ينشر المشغّل DISPLAY, XAUTHORITY وعنوان D-Bus؛ ويرثها كل إطلاق لـ cua-driver ومتصفح بواجهة لذلك profile، لكيلا يعمل البوت على عرض يجلس أمامه إنسان مطلقًا.

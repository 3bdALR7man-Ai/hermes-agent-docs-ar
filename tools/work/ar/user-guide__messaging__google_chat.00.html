إعداد Google Chat

اربط Hermes Agent بـ Google Chat كبوت. يستخدم التكامل اشتراكات السحب في Cloud Pub/Sub للأحداث الواردة و Chat REST API للرسائل الصادرة. وتجربة الاستخدام مكافئة لـ Slack Socket Mode أو Telegram long-polling: لا تحتاج عملية Hermes إلى URL عام أو نفق أو شهادة TLS. فهي تتصل وتصادق وتستمع إلى اشتراك — تمامًا كما يستمع بوت Telegram إلى token.

نفّذ hermes gateway setup واختر Google Chat للحصول على إعداد موجَّه خطوة بخطوة.

إصدار Workspace

Google Chat جزء من Google Workspace. يمكنك استخدام هذا التكامل مع Workspace شخصي (@yourdomain.com مسجّل عبر Google) أو Workspace للعمل تملك فيه صلاحيات المسؤول لنشر تطبيق. ولا تستطيع حسابات Gmail وحدها استضافة تطبيقات Chat.

الخطوة 1: أنشئ مشروع GCP أو اختر مشروعًا قائمًا

تحتاج إلى مشروع Google Cloud لاستضافة موضوع (topic) Pub/Sub. إن لم يكن لديك مشروع، فأنشئه من console.cloud.google.com — تحصل الحسابات الشخصية على فئة مجانية (free tier) تغطي حركة البوت بسهولة.

دوّن معرّف المشروع (مثل my-chat-bot-123). ستستخدمه في كل خطوة لاحقة.

الخطوة 2: فعّل واجهتَي API

في وحدة التحكم (console)، انتقل إلى APIs & Services → Library وفعّل:

  • Google Chat API
  • Cloud Pub/Sub API

كلتاهما مجانية ضمن أحجام الاستخدام التي يولّدها بوت شخصي.

الخطوة 3: أنشئ Service Account

IAM & Admin → Service Accounts → Create Service Account.

  • الاسم: hermes-chat-bot
  • تخطَّ خطوة "Grant this service account access to project". صلاحيات IAM على الاشتراك المحدد هي كل ما تحتاج إليه — لا تمنح أدوار Pub/Sub على مستوى المشروع.

بعد الإنشاء، افتح الـ SA، وانتقل إلى Keys → Add Key → Create new key → JSON ونزّل الملف. احفظه في مكان لا يستطيع قراءته إلا Hermes (مثل ~/.hermes/google-chat-sa.json مع chmod 600).

لا يوجد دور "Chat Bot Caller"

من الأخطاء الشائعة البحث عن دور IAM خاص بـ Chat ومنحه على مستوى المشروع. ذلك الدور غير موجود. وتأتي صلاحية بوت Chat من تثبيته في مساحة، لا من IAM. وكل ما يحتاجه SA لديك هو Pub/Sub subscriber على الاشتراك الذي تنشئه في الخطوة التالية.

الخطوة 4: أنشئ موضوع Pub/Sub والاشتراك

Pub/Sub → Topics → Create topic.

  • Topic ID: hermes-chat-events
  • اترك بقية الإعدادات على قيمها الافتراضية.

بعد الإنشاء، تحتوي صفحة تفاصيل الموضوع على تبويب Subscriptions. أنشئ اشتراكًا:

  • Subscription ID: hermes-chat-events-sub
  • Delivery type: Pull
  • Message retention: 7 أيام (كي تبقى الرسائل المتراكمة بعد إعادة تشغيل hermes)
  • اترك الباقي على الافتراضي.

الخطوة 5: ربط IAM على الموضوع (خطوة حاسمة)

على الموضوع (وليس الاشتراك)، أضف IAM principal:

  • Principal: chat-api-push@system.gserviceaccount.com
  • Role: Pub/Sub Publisher

دون ذلك، لا يستطيع Google Chat نشر الأحداث إلى topic لديك ولن يتلقى بوتك أي شيء مطلقًا.

الخطوة 6: ربط IAM على الاشتراك

على الاشتراك، أضف Service Account الخاص بك بوصفه principal:

  • Principal: hermes-chat-bot@<your-project>.iam.gserviceaccount.com
  • Role: Pub/Sub Subscriber

امنحه كذلك الدور Pub/Sub Viewer على الاشتراك نفسه — إذ يستدعي Hermes subscription.get() عند بدء التشغيل للتحقق من إمكانية الوصول.

الخطوة 7: اضبط تطبيق Chat

انتقل إلى APIs & Services → Google Chat API → Configuration.

  • App name: أي اسم تريد أن يراه المستخدمون ("Hermes" خيار معقول).
  • Avatar URL: أي صورة PNG عامة (توفّر Google بعض الصور الافتراضية).
  • Description: جملة قصيرة تظهر في دليل التطبيقات.
  • Functionality: فعّل Receive 1:1 messages و Join spaces and group conversations.
  • Connection settings: اختر Cloud Pub/Sub، وأدخل اسم الموضوع projects/<your-project>/topics/hermes-chat-events.
  • Visibility: قيّد الإتاحة بمساحة عملك (أو مستخدمين محددين) — لا تنشر للجميع أثناء الاختبار.

الخطوة 8: ثبّت البوت في مساحة اختبار

افتح Google Chat في متصفح. ابدأ رسالة مباشرة مع تطبيقك بالبحث عن اسمه في قائمة + New Chat . وعند أول رسالة إليه، ترسل Google حدث ADDED_TO_SPACE يستخدمه Hermes لتخزين users/{id} الخاص بالبوت نفسه مؤقتًا لترشيح رسائله الذاتية.

الخطوة 9: اضبط Hermes

أضف قسم Google Chat إلى ~/.hermes/.env:

يستخدم معرّف المشروع أيضًا GOOGLE_CLOUD_PROJECTكقيمة احتياطية، ويستخدم مسار SA GOOGLE_APPLICATION_CREDENTIALS — استخدم الاصطلاح الذي تفضله.

ضمن gateway متعدد الـ profiles، يُقرأ كل إعداد GOOGLE_CHAT_* من ملف .env ؛ ولا يرث profile ثانوي مطلقًا مشروع الـ profile الافتراضي أو اشتراكه أو Service Account الخاص به. وإذا لم يكن لدى profile ما SA مضبوط بينما تحمل بيئة العملية SA لـ profile آخر، يرفض المحوّل الرجوع إلى Application Default Credentials (الذي سيصادق بصفته ذلك الـ profile الآخر) ويسجّل خطأ صريحًا بدلًا من ذلك — ضع GOOGLE_CHAT_SERVICE_ACCOUNT_JSON في ملف .env الخاص بذلك الـ profile.

ثبّت اعتماديات محوّل Google Chat عبر مُثبّته الذي تجري صيانته. ويطبّق الحدود الدنيا الأمنية المثبّتة نفسها المستخدمة في فحوص بيئة التشغيل:

--install-deps يطلب من PM إضافة الإضافة (extra) google-chat إلى بيئة Python المُدارة (pm.sync_venv)؛ أعد تشغيل الـ gateway بعد اكتماله لتفعيل البيئة الجديدة. وفي صور Docker / الاستضافة تكون venv للقراءة فقط والتثبيتات عند الطلب معطّلة (HERMES_DISABLE_LAZY_INSTALLS=1)، لذا لا تستطيع هذه الخطوة إضافة شيء هناك. وتضم الصورة المنشورة الإضافة [google-chat] بدلًا من ذلك، لذا لا تحتاج حاوية جديدة إلى تثبيت عند أول تشغيل.

الخطوة 10: تسليم المرفقات الأصلية (اختياري)

يستطيع البوت افتراضيًا نشر النصوص والصور المضمّنة عبر URL وبطاقات التنزيل للصوت/الفيديو/المستندات. ولتسليم مرفقات Chat الأصلية — وهي عنصر الملف نفسه الذي تحصل عليه حين يسحب شخص ملفًا ويفلته — يفوّض كل مستخدم البوت مرة واحدة عبر تدفق OAuth لكل مستخدم.

لماذا تدفق منفصل

يرفض endpoint ‏media.upload في Google Chat رفضًا قاطعًا المصادقة عبر Service Account:

This method doesn't support app authentication with a service account. Authenticate with a user account.

لا يوجد دور IAM أو نطاق يصلح هذا. ولا يقبل endpoint إلا بيانات اعتماد مستخدم. لذا يجب أن يتصرف البوت بصفته مستخدمًا كلما رفع ملفًا — وتحديدًا بصفته المستخدم الذي طلب الملف.

إعداد لمرة واحدة (لكل profile)

  1. انتقل إلى APIs & Services → Credentials في مشروع GCP نفسه.
  2. Create credentials → OAuth client ID → Desktop app.
  3. نزّل ملف JSON، ثم انقله إلى المضيف الذي يشغّل Hermes.
  4. سجّل العميل لدى Hermes (نفّذ الأمر ضمن الـ profile الذي تريد حصر العميل فيه):

يكتب ذلك سرّ العميل (client secret) في مجلد Hermes الرئيسي للـ profile النشط (مثل ~/.hermes/google_chat_user_client_secret.json للـ profile الافتراضي). ويكون client secret ضمن نطاق profile، لا مشتركًا بين profiles — ويسجّل كل profile سره الخاص. وهذا مقصود: فـ profiles حدود مصادقة معزولة، لذا يمكن لـ profile اثنين الإشارة إلى تطبيقات / حسابات Google OAuth مختلفة. سجّله مرة لكل profile يحتاج إلى تسليم مرفقات Google Chat.

التفويض لكل مستخدم (داخل المحادثة)

ينفّذ كل مستخدم هذا التدفق مرة واحدة، في محادثته المباشرة مع البوت:

  1. يرسلون /setup-files إلى البوت. ويرد بالحالة والخطوة التالية.
  2. يرسل /setup-files start، فيرد البوت بـ URL خاص بـ OAuth.
  3. يفتح الـ URL وينقر Allow، ثم يرى المتصفح يفشل في تحميل http://localhost:1/?...&code=.... وهذا الإخفاق متوقع — رمز المصادقة في شريط URL.
  4. ينسخون URL الفاشل (أو قيمة code=... وحدها) ويلصقونه في المحادثة بصيغة /setup-files <PASTED_URL>. ويبادله البوت بـ refresh token.

يُحفَظ الـ token في ~/.hermes/google_chat_user_tokens/<sanitized_email>.json. وتستخدم طلبات الملفات اللاحقة في الرسائل المباشرة لذلك المستخدم الـ token الخاص به ، فيرفع البوت بصفته ويصل المنشور إلى مساحته.

للإلغاء لاحقًا: /setup-files revoke يحذف token ذلك المستخدم وحده. ولا يمس tokens المستخدمين الآخرين.

النطاق (Scope)

يطلب التدفق نطاقًا واحدًا فقط: chat.messages.create. وهو يغطي كلًّا من media.upload واستدعاء messages.create الذي يشير إلى attachmentDataRef. ولا Drive ولا نطاقات Chat أوسع — فهذا أقل قدر من الصلاحيات عمدًا.

السلوك مع تعدد المستخدمين

عندما لا يملك السائل token خاصًا به بعد، يرجع البوت إلى token قديم لمستخدم واحد عند ~/.hermes/google_chat_user_token.json (إذا كان موجودًا من تثبيت سابق لدعم عدة مستخدمين). وإذا لم يتوفر أيهما، ينشر البوت إشعارًا نصيًا واضحًا يطلب من السائل تشغيل /setup-files.

لا يمسح إلغاء المستخدم إلا خانته الخاصة. و401/403 من token مستخدم واحد يخلي التخزين المؤقت لذلك المستخدم وحده. ولا يعطل المستخدمون بعضهم بعضًا.

استكشاف الأخطاء وإصلاحها

يبقى البوت صامتًا بعد إرسال "hola."

  1. تحقّق في وحدة التحكم مما إذا كان اشتراك Pub/Sub يحتوي على رسائل غير مُسلَّمة. إن وُجدت، فهذا يعني أن Hermes غير مُصادَق — تحقّق من GOOGLE_CHAT_SERVICE_ACCOUNT_JSON ومن أن الـ SA مُدرَج بدور Pub/Sub Subscriber على الاشتراك.
  2. إذا لم يكن في الاشتراك أي رسائل، فإن Google Chat لا ينشر الأحداث. تحقّق مجددًا من ربط IAM على الموضوع: يجب أن يمتلك chat-api-push@system.gserviceaccount.com الدور Pub/Sub Publisher.
  3. ابحث في سجلات hermes gateway عن [GoogleChat] Connected. إذا رأيت [GoogleChat] Config validation failed، تخبرك رسالة الخطأ بمتغير البيئة الذي يجب إصلاحه.

يرد البوت، لكن تظهر رسالة خطأ بدلًا من إجابة الوكيل.

افحص السجلات بحثًا عن [GoogleChat] Pub/Sub stream died — إذا تكررت، فقد تكون بيانات اعتماد SA قد دُوّرت أو حُذف الاشتراك. وبعد 10 محاولات يعلّم المحوّل نفسه بوصفه قاتلًا.

ظهور "403 Forbidden" مع كل رسالة صادرة.

أُزيل البوت من المساحة، أو ألغيته في لوحة Chat API. أعد تثبيته في المساحة (حدث ADDED_TO_SPACE سيعيد تفعيل المراسلة تلقائيًا).

يواصل البوت نشر إشعار "/setup-files" بدلًا من الملفات.

تسمح الحصص الافتراضية في Chat API بـ 60 رسالة لكل مساحة في الدقيقة. وإذا أنتج وكيلك ردود بث طويلة تتجاوز ذلك، يعيد المحوّل المحاولة بتراجع أُسّي — لكنك ستظل ترى زمن استجابة ظاهرًا للمستخدم. فكّر في ردود موجزة أو رفع الحصة في لوحة GCP.

يواصل البوت نشر إشعار "/setup-files" بدل الملفات.

لا يملك السائل OAuth token خاصًا به، ولا يوجد خيار احتياطي قديم. نفّذ /setup-files في رسائله المباشرة واتبع الخطوة 10. وبعد اكتمال التبادل، يرفع طلب الملف التالي الملف أصليًا دون إعادة تشغيل الـ gateway.

يعرض /setup-files start الرسالة "No client credentials stored."

لم يُنفَّذ الإعداد لمرة واحدة لهذا الـ profile (client secret ضمن نطاق profile، لذا لن يرى profile آخر تسجيلًا تحت أحد profiles). ومن الطرفية، نفّذه ضمن الـ profile الذي يستخدمه الـ gateway:

ثم أرسل /setup-files start مرة أخرى.

يعرض /setup-files <PASTED_URL> الرسالة "Token exchange failed."

رمز المصادقة صالح للاستخدام مرة واحدة وقصير العمر (عادةً بضع دقائق). أرسل /setup-files start للحصول على URL جديد وأعد المحاولة.

ملاحظات أمنية

  • نطاق Service Account: يطلب المحوِّل النطاقين chat.bot و pubsub. ينبغي أن يكون IAM هو أداة الإنفاذ الفعلية — امنح الـ SA الحد الأدنى (roles/pubsub.subscriber + roles/pubsub.viewer على الاشتراك)، لا أدوار Pub/Sub على مستوى المشروع أو المؤسسة.
  • حماية تنزيل المرفقات: لا يرفق Hermes bearer token الخاص بـ SA إلا بعناوين URL التي يطابق مضيفها قائمة سماح قصيرة من نطاقات Google (googleapis.com, drive.google.com, lh[3-6].googleusercontent.com، وبعض المضيفين الآخرين). ويُرفض أي مضيف آخر قبل طلب HTTP، للحماية من سيناريوهات SSRF التي قد يعيد فيها حدث معدّ بعناية توجيه bearer token إلى خدمة بيانات GCE الوصفية.
  • حجب البيانات: تُزال عناوين بريد Service Account ومسارات الاشتراك والـ topic من مخرجات السجل بواسطة agent/redact.py. ويمر تفريغ غلاف التصحيح (GOOGLE_CHAT_DEBUG_RAW=1) عبر مرشح الحجب نفسه ويُسجَّل بمستوى DEBUG.
  • الامتثال: إذا خططت لربط هذا البوت بمساحة عمل خاضعة للتنظيم (أي ذات سياسة لتوطين البيانات أو حوكمة الذكاء الاصطناعي)، فاحصل على تلك الموافقة قبل أول تثبيت.
  • نطاق OAuth للمستخدم: يطلب تدفق المرفقات لكل مستخدم فقط chat.messages.create — وهو الحد الأدنى الذي يغطي media.upload إضافة إلى استدعاء messages.create اللاحق. تُحفَظ الـ tokens بصيغة JSON نصية عادية في ~/.hermes/google_chat_user_tokens/<sanitized_email>.json (صلاحيات نظام الملفات هي الحماية — وهو نموذج ملف مفتاح SA نفسه). ويملك كل token مستخدم واحد فقط؛ ويقتصر الإلغاء على ذلك المستخدم.

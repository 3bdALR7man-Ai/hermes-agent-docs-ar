كتالوج الإضافات

كتالوج الإضافات دليل منتقى يراجعه البشر لإضافات Hermes التي يمكنك تثبيتها بالاسم عبر أمر واحد:

تصفّحه بصريًا على /docs/plugins — مع البحث، ومرشحات المستوى (Official / Community)، وشارات القدرات، وأوامر تثبيت قابلة للنسخ لكل إدخال.

يُكمّل الكتالوج نظام الإضافات الحالي — ولا يحل محله. فكل ما يمكنك تثبيته من الكتالوج هو في جوهره إضافة عادية؛ وكل ما يضيفه الكتالوج هو طبقة للاكتشاف وأخرى للمراجعة فوقها.

محتويات الإدخال

كل إدخال في الكتالوج ملف YAML صغير داخل مجلد plugin-catalog/ في مستودع hermes-agent، ويصرّح بما يلي:

الحقلالمعنى
nameمفتاح الكتالوج الذي تمرّره إلى hermes plugins install
repoمستودع git العام الخاص بالإضافة
shaالـ commit الدقيق المؤلف من 40 رمزًا ست عشريًا الذي خضع للمراجعة — تسحب عمليات التثبيت هذا الإصدار المثبّت، لا آخر commit في branch
tierofficial (تصونه NousResearch) أو community
maintainerمالك الإضافة
capabilitiesالأدوات والـ hooks والـ middleware المصرّح بها، ومتغيرات البيئة المطلوبة
requires_hermesالحد الأدنى لإصدار Hermes، مثل >=0.19 (اختياري)
platformsقيود نظام التشغيل، والقيمة الفارغة = الكل (اختياري)
docs_urlرابط توثيق خارجي (اختياري)

نموذج الثقة

صُمّم الكتالوج بحيث تعرف بالضبط ما الذي تثبّته:

  • قبول يدمجه البشر. يصل كل إدخال (وكل تحديث لإصدار مثبّت) عبر pull request يراجعه أحد المشرفين على المشروع. ولا يدخل أي شيء إلى الكتالوج تلقائيًا.
  • تثبيت على SHA دقيق. تثبّت الإدخالات commit محددًا، لا branch. فعندما يدفع مؤلف الإضافة كودًا جديدًا إلى مستودعه، لا يتغير ما يثبّته الكتالوج — إذ يتطلب تحديث الإصدار المثبّت PR آخر يخضع للمراجعة.
  • التصريح بالقدرات. تذكر الإدخالات مسبقًا الأدوات والـ hooks والـ middleware التي توفرها الإضافة، ومتغيرات البيئة (مفاتيح API وغيرها) التي تحتاج إليها، لتتمكن من تقدير نطاق تأثيرها المحتمل قبل التثبيت.
  • قائمة الإضافات المسحوبة. تُدرج الإضافات التي تُسحب من الكتالوج (مثلًا بعد حادث أمني) في plugin-catalog/removed.yaml مع السبب والتاريخ. ويرفض المُثبّت تثبيت أي شيء مدرج في هذه القائمة.
  • التثبيت ≠ التفعيل. يضع تثبيت إضافة من الكتالوج ملفاتها على القرص؛ وكأي إضافة، يجب تفعيلها قبل أن تُحمَّل. راجع Plugins → Enabling and disabling.
مراجعة الكتالوج مراجعة في لحظة زمنية محددة

يعني وجود إدخال في الكتالوج أن شخصًا اطّلع على الـ commit المثبّت، وأن تصريحات القدرات فُحصت، وأن المستودع استوفى معايير التقديم. وهذا ليس تدقيقًا أمنيًا، ولا يقول شيئًا عن أي commits أخرى في المستودع نفسه. راجع كود أي شيء تمنحه بيانات اعتماد.

التثبيت من الكتالوج

تعرض رسالة التثبيت ملخص قدرات الإدخال — الأدوات والـ hooks المصرّح بها ومتغيرات البيئة المطلوبة — قبل استنساخ أي شيء.

قد يختلف اسم الإدخال في الكتالوج عن الاسم الوارد في manifest الإضافة نفسها؛ يطبع hermes plugins install الاسم الذي ثُبّتت به الإضافة، وهو الاسم الذي يأخذه enable. فعلى سبيل المثال، يُثبَّت الإدخال touchdesigner (وهو حزمة Agent Plugins v1 محمولة تضم خادم twozero MCP مع المهارة touchdesigner-mcp) باسم td، وقد اختير قصيرًا كي تبقى أسماء أدوات MCP المولَّدة منه ضمن حدود أسماء الدوال لدى المزوّدين:

تحديث إضافة مثبّتة من الكتالوج

لا ينفّذ hermes plugins update <name> الأمر git pull أبدًا مع الإضافات المثبّتة من الكتالوج — بل يقارن الإصدار المثبّت لديك بالإصدار المثبّت حاليًا في الكتالوج، وعندما يتغير الكتالوج (عبر PR خضع للمراجعة)، يعيد التثبيت قسرًا على قيمة SHA الجديدة. وتُحفظ حالة التفعيل أو التعطيل لديك. يعرض hermes plugins list الإضافات المثبّتة من الكتالوج بالشكل catalog:<tier>@<sha> كي ترى مصدرها بنظرة سريعة.

الأسماء غير الموجودة في الكتالوج

يُعدّ استخدام اسم مجرد لا يقابله إدخال في الكتالوج خطأً: إذ لا يوجد فهرس أسماء ثانٍ غير مُراجَع. ثبّت مثل هذه الإضافات بدلًا من ذلك عبر owner/repo أو رابط Git (مصدر مخصص، انظر أدناه)، أو قدّمها إلى الكتالوج.

التحديث المباشر

تنشر عملية بناء التوثيق الكتالوج كمستند JSON واحد (https://hermes-agent.nousresearch.com/docs/api/plugin-catalog.json). تجلبه الأوامر search/install/update مرة كل ست ساعات على الأكثر وتخزّنه مؤقتًا تحت ~/.hermes/cache/، بحيث تصل الإدخالات الجديدة وعمليات الإزالة إلى العملاء المثبّتين دون الحاجة إلى تحديث Hermes. وفي وضع عدم الاتصال، تُستخدم النسخة المرفقة مع النسخة المسحوبة (checkout) لديك. وتُطبَّق دائمًا عمليات الإزالة الواردة في القائمة الموجودة داخل المستودع وفي القائمة المباشرة معًا.

روابط git المخصصة مختلفة

لا يزال hermes plugins install <git-url> يعمل مع أي مستودع، لكنه يتجاوز الكتالوج كليًا:

  • لا مراجعة — تحصل على ما هو موجود في آخر commit على الـ branch، لا على إصدار مثبّت خضع للمراجعة.
  • يُعرض شريط تحذير للتوضيح بأن الكود لم يخضع للتدقيق.
  • تظل قائمة الإضافات المسحوبة تُراجَع (فيُرفض المستودع المعروف بخطورته استنادًا إلى رابطه).

استخدم مسار رابط git لإضافاتك الخاصة وللمستودعات التي تثق بها أصلًا؛ واستخدم الكتالوج للاكتشاف.

تقديم إضافة إلى الكتالوج

تكون طلبات التقديم على شكل pull requests تضيف ملفًا واحدًا plugin-catalog/<name>.yaml. توجد قائمة التحقق الكاملة في ملف README الخاص بـ plugin-catalog؛ وباختصار، يجب أن يكون الإدخال:

  1. مقدَّمًا من المالك — أي أن مؤلف الـ PR يملك مستودع الإضافة أو يصونه.
  2. مستودعًا عامًا — أي أن رابط repo قابل للاستنساخ علنًا.
  3. مُصدَرًا — أي أن للمستودع إصدارات أو وسومًا (tags) فعلية، لا مجرد branch افتراضي.
  4. ناجحًا في التحقق — أي أن GitHub Action الخاص بالتحقق من الكتالوج يظهر باللون الأخضر على الـ PR (المخطط، وصيغة SHA، وإمكانية الوصول).
  5. مثبّتًا على كود مستقر — أي أن عمر الـ SHA المثبّت لا يقل عن أسبوعين، كي لا يشير الكتالوج أبدًا إلى كود دُفع قبل المراجعة بلحظات.

تتبع تحديثات الإصدارات المثبّتة (رفع قيمة sha إلى commit أحدث) عملية الـ PR والمراجعة نفسها.

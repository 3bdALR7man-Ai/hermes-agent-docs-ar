كتالوج الإضافات

كتالوج الإضافات دليل منتقى يراجعه البشر لإضافات Hermes التي يمكنك تثبيتها بالاسم عبر أمر واحد:

تصفّحه بصريًا على /docs/plugins — تُرتّب الإدخالات على رفوف بحسب الفئة (Memory و Desktop و Platforms و Web & Browser و Tools و Voice و Automation و Models)، مع البحث ومرشحات المستوى (Official / Verified / Community) وشارات الإمكانيات وأوامر تثبيت قابلة للنسخ لكل إدخال.

لكل إدخال أيضًا صفحة خاصة في /docs/plugins/<name> (انقر بطاقة): الوصف الكامل وأي إفصاح و commit المثبّت والأدوات و hooks ومتغيرات البيئة وزر تثبيت Desktop وأمر CLI ولقطات الشاشة الاختيارية و README من commit المُراجع، ورف More by this author. للمؤلفين صفحة في /docs/plugins/by/<maintainer> تسرد كل ما يصونونه في الكتالوج. تُولّد الصفحتان وقت البناء من ملفات الكتالوج نفسها، لذا لا تتغير الصفحة إلا بدمج PR.

يكمّل الكتالوج — ولا يستبدل — الآليات الحالية نظام الإضافات الحالي — ولا يحل محله. فكل ما يمكنك تثبيته من الكتالوج هو في جوهره إضافة عادية؛ وكل ما يضيفه الكتالوج هو طبقة للاكتشاف وأخرى للمراجعة فوقها.

خلال التهيئة الأولية في Desktop، يمكن لدليل الإعداد أيضًا عرض إضافات الكتالوج والمهارات عبر بطاقة موافقة. يُثبّت كل صف في profile default الخاص بك فقط عند النقر على Install، وبـ commit المُراجع نفسه الذي تصفه هذه الصفحة.

محتويات الإدخال

كل إدخال في الكتالوج ملف YAML صغير داخل مجلد plugin-catalog/ في مستودع hermes-agent، ويصرّح بما يلي:

subdirالمسار إلى الإضافة داخل المستودع للمستودعات المتعددة المشاريع — مسار نسبي عادي يطابق [A-Za-z0-9._/-]+ (دون .., . أو مقاطع فارغة أو صيغ مطلقة أو شرطات مائلة عكسية) (اختياري، الافتراضي جذر المستودع)

docs_urlرابط توثيق خارجي (اختياري)

versionتسمية مقروءة لـ sha المثبّت، مثل "1.4.0" ؛ تُعرض كـ 1.4.0 @ abcd1234 في CLI وبطاقة الكتالوج وزر Update to في Desktop (اختياري، شكلي)
imageصورة لافتة لبطاقة الكتالوج والجزء الرئيسي لصفحة الإضافة، تُعرض بنسبة 2:1 (1200×600 مناسب؛ تُقص الأشكال الأخرى من الوسط)؛ عنوان https URL على raw.githubusercontent.com, github.com أو *.githubusercontent.com (اختياري). ثبّتها على commit الإدخال (raw.githubusercontent.com/owner/repo/<sha>/...) حتى لا تتغير بعد المراجعة
screenshotsحتى 6 صور تُعرض كمعرض على صفحة الإضافة، مع قاعدة المضيف نفسها الخاصة بـ image (اختياري). ثبّتها أيضًا على commit الإدخال
readmeتعرض صفحة الإضافة README المستودع (أولًا subdir للإدخال، وإلا جذر المستودع) افتراضيًا. يُجلب من commit المثبّت عند بناء التوثيق — لا من branch أبدًا — فتعرض الصفحة README الذي قرأه المُراجع، ولا تتغير إلا عند تغيير التثبيت. اضبط false لإخفائه. مستودعات GitHub و GitLab (اختياري، الافتراضي true)

نموذج الثقة

صُمّم الكتالوج بحيث تعرف بالضبط ما الذي تثبّته:

  • قبول يدمجه البشر. يصل كل إدخال (وكل تحديث لإصدار مثبّت) عبر pull request يراجعه أحد المشرفين على المشروع. ولا يدخل أي شيء إلى الكتالوج تلقائيًا.
  • تثبيت على SHA دقيق. تثبّت الإدخالات commit محددًا، لا branch. فعندما يدفع مؤلف الإضافة كودًا جديدًا إلى مستودعه، لا يتغير ما يثبّته الكتالوج — إذ يتطلب تحديث الإصدار المثبّت PR آخر يخضع للمراجعة.
  • التصريح بالقدرات. يشغّل CI القبول ماسح الأمان نفسه الذي يشغّله المُثبّت (تتضمن hermes plugins validate فحص security scan): تؤدي نتيجة dangerous إلى رفض الإدخال، وتُسرد نتائج caution للمُراجع. لأن المُراجع رآها، لا يتوقف تثبيت الكتالوج المسحوب عند SHA المثبّت بالضبط ليسأل عن caution مرة أخرى؛ يظل dangerous يمنع، ويخضع كل ما يُثبّت من URL خام أو إصدار آخر لـ prompt العادي.
  • تعمل إضافات Desktop بصلاحية التطبيق — والمراجعة هي الحد الفاصل. يُقيَّم desktop/plugin.js الخاص بالإضافة داخل تطبيق Desktop نفسه، في الحيز نفسه الذي يعمل فيه كود التطبيق: لا يوجد sandbox، ويمكنه فعل كل ما يستطيع التطبيق فعله (gateway RPC وجسر window.hermesDesktop الكامل وتخزين إضافات أخرى). ما يحميك هو نموذج الثقة أعلاه — قرأ إنسان الـ commit المثبّت نفسه، والتثبيت هو ذلك الـ commit — مع آليتي إنذار: يرفض فحص desktop surface في القبول الخطوات الواضحة خارج SDK الإضافات (eval، واستيراد أي شيء غير @hermes/plugin-sdk/react، بما فيه السكربتات البعيدة)، ويرفض محمّل التطبيق كل استيراد خارج SDK مجددًا وقت التحميل. يقرأ الفاحص regex من <script — حرفيًا أو كسلسلة النمط في new RegExp(...) مُمرَّرة مباشرة إلى .replace()/.split()/.match() أو مستخدمة كـ .test()/.exec() — بوصفها أداة تنقية، لا حقنًا؛ وتظل سلسلة <script المكتوبة إلى DOM، بما فيها المبنية من new RegExp(...).source، مرفوضة. تعامل مع الفاحص كمعين للمراجعة، لا كضمان؛ وافحص جزء Desktop بالدقة نفسها التي تفحص بها جزء Python.
  • لا تجاوزات لـ Hermes وقت التشغيل. توسّع الإضافات المدرجة Hermes عبر واجهاته العامة (hooks و middleware و profiles المزوّدين ومواضع Desktop SDK)، ولا تستبدل وظائف الجوهر أو أساليبه أو واجهة Desktop في مكانها مطلقًا: إضافتان ترقّعان نقطة الوصل نفسها تكسر إحداهما الأخرى، وقد يكسر إصدار الجوهر كلتيهما. يرفض فحص no core override في القبول Python الذي يعيد ربط وحدات Hermes أو أصنافه أو جداولها وقت التشغيل، ويرفض فحص desktop surface كود desktop/plugin.js الذي يستعلم عن markup التطبيق نفسه لإعادة تنسيق واجهة الجوهر أو إخفائها أو النقر عليها أو إعادة كتابتها.
  • إعلانات الإمكانيات. تذكر الإدخالات مقدمًا الأدوات و hooks و middleware التي توفّرها الإضافة، ومتغيرات البيئة (مفاتيح API وغيرها) التي تحتاجها، لتقدّر نطاق أثرها قبل التثبيت.
  • قائمة الإضافات المسحوبة. تُدرج الإضافات التي تُسحب من الكتالوج (مثلًا بعد حادث أمني) في plugin-catalog/removed.yaml مع سبب وتاريخ. تكون المطابقة بالاسم أو هوية المستودع — صيغ git@, ssh://, http:// و www. للمستودع نفسه كلها تتطابق. يرفض المُثبّت تثبيت أي شيء في قائمة الإزالة، والإضافة التي تدخل القائمة بعد تثبيتها تتوقف عن التحديث، ولا يمكن تفعيلها وتُرفض وقت التحميل (hermes plugins remove <name> ، أو أعد تثبيتها باستخدام --allow-removed للاحتفاظ بها عن علم).
  • التثبيت ≠ التفعيل. يضع تثبيت إضافة من الكتالوج ملفاتها على القرص؛ وكأي إضافة، يجب تفعيلها قبل أن تُحمَّل. راجع الإضافات → التفعيل والتعطيل.
مراجعة الكتالوج مراجعة في لحظة زمنية محددة

يعني وجود إدخال في الكتالوج أن شخصًا اطّلع على الـ commit المثبّت، وأن تصريحات القدرات فُحصت، وأن المستودع استوفى معايير التقديم. وهذا ليس تدقيقًا أمنيًا، ولا يقول شيئًا عن أي commits أخرى في المستودع نفسه. راجع كود أي شيء تمنحه بيانات اعتماد.

التثبيت من الكتالوج

يعرض prompt التثبيت ملخّص إمكانيات الإدخال — الأدوات المعلنة و hooks ومتغيرات البيئة المطلوبة — قبل استنساخ أي شيء. في الطرفية، يسأل بعد ذلك "Enable now?"، فيصبح الأمران أعلاه خطوة واحدة عندما تجيب نعم (--enable / --no-enable يجيبان عنه للسكربتات).

قد يختلف اسم الكتالوج عن اسم manifest الإضافة. كل أمر لاحق (enable, disable, show, capabilities, update, remove) يقبل أيًا منهما: يُحدّد اسم الكتالوج عبر سجل التثبيت الذي كتبه Hermes عند استنساخ الإدخال، لا عبر ملف في مستودع الإضافة نفسه. مثلًا، touchdesigner (وهو حزمة Agent Plugins v1 محمولة تضم خادم twozero MCP مع المهارة touchdesigner-mcp) باسم td ، وقد اختير قصيرًا كي تبقى أسماء أدوات MCP المولَّدة منه ضمن حدود أسماء الدوال لدى المزوّدين:

في تطبيق Desktop، الحزمة التي تملك جزء وكيل وجزء Desktop (desktop/plugin.js) تظهر صفًا واحدًا مع مفتاح لكل جزء. تفعيل الحزمة (بتثبيتها من حوار التثبيت، وهو ما يفعّلها، أو عبر مفتاح Agent في الصف) يفعّل جزء Desktop أيضًا، ما لم تكن قد عطّلت ذلك الجزء بنفسك. يبقى التعطيل خاصًا بكل جزء، لأن جزء Desktop مشترك بين كل الـ profiles.

يمكن للحزم المحمولة أيضًا حمل خادم MCP عبر stdio. الـ snyk إصدارًا محددًا من Snyk CLI ‏(npx -y snyk@<version> mcp) ويضم المهارة snyk-security-scan ، بحيث يمنح تثبيت واحد Hermes القدرة على فحص الكود والاعتماديات والحاويات و IaC، إضافةً إلى سير العمل اللازم لاستخدامها؛ ويتطابق هنا اسم الكتالوج مع اسم الـ manifest:

تحديث إضافة مثبّتة من الكتالوج

hermes plugins update <name> الأمر git pull لتثبيتات الكتالوج — يقارن التثبيت المثبّت لديك بتثبيت الكتالوج الحالي، وعندما يتحرك الكتالوج (عبر PR مُراجع)، يجهّز SHA الجديد ويتحقق من اعتمادياته قبل نشره. تُحفظ حالة التفعيل/التعطيل، وكذلك الملفات التي لا يتتبعها مستودع الإضافة (ملف config.yaml المنشأ من .example وملفات البيانات و .env). لا تُتبع الروابط الرمزية بين الملفات غير المتتبعة إلى الكود الجديد مطلقًا: يتوقف التحديث قبل النشر ويذكرها، فاستبدل كلًا منها بملف عادي. لا تُنقل مجلدات الاعتماديات والتخزين المؤقت (.venv/, venv/, node_modules/ وذاكرات الأدوات المؤقتة) أصلًا، بما فيها الروابط؛ وتعيد الإضافة المحدّثة بناء اعتمادياتها. لتثبيتات المستودعات المتعددة المشاريع/المجلدات الفرعية، التي لا تحمل نسخة Git مسحوبة محليًا، يحفظ التحديث ملفات حالة المستخدم التي لا يأتي بها الإصدار الجديد. يظل كود الإضافة وواجهات التحكم ملكًا للإصدار، ولا يُعاد إحياؤها من التثبيت القديم: الملفات المصدرية (Python و JavaScript/TypeScript بما فيها .mjs/.cjs/.jsx/.tsx ، shell و Ruby و Perl و PHP)، ومجلدات dashboard/, desktop/, skills/, sidecar/ و node_modules/ العليا، و manifest الإضافة و mcp.json و بيانات الاعتماديات الوصفية (pyproject.toml, package.json و lockfiles). إذا تعارض مسار حالة مستخدم مع تخطيط الملفات/المجلدات للشجرة الجديدة، يتوقف التحديث قبل النشر لتبقى النسخة المثبّتة — وبيانات المستخدم — سليمة. لا تُنقل تعديلاتك على الملفات المتتبعة إلى الكود الجديد؛ تُحفظ نسخ تحت ~/.hermes/plugins-backup/<name>-<sha>/ ويحذّرك التحديث. إذا غيّر التثبيت الجديد اسم manifest الإضافة، يُزال المجلد القديم وتنتقل علامة التفعيل إلى الاسم الجديد. hermes plugins list الإضافات المثبّتة من الكتالوج بالشكل catalog:<tier>@<sha> كي ترى مصدرها بنظرة سريعة.

يتحقق PM من اعتماديات الإضافة النشطة قبل أن يحل كودها الجديد محل الإصدار المثبّت. فشل الإصدار أو الفحص أو الاعتماديات أو النشر يبقي الكود العامل واختيار الاعتماديات. تبقى الإضافات المعطّلة معطّلة. يسجّل المُثبّت المنشأ في ~/.hermes/plugins/.install-metadata.json ، خارج شجرة الإضافة نفسها — لا يستطيع مستودع شحن ملف يجعلها تبدو كتثبيت كتالوج مُراجع. (الـ .hermes-catalog.json داخل مجلد الإضافة نسخة للتسهيل فقط.) تثبيت إدخال كتالوج باستخدام --ref <sha> يسجّل SHA الذي سحبته فعليًا، لذا فإن list وتبويب Plugins في Desktop و update كلها تعرضه كخارج التثبيت المُراجع. تحتفظ إضافات Git المخصصة بسياسة تحديث Git/feed المسجّلة، لكنها تستخدم مسار التحقق والنشر نفسه لدى PM.

الأسماء غير الموجودة في الكتالوج

يُعدّ استخدام اسم مجرد لا يقابله إدخال في الكتالوج خطأً: إذ لا يوجد فهرس أسماء ثانٍ غير مُراجَع. ثبّت مثل هذه الإضافات بدلًا من ذلك عبر owner/repo أو رابط Git (مصدر مخصص، انظر أدناه)، أو قدّمها إلى الكتالوج.

التحديث المباشر

تنشر عملية بناء التوثيق الكتالوج كمستند JSON واحد (https://hermes-agent.nousresearch.com/docs/api/plugin-catalog.json). search/install/update مرة كل ست ساعات على الأكثر وتخزّنه مؤقتًا تحت ~/.hermes/cache/ ، فتصل الإدخالات الجديدة والإزالات إلى العملاء المثبّتين دون تحديث Hermes. دون اتصال، تُستخدم النسخة المؤقتة حتى 24 ساعة، ثم تحل محلها النسخة المشحونة مع نسختك المسحوبة (يُتذكر فشل الجلب لدقيقة، فلا يدفع plugins list وصفحة Plugins في لوحة التحكم إلا مهلة اتصال واحدة كحد أقصى، لا مهلة لكل إضافة). عندما تختلف الوثيقة المؤقتة ونسختك المسحوبة في تثبيت إدخال، تتقدم الأحدث — نسخة git التي اعتُمد كتالوجها بعد نشر الوثيقة (نتيجة hermes update جديدة) تثبّت قيمتها، لا القيمة الأقدم المؤقتة. تُفرض الإزالات من القائمة داخل الشجرة والقائمة الحيّة كلتاهما دائمًا، مهما كان عمر التخزين المؤقت.

روابط git المخصصة مختلفة

hermes plugins install <git-url> يعمل مع أي مستودع، لكنه يتجاوز الكتالوج كليًا:

  • لا مراجعة — تحصل على ما هو موجود في آخر commit على الـ branch، لا على إصدار مثبّت خضع للمراجعة.
  • يُعرض شريط تحذير للتوضيح بأن الكود لم يخضع للتدقيق.
  • تظل قائمة الإضافات المسحوبة تُراجَع (فيُرفض المستودع المعروف بخطورته استنادًا إلى رابطه).

استخدم مسار رابط git لإضافاتك الخاصة وللمستودعات التي تثق بها أصلًا؛ واستخدم الكتالوج للاكتشاف.

تقديم إضافة إلى الكتالوج

تكون طلبات التقديم على شكل pull requests تضيف ملفًا واحدًا plugin-catalog/<name>.yaml الملف. توجد الإرشادات الكاملة في التقديم إلى كتالوج الإضافات: ما يجب فحصه قبل التقديم، وكيف يعمل PR والمراجعة، وكل قاعدة قبول، وكيف تعمل تحديثات التثبيت وإلغاء الإدراج والإزالة. تعكس الصفحة القواعد المرجعية في ملف README الخاص بـ plugin-catalog.

باختصار، يُقدّم الإضافة المدرجة مالكها (أو تُضاف في جولة صيانة مُراجعة)، وتوجد في مستودع عام، وتثبّت commit دقيقًا، وتجتاز hermes plugins validate في CI الكتالوج، ولا تحدّث نفسها مطلقًا، وتوسّع Hermes فقط عبر hooks العامة و Desktop SDK، لا بترقيع كود الجوهر أو واجهة Desktop وقت التشغيل.

انظر أيضًا

  • الإضافات (Plugins) — نظام الإضافات نفسه: صيغة الـ manifest، والتفعيل، والإعدادات
  • الإضافات المدمجة — الإضافات التي تأتي مع Hermes
  • بناء إضافة لـ Hermes — اكتب إضافتك الخاصة
  • صفحة كتالوج الإضافات — الكتالوج القابل للتصفح
  • التقديم إلى كتالوج الإضافات — قواعد القبول ودليل التقديم

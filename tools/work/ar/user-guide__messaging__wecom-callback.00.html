WeCom Callback (تطبيق مُخصّص)

اربط Hermes بـ WeCom (WeChat للمؤسسات) كتطبيق مؤسسي مُخصّص (self-built) باستخدام نموذج callback/webhook.

WeCom Bot مقابل WeCom Callback

يدعم Hermes وضعين للتكامل مع WeCom:

  • WeCom Bot — بأسلوب البوت، ويتصل عبر WebSocket. إعداده أبسط، ويعمل في المحادثات الجماعية.
  • WeCom Callback (هذه الصفحة) — تطبيق مُخصّص يستقبل استدعاءات callback بصيغة XML مشفّرة. يظهر كتطبيق أساسي في الشريط الجانبي لـ WeCom لدى المستخدمين. ويدعم التوجيه عبر عدة مؤسسات (multi-corp routing).

راجع أيضًا: WeCom Bot للتكامل بأسلوب البوت.

نفّذ hermes gateway setup واختر WeCom Callback للحصول على إرشاد خطوة بخطوة.

آلية العمل

  1. تسجّل تطبيقًا مُخصّصًا في WeCom Admin Console
  2. يدفع WeCom رسائل XML مشفّرة إلى HTTP callback endpoint الخاص بك
  3. يفك Hermes تشفير الرسالة ويضعها في طابور الوكيل
  4. يُرسل إقرار بالاستلام فورًا (بصمت — لا يُعرض شيء للمستخدم)
  5. يعالج الوكيل الطلب (عادةً من 3 إلى 30 دقيقة)
  6. يُسلَّم الرد استباقيًا عبر واجهة message/send API في WeCom

المتطلبات المسبقة

  • حساب مؤسسة على WeCom بصلاحيات المسؤول
  • حزمتا Python aiohttp و httpx (مضمّنتان في التثبيت الافتراضي)
  • خادم يمكن الوصول إليه علنًا لاستضافة callback URL (أو نفق مثل ngrok)

الإعداد

1. إنشاء تطبيق مُخصّص في WeCom

  1. انتقل إلى WeCom Admin Console → Applications → Create App
  2. دوّن Corp ID الخاص بك (يظهر أعلى لوحة المسؤول)
  3. في إعدادات التطبيق، أنشئ Corp Secret
  4. دوّن Agent ID من صفحة نظرة عامة على التطبيق
  5. ضمن Receive Messages، اضبط callback URL:
    • URL: http://YOUR_PUBLIC_IP:8645/wecom/callback
    • Token: أنشئ token عشوائيًا (يوفّر WeCom واحدًا)
    • EncodingAESKey: أنشئ مفتاحًا (يوفّر WeCom واحدًا)

التشفير

جميع حمولات callback مشفّرة بـ AES-CBC باستخدام EncodingAESKey. ويتولى المحوّل ما يلي:

  • الوارد: فك تشفير حمولة XML والتحقق من توقيع SHA1
  • الصادر: تُرسل الردود عبر API الاستباقي (وليس عبر رد callback مشفّر)

تطبيق التشفير متوافق مع WXBizMsgCrypt SDK الرسمي من Tencent.

القيود

  • لا يوجد بث مباشر — تصل الردود كرسائل كاملة بعد أن ينتهي الوكيل
  • لا توجد مؤشرات كتابة — لا يدعم نموذج callback حالة الكتابة
  • نص فقط — يدعم حاليًا الرسائل النصية كمدخلات؛ ولم يُنفَّذ بعد إدخال الصور أو الملفات أو الرسائل الصوتية. ويدرك الوكيل قدرات إرسال الوسائط الصادرة عبر تلميح منصة WeCom (الصور والمستندات والفيديو والصوت).
  • زمن الاستجابة — تستغرق جلسات الوكيل من 3 إلى 30 دقيقة؛ ويرى المستخدمون الرد عند اكتمال المعالجة

استكشاف الأخطاء وإصلاحها

فشل التحقق من التوقيع. يوقّع WeCom كل طلب باستخدام Token الذي سجّلته في لوحة المسؤول. والسبب الأكثر شيوعًا هو عدم التطابق بين الـ token المضبوط في Hermes والـ token الذي تتوقعه لوحة المسؤول. انسخ مجددًا كلًّا من Token و EncodingAESKey من لوحة المسؤول — فمن السهل اقتطاع جزء منهما. كما أن المسافات البيضاء في قيم ~/.hermes/.env حول = تُفسد فحوص التوقيع أيضًا. بعد الإصلاح، أعد تشغيل hermes gateway run.

تعذّر الوصول إلى callback URL / فشل خطوة التحقق. يتصل WeCom بالـ URL العام الذي سجّلته. تأكد مما يلي:

  1. أن الـ reverse proxy أو النفق يمرّر /wecom/callback إلى منفذ الـ gateway.
  2. أن الـ URL في لوحة المسؤول يستخدم HTTPS (يرفض WeCom بروتوكول HTTP العادي).
  3. أن تنفيذ curl -i https://<your-domain>/wecom/callback من خارج شبكتك يُرجع شيئًا غير انتهاء المهلة (لا بأس برمز 4xx دون معاملات استعلام — فهذا يعني فقط أنه يمكن الوصول إلى المستمع).

تعذّر الوصول إلى المنفذ / المستمع غير مربوط. راجع سجلات hermes gateway run لمعرفة المضيف/المنفذ المربوط. إذا ارتبط المحوّل بـ 127.0.0.1 فيجب أن تضع أمامه reverse proxy أو نفقًا — إذ لا تستطيع خوادم WeCom الوصول إلى واجهة loopback. اترك extra.host دون ضبط ليُطبَّق الربط الافتراضي dual-stack (جميع الواجهات، IPv4+IPv6)، أو ثبّت واجهة محددة في config.yaml (مع allowed_source_cidrs إذا كنت تعرضه مباشرةً)، أو أبقِ على loopback واستخدم نفقًا مثل Cloudflare Tunnel / nginx.

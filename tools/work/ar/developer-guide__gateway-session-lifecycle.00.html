دورة حياة الجلسة

الجمهور المستهدف: مطوّرو الـ gateway والقائمون بصيانته ملفات المصدر: gateway/session.py (نحو 1200 سطر + الملفات session_*.py المجاورة)، gateway/run.py (نحو 5500 سطر للواجهة + مراحل run_*.py )، gateway/config.py آخر تحديث: 2026-06-16

نظرة عامة

تمثل الجلسة محادثة متواصلة بين الوكيل ومستخدم واحد أو أكثر على منصة مراسلة. وتحكم دورة حياة الجلسة متى تبقى المحادثات، ومتى تُعاد ضبطها، وكيف تصمد أمام إعادة تشغيل الـ gateway، وكيف تصطف الرسائل أثناء العمليات المتزامنة.

يوجد نظام الجلسات أساسًا في وحدتين:

  • gateway/session.py — نموذج البيانات (SessionSource, SessionEntry, SessionContext)، وتوليد المفاتيح (build_session_key)، والمخزن الرئيسي (SessionStore).
  • gateway/run.py — واجهة مشغّل الـ gateway (GatewayRunner) التي تربط الجلسات بـ pipeline معالجة الرسائل؛ وتوجد المراحل في ملفات run_*.py المجاورة: صيانة الجلسات (run_watchers.py)، والتخزين المؤقت للوكلاء (run_agent_cache.py)، والاستعادة بعد إعادة التشغيل (session_recovery.py)، وإدراج الرسائل في الطابور (run_busy.py).

1. SessionSource — واصف منشأ الرسالة

SessionSource سجل مجمّد لـ مصدر الرسالة. ويُرفَق بكل MessageEvent وارد ويُستخدم للتوجيه والعزل وحقن السياق.

منطق انتقال الحالة (get_or_create_session)

ترتيب الأولوية في get_or_create_session():

  1. suspended=True → فرض إعادة الضبط دائمًا (مسح صارم)
  2. resume_pending=True → الاحتفاظ بـ session_id (استعادة مرنة)
  3. لا محفّز → إعادة العنصر الحالي (تحديث updated_at)

3. SessionStore — التخزين والعمليات

SessionStore طبقة التخزين الرئيسية. تحتفظ بـ dict في الذاكرة (_entries) محفوظة في sessions.json، مع SQLite (SessionDB) كمخزن معتمد للبيانات الوصفية للجلسات ونصوص المحادثات.

المُنشئ

  • sessions_dir — الدليل الذي يوجد فيه sessions.json .
  • config — GatewayConfig نسخة لإعدادات التوجيه والصيانة.
  • has_active_processes_fn — callback اختياري مفتاحه session_key لفحص عمليات الخلفية الجارية. وتُحمى الجلسات ذات العمليات النشطة من تقليم عناصر التوجيه.

الدوال المساعدة الداخلية

  • _ensure_loaded() / _ensure_loaded_locked() — تحميل sessions.json إلى _entries dict.
  • _save() — كتابة ذرية إلى sessions.json عبر ملف مؤقت + atomic_replace.
  • _generate_session_key(source) — يفوّض إلى build_session_key() مع معاملات الإعدادات.

تنظيم التخزين

مخزن نصوص المحادثات المعتمد هو SQLite عبر SessionDB (من hermes_state). ويحفظ ملف sessions.json ربط session_key → session_id والبيانات الوصفية للعناصر (العلامات، والطوابع الزمنية، وأعداد tokens). وإذا لم تتوفر SQLite، يعود المخزن إلى JSONL، لكن هذا مسار تدهور.

4. قواعد توليد SessionKey

مفاتيح الجلسات سلاسل حتمية تحدد مسار محادثة. وتُولَّد بواسطة build_session_key(source, group_sessions_per_user, thread_sessions_per_user).

تمر أرقام هواتف WhatsApp عبر canonical_whatsapp_identifier() التي تزيل اللاحقة @s.whatsapp.net وتطبّع إلى صيغة E.164. يمنع هذا تفتّت الجلسة حين يعيد الجسر أشكالًا مختلفة للاسم البديل لرقم الهاتف نفسه.

5. استراتيجية العزل متعدد المستخدمين

يحدد العزل متعدد المستخدمين ما إذا كان عدة مستخدمين في المحادثة نفسها يتشاركون محادثة أو يحصل كل منهم على جلسة خاصة.

الأثر على system prompt

عندما يكون shared_multi_user_session=True، يحذف system prompt اسم المستخدم الثابت ويذكر بدلًا منه: "Multi-user {thread|session} — messages are prefixed with [sender name]. Multiple users may participate." يضيف الـ gateway أسماء المرسلين الأفراد في بداية كل رسالة مستخدم وقت التشغيل، مع الحفاظ على تخزين الـ prompt المؤقت (لا يتغير system prompt لكل دور).

6. الحدود الصريحة للمحادثة

لا يدوّر الخمول ولا الزمن الفعلي المحادثة مطلقًا. /new و /reset ينشئان حدًا صريحًا؛ ويستمر ضغط السياق في إدارة السجلات الطويلة. وتُتجاهَل إعدادات المؤقّت القديمة.

يظل التعليق الصريح ينشئ حدًا عند الدور الوارد التالي. وتحترم الاستعادة الحدود الصريحة والمنتهية تاريخيًا بدل إعادة فتحها. ويبقي الإخلاء الخاص بالموارد وحدها وتنظيف WebSocket اليتيم المحادثات قابلة للاستئناف.

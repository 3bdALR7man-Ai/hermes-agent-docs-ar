بناء إضافة مزوّد ذاكرة (Memory Provider Plugin)

تمنح إضافات مزوّدي الذاكرة Hermes Agent معرفة دائمة عبر الجلسات تتجاوز MEMORY.md وUSER.md المدمجين. يغطي هذا الدليل كيفية بناء واحدة.

نصيحة

مزوّدو الذاكرة هم أحد نوعين من إضافات المزوّد (provider plugin). الآخر هو إضافات Context Engine، التي تستبدل ضاغط السياق المدمج. يتبع كلاهما النمط نفسه: اختيار أحادي، مبني على الإعدادات، يُدار عبر hermes plugins.

تخطيطات التثبيت

يكتشف Hermes مزوّدي الذاكرة من أربعة مصادر، بترتيب الأولوية هذا:

ملاحظة

هذا عكس ترتيب "الأحدث يفوز" في نظام الإضافات العام. يُفعَّل مزوّد الذاكرة بـالاسم (memory.provider)، لذا فإن الحجب قد يعيد توجيه ذاكرة الوكيل بصمت بدلًا من مجرد استبدال أداة.

الاكتشاف يُعدِّد فقط — ولا يستورد مزوّدًا أبدًا. لا يعمل شيء حتى يسمّيه memory.provider.

نتائج prefetch كبيرة الحجم بشكل زائد

نتائج prefetch() الخارجية التي تتجاوز عتبة الفيضان المضبوطة تُكتب إلى ملف فيضان خاص وتُستبدَل بمعاينة رأس/ذيل مضبوطة. تتضمن المعاينة المسار بحيث يمكن للوكيل قراءة النتيجة الكاملة عند الحاجة الفعلية إليها. النتائج التي تساوي العتبة أو تقل عنها تُعاد دون تغيير.

يستخدم هذا إعدادات hooks.output_spill المشتركة (10,000 حرف افتراضيًا)؛ راجع الإضافات — فيضان السياق الزائد الحجم.

نقاط تفتيش ما قبل الضغط (فشل بأمان)

on_pre_compress() بأفضل جهد افتراضيًا: إذا أطلق مزوّدك استثناءً، يسجّل المضيف الإخفاق ويستمر الضغط. هذا هو الافتراضي الصحيح لاستخلاص الرؤى — والافتراضي الخاطئ لمزوّد مهمته أرشفة أدلة النص الكامل إلى مخزن دائم قبل إعادة الكتابة المُفقِدة (lossy). لهذه الحالة يقدّم المضيف عقد نقطة تفتيش اختياري (إصدار API v2):

يفعّل المشغّلون هذا الفرض لكل نشر:

مع تفعيل هذا التقييد، يفشل الضغط بأمان قبل أي إعادة كتابة مُفقِدة ما لم يكمل مزوّد نشط يعلن عن الـ API نقطة تفتيشه: يُحفَظ النص الكامل غير المضغوط، وتخفق محاولة الضغط برمز BLOCKED_MISSING_PREREQUISITE، ويمكن إعادة المحاولة بمجرد أن يتعافى مخزنك. مع تعطيل هذا التقييد (الافتراضي)، لا يتغير شيء بالنسبة للمزوّدين الحاليين.

يرتبط هذا التقييد بكل سلطة ضغط، لا بمُلخِّص Hermes فقط: يُوقَف الضغط الأصلي من جهة الخادم (compression.codex_responses_native) بينما التقييد مسلَّح، ويُجبَر الضغط الدقيق بعد الدور (post-turn micro-compaction) (compression.micro_compact) على الإيقاف عند تهيئة الوكيل (فهو يمتصّ التبادلات القديمة في ملخّص متجدد بلا نقطة ربط لنقطة تفتيش في مساره)، ويُرفَض وضع API الخاص بـ codex_app_server عند تهيئة الوكيل — إذ يضغط وكيل codex سلسلته الخاصة بلا حد صادق لما قبل الضغط، لذا لا يمكن ضمان نقطة تفتيش مطلوبة هناك. يبقى ضاغط Hermes الواعي بنقاط التفتيش السلطة المُفقِدة الوحيدة.

ما يستقبله مزوّدك يعتمد على إصدار API المُعلَن. مزوّدو الإصدار 1 (الافتراضي الضمني — كل مزوّد موجود مسبقًا) يحتفظون بالعقد التاريخي: قائمة الرسائل الخام، تمامًا كما كانت. مزوّدو نقاط تفتيش الإصدار 2 يستقبلون أدلة مباشرة مُطبَّعة بدلًا من ذلك: صفوف نصوص المستخدم/المساعد فقط — نتائج الأدوات، والرسائل النظامية، وحمولة tool_calls الخاصة برسائل المساعد (يُحتفَظ بنثرها)، وملخصات الضغط السابقة تُصفَّى من جهة المضيف. تُعرَف الملخصات السابقة عبر علامة رسالة دائمة _compressed_summary تنجو من إعادات تشغيل العملية، بحيث لا تُغذّي جلسة مستأنَفة أرشيفك بملخصات مشتقة أبدًا.

يجب أن تكون نقاط التفتيش متماثلة القوة (idempotent). بعد حظر بسبب الفشل الآمن، تستدعي محاولة الضغط التالية on_pre_compress() مرة أخرى بنفس النص — والنص الذي نما قليلًا فقط ينتج أدلة متداخلة إلى حد كبير. رتّب كتابات أرشيفك حسب المحتوى (مثلًا بصمة رقمية للنص) واستخدم upsert، بحيث تتماثل إعادات المحاولة والتداخلات بدلًا من تراكم أرشيفات مكررة.

اختبارات العقد: tests/agent/test_pre_compress_checkpoint_contract.py.

مخطط مبسّط مقابل مخطط كامل

يُطرَح كل حقل في get_config_schema() أثناء hermes memory setup. المزوّدون ذوو الخيارات الكثيرة ينبغي أن يبقوا المخطط مبسّطًا — لا تُدرِج سوى الحقول التي يجب على المستخدم ضبطها (مفتاح API، بيانات الاعتماد المطلوبة). وثّق الإعدادات الاختيارية في مرجع ملف إعدادات (مثل $HERMES_HOME/myprovider.json) بدلًا من الطلب عن كل واحدة أثناء الإعداد. هذا يبقي معالج الإعداد سريعًا مع الاستمرار في دعم الإعدادات المتقدمة. راجع مزوّد Supermemory كمثال — فهو لا يطلب سوى مفتاح API؛ وكل الخيارات الأخرى تعيش في supermemory.json.

messages هو سياق محادثة اختياري بأسلوب OpenAI كما كان عند اكتمال الدور. عند وجوده، يتضمن رسائل المستخدم/المساعد، واستدعاءات أدوات المساعد، ورسائل نتائج الأدوات. المزوّدون الذين لا يحتاجون سياق الدور الخام يمكنهم حذف معامل messages؛ وسيستمر Hermes باستدعائهم بالتوقيع القديم.

على مزوّدي السحابة توثيق أي أجزاء من messages تُرسَل خارج الجهاز. قد تحتوي استدعاءات الأدوات ونتائجها على مسارات ملفات، أو مخرجات أوامر، أو بيانات مساحة عمل أخرى.

إضافة أوامر CLI

يمكن لإضافات مزوّد الذاكرة تسجيل شجرة أوامر CLI فرعية خاصة بها (مثل hermes my-provider status، وhermes my-provider config). يستخدم هذا نظام اكتشاف قائمًا على الاصطلاح (convention-based) — بلا تغييرات على الملفات الأساسية.

كيف يعمل

  1. أضف ملف cli.py إلى دليل إضافتك
  2. عرّف دالة register_cli(subparser) تبني شجرة argparse
  3. يكتشفها نظام إضافة الذاكرة عند بدء التشغيل عبر discover_plugin_cli_commands()
  4. تظهر أوامرك تحت hermes <provider-name> <subcommand>

التقييد حسب المزوّد النشط: تظهر أوامر CLI الخاصة بك فقط عندما يكون مزوّدك هو memory.provider النشط في الإعدادات. إذا لم يُعِد المستخدم ضبط مزوّدك، لن تظهر أوامرك في hermes --help.

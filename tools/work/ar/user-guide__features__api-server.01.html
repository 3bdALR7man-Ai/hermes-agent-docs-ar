Runs API (بديل ملائم للبث)

إلى جانب /v1/chat/completions و /v1/responses، يوفّر الخادم واجهة عمليات التشغيل API للجلسات الطويلة التي يريد فيها العميل الاشتراك في أحداث التقدّم بدلًا من إدارة البث بنفسه.

POST /v1/runs

ينشئ تشغيلًا (run) جديدًا للوكيل. ويُرجع run_id يمكن استخدامه للاشتراك في أحداث التقدّم.

تقبل عمليات التشغيل سلسلة input بسيطة، ويمكن اختياريًا إرسال session_id, instructions, conversation_history أو previous_response_id. وعند تقديم session_id، يُظهره Hermes في حالة التشغيل لتتمكن الواجهات الخارجية من ربط عمليات التشغيل بمعرّفات المحادثات الخاصة بها.

لجعل عملية الإنشاء آمنة لإعادة المحاولة، أرسل الترويسة Idempotency-Key (من 1 إلى 255 حرف ASCII مرئي). يحجز Hermes المفتاح بشكل دائم قبل بدء العمل. وتُرجع إعادة المحاولة المطابقة run_id الأصلي مع HTTP 202 و Idempotency-Replayed: true، حتى بعد إعادة تشغيل gateway وبعد اكتمال التشغيل أو فشله أو إلغائه. وإعادة استخدام المفتاح نفسه مع حمولة JSON مختلفة تُرجع HTTP 409 مع الرمز idempotency_key_conflict. تُعزل المفاتيح حسب profile/بيانات اعتماد API المصادَق عليها، وتُحفظ لمدة 24 ساعة بعد آخر تحديث لحالتها؛ لذا ينبغي للعملاء استخدام مفاتيح فريدة يصعب تخمينها، ويجب ألا يعيدوا استخدامها في عمليات غير ذات صلة. أما الطلبات التي لا تتضمن الترويسة فتحتفظ بالسلوك القديم وتنشئ دائمًا تشغيلًا جديدًا.

التشغيل الذي لم يستطع الـ gateway قبوله لا يحتفظ بأي حجز، لذا فإعادة المحاولة المطابقة آمنة. وعندما يكون الـ profile في حالة تصريف (draining) أو تقاعد، أو عندما تبقى قاعدة بيانات الحالة مقفلة بعد مهلة الكتابة، يُجيب POST /v1/runs وعناصر التحكم في التشغيل بـ HTTP 503 (runtime_draining أو storage_unavailable) مع Retry-After؛ ويُجيب جسم تحكم مشوَّه بـ 400 invalid_params؛ وتبقى حالات رفض الملكية والجيل (generation) والهوية برمز 409.

عندما يحدد session_id جلسة Hermes موجودة، ولا يُقدَّم conversation_history أو previous_response_id صريح، يحمّل التشغيل النص الكامل النشط لتلك الجلسة (transcript). وتعمل عقود إيجار أدوار الجلسة (session turn leases) على ترتيب الكتّاب المتزامنين تسلسليًا، وتحديث النص الكامل بعد انتظار ناتج عن التنافس.

جلسات API هي جلسات خاصة بها. يجوز لـ session_id (هنا) وللترويسة X-Hermes-Session-Id (في /v1/chat/completions و /v1/responses) أن تسمّي جلسة أنشأها خادم API أو جلسة يجوز له إنشاؤها؛ ولا يمكنها ربط جلسة تملكها واجهة أخرى — محادثة CLI أو TUI أو Desktop أو ACP أو المراسلة. يُرفض مثل هذا الطلب بـ HTTP 409 ورمز الخطأ permission_denied قبل أي قبول: فلا يُنشأ تشغيل، ولا يُحتفظ بحجز Idempotency-Key، وتُجاب إعادة المحاولة المطابقة بـ 409 مرة أخرى. وهذا يحل محل السلوك السابق الذي كان خادم API يشغّل فيه وكيله الخاص على سجل جلسة غريبة بالتوازي مع مالكها الحي. وللعمل على محادثة من واجهة أخرى، اتصل عبر WebSocket الخاص بالـ gateway (prompt.submit على الجلسة المشتركة) بدلًا من المسارات المتوافقة مع OpenAI.

GET /v1/runs/{run_id}

استطلع حالة التشغيل الحالية. وهذا مفيد للوحات التحكم التي تحتاج إلى الحالة دون إبقاء اتصال SSE مفتوحًا، أو للواجهات التي تعيد الاتصال بعد التنقل.

model يعكس ما طلبه الطلب. وفي تشغيل مكتمل، يكون runtime زوج المزوّد/النموذج الذي خدم الدور فعليًا — وبعد الانتقال إلى مزوّد احتياطي يذكر الزوج الاحتياطي، كي ينسب نظام استقصاء التكلفة التشغيل إلى المزوّد الصحيح. و usage.cache_read_tokens / usage.cache_write_tokens هي قراءات التخزين المؤقت للـ prompt وكتاباته في الجلسة، فلا يُسعّر الإدخال المخزّن مؤقتًا بالسعر الكامل. ولـ runtime البنية نفسها الموجودة في /v1/chat/completions و /v1/responses: route_source يوضح كيفية اختيار بيئة التشغيل (global, raw_request, model_routes)، ويحصل الطلب الذي حدد model/provider أيضًا على requested: {provider, model} كي يمكن مقارنة الزوج المطلوب بالزوج المستخدم. ويحمل حدث run.completed في stream الأحداث الحقلين usage و runtime نفسيهما.

تُحفظ الحالات لفترة وجيزة بعد بلوغ الحالات النهائية (completed أو failed أو cancelled أو interrupted) للاستطلاع والتوفيق مع UI. وعندما يتوقف الـ gateway بينما التشغيل نشط، يُحفظ التشغيل بوصفه interrupted (الخطأ Gateway shutdown interrupted the run.، والحدث النهائي run.interrupted) قبل طلب توقف الوكيل، فلا يبقى أي تشغيل دائم بعد إعادة التشغيل بوصفه running؛ ولا تستطيع نتيجة متأخرة من الدور الذي قوطع الكتابة فوقه. أما التشغيل المرجعي الذي أُعيد تشغيل مالكه في منتصف الدور فيُبلغ عن unknown بدلًا من ذلك، وهي حالة غير نهائية: تنتظر الأدوار اللاحقة في تلك الجلسة إلى أن يُقَرّ بها عبر POST /v1/runs/{run_id}/resolve-unknown (أدناه).

بينما ما زال الـ gateway يصرف الأعمال الجارية (hermes gateway stop/restart أو SIGTERM أثناء تنفيذ دور)، يحمل كل تشغيل غير نهائي أيضًا shutdown_requested_at (ثواني Unix) منذ لحظة رفض الأدوار الجديدة. ويبقى status بالقيمة running لأن الدور ما زال يُخدم؛ ويعرف نظام الاستقصاء الذي يرى الحقل أن العملية في طريقها إلى التوقف وأن التشغيل سينتهي interrupted على أبعد تقدير عند انتهاء ميزانية تصريف العمل. ولا تحصل عمليات التشغيل النهائية على هذا الحقل مطلقًا.

GET /v1/runs/{run_id}/events

stream عبر Server-Sent Events يعرض تقدم استدعاءات الأدوات، وفروق tokens ، وأحداث دورة حياة التشغيل. صُمم للوحات التحكم والعملاء متكاملين الوظائف الذين يريدون الاتصال/الانفصال دون فقدان الحالة.

يصل تعليق المساعد في منتصف الدور — مقدمات التقدم openai-codex الخاصة بـ backend phase="commentary"، أو النص الذي يكتبه نموذج إلى جانب استدعاءات أدواته — بصيغة message.interim (text, already_streamed)، وهو العقد نفسه الذي يستخدمه TUI gateway. ويعني already_streamed: true أن النص خرج أيضًا بصيغة message.delta، فيمكن للعملاء الذين يعرضون الفروق تجاوزه. وما زالت الإجابة النهائية لا تصل إلا في run.completed؛ ولا يصبح الاستدلال الخاص message.interim مطلقًا. شرط التمكين: display.interim_assistant_messages (الافتراضي true).

تحمل أحداث دورة حياة الأداة tool.started (tool, preview للوسائط) و tool.completed (tool, duration بالثواني، و error، و preview للنتيجة). ويعكس الخيار error نتيجة الأداة نفسها — قيمة exit_code غير صفرية للطرفية، أو نتيجة {"error": ...} منظّمة، أو موافقة مرفوضة — سواء وصلت النتيجة كسلسلة JSON أو ككائن محلّل مسبقًا. ويكون preview الخاص بالإكمال نص النتيجة (تُرمّز النتائج المنظّمة بصيغة JSON)، ويمر عبر تنقيح إلزامي للأسرار ثم يُقتطع إلى 500 محرف، كي يستطيع العميل تمييز رفض الموافقة (BLOCKED: ...) عن الفشل العادي دون تلقي حمولة الأداة غير المحدودة.

عندما يفوّض الوكيل العمل إلى subagents في الخلفية، يحمل البث أيضًا أحداث دورة الحياة subagent.start و subagent.complete، لكي يتمكن العملاء من مراقبة نتائج التفويض — بما في ذلك انتهاء المهلة والإخفاقات — بدلًا من صمت التشغيل بينما يعمل الوكيل الفرعي. وتحمل حمولة subagent.complete حالة الوكيل الفرعي، وملخّصه، ومدته، وأرقام الـ tokens/التكلفة، و child_session_id لأغراض الربط، و delegation_id الخاص بالدفعة التي ينتمي إليها (لتبقى عمليات التوزيع المتزامنة أو المتداخلة قابلة للتمييز)؛ وتخضع الحقول النصية الحرة لإخفاء إلزامي للأسرار قبل مغادرة العملية. أما أحداث الوكيل الفرعي الخاصة بكل أداة (subagent.tool، ونبضات التقدّم) فهي عمدًا لا تُمرَّر — لأنها ضجيج كثيف في الواجهة؛ استخدم ملفات النص الحي لكل وكيل فرعي لمتابعة التفاصيل خطوة بخطوة. هذه الأحداث متاحة ما دام بث الأصل مفتوحًا؛ وأي إكمال منفصل متأخر لا يعيد فتح بث SSE لتشغيل منتهٍ ولا يغيّر حالته النهائية.

النتائج المنفصلة وسجل الجلسة

يتطلب التفويض في الخلفية استئنافًا يقرأ سجل الجلسة على جانب الخادم: أي ترويسة X-Hermes-Session-Id صريحة في Chat Completions ، أو طلب /api/sessions/{id}/chat أصلي، أو طلب Runs يستخدم سجل الجلسة. أما طلبات Chat Completions بلا ترويسة، وسلاسل Responses ، وطلبات Runs التي تتضمن previous_response_id أو سجلًا يقدّمه المستدعي، فتنفّذ التفويض بشكل متزامن بدلًا من ذلك، وتُرجع النتيجة في الدور الأصلي. ومجرد اشتقاق معرّف جلسة من محتوى الطلب لا يُفعّل التسليم المنفصل.

في الطلبات القابلة للاستئناف، تُحفظ نتيجة الإكمال مرة واحدة لكل وحدة تفويض. وهي متاحة عبر GET /api/sessions/{id}/messages وفي سجل الجلسة للدور الفعلي التالي من العميل. ولا تُدرج إعادة المحاولة النتيجة نفسها مجددًا؛ أما إشعارات فشل المهام المؤقتة فلها هويات منفصلة. وينتظر التسليم ما دام دور العميل يملك عقد إيجار الجلسة، ويتبع عمليات الاستئناف الناتجة عن الضغط (compression). ويعيد Chat Completions معرّف الجلسة الصريح الذي قدّمته في كلٍّ من استجابات JSON واستجابات البث؛ لذا استمر في إرسال ذلك المعرّف حتى بعد الضغط.

لا تبدأ نتيجة الإكمال أبدًا دورًا للنموذج دون طلب، ولا تتجاوز تأكيدًا بشريًا معلّقًا. فالعميل هو من يملك الدور التالي. أما العملاء الذين يواصلون استخدام لقطات (snapshots) السجل الخاصة بهم فينبغي أن يستخدموا التفويض المتزامن بدلًا من توقّع دمج صف تسليم من جانب الخادم في تلك اللقطات.

تنتهي صلاحية مخازن الأحداث غير المستهلكة بعد خمس دقائق، حتى لا يتسبب عميل منفصل في تضخّم الذاكرة إلى ما لا نهاية. ولا ينتهي بذلك إلا حالة وسيلة النقل: فالتشغيل الذي لا يزال قيد التنفيذ يبقى مرئيًا لاستطلاع الحالة، والموافقة، والتحكم في الإيقاف، و احتساب التزامن إلى أن ينتهي عمل المنفّذ الخاص به فعليًا. ويواصل مشترك SSE المتصل استهلاك الأحداث بشكل طبيعي.

POST /v1/runs/{run_id}/resolve-unknown

بعد إعادة تشغيل مالك الجهة (authority-owner)، يكون لدور سبقت المطالبة به نتيجة تنفيذ مجهولة، ويُبلغ عنها GET /v1/runs/{run_id} بالقيمة "status": "unknown" (غير نهائية). يوقف Hermes الأعمال اللاحقة في تلك الجلسة بدلًا من المخاطرة بإعادة تشغيل الرأس المفقود. اقرأ admission_id و execution_generation بدقة من ذلك الجسم، ثم أقِرّ بأن التنفيذ المفقود لن يكتمل:

الطلب مصادَق عليه ومحصور بمالك التشغيل مثل عناصر التحكم الأخرى في التشغيل؛ ويحتاج المستدعون من الغرف المستضافة (hosted-room) إلى منحة stop الموجودة. والاستجابة الناجحة هي إيصال النهاية المرجعي (outcome: "interrupted") مع run_id. وهي تحرر طابور FIFO مرة واحدة وتجدول التابع المصطف دون إعادة تشغيل الرأس المجهول. وتعيد الإعادة المطابقة لحسم سبق تثبيته الإيصال نفسه (200)، فإعادة المحاولة بعد ضياع الاستجابة آمنة. ويعيد الجيل (generation) القديم أو غير الصحيح، أو التشغيل غير المجهول حاليًا، الرمز 409 stale_generation؛ ويعيد معرّف قبول لا ينتمي إلى تشغيل المسار 409 not_found. ويجب أن يحتوي الجسم على هذين الحقلين بالضبط، وإلا يُرجع الخادم 400 invalid_params.

تحسم homes الغرف المستضافة تشغيلَ عضو بحالة unknown بهذه الطريقة عند استطلاعها التالي وتُنهي مهمة الغرفة بوصفها مقاطَعة ("member gateway restarted"). أما room home على إصدار أقدم فلا يعرف الحالة unknown ويُبلغ عن حالة تشغيل غير مطابقة إلى أن تتم ترقيته.

يُعلَن عن عنصر التحكم في الاسترداد هذا بوصفه features.run_unknown_resolution وبوصفه endpoint باسم run_unknown_resolution فقط عندما تكون جهة صلاحية الجلسات المرجعية (canonical session authority) نشطة. ولا يعلن عنه وضع تنفيذ API القديم. أما POST /v1/runs/{run_id}/stop العادي فيبقى عمدًا منفصلًا ويُرجع 409 unknown_execution لقبول مجهول.

بالنسبة إلى عمليات القبول التي أنشأها هذا الإصدار، يُخزَّن نطاق مالك التشغيل المعتم (opaque run-owner scope) ذريًّا مع القبول المرجعي ويُحتفظ به طوال عمر التحكم/الحالة لذلك القبول، بما في ذلك الحالة النهائية. وهو حالة خاصة بالخادم، وليس بيانات اعتماد حامل (bearer) ولا مدخلًا للنموذج ولا حقلًا في استجابة API. تبقى الطلبات غير ذات المفتاح غير متكافئة القوة (non-idempotent)، فتظل أجسام الطلبات المتطابقة تُنشئ تشغيلات منفصلة. أما عمليات القبول القديمة غير ذات المفتاح فلا نطاق مالك محفوظًا لها وتستمر في الفشل بإغلاق آمن (fail closed) بعد إعادة تشغيل المحوّل (adapter)؛ ولا يمكن ملؤها راجعًا بأمان. وتواصل التشغيلات القديمة ذات المفتاح استخدام سجل idempotency القائم. ويزيل إنهاء الجلسة الصريح حمولة القبول المرجعي ومالكها القابل للاسترداد. سجل الإعادة والقبول المرجعي معاملتان منفصلتان في قاعدة البيانات؛ ولا يعد عنصر التحكم في الاسترداد هذا بتنفيذ مرة واحدة بالضبط (exactly-once) على المستوى العام.

POST /v1/runs/{run_id}/stop

يقاطع دور وكيل قيد التشغيل. يُرجع الـ endpoint فورًا {"status": "stopping"} بينما يطلب Hermes من الوكيل النشط التوقف عند نقطة المقاطعة الآمنة التالية. ويبقى التشغيل مُتتبَّعًا بالحالة stopping إلى أن ينتهي العمل المدعوم بالمنفّذ، ثم يستقر على الحالة cancelled؛ فطلب الإيقاف لا يُخفي أبدًا عاملًا (worker) لا يزال قيد التشغيل.

POST /v1/runs/{run_id}/approval

يحسم موافقة معلّقة لتشغيل ينتظر قرارًا بشريًا (مثل استدعاء أداة يخضع لسياسة موافقة). يحمل جسم الطلب قرار الموافقة، ويُستأنف التشغيل بمجرد تسجيل القرار. ويُعلَن عن هذا الـ endpoint في /v1/capabilities على أنه الميزة run_approval، لكي تتمكن الواجهات الخارجية من اكتشاف الدعم قبل عرض طلب موافقة.

مع مالك gateway المرجعي، يعرض GET /v1/runs/{run_id} الحقل pending_controls، مستخدمًا prompt_id و execution_generation نفسيهما اللذين يراهما مشاهدو WebSocket المرتبطون. أجِب بالهوية الحالية الدقيقة:

لا تقبل عناصر التحكم المرجعية ردودًا بلا هوية أو جماعية. وتعيد الأجيال القديمة، ومعرّفات prompt الغريبة، والتشغيلات المستقرة HTTP 409. وتظل قيود مصادقة التشغيل القائمة وموافقة الغرف المستضافة سارية.

POST /v1/runs/{run_id}/clarify

أجِب عن توضيح مرجعي بالحقول request_id و execution_generation و answer (سلسلة نصية). يحسم هذا الـ endpoint المصادَق عليه و clarify.respond في WebSocket الأداة المنتظرة نفسها؛ والإجابة لا تُرسل دور inference آخر. وتظهر موافقة بوابة الثقة في MCP — لأداة قادرة على الكتابة في خادم مُعدّ بالقيمة trust: untrusted — بالطريقة نفسها: يُصدر التشغيل حدث approval.request ويتوقف في waiting_for_approval إلى أن يحسمه هذا الـ endpoint (once يشغّل الأداة، و deny يمنعها).

يجلب تعريف مهمة واحدة وحالة آخر تشغيل لها.

يحدّث حقول مهمة موجودة (الـ prompt ، والجدول الزمني، وغيرها). وتُدمج التحديثات الجزئية.

DELETE /api/jobs/{job_id}

يزيل مهمة. ويلغي أيضًا أي تشغيل جارٍ لها.

POST /api/jobs/{job_id}/pause

يوقف مهمة مؤقتًا دون حذفها. وتُعلَّق الطوابع الزمنية للتشغيل المجدول التالي حتى الاستئناف.

POST /api/jobs/{job_id}/resume

يستأنف مهمة أُوقفت مؤقتًا في السابق.

POST /api/jobs/{job_id}/run

يُطلق تشغيل المهمة فورًا، خارج جدولها الزمني.

Sessions API (التحكم في الجلسات عبر REST)

يمكن للواجهات الخارجية إدارة جلسات Hermes عبر REST دون الحاجة إلى تشغيل لوحة التحكم. جميع الـ endpoints محمية بـ API_SERVER_KEY وتقع تحت /api/sessions/*.

اكتشاف المهارات و toolsets

GET /v1/skills و GET /v1/toolsets للعملاء الخارجيين سرد قدرات الوكيل بشكل حتمي عبر REST بدلًا من سؤال النموذج. كلاهما للقراءة فقط ومحميّ بـ API_SERVER_KEY.

/v1/skills البيانات الوصفية نفسها التي يستخدمها Skills Hub داخليًا. ويُرجع /v1/toolsets مجموعات toolsets كما تُحلّ لمنصة api_server، مع قائمة tools الفعلية التي تتوسع إليها كل منها. ويُعلَن عن كليهما تحت endpoints.* في /v1/capabilities.

تحديد نطاق الذاكرة طويلة المدى (X-Hermes-Session-Key)

تحتاج الواجهات الأمامية متعددة المستخدمين مثل Open WebUI إلى معرّف ثابت لكل قناة من أجل الذاكرة طويلة المدى (Honcho وغيرها)، يكون مستقلًا عن X-Hermes-Session-Id المرتبط بنطاق النص الكامل للمحادثة (والذي يتغيّر عند /new). مرّر X-Hermes-Session-Key على /v1/chat/completions, /v1/responses أو /v1/runs، وسيمرّره Hermes حتى AIAgent(gateway_session_key=...)، حيث يستخدمه مزوّد ذاكرة Honcho لاشتقاق نطاق ثابت.

القواعد: الحد الأقصى 256 حرفًا، وتُرفض محارف التحكم (\r, \n, \x00) تُرفض، وتُعاد القيمة في الاستجابات (JSON + SSE). /v1/capabilities عن الدعم عبر "session_key_header": "X-Hermes-Session-Key". دون المفتاح، فإن استراتيجية Honcho per-session في Honcho نطاقًا مختلفًا لكل session_id — وهو سلوك Hermes السابق بالضبط.

يتبع الاسترجاع التلقائي نص المحادثة: يُهيّأ مزوّد الذاكرة مرة واحدة لكل جلسة ويُحتفظ به عبر الطلبات، لذا تتلقى الجلسة المستمرة (X-Hermes-Session-Id, previous_response_id، أو محادثة X-Hermes-Session-Key مُعلنة) الاسترجاع الذي أعده المزوّد بعد الدور السابق، تمامًا مثل محادثة Telegram أو Discord. أما الطلب دون أي استمرارية فيبدأ جلسة جديدة، ومثل الدور الأول في أي جلسة CLI جديدة لا تكون هناك عناصر مُدرجة بعد. وتحرر الجلسات الخاملة مزوّدها بعد TTL الخمول نفسه الخاص بالتخزين المؤقت لوكلاء الـ gateway (agent.agent_cache.idle_ttl_secs — وهو تمامًا السلوك الذي كان عليه Hermes سابقًا.

التعامل مع System Prompt

عندما ترسل واجهة أمامية رسالة system (في Chat Completions) أو حقل instructions (في Responses API)، فإن hermes-agent يضيفها كطبقة فوق الـ system prompt الأساسي الخاص به. يحتفظ وكيلك بجميع أدواته وذاكرته ومهاراته — ويضيف الـ system prompt الخاص بالواجهة الأمامية تعليمات إضافية فقط.

هذا يعني أنه يمكنك تخصيص السلوك لكل واجهة أمامية دون فقدان أي قدرات:

  • الـ system prompt في Open WebUI: "أنت خبير في Python. أضف دائمًا تلميحات الأنواع (type hints)."
  • يظل لدى الوكيل الطرفية، وأدوات الملفات، والبحث في الويب، والذاكرة، وغيرها.

المصادقة

مصادقة Bearer token عبر الترويسة Authorization في الترويسة:

اضبط المفتاح عبر متغير البيئة API_SERVER_KEY. وإذا كنت تحتاج إلى أن يستدعي متصفحٌ Hermes مباشرةً، فاضبط أيضًا API_SERVER_CORS_ORIGINS على قائمة سماح صريحة.

التوجيه متعدد الـ profiles (/p/<profile>/…)

عند تفعيل توجيه gateway متعدد الـ profiles مفعّل (gateway.multiplex_profiles)، يخدم المستمع المشترك كل profile عبر بادئة URL بالشكل /p/<profile>/ — وترتبط المصادقة بالـ profile الموجَّه إليه:

  • يجب أن تقدّم الطلبات الموجّهة إلى /p/<profile>/v1/... المفتاح الخاص بذلك الـ profile نفسه API_SERVER_KEY (من ~/.hermes/profiles/<profile>/.env). ويُرفض مفتاح المستمع الافتراضي على بادئات الـ profiles المسمّاة.
  • تواصل المسارات بلا بادئة و /p/default/... استخدام مفتاح الـ profile الافتراضي.
  • الـ profile المسمّى الذي ليس له API_SERVER_KEY خاص به يفشل بشكل مغلق — إذ تبقى بادئته غير قابلة للوصول حتى تضبط مفتاحًا له.
  • نطاق عمليات التشغيل خاص بكل profile: فالمسار /v1/runs/{run_id} ومساراته events, stop, steer و approval لا تستجيب إلا للـ profile الذي أنشأ التشغيل (بما في ذلك عمليات التشغيل التي بدأت عبر /api/sessions/{id}/chat/stream)؛ أما معرّف تشغيل يخص profile آخر فيُرجع 404، وليس 403.
تغيير كاسر للتوافق (يوليو 2026)

قبل هذا الإصلاح، كان مفتاح الـ profile الافتراضي الصالح مقبولًا على أي بادئة /p/<profile>/. إذا كنت تعتمد على مفتاح واحد مشترك عبر بادئات الـ profiles ، فاضبط API_SERVER_KEY مختلفًا في ملف .env لكل profile — إذ أصبحت المفاتيح الافتراضية المُعاد استخدامها على البادئات المسمّاة تُرجع الآن 401.

الأمان

يمنح خادم API وصولًا كاملًا إلى مجموعة أدوات hermes-agent ، بما في ذلك أوامر الطرفية. API_SERVER_KEY هو مطلوب في كل عملية نشر، بما في ذلك الربط الافتراضي بعنوان loopback على 127.0.0.1. أبقِ API_SERVER_CORS_ORIGINS ضيق النطاق للتحكم في وصول المتصفحات عندما تسمح صراحةً بالاستدعاء من المتصفح.

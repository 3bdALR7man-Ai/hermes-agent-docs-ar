Sessions API (التحكم في الجلسات عبر REST)

يمكن للواجهات الخارجية إدارة جلسات Hermes عبر REST دون الحاجة إلى تشغيل لوحة التحكم. جميع الـ endpoints محمية بـ API_SERVER_KEY وتقع تحت /api/sessions/*.

الطريقةالمسارالوصف
GET/api/sessionsيسرد الجلسات (مع ترقيم الصفحات — limit، offset، source، include_children)
POST/api/sessionsينشئ جلسة فارغة
GET/api/sessions/{id}يقرأ البيانات الوصفية للجلسة
PATCH/api/sessions/{id}يحدّث العنوان أو end_reason
DELETE/api/sessions/{id}يحذف جلسة
GET/api/sessions/{id}/messagesسجل رسائل الجلسة
POST/api/sessions/{id}/forkيتفرّع من الجلسة عبر سلسلة النَّسب في SessionDB (بنفس دلالات الأمر /branch في CLI)
POST/api/sessions/{id}/chatيشغّل دورًا واحدًا متزامنًا للوكيل
POST/api/sessions/{id}/chat/streamwrapper بتقنية SSE حول دور واحد — يُصدر الأحداث assistant.delta و tool.started و tool.completed و run.completed

يُعلن /v1/capabilities عن الواجهة الكاملة عبر علامات الميزات session_* ومُدخلات endpoints.session_*، لكي تتمكن الواجهات الخارجية من اكتشاف الدعم والرجوع إلى بديل بأمان. وتُدعم الصور المضمّنة في حمولات chat و chat/stream (عبر مسار يدعم الوسائط المتعددة).

اكتشاف المهارات و toolsets

يتيح GET /v1/skills و GET /v1/toolsets للعملاء الخارجيين سرد قدرات الوكيل بشكل حتمي عبر REST بدلًا من سؤال النموذج. كلاهما للقراءة فقط ومحميّ بـ API_SERVER_KEY.

يُرجع /v1/skills البيانات الوصفية نفسها التي يستخدمها Skills Hub داخليًا. ويُرجع /v1/toolsets مجموعات toolsets كما تُحلّ لمنصة api_server، مع قائمة tools الفعلية التي تتوسع إليها كل منها. ويُعلَن عن كليهما تحت endpoints.* في /v1/capabilities.

تحديد نطاق الذاكرة طويلة المدى (X-Hermes-Session-Key)

تحتاج الواجهات الأمامية متعددة المستخدمين مثل Open WebUI إلى معرّف ثابت لكل قناة من أجل الذاكرة طويلة المدى (Honcho وغيرها)، يكون مستقلًا عن X-Hermes-Session-Id المرتبط بنطاق النص الكامل للمحادثة (والذي يتغيّر عند /new). مرّر X-Hermes-Session-Key على /v1/chat/completions أو /v1/responses أو /v1/runs، وسيمرّره Hermes حتى AIAgent(gateway_session_key=...)، حيث يستخدمه مزوّد ذاكرة Honcho لاشتقاق نطاق ثابت.

القواعد: الحد الأقصى 256 حرفًا، وتُرفض محارف التحكم (\r، \n، \x00)، وتُعاد القيمة في الاستجابات (JSON و SSE). ويُعلن /v1/capabilities عن الدعم عبر "session_key_header": "X-Hermes-Session-Key". وبدون المفتاح، تُنتج استراتيجية per-session في Honcho نطاقًا مختلفًا لكل session_id — وهو تمامًا السلوك الذي كان عليه Hermes سابقًا.

التعامل مع System Prompt

عندما ترسل واجهة أمامية رسالة system (في Chat Completions) أو حقل instructions (في Responses API)، فإن hermes-agent يضيفها كطبقة فوق الـ system prompt الأساسي الخاص به. يحتفظ وكيلك بجميع أدواته وذاكرته ومهاراته — ويضيف الـ system prompt الخاص بالواجهة الأمامية تعليمات إضافية فقط.

هذا يعني أنه يمكنك تخصيص السلوك لكل واجهة أمامية دون فقدان أي قدرات:

  • الـ system prompt في Open WebUI: "أنت خبير في Python. أضف دائمًا تلميحات الأنواع (type hints)."
  • يظل لدى الوكيل الطرفية، وأدوات الملفات، والبحث في الويب، والذاكرة، وغيرها.

المصادقة

مصادقة Bearer token عبر الترويسة Authorization:

اضبط المفتاح عبر متغير البيئة API_SERVER_KEY. وإذا كنت تحتاج إلى أن يستدعي متصفحٌ Hermes مباشرةً، فاضبط أيضًا API_SERVER_CORS_ORIGINS على قائمة سماح صريحة.

التوجيه متعدد الـ profiles (/p/<profile>/…)

عند تفعيل توجيه gateway متعدد الـ profiles (gateway.multiplex_profiles)، يخدم المستمع المشترك كل profile عبر بادئة URL بالشكل /p/<profile>/ — وترتبط المصادقة بالـ profile الموجَّه إليه:

  • يجب أن تقدّم الطلبات الموجّهة إلى /p/<profile>/v1/... المفتاح الخاص بذلك الـ profile نفسه API_SERVER_KEY (من ~/.hermes/profiles/<profile>/.env). ويُرفض مفتاح المستمع الافتراضي على بادئات الـ profiles المسمّاة.
  • تواصل المسارات بلا بادئة و /p/default/... استخدام مفتاح الـ profile الافتراضي.
  • الـ profile المسمّى الذي ليس له API_SERVER_KEY خاص به يفشل بشكل مغلق — إذ تبقى بادئته غير قابلة للوصول حتى تضبط مفتاحًا له.
  • نطاق عمليات التشغيل خاص بكل profile: فالمسار /v1/runs/{run_id} ومساراته events و stop و steer و approval لا تستجيب إلا للـ profile الذي أنشأ التشغيل (بما في ذلك عمليات التشغيل التي بدأت عبر /api/sessions/{id}/chat/stream)؛ أما معرّف تشغيل يخص profile آخر فيُرجع 404، وليس 403 أبدًا.
تغيير كاسر للتوافق (يوليو 2026)

قبل هذا الإصلاح، كان مفتاح الـ profile الافتراضي الصالح مقبولًا على أي بادئة /p/<profile>/. إذا كنت تعتمد على مفتاح واحد مشترك عبر بادئات الـ profiles، فاضبط API_SERVER_KEY مختلفًا في ملف .env لكل profile — إذ أصبحت المفاتيح الافتراضية المُعاد استخدامها على البادئات المسمّاة تُرجع الآن 401.

الأمان

يمنح خادم API وصولًا كاملًا إلى مجموعة أدوات hermes-agent، بما في ذلك أوامر الطرفية. والمفتاح API_SERVER_KEY مطلوب في كل عملية نشر، بما في ذلك الربط الافتراضي بعنوان loopback على 127.0.0.1. أبقِ API_SERVER_CORS_ORIGINS ضيق النطاق للتحكم في وصول المتصفحات عندما تسمح صراحةً بالاستدعاء من المتصفح.

config.yaml

يمكن وضع الإعدادات نفسها في ~/.hermes/config.yaml ضمن قسم متداخل gateway.api_server::

تُنقل الخيارات port و key و host و cors_origins و model_name تلقائيًا إلى إعدادات extra الخاصة بالمنصة، لذا تتصرف تمامًا مثل نظيراتها من متغيرات البيئة API_SERVER_*. ولمتغيرات البيئة الأولوية على قيم config.yaml. كما تُقبل هذه الكتلة أيضًا تحت gateway.platforms.api_server: أو ضمن قسم platforms.api_server: في المستوى الأعلى.

حدّ عمليات التشغيل المتزامنة

يحدّ خادم API عدد عمليات تشغيل الوكيل التي يمكن تنفيذها في الوقت نفسه عبر endpoints المتوافقة مع OpenAI و endpoints الخاصة بـ Runs. يُقرأ الحد من gateway.api_server.max_concurrent_runs (القيمة الافتراضية 10؛ والقيمة 0 تعطّل الحد، والقيم السالبة تُقيَّد إلى 0). وعند بلوغ الحد، تُرفض الطلبات الجديدة التي تبدأ عمليات تشغيل مع HTTP 429 Too many concurrent runs (max N) — وينبغي للعملاء التراجع ثم إعادة المحاولة.

ترويسات الأمان

تتضمن جميع الاستجابات ترويسات أمان:

  • X-Content-Type-Options: nosniff — تمنع تخمين نوع MIME (MIME sniffing)
  • Referrer-Policy: no-referrer — تمنع تسريب المُحيل (referrer)

CORS

خادم API لا يفعّل CORS للمتصفحات افتراضيًا.

للوصول المباشر من المتصفح، اضبط قائمة سماح صريحة:

عند تفعيل CORS:

  • استجابات Preflight تتضمن Access-Control-Max-Age: 600 (تخزين مؤقت لمدة 10 دقائق)
  • استجابات البث عبر SSE تتضمن ترويسات CORS لكي تعمل عملاء EventSource في المتصفح بشكل صحيح
  • X-Hermes-Session-Id ترويسة طلب مسموح بها، لذا يمكن للمتصفحات على مصدر مُدرج في قائمة السماح طلب استئناف الجلسة.
  • Idempotency-Key ترويسة طلب مسموح بها — ويمكن للعملاء إرسالها لمنع التكرار (تُخزَّن الاستجابات مؤقتًا حسب المفتاح لمدة 5 دقائق)

معظم الواجهات الأمامية الموثّقة مثل Open WebUI تتصل من خادم إلى خادم ولا تحتاج إلى CORS إطلاقًا.

إعداد متعدد المستخدمين باستخدام Profiles

لمنح عدة مستخدمين نسخة Hermes معزولة خاصة بكل منهم (إعدادات وذاكرة ومهارات منفصلة)، استخدم الـ profiles:

يُعلن خادم API الخاص بكل profile تلقائيًا عن اسم الـ profile بوصفه معرّف النموذج:

  • http://localhost:8643/v1/models → النموذج alice
  • http://localhost:8644/v1/models → النموذج bob

في Open WebUI، أضف كلًّا منها كاتصال منفصل. ستعرض القائمة المنسدلة للنماذج alice و bob كنموذجين مختلفين، يعتمد كلٌّ منهما على نسخة Hermes معزولة تمامًا. راجع دليل Open WebUI لمزيد من التفاصيل.

القيود

  • تخزين الاستجابات — تُحفظ الاستجابات المخزّنة (الخاصة بـ previous_response_id) في SQLite وتبقى بعد إعادة تشغيل gateway. الحد الأقصى 100 استجابة مخزّنة (مع الإزالة وفق LRU).
  • لا يوجد رفع للملفات — الصور المضمّنة مدعومة على كلٍّ من /v1/chat/completions و /v1/responses، لكن الملفات المرفوعة (file، input_file، file_id) ومدخلات المستندات غير المصوّرة غير مدعومة عبر API.
  • عملاء OpenAI البسيطة ما زالت ترى اسمًا مستعارًا — يُعلن /v1/models عن الاسم المستعار الثابت لـ Hermes (hermes-agent أو اسم الـ profile النشط). أما العملاء الأغنى بالميزات فيمكنها إرسال تجاوزات صريحة لـ provider / model_options في الطلبات.

Proxy Mode

يعمل خادم API أيضًا كـ backend لوضع gateway proxy mode. فعندما تُضبط نسخة Hermes gateway أخرى بـ GATEWAY_PROXY_URL يشير إلى خادم API هذا، فإنها تُعيد توجيه جميع الرسائل إليه بدلًا من تشغيل وكيلها الخاص. وهذا يتيح عمليات نشر مقسّمة — مثل حاوية Docker تتولى Matrix E2EE وتمرّر الرسائل إلى وكيل يعمل على الجهاز المضيف.

راجع Proxy Mode في Matrix للاطلاع على دليل الإعداد الكامل.

استخدام MCP مع Hermes

يوضّح هذا الدليل كيفية استخدام MCP فعليًا مع Hermes Agent في سير العمل اليومي.

إذا كانت صفحة الميزة تشرح ماهية MCP، فإن هذا الدليل يركّز على كيفية الاستفادة منه بسرعة وأمان.

متى ينبغي أن تستخدم MCP؟

استخدم MCP عندما:

  • تكون الأداة متوفرة بالفعل بصيغة MCP ولا تريد بناء أداة أصلية في Hermes
  • تريد أن يعمل Hermes على نظام محلي أو بعيد عبر طبقة RPC نظيفة
  • تريد تحكمًا دقيقًا في ما يُتاح من كل خادم على حدة
  • تريد ربط Hermes بواجهات API داخلية، أو قواعد بيانات، أو أنظمة الشركة دون تعديل نواة Hermes

لا تستخدم MCP عندما:

  • تكون هناك أداة مدمجة في Hermes تؤدي المهمة جيدًا بالفعل
  • يُتيح الخادم مجموعة ضخمة وخطيرة من الأدوات ولست مستعدًا لتصفيتها
  • لا تحتاج إلا إلى تكامل واحد محدود جدًا، وتكون الأداة الأصلية أبسط وأكثر أمانًا

النموذج الذهني

فكّر في MCP على أنه طبقة مُحوِّل (adapter):

  • يبقى Hermes هو الوكيل
  • تساهم خوادم MCP بالأدوات
  • يكتشف Hermes هذه الأدوات عند بدء التشغيل أو عند إعادة التحميل
  • يستطيع النموذج استخدامها كأي أدوات عادية
  • تتحكم أنت في مقدار ما يظهر من كل خادم

هذه النقطة الأخيرة مهمة. فالاستخدام الجيد لـ MCP ليس مجرد “اربط كل شيء”، بل هو “اربط الشيء المناسب، بأصغر نطاق مفيد ممكن.”

WSL2: ربط Hermes داخل WSL بمتصفح Chrome على Windows

هذا هو الإعداد العملي عندما:

  • يعمل Hermes داخل WSL2
  • يكون المتصفح الذي تريد التحكم فيه هو متصفح Chrome المعتاد الذي سجّلت الدخول إليه على Windows
  • يكون /browser connect غير مريح أو غير موثوق من داخل WSL

في هذا الإعداد، لا يتصل Hermes بـ Chrome مباشرةً. بل:

  • يعمل Hermes داخل WSL
  • يُشغّل Hermes خادم MCP محليًا من نوع stdio
  • يُطلَق خادم MCP هذا عبر آلية التشغيل البيني في Windows (interop) باستخدام (cmd.exe أو powershell.exe)
  • يرتبط خادم MCP بجلسة Chrome الحية لديك على Windows

متى يكون /browser connect الأداة الخاطئة

الأسباب الشائعة:

  • لا يستطيع WSL الوصول إلى الـ endpoint المحلي نفسه الذي يُتيحه Chrome لأدوات Windows
  • مسارات التصحيح المباشر في إصدارات Chrome الأحدث ليست مماثلة للاتصال الكلاسيكي عبر ws://localhost:9222
  • يكون الارتباط بالمتصفح أسهل عبر أداة مساعدة تعمل على جانب Windows مثل chrome-devtools-mcp

في هذه الحالات، احتفظ بـ /browser connect للإعدادات التي تعمل في البيئة نفسها، واستخدم MCP لربط المتصفح من WSL إلى Windows.

مشكلات معروفة

  • شغّل Hermes من مسار مُركَّب من Windows مثل /mnt/c/Users/<you> أو /mnt/c/workspace/... عند استخدام ملفات Windows التنفيذية من نوع stdio عبر MCP.
  • إذا شغّلت Hermes من /root أو /home/...، فقد يُصدر Windows تحذيرًا بشأن المجلد الحالي من نوع UNC قبل بدء خادم MCP.
  • إذا انتهت مهلة chrome-devtools-mcp --autoConnect أثناء حصر الصفحات، فقلّل عدد علامات التبويب العاملة في الخلفية أو المجمّدة في Chrome ثم أعد المحاولة.

ما الذي تؤثر فيه التصفية فعليًا؟

هناك فئتان من الوظائف التي تُتاح عبر MCP في Hermes:

  1. أدوات MCP الأصلية الخاصة بالخادم
  • تُصفّى باستخدام:
    • tools.include
    • tools.exclude
  1. الـ wrappers المساعدة التي يضيفها Hermes
  • تُصفّى باستخدام:
    • tools.resources
    • tools.prompts

الـ wrappers المساعدة التي قد تراها

الموارد (Resources):

  • list_resources
  • read_resource

الـ Prompts:

  • list_prompts
  • get_prompt

لا تظهر هذه الـ wrappers إلا إذا:

  • كانت إعداداتك تسمح بها، و
  • كانت جلسة خادم MCP تدعم هذه القدرات فعليًا

لذا لن يتظاهر Hermes بأن لدى الخادم موارد أو prompts إن لم تكن لديه.

ملاحظات حول الحدود:

  • يعمل Open Scaffold MCP محليًا في المقام الأول، وهو للقراءة فقط افتراضيًا.
  • تتطلب أدوات الكتابة الخاصة به تشغيل الخادم مع --allow-write؛ لا تفعّل ذلك حتى تريد صراحةً أن يعدّل Hermes ملفات .osc.
  • يسجّل Open Scaffold العمل ويضع له بوابات (gates)؛ لكنه لا يفوّض Hermes بالدمج (merge)، أو النشر، أو الـ deploy، أو إنشاء بيئات تشغيل (runtimes).
  • ثبّت الإصدار عبر open-scaffold@<version> بدلًا من @latest إذا كنت تحتاج إلى مخططات أدوات (tool schemas) قابلة لإعادة الإنتاج.

توصيات للاستخدام الآمن

فضّل قوائم السماح للأنظمة الخطيرة

لأي شيء مالي، أو موجّه إلى العملاء، أو قد يكون مدمّرًا:

  • استخدم tools.include
  • ابدأ بأصغر مجموعة ممكنة

عطّل الأدوات المساعدة غير المستخدمة

إذا كنت لا تريد أن يتصفّح النموذج الموارد أو الـ prompts التي يوفّرها الخادم، فعطّلها:

أبقِ نطاق الخوادم ضيقًا

أمثلة:

  • خادم نظام ملفات جذره مجلد مشروع واحد، وليس مجلد المنزل (home) بأكمله
  • خادم git موجّه إلى مستودع واحد
  • خادم API داخلي يُتيح افتراضيًا أدوات يغلب عليها طابع القراءة

أعد التحميل بعد تغيير الإعدادات

افعل ذلك بعد تغيير:

  • قوائم include/exclude
  • خيارات التفعيل (enabled)
  • مفاتيح تشغيل resources/prompts
  • ترويسات المصادقة (auth headers) / متغيرات البيئة

استكشاف الأخطاء وإصلاحها حسب العَرَض

"الخادم متصل لكن الأدوات التي توقعتها غير موجودة"

الأسباب المحتملة:

  • صُفّيت بواسطة tools.include
  • استُبعدت بواسطة tools.exclude
  • عُطّلت الـ wrappers المساعدة عبر resources: false أو prompts: false
  • الخادم لا يدعم الموارد أو الـ prompts فعليًا

"الخادم مُعدّ لكن لا شيء يُحمَّل"

تحقّق من أن:

  • enabled: false لم يُترك في الإعدادات
  • الأمر أو بيئة التشغيل موجودة (npx، uvx، وغيرهما)
  • الـ HTTP endpoint قابل للوصول
  • متغيرات بيئة المصادقة أو الترويسات صحيحة

"لماذا أرى أدوات أقل مما يُعلن عنه خادم MCP؟"

لأن Hermes أصبح يحترم السياسة التي تحددها لكل خادم، ويعتمد تسجيلًا يراعي القدرات المدعومة. هذا سلوك متوقع، وعادةً ما يكون مرغوبًا.

"كيف أزيل خادم MCP دون حذف إعداداته؟"

استخدم:

يُبقي هذا الإعدادات محفوظة لكنه يمنع الاتصال والتسجيل.

إعدادات MCP الأولى الموصى بها

خوادم مناسبة للبدء لمعظم المستخدمين:

  • filesystem
  • git
  • GitHub
  • خوادم MCP من نوع fetch أو خوادم التوثيق
  • API داخلي واحد محدود النطاق

خوادم غير مناسبة للبدء:

  • أنظمة الأعمال الضخمة التي تحتوي على كثير من الإجراءات المدمّرة دون أي تصفية
  • أي شيء لا تفهمه جيدًا بما يكفي لتقييده

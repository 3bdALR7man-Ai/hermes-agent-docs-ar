مشكلات المزوّد والنموذج

الوكيل يقول إن "Hermes policy" أو "Hermes guardrails" رفضت طلبي

لا يستطيع النموذج أن يحدد بشكل موثوق سبب رفضه لطلبٍ ما. إذا ظهر الرفض في النص النثري للمساعد فقط، فقد يكون ادعاؤه بأن سياسة وقت تشغيل خفية في Hermes هي السبب تفسيرًا مُختلَقًا ناتجًا عن الهلوسة، أو قيدًا فرضه النموذج أو المزوّد المختار.

تطبيق القيود في Hermes صريح: إجراء الأداة المحظور يُعيد خطأ أداة يُسمّي الأمر أو المسار المرفوض، والإجراء الذي يتطلب موافقة يعرض طلب موافقة. ولا يحوّل Hermes ضوابط التنفيذ هذه بصمت إلى طبقة عامة لرفض المحتوى. ومع ذلك، قد تُطبَّق ضوابط على مستوى المزوّد عند إعدادها، مثل Amazon Bedrock Guardrails.

لعزل مصدر الرفض:

  1. نفّذ /status للتأكد من النموذج والمزوّد النشطين.
  2. تحقق مما إذا كان الرفض يتضمن خطأ أداة فعليًا من Hermes أو طلب موافقة. إذا كان نصًا نثريًا فقط، فلا تتعامل مع نسبة النموذج للرفض على أنها دليل من وقت التشغيل.
  3. أعد المحاولة في جلسة جديدة باستخدام نموذج أو مزوّد آخر مُعَدّ. الرفض الذي يتغير بتغيّر النموذج هو سلوك خاص بالنموذج/المزوّد، وليس ضابط تنفيذ من Hermes.
  4. إذا ظهر خطأ أداة صريح، فاستخدم نصه الحرفي عند الإبلاغ عن المشكلة.

راجع الأمان للاطلاع على ضوابط التنفيذ الموثّقة في Hermes، وصفحة المزوّدين (Providers) لمعرفة كيفية إعداد المزوّدين.

الملفات الشخصية (Profiles)

ما الفرق بين الـ profiles ومجرد ضبط HERMES_HOME؟

الـ profiles طبقة مُدارة فوق HERMES_HOME. يمكنك ضبط HERMES_HOME=/some/path يدويًا قبل كل أمر، لكن الـ profiles تتولى كل التفاصيل التأسيسية نيابةً عنك: إنشاء بنية المجلدات، وتوليد أسماء مستعارة (aliases) للـ shell (hermes-work)، وتتبّع الـ profile النشط في ~/.hermes/active_profile، ومزامنة تحديثات المهارات عبر جميع الـ profiles تلقائيًا. كما تتكامل مع الإكمال التلقائي بمفتاح Tab، فلا تحتاج إلى تذكّر المسارات.

هل يمكن لاثنين من الـ profiles مشاركة token البوت نفسه؟

لا. تتطلب كل منصة مراسلة (Telegram و Discord وغيرهما) وصولًا حصريًا إلى token البوت. إذا حاول اثنان من الـ profiles استخدام الـ token نفسه في الوقت ذاته، فسيفشل الـ gateway الثاني في الاتصال. أنشئ بوتًا منفصلًا لكل profile — وبالنسبة إلى Telegram، تحدّث إلى @BotFather لإنشاء بوتات إضافية.

هل تتشارك الـ profiles الذاكرة أو الجلسات؟

لا. لكل profile مخزن ذاكرة خاص به، وقاعدة بيانات للجلسات، ومجلد للمهارات، فهي معزولة تمامًا. إذا أردت بدء profile جديد بالذكريات والجلسات الموجودة، فاستخدم hermes profile create newname --clone-all لنسخ كل شيء من الـ profile الحالي، أو أضف --clone-from <profile> للنسخ من profile مصدر محدد.

وهذا العزل هو أيضًا سبب عدم تشغيل وكيلين أبدًا على الـ profile نفسه أو مجلد Hermes الرئيسي نفسه: فكلاهما يكتب في الذاكرة تلقائيًا، ويحمّل كلٌّ منهما ما كتبه الآخر عند بدء الجلسة، فتتدهور الحالة المخزّنة لديهما مع كل جلسة. وكيل واحد لكل profile؛ وإذا أردت ذاكرة مشتركة فعلًا بين الوكلاء، فاستخدم مزوّد ذاكرة خارجيًا.

ماذا يحدث عند تشغيل hermes update؟

يسحب hermes update أحدث إصدار من الكود ويعيد تثبيت الاعتماديات مرة واحدة (وليس لكل profile)، ثم يزامن المهارات المحدَّثة مع جميع الـ profiles تلقائيًا. لا تحتاج إلى تشغيل hermes update إلا مرة واحدة — فهو يشمل كل profile على الجهاز.

كم عدد الـ profiles التي يمكنني تشغيلها؟

لا يوجد حدّ صارم. فكل profile ما هو إلا مجلد ضمن ~/.hermes/profiles/. ويعتمد الحدّ العملي على مساحة القرص لديك وعلى عدد الـ gateways المتزامنة التي يستطيع نظامك التعامل معها (كل gateway عبارة عن عملية Python خفيفة). لا بأس بتشغيل عشرات الـ profiles؛ فالـ profile الخامل لا يستهلك أي موارد.

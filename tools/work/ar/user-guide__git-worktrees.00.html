Git Worktrees

كثيرًا ما يُستخدم Hermes Agent على مستودعات كبيرة وطويلة العمر. فعندما تريد:

  • تشغيل عدة وكلاء بالتوازي على المشروع نفسه، أو
  • إبقاء عمليات إعادة الهيكلة (refactors) التجريبية معزولة عن الـ branch الرئيسي،

فإن worktrees في Git هي الطريقة الأكثر أمانًا لمنح كل وكيل نسخته المسحوبة (checkout) الخاصة دون تكرار المستودع بأكمله.

توضّح هذه الصفحة كيفية الجمع بين worktrees و Hermes بحيث تحصل كل جلسة على مجلد عمل نظيف ومعزول.

لماذا تستخدم worktrees مع Hermes؟

يتعامل Hermes مع مجلد العمل الحالي على أنه جذر المشروع:

  • CLI: المجلد الذي تشغّل فيه hermes أو hermes chat
  • Messaging gateways: المجلد المحدد عبر terminal.cwd في ~/.hermes/config.yaml

إذا شغّلت عدة وكلاء في النسخة المسحوبة نفسها، فقد تتداخل تغييراتهم مع بعضها:

  • قد يحذف أحد الوكلاء ملفات يستخدمها الآخر أو يعيد كتابتها.
  • يصبح من الأصعب معرفة أي التغييرات تنتمي إلى أي تجربة.

باستخدام worktrees، يحصل كل وكيل على:

  • branch ومجلد عمل خاصين به
  • سجل Checkpoint Manager خاص به لاستخدامه مع /rollback

راجع أيضًا: نقاط الحفظ (Checkpoints) و /rollback.

البدء السريع: إنشاء worktree

من داخل الجلسة: /worktree new

أسرع طريقة (مستوحاة من /worktree new في Copilot CLI): من جلسة CLI تفاعلية، نفّذ

يُنشئ Hermes المجلد .worktrees/my-experiment/ داخل المستودع (على الـ branch hermes/my-experiment، استنادًا إلى أحدث طرف للمستودع البعيد بعد جلبه للتو، ما لم يكن worktree_sync: false)، ويعيد توجيه أدوات الطرفية والملفات الخاصة بالجلسة إليه — دون الحاجة إلى إعادة التشغيل. احذف الاسم لتحصل على شجرة عشوائية باسم hermes-<id>. يعرض /worktree وحده الشجرة النشطة، ويسرد /worktree list جميع الأشجار. وعند الخروج تُحذف الشجرة النظيفة التي دُفعت commits الخاصة بها؛ أما الشجرة ذات التغييرات غير المُثبَّتة أو commits غير المدفوعة فتُطرح عليها السؤال نفسه (إبقاء / أرشفة / إزالة) كما في hermes -w.

  • تكتب نقاط الحفظ تحت hash مختلف لمستودع الظل (shadow repo) (مشتق من مسار الـ worktree).

  • تشغيل عمليات إعادة هيكلة دفعية.
  • تجربة مناهج مختلفة للمهمة نفسها.
  • الجمع بين جلسات CLI و gateway على المستودع الأصلي (upstream) نفسه.

تنظيف worktrees بأمان

عندما تنتهي من تجربة ما:

  1. قرّر ما إذا كنت ستحتفظ بالعمل أم ستتخلص منه.
  2. إذا أردت الاحتفاظ به:
    • ادمج (merge) الـ branch في الـ branch الرئيسي كالمعتاد.
  3. أزِل الـ worktree:

ملاحظات:

  • يرفض git worktree remove إزالة worktree يحتوي على تغييرات لم تُنفَّذ لها commit ما لم تفرض ذلك.
  • إزالة الـ worktree لا تحذف الـ branch تلقائيًا؛ ويمكنك حذف الـ branch أو الاحتفاظ به باستخدام أوامر git branch المعتادة.
  • لا تُحذف بيانات نقاط الحفظ الخاصة بـ Hermes ضمن ~/.hermes/checkpoints/ تلقائيًا عند إزالة worktree، لكنها عادةً صغيرة جدًا.

أفضل الممارسات

  • worktree واحد لكل تجربة Hermes
    • أنشئ branch/worktree مخصصًا لكل تغيير جوهري.
    • يُبقي هذا الفروقات (diffs) مركّزة، والـ PRs صغيرة وقابلة للمراجعة.
  • سمِّ الـ branches باسم التجربة
    • مثل feature/hermes-checkpoints-docs ، feature/hermes-refactor-tests.
  • نفّذ commits بشكل متكرر
    • استخدم git commits للمراحل الرئيسية.
    • استخدم نقاط الحفظ و /rollback كشبكة أمان للتعديلات التي تُجريها الأدوات فيما بينها.
  • تجنّب تشغيل Hermes من جذر المستودع المجرّد عند استخدام worktrees
    • فضّل بدلًا من ذلك مجلدات الـ worktrees، بحيث يكون لكل وكيل نطاق واضح.

استخدام hermes -w (وضع worktree التلقائي)

يتضمن Hermes الخيار المدمج -w الذي يُنشئ تلقائيًا git worktree مؤقتًا مع branch خاص به. لا تحتاج إلى إعداد worktrees يدويًا — فقط انتقل بالأمر cd إلى مستودعك ونفّذ:

سيقوم Hermes بما يلي:

  • إنشاء worktree مؤقت ضمن .worktrees/ داخل مستودعك.
  • سحب branch معزول (مثل hermes/hermes-<hash>).
  • تشغيل جلسة CLI كاملة داخل ذلك الـ worktree.

يسحب Hermes نسخة worktree دون تشغيل إعدادات git الخاصة بالمستودع: تُعطَّل hooks الخاصة به، و core.fsmonitor ، ومرشحات clean/smudge أثناء سحب هذه النسخة، كما يحدث مع worktrees التي ينشئها Hermes لمهام Kanban و subagents. ويحصل المستودع الذي يخزّن ملفاته عبر Git LFS على ملفات مؤشرات فيها؛ نفّذ git lfs pull داخل worktree إذا احتاجت الجلسة إلى محتوياتها.

مغادرة جلسة فيها عمل غير مكتمل

عندما تنتهي جلسة hermes -w تفاعلية (classic CLI أو --tui) ويكون في worktree الخاص بها تغييرات غير مُثبَّتة أو commits غير مدفوعة، يسأل Hermes:

  • إبقاء الـ worktree (الافتراضي، وهو أيضًا ما يختاره Enter/Esc) — لا يتغير شيء.
  • أرشفته ثم إزالته — تُؤرشف حالة العمل كاملة (انظر أدناه) وتُزال الشجرة قبل أن تنتهي الجلسة من الخروج، فلا تُقطع شجرة كبيرة في منتصف العملية؛ ويطبع Hermes الأمر hermes worktree restore. وإذا فشلت الأرشفة تُبقى الشجرة.
  • إزالته وتجاهل التغييرات — فقط عندما تختاره صراحةً.

لا تسأل أبدًا عمليات التشغيل لمرة واحدة (-q و -z)، ولا مهام cron، ولا جلسات gateway، ولا أي خروج بلا طرفية: تُبقى الشجرة ويتولاها لاحقًا مسح الأشجار القديمة (stale-worktree sweep). أما الشجرة النظيفة التي دُفعت commits الخاصة بها فتُزال دون سؤال.

مسح الأشجار القديمة واستعادتها

يُسجَّل كل مستودع ينشئ فيه Hermes worktree (hermes -w و /worktree new، وعزل worktree للـ subagent، ولوحة git في تطبيق سطح المكتب) في <HERMES_HOME>/worktree_repos.json للـ profile النشط. عند بدء hermes -w وكل 6 ساعات من مُؤقِّت cron، يمسح Hermes المجلد .worktrees/ في كل مستودع من تلك المستودعات:

خاملة تجاوزت مستواها (Tier) (hermes-*/subagent-* 24 ساعة، والأشجار المسمّاة 72 ساعة)، ونظيفة ومدموجة أو مدفوعةتُزال
خاملة تجاوزت مستواها مع تغييرات غير مُثبَّتة أو commits غير مدفوعةتُؤرشف ثم تُزال
مالك قفل hermes حي، أو أي عملية حية يقع cwd الخاص بها (وفي Linux: أو ملف مفتوح) داخلهالا تُمسّ أبدًا
نشاط في ملف أو HEAD أو reflog أحدث من مستواها (الملف المحذوف يُحتسب عبر مجلده)لا تُمسّ أبدًا
أشجار مهام Kanban (t_<hex>)لا تُمسّ أبدًا (يتولاها Kanban GC)

مستودع مضمَّن في أي موضع داخلها، سواء كان مُتجاهَلًا (gitignored) أم لا (مثل build/tool/.git)تُبقى (keep-unarchivable)
commit محفوظ فقط عبر مرجع خاص بكل worktree (refs/worktree/* و refs/bisect/* و refs/rewritten/*)تُبقى (keep-worktree-refs: تُحذف تلك المراجع مع الشجرة)
ملف غير متتبَّع (untracked) أكبر من worktrees.archive_max_file_mbتُبقى (keep-large-untracked)

الملفات المتجاهَلة. الملفات المتجاهَلة (نسخ .env وcaches ومخرجات البناء والاختبار) لا تُؤرشف وتُحذف مع الشجرة. ويُستثنى من ذلك أمر واحد: مستودع git متداخل داخل مجلد متجاهَل يُبقي الشجرة.

تُجرى الفحوص نفسها على الأشجار النظيفة المدموجة، ويحتسب كل فحص للتغييرات الملفاتِ التي كان status.showUntrackedFiles=no سيخفيها، وملفات skip-worktree / assume-unchanged التي تختلف بايتاتها عن الفهرس.

الأرشيف هو commit محفوظ في refs/hermes/archive/<tree> يضم HEAD الخاص بالشجرة، والتغييرات المُجهَّزة (staged)، والتغييرات غير المُجهَّزة، والملفات غير المتتبَّعة (أما الملفات التي يستبعدها .gitignore، مثل node_modules/ أو .venv/، فلا تُلتقط). يُبنى باستخدام فهرس مؤقت، فلا تُعدَّل الشجرة نفسها أبدًا؛ وإذا تعذر بناء الأرشيف تُبقى الشجرة. وإذا دُخلت الشجرة أو تحركت تغييراتها المُجهَّزة (git add و git apply --cached) أثناء بناء الأرشيف، يُحفظ الأرشيف وتُبقى الشجرة أيضًا. تُخزَّن بايتات الملفات وتُستعاد كما هي تمامًا: فلا تُطبَّق أي قاعدة لنهايات الأسطر أو مرشح (filter) من .gitattributes أو info/attributes أو core.attributesFile. وتُستبعد الملفات غير المتتبَّعة الأكبر من worktrees.archive_max_file_mb وتُدرج في الأرشيف، ثم تُبقى الشجرة: ويوضح ذلك خيار Archive عند الخروج ونتيجة الـ subagent. أما الـ branch الموجود على مستودع بعيد (PR مفتوح) فيُبقى؛ وإلا يحتفظ الأرشيف بـ commits الخاصة به ويُحذف الـ branch المحلي.

تعيد الاستعادة (restore) الـ branch إلى مكانه عندما يكون مفقودًا أو لا يزال يشير إلى HEAD المؤرشف؛ وإلا تعود الشجرة في حالة detached عند ذلك الـ commit. وتُحذف الأرشيفات الأقدم من worktrees.archive_retention_days بواسطة المسح.

لا يوجد حد لعدد الأشجار الممكن وجودها: مئات الـ subagents المتوازية يحتفظ كل منها بشجرته ما دام يعمل فيها. ولا يُخلي max_total_gb إلا الأشجار الخاملة التي تجاوزت مستواها.

تتبع worktrees الخاصة بالـ subagents (delegation.worktree_isolation: true) القاعدة نفسها عند انتهاء الابن: تُزال الشجرة النظيفة، وتُؤرشف الشجرة التي فيها commits أو تعديلات وتُزال مع إبقاء الـ branch الخاص بها ليدمجه الأصل.

جمع كل ما سبق معًا

  • استخدم git worktrees لمنح كل جلسة Hermes نسختها المسحوبة النظيفة الخاصة.
  • استخدم الـ branches لتسجيل السجل العام لتجاربك.
  • استخدم نقاط الحفظ + /rollback للتعافي من الأخطاء داخل كل worktree.

يمنحك هذا الجمع:

  • ضمانات قوية بألا يتداخل الوكلاء والتجارب المختلفة مع بعضها.
  • دورات تكرار سريعة مع سهولة التعافي من التعديلات السيئة.
  • pull requests نظيفة وقابلة للمراجعة.

تطوير واجهات UI عبر worktrees

تحتاج واجهات TypeScript (ui-tui/ ، apps/desktop/) كلٌّ منها إلى node_modules ، وتنفيذ npm ci جديد لكل worktree يكرّرها عبر كل branch. إذا كنت تعمل على TUI أو تطبيق سطح المكتب من عدة worktrees، فراجع تطوير TUI و Desktop من Worktrees للتعرّف على الأداتين المساعدتين htui / hgui اللتين تتشاركان تثبيتًا واحدًا عبر symlink.

ينعكس كل profile في سجل مصادقة Hermes تحت auth_type الذي يعلنه (استثناءان: api_key له env_vars فارغ، ومعرّفات المجمّع/المزوّد التي يقدمها المستخدم openrouter/custom بالإضافة إلى المزوّدين المدمجين ذوي التحديث المخصص copilot/kimi-coding/zai)، لذا فإن hermes auth, --provider <name> وتحديد بيئة التشغيل يقبلانه مهما كانت بنيته. ويختلف المسؤول عن تسجيل الدخول: تحصل profiles من نوع api_key على prompt المفتاح المدمج / تحديد متغير البيئة؛ وكل auth_type آخر يكون مملوكًا للمزوّد — فتقدم الإضافة hooks الاثنين أدناه، ويجعل profile غير api-key دون auth_handler الأمر hermes auth add <name> يفشل بخطأ واضح "ships no auth_handler" بدل ألا يفعل شيئًا بصمت.

مصادقة مملوكة للمزوّد (auth_handler, refresh_credential)

auth_type يصف نوع بيانات الاعتماد التي يحتاجها المزوّد؛ و auth_handler هو طريقة حصول الإضافة عليها — عبر مسار device-code / OIDC / IdC خاص بها ضمن مجموعة أوامر hermes auth الحالية (يتجاوز محمّل إضافات الأوامر العام manifests مزوّدي النماذج، لذا ليس register(ctx) طريقة إضافة الأوامر). و refresh_credential هو كيفية تدوير مجمع بيانات الاعتماد token مُجمعًا خزّنته الإضافة.

العقد
auth_handler(action, args)args هو نطاق أسماء hermes auth المحلّل لإجراءات CLI ؛ ويمرر منتقي الإعداد التفاعلي نطاقًا محدودًا لا يحمل إلا provider، لذا اقرأ الخيارات باستخدام getattr(args, name, None). قيمة صادقة = تمت المعالجة (لا يطبع Hermes شيئًا آخر، والخروج 0)؛ قيمة غير صادقة = العودة إلى المسار المدمج لذلك الإجراء. ويتحول الاستثناء إلى SystemExit("<provider> auth handler failed for <action>: …").
refresh_credential(entry)يتلقى PooledCredential؛ ويعيد تعيينًا للقيم المدوّرة أو None. والمفاتيح التي تكون حقول PooledCredential (access_token, refresh_token, expires_at_ms، …) تستبدل حقول الصف؛ ويذهب كل مفتاح آخر (expires_in, token_type, scope — البنية الخام لـ token-endpoint) إلى entry.extra ويُحفظ ويُستعاد عبر auth.json. وتعني إعادة None/تعيين فارغ أن الإضافة لم تستطع التدوير: يُستبعد الصف مؤقتًا تمامًا كطلب تحديث فاشل (ولا يُبلغ عنه كمحدّث، فلا يُعاد استخدام bearer متوقف). ووجوده هو ما يجعل المزوّد قابلًا للتحديث — hermes auth refresh <name> واسترداد 401 في الحلقة الرئيسية يستدعيانه عبر المجمع دون تدخل أي قائمة أسماء في النواة؛ ولا يصل إليه استرداد 401 في العميل المساعد إلا للصفوف المُجمعة التي يعاملها بالفعل كقابلة للاسترداد (صفوف api-key ومسارات OAuth المدمجة).
إخفاقات التحديثارفع hermes_cli.auth_constants.AuthError(..., relogin_required=True) (أو مع code invalid_grant / invalid_token / refresh_token_reused) عند انتهاء المنح: يصبح الصف DEAD، ويخرج من التدوير، ويسجل Hermes تحذير WARNING يذكر hermes auth add <name>. وأي استثناء آخر (الشبكة، أو 429، أو 5xx) مؤقت — يُستبعد الصف لدورة تهدئة واحدة ثم تُعاد المحاولة.
التزامنيعمل hook تحت قفل auth.json المشترك. وقبل استدعائه يعيد المجمع قراءة الصف؛ وإذا كانت عملية Hermes أخرى (gateway + CLI ، أو profile اثنان) قد دوّرت الزوج بالفعل، يُعتمد ذلك الزوج و لا يُستدعى hook الخاص بك — وهذا آمن لـ refresh tokens أحادية الاستخدام. وبعد عودة hook ، يُكتب الصف المدوّر إلى auth.json.
دون hooksapi_key تتصرف تمامًا كما سابقًا. ويفشل أي auth_type آخر دون auth_handler بوضوح عند hermes auth add.

hermes auth add|status|logout|refresh <provider> يستشير المعالج أولًا — قبل مسار مجمع بيانات الاعتماد المدمج. وعند تسجيل الاسم نفسه مرتين يتقدم آخر كاتب، لذا تستطيع إضافة مستخدم استبدال مسار مزوّد مضمّن.

يمرر Hermes نطاق الأسماء المحلّل، لا الخيارات المُعلَنة من المزوّد: اطلب القيم الخاصة بالمزوّد تفاعليًا (أو اقرأ إعداداتك/بيئتك). والصفوف التي تخزنها الإضافة في المجمع ملكها — تبقى المفاتيح الإضافية عبر load → save → load، ولا يمرر Hermes أي أسرار خارج ذلك الصف المُجمع إلى refresh_credential.

OAuth تصريحي (PKCE) للإضافات

لا يحتاج المزوّد الذي يدعم IdP لديه OAuth 2.0 Authorization Code + PKCE القياسي إلى كتابة hooks أعلاه يدويًا: أعلن endpoints في OAuthPKCEConfig ودع دالتي الإنشاء تبنيانهما.

حينها يملك Hermes دورة الحياة كلها: يفتح hermes auth add example-pkce [--no-browser] المتصفح (أو يطبع URL مع تلميح SSH-tunnel على جهاز بعيد)، ويستمع على http://127.0.0.1:<port>/callback، ويفحص CSRF state، ويبادل الرمز باستخدام S256 PKCE ويخزن المنح كبيانات اعتماد oauth مُجمّعة (source: manual:loopback_pkce, expires_at_ms, refresh_token); auth status يبلغ عن تسجيل الدخول / انتهاء الصلاحية؛ ويزيل auth logout الصفوف؛ ويدوّر auth refresh ومسارات استرداد 401 عبر منح refresh_token، مع إعادة قراءة auth.json تحت قفل المصادقة أولًا كي يُعتمد تدوير النظير بدل إنفاق refresh token أحادي الاستخدام مرتين.

حد الأمان (مفروض قبل أي طلب، عند الدخول والتحديث على حد سواء): يجب أن يكون كلا endpoint بصيغة https:// (لا يُقبل http:// العادي إلا لمضيف بعنوان loopback حرفي — أي IdP تطوير محلي)؛ ويجب أن يكون مضيف token_url هو مضيف authorize_url أو نطاقًا فرعيًا له (أو مدرجًا في allowed_hosts)؛ ويرتبط المستمع بالعنوان الحرفي 127.0.0.1؛ ولا تُسجّل tokens أو state أو PKCE verifier مطلقًا. الحقول الاختيارية: audience, extra_authorize_params, extra_token_params, redirect_path, timeout_seconds, label.

يضبط العميل السري الذي يوجد سره وراء وسيطك token_request بدل token_url: يستدعيه Hermes بحقوق المنح (grant_type, code / refresh_token, redirect_uri, code_verifier) ويخزن أي JSON لـ token-endpoint يعيده، مع الاحتفاظ بـ refresh_token القديم عندما تحذفه الاستجابة. ارفع AuthError(..., relogin_required=True) للمنح الذي يبلّغ الوسيط عن انتهاء صلاحيته. تُدوّر الصفوف قبل expires_at_ms المخزّن، فتُحدث access tokens غير الشفافة (غير JWT) في وقتها؛ ويستأجر العميل المساعد (الضغط، والعناوين) الصف المُجمع نفسه.

الاسترداد وتصنيف الأخطاء

تُحمَّل إضافة kind: model-provider بواسطة اكتشاف المزوّدين، لا بواسطة مدير الإضافات العام، لذا لا يمكن الوصول منها إلى hook الإضافة transform_api_error_classification دون تقديم مكون إضافة ثانٍ. ويحمل الـ profile نقطة التكامل المكافئة بدلًا من ذلك:

العقد
classify_api_error(error, *, status_code, error_code, message, body, model)يستشيره agent.error_classifier.classify_api_error لإخفاقات هذا المزوّد وحده، بعد أي hooks عامة transform_api_error_classification وقبل pipeline المدمج. و message هو نص الخطأ بأحرف صغيرة، و body هو جسم JSON المحلّل (قد يكون فارغًا). أعد {"reason": <FailoverReason name>} بالإضافة إلى retryable / should_compress / should_rotate_credential / should_fallback / error_context الاختيارية للتجاوز (للأسباب النهائية — الفوترة، والمصادقة، و model_not_found … — يتضمن should_fallback: True القيمة retryable: False ما لم تضبطها، لأن سلسلة البدائل لا تعمل إلا للأحكام غير القابلة لإعادة المحاولة؛ وتحافظ أسباب حد المعدل على البنية المدمجة لإعادة المحاولة ثم البديل)؛ ويترك None (أو سبب غير معروف) الحكم المدمج كما هو. تُحتوى الاستثناءات وتُسجل عند DEBUG. ويوجه الحكم الاسترداد نفسه المستخدم للمزوّدين المدمجين — مثلًا يستبعد billing بيانات الاعتماد لمدة TTL الفوترة بدل تهدئة 403 المؤقتة.
401 على بيانات اعتماد إضافةيعالجه مجمع بيانات الاعتماد دون تعديل النواة: يُحدّث الصف المُجمع الفاشل عبر refresh_credential مرة لكل محاولة (بحد أقصى تحديثين لكل صف في الجلسة)، ويُعاد بناء العميل بالـ token المدوّر وإعادة الطلب. وتستبعد عودة None/فارغة أو استثناء الصف — ثم يدوّر الطلب أو يعود إلى العبارة العامة "sign in again: hermes auth add <name>"، لا إلى إرشاد مزوّد مدمج مطلقًا.
الاستدعاءات المساعدةتخدم إضافة oauth_external / oauth_device_code التي تقدم create_client المهام المساعدة على صفها المُجمع (يُدوّر الصف الذي يوشك على الانتهاء أولًا)؛ وتأخذ أخطاء 401 المساعدة تحديث المجمع نفسه (try_refresh_current → refresh_credential).

الاسترداد الذي يظل مرتبطًا بالاسم في النواة سلوك لا يملك بنية عامة آمنة (مخزن token خاص بمزوّد لإعادة المزامنة، أو حاجز استحقاق لشريحة خطة، أو حجر refresh-token أحادي الاستخدام). وتملك الإضافة التي تحتاج أحد هذه السلوكيات تنفيذه داخل refresh_credential / classify_api_error.

التكامل مع PluginManager العام

المكوّن العام PluginManager (وهو ما يعمل عليه hermes plugins يعمل عليه) يرى إضافات مزوّدي النماذج لكنه لا يستوردها — إذ يتولى providers/__init__.py دورة حياتها. ويسجّل المدير البيان (manifest) لأغراض الاستبطان ويصنّفها حسب kind: model-provider. وعندما تضع إضافة مستخدم غير مصنّفة في $HERMES_HOME/plugins/ وتصادف أنها تستدعي register_provider مع ProviderProfile، يحوّلها المدير تلقائيًا إلى kind: model-provider بأسلوب استدلالي يعتمد على نص الشيفرة المصدرية — فتُوجَّه الإضافة توجيهًا صحيحًا حتى دون plugin.yaml.

التوزيع عبر pip

يمكن توزيع مزوّدي النماذج كحزمة pip. أتِح نقطة دخول (entry point) ضمن المجموعة hermes_agent.plugins في ملف pyproject.toml:

يمكن أن يكون الهدف أحد الخيارين:

  • هو كائنًا قابلًا للاستدعاء (module:func) — يُستدعى دون وسائط، وينبغي أن يستدعي register_provider(profile)، أو
  • هو وحدة مجردة (module) — تُستورد من أجل الأثر الجانبي لاستدعاء register_provider(...) على مستوى الوحدة، على غرار عقد __init__.py في الإضافات القائمة على المجلدات.

providers/__init__.py نقاط الدخول هذه بنفسه — فالمكوّن العام PluginManager لا يستدعي أبدًا تسجيل المزوّدين لحزم pip (إذ يستهدف مسار نقاط الدخول لديه الإضافات العامة بنمط register(ctx)، ويخضع لـ plugins.enabled)، لذا يجري سجل المزوّدين فحصه الخاص. وتنطبق قاعدتان:

  • التفعيل الصريح (opt-in) مطلوب. تحكم هذا الفحص قائمة السماح نفسها plugins.enabled (وقائمة المنع plugins.disabled) الموجودتان في config.yaml. فلا تُستورد حزمة pip أبدًا لمجرد أنها مثبّتة — بل يجب على المستخدمين إضافة اسم نقطة الدخول إلى plugins.enabled:

  • أدنى أسبقية. تُكتشف الإضافات القائمة على نقاط الدخول قبل الإضافات الموجودة في نظام الملفات: ولأن register_provider() تعتمد قاعدة "آخر من يكتب هو الفائز"، فإن أي profile مضمّن أو موجود في $HERMES_HOME يحمل الاسم نفسه يتفوق دائمًا على الـ profile المثبّت عبر pip. ويمكن لحزمة pip أن تضيف مزوّدًا جديدًا فعلًا، لكنها لا تستطيع الاستيلاء بصمت على اسم مزوّد رسمي.

أما الأهداف التي تتطلب وسائط (مثل register(ctx) في الإضافات العامة) فيتخطاها فحص المزوّدين — لأنها تتبع PluginManager. ونقطة الدخول المعطوبة تُعزل — إذ تُسجَّل بمستوى تحذير وتُتخطى، ولا تعطّل أبدًا اكتشاف المزوّدين الآخرين.

راجع بناء إضافة لـ Hermes للاطلاع على الإعداد الكامل لنقاط الدخول.

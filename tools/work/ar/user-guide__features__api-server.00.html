خادم API

يوفّر خادم API وكيل hermes-agent على شكل HTTP endpoint متوافق مع OpenAI. ويمكن لأي واجهة أمامية (frontend) تتعامل بصيغة OpenAI — مثل Open WebUI و LobeChat و LibreChat و NextChat و ChatBox ومئات غيرها — الاتصال بـ hermes-agent واستخدامه كـ backend.

يعالج وكيلك الطلبات بمجموعة أدواته الكاملة (الطرفية، وعمليات الملفات، والبحث في الويب، والذاكرة، والمهارات) ثم يُرجع الاستجابة النهائية. وعند البث (streaming)، تظهر مؤشرات تقدّم الأدوات ضمن الاستجابة مباشرةً لتتمكن الواجهات الأمامية من عرض ما يفعله الوكيل.

backend واحد يغطي النماذج والأدوات

يحتاج Hermes نفسه إلى مزوّد مُعدّ وإلى backends للأدوات حتى يكون خادم API مفيدًا. ويتكفّل اشتراك Nous Portal بالأمرين معًا — أكثر من 300 نموذج إضافةً إلى الويب/الصور/TTS/المتصفح عبر Tool Gateway. نفّذ hermes setup --portal مرة واحدة قبل تشغيل خادم API، وستحصل الواجهات الأمامية مثل Open WebUI أو LobeChat على backend مجهّز بالأدوات بالكامل.

GET /v1/models

يسرد الوكيل كنموذج متاح. ويكون اسم النموذج المُعلَن افتراضيًا هو اسم الـ profile (أو hermes-agent للـ profile الافتراضي). تحتاج إليه معظم الواجهات الأمامية لاكتشاف النماذج.

المسار /v1/models هو عمدًا الواجهة الخفيفة المتوافقة مع OpenAI. فهو لا يسرد كل تركيبات المزوّد/النموذج المصادَق عليها التي يمكن لـ Hermes التوجيه إليها، ولا يُثري النتائج بمعلومات الأسعار أو القدرات.

GET /api/model/options

يمكن للعملاء المُدركين لخصائص Hermes طلب قائمة المزوّدين/النماذج المنتقاة نفسها التي تستخدمها لوحة التحكم و TUI. يستخدم هذا المسار مصادقة bearer المعتادة في خادم API، ويُرجع صفوف المزوّدين، وتلميحات حول قدرات النماذج، وبيانات وصفية للأسعار لا مكان لها في استجابة /v1/models المتوافقة مع OpenAI:

هذه البيانات هي الأساس نفسه الذي تعتمد عليه صفحة Models في لوحة التحكم واستدعاء RPC المسمّى model.options في TUI. فهي تُرجع المزوّدين المصادَق عليهم، وقوائم النماذج المنتقاة، وأسعار كل نموذج، وتلميحات حول قدرات النماذج.

الفتح العادي متحفّظ عمدًا مع المزوّدين المخصّصين: إذ لا يفحص Hermes إلا الـ endpoint المخصص المحدَّد حاليًا، حتى لا يعطّل endpoint محفوظ قديم أو غير متصل المنتقي. أما التحديث الصريح فينتقل إلى الفحص الكامل ويُفرغ التخزين المؤقت لنماذج المزوّد:

استخدم /v1/models عندما يحتاج عميل متوافق مع OpenAI إلى اسم نموذج فقط لإرساله في طلبات chat/responses. واستخدم /api/model/options عندما تحتاج واجهة مصادَق عليها إلى البيانات الوصفية الأغنى الخاصة بمنتقي Hermes.

GET /v1/capabilities

يُرجع وصفًا قابلًا للقراءة آليًا للواجهة المستقرة التي يوفّرها خادم API، وذلك للواجهات الخارجية ومنظِّمات التشغيل (orchestrators) وجسور الإضافات.

استخدم هذا الـ endpoint عند دمج لوحات التحكم أو واجهات المتصفح أو مستويات التحكم (control planes)، لكي تكتشف ما إذا كان إصدار Hermes العامل يدعم runs والبث والإلغاء واستمرارية الجلسة، دون الاعتماد على تفاصيل Python الداخلية الخاصة.

التحكم عبر امتداد المتصفح

يمكن لـ Hermes توجيه أدوات المتصفح عبر امتداد متصفح (browser extension) مصادَق عليه يتحكم في جلسة المتصفح المرتبطة بجلسة Hermes الحالية. هذه الميزة معطّلة افتراضيًا؛ اضبط browser.extension_control.enabled على true لتفعيلها:

يتطلب مسار API المحلي أيضًا مفتاح bearer الخاص بخادم API. ولا يمكن لوحدة التحكم (controller) التسجيل إلا لجلسة خادم موجودة. ويشتق Hermes هوية الجهة الأساسية (principal) لوحدة التحكم من حالة الخادم المصادَق عليها؛ ويُتجاهل أي principal_id يقدّمه العميل.

اكتشف العقد الحالي عبر GET /v1/capabilities. يوضّح الكائن browser_extension_control ما إذا كانت الميزة مفعّلة، وإصدار البروتوكول، وأسماء وسائل النقل (transports)، وقائمة القدرات المسموح بها بدقة:

تُستبعد القدرات المطلوبة التي تقع خارج تلك القائمة. ولا تُعدّ CDP الخام، ولا تقييم السكربتات العشوائية، ولا الوصول إلى console، ولا الرفع، ولا استخراج الصور، ولا الرؤية (vision) جزءًا من بروتوكول وحدة التحكم.

عندما لا تكون للطلب هوية وحدة تحكم مرتبطة به، أو عندما تكون الميزة معطّلة، يحتفظ Hermes بـ backend المتصفح الحالي. أما بمجرد أن يربط gateway هوية وحدة تحكم وعائلة وسيلة نقل بالطلب، يصبح مسار الامتداد هذا هو المرجع الحاسم: فوحدات التحكم المفقودة أو الملتبسة أو غير المتصلة أو غير القادرة تفشل بشكل مغلق (fail closed) بدلًا من الانتقال بصمت إلى متصفح محلي/سحابي مختلف. وبعد اختيار وحدة تحكم بعينها، تكون نتيجتها أو خطؤها هي المرجع الحاسم، ولا يعيد Hermes أبدًا محاولة الإجراء نفسه عبر backend آخر.

التسجيل عبر API المحلي

  1. أرسل طلب POST /v1/browser-control/register مصادَقًا عليه يتضمن protocol_version و session_id و controller_id و browser_profile_id و القدرات المطلوبة في capabilities.
  2. يُرجع Hermes تذكرة (ticket) للاستخدام مرة واحدة بمدة صلاحية (TTL) قدرها 30 ثانية، مع نطاق وحدة التحكم بعد تصفيته وربطه بالخادم.
  3. افتح GET /v1/browser-control/ws مع كلا بروتوكولَي WebSocket الفرعيين: hermes-browser-control-v1 و hermes-browser-control-ticket.<ticket>.

لا تُقبل التذكرة أبدًا في سلسلة الاستعلام (query string). والتذاكر غير المعروفة أو المنتهية أو المُعاد استخدامها أو المشوّهة تفشل قبل ترقية الاتصال إلى WebSocket.

إطارات وحدة التحكم

يرسل Hermes إطارات browser.controller.command تحتوي على command_id، و action، ووسائط arguments غير قابلة للتعديل، ومعرّفات المتصفح/وحدة التحكم، و tool_call_id الذي نشأ منه الطلب. وتردّ وحدة التحكم بـ browser.controller.result مع command_id نفسه، وقيمة منطقية دقيقة ok، وإما result أو error. ويؤدي الإلغاء وانتهاء المهلة إلى إصدار browser.controller.cancel؛ وتُتجاهل النتائج المتأخرة.

يؤدي الانقطاع غير المتوقع للـ socket إلى وسم وحدة التحكم بأنها غير متصلة، مع الاحتفاظ بالعمل الجاري بالفعل حتى الموعد النهائي الأصلي لكل أمر. وإعادة الاتصال بنفس الجهة الأساسية والـ profile والجلسة ومعرّف وحدة التحكم وprofile المتصفح وهوية وسيلة النقل تُحدّث وسيلة النقل دون قبول عمل جديد قبل تنفيذ أي عمليات إلغاء مؤجلة. وقد تتغير القدرات المتفاوض عليها عند إعادة الاتصال تلك؛ فهي ليست من حقول الهوية. أما اختلاف معرّف وحدة التحكم أو profile المتصفح ضمن مسار الجلسة المصادَق عليه نفسه فيُعدّ استبدالًا نهائيًا: إذ يُلغى العمل المعلّق القديم قبل أن تصبح الوحدة البديلة قابلة للتوجيه. أرسل browser.controller.detach عبر وسيلة النقل المصادَق عليها لوحدة التحكم لإجراء فصل نهائي مقصود — وهذا يلغي العمل المعلّق فورًا. أما مجرد إغلاق الـ socket فيُعامل كانقطاع قابل للاسترداد.

توفّر وسيلة النقل المصادَق عليها في لوحة التحكم دلالات التسجيل والنتائج ونبضات الحياة (heartbeat) والقدرات والملكية نفسها عبر قناة Gateway RPC/الأحداث الخاصة بها. وفي كلتا وسيلتي النقل، يتطلب الاختيار تطابقًا دقيقًا واحدًا لا لبس فيه في الجهة الأساسية والـ profile والجلسة ووحدة التحكم وprofile المتصفح وعائلة وسيلة النقل والقدرة. وبمجرد الاختيار، يكون فشل وحدة التحكم هو المرجع الحاسم ولا تُعاد محاولته أبدًا عبر backend متصفح مختلف.

اختيار النموذج لكل طلب

يمكن للعملاء المصادَق عليهم تجاوز اختيار النموذج الافتراضي في Hermes لكل طلب على حدة بإرسال:

  • model — معرّف النموذج المستهدف لهذا الدور
  • provider — المعرّف المختصر (slug) لمزوّد Hermes لتحديد بيانات الاعتماد/بيئة التشغيل لهذا الدور
  • model_options — عناصر تحكم الاستدلال (reasoning) / فئة الخدمة (service tier) الخاصة بهذا الطلب فقط

تُقبل حقول الطلب نفسها على:

  • POST /v1/chat/completions
  • POST /v1/responses
  • POST /v1/runs
  • POST /api/sessions/{session_id}/chat
  • POST /api/sessions/{session_id}/chat/stream

ترتيب الأولوية حتمي:

  1. تجاوز /model على مستوى الجلسة، إن كان للجلسة تجاوز بالفعل
  2. ربط ثابت في gateway.platforms.api_server.model_routes يُختار عندما تكون قيمة model في الطلب اسمًا مستعارًا لمسار مُعدّ
  3. قيمتا model / provider المباشرتان في الطلب عندما لا يتطابق أي اسم مستعار لمسار
  4. الإعدادات العامة لـ gateway / القيم الافتراضية من البيئة

يظل model_options خاصًا بالطلب بغض النظر عن النموذج/المزوّد الذي يُعتمد في النهاية. وإذا أرسل طلبٌ provider يتعارض مع اسم مستعار مُعدّ في model_routes، يرفض Hermes الطلب مع 400 بدلًا من خلط بيانات اعتماد المسار بصمت مع مزوّد آخر.

قيم model المجرّدة على endpoints المتوافقة مع OpenAI تتطلب تفعيلًا صريحًا. فعملاء OpenAI العامّون كثيرًا ما يثبّتون أسماء النماذج في الكود (gpt-4o، ...)، وتعتمد عمليات النشر القائمة على عودة هذه القيم إلى النموذج الافتراضي في gateway. لذلك، على POST /v1/chat/completions و POST /v1/responses، تُتجاهل قيمة model المُرسلة دون أي provider ما لم تفعّل:

أما الطلبات التي تتضمن provider صريحًا — وكذلك endpoints الأصلية في Hermes مثل /v1/runs و endpoints محادثة الجلسات — فتلتزم دائمًا بالنموذج المطلوب بغض النظر عن هذا الخيار.

مثال:

GET /health

فحص السلامة (health check). يُرجع {"status": "ok"}. ومتاح أيضًا على GET /v1/health لعملاء OpenAI المتوافقين الذين يتوقعون البادئة /v1/.

GET /health/detailed

فحص جاهزية مصادَق عليه لأنظمة المراقبة ومستويات التحكم. يعرض حالة موجزة لإعدادات الـ profile النشط، وقاعدة بيانات الحالة، والنموذج المُعدّ، ومساحة القرص، وحالة gateway/المنصات، وعمليات API الجارية، وعمليات إكمال العمليات المعلّقة، والتفويضات النشطة. وتكشف الاستجابة عن الحالة والأعداد فقط، لا عن قيم الإعدادات أو بيانات الاعتماد أو المسارات أو الأوامر أو حمولات قوائم الانتظار أو الأخطاء الخام.

يبقى المسار العام /health فحصًا خفيفًا لبقاء الخدمة حيّة (liveness) ولا يُجري فحوص الجاهزية. ونتيجة الجاهزية المتدهورة لا تزال تستخدم HTTP 200؛ لذا افحص الحقلين status و readiness.checks في المستوى الأعلى.

Runs API (بديل ملائم للبث)

إلى جانب /v1/chat/completions و /v1/responses، يوفّر الخادم واجهة runs API للجلسات الطويلة التي يريد فيها العميل الاشتراك في أحداث التقدّم بدلًا من إدارة البث بنفسه.

POST /v1/runs

ينشئ تشغيلًا (run) جديدًا للوكيل. ويُرجع run_id يمكن استخدامه للاشتراك في أحداث التقدّم.

تقبل عمليات التشغيل سلسلة input بسيطة، ويمكن اختياريًا إرسال session_id أو instructions أو conversation_history أو previous_response_id. وعند تقديم session_id، يُظهره Hermes في حالة التشغيل لتتمكن الواجهات الخارجية من ربط عمليات التشغيل بمعرّفات المحادثات الخاصة بها.

لجعل عملية الإنشاء آمنة لإعادة المحاولة، أرسل الترويسة Idempotency-Key (من 1 إلى 255 حرف ASCII مرئي). يحجز Hermes المفتاح بشكل دائم قبل بدء العمل. وتُرجع إعادة المحاولة المطابقة run_id الأصلي مع HTTP 202 و Idempotency-Replayed: true، حتى بعد إعادة تشغيل gateway وبعد اكتمال التشغيل أو فشله أو إلغائه. وإعادة استخدام المفتاح نفسه مع حمولة JSON مختلفة تُرجع HTTP 409 مع الرمز idempotency_key_conflict. تُعزل المفاتيح حسب profile/بيانات اعتماد API المصادَق عليها، وتُحفظ لمدة 24 ساعة بعد آخر تحديث لحالتها؛ لذا ينبغي للعملاء استخدام مفاتيح فريدة يصعب تخمينها، ويجب ألا يعيدوا استخدامها في عمليات غير ذات صلة. أما الطلبات التي لا تتضمن الترويسة فتحتفظ بالسلوك القديم وتنشئ دائمًا تشغيلًا جديدًا.

عندما يحدد session_id جلسة Hermes موجودة، ولا يُقدَّم conversation_history أو previous_response_id صريح، يحمّل التشغيل النص الكامل النشط لتلك الجلسة (transcript). وتعمل عقود إيجار أدوار الجلسة (session turn leases) على ترتيب الكتّاب المتزامنين تسلسليًا، وتحديث النص الكامل بعد انتظار ناتج عن التنافس.

GET /v1/runs/{run_id}

استطلع حالة التشغيل الحالية. وهذا مفيد للوحات التحكم التي تحتاج إلى الحالة دون إبقاء اتصال SSE مفتوحًا، أو للواجهات التي تعيد الاتصال بعد التنقل.

تُحفظ الحالات لفترة وجيزة بعد بلوغ الحالات النهائية (completed أو failed أو cancelled) لأغراض الاستطلاع ومزامنة الواجهة.

GET /v1/runs/{run_id}/events

بث Server-Sent Events لتقدّم استدعاءات الأدوات في التشغيل، وتغيّرات الـ tokens، وأحداث دورة الحياة. صُمّم للوحات التحكم وتطبيقات العميل الكاملة (thick clients) التي تريد الارتباط/الانفصال دون فقدان الحالة.

عندما يفوّض الوكيل العمل إلى subagents في الخلفية، يحمل البث أيضًا أحداث دورة الحياة subagent.start و subagent.complete، لكي يتمكن العملاء من مراقبة نتائج التفويض — بما في ذلك انتهاء المهلة والإخفاقات — بدلًا من صمت التشغيل بينما يعمل الوكيل الفرعي. وتحمل حمولة subagent.complete حالة الوكيل الفرعي، وملخّصه، ومدته، وأرقام الـ tokens/التكلفة، و child_session_id لأغراض الربط، و delegation_id الخاص بالدفعة التي ينتمي إليها (لتبقى عمليات التوزيع المتزامنة أو المتداخلة قابلة للتمييز)؛ وتخضع الحقول النصية الحرة لإخفاء إلزامي للأسرار قبل مغادرة العملية. أما أحداث الوكيل الفرعي الخاصة بكل أداة (subagent.tool، ونبضات التقدّم) فهي عمدًا لا تُمرَّر — لأنها ضجيج كثيف في الواجهة؛ استخدم ملفات النص الحي لكل وكيل فرعي لمتابعة التفاصيل خطوة بخطوة. هذه الأحداث متاحة ما دام بث الأصل مفتوحًا؛ وأي إكمال منفصل متأخر لا يعيد فتح بث SSE لتشغيل منتهٍ ولا يغيّر حالته النهائية.

النتائج المنفصلة وسجل الجلسة

يتطلب التفويض في الخلفية استئنافًا يقرأ سجل الجلسة على جانب الخادم: أي ترويسة X-Hermes-Session-Id صريحة في Chat Completions، أو طلب /api/sessions/{id}/chat أصلي، أو طلب Runs يستخدم سجل الجلسة. أما طلبات Chat Completions بلا ترويسة، وسلاسل Responses، وطلبات Runs التي تتضمن previous_response_id أو سجلًا يقدّمه المستدعي، فتنفّذ التفويض بشكل متزامن بدلًا من ذلك، وتُرجع النتيجة في الدور الأصلي. ومجرد اشتقاق معرّف جلسة من محتوى الطلب لا يُفعّل التسليم المنفصل.

في الطلبات القابلة للاستئناف، تُحفظ نتيجة الإكمال مرة واحدة لكل وحدة تفويض. وهي متاحة عبر GET /api/sessions/{id}/messages وفي سجل الجلسة للدور الفعلي التالي من العميل. ولا تُدرج إعادة المحاولة النتيجة نفسها مجددًا؛ أما إشعارات فشل المهام المؤقتة فلها هويات منفصلة. وينتظر التسليم ما دام دور العميل يملك عقد إيجار الجلسة، ويتبع عمليات الاستئناف الناتجة عن الضغط (compression). ويعيد Chat Completions معرّف الجلسة الصريح الذي قدّمته في كلٍّ من استجابات JSON واستجابات البث؛ لذا استمر في إرسال ذلك المعرّف حتى بعد الضغط.

لا تبدأ نتيجة الإكمال أبدًا دورًا للنموذج دون طلب، ولا تتجاوز تأكيدًا بشريًا معلّقًا. فالعميل هو من يملك الدور التالي. أما العملاء الذين يواصلون استخدام لقطات (snapshots) السجل الخاصة بهم فينبغي أن يستخدموا التفويض المتزامن بدلًا من توقّع دمج صف تسليم من جانب الخادم في تلك اللقطات.

تنتهي صلاحية مخازن الأحداث غير المستهلكة بعد خمس دقائق، حتى لا يتسبب عميل منفصل في تضخّم الذاكرة إلى ما لا نهاية. ولا ينتهي بذلك إلا حالة وسيلة النقل: فالتشغيل الذي لا يزال قيد التنفيذ يبقى مرئيًا لاستطلاع الحالة، والموافقة، والتحكم في الإيقاف، و احتساب التزامن إلى أن ينتهي عمل المنفّذ الخاص به فعليًا. ويواصل مشترك SSE المتصل استهلاك الأحداث بشكل طبيعي.

POST /v1/runs/{run_id}/stop

يقاطع دور وكيل قيد التشغيل. يُرجع الـ endpoint فورًا {"status": "stopping"} بينما يطلب Hermes من الوكيل النشط التوقف عند نقطة المقاطعة الآمنة التالية. ويبقى التشغيل مُتتبَّعًا بالحالة stopping إلى أن ينتهي العمل المدعوم بالمنفّذ، ثم يستقر على الحالة cancelled؛ فطلب الإيقاف لا يُخفي أبدًا عاملًا (worker) لا يزال قيد التشغيل.

POST /v1/runs/{run_id}/approval

يحسم موافقة معلّقة لتشغيل ينتظر قرارًا بشريًا (مثل استدعاء أداة يخضع لسياسة موافقة). يحمل جسم الطلب قرار الموافقة، ويُستأنف التشغيل بمجرد تسجيل القرار. ويُعلَن عن هذا الـ endpoint في /v1/capabilities على أنه الميزة run_approval، لكي تتمكن الواجهات الخارجية من اكتشاف الدعم قبل عرض طلب موافقة.

Jobs API (أعمال مجدولة في الخلفية)

يوفّر الخادم واجهة CRUD خفيفة للمهام (jobs) لإدارة عمليات تشغيل الوكيل المجدولة / العاملة في الخلفية من عميل بعيد. وجميع الـ endpoints محمية بمصادقة bearer نفسها.

GET /api/jobs

يسرد جميع المهام المجدولة.

POST /api/jobs

ينشئ مهمة مجدولة جديدة. يقبل جسم الطلب البنية نفسها التي يقبلها hermes cron — الـ prompt، والجدول الزمني، والمهارات، وتجاوز المزوّد، ووجهة التسليم.

GET /api/jobs/{job_id}

يجلب تعريف مهمة واحدة وحالة آخر تشغيل لها.

PATCH /api/jobs/{job_id}

يحدّث حقول مهمة موجودة (الـ prompt، والجدول الزمني، وغيرها). وتُدمج التحديثات الجزئية.

DELETE /api/jobs/{job_id}

يزيل مهمة. ويلغي أيضًا أي تشغيل جارٍ لها.

POST /api/jobs/{job_id}/pause

يوقف مهمة مؤقتًا دون حذفها. وتُعلَّق الطوابع الزمنية للتشغيل المجدول التالي حتى الاستئناف.

POST /api/jobs/{job_id}/resume

يستأنف مهمة أُوقفت مؤقتًا في السابق.

POST /api/jobs/{job_id}/run

يُطلق تشغيل المهمة فورًا، خارج جدولها الزمني.

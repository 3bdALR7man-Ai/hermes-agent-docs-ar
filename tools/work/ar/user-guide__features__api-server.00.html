خادم API

يوفّر خادم API وكيل hermes-agent على شكل HTTP endpoint متوافق مع OpenAI. ويمكن لأي واجهة أمامية (frontend) تتعامل بصيغة OpenAI — مثل Open WebUI و LobeChat و LibreChat و NextChat و ChatBox ومئات غيرها — الاتصال بـ hermes-agent واستخدامه كـ backend.

يعالج وكيلك الطلبات بمجموعة أدواته الكاملة (الطرفية، وعمليات الملفات، والبحث في الويب، والذاكرة، والمهارات) ثم يُرجع الاستجابة النهائية. وعند البث (streaming)، تظهر مؤشرات تقدّم الأدوات ضمن الاستجابة مباشرةً لتتمكن الواجهات الأمامية من عرض ما يفعله الوكيل.

backend واحد يغطي النماذج والأدوات

يحتاج Hermes نفسه إلى مزوّد مُعدّ وإلى backends للأدوات حتى يكون خادم API مفيدًا. ويتكفّل اشتراك Nous Portal بالأمرين معًا — أكثر من 300 نموذج إضافةً إلى الويب/الصور/TTS/المتصفح عبر Tool Gateway. نفّذ hermes setup --portal مرة واحدة قبل تشغيل خادم API، وستحصل الواجهات الأمامية مثل Open WebUI أو LobeChat على backend مجهّز بالأدوات بالكامل.

دلالات المحادثة والنتيجة النهائية

تستخدم طلبات API طابور القبول الدائم (durable admission queue) الخاص بالـ gateway. يبقى محتوى الصور المنظَّم منظَّمًا طوال التنفيذ؛ ولا يُفسَّر بوصفه slash command للـ gateway.

  • يحتفظ /v1/runs و /v1/responses بالمحادثة التي تعلنها الترويسة X-Hermes-Session-Key. وتكون الأسبقية لجلسة صريحة أو سلسلة استجابات صريحة، ولا تنقل إلى ترويسة مختلفة هوية محادثتها.
  • في /v1/runs، يكون conversation_history غير الفارغ هو المرجع الحاسم، حتى مع وجود session_id صريح. وإلا فإن استكمال الجلسة يحمّل السجل عند تنفيذ الدور، بعد انتهاء الأعمال المصطفّة قبله.
  • يتفق استطلاع Runs و SSE على الحالتين cancelled و failed. ويستخدم Responses الحالة النهائية نفسها والحدثين response.cancelled / response.failed، بما في ذلك عند وجود نص تشخيصي. ويُبلغ Chat Completions عن finish_reason: "cancelled" للأدوار المقاطَعة وعن "error" للإخفاقات، لا عن "stop" الناجح.
  • الدور (turn) الذي ينفد ميزانية تكراراته (agent.max_turns) يظل يجيب بخلاصة الوكيل لما وجده. يُسلّم Chat Completions هذا النص مع finish_reason: "length" و hermes.error_code: "iteration_budget_exhausted"؛ أما Responses فيُبلغ عن status: "incomplete". تعامل مع المحتوى بوصفه إجابة صالحة للاستخدام عن مهمة توقفت قبل اكتمالها، لا بوصفه إلغاءً.
  • تتضمن ردود محادثة الجلسة الحقل status؛ وتبلّغ تدفقاتها عن أحداث تشغيل نهائية مطابقة. وإطار إنهاء رد المساعد ليس بحد ذاته دليلًا على نجاح التنفيذ.

مفاتيح Idempotency

يقبل POST /v1/chat/completions و POST /v1/responses الترويسة Idempotency-Key. وما يضمنه المفتاح يعتمد على وضع التنفيذ:

  • الوضع المرجعي (Canonical mode) (يشغّل الـ gateway جهة صلاحية للجلسات session authority): المفتاح هوية قبول دائمة. يُقبل الطلب الأول الحامل له ويعمل مرة واحدة، ويظل المفتاح ملكًا لعملية القبول تلك من حينها. تنحصر المفاتيح في نطاق API profile وبيانات الاعتماد المصادَق عليهما، ولذلك فإن profile آخر أو API_SERVER_KEY مُدوَّر يعيد استخدام مفتاح العميل نفسه يُعدّ طلبًا جديدًا. ويصف بقية هذا القسم هذا الوضع.
  • الوضع القديم (Legacy mode) (بلا session authority): تُزال تكرارات الطلبات غير المتدفقة عبر cache في الذاكرة مدته 5 دقائق. أما الطلبات المتدفقة (streaming) فلا تُزال تكراراتها.

لمفاتيح /v1/runs سجلّها الخاص (ledger) واحتفاظ مدته 24 ساعة (انظر Runs API أدناه).

إعادات المحاولة المطابقة والتعارضات. تكون إعادة المحاولة مطابقة عندما تكرر المفتاح نفسه مع حقول الهوية نفسها والهدف المعلَن نفسه. أما تغيير أحد حقول الهوية، أو إرسال المفتاح إلى جلسة أخرى، فهو تعارض: يُرفض بالرمز admission_conflict ولا يُنفَّذ شيء. وتختلف طريقة وصول الرفض بحسب الطلب:

  • Responses (JSON أو متدفق) وChat Completions غير المتدفق: HTTP 409 مع رمز الخطأ admission_conflict.
  • Chat Completions المتدفق: يكون التدفق قد فُتح بالفعل بـ HTTP 200، لذا يأتي الرفض في آخر chunk فيه، مع finish_reason: "error" و error.message "admission_conflict"، يليه data: [DONE]. افحص ذلك الـ chunk لا رمز الحالة.

تختلف حقول الهوية باختلاف الـ endpoint:

  • Responses: input و instructions و previous_response_id و conversation و conversation_history و model و provider و model_options و tools، إضافة إلى truncation عند إرساله.
  • Chat Completions: آخر رسالة للمستخدم، والرسائل السابقة (ما لم تُرسَل X-Hermes-Session-Id، وفي هذه الحالة يأتي السجل من الجلسة)، و system prompt، وإعدادات الدور مثل النموذج والمزوّد المطلوبين و model_options. أما tools و tool_choice فليسا جزءًا منها: إعادة المحاولة التي تغيّر هذين فقط تعيد الرد الأصلي بدلًا من أن تُحدث تعارضًا.

وضع التسليم ليس جزءًا من الهوية في أي من الـ endpoint-ين: يجوز لإعادة المحاولة أن تبدّل بين JSON و stream: true وتحصل على الجواب نفسه بالصيغة المطلوبة.

الإعادة (replay) ومنع التكرار أمران منفصلان. تعيد إعادة المحاولة المطابقة الجواب الأصلي فقط ما دام الخادم يحتفظ بهوية الطلب الخاصة بالمفتاح مع سجل إعادته أو مع قبول نهائي يمكن إعادة بناء الجواب منه. وحين لا تعود الإعادة ممكنة، يظل المفتاح لا يعمل مجددًا ما بقي دليل قبوله: تُرفض إعادة المحاولة بوصفها تعارضًا ولا يُنفَّذ شيء. وقد تتلقى إعادة محاولة Responses بدلًا من ذلك HTTP 409 unknown_execution: يحتفظ المخزن بمطالبة المفتاح (مثلًا مطالبة سجّلها إصدار أقدم) لكن دون جواب، فلا يُعرف هل نُفّذت المحاولة الأولى. وهذا ليس إذنًا بإعادة إرسال العمل بمفتاح جديد؛ فقد تكون المحاولة الأولى نُفّذت بالفعل.

بعد حذف جلسة (DELETE /api/sessions/{id}) تُحفظ عمليات القبول الخاصة بها بوصفها شواهد (tombstones). وبعد سبعة أيام من الحذف تصبح مؤهلة للتقليم (pruning)؛ ولا تُزال إلا عند تشغيل تمريرة تقليم، وإلى ذلك الحين يتصرف المفتاح كما يلي.

  • Chat Completions: تعيد إعادة المحاولة المطابقة الجواب الأصلي دون إعادة إنشاء الجلسة، ويُرفض المفتاح المرسل إلى أي جلسة أخرى بوصفه تعارضًا. وبعد تقليم الشواهد يمكن للمفتاح أن يسمّي عملًا جديدًا على هدف جديد صالح.
  • Responses: تحتاج الإعادة أيضًا إلى أن يحتفظ مخزن الاستجابات بهوية المفتاح، ولذلك قد تنتهي قبل مرور الأيام السبعة: تُحفظ الهويات المستقرة بعدد محدود، ويزيل DELETE /v1/responses/{id} إحداها فورًا. المفتاح الذي زالت هويته يُجاب بـ 409 admission_conflict، حتى على جلسة حية. وحين تزول هويته وتُقلَّم شواهده، يمكن للمفتاح أن يسمّي عملًا جديدًا.
ملاحظة

يحتفظ مخزن الاستجابات افتراضيًا بآخر 1,000 هوية استقرّت لكل profile (10 لكل خانة استجابة مخزّنة). ولا تُحتسب الهويات المعلّقة أو الجارية ولا تُسقَط أبدًا، ويؤدي حذف استجابة إلى إزالة هويتها مبكرًا. وهذا افتراضي حالي وليس ضمانًا للإعادة.

لا يُعاد تعيين X-Hermes-Session-Id الصريح أبدًا. يظل معرّف الجلسة المحذوفة محجوبًا حتى بعد التقليم. وإعادة المحاولة المطابقة ذات المفتاح التي لا تزال هويتها محفوظة هناك تُعاد، أما المتغيّرة فتُرفض بوصفها تعارضًا. والطلب الذي لا هوية محفوظة له هناك، مثل طلب جديد أو إعادة محاولة قُلّمت هويتها، يُرفض بالرمز not_found.

يشتق طلب Chat Completions بلا X-Hermes-Session-Id جلسته من system prompt ورسالة المستخدم الأولى. ولا يُعاد استخدام معرّف جلسة محذوفة أبدًا، لذلك تحصل محادثة جديدة تبدأ مثل محادثة محذوفة على جلسة جديدة، وتستقر أدوارها اللاحقة على تلك الجلسة نفسها، بما في ذلك بعد إعادة التشغيل. أما إعادة المحاولة المطابقة ذات المفتاح لدور من المحادثة المحذوفة فلا تُنقل؛ وتُعاد كما هو موصوف أعلاه.

تصدر جميع تدفقات SSE (Chat Completions و Responses و /api/sessions/{id}/chat/stream و /v1/runs/{id}/events) سطر تعليق : keepalive كلما لم يُرسل حدث لمدة 10 ثوانٍ، كي لا تؤدي استدعاءات الأدوات الطويلة إلى انتهاء مهلة خمول العميل. تتجاهل عملاء SSE القياسية أسطر التعليقات؛ ويجب على المحلّلات المخصّصة تخطّي الأسطر التي تبدأ بـ :.

تقدّم الأدوات أثناء البث:

  • Chat Completions: يُصدر Hermes الحدث event: hermes.tool.progress لإظهار بدء الأدوات دون تلويث نص المساعد المحفوظ. يمكن لعملاء OpenAI الصارمة التي لا تقبل أحداث SSE المسمّاة تعطيل هذه الأُطر باستخدام gateway.platforms.api_server.tool_progress_events: false (القيمة الافتراضية true)؛ ولا تتأثر أجزاء المحتوى. ينطبق التعطيل على Chat Completions فقط — يُصدر /v1/runs/{id}/events أحداث الأدوات دائمًا، وهو ما تصفه ميزة tool_progress_events في /v1/capabilities.
  • Responses: يُصدر Hermes عناصر مُخرَجات function_call و function_call_output الأصلية للمواصفة أثناء تدفق SSE، ليتمكن العملاء من عرض واجهة أدوات منظّمة في الوقت الفعلي.

استدلال النموذج (لا يُصدر إلا عندما ينتج النموذج استدلالًا فعليًا وتسمح به إعدادات reasoning المحددة؛ وخيار تعطيله من المدخلات هو model_options.reasoning.enabled: false):

  • Chat Completions: تصل تغيّرات الاستدلال كأجزاء choices[0].delta.reasoning_content (الحقل بأسلوب DeepSeek الذي يعرضه Open WebUI و opencode و Vercel AI SDK ككتلة تفكير)؛ ويبقى نص الإجابة في delta.content.
  • Responses: كل دفعة تفكير عنصر مخرج reasoning أصلي للمواصفة — response.output_item.added (item.type: "reasoning")، response.reasoning_summary_part.added، response.reasoning_summary_text.delta … response.reasoning_summary_text.done، response.reasoning_summary_part.done، response.output_item.done — يُغلق قبل فتح الرسالة التالية أو عنصر function_call، ويُكرر في مخرج response.completed بصيغة {"id": "rs_…", "type": "reasoning", "status": "completed", "summary": [{"type": "summary_text", "text": "…"}]}. يظل sequence_number متزايدًا رتيبًا عبر أحداث الاستدلال والنص والأدوات.
  • دون بث: /v1/chat/completions يُرجع استدلال الدور في choices[0].message.reasoning_content؛ و /v1/responses يُرجع عناصر مخرج reasoning نفسها قبل الرسالة (وقبل عناصر function_call الخاصة بتلك الخطوة)، وكذلك عند إعادة عرض GET /v1/responses/{id}.
  • يمكن إعادة إرسال قائمة output لاستجابة سابقة بوصفها input التالية (ما تفعله عملاء Responses SDK): تُتجاهل عناصر reasoning عند الإدخال بدلًا من تحليلها كأدوار مستخدم فارغة.
  • يُعلن الدعم بوصفه features.reasoning_streaming: true في GET /v1/capabilities.

GET /v1/models

يسرد الوكيل كنموذج متاح. ويكون اسم النموذج المُعلَن افتراضيًا هو اسم الـ profile (أو hermes-agent للـ profile الافتراضي). تحتاج إليه معظم الواجهات الأمامية لاكتشاف النماذج.

/v1/models هو عمدًا الواجهة الخفيفة المتوافقة مع OpenAI. فهو لا يسرد كل تركيبات المزوّد/النموذج المصادَق عليها التي يمكن لـ Hermes التوجيه إليها، ولا يُثري النتائج بمعلومات الأسعار أو القدرات.

GET /api/model/options

يمكن للعملاء المُدركين لخصائص Hermes طلب قائمة المزوّدين/النماذج المنتقاة نفسها التي تستخدمها لوحة التحكم و TUI. يستخدم هذا المسار مصادقة bearer المعتادة في خادم API، ويُرجع صفوف المزوّدين، وتلميحات حول قدرات النماذج، وبيانات وصفية للأسعار لا مكان لها في استجابة /v1/models المتوافقة مع OpenAI:

هذه البيانات هي الأساس نفسه الذي تعتمد عليه صفحة Models في لوحة التحكم واستدعاء RPC المسمّى model.options في TUI. فهي تُرجع المزوّدين المصادَق عليهم، وقوائم النماذج المنتقاة، وأسعار كل نموذج، وتلميحات حول قدرات النماذج.

الفتح العادي متحفّظ عمدًا مع المزوّدين المخصّصين: إذ لا يفحص Hermes إلا الـ endpoint المخصص المحدَّد حاليًا، حتى لا يعطّل endpoint محفوظ قديم أو غير متصل المنتقي. أما التحديث الصريح فينتقل إلى الفحص الكامل ويُفرغ التخزين المؤقت لنماذج المزوّد:

استخدم /v1/models عندما يحتاج عميل متوافق مع OpenAI إلى اسم نموذج فقط لإرساله في طلبات chat/responses. واستخدم /api/model/options عندما تحتاج واجهة مصادَق عليها إلى البيانات الوصفية الأغنى الخاصة بمنتقي Hermes.

GET /v1/capabilities

يُرجع وصفًا قابلًا للقراءة آليًا للواجهة المستقرة التي يوفّرها خادم API، وذلك للواجهات الخارجية ومنظِّمات التشغيل (orchestrators) وجسور الإضافات.

استخدم هذا الـ endpoint عند دمج لوحات التحكم أو واجهات المتصفح أو مستويات التحكم (control planes)، لكي تكتشف ما إذا كان إصدار Hermes العامل يدعم runs والبث والإلغاء واستمرارية الجلسة، دون الاعتماد على تفاصيل Python الداخلية الخاصة.

التحكم عبر إضافة المتصفح (أُزيل)

أُزيل بروتوكول وحدة التحكم في إضافة المتصفح (POST /v1/browser-control/register، وGET /v1/browser-control/ws، ومسارات /v1/artifacts/*، واستدعاءات RPC في لوحة التحكم browser.controller.*، ومفتاح الإعدادات browser.extension_control). كان يوجّه الأدوات القديمة browser_navigate/browser_click/…، وهي لم تعد موجودة: أصبحت أتمتة المتصفح الآن عبر browser_exec فوق CDP. ولكي يتحكم Hermes في متصفح تشغّله بالفعل، وجّهه إلى endpoint الخاص بـ DevTools في ذلك المتصفح عبر browser.cdp_url في config.yaml أو /browser connect — راجع Your own browser via CDP. تؤدي الترقية إلى حذف كتلة browser.extension_control المتبقية من config.yaml.

اختيار النموذج لكل طلب

يمكن للعملاء المصادَق عليهم تجاوز اختيار النموذج الافتراضي في Hermes لكل طلب على حدة بإرسال:

  • model — معرّف النموذج المستهدف لهذا الدور
  • provider — المعرّف المختصر (slug) لمزوّد Hermes لتحديد بيانات الاعتماد/بيئة التشغيل لهذا الدور
  • model_options — عناصر تحكم الاستدلال (reasoning) / فئة الخدمة (service tier) الخاصة بهذا الطلب فقط

تُقبل حقول الطلب نفسها على:

  • POST /v1/chat/completions
  • POST /v1/responses
  • POST /v1/runs
  • POST /api/sessions/{session_id}/chat
  • POST /api/sessions/{session_id}/chat/stream

ترتيب الأولوية حتمي:

  1. تجاوز /model على مستوى الجلسة، إن كان للجلسة تجاوز بالفعل
  2. ربط ثابت في gateway.platforms.api_server.model_routes يُختار عندما تكون قيمة model في الطلب اسمًا مستعارًا لمسار مُعدّ
  3. قيمتا model / provider المباشرتان في الطلب عندما لا يتطابق أي اسم مستعار لمسار
  4. الإعدادات العامة لـ gateway / القيم الافتراضية من البيئة

model_options يظل خاصًا بالطلب بغض النظر عن النموذج/المزوّد الذي يُعتمد. إذا أرسل طلب provider يتعارض مع اسم مستعار مضبوط في model_routes، يرفض Hermes الطلب مع 400 بدلًا من خلط بيانات اعتماد المسار بمزوّد آخر بصمت.

قيم model المجرّدة على endpoints المتوافقة مع OpenAI تتطلب تفعيلًا صريحًا. فعملاء OpenAI العامّون كثيرًا ما يثبّتون أسماء النماذج في الكود (gpt-4o، ...)، وتعتمد عمليات النشر القائمة على عودة هذه القيم إلى النموذج الافتراضي في gateway. لذلك، على POST /v1/chat/completions و POST /v1/responses، تُتجاهل قيمة model المُرسلة دون أي provider ما لم تفعّل:

أما الطلبات التي تتضمن provider صريحًا — وكذلك endpoints الأصلية في Hermes مثل /v1/runs و endpoints محادثة الجلسات — فتلتزم دائمًا بالنموذج المطلوب بغض النظر عن هذا الخيار.

مثال:

GET /health

فحص السلامة (health check). يُرجع {"status": "ok"}. ومتاح أيضًا على GET /v1/health لعملاء OpenAI المتوافقين الذين يتوقعون البادئة /v1/.

GET /health/detailed

فحص جاهزية مصادَق عليه لأنظمة المراقبة ومستويات التحكم. يعرض حالة موجزة لإعدادات الـ profile النشط، وقاعدة بيانات الحالة، والنموذج المُعدّ، ومساحة القرص، وحالة gateway/المنصات، وعمليات API الجارية، وعمليات إكمال العمليات المعلّقة، والتفويضات النشطة. وتكشف الاستجابة عن الحالة والأعداد فقط، لا عن قيم الإعدادات أو بيانات الاعتماد أو المسارات أو الأوامر أو حمولات قوائم الانتظار أو الأخطاء الخام.

يبقى المسار العام /health فحصًا خفيفًا لبقاء الخدمة حيّة (liveness) ولا يُجري فحوص الجاهزية. ونتيجة الجاهزية المتدهورة لا تزال تستخدم HTTP 200؛ لذا افحص الحقلين status و readiness.checks في المستوى الأعلى.

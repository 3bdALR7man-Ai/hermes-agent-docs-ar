منصات المنفذ الوارد تحت المضاعِف

يربط hermes -p coder gateway run المستقل خوادم webhook الخاصة بـ Twilio و LINE و Teams... التابعة لـ coder على منافذها الخاصة. تحت المضاعِف، تظل تلك المحوّلات تابعة لـ coder — بنفس بيانات الاعتماد من profiles/coder/.env، ونفس config.yaml، وتُرسَل الردود عبر قناة coder — لكنها لا تربط أي منفذ. يمرّر مستمِع الـ profile الافتراضي المشترك /p/coder/<path> إليها، حيث <path> هو المسار نفسه الذي يخدمه المحوّل بشكل مستقل. يتحقَّق من الطلب محوّل الخاص بـ coder بسر الخاص بـ coder (رمز مصادقة Twilio ، أو سر قناة LINE ، أو بيانات اعتماد تطبيق Teams ، أو كلمة مرور BlueBubbles ، ...) ويعمل ضمن نطاق تشغيل coder ؛ ويبقى /path الخاص بالـ profile الافتراضي نفسه سليمًا، ويحصل profile ليس لديه محوّل لمسار ما على 404، وليس أبدًا بوت profile آخر.

ويكرّره كل سطح حالة، حتى تعرف ما تلصقه في لوحة تحكم البائع (vendor console):

hermes gateway status وhermes status على الـ profile الافتراضي الروابط نفسها لكل profile مخدوم، وتُظهرها صفحة Channels في لوحة التحكم وصفحة Messaging في Desktop باسم ingress_url الخاص بكل منصة عند عرض ذلك الـ profile. يُبلَّغ عن api_server وwebhook الخاصَين بالـ profile الافتراضي بالطريقة نفسها لـ profile مخدوم — بصفتهما متصلَين (connected) بـ ingress_url http://127.0.0.1:8642/p/coder/v1 (وعلى التوالي .../p/coder/webhooks/<route>) — لأن الـ profile ليس له محوّل خاص بهما؛ إنه مستمِع الافتراضي الذي يجيب تحت بادئة /p/coder/. يُتجاهَل SMS_WEBHOOK_PORT, LINE_PORT, TEAMS_PORT... الخاص بالثانوي في ملف .env تحت المضاعِف (لا شيء يربط منفذًا)؛ ويعود تطبيقه فور تشغيل ذلك الـ profile gateway مستقلة خاصة به.

3. لا تزال المنصات القائمة على بيانات الاعتماد بحاجة إلى رمز خاص بكل profile

تعمل منصات الاستطلاع/الاتصال (Telegram و Discord و Slack و Matrix و Signal ، ...) جيدًا تحت الـ multiplexing ، لكن كل profile يفعّل واحدة منها يجب أن يزوّد رمز بوت خاصًا به — فلا يمكن استطلاع الرمز نفسه من قِبل profile ين في آن واحد. إذا أعدّ profile ان (platform, token) نفسه، تسجّل الـ gateway خطأ يسمّي كلا الـ profile ين وتُوقِف جانبًا المحوّل المكرَّر (يظهر كـ fatal / duplicate_credential في حالة التشغيل) بينما يظل المُطالِب الأول وكل profile آخر يعملان — لا تخرج الـ gateway نفسها. تتصل محوّلات الـ profile الافتراضي أولًا وتطالب ببيانات اعتمادها، لذا فإن المحوّل الموقَف جانبًا هو دائمًا محوّل الثانوي (راجع أمان تعارض الرموز — القاعدة لم تتغيّر، إنها فقط تُطبَّق داخل العملية الواحدة الآن).

4. مفاتيح الجلسات موزَّعة على نطاقات (namespaced) حسب الـ profile

تعيش جلسات كل profile ضمن نطاق اسم agent:<profile>:… بحيث لا يتصادم profile ان على المنصة/المحادثة نفسها أبدًا في مخزن الجلسات المشترك. يحافظ الـ profile الافتراضي على نطاق الاسم التاريخي agent:main:… حرفيًا، لذا لا تتأثر جلسات الـ profile الافتراضي القائمة — لا ترحيل، ولا سجل يتيم. يقبل كل مسار gateway يقرأ مفتاحًا سابقًا — اكتمالات التفويض بعد إعادة التشغيل، وإشعارات الإيقاف، و/stop خاصًا بمحادثة مستخدم فردية لتشغيل تابع، و/undo، وأزرار موافقة QQ — شكل agent:<profile>:… أيضًا، فتحصل الـ profiles الثانوية على سلوك الـ profile الافتراضي نفسه. واسم الـ profile الوحيد الذي يتعارض مع نطاق أسماء الافتراضي، أي profile اسمه حرفيًا main، يُستخدم له المفتاح agent:main~:… كي يحتفظ بجلساته الخاصة و profiles/main/state.db.

تحطّ صفوف كل profile في ملفه الخاص state.db: صفوف profile مسمّى تحت profiles/<name>/state.db، وصفوف الـ profile الافتراضي تحت منزل الإطلاق — حتى عندما تحدث الكتابة داخل دور موجَّه أو نبضة خلفية (tick) تابعة لـ profile آخر. يظل مخزن backend الخاص بـ Desktop/TUI مثبَّتًا على المنزل الذي أُطلق تحته، وتُحفَظ وكلاء Bot Chat الفرعيون (prompt.background) بجانب محادثتهم الأصل.

5. PID/قفل واحد وسطح حالة واحد

يوجد PID وقفل واحد على مستوى العملية (المضاعِف، تحت منزل الافتراضي). يبلّغ hermes status --full على الـ profile الافتراضي عن المضاعِف ويسرد الـ profiles التي يخدمها (Serves: coder, research). hermes -p coder status وhermes -p coder gateway status جميعًا "running via the default-profile multiplexer" بدلًا من "stopped"، وتبلّغ صفحة /api/status?profile=coder / Channels في لوحة التحكم عن المضاعِف باعتباره gateway coder العاملة (مع محوّلات coder الخاصة بصفتها منصاته). يعيش gateway_state.json الواحد تحت المنزل الافتراضي: تظهر المحوّلات الثانوية هناك كإدخالات <profile>:<platform> بجانب served_profiles؛ ولا يُكتب ملف حالة gateway لكل profile.

hermes -p coder cron status يسمي gateway المضيف الوحيد والـ profiles التي يخدمها — Scheduler host: the host gateway (PID 4211) serving profiles default, coder — ثم يفحص نبضة ticker الخاصة بـ coder وآخر tick ناجح. وتنتج النبضة الغائبة أو القديمة تحذيرًا بدل حكم غير مشروط بأنه يعمل. ويحذر cron list و cron create أيضًا عند غياب نبضة حديثة لـ profile مخدوم. ويضيف cron status تفاصيل إخفاق tick التي لا تقرؤها تلك الفحوص الخفيفة.

عندما لا يملك أي gateway دور المضيف، يخبرك cron status بأن تبدأ gateway المضيف الوحيد (hermes --profile default gateway install / gateway run) وتتأكد من أنه يخدم هذا الـ profile. ولا يُعرض تثبيت خدمة لكل profile إلا تحت LEGACY (pre-multiplex topology, not recommended): إذ سيبدأ عملية gateway ثانية على المضيف. ويتبع hermes doctor القاعدة نفسها — ففي s6 يعرض Host gateway: the host gateway (PID 4211) serving profiles default, coder بدل عدد slots لكل profile ، ويعلّم أي slot لكل profile لا يزال خاضعًا للإشراف بـ LEGACY ، ويفحص linger لوحدة systemd للمضيف حتى عند تشغيل doctor من profile مخدوم. والـ state.db تذكر أسطر الجهات التي تفتح قاعدة البيانات عملية المضيف المشتركة أيضًا، فتحدد "3 process(es) holding the DB open" أي gateway وأي profiles ستتأثر بإيقافه.

ما الذي لا يتغيّر

يبقى عزل بيانات اعتماد .env محفوظًا، بل أشد صرامة إن كان هناك اختلاف: تُحدد مفاتيح الـ profile من نطاقه الخاص ولا تُدمج مطلقًا في بيئة مشتركة. ولا ترى العمليات الفرعية مثل خوادم MCP وعمّال Kanban إلا أسرار الـ profile الخاص بها — بما فيها بيانات الاعتماد المحقونة من مصدر أسرار خارجي (1Password ، و Bitwarden ، …): يتلقى خادم stdio MCP الذي يبدأ للـ profile B قيمة B لذلك الاسم، أو لا شيء إن لم يملك B قيمة، ولا يتلقى قيمة الـ profile الافتراضي مطلقًا. وتُوصل خوادم MCP لكل profile على حدة: يحصل profile ان يسمّيان خادمًا بـ github بـ token خاص بكل منهما على اتصالين، ويرى كل منهما أدواته وحدها؛ والـ profiles التي يكون إدخال mcp_servers الخاص بها متطابقًا (المسار نفسه و بيانات الاعتماد، بما في ذلك mTLS client_cert/client_key) تشترك في اتصال واحد، ويعيد /reload-mcp لدى المالك تسجيل أدوات الـ profiles المشاركة دون إعادة تحميلها. ولا تُشارك خوادم auth: oauth بين profiles مطلقًا: يحتفظ كل profile بـ token الخاص به تحت mcp-tokens/ الخاص به ويفتح اتصاله الخاص. ويوصل بدء التشغيل الـ profiles واحدًا بعد آخر، وداخل profile الواحد لا يزيد عدد الخوادم المتصلة معًا عن mcp.discovery_concurrency (الافتراضي 4، و 0 = غير محدود)، فلا تعود مجموعة profiles ذات خوادم stdio كثيرة تُنشئ كل العمليات المساعدة في اللحظة نفسها. وتبقى سياسة الثقة لكل profile: فما زال profile trust: untrusted الذي يشارك اتصال profile trust: full يُسأل قبل كل استدعاء قادر على الكتابة، و supports_parallel_tool_calls لا ينطبق إلا على الـ profile الذي ضبطه. وتُحدَّد إعدادات الطرفية (terminal.backend, terminal.cwd, terminal.docker_volumes, terminal.docker_shared_container_key، أهداف SSH ، ...) كذلك لكل profile في كل دور موجَّه: يحصل profile يغفل مفتاح طرفية على الافتراضي الموثّق، لا قيمة profile الإطلاق أبدًا، ويُرفَض تنفيذ الطرفية لـ profile يتعذّر تحليل config.yaml/.env الخاص به بدلًا من تشغيله تحت سياسة sandbox لـ profile آخر. يغطّي حارس بيانات اعتماد تسليم الوسائط (قائمة الحظر خلف مرفقات MEDIA: المرفقات — .env, auth.json, config.yaml, state.db، ونصوص الجلسات، ومخازن رموز OAuth) كل profile تحت profiles/، بحيث لا يستطيع دور أي profile إرفاق أسرار أو سجل محادثات profile آخر في رد. التفويض أيضًا لكل profile: تُقرأ GATEWAY_ALLOW_ALL_USERS, GATEWAY_ALLOWED_USERS وكل قائمة سماح منصة أو خيار السماح للجميع من .env الخاص بالـ profile المالك — لا يفتح انضمام الـ profile الافتراضي إلى وصول مفتوح أبدًا بوت profile ثانوي، ويُحترَم انضمام ثانوي في .env الخاص به فقط. الأمر نفسه ينطبق على السلوك الخاص بكل بوت المكتوب في config.yaml (require_mention, mention_patterns, allow_bots, reactions, auto_thread, free_response_auto_thread, dm_policy, ignored_channels، و Matrix session_scope الخاصة بـ Matrix ، ...): لا يحطّ YAML لـ profile ثانوي أبدًا في بيئة العملية المشتركة، لذا لا يمكن أن يصبح سياسة الـ profile الافتراضي، ولا يحكم YAML الخاص بالـ profile الافتراضي بوتًا ثانويًا أبدًا. تُحلّ كذلك لكل profile قائمة السماح terminal.env_passthrough، وقناة المنزل المخصَّصة تلقائيًا لـ Yuanbao ، وحرّاس الكتابة الحامية لملف config.yaml الخاص بكل profile. يتصرف Kanban ، والمهارات/الذاكرة/SOUL المحدَّدة النطاق لكل profile ، وتوجيه النموذج جميعًا لكل profile تمامًا كما تتصرف مع gateways منفصلة.

الهوية الصادرة أيضًا لكل profile. يرسل الدور العامل من أجل الـ profile P والذي يستدعي أداة send_message (إرسال، وتفاعل، ووسائط) عبر بوت P الخاص؛ وكذلك إشعارات "Gateway shutting down/restarted" و/update لجلسات P، وتنبيهات /loop المضبوطة من محادثات P، وتنبيه المشغِّل غير المصرَّح به لأمر Discord المائل (slash) الخاص ببوت Discord لـ P باستخدام بوت Discord الخاص به (إلى P). وإذا لم يكن لدى P بوت متصل لتلك المنصة، يفشل الإرسال برسالة خطأ واضحة — ولا يعود أبدًا إلى بوت الـ profile الافتراضي.

تتبع بيانات اعتماد الأدوات ومزوّدي الذاكرة القاعدة نفسها. يُقرأ OCR المستضاف (FIRECRAWL_API_KEY)، وبوابات Modal / Browser Use السحابية، ومفتاح OpenAI الخاص بـ mem0 OSS ، وفيديو xAI ، وكل هوية مزوّد ذاكرة (MEM0_USER_ID, SUPERMEMORY_CONTAINER_TAG, RETAINDB_PROJECT, OPENVIKING_ACCOUNT/USER, HINDSIGHT_BANK_ID, HERMES_HONCHO_HOST) تُقرأ من .env، لذا تستقر ذاكرة profile ثانوي في خاص به account/bank/project الخاص به (أو القيمة الافتراضية لكل profile لدى المزوّد)، لا في الخاص بالـ profile الافتراضي مطلقًا. وتنتقل endpoints المخصصة مع مفاتيحها — OPENAI_BASE_URL, XAI_BASE_URL, NOUS_INFERENCE_BASE_URL, GATEWAY_PROXY_URL، وروابط Firecrawl / Browserbase / RetainDB / Supermemory / Honcho / Hindsight — بحيث لا يُرسَل مفتاح profile أبدًا إلى proxy أو خادم مستضاف ذاتيًا خاص بـ profile آخر. تكون WEIXIN_HOME_CHANNEL, HERMES_LANGUAGE، وdisplay.language، و hooks.outbound[].secret_env كذلك لكل profile ، ويعمل استخلاص الذاكرة عند نهاية الجلسة لجلسة ثانوية أُخليت (evicted) ضمن نطاق ذلك الـ profile.

تتبع إعدادات وقت التشغيل لكل دور الـ profile الموجَّه إليه أيضًا: agent.max_turns, fallback_providers, file_read_max_chars, tool_output.*, browser.*، وtimezone (بما في ذلك TZ المُسلَّم لـ sandboxes الخاصة بـ execute_code sandboxes)، وسياسة تسليم الوسائط (gateway.strict, media_delivery_allow_dirs, trust_recent_files*)، وملف Nous auth.json المستخدَم للنداءات المساعِدة — كلها تُقرأ من الـ profile الذي يخدم الدور، وليس أبدًا من الـ profile الذي أُطلقت تحته الـ gateway. الأمر نفسه ينطبق على ملفات حالة كل profile (processes.json, checkpoints/، ومخازن لقطة sandbox ، وقواعد تعليقات/اقتران Feishu) وعلى hooks الـ gateway: يُحمَّل دليل hooks/ لكل profile على حدة، ويُفعّل فقط لأحداث ذلك الـ profile. وتعمل shell hooks مع HERMES_HOME الخاص بالـ profile الموجَّه إليه، دون أسرار الـ profile الافتراضي في بيئتها، وتحمل حمولة stdin الخاصة بها حقل profile يسمّي الـ profile الذي أطلقها.

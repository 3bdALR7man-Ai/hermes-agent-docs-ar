hermes cron

الأمر الفرعيالوصف
listعرض المهام المجدولة.
create / addإنشاء مهمة مجدولة من نص prompt، مع إمكانية إرفاق مهارة واحدة أو أكثر عبر تكرار --skill. يدعم تثبيت مستوى تفكير لكل مهمة عبر --reasoning-effort <none|minimal|low|medium|high|xhigh|max|ultra>.
editتحديث جدول مهمة أو نص الـ prompt الخاص بها أو اسمها أو طريقة التسليم أو عدد التكرارات أو المهارات المرفقة. يدعم --clear-skills و--add-skill و--remove-skill، إضافةً إلى --reasoning-effort (تمرير سلسلة فارغة يزيل التثبيت).
pauseإيقاف مهمة مؤقتًا دون حذفها.
resumeاستئناف مهمة متوقفة مؤقتًا. يظل الموعد المتكرر الذي استحق أثناء التوقف مستحقًا (تشغيل تعويضي واحد أو تخطٍّ مسجّل في التكة التالية)؛ وإلا يُحسب موعد التشغيل المستقبلي التالي.
runتشغيل مهمة عند دورة الجدولة القادمة.
removeحذف مهمة مجدولة.
statusالتحقق من تشغيل مجدول Cron.
doctorفحص صحة الأسطول للقراءة فقط: التشغيلات الفاشلة، عمليات التسليم الفاشلة، قيمة next_run_at المتأخرة أو المفقودة، السكربتات أو مجلدات العمل المفقودة. يخرج برمز غير صفري عند وجود مشكلات.
tickتشغيل المهام المستحقة مرة واحدة ثم الخروج.

المشغّل (trigger) لـ cron قابل للتوصيل عبر مفتاح الإعدادات cron.provider. الفارغ (الافتراضي) يستخدم المؤقت المدمج الذي يعمل داخل العملية نفسها. اضبطه على chronos (المزوّد المُدار من NAS للـ gateways المستضافة بنمط scale-to-zero) — يُعدّ عبر مفاتيح cron.chronos.* (portal_url وcallback_url وexpected_audience و nas_jwks_url) — أو حدّد مزوّدًا مخصصًا تحت plugins/cron/<name>/ أو $HERMES_HOME/plugins/<name>/. أي مزوّد غير معروف أو غير متاح يرجع إلى المزوّد المدمج، بحيث لا يبقى cron بلا مشغّل أبدًا. راجع مستند آلية عمل Cron من الداخل.

hermes kanban

لوحة تعاون متعددة الـ profiles ومتعددة المشاريع. يمكن لكل تثبيت استضافة عدة لوحات (واحدة لكل مشروع أو مستودع أو نطاق)؛ كل لوحة هي قائمة انتظار مستقلة لها قاعدة بيانات SQLite ونطاق موزّع (dispatcher) خاصين بها. تبدأ التثبيتات الجديدة بلوحة واحدة تُسمى default، وقاعدة بياناتها هي ~/.hermes/kanban.db للتوافق الخلفي؛ أما اللوحات الإضافية فتوجد في ~/.hermes/kanban/boards/<slug>/kanban.db. يفحص الموزّع (dispatcher) المدمج في الـ gateway كل لوحة في كل دورة.

خيارات عامة (تنطبق على كل إجراء أدناه):

الخيارالغرض
--board <slug>العمل على لوحة محددة. الافتراضي هو اللوحة الحالية (تُضبط عبر hermes kanban boards switch، أو متغير البيئة HERMES_KANBAN_BOARD، أو default).

هذه هي الواجهة المخصصة للبشر / السكربتة. عمّال الوكيل (agent workers) الذين يُنشئهم الموزّع يتعاملون مع اللوحة عبر kanban_* toolset مخصص (kanban_show وkanban_complete وkanban_request_review وkanban_request_changes وkanban_block وkanban_create وkanban_link وkanban_comment وkanban_heartbeat؛ وتحصل profiles المنسّق أيضًا على kanban_list وkanban_unblock) بدلًا من استدعاء hermes kanban عبر الـ shell. العمّال يملكون HERMES_KANBAN_BOARD مثبّتًا في بيئتهم بحيث لا يمكنهم فعليًا رؤية لوحات أخرى.

الإجراءالغرض
initإنشاء kanban.db إن لم تكن موجودة. لا يُحدث تأثيرًا إضافيًا عند التكرار (idempotent).
boards list / boards lsسرد كل اللوحات مع عدد المهام. --json، --all (شمول اللوحات المؤرشفة).
boards create <slug>إنشاء لوحة جديدة. الخيارات: --name، --description، --icon، --color، --switch (جعلها النشطة). الـ slug بصيغة kebab-case، ويُحوَّل تلقائيًا لحروف صغيرة.
boards switch <slug> / boards useحفظ <slug> كاللوحة النشطة (يكتب في ~/.hermes/kanban/current).
boards show / boards currentطباعة اسم اللوحة النشطة حاليًا ومسار قاعدة بياناتها وعدد مهامها.
boards rename <slug> "<name>"تغيير الاسم المعروض للوحة. الـ slug ثابت لا يتغير.
boards rm <slug>أرشفة اللوحة (الافتراضي) أو حذفها نهائيًا. --delete يتخطى خطوة الأرشفة. اللوحات المؤرشفة تنتقل إلى boards/_archived/<slug>-<ts>/. يُرفض للوحة default.
create "<title>"إنشاء مهمة جديدة على اللوحة النشطة. الخيارات: --body، --assignee، --parent (قابل للتكرار)، --workspace scratch|worktree|dir:<path>، --tenant، --priority، --triage، --idempotency-key، --max-runtime، --max-retries، --skill (قابل للتكرار).
list / lsسرد مهام اللوحة النشطة. تصفية بواسطة --mine، --assignee، --status، --tenant، --archived، --json.
show <id>عرض مهمة مع تعليقاتها وأحداثها. --json لمخرجات قابلة للمعالجة آليًا.
assign <id> <profile>تعيين أو إعادة تعيين المهمة. استخدم none لإلغاء التعيين. يُرفض أثناء تشغيل المهمة.
link <parent> <child>إضافة اعتمادية. يُكتشف التسلسل الدائري (cycle). يجب أن تكون المهمتان على نفس اللوحة.
unlink <parent> <child>إزالة اعتمادية.
claim <id>حجز مهمة جاهزة بشكل ذري. يطبع مسار مساحة العمل المُحلَّل.
comment <id> "<text>"إضافة تعليق. العامل التالي الذي يحجز المهمة يقرأه كجزء من استجابة kanban_show() الخاصة به.
complete <id>وضع علامة أن المهمة منجزة. الخيارات: --result، --summary، --metadata.
block <id> "<reason>"وضع علامة أن المهمة معلّقة بانتظار تدخل بشري. كما يضيف السبب كتعليق.
request-review <id>نقل مهمة إلى review مع تسليم إلى مراجِع — وهذا ليس تعليقًا (block). الخيارات: --summary، --metadata، --reviewer (يعيد التعيين قبل إرسال المراجعة).
request-changes <id> <reason>قرار المراجِع لتشغيل مراجعة نشط: إغلاق محاولة المراجعة وإعادة توجيه المهمة إلى منفّذها الأصلي.
reopen-review <id>...إعادة مهمة (أو أكثر) قيد المراجعة لإجراء تعديلات (review → ready/todo). الخيار: --reason (يُضاف كتعليق).
schedule <id> "<reason>"إيقاف عمل مؤجّل/متابعة في حالة scheduled بحيث لا يظهر كعائق بشري.
unblock <id>استعادة مهمة معلّقة إلى مرحلتها المصدر (review أو ready)، أو إلى todo إن بقيت الاعتماديات مفتوحة.
archive <id>إخفاء المهمة من القائمة الافتراضية. الأمر gc سيزيل مساحات العمل المؤقتة.
tail <id>متابعة تدفق أحداث مهمة.
dispatchتمريرة موزّع واحدة على اللوحة النشطة. الخيارات: --dry-run، --max N، --failure-limit N، --json.
context <id>طباعة السياق الكامل الذي سيراه العامل (العنوان + المتن + نتائج المهام الأصل + التعليقات).
specify <id> / specify --allتحويل مهمة في عمود الفرز (triage) إلى مواصفة محددة (عنوان + متن يتضمن الهدف والنهج ومعايير القبول) عبر الـ LLM المساعد، ثم ترقيتها إلى todo. الخيارات: --tenant (تحديد نطاق --all إلى tenant واحد)، --author، --json. يُضبط النموذج تحت auxiliary.triage_specifier في config.yaml.
decompose <id> / decompose --allتفريع مهمة في عمود الفرز إلى شجرة من المهام الفرعية الموجَّهة إلى profiles متخصصة حسب الوصف. يرجع إلى ترقية مهمة واحدة بأسلوب specify عندما يقرر الـ LLM أن المهمة لا تستفيد من التفريع. نفس خيارات specify. يُضبط نموذج التفكيك تحت auxiliary.kanban_decomposer في config.yaml؛ أما kanban.orchestrator_profile فيتحكم فقط في من يملك مهمة الجذر/التنسيق بعد التفريع. يعمل أيضًا تلقائيًا في كل دورة موزّع عندما تكون kanban.auto_decompose: true (الافتراضي). راجع التنسيق التلقائي مقابل اليدوي.
gcإزالة مساحات العمل المؤقتة للمهام المؤرشفة.

أمثلة:

ترتيب تحديد اللوحة (الأولوية الأعلى أولًا): خيار --board <slug> → متغير البيئة HERMES_KANBAN_BOARD → الملف ~/.hermes/kanban/current → default.

كل الإجراءات متاحة أيضًا كأمر slash في الـ gateway (/kanban …)، بنفس مساحة المعطيات — بما في ذلك الأوامر الفرعية لـ boards والخيار --board.

للتصميم الكامل — المقارنة مع Cline Kanban / Paperclip / NanoClaw / Gemini Enterprise، وثمانية أنماط للتعاون، وأربع قصص مستخدمين، وبرهان صحة التزامن — راجع دليل مستخدم Kanban.

hermes webhook subscribe

الخيارالوصف
--promptقالب prompt مع مراجع الحمولة بصيغة {dot.notation}.
--eventsأنواع الأحداث المقبولة مفصولة بفواصل (مثل issues,pull_request). فارغ = الكل.
--descriptionوصف مقروء للبشر.
--skillsأسماء المهارات المفصولة بفواصل التي تُحمَّل لتشغيل الوكيل.
--deliverوجهة التسليم: log (الافتراضي)، telegram، discord، slack، github_comment.
--deliver-chat-idمعرّف المحادثة/القناة الهدف للتسليم عبر المنصات.
--secretسر HMAC مخصص. يُنشأ تلقائيًا إن حُذف.
--deliver-onlyتخطي الوكيل — تسليم الـ --prompt المُصاغ كرسالة حرفية. بلا تكلفة LLM، وتسليم دون الثانية. يتطلب أن يكون --deliver وجهة حقيقية (وليس log).
--mirror-to-sessionاكتب أيضًا كل رسالة مُسلّمة في جلسة المحادثة المستهدفة، لكي يكون للرد عليها في تلك المحادثة سياق. معطّل افتراضيًا؛ فعّله فقط للمصادر التي تثق بمحتواها ضمن محادثتك.
--scriptسكربت تصفية/تحويل تحت ~/.hermes/scripts/. تُمرَّر حمولة webhook كـ JSON عبر stdin؛ ويحل مخرج JSON من stdout محل الحمولة، وتُتجاهل webhook عند stdout فارغ أو [SILENT] أو رمز خروج غير صفري. راجع سكربتات التصفية والتحويل.
--route-profileاربط المسار بـ profile ضمن gateway متعدد profiles: عندئذ لا يمكن الوصول إليه إلا عبر /p/<profile>/webhooks/<name>، ويعمل الوكيل باسم ذلك profile. يُتحقّق منه بمقارنته بالـ profiles الموجودة، ويُحتفظ به عند التحديث إذا أُغفل. ليس هو الخيار العام -p/--profile، الذي يختار gateway الذي يُكتب ملف اشتراكاته. راجع Gateways متعددة profiles.

تُحفظ الاشتراكات في ~/.hermes/webhook_subscriptions.json، ويعيد محوّل webhook تحميلها أثناء التشغيل دون إعادة تشغيل gateway. تحتفظ إعادة تنفيذ subscribe لاسم موجود بسرّه وربطه بالـ profile ما لم تمرّر --secret / --route-profile.

hermes doctor

الخيارالوصف
--fixمحاولة إصلاحات تلقائية حيثما أمكن.

حالة الخروج: 0 عندما لا يورد التقرير أي مشاكل غير محلولة، و 1 عندما تبقى مشكلة واحدة على الأقل (بما فيها المشاكل التي تعذّر على --fix إصلاحها)، لكي تعتمد بوابة فحص السلامة أو خطوة CI على hermes doctor كفحص.

يتضمن قسم API Connectivity فحصًا لـ IPv6 route: يفتح اتصال TCP قصيرًا واحدًا عبر IPv6 (لمدة 2 s) بمضيف معروف يدعم IPv4 و IPv6. يُبلّغ عن المسار المُعلن الذي لا يؤدي إلا إلى انتهاء المهلة (بادئة IPv6 تُسقط حركة البيانات) كتحذير يذكر الحل، network.force_ipv4: true. يُعدّ عدم وجود مسار IPv6 أصلًا حالة سليمة ويُبلّغ عنه بالحالة OK؛ ويُتجاوز الفحص إذا كان force_ipv4 مضبوطًا بالفعل.

فحوص إعدادات endpoints المخصّصة (كلاهما تحذيري فقط؛ لا يعيد --fix كتابتهما):

  • custom_providers الذي لا يكون قائمة YAML (مثل سلسلة نصية تركها تنفيذ خاطئ للأمر config set) كخطأ يذكر المفتاح والنوع المستلَم — يتجاهل وقت التشغيل جميع endpoints المخصّصة حتى يعود إلى كونه قائمة.
  • يُبلّغ عن إدخال قديم في قائمة custom_providers لا يقابله إدخال في providers: (بنفس URL للـ endpoint)، مع بيان النقل المطلوب: لا يزال ذلك الإدخال يُقدّم من مخزن القائمة المتقاعد (يقرأه منتقي النماذج وصفحة Custom Endpoints إلى جانب المخزن الجديد) بدلًا من خريطة providers: التي تعدّلها جميع الواجهات الأخرى، ولا يُعاد تشغيل ترحيل v12 الذي نُفّذ مرة واحدة لنقل القائمة إلى providers:.

Config Structure يشير أيضًا إلى أي إعداد قائمة/خريطة مخزّن كسلسلة نصية واحدة بين علامات اقتباس (plugins.enabled: '["a","b"]', model_catalog.excluded_providers: '["openai-api"]' — البنية التي كتبتها إصدارات config set القديمة): يتجاهل كل قارئ هذه السلسلة، لذا تبقى الإضافات غير مركّبة بصمت ولا يُطبّق الاستبعاد أبدًا. تذكر النتيجة المفتاح وأمر hermes config set <key> '<literal>' الذي يخزّن قائمة فعلية؛ ويظهر التحذير نفسه في شعار بدء التشغيل. لا يعيد --fix كتابة الملف.

hermes debug

رفع تقرير تشخيص (معلومات النظام + السجلات الأخيرة) إلى خدمة لصق نصوص والحصول على رابط قابل للمشاركة. مفيد لطلبات الدعم السريعة — يتضمن كل ما يحتاجه المساعِد لتشخيص مشكلتك.

الخيارالوصف
--lines <N>عدد أسطر السجل المُضمّنة لكل ملف سجل (الافتراضي: 200).
--expire <days>مدة صلاحية اللصقة بالأيام (الافتراضي: 7).
--nousالرفع إلى تخزين تشخيص Nous الداخلي بدلًا من خدمة لصق عامة. استخدم هذا عندما يطلب دعم Nous حزمة تشخيص خاصة.
--localطباعة التقرير محليًا بدلًا من رفعه.
--no-redactتعطيل تنقيح الأسرار وقت الرفع. الرفع منقّح افتراضيًا.

يتضمن التقرير معلومات النظام (OS وإصدار Python وإصدار Hermes)، وسجلات الوكيل و gateway و GUI/لوحة التحكم وتطبيق سطح المكتب الحديثة (بحد 512 KB لكل ملف)، إضافةً إلى سجلات التحديث وتسليم تحديث Desktop عند وجودها، وحالة مفاتيح API بعد حجب الأسرار. تُحجب الأسرار من الملفات المرفوعة افتراضيًا لكيلا تتضمنها؛ ويشمل ذلك تفريغ معلومات النظام (بما فيه قيم الإعدادات، مثل إدخالات fallback_providers وبيانات الاعتماد في عناوين URL الخاصة بها) والسجلات، وكذلك تقرير /debug الخاص بالـ gateway.

الرفع الافتراضي يستخدم خدمات لصق عامة تُجرَّب بالترتيب: paste.rs، dpaste.com. أما --nous فيرفع نفس حزمة التشخيص إلى تخزين تشخيص Nous الخاص بدلًا من ذلك؛ ورابط العارض المُعاد مخصص لفريق Nous ويُحذف تلقائيًا بعد 14 يومًا.

ملاحظة

ليس كل شيء إضافة Python. بعض أسطح التوسّع تستخدم عمدًا أوامر shell معتمدة على الإعدادات (TTS، STT، shell hooks) بحيث تصبح أي أداة CLI لديك بالفعل إضافةً دون كتابة Python. أخرى هي خواديم خارجية (MCP) يتصل بها الوكيل ويسجّل أدواتها تلقائيًا. وبعضها مجلدات جاهزة للإسقاط (gateway hooks) بصيغة manifest خاصة بها. اختر السطح المناسب لأسلوب التكامل الذي يلائم حالتك؛ أدلة التأليف في الجدول أعلاه يغطي كل منها placeholders، والاكتشاف، والأمثلة.

إضافات NixOS التصريحية

على NixOS، يمكن تثبيت الإضافات تصريحيًا عبر خيارات الوحدة — دون الحاجة إلى hermes plugins install. راجع دليل إعداد Nix لكل التفاصيل.

الإضافات التصريحية تُربَط برابط رمزي مسبوق بـ nix-managed- — تتعايش مع الإضافات المثبَّتة يدويًا وتُزال تلقائيًا عند حذفها من إعداد Nix.

روابط تثبيت بنقرة واحدة (Desktop)

يسجّل Hermes Desktop مخطط رابط hermes://، بحيث يمكن لموقع، أو ملف README، أو رسالة محادثة أن ترتبط مباشرةً بتثبيت إضافة:

النقر على أحدها يفتح Hermes ويعرض مربع حوار تأكيد — معرّف المستودع، وملاحظة "قبل أن تثبّت"، وروابط تصفّح واستنساخ GitHub — ثم يستنسخ المستودع استنساخًا سطحيًا لاكتشاف ما يشحنه (إضافة وكيل — Python الخلفي، أو إضافة سطح مكتب — واجهة تطبيق، أو كلاهما). تختار المكوّنات عبر مربعات اختيار ثم تؤكّد. لا يُثبَّت شيء حتى تفعل ذلك؛ الروابط العميقة لا تثبّت تلقائيًا أبدًا، وتثبيتات إضافات الوكيل تمر عبر نفس فحص الأمان وقت التثبيت كما في hermes plugins install.

المستودعات الهجينة (نصفا وكيل + سطح مكتب في مستودع واحد) تستخدم رابطًا واحدًا ومربع حوار واحد. يمكن الوصول إلى نفس النافذة المنبثقة دون رابط عبر Capabilities → Plugins → Install from Git. روابط hermes://plugin-agent/… و hermes://plugin-desktop/… القديمة تُوجَّه إلى نفس مربع الحوار. في إصدارات التطوير (npm run dev) المخطط هو hermes-dev://.

إمكانيات الإضافات والموافقة

يمكن للإضافات الإعلان عن أسطح المضيف المميّزة التي تريدها في plugin.yaml:

عندما تعلن إضافة عن إمكانيات، يعرض hermes plugins install (و hermes plugins enable) القائمة مع أوصاف مخاطر من سطر واحد و يسأل مرة واحدة. الموافقة تسجّل المنح تحت plugins.entries.<id>.granted_capabilities مع بصمة موافقة وطابع زمني. الرفض يترك الإضافة مفعَّلة مع تعطيل تلك الإمكانيات — الإضافة المصمَّمة جيدًا تستكشف الحال بـ ctx.has_capability() وتتراجع بسلاسة.

إعادة الموافقة عند التحديث: إذا أعلن تحديث لإضافة عن إمكانيات لم تمنحها، يعرض hermes plugins update الإضافات ويسأل مجددًا. تبقى الإمكانيات الجديدة مُعطَّلة حتى توافق — تحديث إضافة لا يمكن أبدًا أن يوسّع صلاحياتها بصمت.

الجلسات غير التفاعلية تفشل بأمان: تثبيت أو تحديث دون TTY يكمل التثبيت، لكن الإمكانيات المُعلَنة لا تُمنَح. شغّل hermes plugins enable <id> تفاعليًا لمنحها لاحقًا.

ليست sandbox

الإمكانيات هي طبقة موافقة وتدقيق، وليست عزلًا. الإضافات تعمل ككود Python عادي داخل العملية نفسها: إضافة خبيثة يمكن أن تتجاهل كل بوابة هنا. منح إمكانية هو إعلان ثقة بمؤلف الإضافة — وليس تدقيقًا للكود، ولم يراجع Hermes كود الإضافة. ثبّت فقط إضافات من مصادر تثق بها.

إجراءات المنصة

ctx.platform_actions يمنح الإضافة مجموعة أفعال صغرى مقيَّدة بالإمكانيات للتصرف على منصات دردشة متصلة عبر سجلّ محوّلات gateway الحي — البديل المعتمد لتصحيح محوّل بشكل غير رسمي (monkeypatching). مُعطَّل افتراضيًا: كل استدعاء يعيد فحص إمكانية gateway.platform_actions (المفتاح القديم plugins.entries.<id>.allow_platform_actions)، وأي استدعاء غير ممنوح يعيد خطأً منظَّمًا بدلًا من التصرف.

أفعال v1 (كلاهما async، وكلاهما يعيد قاموسًا عاديًا، ولا يرفعان استثناءً أبدًا في تنفيذ الـ hooks):

النجاح هو {"ok": True, "action": <verb>}. الإخفاقات هي {"ok": False, "error": <code>, "detail": <str>} برموز خطأ ثابتة: capability_not_granted، invalid_argument، gateway_unavailable، unknown_platform، adapter_not_registered، adapter_disconnected، unsupported_platform_action، action_failed. الأفعال تتحقق من أن المحوّل الهدف موجود ومتصل قبل التصرف؛ المحوّل غير المتصل أو المفقود يتدهور إلى خطأ منظَّم، وليس استثناءً أبدًا.

المنصات المدعومة في v1: Telegram وDiscord. add_reaction في Telegram يضبط تفاعل البوت (Bot API يستبدل تفاعل بوت سابق بدلًا من تكديسه). كل إجراء — مسموح أو مرفوض — يُكتَب في السجل مع معرّف الإضافة، والفعل، والمنصة، والنتيجة.

ملاحظة أمنية

إجراءات المنصة هي صلاحية إرسال رسائل باسم البوت: إضافة ممنوحة يمكنها التفاعل وإعادة تسمية سلاسل المحادثات في أي محادثة يستطيع بوت gateway الوصول إليها، وليس فقط المحادثة التي شغّلت الـ hook. امنح gateway.platform_actions فقط للإضافات التي تثق بها، وفضّل الإضافات التي توثّق بدقة الإجراءات التي تتخذها. الوصول الخام إلى حمولة/مقبض SDK المنصة ليس عمدًا جزءًا من هذا السطح — بحسب تصحيح التصميم من الجولة الثانية #64176، فهو يحتاج إمكانية خاصة به (gateway.raw_events) بوسم "لا ضمان استقرار" وتصميمًا منفصلًا، ولم يُشحَن بعد.

اكتشاف الإضافات — كتالوج إضافات Hermes

hermes plugins search <term> يبحث في كتالوج إضافات Hermes — الكتالوج المنسَّق والمثبَّت بـ SHA، والمُدار في مستودع hermes-agent (plugin-catalog/). يشمل التطابق أسماء المدخلات، والأوصاف، والأدوات المُعلَنة:

بمجرد أن تجد إضافة، ثبّتها بالاسم المجرد — يُحلّ الاسم إلى مستودع المدخلة عند الـ SHA المثبَّت، وتُسجَّل نشأة الكتالوج بحيث يمكن لـ hermes plugins update إعادة التثبيت عندما يتحرك الكتالوج:

معرّفات owner/repo أو روابط Git الصريحة لا تلامس الكتالوج أبدًا وتُوسَم كمصادر مخصصة (غير مراجَعة). --ref <40-char commit SHA> صريح يثبّت تثبيتًا مخصصًا.

راجع كتالوج الإضافات لنموذج الثقة الكامل، وCI القبول، وسير عمل التقديم.

مُدرَج في الكتالوج ≠ مُدقَّق

وجود مدخلة في الكتالوج يعني أن بيانات المدخلة الوصفية والإمكانيات المُعلَنة رُوجِعَت عند القبول — وهذا ليس تدقيقًا للكود. التثبيت لا يزال يمر عبر تدفق الموافقة العادي (تثبيت الإضافات مُعطَّل افتراضيًا، والتفعيل خطوة صريحة، وحقوق تجاوز الأداة تتطلب منحًا منفصلًا). راجع مصدر الإضافة قبل تفعيلها.

حزم الإضافات

حزمة الإضافات (plugin pack) هي ملف YAML تصريحي قابل للمشاركة (hermes-pack.yaml) يثبّت مجموعة من الإضافات — مثل مشاركة modpack. تثبيت حزمة يتفرّع إلى تثبيتات ثابتة عادية؛ لا شيء جديد يوجد في وقت التشغيل.

وضعية سلسلة التوريد. يجب أن يكون ref لكل مدخلة SHA كامل مكوَّن من 40 حرفًا — تُرفَض الوسوم tags وأسماء الفروع بخطأ يسمّي المدخلة، وهي نفس القاعدة المطبَّقة على كتالوج الإضافات. تسلك تثبيتات الحزمة نفس مسار التثبيت الثابت تمامًا مثل hermes plugins install --ref <sha> وتسجّل نفس النشأة في plugins/.install-metadata.json، بحيث يُحلّ تثبيتان لنفس الحزمة إلى الشيء نفسه. تُبنى الحزم على حقول manifest v2 (manifest_version، api_version، requires_plugins) — كل manifest خاص بإضافة لا يزال يُتحقَّق منه عبر مسار التثبيت العادي.

الموافقة لا تُمنَح جماعيًا أبدًا. تعرض pack install شاشة مراجعة إلزامية (كل إضافة، ومصدرها، وrefها المثبَّت، والإمكانيات التي تعلن عنها)، ثم تطلب تأكيدًا واحدًا لمحتويات الحزمة. بعد ذلك، تمر إمكانيات كل إضافة المُعلَنة عبر طلب موافقة الإمكانيات القياسي لكل إضافة — مطابق لـ hermes plugins install منفردة. لا وجود لـ --yes، ولا يمكن للجلسات غير التفاعلية تثبيت الحزم.

الأسرار لا تنتقل أبدًا في الحزم. تقتصر بذور config: على مفاتيح plugins.entries.<id> غير السرية — أسماء المفاتيح ذات الشكل السري (*token*، *key*، *password*، …)، ومنح الإمكانيات، وبوابات الثقة allow_* المُهملة، تُرفَض عند التثبيت وتُحذَف عند التصدير. الإضافات التي تحتاج أسرارًا تعلن عنها في requires_env الخاص بها، والتي تُطلَب أثناء التثبيت كالمعتاد. القيم الموجودة أصلًا لدى المستخدم في plugins.entries.<id> تفوز دائمًا على بذور الحزمة.

الفشل الجزئي. تُثبَّت كل إضافة باستقلالية؛ تُبلَّغ الإخفاقات لكل إضافة، وتستمر البقية، ويخرج الأمر برمز غير صفري إذا فشلت أي إضافة.

تحفظات التصدير. يشمل pack export فقط الإضافات ذات نشأة Git معروفة (المثبَّتة عبر hermes plugins install). الإضافات المحلية فقط تُدرَج كتعليقات تحذير في YAML المُصدَر، وليست كمدخلات قابلة للتثبيت.

قائمة skills: تُحلَّل وتُعرَض عند التثبيت لكنها لا تُثبَّت تلقائيًا بعد — ثبّت تلك يدويًا في الوقت الحالي (hermes skills). ربط معرّفات skill-hub في تثبيت الحزم هو مسار تتمة موثَّق.

فحص الأمان وقت التثبيت

واجهة تفاعلية

تشغيل hermes plugins دون وسائط يفتح شاشة تفاعلية مركّبة:

  • قسم الإضافات العامة — مربعات اختيار، بدّل بمفتاح SPACE. محدَّد = في plugins.enabled، غير محدَّد = في plugins.disabled (تعطيل صريح).
  • قسم إضافات المزوّد — يعرض الاختيار الحالي. اضغط ENTER للدخول إلى منتقٍ راديو حيث تختار مزوّدًا فعّالًا واحدًا.
  • الإضافات المدمجة تظهر في نفس القائمة بوسم [bundled].

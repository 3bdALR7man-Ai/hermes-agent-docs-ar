معلومة

مهارة التحليل الجنائي لأمن المصادر المفتوحة

إطار عمل تحقيقي متعدد الوكلاء من 7 مراحل لبحث هجمات سلسلة توريد المصادر المفتوحة. مُقتبَس من نظام التحليل الجنائي في RAPTOR. يغطي GitHub Archive، وWayback Machine، وواجهة GitHub API، وتحليل git المحلي، واستخلاص مؤشرات الاختراق، وتكوين الفرضيات المدعومة بالأدلة والتحقق منها، وإنتاج التقرير الجنائي النهائي.

⚠️ ضوابط منع الهلوسة

اقرأ هذه الضوابط قبل كل خطوة تحقيق. مخالفتها تُبطل التقرير.

  1. قاعدة الأدلة أولًا: يجب أن يستشهد كل ادعاء في أي تقرير أو فرضية أو ملخص بمعرّف دليل واحد على الأقل (EV-XXXX). الادعاءات بلا استشهادات ممنوعة.
  2. التزم بنطاقك: لكل وكيل فرعي (محقق) مصدر بيانات واحد. لا تخلط المصادر. محقق GH Archive لا يستعلم واجهة GitHub API، والعكس صحيح. حدود الأدوار صارمة.
  3. الفصل بين الحقيقة والفرضية: ضع علامة [HYPOTHESIS] على كل استنتاج غير مُتحقَّق منه. لا تُذكر كحقائق إلا العبارات التي تم التحقق منها من المصادر الأصلية.
  4. لا افتعال للأدلة: يجب أن يتحقق مدقق الفرضيات آليًا من أن كل معرّف دليل مستشهد به موجود فعليًا في مخزن الأدلة قبل قبول أي فرضية.
  5. يتطلب الدحض إثباتًا: لا يمكن رفض فرضية دون حجة مضادة محددة ومدعومة بالأدلة. عبارة "لم يُعثر على دليل" لا تكفي للدحض — فهي فقط تجعل الفرضية غير حاسمة.
  6. التحقق المزدوج من SHA/الروابط: يجب تأكيد أي commit SHA أو رابط أو معرّف خارجي مستشهد به كدليل من مصدرين مستقلين على الأقل قبل تصنيفه كمتحقَّق منه.
  7. قاعدة الكود المشبوه: لا تُشغّل أبدًا كودًا موجودًا داخل المستودع قيد التحقيق محليًا. حلّله بشكل ساكن فقط، أو استخدم execute_code في بيئة معزولة (sandbox).
  8. حجب الأسرار: يجب حجب أي مفاتيح API أو رموز أو بيانات اعتماد تُكتشف أثناء التحقيق في التقرير النهائي. سجّلها داخليًا فقط.

سيناريوهات توضيحية

  • السيناريو أ: التباس التبعيات (Dependency Confusion): تُرفَع حزمة خبيثة باسم internal-lib-v2 إلى NPM بإصدار أعلى من النسخة الداخلية. يجب أن يتتبّع المحقق متى شُوهدت هذه الحزمة أول مرة وما إذا حدّث أي PushEvent في المستودع المستهدف ملف package.json إلى هذا الإصدار.
  • السيناريو ب: الاستيلاء على حساب مشرف: يُستخدَم حساب مساهم قديم لدفع ملف .github/workflows/build.yml يحتوي باب خلفي (backdoor). يبحث المحقق عن PushEvents من هذا المستخدم بعد فترة خمول طويلة أو من IP/موقع جديد (إن أمكن اكتشافه عبر BigQuery).
  • السيناريو ج: إخفاء عبر Force-Push: يرتكب مطوّر خطأً بدفع سرّ إنتاجي، ثم يقوم بـ force-push "لإصلاحه". يستخدم المحقق git fsck وGH Archive لاسترداد commit SHA الأصلي والتحقق مما تسرّب.

اصطلاح المسارات: في هذه المهارة، يشير SKILL_DIR إلى جذر دليل تثبيت هذه المهارة (المجلد الذي يحتوي ملف SKILL.md هذا). عند تحميل المهارة، حلّ SKILL_DIR إلى المسار الفعلي — مثلًا ~/.hermes/skills/security/oss-forensics/ أو ما يعادله ضمن optional-skills/. كل مراجع السكربتات والقوالب نسبية إليه.

المرحلة 1: تحليل الطلب واستخلاص مؤشرات الاختراق

الهدف: استخلاص جميع الأهداف التحقيقية المنظَّمة من طلب المستخدم.

الإجراءات:

  • حلّل طلب المستخدم واستخلص:
    • المستودع المستهدف (owner/repo)
    • الجهات الفاعلة المستهدفة (معرّفات GitHub، عناوين البريد الإلكتروني)
    • الإطار الزمني محل الاهتمام (نطاقات تواريخ الالتزامات (commits)، طوابع زمنية لطلبات السحب)
    • مؤشرات الاختراق المُقدَّمة: commit SHAs، مسارات الملفات، أسماء الحزم، عناوين IP، النطاقات، مفاتيح/رموز API، الروابط الخبيثة
    • أي تقارير أمنية من موردين أو منشورات مدونات مرتبطة

الأدوات: الاستدلال فقط، أو execute_code لاستخلاص التعابير النمطية (regex) من كتل نصية كبيرة.

الناتج: املأ iocs.md بمؤشرات الاختراق المستخلَصة. يجب أن يحتوي كل مؤشر على:

  • النوع (من: COMMIT_SHA، FILE_PATH، API_KEY، SECRET، IP_ADDRESS، DOMAIN، PACKAGE_NAME، ACTOR_USERNAME، MALICIOUS_URL، OTHER)
  • القيمة
  • المصدر (من المستخدم، أو مُستنتَج)

المرجع: راجع evidence-types.md لتصنيف مؤشرات الاختراق.

المرحلة 2: جمع الأدلة بالتوازي

أطلق حتى 5 وكلاء فرعيين متخصصين (محققين) باستخدام delegate_task (وضع دفعي، بحد أقصى 3 متزامنين). لكل محقق مصدر بيانات واحد ولا يجوز له خلط المصادر.

ملاحظة للمنسّق: مرّر قائمة مؤشرات الاختراق من المرحلة 1 والإطار الزمني للتحقيق في حقل context لكل مهمة مفوَّضة.

المحقق 1: محقق git المحلي

حدود الدور: تستعلم مستودع GIT المحلي فقط. لا تستدعِ أي واجهات برمجية خارجية.

الإجراءات:

الأدلة التي يجب جمعها (أضفها عبر python SKILL_DIR/scripts/evidence-store.py add):

  • كل commit SHA معلَّق (dangling) ← النوع: git
  • دليل force-push (سجل reflog يُظهر إعادة كتابة التاريخ) ← النوع: git
  • التزامات غير موقَّعة من مساهمين موثَّقين ← النوع: git
  • إضافات ملفات ثنائية مشبوهة ← النوع: git

المرجع: راجع recovery-techniques.md للوصول إلى الالتزامات التي طُبِّق عليها force-push.

المحقق 2: محقق واجهة GitHub API

حدود الدور: تستعلم واجهة GITHUB REST API فقط. لا تشغّل أوامر git محليًا.

الإجراءات:

أهداف المقارنة المرجعية (ضع علامة على التباينات كأدلة):

  • طلب سحب موجود في الأرشيف لكنه غائب عن الواجهة البرمجية ← دليل على الحذف
  • مساهم موجود في أحداث الأرشيف لكنه غائب عن قائمة المساهمين ← دليل على إلغاء الصلاحيات
  • التزام موجود في PushEvents بالأرشيف لكنه غائب عن قائمة الالتزامات في الواجهة البرمجية ← دليل على force-push/حذف

المرجع: راجع evidence-types.md لأنواع أحداث GH.

المحقق 3: محقق Wayback Machine

حدود الدور: تستعلم واجهة WAYBACK MACHINE CDX API فقط. لا تستخدم واجهة GitHub API.

الهدف: استرداد صفحات GitHub المحذوفة (ملفات README، والمشكلات (issues)، وطلبات السحب، والإصدارات، وصفحات الويكي).

الإجراءات:

الأدلة التي يجب جمعها:

  • لقطات (snapshots) مؤرشفة للمشكلات/طلبات السحب المحذوفة مع محتواها
  • نسخ سابقة من ملف README تُظهر التغييرات
  • دليل على وجود محتوى في الأرشيف وغيابه عن حالة GitHub الحالية

المرجع: راجع github-archive-guide.md لمعاملات واجهة CDX API.

المحقق 4: محقق GH Archive / BigQuery

حدود الدور: تستعلم GITHUB ARCHIVE عبر BIGQUERY فقط. هذا سجل غير قابل للعبث بكل أحداث GitHub العامة.

المتطلبات المسبقة: يتطلب بيانات اعتماد Google Cloud بصلاحية وصول إلى BigQuery (gcloud auth application-default login). إذا كانت غير متاحة، تجاوز هذا المحقق ودوّن ذلك في التقرير.

قواعد تحسين التكلفة (إلزامية):

  1. شغّل دائمًا --dry_run قبل كل استعلام لتقدير التكلفة.
  2. استخدم _TABLE_SUFFIX للتصفية حسب النطاق الزمني وتقليل البيانات الممسوحة.
  3. اختر (SELECT) الأعمدة التي تحتاجها فقط.
  4. أضف LIMIT ما لم تكن تُجري تجميعًا.

الأدلة التي يجب جمعها:

  • أحداث force-push (payload.size > 0، payload.distinct_size = 0)
  • أحداث الحذف (DeleteEvents) للفروع/الوسوم
  • أحداث تشغيل سير العمل (WorkflowRunEvents) لأتمتة CI/CD مشبوهة
  • أحداث PushEvents تسبق "فجوة" في سجل git (دليل على إعادة كتابة التاريخ)

المرجع: راجع github-archive-guide.md لكل أنواع الأحداث الـ12 وأنماط الاستعلام.

المحقق 5: محقق إثراء مؤشرات الاختراق

حدود الدور: تُثري مؤشرات الاختراق الموجودة من المرحلة 1 باستخدام مصادر عامة سلبية فقط. لا تُنفّذ أي كود من المستودع المستهدف.

الإجراءات:

  • لكل commit SHA: حاول الاسترداد عبر رابط GitHub المباشر (github.com/OWNER/REPO/commit/SHA.patch)
  • لكل نطاق/IP: تحقق من DNS السلبي وسجلات WHOIS (عبر web_extract على خدمات WHOIS العامة)
  • لكل اسم حزمة: تحقق من npm/PyPI بحثًا عن تقارير حزم خبيثة مطابقة
  • لكل اسم مستخدم فاعل: تحقق من ملف GitHub الشخصي، وسجل المساهمات، وعمر الحساب
  • استرد الالتزامات التي طُبِّق عليها force-push بثلاث طرق (راجع recovery-techniques.md)

المرحلة 3: دمج الأدلة

بعد أن ينهي جميع المحققين عملهم:

  1. شغّل python SKILL_DIR/scripts/evidence-store.py --store evidence.json list لرؤية كل الأدلة المجمَّعة.
  2. لكل قطعة دليل، تحقق من تطابق تجزئة content_sha256 مع المصدر الأصلي.
  3. جمّع الأدلة حسب:
    • الجدول الزمني: رتّب جميع الأدلة ذات الطابع الزمني ترتيبًا زمنيًا
    • الجهة الفاعلة: جمّع حسب معرّف GitHub أو البريد الإلكتروني
    • مؤشر الاختراق: اربط الدليل بمؤشر الاختراق الذي يخصّه
  4. حدّد التباينات: العناصر الموجودة في مصدر والغائبة عن آخر (مؤشرات رئيسية على الحذف).
  5. ضع على الدليل علامة [VERIFIED] (مؤكَّد من مصدرين مستقلين أو أكثر) أو [UNVERIFIED] (مصدر واحد فقط).

المرحلة 4: تكوين الفرضيات

يجب أن تفعل الفرضية ما يلي:

  • تذكر ادعاءً محددًا (مثل "قام الفاعل X بـ force-push إلى BRANCH في DATE لمحو commit SHA")
  • تستشهد بمعرّفي دليل على الأقل يدعمانها (EV-XXXX، EV-YYYY)
  • تحدد ما الدليل الذي يمكن أن يدحضها
  • تُصنَّف بعلامة [HYPOTHESIS] إلى أن يتم التحقق منها

قوالب الفرضيات الشائعة (راجع investigation-templates.md):

  • اختراق المشرف: استخدام حساب شرعي بعد الاستيلاء عليه لحقن كود خبيث
  • التباس التبعيات: احتلال أسماء حزم لاعتراض عمليات التثبيت
  • حقن CI/CD: تعديلات خبيثة في سير العمل لتشغيل كود أثناء عمليات البناء
  • الانتحال بأسماء متشابهة (Typosquatting): اسم حزمة يكاد يطابق اسمًا آخر يستهدف الأخطاء الإملائية
  • تسرّب بيانات الاعتماد: رمز/مفتاح ارتُكب بالخطأ ثم مُحي عبر force-push

لكل فرضية، أطلق وكيلًا فرعيًا عبر delegate_task لمحاولة إيجاد دليل مضادّ قبل التأكيد.

المرحلة 5: التحقق من الفرضيات

يجب أن يتحقق الوكيل الفرعي المدقّق آليًا مما يلي:

  1. لكل فرضية، استخلص كل معرّفات الأدلة المستشهد بها.
  2. تحقق من وجود كل معرّف في evidence.json (فشل صارم إذا كان أي معرّف مفقودًا ← تُرفض الفرضية باعتبارها مُفتعَلة محتملًا).
  3. تحقق من أن كل قطعة دليل موسومة بـ[VERIFIED] قد تأكدت من مصدرين أو أكثر.
  4. تحقق من الاتساق المنطقي: هل يدعم الجدول الزمني الذي تصفه الأدلة الفرضية؟
  5. تحقق من التفسيرات البديلة: هل يمكن أن ينشأ نمط الأدلة نفسه من سبب حميد؟

الناتج:

  • VALIDATED: كل الأدلة مستشهد بها ومتحقَّق منها ومتسقة منطقيًا، ولا تفسير بديل معقول.
  • INCONCLUSIVE: الأدلة تدعم الفرضية لكن توجد تفسيرات بديلة أو الأدلة غير كافية.
  • REJECTED: معرّفات أدلة مفقودة، أو استُشهد بدليل غير متحقَّق منه كحقيقة، أو اكتُشف تناقض منطقي.

تعود الفرضيات المرفوضة إلى المرحلة 4 للتنقيح (بحد أقصى 3 تكرارات).

المرحلة 6: إعداد التقرير النهائي

املأ investigation-report.md باستخدام القالب في forensic-report.md.

الأقسام الإلزامية:

  • الملخص التنفيذي: حكم في فقرة واحدة (مُخترَق / نظيف / غير حاسم) مع مستوى الثقة
  • الجدول الزمني: إعادة بناء زمنية لكل الأحداث المهمة مع استشهادات الأدلة
  • الفرضيات المتحقَّق منها: كل واحدة مع حالتها والأدلة الداعمة
  • سجل الأدلة: جدول لكل مدخلات EV-XXXX مع المصدر والنوع وحالة التحقق
  • قائمة مؤشرات الاختراق: كل مؤشرات الاختراق المستخلَصة والمُثراة
  • سلسلة الحيازة (Chain of Custody): كيف جُمعت الأدلة، ومن أي مصادر، وفي أي أوقات
  • التوصيات: إجراءات تخفيف فورية إذا اكتُشف اختراق؛ توصيات مراقبة

قواعد التقرير:

  • يجب أن يحمل كل ادعاء واقعي استشهادًا واحدًا على الأقل بصيغة [EV-XXXX]
  • يجب أن يذكر الملخص التنفيذي مستوى الثقة (عالٍ / متوسط / منخفض)
  • يجب حجب كل الأسرار/بيانات الاعتماد إلى [REDACTED]

المرحلة 7: الإتمام

  1. شغّل العدّ النهائي للأدلة: python SKILL_DIR/scripts/evidence-store.py --store evidence.json list
  2. أرشِف دليل التحقيق كاملًا.
  3. إذا تأكّد الاختراق:
    • اذكر إجراءات التخفيف الفورية (تدوير بيانات الاعتماد، وتثبيت تجزئات (hashes) التبعيات، وإخطار المستخدمين المتأثرين)
    • حدّد الإصدارات/الحزم المتأثرة
    • دوّن التزامات الإفصاح (إذا كانت حزمة عامة: نسّق مع سجل الحزم)
  4. اعرض investigation-report.md النهائي على المستخدم.

إرشادات الاستخدام الأخلاقي

صُمِّمت هذه المهارة من أجل التحقيق الأمني الدفاعي — حماية برمجيات المصادر المفتوحة من هجمات سلسلة التوريد. يجب ألّا تُستخدم لـ:

  • المضايقة أو المطاردة للمساهمين أو المشرفين
  • كشف الهوية (Doxing) — ربط نشاط GitHub بهويات حقيقية لأغراض خبيثة
  • الاستخبارات التنافسية — التحقيق في مستودعات خاصة أو داخلية دون تفويض
  • الاتهامات الباطلة — نشر نتائج تحقيق دون أدلة متحقَّق منها (راجع ضوابط منع الهلوسة)

ينبغي إجراء التحقيقات وفق مبدأ الحد الأدنى من التدخل: اجمع فقط الأدلة اللازمة لإثبات الفرضية أو نفيها. عند نشر النتائج، اتّبع ممارسات الإفصاح المسؤول وتنسّق مع المشرفين المتأثرين قبل الإفصاح العلني.

إذا كشف التحقيق عن اختراق حقيقي، اتّبع عملية الإفصاح المنسّق عن الثغرات:

  1. أخطر مشرفي المستودع خاصةً أولًا
  2. امنح وقتًا معقولًا للمعالجة (عادةً 90 يومًا)
  3. نسّق مع سجلات الحزم (npm وPyPI وغيرها) إذا كانت حزم منشورة متأثرة
  4. سجّل CVE إذا كان ذلك مناسبًا

تحديد معدل الواجهة البرمجية

تفرض واجهة GitHub REST API حدود معدل قد تعطّل التحقيقات الكبيرة إن لم تُدَر بعناية.

الطلبات المصادَق عليها: 5000 في الساعة (يتطلب متغير بيئة GITHUB_TOKEN أو مصادقة عبر gh CLI) الطلبات غير المصادَق عليها: 60 في الساعة (غير قابلة للاستخدام في التحقيقات)

أفضل الممارسات:

  • صادق دائمًا: export GITHUB_TOKEN=ghp_... أو استخدم gh CLI (يُصادق تلقائيًا)
  • استخدم الطلبات الشرطية (ترويسات If-None-Match / If-Modified-Since) لتجنّب استهلاك الحصة على بيانات لم تتغيّر
  • لنقاط النهاية المُرقَّمة (paginated)، اجلب كل الصفحات بالتسلسل — لا توازِ الطلبات على نفس نقطة النهاية
  • تحقق من ترويسة X-RateLimit-Remaining؛ إذا كانت أقل من 100، أوقف العمل حتى طابع X-RateLimit-Reset الزمني
  • لدى BigQuery حصصه الخاصة (10 تيرابايت/يوم في الفئة المجانية) — شغّل dry-run دائمًا أولًا
  • واجهة Wayback Machine CDX API: لا حدّ معدل رسمي، لكن كن معتدلًا (بحد أقصى 1-2 طلب/ثانية)

إذا تعرّضت لتحديد المعدل في منتصف التحقيق، سجّل النتائج الجزئية في مخزن الأدلة ودوّن القيد في التقرير.

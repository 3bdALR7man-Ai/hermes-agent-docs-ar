metadata.profile (رحلة ذهاب وإياب متعددة الإرسال). يحمل الحقل metadata في كل إطار صادر موجّه إلى محادثة محددات المستأجر التي التقطها الـ gateway من الحدث الوارد (scope_id, user_id)، وفي gateway متعدد الإرسال يحمل أيضًا Hermes profile الذي وجّه إليه الموصل الحدث الوارد لتلك المحادثة؛ وتحمل إطارات follow_up الـ profile المرمّز في نطاق أسماء session_key. يجب على الموصل إلزاميًا وضع profile نفسه على الحدث التالي من نوع passthrough_forward / inbound لتلك المحادثة أو التفاعل، كي يصل الضغط على زر Discord بعد slash command إلى جلسة الـ profile نفسها (gateway/relay/adapter.py::_with_scope, send_follow_up). لا تُصدر gateways أحادية الـ profile هذا المفتاح مطلقًا — وتظل الإطارات متطابقة بايتًا ببايت.

send_media (المرحلة 2: إخراج الوسائط). تعبر الوسائط الاتصال بالمرجع: source_url إما (أ) مرجع إعادة استضافة لدى الموصل سبق أن رفعه الـ gateway عبر POST {connector}/relay/media (جسم من البايتات الخام، وترويسات Content-Type + X-Media-Filename الاختيارية، و bearer عبر HMAC خاص بكل gateway — وهو مخطط token نفسه المستخدم في ترقية WS ؛ الاستجابة {id, size} → المرجع {connector}/relay/media/{id})، أو (ب) عنوان URL عام باستخدام http(s) (مثل توليد عبر fal.media) ينزّله الموصل مباشرة. ويكون media_kind أحد القيم image / voice / audio / video / document ويحدد مسار الرفع الأصلي للمنصة (Telegram sendPhoto/sendVoice/…، ومرفق multipart في Discord ، ورفع خارجي في Slack ، ورفع وسائط + رسالة وسائط في WhatsApp). يُنقل التعليق في content ويُعرض عبر مسار markdown المعتاد للمنصة؛ أما المنصات التي لا تدعم التعليقات أصلًا فتتلقى إرسالًا نصيًا لاحقًا من جهة الموصل. يشترط تمكين المسارين والعملية أن يعلن supported_ops عن send_media — فلا يرى الموصل القديم هذه العملية مطلقًا (وتعود عمليات إرسال الوسائط لدى الـ gateway إلى البدائل النصية السابقة للوسائط). حد الحجم 25 MB (قيمة MEDIA_MAX_BYTES في mediaStore.ts لدى الموصل؛ ويُرفض الرفع الذي يتجاوزها بالرمز 413).

الوسائط الواردة (المرحلة 2: إدخال الوسائط). تحمل حقول media_urls في الحدث الوارد مراجع قابلة للجلب: تمر عناوين URL العامة للمنصة دون تغيير (Discord CDN)؛ أما عناوين URL للمنصة المقيدة بالمصادقة أو المنتهية الصلاحية (Telegram file API ، و Slack url_private، و WhatsApp Graph media) فينزّلها الموصل باستخدام بيانات اعتماد المنصة ويعيد استضافتها بصيغة {connector}/relay/media/{id} — ولا تعبر بيانات اعتماد المنصة الاتصال مطلقًا. تستطيع أي gateway مُصادَق عليها قراءة مراجع إعادة الاستضافة (دلالات capability-URL: المعرّف عشوائي بطول 128-bit ، وقد أُرسل بالفعل إلى كل مستلم مسموح له)؛ وينزّل الـ gateway كل مرجع باستخدام bearer الخاص به، ويقدم مسارات ملفات محلية إلى الوكيل، على غرار adapters الأصلية. تنتهي صلاحية الملفات المعاد استضافتها (TTL نحو 1h) — لذا نزّلها عند الاستلام، لا عند الحاجة لاحقًا. وتضيف مصفوفة media موازية (بالترتيب نفسه) بيانات وصفية من نوع kind, mime, size, filename, caption؛ ويعكس message_type نوع المرفق الأول (image/audio/document).

prompt (المرحلة 3: التفاعل). تعرض عملية واحدة مجردة عن المنصة تفاعلات الـ gateway الأعلى حساسية (موافقات التنفيذ، وتأكيدات slash ، وخيارات التوضيح) باستخدام عناصر تحكم أصلية: مكونات أزرار Discord ، ولوحات مفاتيح Telegram المضمّنة، وإجراءات Slack Block Kit ، ورسائل أزرار WhatsApp (≤3 خيارات) / رسائل القوائم (4–10؛ >10 يعود إلى البديل النصي المرقّم). prompt_kind (approval/clarify/choice) ليس سوى تلميح للتنسيق. prompt_id يُنشئه الـ gateway ويظل غير قابل للتفسير لدى الموصل؛ وتحمل حمولة callback لكل خيار الـ token hp1:<prompt_id>:<option_id> (≤64 bytes — فحد callback_data في Telegram يقيّد كل المسارات؛ ومعرّفات الخيارات هي [A-Za-z0-9_.-]، بطول ≤32 محرفًا). وينشئ الـ gateway معرّف الـ prompt بصيغة <per-process nonce>.<8 hex> ضمن الأبجدية وحد الحجم نفسيهما: يوزع الموصل تمريرًا مباشرًا (ضغطة Discord) إلى كل جلسات gateway الحية للمستأجر، بخلاف الرسالة التي يقصرها على مجموعة النُسخ المسموح لها؛ لذلك فإن nonce هو الوسيلة التي تميز بها gateway الـ prompt الخاص بها من prompt نُسخة أخرى. ويتطابق style مع كل منصة (primary/success/danger/secondary). ويكون timeout_s إرشاديًا على الاتصال — إذ تُفرض الصلاحية لدى الـ gateway (يحذف سجل الـ prompts المعلقة الإدخالات المنتهية؛ ثم يرد الـ gateway المالك بإشعار قصير "no longer waiting").

prompt_response (المرحلة 3: الوارد). تعود ضغطة المستخدم كحدث MessageEvent وارد عادي يحمل prompt_response: {prompt_id, option_id, label?, prompt_message_id?} — وليس custom_id خامًا من المنصة مطلقًا. ويحاكي text في الحدث /{option_id} باستخدام message_type: "command" كي توجه gateway أقدم من هذا الحقل الضغطة كرد مكتوب بدل إسقاطها. أما gateway التي تفهم الحقل فتستهلك الضغطة دائمًا: معرّف prompt الذي لم تنشئه ينتمي إلى gateway أخرى وصلها التوزيع نفسه، وقد أدى السماح لنص /{option_id} بالوصول إلى مسار المحادثة إلى أن ترد كل نُسخة أخرى بـ "Unknown command" تحت إقرار المالك الوحيد. المصدر هو المستخدم الحقيقي الذي ضغط (كما يرصده الموصل: Telegram callback_query.from، و Slack block_actions.user، و WhatsApp messages[].from، وعضو/مستخدم تفاعل Discord)، لذا تُطبَّق بوابات التفويض لدى الـ gateway على ضغطة الزر تمامًا كما تُطبَّق على /approve مكتوب. مسارات الإدخال: Telegram callback_query (بالاستقصاء، مع توسيع allowed_updates؛ وإيقاف مؤشر الانتظار عبر answerCallbackQuery بأفضل جهد)، و Slack POST /slack/interactions (HMAC للبايتات الخام + نافذة منع إعادة الإرسال، بالإجراءات نفسها المتبعة مع /slack/commands)، و WhatsApp interactive button_reply/list_reply (فرع تطبيع webhook)، وتفاعلات مكونات Discord من النوع 3 (تمرير منقّى عبر §5.1؛ ويكون إقرار الحافة للنوع 3 هو DEFERRED_UPDATE فلا يظهر رد "thinking…"). ولا تصبح حمولات callback الأجنبية (أزرار تكامل آخر) أحداث prompt مطلقًا: يسقطها Telegram/Slack/WhatsApp عند الموصل؛ وتحتفظ تمريرات Discord من النوع 3 بالشكل القديم custom_id كنص.

react (المرحلة 3: دورة حياة الإقرار). يضيف/يزيل تفاعل البوت نفسه emoji على message_id — مستعيدًا إقرارات دورة المعالجة 👀→✅/❌ للـ adapters الأصلية عبر relay. يُنقل emoji بصيغة Unicode ؛ ويحوّله مُرسل Slack إلى مفردات أسماء Slack (eyes, white_check_mark، …) ويعامل already_reacted/no_reaction على أنه نجاح (idempotent). ويستخدم Telegram setMessageReaction (المجموعة الفارغة = إزالة؛ وقد يرفض تقييد Telegram للـ emoji المعتمدة بعض الرموز — ويكون الفشل منظّمًا، ويعامل الـ gateway التفاعلات على أنها تجميلية). ويرسل WhatsApp رسالة تفاعل (emoji فارغ = إزالة). وبحسب العقد، تُنفذ التفاعلات بأفضل جهد: يجب ألا يؤدي فشل react إلى فشل أي دور مطلقًا.

thread_create / thread_rename (المرحلة 4: دورة حياة thread). يغطي زوج واحد مجرد عن المنصة threads تسليم المهام، وموضوعات Telegram DM/المنتديات، وإعادة التسمية الدلالية بعنوان LLM. thread_create: ينشئ Discord thread في قناة (النوع 11)، أو thread مرتبطًا برسالة عند ضبط message_id؛ ويستخدم Telegram createForumTopic (مع إعادة معرّف الموضوع)؛ وينشر Slack رسالة جذر أولية ذات اسم ويعيد ts الخاص بها (ترتبط threads هناك برسائل — ويُعاد مرساة message_id الصريحة كما هي حرفيًا). ويُحمل المعرّف المُنشأ في SendResult.thread_id. thread_rename: يُرسل Discord طلب PATCH إلى قناة thread ؛ ويستخدم Telegram editForumTopic. وحارس only_if_current_name هو دلالة adapters الأصلية التي تعطي أولوية لإعادة التسمية البشرية، ويُفرض لدى الموصل: يقرأ Discord الاسم الحالي أولًا ولا يجري أي تغيير (نتيجة منظّمة success:false) عند عدم التطابق؛ ولا يتيح Telegram قراءة اسم الموضوع، لذا لا يمكن تنفيذ إعادة تسمية محمية، فتفشل بأمان (وتستمر عمليات إعادة التسمية غير المحمية). ولا يعلن Slack عن thread_rename (نص رسالة الجذر محتوى، وليس اسمًا). ولا يعلن WhatsApp عن أي منهما (لا توجد threads).

علامات auto-thread + بيان الأوامر المعلن من الـ gateway (المرحلة 4: الوارد/المصافحة). عندما تنشئ سياسة إخراج auto-thread لدى الموصل thread في Discord ، تحمل الأحداث الواردة اللاحقة من ذلك thread source.auto_thread_created: true + source.auto_thread_initial_name — وهو الدليل الذي يرصده الموصل ويُفعّل مسار إعادة التسمية الدلالية لدى الـ gateway (يعيد عنوان جلسة LLM تسمية thread عبر thread_rename محمي؛ والذاكرة خاصة بكل نُسخة، لذا في مجموعة N>1 لا يُفعّل المسار أصلًا عند عدم العثور على الإدخال). ويمكن للـ gateway أيضًا إعلان مجموعة slash commands في إطار hello الخاص بـ Discord (command_manifest: [{name, description, options?}])؛ ويوفّق الموصل تسجيل application-command العام في Discord معها (GET → diff → bulk PUT overwrite ؛ عملية idempotent ، مع دمج الطلبات المتقاربة، وبأفضل جهد — فلا يؤثر فشل التسجيل في المصافحة مطلقًا). وتظل الأوامر تُوجَّه عبر مستوى التمرير المباشر كما سابقًا؛ ولا يفعل البيان سوى إبقاء سجل Discord متزامنًا مع ما يعالجه موزّع أوامر الـ gateway.

إثراء reply_to الوارد (المرحلة 4). قد يحمل رد المنصة reply_to: {text?, author?, is_own?} إلى جانب reply_to_message_id — أي ما اقتبسه المستخدم، ولا يُملأ إلا من البيانات الموجودة بالفعل لدى الموصل (حقل referenced_message المضمّن في Discord ، وحقل reply_to_message المضمّن في Telegram ، و WhatsApp context.from + تخزين مؤقت محدود للنصوص الواردة لكل نُسخة لتوفير الجزء النصي). وتعني الحقول الغائبة أن المنصة لم تحمل البيانات — ولا يؤدي ذلك مطلقًا إلى استدعاء إضافي لـ API المنصة. is_own = الرسالة المقتبسة كتبها البوت الذي يتصدره الموصل (الدليل نفسه المستخدم لعلامة الصلة is_reply_to_bot). ويحوّل الـ gateway هذه القيم إلى حقول سياق الرد نفسها في MessageEvent التي تملؤها adapters الأصلية.

typing content? (مسح حالة Slack). يحذف إطار typing عادةً الحقل content — فيعرض الموصل مؤشر النشاط الخاص بالمنصة (حالة Assistant "is typing…" في Slack ، ومؤشر كتابة لمرة واحدة في غيره). وتكون السلسلة النصية الفارغة content طلبًا صريحًا لـ المسح: ففي Slack يضبط الموصل حالة thread الخاصة بـ Assistant على ""، فيخفيها. ولا يُصدر الـ gateway المسح إلا لـ Slack (الحالة الدائمة)؛ ولا تتلقاه المنصات ذات المؤشر لمرة واحدة مطلقًا. هذا تغيير إضافي ضمن contract_version 1، لكن انتبه إلى ترتيب النشر: فالموصل الأقدم من gateway-gateway #154 يتجاهل content وسوف يضبط "is typing…" عند تلقي إطار مسح — لذا انشر الموصل أولًا.

follow_up (إجراء قدرة A2). تحمل بعض الحمولات الواردة بيانات اعتماد تتصرف بهوية البوت المشتركة (مثل token متابعة تفاعل Discord). ووفق §6 يزيل الموصل هذه البيانات عند الحافة ويربطها في خزينة القدرات بمفتاح الجلسة؛ وهي لا تصل إلى الـ gateway مطلقًا. ولاستخدامها يُصدر الـ gateway follow_up محددًا الجلسة التي يوجد فيها بالفعل (session_key) بالإضافة إلى معرّف القدرة kind (مثل discord.interaction_token) — وليس token مطلقًا. يستخرج الموصل القيمة الفعلية من خزينته، ويفرض تطابق المستأجر (لا يستطيع المستأجر B استخدام قدرة المستأجر A مطلقًا)، ثم يُرسل الطلب الصادر. وتكون النتيجة success: false عند غياب القدرة/انتهاء صلاحيتها أو عدم تطابق المستأجر — ولا يملك الـ gateway أي شيء يعيد المحاولة به، عمدًا (لا تحتفظ gateway مُسرّبة بأي مادة للقدرات). المرجع المعتمد: gateway/relay/transport.py (send_follow_up) + gateway/relay/adapter.py.

5. توجيه المقاطعة (/stop)

  • Gateway → الموصل: send_interrupt(session_key, reason?) يُرسل /stop في منتصف الدور عبر WS الصادر. ويجب على الموصل إلزاميًا تمريره إلى نُسخة gateway التي تشغّل session_key ذلك (ثابت التوجيه).
  • الموصل → gateway: تُسلَّم المقاطعة الواردة لـ session_key كإطار interrupt_inbound عبر WS الصادر للـ gateway (§3: ملاحظة النقل) — ويُوجَّه بين النُسخ عبر relay bus إلى النُسخة التي تحمل socket — ويُمرَّر بواسطة on_interrupt(session_key, chat_id) في adapter إلى آلية المقاطعة الحالية لكل جلسة، مما يلغي ذلك الدور وحده (دون المساس بالنُسخ الأخرى).

يستخدم الاتجاهان WS الصادر للـ gateway: إذ يخرج gateway→الموصل /stop عبره، وتستخدم مقاطعة الموصل→gateway قناة inbound الخلفية نفسها بوصفها حدثًا مطبّعًا.

6. حد الثقة & معالجة الأجسام الموقّعة (A2)

الموصل هو الحد الوحيد للتشفير/الهوية. ولا يعيد الـ gateway التحقق من أي شيء.

تُحسب توقيعات webhook (Discord ed25519، و Twilio HMAC ، و WeCom BizMsgCrypt) على البايتات الخام الدقيقة، وتكون بعض الحمولات مشفّرة بسر مشترك. يتصدر الموصل بوتًا مشتركًا لعدة مستأجرين ويحمل أسرار المنصة لكل مستأجر، ولذلك فهو:

  • يتحقق / يفك التشفير عند الحافة (الموضع الوحيد الذي توجد فيه الأسرار)،
  • يطبع الحمولة إلى MessageEvent (§3),
  • يزيل أي قدرة للهوية المشتركة من الحمولة ويربطها في خزينة القدرات بمفتاح الجلسة (راجع §4 follow_up),
  • يمرّر فقط MessageEvent المنقّى — ولا يمرّر الجسم الموقّع الخام مطلقًا.

لذلك لا يجري الـ gateway أي تحقق من توقيع المنصة/تشفيرها في مسار relay ؛ بل يثق بالحدث المطبّع. وهذا ثابت مفروض لدى الـ gateway (tests/gateway/relay/test_relay_sheds_crypto.py: لا تستورد حزمة relay أي تشفير خاص بالمنصة ولا تستدعيه).

لماذا لا "نمرّر الجسم الموقّع بايتًا ببايت كي يعيد الـ gateway التحقق"؟ هذا النموذج السابق غير متسق عندما تكون gateway المستأجر غير موثوقة وقابلة للاستبدال:

  • سيتطلب إعادة التحقق من Twilio HMAC / تشفير WeCom تسليم الـ gateway سر التوقيع المشترك — وهذا هو التسريب نفسه، ويكون على بوت مشترك تسريبًا بين المستأجرين.
  • تُشفَّر حمولات WeCom بالسر المشترك؛ ويجب على الموصل فك التشفير عند الحافة لمجرد التوجيه، لذا فإن تمرير النص المشفّر سيتطلب مجددًا منح الـ gateway السر.
  • يوجد token تفاعل Discord داخل جسم JSON الموقّع — ولا يمكنك الحفاظ على البايتات وإزالة بيانات الاعتماد في الوقت نفسه؛ فهي البايتات ذاتها.

لذلك يُتخلى عمدًا عن الحفاظ على البايتات: يعيد الموصل تسلسل الحدث المنقّى ويثق به الـ gateway. ويوحّد ذلك أيضًا مستوى التمرير المباشر ومستوى relay — فكلاهما "تحقق عند الحافة → إصدار حدث مطبّع"، ولا يختلفان إلا في النقل. راجع docs/capability-trust-boundary.md (مستودع الموصل: gateway-gateway) للاطلاع على المبررات الكاملة لـ A2 والخزينة من جهة الموصل.

6.1 مصادقة القناة (رابط الموصل⇄gateway نفسه)

يجعل A2 الموصل الحائز الوحيد لأسرار المنصة، بينما قد يكون الـ gateway مُدارًا من العميل ومكشوفًا على الإنترنت؛ لذا تتم مصادقة قناة الموصل⇄gateway نفسها. ويحمل الـ gateway سرًا خاصًا بكل gateway (hermes gateway enroll → الموصل /relay/enroll، أو التزويد الذاتي المُدار → /relay/provision) يصادق ترقية WS الصادرة. ويعتمد مخطط HMAC-SHA256 مع قائمة تحقق متعددة الأسرار للتدوير (من جهة الـ gateway: gateway/relay/auth.py؛ ومن جهة الموصل: src/core/relayAuthToken.ts).

المساربيانات الاعتمادالآلية
ترقية WS من gateway → الموصلسر خاص بكل gatewayترويسة bearer Authorization على ترقية /relay. ويكون الـ token هو base64url(payload:exp:sig) حيث payload = gatewayId و sig = HMAC(payload:exp, secret). يتحقق الموصل ويرفض الترقية (إغلاق 4401) عند عدم التطابق/الغياب/الإلغاء. ويأتي المستأجر المُصادَق عليه من مخزن الموصل، وليس من إطار hello مطلقًا.
الوارد من الموصل → gateway (إطارات inbound / interrupt_inbound)— (يستخدم WS المُصادَق عليه)يُدفَع الوارد عبر socket الصادر الذي صودق عليه بالفعل للـ gateway (§3)، لذا لا حاجة إلى توقيع لكل رسالة. وما زال مفتاح تسليم خاص بكل مستأجر يُصدر عند التسجيل/التزويد ويُحتفظ به للتوافق المستقبلي، لكنه لم يعد يُستخدم لتوقيع الوارد.

هذه أداة مصادقة القناة — وهي مختلفة عن تشفير المنصة الذي ما زال مسار relay يتخلى عنه بالكامل (§6). لا يحمل الـ gateway أي أسرار للمنصة؛ فالسر الخاص بكل gateway يصادق رابط الموصل فقط. نموذج التهديدات الكامل + تصميم التسجيل/التدوير/مفتاح الإيقاف: docs/connector-gateway-auth-design.md (مستودع الموصل).

7. التسليم لكل نُسخة & مستوى الإدارة (المرحلة 6)

تتعامل المراحل 1–5 مع الموصل كواجهة لمستأجر واحد: تتوزع الأحداث الواردة للمستأجر إلى socket أو sockets الـ gateway لذلك المستأجر. وتجعل المرحلة 6 التسليم خاصًا بكل نُسخة — فيستطيع بوت مشترك خدمة عدة مستخدمين/وكلاء ضمن مستأجر واحد (Discord guild واحد، أو بوت Telegram واحد) دون تسليم متبادل — وتضيف مستوى إدارة صغيرًا يستخدمه الوكيل (أو Portal مُدار) لإعلان من يرى ماذا، وما هو ذو صلة. وكل ذلك يوجد لدى الموصل؛ وتقتصر المسؤولية الجديدة للـ gateway على إعلان سياسة الصلة الخاصة به عند بدء التشغيل (§7.3).

7.1 بوابة التسليم (لدى الموصل، للمعلومة)

يقرر الموصل، لكل حدث وارد، النُسخ التي تتلقاه عبر تركيب 3 مرشحات بمنطق AND. لا ينفذ الـ gateway هذه المرشحات — فهي تعمل لدى الموصل — لكنها تحدد دلالات التسليم التي يعتمد عليها الـ gateway:

الطبقةالسؤالالمرجع المعتمد
المالك / النطاق ∧ الطرفهل يجوز لهذه النُسخة رؤية هذا الكاتب هنا؟ارتباطات user_id → instance لكل مستخدم (الحد الأساسي للمالك) + منح نطاق (guild, channel) لكل نُسخة + سياسة الطرف owner-only / allow-list / any.
الحد الأساسي للرؤيةهل يمتلك المالك المرتبط بالنُسخة فعلًا صلاحية VIEW_CHANNEL لرؤية هذا في Discord ؟ACL حي في Discord (الصلاحيات الفعلية)، مع المنع عند الفشل. يضيّق منح النطاق المفرط الاتساع.
الصلةبما أنه يجوز لها رؤيته، فهل ينبغي للوكيل التفاعل؟سياسة الصلة المُعلنة في §7.3 (اشتراط التوجيه / الرد الحر / السماح بالبوتات).

لا يؤدي التركيب إلا إلى تضييق التسليم (deliver ⇔ authorized ∧ visible ∧ relevant)؛ و يتجاوز الحد الأساسي للمالك طبقة الصلة (تصل رسالة الكاتب نفسه دائمًا إلى نُسخته — فأنت لا تستخدم @mention لوكيلك الخاص). ولا تصل رسالة كتبها مستخدم غير مرتبط إلى أي نُسخة (المنع عند الفشل). يوجد التصميم الكامل + الثوابت في مستودع الموصل (NousResearch/gateway-gateway)؛ وهذا القسم ملخص موجّه إلى الـ gateway.

7.2 مسارات الإدارة (لدى الموصل، مُصادَق عليها)

يُركّب الموصل مسارات إدارة مُصادَقًا عليها. وتشترك في المصادقة الثنائية نفسها المستخدمة في ترقية WS: إما RS256 JWT aud=agent:{instanceId} مُدار وموقّع من NAS ، أو bearer السر الخاص بالـ gateway نفسه (§6.1 make_upgrade_token). وفي الحالتين يستخرج الموصل {tenant, instanceId} المعتمد من سجله المخزّن — ولا يستخرجه مطلقًا من جسم الطلب (يُتجاهل instanceId المُدّعى في الجسم).

المسارالغرض
POST /manage/linkإصدار رمز قصير العمر لربط حساب منصة بالنُسخة المُصادَق عليها (مسار /link <code>؛ ويقرأ الموصل user_id الحقيقي من الحدث الوارد).
POST /manage/scope, /manage/scope/releaseالمطالبة بنطاق (guild, channel) / تحريره للنُسخة المُصادَق عليها. تملك القناة نُسخة واحدة على الأكثر (عدم التداخل قيد PK).
POST /manage/principalضبط سياسة الطرف للنُسخة (owner-only | allow-list | any).
POST /manage/dm-defaultضبط نُسخة DM الافتراضية للمستخدم (لفض تعادل DM عندما يربط المستخدم أكثر من نُسخة).

هذه المسارات ملك الموصل (مستوى الإدارة ليس جزءًا من مسار وكيل الـ gateway)؛ ولا يستدعي الـ gateway إلا POST /relay/policy (§7.3). وتُدار المسارات الأخرى عبر Portal المُدار / CLI hermes.

7.3 إعلان سياسة الصلة (مسؤولية الـ gateway)

طبقة الصلة (§7.1) هي المكافئ لكل مستأجر لإعدادات السلوك الخاصة بالـ gateway (require_mention, free_response_channels, {PLATFORM}_ALLOW_BOTS). ولكي يحكم السلوك نفسه تسليم relay ، يُسقط الـ gateway هذه الإعدادات إلى سياسة مستقلة عن المنصة ويرسلها بطلب POST إلى POST /relay/policy عند بدء التشغيل (بعد تحديد السر الخاص بالـ gateway).

الجسم (gateway/relay/__init__.py relay_relevance_policy() → send_relay_policy()):

الحقلالنوعمُسقَط منالمعنى
platformstringالمنصة التي يتصدرها الموصل (relay_platform_identity)المنصة التي تنطبق عليها هذه السياسة.
requireAddressboolrequire_mentionيجب أن تستخدم رسالة غير المالك @mention / الرد على البوت كي تكون ذات صلة.

تستخدم المصادقة token الترقية الخاص بكل gateway (§6.1)، لذا يربط الموصل السياسة بالنُسخة المُصادَق عليها. والـ gateway هو المرجع المعتمد، ويعيد الإعلان عند كل بدء تشغيل (استبدال كامل، يحاكي upsert لـ routeKeys عند التزويد — مع إصلاح ذاتي). عندما تكون السياسة المُسقَطة كلها افتراضية، لا يرسل الـ gateway شيئًا (فالافتراضي لدى الموصل عند غياب الصف يتطابق بالفعل). ويكون POST متسامحًا مع الفشل: يُسجَّل الفشل ويستمر بدء التشغيل — فالصلة تحسين فوق بوابة التفويض (§7.1)، وليست اعتمادًا لبدء التشغيل مطلقًا. ولا يوجد مدخل وارد جديد للـ gateway ولا بيانات اعتماد جديدة — إذ يُعاد استخدام السر الخاص بكل gateway والمضيف نفسه المستخدم في /relay/provision.

يحدث الإسقاط لعدم الصلة قبل أن يوقظ الموصل وكيلًا خُفّض إلى الصفر (المرحلة 5)، لذا لا تشغّل الأحاديث المستبعدة أي وكيل — فالصلة هي الوسيلة الأساسية للتخفيض إلى الصفر، فضلًا عن ضمان الصحة.

الذاكرة الدائمة

يملك Hermes Agent ذاكرة محدودة ومنسَّقة تستمر عبر الجلسات. هذا يتيح له تذكّر تفضيلاتك، ومشاريعك، وبيئتك، والأشياء التي تعلّمها.

كيف تعمل

يتكوّن ذاكرة الوكيل من ملفين:

الملفالغرضحدّ الأحرف
MEMORY.mdالملاحظات الشخصية للوكيل — حقائق البيئة، والاصطلاحات، والأشياء المُتعلَّمة2,200 حرف (~800 token)
USER.mdالملف الشخصي للمستخدم — تفضيلاتك، وأسلوب تواصلك، وتوقعاتك1,375 حرفًا (~500 token)

يُخزَّن كلا الملفين في ~/.hermes/memories/ ويُحقنان في system prompt كلقطة مجمَّدة عند بدء الجلسة. يدير الوكيل ذاكرته بنفسه عبر أداة memory — يمكنه إضافة إدخالات أو استبدالها أو إزالتها.

وكيل واحد لكل Hermes home

لا توجّه عمليتي وكيل إلى نفس دليل Hermes home. كتابات الذاكرة تلقائية وتُحمَّل مجددًا إلى system prompt عند بدء الجلسة، لذا فإن كاتبَين يتشاركان home واحدًا سيراكمان إدخالات كل منهما إلى حالة لم يؤلّفها أيّ منهما (ولا أنت). الذاكرة محصورة النطاق لكل profile بالتصميم — امنح الوكيل الثاني profile خاصًا به، وإذا احتاجا ذاكرة مشتركة، استخدم مزوّد ذاكرة خارجي بدلًا من ذلك.

معلومة

حدود الأحرف تُبقي الذاكرة مركَّزة. الذاكرة لا تُضغَط تلقائيًا: عندما تتجاوز عملية كتابة الحدّ، تُعيد أداة memory خطأً بدلًا من إسقاط الإدخالات بصمت. عندها يُفسح الوكيل المجال بنفسه — بدمج أو إزالة إدخالات في نفس الدور قبل إعادة المحاولة (انظر ماذا يحدث عندما تكون الذاكرة ممتلئة). لاحظ أن replace مقيَّد هو أيضًا بالحدّ: استبدال إدخال بآخر أطول قد يظل يتجاوز الحدّ، لذا يجب تقصير المحتوى الجديد (أو إزالة إدخال آخر) ليتّسع.

كيف تظهر الذاكرة في system prompt

في بداية كل جلسة، تُحمَّل إدخالات الذاكرة من القرص وتُعرَض في system prompt كتلة مجمَّدة:

تتضمن الصيغة:

  • عنوانًا يوضح أي مخزن (MEMORY أو USER PROFILE)
  • نسبة الاستخدام وعدد الأحرف ليعرف الوكيل السعة
  • إدخالات فردية مفصولة بفواصل § (علامة القسم)
  • يمكن أن تكون الإدخالات متعددة الأسطر

نمط اللقطة المجمَّدة: يُلتقط حقن system prompt مرة واحدة عند بدء الجلسة ولا يتغيّر أبدًا في منتصف الجلسة. هذا مقصود — فهو يحافظ على ذاكرة التخزين المؤقت (prefix cache) الخاصة بـ LLM من أجل الأداء. عندما يُضيف الوكيل/يزيل إدخالات ذاكرة أثناء الجلسة، تُحفَظ التغييرات إلى القرص فورًا لكنها لن تظهر في system prompt حتى تبدأ الجلسة التالية. استجابات الأدوات تُظهر دائمًا الحالة الحيّة.

الذاكرة تحتاج حدود جلسات

نظام الذاكرة بأكمله مبني حول لحظة انتهاء الجلسة: يحمل MEMORY.md وUSER.md الأساسيات إلى الجلسة التالية، ويسدّ session_search الفجوات بمجرد زوال السياق القديم. داخل جلسة واحدة، لا سبب يدفع تلك الآلية للعمل — فكل شيء مهم لا يزال في السياق الحيّ، لذا نادرًا ما يستشير الوكيل session_search ويكتفي غالبًا بضغط إدخالات الذاكرة بدلًا من تنسيقها.

هذا مهم على منصات المراسلة (Telegram، Discord، إلخ)، حيث تكون المحادثة عمدًا جلسة مستمرة واحدة تنجو من إعادة التشغيل، وأعطال الـ gateway، وإعادة تشغيل الجهاز. إيقاف تشغيل الجهاز ليلًا لا ينهي الجلسة — فالرسالة التالية تلتقطها بالضبط من حيث توقفت. وإذا لم تُعِد الضبط أبدًا، يمكن أن تستمر محادثة أسابيع كجلسة واحدة: مريح، لكنه يصبح مكلفًا (يعمل الضغط مرارًا على سجل يزداد طولًا) ودورة التعلّم من النسيان ← الاستدعاء من الذاكرة ← البحث في جلسات سابقة نادرًا ما تنطلق أبدًا. الإدخالات الجديدة في الذاكرة تبقى أيضًا غير مرئية للجلسة قيد التشغيل بسبب اللقطة المجمَّدة أعلاه.

ممارسة: شغّل /new عند الحدود الطبيعية — مهمة اكتملت، تغيير موضوع، بداية يوم جديد. كل حدّ هو حين تُثمر الذاكرة: يعيد الوكيل قراءة لقطة MEMORY.md/USER.md المُحدَّثة، ويبدأ من سياق قصير رخيص، ويلجأ إلى session_search عندما يحتاج فعلًا إلى السجل. على CLI يتكفّل هذا بنفسه غالبًا (كل استدعاء جلسة جديدة)؛ أما على gateways فالحدّ متروك لك لتحدثه.

إجراءات أداة الذاكرة

يستخدم الوكيل أداة memory بهذه الإجراءات:

  • add — إضافة إدخال ذاكرة جديد
  • replace — استبدال إدخال موجود بمحتوى مُحدَّث (يستخدم مطابقة سلسلة فرعية عبر old_text)
  • remove — إزالة إدخال لم يعد ذا صلة (يستخدم مطابقة سلسلة فرعية عبر old_text)

لا يوجد إجراء read — يُحقَن محتوى الذاكرة تلقائيًا في system prompt عند بدء الجلسة. يرى الوكيل ذكرياته كجزء من سياق محادثته.

مطابقة السلسلة الفرعية

يستخدم إجراءا replace وremove مطابقة سلسلة فرعية فريدة قصيرة — لست بحاجة إلى نص الإدخال الكامل. معامل old_text يحتاج فقط أن يكون سلسلة فرعية فريدة تحدد إدخالًا واحدًا بالضبط:

إذا طابقت السلسلة الفرعية عدة إدخالات، يُعاد خطأ يطلب مطابقة أكثر تحديدًا.

الهدفان موضَّحان

memory — الملاحظات الشخصية للوكيل

للمعلومات التي يحتاج الوكيل تذكّرها عن البيئة، وسير العمل، والدروس المُستفادة:

  • حقائق البيئة (نظام التشغيل، الأدوات، بنية المشروع)
  • اصطلاحات المشروع وإعداداته
  • غرابات الأدوات والحلول البديلة المُكتشَفة
  • إدخالات يوميات المهام المكتملة
  • المهارات والتقنيات التي نجحت

user — الملف الشخصي للمستخدم

للمعلومات عن هوية المستخدم، وتفضيلاته، وأسلوب تواصله:

  • الاسم، والدور، والمنطقة الزمنية
  • تفضيلات التواصل (موجز مقابل مفصّل، تفضيلات الصيغة)
  • الأمور المزعجة والأشياء الواجب تجنبها
  • عادات سير العمل
  • مستوى المهارة التقنية

ما يجب حفظه مقابل ما يجب تخطّيه

احفظ هذه (استباقيًا)

يحفظ الوكيل تلقائيًا — لست بحاجة إلى الطلب. يحفظ عندما يتعلّم:

  • تفضيلات المستخدم: "أفضّل TypeScript على JavaScript" ← احفظ إلى user
  • حقائق البيئة: "يعمل هذا الخادم بـ Debian 12 مع PostgreSQL 16" ← احفظ إلى memory
  • التصحيحات: "لا تستخدم sudo لأوامر Docker، المستخدم في مجموعة docker" ← احفظ إلى memory
  • الاصطلاحات: "المشروع يستخدم tabs، وعرض سطر 120 حرفًا، وdocstrings بأسلوب Google" ← احفظ إلى memory
  • العمل المكتمل: "تمت هجرة قاعدة البيانات من MySQL إلى PostgreSQL في 2026-01-15" ← احفظ إلى memory
  • الطلبات الصريحة: "تذكّر أن تدوير مفتاح API الخاص بي يحدث شهريًا" ← احفظ إلى memory

تخطَّ هذه

  • معلومات تافهة/بديهية: "سأل المستخدم عن Python" — غامضة جدًا لتكون مفيدة
  • حقائق يسهل إعادة اكتشافها: "يدعم Python 3.12 تعشيش f-string" — يمكن البحث عن هذا في الويب
  • تفريغات بيانات خام: كتل كود كبيرة، ملفات سجلّ، جداول بيانات — كبيرة جدًا للذاكرة
  • أمور عابرة خاصة بالجلسة: مسارات ملفات مؤقتة، سياق تصحيح لمرة واحدة
  • معلومات موجودة أصلًا في ملفات السياق: محتوى SOUL.md وAGENTS.md

إدارة السعة

تملك الذاكرة حدود أحرف صارمة للحفاظ على حدود system prompt:

المخزنالحدّالإدخالات النموذجية
memory2,200 حرف8-15 إدخالًا
user1,375 حرفًا5-10 إدخالات

ماذا يحدث عندما تكون الذاكرة ممتلئة

عند محاولة إضافة إدخال يتجاوز الحدّ، تُعيد الأداة خطأً:

يجب على الوكيل حينها:

  1. قراءة الإدخالات الحالية (المعروضة في استجابة الخطأ)
  2. تحديد الإدخالات التي يمكن إزالتها أو دمجها

  4. ثم add للإدخال الجديد

أمثلة عملية على إدخالات ذاكرة جيدة

الإدخالات المُختصَرة عالية الكثافة المعلوماتية تعمل بشكل أفضل:

منع التكرار

يرفض نظام الذاكرة تلقائيًا الإدخالات المكررة بدقة. إذا حاولت إضافة محتوى موجود بالفعل، يُعيد نجاحًا برسالة "لم يُضَف مكرَّر".

الفحص الأمني

تُفحَص إدخالات الذاكرة بحثًا عن أنماط الحقن والتسريب قبل قبولها، لأنها تُحقَن في system prompt. المحتوى المطابق لأنماط التهديد (حقن الـ prompt، تسريب بيانات الاعتماد، أبواب SSH الخلفية) أو الذي يحتوي أحرف Unicode غير مرئية يُحجَب.

البحث في الجلسات

بالإضافة إلى MEMORY.md وUSER.md، يمكن للوكيل البحث في محادثاته السابقة باستخدام أداة session_search:

  • تُخزَّن جميع جلسات CLI والمراسلة في SQLite (~/.hermes/state.db) مع بحث نصي كامل FTS5
  • استعلامات البحث تُعيد رسائل فعلية من قاعدة البيانات — دون تلخيص من LLM، ودون اقتطاع
  • يمكن للوكيل إيجاد أشياء ناقشها منذ أسابيع، حتى لو لم تكن في ذاكرته النشطة
  • يمكن للوكيل أيضًا التمرير للأمام/للخلف داخل أي جلسة يجدها

انظر أداة بحث الجلسات للأشكال الثلاثة للاستدعاء (الاكتشاف / التمرير / التصفح) وصيغة الاستجابة.

رحلة التعلّم (/journey)

رحلة التعلّم هي عرض زمني لكل ما تعلّمه Hermes — المهارات المحفوظة وإدخالات الذاكرة مرسومة عبر الزمن (الأقدم في الأعلى، الأحدث في الأسفل)، مع مُشغِّل "كوكبة" قابل للتشغيل يعيد تمثيل البناء التراكمي. تُشغِّل نفس بيانات الرسم البياني ثلاث واجهات:

  • CLI الكلاسيكي / المستقل — يعرض hermes journey (الأسماء المستعارة: hermes learning، hermes memory-graph) الخط الزمني في الطرفية. الخيارات: --play يُحرِّك البناء التراكمي (--fps لضبطه)، و--width/--height يتجاوزان حجم العرض، و--no-color يعطّل الألوان، و--json يُفرِّغ بيانات الرسم البياني الخام.
  • TUI — يفتح /journey (الأسماء المستعارة: /learning، /memory-graph) الخط الزمني كطبقة تراكب.
  • تطبيق Desktop — يفتح /journey لوحة Star Map / رسم الذاكرة البياني، عرضًا مرئيًا تفاعليًا لنفس العُقد.

بالإضافة إلى المشاهدة، رحلة التعلّم هي أيضًا حيث تُقلِّم وتصحِّح ما تعلّمه Hermes:

الأمرماذا يفعل
hermes journey listيسرد معرّفات العُقد — أسماء المهارات ومعرّفات memory:<source>:<index> لأجزاء الذاكرة.
hermes journey delete <node> [-y]حذف عُقدة. المهارات تُؤرشَف (قابلة للاستعادة)، وأجزاء الذاكرة تُزال. -y يتخطى التأكيد.
hermes journey edit <node>فتح محتوى العُقدة (ملف SKILL.md الخاص بمهارة أو جزء الذاكرة) في $EDITOR.

نفس الأوامر الفرعية list / delete <id> / edit <id> تعمل من أمر /journey ضمن المحادثة على CLI، وتوفر لوحة desktop تحرير/حذف العُقد مباشرة.

الإعدادات

ضبط كلٍّ من memory_enabled وuser_profile_enabled على false يوقف المخازن المدمَجة تمامًا: تُسقَط أداة memory من المخطط ويُسقَط كتلة إرشاداتها من system prompt، حتى لا يُخبَر النموذج أبدًا عن أداة لا يستطيع استخدامها. مزوّد خارجي مضبوط عبر memory.provider (Hindsight، وMem0، وHoncho، …) غير متأثر ويحتفظ بأدواته الخاصة — استخدم هذا عندما تريد backend ذاكرة من طرف ثالث بدلًا من الملفات المدمَجة. إدراج memory تحت agent.disabled_toolsets هو المفتاح الأثقل: فهو يُخفي أدوات المزوّد الخارجي أيضًا.

مع memory_enabled: false فقط (والملف الشخصي للمستخدم لا يزال مفعّلًا)، تبقى الأداة — فهي تدعم مخزن الملف الشخصي — لكن system prompt يستبدل إرشادات الذاكرة الكاملة بكتلة أضيق خاصة بالملف الشخصي فقط. يعلن مخطط الأداة عن هدف user فقط، وتُرفَض الكتابات المباشرة أو المرحلية إلى MEMORY.md المعطَّل. الإعداد المعاكس يعلن عن memory فقط ويرفض كتابات USER.md.

التحكم في كتابات الذاكرة (write_approval)

افتراضيًا يحفظ الوكيل الذاكرة بحرية — بما في ذلك من مراجعة التحسين الذاتي الخلفية التي تعمل بعد الدور. إذا فضّلت الموافقة على الحفظ أولًا، اضبط memory.write_approval: true. إنه مفتاح تشغيل/إيقاف بسيط يُطبَّق على كلٍّ من الأدوار الأمامية والمراجعة الخلفية:

write_approvalالسلوك
false (الافتراضي)الكتابة بحرية — الحاجز مُعطَّل (السلوك السابق للحاجز).
trueتتطلب موافقة قبل حفظ أي شيء. في CLI التفاعلي، تطلب الكتابات الأمامية موافقتك مضمَّنة (الإدخالات صغيرة بما يكفي لقراءتها كاملة). في كل مكان آخر — منصات المراسلة، والسكربتات، ومراجعة التحسين الذاتي الخلفية — تُوضَع الكتابات مرحلية للمراجعة عبر /memory pending.

لإيقاف تشغيل الذاكرة كليًا (وليس فقط حجبها)، اضبط كلًا من memory_enabled: false وuser_profile_enabled: false. عندما يُعطَّل كلا المخزنين المدمَجين، تُخفى أداة memory المدمَجة تلقائيًا.

راجع الكتابات المرحلية من CLI أو أي منصة مراسلة:

هذا هو الجواب على "حفظ الوكيل افتراضًا خاطئًا عني": اضبط write_approval: true، وكل حفظ — خصوصًا الحفظات الخلفية غير المُطلَب بها — ينتظر رد نعم/لا منك قبل أن يدخل ملفك الشخصي أبدًا.

إشعارات المراجعة الخلفية (display.memory_notifications)

بعد الدور، قد تحفظ مراجعة التحسين الذاتي الخلفية بصمت ذاكرة أو تُحدِّث مهارة. هذه هي حلقة تعلّم Hermes الواعية بالموافقة: التصحيحات المتكررة ودروس سير العمل الدائمة تتحول إلى إدخالات ذاكرة مُختصَرة أو مهارات إجرائية، بينما يمكن لـ write_approval وضع تلك الكتابات مرحليًا للمراجعة قبل أن تؤثر على الجلسات المستقبلية. افتراضيًا يُظهر سطرًا قصيرًا 💾 Memory updated في المحادثة حتى تعرف أن ذلك حدث. تحكّم في مدى ثرثرة ذلك:

القيمةالسلوك
offلا إشعار محادثة. المراجعة تستمر بالتشغيل والكتابة — فقط لا ترى سطرًا لها.
on (الافتراضي)سطر عام، مثل 💾 Memory updated، 💾 Skill 'foo' patched.
verboseيتضمن معاينة مُختصَرة لما تغيّر، مثل 💾 Memory ➕ User prefers terse replies أو مقتطف فرق (diff) للمهارة على شكل "old" → "new".

هذا يحكم فقط إشعار محادثة الـ gateway. المراجعة نفسها، والكتابات إلى مخازن الذاكرة/المهارات لديك، غير متأثرة بهذا الإعداد. اضبطه لكل منصة عبر display.platforms.<platform>.memory_notifications.

دفعات المهارات الناجحة تُسمّي كل عملية مُطبَّقة في كلا الوضعين on وverbose، بما في ذلك كتابات/إزالات الملفات الداعمة وحذف المهارة. الكتابات المرحلية التي تنتظر الموافقة والدفعات المُتراجَع عنها لا تُبلَّغ باعتبارها تغييرات مكتملة. ملخصات الدفعات تستخدم النتائج المُطبَّقة بدلًا من افتراض أن الكتابات المطلوبة قد نُفِّذت.

تشغيل المراجعة على نموذج أرخص (auxiliary.background_review)

تعمل المراجعة على نموذج محادثتك الرئيسي افتراضيًا، بإعادة تشغيل المحادثة — الدافئة أصلًا في ذاكرة الـ prompt المؤقتة، لذا فهي قراءات ذاكرة تخزين مؤقت رخيصة. على نموذج رئيسي مكلف يمكنك تشغيل المراجعة على نموذج أرخص بدلًا من ذلك:

عندما توجّهها إلى نموذج مختلف عن نموذجك الرئيسي، تعمل المراجعة هناك بتكلفة أقل بكثير (~3–5× في القياسات). ولأن نموذجًا مختلفًا لا يمكنه إعادة استخدام ذاكرة تخزين الـ prompt المؤقتة لنموذجك الرئيسي على أي حال، يُعيد الفرع (fork) تلقائيًا تشغيل ملخص مُختصَر للمحادثة (الأدوار الأخيرة حرفيًا + ملخص لما هو أقدم) بدلًا من النص الكامل — لتقليل ما يكتبه إلى ذاكرة التخزين المؤقت الجديدة. الالتقاط يصمد: في الاختبار، كان التقاط الذاكرة مطابقًا والتقاط المهارة شبه مطابق لمراجعة النموذج الرئيسي.

اتركه على auto (أو اضبطه على نموذجك الرئيسي) ولن يتغيّر شيء — تستمر المراجعة بالعمل على النموذج الرئيسي بإعادة التشغيل الكاملة بذاكرة تخزين مؤقتة دافئة.

منطق مراجعة النموذج نفسه

المراجعة التي تستخدم نفس نموذج العملية الأصلية (parent) ترث دائمًا جهد استدلال العملية الأصلية. ضبط auxiliary.background_review.reasoning_effort لا يتجاوز ذلك، سواء كان المسار auto أو يختار صراحة مزوّد/نموذج العملية الأصلية.

إعدادات الاستدلال، وsystem prompt، ولقطة المحادثة الكاملة، وتعريفات الأدوات تبقى مطابقة حرفيًا للعملية الأصلية عند ولادة الفرع حتى تستطيع المراجعة إعادة استخدام بادئة ذاكرة الـ prompt المؤقتة الخاصة بها. تغيير مستوى تفكير المراجعة فقط سيكسر ذلك التطابق. لا يوجد مفتاح جهد مستقل لمراجعات النموذج نفسه.

لتقليل عمل المراجعة دون تغيير جهد المحادثة الرئيسية، اضبط memory.nudge_interval / skills.creation_nudge_interval، أو عطّل المراجعات التلقائية كما هو موضح أدناه، أو وجّه المراجعات إلى نموذج مختلف. مسار النموذج المختلف يستخدم ملخصًا ولا يشارك البادئة الدافئة للعملية الأصلية؛ وعلته المستقلة الخاصة بجهد المهمة موثَّقة في #94825. أدوات التحكم بالتردد والتوجيه هذه لا تفصل استدلال النموذج نفسه.

تعطيل المراجعات التلقائية (enabled)

يمكن أن يستهلك فرع المراجعة حصة معتبرة من إجمالي الـ tokens على المضيفات المشغولة. يمكن للمشغّلين تعطيله دون تصفير فترات التذكير:

مع enabled: false، لا تُطلَق الفروع التلقائية بعد الدور؛ ويستمر /refine اليدوي بالعمل.

يُحفَظ استخدام الفرع في session_model_usage بـ task='background_review' ويُكتَب سطر إكمال إلى agent.log (Background review complete: thread=bg-review calls=… in=… out=… result=…).

السماح بأداة مراجعة إضافية محصورة النطاق بدقة (extra_tools)

يمكن للمراجعة الخلفية استخدام أدوات الذاكرة، وإدارة المهارات، والقراءة فقط للملفات افتراضيًا. إذا وفّر profile ما أداة أخرى آمنة لمراجعة غير مراقَبة، فعِّلها بالاسم:

يجب أن تكون الأداة متاحة أصلًا للوكيل الأصلي (parent)؛ هذا الإعداد يضيفها فقط إلى القائمة البيضاء لوقت تشغيل فرع المراجعة. لا يُفعِّل أدوات عشوائية، والأدوات غير المُدرَجة هنا تبقى مرفوضة. أبقِ القائمة ضيقة وفضّل الأدوات التي تُرحِّل اقتراحًا للمراجعة البشرية بدلًا من تطبيق تغييرات خارجية أو مدمّرة مباشرة. الافتراضي قائمة فارغة.

النماذج المحلية: تنتظر المراجعات وحدة معالجة رسومات (GPU) خاملة (defer)

على مزوّد سحابي، تنتهي المراجعة في ثوانٍ وتعمل جنبًا إلى جنب مع ما تفعله بعد ذلك. عندما يكون وقت تشغيل المراجعة هو خادم llama-server المحلي المُدار (Settings → Local models)، يحتلّ نفس الفرع وحدة معالجة الرسومات (GPU) التي يحتاجها موجّهك (prompt) التالي — لدقائق على نموذج كبير — وإرسال موجّه جديد يُلغي المراجعة، ويهدر التعلّم. لذا على وقت التشغيل المحلي المُدار، تُؤجَّل المراجعات افتراضيًا: تُصفّ عند نهاية الدور وتُنفَّذ بمجرد أن يكون الجهاز هادئًا لفترة استقرار قصيرة. لا شيء في المراجعة نفسها يتغيّر — نفس النموذج، ونفس إعادة تشغيل النسخة الكاملة، ونفس الكتابات — تنتقل فقط لحظة التنفيذ.

القيمةالسلوك
auto (الافتراضي)المراجعات التي يُحلّ وقت تشغيلها إلى الخادم المحلي المُدار تُصفّ وتعمل عند الخمول؛ وكل وقت تشغيل آخر (سحابي، خوادم خارجية) يُطلَق فورًا كالسابق.
neverالسلوك القديم في كل مكان: يُطلَق فورًا عند نهاية الدور، حتى على وحدة معالجة الرسومات المحلية المُدارة.

المراجعات المصفوفة تندمج لكل جلسة (لقطة الدور الأحدث تحل محل اللقطة الأقدم — تُعيد المراجعة تشغيل المحادثة كاملة، لذا لا يُفقَد شيء)، والمراجعة التي يستبقها موجّه جديد تُعاد إلى الصفّ بدلًا من إسقاطها، والمراجعة التي انتظرت أطول من defer_max_age_s تعمل حتى لو لم يخمل الجهاز أبدًا. يعمل /refine الصريح فورًا دائمًا. الصفّ في الذاكرة: المراجعات التي لا تزال معلَّقة عند خروج التطبيق تُسقَط، تمامًا كما كان سيحدث لفرع قيد التشغيل.

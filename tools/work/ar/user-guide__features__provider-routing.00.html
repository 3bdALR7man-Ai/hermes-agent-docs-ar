توجيه المزوّدين (Provider Routing)

عند استخدام OpenRouter كمزوّد LLM، يدعم Hermes Agent توجيه المزوّدين (provider routing) — أي التحكم الدقيق في مزوّدي الذكاء الاصطناعي الفعليين الذين يعالجون طلباتك وكيفية ترتيب أولوياتهم.

يوجّه OpenRouter الطلبات إلى مزوّدين كثيرين (مثل Anthropic و Google و AWS Bedrock و Together AI). ويتيح لك توجيه المزوّدين التحسين من حيث التكلفة أو السرعة أو الجودة، أو فرض متطلبات محددة على المزوّدين.

ملاحظة

يحدّد Nous Portal التوجيه مركزيًا لكل نموذج ولا يقبل تفضيلات المزوّدين التي يحددها المستدعي؛ ولا يرسل Hermes أبدًا الكائن provider إلى Portal، لذا يُتجاهل provider_routing هناك ببساطة.

معلومة

لا ينطبق توجيه المزوّدين إلا عند استخدام OpenRouter. وليس له أي تأثير على Nous Portal أو على الاتصالات المباشرة بالمزوّدين (مثل الاتصال مباشرةً بـ Anthropic API).

الخيارات

sort

يتحكم في كيفية ترتيب OpenRouter للمزوّدين المتاحين لطلبك.

القيمةالوصف
"price"الأرخص أولًا
"throughput"الأسرع من حيث عدد الـ tokens في الثانية أولًا
"latency"الأقل زمنًا حتى أول token أولًا

only

قائمة سماح بمعرّفات المزوّدين (slugs). عند ضبطها، لن يُستخدم سوى هؤلاء المزوّدين، ويُستبعد جميع الآخرين. استخدم المعرّف بالأحرف الصغيرة الذي يعرضه OpenRouter لكل مزوّد.

ignore

قائمة حظر بأسماء المزوّدين. هؤلاء المزوّدون لن يُستخدموا أبدًا، حتى لو قدّموا الخيار الأرخص أو الأسرع.

order

ترتيب صريح للأولوية. يُفضَّل المزوّدون المذكورون أولًا، ويُستخدم المزوّدون غير المذكورين كخيارات احتياطية (fallback).

require_parameters

عند ضبطه على true، لن يوجّه OpenRouter الطلبات إلا إلى المزوّدين الذين يدعمون جميع المعاملات في طلبك (مثل temperature و top_p و tools وغيرها). وهذا يمنع إسقاط المعاملات بصمت.

data_collection

يتحكم في ما إذا كان يحق للمزوّدين استخدام الـ prompts الخاصة بك في التدريب. والخيارات هي "allow" أو "deny".

تجاوزات خاصة بكل نموذج (models)

ثبّت مجموعة مزوّدين مختلفة لكل نموذج. المفاتيح تحت models هي معرّفات النماذج؛ ويقبل كل إدخال المفاتيح نفسها sort / only / ignore / order / require_parameters / data_collection ويتجاوز القيمة العامة لذلك النموذج فقط. وأي شيء لا تضبطه لكل نموذج على حدة يعود إلى القيم الافتراضية العامة.

المطابقة متسامحة مع اختلاف التهجئة كما في agent.reasoning_overrides (claude-fable-5.1 / claude-fable-5-1، مع البادئة openrouter/ أو بدونها). ويتبع التجاوز النموذج الذي يعمل عليه الوكيل حاليًا، لذا فإن التبديل عبر /model وتفعيل النموذج الاحتياطي ومهام cron والـ subagents المفوَّضة على نموذج آخر يحصل كلٌّ منها على تثبيتاته الخاصة. حرّر config.yaml مباشرةً لهذه المفاتيح: فمعرّفات النماذج تحتوي على نقاط، يقرؤها hermes config set على أنها فواصل مسارات.

آلية العمل

تُمرَّر تفضيلات توجيه المزوّدين إلى OpenRouter في طلبات محادثة الوكيل وفي ملخصات بلوغ حدّ التكرارات عبر الحقل extra_body.provider. (extra_body هو وسيط في OpenAI Python SDK؛ ويتحوّل إلى الكائن provider في المستوى الأعلى من طلب JSON.) أما المهام المساعدة مثل الضغط وتوليد العناوين فتُضبط بشكل مستقل تحت auxiliary.<task>.extra_body.

  • وضع CLI — يُضبط في ~/.hermes/config.yaml، ويُحمَّل عند بدء التشغيل
  • وضع Gateway — ملف الإعدادات نفسه، ويُحمَّل عند بدء تشغيل الـ gateway

السلوك الافتراضي

عندما لا يكون قسم provider_routing مضبوطًا (وهو الوضع الافتراضي)، يستخدم المُجمِّع (aggregator) منطق التوجيه الافتراضي الخاص به، والذي يوازن عمومًا بين التكلفة والتوافر تلقائيًا.

توجيه المزوّدين مقابل النماذج الاحتياطية

يتحكم توجيه المزوّدين في المزوّدين الفرعيين خلف OpenRouter الذين يعالجون طلباتك. أما للتحويل التلقائي إلى مزوّد مختلف تمامًا عند فشل نموذجك الأساسي، فراجع المزوّدون الاحتياطيون (Fallback Providers).

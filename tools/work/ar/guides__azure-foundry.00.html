Microsoft Foundry

تستخدم أوامر اعتماديات Python في هذه الصفحة نسخة مصدر مسحوبة ومهيّأة بواسطة PM. بعد تغيير الاعتماديات، أعد تفعيل النسخة المسحوبة وأعد تشغيل Hermes.

يدعم المزوّد azure-foundry في Hermes Agent كلًّا من Microsoft Foundry (المعروفة سابقًا باسم Azure AI Foundry) و Azure OpenAI. ويمكن لمورد Foundry واحد استضافة نماذج بصيغتي نقل مختلفتين (wire formats):

  • نمط OpenAI — POST /v1/chat/completions على endpoints مثل https://<resource>.openai.azure.com/openai/v1. ويُستخدم مع GPT-4.x، و GPT-5.x، و Llama، و Mistral، ومعظم النماذج مفتوحة الأوزان.
  • نمط Anthropic — POST /v1/messages على endpoints مثل https://<resource>.services.ai.azure.com/anthropic. ويُستخدم عندما تقدّم Microsoft Foundry نماذج Claude بصيغة Anthropic Messages API.

يستكشف معالج الإعداد الـ endpoint لديك ويكتشف تلقائيًا بروتوكول النقل (transport) الذي يستخدمه، والـ deployments المتاحة، وطول السياق لكل نموذج.

المتطلبات المسبقة

  • مورد Microsoft Foundry أو Azure OpenAI يحتوي على deployment واحد على الأقل
  • رابط endpoint الخاص بالـ deployment
  • إما مفتاح API (من Azure Portal ضمن "Keys and Endpoint") أو دور RBAC ‏Azure AI User على مورد Foundry إذا كنت تخطط لاستخدام Microsoft Entra ID (المسار دون مفاتيح الذي توصي به Microsoft). وقد تعرض بعض المستأجرين (tenants) هذا الدور باسم Foundry User خلال فترة طرح Microsoft لإعادة التسمية.

البدء السريع

سيقوم المعالج بما يلي:

  1. فحص مسار الرابط — يُتعرَّف على الروابط المنتهية بـ /anthropic على أنها مسارات Claude في Microsoft Foundry.
  2. استكشاف GET <base>/models — إذا أعاد الـ endpoint قائمة نماذج بتنسيق OpenAI، ينتقل Hermes إلى chat_completions ويملأ منتقيًا مسبقًا بمعرّفات الـ deployments المُعادة.
  3. استكشاف تنسيق Anthropic Messages — خيار احتياطي للـ endpoints التي لا تتيح /models لكنها تقبل تنسيق Anthropic Messages.
  4. الرجوع إلى الإدخال اليدوي — تظل الـ endpoints الخاصة/المقيّدة التي ترفض كل عمليات الاستكشاف تعمل؛ إذ تختار وضع الـ API وتكتب اسم الـ deployment يدويًا.

يُحدَّد طول السياق للنموذج المختار عبر سلسلة البيانات الوصفية القياسية في Hermes (models.dev، والبيانات الوصفية للمزوّد، والقيم الاحتياطية الثابتة لكل عائلة نماذج) ويُخزَّن في config.yaml حتى يتمكن النموذج من تحديد حجم الـ context window الخاص به بشكل صحيح.

Microsoft Entra ID (دون مفاتيح، RBAC) — موصى به

توصي Microsoft بـ المصادقة دون مفاتيح باستخدام Microsoft Entra ID لأحمال عمل Foundry في بيئة الإنتاج. ويدعم Hermes استخدام Entra ID مع كلتا واجهتي الـ API:

  • نمط OpenAI (api_mode: chat_completions / codex_responses) — GPT-4/5، و Llama، و Mistral، و DeepSeek، وغيرها.
  • نمط Anthropic (api_mode: anthropic_messages) — نماذج Claude على Microsoft Foundry.

يُطبَّق RBAC في Foundry على مستوى كل مورد (يمنح Azure AI User الوصول إلى الواجهتين معًا؛ وقد تعرض بعض المستأجرين Foundry User)، وتوثّق Microsoft نطاق الـ inference نفسه (https://ai.azure.com/.default) لكلتيهما. أما من الداخل:

  • يستخدم نمط OpenAI عقد api_key= القابل للاستدعاء (callable) المدعوم أصلًا في OpenAI Python SDK — إذ يُصدر الـ SDK رمز JWT جديدًا لكل طلب تلقائيًا.
  • يستخدم نمط Anthropic كائن httpx.Client مع hook لأحداث الطلب يثبّته agent.azure_identity_adapter.build_bearer_http_client، لأن Anthropic SDK لا يقبل auth_token قابلًا للاستدعاء بشكل أصيل. يعيد الـ hook كتابة Authorization: Bearer <fresh-jwt> لكل طلب صادر. RBAC نفسه من Microsoft، ونطاق Foundry نفسه — والفرق الوحيد هو عقد الـ SDK.

لماذا تستخدم Entra ID؟

  • لا توجد مفاتيح API طويلة الأجل تحتاج إلى تبديلها أو إبطالها.
  • وصول قائم على RBAC — امنح Azure AI User على مورد Foundry أو اسحبه، دون الحاجة إلى إعادة كتابة الإعدادات.
  • تُقسَّم سجلات الوصول والتدقيق بحسب الجهة المُسنَد إليها الدور، بدلًا من أن يتشارك جميع المستدعين مفتاحًا ثابتًا واحدًا.
  • واجهة مصادقة واحدة لكلٍّ من Azure VMs، و AKS pods، و App Service، و Functions، و Container Apps، و Foundry Agent Service عبر الهوية المُدارة (managed identity).
  • مسارات workload identity و service principal لـ CI/CD pipelines.

إعداد لمرة واحدة (من جهة Azure)

  1. في Azure Portal، افتح مورد Foundry لديك → Access control (IAM) → Add → Add role assignment.
  2. اختر الدور Azure AI User (أو Foundry User إذا كان المستأجر لديك يعرض الدور بالاسم الجديد).
  3. أسنده إلى:
    • حساب المستخدم الخاص بك للتطوير المحلي باستخدام az login.
    • هوية مُدارة أو workload identity لموارد الحوسبة المستضافة على Azure (موصى به لبيئة الإنتاج).
    • هوية الوكيل الخاصة بوكيل مستضاف في Foundry Agent Service عندما يعمل Hermes داخل وكيل مستضاف.
    • service principal لـ CI/CD pipelines عندما لا تتوفر workload identity.
  4. انتظر نحو 5 دقائق حتى ينتشر الدور.

الإعدادات المكتوبة في config.yaml

لا يدير Hermes سوى إعداد واحد خاص بـ Entra في config.yaml:

  • scope — نطاق مورد OAuth. قيمته الافتراضية هي نطاق الـ inference الموثّق من Microsoft (https://ai.azure.com/.default). لا تغيّره إلا إذا كان موردك قد جُهّز لجمهور (audience) غير قياسي.

أما كل ما عدا ذلك (المستأجر، وسرّ الـ service principal، وملف الـ federated token، وجهة الإصدار (authority) للسحابة السيادية، وتفضيلات الـ broker) فيقرؤه azure-identity مباشرةً من متغيرات البيئة القياسية AZURE_* — راجع ترتيب تحديد بيانات الاعتماد أدناه. اضبطها في ~/.hermes/.env أو في بيئة النشر لديك، تمامًا كما يصف مرجع SDK من Microsoft.

لا تُحفظ أي أسرار في ~/.hermes/.env في وضع Entra — إذ يخزّن azure-identity الـ tokens مؤقتًا داخل العملية (وفي سلسلة مفاتيح نظام التشغيل / ~/.IdentityService حيثما كان ذلك متاحًا).

ترتيب تحديد بيانات الاعتماد

azure-identity، تمرّ DefaultAzureCredential على هذه السلسلة مع كل طلب token، وتتوقف عند أول بيانات اعتماد تُعيد token:

  1. Environment credential — AZURE_TENANT_ID + AZURE_CLIENT_ID + AZURE_CLIENT_SECRET (أو AZURE_CLIENT_CERTIFICATE_PATH / AZURE_FEDERATED_TOKEN_FILE).
  2. Workload Identity — AZURE_FEDERATED_TOKEN_FILE (‏federated tokens في AKS / OIDC).
  3. Managed Identity — endpoint ‏IMDS (169.254.169.254) للأجهزة الافتراضية؛ و IDENTITY_ENDPOINT لـ App Service / Functions / Container Apps. أما الوكلاء المستضافون في Foundry Agent Service فيستخدمون هوية الوكيل الخاصة بالوكيل المستضاف.
  4. Visual Studio Code — إضافة Azure account.
  5. Azure CLI — جلسة az login.
  6. Azure Developer CLI — azd auth login.
  7. Azure PowerShell — Connect-AzAccount.
  8. Broker (على Windows / WSL فقط) — Web Account Manager.

تُستثنى بيانات الاعتماد التفاعلية عبر المتصفح افتراضيًا في تشغيلات Hermes غير المراقَبة؛ لذا استخدم بدلًا منها Azure CLI، أو Azure Developer CLI، أو الهوية المُدارة، أو workload identity، أو بيانات اعتماد service principal.

profiles المتعددة (gateway.multiplex_profiles: true): يُحدَّد كل مصدر في تلك السلسلة انطلاقًا من العملية — أي قيم AZURE_* الخاصة بـ profile الإطلاق، وجلسة az login الخاصة به، والهوية المُدارة للمضيف. لذلك يُرفض profile مخدوم لا يضبط أي قيم AZURE_* خاصة به بدلًا من استعارة هوية الإطلاق (وهي القاعدة نفسها التي يطبّقها محوّل Vertex على Application Default Credentials). أعطِ كل profile قيمة خاصة به لـ AZURE_TENANT_ID + AZURE_CLIENT_ID + AZURE_CLIENT_SECRET (أو AZURE_FEDERATED_TOKEN_FILE) في .env; AZURE_CLIENT_ID وحدها اشتراك ذلك profile في الهوية المُدارة المعيّنة من المستخدم على المضيف. أما التشغيل بـ profile واحد (hermes, hermes -p beta) فيحتفظ بالسلسلة كاملة.

أنماط النشر

التطوير المحلي:

Azure VM / Functions / App Service / Container Apps (هوية مُدارة يعيّنها النظام):

  1. فعّل الهوية التي يعيّنها النظام (system-assigned) على مورد الحوسبة.
  2. امنح الهوية الدور Azure AI User (أو Foundry User) على مورد Foundry.
  3. اضبط model.auth_mode: entra_id في config.yaml — دون الحاجة إلى متغيرات بيئة.

Azure VM / Functions / App Service / Container Apps (هوية مُدارة يعيّنها المستخدم):

  • اضبط AZURE_CLIENT_ID على معرّف العميل (client ID) الخاص بالهوية التي يعيّنها المستخدم (user-assigned) حتى تختار DefaultAzureCredential الهوية الصحيحة.

وكيل مستضاف في Foundry Agent Service:

  • أنشئ الوكيل المستضاف وامنح هوية ذلك الوكيل الدور Azure AI User (أو Foundry User) على مورد Foundry. يستخدم Hermes ‏ManagedIdentityCredential من داخل الوكيل المستضاف؛ ويجب أن يُسنَد الدور إلى هوية الوكيل، لا إلى المشروع الأب أو المستخدم الخاص بك فقط.

AKS Workload Identity (بديلًا عن AAD Pod Identity):

  • أضف إلى حساب الخدمة (service account) الخاص بالـ pod تعليقًا توضيحيًا (annotation) بمعرّف العميل الخاص بالـ workload identity.
  • يُكتشف ملف الـ federated token الخاص بالـ pod تلقائيًا عبر AZURE_FEDERATED_TOKEN_FILE.
  • model.auth_mode: entra_id دون أي تغييرات إضافية في الإعدادات.

service principal في CI:

  • اضبط AZURE_TENANT_ID، و AZURE_CLIENT_ID، و AZURE_CLIENT_SECRET في بيئة الـ runner.

السحابات السيادية (Government، China)

صدّر AZURE_AUTHORITY_HOST (مثل https://login.microsoftonline.us لـ Azure Government، و https://login.partner.microsoftonline.cn لـ Azure China). ويقرؤه azure-identity مباشرةً.

فحوصات السلامة

hermes doctor اختبارًا مدته 10 ثوانٍ على DefaultAzureCredential عندما يكون model.auth_mode: entra_id مضبوطًا، ويُبلغ عن بيانات الاعتماد الداخلية التي نجحت (وجود متغيرات البيئة، وإمكانية الوصول إلى endpoint الهوية المُدارة، وغير ذلك).

hermes auth كتلة حالة منظّمة:

تعيد المهام المساعدة التي تتبع النموذج الرئيسي (provider: auto — عناوين الجلسات، وضغط السياق، والموافقة الذكية) استخدام مزوّد token الخاص بـ Entra للجلسة الرئيسية بدلًا من إعادة المصادقة؛ وتظل قيمة --api-key النصية في CLI تتجاوزه للاختبار لمرة واحدة.

القيود

  • تستخدم endpoints نمط Anthropic ‏event hook من httpx. لا يقبل Anthropic Python SDK قيمة auth_token قابلة للاستدعاء بشكل أصيل (≤ 0.86.0). لذا يثبّت Hermes ‏hook لأحداث الطلب على httpx.Client مخصص يُصدر رمز JWT جديدًا لكل طلب صادر ويعيد كتابة Authorization: Bearer <jwt>. وهذا مكافئ وظيفيًا لعقد Callable[[], str] الأصيل في OpenAI SDK، لكنه يضيف طبقة وسيطة واحدة. وإذا أضاف Anthropic SDK دعمًا كاملًا للمصادقة القابلة للاستدعاء في إصدار مستقبلي، فسينتقل Hermes إليه بشفافية.
  • المهام الدفعية و multiprocessing.Pool. مزوّد token الخاص بـ Entra عبارة عن closure لا يمكن تسلسله (pickle) عبر حدود العمليات. لذا يُسقط batch_runner.py تلقائيًا الكائن القابل للاستدعاء من إعدادات الـ worker، ويترك كل عملية worker تعيد بناء المزوّد الخاص بها من config.yaml — دون أي إجراء من المستخدم، لكن كل worker يمرّ على السلسلة مرة واحدة عند بدء التشغيل.
  • لا يُحفظ bearer JWT في auth.json. لا يكرّر Hermes الـ cache الداخلي للـ tokens في azure-identity؛ وفي حالات البدء البارد (cold start) يمرّ على سلسلة بيانات الاعتماد عند أول عملية inference.

وفي ~/.hermes/.env:

Endpoints بنمط OpenAI (GPT، و Llama، وغيرها)

يقبل endpoint الإصدار v1 العام (GA) في Azure OpenAI عميل Python القياسي openai مع تغييرات طفيفة:

سلوك مهم:

  • تُوجَّه نماذج GPT-5.x و codex وسلسلة o تلقائيًا إلى Responses API. تنشر Microsoft Foundry نماذج GPT-5 / codex / o1 / o3 / o4 بحيث لا تعمل إلا عبر Responses API — واستدعاء /chat/completions عليها يُعيد 400 "The requested operation is unsupported.". يكتشف Hermes عائلات النماذج هذه من أسمائها ويرقّي api_mode إلى codex_responses بشفافية، حتى عندما يظل config.yaml يحتوي على api_mode: chat_completions. أما GPT-4، و GPT-4o، و Llama، و Mistral، وغيرها من الـ deployments فتبقى على /chat/completions.
  • api_mode: responses مقبولة كصيغة بديلة لـ codex_responses. يعمل الاسم البديل على model.api_mode، وفي إدخالات fallback_providers، وفي auxiliary.<task>.api_mode الخاصة بكل مهمة (مثل مسار auxiliary.vision إلى نشر GPT-5.x)، ويختار محوّل Responses نفسه.
  • max_completion_tokens تلقائيًا. يتطلب Azure OpenAI (مثل OpenAI المباشر) المعامل max_completion_tokens لنماذج gpt-4o وسلسلة o و gpt-5.x. ويرسل Hermes المعامل الصحيح بناءً على الـ endpoint.
  • الـ endpoints السابقة للإصدار v1 التي تتطلب api-version. إذا كان لديك رابط أساسي قديم مثل https://<resource>.openai.azure.com/openai?api-version=2025-04-01-preview، يستخرج Hermes سلسلة الاستعلام ويمرّرها عبر default_query مع كل طلب (وإلا فإن OpenAI SDK يُسقطها عند ضمّ المسارات).

Endpoints بنمط Anthropic (Claude عبر Microsoft Foundry)

بالنسبة إلى deployments الخاصة بـ Claude، استخدم المسار بنمط Anthropic:

سلوك مهم:

  • /v1 من الرابط الأساسي. يُلحق Anthropic SDK المسار /v1/messages بكل رابط طلب — لذا يزيل Hermes أي /v1 في نهاية الرابط قبل تسليمه إلى الـ SDK لتجنّب المسارات التي يتكرر فيها /v1.
  • api-version عبر default_query، ولا يُلحق بالرابط. يتطلب Azure Anthropic سلسلة استعلام api-version. ودمجها في الرابط الأساسي يُنتج مسارات تالفة مثل /anthropic?api-version=.../v1/messages ويُعيد 404. لذا يمرّر Hermes ‏api-version=2025-04-15 عبر default_query في Anthropic SDK بدلًا من ذلك.
  • تُستخدم مصادقة Bearer بدلًا من x-api-key. يتطلب مسار Azure المتوافق مع Anthropic الترويسة Authorization: Bearer <key> بدلًا من الترويسة الأصيلة في Anthropic x-api-key. يكتشف Hermes وجود azure.com في الرابط الأساسي ويوجّه مفتاح API عبر الحقل auth_token في الـ SDK حتى تصل الترويسة الصحيحة إلى الخادم الوجهة.
  • يُحتفظ بترويسة beta الخاصة بـ context window بحجم 1M. لا يزال Azure يقيّد سياق Claude بحجم 1M token ‏(Opus 4.6/4.7، و Sonnet 4.6) خلف الترويسة anthropic-beta: context-1m-2025-08-07. ويحتفظ Hermes بترويسة beta هذه على مسارات Azure (وتُحذف من طلبات Anthropic OAuth الأصيلة لأن بعض الاشتراكات ترفضها، لكن Azure يتطلبها).
  • تجديد OAuth token معطّل. تستخدم deployments في Azure مفاتيح API ثابتة. وتُتخطّى صراحةً حلقة تجديد OAuth token الخاصة بـ ~/.claude/.credentials.json والمطبّقة على Anthropic Console عند استخدام endpoints في Azure، وذلك لمنع OAuth token الخاص بـ Claude Code من الكتابة فوق مفتاح Azure في منتصف الجلسة.
  • hermes doctor يفحص المسار نفسه. لا يملك المسار /anthropic نقطة GET /models، ولذلك يرسل فحص الاتصال طلب POST /v1/messages بـ token واحد، وبمصادقة Bearer نفسها ومعامل الاستعلام api-version الذي تستخدمه بيئة التشغيل؛ وتفيد استجابة 200 (أو 400 من Messages API) بأن endpoint سليمة، بينما تفيد 401/403 بمشكلة مصادقة.

بديل: provider: anthropic + رابط Azure الأساسي

إذا كان لديك provider: anthropic مضبوطًا مسبقًا وتريد فقط توجيهه إلى Microsoft Foundry لاستخدام Claude، فيمكنك الاستغناء عن المزوّد azure-foundry كليًا:

مع ضبط AZURE_ANTHROPIC_KEY في ~/.hermes/.env. يكتشف Hermes وجود azure.com في الرابط الأساسي ويتجاوز سلسلة OAuth token الخاصة بـ Claude Code، بحيث يُستخدم مفتاح Azure مباشرةً مع مصادقة x-api-key.

key_env هو اسم الحقل القياسي بصيغة snake_case؛ وتُقبل api_key_env (وكذلك صيغتا camelCase keyEnv / apiKeyEnv) كأسماء بديلة. وإذا ضُبط كلٌّ من key_env و AZURE_ANTHROPIC_KEY/ANTHROPIC_API_KEY، فالأولوية لمتغير البيئة الذي يحمل الاسم المحدد في key_env.

اكتشاف النماذج

يوفر Azure لا يوفّر Azure أي endpoint يعتمد على مفتاح API وحده لسرد deployments النماذج المنشورة لديك. إذ يتطلب سرد الـ deployments مصادقة Azure Resource Manager ‏(az cognitiveservices account deployment list) بجهة Azure AD، وليس مفتاح API الخاص بالـ inference.

ما يستطيع Hermes فعله:

  • تتيح endpoints الإصدار v1 من Azure OpenAI ‏(<resource>.openai.azure.com/openai/v1) المسار GET /models مع كتالوج النماذج المتاحة للنماذج. يستخدم Hermes هذه القائمة لملء منتقي النماذج في معالج الإعداد و منتقي /model azure-foundry داخل الجلسة (CLI و TUI و Desktop و gateway)، لتتمكن من التبديل بين عمليات النشر دون إعادة تشغيل hermes setup.
  • مسارات /anthropic: تُكتشف المسارات من مسار URL، ويُدخل اسم النموذج يدويًا (لا توجد /models هناك — يعرض منتقي /model الاختيار الحالي فقط وأي قيم providers.azure-foundry.models تعلنها).
  • الـ endpoints الخاصة / المحمية بجدار ناري: إدخال يدوي مع رسالة ودّية "couldn't probe".
  • Entra ID (model.auth_mode: entra_id، دون AZURE_FOUNDRY_API_KEY): يسرد منتقي /model المزوّد بمجرد ضبط model.base_url (أو AZURE_FOUNDRY_BASE_URL) — ولا يُنشأ token لمجرد إظهار الصف.

يمكنك دائمًا كتابة اسم نشر مباشرةً — لا يتحقق Hermes من مطابقته للقائمة المُعادة.

لقصر المنتقي على عمليات النشر التي تستخدمها فعلًا (قد يكون الكتالوج طويلًا)، أو لسردها لـ endpoint دون /models، أعلنها في config.yaml؛ وستُدرج أولًا قبل الكتالوج المباشر:

يحدد منتقي وقت التشغيل endpoint من model.base_url عندما يكون Azure Foundry هو المزوّد النشط؛ واضبط AZURE_FOUNDRY_BASE_URL أيضًا إذا أردت بقاء الصف معبّأً بعد التبديل إلى مزوّد آخر.

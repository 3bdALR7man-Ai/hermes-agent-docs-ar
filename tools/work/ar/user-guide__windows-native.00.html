دليل Windows (التشغيل الأصلي)

يعمل Hermes أصليًا على Windows 10 و Windows 11 — دون WSL، ودون Cygwin، ودون Docker. تتعمق هذه الصفحة في التفاصيل: ما الذي يعمل أصليًا، وما المتاح في WSL فقط، وما الذي يفعله المُثبّت (installer) فعليًا، وخيارات الضبط الخاصة بـ Windows التي قد تحتاج إلى تعديلها.

إذا كنت تريد التثبيت فحسب، فالأمر المكوّن من سطر واحد في الصفحة الرئيسية أو في صفحة التثبيت هو كل ما تحتاج إليه. عُد إلى هنا حين يفاجئك شيء ما.

هل تفضّل WSL بدلًا من ذلك؟

إذا كنت تفضّل بيئة POSIX لدلالات fork أو أدوات مراقبة الملفات بأسلوب Linux، فراجع دليل Windows (WSL2). يتعايش الخياران دون تعارض: تُخزَّن بيانات التثبيت الأصلي ضمن %LOCALAPPDATA%\hermes، بينما تُخزَّن بيانات WSL ضمن ~/.hermes.

التثبيت السريع

افتح PowerShell (أو Windows Terminal) ونفّذ:

لا حاجة إلى صلاحيات المسؤول. يُثبَّت Hermes في %LOCALAPPDATA%\hermes\ ويُضيف المُثبّت hermes إلى User PATH الخاص بك — افتح طرفية جديدة بعد انتهائه.

MSIX / App Installer و Microsoft Store

تطبيق سطح المكتب المضمّن منفصل عن سكربت المصدر. تتطلب حزمة MSIX الخاصة به Windows 11 22H2 أو أحدث. لا يعني دعم Windows 10 في سكربت المصدر أن حزمة MSIX تدعم Windows 10.

افتح ملف .appinstaller الذي نزّلته باستخدام Windows App Installer. يثبّت حزمة موحّدة موقّعة ويسجّل مصدر التحديث. تتضمن الحزمة Python و Node والاعتماديات المدعومة والواجهات المبنية مسبقًا. ولا تستنسخ نسخة مصدر أو تبني بيئة التشغيل الأساسية عند التشغيل الأول.

تتيح أسماء التنفيذ البديلة في MSIX الأوامر hermes, hermes-agent و hermes-acp. إذا حجب تثبيت آخر اسمًا بديلًا، فافحص Get-Command hermes -All. تتحكم Windows Settings → Apps → Advanced app settings → App execution aliases في الأسماء البديلة.

تستخدم تحديثات التثبيت الجانبي عنصر Update في التطبيق و Windows App Installer. ينزّل Hermes واصفًا محليًا قبل الإيقاف ويسجّل إعادة تشغيل تلقائية. لا يتطلب بروتوكول URL ms-appinstaller:. ليست نتيجة فحص تحديث مجهولة دليلًا على أن الحزمة محدّثة.

تستخدم نسخة Microsoft Store هوية حزمتها في Partner Center وتحديثات Store. لا تستخدم قناة التثبيت الجانبي. أمر hermes update داخل أي من بيئتَي التشغيل المضمّنتين لا يشغّل Git على ملفات الحزمة.

Hermes-Setup.exe مُثبّت bootstrap مختلف. يُعدّ نسخة مصدر مسحوبة عبر السكربتات. لا تخلط بينه وبين حزمة MSIX المكتفية بذاتها. راجع التحديث وإلغاء التثبيت.

تهيئة الاعتماديات

يدير PM الأدوات المُدارة. يطلب كود الميزة من PM الحزمة اللازمة (pm.ensure("<package>")، مثل cua-driver لـ Computer Use) بدلًا من إعادة تشغيل المُثبّت. يُعاد استخدام الأدوات المثبّتة من الحالة التي سجّلها PM؛ ولا تُجلب أداة اختيارية مفقودة عند الطلب إلا عندما تسمح بذلك security.allow_lazy_installs. لا يوجد لدى install.ps1 وضع -Ensure.

ما يفعله مُثبّت المصدر

  1. يعثر على Git، أو يهيّئ الإصدار المثبَّت المتحقَّق منه من Git for Windows عند غياب Git.
  2. يستنسخ branch المستودع المختار ويطبّق تثبيتًا اختياريًا على commit محدّد.
  3. يهيّئ uv وينشئ بيئة Python الأولية.
  4. يشغّل PM لتوفير Python 3.14 والأدوات المطلوبة وإضافة Python all.
  5. ينشئ مشغّلات CLI في مجلد bin داخل مجلد البيانات الرئيسي ويضيفه إلى User PATH.
  6. يجهّز الإعدادات ويستدعي مرحلتي الإعداد و gateway التفاعليتين ما لم تتجاوزهما.
  7. يبني تطبيق سطح المكتب وينشئ اختصارات Start Menu/Desktop إذا طُلب ذلك.
  8. يكتب علامة اكتمال bootstrap.

ينفّذ مشغّل بيئة التشغيل Python الموجود في متجر PM ويختار بيئة الاعتماديات قبل الاستيراد. يمكن لـ PM نشر بيئة جديدة قابلة للكتابة دون استبدال مكتبات حمّلتها عملية جارية بالفعل. لا يوجد fallback متدرّج لـ pip يقلّص مجموعة الميزات المثبّتة بصمت.

تجنّب البحث عن المزوّدين على Windows

في Windows، يُعد إعداد مفتاح API لكل أداة على حدة (Firecrawl و FAL و Browser Use و OpenAI TTS) الجزء الأكثر إرهاقًا في الحصول على وكيل مفيد. يغطي اشتراك Nous Portal النموذج و كل تلك الأدوات عبر تسجيل دخول واحد بـ OAuth. بعد انتهاء المُثبّت، نفّذ hermes setup --portal لربط كل شيء.

كيف ينفّذ Hermes أوامر الـ shell على Windows

تنفّذ أداة الطرفية في Hermes الأوامر عبر Git Bash، وهي الاستراتيجية نفسها التي يتبعها Claude Code. يتفادى ذلك الفجوة بين POSIX و Windows دون إعادة كتابة كل أداة.

pm.shell() مسؤول عن تحديد Bash. يفحص أولًا حزمة Git المسجّلة في حقائق PM، ثم PATH المُعدّ. إذا كان أحد المرشحين في PATH تابعًا لحزمة WindowsApps، يفضّل المحدّد تثبيتًا تقليديًا لـ Git for Windows عند توافره.

الأدوات المحزّمة ليست تثبيتات عامة الاستخدام على المضيف. قد تفشل عملية Python خارجية في تشغيل ملف تنفيذي من محتويات WindowsApps بخطأ WinError 5. استخدم مشغّل الحزمة نفسه، أو أدوات تقليدية لنسخة مصدر مسحوبة. لا تعطّل ضوابط أمان Windows لتجاوز هذا الحد.

لا يضبط المُثبّت الحالي HERMES_GIT_BASH_PATH. لا يحل MinGit محل Git for Windows المزود بـ Bash.

وحدة التحكم بترميز UTF-8 على Windows

يستخدم stdio الافتراضي في Python على Windows صفحة الترميز النشطة لوحدة التحكم (عادةً cp1252 أو cp437). وتحتوي لافتة Hermes، وقائمة slash commands، وسجل الأدوات، ولوحات Rich، وأوصاف المهارات جميعها على محارف Unicode. ودون تدخّل، يؤدي أي منها إلى انهيار مع الخطأ UnicodeEncodeError: 'charmap' codec can't encode character….

يوجد الحل في hermes_cli/stdio.py::configure_windows_stdio()، الذي يُستدعى مبكرًا في كل نقطة دخول (cli.py::main، hermes_cli/main.py::main، gateway/run.py::main). وهو:

  1. يحوّل صفحة ترميز وحدة التحكم إلى CP_UTF8 (65001) عبر kernel32.SetConsoleCP / SetConsoleOutputCP.
  2. يعيد ضبط sys.stdout / sys.stderr / sys.stdin على UTF-8 مع errors='replace'.
  3. يضبط PYTHONIOENCODING=utf-8 و PYTHONUTF8=1 (عبر setdefault، بحيث تكون الأولوية للقيم التي يحددها المستخدم صراحةً) كي ترث عمليات Python الفرعية ترميز UTF-8.
  4. يضبط EDITOR=notepad إذا لم يكن أيٌّ من EDITOR أو VISUAL مضبوطًا (راجع قسم المحرر أدناه).

العملية idempotent (تكرارها لا يغيّر النتيجة). ولا تفعل شيئًا على الأنظمة غير Windows.

إلغاء التفعيل: ضبط HERMES_DISABLE_WINDOWS_UTF8=1 في البيئة يُرجع السلوك إلى مسار stdio القديم بترميز cp1252. مفيد لتتبّع خطأ ترميز بطريقة التنصيف (bisect)؛ ومن غير المرجح أن يكون الإعداد الصحيح في التشغيل العادي.

المحرر (Ctrl-X Ctrl-E، /edit)

قبل #21561، كان الضغط على Ctrl-X Ctrl-E أو كتابة /edit لا يفعل شيئًا على Windows دون أي رسالة. إذ تملك prompt_toolkit قائمة احتياطية مكتوبة في الكود بمسارات POSIX مطلقة (/usr/bin/nano، /usr/bin/pico، /usr/bin/vi، …) لا يمكن العثور عليها أبدًا على Windows — حتى مع تثبيت Git for Windows كاملًا.

تضبط طبقة stdio الخاصة بـ Windows في Hermes الآن EDITOR=notepad كقيمة افتراضية. يأتي Notepad مع كل تثبيت لـ Windows ويعمل كمحرر حاجب (blocking) — إذ يبقى subprocess.call(["notepad", file]) منتظرًا حتى تُغلق النافذة.

تبقى الأولوية لتخصيصات المستخدم (إذ يجري التحقق منها قبل setdefault):

Ctrl+Enter لإدراج سطر جديد في CLI

يمرّر Windows Terminal المفتاحين Ctrl+Enter كتسلسل مفاتيح مخصص. يربطه Hermes بإجراء "insert newline" (إدراج سطر جديد) كي تتمكن من كتابة prompts متعددة الأسطر في CLI دون اللجوء إلى Esc ثم Enter. يعمل ذلك في Windows Terminal، وفي الطرفية المدمجة في VS Code، وفي أي مضيف حديث لوحدة التحكم في Windows يدعم تسلسلات الهروب VT.

في وحدات تحكم cmd.exe القديمة، يتحول Ctrl+Enter إلى Enter عادي — استخدم Esc Enter بدلًا منه، أو انتقل إلى Windows Terminal (فهو مجاني ومثبّت افتراضيًا على Windows 11).

تشغيل الـ gateway عند تسجيل الدخول إلى Windows

يستخدم hermes gateway install على Windows ميزة Scheduled Tasks مع مجلد Startup كبديل احتياطي — دون الحاجة إلى صلاحيات المسؤول.

التثبيت

ما يحدث في الخلفية:

  1. schtasks /Create /SC ONLOGON /RL LIMITED /TN Hermes_Gateway — يسجّل مهمة تعمل عند تسجيل دخولك بصلاحيات عادية (غير مرفوعة). دون أي نافذة UAC.
  2. إذا حُظر schtasks بواسطة نهج المجموعة (group policy)، فإنه يلجأ إلى كتابة مُشغِّل صغير Hermes_Gateway.vbs (يعمل مخفيًا عبر wscript.exe) في %APPDATA%\Microsoft\Windows\Start Menu\Programs\Startup. النتيجة نفسها، بطريقة أقل أناقة قليلًا. يُستخدم VBScript بدلًا من اختصار cmd.exe لأن نافذة طرفية تُخصَّص عند تسجيل الدخول قد تتلقى حدث إغلاق يقتل gateway قبل اكتمال بدئه. يُحتفَظ دائمًا بأحد الخيارين فقط: تثبيت المهمة بنجاح يزيل أي إدخال في مجلد Startup (بما في ذلك Hermes_Gateway.cmd القديم)، ويُتجاوز الخيار الاحتياطي ما دامت مهمة مسجّلة، وينظّف hermes update / hermes doctor --fix التثبيتات القديمة التي تتضمن الخيارين، لأن كليهما سيشغّل gateway عند تسجيل الدخول.
  3. يشغّل الـ gateway منفصلًا عبر pythonw.exe — وليس python.exe. لا يرتبط pythonw.exe بأي وحدة تحكم، ما يحصّنه ضد بثّ CTRL_C_EVENT من العمليات الشقيقة (وهي مشكلة حقيقية كانت تُنهي الـ gateway عندما تضغط Ctrl+C على أي شيء في مجموعة العمليات نفسها).

الخيارات (flags) المستخدمة عند التشغيل: DETACHED_PROCESS | CREATE_NEW_PROCESS_GROUP | CREATE_NO_WINDOW | CREATE_BREAKAWAY_FROM_JOB.

الإدارة

الأمر hermes gateway status idempotent — استدعِه ألف مرة متتالية ولن يُنهي الـ gateway عن طريق الخطأ أبدًا. (قبل PR #21561 كان يفعل ذلك بصمت، بسبب تصادم os.kill(pid, 0) مع CTRL_C_EVENT على مستوى C — راجع "الآليات الداخلية لإدارة العمليات" أدناه إن كانت القصة تهمك.)

لا يُثبَّت التشغيل التلقائي عند تسجيل الدخول إلا بناءً على إجابة صريحة: hermes gateway install أو Y على طرفية حقيقية أو HERMES_GATEWAY_INSTALL_START_ON_LOGIN=1. تشغيل hermes gateway start عبر سكربت أو أنبوب (دون TTY، أو مع HERMES_NONINTERACTIVE=1) يبدأ gateway دون المساس بالمهمة المجدولة أو مجلد Startup؛ اضبط HERMES_GATEWAY_INSTALL_START_ON_LOGIN=0 لتجاوز السؤال على الطرفية أيضًا.

لماذا لا نستخدم Windows Service؟

تتطلب الخدمات صلاحيات المسؤول لتثبيتها، وتربط دورة حياة الـ gateway بإقلاع الجهاز لا بتسجيل دخول المستخدم. ما يريده مستخدم Hermes المعتاد هو: تسجيل الدخول → الـ gateway متاح، تسجيل الخروج → الـ gateway متوقف. وهذا بالضبط ما تفعله Scheduled Tasks دون رفع الصلاحيات. إذا كنت تريد خدمة فعلًا، فاستخدم nssm أو sc create يدويًا — لكنك على الأرجح لا تحتاج إلى ذلك. إن فعلت، فسمّه Hermes* أو اجعل مساره التنفيذي داخل تثبيت Hermes (venv\Scripts\hermes.exe أو النسخة المسحوبة أو gateway-service\): hermes update يوقف ويعيد تشغيل الخدمات التي يستطيع تحديد ملكية Hermes لها إيجابيًا عبر Service Control Manager فقط، ويوقف مؤقتًا gateway الذي بدأته مهمة مجدولة باستخدام PID (دون المساس بـ Task Scheduler نفسه).

أداة المتصفح

أداة المتصفح (browser_exec) جزء من بيئة Python الخاصة بـ Hermes. وللتصفح المحلي، يشغّل Hermes نسخة Chromium المثبّتة التي يوفّرها PM (نفّذ hermes pm install chromium إن لم تكن موجودة)؛ واضبط browser.executable_path لاستخدام ملف تنفيذي آخر من عائلة Chromium. تُختار المتصفحات السحابية في hermes tools. وتتضمن حزمة MSIX المكتفية بذاتها أدوات المتصفح ضمن محتوياتها.

على Windows ARM64، يكون Chromium المثبّت هو بناء x64 ويعمل تحت محاكاة x64 في Windows. يختلف ذلك عن بيئة Python الأصلية لـ ARM64. راجع أتمتة المتصفح لمعرفة مصادر المتصفح.

تشغيل Hermes على Windows — ملاحظات عملية

PATH بعد التثبيت

يضيف المُثبّت %LOCALAPPDATA%\hermes\bin إلى User PATH الخاص بك عبر [Environment]::SetEnvironmentVariable. لا تلتقط الطرفيات المفتوحة مسبقًا هذا التغيير — افتح نافذة PowerShell جديدة (أو تبويبًا جديدًا في Windows Terminal) بعد التثبيت. أغلق الطرفية وأعد فتحها، ولا تنفّذ $env:PATH += … يدويًا ما لم تكن تعرف ما تفعله.

إلغاء التثبيت

من PowerShell:

في تثبيتات المصدر، يزيل برنامج إلغاء التثبيت المشغّلات وإدخالات الخدمات وملفات التطبيق المملوكة له. راجع hermes uninstall --dry-run قبل الإزالة. الخيار --full يزيل البيانات أيضًا؛ أما --data فيزيل البيانات دون إزالة الكود المحزَّم. لتثبيتات MSIX أو Store، أزل التطبيق عبر Windows Settings → Apps → Installed apps. يرفض CLI حذف الكود الذي تملكه الحزمة.

حذف بيانات المستخدم

قبل حذف البيانات، أوقف كل عمليات Hermes التي تستخدم HERMES_HOME المحدّد وخذ نسخة احتياطية. راجع hermes uninstall --dry-run قبل اختيار وضع إزالة البيانات. لا تحذف جذر البيانات الافتراضي تكراريًا لإصلاح تطبيق أو profile واحد. قد يوجد HERMES_HOME مخصّص في مكان آخر، ولا تزيل إزالة الحزمة تلك البيانات.

يتعامل الأمر الفرعي hermes uninstall في CLI أيضًا مع الحالة التي يكون فيها مُدخل schtasks مسجّلًا تحت اسم مهمة مختلف (في التثبيتات الأقدم) — إذ يبحث حسب مسار التثبيت بدلًا من اسم مهمة ثابت في الكود.

الآليات الداخلية لإدارة العمليات

هذه مادة خلفية — تخطَّها ما لم تكن تتتبّع خللًا غريبًا من نوع "إنه يُنهي نفسه".

في Linux و macOS، يُعد التعبير الاصطلاحي في POSIX os.kill(pid, 0) فحصًا للصلاحيات لا يُحدث أي أثر: "هل هذا الـ PID حي، وهل يمكنني إرسال إشارة إليه؟" أما في Windows، فيربط os.kill في Python القيمة sig=0 بـ CTRL_C_EVENT — إذ يتصادمان عند القيمة العددية 0 — ويمرّرها عبر GenerateConsoleCtrlEvent(0, pid)، الذي يبث Ctrl+C إلى مجموعة عمليات وحدة التحكم بأكملها التي تضم الـ PID المستهدف. هذه هي المشكلة bpo-14484، المفتوحة منذ 2012. ولن تُصلح لأن تغيير هذا السلوك سيُعطّل السكربتات التي تعتمد عليه حاليًا.

النتيجة: أي مسار في الكود كان "يتحقق مما إذا كان هذا الـ PID حيًا" عبر os.kill(pid, 0) على Windows كان يُنهي العملية المستهدفة بصمت. نقل Hermes كل موضع من هذا النوع (14 موضعًا عبر 11 ملفًا) إلى gateway.status._pid_exists()، الذي يستخدم psutil.pid_exists() (والذي يستخدم بدوره OpenProcess + GetExitCodeProcess على Windows — دون أي إشارات). إذا كنت تكتب إضافة (plugin) أو تعديلًا (patch)، فاستخدم psutil.pid_exists() مباشرةً أو gateway.status._pid_exists() — ولا تستخدم os.kill(pid, 0) أبدًا.

يفرض scripts/check-windows-footguns.py هذه القاعدة في CI: أي استدعاء جديد لـ os.kill(pid, 0) يُفشل الفحص Windows footguns (blocking) ما لم يحمل السطر العلامة # windows-footgun: ok — <reason> كعلامة.

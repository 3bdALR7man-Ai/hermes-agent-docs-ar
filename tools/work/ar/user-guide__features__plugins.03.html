تشغيل الإضافات خارج العملية (plugins.isolation)

افتراضيًا، تُستورد إضافات Python من الجهات الخارجية إلى عملية Hermes، كما كان الحال دائمًا. يؤدي ضبط plugins.isolation: host إلى نقلها إلى مضيف إضافات: عملية Python منفصلة واحدة لكل profile، تبدأ عند الطلب، وتستورد الإضافات التي ثبّتها المستخدم في ذلك الـ profile وتتواصل مع Hermes عبر pipe خاص.

لا تتغيّر الإضافات. تتلقى ctx نفسه وتسجّل الأدوات، و hooks، و slash commands، والمهارات، وكائنات المزوّدين (توليد الصور/الفيديو، والبحث في الويب، والمتصفح، و TTS/STT، والذاكرة، ومحركات السياق، و profiles مزوّدي النماذج) كما كانت تفعل؛ ويسجّل Hermes مدخلات مطابقة على جانبه تستدعي المضيف. يخدم المضيف أيضًا APIs الإضافات في لوحة التحكم. تستمر الإضافات المضمّنة في العمل داخل العملية. تشارك معالجات API لوحة التحكم العاملة داخل العملية حلقة أحداث gateway، لذا يجب ألا تحجبها (راجع لا تحجب حلقة الأحداث).

في gateway يخدم عدة profiles، يشغّل كل profile غير الذي بدأ به gateway إضافات لوحة التحكم الخاصة به (المثبّتة تحت مجلد plugins/ الخاص به أو الجذر ~/.hermes/plugins/، وتتغلب نسخة الـ profile الخاصة عند تعارض الاسم نفسه، والمفعّلة في إعداداته الخاصة) في مضيف الإضافات الخاص به، أيًّا كانت قيمة plugins.isolation لديه: فشيفرة إضافة profile آخر لا تعمل أبدًا داخل gateway. لا يحمل المضيف websockets بعدُ، لذا تُرفض مسارات websocket لمثل هذه الإضافة (HTTP 501) لذلك الـ profile؛ أما مسارات HTTP فتعمل. ولا يحتجز المعالج المستضاف البطيء إلا طلبات إضافات الـ profile الخاص به، ويحصل الطلب الذي لم يجب عنه المضيف بعد 60 ثانية على HTTP 504. ويبدأ مثل هذا المضيف عند أول طلب إضافة لوحة تحكم لذلك الـ profile ويعمل حتى يخرج gateway: أي عملية Python إضافية واحدة لكل profile استخدم إضافة لوحة تحكم.

ما الذي يتغيّر في وضع host:

  • لا يوجد مفسّر مشترك. لا تدخل وحدة الإضافة عملية Hermes أبدًا، فلا يمكنها قراءة بيانات profile آخر من الذاكرة أو تعديل الآليات الداخلية لـ Hermes. في gateway متعدد الإرسال، يحصل كل profile على مضيفه الخاص، يبدأ ببيئة ذلك الـ profile وأسراره فقط.
  • تظل الأعطال محصورة. الإضافة التي تتعطل أو تخرج تُنهي مضيفها لا Hermes؛ ويعيد الاستدعاء الجاري خطأ أداة، ثم يعيد Hermes تشغيل المضيف وتحميل إضافاته (مع إعادات محاولة محدودة).
  • تحتاج بعض الواجهات إلى كود داخل العملية، وتُفشِل تلك الإضافة بسبب واضح بدلًا من تحميلها: محوّلات منصات gateway (register_platform)، ووسائل نقل الموافقات، ومعالجات Telegram/المنصات، و profiles مزوّدي النماذج التي تبني عميل SDK خاصًا بها (create_client)، و endpoints البث و websocket في لوحة التحكم، والإضافات التي تعدّل وحدات Hermes عبر monkeypatch. شغّلها باستخدام isolation: in_process.

تثبيت الإعداد لنشر مشترك. plugins.isolation إعداد عادي للـ profile، لذا يستطيع من يملك تعديل config.yaml الخاص بالـ profile تعطيله. عندما تتبع profiles لأشخاص تعزلهم عن بعضهم، ثبّته بدلًا من ذلك في النطاق المُدار (Managed Scope)؛ فتتغلب القيمة المُدارة على الإعدادات الخاصة بكل profile، ويرفض hermes config set تغييرها:

شغّل طرفية الوكلاء أيضًا على backend معزول (Docker، أو SSH، ...) حتى لا يستطيع الوكيل نفسه الوصول إلى ملفات المشغّل.

hermes plugins validate <dir> و hermes plugins show <name> يبيّنان ما إذا كانت الإضافة تعمل في المضيف، وسبب عدم عملها فيه إن لم تفعل. وقت كتابة هذا النص، تعمل 299 من أصل 348 مدخلة في كتالوج الإضافات داخل المضيف دون تغيير.

واجهة تفاعلية

تشغيل hermes plugins دون وسائط يفتح شاشة تفاعلية مركّبة:

  • قسم الإضافات العامة — مربعات اختيار، بدّلها باستخدام SPACE. يظهر الصف محددًا عند فتحه إذا كانت الإضافة نشطة الآن: مدرجة في plugins.enabled، أو منصة مضمّنة أو backend أو مزوّد نماذج (مفعّل دون مدخلة قائمة)، أو المزوّد المحدد لفئة. لا تُكتب عند الخروج إلا الصفوف التي تبدّلها: إلغاء التحديد يضيف الإضافة إلى plugins.disabled (تعطيل صريح)، والتحديد يضيفها إلى plugins.enabled ويمحو تعطيلًا قديمًا. فتح المنتقي والخروج منه لا يغيّر شيئًا.
  • قسم إضافات المزوّد — يعرض الاختيار الحالي. اضغط ENTER للدخول إلى منتقٍ راديو حيث تختار مزوّدًا فعّالًا واحدًا.
  • الإضافات المدمجة تظهر في نفس القائمة بوسم [bundled].

اختيارات إضافة المزوّد تُحفَظ في config.yaml:

مفعَّل مقابل معطَّل مقابل لا هذا ولا ذاك

في جلسة قيد التشغيل، يعرض /plugins الإضافات المحمَّلة حاليًا.

نشر رسالة حية

يمكن للإضافة أن تنشر رسالة واحدة في المحادثة التي تعمل لأجلها وأن تحدّث الرسالة نفسها لاحقًا، على أي قناة، دون كود خاص بكل منصة. استخدم ذلك للتقدم الحي (قائمة تحقق أثناء عمل أداة طويلة، أو بطاقة خطة تتغير مع مراجعة الخطة):

التواقيع: ctx.post_message(text: str) -> PluginMessage و PluginMessage.edit(text: str) -> dict. من شيفرة async تعمل بالفعل على حلقة أحداث gateway (hook غير متزامن أو معالج slash command) استخدم await ctx.apost_message(text) وawait handle.aedit(text) بدلًا منهما؛ فالصيغ المتزامنة تُرفض هناك بالخطأ error: "on_event_loop" بدلًا من تعطيل الحلقة بتوقف تام (deadlock).

أي محادثة. المحادثة الحالية هي الجلسة المرتبطة بالشيفرة المستدعية: معالج أداة أو hook يعمل في دور تلك الجلسة، أو slash command الخاص بها، أو hook أُطلق لأجلها. لا تسمّي الإضافة محادثة أبدًا، فلا يمكنها النشر في مكان آخر. والـ thread الذي تبدؤه الإضافة بنفسها لا يرث ذلك الربط (ابدأه بـ contextvars.copy_context().run(...) إن كان ينبغي ذلك)، وليس للمؤقّت أو تشغيل cron أو العملية التي لا gateway حيًّا لها أي محادثة على الإطلاق.

لا يرفع استثناءً أبدًا. يُرجع كل استدعاء نتيجة. تصف handle.ok وhandle.message_id وhandle.error آخر عملية؛ ويُرجع edit() القيمة {"ok", "message_id", "edited"} إضافةً إلى "fallback": True عندما اضطر إلى نشر رسالة جديدة. رموز الأخطاء: no_conversation (لا شيء مرتبط في السياق المستدعي، أو الجلسة ليست حية، أو تنتمي إلى profile آخر)، gateway_unavailable وadapter_unavailable وsend_failed وedit_failed وon_event_loop وtimeout. يُرجع النشر المرفوض مقبضًا (handle) يُرفض edit() فيه بالطريقة نفسها، فلا يحتاج المسار السليم إلى تفرّع. ويعني timeout أن gateway لم يجب خلال 30 ثانية: تستمر العملية في العمل ويصل ناتجها إلى المقبض لاحقًا (تكون handle.pending صحيحة في أثناء ذلك)، وينتظرها edit() التالي أولًا، فلا يترك نشر بطيء رسالةً لا يستطيع المقبض تحريرها. والتحرير الذي ترفضه المنصة أو يرفع استثناءً يرتد إلى رسالة جديدة بالطريقة نفسها المتّبعة في منصة لا تدعم التحرير. ويُسجَّل كل نشر وتحرير بالصيغة plugin_message plugin=<id> op=post|edit ....

ما تفعله كل واجهة:

الواجهةpost_messageedit
منصات المراسلة القادرة على التحرير (Telegram وDiscord وSlack وMatrix، ...)send العادي للمحوّل (adapter) إلى المحادثة/threadيحرّر الرسالة نفسها في مكانها
المنصات التي لا تدعم التحرير (SMS والبريد الإلكتروني ومحوّلات الإضافات التي لا تنفّذ edit_message)sendيرسل رسالة جديدة؛ ويتبعها المقبض (edited: False, fallback: True)
Desktop وInk TUIإشعار بمفتاح لمشاهدي الجلسة (toast في Desktop، وسطر الحالة في TUI)يستبدل ذلك الإشعار في مكانه
CLI الكلاسيكي (hermes chat)يوضع في الطابور كسطر إشعار، ويُطبع في نهاية الدور التالي (لا يملك CLI الكلاسيكي خانة إشعار حية)يضع كل تحرير سطرًا آخر في الطابور

يُقتطع النص عند حد رسالة المنصة بنقاط حذف (ولا يُقسَّم أبدًا). وهو نص عادي: قد يعرض المحوّل تنسيقه الخاص، لكن لا ينبغي للإضافة الاعتماد عليه. ولا حاجة إلى صلاحية، لأن الرسالة لا يمكن أن تصل إلا إلى المحادثة التي استدعت الإضافة أصلًا. ctx.post_message غير متاح للإضافات التي تعمل في مضيف الإضافات خارج العملية (plugins.isolation: host): فالمقبض مرتبط بحلقة أحداث gateway والمحوّل الحي.

حقن الرسائل (Injecting Messages)

يمكن للإضافات حقن رسائل في محادثة CLI أو جلسة gateway معروفة أو جلسة gateway جديدة في محادثة معيّنة باستخدام ctx.inject_message():

التوقيع: ctx.inject_message(content: str, role: str = "user", *, session_key: str | None = None, origin: Mapping[str, Any] | None = None) -> bool

عندما يشغّل CLI الكلاسيكي الإضافات في عمليته الخاصة (دون جلسة gateway):

  • إذا كان الوكيل خاملًا (بانتظار إدخال المستخدم)، تُصفّ الرسالة كإدخال تالٍ وتبدأ دورًا جديدًا.
  • إذا كان الوكيل وسط دور (قيد التشغيل فعليًا)، تقاطع الرسالة العملية الجارية — تمامًا كما لو كتب المستخدم رسالة جديدة وضغط Enter.
  • بالنسبة للأدوار غير "user"، يُسبَق المحتوى بـ [role] (مثل [system] ...).
  • تُعيد True إذا صُفَّت الرسالة بنجاح.

دون مفتاح جلسة (session_key وorigin كلاهما محذوف)، وحين تعمل الإضافة في gateway (أو مضيف الإضافات الخاص به) — وهو المكان الذي تعمل فيه الإضافات لجلسات CLI الكلاسيكي وTUI وDesktop — يختار gateway المحادثة:

  1. إذا كانت الإضافة تعالج استدعاءً من جلسة محلية (slash command الخاص بها، أو hook أُطلق لتلك الجلسة، أو أداة أو hook في دورها)، تذهب الرسالة إلى تلك الجلسة. ولا يخمّن ذلك أبدًا، مهما بلغ عدد الجلسات المفتوحة.
  2. ومع غياب جلسة في السياق المستدعي (مؤقّت، أو thread خلفي — فالـ thread الذي تبدؤه الإضافة لا يرث سياق الاستدعاء)، تذهب الرسالة إلى الجلسة المحلية الوحيدة في profile الإضافة التي بدأها CLI الكلاسيكي (hermes chat) ولها عارض مرتبط. ولا تُختار بهذه الطريقة جلسات TUI وDesktop ولا محادثات المراسلة ولا جلسات profiles الأخرى.
  3. وفيما عدا ذلك (لا توجد جلسة كهذه، أو توجد عدة جلسات) تُرفض: False، ولا يُحقن شيء في أي مكان، ويسمّي سجل gateway الإضافة ويطلب تمرير مفتاح جلسة.

تتلقى الجلسة المختارة النص كمدخل في الطابور، بالطريقة نفسها التي يعمل بها الحقن بمفتاح؛ ويلزمها إذن allow_gateway_injection أدناه. وعندما تكون جلسة CLI كلاسيكي، يظهر الدور وردّه في سجل الجلسة، لكن CLI الكلاسيكي المرتبط لا يعرضهما. أما الاستدعاء الموجَّه إلى محادثة مراسلة دون مفتاح فيُرفض كما كان. يُفضَّل تمرير session_key: فقد يُرفض الاستدعاء بلا مفتاح عندما تكون المحادثة ملتبسة، وقد يُلغى الحقن بلا مفتاح لاحقًا.

في وضع gateway مع مفتاح:

  • يجب أن يعرّف session_key جلسة gateway موجودة. إنه مفتاح التوجيه الثابت، وليس معرّف جلسة CLI.
  • يعيد Hermes استخدام المنصة والمحادثة والخيط و profile وسجل المحادثة المخزّنة لتلك الجلسة. لا يمكن للإضافات تغيير هذا المسار عبر session_key.
  • يجب أن تنتمي الجلسة إلى profile الإضافة نفسها: فمفتاح محادثة profile آخر أو جلسته المحلية يحصل على False فورًا، مع ذكر السبب في سجل gateway.
  • يعيد Hermes فحص المسار المخزَّن مقابل قواعد التفويض الحالية لـ gateway قبل الإرسال.
  • المسارات التي اعتمدت فقط على قرار تفويض وقت المحوّل أو من مصدر أعلى تُرفَض ما لم يتمكن Hermes من إعادة التحقق منها من قوائم السماح الأساسية الحالية، أو الاقتران، أو إعداد صريح للسماح بكل شيء.
  • النص المحقون هو دائمًا إدخال محادثة عادي. لا يمكنه استدعاء slash commands، أو الموافقة على أدوات، أو حلّ طلبات تأكيد أو توضيح معلَّقة.
  • يبقى المسار والمحادثة مثبَّتين أثناء انتظار الإرسال. يُسقِط Hermes الطلب إذا غيّر استرجاع الموضوع المسار أو دارت الجلسة قبل بدء المعالجة.
  • يدخل الطلب مسار رسائل محوّل المنصة العادي. الجلسات النشطة تستخدم طابور الجلسة المشغولة الحالي بدلًا من بدء دور منافس.
  • تُعيد True عندما يقبل gateway الحي الطلب للإرسال غير المتزامن. هذا لا يؤكّد أن دور الوكيل أو التسليم على المنصة قد اكتمل.
  • تُعيد False عندما يُعطى session_key وorigin معًا، أو لا يُعطى أي منهما ولا تُختار محادثة (أعلاه)، أو لم تُمنح الصلاحية، أو لم يتمكن أي مضيف نشط من قبول الطلب. تُكتب مفاتيح الجلسات المجهولة أو غير القابلة للتوجيه، التي تُكتشف بعد القبول غير المتزامن، في سجل gateway.

بدء جلسة باستخدام origin (في وضع gateway فقط):

  • origin يستخدم البنية نفسها لأصل الجلسة المخزّن (SessionSource.to_dict()): platform و chat_id مطلوبان؛ أما chat_type, thread_id, user_id, user_name, chat_name وحقول الأصل الأخرى فاختيارية. استخدمه عندما لا تكون هناك جلسة بعد — مثل منشور منتدى أنشأه البوت، إذ لا تعيد منصات مثل Discord إرساله إلى البوت كرسالة واردة.
  • تُنشأ الجلسة في profile الخاص بالإضافة نفسها (أي profile الذي حمّل مديرُ إضافاته الإضافةَ) عبر مسار الجلسة المعتاد، مع prompt جديد وسجل فارغ، ويُسلّم الرد إلى تلك المحادثة/الخيط. إذا كانت للمحادثة جلسة موجودة بالفعل في ذلك profile، ينضم النص إليها تمامًا كرسالة بشرية (تُطبّق قائمة انتظار الجلسة المشغولة)، بحيث تتابع رسالة بشرية لاحقة في الخيط نفسه الجلسةَ نفسها.
  • تحت سلطة الجلسات في gateway (كل جلسة يملكها gateway)، يُثبَّت دور الإضافة في FIFO الدائم لتلك الجلسة ويستعير منشأ الموصل (connector provenance) من رسالة بشرية قُبلت فيها بالفعل. لذلك يُرفض origin الذي لم تُقبل في محادثته أي رسالة بشرية بعد (لا جلسة، أو جلسة بلا دور بشري مثبَّت): يُرجع inject_message القيمة False فورًا ويقول سجل gateway "has no human message admitted yet". لا يختلق Hermes أبدًا منشأ منصة لمحادثة لم تسلّمها المنصة. اجعل أول رسالة في تلك المحادثة تأتي من المنصة (أو من إنسان)، ثم احقن باستخدام origin أو session_key.
  • لا يمكن للإضافة استهداف profile آخر مطلقًا. تُعاد القيمة False (مع السبب في سجل gateway) عندما يحدّد الأصل profile مختلفًا، أو يوجّه توجيه profiles الخاص بالـ gateway تلك المحادثة إلى profile آخر، أو لا يخدم هذا الـ gateway الـ profile الخاص بالإضافة، أو لا يملك ذلك profile محوّلًا متصلًا للمنصة platform — لا يُستعار بوت profile آخر مطلقًا. في gateway متعدد profiles، يُنفّذ الدور باستخدام مجلد profile الخاص بالإضافة وأسراره.
  • لا يُتجاوز التفويض: يجب أن يجتاز مستخدم الأصل قوائم السماح الحالية للـ gateway أو الاقتران أو إعداد السماح للجميع لذلك profile، وهو التحقّق نفسه المستخدم في مسار session_key. اختر user_id مخوّلًا، وإلا يُسقط الطلب عند الإرسال ويُسجّل.
  • تُطبّق قواعد النص نفسها: لا slash commands ولا موافقات ولا حلّ prompts. تُقرأ الصلاحية أدناه من ملف config.yaml.

يمثّل Ink TUI (hermes --tui) ومحادثة تطبيق سطح المكتب / لوحة التحكم مضيفًا ثالثًا. لا يضبطان مرجع CLI التقليدي ولا يسجّلان في حاقن messaging gateway — يظل المضيفان منفصلين لكي لا يستبدل gateway نشط حالة TUI (أو العكس). مرّر معرّف الجلسة الدائم session_key (معرّف ses_…)، لا معرّف جلسة واجهة المستخدم المؤقت. يضع Hermes النص في قائمة انتظار الـ prompts لتلك الجلسة: تحتفظ الجلسة المشغولة بالرسالة للدور التالي، وتبدأ الجلسة الخاملة دورًا. يُترك المفتاح الذي لا يشير إلى جلسة TUI نشطة للـ messaging gateway عند وجوده، ولا يُعاد توجيهه إلى محادثة أخرى مطلقًا.

هذا يتيح لإضافات مثل عارضات التحكم عن بُعد، أو جسور المراسلة، أو مستقبِلات webhook، تغذية المحادثة برسائل من مصادر خارجية.

يمكن لحقن gateway إرسال رد الوكيل إلى منصة مراسلة خارجية. مُعطَّل افتراضيًا لكل إضافة. امنحه لكل إضافة في config.yaml:

تحذير

امنح حقن gateway فقط للإضافات التي تثق بها. يتحقّق Hermes من صلاحية API المضيف هذه، ويقيّدها بمسارات جلسات موجودة أو جلسات جديدة في profile الخاص بالإضافة، ويطبّق التفويض الحالي؛ لكن إضافات Python تعمل داخل العملية نفسها وهذا الإعداد ليس sandbox.

ملاحظة

لا تعرض واجهة الإضافة هذه نقطة نهاية HTTP عامة ولا أمر CLI لعمليات خارجية. يجب أن تعرف الإضافة مسبقًا session_key الخاص بـ gateway الهدف، مثلًا من إعداداتها الموثوقة الخاصة أو حالة جلسة محتفَظ بها سابقًا.

شيفرة الإضافة داخل gateway

تعمل hooks والأدوات والأدوار المحقونة لكل محادثة وكل جلسة محلية (CLI وTUI وDesktop) في عملية gateway الواحدة، لا في العميل الذي أطلقته. وبعض عادات مستوى العملية من CLI الكلاسيكي لا تنتقل:

  • os.getcwd() هو مجلد gateway نفسه، وتشاركه كل الجلسات؛ ولا يغيّره Hermes أبدًا. استخدم ctx.session_cwd() لمجلد عمل الجلسة التي يعمل لها الـ hook أو الأداة: مساحة العمل التي بدأت منها جلسة CLI/TUI/Desktop، أو مجلد cwd الطرفية للـ profile في المحادثة ("" عند عدم وجوده). مرّره كـ cwd= إلى العمليات الفرعية. يقرأ الجلسة من الدور الجاري، فيعمل في الشيفرة التي تعمل لأجل جلسة: hooks الأدوار ومعالجات الأدوات وhooks الموافقة. أما hooks الدخول مثل pre_gateway_dispatch فتعمل قبل قبول الرسالة في أي جلسة؛ وهناك يُرجع cwd الطرفية للـ profile، أو "" عند عدم ضبط واحد.
  • تسمّي ctx.session_surface() عميل الجلسة المستدعية: "cli" أو "tui" أو "desktop" أو "acp" أو منصة المراسلة ("telegram", …)؛ و"" خارج الجلسة.
  • تذهب مخرجات print() إلى gateway-stdio.log الخاص بـ gateway لا إلى طرفيتك. استخدم logging بدلًا منها.
  • يحصل input() على نهاية الملف (EOF): فلا طرفية لدى gateway. اسأل عبر نتيجة أداة أو slash command.

في عملية CLI الكلاسيكي نفسها (مثل slash command لإضافة)، يكون ctx.session_cwd() هو مجلد الإطلاق، ويكون ctx.session_surface() هو "cli".

استدعاء خواديم MCP من الإضافات

ctx.call_mcp() يتيح للإضافة استدعاء أداة على أحد خواديم MCP المُعدَّة للمستخدم — بشكل متزامن، من أي hook أو معالج أداة — عبر عميل MCP الأصلي الحالي في Hermes (نفس الاتصالات، وبوابات مستوى الثقة، وقاطع الدارة، ومنطق إعادة الاتصال المستخدَمة في أدوات MCP التي يستدعيها النموذج؛ أبدًا عميل موازٍ).

التوقيع: ctx.call_mcp(server: str, tool: str, arguments: dict | None = None, timeout: float = 30) -> dict

تُعيد ظرفًا ثابتًا: {"ok": True, "result": ...} (بالإضافة إلى structuredContent عندما يوفّره الخادم) أو {"ok": False, "error": "..."}. النتائج التي تتجاوز ~64 كيلوبايت تُقتَطع وتُوسَم بـ "truncated": True.

الأمان: مُعطَّل افتراضيًا، قائمة سماح لكل خادم

لا تملك الإضافة أي وصول إلى MCP افتراضيًا. يجب على المشغّل منح كل خادم صراحةً في config.yaml:

  • استدعاء خادم غير موجود في القائمة يرفع PermissionError يسمّي مفتاح الإعداد الدقيق الواجب ضبطه.
  • المنح لكل خادم ولكل إضافة — أبدًا صلاحية شاملة على كل خادم مُعدّ، ووسوم "*" غير مقبولة.
  • كل استدعاء له مهلة مفروضة (30 ثانية افتراضيًا) بحيث لا يمكن لخادم MCP معلَّق أن يعطّل خط hooks أو الأدوات الذي استدعاه.
  • خواديم MCP تعيد محتوى غير موثوق. عامل result كبيانات، لا كتعليمات — لا تُدخله في قرارات مميَّزة (موافقات، تنفيذ أوامر) دون تحقّق.
تحذير

منح mcp_allowlist يمنح الإضافة نفس وصول النموذج إلى ذلك الخادم — بما في ذلك أي أدوات قادرة على الكتابة يعرضها الخادم (رهنًا ببوابات مستوى trust الخاصة بالخادم). امنح فقط الخواديم التي تحتاجها الإضافة فعلًا.

راجع الدليل الكامل لعقود المعالِج، وصيغة الـ schema، وسلوك الـ hook، ومعالجة الأخطاء، والأخطاء الشائعة.

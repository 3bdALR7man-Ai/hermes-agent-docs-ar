مزوّدو الذاكرة (Memory Providers)

يأتي Hermes Agent مع 8 إضافات (plugins) لمزوّدي الذاكرة الخارجيين تمنح الوكيل معرفة دائمة عبر الجلسات تتجاوز الملفين المدمجين MEMORY.md و USER.md. ولا يمكن تفعيل أكثر من مزوّد خارجي واحد في الوقت نفسه — بينما تبقى الذاكرة المدمجة مفعّلة دائمًا إلى جانبه.

البدء السريع

يمكنك أيضًا اختيار مزوّد الذاكرة النشط عبر hermes plugins → Provider Plugins → Memory Provider.

أو اضبطه يدويًا في ~/.hermes/config.yaml:

كيف يعمل

عندما يكون أحد مزوّدي الذاكرة نشطًا، يقوم Hermes تلقائيًا بما يلي:

  1. حقن سياق المزوّد في system prompt (ما يعرفه المزوّد)
  2. الجلب المسبق للذكريات ذات الصلة قبل كل دور (في الخلفية، دون حجب)
  3. مزامنة أدوار المحادثة مع المزوّد بعد كل رد
  4. استخلاص الذكريات عند انتهاء الجلسة (للمزوّدين الذين يدعمون ذلك)
  5. عكس عمليات الكتابة إلى الذاكرة المدمجة على المزوّد الخارجي
  6. إضافة أدوات خاصة بالمزوّد كي يتمكن الوكيل من البحث في الذكريات وتخزينها وإدارتها

تستمر الذاكرة المدمجة (MEMORY.md / USER.md) في العمل تمامًا كما كانت. فالمزوّد الخارجي إضافة إليها لا بديل عنها.

المزوّدون المتاحون

Honcho

نمذجة للمستخدم عبر الجلسات مصمَّمة أصلًا للذكاء الاصطناعي (AI-native)، مع استدلال جدلي (dialectic reasoning)، وحقن للسياق ضمن نطاق الجلسة، وبحث دلالي، واستنتاجات (conclusions) دائمة. ويتضمن السياق الأساسي الآن ملخص الجلسة إلى جانب تمثيل المستخدم (representation) وبطاقات الـ peers (peer cards)، مما يمنح الوكيل وعيًا بما نوقش بالفعل.

الأنسب لـالأنظمة متعددة الوكلاء التي تحتاج إلى سياق عبر الجلسات، والتوافق بين المستخدم والوكيل
المتطلباتpip install honcho-ai + مفتاح API أو نسخة مستضافة ذاتيًا
تخزين البياناتHoncho Cloud أو مستضاف ذاتيًا
التكلفةحسب تسعير Honcho (سحابي) / مجاني (مستضاف ذاتيًا)

الأدوات (5): honcho_profile (قراءة بطاقة الـ peer أو تحديثها)، honcho_search (بحث دلالي)، honcho_context (سياق الجلسة — الملخص، والتمثيل، والبطاقة، والرسائل)، honcho_reasoning (مُركَّب بواسطة LLM)، honcho_conclude (إنشاء الاستنتاجات أو حذفها)

البنية المعمارية: حقن السياق على طبقتين — طبقة أساسية (ملخص الجلسة + التمثيل + بطاقة الـ peer، وتُحدَّث وفق contextCadence) إضافةً إلى ملحق جدلي (استدلال LLM، ويُحدَّث وفق dialecticCadence). ويختار المكوّن الجدلي تلقائيًا بين prompts البدء البارد (حقائق عامة عن المستخدم) و prompts البدء الدافئ (سياق ضمن نطاق الجلسة) بناءً على وجود السياق الأساسي من عدمه.

ثلاثة مفاتيح إعداد متعامدة تتحكم في التكلفة والعمق كلٌّ على حدة:

  • contextCadence — عدد مرات تحديث الطبقة الأساسية (تكرار استدعاءات API)
  • dialecticCadence — عدد مرات تشغيل LLM الجدلي (تكرار استدعاءات LLM)
  • dialecticDepth — عدد تمريرات .chat() في كل استدعاء جدلي (1–3، عمق الاستدلال)

كما يُكيّف المكوّن الجدلي المحقون تلقائيًا مستوى استدلاله حسب طول الاستعلام (استعلام أطول → استدلال أعمق، بحد أقصى reasoningLevelCap)؛ راجع مستوى الاستدلال المتكيّف مع الاستعلام.

معالج الإعداد:

لا يزال الأمر القديم hermes honcho setup يعمل (إذ يُعيد التوجيه الآن إلى hermes memory setup)، لكنه لا يُسجَّل إلا بعد اختيار Honcho مزوّدًا نشطًا للذاكرة.

الأجهزة بلا واجهة رسومية / البعيدة: للمصادقة السحابية على جهاز لا يتوفر فيه متصفح (SSH، أو VM بعيد)، اختر device عند سؤال المعالج عن طريقة المصادقة. تطبع CLI رمزًا قصيرًا ورابط تحقق؛ افتح الرابط في متصفح على أي جهاز آخر، ووافق، فيكتمل الإعداد — دون نسخ مفتاح API ولصقه. ويختار المعالج هذا الخيار افتراضيًا بشكل تلقائي عندما لا يكتشف متصفحًا محليًا صالحًا للاستخدام.

الإعدادات: $HERMES_HOME/honcho.json (محلي للـ profile) أو ~/.honcho/config.json (عام). ترتيب الأولوية: $HERMES_HOME/honcho.json > ~/.hermes/honcho.json > ~/.honcho/config.json. راجع مرجع الإعدادات ودليل التكامل مع Honcho.

الانتقال من hermes honcho

إذا كنت تستخدم سابقًا hermes honcho setup، فإن إعداداتك وجميع البيانات المخزنة على الخادم سليمة. ما عليك سوى إعادة التفعيل عبر معالج الإعداد مجددًا، أو ضبط memory.provider: honcho يدويًا لإعادة التفعيل عبر النظام الجديد.

إعداد متعدد الـ peers:

ينمذج Honcho المحادثات على أنها peers يتبادلون الرسائل — peer واحد للمستخدم إضافةً إلى peer للذكاء الاصطناعي لكل profile في Hermes، وجميعهم يتشاركون مساحة عمل واحدة. مساحة العمل هي البيئة المشتركة: فالـ peer الخاص بالمستخدم عام عبر الـ profiles، بينما لكل peer خاص بالذكاء الاصطناعي هويته المستقلة. ويبني كل peer للذكاء الاصطناعي تمثيلًا / بطاقة مستقلة من ملاحظاته الخاصة، بحيث يبقى profile coder موجّهًا نحو الكود بينما يبقى profile writer موجّهًا نحو التحرير مع المستخدم نفسه.

التقابل بين المفاهيم:

المفهومما هو
مساحة العمل (Workspace)بيئة مشتركة. ترى جميع profiles الخاصة بـ Hermes ضمن مساحة عمل واحدة هوية المستخدم نفسها.
peer المستخدم (User peer) (peerName)الإنسان. مشترك بين الـ profiles في مساحة العمل.
peer الذكاء الاصطناعي (AI peer) (aiPeer)واحد لكل profile في Hermes. مفتاح المضيف hermes → الافتراضي؛ و hermes.<profile> للبقية.
الملاحظة (Observation)مفاتيح تبديل لكل peer تتحكم فيما ينمذجه Honcho ومن رسائل مَن. directional (الافتراضي، المفاتيح الأربعة كلها مفعّلة) أو unified (مجمّع بمراقب واحد).

profile جديد مع peer جديد في Honcho

يُنشئ --clone كتلة مضيف hermes.coder في honcho.json مع aiPeer: "coder"، و workspace مشتركة، وقيم موروثة لكل من peerName، و recallMode، و writeFrequency، و observation، وغيرها. ويُنشأ الـ peer الخاص بالذكاء الاصطناعي في Honcho مسبقًا بحيث يكون موجودًا قبل الرسالة الأولى.

profiles موجودة: إنشاء peers لها في Honcho بأثر رجعي

يفحص كل profile في Hermes، ويُنشئ كتل مضيف لأي profile يفتقر إليها، ويرث الإعدادات من الكتلة الافتراضية hermes، ويُنشئ الـ peers الجديدة الخاصة بالذكاء الاصطناعي مسبقًا. وهو متساوي الأثر (idempotent) — إذ يتخطى الـ profiles التي تمتلك كتلة مضيف بالفعل.

الملاحظة لكل profile

يمكن لكل كتلة مضيف تجاوز إعدادات الملاحظة بشكل مستقل. مثال: profile يركّز على الكود، يلاحظ فيه الـ peer الخاص بالذكاء الاصطناعي المستخدمَ لكنه لا ينمذج نفسه:

مفاتيح تبديل الملاحظة (مجموعة واحدة لكل peer):

المفتاحالتأثير
observeMeيبني Honcho تمثيلًا لهذا الـ peer من رسائله الخاصة
observeOthersيلاحظ هذا الـ peer رسائل الـ peer الآخر (مما يغذّي الاستدلال بين الـ peers)

الإعدادات المسبقة عبر observationMode:

  • "directional" (الافتراضي) — الخيارات الأربعة كلها مفعّلة. ملاحظة متبادلة كاملة؛ ويُتيح الاستدلال الجدلي بين الـ peers.
  • "unified" — للمستخدم observeMe: true، وللذكاء الاصطناعي observeOthers: true، والبقية false. مجمّع بمراقب واحد؛ ينمذج الذكاء الاصطناعي المستخدمَ دون نفسه، والـ peer الخاص بالمستخدم ينمذج نفسه فقط.

مفاتيح التبديل المضبوطة على الخادم عبر لوحة تحكم Honcho لها الأولوية على القيم الافتراضية المحلية — وتُزامَن مرة أخرى عند تهيئة الجلسة.

راجع صفحة Honcho للاطلاع على المرجع الكامل للملاحظة.

ربط الهويات في Gateway

يغطي نموذج الـ peers الموضّح أعلاه جلسات CLI و TUI و Desktop، حيث تُحال كل محادثة إلى peerName. أما الـ gateway فيضيف محورًا ثانيًا: إذ يصل المستخدمون بمعرّفات وقت تشغيل خاصة بكل منصة (Telegram UID، و Discord snowflake، و Slack user)، وتحدد ثلاثة مفاتيح الـ peer الذي يُحال إليه كل معرّف.

المفتاحالتأثير
pinUserPeer: trueيُدمج كل مستخدم للـ gateway ليس وكيلًا في peerName. ويُفحص هذا التثبيت أولًا، لذا فهو يتجاوز جميع الأسماء المستعارة — اختره فقط عندما لا تحتاج أي هوية من جهة المستخدمين إلى peer خاص بها
userPeerAliasesيربط معرّفات وقت تشغيل محددة بـ peers ({"7654321": "alice"}). وهو الموضع المناسب لتوجيه الهويات المتمايزة — بما في ذلك الوكلاء الذين يحمل كلٌّ منهم peer خاصًا به
runtimePeerPrefixيضيف نطاق أسماء لأي معرّف وقت تشغيل غير مربوط (telegram_7654321) كي لا تتصادم المعرّفات المتشابهة الشكل بين المنصات

خارج الـ gateway، لا تفعل هذه المفاتيح شيئًا. ولا يسأل hermes memory setup عنها إلا عندما يكتشف منصة gateway متصلة. راجع صفحة Honcho للاطلاع على تسلسل الحلّ (resolver ladder) وخطوات الإعداد.

OpenViking

قاعدة بيانات للسياق من Volcengine (ByteDance) تتميز بتسلسل هرمي للمعرفة على غرار نظام الملفات، واسترجاع متدرّج المستويات، واستخلاص تلقائي للذكريات ضمن 6 فئات.

الأنسب لـإدارة المعرفة المستضافة ذاتيًا مع تصفّح منظَّم
المتطلباتأن يكون OpenViking مُهيّأً ومُتحقَّقًا منه وقيد التشغيل
تخزين البياناتمستضاف ذاتيًا (محليًا أو في السحابة)
التكلفةمجاني (مفتوح المصدر، AGPL-3.0)

الأدوات (6): viking_search (بحث دلالي)، viking_read (متدرّج: abstract/overview/full)، viking_browse (التنقل في نظام الملفات)، viking_remember (تخزين الحقائق)، viking_forget (حذف ملف ذاكرة بواسطة URI viking:// الدقيق)، viking_add_resource (استيعاب عناوين URL والمستندات)

الإعداد:

يستطيع hermes memory setup إعادة استخدام قيم الاتصال أو نسخها من ~/.openviking/ovcli.conf. أما الإعداد اليدوي فيستخدم ملف .env الخاص بالـ profile النشط؛ وهو بالنسبة إلى الـ profile الافتراضي ~/.hermes/.env، أما الـ profiles المسمّاة فاستخدم لها ~/.hermes/profiles/<profile>/.env.

توجد إعدادات خادم OpenViking في ov.conf (--config، أو OPENVIKING_CONFIG_FILE، أو ~/.openviking/ov.conf). أما قيم اتصال العميل فتوجد في ovcli.conf (OPENVIKING_CLI_CONFIG_FILE أو ~/.openviking/ovcli.conf).

الميزات الرئيسية:

  • تحميل متدرّج للسياق: L0 (~100 token) → L1 (~2k) → L2 (كامل)
  • استخلاص تلقائي للذكريات عند تثبيت الجلسة (session commit) (الملف الشخصي، والتفضيلات، والكيانات، والأحداث، والحالات، والأنماط)
  • مخطط URI viking:// لتصفّح المعرفة بشكل هرمي

يُستخدم OPENVIKING_ACCOUNT و OPENVIKING_USER في الوضع المحلي/الموثوق. وهوية الـ peer اختيارية. فافتراضيًا، لا يرسل Hermes أي معرّف peer ويكتب الذكريات الصريحة إلى viking://user/<user>/memories/.... ولا يسأل الإعداد عن معرّف peer. وللحصول على سياق منفصل للمساعد، اضبط memory.openviking.agent: work-assistant في config.yaml.

تحتفظ إعدادات الـ peer الموجودة غير الفارغة بعمليات الكتابة والاسترجاع ضمن نطاق الـ peer. ويشمل ذلك OPENVIKING_AGENT و actor_peer_id أو agent_id القديم في إعدادات OpenViking المرتبطة. ولا تُنقل الذكريات الموجودة ولا تُحذف. ومن دون معرّف peer، يغطي البحث الافتراضي ذاكرة المستخدم وذكريات الـ peers الموجودة تحت مستخدم OpenViking نفسه. وتبقى ذكريات الـ peers القديمة قابلة للبحث في مساراتها الحالية. ويحدد الترتيب وحدود النتائج الذكريات التي تُعاد. اضبط memory.openviking.agent: hermes لاستعادة عمليات الكتابة القديمة ضمن نطاق الـ peer. أما الذكريات المكتوبة ضمن نطاق المستخدم قبل هذا التغيير فتبقى هناك وتظل قابلة للبحث. فهذا الإعداد يغيّر عمليات الكتابة المستقبلية، لا مواقع الذكريات الموجودة.

يرسل Hermes الترويسة User-Agent: openviking-memory-hermes/<version> مع طلبات OpenViking. وهذا المعرّف القياسي للأداة لا يحتوي على أي معرّف خاص بالمستخدم، ولا يُضيف طلبًا منفصلًا.

Mem0

استخلاص للحقائق بواسطة LLM على جانب الخادم، مع بحث دلالي، وإعادة ترتيب النتائج (reranking)، وإزالة تلقائية للتكرار. يتوفر بثلاثة أوضاع اتصال: Platform (Mem0 Cloud)، ولوحة تحكم مستضافة ذاتيًا (خادم Mem0 تشغّله عبر Docker)، و OSS (Mem0 داخل العملية مع LLM ومخزن متجهات خاصين بك).

الأنسب لـإدارة الذاكرة دون تدخّل — إذ يتولى Mem0 الاستخلاص تلقائيًا
المتطلباتpip install mem0ai + مفتاح API (platform)، أو خادم Mem0 قيد التشغيل (لوحة تحكم مستضافة ذاتيًا)، أو LLM + مخزن متجهات (OSS)

الخطوة 5: اكتب التسجيل

أنشئ __init__.py — هذا الملف يربط المخططات بالمعالِجات:

ما تفعله register() يفعل:

  • تُستدعى مرة واحدة بالضبط عند بدء التشغيل
  • ctx.register_tool() يضع أداتك في السجل (registry) — يراها النموذج فورًا
  • ctx.register_hook() يشترك في أحداث دورة الحياة
  • ctx.register_cli_command() يسجّل أمرًا فرعيًا في CLI (مثل hermes my-plugin <subcommand>)
  • ctx.register_command() يسجّل slash command داخل الجلسة (مثل /myplugin <args> داخل محادثة CLI / gateway) — انظر تسجيل Slash Commands أدناه
  • ctx.dispatch_tool(name, arguments) — يستدعي أي أداة أخرى (مدمجة أو من إضافة أخرى) مع ربط سياق الوكيل الأصلي (الموافقات، بيانات الاعتماد، task_id) تلقائيًا. مفيد من معالِجات slash command التي تحتاج إلى استدعاء terminal, read_file أو أي أداة أخرى كما لو كان النموذج قد استدعاها مباشرةً.
  • ctx.get_config() / ctx.set_config() إلى مساحة اسم إعدادات هذه الإضافة فقط؛ ويخزّن ctx.state بيانات تشغيل مملوكة للإضافة تحت الـ profile النشط.
  • إذا تعطّلت هذه الدالة، تُعطَّل الإضافة لكن Hermes يستمر بشكل طبيعي

تخزين الإعدادات وحالة التشغيل

استخدم مفاتيح إعدادات نسبية للإضافة لأجل السلوك المرئي للمستخدم. يحسم Hermes مواقعها تحت plugins.entries.<plugin-id>.settings ويرفض المسارات العالمية، والعابرة للإضافات، والمسارات التي تحاول الاجتياز (traversal):

استخدم ctx.state للمؤشرات (cursors) والذاكرة المؤقتة (cache) وبيانات إزالة التكرار المملوكة للإضافة بدلًا من وضع محاسبة وقت التشغيل في config.yaml:

الحالة محددة بنطاق الـ profile ، وتُستبدل ذريًا، وآمنة مع الكاتبين المتزامنين، ومحدودة بـ 10 MiB لكل إضافة. وتشترك الحزم المحمولة في الدليل نفسه مع PLUGIN_DATA الخاص بها؛ وتحصل الإضافات الأصلية على مساحة اسم مقاومة للتصادم وآمنة على Windows. يُبلَّغ عن الحالة الموجودة غير سليمة البنية وتُحفَظ كما هي.

للإعدادات والحالة مالكان مختلفان: الإعدادات سلوك مرئي للمستخدم في config.yaml، بينما الحالة بيانات تشغيل مملوكة للإضافة تحت <HERMES_HOME>/plugin-data/. لا تكشف أي من الواجهتين مساحة اسم إضافة أخرى.

نموذج الإعدادات في Desktop

يُعرض كل مفتاح تعلنه في config_schema الخاص بـ manifest كصف في صفحة الإضافة نفسها ضمن Settings → Plugins في تطبيق Desktop (يفتحها رمز الترس في صف Capabilities → Plugins للإضافة). لا حاجة إلى كود Desktop: يعيد plugins.manage list في backend المخطط بالإضافة إلى القيمة الحالية لكل مفتاح، وتتم الكتابة عند الحفظ عبر الكاتب نفسه المستخدم في ctx.set_config()، لذا فإن plugins.entries.<id>.settings.<key> هو ما تقرؤه إضافتك لاحقًا. ويعتمد النموذج على جدول type:

Manifest typeالحقلمفاتيح إضافية
str (الافتراضي)إدخال نصيchoices: [a, b] (أو enum:) يحوله إلى قائمة منسدلة
int, floatإدخال رقمي
boolمفتاح تبديل
list, dictمحرر JSON
secretإدخال مخفيenv: MY_PLUGIN_TOKEN — متغير .env الذي يُخزَّن تحته (الافتراضي <PLUGIN_ID>_<KEY> بصيغة upper-snaked)

يقبل كل إدخال أيضًا label (أو title؛ وعند غيابهما يُعرض المفتاح بصيغة sentence case ، maps_api_key → "Maps API key")، و description (نص مساعدة تحت التسمية)، و default و required (يضع علامة Required).

الأسرار لا تصل إلى config.yaml. يحمل حقل secret لا يحمل إلا اسم .env فقط وما إذا كانت قيمة مضبوطة؛ ويخزّن Desktop القيمة عبر مسار بيانات الاعتماد نفسه المستخدم لمفاتيح API المزوّدين (PUT /api/env)، وتقرأها إضافتك باستخدام get_secret("MY_PLUGIN_API_KEY") من agent.secret_scope — تمامًا مثل إدخال requires_env. لا تقرأ .env, auth.json أو ملفات بيانات اعتماد أداة أخرى بنفسك مطلقًا (قاعدة الكتالوج 11). يرفض إجراء plugins.manage settings مفاتيح الأسرار وأي قيمة لا يتطابق نوعها أو choices مع المخطط.

الحزم المحمولة (plugin.json) تصرّح بالمخطط نفسه تحت مساحة أسماء المورّد (vendor namespace) الخاصة بـ Hermes، لأن Agent Plugins v1 ترفض الحقول العليا غير المعروفة:

السرّ الذي يسمّي env الخاص به متغيرًا يمرره mcp.json ("env": { "MY_PLUGIN_API_KEY": "${MY_PLUGIN_API_KEY}" }) يصل إلى خادم MCP فورًا: فبعد الحفظ، يعيد Hermes الاتصال بخوادم الإضافة التي تغيّرت مدخلات تشغيلها المحلولة (المفتاح الجديد يغيّرها، والتبديل (toggle) لا يغيّرها)، لذا يكون النموذج أيضًا المكان الذي يضبط فيه المستخدمون مفتاح الخادم.

تفاعل مع الحفظ دون polling. يبثّ كل حفظ plugin.<id>.settings.changed (الحمولة { written: [...keys] }؛ والحفظ الذي يخص الأسرار فقط يرسل قائمة فارغة)، فيعيد نصف Desktop قراءة تفضيلاته فورًا: ctx.onEvent('plugin.my-plugin.settings.changed', reload). اقرأ القيم من plugin_api.py الخاص بك باستخدام load_config_readonly() من hermes_cli.config (plugins.entries.<id>.settings)، مع الرجوع إلى القيم الافتراضية في المخطط.

استكشاف أخطاء اكتشاف الإضافات

إذا لم تظهر إضافتك — أو ظهرت لكنها لا تُحمَّل — اضبط HERMES_PLUGINS_DEBUG=1 للحصول على سجلات اكتشاف مطوَّلة على stderr:

ستَرى، لكل مصدر إضافات (مضمّن، مستخدم، مشروع، نقاط دخول):

  • الأدلة التي جرى فحصها وعدد البيانات الوصفية (manifests) التي أنتجها كل منها
  • لكل بيان: المفتاح المحسوم، والاسم، والنوع، والمصدر، والمسار على القرص
  • أسباب التخطّي: disabled via config، not enabled in config، exclusive plugin، no plugin.yaml, depth cap reached
  • عند التحميل: الإضافة قيد الاستيراد، بالإضافة إلى ملخّص من سطر واحد لما سجّلته register(ctx) (الأدوات، والـ hooks، وslash commands، وأوامر CLI)
  • عند فشل التحليل (parse): تتبّع استثناء كامل (أخطاء ماسح YAML، إلخ)
  • عند فشل register(): تتبّع كامل يشير إلى السطر في ملف __init__.py الخاص بك الذي رفع الخطأ

تُكتب نفس السجلات دائمًا إلى ~/.hermes/logs/agent.log عند مستوى WARNING (الإخفاقات فقط) ومستوى DEBUG (كل شيء) عند ضبط متغير البيئة. لذا إذا لم تستطع التشغيل مع متغير البيئة (مثلًا من داخل gateway)، تابع ملف السجل بدلًا من ذلك:

الأسباب الشائعة لعدم ظهور إضافة:

  • غير مفعّلة في الإعدادات — الإضافات اختيارية (opt-in). نفّذ hermes plugins enable <name> (يأتي الاسم من مُخرَج plugins list، والذي قد يكون <category>/<plugin> للتخطيطات المتداخلة).
  • بنية دليل خاطئة: تستخدم الحزم الأصلية ~/.hermes/plugins/<plugin-name>/plugin.yaml (مسطّحة) أو مستوى فئة واحد. تستخدم الحزم المحمولة plugin.json جذريًا في نفس المواقع. يُتجاهَل أي شيء أعمق من ذلك.
  • غياب __init__.py مفقود: تحتاج الحزم الأصلية إلى كل من plugin.yaml و__init__.py مع دالة register(ctx). لا تستورد الحزم المحمولة Python ولا تتطلّب __init__.py.
  • خطأ في kind — تحتاج مهايئات gateway إلى kind: platform في بياناتها الوصفية. تُكتشَف مزوّدات الذاكرة تلقائيًا كـ kind: exclusive وتُوجَّه عبر إعداد memory.provider بدلًا من plugins.enabled.

البنية النهائية لإضافتك

أربعة ملفات، بفصل واضح:

  • البيان (Manifest) يعلن ماهية الإضافة
  • المخططات (Schemas) تصف الأدوات لأجل LLM
  • المعالِجات (Handlers) تنفّذ المنطق الفعلي
  • التسجيل (Registration) يربط كل شيء معًا

الأداةمتى تُستخدم
breakpoint() + pdbمحلية، تفاعلية، الأبسط. أضف breakpoint() في الكود المصدري، شغّله بشكل عادي، واحصل على REPL عند ذلك السطر.
python -m pdbتشغيل سكربت موجود تحت pdb دون أي تعديل على المصدر. مفيدة للفحص السريع.
debugpyعن بُعد / بلا واجهة رسومية / «الاتصال بعملية قيد التشغيل فعلًا». يتحدث DAP، قابل للسكربتة من الطرفية، يعمل مع العمليات طويلة الأمد (gateway، daemon، عمليات PTY الفرعية).

ابدأ بـ breakpoint(). إنها أرخص وسيلة تنجح.

متى تستخدمها

  • يفشل اختبار ولا يكشف تتبّع الاستثناء (traceback) سبب خطأ إحدى القيم
  • تحتاج إلى الخطو عبر دالة ومراقبة تغيّر مجموعة (collection)
  • تسيء عملية طويلة التشغيل (hermes gateway، tui_gateway) التصرف ولا يمكنك إعادة تشغيلها
  • تحليل ما بعد الحدث (post-mortem): أُطلق استثناء في كود شبيه بالإنتاج وتريد فحص المتغيرات المحلية عند موضع الانهيار
  • عملية فرعية / تابعة (Python _SlashWorker، عامل جسر PTY) هي موضع الخطأ الفعلي

لا تستخدمها في: ما يحلّه print() / logging.debug في أقل من دقيقة، أو ما يكشفه أصلًا pytest -vv --tb=long --showlocals.

مزالق شائعة

  1. لا يفعل pdb شيئًا بصمت تحت مشغّل متوازٍ/يلتقط المخرجات. لن ترى الموجّه، والاختبار يتوقف فقط (صحيح مع pytest-xdist ومع العمليات الفرعية الملتقطة لكل ملف في scripts/run_tests.sh). شغّل pytest مباشرة على ملف واحد للتصحيح التفاعلي.

  2. breakpoint() في CI / سياقات بلا TTY يعلّق العملية. آمن محليًا؛ لا تلتزمه (commit) أبدًا. أضف بحث grep قبل الالتزام كشبكة أمان.

  3. PYTHONBREAKPOINT=0 يعطّل جميع استدعاءات breakpoint(). تحقّق من متغير البيئة إن كانت نقطة توقفك لا تُصاب:

  4. يحجب debugpy.listen فقط إن استدعيت أيضًا wait_for_client(). بدونها يستمر التنفيذ وقد تُطلق نقطة توقفك الأولى قبل اتصال العميل.

  5. يفشل الاتصال بـ PID على النواة المُشدَّدة (hardened). يسمح ptrace_scope=1 (الافتراضي في Ubuntu) فقط بـ ptrace من نفس المستخدم للعمليات الفرعية. الحل البديل: echo 0 > /proc/sys/kernel/yama/ptrace_scope (يحتاج صلاحيات root) أو التشغيل تحت debugpy من البداية.

  6. الخيوط (threads). يصحّح pdb الخيط الحالي فقط. للكود متعدد الخيوط، استخدم debugpy (وهو DAP واعٍ بالخيوط) أو عيّن threading.settrace() لكل خيط.

  7. asyncio. يعمل pdb في الدوال المشتركة (coroutines) لكن await داخل pdb يتطلب Python 3.13+ أو await من نمط interact في الإصدارات الأقدم. لإصداري 3.11/3.12، استخدم حيل asyncio.run_coroutine_threadsafe أو انتظارات (awaits) عبر !stmt باستخدام asyncio.ensure_future.

  8. يزيل scripts/run_tests.sh بيانات الاعتماد ويعيّن HOME=<tmpdir>. إذا كان خطؤك يعتمد على إعدادات المستخدم أو مفاتيح API حقيقية، فلن يتكرّر تحت الغلاف. صحّح باستخدام pytest الخام أولًا لإعادة إنتاجه، ثم تأكّد مجددًا تحت الغلاف.

  9. Forking / multiprocessing. لا يتتبّع pdb عمليات fork. تحتاج كل عملية فرعية إلى breakpoint() أو set_trace() خاصة بها. لـ subagents في Hermes، صحّح عملية واحدة في كل مرة.

قائمة التحقق

  • بعد pip install debugpy، تحقّق: python -c "import debugpy; print(debugpy.__version__)"
  • للتصحيح عن بُعد، تحقّق أن المنفذ يستمع فعليًا: ss -tlnp | grep 5678
  • نقطة التوقف الأولى تُصاب فعليًا (إن لم تُصب، فمن المرجّح أن لديك PYTHONBREAKPOINT=0، أو أنك تحت مشغّل متوازٍ/يلتقط المخرجات، أو انتهى التنفيذ قبل الاتصال)
  • يعرض where / w مكدس الاستدعاءات المتوقع
  • تنظيف ما بعد التصحيح: لا يوجد breakpoint() / set_trace() متبقٍّ في الكود الملتزَم (committed)

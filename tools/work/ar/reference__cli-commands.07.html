hermes update

يحدّث نسخة مصدر مسحوبة مقبولة ويجهّز الاعتماديات عبر PM. استخدم --check للمقارنة مع هدف المصدر المضبوط دون تطبيق التحديث. تحتفظ حزم Desktop و Docker و Nix و Termux بمسؤول التحديث الخارجي الخاص بها. راجع التحديث & إلغاء التثبيت دون التثبيت.

hermes update يتبع قناة التحديث لهذا التثبيت. تستخدم نسخة المصدر المسحوبة من المستودع الرسمي افتراضيًا stable، أي أحدث إصدار GitHub منشور يحمل vX.Y.Z عند commit نفسه؛ وتستخدم forks والمرايا افتراضيًا main. لمتابعة كل commit على main بدلًا من ذلك، نفّذ hermes update --set-channel main; hermes update --set-channel stable يعيد التبديل. على قناة main، قد تُحوَّل النسخة المسحوبة الموجودة على branch آخر إلى branch التحديث قبل السحب. أنشئ commit لعمل branch قبل التحديث إذا أردت إبقاءه خارج تدفق autostash الخاص بالتحديث.

الخيارالوصف
--install-idطباعة هوية هذا التثبيت ومساره، ثم الخروج.
--set-channel CHANNELحفظ قناة التحديث لهذا التثبيت المصدري دون تطبيق تحديث: stable (الإصدارات المنشورة) أو main (كل commit). للتطبيقات المُحزّمة قناة بناء ثابتة وترفض تغيير القناة.
--channel CHANNELاختيار قناة مصدر لهذا الاستدعاء فقط (stable أو main)؛ لا يُحفظ شيء.
--branch NAMEاختيار branch للمصدر في هذا الاستدعاء؛ يتقدّم على اختيار قناة المصدر.
--gatewayوضع داخلي يستخدمه أمر /update في المراسلة. يستخدم IPC القائم على الملفات للطلبات وبث التقدم بدلًا من القراءة من stdin الطرفية. ليس علامة لإعادة تشغيل gateway.
--checkالتحقق من توفر تحديث دون السحب أو تثبيت التبعيات أو إعادة تشغيل أي شيء.
--planطباعة خطة التحديث والخروج دون تغيير أي شيء: نوع التثبيت (git/Docker/Nix/apt)، وكل خدمة Hermes قيد التشغيل عبر جميع profiles مع المُشرِف (supervisor) وإصدار الكود قيد التشغيل، وكيفية إعادة تشغيل كل منها. في التثبيتات المُدارة بصورة (image) أو حزمة، يُبلَّغ عن أمر التحديث الخارجي الصحيح بدلًا من ذلك. للقراءة فقط.
--no-backupتخطي كل النسخ الاحتياطية قبل التحديث لهذا التشغيل (كلًا من لقطة الحالة السريعة وملف zip الكامل)، بغض النظر عن updates.pre_update_backup.
--backupفرض نسخة احتياطية كاملة قبل التحديث لهذا التشغيل: لقطة الحالة السريعة إضافةً إلى ملف zip كامل لـ HERMES_HOME (الإعدادات، المصادقة، الجلسات، المهارات، بيانات الاقتران). الوضع الافتراضي هو quick — لقطة حالة خفيفة فقط. اضبط الوضع الدائم عبر `updates.pre_update_backup: quick
--yes، -yافتراض الموافقة على الطلبات التفاعلية مثل ترحيل الإعدادات واستعادة stash. يُتخطى إدخال مفتاح API؛ شغّل hermes config migrate منفصلًا لذلك.

سلوك إضافي:

  • إعادة تشغيل الـ gateway. بعد تحديث ناجح، يحاول Hermes إعادة تشغيل كل profiles الـ gateway العاملة في المجلد الرئيسي الجاري تحديثه (جذره وكل profiles/<name> تحته) تلقائيًا لتستخدم الكود الجديد. تُسمَّى gateways وخدمات hermes-gateway* التابعة إلى HERMES_HOME مختلف على الجهاز نفسه — تثبيت آخر أو مجلد رئيسي مؤقت يشغّل hermes update — في المخرجات وتُترَك دون مساس. استخدم hermes gateway restart عندما تريد إعادة تشغيل gateway دون تطبيق تحديث.
  • استرجاع مرحلة إعادة التشغيل. إذا أُجهضت مرحلة إعادة التشغيل داخل العملية أثناء استيراد الشجرة المسحوبة حديثًا، تُعاد محاولة profiles الـ gateway المُشرَف عليها عبر عملية Python نظيفة. فقط عمليات إعادة الإطلاق المؤكَّدة بشكل مستقل بواسطة systemd (systemctl --user is-active) تُسجَّل كمُتحقَّق منها؛ أما إعادة الإطلاق التي خرجت برمز 0 فقط فتُسجَّل كـ relaunch_attempted وتظل إعادة التشغيل مستحقة (متابعة gateway_restart؛ ويظل التحديث نفسه يخرج بالرمز 0 لأن الكود في مكانه). لا تُنهى gateways اليدوية وبيئات serve/dashboard مطلقًا دون جهة مخوّلة بإعادة إطلاقها؛ تُسجَّل كمتجاوَزة مع السبب وتبقى في تقرير التحديث غير المكتمل مع أمر إعادة التشغيل الدقيق.
  • إيصالات التحديث + فحص إصدار الأسطول. كل تشغيل يكتب إيصالًا قابلًا للمعالجة آليًا إلى ~/.hermes/logs/update_receipts/ في مجلد Hermes الرئيسي الجذري، حتى من profile ثابت (خطة المجموعة قبل التحديث والخطوات والتجاوزات بأسبابها ونتيجة إعادة التشغيل والمتابعات؛ يشير latest.json إلى الأحدث ويعرض running أثناء التحديث). بعد مرحلة إعادة التشغيل، يتحقق المحدّث من كود كل gateway حيّة مقارنةً بالنسخة المحدّثة ويطبع مصفوفة إصدارات لكل profile. لا تؤدي gateway التي ما زالت على كود ما قبل التحديث إلى فشل التحديث بعد وجود الكود الجديد: يطبع التحديث سطر ⚠ مع أمر إعادة التشغيل الدقيق، ويخرج بالرمز 0 ويسجّل متابعة gateway_restart ويُبقي إعادة التشغيل مستحقة — يحذّر كل بدء CLI منها، ويعيد hermes update التالي المحاولة.
  • تغييرات المصدر المحلية. بالنسبة لتثبيتات git، تُخزَّن (auto-stash) الملفات المُتتبَّعة المتسخة والملفات غير المُتتبَّعة تلقائيًا قبل تحويل الفرع أو السحب (git stash push --include-untracked). التحديثات في طرفية تفاعلية تطلب تأكيدًا قبل استعادة الـ stash. التحديثات غير التفاعلية تستعيده افتراضيًا؛ اضبط updates.non_interactive_local_changes: discard فقط على التثبيتات المُدارة حيث ينبغي التخلص من تعديلات المصدر المحلية بعد سحب ناجح. إذا تعارضت استعادة الـ stash أو فشل السحب، يُترَك الـ stash في مكانه للاسترجاع اليدوي.
  • تراكم ملف قفل npm. قبل الـ stash أو تحويل الفروع، يجري Hermes تنظيفًا بأفضل جهد لفروقات package-lock.json المُتتبَّعة الناتجة عن خطوات npm install/build. أَودِع (commit) أو خزِّن (stash) يدويًا تعديلات ملف القفل المقصودة قبل تشغيل hermes update.
  • لقطة بيانات الاقتران. حتى عندما يكون --backup معطَّلًا، يأخذ hermes update لقطة خفيفة من ~/.hermes/pairing/ وقواعد تعليقات Feishu قبل git pull. يمكنك التراجع عنها بـ hermes backup restore --state pre-update إذا أعاد السحب كتابة ملف كنت تعدّله.
  • تحذير hermes.service القديم. إذا اكتشف Hermes وحدة systemd سابقة لإعادة التسمية باسم hermes.service (بدلًا من hermes-gateway.service الحالية)، يطبع تلميح ترحيل لمرة واحدة لتجنب مشكلات حلقة التذبذب (flap-loop).
  • رموز الخروج. 0 عند النجاح، 1 عند أخطاء السحب/التثبيت/ما بعد التثبيت، 2 عند تغييرات غير متوقعة في شجرة العمل تعيق git pull.

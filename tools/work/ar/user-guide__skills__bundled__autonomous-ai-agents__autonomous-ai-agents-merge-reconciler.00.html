Merge Reconciler

حلّ تعارض دمج (merge conflict) في git بين فرعَي وكيلَين (AGENTS)، بصفتك طرفًا ثالثًا محايدًا. الوكلاء الذين يحلّون التعارضات مقابل عمل نظير لهم يميلون بشكل موثوق إما إلى الكتابة فوق عمل النظير أو التخلي عن تغييرهم الخاص — فهم يفتقرون إلى سياق النظير وينحازون لجانبهم. هذه المهارة هي الحل: مُوفِّق محايد يستلم كلا الفرقين (diffs) مع النوايا المُصرَّح بها من الجانبين وينتج نتيجة مدمجة، مثل حَكَم قائمة الدمج (merge-queue arbiter).

متى تستخدمها

  • عندما يتصادم فرعا/worktree لوكيلين أثناء حملة عمل متوازية (خط أنابيب هندسي على Kanban، موجة PR متوازية، إعادة هيكلة عبر عدة worktrees).
  • عندما يتوقف git merge أو git rebase بسبب تعارضات بين عمل وكيلين ولا ينبغي لأيٍّ من الوكيلين الأصليين أن يحكم بنفسه.
  • لا تستخدمها للتعارضات داخل عمل وكيل واحد، أو للتعارضات التافهة في ملفات القفل (lockfile) أو الملفات المولَّدة (أعد توليدها بدلًا من ذلك).

المتطلبات المسبقة

  • نسخة مسحوبة (checkout) من المستودع تحتوي على الدمج المتوقف، أو اسما الفرعين مع صلاحية تنفيذ الدمج بنفسك.
  • مصادر نية كلا الجانبين: ملخصات إنجاز Kanban (عبر terminal بتشغيل hermes kanban show <task-id>)، أو نص PR، أو على الأقل رسائل commit كل فرع.
  • أمر البناء/الاختبار الخاص بالمشروع، إن وُجد.

كيفية التشغيل

مستقلة (Standalone) — يستدعي إنسان (أو وكيل) هذه المهارة داخل المستودع المتعارض: حمّل المهارة، ثم اتبع الإجراء من الأعلى إلى الأسفل.

وكيل محايد يُستدعى (Spawned) — الشكل المفضّل في الحملات متعددة الوكلاء:

  • delegate_task: أنشئ subagent تحتوي رسالة مهمته على مسار المستودع، واسمَي الفرعين، وملخصَي نية الجانبين حرفيًا، بالإضافة إلى تعليمة باتباع هذه المهارة.
  • أسلوب مبني على Kanban: أنشئ بطاقة توفيق (reconciliation) مُسندة إلى profile ثالث (ليس profile أيٍّ من العاملَين) مع ربط كلتا البطاقتين المتعارضتين كأبوين لها — kanban_create(title="reconcile branch-a x branch-b", assignee="reconciler", parents=["t_a", "t_b"]). تنقل روابط الأصل ملخصات إنجاز الجانبين تلقائيًا إلى سياق المُوفِّق؛ وينبغي أن يذكر نص البطاقة مسار المستودع والفرعين.

مرجع سريع

فئة الجزء المتعارض (hunk)التعريفالحل
disjoint-intent (نيّة منفصلة)التغييران يخدمان هدفين مختلفين ويمكن أن يتعايشاادمج كليهما
same-question-different-answer (سؤال واحد بإجابتين)أجاب الجانبان عن سؤال تصميم واحد بإجابتين مختلفتيناختر إجابة واحدة وفق النوايا المُصرَّح بها؛ واعرض القرار
superseded (تجاوزه الزمن)لم تعد فرضية أحد الجانبين قائمة بعد تغيير الآخرأبقِ على الجانب الصامد؛ ودوّن السبب

عقد الحياد: لا تُفضّل أبدًا الجانب الذي استدعاك؛ اقتصر على تعديل المناطق المتعارضة فقط (بلا تعديلات عرضية)؛ ويجب أن يظهر كل اختيار لسؤال تصميم صراحةً في ملخص التسليم.

الإجراء

1. اجمع الجانبين

  • نفّذ عبر terminal: git status (للتأكد من حالة التعارض وسرد الملفات المتعارضة)، ثم git merge-base <A> <B>، ثم لكل جانب git log --oneline <base>..<side> و git diff <base>..<side> -- <file> لكل ملف متعارض. في الدمج المتوقف، يمثّل HEAD أحد الجانبين ويمثّل MERGE_HEAD الجانب الآخر.
  • اجمع نية كل جانب: hermes kanban show <task-id> لملخصات/بيانات الإنجاز الوصفية، أو نص PR، أو رسائل commit من السجل أعلاه. دوّن جملة واحدة تلخّص نية كل جانب قبل لمس أي ملف.
  • تنتهي هذه الخطوة عندما تستطيع صياغة نية الجانبين بكلماتك وتمتلك كلا الفرقين (diffs) لكل ملف متعارض.

2. صنّف كل جزء متعارض (hunk)

  • افتح كل ملف متعارض باستخدام read_file وحدّد موضع كل كتلة <<<<<<</=======/>>>>>>>.
  • أسنِد لكل جزء فئة واحدة بالضبط من جدول المرجع السريع، بالحكم استنادًا إلى النوايا المُصرَّح بها — لا إلى أي التغييرين يبدو أفضل.
  • إذا احتوى جزء واحد على عدة قرارات مستقلة (مثلًا منطق جديد يندمج بسلاسة مع اختيار أسلوب/تقريب أجاب عنه الجانبان بشكل مختلف)، فكِّكه إلى قرارات فرعية وصنّف كل واحد منها.
  • غالبًا ما يمزج الملف الواحد بين عدة فئات: قد يكون جزء تصادمًا تصميميًا بينما يكون الجزء المجاور منفصل النية. صنّف حسب الجزء لا حسب الملف.
  • تنتهي هذه الخطوة عندما تحصل كل جزء على فئة مكتوبة ومسوّغ من سطر واحد.

3. الحلّ بموجب عقد الحياد

  • عدّل كل جزء باستخدام patch (أو write_file لإعادة كتابة الملف كاملًا):
    • disjoint-intent ← ادمج التغييرين معًا بحيث تُخدَم كل نية بالكامل.
    • same-question-different-answer ← اختر الإجابة الأنسب للنوايا المُصرَّح بها (مثلًا نية «التحقق الصارم» تتغلّب على «قيمة افتراضية سريعة» إذا كانت المهمة تتطلب الدقة). لا تقسّم الفارق أبدًا إلى حل هجين لم يطلبه أي جانب.
    • superseded ← أبقِ على الجانب الصامد؛ واحذف الفرضية الميتة.
  • لا تُفضّل أبدًا الجانب الذي استدعاك. وإذا تعادلت النوايا فعلًا، صعّد الأمر (عطّل بطاقة Kanban / أبلغ عن ذلك) بدلًا من التخمين.
  • لا تغيّر شيئًا خارج علامات التعارض — بلا تنسيق أو إعادة تسمية أو إصلاحات عرضية.
  • نفّذ git add لكل ملف مُحلّ عبر terminal.
  • تنتهي هذه الخطوة عندما لا يجد search_files أي علامات <<<<<<< في المستودع ويكون كل ملف محلول مُهيَّأً (staged).

4. التحقق

  • شغّل بناء/اختبارات المشروع عبر terminal؛ وفي أقل الأحوال استورد/نفّذ الوحدات (modules) التي طالها التعديل. يجب أن تكون كلتا النيتين ملحوظتين في السلوك المدموج (مثلًا الدلالات الجديدة للجانب A والإضافة المنفصلة للجانب B، كلتاهما حاضرة).
  • أكمل الدمج: git commit (تكفي رسالة الدمج الافتراضية مع نص يسرد قرارات الأجزاء).
  • تنتهي هذه الخطوة عند نجاح التحقق ووجود commit الدمج.

5. التسليم

  • أنتج ملخص إنجاز يذكر كل قرار جزء (hunk): file:lines — class — which side(s) kept — rationale. ولكل جزء من نوع same-question-different-answer، اذكر سؤال التصميم والإجابة التي اخترتها حتى يتمكن إنسان من الاعتراض عليها — لا تُخفِ قرارًا تصميميًا أبدًا.
  • على Kanban: kanban_complete(summary=...). في الوضع المستقل: اطبع الملخص.
  • تنتهي هذه الخطوة عند تسليم الملخص وسرده لكل الأجزاء.

المزالق

  • التحيّز الذاتي: إذا استدعاك أحد الوكيلين المتعارضين، فأنت منحاز بنيويًا — أقرّ بذلك ورجّح نية الجانب الآخر عمدًا. يُفضَّل استخدام شكل الـ profile الثالث كي لا ينشأ هذا الموقف أصلًا.
  • تقسيم الفارق في تصادم تصميمي ينتج حلًا هجينًا لم يصممه أحد؛ اختر إجابة واحدة واعرضها.
  • التصنيف حسب الملف: غالبًا ما تمزج الملفات بين فئات الأجزاء؛ تصنيف ملف كامل كفئة واحدة يُسقط بصمت تغييرًا منفصل النية.
  • التعديلات العرضية تجعل الدمج غير قابل للمراجعة وتسلب القرار من الوكيلين الأصليين.
  • غياب النوايا: قد تكون رسائل commit وحدها ضعيفة المحتوى؛ فضّل ملخصات إنجاز Kanban أو نصوص PR. وإذا تعذّر استرداد نية أي جانب، صعّد الأمر بدلًا من التخمين.
  • المخالفون المتكررون: تكرار التعارضات على نفس الملف عبر جولات متتالية هو مؤشر بؤرة مشكلة (hotspot)، وليس عملًا اعتياديًا للتوفيق — أبلغ عنه (مثلًا بتعليق Kanban على شكل hotspot: <path> — <reason>) كي يقوم المنسّق (orchestrator) بتفكيك ذلك الملف، بدلًا من التوفيق التسلسلي في كل تصادم جديد عليه.

التحقق

  • يُظهر git status شجرة نظيفة على الفرع الهدف مع وجود commit الدمج.
  • لا تبقى أي علامات تعارض (نمط search_files هو <<<<<<<).
  • تنجح عمليات البناء/الاختبار؛ وتكون نوايا الجانبين حاضرة بوضوح، أو يُذكر صراحةً في الملخص الجانب المُسقَط إن وُجد.
  • يسرد ملخص التسليم كل جزء (hunk) مع فئته ومسوّغه.

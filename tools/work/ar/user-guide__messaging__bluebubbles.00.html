BlueBubbles (iMessage)

اربط Hermes بخدمة Apple iMessage عبر BlueBubbles — وهو خادم مجاني ومفتوح المصدر يعمل على macOS ويصل iMessage بأي جهاز.

المتطلبات المسبقة

  • جهاز Mac (يعمل باستمرار) يشغّل BlueBubbles Server
  • حساب Apple ID مسجَّل الدخول في Messages.app على ذلك الـ Mac
  • BlueBubbles Server بالإصدار v1.0.0 أو أحدث (تتطلب الـ webhooks هذا الإصدار)
  • اتصال شبكي بين Hermes وخادم BlueBubbles

الإعداد

1. تثبيت BlueBubbles Server

نزّله وثبّته من bluebubbles.app. أكمل معالج الإعداد — سجّل الدخول بحساب Apple ID الخاص بك واضبط طريقة الاتصال (الشبكة المحلية، أو Ngrok، أو Cloudflare، أو Dynamic DNS).

2. الحصول على عنوان URL للخادم وكلمة المرور

في BlueBubbles Server → Settings → API، دوّن ما يلي:

  • Server URL (مثلًا http://192.168.1.10:1234)
  • Server Password

5. تشغيل الـ Gateway

6. التحقق من الإعداد

يحفظ معالج الإعداد بيانات اعتمادك في ~/.hermes/.env — وهو لا يكتب platforms.bluebubbles.enabled في ~/.hermes/config.yaml. وعند غياب إعداد صريح، يكفي وجود بيانات الاعتماد لبدء المهايئ؛ لكن قيمة enabled: false الصريحة تسود دائمًا على بيانات الاعتماد، لذا إذا عطّلت المهايئ سابقًا (أثناء استخدام جسر iMessage آخر مثلًا)، فسيُبلِغ المعالج عن النجاح، ولن يبدأ المهايئ رغم ذلك أبدًا.

تحقق من الإعداد المخزَّن:

  • true — مفعّل صراحةً
  • Config key not set — لا يوجد إعداد صريح؛ وبيانات الاعتماد في .env تحدّد التفعيل
  • false — معطّل صراحةً؛ ولن تغيّر إعادة الإعداد ذلك — اضبطه على true بنفسك

ثم راجع سجل gateway بحثًا عن السطرين اللذين يثبتان الاتصال وتسجيل webhook:

وأخيرًا، أرسل إلى نفسك رسالة اختبار من جهاز آخر: فالرد (أو رمز الإقران لرسالة مباشرة جديدة) دليل كامل على عمل التسليم الوارد.

آلية العمل

  • الوارد: يرسل BlueBubbles أحداث webhook إلى مستمع محلي عند وصول رسائل جديدة. لا يوجد استطلاع دوري (polling) — فالتسليم فوري.
  • الصادر: يرسل Hermes الرسائل عبر BlueBubbles REST API.
  • الوسائط:تُدعَم الصور والرسائل الصوتية والفيديو والمستندات في الاتجاهين. وتُنزَّل المرفقات الواردة وتُخزَّن مؤقتًا محليًا ليعالجها الوكيل.

عنوانا URL، في اتجاهين متعاكسين

يستخدم الإعداد عنواني URL يشيران في اتجاهين متعاكسين — فلا تخلط بينهما:

  • BLUEBUBBLES_SERVER_URL (مثل http://192.168.1.10:1234) — يستدعي Hermes الـ API الخاص بخادم BlueBubbles لديك. وهو Server URL الظاهر في BlueBubbles Server → Settings → API.
  • الـ webhook (الافتراضي http://localhost:8645/bluebubbles-webhook) — يرسل BlueBubbles أحداث الرسائل الجديدة إلى Hermes عبر POST. ويأتي المضيف/المنفذ/المسار من BLUEBUBBLES_WEBHOOK_HOST / BLUEBUBBLES_WEBHOOK_PORT / BLUEBUBBLES_WEBHOOK_PATH.

كيفية تسجيل webhook

أنت لا تحتاج إلى إنشاء webhook في واجهة BlueBubbles. فعندما يتصل gateway، يسجّله Hermes بنفسه عبر BlueBubbles REST API (/api/v1/webhook) لأحداث new-message و updated-message ، ويزيل التسجيل عند الإغلاق السليم.

تفصيلان يستحقان المعرفة:

  • يحمل عنوان URL المسجَّل كلمة مرور الخادم كمعامل استعلام (?password=…) لأن API الخاص بـ webhook في BlueBubbles لا يدعم الترويسات المخصَّصة — وهذه آلية مصادقة الأحداث الواردة.
  • يرتبط مستمع webhook بـ 127.0.0.1 افتراضيًا. وهذا مناسب عندما يعمل Hermes و BlueBubbles على الجهاز نفسه؛ وإذا كانا على جهازين مختلفين، فاضبط BLUEBUBBLES_WEBHOOK_HOST على عنوان يستطيع Mac الذي يشغّل BlueBubbles الوصول إليه.

الميزات

المراسلة النصية

أرسل رسائل iMessage واستقبلها. ويُزال تنسيق Markdown تلقائيًا لتسليم نص عادي نظيف.

الوسائط الغنية

  • الصور: تظهر الصور بشكل أصلي في محادثة iMessage
  • الرسائل الصوتية: تُرسَل الملفات الصوتية كرسائل iMessage صوتية
  • مقاطع الفيديو: مرفقات فيديو
  • المستندات: تُرسَل الملفات كمرفقات iMessage

تفاعلات Tapback

تفاعلات الحب والإعجاب وعدم الإعجاب والضحك والتأكيد والاستفهام. تتطلب Private API helper الخاص بـ BlueBubbles.

مؤشرات الكتابة

يعرض "typing..." في محادثة iMessage أثناء معالجة الوكيل للرسالة. يتطلب Private API.

إشعارات القراءة

يضع علامة "مقروءة" على الرسائل تلقائيًا بعد معالجتها. يتطلب Private API.

تحديد المحادثات

يمكنك تحديد المحادثات بالبريد الإلكتروني أو رقم الهاتف — إذ يحوّلها Hermes تلقائيًا إلى معرّفات GUID للمحادثات في BlueBubbles، فلا حاجة إلى استخدام صيغة GUID الخام.

Private API

تتطلب بعض الميزات Private API helper الخاص بـ BlueBubbles:

  • تفاعلات Tapback
  • مؤشرات الكتابة
  • إشعارات القراءة
  • إنشاء محادثات جديدة عبر العنوان

ومن دون Private API، تظل المراسلة النصية الأساسية والوسائط تعمل.

تنبيه: تفترض عبارة "المراسلة الأساسية تعمل دون Private API" أن BlueBubbles يستطيع التحكم في Messages.app في الواجهة الأمامية لمستخدم macOS مسجّل الدخول. وإذا ظل Mac المشغّل لـ BlueBubbles على شاشة تسجيل الدخول أو بُدِّل بعيدًا عن مستخدم الخادم (Fast User Switching)، يفشل الإرسال المعتمد على AppleScript — راجع BlueBubbles: عدة مستخدمين على Mac واحد. وفي هذا الإعداد يلزم Private API لإرسال موثوق، لا للميزات الإضافية أعلاه فقط.

استكشاف الأخطاء وإصلاحها

ظهور "Cannot reach server"

  • تحقق من صحة عنوان URL للخادم ومن أن الـ Mac قيد التشغيل
  • تحقق من أن BlueBubbles Server يعمل
  • تأكد من الاتصال الشبكي (جدار الحماية، وإعادة توجيه المنافذ)

الرسائل لا تصل

  • راجع hermes logs gateway بحثًا عن أخطاء webhook (أو hermes logs -f للمتابعة مباشرةً)
  • يسجّل Hermes الـ webhook بنفسه عند الاتصال — ولا تفحص BlueBubbles Server → Settings → API → Webhooks إلا إذا أظهر السجل فشلًا في التسجيل
  • صف webhook في واجهة BlueBubbles ليس دليلًا على التسليم؛ الدليل الكامل هو أن يسجّل Hermes الرسالة ويردّ عليها
  • إذا كان Hermes و BlueBubbles على جهازين مختلفين، فلا يستطيع Mac الوصول إلى عنوان الربط الافتراضي لـ webhook 127.0.0.1 — اضبط BLUEBUBBLES_WEBHOOK_HOST على عنوان يمكن الوصول إليه وأعد تشغيل gateway

نجح الإعداد، لكن المهايئ لا يبدأ أبدًا

  • hermes gateway setup يحفظ بيانات الاعتماد في ~/.hermes/.env ؛ ولا يضبط platforms.bluebubbles.enabled: true
  • قيمة enabled: false الصريحة في ~/.hermes/config.yaml تسود على وجود بيانات الاعتماد — تحقق باستخدام hermes config get platforms.bluebubbles.enabled
  • يحدث هذا غالبًا بعد تبديل جسور iMessage: فإذا استخدمت جسرًا آخر وعطّلت BlueBubbles وقتها، فلن تعيد عملية الإعداد تفعيله. اضبط enabled: true (وعطّل الجسر الذي لم تعد تستخدمه — فجسرا iMessage يعالجان الرسائل مرتين)

خادما BlueBubbles على Mac واحد (Apple ID غير صحيح)

  • يستخدم Hermes BLUEBUBBLES_SERVER_URL من ~/.hermes/.env ، لا Server URL الظاهر في واجهة BlueBubbles (الذي قد يكون متقادمًا بعد تغيير DHCP)
  • يشغّل مستخدما macOS على Mac واحد كلٌّ منهما خادم BlueBubbles خاصًا به مع منفذ API و Apple ID خاصين — تحقق من الخادم الذي يصل إليه Hermes: curl "http://<server-url>/api/v1/server/info?password=<password>" وقارن computer_id
  • ولإعداد عدة مستخدمين نفسه، اتبع BlueBubbles: عدة مستخدمين على Mac واحد — منفذ واحد لكل مستخدم، ولا تسجّل خروج المستخدم الذي يشغّل الخادم

ردود مكررة

  • مشكلة معروفة: قد تفصل معالجة الجلسات مراسلًا واحدًا إلى جلستين (صيغة GUID الخام مقابل صيغة الهاتف/البريد الإلكتروني) — تُتابَع في #30708 و #34372
  • ليست مشكلة توثيق أو إعدادات — تابع هاتين المسألتين للحصول على الإصلاحات

تكرار "♻️ Recovered reply"، أو تعليق الإرسال لدقائق

  • إذا ضُبط BLUEBUBBLES_HOME_CHANNEL (أو platforms.bluebubbles.home_channel)، فإن إعادة تشغيل gateway وإعادة اتصال المنصة تُخطران القناة الرئيسية وقد تعيدان تسليم الردود المعلّقة بالشكل "♻️ Recovered reply"
  • إذا فشل الإرسال من جانب BlueBubbles بصمت — وغالبًا بأخطاء AppleScript مثل Not authorized to send Apple events to Messages. (-1743) مع مهل طويلة لمستخدم macOS في الخلفية — تتراكم إعادات المحاولة وقد تزاحم تسليم webhook
  • اترك القناة الرئيسية فارغة إلى أن تثبت موثوقية الإرسال، وفعّل مساعد Private API لإعدادات المستخدمين في الخلفية (راجع Private API)

ظهور "Private API helper not connected"

  • ثبّت Private API helper: docs.bluebubbles.app
  • تعمل المراسلة الأساسية من دونه — ولا تتطلبه إلا التفاعلات ومؤشرات الكتابة وإشعارات القراءة

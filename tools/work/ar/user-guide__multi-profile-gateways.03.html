أي الـ profiles تُخدَم

يخدم gateway.multiplex_profiles: true الـ profile الافتراضي إضافة إلى كل profile مسمّى حيّ تحت profiles/، باستثناء تلك التي استُبعدت باستخدام gateway.standalone: true في ملف config.yaml الخاص بها — إذ يشغّل الـ profile المستقل gateway خاصًا به ولا يدرجه المضيف (راجع لا gateways جديدة لكل profile). (الخيار السابق gateway.multiplex_profile_allowlist السابق أُلغي؛ يزيله ترحيل الإعدادات من config.yaml، ويُؤرشف أو يُحذف بدلًا من ذلك الـ profile الذي لا تريد تقديمه ولم يستبعد نفسه — hermes profile delete <name>، أو انقل الدليل خارج profiles/.) تترك الـ profiles المحذوفة شاهدًا (tombstone) ولا تُعدَّد أبدًا؛ ولا يُعاد إنشاء profile اختفى دليله أبدًا من قِبل دور مخدوم، أو مؤقّت cron، أو توجيه السجلات.

تتحكم المجموعة المخدومة في بادئات /p/<profile>/ الخاصة بـ API و webhook، وحالة بيئة التشغيل، وأهلية توجيه الـ profile، والـ profiles التي يشغّل لها مجدول cron داخل العملية دوراته (يعيد مؤقّت backend الخاص بـ Desktop تعداد المجموعة نفسها في كل دورة — وينضم profile أُنشئ أثناء عمل Desktop إلى مجموعة الدورات أو يغادرها إذا حُذف دون إعادة تشغيل — ويتنحّى لأي profile يقدّمه بالفعل مُعدّد إرسال جارٍ أو gateway خاص به). مُعدّد إرسال بدأ باستخدام hermes -p <name> gateway run يجري دائمًا مخزن cron الخاص بـ profile نفسه أيضًا.

المجموعة المخدومة حيّة. يُخدَم profile أُنشئ أثناء تشغيل المضاعِف (hermes profile create، أو لوحة التحكم، أو Desktop، أو TUI) فورًا: يُرسل المنشئ إشارة إلى المضاعِف عبر مقبس التحكم (control socket) الخاص به، كما يعيد المضاعِف فحص profiles/ كل 30 ثانية كإجراء أمان إضافي. تُبنى مهايئات الـ profile الجديد بمجرد أن يتضمن config.yaml/.env token لبوت (عادةً ينشئ المستخدم الـ profile أولًا ثم يضيف الـ token)، وتُحدَّث served_profiles في ملف gateway_state.json الخاص بالـ profile الافتراضي، ويبلّغ hermes -p <name> gateway status أنه مقدَّم — دون إعادة تشغيل، ودون المساس بمهايئات الـ profiles الأخرى أو أدوارها الجارية. ويؤدي حذف profile إلى إيقاف مهايئاته وإزالة توجيهها بالطريقة نفسها، ويزيل hermes profile rename توجيه الاسم القديم قبل نقل المجلد ويقدّم الاسم الجديد أثناء التشغيل (ولا تعيد المهايئات أو مؤقّت cron اللذان كانا مرتبطين بالاسم القديم إحياءه). وتظل قاعدة بيانات اعتماد واحدة لكل مستقصٍ سارية: يُعلَّق الـ profile المضاف أثناء التشغيل الذي يعيد استخدام token لـ profile آخر مع duplicate_credential كخطأ، ولا يُشغَّل أبدًا كمستقصٍ ثانٍ.

يوسّع الخدمة الساخنة (hot-serving) أيضًا حجز profile الخاص بالمُضاعِف (multiplexer): إذ يُؤخذ gateway.lock الخاص بالـ profile الجديد وتُبنى سلطة الجلسات الخاصة به، فيجد hermes -p <name> المُضاعِف بوصفه مالكه (دون daemon منفصل شارد لكل profile)، ويحجز hermes gateway restart التالي المجموعة كلها بسلاسة. أما الـ profile الذي يتعذّر فتح state.db الخاص به فيُوضع في الركن (parked) — يُسجَّل باسم Profile '<name>' not served ويُستبعد من served_profiles — وتستمر بقية الـ profiles في الإقلاع؛ أصلح المخزن ثم أعد تشغيل hermes profile create أو انتظر الفحص الدوري.

توجيه محادثات البوت المشتركة إلى الـ profiles (profile_routes)

يختار الـ multiplexing profile لكل بيانات اعتماد (رمز البوت الخاص بكل profile) أو لكل بادئة رابط (URL prefix) (/p/<profile>/ لمنصات HTTP). عندما تشترك عدة مجتمعات في token واحد للبوت — مثل بوت Discord واحد يخدم guilds متعددة — يمكنك أيضًا توجيه مستخدمين/guilds/قنوات/threads محدَّدة إلى profiles مختلفة باستخدام gateway.profile_routes:

تُطابَق المسارات بحسب درجة تخصيص تراكمية: user_id = 16, thread_id = 8, chat_id = 4، و guild_id = 2. لذا يتقدّم user_id + chat_id (20) على user_id وحده (16)، وهذا يتقدّم على كل مسار يعتمد على الموقع فقط (14 كحد أقصى). يجب تحقق جميع الحقول المصرّح بها (AND)، وتحتفظ الدرجات المتساوية بترتيب التصريح، كما يطابق المسار المعتمد على قناة threads ومنشورات المنتديات التي تكون تلك القناة أصلها. تبقى الرسائل التي لا تطابق أي مسار في الـ profile الافتراضي/النشط. ويحصل الـ profile المُوجَّه على العزل الكامل لكل profile الموضّح أعلاه (الإعدادات والمهارات والذاكرة وبيانات الاعتماد ونطاق أسماء الجلسات). يعمل التوجيه على كل مهايئ منصة، وليس Discord فقط.

user_id هو مرسِل الرسالة الواردة، وتُقارَن قيمته للتطابق التام. تعتمد موثوقيته على المهايئ الذي يبلّغ عنه، فلا تعتبره مدخل تفويض إلا في المنصات التي تصادق على المرسل عند الاستقبال. كما تُحدّد معرّفات المرسلين بنطاق المستأجر في بعض المنصات — فمعرّف مستخدم Slack محلي لمساحة العمل — لذا عند تقديم gateway لأكثر من مساحة عمل أو خادم، اقرن user_id بقيمة guild_id الخاصة بذلك النطاق (Discord guild أو مساحة عمل Slack أو خادم Matrix) بدلًا من الاعتماد على المعرّف وحده.

يؤدي حذف user_id إلى إبقاء المسار غير مقيّد بالمرسل للتوافق مع الإصدارات السابقة. أما ضبطه على null أو سلسلة فارغة أو مسافات بيضاء فيُبطل المسار بدلًا من توسيعه ليشمل كل مرسل على المنصة.

يختار التوجيه بحسب المرسل profile؛ ولا يشكّل تفويضًا قائمًا على المنع الافتراضي. ينتقل المرسل الذي لا يطابق أي مسار إلى الـ profile الافتراضي/النشط، تمامًا كالقناة غير الموجَّهة. لمنح شخص واحد profile مميّزًا وجميع الآخرين profile مقيّدًا، صرّح أولًا بمسار المرسل المميّز، ثم أضف بعده مسارًا شاملًا على مستوى المنصة إلى الـ profile المقيّد، وأبقِ قائمة السماح الخاصة باستقبال المنصة قائمة.

لا ينطبق المسار إلا على الرسائل التي يستقبلها بوت الـ profile الافتراضي ما لم يسمِّ بوتًا آخر بـ bot_profile: <profile>. تستخدم الرسائل المباشرة في Telegram قيمة chat_id نفسه لكل بوت (معرّف المستخدم)، لذا من دون هذا فإن مسار chat_id مقصودًا للبوت المشترك سيلتقط أيضًا رسائل ذلك المستخدم المباشرة مع بوت مخصص تابع لـ profile ثانوي. تبقى الرسائل الواصلة إلى بوت خاص بـ profile ثانوي داخل ذلك الـ profile:

يُحسَم التفويض لرسالة موجَّهة دائمًا بواسطة profile البوت المستقبِل (رمزه وقائمة سماحه)، بما في ذلك المتابَعات المرسَلة أثناء انشغال الوكيل والفحوص أثناء الدور مثل /topic أو /stop؛ ولا يحتاج الـ profile الموجَّه إليه نفسه أي نسخة من قائمة السماح. يتلقى profile موجَّه إليه لا يملك بوتًا خاصًا به أيضًا الإشعارات الخلفية (اكتمالات العمليات، والنبضات، ونتائج التفويض غير المتزامن) عبر البوت المشترك بعد إعادة تشغيل الـ gateway.

على WhatsApp و WhatsApp Cloud، يطابق مسار chat_id عبر أشكال هوية المستخدم المختلفة: رقم هاتف مجرد (15551234567)، و JID (15551234567@s.whatsapp.net)، و LID (…@lid) — كلها تشير إلى الشخص نفسه بمجرد أن يقرنها الجسر (bridge) (نفس التحويل القانوني (canonicalization) الذي تستخدمه مفاتيح جلسات المطابقة وقوائم سماح المحوّل بالفعل). يمكنك وضع رقم الهاتف في profile_routes وستظل الرسائل المباشرة الواردة تطابق سواء سلّم WhatsApp JID أو LID. من دون ربط LID بعد، يظل شكل الرقم يطابق JID (تُحذَف اللاحقة) لكنه لا يستطيع حل LID مجهول — يسقط ذلك الوارد عندئذٍ إلى الـ profile الافتراضي إلى أن يظهر الربط. محادثات المجموعات (…@g.us) ليست هويات مرسِل وتظل تطابق تمامًا. تبقى معرّفات Telegram الرقمية دون تغيير.

يتطلب profile_routes وجود gateway.multiplex_profiles: true؛ ومع إيقاف الـ multiplexing تُتجاهَل المسارات. إذا طابق مسار صريح لكنه يستهدف profile غير مثبَّت (أو محذوف)، ترفض الـ gateway ذلك الوارد وتسجّل المسار والهدف. ولا تُشغِّل الـ profile الافتراضي. أما الحركة التي لا تطابق أي مسار فتحافظ على السلوك الافتراضي التاريخي للـ profile.

تُسلَّم مهام cron التي يملكها profile موجَّه إليه عبر البوت المشترك أيضًا، لكن فقط للأهداف التي يربطها مسار مفعَّل بـ chat_id/thread_id بذلك الـ profile (يؤهِّل مسار guild_id + chat_id قناته) — لا تُرسَل أبدًا مهمة لـ profile موجَّه إليه تستهدف محادثة غير موجَّهة (أو محادثة موجَّهة إلى profile آخر) عبر البوت المشترك. لا تؤهِّل المسارات المقتصرة على guild فقط هدف cron؛ أضف مسار chat_id لقناة التسليم. ولا تتأهل أيضًا المسارات التي تصرّح بـ user_id: لا يوجد لدى cron مرسِل وارد مُصادَق عليه، لذا تحتاج إلى مسار منفصل يعتمد على الموقع فقط. ولا يحتاج الـ profile المُوجَّه إلى platforms.<platform> الخاص به لهذا: يأتي تفويض البوت المشترك من المسار، لا من إعدادات القمر الصناعي (satellite).

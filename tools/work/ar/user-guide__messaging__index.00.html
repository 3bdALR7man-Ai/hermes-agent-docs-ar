Messaging Gateway

تحدث مع Hermes من Telegram أو Discord أو Slack أو WhatsApp أو Signal أو SMS أو Email أو Home Assistant أو Mattermost أو Matrix أو DingTalk أو Feishu/Lark أو WeCom أو Weixin أو BlueBubbles (iMessage) أو QQ أو Yuanbao أو Microsoft Teams أو LINE أو ntfy، أو من متصفحك. الـ gateway عبارة عن عملية خلفية واحدة تتصل بكل منصاتك المُعدّة، وتدير الجلسات، وتشغّل مهام cron، وتسلّم الرسائل الصوتية.

لمجموعة ميزات الصوت كاملة — بما في ذلك وضع الميكروفون في CLI، والردود المنطوقة في المراسلة، والمحادثات الصوتية في Discord — راجع الوضع الصوتي (Voice Mode) واستخدام Voice Mode مع Hermes.

نصيحة

تحتاج البوتات إلى مزوّد نموذج ومزوّدي أدوات (TTS، الويب) معًا. يجمع اشتراك Nous Portal بينهما جميعًا.

حالة المراسلة في Desktop ولوحة التحكم

تنتمي حالة المراسلة إلى الـ profile المحدد على الجهاز المحدد. يمكن لبيانات الاعتماد المحفوظة عبر hermes gateway setup تفعيل منصة تعتمد على بيانات الاعتماد دون وجود إدخال platforms في config.yaml؛ أما platforms.<name>.enabled: false الصريح فيظل يعطّلها. لا يرث profile مختلف أبدًا بيانات اعتماد عملية الخادم. المنصات التي تفتقر إلى حقول بيانات الاعتماد المطلوبة لا تُفعَّل لمجرد أن تلك القائمة فارغة.

تسمية profile الخادم نفسه صراحةً (مثل profile=default على خادم بـ profile افتراضي) تعطي نفس حالة الطلب غير المحدد النطاق. تعني Saved أن بيانات الاعتماد مخزّنة، لا أن messaging gateway يعمل أو أن المنصة متصلة. يمكن أن تُظهر منصة مفعّلة بشكل صحيح Messaging gateway stopped.

Hermes Relay

Hermes Relay (تجريبي) ليس منصة محادثة بحد ذاته — بل هو نظام موصلات (connector) يقف أمام منصات مثل Discord و Telegram و Slack و WhatsApp عبر موصل خارجي يملك بيانات اعتماد المنصة. تُتفاوض القدرات (الوسائط، مطالبات الموافقة/الاستيضاح الأصلية، التفاعلات، Threads، الكتابة، Streaming) لكل موصل عند المصافحة (handshake) بدلًا من أن تكون ثابتة كما في الجدول أعلاه.

البنية المعمارية

يستقبل كل platform adapter الرسائل، ويوجّهها عبر مخزن جلسات لكل محادثة، ثم يرسلها إلى AIAgent للمعالجة. يشغّل الـ gateway أيضًا جدولة cron، بمعدل نبضة كل 60 ثانية لتنفيذ أي مهام مستحقة.

رموز الصمت المتعمد (Intentional Silence Tokens)

في المحادثات الجماعية والـ hooks وتدفقات الأتمتة، يدعم Hermes رموز صمت صريحة. إذا كانت الاستجابة النهائية للوكيل هي بالضبط أحد الرموز المدعومة، يوقف الـ gateway التسليم الصادر ولا يرسل شيئًا إلى المحادثة.

الرموز المدعومة:

  • [SILENT]
  • SILENT
  • NO_REPLY
  • NO REPLY
  • [静默] / 静默 و [沉默] / 沉默 — الصيغ الصينية التي ينتجها النموذج حين يترجم العلامة الحارسة بدلًا من إخراجها حرفيًا

تُطبَّع المسافات البيضاء وحالة الأحرف، لكن يجب أن تكون الاستجابة النهائية بأكملها هي الرمز نفسه. جملة مثل "استخدم [SILENT] عندما لا يتغيّر شيء" تُسلَّم بشكل طبيعي.

الصمت قرار تسليم فقط. يحتفظ Hermes بدور صمت المساعد في نص الجلسة، بحيث تظل المحادثة تتناوب بشكل طبيعي:

تظل الأدوار الفاشلة تظهر كأخطاء؛ لا يخفي Hermes الإخفاقات لمجرد تشابه النص مع token للصمت.

عند ورود رسالة من شخص، يُستبدل token صمت منفرد بتنبيه قصير، لأن الرسالة التي تحتاج إلى رد يجب ألا تختفي. قد تظل التنبيهات الداخلية، مثل إشعارات عمليات الخلفية، صامتة، وكذلك الرسالة التي يبلّغ مهايئ المنصة أنها غير موجّهة إلى البوت. يبلّغ Slack عن ذلك للرسائل التي تبدأ بإشارة @mention لشخص آخر، وللرسائل على المستوى الأعلى دون إشارة التي تبدأ thread جديدًا في قناة رد حر؛ وتحصل المنصات الأخرى على التنبيه دائمًا.

أوامر Gateway

تفريغ المكدس عند الطلب (SIGUSR2)

على Linux و macOS، يُلحق kill -USR2 <gateway pid> تفريغًا لمكدس كل thread بملف ~/.hermes/logs/gateway_faulthandler.log ويواصل gateway العمل — استخدمه لمعرفة ما يفعله gateway متوقف عن الاستجابة أو سيئ التصرف دون إعادة تشغيله.

مراقب مدمج لحيوية حلقة الأحداث

على كل منصة، يشغّل gateway thread مراقبة خارج الحلقة يفحص حلقة asyncio (gateway.loop_watchdog_probe_interval_s، الافتراضي 30 s). عندما تتوقف الحلقة عن إرسال المهام لمدة gateway.loop_watchdog_max_strikes فحوص متتالية (الافتراضي 3)، تكون أعمال الصيانة ومجدول cron وموزّع Kanban المضمّن قد تجمّدت معها أيضًا، لذا يفرّغ المراقب مكدس كل thread في السجل، ويضع في gateway_state.json قيمتي gateway_state: degraded و exit_reason: loop_liveness_watchdog، ويخرج بالرمز 75 كي يعيد مشرف الخدمة تشغيل العملية. يعرض hermes gateway status ذلك السجل بالشكل ⚠ Gateway exited degraded: event loop stopped dispatching … حتى تستبدله عملية gateway جديدة، وتعرض شارة gateway في لوحة التحكم Degraded بالسبب نفسه. اضبط gateway.loop_watchdog: false في config.yaml لتعطيل المراقب.

تحدّث أعمال الصيانة أيضًا قيمة gateway_state.json الخاصة بـ updated_at كل مرة (60 s)، فتعمل كنبض أيضًا: عندما تظل العملية حية لكن مضى أكثر من 120 s على التحديث، يطبع hermes gateway status الرسالة ⚠ Gateway heartbeat stale: housekeeping has not refreshed gateway_state.json for N s … وتعرض شارة لوحة التحكم Heartbeat stale — وهي حالة "يبدو أنه يعمل لكن لا يُجدول شيء". أعد تشغيل gateway.

مراقب حلقة الأحداث الاختياري في Linux (event-loop watchdog)

يمكن لـ gateway تديره systemd أن يفعّل استرداد العملية عند توقف حلقة أحداث asyncio في Python عن تلقّي وقت الجدولة. يغطي هذا حالات التجمّد الكامل للعملية التي تمنع أيضًا مهام فحص الحيوية (liveness) الخاصة بالمنصات من العمل:

القيمة الموجبة تجعل الوحدة المُولَّدة تستخدم Type=notify، وNotifyAccess=main، وWatchdogSec المطابقة. يرسل Hermes نبضات (heartbeats) فقط بينما تُحرز حلقة أحداثه تقدمًا في الوقت المناسب؛ يعيد systemd تشغيل العملية عند توقفها. القيمة الافتراضية 0 تُبقي سلوك Type=simple الحالي. هذا الإعداد خاص بـ Linux/systemd فقط ولا يعامل انقطاع شبكة عادي في إحدى المنصات كفشل في حلقة الأحداث.

إدارة الجلسات

استمرارية الجلسة

تستمر الجلسات عبر الرسائل حتى يُعاد ضبطها. يتذكر الوكيل سياق محادثتك.

العثور على الجلسات السابقة (/sessions)

يعرض /sessions جلساتك السابقة للمحادثة الحالية — بما في ذلك الجلسة التي أنت فيها الآن، والمُعلّمة بـ (current) — بينما تستأنف /sessions <name> إحداها (اختصار لـ /resume). عندما تطول القائمة، تُصفّي /sessions search <query> (بالاسم البديل find) حسب تطابق العنوان أو معرّف الجلسة، مرتبةً بحسب الأحدث نشاطًا. عرض الجلسات عبر مصادر مختلفة بـ /sessions all مقتصر على admin فقط — يتلقى المستخدمون العاديون إشعارًا يوضح أن القائمة بقيت مقتصرة على نطاق المحادثة، ولا يرون أبدًا سوى جلسات من مصدر محادثتهم الخاص.

تجاوزات /model الدائمة

يُطبَّق تبديل /model في محادثة gateway على تلك الجلسة، وهو الآن يبقى بعد إعادة تشغيل الـ gateway: يُحفظ اختيار النموذج/المزوّد في مخزن الجلسة ويُستعاد عند أول استخدام بعد إعادة التشغيل (تُعاد معالجة بيانات الاعتماد وقت التحميل ولا تُكتب أبدًا على القرص). يمسح /new (أو /reset) هذا التجاوز، بينما تكتب /model <name> --global القيمة مباشرة إلى config.yaml. تُطبَّق /model <name> --once على دور واحد فقط.

موثوقية التسليم

تُسجَّل استجابات الوكيل النهائية في دفتر تسليم (delivery ledger) دائم (state.db) حول كل إرسال إلى منصة. إذا تعطّل gateway أو أُعيد تشغيله بين إنتاج رد وتأكيد المنصة استلامه، يعيد الإقلاع التالي تسليم الرد المخزَّن بدلًا من فقدانه — أو إعادة تشغيل الدور كله. يوجد السجل في المجلد الرئيسي الذي بدأ منه gateway؛ ويحتفظ gateway متعدد الإرسال بردود كل profiles المقدَّمة فيه أيضًا.

الدلالات صادقة من نوع at-least-once:

  • الاستجابة التي لم يبدأ إرسالها أبدًا تُعاد تسليمها كما هي.
  • الاستجابة التي كانت قيد الإرسال عندما توقف gateway (قد تكون المنصة تلقته أو لم تتلقه)، بما فيه إعادة تسليم كان إقلاع سابق لا يزال يرسلها، يُعاد تسليمه مع البادئة الظاهرة "♻️ Recovered reply — … may be a duplicate". يُميَّز الغموض، ولا تُعاد الرسالة بصمت أبدًا.
  • الإرسال النهائي الذي ترفضه ضوابط الفيضان (flood control) (مثل حدود معدل Telegram) يُعاد المحاولة تلقائيًا بعد انتهاء الجزاء المسجّل، دون الحاجة إلى إعادة اتصال أو إعادة تشغيل. تعتمد إعادة التشغيل أثناء الجزاء الرد المخزّن دون استهلاك محاولة إعادة أو إعادة تشغيل الوكيل. تحتفظ إعادة المحاولة بملف البوت والمحادثة والمسار الفرعي الأصليين. تحذّر بادئة استرداد حدّ المعدل من أن أجزاء سابقة قد تكون وصلت بالفعل؛ لا يستطيع الدفتر استنتاج التسليم الجزئي من طول الرسالة.
  • تُعاد محاولة أي إرسال نهائي مرفوض آخر (خطأ 5xx من المنصة أو خطأ غير مصنّف) بالطريقة نفسها بعد تأخير متزايد (30 s ثم 2 دقيقة)؛ وتُترك المحاولة الأخيرة ضمن الميزانية لبدء gateway التالي، فلا يترك انقطاع يتجاوز المؤقّت الرد عالقًا أبدًا. لا تُعاد المحاولة لمحادثة يتعذر الوصول إليها نهائيًا (بوت محظور أو مجموعة محذوفة).
  • إعادة التسليم محدودة: 3 محاولات، وحداثة لمدة 24 ساعة، ثم يُتخلّى عن الصف. تُحذف الصفوف المُسلَّمة بعد 7 أيام.

عطّل هذا عبر gateway.delivery_ledger: false في config.yaml (يعيد السلوك القديم: تُفقد الاستجابات قيد التنفيذ عند التعطل).

استمرارية الجلسة

لا تُعاد ضبط محادثات الـ gateway بعد فترة خمول أو عند حد يومي. استخدم /new أو /reset لبدء محادثة جديدة صراحةً؛ يظل ضغط السياق تلقائيًا. تُتجاهل إعدادات session_reset وتجاوزات سياسة إعادة الضبط ومتغيرات البيئة الخاصة بمؤقّتها. إذا كانت إعداداتك لا تزال تضبط session_reset.mode على idle, daily أو both، يحذّر بدء تشغيل gateway وأمر hermes doctor من ذلك. للإبقاء على عمليات إعادة الضبط الزمنية، ثبّت إضافة الكتالوج التي تقرأ الكتلة نفسها دون تغيير: hermes plugins install hermes-session-reset-policy. يمكن تحرير الوكلاء المخزَّنين مؤقتًا لاستعادة الموارد دون استبدال المحادثة الدائمة. تحدّ حداثة الاستعادة بعد إعادة التشغيل من المتابعة التلقائية، لا من السجل الذي يُحمَّل عندما ترسل رسالة.

تجاوزات النموذج و system prompt لكل قناة

يمكن لقنوات مختلفة تشغيل نماذج وشخصيات مختلفة من gateway واحد — مثلًا نموذج سريع ورخيص في #daily ونموذج متقدم بـ prompt متخصص في #dev. اضبط channel_overrides تحت المنصة في ~/.hermes/config.yaml:

تفاصيل:

  • المفاتيح الثلاثة جميعها اختيارية — اضبط model فقط، أو system_prompt فقط، أو أي مزيج منهما. الحقول غير المضبوطة تعود إلى القيم الافتراضية العامة.
  • ترتيب البحث هو معرّف القناة/المسار الفرعي الدقيق أولًا، ثم معرّف القناة/المنتدى الأصل (parent) — بحيث ترث مسارات Discord الفرعية تجاوز قناتها الأصل تلقائيًا.
  • أولوية تحديد النموذج هي: تجاوز /model للجلسة ← channel_overrides ← الإعدادات العامة. المستخدم الذي يشغّل /model في محادثة يظل له الأولوية على افتراضي القناة.
  • يستبدل تجاوز system_prompt prompt الـ gateway العام لتلك القناة (وهو مؤقت — يُحقَن في كل دور، ولا يُخزَّن في السجل).

من مشكلة GitHub إلى طلب pull request

حوّل مشكلة (issue) على GitHub إلى PR مُختبَر وموثَّق. تتولّى هذه المهارة الانضباط من البداية للنهاية — التحقّق من صحة الفرضية، مسح التكرارات، الإصلاحات على مستوى الفئة، والتقارير الصادقة عن CI؛ أمّا مهارات GitHub والتطوير الشقيقة فتتولّى آلياتها الخاصة.

متى تُستخدم

  • "أصلح المشكلة رقم 123 وافتح PR."
  • "نفّذ طلب الميزة هذا على GitHub."
  • "خذ هذا الخطأ من مشكلة إلى CI ناجح."

لا تستخدمها من أجل: مراجعة PR موجود، أو الإجابة عن سؤال بخصوص الكود بدون طلب تغيير.

الإجراء

1. اقرأ المشكلة الحيّة — النص الأساسي والمحادثة الكاملة

استخدم terminal لتنفيذ gh issue view <N> --comments. النص الأساسي هو لقطة من وقت تقديم المشكلة؛ بينما تحمل أحدث التعليقات الحالة الحيّة: إصلاحات جزئية دُمجت بالفعل، تحليلات جديدة للسبب الجذري، قرارات الصائنين (maintainers)، أو أسئلة موجَّهة إليك تُغيّر المهمة. اقرأ أيضًا تعليمات المستودع (AGENTS.md، مستندات المساهمة) باستخدام read_file. تنتهي هذه الخطوة عندما يكون السلوك المطلوب حاليًا، والأهداف المستبعَدة، وأي أسئلة غير مُجاب عنها في المحادثة، معروفة.

2. امسح بحثًا عن عمل موجود أو مكرَّر

قبل كتابة أي شيء، نفّذ gh pr list --search "#<N>" --state all إضافةً إلى نسختين على الأقل من الكلمات المفتاحية/المرادفات للعرَض (gh pr list --search "<subsystem> <symptom>" --state open). تجتذب المشكلات الشائعة إصلاحات مستقلة متعدّدة؛ وبناء نسخة مكرَّرة يهدر الجهد والفضل. تحقّق أيضًا مما إذا كان commit حديث قد أصلحها بالفعل: git log --oneline -20 -- <relevant files>. تنتهي هذه الخطوة عندما تعرف كل PR مفتوح وكل commit حديث يلامس هذه المشكلة، أو أن لا شيء من ذلك موجود.

3. تحقّق من صحة الفرضية مقابل الكود الحالي — ومقابل نية التصميم

أعِد إنتاج الخطأ أو أثبِت السلوك المفقود على الفرع الافتراضي الحالي باختبار أو fixture فاشل، مستخدمًا search_files وread_file لتتبّع المسار المُبلَّغ عنه. ثم تحقّق من السؤال الثاني: هل "الخطأ" هو في الواقع تصميم متعمَّد؟ نفّذ git log -p -S "<symbol>" على الكود الذي تريد المشكلة تغييره واقرأ نية الـ commit الأصلي — فغياب رابط أو وجود قيد ما هو غالبًا الميزة نفسها. اطعن في نص المشكلة القديم أو المعيب بدلًا من تنفيذه أعمى. تنتهي هذه الخطوة عندما يُثبَت السبب الجذري أو الفجوة في الميزة في الكود الحالي، وعندما لا يتعارض التغيير مع تصميم مقصود.

4. حدِّد معايير القبول والمخاطر

اسرد معايير القبول، والواجهات، والترحيلات (migrations)/تغييرات الحالة، والتوافق، والأمان/الخصوصية، والطرح (rollout)، والتراجع (rollback). اربط كل معيار باختبار أو تحقّق صريح. تنتهي هذه الخطوة عندما يكون لدى المراجعة عقد محدود.

5. نفّذ أصغر تغيير كامل — وأصلح الفئة بأكملها

اعمل على branch أو worktree معزول، مستعينًا بـ systematic-debugging أو test-driven-development عندما تستدعي فئة الخطأ ذلك. أضف اختبارات الانحدار (regression) أولًا، ثم نفّذ. عند التوصّل إلى الإصلاح، استخدم search_files بحثًا عن نفس شكل الخطأ في مواضع الاستدعاء الشقيقة وأصلح الفئة بأكملها ضمن هذا الـ PR — فإصلاح غير مكتمل يترك مواضع شقيقة معروفة معطوبة أسوأ من عدم الإصلاح. يجب أن يُتتبَّع كل سطر متغيّر إلى المشكلة؛ بلا تنظيف عرَضي. تنتهي هذه الخطوة عندما تنجح الاختبارات المستهدفة، ولم يعد الفشل الأصلي يتكرّر، وتُصلَح المواضع الشقيقة أو تُستبعَد صراحةً.

6. أثبِت أن اختبار الانحدار فعّال (تشغيل تخريبي)

أعِد مؤقتًا السلوك القديم للدالة المحدّدة قيد الاختبار، شغّل الاختبار الجديد، وتأكّد من أنه يفشل؛ ثم أعِد الإصلاح وتأكّد من أنه ينجح. اختبار انحدار ينجح مع الإصلاح وبدونه لا يثبت شيئًا. تنتهي هذه الخطوة عندما يفشل الاختبار بشكل واضح على الكود قبل الإصلاح.

7. شغّل بوابات جودة المستودع، ثم افتح PR فورًا

شغّل المنسِّق (formatter)، والـ lint، وفحص الأنواع (typecheck)، ونقطة دخول الاختبار الرسمية للمستودع على المناطق المتأثرة؛ واستخدم requesting-code-review على الـ diff. ثم ادفع (push) وافتح PR فورًا — فالـ PR هو ما يُشغّل CI، وزمن استجابة CI هو أطول عنصر في المسار؛ لا تُبقِ العمل المُنجَز معلّقًا. استعن بـ github-pr-workflow لآليات الـ PR: branch/commit وفق الاتفاقيات، ونص وصفي يربط المشكلة بالمشكلة والنهج والاختبارات والمخاطر والاستثناءات. أعِد قراءة الـ PR وتحقّق من head SHA والـ base والعنوان والملفات. تنتهي هذه الخطوة عندما يكون الـ PR موجودًا بالـ diff المقصود و CI قيد التشغيل.

8. تابع CI بصدق وأغلق الحلقة

افحص الفحوصات الحيّة وسجلات الفشل عبر gh pr checks / gh run view --log-failed. ميّز بين الإخفاقات التي أدخلها الـ diff الخاص بك وبين إخفاقات خط الأساس أو البنية التحتية الموجودة مسبقًا — أعِد الإنتاج على الفرع الافتراضي عند الشك، وأعِد التشغيل مرة واحدة فقط لحالات تذبذب البنية التحتية الحقيقية (flakes). لا تقل أبدًا "ناجح" أو "مدموج" أو "منشور" بدون دليل حي على تلك الحالة بالضبط. عند دمج الـ PR، علّق على المشكلة برابط الـ PR وشرح من سطر واحد كي يحصل المُبلِّغ على حلّ قابل للتتبّع. تنتهي هذه الخطوة عندما تعكس حالة CI، والعوائق المتبقية، ومحادثة المشكلة، الواقع كله.

مزالق شائعة

  • البدء بكتابة الكود قبل قراءة تعليقات المشكلة، أو مسح PRs المكرَّرة، أو قراءة الكود الحالي.
  • "إصلاح" سلوك يُظهر الـ commit الأصلي أنه تصميم متعمَّد.
  • إصلاح عرَض في موضع استدعاء واحد بينما تحتفظ المواضع الشقيقة بنفس الخطأ.
  • شحن اختبار انحدار ينجح أيضًا بدون الإصلاح.
  • فتح PR باختبارات لم تُشغَّل أو ضجيج تنسيق غير ذي صلة.
  • ادّعاء أن المشكلة مُنجَزة لمجرّد وجود PR.

التحقّق

  • قراءة كامل محادثة المشكلة؛ وحالة أحدث تعليق منعكسة في الخطة.
  • تنفيذ مسح PR المكرَّرة برقم المشكلة + نسختين من الكلمات المفتاحية.
  • إعادة إنتاج الفرضية على الكود الحالي؛ والتحقّق من نية التصميم عبر تاريخ git.
  • إثبات أن اختبار الانحدار يفشل بدون الإصلاح.
  • إصلاح مواضع الاستدعاء الشقيقة أو استبعادها صراحةً.
  • كل سطر متغيّر يُتتبَّع إلى المشكلة.
  • الإبلاغ عن حالة CI من دليل حي فقط؛ والتعليق على المشكلة برابط الـ PR.

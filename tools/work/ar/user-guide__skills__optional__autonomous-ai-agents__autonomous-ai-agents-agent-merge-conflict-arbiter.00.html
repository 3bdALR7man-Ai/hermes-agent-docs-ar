محكّم تعارضات الدمج بين الوكلاء (Agent Merge-Conflict Arbiter)

حلّ تعارض دمج (merge conflict) في git بين فرعَي وكيلَين (AGENTS) بصفتك طرفًا ثالثًا محايدًا. الوكلاء الذين يحلّون التعارضات مقابل عمل نظير لهم يميلون دائمًا إما إلى الكتابة فوق عمل النظير أو التخلي عن تغييرهم الخاص — فهم يفتقرون إلى سياق النظير ومنحازون نحو جانبهم الخاص. هذه المهارة هي الحل: مُوفِّق محايد يتلقى كلا الفرقين (diffs) مع النوايا المُصرَّح بها من كلا الجانبين وينتج نتيجة مدمجة، تمامًا كمحكّم merge-queue.

متى تُستخدم

  • عندما يتصادم فرعا/worktree وكيلين أثناء حملة متوازية (خط أنابيب هندسي على Kanban، موجة PR متوازية، إعادة هيكلة متعددة الـ worktree).
  • عندما يتوقف git merge أو git rebase بسبب تعارضات بين عمل وكيلين ولا ينبغي لأي من الوكيلين الأصليين أن يفصل في الأمر بنفسه.
  • لا تستخدمها لتعارضات ضمن عمل وكيل واحد، ولا لتعارضات ملفات lockfile/الملفات المولّدة تلقائيًا التافهة (أعد توليدها بدلًا من ذلك).

المتطلبات الأساسية

  • نسخة مسحوبة (checkout) من المستودع تحتوي الدمج المتوقف، أو اسما الفرعين مع الصلاحية لتشغيل الدمج بنفسك.
  • مصادر نية كل جانب: ملخصات إنجاز Kanban (عبر terminal بتشغيل hermes kanban show <task-id>)، أو نص الـ PR، أو على الأقل رسائل commit كل فرع.
  • أمر البناء/الاختبار الخاص بالمشروع، إن وُجد.

طريقة التشغيل

مستقلة — يستدعي إنسان (أو وكيل) هذه المهارة داخل المستودع المتعارض: حمّل المهارة، ثم اتبع الإجراء من الأعلى إلى الأسفل.

وكيل محايد يُستدعى (spawned) — الشكل المفضّل في حملات الوكلاء المتعددين:

  • delegate_task: استدعِ subagent تحتوي رسالة مهمته مسار المستودع، واسمَي كلا الفرعين، وملخصَي نيّة كلا الجانبين حرفيًا، بالإضافة إلى تعليمة باتباع هذه المهارة.
  • أصيل على Kanban: أنشئ بطاقة تسوية مُسندة إلى profile ثالث (ليس أيًّا من profile العاملين) مع ربط كلتا البطاقتين المتعارضتين كبطاقتين أصل — kanban_create(title="reconcile branch-a x branch-b", assignee="reconciler", parents=["t_a", "t_b"]). تنقل روابط البطاقة الأصل ملخصَي إنجاز كلا الجانبين إلى سياق المُوفِّق تلقائيًا؛ ويجب أن يذكر نص البطاقة مسار المستودع والفرعين.

مرجع سريع

فئة القطعة (hunk)التعريفالحل
disjoint-intentيخدم التغييران هدفين مختلفين ويمكن أن يتعايشاادمج كليهما
same-question-different-answerأجاب الجانبان عن سؤال تصميمي واحد بإجابتين مختلفتيناختر إجابة واحدة وفق النوايا المُصرَّح بها؛ وأظهر القرار
supersededلم تعد فرضية أحد الجانبين قائمة بعد تغيير الآخرأبقِ الجانب الباقي؛ ودوّن السبب

عقد الحياد: لا تحابِ أبدًا الجانب الذي استدعاك؛ عدّل المناطق المتعارضة فقط (بلا تعديلات عرضية)؛ ويجب أن يظهر كل اختيار في سؤال تصميمي بوضوح في ملخص التسليم.

الإجراء

1. اجمع كلا الجانبين

  • نفّذ عبر terminal: git status (للتأكد من حالة التعارض وسرد الملفات المتعارضة)، ثم git merge-base <A> <B>، ثم لكل جانب git log --oneline <base>..<side> و git diff <base>..<side> -- <file> لكل ملف متعارض. في الدمج المتوقف، يمثّل HEAD جانبًا و MERGE_HEAD الجانب الآخر.
  • اجمع نية كل جانب: hermes kanban show <task-id> لملخصات/بيانات الإنجاز الوصفية، أو نص الـ PR، أو رسائل commit من السجل أعلاه. دوّن جملة واحدة تصف نية كل جانب قبل التعامل مع أي ملف.
  • تنتهي هذه الخطوة عندما: تستطيع صياغة نيتَي الجانبين بكلماتك وتملك الفروقات (diffs) لكل ملف متعارض.

2. صنّف كل قطعة متعارضة (hunk)

  • افتح كل ملف متعارض باستخدام read_file وحدّد كل كتلة <<<<<<</=======/>>>>>>>.
  • أسند لكل قطعة فئة واحدة فقط من جدول المرجع السريع، بناءً على النوايا المُصرَّح بها — لا على أي التغييرين يبدو أفضل.
  • إذا احتوت قطعة واحدة على عدة قرارات مستقلة (مثلًا منطق جديد يندمج بسلاسة مع خيار تنسيق/تقريب أجاب عنه الجانبان بشكل مختلف)، فكّكها إلى قرارات فرعية وصنّف كلًّا منها.
  • غالبًا ما يمزج الملف الواحد بين الفئات: قد تكون إحدى القطع تصادمًا تصميميًا بينما تكون القطعة المجاورة منفصلة النية. صنّف حسب القطعة لا حسب الملف.
  • تنتهي هذه الخطوة عندما: تحمل كل قطعة فئة مكتوبة وسببًا موجزًا.

3. حلّ التعارض بموجب عقد الحياد

  • عدّل كل قطعة باستخدام patch (أو write_file لإعادة كتابة الملف بالكامل):
    • disjoint-intent ← ادمج كلا التغييرين بحيث تُخدم كل نية بالكامل.
    • same-question-different-answer ← اختر الإجابة التي تخدم النوايا المُصرَّح بها على أفضل وجه (مثلًا نية "التحقق الصارم" تتغلب على "قيمة افتراضية سريعة" إذا تطلبت المهمة الدقة). لا تختر أبدًا حلًّا هجينًا لم يطلبه أي من الجانبين.
    • superseded ← أبقِ الجانب الباقي؛ واحذف الفرضية المنتهية.
  • لا تحابِ أبدًا الجانب الذي استدعاك. إذا تعادلت النوايا فعليًا، صعّد الأمر (أوقف بطاقة Kanban / أبلغ عن الحالة) بدلًا من التخمين.
  • لا تغيّر شيئًا خارج علامات التعارض — لا تنسيقًا ولا إعادة تسمية ولا إصلاحات عرضية.
  • نفّذ git add لكل ملف تم حله عبر terminal.
  • تنتهي هذه الخطوة عندما: لا يجد search_files أي علامات <<<<<<< في المستودع وتكون كل الملفات المحلولة مُهيّأة (staged).

4. تحقّق

  • نفّذ عملية البناء/الاختبارات الخاصة بالمشروع عبر terminal؛ وكحد أدنى استورد/نفّذ الوحدات المتأثرة. يجب أن تكون كلتا النيتين ملحوظتين في السلوك المدمج (مثلًا دلالات الجانب A الجديدة وإضافة الجانب B المنفصلة معًا).
  • أكمل الدمج: git commit (تكفي رسالة الدمج الافتراضية مع نص يسرد قرارات القطع).
  • تنتهي هذه الخطوة عندما: ينجح التحقق ويكون commit الدمج موجودًا.

5. سلّم النتيجة

  • أنتج ملخص إنجاز يذكر كل قرار قطعة بالصيغة: file:lines — class — which side(s) kept — rationale. في كل قطعة من نوع same-question-different-answer، اذكر السؤال التصميمي والإجابة التي اخترتها ليتمكن إنسان من نقضها — لا تُخفِ قرارًا تصميميًا أبدًا.
  • Kanban: kanban_complete(summary=...). مستقلة: اطبع الملخص.
  • تنتهي هذه الخطوة عندما: يُسلَّم الملخص ويسرد كل القطع.

المزالق

  • المحاباة الذاتية: إذا استدعاك أحد الوكيلين المتعارضين، فأنت منحاز بنيويًا — أقرّ بذلك وزِن نية الجانب الآخر عن قصد. فضّل شكل الـ profile الثالث حتى لا تنشأ هذه المشكلة أصلًا.
  • تقسيم الفرق في تصادم تصميمي ينتج حلًّا هجينًا لم يصممه أحد؛ اختر إجابة واحدة وأظهرها.
  • التصنيف حسب الملف: غالبًا ما تمزج الملفات فئات القطع؛ تصنيف ملف كامل كفئة واحدة يُسقط بصمت تغييرًا منفصل النية.
  • التعديلات العرضية تجعل الدمج غير قابل للمراجعة وتسلب القرار من الوكيلين الأصليين.
  • غياب النوايا: قد تكون رسائل commit وحدها ضحلة؛ فضّل ملخصات إنجاز Kanban أو نصوص الـ PR. إذا تعذّر استرجاع نية أي من الجانبين، صعّد الأمر بدلًا من التخمين.
  • المخالفون المتكررون: التعارضات المتكررة على نفس الملف عبر جولات متعددة إشارة إلى نقطة ساخنة (hotspot)، لا عمل تسوية روتيني — أبلغ عنها (مثلًا بتعليق Kanban على شكل hotspot: <path> — <reason>) ليقوم المنسّق بتفكيك ذلك الملف، بدلًا من تسوية كل تعارض جديد عليه تباعًا.

التحقق

  • يُظهر git status شجرة نظيفة على الفرع الهدف مع commit دمج.
  • لا تبقى أي علامات تعارض (نمط search_files: <<<<<<<).
  • ينجح البناء/الاختبارات؛ وتكون نيتا الجانبين حاضرتين فعليًا أو الجانب المُسقَط مذكورًا صراحة في الملخص.
  • يسرد ملخص التسليم كل قطعة مع فئتها وسببها.

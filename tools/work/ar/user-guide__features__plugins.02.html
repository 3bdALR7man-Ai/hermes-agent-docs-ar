إدارة الإضافات

فحوص التحديث وبيانات المصدر

يسجّل Hermes مصدر تثبيت Git والمراجعة في .install-metadata.json. تقارن التثبيتات المتتبَّعة غير المثبّتة عند مراجعة محددة قيمة HEAD البعيدة للمصدر المحفوظ، أو خلاصة update_url محفوظة ومطابقة. تظل التثبيتات المثبّتة عند مراجعة محددة كما هي. تحتاج الأدلة التي استنسختها بنفسك إلى hermes plugins adopt NAME قبل أن تصبح تثبيتات متتبَّعة. تتلقى الأدلة المنسوخة يدويًا أو التي انحرفت بيانات مصدرها إرشادات تشخيصية. يمكن لإضافات نقاط دخول pip الإبلاغ عن الإصدار المتاح للتوزيعة المالكة لها؛ ولا يحوّلها هذا الفحص إلى تثبيتات مُدارة عبر Git.

hermes plugins check-updates يترك ملفات الإضافات دون تغيير. يعمل فحص gateway المجدول عند حلول موعد plugins.auto_update_check_hours: القيمة الافتراضية 24 ساعة، و 0 يعطّله. يتوفر إيصال الفحص عبر hermes pm status وعرض حالة المزامنة في Desktop. ليس هذا حدًا صارمًا لمرة واحدة يوميًا إذا ضبطت فاصلًا مختلفًا.

تتطلب التحديثات افتراضيًا hermes plugins update NAME. ضبط plugins.auto_apply: true يتيح تحديث إضافات Git المتتبَّعة دون إشراف. يستخدم المساران فحص أمان التحديث. لا يدير التطبيق التلقائي الصفوف المثبّتة عند مراجعة محددة، أو اليدوية، أو المنحرفة، أو التابعة لتوزيعات pip.

إذا غيّر manifest عنوان update_url أو أضافه، يرفض Hermes العنوان الجديد حتى توافق عليه باستخدام hermes plugins trust-update-url NAME. هذا فحص لمصدر الخلاصة، وليس sandbox يحمي من كود إضافة موثوق بها بالفعل.

تجهيز الاعتماديات والحفاظ عليها

لتثبيت اعتماديات Python خطوة منفصلة للموافقة/القبول. الخيار plugins install --enable لا يتجاوزها. قد يترك رفض تثبيت الاعتماديات أو إجراؤه دون تفاعل الإضافة مثبّتة لكن معطّلة. لاعتماديات Node sidecar مطالبة منفصلة، وتظل محلية للإضافة.

يجهّز PM اعتماديات Python مع المكوّن الأساسي ومجموعة الإضافات المفعّلة قبل نشر البيئة والإعدادات الجديدة. يحافظ فشل حلّ الاعتماديات على الاختيار السابق. أعد تشغيل Hermes عندما لا تكون البيئة المحددة الجديدة نشطة بعد في العملية الجارية.

المجموعة المفعّلة هي اتحاد الإضافات في الدليل الرئيسي الافتراضي وكل profile ضمن profiles/، وتُقرأ من كل config.yaml (plugins.enabled، plugins.disabled، memory.provider). يرفض PM التخمين بشأن دليل رئيسي لا يستطيع قراءته: إذا كان config.yaml ليس YAML صالحًا، أو ليس mapping، أو يتضمن قيمة ليست قائمة لـ plugins.enabled/plugins.disabled أو قيمة غير نصية لـ memory.provider، يفشل تجهيز الاعتماديات لـ جميع الأدلة الرئيسية (could not parse plugin selection: <path>)، بدلًا من إسقاط إضافات ذلك الـ profile بصمت من البيئة التالية. أصلح الملف المسبب للمشكلة أو أزله؛ ملف config.yaml فارغ مقبول.

تحافظ تحديثات تطبيق Hermes العادية على أدلة إضافات المستخدم، بما فيها ملفات wrapper وروابط sidecar الخارجية. قد تغيّر التحديثات الصريحة للإضافات أو إزالتها تلك الملفات. راجع إدارة الحزم و دليل تأليف الإضافات.

روابط تثبيت بنقرة واحدة (Desktop)

يسجّل Hermes Desktop مخطط رابط hermes://، بحيث يمكن لموقع، أو ملف README، أو رسالة محادثة أن ترتبط مباشرةً بتثبيت إضافة:

صيغة catalog=<name> هي ما يستخدمه زر Open in Hermes Desktop في كل بطاقة من كتالوج الإضافات. يحلّ Desktop الاسم بالرجوع إلى الكتالوج الحي (نفس الخلاصة التي يعرضها منتقي Capabilities → Plugins)، ويفتح مربع حوار مدخلة الكتالوج المراجَعة نفسه الذي يفتحه الاختيار داخل التطبيق: يُثبَّت جانب الوكيل عند commit المثبّت في الكتالوج، وليس عند أحدث commit في branch أبدًا. لا يحمل الرابط URL للمستودع، ويُظهر الاسم غير الموجود في الكتالوج إشعار خطأ عابرًا فقط — لا يُعاد تفسيره كمسار git أبدًا، لذا لا يمكن لرابط تهريب مستودع غير مراجَع خلف اسم يبدو مألوفًا.

بالنسبة إلى رابط repo=، يفتح النقر عليه Hermes ويعرض مربع حوار تأكيد — معرّف المستودع، وملاحظة "قبل أن تثبّت"، وروابط تصفّح واستنساخ GitHub — ثم يستنسخ المستودع استنساخًا سطحيًا لاكتشاف ما يشحنه (إضافة وكيل — Python الخلفي، أو إضافة سطح مكتب — واجهة تطبيق، أو كلاهما). تختار المكوّنات عبر مربعات اختيار ثم تؤكّد. لا يُثبَّت شيء حتى تفعل ذلك؛ الروابط العميقة لا تثبّت تلقائيًا أبدًا، وتثبيتات إضافات الوكيل تمر عبر نفس فحص الأمان وقت التثبيت كما في hermes plugins install.

المستودعات الهجينة (نصفا وكيل + سطح مكتب في مستودع واحد) تستخدم رابطًا واحدًا ومربع حوار واحد. يمكن الوصول إلى نفس النافذة المنبثقة دون رابط عبر Capabilities → Plugins → Install from Git. روابط hermes://plugin-agent/… و hermes://plugin-desktop/… القديمة تُوجَّه إلى نفس مربع الحوار. في إصدارات التطوير (npm run dev) المخطط هو hermes-dev://.

لا تحتاج المواقع إلى أي SDK — تكفي وصلة عادية:

إمكانيات الإضافات والموافقة

يمكن للإضافات الإعلان عن أسطح المضيف المميّزة التي تريدها في plugin.yaml:

عندما تعلن إضافة عن إمكانيات، يعرض hermes plugins install (و hermes plugins enable) القائمة مع أوصاف مخاطر من سطر واحد و يسأل مرة واحدة. الموافقة تسجّل المنح تحت plugins.entries.<id>.granted_capabilities مع بصمة موافقة وطابع زمني. الرفض يترك الإضافة مفعَّلة مع تعطيل تلك الإمكانيات — الإضافة المصمَّمة جيدًا تستكشف الحال بـ ctx.has_capability() وتتراجع بسلاسة.

إعادة الموافقة عند التحديث: إذا أعلن تحديث لإضافة عن إمكانيات لم تمنحها، يعرض hermes plugins update الإمكانيات المضافة ويسأل مجددًا. تظل الإمكانيات الجديدة معطّلة حتى توافق — لا يمكن لتحديث إضافة توسيع وصولها بصمت أبدًا. تذهب إعادة التثبيت عند مراجعة جديدة في الكتالوج أبعد من ذلك: عندما تضيف المراجعة الجديدة أدوات، أو hooks، أو اعتماديات Python، أو إمكانيات المضيف، أو تسجيل دخول إلى مزوّد (requires_auth)، أو جانب واجهة Desktop لم يكن في الإصدار المثبّت، يعرض CLI الفرق ويسأل y/N قبل أي تغيير، ويفتح زر Update في Desktop / لوحة التحكم التأكيد نفسه. يترك الرفض (أو الجلسة غير التفاعلية) الإضافة عند المراجعة القديمة.

الجلسات غير التفاعلية تفشل بأمان: تثبيت أو تحديث دون TTY يكمل التثبيت، لكن الإمكانيات المُعلَنة لا تُمنَح. شغّل hermes plugins enable <id> تفاعليًا لمنحها لاحقًا.

ليست sandbox

الإمكانيات هي طبقة موافقة وتدقيق، وليست عزلًا. الإضافات تعمل ككود Python عادي داخل العملية نفسها: إضافة خبيثة يمكن أن تتجاهل كل بوابة هنا. منح إمكانية هو إعلان ثقة بمؤلف الإضافة — وليس تدقيقًا للكود، ولم يراجع Hermes كود الإضافة. ثبّت فقط إضافات من مصادر تثق بها.

إجراءات المنصة

ctx.platform_actions يمنح الإضافة مجموعة أفعال صغرى مقيَّدة بالإمكانيات للتصرف على منصات دردشة متصلة عبر سجلّ محوّلات gateway الحي — البديل المعتمد لتصحيح محوّل بشكل غير رسمي (monkeypatching). مُعطَّل افتراضيًا: كل استدعاء يعيد فحص إمكانية gateway.platform_actions (المفتاح القديم plugins.entries.<id>.allow_platform_actions)، وأي استدعاء غير ممنوح يعيد خطأً منظَّمًا بدلًا من التصرف.

أفعال v1 (كلاهما async، وكلاهما يعيد قاموسًا عاديًا، ولا يرفعان استثناءً أبدًا في تنفيذ الـ hooks):

النجاح هو {"ok": True, "action": <verb>}. الإخفاقات هي {"ok": False, "error": <code>, "detail": <str>} برموز خطأ ثابتة: capability_not_granted، invalid_argument، gateway_unavailable، unknown_platform، adapter_not_registered، adapter_disconnected، unsupported_platform_action، action_failed. الأفعال تتحقق من أن المحوّل الهدف موجود ومتصل قبل التصرف؛ المحوّل غير المتصل أو المفقود يتدهور إلى خطأ منظَّم، وليس استثناءً أبدًا.

المنصات المدعومة في v1: Telegram وDiscord. add_reaction في Telegram يضبط تفاعل البوت (Bot API يستبدل تفاعل بوت سابق بدلًا من تكديسه). كل إجراء — مسموح أو مرفوض — يُكتَب في السجل مع معرّف الإضافة، والفعل، والمنصة، والنتيجة.

ملاحظة أمنية

إجراءات المنصة هي صلاحية إرسال رسائل باسم البوت: إضافة ممنوحة يمكنها التفاعل وإعادة تسمية سلاسل المحادثات في أي محادثة يستطيع بوت gateway الوصول إليها، وليس فقط المحادثة التي شغّلت الـ hook. امنح gateway.platform_actions فقط للإضافات التي تثق بها، وفضّل الإضافات التي توثّق بدقة الإجراءات التي تتخذها. الوصول الخام إلى حمولة/مقبض SDK المنصة ليس عمدًا جزءًا من هذا السطح — بحسب تصحيح التصميم من الجولة الثانية #64176، فهو يحتاج إمكانية خاصة به (gateway.raw_events) بوسم "لا ضمان استقرار" وتصميمًا منفصلًا، ولم يُشحَن بعد.

اكتشاف الإضافات — كتالوج إضافات Hermes

hermes plugins search <term> يبحث في كتالوج إضافات Hermes — الكتالوج المنسَّق والمثبَّت بـ SHA، والمُدار في مستودع hermes-agent (plugin-catalog/). يشمل التطابق أسماء المدخلات، والأوصاف، والأدوات المُعلَنة:

بمجرد أن تجد إضافة، ثبّتها بالاسم المجرد — يُحلّ الاسم إلى مستودع المدخلة عند الـ SHA المثبَّت، وتُسجَّل نشأة الكتالوج بحيث يمكن لـ hermes plugins update إعادة التثبيت عندما يتحرك الكتالوج:

معرّفات owner/repo أو روابط Git الصريحة لا تلامس الكتالوج أبدًا وتُوسَم كمصادر مخصصة (غير مراجَعة). --ref <40-char commit SHA> صريح يثبّت تثبيتًا مخصصًا.

راجع كتالوج الإضافات لنموذج الثقة الكامل، وCI القبول، وسير عمل التقديم.

مُدرَج في الكتالوج ≠ مُدقَّق

وجود مدخلة في الكتالوج يعني أن بيانات المدخلة الوصفية والإمكانيات المُعلَنة رُوجِعَت عند القبول — وهذا ليس تدقيقًا للكود. التثبيت لا يزال يمر عبر تدفق الموافقة العادي (تثبيت الإضافات مُعطَّل افتراضيًا، والتفعيل خطوة صريحة، وحقوق تجاوز الأداة تتطلب منحًا منفصلًا). راجع مصدر الإضافة قبل تفعيلها.

حزم الإضافات

حزمة الإضافات (plugin pack) هي ملف YAML تصريحي قابل للمشاركة (hermes-pack.yaml) يثبّت مجموعة من الإضافات — مثل مشاركة modpack. تثبيت حزمة يتفرّع إلى تثبيتات ثابتة عادية؛ لا شيء جديد يوجد في وقت التشغيل.

وضعية سلسلة التوريد. يجب أن يكون ref لكل مدخلة SHA كامل مكوَّن من 40 حرفًا — تُرفَض الوسوم tags وأسماء الفروع بخطأ يسمّي المدخلة، وهي نفس القاعدة المطبَّقة على كتالوج الإضافات. تسلك تثبيتات الحزمة نفس مسار التثبيت الثابت تمامًا مثل hermes plugins install --ref <sha> وتسجّل نفس النشأة في plugins/.install-metadata.json، بحيث يُحلّ تثبيتان لنفس الحزمة إلى الشيء نفسه. تُبنى الحزم على حقول manifest v2 (manifest_version، api_version، requires_plugins) — كل manifest خاص بإضافة لا يزال يُتحقَّق منه عبر مسار التثبيت العادي.

الموافقة لا تُمنَح جماعيًا أبدًا. تعرض pack install شاشة مراجعة إلزامية (كل إضافة، ومصدرها، وrefها المثبَّت، والإمكانيات التي تعلن عنها)، ثم تطلب تأكيدًا واحدًا لمحتويات الحزمة. بعد ذلك، تمر إمكانيات كل إضافة المُعلَنة عبر طلب موافقة الإمكانيات القياسي لكل إضافة — مطابق لـ hermes plugins install منفردة. لا وجود لـ --yes، ولا يمكن للجلسات غير التفاعلية تثبيت الحزم.

الأسرار لا تنتقل أبدًا في الحزم. تقتصر بذور config: على مفاتيح plugins.entries.<id> غير السرية — أسماء المفاتيح ذات الشكل السري (*token*، *key*، *password*، …)، ومنح الإمكانيات، وبوابات الثقة allow_* المُهملة، تُرفَض عند التثبيت وتُحذَف عند التصدير. الإضافات التي تحتاج أسرارًا تعلن عنها في requires_env الخاص بها، والتي تُطلَب أثناء التثبيت كالمعتاد. القيم الموجودة أصلًا لدى المستخدم في plugins.entries.<id> تفوز دائمًا على بذور الحزمة.

الفشل الجزئي. تُثبَّت كل إضافة باستقلالية؛ تُبلَّغ الإخفاقات لكل إضافة، وتستمر البقية، ويخرج الأمر برمز غير صفري إذا فشلت أي إضافة.

تحفظات التصدير. يشمل pack export فقط الإضافات ذات نشأة Git معروفة (المثبَّتة عبر hermes plugins install). الإضافات المحلية فقط تُدرَج كتعليقات تحذير في YAML المُصدَر، وليست كمدخلات قابلة للتثبيت.

قائمة skills: تُحلَّل وتُعرَض عند التثبيت لكنها لا تُثبَّت تلقائيًا بعد — ثبّت تلك يدويًا في الوقت الحالي (hermes skills). ربط معرّفات skill-hub في تثبيت الحزم هو مسار تتمة موثَّق.

فحص الأمان وقت التثبيت

كل hermes plugins install وhermes plugins update يشغّل فحصًا أمنيًا ساكنًا على شجرة الإضافة قبل تفعيلها (مستوحى من فحص أمان المهارات & الإضافات في Claude Cowork). يعيد الفاحص استخدام محرّك أنماط التهديد نفسه الذي يستخدمه حارس Skills Hub — تسريب مخازن بيانات الاعتماد، وقذائف عكسية، وأوامر مدمِّرة، وآليات استمرارية، وتنفيذ مبهم، وحقن prompt في ملفات التوثيق — مع استثناءات واعية بالإضافات: إضافة مزوّد تقرأ مفتاح API الخاص بها من البيئة (نمط requires_env الموثَّق) لا تُوسَم.

ثلاثة أحكام، مطابقة لـ pass/warn/fail الخاصة بـ Cowork:

الحكمالسلوك
آمن (safe)يثبَّت عاديًا، دون مخرجات إضافية
احتراس (caution)تُعرَض النتائج؛ تؤكّد Install anyway? [y/N] (أو تمرّر --force)
خطر (dangerous)محظور. --force لا يتجاوزه

في hermes plugins update، يؤدي الحكم بالخطر على الشجرة المحدَّثة إلى تعطيل الإضافة حتى تراجع النتائج وتعيد تفعيلها. يسمّي الحظر الخطر النتائج الحرجة المسببة له (مثل 1 critical of 42 findings (destructive_root_rm))، فلا يختبئ سطر واحد يسبّب الحظر خلف الإجمالي.

يُقيَّم النص الذي لا يمكن تشغيله على المضيف وقت التثبيت بوصفه سياقًا، لا سلوكًا للإضافة، لذا قد يخفض درجة نتيجة لكنه لا يحذفها أبدًا — تظل كل نتيجة في التقرير مع الملف والسطر:

  • نثر التوثيق (README.md، AGENTS.md، docs/**/*.md، .txt، .rst، .html) لا يمكنه وحده إنتاج حكم خطر: يخفض الأمر أو مسار بيانات الاعتماد المقتبَس هناك (خطوة إلغاء تثبيت أو قائمة رفض تسمّي ~/.ssh) مستوى خطورته درجة واحدة، ويُعدّ ملف README الذي يزيل دليل تثبيت الإضافة نفسها (rm -rf "$HOME/.hermes/plugins/<name>") ملاحظة. تحتفظ الأنماط الموجّهة للوكيل بخطورتها كاملة — حقن prompt، وتسريب البيانات عبر Markdown، وتعديلات إعدادات الوكيل، وأوامر curl … | sh ذات السطر الواحد، والإلحاق بـ authorized_keys، ومفتاح مزوّد مسرَّب — وكذلك أي شيء ضمن شجرة skills/ مضمّنة أو في after-install.md، إذ يقرأه الوكيل كتعليمات.
  • أشجار الاختبارات وبياناتها الثابتة (tests/، test/، testing/، spec/، specs/، fixtures/ في جذر الإضافة؛ و __tests__/ و __fixtures__/ على أي عمق؛ و *.test.*، *.spec.*، test_*.py، *_test.*) تظل خاضعة للفحص — فقد يستورد __init__.py الخاص بالإضافة منها — لكن السلسلة العدائية المقتبسة فقط (verdict_for("rm -rf /")، أو مجموعة نصوص لاختبار الحجب تضم مفتاح sk-… زائفًا) تكون ملاحظة، ويكون أقصى حكم لكود اختبار يُنفَّذ عند الاستيراد (os.system('rm -rf /')) هو تنبيه. تظل النتيجة نفسها في أي ملف آخر (setup.sh، src/spec/…) خطرة.
  • التعليقات التي تشغل سطرًا كاملًا و CHANGELOG.md تصف دفاعًا؛ وتُقيَّم كما يُقيَّم النثر.
  • Base64 الذي يُفكّ إلى ترويسة وسائط (PNG/JPEG/GIF/WOFF/PDF … ضمن data URI أو سياق JSON) للمعلومات فقط؛ و base64 -d الموجّه عبر pipe إلى مرشِّح نص (grep، jq) ملاحظة، أما توجيهه إلى shell أو مفسّر فيُبقي خطورته كاملة؛ و sudo / env| بوصفه بديلًا في تعبير regex حرفي (/approval|sudo|secret/، نمط حجب) ملاحظة، لكنه ليس كذلك داخل سلسلة أمر (subprocess.run("sudo …")).

وبالمثل، يكون أقصى حكم لـ token عام من أمثلة التوثيق (hardcoded_secret) داخل كتلة الاختبار الذاتي .py في ملف if __name__ == "__main__": مستخدَم وقت التشغيل هو تنبيه — إذ يستورد المحمِّل الإضافات ولا يشغّل تلك الكتلة أبدًا — بينما تحتفظ جميع النتائج الأخرى داخلها (أوامر مدمّرة، ومفاتيح على هيئة مفاتيح المزوّدين مثل sk-…) وكذلك الـ token نفسه في أي موضع فوق شرط الحماية بخطورتها كاملة.

تشغيل الإضافات خارج العملية (plugins.isolation)

افتراضيًا، تُستورد إضافات Python من الجهات الخارجية إلى عملية Hermes، كما كان الحال دائمًا. يؤدي ضبط plugins.isolation: host إلى نقلها إلى مضيف إضافات: عملية Python منفصلة واحدة لكل profile، تبدأ عند الطلب، وتستورد الإضافات التي ثبّتها المستخدم في ذلك الـ profile وتتواصل مع Hermes عبر pipe خاص.

لا تتغيّر الإضافات. تتلقى ctx نفسه وتسجّل الأدوات، و hooks، و slash commands، والمهارات، وكائنات المزوّدين (توليد الصور/الفيديو، والبحث في الويب، والمتصفح، و TTS/STT، والذاكرة، ومحركات السياق، و profiles مزوّدي النماذج) كما كانت تفعل؛ ويسجّل Hermes مدخلات مطابقة على جانبه تستدعي المضيف. يخدم المضيف أيضًا APIs الإضافات في لوحة التحكم. تستمر الإضافات المضمّنة في العمل داخل العملية.

ما الذي يتغيّر في وضع host:

  • لا يوجد مفسّر مشترك. لا تدخل وحدة الإضافة عملية Hermes أبدًا، فلا يمكنها قراءة بيانات profile آخر من الذاكرة أو تعديل الآليات الداخلية لـ Hermes. في gateway متعدد الإرسال، يحصل كل profile على مضيفه الخاص، يبدأ ببيئة ذلك الـ profile وأسراره فقط.
  • تظل الأعطال محصورة. الإضافة التي تتعطل أو تخرج تُنهي مضيفها لا Hermes؛ ويعيد الاستدعاء الجاري خطأ أداة، ثم يعيد Hermes تشغيل المضيف وتحميل إضافاته (مع إعادات محاولة محدودة).
  • تحتاج بعض الواجهات إلى كود داخل العملية، وتُفشِل تلك الإضافة بسبب واضح بدلًا من تحميلها: محوّلات منصات gateway (register_platform)، ووسائل نقل الموافقات، ومعالجات Telegram/المنصات، و profiles مزوّدي النماذج التي تبني عميل SDK خاصًا بها (create_client)، و endpoints البث في لوحة التحكم، والإضافات التي تعدّل وحدات Hermes عبر monkeypatch. شغّلها باستخدام isolation: in_process.

تثبيت الإعداد لنشر مشترك. plugins.isolation إعداد عادي للـ profile، لذا يستطيع من يملك تعديل config.yaml الخاص بالـ profile تعطيله. عندما تتبع profiles لأشخاص تعزلهم عن بعضهم، ثبّته بدلًا من ذلك في النطاق المُدار (Managed Scope)؛ فتتغلب القيمة المُدارة على الإعدادات الخاصة بكل profile، ويرفض hermes config set تغييرها:

واجهة تفاعلية

تشغيل hermes plugins دون وسائط يفتح شاشة تفاعلية مركّبة:

  • قسم الإضافات العامة — مربعات اختيار، بدّلها باستخدام SPACE. يظهر الصف محددًا عند فتحه إذا كانت الإضافة نشطة الآن: مدرجة في plugins.enabled، أو منصة مضمّنة أو backend أو مزوّد نماذج (مفعّل دون مدخلة قائمة)، أو المزوّد المحدد لفئة. لا تُكتب عند الخروج إلا الصفوف التي تبدّلها: إلغاء التحديد يضيف الإضافة إلى plugins.disabled (تعطيل صريح)، والتحديد يضيفها إلى plugins.enabled ويمحو تعطيلًا قديمًا. فتح المنتقي والخروج منه لا يغيّر شيئًا.
  • قسم إضافات المزوّد — يعرض الاختيار الحالي. اضغط ENTER للدخول إلى منتقٍ راديو حيث تختار مزوّدًا فعّالًا واحدًا.
  • الإضافات المدمجة تظهر في نفس القائمة بوسم [bundled].

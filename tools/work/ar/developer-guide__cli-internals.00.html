خط أنابيب التحديث (Update pipeline)

السلوك الظاهر للمستخدم (الإيصالات، --plan، أوضاع الـ snapshot) فموجود في التحديث; hermes_cli/AGENTS.md يعرض الصيغة المختصرة للقواعد.

حملة تحديث الأسطول #91277 (أغسطس 2026). يجب أن يبرّر PR الذي يضعف مرحلةً تعامله مع فئة الإخفاق التي تحمي منها. plan → snapshot → apply → restart-per-kind → verify → report

  • التخطيط (update_inventory.py, hermes update --plan): جرد للقراءة فقط — نوع التثبيت، وجميع profiles، وكل gateway نشط مع المشرف عليه وإصدار الكود الذي يعمل عليه. أنواع النشر كيانات أساسية: يُحدّث git في موضعه؛ أما docker/nix/apt فلا يمكن تحديثها في موضعها، ويُبلّغ برنامج التحديث عن الأمر الخارجي الصحيح بدلًا من مقاومة نموذج النشر.
  • اللقطة (backup.py): لقطة سريعة قبل التحديث لكل profile (يؤثر تبديل الكود وإعادة تشغيل الأسطول فيها جميعًا)، كل منها في state-snapshots/ الخاصة به، بمجموعة الملفات نفسها، وحد 1 GiB لكل ملف، و keep=1. لا تضف مطلقًا مجموعة لقطات جزئية/متدرّجة — تؤدي التغطية المختلطة إلى حالات استعادة غير متّسقة عبر أجيال المخطط. اللقطات السريعة لاستعادة الملفات المفقودة (تستعيد منها شبكة الأمان لمهام cron لكل profile)، وليست ضمانًا للتراجع عن الكود؛ ويتولى --backup في الوضع الكامل التراجع.
  • التطبيق: git pull، أو مسار Windows ZIP الاحتياطي — الذي لا يُفعّل إلا عندما يفشل git نفسه (_should_zip_fallback_on_update_error، مصنّفًا بحسب argv؛ يجب ألا يؤدي فشل تثبيت الاعتماديات مطلقًا إلى إعادة تنزيل تستبدل الشجرة)، ويرفض شجرة عمل غير نظيفة (-uall + إعادة فحص TOCTOU قبل التبديل — لكنه يصنّف سطر !! بحسب ما إذا كان التبديل سيدمّره: يُسمح بمسار متجاهَل تحت إدخال جذر لا يوفّره ZIP (.bytecode-fingerprint, .hermes-bootstrap-complete, hermes_agent.egg-info/؛ تمثّل إدخالات الجذر المتتبَّعة مجموعة ZIP قبل التنزيل، وتحصل إعادة الفحص على المجموعة الفعلية)، أو __pycache__/node_modules متداخل، أو مخرجات _ZIP_PRESERVED_NESTED؛ وتظل الملفات المتجاهَلة الأخرى داخل المجلدات الموفّرة تمنع التبديل)، ويُطعّم مخرجات البناء المتداخلة النشطة (_ZIP_PRESERVED_NESTED: apps/desktop/{release,dist,node_modules,build}, hermes_cli/web_dist, ui-tui/{dist,node_modules,packages/hermes-ink/dist}, web/node_modules, scripts/whatsapp-bridge/node_modules) في التبديل المُجهّز بروابط صلبة (لا يتضمن ZIP المصدر من GitHub أيًا منها؛ ودون التطعيم يحذفها التبديل). بعد التبديل، يثق قرار إعادة بناء Desktop أيضًا بختم البناء تحت HERMES_HOME، لكي يُعاد بناء تثبيت فقد آثاره بالفعل في تحديث سابق بدلًا من "نسيانه" (#90495).
  • إعادة التشغيل حسب النوع: تشمل إعادة تشغيل systemd و launchd الأسطول كله ضمن التثبيت الذي يجري تحديثه (كل وحدة hermes-gateway* / LaunchAgent من نوع ai.hermes.gateway* يكون مجلدها هو الجذر المحدَّث أو أحد profiles/<name> الخاصة به)، مع تفريغ العمل أولًا (SIGUSR1)، وعزل الإخفاق لكل وحدة/تسمية. تترك إعادة تشغيل خدمة profile المستدعي فقط بقية profiles على sys.modules قديم حتى تتعطل — وقد نشأت أكبر مجموعة PRs مكرّرة في تاريخ المستودع عن ذلك الخطأ. يتحدّد الأسطول بـ HOME، لا بمساحة الأسماء: يحكم hermes_cli/update_fleet_scope.py على كل وحدة/تسمية/عملية بحسب المجلد الذي تعمل عليه فعليًا (البيئة النشطة، و Environment= في الوحدة، و HERMES_HOME في plist)، ويُذكر وقت تشغيل HERMES_HOME آخر على الحساب نفسه — تثبيت مجاور، أو hermes-gateway.service الفعلي المرئي من مجلد مؤقت — ويُترك دون تدخّل، ولا يُعاد تشغيله مطلقًا (#93349).
  • التحقّق: تختم gateways code_sha/code_version في gateway_state.json عند كل كتابة لحالة وقت التشغيل (gateway/status.py)؛ ويقارن برنامج التحديث كل gateway نشط بالنسخة المسحوبة الجديدة ويطبع مصفوفة إصدارات الأسطول. بعد نقطة الالتزام (انتقال الشجرة)، لا يُفشل شيء hermes update (الخروج 0 ما لم يُرجَع الكود): يطبع كل gateway ثبت تقادمه أو توقفه، وكل إخفاق في البناء/المشغّل/ترحيل الإعدادات/مسح bytecode/اعتماد القناة/استئناف Windows، القيمة ⚠، ويُسجّل في الإيصال بحالة outcome: "success" مع followups: [{step, reason}]، ويُبقي التزامه معلّقًا (source-completion-pending للخطوات اللاحقة، والتزام إعادة تشغيل الأسطول للـ gateways)، لكي يعيد التشغيل التالي أو hermes update — حتى عند "Already up to date" — المحاولة. يمنع تحذير بدء CLI عن إعادة تشغيل الأسطول المستحقة ظهور أسطول مختلط الإصدارات بمظهر السليم. تُعدّ عملية إكمال تعذّر بدؤها (المجلد المؤقت أو ملف الطلب أو الإطلاق) أو انتهت دون نتيجة مترابطة (OOM أو SIGKILL) دينًا من النوع نفسه: متابعة completion مستحقة مع إعادة تسليح الخطوات اللاحقة لتحديث المصدر، والخروج 0. يحتفظ الخروج 2 (مرفوض/متزامن) والخروج 1 (لم يُلتزم شيء / أُرجع) بمعناهما؛ والتشغيل الملتزِم الوحيد الذي يخرج 1 هو autostash تعارضت استعادته وبقي معلّقًا: يكون الإيصال partial مع user_action، لأن لا شيء يعيد محاولة ما لا يستطيع إعادة تطبيقه إلا المستخدم (#122557).
  • الإبلاغ: يكتب كل تشغيل إيصالًا قابلًا للقراءة آليًا إلى logs/update_receipts/ في مجلد الجذر (لا مجلد profile ثابت مطلقًا؛ وينطبق الأمر نفسه على update.log) — مؤشر latest.json؛ والخطوات، والتجاوزات مع أسبابها، ونتيجة إعادة التشغيل، والخطة، ولقطة الأسطول، و followups. يوجد الإيصال على القرص بحالة outcome: "running" منذ البداية ويُحدّث عند كل حد مرحلة؛ ويضع التحديث التالي السجل running الذي انتهت عملياته في حالة interrupted ويصرّح بذلك. يستخدم القرّاء (hermes logs update وحزمة تصحيح الأخطاء وحالة لوحة التحكم وإيصالات pm) مجلد الجذر أيضًا. إخفاق مزامنة الاعتماديات في bootstrap الإكمال متابعة dependencies (A6)، ويُنهي Ctrl-C بعد نقطة الالتزام الحالة interrupted (الخروج 130)، لا failed. قبل تبديل المصدر، يلتقط الأصل الخطة/اللقطات/الإيصال و token الإيقاف المؤقت في Windows الخاص به. ينفّذ update_completion.py تجهيز PM بالكود الجديد مع تعطيل تهيئة الموقع، ثم البناء بواسطة Python المختار، والصيانة، والفحوص/إعادة التشغيل، والتحقّق. يشترك Git/current/ZIP في هذا المالك؛ لا تُعد تحميل الوحدات أو تُزلها للاستمرار في المفسّر القديم. يحتفظ الأصل بالقفل وينتظر ولا يقبل إلا نتيجة نهائية مترابطة. لا يزال cmd_update ينهي الإخفاقات المبكرة وحالات العملية المتفرّعة المفقودة/المقتولة؛ تبقى بيانات رفض PM عبر التسليم. راجع website/docs/developer-guide/source-update-completion.md. الإيصال الذي بدأ ولم يُكتب خطأ برمجي.
  • لا يشغّل أي شيء الكود المسحوب في مفسّر ما قبل السحب. تنهي هذه الشجرة التحديثات عبر update_completion.run_completion / _update_takeover.py. hermes_cli/update_handoff.py و hermes_cli/update_serve_obligations.py هما واجهة التوافق الثابتة للإصدارات التي تستورد أسماء تلك الوحدات عند الحاجة من الشجرة الجديدة بعد تبديل النسخة المسحوبة. أبقِ أسماءها العامة قابلة للاستيراد ومحافظةً على السلوك. تستدعي _old_updater.stop_for_relaunch → _run_child. إزالة اسم تعطّل كل إصدار في منتصف تحديثه. راجع tests/compat/old_updater_surface.json.

يُستبدل التنسيق عبر فحص العمليات بين برنامج التحديث و serve/لوحة التحكم و gateway بمقبس تحكّم يملكه gateway (#92091)؛ والفحوص طبقة احتياطية للعمليات القديمة/المتعطلة — اقرأ #92091 قبل إضافة أي قاعدة استدلالية. قواعد هوية العملية (لا سلاسل فرعية في argv مطلقًا؛ مطابِقات معيارية؛ مجموعات خيارات مشتقة من المحلّل؛ لا تستبعد أسلاف gateway جماعيًا مطلقًا، #87594): الجذر AGENTS.md و website/docs/developer-guide/cli-internals.md.

ينتظر الحل الاحتياطي لإعادة التشغيل القسري في systemd مدة TimeoutStopUSec زائد TimeoutStartUSec، مع هامش 15 ثانية من جهة العميل. يقرأ الوحدة الهدف ضمن نطاق المدير نفسه لإعادة التشغيل؛ تستخدم كل من المحاولة الأولى وإعادة المحاولة هذه الميزانية، بما في ذلك إعادة التشغيل التعويضية بعد تحديث مُقاطَع. يستخدم بدء التشغيل بعد استنزاف تدريجي (graceful drain) ميزانية البدء زائد الهامش فقط. يعود حدّ مرحلة مفقود، أو غير قابل للتحليل، أو لا نهائي إلى القيمة الاحتياطية 90 ثانية لتلك المرحلة، مما يبقي التحديثات غير المراقَبة محدودة زمنيًا. انتهاء مهلة عميل systemctl لا يلغي معاملة المدير. يمكن لسلاسل أوامر إيقاف متعددة مخصّصة أو EXTEND_TIMEOUT_USEC أن تتجاوز هذا التقدير مع ذلك؛ ويبقى انتهاء المهلة الفعلي إعادة تشغيل غير مكتملة، وما زالت الأوامر الناجحة تتطلب التحقق القائم من صحة الخدمة وإصدار الأسطول (fleet-version). القيم الرقمية الخام *USec قيمهما بالميكروثانية، بينما تستخدم القيم المنسّقة وحدات systemd الثابتة، بما فيها الأيام والأسابيع والشهور والسنوات. تُحدّ المهلة المجمّعة دون حد الاستطلاع الأصلي بالميلي ثانية الصحيح الموقّع من 32 بت (مع هامش للتقريب)، لكيلا تفيض حدود الوحدات الطويلة جدًا عند استطلاع العمليات الفرعية. تستخدم حدود المراحل الصفرية/المجهولة/غير المحدودة المسار الاحتياطي المحدود. لا يغيّر ذلك إعدادات تفريغ الأدوار النشطة.

تسجيل الدخول إلى المستوى المجاني في Nous

إكمال تسجيل الدخول دالة واحدة، settle_after_upgrade، يستدعيها كل مستدعٍ يحفظ حسابًا فوق هوية المستوى المجاني (CLI upgrade_guest ومستطلِع تطبيق سطح المكتب): تنقل إعدادًا على مسار الترحيب إلى مضيف الحساب والقيمة الافتراضية الموصى بها للمستوى (models.recommended_nous_default_model، مشتركة مع GET /api/model/recommended-default).

يوجد التدفق المشترك والحالات والنص في anon_sign_in.py؛ ويوجد عرض CLI في anon_sign_in_cli.py. anon_auth.py يحتفظ بالهوية واستطلاع الترقية والتسوية، ويعيد تصدير API تسجيل الدخول الحالية. يحلّ التدفق جهات التعاون الخاصة بالهوية والحفظ عبر anon_auth وقت الاستدعاء للحفاظ على نقاط monkeypatch لسمات الوحدة.

تسجيل الدخول نفسه تركيب واحد: ينتج anon_auth.run_sign_in() كائنات SignInState (Code, Waiting, Completed, Declined, Superseded, TimedOut, Retired, Failed, AlreadySignedIn, Unavailable). يقرأ الحالة الحالية بنفسه، ويحافظ على مهلة مطلقة واحدة عبر الانتظارين، ولا يحفظ إلا بعد اكتمال الترقية و منح token، وينفّذ settle_after_upgrade مرة واحدة بالضبط لكل إكمال، ولا يسمح مطلقًا بخروج فشل الحفظ أو التسوية كاستثناء — بل يصبح Failed. تحمل كل حالة .copy الخاص بها (صيغة المحادثة، التي لا تحتوي مطلقًا على استثناء خام أو URL أو فعل hermes) و .copy_terminal، لذا لا يحوّل أي مستدعٍ سببًا إلى سلسلة نصية. يوقف cancelled() محاولةً؛ ويقرّر cancel_wins_after_promotion ما يحدث عندما يكون الخادم قد أكمل النقل بالفعل — يحتفظ تطبيق سطح المكتب بـ True (تعني DELETE "ليس على هذا الجهاز")، ويمرّر gateway False (يجب ألا يؤدي الاستبدال إلى إسقاط نقل وافق عليه المستخدم فعليًا). لا يُدخل scope إلا حول كتل الشرط المسبق والحفظ، ولا يمتد مطلقًا عبر yield أو انتظار شبكة، لأن run_in_executor لا يحمل contextvars. upgrade_guest (hermes auth upgrade)، ومعالج CLI /login ومستطلِع الترقية في تطبيق سطح المكتب جهات عرض فوقه؛ وتمرّر الواجهة التي تحتاج إلى أن يكون فحص الإلغاء والحفظ ذريّين persist_guard. تسجيل دخول تطبيق سطح المكتب العادي عبر رمز الجهاز بعنوان "connect another Nous account" مسار منفصل (_nous_plain_poller) ويجب أن يبقى كذلك.

هوية العملية: لا تستنتجها أبدًا من أجزاء نصية في argv

فئة الخلل وراء نحو 10 مشاكل في تحديث الأسطول (#90778، #87594، #78089، #76129، #91964، ...): تصنيف عملية بناءً على "serve" in cmdline أو ما شابه. يحتوي kanban --preserve-cache على "serve"؛ يمكن لقيمة flag أن تساوي أمرًا فرعيًا (-m dashboard serve)؛ تخفي سطور الأوامر المُقتَطعة الأمر الفرعي الحقيقي. القواعد:

  • استخدم أدوات المطابقة القياسية: gateway.status.looks_like_gateway_command_line (تشغيل gateway)، وhermes_cli.update_cmd._hermes_holder_subcommand (الأمر الفرعي من المستوى الأعلى لأي argv خاص بـ Hermes). لا تكتب فحوصات رموز (token scans) يدويًا مطلقًا.
  • يجب أن تكون مجموعات الـ flags مُشتَقّة من المحلِّل (يفحص _holder_value_flags() build_top_level_parser())، وليس قوائم مكتوبة يدويًا — فهي تنحرف عن الواقع مع الوقت.
  • لا تستبعد الأسلاف (ancestors) بشكل شامل من فحوصات العمليات مطلقًا: عندما يعمل /update كعملية ابنة لـ gateway، يجب أن يبقى سلف الـ gateway مرئيًا لآلية الإيقاف المؤقت (#87594). استبعد النسب التفاعلي (interactive ancestry)، واستثنِ الأسلاف على هيئة gateway.
  • طابق على سطور الأوامر الكاملة؛ اقتطع فقط عند العرض (#78089).
  • قبل إضافة أي طريقة فحص جديدة، اقرأ #92091 — يحلّ مقبس التحكم بالـ gateway محل الفحوصات كـ آلية التنسيق الأساسية؛ الفحوصات هي طبقة احتياطية للعمليات القديمة/المنهارة.

Profiles: دعم النُّسخ المتعددة

يدعم Hermes الـ profiles — نُسخ معزولة تمامًا، لكل منها HERMES_HOME (الإعدادات ومفاتيح API والذاكرة والجلسات والمهارات و gateway). للأوامر أحادية profile (hermes -p x <cmd>), _apply_profile_override() في hermes_cli/main.py HERMES_HOME قبل استيراد أي وحدة (module)، لذا يُحدَّد نطاق كل مرجع لـ get_hermes_home() يحدّد النطاق إلى profile النشط. أما gateway المتعدد و backend serve في Desktop/لوحة التحكم فيخدمان عدة profiles من عملية واحدة: profile النشط تجاوز contextvar مرتبط بكل نشاط، وتظل قيمة os.environ["HERMES_HOME"] هي الخاصة بـ profile التشغيل، ويتجمّد ثابت على مستوى الوحدة مشتق من المجلد عند profile التشغيل ذاك (راجع آلية عمل Gateway من الداخل § Profiles متعددة). ترتكز عمليات profile على HOME (_get_profiles_root() Path.home() / ".hermes" / "profiles"، وليس get_hermes_home() / "profiles") لذا يرى hermes -p coder profile list جميع الـ profiles بغض النظر عن أيها نشط — وهذا مقصود. قواعد البرمجة الآمنة للـ profile موجودة في ملف AGENTS.md الجذري؛ وقواعد نطاق الأسرار (secret-scope) للتعدد (multiplex) في gateway/AGENTS.md.

استكشاف الأخطاء وإصلاحها

فشل التحقق من الإعداد ("URL couldn't be validated") في لوحة تحكم Meta

في الغالب يكون السبب واحدًا مما يلي:

  • URL النفق خاطئ أو قديم — تتغير عناوين الأنفاق السريعة في cloudflared. احصل على URL جديد وحدّث كلًّا من .env ولوحة تحكم Meta.
  • عدم تطابق Verify token — يجب أن يتطابق الـ token الموجود في ملف ~/.hermes/.env ضمن المتغير WHATSAPP_CLOUD_VERIFY_TOKEN تمامًا مع ما كتبته في لوحة تحكم Meta. نفّذ فحص curl الوارد أعلاه للتأكد أولًا من أن مصافحة التحقق في الـ gateway تعمل محليًا.
  • الـ gateway لا يعمل — تحقّق من أن hermes gateway قيد التشغيل.
  • App Secret غير مضبوط — من دونه يرفض Hermes طلبات POST الواردة بالرمز 503، وتفسّر Meta ذلك على أنه "can't validate."

graph error 100: Object with ID '...' does not exist

لقد لصقت رقم هاتفك (10-11 خانة) في WHATSAPP_CLOUD_PHONE_NUMBER_ID بدلًا من Phone Number ID (المعرّف الداخلي لدى Meta المكوّن من 15-17 خانة). راجع صفحة API Setup مرة أخرى — إذ يظهر Phone Number ID أسفل القائمة المنسدلة "From".

يكتشف المعالج هذا الخطأ الآن عبر أداة تحقق، لكن من المفيد معرفته إذا كنت تُجري الإعداد يدويًا.

graph error 190: خطأ في المصادقة (Authentication Error)

الـ access token الخاص بك غير صالح. الرموز الفرعية:

  • subcode 463 — انتهت صلاحية الـ token. الـ tokens المؤقتة تدوم 24 ساعة. أعد توليده، أو انتقل إلى token دائم لمستخدم نظام (System User) (راجع ما سبق).
  • subcode 467 — أُبطل الـ token (أُلغي أو تغيّرت كلمة المرور).
  • رموز 190 الأخرى — لم يُمنح الـ token الصلاحيات المطلوبة عند توليده. تأكد من تحديد الصلاحيات الثلاث جميعها (business_management، whatsapp_business_messaging، whatsapp_business_management).

graph error 131047: Re-engagement message (رسالة إعادة التفاعل)

انتهت نافذة المحادثة ذات الـ 24 ساعة (راجع "القيود المعروفة"). ويمكنك إما:

  • أن تطلب من المستخدم مراسلة البوت أولًا لإعادة فتح النافذة.
  • أو أن تنتظر إضافة دعم القوالب إلى Hermes.

رسالة واردة: media metadata fetch failed (status=401)

أسباب الخطأ 401 هنا هي نفسها في الرسائل الصادرة (graph error 190) — فالـ access token غير صالح أو منتهي الصلاحية. أصلح الـ token.

ظهور ردود البوت كـ JSON خام / تسرّب استدعاءات الأدوات

السبب الشائع: الـ toolset المُعدّ لـ whatsapp_cloud يفتقد الأدوات التي يريد الوكيل استدعاءها. تحقّق من hermes tools list وتأكد من أن المنصة تستخدم hermes-whatsapp (الـ toolset الافتراضي لمحوّل Cloud، وهو نفسه المستخدم مع Baileys).

إذا أخرج النموذج نصًا على هيئة استدعاء أداة بدلًا من استدعاء منظّم، فهذا يعني عادةً أن الـ toolset كان فارغًا فعليًا. راجع hermes_cli/platforms.py لمعرفة الربط بين المنصة → الـ toolset الافتراضي.

STT (تفريغ الملاحظات الصوتية) يُرجع نتيجة فارغة / "could not transcribe"

يتطلب الإعداد الافتراضي stt.provider: local تنفيذ pip install faster-whisper. وإذا كنت مشتركًا في Nous، فيمكنك بدلًا من ذلك توجيه STT عبر الـ gateway المُدار — اختر Nous Subscription لتحويل الكلام إلى نص في hermes tools، أو اضبطه مباشرةً:

يستخدم هذا الـ access token الخاص بك في Nous Portal بدلًا من الحاجة إلى مفتاح OpenAI منفصل. (اقترحت الوثائق القديمة stt.use_gateway true — وهو خيار قديم (legacy)؛ إذ أصبح اختيار المزوّد وحده هو ما يتحكم في التوجيه الآن.)

ملاحظات أمنية

  • تعامل مع App Secret ككلمة مرور — فأي شخص يملكه يستطيع تزوير حمولات webhook يقبلها Hermes على أنها أصلية.
  • الـ verify token سرّ مشترك — تسريبه أقل خطورة (ففي أسوأ الأحوال قد يعيد شخص ما توجيه اشتراك webhook لدى Meta إلى URL آخر يملكه)، لكن تجنّب مع ذلك إضافته إلى أي commit.
  • الـ access token هو هوية بوتك — فـ tokens مستخدمي النظام (System User) تعادل مفاتيح API طويلة الأمد. بدّله فورًا إذا تعرضت عملية نشر للاختراق.
  • لا يقبل endpoint الخاص بـ webhook إلا الطلبات الموقّعة عند ضبط WHATSAPP_CLOUD_APP_SECRET — أبقِه مضبوطًا حتى في بيئة التطوير. فمن دونه يرفض الـ gateway تسليم الرسائل الواردة بالرمز HTTP 503.
  • الـ endpoint /health لا يتطلب مصادقة — ومن الآمن كشفه لأنه لا يُبلغ إلا بقيم منطقية (booleans) تشير إلى وجود الإعدادات، لا بالقيم نفسها. لكن إن كنت تفضّل عدم إظهاره، فقيّد الوصول إليه على مستوى الـ reverse proxy / النفق.

Profiles: تشغيل عدة وكلاء

شغّل عدة وكلاء Hermes مستقلين على الجهاز نفسه — لكل منها إعداداته الخاصة، ومفاتيح API، والذاكرة، والجلسات، والمهارات، وحالة gateway الخاصة به.

ما هي الـ profiles؟

الـ profile هو دليل منزلي (home directory) منفصل لـ Hermes. يحصل كل profile على دليله الخاص الذي يحتوي على config.yaml و.env وSOUL.md، والذكريات، والجلسات، والمهارات، ومهام cron، وقاعدة بيانات الحالة. لا يتعرّف Hermes إلى مجلد ضمن ~/.hermes/profiles/ بوصفه profile إلا إذا احتوى أحد ملفات الهوية تلك (config.yaml, .env, SOUL.md, profile.yaml, auth.json, state.db)؛ ويتجاهل profile list و gateways و -p أي مجلد فارغ خلّفته السجلات أو cron. تتيح لك profiles تشغيل وكلاء منفصلين لأغراض مختلفة — مساعد برمجة، أو بوت شخصي، أو وكيل بحث — دون خلط حالة Hermes.

امنح كل وكيل profile خاصًا به

لا توجّه أبدًا عمليتَي وكيل إلى الـ profile نفسه (نفس دليل Hermes المنزلي). فكلاهما يكتب في الذاكرة تلقائيًا، ويحمّل كل منهما كتابات الآخر في الـ system prompt الخاص به عند بدء الجلسة — بحيث يتراكم أثر كاتبَين على منزل واحد إلى أن يتوقف عن أن يكون ما ضبطته أنت. الـ profiles موجودة تحديدًا لمنع هذا؛ الوكلاء الذين يحتاجون إلى ذاكرة مشتركة ينبغي أن يستخدموا بدلًا من ذلك مزوّد ذاكرة خارجي (external memory provider).

عند إنشاء profile، يصبح تلقائيًا أمرًا خاصًا به. أنشئ profile باسم coder وستحصل فورًا على coder chat وcoder setup وcoder gateway start وهكذا.

Profiles والوكلاء والبوتات

تصف هذه المصطلحات أجزاء مختلفة من Hermes:

  • Profile هو المجلد الرئيسي الدائم لإعدادات المساعد وبياناته. يحتفظ بالحالة نفسها عبر المحادثات وإعادة التشغيل.

  • الوكيل هو مساعد Hermes قيد التشغيل الذي يستخدم تلك الإعدادات والحالة. ويشير اسم "Hermes Agent" أيضًا إلى المنتج.

  • بوت Bot Mode هو profile يظهر كإدخال مسمّى في قائمة Bot Mode على سطح المكتب، مع صورة رمزية و Bot Chat دائمة. يظل profile نفسه متاحًا من CLI. كل Bot هو profile، لكن ليس كل profile هو Bot: يصبح profile بوتًا عندما يخزّن Bot Mode طريقة عرضه في القائمة (العنوان، والصورة الرمزية، والقسم، وحالة الإخفاء) في بيانات profile الوصفية ويثبّت Bot Chat الأساسية الخاصة به. ويظل profile الذي لا تستخدمه إلا من CLI أو Docker أو gateway، ولا تضيفه أبدًا إلى القائمة، profile عاديًا.

  • بوت المراسلة هو حساب على منصة مثل Telegram أو Discord أو Slack، متصل بـ Hermes عبر gateway. وتعرّف قيمة token البوت حسابه على تلك المنصة.

  • Subagent هو مساعد فرعي يُطلَق عبر delegate_task لمهمة، بمحادثة جديدة. تختلف المحادثة المنفصلة عن profile منفصل.

استنساخ الإعدادات فقط (--clone)

ينسخ config.yaml و.env وSOUL.md الخاصة بالـ profile الحالي، والمهارات، وملفَي الذاكرة المنسّقين memories/MEMORY.md وmemories/USER.md إلى الـ profile الجديد — تُعامَل الذاكرة كجزء من هوية الوكيل، شأنها شأن SOUL.md. إذا اختار config.yaml مزوّد ذاكرة خارجيًا (memory.provider)، تنتقل إعدادات ذلك المزوّد أيضًا — مجلده <provider>/ أو ملفه <provider>.json ضمن المجلد الرئيسي لـ profile، مثل hindsight/config.json — لتكون ذاكرة النسخة متاحةً بدلًا من تعطيلها بصمت؛ وتظل إعدادات hindsight المستنسخة من نوع local_embedded تشارك daemon المضمّن والبنك مع المصدر حتى تمنح النسخة قيمة hindsight خاصة بها لـ profile/bank_id (#81815). تنتقل الإضافات المثبتة أيضًا: يُنسخ plugins/ (إضافات الكتالوج و Git والمثبتة يدويًا، وسجلات تثبيتها)، ولذلك يظل مزوّد الذاكرة المثبّت من كتالوج الإضافات يعمل في النسخة عند المراجعة نفسها ويحتفظ بسجل تثبيته في الكتالوج. توجد اعتماديات Python للإضافات في البيئة المشتركة ولا تُثبّت مجددًا. ولا تُنسخ الجلسات، ولا state.db ومهام cron وكل شيء آخر فتبدأ فارغة. للحصول على ذاكرة فارغة أيضًا، أنشئ الـ profile من دون --clone أو احذف الملفين لاحقًا؛ فالوكيل لا يرجع أبدًا إلى ذاكرة profile آخر عند غيابهما. حرّر ~/.hermes/profiles/work/.env لمفاتيح API مختلفة، أو ~/.hermes/profiles/work/SOUL.md لتغيير الشخصية.

استنساخ كل شيء (--clone-all)

ينسخ كل شيء — الإعدادات، ومفاتيح API، والشخصية، وكل الذاكرة، والمهارات، والإضافات. لقطة (snapshot) عاملة كاملة. يُستثنى تاريخ كل profile على حدة (تاريخ الجلسات، وstate.db، وbackups/، وstate-snapshots/، وcheckpoints/) — فهي تخص profile المصدر وقد تبلغ عشرات GB. وعند الاستنساخ من profile الافتراضي، تُتجاوز أيضًا أشجار تشغيل النماذج المحلية (models/, runtimes/, node/ — الأوزان والملفات التنفيذية المُدارة المُنزَّلة، ويُعاد جلبها عند الطلب)، كما يفعل hermes backup بالفعل. مهام cron: فهي عمل مجدول مرتبط بالـ profile المصدر وقناة التسليم الخاصة به، والاستنساخ الذي يرثها سيؤدي إلى تشغيل كل مهمة مرتين (بوابتان (gateways)، ومعرّفات مهام متطابقة). يبدأ الـ profile الجديد بمجلد cron/ فارغ. للحصول على نسخة احتياطية كاملة تتضمن التاريخ ومهام cron، استخدم بدلًا من ذلك hermes profile export أو hermes backup.

تسجيلات دخول OAuth مشتركة وليست منسوخة

تعتمد تسجيلات دخول OAuth الخاصة بـ Anthropic (Claude Pro/Max) وOpenAI Codex وxAI على رموز تحديث (refresh tokens) للاستخدام الواحد — فنسخة إحداها ليست بيانات اعتماد ثانية، بل هي بيانات الاعتماد نفسها بمالكَين، وأول profile يحدّثها يلغيها لكل النسخ الأخرى. لذلك يُسقط --clone-all (وكذلك مرآة بيانات الاعتماد في لوحة التحكم) صفوف OAuth هذه من النسخة. يستمر الـ profile الجديد بقراءة تسجيل الدخول من ~/.hermes/auth.json الجذري، ويُكتب أي تحديث للرمز يتم داخل أي profile إلى الجذر، بحيث تبقى كل الـ profiles مسجّلة الدخول. أما مفاتيح API الثابتة فتُنسخ كالمعتاد. لمنح profile تسجيل دخول OAuth منفصلًا خاصًا به، نفّذ hermes -p <name> auth add <provider> داخله. يُحفظ تسجيل الدخول في auth.json الخاص بـ profile، حتى إذا لم يكن لدى الجذر تسجيل دخول للمزوّد بعد؛ ومنذ ذلك الحين يستخدمه profile بدلًا من تسجيل دخول الجذر؛ ولا يتغير auth.json الخاص بالجذر. وإذا تعذّر حفظ تسجيل الدخول، يفشل الأمر بخطأ بدلًا من طباعة Added.

الاستنساخ من profile محدد

--clone-from <source> الـ profile المصدر مباشرةً، ويعني ضمنيًا استنساخ الإعدادات/المهارات/SOUL. اجمعه مع --clone-all عندما تريد نسخة كاملة من ذلك الـ profile المصدر:

قنوات المراسلة لا تُستنسخ أبدًا (استخدم --clone-channels للانضمام اختياريًا)

كل استنساخ — سواء --clone أو --clone-from أو --clone-all، أو خيار "clone from profile" في لوحة التحكم أو Desktop أو TUI — ينسخ المصدر من دون قنوات المراسلة الخاصة به: رموز البوت وقوائم السماح (TELEGRAM_BOT_TOKEN وDISCORD_ALLOWED_USERS وWHATSAPP_ENABLED وAPI_SERVER_KEY وWEBHOOK_SECRET، ...)، وأقسام platforms: / telegram: / discord: في config.yaml، وgateway.multiplex_profiles / profile_routes، و(في حالة --clone-all) مخزن الاقتران (pairing store)، وجلسة WhatsApp، وحالات أخرى خاصة بكل بوت. أما مفاتيح API للمزوّدين والأدوات، وقسم النموذج، وإعدادات الذاكرة، والمهارات، وSOUL.md فتُنسخ كما كانت. ويطبع الأمر أي منصات تُركت خلف الركب.

السبب هو أن البوت الواحد لا يمكن أن ينتمي إلا إلى profile واحد: فبوابتان (gateways) مستقلتان تحملان نفس الرمز تتنازعان على الـ long-poll الخاص به، وأي بوابة مضاعَفة (multiplexed gateway) تُوقف المحوّل المكرَّر جانبًا (كما يرفض hermes gateway migrate --multiplex ذلك برسالة عائق واحدة لكل بيانات اعتماد مكررة لكل منصة). اضبط بوتات الـ profile الجديد الخاصة به عبر hermes -p <name> setup أو صفحة Messaging في لوحة التحكم.

--clone-channels يُرفض عندما تكون gateway متعددة profiles قيد التشغيل تخدم المصدر بالفعل (ستُوقَف النسخة جانبًا فورًا) — في CLI ولوحة التحكم و TUI على السواء — ويطبع خلاف ذلك تحذيرًا يسمّي المنصات المشتركة الآن مع المصدر. ويُعدّ خطأً دون خيار استنساخ.hermes profile list يطبع التحذير نفسه لأي profile موجود تطابق بيانات اعتماد بوته بيانات الافتراضي على مستوى البايتات، فتظهر النسخ الأقدم قبل أن تسبب مشكلات.

ما يُعدّ إعدادًا للقناة — تعتمد القائمة على الملكية، ويُقيَّم ذلك في نطاق إضافات profile المصدر (بما فيها محوّلات plugins/ الخاصة به):

  • كل مفتاح يعلنه محوّل (tokens، ومعرّفات التطبيقات/العملاء، وقوائم السماح، وخيارات السماح للجميع، والقنوات الرئيسية)، وكل مفتاح ضمن البادئة <PLATFORM>_ الخاصة به، بما في ذلك الأسماء البديلة القديمة (WECOM_*, SMS_*/TWILIO_*, QQ_*, HASS_*, EMAIL_*);
  • سياسة القنوات العامة للـ gateway، وهي GATEWAY_ALLOW_ALL_USERS / GATEWAY_ALLOWED_USERS وهوية تسجيل relay، وهي GATEWAY_RELAY_ID / GATEWAY_RELAY_SECRET / GATEWAY_RELAY_DELIVERY_KEY;
  • في --clone-all، ملفات الحالة الخاصة بكل بوت ومجلداتها (platforms/، وسجلات الاقتران، و google_chat_user_tokens/, <platform>_*).

بيانات الاعتماد التي يشترك فيها محوّل مراسلة مع قدرة غير متعلقة بالقناة — HASS_TOKEN/HASS_URL (أدوات إضافة Home Assistant أيضًا؛ وتعلن محوّلات الإضافات عنها باسم shared_env_prefixes), TWILIO_* (مهارة الاتصال الهاتفي أيضًا)، و EMAIL_* (سكربتات إرسال البريد أيضًا) — تُزال فقط عندما تكون gateway الخاصة بالمصدر ستشغّل ذلك المحوّل (تكون المنصة مفعّلة في config.yaml الخاص به، أو تكون مجموعة بيانات اعتمادها مكتملة وغير معطّلة صراحةً). يستخدم المصدر الذي يحتوي platforms.homeassistant.enabled: false قيمة HASS_TOKEN كمفتاح للأداة، لذلك تحتفظ النسخة بها. تكون قوائم السماح والمنافذ ضمن تلك البادئات دائمًا خاصة بالقنوات وحدها، وتُزال دائمًا.

تُنشأ النسخ في مجلد تجهيز مخفي بجوار profiles/ وتُنشَر بإعادة تسمية واحدة بعد الإزالة، بحيث لا تستطيع خدمة تعدد profiles قيد التشغيل (التي تعيد فحص profiles/ عند الإنشاء) تشغيل محوّلات على شجرة منسوخة جزئيًا. ويُحوَّل ملف المصدر المرتبط رمزيًا، مثل .env/config.yaml، إلى نسخة خاصة أولًا — ولا تكتب النسخة المستنسخة في المصدر عبر الرابط مطلقًا.

يضبط افتراضيًا بحيث تستهدف أوامر hermes العادية ذلك الـ profile. مثل kubectl config use-context.

معرفة أين أنت

تُظهر واجهة CLI دائمًا الـ profile النشط:

  • موجّه الأوامر (Prompt): coder ❯ بدلًا من ❯
  • الشعار الافتتاحي (Banner): يُظهر Profile: coder عند بدء التشغيل
  • hermes profile: يُظهر اسم الـ profile الحالي، والمسار، والنموذج، وحالة gateway

الـ profiles مقابل مساحات العمل مقابل الحوسبة المعزولة (sandboxing)

كثيرًا ما تُخلط الـ profiles بمساحات العمل أو sandboxes، لكنها أمور مختلفة:

  • يمنح الـ profile Hermes دليل حالة خاصًا به: config.yaml و.env وSOUL.md، والجلسات، والذاكرة، والسجلات، ومهام cron، وحالة gateway.
  • مساحة العمل (workspace) أو دليل العمل (working directory) هو المكان الذي تبدأ منه أوامر الطرفية. يُضبط ذلك بشكل منفصل عبر terminal.cwd.
  • الـ sandbox هو ما يحدّ من الوصول إلى نظام الملفات. لا تعزل الـ profiles الوكيل عزلًا حقيقيًا (sandbox).

على terminal backend الافتراضي وهو local، يظل للوكيل نفس صلاحية الوصول إلى نظام الملفات التي يملكها حساب مستخدمك. الـ profile لا يمنعه من الوصول إلى مجلدات خارج دليل الـ profile.

إذا أردت أن يبدأ profile في مجلد مشروع محدد، فاضبط قيمة مطلقة صريحة لـ terminal.cwd صريحًا ومطلقًا في config.yaml الخاص بذلك الـ profile:

استخدام cwd: "." على backend المحلي (local) يعني "الدليل الذي انطُلق منه Hermes"، وليس "دليل الـ profile".

لاحظ أيضًا ما يلي:

  • SOUL.md أن يوجّه النموذج، لكنه لا يفرض حدود مساحة عمل.
  • تسري التغييرات في SOUL.md بشكل نظيف على جلسة جديدة. أما الجلسات القائمة فقد لا تزال تستخدم حالة الـ prompt القديمة.
  • سؤال النموذج "في أي دليل أنت؟" ليس اختبار عزل موثوقًا. إن احتجت دليل بداية يمكن التنبؤ به للأدوات، اضبط terminal.cwd صراحةً.

داخل صورة Docker الرسمية

تُشرف على gateways كل profile أداة s6-overlay (وهي PID 1 داخل الحاوية)، لذا يسجّل hermes profile create <name> تلقائيًا فتحة خدمة s6 عند /run/service/gateway-<name>/. يُرسِل hermes -p <name> gateway start/stop/restart الأمر إلى s6-svc بدلًا من توليد عملية مستقلة — تُعاد الأعطال (crashes) إلى العمل تلقائيًا، ويحافظ docker restart على مجموعة الـ gateways التي كانت تعمل سابقًا. راجع الإشراف على gateway لكل profile للتفاصيل.

إعداد الـ profiles

لكل profile ما يخصّه:

  • config.yaml — النموذج، والمزوّد، والـ toolsets، وكل الإعدادات
  • .env — مفاتيح API، ورموز البوت
  • SOUL.md — الشخصية والتعليمات

من لوحة التحكم

تتيح لوحة تحكم الويب هي واجهة على مستوى الجهاز يمكنها إدارة إعدادات أي profile، ومفاتيح API، والمهارات، وMCPs، والنموذج عبر مبدّل الـ profile في الشريط الجانبي — من دون حاجة إلى لوحة تحكم لكل profile على حدة. يوجّه coder dashboard إلى لوحة تحكم الجهاز مع تحديد profile باسم coder مسبقًا. يتبع تبويب Chat في لوحة التحكم المبدّلَ أيضًا، فيُنشئ محادثة تحت منزل الـ profile المحدد.

ملاحظة: "Set as active" في صفحة Profiles بلوحة التحكم هو الافتراضي الثابت لتشغيلات CLI/gateway المستقبلية (كما في hermes profile use) — لتحرير profile من لوحة التحكم، استخدم المبدّل بدلًا من ذلك.

لا تُستبدل أبدًا المهارات التي عدّلها المستخدم.

تقرأ تهيئة الاعتماديات config.yaml لكل profile لحساب مجموعة الإضافات التي يجب أن تتضمنها البيئة المشتركة. وإذا تعذّر تحليل config.yaml الخاص بـ profile (أو كانت أقسام plugins / memory فيه ذات بنية غير صحيحة)، تفشل تلك الخطوة للتثبيت بأكمله — راجع تهيئة الاعتماديات والحفاظ عليها.

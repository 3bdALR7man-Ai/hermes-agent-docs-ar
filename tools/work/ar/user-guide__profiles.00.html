Profiles: تشغيل عدة وكلاء

شغّل عدة وكلاء Hermes مستقلين على الجهاز نفسه — لكل منها إعداداته الخاصة، ومفاتيح API، والذاكرة، والجلسات، والمهارات، وحالة gateway الخاصة به.

ما هي الـ profiles؟

الـ profile هو دليل منزلي (home directory) منفصل لـ Hermes. يحصل كل profile على دليله الخاص الذي يحتوي على config.yaml و.env وSOUL.md الخاصة به، إضافةً إلى الذاكرة، والجلسات، والمهارات، ومهام cron، وقاعدة بيانات الحالة. تتيح لك الـ profiles تشغيل وكلاء منفصلين لأغراض مختلفة — مساعد برمجة، وبوت شخصي، ووكيل بحث — دون خلط حالة Hermes بينها.

امنح كل وكيل profile خاصًا به

لا توجّه أبدًا عمليتَي وكيل إلى الـ profile نفسه (نفس دليل Hermes المنزلي). فكلاهما يكتب في الذاكرة تلقائيًا، ويحمّل كل منهما كتابات الآخر في الـ system prompt الخاص به عند بدء الجلسة — بحيث يتراكم أثر كاتبَين على منزل واحد إلى أن يتوقف عن أن يكون ما ضبطته أنت. الـ profiles موجودة تحديدًا لمنع هذا؛ الوكلاء الذين يحتاجون إلى ذاكرة مشتركة ينبغي أن يستخدموا بدلًا من ذلك مزوّد ذاكرة خارجي (external memory provider).

عند إنشاء profile، يصبح تلقائيًا أمرًا خاصًا به. أنشئ profile باسم coder وستحصل فورًا على coder chat وcoder setup وcoder gateway start وهكذا.

البدء السريع

هذا كل ما في الأمر. أصبح coder الآن profile خاصًا به لـ Hermes، بإعداداته وذاكرته وحالته الخاصة.

استنساخ الإعدادات فقط (--clone)

ينسخ config.yaml و.env وSOUL.md الخاصة بالـ profile الحالي، والمهارات، وملفَي الذاكرة المنسّقين memories/MEMORY.md وmemories/USER.md إلى الـ profile الجديد — تُعامَل الذاكرة كجزء من هوية الوكيل، شأنها شأن SOUL.md. أما الجلسات وstate.db ومهام cron وكل شيء آخر فتبدأ فارغة. للحصول على ذاكرة فارغة أيضًا، أنشئ الـ profile من دون --clone أو احذف الملفين لاحقًا؛ فالوكيل لا يرجع أبدًا إلى ذاكرة profile آخر عند غيابهما. حرّر ~/.hermes/profiles/work/.env لمفاتيح API مختلفة، أو ~/.hermes/profiles/work/SOUL.md لشخصية مختلفة.

استنساخ كل شيء (--clone-all)

ينسخ كل شيء — الإعدادات، ومفاتيح API، والشخصية، وكل الذاكرة، والمهارات، والإضافات. لقطة (snapshot) عاملة كاملة. يُستثنى تاريخ كل profile على حدة (تاريخ الجلسات، وstate.db، وbackups/، وstate-snapshots/، وcheckpoints/) — فهذه تخصّ الـ profile المصدر ويمكن أن تصل إلى عشرات الغيغابايتات. كما لا تُستنسخ مهام cron: فهي عمل مجدول مرتبط بالـ profile المصدر وقناة التسليم الخاصة به، والاستنساخ الذي يرثها سيؤدي إلى تشغيل كل مهمة مرتين (بوابتان (gateways)، ومعرّفات مهام متطابقة). يبدأ الـ profile الجديد بمجلد cron/ فارغ. للحصول على نسخة احتياطية كاملة تتضمن التاريخ ومهام cron، استخدم بدلًا من ذلك hermes profile export أو hermes backup.

تسجيلات دخول OAuth مشتركة وليست منسوخة

تعتمد تسجيلات دخول OAuth الخاصة بـ Anthropic (Claude Pro/Max) وOpenAI Codex وxAI على رموز تحديث (refresh tokens) للاستخدام الواحد — فنسخة إحداها ليست بيانات اعتماد ثانية، بل هي بيانات الاعتماد نفسها بمالكَين، وأول profile يحدّثها يلغيها لكل النسخ الأخرى. لذلك يُسقط --clone-all (وكذلك مرآة بيانات الاعتماد في لوحة التحكم) صفوف OAuth هذه من النسخة. يستمر الـ profile الجديد بقراءة تسجيل الدخول من ~/.hermes/auth.json الجذري، ويُكتب أي تحديث للرمز يتم داخل أي profile إلى الجذر، بحيث تبقى كل الـ profiles مسجّلة الدخول. أما مفاتيح API الثابتة فتُنسخ كالمعتاد. لمنح profile تسجيل دخول OAuth منفصلًا خاصًا به، نفّذ hermes -p <name> auth add <provider> داخله.

الاستنساخ من profile محدد

يحدّد --clone-from <source> الـ profile المصدر مباشرةً، ويعني ضمنيًا استنساخ الإعدادات/المهارات/SOUL. اجمعه مع --clone-all عندما تريد نسخة كاملة من ذلك الـ profile المصدر:

قنوات المراسلة لا تُستنسخ أبدًا (استخدم --clone-channels للانضمام اختياريًا)

كل استنساخ — سواء --clone أو --clone-from أو --clone-all، أو خيار "clone from profile" في لوحة التحكم أو Desktop أو TUI — ينسخ المصدر من دون قنوات المراسلة الخاصة به: رموز البوت وقوائم السماح (TELEGRAM_BOT_TOKEN وDISCORD_ALLOWED_USERS وWHATSAPP_ENABLED وAPI_SERVER_KEY وWEBHOOK_SECRET، ...)، وأقسام platforms: / telegram: / discord: في config.yaml، وgateway.multiplex_profiles / profile_routes، و(في حالة --clone-all) مخزن الاقتران (pairing store)، وجلسة WhatsApp، وحالات أخرى خاصة بكل بوت. أما مفاتيح API للمزوّدين والأدوات، وقسم النموذج، وإعدادات الذاكرة، والمهارات، وSOUL.md فتُنسخ كما كانت. ويطبع الأمر أي منصات تُركت خلف الركب.

السبب هو أن البوت الواحد لا يمكن أن ينتمي إلا إلى profile واحد: فبوابتان (gateways) مستقلتان تحملان نفس الرمز تتنازعان على الـ long-poll الخاص به، وأي بوابة مضاعَفة (multiplexed gateway) تُوقف المحوّل المكرَّر جانبًا (كما يرفض hermes gateway migrate --multiplex ذلك برسالة عائق واحدة لكل بيانات اعتماد مكررة لكل منصة). اضبط بوتات الـ profile الجديد الخاصة به عبر hermes -p <name> setup أو صفحة Messaging في لوحة التحكم.

يُرفض --clone-channels عندما تخدم بوابة مضاعَفة قيد التشغيل المصدر فعلًا (لأن النسخة ستُوقف جانبًا فورًا)، وإلا فإنه يطبع تحذيرًا يسمّي المنصات المشتركة الآن مع المصدر. يطبع hermes profile list التحذير نفسه لأي profile موجود تتطابق بيانات اعتماد البوت الخاصة به حرفيًا مع الافتراضي، بحيث تظهر النسخ القديمة قبل أن تسبّب مشكلة. تُشتق مجموعة المفاتيح من محوّلات المنصات نفسها (سجلات التسجيل وجدول env الخاص بالبوابة)، لذا تُغطّى أي منصة جديدة تلقائيًا.

الافتراضي الثابت (hermes profile use)

يضبط افتراضيًا بحيث تستهدف أوامر hermes العادية ذلك الـ profile. مثل kubectl config use-context.

معرفة أين أنت

تُظهر واجهة CLI دائمًا الـ profile النشط:

  • موجّه الأوامر (Prompt): coder ❯ بدلًا من ❯
  • الشعار الافتتاحي (Banner): يُظهر Profile: coder عند بدء التشغيل
  • hermes profile: يُظهر اسم الـ profile الحالي، والمسار، والنموذج، وحالة gateway

الـ profiles مقابل مساحات العمل مقابل الحوسبة المعزولة (sandboxing)

كثيرًا ما تُخلط الـ profiles بمساحات العمل أو sandboxes، لكنها أمور مختلفة:

  • يمنح الـ profile Hermes دليل حالة خاصًا به: config.yaml و.env وSOUL.md، والجلسات، والذاكرة، والسجلات، ومهام cron، وحالة gateway.
  • مساحة العمل (workspace) أو دليل العمل (working directory) هو المكان الذي تبدأ منه أوامر الطرفية. يُضبط ذلك بشكل منفصل عبر terminal.cwd.
  • الـ sandbox هو ما يحدّ من الوصول إلى نظام الملفات. لا تعزل الـ profiles الوكيل عزلًا حقيقيًا (sandbox).

على terminal backend الافتراضي وهو local، يظل للوكيل نفس صلاحية الوصول إلى نظام الملفات التي يملكها حساب مستخدمك. الـ profile لا يمنعه من الوصول إلى مجلدات خارج دليل الـ profile.

إذا أردت أن يبدأ profile داخل مجلد مشروع محدد، اضبط terminal.cwd صريحًا ومطلقًا في config.yaml الخاص بذلك الـ profile:

استخدام cwd: "." على backend المحلي (local) يعني "الدليل الذي انطُلق منه Hermes"، وليس "دليل الـ profile".

لاحظ أيضًا ما يلي:

  • يمكن لـ SOUL.md أن يوجّه النموذج، لكنه لا يفرض حدود مساحة عمل.
  • تسري التغييرات في SOUL.md بشكل نظيف على جلسة جديدة. أما الجلسات القائمة فقد لا تزال تستخدم حالة الـ prompt القديمة.
  • سؤال النموذج "في أي دليل أنت؟" ليس اختبار عزل موثوقًا. إن احتجت دليل بداية يمكن التنبؤ به للأدوات، اضبط terminal.cwd صراحةً.

الخدمات الدائمة (Persistent services)

داخل صورة Docker الرسمية

تُشرف على gateways كل profile أداة s6-overlay (وهي PID 1 داخل الحاوية)، لذا يسجّل hermes profile create <name> تلقائيًا فتحة خدمة s6 عند /run/service/gateway-<name>/. يُرسِل hermes -p <name> gateway start/stop/restart الأمر إلى s6-svc بدلًا من توليد عملية مستقلة — تُعاد الأعطال (crashes) إلى العمل تلقائيًا، ويحافظ docker restart على مجموعة الـ gateways التي كانت تعمل سابقًا. راجع Per-profile gateway supervision للتفاصيل.

من لوحة التحكم

لوحة تحكم الويب هي واجهة على مستوى الجهاز يمكنها إدارة إعدادات أي profile، ومفاتيح API، والمهارات، وMCPs، والنموذج عبر مبدّل الـ profile في الشريط الجانبي — من دون حاجة إلى لوحة تحكم لكل profile على حدة. يوجّه coder dashboard إلى لوحة تحكم الجهاز مع تحديد profile باسم coder مسبقًا. يتبع تبويب Chat في لوحة التحكم المبدّلَ أيضًا، فيُنشئ محادثة تحت منزل الـ profile المحدد.

تسمية الـ profile الافتراضي

المعرّف الداخلي للـ profile الافتراضي هو دائمًا default — ولا يمكن إعادة تسميته حقًا لأن ~/.hermes هو جذر التثبيت. بدلًا من ذلك تؤدي إعادة تسميته إلى ضبط اسم عرض (display name)، تُظهره واجهات المستخدم بدلًا من المعرّف الخام:

يظهر اسم العرض في hermes profile list/show، وأمر المحادثة /profile، ولوحة التحكم، وتطبيق سطح المكتب (بما في ذلك قائمة Bot Mode). وهو عرض فقط: يستمر -p default، وأسماء الخدمات، ومهام cron، وكل مرجع آخر في استخدام المعرّف الأصلي default. يُخزَّن كـ display_name في ~/.hermes/profile.yaml؛ احذف ذلك السطر للتراجع. يمكن أن تحمل الـ profiles المسمّاة display_name أيضًا (يبقى بعد إعادة تسمية حقيقية)، لكن rename لها ما زال يعيد تسمية الـ profile نفسه.

حذف profile

يوقف هذا الأمر الـ gateway، ويزيل خدمة systemd/launchd، ويزيل الاسم المستعار للأمر، ويحذف كل بيانات الـ profile. سيُطلب منك كتابة اسم الـ profile للتأكيد.

استخدم --yes لتخطي التأكيد: hermes profile delete coder --yes

ملاحظة

لا يمكنك حذف الـ profile الافتراضي (~/.hermes). لإزالة كل شيء، استخدم hermes uninstall.

الإكمال التلقائي بمفتاح Tab

أضف هذا السطر إلى ~/.bashrc أو ~/.zshrc للحصول على إكمال تلقائي دائم. يُكمِل أسماء الـ profiles بعد -p، وأوامر profile الفرعية، والأوامر ذات المستوى الأعلى.

آلية العمل

تستخدم الـ profiles متغير البيئة HERMES_HOME. عند تشغيل coder chat، يضبط سكربت الـ wrapper HERMES_HOME=~/.hermes/profiles/coder قبل تشغيل hermes. وبما أن 119 ملفًا أو أكثر في قاعدة الكود تحلّ المسارات عبر get_hermes_home()، تُحدَّد حالة Hermes تلقائيًا ضمن نطاق دليل الـ profile — الإعدادات، والجلسات، والذاكرة، والمهارات، وقاعدة بيانات الحالة، وPID الخاص بـ gateway، والسجلات، ومهام cron.

وهذا منفصل عن دليل عمل الطرفية. يبدأ تنفيذ الأدوات من terminal.cwd (أو دليل الإطلاق عند cwd: "." على backend المحلي)، وليس تلقائيًا من HERMES_HOME.

في التثبيتات على الجهاز المضيف (host)، تحافظ العمليات الفرعية للأدوات على HOME الحقيقي لمستخدم نظام التشغيل افتراضيًا، بحيث تستمر بيانات اعتماد CLI الموجودة تحت ~ في العمل عبر الـ profiles. تُعزل بيانات الـ profile عبر HERMES_HOME، لا عبر تغيير HOME. لا تزال backends الحاويات تستخدم {HERMES_HOME}/home لحالة الأدوات الدائمة، ويمكن لمستخدمي الجهاز المضيف الذين يحتاجون إلى إعدادات أدوات منفصلة تمامًا لكل profile أن ينضموا اختياريًا عبر terminal.home_mode: profile.

هذا يعني أمرين يسهل الخلط بينهما:

  • HERMES_HOME هو حدود الـ profile. يتحكم في إعدادات Hermes، و.env، والذاكرة، والجلسات، والمهارات، والسجلات، ومهام cron، وحالة gateway، وبيانات Hermes الأخرى.
  • HOME هو منزل نظام التشغيل/المستخدم الذي تتوقعه الأدوات الخارجية. في تثبيتات الجهاز المضيف، يحافظ Hermes عليه كمنزل المستخدم الحقيقي افتراضيًا بحيث تجد أدوات مثل git وssh وgh وaz وnpm وClaude Code وCodex نفس بيانات الاعتماد التي تستخدمها في shell العادي.

المقايضة هي أن profiles الجهاز المضيف تشترك في حالة CLI العادية على مستوى المستخدم افتراضيًا. إذا احتجت هويات CLI منفصلة لكل profile، اضبط terminal.home_mode: profile في config.yaml الخاص بذلك الـ profile. في هذا الوضع يشغّل Hermes العمليات الفرعية للأدوات بـ HOME={HERMES_HOME}/home؛ وستحتاج بعدها إلى تهيئة أو ربط ~/.ssh و~/.gitconfig و~/.config/gh الخاصة بالـ profile، ومصادقة CLI السحابية، ومصادقة Claude/Codex، وحالة npm، وملفات مماثلة داخل منزل ذلك الـ profile.

يعرض Hermes أيضًا HERMES_REAL_HOME للعمليات الفرعية بحيث تستطيع السكربتات إيجاد منزل الحساب الحقيقي عندما يكون home_mode: profile مفعّلًا.

الـ profile الافتراضي هو ببساطة ~/.hermes نفسه. لا حاجة إلى ترحيل — تعمل التثبيتات القائمة بالطريقة نفسها.

مشاركة profile

يمكن نقل profile بنيته على جهاز إلى جهاز آخر — محطة عملك الخاصة، أو حاسوب زميل، أو المجتمع. مساران:

إرسال ملف. يحزم /export الـ profile في ملف .tar.gz واحد — المهارات، والذاكرة، والشخصية، ومهام cron، والإضافات، والإعدادات، و(من سطح المكتب) السمة (theme) والتخطيط الخاصَين بك. تُزال مفاتيح API. يشغّل المستلم /import.

نشر توزيعة (distribution). غلّف الـ profile كـ مستودع git بحيث يثبّته المستلمون بأمر واحد ويسحبون تحديثات مُصدَرة لاحقًا. يحمل SOUL، والإعدادات، والمهارات، ومهام cron، واتصالات MCP؛ أما بيانات الاعتماد والذاكرة والجلسات فتبقى خاصة بكل جهاز.

استخدم ملف تصدير لتسليم لمرة واحدة أو نقل؛ واستخدم توزيعة لوكيل ستستمر في شحن تحديثاته. راجع توزيعات Profile: مشاركة وكيل كامل لكليهما — جدول المقارنة، والتأليف، والنشر، ودلالات التحديث، ونموذج الأمان.

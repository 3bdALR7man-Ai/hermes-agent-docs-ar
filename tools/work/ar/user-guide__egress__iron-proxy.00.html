Egress proxy لحقن بيانات الاعتماد (iron-proxy)

عندما يشغّل Hermes وكيلك داخل sandbox طرفية في Docker، فإن تلك الـ sandbox تحمل عادةً مفاتيح API الحقيقية الخاصة بالخدمات الخارجية (upstream) لديك (OPENROUTER_API_KEY، OPENAI_API_KEY، وغيرها). ويستطيع وكيل تعرّض لحقن prompt (prompt injection) داخل تلك الـ sandbox تنفيذ cat ~/.config/openrouter/auth.json أو printenv | grep -i key وتسريبها.

يحلّ الـ egress proxy هذه المشكلة: فالـ sandbox تحمل proxy tokens معتمة، ولا تحمل المفاتيح الحقيقية أبدًا. تمر كل حركة المرور الصادرة من الـ sandbox عبر daemon محلي لـ iron-proxy (Apache-2.0، مكتوب بـ Go) على الجهاز المضيف، يُنهي اتصال TLS ويستبدل الـ proxy token ببيانات الاعتماد الحقيقية قبل تمرير الطلب إلى الخدمة الخارجية. وإذا اختُرقت الـ sandbox، فلن يخرج المهاجم إلا بـ tokens لا تعمل إلا خلف حدود الـ proxy الموثوقة المُعدّة — ويُعدّ المفتاح الخاص لـ CA وسلامة endpoint الخاص بالـ proxy جزءًا من هذه الحدود. فإذا أمكن إعادة توجيه حركة المرور إلى بنية proxy يتحكم بها المهاجم (مثل مفتاح CA خاص مسروق أو endpoint مُختطف للـ proxy)، فلن يعود ضمان الـ tokens قائمًا.

يربط هذا الإصدار الـ egress proxy بالـ backend الخاص بـ Docker فقط. أما Modal و Daytona و SSH و Singularity فهي لا تتلقى متغيرات بيئة الـ proxy أو تركيب (mount) شهادة CA حتى الآن.

ما هو

  • عملية فرعية مُدارة لـ iron-proxy على الجهاز المضيف، تُثبَّت عند الحاجة في ~/.hermes/bin/iron-proxy
  • CA محلية في ~/.hermes/proxy/ca.crt تثق بها الـ sandbox كي يتمكن iron-proxy من اعتراض TLS (MITM) وإعادة كتابة الترويسات (headers)
  • ملف إعدادات proxy.yaml في ~/.hermes/proxy/proxy.yaml يسرد مضيفي upstream الذين تسمح بهم وربط تحويل الأسرار (secrets transform)
  • ملف mappings.json يسجّل أي proxy token يقابل أي متغير بيئة حقيقي

تحصل الـ sandbox على HTTPS_PROXY=http://host.docker.internal:9090 و HTTP_PROXY=http://host.docker.internal:9091، وعلى متغيرات البيئة القياسية للمزوّدين مثل OPENROUTER_API_KEY مضبوطةً على proxy tokens معتمة. كما تُصدَّر أسماء بديلة مطابقة HERMES_PROXY_TOKEN_<ENV_NAME> لأغراض التشخيص. تقرأ SDKs المزوّدين الحالية أسماء متغيرات البيئة المعتادة، وترسل الـ proxy token في Authorization، ثم يستبدل تحويل secrets في iron-proxy به القيمة الحقيقية المأخوذة من بيئة الـ daemon على الجهاز المضيف.

ما ليس هو

  • ليس هو الأمر hermes proxy الخاص بالاتصالات الواردة، والذي يمثل reverse proxy لتجميع OAuth. فهذا أمر مختلف (hermes egress) واتجاه مختلف.
  • لا يقع بين طرفيتك المحلية والمزوّدين — بل بين الـ sandbox والمزوّدين فقط.
  • لا يعيد كتابة بيانات الاعتماد لاستدعاءات LLM التي تجريها عملية الجهاز المضيف داخليًا، إذ تواصل تلك الاستدعاءات استخدام مفاتيح .env مباشرةً. فنموذج التهديد يخص الـ sandbox، لا الجهاز المضيف.

البدء السريع

يكتشف hermes egress setup مفاتيح المزوّدين من بيئتك. وإذا كانت مفاتيحك موجودة فقط في ~/.hermes/.env (دون تصديرها إلى الـ shell)، فإن الإعداد يقرأ ذلك الملف تلقائيًا — فلا تحتاج إلى تنفيذ export لها أولًا.

عندما تعيد تشغيل setup لاحقًا (مضيف جديد في قائمة السماح، أو tokens مُدوَّرة، أو تغيير مصدر بيانات الاعتماد)، فإنه يوقف الـ daemon العامل لأن إعداداته محفوظة في الذاكرة، ثم يعرض إعادة تشغيله نيابةً عنك كي يسري التغيير فورًا. في tty يسألك أولًا؛ ومرّر --restart لإعادة التشغيل دائمًا أو --no-restart لإبقائه متوقفًا. ولتطبيق التغييرات في أي وقت آخر، يؤدي hermes egress restart الإيقاف ثم التشغيل بأمر واحد.

بمجرد تشغيله، يقوم الـ terminal backend الخاص بـ Docker تلقائيًا بما يلي:

  • تركيب ~/.hermes/proxy/ca.crt داخل الـ sandbox في /etc/ssl/certs/hermes-egress-ca.crt
  • ضبط HTTPS_PROXY، HTTP_PROXY، REQUESTS_CA_BUNDLE، SSL_CERT_FILE، CURL_CA_BUNDLE، NODE_EXTRA_CA_CERTS كي تمر كل بيئات تشغيل HTTP الشائعة عبر الـ proxy وتثق بالـ CA
  • ضبط NODE_OPTIONS=--use-openssl-ca (مُلحقًا بأي قيمة موجودة لديك في docker_env.NODE_OPTIONS) كي يمر Node.js عبر مخزن OpenSSL الذي تتحكم فيه متغيرات حزمة CA الأخرى — راجع تحفّظ عدم تماثل CA في Node.js أدناه لمعرفة الثغرة المتبقية
  • إضافة --add-host=host.docker.internal:host-gateway كي تتمكن الـ sandbox من الوصول إلى الـ proxy على الجهاز المضيف في Linux (يتولى Docker Desktop ذلك تلقائيًا على macOS/Windows)
  • تصدير الـ proxy token تحت اسم متغير البيئة القياسي للمزوّد (مثل OPENROUTER_API_KEY) إضافةً إلى اسم بديل تشخيصي واحد HERMES_PROXY_TOKEN_<ENV_NAME> لكل ربط مُنشأ

الإعدادات

توجد الإعدادات الكاملة في ~/.hermes/config.yaml ضمن قسم proxy:. القيم الافتراضية موثّقة داخل الملف نفسه، وكل الإعدادات اختيارية.

مضيفو upstream المسموح بهم افتراضيًا

إذا احتاج وكيلك إلى upstream غير موجود في القائمة — مثل inference endpoint مستضاف ذاتيًا، أو LLM سحابي إضافي، أو خادم MCP — فأضفه إلى proxy.extra_allowed_hosts. تُطابَق أحرف البدل (wildcards) مع اسم المضيف الكامل (*.example.com يطابق api.example.com و staging.example.com لكنه لا يطابق example.com نفسه).

تُطبَّق بغض النظر عن قائمة السماح. يرفض iron-proxy هذه النطاقات عند حدود الشبكة، لذا لا يستطيع هجوم DNS rebinding عبر اسم مضيف مسموح به الوصول إلى IMDS أو إلى شبكتك الداخلية:

سياسة الربط (Bind)

لا يرتبط الـ proxy أبدًا بـ 0.0.0.0. ويعتمد عنوان الربط الافتراضي على المنصة لأن iron-proxy v0.39 لا يدعم إلا ربطًا واحدًا لكل عملية daemon:

  • Linux: بوابة جسر docker (bridge gateway) (172.17.0.1:<tunnel_port> افتراضيًا). تصل الحاويات إلى الـ proxy عبر host.docker.internal، الذي يحلّه --add-host=host.docker.internal:host-gateway إلى عنوان IP بوابة الجسر هذا تحديدًا — فالربط بـ loopback فقط لن يكون قابلًا للوصول من داخل الـ sandboxes. وعنوان IP الجسر هو عنوان على الواجهة docker0 للجهاز المضيف، لذا فهو غير مكشوف للشبكة المحلية (LAN)؛ لكنه قابل للوصول فعلًا من الحاويات الأخرى على شبكة الجسر الافتراضية، ومع ذلك تظل الطلبات تتطلب proxy token مُنشأً و upstream مسموحًا به. وإذا لم يُكتشف جسر docker (أي أن docker غير مثبّت أو لا يعمل)، يعود الربط إلى loopback مع تحذير.
  • Docker Desktop على macOS / Windows: loopback (127.0.0.1:<tunnel_port>). يوجّه VPNkit في Desktop العنوان host.docker.internal إلى الجهاز المضيف، لذا يكون loopback قابلًا للوصول من الحاويات وهو الخيار الأقل انكشافًا.

لا يستطيع جهاز آخر على الشبكة المحلية يملك proxy token مسرّبًا استخدام الـ proxy — فلا يمكن الوصول إلى أيٍّ من عنواني الربط من الشبكة الخارجية.

نثبّت أيضًا metrics.listen: 127.0.0.1:0 كي يحصل خادم المقاييس (metrics) المدمج في الـ daemon على منفذ loopback مؤقت بدلًا من منفذه الافتراضي :9090 — وإلا فسيتنازع مع tunnel_port: 9090 على المقبس (socket) نفسه وسيرفض الـ daemon البدء مع الرسالة "address already in use". لاحظ أن المنفذ المؤقت :0 عشوائي في كل تشغيل ولا يظهر في أي مكان، لذا تكون المقاييس معطّلة فعليًا مع هذا التثبيت.

حتى لو تمكّن shim خبيث باسم ip يسبق غيره في PATH من حقن عنوان IPv4 غير خاص كعنوان للجسر (0.0.0.0، أو عنوان عام، أو multicast، أو link-local، وما إلى ذلك)، يظل الرجوع إلى loopback ساريًا — فنحن لا نربط أبدًا بأي عنوان لم نتمكن من التحقق منه عبر ipaddress.IPv4Address + فحوص is_*.

لا يمكن استبدال مخططات المصادقة التي تتضمن توقيع الطلبات أو OAuth يُنشئه الـ SDK عبر استبدال ثابت للترويسات — فإذا كانت متغيرات البيئة الخاصة بها موجودة، فستحمل الـ sandbox بيانات اعتماد حقيقية لهؤلاء المزوّدين ويكون ضمان عزل الاتصالات الصادرة ناقصًا بالنسبة إليهم:

التكامل مع Bitwarden

إذا كنت تستخدم Bitwarden Secrets Manager بالفعل عبر hermes secrets bitwarden setup، فيمكن للـ egress proxy سحب بيانات الاعتماد الحقيقية من هناك بدلًا من os.environ:

يضبط هذا proxy.credential_source: bitwarden ويكتشف أسماء متغيرات بيئة المزوّدين من مشروعك في BW.

آلية التدوير

عند ضبط credential_source: bitwarden، يعيد daemon الخاص بـ iron-proxy جلب الأسرار من BWS عبر bws secret list <project_id> في كل مرة يبدأ فيها. لذا يكون مسار التدوير كالتالي:

  1. دوّر المفتاح في تطبيق Bitwarden على الويب.
  2. نفّذ hermes egress stop && hermes egress start على الجهاز المضيف.
  3. تستبدل الـ sandboxes التي تبدأ بعد ذلك الـ proxy tokens بالقيمة الجديدة.

لا حاجة إلى تعديل .env، ولا إلى إعادة تشغيل Hermes على الجهاز المضيف. فـ daemon الخاص بالـ proxy هو الوحيد الذي يتعامل مع القيمة الجديدة — وتبقى عملية الجهاز المضيف و os.environ دون مساس.

الإخفاق الصريح عند البدء

عند ضبط credential_source: bitwarden، يُجري hermes egress start فحصًا مسبقًا في طبقة المعالج، كما يعيد _build_proxy_subprocess_env الفحص في طبقة الـ daemon:

  • متغير بيئة الـ access token الخاص بـ BWS غير مضبوط → يرفض البدء مع تلميح بتنفيذ unset ثم إعادة التشغيل، أو hermes egress setup --no-bitwarden للعودة إلى وضع env
  • secrets.bitwarden.project_id فارغ → يرفض البدء مع تلميح بتشغيل hermes secrets bitwarden setup
  • bws secret list لا يُعيد قيمًا لمزوّد مربوط واحد أو أكثر → يرفض البدء، مع سرد الأسماء المفقودة

هذا السلوك مقصود. فالرجوع إلى بيئة الجهاز المضيف في وضع BW يعيد تمامًا مشكلة القيم القديمة التي صُمّم مسار BW للقضاء عليها (فالمشغّل اختار BW من أجل ضمان التدوير، والرجوع الصامت يكسر هذا الضمان).

يعيد خيار الإعدادات proxy.allow_env_fallback: true تفعيل السلوك القديم "الرجوع الصامت إلى بيئة الجهاز المضيف إذا تعذّر الوصول إلى BWS" لسيناريوهات الترحيل. استخدمه عندما تنقل الأسرار إلى BW واحدًا تلو الآخر وتريد أن يبدأ الـ daemon بأي قيم متاحة.

التسجيل (Logging) في iron-proxy v0.39

في إصدار الملف التنفيذي المثبّت حاليًا (v0.39.0)، يكتب iron-proxy كل المخرجات — تشخيصات مستوى الـ daemon وسجلات كل طلب على حد سواء — إلى ~/.hermes/proxy/iron-proxy.log. لا تحتوي بنية config.Log في v0.39 على حقل audit_path منفصل، لذا لا يمكننا فيه توجيه سجلات كل طلب إلى تدفق مخصص.

ومع ذلك ننشئ مسبقًا ~/.hermes/proxy/audit.log بصلاحيات 0o600 ومع O_NOFOLLOW للأسباب التالية:

  1. يحجز المسار لترقية الإصدار المستقبلية: فعندما ينتقل الإصدار المثبّت إلى إصدار يدعم log.audit_path، ستبدأ سجلات كل طلب بالتدفق إليه دون إعادة إعداد من جهة المشغّل. وحتى ذلك الحين يبقى حجم الملف 0 بايت — فلا توجّه إليه أدوات المراقبة أو التنبيه أو التحليل الجنائي بعد. استخدم iron-proxy.log لكل شيء حاليًا.
  2. يحمي ضمان صلاحيات 0o600 منذ البايت الأول من سيناريو يوم وصول الإصلاح من المشروع الأصلي، حين يُنشئ v0.40+ الملف بقيمة umask الافتراضية إن لم يكن موجودًا مسبقًا.

إلى أن تصل ترقية الإصدار تلك، اعتبر iron-proxy.log مصدر الحقيقة لكلتا الفئتين:

  • أحداث مستوى الـ daemon (رسالة بدء التشغيل، وأخطاء الربط، وسبب الإيقاف، وأخطاء التحويل). للعمليات + استكشاف الأخطاء وإصلاحها.
  • سجلات كل طلب (CONNECT إلى upstream مسموح به، وتنفيذ استبدال سرّ، والرفض بسبب قائمة السماح). للتحليل الجنائي + الامتثال.

يُلحَق بكلا الملفين عبر عمليات إعادة التشغيل. دوّرهما باستخدام logrotate إن كان استهلاك القرص يهمك على الأجهزة المضيفة طويلة العمر.

آلية العمل

  1. تُرسل الـ sandbox طلب HTTPS، مثل POST https://openrouter.ai/v1/chat/completions مع Authorization: Bearer hermes-proxy-openrouter-… (الـ proxy token، وليس المفتاح الحقيقي).
  2. لأن HTTPS_PROXY مضبوط، يذهب الطلب إلى iron-proxy كنفق CONNECT.
  3. يتحقق iron-proxy من قائمة السماح، والمضيف openrouter.ai مسموح به.
  4. يُنشئ iron-proxy شهادة طرفية (leaf cert) موقّعة من الـ CA الخاصة بنا لـ openrouter.ai، ويُنهي اتصال TLS، ويفحص الطلب.
  5. يطابق تحويل secrets سلسلة الـ proxy token في ترويسة Authorization ويستبدل بها القيمة الحقيقية لـ OPENROUTER_API_KEY المأخوذة من بيئة iron-proxy نفسه.
  6. يُعاد تشفير الطلب ويُمرَّر إلى OpenRouter.
  7. يُسجَّل الطلب في ~/.hermes/proxy/iron-proxy.log في v0.39. وعندما يدعم إصدار الملف التنفيذي المثبّت فصل التدفقات (v0.40+)، ستتدفق سجلات كل طلب إلى ~/.hermes/proxy/audit.log وستبقى تشخيصات مستوى الـ daemon في iron-proxy.log. راجع التسجيل في iron-proxy v0.39.

يُرفض أي طلب إلى مضيف غير مسموح به (مثل https://attacker.example.com/leak?key=...) بالرمز HTTP 403 قبل أن يغادر أي بايت الجهاز المضيف. ويُسجَّل الرفض في iron-proxy.log مع مضيف upstream والـ sandbox المصدر.

توزيع CA داخل الـ sandbox

عندما يبدأ الـ backend الخاص بـ Docker حاوية مع proxy.enabled: true وكان الـ daemon في وضع الاستماع، فإنه يضيف الوسائط التالية إلى docker run:

الوسيطالغرض
-v ~/.hermes/proxy/ca.crt:/etc/ssl/certs/hermes-egress-ca.crt:roتركيب الـ CA للقراءة فقط
-e HTTPS_PROXY=http://host.docker.internal:9090Python httpx / curl / الـ transport الافتراضي في Go / Node fetch
-e HTTP_PROXY=http://host.docker.internal:9091curl + wget لطلبات HTTP العادية — إذ يعمل مستمع التمرير (forward listener) الخاص بـ HTTP العادي على tunnel_port + 1
-e NO_PROXY=127.0.0.1,localhost,::1خوادم التطوير على loopback داخل الـ sandbox تتجاوز الـ proxy
-e REQUESTS_CA_BUNDLE=…ca.crtمكتبة Python requests
-e SSL_CERT_FILE=…ca.crtوحدة ssl في Python / OpenSSL — يستبدل مخزن النظام
-e CURL_CA_BUNDLE=…ca.crtcurl — يستبدل مخزن النظام
-e NODE_EXTRA_CA_CERTS=…ca.crtNode.js — يُضيف إلى مخزن النظام
-e NODE_OPTIONS="<your value> --use-openssl-ca"Node.js — المرور عبر مخزن OpenSSL (يُلحَق بالقيمة الحالية؛ ويُحافَظ على --max-old-space-size وغيره من خياراتك)
-e HERMES_EGRESS_PROXY=1علامة يمكن للوكيل قراءتها ليعرف أنه يعمل عبر الـ proxy
-e OPENROUTER_API_KEY=<proxy-token>تتلقى أسماء متغيرات البيئة القياسية للمزوّدين proxy tokens كي تستمر SDKs الحالية في العمل
-e HERMES_PROXY_TOKEN_<NAME>=…اسم بديل تشخيصي لكل ربط؛ بنفس قيمة متغير البيئة القياسي للمزوّد
--add-host=host.docker.internal:host-gatewayلـ Linux فقط؛ إذ يربطه Docker Desktop تلقائيًا

تحفّظ عدم تماثل CA في Node.js

المتغيرات REQUESTS_CA_BUNDLE / SSL_CERT_FILE / CURL_CA_BUNDLE تستبدل مخزن CA الخاص بالنظام داخل الـ sandbox، أما NODE_EXTRA_CA_CERTS فيُضيف إليه. ويمكن نظريًا لعملية Node.js داخل الـ sandbox تجاوز الـ proxy بفتح net.Socket خام وبدء مصافحة TLS خاصة بها — إذ سيظل مخزن CA الخاص بالنظام يثق بشهادات upstream الحقيقية، فينجح الطلب في حين يفشل التحقق في Python / curl.

يُلحَق NODE_OPTIONS=--use-openssl-ca بأي قيمة موجودة لديك في docker_env.NODE_OPTIONS. وهذا يجبر Node على المرور عبر مخزن OpenSSL الذي يتحكم فيه SSL_CERT_FILE، مما يقلّص عدم التماثل. لكنه لا يغطي الكود الذي يمرّر صراحةً خيار ca خاصًا به إلى tls.connect() أو https.request()، وإن كان يسدّ الحالة السهلة.

هذا قيد معروف في v1. تابع github.com/ironsh/iron-proxy/issues لمعرفة الحل من المشروع الأصلي؛ وفي الأثناء، لا تشغّل كود Node غير موثوق يفتح مقابس خام داخل sandbox تعتمد فيها على عزل الاتصالات الصادرة.

تعارضات docker_env

إذا ضبطت متغيرات بيئة تتحكم في الـ proxy داخل كتلة الإعدادات docker_env: (وهذا نادر لكنه ممكن)، يرفض Hermes بدء الـ sandbox عند ضبط enforce_on_docker: true. ويشمل ذلك كلًّا من:

  • متغيرات التحكم في الاتصالات الصادرة: HTTPS_PROXY، HTTP_PROXY، NO_PROXY، REQUESTS_CA_BUNDLE، SSL_CERT_FILE، CURL_CA_BUNDLE، NODE_EXTRA_CA_CERTS
  • متغيرات البيئة الحقيقية للمزوّدين: كل اسم في mappings.json (مثل OPENROUTER_API_KEY، OPENAI_API_KEY)

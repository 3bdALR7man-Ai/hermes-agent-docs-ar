Hermes s6-overlay Container Supervision

متى تُستخدم هذه المهارة

حمّل هذه المهارة عندما تعمل على:

  • إضافة خدمة ثابتة إلى صورة Hermes لـ Docker أو إزالتها (شيء ينبغي الإشراف عليه عند كل بدء تشغيل للحاوية، مثل لوحة التحكم)
  • تشخيص سبب عدم بدء gateway خاص بـ profile معيّن، أو عدم إعادة تشغيله، أو عدم بقائه بعد docker restart
  • فهم سبب كون CMD الخاص بالحاوية هو /opt/hermes/docker/main-wrapper.sh، وكيفية وصول المعطيات التي تبدأ بشرطة إلى برنامج المستخدم
  • تعديل سكربتات الإقلاع cont-init.d (إعادة تعيين UID، تهيئة الأحجام، مطابقة الـ profiles)
  • تغيير سكربت التشغيل المُولَّد لـ gateways الخاصة بكل profile (المرحلة 4)

إذا كنت تشغّل Hermes Agent فقط وتريد استخدام Docker، فراجع website/docs/user-guide/docker.md بدلًا من ذلك.

لماذا البنية B (CMD كبرنامج رئيسي، دون إشراف s6)

الخطة الأصلية (الإصدارات v1–v3) دعت إلى تشغيل hermes الرئيسي كخدمة s6-rc خاضعة للإشراف. لكن آليتين حقيقيتين من s6-overlay v3 منعتا ذلك:

  1. سكربتات cont-init.d لا تتلقى أي معطيات CMD — لذا لا يمكن لخطاف stage2 تحليل docker run <image> chat -q "hi" لضبط HERMES_ARGS كي يستهلكها سكربت run لخدمة ما.
  2. /run/s6/basedir/bin/halt لا يُمرّر كود الخروج المكتوب في /run/s6-linux-init-container-results/exitcode. تخرج الحاويات دائمًا بالكود 143 (SIGTERM) بغض النظر عن ذلك. أكّد ذلك skarnet (مؤلف s6) في المشكلة #477: "if you want a container shutdown, you need to either have your CMD exit, or, if you have no CMD, write the container exit code you want then call halt".

لذا نستخدم نمط CMD الأصلي في s6-overlay عبر الموزّع: ENTRYPOINT ["/opt/hermes/docker/entrypoint-dispatch.sh"]، والذي ينفّذ تحت PID 1 الأمر /init /opt/hermes/docker/main-wrapper.sh "$@". يُضاف الغلاف (wrapper) تلقائيًا قبل معطيات المستخدم — فيصبح docker run <image> --version هو /init main-wrapper.sh --version، ولا يعترض shell POSIX الخاص بـ /init الخيار --version. ينزل الغلاف إلى مستخدم hermes عبر s6-setuidgid، ثم ينفّذ البرنامج المختار. يصبح كود خروج البرنامج هو كود خروج الحاوية، بما يطابق تمامًا عقد tini قبل s6. عندما لا يكون entrypoint هو PID 1 (Fly Machines، docker run --init)، يتجاوز الموزّع /init بالكامل (لأنه سيتوقف مع رسالة can only run as pid 1)، ويستعيد PATH الخاص بأدوات s6 المساعدة، وينفّذ stage2-hook.sh، ثم ينفّذ main-wrapper.sh مباشرة — بلا خدمات خاضعة للإشراف على هذا المسار (#38349).

المقايضة: hermes الرئيسي بلا إشراف تحت s6. وهذا يطابق تمامًا سلوكه تحت tini (الصورة السابقة لـ s6). الإشراف على لوحة التحكم هو الضمان الجديد الوحيد — وتحصل gateways الخاصة بكل profile تحت /run/service/ على إشراف كامل.

مراقبة سجل مطابِق cont-init

إضافة خدمة ثابتة جديدة

  1. أنشئ docker/s6-rc.d/<name>/type بمحتوى longrun\n وdocker/s6-rc.d/<name>/run (استخدم #!/command/with-contenv sh + # shellcheck shell=sh).
  2. انزل إلى مستخدم hermes عبر s6-setuidgid hermes في أعلى سكربت run (ما لم تحتج تحديدًا إلى root).
  3. أنشئ ملفًا فارغًا docker/s6-rc.d/<name>/dependencies.d/base حتى تنتظر الخدمة الحزمة الأساسية.
  4. أنشئ ملفًا فارغًا docker/s6-rc.d/user/contents.d/<name> حتى تنضم إلى حزمة المستخدم.
  5. يلتقطها أمر COPY docker/s6-rc.d/ في Dockerfile تلقائيًا — لا حاجة إلى أي تغييرات أخرى.

تغيير أمر تشغيل gateway الخاص بكل profile

عدّل S6ServiceManager._render_run_script في hermes_cli/service_manager.py. تُستدعى هذه الدالة أيضًا من hermes_cli/container_boot.py::_register_service أثناء مطابقة الإقلاع، فهي المصدر الوحيد للحقيقة. حدّث التأكيد (assertion) المقابل في tests/hermes_cli/test_service_manager.py::test_s6_register_creates_service_dir_and_triggers_scan.

تشغيل إطار اختبار Docker

يوجد إطار الاختبار في tests/docker/ ويُتخطّى عندما لا يتوفر Docker. رُفعت مهلة كل اختبار إلى 180 ثانية (راجع tests/docker/conftest.py).

المزالق الشائعة

"command not found" عبر docker exec

/command/ (حيث يضع s6-overlay ملفاته التنفيذية) موجود في PATH فقط للعمليات التي تنشأ من شجرة الإشراف — الخدمات، وcont-init.d، وmain-wrapper.sh. سيفشل docker exec <c> s6-svstat … برسالة "command not found"؛ استخدم دائمًا المسار المطلق /command/s6-svstat. أما الملف التنفيذي hermes فيعمل لأن Dockerfile يضيف /opt/hermes/.venv/bin إلى ENV PATH وقت التشغيل.

ملكية مجلد الـ profile

يعمل مطابِق cont-init بصفته hermes (s6-setuidgid hermes في 02-reconcile-profiles). فإذا انتهى مجلد profile مملوكًا لـ root (مثلًا لأن docker exec <c> hermes profile create … عمل افتراضيًا بصفته root)، لا يستطيع المطابِق قراءة SOUL.md ويفشل بخطأ PermissionError. الحل: يُصلح stage2-hook.sh ملكية $HERMES_HOME/profiles إلى hermes في كل إقلاع، بشكل idempotent. لا تُزل هذا الجزء.

الملفات المكتوبة عبر docker exec مملوكة لـ root

يفترض docker exec افتراضيًا صلاحيات root. إما مرّر --user hermes أو اعتمد على تصحيح الملكية في stage2 عند إعادة التشغيل التالية. لا تكتب ملفات تحت $HERMES_HOME/profiles/<name>/ بصفتك root يدويًا — فرغم أن دورة المطابقة التالية ستصحّحها، قد تصطدم العمليات الجارية بأخطاء أذونات.

فتحة الخدمة موجودة لكن s6-svstat يقول "s6-supervise not running"

مجلد الخدمة موجود على tmpfs وقد مُحي عند إعادة تشغيل الحاوية. إما أن مطابِق cont-init لم يعمل بعد (امنحه لحظة بعد docker restart) أو أنه فشل. تحقّق من docker logs <c> | grep '02-reconcile'.

الـ gateway يبدأ ثم يخرج فورًا (down (exitcode 1) في svstat)

على الأرجح لا يملك الـ profile نموذجًا أو مصادقة مضبوطة. فتحة الخدمة صحيحة — الـ gateway نفسه غير معدّ. شغّل hermes -p <profile> setup أولًا. سيستمر المُشرِف s6 في إعادة تشغيله؛ وهذا هو السلوك المطلوب (عند إصلاح الإعدادات، تنجح المحاولة التالية ويبقى قيد التشغيل).

المطابِق تجاوز أحد الـ profiles

يعتمد المطابِق على وجود SOUL.md كعلامة على "profile حقيقي". يزرعه hermes profile create دائمًا. فإذا كان مجلد الـ profile يفتقد SOUL.md (مجلد شارد، استعادة جزئية، نسخ احتياطي جارٍ)، يتجاوزه المطابِق عمدًا. أضِف SOUL.md (حتى لو كان فارغًا) لإعادة تفعيله.

"النجدة، الحاوية تخرج بالكود 143!"

تحقّق مما إذا كان شيء ما يستدعي s6-svscanctl -t أو /run/s6/basedir/bin/halt — فكلاهما يجعل /init يبدأ المرحلة 3 من الإيقاف لكنه يعيد 143 (SIGTERM) بدلًا من كود الخروج المطلوب. كان هذا هو التحوّل في البنية من A إلى B في المرحلة 2. لإيقاف الحاوية بكود خروج حقيقي، يجب أن تدع CMD (main-wrapper.sh) يخرج بصورة طبيعية؛ لا تحاول التحكم بالخروج من سكربت finish.

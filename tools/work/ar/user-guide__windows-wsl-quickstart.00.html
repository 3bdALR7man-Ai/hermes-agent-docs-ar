دليل Windows (WSL2)

يدعم Hermes Agent الآن كلًا من Windows الأصلي و WSL2. تتناول هذه الصفحة مسار WSL2؛ أما للتثبيت الأصلي عبر PowerShell فراجع دليل Windows (التشغيل الأصلي) المخصص لذلك.

متى تختار WSL2 بدلًا من التثبيت الأصلي:

  • عندما تريد استخدام الطرفية المضمّنة في لوحة التحكم (تبويب /chat) — فهذه اللوحة تتطلب POSIX PTY وهي متاحة في WSL2 فقط.
  • عندما تعمل على تطوير يعتمد بكثافة على POSIX وتريد أن تتشارك جلسات Hermes نظام الملفات والمسارات نفسها مع أدوات التطوير لديك.
  • عندما تكون لديك بيئة WSL2 بالفعل ولا تريد صيانة تثبيت ثانٍ.

متى يكون التثبيت الأصلي كافيًا (أو أفضل):

  • المحادثة التفاعلية، والـ gateway (Telegram/Discord/إلخ)، ومُجدول cron، وأداة المتصفح، وخوادم MCP، ومعظم ميزات Hermes تعمل جميعها أصليًا على Windows.
  • عندما لا تريد التفكير في عبور الحد الفاصل WSL↔Windows في كل مرة تشير فيها إلى ملف أو تفتح URL.

في WSL2 هناك فعليًا جهازا كمبيوتر في الصورة: مضيف Windows لديك، وآلة Linux افتراضية (VM) يديرها WSL. ينشأ معظم الالتباس من عدم التأكد من أيهما تعمل عليه في لحظة ما.

يغطي هذا الدليل جوانب هذا الانقسام التي تؤثر في Hermes تحديدًا: تثبيت WSL2، ونقل الملفات ذهابًا وإيابًا بين Windows و Linux، والشبكات في كلا الاتجاهين، والمآزق التي يقع فيها المستخدمون فعلًا.

لماذا WSL2 (مقارنةً بـ Windows الأصلي)

يعمل التثبيت الأصلي على Windows مباشرةً: طرفية Windows لديك (PowerShell، أو Windows Terminal، وما إلى ذلك)، ومسارات نظام ملفات Windows (C:\Users\…)، وعمليات Windows. يستخدم Hermes برنامج Git Bash لتنفيذ أوامر الـ shell، وهي الطريقة التي يتعامل بها Claude Code ووكلاء آخرون مع Windows اليوم — إذ تتفادى الفجوة بين POSIX و Windows دون إعادة كتابة كاملة.

يشغّل WSL2 نواة Linux حقيقية داخل آلة افتراضية خفيفة، لذا فإن تشغيل Hermes داخلها مطابق فعليًا لتشغيله على Ubuntu. وهذا مفيد عندما تريد بيئة POSIX حقيقية: fork، و /tmp، و UNIX sockets، ودلالات الإشارات (signals)، والطرفيات المدعومة بـ PTY، وأنواع shell مثل bash/zsh، وأدوات مثل rg و git و ffmpeg تتصرف كما تتصرف على Linux.

العواقب العملية لاستخدام WSL2:

  • يعيش كل من Hermes CLI، والـ gateway، والجلسات، والذاكرة، والمهارات، وبيئات تشغيل الأدوات داخل آلة Linux الافتراضية.
  • أما برامج Windows (المتصفحات، والتطبيقات الأصلية، و Chrome مع profile الذي سجّلت الدخول به) فتعيش خارجها.
  • في كل مرة تريد فيها أن يتواصل الطرفان — مشاركة الملفات، أو فتح عناوين URL، أو التحكم في Chrome، أو الوصول إلى خادم نماذج محلي، أو إتاحة Hermes gateway لهاتفك — فإنك تعبر حدًا فاصلًا. وهذه الحدود الفاصلة هي موضوع هذا الدليل.

نظام الملفات: عبور الحد الفاصل Windows ↔ WSL2

هذا هو الجزء الذي يتعثر فيه أكبر عدد من الناس. هناك نظاما ملفات، ومكان وضع ملفاتك مهم — من حيث الأداء، والصحة، وما تستطيع الأدوات رؤيته.

الاتجاهان

الاتجاهالمسار الأصليالمسار الذي تستخدمه
قرص Windows، كما يُرى من WSLC:\Users\you\Documents/mnt/c/Users/you/Documents
قرص WSL، كما يُرى من Windows/home/you/code\\wsl$\Ubuntu\home\you\code (أو \\wsl.localhost\Ubuntu\... في الإصدارات الأحدث)

كلاهما حقيقي، وكلاهما يعمل، لكنهما ليسا نظام الملفات نفسه — إذ يربط بينهما في الخلفية بروتوكول الشبكة 9P. ولذلك عواقب حقيقية على الأداء والسلوك.

أين تضع Hermes ومشاريعك

القاعدة العامة: أبقِ كل ما هو ذو طابع Linux داخل نظام ملفات Linux.

  • تثبيت Hermes الخاص بك (~/.hermes/) — على جانب Linux. يفعل المُثبّت ذلك بالفعل.
  • مستودعات git التي تعمل عليها من WSL — على جانب Linux (~/code/...، ~/projects/...).
  • النماذج، ومجموعات البيانات، والبيئات الافتراضية (venvs) — على جانب Linux.

ما تحصل عليه باتباع هذه القاعدة:

  • إدخال/إخراج سريع. تمر العمليات على /mnt/c/... عبر 9P وهي أبطأ بمقدار 10 إلى 100 مرة من ext4 الأصلي. قد يستغرق git status على مستودع يضم 10 آلاف ملف، والذي يبدو فوريًا ضمن ~/code، أكثر من 15 ثانية ضمن /mnt/c.
  • صلاحيات صحيحة. بتات صلاحيات Linux على /mnt/c مجرد محاكاة بأفضل جهد. ومن الشائع أن يرفض ssh مفتاحًا بسبب "bad permissions" أو أن يفشل chmod +x بصمت.
  • مراقبة ملفات موثوقة. inotify عبر 9P غير مستقر — إذ تفوّت أدوات مراقبة الملفات (خوادم التطوير، ومشغّلات الاختبارات) التغييرات على /mnt/c بشكل متكرر.
  • لا مفاجآت في حساسية حالة الأحرف. مسارات Windows غير حساسة لحالة الأحرف افتراضيًا؛ بينما Linux حساس لها. فالمشاريع التي تحتوي على Readme.md و README.md معًا تتصرف بشكل مختلف بحسب الجانب الذي تعمل عليه.

لا تضع الأشياء على /mnt/c إلا عندما تحتاج إلى أن يكون الملف على جانب Windows — مثلًا عندما تريد فتحه من تطبيق رسومي على Windows، أو عندما يحتاج DevTools MCP الخاص بـ Chrome على Windows إلى أن يكون المجلد الحالي مسارًا يمكن لـ Windows الوصول إليه.

الشبكات: WSL ↔ Windows

يعمل WSL2 داخل آلة افتراضية خفيفة لها مكدس شبكة خاص بها. هذا يعني أن localhost داخل WSL ليس هو نفسه localhost على Windows — فهما مضيفان منفصلان من وجهة نظر الشبكة. عليك أن تحدد، لكل خدمة، اتجاه تدفق حركة المرور وأن تختار الجسر المناسب.

هناك حالتان تتكرران باستمرار.

الحالة 1 — Hermes داخل WSL يتصل بخدمة على Windows

الحالة الأكثر شيوعًا: أنت تشغّل Ollama أو LM Studio أو llama-server على Windows، ويحتاج Hermes (داخل WSL) إلى الوصول إليه.

يوجد الشرح المرجعي لهذا في دليل المزوّدين: شبكات WSL2 للنماذج المحلية →

باختصار:

  • Windows 11 22H2 أو أحدث: فعّل وضع الشبكات المنعكسة (mirrored) (networkingMode=mirrored في %USERPROFILE%\.wslconfig، ثم wsl --shutdown). بعدها يعمل localhost في كلا الاتجاهين.
  • Windows 10 أو الإصدارات الأقدم: استخدم عنوان IP لمضيف Windows (البوابة الافتراضية لشبكة WSL الافتراضية)، وتأكد من أن الخادم على Windows مرتبط بـ 0.0.0.0، وليس فقط بـ 127.0.0.1. وعادةً ما يحتاج Windows Firewall أيضًا إلى قاعدة للمنفذ.

للاطلاع على الجدول الكامل (عناوين الربط لـ Ollama / LM Studio / vLLM / SGLang، وأوامر قواعد الجدار الناري ذات السطر الواحد، وأدوات مساعدة لعناوين IP الديناميكية، وحل التفافي لجدار Hyper-V الناري)، اتبع الرابط أعلاه — ولا تكرره.

الحالة 2 — شيء ما على Windows (أو على شبكتك المحلية LAN) يتصل بـ Hermes داخل WSL

هذا هو الاتجاه المعاكس، وهو أقل توثيقًا في أماكن أخرى، لكنه ما تحتاج إليه من أجل:

  • استخدام لوحة تحكم Hermes على الويب من متصفح على Windows.
  • استخدام خادم API المتوافق مع OpenAI (الذي يتيحه hermes gateway عندما تكون API_SERVER_ENABLED=true) من أداة على جانب Windows. راجع صفحة ميزة خادم API.
  • اختبار messaging gateway (Telegram، و Discord، وما إلى ذلك) حيث تستدعي المنصة URL لـ webhook محلي — وعادةً ما تستخدم cloudflared/ngrok بدلًا من إعادة توجيه المنافذ المباشرة.

الحالة الفرعية 2a: من مضيف Windows نفسه

على Windows 11 22H2 أو أحدث مع تفعيل الوضع المنعكس (mirrored)، لا شيء عليك فعله. فالعملية داخل WSL المرتبطة بـ 0.0.0.0:8080 (أو حتى 127.0.0.1:8080) يمكن الوصول إليها من متصفح على Windows عبر http://localhost:8080. إذ ينشر WSL الربط إلى المضيف تلقائيًا.

في وضع NAT (Windows 10 / إصدارات Windows 11 الأقدم)، تعيد ميزة "localhost forwarding" الافتراضية في WSL2 عمومًا توجيه عمليات الربط على 127.0.0.1 في جانب Linux إلى localhost في Windows، لذا يمكن عادةً الوصول إلى خدمة Hermes التي بدأت باستخدام --host 127.0.0.1 عبر http://localhost:PORT من Windows. إذا لم يكن ذلك ممكنًا:

  • اربط صراحةً بـ 0.0.0.0 داخل WSL.
  • اعثر على عنوان IP للآلة الافتراضية لـ WSL باستخدام ip -4 addr show eth0 | grep inet واتصل به من Windows.

الحالة الفرعية 2b: من جهاز آخر على شبكتك المحلية (هاتف، أو جهاز لوحي، أو كمبيوتر آخر)

هنا تكمن الصعوبة الحقيقية. تتدفق حركة المرور على النحو جهاز LAN → مضيف Windows → WSL VM، وعليك إعداد كلتا القفزتين:

  1. اربط على جميع الواجهات داخل WSL. لا يمكن أبدًا الوصول من خارج الآلة الافتراضية إلى عملية تستمع على 127.0.0.1. استخدم 0.0.0.0.

  2. أعد توجيه المنفذ من Windows → WSL VM. في الوضع المنعكس يحدث هذا تلقائيًا. أما في وضع NAT فعليك فعله بنفسك، لكل منفذ، من PowerShell بصلاحيات المسؤول:

    أزل القاعدة لاحقًا باستخدام netsh interface portproxy delete v4tov4 listenaddress=0.0.0.0 listenport=8080.

  3. وجّه جهاز LAN إلى http://<windows-lan-ip>:8080.

بما أن عنوان IP للآلة الافتراضية لـ WSL يتغير مع كل إعادة تشغيل في وضع NAT، فإن القاعدة التي تُضبط مرة واحدة لا تصمد إلا حتى تنفيذ wsl --shutdown التالي. ولأي إعداد دائم، إما أن تستخدم الوضع المنعكس أو تضع خطوة port-proxy في سكربت يعمل عند تسجيل الدخول إلى Windows.

بالنسبة إلى webhooks القادمة من مزوّدي المراسلة السحابيين (setWebhook في Telegram، وأحداث Slack، وما إلى ذلك)، لا تصارع إعادة توجيه المنافذ — استخدم أنفاق cloudflared. راجع دليل webhooks.

جعل WSL نفسه يبدأ عند تسجيل الدخول إلى Windows

لا تبقى الآلة الافتراضية لـ WSL قيد التشغيل إلا ما دام هناك شيء يستخدمها. لإبقاء الـ gateway قابلًا للوصول دون نافذة طرفية مفتوحة، شغّل عملية WSL عند تسجيل الدخول إلى Windows عبر Task Scheduler:

  • المشغّل (Trigger): At log on (لمستخدمك).
  • الإجراء (Action): Start a program
    • البرنامج (Program): C:\Windows\System32\wsl.exe
    • الوسائط (Arguments): -d Ubuntu --exec /bin/sh -c "sleep infinity"

يُبقي ذلك الآلة الافتراضية حية كي يظل الـ gateway الذي يديره systemd قيد التشغيل. على Windows 11، تعمل أيضًا الطرق الأحدث مثل wsl --install --no-launch + التشغيل التلقائي؛ أما حيلة sleep infinity فهي النسخة القابلة للنقل.

تمرير GPU (النماذج المحلية)

يدعم WSL2 وحدات GPU من NVIDIA أصليًا منذ نواة WSL 5.10.43 وما بعدها — ثبّت برنامج تشغيل NVIDIA القياسي على Windows (لا تثبّت برنامج تشغيل NVIDIA لـ Linux داخل WSL)، وسيرى nvidia-smi داخل WSL وحدة GPU. ومن هناك، تُبنى أدوات CUDA و torch و vllm و sglang و llama-server على وحدة GPU الحقيقية كالمعتاد.

لا يزال دعم AMD ROCm و Intel Arc داخل WSL2 قيد التطور، وهو خارج مصفوفة اختبارات Hermes — قد يعمل مع برامج التشغيل الحالية، لكن ليست لدينا وصفة نوصي بها.

إذا كنت تشغّل خادم نماذج محليًا أصليًا على Windows (Ollama لـ Windows، أو LM Studio) يستخدم GPU لديك بالفعل عبر برامج تشغيل Windows، فلا حاجة إطلاقًا إلى تمرير GPU في WSL — فقط اتبع الحالة 1 أعلاه واتصل به عبر الشبكة من WSL.

مآزق شائعة

"Connection refused" عند الاتصال بـ Ollama / LM Studio المستضاف على Windows. راجع شبكات WSL2. في تسعين بالمئة من الحالات يكون الخادم مرتبطًا بـ 127.0.0.1 ويحتاج إلى 0.0.0.0 (في Ollama: OLLAMA_HOST=0.0.0.0)، أو تكون قاعدة الجدار الناري مفقودة.

بطء شديد في git status / hermes chat داخل مستودع. على الأرجح أنك تعمل ضمن /mnt/c/.... انقل المستودع إلى ~/code/... (جانب Linux). وستحصل على سرعة أكبر بعدة مراتب.

ظهور bad interpreter: /bin/bash^M في السكربتات. نهايات أسطر CRLF من محرر على Windows. نفّذ dos2unix script.sh، واضبط core.autocrlf input في إعدادات git داخل WSL.

تحذير "UNC paths are not supported" من ملفات Windows التنفيذية التي تُشغَّل عبر MCP. مجلد العمل الحالي (cwd) لـ Hermes موجود داخل نظام ملفات Linux، ولا يعرف cmd.exe في Windows كيف يتعامل معه. شغّل Hermes من /mnt/c/... في تلك الجلسة، أو استخدم wrapper ينفّذ cd إلى مسار يمكن لـ Windows الوصول إليه قبل استدعاء الملف التنفيذي لـ Windows.

انحراف الساعة بعد السكون/الإسبات. قد تتأخر ساعة WSL2 عدة دقائق بعد استئناف المضيف من السكون، ما يُعطّل أي شيء يعتمد على الشهادات (OAuth، وواجهات HTTPS APIs). أصلحها عند الحاجة:

أو ثبّت ntpdate وشغّله عند تسجيل الدخول.

توقف DNS عن العمل بعد تفعيل الوضع المنعكس، أو عند الاتصال بشبكة VPN. ينقل الوضع المنعكس إعدادات شبكة المضيف إلى WSL — فإذا كان DNS في Windows يتصرف بغرابة (split-tunnel في VPN، أو محلّل أسماء خاص بالشركة)، فسيرث WSL ذلك. الحل الالتفافي: تجاوز resolv.conf يدويًا (اضبط generateResolvConf=false في /etc/wsl.conf، ثم اكتب ملف /etc/resolv.conf خاصًا بك يحتوي على 1.1.1.1 أو DNS الخاص بشبكة VPN لديك).

عدم العثور على hermes بعد تشغيل المُثبّت. يضيف المُثبّت ~/.local/bin إلى PATH الخاص بالـ shell عبر ~/.bashrc. تحتاج إلى تنفيذ source ~/.bashrc (أو فتح طرفية جديدة) كي يسري التغيير في الجلسة الحالية.

بطء Windows Defender مع ملفات WSL. يفحص Defender الملفات عبر جسر 9P عند الوصول إليها من Windows، ما يضاعف بطء الوصول عبر الحدود على غرار /mnt/c. إذا كنت لا تتعامل مع ملفات WSL إلا من داخل WSL، فلا أهمية لذلك. أما إذا كنت تستخدم أدوات Windows على \\wsl$\... بشكل متكرر، ففكّر في استثناء مسار توزيعة WSL من الفحص الفوري.

نفاد مساحة القرص. يخزّن WSL2 قرص آلته الافتراضية كملف VHDX متناثر (sparse) ضمن %LOCALAPPDATA%\Packages\.... يكبر هذا الملف لكنه لا يتقلص تلقائيًا عند حذف الملفات. لاستعادة المساحة: نفّذ wsl --shutdown، ثم من PowerShell بصلاحيات المسؤول نفّذ Optimize-VHD -Path <path-to-ext4.vhdx> -Mode Full (يتطلب أدوات Hyper-V) — أو اتبع مسار diskpart الأبسط الموثّق في وثائق WSL.

إلى أين بعد ذلك

  • التكاملات → المزوّدون → شبكات WSL2 — الشرح المرجعي المفصّل للشبكات الخاص بخوادم النماذج المحلية.
  • دليل MCP → WSL → Chrome على Windows — التحكم في Chrome على Windows الذي سجّلت الدخول فيه من Hermes داخل WSL.
  • Tool Gateway و لوحة التحكم على الويب — الخدمات طويلة الأمد التي ستحتاج في الغالب إلى إتاحتها من WSL لبقية شبكتك.

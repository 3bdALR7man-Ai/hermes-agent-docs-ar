النقاط الحرجة والدروس المستفادة

  1. لا تفترض أن "headless" تعني استحالة OAuth. يعمل التدفق المدمج بشكل جيد مع CLI المحلي؛ والمشكلة تقتصر على عمليات النشر البعيدة حيث يكون متصفح المستخدم وعملية Hermes على جهازين مختلفين. تحقق من بيئة التشغيل قبل أن تجزم بأن OAuth غير متاح.

  2. اقرأ المصدر، لا وثائق المهارة فقط. tools/mcp_oauth.py ومرجع إعدادات MCP في website/docs/ هما المرجعان الموثوقان. ابحث في شجرة الكود (grep) قبل أن تخبر المستخدم أن ميزة ما "غير موجودة".

  3. فلتر وكيل المستخدم في Cloudflare. يضع كثير من مزوّدي MCP/OAuth بنيتهم التحتية خلف Cloudflare، الذي يرفض بـ 403 وكلاء مستخدم من نوع python-urllib/* على نقاط البيانات الوصفية رغم أنها عامة. اضبط User-Agent: python-httpx/0.27 (أو أي سلسلة تشبه المتصفح) في كل طلب ضمن هذا التدفق. يستخدم Hermes نفسه httpx، لذا لا تظهر هذه المشكلة أبدًا في مسار الاتصال الفعلي.

  4. أدرج resource في كل من طلب التفويض وطلب الرمز. مؤشرات الموارد في RFC 8707 ليست اختيارية بالنسبة لمعظم خوادم MCP الحديثة — فهي تربط الرمز الصادر بمورد MCP المحدد. قد يعمل حذفها أحيانًا رغم ذلك، لكنه قد يُنتج رمزًا يفشل لاحقًا عند خادم MCP بخطأ في النطاق (scope) أو الجمهور (audience).

  5. الشرطة المائلة الختامية مهمة. تُعلن بعض الخوادم عن المورد بصيغة https://mcp.example.com/ بشرطة مائلة ختامية وترفض الرموز الصادرة مقابل النسخة بلا شرطة. انسخ قيمة resource حرفيًا من استجابة .well-known/oauth-protected-resource.

  6. /reload-mcp صامت عند الفشل. إذا أظهرت إعادة التحميل "No MCP tools available" دون سطر change_detail، فهذا يعني أن خادمًا موجودًا في الإعدادات فشل في الاتصال ولم يظهر أي خطأ. تتبّع سجل الأخطاء، واختبر الرمز مباشرةً بطلب initialize يدوي، واطلب — إن بدا كل شيء سليمًا — إعادة تشغيل كاملة للعملية.

  7. يمكن لقاطع الدارة (circuit breaker) أن يبقى صامدًا بعد /reload-mcp. يحتفظ tools/mcp_tool.py بقاموس عدّاد أخطاء على مستوى الوحدة (module-level) بحد أدنى صغير. وبمجرد تفعيله (مثلًا بعد أن ينتج انتهاء صلاحية الرمز عدة إخفاقات متتالية)، يمكن لمعالج الأداة أن يقطع الدارة قبل استدعاء الخادم، فلا يعيد أي استدعاء ناجح ضبط العدّاد. العرَض: تقول إعادة التحميل "Reconnected: X" لكن الاستدعاءات اللاحقة ما زالت تفشل بخطأ "server unreachable" في المحادثة نفسها. ترتيب الاسترداد: جرّب /reload-mcp أولًا (رخيص، لا يسبب أي اضطراب في عملية الدردشة) — فهو قادر في الإصدارات الحالية على مسح العدّاد؛ لا تصعّد إلى إعادة تشغيل كاملة لعملية gateway إلا إذا ظل استدعاء حي يقطع الدارة بعد إعادة التحميل. لا تبدأ بالقول "يجب أن تعيد التشغيل".

  8. تحديث رمز access_token منتهي الصلاحية مع قاطع دارة مفعّل يمثّل جمودًا (deadlock). يعمل منطق التحديث التلقائي (auto-refresh) ضمن مسار استدعاء MCP نفسه، وهو ما يقطعه قاطع الدارة بعد تفعيله. لا يفيد تحديث الرمز يدويًا على القرص بمفرده — اقرن أي تحديث يدوي للرمز بإعادة تشغيل كاملة، لا بـ /reload-mcp.

  9. ظهور invalid_grant عند تحديث يدوي يعني أن رمز التحديث ميت — وإعادة المصادقة هي الحل الوحيد، فلا تكرر المحاولة. عندما تنتهي صلاحية access_token لفترة طويلة كفاية، قد يُلغى refresh_token أيضًا من جهة الخادم. عندئذ يُعيد طلب POST بـ grant_type=refresh_token استجابة HTTP 400 بصيغة {"error":"invalid_grant",...} (تختلف الصياغة: "Grant not found"، "Token expired"، "refresh token is invalid"). لا يوجد أي تعافٍ من جهة gateway. أعد الأمر إلى المستخدم بخيارين: (أ) إعادة تنفيذ خطوات OAuth اليدوية كاملة (الخطوات 3–10)، أو (ب) إن كان المزوّد يوفّر مفتاح API شخصيًا ثابتًا، التحوّل إليه — بلا دورة تحديث/انتهاء صلاحية، وأكثر ثباتًا لـ gateway بعيد غير مراقَب. اكتشف المشكلة مبكرًا: قبل أي عملية إنشاء/تحديث ضد MCP يعمل بـ OAuth، تحقق من expires_at مقابل time.time()؛ فإن كانت الصلاحية منتهية بالفعل، حاول التحديث أولًا وأظهر invalid_grant فورًا بدل أن تفشل في منتصف المهمة.

  10. نجاح التحديث مع استمرار رفض الرمز = إلغاء الجلسة من جهة الخادم؛ ولا يُصلحه إلا تدفق authorization_code جديد. يختلف هذا عن النقطة 9. قد يبدو ملف الرمز المخزّن سليمًا (expires_at بعيد، و refresh_token موجود)، لكن طلب initialize حيًا يُعيد 401 invalid_token بجسم JSON-RPC مثل {"error":{"code":-32002,"message":"Session expired. Please re-authenticate."}}. وطلب POST بـ grant_type=refresh_token قد ينجح (HTTP 200، رمز وصول جديد) — لكن الرمز الجديد تمامًا يحصل على نفس الخطأ -32002. لقد ألغى المزوّد جلسة MCP الأساسية من جهته؛ وتُعيد سلسلة تحديث OAuth سك بيانات اعتماد جديدة لكنها لا تستطيع إعادة إنشاء جلسة مُلغاة. قاعدة القرار عندما يبلّغ MCP يعمل بـ OAuth بأنه "غير متصل": (1) اختبر access_token المخزّن بطلب initialize يدوي؛ (2) إن ظهر 401 invalid_token، حاول التحديث واختبر الرمز الجديد؛ (3أ) إذا نجح الرمز الجديد → اكتبه وأعد التشغيل لمسح قاطع الدارة؛ (3ب) إذا استمر ظهور -32002/"Session expired" على الرمز الجديد → توقّف، فهذا إلغاء جلسة، وسلّم المستخدم رابط التفويض لإعادة مصادقة كاملة. يُشغّل scripts/diagnose-oauth-mcp.py الخطوتين 1–2 تلقائيًا ويطبع الفرع الذي أنت فيه. لـ gateway غير مراقَب تتكرر فيه إلغاءات الجلسة، فضّل مفتاح API شخصيًا ثابتًا. راجع references/stripe-mcp-oauth-revocation.md لمثال عملي على مزوّد يُلغي الجلسة أسبوعيًا.

  11. ملف معلومات العميل ليس اختياريًا. يحتاج Hermes إلى <server>.client.json لمعرفة client_id اللازم لعمليات منح التحديث (refresh). تخطّي كتابته يعني فشل أول تحديث واضطرار المستخدم لإعادة المصادقة — وكتابة كلا الملفين هي بيت القصيد من هذه المهارة.

  12. لا تكتب رابط إعادة التوجيه يدويًا ليفتحه المستخدم. ولّد رابط التفويض برمجيًا باستخدام urllib.parse.urlencode(). المسافات في الصلاحيات (scopes) والأحرف الخاصة في state تُفسد الروابط المُركّبة بدمج نصي (string-concatenated).

  13. أمان: ملف التخزين المؤقت (stash) يحتوي على code_verifier. احذف /tmp/.mcp-oauth-work/<server>.json فورًا بعد نجاح تبادل الرمز. لا داعي للاحتفاظ بسرّ إثبات هوية بعد استهلاكه.

  14. اكتب ما أعادته نقطة نهاية الرمز فعليًا. قد يمنح خادم التفويض نطاقًا (scope) أضيق (أو أوسع) مما طُلب. اكتب scope من استجابة تبادل الرمز إلى <server>.json، لا ما طلبته في الخطوة 5. عندما تكون scopes_supported: []، فإن قائمة الصلاحيات الصريحة التي ترسلها هي المرجع الموثوق في الاتجاهين: بعض الخوادم تمنح بالضبط ما تسرده (أرسل صلاحيات ضيّقة لأقل امتياز، أو عدّد المجموعة الكاملة إذا احتاج المستخدم كل شيء)، وبعضها لا يُعيد الصلاحية الممنوحة وقت التسجيل — واستجابة تبادل الرمز وحدها هي الموثوقة.

  15. غالبًا ما تعمل رموز OAuth أيضًا كرموز Bearer ضد واجهة REST العامة للمزوّد. غالبًا ما لا يكون access_token في <server>.json "خاصًا بـ MCP فقط" — فينجح Authorization: Bearer <token> ضد واجهة REST الموثّقة للمزوّد كلما مُنح نطاق المورد المقابل. هذا جزء من مواصفة OAuth 2.0 نفسها، لا خاصية من خصائص مزوّد بعينه. عندما يكون خادم MCP للقراءة فقط لكنك تحتاج عملية كتابة، تحقق مما إذا كان رمز OAuth يستطيع الوصول مباشرةً إلى واجهة REST الخاصة بالمزوّد قبل اقتراح مفتاح API منفصل.

  16. يمكن لإخفاء الأسرار (secret redaction) أن يخفي الرموز في مخرجات الأدوات. إذا كان إخفاء الأسرار مفعّلًا، تظهر الرموز والسلاسل المبهمة الطويلة كـ *** في مخرجات نتائج الأدوات، فلا يمكنك تنفيذ print(response) للحفاظ على ظهور access_token عبر الأدوار. ومقترنًا بقيم code أحادية الاستخدام في منح authorization_code: إذا طبعت استجابة تبادل الرمز، فقد تفقد الرمز وتستهلك الرمز (code) معًا، مما يفرض إعادة البدء برابط تفويض جديد. اكتب access_token دائمًا مباشرةً إلى ملفه النهائي في نفس كتلة الكود التي تنفّذ فيها تبادل الرمز. إن احتجت الطباعة للتنقيح (debugging)، اطبع فقط len(access_token) و token_type و scope و expires_in — لا السرّ نفسه أبدًا.

  17. يستخدم GitHub MCP (api.githubcopilot.com/mcp/) تطبيق OAuth سرّي مُسجّلًا مسبقًا، لا DCR + PKCE عامًا. تحمل معلومات عميله client_secret فعليًا و token_endpoint_auth_method: client_secret_post. يجب أن يتضمّن طلب POST لتبادل الرمز إلى https://github.com/login/oauth/access_token حقل النموذج client_secret إلى جانب client_id و code و code_verifier و redirect_uri (يظل PKCE مُحترمًا فوق ذلك). رابط إعادة التوجيه ثابت في إعدادات تطبيق OAuth — لا يمكنك تغييره، فلا تنطبق حيلة منفذ المستمع اليدوي؛ يترك المستخدم فقط المتصفح يفشل في الاتصال بذلك المنفذ ثم يلصق رابط شريط العناوين لاحقًا.

ما لا يجب فعله

  • لا تستخدم mcp-remote كحل احتياطي. فهو يشغّل عملية فرعية npx يجلس خادم استدعاء OAuth الخاص بها أيضًا على loopback الحاوية البعيدة — المشكلة نفسها. لا يفيد mcp-remote إلا عندما لا يتحدث عميل MCP HTTP بعيدًا إطلاقًا (وHermes يتحدثه أصلًا).
  • لا تدفع نحو "الصق رمز API الخاص بك وسأضيف الترويسات" إذا طلب المستخدم صراحةً استخدام OAuth. اعرض الاختصار عبر الرمز الثابت فقط بعد شرح سبب فشل تدفق OAuth الأصلي في عمليات النشر البعيدة. احترم اختيار المستخدم لبذل الجهد الإضافي مقابل وصول محدود النطاق وبلا حاجة لتدوير الرموز.
  • لا تدّعِ أن Hermes لا يدعم ميزة ما دون قراءة المصدر. ابحث في شجرة الكود المصدري قبل إطلاق أي حكم حول القدرات.

ملفات مرجعية سريعة

  • scripts/diagnose-oauth-mcp.py — أداة تشخيص قابلة لإعادة التشغيل، للقراءة فقط افتراضيًا. لاسم خادم مُعطى، تختبر access_token المخزّن، وتحاول التحديث، وتختبر الرمز الجديد، وتطبع بالضبط فرع الاسترداد الذي أنت فيه (TOKEN_OK = قاطع الدارة/إعادة التشغيل، REFRESH_FIXED = حفظ+إعادة تشغيل، SESSION_REVOKED = إعادة مصادقة كاملة، REFRESH_DEAD = إعادة مصادقة كاملة/مفتاح API). مرّر --write لحفظ رمز مُحدَّث ناجح بشكل ذري (atomically). لا يطبع قيم الأسرار أبدًا. شغّل هذا أولًا عندما يبلّغ خادم MCP يعمل بـ OAuth بأنه "غير متصل" — فهو يجسّد شجرة قرار النقاط الحرجة 7/9/10.
  • references/stripe-mcp-oauth-revocation.md — مثال عملي (Stripe) على مزوّد يُلغي جلسة OAuth الخاصة به بشكل متكرر، والحل الدائم: التحوّل إلى مفتاح API مقيَّد ثابت.

ذات صلة

  • native-mcp — دليل عام لإعداد MCP في Hermes. المرجع الموثوق للإعدادات موجود هناك.
  • mcporter — جسر CLI الخارجي، لاستدعاءات MCP العرضية خارج إعدادات Hermes.

الوضع المُدار (Managed Mode)

عند تشغيل hermes عبر وحدة NixOS، تكون أوامر CLI التالية محظورة، مع رسالة خطأ وصفية توجّهك إلى configuration.nix:

الأمر المحظورالسبب
hermes setupالإعدادات تصريحية — عدّل settings في إعدادات Nix
hermes config editتُولَّد الإعدادات من settings
hermes config set <key> <value>تُولَّد الإعدادات من settings
hermes gateway installتتولى NixOS إدارة خدمة systemd
hermes gateway uninstallتتولى NixOS إدارة خدمة systemd

يمنع ذلك الانحراف بين ما يعرّفه Nix وما هو موجود على القرص. ويعتمد الاكتشاف على إشارتين:

  1. متغير البيئة HERMES_MANAGED. تضبطه الخدمة، وتقرؤه عملية gateway.
  2. ملف العلامة .managed في HERMES_HOME. يكتبه سكربت التفعيل، ويقرؤه الـ shell التفاعلي. ولذلك يحظر CLI أيضًا أوامر مثل docker exec -it hermes-agent hermes config set ....

تحمل كلتا الإشارتين اسم النظام الذي يدير التثبيت، ولذلك تذكر رسالة الرفض أمر إعادة البناء الصحيح: فوحدة NixOS تعطي sudo nixos-rebuild switch، ووحدة Home Manager تعطي home-manager switch.

وحدة Home Manager

يُصدِّر الـ flake أيضًا homeManagerModules.default. إن Hermes وكيل لشخص واحد؛ فبيانات الاعتماد والذاكرة والجلسات ومهام cron كلها تخص ذلك الشخص. ولذلك فإن خدمة على مستوى المستخدم هي الشكل الصحيح على الجهاز الشخصي. وهي تعمل على كل توزيعة يدعمها Home Manager، وليس على NixOS فقط.

مجموعة الخيارات هي نفسها التي تستخدمها وحدة NixOS، أي services.hermes-agent، مع الخيارات نفسها settings و environmentFiles و documents و mcpServers و extraPlugins و backend. ويعمل كل مثال مما سبق هنا دون تغيير، ولا يختلف سوى الأجزاء الضرورية:

يعمل serve دون واجهة مستخدم. فهو يوفّر الـ sockets /api/ws و /api/pty التي يتصل بها Hermes Desktop، ولا يبني تطبيق الويب. أما dashboard فيوفّر كل ذلك، ويقدّم أيضًا لوحة الإدارة في المتصفح. تستخدم كلتا العمليتين HERMES_HOME واحدًا مشتركًا مع الـ gateway، ولذلك تكون الجلسات والمهارات والذاكرة ومهام cron هي نفسها للجميع. ويعمل backend.mode بالطريقة نفسها في وحدة NixOS، لكن ليس في وضع الحاوية.

الربط بعنوان غير عنوان loopback

العنوان الافتراضي هو 127.0.0.1. وأي عنوان آخر يفعّل بوابة المصادقة الخاصة بلوحة التحكم. كما يرفض الخادم أي طلب يحمل ترويسة Host تختلف عن العنوان الذي رُبط به الخادم، وذلك للحماية من هجمات DNS rebinding. اربط الخادم بالاسم أو العنوان الذي يستخدمه عميلك.

لا يُعاد إنشاء الحاوية إلا عند تغيّر hash الهوية الخاص بها. يشمل الـ hash: إصدار المخطط (schema)، والصورة، و extraVolumes، و extraOptions، وسكربت نقطة الدخول. أما التغييرات على متغيرات البيئة أو الإعدادات أو المستندات أو حزمة hermes نفسها فإنها لا تؤدي إلى إعادة الإنشاء.

فقدان الطبقة القابلة للكتابة

عندما يتغير hash الهوية (ترقية الصورة، أو وحدات تخزين جديدة، أو خيارات حاوية جديدة)، تُحذف الحاوية ويُعاد إنشاؤها من نسخة جديدة مسحوبة من container.image. وتُفقد أي حزم مثبّتة عبر apt install أو pip install أو npm install في الطبقة القابلة للكتابة. أما الحالة في /data و /home/hermes فتبقى محفوظة (لأنها مربوطة عبر bind mount).

إذا كان الوكيل يعتمد على حزم معيّنة، ففكّر في تضمينها داخل صورة مخصصة (container.image = "my-registry/hermes-base:latest") أو في كتابة سكربت لتثبيتها ضمن ملف SOUL.md الخاص بالوكيل.

حماية GC Root

ينشئ سكربت preStart جذر GC (GC root) في ${stateDir}/.gc-root يشير إلى حزمة hermes الحالية. يمنع ذلك nix-collect-garbage من حذف الملف التنفيذي قيد التشغيل. وإذا تعطّل الـ GC root لسبب ما، فإن إعادة تشغيل الخدمة تعيد إنشاءه.

مجموعات الاعتماديات الاختيارية (extraDependencyGroups)

للإضافات الاختيارية (extras) المُعرَّفة في ملف pyproject.toml الخاص بـ hermes-agent، استخدم extraDependencyGroups لتضمينها في الـ venv المختوم وقت البناء. وهذا مطلوب لأي إضافة غير موجودة في المجموعة الافتراضية [all] — إذ لا يمكن على Nix التثبيت وقت التشغيل داخل الـ store المخصص للقراءة فقط.

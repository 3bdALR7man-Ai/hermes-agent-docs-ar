نقاط الحفظ (Checkpoints) و /rollback

يستطيع Hermes Agent أخذ لقطة (snapshot) من مشروعك تلقائيًا قبل العمليات المدمّرة واستعادته بأمر واحد. ومنذ الإصدار v2 أصبحت نقاط الحفظ اختيارية التفعيل (opt-in) — فمعظم المستخدمين لا يستخدمون /rollback أبدًا، كما أن المساحة التي يشغلها الـ shadow store تصبح كبيرة مع مرور الوقت، لذا فهي معطّلة افتراضيًا.

تعتمد شبكة الأمان هذه على Checkpoint Manager داخلي يحتفظ بمستودع git ظلّي (shadow) واحد مشترك تحت ~/.hermes/checkpoints/store/ — ولا يُمَسّ مجلد .git الحقيقي لمشروعك أبدًا. تتشارك جميع المشاريع التي يعمل عليها الوكيل المخزن نفسه، لذا تُزيل قاعدة بيانات الكائنات في git، المعنونة حسب المحتوى، التكرارات عبر المشاريع وعبر الأدوار.

ما الذي يُنشئ نقطة حفظ

تُنشأ نقاط الحفظ تلقائيًا قبل:

  • أدوات الملفات — write_file و patch
  • أوامر الطرفية المدمّرة — rm و rmdir و cp و install و mv و sed -i و truncate و dd و shred، وإعادة توجيه المخرجات (>)، و git reset/clean/checkout

يُنشئ الوكيل نقطة حفظ واحدة على الأكثر لكل مجلد في كل دور، حتى لا تُغرق الجلسات الطويلة المخزن باللقطات.

مرجع سريع

Slash commands داخل الجلسة:

الأمرالوصف
/rollbackيعرض جميع نقاط الحفظ مع إحصاءات التغييرات
/rollback <N>يستعيد الحالة إلى نقطة الحفظ N مع الإبقاء على تعديلاتك اليدوية (ويتراجع أيضًا عن آخر دور في المحادثة)
/rollback <N> --allاستعادة كاملة — تكتب فوق تعديلاتك اليدوية أيضًا
/rollback diff <N>يعاين الفروق (diff) بين نقطة الحفظ N والحالة الحالية
/rollback <N> <file>يستعيد ملفًا واحدًا من نقطة الحفظ N

أوامر CLI لفحص المخزن وإدارته خارج الجلسة:

الأمرالوصف

كيف تعمل نقاط الحفظ

على مستوى عام:

  • يكتشف Hermes متى تكون الأدوات على وشك تعديل ملفات في شجرة العمل لديك.
  • مرة واحدة في كل دور من المحادثة (لكل مجلد)، يقوم بما يلي:
    • يحدد جذرًا مناسبًا للمشروع الذي ينتمي إليه الملف.
    • يهيّئ الـ shadow store الوحيد المشترك في ~/.hermes/checkpoints/store/ أو يعيد استخدامه.
    • يُجهّز التغييرات (stage) في فهرس خاص بكل مشروع، ويبني شجرة، ثم ينفّذ commit إلى مرجع (ref) خاص بكل مشروع (refs/hermes/<project-hash>).
  • تشكّل هذه المراجع الخاصة بكل مشروع سجلًّا لنقاط الحفظ يمكنك فحصه والاستعادة منه عبر /rollback.

الاستعادة باستخدام /rollback

خلف الكواليس، يقوم Hermes بما يلي:

  1. يتحقق من وجود الـ commit المستهدف في الـ shadow store.
  2. يأخذ لقطة سابقة للتراجع من الحالة الحالية حتى تتمكن لاحقًا من "التراجع عن التراجع".
  3. يستعيد الملفات المتتبَّعة في مجلد العمل — مع الحفاظ على تعديلاتك اليدوية (انظر أدناه).
  4. يتراجع عن آخر دور في المحادثة حتى يتطابق سياق الوكيل مع حالة نظام الملفات المستعادة.

تعديلات المستخدم اليدوية محفوظة افتراضيًا

لا يستعيد /rollback <N> إلا الملفات التي غيّرها Hermes نفسه. فكل عملية write_file / patch ناجحة تسجّل بصمة (hash) محتوى الملف في سجل كتابات الوكيل (agent-write ledger)؛ وعند الاستعادة، فإن أي ملف لم يعد محتواه الحالي يطابق آخر ما كتبه Hermes (لأنك عدّلته لاحقًا، أو لأن Hermes لم يلمسه قط) يجري تخطيه بدلًا من الكتابة فوقه، ويُدرج في المخرجات:

لفرض الاستعادة الكاملة التقليدية التي تُرجع كل شيء — بما في ذلك تعديلاتك الخاصة — أضف --all:

إذا كان السجل فارغًا (مخزن أُنشئ قبل هذه الميزة، أو لم يكتب Hermes أي ملفات في المشروع بعد)، يلجأ /rollback تلقائيًا إلى الاستعادة الكاملة.

استعادة ملف واحد

استعد ملفًا واحدًا فقط من نقطة حفظ دون التأثير في بقية المجلد:

ضوابط الأمان والأداء

  • توفّر Git — إذا لم يُعثر على git ضمن PATH، تُعطَّل نقاط الحفظ بشكل شفاف.
  • نطاق المجلد — يتخطى Hermes المجلدات الواسعة جدًا (الجذر /، والمجلد الرئيسي $HOME).
  • حجم المستودع — يجري تخطي المجلدات التي تحتوي على أكثر من 50,000 ملف.
  • الحد الأقصى لحجم الملف الواحد — تُستبعد من اللقطة الملفات الأكبر من max_file_size_mb (الافتراضي 10 MB). وهذا يمنع ابتلاع مجموعات البيانات أو أوزان النماذج أو الوسائط المولَّدة عن طريق الخطأ.
  • الحد الأقصى للحجم الإجمالي للمخزن — عندما يتجاوز المخزن max_total_size_mb (الافتراضي 500 MB)، يُحذف أقدم commit لكل مشروع بالتناوب (round-robin) حتى يعود الحجم إلى ما دون الحد.
  • تقليم فعلي — يُفرض max_snapshots بإعادة كتابة المرجع الخاص بكل مشروع ثم تشغيل git gc --prune=now بعد ذلك، حتى لا تتراكم الكائنات السائبة.
  • اللقطات دون تغييرات — إذا لم تكن هناك تغييرات منذ آخر لقطة، يجري تخطي نقطة الحفظ.
  • أخطاء غير قاتلة — تُسجَّل جميع الأخطاء داخل Checkpoint Manager على مستوى debug؛ وتستمر أدواتك في العمل.

أين تُخزَّن نقاط الحفظ

تُشتق كل قيمة <hash> من المسار المطلق لمجلد العمل. ولا تحتاج عادةً إلى التعامل مع هذه المجلدات يدويًا — استخدم hermes checkpoints status / prune / clear بدلًا من ذلك.

الترحيل من v1

قبل إعادة الكتابة في v2، كان لكل مجلد عمل مستودع git ظلّي كامل خاص به تحت ~/.hermes/checkpoints/<hash>/ مباشرةً. لم يكن ذلك التنظيم قادرًا على إزالة تكرار الكائنات عبر المشاريع، وكانت أداة التقليم فيه لا تفعل شيئًا (وهو أمر موثّق) — فكان المخزن ينمو بلا حدود.

عند أول تشغيل لـ v2، تُنقل أي مستودعات ظلّية سابقة لـ v2 إلى ~/.hermes/checkpoints/legacy-<timestamp>/ حتى يبدأ التنظيم الجديد ذو المخزن الواحد نظيفًا. ويظل سجل /rollback القديم متاحًا عبر فحص الأرشيف القديم يدويًا باستخدام git؛ وعندما تتأكد من أنك لم تعد بحاجة إليه، نفّذ:

لاستعادة المساحة. كما يُنظّف auto_prune الأرشيفات القديمة بعد انقضاء retention_days.

أفضل الممارسات

  • فعّل نقاط الحفظ فقط عند الحاجة إليها — عبر hermes chat --checkpoints أو بضبط enabled: true لكل profile.
  • استخدم /rollback diff قبل الاستعادة — عاين ما سيتغير لاختيار نقطة الحفظ الصحيحة.
  • استخدم /rollback بدلًا من git reset عندما تريد التراجع عن التغييرات التي أجراها الوكيل فقط.
  • راجع hermes checkpoints status من حين لآخر إذا كنت تستخدم نقاط الحفظ بانتظام — فهو يعرض المشاريع النشطة والمساحة التي يستهلكها المخزن.
  • اجمع بينها وبين Git worktrees لتحقيق أقصى درجات الأمان — أبقِ كل جلسة Hermes في worktree/branch خاص بها، مع نقاط الحفظ كطبقة إضافية.

لتشغيل عدة وكلاء بالتوازي على المستودع نفسه، راجع دليل Git worktrees.

معلومة

ما يلي هو التعريف الكامل للمهارة الذي يحمّله Hermes عند تفعيل هذه المهارة، وهو ما يراه الوكيل كتعليمات أثناء عمل المهارة.

قاعدة التواصل 1-3-1

صيغة اتخاذ قرار منظّمة لعندما تكون للمهمة عدة أساليب صالحة ويحتاج المستخدم توصية واضحة. تُنتج صياغة موجزة للمشكلة، وثلاثة خيارات مع المقايضات، وخطة قابلة للتنفيذ للمسار الموصى به.

متى تُستخدم

  • يطلب المستخدم صراحة استجابة بصيغة "1-3-1".
  • يقول المستخدم "أعطني خيارات" أو "ما هي خياراتي" بشأن قرار تقني.
  • للمهمة عدة أساليب صالحة ذات مقايضات معنوية (البنية المعمارية، الأدوات، استراتيجية الترحيل).
  • يحتاج المستخدم اقتراحًا يمكنه إحالته إلى فريق أو جهة معنية.

لا تستخدمها لأسئلة بسيطة ذات إجابة واضحة واحدة، أو جلسات تصحيح الأخطاء، أو مهام قرر فيها المستخدم بالفعل الأسلوب.

الإجراء

  1. المشكلة (جملة واحدة)

    • اذكر القرار الأساسي أو النتيجة المرغوبة في جملة واحدة موجزة.
    • ركّز على ماذا، لا كيف — بلا تفاصيل تنفيذ، أو أسماء أدوات، أو تقنيات محددة.
    • اجعلها مُحكَمة. إذا احتجت "و"، فأنت تصف مشكلتين.

  2. الخيارات (ثلاثة بالضبط)

    • اعرض ثلاثة أساليب متمايزة وصالحة، مُسمّاة A وB وC.
    • يحصل كل خيار على وصف موجز، وإيجابيات، وسلبيات.
    • يجب أن تمثّل الخيارات استراتيجيات مختلفة حقًا، لا تنويعات طفيفة على نفس الأسلوب.

  3. التوصية (خيار واحد)

    • اذكر أي خيار توصي به ولماذا، بناءً على سياق المستخدم وأولوياته.
    • كن مباشرًا — هذا حكمك المهني، لا تحفّظ.

  4. تعريف الاكتمال (Definition of Done)

    • اسرد معايير النجاح المحددة للخيار الموصى به.
    • هذه نتائج ملموسة قابلة للتحقق — لا تطلعات غامضة.
    • إذا اختار المستخدم خيارًا مختلفًا، راجع هذا القسم ليطابقه.

  5. خطة التنفيذ

    • خطوات ملموسة لتنفيذ الخيار الموصى به.
    • ضمّن أوامر أو أدوات أو إجراءات محددة حيثما ينطبق ذلك.
    • إذا اختار المستخدم خيارًا مختلفًا، راجع هذا القسم ليطابقه.

التحقق

  • تحتوي الاستجابة على جملة مشكلة واحدة بالضبط.
  • تحتوي الاستجابة على ثلاثة خيارات بالضبط (A وB وC) مع إيجابيات وسلبيات لكل منها.
  • تحتوي الاستجابة على توصية واحدة تختار خيارًا واحدًا مع تسويغ.
  • يتوافق تعريف الاكتمال وخطة التنفيذ مع الخيار الموصى به.
  • إذا اختار المستخدم خيارًا مختلفًا، تُحدَّث التوصية وتعريف الاكتمال وخطة التنفيذ وفقًا لذلك.

مثال

المستخدم: "أعطني صيغة 1-3-1 لإضافة منطق إعادة المحاولة إلى عميل API الخاص بنا."

الوكيل:

المشكلة: تفشل استدعاءات API إلى خدمات خارجية بشكل متقطع تحت الحِمل، وتحتاج معالجة إعادة محاولة سلسة.

الخيارات:

  • الخيار A: تراجع أُسّي (exponential backoff) مع jitter في أداة مساعدة مشتركة. الإيجابيات: نمط بسيط ومفهوم جيدًا؛ تنفيذ واحد مشترك بين كل المستدعين. السلبيات: لا يوجد قطع دائرة (circuit-breaking)؛ لا يزال المستدعون يُحجبون أثناء إعادة المحاولة.

  • الخيار B: مكتبة إعادة محاولة (tenacity) كمزخرف (decorator) على كل استدعاء endpoint. الإيجابيات: قابلة للضبط لكل endpoint؛ دعم مدمج لقواطع الدارة (circuit breakers) وحدود المعدل. السلبيات: تضيف اعتمادية؛ نمط المزخرف قد يُبهم تدفق التحكم.

  • الخيار C: إعادة محاولة غير متزامنة قائمة على قائمة انتظار (queue) مع معالجة الرسائل الميتة (dead letter). الإيجابيات: غير حاجب؛ الاستدعاءات الفاشلة تُتَتبَّع ويمكن إعادة تشغيلها؛ تتوسع بشكل جيد. السلبيات: زيادة كبيرة في التعقيد؛ تتطلب backend لقائمة الانتظار؛ مبالغة للخدمات منخفضة الحجم.

التوصية: الخيار A. حجم الاستدعاءات لا يبرر بنية قائمة الانتظار، وأداة مساعدة مشتركة بتراجع أُسّي + jitter تغطي نمط الفشل بوضوح دون اعتماديات جديدة.

تعريف الاكتمال:

  • أداة api_retry() تعالج أخطاء HTTP العابرة (429، 502، 503، 504).
  • تعيد المحاولة حتى 3 مرات بتراجع أُسّي وjitter.
  • كل استدعاءات API الخارجية تمر عبر أداة إعادة المحاولة.
  • تسجّل كل محاولة إعادة مع الـ endpoint ورقم المحاولة.
  • الاختبارات تغطي استنفاد إعادة المحاولة، والنجاح الفوري، وسيناريوهات العبور ثم النجاح.

خطة التنفيذ:

  1. أنشئ utils/api_retry.py بحد أقصى قابل للضبط لإعادة المحاولات، وتأخير أساسي، وأكواد حالة قابلة لإعادة المحاولة.
  2. أضف jitter باستخدام random.uniform(0, base_delay) لمنع "القطيع الرعدي" (thundering herd).
  3. لُفّ استدعاءات API الحالية في api_client.py بأداة إعادة المحاولة.
  4. أضف اختبارات وحدة تُحاكي استجابات HTTP لكل سيناريو إعادة محاولة.
  5. تحقّق تحت الحِمل باختبار إجهاد بسيط مقابل محاكاة endpoint متقلّب.

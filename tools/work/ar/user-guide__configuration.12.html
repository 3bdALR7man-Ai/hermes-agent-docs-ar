التهيئة الأولى (Onboarding)

تلميحات التهيئة عند أول لمسة وعرض بناء profile البنيوي:

  • profile_build — يتحكّم في العرض عند أول رسالة على الإطلاق، في TUI وتطبيق سطح المكتب والرسائل المباشرة على منصات المراسلة (لا في محادثة جماعية مطلقًا). "ask" (الافتراضي) يعرض بناء profile للمستخدم؛ والعرض اختياري ويتطلب موافقة — يسأل الوكيل قبل أي بحث، ولا يقرأ الحسابات المتصلة بصمت أبدًا، ويحفظ الحقائق المؤكَّدة في ذاكرة المستخدم. ويوقف "off" العرض فقط؛ ويستمر الوكيل في تقديم تعريف بسيط. يظهر العرض مرة واحدة على الأكثر لكل profile.
  • seen — حالة داخلية. يُثبّت Hermes كل تلميح مُعروض هنا بحيث لا يظهر مرة أخرى أبدًا؛ يُسجَّل عرض بناء profile هنا أيضًا بمجرد عرضه. لا تُحرِّره يدويًا — امسح قسم onboarding بالكامل إذا أردت رؤية كل التلميحات مجددًا.
  • run — يحدّد ما إذا كان تطبيق سطح المكتب يفتح محادثة الإعداد الأولى (onboarding) عند التشغيل التالي. وعدم الضبط يعني أنها تُفتح فقط عند تثبيت جديد (لا جلسات ولا profiles بعد). يكتب Hermes القيمة true عند بدء الـ onboarding وfalse عند انتهائه أو تخطيه. وهو يوجد دائمًا في config.yaml الخاص بالـ profile الافتراضي، أيًّا كان الـ profile الذي يعمل به التطبيق. اضبط false كي لا تظهر أبدًا؛ ويمكن للتثبيتات المُدارة تثبيته في الإعدادات المُدارة.

Webapp

يستطيع gateway تقديم مساحة عمل Desktop في المتصفح على مستمع (listener) خاص به. وهو معطّل إلى أن تفعّله.

  • enabled — يقرؤه gateway عند البدء؛ أعد تشغيل gateway بعد تغييره (hermes gateway restart).
  • host — القيمة 127.0.0.1 أو ::1 أو localhost تُبقي Webapp على هذا الجهاز. أما 0.0.0.0 أو :: فتجعله متاحًا من أجهزة أخرى وتتطلب مزوّد تسجيل دخول للوحة التحكم؛ وبدونه يخدم gateway العملاء الأصليين فقط ويوضح hermes webapp --status السبب. أعد تشغيل gateway بعد إضافة المزوّد. وأي قيمة أخرى، بما فيها عنوان loopback آخر مثل 127.0.0.2، تُبقي Webapp معطّلًا.
  • port — يحتاج gateway الخاص بـ profile مستقل إلى منفذ غير منفذ gateway الافتراضي. يختار Settings → Web Access → Start منفذًا لـ profile مستقل لم يضبط أي منفذ (أول منفذ حر فوق 9120 لا يستخدمه أي profile آخر) ويحفظه هنا؛ ولا يستبدل أبدًا منفذًا ضبطته أنت. وعندما يكون المنفذ مشغولًا، يخدم gateway العملاء الأصليين فقط كذلك ويبلّغ hermes webapp --status بالسبب. كما يستبدل ذلك تسجيل دخول Webapp في المتصفح، لأن برنامجًا آخر ربما تلقّاه، لذا تحتاج علامات التبويب المفتوحة إلى hermes webapp مرة أخرى بعد أن يصبح المنفذ حرًا.
  • public_url — اضبطه عندما يخدم reverse proxy أو نفق (tunnel) تديره Webapp على عنوانه الخاص (مع التمرير إلى host:port). فهو يفعّل تسجيل الدخول إلى لوحة التحكم حتى مع host من نوع loopback، وهو اسم المضيف الخارجي الوحيد الذي يقبل Webapp الطلبات له، وتُبنى عليه callbacks تسجيل الدخول. وبدون مزوّد تسجيل دخول يخدم gateway العملاء الأصليين فقط، كما في حالة 0.0.0.0. ويجب أن يكون عنوانًا يبدأ بـ http:// أو https:// بلا بيانات اعتماد أو استعلام (query) أو جزء (fragment)؛ وأي شيء آخر يُبقي Webapp معطّلًا. أما dashboard.public_url فهو لـ hermes dashboard ولا ينطبق على Webapp أبدًا.

يُفعَّل تسجيل الدخول عندما يكون host هو 0.0.0.0 أو ::، أو عند ضبط public_url، أيًّا كان المضيف. ثم يفتح hermes webapp عنوان Webapp (قيمة public_url عند ضبطه، وهو الموضع الذي يعود إليه تسجيل الدخول) لتسجّل الدخول بحساب لوحة التحكم: فروابطه ذات الاستخدام الواحد لا تفتح إلا Webapp لا يحتاج إلى تسجيل دخول. أما العملاء الأصليون (CLI و TUI وتطبيق Desktop) فلا يسجّلون الدخول أبدًا: فمستمع gateway المخصص لهم لا يطلب ذلك أبدًا، مهما كانت الإعدادات.

تُقرأ إعدادات Webapp من إعدادات gateway الذي يخدم الـ profile: إعدادات الـ profile الافتراضي بالنسبة للـ profiles المسماة التي يخدمها، وإعدادات الـ profile المستقل نفسه فيما عدا ذلك.

لوحة التحكم

إعدادات لوحة التحكم على الويب — المظهر البصري، والرابط العام، ومزوّدو المصادقة. مزوّدو المصادقة (OAuth ، كلمة المرور الأساسية، drain) موثّقون بالتفصيل في صفحة لوحة التحكم على الويب؛ هذا هو شكل config.yaml البنية.

  • theme — المظهر البصري للوحة التحكم.
  • show_token_analytics — مُعطَّل افتراضيًا. صفحة Analytics وأرقام tokens/التكلفة هي تقدير محلي بحد أدنى (تستثني الاستدعاءات المساعدة، وإعادات المحاولة، والاحتياطات، وكتابات التخزين المؤقت)، لذا قد تظهر أقل بكثير من فاتورة المزوّد. اضبطها على true فقط إذا كنت تدرك أنها ليست فوترة.
  • public_url — عند ضبطه، يصبح هذا هو المرجع الكامل (المخطط + المضيف + بادئة المسار الاختيارية) الذي يُبنى منه redirect_uri الخاص بـ OAuth. اضبطه للنشر خلف وكلاء عكسيين (reverse proxies) لا يعيدون توجيه ترويسات X-Forwarded-* بشكل موثوق. اتركه فارغًا لاستخدام إعادة بناء ترويسات الوكيل.
  • trusted_proxies — عناوين IP أو شبكات CIDR محدودة يُسمح لها بتزويد X-Forwarded-Proto وX-Forwarded-For. يظل loopback موثوقًا تلقائيًا. اضبط هذا عندما يتصل وكيل TLS العكسي من حاوية أو مضيف آخر. فضّل عنوان IP الدقيق للوكيل؛ استخدم شبكة مخصّصة صغيرة فقط عندما يكون عنوانه متغيّرًا. تُرفض الرموز العامة (wildcards) وشبكات /0 تُرفض الشبكات.
  • oauth / basic_auth / drain_auth — إعدادات مزوّد المصادقة التي تقرأها إضافات dashboard-auth المضمّنة. سرّ drain نفسه لا يُضبط هنا؛ بل يُوفَّر عبر متغير البيئة HERMES_DASHBOARD_DRAIN_SECRET. راجع لوحة تحكم Hermes على الويب لإعداد المصادقة الكامل.
  • ws_ping_interval / ws_ping_timeout — ضبط دقيق لإبقاء اتصال WebSocket حيًا للربط غير loopback (اتصالات loopback لا تُرسل نبضات أبدًا). ارفع هذه القيم على الروابط عالية الكمون (Tailscale ، أنفاق SSH البعيدة) حيث يمكن للقيم الافتراضية البالغة 20 ثانية أن تُصنِّع قطعًا وهميًا برمز 1006.
  • ssh_isolated_idle_grace_s (الافتراضي 900) — backend من نوع hermes serve --isolated يملكه Desktop ويُصل إليه عبر SSH يُفصل عن جلسة SSH عمدًا، حتى لا يستطيع نوم الحاسوب المحمول أثناء الاتصال إسقاطه؛ كانت كل إعادة اتصال بعد استيقاظ مظلم تترك backend آخر يمسك بـ state.db. يتوقف backend الآن تلقائيًا عند عدم اتصال أي عميل WebSocket لهذه المدة وعدم تشغيل أي دور للوكيل (يبقيه الدور حيًا؛ وكذلك حالة دور غير قابلة للقراءة). اضبطه مرتفعًا إذا كنت تعتمد على backend منفصل لإنهاء عمل طويل بعد نوم الحاسوب المحمول. وترسل هذه backends أيضًا ping WebSocket بطيئًا (60 s ، ومهلة 10 min) لاكتشاف نفق نصف مفتوح. وبصرف النظر عن هذه المهلة، يتوقف backend (بين الأدوار) عندما يشير قفل ملكية Desktop على المضيف البعيد إلى تشغيل أحدث للاتصال نفسه، فلا تُراكم عاصفة إعادة الاتصال backends منفصلة؛ ويغطي ذلك مضيفي SSH من POSIX و Windows الأصلي.
  • ws_orphan_reap_grace_s — المدة التي تنتظرها جلسة منفصلة عن WS قبل أن يجمعها حاصد اليتامى (orphan reaper). ارفعها إلى جانب قيم إبقاء الاتصال حيًا إذا كان العملاء يعيدون الاتصال ببطء. تُتمّم صيانة الجلسة الدورية أيضًا تنظيف المقابس المغلقة وتعيد تسليح مؤقت يتيم مفقود، لذا لا يمكن لمحادثة منفصلة الاحتفاظ بحق ملكيتها لمجرد فقدان تنظيفها الأولي أو مؤقتها. إعادة الاتصال تُلغي ذلك المؤقت؛ ويظل العمل المفوَّض النشط والأدوار الجارية السليمة محميين بفحوصات حاصد اليتامى العادية. (يبقى HERMES_TUI_WS_ORPHAN_REAP_GRACE_S كتجاوز داخلي.)
  • ws_orphan_activity_stale_s (الافتراضي 600) — المدة التي يجب أن تظل فيها ساعة نشاط دور جارٍ منفصل (نفس الساعة التي يراقبها حارس agent.turn_liveness: انتظارات API ، tokens البث، نبضات الأدوات) خاملة قبل أن يقاطعه حاصد اليتامى. الدور الغائب عن العميل الذي لا يزال يُنتج فعليًا يستمر في العمل حتى الاكتمال بشكل منفصل — إغلاق الحاسوب المحمول، أو تشغيل تطبيق الجوال في الخلفية، أو تحديث سطح المكتب لم يعد يُلغي الأدوار الطويلة السليمة؛ فقط الدور المُعطَّل فعليًا يُقاطَع. اضبطه على 0 للمقاطعة عند نافذة الإمهال بغضّ النظر عن النشاط (السلوك القديم).
  • startup_orphan_sweep (الافتراضي true) — مؤقت حصد يتامى WS أعلاه يعمل داخل العملية نفسها، لذا فإن إعادة تشغيل gateway (تحديث، عطل، systemd) قبل أن يُطلَق يترك صف الجلسة مفتوحًا إلى الأبد — عمل "نشط" وهمي في /resume ولوحات التحكم. عند كل إقلاع لـ gateway — كلٌّ من TUI عبر stdio (entry.main) و sidecar WebSocket لسطح المكتب/لوحة التحكم (handle_ws) — تُغلَق الصفوف التي مصدرها tui / desktop / subagent / unknown (صف اضطر حارس حساب tokens إلى إنشائه بنفسه) ويكون وقت بدئه وأحدث رسالة فيها أقدم من مدة صلاحية الجلسة (HERMES_TUI_SESSION_TTL_S، الافتراضي 6 ساعات) بسبب إغلاق end_reason: startup_orphan_reap. جلسات منصات المراسلة (Telegram ، Discord ، …) لا تُمس أبدًا، وتُستثنى الجلسات الحية في الذاكرة (عميل استأنف بالفعل)، وتظل الجلسات المُجرَّفة قابلة للاستئناف.

تشغيل gateway متعدد المنصات

يشغّل gateway عادةً عدة محوّلات (adapters) في آن واحد (Telegram + Discord + Slack، إلخ). وتتناول الأقسام التالية العمليات اليومية بعد الإعداد (day-2 operations) التي تشمل جميع المنصات.

/platformالأمر

بعد تشغيل gateway، استخدم الـ slash command /platform من أي جلسة CLI أو محادثة متصلة لفحص المحوّلات كلٍّ على حدة والتحكم بها دون إعادة تشغيل gateway بالكامل:

/platform list ما إذا كان كل محوّل في حالة running، أو paused (يدويًا)، أو paused-by-breaker (انظر أدناه). ويُبقي الإيقاف المؤقت المحوّلَ محمّلًا وحلقاته الخلفية نشطة — إذ تُهمل الرسائل الواردة، لكن الاتصال نفسه يبقى مفتوحًا فيكون الاستئناف فوريًا.

راجع أيضًا أمر ملخص الحالة الأشمل /platforms.

تعطيل منصة لا تزال بيانات اعتمادها موجودة في .env

platforms.<name>.enabled: false في ~/.hermes/config.yaml هو المرجع الحاسم. فبيانات الاعتماد الخاصة بتلك المنصة المتروكة في البيئة (TELEGRAM_BOT_TOKEN، WEIXIN_TOKEN، HASS_TOKEN، EMAIL_*، TWILIO_ACCOUNT_SID، ...) تبقى مربوطة بإعدادات المنصة كي تواصل أدوات الإرسال فقط عملها، لكنها لم تعد تُشغّل المحوّل:

~/.hermes/config.yaml

كانت الإصدارات السابقة تسمح لمجرد وجود بيانات الاعتماد بإعادة تفعيل اثنتي عشرة منصة (Weixin و WhatsApp Cloud و Home Assistant و Email و SMS و DingTalk و Feishu و WeCom و WeCom callback و BlueBubbles و QQ Bot و Yuanbao) بغض النظر عن ذلك المفتاح. وإذا كنت تعتمد على ذلك، فإن gateway يسجّل الآن رسالة WARNING واحدة لكل منصة متأثرة عند بدء التشغيل حتى لا تتوقف بصمت:

أما حذف المفتاح enabled كليًا فيُبقي السلوك المعتمد على البيئة وحدها: وجود بيانات الاعتماد → يبدأ المحوّل.

تجاهل proxy موروث (gateway.trust_env)

افتراضيًا، يلتزم كل محوّل منصة بالمتغيرات HTTP_PROXY / HTTPS_PROXY / NO_PROXY (و SSL_CERT_FILE) من بيئة gateway، ويكتشف proxy النظام في macOS تلقائيًا. وقد يرث gateway الذي تشغّله مهمة مجدولة في Windows (Scheduled Task) أو مدير خدمات proxy لا يراه الـ shell التفاعلي أبدًا — كمستمع Clash/V2Ray محلي لم يبدأ تشغيله بعد — فيسجّل Cannot connect to host 127.0.0.1:7890 عند كل عملية استطلاع. أوقف الـ proxy الموروث لجميع المحوّلات دفعة واحدة:

~/.hermes/config.yaml

أما متغيرات الـ proxy الصريحة الخاصة بكل منصة (DISCORD_PROXY، TELEGRAM_PROXY، MATRIX_PROXY، ...) فيظل الالتزام بها قائمًا. أعد تشغيل gateway بعد تغيير هذا الإعداد.

قاطع الدائرة التلقائي (circuit breaker)

يُغلَّف كل محوّل بقاطع دائرة. وتؤدي حالات الفشل المتكررة القابلة لإعادة المحاولة (انقطاعات الشبكة العابرة، وردود حدّ المعدل، واستجابات 5xx من الخدمة الأصلية، وانقطاعات websocket) إلى تفعيل القاطع — فيُوقَف المحوّل مؤقتًا تلقائيًا، ويُرسل إشعار للمشغّل إلى القناة الرئيسية (home channel) لمنصة أخرى تعمل إن كانت مضبوطة، ويُكتب سطر سجل منظّم.

القاطع لا يستأنف العمل تلقائيًا — بل يبقى مفتوحًا إلى أن تنفّذ /platform resume <name> يدويًا. وهذا مقصود: فإذا كانت منصة ما تعاني انقطاعًا مستمرًا، فلن ترغب في أن يستنزف gateway نفسه بمحاولات إعادة الاتصال المتكررة.

أين تبحث عندما تكون منصة موقوفة مؤقتًا

عندما يكون محوّل موقوفًا مؤقتًا، تحقق مما يلي:

  1. سجل gateway (~/.hermes/logs/gateway.log أو سجل وحدة systemd / launchd). ابحث عن اسم المنصة مع circuit breaker أو paused أو disabled. ويتضمن حدث التفعيل عدد حالات الفشل وآخر خطأ.
  2. /platform list — تعرض الحالة الحالية وآخر سبب.
  3. صفحة حالة المزوّد (حالة Telegram bot API، وحالة Discord، إلخ). فقد تفعّل القاطع لأن المنصة كانت متعثرة؛ لذا لا تحاول الاستئناف حتى تعود للعمل.

بمجرد أن تتعافى الخدمة الأصلية، يُعيد /platform resume <name> ضبط القاطع ويعيد تجهيز المحوّل.

إشعارات إعادة التشغيل

عندما يُعاد تشغيل gateway (أو يُوقف أثناء وجود جلسات قيد التنفيذ)، يمكنه إرسال رسالة لمرة واحدة من نوع "the agent is back" / "the agent was interrupted" إلى القناة الرئيسية لكل منصة. ويُتحكم في ذلك لكل منصة عبر الخيار gateway_restart_notification في config.yaml، وقيمته الافتراضية true:

عطّله على المنصات المزعجة أو منخفضة الأولوية مع إبقائه مفعّلًا لمحادثتك الرئيسية. يُرسل الإشعار مرة واحدة لكل إعادة تشغيل، بغض النظر عن عدد الجلسات التي كانت قيد التنفيذ.

مؤشرات الكتابة

أثناء معالجة الوكيل لرسالة، يعرض gateway حالة كتابة مباشرة على المنصات التي تدعمها — فقاعة "typing…" على Telegram/Discord/Signal، أو حالة المساعد "is thinking…" على Slack. ويُتحكم في ذلك لكل منصة عبر الخيار typing_indicator في config.yaml، وقيمته الافتراضية true:

اضبط typing_indicator: false على أي منصة لا ترغب فيها بالمؤشر. يجد بعض المستخدمين حالة "is thinking…" في Slack مزعجة (كما أنها تعطّل مربع الكتابة لفترة وجيزة أثناء ظهورها، لأنها تستخدم Assistant API الخاصة بـ Slack). ولا يؤدي تعطيلها إلا إلى إخفاء المؤشر — أما تسليم الرسائل وكل ما عداه فلا يتغير. والخيار عام، لذا يعمل المفتاح نفسه مع كل منصة.

استئناف الجلسات عبر عمليات إعادة تشغيل gateway

عندما يتوقف gateway أثناء وجود استدعاء أداة أو عملية توليد قيد التنفيذ، تُعلَّم الجلسات المتأثرة بالحالة restart_interrupted. وعند بدء التشغيل التالي، يجدول gateway استئنافًا تلقائيًا لكل منها — فيتلقى المستخدم تنبيهًا قصيرًا في المحادثة ("Send any message after restart and I'll try to resume where you left off.") وتستأنف الجلسة من آخر دور مُثبَّت عندما يرد.

لا تُستأنَف إلا الأدوار التي كانت قيد التنفيذ فعلًا، ويُستأنَف كل منها مرة واحدة. لا يُجاب عن محادثة انتهى دورها سابقًا مرة أخرى لمجرد أنها كانت نشطة قبيل التعطّل. إذا أُنهي gateway بعد أن أكمل الوكيل الرد لكن قبل إرساله، يُسلَّم الرد المحفوظ (مع تنبيه "Recovered reply") بدل توليده مجددًا.

هذا السلوك مفعّل افتراضيًا ويُسجَّل عند بدء تشغيل gateway:

لا يلزم أي إعداد. وإذا كنت لا تريد هذا التنبيه، فاضبط gateway_restart_notification: false على المنصة.

إعدادات تقدّم افتراضية ملائمة للهاتف المحمول

غالبًا ما يُستخدم Telegram كصندوق وارد على الهاتف المحمول، لذا ضُبطت القيم الافتراضية لتلائم هذه الواجهة:

  • tool_progress هي off — فلا يوجد سيل من إشعارات التتبع لكل أداة يملأ المحادثة.
  • busy_ack_detail هي off — فتبقى إشعارات حالة الانشغال ونبضات المهام الطويلة مقتضبة (دون تفاصيل تصحيح مثل iteration 21/60).
  • interim_assistant_messages يظل مفعّلًا — فتعليقات المساعد الفعلية في منتصف الدور (حين يخبرك النموذج حرفيًا بما هو على وشك فعله) معلومات مفيدة، لا ضجيج.
  • long_running_notifications يظل مفعّلًا — إذ تتحدّث فقاعة واحدة تُعدَّل في مكانها "⏳ Working — N min" كل بضع دقائق، فتحصل على نبضة تطمئنك بدلًا من التحديق في typing… لنصف ساعة.

لا تسري هذه القيم الافتراضية الخاصة بكل منصة إلا ما دام المفتاح نفسه غير مضبوط مباشرةً ضمن display:. ينطبق الإعداد العام display.tool_progress, display.show_reasoning, display.busy_ack_detail, display.interim_assistant_messages أو display.long_running_notifications على كل المنصات ويستبدل قيمتها الافتراضية. إذا نُسخ config.yaml من cli-config.yaml.example أقدم، فإنه يضبط الخمسة جميعها على المستوى العام، كما أن تشغيل hermes setup لأول مرة في إصدار أقدم كان يكتب tool_progress: all؛ احذف هذه الأسطر لاستعادة القيم الافتراضية الخاصة بكل منصة.

إشعارات التحذير والخطأ (إخفاء اختياري)

تُعرَض إشعارات التحذير والخطأ التلقائية افتراضيًا. لإخفاء هذه الإشعارات، فعّل suppress_warning_notifications على المستوى العام أو لواجهة بعينها:

يخفي هذا المثال الإشعارات على المستوى العام مع إبقائها ظاهرة على Telegram. أغفِل الإعداد أو استخدم false للحفاظ على التسليم المعتاد. تتقدّم التجاوزات الخاصة بالمنصة؛ وتَرث null القيمة. لا تؤدي القيم غير الصالحة إلى تفعيل الإخفاء.

يتحكم الإعداد في التحذيرات التلقائية للمحرك وتشخيصات إعادة المحاولة/الاحتياط وتنبيهات watchdog وقاعدة البيانات وإشعارات فشل cron وإشعارات فشل Kanban وتشخيصات العمل الخلفي/التفويض وتنبيهات الخطأ التي يولّدها المحوّل. ينطبق على منصات المراسلة وعرض CLI/TUI وعرض إشعارات API. تقع مسؤولية التصنيف على الجهة المنتجة: لا يُرشَّح النص الذي يشبه التحذير في طلب مستخدم أو نتيجة عادية بناءً على صياغته.

يغيّر الإخفاء العرض، لا التنفيذ. تظل السجلات الحالية والمحتوى التشخيصي المحفوظ وقرارات إعادة المحاولة وحالة الفشل وسجلات المجدول ومؤشرات الإشعارات متاحة. تظل الإيقاظات الداخلية التشخيصية وحدها (فشل subagent أو الرصيد، أو تنبيه تعطّل Kanban) تشغّل دور الوكيل — لكي يتمكن من التعامل مع الفشل ويظل سجل الجلسة متسقًا — وتُحتسَب تكلفة ذلك الدور كالمعتاد؛ ولا يُخفى إلا العرض غير المطلوب للنص والوسائط والبث. لا تُحوَّل عناصر التحكم المنظّمة للموافقة والاستيضاح ولا نتائج الأوامر/API المباشرة ولا النتائج المطلوبة إلى نجاح ولا تُهمَل. تظل علامات فشل API ورموز الحالة وبيانات الاستخدام صادقة حتى عند إخفاء النص التشخيصي.

تظل قيمة failure_deliver في cron تحدد الوجهة؛ وتحدد سياسة التحذيرات في الوجهة ما إذا كان إشعار الفشل التلقائي سيُعرَض هناك. تُسوَّى عمليات التسليم المخفية دون ادعاء نجاح الإرسال. تحتفظ عمليات التسليم التي قُبلت بالفعل بهوية تسليمها ونتيجتها.

تُحدَّد السياسة للـ profile المالك والوجهة المنطقية. تستخدم أدوار الوكيل سياسة الدور الخاصة بها؛ وتقيّم الإشعارات المستقلة وعمليات التسليم المؤجّلة السياسة عند حدود تسليمها الخاصة. لا تُحذف الرسائل التي سُلّمت بالفعل. لا يصلح الإخفاء الفشل الأساسي ولا يضيف وجهة تسجيل أخرى.

تنظيف فقاعات التقدّم (اختياري)

يمكن أيضًا حذف رسائل تقدّم الأدوات ونبضة "still working…" وفقاعات استدعاء الحالة تلقائيًا بعد وصول الرد النهائي. فعّل ذلك لكل منصة عبر display.platforms.<platform>.cleanup_progress:

القيمة الافتراضية false. ولا تلتزم بهذا الإعداد إلا المنصات التي يطبّق محوّلها delete_message (حاليًا Telegram و Discord). أما عمليات التشغيل الفاشلة فتتخطى التنظيف لتبقى الفقاعات كأثر يمكن تتبعه.

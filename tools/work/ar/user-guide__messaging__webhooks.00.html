Webhooks

استقبل الأحداث من الخدمات الخارجية (GitHub وGitLab وJIRA وStripe وغيرها) وشغّل وكيل Hermes تلقائيًا. يشغّل محوِّل (adapter) الـ webhook خادم HTTP يقبل طلبات POST، ويتحقق من توقيعات HMAC، ويحوّل الحمولات (payloads) إلى prompts للوكيل، ثم يوجّه الردود عائدةً إلى المصدر أو إلى منصة أخرى مضبوطة.

يعالج الوكيل الحدث ويمكنه الرد بنشر تعليقات على طلبات PR، أو إرسال رسائل إلى Telegram/Discord، أو تسجيل النتيجة في السجل.

درس تطبيقي بالفيديو

البدء السريع

  1. فعّله عبر hermes gateway setup أو عبر متغيرات البيئة
  2. عرّف المسارات (routes) في config.yaml أو أنشئها ديناميكيًا باستخدام hermes webhook subscribe
  3. وجّه خدمتك إلى http://your-server:8644/webhooks/<route-name>

ضبط المسارات

تحدّد المسارات كيفية التعامل مع مصادر الـ webhook المختلفة. كل مسار هو إدخال مُسمّى ضمن platforms.webhook.extra.routes في ملف config.yaml. يمكن أيضًا كتابة إعدادات المحوِّل (port، host، secret، routes) مباشرة ضمن platforms.webhook: — فكلتا الصيغتين تصلان إلى المحوِّل؛ وإذا ظهر المفتاح نفسه في الموضعين، فالأولوية للقيمة المتداخلة ضمن extra:.

خصائص المسار

الخاصيةمطلوبةالوصف
eventsلاقائمة بأنواع الأحداث المقبولة (مثل ["pull_request"]). إذا كانت فارغة، تُقبَل جميع الأحداث. يُقرأ نوع الحدث من X-GitHub-Event أو X-GitLab-Event أو event_type في الحمولة.
secretنعمسرّ HMAC للتحقق من التوقيع. يرجع احتياطيًا إلى secret العام إذا لم يُضبط على المسار. اضبطه على "INSECURE_NO_AUTH" للاختبار فقط (يتخطى التحقق).
profileلاالـ profile المخوّل بتنفيذ هذا المسار عند تفعيل gateway.multiplex_profiles. احذفه لمسار خاص بالـ profile الافتراضي فقط؛ واضبط اسم profile (مثل coder) لربط المسار وسرّه بـ /p/coder/webhooks/<route>. تضبطه الاشتراكات الديناميكية باستخدام hermes webhook subscribe <name> --route-profile coder.
promptلاسلسلة قالب تتيح الوصول إلى الحمولة بصيغة النقاط (مثل {pull_request.title}). إذا حُذفت، تُفرَّغ حمولة JSON كاملة في الـ prompt. حقول الحمولة غير موثوقة — راجع المصادقة لا تعني الثقة.
filtersلامرشحات تصريحية للحمولة تُقيَّم بعد المصادقة وتحليل المتن وتصفية الأحداث، وقبل أي عمل للوكيل أو للتسليم المباشر. تُعيد الحمولات غير المطابقة {"status":"ignored","reason":"filter"} مع HTTP 200.
scriptلاسكربت تصفية/تحويل ضمن ~/.hermes/scripts/. تُمرَّر حمولة الـ webhook بصيغة JSON عبر stdin. إذا كانت stdout كائن JSON فإنه يحل محل الحمولة قبل تطبيق القالب؛ وإذا كانت نصًا فتُتاح بوصفها script_output؛ أما stdout الفارغة، أو [SILENT]، أو رمز خروج غير صفري فتؤدي إلى تجاهل الـ webhook.
skillsلاقائمة بأسماء المهارات المراد تحميلها لتشغيل الوكيل.
toolsetsلاقائمة بمفاتيح toolset (مثل ["terminal", "file", "web"]) تحل محل toolset الخاص بالـ webhook على مستوى المنصة، وذلك للتشغيلات التي يطلقها هذا المسار فقط. تُضبط بتحرير الإعدادات يدويًا فقط — ولا يمكن ضبطها عبر hermes webhook subscribe، كي لا تتمكن الاشتراكات التي ينشئها الوكيل من منح نفسها أدوات ذات صلاحيات مرتفعة. يُتحقَّق من الأسماء بالطريقة نفسها المتبعة مع إدخالات platform_toolsets (تُحذف الأسماء المجهولة أو المقيّدة بالمنصة). راجع Toolsets لكل مسار.
deliverلاوجهة إرسال الرد: github_comment، telegram، discord، slack، signal، sms، whatsapp، matrix، mattermost، homeassistant (إضافة)، email، dingtalk، feishu، wecom، weixin، bluebubbles، qqbot، أو log (الافتراضي).
deliver_extraلاإعدادات تسليم إضافية — تعتمد المفاتيح على نوع deliver (مثل repo، pr_number، chat_id). تدعم القيم قوالب {dot.notation} نفسها المستخدمة في prompt.
deliver_onlyلاإذا كانت true، يُتخطّى الوكيل كليًا — ويصبح قالب prompt بعد عرضه هو نص الرسالة الحرفي الذي يُسلَّم. بلا أي تكلفة LLM، وتسليم في أقل من ثانية. راجع وضع التسليم المباشر لحالات الاستخدام. يتطلب أن تكون deliver وجهة حقيقية (وليست log).
cron_jobلاتشغيل مهمة cron قائمة (بالمعرّف أو الاسم) عند كل حدث بدلًا من بدء جلسة وكيل webhook جديدة. يصبح prompt المعروض سياقًا مؤقتًا خاصًا بكل تشغيل؛ وتسري إعدادات الـ prompt والمهارات والنموذج والتسليم الخاصة بالمهمة نفسها. لا يمكن الجمع بينه وبين deliver_only. راجع مهام Cron التي تطلقها الأحداث.
coalesceلاتجميع الأحداث المختلفة المتلاحقة للكيان المنطقي نفسه في تشغيل وكيل واحد بعد فترة هدوء. كتلة تتطلب key (حقل حمولة أو قالب يحدد الكيان، مثل pull_request.number)، مع window_seconds اختياري (نافذة الهدوء، الافتراضي 30) و max_wait_seconds (الحد الأقصى لتأخير الإرسال، الافتراضي 300). راجع تجميع الأحداث. لا يمكن الجمع بينه وبين deliver_only و cron_job.
mirror_to_sessionلاالافتراضي false. عندما تكون true، يُكتب بعد التسليم الناجح إلى منصة محادثة نص الرسالة المُسلَّمة أيضًا في سجل جلسة تلك المحادثة (كدور مستخدم موسوم، مثل ملخصات cron القابلة للمتابعة)، فيعرف الوكيل ما أرسله إليك للتو عندما ترد في تلك المحادثة. راجع الرد على رسالة مُسلَّمة.

مرشحات الحمولة

استخدم filters عندما يرسل مزوّد ما تدفقًا واسعًا من الأحداث، بينما يجب أن توقظ بعض الحمولات فقط الوكيل أو تُطلق تسليم deliver_only. تعمل المرشحات بعد التحقق من التوقيع وتحليل المتن و events، لكن قبل عرض الـ prompt، والتحقق من عدم التكرار (idempotency)، وإرسال المهمة إلى الوكيل، أو التسليم المباشر.

المعاملات المدعومة:

  • exists: true|false
  • missing: true
  • equals / not_equals
  • contains للسلاسل النصية والقوائم ومفاتيح القواميس
  • in للقوائم المضمّنة
  • in_file لمصفوفات JSON، أو كائنات JSON (تُستخدم مفاتيحها)، أو الملفات النصية المفصولة بأسطر جديدة
  • regex
  • مجموعات all و any و not

تستخدم مسارات الحقول صيغة النقاط. يقرأ payload.foo من كائن payload في المستوى الأعلى عند وجوده، أو من جذر متن الـ webhook في حالة الحمولات المسطّحة. يطابق event / event_type نوع الحدث الذي جرى تحديده، ويقرأ headers.<Name> ترويسات الطلب.

تجميع الأحداث

كثيرًا ما يطلق المزوّدون عدة أحداث مختلفة للكيان المنطقي نفسه بتتابع سريع — خمس عمليات push سريعة إلى pull request واحد، أو سلسلة تعديلات على تذكرة واحدة، أو تنبيه مراقبة متذبذب. يحمل كل حدث معرّف تسليم جديدًا، لذا لا يستطيع التخزين المؤقت لمنع التكرار كتمها، ويوقظ كل حدث تشغيل وكيل منفصلًا.

اضبط coalesce على مسار لتجميعها في تشغيل واحد لكل كيان بعد فترة هدوء:

آلية العمل:

  • تُجمع الأحداث لكل مسار وفق key المعروض. يعمل كلٌّ من الحقل المجرّد بصيغة النقاط (pull_request.number) والقالب الكامل ({repository.full_name}#{pull_request.number}).
  • كل حدث جديد يستبدل الحدث المعلّق ويؤخّر مؤقت نافذة الهدوء. عندما تمر window_seconds دون حدث جديد، ترسل المجموعة تشغيل وكيل واحدًا باستخدام حمولة الحدث الأحدث وقوالب الـ prompt والتسليم الخاصة به.
  • max_wait_seconds يحدّ مدة التخزين الإجمالية منذ أول حدث للمجموعة، فلا يؤجل تدفّق أحداث مستمر الإرسال إلى الأبد.
  • عندما يُجمع أكثر من حدث، تُضاف إلى الـ prompt ملاحظة قصيرة تبيّن للوكيل عدد الأحداث السابقة التي استُبدلت.
  • إذا تعذّر حسم key لحدث (تفتقر الحمولة إلى الحقل — مثل حدث issue_comment على مسار مفتاحه pull_request.number)، يُرسَل ذلك الحدث فورًا بدلًا من تجميعه، فلا تندمج الكيانات غير ذات الصلة في مجموعة واحدة أبدًا. اختر مفتاحًا موجودًا في كل نوع حدث يقبله المسار.
  • تعيد الطلبات المجمّعة HTTP 202 مع {"status": "coalesced"}. يظل منع التكرار وفق معرّف التسليم يعمل أولًا، لذا تُسقَط محاولات المزوّد لإعادة التسليم نفسه بدلًا من احتسابها.
  • تُفرَّغ المجموعات المعلّقة (وتُرسل فورًا) عندما ينقطع المحوّل — إعادة اتصال gateway أو hermes gateway stop — ولا تُسقَط. تبقى الأحداث المخزّنة في الذاكرة، لذا يؤدي قتل العملية قسرًا إلى فقدان دفعة الأحداث المخزّنة في النافذة الحالية كحد أقصى.
  • coalesce ينطبق على مسارات وضع الوكيل فقط؛ ويُرفض عند بدء التشغيل الجمع بينه وبين deliver_only أو cron_job.

مرشحات وتحويلات السكربتات

استخدم script عندما لا تكفي المرشحات التصريحية. يجب أن توجد السكربتات ضمن ~/.hermes/scripts/ الخاص بالـ profile النشط؛ إذ تُحَلّ المسارات النسبية هناك، ويُحظَر اجتياز المسارات إلى خارج ذلك المجلد. تعمل سكربتات .sh و .bash باستخدام bash، بينما تعمل جميع الامتدادات الأخرى باستخدام مفسّر Python الحالي.

تُرسَل حمولة المسار إلى stdin بصيغة JSON:

نتائج السكربت:

  • إذا كانت stdout كائن JSON، فإنه يحل محل الحمولة التي يستخدمها prompt و deliver_extra.
  • إذا كانت stdout نصًا ليس بصيغة JSON، فإنه يُضاف إلى الحمولة بوصفه script_output.
  • stdout الفارغة، أو [SILENT] بالضبط، أو {"__hermes_ignore__": true}، أو انتهاء المهلة، أو غياب السكربت، أو رمز خروج غير صفري — كل ذلك يعيد HTTP 200 مع {"status":"ignored","reason":"script"}.

قوالب الـ Prompt

تستخدم الـ prompts صيغة النقاط للوصول إلى الحقول المتداخلة في حمولة الـ webhook:

  • {pull_request.title} يُحَلّ إلى payload["pull_request"]["title"]
  • {repository.full_name} يُحَلّ إلى payload["repository"]["full_name"]
  • {__raw__} — رمز خاص يفرّغ الحمولة كاملة بصيغة JSON مُنسّقة بمسافات بادئة (مقتطعة عند 4000 حرف). مفيد لتنبيهات المراقبة أو الـ webhooks العامة التي يحتاج فيها الوكيل إلى السياق الكامل.
  • تُترك المفاتيح المفقودة كسلسلة {key} الحرفية (دون خطأ)
  • تُسلسَل القواميس والقوائم المتداخلة بصيغة JSON وتُقتطع عند 2000 حرف

يمكنك الجمع بين {__raw__} ومتغيرات القالب العادية:

إذا لم يُضبط قالب prompt لمسار ما، تُفرَّغ الحمولة كاملة بصيغة JSON مُنسّقة بمسافات بادئة (مقتطعة عند 4000 حرف).

تعمل قوالب صيغة النقاط نفسها في قيم deliver_extra.

مراجعة GitHub PR (خطوة بخطوة)

يُعِدّ هذا الشرح مراجعة تلقائية للشيفرة على كل pull request.

1. أنشئ الـ webhook في GitHub

  1. انتقل إلى مستودعك → Settings → Webhooks → Add webhook
  2. اضبط Payload URL على http://your-server:8644/webhooks/github-pr
  3. اضبط Content type على application/json
  4. اضبط Secret بحيث يطابق إعدادات مسارك (مثل github-webhook-secret)
  5. ضمن Which events?، اختر Let me select individual events وحدّد Pull requests
  6. انقر Add webhook

2. أضف إعدادات المسار

أضف المسار github-pr إلى ملف ~/.hermes/config.yaml كما هو موضح في المثال أعلاه.

3. تأكد من مصادقة أداة gh CLI

4. اختبره

إعداد Webhook في GitLab

تعمل webhooks في GitLab بطريقة مشابهة، لكنها تستخدم آلية مصادقة مختلفة. إذ يرسل GitLab السرّ كترويسة X-Gitlab-Token عادية (مطابقة تامة للسلسلة النصية، وليس HMAC).

1. أنشئ الـ webhook في GitLab

  1. انتقل إلى مشروعك → Settings → Webhooks
  2. اضبط URL على http://your-server:8644/webhooks/gitlab-mr
  3. أدخل Secret token الخاص بك
  4. اختر Merge request events (وأي أحداث أخرى تريدها)
  5. انقر Add webhook

2. أضف إعدادات المسار

الرد على رسالة مُسلَّمة

افتراضيًا، يكون التسليم إرسالًا دون متابعة: يعمل كل حدث webhook في جلسته الخاصة، لذا إذا رددت على الرسالة المُسلَّمة في تلك المحادثة، فلن يملك الوكيل فيها سجلًا بما أُرسل. اضبط mirror_to_session: true على المسار (أو مرّر --mirror-to-session إلى hermes webhook subscribe) ليُلحَق النص المُسلَّم أيضًا بجلسة المحادثة المستهدفة على هيئة [Webhook delivery: <route>] متبوعًا بالرسالة، فيكون لمتابعة مثل ("إذًا هو خارج؟") سياق.

  • إنشاء النسخة يتم بأفضل جهد: لا يفشل التسليم بسببه أبدًا، ويُتخطَّى عندما لا تكون للمحادثة جلسة gateway بعد (لم يتحدث أحد إلى الوكيل فيها).
  • في مسار /p/<profile>/، تُكتب في جلسة ذلك الـ profile للمحادثة، وليس في جلسة profile آخر أبدًا.
  • يدخل النص المنسوخ سجل المحادثة كما لو أنك أرسلته. في مسار deliver_only يكون الحمولة المعروضة الخام، لذا لا تفعّله إلا لمصادر تثق بمحتواها داخل محادثتك (خدماتك الخاصة، لا متتبّع issues عام).

آلية عمل Gateway من الداخل

Messaging gateway هو العملية طويلة الأمد التي تصل Hermes بأكثر من 20 منصّة مراسلة خارجية عبر بنية معمارية موحّدة.

الملفات الرئيسية

نظرة عامة على البنية المعمارية

تدفّق الرسائل

عند وصول رسالة من أي منصّة:

  1. مهايئ المنصّة يستقبل الحدث الخام، ويوحّد صيغته إلى MessageEvent
  2. المهايئ الأساسي يتحقّق من حارس الجلسة النشطة:
    • إذا كان الوكيل يعمل بالفعل لهذه الجلسة ← تُصفّ الرسالة في قائمة الانتظار، ويُضبط حدث مقاطعة
    • إذا كانت /approve أو /deny أو /stop ← تتجاوز الحارس (تُوزَّع مباشرة (inline))
  3. GatewayRunner._handle_message() يستقبل الحدث:
    • يحدّد مفتاح الجلسة عبر _session_key_for_source() (الصيغة: agent:main:{platform}:{chat_type}:{chat_id})
    • يتحقّق من التفويض (انظر التفويض أدناه)
    • يتحقّق مما إذا كانت slash command ← يوزّعها إلى معالِج الأوامر
    • يتحقّق مما إذا كان الوكيل يعمل بالفعل ← يعترض أوامر مثل /stop و/status
    • وإلا ← ينشئ نسخة AIAgent ويشغّل المحادثة
  4. الاستجابة تُرسل عائدةً عبر مهايئ المنصّة

صيغة مفتاح الجلسة

تُرمّز مفاتيح الجلسات سياق التوجيه الكامل:

على سبيل المثال: agent:main:telegram:private:123456789

قد تُضمِّن المنصات المدركة للخيوط (Telegram forum topics، Discord threads، Slack threads) معرّفات الخيط ضمن جزء chat_id. لا تبنِ مفاتيح الجلسات يدويًا أبدًا — استخدم دائمًا build_session_key() من gateway/session.py.

حارس رسائل ثنائي المستوى

عندما يكون الوكيل قيد التشغيل فعليًا، تمرّ الرسائل الواردة عبر حارسَين متتاليين:

  1. المستوى 1 — المهايئ الأساسي (gateway/platforms/base.py): يتحقّق من _active_sessions. إذا كانت الجلسة نشطة، يضع الرسالة في قائمة انتظار _pending_messages ويضبط حدث مقاطعة. يلتقط هذا الرسائل قبل وصولها إلى مشغّل gateway.

  2. المستوى 2 — مشغّل gateway (gateway/run_inbound.py): يتحقّق من _running_agents. يعترض أوامر محدَّدة (/stop، /new، /queue، /status، /approve، /deny) ويوجّهها بحسب الحاجة. أي شيء آخر يُطلق running_agent.interrupt().

الأوامر التي يجب أن تصل إلى المشغّل أثناء انسداد الوكيل (مثل /approve) تُوزَّع مباشرة (inline) عبر await self._message_handler(event) — فهي تتجاوز نظام المهام الخلفية لتجنّب حالات التسابق (race conditions).

التفويض

يستخدم gateway تحقّق تفويض متعدّد الطبقات، يُقيَّم بالترتيب التالي:

  1. علامة السماح للجميع الخاصة بكل منصّة (مثل TELEGRAM_ALLOW_ALL_USERS) — إذا ضُبطت، يُفوَّض جميع المستخدمين على تلك المنصّة
  2. قائمة السماح الخاصة بالمنصّة (مثل TELEGRAM_ALLOWED_USERS) — معرّفات مستخدمين مفصولة بفواصل
  3. اقتران DM — يمكن للمستخدمين المصادَق عليهم اقتران مستخدمين جدد عبر رمز اقتران
  4. السماح للجميع عالميًا (GATEWAY_ALLOW_ALL_USERS) — إذا ضُبطت، يُفوَّض جميع المستخدمين عبر كل المنصات
  5. الافتراضي: الرفض — يُرفض المستخدمون غير المفوَّضين

تدفّق اقتران DM

تُحفظ حالة الاقتران في gateway/pairing.py وتنجو من إعادة التشغيل.

توزيع Slash Commands

تمرّ كل الـ slash commands في gateway عبر خط أنابيب الحسم نفسه:

  1. تربط resolve_command() من hermes_cli/commands.py المُدخل بالاسم الأساسي (تعالج الأسماء البديلة، ومطابقة البادئات)
  2. يُتحقّق من الاسم الأساسي مقابل GATEWAY_KNOWN_COMMANDS
  3. تبحث _handle_message() (في gateway/run_inbound.py) عن المعالِج بالاسم — _handle_<name>_command في mixins الخاصة بـ gateway/slash_commands_*.py — عبر _command_handler_table فوق _IDLE_COMMANDS / _PLAIN_COMMANDS في gateway/run_busy.py؛ ولا توجد سلسلة if canonical == ...
  4. بعض الأوامر مقيَّدة بحسب الإعدادات (gateway_config_gate على CommandDef)

حارس الوكيل قيد التشغيل

تُرفض الأوامر التي يجب ألا تُنفَّذ أثناء معالجة الوكيل مبكرًا:

أثناء وجود _quick_key in self._running_agents، توجّه _dispatch_busy_slash_command() في gateway/run_busy.py كل أمر معروف حسب CommandDef.busy_policy / busy_handler الخاصة به: نسخة أثناء التشغيل (_busy_<key>_command) إن وُجدت، وإلا المعالِج العادي عندما تسمح busy_policy بذلك، وإلا رسالة رفض ("⏳ Agent is running — /model can't run mid-turn…").

أوامر التجاوز (/stop، /new، /approve، /deny، /queue، /status) لها معالِجات أثناء التشغيل وتُوزَّع مباشرة (inline).

مصادر الإعدادات

يقرأ gateway الإعدادات من مصادر متعدّدة:

المصدرما يوفّره
~/.hermes/.envمفاتيح API، وتوكنات البوت، وبيانات اعتماد المنصات
~/.hermes/config.yamlإعدادات النموذج، وإعداد الأدوات، وخيارات العرض
متغيرات البيئةتتجاوز أيًا مما سبق

خلافًا لـ CLI (الذي يستخدم load_cli_config() بقيم افتراضية مثبَّتة في الكود)، يقرأ gateway ملف config.yaml مباشرةً عبر محمِّل YAML. هذا يعني أن مفاتيح الإعدادات الموجودة في قاموس افتراضيات CLI ولكن غير الموجودة في ملف إعدادات المستخدم قد تتصرّف بشكل مختلف بين CLI وgateway.

مهايئات المنصات

تُشحَن معظم منصات المراسلة كمهايئات إضافات تحت plugins/platforms/<name>/adapter.py؛ ولا تزال بضعة مهايئات قديمة تعيش مباشرةً في gateway/platforms/. تمتد جميعها من BasePlatformAdapter في gateway/platforms/base.py:

التحميل المؤجَّل: تسجّل إضافات kind: platform المضمّنة محمِّلات register_deferred منخفضة التكلفة في gateway/platform_registry.py (عبر hermes_cli/plugins.py) بحيث لا تُستورد SDKs المنصات إلا عندما يبدأ gateway أو يُسلّم أو يشغّل الإعداد/الحالة — وليس عند تنفيذ hermes chat العادي. يحمّل الحسم مهايئًا واحدًا عند البحث؛ ويشغّل التعداد الكامل المحمِّلات المعلّقة فقط في المسارات التي تحتاج كل منصّة.

تستخدم منصات موصولات الاختبار التجريبية (connector-backed) المهايئ العام للترحيل (relay) في gateway/relay/ بدلًا من وحدة منصّة مباشرة. عند ضبط GATEWAY_RELAY_URL أو gateway.relay_url، يسجّل gateway منصّة relay، ويطلب الموصول عبر WebSocket صادر، ويستقبل إطارات descriptor وinbound وinterrupt_inbound على نفس المقبس (socket). يعلن الموصول عن CapabilityDescriptor؛ ويمكن لـ Hermes إرسال ردود صادرة عادية، وعمليات follow_up بدون توكن، وإطارات مقاطعة عائدة عبر relay. يعيش عقد السلك (wire contract) المستند إلى المصدر في docs/relay-connector-contract.md.

تنفّذ المهايئات واجهة مشتركة:

  • connect() / disconnect() — إدارة دورة الحياة
  • send() — تسليم الرسائل الصادرة
  • تُوحَّد الأحداث الواردة إلى MessageEvent وتُمرَّر عبر handle_message()

يستخدم التنشيط (wake) الداخلي عبر الدفع gateway.wake.admit_internal_event: لا تزال handle_message() العامة تعيد None، لكن إيصال _gateway_accepted المحلي للعملية الخاص بالحدث لا يُضبط إلا بعد الجدولة أو الإدراج في قائمة الانتظار. المعالِج المفقود، أو مفتاح الجلسة الصريح غير المطابق، أو إسقاط بسبب سقف قائمة الانتظار ليست قبولًا. يجب على المهايئات المخصّصة التي تتجاوز الاستقبال (ingress) تفويض الأحداث الداخلية إلى BasePlatformAdapter.handle_message() (أو تسجيل القبول الفعلي صراحةً)، لا معادلة رد نداء استُهلِك/أُسقِط بالقبول. هذا الإيصال منفصل عن محاسبة تنفيذ نبضات الجلسة (heartbeat)، ولا يتجاوز التفويض أو الإيقاف الطارئ أو حواجز تحضير الدور اللاحقة.

أقفال التوكن

تستدعي المهايئات التي تتصل ببيانات اعتماد فريدة acquire_scoped_lock() في connect() وrelease_scoped_lock() في disconnect(). يمنع هذا وجود profile اثنين يستخدمان نفس توكن البوت في آن واحد.

يُصدَر تعارض القفل باسم {scope}_lock مع retryable=True بحيث يمكن لإعادة اتصال أثناء التشغيل أن تسترجع عملها بمجرد خروج الحائز الآخر. أما عند بدء التشغيل، فإن وجود حائز أجنبي حيّ يُعدّ تعارض إعداد: تتعرّف gateway/restart.py::is_global_startup_conflict() على عائلات رموز *_lock / lock_conflict، ويوقف موجّه بدء التشغيل المنصّة بشكل fatal بدلًا من وضعها في قائمة إعادة المحاولة. وإن لم يكن هناك شيء آخر متصل، يخرج gateway بالرمز 78 (EX_CONFIG، gateway_state=startup_failed) بحيث يتوقّف المُشرِف (supervisor) عن إعادة تشغيله؛ أما بجانب فشل نظير عابر بالفعل، فيبقى gateway حيًا ويعيد النظير وحده المحاولة.

مسار التسليم

تتعامل التسليمات الصادرة (gateway/delivery.py) مع:

  • الرد المباشر — إرسال الاستجابة عائدةً إلى المحادثة الأصلية
  • التسليم إلى قناة رئيسية (home channel) — توجيه مخرجات مهام cron والنتائج الخلفية إلى قناة رئيسية مضبوطة
  • التسليم إلى هدف صريح — يحدّد محرّك الإرسال هدفًا مثل telegram:-1001234567890، مكشوفًا عبر أداة سطر الأوامر hermes send لسكربتات الـ shell وعبر أهداف deliver: في cron
  • التسليم عبر منصات مختلفة — التسليم إلى منصّة مختلفة عن منصّة الرسالة الأصلية

تسليمات مهام cron لا تُرآى (mirror) في سجل جلسة gateway — بل تعيش في جلسة cron الخاصة بها فقط. هذا قرار تصميم متعمَّد لتجنّب انتهاكات تناوب الرسائل.

Hooks

hooks الخاصة بـ gateway وحدات Python تستجيب لأحداث دورة الحياة:

أحداث hooks الخاصة بـ Gateway

الحدثوقت الإطلاق
gateway:startupبدء عملية gateway
session:startبدء جلسة محادثة جديدة
session:endاكتمال الجلسة أو انتهاء مهلتها
session:resetيعيد المستخدم ضبط الجلسة بـ /new
agent:startيبدأ الوكيل معالجة رسالة
agent:stepيُكمل الوكيل تكرارًا واحدًا لاستدعاء أداة
agent:endينهي الوكيل عمله ويعيد الاستجابة
command:*تنفيذ أي slash command

تُكتشَف hooks من gateway/builtin_hooks/ (نقطة توسعة — فارغة حاليًا في التوزيعة المُشحَنة؛ _register_builtin_hooks() جذع (stub) بلا عملية) ومن ~/.hermes/hooks/ (مثبَّتة من قِبل المستخدم). كل hook هو دليل يحتوي بيان HOOK.yaml وhandler.py.

تكامل مزوّد الذاكرة

عندما تكون إضافة مزوّد ذاكرة (مثل Honcho) مفعّلة:

  1. ينشئ gateway نسخة AIAgent لكل رسالة بمعرّف الجلسة
  2. تُهيّئ MemoryManager المزوّد بسياق الجلسة
  3. تُوجَّه أدوات المزوّد (مثل honcho_profile وviking_search) عبر:
  1. عند انتهاء الجلسة أو إعادة ضبطها، تُطلق on_session_end() للتنظيف وتفريغ البيانات النهائي

دورة حياة تفريغ الذاكرة

حدود المحادثة الصريحة (مثل /new أو /reset أو /resume) تفرّغ الجلسة الصادرة وتُنهيها. أما وقت الخمول والحدود اليومية فلا تُنهيها أبدًا.

إخلاء TTL الخاص بالموارد فقط، وLRU، وإخلاء ضغط الذاكرة، يودِعون النسخة المخزَّنة مؤقتًا من المحادثة لدى مزوّدي الذاكرة المضبوطين قبل تحرير عملاء الوكيل. وهذا لا يُغلق المحادثة الدائمة: يعيد الدور التالي تحميل نفس المحادثة والهوية.

الصيانة الخلفية

يشغّل gateway صيانة دورية جنبًا إلى جنب مع معالجة الرسائل:

  • نبض cron — يتحقّق من جداول المهام ويطلق المهام المستحقة
  • تدبير الجلسات — يستعيد الموارد المخزَّنة مؤقتًا دون إنهاء المحادثات
  • تفريغ الذاكرة — يودِع الذاكرة قبل الإخلاء المؤقت اللين
  • تحديث الذاكرة المؤقتة (cache) — يحدّث قوائم النماذج وحالة المزوّدين

إدارة العمليات

يعمل gateway كعملية طويلة الأمد، تُدار عبر:

  • hermes gateway start / hermes gateway stop — تحكّم يدوي
  • systemctl (على لينكس) أو launchctl (على macOS) — إدارة الخدمات
  • ملف PID في ~/.hermes/gateway.pid — تتبّع عمليات محدَّد بـ profile

محدَّد بـ profile مقابل عالمي: تستخدم start_gateway() ملفات PID محدَّدة بـ profile. يوقف hermes gateway stop gateway الخاص بالـ profile الحالي فقط. يستخدم hermes gateway stop --all فحص ps aux عالميًا لإنهاء كل عمليات gateway (يُستخدم أثناء التحديثات).

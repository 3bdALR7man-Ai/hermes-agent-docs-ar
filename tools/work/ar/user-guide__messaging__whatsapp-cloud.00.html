إعداد WhatsApp Business Cloud API

يستطيع Hermes الاتصال بـ WhatsApp عبر WhatsApp Business Cloud API الرسمي من Meta. وهذا هو المسار المناسب لبيئات الإنتاج: لا عملية فرعية لجسر Node.js، ولا رموز QR، ولا خطر لحظر الحساب.

في المقابل:

  • تحتاج إلى حساب Meta Business (وليس حساب WhatsApp شخصيًا).
  • يعمل البوت على رقم هاتف تجاري مخصص، وليس على رقمك الشخصي.
  • يحتاج Hermes gateway إلى URL عام يعمل بـ HTTPS كي تتمكن Meta من تسليم الرسائل الواردة عبر webhook.
  • الردود المُرسلة بعد مرور أكثر من 24 ساعة على آخر رسالة من المستخدم تتطلب قالبًا (template) معتمدًا مسبقًا (وهذه قاعدة "نافذة خدمة العملاء" الخاصة بـ Meta، وليست قيدًا من Hermes).

إذا لم تناسب هذه القيود حالة استخدامك، فإن التكامل عبر جسر Baileys هو البديل — يعمل مع الحساب الشخصي ولا يحتاج إلى URL عام، لكنه غير رسمي ومعرّض للحظر.

أيهما أستخدم؟
  • Cloud API (هذا الدليل) — إذا كنت تشغّل بوتًا تجاريًا حقيقيًا، وتريد الاستقرار، ولا تمانع إجراءات التحقق لدى Meta واعتماد القوالب
  • جسر Baileys — للمشاريع الشخصية، والعروض التجريبية السريعة، وإعدادات المستخدم الواحد، إذا كنت مستعدًا للمخاطرة بحساب رقم هاتف البوت

البدء السريع

يرشدك المعالج خلال كل بيانات الاعتماد، ويتحقق من صحة كل منها فور لصقها (فيكتشف الفخ الأول في الإعداد — لصق رقم هاتف في حقل Phone Number ID)، ويطبع تعليمات متابعة دقيقة للأجزاء التي يجب إنجازها خارج المعالج (تشغيل cloudflared، وضبط webhook في لوحة تحكم Meta).

بقية هذه الصفحة مرجع للإعداد اليدوي.

المتطلبات المسبقة

  1. حساب Meta Business. أنشئ واحدًا من business.facebook.com.
  2. تطبيق Meta مفعّل فيه WhatsApp. راجع "إنشاء تطبيق Meta" أدناه.
  3. وسيلة لكشف منفذ محلي على الإنترنت العام عبر HTTPS. يُوصى بـ Cloudflare Tunnel (cloudflared) — فهو مجاني، ولا يتطلب إعادة توجيه المنافذ (port forwarding)، ولا يحتاج إلى نطاق (domain). كما تصلح أيضًا خيارات ngrok، أو نطاقك الخاص مع reverse proxy و TLS، أو VPS يرتبط فيه الـ gateway مباشرةً بعنوان IP عام.
  4. اختياري لكنه موصى به: وجود ffmpeg على PATH كي تُعرض الرسائل الصوتية الصادرة كفقاعات ملاحظات صوتية أصلية في WhatsApp (موجة صوتية خضراء) بدلًا من مرفقات صوتية بصيغة MP3. ويتكيف Hermes بسلاسة في حال عدم وجوده.

إنشاء تطبيق Meta

  1. انتقل إلى developers.facebook.com/apps → Create App.
  2. اختر حالة الاستخدام: "Connect with customers through WhatsApp" → Next.
  3. اختر محفظة أعمال (business portfolio) أو أنشئ واحدة. راجع متطلبات النشر. ثم أكّد → Create app.
  4. بعد الإنشاء ستنتقل إلى Customize use case → Connect on WhatsApp → Quickstart. انقر على Start using the API → وستصبح الآن في صفحة API Setup.
  5. تأكد من ربط حساب WhatsApp Business Account (WABA). إذا أنشأت محفظة جديدة في الخطوة 3، فقد أُنشئ هذا الحساب تلقائيًا. تحقّق من ذلك في صفحة API Setup.

ستحتاج إلى القيم التالية من لوحة التحكم — ويطلبها المعالج بهذا الترتيب:

الـ token الدائم (للإنتاج)

تنتهي صلاحية access tokens المؤقتة بعد 24 ساعة، أي أن الـ token الذي تولّده اليوم يتوقف عن العمل غدًا. في عمليات النشر الإنتاجية، استخدم token دائمًا لمستخدم نظام (System User):

  1. انتقل إلى business.facebook.com/latest/settings → System users (في الشريط الجانبي الأيسر).
  2. Add → الاسم (مثل hermes-bot) → الدور: Admin.
  3. اختر المستخدم الجديد → Assign Assets:
    • اختر تطبيقك → فعّل Manage app تحت Full control.
    • اختر حساب WhatsApp الخاص بك → فعّل Manage WhatsApp Business Accounts تحت Full control.
    • انقر على Assign assets.
  4. Generate token مع منح الصلاحيات التالية:
    • business_management
    • whatsapp_business_messaging
    • whatsapp_business_management
  5. اضبط token expiration: Never.
  6. انسخ الـ token → حدّث WHATSAPP_CLOUD_ACCESS_TOKEN في ~/.hermes/.env → أعد تشغيل الـ gateway.

لا تنتهي صلاحية tokens مستخدمي النظام (System User) ما لم تُلغِها صراحةً.

كشف Hermes على الإنترنت

يسلّم Cloud API الرسائل الواردة عبر طلبات HTTPS POST إلى URL الخاص بـ webhook لديك — ما يعني أن Hermes gateway يجب أن يكون قابلًا للوصول من خوادم Meta. وهناك ثلاث طرق شائعة لذلك:

Cloudflare Tunnel (موصى به)

مجاني، ولا يتطلب إعادة توجيه المنافذ، ويعمل على Windows / macOS / Linux. ويعمل كعملية منفصلة إلى جانب الـ gateway.

التثبيت:

شغّل نفقًا سريعًا (quick tunnel) (لا حاجة إلى حساب Cloudflare — ويمنحك URL بالشكل https://<random>.trycloudflare.com):

دوّن الـ URL المطبوع — فهو ما ستعطيه لـ Meta.

عناوين الأنفاق السريعة تتغير

يتغير URL النفق السريع المجاني في كل مرة تعيد فيها تشغيل cloudflared. وللحصول على URL ثابت، سجّل الدخول باستخدام cloudflared tunnel login وأنشئ نفقًا مُسمّى (named tunnel). تحصل حسابات Cloudflare المجانية على عدد غير محدود من الأنفاق المُسمّاة — راجع توثيق Cloudflare للاطلاع على سير عمل الأنفاق المُسمّاة.

ngrok

تعرض الفئة المجانية URL مختلفًا عند كل إعادة تشغيل، أما الفئة المدفوعة فتمنحك نطاقًا فرعيًا ثابتًا.

نطاقك الخاص + reverse proxy

إذا كان لديك بالفعل خادم بشهادة TLS (مثل Caddy أو nginx أو غيرهما)، فوجّه مسارًا إلى localhost:8090. هذا هو الخيار الأكثر استقرارًا للإنتاج، لكنه يتطلب بنية تحتية قائمة.

إعداد webhook من جهة Meta

بمجرد تشغيل النفق:

  1. دوّن الـ URL العام الذي يطبعه النفق — لنفترض أنه https://abc123.trycloudflare.com.
  2. ولّد Verify Token — يتولى المعالج ذلك نيابةً عنك باستخدام secrets.token_urlsafe(32)؛ وإذا كنت تُجري الإعداد يدويًا، فنفّذ:
    احفظه باسم WHATSAPP_CLOUD_VERIFY_TOKEN في ~/.hermes/.env.
  3. شغّل Hermes gateway: hermes gateway.
  4. في Meta App Dashboard → WhatsApp → Configuration (أو Use cases → Customize → Configuration حسب إصدار الواجهة) → انقر على Edit في قسم Webhook.
  5. املأ الحقول:
    • Callback URL: https://abc123.trycloudflare.com/whatsapp/webhook
    • Verify Token: السلسلة النصية من الخطوة 2 (يجب أن تتطابق تمامًا)
  6. انقر على Verify and save. سترسل Meta طلب GET إلى الـ URL الخاص بك، فيعيد الـ gateway قيمة التحدي (challenge)، ثم تعتمد Meta الـ webhook كمُتحقَّق منه.
  7. ضمن Webhook fields، انقر على Manage → اشترك في الحقل messages. فهذا ما يُبلغ Meta بأن تسلّم الرسائل الواردة فعليًا إلى الـ webhook الخاص بك.

للتحقق من الحلقة يدويًا (من طرفية ثالثة):

قائمة المستلمين المسموح بهم (من جهة Meta)

في وضع التطوير (قبل أن يمر تطبيقك بمراجعة App Review)، تقيّد Meta الأرقام التي يمكن لبوتك مراسلتها:

  1. App Dashboard → WhatsApp → API Setup → القائمة المنسدلة To.
  2. انقر على Manage phone number list.
  3. أضف أرقام الهواتف التي تريد مراسلتها (رقمك، وأرقام فريقك، والمختبرين المتعاونين). سترسل Meta إلى كل رقم رمز تحقق من 6 أرقام عبر SMS أو WhatsApp.

يُسمح بما يصل إلى 5 أرقام في وضع التطوير، ويؤدي اجتياز App Review إلى إزالة هذا الحد.

الميزات

الرسائل الواردة

  • الرسائل النصية — تُمرَّر مباشرةً إلى الوكيل.
  • الصور — تُنزَّل تلقائيًا وتُرفق بمدخلات الوكيل. تقرأ النماذج ذات قدرات الرؤية الأصلية (Claude و GPT-4o و Gemini وغيرها) الصورة مباشرةً؛ بينما تتلقى النماذج التي لا تدعم الرؤية وصفًا نصيًا مولّدًا تلقائيًا.
  • الملاحظات الصوتية — تُنزَّل تلقائيًا بصيغة .ogg، وتُفرَّغ إلى نص عبر مزوّد STT المُعدّ لديك (faster-whisper المحلي، أو OpenAI/Nous، أو Groq، وغيرها)، ثم تُسلَّم إلى الوكيل كنص.
  • المستندات — تُنزَّل تلقائيًا. الملفات النصية الصغيرة القابلة للقراءة (.txt، .md، .json، .py، .csv، وغيرها) حتى 100KB تُضمَّن مباشرةً في مدخلات الوكيل ليقرأها دون استدعاء أداة. أما الملفات الأكبر فتُخزَّن مؤقتًا محليًا لتصل إليها أدوات الوكيل الأخرى.
  • الضغط على الأزرار — عندما يضغط المستخدم على زر أرسله البوت سابقًا (اختيار في سؤال توضيح، أو موافقة على أمر، أو تأكيد slash command)، تُوجَّه الضغطة مباشرةً إلى الـ handler المناسب. أما الضغطات القديمة فتُعامَل كمدخلات نصية عادية.
  • سياق الرد — عندما يرد المستخدم على رسالة سابقة، يرى الوكيل النص الأصلي كسياق. واقتباس صورة أو ملاحظة صوتية أو فيديو أو مستند (سواء كان منك أو مما أرسله البوت، مثل رسم بياني سلّمته مهمة cron) يُرفق ذلك الملف أيضًا بالدور، لذا فإن كتابة "ما هذا؟" تحت صورة مقتبسة تعمل كما هو متوقع. لا يحمل webhook الخاص بـ Meta إلا معرّف الرسالة المقتبسة، لذا يُستخرج الملف من فهرس محلي للرسائل المُرسلة/المستلمة مؤخرًا (آخر 1000 رسالة لكل gateway)؛ أما الاقتباسات الأقدم فتصل دون المرفق.

الرسائل الصادرة

  • النص — يُحوَّل markdown تلقائيًا إلى صيغة WhatsApp الخاصة (**bold** → *bold*، ~~strike~~ → ~strike~، العناوين → نص عريض، [link](url) → link (url)). وتُقسَّم الرسائل الطويلة إلى أجزاء بحد 4096 حرفًا لكل جزء.
  • الصور — تُدعم الصور التي يولّدها الوكيل وملفات الصور المحلية على حد سواء، وتُسلَّم كمرفقات صور أصلية.
  • الرسائل الصوتية — تُحوَّل مخرجات تحويل النص إلى كلام (text-to-speech) عبر ffmpeg إلى فقاعة ملاحظة صوتية أصلية في WhatsApp (موجة صوتية خضراء). ومن دون تثبيت ffmpeg، يُستعاض عنها بمرفق صوتي بصيغة MP3. راجع "الرسائل الصوتية" أدناه.
  • الفيديو / المستندات — كلاهما مدعوم، ويُرسلان كمرفقات أصلية.

تجربة الاستخدام التفاعلية

عندما يستدعي الوكيل أيًّا من هذه التدفقات، يستخدم Hermes الرسائل التفاعلية الأصلية في WhatsApp — أزرارًا يُجاب عنها بالضغط بدلًا من مطالبات "رد برقم الخيار":

  • أداة clarify — تُعرض الأسئلة متعددة الخيارات كأزرار رد سريع (1–3 خيارات) أو كقائمة تُفتح بالضغط (4 خيارات أو أكثر). واختيار "✏️ Other" يتيح للمستخدم كتابة إجابة حرة يتلقاها الوكيل كجواب على السؤال.
  • الموافقة على الأوامر الخطرة — عندما يصادف تنفيذ الطرفية/الشيفرة لدى الوكيل أمرًا مقيّدًا، يرى المستخدم أزرار ✅ Approve / ❌ Deny بدلًا من الحاجة إلى كتابة /approve أو /deny.
  • تأكيدات slash commands — تعرض الأوامر ذات الصلاحيات الخاصة مثل /reload-mcp أزرار ✅ Approve Once / 🔒 Always / ❌ Cancel.

تتحول جميع المطالبات التفاعلية بسلاسة إلى نص عادي إذا فشل عرض الأزرار (مثلًا في عملاء WhatsApp القديمة).

إشعارات القراءة ومؤشر الكتابة

يُقرّ Hermes باستلام الرسائل الواردة فورًا:

  • تظهر على رسالتك علامتا الصح الزرقاوان بمجرد أن يستلمها الـ gateway.
  • يظهر تحت اسم البوت في محادثة WhatsApp لديك "typing…" أثناء تحضير الوكيل للرد.
  • يختفي مؤشر الكتابة تلقائيًا عند وصول أول رسالة رد من البوت.

يوضح هذا بجلاء متى رأى البوت رسالتك ومتى لا يزال يعمل على الرد.

الرسائل الصوتية

يميّز WhatsApp بين "الملاحظة الصوتية" (فقاعة الموجة الصوتية الخضراء) ومرفق الملف الصوتي العادي. والفرق يتعلق بالترميز (codec) فقط: إذ يجب أن تكون الملاحظات الصوتية بصيغة audio/ogg مع ترميز opus.

ينتج TTS في Hermes ملفات MP3. وهناك مساران:

  • مع وجود ffmpeg على PATH (موصى به) — تُحوَّل مخرجات TTS الصادرة وتصل كملاحظة صوتية حقيقية. التثبيت:
    • Windows: winget install Gyan.FFmpeg
    • macOS: brew install ffmpeg
    • Linux: عبر مدير الحزم
  • من دون ffmpeg — تصل مخرجات TTS الصادرة كمرفق صوتي بصيغة MP3. يُشغَّل بشكل طبيعي، لكنه لا يبدو كملاحظة صوتية. ويُسجَّل تحذير لمرة واحدة في سجل الـ gateway لتكون على علم بذلك.

القيود المعروفة

نافذة المحادثة ذات الـ 24 ساعة

لا تسمح Meta بـ الرسائل الحرة إلا خلال نافذة مدتها 24 ساعة بعد آخر رسالة واردة من المستخدم. وخارج هذه النافذة، لا يقبل API الخاص بـ Meta إلا قالب رسالة (message template) معتمدًا مسبقًا.

ماذا يعني هذا عمليًا:

  • المحادثة التفاعلية (يراسل المستخدم البوت → يرد البوت خلال 24 ساعة → يرد المستخدم → ...) تعمل إلى ما لا نهاية. وهذا يغطي >95% من الاستخدام المعتاد للبوتات.
  • مهام cron التي تُسلِّم إلى WhatsApp بعد فجوة > 24 ساعة ستفشل مع رمز خطأ Graph 131047 ("Re-engagement message").
  • النتائج غير المتزامنة لمهام delegate_task طويلة التشغيل التي تستغرق أكثر من 24 ساعة تفشل بالطريقة نفسها.
  • مشتركو webhook الذين يوجّهون أحداثًا خارجية إلى WhatsApp يفشلون عندما لا يكون المستخدم قد راسل البوت مؤخرًا.

يُنبّه Hermes الوكيلَ إلى هذه النافذة في الـ system prompt الخاص به، ليعرف النموذج أن عليه ذكرها عند جدولة رسائل مؤجلة.

دعم قوالب الرسائل (الحل البديل للإرسال خارج النافذة) غير مُنفَّذ بعد في Hermes. إذا كنت تحتاج إليه، فيُرجى فتح issue — فهو مُخطَّط له لكنه ينتظر مؤشرًا واضحًا على وجود طلب.

المحادثات الجماعية

يدعم Cloud API المجموعات بشكل محدود (وفق فئات القدرات التي تحددها Meta). ويتعامل محوّل whatsapp_cloud في Hermes حاليًا مع الرسائل المباشرة فقط في الإصدار v1. إذا كنت تحتاج إلى المحادثات الجماعية، فاستخدم جسر Baileys.

حدّ معدل الإرسال (rate limit)

الإنتاجية الافتراضية لدى Meta هي 80 رسالة/ثانية لكل رقم هاتف تجاري، مع إمكانية الترقية. ولا يفرض Hermes حاليًا هذا الحد من جهة العميل — لذا قد تصطدم عمليات الإرسال بكميات كبيرة جدًا بحد Meta.

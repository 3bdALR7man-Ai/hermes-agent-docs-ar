إعداد DingTalk

يتكامل Hermes Agent مع DingTalk (钉钉) كبوت محادثة (chatbot)، ما يتيح لك محادثة مساعد الذكاء الاصطناعي عبر الرسائل المباشرة أو المحادثات الجماعية. يتصل البوت عبر Stream Mode في DingTalk — وهو اتصال WebSocket طويل الأمد لا يتطلب عنوان URL عامًا أو خادم webhook — ويردّ برسائل منسّقة بصيغة markdown عبر session webhook API الخاصة بـ DingTalk.

قبل الإعداد، إليك ما يريد معظم الناس معرفته: كيف يتصرف Hermes بعد انضمامه إلى مساحة عمل DingTalk الخاصة بك.

كيف يتصرف Hermes

السياقالسلوك
الرسائل المباشرة (محادثة فردية 1:1)يردّ Hermes على كل رسالة، دون الحاجة إلى @mention. لكل محادثة مباشرة جلستها الخاصة.
المحادثات الجماعيةيردّ Hermes عندما تشير إليه بـ @mention. وبدون إشارة، يتجاهل Hermes الرسالة.
المجموعات المشتركة بين عدة مستخدمينافتراضيًا، يعزل Hermes سجل الجلسة لكل مستخدم داخل المجموعة. فالشخصان اللذان يتحدثان في المجموعة نفسها لا يتشاركان سجل محادثة واحدًا ما لم تعطّل ذلك صراحةً.

الخطوة 1: أنشئ تطبيق DingTalk

  1. انتقل إلى DingTalk Developer Console.
  2. سجّل الدخول بحساب مسؤول DingTalk الخاص بك.
  3. انقر على Application Development → Custom Apps → Create App via H5 Micro-App (أو Robot بحسب إصدار وحدة التحكم لديك).
  4. املأ الحقول التالية:
    • App Name: مثل Hermes Agent
    • Description: اختياري
  5. بعد الإنشاء، انتقل إلى Credentials & Basic Info للعثور على Client ID (AppKey) و Client Secret (AppSecret). انسخ القيمتين.
تُعرض بيانات الاعتماد مرة واحدة فقط

لا يُعرض Client Secret إلا مرة واحدة عند إنشاء التطبيق. إذا فقدته، فستحتاج إلى إعادة توليده. لا تشارك بيانات الاعتماد هذه علنًا أبدًا، ولا تضفها في commit إلى Git.

الخطوة 2: فعّل قدرة Robot

  1. في صفحة إعدادات تطبيقك، انتقل إلى Add Capability → Robot.
  2. فعّل قدرة الروبوت (robot).
  3. ضمن Message Reception Mode، اختر Stream Mode (موصى به — لا حاجة إلى عنوان URL عام).
نصيحة

يُعد Stream Mode الإعداد الموصى به. فهو يستخدم اتصال WebSocket طويل الأمد يبدأ من جهازك، لذا لا تحتاج إلى عنوان IP عام أو اسم نطاق أو webhook endpoint. ويعمل خلف NAT والجدران النارية وعلى الأجهزة المحلية.

الخطوة 3: اعثر على User ID الخاص بك في DingTalk

يستخدم Hermes Agent معرّف المستخدم (User ID) الخاص بك في DingTalk للتحكم في من يمكنه التفاعل مع البوت. معرّفات المستخدمين في DingTalk سلاسل أبجدية رقمية يضبطها مسؤول مؤسستك.

للعثور على معرّفك:

  1. اسأل مسؤول مؤسستك في DingTalk — إذ تُضبط معرّفات المستخدمين في وحدة تحكم مسؤول DingTalk ضمن Contacts → Members.
  2. بدلًا من ذلك، يسجّل البوت قيمة sender_id لكل رسالة واردة. شغّل gateway، وأرسل رسالة إلى البوت، ثم ابحث عن معرّفك في السجلات.

الخطوة 4: اضبط Hermes Agent

الخيار A: الإعداد التفاعلي (موصى به)

نفّذ أمر الإعداد الموجَّه:

اختر DingTalk عند المطالبة. يمكن لمعالج الإعداد إتمام التفويض عبر أحد مسارين:

  • تدفق الجهاز عبر رمز QR (موصى به). امسح رمز QR الذي يُطبع في الطرفية باستخدام تطبيق DingTalk على الهاتف — فتُعاد قيمتا Client ID و Client Secret تلقائيًا وتُكتبان في ~/.hermes/.env، دون الحاجة إلى زيارة وحدة تحكم المطوّرين.
  • اللصق اليدوي. إذا كانت لديك بيانات الاعتماد مسبقًا (أو لم يكن مسح رمز QR مناسبًا)، فالصق Client ID و Client Secret ومعرّفات المستخدمين المسموح لهم عند المطالبة.
إفصاح بشأن علامة openClaw التجارية

نظرًا لأن قيمة verification_uri_complete في DingTalk مثبّتة برمجيًا على هوية openClaw في طبقة API، فإن رمز QR يمنح التفويض حاليًا تحت سلسلة المصدر openClaw إلى أن تسجّل Alibaba / DingTalk-Real-AI قالبًا خاصًا بـ Hermes من جهة الخادم. هذه مجرد طريقة عرض DingTalk لشاشة الموافقة — فالبوت الذي تنشئه ملكك بالكامل وخاص بالمستأجر (tenant) الخاص بك.

الخيار B: الإعداد اليدوي

أضف ما يلي إلى ملف ~/.hermes/.env:

إعدادات سلوك اختيارية في ~/.hermes/config.yaml:

  • group_sessions_per_user: true يُبقي سياق كل مشارك معزولًا داخل المحادثات الجماعية المشتركة
  • require_mention: true يمنع البوت من الرد على كل رسالة في المجموعة — فلا يجيب إلا عندما يشير إليه أحدهم بـ @mention
  • allowed_users ضمن dingtalk.extra بديل لـ DINGTALK_ALLOWED_USERS؛ اضبط أحدهما فقط (إذا ضُبط كلاهما، فلن يُصرَّح إلا للمستخدمين الموجودين في القائمتين معًا)

استكشاف الأخطاء وإصلاحها

البوت لا يردّ على الرسائل

السبب: قدرة الروبوت غير مفعّلة، أو أن DINGTALK_ALLOWED_USERS لا يتضمن User ID الخاص بك.

الحل: تحقّق من تفعيل قدرة الروبوت في إعدادات تطبيقك ومن اختيار Stream Mode. وتحقّق من وجود User ID الخاص بك في DINGTALK_ALLOWED_USERS. ثم أعد تشغيل gateway.

الخطأ "dingtalk-stream not installed"

السبب: الحزمة dingtalk-stream الخاصة بـ Python غير مثبّتة.

الحل: ثبّتها:

الخطأ "DINGTALK_CLIENT_ID and DINGTALK_CLIENT_SECRET required"

السبب: بيانات الاعتماد غير مضبوطة في البيئة أو في ملف .env.

الحل: تحقّق من ضبط DINGTALK_CLIENT_ID و DINGTALK_CLIENT_SECRET بشكل صحيح في ~/.hermes/.env. قيمة Client ID هي AppKey، وقيمة Client Secret هي AppSecret من DingTalk Developer Console.

انقطاع Stream / حلقات إعادة الاتصال

السبب: عدم استقرار الشبكة، أو صيانة منصة DingTalk، أو مشكلات في بيانات الاعتماد.

الحل: يعيد المحوّل (adapter) الاتصال تلقائيًا مع تراجع أسّي (exponential backoff) (2s → 5s → 10s → 30s → 60s). تحقّق من صلاحية بيانات الاعتماد ومن أن تطبيقك لم يُعطَّل. وتأكد من أن شبكتك تسمح باتصالات WebSocket الصادرة.

البوت غير متصل

السبب: gateway الخاص بـ Hermes لا يعمل، أو فشل في الاتصال.

الحل: تحقّق من أن hermes gateway قيد التشغيل. راجع مخرجات الطرفية بحثًا عن رسائل الخطأ. المشكلات الشائعة: بيانات اعتماد خاطئة، أو تطبيق معطَّل، أو عدم تثبيت dingtalk-stream أو httpx.

الخطأ "No session_webhook available"

السبب: حاول البوت الرد لكنه لا يملك عنوان URL لـ session webhook. يحدث ذلك عادةً إذا انتهت صلاحية webhook أو أُعيد تشغيل البوت بين استلام الرسالة وإرسال الرد.

الحل: أرسل رسالة جديدة إلى البوت — فكل رسالة واردة توفّر session webhook جديدًا للردود. هذا قيد طبيعي في DingTalk؛ إذ لا يستطيع البوت الرد إلا على الرسائل التي استلمها مؤخرًا.

الأمان

تحذير

اضبط دائمًا DINGTALK_ALLOWED_USERS لتقييد من يمكنه التفاعل مع البوت. بدونه، يرفض gateway جميع المستخدمين افتراضيًا كإجراء احترازي. لا تُضف إلا معرّفات مستخدمين تثق بهم — فالمستخدمون المصرّح لهم يملكون وصولًا كاملًا إلى قدرات الوكيل، بما في ذلك استخدام الأدوات والوصول إلى النظام.

لمزيد من المعلومات حول تأمين نشر Hermes Agent، راجع دليل الأمان.

ملاحظات

  • Stream Mode: لا حاجة إلى عنوان URL عام أو اسم نطاق أو خادم webhook. يبدأ الاتصال من جهازك عبر WebSocket، لذا يعمل خلف NAT والجدران النارية.
  • AI Cards: يمكن اختياريًا الرد ببطاقات AI Cards غنية بدلًا من markdown العادي. اضبطها عبر card_template_id.
  • تفاعلات الإيموجي: تفاعلات 🤔Thinking/🥳Done تلقائية لإظهار حالة المعالجة.
  • ردود Markdown: تُنسَّق الردود بصيغة markdown الخاصة بـ DingTalk لعرض نص منسّق.
  • دعم الوسائط: تُستخرج الصور والملفات الموجودة في الرسائل الواردة تلقائيًا، ويمكن معالجتها بأدوات الرؤية (vision).
  • إزالة تكرار الرسائل: يزيل المحوّل الرسائل المكرّرة ضمن نافذة زمنية مدتها 5 دقائق لتجنّب معالجة الرسالة نفسها مرتين.
  • إعادة الاتصال التلقائية: إذا انقطع اتصال stream، يعيد المحوّل الاتصال تلقائيًا مع تراجع أسّي.
  • حدّ طول الرسالة: تُقيَّد الردود بحدّ أقصى 20,000 حرف لكل رسالة، وتُقتطع الردود الأطول.

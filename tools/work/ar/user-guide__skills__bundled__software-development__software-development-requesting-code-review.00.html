التحقق من الكود قبل الالتزام (Pre-Commit)

خط أنابيب تحقق آلي قبل وصول الكود. فحوصات ثابتة (static)، وبوابات جودة واعية بخط الأساس (baseline)، و subagent مراجع مستقل، وحلقة إصلاح تلقائي.

المبدأ الأساسي: لا يجب أن يراجع أي وكيل عمله بنفسه. السياق الجديد يجد ما فاتك.

متى تستخدمها

  • بعد تنفيذ ميزة أو إصلاح خطأ، وقبل git commit أو git push
  • عندما يقول المستخدم «commit» أو «push» أو «ship» أو «done» أو «verify» أو «review before merge»
  • بعد إكمال مهمة بتعديل ملفين أو أكثر في مستودع git
  • بعد كل مهمة في subagent-driven-development (المراجعة ذات المرحلتين)

تخطَّها من أجل: التغييرات المقتصرة على التوثيق، أو تعديلات الإعدادات الصرفة، أو عندما يقول المستخدم «skip verification».

هذه المهارة مقابل github: هذه المهارة تتحقق من تغييراتك أنت قبل الالتزام. أما github فتراجع طلبات سحب (PR) أشخاص آخرين على GitHub بتعليقات مضمّنة.

الخطوة 1 — احصل على diff

إن كانت فارغة، جرّب git diff ثم git diff HEAD~1 HEAD.

إذا كانت git diff --cached فارغة بينما يُظهر git diff تغييرات، أخبر المستخدم بتنفيذ git add <files> أولًا. وإذا ظلت فارغة، شغّل git status — لا شيء ليُتحقّق منه.

الخطوة 4 — قائمة تحقق للمراجعة الذاتية

فحص سريع قبل إرسال المهمة إلى المراجع:

  • لا أسرار أو مفاتيح API أو بيانات اعتماد مضمّنة في الكود مباشرة
  • التحقق من صحة المدخلات التي يقدّمها المستخدم
  • استعلامات SQL تستخدم عبارات ذات معاملات (parameterized)
  • عمليات الملفات تتحقق من المسارات (بلا traversal)
  • الاستدعاءات الخارجية لديها معالجة أخطاء (try/catch)
  • لا يوجد print/console.log للتصحيح متروك في الكود
  • لا يوجد كود معلَّق (commented-out)
  • الكود الجديد لديه اختبارات (إن وجدت مجموعة اختبارات)

الخطوة 5 — subagent مراجع مستقل

استدعِ delegate_task مباشرة — فهي غير متاحة داخل execute_code أو السكربتات.

يحصل المراجع فقط على الـ diff ونتائج الفحص الثابت. لا سياق مشترك مع المنفّذ. فشل بشكل افتراضي (fail-closed): استجابة غير قابلة للتحليل = فشل.

التكامل مع المهارات الأخرى

subagent-driven-development: شغّل هذه المهارة بعد كل مهمة كبوابة جودة. تعتمد المراجعة ذات المرحلتين (مطابقة المواصفات + جودة الكود) على خط الأنابيب هذا.

test-driven-development: يتحقق خط الأنابيب هذا من اتّباع انضباط TDD — وجود اختبارات، نجاح الاختبارات، عدم وجود تراجعات (regressions).

plan: يتحقق من مطابقة التنفيذ لمتطلبات الخطة.

مزالق شائعة

  • diff فارغ — تحقّق من git status، وأخبر المستخدم أنه لا يوجد ما يُتحقّق منه
  • ليس مستودع git — تخطَّ ذلك وأخبر المستخدم
  • diff كبير (أكثر من 15 ألف حرف) — قسّمه حسب الملف، وراجع كل ملف على حدة
  • delegate_task يعيد استجابة ليست JSON — أعد المحاولة مرة واحدة بـ prompt أكثر صرامة، ثم اعتبرها فشلًا
  • إيجابيات كاذبة (false positives) — إذا رصد المراجع شيئًا مقصودًا، دوّن ذلك في prompt الإصلاح
  • لم يُعثر على إطار اختبار — تخطَّ فحص التراجع، ويستمر تنفيذ حكم المراجع رغم ذلك
  • أدوات linting غير مثبّتة — تخطَّ ذلك الفحص بصمت، دون فشل
  • الإصلاح التلقائي يُدخل مشكلات جديدة — يُحتسب كفشل جديد، وتستمر الدورة

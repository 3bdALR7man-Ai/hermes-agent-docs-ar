تنفيذ الكود (Programmatic Tool Calling)

تتيح أداة execute_code للوكيل كتابة سكربتات Python تستدعي أدوات Hermes برمجيًا، فتختصر سير العمل متعدد الخطوات في دور LLM واحد. يعمل السكربت في عملية ابنة على مضيف الوكيل، ويتواصل مع Hermes عبر RPC من خلال Unix domain socket.

آلية العمل

  1. يكتب الوكيل سكربت Python باستخدام from hermes_tools import ...
  2. يولّد Hermes وحدة بديلة (stub) باسم hermes_tools.py تحتوي على دوال RPC
  3. يفتح Hermes مقبس Unix domain socket ويبدأ خيطًا (thread) للاستماع إلى RPC
  4. يعمل السكربت في عملية ابنة — وتنتقل استدعاءات الأدوات عبر المقبس عائدةً إلى Hermes
  5. لا تُعاد إلى LLM إلا مخرجات print() الخاصة بالسكربت؛ ولا تدخل نتائج الأدوات الوسيطة إلى context window أبدًا

الأدوات المتاحة داخل السكربتات: web_search، web_extract، read_file، write_file، search_files، patch، terminal (في المقدمة فقط).

متى يستخدم الوكيل هذه الأداة

يستخدم الوكيل execute_code عندما يكون هناك:

  • 3 استدعاءات أدوات أو أكثر بينها منطق معالجة
  • ترشيح بيانات بالجملة أو تفرّع شرطي
  • حلقات تكرار على النتائج

الفائدة الأساسية: لا تدخل نتائج الأدوات الوسيطة إلى context window أبدًا — ولا يعود إلا ناتج print() النهائي، مما يقلّل استهلاك الـ tokens بشكل كبير.

وضع التنفيذ

لأداة execute_code وضعا تنفيذ يتحكم فيهما code_execution.mode في ~/.hermes/config.yaml:

الوضعمجلد العملمفسّر Python
project (الافتراضي)مجلد العمل الخاص بالجلسة (كما في terminal())مفسّر python النشط من VIRTUAL_ENV / CONDA_PREFIX، مع الرجوع إلى مفسّر python الخاص بـ Hermes احتياطيًا
strictمجلد تجهيز مؤقت معزول عن مشروع المستخدمsys.executable (مفسّر python الخاص بـ Hermes)

متى تُبقيه على project: عندما تريد أن تعمل import pandas أو from my_project import foo أو المسارات النسبية مثل open(".env") بالطريقة نفسها التي تعمل بها في terminal(). وهذا ما تريده في أغلب الأحيان.

متى تحوّله إلى strict: عندما تحتاج إلى أقصى قدر من قابلية إعادة الإنتاج — أي تريد المفسّر نفسه في كل جلسة بغضّ النظر عن الـ venv الذي فعّله المستخدم، وتريد عزل السكربتات عن شجرة المشروع (دون خطر قراءة ملفات المشروع عن طريق الخطأ عبر مسار نسبي).

السلوك الاحتياطي في وضع project: إذا كان VIRTUAL_ENV / CONDA_PREFIX غير مضبوط، أو معطوبًا، أو يشير إلى Python أقدم من 3.8، فإن آلية التحديد ترجع بسلاسة إلى sys.executable — فلا تترك الوكيل أبدًا دون مفسّر يعمل.

الثوابت الحرجة أمنيًا متطابقة في كلا الوضعين:

  • تنقية البيئة (إزالة مفاتيح API والـ tokens وبيانات الاعتماد)
  • قائمة الأدوات المسموح بها (لا تستطيع السكربتات استدعاء execute_code تكراريًا، ولا delegate_task، ولا أدوات MCP)
  • حدود الموارد (المهلة، وسقف stdout، وسقف استدعاءات الأدوات)

تبديل الوضع يغيّر مكان تشغيل السكربتات والمفسّر الذي يشغّلها، لا بيانات الاعتماد التي يمكنها رؤيتها أو الأدوات التي يمكنها استدعاؤها.

الحالة بين الاستدعاءات (نواة الجلسة)

على terminal backend المحلي، لا تبدأ execute_code مفسّرًا جديدًا مع كل استدعاء. فلكل جلسة نواة (kernel) Python دائمة، لذا تكون المتغيرات والاستيرادات والبيانات المحمّلة في استدعاء ما متاحةً في الاستدعاء التالي. ويمكن للوكيل تحميل مجموعة بيانات مرة واحدة والاستعلام عنها عبر عدة أدوار بدلًا من إعادة قراءتها في كل مرة. ويحصل كل subagent على نواته الخاصة؛ ولا تُشارك النوى بين الجلسات أبدًا.

ما يُنهي النواة:

  • انتهاء المهلة أو المقاطعة. الخلية التي تبلغ المهلة (أو تُقاطَع) تُنهي عملية النواة وتُفقد حالتها عن قصد؛ وتذكر النتيجة ذلك، ويبدأ الاستدعاء التالي نواة جديدة.
  • reset=true. يمكن للوكيل تمرير reset: true لتجاهل حالة النواة والبدء من جديد. وهذه أيضًا طريقة التقاط تغييرات البيئة: فبيئة النواة تُجمَّد عند تشغيلها، لذا يبقى المتغير المُضاف حديثًا إلى قائمة السماح بالتمرير غير مرئي حتى تُعاد ضبط النواة.
  • مهلة الخمول والإخلاء. تموت النوى مع الجلسة، أو بعد code_execution.kernel_idle_timeout ثانية من الخمول (الافتراضي 1800)، أو عندما يتجاوز عدد النوى الحية code_execution.max_session_kernels (الافتراضي 4) فتُخلى أقدمها.

الغلاف الأمني هو نفسه كما في السكربت أحادي التشغيل: إذ تنطبق تنقية البيئة، وقائمة الأدوات المسموح بها، وميزانية الأدوات لكل استدعاء على كل خلية، ويُعاد ربط صلاحية استدعاء الأدوات (الموافقات، والجلسة، وقائمة السماح) عند كل خلية.

الـ backends البعيدة (Docker و SSH و Modal) تشغّل نواة جلسة بعيدة بالعقد نفسه. وإذا تعذّر تشغيل النواة على الـ backend، يرجع Hermes إلى تشغيل كل استدعاء بوصفه سكربتًا مستقلًا ويذكر ذلك في النتيجة.

المخرجات الكبيرة. تُعرض مخرجات stdout التي تتجاوز 50 KB بعرض البداية والنهاية ضمن النتيجة، ويُحفظ النص الكامل تحت ~/.hermes/cache/exec/ مع تضمين المسار في النتيجة، لكي يتمكن الوكيل من تصفّحه باستخدام read_file بدلًا من إعادة تشغيل السكربت.

كيف تعمل استدعاءات الأدوات داخل السكربتات

عندما يستدعي سكربتك دالة مثل web_search("query"):

  1. يُسلسَل الاستدعاء إلى JSON ويُرسل عبر Unix domain socket إلى العملية الأم
  2. تمرّر العملية الأم الاستدعاء عبر المعالج القياسي handle_function_call
  3. تُعاد النتيجة عبر المقبس
  4. تُعيد الدالة النتيجة بعد تحليلها

وهذا يعني أن استدعاءات الأدوات داخل السكربتات تتصرف تمامًا مثل استدعاءات الأدوات العادية — بحدود المعدل نفسها، ومعالجة الأخطاء نفسها، والقدرات نفسها. القيد الوحيد هو أن terminal() يعمل في المقدمة فقط (دون المعاملين background أو pty).

معالجة الأخطاء

عندما يفشل سكربت، يتلقى الوكيل معلومات خطأ منظَّمة:

  • رمز خروج غير صفري: يُضمَّن stderr في المخرجات فيرى الوكيل الـ traceback كاملًا
  • انتهاء المهلة: يُنهى السكربت ويرى الوكيل "Script timed out after 300s and was killed."
  • المقاطعة: إذا أرسل المستخدم رسالة جديدة أثناء التنفيذ، يُنهى السكربت ويرى الوكيل [execution interrupted — user sent a new message]
  • حد استدعاءات الأدوات: عند بلوغ حد الـ 50 استدعاءً، تُعيد استدعاءات الأدوات اللاحقة رسالة خطأ

تتضمن الاستجابة دائمًا status (success/error/timeout/interrupted)، و output، و tool_calls_made، و duration_seconds.

الأمان

نموذج الأمان

تعمل العملية الابنة في بيئة بالحد الأدنى. تُزال مفاتيح API والـ tokens وبيانات الاعتماد افتراضيًا. ويصل السكربت إلى الأدوات حصريًا عبر قناة RPC — ولا يستطيع قراءة الأسرار من متغيرات البيئة ما لم يُسمح بذلك صراحةً.

تُستبعد متغيرات البيئة التي تحتوي أسماؤها على KEY أو TOKEN أو SECRET أو PASSWORD أو CREDENTIAL أو PASSWD أو AUTH. ولا تُمرَّر إلا متغيرات النظام الآمنة (PATH، HOME، LANG، SHELL، PYTHONPATH، VIRTUAL_ENV، إلخ).

تمرير متغيرات البيئة الخاصة بالمهارات

عندما تُصرّح مهارةٌ عن required_environment_variables في الـ frontmatter الخاص بها، فإن هذه المتغيرات تُمرَّر تلقائيًا إلى كلٍّ من العمليات الأبناء لـ execute_code و terminal بعد تحميل المهارة. يتيح ذلك للمهارات استخدام مفاتيح API المُصرَّح عنها دون إضعاف الوضع الأمني للكود العشوائي.

لحالات الاستخدام غير المرتبطة بالمهارات، يمكنك إضافة المتغيرات صراحةً إلى قائمة السماح في config.yaml:

راجع دليل الأمان للاطلاع على التفاصيل الكاملة.

متغيرات HERMES_* في العملية الابنة

لا تتلقى العملية الابنة إلا مجموعة صغيرة وثابتة من متغيرات HERMES_* التشغيلية المحددة بأسمائها الدقيقة:

  • HERMES_HOME
  • HERMES_PROFILE
  • HERMES_CONFIG
  • HERMES_ENV

(إضافةً إلى HERMES_RPC_DIR / HERMES_RPC_SOCKET / TZ / HOME، التي يحقنها Hermes صراحةً لكي تعمل قناة RPC).

تغيير في السلوك

كانت الإصدارات السابقة تمرّر أي متغير يبدأ اسمه بـ HERMES_ إلى العملية الابنة. وقد أُزيلت هذه البادئة الواسعة لتعزيز الأمان: إذ كان يمكن أن تتسرّب إعدادات تحمل أسماء HERMES_* ولا تطابق أي جزء نصي يدل على سرّ (مثل HERMES_BASE_URL أو HERMES_KANBAN_DB أو endpoint من نوع HERMES_*_WEBHOOK) إلى كود عشوائي يعمل في sandbox.

إذا كان سكربت execute_code — أو وحدة من مستودع/إضافة يستوردها عند الاستيراد — يعتمد على متغير HERMES_* خارج الأسماء التشغيلية الأربعة المذكورة أعلاه، فسيجد ذلك المتغير الآن غير مضبوط في العملية الابنة. هذا الإسقاط مقصود، وليس خطأً برمجيًا.

الحل البديل — أعِد إدراج المتغير صراحةً. يمرّر كلا المسارين المتغيرَ إلى العمليات الأبناء لكلٍّ من execute_code وكذلك terminal، ولا يُضعف أيٌّ منهما ضمان إزالة الأسرار (فبيانات اعتماد المزوّدين التي يديرها Hermes لا يمكن السماح بها مجددًا بهذه الطريقة أبدًا):

  1. لكل جهاز، في config.yaml — أضف اسم المتغير الدقيق إلى قائمة السماح بالتمرير:

  2. لكل مهارة، في الـ frontmatter الخاص بالمهارة — صرّح عنه لكي يُسجَّل تلقائيًا كلما حُمّلت تلك المهارة:

التشخيص. عندما تُسقط العملية الابنة متغيرًا واحدًا أو أكثر من متغيرات HERMES_* غير المدرجة في قائمة السماح، يُصدر Hermes سجلًا من سطر واحد بمستوى debug يسمّيها ويشير إلى منفذ الخروج env_passthrough. شغّل مع تفعيل سجلات التصحيح (hermes logs --level DEBUG، أو راجع ~/.hermes/logs/agent.log) وابحث عن execute_code: dropped N non-allowlisted HERMES_* var(s) إذا تصرّف سكربت كما لو أن متغير HERMES_* مفقود.

يكتب Hermes دائمًا السكربت ووحدة RPC البديلة المولَّدة تلقائيًا hermes_tools.py في مجلد تجهيز مؤقت يُنظَّف بعد التنفيذ. في وضع strict يعمل السكربت هناك أيضًا؛ أما في وضع project فيعمل في مجلد العمل الخاص بالجلسة (ويبقى مجلد التجهيز ضمن PYTHONPATH لكي تظل الاستيرادات قابلة للتحديد). وتعمل العملية الابنة في مجموعة عمليات خاصة بها لكي يمكن إنهاؤها بشكل نظيف عند انتهاء المهلة أو المقاطعة.

دعم المنصات

تنفيذ الكود متاح على Linux و macOS و Windows. على Linux و macOS تستخدم قناة RPC مقبس Unix domain socket؛ أما على Windows، حيث لا يُعتمد على AF_UNIX، فيرجع Hermes تلقائيًا إلى مقبس TCP على واجهة loopback لنقل RPC الخاص بالـ sandbox. وتستخدم terminal backends البعيدة (Docker/SSH/Modal/إلخ) بدلًا من ذلك نقل RPC قائمًا على الملفات، وتتطلب إضافةً إلى ذلك وجود Python 3 داخل الـ backend.

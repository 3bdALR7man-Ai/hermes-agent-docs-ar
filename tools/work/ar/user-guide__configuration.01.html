إعدادات terminal backend

يدعم Hermes سبعة terminal backends. يحدّد كل واحد منها المكان الذي تُنفَّذ فيه فعليًا أوامر shell الخاصة بالوكيل — جهازك المحلي، أو حاوية Docker، أو خادم بعيد عبر SSH، أو sandbox سحابي من Modal (مباشرة أو عبر gateway المُدار من Nous)، أو workspace من Daytona، أو Vercel Sandbox، أو حاوية Singularity/Apptainer.

يتحكّم terminal.temp_dir في مكان وضع Hermes للعناصر المؤقتة للجلسة على الـ backend المحلي — سجلات/pid/ملفات خروج العمليات الخلفية، وsandboxes تنفيذ الكود، ونتائج الأدوات المُنسكبة (spilled). عندما تكون فارغة (الوضع الافتراضي)، يحترم Hermes أي قيمة صريحة لـ TMPDIR/TMP/TEMP من البيئة، وإلا يستخدم دليلًا مُدارًا على تخزين حقيقي في ~/.hermes/cache/terminal بدلًا من /tmp — ففي كثير من التوزيعات (توزيعات مبنية على Arch خصوصًا) يكون /tmp عبارة عن tmpfs صغير مدعوم بالذاكرة العشوائية يمكن أن تملأه عناصر جلسة Hermes تحت الحمل. يُقلَّم الدليل المُدار تلقائيًا: تُكنَس العناصر الأقدم من 72 ساعة كل ساعة عبر أعمال صيانة الـ gateway، ومرة واحدة لكل عملية في التثبيتات القائمة على CLI فقط. اضبط temp_dir على مسار مطلق موجود لإعادة توجيه العناصر المؤقتة للجلسة إلى أي مكان آخر؛ لا تُقلَّم المسارات التي يضبطها المستخدم تلقائيًا أبدًا.

يتحكّم terminal.font_family في الطرفية المضمَّنة في Hermes Desktop. يقبل إما اسم عائلة خط مثبَّتة محليًا (على سبيل المثال MesloLGS NF) أو مجموعة خطوط CSS. يُلحق Hermes مجموعة JetBrains Mono المضمَّنة كخيار احتياطي، وتُبقي القيمة الفارغة على الافتراضي. يمكنك تعديل نفس هذا الإعداد المحدد النطاق بمستوى profile في Settings → Appearance → Terminal Font؛ ولا حاجة لتنزيل من Google Fonts أو صلاحية خطوط نظام.

بالنسبة إلى sandboxes السحابية مثل Modal وDaytona وVercel Sandbox، تعني container_persistent: true أن Hermes سيحاول الحفاظ على حالة نظام الملفات عبر إعادة إنشاء الـ sandbox. لا يَعِد ذلك بأن نفس الـ sandbox الحي، أو نفس فضاء PID، أو نفس العمليات الخلفية ستظل تعمل لاحقًا.

الـ Backend المحلي

الافتراضي. تُنفَّذ الأوامر مباشرة على جهازك دون أي عزل. لا حاجة لأي إعداد خاص.

افتراضيًا، تحتفظ العمليات الفرعية للأدوات المحلية بـ HOME الفعلي لمستخدم نظام التشغيل لديك. يتيح هذا لأدوات CLI الخارجية مثل git وَssh وَgh وَaz وَnpm وClaude Code وCodex العثور على بيانات الاعتماد والإعدادات التي تستخدمها بالفعل في shell العادي لديك. لا تزال حالة Hermes محدودة النطاق بحسب profile عبر HERMES_HOME؛ فـHOME ليس الطريقة التي تختار بها الـ profiles الإعدادات أو الذاكرة أو الجلسات أو المهارات.

لا يغيّر Hermes أبدًا HOME الخاص بك على مستوى النظام، أو ملفات بدء تشغيل shell لديك، أو دليل حساب نظام التشغيل. يتحكّم هذا الإعداد فقط في البيئة الممرَّرة إلى العمليات الفرعية التي يطلقها Hermes عبر أدوات مثل terminal، والعمليات الطرفية الخلفية، وexecute_code، وعمليات ACP المساعدة.

تحذير

Backend الخاص بـ Docker

يشغّل الأوامر داخل حاوية Docker مع تقوية أمنية (إسقاط جميع الصلاحيات، ومنع تصعيد الامتيازات، وحدود عدد العمليات PID).

حاوية واحدة دائمة، مشتركة عبر عمليات Hermes. يبدأ Hermes حاوية واحدة طويلة الأمد عند أول استخدام ويوجّه كل استدعاء terminal وfile وَexecute_code عبر docker exec إلى تلك الحاوية نفسها — عبر الجلسات، و/new، و/reset، وsubagents الخاصة بـdelegate_task. تنتقل تغييرات دليل العمل، والحزم المثبَّتة، والملفات في /workspace، والعمليات الخلفية من استدعاء أداة إلى التالي، ومن عملية Hermes إلى التالية. عندما تُغلق جلسة TUI، أو تنفّذ /quit، أو تبدأ استدعاءً جديدًا لـhermes، تبقى الحاوية تعمل وتُعيد استخدامها عملية Hermes التالية عبر بحث بالتصنيفات (labels). راجع دورة حياة الحاوية أدناه لمعرفة قواعد إيقاف التشغيل الدقيقة.

وضع العزل لكل جلسة (container_persistent: false). يؤدي ضبط container_persistent: false على backend الخاص بـ Docker إلى التحوّل إلى حاوية واحدة لكل جلسة: تحصل كل محادثة (جلسة تطبيق سطح المكتب، أو محادثة gateway، أو جلسة TUI) على sandbox جديد خاص بها، يُنشأ عند أول استدعاء terminal/file لها ويُزال عند إغلاق الجلسة أو دخولها في الخمول متجاوزةً lifetime_seconds. لا شيء ينتقل بين الجلسات — لا حالة نظام ملفات، ولا mounts، ولا عمليات خلفية. مع docker_mount_cwd_to_workspace: true، لا يُركَّب سوى workspace المرفَق بتلك الجلسة في /workspace؛ وتحصل جلسة جديدة بلا دليل مرفَق على workspace فارغ بدلًا من وراثة mount الجلسة السابقة. لا تزال subagents الخاصة بـdelegate_task تشترك في حاوية الجلسة الأصل. استخدم هذا الوضع عندما يكون الـ sandbox حدًّا أمنيًا بين المحادثات؛ وأبقِ على الافتراضي true عندما تريد الحاوية المشتركة طويلة الأمد الموصوفة أعلاه.

docker_env مقابل docker_forward_env: يحقن الأول أزواج KEY=value حرفية تحدّدها في الإعدادات (تعيش القيم في config.yaml أو تُمرَّر كقاموس JSON عبر TERMINAL_DOCKER_ENV='{"DEBUG":"1"}'). أما الثاني فيوجّه قيمًا من shell لديك أو من ~/.hermes/.env، بحيث لا يظهر السرّ الفعلي في ملف الإعدادات أبدًا. استخدم docker_forward_env للـ tokens وَdocker_env للخيارات الثابتة التي تحتاجها الحاوية.

terminal.docker_extra_args (يمكن تجاوزها أيضًا عبر TERMINAL_DOCKER_EXTRA_ARGS='["--gpus=all"]') تتيح لك تمرير أعلام docker run عشوائية لا يعرضها Hermes كمفاتيح أساسية — مثل --gpus وَ--network وَ--add-host وتجاوزات بديلة لـ--security-opt، وغيرها. يجب أن يكون كل عنصر سلسلة نصية؛ وتُلحَق القائمة أخيرًا باستدعاء docker run المُجمَّع بحيث يمكنها تجاوز افتراضيات Hermes عند الحاجة. استخدمها بحذر — فالأعلام المتعارضة مع تقوية الـ sandbox (إسقاط الصلاحيات، و--user، وbind mount الـ workspace) ستُضعف العزل بصمت.

terminal.docker_network (الافتراضي true؛ متغير البيئة: TERMINAL_DOCKER_NETWORK) — اضبطها على false لتشغيل حاوية الـ sandbox بـ--network=none، مما يقطع كل خروج شبكي (egress) من أوامر الوكيل. ينطبق هذا على حاوية التنفيذ المستخدمة من قِبل terminal وَexecute_code وأدوات الملفات. وبما أن الحاويات تستمر عبر عمليات Hermes، فإن قلب هذه القيمة إلى false بينما توجد حاوية أقدم متصلة بالشبكة سيؤدي إلى إزالة تلك الحاوية وبدء حاوية جديدة معزولة عن الشبكة تمامًا (يُسجَّل تحذير)؛ وتُفقَد العمليات الخلفية التي كانت تعمل بداخلها. يُفضَّل استخدام هذا المفتاح على تمرير --network=none عبر docker_extra_args.

المتطلبات: Docker Desktop أو Docker Engine مثبَّت وقيد التشغيل. يفحص Hermes $PATH إضافة إلى مواقع تثبيت macOS الشائعة (/usr/local/bin/docker، وَ/opt/homebrew/bin/docker، وحزمة تطبيق Docker Desktop). Podman مدعوم جاهزًا: اضبط HERMES_DOCKER_BINARY=podman (أو المسار الكامل) لفرضه عند تثبيت الاثنين معًا.

دورة حياة الحاوية

تُوسَم كل حاوية يديرها Hermes بثلاث تصنيفات (labels) بحيث يمكن للعمليات اللاحقة (وحاصد العناصر اليتيمة) تحديدها:

  • hermes-agent=1 — يشير إلى أنها مُدارة من Hermes
  • hermes-task-id=<sanitized task_id> — يُستخدم كمفتاح لاستقصاء إعادة الاستخدام لكل مهمة
  • hermes-profile=<sanitized profile name> — يحدّد نطاق إعادة الاستخدام والحصاد بحسب profile Hermes النشط افتراضيًا؛ وعند ضبط docker_shared_container_key، تُستخدم قيمته المُطهَّرة بدلًا من ذلك

عند بدء التشغيل، ينفّذ Hermes docker ps --filter label=hermes-task-id=<id> --filter label=hermes-profile=<identity> ويتصل بالحاوية الموجودة عند العثور عليها. الهوية هنا هي الـ profile النشط ما لم يُدرِج docker_shared_container_key صراحةً profiles موثوقة في قيمة مشتركة. إذا كانت الحاوية exited (مثلًا بعد إعادة تشغيل خدمة Docker daemon)، تُشغَّل بـdocker start ويُعاد استخدامها — تنجو حالة نظام الملفات وأي حزم مثبَّتة، لكن لا تنجو العمليات الخلفية داخل الحاوية.

عندما تخرج عملية Hermes — عبر /quit، أو إغلاق جلسة TUI، أو إيقاف الـ gateway، أو حتى SIGKILL — يكون مسار التنظيف عملية بلا أثر (no-op) بالنسبة للحاوية في الوضع الافتراضي. تبقى الحاوية تعمل. تتصل بها عملية Hermes التالية في أجزاء من الثانية عبر استقصاء التصنيفات. هذا هو السلوك الذي يقتضيه عقد "حاوية واحدة طويلة الأمد مشتركة عبر الجلسات": إنها الطريقة الوحيدة التي تنجو بها العمليات الخلفية (مراقبو npm، وخوادم التطوير، واختبارات pytest طويلة الأمد) عبر الجلسات.

لا تُفكَّك الحاوية (تُوقَف وتُحذَف بـdocker rm -f) إلا في هذه الحالات:

المُحفِّزمتى يُفعَّل
docker_persist_across_processes: falseعزل صريح لكل عملية. كل cleanup() ينفّذ stop ثم rm -f. يطابق سلوك ما قبل issue #20561.
حاصد الخمول (lifetime_seconds، الافتراضي 300 ثانية)فقط عندما تكون البيئة persist_across_processes=false. تُترَك بيئات وضع الاستمرارية بلا أثر (no-op)؛ وتنجو الحاوية من مسح الخمول.
حاصد العناصر اليتيمة عند بدء التشغيل التالييكنس الحاويات المُوسَومة بـHermes التي حالتها Exited والأقدم من 2 × lifetime_seconds (الافتراضي 600 ثانية = 10 دقائق)، ضمن نطاق الـ profile الحالي. لا يُمَسّ الحاويات قيد التشغيل أبدًا — لسلامة العمليات المتزامنة (sibling). اضبط docker_orphan_reaper: false لتعطيله.
إجراء مباشر من المستخدمdocker rm -f، أو docker system prune، أو إعادة تشغيل Docker Desktop. لا نضبط --restart=always، لذا تترك إعادة تشغيل المضيف الحاوية بحالة Exited (تنجو طبقة CoW الخاصة بها ويُعاد استخدامها عند بدء التشغيل التالي، لكن العمليات الخلفية تختفي).

حالات حافة تستحق المعرفة:

  • قتل OOM لـ PID 1 داخل الحاوية يحوّل الحاوية إلى Exited. سيُشغّلها الاستخدام التالي بـdocker start؛ وتنجو حالة نظام الملفات، لكن لا تنجو العمليات الخلفية.
  • تبديل الـ profiles يعزل الحاويات عن بعضها — حاوية موسومة بـhermes-profile=work غير مرئية لعملية Hermes تعمل تحت hermes-profile=research. حاصد العناصر اليتيمة أيضًا محدود النطاق بحسب profile، لذا لا تُحصَد الحاويات عبر الـ profiles عرضًا، لكنها أيضًا لن تُنظَّف تلقائيًا حتى تبدأ Hermes مجددًا تحت الـ profile الأصلي الخاص بها.
  • المشاركة الصريحة عبر الـ profiles — اضبط نفس docker_shared_container_key غير الفارغ تحت terminal: للـ profiles التي تتعاون عن قصد في مساحة عمل موثوقة واحدة. يستبدل هذا فقط تصنيف هوية حاويتها؛ وتظل فحوصات توافق المهمة والخروج الشبكي (egress) والشبكة سارية. تبقى الـ profiles بلا هذا المفتاح معزولة. يُشتَق تصنيف الهوية من المفتاح مع لاحقة اختصار (digest) قصيرة، بحيث لا تتصادم المفاتيح المتشابهة الشكل (مثل team/workspace مقابل team_workspace) أبدًا في حاوية واحدة. مهم: تُنشأ الحاوية المشتركة مرة واحدة، من قِبل أي profile يبدأها أولًا — وتفوز إعدادات ذلك الـ profile من docker_image والـ volumes وحجم shm وإعدادات Docker الثابتة الأخرى، وتتصل الـ profiles اللاحقة بها كما هي؛ وتُتجاهَل الإعدادات المختلفة في ملفات إعداداتها حتى تُزال الحاوية وتُعاد إنشاؤها. ينبغي على الـ profiles التي تتشارك مفتاحًا الاتفاق على الصورة (image) والـ mounts.

تشترك subagents المتوازية المُطلَقة عبر delegate_task(tasks=[...]) في هذه الحاوية الواحدة؛ فتغييرات cd، وتعديلات البيئة، والكتابة إلى نفس المسار المتزامنة يمكن أن تتصادم. إذا احتاج subagent إلى sandbox معزول، عليه تسجيل تجاوز صورة لكل مهمة عبر register_task_env_overrides()، وهو ما تفعله تلقائيًا بيئات RL والمعايير القياسية (مثل TerminalBench2، وHermesSweEnv) لصور Docker الخاصة بكل مهمة لديها.

التقوية الأمنية:

  • --cap-drop ALL مع إعادة إضافة DAC_OVERRIDE وَCHOWN وَFOWNER فقط
  • --security-opt no-new-privileges
  • --pids-limit 256
  • tmpfs محدود الحجم لـ/tmp (512MB)، وَ/var/tmp (256MB)، وَ/run (64MB)

توجيه بيانات الاعتماد: تُحسم متغيرات البيئة المُدرَجة في docker_forward_env من بيئة shell لديك أولًا، ثم من ~/.hermes/.env. يمكن للمهارات أيضًا أن تُعلن required_environment_variables التي تُدمَج تلقائيًا.

Backend الخاص بـ SSH

يشغّل الأوامر على خادم بعيد عبر SSH. يستخدم ControlMaster لإعادة استخدام الاتصال (استمرار خمول لمدة 5 دقائق). الـ shell الدائم مفعَّل افتراضيًا — تنجو الحالة (دليل العمل، متغيرات البيئة) عبر الأوامر.

متغيرات البيئة المطلوبة:

اختياري:

المتغيرالافتراضيالوصف
TERMINAL_SSH_PORT22منفذ SSH
TERMINAL_SSH_KEY(افتراضي النظام)مسار مفتاح SSH الخاص
TERMINAL_SSH_PERSISTENTtrueتفعيل الـ shell الدائم

كيف يعمل: يتصل عند وقت التهيئة بـBatchMode=yes وَStrictHostKeyChecking=accept-new. يُبقي الـ shell الدائم على عملية bash -l واحدة حيّة على المضيف البعيد، تتواصل عبر ملفات مؤقتة. الأوامر التي تحتاج stdin_data أو sudo تعود تلقائيًا إلى الوضع الفوري (one-shot).

تمرير متغيرات المهارة/الإعدادات: المتغيرات التي تعلنها مهارة في required_environment_variables، أو التي تُدرِجها تحت terminal.env_passthrough، تُمرَّر عبر SendEnv الخاصة بـ OpenSSH — تذهب الأسماء إلى سطر أمر ssh بينما تسافر القيم في بيئة العميل، ولا تظهر أبدًا في نص الأمر البعيد. يجب أن يقبلها sshd البعيد؛ أضِفها إلى /etc/ssh/sshd_config على الخادم وأعِد تحميل sshd:

بدون AcceptEnv مطابقة، يُسقِط الخادم المتغيرات بصمت ويرى الـ shell البعيد أنها غير مضبوطة. بيانات اعتماد مزوّدي Hermes (OPENAI_API_KEY، ...) لا تُمرَّر أبدًا حتى لو أُدرِجت. راجع تمرير متغيرات البيئة (Env Var Passthrough).

Backend الخاص بـ Modal

يشغّل الأوامر في sandbox سحابي من Modal. تحصل كل مهمة على VM معزول بإعدادات قابلة للتخصيص من CPU وذاكرة وقرص. يمكن أخذ لقطة (snapshot) من نظام الملفات واستعادتها عبر الجلسات.

مطلوب: إما متغيرا البيئة MODAL_TOKEN_ID وَMODAL_TOKEN_SECRET، أو ملف إعدادات ~/.modal.toml.

الاستمرارية: عند تفعيلها، تُؤخَذ لقطة من نظام ملفات الـ sandbox عند التنظيف وتُستعاد في الجلسة التالية. تُتَتَبَّع اللقطات في ~/.hermes/modal_snapshots.json. يحافظ هذا على حالة نظام الملفات، وليس على العمليات الحية، أو فضاء PID، أو المهام الخلفية.

ملفات بيانات الاعتماد: تُركَّب تلقائيًا من ~/.hermes/ (tokens الخاصة بـ OAuth، وغيرها) وتُزامَن قبل كل أمر.

Backend الخاص بـ Daytona

يشغّل الأوامر في workspace مُدار من Daytona. يدعم الإيقاف/الاستئناف من أجل الاستمرارية.

مطلوب: متغير البيئة DAYTONA_API_KEY.

الاستمرارية: عند تفعيلها، تُوقَف الـ sandboxes (لا تُحذَف) عند التنظيف وتُستأنَف في الجلسة التالية. تتبع أسماء الـ sandboxes نمط hermes-{task_id}.

حد القرص: يفرض Daytona حدًا أقصى قدره 10 GiB. تُقيَّد الطلبات التي تتجاوز ذلك مع تحذير.

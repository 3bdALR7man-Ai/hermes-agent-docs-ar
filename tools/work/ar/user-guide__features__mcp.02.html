التصفية على مستوى كل خادم

يمكنك التحكم في الأدوات التي يضيفها كل خادم MCP إلى Hermes ، ما يتيح إدارة دقيقة لمساحة أسماء الأدوات لديك.

تعطيل خادم بالكامل

عند ضبط enabled: false، يتخطى Hermes الخادم كليًا ولا يحاول حتى الاتصال به.

قائمة سماح لأدوات الخادم

لا تُسجَّل إلا أدوات خادم MCP المذكورة.

يمكن أن تكون الإدخالات في include/exclude أيضًا أنماط glob ‏(*, ?, [...]، وتُطابَق مع مراعاة حالة الأحرف): فالنمط include: ["*_dns_*"] يسجّل كل أداة يحتوي اسمها على _dns_. أما الإدخالات العادية التي لا تتضمن محارف خاصة فتبقى مطابقة تامة. وأنماط glob هي الطريقة العملية لتصفية الخوادم التي توفّر آلاف الأدوات المولَّدة تلقائيًا للـ endpoints بحسب عائلة المنتج.

الإدخالات التي لا تحتوي على محارف glob الخاصة (*, ?, [) تُطابَق بدقة — فالإدخال docs يستبعد فقط الأداة المسمّاة docs، ولا يستبعد أبدًا docs_search.

السلوك وقت التشغيل

وقت الاكتشاف

يكتشف Hermes خوادم MCP عند بدء التشغيل ويسجّل أدواتها في سجل الأدوات المعتاد.

لا يُوصل أكثر من 4 خوادم في الوقت نفسه لكل تمريرة اكتشاف (بدء التشغيل، و /reload-mcp، ومراقب الإعدادات). ينشئ كل خادم stdio شجرة عمليات فرعية خاصة به، لذا كانت التمريرة غير المحدودة ذات الخوادم الكثيرة تطلقها كلها في اللحظة نفسها — طفرة CPU/RAM ، وفي مجموعات متعددة الـ profiles دفعة متزامنة من استدعاءات المزوّد. اضبط ذلك في config.yaml:

تعمل التمريرة ذات الخوادم الأكثر من السقف على دفعات؛ وتحتفظ كل دفعة بميزانية 120 s المعتادة (التمرير الكامل مقيد بـ 300 s)، لذا تنتهي المجموعة البطيئة لاحقًا بدل انتهاء مهلتها.

بدء كسول

يُسجّل الخادم ذو lazy: true من التخزين المؤقت للمخطط على القرص بدلًا من ذلك: تظهر أدواته في السجل فورًا، وتُنشأ العملية (أو يُوصل endpoint HTTP) عند أول استدعاء أداة. يُكتب التخزين المؤقت عند كل اتصال حي، لذا يكون التشغيل الأول لخادم جديد أو متغير فوريًا دائمًا. وتعرض اللافتة ولوحة جلسة TUI ذلك الخادم بوصفه lazy مع عدد أدواته المخزّن مؤقتًا (3 tool(s) (lazy, starts on first use)) — فهو خادم يعمل، لا خادم فاشل — ويحتسبه ملخص اكتشاف بدء التشغيل بوصفه N lazy, not spawned yet.

الاكتشاف الديناميكي للأدوات

يمكن لخوادم MCP إبلاغ Hermes عند تغيّر أدواتها المتاحة وقت التشغيل عبر إرسال إشعار notifications/tools/list_changed. وعندما يتلقى Hermes هذا الإشعار، يعيد تلقائيًا جلب قائمة أدوات الخادم ويحدّث السجل — دون الحاجة إلى تشغيل /reload-mcp يدويًا.

يفيد هذا مع خوادم MCP التي تتغير قدراتها ديناميكيًا (مثل خادم يضيف أدوات عند تحميل مخطط قاعدة بيانات جديد، أو يزيل أدوات عندما تتوقف خدمة ما عن العمل).

عملية التحديث محمية بقفل، بحيث لا تتسبب الإشعارات المتلاحقة من الخادم نفسه في عمليات تحديث متداخلة. أما إشعارات تغيّر الـ prompts والموارد (prompts/list_changed, resources/list_changed) فتُستقبل لكن لا يُتخذ بشأنها أي إجراء بعد.

إعادة التحميل

إذا غيّرت إعدادات MCP ، فاستخدم:

يعيد هذا تحميل خوادم MCP من الإعدادات ويحدّث قائمة الأدوات المتاحة. وهو أيضًا الطريقة الصريحة لإعادة فحص الأدوات المشروطة بالتوفر (Docker ، وHASS_TOKEN، و OAuth…): فمجموعة أدوات الجلسة تبقى مجمّدة فيما عدا ذلك، لذا فإن بيانات الاعتماد أو الـ daemon الذي يظهر في منتصف الجلسة لا يُلتقط إلا عند /reload-mcp, /new، أو ضغط السياق. أما تغييرات الأدوات وقت التشغيل التي يدفعها الخادم نفسه، فراجع الاكتشاف الديناميكي للأدوات أعلاه.

يراقب Messaging Gateway عامل (hermes gateway run) أيضًا config.yaml بنفسه: خلال نحو دقيقة من إزالة إدخال mcp_servers أو ضبط enabled: false، يُفك اتصال ذلك الخادم؛ ويُوصل الإدخال المضاف حديثًا. ويُعاد تلقائيًا طلب اتصال خادم فشل اتصاله الأول (مضيف غير قابل للوصول، أو خادم OAuth على جهاز دون واجهة لم يكن لديه token بعد) بحسب جدول تهدئة الاتصال (30 s ، يتضاعف حتى 10 min) بعد إصلاح السبب. لا تلزم إعادة تشغيل أو /reload-mcp كي يسري التعديل.

OAuth tokens المنتهية الصلاحية في الخلفية. لا يفتح الـ gateway أو /reload-mcp أو الفحص الذاتي الدوري لخادم معلّق متصفحًا أبدًا — فلا يوجد من يُكمل العملية. وعندما يتوقف refresh token عن العمل، يُعلَّق الخادم مع تحذير في gateway.log وتعيد التفويض مرة واحدة باستخدام hermes mcp login <server> (أو زر Authorize في Desktop/لوحة التحكم)؛ ويلتقط الخادم المعلّق الـ token الجديد عند فحصه التالي. وإلى أن تتغير ملفات الـ token، لا يعيد بدء جلسات جديدة محاولة استخدام الـ token المرفوض: الفحص الذاتي المؤقّت وحده يفعل ذلك، فلا يمكن لتفويض منتهٍ أن يُغرق token endpoint الخاص بالمزوّد بالطلبات.

خادم بعيد (HTTP) يرفض الاتصال

hermes mcp test <name> يعرض الاستجابة الفعلية للخادم. عندما لا يستطيع MCP SDK إلا ذكر Server returned an error response (استجابة 4xx/5xx لا يكون جسمها خطأ JSON-RPC)، يضيف Hermes حالة HTTP ، وعنوان URL المطلوب، وبداية جسم الاستجابة:

اقرأ الحالة والجسم أولًا: تعني 400/405 على POST initialize عادة أن endpoint لا يدعم إلا SSE (اضبط transport: sse) أو أن proxy أمامه يرفض الطلب؛ وتعني 401/403 أن token أو منح OAuth غير صحيح؛ ويعني جسم HTML أن URL يشير إلى صفحة ويب، لا endpoint MCP. hermes logs --level debug يعرض أيضًا endpoint الدقيق الذي استخدمته كل محاولة اتصال.

استجابة الخادم كبيرة جدًا

يقبل Hermes ما يصل إلى 10 MiB في استجابة HTTP واحدة، أو في حدث SSE واحد ضمن استجابة متدفقة، بحيث يتسع كتالوج tools/list كبير أو نتيجة أداة كبيرة (لقطة شاشة من محرر مثلًا). وفي نقل SSE القديم (transport: sse) تحدّد حزمة MCP SDK كل حدث بـ 1 MiB ولا تتيح رفع هذا الحد؛ وإذا كان الخادم يدعم Streamable HTTP أيضًا، فأزل transport: sse من مدخله.

الأدوات لا تظهر

الأسباب المحتملة:

  • فشل الخادم في الاتصال
  • فشل الاكتشاف
  • استبعدت إعدادات التصفية لديك الأدوات
  • القدرة المساعدة غير موجودة على ذلك الخادم
  • الخادم معطّل بواسطة enabled: false

إذا كنت تُجري التصفية عن قصد، فهذا متوقع.

لماذا لم تظهر الأدوات المساعدة للموارد أو الـ prompts ؟

لأن Hermes أصبح لا يسجّل تلك الأغلفة إلا عند تحقق الشرطين معًا:

  1. أن تسمح بها إعداداتك
  2. أن تدعم جلسة الخادم تلك القدرة فعلًا

هذا مقصود، ويُبقي قائمة الأدوات معبّرة عن الواقع بدقة.

استدعاءات الأدوات المتوازية

تعمل أدوات MCP افتراضيًا بالتتابع — أداة واحدة في كل مرة. إذا كان خادم MCP لديك يوفّر أدوات آمنة للتشغيل المتزامن (مثل الاستعلامات للقراءة فقط، أو استدعاءات API المستقلة)، فيمكنك تفعيل التنفيذ المتوازي:

عندما تكون قيمة supports_parallel_tool_calls هي true، قد ينفّذ Hermes عدة أدوات من ذلك الخادم في الوقت نفسه ضمن دفعة واحدة من استدعاءات الأدوات، تمامًا كما يفعل مع الأدوات المدمجة المخصّصة للقراءة فقط (web_search و read_file وغيرهما).

تنبيه

لا تفعّل الاستدعاءات المتوازية إلا لخوادم MCP التي تكون أدواتها آمنة للتشغيل في الوقت نفسه. إذا كانت الأدوات تقرأ وتكتب حالة مشتركة أو ملفات أو قواعد بيانات أو موارد خارجية، فراجع حالات التسابق (race conditions) في القراءة/الكتابة قبل تفعيل هذا الإعداد.

تكاليف الأدوات وحدود الإنفاق

تنفق بعض خوادم MCP أموالًا أو رصيدًا حقيقيًا مع كل استدعاء (توليد الصور والفيديو والمجسمات ثلاثية الأبعاد، وواجهات API المدفوعة). يمكن لإدخال الخادم أن يصرّح بتكلفة كل أداة وبميزانية لكل محادثة:

  • تذكر رسالة طلب الموافقة التكلفة: Costs about 20 credits. أو Costs 5-20 credits (per animation).، إضافةً إلى This chat has used about 40 credits on 'renders' (limit 100). بعد أن تنفق المحادثة شيئًا.
  • يحتفظ Hermes بإجمالي تراكمي لكل محادثة ولكل خادم، يحتسب فيه الرقم المصرَّح به (الحد الأعلى للنطاق) لكل استدعاء ذي تكلفة وافق عليه وبدأ تنفيذه. ولا تضيف الاستدعاءات المرفوضة أو المحظورة شيئًا؛ أما الاستدعاء الذي يتوقف خادمه قبل أن يتلقاه فيُحتسب مع ذلك، وهذا يميل إلى السؤال مبكرًا. يُحفظ الإجمالي في الذاكرة: فهو ميزانية لمحادثة واحدة، وليس فاتورة المورّد.
  • يتبع الإجمالي المحادثة عندما يواصلها ضغط السياق أو /branch تحت معرّف جلسة جديد. أما بدء محادثة جديدة (/new في CLI، أو محادثة Desktop جديدة) فيبدأ إجماليًا جديدًا؛ وعلى منصات المراسلة يعود الإجمالي إلى المحادثة، فيبقى قائمًا بعد /new هناك. ولكل تشغيل cron إجماليه الخاص. وإعادة تشغيل Hermes تصفّر كل الإجماليات.
  • مع spend_limit، يسأل أي استدعاء ذي تكلفة كان سيتجاوز بالمحادثة الحد المسموح قبل تنفيذه، حتى على خادم trust: full الذي لا يسأل عادةً، ويسأل كل استدعاء إضافي ذي تكلفة في تلك المحادثة مرة أخرى: لا تعرض هذه الرسالة إلا Allow Once وDeny، ولا تسكتها إجابة سابقة بـ Session أو Always للأداة. وحيث لا يوجد من يجيب (مهام cron، وhermes chat -q، وgateway بلا جهة موافقة)، يُرفض الاستدعاء دون تنفيذ ويُخبَر النموذج بألا يعيد المحاولة.
  • دون الحد، يواصل خادم trust: full تشغيل الأدوات ذات التكلفة دون سؤال؛ وفي خادم trust: untrusted يسأل كل استدعاء قادر على الكتابة أصلًا، ويحمل السؤال الآن التكلفة. وتبقى الأدوات المعلّمة بـ readOnlyHint: true دون سؤال ما لم تتطلب الميزانية ذلك.
  • يتجاوز YOLO (/yolo, --yolo) وapprovals.mode: off رسالة trust: untrusted (/yolo لتلك المحادثة، و--yolo لتلك العملية، وapprovals.mode: off لذلك الـ profile)، لكنهما لا يتجاوزان حد الإنفاق: دون الحد يعمل الاستدعاء ذو التكلفة دون سؤال، أما الاستدعاء الذي سيعبر الحد فيسأل أيضًا (أو يُرفض حيث لا يوجد من يجيب، مثل مهمة cron مع approvals.mode: off).
  • إذا كان tool_costs أو spend_limit أو cost_unit مشوّهًا، يُتخطى الخادم مع خطأ يسمّي المفتاح، فلا تُسقَط ميزانية صرّحت بها بصمت. أما مفتاح في tool_costs لا يقدّمه الخادم (خطأ إملائي، أو نسخ بادئة العرض mcp_<server>_ الخاصة بـ Hermes) فيُذكر في تحذير عند الاتصال: استخدم أسماء الأدوات الأصلية للخادم.

يمكن لـ حزمة إضافة محمولة أن تصرّح بالجدول نفسه لخادمها. وإذا أضفت إدخال mcp_servers بالاسم نفسه (مثلًا لضبط trust: full)، فتظل tool_costs وspend_limit وcost_unit الخاصة بالحزمة سارية ما لم يضبط إدخالك هذه المفاتيح بنفسه؛ وتؤدي spend_limit: 0 إلى إيقاف حد الحزمة، وتؤدي tool_costs: {} إلى إسقاط تكاليفها.

دعم MCP Elicitation

يمكن لخوادم MCP أن تطلب من المستخدم مدخلات منظّمة في منتصف استدعاء أداة عبر بروتوكول elicitation/create (mcp Python SDK ≥ 1.11.0). يوجّه Hermes طلبات الـ elicitation من نوع وضع النموذج (form-mode) عبر واجهة الموافقة الموجودة لديه — مطالبة تفاعلية في CLI/TUI، أو أزرار موافقة على منصات الـ gateway مثل Telegram و Slack — بحيث يصل الطلب إليك أينما كانت الجلسة. وتغطي كل إجابة ذلك الطلب وحده، لذا لا تعرض الرسالة إلا Allow Once وDeny. ولا يجيب YOLO وapprovals.mode: off عنك على هذه الطلبات: فالخادم يطرح عليك سؤالًا، ولا يطلب إذنًا. أما طلبات الـ elicitation من نوع وضع URL (URL-mode) (حيث يوجّهك الخادم إلى عنوان URL خارجي) فتُرفض لأنها غير مدعومة.

الـ Elicitation مفعّل افتراضيًا لكل خادم. اضبطه تحت المفتاح elicitation المفتاح:

تطابق المهلة الافتراضية البالغة 5 دقائق القيمة الافتراضية لموافقات الـ gateway ، حتى يتسع الوقت للمستخدمين على الواجهات غير المتزامنة للرد قبل أن يستسلم الخادم. وتُتتبَّع المقاييس لكل خادم (الطلبات، والمقبولة، والمرفوضة، والأخطاء) في المعالج.

MCP Events (تجريبي)

يمكن لبعض خوادم MCP إخطار الوكيل عند حدوث شيء في المصدر (بريد جديد، أو حادثة، أو عنصر جديد في خلاصة) عبر دوال events/* في مخطط تصميم أحداث MCP. لا يزال المقترح مسودة لدى مجموعة عمل. ينفّذ Hermes وضع التسليم عبر webhook: يرسل الخادم كل حدث بـ POST إلى مستمع webhook الخاص بالـ gateway، ويبدأ كل حدث تشغيلًا للوكيل كأي مسار webhook آخر.

فعّله لكل خادم على حدة، وأخبر Hermes بعنوان HTTPS العام لمستمع webhook (ترفض الخوادم عناوين callback بـ HTTP العادي، لذا ضع reverse proxy ينهي TLS أو نفقًا (tunnel) أمام المنفذ 8644):

يحصل الخادم حينئذٍ على ثلاث أدوات مساعدة إضافية:

  • list_event_types: أنواع الأحداث التي يقدّمها الخادم، واشتراكاتك الحالية فيها
  • subscribe_event: اشترك بوسائط الحدث، وما يجب فعله عند وصوله (instructions، حتى 2000 حرف) ووجهة نتيجة كل تشغيل (deliver، deliver_chat_id). يُطلب منك الموافقة على كل اشتراك، لأنه يبدأ تشغيلات للوكيل دون إشراف؛ وتعرض الموافقة التعليمات والوجهة كاملتين.
  • unsubscribe_event: إلغاء اشتراك

يُخزَّن كل اشتراك بوصفه مسار webhook ديناميكيًا (يعرضه hermes webhook list) له سرّ توقيع whsec_ خاص به؛ ويُحفظ المنح (grant) ومؤشر إعادة التشغيل (replay cursor) بجانبه في mcp_event_subscriptions.json، فلا يتغير المسار نفسه إلا عند إعادة الاشتراك بتعليمات مختلفة أو بوجهة مختلفة. يجيب Hermes عن تحدّي التحقق الموقَّع الذي يرسله الخادم، ويزيل تكرار الأحداث بحسب eventId، ويجدّد الاشتراك قبل انتهاء المدة التي منحها الخادم ما دام اتصال MCP قائمًا (ومرة أخرى كلما أعاد الاتصال). ومع lazy: true أو idle_timeout_seconds لا يكون الاتصال قائمًا دائمًا، لذا قد ينقطع اشتراك إلى أن يعيد الاتصال التالي تسجيله. أما التجديد الذي يرفضه الخادم نهائيًا (سُحب الوصول، أو أُزيل نوع الحدث، أو لم تعد الوسائط صالحة) فيزيل المسار؛ وتُعاد محاولة الإخفاقات الأخرى مع تأخير تصاعدي (back-off). يؤدي إيقاف المسار في لوحة webhook إلى انقطاع الاشتراك، وإعادة تشغيله تعيد الاشتراك. وإذا أنهى الخادم اشتراكًا، يزيل Hermes المسار ويخبر وجهة deliver. لا تصل الأحداث إلا أثناء تشغيل hermes gateway run. تصل حمولة الحدث إلى التشغيل كاملة، حتى 32,000 حرف من JSON، مع ملاحظة عند اقتطاعها. حمولات الأحداث بيانات خارجية: تستخدم تشغيلات الأحداث مجموعة أدوات webhook المقيَّدة نفسها التي تستخدمها مسارات webhook الأخرى. ينطبق حدّ المعدل لكل مسار في المستمع (platforms.webhook.extra.rate_limit، وقيمته الافتراضية 30 في الدقيقة) على تسليمات الأحداث أيضًا؛ ارفعه لنوع حدث كثير النشاط، فقد لا يعيد الخادم محاولة تسليم مرفوض.

غير مدعوم بعد: وضعا التسليم poll وpush، والاشتراكات المنفَّذة من profile ثانوي ضمن gateway.multiplex_profiles.

تشغيل Hermes كخادم MCP

يمكن لـ Hermes أيضًا أن يكون خادم MCP، فيتمكن Claude Code وClaude Desktop وCursor وCodex أو أي عميل MCP من سرد محادثات المراسلة لديك وقراءتها، وانتظار الرسائل الجديدة وإرسال الرسائل عبر كل منصة متصل بها Hermes، واستدعاء أدوات Hermes الخاصة بالويب والمتصفح والرؤية وتوليد الصور والمهارات وTTS اختياريًا. ويأتي هذا في صورة إضافة mcp-serve الرسمية:

كان مدمجًا سابقًا بالصيغة hermes mcp serve. على عميل MCP المضبوط بـ "args": ["mcp", "serve"] أن يغيّرها إلى ["mcp-serve"]؛ أما أسماء الأدوات ومعاملاتها فلم تتغير، ويطبع hermes mcp serve الآن الصيغة الجديدة وسطر التثبيت. وتوثَّق الأدوات والوضع --tools وحدود الأمان الخاصة به في README الخاص بالإضافة.

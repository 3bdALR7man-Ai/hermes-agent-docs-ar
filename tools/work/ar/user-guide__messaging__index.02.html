إدارة الخدمة

Linux (systemd)

استخدم خدمة المستخدم على الحواسيب المحمولة وأجهزة التطوير. واستخدم خدمة النظام على خوادم VPS أو الأجهزة المضيفة بلا واجهة (headless) التي يجب أن تعود للعمل عند الإقلاع دون الاعتماد على خاصية linger في systemd.

لا تُضف drop-in مخصصًا لإنهاء العملية عبر ExecStopPost

الوحدة (unit) التي يثبّتها Hermes توقف gateway بشكل نظيف بالفعل باستخدام KillMode=mixed + KillSignal=SIGTERM، وتستخدم Restart=always مع RestartForceExitStatus كي تُعاد عمليات التحديث و/restart بشكل صحيح. لا تُضف drop-in لـ systemd مثل ExecStopPost=/bin/kill -9 $MAINPID — إذ يُنفَّذ ExecStopPost عند كل إيقاف، بما في ذلك عمليات إعادة التشغيل النظيفة، فيرسل SIGKILL إلى النسخة التي أُنشئت للتو قبل أن تستقر، ثم يعيد Restart=always تشغيلها فورًا. والنتيجة حلقة لا نهائية من إعادة التشغيل (وعلى Telegram، سيل من رسائل إعادة التشغيل). وإذا كنت قد أضفت drop-in كهذا، فأزله: systemctl --user edit hermes-gateway (أو sudo systemctl edit hermes-gateway لخدمة النظام) واحذف سطر ExecStopPost، ثم نفّذ systemctl --user daemon-reload.

تنفيذ systemctl restart / stop مباشرةً يخرج بصورة سليمة

تعلن الوحدة المثبّتة ExecStop= لتسجيل علامة إيقاف مخطَّط لـ $MAINPID قبل تسليم SIGTERM، فيُصنَّف إيقاف الخدمة أو إعادة تشغيلها مباشرةً كإجراء مقصود: يُنهي gateway العمل الجاري، ويحفظ gateway_state=stopped، ويخرج بالحالة 0 — ويعرض journal إيقافًا/بدءًا سليمًا دون سطر Failed with result exit-code.

فضّل hermes gateway restart عندما تهمّ أدوار الوكيل الجارية: يطلب من gateway إنهاء العمل الجاري أولًا (SIGUSR1، مع مراعاة ميزانية انتظار إعادة التشغيل)، وينتظر البديل، بينما يوقف systemctl restart الخام العملية الحالية وفق جدول systemd. بعد تحديث Hermes، نفّذ hermes gateway restart مرة واحدة كي تلتقط الخدمة الجارية الوحدة المعاد توليدها التي تحتوي على سطر ExecStop= (يُصدر hermes gateway status تحذيرًا ما دامت الوحدة المثبّتة قديمة).

تربط الوحدة المثبّتة أيضًا systemctl reload hermes-gateway بـ SIGUSR1. لذا يعني reload بالنسبة إلى Hermes إنهاء العمل الجاري بسلاسة، والخروج من العملية، وإعادة الإطلاق بواسطة المشرف؛ وهو ليس إعادة تحميل للإعدادات داخل العملية. استخدم hermes gateway restart عندما تريد من CLI انتظار العملية البديلة والتحقق منها.

أجهزة VM بلا واجهة: خدمة مستخدم + linger تتجنّب مطالبات root

تحتاج خدمة النظام إلى root في كل إعادة تشغيل — بما فيها إعادة تشغيل gateway التلقائية في نهاية hermes update. عندما يعمل hermes update كمستخدم غير root، يجرّب sudo systemctl دون كلمة مرور؛ وإذا لم يتوفر، يتخطى إعادة التشغيل ويطبع أمر sudo systemctl restart hermes-gateway اليدوي (لا يتوقف أبدًا عند مطالبة كلمة مرور تفاعلية).

تتبع الوحدة المثبّتة (أو launchd plist) قيمة HERMES_HOME التي تثبّتها. لا يعيد gateway بدأ من دليل رئيسي مختلف، مثل دليل اختبار أو scratch يصادف أنه يُحلّ إلى اسم الخدمة نفسه، كتابتها أبدًا: ترفض gateway run، start، restart و install --force برسالة تسمّي الدليلين وتترك الملف كما هو. لتوجيه خدمة موجودة عمدًا إلى الدليل الحالي، نفّذ hermes gateway install --force-unit-path.

داخل الحاوية، لا يُعرض إلا نطاق النظام

hermes gateway install (ومعالج hermes gateway setup) يرفضان تثبيت خدمة مستخدم عندما يكتشف Hermes أنه يعمل داخل حاوية. تُكتب وحدة المستخدم في ~/.config/systemd/user، وعندما يكون ذلك الدليل الرئيسي مركّبًا من المضيف عبر bind mount (podman/distrobox)، يفعّل systemd --user الخاص بالمضيف الوحدة نفسها ويبدأها — gateway ثانٍ يستطلع bot token نفسه. شغّل gateway كعملية الحاوية الرئيسية (hermes gateway run، مع سياسة إعادة تشغيل للحاوية)، أو ثبّت نطاق النظام المعزول في حاوية systemd (systemd هو PID 1): sudo hermes gateway install --system --run-as-user <user>.

تثبيتات متعددة

إذا شغّلت عدة تثبيتات Hermes على الجهاز نفسه (بأدلة HERMES_HOME مختلفة)، يحصل كل واحد على اسم خدمة systemd خاص به. يستخدم ~/.hermes الافتراضي hermes-gateway؛ وتستخدم التثبيتات الأخرى hermes-gateway-<hash>. تستهدف أوامر hermes gateway تلقائيًا الخدمة الصحيحة لقيمة HERMES_HOME.

macOS (launchd)

يوجد ملف plist المُولَّد في ~/Library/LaunchAgents/ai.hermes.gateway.plist. ويتضمن ثلاثة متغيرات بيئة:

  • PATH — قيمة PATH الكاملة للـ shell لديك وقت التثبيت، مع إضافة مجلد bin/ الخاص بالـ venv وnode_modules/.bin في بدايتها. وهذا يضمن توفر الأدوات التي ثبّتها المستخدم (Node.js و ffmpeg وغيرها) للعمليات الفرعية لـ gateway مثل جسر WhatsApp.
  • VIRTUAL_ENV — يشير إلى البيئة الافتراضية لـ Python كي تتمكن الأدوات من تحديد الحزم بشكل صحيح.
  • HERMES_HOME — يحصر نطاق gateway في تثبيت Hermes الخاص بك.
تغييرات PATH بعد التثبيت

ملفات plist الخاصة بـ launchd ثابتة — فإذا ثبّتّ أدوات جديدة (مثل إصدار جديد من Node.js عبر nvm، أو ffmpeg عبر Homebrew) بعد إعداد gateway، فنفّذ hermes gateway install مرة أخرى لالتقاط قيمة PATH المحدّثة. وسيكتشف gateway ملف plist القديم ويعيد التحميل تلقائيًا.

التثبيت دون بدء التشغيل

يضبط plist RunAtLoad، لذا يؤدي تحميله إلى بدء gateway. الخيار hermes gateway install --no-start-now، مثل الإجابة No عن "Start the gateway now?" في hermes gateway setup، يكتب plist دون تحميله: يبدأ gateway عند تسجيل دخولك التالي، أو عندما تنفّذ hermes gateway start. يُعاد تحميل gateway الذي يشغّله launchd بالفعل باستخدام plist الجديد، ولا يُوقَف.

الوصول إلى الشبكة المحلية (تفشل أجهزة LAN برسالة "No route to host")

تنسب خصوصية الشبكة المحلية في macOS الـ socket إلى الملف التنفيذي الذي أطلقه launchd للمهمة. لا يملك Python المجرّد في venv هوية تطبيق، لذا لم يستطع gateway الذي يشغّله launchd الوصول إلى مضيفي LAN (Home Assistant، وخوادم النماذج المحلية) — فشل كل اتصال بالرسالة errno 65 No route to host بينما نجح URL نفسه من Terminal، ولم تظهر مطالبة لمنح الوصول أبدًا. لذا يشغّل plist المُولَّد gateway عبر /usr/bin/osascript؛ ويبدأ استدعاء JXA system() gateway دون حلقة استطلاع أحداث تفاعلية، ويعامل macOS أبناءه كأبناء osascript نفسه — ملف تنفيذي من منصة Apple، معفى من الفحص. يعرض ps osascript → stderr_timestamp → gateway run؛ ويعمل الإيقاف/إعادة التشغيل/KeepAlive كما كان تمامًا. يُحدَّث plist الذي ثبّته Hermes أقدم بواسطة hermes gateway install (أو عند hermes gateway start).

التقاط بيانات اعتماد جديدة بعد hermes auth add / hermes auth reset

تعمل الوكلاء كخيوط داخل عملية gateway الواحدة؛ والعمليات الفرعية الوحيدة هي عمليات الأدوات (أوامر الطرفية، والمتصفحات)، التي لا تحمل بيانات اعتماد المزوّد أبدًا. يعيد gateway الجاري أيضًا قراءة تسجيل دخول openai-codex الذي أدخله من auth.json في المرة التالية التي يختار فيها مجمّعه تلك المدخلة بعد أن أصبحت exhausted أو dead (المدخلات المضافة باستخدام hermes auth add openai-codex حسابات مستقلة ولا تُعاد مزامنتها). عندما تريد جميع الجلسات على تسجيل الدخول الجديد دفعة واحدة، أعد تشغيل gateway — لكن فضّل المسار الذي ينهي العمل الجاري على القتل المباشر:

  • hermes gateway restart يطلب من gateway (SIGUSR1) رفض أدوار جديدة، وينتظر حتى agent.restart_after_turn_timeout (الافتراضي 1800 s) لإنهاء الأدوار الجارية، ثم يخرج ويدع KeepAlive في launchd يعيد إطلاقه؛ وتقرأ العملية الجديدة auth.json من البداية.
  • launchctl kickstart -k gui/$UID/ai.hermes.gateway يرسل SIGTERM بدلًا من ذلك: يقاطع gateway أدوار المحادثة الجارية بعد agent.restart_drain_timeout (الافتراضي 0 — فورًا؛ يُبلَّغ المستخدم ويُستأنف الدور عند رسالته التالية)، ويمنح تشغيلات cron و api_server (/v1) مدة agent.cron_drain_timeout (الافتراضي 30 s)، ويقتل عمليات الأدوات الفرعية ويخرج، ثم يعيد launchd إطلاقه. لا يبقى شيء من العملية القديمة، لذا جلسة تستمر في الفشل بالرسالة 401 بعد إعادة الإطلاق تتواصل مع عملية gateway أخرى — راجع hermes gateway status (و launchctl list | grep hermes) بحثًا عن PID ثانٍ، مثل hermes gateway run بدأ يدويًا، وأوقفه أيضًا.
تثبيتات متعددة

كما في خدمة systemd على Linux، يحصل كل دليل HERMES_HOME على تسمية launchd خاصة به. يستخدم ~/.hermes الافتراضي ai.hermes.gateway؛ وتستخدم التثبيتات الأخرى ai.hermes.gateway-<suffix>.

Windows (Task Scheduler)

تشغّل Scheduled Task برنامج wscript.exe على مُطلِق .vbs مُولَّد تحت %USERPROFILE%\.hermes\gateway-service\. يبدأ المُطلِق python.exe -m hermes_cli.main gateway run بنافذة مخفية و يخرج فورًا — عمدًا: لا يملك wscript.exe وحدة تحكم، لذا لا يتلقى عند تسجيل الدخول CTRL_CLOSE_EVENT الذي يقتل gateway مستضافًا بواسطة cmd.exe، ويرث gateway وحدة تحكم مخفية واحدة بدلًا من إظهار كل عملية فرعية نافذتها الخاصة لحظةً (راجع hermes_cli/gateway_windows.py::_build_gateway_vbs_script).

يشمل RestartOnFailure المُطلِق، لا gateway

لأن المُطلِق يعود فور إطلاق gateway، لا يرى Task Scheduler إلا رمز خروج المُطلِق. لذا لا تعمل سياسة <RestartOnFailure> في المهمة المسجَّلة إلا عندما يفشل wscript.exe نفسه في بدء gateway — وهي لا تعيد تشغيل gateway يتعطل أو يُقتل لاحقًا. تعتمد إعادة التشغيل التلقائية لـ gateway على Windows على مسار إعادة التشغيل الخاص به داخل العملية (/restart، والتحديثات، وأمر hermes gateway restart)؛ ويظل gateway الذي يُقتل من الخارج متوقفًا حتى hermes gateway start أو schtasks /Run /TN <task>.

hermes gateway install يكتب المهمة من القالب الحالي؛ وإلا ستحتفظ مهمة مسجّلة ببناء أقدم بإعداداتها القديمة (دون RestartOnFailure، ودون Delay عند تسجيل الدخول، وسطر أوامر مُطلِق أقدم) إلى أجل غير مسمّى. يقارن hermes gateway status المهمة المسجَّلة بالقالب الحالي ويحذّر عندما تكون أقدم منه:

hermes gateway start و hermes update يجريان المقارنة نفسها ويعيدان تسجيل مهمة منحرفة من القالب الحالي تلقائيًا (مثل تحديث وحدة systemd على Linux)؛ عندما يرفض schtasks دون رفع الصلاحيات، أعد تشغيل hermes gateway install، الذي يمكنه طلب موافقة المسؤول. يكون الفحص صامتًا عند تعذّر الاستعلام عن المهمة، ولا يفحص إلا إعدادات قليلة يملكها Hermes (إصدار المهمة، و RestartOnFailure، وتأخير مُشغِّل تسجيل الدخول، ووسائط المُطلِق)، فلا يُعلِّم تعديلات محلية مقصودة في مواضع أخرى بالمهمة.

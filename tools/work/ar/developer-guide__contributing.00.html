المساهمة

شكرًا لمساهمتك في Hermes Agent! يغطي هذا الدليل إعداد بيئة التطوير، وفهم قاعدة الكود، ودمج الـ PR الخاص بك.

أولويات المساهمة

نقدّر المساهمات وفق الترتيب التالي:

  1. إصلاح الأخطاء (Bug fixes) — الأعطال المفاجئة، والسلوك غير الصحيح، وفقدان البيانات
  2. التوافق عبر المنصات — macOS، وتوزيعات Linux المختلفة، و WSL2
  3. تعزيز الأمان — حقن الأوامر في الـ shell، وحقن الـ prompt (prompt injection)، واجتياز المسارات (path traversal)
  4. الأداء والمتانة — منطق إعادة المحاولة، ومعالجة الأخطاء، والتدهور السلس (graceful degradation)
  5. مهارات جديدة — المفيدة على نطاق واسع (راجع إنشاء المهارات (Skills))
  6. أدوات جديدة — نادرًا ما تكون مطلوبة؛ فمعظم القدرات ينبغي أن تكون مهارات
  7. التوثيق — الإصلاحات، والتوضيحات، والأمثلة الجديدة

مسارات المساهمة الشائعة

  • هل تبني أداة مخصّصة/محلية دون تعديل نواة Hermes؟ ابدأ بصفحة بناء إضافة (Plugin) لـ Hermes
  • هل تبني أداة أساسية مدمجة جديدة لـ Hermes نفسه؟ ابدأ بصفحة إضافة أدوات
  • هل تبني مهارة جديدة؟ ابدأ بصفحة إنشاء المهارات (Skills)
  • هل تبني مزوّد inference جديدًا؟ ابدأ بصفحة إضافة مزوّدين

التثبيت باستخدام المُثبّت القياسي

بالنسبة إلى معظم المساهمين، فإن أفضل طريقة لتهيئة بيئة التطوير هي المسار نفسه الذي يسلكه المستخدمون: شغّل المُثبّت القياسي، ثم اعمل داخل المستودع الذي استنسخه. يُنشئ المُثبّت الـ venv الخاص بـ Hermes، ويربط الأمر hermes، ويسجّل طريقة التثبيت لكي يستخدمها hermes update، ويستنسخ مشروع git الكامل إلى $HERMES_HOME/hermes-agent (عادةً ~/.hermes/hermes-agent). يُبقي ذلك بيئة التطوير لديك على البنية نفسها التي يفترضها كلٌّ من CLI، والمحدِّث، ومُثبّت الاعتماديات الكسول (lazy)، والـ gateway، والتوثيق.

البديل الاحتياطي: الاستنساخ اليدوي

استخدم هذه الطريقة فقط إذا كنت لا تريد عمدًا بنية التثبيت المُدارة الخاصة بـ Hermes (مثل نسخة مستنسخة مؤقتة داخل حاوية أو مهمة CI). إذا ثبّتت بهذه الطريقة، فتأكد من تشغيل نقطة الدخول hermes من هذا الـ venv؛ إذ قد يؤدي تشغيل python3 -m hermes_cli.main الخاص بالنظام إلى التقاط حزم Python غير ذات صلة مثبّتة على النظام.

أنشئ الـ venv خارج شجرة المصدر المستنسخة. فالـ venv الموجود داخل المجلد الذي يعمل منه الوكيل قد يُمحى بأمر يستخدم مسارًا نسبيًا ينفّذه الوكيل على نسخته المسحوبة نفسها (rm -rf venv، uv venv venv، إلخ)، ما يدمّر بيئة التشغيل الجارية بصمت في منتصف الجلسة. أما إبقاؤه خارج الشجرة فيعني أنه لا يوجد مسار نسبي من مساحة العمل يؤدي إليه.

تشغيل الاختبارات

أسلوب كتابة الكود

  • PEP 8 مع استثناءات عملية (دون فرض صارم لطول السطر)
  • التعليقات: فقط عند شرح مقصد غير واضح، أو مقايضات، أو خصوصيات غريبة في API
  • معالجة الأخطاء: التقط استثناءات محددة. استخدم logger.warning()/logger.error() مع exc_info=True للأخطاء غير المتوقعة
  • التوافق عبر المنصات: لا تفترض أبدًا أن النظام Unix (انظر أدناه)
  • مسارات آمنة مع الـ profiles: لا تكتب ~/.hermes بشكل ثابت في الكود أبدًا — استخدم get_hermes_home() من hermes_constants لمسارات الكود، وdisplay_hermes_home() للرسائل التي تظهر للمستخدم. راجع AGENTS.md للاطلاع على القواعد كاملة.

التوافق عبر المنصات

راجع دعم المنصات. يستخدم Windows الأصلي Git Bash (من Git for Windows) لأوامر الـ shell. تتطلب بعض الميزات بدائيات نواة POSIX ولذلك تُقيَّد: فلوحة الطرفية المضمّنة PTY في لوحة التحكم (تبويب /chat) تحتاج إلى PTY متوافق مع POSIX (على Linux أو macOS أو WSL2). إذا كان تطويرك يعتمد بكثافة على Windows، فشغّل أداة الفحص الخاصة بمزالق Windows (scripts/check-windows-footguns.py) قبل الدفع (push).

عند المساهمة بالكود، ضع هذه القواعد في اعتبارك:

  • لا تُضف إشارات غير محمية إلى signal.SIGKILL. فهي غير معرّفة على Windows. إما أن تمرّ عبر gateway.status.terminate_pid(pid, force=True) (البدائية المركزية التي تنفّذ taskkill /T /F على Windows و SIGKILL على POSIX)، أو أن تلجأ احتياطيًا إلى getattr(signal, "SIGKILL", signal.SIGTERM).
  • التقط OSError إلى جانب ProcessLookupError في فحوصات os.kill(pid, 0). إذ يرفع Windows الاستثناء OSError (WinError 87، "parameter is incorrect") لمعرّف عملية (PID) لم يعد موجودًا بدلًا من ProcessLookupError.
  • لا تفرض دلالات POSIX على الطرفية. فالدوال os.setsid وos.killpg وos.getpgid وos.fork كلها ترفع استثناءات على Windows — قيّدها بالشرط if sys.platform != "win32": أو if os.name != "nt":.
  • افتح الملفات مع تحديد encoding="utf-8" صراحةً. فالقيمة الافتراضية في Python على Windows هي لغة النظام المحلية (locale) (غالبًا cp1252)، ما يؤدي إلى تشوّه النصوص غير اللاتينية (mojibake) أو إلى تعطّل البرنامج.
  • استخدم pathlib.Path / os.path.join — ولا تدمج المسارات يدويًا باستخدام / أبدًا. يهمّ هذا بدرجة أقل في السلاسل النصية التي يُعيدها نظام التشغيل، وبدرجة أكبر في السلاسل التي نبنيها لتمريرها إلى العمليات الفرعية (subprocesses).

المساهمة بكود حسّاس أمنيًا

  • استخدم دائمًا shlex.quote() عند إدراج مدخلات المستخدم في أوامر الـ shell
  • حُلّ الروابط الرمزية باستخدام os.path.realpath() قبل فحوصات التحكم في الوصول
  • لا تسجّل الأسرار في السجلات
  • التقط الاستثناءات العامة حول تنفيذ الأدوات
  • اختبر على جميع المنصات إذا كان تغييرك يمسّ مسارات الملفات أو العمليات

عملية Pull Request

تسمية الـ Branches

قبل الإرسال

  1. شغّل الاختبارات: scripts/run_tests.sh لمطابقة بيئة CI. لا تستخدم python -m pytest ... مباشرةً إلا حين يكون السكربت المُغلِّف غير متاح أو حين تتعمّد تصحيح الأخطاء خارجه.
  2. اختبر يدويًا: شغّل hermes وجرّب مسار الكود الذي غيّرته
  3. تحقّق من الأثر عبر المنصات: ضع في اعتبارك macOS و Linux و WSL2 و Windows الأصلي. إذا كنت تعدّل عمليات إدخال/إخراج الملفات، أو إدارة العمليات، أو التعامل مع الطرفية، أو العمليات الفرعية، أو الإشارات، فشغّل scripts/check-windows-footguns.py.
  4. اجعل الـ PRs مركّزة: تغيير منطقي واحد لكل PR

وصف الـ PR

ضمّن ما يلي:

  • ما الذي تغيّر ولماذا
  • كيفية اختباره خطوة بخطوة

قوائم مراجعة محلية داخل المستودع: .agents/checks/*.md

يمكن للمشاريع المبنية على Hermes (أو التي يراجعها Hermes) الاحتفاظ بقوائم تحقق للمراجعين داخل المستودع ضمن .agents/checks/. كل ملف هو قائمة تحقق مركّزة بصيغة markdown عادية، يحمّلها الوكيل قبل مراجعة أي تغيير يمسّ المجال المطابق:

أعراف تجعل هذه القوائم تعمل جيدًا:

  • اهتمام واحد لكل ملف، ويُسمّى الملف باسم ذلك الاهتمام. فالملفات الصغيرة تُقرأ كاملة، أما ملف checklist.md الضخم فيُقرأ على عجل.
  • اكتب الفحوصات كإجراءات قابلة للتحقق («شغّل X وتأكد من Y»)، لا كتطلعات («يجب أن يكون الكود آمنًا»).
  • اذكر شرط التطبيق في أعلى الملف — أي المسارات أو أنواع التغييرات التي تنطبق عليها القائمة — كي يتمكن الوكيل (أو الإنسان) من تخطّي غير المتعلّق منها بسهولة.
  • احفظها في نظام التحكم بالإصدارات بجوار الكود الذي تحرسه: فهي تتطور مع قاعدة الكود، والـ PR الذي يغيّر القواعد يغيّر قائمة التحقق في الـ diff نفسه.

حين تطلب من Hermes مراجعة PR في مستودع يحتوي على .agents/checks/، اطلب منه (أو علّمه عبر مهارة) أن يقرأ قوائم التحقق ذات الصلة أولًا وأن يقدّم تقريره وفقًا لها. يمنح هذا وكلاء المراجعة المعيار الخاص بالمشروع الذي تغفله الـ prompts العامة للمراجعة.

Hooks المراقبة في Hermes

Hooks المراقبة في Hermes هي عقد قياس للقراءة فقط للإضافات التي تحتاج إلى إعادة بناء تنفيذ الوكيل دون تغيير سلوك وقت التشغيل. يدعم هذا العقد تكاملات التتبّع والمقاييس والتدقيق وإعادة العرض والتصدير، مثل Langfuse، ومجمّعات على نمط OpenTelemetry، و NeMo Relay.

Hooks المراقبة مستقلة عمدًا عن backend. تكشف أحداث دورة حياة ثابتة، ومعرّفات ارتباط، وحمولات منقَّاة، وحقول التوقيت والحالة والخطأ. لا تستبدل مخطِّط Hermes، أو مزوّدي النماذج، أو الذاكرة، أو سجل الأدوات، أو تجربة الموافقة، أو CLI، أو سلوك gateway، أو دلالات التنفيذ.

أغلفة الطلبات أو التنفيذ التي تغيّر السلوك خارج عقد المراقبة هذا. ينبغي لـ hooks المراقبة الإبلاغ عما حدث؛ ولا ينبغي أن تستبدل طلبات المزوّد أو وسائط الأدوات أو callbacks التنفيذ.

لدى Hermes أيضًا مسار مقاييس مشتركة مباشر من NeMo Relay. يستخدم حدود دورة الحياة هذه مباشرةً ولا يتطلب تفعيل إضافة للرصد. راجع مقاييس Relay المشتركة.

لا توقف callbacks الـ hook التنفيذ عند الفشل. يلتقط Hermes استثناءاتها، ويسجّل تحذيرًا، ويُبقي حلقة الوكيل تعمل.

تُتجاهَل معظم قيم إرجاع hooks المراقبة. الاستثناءات هي hooks أقدم تؤثر في السلوك:

Hookسلوك الإرجاع
pre_llm_callقد يعيد سلسلة نصية أو {"context": "..."} لحقن سياق مؤقت في رسالة المستخدم الحالية.
pre_tool_callقد يعيد {"action": "block", "message": "..."} لحظر أداة قبل التنفيذ، أو {"action": "modify", "args": {...}} لتحويل وسائط إدخال الأداة.
transform_tool_resultقد يعيد سلسلة بديلة لنتيجة أداة بعد post_tool_call.
transform_llm_outputقد يعيد سلسلة بديلة للنص النهائي للمساعد.

ينبغي لإضافات القياس التعامل مع قيم الإرجاع المؤثرة في السلوك كميزات توافق اختيارية، لا كمتطلبات للرصد.

معرّفات الارتباط

تستخدم حمولات المراقبة معرّفات ثابتة كي تربط الإضافات الأحداث دون الاعتماد على ترتيب callbacks وحده.

الحقلالمعنى
session_idهوية المحادثة/الجلسة.
task_idهوية المهمة، مفيدة خصوصًا لـ subagents والتنفيذ المعزول.
turn_idهوية دور المستخدم التي تشترك فيها محاولات API واستدعاءات الأدوات داخل الدور.
api_request_idهوية معتمة لمحاولة المزوّد. لا تحلّل صيغتها النصية.
api_call_countالعدد الرقمي لمحاولات API داخل حلقة الوكيل.
tool_call_idمعرّف استدعاء الأداة الذي يقدّمه المزوّد عند توفره.
parent_session_id / child_session_idرابط الجلسة لـ subagents المفوَّضة.
parent_subagent_id / child_subagent_idرابط subagent عند توفره.
parent_turn_idالدور الأب الذي أطلق العمل المفوَّض.

ينبغي للمستهلكين تفضيل الحقول الصريحة على تحليل معرّفات مركَّبة. تحديدًا، api_request_id قيمة ارتباط معتمة.

عائلات الأحداث

دورة حياة الجلسة

تصف hooks الجلسة حدود المحادثات وإعادة الضبط:

Hookوقت الإطلاق
on_session_startتبدأ جلسة جديدة تمامًا بعد بناء system prompt.
on_session_endينتهي استدعاء run_conversation، بما فيه الأدوار المقاطَعة أو غير المكتملة.
on_session_finalizeينهي CLI أو gateway هوية جلسة نشطة.
on_session_resetينتقل CLI أو gateway من هوية جلسة قديمة إلى أخرى جديدة.
on_session_deleteتم تثبيت حذف جلسة أو أرشفتها عمدًا (يوضّح reason أيهما حدث).

تشمل الحقول المشتركة session_id، completed، interrupted، reason، old_session_id، و new_session_id عند توفرها.

on_session_end محدد النطاق بالدور/التشغيل. ليس بالضرورة حد نهاية عمر هوية محادثة. استخدم on_session_finalize و on_session_reset لتنظيف دورة الحياة الذي يجب أن يحدث مرة واحدة لكل هوية جلسة.

Hooks LLM المحددة النطاق بالدور

تؤطر هذه hooks دور المستخدم، لا محاولات API الفردية لدى المزوّد:

Hookوقت الإطلاق
pre_llm_callقبل بدء حلقة الأدوات لدور مستخدم.
post_llm_callبعد اكتمال الدور بمخرجات نهائية للمساعد.

تشمل حقول pre_llm_call المشتركة session_id، turn_id، user_message، conversation_history، is_first_turn، model، platform، و sender_id.

تشمل حقول post_llm_call المشتركة session_id، turn_id، user_message، assistant_response، conversation_history، model، و platform.

استخدم hooks API المحددة النطاق بالطلب لقياس spans الخاصة بـ LLM. استخدم pre_llm_call و post_llm_call لسياق الدور، والتوافق، والملخّص النهائي للدور.

Hooks API المحددة النطاق بالطلب

تصف hooks API محاولات المزوّد داخل حلقة الوكيل:

Hookوقت الإطلاق
pre_api_requestمباشرةً قبل طلب API للمزوّد.
post_api_requestبعد استجابة ناجحة من المزوّد.
api_request_errorبعد طلب مزوّد فاشل أو مسار خطأ قابل لإعادة المحاولة.
pre_auxiliary_callقبل كل محاولة لدى المزوّد لاستدعاء LLM مساعد (التسمية، والضغط، و MoA، والرؤية، ...). يحمل aux_task؛ وتظل hooks *_api_request للحلقة الرئيسية فقط.
post_auxiliary_callبعد عودة تلك المحاولة أو إثارتها استثناءً (يُضبط error عند الفشل).

pre_api_request يتضمن:

  • الهوية: session_id، task_id، turn_id، api_request_id
  • وقت التشغيل: platform، model، provider، base_url، api_mode
  • بيانات المحاولة الوصفية: api_call_count، message_count، tool_count، approx_input_tokens، request_char_count، max_tokens
  • التوقيت: started_at
  • حمولة الطلب المنقَّاة: request

post_api_request يتضمن حقول الهوية/وقت التشغيل نفسها، مع:

  • api_duration، started_at، ended_at
  • finish_reason، message_count، response_model
  • usage
  • assistant_content_chars، assistant_tool_call_count
  • حمولة الاستجابة المنقَّاة: response
  • كائن التوافق: assistant_message

api_request_error يتضمن حقول الهوية/وقت التشغيل نفسها، مع:

  • api_duration، started_at، ended_at
  • status_code، retry_count، max_retries، retryable، reason
  • كائن منظّم من error = {"type": ..., "message": ...}
  • حمولة الطلب الفاشل المنقَّاة: request

الحقول المنقَّاة request، response، و error هي المدخلات المعتمدة للمراقبة لدى المستهلكين الجدد.

دورة حياة الأداة

تصف hooks الأدوات استدعاءات الأدوات الفردية:

Hookوقت الإطلاق
pre_tool_callقبل إرسال أداة وافقت عليها الضوابط الوقائية.
post_tool_callبعد إرسال الأداة، أو إلغائها، أو حظرها، أو اكتمالها بخطأ.
transform_tool_resultبعد post_tool_call، وقبل إلحاق النتيجة بسياق النموذج.

pre_tool_call يتضمن tool_name، args، task_id، session_id، tool_call_id، turn_id، و api_request_id.

post_tool_call يتضمن حقول الهوية نفسها مع result، duration_ms، status، error_type، و error_message.

status هو نتيجة دورة الحياة الملائمة للمراقبة. تشمل القيم الشائعة:

الحالةالمعنى
okاكتملت الأداة طبيعيًا.
errorعملت الأداة وأعادت نتيجة خطأ أو أثارتها.
blockedحظر hook pre_tool_call التنفيذ.
cancelledأُلغي التنفيذ قبل اكتماله الطبيعي.

post_tool_call يُصدر للمسارات المحظورة والملغاة كي تغلق إضافات القياس spans بصورة سليمة.

دورة حياة الإدخال البشري

on_human_input_request / on_human_input_resolved يُطلَقان حول كل نقطة يتوقف فيها الوكيل منتظرًا شخصًا: مطالبات كلمة مرور sudo (kind="sudo")، وأسئلة أداة clarify (kind="clarify")، ومطالبات الموافقة (kind="approval") في CLI، و TUI/Desktop، و ACP، ومنصات gateway. الحقول: kind، request_id (مشترك بين الزوج)، و session_id، session_key، platform، و prompt محجوب إلزاميًا؛ ويضيف hook الحسم outcome. لا تُضمَّن أبدًا كلمة المرور أو الإجابة المكتوبة. لا تطلقه الموافقات الذكية (LLM المساعد). المصدر: tools/human_input_hooks.py.

دورة حياة الموافقة

تصف hooks الموافقة مطالبات الموافقة على الأوامر الخطرة:

Hookوقت الإطلاق
pre_approval_requestقبل عرض طلب الموافقة أو إرساله.
post_approval_responseبعد إجابة المستخدم أو انتهاء مهلة الطلب.

تشمل الحقول المشتركة command، description، pattern_key، pattern_keys، session_key، و surface.

post_approval_response يتضمن أيضًا choice، بقيم مثل once، session، always، deny، timeout، و cancelled (لم يُجب أحد: سُحبت المطالبة — قُوطع الدور أو انتهى — أو لم تصل إلى المستخدم في CLI).

Hooks الموافقة للمراقبة فقط. لا تستطيع الإضافات الإجابة المسبقة عن الموافقات أو نقضها من هذه hooks. لمنع أداة من الوصول إلى الموافقة، استخدم حظر pre_tool_call.

دورة حياة Subagent

تصف hooks الـ subagent عمل الوكيل الفرعي المفوَّض:

Hookوقت الإطلاق
subagent_startيُنشأ وكيل فرعي مفوَّض.
subagent_stopيعود وكيل فرعي مفوَّض أو يفشل.

subagent_start تشمل حقوله parent_session_id، parent_turn_id، parent_subagent_id، child_session_id، child_subagent_id، child_role، و child_goal.

subagent_stop تشمل حقوله معرّفات جلسات الأب/الفرع، وحقول الدور/الحالة، و child_summary، duration_ms، و tool_call_history لا يتضمن إلا البيانات الوصفية. تتضمن كل مدخلة سجل اسم الأداة، وأسماء الوسائط، وأهداف آثار جانبية محدودة، وعدد بايتات الإدخال/الإخراج، والنتيجة. تُزال سلاسل استعلام URL وأجزاؤه؛ وتُستثنى عمدًا الوسائط الخام، و prompts، والأوامر، والمحتويات، والترويسات، والنتائج.

يمكن للمراقبين استخدام هذه hooks لنمذجة مسارات متداخلة مع إبقاء تنفيذ الوكيل الفرعي مرتبطًا بالدور الأب الذي أطلقه.

أمان الحمولة

صُممت حمولات المراقبة لمستهلكي القياس، لا للوصول إلى الكائنات الخام. ينبغي للمستهلكين الجدد استخدام حمولات API المنقَّاة:

  • pre_api_request.request
  • post_api_request.response
  • api_request_error.request
  • api_request_error.error

تحوّل التنقية كائنات المزوّد إلى بنى متوافقة مع JSON، وتحدّ الحمولات الكبيرة، وتحجب المفاتيح الحساسة، وتتجنب كشف كائنات الاستجابة الخام في الحقول المنقَّاة.

قد تظل حقول التوافق القديمة مثل request_messages، conversation_history، و assistant_message موجودة للإضافات الحالية. ينبغي لمستهلكي الرصد الجدد تفضيل الحمولات المنقَّاة.

الأداء

ينبغي أن يبقى المسار الافتراضي دون قياس منخفض التكلفة. يُقيَّد بناء حمولات الطلب/الاستجابة المكلف خلف has_hook(...)، فلا يبني Hermes حمولات قياس API المنقَّاة إلا عندما تسجّل إضافة واحدة على الأقل الـ hook المعني.

ينبغي لمؤلفي الإضافات الحفاظ على هذه الخاصية:

  • لا تسجّل إلا hooks التي تستهلكها الإضافة فعلًا.
  • تجنب النسخ العميق أو إعادة تنقية حمولات منقَّاة بالفعل.
  • أبقِ callbacks الـ hook سريعة ولا توقف التنفيذ عند فشلها.
  • أحِل التصدير الشبكي أو الكتابات الدفعية إلى خارج المسار المباشر عندما يكون ذلك عمليًا.

كتابة إضافة مراقبة

إضافة مراقبة بالحد الأدنى:

استخدم session_id، turn_id، api_request_id، و tool_call_id لربط spans. استخدم hooks الـ subagent والموافقة عندما تدعم صيغة التصدير عمل وكلاء متداخلًا أو أحداث دورة حياة الأمان.

المستهلكون الحاليون

توضّح الإضافة الرسمية Langfuse من الكتالوج كيفية تحقيق قابلية المراقبة (observability) مباشرةً عبر hooks للأدوار وطلبات المزوّد واستدعاءات الأدوات.

يربط تكامل NeMo Relay SDK الأصلي دورات حياة الجلسة والدور و LLM والأداة في Hermes بـ Relay. يمكن لإعدادات المستخدم والنظام التي يكتشفها Relay، أو ملف صريح محدد باستخدام HERMES_NEMO_RELAY_PLUGINS_TOML، إضافة مصدِّرات ATOF، أو ATIF، أو OTEL ووسيط تنفيذ؛ راجع مقاييس Relay المشتركة.

Teams Meeting Pipeline

استخدم هذه المهارة كلما سأل المستخدم عن ملخصات اجتماعات Microsoft Teams، أو النصوص المكتوبة (transcripts)، أو التسجيلات، أو بنود العمل، أو اشتراكات Graph، أو أي سؤال تشغيلي حول pipeline اجتماعات Teams. تعمل بأي لغة — الأمثلة المُحفّزة أدناه توضيحية وليست قائمة شاملة.

كل ما يواجه المشغّل هو أمر فرعي من hermes teams-pipeline يُشغَّل عبر أداة terminal. لا توجد أدوات نموذج جديدة لهذا الـ pipeline — الواجهة هي CLI.

متى تُستخدم هذه المهارة

عندما يطلب المستخدم:

  • تلخيص اجتماع Teams / استخراج بنود العمل / سحب ملاحظات الاجتماع
  • التحقق من حالة الـ pipeline، أو فحص مهمة اجتماع مخزّنة، أو الاطلاع على الاجتماعات الأخيرة
  • إعادة تشغيل مهمة مخزّنة فشلت أو تحتاج إلى ملخص جديد
  • التحقق من إعداد Microsoft Graph بعد تغيير بيئة أو ملف إعدادات
  • استكشاف مشكلة "ملخص الاجتماع لم يصل أبدًا" أو "لا اجتماعات جديدة تُستوعب"
  • إدارة اشتراكات webhook الخاصة بـ Graph (إنشاء، تجديد، حذف، فحص)
  • إعداد تجديد تلقائي للاشتراك (انظر الخطأ الشائع أدناه)

أمثلة محفّزة متعددة اللغات (غير شاملة):

  • الإنجليزية: "summarize the Teams meeting"، "pipeline status"، "replay job X"
  • التركية: "Teams meeting özetle"، "action item çıkar"، "toplantı notu"، "pipeline durumu"، "replay job"

شجرة قرار للأسئلة الشائعة

  • عندما يسأل المستخدم "لماذا لم أتلقَّ ملخصًا لاجتماع اليوم؟" ← ابدأ بـ list --status failed، ثم show <job-id> على الصف المعني. إذا لم تكن المهمة موجودة أصلًا، تحقّق من subscriptions — فقد يكون الـ webhook قد انتهت صلاحيته (انظر الخطأ الشائع أدناه).
  • عندما يسأل المستخدم "هل الإعداد يعمل؟" ← نفّذ validate، ثم token-health، ثم subscriptions. إذا نجحت الثلاثة، اطلب اجتماعًا تجريبيًا وتحقّق من list بحثًا عن صف جديد.
  • عندما يسأل المستخدم "أعد تشغيل الملخص للاجتماع X" ← استخدم list لإيجاد معرّف المهمة، ثم run <job-id> لإعادة التشغيل. إذا فشلت مجددًا، استخدم show <job-id> لفحص الخطأ وfetch --meeting-id لتجربة حل المرفقات دون تنفيذ فعلي.
  • عندما يسأل المستخدم "أضف الاجتماع X إلى الـ pipeline" ← عادةً لا تفعل ذلك — فالـ pipeline يعمل بالاشتراكات، لا لكل اجتماع على حدة. إذا أراد ملخصًا لاجتماع سابق محدد، استخدم fetch لسحب النص المكتوب ثم run بعد إنشاء مهمة.

خطأ شائع حرج: تنتهي صلاحية اشتراكات Graph خلال 72 ساعة

يحدّد Microsoft Graph اشتراكات webhook بمدة أقصاها 72 ساعة ولن يجدّدها تلقائيًا. إذا لم تكن maintain-subscriptions مجدولة، تتوقف إشعارات الاجتماعات عن الوصول بصمت بعد 3 أيام من أي إنشاء يدوي للاشتراك.

عندما يبلّغ المستخدم بأن "الـ pipeline كان يعمل بالأمس لكن لا شيء يصل اليوم":

  1. شغّل hermes teams-pipeline subscriptions — إذا كانت النتيجة فارغة أو كانت كل الإدخالات تُظهر expirationDateTime في الماضي، فهذا هو السبب.
  2. أعد الإنشاء باستخدام subscribe كما هو موضح أعلاه.
  3. أعدّ تجديدًا تلقائيًا فورًا عبر hermes cron add، أو مؤقّت systemd، أو crontab عادي. دليل تشغيل المشغّل على /docs/guides/operate-teams-meeting-pipeline#automating-subscription-renewal-required-for-production يضمّ الخيارات الثلاثة جميعها. فاصل زمني مدته 12 ساعة آمن (بهامش أمان 6 أضعاف مقابل حد الـ72 ساعة).

أخطاء شائعة أخرى

  • النص المكتوب غير متوفر بعد. يستغرق Teams بعض الوقت بعد انتهاء الاجتماع لإنشاء مرفق النص المكتوب. قد يُرجع fetch --meeting-id على اجتماع انتهى للتو نتيجة فارغة. انتظر من 2 إلى 5 دقائق وأعد المحاولة، أو دع webhook الخاص بـ Graph يدفع عملية الاستيعاب طبيعيًا.
  • عدم تطابق وضع التسليم. إذا كانت الملخصات تُنتَج (يُظهر list نجاحًا) لكن لا شيء يصل إلى Teams، تحقّق من platforms.teams.extra.delivery_mode وإعدادات الهدف المطابقة (incoming_webhook_url أو chat_id أو team_id+channel_id). تقرأ أداة الكتابة هذه القيم من config.yaml أو متغيرات البيئة TEAMS_*.
  • صلاحيات تطبيق Graph. قد يُستخرَج الرمز المميّز (token) بنجاح (ينجح token-health) لكن استدعاءات Graph API تُرجع 401/403 عندما تُضاف الصلاحيات دون إعادة منح موافقة المسؤول. اطلب من المستخدم مراجعة تسجيل التطبيق في بوابة Azure والنقر على "Grant admin consent" مجددًا.

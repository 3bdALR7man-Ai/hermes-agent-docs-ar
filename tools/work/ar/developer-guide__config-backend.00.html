واجهة Config Backend

تمرّ كل عمليات القراءة والفحص (stat) والتحقق من الوجود والكتابة الخاصة بملف config.yaml الخاص بالمستخدم في أي profile عبر hermes_cli/config_backend.py. تعيد get_config_backend() الـ backend الخاص بكل home؛ وهو اليوم FileBackend، أي ملف config.yaml المحلي مع الأدوات الأولية نفسها التي كان Hermes يستخدمها قبل هذه الواجهة (توقيع stat، و fast_safe_load، وكاتبات ruamel ذات الذهاب والإياب). وأي backend لا يخزّن الطبقة كملف محلي ينفّذ بروتوكول ConfigBackend نفسه، ويصل إليه كل مستدعٍ بالفعل.

الدوال المساعدة

الدالة المساعدةالاستخدام
read_config_doc(path)تعيد طبقة المستخدم بعد تحليلها (وترفع الأخطاء كما تفعل open مع fast_safe_load)
read_config_doc_readonly(path)قراءة مخزَّنة مؤقتًا بحسب التوقيع؛ لا تعدّل النتيجة أبدًا
config_version(path)توقيع الـ cache (صف stat الخاص بالملف)
config_exists(path)هل الطبقة موجودة
probe_config_readable(path)ترفع OSError ما دامت الطبقة غير قابلة للقراءة (دون تحليل)
write_config_document(path, doc) / write_config_key(path, key, value)عمليات الكتابة؛ وعادةً يستخدم المستدعون atomic_config_write / atomic_config_replace

الملف <home>/config.yaml وحده هو طبقة المستخدم. أما أي ملف آخر يُمرَّر إلى هذه الدوال (مصدر استيراد، أو fixture) فيُقرأ ويُكتب في مكانه. تفقد الـ caches المبنية على config_version صلاحيتها (miss) كلما تغيّرت طبقة الـ backend. ويبقى النطاق المُدار (/etc/hermes) overlay فوق أي طبقة مستخدم يعيدها الـ backend.

فحوص Lint

  • يرفض scripts/check_config_yaml_writers.py أي تفريغ YAML مباشر لمسار إعدادات.
  • يرفض scripts/check_config_yaml_readers.py أي open / read_text / stat / exists / تحميل YAML مباشر لمسار إعدادات. وأي إنذار كاذب حقيقي (ملف إعدادات منتج آخر، أو أداة تنسخ الملف المحلي أو تعدّله بنفسها: config edit والنسخ الاحتياطية واستنساخ الـ profile) يحمل # config-reader: ok — <why> على السطر نفسه.

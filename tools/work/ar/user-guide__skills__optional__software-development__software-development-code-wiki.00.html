معلومة

ما يلي هو التعريف الكامل للمهارة الذي يحمّله Hermes عند تفعيل هذه المهارة، وهو ما يراه الوكيل كتعليمات أثناء عمل المهارة.

مهارة Code Wiki

أنشئ ويكي كاملًا لأي قاعدة كود — نظرة عامة، بنية معمارية، تفصيل لكل وحدة على حدة، ومخططات Mermaid للفئات (class) والتسلسل (sequence). مستوحاة من Google CodeWiki، لكنها تعمل على المستودعات المحلية، والمستودعات الخاصة، وبأي لغة. تستخدم فقط أدوات Hermes الموجودة (terminal، read_file، search_files، write_file) دون الحاجة إلى Docker أو خدمات خارجية أو اعتماديات إضافية.

تنتج هذه المهارة مستندات مرجعية (ماذا/كيف). ولا تنتج سردًا استراتيجيًا (لماذا — وهذه مهارة مختلفة).

متى تُستخدم

  • يقول المستخدم "وثّق قاعدة الكود هذه"، "أنشئ ويكي"، "اصنع مخططات بنية معمارية"
  • عند التعرّف على مستودع غير مألوف والحاجة إلى مرجع منظّم
  • يشير المستخدم إلى رابط GitHub ويطلب توثيقًا
  • الحاجة إلى ناتج ثابت (markdown + Mermaid) يُعرض بشكل صحيح على GitHub

لا تستخدمها في الحالات التالية:

  • توثيق ملف واحد أو دالة واحدة — أجب مباشرة فحسب
  • مرجع API لنقطة نهاية (endpoint) واحدة محددة — استخدم read_file وأجب ضمن المحادثة
  • السرد الاستراتيجي حول "لماذا يوجد هذا" — مهارة مختلفة بغرض مختلف
  • قواعد الكود التي يعمل عليها المستخدم فعليًا في هذه الجلسة — اكتفِ بالإجابة عن الأسئلة كلما وردت

المتطلبات المسبقة

  • لا حاجة إلى متغيرات بيئة.
  • git متاح في PATH لتتبّع SHA المستودع والاستنساخ عن بُعد.
  • اختياري: pygount لإحصاءات توزيع اللغات (راجع مهارة codebase-inspection).

طريقة التشغيل

استدعِها عبر أداة terminal من جذر المستودع الهدف، ثم استخدم read_file / search_files / write_file لإنتاج الويكي. موقع الإخراج الافتراضي هو ~/.hermes/wikis/<repo-name>/. لا تكتب داخل المستودع (docs/wiki/) إلا إذا طلب المستخدم ذلك صراحةً.

استخدم أداة terminal لعمليات shell، وread_file لملفات manifest:

ثم استخدم read_file لقراءة ملفات manifest ذات الصلة (package.json، pyproject.toml، setup.py، Cargo.toml، go.mod، pom.xml، build.gradle) وملف README الخاص بالمشروع. استخدم search_files target='files' للعثور عليها بدلًا من تخمين أسمائها.

3. اختر الوحدات المراد توثيقها

احصر الجولة الأولى في 8 إلى 10 وحدات. القواعد الإرشادية حسب اللغة:

  • Python: الحزم (packages) على المستوى الأعلى (الأدلة التي تحتوي __init__.py)، إضافة إلى أدلة الأنظمة الفرعية
  • JS/TS: src/<subdir>، أدلة workspace على المستوى الأعلى
  • Rust: كل crate ضمن workspace، أو أدلة src/<module> على المستوى الأعلى
  • Go: كل دليل حزمة (package) على المستوى الأعلى
  • مختلط/غير مألوف: الأدلة على المستوى الأعلى التي تحتوي كود مصدري (وليست إعدادات أو اختبارات)

للمستودعات الكبيرة جدًا، رتّب الأولوية حسب:

  1. عدد مرات الاستيراد (الوحدة التي تُستورَد من قِبل وحدات كثيرة تُعدّ أساسية)
  2. عدد أسطر الكود (LOC) (الوحدات الأكبر تستحق عادة مستندًا خاصًا بها)
  3. ذكرها في README أو المستندات على المستوى الأعلى

اذكر للمستخدم قائمة الوحدات قبل توليد مستندات كل وحدة في المستودعات الكبيرة — يمنحه ذلك فرصة لإعادة التوجيه.

5. اكتب architecture.md

التحكم في النطاق

توليد ويكي كامل لمستودع أحادي (monorepo) بحجم 500 ألف سطر كود مكلف جدًا من حيث الـ tokens. اجعل النطاق محدودًا افتراضيًا:

  • الفحص الأولي: عمق أقصى 3 أدلة
  • مستندات كل وحدة: حدّها بـ 10 وحدات ما لم يوسّع المستخدم النطاق
  • قراءة الملفات: فضّل search_files للرموز مع read_file باستخدام offset/limit بدلًا من القراءة الكاملة
  • تخطَّ الكود المُستورد جاهزًا (vendor/، third_party/، الكود المُولَّد، _pb2.py، .min.js)

إذا قال المستخدم "نفّذ الأمر كاملًا وبشمولية"، صدّقه — لكن قدّر التكلفة أولًا: "هذا المستودع يحتوي نحو 340 ملفًا مصدريًا، والتغطية الشاملة ستكون مكلفة — هل تؤكد؟"

إعادة التشغيل / التحديث

إذا كان .codewiki-state.json موجودًا مسبقًا في المسار الهدف:

  • اقرأه للحصول على SHA السابق وقائمة الوحدات
  • إذا تطابق SHA المصدر: اسأل المستخدم إن كان يريد إعادة التوليد أو التخطي
  • إذا اختلف SHA: اقترح إعادة توليد الوحدات ذات الملفات المتغيرة فقط (git diff --name-only <old-sha> HEAD)

إعادة التوليد التزايدية الكاملة تحسين مستقبلي — أما الآن، فإعادة توليد كل شيء أمر مقبول.

المزالق

  • اختلاق مكوّنات. يجب أن تكون كل عقدة في المخطط وكل استدعاء دالة مزعوم موجودًا فعلًا في المصدر. استخدم read_file قبل الكتابة. أكبر أنماط الفشل في المستندات المُولَّدة تلقائيًا هو الاختلاق الذي يبدو معقولًا.
  • نثر عام من الذكاء الاصطناعي. عبارة "هذه الوحدة مسؤولة عن..." خالية من أي مضمون. اذكر ما تفعله الوحدة فعلًا بمصطلحات خاصة بالمجال.
  • إعادة صياغة الكود نثرًا. مستند وحدة يقول "تقوم دالة process بمعالجة الأشياء عبر استدعاء process_item على كل عنصر" أسوأ من مجرد الربط بالدالة.
  • مخطط Mermaid بأكثر من 50 عقدة. لا يُعرض بوضوح. قسّمه.
  • توثيق الاختبارات أو الكود المُولَّد أو الاعتماديات المستوردة جاهزة وكأنها كود المنتج. تخطَّها.
  • الإخراج داخل المستودع دون سؤال. الافتراضي هو ~/.hermes/wikis/. لا تكتب داخل المستودع إلا إذا طلب المستخدم ذلك صراحةً.
  • الرموز الخاصة في Mermaid تحتاج علامات اقتباس: A["Tool / Agent"] وليس A[Tool / Agent]. استخدم <br> لفواصل الأسطر داخل العقدة.
  • أسيجة الكود المتداخلة في SKILL.md. عند كتابة مثال markdown يحتوي كتلة Mermaid، استخدم أسيجة خارجية من 4 علامات backtick حتى لا تُغلق الكتلة الداخلية ذات الـ3 علامات ```mermaid السياج الخارجي. (ملف SKILL.md هذا يفعل ذلك.)
  • الأنواع العامة (generics) في classDiagram تُعرض بالصيغة ~T~ (مثل List~Tool~) وليس <T>.
  • سمة Mermaid على GitHub ثابتة — لا تُضمِّن كتل %%{init: ...}%%؛ إذ تُحذف عند العرض.
